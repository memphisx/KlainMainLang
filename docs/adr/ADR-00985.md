# ADR-00985: createServer async handler awaiting a task-promise on a fiber

- **Date**: 2026-09-17

## Context

A Node `http.createServer(async (req, res) => …)` handler whose body awaits a
**task-shaped** promise — the result of a call to a may-suspend async function,
e.g.

```ts
async function proxy(p: string): Promise<string> {
  const r = await fetch(UP + p)
  return await r.text()
}
const server = http.createServer(async (req, res) => {
  const v = await proxy(req.url)     // await of a task-promise, on the conn fiber
  res.writeHead(200); res.end("front:" + v)
})
server.listen(port)
```

crashed the server on a single request when the upstream `UP` was fast/instant.
The response was written correctly (the client received `front:…`) and *then*
the process died. Reproduced on both plain `http.createServer` (HTTP/1.1) and
`http2.createServer` (h2c). A slow upstream let a lone request survive;
concurrency and/or a fast upstream crashed it — a classic timing-dependent
memory corruption.

Symptoms were build-dependent, the signature of the heap already being trashed:
under `-O2` on HTTP/1.1, a `SIGABRT` from `_os_unfair_lock_unowned_abort` (macOS
malloc's own per-zone lock) three frames deep in `__kml_http_send_response`'s
`malloc`/`sprintf`/`free`; under ASan, `stack-overflow` at an address where
`pc == bp == sp` — a return jumped to a garbage stack address (a smashed return
address), not depth recursion.

The coverage gap that let this rot: the existing passing test
`TestE2EHTTPListenAsyncHandlerAwaitFetch` uses the `klain:http` **return-value**
model (`return { status, body }`), whose handler awaits `fetch` directly. The
Node `ServerResponse` (`res.writeHead`/`res.end`) path with an async handler
awaiting a *task-promise* had no test.

## Investigation

`__kml_http_send_response` (`runtime_http.go`) is only the detonation site: its
`malloc`/`free` trip over heap metadata already corrupt. ASan did not flag the
overflowing store, pointing at a write across a `ucontext` stack switch (ASan
doesn't instrument `makecontext`/`swapcontext` stacks).

The discriminator: an async handler awaiting **`fetch` directly** never crashed.
`await fetch(...)` on a connection fiber goes through `__kml_await_fetch_headers`,
whose `maybeconn` block parks the fiber and yields to the reactor. Awaiting a
**task-promise** instead goes through `__kml_task_await_ready`.

`__kml_task_await_ready` branches on `@__kml_current_task == null` → `toploop`
(a top-level busy-drive that calls `__kml_task_sched_step`), else `ontask`. A
connection fiber is not a task (`current_task == null` on it), so an async
`(req,res)` handler awaiting a task-promise fell into `toploop`, which drove
`__kml_task_sched_step` **from the fiber**.

The bug was in `__kml_task_sched_step` itself. To resume a suspended task it did:

```
store ptr @__kml_main_ctx, ptr %task.resumerCtx
… swapcontext(ptr @__kml_main_ctx, ptr %task.ctx)
```

`swapcontext(oucp, ucp)` **saves the current context into `*oucp`**. Run from the
real main context (the ordinary case) that is harmless. Run re-entrantly from a
connection fiber (via `toploop`), it overwrites the global `@__kml_main_ctx` — the
event loop's own context and every fiber's `uc_link` — with the fiber's own
half-executed `toploop` frame. The resumed task returns there correctly, so the
`await` even completes and the response is sent; but `@__kml_main_ctx` is now a
stale in-fiber frame, and when the handler's fiber later returns through its
`uc_link` it jumps wild — the smashed return address / trashed heap that
`send_response` detonates on. A slow upstream hid it because the fiber parked
before `sched_step` had a resumable task to swap into (no clobber); a fast/instant
upstream had the task ready, so the clobbering swap fired.

`__kml_spawn_task` already faced this exact "a spawner may be a connection fiber
whose `uc_link` is `@__kml_main_ctx`" hazard and solved it (TDD-00097 Stage 5b) by
saving into a **local `alloca`** (`%callerctx`) rather than the global. An
alternative fix — giving the fiber its own park-and-yield path in
`__kml_task_await_ready` instead of busy-driving — was prototyped and rejected: it
corrupted the `ReadableStream` `pull` / `req.stream()` streaming paths
(`examples/streams/http_chunked.ts`, `http_upload.ts`), which drive task-promise
awaits on a fiber in contexts where a direct fiber-yield is unsafe.

## Decision

Make `__kml_task_sched_step` re-entrancy-safe, mirroring `__kml_spawn_task`:
resume a task through a **per-call `alloca` return slot** instead of the global
`@__kml_main_ctx`. The task's `resumerCtx` points at that local slot and its
suspend/finish swaps back into it, so `sched_step` never writes the global main
context and can be driven from a connection fiber's `toploop` without clobbering
the loop.

## Implementation notes

- `codegen/llvm/runtime_task.go`, `__kml_task_sched_step`: a `%saveslot = alloca
  [ctxSize x i8]` in the entry block; the resume block stores `%saveslot` (not
  `@__kml_main_ctx`) into the task's `resumerCtx` and swaps
  `swapcontext(%saveslot, task.ctx)`. `ctxSize` (from `ucontextLayout()`, already
  in scope) was prepended to the format args.
- The single `%saveslot` is safe to reuse across the scan loop's iterations:
  each resumed task fully returns into it before the next task is resumed. Nested
  `sched_step` (a fiber's `toploop` calling it) gets a fresh per-call slot.
- `store ptr null, @__kml_current_task` after the swap is unchanged: `sched_step`
  is only ever entered with `current_task == null` (the main loop, or a fiber's
  `toploop` — a fiber is not a task).

## Side effects discovered

- **Serialization (follow-up).** With `sched_step` safe, a fiber awaiting a
  task-promise keeps the `toploop` **busy-wait**: it drives the scheduler inline
  rather than yielding, so concurrent connections whose handlers await a
  task-promise **serialize** (measured: three requests behind a 400 ms upstream
  took ~1.2 s, not ~0.4 s). Awaiting `fetch` **directly** still yields and stays
  concurrent (`maybeconn`, unchanged). Node runs both concurrently, so this is a
  fidelity gap for the await-a-helper shape; a fiber-park that yields is the
  right fix but needs the streaming (`pull`/`req.stream`) contexts made safe
  first. Tracked in `docs/BACKLOG.md`.
- An async task-promise handler driven by an **in-process** `http.get` client now
  runs to completion correctly (verified via `examples/http/async_handler_proxy.ts`),
  but if the program then waits on that in-process client's own completion
  callback, the callback is not delivered and the process hangs — a distinct
  event-loop interaction, on a scenario that previously only crashed (so no
  regression). External clients (curl, Go `net/http`, browsers) are unaffected.
  Tracked in `docs/BACKLOG.md`.
- This confirms async h2 handlers already work (they run on the connection fiber,
  not synchronously inline), contradicting TDD-00218's central premise. The h2
  dispatch reuses the 1.1 path wholesale — `emitHTTP2PrefaceDivert` drives the
  nghttp2 session inside `__kml_http_dispatch`'s fiber, and `buildHTTP2Bridge`
  threads the same `isAsyncHandler` into the shared `emitHTTPCallHandler` — so an
  `await` yields the whole fiber (nghttp2 C frames included). TDD-00218 had
  over-generalized the one true synchronous fact (its `stream.on('data')` fires
  the body as a single buffered chunk at `END_STREAM`) into a false claim about
  the handler itself, without a repro. TDD-00218 is reconciled here: its Status
  moves to Partially Implemented with a dated correction note, and the stale
  "h2 handlers run synchronously" caveat and roadmap entry in the status data are
  corrected the same commit. Its remaining real work is a streaming h2 request
  body and h2 response flow-control.

## Verification

- `tests/http_test.go`: `TestE2EHTTPCreateServerAsyncHandlerAwaitFetch` (HTTP/1.1,
  four sequential + eight concurrent requests against an instant upstream) and
  `TestE2EHTTP2CreateServerAsyncHandlerAwaitFetch` (h2c via curl) — both fail
  (crash) before the fix, pass after.
- The saved ASan+UBSan probe that reported `stack-overflow` (smashed return
  address) before the fix reports clean after.
- `examples/http/async_handler_proxy.ts` added; `make examples` green (including
  `examples/streams/http_chunked.ts`/`http_upload.ts`, which the rejected
  fiber-park alternative broke).
- Machine: macOS arm64 (M4). A Linux recheck (the corruption was `ucontext`-path)
  is a reasonable follow-up.
