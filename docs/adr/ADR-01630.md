# ADR-01630: `process.kill` answers ESRCH for an exited process on Windows

- **Relations**: Extends ADR-00737
- **Date**: 2026-10-14

## Context

Node's `test-process-kill-null` failed on Windows: `process.kill(pid, 0)`
after the child's `'exit'` returned `true` where Node throws.

## Investigation

`kill()` (`win32proc.c`) answered signal 0 by opening the process. A process
that has exited opens fine while a handle to it is still held (its parent's,
until reaped). libuv's `uv_kill` reads the exit code: anything but
`STILL_ACTIVE` is `UV_ESRCH`. Its terminate path does the same when
`TerminateProcess` fails, where ours said EACCES.

## Decision

- Signal 0 opens the process with query rights and calls `GetExitCodeProcess`:
  `STILL_ACTIVE` is alive, any other code is ESRCH, and a failed query is
  EACCES.
- The terminate path opens with query rights as well; a failed
  `TerminateProcess` on a process whose exit code is no longer `STILL_ACTIVE`
  is ESRCH.

## Implementation notes

`win32src/win32proc.c`. A reaped child of this process was already ESRCH from
the child table (ADR-00737); this covers a pid that is not, or not yet.

## Verification

Windows 11: Node 24.19 and ours print `alive true / ESRCH / ESRCH` for a
child killed with SIGKILL and probed with 0 and SIGTERM after `'exit'`.
`TestE2EProcessKillZeroAfterExitThrowsESRCH` (every host) and Node's
`test-process-kill-null` pass.
