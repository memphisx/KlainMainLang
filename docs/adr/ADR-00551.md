# ADR-00551: JS minimum-digit exponent for toExponential/toPrecision

- **Relations**: Extends ADR-00065
- **Date**: 2026-09-01

## Context

`Number.prototype.toExponential` and `toPrecision` format via C's
`sprintf("%.*e"/"%#.*g")`, whose exponent is always at least two digits with a
sign (`1.23e+03`). Real JS uses the minimum digit count (`1.23e+3`). This
cosmetic deviation was the *only* disclosed caveat on `toExponential` and one
of two on `toPrecision`.

## Investigation

The value bytes printed by glibc are otherwise correct; only the exponent
field needs its leading zeros trimmed. A shared post-processing step over the
formatted buffer is the minimal fix. While testing, a *separate* pre-existing
`toPrecision` divergence surfaced: C `%g` switches to exponential notation when
the decimal exponent is `< -4`, whereas JS's `toPrecision` switches at `< -6`,
so `(0.0000123).toPrecision(3)` yields `"1.23e-5"` here vs `"0.0000123"` in JS.
That is a distinct notation-selection issue, not an exponent-format one, and is
now disclosed as `toPrecision`'s remaining caveat (fixing it means bypassing
`%g`'s notation choice — deferred as separate work).

## Decision

Add `__kml_strip_exp_zeros(ptr) -> i64`: finds the first `e`/`E`, skips an
optional sign, drops leading `0` digits from the exponent while keeping at
least one digit (`e+00` → `e+0`), memmoves the tail (incl. NUL) left, and
returns the new length. `toExponential` calls it before finalizing the string;
`toPrecision` calls it right after `sprintf` and uses the returned length for
its existing trailing-`.` trim. A buffer with no `e`/`E` is returned unchanged.

## Implementation notes

- Runtime function in runtime_core.go, guarded by `usedStripExpZeros`; pulls in
  `strlen` + `memmove`.
- `toExponential` is now caveat-free (strict). `toPrecision` keeps the
  notation-threshold caveat above, so it remains non-strict for a real reason.

## Side effects discovered

The `%g` exponential/fixed threshold divergence on `toPrecision` (see
Investigation) — documented as that row's caveat, not fixed here.

## Verification

`TestE2ENumberToExponential` (updated to the min-digit form: `1.23e+3`, `1e+0`,
`1.235e+5`) and `TestE2ENumberToPrecisionExponentMinDigits` (`1.2e+5`,
`1.23e+6`) pass, along with the existing toPrecision tests. Built and verified
on Mac (Apple Silicon).
