# ADR-01024: Windows timer resolution — high-resolution timer packets + QPC deadlines

- **Relations**: `Implements TDD-00183` (Stage 4); `Extends ADR-00865` (Stage 1), `ADR-01022` (Stage 2 — the completion-port wait this bounds)
- **Date**: 2026-09-20

## Context

Stage 2 (ADR-01022) made the reactor's wait one `GetQueuedCompletionStatusEx`, bounded by the caller's deadline. But two millisecond-granularity primitives sat under it:

- The deadline itself was computed from `GetTickCount64`, whose resolution is the system clock tick (~15.6 ms, and unaffected by `timeBeginPeriod`).
- `GetQueuedCompletionStatusEx`'s timeout is a `DWORD` of milliseconds that the kernel rounds up to the current timer resolution — ~15.6 ms by default.

Together a 50 ms `setInterval` fired about every 62 ms (`4 × 15.6`), and `event_loop_wait_test.go`'s `minTicks` had to stay loose to tolerate it. `usleep`/`nanosleep` were `Sleep`-based with the same quantisation. This is TDD-00183 Stage 4 ("QPC deadlines, high-res waitable timer packets, last `Sleep`-slice remnants removed, `usleep` precision").

## Decision

Deadlines are taken from `QueryPerformanceCounter` in microseconds (`kml_now_us`, computed `sec*1e6 + frac` so a multi-day-uptime counter cannot overflow `int64`), replacing every `GetTickCount64` in `select()`.

The wait is ended at the real deadline by a **per-thread high-resolution waitable timer**: `CreateWaitableTimerExW(…, CREATE_WAITABLE_TIMER_HIGH_RESOLUTION, …)` (the ~0.5 ms timer Windows 10 1803+ exposes). Its expiry reaches the reactor as a **completion packet on the thread's own port**, as TDD-00183 specified: a per-thread wait completion packet (`NtCreateWaitCompletionPacket`) is associated with the armed timer (`NtAssociateWaitCompletionPacket`, completion key `KML_KEY_TIMER`), and `select()` then blocks in the existing `GetQueuedCompletionStatusEx` with no timeout. `kml_port_drain` dequeues the timer packet and ignores it — unlike a bare wake packet it does not raise `kml_woken`, so it only ends the wait and the loop re-evaluates its deadline. A real I/O packet ends the wait first when one arrives; on the way out the timer is cancelled and the association disarmed with `NtCancelWaitCompletionPacket(…, RemoveSignaledPacket = TRUE)`, so a stale expiry cannot surface in a later wait and the packet is free to be associated again.

**A timer APC is not an equivalent.** The first cut armed the timer with an APC completion routine and relied on the alertable port wait returning `WAIT_IO_COMPLETION`. Measured, that path stays quantised: the timer is precise, but the APC's delivery to the blocked thread is not — a 49 ms wait still took ~62 ms, and a server with a 50 ms `setInterval` still ran twenty ticks in ~1250 ms. It went unnoticed because a timers-only program never reaches `select()` (it sleeps in `nanosleep`, which waits on the timer directly and was precise). The APC route is kept only as the fallback where wait completion packets do not exist (pre-Windows 8).

`usleep`/`nanosleep` share one helper, `__kml_win_hr_sleep_us`, which arms the same high-resolution timer and `WaitForSingleObject`s it. `nanosleep`'s signal-aware path (a handler is installed, ADR-00728) keeps its ≤ 50 ms slices between signal checks, but each slice is now a high-resolution sleep against a QPC deadline — it was `GetTickCount64` + `Sleep`, which put any program with a `process.on(<signal>)` handler back on the ~15.6 ms tick.

**Fallbacks, no new hard dependency.** The timer and wait-completion-packet entry points are resolved with `GetProcAddress` (the file's established pattern for `Nt*`/`AcceptEx`), so no import-library or newer-header dependency is added and a machine without them degrades in steps: no wait completion packets → the timer APC; no high-resolution flag → a plain waitable timer; no timer API at all → the previous coarse millisecond `kml_port_drain(ms)` / `Sleep`. The lazy resolve publishes its "done" flag only after the pointers are written, because a worker thread can reach its first wait alongside the main loop. Deliberately **not** `timeBeginPeriod(1)`: it raises the timer resolution process- (really system-) wide for power the loop does not need, which is the cost TDD-00183 chose the waitable timer to avoid.

The one remaining bounded wait is unchanged and still documented: an anonymous pollable pipe caps the wait at a 10 ms re-probe (ADR-01022), which no emitted-IR path produces.

## Implementation notes

- All in `codegen/llvm/win32src/win32io.c` (timer + packet helpers, `select()` deadline + wait, the drain's `KML_KEY_TIMER` case) and `win32shim.c` (`nanosleep`, both paths).
- The `KML_IO_TRACE` `[io] wait slice=N` line is retained (N is now the milliseconds until the deadline, `-1` for an infinite wait) so `reactor_windows_test.go`'s blocking-wait count still reads it. It is still exactly one blocking wait per timer period.
- The timer, the packet and their "already tried" flags are `_Thread_local`, like the port: a worker thread's loop gets its own, created lazily on first blocking wait.
- The other `kml_port_drain(-1)` callers (blocking `accept`/`connect`) loop on their own condition, so a dequeued timer packet is harmless to them.

## Verification

Windows dev box (Windows 11 26200, MSYS2 UCRT64 clang). Twenty 50 ms `setInterval` ticks, three runs each, before → after:

- timers-only (the `nanosleep` path): ~1250 ms → 1005–1007 ms.
- with a `SIGINT` handler installed (`nanosleep`'s sliced path): ~1250 ms → 1005–1007 ms.
- with an HTTP server listening (the reactor's `select()` path): ~1250 ms → 1011–1013 ms, one blocking wait per tick in the trace.

`tests/timer_precision_windows_test.go` guards all three as subtests. `win32io.c`/`win32shim.c` compile clean; `go build`, `go vet ./...` clean. Regression: the timers, reactor (Windows), event-loop-wait, net, dgram, HTTP/fetch, TLS, worker, cluster, child-process, signal, TTY/ConPTY, stdin and readline suites. Linux/macOS untouched (Windows-only C, behind the same shim boundary); CI's POSIX lanes are the guard.
