# ADR-00138: `symbol` V1 (opaque unique values)

- **Relations**: Implements [TDD-00044](../tdd/TDD-00044.md)
- **Date**: 2026-08-09

## Context

`docs/status/TYPE-SYSTEM.md` listed `symbol` at 0% — no lexer, parser, or codegen trace anywhere. [TDD-00044](../tdd/TDD-00044.md) scoped a V1: a guaranteed-unique opaque token (`Symbol()`/`Symbol("desc")`), comparable with `===`/`!==`, readable via `.description`, printable via `.toString()`/`console.log`/template literals — deliberately excluding dynamic property keys and well-known symbols (`Symbol.iterator`, `Symbol.for`), which this compiler's fixed-shape-object model can't support without a much larger, separate design effort. This ADR documents building exactly that scope.

## Investigation

Traced how the closest existing precedents work before designing anything new:

- `URLType()`/`HeadersType()` (`codegen/llvm/types.go:343`) — both a plain `ObjectType([]Field{...})` plus a marker flag (`IsURL`/`IsHeaders`) so special-case dispatch sites can recognize them; field reads (`.protocol`, etc.) come for free from the generic `IsObject` GEP machinery. Directly reused for `SymbolType()`.
- `emit_exprs_operators.go`'s generic `===`/`!==` comparison switch: already lowers to `icmp eq/ne ptr` for any `IsObject`-shaped pointer (excluded from the string-comparison branch at `:100` by `!ty.IsObject`). This meant Symbol's uniqueness didn't need an id/counter field at all — two separate heap allocations already have distinct addresses, so pointer identity alone gives correct `===` semantics for free.
- `structuredCloneUnsupportedKind` (`emit_structured_clone.go:45`) — an existing reject-list pattern, checked *before* the generic `IsObject` deep-clone path specifically so special `IsObject`-shaped types (`URL`, `Map`, etc.) aren't silently mishandled by it.
- `emitJSONStringifyValue` (`emit_call_json.go:179`) — checks `val.Ty.IsObject` *first*, before anything else. This is the one real correctness risk found during design, not just implementation: reusing `IsObject` for Symbol's storage means this check would silently serialize a Symbol as `{"description":"..."}` unless given its own, earlier carve-out. Confirmed this by reading the code before writing any of the new code, not discovered by trial and error.
- `emitVarDecl`'s pre-inference `switch callee.Name` for bare-identifier calls (`emit_exprs_vardecl.go:89`, alongside `btoa`/`structuredClone`) — this exists specifically because an *unannotated* `const x = someBuiltinCall()` needs its declared storage type inferred before `ty.IsObject` is known to route into `emitObjectVarDecl`. Missed on the first implementation pass (see below) and confirmed as a real, reproducible bug, not a hypothetical.

## Decision

`Type` gains `IsSymbol bool` (`codegen/llvm/types.go`, alongside `IsURL`). `SymbolType()` returns `ObjectType([]Field{{Name: "description", Ty: TypePtr}})` with `IsSymbol` set — a genuine 1-field heap struct, no id/counter field (see Investigation). `ResolveTypeName` gains `case "symbol": return SymbolType()` for `symbol`-typed annotations.

New `emit_symbol.go`: `emitSymbolConstructor(args, pos)` (malloc + GEP-store `description`, defaulting to `""` when omitted, rejecting >1 argument or a non-string argument) and `emitSymbolToString(val)` (GEP-load `description`, concatenate into `"Symbol(desc)"`) — the latter shared by three call sites (`.toString()`, `console.log`, template-literal interpolation), a deliberate V1 simplification: real JS throws on template-literal interpolation of a Symbol specifically, but this compiler treats all three the same way rather than adding a fourth, stricter code path.

Every dispatch site keyed on `ty.IsObject`/`ty.IR == "ptr"` that would otherwise mishandle a Symbol got an explicit `IsSymbol` carve-out, checked first: `typeofString` (→ `"symbol"`), `emitBinary` (reject every operator except `===`/`!==`/`==`/`!=`), `emitValueToString` (template literals), `emitConsolePrint` (`console.log`), `emitJSONStringifyValue` (clean reject, not silent mis-serialization — the real risk found during design), `structuredCloneUnsupportedKind` (clean reject, matching real JS's `DataCloneError`). `new Symbol(...)` needed no new code: it falls through to the pre-existing "unknown class" rejection any unregistered `new` target already produces.

## Implementation notes

Files touched: `codegen/llvm/types.go` (`IsSymbol` flag, `SymbolType()`, `ResolveTypeName` case), `codegen/llvm/emit_symbol.go` (new — constructor + shared formatter), `codegen/llvm/emit_call.go` (`Symbol(...)` construction dispatch, `.toString()` method dispatch), `codegen/llvm/emit_exprs_types.go` (`inferExprType`'s `Symbol(...)` case, `emitValueToString`'s `IsSymbol` branch), `codegen/llvm/emit_exprs_operators.go` (`typeofString`, `emitBinary`'s operator-reject guard), `codegen/llvm/emit_call_console.go` (`console.log` formatting branch), `codegen/llvm/emit_call_json.go` (`JSON.stringify` reject), `codegen/llvm/emit_structured_clone.go` (`structuredClone` reject), `codegen/llvm/emit_exprs_vardecl.go` (unannotated-`const`/`let` type inference — see Side effects below).

`Memory.free(sym)` needed zero new code: `freeResolvedPointer`'s existing `ty.IsObject` branch already frees the struct correctly (shallow free, same semantics as every other object type) — confirmed by a manual repro (see Verification), not just read from the code.

## Side effects discovered

Found and fixed one real, reproducible bug during implementation, not anticipated by the TDD: `emitVarDecl`'s pre-inference switch for unannotated bare-identifier calls (`emit_exprs_vardecl.go:89-97`, the same switch that already special-cases `btoa`/`structuredClone`) had no `"Symbol"` case. `const noDesc = Symbol()` (no type annotation) fell through to that switch's `default:` arm, which only recognizes registered user functions — `ty` stayed at the surrounding scalar default (`TypeI64`), so `noDesc` got allocated as a plain `i64` slot instead of a Symbol-typed one. This didn't surface as a compile error immediately: `noDesc.toString()` still "worked" by silently routing through the numeric `isNumberTy`-gated `.toString()` dispatch instead (since the misinferred type's `IR` was `"i64"`), and only `noDesc.description` (a field read with no numeric equivalent to fall back to) actually produced a compile error ("field access on non-object"). Fixed by adding the missing `case "Symbol": ty = SymbolType()` alongside the existing `structuredClone` case. Filed here rather than separately since it has no reachable path without `Symbol()` existing at all.

## Verification

- `go build -o klainmain .`, `go vet ./...`, `go test ./...` all pass (Linux x86-64 box).
- New tests, `tests/symbol_test.go`: `TestE2ESymbolUniqueness`, `TestE2ESymbolTypeofAndDescription`, `TestE2ESymbolToStringAndFormatting`, `TestE2ESymbolArithmeticRejected`, `TestE2ESymbolDescriptionMustBeString`, `TestE2ESymbolTooManyArgs`, `TestE2ESymbolNewIsNotAConstructor`, `TestE2ESymbolJSONStringifyRejected`, `TestE2ESymbolStructuredCloneRejected`, `TestE2ESymbolMemoryFree` — all pass.
- New example `examples/types/symbol.ts`, compiled and run directly (not just via the test harness); output matches every inline comment exactly, including the blank-line case for an omitted description.
- Manually verified every reject path at the CLI (`klainmain <file>.ts`) produces the intended clean compile error rather than a crash or silent misbehavior: `<` between two symbols, `new Symbol(...)`, `Symbol(1)` (non-string description), `Symbol("a", "b")` (too many args), `JSON.stringify(symbol)`, `structuredClone(symbol)`.
- Manually verified `Memory.free(sym)` (manual mode) frees cleanly with no crash, both before and after the free.
