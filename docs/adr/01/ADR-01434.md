# ADR-01434: Class-typed unbound names; `any` arithmetic and bigints

- **Relations**: Implements TDD-00230 (P2.2), Extends ADR-01431
- **Date**: 2026-10-07

## Context

Two shadow buckets after ADR-01433 were codegen answers, not oracle gaps:

- `internal_timers.ts`'s `prevImmediate !== null ? prevImmediate._idleNext
  : null` read as `i64` where the checker types an `Immediate`;
- `after * 1` with `after: any` held as a boxed `any` where the checker
  types `number`.

## Investigation

- The first is read by `crossTypeWidenedBindings`, a body pre-pass that
  runs before the body's locals are bound. ADR-01431's checker fallback
  answered it, but through the context-free representation, which has no
  class arm, so `Immediate | null` had no answer and the name fell to the
  number default.
- For `- * / % **` the `any` operand dispatch already computes a double and
  boxes it. When the other operand is a number, the result is a number: an
  `any` holding a bigint cannot mix with a number (that is a TypeError).
  With two `any` operands a bigint result is possible, so that case stays
  boxed (tsc types it `number` regardless).
- Probing the bigint side: every `- * / % **` on `any` operands ran
  ToNumber, so `x * y` with two `any` bigints printed NaN (Node: `12n`)
  and a bigint against a number printed NaN instead of throwing the
  TypeError. Three causes:
  - the operator dispatch had no bigint arm unless an operand was
    statically a bigint;
  - the runtime ToPrimitive treated a boxed bigint's cell (tagged as an
    object) as an object to convert;
  - tsc types `any * any` as number, and codegen takes the checker's type
    for a function's return (ADR-01427) and for a variable read, so a
    bigint result was unboxed as a double.
- Whether a program can hold a bigint is known only once one is emitted;
  a function emitted earlier would miss the bigint arm.

## Decision

- The unbound-name fallback represents the checker's type with codegen's
  class registry (object types still keep the old inference).
- An arithmetic operator between an `any` and a non-bigint number yields an
  unboxed double, in both the emitter and inference.
- Arithmetic on boxed operands checks at run time for a bigint: both
  bigints run the bigint operation, one throws the spec's TypeError, none
  takes the number path. With a number on the other side only the `any`
  operand is tested (`__kml_any_is_bigint`, boxsrc/toprim.c), a bigint
  can only throw, and the operation runs on doubles with no box: a first
  cut boxed the double and unboxed it again for the caller, which grew
  the frame of Test262's `tco-catch.js`/`tco-finally.js` from 72 to 88
  bytes, and their 100000 recursive `f(n - 1)` calls overflowed the 8 MB
  stack on Linux (they pass with no margin to spare either way). The check is emitted when the program can make a
  bigint (a `123n` literal or a `BigInt…` name anywhere in it, the builtin
  modules included, scanned once before emission).
- ToPrimitive returns a boxed bigint unchanged (a primitive).
- The checker types an arithmetic operator on two `any` operands as a
  distinct number (`Type.AnyArith`): `number` for every relation and
  diagnostic, held as `any` by `reprOf` and by every codegen site that
  maps the checker's number to a double. In a union it absorbs plain
  numbers and number literals (`c ? a * b : 1` stays boxed).

## Verification
`TestE2EAnyNumberArithmeticUnboxed`, `TestE2EAnyBigIntArithmetic` (against
Node); checker and binder unit tests. Gates on this tree (Linux, kmlbox):
test-par on Node304, examples 396/396 and Test262 strict on DeskMini (8411,
two new, none lost), Test262 js on Node304 (10835, two new, none lost),
neither with invalid IR.
