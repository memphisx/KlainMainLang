# ADR-00062: Classes Stage 0 — lexer/parser/AST groundwork

- **Relations**: Implements [TDD-00009](../tdd/TDD-00009.md) (Stage 0 of 4)
- **Date**: 2026-07-27

## Context

[TDD-00009](../tdd/TDD-00009.md) scopes `class` support into four stages, with Stage 0 as the shared front-end prerequisite for all of them: new keyword tokens, a `ClassDeclaration` AST node, a generic `new UserClass(args)` AST node, and `this` as a parseable expression. The TDD's own investigation (grepping the lexer/parser for `class`/`extends`/`this`/`super`/`private`/`public`/`protected`/`static`/`implements`/`abstract`) had already confirmed none of it exists. Picked up as the first concrete slice of that TDD, per direct instruction to start Stage 0.

## Investigation

Re-confirmed the TDD's grep findings directly before writing any code — no `CLASS`/`THIS` token types in `lexer/token.go`, no `ClassDeclaration`/`ThisExpression` node in `ast/nodes.go`.

Looked for existing patterns to reuse rather than invent new ones:
- Every current `new X(...)` form (`NewArrayExpression`, `NewMapExpression`, `NewSetExpression`, `NewErrorExpression`, `NewDateExpression`) is parsed by `parser.parseNew` (`parser/parser.go`) switching on the literal callee name (`"Array"`, `"Map"`, `"Set"`, `"Error"`, `"Date"`) with a `default` case that hard-errored `'new %s' is not supported`. Confirmed no `new Response(...)` form exists either (Response is only constructed via `fetch()`), so a generic fallthrough for any other name is safe — no naming collision with a hardcoded form to worry about.
- `parser.parseInterfaceDecl` already implements exactly the field-list parsing a class needs: `IDENT`, optional `?`, `:`, a `TypeAnnotation`, with a JSDoc-comment override for the type (the same convention `parseVarDecl` uses). Reused verbatim rather than re-deriving.
- `parser.parseFunctionDecl` inlined its "parse `(params): retType { body }`" logic directly after consuming `function NAME`, with no way to reuse just that tail for a class method/constructor (whose name isn't preceded by a `function` keyword). Extracted the shared tail into `parseFunctionRest(name string, isAsync bool)`.
- `codegen/llvm/emit_stmts.go`'s `emitStmt` and `emit_exprs.go`'s `emitExpr` both already end with a generic `fmt.Errorf("unknown statement/expression type %T", ...)` fallback for anything unhandled — confirmed this produces a clean compiler error (not a panic) for any AST node codegen doesn't yet know about, which is exactly the failure mode wanted for `ClassDeclaration`/`ThisExpression`/generic `NewExpression` until Stage 1 lands.
- `resolver/resolver.go`'s `declNameOf`/`validateDeclarationsOnly` already enumerate every top-level declaration kind (function/var/interface/type alias/enum) for the cross-file uniqueness check and the "imported files may only contain declarations" rule. Per the TDD ("No new module-system work: a class is just one more top-level declaration kind"), added `*ast.ClassDeclaration` to both rather than inventing any class-specific module handling.

## Decision

**Lexer** (`lexer/token.go`): added `CLASS` and `THIS` keyword tokens (`tokenNames` + `keywords` map entries). Deliberately did *not* add `extends`/`super`/`private`/`protected`/`static`/`implements`/`abstract` — the TDD defers all of those to Stages 3-4, so code using them now hits a plain, unremarkable parse error (e.g. `class Foo extends Bar` fails with `expected {, got IDENT` since `extends` lexes as a plain identifier) rather than being silently accepted and ignored.

**AST** (`ast/nodes.go`): three new node types, following the file's existing constructor-function + unexported-`pos` pattern:
- `ClassDeclaration{Name, Fields []AnnotField, Constructor *FunctionDeclaration, Methods []*FunctionDeclaration}`. Fields carry no initializer — matching the TDD's own Stage 1 design, where a field is a pure type declaration and `this.field = value` statements in the constructor body do the initializing. Constructor/methods are literally `*FunctionDeclaration` (the TDD's own phrasing: "shaped like a FunctionDeclaration body but with an implicit receiver" — the receiver itself is a Stage 1 codegen concern, not part of this node's shape).
- `ThisExpression{}` — no fields beyond position; parses anywhere an expression can.
- `NewExpression{ClassName string, Args []Expression}` — the generic fallthrough for `new <Name>(...)` when `Name` isn't one of the five hardcoded builtins.

**Parser** (`parser/parser.go`):
- `parseStatement` dispatches `lexer.CLASS` to a new `parseClassDecl`, which parses `class Name { ... }`: each member is an `IDENT`, then either `(` (method or, if named exactly `"constructor"`, the constructor — parsed via the new `parseFunctionRest` helper; a second `constructor` member is a parse error) or `:` (a typed field, reusing `parseInterfaceDecl`'s field+JSDoc-override logic).
- `parseExportDeclaration`'s allowed-declaration switch gained `*ast.ClassDeclaration`, so `export class Foo {...}` works like `export function`/`export interface` already do.
- `parsePrimary` gained a `lexer.THIS` case returning `ast.NewThisExpression`.
- `parseNew`'s `default` case now calls `parseNewGenericBody`, which parses `(args)` the same comma-separated-`parseAssignment` way `parseNewDateBody`/`parseNewErrorBody` already do, returning a generic `ast.NewExpression`.

**Resolver** (`resolver/resolver.go`): `*ast.ClassDeclaration` added to `declNameOf` (participates in the cross-file name-uniqueness check) and to `validateDeclarationsOnly`'s allowed set (a class can be declared in an imported non-entry file, same as an interface or function). Updated the package doc comment's declaration-kind list to match.

**Codegen**: no changes. `ClassDeclaration` reaching `emitStmt`, and `ThisExpression`/`NewExpression` reaching `emitExpr`, fall through to the existing generic `"unknown statement/expression type %T"` errors. This is intentional — Stage 1 (a separate piece of work) replaces these with real emission; producing a clean, expected error now rather than silently no-op'ing or panicking is the correct Stage 0 behavior.

## Implementation notes

Files touched: `lexer/token.go`, `ast/nodes.go`, `parser/parser.go`, `resolver/resolver.go`. No codegen files touched, by design.

`parseFunctionRest` is a genuine refactor, not just new code: `parseFunctionDecl` now consumes `function NAME` and delegates the rest to it, so top-level functions and class methods/constructors share one implementation of "parse the params/return-type/body tail" instead of duplicating it.

No modifier keywords (`private`/`static`/etc.) are recognized on class members in Stage 0 — encountering one produces a parse error rather than being skipped, consistent with the TDD explicitly deferring them to Stage 4 and with the decision (above) to not special-case `extends` either.

## Side effects discovered

None. This is pure additive front-end surface; no existing behavior changed. Confirmed via the full existing test suite passing unchanged, plus a regression test (`TestNewBuiltinFormsUnaffected`) specifically guarding that the new generic `new` fallback doesn't swallow any of the five pre-existing hardcoded `new` forms.

## Verification

- `go build -o klainmain .` and `go test ./...` — all green (`tests/` E2E suite, `lexer`, `parser` packages).
- New unit tests: `lexer/lexer_test.go`'s `TestKeywords` extended with `class`/`this`; `parser/parser_test.go` gained `TestClassDeclaration` (fields + constructor + method), `TestClassDeclarationExport`, `TestNewExpressionGeneric`, `TestNewBuiltinFormsUnaffected` (regression guard), `TestThisExpression` (bare `this` and `this.x`), plus a duplicate-constructor case added to `TestParseError`.
- Manual repro: a `.ts` file declaring a `Point` class with a constructor and a method, plus `new Point(3, 4)`, parses successfully and fails at codegen with exactly `codegen error: unknown statement type *ast.ClassDeclaration` — confirmed this is a clean compiler error, not a panic. A second manual repro (`class Foo extends Bar {}`) confirmed the expected plain parse error (`expected {, got IDENT`) since `extends` isn't supported yet.
- No `tests/` E2E test or `examples/` entry added this stage — per explicit decision, since nothing produces a runnable binary until Stage 1 exists; adding one now would either be untestable (nothing executes) or would need to assert on a codegen error message, which isn't the "feature" `tests/`/`examples/` are meant to demonstrate. Deferred to Stage 1's ADR.
