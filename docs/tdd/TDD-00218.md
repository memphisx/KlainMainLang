# TDD-00218: asynchronous HTTP/2 request handlers

- **Status**: Partially Implemented
- **Notes**: Premise corrected — async h2 handlers already work ([ADR-00985](../adr/ADR-00985.md), and this TDD's Update note); the real remaining work is Stages 2–3 (streaming request body, h2 response flow-control). [TDD-00230](TDD-00230.md) phase 4 drives nghttp2 from libuv read callbacks outside any fiber, so the per-stream fiber and deferred data provider set aside in the Update become required there.
- **Date**: 2026-09-16

## Update (2026-09-17)

The Context below is wrong on its central premise, and the correction is worth
recording as much as the remaining work: **async h2 handlers already work.** An
`await` inside an `http2.createServer` handler yields and resumes exactly as on
HTTP/1.1, and concurrent h2 connections each awaiting a fetch overlap rather than
serialize — verified empirically (`tests/http_test.go`,
`TestE2EHTTP2CreateServerAsyncHandlerAwaitFetch`; [ADR-00985](../adr/ADR-00985.md)).

Why the premise was false: the h2 dispatch is *not* a synchronous call on the
main context. `emitHTTP2PrefaceDivert` drives the whole nghttp2 session
(`__kml_h2_session_recv`) from *inside* the connection fiber (`__kml_http_dispatch`),
and `buildHTTP2Bridge` threads the same `isAsyncHandler` flag as the 1.1 path
into the shared `emitHTTPCallHandler` (`emit_http.go`). So an `await` inside a
handler `swapcontext`s the entire fiber — nghttp2's C frames included — back to
the reactor, just like 1.1. Async h2 handlers worked from the moment the h2
dispatch was unified with the 1.1 dispatcher.

Where the false premise came from — the documentation lesson: the one genuinely
synchronous thing is *request-body delivery*. `stream.on('data')` fires the whole
body as a single chunk at `END_STREAM` (the accurate "V1 synchronous delivery"
comment at `emit_http.go`, quoted below as the second consequence). That true
body-buffering fact was over-generalized, without a repro, into a false claim
that the *handler* runs synchronously and an `await` cannot yield — and then
copied into a status caveat and roadmap entry. (The Context even cites
`http2src/http2.c`; the file is at `codegen/llvm/http2src/http2.c` — a tell that
it was written from reading comments rather than running the case.) A ✅/claim
needs an actual repro before it is written down, not after a user hits the gap.

What actually remains, re-scoped: **Stage 2** (streaming request body via
`on_data_chunk_recv` → `on('data')`, rather than one buffered chunk) and **Stage
3** (h2 response backpressure/flow-control parity with the 1.1 `res.write` path).
Stage 1 as *designed* below (per-stream fibers + nghttp2 data-provider deferral)
was never built and is not needed for the await-yields capability it targeted;
if Stages 2–3 end up wanting a per-stream fiber model, that is a fresh design
decision for their ADR, not a debt carried from here.

The original Context and design below are left intact as the historical record
(house rule: a TDD's design body is not rewritten post-hoc).

## Context

Over HTTP/1.1, a `createServer` handler runs on the connection's own fiber, so an
`await` inside it (e.g. `await fetch(...)`) parks that fiber and the reactor keeps
serving others (`emit_http.go`, the `swapcontext`-based dispatch). Over **HTTP/2**
the handler instead runs **synchronously**, inline inside nghttp2's
`on_frame_recv` callback once `END_STREAM` arrives, with the whole request body
already assembled (`http2src/http2.c:184-201`, "V1: synchronous handlers"). Two
consequences, both surfaced as a status caveat:

- An `await` inside an h2 handler cannot yield — there is no fiber wrapping the
  nghttp2 callback to swap out to; returning early from `on_frame_recv` would hand
  control back to nghttp2 before the response exists.
- The core-streams view of the request (`stream.on('data')`) delivers the entire
  body as a single chunk, because dispatch only fires after the body is fully
  buffered at `END_STREAM` (`emit_http.go`, "V1 synchronous delivery").

This was split out of the `http.createServer` "edges" backlog bullet (its
timeouts and `highWaterMark` shipped as TDD-00217/ADR-00983-00984); it is a
distinct, self-contained h2 feature, not a loose end of those.

## Problem shape

The blocker is structural, not a missing API: the nghttp2 session driver owns the
call stack while a handler runs. To make h2 handlers async we need the same
fiber-per-request model the 1.1 path has, adapted to nghttp2's callback-driven
I/O:

1. **Run each h2 request dispatch on its own fiber** (a `ucontext` + stack, as
   `__kml_http_append_conn` builds for a 1.1 connection), entered from
   `on_frame_recv` at `END_STREAM` instead of a direct synchronous call. An
   `await` inside then `swapcontext`s back to the reactor exactly as on 1.1.
2. **Resume + respond via a data-provider.** nghttp2 pulls response bytes through
   a `nghttp2_data_source_read_callback`; the response can be produced
   incrementally as the handler's fiber makes progress, with `NGHTTP2_ERR_DEFERRED`
   while the fiber is still parked and `nghttp2_session_resume_data` when it
   advances. This is the integration point between the fiber scheduler and the
   nghttp2 driver that V1 skipped.
3. **Streaming request body.** Deliver `on('data')` per `on_data_chunk_recv`
   callback rather than one buffered chunk at `END_STREAM`, so a large h2 upload
   streams — the same `Uint8Array`-chunk shape the 1.1 `req.stream()` path uses.

## Open questions

- Whether to reuse the 1.1 connection-fiber array/scheduler wholesale (one fiber
  per active h2 *stream*, many per connection) or a dedicated per-session fiber
  pool — h2 multiplexes many concurrent streams over one socket, unlike 1.1's one
  request per connection at a time.
- Flow control: honoring `WINDOW_UPDATE`/`DATA` framing while a fiber is parked
  mid-response, so a slow h2 consumer applies backpressure the way the 1.1
  `res.write` path now does (TDD-00214).
- Interaction with the h2-over-TLS accept path (TDD-00191 Stage 4) and whether the
  connection-timeout sweep (TDD-00217) extends to h2 streams.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| fiber scheduler (`ucontext` + reactor resume) | Built | the 1.1 connection-fiber model |
| nghttp2 session driver | Built | `http2src/http2.c`, synchronous dispatch |
| streaming request body (`Uint8Array` chunks) | Built (1.1) | `req.stream()` / core `Readable` |
| nghttp2 data-provider deferred/resume | Missing | the core new integration |

## Staging

- **Stage 1** — per-stream fiber + data-provider deferral, so an `await` inside an
  h2 handler yields and resumes (the response still produced whole, but
  asynchronously).
- **Stage 2** — streaming request body (`on_data_chunk_recv` → `on('data')`).
- **Stage 3** — response backpressure / flow-control parity with the 1.1
  `res.write` path.
