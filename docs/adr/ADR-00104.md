# ADR-00104: Array/Map/Set/EventEmitter literals as general expressions

- **Relations**: Implements [TDD-00028](../tdd/TDD-00028.md); surfaced and split out [TDD-00029](../tdd/TDD-00029.md) (array-of-arrays storage)
- **Date**: 2026-08-05

## Context

`emitExpr`'s core dispatch (`codegen/llvm/emit_exprs.go`) had no real case for `*ast.ArrayLiteral`, `*ast.NewArrayExpression`, `*ast.NewMapExpression`, `*ast.NewSetExpression`, or `*ast.NewEventEmitterExpression` — every one of them unconditionally errored ("array literal must be used in a variable declaration", etc.) the moment any of them appeared anywhere other than directly as a `const`/`let` initializer. Concretely, none of these compiled before this ADR: an array literal as a call argument or return value, as an object-literal field value, on the right-hand side of a plain reassignment (no `let`/`const`), or as an element of another array literal.

Found while implementing generics ([ADR-00103](ADR-00103.md)) — `first([1,2,3])` failed identically to a plain, non-generic `firstNum([1,2,3])`. Already a known, named boundary before that too: [ADR-00057](ADR-00057.md) found the same restriction blocking `number[][]` literals and documented it in `docs/status/ARRAY-METHODS.md` as a "known limitation." Revisited at the user's explicit request, with a sharper framing: `[1,2,3]` failing to pass as a function argument is a basic, unannounced ergonomics gap, not a limitation a user could reasonably be expected to already know about. See [TDD-00028](../tdd/TDD-00028.md) for the design this ADR implements.

## Investigation

Confirmed the fix splits into two genuinely different-sized pieces:

- **`Map<K,V>`/`Set<T>`/`EventEmitter<T>`**: trivial. `emitMapVarDecl`/`emitSetVarDecl`/`emitEventEmitterVarDecl` (`emit_collections.go`/`emit_eventemitter.go`) already computed a single heap pointer and only stored it into an alloca because the caller was hardwired to a `*ast.VarDeclaration` — no new codegen needed, just factoring the pointer-creation logic out so a general-expression path can reuse it.
- **Array literals / `new Array<T>(n)`**: real new codegen. `emitArrayVarDecl` (`emit_arrays_core.go`) wrote a literal's malloc'd data pointer and length directly into two caller-supplied allocas (the "Named Symbol" array representation) — there was no path that built a literal's malloc-and-populate loop and returned the `{ptr, i64}` **aggregate** `Value` this compiler already produces for a function's own array-typed return value (and already consumes in several places: `emitArrayVarDecl`'s own call-expression branch, `resolveArrayForHOF`, `resolveArrayDataPtr`). Also found a *third*, independently-duplicated version of the same "malloc + populate a literal" logic in `resolveArrayDataPtr`'s own `*ast.ArrayLiteral` case (used for array destructuring), with no hint-awareness at all.

Confirmed the same gap also blocked plain reassignment (`emit_exprs_assign.go` had no `*ast.ArrayLiteral` right-hand-side handling) and that a nested array literal (`[[1,2],[3,4]]`) hit the identical wall for its inner literal.

## Decision

Two fixes, landed together but genuinely different in shape:

**Map/Set/EventEmitter**: factored the shared heap-pointer-creation logic (`emitMapOrSetCreate` for Map/Set — Set reuses the same string-keyed-vs-numeric-keyed runtime Map already provides, keyed on element type alone) out of each var-decl function into its own small helper; each var-decl function now calls a new `emitNewMapValue`/`emitNewSetValue`/`emitNewEventEmitterValue` (returning a plain `Value`) and stores its result into the var-decl's alloca, while `emitExpr` calls the same three functions directly for the general-expression case.

**Array literals / `new Array<T>(n)`**: new `emitArrayLiteralAggregate`/`emitNewArraySizedAggregate` (`emit_arrays_core.go`) build the malloc-and-populate logic once and return the `{ptr, i64}` aggregate via `insertvalue` — the same shape every existing aggregate consumer already expects, so nothing downstream needed to change to accept a literal built this way. `emitArrayVarDecl` was refactored to call through these (extracting via a new shared `storeArrayAggregateInto`) rather than keeping a separate, duplicated direct-to-alloca implementation; `resolveArrayDataPtr`'s own duplicate was replaced with a call to the shared `emitArrayLiteralData` (the non-spread half of the aggregate builder). `emitSpreadArrayLit` was renamed `emitSpreadArrayLitData` and changed to return `(dataReg, lenReg, err)` instead of storing into caller-supplied allocas, so both the var-decl path and the new aggregate path share one spread-array-literal implementation.

**Hint propagation**: `emitExprWithObjectHint` (`emit_objects.go`) — previously only special-casing an object literal against a known object-typed hint (TDD-00007) — gained an array-literal branch (and a `new Array<T>(n)`-with-no-explicit-`<T>` branch), delegating to the new aggregate builders with the hint's element type. Kept the existing name despite now covering both literal kinds, to avoid a purely mechanical rename across its many pre-existing call sites (call arguments, function defaults, rest-param elements, nested object-literal fields, `EventEmitter.emit()` payloads, closure/callback arguments, return statements) — every one of those now threads an array-literal argument's hint automatically, with no changes of their own needed. `emitExpr`'s own bare `*ast.ArrayLiteral`/`*ast.NewArrayExpression` cases (no hint available) fall back to the literal's existing self-inferred-first-element convention (`inferArrayType`), unchanged.

**`Map`/`Set`/`EventEmitter` deliberately did not get the same hint-propagation treatment** — resolved as a real "no gap to fix," not deferred: all three already default sensibly (string keys/number values for `Map`, string elements for `Set`, `ptr` payload for `EventEmitter`) matching their own var-decl defaults, and an explicit `<K,V>`/`<T>` type argument is always available directly at the construction site (`new Map<string, number>()`) — unlike an array literal, which has no per-instantiation syntax of its own to pin its element type other than surrounding context.

**Nested arrays (array-of-arrays) were explicitly scoped out**, discovered mid-implementation, not assumed away: an array's backing buffer is a flat sequence of fixed-width, scalar/pointer-sized slots, but a nested array element's own value is a 16-byte `{ptr, i64}` pair — a real storage-representation gap, not something this fix's aggregate-building work happens to also solve (see Side effects discovered). `emitArrayLiteralAggregate` rejects `elemTy.IsArray` with a clear, deliberate error rather than reaching the confusing clang-stage type mismatch a few instructions later. Split into [TDD-00029](../tdd/TDD-00029.md).

## Implementation notes

Files touched:
- `codegen/llvm/emit_arrays_core.go`: `emitSpreadArrayLit` → `emitSpreadArrayLitData` (returns operands instead of storing); new `emitArrayLiteralData`, `emitArrayLiteralAggregate` (with the nested-array guard), `emitNewArraySizedAggregate`, `storeArrayAggregateInto`; `emitArrayVarDecl` refactored to call through them; `resolveArrayDataPtr`'s `*ast.ArrayLiteral` case simplified to call `emitArrayLiteralData`.
- `codegen/llvm/emit_collections.go`: new `emitMapOrSetCreate`, `emitNewMapValue`, `emitNewSetValue`; `emitMapVarDecl`/`emitSetVarDecl` refactored to call through them.
- `codegen/llvm/emit_eventemitter.go`: new `emitNewEventEmitterValue`; `emitEventEmitterVarDecl` refactored to call through it.
- `codegen/llvm/emit_exprs.go`: `emitExpr`'s five previously-erroring cases now dispatch to the functions above.
- `codegen/llvm/emit_exprs_types.go`: `inferExprType` gained an `*ast.ArrayLiteral` case (delegating to the pre-existing `inferArrayType`) — previously missing entirely, which (found while adding the nested-array guard) meant a nested literal's outer element type silently inferred as `i64` instead of being recognized as array-typed at all.
- `codegen/llvm/emit_objects.go`: `emitExprWithObjectHint` extended with the array-literal/`new Array<T>(n)` branches described above.
- `codegen/llvm/emit_exprs_assign.go`: the array-element and object-field `ex.Op == "="` branches now route through `emitExprWithObjectHint`; new dedicated array-variable-reassignment branch (see Side effects discovered); the scalar-variable fallback also now hint-aware.
- `codegen/llvm/emit_call.go`: `emitCallToFuncSig`'s array-parameter argument-evaluation branch switched from a bare `e.emitExpr(arg)` to `e.emitExprWithObjectHint(arg, paramTy)` — see Side effects discovered, this was the one spot that made the hint-propagation work silently not apply to the single most common case (a plain function call).

## Side effects discovered

Three real, pre-existing bugs surfaced while verifying this fix end-to-end, all fixed as part of this same piece of work:

1. **Array-variable reassignment (`arr = otherArrayVar`, no `let`/`const`) was already broken independent of anything about literals** — confirmed directly (`arr = other` failing with `'%tN' defined with type '{ ptr, i64 }' but expected 'ptr'`) before any array-literal-specific change was made. The generic scalar-variable assignment path stores into a single alloca (`sym.Ptr`), but an array variable is represented by *two* allocas (`Ptr`/`LenPtr` — see the project's own Array value duality note); the scalar path had no way to know that. Fixed with a dedicated array-variable-reassignment branch in `emitAssign`, checked before the generic scalar fallback, using the same `storeArrayAggregateInto` the var-decl path now shares.
2. **A plain array-literal call argument silently reinterpreted its raw bit pattern when the declared parameter type didn't match its self-inferred type** — `sum([1, 2])` against a `float64[]` parameter printed `1.4822e-323` instead of `3`. Root cause: `emitCallToFuncSig`'s array-parameter branch evaluated a non-identifier argument via a bare `e.emitExpr(arg)`, bypassing the hint-aware `emitExprWithObjectHint` entirely — the one array-specific special-case in the whole call-argument-evaluation path, and the one spot that made this ADR's own hint-propagation work not actually reach the single most common real-world case (an array literal passed directly to a function). Fixed by routing that branch through `emitExprWithObjectHint` like every other parameter already was.
3. **`inferExprType` had no case at all for a bare `*ast.ArrayLiteral`**, silently falling through to its final `TypeI64` default — harmless while a literal could only ever appear in var-decl position (var-decl's own inference went through `inferArrayType` directly, never through `inferExprType`), but a real, silent mistyping risk now that a literal can appear as a general sub-expression (most concretely: it's what let a nested array literal's outer element type silently infer as `i64` instead of being caught as array-typed by the new nested-array guard). Fixed by adding the missing case, delegating to `inferArrayType`.

Additionally confirmed, but *not* fixed here — pre-existing, unrelated, out of this ADR's scope: closures/callbacks (`emitClosureCallByPtr`/`emitCBCall`, `emit_func.go`) still don't support array-typed parameters at all (no array-specific two-slot argument passing exists on that path, unlike named-function calls); array literals still cannot be passed as an inline argument in *every* position (e.g. directly into a closure call) for that separate, pre-existing reason.

## Verification

- `go build -o klainmain .`, `go vet ./...`, `gofmt` — all clean.
- `go test ./... -count=1` passes in full, including the new `tests/literal_exprs_test.go` (16 tests: array literal as call argument/return value/object-literal field, hint-driven coercion correctness, plain reassignment of a literal and of another array variable, const-reassignment rejection, spread-containing literal as a call argument, `new Array<T>(n)` as a call argument, nested-array-literal clean rejection, `new Map`/`new Set`/`new EventEmitter` as a call argument/return value).
- Manually confirmed the exact pre-fix failures now work: `first([1,2,3])` (call argument), `function pair(): number[] { return [1,2] }` (return value), `const box: Box = { data: [5,6,7] }` (object-literal field), `arr = [4,5]`/`arr = other` (plain reassignment, both a literal and a named variable), and that a nested literal now fails with a clear, TDD-00029-referencing error instead of a confusing clang type mismatch.
- `examples/literal_expressions/literal_expressions.ts` (new) compiled and run directly via `klainmain` (`make`/`make examples` unavailable in this sandbox — no `make` binary); output matched every inline expected-output comment exactly.
- Verified only on the x86-64 Linux development box (see the project's own platform-flagging rule) — pure LLVM-IR-text/Go compiler logic, no OS/libc-specific code path, not expected to be platform-sensitive, but not directly confirmed on the Apple Silicon Mac.
