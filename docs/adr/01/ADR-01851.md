# ADR-01851: A member read on a possibly absent receiver is typed

- **Relations**: `Implements TDD-00230` (P3.3: the checker answers what inferExprType did)
- **Date**: 2026-10-21

## Context

- A property read whose receiver's type includes `null` or `undefined` (`o.a` with `o: {a: number} | undefined`, `desc.get` on an optional JSDoc parameter) came back unanswered. The member loop met the nullish member and gave up.
- tsc reports such an access (TS18047–TS18049, TS2531–TS2533) and types the read from the receiver's non-nullable type. The Test262 harness's `propertyHelper.js` reads optional descriptor parameters this way, so every file including it fell back for those reads.

## Decision

- A non-optional member read drops the receiver's `null` and `undefined` members before looking the property up, when another member remains. The diagnostic stays with `nonnull.go`. `?.` keeps its own typing, which adds `undefined`. A receiver that is only `null` or `undefined` stays unanswered.

## Consequences

- `TestMemberOfPossiblyAbsentReceiver` covers `| undefined`, `| null`, `?.` and the all-nullish receiver.
- Verified on Apple Silicon (checker package; targeted nullable, optional, narrowing, short-circuit, nullish, JSDoc and js-lane E2E tests).
