# Binary Data & Typed Arrays

> Part of the [Implementation Status](README.md) index. Binary views over a raw `ArrayBuffer` — essential for networking, crypto, and file I/O.

**Coverage**: 5/9 (~56%) · **Strict Coverage**: 1/9 (~11%).

Format: [Status page format](README.md#status-page-format).

| Feature | Status | Caveats | Notes |
|---|---|---|---|
| `ArrayBuffer` | ✅ | | • `new ArrayBuffer(byteLength)` — a fixed-length, zero-initialized (`calloc`'d) raw byte buffer, plus `.byteLength`. A general expression (works anywhere), unlike the TypedArrays below. See [ADR-00078](../adr/ADR-00078.md)/[TDD-00018](../tdd/TDD-00018.md) |
| `Uint8Array` / `Int8Array` / `Uint16Array` / `Int16Array` / `Uint32Array` / `Int32Array` / `Float32Array` / `Float64Array` | ✅ | • Construction is restricted to a variable declaration's initializer — `new Uint8Array(...)` can't appear as a general expression (TypedArrays weren't in scope for [TDD-00028](../tdd/TDD-00028.md)/[ADR-00104](../adr/ADR-00104.md), which lifted the identical restriction on plain array literals and `new Array<T>(...)`/`new Map<K,V>()`/`new Set<T>()`/`new EventEmitter<T>()`, but not for TypedArrays)<br>• No `.buffer` property (would require every TypedArray, including the "own buffer" form, to carry a back-reference to a real `ArrayBuffer` object — a shape change from the plain `{ptr,i64}` array representation)<br>• Only whole-buffer views at offset 0 are supported — no 3-argument `new XArray(buffer, byteOffset, length)` sub-range form | • Construction forms: from a size (`new Uint8Array(10)`, own new buffer), an existing `ArrayBuffer` (`new Uint8Array(buf)`, a **view** sharing the same memory — writes through one view are visible through any other view over the same buffer, including a differently-typed one reinterpreting the same bytes), or a `number[]`/array literal/another TypedArray (`new Uint8Array([1,2,3])`, copy-construct)<br>• Indexing, `.length`, `.fill`/`.slice`/`.reverse`/`.at`/`.indexOf`/`.includes`/`.map`/`.filter`/`.reduce`/`.forEach`/`.some`/`.every`, for-of, and `.keys()`/`.values()`/`.entries()` all come from the same machinery a plain `number[]` uses; `.set(source, offset?)`, `.subarray(start?, end?)` (a view, not a copy — unlike `.slice()`), and `.byteLength` are TypedArray-specific additions<br>• Non-clamped writes wrap (mod 2^width, e.g. `new Uint8Array([300])[0] === 44`), matching real JS<br>• See [ADR-00078](../adr/ADR-00078.md)/[TDD-00018](../tdd/TDD-00018.md) |
| `BigInt64Array` / `BigUint64Array` | ❌ | | • Not built; `bigint` ([TDD-00074](../tdd/TDD-00074.md)) exists to build them on |
| `Uint8ClampedArray` | ❌ | | • Real clamp-on-write semantics need a distinct store path (not just truncation) — deliberately skipped rather than approximated; see [TDD-00018](../tdd/TDD-00018.md)'s "Deliberately out of scope" |
| `DataView` | ✅ | • No `BigInt64`/`BigUint64` accessors (same scope line the TypedArray set drew), no `getFloat16` | • `new DataView(buffer, byteOffset?, byteLength?)`, full `get/set` × `Int8..Uint32/Float32/Float64` with the spec's per-call `littleEndian` flag (default big-endian, via `llvm.bswap`), `.byteLength`/`.byteOffset`/`.buffer` (aliasing-identical ArrayBuffer), RangeError on out-of-bounds access *and* construction ([ADR-00294](../adr/ADR-00294.md)) |
| `Blob` | ❌ | | • Immutable binary data object with MIME type |
| `SharedArrayBuffer` | ✅ | • No `.slice()` / `growable`/`grow()` (same scope line `ArrayBuffer` drew)<br>• Crosses a worker boundary whole or as an object field; a TypedArray **view** doesn't cross — send the buffer, re-view on the other side<br>• Views over it can't be captured by closures (the general array-capture limitation), so cross-thread handlers re-view inside the handler | • `new SharedArrayBuffer(n)` — identical representation to `ArrayBuffer` (all view constructions, `.byteLength`, `DataView` work unchanged), but `postMessage`/`workerData`/`structuredClone` **share it by reference** instead of deep-copying, the spec's semantics ([TDD-00099](../tdd/TDD-00099.md), [ADR-00308](../adr/ADR-00308.md))<br>• Under `-mm=gc`, allocated uncollectable (cross-thread references are invisible to a per-thread Boehm scan)<br>• Cross-thread visibility verified on darwin/arm64 and Linux (glibc/arm64, Docker) |
| `Atomics` | ✅ | • `wait` blocks the whole calling thread (event loop and fibers included) — allowed on the main thread (Node posture); no `waitAsync`<br>• No `BigInt64Array` support (that TypedArray doesn't exist yet); `wait`/`notify` are `Int32Array`-only (spec, minus the BigInt64 half)<br>• Index is bounds-unchecked, matching ordinary TypedArray indexing<br>• No `Atomics.isLockFree` | • `load`/`store`/`add`/`sub`/`and`/`or`/`xor`/`exchange`/`compareExchange` on any integer TypedArray, lowered directly to seq_cst LLVM atomics; float TypedArrays are a compile-time rejection ([TDD-00099](../tdd/TDD-00099.md), [ADR-00308](../adr/ADR-00308.md))<br>• `wait(ta, i, expected, timeoutMs?)` returns the spec's `"ok"`/`"not-equal"`/`"timed-out"`; `notify(ta, i, count?)` returns the wake count — implemented as a portable futex substitute (process-wide pthread mutex/cond + address-keyed waiter list; macOS has no futex syscall)<br>• Real cross-thread block/wake verified on darwin/arm64 and Linux (glibc/arm64, Docker) |
| Node `Buffer` (`Buffer.from`/`.alloc`/`.toString(encoding)`/`.write`/etc.) | ❌ | | • Node-specific, not a WHATWG API — a `Uint8Array` subclass in real Node with a much larger method surface (string encoding/decoding, concatenation, comparison). Not implemented at all; confirmed zero references anywhere in `codegen/llvm/`. [ADR-00094](../adr/ADR-00094.md) settled the "what should `fetch`/`fs`'s null-byte-truncation fix return" question in favor of plain `ArrayBuffer`/`Uint8Array` — no `Buffer` class, matching this compiler's existing WHATWG-over-Node-specific bias elsewhere |
