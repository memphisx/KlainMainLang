# ADR-01126: Possibly-null operands; closure and IIFE narrowing; `unknown` narrows to `{}` and `object`

- **Relations**: `Implements TDD-00230` (Phase 2, P2.2, P2.5, P2.7); `Extends ADR-01110`, `ADR-01112`, `ADR-01125`
- **Date**: 2026-09-25

## Context

Under `--strict` (`strictNullChecks`), tsc's `checkNonNullType` rejects
using a value that may be absent. It runs on:
- the object of a property or element access;
- the operands of arithmetic and relational operators;
- the operand of `-`, `+`, `~`, `++` and `--`.

It reports these codes:

| Operand | Codes |
|---|---|
| a name that may be null, undefined or both | TS18047, TS18048, TS18049 |
| any other expression | TS2531, TS2532, TS2533 |
| a bare `null` or `undefined` | TS18050 |
| `unknown` | TS18046 (a name), TS2571 (otherwise) |
| a callee that may be absent | TS2721, TS2722, TS2723 |

TS18048 is the family's most frequent code in TypeScript's baselines.
Reporting these codes also tests the narrowing hardest: every read tsc
narrows and the checker does not becomes a false positive.

## Investigation

The first measurement gave 37 false positives, each a narrowing gap
checked against tsc 5.6.3's source and behaviour.

- **Closures (TypeScript 5.4, `narrowingPastLastAssignment.ts`,
  `narrowedConstInMethod.ts`).**
  - A read inside a function expression, an arrow function, or a method of
    an object literal or class expression sees an outer binding narrowed at
    the point where the closure was created. This applies to a `const`, or
    to a parameter or local `let` that no assignment follows.
  - tsc's binder gives such a function's start node its container. The
    checker's walk continues from there (`getTypeAtFlowNode`'s `FlowStart`
    case).
  - "No assignment follows" is `isPastLastAssignment`. Each assignment's
    position is extended to the end of its enclosing statement
    (`extendAssignmentPosition`). An assignment from a nested function makes
    the binding never "past".
  - A `let` exported from a module, or declared at the top of a script,
    does not qualify.
- **Immediately invoked function expressions (`controlFlowIIFE.ts`).**
  tsc binds a non-async, non-generator IIFE inside its caller's flow. Its
  arguments are bound first, then its body; a `return` goes to a label
  after the call. `getControlFlowContainer` skips such a function.
- **`unknown`** narrows as `{} | null | undefined` (TypeScript 4.8):
  - a truthy `unknown` is `{}`;
  - `x !== null` gives `{} | undefined`;
  - `typeof x === "object"` gives `object | null`, and on `{}` gives
    `object`.
  - This needs TypeScript's non-primitive `object` type.
- **Other narrowing forms tsc applies:**
  - a template literal with no substitutions as a `typeof` operand;
  - `cond === true`/`false` (`narrowTypeByBooleanComparison`);
  - `x[k]` with a `const` literal key (TypeScript 4.7);
  - optional-chain containment, where `x?.a?.b != null` narrows `x` and
    `x.a`, in equality, `typeof`, type predicates and assertions
    (`narrowTypeByOptionalChainContainment`);
  - `n ??= 0` / `||=` / `&&=`, each path conditioned on the target, storing
    the right side;
  - a parameter whose default cannot be undefined starts without `undefined`
    (`removeOptionalityFromDeclaredType`).
- **The catch variable.** Under `--strict`, `useUnknownInCatchVariables`
  types an unannotated catch variable `unknown`, so `e.message` is TS18046.
  - The parser read a `catch (e: any)` annotation and dropped it.
  - A case measured without `strict` has `any` there.
- **An evolving variable** (`let e;`). tsc reports TS18048 when it is only
  `undefined`, but TS2454 ("used before being assigned") when some path
  assigned it. Without `noImplicitAny` it is `any`.
- **An `instanceof` against a library class** (`RangeError`) narrows
  `unknown` in tsc. The checker has no declaration for that class until
  P3.1, so the honest answer there is "not modelled".

## Decision

- **`checker/nonnull.go`:**
  - `checkNonNull` runs on every operand position listed in Context, and on
    a compound assignment's operands;
  - `checkCallee` covers TS2721–2723;
  - `entityName` names the operand as tsc does;
  - `startOf` reports at the start of the operand's source.
- **The binder:**
  - it records a function expression's creation flow on its `FlowStart`
    (`Outer`);
  - it keeps the visiting order of references, declarations and extended
    assignments (`ord`, `stmtFrame`, `markAssignment`);
  - `ClosureNarrows` answers tsc's rule;
  - it binds an IIFE inline: `Scope.Inline`, which `containerOf` skips, a
    return label, and arguments bound first. `functionOf` still counts the
    IIFE as a function for assignment positions, as tsc's `markNodeAssignments`
    does.
- **The checker** walks out through `Outer` (`ref.outer`, part of the flow
  cache key) up to the binding's own function. It also gains:
  - an `object` type (`NonPrimitive`) and `{}`;
  - the `unknown` narrowing rules above;
  - the other narrowing forms listed above.
- **`CatchClause.ParamType`** keeps the annotation. `Checker.CatchVariablesAny`
  and `Checker.ImplicitAnyVariables` model tsc without
  `useUnknownInCatchVariables` or `noImplicitAny`. The compiler never sets
  either, since the strict lane is `--strict`; `tools/tsdiag` sets them from
  a case's options.
- **`binder.Options.Script`** marks a program with no imports or exports,
  whose top-level `let` is a global.

## Implementation notes

- **The ordinal replaces source positions.** Statements carry no end
  offsets, so each assignment's extended position is the visiting ordinal
  at the end of its outermost enclosing statement that begins after the
  declaration.
- **A parameter default that reads the parameter** (`x = x + 1`) made
  `initialType` recurse. The `initializing` set returns the declared type
  there, as tsc's resolution stack does.
- **`??=`'s condition** is a synthetic `x != null`, used only as a flow
  node's expression and never attached to the program.
- **The examples used tsc-rejected forms.** 42 catch-variable reads now use
  `(e as Error)`, `(e as AggregateError)` or
  `(e as NodeJS.ErrnoException)`. Three deliberate throws use `!`, and
  `+null` is written through an `any`. The change in how codegen compiles
  the latter is [ADR-01127](ADR-01127.md).

## Side effects discovered

- **The resolver now rejects a read in an IIFE before a `let`'s
  declaration**, which throws at run time. Its dead-zone check treats an
  IIFE's reads as the caller's. tsc rejects the same program with a
  different code: TS2454 ("used before being assigned"), where the resolver
  reports TS2448, because tsc treats a read inside a function as deferred.
  Aligning that code belongs with the dead-zone check's move onto the
  checker (P2.7).
- **A read of a partly assigned evolving variable (TS2454) is skipped, not
  reported.** The binder's `UsedBeforeAssigned` covers only annotated
  `let`s.

## Verification

- **Checker tests:** the closure cases (narrowed; assigned afterwards;
  assigned from another closure; a nested function expression; a function
  declaration) are in `TestNarrowing`.
- **`tools/tsdiag`:** 1,158 diagnostics, of which 1,156 match tsc's
  baselines. The two misses are the known Annex B cases. TS18046, TS18047,
  TS18048, TS18049, TS18050 and TS2723 report no false positives. The
  project's own programs report 0.
- **Every edited example** prints the same output as Node.
