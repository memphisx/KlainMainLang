# ADR-00333: writable `process.env`

- **Date**: 2026-08-24

## Context

`process.env` was read-only (a `getenv()` wrapper). Part of completing the
Process / CLI area: make `process.env.KEY = val` / `process.env["KEY"] = val`
work, so a program can set variables its child processes then inherit.

## Decision

Intercept an assignment whose left-hand side's object is `process.env`
(`isProcessEnvExpr`) in `emitAssign`, before the generic member/index-assignment
paths (`process.env` is a pseudo-namespace, not a real object). Emit
`setenv(key, String(val), overwrite=1)`; the value is coerced to a string
(`emitValueToString`), matching Node's env-value stringification. Both the
static (`process.env.KEY`) and dynamic (`process.env[expr]`) key forms are
supported. The assignment evaluates to the assigned string.

Compound assignment (`process.env.X += …`) is rejected: it is a
read-modify-write of a possibly-unset `getenv` result, better made explicit.

`delete process.env.KEY` is **not** implemented — `delete` is not a parser
keyword (the fixed-shape object model deliberately has no dynamic property
delete), so it would need new unary-operator parsing. Disclosed on the status
page.

## Implementation notes

- `emit_process.go`: `emitProcessEnvSet(keyPtr, valExpr, pos)`.
- `emit_exprs_assign.go`: the `process.env` write dispatch (member + index),
  early, before static-field / dynamic-object assignment.
- `setenv` was declared inline in the cluster runtime; factored into a guarded
  `ensureSetenvDecl` (runtime_core.go) shared with the env-write path, so both
  can co-occur without a duplicate declaration.

## Side effects discovered

None. `unsetenv`/`delete` deferred (needs the `delete` operator).

## Verification

- `tests/process_test.go`: static + dynamic-key writes and read-back; a written
  var inherited by a child (`execFileSync("printenv", …)`); compound assignment
  rejected at compile time.
- Machine: verified on Mac (arm64); `setenv` is POSIX, so parity expected on
  Linux.
