# ADR-00369: Static CommonJS `require('<literal>')` desugars to an ES import

- **Relations**: `Extends ADR-00135`
- **Date**: 2026-08-25

## Context

Node source and much of the Node test corpus use CommonJS `require` rather than
ES `import`: `const path = require('path')`, `const { basename } = require('path')`,
`require('./setup')`. This compiler accepts only `import`, so every such file
failed at parse/codegen ("unknown statement type", or an undefined `require`
call). Supporting the *static* form — a string-literal module path at top-level
declaration/statement position — lets Node-style code compile directly and is a
pure front-end rewrite over the import machinery that already exists. The
*dynamic* form (`require(variable)`, a `require` nested in a function body for
lazy loading) is explicitly out of scope here and left to the separate deferred
runtime/lazy-loading capability.

## Investigation

The import path is fully modeled: `ast.ImportDeclaration` carries either named
specifiers (`{Imported, Local}`), a namespace alias (`import * as ns`), or a
default specifier, and is consumed entirely by `resolver.ResolveProgram` before
codegen (`ast/nodes.go`). So a `require` only needs to be turned into the right
`ImportDeclaration` shape at parse time; nothing downstream changes.

Choosing the binding shape for `const x = require('mod')` mattered. A CommonJS
`require` returns the whole `module.exports` object, so the faithful mapping is a
**namespace** import (`import * as x`), not a default import. Verified directly:
for a built-in both forms work (`import path from 'path'` and `import * as path
from 'path'` each expose `path.basename`), but for a user module with only named
exports, `import x from './lib'` fails ("no exported member 'default'") while
`import * as x from './lib'` binds the exports object correctly. Namespace is
therefore the right and more general choice.

Statement shapes observed: `const NAME = require('lit')`, `const { a, b: c } =
require('lit')` (object-destructuring node), and a bare `require('lit')`
expression statement (side effect). The parser already produces
`*ast.VarDeclaration`, `*ast.ObjectDestructuring`, and `*ast.ExpressionStatement`
for these, each carrying the initializer/expression — so a post-parse converter
can inspect them without any new pattern parsing.

## Decision

Add `desugarRequire` (`parser/parser_require.go`), called from `ParseProgram` on
each **top-level** statement (so a nested `require` stays an ordinary call — the
lazy form, out of scope):

- `const x = require('lit')` → `ImportDeclaration{Namespace: "x", Source: lit}`
  (namespace import).
- `const { a, b: c } = require('lit')` → named import with one specifier per
  destructured property. A property with a default, nested pattern, or rest is a
  clean error (not expressible as an import).
- bare `require('lit')` → `ImportDeclaration` with no bindings (side-effect
  import).
- Any of the above with a non-string-literal argument → a clean compile error
  naming the dynamic form as unsupported (message carries no doc path).

`requireCall` centralizes the detection (callee is the identifier `require`,
exactly one argument, argument is/ isn't a string literal).

## Implementation notes

Scoping the desugar to `ParseProgram`'s top-level loop — rather than the shared
`parseStatement`, which also parses function/block bodies — is what keeps a
lazy `require` inside a function from being wrongly hoisted into a program-level
import; it simply remains an ordinary (currently unresolved) call, which is the
correct home for the deferred dynamic capability.

`require` is treated as a reserved module-loading form at top level; a program
that shadows it with its own top-level `const require = …` is not something this
rewrite tries to preserve (consistent with the compiler's treatment of other
builtins).

## Side effects discovered

None. The Node conformance transform (`tools/conformance/node.go`) still does its
own `require`→`import` rewrite; it now overlaps this native support and could be
simplified to lean on it later, but was left unchanged here to avoid perturbing
that track's measured results.

## Verification

`go build` clean. New E2E tests (`tests/require_test.go`): namespace require,
named-destructure require, bare side-effect require, require/import interop, and
a dynamic-`require(variable)` rejection — all green. Example
`examples/imports/require_commonjs.ts` compiles and runs. Full `tests` E2E suite
green (no regression from the parser change). Verified on macOS (arm64).
