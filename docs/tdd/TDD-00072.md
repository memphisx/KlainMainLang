# TDD-00072: Enriched compiler diagnostics, and a strict spec-error-matching mode

- **Status**: Not Started
- **Date**: 2026-08-18
- **Notes**: Two independent parts. **Part 1 (low-cost, default):** a diagnostic renderer — source snippet + `^` caret + optional hint around the existing `%d:%d:` errors; the one plumbing gap is threading each error's origin file (the resolver merges files). **Part 2 (research-gated):** classify errors under a JS error *kind* (`SyntaxError`/`TypeError`/…) and optionally match Node/V8 wording, behind a strict compatibility mode — the same axis as [TDD-00022](TDD-00022.md)'s `compatibilityMode`. Grounding: the Test262 harness scores negative tests on *phase*, not error type/text, so message-matching has little conformance value and belongs in a mode, not the default

## Context

Every compile error today is built as `fmt.Errorf("%d:%d: <message>", line, col, …)` and printed by `main.go`'s `fatal` as, for example, `klainmain: codegen error: 3:15: undefined variable 'x'`. That's a bare line:col plus a message — no source snippet, no caret at the offending column, and the *file* isn't reliably present (a single-file build relies on the CLI argument; the resolver embeds `path` in some errors but not all). For a compiler whose whole point is developer ergonomics on CLI tools and microservices, that's the weakest part of the experience.

Two genuinely different concerns hide behind "better errors," and conflating them is a trap this TDD exists to avoid:

1. **How an error is *rendered*** — the developer-experience layer. A framed snippet with a `^` under the column and an optional hint. Strictly an improvement; wanted by default.
2. **What an error *is* — its classification and exact text** — matching real JavaScript/TypeScript/Node error *kinds* (`SyntaxError`/`TypeError`/`ReferenceError`/`RangeError`) and spec-exact message strings 1-to-1. Good for spec fidelity and any tooling that scrapes Node/V8 output, but the terse spec wording is *worse* DX than a purpose-written message. So it belongs behind a strict compatibility mode, not the default — the same instinct behind [TDD-00022](TDD-00022.md)'s `compatibilityMode`.

A grounding fact that sharpens concern #2: the Test262 harness (`tools/conformance/main.go`) keys a negative test on its **phase** (`negative: phase: parse|resolution|runtime`) and does *not* read the expected error *type* or message. So the conformance number moves on **rejecting at the right phase**, largely independent of what the message says. Matching error *class* and exact V8/Node wording is therefore a separate fidelity concern with little current conformance value — worth doing deliberately, in a mode, not by default.

## Design

Two independent parts. Part 1 is the high-value, low-cost piece and can ship alone; Part 2 is research-gated and conformance-adjacent.

### Part 1 — diagnostic rendering (default, or `--diagnostics=rich`)

A small `diagnostics` renderer: given `(file, line, col, message, [hint])`, read the source, and print the offending line with a caret under the column, ±1 line of context, rustc/clang-style. Wired at `main.go`'s two `fatal` sites (parse and codegen).

Two viable implementation shapes:

- **MVP — parse the existing prefix.** Every error already begins `%d:%d:`; a thin layer regex-extracts `line`/`col`, looks up the file (see below), and renders the frame around the existing message. Zero changes to the ~hundreds of `fmt.Errorf` sites. Fastest path to the visible win.
- **Structured — a `Diagnostic` value.** Replace the bare `error` for compiler diagnostics with a `Diagnostic{File, Line, Col, Severity, Message, Hint}` carried through parse/resolve/codegen, rendered once at the top. Cleaner and extensible (multiple diagnostics, warnings, hints), but a broad refactor of every error site. Better long-term; not required for the first cut.

The one real plumbing gap either way: **every error must know its origin file.** Positions already flow (`Pos{Line,Col}` on every AST node), but the file is inconsistent — the resolver merges multiple files ([ADR-00022](../adr/ADR-00022.md)/TDD-00041), so a position needs its source file to render the right snippet. This likely means carrying a file id alongside `Pos`, or a position→file map from the resolver.

### Part 2 — spec-error matching under a strict compatibility mode

Default mode keeps this compiler's own clearer messages. A strict/compat mode instead classifies each error under a JavaScript error *kind* and, optionally, emits spec-exact message text matching Node/V8, for fidelity and any future error-type assertions.

- **Classification first, wording second.** Tag each diagnostic with a JS error class (`SyntaxError` for early/parse errors, `ReferenceError`/`TypeError`/`RangeError` for the runtime-shaped ones) — a catalog mapping this compiler's existing errors to the class real JS raises for the same condition. Exact message *strings* are a further, larger step (V8's wording is an unversioned moving target).
- **Shared flag with [TDD-00022](TDD-00022.md).** This is the same `compatibilityMode` axis (`ts`/`js`/strict): the compat mode that suppresses TS-only strictness ([TDD-00022](TDD-00022.md) sub-problem 5) is also the mode that would turn on spec-exact error matching. One flag/profile, consulted in the renderer, rather than a dedicated `--errors=strict` — though that's an open question.
- **Note the semantic mismatch.** This compiler's runtime errors are native (setjmp/longjmp exceptions, hard traps), not JS exception *objects*. So "matching TypeError" is mostly a *CLI-output/classification* concern, not a real thrown-object contract — worth being honest that full 1-to-1 runtime error-object behavior is out of scope even here (it overlaps the dynamic-object-model work [TDD-00022](TDD-00022.md) sub-problem 3 defers).

### Research needed (concern #2)

- Confirm precisely what the conformance harness rewards — today it reads only `negative: phase:` (not `type:`), so phase-correct rejection is what moves the number; verify no other path checks type before investing in error-class matching.
- Catalog which of this compiler's existing errors correspond to which JS error class and spec condition.
- Decide flag granularity: fold into [TDD-00022](TDD-00022.md)'s `compatibilityMode`, or a separate `--errors=strict`.

## Open questions

- MVP prefix-parse vs. a structured `Diagnostic` refactor for Part 1 — lean MVP first, structured later if warnings/multi-diagnostic output become worth it.
- Rich rendering default-on vs. `--diagnostics=rich` — leaning default-on (it's strictly better) with an opt-out for machine-readable output.
- Whether Part 2 shares [TDD-00022](TDD-00022.md)'s `compatibilityMode` flag or gets a dedicated `--errors=strict`.
- Whether to model JS error *classes* at all given this compiler's native (non-object) runtime errors, or keep matching purely at the CLI-message layer.
- Priority: Part 1 is cheap and high-value and can be done any time; Part 2 is deliberately low-priority and gated on the same forcing function as [TDD-00022](TDD-00022.md) (actually caring about JS/Node error fidelity).
