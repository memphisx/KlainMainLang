# ADR-00130: Real `Request`/`Headers` classes, and freeing up `Request` from `http.listen`'s server-side type

- **Relations**: Supersedes the `Request`/`Headers` decision in [ADR-00074](ADR-00074.md). Implements [TDD-00040](../tdd/TDD-00040.md) (Stage 1 of 2 — `XMLHttpRequest` is Stage 2, a separate ADR)
- **Date**: 2026-08-08

## Context

[`docs/status/NETWORKING.md`](../status/NETWORKING.md) listed real `Request`/`Headers` classes as ❌, with a note that this was a *deliberate* scope decision — [ADR-00074](ADR-00074.md)/[TDD-00017](../tdd/TDD-00017.md) explicitly chose `fetch(url, init)`'s plain-object `init` argument over introducing `Request`/`Headers` types, judging the latter "more machinery than this project's existing conventions call for". Picked up at explicit user request to reverse that decision and bring this row to done, alongside `XMLHttpRequest` (Stage 2, tracked separately) — see [TDD-00040](../tdd/TDD-00040.md) for the full design this ADR implements the first half of.

## Investigation

- Confirmed `Headers`' natural implementation reuses `URLSearchParams`'s own precedent almost exactly: `URLSearchParamsType()` (`types.go`) is already just `MapType(TypePtr, TypePtr)` with an `IsURLSearchParams` flag, dispatched ahead of the generic `IsMap` branch in `emit_call.go` for its two extra methods (`toString`/`getAll`) while `get`/`set`/`has`/`delete`/`forEach`/`entries`/`keys`/`values` fall through unchanged. `Headers` follows the identical shape.
- Found a real naming collision only once implementation started (not caught during TDD-00040's design pass): `codegen/llvm/types.go` already had `RequestType()`/`IsRequest` for `http.listen`'s server-side request object, **and** `ResolveTypeName`'s `case "Request": return RequestType()` already claimed the *source-level* TypeScript annotation name `Request` for that server type. The TDD's own naming note only addressed the Go-identifier collision (solved by naming the new type `FetchRequestType`/`IsFetchRequest`) — it didn't catch that the user-facing annotation name was *also* already spoken for. Discovered concretely via a failing test: `const req: Request = new Request(url); req.url` compiled but then failed with `no field 'url'` — `resolveType` was resolving the `: Request` annotation to the *old* `RequestType()` (method/path/query/headers/body/bodyLength — no `url` field at all), while `new Request(...)` itself constructed the *new* `FetchRequestType()` (url/method/headers/body), a silent type mismatch between the declared annotation and the actual constructed value.
- Considered three ways to resolve the collision (see [TDD-00040](../tdd/TDD-00040.md)'s own note, which named the Go-side half of this but deferred the source-naming half): (1) keep the client-side type under a different source name entirely (rejected — defeats the actual point of matching the real Fetch API's naming, which is what "implement Request for real" means); (2) actually unify the two into one shape (rejected — the server-side shape has HTTP-server-specific fields, `path`/`query`/`bodyLength`, with no client equivalent; unifying would mean redesigning `http.listen`'s request object, well beyond this feature's scope); (3) rename the server-side annotation to something else, freeing `Request` for the client type. Went with (3): real prior art (Deno.serve, Cloudflare Workers) actually does hand a real spec `Request` to a server handler, so `Request` reads more naturally as the client/spec type than as this compiler's own bespoke server-request shape — and moving the *less* spec-shaped one out of the way, rather than the fetch-API-shaped one, keeps naming intuitive going forward.
- Verified the actual blast radius of the rename before doing it: `grep -rn "req: Request\b"` found the pattern in exactly 6 example files and 5 test files (57 occurrences total), always in the fixed shape `(req: Request)`/`(req: Request):` as an `http.listen` handler's parameter annotation — no other usage shape existed anywhere in the tree (checked with a broader `: Request\b` grep too). Confirmed via `codegen/llvm/emit_http.go:120` that `emitHTTPListen` never checks `IsRequest`/a fixed type identity for the handler parameter at all — it reads `handlerVal.Ty.FuncParams[0]` and works purely structurally (`FieldIndex` on whatever the user annotated), so the rename is purely a source/vocabulary change, not a semantic one.

## Decision

**`Headers`** (`types.go`'s `HeadersType()`): `MapType(TypePtr, TypePtr)` plus `IsHeaders`. `get`/`set`/`has`/`delete` are dispatched in `emit_call.go` ahead of the generic `IsMap` branch (same ordering `IsURLSearchParams` already established) as thin lowercased-key wrappers around the exact same `__kml_map_str_get/set/has/delete` primitives `emitMapCall` already calls — key lowercasing via the existing `__kml_tolower` (`String.prototype.toLowerCase()`'s own primitive). `append(name, value)` is the one new method: `has` then either `set` or `set(existing + ", " + value)` via the existing `emitStringConcat`. `forEach`/`entries`/`keys`/`values` are *not* overridden — they fall through to the generic `Map<string,string>` path unchanged, since none need case-insensitive handling (they just read back whatever was already normalized on the way in). `new Headers()`/`new Headers(init)` (`emit_headers.go`'s `emitNewHeadersExpression`) — `init: Map<string,string>` copies every entry, lowercasing each key during the copy (`emitHeadersFromMapValue`, shared with `Request`'s own `init.headers` extraction below).

**`Request`** (`types.go`'s `FetchRequestType()`): a plain heap object — `url`/`method`/`headers: Headers`/`body` — exactly `Response`/`URL`'s "fields readable directly, no dispatched getters" shape. `new Request(url)`/`new Request(url, init)` (`emit_fetch_request.go`) reuses `emitFetch`'s own `init`-field-extraction pattern (`FieldIndex`/`loadFieldValue`) near-verbatim: `method` defaults to `"GET"`, `headers` to a fresh empty `Headers`, `body` to `null`.

**`fetch()` grows a third call shape**: `fetch(request)` — a single argument whose inferred type is `IsFetchRequest` is destructured into url/method/headers/body (`emit_fetch.go`), then falls into a new shared tail, `emitFetchAsyncCall`, factored out of the previous `fetch(url)`/`fetch(url, init)` bodies so all three forms converge on the identical `__kml_fetch_async` call — no runtime signature change. `fetch(url, init)`'s existing `init.headers` field check (`fieldTy.IsMap`) already accepts a `Headers` value with zero code changes, since `Headers` *is* `Map<string,string>` under the hood — confirmed by `TestE2EFetchInitAcceptsHeadersInstance`.

**The naming-collision fix**: `http.listen`'s server-side request type's TypeScript annotation moves from `Request` to `HttpRequest` — the Go-side `RequestType()`/`IsRequest` identifiers are unchanged (only `ResolveTypeName`'s `case` label moved), and every one of the 57 `req: Request` occurrences across 6 examples and 5 test files was mechanically updated to `req: HttpRequest`. `ResolveTypeName` now has both `case "HttpRequest": return RequestType()` and `case "Request": return FetchRequestType()` side by side.

## Implementation notes

- `codegen/llvm/types.go`: `IsHeaders`/`IsFetchRequest` flags, `HeadersType()`/`FetchRequestType()`, `VisibleFields()` unaffected for both (no hidden fields on either — `Headers` is a bare `Map`, `Request`'s four fields are all visible). `ResolveTypeName`'s `Request`→`HttpRequest` split (documented above).
- `codegen/llvm/emit_headers.go` (new): `emitNewHeadersExpression`, `emitHeadersFromMapValue` (shared copy-with-lowering loop), `emitHeadersCall` (get/set/has/delete/append), `isHeaderMapType` (the `Map<string,string>`-shape check shared by `Headers`' own init validation and `Request`'s `init.headers` validation).
- `codegen/llvm/emit_fetch_request.go` (new): `emitNewRequestExpression`.
- `codegen/llvm/emit_fetch.go`: `emitFetch` restructured — a new leading branch handles the single-`Request`-argument form before falling into the pre-existing url/init logic; the trailing `__kml_fetch_async` call + `Promise<Response>` slot construction extracted into `emitFetchAsyncCall`, shared by every form.
- `codegen/llvm/emit_call.go`, `emit_exprs.go`, `emit_exprs_types.go`, `emit_exprs_vardecl.go`: the same four wiring points every prior builtin-object type (`URL`, `EventSource`, `WebSocket`, ...) needed — call dispatch, `emitExpr`'s `NewXExpression` switch, `inferExprType`'s switch, and the unannotated-var-decl inference switch. `XMLHttpRequest`'s AST node/parser cases and a minimal constructor were also added in this same pass (build-completeness only — `emit_xhr.go`'s real method dispatch is Stage 2, a separate ADR) since `emit_exprs.go`'s switch needed all three `New*Expression` cases to compile together.
- `codegen/llvm/emit_structured_clone.go`: `IsHeaders`/`IsFetchRequest` added to `structuredCloneUnsupportedKind` — ordering bug caught and fixed during implementation (an `IsHeaders` case placed *after* the generic `IsMap` case would never be reached, since `Headers.IsMap` is also true and Go's `switch` picks the first matching case; moved ahead of it, mirroring where `IsURLSearchParams` already sits).
- `ast/nodes.go`, `parser/parser_literals.go`: `NewHeadersExpression`/`NewRequestExpression`/`NewXMLHttpRequestExpression`, each following an existing sibling's exact shape (`NewURLSearchParamsExpression`'s optional-init pattern for `Headers`; `NewURLExpression`'s required-arg-plus-comma pattern extended for `Request`'s optional second arg; `NewTextEncoderExpression`'s zero-arg pattern for `XMLHttpRequest`).

## Side effects discovered

- The `Request`/`HttpRequest` naming collision itself (documented above under Investigation) — not a pre-existing bug, but a real gap in TDD-00040's own design pass that implementation surfaced; recorded here rather than silently patched over, per this project's standing rule.
- the project's own project-direction section still said "no real `Request`/`Headers` classes" — fixed alongside this ADR (unrelated stale-doc fix bundled in, per this project's "fix bugs/staleness found during work" rule) rather than deferred.
