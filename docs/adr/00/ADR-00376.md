# ADR-00376: `++`/`--` on a member or index target

- **Relations**: Extends [ADR-00375](ADR-00375.md)
- **Date**: 2026-08-26

## Context

While delivering static field initializers ([ADR-00375](ADR-00375.md)) it
surfaced that `++`/`--` worked only on a plain identifier — `C.count++`,
`this.x++`, `obj.x++`, and `arr[i]++` all failed with `update expression
requires an identifier`, even though the equivalent compound assignment
(`C.count += 1`, `arr[i] += 1`) already worked. `this.count++` is everyday code;
the gap was general (any member/index lvalue), not static-field-specific.

## Investigation

`emitUpdate` (`codegen/llvm/emit_exprs_operators.go`) type-asserted its argument
to `*ast.Identifier` and errored otherwise. The full read-modify-write path for
every non-identifier lvalue — static field global, instance field GEP, array
index — already exists in `emitAssign`, reachable through a compound-assignment
node (`AssignmentExpression` with op `+=`/`-=`). Verified `obj.k += 1`,
`arr[i] += 1`, and `C.n += 1` all compile and run.

## Decision

For a member or index target, desugar the update to the equivalent compound
assignment and reuse `emitAssign`:

- Build `AssignmentExpression(op: "+="|"-=", left: ex.Arg, right: 1, …)`. The
  step literal matches the target type — a bigint field steps by `1n` (via
  `inferExprType(ex.Arg).IsBigInt`), everything else by the numeric `1`, which
  the compound-assign path coerces to the field type (so a `float64` field steps
  by `1.0`).
- **Prefix** returns the compound assignment's result (the post-update value).
- **Postfix** reads the target once before the update and returns that old
  value.

Identifier targets keep their existing dedicated path unchanged. The error
message for a genuinely unsupported target (e.g. a call result) now reads
"requires an identifier, member, or index target".

## Implementation notes

- `codegen/llvm/emit_exprs_operators.go`: `emitUpdate` routes a
  `*ast.MemberExpression` / `*ast.IndexExpression` argument to the new
  `emitTargetUpdate`; the rest of `emitUpdate` (identifier, nullable-scalar,
  bigint, float) is untouched.

## Side effects discovered

For a **postfix** update whose value is consumed, the target's object
sub-expression is evaluated twice — once for the pre-read, once inside the
compound assignment. For a simple receiver (identifier / `this` / static class
name / an identifier-chain member) this is side-effect-free; only a
side-effecting receiver used as a postfix *value* (`makeObj().x++` read into a
variable) would run its side effect twice. That shape was a hard rejection
before, so this is strictly more capable, and a statement-position postfix (the
common case) discards the pre-read entirely (dead-code-eliminated). Documented as
a caveat on the increment/decrement row.
