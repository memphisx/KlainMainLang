# ADR-00754: `child_process.spawn` fires the `'error'` event on a start failure

- **Relations**: Implements a [TDD-00180](../tdd/TDD-00180.md) §3 row ("Spawn failure: Node emits `'error'`, no `'exit'`. Here: `'exit'` with 127, the `'error'` slot never fires"); extends [ADR-00322](ADR-00322.md) (the `spawn` fork/pipe/select core), [ADR-00740](ADR-00740.md) (the `.bat`-without-shell refusal), [ADR-00719](ADR-00719.md)/[ADR-00737](ADR-00737.md) (the Win32 spawn shim)
- **Date**: 2026-09-07

## Context

When a `spawn()` cannot start the child at all — the command does not exist (`ENOENT`), or a `.bat` is refused without a shell — Node emits the ChildProcess `'error'` event with an `Error` and never emits `'exit'`. This compiler instead reaped the fork's `_exit(127)` and fired `'exit'` with code 127; the `'error'` listener slot (cp struct field 12) existed but nothing ever invoked it. A program doing `child.on('error', …)` — the canonical way to detect "command not found" — never heard about the failure, and one doing `child.on('exit', …)` saw a spurious 127.

## Investigation

The gap is that "the child exec-failed" and "the child ran and exited 127" are indistinguishable from the parent's `waitpid` alone — both yield status 127. `__kml_cp_finalize` decoded that status and fired `'exit'`/`'close'` unconditionally. A reliable start-failure signal was missing:

- **POSIX**: the child (`cpSpawnForkIR`) did `execvp` then `_exit(127)` with nothing written back to the parent.
- **Windows**: `__kml_win_spawn` (`win32proc.c`) already *knew* a `CreateProcessW` failure — it set a `failed` flag on its `kml_proc` and returned a pseudo-pid whose `waitpid` reports 127 — but exposed nothing the IR could read.

## Decision

Give the ChildProcess handle a spawn-failure errno (new cp struct field 20, `calloc` grown 160→168, zeroed = "started fine") and fire `'error'` from `__kml_cp_finalize` when it is set — skipping `'exit'`, still firing `'close'` (Node's ordering).

- **POSIX** — a fourth pipe whose write end is `FD_CLOEXEC` (`cpSpawnStatusSetupIR`). A successful `execvp` closes it, so the parent's read gets EOF; a failed one has the child write its `errno` (4 bytes) before `_exit(127)`, so the parent's read returns it (`cpSpawnFailDetectIR`). Both ends are close-on-exec so the exec'd program inherits neither. The parent read is blocking, which briefly serializes spawn with the child reaching `exec` — microseconds for a real command, and it never waits for a long-running child (exec closes the pipe immediately).
- **Windows** — no fork; `__kml_win_spawn` now records the mapped errno on the `kml_proc` (`spawnerrno`), and a new `__kml_win_spawn_failed(pid)` shim returns it (0 on success). `cpSpawnFailDetectIR`'s Windows branch stores that into field 20.
- **`__kml_cp_finalize`** — the streaming path checks field 20 first: non-zero routes to an `'error'` block that builds an `Error` via `__kml_cp_spawn_errobj(errno)` (message `spawn <strerror>`, a full 6-field `errorObjType`) and invokes the field-12 listener, then falls to the existing `'close'` firing, bypassing `'exit'`. The buffered `exec` path is unchanged (it already synthesizes an `Error` for the `(err, …)` callback).

The `Error` carries `.message` only; Node's `.code`/`.errno`/`.syscall`/`.path`/`.spawnargs` are not attached (the same `errorObjType` boundary as the other runtime errors — extending that shared 6-field shape is out of scope).

## Implementation notes

- Field 20 is appended, so every existing cp field index is unchanged; `runtime_ipc.go`'s `calloc` was bumped to 168 too (it allocates the same struct).
- The `.bat`-without-shell refusal ([ADR-00740](ADR-00740.md)) now surfaces through this same path as `'error'` (EINVAL) rather than a synthesized `'exit' 127`, which is what Node actually does — `TestE2EChildProcessSpawnBatWithoutShellFails` was updated to assert the `'error'`/`'close'` shape.
- `cpSpawnFailDetectIR`/`cpSpawnStatusSetupIR` are GOOS-conditional (the Windows build never references the POSIX pipe SSA values, and vice-versa).

## Side effects discovered

None. `exec`/`execFile`/`fork`/`cluster` and the buffered path are untouched; the full child_process/spawn/fork/cluster/worker suite stays green.

## Verification

- New E2E test `TestE2EChildProcessSpawnErrorEvent` (`tests/childprocess_test.go`): spawning a nonexistent command fires `'error'` (non-empty message) and **not** `'exit'`, while `'close'` still fires — cross-platform (a bogus name fails to spawn everywhere), verified on **Windows 11**.
- `TestE2EChildProcessSpawnBatWithoutShellFails` updated to the faithful `'error'` shape (Windows).
- Full `child_process`/`spawn`/`exec`/`fork`/`cluster`/`worker` suite green (29s on Windows 11) — the grown struct and new spawn-path code introduced no regression.
- `examples/child_process/child_process.ts` extended with a spawn `'error'` demonstration.
- `go build`, `go vet ./...` clean; `make status`/`make status-check` and `make reference-check` pass (status JSON + website reference JSON updated same-commit); `make conformance` run at delivery.
- Platform: verified on **Windows 11** (x86-64, MSYS2 UCRT); the POSIX status-pipe path is the standard libuv-style mechanism.
