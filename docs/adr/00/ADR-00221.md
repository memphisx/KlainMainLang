# ADR-00221: Bound the object inspector's recursion (fix compile-time infinite loop on recursive types)

- **Date**: 2026-08-18
- **Relations**: Extends [ADR-00218](ADR-00218.md) (fixes a bug in its inspector)

## Context

The object inspector ([ADR-00218](ADR-00218.md)) recurses over the **static type structure** — `emitInspectObject` walks each field via `emitInspectField`, which recurses into nested objects/arrays. That recursion had **no depth bound**, so a self-referential or mutually-recursive type — `interface A { b: B }` / `interface B { a: A }`, or any deeply-nested shape — recursed **forever at compile time** (`emitInspectObject` → field of type `B` → `emitInspectObject` → field of type `A` → …).

Surfaced by `make conformance`: the run froze at ~53000/53578 with the harness process pegged at ~500% CPU and **no child processes** — i.e. spinning in-process in codegen (`EmitProgram`), not in a test binary. Five workers had each hit a Test262 file with a recursive type and were looping in the inspector.

## Investigation

- The inspector's recursion is driven by types, not runtime values, so a recursive type diverges regardless of the actual data — a pure compile-time infinite loop.
- The conformance harness (`tools/conformance/main.go`) runs `parser.Parse`/`llvm.EmitProgram` **in-process** in each worker goroutine; its per-file timeout guards only the `clang` **subprocess**. An in-process codegen infinite loop is therefore not interruptible (Go doesn't preempt a CPU-bound goroutine), so one bad file hangs a worker permanently and the whole run silently stalls.
- Node's `util.inspect` bounds this with a default depth (2), rendering `[Object]`/`[Array]` beyond it — a depth cap both fixes the loop and matches JS.

## Decision

Thread a `depth` through `emitInspectObject`/`emitInspectField`/`emitInspectArray` (entry points pass `0`, each nesting level `+1`); at `depth > maxInspectDepth` (= 4), a nested object/array renders as `[Object]`/`[Array]` instead of recursing. This bounds compile-time recursion for *any* type — recursive, mutually-recursive, or merely deep — and mirrors Node's depth-limited inspection. Chose a cap of 4 (a little deeper than Node's 2) as a readable default; the exact value is a detail, the bound is the point.

Separately, made the conformance harness report progress every **250** files (was 1000) with elapsed time / throughput / ETA, so a future in-process stall shows up as a frozen counter within seconds rather than a silent multi-minute hang. (An in-process per-file timeout was considered and rejected — a busy Go goroutine can't be cleanly cancelled.)

## Implementation notes

- `emit_inspect.go`: `maxInspectDepth` const; `depth` parameter on the three inspector functions; the `depth > maxInspectDepth` guard in `emitInspectField`'s object/array cases.
- Callers (`emit_call_console.go` ×2, `emit_exprs_types.go` ×1) pass `0`.
- `tools/conformance/main.go`: finer, timestamped progress logging.

## Side effects discovered

- This masked how brittle a codegen infinite loop makes the whole conformance run (a single file hangs everything). The progress-logging change mitigates detection; a structural fix (running codegen in a killable worker) is a larger, separate effort noted here.

## Verification

- `tests/inspect_test.go` — `TestE2EInspectDepthCap` (`{ a: { b: { c: { d: { e: [Object] } } } } }`). Manual: a self-referential `interface Node { next: Node }` and mutually-recursive `A`/`B` now compile in well under a second (were non-terminating); shallow objects/arrays render unchanged.
- `go vet ./...` clean; inspect/class suites green; full `go test ./...` at the delivery's end. Conformance itself deliberately not re-run (per the Jamf-Protect slowdown) until the final commit.
