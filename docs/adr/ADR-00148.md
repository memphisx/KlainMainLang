# ADR-00148: `import.meta.url` (Stage 1 of dynamic `import(...)`/`import.meta`)

- **Relations**: Implements [TDD-00055](../tdd/TDD-00055.md) (Stage 1 only)
- **Date**: 2026-08-10

## Context

[TDD-00055](../tdd/TDD-00055.md) scoped `import.meta.url` and dynamic `import(...)` together, since both extend the `import` keyword into expression position at the same parser dispatch point. Stage 1 (this ADR) is `import.meta.url` — small, fully self-contained, no codegen changes — plus enough of the shared `import`-in-expression-position parser plumbing that dynamic `import(...)` (Stage 2, not built here) gets a clean, dedicated "not yet supported" rejection instead of falling into a confusing generic parse error in the meantime.

## Decision

**Parser.** `lexer.IMPORT` previously only had a case in `parseStatement`'s top-level switch (unconditional dispatch to `parseImportDeclaration`) and no case at all in `parsePrimary` (expression-level dispatch), where it fell through to a generic "unexpected token" error. Two additions:
- `parsePrimary` gains `case lexer.IMPORT: return p.parseImportExpr()` — a new, dedicated parse function (`parser/parser_imports.go`), following the same pattern `case lexer.NEW: return p.parseNew()` already uses for a keyword with its own argument-shape rules. It recognizes exactly `import.meta.url` as one atomic sequence (returning `*ast.ImportMetaUrl`) — anything else after `import.meta` (a different member, or `import.meta` alone) is a parse-time error, the earliest and clearest point to reject it, deliberately not deferred to a later "misuse" check the way [TDD-00042](../tdd/TDD-00042.md)'s namespace-import misuse case still is. `import(` is recognized and produces a clear "dynamic import() is not yet supported" error rather than a generic one.
- `parseStatement`'s `IMPORT` case gains one token of lookahead (`p.peekNth(1).Type == lexer.DOT || lexer.LPAREN` routes to `parseExpressionStatement` instead of `parseImportDeclaration`) so `import.meta.url` (or a not-yet-supported `import(...)`) reached at statement-initial position parses through the same expression path rather than hitting `parseImportDeclaration`'s specifier-list parsing and a confusing "expected {" error.

**New AST node**, `ast.ImportMetaUrl{pos}` (`ast/nodes.go`) — deliberately carries no fields; the parser only ever produces it for the complete `import.meta.url` sequence, so there's nothing else for it to represent.

**Resolution.** `resolver/rename.go`'s existing per-file, closure-capturing `rewriteExpr` walk (the same pass that already resolves namespace-import member access, [TDD-00042](../tdd/TDD-00042.md)) gains one more case: `*ast.ImportMetaUrl` is rewritten in place to `ast.NewStringLiteral("file://" + that file's own absolute path, pos)` — a plain string literal by the time codegen ever sees it, needing zero codegen changes, the same "resolver fully consumes this node type" pattern `ImportDeclaration`/`ExportDeclaration` already established. `lookupTable` (`resolver/rename.go`) gained one new field, `filePath string`, set from `resolver.go`'s existing per-file loop (which already has each file's absolute path in scope as `path`) at the same call site that already builds every other per-file lookup table.

## Implementation notes

- `ast/nodes.go`: `ImportMetaUrl` + `NewImportMetaUrl`.
- `parser/parser_literals.go`: `parsePrimary` gains `case lexer.IMPORT`.
- `parser/parser_imports.go`: new `parseImportExpr`.
- `parser/parser_stmts.go`: `parseStatement`'s `IMPORT` case gains the lookahead.
- `resolver/rename.go`: `lookupTable.filePath`; `rewriteExpr`'s new `*ast.ImportMetaUrl` case.
- `resolver/resolver.go`: the `renameFile` call site passes `filePath: path`.
- No codegen changes anywhere — confirmed by the full test/example suite passing unmodified against `codegen/llvm`.

## Side effects discovered

None.

## Verification

- `go build ./...`, `go vet ./...`, `go test ./...` all clean.
- 5 new tests in `tests/import_meta_test.go`: a single-file `import.meta.url` check against the actual resolved absolute path, confirmation that two different files in the same program each get *their own* path (not the entry file's), bare `import.meta` rejected, `import.meta.resolve` (any member but `.url`) rejected, and dynamic `import(...)` producing its dedicated "not yet supported" error. The first two drive `resolver.ResolveProgram`/codegen/`clang` directly (mirroring `buildBinaryMultiFile`'s own implementation) rather than the shared multi-file test helpers, since those don't expose the temp directory needed to compute the expected `file://` path.
- `examples/imports/import_meta_url.ts` (new) — manually run standalone (both `console.log`s print `1`, matching the comments) and via `make examples`: 107/107 passed (106 from [ADR-00146](ADR-00146.md)'s klmpm example plus this one).
