# ADR-00249: Every async function returns a real promise — inline catch-and-settle (TDD-00084 Part A)

- **Relations**: `Implements TDD-00084` (Part A); builds on [ADR-00244](ADR-00244.md), [ADR-00248](ADR-00248.md)
- **Date**: 2026-08-19

## Context

Before this change a *non-suspending* `async` function (one that never awaits a
fetch or another may-suspend fn) was inlined synchronous code returning a bare
malloc'd value slot: it was not a task promise, and a `throw` in its body
propagated *synchronously at the call site* rather than settling a rejected
promise. Real JS: calling an `async` function never throws synchronously — it
always returns a promise, rejected if the body threw. This blocked
`.then`/`.catch`/`.finally` and `Promise.any` on such results (they require a
task promise, [ADR-00248](ADR-00248.md)) — TDD-00084's root cause.

## Decision

**Option A2 — keep the no-fiber fast path, add a catch-and-settle wrapper.** A
non-suspending async fn (and every async arrow / function expression, none of
which are may-suspend-classified) now allocates a real task-shaped promise and
brackets its body in a `setjmp` handler (`emitSettledAsyncPrologue`/`Epilogue`,
emit_async.go):

- normal completion marshals the body's return value into the promise and marks
  it fulfilled (resolved = 1);
- a thrown error is caught (the body `longjmp`s to the catch block), stored, and
  the promise marked rejected (resolved = 2);
- the function returns the promise pointer.

The only cost over the old bare slot is one `setjmp` + a 40-byte promise — **no
fiber, no scheduler**. A may-suspend body keeps its fiber path
(`emitAsyncPrologue` + `emitTaskEpilogue`) unchanged.

**Preserving the "libcurl only when fetch is used" invariant.** A pure-async
program (no fetch) must not link the fiber runtime or libcurl. The whole-program
`hasMaySuspend` flag is the discriminator:

- A new lightweight `ensurePromiseRuntime` emits just the promise struct +
  `__kml_task_alloc_promise` + microtask/exception helpers — no fibers, no fetch.
  The settled-async wrapper, `.then` (emitPromiseThen), and — when
  `!hasMaySuspend` — `await` and the combinators all use it.
- `await` on a task promise reads it directly (it settled inline) when
  `!hasMaySuspend`, versus the scheduler-driven `__kml_task_await_ready` when the
  program has fibers.
- The combinators (`all`/`race`/`allSettled`/`any`) over task promises likewise
  skip the scheduler when `!hasMaySuspend` — settled members are read directly,
  with a scheduler-free `__kml_promise_first_fulfilled` for `.any`.
- The may-suspend classifier no longer marks awaiting *any* `Promise.combinator`
  as suspending — only when an array-literal member is a fetch/may-suspend call —
  so `await Promise.all([f(), g()])` over non-suspending fns stays fetch-free.

**Typing.** `FuncSig.IsAsync` tags a call's result `PromiseTask` for named async
fns; `asyncClosureRetType` does the same for an async arrow/function-expression's
`FuncType.FuncRetType`, so a call through a closure variable takes the task path.

**HTTP handlers excepted.** An `http.listen` handler runs on a connection fiber
and its response object is read straight out of the bare slot by the dispatcher —
it is not a task promise. `http.listen` sets `emittingHTTPHandler` while emitting
its handler arrow, and `emitInlineAsync{Prologue,Epilogue}` keep the old bare-slot
model for it.

## Consequences

- A non-suspending async fn returns a settled promise: `.then`/`.catch`/`.finally`
  (with value-chaining), `Promise.all`/`.any`/`.race`/`.allSettled`, and
  `await` (re-throwing a rejection into a surrounding `try/catch`) all work on
  ordinary async results — no fetch required, no libcurl linked (verified with
  `otool -L`, macOS).
- A throwing async fn rejects its promise instead of throwing at the call site.
- Still Part B (not this ADR): a program mixing tasks with EventSource/WebSocket/
  `http.listen` still has the two mutually-exclusive exit loops; `.then` on a raw
  fetch `Promise<Response>` and `Promise.any` over raw fetches remain out.
- Known divergence unchanged: `await` on an already-settled promise does not yield
  a microtask tick (true microtask-accurate await ordering is separate).
