# ADR-02002: libwasmtime is loaded on first use, and globalThis carries WebAssembly

- **Date**: 2026-11-21

## Context

A program that read `globalThis` as a value linked the WebAssembly natives,
so it needed libwasmtime to link and to run even when it never touched
WebAssembly. And `globalThis.WebAssembly` was `undefined`, even in a
program that named `WebAssembly`; in Node it is the namespace object.

## Investigation

- The WebAssembly backend (threadpoolsrc/klainwasm_wasmtime.c) called the
  wasmtime C API directly and linked `-lwasmtime` (wasm.go `wasmLibs`).
- The zlib unit already loads brotli and zstd with `dlopen`.
- Every backend entry point first runs `kw_cx`, whose `pthread_once` builds
  the engine, so one load there covers every call.
- The backend calls 77 wasmtime functions. libwasmtime exports all of them;
  none is `static inline` in the headers.
- `WebAssembly` was in neither `globalOnGlobalThis` nor `globalObjectOrder`
  (emit_exprs.go), the lists that put a global module's global on the
  global object.

## Decision

- Off Windows the backend keeps wasmtime.h for its types and calls every
  function through a pointer table filled by `dlopen` + `dlsym` when the
  engine is first built. `KW_LIBDIR`, the library directory the compiler
  found, is tried before the loader's own search, so a Homebrew install
  outside the default path still loads. A missing library or symbol fails
  the first WebAssembly call with `WebAssembly: libwasmtime could not be
  loaded: <reason>`.
- Only the headers are needed to compile the unit. Linux links `-ldl`; macOS
  links nothing extra. Windows still links wasmtime as before.
- `WebAssembly` is a non-enumerable property of the global object, in
  Node's order.

## Implementation notes

- codegen/llvm/threadpoolsrc/klainwasm_wasmtime.c: `KW_FNS`, `kw_load`.
- codegen/llvm/wasm.go: `LocateWasm`, `wasmLibDirFlag`, `wasmLibs`.
- codegen/llvm/emit_exprs.go: `globalOnGlobalThis`, `globalObjectOrder`.

## Verification

- Linux x86 (Node304): `const g: any = globalThis; typeof g.WebAssembly,
  typeof g.WebAssembly.Module` prints `object function` as Node does, and
  the binary has no libwasmtime dependency (`ldd`); at HEAD it had one. The
  `Wasm|WebAssembly|Global` E2E tests pass.
- The binary is 131 KB larger than at HEAD (2,922,592 vs 2,791,704 bytes):
  the WebAssembly natives are now in it.
