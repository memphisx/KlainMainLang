# ADR-00552: Number.toString(radix) validates its radix (RangeError)

- **Relations**: Extends ADR-00065
- **Date**: 2026-09-01

## Context

`Number.prototype.toString(radix)` trusted the radix argument without
validation. Real JS throws a `RangeError` ("toString() radix must be between 2
and 36") for a radix outside `2..36`. This was a disclosed caveat on the
number-math status row. A second, now-stale caveat on the same row referenced
"the same sprintf-based exponent padding as the two rows below" — but this
integer digit-loop path emits no exponent, and the two rows below
(toExponential/toPrecision) no longer pad exponents after ADR-00551, so that
caveat was inaccurate and is removed.

## Investigation

`emitNumberToStringRadix` (emit_strings.go) coerces the radix to `i64` and uses
it directly in the `urem`/`udiv` digit loop. The catchable-throw machinery
(`buildErrorObj` + `__kml_throw` + `errorKindIDs`) is already used elsewhere in
codegen, so the check is a small insert.

## Decision

When a radix argument is present, emit a range check right after coercion: if
`radix < 2` or `radix > 36`, build a `RangeError` and throw it before any
formatting. The no-argument case (default radix 10) skips the check entirely.

## Implementation notes

- The check lives inside the `len(args) == 1` branch, so `x.toString()` pays
  nothing.
- Uses `errorKindIDs["RangeError"]` and the standard headered-message path.

## Side effects discovered

Removed the stale exponent-padding caveat from this row (see Context). The
fractional-truncation caveat remains — real JS renders fractional digits in the
target base, which this integer digit-loop does not attempt (matching V8's
exact fractional output would need a distinct algorithm; deferred).

## Verification

`TestE2ENumberToStringRadixRangeError` (radix 1 and 37 throw `RangeError`, 16
works) plus the existing `TestE2ENumberToStringRadix` pass. Built and verified
on Mac (Apple Silicon).
