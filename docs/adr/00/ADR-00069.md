# ADR-00069: Fix division/modulo by zero producing undefined behavior instead of a catchable Error

- **Date**: 2026-07-28

## Context

While scoping how to extend fuzz testing ([ADR-00068](ADR-00068.md)) down into codegen, the plan was to build a correctness oracle for integer arithmetic by generating random expressions and comparing the compiled binary's output against the same expression evaluated in Go with `int64` semantics (see [ADR-00070](ADR-00070.md)). Before writing that generator, a quick manual check of `10 / 0` was needed to know whether the oracle would have to special-case zero divisors.

Repro:

```ts
console.log(10 / 0);
```

Compiled and run on this dev machine (arm64 macOS), this printed `8310554880` — not a crash, not `Infinity`, not `0`, just garbage. `tests/exceptions_test.go`'s existing `TestE2ETryCatchBasic` already demonstrates division by zero going through a manual `if (b === 0) { throw ... }` guard written in user code, which only proves the *language* can express a guard — it says nothing about what the compiler itself does when a program divides by zero without one, and until now nothing did.

## Investigation

`codegen/llvm/emit_exprs.go`'s `/` and `%` cases (both the plain-binary path around what was line 263-280, and the compound-assignment path in `emitArith` around line 672-679) emit LLVM `sdiv`/`udiv`/`srem`/`urem` directly on the operands with no zero check. Per the LLVM Language Reference, integer division/remainder by zero is undefined behavior (`poison`), not merely a trap — under `-O2`, `clang` is free to (and evidently does) miscompile around that UB rather than preserving whatever a specific target's hardware instruction would naturally do. That also makes the *actual* failure mode platform-dependent even without optimization: x86's `idiv` raises `#DE` (`SIGFPE`, hard crash) on a zero divisor, while ARM's `sdiv`/`udiv` instructions are defined to return `0` — so the same source line was already latent to behave three different ways (garbage under `-O2` on arm64, most likely `SIGFPE` on x86_64, `0` only on unoptimized arm64) depending entirely on build flags and CPU architecture, none of which is a defined, catchable outcome.

The fix precedent already exists in this codebase: `emitIndexPtr` (`codegen/llvm/emit_exprs.go:905`, added in [ADR-00044](ADR-00044.md)) guards array indexing with a runtime bounds check that throws a catchable `Error` via the existing `setjmp`/`longjmp` exception machinery (`e.ensureExceptionHelpers()` + `@__kml_throw`) rather than letting an out-of-range GEP read garbage memory. Division by zero is the same shape of problem — a specific input value makes an otherwise-fine instruction undefined — so the same pattern applies directly.

Float division/modulo (`fdiv`/`frem`) were left untouched: IEEE-754 already gives `x / 0.0` a well-defined value (`Infinity`/`-Infinity`/`NaN`), matching real JS's float-division semantics, so no guard is needed or wanted there.

Considered whether to also guard the unary negation / other arithmetic paths for similar UB — none of `add`/`sub`/`mul` carry `nsw`/`nuw` flags in this codegen (confirmed by grep), so they're plain wrapping two's-complement, not UB, and don't need this treatment.

## Decision

Added `emitDivZeroGuard(ty Type, right Value)` in `codegen/llvm/emit_exprs.go`, placed immediately before `emitIndexPtr` since it mirrors that function's bounds-check shape: for a non-float type, it emits `icmp eq` against zero on the divisor, branches to a `div.zero` block that throws `new Error("Division by zero")` via the same `@__kml_throw` mechanism as the array bounds check, or falls through to a `div.ok` block where the actual `sdiv`/`udiv`/`srem`/`urem` is emitted. Called from both `emitBinary`'s `/`/`%` cases and `emitArith`'s `/` case (the compound-assignment path — `emitArith` has no `%` case at all today, so `%=` is unaffected; it already fails to compile with a clear "unknown arithmetic operator" error, an existing, unrelated, non-silent gap not addressed here).

## Implementation notes

Files touched: `codegen/llvm/emit_exprs.go` (new `emitDivZeroGuard`, called from `emitBinary`'s `"/"`/`"%"` cases and `emitArith`'s `"/"` case), `tests/exceptions_test.go` (new test), `examples/try_catch/division_by_zero.ts` (new example).

`reg := e.freshReg()` in both call sites is allocated before the guard branches; the guard's `div.ok` block is what actually emits the `sdiv`/`udiv`/`srem`/`urem` instruction into `reg`, and control always reaches code using `reg` from inside that block (the `div.zero` branch ends in `unreachable`), so there was no SSA-ordering issue introducing the branch mid-expression — the same reasoning `emitIndexPtr`'s existing bounds check already relies on.

## Side effects discovered

None beyond the bug this ADR fixes.

## Verification

- Manual repro before the fix: `10 / 0` on arm64 macOS printed `8310554880` (`-O2`, garbage from UB, not a crash).
- Manual repro after the fix: `10 / 0` and `10 % 0` both throw a catchable `Error` with message `"Division by zero"`; `x /= 0` too. Normal division/modulo (`10 / 2` → `5`, `10 % 3` → `1`, `-7 / 2` → `-3`, `-7 % 2` → `-1`, truncating toward zero) unaffected.
- New test `TestE2EDivisionByZeroThrows` in `tests/exceptions_test.go`, new example `examples/try_catch/division_by_zero.ts`.
- `go test ./...` — full suite passes (`go test ./lexer/... ./parser/...` cached/ok, `go test ./tests/...` 83.7s, all green).
