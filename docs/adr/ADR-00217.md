# ADR-00217: `-compat` compatibility axis (step 1) — absorb `-globals`, add bigint cross-type comparison

- **Date**: 2026-08-18
- **Relations**: Implements [TDD-00075](../tdd/TDD-00075.md) (step 1); extends [ADR-00143](ADR-00143.md) (absorbs its `-globals` flag) and [ADR-00216](ADR-00216.md) (bigint)

## Context

While retiring `bigint`'s caveats ([ADR-00216](ADR-00216.md)), a recurring shape surfaced: some divergences from JS are neither bugs nor permanent narrowings but *deliberate choices where the compiler is stricter/safer than JS* — e.g. rejecting `10n < 5.5`, which is almost always a bug. [TDD-00075](../tdd/TDD-00075.md) scoped a single named axis for these — `-compat=strict|js` — generalizing the existing one-off `-globals=strict|permissive` and giving such behaviors a home instead of accreting them as caveats.

This ADR is step 1 of that TDD: land the axis, **absorb `-globals` into it**, and use it to reclassify `bigint`'s float-comparison behavior — while also shipping the always-correct integer cross-type comparison that was previously (wrongly) lumped into the same caveat.

## Investigation

- `-globals` (from [ADR-00143](ADR-00143.md)/[TDD-00050](../tdd/TDD-00050.md)) is purely resolver-side: `main.go` passes `*globals == "permissive"` to `resolver.ResolveProgramWithOptions(entry, allowGlobalShadowing)`. The emitter has no globals state — the codegen shadowing guards (`isShadowedByLocal`) are unconditionally correct regardless of mode. So absorbing `-globals` is a flag-surface rename, not a behavior change.
- The escape-hatch string `-globals=permissive` appeared in two resolver error messages, one test assertion (`reserved_globals_test.go`), and one example — all needing to point at `-compat=js`.
- The `bigint`↔`number` "no cross-type comparison" caveat ([ADR-00216](ADR-00216.md)) actually conflated two things: JS *permits* `10n < 5` / `10n == 10` (mathematical comparison), which we could support exactly for an **integer** number by lifting it to a bigint; the genuinely hard case is only a **float** operand (exact bigint-vs-double comparison), which the TDD deferred.

## Decision

**Add `-compat=strict|js` (default `strict`); remove `-globals`.** `-compat=js` drives `allowGlobalShadowing` in the resolver (so the ambient-global-shadowing behavior is identical to the old `-globals=permissive`, `new`-form built-ins still reserved). A clean removal, not a deprecated alias — the project makes no cross-commit stability guarantee. A `compatMode` field + `compatJS()` is threaded to the emitter for emitter-side inhabitants (currently just the differentiated bigint-float error message; future inhabitants like `&&`/`||` value-preserving will use it).

**`bigint` cross-type comparison, split by operand:**
- **Integer `number`** (`10n < 5`, `10n == 10`, `5 < 10n`, a variable `let x = 100; 50n < x`): supported in *both* modes, exact — the integer is lifted to a bigint via `from_i64` and compared with the same `cmp` ABI. This is correct JS behavior *and* good design, so it is always-on, not a `-compat` inhabitant.
- **Float `number`** (`10n < 5.5`): a clean compile error under `strict` (the default) — the value is almost always a bug, so forcing an explicit `BigInt()`/`Number()` is the better behavior. Under **`-compat=js`** it does JS's **exact** real-number comparison, implemented via a new ABI call `__kml_bigint_cmp_double`: a finite double is exactly `M · 2^e` for an integer `M` (≤53 bits) and integer `e` via `frexp`, so the comparison reduces to an exact bigint compare with no rounding — correct even past 2^53 (e.g. `2n**53n + 1n > 9007199254740992.0` is `true` and `== ` is `false`). NaN is handled as "unordered" (every ordered comparison false, `!=` true). Both backends use this explicit decomposition rather than GMP's `mpz_cmp_d` (whose truncation semantics are version-dependent), keeping the two identical.

Arithmetic mixing (`10n + 5`) stays a clean compile error in both modes (matches JS's `TypeError`). `===`/`!==` across types stay constant `false`/`true`; `bigint`-vs-`null` equality is handled (never equal).

**Reframe, not a fix:** the float-comparison rejection moves *out* of `bigint`'s Caveats and into the `-compat` framing (a Cross-Cutting row + a per-row note) — it is now a documented design choice, not an unfinished caveat.

## Implementation notes

- **Flag/plumbing**: `main.go` `-compat=strict|js` (validated), feeding `ResolveProgramWithOptions(entry, *compat == "js")` and `em.SetCompatMode(*compat)`; `-globals` removed. `emitter.go` gains `compatMode` + `SetCompatMode` + `compatJS()`.
- **Resolver**: the two `checkReservedBinding` messages now name `-compat=js`; comments across `resolver/*.go` updated.
- **bigint** (`emit_bigint.go`): the mixed-operand branch in `emitBinary` now calls `emitBigIntMixed`, which routes null-equality, `===`/`!==` constants, integer cross-comparison (via `bigintOperand` → `from_i64`), the float case (strict reject / `-compat=js` `emitBigIntFloatCompare` → `__kml_bigint_cmp_double`, with an operand-swap when the bigint is on the right and a NaN-sentinel `select`), and the arithmetic-mixing error. `isIntegerNumberTy` gates which operands can be lifted (i8…i64, excluding bool/float/ptr/reference types). The exact `__kml_bigint_cmp_double` lives in both C backends (`<math.h>` `frexp`/`ldexp`).
- **Docs**: README CLI-flags (`-globals`→`-compat`, plus `--help` note from the same session); `docs/status/` Cross-Cutting row renamed to "Compatibility mode (`-compat`)"; `GLOBAL-FUNCTIONS.md` and the `bigint` row reworded; historical ADRs/TDDs left unedited (they correctly describe `-globals` as it was).

## Side effects discovered

- Implementing the float comparison surfaced two latent `bigint` bugs, both fixed here: (1) `isStringTy` treated a bigint — a bare `ptr`, not `IsObject` — as a **string**, so `"x" + 10n` would have `strcmp`'d the handle (fixed: `!ty.IsBigInt`); (2) `inferExprType` didn't infer bigint for a binary *expression*, so `const x = 2n ** 53n + 1n` typed `x` as a string/i64 (fixed: a bigint operand → bigint arithmetic result, comparison → bool). String↔bigint concatenation (`"x" + 10n` → `"x10"`) now works and is correctly excluded from the bigint operator branch. These were pre-existing gaps in [ADR-00216](ADR-00216.md)'s V1, unreached by its tests.
- `bigint`↔float comparison is the axis's first genuinely emitter-side inhabitant with divergent codegen (`compatJS()` selects it); global shadowing stays resolver-side.
- `bigint` vs a `boolean` or other non-integer, non-float scalar is a clean "can only compare with a bigint or integer number" error rather than JS's coercion (`10n == true` → `true` in JS) — a rare edge, left as a narrow documented gap.
