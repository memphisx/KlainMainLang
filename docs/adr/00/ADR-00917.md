# ADR-00917: Async function expression returns a Promise-typed define (invalid-IR sweep)

- **Date**: 2026-09-12

## Context

An `async function () { … }` expression that falls off the end (no explicit
`return`) emitted invalid LLVM IR: the `define` was typed `void`, but the inline
async epilogue returns the settled promise pointer (`ret ptr`). clang rejected it
with `value doesn't match function result type 'void'`. Surfaced in the Test262
CLANG_ERROR sweep — the `language/expressions/async-function/try-*-finally-*`
family (async functions whose only exits are through a `try`/`finally` that
`await`s, so the block has no inferable return) plus
`language/function-code/10.4.3-1-85{,gs}.js`-adjacent async shapes.

## Investigation

- `emitArrowFunctionWithHints` already wraps a non-promise inferred/void return
  type in `Promise<…>` for an async arrow (`emit_func.go`, the `af.IsAsync &&
  !retTy.IsPromise` guard added for ReadableStream's async pull), so the emitted
  define's `ret ptr` matches its signature.
- `emitFunctionExpression` resolves its return type (annotation →
  `inferUnannotatedReturnType` → `void`/`TypeF64` fallbacks) but never applied the
  same async wrapping, so an async function *expression* with no inferable return
  kept a `void`/scalar signature while its epilogue returned the promise pointer.

## Decision

After `emitFunctionExpression` resolves `retTy`, wrap it exactly as the arrow path
does: `if fe.IsAsync && !retTy.IsPromise { retTy = PromiseOf(retTy) }`. The
`selfTy` used for a named function expression's self-reference is built from the
wrapped `retTy`, so recursion sees the Promise type too.

## Implementation notes

- One addition in `codegen/llvm/emit_func.go`, right after the return-type
  resolution block and before `selfTy` is constructed.
- This only corrects the emitted *signature*. The `try/finally`-with-`await`
  rejection family still fails at *runtime* for a separate, pre-existing reason
  (see Side effects) — but those files are no longer invalid IR.

## Side effects discovered

A rejected promise's handler path crashes: `new Promise((_, reject) => reject(x))`
followed by `.then(onFulfilled, onRejected)` (or `.catch`) **segfaults**
(exit 139) — the reject/catch handler is never invoked. This affects direct
`new Promise` rejection, `Promise.reject`, and any async function that `throw`s or
awaits a rejected promise, across named/arrow/function-expression forms. It is a
distinct, larger runtime bug (the promise rejection-settlement → microtask
handler path), not addressed here; flagged for its own investigation.

## Verification

- `TestE2EAsyncFunctionExpressionReturnsPromise` (new): a fall-off-the-end async
  function expression resolves and its `.then` fulfill handler fires.
- The four `async-function/try-*-finally-*` Test262 files now compile (were
  CLANG_ERROR); they remain runtime failures pending the rejection-handler bug.
- Normal async function expressions (annotated `Promise<void>`, `return 42`,
  no-annotation fall-off-end) unchanged. `go test` function/closure/async lane
  green. macOS arm64.
