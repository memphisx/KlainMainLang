# ADR-01022: Windows IOCP reactor Stage 2 — sockets and pipes on the completion port

- **Relations**: `Implements TDD-00183` (Stage 2); `Extends ADR-00865` (Stage 1), `ADR-00864` (the owned fd table); relates to `ADR-01021` (async `net.connect`, the `EINPROGRESS` path `ConnectEx` serves)
- **Date**: 2026-09-20

## Context

After Stage 1 (ADR-00865) the Windows reactor blocked on its completion port only for a program that watched nothing but stdin, the console, or a child's stdin. Every watched **socket** still went through a Winsock `select` probe taken in slices (10 ms; 50 ms with a console-ctrl handler installed), and every `pipe()` read end — a child's stdout/stderr, a worker's or channel's inbox — was an anonymous pipe re-probed with `PeekNamedPipe` every 10 ms. An idle HTTP server, or a parent waiting on a child, woke a hundred times a second. TDD-00183 Stage 2 is the removal of all of it: "the wait is one `GetQueuedCompletionStatusEx` always."

A first pass at Stage 2 existed in the working tree (an `IOCTL_AFD_POLL` arm in `select()`, helpers for a zero-read). This ADR covers auditing that pass, replacing what was wrong in it, and finishing the stage.

## Investigation

Each claim below was checked with a standalone C program against the real APIs before anything was built on it.

- **The first-pass AFD poll never woke the port.** It called `NtDeviceIoControlFile(…, ApcContext = NULL, …)`. A completion packet is queued only when `ApcContext` is non-NULL — that value *is* the packet's `OVERLAPPED` pointer. Measured: with `NULL` the poll completes (its output buffer fills in) and `GetQueuedCompletionStatus` times out; with the op pointer the packet arrives. The arm was also unreachable for most programs (it was gated on a port that only the stdin/console paths created), and where it was reached the 50 ms signal slice hid that the wake never came. A green suite proved nothing about it, which is why the acceptance tests below measure *how* the reactor waits.
- **AFD poll does not need the socket on the port.** Issued on a handle to `\Device\Afd` that is itself associated with the port, with the polled socket named inside the request (libuv's and wepoll's arrangement), the poll completes to our port for any socket — measured. The first pass issued it on the socket's own handle, which forced a permanent port association onto every polled socket and was the stated reason foreign (libcurl) sockets were left on a bounded Winsock `select`.
- **A datagram zero-read is safe with `MSG_PEEK`.** The working tree recorded UDP as unable to use a zero-read ("discards the datagram"). Measured: a zero-byte overlapped `WSARecv` **with `MSG_PEEK`** completes with `ERROR_MORE_DATA` when a datagram is queued (before or after arming) and the following `recvfrom` returns it intact. This is exactly what TDD-00183 specifies and what libuv's udp zero-read does; the recorded deviation came from omitting the flag.
- **A failed port association is not benign.** `CreateIoCompletionPort` on an already-associated handle fails with `ERROR_INVALID_PARAMETER` (measured), and the association belongs to the socket object, not the handle: a listener a cluster worker inherited is on the *primary's* port (or the primary's on the worker's, whoever armed first). A plain overlapped op on it queues a packet carrying our `OVERLAPPED` pointer to the other process's port. The first pass treated the failure as "already on our port".
- **Why the earlier overlapped-`pipe()` attempt regressed worker IPC** (ADR-00865, Side effects): readiness was re-derived by probing `PeekNamedPipe` after the zero-read's wake, and the probe missed data the completion had signalled. Taking readiness *from the completion* removes the failure mode by construction.
- Every `pipe()` call site in the emitted IR has one shape — the read end stays with a reactor, the write end goes to a producer thread or an inheriting child (`runtime_chan.go`, `runtime_worker.go`, `runtime_cluster.go`, `runtime_childprocess.go`, `runtime_process.go`); the one opposite shape (a child that reads) already has its own creator, `__kml_win_pipe_pw`.
- The IR's async connect (ADR-01021) decides completion by `getsockopt(SO_ERROR)`, then a second `connect()` answering `0`/`EISCONN` (connected) or anything else (keep waiting) — `runtime_net.go` `complc`/`compltry`. `ConnectEx` reports failure through its completion, not through the socket's `SO_ERROR`, so the shim has to present that contract itself.

## Decision

Readiness is a set of **per-fd ready bits written by the port drain** and projected onto the IR's bitmaps by `select()`. A reported bit is consumed; the I/O call that uses the condition up clears it too; a condition that still holds completes again at once on the next arm — which is what makes the one-shot completion model level-triggered. The Winsock `select` probe, the 10 ms and 50 ms slices, and the no-port `Sleep` fallback are deleted. Every thread that calls `select()` owns a port, and the only wait is `GetQueuedCompletionStatusEx` on it, bounded by the caller's deadline.

- **Connected stream socket, read-interest**: zero-byte overlapped `WSARecv`. Data, FIN and reset all complete it; only our own cancellation does not set the bit.
- **Datagram socket, read-interest**: the same with `MSG_PEEK` (completes with "more data", consumes nothing).
- **Listener, read-interest**: one posted `AcceptEx` into a pre-created socket. `accept()` first drains the port and pops a completed connection (`SO_UPDATE_ACCEPT_CONTEXT`), which keeps connections in arrival order; with no `AcceptEx` outstanding it reads the backlog directly (a never-watched listener, or the rest of a burst); with one outstanding and nothing completed, the backlog is empty by construction, so a non-blocking listener answers `EAGAIN` and a blocking one waits on the port.
- **Non-blocking stream connect (AF_INET/AF_INET6)**: `ConnectEx`, bind-first (wildcard, as `connect()` binds implicitly). It reports `EINPROGRESS`, synchronous success included; the drain records the outcome — success sets `SO_UPDATE_CONNECT_CONTEXT` and the write bit; failure stores the mapped errno and leaves the socket readable, writable and excepted for as long as anyone asks, the way a POSIX socket holds its error. `getsockopt(SO_ERROR)` hands the stored error out once; a second `connect()` answers `EALREADY` while pending and `EISCONN` after. Other families keep the plain non-blocking `connect()` and learn the outcome from an AFD poll.
- **Write-interest and the except set** on owned sockets, and **both directions of a foreign (libcurl) socket**: `IOCTL_AFD_POLL` on the reactor's helper device, `ApcContext` = the op. One poll per socket stays in flight across `select()` calls and is cancelled-and-replaced only when the interest mask changes. A retired foreign slot cancels its poll and bumps its generation.
- **Sockets that cannot join this port** (another thread's, another process's): the op carries an event with its low bit set — the kernel signals it and queues nothing — and a registered wait forwards the signal to our port as an ordinary packet. This is libuv's emulated-IOCP path, used for the same sockets.
- **`pipe()`**: fds[0] is an overlapped inbound named-pipe server end, fds[1] a synchronous client end. Read-interest is a zero-byte overlapped `ReadFile` on the port; already-buffered bytes answer without arming; a broken pipe is readable (EOF). `read()` on the overlapped end is an overlapped `ReadFile` waited for inline (non-blocking: bounded by what is buffered, and when a completion claimed data the probe denies, the read itself is tried and cancelled if it pends).
- **Inherited pipe handles** are asked how they were opened (`FileModeInformation`, as libuv does): synchronous ones — not just fd 0 — are read through the buffering reader thread; overlapped ones take the overlapped paths.
- **Wake routing is addressed, not "first port created"**: a reader thread wakes the port of the reactor that started it; a signal wakes the port of the signal-delivering thread. A worker spawned at top level can reach its first `select()` before the main loop does, so "the first port" is not reliably the main reactor's.

No behaviour is left behind a caveat. The one remaining bounded wait — a 10 ms re-probe — applies only to a pipe handle that can be neither port-armed nor given a reader thread, which no path in the emitted IR or the std-fd classifier produces.

## Implementation notes

- All in `codegen/llvm/win32src/win32io.c`. `kfd_op` gained the AFD device, the AcceptEx socket + address block, and the emulation event/wait/port; `kfd_slot` gained the ready bits, connect state, `family`/`bound`, the associated port, and the pending Accept/Connect ops. `kfd_adopt_socket` reads a socket's shape off the socket (`SO_TYPE`, `SO_ACCEPTCONN`, `getsockname`), because an inherited listener never passed through this layer's `socket()`/`listen()`.
- Ownership rule: a socket or AFD op always posts a packet (no `FILE_SKIP_COMPLETION_PORT_ON_SUCCESS` on sockets or the helper device), so from the moment it is issued the drain owns it. Only a synchronous *failure* is freed by its creator. Pipe write ops keep the Stage 1 skip-on-success rule.
- Op status comes from `OVERLAPPED.Internal`, which holds the NTSTATUS for a native op, an AFD poll (its `IO_STATUS_BLOCK` is overlaid on the `OVERLAPPED`) and an emulated op alike; a connect's Winsock error comes from `WSAGetOverlappedResult`.
- `close()` cancels the socket's ops (`CancelIoEx(handle, NULL)` is process-scoped, so an inherited listener's other owner is untouched), closes a connection `AcceptEx` took that `accept()` never popped, and bumps the generation; cancelled ops still post, and the drain frees them as stale.
- `KML_IO_TRACE` gained one `[io] wait slice=N` line per blocking wait and the op status on each `port op` line.
- TDD-00183's Verification section names its suites `TestE2EHttp|TestE2ETls`; the suites are `TestE2EHTTP*`/`TestE2ETLS*`, so a run using the TDD's pattern silently skips HTTP and TLS. Use a case-insensitive pattern.
- TDD-00183's Context cites a "no-throwaway" reading of the faithfulness rule. That rule says only that observable behaviour matches Node and diverges solely for a genuine native-compilation impossibility; it says nothing about throwaway work. The design stands on its own merits (it is libuv's); the cited justification does not exist.
- The ConPTY harness (`tests/conpty_windows_test.go`) now also exposes the console's output with VT sequences stripped (`Text`). conhost emits its own sequences (the window-title OSC) at arbitrary byte boundaries, including mid-line, which is what failed `TestE2ETtyConsoleRawReadKey` on the CI runner: the program's output was correct and an OSC landed inside it.

## Side effects discovered

Two pre-existing bugs, in the emitted IR on every platform, surfaced while writing the acceptance tests. Neither is a reactor bug and neither is fixed here:

- **A top-level `await fetch()` / `fetch().then()` busy-spins and starves the loop.** Outside a connection fiber `__kml_await_fetch` loops on `curl_multi_perform` without running the event loop (`runtime_fetch.go`, "nothing else could run concurrently in that case anyway"). Timers and other I/O starve for the duration at 100 % CPU, and a program that fetches from its own server deadlocks (the server is never accepted).
- **Child exit is polled, and only after stdio EOF.** `__kml_cp_finalize` calls `waitpid(WNOHANG)` once both stdio pipes are at EOF and the loop re-enters `select()` with a zero timeout until the reap succeeds — 32 198 iterations in 2 s for a child that closes its stdio and keeps running. It also means `'exit'` cannot fire before the pipes close, where Node fires `'exit'` at process exit and `'close'` after stdio ends.

## Verification

Windows dev box (Windows 11, MSYS2 UCRT64 clang 22):

- The four API facts in Investigation: standalone C programs (zero-byte `MSG_PEEK` receive; AFD poll on a helper device with and without `ApcContext`; re-association of an associated handle).
- `win32io.c` compiles clean under `-Wall -Wextra`; `go build`, `go vet ./...` clean.
- `KML_IO_TRACE` on `examples/net/client_server.ts` and `connect_error.ts` shows `ConnectEx` (op kind 5), `AcceptEx` (4) and zero-read (1) completions through the port; the refused connect completes with `STATUS_CONNECTION_REFUSED` and surfaces as `connect ECONNREFUSED 127.0.0.1:1`.
- New `tests/reactor_windows_test.go`: an idle parent of a 1.5 s child and an idle listener with a SIGINT handler each take **one** blocking wait (a 10 ms slice would take ~150); a 40-datagram burst is delivered whole and in order; a handler awaiting a slow upstream shows AFD poll completions for libcurl's socket (an fd in the foreign range) arriving through the port.
- The emulated-completion path has no E2E program that reaches it — each Windows cluster worker currently binds the port for itself rather than sharing one listener (the TDD-00177 cluster gap), so nothing in the emitted runtime shares a socket across ports yet. It is therefore tested natively: `tests/reactor_emulated_windows_test.go` builds `tests/testdata/win32/emulated_completion.c` against the shim sources; the C program associates a listener and then an accepted socket with a *foreign* completion port first, drives them through the shim's own `select()`/`accept()`/`read()`, and asserts the emulated `AcceptEx` and zero-read complete, EOF is reported, and nothing of ours is ever queued to the foreign port.
- Regression: the net, dgram, signal, HTTP/HTTPS, TLS, WebSocket, streams, fetch, cluster, worker, channel, child_process, readline and stdin suites, and the full `go test ./...` run.
- Linux/macOS are untouched by this change (Windows-only C, Windows-gated tests); CI's POSIX lanes are the guard.
