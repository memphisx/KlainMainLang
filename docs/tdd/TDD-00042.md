# TDD-00042: `export default`, default imports, and namespace imports

- **Status**: Implemented
- **Date**: 2026-08-09
- **Notes**: Namespace imports are compile-time-only, never a runtime value; re-exports deliberately left for a future TDD

## Context

[TDD-00041](TDD-00041.md)/[ADR-00134](../adr/ADR-00134.md) just gave every file's top-level declarations true per-file scope via mangled internal names, plus real import aliasing. [MODULES.md](../status/MODULES.md) lists three remaining named-import-adjacent gaps at ~46% coverage: `export default`, `import * as ns from '...'` (namespace import), and re-exports (`export { x } from './other'`). This TDD scopes the first two — they share enough machinery (both are extensions of the same mangled-name lookup table `resolver.ResolveProgram` already builds) to design together. Re-exports are a distinct problem (a file re-publishing a name it didn't itself declare, which touches the `exported`/`mangled` maps' per-file assumption differently) and are left for a future TDD rather than folded in here.

Picked as the next module-system slice specifically because it builds directly on TDD-00041's still-fresh mangling infrastructure rather than starting a new area cold.

## Design

### `export default`

Real ES modules bind a default export as a distinct export key (`"default"`) separate from any named exports — `export default function foo() {}` does **not** make `foo` importable via `import { foo }`, but `foo` does remain a valid identifier for the rest of that file (recursion, self-reference in static members, etc.).

This compiler's `exported` map (`resolver.go`) is currently `map[string]bool` keyed by original declaration name, and `mangled` is `map[string]string` from original name to this file's mangled name. Both are reused unchanged — `"default"` is just one more possible key in each, alongside a real declaration's own name. That means the only new work is populating that key correctly:

- **Named form** (`export default function foo() {...}`, `export default class Foo {...}`, `export default interface Foo {...}`, `export default type Foo = ...`, `export default enum Foo {...}`) — the declaration keeps its own name (`"foo"`) for mangling and intra-file self-reference, exactly like a normal `export`. `mangleFileDecls` additionally aliases `mangled["default"] = mangled["foo"]` when it sees the wrapping `ExportDeclaration.IsDefault`. `exportedNames` adds `"default"` to the export set for that file (in addition to *not* adding `"foo"` itself as a named export — matching real ES module semantics, and cheap to get right since `exportedNames` already only walks `ExportDeclaration` nodes explicitly).
- **Anonymous form** (`export default function() {...}`, `export default class {...}`) — reuses the exact same path by giving the declaration the literal name `"default"` instead of a real identifier. This is safe and permanently collision-free: `default` is a reserved lexer keyword (`lexer.DEFAULT`, confirmed via `lexer/token.go` — used today by `switch`'s `default:` clause), so no real top-level declaration can ever be named `default` via normal parsing. Once the declaration's `Name` is `"default"`, `mangleFileDecls`'s existing generic per-declaration mangling handles it with zero special-casing — no separate alias step needed for this sub-case since the declaration's own name already *is* `"default"`.
- **Expression form** (`export default 42;`, `export default someExpr;`, `export default () => {...};`) — wrapped at parse time as `ast.VarDeclaration{Kind: "const", Name: "default", Init: expr}`, then handled identically to the anonymous-declaration case above. Reuses `VarDeclaration` rather than inventing a new AST node.

`ast.ExportDeclaration` gains one field: `IsDefault bool`. `ast.NewExportDeclaration`'s signature grows a parameter accordingly (all current call sites updated).

Only one `export default` is allowed per file (matches real ES modules) — enforced the same way in-file duplicate declarations already are: `Name == "default"` colliding is caught for free by `mangleFileDecls`'s existing duplicate check, since both the anonymous-declaration and expression-wrapper paths route through `Name = "default"`; the *named* form's `mangled["default"] = ...` alias assignment needs one explicit "already set" check alongside it (a second `export default` in the same file, e.g. `export default function foo(){}` followed later by `export default function bar(){}`, must be rejected — `foo`/`bar` don't collide against each other via the normal duplicate check since they're different names, only the `"default"` alias assignment would silently overwrite).

### Default import

`import Foo from './path'` and the combined `import Foo, { a, b } from './path'` are sugar for a specifier list. Reusing the existing `ast.ImportSpecifier{Imported: "default", Local: "Foo"}` shape (prepended to whatever named specifiers follow) means **zero resolver.go changes are needed beyond what `export default` above already provides** — the existing per-specifier validation loop (`target.exported[spec.Imported]`) and lookup-building loop (`lookup[spec.Local] = target.mangled[spec.Imported]`) already handle any string key, `"default"` included, with no awareness that anything special is happening.

Only `parser/parser_imports.go` changes: branch on the token right after `import` — `{` keeps the existing named-only path; a bare `IDENT` parses a default specifier, optionally followed by `, { ... }` for the combined form; `*` is the namespace form (below).

**Deliberately out of scope**: `import Foo, * as ns from './path'` (combined default+namespace) — valid in real ES modules but rare, and adds a second combination path for little payoff. `import Foo from './path'` and `import * as ns from './path'` each work standalone.

### Namespace import (`import * as ns from './path'`)

This is the one genuinely new mechanism. Real ES modules make `ns` a live namespace object at runtime — every export reachable as `ns.exportName`, `ns` itself passable as an ordinary value (stored in a variable, passed to a function, etc.).

This compiler has no runtime module-object representation, and building one would be real, disproportionate work: exports mix genuine runtime values (functions, consts, classes) with pure compile-time constructs (interfaces, type aliases, enums-as-types), and this compiler's objects are fixed-shape heap structs (see [OBJECT-COLLECTIONS.md](../status/OBJECT-COLLECTIONS.md)'s dynamic-property-bag gap) — there's no existing mechanism to build an ad hoc struct-of-mixed-member-kinds shape at compile time from an arbitrary imported file's export list.

**Decision: `ns` is a compile-time-only construct, fully erased during resolution — never a runtime value.** `import * as ns from './path'` records that the local name `ns` is bound to a whole file (not a single mangled name, unlike every other import form). `ns.member` — a non-computed `MemberExpression` whose `Object` is an `Identifier` bound to a namespace import — is rewritten during the resolver's existing rename pass into a direct reference to that member's mangled name, exactly as if the code had written a normal named import for just that one member. This matches this compiler's whole-program-merge design ethos already established for named imports/aliasing: nothing about modules survives past `resolver.ResolveProgram` into `codegen/llvm`, and this is no exception — `codegen/llvm` needs zero changes.

Consequences of this choice, all deliberate scope narrowings for V1:

- **`ns` used anywhere other than as the object of a non-computed dot-access is unsupported.** `const x = ns;`, `someFunc(ns)`, `console.log(ns)`, `ns["foo"]` (computed — moot anyway, since this AST's `MemberExpression.Property` is already a plain `string`, not an expression; only `IndexExpression` supports a computed/dynamic operand, and that's reserved for array/map indexing) all fall through unresolved. No special detection/error is added for this — an unresolved `ns` identifier simply reaches codegen as a genuinely undefined reference and fails there with codegen's existing "unknown identifier" error. That error is generic (it won't say "namespace values aren't supported"), which is an accepted quality gap for V1 rather than a functional one.
- **Type-position namespace access (`let x: ns.SomeInterface`) is unsupported.** `ast.TypeAnnotation.Name` is a flat string (with a special flattened `"Foo[]"` array-suffix encoding, per TDD-00041's own side-effect finding) and has no dotted-path representation — teaching the type grammar a qualified-name form is real, separate parser work, not a resolver-side concern like the value-position case above. Left for later; only named/default type imports (`import { Foo } from ...` / `import Foo from ...` used as a type annotation) are affected — both already work today via the plain mangled-name substitution path, no change needed.
- **`new ns.SomeClass(...)` is unsupported** — but this is not a namespace-specific gap: `parser.parseNew` (`parser/parser_literals.go:111`) already requires a single `IDENT` token after `new`, with no member-expression form at all, regardless of namespaces. Confirmed by direct inspection rather than assumed. Not a new restriction introduced by this TDD.

**Implementation shape**: the existing rename pass (`resolver/rename.go`) recurses through every expression node via direct in-place field mutation (`e.Left = ...` never happens — instead, e.g. `rewriteExpr(e.Left, sc, lu)` mutates identifiers found deeper inside `e.Left` in place, relying on every node already being a pointer). That works for renaming an `Identifier.Name` string in place, but *cannot* replace an entire node's dynamic type (swap a `*ast.MemberExpression` for a `*ast.Identifier`) without the caller reassigning the field — which the current signature (`rewriteExpr(expr ast.Expression, sc *scope, lu map[string]string)`, no return value) has no way to do.

Two ways to close that gap, considered:

1. **Change `rewriteExpr`'s signature to return `ast.Expression`**, and update every one of its ~40 call sites (`e.Field = rewriteExpr(e.Field, sc, lu)` / `arr[i] = rewriteExpr(arr[i], sc, lu)` instead of the current bare `rewriteExpr(e.Field, sc, lu)`) so a replaced node actually propagates back into the tree. Mechanical, but touches most of `rename.go`.
2. **A second, separate, self-contained tree-walking pass** (new file, e.g. `resolver/namespace.go`) that runs *before* `renameFile`, walking the same expression/statement/type shapes but solely to find-and-replace `ns.member` patterns, using its own return-based signature — leaving `rename.go` completely untouched.

**Recommendation: option 1.** Option 2 avoids touching working, tested code, but requires re-implementing a second full expression/statement/type walker with the same shape as `rewriteExpr`'s existing ~30-case switch — a real duplication-maintenance cost (every future new AST node kind would need updating in two parallel walkers instead of one). Option 1's mechanical churn is a one-time cost; option 2's duplicated-walker cost is ongoing. Given this project's own practice of preferring one real mechanism over a parallel one (see e.g. TDD-00041 folding aliasing into the same mangling pass rather than a separate rename step), option 1 is the more consistent choice. Implementation should double check every call site is updated — a missed one fails silently (the old node stays in place, uncompiled `ns.member` reaches codegen and errors there) rather than at compile-of-the-compiler time, since both the old and new signatures involve `ast.Expression`-typed values.

Namespace bindings need their own lookup table, separate from the existing `lu map[string]string` (a flat local-name → mangled-name map that doesn't fit "alias name → (member name → mangled name)"). `renameFile`/`rewriteExpr`/etc. gain a second parameter (or `lu` becomes a small struct bundling both tables) threaded alongside the existing one.
