# ADR-00170: Destructured catch binding (`catch ({ message, name }) {}`)

- **Relations**: Extends [ADR-00086](ADR-00086.md); reuses `unpackObjectPatternInto` (shared with destructured function parameters and `const {..} = ..`)
- **Date**: 2026-08-12

## Context

Sampling the Test262 conformance harness's largest still-unexplained failure buckets after [ADR-00169](ADR-00169.md) found a new 4th-largest bucket, "expected IDENT, got {" (3286 files) — mostly files where object-literal method shorthand (ADR-00169) now parses far enough to reach a real `catch ({ ... })` destructuring pattern this compiler's `catch` clause couldn't parse at all: `catch (e)` only ever accepted a bare identifier.

## Investigation

The caught value's actual runtime shape is always `errorObjType` — `codegen/llvm/emit_exceptions.go`'s `buildErrorObj` builds this exact `{i64 kind, ptr message, ptr name}` struct for every thrown value this compiler handles, including a thrown non-Error primitive and every internally-generated runtime error (array bounds, division by zero, `fs`/`fetch` failures, ...). This is a real, pre-existing limitation independent of this ADR: `throw { customField: 1 }` doesn't preserve `customField` at all — the thrown value is coerced into the same fixed 3-field shape regardless of what was actually thrown. Test262's own repro (`throw {}; catch ({ f }) {}`) exercises exactly this gap and can't be made to pass without first fixing that separate, larger limitation (a real per-throw-site object shape, not a single fixed one) — out of scope here.

What IS in scope and genuinely useful: destructuring the fields `errorObjType` *does* have — `catch ({ message, name })` to pull an Error's own message/name directly into locals, a common enough real-world pattern (avoiding the `e.message`/`e.name` accessor spelling). The object-pattern parsing and unpacking machinery already exists and already handles exactly this shape (a known, fixed-layout object type) — `unpackObjectPatternInto` (`emit_objects.go`), shared by destructured function parameters and `const {..} = ..`/`let`/`var` declarations, needed no changes at all.

No array-pattern catch binding (`catch ([a, b])`): `errorObjType` has no numeric-indexed fields, so nothing a `catch ([...])` could bind — parses as before (a clean rejection via the existing `expect(IDENT)` path), not newly supported.

## Decision

1. `ast/nodes.go`: extend `CatchClause` with `ObjectPattern []DestructProp` (unused when `Param != ""`) and a `Pos Pos` field (the `catch` keyword's own position, needed for the destructuring unpack's own error messages — `CatchClause` isn't a `Statement`/`Expression` node with an existing `GetPos()`).
2. `parser/parser_stmts.go`'s `parseTryStatement`: after consuming `catch (`, check for `LBRACE` before the existing bare-`IDENT` path; if present, parse the same `{ key[: local][= default], ... }` shape `parseObjectDestructuring` already parses (minus the trailing `= init`, since the caught value is the implicit source) directly inline, matching the multiple existing near-identical duplications of this same loop shape elsewhere in the parser (`parseParamList`, `parseObjectDestructuring`, `parseArrowFunction`) rather than introducing a new shared abstraction unprompted.
3. `codegen/llvm/emit_exceptions.go`'s `emitTry`: when `len(s.Catch.ObjectPattern) > 0`, load the thrown value's pointer (same `__kml_get_thrown()` call the plain-identifier path already makes) and call `unpackObjectPatternInto(errPtr, errorObjType, s.Catch.ObjectPattern, s.Catch.Pos)` — no new codegen machinery.
4. `resolver/rename.go`'s `TryStatement` case: bind each pattern-destructured local into scope and rewrite its own `Default` expression, mirroring `bindParams`/`rewritePatternDefaults`'s identical treatment of a destructured function parameter.

## Implementation notes

- Files touched: `ast/nodes.go`, `parser/parser_stmts.go`, `codegen/llvm/emit_exceptions.go`, `resolver/rename.go`.
- A default value on a destructured catch field (`catch ({ message = "?" })`) inherits `unpackObjectPatternInto`'s own existing restriction — only a nullable-pointer-typed field can have one, and `errorObjType`'s `message`/`name` fields aren't nullable, so this is a clean compile-time rejection ("a destructuring default requires field '...' to be a nullable reference type"), not silently accepted or silently wrong.

## Side effects discovered

None — `unpackObjectPatternInto` was reused entirely as-is; no bugs found in it during this integration.

## Verification

- Linux x86-64. `go build`, `go vet ./...`, `go test ./...` all pass.
- New E2E tests in `tests/exceptions_test.go`: `TestE2EDestructuredCatchBinding`, `TestE2EDestructuredCatchBindingRenamed`, `TestE2EDestructuredCatchBindingScopedCorrectly` (confirms the destructured local doesn't leak into or shadow the enclosing scope), `TestE2EDestructuredCatchBindingUnknownFieldRejected`.
- Independently verified by temporarily reverting the codegen branch and confirming all four new tests fail with the exact predicted "undefined variable" errors, then restoring and confirming they pass again.
- `examples/try_catch/try_catch.ts` extended with a destructured-catch section. `make examples` — 111/111.
- `make conformance` — 4499/53578, **unchanged** (zero files gained or lost — confirmed via a full before/after `tools/conformance -passlist` diff, byte-for-byte identical pass lists). Directly confirmed why: re-tested the exact `throw {}; catch ({ f }) {}` shape that motivated this ADR (sampled from `annexB/language/function-code/*-skip-early-err-try.js`) and it still fails, now with "object has no field 'f'" instead of a parse error — this compiler's `errorObjType` coercion (see Investigation) means virtually every Test262 file exercising catch-clause destructuring does so via `throw {}`/`throw <arbitrary value>` specifically to test generic destructuring semantics against a custom shape, not `Error.message`/`.name` access, so this fix's real target (`catch ({ message, name })` against an actual thrown `Error`) essentially doesn't overlap with what the corpus exercises. The feature itself is still real and shipped (see the E2E tests above) — it just isn't the fix for this particular conformance bucket. The actual blocker for that bucket is preserving an arbitrary thrown value's own shape through `throw`/`catch` instead of coercing everything into the fixed `errorObjType`, a materially larger redesign not attempted here.
