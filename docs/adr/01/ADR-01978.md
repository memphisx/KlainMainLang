# ADR-01978: A generic method's own-class instance, and tuple type arguments

- **Relations**: Implements TDD-00230; follows [ADR-01977](ADR-01977.md)
- **Date**: 2026-11-07

## Context

`zip<O extends unknown[]>(...o: O): Opt<[T, ...O]> { return new
Opt([this.v, ...o] as [T, ...O]); }` segfaulted when the result's `v` was
read. Two separate causes:

- The `new` inside the method took its type argument from the checker's
  type of the argument. That type is `[T, ...O]`, spelled with the
  method's own type parameters, and an annotation of it answers `any`.
  The instance was `Opt<any>`, with `v` held as a box. The method's result
  annotation, typed under the same instantiation, is `Opt<any[]>`, where
  `v` is an array pointer. The caller read the box as a pointer.
- Since tuples became arrays ([ADR-01977](ADR-01977.md)), a tuple type
  argument mangled as its storage array. `Opt<[number, string, boolean]>`
  and `Opt<[string, number]>` were one class, so one of them read its
  elements with the other's element types.

## Decision

- A `new` whose checker type argument is generic takes its type argument
  from the constructor's arguments. An argument written `x as A` gives
  `A`, resolved under the instantiation being emitted, as the method's
  own annotations are.
- A tuple type argument mangles by its element types (`tup…`), as it did
  when a tuple was an object.

## Consequences

- Covered by `TestE2EGenericMethodAssertedInstance`, which matches Node.
