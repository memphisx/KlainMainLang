# ADR-00436: klain:webview Stage 0 — C++ embedded-source plumbing + LocateWebview

- **Relations**: Implements [TDD-00142](../tdd/TDD-00142.md); Extends [ADR-00411](ADR-00411.md), [ADR-00020](ADR-00020.md)
- **Date**: 2026-08-28

## Context

TDD-00142 binds the [webview/webview](https://github.com/webview/webview)
library (a ~13-function extern "C" API over the system browser engine) so
compiled binaries can open a real window. Every embedded C runtime this project
links so far is C compiled by clang as `<name>.c`; the webview library is
C++14. Stage 0 is the one genuinely new build capability: compile a C++ member
alongside the emitted IR and add the C++ runtime library to the link line,
without letting any of the three EmbeddedCSources writers regress the existing
`.c` members.

## Investigation

- `codegen/llvm/embedded_c.go`: `CSource` had `{Name, Content, CFlags, Libs}`,
  and all three writers (`main.go:171`, `tools/conformance/main.go:493`,
  `tests/compiler_test.go`'s per-helper functions) hard-coded a `.c` suffix.
- `codegen/llvm/crypto.go:44` `LocateCrypto` is the framework/pkg-config split
  precedent: darwin returns `-framework` flags, linux probes `pkg-config`.
- webview upstream: pinned **0.10.0**. Its `webview.h` is a single amalgamated
  header whose implementation is compiled inline (there is no `WEBVIEW_HEADER`
  gate in that release), so the vendored header *is* the translation unit — no
  separate stub `.cc` is needed. The 0.10.0 API returns `void` (not the newer
  `webview_error_t`) and exposes `webview_get_window`/`webview_return(w, seq,
  status, result)`; the design's function list was written against a newer
  release and is resolved here against 0.10.0's actual surface.

## Decision

1. `CSource` grows an `Ext string` field (empty ⇒ `"c"`), resolved by
   `SrcExt()` — the single point every writer consults. main.go and the
   conformance runner switch to `cs.SrcExt()`; the test build path gets an
   `appendWebview` helper writing `webview.cc`.
2. `webview.go` vendors `webviewsrc/webview.h` via `go:embed` (MIT notice
   retained) and adds `LocateWebview()`: darwin → `-framework WebKit -framework
   CoreGraphics -lc++`; linux → `pkg-config` probe for `gtk4 webkitgtk-6.0`,
   falling back to `gtk+-3.0 webkit2gtk-4.1`, with `-lstdc++` and a clean error
   naming the dev packages when neither resolves.
3. `EmbeddedCSources` emits the header as a `.cc` member (`Ext: "cc"`) gated on
   `UsesWebview()`.

## Implementation notes

- Adding `Ext` made every positional `CSource{...}` literal a compile error
  (Go requires all fields); each existing literal gained a trailing `, ""`.
- Compiling `webview.h` directly as the `.cc` TU relies on 0.10.0 having no
  header-only mode — confirmed by grep (no `WEBVIEW_HEADER`).

## Side effects discovered

clang emits `-Wdeprecated-literal-operator` warnings from webview.h's
`operator"" _sel` etc. under a modern C++ frontend — harmless, upstream style.

## Verification

- macOS (Apple Silicon M4): a hand-written `.cc` probe calling
  `webview_create`/`set_title`/`destroy` compiles and links with `-framework
  WebKit -framework CoreGraphics -lc++`.
- Full end-to-end: `klainmain` compiles a `klain:webview` program, writing
  `<base>.webview.cc` and linking it — exit 0, binary produced.
- Linux: the vendored 0.10.0 header compiles and links against `gtk+-3.0 +
  webkit2gtk-4.1` via Docker (`ubuntu:24.04`, no display) — only a
  `webkit_web_view_run_javascript` deprecation warning. The CI apt list
  (`release.yml`) gained `libgtk-3-dev libwebkit2gtk-4.1-dev` so the
  compile-tier tests link for real on Linux (headless-safe: they never open a
  window). The full `klainmain`-driven link and a windowed run on Linux are not
  yet exercised.
