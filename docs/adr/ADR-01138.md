# ADR-01138: The checker's `symbol` type, and narrowing `unknown` as tsc does

- **Relations**: `Implements TDD-00230` (P2.5, P2.7, P3.1); `Extends ADR-01112`, `ADR-01134`
- **Date**: 2026-09-25

## Context

Lowering `indexOf` ([ADR-01137](ADR-01137.md)) removed codegen's rejection
of `"hello".indexOf("l", Symbol("x"))`. tsc rejects that call (TS2345), but
the checker had no `symbol` type and could not type `Symbol(...)`, so the
strict lane accepted it.

Adding the type made a TypeScript corpus case parse for the first time.
That case exposed three places where the checker narrows `unknown`
differently from tsc.

## Investigation

- **`unique symbol` did not parse.** In `declare const s: unique symbol`,
  `unique` became a type reference and `symbol` a separate member or
  statement. TypeScript's own library parsed without error, but into the
  wrong shape. `unknownType2.ts` in the corpus, previously a parse failure,
  now checks.
- **tsc 5.6.3's narrowing of `unknown`**, from its source
  (`/private/tmp/tscheck`) and the case's baseline:
  - `u === v` narrows `u` to `v`'s type when `v` is a primitive or `object`,
    and to `object` when `v` is an object type. This applies only in the
    true branch of a strict comparison.
  - Where branches that narrowed `unknown` to `{}`, `null` and `undefined`
    join, the reference is `unknown` again. Without this, `if (u === null)
    {}` left `u` as `{} | null | undefined` afterwards.
  - A switch without a `default` narrows an `unknown` discriminant, in each
    clause, to that clause's case type alone.
  - `x === true` narrows by `x`'s truthiness (narrowTypeByBooleanComparison)
    only when `x` is not itself the reference; the reference narrows by
    equality first. So `u === true` narrows to `true`, not to `{}`.

## Decision

- **The `symbol` type.** `ESSymbol` is a new primitive type flag, the
  `symbol` keyword, and `unique symbol` (a new `unique` type operator in
  the parser, typed as `symbol`). It relates only to `symbol`, `{}` and the
  object types a primitive may satisfy. It is the apparent type `Symbol`
  and the `typeof "symbol"` narrowing.
  - Operators on a symbol are not reported: tsc's TS2469 is not modelled,
    so its operands are not plain.
- **`lib/es.d.ts` declares `Symbol`:** `Symbol(description?)`, `for`,
  `keyFor`, `description`, `toString`, `valueOf`, and the `iterator` and
  `asyncIterator` well-known symbols this compiler honours syntactically.
- **The four `unknown` rules above**, in `narrowByEquality`, the flow join
  (`unknownJoin`), `narrowBySwitch` and the boolean-comparison shortcut.
- **`Symbol.keyFor` of an unregistered symbol is `undefined`**, as in Node,
  not `null`. It is typed `string | undefined` in codegen, matching the
  declaration. The status note that recorded `null` as the behaviour, and
  the test that asserted it (which tsc rejects, TS2367), are corrected.

## Side effects discovered

- **Stale reference prose.** The `symbol` reference entry said there was no
  `Symbol.for`/`keyFor` registry (there is, [ADR-00488](ADR-00488.md)), and
  its snippet printed `0` for a comparison that prints `false`.

## Verification

- **`tools/tsdiag`:** 1,587 reports over 6,560 cases. 1,585 match tsc's
  baselines (up from 1,580); the 2 that don't are the known Annex B cases.
  The project's own programs report 0.
- **`TestE2EStringNonNumericArgRejected`:** each Symbol argument to a
  numeric builtin parameter is now the checker's TS2345.
- **`TestE2ESymbolForRegistry`** checks `keyFor`'s `undefined`.
