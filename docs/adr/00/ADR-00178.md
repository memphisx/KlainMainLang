# ADR-00178: Named function expressions (self-reference binding)

- **Relations**: `Implements TDD-00060` (V2 — the named-expression case ADR-00168 deferred). `Extends ADR-00168`.
- **Date**: 2026-08-12

## Context

ADR-00168 shipped anonymous function expressions but rejected the *named* form (`var f = function fact(n) { ... }`) at parse time, deferring the scope machinery for a name that is visible only inside the expression's own body (for self-reference/recursion) without leaking to the enclosing scope. That rejection was the largest single parser-error bucket in the Test262 report (2469 files), so it is the highest-value bounded language feature to close next.

## Investigation

- The parser already parsed the name and built `ast.NewFunctionExpression(name, …)` — the rejection was the only thing in the way (`parser/parser_literals.go`).
- `emitFunctionExpression` compiles the body into a top-level LLVM function with a heap `{funcPtr, envPtr}` closure header and a captured-variable env struct where **every slot is a `ptr` to a heap cell** (`envStructIR`). That is exactly the shape a self-reference needs: a cell holding the closure's *own* header.
- The self-reference is circular — the body must reach the header, but the header isn't allocated until after the body is emitted. Resolvable by building the cell during env construction (after the header exists) and having the body load the name from its env slot like any other capture.
- **Collision problem found.** When the expression's name shadows a top-level function of the same name, the resolver's rename pass (TDD-00041) has already rewritten the body's self-references to that outer function's mangled name (`rec` → `rec__kml_mod0`) and renamed the outer declaration — before codegen sees the expression's self-scope. The self-binding can't reclaim those references, so recursion would silently call the *outer* function (observed: `factorial`-style test returned the wrong value). This is the same "no notion of the expression's own name scope" gap, now in the resolver rather than the parser.

## Decision

1. **Parse** the named form (remove the two parse-time rejections, sync + async).
2. **Bind the name inside the body** as a synthetic self-capture (`CapturedVar{IsSelf: true}`), added only when the body references the name. Its env cell is filled with the closure's own header after the header is allocated — circular by construction, which is exactly what lets the body call itself. The name is scoped to the body (a fresh scope), so it does not leak to the enclosing scope, and it shadows an enclosing *variable* of the same name (excluded from ordinary capture).
3. **Reject the top-level-function shadowing collision cleanly** rather than miscompile it. Detected on both pipelines: the mangled reference (`<name>__kml_mod<N>` in the body's free variables) when the resolver has run, and `resolveFuncRef(fe.Name)` finding the outer function when it has not (the direct parse→emit test path). Rejecting it — instead of a proper resolver-level fix that teaches the rename pass about expression name scopes — is a deliberate scope cut for this stage.

## Implementation notes

- `parser/parser_literals.go` — drop the two "named function expressions are not yet supported" rejections.
- `codegen/llvm/emit_func.go` — `CapturedVar.IsSelf`; self-capture append (with collision detection) in `emitFunctionExpression`; self-cell env-build special case (malloc a cell, store the header, point the env slot at it). The body-setup capture loop binds it generically (no special case).
- The self-symbol's type is the closure's own `FuncType`, so a call to the name dispatches through the normal closure-call path, and using the name as a value yields the closure header.

## Side effects discovered

The dispatch order in `emitExpr`'s call path (`resolveFuncRef` before closure-variable lookup) means a function-typed *local* binding does not lexically shadow a same-named top-level function. A reorder fixes it and is correct, but it does not help the named-FE collision (the reference is already mangled by then) and is a broader change; left out of this ADR and noted as a separate potential fix.
