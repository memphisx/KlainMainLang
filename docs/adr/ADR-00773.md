# ADR-00773: Blocking-work thread pool — real async `fs.promises.readFile`

- **Relations**: `Implements [TDD-00185](../tdd/TDD-00185.md)` (Stages 1-2); `Extends [ADR-00340](ADR-00340.md)` (the async-shaped fs delivery this makes genuinely non-blocking for readFile)
- **Date**: 2026-09-08

## Context

`fs.promises.readFile` — and every async fs op — ran its blocking syscall
*inline on the single event-loop thread* and returned an already-settled Promise
([emit_fs_async.go](../../codegen/llvm/emit_fs_async.go), pre-this-change). For
CLI tools that is invisible, but for the microservice / REST-server target
(this project's priority-1/2 path) it is disqualifying: a request handler that
`await`s a file read freezes the `select()`-based reactor for the whole read,
stalling every other connection, timer, and microtask. This is BACKLOG §1 item 3
and the first stage of it to land.

## Investigation

The terrain (mapped in [TDD-00185](../tdd/TDD-00185.md)): the one reactor is
`@__kml_event_loop_run` ([runtime_http.go](../../codegen/llvm/runtime_http.go)),
single-threaded over POSIX `select()`, with no worker pool. All loop / fiber /
microtask / Promise state is `thread_local` and the loop is thread-pinned
(`@__kml_reactor_thread_lock`), so a background thread **cannot** settle a
Promise or enqueue a microtask directly. The reusable pieces were all present:
`@__kml_promise_settle` + a microtask-scheduled fiber resume is exactly a
completion callback; `Worker`/`klain:sync` already create real pthreads and
register them with Boehm; the fs sync helpers (`@__kml_fs_read_file`) already
funnel their failure through a `thread_local` `setjmp`/`@__kml_fs_throw`.

Rejected: running the throwing sync helper *unguarded* on a worker (its
`longjmp`/GC-Error build would corrupt the loop thread's state) — instead each
worker guards its own call with its own `thread_local` jmpbuf. Rejected:
per-loop pools (libuv shares one process-wide pool; N Workers would mean
N×threads) — one shared pool, per-loop completion routing.

## Decision

A libuv-style **blocking-work thread pool** with one invariant: **I/O runs
off-thread; the Promise settles on the loop thread.**

- **Threading in C** ([threadpoolsrc/klainpool.c](../../codegen/llvm/threadpoolsrc/klainpool.c),
  linked with `-pthread` when `UsesThreadPool()`): one process-wide FIFO work
  queue (mutex + condvar) drained by a lazily-started pool of **4** threads
  (libuv's default; `UV_THREADPOOL_SIZE` honored, capped 1024). Each *event
  loop* owns a `kml_loop_port`: a lock-free Treiber stack of completions, a
  `socketpair` the workers write to wake this loop's `select()`, and an
  `inflight` counter. A worker runs the op, pushes the completion onto the
  origin loop's port, and writes its wakeup byte.
- **Promise/exception layout stays in the IR** ([threadpool.go](../../codegen/llvm/threadpool.go)):
  the C side is deliberately ignorant of both structs and calls two emitted
  thunks — `__kml_pool_thunk_readfile` (runs `@__kml_fs_read_file` under the
  worker's own setjmp guard, returns `{result, err}`) and `__kml_pool_settle`
  (stores the value word, calls `@__kml_promise_settle`). So the existing sync
  helper is reused **verbatim**, no parallel non-throwing I/O path — the same
  elegance the inline design had, moved off-thread.
- **Reactor integration** via the established hook trio: a per-loop wakeup fd
  folded into the read `fd_set` while `inflight > 0` (`__kml_pool_fdset_add`,
  returning "don't force a zero timeout" so `select()` truly sleeps until a
  completion lands), an `anywork` keepalive (`__kml_pool_keepalive`) so the loop
  doesn't exit mid-read, and an `afterselect` drain (`__kml_pool_dispatch`) that
  settles arrived completions on the loop thread. No-op stubs when the pool is
  unused ([runtime_task.go](../../codegen/llvm/runtime_task.go)), exactly like
  the worker/`fs.watch` hooks.
- **Lowering**: `fs.promises.readFile(path)` now allocates a **pending** Promise,
  submits the read, and returns it; the awaiting fiber parks through the
  existing await-on-unsettled-Promise path. The callback form and the other
  Promise ops (`writeFile`/`unlink`/`readdir`/…) stay on the inline path until
  TDD-00185 Stage 3.
- **`-mm=gc`**: workers register with Boehm before their first allocation.
  `GC_allow_register_threads` is call-once and shared, so the pool owns the
  enable (`KLAINPOOL_GC_ENABLE`) only when there are no Worker modules and
  `klain:sync` is not linked (each of which already owns it) — computed once in
  `ThreadPoolCFlags()`, the single source of truth shared by `EmbeddedCSources`
  and the test build harness.

Windows keeps the inline fs path for now; the general wakeup primitive folds
into the Windows reactor work ([TDD-00182](../tdd/TDD-00182.md)/[TDD-00183](../tdd/TDD-00183.md)).

## Consequences

`fs.promises.readFile` no longer blocks the loop: verified on macOS (arm64) that
three concurrent reads round-trip through the pool via `Promise.all`, a timer
set before the `await` keeps firing during the read, and a missing file rejects
with the Node error shape (`code`/`errno`) built on the worker and surfaced on
the loop thread — in both the default (malloc) and `-mm=gc` allocators. New E2E
tests (`TestE2EFsPromisesPooledConcurrentReads`,
`TestE2EFsPromisesPooledReadDoesNotFreezeLoop`) and `examples/fs_promises_pool/`.
The write/other ops remain inline (Stage 3); busy-drive while a fiber is
*runnable* is unchanged (a parked-on-read fiber lets `select()` block on the
wakefd, the efficient path). The perf follow-up is real streaming (Stage 4).
