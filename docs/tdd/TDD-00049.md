# TDD-00049: Import-gated built-in bindings (collision-safe `fs`/`process`/`path`/`os`/…/`Memory`)

- **Status**: Implemented
- **Date**: 2026-08-10

## Context

Every Node-runtime pseudo-namespace this compiler has ever shipped — `fs`, `process`, `path`, `os`, `querystring`, `assert`, `events`/`EventEmitter`, `http` (as a module), `cluster` — plus this project's own invented `Memory.free(x)` builtin, is recognized in `codegen/llvm` by **pure textual identifier-name matching** against the AST (`if id, ok := mem.Object.(*ast.Identifier); ok && id.Name == "fs"`, repeated per-name across `emit_call.go` and friends — confirmed by grepping every `.Name == "..."` site in `codegen/llvm/*.go`). This is completely independent of, and untouched by, the real per-file module-scope work already shipped ([TDD-00041](TDD-00041.md)/[ADR-00134](../adr/ADR-00134.md), [TDD-00042](TDD-00042.md)/[ADR-00135](../adr/ADR-00135.md)) — these ~20 names were never routed through the resolver's import/binding machinery at all, in either direction. `docs/status/README.md`'s own Node.js APIs section already names this plainly: "Recognized as pseudo-namespaces (`fs.*`, `process.*`), like `Math`/`JSON` — not real importable modules."

Picked up now, ahead of [TDD-00047](TDD-00047.md) (`Worker`) and [TDD-00048](TDD-00048.md) (WebAssembly), on direct request: adding a 21st hardcoded ambient name (`worker_threads`' `Worker`) on top of the same collision-prone pile would repeat a known-bad pattern rather than fix it, and the fix genuinely is prerequisite work — `worker_threads` is exactly the kind of Node module real Node itself gates behind an explicit `import`/`require`, specifically to avoid clashing with user code.

**This is not a hypothetical gap** — a two-file empirical check against the current `klainmain` binary (this session, Linux) confirmed a real, live miscompilation:

1. `let fs: FakeFs = makeFakeFs(); fs.readFileSync(...)` at the **top level** of the entry file compiles and runs correctly, calling the user's own function. This works only *incidentally* — [TDD-00041](TDD-00041.md)'s per-file mangling rewrites every top-level declaration's name before codegen ever runs, so by the time `emit_call.go`'s string-match dispatch sees it, `id.Name` is no longer literally `"fs"`. Not a designed collision guard; a side effect of unrelated work.
2. The identical pattern with `fs` declared **inside a function body** (never touched by top-level mangling) miscompiles: `emit_call.go`'s `id.Name == "fs"` check fires on the identifier's literal text regardless of what's actually in scope, routes the call straight to the real `emitFsReadFileSync`, and the program crashes with `Uncaught: cannot open file for reading 'nope.txt': No such file or directory` instead of ever running the user's own `readFileSync`. Confirmed identically reproducible for any of the ~20 names below, anywhere they're used as a local variable, function parameter, or closure capture rather than a top-level declaration.

## Design

### Three categories of "ambient global" today, needing different treatment

Grepping every `*.Name == "<Name>"` site in `codegen/llvm/*.go` surfaces the full current list. It splits into three groups that should **not** all be treated the same way:

| Category | Names | Reasoning |
|---|---|---|
| **A — true ECMAScript/WHATWG ambient globals** | `Math`, `JSON`, `String`, `Number`, `Object`, `Array`, `Date`, `Error`, `Map`, `Set`, `Promise`, `Infinity`, `console`, `crypto`, `performance` | Never imported in real JS/TS on any host (browser, Node, Deno, Bun) — these are language- or WHATWG-spec-level globals. Should **stay ambient** here too; gating them behind `import` would make ordinary, unremarkable TS code fail to compile for no real-world reason. |
| **B — Node-specific core modules + this project's own extension** | `fs`, `path`, `os`, `querystring`, `assert`, `events`/`EventEmitter`, `http` (as a module), `cluster`, `Memory` (invented — no real-JS/Node equivalent at all) | Real Node itself requires `require('fs')`/`import fs from 'fs'` for every one of these — gating them behind import here isn't a new restriction relative to real Node, it's *catching up* to how real Node already avoids exactly this class of collision. |
| **C — environment-identity global(s)** | `process` (and, hypothetically, a future `window` — see below; neither is Category A, since both are host-specific rather than ECMAScript-spec globals, and neither is Category B, since real JS/TS code relies on being able to reference them *unconditionally*, import or no import) | **Decided: `process` stays ambient, matching real Node exactly** — see Design note below for why this is a deliberate exception, not an inconsistency. |

Resolved (previously an open question): `process` does **not** move to Category B. Real-world JS/TS code universally uses `typeof process !== 'undefined'` (and, in browser code, `typeof window !== 'undefined'`) as the standard runtime environment-detection idiom — code that needs to behave differently under Node vs. a browser checks for the *presence* of the ambient global, with no import involved on either side. Gating `process` behind an import would break that idiom outright (the whole point is checking whether the name exists at all, before committing to using it), and would make this project's `process` behave unlike every real JS runtime's for no real benefit — Category B's collision-safety motivation doesn't actually apply to a name real code needs to probe unconditionally.

### Forward-looking: keeping `process`/`window` mutually exclusive if `window` is ever added

No `window` global exists anywhere in this compiler today (confirmed by grep) — the currently-scoped TUI work ([TDD-00031](TDD-00031.md)) is built entirely on `process.stdin`/`process.stdout`, not a `window`-shaped API, so this is speculative, not a currently-planned change. But if a `window`-style global is ever added for some future browser-adjacent or sandboxed-frontend direction, it needs to preserve the same environment-sniffing idiom Category C exists for: `typeof window` should read as `"undefined"` in a build that has no business calling itself a browser-like environment, and `typeof process` should likewise read as `"undefined"` in one that doesn't behave like Node — not both permanently defined together, which would make the idiom meaningless and diverge from how every real JS host actually behaves (a real browser has no `process`; real Node has no `window`). Concretely, this points toward Category C bindings being gated by **compile target**, not by import — a `-target-env=node|browser`-shaped flag (naturally adjacent to whatever target-selection mechanism [TDD-00048](TDD-00048.md)'s WebAssembly work would also need) selecting which of `process`/`window` actually exists as an ambient global for a given build, rather than a per-file import decision the way Category B works. Not designed further here — noted so Category C's shape doesn't get accidentally boxed in by whatever Category B mechanism ships first.

### Recommended mechanism: virtual module specifiers, resolved through the existing import machinery

- Add a small, fixed, compiler-known table of **virtual specifiers** (`'fs'`, `'path'`, `'os'`, `'querystring'`, `'assert'`, `'events'`, `'http'`, `'cluster'`, `'memory'`, …) that `resolveImportPath` (`resolver/resolver.go`) recognizes and short-circuits, instead of resolving them against the filesystem the way every import today requires (`docs/status/MODULES.md`'s own "Bare/package-style imports ❌ — No package ecosystem here — only relative paths resolve to anything" row is exactly the gap this needs to selectively lift, for this fixed built-in set only — not a general package ecosystem). Each virtual specifier resolves to a compiler-internal synthetic export table (name → arity/signature) already implicit in that domain's existing `emit_*.go` switch statement — no file to parse, no AST body.
- `import fs from 'fs'` / `import { readFileSync, writeFileSync } from 'fs'` binds those names into the importing file's scope through the **same per-file mangling/binding path** [TDD-00041](TDD-00041.md) already built for real file-to-file imports — shadowing, redeclaration-conflict detection, and aliasing (`import { readFileSync as rfs } from 'fs'`) all fall out for free, no new resolver mechanism needed beyond specifier recognition.
- Every one of `emit_call.go`'s (and friends') `if id.Name == "fs"` blocks becomes a lookup against "was this name bound via an import of the virtual `'fs'` specifier in *this* file" — a small map the resolver pass already has to build to support the binding above — instead of a bare AST string comparison. This is what actually closes the shadowing bug from the Context section, as a structural consequence of routing these names through real scope resolution, not a special-cased patch on top of the existing string match.
- Referencing `fs.readFileSync(...)` without ever importing `fs` becomes a real, clean compile-time error ("`fs` is not defined") instead of silently working as it does today — a genuine behavior change for every existing example/test using any Category-B name; see Prerequisites for the migration size.

### Direct payoff for `Worker` ([TDD-00047](TDD-00047.md))

That document currently frames Node's `worker_threads.Worker` vs. the browser DOM `Worker` as "pick one." With this TDD in place, `worker_threads` becomes just another virtual specifier (`import { Worker } from 'worker_threads'`) — a Node-shaped API that's collision-safe by construction from day one, rather than a 21st name added to the pre-existing hardcoded pile. The browser-global `Worker` (ambient, Category A-shaped — real browsers never `import` it) can follow later as its own stage without needing to be designed or picked between now; see the edit to [TDD-00047](TDD-00047.md) alongside this document.

## Open questions

- **Is Category A ever revisited**, or is "matches real JS/WHATWG, permanently ambient" the deliberate, final answer? Recommend stating this explicitly in whatever ships, so it doesn't get re-litigated per future feature. Category C (`process`) is now resolved the same way, for a different reason — see Design.
- **Category C's compile-target gating mechanism** (if `window` is ever added): a real design question in its own right, not scoped here — does it reuse whatever target-flag plumbing [TDD-00048](TDD-00048.md) would need, get its own narrower flag, or something else entirely? Purely forward-looking; nothing blocks on this today since `window` doesn't exist.
- **Virtual specifier naming**: `'fs'`/`'path'`/`'os'`/`'events'` match real Node's own module names; `'memory'` for `Memory.free` is invented from scratch (no real precedent to match). Worth deciding once, not per-PR as new Category-B features get added.
- **Migration sequencing**: one large mechanical pass across every existing example/test, or incrementally per-module alongside whichever real feature work touches that module next (e.g. migrate `fs` when `fs` async variants are eventually picked up)? Given this blocks [TDD-00047](TDD-00047.md), leaning toward doing it as one dedicated pass rather than letting `Worker` wait on an incremental trickle.
- **This does not close the shadowing bug for Category A or C** — worth stating plainly rather than leaving implicit. Both stay on the same bare AST string-match mechanism as today (by design — gating `Math`/`process`/etc. behind import would be wrong, see Design), so a local variable named `Math`, `console`, or `process` still silently miscompiles exactly like the `fs` repro in Context, just less likely to be hit in practice since those names are rarely reused. That's a real, knowing gap this TDD leaves open, not a "matches real JS" equivalence — real JS's own lexical scoping always shadows correctly; this compiler's bare-identifier dispatch for A/C never did. Closing it for A/C too would need the same import-binding machinery extended to cover *shadowing detection for non-imported ambient names specifically* (i.e., the resolver would need to know `Math`/`process` are reserved ambient identifiers and flag a colliding local declaration, even though no import is involved) — real, additional, un-scoped work if ever wanted.
