# ADR-00782: `codePointAt` out-of-range and `AsyncLocalStorage.getStore()` unset as `T | undefined` (TDD-00187 adopters)

- **Relations**: Extends [TDD-00187](../tdd/TDD-00187.md)'s sentinel to two more per-site adopters listed in BACKLOG §1.1 (the mechanism shipped in [ADR-00778](ADR-00778.md)–[ADR-00781](ADR-00781.md)); fixes a latent `??` bug in the Stage 1 nullable-pointer path
- **Date**: 2026-09-08

## Context

Two operations TypeScript types as `T | undefined` still returned a fabricated
zero value, left over from before the sentinel existed:

- **`str.codePointAt(i)` out of range** returned `NaN` — a copy of
  `charCodeAt`'s behavior (a double so an out-of-range read can be `NaN`). But
  Node returns `undefined` for `codePointAt` out of range (only `charCodeAt`
  yields `NaN`); tsc types it `number | undefined`.
- **`AsyncLocalStorage.getStore()` on an unset/disabled instance** coerced the
  runtime's NaN-boxed `undefined` word straight down to the store element type
  `T`, collapsing absence to `T`'s zero — indistinguishable from a genuine `0`
  store. Node/tsc type it `T | undefined`.

## Decision

- **`codePointAt`** now loads the byte as before but returns the presence-flagged
  `{ i1, i64 }` optional (`wrapUndefinedable`, present = in-bounds) instead of a
  `NaN`-bearing double. An in-range code point is a real integer, so the payload
  is `i64`; out of range is a real `undefined`. `inferExprType` reports
  `undefinedableElem(TypeI64)`, so the strict gate applies (`const c: number =
  s.codePointAt(0)` is a compile error; narrow / `?? n` / `!`) and `-compat=js`
  auto-widens. `charCodeAt` is unchanged (still `NaN`/double) — the two methods
  now differ exactly as in Node.
- **`getStore()`** keeps the existing "disabled OR no active frame →
  `nbUndefined`" word (`__kml_als_lookup` already returns the undefined box for
  no frame). A **dynamic** store hands that word straight back — `any` carries
  `undefined` natively. A **concrete scalar/pointer** store now wraps it:
  present = `word != nbUndefined`, payload = the decoded value, and a pointer
  payload is `select`ed to `null` when absent so `=== null` / optional-chaining
  keep working. `inferExprType` reports `undefinedableElem(*ElemType)`.

## Latent `??` bug fixed in passing

`emitNullCoalesce`'s statically-nullish shortcut fired on
`left.Ty.IsNull || left.Ty.IsUndefined` and returned the right operand outright.
That was written for the literal `null`/`undefined` (both `IsNull`), but a
runtime `T | undefined` **pointer** union produced by `wrapUndefinedable`
(`IsUndefined` set, `IsNull` *not* set) also matched — so `stringArr.pop() ??
"x"` and `getStore() ?? d` on a present value wrongly took the fallback. This
was reachable from Stage 1 (`.pop()`/`.find()` on a string/object array), not
new to this change. The guard now keys on `IsNull` alone; a runtime pointer
union falls through to the existing runtime null test.

## Consequences

- `codePointAt` gains a caveat-free `number | undefined` row; a program wanting
  the old total behavior writes `s.codePointAt(i) ?? 0`.
- `getStore()` distinguishes an unset store from a `0`/`""`/null store; existing
  object-store `=== null` idioms keep compiling (absent is still a null
  pointer), and `=== undefined` is now the type-faithful check.
- The `??`-on-a-present-nullable-pointer bug is fixed for every Stage 1 op, not
  just these two.
