# ADR-01994: Sparse array elements past the buffer

- **Date**: 2026-11-20

## Context

Test262 `built-ins/Array/S15.4_A1.1_T10.js` writes `x[k - 2] = k` for
k = 2, 4, …, 2^32. On the Mac conformance lane its program reached 4.6 GB
in two seconds and the memory guard stopped the run; on Linux the same
binary reached 4.3 GB and crashed with SIGSEGV (HEAD did the same). An
array was always one contiguous buffer as long as its length, so a gap write
grew the buffer to the new index and filled every slot of the gap with what
a hole reads as. Node keeps such an array in dictionary mode: the far
element costs one entry, not 2^32 slots. The holes model this extends is
TDD-00226's.

## Investigation

- The gap write (`emitArrayIndexAssignGrow`, codegen/llvm/emit_arrays_mutate.go)
  reallocated to `idx + 1` elements and ran `emitFillHoles` over the gap,
  writing every page: at 2^32 doubles, 32 GB.
- Lazy allocation (calloc, or reserving address space and filling pages on
  fault) was rejected: the conformance runner's `ulimit -d` counts the
  reservation, a fault handler would have to cooperate with the stack-guard
  handler on three systems, and every growth path calls the C allocator's
  realloc directly.
- holes.c already holds an element out of line: an accessor element is a
  hole bit plus an index-keyed entry in the added-property table, and the
  element read (emit_exprs_member.go) never loads the buffer for a hole —
  `__kml_holes_elem` returns the entry's value.

## Decision

An array may hold *sparse elements*. The holes bitmap gains a `dense` word:
the number of elements the buffer holds, -1 when it holds all of them.

- A write at least 1024 elements past the end (V8's fast-elements gap) of an
  array whose element is an 8-byte boxed word, double, string, plain object
  or integer does not grow the buffer: `dense` becomes the old length, the
  value goes into the property table under its index, and the length becomes
  `idx + 1`. Once sparse, every write at `dense` or later does the same.
- Every element from `dense` up is a hole bit implicitly (`hole_bit`), so
  nothing is marked: the element read, `in`, `hasOwnProperty` and the
  holes-aware walks see the set ones through the table.
- `length = n` on a sparse array keeps the buffer: entries at `n` and up are
  dropped, and an `n` at or below `dense` makes the array dense again.
- Every other access to the buffer makes the array dense first
  (`__kml_holes_densify`): the buffer is grown to the length, the gaps get
  the hole value, and the table entries move into their slots (a number box
  decoded to its double or integer, a pointer box to its address). This sits
  in the buffer accessors (`arrayParts`/`arrayData`, `arrayDataLenSlots`), in
  `resolveArrayMutLoc` for every mutator but the element and length writes,
  in the element-address path of compound assignment, and where an array is
  boxed into `any` — the dynamic runtime reads a boxed array's buffer
  directly. The element read, the element and length writes, and the length
  read use the raw accessors.
- An element that is an array, a BigInt64Array element, an inline struct or
  a narrower scalar stays dense: its hole read cannot carry a stored value.

## Implementation notes

- codegen/llvm/holessrc/holes.c: `BM_DENSE`, `sparse_from`,
  `__kml_holes_sparse_write`, `__kml_holes_sparse_len`,
  `__kml_holes_densify`, `__kml_holes_buflen`; `__kml_holes_elem_set` stores a
  write past the buffer in the table.
- codegen/llvm/holes_c.go: `sparseElem`/`sparseKind`, `emitDensify`.
- codegen/llvm/emit_arrays_mutate.go, emit_arrays_core.go,
  emit_exprs_member.go, emit_dynamic.go, emit_memory.go,
  emit_free_deep.go: the hooks above. A deep free walks only the elements the
  buffer holds.
- Making a 2^32-element array dense still needs its whole buffer; a walk over
  it is 2^32 steps in Node too. An allocation failure there reports a
  fatal out-of-memory error, as Node does, and aborts instead of crashing.

## Side effects discovered

- The property table finds a key by a linear search, so an array with many
  sparse elements reads each in time linear in their number (Node's
  dictionary is a hash table). Correct, slower; a perf follow-up.

## Verification

- `TestE2EArraySparseElements` (strict) and `TestE2EArraySparseElementsJS`
  (js lane) match Node: the 2^32 - 2 write, truncation, compound assignment,
  forEach/filter/map/indexOf/lastIndexOf/slice/join/push/JSON over sparse
  arrays of strings, numbers, objects and mixed values.
- examples/arrays/sparse_elements.ts matches Node.
- The Test262 repro runs in 11 MB instead of crashing at 4.3 GB (Linux x86,
  Node304); `built-ins/Array` compared test by test against the previous
  build on Node304, both lanes.
