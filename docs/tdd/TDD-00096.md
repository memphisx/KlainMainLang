# TDD-00096: Generator function expressions + yield-based element-type inference

- **Status**: Implemented
- **Date**: 2026-08-22
- **Notes**: Bound `const G = function* ...` rewrites to a named generator declaration (class-expression precedent); an un-annotated generator infers its element type from yields (numeric join, `yield*` delegation, return fallback). Other expression positions stay clean rejections

## Context

Two adjacent generator gaps, both long-documented caveats and both large in
the conformance blocked-by histogram (ADR-00288):

1. A generator *expression* (`const g = function* () {...}`, incl. the
   anonymous `function*` passed straight to an API) doesn't parse in
   expression position at all — the `expected (, got *` cluster, 2,086
   files.
2. A generator declaration requires an explicit return-type annotation (the
   yielded element type). Real-JS sources never carry one, so even once the
   expression form parses, every un-annotated generator dies on the
   annotation requirement — its own 662-file reason bucket.

## Design

### Part 1 — bound generator expressions (rewrite)

The exact precedent is TDD-00063 Stage 4's class-expression handling: a
top-level `const/let/var G = function* (...) {...}` is observationally a
declaration under another name — rewrite it in a pre-pass
(`rewriteTopLevelGeneratorExpressions`, running alongside
`rewriteTopLevelClassExpressions`) into a named generator
`FunctionDeclaration` before registration. The parser must therefore parse
`function*` in expression position into the existing FunctionExpression node
shape with an `IsGenerator` flag (parse-level acceptance is general; only
the top-level-binding form is *supported*, everything else — an argument, a
nested binding, an IIFE — stays a clean codegen-time rejection naming the
V1 scope).

`async function* () {...}` expressions follow the same rewrite into the
existing async-generator declaration machinery.

### Part 2 — yield-based element-type inference

When a generator declaration (named or rewritten) has no return-type
annotation, infer the element type from the body instead of rejecting:

- Walk the body for `yield <expr>` / `yield* <inner>` (the latter takes the
  inner generator's element type when resolvable).
- Infer each yielded expression's type via `inferExprType` **with the
  generator's parameters temporarily bound** (a scope push of param name →
  declared type — parameters are annotated even in conformance sources
  rarely; an unannotated parameter contributes `i64` as everywhere else).
- All yields agree (after the usual i64/f64 numeric join) → that's the
  element type; disagreeing yields, or zero yields, fall back: zero yields →
  `void`-ish `i64` zero element (a generator that only returns), mixed →
  keep the explicit-annotation requirement with the existing error message
  (now only for the genuinely ambiguous case).

### Explicitly out of scope

- Generator expressions as arguments/IIFEs (no first-class function-with-
  fiber value model yet).
- `yield`-type-driven bidirectional checking (TS's full `Generator<T, R, N>`
  triple) — the element type is all this compiler's iteration model uses.
