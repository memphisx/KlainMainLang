# ADR-00115: RegExp Stage 1 — .test(str)

- **Relations**: Implements [TDD-00035](../tdd/TDD-00035.md). Extends [ADR-00114](ADR-00114.md)
- **Date**: 2026-08-07

## Context

[TDD-00035](../tdd/TDD-00035.md)'s Stage 1 is `.test(str): boolean` — the smallest possible slice that actually runs a PCRE2 match, deliberately chosen to come before `.exec()` (Stage 2) since it needs no result-array machinery at all. Picked up directly following Stage 0 ([ADR-00114](ADR-00114.md)), per the user's "continue with Stage 1."

## Investigation

Verified `pcre2_match_data_create_from_pattern`/`pcre2_match`/`pcre2_match_data_free`'s exact signatures directly against the real `pcre2.h` (re-extracted the same `libpcre2-dev` `.deb` via `apt-get download`, same no-root approach ADR-00114 used, since this machine still doesn't have `libpcre2-dev` installed system-wide — see that ADR's Verification section and this one's own below): `pcre2_match(const pcre2_code*, PCRE2_SPTR, PCRE2_SIZE, PCRE2_SIZE, uint32_t, pcre2_match_data*, pcre2_match_context*) -> int` (`pcre2.h:682-683`) and `pcre2_match_data_create_from_pattern(const pcre2_code*, pcre2_general_context*) -> pcre2_match_data*` (`pcre2.h:675-677`) — both matched what was assumed while writing the `declare` lines, no surprises.

**Decided against caching a `pcre2_match_data` on the RegExp instance.** PCRE2's own documentation recommends reusing one match_data block across repeated matches for performance, which would mean adding it as an eighth (hidden) field on `RegExpType()` alongside the compiled-pattern handle. Rejected for now: Stage 0's one-time compiled-pattern handle is a bounded, single allocation per `RegExp` instance that this project's manual-mode "leak by default" convention already tolerates (matching how a `curl_url()` handle is deliberately never freed on `new URL(...)`'s happy path, ADR-00114/emit_url.go) — but a match_data allocated once and never freed inside a `.test()` call that runs inside a loop (a very natural usage pattern — filtering an array by a regex) would leak once *per call*, not once per instance, a materially different and worse leak shape. Simpler and safer for V1: allocate and free a match_data within `.test()` itself, accepting the small repeated alloc/free cost over an unbounded loop-scaled leak. Worth revisiting if a later stage's profiling ever shows this mattering — not expected to, given `README.md`'s own "not production-ready, never expected to be" framing.

**Confirmed real JS's `.test()` is not actually as simple as "always match from offset 0."** Per spec, `RegExp.prototype.test()` calls the same internal `[[RegExpExec]]` that `.exec()` uses, which means a global (`g`) or sticky (`y`) regex's `.test()` reads and writes `lastIndex` exactly like `.exec()` does — the common `while (re.test(s))`-style iteration idiom depends on this. Since Stage 2 (not yet built) is where `lastIndex` read/write machinery is scoped to land, decided to explicitly *not* attempt a partial version of it here: Stage 1's `.test()` always matches from offset 0 and never touches `lastIndex`, full stop. This is a real, user-visible gap versus real JS for a global/sticky regex specifically, not merely an internal implementation detail — documented prominently (this ADR, `docs/status/REGEXP.md`, the example file) rather than left to be discovered by surprise.

## Decision

- `emitRegexHandleLoad(objVal Value) string` (`emit_regexp.go`) — a small shared helper that GEPs/loads the hidden `RegexHandleField` out of an already-evaluated `RegExp` instance. Factored out now, ahead of strictly needing it more than once, specifically because every later stage (`.exec`, `str.match`, `str.replace`, ...) needs the exact same load — the TDD's own cross-cutting design already implied every method starts this way.
- `emitRegexTest(mem *ast.MemberExpression, args []ast.Expression, pos ast.Pos) (Value, error)` (`emit_regexp.go`): evaluates the receiver and the string argument, creates a match_data sized to the pattern's capture count, calls `pcre2_match_8` with `PCRE2_ZERO_TERMINATED` (matching Stage 0's convention for this compiler's NUL-terminated strings) at start offset 0 with no extra options, frees the match_data immediately, and returns `icmp sge i32 <rc>, 0` as the boolean result. Any negative return code (not just `PCRE2_ERROR_NOMATCH` specifically) is treated as "no match" — permissive, matching `atob`/`decodeURI`'s existing convention for unusual input rather than surfacing PCRE2's other, rarer internal error codes as something more specific.
- New `ensureRegexMatch()` (`runtime_regexp.go`) declares `pcre2_match_data_create_from_pattern_8`/`pcre2_match_8`/`pcre2_match_data_free_8`, calling `requireLink("pcre2-8")` itself too (idempotent) rather than depending on `ensureRegexCompile` having already run — keeps the two `ensure*()` helpers independently self-sufficient even though, in practice, you can't have a `RegExp` value to call `.test()` on without having already constructed one.
- Dispatch: a new guarded block in `emit_call.go` (`mem.Property == "test" && e.inferExprType(mem.Object).IsRegExp`), positioned right after the existing `TextEncoder`/`TextDecoder` blocks — same shape as every other receiver-type-guarded method (`IsDate`, `IsResponse`, `IsTextDecoder`).
- `inferExprType` (`emit_exprs_types.go`) gained a `case "test": if e.inferExprType(mem.Object).IsRegExp { return TypeBool }` — needed for the same reason ADR-00112/ADR-00113 already found: an unannotated `const matched = r.test(s)` needs `inferExprType` to report the real return type (`i1`) so `emitVarDecl`'s generic `MemberExpression`-callee fallback (`emit_exprs_vardecl.go`'s `default: inferred := e.inferExprType(init); if inferred.IR != TypeI64.IR ...`) allocates a correctly-typed slot instead of silently defaulting to `i64` and producing a type-mismatched `store` instruction.

## Implementation notes

Files touched: `codegen/llvm/emitter.go` (one new `usedRegexMatch` guard field), `codegen/llvm/runtime_regexp.go` (`ensureRegexMatch`), `codegen/llvm/emit_regexp.go` (`emitRegexHandleLoad`, `emitRegexTest`), `codegen/llvm/emit_call.go` (dispatch), `codegen/llvm/emit_exprs_types.go` (`inferExprType` case). No `emit_exprs_vardecl.go` change was needed this time — unlike Stage 0's `NewRegExpExpression` node (which needed its own explicit vardecl-inference case), `.test()` is an ordinary `MemberExpression`-callee call, which `emitVarDecl`'s existing generic fallback already routes through `inferExprType` automatically once that function knows about `"test"`.

## Side effects discovered

None — no pre-existing unrelated bug surfaced this time.
