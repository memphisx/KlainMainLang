# TDD-00254: -dynamic-import=lazy on Windows

- **Status**: Implemented
- **Date**: 2026-10-13

## Context

`-dynamic-import=lazy` (ADR-01330) puts each `import()` target's code in a
shared library beside the executable, bound to the executable's library,
runtime and event loop. Linux and macOS leave the library's references to
the executable undefined until it loads. Windows refused the mode: a DLL
binds at link time, to an import library, and a DLL cannot import a
thread-local variable from another module, while the generated code and
the C runtime read dozens of them (`__kml_current_task`, the loop's state,
module globals).

## Design

**Option A — emulated thread-locals (chosen).** With `-femulated-tls`
every `thread_local` becomes an ordinary control variable plus a call to
`__emutls_get_address`; a DLL imports the control variable like any other
data. The executable links with `--export-all-symbols` and writes an import
library (`<binary>.d/program.lib`); each island DLL links against it. The
switch applies to every compile of a program built with
`-dynamic-import=lazy` on Windows (the program's IR units, the islands, the
C runtime objects), and is part of the object cache's keys through
`HostClangArgs`. A prototype (a C executable with a `_Thread_local`, a DLL
reading it on two threads) gave each thread its own value.

**Option B — accessor functions.** Replace each thread-local the islands
read with a getter exported by the executable. Rejected: every access in
the generated IR and the C runtime changes, for one backend on one OS.

**Cost.** A thread-local access in a lazy-mode Windows program is a call
instead of a segment-relative load. The default (`bundled`) and every
other host are unchanged. A faster path, if one is ever needed, is
Option B for the few hottest variables.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|

| `__emutls_get_address` in the mingw runtime | Available | libgcc / compiler-rt |
| The island loader on Windows (`LoadLibrary`) | Built | isolated mode |
