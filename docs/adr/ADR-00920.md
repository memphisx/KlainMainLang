# ADR-00920: `Atomics.isLockFree` rejects a non-numeric size argument cleanly (invalid-IR sweep)

- **Date**: 2026-09-13

## Context

`Atomics.isLockFree(x)` emitted its size comparison as `icmp eq i64 <x>, 1`
(and `2`/`4`/`8`) after `e.coerce(x, TypeI64)`. When `x` was a string, `coerce`
reinterpreted the string's `ptr` value as an `i64` operand rather than
converting it, so the emitted comparison read
`icmp eq i64 getelementptr(... @.s0 ...), 1` — a `ptr` constant expression where
`i64` is expected. Invalid IR, clang rejected it. Surfaced in the Test262
CLANG_ERROR sweep (`built-ins/Atomics/isLockFree/corner-cases.js`, which does
`Atomics.isLockFree('1')`).

## Decision

TypeScript types `isLockFree` as `(size: number) => boolean`, so a string
argument is a type error in the source language. Reject it cleanly at compile
time via `coerceChecked` (the established A1 technique) instead of letting
`coerce` produce invalid IR. A valid numeric argument is unaffected: the four
width comparisons emit as before.

## Implementation notes

- `codegen/llvm/emit_atomics.go` (`isLockFree` case): replaced
  `e.coerce(szVal, TypeI64)` with
  `e.coerceChecked(szVal, TypeI64, args[0].GetPos(), "Atomics.isLockFree size")`
  and propagated its error.
- `coerceChecked` already rejects a `ptr`-shaped (string) value against a numeric
  target via `coercionIsSound`, with the typed-subset diagnostic.

## Verification

- `TestE2EAtomicsIsLockFreeNumeric` (valid `1/2/4/8` → true, others → false,
  matching Node) and `TestE2EAtomicsIsLockFreeStringRejected` (string arg → clean
  compile error, no invalid IR) — new.
- `built-ins/Atomics/isLockFree/corner-cases.js` now clean-rejects at the
  `isLockFree('1')` line instead of CLANG_ERROR.
- macOS arm64.
