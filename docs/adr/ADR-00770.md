# ADR-00770: fs errors carry the numeric `err.errno`

- **Relations**: completes the fs error-shape surface started in [ADR-00684](ADR-00684.md) (`code`/`errcode`/`errstr`) and [ADR-00768](ADR-00768.md) (`syscall`/`path`); answers [TDD-00180](../tdd/TDD-00180.md) §4 / OQ2
- **Date**: 2026-09-07

## Context

Node fs (and net/child_process) errors expose `err.errno`: the **negative
libuv-style errno** (`ENOENT` → `-2`). The port carried `err.code` (the string),
`err.syscall`, and `err.path` ([ADR-00768](ADR-00768.md)) but not the numeric
`errno` — the last field of the fs-error shape. The shared `errorObjType` already
had an `errcode` field (idx 4), but that is **node:sqlite's** positive result
code (`err.errcode`, [ADR-00684](ADR-00684.md)) — a different property with a
different sign and meaning; `__kml_fs_throw` had been storing the raw positive
errno there, which is neither Node's `.errno` (wrong name and sign) nor a real
Node fs property.

## Decision

- **New `errno` field** on `errorObjType` (idx 8, `f64`), distinct from `errcode`
  (sqlite). `buildErrorObj` defaults it to `0`, so an ordinary `new Error()` reads
  `err.errno === 0` (Node reports `undefined`; the port's `0` is the same falsy
  default it uses for an unset numeric error slot). Resolved by name through
  `FieldIndex` — no special-casing.
- **`__kml_fs_throw` stores `-(errno)`** into the new field (negated at the IR
  level: `sub i32 0, %errno_val` then `sitofp`). The existing `errcode` (idx 4)
  store is left untouched to avoid disturbing sqlite; it is a non-Node stray on fs
  errors (Node fs errors have no `.errcode`), harmless and pre-existing.
- **AggregateError allocation bumped 64 → 72 bytes** so an `errorObjType`-typed
  read of the new trailing field on an AggregateError stays in-bounds — the same
  guarantee the earlier trailing fields rely on.

## Faithfulness notes

- **POSIX (Linux/macOS): exact.** `-(errno)` is precisely Node/libuv's value
  (`ENOENT` → `-2`, `EACCES` → `-13`, …).
- **Windows: a documented divergence.** Node on Windows reports libuv `UV_E*`
  numbers (e.g. `UV_ENOENT === -4058`), not the negated OS errno. This port
  normalizes errno to the **Linux numbers** on Windows (so `err.code` matches
  Node — the whole errno table is Linux-valued there), which makes `err.errno`
  the negated *Linux* value (`ENOENT` → `-2`) rather than `-4058`. The string
  `err.code` — the idiomatic discriminator — is identical to Node on every host;
  only the rarely-used numeric magnitude differs on Windows. Matching the exact
  `UV_E*` numbering would need a Windows-only translation table and is deferred as
  low-value (no code hardcodes `err.errno === -4058`).

## Verification

- New E2E test `TestE2EFsErrorErrno` (`tests/fs_test.go`): `readFileSync` on a
  missing path → `err.errno === -2`; a plain `throw new Error()` → `0`.
- `sqlite` oracle tests (which read the separate `err.errcode` field) still pass —
  confirms the new field is additive and didn't disturb the sqlite result code.
- Full `Error`/`Exception`/`Aggregate`/`throw`/`catch`/`StructuredClone` suites
  green on Windows 11 (the shared-`errorObjType` grew by one field).
- `go build`, `go vet ./codegen/...` clean. Verified on **Windows 11 native**;
  Docker Linux + conformance run at delivery. `make status`/`status-check`,
  `make reference-check` run at delivery.
