# ADR-00252: Re-resolve an assigned variable's storage after the RHS runs (closure-capture promotion)

- **Relations**: fixes a latent bug; complements [ADR-00001](ADR-00001.md) (closure-capture boxing)
- **Date**: 2026-08-20

## Context

The idiomatic self-cancelling interval assigned through a pre-declared binding —

```ts
let id = 0
id = setInterval(() => { /* … */ if (done) clearInterval(id) }, 5)
```

— never cancelled: inside the callback `id` read as `0`, so `clearInterval(id)`
never matched the real timer. The callback's own writes to *other* captured
variables (e.g. a `count`) worked, and a plain `id = setTimeout(cb)` with a
callback that does *not* capture `id` also worked — only the self-referential
case failed.

## Investigation

Closure capture ([ADR-00001](ADR-00001.md)) *promotes* a captured local to a
freshly-`malloc`'d heap cell the first time a closure captures it, updating the
binding's storage pointer in place (`updateSymbolInPlace`, emit_func.go) so the
enclosing scope and every capturing closure share one cell.

`emitAssign`'s scalar path resolved the target binding's pointer **before**
evaluating the right-hand side, then stored to that pointer **after**. In the
self-referential case the RHS (`setInterval(() => { … id … }, …)`) creates the
capturing closure while it is evaluated, which promotes `id` to a new cell — so
the pre-evaluation pointer is now stale. The assignment wrote the real timer id
to the *old* alloca; the closure read the *new* cell, still holding `id`'s
pre-initialization `0`.

The var-decl form (`const id = setInterval(…)`) had already been fixed the same
way in `emitVarDecl`; the assignment form (`emitAssign`) was the remaining path.

## Decision

In `emitAssign`'s scalar-identifier store, re-resolve the binding with a fresh
`lookup(ident.Name)` **after** the RHS has been emitted and just before the
store, so the write targets whatever cell the binding now lives in — the same
cell the closure captured. A one-line, behavior-preserving change for every
non-self-referential assignment (the fresh lookup returns the same pointer).

## Consequences

- `id = setInterval(() => { … clearInterval(id) … }, …)` (and the `setTimeout`
  equivalent) now sees the real timer id and cancels correctly; the program
  terminates instead of looping forever.
- Any `x = <expr>` where evaluating `<expr>` promotes `x` for capture now stores
  to the promoted cell — the assignment and the closure agree on one location.
- Scoped to the scalar-identifier `=`/arithmetic-compound path (the reported
  case). The array-variable, nullable-scalar-local, and logical-compound paths
  keep their own storage handling; a self-referential capture through those is a
  far narrower combination, not addressed here.
