# ADR-00694: String array indices and slice-method bounds emit valid IR

- **Date**: 2026-09-04

## Context

A cluster of `built-ins/Array` Test262 files failed codegen under `-compat=js`
with clang errors:

- `constant expression type mismatch: got type 'ptr' but expected 'i64'`
- `'%tNN' defined with type 'ptr' but expected 'i64'`

The common trigger is a *string* value flowing into an array index position —
either a bracket index (`x["4294967296"]`, `z["1.1"]`, `a["2"]`) or a
slice-style method bound (`[0,1,2,3].copyWithin("0", 2)`,
`arr.fill(9, "1", "3")`, `arr.at("0")`, `arr.slice("1", "4")`). In JS a string
array index addresses the same slot as the equivalent number: `a["2"]` is
`a[2]`. The bracket-index and slice-bound code paths coerced the index with
`e.coerce(v, TypeI64)`, which has no string→integer rule — the string's data
pointer was left in the register where an i64 was required, so the emitted
bounds check (`icmp uge i64 <ptr>, …`) and slot GEP (`getelementptr … i64
<ptr>`) referenced a pointer where an integer was demanded.

## Investigation

`emitIndexPtr` (`codegen/llvm/emit_exprs_member.go`) computes the slot GEP for
both reads (`emit_exprs_member.go`) and writes (`emit_exprs_assign.go`,
`emit_arrays_mutate.go`); it ended with `idxVal = e.coerce(idxVal, TypeI64)`
before the `icmp uge` bounds check. Inspecting the invalid IR from
`property-cast-number.js` showed
`%t51 = icmp uge i64 getelementptr inbounds ({ i64, [11 x i8] }, ptr @.s9, …), %t49`
— the interned string `@.s9` used directly as the index. `coerce`
(`emit_exprs_coerce.go`) converts a NaN-boxed dynamic value into i64 via
`emitAnyToNum`, and a numeric value via `fptosi`, but a plain string-typed
`ptr` falls through to the same-IR passthrough and is emitted unchanged.

The identical defect reached every slice-style bound, which all normalize a
raw index through `e.emitNormalizeSliceIdx(e.coerce(x, TypeI64).Ref, …)` in the
array codegen files (copyWithin/fill/at/slice/splice/toSpliced).

Two representative files in the reported set — `at/index-non-numeric-argument-
tointeger.js` (`a.at(function(){})`, `a.at([])`) and the `find/findIndex/
findLast/findLastIndex` `array-altered-during-loop.js` — fail for a *different*
root cause (ToNumber of an arbitrary object/function, and an empty array
literal inferred as `number[]` then receiving `string` elements via `push`).
Those are out of scope here and left tracked as follow-up (see Side effects).

## Decision

Add `arrayIndexToI64` in `codegen/llvm/emit_arrays_core.go`: a single
normalizer that all array-index and slice-bound sites use in place of
`e.coerce(x, TypeI64)`. For a string-typed operand it parses the value to an
integer at runtime with `strtoll(base 10)` — matching the canonical decimal
array-index spelling — and returns the i64. Every other operand (numeric,
dynamic/NaN-boxed) rides the unchanged `e.coerce(x, TypeI64)` path, so no
existing numeric behavior moves. A non-index string such as `"1.1"` or
`"4294967296"` resolves to an out-of-range slot and is caught by the existing
bounds check rather than crashing the build.

## Implementation notes

- `emit_arrays_core.go`: new `arrayIndexToI64(Value) Value`; string kind →
  `ensureStrtoll()` + `call i64 @strtoll(ptr %s, ptr null, i32 10)`.
- `emit_exprs_member.go`: `emitIndexPtr` now calls `arrayIndexToI64` for the
  bracket index (covers array reads and, through the shared helper, writes).
- `emit_arrays_iter.go`, `emit_arrays_transform.go`, `emit_arrays_mutate.go`,
  `emit_arrays_sort.go`: the `emitNormalizeSliceIdx(e.coerce(x, TypeI64).Ref …)`
  sites for copyWithin/fill/at/slice/splice now feed through `arrayIndexToI64`.
- The buffer/blob/arraybuffer/string variants of the same normalize call were
  left untouched — this change is scoped to the array element path.

## Side effects discovered

- `a.at(function(){})` / `a.at([])` and the `find*` `array-altered-during-loop`
  files still fail codegen, from unrelated root causes: full ToNumber of a
  non-numeric object, and an empty-array literal inferred as `number[]` then
  fed heterogeneous elements. Both belong to the dynamic-object/any-array line
  of work, not the index-coercion path fixed here.
- The runtime semantics of an *out-of-range* string index (real JS makes it an
  own property returning `undefined`, not an out-of-bounds throw) remain part
  of the separate dynamic-object model; this change only makes the IR valid.

## Verification

- `go build -o klainmain .` clean; `go vet ./codegen/...` clean.
- New E2E suite `tests/array_index_coercion_ir_test.go` (string index read/
  write, copyWithin/fill/at/slice string bounds) passes.
- Example `examples/jsmode/array_string_index.js` compiles under `-compat=js`
  and prints the expected slots.
- Test262 (with the repo harness shim), `-compat=js`: `property-cast-number`,
  `property-cast-nan-infinity`, `property-cast-boolean-primitive`,
  `S15.4_A1.1_T4/T5/T9`, `copyWithin/coerced-values-{target,start,end}`, and
  `fill/coerced-indexes` all reach clang cleanly (previously CLANG_ERROR).
- Verified on Apple Silicon (M4) macOS.
