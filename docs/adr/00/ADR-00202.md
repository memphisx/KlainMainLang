# ADR-00202: Fix invalid SSA in the WebSocket frame-decode and client-scan runtime templates

- **Relations**: `Extends ADR-00125, ADR-00128`
- **Date**: 2026-08-17

## Context

First development session back on the Apple Silicon (M4) machine after several releases done on the Linux box (last Mac work was ~v0.10.0; the tree is now at v0.37.0). The machine-switch sanity pass (`go build`, `go vet`, `go test ./...`) surfaced **61 failing E2E tests**, every one dying at the `clang` step with the same LLVM IR verifier error:

```
error: invalid LLVM IR input: Instruction does not dominate all uses!
  %maskkey = add i32 %maskkey_o3, 0
  call void @__kml_ws_mask_apply(ptr %outbuf, i64 %plen, i32 %maskkey)
Instruction does not dominate all uses!
  %dninstance = load ptr, ptr %dninstance_p, align 8
  %dm_onmsg_p = getelementptr ..., ptr %dninstance, i32 0, i32 4
  ...
```

The failures spanned four *unrelated* features — `WebSocket` (server + client), `EventSource`, `http.listen`, and `process.on('SIGINT'/'SIGTERM')` — which was the tell: a plain `http.listen` GET test (no WebSocket in the program at all) failed with a `maskkey`/WS-client error. The WebSocket runtime functions (`@__kml_ws_frame_decode`, `@__kml_wsclient_scan`) are emitted into the module for any event-loop-driven program, so two malformed functions poisoned the whole-module verify for every such program.

These features shipped green on the Linux dev machine (their own ADRs — [ADR-00125](ADR-00125.md)–[ADR-00131](ADR-00131.md), [ADR-00201](ADR-00201.md) — record full `go test ./...` green on Linux/x86-64). The invalid IR is target-independent, so the divergence is in the toolchain: the Linux LLVM build accepted the malformed SSA, whereas Apple clang 21.0.0 on arm64-darwin rejects it at the verifier. This was one of the open "changes being tested on Apple Silicon" questions.

## Investigation

Both offending functions are hand-written IR string templates, not builder-emitted SSA, so the defect is fixed in the template text.

**`@__kml_ws_frame_decode`** (`codegen/llvm/runtime_websocket.go`): `%maskkey` is defined only in block `readmask:` (the masked-frame path). It is consumed in `dounmask:`. But `readmask` does not dominate `dounmask`: the CFG is `lenmerge → {maskcheck→readmask | nomaskhdr} → afterhdr → havefullframe → {dounmask | afterunmask}`, so `afterhdr` (and everything below it, including `dounmask`) is reachable via `nomaskhdr`, bypassing `readmask`. At runtime `dounmask` is only entered when `%masked` is true — which implies the `readmask` path ran — so the value is always live in practice; but LLVM's dominator analysis is purely structural and (correctly) rejects it. The template already solved this exact problem for `%payloadstart_m`, defined in the same `readmask` block and phi'd through `afterhdr` (`%payloadstart`); `%maskkey` was simply missed.

**`@__kml_wsclient_scan`** (`codegen/llvm/runtime_websocket_client.go`): `%dninstance` (the per-connection instance pointer, field 5 of the entry struct) is loaded in block `donotify:`, which is entered only when `pending == 1`. It is consumed in `ddispatch:` and `doclose:`, both reachable via the `checkopen → doread → … → decodeloop → …` path that skips `donotify` entirely. Same class of defect: definition block does not dominate the use blocks.

Both are genuine invalid SSA, independent of the WebSocket masking / dispatch logic being otherwise correct.

## Decision

Make each value dominate all its uses, without changing runtime behavior:

- **`maskkey`**: rename the `readmask:` definition to `%maskkey_r` and add a phi in `afterhdr:` (which dominates `dounmask:`) alongside the existing `%payloadstart` phi: `%maskkey = phi i32 [ %maskkey_r, %readmask ], [ 0, %nomaskhdr ]`. The `0` incoming value on the unmasked path is never consumed (`dounmask` is guarded by `%masked`), so behavior is identical.
- **`dninstance`**: hoist the two-line load (`%dninstance_p` GEP + `%dninstance` load) out of `donotify:` into `scanbody:`, which dominates every block in the function that uses it (`donotify` and its subtree, plus `ddispatch`/`doclose`). The pointer at field 5 is set at connection creation and always valid to load in `scanbody`, so the hoist is unconditionally safe.

Both fixes make the IR valid on every target; they were chosen over any target-specific workaround because the IR was objectively wrong, not merely disagreeable to one verifier.

## Implementation notes

- `codegen/llvm/runtime_websocket.go`: `%maskkey_r` rename at the `readmask` definition + new phi in `afterhdr` (with a comment explaining the never-consumed `0`).
- `codegen/llvm/runtime_websocket_client.go`: `%dninstance_p`/`%dninstance` load moved from `donotify:` to immediately after the `%entryp` load in `scanbody:`; removed from `donotify:`.
- No change to any Go-side codegen logic, callback wiring, or struct field indices.

## Side effects discovered

- The root cause is a toolchain-verifier divergence, not a Mac-only codegen path: the same IR would be rejected by any strict LLVM verifier. The Linux dev machine's earlier "green" runs did not exercise this verifier strictness. Recorded here so future "passes on Linux" claims for hand-written IR templates are not treated as proof of valid SSA — the Apple clang verifier is now the stricter gate of the two dev machines.
- No other hand-written IR template failed the verifier in the full-suite run (only these two functions appeared in the errors), but hand-written templates as a class carry this risk; the two `.entries()`/phi patterns here are the model for the correct idiom.

## Verification

- **Mac (Apple Silicon M4, Apple clang 21.0.0, arm64-apple-darwin)**: `go build`, `go vet ./...` clean. Full `go test ./...` green (was 61 failing across `TestE2EWS*`, `TestE2EWebSocket*`, `TestE2EHTTPListen*`, `TestE2EEventSource*`, `TestE2ESignal*`). The affected groups run in ~44s; full suite green in ~351s.
- Not re-run on Linux this session (single-machine-at-a-time); the fix is valid SSA on all targets and preserves behavior, so no Linux regression is expected.
- `make conformance` (Test262) run at delivery.
