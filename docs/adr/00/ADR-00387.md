# ADR-00387: The `arguments` object, synthesized from parameters

- **Date**: 2026-08-27

## Context

Referencing `arguments` inside a function body failed with `undefined variable
'arguments'` — the Functions & closures status row's first caveat ("The
`arguments` object is unsupported — use a `...rest` parameter"). Real code, and a
slice of the Test262/TS corpus, uses `arguments` for simple same-typed variadic
patterns (`sum`, `max`, string joins), so it was worth closing for the common
case.

## Investigation

`arguments` was simply an unbound identifier: nothing in `emitFunctionDeclAs`
(`codegen/llvm/emit_func.go`) ever defined it, so it fell through to the
undefined-variable error like any other free name.

This compiler has **static arity** — there is no variadic call beyond an
explicit `...rest` parameter — so `arguments` can only ever reflect the declared
parameters. And its arrays are **homogeneous**, so an `arguments` array is only
representable when every parameter shares one element type. That bounds a clean
V1: synthesize `arguments` as an array of the declared parameter values, for
same-typed simple parameters.

The array machinery to build it already existed: `emitArrayLiteralData`
(`emit_arrays_core.go`) malloc's a buffer and stores each element by evaluating
its expression — so an array literal of identifier elements (one per parameter,
each already in scope after the param-binding loop) produces exactly the backing
buffer, and a two-alloca `Symbol{Ptr, LenPtr}` binds it under the name.

## Decision

After the parameter-binding loop in `emitFunctionDeclAs` (non-task bodies only),
call `synthesizeArgumentsObject`, which:

1. Returns early if a parameter is literally named `arguments` (user binding
   wins), or if a free-variable scan of the body shows `arguments` is never
   referenced (so an ordinary function pays nothing), or if `arguments` is
   shadowed by a local of that name (the scan treats it as bound).
2. Rejects cleanly, with a specific message, when the parameter list can't form
   one homogeneous array: a **rest** parameter (use it directly), a
   **destructured** parameter, **mixed** parameter types, or an
   array/nullable/`any` parameter type.
3. Otherwise builds `[p0, p1, …]` via `emitArrayLiteralData` at the element type
   of the (uniform) parameters, and binds `arguments` as a two-alloca array
   `Symbol` of `elemTy[]`. A zero-parameter `arguments` is an empty `number[]`.

`arguments.length`, indexing, and `for…of` then work through the ordinary array
paths with no further changes.

## Implementation notes

- Restricted to `emitFunctionDeclAs` (named function declarations). An **arrow
  function** has no own `arguments` in real JS; here the reference simply stays
  an undefined-variable error rather than incorrectly synthesizing one from the
  arrow's parameters.
- Skipped for a may-suspend **task body** (`taskBody`), whose parameters live in
  `%__taskargs` rather than plain allocas — out of V1 scope.
- Since arity is static, the synthesized `arguments` reflects exactly the
  declared parameters. For a call that passes every declared argument this
  matches real JS; it does not shrink for an omitted optional/defaulted argument
  the way real JS's `arguments` would, and never grows beyond the declared
  parameters. This is a disclosed divergence, not silent — the mismatching cases
  above are clean rejections.

## Side effects discovered

None beyond the disclosed divergences above.
