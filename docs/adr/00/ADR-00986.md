# ADR-00986: async createServer handler task-await — concurrency + in-process client

- **Relations**: `Extends ADR-00985`
- **Date**: 2026-09-17

## Context

ADR-00985 made a Node `http.createServer(async (req, res) => …)` handler that
awaits a **task-shaped** promise (the result of a may-suspend async helper, not
`fetch` directly) run correctly instead of crashing. It left two follow-ups,
both on scenarios that previously only crashed (so neither is a regression):

- **(a) Serialization.** On the connection fiber, `await <task-promise>` took
  `__kml_task_await_ready`'s top-level busy-wait (`toploop`: drain microtasks +
  `sched_step` + fire timers + `usleep`, repeat) because the fiber is not a
  scheduler task (`@__kml_current_task` is null). The busy-wait held the loop to
  that one fiber, so concurrent such requests serialized — measured 3× behind a
  400ms upstream ≈ 1.2s instead of ≈ 0.4s. Awaiting `fetch` directly already
  stayed concurrent (its `maybeconn`/`doyield` path parks the fiber).

- **(b) In-process client hang.** With the same async handler driven by an
  **in-process** `http.get` client on the one event loop, the client's own
  completion reaction (`res.on('end')`) was never delivered and the process
  hung. External clients (curl / Go / browser) were fine.

## Investigation

**(a).** `__kml_task_await_ready` (codegen/llvm/runtime_task.go) branched
`current_task == null ? toploop : ontask`. The `ontask` arm already parks a
scheduler task cleanly via `swapcontext`. The connection-handler async fn runs
directly *on the connection fiber* (not as a spawned task), so inside it
`current_task == null` while `@__kml_current_conn_idx >= 0` — it fell into the
busy-wait. `__kml_reqbody_pull` (codegen/llvm/runtime_http_reqbody.go:207) had
already solved the exact task-vs-fiber question: only the fiber's own stack may
`swapcontext` through the conn slot; a spawned task that merely inherited
`@__kml_current_conn_idx` must not (a wild-jump crash on multi-chunk uploads).
`await` only compiles inside async fns, and the sole async fn that runs with no
current task is the connection handler itself, so `(task==null && conn_idx>=0)`
means we are genuinely on that fiber and may yield it — mirroring `fetch`'s
`doyield` and `reqbody`'s guard. The rejected approach in ADR-00985 yielded
without that `current_task`-first guard and corrupted the streaming (`pull` /
`req.stream`) contexts, whose async callbacks run as tasks.

**(b).** Instrumented repro (scratchpad): the handler ran to completion and
wrote its response, but the in-process client's `http.get` callback never fired
— curl never delivered the buffered response. Adding an unrelated
`setInterval(…, 3)` to keep the loop spinning made it work, pinning the cause to
a **blocking `select()`**. The event loop's timeout decision
(runtime_http.go, `ctodone:`) forces a non-blocking poll (`needimmediate`) when
microtasks are queued, a task is resumable, or `@__kml_conn_poke` is set — but
all of those are one-shot and cleared before the iteration that must read the
in-process client's now-readable socket. After the resumed fiber writes its
response there is no JS timer left and curl's idle deadline is -1, so `select()`
blocked forever with the client's completed response sitting unread. The
in-process client (`__kml_httpc_fire_ready`, emit_http_client.go) shares the
same curl-multi and loop; its completion is serviced only by `docurlperform`,
which runs once per iteration *before* the fiber resume scan.

## Decision

**(a)** In `__kml_task_await_ready`, when `current_task == null` and
`@__kml_current_conn_idx >= 0` **and the connection is not consuming its own
request body** (see the gate below), park by yielding the connection fiber to
the event loop instead of busy-waiting: re-check the promise's result, drive
microtasks/scheduler/timers once (so a promise settleable without I/O returns
with no yield), and if still pending `swapcontext(slot.ctx, @__kml_main_ctx)`,
recomputing the slot each pass (the conn array may realloc while suspended). The
fiber is resumed by `@__kml_conn_poke` (set by `__kml_task_finish`/`_reject`
when the awaited task settles) or fd readiness, then re-checks and re-parks. The
top-level (`conn_idx == -1`) busy-drive `toploop` is unchanged.

**Streaming-safety gate.** A handler that consumes its request body — `for await
(… of req.stream())`, as in examples/streams/http_upload.ts — awaits a
task-promise on the connection fiber *while that same fiber's fd is actively
delivering the body*. Yielding it there lets the reactor re-drive/re-resume the
fiber on its own still-readable fd, a wild-jump crash (the exact failure that
sank ADR-00985's rejected first attempt on the streaming examples; a bare
`task==null && conn_idx>=0` guard does not exclude it, since the handler here
genuinely is on its own fiber). So the yield is gated on a new precise,
non-flickering predicate `__kml_reqbody_active_on_fd(fd)` — is a req.stream
context active on *this* connection's fd (the `active` flag, held for the whole
streaming lifetime, not `reqbody_want`'s momentary hint). When it is, the await
keeps the busy-drive `toploop` (correct pre-ADR-00986 behavior); the yield is
taken only for an idle-fd await (proxy front, request already received).

**(b)** Add `@__kml_conn_ran` (thread-local i8). Set it right after any
connection fiber runs — the resume-scan `rresume` swap and the freshly-accepted
`__kml_http_append_conn` swap. Consume and clear it in the select-timeout
decision, OR-ing it into `needimmediate`. A fiber that ran may have written a
response an in-process client must now read, so the very next `select()` polls
without blocking and that iteration's `docurlperform` delivers the bytes. It is
one-shot (at most one extra non-blocking poll per fiber run) — not a spin: if
the resumed fiber merely re-parked, the next poll finds nothing and the loop
blocks normally.

## Implementation notes

- runtime_task.go: `entry` now branches to `checkconn` → `ckstreaming` (the
  gate) → `fiberwait` / `fdrive` / `fyield`, all preceding the unchanged
  `toploop`. One extra `promiseStructIR` arg in the `Sprintf` (the added
  `fres_p` GEP). No GC-restore after the `fyield` swap — the resumer (`rresume`)
  sets `GC_stackbottom`, same as `fetch`'s `doyield`.
- runtime_http_reqbody.go: `__kml_reqbody_active_on_fd` (scans the pump
  registry for an active context on the fd). Always linkable: a `ret i1 0` stub
  is emitted next to the existing `reqbody_want`/`reqbody_pump` stubs when a
  program uses the task/http runtime but no req.stream.
- runtime_http.go: `@__kml_conn_ran` defined in `ensureFiberRuntime` (so it
  links wherever the task runtime is emitted — `ensureTaskRuntime` →
  `ensureFiberRuntime`, even in a no-http async program where the fiber path is
  never taken); set in `rresume` and `append_conn`; read/cleared in `ctodone`.
- Ordering relied on: `ctodone` (timeout decision) runs at loop bottom before
  `select`; the fiber resume scan runs after `select`; so a flag set in the scan
  is read by the immediately-following iteration's `ctodone` with no intervening
  `select`.

## Side effects discovered

The (a) fiber-yield initially crashed examples/streams/http_upload.ts (and would
have http_chunked.ts) deterministically — caught by `make examples`, not the
HTTP test suite, the same lesson as ADR-00985's rejected attempt. Root-caused to
the streaming-safety hole above and fixed with the `__kml_reqbody_active_on_fd`
gate; both streaming examples pass. The `http.createServer` remaining edges
bullet in docs/BACKLOG.md is updated to drop (a) and (b).
