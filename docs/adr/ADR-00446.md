# ADR-00446: TS overload signatures parsed and erased

- **Date**: 2026-08-29

## Context

The TypeScript acceptance oracle's false-reject histogram put `expected {, got
;` at 117 cases — every one a TypeScript overload group (`function f(x:
string): void;` signatures preceding one implementation, and the class-method/
constructor equivalents). A single unsupported construct rejects an entire
case, so this was the largest single-message parse gap in the corpus.

## Investigation

Sampled cases (`ambiguousCallsWhereReturnTypesAgree`, `classdecl`,
`callSignaturesWithOptionalParameters2`) all share the same shape: one or more
body-less signatures immediately followed by the implementation, in the two
positions TS permits them — top-level `function` declarations and class
members (methods and `constructor`). Since this compiler dispatches calls
against a single concrete implementation and has no overload-resolution type
model, the correct subset semantics is *erasure*: parse the signatures,
verify the group is well-formed, and keep only the implementation — the same
"TS erased syntax" treatment `debugger`, ambient declarations, and type
annotations already get.

## Decision

- `parseFunctionRest` gains an `overloadOK` mode: a `;` where the body block
  would start returns the declaration with `Body == nil` and a new
  `ast.FunctionDeclaration.IsOverloadSig` flag. Only the two legal contexts
  set the mode — top-level `function` declarations and non-abstract,
  non-accessor class members. Function expressions and object-literal methods
  still require a body.
- Top-level: `parseFunctionDecl` loops while the parsed declaration is a
  signature — the next tokens must be `[export] [async] function [*] <same
  name>` — and returns only the final body-bearing implementation. JSDoc
  (`@erased`, `@param`) and generator flags apply to the implementation.
- Class body: a signature member is dropped and the group held open in
  `pendingOverload`; any member that is not another same-name
  method closes the class with a clear rejection, as does reaching `}` with
  the group still open. Constructor overloads ride the same path.
- Ill-formed groups stay rejections, not silent acceptance: a signature with
  no implementation, an interrupted group, and a mismatched name each get a
  dedicated error naming the offending overload.

Erasure means no arity/type checking of call sites against individual
signatures — calls type-check against the implementation's (usually wider)
parameter list. That is the subset's existing semantics for every call, just
now reachable for overloaded declarations too.

## Implementation notes

- `ast/nodes.go`: `IsOverloadSig` field.
- `parser/parser_stmts.go`: `parseFunctionRest` fourth parameter + the
  top-level group loop in `parseFunctionDecl`.
- `parser/parser_classes.go`: `pendingOverload` tracking in `parseClassDecl`.
- `parser/parser_literals.go`: call sites pass `overloadOK=false`.
- Codegen is untouched — no `IsOverloadSig` declaration ever reaches it.

## Side effects discovered

The TS oracle's false-accept count rose 530 → 562: cases whose *only* error
is an ill-formed-overload rule this compiler doesn't model (e.g. signature/
implementation type mismatches) now compile clean. Expected for erasure
semantics; they remain listed in the report's false-accept table.

## Verification

Mac. `tests/overloads_test.go` (two positive E2E, three rejection tests) and
`examples/language/overload_signatures.ts` both pass; parser + class/function
E2E test batch green. TS oracle: **53.8% → 54.1%** agreement (match-accept
1130 → 1191). Node oracle unchanged (37 passed), as expected for a TS-only
parse feature.
