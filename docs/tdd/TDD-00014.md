# TDD-00014: Full-pipeline (codegen-through-binary) fuzz testing

- **Status**: Implemented
- **Date**: 2026-07-28

## Context

[ADR-00068](../adr/ADR-00068.md) added native Go fuzz testing (`go test -fuzz`) for the lexer and parser, deliberately scoped to those two pure, fast, in-process stages. It explicitly deferred fuzzing anything downstream of the parser — codegen, `clang`, and the resulting native binary — because reusing the same approach (feed raw mutated bytes in as source text) doesn't work well there: almost every random byte string is syntactically invalid TypeScript and gets rejected by the parser before it ever reaches codegen, so the "interesting" hit rate for actually exercising codegen would be very low, and each iteration that *does* get that far is orders of magnitude slower (it shells out to `clang`) than lexer/parser fuzzing's millions-of-execs-per-second throughput.

Fuzzing a compiler's backend is also a different problem from fuzzing a typical library function in one specific way this project's own goals make sharp: this compiler's job on the "number" happy path isn't just "don't crash," it's "produce the exact value real JS/TS semantics (or this compiler's documented, deliberate deviations — see `number → i64`, `STATUS.md`'s Type System section) would produce." A crash-only fuzzer can never find a bug where the compiler runs to completion, produces a binary, and that binary confidently prints the *wrong number*. Catching that class of bug needs a fuzzer with an oracle — something to compare the compiled program's actual output against a known-correct expected value — not just a "did it panic" check.

This was scoped out concretely while investigating: prototyping the arithmetic-correctness oracle below (before this document existed) immediately surfaced a real bug on the first hand-written repro (`10 / 0` silently printing garbage instead of crashing or throwing — LLVM's `sdiv`/`srem` are undefined behavior on a zero divisor) — fixed separately in [ADR-00069](../adr/ADR-00069.md) since it's a self-contained codegen fix, not part of the fuzz harness itself. That result is direct evidence the "generate a program with a known-correct answer, run it, compare" approach finds real bugs that crash-only fuzzing structurally cannot.

## Design

Two complementary lanes, both driven by Go's native fuzzer (`go test -fuzz`), both living in `tests/` (the package that already owns `buildBinary`/`compileAndRun` — the full parse → codegen → `clang` → execute pipeline — via `tests/compiler_test.go`, so no new pipeline plumbing is needed):

### Lane A — Correctness oracle: random arithmetic expressions

The core idea, and the one that directly answers "catch bugs where the generated binary's *execution* is wrong, not just where compilation crashes":

- Fuzz over a single `int64` seed (Go's native fuzzer supports `int64` as a fuzz-corpus type directly — no need to hand-roll a byte-to-PRNG scheme). Feed it into `rand.New(rand.NewSource(seed))` for a fully deterministic generator.
- Recursively build a random arithmetic expression tree (`+ - * / %`, unary `-`, integer literals clamped to a small range) using that RNG, **simultaneously** computing the expected result using Go's own `int64` arithmetic as the oracle. This is a valid oracle specifically *because* this compiler's default `number` type is `i64` with wraparound (non-`nsw`/`nuw`) `add`/`sub`/`mul` and truncating `sdiv`/`srem` — confirmed by reading `codegen/llvm/emit_exprs.go` — which is bit-for-bit what Go's own `int64` operators do. This wouldn't be a valid oracle for real JS's `number` (IEEE-754 double, non-truncating `/`), which is a deliberate, documented divergence this compiler already made.
- Emit the expression as fully-parenthesized KlainMainLang source (`console.log(((a + b) * c));`) — parenthesizing every subexpression sidesteps ever needing the generator to replicate the parser's own precedence table to guarantee a specific parse tree.
- Compile and run it through the real pipeline (`buildBinary` + `exec.Command`), and assert the printed stdout equals the Go-computed expected value exactly.
- Literal range and tree depth are both clamped (literals to `[-1000, 1000]`, depth to a small constant) specifically to keep the *oracle* simple and unambiguous — not because larger values are uninteresting, but because two known edge cases exist where "what should happen" is itself ambiguous/UB at the LLVM level rather than a place a fix belongs:
  - Division/modulo by a zero divisor — already handled: as of [ADR-00069](../adr/ADR-00069.md), this throws a catchable `Error`, so the generator instead avoids generating a zero divisor (substitutes `1`) to keep this lane's oracle a plain "compare printed numbers," not "sometimes compare printed numbers, sometimes compare thrown-error text."
  - `math.MinInt64 / -1` (and the `%` equivalent) — LLVM's language reference documents this as a second, *separate* UB case for `sdiv`/`srem`, distinct from division-by-zero, not covered by ADR-00069's guard. Reaching this exactly by chance (an intermediate wraparound result landing on exactly `-9223372036854775808` before a later `/-1`) is astronomically unlikely with clamped small literals, so it's not something this generator will organically find, and deliberately engineering it is a different (still valid) kind of test than what this lane is for. Tracked as a known latent gap in `STATUS.md`'s Known Limitations rather than fixed here.

### Lane B — Broad well-formedness/crash fuzzing across more language surface

A second fuzz target generates a wider grammar — variable declarations, `if`/`else`, `for`/`while` loops, arrays, function calls — with **no correctness oracle**, only well-formedness assertions: the Go compiler itself must not panic, `clang` must accept the emitted LLVM IR (any `clang` failure is unambiguously a codegen bug — it means invalid IR was emitted, regardless of what the *source* program was trying to do), and the resulting binary must not crash (segfault/abort) on a clean run. This trades oracle precision for surface coverage — it can't catch "silently wrong output," but it covers far more of the language than Lane A's arithmetic-only grammar, at the same "guaranteed syntactically valid, so it actually reaches codegen" cost Lane A already pays for.

### Rejected: differential testing against a real JS engine (e.g., Node)

Considered generating programs and comparing the compiled binary's output against running the same (or a translated) program through `node`. This is the standard "real" oracle for a JS/TS-targeting compiler and would be strictly more powerful than Lane A's hand-rolled Go-arithmetic oracle for anything outside the narrow `i64`-exact-match subset. Rejected for this pass specifically because KlainMainLang is a deliberately *non-conforming* subset of TypeScript in ways that are load-bearing to this project (`number → i64` truncating arithmetic instead of JS's float `number`, being the running example throughout this document) — a generator would have to itself encode exactly which language constructs currently have matching semantics vs. deliberate divergence to avoid the fuzzer reporting a flood of "bugs" that are actually documented, intentional behavior. `docs/testing/CONFORMANCE-COVERAGE.md`/[TDD-00008](TDD-00008.md)'s existing Test262-porting effort is already doing this classification work by hand, one spec-conformant behavior at a time — a real differential fuzzer belongs on top of that effort once it's mature enough to know which constructs are safe to compare, not stapled onto the compiler as it currently stands. Worth revisiting later; not scoped further here.
