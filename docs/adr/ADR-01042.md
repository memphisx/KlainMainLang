# ADR-01042: A cluster worker does not outlive its primary

- **Relations**: `Extends ADR-01027`; `Implements TDD-00025, TDD-00117` (the `{ workers: N }` cluster and its shared close flag)
- **Date**: 2026-09-21

## Context

Eighteen `prog.exe` processes from `TestE2EWindowsClusterRoundRobin` were found alive hours after the runs that
started them. The note that recorded them read it as "workers outlive a dead primary". That was half right, and
the half that was wrong mattered:

- The 18 were six complete trees — one **live primary** and its two workers each. The dead parent of every tree
  was the *test binary*: the runs were 2 minutes apart, i.e. killed by their timeout, and a killed or
  timed-out test binary runs no `t.Cleanup`, so `killProcGroup` never fired.
- The workers-outlive-the-primary bug is nevertheless real. Killing one of those primaries alone
  (`Stop-Process`, no tree kill) left both of its workers running and the port accepting, indefinitely.

Node's cluster worker exits when its channel to the primary disconnects (`process.exit(0)` on `'disconnect'`,
`lib/internal/cluster/child.js`). A worker left behind holds the listening socket, so the port never frees.

## Investigation

- Windows, `win32io.c` `kfd_rr_recv`: when the hand-off channel reports EOF the worker drops it and "falls back
  to accepting for itself" on the inherited listener — deliberately, mirroring what forked workers do. So a dead
  primary turned its workers into independent servers.
- POSIX, `__kml_http_cluster_fork`: plain `fork()`; nothing reacts to the parent's death. Workers are re-parented
  and keep serving the shared listener.
- The channel's EOF is not usable as the death signal: `close()` of a cluster listener in a primary that lives on
  closes the channels too (`win32io.c`, "A cluster listener takes its hand-off channels with it").
- `prctl(PR_SET_PDEATHSIG)` is Linux-only; macOS has no equivalent short of a kqueue `EVFILT_PROC` registration.
  The cluster event loop already wakes at least every 200 ms to poll the shared close flag (TDD-00117), so a
  `getppid()` comparison there is portable and costs one syscall per idle wake.

## Decision

A worker exits with status 0 once its primary is gone.

- **Windows** — the worker's start-up constructor (`kml_win_adopt_cluster`) opens the primary by the pid it was
  handed (`KML_WIN_RR`) and registers a thread-pool wait on the process handle
  (`RegisterWaitForSingleObject` → `ExitProcess(0)`). If the pid cannot be opened, or names a process *younger*
  than the worker (the primary died and the number was reused before the constructor ran), the worker exits at
  once. The self-accept fallback in `kfd_rr_recv` stays: it is what a worker does when a living primary closes
  one server.
- **POSIX** — the primary's pid is read with `getpid()` *before* `fork()` and stored in the child
  (`@__kml_cluster_primary_pid`; reading `getppid()` in the child could already name the reaper). The loop's
  per-iteration cluster poll compares `getppid()` with it and calls `exit(0)` on a mismatch
  (`httpClusterOrphanIR`). Bounded by the existing 200 ms cluster wake.

Test harness, Windows: the test binary assigns **itself** to a job object with
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` at `init`. Children inherit the job; its only handle dies with the binary,
so a killed or timed-out run takes every server tree it started with it. This is what actually produced the 18
orphans.

## Implementation notes

- `codegen/llvm/win32src/win32proc.c`: `kml_watch_primary`, called from `kml_win_adopt_cluster`.
- `codegen/llvm/runtime_spawn_win.go`: `httpClusterOrphanIR`; the fork block stores the primary's pid.
- `codegen/llvm/runtime_http.go`: `@__kml_cluster_primary_pid`, the `ccpoll` → `ccpoll1` splice.
- `codegen/llvm/emitter.go`: `usedGetppid`.
- `tests/procgroup_windows_test.go`: the job object; `tests/http_test.go`, `tests/cluster_windows_test.go`: tests.
- The POSIX poll lives inside the close-flag branch: a cluster whose flag `mmap` failed has no bounded wake and
  therefore no orphan poll either.

## Side effects discovered

None.

## Verification

Windows 11 x64: `TestE2EHTTPClusterWorkersExitWithPrimary` (port stops accepting after the primary alone is
killed), `TestE2EWindowsClusterWorkersExitWithPrimary` (both worker pids gone), `TestE2EWindowsClusterRoundRobin`
— all pass, no process left behind. Job object: the test binary hard-killed mid-run with three `prog.exe` alive
→ zero afterwards. Linux x86-64 (Debian container, glibc): `TestE2EHTTPClusterWorkersExitWithPrimary` and the
`TestE2ECluster*` / `TestE2EHTTPCluster*` set pass, no process left behind. macOS: not run. Before the fix, the manual repro above left both workers alive.
