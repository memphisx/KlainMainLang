# ADR-00726: `-package` on Windows — GUI-subsystem executable with icon and version resources

- **Relations**: Extends [ADR-00725](ADR-00725.md) (`klain:webview` on Windows; recorded this as a side effect), [ADR-00440](ADR-00440.md) (`-package` for macOS/Linux)
- **Date**: 2026-09-06

## Context

With the webview module working on Windows (ADR-00725), a compiled desktop app launched from Explorer still opened a console window beside its webview: the mingw link produces a console-subsystem executable, and `-package` — the flag whose purpose is a double-clickable desktop app — refused Windows ("only supported on macOS and Linux"). Windows has no bundle format to write; what makes an executable a desktop app there is the PE subsystem field, and what Explorer shows for it (tile icon, the Properties → Details tab) comes from the icon and `VERSIONINFO` resources linked into the image.

## Investigation

- Both properties are link-time. `-Wl,--subsystem,windows` sets the subsystem; a compiled `.res` on the link line adds the resources — lld's MinGW driver accepts `.res` files directly, verified with a relink of the webview smoke program: `llvm-readobj --file-headers` reports `IMAGE_SUBSYSTEM_WINDOWS_GUI`, `--coff-resources` lists the `VERSIONINFO`, and the app still runs and terminates from the page.
- Resource compilers on hand: `llvm-rc` ships in LLVM's Windows release (the `clang` this port already requires); GNU `windres` comes with MSYS2's binutils. `llvm-rc` takes `rc.exe`-style options (`/FO`, `/C 65001`); under an MSYS shell a `/FO` argument is rewritten as a path, which only matters when invoking it by hand.
- Icons: the `.ico` container accepts PNG-compressed images since Windows Vista, at most 256×256 per image, so a `.png` can be wrapped without re-encoding (ICONDIR + one ICONDIRENTRY + the PNG bytes). No converter is needed, unlike macOS's `sips`/`iconutil` path.
- Post-hoc patching of the subsystem field in the already-linked PE would avoid the second link, but adding resources post hoc means rewriting the `.rsrc` section; one mechanism (relink) covers both, and the link is ~1 s.
- Artifact naming: the default app name on Windows strips the binary's `.exe`, so `<AppName>.exe` beside `app.exe` would overwrite the console build. The per-app folder `<AppName>\<AppName>.exe` is the layout every Windows install uses and never collides; the console build stays the one to run from a terminal, since a GUI-subsystem process has no stdout.

## Decision

`-package` on Windows re-links the program as `<dir>\<AppName>\<AppName>.exe` with `--subsystem,windows` and a compiled resource script carrying resource ID 1 as the icon (when given) and a `VERSIONINFO` block (`FileDescription`/`ProductName`/`InternalName` = the app name, `OriginalFilename` = `<AppName>.exe`, `FileVersion`/`ProductVersion` = `-app-version` verbatim, the binary fields folded to `a,b,c,d`). `-app-icon` accepts `.ico` (copied) or `.png` up to 256×256 (wrapped). A resource-compiler or icon failure warns and continues with the subsystem change alone, matching the best-effort icon on macOS; a link failure is fatal. Sidecars (`app.rc`, `app.res`, `app.ico`) are written in the app folder and removed after the link. The standalone binary is untouched.

`packageApp` takes a `relink` function; `main.go` builds it from the clang argv of the link it just ran (same inputs, `-o` replaced, the packager's extras appended), so the packaged executable is the same program in every respect but subsystem and resources.

## Implementation notes

- `packaging_win32.go` (not build-tagged; the builders are pure): `writeWindowsApp`, `compileRC` (`llvm-rc`, then `windres`), `buildWindowsRC`, `versionQuad`, `rcQuote`, `makeICO`/`pngToICO`.
- `packaging.go`: the `windows` arm; Windows defaults (`AppName` without extension) and accepted icon types; the `relink` parameter.
- `main.go`: the flag help, the host gate, the relink closure.
- `packaging_test.go`: `TestVersionQuad`, `TestBuildWindowsRC`, `TestPngToICO` on every host; `TestPackageWindowsAppStructure` (a stub through a fake relink: artifact path, subsystem switch, sidecar cleanup) on Windows.
- `tests/webview_test.go`: `TestE2EPackageWindowsGUIExe` drives the CLI with `-package -app-name "Smoke App" -app-version 2.1.0 -app-icon icon.png` and checks the PE with `debug/pe`: PE32+, `IMAGE_SUBSYSTEM_WINDOWS_GUI`, a `.rsrc` section, the console binary still present, no sidecars left.

## Side effects discovered

- `-app-id` has no Windows counterpart (there is no bundle identifier); it is accepted and ignored there, as on Linux.
- No code-signing or installer step; `signtool`/MSIX are outside this flag's scope, as `codesign`/`.dmg` are on macOS.

## Verification

Windows 11 x86-64 (toolchain as in ADR-00725):

- `go test .` — the packaging unit tests pass, including the Windows structure test.
- `go test ./tests -run TestE2EPackageWindowsGUIExe` passes: the CLI produces `Smoke App\Smoke App.exe`, GUI subsystem, `.rsrc` present, console `app.exe` retained.
- By hand, on the relinked webview smoke program: `llvm-readobj --file-headers` reports `Subsystem: IMAGE_SUBSYSTEM_WINDOWS_GUI`, `--coff-resources` lists the `VERSIONINFO` resource, and the program opens its window, completes the page→native round trip and exits 0. The subsystem field is what decides whether Windows allocates a console at launch; no separate Explorer launch was staged.
