# TDD-00132: Node streams as real classes (`class X extends Readable/Writable`)

- **Status**: Stages A–B Implemented (Readable + Writable); Stage C (Duplex/Transform) deferred — [ADR-00393](../adr/ADR-00393.md)
- **Date**: 2026-08-27

## Context

Node streams are supported only in **options form** — `new Readable({ read() {
… } })`, where `read`/`write` are callbacks on an options object (a documented
deviation from Node's `this`-based `_read()`). The idiomatic Node shape,

```js
class Counter extends Readable {
  _read() { this.push(next()) }
}
```

fails at compile: *"class 'Counter' extends unknown class 'Readable'"*. The Node
`test/parallel` oracle histogram (TDD-00121) ranks `stream` the second-largest
failing module (129 files), with "unknown Readable/Writable option" and "unknown
stream method" among the concrete blockers — and `class X extends Readable` is
the shape most of that real-world/test code uses. It's the highest-value
self-contained bespoke-shape stage after `http.createServer` (TDD-00131 Stage 1)
and EventEmitter multi-arg (ADR-00392).

## Design

### The reuse model: mirror `extends EventEmitter`

The mechanism already exists for a sibling case. `class X extends EventEmitter<T>`
works via a **synthetic root**: EventEmitter is never a real registered class
(`emit_classes.go` Pass 0); a class that extends it gets `ClassInfo.HasEventEmitter`
+ a hidden listener-map field + method dispatch for `on`/`emit`/… And Node streams
already *ride the EventEmitter listener runtime* (their `on('data')`/`on('end')`
surface is the same list machinery) plus the `rstream`/`wstream` state
(`runtime_node_stream.go`).

So `class X extends Readable/Writable/Duplex/Transform` follows the same pattern:

1. **Synthetic stream roots.** `Readable`/`Writable`/`Duplex`/`Transform` become
   synthetic base classes (like EventEmitter) — never real registered classes.
   A class extending one gets a `ClassInfo.HasNodeReadable`/`HasNodeWritable`
   flag (Duplex/Transform set both) and a hidden **stream-state field** (the
   same `rstream`/`wstream` handle the options-form `new Readable(...)` builds),
   alongside the EventEmitter listener field it already implies (a stream *is* an
   EventEmitter, so `HasEventEmitter` is set too — the event surface reuses that
   path unchanged).

2. **`_read()` / `_write(chunk, enc, cb)` override dispatch — the one new
   mechanism.** In options form the runtime's "pull more data" trigger calls the
   options object's `read` callback; in class form it must call the subclass's
   **`_read`/`_write` method**. Since these are ordinary user class methods,
   they compile to real functions; the stream runtime is handed a pointer to the
   instance's `_read`/`_write` (resolved through the class's method table) as the
   pull/sink callback — the same slot the options-form callback fills, only
   sourced from the method table instead of the options literal.

3. **`this.push(chunk)` / `this.on(event, …)` / `this.emit(…)` inside a method.**
   `this` is a `HasNodeReadable`/`HasNodeWritable` (and `HasEventEmitter`)
   instance, so `this.push`/`this.on`/`this.emit`/`this.end` dispatch through the
   existing `emitNodeStreamCall` / EventEmitter method paths against the hidden
   stream-state / listener fields — no new runtime.

### What stays / what's new

- **Options form is unchanged** — `new Readable({ read() {…} })` keeps working;
  the class form is purely additive, sharing the same runtime.
- **New:** the `extends`-a-stream-root class registration (flags + hidden field),
  and routing the runtime pull/sink to the subclass `_read`/`_write` method.

### Staging

- **Stage A — `Readable`.** `class X extends Readable`, `_read()` override,
  `this.push(chunk)` / `this.push(null)` (end), and the `on('data')`/`on('end')`
  event surface. The most common form and the biggest slice of the histogram.
- **Stage B — `Writable`.** `class X extends Writable`, `_write(chunk, enc, cb)`
  override, `this.end()`; `.write()` from outside.
- **Stage C — `Duplex` / `Transform`.** Both flags on one instance; `Transform`'s
  `_transform(chunk, enc, cb)` + `this.push`. `.pipe` across class-form streams
  reuses the existing pipe runtime.
- **Constructor `super(options)`** — a subclass `constructor` calling
  `super({ highWaterMark })` threads options into the stream-state init (the
  same options the options-form parses), decided per stage.

### Divergences to keep bounded (V1)

- String-chunk / eager-read limitations inherited from the current Node-stream
  runtime (STREAMS.md) carry over — this stage is about the **class shape**, not
  changing the chunk model (binary `Uint8Array` streaming stays a separate
  follow-on).
- Node's full `_read(size)` backpressure/HWM contract is approximated by the
  existing runtime's HWM handling; `_writev`, `cork`/`uncork`, `_final`,
  `_destroy` are out of V1 scope.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `extends EventEmitter` synthetic-root class model | Built | `emit_classes.go` — the exact pattern to mirror for stream roots |
| Options-form Node `Readable`/`Writable` runtime (`rstream`/`wstream`, push/write/end/`on`) | Built | `emit_node_stream.go` / `runtime_node_stream.go` — reused as the class-form's state + methods |
| EventEmitter listener runtime (a stream's event surface) | Built | Reused via `HasEventEmitter` on the stream class |
| Class method table / `this`-method dispatch | Built | [TDD-00009](TDD-00009.md) — how `_read`/`_write`/`this.push` resolve |
| Routing the runtime pull/sink to a class method pointer | Missing | The one new mechanism (Stage A) |

## Open questions

- How the runtime obtains the instance's `_read`/`_write` method pointer — a
  fixed method-table slot resolved at construction, versus storing the bound
  method into the stream-state field the options-form callback already uses.
- Whether `super(options)` in a subclass constructor is required in V1 or a
  no-arg `super()` with defaults suffices for Stage A.
- Interaction with the existing WHATWG `ReadableStream` class (distinct from Node
  `Readable`) — they must stay separate synthetic roots, not conflated.
- Whether Duplex/Transform need a combined single stream-state or two
  (read-side + write-side) handles.
