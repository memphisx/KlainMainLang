# TDD-00170: Gamepad API — native game-controller input over the W3C shape

- **Status**: Not Started
- **Date**: 2026-09-03

## Context

The [W3C Gamepad API](https://www.w3.org/TR/gamepad/) (`navigator.getGamepads()`,
the `Gamepad`/`GamepadButton` interfaces, `gamepadconnected`/`gamepaddisconnected`
events) is currently listed **out of scope** as "pure browser-only" alongside
DOM/Canvas/WebGL. That framing is being revisited: unlike DOM/Canvas (which need
a document/renderer), the Gamepad API is a thin, **polling-based** read over OS
controller state — `getGamepads()` returns a snapshot of button/axis values —
and maps cleanly onto native OS input with no browser assumptions. It fits this
project's established pattern of implementing a web API's *shape* natively (URL,
fetch, EventTarget, WebSocket, klain:webview) and its interactive-native-app
direction (klain:tui, klain:webview). Use cases: controller-driven TUIs, robotics
/ control CLIs, interactive native tools.

Crucially, the OS-input plumbing is **not** hand-rolled here: it hooks the mature
cross-platform **SDL2** controller layer (`SDL_GameController`), so the whole
feature reduces to mapping SDL's abstract layout onto the W3C `Gamepad` shape —
SDL already provides the standard mapping DB, hotplug, and rumble across
Linux/macOS/Windows.

## Design

### Surface — the faithful W3C shape

Expose the standard API, backed natively:

- `navigator.getGamepads(): (Gamepad | null)[]` — a snapshot array (index =
  controller slot; `null` for an empty slot).
- `Gamepad` (read-only): `id: string`, `index: number`, `connected: boolean`,
  `mapping: string` (`"standard"` when the layout matches the W3C standard
  mapping, else `""`), `timestamp: number` (a `performance.now()`-style stamp of
  the last state read), `buttons: GamepadButton[]`, `axes: number[]`.
- `GamepadButton` (read-only): `pressed: boolean`, `touched: boolean`,
  `value: number` (0..1, analog for triggers).
- Events `gamepadconnected` / `gamepaddisconnected` carrying a `GamepadEvent`
  with `.gamepad`, delivered through the existing EventTarget machinery.

`navigator` becomes a minimal host object for `getGamepads` (the faithful entry
point); the events attach via `addEventListener` on the same global host. This is
the standard shape, so a program written against a browser's Gamepad API runs
unchanged — the native-reinterpretation posture, not a `klain:` bespoke name.
(**Open question below**: `navigator` global vs a `klain:gamepad` module for the
non-browser host — the standard uses `navigator`, which argues for it.)

### Backend — a single cross-platform library (SDL2), not hand-rolled per-OS

Rather than reinvent platform input (`/dev/input/js*`, `GameController.framework`)
and a controller mapping database, hook **SDL2's `SDL_GameController`** — the de
facto cross-platform (Linux/macOS/Windows) controller layer. This makes the whole
feature *a mapping exercise*, because SDL already solves everything hard:

- **Standard mapping for free.** `SDL_GameController`'s abstract layout (A/B/X/Y,
  L/R shoulders + triggers, dpad, two sticks) is precisely the model the W3C
  "standard mapping" is built on, and SDL ships/loads a community
  `gamecontrollerdb.txt` recognizing thousands of controllers. So a
  DB-recognized pad reports `mapping: "standard"` with no bespoke tables.
- **No window required.** Initialize only `SDL_INIT_GAMECONTROLLER` (+
  `SDL_INIT_JOYSTICK`); no video/audio subsystem, no Cocoa app.
- **State poll = `getGamepads()`.** `SDL_GameControllerGetButton(gc, …)` for the
  15 standard buttons, `SDL_GameControllerGetAxis(gc, …)` for the two triggers
  (→ `buttons[6/7].value`, normalized 0..1) and the four stick axes (→ `axes[]`,
  normalized -1..1); `SDL_GameControllerName` → `Gamepad.id`.
- **Hotplug events.** `SDL_PumpEvents` + `SDL_PollEvent` on the event-loop tick
  yields `SDL_CONTROLLERDEVICEADDED`/`REMOVED` → `gamepadconnected`/`disconnected`.
- **Haptics.** `SDL_GameControllerRumble` → `GamepadHapticActuator.playEffect`.

The only KML-side work is the **enum→index map** (SDL button/axis enum → the W3C
standard index) and marshaling into the `Gamepad`/`GamepadButton` value objects.

**Linking.** `-lSDL2`, emitted only when a program uses the gamepad API (a
`usedGamepad` guard), exactly like `-lcurl`/`bdw-gc` today — a per-machine
dependency (`brew install sdl2` / `apt install libsdl2-dev`), documented in the
README Requirements. When SDL is absent at build time the link fails (same story
as `-mm=gc` without libgc); a *runtime* absence of any controller is not an error
— `getGamepads()` returns an all-`null` array.

### Model — polling, not per-button events

`getGamepads()` is a **snapshot read** (the W3C model: the consumer polls each
frame). There is no per-button DOM event, so no rAF loop is required — a program
polls in its own loop (a `klain:tui` render tick, a `setInterval`, a game loop).
Only connect/disconnect are events, driven by the OS device-add/-remove signal
folded into the event loop. This keeps the runtime cost zero until
`getGamepads()` is first called (the `usedGamepad` guard), consistent with the
fast-path philosophy.

### Standard mapping

The W3C "standard mapping" fixes button/axis indices (face buttons 0–3, shoulders
4–7, dpad 12–15, sticks on axes 0–3, …). Because these come straight from SDL's
own `SDL_CONTROLLER_BUTTON_*`/`AXIS_*` enums via a fixed index table, any
SDL-DB-recognized controller reports `mapping: "standard"` directly; a controller
SDL doesn't recognize surfaces as a raw joystick with `mapping: ""` (faithful —
the spec allows the empty mapping).

## Staging (ordering, not dropping)

With SDL2 the per-OS split disappears — one backend covers Linux/macOS/Windows:

1. **`navigator.getGamepads()` + `Gamepad`/`GamepadButton`** over SDL
   (`SDL_INIT_GAMECONTROLLER`, poll button/axis state, `id`, `mapping:"standard"`,
   `timestamp`). The enum→W3C-index map + value-object marshaling.
2. **`gamepadconnected`/`gamepaddisconnected`** via `SDL_PollEvent`
   (`CONTROLLERDEVICEADDED`/`REMOVED`) pumped on the event-loop tick, through
   EventTarget.
3. **Haptics** — `GamepadHapticActuator.playEffect` → `SDL_GameControllerRumble`.

## Decided

- **Host = `navigator.getGamepads()`** (W3C-faithful): a minimal `navigator`
  global gains `getGamepads()`, and `gamepadconnected`/`disconnected` attach via
  the global `addEventListener`. Browser code ports unchanged.
- **Backend = SDL2 `SDL_GameController`**, one cross-platform library, so there is
  no "which OS first" — Stage 1 works on both the M4 Mac and the Ubuntu box.

## Open questions

- **SDL2 vs SDL3.** SDL2 (`SDL_GameController`) is the most widely-installed today;
  SDL3 renames the API to `SDL_Gamepad` and is the future. Target SDL2 first
  (ubiquitous), keep the KML surface identical so an SDL3 swap is internal.
- **Event-loop pump cadence.** `SDL_PumpEvents` needs to run often enough that
  hotplug feels responsive without busy-spinning — confirm the existing tick
  (webview's ~16 ms, or the timer/loop cadence) is the right hook and that a
  program *only* polling `getGamepads()` (no event listeners) still pumps.
- **CI/headless testing.** CI has no controller; SDL2 may not be installed on the
  test lane. Gate the E2E behind SDL presence (skip-if-absent, like `-mm=gc`
  tests skip without libgc), and cover the marshaling with SDL's virtual-joystick
  (`SDL_JoystickAttachVirtual`) or a fake so a real pad isn't required.
