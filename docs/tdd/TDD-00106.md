# TDD-00106: Spread in call arguments (`f(...arr)`)

- **Status**: Implemented (V1: ADR-00335; V2: ADR-00337)
- **Date**: 2026-08-24

## Context

`f(...arr)` fails to parse today (`unexpected token ... in expression`) — the
one core-language gap flagged under [What Is NOT Implemented → Medium
complexity]. It was deferred pending a design because "spreading a runtime-length
array into a statically-typed rest slot — possibly combined with other
positional arguments, multiple spreads, or a non-rest fixed-arity target — is
real design space, not a mechanical fix." This document scopes what V1 supports.

## Design

### What already fits

- The `...` (`ELLIPSIS`) token is lexed; the `SpreadElement` AST node exists
  (used in array/object literals). The only parser gap is that `parseArgList`
  (parser_literals.go) never checks for `ELLIPSIS` before `parseAssignment`.
- **A rest parameter's ABI is `(ptr, i64 len)` — byte-identical to how an array
  variable is passed as an argument.** A rest param `...xs: T[]` is received as
  two params `(ptr, i64)`; an array variable argument `f(arr)` already lowers to
  `(ptr, i64)` (via `resolveArrayForHOF`). So forwarding `arr`'s pointer+length
  straight into a rest slot is a near-exact match — no per-element work, no
  concatenation, no runtime arity anything.
- The rest-packing branch in `emitCallToFuncSig` today mallocs a buffer and
  stores N compile-time-known trailing args, then passes `(ptr, i64)`. The
  spread case simply substitutes "forward this array's `(ptr,len)`" for "pack N
  scalars".

### The hard cases (why they're out of V1)

Function arity here is **static**. `emitCallToFuncSig` walks one AST expression
per parameter slot, emitting one LLVM arg each. A runtime-length array cannot be
split into a compile-time-fixed number of positional slots:

- `f(a, b, c)` (fixed arity, no rest) with `f(...arr)` — would need per-slot
  indexed loads plus a runtime length assertion; ill-defined against static
  arity. **Reject.**
- `f(...a, ...b)` / `f(...arr, y)` / `f(x, ...arr, z)` (multiple spreads, or a
  spread that isn't the last thing feeding the rest slot) — needs runtime
  concatenation into one buffer. The primitive exists (`emitSpreadArrayLitData`,
  used by array-literal spread) but is not wired to calls. **V2.**
- `console.log(...args)`, `Math.max(...arr)`, and other variadic builtins fold a
  *static* arg list one expression at a time; each would need bespoke
  array-input handling. **V2.**

### V1 decision

Support a spread argument **only as the sole filler of a callee's rest
parameter**, optionally preceded by ordinary fixed arguments:

- `f(...arr)` — `arr` fills the rest slot.
- `f(a, b, ...arr)` — `a`/`b` fill the fixed params, `arr` fills the rest.
- Element type of `arr` must match the rest element type.

Implementation: forward `arr`'s `(ptr, len)` (via `resolveArrayForHOF`) into the
rest slot instead of malloc-packing individual trailing args. This applies to
both the named-function path (`emitCallToFuncSig`) and the closure-call path
(the mirrored logic in emit_func.go).

Everything else with a spread argument is a **clean compile error** naming the
V1 limitation (so `console.log(...a)`, `f(...a, ...b)`, `f(...arr)` into a
fixed-arity `f`, and a leading/middle spread all fail with a clear message
rather than the generic parser error or a miscompile). The existing "spread
element must be used inside an array literal" guard (emit_exprs.go) stays for
spread in genuinely-unsupported expression positions.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `ELLIPSIS` token + `SpreadElement` node | Built | lexer/token.go, ast/nodes.go |
| Rest-param support + `(ptr,i64)` ABI | Built | emitter.go `buildFunctionSig`, emit_func.go param decomposition |
| Array → `(ptr,len,elemTy)` normalizer | Built | `resolveArrayForHOF` (emit_arrays_core.go); already used to hand a runtime array's buffer to `child_process.spawn` argv |
| Rest-packing branch in call emit | Built | `emitCallToFuncSig` (emit_call.go:1300) + closure mirror (emit_func.go) |
| Runtime array concat (for V2 multi-spread) | Built but unwired to calls | `emitSpreadArrayLitData` (emit_arrays_core.go) |

## Open questions

- **Element-type check strictness.** `arr`'s element type vs the rest element
  type — require an exact match (`elemTy.IR ==`) or allow a widening coerce? V1
  leans exact-match with a clear error, matching how the fixed-arg path already
  coerces per slot.
- **A rest param that also receives individual args plus a spread**
  (`f(a, ...arr)` where the signature is `f(...rest)` so `a` and `arr` both feed
  the rest) — V1 treats a spread as the *sole* rest filler, so `f(a, ...arr)`
  into a pure-rest `f(...rest)` is a mixed fill → V2. Only fixed-params-then-one-
  spread is V1.
