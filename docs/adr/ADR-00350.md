# ADR-00350: Fix `-mm=gc` collection crash on class-instance churn (frozen-set is thread-local, unscanned by Boehm)

- **Relations**: Extends [ADR-00055](ADR-00055.md) (`Object.freeze` frozen set); relates to [ADR-00071](ADR-00071.md) (GC allocator shim)
- **Date**: 2026-08-25

## Context

Under `-mm=gc`, a program that allocates class instances in a loop segfaulted
once Boehm's first collection ran (~50,000 allocations); churning strings,
arrays, or numbers collected cleanly. Surfaced while verifying the `-mm=gc` weak
path ([ADR-00349](ADR-00349.md)) and reproduced with zero weak/collection code,
on the clean tree, on **both** Mac (arm64) and Linux (Docker, arm64).

## Investigation

An lldb backtrace put the fault in the class constructor — specifically a load
inside the *frozen-set check* that every object-field write performs
(`Object.freeze` enforcement, [ADR-00055](ADR-00055.md)): at `-O2` the inlined
`__kml_map_num_has` scan loaded from a NULL keys-array pointer. This check is the
one thing class-instance construction does on every write that string/array/
number churn does not — which is why only class churn crashed.

The frozen set (`runtime_collections.go`) is a per-thread global declared
`internal thread_local global ptr null`. Its *only* live reference to the
GC-allocated map header is that thread-local pointer. **Boehm does not scan
thread-local storage as a GC root** (it scans the static data segment and
registered thread stacks). So under `-mm=gc` the map header — and transitively
its keys/vals arrays — became unreachable to the collector and was reclaimed
while still in use; the next field-write check dereferenced freed/NULL storage.

Thread-local is deliberate (a per-thread frozen set avoids a cross-thread race on
the hot per-write check; plain objects are never shared across workers), so the
fix had to preserve it, not drop it.

## Decision

In `-mm=gc`, allocate the frozen-set map **header** with
`GC_malloc_uncollectable` instead of plain `malloc` — never collected, but still
*scanned*. Because the header is scanned, its `keys`/`vals` pointers are followed
during marking, so the ordinary `GC_malloc`'d arrays (including the larger arrays
`realloc` installs as the set grows) stay reachable through the header. The
thread-local access pattern is unchanged; manual mode is unchanged (plain
`__kml_map_num_create`).

`ensureFrozenSet` now inlines the header construction in gc mode (same
`{size, cap, keys, vals}` layout as `__kml_map_num_create`) so only the header
allocation differs; every other frozen-set operation (`has`/`set`) is untouched.

## Side effects discovered

None new. The related **Linux `-mm=gc` + `Worker` round-trip segfault**
(`TestE2EWorkerGCModeRoundTrip`) is a separate open bug (per-thread Boehm
thread-registration on the fiber stack), tracked on
[CONCURRENCY-WORKERS.md](../status/CONCURRENCY-WORKERS.md); it is not this crash.

## Verification

- `tests/memory_gc_test.go`: `TestE2EGCModeClassChurn` churns 200,000 class
  instances under `-mm=gc` and checks the sum — was a reliable segfault, now
  passes. Peak RSS stays ~3 MB for 500k allocations (collections are reclaiming,
  not leaking).
- The full `-mm=gc` test group and the weak-collection tests still pass.
- Machine: verified on Mac (arm64), Homebrew `bdw-gc`. Cross-platform crash, so
  the fix applies to Linux too (re-verify via Docker when convenient).
