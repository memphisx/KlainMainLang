# ADR-00955: Self-referential class field (`f = Object.freeze(this)`) + frozen-write TypeError

- **Relations**: `Extends ADR-00946, ADR-00949` (the class/interface self-reference machinery)
- **Date**: 2026-09-15

## Context

Test262 `language/statements/class/elements/class-field-on-frozen-objects.js`
— the last invalid-IR survivor in the `language/*` census — failed at compile
time:

```ts
class Test {
  f = Object.freeze(this);
  g = "Test262";
}
assert.throws(TypeError, function() { new Test(); });
```

```
error: '%t15' defined with type 'ptr' but expected 'i64'
  store i64 %t15, ptr %t14, align 8
```

Two distinct problems are tangled in one test:

1. **Self-referential field type.** `f = Object.freeze(this)` has the type of
   `this` — the class instance itself. Field types are collected before any
   constructor scope exists, so `Object.freeze`'s argument-type passthrough
   (`inferExprType`) resolved `this` via `lookup("this")`, missed, and defaulted
   the field to the numeric `i64`. The instance pointer was then stored into that
   `i64` slot — invalid IR.

2. **Frozen-write-during-construction semantics.** After `f = Object.freeze(this)`
   freezes the instance, the second field initializer `g = "Test262"` writes to a
   now-frozen object, which must throw a **TypeError** mid-construction.

## Investigation

- The `this`-type miss is at the unannotated-field inference in `registerClasses`
  (`emit_classes.go`, `fty = e.inferExprType(f.Initializer)`).
  `inferExprType(ThisExpression)` (`emit_exprs_types.go:1156`) reads
  `lookup("this")`, which is unbound this early. `Object.freeze`/`seal`/`assign`
  return `inferExprType(arg[0])` (`emit_exprs_types.go:2646`), so the whole
  expression inherited the `i64` default.
- The class self-reference machinery already exists: `registerClassNamePlaceholders`
  seeds a nominal placeholder, and `canonicalizeClassTy` re-resolves a class-typed
  field's stale by-value snapshot through the live registry on demand at each
  drilling access (ADR-00946). It only needed `this` bound to that placeholder
  during field inference.
- The frozen check (`emitFrozenCheck`, `emit_objects.go:1501`) already fires on
  the field-init write and already produces the correct V8 message — but through
  `emitInternalThrow`, which builds a plain `Error` (kind tag 0, name "Error"),
  so `instanceof TypeError` returned false. Real strict-mode JS throws a
  `TypeError`.

## Decision

1. **Bind `this` during instance-field inference.** In `registerClasses`, wrap
   the unannotated-field `inferExprType(f.Initializer)` in a scope binding `this`
   to `ClassType(cd.Name, …)` — the same nominal name-placeholder the class self-
   reference path uses. The field keeps a `ClassName`-tagged class type (a `ptr`),
   whose fields `canonicalizeClassTy` re-resolves on demand; the store is now
   `ptr`→`ptr`. Only instance fields are wrapped — a static field's `this` is the
   class object, a different binding, left untouched.

2. **Frozen write throws TypeError.** Add `emitInternalThrowKind(kind, msg)`
   (a kind-parameterized sibling of `emitInternalThrow`) and use it from
   `emitFrozenCheck` with kind `"TypeError"`. The error now carries the TypeError
   kind tag and name, so `instanceof TypeError` narrows it.

## Implementation notes

- `emit_classes.go`: `pushScope`/`define("this", …)`/`inferExprType`/`popScope`
  around the instance-field initializer inference only.
- `emit_exceptions.go`: `emitInternalThrowKind` reuses `buildErrorObj` with
  `errorKindIDs[kind]`.
- `emit_objects.go`: `emitFrozenCheck` calls `emitInternalThrowKind("TypeError", …)`.
- The TypeError upgrade is general — every frozen-object write (plain objects,
  `Object.assign` onto a frozen target, this field-init case) now throws a
  TypeError, matching JS, not just the class-field path.

## Side effects discovered

- `(e as Error).constructor.name` on a caught value still hits the "dynamic
  property access on a statically-typed value is not supported" limitation — a
  separate, pre-existing gap unrelated to this fix (the test itself uses
  `assert.throws(TypeError, …)`, which the `instanceof` narrowing satisfies).

## Verification

- Repro compiles to valid IR (`clang -x ir` clean) and, run under the harness,
  the Test262 file now **passes** (dropped from the faillist, not merely
  IR-valid). `language/statements` is 0 CLANG_ERROR.
- New E2E test `TestE2EClassFieldFreezeThisIsTypeError`.
- macOS arm64 / M4.
