# ADR-01620: Array.prototype.sort is V8's TimSort; strings compare by UTF-16 code units

- **Relations**: Supersedes the sort mechanics of ADR-00152, Extends ADR-00546, ADR-00681
- **Date**: 2026-10-14

## Context

A WPT observer test failed on the order of two performance entries with the
same start time. Following it found a cluster of sort and comparison
differences from Node.

## Investigation

- Sorting called the C library's `qsort`, which is not stable on Windows
  (UCRT) or macOS; glibc's merges, so Linux hid it. ECMA-262 requires a
  stable sort since ES2019.
- For a comparator that is not consistent (`(a, b) => a < b ? -1 : 1`, common
  in real code) the result depends on which pairs are compared in which
  order; Node's is V8's TimSort (third_party/v8/builtins/array-sort.tq, a
  port of CPython's listsort).
- Each element kind had one trampoline reading the comparator's result in one
  type: an object comparator returning integer literals had its i64 read as
  a double (a garbage order); a boolean or void comparator was misread too.
- `undefined` elements were passed to the comparator and sorted among the
  rest; SortIndexedProperties sets them aside and appends them. The default
  string sort called `strcmp` on a three-state array's null sentinel and on
  `undefined` (a null pointer: a crash).
- An object, class or `Date` array's default sort compared pointers as
  integers; SortCompare compares `ToString` of each side.
- A nested array (`number[][]`) was rejected outright.
- Strings compared by UTF-8 bytes, which is code-point order; JavaScript
  compares UTF-16 code units, which differ only in placing U+E000..U+FFFF
  after the supplementary characters (`"￿" < "\u{10000}"` is false).

## Decision

- **`__kml_stable_sort`** (`coresrc/core.c`) is V8's TimSort: binary
  insertion to V8's minimum run, run detection (a descending run reversed),
  the run-stack invariants, galloping merges (`MergeLow`/`MergeHigh`, minimum
  gallop 7), over a work copy written back when sorted, so a throwing
  comparator leaves the array unchanged.
- **`__kml_sort_any`** and **`__kml_sort_ptr`** set an `any[]`'s `undefined`
  boxes and a pointer array's null pointers aside, then sort the rest.
- **The comparator's result** is read by its own return type, which the
  program stores in `__kml_sort_res` beside `__kml_sort_clos`: i64, i32, i16,
  i8, double, float, boolean, boxed `any`, void. The `any` trampoline moves
  from IR text to C; an array-of-arrays trampoline passes each header with
  its length, and the nested-array rejection goes.
- **A pointer array's default sort** (objects, classes, `Date`, nested
  arrays) uses a generated comparator converting each side once with a
  template literal, so a `toString()` decides and is called as often as in
  Node.
- **`__kml_str_cmp`** compares in UTF-16 order; the `any` relational path, the
  default string sort (`__kml_cmp_str`, now in `strheader.c` with the null
  sentinel `__kml_sort_nullref`) and the `any[]` default sort use it.

## Implementation notes

`codegen/llvm/coresrc/core.c`, `collectionssrc/collections.c`,
`stringsrc/strheader.c`, `emit_arrays_sort.go`, `runtime_collections.go`,
`runtime_core.go`, `emit_anyops.go`, `emitter.go`; tests in
`tests/sort_order_test.go` (`TestE2ESortArrayOfArrays` among them);
`TestE2ENestedArrayHOFRejectedCleanly` no longer lists `m.sort()` on a
`number[][]`, which now sorts.

## Side effects discovered

None.

## Verification

Windows 11 (this machine): `tests/sort_order_test.go` — including a hash of
the results and comparator call counts of a consistent, two inconsistent and
a random comparator over arrays of 0 to 3000 elements, identical to Node 24's —
and nested-array, `undefined`/`null`, object, `Date` and string-order cases
compared with Node 24. Linux (Docker, `klain-ci`): the same tests.
