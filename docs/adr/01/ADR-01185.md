# ADR-01185: The TCP handles run on Windows; the code-generated `net`, `tls` and `klain:ws` server are deleted

- **Relations**: `Implements TDD-00231`, `Extends ADR-01170`
- **Date**: 2026-09-28

## Context

The TCP handles under the TypeScript `net`/`tls`/`http` (ADR-01170) were
POSIX-only, so a Windows program was redirected to the earlier code-generated
`net`, `tls` and `klain:ws`, and every companion module (`fs` streams and
callback operations, `http`) was switched off there. The Windows CI lane
showed the cost: about 70 failures, from "fs has no method
'createReadStream'" to `http.Server` being unknown.

## Investigation

- The Windows I/O layer (`win32io.c`) already provides the POSIX surface the
  handles use — `socket`/`bind`/`listen`/`accept`/`connect`/`read`/`write`/
  `close`/`fcntl`/`poll` on small-integer descriptors, taking Linux constants
  and setting Linux errno values — and `kml_posix_compat.h` declares it.
- Three differences matter: a sockaddr carries Winsock's `AF_INET6` (23), not
  Linux's 10; `getaddrinfo` fails with Winsock codes (11001 …); and the layer
  *consumes* a readiness it reports, so the per-handle `poll()` the dispatch
  ran after the reactor's `select()` would re-arm what `select()` had just
  taken.
- With the redirect gone, nothing reaches the code-generated `net`/`tls`
  entry points; the `klain:ws` server was already unreachable (its resolver
  flag lost its only setter in the restructure).

## Decision

- `klainpool.c` builds its TCP handles and `dns.lookup` on Windows over the
  Windows I/O layer: the fs operations and the handles include
  `kml_posix_compat.h` instead of `<unistd.h>`/`<fcntl.h>`, `O_*` flags are
  the Linux values that layer's `open` takes, `AF_INET6` is 23 in this unit,
  and the reactor's descriptor sets are the IR's bitmaps.
- On Windows the dispatch tries each operation (an accept, read or write that
  cannot proceed answers EAGAIN) and asks only whether a connect is still in
  flight (`__kml_win_connect_pending`). A flush reports whether it made
  progress, so a full send buffer never counts as work done.
- The resolver no longer redirects Windows programs, and companion modules
  are included on every target.
- Deleted: `emit_ws_server.go`, `runtime_tls.go`, the `net`/`tls` module and
  server emitters, the `klain:ws` server path of the HTTP dispatcher and its
  handler globals, `NetServerType`/`IsNetServer`, `IsWebSocketServer`,
  `WSConnectionType`, `Program.UsesKlainWS`, the dead IR functions of
  `runtime_net.go` (server registration, listen, connect, `isIP`), and the
  virtual-module rows of `net`, `tls` and `klain:ws`. The net socket the HTTP
  `'upgrade'`/`'connection'`/`'clientError'` events hand out keeps its
  runtime. The remaining unreachable functions the dead-code analysis found
  across the compiler went too.

## Implementation notes

`codegen/llvm/threadpoolsrc/klainpool.c`, `codegen/llvm/win32src/win32io.c`
(`__kml_win_connect_pending`), `resolver/resolver.go`,
`resolver/virtual_modules.go`, `resolver/rename.go`, `ast/nodes.go`,
`checker/check.go`; `codegen/llvm/emit_call.go`, `emit_exprs_types.go`,
`emit_exprs_vardecl.go`, `emit_classes.go`, `emit_http.go`,
`emit_websocket.go`, `emit_net.go`, `emit_tls.go`, `runtime_net.go`,
`runtime_http.go`, `types.go`, `emitter.go`.

## Side effects discovered

None beyond the Windows test expectations of ADR-01186.

## Verification

- Mac (Apple Silicon): the `net`, `tls`, `websocket`, `http_upgrade`,
  `http`, `streams`, `dgram`, fs-stream and node-stream test files; the full
  `tests/` suite.
- Windows: `klainpool.c` (with the HTTP parser) and `win32io.c` compile
  cleanly for `x86_64-w64-mingw32` (Debian's mingw-w64, in Docker on the
  Mac). Not yet run on Windows; the Windows CI lane is the first run.
