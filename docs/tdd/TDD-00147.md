# TDD-00147: Android target — NDK backend port + WebView apps via a thin Java shim

- **Status**: Not Started
- **Date**: 2026-08-29

## Context

Android is Linux-kernel but **not** Linux-userland: libc is **bionic**, not
glibc, and that single fact carries most of this TDD's difficulty. Unlike
Sailfish ([TDD-00146](TDD-00146.md)), where the existing runtime is expected
to carry over intact, the Android backend port hits real gaps:

- **No ucontext.** Bionic declares the types but implements none of
  `makecontext`/`swapcontext`/`getcontext`/`setcontext` — and the whole
  concurrency runtime (HTTP fibers, task fibers, the scheduler) sits on them.
  This is the port's hard core.
- **No system libcurl / pcre2 / bdw-gc.** Android has no stable public C
  library surface beyond bionic + a short NDK list (`liblog`, `libz`,
  `libandroid`, `libmediandk`, …). Everything else must be vendored and
  compiled into the binary/app.
- **Apps are not processes started by `main()`.** The deliverable shape
  differs by tier: a real `main()` binary is only directly useful for
  `adb`/Termux/rooted contexts; an *app* is a zygote-forked ART process where
  native code lives in a `.so` and the UI thread belongs to Java.
- **The UI story, as anticipated, is the easy half.** `android.webkit.WebView`
  is a first-class, evergreen (Play-updated, Chromium) component with
  `evaluateJavascript(script, callback)`, `addJavascriptInterface` /
  `WebViewCompat.addWebMessageListener` for JS→native, and
  `WebViewAssetLoader` for serving bundled content — a richer bridge than
  either WebKitGTK or Sailfish's embedlite offers. The catch is that it must
  be created on the Java UI thread with a `Context`, so a `NativeActivity`
  cannot host it: a thin Java/Kotlin shim `Activity` is unavoidable, with our
  compiled code entered through JNI as a shared library.

Toolchain, by contrast, is a non-problem: the NDK *is* clang/lld with
per-API-level sysroots (`--target aarch64-linux-android<minapi>`), so Stage 1
of TDD-00146's `--target`/`--sysroot` flag covers Android's compile step with
a different preset. The two TDDs deliberately share that flag.

One hard OS rule shapes the CLI tier: since API 29, untrusted apps cannot
`exec()` files from their writable data directory (W^X). The sanctioned
workaround is shipping executables as fake JNI libs (`lib<name>.so` in
`jniLibs/<abi>/`, executed from `nativeLibraryDir`) — Termux's own approach.
This matters for any app that wants to bundle and run compiled tools, and for
`child_process`/`cluster` semantics inside apps.

## Design

### Tier model

Three tiers, in dependency order. Each is independently shippable.

1. **Tier A — standalone binaries** (adb shell, Termux, root, CI emulators):
   the backend port proper. `klainmain --target android-aarch64 tool.ts` →
   a static-ish ELF that runs under `adb push && adb shell`.
2. **Tier B — native library form**: the same program compiled as
   `lib<app>.so` with `main()` replaced by an exported JNI entry
   (`Java_..._nativeMain`), runnable inside an ART process. Pure packaging of
   Tier A's runtime; no new semantics.
3. **Tier C — WebView apps**: a generated thin Kotlin/Java shim Activity +
   Tier B library + APK packaging; `klain:webview` gets an `android` backend.

### Tier A — the backend port (the hard part)

**Fibers without ucontext.** Options:

1. **Vendor libucontext** (ISC-licensed, pure-asm context switch, supports
   aarch64/x86_64 on bare ABIs — exists precisely because musl/bionic dropped
   ucontext). Smallest diff: the runtime keeps its `ucontext.h` API verbatim.
2. **Own minimal context switch**: ~30 instructions of aarch64/x86_64 asm
   (save/restore callee-saved regs + SP + PC) behind the existing fiber API.
   No third-party code, but hand-rolled asm per arch, and it must coexist
   with ASan/unwinding.
3. **Thread-backed fibers**: real pthreads + a baton. Semantically safest,
   heaviest (the fiber counts assume cheap stacks), and it would silently
   change the cooperative "one fiber at a time" guarantees. Rejected except
   as a debugging fallback.

Recommended: **1**, falling back to **2** only if libucontext misbehaves on
bionic. Either way the existing configurable stack sizes carry over; bionic's
default guard pages still apply to mmap'd stacks.

**Vendored dependencies.** libcurl (built against BoringSSL or mbedTLS —
Android has no public system TLS C API), pcre2, and bdw-gc (has Android
support upstream) become static archives compiled per-target and linked only
when used — the same conditional-linking convention, with a `deps/`
cross-build recipe (CMake/autotools invoked with the NDK toolchain file)
cached in CI. Alternative for HTTP only: Google's Cronet has a stable C API
(`cronet.h`) and ships with the OS via Play — but it is callback/executor
shaped, a poor match for the synchronous-under-the-hood curl model; keep
curl-static as the primary route and note Cronet as a possible later
`-http-backend=` inhabitant.

**Bionic audit.** Known deltas to sweep for in the embedded-C runtime:
`fork()` works but is hostile inside ART processes (Tier B/C: `spawn` a
`nativeLibraryDir` executable instead of self-`fork`; Tier A binaries keep
full `fork`/`cluster` semantics); `NODE_CHANNEL_FD`-style FD inheritance
works in Tier A, needs the exec-from-jniLibs shape in apps;
DNS goes through bionic's resolver (fine via curl);
`getpwnam`/locale/iconv surfaces are thin (we don't use them);
`/proc` access is progressively restricted (affects nothing we ship today);
signals + `select()` + socketpair + eventfd all standard.

**Verification tier**: the Android Emulator (x86_64 and aarch64 system
images) under `adb shell` in CI, plus qemu-user for quick smoke runs. Same
open question as Sailfish about how the E2E suite drives a remote runner —
solve it once, share it.

### Tier B — library entry

- `-shared`-style build mode: emit the same program with `main()` wrapped as
  both a normal `main` (Tier A) and an exported
  `klain_main(int argc, char** argv)` + a generated JNI stub
  (`JNIEXPORT jint JNICALL Java_<pkg>_KlainRuntime_nativeMain(JNIEnv*, jclass, jobjectArray)`).
- The runtime owns a **secondary thread**: the shim starts `klain_main` on a
  dedicated pthread (ART owns the main thread), and the fiber scheduler runs
  entirely inside it — no loop fusion with Android's Looper is needed for
  Tier B, because nothing native touches the UI.
- stdout/stderr route to logcat via `liblog` (bionic swallows them
  otherwise) — a small runtime shim, Tier B/C only.

### Tier C — WebView apps + `-webview=android`

**Architecture** (the JNI mirror of TDD-00142's same-process model):

- `-package apk` generates a minimal project: a ~150-line Kotlin shim
  (`Activity` + `WebView` setup + `KlainRuntime` JNI holder), `jniLibs/` with
  the Tier B `.so` (plus any bundled tool executables as fake `lib*.so`), a
  manifest, and resources. Build with the SDK's command-line tools directly —
  `d8` for the shim dex, `aapt2` + `zipalign` + `apksigner` — **no Gradle**;
  Gradle is the ecosystem default but an unnecessary, heavyweight moving part
  for a generated, dependency-free shim. (Debug-signing by default;
  release-signing takes a keystore flag.)
- The 13-function C binding gets an `android` implementation whose calls
  marshal to the UI thread over JNI (`runOnUiThread` /
  `Handler(Looper.getMainLooper())`):
  - **eval** → `webView.evaluateJavascript(script) { result -> … }` — richer
    than WebKitGTK's (it returns the result string natively).
  - **bind** → `WebViewCompat.addWebMessageListener` (androidx.webkit; falls
    back to `addJavascriptInterface` below API 23-era WebView versions):
    page-side shim posts `{id, fn, args}` JSON exactly as today; replies
    resolve via `evaluateJavascript`. `addJavascriptInterface` is the
    fallback, not the default — its injected-object model has a history of
    scoping/security sharp edges and it marshals on a background thread.
  - The typed-bind / `bindings` allowlist / `--emit-window-dts` layers are
    transport-agnostic and carry over untouched.
- **serve/assets — one Android-specific decision**: cleartext HTTP is blocked
  by default for API 28+ *including* 127.0.0.1, so the in-binary
  `http://127.0.0.1:<port>` server needs a generated
  `network_security_config.xml` permitting cleartext to localhost only.
  That is the smallest-diff route and keeps `Webview({ serve })` semantics
  identical across platforms. The idiomatic alternative —
  `WebViewAssetLoader` mapping `https://appassets.androidplatform.net/…`
  into the embedded `klain:assets` bundle without any socket — is *better*
  on Android (no port, no config, https origin) but changes the page origin
  and bypasses the shared server code; offer it later as an opt-in, not V1.
- **Lifecycle**: `onDestroy` → signal the runtime thread to run exit
  verifiers/atexit; `onPause`/`onResume` exposed as events on the `Webview`
  object later if demanded. Back-button → window close event.

**What Tier C does not do in V1**: multi-window (same as desktop), Play Store
policy/AAB packaging (APK sideload/CI only; AAB is a packaging follow-up),
Compose/native-UI interop, foreground-service background execution.

### Explicitly out of scope for the whole TDD

- Termux-specific packaging (their apt repo has its own conventions; a plain
  Tier A binary already runs there).
- 32-bit ABIs (armeabi-v7a, x86) — same verdict as Sailfish's armv7hl.
- Running the compiler itself on-device.
- Android AppSupport on Sailfish as a delivery route for *this* TDD's output
  (it would technically run Tier C APKs; treat as a happy accident, not a
  supported target).

## Open questions

- **libucontext vs. own asm** — vendoring policy (first third-party asm in
  the runtime) vs. maintaining per-arch context-switch code ourselves.
- **TLS for vendored curl** — BoringSSL (Google-aligned, no stable ABI,
  bigger build) vs. mbedTLS (small, stable, weaker cipher coverage). Affects
  binary size and the ADR-00080-style exit-cleanup interactions.
- **Min API level** — 29+ makes the exec/W^X rules uniform and
  `addWebMessageListener` reliably available; lower widens devices but
  forks behavior. Leaning 29.
- **`child_process` semantics inside apps** — expose the
  exec-from-`nativeLibraryDir` mechanism as the documented Android shape of
  `spawn`, or restrict `child_process` to Tier A and fail clearly in apps?
- **Kotlin vs. Java for the shim** — Kotlin needs its stdlib in the APK
  (~1.5MB) or a compiler on PATH; plain Java (javac + d8) is
  dependency-lighter for a generated file nobody edits. Leaning Java despite
  Kotlin being the ecosystem default.
- **Where the JNI thread meets the fiber scheduler** — bind callbacks arrive
  on the UI thread and must hop into the runtime thread's scheduler; the
  existing async-bind trampoline assumed same-thread delivery. Likely a
  pipe/eventfd wake into the `select()` loop; needs a design pass with the
  Worker channel machinery in view.
- **AAB / Play distribution** — follow-up packaging TDD once someone actually
  wants store delivery.
