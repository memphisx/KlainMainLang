# ADR-00094: Fix fetch/fs embedded-null-byte truncation via `Response.arrayBuffer()` / `fs.readFileSyncBytes()` / binary-aware `writeFileSync`/`appendFileSync`

- **Relations**: Extends [ADR-00021](ADR-00021.md) (`Response`), [ADR-00023](ADR-00023.md) (`fs.readFileSync`), [ADR-00078](ADR-00078.md) (`ArrayBuffer`/TypedArrays, this fix's prerequisite); "no `Buffer` class" half superseded by [ADR-00315](ADR-00315.md) (the WHATWG fetch/fs return surface decided here stands)
- **Date**: 2026-08-04

## Context

Both `fetch()` response bodies and `fs.readFileSync` hand back plain
null-terminated C strings. Since this compiler's `.length` is
`strlen`-based, any binary payload with an embedded null byte silently
reads back shorter than it really is — a real concern for the REST API
interaction / file I/O directions the project's own instructions prioritizes. This was a
long-documented, explicitly-deferred limitation
(`docs/status/NETWORKING.md`, `docs/status/FILE-SYSTEM.md`), whose stated
prerequisite (`ArrayBuffer`/TypedArrays) shipped in ADR-00078, and was the
one item in `docs/status/README.md`'s "Next up — bugs found but not yet
fixed" table.

## Investigation

Read the actual read/write paths directly rather than assuming the fix
needed new byte-counting logic:

- `fetch`'s libcurl write callback (`__kml_curl_write_cb`,
  `codegen/llvm/runtime_fetch.go:44-83`) already tracks the exact real byte
  count in a `{ptr data, i64 len, i64 cap}` growable buffer (`%len_p`,
  offset 1) — every consumer downstream (`__kml_pending_finish`,
  `__kml_pending_finish_settled`, and, transitively, `__kml_fetch`, the
  dead blocking variant) read offset 0 (the data pointer) only and threw
  offset 1 (the real length) away.
- `fs.readFileSync`'s C implementation (`codegen/llvm/runtime_fs.go`,
  `__kml_fs_read_file`) already computes the exact file size via
  `fseek`/`ftell` before `fread`ing — then discarded it, returning a bare
  `ptr`.

So the fix is almost entirely "stop throwing the length away," not "read
the bytes differently" — confirmed directly against the code, not assumed
from the docs' own description of the bug.

**Scope decision**: fix both directions. Read-only would have let a
program receive binary data intact (`Response.arrayBuffer()`,
`fs.readFileSyncBytes()`) but not save it back out — `fs.writeFileSync`/
`appendFileSync` still only accepted strings (`strlen`-based). Asked the
user directly (a real scope fork, not a judgment call): confirmed "read +
write."

## Decision

**New API surface, purely additive** — every existing function/method
keeps its exact current signature and behavior (`readFileSync`, `.text()`,
`.json()` remain string/`strlen`-based by design, since JSON/text bodies
aren't expected to legitimately contain embedded nulls):

- `Response.prototype.arrayBuffer(): ArrayBuffer` — matches the real Fetch
  API's method name and return type exactly.
- `fs.readFileSyncBytes(path): Uint8Array` — no `Buffer` class exists in
  this compiler and none was added here (resolves
  `docs/status/BINARY-DATA-TYPED-ARRAYS.md`'s previously-open "not decided
  either way" note in favor of the already-existing `ArrayBuffer`/TypedArray
  machinery); `Uint8Array` matches Deno's `readFileSync` convention for
  "give me the raw bytes."
- `fs.writeFileSync`/`appendFileSync` keep their existing 2-argument call
  shape but now branch on the inferred type of `data`: a string keeps using
  the original, untouched `strlen`-based runtime path; an `ArrayBuffer` or
  any TypedArray routes to a new explicit-length runtime path instead — the
  same "dispatch on the argument's inferred type" pattern `emitFetch`
  already uses for `init`'s optional fields (`codegen/llvm/emit_fetch.go`).

### Threading the real length through fetch (`runtime_fetch.go`, `emit_async.go`, `emit_promise.go`, `types.go`)

Extended 3 return-aggregate shapes by one `i64` field, reusing the length
already sitting in the write buffer rather than computing anything new:

- `__kml_pending_finish`: `{i64, ptr}` → `{i64, ptr, i64}` (status, body,
  bodyLen).
- `__kml_pending_finish_settled` (used only by `Promise.allSettled`):
  `{i1, i64, ptr, ptr}` → `{i1, i64, ptr, ptr, i64}`.
- `__kml_await_fetch`: return type header only, its body already just
  tail-calls `__kml_pending_finish`.

`ResponseType()` (`codegen/llvm/types.go`) gained a `bodyLength: i64` field
— an implementation-only field feeding `.arrayBuffer()`, not part of the
documented public surface (real `Response` has no such field either).
`buildResponseFromStatusBody` (`codegen/llvm/emit_async.go`) took a third
`bodyLen` parameter and stores it. All 4 call sites building a `Response`
from a completed fetch were updated to extract and thread the new field:
`emitAwait`'s `IsResponse` branch (`emit_async.go`), and `.all`/`.race`/
`.allSettled`'s `IsResponse` branches (`emit_promise.go`, 3 sites).

`Response.arrayBuffer()` (`codegen/llvm/emit_fetch.go`'s new
`emitResponseArrayBuffer`) hand-builds an `ArrayBuffer` header exactly like
`emitNewArrayBufferExpression` does — `malloc(16)`, store `bodyLength` at
offset 0, store the *existing* body pointer at offset 1. No copy: the
buffer already holds the right bytes, `.arrayBuffer()` just wraps it.

**Left `__kml_fetch` (the blocking variant) untouched.** Confirmed via
`grep` it has exactly one caller, `ensureFetchAsync`, which only needs it
for its shared `curl_easy_*` declarations/`__kml_curl_write_cb` side
effect — `@__kml_fetch` itself is dead code, never called from any live
code path (`emitFetch` always goes through `__kml_fetch_async`). Confirmed
but not fixed here — see Side effects discovered.

### `fs.readFileSyncBytes` (`runtime_fs.go`, `emit_fs.go`)

Split `__kml_fs_read_file` into `__kml_fs_read_file_raw(path) -> {ptr, i64}`
(the real fopen/fseek/ftell/fread implementation, now returning both the
buffer and its real byte count) and a thin `__kml_fs_read_file(path) -> ptr`
wrapper that extracts just the pointer — preserving `readFileSync`'s exact
external behavior byte-for-byte, so its own codegen and every existing fs
test needed zero changes. `emitFsReadFileSyncBytes` (`emit_fs.go`) calls
`__kml_fs_read_file_raw` directly: its `{ptr, i64}` return is already the
exact SSA aggregate shape a first-class TypedArray value uses (the same
shape `.subarray()` builds via `insertvalue` in `emit_arraybuffer.go`), so
no repacking is needed.

### Binary-aware `writeFileSync`/`appendFileSync` (`runtime_fs.go`, `emit_fs.go`)

New `ensureFsWriteLikeBytes` (mirroring the existing `ensureFsWriteLike`)
declares `__kml_fs_write_file_bytes`/`__kml_fs_append_file_bytes`, taking
an explicit `i64 %len` parameter and calling `fwrite` directly — no
`strlen` at all. The existing `__kml_fs_write_file`/`__kml_fs_append_file`
are untouched; the string call path is bit-for-bit unchanged.
`emitFsWriteLikeCall` (`emit_fs.go`) now infers `data`'s type first: an
`ArrayBuffer` gets its byteLength/data pointer GEP'd straight out of its
hidden header (the same shape `emitArrayBufferByteLength`/
`emitTypedArrayFromBuffer` already use); a TypedArray resolves via the
existing `resolveArrayForHOF` plus the **already-existing**
`emitTypedArrayByteLength` helper (`elemTy.Align() * count` — exactly what
a TypedArray's own `.byteLength` getter already computes); anything else
falls through to the original, unmodified string path.

## Implementation notes

Files touched: `codegen/llvm/runtime_fetch.go`, `emit_async.go`,
`emit_promise.go`, `types.go`, `emit_fetch.go`, `emit_exprs_types.go`,
`runtime_fs.go`, `emit_fs.go`, `emit_call.go`, `emitter.go` (new
`usedFsReadFileRaw`/`usedFsWriteFileBytes`/`usedFsAppendFileBytes` flags),
`tests/fetch_test.go`, `tests/fs_test.go`, `examples/fetch/fetch.ts`,
`examples/fs/fs.ts`.

No new declaration-context (var-decl target-type) special-casing was
needed for `.arrayBuffer()` — unlike `.json()`, which needs
`emitResponseJSON`'s separate target-type-aware path
(`emit_exprs_vardecl.go`/`emit_objects.go`), `.arrayBuffer()` always
returns `ArrayBuffer` regardless of context, exactly like `.text()`
already does with no such special-casing.

## Side effects discovered

Confirmed `@__kml_fetch` (the original blocking-fetch function,
predating the async multi-interface rewrite) is dead code: its only caller
is `ensureFetchAsync`, and only for its shared declarations/write-callback
side effect, never for its own body. Initially left as-is here, on the
reasoning that dead code isn't a *bug* the way wrong output is. Corrected
immediately after: removed in [ADR-00095](ADR-00095.md), on the standing
principle that code serving no purpose, with nothing pointing at it as
intentionally kept, should be treated as a bug and removed rather than
filed away as a footnote.

`fs.copyFileSync` (composed from the string-based `readFileSync`/
`writeFileSync`) is **not** fixed by this change — it still inherits the
embedded-null truncation limitation, since it wasn't rewritten to use the
new binary-aware functions. Documented in `docs/status/FILE-SYSTEM.md`
rather than silently left ambiguous.

## Verification

- `go build -o klainmain .`, `go vet ./...` — clean.
- Manual smoke tests (compiled and run directly, before writing the
  automated test suite) confirmed exact byte-for-byte correctness through
  an embedded null not at the end of the buffer, for all four new/changed
  paths: `fetch(...).arrayBuffer()` against a real local HTTP server
  (`"abc\x00def"`, 7 bytes, all recovered correctly including the byte at
  index 3), `fs.readFileSyncBytes` against a Go-written fixture file,
  `fs.writeFileSync`/`appendFileSync` with a `Uint8Array` argument
  (write+append round-tripped 12 bytes including two embedded nulls, byte
  values on disk confirmed via `xxd`), and again with a plain `ArrayBuffer`
  argument (5 bytes, embedded null at index 2).
- New tests: `tests/fetch_test.go` (`TestE2EFetchArrayBufferPreservesEmbeddedNullByte`,
  a paired `TestE2EFetchTextStillStrlenBasedAfterArrayBuffer` pinning down
  that `.text()` deliberately stays truncated, and one test per
  `Promise.all`/`.race`/`.allSettled` call site to regression-guard the 3
  `emit_promise.go` aggregate-shape changes) and `tests/fs_test.go`
  (`readFileSyncBytes` against a null-byte fixture, `writeFileSync`/
  `appendFileSync` round-trips for both `Uint8Array` and `ArrayBuffer`
  arguments verified against the real bytes on disk via `os.ReadFile`, and
  a pinning test confirming the plain-string call path is unchanged) — all
  use a null byte *not* at the end of the buffer, specifically to catch an
  off-by-one that a null-at-the-end case could hide.
- `go test ./...` — full suite green (~48s), no regressions in any
  existing `fetch`/`fs`/`Promise.all`/`.race`/`.allSettled` test.
- `examples/fs/fs.ts` compiled and run directly, output matches every
  inline comment exactly. `examples/fetch/fetch.ts` (needs real network
  access, not run as part of this verification) confirmed to compile
  (`--emit-llvm`) cleanly with its new `.arrayBuffer()` section.
