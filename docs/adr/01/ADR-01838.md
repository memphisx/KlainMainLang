# ADR-01838: An object or callback typedef carries a type node

- **Relations**: `Implements TDD-00230` (P3.3: the checker answers what inferExprType did); follows TDD-00125 Stage 2 (JSDoc typedefs)
- **Date**: 2026-10-20

## Context

- A JSDoc `@typedef {Object} Point` with `@property` tags, or a `@callback Combine` with `@param`/`@returns`, becomes a synthesized `type Name = …` declaration. Its annotation was built field by field as a bare structure, with no type node.
- The checker resolves types from nodes, so it could not resolve `Point` or `Combine`. Every parameter typed by one was unanswered, and so was everything read off it. In `examples/jsdoc/typed-javascript.ts`, `p.x + p.y` and `run((a, b) => a * b)` fell back to the old inference, which typed the arrow's product `any` on the checker's side.
- A single JSDoc type (`@param {number} a`) already went through the TypeScript type parser and carried its node.

## Decision

- An object typedef is spelled as the TypeScript object type it declares, a bracketed `[name]` property optional (`{ x: number; y?: string; }`). A callback typedef is spelled as its function type (`(a: number, ...b: string[]) => number`, `void` without `@returns`).
- That text goes through the same parser as every other JSDoc type. The structural form remains as the fallback for a member with no type.

## Consequences

- The typed-JavaScript example has no disagreements left. Its output is unchanged.
- Verified on Apple Silicon (parser and jsdoc unit tests, the JSDoc E2E tests), and with the gate on Linux x86-64 (DeskMini).
