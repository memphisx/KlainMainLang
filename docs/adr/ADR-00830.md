# ADR-00830: string `.at(i)` returns `string | undefined` (out-of-range → `undefined`)

- **Relations**: Extends [TDD-00187](../tdd/TDD-00187.md) (the `T | undefined` sentinel); supersedes the out-of-range behavior of [ADR-00166](ADR-00166.md)
- **Date**: 2026-09-10

## Context

A stale-caveat sweep found `String.prototype.at(i)` still returned `""` for an
out-of-range index, where Node types it `string | undefined` and returns
`undefined`. The `undefined` sentinel already existed (TDD-00187) and the array
`.at()` path already used it; only the **string** `.at()` path was missed — a
real parity gap, not a deliberate divergence.

## Investigation

`emitStringAt` (`emit_strings.go`) clamped the index via `emitNormalizeSliceIdx`
(slice semantics) and returned `emitStringExtract(...)` with a zero length for
out-of-range — i.e. `""`. `inferExprType`'s `at` case (`emit_exprs_types.go`)
returned bare `TypePtr` for the string receiver while the array receiver already
returned `undefinedableElem(*elemType)`. A first fix exposed a second bug my own
regression test caught: slice-normalization clamps a negative index to `0`, so
`"hi".at(-9)` wrongly yielded `"h"` instead of `undefined` — `.at` index
semantics differ from slice (a negative index adds length once, then anything
outside `[0, len)` is a miss, with no clamping).

## Decision

- `emitStringAt` now applies `.at` index semantics directly: `adjusted = i < 0 ?
  i + len : i`; `inBounds = adjusted >= 0 && adjusted < len`. In bounds → the
  one-char string; out of bounds → the null pointer, wrapped via
  `wrapUndefinedable` so the static type is `string | undefined`
  (Nullable|IsUndefined) and it renders/compares as `undefined`. The extract
  uses a `safeIdx` (0 when out of bounds) so no out-of-range pointer is formed.
- `inferExprType`'s string `at` case returns `undefinedableElem(TypePtr)`,
  mirroring the emit site.
- Consumer policy is TDD-00187's existing strict/`-compat=js` split.

## Implementation notes

- `emit_strings.go` `emitStringAt`; `emit_exprs_types.go` string `at` case.
- The `.at(i)` status row drops its caveat (now a clean note), raising String
  methods' Strict Coverage.

## Side effects discovered

The negative-out-of-range bug (`-9` clamped to `0`) was latent behind the old
`""` behavior and only surfaced once the result had to be `undefined`; fixed in
the same change. `.charAt(i)` is unaffected (it correctly never wraps negatives).

## Verification

macOS (Apple Silicon M4): repro matches Node — `"hi".at(0)='h'`, `.at(-1)='i'`,
`.at(5)=undefined`, `.at(5)===undefined` and `.at(-9)===undefined` both `true`.
New `TestE2EStringAtUndefinedOutOfRange` + full `go test -run TestE2EString`
green.
