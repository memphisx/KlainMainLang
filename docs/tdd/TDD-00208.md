# TDD-00208: `any`/`unknown`-typed object and class fields (boxed field slots)

- **Status**: Implemented

## Context

A statically-shaped object literal or class may declare a field whose type is
`any`/`unknown` — `class C { #field: any = null }`, `{ x: any }`. The compiler
rejects this today (`containsDynamicElement` →
"any/unknown is not yet supported as an array element or object field type"),
even though the *array* analogue (`any[]`, TDD-00200/00205) already ships: a
boxed-element buffer of one NaN box per slot, box-on-write / unbox-on-read over
the ordinary array machinery.

This blocks real code (an evolving-any class field, a heterogeneous config
object) and is a prerequisite for consistent dynamic values through the
throw/reject channel (a thrown object's fields, TDD-00202 residue). It is the
field-shaped counterpart of the shipped boxed-element array — NOT the full
runtime dynamic-object model (heterogeneous/runtime-shaped objects, TDD-00155):
the object's field *set* stays statically known; only a field's *value type* is
`any`.

## Design

An `any`/`unknown` field occupies a normal `i64` struct slot holding a NaN box
(the same encoding `any` locals and `any[]` elements use). Every field *write*
boxes its value (`coerce(v, TypeAny)`); every field *read* yields the box as a
dynamic value (unbox/dispatch happens in the existing dynamic-value consumers —
`emitDynamicToString`, dynamic `typeof`, dynamic member/`??`, etc.). Because a
number field is already an `i64` slot, storage layout is unchanged; the work is
routing box/unbox at each field-touch site and relaxing the type gate.

**Recommended direction.** Mirror the `any[]` rollout: relax the gate, wire the
core field-touch sites, and keep a *documented* clean-rejection for the edges
not yet wired (constrained-union field types stay rejected exactly as
constrained-union array elements do). Bare `any`/`unknown` only.

### Stages

1. **Storage + core read/write.** Relax `objectFieldDynamicRejected` for a bare
   `any` field. Box on: object-literal construction, class field initializers /
   constructor `this.f =`, and `obj.f = v` / `this.f = v` assignment (including
   compound/logical assign — reuses the `IsDynamic` `??=` path from ADR-00923).
   Unbox-as-dynamic on `obj.f` / `this.f` read. Fixes the Test262 class-field
   file (`logical-assignment/left-hand-side-private-reference-data-property-nullish.js`).
2. **Aggregate operations.** `JSON.stringify`, `console.log`/`inspect`,
   `===`/`==`, `typeof`, object spread `{...o}`, and destructuring over an `any`
   field — each already has a dynamic-value path from the `any` local / `any[]`
   work; point the field slot at it.
3. **Interop edges.** A method parameter/return typed through an `any` field, a
   nested `any` field, optional chaining `o.f?.x` on an `any` field. Anything
   still unwired rejects cleanly with a recognizable diagnostic (not invalid IR),
   documented as scope.

## Open questions

- Does an `any` field participate in structural-assignability between two object
  types (`{x:any}` ↔ `{x:number}`)? V1: require an exact `any`-to-`any` field
  match, reject a mismatch cleanly (the boxed vs raw representations differ) —
  same spirit as the synthetic-accessor-class boundary.
- Constrained-union field types (`string | number` field) are already supported
  (TDD-00119, an `{i8,i64}` box) — unaffected here. The scope cut is only for a
  constrained-union *array element* (`(A|B)[]`), which stays rejected.
