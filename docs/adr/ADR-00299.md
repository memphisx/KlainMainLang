# ADR-00299: fetch `Response.body` streaming — resolve-at-headers, curl pause/unpause

- **Relations**: Implements [TDD-00097](../tdd/TDD-00097.md) Stage 4; extends [ADR-00296](ADR-00296.md)–[ADR-00298](ADR-00298.md); reshapes [ADR-00050](ADR-00050.md)'s await point and [ADR-00280](ADR-00280.md)'s `.then` bridge
- **Date**: 2026-08-22

## Context

TDD-00097 Stage 4: the first real producer for the WHATWG stream surface.
`Response.body` becomes a `ReadableStream<Uint8Array>` fed incrementally from
libcurl's write callback — which requires `await fetch(...)` to resolve when
the response *headers* arrive (as in real JS), not when the whole body has
been buffered.

## Investigation

The TDD's flagged spike (curl pause reliability) resolved cleanly on this
machine: returning `CURL_WRITEFUNC_PAUSE` from the write callback (the chunk
is *not* consumed and is redelivered on unpause) plus
`curl_easy_pause(CURLPAUSE_CONT)` from the stream's pull hook, with the
regular `curl_multi_perform` pumping, resumed transfers reliably (Mac,
Secure Transport backend — the GnuTLS/Linux side should be re-verified on the
other machine per standing practice).

Moving the resolve point is the invasive part — three ordering/concurrency
regressions surfaced immediately and shaped the final design:

1. **`.then` ordering** (`TestE2EFetchThenAndAwaitShareOneHandle`): the
   deferred `.then` drive (ADR-00280) used to complete during the awaiter's
   full-body wait. Fix: the drive runner also resolves at headers, and the
   headers wait drains the microtask FIFO each spin, preserving the old
   observable order.
2. **AbortSignal machinery** lives in the full await loop; a signal-carrying
   fetch therefore keeps resolve-at-completion (caveat) rather than
   duplicating the teardown.
3. **Connection-fiber concurrency** (`TestE2EHTTPListenConcurrentAwaitFetch`):
   a busy-spin headers wait blocked the whole event loop during a slow
   upstream's pre-header delay. Fix: the headers wait parks a connection
   fiber exactly like the full await, and the event loop's resume scan wakes
   a parked fiber on `headersDone` as well as `done`.

## Decision

- The pending-fetch struct grows 48 → 72 bytes: `headersDone`, `bodyStream`
  (the activated ReadableStream, or null), `paused`. The write buffer grows
  24 → 32 bytes, carrying a pending backpointer so the shared write callback
  can reach the fetch state (null on the EventSource path, which shares the
  callback).
- The write callback marks `headersDone` on first invocation, then consults
  `__kml_fetch_body_write`: no stream → buffer exactly as before; stream with
  queue room (or a parked read) → malloc-copy + enqueue the chunk as a
  `Uint8Array`; queue at its high-water mark → set `paused`, return
  `CURL_WRITEFUNC_PAUSE`. `__kml_fetch_body_on_done` (called from the
  multi-message drain) closes the stream, or errors it on a transfer-level
  failure. Both are no-op stubs when no `.body` stream is ever created — the
  buffered path is byte-for-byte unchanged.
- `__kml_await_fetch_headers` replaces the await/`.then` resolve point:
  park-on-fiber / microtask-draining busy-spin until `headersDone || done`,
  status via `CURLINFO_RESPONSE_CODE` (or the recorded status once done).
  The Response is built with a null body and its pending handle in a new
  hidden `__kml_pending` field; `.text()`/`.json()`/`.arrayBuffer()` first
  drive the transfer to completion (`__kml_await_fetch`, unchanged) and
  cache body/bodyLength back into the object.
- `res.body` (dispatched ahead of the generic field read) creates the stream:
  pull closure `__kml_fetch_body_pull` (clear `paused`,
  `curl_easy_pause(CONT)`, pump), pre-stream buffered bytes flushed as the
  first chunk, repeated access returns the same stream. A null-pending
  Response (combinator-built, or already driven) replays its buffered body
  as one chunk and closes.
- The no-fiber await drive loop additionally pumps `__kml_fetch_pump`
  (multi_perform + message drain; stubbed without fetch), so a parked
  body-stream read at top level makes progress.

## Implementation notes

`runtime_fetch.go` (struct/callback/headers-await), new
`runtime_fetch_stream.go` (hooks), `runtime_eventsource.go` (32-byte buffer),
`runtime_http.go` (resume scan), `emit_async.go` (await slot + pump),
`emit_promise_then.go` (drive runner), `emit_fetch.go` (lazy body accessors),
`emit_streams_pipe.go` (`emitResponseBodyStream`), `types.go`
(`__kml_pending` field), member/inference dispatch.

## Side effects discovered

- A signal-carrying fetch still resolves at completion (see above) — caveat.
- `Object.keys`/`JSON.stringify` of a Response now see the internal
  `__kml_pending` field — caveat.
- Reading `.text()` after consuming `.body` returns `""` instead of throwing
  the spec's already-disturbed TypeError — caveat.

## Verification

- `tests/streams_test.go` Stage 4 block: a flushed chunked endpoint observed
  as ≥ 2 incremental chunks decoded to the full text; `.text()` (twice) on a
  headers-resolved Response; `.body` replay equality after `.text()`.
- Full `go test ./...` green (Mac) — including the fetch/XHR/EventSource/
  Promise-combinator suites and the two ordering/concurrency tests that
  caught the regressions above. `examples/streams/fetch_body.ts` against
  httpbin-lite's new `/chunked` endpoint; `go vet` clean.
