# ADR-00535: `for…of` over a string iterates its characters

- **Relations**: Extends ADR-00482
- **Date**: 2026-08-31

## Context

`for (const c of "abc")` was a compile error ("for...of requires an array,
Map, Set, generator, or class-with-next() value"). Iterating a string
character-by-character is a common, fundamental use of `for…of`. `Array.from(a
string)` already worked (ADR-00482), so the string→character-array runtime
existed — it just wasn't wired into `for…of`.

## Investigation

`emitForOf` (`emit_stmts.go`) resolves the iterable to a `(dataPtr, len,
elemTy)` triple and drives a shared array loop; strings fell through to the
error. `Array.from`'s string case (`emit_arrays_iter.go`) already materializes a
`string[]` of 1-byte character strings. The one hazard: `isStringTy` is a *loose*
predicate — it matches any bare `ptr` type, which includes `Map`/`Set`/`RegExp`/
`Promise`/etc. (all `ptr`-typed). A first attempt using `isStringTy` directly
made `for (const v of map)` treat the Map pointer as a string and segfault
(`__kml_str_len` on a Map).

## Decision

1. Extract `Array.from`'s inline string→char-array logic into a shared
   `emitStringToCharArray(v)` helper.
2. Add `isForOfStringTy` — a strict "really a plain string" predicate that
   excludes every `ptr`-typed special type the type system flags
   (`Map`/`Set`/`RegExp`/`Promise`/`Date`/`URL`/`Symbol`/`Blob`/typed arrays/
   streams/generators/dynamic/nullable).
3. In `emitForOf`, when the iterable is a string, materialize the char array and
   feed it into the existing array-iteration loop (`elemTy = string`).

Per byte, not per code point — the same documented Unicode narrowing the rest of
the string layer carries; correct for ASCII/Latin-1.

## Implementation notes

`emit_arrays_iter.go` (helper extraction + `Array.from` reuse), `emit_stmts.go`
(the for-of string branch), `emit_strings.go` (`isForOfStringTy`). The strict
predicate is deliberately a superset of exclusions so a future `ptr`-typed
iterable can't silently be mis-read as a string.

## Side effects discovered

The initial loose-`isStringTy` version segfaulted `for (const v of map)` — the
regression that motivated `isForOfStringTy`. Caught by
`TestE2EForOfMapEntriesDecomposition` before this shipped. String spread
(`[..."abc"]`), string destructuring (`const [a,b] = "xy"`), and string spread
into a call remain separate, still-unsupported cases (their own spread/
destructuring machinery, not this for-of path).

## Verification

`TestE2EForOfString` (new): a literal, a string variable, and the empty string,
cross-checked against real Node. The full collections/arrays/strings/generators
suites pass (the Map-values regression is gone). Verified on Mac (Apple Silicon).
