# ADR-00247: A string enum's name resolves to its string backing type as an annotation

- **Relations**: none (fixes a [ADR-00166](ADR-00166.md) 2026-08-11-audit find)
- **Date**: 2026-08-19

## Context

A string enum (`enum Color { Red = "RED", ... }`) worked when a member was used
directly (`console.log(Color.Red)` prints `RED`) but crashed the moment a member
was assigned to anything *explicitly typed with the enum*:

```ts
const c: Color = Color.Green;   // clang: global variable reference must have pointer type
```

The 2026-08-11 audit ([ADR-00166](ADR-00166.md)) recorded this as a hard `clang`
error emitting invalid IR — `store i64 @.s1, ptr %t1` — and flipped the "Enums
(string)" row to ❌.

## Investigation

`registerEnums` (`emitter.go`) already interns each string member as a global
string constant and records the member Value with `Ty: TypePtr`, so a *member
expression* has the right type. The break was on the annotation side:
`resolveType(ta)` had no enum case at all. A bare enum name fell through to the
`ResolveTypeName(ta.Name)` built-in fallback, which defaults an unknown name to
`i64` — the numeric-enum backing type. So `const c: Color` allocated an `i64`
slot, and storing the member's string *pointer* (`@.s1`) into it was the type
error. Numeric enums happened to work only because their members and the fallback
agreed on `i64` by coincidence.

Two annotation shapes reach `resolveType` for an enum:

1. the bare name `Color`, and
2. the array form, which the parser hands over as a **single `"Color[]"` suffix
   name** (not an `ElemType`), so it needs the same enum lookup the interface
   registry already gets in the `"[]"`-suffix branch.

## Decision

Record each enum's backing value type at registration — `enumBacking[name] =
TypePtr` for a string enum, `TypeI64` for a numeric one — and consult it in
`resolveType`:

- bare name `Color` → `enumBacking["Color"]` (before the `ResolveTypeName`
  fallback);
- `Color[]` → in the existing `"[]"`-suffix branch, after the interface check,
  return `ArrayOf(enumBacking[base])`.

`ta.Nullable` is threaded through both, matching every other named-type branch.
Numeric enums resolve to `i64` exactly as before (no behavioral change; the
coincidence is now explicit).

## Consequences

- A string enum in every annotation position works: typed variable, `===`
  comparison, function parameter and return type, interface/class field,
  `switch` discriminant, and a typed array `Color[]`.
- No representation change — members were already interned string pointers; this
  only teaches the *type resolver* the backing shape, so reads/stores/printing
  all use `ptr`/`%s` instead of `i64`/`%lld`.
- The read side of the value (`inferExprType` on a member) already returned
  `TypePtr`; the fix is purely the annotation-to-type mapping.

## Verification

- `go build`, `go vet ./...` clean.
- New E2E test `TestE2EStringEnumTypedVariable` (typed var, comparison,
  param+return, interface field, `switch`, typed array); the existing
  numeric/explicit/const-enum tests stay green, including a numeric-enum typed
  array as a regression guard.
- `examples/enums/enums.ts` gains a string-enum section.
- `make examples` and `make conformance` run at delivery. Apple Silicon (macOS).
