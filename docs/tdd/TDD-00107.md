# TDD-00107: Asynchronous `fs` — callback and Promise (`fs/promises`) variants

- **Status**: Implemented
- **Date**: 2026-08-24
- **Notes**: Callback (`fs.readFile(path, cb)`) + Promise (`fs.promises.*` / `import from 'fs/promises'`) over the sync op set. Blocking I/O under the hood (no thread pool) — async-shaped, not thread-pooled; the throwing sync helpers are reused verbatim, their throw caught via the `setjmp` catch primitive and re-surfaced as `err` / a rejection

## Context

`fs` today is synchronous only (`readFileSync`/`writeFileSync`/… — ADR-00023/
00027/00094). The async row on [FILE-SYSTEM.md](../status/FILE-SYSTEM.md) is the
last ❌ there and directly on the priority path (file I/O, the second
tiebreaker). Node offers two async shapes over the same operations: the classic
**callback** form (`fs.readFile(path, cb)` where `cb(err, data)`) and the
**Promise** form (`fs.promises.readFile(path)` / `import { readFile } from
'fs/promises'`). This document scopes both for V1.

## The honesty problem

Node's async `fs` is genuinely non-blocking: the work runs on a libuv thread
pool while the event loop continues. **This compiler has no thread pool.** V1
does not pretend otherwise: the underlying I/O is the existing *blocking*
syscall, run inline; only the *delivery* is async-shaped — the callback fires
(synchronously, right after the operation) and the Promise is returned already
settled (immediately awaitable). This is the same posture the project already
takes for `dns.promises.lookup`, Web Crypto (settled task promises over
synchronous backends), and every event callback that "fires synchronously from
the dispatch" (readline/child_process). Documented as a caveat, not hidden.

The value is real regardless: async-shaped `fs` is what lets existing
Promise/`async`-`await` TS code and callback-style code compile and run
unchanged; it is not a performance claim.

## Design

### Reuse: throwing sync helpers + setjmp-catch

The sync runtime helpers (`@__kml_fs_read_file`, `…_write_file`, `…_unlink`, …)
already exist and signal failure by **throwing** a catchable `Error` (built from
`strerror(errno)` via `@__kml_fs_throw` → `@__kml_throw`). Async delivery needs
the failure as a *value* (a rejected Promise / an `err` callback argument), not
a throw. Rather than add a parallel set of non-throwing runtime variants, V1
wraps the existing sync call in the compiler's own `setjmp`/`__kml_get_thrown`
catch primitive (the exact mechanism `emitTry` uses):

```
q / cb ready
%jb   = call ptr @__kml_push_jmpbuf()
%sj   = call i32 @setjmp(ptr %jb)
%thr  = icmp ne i32 %sj, 0
br %thr, %catch, %try
try:    <emit the existing sync op>   ; may throw
        call @__kml_pop_jmpbuf()
        <resolve promise / call cb(null, result)>
        br done
catch:  %err = call ptr @__kml_get_thrown()   ; __kml_throw already popped the jmpbuf
        <reject promise / call cb(err)>
        br done
done:
```

No new runtime code — every operation reuses its existing `emitFs<Op>Sync`
emitter verbatim as the `try`-body, so the async and sync paths cannot diverge
in behavior. No tryL-computed SSA value is read in `catch`/after, so the
`setjmp` value-liveness rules are satisfied (same as `emitTry`).

### Surfaces (both delivered in V1)

- **Callback**: `fs.<op>(...opArgs, cb)`. New async members on the existing `fs`
  pseudo-namespace, beside the `*Sync` ones (mirroring `zlib`'s
  `gzipSync`/`gzip` split). `cb` is an arrow/function-expression literal
  (project posture). Signatures: `(err, data)` for `readFile`/`readdir`; `(err)`
  for the write/mutate ops.
- **Promise**: `fs.promises.<op>(...opArgs)` (a two-level member chain on the
  `fs` marker, like `dns.promises.lookup`) **and** `import { <op> } from
  'fs/promises'` (a new virtual module `fs/promises`, marker
  `fspromises__kml_builtin`, like `stream/promises`). Returns a settled task
  Promise (`PromiseOf(resultTy)`, `PromiseTask`), resolved with the result or
  rejected with the `Error`. The existing settled-promise plumbing
  (`emitAllocSettledPromise`/`storePromiseValue`/`emitSetPromiseState`/
  `emitAsyncGenRejectPromise`) already stores string, `string[]` (the
  `IsArray` `{ptr,i64}` split), and void results.

### Operations (V1 set = the sync set)

| op | opArgs | callback | promise result |
|---|---|---|---|
| `readFile` | (path) | (err, data: string) | `string` |
| `writeFile` | (path, data) | (err) | `void` |
| `appendFile` | (path, data) | (err) | `void` |
| `unlink` | (path) | (err) | `void` |
| `mkdir` | (path) | (err) | `void` |
| `rmdir` | (path) | (err) | `void` |
| `rename` | (old, new) | (err) | `void` |
| `copyFile` | (src, dest) | (err) | `void` |
| `readdir` | (path) | (err, files: string[]) | `string[]` |

`writeFile`/`appendFile` keep the sync path's string/`ArrayBuffer`/TypedArray
`data` dispatch. `readFile` delivers a **string** (text), inheriting
`readFileSync`'s documented text-only caveat — no async binary (`Buffer`) form
in V1.

### Out of scope (V1)

- `fs.createReadStream` / `createWriteStream` — stream-based, a separate follow-on
  (the Streams subsystem exists, TDD-00097, but wiring a file-fd Readable/Writable
  is its own unit).
- Truly non-blocking / thread-pool execution — needs a worker offload the
  runtime doesn't have.
- The `options`/`encoding` argument (`fs.readFile(path, 'utf8', cb)`); an async
  `stat`/`promises.stat` (no sync `stat` exists yet either).
