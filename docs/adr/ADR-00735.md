# ADR-00735: `Math.random()` on Windows never exceeded 1.5e-5

- **Relations**: Extends [ADR-00719](ADR-00719.md) (the Windows platform layer), [ADR-00718](ADR-00718.md) (the mingw/UCRT toolchain)
- **Date**: 2026-09-07

## Context

Found while auditing the Windows platform layer against Node's documented Windows behaviour (the "is mingw's POSIX surface leaking into observable semantics" question left open when the port landed, [TDD-00177](../tdd/TDD-00177.md) Option D). Repro on the Windows box:

```
for (let i=0;i<5;i++) console.log(Math.random());
```

```
4.2328611035984294e-7
0.000011653173720302607
0.0000028680078698638863
0.000011276453738695222
0.000014550983912568066
```

Every sample lands in `[0, 1.5e-5]`. Any program using `Math.random()` for a coin flip, a shuffle, a jitter or an id is wrong on Windows. No test caught it: the only `Math.random()` tests asserted compile-time properties (`@pure` rejection, reserved-global handling), never the range.

## Investigation

`emitMathRandom` (`codegen/llvm/emit_call_math.go`) has two paths: `arc4random()` on the BSDs/macOS, and otherwise an IR helper `@__klain_math_random` (`codegen/llvm/runtime_core.go`) that seeds with `time(NULL)` and returns `rand() / 2147483647.0`. The divisor is glibc's `RAND_MAX`. The UCRT's `RAND_MAX` is `32767`, so on Windows the quotient is bounded by `32767 / 2147483647 ≈ 1.5e-5`. Even with the right divisor the fallback would be a 15-bit LCG seeded to the second, which is a poor stand-in for V8's xorshift128+.

Alternatives considered:

- Divide by `RAND_MAX` per host. Fixes the range but keeps 15 bits of entropy and the once-per-second seed.
- The shim's `getrandom()` (BCryptGenRandom, `win32src/win32shim.c`). Correct, but one syscall-shaped call per `Math.random()`, and it is a Linux-ABI shim symbol rather than a C-runtime function.
- UCRT `rand_s()`. Uniform 32-bit output from the system RNG (`RtlGenRandom`), no seeding, declared in `<stdlib.h>`, exported by `ucrtbase.dll`. Same shape as the `arc4random()` path already used on macOS.

## Decision

`rand_s()` on Windows: a third case in `emitMathRandom` that allocas an `i32`, calls `@rand_s(ptr)`, converts the value with `uitofp` and divides by `4294967296.0`, giving `[0, 1)` exactly like V8. `ensureRandS` declares the symbol once, reusing the `usedArc4Random` slot the same way `ensureRandRandom` does (only one of the three paths is ever taken per host).

## Implementation notes

- `codegen/llvm/emit_call_math.go`: the `"windows"` case.
- `codegen/llvm/runtime_core.go`: `ensureRandS`.
- The divisor differs from the macOS path (`4294967295.0`), which can yield exactly `1.0` once in 2^32 draws; that is a pre-existing off-by-one against `[0, 1)` and is left for a separate fix so this change stays Windows-only.

## Side effects discovered

- The rest of the audit that surfaced this is recorded in [TDD-00180](../tdd/TDD-00180.md): the toolchain decision held, but a number of observable behaviours on Windows are still CRT/POSIX-shaped rather than Node-shaped.

## Verification

- `tests/exprs_test.go` `TestE2EMathRandomSpreadsAcrossUnitInterval`: 2000 samples, asserts max above 0.5, min below 0.5 and both inside `[0, 1)`. Fails on the old code on Windows, passes on the new; passes unchanged on Linux and macOS (the other two paths are untouched).
- Repro above re-run on Windows after the fix: `0.572…`, `0.343…`, `0.960…`, `0.572…`, `0.295…`.
- `go vet ./...`, `go test ./tests -run 'Math|ReservedGlobals'` on Windows (x86-64, Windows 11).
