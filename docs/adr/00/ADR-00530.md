# ADR-00530: `parseInt` hex auto-detect when the radix is omitted

- **Relations**: Extends ADR-00287
- **Date**: 2026-08-31

## Context

`parseInt("0xFF")` returned `0`; real JS returns `255`. With no radix argument
JS auto-detects base 16 for a `"0x"`/`"0X"` prefix (past leading whitespace and
an optional sign) and base 10 otherwise. This compiler hard-coded base 10 when
the argument was omitted, so `strtoll` stopped at the `x`. Documented as a
caveat on the `parseInt` row.

## Investigation

JS deliberately does NOT auto-detect octal from a leading `0` (that ES3
behavior was removed in ES5): `parseInt("077")` is `77`, `parseInt("08")` is
`8`. So `strtoll` base 0 (which auto-detects both hex and octal) is wrong — the
detection has to be hex-only. The specifier is a runtime string value, so the
base must be computed at runtime. `strtoll` accepts the `0x` prefix when handed
base 16, so a detected base flows straight through. One edge remained:
`parseInt("0x")` (prefix, no hex digit) — `strtoll` consumes just the leading
`0` and stops on the `x`, looking like a successful parse of `0`, where JS
gives `NaN`.

## Decision

Add `@__kml_parseint_base(ptr s) -> i32` (`runtime_core.go`): skip whitespace
and an optional sign, return 16 for a `0x`/`0X` prefix and 10 otherwise. In
`emitParseInt`, when the radix argument is omitted, call it and pass the result
to `strtoll`. Additionally, in that auto-detect path, fold "base 16 chosen but
`endptr` landed on the `x`/`X`" (the `"0x"`-with-no-digit case) into the
existing no-digits→NaN condition. The explicit-radix path is unchanged.

## Implementation notes

`runtime_core.go` (`__kml_parseint_base` + `usedParseIntBase` flag in
`emitter.go`), `emit_call_number.go` (`emitParseInt` auto-detect + the
`0x`-stuck NaN fold). The `x`/`X` end-char check is gated on the detected base
being 16, so a base-10 string like `"5x"` (→ 5) is untouched.

## Side effects discovered

None. `Number("0x10")` → 16 was already correct (JS ToNumber reads hex) and is
unrelated to this path.

## Verification

`TestE2EParseIntHexAutoDetect` (new): 15 cases — prefixes, signs, whitespace,
`0x`/`0X`/`0xG`/`0x0` edges, non-octal `077`/`08`, `5x`, and explicit-radix
forms — all cross-checked against real Node. Existing parse tests pass. Verified
on Mac (Apple Silicon).
