# TDD-00038: `EventSource` (Server-Sent Events, staged)

- **Status**: Implemented ([ADR-00122](../adr/ADR-00122.md) — Stage 0: connection plumbing; [ADR-00123](../adr/ADR-00123.md) — Stage 1: SSE record parsing + `onmessage`; [ADR-00124](../adr/ADR-00124.md) — Stage 2: named events/`addEventListener`, `onopen`/`onerror`; [ADR-00129](../adr/ADR-00129.md) — Stage 3: CRLF-tolerant record boundaries, non-2xx/wrong-`Content-Type` terminal failure, and auto-reconnect with `retry:`/`Last-Event-ID` replay) — every stage this document now commits to is done
- **Date**: 2026-08-07 (Stages 0-2); Stage 3 added 2026-08-08

## Context

`EventSource` is the last unstarted row in [`docs/status/NETWORKING.md`](../status/NETWORKING.md)'s API table (`WebSocket`/`XMLHttpRequest` remain lower priority — see `docs/status/README.md`'s Roadmap). It was originally tiered as High effort pending two prerequisites — non-blocking `fetch` and a real event loop — both of which now exist ([ADR-00050](../adr/ADR-00050.md), [TDD-00006](TDD-00006.md)); `docs/status/README.md`'s Roadmap already flagged the remaining gap precisely: "SSE needs incremental delivery as chunks arrive (firing a callback per event), whereas today's `fetch` buffers the whole body until the transfer completes." That's real, design-worthy work, not a small feature — hence this document, per `CLAUDE.md`'s standing rule for anything needing a design pass before implementation.

Investigated three existing subsystems directly (reading `codegen/llvm/runtime_fetch.go`, `runtime_http.go`, `emit_eventemitter.go`/`runtime_eventemitter.go`) before designing, since the whole point of scoping this now is to reuse as much of them as possible rather than invent new machinery:

1. **`fetch`'s libcurl write callback is already chunk-aware at the C/IR level.** `__kml_curl_write_cb` (`runtime_fetch.go:47-81`) is called by libcurl "possibly many times, once per chunk" (its own doc comment) and just appends into a realloc-doubled `{ptr data, i64 len, i64 cap}` accumulator (24 bytes) — it has no notion of message boundaries and nothing reads the buffer until the transfer's `done` flag is set, but the buffering-into-one-blob is a *Go-side codegen choice* (nothing reads it early), not a hard C-level constraint. This is good news: EventSource's own record-boundary parsing can be layered on top of the *existing*, unmodified write callback rather than requiring a new one.
2. **The fiber scheduler only ever wakes a parked fiber once, at full transfer completion** (`__kml_event_loop_run`'s `rcheckfetchdone` block, `runtime_http.go:1163-1176`, tests `pending->done`, set only on `CURLMSG_DONE` in `runtime_fetch.go:291-292`) — there's no "wake on partial progress" primitive today. This looked like a real gap until working through EventSource's own actual API shape (see Design): `new EventSource(url)` is fire-and-forget, not `await`ed, so nothing ever needs to *park a fiber* on it in the first place — this isn't a prerequisite gap to close at all, just a wrong initial framing corrected during investigation.
3. **`EventEmitter<T>`'s underlying listener-list storage is directly reusable; its generic wrapper is not.** The real machinery (`runtime_eventemitter.go`'s `__kml_ee_list_create/_push/_remove`, keyed by a per-instance `Map<string,ptr>` via `runtime_collections.go`'s `__kml_map_str_*`) is generic and reusable as-is. But `EventEmitter<T>`'s *single concrete payload type `T` per instance* constraint (`resolveEventEmitterListenerArg`, `emit_eventemitter.go:125`) doesn't fit — SSE's payload is always the same fixed shape (`data`/`type`/`lastEventId`, all strings) regardless of user code, so there's no generic instantiation problem to begin with; and `.emit('error', ...)`'s existing "throw if nobody's listening" behavior (`emit_eventemitter.go:442-460`) is wrong for SSE's `onerror` (a dropped connection is a normal, expected occurrence, not something that should throw). EventSource should call the listener-list C helpers directly, the same way `emit_eventemitter.go` itself does, without going through the full `EventEmitter<T>` Go-level wrapper.

No existing precedent for "a long-lived class-like object, constructed once, that keeps receiving callbacks over time until explicitly closed" — `setTimeout`/`setInterval` are the closest structural analogue (a registered, opaque, ID-keyed entry the event loop's per-iteration scan drains repeatedly, `emit_timers.go`) but aren't object-shaped (no instance, no `.close()` method). EventSource is the first "instance with its own long-lived event-loop-driven lifecycle" this compiler will have.

## Design

### Not fiber-parked — a third scanned-every-iteration resource, like a timer

`__kml_event_loop_run` already drains three independent things every iteration: the timer queue, the connection-fiber array (fd readiness / pending-fetch completion), and (per `runtime_http.go`'s doc comment) HTTP dispatch. EventSource is a **fourth**: `new EventSource(url)` immediately (synchronously, at construction — matching real `EventSource`'s own "connects without an explicit `.connect()` call") does the same `curl_easy_init`/`CURLOPT_URL`/`CURLOPT_WRITEFUNCTION`/`CURLOPT_WRITEDATA`/`curl_multi_add_handle` sequence `await fetch(...)` already does (`runtime_fetch.go` lines ~190-220), reusing the **same** global `CURLM` multi handle fetch already creates on first use — but the resulting pending entry is never attached to any fiber's `pendingFetch` slot. Instead it's appended to a new, parallel global array (mirroring `__kml_conn_data/_len/_cap`'s existing shape): one entry per open `EventSource`, `{ ptr easy, ptr buf, i64 consumedOffset, i64 state, ptr instance }` — `buf` is the *same* `{ptr,i64,i64}` accumulator struct the write callback already knows how to grow; `state` is `0=CONNECTING, 1=OPEN, 2=CLOSED`; `instance` is the KML-level object pointer (holds the per-instance listener-list map, needed so the scan can dispatch into user code).

`__kml_event_loop_run`'s existing per-iteration body already calls `curl_multi_perform`/drains completion messages unconditionally once curl is in play at all (today only to detect `CURLMSG_DONE` for a parked fetch) — that call now also advances every open `EventSource`'s transfer, for free, with no new libcurl-level plumbing. A new scan step, sibling to the existing timer/fd/fetch scans, then walks the EventSource array: for any entry with `buf.len > consumedOffset`, look for complete `\n\n`-delimited (also accepting `\r\n\r\n`/bare `\r\r`, per the real SSE spec's line-ending tolerance) records in the unconsumed tail, parse each into `field: value` lines (`data`/`event`/`id`/`retry`, `:`-prefixed lines are comments and ignored, unknown fields ignored — the real spec's own parsing algorithm, not a KML-specific narrowing), dispatch each complete record to the matching listener(s), and advance `consumedOffset` past it. A record that isn't `\n\n`-terminated yet (a chunk boundary landed mid-record) is simply left for the next iteration — `consumedOffset` only ever advances past *fully parsed* records, so this is naturally incremental and correct regardless of how libcurl happens to chunk the transfer.

### Event-loop keep-alive

`__kml_event_loop_run`'s own "is there still work" condition already accounts for the timer queue, `__kml_conn_active`, and a registered HTTP listener. It needs one more OR-branch: at least one EventSource entry with `state != CLOSED`. Symmetric with `e.usedTimers`'s existing gate (`emitter.go:156`, checked at `emitter.go:593` to decide whether Pass 3 emits a trailing `__kml_timer_drain()` call) — propose a parallel `e.usedEventSource` bool that, when set, emits a trailing `__kml_event_loop_run()` call (if one isn't already going to run some other way, e.g. inside `http.listen`) so a plain top-level script that only ever does `new EventSource(url); es.onmessage = ...;` doesn't fall straight through and exit immediately after synchronous top-level code finishes — mirroring exactly how a plain `setInterval` already keeps a script alive today.

### Object shape: not a real `class`, a dedicated built-in type

Modeled directly on `Date`/`URL`/`Response` (`emit_date.go`/`emit_url.go`/`emit_fetch.go`) rather than as something expressible in user-authored `class` syntax: a new `NewEventSourceExpression` AST node (`new EventSource(url: string)` — single string argument only, matching the real spec's own narrow constructor, no `init` object; the Web platform's real `EventSource` only ever takes a `{ withCredentials }` second argument, which has no meaning without cookies/credentialed requests in this compiler's `fetch` model either, so it's simply omitted rather than accepted-and-ignored) and a dedicated `EventSourceType()` `Type`, with field/method dispatch (`.readyState`, `.close()`, `.onmessage=`, `.addEventListener(...)`) special-cased in the emitter the same way `Response`'s `.text()`/`.json()` are today.

### Listener storage and dispatch: reuse EventEmitter's C helpers directly, bypass its Go-level generic wrapper

One per-instance `Map<string,ptr>` (via `__kml_map_str_*`, exactly as `EventEmitter<T>` already uses), each value a `__kml_ee_list` (`runtime_eventemitter.go:3-16`) — `.addEventListener(type, cb)`/`.removeEventListener(type, cb)` call the existing `__kml_ee_list_push`/`_remove` helpers directly, no new C code needed there at all. `.onmessage`/`.onopen`/`.onerror` are property-assignment sugar that install (replacing any prior value — these are single-slot properties, not accumulating listener lists, matching the real spec) into the same map under fixed keys `"message"`/`"open"`/`"error"`; the event-loop scan's dispatch step doesn't need to know or care which form registered a listener, it just looks up by event-type string and calls whatever's there — one dispatch mechanism, two registration surfaces. Dispatch itself is a direct call loop exactly like `emitEventEmitterEmit`'s (`emit_eventemitter.go:329`, snapshot-copy the list, call each listener via `emitCBCall`) but **without** its "`'error'` with no listener throws" special case — an `EventSource` with no `onerror` registered and a dropped connection simply does nothing observable beyond the `readyState` transition to `CLOSED`, matching real `EventSource` (which never throws from a background connection failure).

### Message payload: a fixed concrete struct, no generics needed

Every dispatched listener receives one argument of a single, fixed shape — `{ data: string, type: string, lastEventId: string }` — regardless of user code, since (unlike `EventEmitter<T>`) there's no user-chosen payload type here at all. This is simpler than `EventEmitter<T>`'s own machinery in exactly this one respect: no `resolveEventEmitterListenerArg`-style type inference/constraint-checking needed, just a plain, always-the-same `ObjectType`.

### `.close()`

`curl_multi_remove_handle` + `curl_easy_cleanup` on the entry's easy handle (the same pair `docs/status/README.md`'s Roadmap already floated as viable for a `fetch`-specific `AbortController`, confirming it's a real, already-relied-upon libcurl pattern rather than a new one), then `state = CLOSED`. The array slot itself is never compacted/removed — same "grow-only array, dead entries marked not active" shape `@__kml_conn_active`'s counter-based tracking already uses for the connection-fiber array — so the event-loop scan's own iteration just skips `CLOSED` entries rather than needing a real removal.

## Staging

Matches this project's existing convention for a feature with real internal phases (RegExp, [TDD-00035](TDD-00035.md); `TextDecoder`, [TDD-00034](TDD-00034.md)) — ship a narrow, useful slice first rather than one large change.

- **Stage 0 — connection plumbing, no dispatch yet.** `new EventSource(url)`: curl easy-handle setup + `multi_add_handle` (reusing `fetch`'s existing global multi handle), the new EventSource array + event-loop scan skeleton (advances `consumedOffset` fully across all received bytes with no parsing — i.e. discards data, proving the keep-alive/scan/close wiring end-to-end in isolation before layering SSE parsing on top), `.readyState` (`CONNECTING`→`OPEN` once the transfer's headers are received — libcurl's write callback firing at all is a sufficient, simple proxy for "connected"), `.close()`, event-loop keep-alive integration. Deliberately foundational-only: nothing observable except `readyState` transitions, so a bug here can't be confused with a parsing bug in Stage 1.
- **Stage 1 — SSE record parsing + the default `message` event.** The `\n\n`-delimited record parser (`data:`/`event:`/`id:`/`retry:` fields, comment lines, multi-line `data:` concatenation per spec), `.onmessage`, unnamed (no `event:` field, defaulting to type `"message"`) record dispatch.
- **Stage 2 — named custom events + lifecycle properties.** `.addEventListener(type, cb)`/`.removeEventListener(type, cb)` for a server-sent `event: foo` field, `.onopen` (fires on the `CONNECTING`→`OPEN` transition), `.onerror` (fires, does not throw-if-unlistened, on a dropped/failed transfer).
- **Stage 3 — CRLF-tolerant boundaries, terminal vs. retryable failure, and auto-reconnect.** Closes all three gaps Stages 0-2 left open (see the former Open Questions below, now resolved here). Three sub-parts, designed together since the third depends on the second's terminal/retryable distinction:

  1. **CRLF-tolerant record boundaries.** `__kml_eventsource_process_available`'s boundary search (previously a single literal `"\n\n"` `strstr`) now runs three `strstr` searches per iteration — `"\n\n"`, `"\r\n\r\n"`, `"\r\r"` — and picks whichever match starts earliest in the unconsumed tail. The three patterns can never spuriously overlap (no two of them share a substring relationship: `"\r\n\r\n"` contains neither two adjacent `\n`s nor two adjacent `\r`s), so "earliest wins" is unambiguous and, unlike a single fixed delimiter, correctly handles even a stream that varies its line-ending style record-to-record. The extracted record body is then passed through a new `__kml_es_normalize_record(ptr raw, i64 rawlen)` helper — a two-pointer in-place-into-a-copy scan converting every `\r\n` or lone `\r` to `\n` — before handing it to the existing, unchanged `__kml_eventsource_dispatch_record` (which still splits on plain `\n`). This isn't just cosmetic: the real SSE stream-decoding algorithm defines line-splitting at the byte level as "terminated by `\r`, `\n`, or `\r\n`" with no escaping mechanism, so treating every one of those sequences as a line terminator (including one that happens to appear mid-value) is spec-correct, not an approximation.
  2. **Non-2xx / wrong `Content-Type` is a terminal failure, not a retryable one.** Investigated the real spec's own algorithm (WHATWG HTML's "Fetching the event source") before designing this: it draws a hard line between a *network-level* failure (DNS/connection-refused/mid-stream drop — reestablish the connection, i.e. retry) and a response that *arrived* but had the wrong shape (status ≠ 200, or `Content-Type` isn't `text/event-stream` — fail the connection, permanently, no retry). Getting this backwards (retrying a 404 forever) is a real, plausible bug shape, not a hypothetical — worth calling out since it inverts the naive "any failure should retry" framing this document almost shipped with. Status is read via `curl_easy_getinfo(CURLINFO_RESPONSE_CODE)` in `__kml_eventsource_scan`'s `checkstatus` step, but *only* while the transfer is still live (`pending->done == 0`) — once done, `__kml_curl_drain_messages` (`runtime_fetch.go`) has already `curl_multi_remove_handle`+`curl_easy_cleanup`'d the easy handle, and re-querying it would be a use-after-free, not just stale data. `checkstatus` branches on `pending->done` first and, when already done, reads the status `__kml_curl_drain_messages` itself already safely captured into `pending->status` *before* cleanup (the exact mechanism fetch's own async path already relies on) instead of re-touching the freed handle. Content-Type needed the same treatment but has no such safe post-cleanup source — fetch's pending struct only ever captures status, not Content-Type, and extending that *shared* 40-byte struct (also used by every plain `fetch()`) felt like too much blast radius for what turned out to be avoidable. Instead, Stage 3 adds a dedicated `CURLOPT_HEADERFUNCTION` callback (`__kml_eventsource_header_cb`, `CURLOPT_HEADERDATA` = the KML-level `es_entry` pointer itself) that captures a `Content-Type:` line into the entry's own `contentType` field as soon as libcurl parses it — which happens strictly before the body write callback ever runs, and therefore strictly before the transfer can possibly finish and get cleaned up, regardless of how small/fast the response is. `checkct` (only reached once status is confirmed 2xx) just reads `ent->contentType` directly — always safe, since it's this file's own heap allocation, not libcurl's, so there's no liveness question at all. A `null` (never-seen) `Content-Type` is treated leniently (proceeds as if valid) rather than failing — real minimal test servers/backends often skip it. A non-null value that isn't a `"text/event-stream"` prefix match (`strncmp`, case-sensitive — a documented narrowing) joins a bad status in the terminal path: tear down the easy handle (only if `pending->done` is still 0 — already torn down otherwise), `state`/`readyState` → `CLOSED`, `onerror` fires once, `@__kml_es_active` decrements, no reconnect ever scheduled. **A bug found during this exact implementation, not just a hypothetical avoided:** an earlier version of this design tried to read Content-Type live via `curl_easy_getinfo(CURLINFO_CONTENT_TYPE)` from `checkstatus` too, falling back to "assume OK, proceed to OPEN" whenever the transfer had already completed by the time the scan looked (the same race `checkstatus` itself has to guard against for status). That fallback is what the header-callback redesign above replaced — but before it was replaced, `TestE2EEventSourceWrongContentTypeEndsClosedNoRetry` (a 200 response with a small, ~18-byte `text/plain` body — small enough to always finish inside a single `curl_multi_perform` call, so the race triggered *every* time, not rarely) hung indefinitely: "assume OK" opened the connection, the very next scan noticed the already-ended transfer and treated it as a normal drop-while-open (retryable per sub-part 3), and reconnecting to the same permanently-misconfigured URL hit the identical race on every attempt — an infinite reconnect loop against a dead endpoint, not a crash, so easy to miss without an end-to-end test that actually waits for process exit. Caught immediately by that test hanging under `go test`; the header-callback redesign closes the race at its root rather than picking a better fallback for it.
  3. **Auto-reconnect** (retry after a dropped connection or network-level connect failure, honoring a server-sent `retry:` value, replaying `Last-Event-ID` as a request header on reconnect). No fiber-parking or the general-purpose `setTimeout` timer queue involved (deliberately — reconnecting is pure runtime bookkeeping, not user-visible KML code, so wrapping it in a KML closure just to hand it to `__kml_timer_schedule` would be indirection with no payoff): a new `reconnectAtMs` field on the `es_entry` runtime struct (`ptr pending, ptr instance, i64 consumedOffset, i64 state, ptr listeners, ptr url, i64 retryMs, i64 reconnectAtMs, ptr contentType` — 9 fields, 72 bytes, up from Stage 0's 5-field/40-byte struct; `contentType` is sub-part 2's own field, described there) holds an absolute deadline in milliseconds off a dedicated `__kml_eventsource_now_ms()` helper (`clock_gettime(CLOCK_MONOTONIC, ...)`, the same clock source `emit_timers.go`'s own `__kml_monotonic_ns` and `emit_date.go`'s `performance.now()` already use, but declared standalone here via `ensureClockGettime()` directly rather than pulling in the whole timer-queue subsystem for an unrelated purpose). `reconnectAtMs == 0` means "has a live in-flight transfer right now" (the Stage 0-2 steady state); nonzero means "waiting to reconnect, no live easy handle currently exists" — this single field is the whole state machine, checked first thing in the scan's per-entry body (ahead of the existing `CONNECTING`/`OPEN` dispatch). When a scan finds a waiting entry whose deadline has passed, it rebuilds the connection via a new `__kml_eventsource_connect(ptr url, ptr headers, ptr es_entry) -> ptr pending` helper — factored out of what Stage 0's `__kml_eventsource_open` used to do inline, now shared by both the original connect and every reconnect (the `es_entry` parameter exists solely to hand libcurl as `CURLOPT_HEADERDATA` for sub-part 2's header callback; `__kml_eventsource_open` now allocates the entry *before* connecting, a reordering from Stage 0-2, specifically so a valid entry pointer exists to pass in) — passing a `curl_slist` built from `"Last-Event-ID: " + instance.lastEventId` when that field is non-empty (reusing `ensureCurlSlist`'s `curl_slist_append`, the same mechanism `fetch(url, init)`'s custom-headers support already established), resets `consumedOffset` and `contentType`, and clears `reconnectAtMs`. The retry delay itself defaults to 3000ms (matching the real spec's own default) and is overridable per-connection by a `retry:` field in any dispatched record — `__kml_eventsource_dispatch_record` (previously parsing-but-discarding `retry:`, per Stage 1/2's own comment) now `atoll`s its value into the entry's `retryMs` field. Reconnect is scheduled from two triggers, both landing in one shared `doReconnectSchedule` block: (a) a mid-stream drop while `OPEN` (`pending->done` becomes true after a successful open — the old Stage 0-2 behavior of going straight to permanent `CLOSED` here was itself the documented gap this stage closes) and (b) a network-level connect failure while still `CONNECTING` (`pending->done` becomes true *without* a response status ever having become available — see sub-part 2's live-vs-done status split, which is what makes this distinguishable from a same-iteration terminal failure). Both set `readyState` back to `CONNECTING` (0) — matching the real spec, which never surfaces the retry wait as `CLOSED` — fire one `error` event, and leave `@__kml_es_active` untouched (an entry waiting to reconnect is still "work outstanding" for the event loop's keep-alive check, exactly like a live transfer). `.close()` during the wait (checked via the same `reconnectAtMs != 0` test) skips the now-meaningless curl teardown (there is no live easy handle to tear down) and just marks `CLOSED` + decrements `@__kml_es_active` directly — the one place `__kml_eventsource_close` needed to branch on the new field at all.

## Open questions

- ~~Auto-reconnect (`retry:`, `Last-Event-ID` replay).~~ Resolved: designed and implemented in Stage 3 above.
- **Unbounded per-connection buffer growth.** The response accumulator (`buf`) never shrinks or compacts as records are consumed — for a long-lived `EventSource` (the microservice use case this project's `CLAUDE.md` cares about most, potentially open for hours/days), this means steady memory growth proportional to total bytes ever received, not just unconsumed bytes. Given this project's existing, already-honest posture on memory (`manual` mode never frees by default; see `docs/status/MEMORY-MANAGEMENT.md`), leaning toward accepting this as a known, documented cost rather than adding buffer-compaction complexity (`memmove` the unconsumed tail to offset 0 once consumed bytes cross some threshold). Still unresolved even after Stage 3 — auto-reconnect gives a long-lived `EventSource` a natural buffer-reset point for free (a reconnect always starts a brand new `buf` via `__kml_eventsource_connect`, so growth is now bounded *per connection attempt*, not truly unbounded for a program that stays on one connection for its whole lifetime) — worth a second look if a single, never-dropped connection open for days in practice turns out to matter, but not addressed further here.
- ~~Exact record-boundary scanning algorithm.~~ Resolved twice: first for bare-LF-only in [ADR-00123](../adr/ADR-00123.md) (realloc-safe by construction — the buffer's data pointer/length are reloaded fresh on every call, nothing ever caches a raw pointer into the accumulator across two separate calls), then extended to also accept `"\r\n\r\n"`/`"\r\r"` in Stage 3 above (same realloc-safety property preserved — the three-way `strstr` search still only ever reads from a pointer/length pair loaded once at the top of the current call).
- ~~Does a non-2xx HTTP response fire `onerror` immediately, or only once/if the transfer itself fails at the libcurl level? Status-code-only vs. also `Content-Type`-sniffing?~~ Resolved in Stage 3 above: checked as soon as response headers arrive (not gated on the transfer completing), both status-code (`[200,300)`) and `Content-Type` (`text/event-stream` prefix, when present) are checked, and either failing is terminal (no reconnect) per the real spec's own "fail the connection" step.
