# ADR-01052: `finished(readable)` follows the stream's `'end'`

- **Relations**: `Extends ADR-01050`; `Implements TDD-00097` (Stage 8, corrected)
- **Date**: 2026-09-21

## Context

`examples/streams/node_stream.ts` changed its output once its top level became a coroutine
([ADR-01050](ADR-01050.md)). Reduced:

```ts
import { Readable } from 'stream';
import { finished } from 'stream/promises';
const words = Readable.from(["kalimera", "kosme"]);
words.on("data", (w) => { console.log("word:", w); });
words.once("end", () => { console.log("all words delivered"); });
await finished(words);
console.log("after finished");
```

Node: both words, `all words delivered`, `after finished`. On the task path: `word: kalimera`, `after finished`,
`word: kosme`, …, `all words delivered` last. The same program wrapped in an `async function` printed the wrong order
with the previous compiler too — the defect predates the module task; the main-stack wait merely hid it at top level
by noticing the settle a loop turn late.

## Investigation

`emitStreamPromisesCall` / `emitStreamModuleCall` (`emit_node_stream.go`) returned the inner WHATWG readable's
*closed* promise (rstream field 16). That settles when the closed source's queue drains — on the read that hands out
the last chunk — which for a flowing Node stream is one read *before* the flow loop (`@__kml_ns_flow_onread`) sees
`done` and emits `'end'`/`'close'`. Node's `finished()` is an `'end'`/`'close'` listener: it completes after every
`'data'` and after every `'end'` listener registered before it.

## Decision

The Node stream wrapper's reserved field 9 becomes `finishedProm`, created lazily by
`@__kml_ns_finished_prom(n, closed)`:

- already ended → fulfilled at once;
- otherwise a reaction on the closed promise: rejected → reject with the same reason; fulfilled while the stream is
  flowing or paused and has not emitted `'end'` → leave it to the flow loop; fulfilled on a stream that never flowed
  (consumed by a pipe or a reader) → fulfil;
- the flow loop's `ended` block fulfils it after emitting `'end'` and `'close'`.

`finished()` (promise and callback forms) uses it for a Readable. A Writable keeps its closed promise, which already
is its `'finish'`; `pipeline()` is unchanged.

A Duplex/Transform has both sides, and Node's `finished()` waits for both. It used to get the writable side's closed
promise only — `TestE2ENodeStreamClassExtendsDuplex` (`d.end(); await finished(d); console.log(out)`) passed on the
main-stack wait by the same accident and printed an empty `read:` line on the task path. `@__kml_ns_finished_both(a,
b)` returns a promise fulfilled once the readable side's finished promise and the writable side's closed promise both
are, rejected with whichever rejects first.

`examples/streams/node_stream.ts` prints Node's order. Broader runs: see the session's final pass.
