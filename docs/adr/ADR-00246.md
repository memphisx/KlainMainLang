# ADR-00246: Presence-aware logical compound assignment on a nullable-scalar field

- **Relations**: `Implements TDD-00064` (closes the [ADR-00199](ADR-00199.md) "Side effects discovered" remainder)
- **Date**: 2026-08-19

## Context

[ADR-00199](ADR-00199.md) gave nullable non-pointer scalars (`number | null`,
`boolean | null`, ...) a presence-flagged `{ i1, T }` representation across
locals, parameters, return values, object/interface/class fields, and Maps. It
left one niche gap, recorded in its own "Side effects discovered": a **logical
compound assignment** (`??=` / `&&=` / `||=`) on a nullable-scalar *field* was
not routed through the presence path. Every non-field form (including the plain
`=` into such a field, and all three operators on a *local*) worked.

The symptom was a silent no-op: `b.v ??= 5` where `v: number | null` and `b.v`
is currently `null` left the field `null` instead of assigning `5` — confirmed
reproducing 2026-08-19.

## Investigation

Field `obj.f OP= rhs` is emitted in `emitAssign` (`emit_exprs_assign.go`): after
computing the field's `getelementptr`, a logical-assign op was dispatched
straight to the storage-generic `emitLogicalCompoundAssign(op, gepReg, fieldTy,
rhs)`. That helper `load`s the whole slot as a single `fieldTy.IR` value and, for
`??=`, takes its `ty.IR != "ptr"` fast path — "a non-pointer left can never be
null, so never store." For a nullable-scalar field `fieldTy.IR` is the `{ i1, T
}` aggregate, not `ptr`, so the fast path fired and `??=` became a no-op; `&&=` /
`||=` keyed truthiness off the whole aggregate bit pattern rather than the
payload. The generic helper is correct for every genuinely-single-value lvalue
(bare scalar, array element, static field, plain object field) — it simply has no
concept of the two-part presence-flagged slot.

The local case already had a dedicated path,
`emitNullableScalarNullishOrLogicalAssign` (`emit_nullable_scalar.go`), driving
the store off the presence bit for `??=` and off the payload's truthiness for
`&&=` / `||=`. Its only dependence on the local was `sym.Ptr` / `sym.Ty`, and its
low-level helpers (`loadNullableScalarPresent` / `loadNullableScalarPayload` /
`storeNullableScalarPresent`) already take a raw `ptr` — a field `getelementptr`
addresses the identical `{ i1, T }` layout.

## Decision

Extract the storage-generic core `emitNullableScalarNullishOrLogicalAssignAt(ptr,
ty, op, rhsExpr)` from the local helper (which now delegates to it), and route the
field path to it whenever `isNullableScalar(fieldTy)`:

```go
if isLogicalAssignOp(ex.Op) {
    if isNullableScalar(fieldTy) {
        return e.emitNullableScalarNullishOrLogicalAssignAt(gepReg, fieldTy, ex.Op, ex.Right)
    }
    return e.emitLogicalCompoundAssign(ex.Op, gepReg, fieldTy, ex.Right)
}
```

`??=` now stores exactly when the field's presence bit is false; `&&=` / `||=`
key off the payload's truthiness (a null's payload is its zero, hence falsy),
matching the local semantics and real JS. The right side is still evaluated only
down the branch that actually stores. Every non-nullable field keeps the generic
path unchanged.

## Consequences

- `obj.n ??= v` on a nullable-scalar field fires exactly when the field is
  absent; a present value (including a present `0` / `false`) is preserved.
- No new representation or ABI change — this is a dispatch fix reusing the
  Stage-3 field slot and the local operator's own branch logic.
- The array-element / static-field logical-assign paths still use the generic
  helper; a nullable-scalar element type there is a pre-existing, separate
  boundary (nullable scalars aren't yet supported nested inside an array), not
  regressed by this change.
