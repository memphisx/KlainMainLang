# TDD-00105: Node `cluster` module

- **Status**: Partially Implemented
- **Date**: 2026-08-23

## Context

`cluster` is one of the last unstarted Node core modules. It was assessed as
"closer than stated" because a fork + shared-listen-socket + worker-id
machinery already ships for `http.listen({ workers: N })`. On closer inspection
that machinery implements a *different* clustering model than Node's `cluster`
API exposes, so `cluster.fork()` needs its own mechanism. This document settles
which model to build.

## Design

### The two clustering models

**A. Existing shared-fd auto-fork** (`__kml_http_cluster_fork`, runtime_http.go).
`http.listen(port, handler, { workers: N })` binds the port **once** in the
parent, then forks `N-1` children *after* the bind. Every process — parent
(worker id 0) and children (ids 1..N-1) — inherits the one `listenfd` and
`accept()`s on it. All peers serve equally; the "primary" is just a label. The
fork happens at a fiber-free point (right after bind, before any connection
`ucontext_t` state), which the design requires. `cluster.isPrimary`/`workerId`
already read the child-assigned `@__kml_cluster_worker_id` global.

**B. Node's `cluster` idiom.**
```ts
if (cluster.isPrimary) { for (…) cluster.fork(); }
else { http.listen(port, handler); }
```
Node's primary **does not serve** — it forks workers and supervises. Each worker
runs the entry file from the top with `isWorker` true and independently
`listen(port)`s (real Node passes the fd from the primary; the observable
contract is "each worker calls listen and they share the port"). A native
`fork()` cannot reproduce this directly: the child resumes right after the
`fork()` call, so a child of `cluster.fork()` would re-enter the primary's `for`
loop and fork-bomb.

### Decision — model B via fork + re-exec-self, unified with model A's id global

`cluster.fork()` = `fork()`; in the child, **`execv` the current executable**
with an environment marker `KML_CLUSTER_WORKER_ID=<n>` set. The re-exec'd worker
runs `main()` from the top with fresh state (satisfying the fiber-free-fork
constraint for free — the child image is replaced before any fiber exists) and,
critically, does **not** resume inside the primary's `for` loop — mirroring
Node's "worker runs the file from the top" semantics and avoiding the fork bomb.

Worker identity is unified with model A: at program startup the runtime reads
`KML_CLUSTER_WORKER_ID` into the existing `@__kml_cluster_worker_id` global, so
`cluster.isPrimary` = `(id == 0)` keeps working unchanged for **both** models —
model A children set the global directly in the fork loop; model B workers seed
it from the env at startup. A program uses one model or the other, never both.

Independent per-worker `listen(port)` needs `SO_REUSEPORT` (multiple processes
binding the same port); model A never needed it because it shares one fd. Add
`SO_REUSEPORT` to the http/net bind path (alongside the existing
`SO_REUSEADDR`), guarded by platform constants like `httpSockConstants`.

Self-executable path: Linux `readlink("/proc/self/exe")`, Darwin
`_NSGetExecutablePath`. Fall back to `argv[0]` only if those are unavailable
(argv[0] breaks under a changed cwd, so it is the last resort).

### V1 surface

- `cluster.isPrimary` (exists), `cluster.isWorker` (new; `= !isPrimary`).
- `cluster.fork()` → a `Worker` handle exposing `.id` and `.process.pid`;
  forks + re-execs self with the next worker id (1, 2, …). Returns in the
  primary; the worker never returns from it (it re-execs).
- `cluster.on('exit', (worker, code) => …)` — optional; the primary reaps
  workers via `waitpid` folded into… (see Open questions). May defer to V2.
- Startup env seed of `@__kml_cluster_worker_id`.
- `SO_REUSEPORT` on the server bind so workers can each `listen(port)`.

Out of scope for V1: IPC / `worker.send()` / message passing between primary and
workers (no channel exists — the http auto-fork model also has none, HTTP-SERVER
Known Limitations), `cluster.schedulingPolicy`, `cluster.settings`,
`worker.disconnect()`/graceful shutdown, `'online'`/`'listening'`/`'message'`
events.

## Open questions

- **`cluster.on('exit')` in V1 or V2?** Reaping workers requires the primary to
  `waitpid` — but the primary typically has no event loop of its own (it just
  forks and ends). A blocking `waitpid` loop at program end, or folding child
  pids into the existing select() loop, are both options. Leaning V2 unless a
  test needs it, to keep V1 to the fork+identity+bind core.
- **Darwin `SO_REUSEPORT` load-balancing.** Linux `SO_REUSEPORT` kernel-load-
  balances accepts across listeners; Darwin's distribution semantics differ
  (may favor the last binder). Acceptable for V1 (correctness, not even
  balancing); note as a caveat and verify on the machine.
- **Primary lifetime.** If the primary forks workers then reaches end of
  `main()` and exits, workers are reparented to init and keep serving. Node's
  primary stays alive. V1 may leave the primary to exit (documented) or add a
  `waitpid`-all at program end when `cluster.fork()` was used.
