# ADR-00197: Reject numeric separators in legacy-octal / non-octal-decimal literals

- **Relations**: Extends [ADR-00085](ADR-00085.md) (numeric separators); surfaced by [ADR-00195](ADR-00195.md)'s report breakdown
- **Date**: 2026-08-13

## Context

The lexer accepted `0_0`, `08_0`, `00_0`, `0_9` and similar — a numeric
separator inside a literal that begins with a leading `0` directly followed by
another digit (a LegacyOctalIntegerLiteral or NonOctalDecimalIntegerLiteral).
Real JS makes these a `SyntaxError` **unconditionally** (not only under strict
mode): a `0`-prefixed integer literal may not contain a `NumericLiteralSeparator`.
Worse, the compiler didn't just accept them, it evaluated them nonsensically —
`08_0` read as `80`.

Found by mining the enriched conformance report's "wrongly-accepted" phase
([ADR-00195](ADR-00195.md)): `language/literals/numeric` had a cluster of
`negative: phase: parse` tests we compiled instead of rejecting. Most of that
directory needs a strict-mode context this compiler doesn't have (bare `010`,
`08` are only errors under `"use strict"`), but the separator-in-leading-zero
cases are unconditional and self-contained.

## Decision

In `lexer.readNumber`'s decimal path, compute `legacyLeadingZero` once — true
when the literal starts with `0` and the next character is a decimal digit or
`_` — and reject any `_` encountered while it holds, with a clear error. Every
other separator position keeps its existing "must be between two digits" rule.

Deliberately *not* addressed here: legacy-octal **value** semantics (`010`
still reads as decimal `10`, not octal `8`) and the strict-mode-only errors for
`010`/`08` without a separator — both need machinery (Annex B octal evaluation,
a strict-mode parser context) far larger than this narrow, unconditional rule.

## Implementation notes

- Files touched: `lexer/lexer.go`.
- The `0x`/`0b`/`0o`-prefixed paths return before this code, so hex/binary/octal
  separators (`0x1_F`) are unaffected; `0.5_5` and `1_000` keep working because
  the leading char is `0.`-then-`.` (not a digit) or a non-zero digit
  respectively.

## Verification

- Linux (x86-64). `go build`, `go vet ./...`, `go test ./...` all pass.
- New lexer-level test in `tests/exprs_test.go`
  (`TestE2ENumericSeparatorInLegacyLeadingZeroIsError`): `0_0`, `08_0`, `0_9`,
  `00_0` rejected; `1_000`, `0.5_5`, `0`, `0x1_F` still parse.
- Conformance: the `language/literals/numeric` separator-in-leading-zero
  negatives (`numeric-separator-literal-*-err`, ~11 files) now correctly reject.
