# Networking

> Part of the [Implementation Status](README.md) index. All require linking a network library (libcurl for fetch/HTTP; system sockets for WebSocket). A server-side HTTP listener (`http.listen(port, handler)`) is tracked under [HTTP-SERVER.md](HTTP-SERVER.md) instead — listening for incoming connections has no browser-side Web API equivalent.

**Coverage**: ~67% (4/6).

**Caveats**: No real `Request`/`Headers` classes — `fetch(url, init)`'s `init` is a plain object with `method`/`headers`/`body` fields instead, `headers` a `Map<string,string>`. `XMLHttpRequest` isn't implemented. `WebSocket` has no binary `.send()`, no `wss://`/TLS, and the client's `new WebSocket(url)` connects synchronously (see the `WebSocket` row below). `EventSource`'s `Content-Type` check on connect is a case-sensitive `"text/event-stream"` prefix match, and a `retry:`-driven reconnect always replays the *full* stored `Last-Event-ID`, not a per-listener value (see the `EventSource` row below). `.text()`/`.json()` stay `strlen`-based by design (fine for JSON/text, which aren't expected to contain embedded nulls) — use `.arrayBuffer()` for binary bodies, see Known Limitations below.

| API | Status | Notes |
|---|---|---|
| `fetch(url)` / `fetch(url, init)` | ✅ | `init` is any value with some subset of `method: string` / `headers: Map<string,string>` / `body: string` fields — no `Request`/`Headers` classes, matching how this compiler already represents every other bag of string headers (`http.listen`'s `req.headers`, a handler's own optional response `headers` field) as a plain `Map<string,string>` ([ADR-00074](../adr/ADR-00074.md)/[TDD-00017](../tdd/TDD-00017.md)). Setting a `body` without an explicit `method` sends it as `POST` (real, confirmed libcurl behavior — `CURLOPT_POSTFIELDS` implies `POST` unless overridden); an explicit `method` always wins over that default. Real non-blocking I/O since [ADR-00050](../adr/ADR-00050.md): uses libcurl's multi-interface, driven by the same `select()`-based event loop `http.listen` uses, so `await fetch(...)` yields instead of blocking when called from inside a connection-handler fiber — one slow upstream call no longer freezes every other connection or timer. Outside any fiber (plain top-level code, no `http.listen`), there's nothing else to overlap with, so it busy-spins the same multi-interface calls to the same effect as a blocking wait. A network-level failure (DNS, connection refused, TLS, timeout) throws; a non-2xx HTTP status still resolves normally (`.ok` distinguishes it), matching real `fetch`. See [ADR-00021](../adr/ADR-00021.md) (original V1), [ADR-00050](../adr/ADR-00050.md) (non-blocking rework), [ADR-00052](../adr/ADR-00052.md) (fixed a real stack-overflow crash in the busy-spin path, confirmed via a slow-endpoint repro), and [ADR-00074](../adr/ADR-00074.md) (custom method/headers/body). |
| `Response` (`.status`, `.ok`, `.body`, `.text()`, `.json()`, `.arrayBuffer()`) | ✅ | Plain object with `status`/`ok`/`body` fields (readable directly, not hidden) plus `text()`/`json()`/`arrayBuffer()` methods. `.json()` reuses `JSON.parse`'s existing machinery, including its scope (flat objects with primitive fields only — nested JSON fields aren't supported yet, same as bare `JSON.parse`). `.text()`/`.json()` are plain null-terminated strings: a binary body with an embedded null byte truncates at the first one through them, by design — for a binary body, use `.arrayBuffer()` ([ADR-00094](../adr/ADR-00094.md)) instead, which carries the real byte count and comes back whole regardless of content. See [ADR-00021](../adr/ADR-00021.md) (original V1), [ADR-00094](../adr/ADR-00094.md) (`.arrayBuffer()`). |
| `Request` / `Headers` objects | ❌ | No real `Request`/`Headers` classes — but custom method/headers/body are covered without them: `fetch(url, init)`'s `init` is a plain object with `method`/`headers`/`body` fields, `headers` being a `Map<string,string>` ([ADR-00074](../adr/ADR-00074.md)/[TDD-00017](../tdd/TDD-00017.md)). Deliberately scoped this way — see the `fetch(url)` row above |
| `WebSocket` | ✅ | Both server and client. Server: `http.listen(port, handler, { ws })`'s optional third-argument handler is called once per successfully upgraded connection with a `WSConnection` (`.onmessage`/`.send(data: string)`/`.close()`), coexisting with ordinary HTTP requests on the same listener; a client `ping` gets an automatic `pong` reply with identical payload (RFC 6455 §5.5.2), and both a peer `close` frame and `.close()` itself send a proper Close frame before the connection ends (RFC 6455 §5.5.1). Client: `new WebSocket(url)` (`ws://` only — `wss://` throws immediately) performs its connect + handshake *synchronously*, before the constructor returns, so `.onopen`/`.onerror` are deliberately deferred to the first event-loop pass after construction (giving assignment code a chance to run first) rather than fired inline; a failed connect never throws (`.onerror`/`.onclose` fire instead, matching real `WebSocket`). Neither side supports binary `.send()` (`ArrayBuffer` payloads) yet, and `.close()` on either side doesn't wait for the peer's own echo back before actually closing — deliberate simplifications, not oversights. See [TDD-00039](../tdd/TDD-00039.md) ([ADR-00125](../adr/ADR-00125.md) Stage 0 frame codec/SHA-1, [ADR-00126](../adr/ADR-00126.md) Stage 1 server handshake, [ADR-00127](../adr/ADR-00127.md) Stage 2 ping/pong + close handshake, [ADR-00128](../adr/ADR-00128.md) Stage 3 client). |
| `EventSource` | ✅ | Server-sent events (SSE) over HTTP — connection plumbing (`readyState`/`close()`), `onmessage`/`onopen`/`onerror`, `addEventListener`/`removeEventListener` for named (`event: name`) records (`data`/`event`/`id`/`retry` field parsing, multi-line `data:` concatenation), `\n\n`/`\r\n\r\n`/bare-`\r\r` record boundaries, and auto-reconnect (retries after a dropped connection or network-level connect failure, honoring a server-sent `retry:` delay — default 3000ms — and replaying `Last-Event-ID` as a request header) all work. A response that *arrives* with the wrong shape (non-2xx status, or a 2xx with a `Content-Type` that isn't `text/event-stream`) fails permanently instead of retrying, matching the real spec's distinction between a network failure (retryable) and a malformed response (terminal). See [TDD-00038](../tdd/TDD-00038.md). |
| `XMLHttpRequest` | ❌ | Legacy HTTP; lower priority than `fetch` |

## Known Limitations

| Limitation | Notes |
|---|---|
| `.text()`/`.json()` still truncate a body at an embedded null byte | Deliberate, not a bug: every string in this compiler is a plain null-terminated C string (`.length` is `strlen`-based), so *any* string value with an embedded `\0` reads as shorter than it actually is. `.text()`/`.json()` keep that behavior by design (JSON/text bodies aren't expected to legitimately contain embedded nulls) — use `.arrayBuffer()` (see the `Response` row above) for a binary body, which carries the real byte count and comes back whole. Originally confirmed via `httpbin.org/bytes/50000` coming back as a 383-byte string through `.text()`; fixed for the binary case by [ADR-00094](../adr/ADR-00094.md) now that `ArrayBuffer`/`TypedArrays` exist (see [BINARY-DATA-TYPED-ARRAYS.md](BINARY-DATA-TYPED-ARRAYS.md)). |
