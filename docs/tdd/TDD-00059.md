# TDD-00059: Tagged template literals

- **Status**: Implemented (see [ADR-00151](../adr/ADR-00151.md))
- **Date**: 2026-08-10

## Context

`` tag`Hello ${name}` `` — a template literal immediately preceded by a callable expression — desugars in real JS/TS to a function call: the tag function receives an array of the literal string segments as its first argument, followed by each interpolated expression's evaluated value as the remaining arguments (`` tag`a${x}b${y}c` `` ≈ `tag(["a","b","c"], x, y)`). Confirmed absent from this compiler by two independent prior audits (`docs/status/LANGUAGE-CONSTRUCTS.md`'s row 19, `docs/adr/ADR-00028.md`'s Context, which punted `String.raw` on exactly this gap) — no `TaggedTemplate` AST node, no parser handling, `` foo`bar` `` today parses `foo` as a complete expression and then chokes on the orphaned template token at whatever comes next.

Traced against the source before designing: the pieces this needs turn out to already mostly exist, just not wired together for this one syntactic shape (see Design). The one deliberate scope cut, decided directly rather than left open: **no `.raw` property on the `strings` array** — this compiler's arrays are fixed-shape heap structs with no room for an extra property (`docs/status/README.md`'s "Opt-in dynamic property add/delete on objects" gap, structurally the same constraint), and [ADR-00028](../adr/ADR-00028.md) already scoped real `String.raw` as its own, separate, meaningfully larger feature. A tag function that reads `strings.raw` gets the same clean "field not found" error any other array's nonexistent property already produces.

## Design

### Desugaring, not new codegen

A tagged template call is exactly a normal function call whose first argument is a compile-time-known array of the cooked string segments and whose remaining arguments are the interpolated expressions, evaluated and passed through completely untouched (no implicit stringification the way a *plain* template literal's own interpolation already does via `emitValueToString` — a tag function receives real typed values, that's the entire point of the feature). Given that, the implementation is a thin syntactic layer over machinery that already exists and needs no changes:

- `emitArrayLiteralAggregate` (`codegen/llvm/emit_arrays_core.go:301`) already turns an `*ast.ArrayLiteral` of string literals into a real `{ptr,i64}` array value — reused unmodified for the `strings` argument by literally constructing one (`ast.NewArrayLiteral` of `ast.NewStringLiteral` quasis) at codegen time.
- `emitCallToFuncSig`'s existing rest-parameter packing (`emit_call.go:928`) already mallocs a buffer and packs N trailing call arguments — reused unmodified for `...values` by literally constructing an `*ast.CallExpression` (`ast.NewCallExpression`) whose `Args` are `[quasisArrayLiteral, expr1, expr2, ...]` and dispatching through the *existing* `emitCall` entirely as-is.

So a `*ast.TaggedTemplateExpression` (new AST node, added for the reasons below) is handled by exactly one small piece of new logic, `desugarTaggedTemplate(tt) *ast.CallExpression`, called from both `emitExpr`'s new case (`return e.emitCall(e.desugarTaggedTemplate(ex))`) and `inferExprType`'s new case (`return e.inferExprType(e.desugarTaggedTemplate(ex))`) — every existing call-dispatch behavior (named function, closure variable, class method tag, generic function tag, per-argument coercion/type-checking, the rest-param element-type check) applies automatically, with zero new type-checking or coercion code. A tag function declared with the wrong `strings` parameter type (not `string[]`) or a rest element type that doesn't accept one of the interpolated expressions fails with exactly the same error an equivalent hand-written `tag(["a","b"], x)` call would — no special-cased diagnostics needed or added.

### Why a real AST node instead of desugaring in the parser

Considered desugaring straight to `*ast.CallExpression` inside the parser, needing zero codegen changes at all (not even the two new `case` arms above). Rejected: it would make a tagged template permanently indistinguishable in the AST from a hand-written `tag(["a","b"], x)` call, which forecloses ever adding `.raw`/`String.raw` support later (the raw segments would need to have been preserved somewhere) and contradicts `docs/status/LANGUAGE-CONSTRUCTS.md`'s own framing of this gap as "no `TaggedTemplate` AST node... found anywhere," which names the fix. A real `ast.TaggedTemplateExpression{Tag, Quasis, Exprs}` node — parsed as its own thing, desugared only at the point codegen actually needs a `Value`/`Type` — keeps the "this was written as a tagged template" fact recoverable while still getting full reuse of existing call machinery underneath.

### Parser mechanics

`parseCallMember`'s postfix loop (`parser/parser_exprs.go:331`) already handles `LPAREN` → call, `LBRACKET` → index, `.`/`?.` → member access, immediately after parsing a primary/postfix expression — exactly the right place to add: a `TEMPLATE_NO_SUB` or `TEMPLATE_HEAD` token encountered here (immediately following another expression, as opposed to `parsePrimary`'s existing handling of the same two token types when a template literal starts a *new* primary expression) means the preceding `expr` is a template tag. Reuses `parseTemplateLiteral`'s existing quasis/expression-scanning loop (`parser/parser_literals.go:798`) — factored out into a shared helper returning `(quasis []string, exprs []ast.Expression, err error)` so `parsePrimary`'s existing bare-template-literal path and the new tagged-template path both call it, rather than the loop existing twice.

### Type-inference/var-decl touch points

Three call sites, each getting one new case that mirrors how `*ast.CallExpression`/`*ast.ArrowFunction` are already handled at that exact spot:
- `emit_exprs.go`'s `emitExpr` dispatch switch.
- `emit_exprs_types.go`'s `inferExprType` dispatch switch.
- `emit_exprs_vardecl.go`'s `emitVarDecl` pre-inference switch (an unannotated `const r = tag\`...\`` needs the same "delegate to `inferExprType`" treatment `*ast.CallExpression`/`*ast.MemberExpression` already get there — this switch has no catch-all default, so a missing case here would silently misinfer rather than error).

No change needed to `emitExprWithObjectHint` (`emit_objects.go:40`) — its own fallback (`return e.emitExpr(expr)`) already covers any expression kind it doesn't special-case, and a tagged template needs no object/array/arrow-function hint threaded through it.

## Open questions

- `.raw`/`String.raw` support, if ever picked up, needs the lexer to additionally capture each template segment's raw (pre-escape-translation) source text alongside the existing cooked form (`readTemplateSegment`, `lexer/lexer.go:556`, currently discards it) and a real per-array `.raw` property mechanism this compiler's fixed-shape arrays don't have today — tracked as the reason [ADR-00028](../adr/ADR-00028.md) punted `String.raw` originally, not re-scoped here.
