# ADR-00664: A completeness index for Node.js built-in modules

- **Date**: 2026-09-03

## Context

The status pages documented the Node built-in modules that are *implemented* in
detail (fs, http, streams, os, path, process, sqlite, and the "Other Node core
modules" grab-bag), but there was no complete list of Node's built-in modules.
A reader could not tell, for an unlisted module (`async_hooks`, `inspector`,
`string_decoder`, `ffi`, …), whether it was missing, deliberately out of scope,
or simply undocumented. The goal: make it unambiguous which Node modules are
supported, which work only through an ambient global, which are not started, and
which are out of scope by design.

## Investigation

The authoritative list of what the compiler actually accepts as a module import
is `resolver/virtual_modules.go`'s `virtualBuiltinMarkers` allowlist — a bare or
`node:`-prefixed specifier outside it is rejected (`import path '<x>' must start
with './' or '../'`). Cross-checking every canonical Node built-in against that
allowlist and the status data surfaced three classes:

- **Implemented and importable** — the ~26 specifiers in the allowlist, each
  already documented on a detailed page.
- **Works as an ambient global, but the module specifier is not importable** —
  `Buffer`, `setTimeout`/timers, `URL`, `performance` all work as globals, yet
  `import … from 'buffer'`/`'timers'`/`'url'`/`'perf_hooks'` (and `node:events`)
  fail the allowlist gate. Verified directly with one-line repros (Mac).
- **Absent entirely** — `string_decoder`, `util/types`, `async_hooks`,
  `inspector`, `repl`, `v8`, `wasi`, `trace_events`, `vm`, `ffi`, the deprecated
  `domain`/`punycode`/`sys`, and the promise/consumer subpath specifiers.

`docs/testing/NODE-GAP-ANALYSIS.md` already ranks the not-yet-built modules by
how many conformance files each blocks (`vm` 77, `async_hooks` 52, `v8` 18,
`domain` 35-but-deprecated, `inspector`/`repl`/`wasi`/`perf_hooks` <15 each) —
the natural companion for prioritization, so the new page cites it rather than
duplicating the ranking.

## Decision

Add a dedicated, standalone status page — `docs/status/NODE-MODULES.md` (source
`docs/status/data/node-modules.json`) — a completeness map of every Node
built-in, grouped into four tables: **Implemented**, **Available as globals
(module specifier pending)**, **Not started (in scope)**, and **Out of scope (by
the whole-program AOT / no-runtime model)**. Each implemented row links to its
detailed page; each gap row carries a one-line reason and, for the big ones, the
blocked-file count from NODE-GAP-ANALYSIS.

The page is **informational**: every table sets `countsTowardParity: false`, so
these rows do not move the coverage percentages. Rationale, per an explicit
decision: an out-of-scope or deprecated Node module (`repl`, `v8`, `domain`) is
not the same as a missing feature, and folding ~30 such rows into the
denominators would make the honest "these work" numbers misleading. Modules
graduate onto the counted detailed pages as they are built; subsequent audits
will move individual rows from this index onto a counted page by importance.

## Implementation notes

- The page registers in the README index (`_index.json`) as a row in the
  Node.js APIs category table using `pageText` + `coverageOverride`/`strictOverride`
  ("— index"), not `pageFile` — because `resolveCategoryTableRef` only resolves
  pages that have at least one parity table, and this page deliberately has none.
  A `coverageOverride` row is also skipped by `sumCategoryTable`, so the section
  total is unaffected (verified: Node section stayed 118/120).
- Statuses use the schema's two row states (`implemented` ✅ / `missing` ❌); the
  four-way nuance lives in the table groupings and notes, not new status values.

## Side effects discovered

Confirmed a real, separately-trackable gap the matrix now names: several modules
work only as ambient globals because their `import … from '<name>'` specifier
isn't in the resolver allowlist (`buffer`, `timers`, `url`, `perf_hooks`,
`node:events`). Wiring those specifiers is a mechanical follow-on, left for a
future pass.

## Verification

`make status` regenerates NODE-MODULES.md + README.md; `make status-check` and
`make reference-check` green. Module classifications verified against the
`virtualBuiltinMarkers` allowlist and one-line compile repros on Mac. Companion
TypeScript- and JavaScript/MDN-surface completeness audits are the next pass.
