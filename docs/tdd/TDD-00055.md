# TDD-00055: Dynamic `import(...)` and `import.meta`

- **Status**: Partially Implemented
- **Date**: 2026-08-10
- **Notes**: Stage 1 (`import.meta.url`) done. In **this V1 eager-merge design**, a "dynamic" import can only ever be a literal-specifier, eagerly-run static import wrapped in a resolved Promise — real lazy-loading/runtime-conditional loading is out of scope *for V1* because V1 adds no runtime module loader, not because it is impossible for the project. [TDD-00056](TDD-00056.md) (V2) achieves genuine laziness (and is *more* faithful to ES module semantics) by compiling each dynamic-import target to a `dlopen`'d shared-library island — deliberately reopening the linker boundary [ADR-00022](../adr/ADR-00022.md) avoided, which V1 stays inside to keep a single `--static`-compatible binary. The two are complementary modes (a `-dynamic-import=eager|lazy` flag selects between them), not competitors, and **V1 is not a prerequisite for V2** — they share only the parser/resolver frontend. Named-function exports need real new codegen (thunks, Stage 3) to be usable through the result object

## Context

The last two ❌ rows in [MODULES.md](../status/MODULES.md): dynamic `import(...)` ("this compiler only recognizes the static `import { a } from '...'` form") and `import.meta` ("not meaningful yet given there's no dynamic `import()`/module-identity concept to expose either"). Grouped into one TDD because both extend the `import` keyword into *expression* position in the parser — the same lookahead dispatch point — even though their actual designs are otherwise mostly independent; this mirrors [TDD-00042](TDD-00042.md)'s precedent of combining features that "share enough machinery to design together."

A pre-implementation investigation (this session) into what's actually buildable found the honest scope is narrower than the feature names suggest, for a structural reason worth stating up front rather than discovering mid-implementation: **this compiler does whole-program, ahead-of-time compilation** — `resolver.ResolveProgram` merges the entry file plus everything it transitively imports into one `*ast.Program` *before* codegen ever runs ([ADR-00022](../adr/ADR-00022.md)), and there is no runtime module loader, no dynamic linking, no bytecode/JIT fallback anywhere in the pipeline. Real dynamic `import()` — a runtime-*variable* specifier, lazily fetched and evaluated the first time that code path actually executes — has no implementable meaning **in this V1 eager-merge model**, which adds no runtime module loader: there is nothing in *this design* to load or compile code after the binary exists. (This is a scoping choice for V1, not a project-wide impossibility: [TDD-00056](TDD-00056.md) (V2) adds exactly such a mechanism — `dlopen`'d shared-library islands — and delivers real laziness, at the cost of reopening the linker boundary [ADR-00022](../adr/ADR-00022.md) avoids and giving up `--static`. V1 stays inside that boundary on purpose.) The only form V1 implements is what bundlers call a "static dynamic import": `import('./literal/path')` where the specifier is a compile-time string literal, resolved exactly like a static import, wrapped in an already-resolved `Promise` purely for API-shape compatibility (`await import('./x')` parses and behaves sanely) — a runtime-computed specifier is a clean, explicit compile error, not a silent restriction.

**This also means the target's top-level code runs eagerly, unconditionally, in dependency order — exactly like every other import (TDD-00052) — regardless of whether the `import()` call site itself is ever reached at runtime.** Real JS's actual value propositions for dynamic import — code-splitting/lazy bundle loading (moot for a natively-compiled binary; there's no "bundle" or "chunk" concept at all) and genuine runtime-conditional loading (needs a variable specifier and true laziness, neither of which V1 provides) — are both unavailable **in V1** (V2/[TDD-00056](TDD-00056.md) provides the laziness half via `.so`/`.dylib` islands). What V1 delivers is narrow but real: syntax compatibility, so real-world `await import('./x')` patterns at least parse and run sanely instead of hitting a hard rejection, plus a legitimately convenient `Promise`-returning spelling for what's otherwise identical to a static import. Worth being direct about this rather than overselling V1 once built.

## Design

### `import.meta.url` (Stage 1)

Scoped to exactly `import.meta.url` — nothing else. Real Node/browser `import.meta` has grown other members over time (`import.meta.resolve()`, bundler-specific `import.meta.env`, etc.); none are in scope, and neither is bare `import.meta` used as a value on its own (there's no real "module metadata object" to represent — same "compile-time-only, never a real runtime value" character [TDD-00042](TDD-00042.md)'s namespace imports already have). Rather than modeling that restriction as a resolve-time check, the parser only ever recognizes the complete `import`/`.`/`meta`/`.`/`url` token sequence as one atomic expression node (`ast.ImportMetaUrl`) — anything else after `import.meta` (a different member, or `import.meta` alone) is a **parse-time** error, the earliest and clearest point to reject it, rather than a resolve-time "misuse" case discovered later (the sharper posture [TDD-00042](TDD-00042.md)'s own Open Questions flagged as unfinished for namespace-import misuse — this TDD doesn't repeat that gap for a construct being designed fresh).

Resolution: `resolver/resolver.go`'s `fileInfo` already tracks each file's own absolute path (`path` field) during its own per-file resolve pass, before the merge into one program erases per-file identity. `rename.go`'s existing scope-aware AST walk (already closure-capturing per-file context) gains one more case: an `ast.ImportMetaUrl` node is rewritten in place to `ast.NewStringLiteral("file://" + thatFile'sAbsPath, pos)` — a plain string literal by the time codegen ever sees it, needing zero codegen changes, following the exact "resolver fully consumes this node type, codegen never sees it" pattern `ImportDeclaration`/`ExportDeclaration` already established.

### Dynamic `import(...)` (Stages 2-3)

**Parsing.** `lexer.IMPORT` is currently only ever dispatched from `parseStatement`'s top-level switch (unconditional `case lexer.IMPORT: return p.parseImportDeclaration()`) and has no case at all in `parsePrimary` (expression-level dispatch) — reaching expression context today is already a clean, well-defined parse error, not a silent gap. Two additions, no grammar collision:
- `parseStatement`'s `IMPORT` case gains one token of lookahead (`p.peekNth(1).Type == lexer.LPAREN` → route to `parseExpressionStatement` instead of `parseImportDeclaration`) — the exact pattern already used to disambiguate `ASYNC` (function declaration vs. arrow expression).
- `parsePrimary` gains `case lexer.IMPORT`, dispatching to a dedicated parse function (mirrors `case lexer.NEW: return p.parseNew()`'s precedent of a self-contained parser for a keyword with its own argument-shape rules rather than routing through the generic call-postfix machinery) — after `import`, `(` routes to the dynamic-import-call parse (below), `.` routes to `import.meta.url` (above), anything else is a parse error.
- New AST node `ast.ImportCallExpression{Specifier ast.Expression, pos}` — `Specifier` stays a general expression at the parser level (so a non-literal argument is a real, specific resolve-time error with a clear message — "dynamic import requires a string literal specifier; this compiler resolves all imports at compile time" — rather than a confusing parse-time rejection that can't explain *why*).

**Resolution.** `resolver.go`'s `visit` DFS already treats `ImportDeclaration.Source` and (since [TDD-00051](TDD-00051.md)) `ExportFromDeclaration.Source` as dependency edges — an `ImportCallExpression` with a literal `Specifier` is a third instance of exactly the same kind of edge, walked and merged into `order` identically (same mangling, same re-export resolution, same [TDD-00052](TDD-00052.md) cycle handling — nothing about those passes needs to know an import edge came from `import(...)` rather than a top-of-file `import`). The one new resolver-side check: a non-`StringLiteral` `Specifier` is rejected with the message above, at the point the DFS would otherwise need to resolve it.

**Codegen — the result value.** This is the one place dynamic import is a genuinely different shape from every other import form: `import * as ns from '...'` is compile-time-only (`ns.member` rewritten directly, `ns` itself never a real value) precisely because real ES modules' emphasis there was static analyzability — but `import()`'s whole contract is a real value you can `await`, store, and pass around. So its result must be an actual heap object, not a compile-time rewrite:
- At the call site, synthesize an anonymous fixed-shape object type with one field per the target's exported name (including `"default"` if present) — exactly the same "walk `target.exported`" enumeration `import * as ns`'s member-table-building already does (`resolver.go`), just materializing real values into a real object instead of a compile-time name-substitution table.
- A field backed by a top-level `var`/`let`/`const` export is a plain load of that export's already-mangled global (identical to how any cross-file static reference to it already works).
- A field backed by a `class`/`interface`/`type`/`enum` export is simply **omitted** from the synthesized object — this compiler's classes aren't first-class values (`new` only ever accepts a single bare identifier, not an arbitrary expression, a pre-existing restriction unrelated to this TDD), so there's no value representation to give it. Accessing it off the dynamic-import result then fails with the same "no such field" error any fixed-shape object already gives for a genuinely absent field — no new error message needed, this falls out of the existing object model for free.
- A field backed by a `function` export needs to be *callable* through the result object, and every existing call-through-a-field site (`emitClosureCallByPtr` and friends) universally assumes a 2-word `{fnPtr, envPtr}` closure header — the calling convention arrow functions/closures already compile to. A plain top-level `function` declaration compiles to a bare `define @name(...)` with **no env parameter at all** — a real ABI mismatch, not just a missing map entry. **Stage 2 ships without this**: a function-typed export is, like a class export, omitted from Stage 2's synthesized object (explicit, clearly-erroring gap, not a silent miscompile) — deferred to Stage 3 specifically because it's genuinely new codegen (see below), and this codebase's own examples lean heavily on `export function` over arrow-function exports, so Stage 2 alone would cover class/interface/enum-style modules fine but not the more common function-exporting case.
- The whole object is then wrapped via the already-existing `wrapResolvedPromise(val Value) Value` (`codegen/llvm/emit_promise.go`) — exactly "`Promise.resolve(x)`" for an arbitrary already-computed value, the same primitive `Promise.all`/`.race`/`.allSettled` already use. `await import('./x')` then reads back through the ordinary `emitAwait` path with zero new await-side code, since every other already-resolved `Promise` in this compiler already goes through the identical wrap/unwrap shape.

**Stage 3 — function-export thunks.** Closes the Stage 2 gap: for each `function`-typed export actually reachable through a dynamic-import result, generate a small wrapper once (memoized per mangled function name, generated the first time it's needed) — `RETTY @name.thunk(ptr %unused_env, params...) { %r = call RETTY @name(params...); ret %r }` — and pack `{fnPtr: @name.thunk, envPtr: null}` as that field's closure-header value. Arrow-function exports need no such wrapper (already closure-shaped). This is real new codegen (nothing in the compiler generates a function like this today), though the compiler already generates functions on-demand elsewhere (generic instantiation) — the *pattern* isn't new, the specific thunk shape is.

## Open questions

- Whether Stage 3's thunk generation is worth doing at all given the broader finding that dynamic import's real-world value is already narrow (see Context) — leaning yes, since `export function` is this codebase's own dominant style and Stage 2 alone would make the feature feel broken for the common case, but worth re-confirming once Stage 2 ships and the actual narrowness is concretely visible rather than theoretical.
- Whether a bare `import('./x')` (result discarded, not awaited) should warn/lint that its target's top-level code already ran unconditionally regardless — real JS code written expecting lazy side-effect-on-first-import semantics would silently get "always runs at startup" instead. Leaning toward documenting this prominently (this TDD, `MODULES.md`, the eventual ADR) rather than a dedicated compiler diagnostic, consistent with how [TDD-00052](TDD-00052.md)'s own cycle-handling caveats are documented rather than specially warned about.
- Exact wording/format of `import.meta.url`'s `file://` prefix on Windows-style paths — moot until [TDD-00020](TDD-00020.md) (Windows support) exists at all; not designed further here.
