# TDD-00047: `Worker` (background-thread concurrency)

- **Status**: Superseded
- **Date**: 2026-08-10
- **Notes**: Superseded by [TDD-00098](TDD-00098.md): its scope, API staging, and the four confirmed blockers carry forward unchanged, but its prerequisites went stale (structured-clone copy and per-event `EventEmitter` payload typing shipped since) and its four open designs (entry compilation, per-thread state, channel mechanics, channel typing) are settled there
- **Relations**: Superseded by [TDD-00098](TDD-00098.md)

## Context

Tracked in [docs/status/CONCURRENCY-WORKERS.md](../status/CONCURRENCY-WORKERS.md) as 0/3, "High effort" in the roadmap's own tiering — the only backlog item that needs a genuinely different concurrency model rather than an extension of what already exists. Picked up now, ahead of the lower-risk `EventTarget`/`AbortController` track ([EVENTS-CANCELLATION.md](../status/EVENTS-CANCELLATION.md)), deliberately: real OS-thread concurrency is far more likely to surface deep bugs in shared runtime state than anything shipped so far, and the earlier those surface the cheaper they are to fix.

The shipped event loop ([TDD-00006](TDD-00006.md)) is cooperative, one-fiber-at-a-time concurrency on a single OS thread (`ucontext.h`'s `getcontext`/`makecontext`/`swapcontext`) — a fiber yields control voluntarily, nothing ever runs in parallel. `Worker` needs actual preemptive, parallel execution across real OS threads. That is not a bigger version of the existing scheduler; it is a second, different mechanism that has to coexist with the first one.

Before any design could be trusted, the actual runtime source was checked directly for shared global state that a second concurrently-running thread would touch — not assumed from the architecture doc. Three genuine, concrete conflicts turned up (Design section below), plus one confirmed absence (no `pthread` use anywhere in the codebase today — this would be the project's first).

**Now depends on [TDD-00049](TDD-00049.md)** (import-gated built-in bindings): that document found every Node-style pseudo-namespace this compiler has today (`fs`, `process`, `path`, etc.) is recognized by bare AST-identifier-text matching, with a confirmed, empirically-reproduced bug where a local variable of the same name gets silently miscompiled into a call to the built-in instead of the user's own code. Adding `worker_threads`'s `Worker` as a 21st hardcoded ambient name would repeat that exact pattern. **Update**: [TDD-00049](TDD-00049.md) has now fully shipped, both stages — Stage 1 ([ADR-00141](../adr/ADR-00141.md), default/namespace-form imports) and Stage 2 ([ADR-00142](../adr/ADR-00142.md), named per-member imports, needed zero codegen changes once built). `import { Worker } from 'worker_threads'` as sketched below is directly supported by the mechanism now — the only remaining prerequisite is adding `'worker_threads'` itself to `resolver/virtual_modules.go`'s specifier tables once this document is actually implemented, not a design gap.

## Design

### Scope: message-passing only for V1, shared memory explicitly deferred

Real JS/Node concurrency has two tiers: `postMessage`-based copying (the default — a sent value is deep-copied at the boundary, so each thread only ever touches its own memory) and `SharedArrayBuffer`/`Atomics` (an explicit, opt-in escape hatch for true shared memory, which is exactly why it needs its own separate synchronization primitives in real JS too). **Recommended V1 scope is message-passing only** — it maps directly onto the "no data races because nothing is actually shared" safety story real JS relies on, and every one of this compiler's existing heap-allocated value shapes (arrays, objects, closures, `Map`/`Set`) has zero synchronization today and never needed any (`manual`-mode allocation has no locking beyond what `malloc`/`free` do internally). Shared memory is a different, harder feature — deferred, not designed here; see Open Questions.

### API shape: both, staged — Node's `worker_threads` first, browser `Worker` later

Both real precedents are wanted long-term, not a pick-one choice:

- **Node `worker_threads.Worker`**: `import { Worker } from 'worker_threads'; new Worker(path, { workerData })`, and the `Worker` object itself **extends `EventEmitter`** — `.on('message', ...)`, `.on('error', ...)`, `.on('exit', ...)`.
- **Browser `Worker`**: `new Worker(url)` (a bare, ambient global — real browsers never `import` it), communicates via `postMessage`/`onmessage` (a dedicated event-handler property, not `EventEmitter`).

**Recommended staging: Node's shape first, browser's shape as a later stage of this same document.** This project already ships a 100% `EventEmitter` ([TDD-00023](TDD-00023.md)/[ADR-00089](../adr/ADR-00089.md)) with the exact hand-written-dispatch pattern (`.on`/`.emit`/`.off`) a `Worker` object needs for its own public surface — composing on top of that reuses a proven pattern instead of waiting on the separate `EventTarget`/`AbortController` track ([EVENTS-CANCELLATION.md](../status/EVENTS-CANCELLATION.md)) to exist first. `EventEmitter`'s known single-payload-type-per-instance limitation is a fine fit here too: `Worker.on('message', handler)` only ever needs one payload shape (the cloned message value), so it doesn't run into the variadic-`...args` gap that limits `EventEmitter` elsewhere. Matches this project's stated CLI-tool/microservice priority over browser-shaped APIs as an ordering preference, not an exclusion.

Once both stages exist, the two APIs are almost entirely orthogonal at the codegen level — same underlying `pthread`/fiber-per-thread mechanism and message-copy machinery, different surface bindings (`worker_threads`'s named-export `Worker` vs. a bare ambient `Worker` global) and a different event-delivery convention (`EventEmitter` methods vs. `onmessage`/`onerror` properties). Staging Node's shape first also means it ships with real import-gated collision safety from day one — see the dependency on [TDD-00049](TDD-00049.md) directly below — rather than adding `Worker` as yet another hardcoded ambient name the way `fs`/`process`/etc. were before that document. The browser stage's ambient global is a deliberate, documented exception to [TDD-00049](TDD-00049.md)'s import-gating (it matches real browsers, which also never import `Worker`), not an oversight.

### Mechanism: `pthread_create`/`pthread_join`, declared like every other libc dependency

`pthread_create` to spawn, `pthread_join`/`pthread_detach` for lifecycle — declared via `ensure*()` exactly like every other C stdlib dependency this compiler already has (`ensureCurl`, `ensureGC`, etc. — see codegen conventions), and each spawned thread runs its own independent fiber-based event loop (reusing `TDD-00006`'s scheduler *as a pattern*, one instance per thread, not one shared instance). Needs `-pthread` added to `main.go`'s clang invocation — confirmed absent today by direct check of the current `clangArgs`.

### Confirmed blockers — process-wide singleton state that breaks under real threads

Found by grepping the actual runtime codegen, not inferred:

1. **Exception state is one global, not per-thread.** `runtime_exceptions.go` declares `@__kml_thrown` (the in-flight exception pointer), `@__kml_jmp_stk` (a 64-deep `setjmp` buffer stack), and `@__kml_jmp_top` (its depth) as plain `internal global`s. Two threads throwing/catching concurrently would corrupt each other's jump-buffer stack — a real, immediate correctness bug the moment two workers both use `try`/`catch`, not an edge case. **Fix**: these three symbols need to become LLVM `thread_local global`s instead of plain `global`s — clang emits real TLS access for `thread_local` on both ELF (Linux, via `__tls_get_addr` or initial-exec, whichever the linker picks) and Mach-O (Darwin) targets, so this is mechanical once identified, but every one of the ~dozen call sites across `emit_exceptions.go`/`runtime_exceptions.go` that reference these needs auditing, not just the declarations.
2. **GC's stack-bottom tracking is also a singleton, and it's Boehm's single-threaded API.** `-mm=gc` builds repoint one global, `@GC_stackbottom`, around whichever fiber is currently running (`emitter.go`, `runtime_http.go`) — a trick that only works because today everything happens on one OS thread. Real Boehm multi-threaded support is a **different, dedicated API** — `GC_register_my_thread`/`GC_unregister_my_thread`, each called with its own `struct GC_stack_base` — not an extension of the stackbottom-repointing trick. This needs its own sub-design within implementation, not just "link `-lgc` and hope"; per-thread registration has to happen at `pthread_create` time, before that thread does its first `GC_malloc`.
3. **No `pthread` dependency exists anywhere today** (confirmed by grep across `*.go`) — first one this project would add. Low risk on its own (both dev machines' `clang` link pthreads trivially), but it changes `main.go`'s clang-args assembly and `--static` linking story (Linux-only already, per the project's own instructions) — needs re-verifying `--static` still links cleanly once `-pthread` is in the mix, not assumed to just work.
4. **`fetch`'s libcurl usage was never built to be thread-safe** ([ADR-00050](../adr/ADR-00050.md)'s multi-interface machinery). libcurl *is* thread-safe in general, but only under real constraints: `curl_global_init` must run exactly once before any thread starts (not per-thread), and each thread needs its own easy/multi handles — never share a handle across threads. Needs verifying the current handle lifecycle already satisfies this (it may, by construction, since each `fetch()` call already gets its own easy handle) or a small fix — not yet checked, since it never had to matter before.

### What a Worker boundary actually copies

Deep-copy (structured-clone-equivalent) the same "JSON-safe" set this compiler already treats specially elsewhere: `number`/`string`/`boolean`/`null`/plain arrays/plain objects. **Functions and closures are not transferable** — matches real JS (neither browser `Worker` nor Node's `worker_threads` can clone a function either), so this is a compile-time rejection at the `postMessage` call site based on the static type of the argument, not a runtime limitation to work around. Whether a `class` instance is cloneable is an open question (see below) — real JS silently drops the prototype chain when structured-cloning a class instance, which is arguably worse than a clean compile-time rejection.

## Open questions

- **`manual` mode + `Worker`**: does spawning threads make sense under `manual` mode's "process exits, OS reclaims everything" model, or should multi-threaded + long-running push a program toward `-mm=gc`? Leaning toward allowing both (every other feature so far has been mode-orthogonal) but documenting the compounding leak risk prominently rather than restricting it outright.
- **Uncaught exception on a worker thread**: crash the whole process (today's single-thread behavior for any uncaught `throw`), or terminate just that worker and emit `'error'` on the parent `Worker` object (real Node/browser behavior)? The latter is almost certainly right, and depends directly on the `thread_local` exception-state fix above already being in place.
- **Termination (`worker.terminate()`)**: `pthread_cancel` is broadly considered unsafe (skips destructors/cleanup, and this compiler has no destructor concept to skip, but it can still leave `malloc`/GC state mid-update). Likely needs a cooperative cancellation flag checked at existing fiber-yield points instead of a hard OS-level cancel — needs its own small design pass during implementation.
- **`class` instances across the `postMessage` boundary**: compile-time reject (safest, matches the "if it's ambiguous in real JS, don't support it in V1" pattern this project uses elsewhere — e.g. RegExp's implicit-coercion rejections) or attempt a field-only structural copy? Leaning reject for V1.
- **Staging**: given the number of distinct cross-cutting fixes found above (thread-local exception state, GC thread registration, libcurl verification, `--static` re-check), a single monolithic implementation pass looks like the wrong shape — this likely wants explicit stages, the same way [TDD-00035](TDD-00035.md)/[TDD-00038](TDD-00038.md)/[TDD-00039](TDD-00039.md) staged large features rather than shipping them in one piece:
  1. `worker_threads`-shaped spawn/join + copy-only `postMessage`, `manual` mode only, no `-mm=gc` combo yet, gated behind [TDD-00049](TDD-00049.md)'s import mechanism.
  2. `-mm=gc` thread registration.
  3. Error/termination semantics.
  4. Browser-shaped ambient `Worker` global, layered on top of the same underlying mechanism built in stages 1-3 — see the Design section's staging note above.

  Recommend prototyping the riskiest, least-reversible piece first and in isolation — `thread_local` globals plus `GC_register_my_thread` in a handful of throwaway `.ll` files compiled directly with this project's exact `clang` invocation — before committing to the full staged plan, the same "prototype directly, don't decide from the design doc alone" approach [TDD-00006](TDD-00006.md) used for its own fiber mechanism.
