# ADR-01029: `Promise.race`/`Promise.any` at module top level never advanced their members' fetches

- **Relations**: `Extends ADR-01021`, `Implements TDD-00223`
- **Date**: 2026-09-21

## Context

Both Linux CI lanes regressed from green to a 90-minute job timeout. The commit
that did it is titled as Windows work, so the breakage was invisible in the
handover notes, which recorded only "windows-x64 green, both macOS lanes hung"
— Linux was never mentioned because Linux never *reported*.

Per-lane history from the Actions API:

| Commit | linux-x64 | linux-arm64 | windows-x64 |
|---|---|---|---|
| `ce46689` | success, 22m | success, 18m | failure |
| `43d171e` | **cancelled, 90m15s** | **cancelled, 90m15s** | success |

"Cancelled" at exactly `timeout-minutes: 90` is a job ceiling, not a
cancellation — the matrix already sets `fail-fast: false`, so the macOS
failures at ~51m did not cancel anything. Step-level status showed
`go test -timeout 50m ./...` **succeeded** on both Linux lanes; both died in
the next step, `make examples`.

`make examples` runs each example with no per-example time cap
(`Makefile:117` — `$$out </dev/null 2>/dev/null >/dev/null`), so one
non-terminating example wedges the step until the job ceiling and CI can only
report "the step ran to the limit."

## Investigation

Re-running the recipe on linux/amd64 with a 25 s cap per example named the
culprit immediately: **329 passed, 0 failed, 1 hang** —
`examples/async/concurrent_tasks.ts`.

Its stdout stops in a fixed place:

```
200            <- line 22, composition concurrency
404            <- line 23
200 404 200    <- line 31, Promise.all
<hangs>
```

so `Promise.all` completes and **line 35's `Promise.race` never settles**. The
same example at `ce46689` runs to completion (`rc=0`, all eight lines), which
confirms a regression rather than a long-standing gap.

`emit_promise.go:551` lowers `Promise.race` over may-suspend task promises to
`@__kml_task_await_any_of`; `Promise.any` uses the sibling
`@__kml_task_await_first_fulfilled`. At module top level both took this branch
(`runtime_task.go`):

```llvm
drive:
  call void @__kml_task_sched_step()
  br label %scan
```

`@__kml_task_sched_step`'s pump block calls `@__kml_curl_drain_messages()` and
nothing else — it *collects* finished transfers but never calls
`curl_multi_perform`, which is what actually advances them. The only caller of
`curl_multi_perform` on a waiting path is `@__kml_fetch_pump`
(`runtime_fetch.go:450`), reached through `@__kml_loop_turn`
(`runtime_loop_turn.go:134`).

`43d171e` converted every *other* main-stack wait to take a real loop turn,
keeping the old libcurl spin only as a `rawspin` fallback for turn == 2:

- `ensureFetchAsync`'s `busyspin` (two sites)
- `@__kml_await_group_wait`'s `busyspin`
- `@__kml_task_await_ready`'s top-level branch (`toploop` → `topawait` →
  `@__kml_top_await`)

It missed the two combinator helpers. So a `race`/`any` member backed by an
in-flight fetch could never progress: the wait span forever draining a transfer
that nothing was performing. `Promise.all` was unaffected because it awaits a
single combined promise through the converted `@__kml_task_await_ready`.

Leaving the helpers on the old drive and instead teaching
`@__kml_task_sched_step` to pump libcurl was rejected: the scheduler is called
from inside loop callbacks and from the webview tick, where re-entering
libcurl's perform under the loop's own iteration is exactly what
`@__kml_loop_turn`'s result 2 exists to prevent.

## Decision

Give both combinator helpers the same top-level wait as every other main-stack
wait: a turn of the real event loop.

`drive:` now calls `@__kml_loop_turn(i1 false)` and switches on the result:

- **0 (a turn was taken)** — rescan the members.
- **2 (inside a loop callback)** — the old subset drive, unchanged:
  `@__kml_drain_microtasks`, `@__kml_task_sched_step`,
  `@__kml_timer_fire_next`, `@__kml_fetch_pump`.
- **1 (loop idle)** — nothing alive can wake the loop. The turn's own final
  microtask/scheduler pass may still have settled a member, so rescan once; a
  second idle verdict means the await can never settle, and it ends the way
  Node ends an unsettled top-level await.

`pin` is `false`, matching `@__kml_top_await`. These helpers do not themselves
own an in-flight transfer — their members do, and a member's libcurl socket is
already a loop source — so pinning would suppress the idle verdict that makes
a genuinely unsettleable race terminate.

The one-rescan-then-give-up needs a bit of state; it is an `alloca` in each
function's entry block (not a global) so nested top-level combinators cannot
observe each other's flag.

## Implementation notes

- `codegen/llvm/runtime_task.go` — the `drive:` block in
  `@__kml_task_await_any_of` and `@__kml_task_await_first_fulfilled`; an
  `%idleseen` alloca in each entry block; a `noteLoopTurn()` at the emission
  site so the loop-turn runtime is emitted when these helpers are used, mirroring
  what `@__kml_task_await_ready` already does.
- `codegen/llvm/runtime_loop_turn.go` — `@__kml_tla_unsettled()`, the shared
  give-up path. The combinator helpers wait on a *set* of member promises rather
  than one state word, so they cannot call `@__kml_top_await` itself, but an
  unsettleable top-level await must end identically wherever it was issued;
  factoring the warning and `exit(13)` into one function keeps the message from
  being duplicated.
- `drescan` clears `%idleseen`: real progress in a turn must reset the
  give-up countdown, or a single idle report early in a long wait would arm the
  exit for a race that is still making progress.

## Side effects discovered

- **`make examples` has no per-example timeout** (`Makefile:117`), which is why
  a single wedged example costs 90 minutes of CI on two lanes and reports
  nothing about which example it was. Not changed here — it is a test-harness
  robustness question separate from this defect, and worth deciding on its own
  terms rather than inside a regression fix.
- **`docs/BACKLOG.md:486`** still states that `fs.createReadStream` /
  `createWriteStream` keep the eager read-to-EOF fill because "the pool runtime
  is POSIX-only, pending the reactor work (TDD-00186)". ADR-01026 removed both
  `targetGOOS()=="windows"` gates and deleted the eager path, so that caveat is
  stale.
- Windows CI **skips** `make examples` entirely
  (`.github/workflows/release.yml:135`, `if: matrix.goos != 'windows'`), so the
  examples corpus is unverified on Windows; a Windows-only break in an example
  would not be caught by that lane.
