# ADR-01854: Literals returning unmappable results; self-referencing parameter defaults

- **Relations**: `Implements TDD-00230` (P3.3: the checker answers what inferExprType did)
- **Date**: 2026-10-21

## Context

- A function expression returning a generator object (`function () { return iter; }` with `var iter = function* () {}()`) fell back: the checker types its result `Generator<never, void, unknown>`, which no representation names, while emission holds `iter` as a box. Its in-place call fell back with it. Test262's destructuring-default files build their iterators this way, and the pattern led the shadow report's largest bucket.
- A parameter default reading the parameter itself (`(x = x) => {}`) recursed in the checker and came back unanswered. tsc reports TS2372 and types the parameter `any`.

## Decision

- When a synchronous, non-generator, unannotated function expression's checker type fails to map only because of its result, the oracle builds its type from the mapped parameters and what its body's returns read as (`ReturnType`). A call of that literal in place takes the same result.
- A parameter whose default reads the parameter itself, outside a nested function, is `any`, in the declaration signature and in the literal signature alike.

## Consequences

- `TestSelfReferencingParameterDefault` covers the self-reference and a closure default reading another parameter, which stays typed.
- The shadow report on Node304 went from 17,553 to 11,340 rows with the preceding fixes; these address its first and third buckets.
- Verified on Apple Silicon (checker package; the Test262 files named above report no rows in either lane).
