# ADR-01375: A static eval is expanded before binding; two early errors

- **Relations**: Extends TDD-00046 (static eval subset), TDD-00230 P2
- **Date**: 2026-10-03

## Context

Test262's `call/S11.2.3_A1.js` (`eval("Number ()")`) regressed to
"undefined function or closure 'Number'". Three negative tests
(`void 1 ** 2`, a strict object-literal setter taking `eval` or
`arguments`) started compiling once `void` parsed.

## Investigation

- `emitStaticEval` parsed the string in code generation, after binding and
  checking. Builtin calls now dispatch through the checker's declarations,
  which have never seen those nodes: `eval("Math.abs(-1)")` failed too.
- The exponentiation early error checked only for a `UnaryExpression`
  node; `void x`, `typeof x` and `delete x` parse to other nodes.
- The strict parameter-name error was raised for a function whose own body
  is `"use strict"` and for class members, not for strict program code.

## Decision

- The resolver replaces `eval("<expression>")`, its argument a constant
  string holding a single expression, with that expression in each user
  file, unless the file declares its own `eval`. The binder and checker
  then see it as ordinary code. Every other eval still reaches
  `emitStaticEval`, which rejects it cleanly.
- `**` rejects an unparenthesized unary left operand by its start token:
  `-`, `+`, `!`, `~`, `typeof`, `void`, `delete`, and `await` when it is not
  an identifier.
- In strict program code, a parameter named `eval` or `arguments` of any
  function, arrow, method or accessor is an early error (`strictErrors`).

## Implementation notes

`resolver/resolver.go` (`rewriteStaticEval`), `parser/parser_exprs.go`
(`unaryOperatorStart`), `parser/parser.go` (`strictParamNames`).

## Side effects discovered

- `var await = 2` is rejected in a script ("expected IDENT"), at HEAD too.
- `typeof new String("1")`, `typeof this.NaN` at the top level and
  `typeof await this` in a module passed at HEAD only because `typeof`
  folded its operand without evaluating it. That fold also skipped side
  effects (`typeof f()` never called `f`) and answered `"number"` for
  `new Number(1)`. With the operand evaluated, these fail on missing
  features: primitive wrapper objects and top-level `this`.

## Verification

Mac (Apple Silicon): `eval` with each whitespace of the Test262 file,
`Math.abs`, a template-literal source, a local `x`, and a parameter named
`eval` match Node; the eval E2E tests; parser, lexer and resolver unit tests;
`(-2) ** 2`, `(void 1) ** 2` and a sloppy setter taking `eval` still compile.
