# ADR-00545: parseFloat rejects a "0x" hex prefix (not ToNumber)

- **Relations**: Extends ADR-00287, ADR-00529
- **Date**: 2026-09-01

## Context

`parseFloat(s)` and `Number.parseFloat(s)` went through `__kml_strtod_js`,
which wraps C's `strtod`. C99 `strtod` reads the C hex-float form, so
`strtod("0x10")` is `16`. Real JS `parseFloat("0x10")` is `0`: `parseFloat`
parses the longest prefix that is a valid `StrDecimalLiteral`, and `"0"` is
valid while `"0x"` is not — so it reads the leading `0` and stops at the `x`.
(`Number("0x10")`/ToNumber is a separate operation that *does* read hex as
`16` — that behavior is correct and must not change.) This deviation was a
disclosed caveat on both parseFloat rows of the number-math status page.

## Investigation

`emitParseFloat` (emit_call_number.go:268) calls `__kml_strtod_js`
(runtime_core.go), which `__kml_to_number` also uses. Changing `strtod_js`
itself would wrongly break `Number("0x10")`. The fix has to be scoped to
parseFloat only, so a dedicated wrapper is the clean seam.

## Decision

Add `__kml_strtod_parsefloat`, a parseFloat-only wrapper. It skips leading
whitespace and an optional sign, and if the next two characters are `0` and
`x`/`X` it returns a signed zero (`-0.0` for a leading `-`) with `endptr`
pointed just past the `0` — so the caller's existing endptr!=start "did we
convert anything" check sees a successful one-digit conversion and yields `0`,
not `NaN`. Any non-hex input delegates unchanged to `__kml_strtod_js`, so the
`Infinity`-word handling is preserved. `emitParseFloat` now calls the new
wrapper; ToNumber's path is untouched.

## Implementation notes

- `ensureStrtodParseFloat` (runtime_core.go) defines the wrapper; guarded by a
  new `usedStrtodParseFloat` emitter flag.
- Only `emitParseFloat` was switched — both `parseFloat` (global) and
  `Number.parseFloat` route through it, so one change covers both rows.

## Side effects discovered

None.

## Verification

`TestE2EParseFloatHexPrefix` asserts `parseFloat("0x10")`/`"0X1F"` → `0`,
`"0.5x"` → `0.5`, `"-0x10"` → `-0`, and `Number("0x10")`/`Number.parseFloat`
still behave (`16`/`0`). Existing `TestE2ENumberParseFloatInfinitySpelling`
and `TestE2EGlobalConversionFunctions` still pass. Built and verified on Mac
(Apple Silicon).
