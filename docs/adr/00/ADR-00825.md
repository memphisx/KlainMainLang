# ADR-00825: Response flush driven by res.end() (TDD-00195 Stage 2 core)

- **Relations**: `Implements TDD-00195`, `Extends ADR-00300, ADR-00824`
- **Date**: 2026-09-10

## Context

After ADR-00824 (Stage 1) a server `req` is a Node `Readable`, but a *fire-and-
forget* `(req,res)=>void` handler — the classic Node form that attaches
`req.on('data')`/`req.on('end')` and calls `res.end()` from the `'end'` callback
— did not work. The response was flushed **when the handler returned**, before
`'end'` (hence `res.end`) ever fired, so the client got an empty response. The
only working forms were those where the handler stays alive until the body is
consumed (`for await`, or an `async` handler `await`ing a promise resolved in
`'end'`). This was disclosed as a caveat; this ADR removes it.

## Investigation

- The void-`res` handler path is gated by the compile-time flag `e.httpResMode`
  (`emit_http.go`): it builds `res` (a `{status, body, headers}` object), calls
  `handler(req, res)` as `void`, and returns `res` to the shared response tail,
  which sends after the handler call returns.
- `res.write`/`res.end` only concatenate onto `res.body` (`emit_http.go`) — there
  was no "ended" flag and no connection reference on `res`. An `async` handler's
  `call` blocks until its body fully runs (awaits park *this same* connection
  fiber), which is why `await`-until-end already worked; a sync/non-awaiting
  handler returns immediately, so the tail flushed early.
- The event loop already "pokes every parked connection fiber once to re-check
  its condition" on task completion (`@__kml_conn_poke`, `runtime_http.go`), and
  the req-body **pump** feeds the request body to a parked fiber's stream while
  it sleeps (`runtime_http_reqbody.go`). So a parked fiber's `req.on('data')`/
  `'end')` callbacks still fire from loop microtasks.

## Decision

Defer the flush of a void-`res` handler's response until `res.end()`:

- `ServerResponseType` gains an `ended` field (init 0 in `emitNewServerResponse`).
- `res.end()` sets `ended = 1` and sets `@__kml_conn_poke` — waking the parked
  connection fibers to re-check.
- After the void handler call (`httpResMode` branch), `emitParkUntilResEnded`
  parks the connection fiber in a re-check loop: while `res.ended == 0`,
  `swapcontext` to the event loop; on resume, re-check. Only on a connection
  fiber (`__kml_current_conn_idx >= 0`). Once `ended` flips, control falls
  through to the existing send tail + keep-alive re-arm, unchanged.

A synchronous `res.end()` (or an awaited async handler) has `ended` already set
when the loop is reached, so it never parks — byte-identical to before. The
existing 42-site connection-slot layout is untouched: the re-check loop needs no
new slot field, reusing the poke-and-recheck mechanism the loop already has.

## Implementation notes

- The park recomputes the self slot each iteration (the connection array may
  realloc-move while parked), mirroring the fetch-await and req-body yields.
- This is a partial Stage 2: the response is still **buffered** (`res.write`
  accumulates, one flush at `res.end`) — fully incremental `res.write` with
  socket backpressure and a real `'drain'` event, and `req.pipe(res)`, remain.

## Side effects discovered

Behavior change: a void handler that never calls `res.end()` now leaves the
connection open (as Node does) instead of flushing an empty 200 on return. No
test or example relied on the old auto-flush (all call `res.end`), and the new
behavior is the faithful one.

## Verification

- New E2E test (`tests/http_test.go` `TestE2EResFireAndForgetOnData`): a
  fire-and-forget `req.on('data')`/`'end')` → `res.end` handler returns the byte
  count over a POST. Manual: keep-alive across two fire-and-forget requests on
  one connection works; synchronous `res.end` unchanged. Full
  http/stream/fetch/upgrade/websocket/cluster suites pass.
- `go build`, `go vet` pass.
