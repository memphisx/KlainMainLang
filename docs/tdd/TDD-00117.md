# TDD-00117: Cross-worker `http.close()` in a `{ workers: N }` cluster

- **Status**: Implemented

## Context

`http.listen(port, handler, { workers: N })` forks `N-1` extra processes that
share the listening socket (TDD-00025). `http.close()` (TDD-00027) closes the
listener in the *calling* process only — each worker is a separate `fork()`ed
process with no IPC between them, so a `.close()` call (typically from one
worker's request handler or `SIGINT` handler) leaves the other `N-1` workers
still accepting on the shared socket. A full-cluster shutdown today requires an
external signal to the whole process group.

This is the standing HTTP Server caveat that drops the `http.close()` row out of
Strict Coverage (docs/status/HTTP-SERVER.md). Scoping it now as the first of the
HTTP-Server caveat-cleanup pass (the null-byte string caveat is deferred to its
own effort; this is self-contained).

## Design

The workers are real processes (unlike `new Worker(...)`, which is a pthread in
the same address space — `runtime_worker.go:165`), so signalling one from
another needs a genuine cross-process channel. Three options considered:

1. **Shared anonymous `mmap` flag (chosen).** Before the fork loop in
   `__kml_http_cluster_fork`, `mmap(NULL, 8, PROT_READ|PROT_WRITE,
   MAP_SHARED|MAP_ANONYMOUS, -1, 0)` one page and stash the pointer in a global
   `@__kml_cluster_close_flag` (init null). Every forked worker inherits the
   mapping, so all `N` processes see the *same* physical word. `http.close()`
   additionally does an atomic `store 1` into that word (when the pointer is
   non-null). Each worker's event loop, once per iteration, atomically loads the
   word and — if set and it still holds a live listener — runs the same local
   teardown `__kml_http_close()` does (`close(listenfd)`,
   `@__kml_listen_fd = -1`). The existing drain logic (`hasactiveconns`) then
   lets each worker finish its own in-flight connections and exit naturally.

   Symmetric (any worker may call `.close()`, not just the primary), needs no
   PID bookkeeping, no signal handlers, no async-signal-safety hazard (the flag
   is polled from ordinary loop control flow, exactly where `.close()` already
   runs). The flag is monotonic 0→1, so the atomic is a plain `seq_cst`
   store/load with no CAS or ABA concern.

2. **Track child PIDs in the primary + `kill(pid, SIGTERM)`.** Rejected: only
   works when `.close()` is called from the primary (a worker doesn't know its
   siblings' PIDs, and the primary doesn't learn a worker-initiated close);
   needs a real signal handler in every worker routed through the existing
   pending-flag machinery; and racy against a worker mid-fork.

3. **`kill(0, SIGTERM)` to the whole process group.** Rejected: SIGTERM's
   default disposition kills the process outright rather than running graceful
   drain, and hijacking it collides with the user's own
   `process.on('SIGTERM', ...)` graceful-shutdown handler (a first-class
   supported feature, PROCESS-CLI.md).

Non-cluster programs (`workers` ≤ 1, or no `{ workers }` at all) never call
`__kml_http_cluster_fork`, so `@__kml_cluster_close_flag` stays null and every
shared-flag operation is a guarded no-op — behavior is byte-identical to today
for the single-process case.

### `mmap` failure

If the pre-fork `mmap` fails, leave the flag pointer null and degrade cleanly to
today's single-process `.close()` semantics (the caller's own listener still
closes; siblings still need an external signal). No throw — a clustered server
losing *cross-worker* close on an `mmap`-exhausted host should not fail to boot.
