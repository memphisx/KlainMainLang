# ADR-00587: Event cancelable honored by preventDefault

- **Relations**: Extends [ADR-00234](ADR-00234.md), [TDD-00081](../tdd/TDD-00081.md)
- **Date**: 2026-09-01

## Context

`Event`/`CustomEvent` ignored their init object's `cancelable`, and
`preventDefault()` set `defaultPrevented` unconditionally. Per WHATWG,
`preventDefault()` sets `defaultPrevented` only on a **cancelable** event (the
default is non-cancelable), so the compiler reported `defaultPrevented === true`
where a browser/Node reports `false` — a genuine fidelity bug, and the existing
tests asserted the wrong value.

## Decision

Thread `cancelable` end-to-end:

1. `NewEventExpression`/`NewCustomEventExpression` gain a `Cancelable`
   expression, extracted from the init object literal at parse time (like
   `CustomEvent`'s `detail`); nil when absent (WHATWG default `false`).
2. `EventType()`/`CustomEventType()` gain a `cancelable` bool field, stored at
   construction from the init value (`0` when absent).
3. `preventDefault()` loads `cancelable` and stores it into `defaultPrevented` —
   so it becomes `true` only on a cancelable event and is a no-op otherwise.
   `EventTarget.dispatchEvent` therefore returns `false` only when a listener
   cancelled a cancelable event, matching the DOM.

`bubbles` stays accepted-and-ignored (single-target dispatch, no capture/bubble
tree).

## Verification

Updated `TestE2EEventBasics` (now covers both a cancelable and a non-cancelable
event), `TestE2EEventAsParameter`, and `TestE2EEventTargetDispatchReturn` to use
`{ cancelable: true }` where cancellation is intended, and their outputs match
real Node v26. The events/customevent and eventtarget examples were corrected
the same way. Built and verified on Mac (Apple Silicon).
