# ADR-00697: String-literal-search replace()/replaceAll() function replacer

- **Date**: 2026-09-04

## Context

`String.prototype.replace` and `.replaceAll` accept a function as the second
argument. When the search argument is a RegExp, the callback path already
worked (`emit_regexp_replace.go`): the replacer is invoked per match with
`(match, offset, string)`. But when the search argument is a plain string, the
literal-search path only ever evaluated the second argument as a *string
value* — a function replacer was silently coerced to its string form (or
produced wrong output), so none of these worked:

- `"hello".replace("l", (m) => m.toUpperCase())` → Node `heLlo` (first only)
- `"hello".replaceAll("l", (m) => m.toUpperCase())` → Node `heLLo` (all)
- `"a-b-c".replaceAll("-", (m, o) => "/" + o + "/")` → Node `a/1/b/3/c`

The RegExp and string-literal search forms should be at parity for a function
replacer.

## Investigation

`emitStringReplace`/`emitStringReplaceAll` (`emit_strings.go`) branch to the
RegExp path only when `inferExprType(args[0]).IsRegExp`; otherwise they
evaluate both the search and the replacement as string values and call the
runtime `__kml_replace`/`__kml_replace_all` helpers, which take a replacement
*buffer*, not a callback. The RegExp path resolves its callback with
`resolveCallbackWithHints(argExpr, []Type{TypePtr, TypeI64, TypePtr})` so
untyped arrow parameters default to `(match: string, offset: number, string:
string)`, then computes each match's replacement by invoking the callback via
`emitCBCall`. The same hint approach applies directly to the literal-search
path — the only difference is that the matched substring is always exactly the
literal search string, so no capture-group extraction is needed.

## Decision

In `emitStringReplace`/`emitStringReplaceAll`, after the RegExp check, detect a
function replacer (`inferExprType(args[1]).IsFunc`) and route to a new
`emitStringReplaceLiteralCallback`. It mirrors the RegExp all-matches builder
as a 3-pass `memmem` scan:

1. Count occurrences (pure).
2. Fill: for each match, invoke the callback exactly once (a real side effect
   that must never be re-run) with `(searchString, byteOffset, subject)`,
   recording the match start offset and the computed replacement `(ptr, len)`.
3. Build (pure): sum the output length and copy each gap-then-replacement
   segment plus the trailing gap.

`replace()` clamps the match count to at most one; `replaceAll()` uses the full
count. The callback is resolved with the same `(TypePtr, TypeI64, TypePtr)`
hints as the RegExp path. The string-value replacer path is untouched.

## Implementation notes

- New file `codegen/llvm/emit_strings_replace_cb.go`
  (`emitStringReplaceLiteralCallback` + two pure helpers,
  `emitStringLiteralCountMatches` and `emitStringLiteralBuildOutput`). No
  shared hot file touched beyond the two four-line dispatch guards in
  `emit_strings.go`.
- Reuses existing infrastructure: `resolveCallbackWithHints`, `emitCBCall`,
  `emitStrLenHeader`, `emitStringAlloc`, and the `memmem`/`__kml_str_alloc`
  runtime declared by `ensureStrHeaderRuntime`.

## Side effects discovered

Two documented narrowings for the literal-search callback path only:

- The `offset` argument is a byte offset — identical to JS's UTF-16 code-unit
  index for BMP/ASCII text, divergent for astral text. Tracked in the status
  row caveat.
- An empty search string with a *function* replacer returns the subject
  unchanged instead of JS's insert-between-every-position behavior. The
  string-value empty-search path (ADR-00547) is unaffected.
