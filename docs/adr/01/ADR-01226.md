# ADR-01226: Declaration modules take `export =`; assert, dns and zlib are declared

- **Relations**: `Implements TDD-00230`
- **Date**: 2026-09-29

## Context

TDD-00230 P3.1 declares the Node modules. @types/node declares `assert`
as a function merged with a namespace, and the module as that function:

```ts
declare module "assert" {
    function assert(value: unknown, message?: string | Error): asserts value;
    namespace assert { function strictEqual<T>(…): asserts actual is T; … }
    export = assert;
}
```

The declaration parser rejected `export =`. `dns` and `zlib` were not
declared at all.

## Investigation

- A namespace inside `declare module` desugars (as a program's does) into
  mangled declarations and a namespace group. The binder scoped a group's
  members only at a declaration file's top level. Inside a module they
  were bound as plain module members, so `assert.ok` was unanswered.
- The parser sends a namespace's second and later members through
  `pendingTopLevel`, which drains into the program body. Inside a
  `declare module` they ended up in the library's top level. There they
  were bound a second time, under an `inNamespace` entered outside the
  module, and that left the binder's current scope unbalanced. Every
  later library declaration (the Web Crypto global `crypto`) was then bound
  into the `assert` module.
- `narrowByAssertion` needed the callee's type to be a function; a
  callable object (the module) was not followed to its call signature.
- `checkCall` returned before the argument-count check for a generic
  function, so `assert.strictEqual(1)` (TS2554) reached codegen.

## Decision

- `declare module "m" { … export = X; }` parses: the module records X.
  The checker types the module (default and namespace imports) as X's call
  signatures plus the exported values of the namespace merged into X. A
  named import reads that namespace.
- A `declare module` body keeps its namespaces' members (the parser drains
  `pendingTopLevel` into the body). The binder scopes them with the
  declaration file's namespace groups.
- An assertion signature narrows through a callable object's single call
  signature.
- A generic call's argument count is checked; its arguments are still
  checked only through inference.
- `lib/node.d.ts` declares `assert` (every member codegen implements, with
  `export =`), `dns` (`lookup`, `resolve`, `resolve4`,
  `promises.lookup`) and `zlib` (the one-shot codecs, sync and callback).

## Implementation notes

`parser/parser_stmts.go`, `ast/nodes.go`, `binder/binder.go`,
`checker/checker.go`, `checker/check.go`, `checker/narrow.go`,
`lib/node.d.ts`, `resolver/virtual_modules.go` (assert's member table
lists every implemented check).

## Side effects discovered

- `assert`'s failure messages are not Node's (`values are not equal` for
  `Expected values to be strictly equal:\n\n1 !== 2\n`): a status caveat,
  next to the aliasing of `equal`/`strictEqual` it already had.
- A function merged with a namespace in a program's own code is still read
  through the function's type alone (`f.a` unanswered).
