# ADR-01972: fs.opendir and Dir

- **Relations**: Implements TDD-00230 (P3.3); extends [ADR-01298](ADR-01298.md)
- **Date**: 2026-11-06

## Context

A shadow unit (`test/sequential/test-fs-opendir-recursive.js`) was refused
with "no type for AwaitExpression": `fs.promises.opendir` did not exist.
The status data listed `opendir` → `Dir` among the fs members not ported
yet. `fs` is the second priority after HTTP, so the API is ported rather
than left to fail at run time.

## Investigation

Node's `lib/internal/fs/dir.js` keeps a native directory handle
(`uv_fs_opendir`) and reads it a batch at a time (`uv_fs_readdir`,
`bufferSize` entries, 32 by default), buffering the batch. A recursive
handle opens each subdirectory as its entry is handed out and drains those
handles (a queue) before its own next batch. An async read keeps an
operation queue; until the read's callback has run and one tick has
passed, a second read or a close waits in that queue, and `readSync` or
`closeSync` throws `ERR_DIR_CONCURRENT_OPERATION`. A closed handle throws
`ERR_DIR_CLOSED` from `read`/`readSync`/`closeSync`, rejects from
`read()`/`close()`, and passes the error to a `close` callback on the next
tick. Node's opendir error names the syscall but no path
(`ENOENT: no such file or directory, opendir`). `bufferSize` is validated
as a positive uint32 (`>= 1 && <= 4294967295`). Unlike `scandir`, which
libuv sorts, `uv_fs_readdir` returns entries in the system's order.

The fs pool (`codegen/llvm/threadpoolsrc/klainfs.c`) already had a
`readdir` op that read every entry and sorted them. It had no handle that
stays open between calls.

## Decision

Three pool ops back the handle: `OP_OPENDIR` (33) opens the directory and
returns the `DIR*` as the result number; `OP_DIRREAD` (34) reads up to
`d[1]` entries of handle `d[0]`, unsorted, as the same `<type><name>/…`
string `readdir` returns, with the count as the result (0 at the end);
`OP_CLOSEDIR` (35) closes it. `kfs_readdir` now shares the entry reader and
the result encoder with `OP_DIRREAD`.

`Dir` (`lib/node/internal_fs.ts`) is a port of Node's class, with private
`#` fields so an instance has no own keys: buffered entries, the handler
queue of recursive subdirectory handles, the operation queue,
`read`/`readSync`/`close`/`closeSync`/`entries`, `[Symbol.asyncIterator]`,
`[Symbol.dispose]` and `[Symbol.asyncDispose]`. `processReadResult` and
`readSyncRecursive` are public, as Node's are. `opendir`, `opendirSync` and
`fs.promises.opendir` open the handle and build the `Dir`. The handle
requests raise errors without a path, as Node's binding does.

## Implementation notes

- A non-UTF-8 `encoding` re-encodes each entry's name (`'buffer'` gives a
  Buffer name), as Node's binding returns them.
- `new Dir` with an invalid `bufferSize` closes the handle it was given
  before throwing. Node leaks it until GC; there is no observable
  difference.

## Side effects discovered

- Node's `Dir.prototype[Symbol.asyncIterator]` is `Dir.prototype.entries`
  itself. Here it is a method that returns `this.entries()`, because a
  class's methods are fixed when it is compiled: assigning to a class
  prototype at run time (`C.prototype.m = f`,
  `Object.defineProperty(C.prototype, Symbol.iterator, …)`) is not
  observed by calls or iteration on its instances. That limitation is
  general, not specific to `Dir`.
- Node closes an unclosed handle on garbage collection with a warning
  ("Closing directory handle on garbage collection"). Here an unclosed
  handle stays open until the process exits.

## Verification

`TestE2EFsOpendirDir` (JS lane, output identical to Node): batched sync
reads with `bufferSize: 1`, recursion, the callback form, async iteration
closing the handle, the closed/concurrent errors and their ordering, option
validation and the pathless opendir error. A strict-lane program typed with
`Dir`/`Dirent` and `fs/promises`' `opendir` printed the same as Node.
Example `examples/fs/opendir.ts`. Verified on the Mac (arm64) and on
Linux (x86-64, the Node304 box). On Windows the three ops go through
`win32fs.c`'s `opendir`/`readdir`/`closedir`; that build has been neither
compiled nor run.
