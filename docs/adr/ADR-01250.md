# ADR-01250: `process` is an EventEmitter, in TypeScript

- **Relations**: `Implements TDD-00230`, `Extends ADR-01238, ADR-01239, ADR-01228`, `Supersedes ADR-00079` (its fixed per-signal slots), `Supersedes ADR-00580` (its code-generated `emitWarning`)
- **Date**: 2026-09-29

## Context

TDD-00230 P3.1 moves the Node surface to TypeScript modules. `process.on`
was code-generated: a literal event name from a fixed list (four signals,
`exit`, `uncaughtException`, `unhandledRejection`, `warning`, `message`),
one listener slot per event, arrow literals only, no `once`/`off`/`emit`,
and `process` itself was not a value (`const p = process` failed with
"undefined variable"). readline's Ctrl+Z path needed `process.once`, and
`events.once(process, 'SIGINT')` could not compile.

## Decision

`process`'s emitter half is `lib/node/internal_process.ts`, ported from
Node's lib/internal/bootstrap/node.js, lib/internal/process/per_thread.js
and the child side of lib/internal/child_process.js:

- `_kmlProcess()` makes the object on first use: an `EventEmitter` with
  Node's `newListener`/`removeListener` hooks and the default `warning`
  printer registered, as Node's bootstrap registers them.
- Signals: a signal's first listener starts a watcher
  (`__kml_native.signalStart`), and removing its last listener stops it,
  which restores the default disposition. A refused signal (SIGKILL,
  SIGSTOP) throws Node's `uv_signal_start EINVAL` ErrnoException. The
  runtime keeps one pending flag and one watcher per signal number (1–64).
  The handler sets the flag and the event loop's iteration runs the
  watcher (`__kml_signal_dispatch`), replacing the four fixed IR slots.
  Watchers never hold the loop open, as Node's signal handles are unref'd.
- Runtime events: the runtime raises `exit`, `uncaughtException` and
  `unhandledRejection` through hooks the module registers
  (`processHook(which, (a: any, b: any) => void)`). The last two are
  registered only while they have listeners, so the runtime's own default
  applies otherwise. `uncaughtException` gets the thrown value itself (it
  used to get the Error, or null for any other value) and its origin; a
  non-Error rejection reason is wrapped in Node's `UnhandledPromiseRejection`
  (`ERR_UNHANDLED_REJECTION`). An `exit` listener may set
  `process.exitCode`, and `process.exit(code)` sets it before emitting, as
  Node does.
- `process.emitWarning` is `lib/node/internal_process_warning.ts`
  (Node's warning.js). It emits `warning` on the next tick with an `Error`
  carrying `name`, `code` and `detail`, and Node's `onWarning` prints it.
  That module imports nothing, so `events` can warn; until the emitter
  exists, the warning goes straight to the printer.
- The fork channel's child side is the emitter's too. When
  `NODE_CHANNEL_FD` is set, `send`, `disconnect`, `connected`, `channel`,
  `message` and `disconnect` are a `net.Socket` over the descriptor, speaking
  the parent's json serialization. It is unref'd except while `message` or
  `disconnect` listeners exist (Node's `refCounted`). `process.send` is
  undefined in a program that was not forked.
- Code generation binds `process.<emitter member>`, `send`, `disconnect`,
  `connected`, `channel` and `process` as a value to `_kmlProcess()`, and
  `process.emitWarning` to the TypeScript function. The resolver brings the
  modules in when a file names those members, or when a program file uses
  `process` as a value. `lib/node.d.ts` declares the members with
  @types/node's overloads, so listener parameters are contextually typed.

The code-generated `process.on`, `emitWarning`, `send` and `disconnect`
are deleted, along with the child-side message-listener path of the IPC
runtime. The cluster worker still announces through that runtime. Once
the channel is the emitter's (`ipcChildClaim`), the runtime's reader
leaves the descriptor alone.

## Side effects discovered

Four compiler bugs on the port's path are fixed in their own records:
- the `object` type (ADR-01251);
- a function-typed top-level `let` read from a named function (ADR-01252);
- optional chains and calls on `any` (ADR-01253).

Two gaps remain:
- A handled `uncaughtException` from a synchronous throw still exits, as
  before (the status caveat).
- `const [x] = await once(...)` does not compile. Array destructuring of an
  awaited `any` is not supported.

## Verification

Mac (Apple Silicon), against Node v24.19:
- New tests: `TestE2EProcessIsEventEmitter`, `TestE2EProcessLifecycleEventArgs`,
  `TestE2ESignalAnyNameOnceAndRemoval` and `TestE2ESignalKillRefused`.
- The literal-name rejection tests are gone; Node accepts any name.
- The fork and cluster tests now use tsc's forms (`process.send!`, and an
  annotated `message` parameter, which @types/node types `unknown`).
- The signal, process, child-process, cluster, readline, events, stdin and
  tty groups all pass.

Windows was not run: the signal install goes through the existing
`signal()` shim, and the path is compile-checked only.
