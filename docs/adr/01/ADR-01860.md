# ADR-01860: Nested patterns under a parameter default, typed as tsc types them

- **Relations**: `Implements TDD-00230` (P3.3: found while answering the shadow report's MemberExpression bucket)
- **Date**: 2026-10-21

## Context

- A parameter whose pattern nests and whose default is an array literal holding an empty literal (`([[,] = g()] = [[]])`, Test262's `dflt-ary-ptrn-elem-ary-elision-*` family) had no type: the empty inner literal has none of its own, and the checker gave up on the whole parameter, and so on the method and every read of it (`C.method`).
- tsc types that inner literal by binding-pattern context: the empty tuple `[]` where the nested pattern's context is tuple-like (no default of its own, or an array-literal one), else `never[]`.
- Separately, the strict lane reported TS7031 for every leaf of a nested pattern with a default (`([[y] = g()])`), which tsc accepts: the leaves take their types from the default. tsc reports TS7031 there only for the positions an array-literal default leaves out (`[[w, v] = [1]]`: v), and TS2339 for a key an object-literal default lacks (`[{ k } = {}]`).

## Decision

- `patternDefaultType` types an empty array literal under a nested array pattern as `[]` or `never[]` by that rule, and an empty object literal under a nested object pattern without a default by the pattern (`impliedPatternType`).
- `reportImplicitAnyLeaves` reports, under a defaulted sub-pattern, only the positions past an array-literal default's length, and checks an object sub-pattern's keys against the default's type (`checkPatternProps`).

## Consequences

- `TestNestedPatternEmptyDefault` holds tsc 5.6's declaration types; `TestCheck` holds its TS7031/TS2339 lines.
- A pattern element with a default still implies a required tuple element where tsc implies an optional one (`([x = 1])` is `[number]`, tsc's `[(number | undefined)?]`): this checker's tuples have no optional elements yet.
- Verified on Apple Silicon.
