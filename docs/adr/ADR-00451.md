# ADR-00451: old-style angle-bracket type assertions `<T>expr`

- **Relations**: Extends [ADR-00371](ADR-00371.md)
- **Date**: 2026-08-29

## Context

The TS acceptance oracle's `unexpected token < in expression` bucket (110
false-rejects) is the pre-`as` type-assertion spelling `<T>expr`, used
throughout the older half of the TypeScript test corpus.

## Decision

A `<` can never begin an expression in .ts (no JSX dialect here), so the
prefix position is unambiguous: `parseUnary` consumes `<`, a type
annotation, `>`, and returns the operand's own parse — erased exactly like
the postfix `expr as T` form (ADR-00371), keeping the operand's inferred
type. Binary `a < b` is untouched (the `<` there is never in prefix
position). Nested assertions (`<number><number>x`) fall out of the
recursion for free.

## Implementation notes

`parser/parser_exprs.go`, one prefix case at the top of `parseUnary`.
`expectGT` handles the closing bracket (including `>>` splitting).

## Verification

Mac. `tests/as_cast_test.go` additions (erasure E2E incl. `<number[]>`
array form and precedence `<number>n * 2`; a less-than non-regression
test) and the `examples/types/erased-syntax.ts` extension pass; parser +
expression/generics E2E batches green. TS oracle: **54.7% → 54.9%**
(match-accept 1306 → 1337). Node oracle unchanged (37).
