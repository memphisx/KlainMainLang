# RegExp

> Part of the [Implementation Status](README.md) index.

**Coverage**: 13/14 (~93%) · **Strict Coverage**: 2/14 (~14%).

This page follows the shared status-page format ([Status page format](README.md#status-page-format)): **Status** is a bare ✅/❌; **Caveats** lists behavioral divergences from real JS/TS (a non-empty Caveats cell is what excludes an otherwise-✅ row from Strict Coverage); **Notes** carries implementation/representation detail only. One table per index category; each category's figures above derive from its table below.

All 7 stages are done, including Stage 6 (`--static` linking, verified both on bare Linux and inside a real Docker `scratch` container — `docker/Dockerfile.regexp-test`; PCRE2 has no TLS-backend-style transitive dependency chain, unlike `fetch`'s libcurl, so it links with zero extra flags — see [ADR-00120](../adr/ADR-00120.md)). See [TDD-00035](../tdd/TDD-00035.md) for the full design and [ADR-00114](../adr/ADR-00114.md), [ADR-00115](../adr/ADR-00115.md), [ADR-00116](../adr/ADR-00116.md), [ADR-00117](../adr/ADR-00117.md), [ADR-00118](../adr/ADR-00118.md), [ADR-00119](../adr/ADR-00119.md), [ADR-00120](../adr/ADR-00120.md) for what actually shipped.

Matching now follows the **ECMAScript dialect by default** ([TDD-00067](../tdd/TDD-00067.md) Options A + B, [ADR-00206](../adr/ADR-00206.md); Stage 3 `es-utf16` index mode + the global empty-match fix, [ADR-00207](../adr/ADR-00207.md); Stage 4 `ecmascript` normalization pass v1, [ADR-00208](../adr/ADR-00208.md); verified on Apple Silicon, pcre2 10.47). The whole-program `-regex=<mode>` flag selects fidelity: `ecmascript` (default — `es-unicode` matching plus the Option C source-normalization pass, which rewrites `.` to ECMAScript's exact "any character except a line terminator" so it matches `\x0b`/`\x0c`/`\x85` as real JS does), `es-unicode` (`PCRE2_UTF` code-point matching + `NEWLINE_ANY`, plus the option-level fixes — no normalization), `es-utf16` (`es-unicode` matching plus true UTF-16 code-unit positions at every user-visible offset — `str.search`'s return, `lastIndex`, a replace callback's `offset` — instead of the byte offsets the rest of the string layer uses), `es-ascii` (the option-level fixes only, byte matching — smallest/fastest for known-ASCII programs), or `pcre` (raw PCRE2/Perl semantics, no ES wrapping — an explicit opt-in for PCRE-only features, *not* a fallback). This retired the three PCRE2-vs-ECMAScript correctness bugs previously listed here (`$`/newline, unset backref, `\uXXXX`/`\xXX` throw) for the ES modes. A separate, previously-undisclosed hang — a zero-length-capable global pattern (`/x*/g`) sending `str.match`/`matchAll`/`replaceAll` into an infinite loop — is also fixed in every mode ([ADR-00207](../adr/ADR-00207.md)). The `ecmascript` normalization pass is **v1** — only the exact `.` rewrite so far; the remaining Option C sub-items (`\u{…}`/`\p{…}`, Unicode `\w`/`\s`/`\b`, Annex-B legacy octal escapes, exact `$`/`m`) are deferred and disclosed in Known limitations below.

## Known limitations

- **No implicit string→RegExp coercion.** Neither `match()`/`matchAll()`/`replace()`/`replaceAll()`/`search()` implicitly coerces a non-`RegExp` argument (a compile-time error instead), unlike real JS.
- **Dialect-mode caveats** (the ECMAScript alignment shipped in [TDD-00067](../tdd/TDD-00067.md) Options A + B / [ADR-00206](../adr/ADR-00206.md), Stage 3 / [ADR-00207](../adr/ADR-00207.md), Stage 4 / [ADR-00208](../adr/ADR-00208.md); what still diverges from ES, per mode — these residuals exclude the matching rows above from Strict Coverage):
  - **`ecmascript` (default) — `.` is exact; `$`/`m` still over-exclude three control chars, and Option C is v1.** The normalization pass rewrites `.` to ECMAScript's exact "any character except a line terminator" class, so `.` correctly matches `\x0b`/`\x0c`/`\x85` (unlike es-unicode). But `$`/`m` still use `PCRE2_NEWLINE_ANY` and anchor at those three extra chars, where ES does not — exact anchoring needs a further `$`-rewrite (deferred). The pass is v1: it does **not** yet handle `\u{…}`/`\p{…}` code-point escapes, ES Unicode `\w`/`\s`/`\b` semantics, Annex-B legacy octal escapes, or the `u`/`v` flags.
  - **`es-unicode` (opt-in) — `.`/`$`/`m` over-exclude three rare control characters.** The newline convention is `PCRE2_NEWLINE_ANY`, the closest single PCRE2 convention to ES's exact line terminators `\n \r \u2028 \u2029`, but it additionally treats `\x0b` (VT), `\x0c` (FF), and `\x85` (NEL) as line boundaries — so `.` excludes them and `$`/`m` anchor at them, where ES does not. Use the default `ecmascript` (whose normalization pass fixes `.`) if this matters.
  - **`es-utf16` — offsets diverge from the byte-indexed string layer, by design.** `str.search`/`lastIndex`/replace-callback `offset` report UTF-16 code units, but `.charCodeAt`/`.length`/`.slice` stay byte-indexed (ADR-00028), so a program that feeds an `es-utf16` RegExp offset into `str.slice(...)` over non-ASCII text gets mismatched positions. This is why `es-utf16` is opt-in and not the default. Matching is identical to `es-unicode`, so every `es-unicode` matching caveat applies to it too.
  - **`es-ascii` — `.` matches `\r`.** With no compile context, PCRE2's default newline convention treats only `\n` as the line end, so `.` matches `\r` where ES excludes it. Deliberate: `es-ascii` is defined as option-bits-only. Use the default `es-unicode` (which excludes `\r`) if this matters.
  - **`pcre` — raw PCRE2/Perl semantics throughout.** All three retired correctness divergences (`$`/newline, unset backref, `\uXXXX` throw) reappear by design in this mode; it exists for PCRE-only features and pattern porting, not ES fidelity.
  - **`es-unicode`/`ecmascript` — `\w`/`\s`/`\b` are not Unicode-aware.** `PCRE2_UCP` is deliberately not enabled: its Unicode-property tables diverge from ECMAScript's (UCP `\s` matches U+180E, dropped as whitespace by ES in Unicode 6.3), and enabling it *lost* net conformance on `built-ins/RegExp`. So `\w`/`\s`/`\b` match the ASCII/PCRE-default set, not ES's Unicode definitions — the ES Unicode class semantics are the deferred part of Option C ([TDD-00067](../tdd/TDD-00067.md)); the shipped `ecmascript` v1 does the `.` rewrite but not this. Code-point `.` (from `PCRE2_UTF`) is unaffected and works.
  - **`u`(nicode) flag still not implemented in any mode.** `es-unicode`'s `PCRE2_UTF` gives it code-point matching, but `\u{…}` code-point escapes, surrogate handling, Unicode `\p{…}`/class semantics, and strict-syntax validation are Option C — the `u`/`y`/`d` flags remain out of scope (see the row above).
