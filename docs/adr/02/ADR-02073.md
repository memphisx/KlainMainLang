# ADR-02073: The runtime files a program links do not depend on map order

- **Relations**: Implements TDD-00230
- **Date**: 2026-11-24

## Context

Comparing the clang link commands of every example between two compilers
showed six examples linking a different set of runtime C objects. The
same compiler, compiling `examples/date/date.ts` four times with the same
cache, linked `task.o` once and not the other three times.

## Investigation

`resolveRuntime` (`runtime_resolve.go`) picks the runtime files a program
reaches. Linking a file adds its definitions, and a later file that
defines one of them no longer links (`clashes`); one whose closure needs
an unlinked library does not either (`closes`). So the order in which
symbols are considered decides the outcome. That order came from ranging
over Go maps: the program's named symbols (`irNamed`), the weak
definitions seeding the work list (`irWeak`), and each linked file's weak
and undefined symbols appended as it was pulled in (`add`). Go randomizes
map iteration, so the set differed between compiles.

`closes` also ranges over a map, but explores every reachable file and
fails if any does, so its answer does not depend on the order.

## Decision

Every walk over a set of names in `resolveRuntime` goes in name order
(`sortedNames`).

## Consequences

- A program links the same runtime files on every compile.
- The library drift check (`make drift`) compares library IR only, so it
  did not see this; the comparison of link commands across all examples
  did.
- Verified on Node304 (Linux x86-64): eight compiles of `date.ts`, and
  four of each of the five other examples that differed, link the same
  objects every time.
