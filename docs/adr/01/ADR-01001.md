# ADR-01001: `undefined` for a nested-array (`T[][]`) element result

- **Relations**: Implements TDD-00221; Extends ADR-00778 (TDD-00187 scalar/pointer `T | undefined`)
- **Date**: 2026-09-17

## Context

An element-absence op (`.pop()`/`.shift()`/`.at()`/`.find()`/`.findLast()`) on a
`T[][]` receiver returns `T[] | undefined`, but the element type is the
`{ptr, i64}` array aggregate, which TDD-00187 left unflagged (`undefinedableElem`
skipped `IsArray`). Five `array-methods` rows carried the caveat "a nested-array
element still zero-fills the miss (`{null,0}`) instead of `undefined`".

Re-characterising against `node` showed the miss (a null *data-ptr* aggregate)
was already read correctly by `===`/`== null`/truthiness/`Array.isArray` — the
null-vs-empty-header discriminator from TDD-00213 (a genuine empty inner `[]`
allocates a header, so its data-ptr is non-null). What was still wrong were the
value-producing / coercion ops:

```
typeof p            "object"   (Node "undefined")
String(p) / `${p}`  the join   (Node "undefined")
JSON.stringify(p)   "[]"       (Node: the value undefined)
p ?? alt            not nullish (and a type-mismatch reject)
console.log(p)      []         (Node "undefined")
Array.isArray(p)    true       (Node false)
```

## Investigation

A raw "null data-ptr ⇒ undefined" rule in the coercion sites is **wrong**: a null
data-ptr is also how an explicit `null` array is stored, and `typeof null` is
`"object"` while `typeof undefined` is `"undefined"` (`String(null)` is `"null"`,
not `"undefined"`). The static type must carry the `IsUndefined` vs `IsNull`
discriminator. `typeof` was found to be a *static* answer (`typeofString`), so it
reported `"undefined"` for a flagged value even when present — a latent bug for
the scalar/pointer `T | undefined` cases too (`typeof strArr.find(...)` on a hit
was already `"undefined"`).

## Decision

1. `undefinedableElem` (`emit_undefined.go`) now flags an `IsArray` element type
   `Nullable | IsUndefined`; the miss producers already store the `{null,0}`
   aggregate, so no producer change is needed.
2. `typeof` becomes a *runtime* answer for any `T | undefined` value
   (`emitUndefinedableTypeof`): test the presence signal — nullable-scalar
   presence bit, a null pointer, or a null array data-ptr — and pick the base
   type's typeof when present, `"undefined"` when absent. This also fixes the
   pre-existing scalar/pointer `typeof`-when-present bug.
3. The array coercion sites gained a null-data-ptr branch keyed on `Ty.Nullable`:
   - `emitValueToString` — `String`/template → `absentLiteral` ("undefined").
   - `emitNullCoalesceArray` — `??` treats a null data-ptr as nullish.
   - `JSON.stringify` — top-level (`emitJSONStringifyNullableArray`, result value
     `undefined`), array element (`null`), and object field (dropped).
   - `console.log` (`emit_call_console.go`) and nested `util.inspect`
     (`emitInspectField`) — render "undefined", not `[]`.
   - `Array.isArray` — runtime false on a null data-ptr.

The strict-consumer gate (`checkStrictUndefinedAssign`) is **not** wired for
arrays, so `const x: T[] = m.pop()` stays a lenient accept as it was before —
no new rejections, no test/example fallout. Tightening that to a faithful strict
rejection (as `tsc --strictNullChecks` does) is a separate, optional strictness
change, not required to close these caveats; deliberately deferred to keep the
change contained (TDD-00221 records it).

## Implementation notes

- Each site tests the aggregate's field-0 data-ptr; a genuine empty `[]` has a
  non-null data-ptr, so it always reads present.
- `emitUndefinedableTypeof` returns `ok=false` for a shape it can't classify,
  falling back to the static answer.
- One existing test (`TestE2ENestedArrayHOFCallbacks`) asserted the pre-fix bug —
  a `.find()` miss comparing `=== null` true. Corrected to the JS-faithful
  result (`undefined === null` is false).

## Side effects discovered

- `typeof` on a present scalar/pointer `T | undefined` was statically
  "undefined" — fixed here as part of making `typeof` runtime for the family.
