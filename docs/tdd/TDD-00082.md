## Context

[TDD-00008](TDD-00008.md) established external conformance corpora as a real,
outside-in coverage benchmark and took it from a hand-curated idea (V1) to an
automated full-corpus runner (V2). That work covers exactly one layer of the
stack: TC39's **Test262**, the ECMAScript *language* suite. The status index's
other two big buckets — **Web Platform APIs** (`URL`, `fetch`, `Event`/
`EventTarget`, `AbortController`, encoding, streams, crypto) and **Node.js APIs**
(`fs`, `path`, `os`, `http`, `process`) — have no external oracle at all; their
coverage numbers are still entirely self-reported, the exact gap TDD-00008 set
out to close for the language layer.

This document supersedes TDD-00008 rather than appending a third "V3" section,
matching the [TDD-00077](TDD-00077.md)-supersedes-[TDD-00015](TDD-00015.md)
precedent: the scope widens from "one language suite" to "one benchmark story
across all three buckets," and the new home carries the inherited Test262 track
forward unchanged while adding two tracks with materially different economics.
As with that precedent, TDD-00008's design text stays the honest record of its
own moment; only its `Status` line is updated to point here.

A specific candidate — `nodejs/node-api-cts` — prompted this. It was evaluated
directly (Investigation below) and **rejected as the wrong layer**: it is the
Node-API *native-addon C ABI* conformance suite (`napi_*` functions, `.node`
addon hosting), aimed at runtimes that host native addons. This compiler emits
standalone native binaries and hosts no addons, so it has no `napi_*` surface for
that suite to test.

## Investigation: `nodejs/node-api-cts`

**Checked directly, not assumed** (repository README). It validates
implementations of the Node-API native-addon interface — the `napi_*` C functions
in `js_native_api.h`/`node_api.h` — with tests written in C/C++ and ECMAScript,
for runtime engineers proving their addon-hosting ABI. Out of scope: this
compiler has no addon-hosting layer to conform. Recorded and dismissed.

## Investigation: Web Platform Tests (WPT)

**Investigated directly, not assumed**: sparse-cloned `dom/events`, `dom/abort`,
and `url` (blobless, pinned checkout) and measured the slice.

- **Most of the raw file count is out of scope by construction.** Of 231 files
  in the slice, 174 are `.html` — browser tests that build a real document tree
  and dispatch events through DOM nodes (`addEventListener` on a `<div>`, capture/
  bubble across elements). With no DOM, these are legitimately inapplicable, the
  same "stricter, deliberately different runtime" filter Test262's writable-
  `Array.length` category hit.
- **The runnable core is the multi-global harness files.** WPT's `.any.js`/
  `.window.js` files are exactly the ones a non-browser host runs (Node imports
  this subset into its own `test/`). The slice has **47** such files; **35 are
  DOM-free** (12 still reach for `document`/`window`/`Element` despite the
  extension and drop out). `url/` alone contributes **28** headless files (URL is
  a pure API with no DOM) — though **10** load a `resources/*.json` fixture, so a
  real run needs file IO in the harness driver.
- **`dom/abort` is a near-exact oracle for the cancellation work just shipped.**
  Its 4 `.any.js` files assert `signal instanceof AbortSignal`, `signal.aborted`,
  `signal.reason instanceof DOMException`, and `signal.reason.name ===
  "TimeoutError"` — precisely the DOMException + `TimeoutError` behavior added in
  [ADR-00240](../adr/ADR-00240.md). They would also honestly *fail* on this
  compiler's known caveats: they use the `signal.onabort` handler property (only
  `addEventListener` is implemented) and `async_test`/`step_func` callbacks that
  depend on a background timer actually firing — i.e. the lazy-`aborted`/no-
  background-latching caveat. That is the point of an external oracle: it names
  the gaps instead of trusting self-report.
- **Harness surface is bounded, like Test262's.** Across the slice the assertion
  vocabulary is ~15 functions — `test`, `promise_test`, `async_test`,
  `assert_equals`/`_true`/`_false`/`_array_equals`, `assert_throws_js`,
  `assert_throws_dom`, `assert_unreached`, and a few long-tail ones — plus a
  `// META:` frontmatter line (globals selector), structurally the same extract-
  frontmatter + prepend-harness shape the Test262 runner already implements.
  `assert_throws_dom` (checks a thrown DOMException by name) is newly satisfiable
  after [ADR-00240](../adr/ADR-00240.md).
- **The new cost over Test262 is async.** `promise_test`/`async_test` (98 + 73
  uses in the slice) need the harness to await and the event loop to advance —
  which couples a WPT track's usefulness to the same async-model work the current
  plan is doing first. That ordering is deliberate: WPT lands *after* async/await
  and cancellation, so the oracle has something real to measure.

**Conclusion**: WPT is the right external benchmark for the Web Platform bucket
and is automatable as a track parallel to Test262 — restricted to headless
`.any.js`/`.window.js` files (the `.html` DOM majority stays out of scope, kept
visible in the report rather than deleted), behind a `testharness.js`-shaped shim.
It is the highest-value new track, but it is gated on the async work.

## Investigation: Node's own `test/` suite

**Investigated directly, not assumed**: sparse-cloned `nodejs/node`
`test/parallel` + `test/common` and measured.

- **It is the only behavioral corpus for the Node-specific modules** (`fs`,
  `path`, `os`, `http`, `process`) — WPT does not cover them.
- **But it is almost entirely coupled to Node's internal harness.** Of 4,234
  `test-*.js` files, **4,229 (99.9%) `require('../common')`** and 3,639
  `require('assert')`. Running any meaningful fraction means shimming Node's
  `common` module (platform probes, `mustCall`, tmpdir, flags) plus `assert` plus
  a CommonJS `require` — a substantially larger adaptation cost than Test262 or
  WPT, both of which are a frontmatter-plus-small-assert-shim.
- **The distribution splits work sharply.** The pure/near-pure modules are small
  (`path` 17, `querystring` 4, `url` 18, `os` 8, `assert` 14 files); the bulk is
  side-effectful and partly out of scope (`fs` 259, `http` 755, `stream` 250,
  `buffer` 72, `process` 94), leaning on real filesystem/socket state and dynamic-
  JS behavior.

**Conclusion**: worth adopting, but **not** as a full-corpus automated track like
Test262/WPT — the `common`-harness coupling and side-effect surface make that a
poor cost/return. Two viable shapes, decided at implementation time: (a) build the
minimal `require`+`common`+`assert` shim and automate only the pure modules
(`path`/`querystring`/`url` ≈ 39 files), or (b) mine value-semantics cases by hand
into the E2E suite, the TS-suite checklist treatment. Lower priority than WPT.

## Design (going forward — implementation deferred)

Four tracks, by descending automatability:

1. **Test262 (language)** — inherited from TDD-00008, unchanged. Full-corpus
   automated runner + honest per-category report.
2. **WPT (Web Platform)** — new automated track, parallel to Test262. Fetch (not
   vendor) a pinned checkout; run only headless `.any.js`/`.window.js`; a
   `testharness.js` shim exposing the ~15-function surface above (sync first;
   `promise_test`/`async_test` once the async model supports it); `// META:`
   frontmatter extraction; a harness driver able to load `resources/*.json`
   fixtures for the URL files. Report alongside Test262, with `.html`-DOM and
   DOM-touching `.any.js` files reported as an explicit out-of-scope bucket, not
   silently dropped. **Gated on the in-flight async/await + cancellation work.**
3. **Node core** — semi-automated, pure-modules-only (`path`/`querystring`/`url`)
   behind a minimal `common`+`assert`+`require` shim, or hand-mined; explicitly
   *not* full-corpus. Lower priority.
4. **TypeScript conformance suite** — unchanged checklist treatment (no runnable
   oracle exists); finish the remaining category scan only.

Shared infrastructure reused as-is: the fetch-don't-vendor pattern
(`tools/conformance/fetch.sh` gains WPT/Node checkouts into gitignored dirs), the
frontmatter-extract + harness-prepend + compile-through-the-real-pipeline runner
shape, and the generated honest-numbers report (`CONFORMANCE-RESULTS.md`) beside
the qualitative coverage doc (`CONFORMANCE-COVERAGE.md`).

### TypeScript version coverage (low priority)

TypeScript is a versioned language: each release adds syntax/type surface (e.g.
`satisfies`, `const` type parameters), and both Microsoft's suite and the language
it targets move with it. Two small implications, both explicitly deprioritized:
the mined corpus should be pinned to a specific TS release tag (as Test262 is
pinned by SHA), so the checklist has a stable denominator; and a *per-version*
coverage view (what fraction of TS N's feature set this compiler accepts) is
conceivable but low value now — this compiler targets a deliberately narrow typed
subset, so "which TS version" is far behind "which features at all." Recorded so
it is not rediscovered later; not planned.

## Open questions

- WPT track: shim `testharness.js` to compile-and-run each `.any.js` (Test262
  shape), or adopt Node's own `test/wpt` driver design as a reference? Lean toward
  the former, to reuse the existing runner wholesale.
- Node track: build the `common`/`require` shim for the ~39 pure-module files, or
  hand-mine value-semantics cases into `compiler_test.go`? Decide when the async
  work clears and this track is actually picked up.
- Whether the URL surface is better served by WPT's `url/` (28 headless files) or
  Node's `test-url*` (18 files) — likely WPT, since it is the standards oracle and
  needs no `common` shim; measure both when track 2 begins.
- Does a single generated report cover all tracks, or one per corpus? Deferred to
  implementation; the Test262 report format already generalizes.
- **Blocked-by histogram (prioritization instrument).** The runner already buckets
  a failure by reason (compile-error first line, `RUNTIME_NONZERO_EXIT`, …). Extend
  the report with a ranking of *which unimplemented API/syntax* causes the most
  files to fail at compile — a measured worklist of unblock leverage across all
  three corpora. This matters because an unimplemented API doesn't only cost its
  own tests: a file that references it in setup/harness compile-fails, masking any
  bug in the valuable feature that same file also exercises, so implementing the
  API flips the file to actually-running and surfaces the hidden bug. It also
  ranks the intrinsically-low-value leaf APIs (webstorage/notifications/IndexedDB/
  XML) by how much corpus they each unblock — the honest basis for doing them in
  the end-game rather than never. A report feature, not a language feature; cheap
  and worth doing early once any track past Test262 is live.
