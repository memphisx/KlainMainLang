# ADR-01005: lost-wakeup hang in concurrent task-await handlers (mid-scan conn poke)

- **Relations**: Extends ADR-00986 (fixes a race in its conn-poke protocol)
- **Date**: 2026-09-18

## Context

`TestE2EHTTPCreateServerAsyncHandlerConcurrentTaskAwait` (4 concurrent requests
whose async handler awaits a task-shaped `proxy` helper) hung the full
`make test-par` run once: one of the 4 Go-side `http.Get`s was never answered
and the shard sat until the go-test timeout's goroutine dump. The test passes
reliably in isolation — the failure needed the load of 4 parallel test shards.

## Investigation

- Reproduced deliberately: 30 runs of the single test under 8 CPU-hog
  processes → **9/30 hangs** (never in isolation). Each hang leaves exactly
  one request unanswered.
- `sample` of a live hung server: 100% of samples blocked in `select()` inside
  `__kml_event_loop_run` — a terminal blocking select, not slowness. So on the
  final iteration every "don't block" predicate in `ctodone` read false while a
  fiber was still parked.
- The park/wake chain for this shape: the conn fiber parks in the task-await
  `fyield` loop; its resume signal is the global one-shot `@__kml_conn_poke`,
  set by `__kml_task_finish`/`__kml_task_reject`. The resume scan runs after
  `select()`; `ctodone` (the select-timeout decision) reads the poke at loop
  bottom; ADR-00986 documented the ordering this relies on.
- The hole: the scan consumed the poke by clearing it **after** the scan
  (`checktimerfire`). But a fiber resumed mid-scan drives the scheduler from
  its own await loop (`fdrive` → `__kml_task_sched_step`), which can finish
  **another** fiber's awaited task and set the poke — and when that other fiber
  sits at an earlier index, it was already scanned un-poked. The post-scan
  clear then wiped the flag before `ctodone` ever saw it. With that task
  finished (`__kml_task_resumable` false — it only reports *suspended* tasks),
  no curl fds left and no timer, `select()` blocked forever and the victim's
  response was never written.
- Load-dependence: the window needs several fibers parked on task-awaits with
  upstream completions landing mid-scan in the right index order — CPU
  starvation jitters the 4 × 300 ms completions into it.

## Decision

Snapshot-and-clear the poke **before** the scan: `scanconn` loads
`@__kml_conn_poke` into a stack slot, clears the global, and the scan reads
only the snapshot; the post-scan clear at `checktimerfire` is removed. A poke
set during the scan now survives in the global, forbids the following
`ctodone` from choosing a blocking select, and is serviced by the next
iteration's snapshot. Spurious extra resumes stay benign by design (a resumed
fiber re-checks its own await condition and re-parks).

## Implementation notes

`codegen/llvm/runtime_http.go` only: the `%pokesnap` alloca, the
snapshot/clear at `scanconn`, the scan's read switched to the snapshot, the
`checktimerfire` clear dropped. No other consumer of the flag changes —
`ctodone` still reads the global, and all set sites are untouched.

## Side effects discovered

A go-test timeout panic skips `t.Cleanup`, so each hung run leaks its compiled
server process (observed live and used for the `sample`); harmless but worth
knowing when stray `…/T/TestE2E…/prog` processes linger after a timed-out run.

## Verification

macOS arm64 (M4). The same 30-run stress harness against the fix: **0/30**
hangs (part of the streak under doubled load — a second stress loop and 16
hogs overlapped). Full HTTP/Listen/Cluster/Upgrade/WebSocket/SSE suite passes;
`make examples` and a full `make test-par` pass against the final binary.
