# ADR-00918: Funcref identifier carries its signature for `.apply`/`.call`/`.bind` inference (invalid-IR sweep)

- **Date**: 2026-09-12

## Context

A named function used as a value through `f.apply()` / `f.call()` in an expression
position inferred `void` as its result type, even when `f` has a concrete return
type. When that result was itself returned — `return f.apply()` inside an
enclosing function — the enclosing function's return type was inferred `void`
while emit produced a real typed call (`ret i1`), so the `define`'s signature
disagreed with its `ret` (invalid IR: `value doesn't match function result type
'void'`). Surfaced in the Test262 CLANG_ERROR sweep
(`language/function-code/10.4.3-1-85{-s,gs}.js`, which do
`(function () { "use strict"; return f.apply(); })()`).

A second, adjacent defect: `f.call()` with no arguments at all (not even a
`thisArg`) panicked in codegen — `emitFunctionCallApply` sliced `args[1:]` on an
empty argument slice.

## Investigation

- `inferExprType` on a `.call`/`.apply`/`.bind` member call reads
  `inferExprType(mem.Object)` and uses its `FuncRetType` / `FuncParams`
  (`emit_exprs_types.go:1489`). For a bare function-name identifier, the
  `*ast.Identifier` case returned `Type{IR: "ptr", IsFunc: true}` with **no**
  `FuncRetType`/`FuncParams` (`emit_exprs_types.go:575`) — so `f.apply()` hit the
  `FuncRetType == nil → TypeVoid` fallback.
- The *emit* path (`emitFunctionCallApply`) resolves the real signature via
  `emitExpr(f)`, so the call was emitted with the correct return type — only the
  *inference* used by the enclosing function's return-type deduction was wrong.
- `resolveFuncRef(name)` already returns the function's `FuncSig`, so the
  signature is in hand at the identifier site.

## Decision

- Populate the funcref identifier's `Type` with its resolved signature:
  `FuncParams = sig.ParamTypes`, `FuncHasRest = sig.HasRest`, and
  `FuncRetType = &sig.RetType`. `.apply`/`.call`/`.bind` inference then sees the
  real return type instead of defaulting to void.
- Guard the `method == "call"` argument-forwarding slice in
  `emitFunctionCallApply`: forward `args[1:]` only when `len(args) >= 1`,
  otherwise an empty list.

## Implementation notes

- `codegen/llvm/emit_exprs_types.go` (`*ast.Identifier` funcref case) and
  `codegen/llvm/emit_func.go` (`emitFunctionCallApply`).
- The signature was previously deliberately omitted from the funcref Type; adding
  it is consistent with how a first-class closure value's Type already carries its
  params/return (the `.bind` inference path right below already expected it). The
  function/closure/async test lane confirms no consumer relied on the bare shape.

- `TestE2EFuncRefApplyCallReturnType`, `TestE2EFuncCallZeroArgs` (new).
- `language/function-code/10.4.3-1-85{-s,gs}.js` now compile and exit 0 (were

- Function/closure/apply/call/bind/async test lane green (`go test -run`, ~201s).
  macOS arm64.
