# ADR-01027: Windows `{ workers: N }` cluster — round-robin hand-off, live workers, shared close flag

- **Relations**: `Implements TDD-00177` (Stage 4 cluster scheduling, open question 7); `Extends ADR-00719` (re-spawned cluster workers), `ADR-00989` (cluster + `createServer` listeners), `ADR-01022`/`ADR-01025` (the reactor and fd layer it sits on); `Implements TDD-00117` (cross-worker `http.close()`) on Windows
- **Date**: 2026-09-20

## Context

`http.listen(port, handler, { workers: N })` forks `N-1` workers that share the listener. Windows has no `fork()`, so the primary re-spawns its own executable per worker (ADR-00719). Three cluster tests were skipped there as a "documented gap: shared-accept distribution instead of round-robin", and the status page carried the row "`cluster` round-robin — workers share one listening socket; `http.close()` from a worker doesn't reach siblings".

Removing the skips showed the gap was not what the documentation said. Every request was answered by one PID because **the workers were not running at all**.

## Investigation

1. **Workers died at startup.** `__kml_http_cluster_fork` read the listener to inherit from `@__kml_listen_fd`, but `emit_http.go` calls the fork *before* storing that global (harmless under `fork()`, which needs no fd; fatal for a re-spawn). The worker inherited nothing, was told to adopt fd `-1`/`0`, and exited. `tasklist` showed one process where three were expected.
2. **Shared accept cannot distribute on Windows.** With the workers alive and each holding a pending `AcceptEx` on the inherited listener (completions reaching the worker's own port through the emulated-completion path, since the socket is bound to the primary's port), sequential requests still all went to one PID. The kernel completes pending accepts most-recent-first: the process that just served re-arms and wins again. A variant that also stopped each process draining the backlog directly (libuv's single-pending-accept rule for shared sockets) was enough for a 40-goroutine burst to reach a second PID, but request-at-a-time traffic still stayed on one process. This is why libuv/Node do not share the listener on Windows: the primary accepts and deals connections out (`SCHED_RR`).
3. **The worker's listener was blocking.** A worker's `__kml_http_bind_and_listen` returns the inherited fd before the `fcntl(O_NONBLOCK)` the normal path performs. `O_NONBLOCK` is a file-description flag a forked child shares; this layer's flag is per-process, so the worker's `accept()` took the blocking branch and could park the whole event loop inside `accept()`.
4. **The close flag did not exist.** The cross-worker `http.close()` flag is an anonymous `MAP_SHARED` page inherited by `fork()`; the Windows `mmap` shim answers `ENOSYS`, and the worker never ran the allocation anyway. `TestE2EHTTPListenClusterCloseReachesAllWorkers` had been passing only because there were no workers to keep the port open.
5. `WSAPROTOCOL_INFOW` is 628 bytes (the 372 in TDD-00177's sketch is the ANSI structure). Sizing the hand-off buffer at 372 let `WSADuplicateSocketW` overrun the primary's stack; verified against the toolchain header.
6. With several listeners (ADR-00989's cluster + `createServer`), the single `KML_HTTP_LISTEN_FD` made every bind in the worker return the same fd.

## Decision

**Round-robin from the primary** (win32io.c, "cluster round-robin"). A cluster-worker spawn (`__kml_win_spawn` flag `0x20000`) hands the worker *every* listening socket the primary holds, each with the far end of a loopback socket pair. `KML_WIN_RR=<primary pid>|fd:listener:channel:nonblock;…` carries the handles; a constructor in the worker adopts each listener under the primary's fd number, registers the channel, and records it on the listener's description (`rr_chan`), together with the listener's non-blocking state (finding 3).

- *Primary*: `accept()` takes the connection as before (the completed `AcceptEx`, else the backlog), then gives it to whoever's turn it is — slot 0 is the primary itself, which stays one of the N serving processes exactly as under `fork()`. For a worker, `WSADuplicateSocketW` makes the descriptor for that pid, it is sent over the worker's channel, the primary closes its copy and loops to take the next connection. A channel that fails drops that worker from the rotation; one that would block skips the worker for this connection (the channel is non-blocking so a wedged worker cannot stall the primary); a descriptor is never left half-sent.
- *Worker*: read-interest in the listener is answered by the channel (`kfd_rd_src`): `select()` arms the channel's zero-read and projects its readiness onto the listener's bit. `accept()` reads one descriptor and `WSASocketW(FROM_PROTOCOL_INFO)` turns it into a socket. If the channel reaches EOF (the primary closed the listener or died) the worker accepts on its inherited listener directly from then on — it keeps serving, as a forked worker would.
- A worker's bind takes its inherited listener **by port** (`__kml_win_inherited_listener(port)`, first unclaimed one for port 0), so a program with several servers gets the right listener for each bind (finding 6). `KML_HTTP_LISTEN_FD` is gone.
- `close()` of a listener closes its channel(s).

**The fork hook takes the listener explicitly.** `__kml_http_cluster_fork(i64 workers, i32 lfd)` — no dependence on when `@__kml_listen_fd` is stored (finding 1). Windows ignores `lfd` now (the platform layer enumerates the listeners); the parameter keeps the contract honest for any future consumer.

**Shared close flag.** `__kml_win_cluster_flag()` maps a 16-byte section: the primary creates it where POSIX calls `mmap`, each worker **inherits its handle** at spawn, and both map it at the top of `__kml_http_cluster_fork`. The reactor's existing 200 ms poll then works unchanged.

The handle is inherited rather than the section opened by name, and the difference is not cosmetic — the first attempt named the section after the primary's pid and failed roughly one run in four. A named section exists only while some process holds a handle or view of it. A worker still starting up when the cluster shuts down reaches `CreateFileMappingW` after the primary and its faster sibling have already closed and exited, finds the name unused, and gets a **new, zero-filled section**: it then waits forever on a flag nobody will set again, holding the listening socket alive through its inherited handle so the port never stops accepting. An inherited handle exists from the moment the worker does and keeps the section alive by itself — the property `fork`'s shared page has for free.

**What stays different, and why.** A re-spawned worker runs the program from the top, so code before `http.listen` runs in every worker — as it does in every Node cluster worker, and unavoidably without `fork()`. `TestE2EHTTPListenClusteringFlushesStdoutBeforeFork` asserts the fork-only property (a banner printed once) and keeps a Windows skip under an accurate name (`skipForkOnlyOnWindows`); the status page records it under faithful platform differences.

## Implementation notes

`win32src/win32io.c` (`kfd_rr`, `kfd_listeners`, `kfd_rr_add_worker`, `kfd_rr_adopt`, `__kml_win_inherited_listener`, dispatch/recv, `accept`/`close`/`select` hooks, `WSADuplicateSocketW`/`WSASocketW` bindings, an `AcceptEx` failure trace line), `win32src/win32proc.c` (spawn flag, marker, handle list, worker constructor, `__kml_win_cluster_flag`), `runtime_spawn_win.go`, `runtime_http.go`, `emit_http.go`. Adoption order matters: all listeners are adopted at their fixed fd numbers before any channel takes a free one. `KML_IO_TRACE` prints `rr sock=… -> pid …`.

## Side effects discovered

The status row for cross-worker `http.close()` and the clustering row described the POSIX mechanism only; both now state the Windows one.

## Verification

Windows 11 (26200), MSYS2 UCRT64 clang. By hand, `{ workers: 3 }`: nine sequential requests rotate over the three PIDs in order; 90 concurrent requests split 30/30/30 (twice); all three processes stay alive. Tests now running on Windows with no skip: `TestE2EHTTPListenClusteringMultipleWorkerPIDs`, `TestE2EHTTPClusterCombinedWithCreateServer`, `TestE2EHTTPListenClusteringGCModeMultipleWorkerPIDs`; `TestE2EHTTPListenClusterCloseReachesAllWorkers` passes with live workers, 12/12 on repeat — it is also what caught the named-section lifetime bug above, and only in a *full-suite* run: in isolation the workers start fast enough to map the section before anyone exits, so the race never opens. Worth remembering that a green single-test run said nothing here; the `TestE2ECluster*` (Node `cluster` module) suite is unaffected; the full `./tests` package passes (0 failures, 1438 s). Linux: the full `./tests` package passes in Docker (`klain-ci`, Go 1.27.1 + clang 19), 0 failures — the shared change here is the extra `i32` parameter of `__kml_http_cluster_fork`, which that run exercises. macOS: not run, no machine reachable; CI is the check.
