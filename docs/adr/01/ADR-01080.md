# ADR-01080: child_process options — the *Sync forms in full, `exec`/`execFile` options + `maxBuffer`, ExecException properties

- **Relations**: Extends ADR-00411 (the sync sidecar), ADR-00753 (execSync throws), ADR-00433/00762/00764/00766 (spawn options), ADR-00754 (spawn failure shape); Extended by (fork options — open)
- **Date**: 2026-09-22

## Context

BACKLOG §2 "child_process options": `argv0`, `windowsVerbatimArguments`, `maxBuffer`; `env`/`timeout`/
`killSignal`/`stdio`/`shell`/`windowsHide` on `exec`/`*Sync`/`fork`; numeric-fd `stdio`; `execSync`'s Error
with `.status`/`.stdout`/`.stderr`. The sync forms took `{ cwd, encoding }` only, `spawnSync`'s result had
four fields, and the thrown execSync Error was a bare message.

## Investigation

- The sync sidecar (`runtime_spawnsync.go`) was a single `(file, args, argn, cwd, flags)` entry with two
  captured pipes and a wait. Every new option needs the sidecar (input feeding, timeout, maxBuffer, stdio
  modes, env), so it takes an options record instead of a growing argument list; the result grows `signal`
  and `error`. Windows starts the child through `__kml_win_spawn`, whose `-1`/`-2` stdio sentinels already
  mean inherit/NUL; its stdin write end is an overlapped handle `poll()` cannot report, so the input is fed
  from a thread there, while POSIX feeds it non-blocking inside the drain loop (and ignores `SIGPIPE`, as Node
  does process-wide — a sync spawn can run before the reactor's own ignore).
- Node's shapes, checked against Node 24 on Windows and known for Linux: `spawnSync` returns
  `{ status, signal, output, pid, stdout, stderr, error? }` in that key order; a never-started child is
  `status: null, pid: 0, stdout/stderr/output: null` plus the error; a signal death is `status: null`;
  `execSync` writes the child's stderr to ours unless `stdio` was given, throws the spawn/timeout/maxBuffer
  error as is or `Command failed: <cmd>\n<stderr>`, and decorates the Error with `status`, `signal`,
  `output`, `pid`, `stdout`, `stderr`. A first Windows run matched except for the key order, `""` where
  Node has `null` for an unpiped stream, and an undefined `status` where Node has `null` — all fixed.
- `errorObjType` is a fixed 13-field struct; the ExecException properties are arbitrary own properties. A
  14th field `extra` (a D1 dynamic-object bag, null by default) carries them, and the boxed-error arm of the
  dynamic member read consults it — the same arm now reads *every* fixed field (`code`, `errno`, `syscall`,
  `path`, …), where before only `message`/`name`/`stack` were readable through `any`.
- Two latent bugs surfaced: the async exec callback's Error was `malloc(24)` (three fields) but read through
  the full struct — a `err.code` read was out of bounds; and a closure parameter annotated `any`
  (`(err: any) => …`) called by a runtime with a concrete type (`errorObjType`) received the raw pointer bits
  in its i64 slot, which decode as a string-kind box — `err.message` was undefined. A third: a top-level
  `const isWin = process.platform === 'win32'` was not promoted to a module global (only `Math`/`Number`
  members were "constant" to the pre-pass), so a named function reading it failed to compile.
- POSIX `ENOBUFS` was missing from the errno-name table; Linux's `sched_getaffinity` needs `_GNU_SOURCE`.

## Decision

1. **Sync sidecar** (`runtime_spawnsync.go`): `__kml_cp_spawn_sync(file, args, argn, const kmlss_opts *)`
   with `{ cwd, env, input, input_len, timeout_ms, kill_signal, max_buffer, stdio, flags, argv0 }` (ten
   8-byte slots) and `kmlss_result { status, out, err, pid, signal, error }`. `status` is -1 for a signal
   death or a never-started child; `error` is the errno-shaped failure (`ETIMEDOUT`/`ENOBUFS`/the exec
   errno through a CLOEXEC status pipe, Linux numbering on Windows). A pseudo-pid refusal on Windows (ENOENT,
   the `.bat` EINVAL guard) is reaped and reported the same way.
2. **`emit_childprocess_sync.go`** (replacing the sync emitters): `cpSyncOptions` reads Node's full set —
   run-time values for `cwd`/`input`/`timeout`/`maxBuffer`/`argv0`/`env` values, literals for the knobs that
   change emitted code (`stdio`, `shell`, `killSignal`, `encoding`, `windowsHide`,
   `windowsVerbatimArguments`); `cpSpawnSyncResultType` is Node's record (`status: number | null`, `signal:
   string | null`, `output: (string | null)[]`, `error?: Error`); `cpExecSyncResult` mirrors stderr, builds
   the thrown Error and hangs the six ExecException properties on its `extra` bag; `shell: true` joins args
   with spaces, a `shell: <path>` takes `/d /s /c` when cmd-shaped else `-c`.
3. **Async** (`emit_childprocess.go`, `runtime_childprocess.go`): `exec(cmd[, options], cb)` /
   `execFile(file[, args][, options], cb)` accept the spawn options plus `maxBuffer` (1 MiB default) and a
   `shell` path; the cp struct gains `maxBuffer` (27) and `maxBuffer hit` (28), the drain loop kills the
   child past the limit, and the close path builds a full-size Error — `RangeError
   ERR_CHILD_PROCESS_STDIO_MAXBUFFER` for an overrun, else the exit error with `killed`/`signal` own
   properties. The two hard-coded `calloc(216)` sites now use `cpStructBytes`.
4. **`errorObjType.extra`** (`emit_exceptions.go`, `emit_dynobj.go`): the bag field, defaulted null in
   `buildErrorObj` (every IR allocator is calloc'd); the boxed-error member read falls through to it, and
   reads any fixed field generically (a null string field is `undefined`).
5. **`any`-annotated closure parameters with a concrete hint** (`emit_func.go`): the hint is the ABI type;
   the value is boxed on entry and the name bound as `any` (`closureBoxOnEntry`). Arrays, nullable scalars and
   destructured patterns keep their own paths.
6. **`process.platform`/`arch`/`execPath`/`version`/`pid` are pre-pass constants** (`processConstMember`),
   so a top-level binding built from them promotes to a module global.

`fork()` options stay open (its runtime is a separate fork/exec path on both platforms) — BACKLOG §2 keeps
that line. Numeric-fd `stdio` entries also stay open.

## Implementation notes

`codegen/llvm/runtime_spawnsync.go`, `emit_childprocess_sync.go` (new), `emit_childprocess.go`,
`runtime_childprocess.go`, `runtime_ipc.go`, `emit_exceptions.go`, `emit_dynobj.go`, `emit_func.go`,
`emit_exprs_vardecl.go`, `emitter.go`, `runtime_fs.go` (`ENOBUFS`). `aggregateErrorStructSize` is 112 now
(fourteen fields). The `kmlss_opts`/`kmlss_result` slot indexes are written by hand on the IR side
(`cpSyncOptsIR`, `cpSpawnSyncField`) — keep the two in step.

## Side effects discovered

- The exec callback Error's `code` stays null (Node's is the numeric exit code; the slot is a string) and
  `cmd` is absent — recorded on the row.
- `<`/`>`/`&&` on `any` operands are still rejected (the §1 D1 residue), which shaped the tests.

## Verification

Windows, byte-identical to Node 24 (`R:\kml-scratch\s26\cp1.ts`, `cp2.ts`, outputs diffed): the spawnSync
record and key order, `input`, `env`, `argv0`, timeout (`ETIMEDOUT`, `SIGTERM`/`SIGKILL`), `maxBuffer`
(`ENOBUFS`), `shell: true` with args, `stdio` inherit/ignore, `cwd`, the ENOENT spawn-failure shape, the
execSync/execFileSync ExecExceptions, and the six async exec/execFile scenarios (options, the maxBuffer
RangeError undecorated, `killed`/`signal`). Linux (Docker): the same sync probe by hand (`sh`/`cat`/`sleep`
children, a 300 KB input, `argv0` via `$0`, `ENOBUFS`, `status: null` + `pid: 0` on ENOENT), and the
child_process / error / closure / any / promise test subsets green on both hosts. E2E:
`tests/childprocess_sync_options_test.go` (eight tests, Node as oracle).
