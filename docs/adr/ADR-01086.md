# ADR-01086: A generator's `.next()` restores the caller's GC stack bottom

- **Relations**: `Extends ADR-01050, ADR-00098`
- **Date**: 2026-09-23

## Context

`make examples MM=gc` on Linux x86-64: `examples/classes/classes.ts` segfaulted, deterministically, at the first generator used after the file's top-level `await`s. The same example passes at the previous commit and with `GC_DONT_GC=1`, so this is a regression from ADR-01050, where an entry with top-level await became a module task on a coroutine stack.

## Investigation

- `generatorGCStackbottomOps` (`codegen/llvm/emit_generators.go`) repoints the collector's stack bottom at the generator's stack before the swap. After the swap it restored `@__kml_gc_orig_stackbottom`, the process stack, unconditionally.
- That was right while every `.next()` ran on the process stack. It is wrong when the caller runs on a coroutine stack: the module task, an async task, or another generator.
- The collector then scanned from the module task's stack pointer (an mmap'd block) to the process stack base, across unmapped memory.
- The task runtime already does this correctly: `__kml_task_gc_restore` restores the swapper's own stack.

## Decision

- Save the current stack bottom right before repointing, and restore exactly that value after the swap.
- `gcSBLoad` (`codegen/llvm/runtime_worker.go`) is the read side of `gcSBStore`:
  - single-threaded, `@GC_stackbottom`;
  - under Worker threads, the per-thread record through `GC_get_my_stackbottom` (a small `@__kml_gc_get_sb` helper);
  - on Windows, any defined value, because `gcSBStore` there reads the TEB and ignores its operand.

## Implementation notes

`emit_generators.go`, `runtime_worker.go`, `emitter.go` (the `usedGCSBGet` flag). The saved register is defined in the same straight-line block as the swap, before it.

## Side effects discovered

- `examples/async/for_await_iterables.ts` also passes under `-mm=gc` with this fix.
- `promise_all`, `fetch` and `fetch-abort` aborted with `Collecting from unknown thread`. Those three pass at the previous commit, so they are regressions too, fixed in ADR-01088.
- `crypto`, `wttr_weather` and the four TLS server/client examples crash at the previous commit as well. They are recorded in BACKLOG §0 item 20.
- The Makefile's memory-mode examples lane covers manual/auto. gc has its own suite, which is why no lane caught any of this.

## Verification

- `tests/task_reclaim_gc_tls_test.go` `TestE2EGCModeGeneratorFromModuleTask`: a generator driven from the module task with allocation pressure, so collections run mid-iteration.
- Windows x64: passes, along with the existing gc and generator tests.
- Linux x86-64 (Docker): re-run with the full suite and `make examples MM=gc`.
