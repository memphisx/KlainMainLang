# ADR-00073: Promise.all / .race / .allSettled

- **Relations**: Extends [ADR-00049](ADR-00049.md), [ADR-00050](ADR-00050.md). Implements [TDD-00016](../tdd/TDD-00016.md)
- **Date**: 2026-07-29

## Context

[TDD-00006](../tdd/TDD-00006.md) (Event Loop)'s two real slices — the `select()`-based wait loop and the fiber-based suspension mechanism used for concurrent `http.listen` connections and non-blocking `await fetch(...)` — were both already shipped, but only ever awaited *one thing per call site*. `Promise.all`/`.race`/`.allSettled` (fanning out to several concurrent operations from one call site and combining their results) was the explicitly named remaining gap in both `STATUS.md`'s roadmap and [TDD-00006](../tdd/TDD-00006.md)'s own closing paragraph — and a completely ordinary shape for the REST-API-client/microservice code this project's stated direction (`CLAUDE.md`) prioritizes. [TDD-00016](../tdd/TDD-00016.md) scoped the design; this ADR is that implementation.

## Investigation

- Confirmed the scope narrowing [TDD-00016](../tdd/TDD-00016.md) is built on directly from `emit_async.go`'s own header comment: an ordinary `async function`'s body runs to completion synchronously at call time, so `Promise<T>` for anything other than `fetch()`'s `Promise<Response>` is never actually pending by the time a program can observe it. This meant only the `Array<Promise<Response>>` case needed real concurrency machinery; every other `T` needed a plain synchronous collection loop.
- Read `ensureFetchAsync`'s existing pending-fetch struct layout (`{ ptr easy, ptr buf, i64 done, i64 httpStatus, i64 curlResult }`, `runtime.go`) and `__kml_await_fetch`'s existing wait loop (`checkloop`/`maybeyield`/`doyield`/`busyspin`) to confirm a "wait for N of these instead of one" primitive could be a structural clone reusing the exact same fiber-park/busy-spin branches, rather than a new mechanism — confirmed by inspection, no prototyping needed since the existing single-fetch mechanism was already proven correct by [ADR-00050](ADR-00050.md)'s own verification.
- **Two real bugs were found only by writing genuine end-to-end tests against a real `Response` array — not by design review or the ordinary-promise tests alone.** Both are described in Decision/Implementation notes below with the fix; the finding process itself:
  - `tests/async_test.go`'s three ordinary-promise combinator tests (`double(n): Promise<number>`) all passed immediately. This gave false confidence — the `Array<Promise<Response>>` branch (the actually-hard, actually-concurrent case) had zero coverage at that point.
  - Writing `tests/fetch_test.go`'s `TestE2EPromiseRaceFetchesReturnsFirstDone` (a local `httptest.Server`, one `/slow` 300ms endpoint and one near-instant endpoint, slow listed *first* in the array so a pass can only mean a genuine race) immediately crashed: `Uncaught: Unknown error`, non-deterministically also `Uncaught: URL using bad/illegal format or missing URL` and a bare segfault across repeated runs — three different symptoms for the same input, the signature of memory corruption rather than a logic bug. Isolated with temporary `printf`-based instrumentation (removed before landing) reading the winning member's `done`/`status`/`result` fields immediately before calling `__kml_pending_finish` on it, and again from inside that function: the value read immediately before the call was `result=0` (success); the value read a few IR instructions later, *inside the very call being made on the same pointer*, was `printf`-visible as a second, unexplained invocation of `__kml_pending_finish` at a completely different address with garbage `result`. Root cause, once that pointed at the right place: `emitAwait`'s existing `promiseTy.IsResponse` branch unconditionally treats *every* `Promise<Response>` as a still-pending fetch handle — true for a raw `fetch()` call (the only producer that existed before this feature), but `Promise.race`'s own Response branch had already fully resolved the winner and wrapped it via `wrapResolvedPromise` using the *generic* resolved-Promise convention. `await Promise.race(...)` therefore ran `emitPromiseRace`'s own resolution (correct), then `emitAwait` ran a *second* time on the result, reinterpreting the finished `Response` struct's own bytes (`{status: i64, ok: i1, body: ptr}`) as if they were a `{ptr, ptr, i64, i64, i64}` pending-fetch struct — explaining both the garbage values and the run-to-run-different symptom (whatever bytes happened to land where the pending struct's `result` field would be).
  - `TestE2EPromiseAllFetchesRunConcurrently` (two `/slow` 300ms fetches via `Promise.all`, timed) initially failed too: `538ms`+ external wall-clock for what should be ~300ms of genuine overlap — much closer to serial (600ms) than parallel. Diagnosed by adding an in-program `Date.now()` diff printed alongside the external `exec.Command` timing for the *same run*: the in-program figure read `306ms` — correct — while the external one read `543ms` for that identical execution. Root cause was the test's own measurement, not the compiler: wall-clock timing around `exec.Command(...).Output()` in this environment carries roughly 200ms of process start/exit overhead unrelated to the feature. Fixed by rewriting the test to measure with `Date.now()` from inside the compiled program, the same technique used to diagnose it — see Verification.

## Decision

**Response branch — a generalized wait, reusing [ADR-00049](ADR-00049.md)/[ADR-00050](ADR-00050.md)'s mechanism directly**, not a second parallel one:
- Connection-array entries gain a fifth field, `pendingGroup` (32 → 40 bytes; every existing GEP over the 4-field shape updated to 5), a direct sibling of the existing `pendingFetch` field.
- A "group" is a malloc'd `{ ptr membersArr, i64 count, i64 mode }` (24 bytes): `membersArr` points at the *same* pending-fetch structs `__kml_fetch_async` already produced for each array element (no copying), and `mode` (0 = wait-for-all, 1 = wait-for-first) lets `.all`/`.allSettled` and `.race` share one wait primitive.
- `__kml_group_satisfied(ptr group) -> i1` and `__kml_first_done_index(ptr group) -> i64` (`runtime.go`, new) scan `membersArr`, reading each member's existing `done` field (offset 2 of the unchanged pending-fetch struct).
- `__kml_await_group_wait(ptr group)` (new) is a structural clone of `__kml_await_fetch`'s own `checkloop`/`maybeyield`/`doyield`/`busyspin` shape, polling `__kml_group_satisfied` instead of one struct's `done` flag, and parking on `pendingGroup` instead of `pendingFetch` when yielding. The event loop's resume-scan (`__kml_event_loop_run`) gets a third branch, `rcheckgroup`, structurally identical to the existing `pendingFetch` check.
- `__kml_pending_finish(ptr pending) -> {i64 status, ptr body}` (new): a pure, non-loop extraction of what used to be inlined directly in `__kml_await_fetch`'s own `finish` block (throws on transfer failure, otherwise returns status/body) — `__kml_await_fetch` itself is now "loop until done, then tail-call this," unchanged in behavior. Factored out so `.all`/`.race` can call it once per already-known-done group member without duplicating the neterror/emptybody/havebody logic a third time.
- `__kml_pending_finish_settled(ptr pending) -> {i1 failed, i64 status, ptr body, ptr reasonMsg}` (new): a non-throwing sibling used only by `.allSettled`, which by definition must not abort the whole combinator on one member's transport failure.

**Non-Response branch**: each builtin loops directly over the array's already-resolved Promise slots (`.all` collects in order; `.race` takes the first element; `.allSettled` always reports "fulfilled") — no group-wait involved, matching [TDD-00016](../tdd/TDD-00016.md)'s scope narrowing.

**Result wrapping and the `emitAwait` fix**: all three builtins build their result value synchronously, then wrap it via a new `wrapResolvedPromise` helper using the same malloc-and-store convention `emitAsyncPrologue`/`emitReturn` already use for an ordinary async function's return. This is where the corruption bug (see Investigation) was found and fixed: `Type` gained a new `PromiseResolved` field (`types.go`), set on the `PromiseType` `wrapResolvedPromise` returns whenever the wrapped value `IsResponse` — the only case that can collide with `emitAwait`'s existing fetch-specific branch. `emitAwait`'s condition changed from `if promiseTy.IsResponse` to `if promiseTy.IsResponse && !promiseTy.PromiseResolved`; when the flag is set, the existing generic branch below runs instead (a plain load-and-free), which is already exactly correct for an already-built `Response` struct. `inferExprType`'s own static-type computation for `Promise.race(...)` mirrors the same flag, so the indirect form (`const p = Promise.race(ps); await p`) agrees with the direct-call codegen path.

**Parser fix, found and fixed along the way**: `Array<Promise<T>>`'s own type annotation — the exact syntax every one of these builtins' argument type needs — failed to parse at all. Every existing `<...>`-closing call site (`Array<T>`, `Map<K,V>`) used `p.expect(lexer.GT)` directly, which can't handle nested generics closing with a fused `>>`/`RSHIFT` token (the lexer has no parsing-context awareness, so it always emits one `RSHIFT` for a doubled `>`, the same ambiguity C++/Rust/TypeScript's own parsers resolve once nesting is known). Fixed with a new `expectGT` helper (`parser.go`) that "un-merges" one `>` worth of a fused `RSHIFT`/`URSHIFT` token in place when closing a generic, without advancing the cursor, so an enclosing level's own `expectGT` call still finds a real closing token. All existing `<...>`-closing call sites switched to it.

## Implementation notes

- `codegen/llvm/emit_promise.go` (new file): `emitPromiseAll`/`emitPromiseRace`/`emitPromiseAllSettled` and their shared helpers (`promiseArrayElemType`, `emitPromiseLoop`, `mallocArrayBuffer`/`storeArrayElement`/`wrapArrayAggregate`, `wrapResolvedPromise`, `buildSettlement`, `buildPendingMembersArr`).
- `codegen/llvm/emit_async.go`: `buildResponseFromStatusBody` factored out of `emitAwait`'s existing `IsResponse` branch so `emit_promise.go` can build the same `Response` struct per group member without duplicating it a third time; `emitAwait`'s dispatch condition and `emitAsyncPrologue`/`emitAwait`'s slot sizing/loading now use `StructFieldSize`/`StructFieldIR` instead of `.Align()`/`.IR` directly — a real, separate bug found while implementing `Promise<Array<T>>` (`.all`'s own return shape): the bare `Align()`/`.IR` a plain `Promise<T>` prologue used previously is only 8 bytes for an array-typed `T` (a bare `ptr`), silently dropping the `i64` length half of the `{ptr, i64}` aggregate arrays are represented as everywhere else. Regression-covered by `TestE2EAsyncPromiseArrayReturnLengthAndContents`.
- `codegen/llvm/types.go`: `PromiseResolved` field (documented above); `StructFieldIR`/`StructFieldSize` (new) — the struct-layout-aware counterparts to `.IR`/`.Align()` used everywhere a `Promise<T>` slot or struct field is sized/typed, needed by the `emit_async.go` fix above.
- `codegen/llvm/runtime.go`: `__kml_pending_finish`/`__kml_pending_finish_settled`/`__kml_group_satisfied`/`__kml_first_done_index`/`__kml_await_group_wait`/`ensurePromiseCombinators` (all new); connection-array entry grown to 5 fields (every existing GEP in `__kml_http_append_conn`/`__kml_event_loop_run` updated); `ensureHTTPRuntime` now also calls `ensurePromiseCombinators` unconditionally, mirroring [ADR-00050](ADR-00050.md)'s existing "the event loop's own IR references these symbols regardless of whether this specific program calls `Promise.all`" reasoning for `ensureFetchAsync`.
- `codegen/llvm/emit_call.go`/`emit_exprs.go`: `Promise.all`/`.race`/`.allSettled` call dispatch and `inferExprType` support (including the `PromiseResolved`-mirroring fix described above).
- `parser/parser.go`: `expectGT` (documented above); `Array<T>`'s and `Map<K,V>`'s existing closing-`>` call sites switched to it.
- `tests/fuzz_codegen_test.go`: `FuzzPromiseCombinatorsOrdinary` (new, "Lane C" alongside [TDD-00014](../tdd/TDD-00014.md)'s existing two) — see Verification below. `Makefile`'s `fuzz-codegen` target runs it alongside the other two lanes.

## Side effects discovered

None beyond the two bugs already described in Investigation/Decision (both fixed within this same piece of work, not deferred). One deliberate, documented-not-fixed limitation carried over directly from this compiler's pre-existing single-owner Promise model (not new here): each combinator call frees every element's own Promise slot as it consumes it, exactly like a plain `await` already does to a single slot — feeding the same array to a second combinator call afterward is a use-after-free. See [TDD-00016](../tdd/TDD-00016.md)'s Open Questions.

## Verification

- `go build .`, `go vet ./...`, full `go test ./...` all green, including every pre-existing `TestE2EAsync*`/`TestE2EFetch*`/`TestE2EHTTPListen*` test (confirming the `emitAwait`/parser/struct-layout fixes didn't regress the existing single-fetch/HTTP-server paths) plus the new tests below.
- `tests/async_test.go`: `TestE2EAsyncPromiseArrayReturnLengthAndContents` (regression test for the `StructFieldSize`/`StructFieldIR` fix — would have printed a garbage/zero array length before it); `TestE2EPromiseAllOrdinaryPromises`/`TestE2EPromiseRaceOrdinaryPromises`/`TestE2EPromiseAllSettledOrdinaryPromises` (the non-Response, order-preserving-collection branch).
- `tests/fetch_test.go`, all against a local `httptest.Server` (deterministic, offline-capable, same convention the file's existing fetch tests already use): `TestE2EPromiseAllFetchesCollectsInOrder`; `TestE2EPromiseRaceFetchesReturnsFirstDone` (slow member listed *first* in the array, so a pass can only mean a genuine race — this is the test that caught the `PromiseResolved` corruption bug); `TestE2EPromiseAllSettledFetchesReportsPerMemberFailure` (one real network failure alongside one success, asserting both `.status` and the fulfilled entry's nested `.value.status`); `TestE2EPromiseAllFetchesRunConcurrently` (two 300ms `/slow` fetches via `Promise.all`, timed with an in-program `Date.now()` diff rather than external wall-clock — see Investigation for why — asserting well under the ~600ms a serialized implementation would take; passes at ~300ms).
- `examples/async/promise_all.ts` (new): both branches end to end — the ordinary-promise section produces fully deterministic output and was run directly; the real-fetch section (`httpbin.org`) follows `examples/fetch/fetch.ts`'s own existing precedent of needing real network access, and was confirmed to return the *shape* of correct behavior in an environment with restricted outbound access (a proxy 503 on every request, reproduced identically by the pre-existing `fetch.ts` example run side by side — an environment limitation, not a regression) — the deterministic local-server test suite above is the real correctness evidence, this example is illustrative/documentation.
- `tests/fuzz_codegen_test.go`'s new `FuzzPromiseCombinatorsOrdinary` ("Lane C", extending [TDD-00014](../tdd/TDD-00014.md)'s existing arithmetic-oracle/well-formedness lanes): chains 1-3 combinator calls (kind, array length 1-6, and every element's `number` argument all randomized per fuzz iteration) inside one generated program, against an oracle computed in Go from the same `n * 2 + 1` transform the generated `elemFn` actually runs — catching the category of bug a fixed per-combinator hand-written test can't, by construction: compile-time label/register collisions across multiple textual call sites of the same builtin, and cross-call interference between different combinator kinds sharing lazily-emitted global runtime declarations (`ensurePromiseCombinators`'s `usedPromiseCombinators` flag, etc.). Run for 90s (536 executions, ~5.8/exec/sec — consistent with the existing two lanes' own clang-invocation-per-execution cost) against the seed corpus plus corpus entries the fuzzer found "interesting" (81 total by the end of the run): zero failures, no new corpus entries persisted to `testdata/fuzz/` (which only happens on an actual failure). `go vet`/`gofmt` clean on the new file.
- `STATUS.md` updated: Language Constructs table (`Promise.all`/`.race`/`.allSettled` row, ✅); "What Is NOT Implemented" table (row struck through, matching the existing convention for completed items); Design Documents section (new [TDD-00016](../tdd/TDD-00016.md) bullet, including the fuzz lane above; Event Loop bullet's "remaining gap" sentence updated); Coverage Summary (Async/Promise 3/9 → 4/9); Roadmap's Structural priorities #2 (Event Loop) updated to note this gap is now closed. `docs/tdd/README.md`'s index and [TDD-00006](../tdd/TDD-00006.md)'s own `Status` line updated to `Implemented`, cross-referencing this ADR.
