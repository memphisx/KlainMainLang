# ADR-00181: Async class methods + method-modifier parsing (TDD-00063 Stage 2a)

- **Relations**: `Implements TDD-00063` (Stage 2a of the Stage 2 method-modifier work). `Extends ADR-00180`.
- **Date**: 2026-08-13

## Context

[TDD-00063](../tdd/TDD-00063.md) Stage 2 is class-body method modifiers — `async m()`, `*m()` (generator), and `async *m()` (async generator). Before this, all three were parse-time rejections (`expected IDENT, got async` / `expected IDENT, got *` — 727 + 952 first-error files across the class corpus). This ADR does Stage 2a: **parse all three forms** and make **async methods** actually work, while generator/async-generator methods become a clean, specific codegen rejection (their real implementation — fiber `this`-capture — is Stage 2b).

## Investigation

- `parser/parser_classes.go`'s member loop had no `async`/`*` handling. `async` must stay contextual — a method may be named `async` (`async() {}`) — so it's a modifier only when a member-name-start (`IDENT`/`PRIVATE_NAME`/`*`) follows, the same 2-token disambiguation the adjacent `get`/`set` detection already uses. The `FunctionDeclaration` node already carries `IsAsync` and `IsGenerator`; only the parser wasn't setting them for methods.
- Async top-level functions (`emit_func.go:100-148, 226-240`) compile to an LLVM coroutine: `e.isAsync` set, `Promise<T>`'s T tracked in `e.currentPromiseTy`, IR return type forced to `ptr` (the coro handle), `emitAsyncPrologue`/`emitAsyncEpilogue` bracketing the body. This is a self-contained, replicable block.
- `emitClassMember` (`emit_classes.go`) — the shared method/constructor emitter — did **none** of that: it took no async flag and always emitted a plain `define <retTy>`. So a `Promise<T>`-returning async method emitted broken IR (`value doesn't match function result type 'ptr'`, confirmed directly).
- An unannotated async function (top-level *or* method) already requires an explicit `Promise<T>` return — `async function f() { return 5 }` gives a clean `await requires a Promise value`, unchanged pre-existing behavior. So async methods need no new unannotated-case rejection; they inherit the same limitation.
- A generator method with **no** `yield` in its body would silently emit as an ordinary method (dropping generator semantics entirely) rather than erroring — a silent-wrong hazard, since the `yield`-context check only fires when a `yield` is actually present.

## Decision

1. **Parser**: detect a contextual `async` and a `*` before the member name; set `fn.IsAsync`/`fn.IsGenerator`. `async`/`*` preclude an accessor (`async get() {}` is an async method named `get`), and a constructor cannot be async/generator. A stray `async`/`*` not followed by a `()` method is a clean rejection.
2. **Async methods**: thread an `isAsync bool` into `emitClassMember` and replicate the top-level async coroutine setup/epilogue (save+restore of `isAsync`/`coroHdl`/`currentPromiseTy`/`coroRetLabel`, `ptr` IR return, prologue/epilogue). Every `emitClassMember` call site passes `m.IsAsync` (constructors always `false`); the generic path (`emit_generics.go`) does the same.
3. **Generator methods**: a clean, specific codegen rejection at both `emitClassDecl` and the generic `emitClassDeclAs`, checked before emission so a no-`yield` generator method can't slip through as a plain method. Covers async generators too (they are `IsGenerator` as well).

## Implementation notes

- `emitClassMember`'s signature gained a trailing `isAsync bool`; five call sites updated (three in `emit_classes.go`, two in `emit_generics.go`).
- The async setup was moved to just after `pushScope()` so the prologue's coro intrinsics land in the entry block alongside the `this`/param allocas, matching `emit_func.go`'s ordering.
- Static async methods (`static async m()`) work through the same path — `isStatic` (no receiver) and `isAsync` (coroutine) are independent flags on `emitClassMember`.

## Side effects discovered

- **Early-error gaps exposed by accepting more class syntax** — the same category [ADR-00168](ADR-00168.md) hit shipping function expressions (adding a construct surfaces the early-error rules that only ever mattered once the construct parsed). A per-file conformance diff found ~14 negative Test262 tests that previously "passed" only because the whole construct was rejected at parse, and now compile because the specific early-error rule isn't enforced. All are negative/early-error tests — **no valid program is miscompiled**. Two cheap, unambiguous, zero-false-positive rules are **fixed here**: a `static` member named `prototype`, and `eval`/`arguments` as a class-method parameter name (a class body is always strict). The rest are **deferred** (disclosed in [LANGUAGE-CONSTRUCTS.md](../status/LANGUAGE-CONSTRUCTS.md)), each needing machinery beyond a name check: a field initializer containing `arguments` or a `super()` call (needs a "Contains" walk over the initializer expression — a naive token match would wrongly reject the legal `super.prop`), a `super()` call in a method parameter default (same walk), field-definition ASI on the same line (needs line-terminator tracking), and the `#constructor` private-name ban (already a [TDD-00021](../tdd/TDD-00021.md) deferred item). Net conformance is flat vs. the Stage 1 baseline — the async-method wins and the two fixed rules offset the newly-exposed flips — consistent with [TDD-00063](../tdd/TDD-00063.md)'s stated dynamic-object-model ceiling.
- A method literally named `async` with no modifier (`async() {}`) is still a parse rejection (the name is an `ASYNC` keyword token, not an `IDENT`). This predates Stage 2 (it was never accepted) and is left as-is — rare in real code, and Test262's use of it is incidental to tests that also need the dynamic object model.
- Generator methods (`*m()`, `async *m()`) remain unimplemented — [TDD-00063](../tdd/TDD-00063.md) Stage 2b. They need the generator fiber's frame to capture `this` and a per-class dispatch key, a genuinely larger piece than async methods (which reuse the existing coroutine path unchanged).
