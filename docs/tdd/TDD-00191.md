## Progress

- **Stage 1 — core multi-listener: shipped** ([ADR-00803](../adr/ADR-00803.md)).
  Additional plain Node HTTP servers run concurrently via a thread-local
  extra-listener table + per-server suffixed dispatchers; the primary server's
  path is unchanged. `server.close()` on an additional server shipped alongside,
  since the loop couldn't otherwise exit.
- **Stage 2 — per-listener close + relisten: shipped**
  ([ADR-00804](../adr/ADR-00804.md)). An additional server can `close()` then
  `listen()` again on a fresh port; `register_extra_listener` reuses the freed
  table slot so a relisten cycle stays bounded. Primary relisten already worked.
- **Stage 3 — per-server ws/upgrade: shipped**
  ([ADR-00804](../adr/ADR-00804.md), [ADR-00805](../adr/ADR-00805.md)).
  WebSocket/`upgrade` handling works on *any* server (primary or additional):
  each dispatcher reads its own suffixed handler globals, and a
  `server.on('upgrade', …)` / `new WebSocketServer({ server })` registration is
  routed to the named server's globals by a compile-time binding→suffix map (a
  simple `const x = http.createServer(...)` binding; an unrecognized handle falls
  back to a primary-only runtime guard).
- **Stage 3 — HTTPS/1.1 multi-instance: shipped**
  ([ADR-00806](../adr/ADR-00806.md)). An additional server may be HTTPS/1.1: its
  SSL_CTX rides in the extra-listener table and its accepts do their own TLS
  handshake, registering the fd→SSL entry the connection I/O shims already
  self-dispatch on. Plain + HTTPS servers freely mix. A whole-program pre-scan
  keeps the extra-accept path TLS-aware even when a plain primary triggers the
  runtime first.
- **Stage 4 — per-listener HTTP/2 + edges: shipped**
  ([ADR-00807](../adr/ADR-00807.md)). The C nghttp2 driver routes each connection
  through a per-server dispatch vtable (`h2_disp_vtbl` on the `h2_conn`), so an
  additional `http2.createServer` (h2c) and `http2.createSecureServer`
  (h2-over-TLS, ALPN-driven in the extra-listener accept with the listener's
  vtable) each reach their own handler. **Edges (decisions):** `klain:http` and
  its `{ workers }` cluster keep the single blocking model — mixing with the Node
  multi-server reactor stays a clean rejection; the `select()` ~384-fd ceiling
  (TDD-00182) now spans all listeners + connections, same shared read set. **All
  stages complete.**

## Context

`http.createServer(...).listen(port)` is single-instance, once-per-program. A
second `createServer`/`listen` is a hard codegen rejection
(`emit_http.go`, `e.httpListenCallSeen`: *"only one HTTP server … is supported
per program (V1)"*). This is the headline caveat on the HTTP-server status page
("One server per program") and backlog item §1.3's largest slice.

Real servers routinely run more than one listener in one process: an app port
plus a health/metrics port, HTTP alongside an admin socket, a public server plus
an internal one on a different interface (now bindable via `listen({ host })`,
[ADR-00801](../adr/ADR-00801.md)). Node supports this directly — each
`createServer()` is an independent `Server` with its own `listen`/`close`. The
per-server handle model here already matches Node's shape (a distinct handle per
`createServer`, its own `.listen`/`.close`/`.address`/`.on` — ADR-00406/00423);
the only thing missing is the runtime's ability to *drive* more than one
listener. The `http.close()`-can't-relisten limit and the item-3 close-reuse
caveat both fall out of the same single-listener state, so they are folded in
here.

Scoped now because the two adjacent server pieces just shipped
(`listen(options)`/host bind — ADR-00801; chunked/streaming keep-alive —
ADR-00802), leaving the single-instance limit as the last structural gap on the
Node `http` server and the #1 REST/microservice priority.

## Design

### Where the single-listener assumption lives

The runtime keeps the *one* listener in thread-local scalar globals
(`runtime_http.go`):

- `@__kml_listen_fd` (i32) — the listening socket, or -1.
- `@__kml_listen_dispatch` (ptr) — the connection-fiber entry point.
- `@__kml_listen_handler` / `@__kml_listen_ws_handler` /
  `@__kml_listen_upgrade_handler` (ptr) — the user's handler closures.

The event loop (`__kml_event_loop_run`) adds the single `@__kml_listen_fd` to
`select()`'s read set, and on readiness `doaccept` accepts *one* connection and
calls `__kml_http_append_conn(fd)`, which builds a fiber whose entry point is
read from `@__kml_listen_dispatch` (baked into `makecontext`). The connection
slot is `{ i64 fd, ptr ctx, ptr stack, ptr pendingFetch, ptr pendingGroup }`
(40 B) — no owning-server field. The dispatcher itself is a single named
function `@__kml_http_dispatch`, emitted once by `buildHTTPDispatcher`, reading
the handler globals above.

So four things are hard-wired to one server: (1) the listener globals, (2) the
select/accept path, (3) the loop's keep-alive/exit condition
(`%haslistener` from the one fd), and (4) the single `@__kml_http_dispatch`
symbol. The codegen guard `httpListenCallSeen` exists precisely because the
runtime can't express more.

### Recommended direction: a listener table + per-server dispatchers

Replace the scalar listener globals with a small growable **listener table**,
each entry `{ i32 fd, ptr dispatch }`, and emit one dispatcher function per
server. The handler/ws/upgrade closures stay per-server but move from shared
scalars to server-indexed globals that each dispatcher reads directly — the
dispatcher is already a per-call-site specialization, so baking in its own
server's globals is the natural place to hold them, and keeps the table to just
`{fd, dispatch}`.

Concretely:

1. **Listener table** (`@__kml_listeners_data/len/cap`, thread-local, same
   realloc-doubling shape as the connection and timer tables). `listen()`
   appends `{ fd, @__kml_http_dispatch_N }` instead of storing the scalars.

2. **select/accept over all listeners.** The loop adds every table entry's fd
   (>= 0) to the read set, tracking the running max-fd for `select`'s nfds. In
   `doaccept`, loop over the table: for each listener fd flagged ready, `accept()`
   it and call `__kml_http_append_conn(newfd, dispatch)` — `append_conn` gains a
   `dispatch` parameter and uses it in `makecontext` instead of reading the
   global. The accepted connection therefore runs *its* server's dispatcher; no
   owning-server field is needed on the connection slot (the entry point is
   already captured in the fiber's `ucontext`).

3. **Per-server dispatchers.** `buildHTTPDispatcher(N)` emits
   `@__kml_http_dispatch_N` reading `@__kml_listen_handler_N` /
   `_ws_handler_N` / `_upgrade_handler_N`. Each `createServer`/`listen` gets a
   fresh index; the single-server `httpListenCallSeen` guard is removed for the
   Node path.

4. **Loop keep-alive / exit.** `%haslistener` becomes "any table entry has fd >=
   0"; the existing `%hasactiveconns` term is unchanged (already the mechanism
   that lets accepted connections finish after a `close()`). The loop runs while
   any listener is open or any connection is active.

5. **`server.close()` per listener.** A handle already stores its own listen fd
   (`emitHTTPServerListen` writes it into the handle). `close()` clears that
   listener's table entry (fd = -1) rather than the single global, letting its
   in-flight connections drain via the existing `%hasactiveconns` path. Because
   entries are addressed by fd, a subsequent `listen()` on the same handle
   appends a fresh entry — **`http.close()` can relisten**, closing that
   sub-caveat and the item-3 close-reuse gap.

### Why per-server dispatchers rather than threading handler pointers

The alternative — one shared dispatcher that reads the handler from the
connection slot — would need the slot to carry handler/ws/upgrade pointers and
the response-shape metadata (each server's handler has a different return type,
which the dispatcher lowers at compile time). That metadata isn't representable
at runtime without boxing. Keeping a distinct compiled dispatcher per server
sidesteps it entirely: response lowering stays fully static, and the only
runtime hand-off is the entry-point pointer already carried by `makecontext`.

### Staging

- **Stage 1 — core multi-listener.** Listener table, multi-accept,
  per-server dispatchers, loop keep-alive over any listener, drop the codegen
  guard. Target: two-plus plain Node servers (`(req,res)` handler + response)
  on different ports in one program, each serving concurrently. No ws/upgrade,
  no cluster, no HTTPS yet.
- **Stage 2 — per-listener `close()` + relisten.** Route `server.close()` to
  the owning table entry; allow `listen()` after `close()`. Closes the
  `http.close()`-can't-relisten and close-reuse caveats.
- **Stage 3 — the specialized handlers.** Per-server `ws`/`upgrade` handler
  globals so a program can run a WebSocket-upgrading server alongside a plain
  one; HTTPS/1.1 multi-instance (per-listener TLS context — interacts with the
  chunked-keepalive HTTPS hold-back in [ADR-00802](../adr/ADR-00802.md)).
- **Stage 4 — HTTP/2 + edges.** Per-listener h2c/h2 driver state; decide the
  `klain:http`/Node coexistence and cluster interaction (see Open questions).

## Open questions

- **`klain:http` coexistence.** `klain:http`'s `http.listen(port, handler)` is
  blocking and enters the loop itself, and its `{ workers: N }` cluster fork
  depends on that blocking call. Does multi-instance stay Node-`createServer`
  only (klain:http remains single, blocking), or does klain:http also get a
  non-blocking multi form? Leaning: Node path only; klain:http keeps its single
  blocking contract, and mixing the two in one program stays rejected.
- **Cluster `{ workers }` interaction.** Cluster fork shares one listening fd via
  `SO_REUSEPORT` across processes — orthogonal to multiple *distinct* listeners
  in one process. Can a program have both (N forked workers, each running M
  listeners)? Probably yes since the mechanisms compose, but the fork point
  (after the first bind) and the table's per-process copy need checking.
- **Ready-listener fairness.** When several listener fds are ready in one
  `select()` wake, accept round-robin vs. in-table-order — does starvation
  matter at this scale? Likely accept one per ready listener per iteration and
  move on (the loop re-selects immediately when connections are pending).
- **`nfds` / fd-set sizing.** The existing 384-socket `select()` ceiling
  (a documented Windows-reactor limit, TDD-00182) now spans listeners +
  connections across all servers; confirm the accounting and whether the
  many-listener case pressures it sooner.
- **Per-thread scope.** The listener globals are `thread_local` (for
  goroutine-migrated reactors under `klain:sync`). The table stays thread-local;
  confirm nothing assumes a process-global single listener across threads.
