# ADR-01823: Object.prototype's own members

- **Relations**: `Implements TDD-00230`
- **Date**: 2026-10-20

## Context

- Object.prototype's bag had no `isPrototypeOf`, no `__defineGetter__` / `__defineSetter__` / `__lookupGetter__` / `__lookupSetter__`, and no `__proto__` accessor. Its methods are compiled from JS source, and that source could not call the `Object.*` statics: the parsed helper is never bound against their declarations.
- A bag's `__proto__` read and write always meant the prototype link, even on a chain that never reaches Object.prototype (`Object.create(null).__proto__` read `null`, and assigning it re-linked the prototype).

## Decision

- A helper's `Object.f(…)` calls go straight to the statics' intrinsics.
- The five methods are written to the spec over those statics. `__proto__` is a configurable, non-enumerable accessor whose getter and setter run `Object.getPrototypeOf` / `Object.setPrototypeOf` with the spec's receiver checks.
- A property missing on a chain that ends at the implicit Object.prototype runs Object.prototype's accessor for reads and writes, as it already read its data properties.
- `x.__proto__` on a bag is a plain property when the chain holds an own `__proto__` before Object.prototype, or never reaches Object.prototype.

- The module text codegen returns drops a `declare` of a function it also defines. A helper declared at its call and defined at the end left both, which the split build tolerated and a single-module compile rejected (`invalid redefinition`).

## Consequences

- `TestE2EJSFileObjectPrototypeMembers` covers each member.
