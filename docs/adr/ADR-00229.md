# ADR-00229: Utility types, stage 1b — Pick/Omit/Record + string-literal types

- **Relations**: `Implements TDD-00079` (Stage 1b); `Extends ADR-00228`
- **Date**: 2026-08-19

## Context

Second utility-type increment ([TDD-00079](../tdd/TDD-00079.md)): the key-based
utilities `Pick`, `Omit`, and `Record`. Unlike stage 1a's Partial/Required/
Readonly (structural no-ops in this object model), these produce a **genuinely
different field set**, so they deliver visible value. They need one new
building block: **string-literal types** (`"a" | "b"`) for the key argument.

## Investigation

`Pick<T, K>`/`Omit<T, K>` filter `T`'s fields by the key set `K`; `Record<K, V>`
builds an object (literal-union `K`) or a map (general `K`). Because the compiler
monomorphizes, all three evaluate to a concrete `Type` at `resolveType` and reuse
the existing object/map machinery — the same seam stage 1a used.

The missing piece was purely the **key type**: the type-annotation parser had no
notion of a string literal in a type position (a `STRING` token there was an
"expected type name" error). The key is either a single literal (`"a"`) or a
union of them (`"a" | "b"`) — and the union parser already exists, so a
string-literal *atom* is all that was needed; a union of them falls out.

## Decision

- **String-literal types.** `ast.TypeAnnotation` gains `IsStringLiteral bool` +
  `LiteralValue string`. `parseTypeAnnotationAtom` handles a leading `STRING`
  token, producing such an annotation (and it composes into the existing union
  loop, so `"a" | "b"` is a union of literals). In `resolveType` a string-literal
  type resolves to `string` (`TypePtr`) — as a value type the literal is not
  narrowed/enforced, a disclosed V1 simplification; the literal *value* is only
  consumed at the AST level for keys.
- **Pick/Omit/Record** in `resolveUtilityType` (arity-2):
  - `Pick`/`Omit` — resolve `T` (must be an object), collect the literal keys
    from `K` via `collectStringLiteralKeys`, and keep the fields `∈ K` (Pick) or
    `∉ K` (Omit). The resulting `ObjectType` flows through the normal object-
    literal coercion, so assigning a dropped field is a clean "no field" error.
  - `Record` — a literal-union `K` gives a fixed-shape `ObjectType` with those
    keys typed `V`; a general `K` (`string`) gives `Map<string, V>`.
  A non-object `T` or a non-literal `K` returns `false` so `resolveType` falls
  through rather than fabricate a wrong shape.

## Implementation notes

No new runtime representation: a resolved utility type is an ordinary
`ObjectType` or `MapType`. `collectStringLiteralKeys` handles both a single
literal and a union of literals (reading each `UnionMembers` entry's
`LiteralValue`). String-literal types are also usable standalone
(`type Dir = "n" | "s"`), resolving to `string`.

## Side effects discovered

A `Pick`/`Omit` with a key that isn't actually a field of `T`, or `Record` with a
non-literal non-`string` key, is not yet a *clean* error — it currently falls
through to `resolveType`'s generic fallback. Tightening that is part of
TDD-00079 Stage 0 (unknown-`Name<Args>` rejection), which needs the
use-site-validator plumbing (`resolveType` has no error return).

## Verification

- `tests/utility_types_test.go`: Pick (kept fields + a dropped-field rejection),
  Omit, Record (literal-union → object, `string` → Map), and a standalone
  string-literal union type. All pass; the Pick/Omit/Record example IR verified
  with `clang`.
- `examples/types/utility-types.ts` extended and runs correctly.
- `go build`, `go vet ./...`, and the utility/object/interface/map/union/nullable
  test subset are green on Apple Silicon (macOS).
