# TDD-00239: `klain:test`, testing the compiled application

- **Status**: Not Started
- **Date**: 2026-10-01

## Context

A program built with this compiler is a native binary: a CLI tool, a
terminal UI, an HTTP service or a webview window (the `apps/` gallery has
all four). Its developer can unit-test its functions with `node:test` and
`node:assert`, which are Node's own ([ADR-01282](../adr/ADR-01282.md),
[ADR-01288](../adr/ADR-01288.md)). Nothing tests the application as a user
meets it: the screen a terminal app draws, the responses a service gives,
the page a window shows. The gallery apps are checked by hand.

A Jest clone adds nothing over `node:test`, and anything that matches
Node's API belongs in the Node module, not under `klain:`
([TDD-00131](TDD-00131.md)). `klain:test` is for what Node's runner
cannot do: drive a compiled binary from outside, and use what only the
compiler knows.

**Ordering.** This comes after [TDD-00230](TDD-00230.md) (`klain:`
modules last) and after the open bugs and caveats: the compiler has to be
stable before it tells developers how to test their applications. It may
still come before many open TDDs. [TDD-00238](TDD-00238.md) comes first,
since a test run compiles many programs.

## Design (direction, to be detailed)

### Terminal applications

Playwright for terminals: run the binary under a pseudo-terminal of a
given size, send keys and resizes, wait for text or a screen state, and
compare the rendered screen against a stored snapshot. The screen is
reconstructed from the escape sequences the app writes (a terminal
emulator's state machine). References: Microsoft's `tui-test`, `expect`.
First users: `apps/klaintop`, `files`, `menu`, `explorer`.

### HTTP services

Start the binary on a free port, wait until it accepts connections, run
requests through `fetch`, assert on status, headers and bodies, and stop
it, collecting its output and exit code.

### Webview applications

Drive the page through the platform's automation protocol: the WebKit
inspector protocol on Linux and macOS, the DevTools protocol of WebView2
on Windows. Locate elements, click, type, and read the DOM. The hardest
part; last.

### What only the compiler can add

- Leak checks per test, under the memory-management modes and ASan.
- Coverage from LLVM's instrumentation (`-fprofile-instr-generate`).
- Tests discovered at compile time.
- One self-contained test binary per application.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `node:test`, `node:assert` | Built | The in-process runner and assertions this builds on |
| `child_process` spawning with pipes | Built | Running the binary under test |
| A pseudo-terminal from the runtime | Missing | `forkpty`/`openpty`; ConPTY on Windows |
| A terminal-screen model | Missing | An escape-sequence state machine producing a cell grid |
| Webview automation | Missing | Per-platform protocol client |

## Open questions

- One module (`klain:test`), or a module plus a `klainmain test` command
  that builds and runs the test binaries?
- The snapshot format for terminal screens: plain text, or text with
  colours and attributes.
- Whether the webview part waits for a cross-platform protocol
  (WebDriver BiDi) rather than three platform ones.
