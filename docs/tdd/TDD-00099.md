# TDD-00099: Shared memory & remaining channels — `SharedArrayBuffer`/`Atomics`, `BroadcastChannel`, `MessageChannel`/`MessagePort`

- **Status**: Implemented
- **Date**: 2026-08-23
- **Notes**: Resolves TDD-00098's three open questions. `SharedArrayBuffer` reuses the ArrayBuffer header and crosses the worker boundary by reference; `Atomics` lowers to seq_cst LLVM atomics, with `wait`/`notify` as a portable futex substitute (process-wide mutex/cond + address-keyed waiter list — no futex on macOS, and zeroed pthread statics are invalid on Darwin). BroadcastChannel/MessagePort share one pipe-backed endpoint runtime folded into each thread's loop via a stub-backed hook trio; ownership follows the `onmessage` registration thread
- **Relations**: Builds on [TDD-00098](TDD-00098.md) (Worker); resolves all three of its remaining open questions.

## Context

[TDD-00098](TDD-00098.md) shipped `Worker` message-passing but left three things explicitly open: `SharedArrayBuffer`/`Atomics` ("still not designed"), `BroadcastChannel`, and `MessageChannel`/`MessagePort`. Deferring shared memory made sense while there were no threads; now that real pthreads exist, deep-copy-only messaging is the *only* concurrency primitive, and any workload that wants shared state (counters, work queues, result buffers) has to round-trip everything through clone envelopes. This document designs all four surfaces so the Concurrency status page and the two ❌ rows on the Binary-data page can be closed together.

Tracked in [docs/status/CONCURRENCY-WORKERS.md](../status/CONCURRENCY-WORKERS.md) (1/3) and [docs/status/BINARY-DATA-TYPED-ARRAYS.md](../status/BINARY-DATA-TYPED-ARRAYS.md) (`SharedArrayBuffer`/`Atomics` rows).

## Design

### `SharedArrayBuffer`: an `ArrayBuffer` that crosses by reference

Same hidden two-word header as `ArrayBuffer` (`{ i64 byteLength, ptr data }`), same `calloc` zero-fill, same `.byteLength`, and the same TypedArray view constructions (`new Int32Array(sab)` is a view — the existing from-buffer path works unchanged because the header layout is identical). The differences are all in the type system and the worker boundary:

- A new `Type.IsSharedArrayBuffer` flag (implies the `IsArrayBuffer` representation). `new SharedArrayBuffer(n)` is a general expression, like `ArrayBuffer`.
- Structured clone treats it as **share, not copy**: `emitDeepClone` passes the header pointer through unchanged. That is exactly the spec's semantics (`postMessage` shares an SAB, clones everything else).
- Boundary encoding: the header pointer travels as envelope word 0 — the same `ptr` encoding every other heap payload already uses; the receiving side just doesn't own a fresh copy.
- Allocation: process-wide visibility is free (threads share an address space). Under `-mm=gc` the header and data are allocated with `GC_malloc_uncollectable` — while the only live reference is on another thread's stack/TLS, Boehm on this thread must never reclaim it, and cross-thread reachability through a pipe envelope is already invisible to the collector (same reasoning as the worker envelope allocation).
- A TypedArray view over an SAB is a plain `{ptr,i64}` like any other view — views themselves still can't cross the boundary (send the SAB, re-view on the other side). Same rule as real `postMessage` transfer-less cloning would copy a view; here it's a compile-time "send the buffer instead" error, which is honest about what the envelope can carry.

### `Atomics`: LLVM atomic instructions + a portable futex substitute

`Atomics` parses like `Math` — a namespace dispatch on member calls (`Atomics.add(ta, idx, v)`), no import.

- **RMW/load/store**: `Atomics.load`/`store`/`add`/`sub`/`and`/`or`/`xor`/`exchange` lower directly to `load atomic`/`store atomic`/`atomicrmw` with `seq_cst` ordering; `Atomics.compareExchange` lowers to `cmpxchg` (returning the old value, per spec). Accepted receivers: any **integer** TypedArray (`Int8` through `Uint32`) — float TypedArrays are rejected at compile time exactly as the spec rejects them. Index is bounds-unchecked like ordinary TypedArray indexing (same posture, documented). Each op returns the same value the spec returns (old value for RMW, stored value for `store`, loaded value for `load`), widened to the receiver's element type then to `number`.
- **`Atomics.wait(i32ta, idx, expected, timeout?)` / `Atomics.notify(i32ta, idx, count?)`**: no portable futex exists on macOS, so the runtime implements the classic address-keyed waiter list: one **process-wide** (deliberately *not* thread_local) `pthread_mutex_t` + `pthread_cond_t` pair guarding a linked list of `{ addr, notified, next }` nodes.
  - `wait`: lock; `load atomic` the cell; if `!= expected` → unlock, return `"not-equal"`; append a stack-allocated node; loop `pthread_cond_wait` (or `pthread_cond_timedwait` against `gettimeofday`+timeout) until `node.notified` or timeout; unlink; return `"ok"` / `"timed-out"`. Spurious cond wakeups can't produce a false `"ok"` because only a matching `notify` sets the node's flag.
  - `notify`: lock; walk the list marking up to `count` (default all) nodes whose `addr` matches; `pthread_cond_broadcast`; unlock; return the number marked. Broadcast + per-node flags trades a thundering herd (bounded by waiter count) for zero per-address state — the right trade at this scale.
  - `wait` is only accepted on an `Int32Array` (spec). It blocks the calling **thread**, including the event loop and any fibers on it — allowed on the main thread (Node's behavior, not the browser's main-thread throw), with the blocking hazard documented.
  - Return type is the spec's string (`"ok"`/`"not-equal"`/`"timed-out"`), interned constants.
  - The mutex/cond/list globals are the first deliberately-shared mutable runtime globals. Zero-initialized static storage is **not** a valid mutex/cond on Darwin (`PTHREAD_MUTEX_INITIALIZER` carries a nonzero signature; locking a zeroed one returns `EINVAL` — verified by prototype on the Mac), so the runtime calls `pthread_mutex_init`/`pthread_cond_init` once from a start-of-`main` init hook, which runs strictly before any worker thread can exist.
- `Atomics.*` on a non-shared TypedArray is legal (spec: any integer TA) — it just isn't useful cross-thread unless the underlying buffer is an SAB.

### `BroadcastChannel`: process-wide named fan-out over per-endpoint pipes

`new BroadcastChannel(name)` — `name` a compile-time string literal (it keys the compile-time channel-type registry, same posture as the worker-path literal).

- **Runtime**: a process-wide registry (mutex-guarded array of endpoint records) — each endpoint is `{ name ptr, pipe r/w fds, owner-alive flag, cb ptr, hold flag }`. Construction creates the endpoint's own pipe (read end non-blocking) and registers it; each thread also keeps a TLS list of *its own* endpoints for event-loop integration.
- **`postMessage`**: under the registry mutex, for every *other* live endpoint with the same name: deep-clone the payload (one fresh clone per subscriber — subscribers each own their copy, per spec) and write an envelope pointer into that endpoint's pipe. Delivery therefore rides the exact same select()-wakeup mechanism worker messages use.
- **Event loop**: three new hooks mirroring the worker trio — `__kml_chan_keepalive` / `__kml_chan_fdset_add` / `__kml_chan_dispatch` — called from `__kml_event_loop_run` with no-op stubs when the program never uses channels (`emitLoopTaskStubs` pattern).
- **`onmessage` / `close()`**: `bc.onmessage = (e: { data: T }) => ...` (browser event shape, reusing the worker `onmessage` adapter machinery); a registered listener holds the owning thread's loop alive (Node's ref semantics) until `close()`, which clears the hold, marks the endpoint dead, and closes its pipe fds.
- **Typing**: one message type per channel *name*, program-wide: the first annotated `onmessage` or `postMessage` site fixes it; every later site is checked against it (the worker-channel single-type rule, keyed by name instead of path).

### `MessageChannel`/`MessagePort`: a symmetric port pair, shared (not cloned) across the boundary

- `const ch = new MessageChannel<T>()` — the explicit type argument declares the (single, symmetric) message type for both ports; `ch.port1`/`ch.port2` are `MessagePort<T>` values. `new`-with-type-args already parses (the `new Map<K,V>` grammar).
- **Runtime**: one control block per channel: two endpoint halves, each `{ pipe r/w fds, cb, hold }`; a port value is a pointer to its half (halves back-reference each other for peer lookup). `port.postMessage(v)` deep-clones `v` and writes the envelope into the *peer* half's pipe; `port.onmessage = (e: { data: T }) => ...` registers the handler on its own half and sets the loop hold; `port.close()` drops both holds. Ports fold into the same `__kml_chan_*` event-loop hooks as `BroadcastChannel` endpoints (one TLS endpoint list serves both).
- **Crossing the boundary**: a `MessagePort` is, like an SAB, a **shared** handle — passing a port as `workerData` (or as a whole `postMessage` payload) passes the half's pointer through the envelope, no clone. The worker side annotates `const port: MessagePort<T> = workerData`. This is the spec's *transfer* semantics minus neutering: the sender is trusted not to keep using the sent port (using both ends from two threads is unsynchronized-but-memory-safe pipe writes; documented, not detected).
- A port embedded *inside* an object/array payload is a compile-time rejection (the clone walker refuses it) — ports cross whole, or not at all. Same restriction as SABs-inside-objects for V1.
- The event-shape handler means the browser `MessagePort` surface and the Node `worker_threads` port surface coincide except for `on('message')` vs `onmessage`; both are accepted (the worker listener machinery already supports both shapes).

### Staging

1. **Prototype checks** (throwaway `.ll`): zero-initialized `pthread_mutex_t`/`pthread_cond_t` static storage on macOS + Linux; `atomicrmw`/`cmpxchg` `seq_cst` on both targets; `pthread_cond_timedwait` absolute-time behavior.
2. **`SharedArrayBuffer`** — type flag, parser case, boundary share semantics. Independent of 3–5.
3. **`Atomics`** RMW/load/store, then `wait`/`notify`.
4. **`BroadcastChannel`** — the `__kml_chan_*` hook trio + registry + fan-out.
5. **`MessageChannel`/`MessagePort`** — reusing the hook trio and the boundary-share path from stage 2.

## Open questions

- `Atomics.waitAsync` — out of scope here (needs a waiter integrated with the event loop rather than blocking it); noted as a status-page caveat, not designed.
- Port/SAB values nested inside clone payloads — rejected in V1; lifting it means teaching the clone walker a per-field share list.
