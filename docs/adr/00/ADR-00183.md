# ADR-00183: `console.log(boolean)` prints `true`/`false`, not `1`/`0`

- **Date**: 2026-08-13

## Context

`console.log` of a boolean printed the raw `i1` as `1`/`0` instead of JavaScript's `true`/`false`. This had been treated as an accepted convention (several tests asserted `1`/`0` for `instanceof`, comparisons, `Array.includes`, `Map.has`, etc.), but it is not a defensible design choice — it is a deferred shortcut that diverges from real JS/TS for no benefit, and it is exactly the kind of "works well enough for now" caveat worth correcting the moment there's an opportunity, rather than letting it calcify into apparent intent. Surfaced while writing a generator-method test whose `.next().done` (a boolean) printed `0`/`1`.

## Investigation

- `emitValueToString` (`emit_exprs_types.go`), which backs **template-literal interpolation** and string concatenation, already converts an `i1` to `"true"`/`"false"` via a `select i1 %v, ptr @"true", ptr @"false"`. So `` `${x > 0}` `` has always printed `true`/`false` correctly.
- `console.log` (`emit_call_console.go`) simply never routed booleans through that helper: it special-cased dynamic and symbol values, then fell through to `val.Ty.PrintfFmt()`, which returns `%d` for `i1` — printing the integer. The two output paths had silently disagreed.
- Every `i1`-typed value in this compiler is a genuine boolean (comparison/logical/`instanceof`/`in`/`Array.includes`/`Map.has`/… results are all `TypeBool`), so printing `true`/`false` for any `i1` is correct everywhere, with no case where a numeric `0`/`1` is the intended output.

## Decision

Add a boolean case to `console.log`'s per-argument formatting (mirroring the existing dynamic/symbol cases): an `i1` value is converted through `emitValueToString` and printed with `%s`, yielding `true`/`false`. One code path, reusing the conversion template literals already used — the two now agree.

## Implementation notes

- The fix is four lines in `emit_call_console.go`; no new runtime, and it composes with `console.group` indentation and stderr (`console.error`/`warn`) exactly like every other scalar.
- 113 E2E test assertions that had encoded the old `1`/`0` output were updated to `true`/`false` (the corrected output), and `examples/classes/classes.ts`'s `instanceof` comments likewise. The updates were regenerated from the compiler's own now-correct output, not hand-edited value by value.

## Side effects discovered

This is the first of the "deferred shortcut, not real behavior" caveats to be corrected on sight rather than merely documented. `docs/status/README.md` now frames its remaining caveats that way — as fix-ASAP debt, not settled design — so the next such opportunity (e.g. an `any`-typed boolean's own printing convention, `NaN`/`Infinity` arithmetic edge cases, the non-short-circuiting `&&`/`||`) is picked up the same way rather than assumed intentional.

## Verification

- Full `go test ./...` green after the 113 assertion updates (the suite is the safety net: a mis-encoded expectation would fail).
- `console.log(1 < 2)` → `true`; `console.log(x instanceof C)` → `true`/`false`; a boolean inside a template literal was already correct and stays so.
- `make conformance` re-run — see `docs/testing/CONFORMANCE-RESULTS.md`.
