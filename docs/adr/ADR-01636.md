# ADR-01636: A buffer that cannot be allocated is a RangeError; range errors carry Node's messages

- **Relations**: Extends ADR-00312, ADR-00494
- **Date**: 2026-10-14

## Context

The Test262 run's memory line named a 32 GB request, refused by the job cap.
It came from the four `allocation-limit` files, which fail: `new
ArrayBuffer(7 PiB)` must throw a RangeError (CreateByteDataBlock: "if it is
impossible to create such a Data Block, throw a RangeError").

## Investigation

- `emitNewArrayBufferExpression` called `calloc` and never looked at the
  result. Outside a job a 7 PiB buffer "succeeded" with a null data pointer.
- With a null check added, an *unused* `new ArrayBuffer(n)` still succeeded:
  clang -O2 deletes an unused `calloc` it can see and folds the null check as
  if the allocation had succeeded. A `nobuiltin` call-site attribute did not
  survive optimization.
- `new XArray(n)` allocated the same way, with no length validation.
- Every range check in `emit_arraybuffer.go` and `emit_buffer.go` threw a
  plain `Error` whose message began `RangeError: `, so `instanceof
  RangeError` was false, and none of the messages were Node's. Node 24.19's
  messages, for each case, were taken from runs of the same programs.

## Decision

- An ArrayBuffer's or typed array's data block comes from
  `__kml_byte_block_alloc` (`coresrc/core.c`), out of the optimizer's view; a
  null block for a non-zero size throws `RangeError: Array buffer allocation
  failed` (`Invalid array buffer max length` for a growable buffer's
  reservation).
- `new XArray(n)`: a negative length, or one past 2^53−1 bytes, is
  `RangeError: Invalid typed array length: n`, as in V8.
- `new XArray(buffer, offset, length)` checks in
  InitializeTypedArrayFromArrayBuffer's order with V8's messages: `Start
  offset N is outside the bounds of the buffer` (negative, or past the end
  without a length), `start offset of T should be a multiple of S`, `byte
  length of T should be a multiple of S`, `Invalid typed array length: N`.
- `resize`/`grow`: `ArrayBuffer.prototype.resize: Invalid length parameter`,
  `SharedArrayBuffer.prototype.grow: Invalid length parameter`.
- Buffer `read*`/`write*` follow Node's `boundsError`: a fractional offset is
  `ERR_OUT_OF_RANGE … It must be an integer`; a buffer shorter than the
  access is `ERR_BUFFER_OUT_OF_BOUNDS`; otherwise `ERR_OUT_OF_RANGE … It must
  be >= 0 and <= L. Received N`, the received value grouped by underscores
  past 2^32 as Node prints it (`__kml_received_int`).
- All of these are real RangeErrors (`emitInternalThrowKind`,
  `emitThrowCoded`); `emitThrowRangeErrorNum` builds a message around a
  runtime number.

## Implementation notes

`codegen/llvm/emit_arraybuffer.go`, `emit_buffer.go`, `runtime_core.go`,
`emitter.go`, `coresrc/core.c`.

## Verification

Windows 11: 24 cases (allocation failures, every view, resize/grow and
Buffer accessor error) print the same class, code and message as Node 24.19;
`TestE2EArrayBufferAllocationFailureIsRangeError` compares them with Node.
`TestE2EArrayBufferResizeShrink`, `TestE2EGrowableBuffers` and
`TestE2ETypedArrayBufferLengthNotMultipleOfElementSizeThrows` had encoded the
old messages and now check Node's. The ArrayBuffer, DataView, TypedArray and
Buffer tests pass. Test262 (js lane), `built-ins/ArrayBuffer`,
`SharedArrayBuffer`, `TypedArray`, `TypedArrayConstructors`, `DataView`: 12
files newly pass (the allocation limits, too-large and negative lengths and
max lengths), none newly fail.
