# TDD-00250: The `dns` resolver on c-ares

- **Status**: Implemented
- **Date**: 2026-10-11

## Context

[TDD-00236](TDD-00236.md) chose an own DNS client over vendoring c-ares,
on the grounds that the observable results are the records and status
codes, and that those follow from the RFCs. They do not. Each step from
the wire to the callback is a c-ares behavior that Node users see:

- which servers a channel starts with, and the loopback fallback;
- the query it sends (no EDNS OPT record);
- `ARES_FLAG_NOCHECKRESP`, which returns SERVFAIL/REFUSED instead of
  trying the next server;
- the parsers' handling of CNAME chains, TTL caps, TXT chunks and SOA;
- the status a malformed answer maps to.

The own client got several of these wrong. It sent EDNS, and
`resolveAny` returned `ENOTIMP` against Node's own `test/common/dns`
servers. The node-suite tests that drive a fake server could not pass.
The one E2E test of the resolver queried the internet and was never
deterministic.

## Design

Node's `src/cares_wrap.cc` (v26.10.0), ported to C over the system c-ares.

- **Channel**: `ChannelWrap::Setup` exactly:
  - flags `ARES_FLAG_NOCHECKRESP`;
  - optmask `ARES_OPT_FLAGS|TIMEOUTMS|SOCK_STATE_CB|TRIES|QUERY_CACHE`, plus
    `MAXTIMEOUTMS` when set;
  - query cache off.
- **Running a channel on POSIX**: on the loop of the thread that made it,
  as Node does: the sockstate callback starts a `uv_poll_t` per socket
  and a `uv_timer_t` drives `ares_process_fd`. `EnsureServers` re-creates
  a channel left with the loopback fallback after a failed query.
- **Queries**: `ares_query` for each record type and `ares_gethostbyaddr`
  for `reverse`. The answer is parsed by c-ares' parsers in the order and
  shape of each `*Traits::Parse` (including `AnyTraits::Parse`). The
  parsed value crosses to TypeScript as JSON; the TS side no longer
  interprets records.
- **Delivery**: the answer reaches the callback on a later turn of the
  loop, through the thread pool's completion queue. This stands in for
  cares_wrap's `SetImmediate`.
- **Servers, local address, cancel**: `ares_get_servers_ports`,
  `ares_set_servers_ports`, `ares_set_local_ip4/6`, `ares_cancel`;
  `DNS_ESETSRVPENDING` while queries are in flight.
- **Names**: the query name passes through IDNA to-ASCII (lowercase, then
  Punycode), as Node's `ada::idna::to_ascii` does.
- **Windows**: no libuv loop runs there yet (win32io's reactor), so a
  channel uses c-ares' own event thread (`ARES_OPT_EVENT_THREAD`), which
  posts each answer to the loop. The resolver is its own C unit, because
  `ares.h` brings in the platform socket headers, which the pool's unit
  does not include on Windows.
- **Old system c-ares**: c-ares 1.27, the version Ubuntu 24.04 ships,
  joins a TXT record's strings into one chunk; the c-ares Node bundles
  keeps them as separate chunks. TXT records are therefore read from the
  answer section directly. TLSA is read the same way, because its
  c-ares parser is newer than 1.27.

c-ares becomes a system dependency, like libuv: Homebrew `c-ares`, apt
`libc-ares-dev`, MSYS2 `mingw-w64-ucrt-x86_64-c-ares`. Only a program
that uses the resolver links it.
