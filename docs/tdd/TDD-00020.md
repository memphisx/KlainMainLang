# TDD-00020: Windows support

- **Status**: Not Started
- **Date**: 2026-07-30

## Context

The compiler only ever targets the host it runs on (`main.go` never emits an explicit `target triple` and invokes a bare `clang -O2 <file.ll> -o <out>`), and its C runtime is written directly against POSIX/BSD APIs throughout. `docs/status/README.md`'s `path` row already calls this out explicitly: "POSIX-only (this compiler doesn't cross-compile)." This document is the first real design pass on what a Windows target would actually take.

This is explicitly the lowest-priority item anywhere in this project — not a queued feature, not a roadmap entry, closer to a curiosity/reference document than a commitment. It exists so the shape of the work is on record in case it's ever picked up (e.g. to let programs run natively for people without WSL/Docker Desktop access), not because of any concrete need today. Nothing in `docs/status/README.md`'s Roadmap depends on it, and none of the three stated priority areas (REST API interaction, file I/O, CLI/process interaction) require it — all three already work fine on the two platforms actually supported.

## Design

### Two different problems, both scoped here

- **Cross-compile**: the compiler keeps running on macOS/Linux exactly as today, but emits IR for a Windows target triple (`x86_64-w64-mingw32`) and invokes a MinGW-w64 cross-clang (installable via Homebrew/apt on the existing dev/CI machines).
- **Native**: `klainmain.exe` itself runs on Windows, shells out to a Windows-installed clang, targets Windows directly.

The runtime-portability work in the audit table below — Winsock, the Fibers API port, `CreateProcess`, `SetConsoleCtrlHandler`, Boehm GC — is **identical between the two**: none of it cares whether the compiler binary driving clang runs on Windows or on macOS/Linux. The two paths only differ in toolchain setup and testing story, not in engineering scope, so there's no real reason to treat native as a deferred superset rather than an equally-valid entry point — which one to actually build first is purely a matter of which toolchain/test-infrastructure tradeoff is preferable (see below), not of one being cheaper in compiler-engineering terms.

**Cross-compile**: needs no new physical or virtual machine — the existing macOS/Linux dev loop and CI stay untouched — and the resulting `.exe` can be run and asserted on directly under Wine, so even acceptance testing doesn't require touching real Windows.

**Native**: Go itself cross-compiles to a Windows binary trivially (`GOOS=windows GOARCH=amd64 go build`), so building `klainmain.exe` isn't the hard part — `main.go` is pure Go plus `os/exec`/`filepath`, both already OS-aware in the standard library. The natural toolchain is **MSYS2** (ships MinGW-w64's clang running natively *on* Windows, not just as a cross-compiler target) rather than MSVC, for the same reasons the Toolchain section below gives. Two concrete advantages over cross-compiling: `pkg-config` genuinely works under MSYS2, so `LocateGC()`'s existing pkg-config-first strategy for finding libcurl/Boehm GC could work close to unmodified instead of needing a bundled-path/vcpkg fallback; and testing needs no Wine layer at all — `go test ./...` and `make examples` can run directly, using a real Windows CI runner (GitHub Actions' `windows-latest` makes this available with no new infrastructure to stand up). The tradeoff is exactly that: a new CI lane touching real Windows, where cross-compile keeps everything on the existing macOS/Linux machines.

### Toolchain: MinGW-w64, not MSVC/clang-cl

Two real options for the Windows target ABI:

- **MinGW-w64**: GNU-flavored, `-l<lib>` link flags (`main.go`'s `LinkLibs()` already emits exactly that syntax, unmodified), a libc closer in spirit to glibc, real `setjmp`/`longjmp` support.
- **MSVC / `clang-cl`**: Microsoft's ABI, SEH-based structured exception handling, `/link`-style flags instead of `-l`, a materially different C runtime.

Recommend MinGW-w64. It reuses the existing GNU-style link-flag generation as-is, and its C-level exception primitives (`setjmp`/`longjmp`, used throughout `runtime_exceptions.go`) are the same POSIX-style ones this compiler already emits against — MSVC's SEH model is a different mechanism entirely and would risk exactly the class of ABI-layout landmine already hit once with `ucontext_t` across Linux/Darwin ([ADR-00051](../adr/ADR-00051.md)) and with `sigaction`'s struct layout ([TDD-00019](TDD-00019.md)), just with a third, less-tested toolchain in the mix.

### Runtime surface audit — what's portable as-is vs. what needs a real rewrite

| Subsystem | Current implementation | Windows status |
|---|---|---|
| malloc/free/memcpy/strlen/printf/math/qsort/random/errno (`runtime_core.go`) | Plain C stdlib | Portable as-is, no change needed |
| `process.env`/`argv`/`cwd`/`chdir` (`runtime_process.go`) | `getenv`/CRT argv/`getcwd`/`chdir` | Portable as-is (MinGW's CRT supports all of these) — lowest-risk piece of the whole surface |
| `fetch`/`URL`/`URLSearchParams` (`runtime_fetch.go`, `runtime_url.go`) | libcurl | libcurl ships native Windows builds; no runtime-code changes, only build/link plumbing (see below) |
| `-mm=gc` (Boehm GC, `gclocate.go`) | pkg-config-located `libgc`/`bdw-gc` | Boehm GC has a Windows/MinGW port. Under a **cross-compile** toolchain, `LocateGC()`'s pkg-config-first strategy finds nothing (pkg-config on the macOS/Linux host knows nothing about Windows-target libs) — needs a genuine third branch (bundled path or vcpkg). Under **native**-via-MSYS2, pkg-config is a real, working package there too, so the existing strategy likely needs no change at all beyond confirming MSYS2 ships a `bdw-gc`/`gc` package |
| `try`/`catch`/`throw` (`emit_exceptions.go`, `runtime_exceptions.go`) | `setjmp`/`longjmp` | MinGW's libc has real `setjmp`/`longjmp`; should work unmodified for pure-C, non-SEH code (which is all this compiler ever emits) — needs empirical confirmation before trusting it, the same caution [TDD-00019](TDD-00019.md) gave `sigaction`'s struct layout rather than trusting docs alone |
| Sockets (`runtime_http.go`: `socket`/`bind`/`listen`/`accept`/hand-encoded `sockaddr_in`/`fcntl`) | Raw BSD sockets, with `SOL_SOCKET`/`SO_REUSEADDR` and `sockaddr_in` layout already hand-branched per-OS (Linux vs. Darwin) | Needs a genuine Winsock port: `WSAStartup`/`WSACleanup` bootstrap (nothing else needs this), `closesocket` instead of `close`, `ioctlsocket` instead of `fcntl(..., O_NONBLOCK)`, and a **third** `SOL_SOCKET`/`SO_REUSEADDR` constant pair alongside the Linux/Darwin ones already there — extends the existing `runtime.GOOS`-branch pattern rather than needing new machinery |
| `select()`-based event loop (`runtime_http.go`, backing `http.listen` and non-blocking `await fetch`) | POSIX `select()` over listener + connection fds | **Favorable finding**: this compiler's `select()` usage never watches anything but socket fds (no files, no pipes, no timerfds) — exactly the one case Winsock's own `select()` supports. The event loop's design translates directly; no IOCP/`WaitForMultipleObjects` rewrite needed here |
| Fiber scheduler (`runtime_http.go`: `getcontext`/`makecontext`/`swapcontext`, backing per-connection concurrency) | POSIX `ucontext.h` | **No equivalent exists in MinGW at all** — `ucontext.h` is a Unix-only concept, not just an unported header. Needs a genuine second implementation against the Windows Fibers API (`ConvertThreadToFiber`/`CreateFiber`/`SwitchToFiber`/`DeleteFiber`) — different lifecycle (explicit fiber objects, no stack+entry-point struct to lay out), so this is real new work, not a portability shim. The single hardest piece of this whole surface |
| `execFileSync` (`runtime_process.go`: `fork`/`pipe`/`execvp`/`waitpid`) | POSIX process model | **No equivalent exists at all** — `fork()` has no cheap Windows emulation, full stop. Needs a genuine rewrite against `CreateProcess`/`CreatePipe`/`WaitForSingleObject` |
| `process.on('SIGINT'\|'SIGTERM', ...)` ([TDD-00019](TDD-00019.md), [ADR-00079](../adr/ADR-00079.md)) | `signal()` + a `volatile` pending-flag checked at the top of the event loop | Windows' CRT `signal()` exists but Ctrl+C on a console app is normally delivered via `SetConsoleCtrlHandler`, not a POSIX-style `SIGINT` — MinGW's `signal(SIGINT, ...)` has a history of being unreliable for real Ctrl+C. Would need a `SetConsoleCtrlHandler`-based rewrite; the "handler only sets a `volatile` flag, real work happens later on the event loop" shape carries over unchanged, just triggered by a different OS mechanism. `SIGTERM` has no real Windows console equivalent at all outside Job Objects — would need to ship as a documented, permanent gap, not a silently-faked no-op |
| `fs.*` (`runtime_fs.go`) | POSIX `dirent.h`/paths | `struct dirent`'s layout is already flagged as non-portable even between Linux/Darwin (`runtime_fs.go:299`); MinGW ships a compatibility shim for `opendir`/`readdir`, but path-separator handling (`/` vs `\`) and the shim's actual semantics need real verification, not an assumption of drop-in compatibility — same category of risk `PATH.md`/[ADR-00081](../adr/ADR-00081.md) already flagged as POSIX-only |
| `--static` (`main.go:27-29`) | Already explicitly gated to Linux only (macOS ships no static libc) | Windows static linking (MinGW can static-link against its own runtime) is a third, different story and would need its own explicit gate rather than assuming the existing Linux-only check extends |

### Recommended sequencing, if ever picked up

Given the priority level, sequence for maximum optionality rather than completeness:

1. **Sockets/`select()` port** — mechanical, well-understood (a third branch on an already-three-way-in-spirit `runtime.GOOS` pattern), no new concepts.
2. **`fs.*` verification/port** — mostly confirming MinGW's `dirent` shim behaves, plus path-separator handling.
3. **`process.env`/`argv`/`cwd` verification** — expected close to free.
4. **`process.on(SIGINT/SIGTERM)` port** — `SetConsoleCtrlHandler`, same design shape as [TDD-00019](TDD-00019.md), smaller than it looks.
5. **`execFileSync` port** — `CreateProcess`, genuinely new but self-contained (one call site).
6. **Fiber scheduler port** — the hardest, most deferrable piece. A first Windows target could plausibly ship without it by gating `http.listen` (and non-blocking `await fetch`) as still-POSIX-only, covering the CLI-application use case (already one of this project's three stated priority areas) without touching the single riskiest subsystem. Only the microservice/HTTP-server use case would remain unavailable on Windows in that intermediate state.

Steps 1–6 are the same regardless of cross-compile vs. native. The one native-only addition is a Windows CI runner (`windows-latest`) to actually exercise `go test ./...`/`make examples` there; the one cross-compile-only addition is the Wine-based test harness listed in Prerequisites below.

## Open questions

- Whether to build cross-compile or native first if this is ever picked up — not decided. Cross-compile keeps everything on the existing macOS/Linux dev loop (no new CI runner) at the cost of a Wine-based test harness and a bundled/vcpkg GC-detection path; native needs a new Windows CI lane but tests directly with no Wine layer and likely gets pkg-config-based GC/curl detection close to free via MSYS2. Given the engineering scope is otherwise identical (see Design above), this is really a toolchain/CI preference, not a technical fork.
- Whether MSVC/`clang-cl` support is worth ruling out permanently in writing, or just left unaddressed until someone asks — not decided.
- Whether `process.on('SIGTERM', ...)` on Windows should be a silent no-op or a compile-time error given it has no real OS equivalent — leaning toward a compile-time error (consistent with this project's general preference for a clean rejection over a silently-wrong feature) but not decided.
- Whether a fiber-less "CLI-only" Windows target (see Recommended sequencing above) is worth ever shipping as an intermediate milestone, or whether Windows support only makes sense as an all-or-nothing port — not decided, and moot until this is ever actually picked up.
