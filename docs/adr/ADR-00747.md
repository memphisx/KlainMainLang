# ADR-00747: Windows console — UTF-8 code page for non-ASCII I/O

- **Relations**: Implements a [TDD-00180](../tdd/TDD-00180.md) §2 row; extends [ADR-00744](ADR-00744.md) (VT output at startup, same constructor), [ADR-00745](ADR-00745.md) (UTF-8 argv); relates to [ADR-00727](ADR-00727.md) (the pseudo-console harness that verifies it)
- **Date**: 2026-09-07

## Context

`console.log` writes UTF-8 bytes through the CRT (`printf`/`dprintf`), but a Windows console interprets bytes in its OEM code page (typically 437/850), so `console.log('café-日本語-Ω')` renders as `caf├®-µùÑµ£¼Þ¬×-╬®`. Reproduced under the pseudo-console harness. Node avoids this with `WriteConsoleW` (per-write UTF-16), which does not touch the console's code page.

The output path here has no single choke point to reroute through `WriteConsoleW`: `console.log` emits a series of `printf`/`dprintf` calls with C format strings, so a faithful `WriteConsoleW` port would mean reimplementing the formatting layer — an invasive, high-risk rewrite of the path every program uses, including the piped path the test harness reads.

## Decision

Set the attached console's code pages to UTF-8 at startup — `SetConsoleOutputCP(CP_UTF8)` and `SetConsoleCP(CP_UTF8)` in the shim constructor (`win32shim.c`, alongside the VT enable) — and **restore the originals at exit** via `atexit`, so a later program in the same real console is unaffected. This is a deliberate, documented divergence from Node's `WriteConsoleW`: it is *observably* the same for whole-line output (correct non-ASCII rendering) without the invasive reroute, and the save/restore removes the "changes global console state" objection for normal exits.

Key safety property: `SetConsoleOutputCP` affects only a console, never a pipe or file. `console.log` to a redirected/piped stdout still emits raw UTF-8 bytes unchanged — so the redirect path the test harness (and any `>` redirect, or a parent process capturing output) relies on is untouched. On a GUI/no-console process the calls are harmless no-ops.

## Consequences

- `tests/console_utf8_windows_test.go`: `console.log('café-日本語-Ω')` renders as that text under the pseudo-console (was mojibake) — verified on Windows 11. A separate piped assertion confirms redirected UTF-8 output is unchanged.
- Divergence from Node (code page vs `WriteConsoleW`) is documented here; the observable result matches. If a future need requires the exact `WriteConsoleW` behavior (e.g. streaming partial UTF-8 sequences, or never touching the console cp even transiently), that is a larger refactor of the console output path, tracked as future work.
- Input: `SetConsoleCP(CP_UTF8)` covers non-ASCII typed at the console for the raw-read path; whole-line `ReadConsoleW` conversion is not separately implemented.
- Still open in §2: a console-resize (`'resize'`) event; the `WriteConsoleW`/`ReadConsoleW` exact-fidelity path if ever needed.
