# ADR-02008: A flow answer left unanswered by a cycle is not cached

- **Date**: 2026-11-21

## Context

On the Test262 js lane, every `built-ins/Function/prototype/toString` test
(39 files) failed to compile: "no type for IndexExpression" inside the
`nativeFunctionMatcher.js` harness. HEAD compiled them. A reduced form:

```js
function v(source) {
  const nl = (c) => c === 1;
  let pos = 0, end = 0, match = 0;
  const e = () => { while (pos < source.length) {
    if (source[pos + 1] === "/") { if (nl(source[pos])) {} } } };
  const g = () => { switch (source[end]) { default: if (source[pos] === match) {} } };
}
v("s");
```

## Investigation

- A parameter inferred from its call sites (`nl`'s `c`, from
  `nl(source[pos])`) now answers `unanswered` when it is met again while
  still being inferred. Before, it answered `any`. A query that met such a
  cycle is not cached, so it is asked again once the parameter is typed.
- The flow walk's cache (`flowCache`, narrow.go) kept the answer anyway.
  Narrowing `pos` around `if (nl(source[pos]))` reaches `nl`'s signature
  while its parameter is open. The walk's join was cached as `unanswered`
  for `pos`, and every later read of `pos` and `source` in the arrows was
  answered from it.

## Decision

- A flow join that is unanswered because the walk met a query still being
  computed is not cached, as TypeOf and symbol typing already do.
- `callSiteParam` (jsmode.go) does not cache an unanswered parameter for
  the same reason.

## Implementation notes

- checker/narrow.go: `flowType`; checker/jsmode.go: `callSiteParam`.

## Verification

- Test262 on Linux x86 (Node304), `built-ins/Function`, js lane: 285 → 324
  of 509, the same as HEAD; strict 111.
- The checker and binder unit tests pass.
