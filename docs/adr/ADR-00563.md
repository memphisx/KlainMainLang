# ADR-00563: atob() rejects interior/excess `=` padding

- **Relations**: Extends ADR-00550, ADR-00458
- **Date**: 2026-09-01

## Context

After ADR-00550 brought `atob(s)` (`__kml_atob`) up to WHATWG forgiving-base64
for whitespace and missing padding, one disclosed leniency remained: the
character-validity loop marked `=` valid *anywhere* in the input, so an interior
or excess `=` (`"a=b="`, `"ab==="`, `"=abc"`) was tolerated — decoded as
alphabet index 0 — instead of rejected. Real `atob` accepts `=` only as trailing
padding.

## Investigation

The normalization prefix already computes `%sw` — the input length after the
up-to-two trailing `=` are stripped — and then re-pads from `%sw` to `%len` with
`=` to reach a multiple of 4. The validity loop, however, scanned `[0, %len)`
(including the re-padded region) with `=` marked valid in the lookup table. That
combination is exactly why an interior `=` slipped through: it was inside the
scanned range but treated as an allowed character.

## Decision

Two changes to `__kml_atob`:

1. `=` is removed from the base64 validity table — it is no longer a valid
   character anywhere.
2. The validity loop scans only the data region `[0, %sw)` — the bytes before
   the stripped trailing padding — instead of `[0, %len)`. The re-padded `=`
   region `[%sw, %len)` is known-`=` by construction and does not need
   validation.

Any `=` that survives into the data region is therefore an interior/excess pad
and throws `InvalidCharacterError`, matching real `atob`.

## Implementation notes

- Only `__kml_atob` changed; the decode loop still consumes `%norm`/`%len`
  (including the padding) unchanged, and its existing `ch2eq`/`ch3eq` selects
  still handle genuine trailing `=`.
- `%sw` dominates the validity loop (defined in the trailing-`=`-stripping
  `sloop`, which precedes the re-pad and validation blocks), so referencing it
  there is SSA-legal.

## Side effects discovered

None. Valid padded (`"aGVsbG8="`) and unpadded (`"aGVsbG8"`) inputs still decode
identically, and the whitespace/missing-padding behavior from ADR-00550 is
untouched.

## Verification

New `TestE2EAtobInteriorPaddingThrows` (`"a=b="`, `"ab==="`, `"=abc"` all throw
`InvalidCharacterError`; `"aGVsbG8="` still decodes) plus the existing
`TestE2EAtobForgivingBase64`, `TestE2EAtobInvalidCharacterThrows`, and
btoa/atob round-trip tests pass. Built and verified on Mac (Apple Silicon).
