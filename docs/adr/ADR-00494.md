# ADR-00494: Growable SharedArrayBuffer / resizable ArrayBuffer

- **Date**: 2026-08-29

## Context

`SharedArrayBuffer` had a "No `growable`/`grow()`" caveat. TypedArray
views hold raw data pointers, so any reallocating grow would invalidate
every existing view.

## Decision

The `{maxByteLength}` construction option reserves the maximum upfront
(the spec explicitly permits implementation-defined reservation): the
data block never moves, and `grow(n)`/`resize(n)` only bounds-checks
(RangeError on shrink or past-max — shrink rejection is a narrowing on
the resizable `ArrayBuffer` side, which the spec allows to shrink) and
bumps the header's length word. Growable buffers get a 24-byte
{len, data, max} header; every other producer keeps the 16-byte one, and
`BufferGrowable` on the *type* gates all word-2 reads so a fixed-header
buffer can never read out of bounds. Fixed buffers report
`growable`/`resizable` false and `maxByteLength` = `byteLength`, per
spec. `.grow()` on a buffer not constructed with `{maxByteLength}` is a
compile-time rejection rather than the spec's runtime TypeError.

## Verification

Mac. `tests/arraybuffer_test.go` `TestE2EGrowableBuffers` passes
(grow, view-across-grow, fixed-buffer reporting, RangeError);
ArrayBuffer/SAB/DataView/Atomics batch green;
