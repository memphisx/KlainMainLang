# ADR-00087: Logical assignment operators (`&&=`, `||=`, `??=`)

- **Date**: 2026-07-31

## Context

Flagged in `docs/status/README.md`'s "Newly identified gaps" list (2026-07-30
audit) as confirmed absent from the lexer/parser. Picked up alongside
ADR-00085/ADR-00086/ADR-00088 as another small front-end feature — though
this one turned out to need real new codegen, not just lexer/parser surface,
since these three operators are the only compound-assignment forms that are
genuinely short-circuiting (the right side must not even be evaluated down
the branch where the operator's own rule doesn't require it).

## Investigation

Checked how this compiler's existing `&&`/`||`/`??` binary operators behave
before designing the assignment forms, since a naive "desugar `a &&= b` to
`a = a && b`" approach would inherit whatever semantics those already have:

- `&&`/`||` (`codegen/llvm/emit_exprs_operators.go:178-188`) are **not**
  actually short-circuiting at the IR level — `emitBinary`
  (`emit_exprs_operators.go:8-16`) unconditionally evaluates both `left` and
  `right` before dispatching to the operator switch, and the `&&`/`||` cases
  themselves just do a plain `and`/`or` on two already-computed i1 values.
  A comment at the call site even documents this as deliberately
  "Simplified." This ruled out a `a &&= b` → `a = a && b` desugaring outright:
  logical assignment's entire reason to exist is the short-circuit, and if
  the desugared form doesn't have one, the feature doesn't do what it says.
- `??` (`emitNullCoalesce`, `emit_exprs_operators.go:483-521`) **is** genuinely
  short-circuiting — real branches, right side only evaluated inside the
  `null` branch — but only for `ptr`-typed values; for anything else (a
  number, a bool) the function returns `left` immediately without even
  reaching the branch, since a non-pointer value in this compiler's type
  system can never be null. Confirmed directly: `let x: number | null =
  null; console.log(x ?? 42)` prints `0`, not `42` — a real, pre-existing gap
  in how `number | null` represents "null" for a non-pointer type (see Side
  effects below), inherited as-is rather than fixed here.
- Also confirmed real JS semantics: `a &&= b` assigns (and only evaluates)
  `b` when `a` is truthy; `a ||= b` when `a` is falsy; `a ??= b` when `a` is
  null/undefined — in every case the *type* of the result can differ from
  `a`'s own type (assigning a string into what was a `string | null`, etc.),
  ruling out "just compute a boolean and store that" as a valid
  implementation shape.
- Checked `emitAssign` (`codegen/llvm/emit_exprs_assign.go`)'s four existing
  assignable forms (scalar variable, array element, object field, static
  class field via `emitStaticFieldAssign` in `emit_classes.go`) — every one
  of them already resolves to exactly a `(ptr, Type)` pair before running its
  own compound-op branch (`emitArith(strings.TrimSuffix(op, "="), ...)`),
  which is the one shape all four forms share. A fifth assignable form,
  computed-key dynamic-object bracket assignment (`emitDynamicObjectAssign`
  in `emit_objects.go`), does **not** share this shape — it stores through
  `__kml_map_str_set` calls, not a raw `ptr`/`store` — and was confirmed to
  already fail cleanly (`emitArith` hits its `default: unknown arithmetic
  operator` case) rather than silently misbehave if handed `&&`/`||`/`??`
  after `TrimSuffix`. That clean-failure precedent is what made scoping this
  case out (rather than building a second mechanism for it) an acceptable,
  documented narrowing rather than a silent gap.

## Decision

Added one shared helper, `emitLogicalCompoundAssign(op, ptr string, ty Type,
rhsExpr ast.Expression) (Value, error)` (`emit_exprs_assign.go`), used by all
four ptr-based assignable forms in place of the generic arithmetic-compound
branch when `op` is one of the three logical-assignment operators
(`isLogicalAssignOp`):

1. Load the current value from `ptr` once.
2. `??=` against a non-`ptr`-typed location returns the current value
   immediately, right side never evaluated — mirroring `emitNullCoalesce`'s
   own "left can never be null" fast path exactly, so this inherits that
   function's existing (documented, pre-existing) `number | null` gap rather
   than introducing a second, differently-shaped one.
3. Otherwise, compute the branch condition: `toBool(cur)` for `&&=`; its
   logical negation for `||=`; a real `icmp eq ptr ..., null` for `??=`.
4. Branch: down the "should assign" side, evaluate `rhsExpr`, coerce to
   `ty`, and store it back into the *same* `ptr` — the other side does
   nothing at all, leaving `ptr`'s existing contents untouched.
5. At the merge block, reload from `ptr`. Since `ptr` already holds the
   correct final value on both branches (either untouched, or freshly
   stored), no separate result temporary is needed the way
   `emitConditional`/`emitNullCoalesce` need one — those two branch into
   values that were never already sitting in one shared memory location.

Wired into all four sites: scalar variable assignment, array-element
assignment (`gepReg` from `emitIndexPtr`), object-field assignment (`gepReg`
from the field's `getelementptr`), and static-field assignment
(`globalPtr := "@ClassName_static_fieldName"` — an ordinary LLVM global
reference works with the exact same `load`/`store ptr` shape a local
`alloca` does, so no separate global-specific code path was needed).
Computed-key dynamic-object bracket assignment was deliberately left
unhandled — it already fails with a clean "unknown arithmetic operator"
error rather than miscompiling, and building the map-backed equivalent of
this mechanism was scoped out as a narrower, separate follow-on.

Lexer: three new tokens, `LOGICAL_AND_ASSIGN`/`LOGICAL_OR_ASSIGN`/
`NULLISH_ASSIGN` (`&&=`/`||=`/`??=`), recognized by extending the existing
`&`/`|`/`?` branches in `readNumber`'s sibling `NextToken` switch — after
already consuming the doubled character (`&&`, `||`, `??`), peek one further
for a trailing `=`. Parser: added to `parseAssignment`'s existing operator
switch, right-associative exactly like every other assignment operator
already is.

## Implementation notes

Files touched: `lexer/token.go` (three new token types + names map);
`lexer/lexer.go` (`&`/`|`/`?` branches extended); `parser/parser_exprs.go`
(`parseAssignment`'s switch, plus the file's own precedence-table doc
comment); `codegen/llvm/emit_exprs_assign.go` (`isLogicalAssignOp`,
`emitLogicalCompoundAssign`, wired into the scalar/array/field branches);
`codegen/llvm/emit_classes.go` (`emitStaticFieldAssign` wired the same way).

Non-obvious: `emitLogicalCompoundAssign` takes a bare `ptr string`, not a
`Symbol` — this is what let one function serve all four call sites, since a
scalar's `sym.Ptr`, an array element's `gepReg`, an object field's `gepReg`,
and a static field's `"@ClassName_static_x"` global reference are all
syntactically interchangeable as the operand of an LLVM `load`/`store`, even
though they come from four structurally different call sites upstream.

## Side effects discovered

- Confirmed (not fixed) the pre-existing `number | null` / `??` gap noted
  above: a `T | null` where `T` is a non-pointer type has no real "is this
  null" runtime check anywhere in this compiler today, so both bare `??` and
  the new `??=` silently treat such a value as never-null. Not a regression
  from this change — inherited as-is from `emitNullCoalesce`, which already
  had this exact shape before `??=` existed. Not tracked as a separate
  status-page row before this ADR; worth a follow-up if a concrete need for
  nullable-number/-bool `??`/`??=` shows up.
- Computed-key dynamic-object bracket assignment (`obj[key] &&= val` where
  `obj` is a computed-key object literal) is a documented, deliberate scope
  narrowing, not a silent gap — confirmed it fails with a clean compile
  error (`unknown arithmetic operator '&&'`) rather than misbehaving.
