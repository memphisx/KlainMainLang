# ADR-00114: RegExp Stage 0 — construction, literal syntax, field reads

- **Relations**: Implements [TDD-00035](../tdd/TDD-00035.md)
- **Date**: 2026-08-07

## Context

[TDD-00035](../tdd/TDD-00035.md) scoped RegExp support as a 7-stage design (Stage 0 through Stage 6). This ADR covers Stage 0: everything needed to construct a `RegExp` (both `new RegExp(pattern, flags?)` and a `/pattern/flags` literal), read its fields, and get a real catchable error on an invalid pattern — with no methods (`.test()`/`.exec()`/etc.) yet, those are later stages. Picked up directly following the TDD's approval, per the user's "start implementing Stage 0."

## Investigation

**PCRE2 was not actually installed as a dev dependency on this machine.** `dpkg -l` showed only the runtime package (`libpcre2-8-0`, providing `libpcre2-8.so.0`) already present — `libpcre2-dev` (headers, the `-l`-linkable `.so` symlink, the `.a` static archive) was not. Passwordless `sudo` isn't available in this environment (`sudo apt-get install` prompted for a password with no TTY), so a real system-wide install wasn't possible from here. Used `apt-get download libpcre2-dev` (no root needed, downloads the `.deb` to the working directory) plus `dpkg-deb -x` to extract it into a scratch directory (`/tmp/pcre2extract`) without installing — this gave direct access to the real `pcre2.h` and both `libpcre2-8.so`/`libpcre2-8.a` for verification and testing, without touching the system.

**Verified every hardcoded PCRE2 constant directly against the extracted `pcre2.h`** (Ubuntu/Debian `libpcre2-dev` 10.42-4ubuntu2.1) rather than trusting them from memory, per `CLAUDE.md`'s standing rule: `PCRE2_CASELESS = 0x00000008` (8), `PCRE2_MULTILINE = 0x00000400` (1024), `PCRE2_DOTALL = 0x00000020` (32), `PCRE2_ZERO_TERMINATED = ~(PCRE2_SIZE)0` (all bits set, i.e. `-1` as a signed `i64`). Also confirmed `pcre2_compile`'s and `pcre2_get_error_message`'s exact parameter types (`pcre2.h:650,785`) match what was assumed: `PCRE2_SPTR`/`PCRE2_UCHAR*` are byte pointers (`ptr` at the LLVM level), `PCRE2_SIZE` is `size_t` (`i64` on this target), `uint32_t` options map to `i32`. `pcre2_code`/`pcre2_match_data` are opaque pointers this code never lays out itself — unlike past cross-platform struct-layout bugs this project has hit (`ucontext_t`, ADR-00051; `GC_stackbottom`, ADR-00080), there's no memory-layout risk here, only these numeric constants need re-verification on the Apple Silicon Mac (flagged in Open Questions below).

**Found a real, general constraint the TDD hadn't fully worked through**: `emitGlobal` (`emitter.go:293`) is a bare string-append with no deduplication (`e.globals.WriteString(line + "\n")`), and confirmed empirically (a minimal two-line `.ll` file with an identical `declare ptr @strchr(...)` twice) that LLVM's parser rejects this outright — `invalid redefinition of function 'strchr'` — even though the two declarations are textually identical. This matters because `strchr` is already declared inline inside an unrelated `runtime_os.go` helper (`os.cpus()`'s parsing code, `runtime_os.go:198`), and flags-string parsing (`g`/`i`/`m`/`s` detection) looked at first like a natural fit for repeated `strchr` calls. Declaring `strchr` a second time from `runtime_regexp.go` would silently work in isolation but break any program that used both `os.cpus()` and a `RegExp` in the same compile. Resolved by not calling `strchr` at all — `ensureRegexParseFlags` hand-writes a single-pass byte-scanning loop as a uniquely-named `@__kml_regex_parse_flags` function instead, sidestepping the collision risk entirely (the established, safe convention: every C library function this compiler calls has exactly one owning `ensure*()` helper). Worth a wider callout: this is a real, general landmine for *any* future feature that wants to call a libc function already declared elsewhere in the codebase, not specific to regex — not fixed generally here (e.g. by adding real deduplication to `emitGlobal`), just worked around locally, and noted under Side effects below.

**Confirmed `emitInternalThrow`'s `msgPtr` parameter accepts any `ptr`-typed IR operand**, not just a compile-time-interned string constant (`emit_exceptions.go:83-87` — it's substituted directly into a `store ptr %s` instruction) — needed since PCRE2's compile-error message is only known at runtime, built via `pcre2_get_error_message_8` into a `malloc`'d buffer, not something `internString` could produce ahead of time.

**Decided the thrown error should be a real `SyntaxError`, not the generic base `Error` `emitInternalThrow` always uses.** Real JS's `new RegExp("(")` throws `SyntaxError: Invalid regular expression`, and this compiler already has a real `SyntaxError` kind (`errorKinds`/`errorKindIDs`, `emit_exceptions.go:13-25`, kind index 3, from TDD-00013/ADR-00082) — so `emitInternalThrow` (hardcoded to kind 0) wasn't used directly; instead `buildErrorObj(errorKindIDs["SyntaxError"], msgBuf, e.internString("SyntaxError"))` plus `__kml_throw`/`unreachable` were inlined in `emitNewRegExpExpression`, mirroring `emitInternalThrow`'s own 3-line body exactly but with the right kind — a correctness improvement over the TDD's original framing of "just throw a catchable Error," at negligible extra cost since the machinery already existed.

## Decision

- **Lexer** (`lexer/lexer.go`, `lexer/token.go`): added a `lastSig TokenType` field to `Lexer`, initialized to `SEMICOLON` (a statement boundary — the correct "start of input is regex-legal" default) and updated by a new thin `NextToken()` wrapper around the renamed `nextToken()` (the original body, unchanged in its own logic — its two internal comment-skipping recursive calls now call `nextToken()` directly rather than the public wrapper, so `lastSig` updates exactly once per real token returned to the caller). `regexIllegalAfter` is a small, deliberately *inverted* map — only the "a value just ended" token types are listed (`IDENT`, `NUMBER`, `STRING`, `TEMPLATE_NO_SUB`/`TEMPLATE_TAIL`, `TRUE`/`FALSE`/`NULL`/`UNDEFINED`, `THIS`/`SUPER`, `RPAREN`/`RBRACKET`/`RBRACE`, `INC`/`DEC`) — with every other token type (all operators, keywords, punctuation) defaulting to regex-legal, matching how real JS engines implement this same heuristic and keeping the list short. `readRegex` scans a `/pattern/flags` literal once `regexAllowed()` (checked right after the existing comment-detection code, which still runs first and wins — preserving real JS's own grammar restriction that a regex literal's first character can never be `*` or `/`, so `//` always stays a comment): backslash escapes are preserved verbatim (unlike `readString`, which translates them — PCRE2 needs to see the real `\d`/`\/`), and an `inClass` boolean tracks unescaped `[`/`]` so an unescaped `/` inside a character class doesn't terminate the pattern. A new `Token.Flags string` field carries the flag letters (scanned with zero validation at this layer, deferred downstream). New `REGEX` `TokenType`.
- **AST/parser** (`ast/nodes.go`, `parser/parser_literals.go`): one node, `ast.NewRegExpExpression{Pattern, Flags Expression}` (`Flags` nilable for the constructor's 1-arg form). `new RegExp(pattern, flags?)` (`parseNew`'s dispatch, alongside `URL`/`TextEncoder`) and a bare `/pattern/flags` literal (`parsePrimary`'s new `case lexer.REGEX`, wrapping the token's pattern/flags text as `ast.StringLiteral`s) both build this same node — codegen has exactly one shape to handle regardless of surface syntax.
- **Type system** (`codegen/llvm/types.go`): `IsRegExp` flag + `RegExpType()`, a real `ObjectType`-based heap object (not `TextDecoder`'s stateless-`"null"`-marker shape) with a hidden field 0 (`RegexHandleField`, excluded from `VisibleFields()` the same way `IsError`'s hidden kind tag is) holding the compiled `pcre2_code*`, followed by visible `source`/`flags`/`global`/`ignoreCase`/`multiline`/`dotAll`/`lastIndex` fields — `dotAll` was added beyond the TDD's originally-sketched field list once cross-checked against its own flag-scope table, which already listed `s` as in-V1-scope. `RegExp` also added to `ResolveTypeName` (a `re: RegExp`-typed parameter/annotation now resolves correctly).
- **Runtime declarations** (new `codegen/llvm/runtime_regexp.go`): `ensureRegexCompile` declares `pcre2_compile_8`/`pcre2_get_error_message_8` and calls `requireLink("pcre2-8")` (exactly where `ensureFetch`/`ensureCurlURL` call `requireLink("curl")` — `main.go` needed zero changes, `LinkLibs()` is already fully generic). `ensureRegexParseFlags` defines `__kml_regex_parse_flags`, a hand-written single-pass loop over the flags string producing PCRE2's combined option bits plus the four decomposed booleans — see Investigation for why this isn't built from `strchr`.
- **Construction** (new `codegen/llvm/emit_regexp.go`): `emitNewRegExpExpression` evaluates pattern/flags (defaulting flags to `""` when omitted), calls `__kml_regex_parse_flags`, calls `pcre2_compile_8`, branches on a null return, throws a real `SyntaxError` (see Investigation) on the bad branch, and on the OK branch builds the full `RegExpType()` object.
- **Dispatch wiring**: `emit_exprs.go` (generic `emitExpr`), `emit_exprs_types.go` (`inferExprType`), `emit_exprs_vardecl.go` (the separate unannotated-`const` inference switch) — all three, the same trio ADR-00112/ADR-00113 found necessary earlier this session for the identical reason (an unannotated `const r = new RegExp(...)` needs its real type known before `r.source` type-checks, and neither inference path falls back to the other automatically for a dedicated `New*Expression` node).

## Implementation notes

Files touched: `lexer/lexer.go`, `lexer/token.go`, `ast/nodes.go`, `parser/parser_literals.go`, `codegen/llvm/types.go`, `codegen/llvm/emitter.go` (two new `used*` guard fields), `codegen/llvm/emit_exprs.go`, `emit_exprs_types.go`, `emit_exprs_vardecl.go`; new `codegen/llvm/runtime_regexp.go`, `codegen/llvm/emit_regexp.go`.

Non-obvious ordering constraint: the regex-literal check (`if ch == '/' && l.regexAllowed()`) must sit *after* the existing comment-detection block but *before* the digit/template/string/ident checks in `nextToken` — comment detection winning first is load-bearing (see Investigation), and the position relative to the other checks doesn't matter functionally but keeping it immediately after comments reads clearest.

`errCodeSlot`/`errOffSlot` (PCRE2's out-parameters for the compile error code/offset) are always allocated even on the eventual success path — matches this project's two-builder convention (`e.allocas` for every entry-block alloca regardless of which branch actually uses it, `e.body` for everything else) rather than trying to conditionally skip the allocation.

## Side effects discovered

The `emitGlobal`-has-no-deduplication + "two identical `declare`s for the same symbol still fail" landmine (see Investigation) is real and general, not regex-specific — any future feature wanting to call a libc function some other file already declares would hit it. Not fixed here (worked around locally by not calling `strchr` at all); if it recurs, the real fix would be either a real dedup set in `emitGlobal` keyed on the declared symbol name, or consolidating every libc `declare` into one shared, always-available set of `ensure*()` helpers regardless of which feature first needed them. Tracked here as a known landmine, not yet worth a dedicated ADR of its own since it hasn't caused a real bug (only would-have, caught during this investigation before it shipped).

## Verification

- `go build ./...` and `go vet ./...` clean.
- `go test ./...` — full existing suite passes unchanged (confirmed with `LIBRARY_PATH` pointed at the extracted PCRE2 `.deb`'s library directory so the new RegExp tests could link — see the note below on the real install requirement).
- New tests: `tests/regexp_test.go` — constructor field decomposition (with and without flags), the `s`/`dotAll` flag, literal syntax, an escaped `\/` inside a pattern, an unescaped `/` inside a `[...]` class not terminating the literal, plain division still working unaffected (`a / b`, `a / b / 1`), two distinct invalid-pattern-throws-`SyntaxError` cases, and permissive handling of an unrecognized flag letter.
- New example: `examples/regexp/regexp.ts`, manually verified end-to-end (both construction forms, field reads, division non-interference, the character-class-slash case, and the catchable-`SyntaxError` case) — not yet run through `make examples` on a machine with `libpcre2-dev` actually installed (see below).
- **A real, not-yet-satisfied install requirement remains**: this machine does not have `libpcre2-dev` installed system-wide (only the runtime `.so.0` was already present), and passwordless `sudo` isn't available in this environment to install it directly. All verification above was done by extracting the `.deb` via `apt-get download` (no root) into a scratch directory and pointing `clang`'s `LIBRARY_PATH` at it for linking — the resulting binaries then ran correctly using the system's already-installed runtime `.so.0` (no `LD_LIBRARY_PATH` needed at run time, only at link time). **The user needs to run `sudo apt-get install libpcre2-dev` (or the equivalent for their distro) themselves** before `go test ./...`/`make examples` will pass normally on this machine without the `LIBRARY_PATH` workaround; `README.md`'s Requirements section has been updated accordingly.
- Verified on: x86-64 Linux only (this session's machine). Per `CLAUDE.md`'s standing platform-verification rule, the hardcoded PCRE2 constants and the whole PCRE2 linking story have not yet been re-verified on the Apple Silicon Mac — flagged as an open item, same as [TDD-00035](../tdd/TDD-00035.md) already anticipated.
