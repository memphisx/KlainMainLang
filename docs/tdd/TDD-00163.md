# TDD-00163: FinalizationRegistry — mode-dependent finalization + leak diagnostics

- **Status**: Not Started
- **Date**: 2026-09-03

## Context

`FinalizationRegistry` is one of the two GC-observing primitives in modern
JavaScript (the other, `WeakRef`, this compiler already implements — see
`emit_weak.go` / `runtime_weak.go`). Its stated job: run a cleanup callback,
with a caller-supplied *held value*, some time after a registered *target*
object is garbage-collected — the standard way to release an external resource
(a file descriptor, a native handle, a WASM buffer) tied to a JS object's
lifetime without manual bookkeeping.

Two facts make it an unusually good fit to scope *now*, and to scope
*ambitiously* rather than as a rote port:

1. **The spec hands us total freedom on timing.** Cleanup callbacks are
   explicitly *best-effort*: the engine may run them late, batched, or **never**
   (§ "Execution" of the FinalizationRegistry proposal, and the note that a
   conforming implementation may never call any cleanup callback). So *every*
   firing policy we choose is conformant, including firing at points real
   engines never would. Correctness is free; the design question is which
   timing is most *useful* per memory mode.

2. **This compiler has more than one memory model, chosen at compile time.**
   Under `-mm=gc` (Boehm) objects are collected and a real finalizer can fire.
   Under the default `-mm=manual` objects are never collected ("leak by
   design") — so a naive port would be a no-op that *never* fires, which is
   conformant but useless. Instead, manual mode has something the GC world does
   not: a **deterministic death point** (`Memory.free(x)`), and a program that
   leaks by default and therefore *badly wants a leak story*.

The result is a feature whose *same source API* produces genuinely different,
each-honest behavior per memory mode: a faithful GC hook, deterministic
destructors, and an opt-in leak detector. That directly inverts a competitor
gap — PerryTS ties FinalizationRegistry to its always-on GC; here it becomes a
first-class **memory-management and debugging tool that works in every mode**,
including the future `auto` mode.

## Design

### API surface (identical across all modes)

Standard shape, typed:

```ts
// T is the held-value type; the callback receives held values, never targets.
const reg = new FinalizationRegistry<T>((held: T) => { /* cleanup */ })
reg.register(target /* object */, held: T, unregisterToken? /* object */): void
reg.unregister(unregisterToken /* object */): boolean
```

Notes on the contract we hold to in every mode:

- `target` must be an object reference. Reuse the existing object-reference
  check from `weakObjectKey` (`emit_weak.go`) — including its brand-new
  `-compat=js` path that unboxes a dynamic (`any`) object referent (ADR-00661),
  so `new FinalizationRegistry` "just works" against D1 dynamic objects too.
- `held` is stored in the registration and handed to the callback; it must be
  independent of `target` (real JS requires `held !== target`; we can enforce
  that at compile time when both are statically known, else leave it to the
  caller — a `held === target` would keep the target alive under gc, defeating
  the point).
- `unregisterToken`, if given, must be an object; `unregister(token)` removes
  every registration made with that token and returns whether any existed.
- The non-standard-but-widely-shipped `reg.cleanupSome(cb?)` (V8/JSC) maps
  naturally onto "drain N pending callbacks now" (see the queue below) — worth
  supporting since some Node tests use it; optional for V1.

### Mode-dependent timing (the core idea)

| Mode | When the callback fires | Nature |
|---|---|---|
| `-mm=gc` | when Boehm proves `target` unreachable | real, best-effort, event-loop-deferred |
| `-mm=manual` (default) | at `Memory.free(target)`, **plus** any survivors at `atexit` | deterministic destructors + exit flush |
| `-mm=manual -finalizers=report` | as above, **plus** a labeled diagnostic for every registration still live at exit | deterministic destructors + leak detector |
| `-mm=auto` (future, TDD-00134/00135) | at escape-analysis scope exit where provable, else at collection | deterministic where provable, GC otherwise |

All four are conformant (best-effort permits every one). The manual-mode
behaviors are *more* useful than the JS original for this project's CLI /
microservice targets, not a degradation.

### Unified runtime: one pending-callback queue, several death signals

The elegant version has a single execution path and several triggers:

- **A runtime registry object** per `FinalizationRegistry` instance:
  - a strong list of registrations `{ held, token }` keyed by an internal id;
  - a `token → []registrationId` index for `unregister`;
  - under `-mm=manual`, a **process-global `pointer → []registration` map**
    (a small open-addressing hashtable in the C runtime) so `Memory.free(ptr)`
    can find the registrations targeting that pointer. (gc mode needs no such
    map — Boehm holds the association.)
- **A process-global pending-finalizer FIFO** of `{ jsCallbackClosure, held }`.
- **Death signals enqueue, they do not execute:**
  - `-mm=gc`: a Boehm finalizer trampoline (registered via
    `GC_register_finalizer` — the finalizer sibling of the
    `GC_general_register_disappearing_link` call `runtime_weak.go` already
    makes) pushes `{cb, held}` onto the FIFO. It runs in the collector, so it
    does the *minimum* — enqueue only, never call into JS (reentrancy /
    allocation-during-GC hazard).
  - `-mm=manual`: `Memory.free(ptr)` looks up `ptr` in the pointer map and
    pushes each registration's `{cb, held}` onto the FIFO, then removes them.
  - `atexit`: a runtime shutdown hook drains the FIFO, and (manual mode) first
    enqueues every still-live registration so survivors get one last cleanup.
- **The event loop drains the FIFO as a macrotask.** The existing
  `select()`-based loop already has a "run pending callbacks" turn; finalizer
  callbacks are just another queue it services, one at a time, matching JS's
  "callbacks run on the event loop, not synchronously" semantics. A program
  with no event loop turns before exit still gets its callbacks at the atexit
  drain. `cleanupSome` = drain up to N now.

This gives one code path (`enqueue → event-loop/atexit drain → invoke
`cb(held)`), three triggers, and identical observable ordering semantics
regardless of mode.

### Leak diagnostics (`-finalizers=report`)

A `FinalizationRegistry` is, structurally, *a ledger of live resources labeled
by their held values*. Under `-mm=manual` a registration still live at exit
means its target was **never freed** — a leak, and one the program has already
labeled for us. With `-finalizers=report` (default off), the atexit hook, before
its cleanup drain, prints one diagnostic line per surviving registration:

```
[finalizers] leak: 3 registration(s) never freed
  held=<stringified held value>   registered at <file:line of .register()>
  ...
```

`held` is stringified with the existing value-printer (a descriptive held value
— `"buffer for request 42"` — makes the report self-documenting); the
registration site comes from a `file:line` captured at the `.register()` call
(cheap: pass the call-site position into the registration as two ints). This
turns a GC primitive into the leak detector the manual-memory model otherwise
lacks — and it composes: cleanup still runs (fds released), *and* you get told
what you forgot to free.

Flag surface: `-finalizers=off` (default) | `report` (leak lines) — with room
to grow (`strict` could make a leak a nonzero exit, for CI). Follows the
existing conditional-flag convention (`-bigint`, `-crypto`, `-regex`).

### Callback execution context & reentrancy

- gc mode: enqueue-only in the Boehm finalizer; never allocate or call JS there.
  Drained later on the main fiber.
- manual mode: `Memory.free` also only enqueues — it must not run arbitrary JS
  mid-expression (the free could be inside another expression). Drained on the
  next event-loop turn / at exit.
- Ordering: FIFO by death order; within one drain, one callback at a time; a
  callback that throws is reported and does not abort the drain (matches JS's
  per-callback isolation).

### Type & parser design

- Parser: `new FinalizationRegistry<T>(cb)` — a `NewExpression` with an optional
  type argument, like `new Map<K,V>()` / `new WeakRef<T>()`. The callback is a
  one-parameter function of `T`.
- `types.go`: a `FinalizationRegistryType(T)` carrying the held type (mirrors
  `WeakRefType`); methods `register`/`unregister`/`cleanupSome` dispatched in
  `emit_call.go` the way `emitWeakCall` dispatches WeakMap/WeakSet.
- `inferExprType`: `new FinalizationRegistry<T>()` → that type; method-call
  return types (`register` → void, `unregister` → boolean).

### Interaction with existing primitives

- **WeakRef**: the natural companion. A common idiom is a `WeakRef` plus a
  `FinalizationRegistry` on the same target; both ride the same Boehm object in
  gc mode and can share the object-reference plumbing.
- **`Memory.free`**: gains a finalizer-lookup step in manual mode (behind a
  "any finalizers registered?" global flag so programs that never use the
  feature pay nothing).
- **`-compat=js` D1 objects**: `register(target, …)` accepts a dynamic object
  referent via the ADR-00661 unbox path — no extra work.

### Staging (incremental delivery)

1. **Stage 1 — API & type surface.** Parser, type, `new FinalizationRegistry`,
   `register`/`unregister` storing registrations; no firing yet. Compiles and
   type-checks; callbacks simply never run (still conformant).
2. **Stage 2 — manual-mode firing (highest value, default mode, no GC needed).**
   The pointer→registration map, `Memory.free` enqueue, the pending FIFO, the
   event-loop drain, and the `atexit` survivor-flush. Deterministic destructors
   land here.
3. **Stage 3 — `-mm=gc` faithful path.** `GC_register_finalizer` trampoline →
   same FIFO. Real collection-triggered finalization.
4. **Stage 4 — `-finalizers=report` leak diagnostics.** Call-site capture +
   atexit report.
5. **Stage 5 (future) — `auto` mode.** Escape-analysis scope-exit finalization
   where provable (TDD-00134), Boehm/Immix finalizers otherwise (TDD-00135).

Recommended order is exactly the above: Stage 2 first, because it delivers the
most useful, most differentiated behavior in the *default* mode and needs no GC.

### Faithfulness / documented divergence

The one deliberate divergence to record (an ADR, same posture as WeakRef's
"leak by design in manual mode"): **manual-mode timing is deterministic**
(`free`-point / `atexit`), where real JS is non-deterministic and
collection-driven. This is a divergence in observable *timing only*, and the
spec's best-effort clause explicitly permits it — the *contract* (callback
eventually runs with `held`, or never) is upheld. Under `-mm=gc` timing matches
real JS's "eventually, after collection, on the event loop."

## Open questions

1. **`atexit` seam**: the C `atexit` hook is already in use (`__kml_h2c_flush`),
   so the main-thread drain + report has a home. Open part: `atexit` is
   process-global, but every runtime singleton is `thread_local` — a worker
   thread should drain *its own* FIFO at *its own* exit (a thread-exit hook /
   the worker loop's teardown), not at the process `atexit`. Resolve where the
   per-worker teardown seam is.
2. **Cross-thread targets**: a `FinalizationRegistry` and its target created on
   different worker threads — restrict registration to same-thread targets for
   V1 (the pointer map is `thread_local`), reject or document otherwise.
3. **`held === target` enforcement**: reject at compile time when both are
   statically the same binding (cheap, catches the footgun) and leave the
   dynamic case to best-effort, or skip entirely for V1?
4. **`cleanupSome`**: ship in V1 (some Node tests use it) or defer? It's a thin
   wrapper over "drain up to N".
5. **Double registration / `Memory.free` of an already-freed pointer**: manual
   mode must tolerate a pointer freed twice (guard the pointer-map lookup) and a
   target registered under multiple registries.
6. **Report verbosity**: `report` lists every leak; for a program with thousands
   of registrations a summarized + top-N form may be needed (mirror the
   conformance blocked-by histogram's top-N cap).
7. **Should `-finalizers=strict` (leak ⇒ nonzero exit) be in scope**, for using
   this as a CI leak-gate? Natural extension, but decide whether V1 or later.
