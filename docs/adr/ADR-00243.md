# ADR-00243: CI robustness — link libpcre2 explicitly, de-flake performance.mark overwrite test

- **Relations**: Surfaced while replicating [ADR-00242](ADR-00242.md)'s cbrt CI failure in Docker
- **Date**: 2026-08-19

## Context

Replicating the [ADR-00242](ADR-00242.md) `cbrt` CI failure meant running the full
suite in a glibc container matching `ubuntu-latest`. Two pre-existing CI-robustness
issues surfaced, both unrelated to the cbrt fix:

1. **RegExp tests link `-lpcre2-8`, but the workflow never installs it.** The
   `release.yml` step installed `clang libcurl4-openssl-dev libgc-dev
   libtommath-dev` — no `libpcre2-dev`. CI passed only because `ubuntu-latest`
   happens to ship pcre2; a minimal container failed the RegExp tests with
   `cannot find -lpcre2-8`. A runner-image change dropping pcre2 would break CI
   with no code change.
2. **`TestE2EPerformanceMarkOverwrite` is timing-flaky.** It asserted `d2 < d1`,
   where `d1` spans a 200k-iteration loop and `d2` spans ~nothing after re-marking;
   ~1 failure in 5 runs inside a Docker-on-macOS VM. The cause was investigated,
   not assumed — a `clang -O2` dead-code-eliminating the loop was one hypothesis,
   but a probe printed `arrlen=200000` on every run (the loop executes) and, more
   tellingly, `d1` was always an *integer* `0` or `1` where the nanosecond
   `CLOCK_MONOTONIC` the impl uses would show a fraction for a real interval. So
   the VM's monotonic clock is ~1 ms coarse, and the ~0.5–1 ms loop straddles the
   tick: sometimes `d1 == 1`, sometimes `d1 == 0 == d2`. On real hardware/CI (fine
   clock) `d1` is a nonzero fraction and `<` is solid — which is why CI passed.

## Decision

1. Add `libpcre2-dev` to the workflow's apt install line (and note in the step
   name that RegExp links `-lpcre2-8`), so the dependency is explicit rather than
   inherited from the runner image.
2. Two tests instead of one:
   - Keep the original as the **pure, dependency-free** check, but relax `d2 < d1`
     to `d2 <= d1`. This removes exactly the coarse-clock false-failure (`0 <= 0`
     holds) while still catching a regression on any clock fine enough to measure
     the loop: without the overwrite, `d2` spans the whole loop plus the two
     `measure` calls, so `d2 > d1`.
   - Add a **stricter companion** (`TestE2EPerformanceMarkOverwriteMeasuredSpan`)
     that keeps `d2 < d1` but guarantees a measurable interval: it busy-waits on
     `performance.now()` until ~8 ms have elapsed (well above any plausible
     monotonic-clock resolution) before the first measure, so `d1` spans a real
     interval regardless of clock granularity. A `setTimeout`-based `await` sleep
     would be the obvious delay, but this compiler has no `sleepSync` and `new
     Promise(...)` is not constructible (`unknown class 'Promise'`), so the
     synchronous busy-wait on the monotonic clock is used — it also self-calibrates
     against the same clock rather than assuming a wall-clock duration.

## Consequences

- CI no longer depends on the runner image implicitly providing pcre2.
- The pure test is deterministic across clock resolutions, trading only the
  unmeasurable coarse-clock case; the companion restores full strict-`<`
  regression detection unconditionally at the cost of a few ms of spin and a
  dependency on `performance.now()`.

## Verification

Full `go test ./...` passes in a fully-provisioned glibc container (Debian,
clang-16, with `libpcre2-dev`). Both overwrite tests passed 12/12 container runs
after the change (the pure one was ~4/5 before); the busy-wait companion produced
`d1≈7ms`, `d2=0` every run. Neither change touches compiler behavior.
