# ADR-00750: `fs.fsyncSync` / `fdatasyncSync` / `ftruncateSync` — fd-level durability and resize

- **Relations**: Implements a [TDD-00180](../tdd/TDD-00180.md) §4 row ("Missing entirely … `fsync`, `ftruncate`"); extends [ADR-00498](ADR-00498.md) (the fd-based fs ops `openSync`/`readSync`/`writeSync`/`fstatSync`/`closeSync`), [ADR-00719](ADR-00719.md) (the Win32 fs shim layer), [ADR-00737](ADR-00737.md) (the `__asm__` symbol-alias convention for POSIX names on Windows)
- **Date**: 2026-09-07

## Context

The fd-based fs family ([ADR-00498](ADR-00498.md)) covered `openSync`/`closeSync`/`readSync`/`writeSync`/`fstatSync` but not the two remaining fd operations Node exposes: `fs.fsyncSync(fd)` (flush buffered writes to disk) and `fs.ftruncateSync(fd[, len])` (resize an open file). The [TDD-00180](TDD-00180.md) §4 audit listed both under "Missing entirely (link errors, not `ENOSYS`)" — a program calling either would fail to link on Windows, and no emitter path existed on any host. `fdatasyncSync` (the data-only flush) was likewise absent. These are ordinary durability primitives for the CLI-tool / log-writer / database-file workloads this compiler targets.

## Investigation

`emit_fs.go`'s `emitFsCloseSync` (fd → `@close(i32)`) and `emitFsWriteSync`/`emitFsFstatSync` established the fd-op shape: `coerce(arg, TypeI64)`, `ensureFsFdOps()`, one call. `ensureFsFdOps` in `runtime_fs.go` already declared `open`/`close`/`read`/`write`/`lseek`/`fstat` and defined the throwing wrappers `__kml_fs_open`/`__kml_fs_fdrw` around `__kml_fs_throw` (which formats `"<opDesc> '<path>': <reason>"` from `errno` via `strerror`). `truncate(path,len)` already existed as a Win32 shim in `win32fs.c` (`SetFilePointerEx`+`SetEndOfFile`), giving the exact recipe for the fd form.

Two things surfaced while wiring it:

- On Windows, `fsync`/`ftruncate` are not CRT symbols, so a plain `@fsync`/`@ftruncate` call would link-fail — the reason the audit filed them under "link errors". They need Win32 shims like the rest of `win32fs.c`.
- `__kml_fs_throw` calls `strlen()` on its `path` argument. The existing `__kml_fs_fdrw` fail path passes `ptr null` — a latent segfault that no test exercises because `read`/`write` on a valid fd rarely fail. A new fd op whose *first* observable behaviour is "throw on a bad fd" hits it immediately (reproduced: a `try { fs.fsyncSync(9999) }` compiled binary segfaulted, exit 139).

## Decision

Add `fs.fsyncSync(fd)`, `fs.fdatasyncSync(fd)`, and `fs.ftruncateSync(fd[, len])`.

- **Emitters** (`emit_fs.go`): `emitFsFsyncSync` (1 arg → `call void @__kml_fs_fsync`) and `emitFsFtruncateSync` (1–2 args, `len` defaulting to `0` → `call void @__kml_fs_ftruncate`). `fdatasyncSync` dispatches to the same emitter as `fsyncSync`: the data-only optimization is not observable in a file's contents, so aliasing it is faithful and avoids a Windows/macOS `fdatasync`-symbol availability question.
- **Runtime** (`runtime_fs.go`, inside `ensureFsFdOps`): declare `@fsync`/`@ftruncate`, and define `__kml_fs_fsync`/`__kml_fs_ftruncate` — each calls the libc/shim function and, on a non-zero return, throws through the shared `__kml_fs_throw` with the existing `fdDesc` ("fd operation failed"). The path argument is an interned **empty string**, never `ptr null`, so `strlen` is safe (fd ops carry no path in the message anyway).
- **Windows shims** (`win32fs.c`): `int fsync(int fd)` → `_get_osfhandle` + `FlushFileBuffers`; `int ftruncate(int fd, int64_t len)` → `_get_osfhandle` + `SetFilePointerEx`/`SetEndOfFile` (mirroring the existing `truncate(path,len)`). Both are defined under `__asm__("fsync")`/`__asm__("ftruncate")` aliases (the [ADR-00737](ADR-00737.md) convention) so no mingw header prototype can collide with the definition. On error they route `GetLastError()` through the shim's `fail()` → Linux-ABI `errno`, so `e.code === 'EBADF'` matches.
- **Resolver** (`virtual_modules.go`): add the three names to the `fs` virtual module's member set so named imports (`import { fsyncSync } from 'fs'`) validate, alongside the existing `openSync`/`writeSync`/`readSync`.

## Implementation notes

- The empty-string path fix in `__kml_fs_throw`'s two new callers also documents the pre-existing `ptr null` in `__kml_fs_fdrw` as a latent crash; it is left as-is here (out of scope, never hit by a test) but noted so a future `read`/`write`-failure test knows to change it too.
- `ftruncateSync` growing a file zero-fills the gap, matching POSIX `ftruncate` and Windows `SetEndOfFile` semantics — no special-casing needed.
- The message text is `fd operation failed '': <reason>`, not Node's `EBADF: …, fsync` shape; this matches the rest of the fd-op family and is recorded as a caveat rather than closed here (the numeric `err.errno`/`err.syscall` gap is the same cross-cutting item tracked on every fs row).

## Side effects discovered

The `__kml_fs_throw` null-path segfault described above. Fixed for the new helpers; flagged for `__kml_fs_fdrw`.

## Verification

- New E2E test `TestE2EFsFsyncFtruncate` (`tests/fs_test.go`): write 11 bytes → `fsyncSync` → `ftruncateSync(fd, 5)` → file is 5 bytes (`"hello"`); grow to 8; default-`len` truncate to 0; bad-fd `fsyncSync`/`ftruncateSync` throw `e.code === 'EBADF'`. Passes on Windows 11 alongside the existing `TestE2EFsFdOps`.
- `examples/fs/fs.ts` extended: the fd-based I/O section now `fsyncSync`es and `ftruncateSync`es the open fd before closing. Compiles on Windows 11; the example's full run is a POSIX-lane CI recipe (the earlier `symlinkSync` line needs Developer Mode on Windows, an existing documented skip).
- `go build`, `go vet ./...` clean; `make status` regenerates `FILE-SYSTEM.md` from the new `file-system.json` row; `make conformance` run at delivery.
- Platform: implemented and verified on **Windows 11** (x86-64, MSYS2 UCRT); the POSIX path is the plain `fsync`/`ftruncate` syscalls.
