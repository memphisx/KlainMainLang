# ADR-01677: The checker types JavaScript parameters and constructor fields

- **Relations**: Implements TDD-00230, Supersedes the inference of ADR-00624 and ADR-00625
- **Date**: 2026-10-17

## Context

Under `-compat=js`, codegen ran its own inference (jsinfer) before class and function registration. It collected the argument types at every `new` and call site, and the types of a constructor's `this.x = …` stores. Phase 2 had already given the checker the same answers (checker/jsmode.go), so two places decided one type. TDD-00230 lists deleting jsinfer from codegen as open.

The two also disagreed. Codegen rejected a constructor that stores two types in one field ("assigned conflicting types") and a field it could not type, where JavaScript runs both.

## Decision

- **One answer.** An unannotated parameter's representation is the checker's call-site type (`jsCallSiteType`, through the representation context). A JavaScript constructor's fields are the checker's `JSConstructorFields`, and its parameters are typed from its `new` sites. A field the checker cannot type, because its stores disagree, is `any`.
- **Sites.** A plain function's sites include its `new` sites, since a plain function is also a constructor. A site that omits an argument makes the parameter `any`, since it is undefined there; a site with a spread does not count.
- **Deleted.** The two collection pre-passes, their maps, the constructor-field walk with its two rejections, and the prototype-constructor fold that rebuilt signatures from `new` sites. A prototype constructor is now recognised by a `new` of its name.

## Side effects discovered

None.

## Verification

- A side-by-side probe of vanilla classes, prototype constructors, polymorphic functions and linked nodes matches Node. A field stored with two types now runs, where it was a compile error.
- `TestE2EJSModeCtorFieldTypeConflict` replaces the rejection test. The `-compat=js`, class, dynamic and any tests pass.
