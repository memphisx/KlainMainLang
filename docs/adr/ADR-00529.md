# ADR-00529: JS-faithful string→number infinity spelling (`Number`/`parseFloat`)

- **Relations**: Extends ADR-00287, ADR-00291
- **Date**: 2026-08-31

## Context

`Number("inf")`, `Number("infinity")`, and `Number("INFINITY")` all returned
`Infinity`; real JS returns `NaN`. The only string infinity spelling JS's
`StringNumericLiteral` grammar accepts is the exact word `"Infinity"` (with an
optional leading sign and surrounding whitespace). The divergence came straight
from the C runtime: both `Number`'s `__kml_to_number` and `parseFloat` used
`strtod`, which additionally accepts `"inf"`, `"infinity"`, and every case
variant. Documented as a caveat on both rows.

## Investigation

`Number("1e999")` must still be `Infinity` (a genuine decimal overflow, which
JS does render `Infinity`), so the fix cannot blanket-reject every infinite
result — it has to distinguish the *word* form from a numeric overflow.
`strtod`'s only alphabetic-token results are the infinity and `nan` words;
`"nan"` renders `NaN` in JS either way, so only the infinity words needed
handling. After `strtod`, when the result is ±Infinity and the consumed token
begins (past whitespace and an optional sign) with a letter, that token is an
infinity word and must equal `"Infinity"` byte-for-byte or the input is not a
number.

## Decision

Add `@__kml_strtod_js` (`runtime_core.go`): call `strtod`, and when the result
is ±Infinity, scan the input past leading whitespace and an optional sign; if
the first significant character is a letter, require `strncmp(p, "Infinity", 8)
== 0`, otherwise rewind `*endptr` to the start so the caller treats it as "no
conversion" — exactly the path each caller already uses for junk. A numeric
overflow (`1e999`) has a digit first character and is left untouched. Route both
`__kml_to_number` and `parseFloat` through it instead of bare `strtod`.

Because the mechanism is an `endptr` rewind, each caller's own tail rule keeps
working: `Number("Infinityx")` → `NaN` (whole-string parse) while
`parseFloat("Infinityx")` → `Infinity` (numeric prefix), matching real JS.

## Implementation notes

`runtime_core.go` (the new helper + `ensureToNumber` rewire),
`emit_call_number.go` (`parseFloat` rewire), `emitter.go` (`usedStrtodJS`
singleton flag). No change to the callers' surrounding logic.

## Side effects discovered

`parseFloat` still parses C hex-float syntax (`"0x10"` → 16, `"0x1.8p3"` → 12)
where real JS reads only the leading `0` — a separate `strtod` divergence, left
as a narrowed caveat on the `parseFloat` row. `Number("0x10")` → 16 is correct
(JS ToNumber does read hex).

## Verification

`TestE2ENumberParseFloatInfinitySpelling` (new): every `Number`/`parseFloat`
infinity spelling, sign, surrounding-whitespace, overflow, and prefix-vs-whole
case cross-checked against real Node. Existing conversion/parse tests pass.
Verified on Mac (Apple Silicon).
