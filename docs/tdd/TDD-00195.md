# TDD-00195: http req/res bodies as Node Readable/Writable

- **Status**: Partially Implemented
- **Date**: 2026-09-10

Stage 1 (req as a Node `Readable`) shipped ([ADR-00824](../adr/ADR-00824.md)), and
Stage 2's **flush-model core** — the response flush driven by `res.end()` rather
than by handler return, so a fire-and-forget `(req,res)` handler works
([ADR-00825](../adr/ADR-00825.md)). The remaining Stage 2 part is a fully
incremental `res` `Writable`: `res.write` streaming to the socket mid-handler
with real backpressure/`'drain'` and `req.pipe(res)` (the response is still
buffered — one flush at `res.end`).

## Context

BACKLOG §1 "real async streaming": an http server request/response body is not
yet a Node stream. Today (see the survey below) a server `req` exposes `.body`
(buffered string), `.bodyBytes()`, and `.stream()` (a *WHATWG* `ReadableStream`,
incremental + backpressured, TDD-00097 Stage 5b), but has no `.on('data')`,
`.pipe()`, or async iteration — so the idiomatic Node forms
(`for await (const chunk of req)`, `req.on('data', …)`, `req.pipe(dest)`) don't
work. A server `res` is a buffered value object: `res.write`/`res.end` string-
concatenate into a field flushed *after the handler returns*; there is no
incremental socket write, no backpressure/`'drain'`, no `res.on`/`res.pipe`, so
`req.pipe(res)` is impossible. TDD-00131 named the res-Writable contract as open
scope and deliberately declined incremental backpressure as disproportionate,
pointing large responses at the `ReadableStream`-typed return `body` instead
(ADR-00300).

The Node `Readable`/`Writable` machinery already exists in full (TDD-00132):
`wrapWebReadable` (a Node `Readable` over a WHATWG readable), fd-backed
`createWriteStream` Node `Writable`s, and the `.on`/`.pipe`/for-await dispatch on
`NodeReadableType`/`NodeWritableType`. The gap is *connecting the http bodies to
that machinery*.

## Design

### Stage 1 — `req` as a Node `Readable` (shipped)

`req.stream()` already yields a WHATWG readable; `wrapWebReadable` turns it into a
full Node `Readable` with `.on('data'/'end')`, `for await`, and `.pipe` for free
(all already implemented on `NodeReadableType`). The whole stage is: expose that
Node `Readable`, once, from the Node-`Readable`-shaped operations on a server
`req`.

Single-consumption is already enforced by the reqbody runtime (`.body`/
`.bodyBytes()` after streaming throw the WHATWG "disturbed" TypeError, ADR-00362),
so the same guarantee must hold across the Node forms: `req.on('data')` then
`req.on('end')` must attach to the **same** underlying readable, not two
(a second `req.stream()` would throw disturbed). So the wrapped Node `Readable`
is created lazily on the first Node-`Readable` access and **cached on the
request** (a dedicated request-struct field, null until first use); every
subsequent `.on`/`.pipe`/for-await reuses it.

Dispatch, all forwarding to `reqAsNodeReadable(req)`:
- `req.on(evt, cb)` / `req.once(...)` → the `NodeReadableType` `.on` handler.
- `req.pipe(dest[, opts])` → the Node `.pipe` handler.
- `for await (const chunk of req)` → the async-iterator lowering recognizes an
  `IsRequest` iterable and iterates the wrapped readable.

Chunks are `Uint8Array` (the reqbody stream's element type), matching Node's
default (a `Buffer` there; this compiler has no `Buffer`, so `Uint8Array`).

### Stage 2 — `res` as a Node `Writable` (designed, not built)

The obstacle is structural, not mechanical: this compiler's http handler
**returns** its response (status/headers/body object), whereas a Node `Writable`
`res` is written to *imperatively* mid-handler, with the fd owned early. The
existing incremental writer — `runtime_http_stream.go`'s `%kml.hws`
(`__kml_hws_start`/`_step`/`_on_read`, chunked framing + keep-alive re-arm) —
already owns the connection fd and frames chunks, but it is driven by a
*returned* `ReadableStream` body, not by `res.write`.

Proposed approach: expose `res` as a Node `Writable` whose sink drives the same
`%kml.hws` chunked writer, started on the first `res.write` (emit status+headers,
switch the connection to chunked transfer-encoding), each `write` framing one
chunk to the fd, `res.end` writing the terminal chunk and releasing the fd.
Backpressure: `res.write` returns `false` when the socket write would block,
buffering the chunk and emitting `'drain'` when the fd drains (the reactor's
writable-fd scan is the signal). This must reconcile with the return-`{body}`
flush model: a handler that has called `res.write` has taken the fd, so its
return value must not also flush — the dispatcher needs to detect "res already
streaming" and skip the post-return flush. `req.pipe(res)` then reduces to
`Readable.pipe(Writable)` over machinery that exists on both ends.

This is a large change to the fd-ownership/flush model TDD-00131 deferred; it is
scoped as its own stage so Stage 1 (which needs none of it) ships independently.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| WHATWG readable over the request body | Done | `req.stream()` / `runtime_http_reqbody.go` (TDD-00097 5b) |
| Node `Readable` over a WHATWG readable | Done | `wrapWebReadable` (TDD-00132) |
| Node `.on`/`.pipe`/for-await dispatch | Done | `NodeReadableType` (TDD-00132) |
| A request-struct field to cache the Node `Readable` | Stage 1 | |
| Incremental chunked fd writer | Done (returned-body only) | `%kml.hws` `runtime_http_stream.go` — needs an imperative `res.write` driver |
| Socket-write backpressure + `'drain'` | Missing | Stage 2 |
| Skip post-return flush when `res` is streaming | Missing | Stage 2 |

## Open questions

1. **Stage 2 fd-ownership reconciliation.** The cleanest handshake between a
   handler that returns `{body}` and one that drives `res.write` — a per-response
   "streaming taken" flag the dispatcher consults before flushing, or a distinct
   Writable-`res` type. Deferred with Stage 2.
2. **`req` chunk element type ergonomics.** `Uint8Array` chunks (no `Buffer`);
   whether a `req.setEncoding('utf8')` should flip the wrapped readable to string
   chunks (as Node does) or stay bytes. Stage 1 keeps bytes.
