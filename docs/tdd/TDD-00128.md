# TDD-00128: `@pure` — compile-time enforcement of function purity

- **Status**: Implemented
- **Date**: 2026-08-27
- **Notes**: A JSDoc `@pure` tag enforced by a front-end pass (zero runtime/codegen cost, like `@erased`): inside a `@pure` function, reject parameter mutation, captured/global mutation, I/O, nondeterminism (`Date.now`/`random`), and calls to non-`@pure` functions (contagious). Chosen over the original deep-copy-params idea, which addresses only argument mutation, can't safely free inputs the return aliases, and is ill-defined on cycles/DAGs. Doubles as a static purity linter for FP code that only runs under Node. Sibling to [TDD-00126](TDD-00126.md)'s enforcement flag; independent of [TDD-00127](TDD-00127.md). — Shipped as Option A (enforce-only, no codegen change) in [ADR-00516](../adr/ADR-00516.md): all five violation classes on function/arrow/function-expression forms incl. capturing closures, with documented conservative gaps (local aliasing untracked, higher-order calls allowed, curated builtin tables). Deferred, still open below: the whole-file/project Node-linter mode, Option B (deep-`readonly` parameter types), and the memoize/CSE optimization the sound guarantee now enables.

## Context

Functional-programming code leans on *referential transparency*: a function's
result depends only on its arguments, and calling it produces no observable side
effect. JavaScript (like Java) actively undermines this — objects and arrays
pass by shared reference, so a callee can mutate a caller's data, and nothing
stops a function from mutating captured state, doing I/O, or reading a
nondeterministic clock. There is no way to *declare* "this function is pure" and
have the tool hold it to that.

An initial idea was to give parameters value semantics by **deep-copying**
objects at the call site and freeing them on return (keeping only the returned
value), gated by a JSDoc tag. That mechanism is wrong for the goal:

- **It addresses the smallest slice of purity at the highest runtime cost.**
  Copying arguments does nothing about the other side-effect channels —
  mutation of captured/global state, I/O (`console`/`fs`/`fetch`), or
  nondeterminism (`Date.now`/`Math.random`). A "pure" function that deep-copies
  its params can still do all of those.
- **"Free everything but the return" is unsound.** Returned values almost always
  *share substructure* with the inputs (`return {...user, active:true}` aliases
  `user`'s nested objects; `return arr.filter(...)` holds the *same* element
  objects). Freeing the inputs' deep structure on return leaves the result
  dangling. Proving the return aliases no input is undecidable in general.
- **Deep copy is ill-defined** for cyclic references (infinite copy) and shared
  DAGs (copying silently destroys sharing and can blow up memory).

The FP-idiomatic guarantee comes not from *hiding* mutation behind a copy but
from *forbidding* it: make an impure operation inside a `@pure` function a
**compile-time error**. This is a front-end-only check with zero runtime and
zero codegen cost — the same layer and opt-in shape as the modifier-tag
enforcement flag scoped in [TDD-00126](TDD-00126.md), and the same "front-end
tag, no runtime footprint" precedent as `@erased` generics
([TDD-00010](TDD-00010.md) V2).

Two payoffs justify scoping it now:

1. **Enforced FP discipline** for code authored in this language.
2. **A static purity checker for existing Node.js FP code.** Because the
   compiler already parses real TS/JS with JSDoc, `@pure` (or a whole-file/whole
   -project mode) can flag accidental impurity — a stray `arr.push` on an
   argument, a captured-variable mutation, a `console.log` buried in a
   "transformer" — in codebases that only ever run under Node. The compiler
   becomes a lint pass those authors otherwise lack.

This is independent of [TDD-00127](TDD-00127.md) (boxed arrays); neither blocks
the other.

## Design

### What `@pure` means

A function tagged `@pure` (in a JSDoc block, e.g. `/** @pure */`) asserts
referential transparency. The front end verifies, and rejects with a diagnostic
naming the specific violation, any of the following **inside the function body**:

1. **Parameter mutation** — reassigning a parameter (`x = …`), or writing a
   field/element/nested location reachable from a parameter (`x.f = …`,
   `x[i] = …`, `x.a.b = …`), including via mutating methods on it
   (`x.push`/`x.splice`/`x.sort`/`Object.assign(x, …)`/`x.foo = …`).
2. **Free-variable / global mutation** — assigning to any binding not declared
   inside the function (a captured closure variable, a module-level `let`, a
   global). Reading them is allowed *only* if they are provably immutable
   (`const` bound to a primitive or a deeply-frozen value); see Open questions
   on how far to push this.
3. **I/O and other impure builtins** — calls to a denylist of known-impure
   builtins: `console.*`, `fs.*`, `fetch`/network, `process.*` side effects,
   timers (`setTimeout`/`setInterval`), DOM/storage, etc.
4. **Nondeterminism** — `Date.now()`, `new Date()` (argless), `Math.random()`,
   and friends.
5. **Calling a non-pure function** — purity is contagious. A `@pure` function
   may only call functions that are themselves `@pure` (or a curated allowlist
   of builtins statically known to be pure: `Math.max`, `Array.prototype.map`
   with a pure callback, string methods that return new strings, etc.).

Local mutation is fine: a `@pure` function may freely declare and mutate its own
`let`s and locally-constructed objects/arrays — purity constrains *observable*
effects, not internal implementation. `return {...user, active:true}` is pure;
it constructs a fresh object and mutates nothing the caller can see.

### Mechanism: enforce, don't copy

No runtime behavior changes. Arguments still pass exactly as they do today
(shared references); codegen is untouched. The tag adds a **front-end analysis
pass** over the function's AST that walks for the five violation classes above
and emits compile errors. Zero cost in the emitted binary.

This is strictly stronger *and* cheaper than copy-on-call: it also catches
captured-state mutation, I/O, and nondeterminism (which copying cannot), and it
costs nothing at runtime.

### Options considered

- **Option A — enforce-only (recommended).** Exactly the five checks above; no
  type-system change, no runtime change. Smallest, shippable incrementally
  (each violation class can land independently). The purity guarantee is as
  sound as the analysis; unprovable cases (see below) are *rejected*
  conservatively, not silently allowed.
- **Option B — enforce + deep-`readonly` parameter types.** In addition to A,
  treat every parameter of a `@pure` function as deeply `readonly`, integrating
  with any future `readonly`/`ReadonlyArray` support so the mutation errors fall
  out of the type checker uniformly rather than a bespoke pass. More principled,
  but couples `@pure` to a `readonly` subsystem that does not fully exist yet.
- **Option C — copy-on-call fallback.** Keep A as the primary guarantee, but for
  a call the analysis *cannot* prove safe (e.g. passing an object to a
  non-`@pure` third-party function while wanting to protect the caller), fall
  back to deep-copying that argument. Narrow, opt-in, and inherits all the deep
  -copy hazards (cycles, aliasing, cost); scoped here only to record that it was
  considered and deprioritized. Not part of the initial build.

Recommended path: **A now**, evolving toward **B** if/when a `readonly`
subsystem lands. C only if a concrete need appears.

### Purity as an optimization enabler (secondary payoff)

Once purity is *enforced* (not merely asserted), the compiler may soundly:
memoize `@pure` calls on identical arguments, common-subexpression-eliminate
repeated pure calls, reorder them, or hoist/parallelize them. These are only
valid because enforcement rules out nondeterminism and hidden state — which is
exactly what copy-on-call fails to guarantee. Out of scope for the first
delivery, but the reason to make the guarantee *sound* rather than best-effort.

### Node-oriented checker mode

Beyond per-function tags, expose a mode that treats a file or project as an
FP-lint target: report every function that *could* be `@pure` but isn't, or
every impurity in functions the author intended to be pure. This turns the
compiler into a static purity linter for code that only runs under Node,
independent of whether that code compiles to a native binary. Delivery detail
(a CLI flag) deferred; noted so the design keeps the whole-file analysis
reusable, not welded to a single tagged function.

### Diagnostics

Each rejection names the violation class, the offending location, and the reason
(`'result' is a parameter of a @pure function and cannot be mutated`;
`console.log is a side effect; f is declared @pure`; `f is @pure but calls g,
which is not @pure`). Per the standing rule, no doc/ADR/TDD paths in the
user-facing message — the explanation is inline.

### Verification

- E2E tests: a `@pure` function that (a) mutates a param field, (b) mutates a
  captured variable, (c) calls `console.log`, (d) calls `Math.random`, (e) calls
  a non-`@pure` function — each must fail compilation with the right diagnostic.
- Positive tests: `@pure` functions that reassign locals, build & return fresh
  objects (`{...x}`), map/filter with pure callbacks, and call other `@pure`
  functions — must compile and run unchanged (byte-identical codegen to the
  untagged version, since the tag is enforcement-only).
- Contagion: a `@pure` function calling another `@pure` function that is
  *itself* impure must surface the inner violation.
- Example under `examples/` demonstrating a small pure pipeline plus a caught
  violation (in a comment / expected-fail harness).
- `make test-par`, `make examples`, then `make conformance` once at the end.

## Open questions

- **Free-variable *reads*.** A pure function reading a module-level `const`
  bound to an immutable value is fine; reading one bound to a mutable object is
  a determinism hole (someone else can mutate it between calls). How strict:
  forbid all free reads except `const`-primitives, or allow reads of
  deeply-frozen values, or allow reads and only forbid writes (weaker but far
  more usable on real Node code)? Likely a strictness level, not a single
  answer.
- **Granularity of the guarantee.** Is `@pure` all-or-nothing, or is there a
  weaker `@no-mutate-params` (only violation class 1) for authors who want the
  argument-safety win without swearing off `console.log`? The Node-linter use
  case may want the dial.
- **Allowlist maintenance.** The pure-builtin allowlist (which `Array`/`String`
  /`Math`/`Object` methods count as pure, and under what argument conditions —
  `.map` is pure only if its callback is) is real surface area that can drift as
  builtins are added. How to keep it honest — a test that every builtin is
  classified?
- **Higher-order purity.** `arr.map(fn)` inside a `@pure` function is pure only
  if `fn` is pure. Does the checker require the callback to be `@pure`, infer
  purity of an inline arrow by analysing it in place, or both?
- **Interaction with [TDD-00126](TDD-00126.md).** If both ship, `@pure` and the
  modifier-enforcement flag share an enforcement-pass framework; decide whether
  they are one pass with several rule sets or independent passes, and whether
  `@pure` is on-by-tag always or also gated behind the same opt-in flag.
- **Relationship to the memory model.** Enforcement-only `@pure` needs no
  allocation change. If Option C (copy fallback) is ever revisited, it reopens
  every deep-copy hazard (cycles, return aliasing, per-mode free) — keep it out
  unless a concrete need forces it.
