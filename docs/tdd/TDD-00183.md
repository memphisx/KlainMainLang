# TDD-00183: Windows IOCP reactor (completion-model I/O)

- **Status**: In Progress — design complete (this revision); Stage 1 in implementation. Supersedes [TDD-00182](TDD-00182.md) Stages 2–6 (see Context).
- **Date**: 2026-09-07 (scoped) / 2026-09-11 (full design)

## Context

[TDD-00180](TDD-00180.md) identified two ways out of the Windows CRT-fd-table debt, and [TDD-00182](TDD-00182.md) designed **Option A** — an owned handle table under a readiness-shaped wait (`WaitForMultipleObjectsEx` + `WSAEventSelect`). Option A's Stage 1 (the owned, kind-tagged fd descriptor table + `fstat` kind dispatch) shipped as [ADR-00864](../adr/ADR-00864.md) and is the foundation this document builds on.

This revision expands the originally-sketched **Option B** into the implementable design and **supersedes TDD-00182 Stages 2–6**. The reason for skipping A's readiness wait entirely: it is the emulation libuv itself outgrew (the 63-handle `MAXIMUM_WAIT_OBJECTS` wall, helper-thread fan-out, `WSAEventSelect` edge-cases), and every line of it would be discarded when B lands. A's Stage 1 — the part B reuses — is done; building A's Stages 2–6 first would now be throwaway engineering, which is exactly what the standing faithfulness rule forbids. The reactor goes straight to the completion model Windows is built around and libuv uses: overlapped I/O on one I/O completion port, drained by a single `GetQueuedCompletionStatusEx` wait.

The symptoms this must fix are TDD-00180 §1 (all of them, minus the already-fixed `fstat`): blocking `process.stdin`/child-pipe reads, the ~10 ms idle poll slice (50 ms with a console-ctrl handler), the 384-socket cap, `dup2`-of-socket aliasing, synchronous 4 KB `CreatePipe` child stdio, console input readable-on-any-record + blocking + code-page decoding (also §2 non-ASCII input), and the 15.6 ms timer tick.

## Design

### The central decision: the `select()` contract over a completion engine

The emitted IR is written against a POSIX readiness world: int fds, `read`/`write`/`close`/`fcntl`, and a reactor that calls `select()` over a 1024-bit fd bitmap. Twenty-nine Go emitter files plus `tls.c`/`http2.c` speak this contract; on Linux and macOS it maps to the real syscalls. The original scoping left open whether B should (i) keep that contract as a shim over IOCP or (ii) introduce a completion-oriented internal API and migrate the IR callers.

**Decision: (i), with the engine underneath built so the projection is thin and copy-free.** The rationale, evaluated against both faithfulness and no-throwaway:

- **Faithfulness is defined by observable behaviour plus the kernel-facing model.** Nothing about the internal reactor API is JS-observable. What libuv actually does on Windows — the thing "faithful" means here — is overlapped operations on an IOCP drained by one `GetQueuedCompletionStatusEx`. That is exactly what this design's kernel-facing side is. The `select()` bitmap is retained only as the *projection* the IR reads results through.
- **(ii) is not a Windows change — it is a cross-platform reactor-API redesign.** The `select()` shape is the project's portable internal contract; a completion-shaped replacement would have to be re-implemented over epoll/kqueue on the primary platforms (that is, rewrite libuv's Unix half too) and would churn every emitter that touches the loop, for zero observable gain. If the project ever redesigns the internal reactor API, that is its own TDD; the engine built here (port, op records, per-handle state) is precisely what such an API would sit on — only the ~150-line bitmap-projection function would be replaced. Nothing is throwaway either way.
- **The projection costs no copy and loses no events**, because of how reads are armed (next section): the engine never takes ownership of stream bytes; it only learns *that* bytes (or EOF, or a connection) have arrived. The classic objection to a readiness veneer over IOCP — proactively-posted reads forcing double buffering and edge-case divergence — does not apply.

### Read-interest: libuv's zero-read mode, end to end

For every stream handle the shim owns, read-interest is expressed as a **zero-byte overlapped read** posted to the port — the exact mechanism libuv ships as its zero-read mode (`uv_zero_` in its Windows tcp/pipe code), used precisely when it needs "tell me when data is there" semantics inside its IOCP loop:

| Handle class | Armed with | Completion means | Data then flows via |
|---|---|---|---|
| TCP stream socket | `WSARecv` with a 0-length buffer | data available, EOF (FIN), or error (RST) | the existing non-blocking `recv` in `read()` |
| UDP socket | `WSARecvFrom`, 0-length buffer, `MSG_PEEK` | a datagram is queued (peek: nothing truncated/consumed) | the existing `recvfrom` |
| TCP listener | `AcceptEx` (extension pointer via `SIO_GET_EXTENSION_FUNCTION_POINTER`) | a connection is accepted into a pre-created socket | `accept()` pops the completed socket, `SO_UPDATE_ACCEPT_CONTEXT`, re-posts |
| Overlapped pipe (ours) | `ReadFile` with a 0-length buffer | data available or `ERROR_BROKEN_PIPE` (EOF) | `PeekNamedPipe` + bounded `ReadFile` in `read()` |
| Inherited synchronous pipe (e.g. our own piped-in fd 0) | a per-fd reader thread blocked in a 0-byte `ReadFile`, posting a packet on return (libuv's non-overlapped-pipe thread, `CancelSynchronousIo` on close) | same | same |
| Console input | a dedicated reader thread: `ReadConsoleW` in cooked mode (line editing and UTF-16 preserved), `ReadConsoleInputW` filtering key-down records in raw mode; decoded UTF-16→UTF-8 into a queue, packet posted per chunk | decoded input is buffered | `read()` drains the thread's UTF-8 queue |
| Regular file | never armed | always readable (POSIX `select` semantics) | synchronous I/O, unchanged |
| Foreign socket (libcurl's) | AFD poll (below) | readiness | libcurl's own non-blocking I/O |

Zero reads consume nothing, so they compose with any consumer of the same stream — including OpenSSL's socket BIO reading the raw `SOCKET` behind a TLS fd (`__kml_win_fd_socket`): if OpenSSL drains the data first, the reported readiness is spurious and the next `read()`/`SSL_read` sees WOULDBLOCK, which every caller already handles (POSIX `select` permits spurious readiness). Level-trigger semantics fall out naturally: readiness is consumed when reported, and re-arming at the next `select()` entry completes immediately if data is still queued.

Determinism note: the data → EOF ordering that the current Winsock-select reactor races on (the known `TestE2ENetSocketCloseAndReadyEvents` flake) becomes deterministic — a zero-read posted while data is queued completes as "readable" and the subsequent `recv` returns the bytes; FIN is only observable on a later arm. The flake test passing consistently is an acceptance signal for Stage 2.

### Write-interest: AFD poll, the completion-model readiness primitive

Write-interest has no zero-read analogue (a 0-byte send completes immediately regardless of buffer state), and its only consumers are streams whose bytes the shim does *not* own at wait time: libcurl's sockets (`curl_multi_fdset` write set) and `poll(POLLOUT)` from `tls.c`/`http2.c` after a WANT_WRITE. The completion model's primitive for this is **`IOCTL_AFD_POLL`** on the socket's base handle (`SIO_BASE_HANDLE`) — an overlapped IOCTL that completes on the port when the socket becomes writable/readable/broken. This is not a readiness *emulation* bolted beside the port: it is how libuv itself implements externally-owned-socket watching on Windows (its poll.c "fast mode"), and it is drained by the same single `GetQueuedCompletionStatusEx` as everything else. Used for:

- foreign (libcurl) sockets, read- and write-interest both;
- write-interest on owned sockets (`POLLOUT` waits; the main loop's write set);
- `except`-set membership (connect-failure reporting), completing the current `select()`'s "excepted ⇒ also writable" contract.

Owned-socket sends keep the non-blocking `WSASend` fast path exactly as today (`EAGAIN` on a full buffer, caller retries after writability) — no copies, no behavioural shift.

Non-blocking `connect()` (the `EINPROGRESS` path — currently unexercised by the IR, which connects blocking, but part of the POSIX surface and needed for future async `net.connect`) moves to `ConnectEx` (bind-first, `SO_UPDATE_CONNECT_CONTEXT` on success), its completion recorded per-fd so writability + `SO_ERROR` report it, matching the POSIX shape.

### Writes on pipes: overlapped, queued when non-blocking

Owned pipes become overlapped named-pipe pairs, so `_write` leaves the picture:

- **Blocking pipe fd**: overlapped `WriteFile` + inline wait on a per-op event — same observable semantics as today, no CRT.
- **Non-blocking pipe fd** (the loop's ends): a FIFO of heap-copied overlapped writes, head posted, next posted on completion. `write()` accepts the bytes and returns immediately — the user-space write queue Node itself keeps for a `Writable`. This is what un-deadlocks the ">4 KB each way" child-stdio scenario and unblocks parent→child-stdin streaming. (The parent's child-stdin write end is marked non-blocking at pipe creation; the out/err read ends already are, via the IR's `fcntl`.)

The child-facing ends of stdio pipes must be synchronous (an arbitrary child's CRT does plain `ReadFile`/`WriteFile` with no OVERLAPPED, which is undefined on an overlapped handle). Since `pipe()` cannot know the direction, child stdio moves to a direction-aware pair creator — `__kml_win_stdio_pipe(dir, fds)`, libuv's `uv__create_stdio_pipe_pair` shape: a uniquely-named `CreateNamedPipeW(FILE_FLAG_OVERLAPPED | FILE_FLAG_FIRST_PIPE_INSTANCE)` server end for the parent, a synchronous `CreateFileW` client end for the child. The `runtime_childprocess.go` Windows branch calls it in place of its three `pipe()` calls; plain `pipe()` (worker/chan/IPC pairs — both ends loop-side, in-process) creates both ends overlapped.

### The wait: one alertable `GetQueuedCompletionStatusEx`

`select()` becomes: arm interests → drain the port (timeout from the caller's `timeval`, alertable) → project completions/posted packets onto the result bitmaps → return ready count, or 0 on timeout, or `EINTR`. All wakeup sources unify as posted packets (`PostQueuedCompletionStatus`):

- **Signals**: the console-ctrl handler posts a packet (in addition to raising the existing flags), so a blocked wait ends immediately and `__kml_win_sig_deliver` turns it into `EINTR` — the 50 ms handler-installed slice dies. The wait stays alertable, preserving any APC-based paths.
- **Reader threads** (console, sync pipes) post per-chunk packets.
- **`fs.watch` and the async-I/O thread pool** keep their loopback-socketpair wakeups *unchanged* — those are owned sockets, so their read ends are zero-read armed like any other and wake the port with no code changes. Folding them into native packets is an optional later cleanup, not correctness work ([ADR-00757](../adr/ADR-00757.md)'s wakeup generalizes to the port exactly as it anticipated).
- **Timers** (Stage 4): a high-resolution waitable timer posting a packet.

`poll()` continues to ride `select()` unchanged.

### Op records, lifetimes, and the descriptor table

Every pending overlapped operation is a heap **op record** — `{ OVERLAPPED, fd, generation, op-kind, per-kind payload }` — so a completion dequeued after the fd was closed and the slot reused is recognized (generation mismatch) and discarded, and a closed handle's in-flight ops (`CancelIoEx`ed at close) can drain safely as orphans. Socket close with a pending queued write flushes first (shutdown-after-drain, libuv's teardown order). The `kfd_slot` from ADR-00864 is extended in place (per-fd readiness bits, pending-op pointers, reader-thread handle, write queue) — no new parallel arrays.

**Stage 3** converts the slot to a pointer to a refcounted **description** `{ handle, kind, refs, flags, overlapped state }`: `dup2` shares the description (close decrements; the handle closes once — the aliasing fix), and the fixed fd-range partition dissolves. CRT fds remain only for regular files (`[0, 512)`); every owned kind (socket, pipe, console) allocates from a unified `[512, 1024)` pool — the 384-socket cap becomes a shared 512-slot owned pool, and the remaining ceiling is the IR's own 1024-bit `fd_set` width (widening that is IR-side work, out of scope, recorded as the new documented limit). Slots 0–2 can hold descriptions (a `dup2(sock, 0)` shadows the CRT std fd; all I/O already dispatches through the shim).

### Timer resolution (Stage 4)

Timer deadlines move from `GetTickCount64` (15.6 ms tick) to QPC; the wait's timeout is backed by a `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` waitable timer (registered-wait callback posting a timer packet) when the deadline is nearer than the tick. `timeBeginPeriod(1)` is deliberately **not** used: it is process-global with a power cost, and the waitable timer localizes the precision to exactly the waits that need it.

### What keeps working with no changes

- **libcurl**: the `curl_multi_fdset` shadow bridge is untouched; foreign fds get AFD-poll interests instead of Winsock-select membership. The generation guard covers curl closing sockets between iterations.
- **TLS/HTTP2 helpers**: `tls.c`/`http2.c` call `poll()`/`read()`/`write()` by POSIX name — they ride the new engine unmodified.
- **Fibers, `curl_multi_fdset` contract, WSA→errno mapping, `KML_IO_TRACE`**: unchanged (trace gains port-drain and arm/complete lines — a reactor that hangs is otherwise opaque).
- **Console resize watcher** ([ADR-00749](../adr/ADR-00749.md)) and ConPTY/`setRawMode` harness: the console reader thread must coexist — in raw mode it forwards `WINDOW_BUFFER_SIZE_EVENT` records it necessarily consumes; the cooked path's `ReadConsoleW` interaction is verified under the ConPTY harness in Stage 1.

## Staging

Each stage independently shippable and verified on the Windows box + CI lane; the suites named in Verification below run per stage.

1. **The port + the non-socket world.** Thread-local port creation, op records/generations, posted-packet wakeups (signals included), the child-stdin overlapped write-queued pair (`__kml_win_pipe_pw`) + the childprocess-emitter switch, a buffering reader thread for a piped `process.stdin`, the console reader thread (cooked `ReadConsoleW`→UTF-8), queued non-blocking pipe writes, `select()` draining the port. **Scoping actually shipped** ([ADR-00865](../adr/ADR-00865.md)): `pipe()` stays anonymous/polled (converting in-process worker/channel pipe pairs to named overlapped ends regressed cross-thread IPC — reverted); only fd 0 and child stdin get the completion treatment, so an anonymous pipe read end keeps the 10 ms poll slice as its fallback and zero-read arming (for overlapped read ends) defers to Stage 2. **Sockets stay on the Winsock-select probe** — an explicitly temporary migration bridge (the slice survives only when a socket or an anonymous pipe is watched; a pipe(reader)/console/stdin-only program gets the true single blocking wait). Fixes: blocking stdin/child-pipe reads, the child-stdio streaming deadlock, console readable-on-any-record + blocking + non-ASCII input, the 50 ms signal slice, and the idle spin for the no-socket/no-pollable-pipe case.
2. **Sockets to completion.** Zero-read `WSARecv`/`WSARecvFrom(MSG_PEEK)` arming, `AcceptEx` listeners, `ConnectEx` non-blocking connect, AFD-poll write/foreign/except interests; the Winsock-select probe is deleted — the wait is one `GetQueuedCompletionStatusEx` always. Fixes: the idle spin entirely; the data/EOF ordering race (flake becomes deterministic — acceptance criterion, the test is not loosened).
3. **Refcounted descriptions.** `dup2` aliasing fixed, ranges dissolved, 384-socket cap replaced by the unified owned pool (ceiling: the IR's 1024-bit bitmap, documented).
4. **Timer resolution + remnants.** QPC deadlines, high-res waitable timer packets, last `Sleep`-slice remnants removed, `usleep` precision.

## Resolved questions (from the original scoping)

1. **Shim vs native completion API** → the projection (i), with the engine completion-model underneath; rationale in Design. Revisit only if the cross-platform internal reactor API is ever redesigned (its own TDD).
2. **TLS over IOCP** → no TLS-path changes: OpenSSL keeps the raw socket byte stream; zero-reads compose (consume nothing), `POLLOUT` waits ride AFD poll.
3. **Retire or retain A's wait** → retired before being built; the port subsumes every source (files never wait; console/sync-pipes wait on their reader threads' packets).
4. **Sequencing** → immediately, on the Windows box (the ADR-00864 correction to TDD-00182's implementation-host note: this work genuinely needs the native box and is done while on it).
