# ADR-00869: `never` return type for always-throwing functions

- **Relations**: `Relates to ADR-00866`
- **Date**: 2026-09-11

## Context

`x() & y()` where `x`/`y` always throw emitted `trunc i64  to i32` — an empty IR
operand clang rejects with "expected value token" (Test262
`bitwise-and/S11.10.1_A2.4_T2.js`, `order-of-evaluation.js`). An unannotated
function whose body only throws was typed `void`, so using its call result as an
operand produced a value with no register.

TypeScript types such a function `never` (the bottom type, assignable to every
operand position), so `alwaysThrows() & 1` type-checks and at runtime throws
before the `&` — the faithful behavior. The compiler already handles a `never`
*value* correctly: `coerce` turns it into a dead zero of the target type
(`emit_exprs_coerce.go`), keeping the IR well-typed. Only the *inference* was
missing.

## Decision

Infer `never` (not `void`) for an unannotated function/closure whose body always
diverges:

- `buildFunctionSig` (function declarations) and the `FunctionExpression` /
  block-body `ArrowFunction` arms of `inferExprType`: when there is no reachable
  `return` **and** `blockAlwaysDiverges(body)`, the return type is `TypeNever`
  instead of the `TypeVoid` default.
- `blockAlwaysDiverges` / `stmtAlwaysDiverges` (`emit_func.go`) are conservative:
  a `throw`, a block containing a diverging statement, or an `if` whose both arms
  diverge. Infinite loops (`while(true)` with no break) also yield `never` in TS
  but are **not** detected here — erring toward `void` when unsure is safe (a
  false positive would emit an `unreachable` the body actually reaches).

`TypeNever`'s IR is `i64`, so such a function emits `define i64 @f { …throw…;
unreachable }` (the `unreachable` fallthrough the non-void path already emits) and
its call is `call i64 @f`; the never result coerces to a dead zero at any operand
site. Faithful in both `-compat` lanes — pure TS inference, no untyped-JS
dependency.

## Side effects discovered

- **`throw` of a primitive (non-Error) value is wrapped as an Error**: `throw "x"`
  is caught as `Error: x` (`typeof e === "object"`), where Node/TS give the raw
  string `"x"` (`typeof e === "string"`, `e === "x"`). So `S11.10.1_A2.4_T2.js`
  now *compiles and runs* (the invalid IR is gone) but still fails its assertion
  on `e === "x"`. Separate thrown-value-representation gap (catch binds the wrong
  kind), recorded in BACKLOG; a larger change than this one and cleanly separable.

## Verification

- E2E `tests/func_test.go`: `TestE2ENeverReturningFunctionInBitwiseOperand` and
  `…FunctionExpressionInBitwiseOperand` — an always-throwing function/expression
  used as a bitwise operand compiles, the call throws, and the operator never
  produces a value (`caught` / `reached:false`). Runtime matches `node` (the
  expression throws rather than yielding a number).
- `bitwise-and/S11.10.1_A2.4_T2.js`: CLANG_ERROR → compiles+runs (now blocked
  only by the primitive-throw gap above); `order-of-evaluation.js`: past the
  bitwise stage (now a pre-existing strict var-retype rejection, unrelated).
- Platform: Apple-Silicon Mac.
