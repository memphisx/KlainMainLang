# TDD-00193: Docker builder images — install-free builds + reusable CI lanes

- **Status**: Not Started
- **Date**: 2026-09-09
- **Notes**: Publish toolchain images (`klainmain` + clang + optional libs, multi-arch amd64/arm64, plus an `sfos-aarch64` variant) so a user builds a native binary or a microservice image with `docker run` / a multi-stage `FROM` and no local install; the same images back new CI test lanes so "tested" and "shipped-to-users" are one artifact. Hosted on GHCR (GitHub Container Registry), versioned by release tag. macOS stays a local install (no Linux-hosted macOS containers); Windows out of scope

## Context

Two needs converge on the same piece of infrastructure:

1. **A Sailfish CI lane.** [TDD-00146](TDD-00146.md)'s `-webview=sailfish` and the
   ~122 `targetGOOS`/`targetGOARCH` codegen sites now have zero automated
   coverage — every Sailfish claim is verified by hand. The reproducible
   `-devel` sysroot ([ADR-00812](../adr/ADR-00812.md)/`docker/Dockerfile.sfos-sysroot`)
   is a full Sailfish userland (glibc 2.41, aarch64, Qt5/webview `-devel`), and CI
   already runs a **native arm64 runner** (`ubuntu-24.04-arm`). A job pinned to
   `container:` that image runs the suite *inside a real Sailfish userland*,
   natively — binaries built there are Sailfish binaries and execute in place, so
   the existing compile-and-run E2E suite becomes a genuine on-Sailfish gate.

2. **An install-free build story.** The compiler targets CLI tools and Docker
   microservices; today building one means installing Go, clang, and a handful of
   optional libraries. A published *toolchain image* (klainmain + clang + libs)
   turns that into `docker run … klainmain build app.ts` — nothing on the host —
   and a multi-stage `FROM` turns it into a tiny microservice image with just the
   native binary, no runtime. This is directly on the stated priorities.

Both reduce to: build and publish a small set of container images, keep them
current, and consume them from CI. Scoping it now because the Sailfish work just
shipped and its regression surface is real, and because the toolchain image is
the broadest-leverage half of the same machinery.

## Design

### The images

- **`klainmain` (toolchain, multi-arch `linux/amd64` + `linux/arm64`)** — a base
  Linux image (Debian/Ubuntu-class) with a release `klainmain`, `clang`, and the
  optional libraries the suite links (`libcurl`, `libpcre2`, `libssl`,
  `libnghttp2`, `libsqlite3`, `libgc`, `libtommath`, WebKitGTK for the webview
  compile tier). Entry point runs `klainmain` so `docker run -v "$PWD":/src
  <img> build app.ts` produces a native binary. One multi-arch manifest so
  `docker run` selects the right arch automatically.
- **`klainmain-sfos-aarch64`** — `docker/Dockerfile.sfos-sysroot` (the Sailfish
  `-devel` userland) with `clang` (Jolla repos ship 15.0.7) + a release
  `klainmain` added. Building *natively in this container* produces Sailfish
  binaries (host == target == aarch64 Sailfish), needing no `--target`, no
  `--sysroot`, and no lld (the native `ld` links). Also usable as a
  `--target sfos-aarch64 --sysroot /` cross-build target to exercise that path.

### The consumption patterns (what a user runs)

- **One-shot build**: `docker run --rm -v "$PWD":/src ghcr.io/<owner>/klainmain build app.ts -o app`.
- **Microservice multi-stage** (the idiomatic payoff):
  ```dockerfile
  FROM ghcr.io/<owner>/klainmain AS build
  COPY . /src
  RUN klainmain server.ts -o /server
  FROM debian:trixie-slim
  COPY --from=build /server /server
  ```
  A final image of the slim base + one native binary — far smaller than a Node
  base, no interpreter.

### The publish workflow

A dedicated workflow (`publish-images`) builds and pushes with buildx, on three
triggers so both our edits and upstream drift are covered:

- `push` with a `paths:` filter on the relevant Dockerfiles — rebuild when we
  change them.
- `workflow_dispatch` — manual button.
- `schedule` (monthly) — the honest catch for upstream drift: our Dockerfile can
  be byte-identical while the Jolla repos / base image ship new package versions
  under `zypper install` / `apt-get`, which a path filter never sees. Pin the
  content by the SFOS release tag (`5.1.0.11`) and the klainmain release version
  for reproducibility; the cron refreshes within that pin.

Tags: `klainmain:<release-version>` (reproducible) + `:latest`. The klainmain
binary baked in comes from the release pipeline's artifact, so the image version
tracks the compiler version.

### Reuse in CI

The `release.yml` test matrix gains a `sailfish-arm64` lane: `runs-on:
ubuntu-24.04-arm`, `container: <the sfos image>`, a `zypper install -y clang`
step (or baked into the image), then the same `go build` / `go vet` / `go test
./...` / `make examples` steps and a published `sailfish-arm64` gate — slotting
into the existing gate model where a red lane drops that platform from the release
without blocking the others. Because the lane runs *inside the published image*,
CI tests exactly what a user would build in.

### Registry — GHCR (decided)

Images live on **GHCR** (GitHub Container Registry) for the initial build: same
repository as the code, auth via the built-in `GITHUB_TOKEN` (no extra secret to
manage), and a `container:` job pulls it with that token directly. Docker Hub is
not the primary — it needs a PAT secret and its post-limits anonymous pull-rate
caps cut against the "just docker, no setup" UX.

**Dual-publishing is a deliberate future option, not ruled out.** Pinning to one
registry is a single point of failure and a single-vendor dependency — and GHCR
is no exception (GitHub is Microsoft-owned). So the publish workflow should be
written to make adding a second push target (a Docker Hub mirror, or a
self-hosted / neutral registry) a small change: build once, push to a *list* of
registries. Deferred, but the structure should not preclude it.

### Scope boundaries

- **macOS**: no Linux-hosted macOS containers, so Mac stays a local (brew)
  install — acceptable, Mac users have a toolchain.
- **Windows**: out of scope (WSL2 users can use the Linux image).
- **Windowed webview**: still can't run headless (no Wayland/lipstick/Gecko
  display in CI) — the `-webview=sailfish` *compile* tier (moc + link) gates in
  CI, the windowed run stays the manual device test, same posture as the system
  webview backend.
- **`-mm=gc` on Sailfish**: libgc isn't in the Sailfish base, so those tests skip
  (they already skip-not-fail when libgc is absent).

### Suggested staging

| Stage | Content | Exit criterion |
|---|---|---|
| 1 | `klainmain` toolchain image (multi-arch) + the `publish-images` workflow (GHCR, three triggers) | `docker run … build app.ts` produces a working native binary on amd64 and arm64; the multi-stage microservice pattern documented |
| 2 | `klainmain-sfos-aarch64` image published the same way | building natively in it produces a runnable Sailfish binary |
| 3 | `sailfish-arm64` CI lane inside the sfos image + gate; optionally a cross-build step for the `--target` path | the lane goes green and publishes its gate; a Sailfish regression turns it red |

## Open questions

- **Base image for the toolchain** — Debian/Ubuntu (broad, familiar) vs Alpine
  (smaller, but musl vs the glibc the project targets); likely Debian to match
  the runtime microservice base users will pair it with.
- **klainmain binary source in the image** — baked from the release artifact
  (image version == compiler version, clean) vs built from source in the image
  (heavier, but any-commit). Leaning baked-from-release.
- **Does the toolchain image also ship the Sailfish sysroot** for cross-builds
  from an amd64 host, or is Sailfish only the native-in-container image? (Cross
  from amd64 needs lld + the sysroot; native-in-arm64-container needs neither.)
- **Cross-build gate** — is the native-in-container Sailfish lane enough, or add a
  separate step exercising `--target sfos-aarch64` so the Mac→Sailfish cross path
  is also gated?
- **Image retention / size budget** — the sfos image is ~1.1 GB; retention policy
  for old version-tagged images on GHCR.
