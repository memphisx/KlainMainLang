# ADR-00331: Node `cluster` module — fork + re-exec worker model

- **Relations**: Implements TDD-00105; extends the http.listen({ workers }) fork machinery (TDD-00025)
- **Date**: 2026-08-23

## Context

`cluster` was one of the last unstarted Node core modules, with only the
read-only `cluster.isPrimary`/`workerId` accessors present (over the
`@__kml_cluster_worker_id` global that `http.listen({ workers: N })` sets). This
adds the callable surface — `cluster.fork()` and `cluster.isWorker` — so the
idiomatic Node cluster program works. TDD-00105 settled the model.

## Decision

Per TDD-00105, `cluster.fork()` = `fork()` + **re-exec the program's own
executable** in the child with `KML_CLUSTER_WORKER_ID=<n>` set in the
environment. The re-exec'd worker runs `main()` from the top with fresh state:
this matches Node's "a worker runs the entry file from the top" semantics,
avoids the fork bomb a plain `fork()` would cause when the child resumes inside
the primary's `for (…) cluster.fork()` loop, and sidesteps the fiber-safety
constraint (the child image is replaced before any event-loop/fiber state
exists).

Worker identity is unified with the existing http fork machinery: at program
start `@__kml_cluster_seed_id()` reads `KML_CLUSTER_WORKER_ID` into
`@__kml_cluster_worker_id`, so `cluster.isPrimary` (id == 0) / `isWorker`
(id != 0) / `workerId` work for a re-exec'd worker exactly as they already do
for an http-fork child. A program uses one clustering mechanism or the other.

Workers each `listen(port)` independently, so a cluster worker's listening
socket sets **`SO_REUSEPORT`** — but **only** when running as a worker
(`@__kml_cluster_worker_id != 0`). An ordinary single server must NOT set it, or
a second bind to an in-use port would silently succeed instead of throwing (this
broke `TestE2EHTTPListenBindFailureThrows` when it was set unconditionally). The
primary blocks in `@__kml_cluster_wait_all()` at program end,
reaping its forked workers via `waitpid` — keeping it alive while the workers
serve, like Node's primary.

V1 surface: `cluster.fork()` → a `Worker { id }`; `cluster.isPrimary` /
`isWorker` / `workerId`. Out of scope (V2): IPC / `worker.send()`,
`worker.process.pid`, `cluster.on('exit'/'online'/'listening')`,
`cluster.workers`, `schedulingPolicy`, graceful `disconnect()`.

## Implementation notes

- New `runtime_cluster.go` (`__kml_cluster_seed_id`/`_self_exe`/`_register_pid`/
  `_fork`/`_wait_all`) and `emit_cluster.go` (`emitClusterModuleCall` for
  `fork`, `emitClusterIsWorker`, `emitClusterWorkerMember` for `.id`).
- Self-executable path is platform-branched: Linux `readlink("/proc/self/exe")`,
  Darwin `_NSGetExecutablePath`.
- The re-exec passes the process's original `argv` (`@__argv_ptr`), so a worker
  sees the same command line — matching Node.
- `emitter.go` injects `@__kml_cluster_seed_id()` at the top of `main` and
  `@__kml_cluster_wait_all()` before its `ret`, both guarded by
  `usedClusterRuntime`.
- `ClusterWorkerType` / `IsClusterWorker` in types.go; dispatch in emit_call.go
  (`fork`), emit_exprs_member.go (`isWorker`, worker `.id`), emit_exprs_types.go
  (return types).
- `waitpid` was declared inline in `runtime_process.go` and
  `runtime_childprocess.go`; factored into a guarded `ensureWaitpidDecl`
  (runtime_core.go) shared with cluster so any two of the three can co-occur
  without a duplicate declaration.

## Side effects discovered

`SO_REUSEPORT` on a cluster worker: on Linux the kernel load-balances accepts
across workers bound to the same port; on Darwin the distribution is uneven
(observed: all requests to one worker) — correctness holds (every worker binds
and can serve), only balancing differs. Disclosed as a caveat. Gating it to
workers only (not every http listener) was necessary — set unconditionally it
made a second bind to an in-use port succeed, defeating http.listen's
bind-failure error.

An http-based cluster cannot cleanly self-terminate in V1 (workers run their
event loop forever with no IPC to signal shutdown) — the example is therefore a
finite-work fork demo; the http-cluster path is exercised by the Go test, which
reaps the worker process group.

## Verification

- `tests/cluster_test.go`: a single process reports `isPrimary`/`isWorker`/
  `workerId`; a clustered HTTP server (3 forked workers on a shared port via
  SO_REUSEPORT) serves a request, driven by the process-group cleanup helper.
- `examples/cluster/cluster.ts`: primary forks 3 workers that each run and exit;
  the primary reaps them and exits 0 — verified on macOS (arm64).
- Machine: verified on Mac (Apple Silicon). The self-exe path and SO_REUSEPORT
  balancing differ on Linux (`/proc/self/exe`; kernel load-balancing) — not
  re-run on Linux this session.
