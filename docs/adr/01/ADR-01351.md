# ADR-01351: Typed arrays answer `buffer` and `byteOffset` through a view registry

- **Relations**: Implements part of TDD-00243; extends TDD-00018
- **Date**: 2026-10-03

## Context

Typed arrays had no `.buffer` and no `.byteOffset`, a caveat on the typed
array, BigInt64Array and Uint8ClampedArray rows. That also blocked
`new DataView(b.buffer, b.byteOffset, b.byteLength)`, the usual way to read a
Buffer as binary, and moving DataView to TS (TDD-00230 P3.4).

## Investigation

- A view over an ArrayBuffer already points its data at `base + offset`, so
  aliasing works. Only the provenance is lost.
- TDD-00243 compares widening the typed-array header with a registry keyed
  by data address. Widening touches every site that mints an array header,
  and a header minted by generic array code would come out narrow. The
  registry changes no representation.
- Typed-array and ArrayBuffer storage is never freed explicitly. Under
  `-mm=manual` and `-mm=auto` an entry cannot go stale. Under `-mm=gc` the
  entries must neither keep storage alive nor outlive it.

## Decision

`codegen/llvm/viewsrc/views.c` keeps a chained hash table from a data address
to `(root, root length, offset)`. The root's entry holds its ArrayBuffer
header.
- `new T(buffer, off, len)` registers the view and its buffer.
- `subarray` registers the child under its parent's root, with the offsets
  summed. A parent that is not registered is an array with its own storage,
  so it becomes the root and no buffer is created yet.
- `.byteOffset` looks the address up; a miss is 0.
- `.buffer` returns the root's header. An array with its own storage gets
  one on first read, `{byteLength, data}` aliasing its bytes, and keeps it.
- Under `-mm=gc` entries are `GC_malloc_atomic`, and the buffer field is a
  disappearing link.
- A mutex guards the table, for SharedArrayBuffer views made on several
  threads.

Through `any`, dynjson's `__kml_anyarr_get_by_key` answers `byteOffset` and
`buffer` for a boxed typed array. The buffer is boxed as a host cell whose
header word the compiler exports (`__kml_view_ab_header`) once a typed array
is boxed. It inspects, compares and passes `instanceof` as an ArrayBuffer.

## Implementation notes

- `runtime_views.go`: embedding, `ensureViews` and `ensureBoxedViews`.
- `emit_arraybuffer.go`: registration, `subarray` derivation and
  `emitTypedArrayViewProp`.
- Member dispatch and its type mirror: `emit_exprs_member.go`,
  `emit_exprs_types.go`.
- The boxing hook (`boxAnyArray`) in `emit_dynamic.go`, and the `KML_VIEWS`
  keys in `dynjson.c`.

## Side effects discovered

- Node pools small Buffers, so `Buffer.from('x').byteOffset` there is an
  offset into an 8 KiB pool. Here it is 0, and the buffer is the Buffer's
  own bytes. Node documents the pooling as an allocation detail; the
  offsets programs compute from it come out the same.
- The worker caveat (a shared-buffer view is copied, not shared) no longer
  blames the missing `.buffer`. Its fix is TDD-00243's next stage.

## Verification

Mac (Apple Silicon), against Node 24, all matching byte for byte:
- views, subarrays, own-storage buffers, a Buffer read through a DataView
  and float aliasing;
- the same through `any`, including identity, inspection and `instanceof`;
- Uint8ClampedArray and BigInt64Array/BigUint64Array;
- the program also run with `-mm=gc`.

Tests: new `TestE2ETypedArrayBufferAndByteOffset`, the extended
`examples/typedarrays/typedarrays.ts`, and the TypedArray, ArrayBuffer,
DataView, Buffer and SharedArrayBuffer groups.
