# ADR-00207: RegExp `es-utf16` index mode and the global empty-match advance

- **Relations**: `Implements TDD-00067` (Stage 3). `Extends ADR-00206` (Options A + B / the `-regex` mode selector).
- **Date**: 2026-08-17

## Context

ADR-00206 shipped TDD-00067 Options A + B: the `-regex=<mode>` selector with `pcre`/`es-ascii`/`es-unicode`, defaulting to `es-unicode`. It deliberately kept all offsets in the UTF-8 **byte** space the rest of the string layer uses (`.charCodeAt`/`.slice` are byte-indexed, ADR-00028), so `match.index`-style values line up with `str.slice(...)`. That leaves one gap versus real ECMAScript: JS reports RegExp offsets in **UTF-16 code units**, not bytes. TDD-00067 scoped this as its own opt-in stage (`es-utf16`) precisely because a UTF-16 index space diverges from the byte-indexed string layer, so it must never be silently forced on the default.

Two things are delivered here:

1. **`-regex=es-utf16`**: matches identically to `es-unicode`, but converts every offset that crosses back to user code — `str.search()`'s return, a RegExp's `lastIndex`, and a replace callback's `offset` — to true UTF-16 code-unit positions.
2. **A global empty-match advance** (found while building Stage 3): the multi-match driver loops (`str.match`/`matchAll`/`replaceAll`) had no AdvanceStringIndex step, so a zero-length-capable global pattern (`/x*/g`, `/(?=a)/g`) drove them into an **infinite loop** — `lastIndex` never advanced past the empty match. `docs/status/REGEXP.md`'s dialect caveat #2 described a one-byte advance that did not actually exist in the code; a repro (`"abc".match(/x*/g)`) hung (`SIGKILL`, exit 137). This is a prerequisite for any correct global iteration, UTF-16 or not, so it is fixed here rather than deferred.

## Investigation

- The offset-producing/consuming boundaries were enumerated across `emit_regexp*.go`: `emitRegexSingleMatchCore` reads `lastIndex` as the match start and writes the match end back (`emit_regexp.go`); `emitRegexSearch` returns the match-start offset (`emit_regexp_split.go`); `emitRegexComputeOneReplacement` passes the match start to a callback as `offset` (`emit_regexp_replace.go`). `.exec()`/`.match()` build no `.index` property (a documented V1 narrowing), so the result *array* carries no offset to convert — the boundary set is exactly those three.
- The string layer has **no** byte↔UTF-16 helper (`codePointAt` is just `charCodeAt` under a second name — `emit_strings.go:362`), confirming Stage 3 needs a fresh converter, as the TDD's prerequisite table predicted.
- The empty-match hang was confirmed empirically: `"abc".match(/x*/g)` compiled and ran to a `SIGKILL` timeout. `emitRegexSingleMatchCore` stores `lastIndex = matchEnd`, which for an empty match equals the match start, so the count/collect/replaceAll loops re-find the same empty match forever. Real JS avoids this via AdvanceStringIndex in the String.prototype.* algorithms, *not* in `RegExpBuiltinExec` — so `.exec()` used by hand in a `while` loop legitimately loops (a real-JS footgun), and the advance belongs only in the driver loops.
- Cross-checked expected values against Node: `"abc".match(/x*/g).length` → 4, `"abc".replaceAll(/x*/g,"-")` → `-a-b-c-`, `[..."aXbXc".matchAll(/X/g)].length` → 2, `"a".match(/(?=a)/g).length` → 1 — all now equal.

## Decision

**Index conversion.** Two pure runtime helpers (`runtime_regexp.go`), emitted only when a UTF-converting/advancing path is reached:

- `__kml_regex_utf8_width(str, off)` — code-point byte width (1–4) from the lead byte's high bits.
- `__kml_regex_byte_to_utf16(str, byteLen)` / `__kml_regex_utf16_to_byte(str, target)` — walk code points via the width helper, counting a 4-byte (supplementary) code point as 2 UTF-16 units. `utf16_to_byte` stops at the NUL terminator so an out-of-range target clamps to the string end.

`regexModeOpts` gains `utf16Index` (true only for `es-utf16`) and `utfMatching` (true whenever `PCRE2_UTF` is on). Three Go-side wrappers — `regexByteToUTF16`, `regexByteToUTF16Signed` (passes the `-1` no-match sentinel through), `regexUTF16ToByte` — are **identity passthroughs** unless `utf16Index`, so each call site stays single-form across all modes. They are applied at exactly the three boundaries: `lastIndex` read (UTF-16→byte for the PCRE2 start offset) and write (byte→UTF-16 for the stored end) in `emitRegexSingleMatchCore`; `str.search`'s return (signed, in `emitRegexSearch`); the callback `offset` (in `emitRegexComputeOneReplacement`). Matching options are identical to `es-unicode`. `lastIndex` is thus stored in the mode's own space (UTF-16 units for `es-utf16`, bytes otherwise), converted only where it meets PCRE2 or user code.

**Empty-match advance.** `emitRegexAdvancePastEmpty(obj, str, startByte, endByte)`: when `startByte == endByte`, bump the stored `lastIndex` to `end + width`, where `width` is a whole UTF-8 code point in the UTF-matching modes (so the next start offset never lands mid-code-point, which `PCRE2_UTF` would reject) and 1 byte in the raw-byte modes; the new value is written back in the mode's index space. Called in the continue branch of all three drivers — `emitRegexCountGlobalMatches`, `emitRegexCollectGlobalMatches`, and the `emitRegexReplaceAllMatches` fill loop — so the count and fill passes stay in lockstep. `str.split`'s own local zero-length advance (`emit_regexp_split.go`) was likewise widened from 1 byte to a code point in the UTF modes.

The default stays `es-unicode`; `es-utf16` is opt-in, per TDD-00067's resolution that the byte-indexed default must stay consistent with the string layer.

## Implementation notes

- New `used`-flags `usedRegexUTF8Width` / `usedRegexUTF16Convert`; `ensureRegexUTF16Convert` calls `ensureRegexUTF8Width` so the width helper is declared exactly once even when both the converters and the empty-advance need it.
- `main.go` now accepts `es-utf16` (only `ecmascript` remains rejected as not-yet-implemented); the `-regex` help text and `resolveRegexMode`'s doc were updated. The default is unchanged.
- Round-trip correctness relies on match boundaries always being code-point-aligned: byte→UTF-16→byte returns the same byte offset for any boundary-aligned offset, which every match start/end is. A hand-set `lastIndex` landing mid-surrogate resolves to the following code point's byte start — best-effort for a pathological input, never a read past the end.
- Files touched: `main.go`, `codegen/llvm/emitter.go`, `codegen/llvm/runtime_regexp.go`, `codegen/llvm/emit_regexp.go`, `codegen/llvm/emit_regexp_replace.go`, `codegen/llvm/emit_regexp_split.go`, `tests/regexp_test.go`, `examples/regexp/regexp_utf16.ts`, `docs/status/REGEXP.md`, `docs/tdd/TDD-00067.md`.

## Side effects discovered

- **The empty-match infinite loop was a real, undisclosed hang**, not the one-byte-advance-with-early-stop that REGEXP.md's caveat #2 claimed. Fixing it also removes that caveat: because the advance now steps a whole code point in the UTF modes, `es-unicode` global iteration over multibyte text no longer stops early either — the fix is not `es-utf16`-specific. Caveat #2 is retired for both UTF modes.
- **`str.split` zero-length handling** in the UTF modes previously advanced by 1 byte and could land mid-code-point (a latent early-truncation); now widened to a code point. `split`'s "only non-zero-length matches split" narrowing is unchanged.
- `es-utf16` inherits every `es-unicode` matching caveat (NEWLINE_ANY over-exclusion of `\x0b`/`\x0c`/`\x85`; non-Unicode `\w`/`\s`/`\b`) since matching is identical — those remain Option C's territory.

## Verification

Machine: Apple Silicon M4, pcre2 10.47, `clang -O2`.

- New E2E `TestE2ERegExpUTF16IndexMode` (10 sub-cases) pins each boundary `es-unicode` (byte) vs `es-utf16` (unit): `search` on `"é1"`/`"😀1"`, the `-1` sentinel, `lastIndex` after a global `exec`, a hand-set-`lastIndex` round-trip, and the callback `offset`. New `TestE2ERegExpEmptyGlobalMatchTerminates` (5 sub-cases, values cross-checked against Node) pins the hang fix, including the multibyte code-point advance.
- Full suite green: `go build`, `go vet ./...`, `go test ./...`.
- Example `examples/regexp/regexp_utf16.ts` compiles under `-regex=es-utf16` and runs with output matching every annotated line.
