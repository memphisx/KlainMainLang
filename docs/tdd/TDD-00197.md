# TDD-00197: the server `'close'` event + drain-accurate `server.close(cb)`

- **Status**: Implemented
- **Date**: 2026-09-10

## Context

An `http.Server` supported `.on('request'|'stream'|'listening'|'upgrade')` but
not `'close'` — the event real code relies on for graceful-shutdown logging and
test teardown. Separately, `server.close(cb)` fired `cb` **synchronously** the
instant `close()` was called, a divergence from Node, where `cb` (and the
`'close'` event) fire only once the server has stopped listening **and** every
in-flight connection has finished. Both share one missing piece: a signal for
"the server has fully drained."

## Design

`__kml_http_close()` already clears the listener (`@__kml_listen_fd = -1`)
immediately while letting accepted connections finish; the reactor already
tracks in-flight connections in `@__kml_conn_active`. So "fully drained" for the
**primary** server is exactly `listen_fd < 0 && conn_active == 0`, computable
from state the reactor already owns.

- Three primary-server reactor globals: `@__kml_http_close_cb` (the deferred
  `close(cb)` closure), `@__kml_http_close_evt` (the `.on('close')` handler), and
  `@__kml_http_close_pending` (set when `close()` is called).
- A runtime helper `__kml_http_fire_close()` the reactor calls **once per
  iteration**: it self-checks `pending && listen_fd<0 && conn_active==0`, and on
  the first iteration all hold, clears the state and invokes the `'close'`
  handler then the `close(cb)` callback (each a zero-arg `{fn,env}` closure).
  Placed in the loop after draining is computed but before the keep-alive/exit
  decision, so a handler's own newly-scheduled work is still seen that
  iteration. Unconditional (three cheap loads per idle iteration) — no
  whole-program pre-scan needed to decide whether the reactor references it.
- `server.close(cb)` on the primary stops firing `cb` synchronously: it stores
  `cb` and sets `pending`. An **additional** server keeps synchronous `cb`
  (it has no per-server active-connection global), and `.on('close')` on a
  non-primary server is a clean compile-time rejection — primary-only for V1.

### Alternatives rejected

- *Fire at loop exit (`alldone`).* Simpler (one call at teardown) but wrong when
  other work (a timer) outlives the server: Node fires `'close'` at drain, not
  at process wind-down. The per-iteration self-checking helper fires at the
  faithful moment for a negligible cost.
- *A per-server drain edge for every server.* Correct but needs per-server
  active-connection counters the reactor doesn't have; deferred with the rest of
  multi-server parity.
