# ADR-00865: Windows IOCP reactor Stage 1 — completion port, overlapped/buffered pipes, console reader

- **Relations**: Implements [TDD-00183](../tdd/TDD-00183.md) (Stage 1); Extends [ADR-00864](ADR-00864.md) (the owned fd table), [ADR-00757](ADR-00757.md) (the loop wakeup)
- **Date**: 2026-09-11

## Context

TDD-00183 committed to an I/O completion port (IOCP) reactor — the completion model Windows and libuv are built around — as the faithful Windows event loop, superseding TDD-00182's readiness-wait Stages 2–6 (which would have been throwaway work once IOCP landed). Stage 1 delivers the non-socket half: the port itself, non-blocking pipe and console I/O, and the wakeup unification, while sockets stay temporarily on the existing Winsock-`select` probe as an explicit migration bridge (Stage 2 moves them to overlapped ops).

The symptoms this stage removes (TDD-00180 §1/§2): `process.stdin` and child-stdout pipe reads that blocked the whole loop; the synchronous 4 KB `CreatePipe` child stdio that deadlocked a parent streaming a large stdin against an unread child stdout; the 50 ms poll slice while a console-ctrl handler was installed, and the 10 ms slice for a pipe/console-only program; console input read via the CRT code page (non-ASCII corruption).

## Investigation

`win32io.c`'s `select()` was a poll emulation: Winsock `select` over the socket subset in short slices, `PeekNamedPipe`/`WaitForSingleObject` over pipes/console each pass, `Sleep(slice)` when only plain fds were watched (`win32io.c:710-769` pre-change). The root cause of the blocking-stdin/child-stdio symptoms was that non-socket fds had no wait object the loop could block on and be woken from, and reads fell to CRT `_read`.

The subtle trap, found while building the reader path: a zero-byte `ReadFile` — libuv's zero-read readiness primitive for *overlapped* handles — is the wrong primitive for a *synchronous* byte pipe (Go's `StdinPipe`, our inherited fd 0). It returns immediately without waiting for data, and worse, a zero-byte `ReadFile` running on a background thread serializes in the kernel against the real `ReadFile` in `read()`, so the real read stalled until the *next* write flushed both — an 78 ms per-chunk stall observed directly under `KML_IO_TRACE`. The fix is the libuv model for non-overlapped pipes: a thread that blocks reading *real* bytes into a buffer, with `read()` draining the buffer and never touching the handle.

## Decision

A single process-wide `CreateIoCompletionPort`, drained by one alertable `GetQueuedCompletionStatusEx`. `select()` becomes a projection over it (the IR's `select`-shaped contract is preserved — the TDD's central decision), keeping every IR-level net/http/stdin caller untouched.

- **Op records with generations.** Every overlapped op is a heap `kfd_op { OVERLAPPED, fd, gen, kind, buf, len, next }`; a completion dequeued after its fd closed (slot reused, `gen` bumped) is recognized and freed. `FILE_SKIP_COMPLETION_PORT_ON_SUCCESS` keeps synchronously-satisfied ops off the port.
- **`pipe()` stays anonymous.** The scope was deliberately narrowed while implementing (see Investigation/Side effects): `pipe()` keeps creating an anonymous synchronous `CreatePipe` pair exactly as before. Its ends are in-process (worker / `BroadcastChannel` / fork IPC) or the write end is inherited by a child that writes it (child stdout/stderr, `execSync`); the loop-side read end stays on the `PeekNamedPipe` poll path with the 10 ms slice as its fallback (anonymous pipes cannot be overlapped, so they are not port-armable). Converting these to named/overlapped ends regressed cross-thread worker IPC and was reverted. Only the two cases that genuinely need completion behaviour opt out of `pipe()`:
  - **Child stdin** — `__kml_win_pipe_pw` (child read end = synchronous client, parent write end = overlapped named server). Parent writes are **copied and queued** overlapped ops (the Node user-space write queue), so a parent streaming a large stdin never deadlocks against an unread child stdout. `close()` flushes the queue.
  - **`process.stdin` (fd 0)** — a piped fd 0 is served by a **buffering reader thread** (blocks reading real bytes into a 64 KiB ring, posts a wake; `read()`/`select()` drain/probe the buffer, never the handle — a zero-byte `ReadFile` is the wrong primitive for a synchronous byte pipe and races a concurrent real read, the 78 ms stall in Investigation).
- **Console reader thread.** `read()` on a `KFD_CONSOLE` fd 0 is served by a `ReadConsoleW` thread decoding UTF-16→UTF-8 into a queue — cooked-mode line editing preserved, non-ASCII input correct (TDD-00180 §2), Ctrl+Z at line start = EOF. Readiness is "decoded bytes queued", not "any input record", fixing the readable-on-any-record bug.
- **Thread-local port + unified wakeups.** The completion port is **thread-local** (each worker runs its own reactor; a shared port would let one thread steal another's wake); the first one created — the main reactor's — is `kml_main_port`. `__kml_win_loop_wake` = `PostQueuedCompletionStatus(kml_main_port, …)`; the stdin/console reader threads, the console-ctrl handler, and the resize watcher (`win32proc.c`) post it (all main-reactor sources), so a blocked wait ends at once — the 50 ms handler slice dies. The stdin/console spawners call `kml_port_get()` so the main reactor has a port to block on. `fs.watch`/thread-pool socketpair wakeups keep working unchanged (their read ends are sockets).
- **Zero-read arming deferred.** Zero-byte overlapped-read wake arming (libuv's zero-read mode) is Stage 2 work — Stage 1 has no overlapped *read* ends (pipe() is anonymous, the child-stdin overlapped end is write-only), so nothing arms one yet; the `OPK_ZERO_READ` slot state and its drain handling are kept ready.
- **Wait / migration bridge.** With a port (main reactor: stdin/console/child-stdin), `select()` blocks in `kml_port_drain`; without one (a worker thread, or before any port source), it falls back to the old poll `Sleep(slice)`. A watched socket (still on Winsock `select`, the Stage-2 bridge) or an anonymous pollable pipe forces the 10 ms slice; when neither is watched the wait is the port alone — single, blocking, packet-woken — so the idle spin is gone for a pipe(reader)/console/stdin program. For a pure-socket program `kml_port` is never created and the socket path is byte-for-byte unchanged this stage.

## Implementation notes

- `win32io.c`: `kfd_slot` extended in place (ADR-00864's array-of-structs paying off) with reactor fields — no new parallel arrays. `KFD_CONSOLE` added to the kind enum. New sections: the thread-local port + op records + drain, the overlapped named-pipe pair creator (used only by `__kml_win_pipe_pw`), the buffering reader thread (for a piped fd 0), the console reader, std-fd lazy classification (`kfd_classify` on `GetFileType`, flagging fd 0's `use_reader`).
- `runtime_childprocess.go` / `runtime_spawn_win.go`: the child-stdin `pipe()` call routes through `cpStdinPipeCallIR()` → `@__kml_win_pipe_pw` on Windows (child read end synchronous, parent write end the overlapped write-queued server); out/err keep the anonymous `pipe()`.
- `win32proc.c`: the console-ctrl handler and resize watcher post the wake packet.
- `KML_IO_TRACE` gains timestamped read/select lines (a per-chunk stall is invisible otherwise); stderr is set unbuffered under the trace so no line is lost.

## Side effects discovered

- **Named/overlapped `pipe()` regressed worker IPC.** The first cut made `pipe()` create a named overlapped-server + synchronous-client pair (so read ends were port-armable). Two in-process worker reactor threads then each blocked `select()` on the port with `timeout=-1`, and the overlapped server read end's `PeekNamedPipe` readiness re-probe *missed* data a zero-read completion had signalled, so the loop re-armed and hung (`TestE2EWorker*`/`TestE2EBroadcastChannelAcrossWorker` timed out at 600 s). Root-caused via `KML_IO_TRACE`; fixed by reverting `pipe()` to anonymous and narrowing the reactor treatment to fd 0 + child stdin (the Decision above). This also surfaced that the completion port had to be **thread-local** (a shared port lets one worker steal another's wake).
- Socket-path tests (`TestE2ENetSocketCloseAndReadyEvents`; occasionally `fork`-IPC and `TestE2EDgramEchoServer` under load) stay flaky — sockets and fork/dgram IPC (loopback TCP) are still on the Winsock-`select` bridge this stage. Pre-existing (ADR-00864); Stage 2's overlapped `WSARecv` is expected to make them deterministic (consistent passing = Stage 2 acceptance), so they are left unmasked.
- On a real console, `process.stdin`/`readline` now read through the console reader thread rather than the CRT — the piped E2E suite can't observe this (a pipe is `KFD_PIPE`), so a ConPTY test was added for it.

## Verification

Windows dev box, MSYS2 UCRT64 clang 22.1.7 (`/c/msys64/ucrt64/bin`):

- All three win32 C files compile clean (`clang -c -Wall -Wextra`); `go build`/`go vet ./...` clean.
- New tests: `TestE2EStdinDoesNotBlockLoop` (a slow Go-driven producer on stdin; a 15 ms `setInterval` accrues ~5/16/23 ticks between chunks — proof the loop is not stalled; the pre-reactor path starved it), `TestE2EChildProcessLargeBidirectionalStdio` (64 KiB each way through `cat` — the old 4 KB sync pipe deadlocked), `TestE2EStdinConsoleReaderUTF8` (ConPTY: a typed `café\r` line delivered UTF-8-intact to `'data'`, Ctrl+Z ends the stream).
- Regression (all pass bar the two flakes above): `TestE2EFs*`, `TestE2EProcessStdin*`, `TestE2EReadline*`, `TestE2EStdin*`, `TestE2EChildProcess*`, `TestE2ECluster*`, `TestE2ETty*`/`TestE2ETuiConsole*`/ConPTY console suite, `TestE2ENet*`/`TestE2EDgram*`/`TestE2EHttp*`/`TestE2ETls*`/`TestE2EWebSocket*`.
- Not re-verified on macOS/Linux from here (Windows-only C plus Windows-gated tests); CI's POSIX lanes are the guard.
