# TDD-00051: Re-exports (`export { a } from './x'`, `export * from './x'`)

- **Status**: Implemented
- **Date**: 2026-08-10

## Context

[MODULES.md](../status/MODULES.md) lists re-exports as the one named-import-adjacent gap [TDD-00042](TDD-00042.md) explicitly left out: "a file re-publishing a name it didn't itself declare, which touches the `exported`/`mangled` maps' per-file assumption differently." Everything else in that cluster (`export default`, default imports, namespace imports) is done. This is the next module-system slice.

## Design

### Syntax scoped for V1

- `export { a, b as c } from './path'` — named re-export list.
- `export { default } from './path'` / `export { default as Foo } from './path'` — re-exporting another file's default export, either as this file's own default or under a named export. `default` is `lexer.DEFAULT`, not `lexer.IDENT`, so the specifier-list parser needs to accept that token literally alongside `IDENT` (only inside this new export-from list — regular `import { default as Foo }` stays unsupported, unchanged, since `import Foo from` is already the sugar for that case).
- `export * from './path'` — re-export every name the target itself exports, **except** `"default"` (matches real ES module semantics: a star re-export never forwards a default).

Reuses `ast.ImportSpecifier`'s `{Imported, Local}` shape for each entry (renamed in spirit only — `Imported` is the name in the source file, `Local` is what this file exposes it as) rather than inventing a parallel type, since it's the same name-forwarding problem `import { a as b }` already solved.

New AST node, since this isn't a `Decl`-wrapping form like `ExportDeclaration`:

```go
// ExportFromDeclaration re-exports members of another module without
// binding any local name in this file: `export { a, b as c } from './path'`
// (Specifiers set, All false) or `export * from './path'` (All true,
// Specifiers empty — every name the target exports except "default").
type ExportFromDeclaration struct {
    Specifiers []ImportSpecifier
    All        bool
    Source     string
    pos        Pos
}
```

Parser: `export {` and `export *` are both otherwise-unused continuations after `export` (there's no existing `export { ... }` — without `from` — form, see Not Yet Supported below), so they're unambiguous dispatch points in `parseExportDeclaration`. `export * as ns from` (namespace re-export, see below) must get an explicit, clear rejection at parse time rather than falling through to a confusing error.

### Resolver: why the export table can't reuse the intra-file scope map

`fileInfo.mangled` currently serves two purposes at once: it's the file's own intra-file scope lookup (`renameFile` rewrites bare references inside that file using exactly this map) *and* the table an importer reads via `target.mangled[spec.Imported]`. For every case that exists today those two purposes coincide — a file's own declarations are always both locally referenceable *and* (if exported) importable under the same mangled name.

Re-exports break that coincidence: `export { x } from './other'` does **not** introduce `x` as a usable bare identifier inside the re-exporting file (real ES modules agree — a re-export is forwarding, not a local binding). If the resolved alias were written into `info.mangled` the way `mangled["default"]` already is for `export default`, a stray bare reference to `x` elsewhere in the *re-exporting* file would silently resolve to the target's mangled name instead of being a legitimate "undefined name" error.

So re-export aliases go into a new, separate table, consulted only by the two places that build another file's *public* view (never by `renameFile`'s intra-file lookup):

```go
type fileInfo struct {
    ...
    mangled         map[string]string // unchanged: own declarations only, intra-file + public
    reExportMangled map[string]string // NEW: local export name -> target's mangled name, public-only
}

func (info *fileInfo) publicMangled(name string) (string, bool) {
    if m, ok := info.mangled[name]; ok {
        return m, true
    }
    m, ok := info.reExportMangled[name]
    return m, ok
}
```

The two existing consumer sites that currently read `target.mangled[...]` directly switch to `target.publicMangled(...)`:
- the named-import lookup-building step (`lookup[spec.Local] = target.mangled[spec.Imported]`)
- the namespace-import member-table builder (`members[name] = target.mangled[name]`, iterated over `target.exported`)

`info.exported` (existence-only, already used for import validation and to enumerate namespace members) *does* get re-export names added directly — a re-exported name really is part of the file's export surface, that part of the conflation is correct and desired.

### Resolver: dependency ordering

`ResolveProgram`'s DFS (`visit`) currently only follows `ImportDeclaration.Source` to discover files and build `order` (dependency-first: a file's dependencies land in `order` before the file itself). `ExportFromDeclaration.Source` is exactly the same kind of edge and must be walked by `visit` too, otherwise a file that *only* re-exports (no `import`) from another file would never get that file visited/ordered relative to it.

With that fixed, two new passes slot into the existing pipeline, both processed in `order` (then the entry file), i.e. dependency-first — a file's re-export sources are always fully finalized before the file itself is processed:

1. **After the full DFS, before the existing import-specifier validation loop**: walk each file's `ExportFromDeclaration` statements. For each resolved `(local, target, remote)` triple (expanding `export * from` into one triple per name in `target.exported` minus `"default"`), reject a collision against `info.exported` (own declarations or an earlier re-export in the same file — "already declared/exported" is the existing error family, reused verbatim), reject `!target.exported[remote]` the same way a normal import's unknown-member check does, then set `info.exported[local] = true` and stash `(target, remote)` in a same-shaped side table for pass 2. This has to happen before the existing validation loop because that loop's correctness already depends on every file's `exported` set being its *final* set.
2. **After the existing `mangleFileDecls` loop** (so every file's own `mangled` map — needed by `target.publicMangled`, which itself may recurse through another re-export — is final): walk the same side table and set `info.reExportMangled[local] = target.publicMangled(remote)`, resolving arbitrarily deep re-export chains for free since the target was necessarily processed earlier in the same dependency-ordered pass.

`unwrap()` drops `ExportFromDeclaration` entirely (like `ImportDeclaration` — it produces no runtime statement). `validateDeclarationsOnly` allows it in a non-entry file, same bucket as `ImportDeclaration`.

### Not yet supported (explicit scope cuts, not oversights)

- `export * as ns from './path'` (namespace re-export, ES2020) — parsed and rejected with a clear message, not silently mis-parsed. No forcing use case yet; can fold in later using the same `ns` machinery [TDD-00042](TDD-00042.md) already built for namespace imports.
- `export { x };` (no `from` — exporting a name already declared earlier in the same file, real ES modules' "export list" form) — a different, smaller feature (it never leaves this file's own declarations) that happens to share `{ ... }` syntax with the `from` form. Left for whoever needs it; not implemented by this TDD's parser changes.
- Re-exporting from a built-in module (`export { readFileSync } from 'fs'`) — rejected with an explicit error. No concrete use case, and it would need `ExportFromDeclaration` to also understand `virtualBuiltinMarkers`, which the rest of this design deliberately keeps out of.
- A dedicated "circular re-export" diagnostic. A genuine cycle with no real declaration backing it anywhere in the graph (`A` re-exports `x` from `B`, `B` re-exports `x` from `A`, neither ever declares `x`) still fails to compile — pass 1 hits `!target.exported[remote]` for whichever file's `ExportFromDeclaration` gets processed against the not-yet-augmented other side — but the message reads as an ordinary "no exported member" error, not one that calls out the cycle by name. Acceptable for V1: it fails closed, just not with the friendliest wording. See Open Questions.

## Open questions

- Whether the "no exported member" error for a genuine circular re-export (see above) is worth a dedicated detection pass with a clearer message, or whether it's rare enough in practice to leave as-is indefinitely.
- Whether `export * as ns from` (namespace re-export) is worth picking up later as a small follow-on once there's a real caller, given it reuses [TDD-00042](TDD-00042.md)'s namespace machinery almost directly.
