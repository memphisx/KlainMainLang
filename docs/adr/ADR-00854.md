# ADR-00854: Destructured callback parameters (`([k, v]) => …`)

- **Relations**: Implements [TDD-00199](../tdd/TDD-00199.md); extends the tuple
  model ([ADR-00492](ADR-00492.md) `Object.entries` typed values, TDD-00066)
- **Date**: 2026-09-10

## Context

`arr.map(([k, v]) => …)` — destructuring a tuple element directly in a
callback's parameter list — is the single most common destructuring idiom in
real code (iterating `Object.entries(o)`, `Map` entries, `[key, value]` pairs).
Two gaps blocked it:

1. **Un-annotated pattern param parse-failed.** `([k, v]) => …` gave
   `parse error: expected ), got =>`. The arrow-detection lookahead recognized a
   destructured first param only when a `:` type annotation followed the pattern,
   and `parseArrowFunction` then hard-errored "a destructured parameter requires
   an explicit type annotation".
2. **Heterogeneous tuple params didn't bind even when annotated.**
   `([x, y]: [number, number]) => …` gave `codegen error: undefined variable 'x'`:
   the param-binding path dispatched only on `pty.IsArray` (a uniform element
   type), never on `pty.IsTuple`.

## Investigation

The machinery already existed in adjacent positions. A tuple `Type` is an
`IsObject` struct with synthetic positional fields `"0","1",…` and `IsTuple` set
(`types.go`, `TupleType`); per-index types live in `Fields[i].Ty`.
`for (const [k, v] of Object.entries(o))` already decomposes a heterogeneous
`[string, V]` entry tuple via `unpackTuplePatternInto` (`emit_tuple.go:54`),
dispatched on `elemTy.IsTuple` at `emit_stmts.go`. The contextual-typing channel
(`emitArrowFunctionWithHints`, `hints []Type`) already delivers a HOF receiver's
element type — a tuple — into an un-annotated param. Only the parameter-binding
path and the parser were missing.

A tuple param is passed as a single `ptr` object (not the two-word `(ptr, i64)`
array ABI), so it lands on the object side of each param loop — the same side the
`ObjectPattern` branch already uses.

## Decision

**Parser** (`parser_literals.go`): rewrote `destructuredArrowParamLookahead` to
scan to the `)` that closes the parameter list, tracking paren depth (nested
parens in a type annotation balance out; the pattern brackets/braces never affect
paren depth), then accept the group as an arrow iff `=>` or `:` (a return-type
annotation) follows — a parenthesized object/array literal is never followed by
either. Dropped the required-annotation error, leaving `p.Type == nil` for the
contextual-typing path to fill.

**Codegen param binding** (`emit_func.go`): in all three param-binding sites
(named functions, arrow closures, function expressions) added a
`p.ArrayPattern != nil && pty.IsTuple` branch that loads the object pointer and
calls `unpackTuplePatternInto` — mirroring the for-of dispatch — before the
uniform-array and object-pattern branches. No change to `unpackTuplePatternInto`,
`Object.entries`, hint propagation, or the tuple `Type`.

**Return-type inference** (`emit_func.go`, `emit_exprs_types.go`): the two
independent return-type inference paths (the emission-time
`emitArrowFunctionWithHints` and the `inferExprType` HOF path via
`callbackReturnType`) both pushed only the synthetic `__paramN` name into scope,
so a body referencing `k`/`v` couldn't resolve them and the return type wrongly
defaulted to a number. Added `definePatternParamForInference`, which binds each
pattern leaf with its per-position type (tuple field type, or uniform array
element type, or object field type), and routed both paths through it. For block
bodies added `inferUnannotatedReturnTypeParams` (a pattern-aware sibling of
`inferUnannotatedReturnType` sharing a new `inferBlockReturnExpr` core), leaving
the nine other name-based callers untouched.

## Implementation notes

- The inference fix was the subtle half: the inline form `p.map(...).join(",")`
  worked from the start (join reads the emitted result Value's type) and masked
  that `const b = p.map(...)` typed `b` via the separate `inferExprType` path,
  which defaulted the string-returning callback to a number — rendering raw
  pointers. Both inference entry points had to route through the shared helper.
- `unpackTuplePatternInto` already handles holes (`[, v]`), nested sub-patterns
  (`[[x, y], z]`), and per-index array/nullable fields, so those work for free.

## Side effects discovered

- Un-annotated **object**-destructured arrow params returning a field
  (`a.map(({n, v}) => n + v)` assigned to a variable) were also mis-inferred by
  the same synthetic-name gap; the shared helper fixes them too.
- The `(a, b)` comma-sequence-of-identifiers expression remains unsupported (the
  pre-existing `IDENT COMMA` arrow heuristic claims it) — untouched here,
  unrelated to destructuring.

## Verification

macOS (Apple Silicon M4): matches Node across un-annotated / annotated-tuple
forms, string- and number-returning bodies, holes, nested patterns, three-tuples,
Map entries, and `filter`/`reduce`/`some`/`forEach`; both inline and
assigned-to-variable. New `TestE2EDestructuredCallbackParam`; the tuple, HOF,
arrow, closure, and object suites stay green. `go build`, `go vet` clean;
`examples/tuples/tuples.ts` extended and runs.
