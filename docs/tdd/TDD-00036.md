# TDD-00036: Freestanding microcontroller target (Raspberry Pi Pico) — minimal core

- **Status**: Not Started
- **Date**: 2026-08-07

## Context

A stretch-goal exploration, explicitly low priority relative to this project's core-language blockers (modules, type system, generics V2 — see `CLAUDE.md`) but recorded now because the shape of the problem is worth having on record, in the same spirit as [TDD-00020](TDD-00020.md) (Windows) and the UI-direction placeholders ([TDD-00031](TDD-00031.md)/[TDD-00032](TDD-00032.md)/[TDD-00033](TDD-00033.md)). The motivating case: hobbyists who want to write small programs for a microcontroller like the Raspberry Pi Pico without touching C or Python. [KalumaJS](https://kalumajs.org/) already occupies this niche as a JS *interpreter* for microcontrollers; this compiler's AOT-to-native-code model plus real DWARF debug info is a plausible differentiator (real breakpoints/variable inspection over SWD via `gdb`/`lldb` and a picoprobe, instead of debugging through an interpreter's own tooling) — but that's a product hypothesis, not something this document verifies.

Every platform this project targets or has scoped so far — macOS, Linux, and (per [TDD-00020](TDD-00020.md)) Windows — is a **hosted** target: a real OS, a real libc, processes, a filesystem, virtual memory. `main.go` never emits an explicit `-target` triple and just shells out to `clang -O2 <file.ll> -o <out>`, and every `runtime_*.go` file is written directly against POSIX/BSD APIs (or, for Windows, scoped as a port of the same POSIX-shaped concepts onto Win32 equivalents). A microcontroller like the RP2040 (original Pico: dual Cortex-M0+, no FPU, 264KB SRAM, no MMU) or RP2350 (Pico 2: dual Cortex-M33 or Hazard3, has FPU, 520KB SRAM) is **freestanding**: no OS, no processes, no filesystem unless one is built on top of raw flash, no virtual memory, and RAM measured in hundreds of kilobytes rather than gigabytes. This isn't "a third hosted platform" — it's a different category that breaks assumptions baked into nearly every `runtime_*.go` file: no `malloc` from a real libc, no `setjmp`/`longjmp` guaranteed, no `pthread` (which Boehm GC's stack-bottom detection depends on — see `CLAUDE.md`'s ADR-00080 reference), no sockets, no `fork`/`exec`, no filesystem syscalls.

**Scope boundary — this document covers the minimal core only.** "Minimal" means: enough of a toolchain and runtime to compile a KlainMainLang program that blinks an onboard LED and prints to a USB-serial console, proving the `klainmain` → LLVM IR → freestanding ELF → flashable image pipeline works end to end. Full stdlib parity — networking via lwIP on Pico W, a filesystem via LittleFS over onboard flash, a broader hardware peripheral surface (PWM/ADC/I2C/SPI) — is deliberately **out of scope** here. Those are each their own later TDD once this minimal core exists and there's real hardware experience to design against, rather than speculative later "stages" of this same document — matching this project's existing practice of one TDD per real design decision (the event loop, `-mm=gc`, the HTTP server all got separate docs) instead of one document trying to pre-solve unrelated problems at once.

## Design

### Toolchain

- **Target triple**: `thumbv6m-none-eabi` (RP2040/Cortex-M0+) or `thumbv8m.main-eabi` (RP2350/Cortex-M33). Recommend RP2040 first — simpler core (no FPU to reason about in codegen), the original and still most common board, and by far the larger tutorial/community base if this ever needs outside debugging help. RP2350/Pico 2 support, if ever picked up, should follow as a second target once the M0+ path is proven, not built in parallel.
- Cross-compilation is effectively mandatory, unlike the Windows TDD's native-vs-cross-compile fork — an RP2040 obviously cannot run the Go toolchain or `clang` itself. `klainmain` keeps running on the existing macOS/Linux dev machines and emits IR for the Pico target.
- clang already ships an ARM Cortex-M backend (no new compiler dependency) — the gap is the same one [TDD-00020](TDD-00020.md) names for Windows: `main.go` never emits an explicit `-target`, and would need a new flag (e.g. `--target=pico`) that both selects the triple and changes what output step runs next (see below).
- **Build on the Raspberry Pi Pico SDK (`pico-sdk`), not true bare-metal from scratch.** `pico-sdk` already provides the linker script (placing the vector table and stage-2 bootloader correctly in flash), the boot2 blob, clock/PLL init, and a `-nostdlib`-friendly minimal libc (picolibc). Reimplementing that from first principles would be a large undertaking almost entirely unrelated to what this project is actually about. This mirrors the project's existing posture toward Boehm GC and libcurl: build on an established C library for the hard, unrelated-to-language-design parts rather than reinvent them.
- **Output step is fundamentally different, not just a different `-target`.** Desktop compilation ends at a directly-executable binary; a Pico target ends at an ELF that must be linked against `pico-sdk`'s memory layout and then either converted to a `.uf2` file (drag-and-drop flashing over the Pico's BOOTSEL USB mass-storage mode) or flashed via SWD (`picotool`/OpenOCD + a picoprobe). `main.go`'s "run clang, produce a binary, done" flow needs a real new terminal step, not a flag tweak.

### Minimal runtime surface

| Concern | Desktop today | Pico minimal-core plan |
|---|---|---|
| `console.log` | libc `printf` to stdout (`emit_call_console.go`) | `pico-sdk`'s `stdio_init_all()` + `printf` over USB CDC (or UART) — `pico-sdk` already wires this, so the existing printf-based console codegen likely reuses close to unchanged once linked against picolibc instead of glibc/libSystem |
| `malloc`/`free` | libc (`runtime_core.go`) | `pico-sdk`/picolibc ship a heap allocator over unused SRAM; same C call shape, needs validating it actually resolves under this toolchain |
| `-mm=gc` (Boehm GC) | `LocateGC()`, pkg-config | **Out of scope for the minimal core** — Boehm's stack-bottom detection depends on `pthread`, which doesn't exist here. `manual` mode only, at least initially |
| `try`/`catch` (`setjmp`/`longjmp`) | glibc/libSystem | Unverified against picolibc — may stay out of the minimal core rather than assumed to work (see Open questions) |
| `fs.*`, `process.*`, `fetch`/`URL`, `http.listen`, sockets, `Date` (wall-clock) | POSIX syscalls / libcurl | **Out of scope entirely** for the minimal core — no OS underneath any of these. Must be a hard compile-time error under this target, not a silent miscompile or a runtime crash |
| GPIO | Doesn't exist today | **New surface**, the actual point of targeting a microcontroller at all — a thin binding to `pico-sdk`'s `gpio_init`/`gpio_set_dir`/`gpio_put`/`gpio_get`. Exact language-facing shape is an open question below |
| Program entry/exit | `main()` returns, process exits with a code | Doesn't map cleanly — embedded programs normally run forever. Needs a small runtime wrapper around emitted `main()` that loops (or halts) rather than returning, since "exit code to a shell" isn't a concept that exists here |

### Compile-time target gating

This needs a genuinely new mechanism, not an extension of the existing `runtime.GOOS`-branching pattern (which assumes "some hosted OS", just a different one) or the Windows TDD's "port this subsystem" framing (which assumes the subsystem still makes sense, just needs a different OS API underneath). Most of today's stdlib — `fs`, `http`, `fetch`, `URL`, `process`, `-mm=gc` — has **no equivalent at all** under `--target=pico`, so referencing any of it must be a clean compile-time error naming the target as the reason, the same "clean rejection over a silently-wrong feature" preference [TDD-00020](TDD-00020.md) leans toward for `SIGTERM` on Windows.

## Open questions

- **RP2040 vs RP2350 as the first target** — Design above recommends RP2040/Cortex-M0+ for simplicity and community size, but this isn't decided.
- **`pico-sdk` vs true bare-metal from scratch** — Design recommends `pico-sdk`; worth stating explicitly as a real fork someone could reasonably disagree with, given this project's general preference for building things itself where feasible.
- **GPIO binding shape**: a small hand-written binding (the same one-off pattern libcurl already uses for `fetch`) vs. waiting on general FFI ([TDD-00032](TDD-00032.md)'s blocked prerequisite). GPIO's real surface is tiny (a handful of functions) compared to a GUI toolkit, so a hand-written binding seems clearly justified without waiting on FFI — but not decided.
- **Whether `try`/`catch` is worth supporting in the minimal core at all** — embedded programs often prefer to halt/reset on a fatal error rather than unwind; `setjmp`/`longjmp` support on picolibc is also simply unverified. Could reasonably be deferred past the minimal core regardless of the verification outcome.
- **Testing story with no CI-friendly hardware target.** Every other platform this project supports can be tested by a CI runner (native Linux/macOS, or Wine for the Windows cross-compile path per [TDD-00020](TDD-00020.md)). QEMU has partial, community-maintained RP2040 support of unclear current quality — unresearched. Absent that, this may only ever be testable manually by whoever has physical hardware, which is a real departure from this project's normal "flip the status page row once tests pass" workflow.
- **Whether `pico-sdk`'s own build system (CMake) needs to be shelled out to from `main.go`**, or whether `clang` can be invoked directly against `pico-sdk`'s headers and prebuilt objects without going through a full CMake configure/build. This likely determines a large fraction of the real implementation effort and hasn't been researched.
- **Code size and stack usage genuinely matter here** in a way they never have for this compiler before — 264KB of total SRAM (RP2040) including the stack, versus gigabytes on any desktop target. Whether `-O2`'s usual inlining behavior needs revisiting for this target (e.g. `-Os`) is unresearched.
