# ADR-00658: -compat=js constructor params widen to any on call-site disagreement

- **Relations**: Extends ADR-00656, ADR-00653
- **Date**: 2026-09-03

## Context

The two-lane Test262 report (ADR-00656) exposed that `-compat=js` fails a set of
files the strict lane accepts — starting with five in
`language/expressions/assignment`, all rejected with `constructor argument 1 of
'new Test262Error(...)' disagrees with another call site's type — annotate the
constructor parameter`. That is backwards: `-compat=js` is meant to be *more*
permissive than strict (it accepts vanilla untyped JS), so it must be at least
as accepting as strict, which has no such rejection.

## Investigation

`jsCollectCtorParamTypes` (`codegen/llvm/emit_classes_jsinfer.go`) is a
`-compat=js`-only pre-pass that infers each unannotated constructor parameter's
type from the `new C(...)` argument types across the program. It kept the first
inferred type per parameter and **hard-errored** when a later call site
disagreed. The Test262 harness constructs `new Test262Error('msg')` in one place
and `new Test262Error('msg' + n)` in another, so the `message` parameter is seen
as two different concrete types — a hard error under js, while strict (no such
pre-pass) compiles it.

This directly contradicts the sibling plain-function pass: a plain function
whose call sites disagree already widens the parameter to `any`
(`TestE2EJSModePolymorphicParamBecomesAny`). Constructors were the outlier.

## Decision

On call-site disagreement, **widen the constructor parameter to `any`** instead
of rejecting — matching the plain-function behavior and vanilla-JS semantics (a
constructor may receive different types at different sites). Once widened the
slot is `any` (`IsDynamic`), so a third disagreeing site does not re-trigger.

A function-constructor's `this.field = param` lives on a D1 dynamic object,
which stores the widened `any` — so the real harness case (`Test262Error`)
compiles and runs. A `class` (fixed-shape struct) instance still cannot hold an
`any` field, so a genuinely polymorphic *class* constructor parameter stored to
a field now surfaces the pre-existing "any is not yet supported as an object
field type" error instead of the call-site message — still a clean rejection,
not a miscompile; supporting `any` class fields is separate (D1-for-classes).

## Implementation notes

- `emit_classes_jsinfer.go`, `jsCollectCtorParamTypes`: the disagreement branch
  sets `slots[i] = TypeAny` (guarded by `!slots[i].IsDynamic`) instead of
  returning an error. `TypeAny` flows through `jsApplyCtorParamOverride` /
  `jsInferConstructorFields` as the parameter/field type unchanged.

## Side effects discovered

The full-corpus two-lane run showed the js lane **−1367 in-scope vs strict** —
compat=js regresses far more than the 524 strict rejections it should recover.
This one fix closes the constructor-disagreement slice; the remaining gap is a
broad compat=js completeness effort (many independent causes), tracked as
follow-up under TDD-00022, not attempted here.

## Verification

- The five `language/expressions/assignment` files that failed only under
  `-compat=js` now compile and run under it.
- `TestE2EJSModeConflictingCallSitesWidenToAny` (was
  `TestJSModeConflictingCallSitesRejected`, inverted from a rejection assertion
  to a run assertion, function-constructor form); the jsmode + classes suites
  stay green. macOS (Apple Silicon).
