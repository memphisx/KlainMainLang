# TDD-00182: Windows owned handle table + event-loop reactor

- **Status**: Superseded after Stage 1 — Stage 1 shipped ([ADR-00864](../adr/ADR-00864.md)): the owned, kind-tagged fd descriptor table (the five parallel `kfd_*` arrays consolidated into one array-of-structs reached through accessors) + `fstat(fd)` kind dispatch (a socket/pipe/console fd now stats correctly instead of `EBADF`/failure). Stages 2–6 (unified wait object, overlapped pipe I/O, console-input thread, description refcounting, timer resolution) are **superseded by [TDD-00183](TDD-00183.md)** (the IOCP reactor), which builds directly on Stage 1's table and delivers those stages' goals under the completion model instead of the readiness wait — building the `WaitForMultipleObjectsEx` path first would now be throwaway work.
- **Date**: 2026-09-07

## Context

[TDD-00180](TDD-00180.md) audited the shipped Win32 platform layer against libuv/Node and reached one structural conclusion: the toolchain held, the incremental gaps are a list, but **one decision is worth revisiting — routing non-socket I/O through the CRT fd table**. Every finding in that audit's §1 (Event loop and stdio) descends from it:

- Reading `process.stdin` or a child's stdout pipe falls to CRT `_read` and **blocks the whole event loop** until a line or EOF (`win32io.c` `plain_read`, `runtime_stdin.go`).
- Console input reports readable on *any* input record (key-up, focus, mouse) via `WaitForSingleObject` on the console handle (`win32io.c:645-648`), then the read blocks until Enter; non-ASCII input comes through the CRT in the input code page, not `ReadConsoleW`→UTF-8 (§2).
- With a pipe or console watched, the emulated `select()` never truly waits — it busy-slices at **10 ms** (50 ms with a console-ctrl handler), because plain fds have no wait object the loop can block on and be woken from (`win32io.c:715-717`, `Sleep(slice)`).
- Plain fds are declared always-writable (`win32io.c:706`), then `_write` blocks on a full pipe; child stdio are synchronous 4 KB anonymous pipes.
- `fs.fstatSync(0)` on a pipe/console returns `EIO` because `GetFileInformationByHandle` is called before any `GetFileType` kind dispatch.
- A fixed **384-socket cap** (fds `[512, 896)`) and `dup2`-of-socket **aliasing** (a raw `SOCKET` copied, so closing either fd closes both) both follow from the fd-range partition rather than an owned, refcounted description.
- Timer deadlines use `GetTickCount64`, a **15.6 ms** tick.

The current `select()` (`win32io.c:672-760`) is a poll emulation: sockets go through Winsock `select`, plain fds are probed with `PeekNamedPipe`/`WaitForSingleObject` each pass, and the loop spins in short slices because the two families cannot share one blocking wait. This is the "readiness by polling" shape; a faithful reactor waits once and is woken by the source itself.

It is scoped now because the pieces around it are in place. The incremental §2–§6 pile is nearly cleared (console encoding, `child_process` shell/exit-code, fs sharing/long-paths/errno, `TCP_KEEPIDLE` — [ADR-00736](../adr/ADR-00736.md) through [ADR-00760](../adr/ADR-00760.md)), leaving this as the one remaining structural item. Crucially, its central missing primitive — a **loop wakeup channel** — was built for `fs.watch`: [ADR-00757](../adr/ADR-00757.md)'s loopback socketpair is exactly the "wake the wait from another thread" mechanism the audit flagged as absent, and it already folds into the `select()` set. This TDD elaborates the audit's recommended **Option A** into an implementable design.

## Design

### The two options (from TDD-00180), restated

- **Option A — own the fd table, keep the readiness/`select` shape.** Replace CRT fds with a private table of `HANDLE`s carrying a kind tag; read overlapped pipes and a console-input thread; wait once on a unified wait object that the wakeup channel can signal. The reactor stays `select()`-shaped, so `runtime_net.go`/`runtime_http.go`/`runtime_stdin.go` are **untouched**.
- **Option B — IOCP reactor.** libuv's model: overlapped `WSARecv`/`AcceptEx` for sockets too, one `GetQueuedCompletionStatusEx`. Faithful and scalable, but the socket helpers change from readiness to completion, reaching into the IR-level net/http/TLS paths.

This TDD commits to **Option A**, for the reasons TDD-00180 gave: it is the smaller change, it removes the CRT from the I/O path entirely (the actual faithfulness debt), and — designed carefully — its handle table and wakeup object are what an IOCP reactor would reuse anyway. Option B is **not shelved by this choice**: it is a committed follow-on, sequenced after A and scoped in its own [TDD-00183](TDD-00183.md) (lower priority than A, but a tracked goal, not deferred). A is therefore designed so B builds on it — see Open question 5.

### Core: an owned handle table

Extend the ownership that sockets already have (`kfd_kind`/`kfd_sock_handle`, fds `[512, 896)`) to *every* non-CRT fd. One table keyed by fd, each slot carrying:

- `HANDLE h` — the real OS handle (file, pipe, console, or the `SOCKET` for socket kinds).
- `kind` — `FILE`, `PIPE_ANON`, `PIPE_NAMED`, `CONSOLE_IN`, `CONSOLE_OUT`, `SOCKET`, `FOREIGN` (the enum already exists: `KFD_PLAIN/SOCKET/PIPE/FOREIGN`, extended).
- `flags` — non-blocking, append, a per-handle read/write overlapped state, and a **refcount / shared description** so `dup2` aliases a description rather than copying a raw handle.

Because the table owns the handle and its kind, the fixed `[512, 896)` socket partition dissolves: any fd slot can hold any kind, tagged. This removes the 384-socket cap and makes `dup2` a description-share (`close` decrements; the handle is closed once). It also resolves `fstat(fd)` — dispatch on `kind` (FIFO / char-device / regular) *before* `GetFileInformationByHandle`.

### The wait primitive: one blocking wait, woken by the source

Replace the poll-slice loop with a single wait. Two families must be waited on together — OS handles (pipes, console, files-are-always-ready) and Winsock sockets — which cannot share one native wait call directly. The design:

- **Sockets** join the wait via `WSAEventSelect(s, hEvent, FD_READ|FD_WRITE|FD_ACCEPT|FD_CONNECT|FD_CLOSE)`, turning each watched socket into an auto-reset event.
- **Pipes/console** contribute their own handles (overlapped read completion events for pipes; the console input handle or its reader-thread event for `CONSOLE_IN`).
- **The wakeup object** — a generalisation of [ADR-00757](../adr/ADR-00757.md)'s loopback socketpair to a single process-wide auto-reset `Event` — is always in the set, so any background thread (the `fs.watch` watcher, a console-input thread, a future overlapped completion) wakes the loop immediately, killing the 10 ms spin.
- The loop calls `WaitForMultipleObjectsEx(handles, …, alertable=TRUE, timeout)`; the `select()` contract (`nfds`, three fd-sets, a `timeval`) is preserved as a thin translation over this wait, which is what keeps the IR-level callers unchanged.

`WaitForMultipleObjects`' **63-handle limit** (`MAXIMUM_WAIT_OBJECTS − 1`, one slot reserved for the wakeup) is the one scaling wrinkle. Options, in Open questions: a `RegisterWaitForSingleObject` thread-pool fan-out; libuv's pre-IOCP "one helper thread per 63 handles, each signalling the wakeup" grouping; or simply retaining Winsock `select()` for the *socket* subset on a helper thread that signals the wakeup, and reserving the native wait for the (few) pipe/console handles. The last is the smallest step from today's code.

### Reads and writes without blocking the loop

- **Pipes** (anonymous child stdio and named): overlapped `ReadFile`/`WriteFile`. A read is posted; its completion event is in the wait set; `read()` returns the buffered bytes without blocking. Writes go through a bounded per-fd queue so a full pipe reports "not writable" (via the description's queue state) instead of blocking `_write`. This is what makes `process.stdin` and child-stdout streaming faithful.
- **Console input**: a dedicated reader thread doing `ReadConsoleInputW`, filtering to real key-down character events, decoding to UTF-8, and buffering — signalling the wakeup on data. This fixes both the "readable on any input record" bug and §2's non-ASCII console input in one move. (Interaction with the existing ConPTY harness and `setRawMode` is an Open question.)
- **Files** stay synchronous and always-ready, exactly as POSIX treats regular files.

### Timer resolution

`WaitForMultipleObjectsEx`'s timeout is milliseconds, but the system tick still bounds it at ~15.6 ms. Fix with `timeBeginPeriod(1)` around the loop, or a waitable timer for the next timer deadline. Called out as its own sub-item, not on the critical path.

### Suggested staging

Each stage is independently shippable, verifiable on the CI Windows lane, and leaves the `select()` contract intact:

1. **Owned table + kind tags**, sockets/foreign migrated into it; no behavioural change (dispatch still matches today). Unblocks `fstat(fd)` kind dispatch as a first visible win.
2. **Unified wait object** (auto-reset Event + `WaitForMultipleObjectsEx` for pipe/console; sockets via `WSAEventSelect` or a helper-thread `select`), folding in the [ADR-00757](../adr/ADR-00757.md) wakeup. Removes the 10 ms / 50 ms spin. This is the reactor's heart.
3. **Overlapped pipe reads/writes** — non-blocking stdin and child-stdout, queued (non-blocking) pipe writes.
4. **Console-input thread** — correct readability + `ReadConsoleInputW`/UTF-8 (also closes §2 non-ASCII input).
5. **Description refcounting** — `dup2` aliasing fixed, the 384-socket cap dropped.
6. **Timer resolution** — `timeBeginPeriod`/waitable timer.

### Implementation-host note

Per TDD-00180's own recommendation and the standing Windows dev direction, this is **not** to be started from the Windows box: it is designed here so it can be built (and its handle table / wakeup object shaped for a later IOCP reactor) when the platform work resumes deliberately, with the CI Windows lane as the regression guard.

## Open questions

1. **>63 watched handles**: `RegisterWaitForSingleObject` pool, libuv's 63-handle helper-thread groups, or retain Winsock `select()` for the socket subset on one helper thread (smallest step) and native-wait only the pipe/console handles?
2. **Internal contract**: keep the `select()`-shaped shim (zero IR churn) or introduce a small explicit readiness API the reactor and IR agree on — the latter eases a future IOCP swap but touches the callers Option A was chosen to protect.
3. **Sockets in the unified wait**: `WSAEventSelect` every socket (fully spin-free, but the handle-count problem) vs. keep Winsock `select()` for sockets and only native-wait the non-socket handles + wakeup?
4. **Console input timing**: build the reader thread now, or defer until the ConPTY/`setRawMode` interaction is settled — and how it coexists with the existing resize watcher thread ([ADR-00749](../adr/ADR-00749.md)).
5. **Shaping A's table for IOCP (Option B) reuse**: B is a committed follow-on ([TDD-00183](TDD-00183.md)), so A's owned handle table, refcounted descriptions, and wakeup object **must** be designed for B to build on (B replaces A's `WaitForMultipleObjects` wait with a completion port but reuses the table). The open part is only how far to go now — how much of the description shape to fix in A's Stage 1/5 vs. adjust when B lands.
6. **Timer resolution**: process-wide `timeBeginPeriod(1)` (raises the global tick rate, power cost) vs. a per-deadline waitable timer (localised, more code).
