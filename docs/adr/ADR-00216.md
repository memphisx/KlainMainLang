# ADR-00216: `bigint` V1 — arbitrary-precision integers behind a selectable backend

- **Date**: 2026-08-18
- **Relations**: Implements [TDD-00074](../tdd/TDD-00074.md)

## Context

`bigint` was the last unimplemented primitive on `docs/status/TYPE-SYSTEM.md` (Type primitives 11/12). [TDD-00074](../tdd/TDD-00074.md) scoped it: arbitrary-precision integers exposed through a backend-agnostic `__kml_bigint_*` ABI, with the concrete bignum implementation chosen by a whole-program `-bigint=<backend>` flag (the same posture as `-mm=`/`-regex=`/`-globals=`). The design deliberately keeps the codegen ignorant of which library is underneath, so additional backends are additive.

## Investigation

- The `symbol` primitive (`emit_symbol.go`, `IsSymbol`) was the closest existing template for adding an opaque primitive: a `Type` flag plus a handful of special-cased dispatch sites (typeof, stringification, JSON, operators). bigint adds one thing symbol didn't need — a **literal** (`123n`) — so it also touches the lexer/AST/parser.
- The `-mm=gc` allocator shim (`gcsrc/gcshim.c`, `//go:embed` + compiled alongside the `.ll` by `main.go`) was the template for shipping a backend as an **embedded C file compiled with the program**, rather than hand-written LLVM IR calling the library. Hand-writing IR over `mpz_t`/`mp_int` structs would have been far more error-prone; a C wrapper over the library's own header is trivial to get right.
- Backend availability on the dev machines: **GMP** installs via the system package manager (`-lgmp`), **libtommath** likewise (`-ltommath`), but **libbf** (the TDD's intended MIT default) is *not* a system package — it is a single-file library bundled inside QuickJS, so it must be vendored. That reality reordered the delivery (see Decision).

## Decision

**Ship V1 with two system-library backends — `libtommath` (default) and `gmp` — deferring the vendored `libbf`.** The TDD named `libbf` (MIT) as the eventual default for licensing reasons; since it needs vendoring and could not be linked/validated on the dev machine, V1 makes **`libtommath` (public domain)** the default instead. This preserves the actual requirement that drove the TDD's choice — *a license-clean, no-copyleft default* — while being installable and testable today. `gmp` (LGPL, faster) is the explicit opt-in. `libbf` remains the planned follow-on; whether it becomes the default is left open.

**The backend-agnostic ABI is the load-bearing decision.** All codegen — operators, `typeof`, stringification, JSON, truthiness, literals — is written once against a fixed set of `__kml_bigint_*` functions over an opaque `ptr` handle. Each backend is one C file (`bigintsrc/bigint_tommath.c`, `bigint_gmp.c`) implementing that ABI; `main.go` writes the selected file next to the `.ll` and compiles+links it, only when the program used bigint. Adding `libbf` later is a new C file plus a flag value, with zero codegen change.

**Non-interoperability with `number` is a compile error, not a runtime throw.** Real JS `TypeError`s on `10n + 1`; as a statically-typed compiler this is caught at the operator site. Across-type `===`/`!==` resolve to a constant (a bigint is never `===` a non-bigint). `>>>`, unary `+`, and `JSON.stringify` on a bigint — all `TypeError`s in JS — are likewise clean compile errors.

Rejected, per the TDD: fixed `i128` (silent overflow) and hand-rolled bignum (disproportionate effort against the RegExp/PCRE2 "link a mature library" precedent).

## Implementation notes

- **Frontend**: `lexer/token.go` (`BIGINT` token); `lexer/lexer.go` `readNumber` recognizes a trailing `n` on hex/bin/oct/decimal integers (rejecting it on a float or legacy-octal form) and adds `BIGINT` to `regexIllegalAfter` so `5n / 2n` lexes as division, not a regex; `ast/nodes.go` `NumberLiteral.IsBigInt` + `NewBigIntLiteral`; `parser/parser_literals.go` maps the token.
- **Type system**: `types.go` `IsBigInt` flag + `BigIntType()` (an opaque `ptr`, deliberately not `IsObject`) + `ResolveTypeName("bigint")`; `typeofString` → `"bigint"`; `inferExprType` and the var-declaration inference (`emit_exprs_vardecl.go`, for both a `123n` initializer and a `BigInt(...)` call) return bigint.
- **Codegen** (`emit_bigint.go`): literal lowering (prefix→radix, `from_str`), the `emitBigIntBinary` operator dispatch, `emitBigIntUnary`, `emitBigIntToString(suffix)` (the console-`n` vs `String()`-bare split), the `.toString([radix])` method (`emitBigIntToStringMethod`, lowercasing the backend's digit letters to match JS), `BigInt()` construction, a catchable div/modulo-by-zero guard (`emitBigIntDivZeroGuard`, reusing `emitInternalThrow` exactly like the i64 `emitDivZeroGuard`), and `ensureBigInt` (the one-time `declare`s). Dispatch sites: `emitBinary`/`emitArith`/`emitUpdate`/`emitUnary` (operators, compound assignment, `++`/`--`), `toBool` (0n falsy), `emit_call_console.go` + `emit_exprs_types.go` (print split), `emit_call_json.go` (reject), `emit_call.go` (`BigInt(...)`).
- **Backends & wiring**: `bigint.go` (`//go:embed` of both C files, `BigIntBackendSource`, `LocateBigInt` — `brew --prefix` for the Homebrew include/lib path, `-Wno-unused-result` to keep the build clean); `main.go` `-bigint` flag + validation + compile/link; `tests/compiler_test.go` mirrors it via `appendBigIntBackend` so the test build can't drift from the real build (the same discipline the `-mm=gc` path uses).
- **`/` and `%`**: both come from one truncating division (`mp_div`/`mpz_tdiv_*`) so `/` truncates toward zero and `%` carries the dividend's sign, matching JS — *not* `mp_mod`/`mpz_mod`, which take the divisor's sign.

## Side effects discovered

- Unary `+` is rejected by the **parser** for every operand type (not just bigint), so the bigint-specific unary-`+` guard is currently unreachable — kept as documentation/defense.
- Bare `String(x)`/`Number(x)` conversion calls are a pre-existing general gap (only `String.*`/`Number.*` member calls are handled), so `String(10n)`/`Number(10n)` aren't available; template interpolation and `BigInt()` cover the common needs. Tracked in `docs/status/TYPE-SYSTEM.md`'s bigint caveats.
- Under `-mm=gc`, the backend's internal allocations route through the shim's global `malloc` override transparently, so the TDD's flagged "libtommath has no allocator hook" concern does not bite here — noted for whenever the gc path is exercised with bigint.

## Verification

- `tests/bigint_test.go` — 14 E2E tests (arithmetic incl. truncating `/`/`%`, arbitrary precision, `typeof`, comparisons, bitwise/shift, unary + truthiness, the print split, `BigInt()` + hex/bin/oct/separator literals, functions/arrays/fields/compound-assign/`++`, catchable div-by-zero, `.toString([radix])`, and the three deliberate compile-error rejections). All pass on the default libtommath backend; each Skips rather than Fails if the backend library is absent.
- `examples/bigint/bigint.ts` — runs end-to-end (incl. `huge * huge` and `30!`), wired into `make examples`.
- The identical program compiled with `-bigint=gmp` produces identical output (bitwise, shifts, arbitrary precision, truncating division) — verified manually on macOS (Apple Silicon, gmp 6.3.0, libtommath 1.x).
- `go vet ./...` clean; full `go test ./...` run for regressions (shared paths `toBool`/`emitBinary`/`emitArith`/`emitUpdate`/`emitUnary`/var-decl were touched).
- `make conformance` run per the standing rule.
- Platform: verified on macOS Apple Silicon; not yet re-verified on the Linux box (both backends are Homebrew-installed here; on Linux the distro `libtommath`/`libgmp` packages land on clang's default search path).
