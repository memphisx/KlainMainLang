# ADR-00392: Multi-argument EventEmitter events (TDD-00131 Stage 2)

- **Relations**: Implements TDD-00131; Extends ADR-00089 (TDD-00023)
- **Date**: 2026-08-27

## Context

`EventEmitter` supported at most **one** payload argument per event — real Node's
`emit('data', chunk, size)` with a `(chunk, size) => …` listener was unsupported
("no heterogeneous rest/spread machinery to build it on"). This is a common Node
shape and a portability gap (TDD-00131 EventEmitter stage).

## Investigation

The emitter already had everything needed but hadn't connected it: a **tuple**
type `[A, B, …]` is exactly N heterogeneous values (a fixed-shape struct with
positional fields `"0","1",…`, TDD-00066), and the existing single-payload
storage already carries an arbitrary payload value. No existing code used a
tuple payload as a single argument (the event maps in use are all single-typed),
so a tuple payload could be **defined** as Node's multi-argument event with zero
breakage.

## Decision

An event whose payload type is a tuple `[A, B, …]` — either a single-event
`EventEmitter<[A, B]>` or an event-map field `{ data: [A, B] }` — is Node's
multi-argument event:

- `emit(event, a, b, …)` takes one data argument per tuple element, packing them
  into the tuple payload.
- The listener takes one parameter per element (`(a: A, b: B) => void`); the
  dispatcher unpacks the stored tuple into N arguments when invoking it.

Non-tuple payloads keep the existing single-argument (or zero, for `void`)
semantics unchanged.

## Implementation notes

All in `codegen/llvm/emit_eventemitter.go`:

- `resolveEventEmitterListenerArg`: for a tuple payload, hint each listener
  parameter with its element type and validate the listener's arity/types match
  the tuple elements (instead of the one-argument check).
- `emitEventEmitterEmit`: for a tuple event, accept `1 + len(elements)` arguments
  and pack them via a new `emitBuildTuple` (malloc + store each coerced value at
  its positional field); the loop that invokes each listener unpacks the tuple
  into per-element `cbArgs`/`cbParams` before `emitCBCall`.
- `tupleElemTypes` / `emitBuildTuple` helpers.

The `emit()` arity check is now `>= 1` (was capped at 2) so multi-argument calls
pass, with the exact count enforced per resolved event payload.

## Side effects discovered

- **Labeled tuple elements** (`[loaded: number, total: number]`) are not parsed
  (a pre-existing tuple-grammar gap) — use plain `[number, number]`. Noted, not
  fixed here.
