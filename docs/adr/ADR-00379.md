# ADR-00379: Bitwise/count results return `number`; exact int64 literals (TDD-00123 Stages 2–3, 5)

- **Relations**: Extends [ADR-00377](ADR-00377.md); Implements [TDD-00123](../tdd/TDD-00123.md)
- **Date**: 2026-08-26

## Context

After the Stage 1 `number`→double flip (ADR-00377), the bitwise and shift
operators (`& | ^ ~ << >> >>>`) still produced an `i64` result. In JS these
operators compute in a 32-bit integer domain (`ToInt32`/`ToUint32` on the
operands) but the *result is a Number* — a double. Leaving the result `i64`
reintroduced integer division through the back door:

```
(7 & 6) / (7 & 5)   // JS 1.2 — this compiler printed 1 (i64 & i64, then i64 /)
(1 << 4) / (1 << 1) // JS 8   — printed 8 by luck, but the type was still i64
```

The common `(a & b) / 2` case was already correct only because the literal `2`
is now a float and the mixed-operand promotion in `emitBinary` pulled the
division into the float path. The moment *both* division operands came from a
bitwise expression, the result stayed integer.

## Investigation

`emitBinary` (`emit_exprs_operators.go`) coerced both operands to `TypeI64`,
emitted `and/or/xor i64`, and returned `TypeI64`. `emitBitShift` truncated to
i32 (correct `ToInt32` wraparound) and sign/zero-extended the i32 result back to
`i64`, again returning `TypeI64`. Unary `~` coerced to i64 and `xor i64 …, -1`.
`inferExprType` mirrored all of them as `TypeI64`. The compound-assign twin
(`emitArith`, backing `&= |= ^=`) had its own i64 copy.

## Decision

Compute in the 32-bit integer domain, then `sitofp` the result back to a double
so it is an ordinary `number`:

- **`& | ^`** — `ToInt32` both operands (`trunc i64 → i32`), do the op in `i32`,
  `sitofp i32 → double`. Result `TypeF64`.
- **`~`** — `ToInt32(x) xor i32 -1`, then `sitofp` to double.
- **`<< >>`** — the existing i32 shift result is `sitofp i32 → double` (signed
  Int32).
- **`>>>`** — the result is an unsigned Uint32, so `zext i32 → i64` first, then
  `sitofp i64 → double` (a bare `sitofp i32` would misread a result ≥ 2^31 as
  negative — `-1 >>> 0` must be `4294967295`, not `-1`).

Two shared helpers factor the `ToInt32`/`sitofp` boilerplate: `toInt32(v) →
i32-register` and `int32ToNumber(i32) → TypeF64 Value`. `emitBinary`,
`emitArith`, unary `~`, and `emitBitShift` all route through them, and
`inferExprType`'s `& | ^ << >> >>>` case returns `TypeF64` to match.

Operand `ToInt32` reuses the same `coerce(v, TypeI64)` + `trunc i32` path
`emitBitShift` already used — a large fractional/out-of-range double is not given
JS's exact modular `ToInt32` reduction (an `fptosi` of an out-of-range double is
saturating/poison), the same pre-existing boundary the shift operators carry.
In-range integer-valued doubles (the overwhelmingly common case, and everything
the escape-hatch integer types produce) reduce exactly.

## Decision — Stage 3 (count/index builtins)

`.length` (array/string/tuple/typed-array/`byteLength`), `indexOf`/`lastIndexOf`
(string + array + typed-array), `findIndex`/`findLastIndex`, `search`,
`localeCompare`, and the `push`/`unshift` new-length result all computed an
`i64` and returned `TypeI64`. Each is a Number in JS, and — like the bitwise
ops — leaving them `i64` did integer division whenever *both* operands came from
one of these (`arr.length / other.length`, `s.indexOf(x) / s.length`); the
common `count / literal` case was already saved by Stage 1's float literals and
the mixed-operand promotion.

A single helper `countToNumber(v)` `sitofp`s an `i64`-typed count/index `Value`
to a double (`TypeF64`) and passes an already-float value through. It is applied
at each producer's return site, and `inferExprType` mirrors every one (a new
`.length` case for array/string/tuple/typed-array receivers; the
`indexOf`/`push`/… method cases flipped to `TypeF64`). Consumers that need an
integer (array index, slice/substring bounds, count args) already
`coerce(…, TypeI64)` at the use site — e.g. `emitIndexPtr` `fptosi`s the index —
so no consumer needed a change.

**Left as i64 by design:** callback *index parameters* (`arr.map((v, i) => …)`),
which keep the HOF callback ABI stable and coerce cleanly for indexing;
compiler-internal induction variables; and `Math`/`Number()`/`parseInt`, which
already return the JS-correct double for a float argument (every numeric literal
is a float post-Stage-1) and stay `i64` only for an explicit integer-typed
argument — the escape hatch, by design.

## Decision — integer escape-hatch precision (Stage 5)

Stage 1 made every numeric literal a `float64`, which meant an `int64`/`uint64`
binding seeded from a literal above 2^53 rounded on its way through the double
model — `let a: int64 = 9007199254740993` stored `…992`, defeating the escape
hatch whose entire purpose is exact integers. (A large `uint64` literal was
worse: it emitted invalid IR — `fptoui double 1e+19` — and failed to compile.)

`emitInt64LiteralForTarget(n, ty)` parses the literal's original digit string
straight to a 64-bit integer when the target is an explicit `int64`/`uint64`,
preserving the full value; it is wired into `emitExprWithObjectHint`, so every
typed sink that already threads its target type through the hint (var decl,
object field, function argument, assignment) gets it. Narrow-int targets and
values ≤ 2^53 are unaffected — the double represents them exactly — so the
interception is deliberately limited to the 64-bit case. A plain `number` past
2^53 still rounds, matching JS exactly (`Number.MAX_SAFE_INTEGER`).

Printing an unsigned 64-bit value was also fixed: `Type.PrintfFmt()` and
`emitValueToString` now select `%llu` for an unsigned `i64`, so a `uint64` above
2^63 prints its true value instead of a negative one (`%lld` would misrender the
high-bit-set pattern).

## Implementation notes

- `emitBitShift` now returns `TypeF64`; every caller already treated its result
  as a generic numeric `Value`, so no downstream site needed a change.
- The compound-assign store in `emitArith` coerces the `TypeF64` bitwise result
  back to the assignment target's declared type — an `int32`-typed accumulator
  doing `x &= 3` still stores an `int32`.
- `countToNumber` guards on `v.Ty.IR == "i64"`, so re-wrapping an already-float
  producer (e.g. `charCodeAt`, which independently returns `TypeF64` so an
  out-of-range index can be NaN) is a no-op.

## Side effects discovered

None. The dtoa printer already renders an integer-valued double without a
trailing `.0`, so `console.log(5 & 3)` still prints `1`; only the *type* (and
thus downstream division/modulo) changed.
