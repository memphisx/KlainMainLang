# ADR-00534: `Number.prototype.toPrecision` precision argument is optional

- **Relations**: (none)
- **Date**: 2026-08-31

## Context

`(123.456).toPrecision()` — `toPrecision` with no argument — was a compile
error ("toPrecision takes exactly 1 argument"). Real JS makes the `precision`
argument optional: with it omitted, `x.toPrecision()` returns exactly
`String(x)` (the number's default `toString`). Companion to ADR-00533's `toFixed`
optional-argument fix.

## Investigation

`emitNumberToPrecision` (`emit_strings.go`) required exactly one argument and
always fed it to `sprintf("%#.*g", precision, x)`. The no-argument case is not a
`%g` call at all — the spec routes it straight to `Number::toString`, which this
compiler already implements as `emitValueToString` for a numeric value (JS-
faithful shortest round-trip via dtoa).

## Decision

Accept 0 or 1 arguments; when omitted, evaluate the receiver and return
`emitValueToString(numVal)` — the same rendering `String(x)` / `` `${x}` ``
produce. The one-argument path (the `%#.*g` formatting with the trailing-`.`
trim) is unchanged.

## Implementation notes

`emit_strings.go` only. No inference change — `toPrecision` already returns
`string`.

## Side effects discovered

None. `toExponential()` with no argument remains a required-argument case: its
JS no-arg behavior ("as many digits as needed") does not map onto the fixed
6-digit `sprintf("%e")` default, so it is intentionally left out of this change.

## Verification

`TestE2ENumberToPrecisionNoArg` (new): `(123.456).toPrecision()` → `"123.456"`,
`(1000).toPrecision()` → `"1000"`, `(0).toPrecision()` → `"0"`, cross-checked
against real Node. The existing `TestE2ENumberToPrecision` (explicit precision)
passes. Verified on Mac (Apple Silicon).
