# ADR-00410: `https` module (client) and `stream/web` re-exports

- **Relations**: Extends [TDD-00138](../tdd/TDD-00138.md) (http client), [TDD-00097](../tdd/TDD-00097.md) Stage 8 (streams); Extends ADR-00409
- **Date**: 2026-08-27

## Context

The reclassified Node oracle put `https` (61 files) and `stream/web` (18) in
the MODULE_NOT_IMPLEMENTED failure column. Both are near-free: the http
client (`http.get`/`request`, TDD-00138) is libcurl-backed, so TLS handshake
and certificate verification already come from the URL scheme; and
`stream/web` is Node's module home for the WHATWG stream classes this
compiler already ships as ambient constructors.

## Decision

- `https` resolves as a builtin module with members `get`/`request`, marker
  `https__kml_builtin`, dispatched to the same `emitHTTPClientGet` emitter as
  http's. **Client only**: `https.createServer` is a clean, explicit
  rejection (the HTTP accept loop is not TLS-wrapped — a silent plain-HTTP
  server behind an `https.` name would be a correctness lie), with the
  message pointing at `tls.createServer` / TLS termination as alternatives.
  This is why `https` gets its own marker instead of aliasing
  `http__kml_builtin`: sharing the marker would have made
  `https.createServer` silently create a non-TLS server.
- `stream/web` resolves with members `ReadableStream`/`WritableStream`/
  `TransformStream`/`CompressionStream`/`DecompressionStream`, bound as
  identity in the resolver (same mechanism as `stream`'s class names) so the
  imports are interchangeable with the ambient globals. The queuing-strategy
  classes are not exported (not implemented as constructors).
- Both registered in the Node oracle's supported-module set.

## Implementation notes

`resolver/virtual_modules.go` (markers + member tables), `resolver/rename.go`
(streamweb identity case), `codegen/llvm/emit_call.go` (https dispatch),
`codegen/llvm/emit_exprs_types.go` (https get/request → void),
`tools/conformance/node.go` (supported set).

## Side effects discovered

- One unreproduced segfault (exit 139) on the very first run of the
  `https.get` example against a live host; every subsequent run — including
  byte-identical sources and a deliberate DNS-failure probe (clean `Uncaught:
  Couldn't resolve host name`, exit 1) — behaved correctly. Possibly a
  transient network condition hitting an error path mid-TLS-handshake; not
  chased further, recorded here so a recurrence has a trail.

## Verification

- New E2E tests: `TestE2EHTTPSClientGet` (module wiring against the local
  fixture upstream), `TestE2EHTTPSCreateServerRejected` (clean rejection),
  `TestE2EStreamWebReExports` — all pass (Mac).
- Manual live-TLS verification: `https.get("https://example.com/")` → status
  200, body received (Mac).
- New examples: `examples/http/https_client.ts` (real network),
  `examples/streams/stream_web.ts` (offline) — both compiled and run.
