# ADR-01028: Windows `-mm=gc` — the collector must be told which stack a fiber runs on

- **Relations**: `Extends ADR-00071` (the Boehm allocator shim), `ADR-00099`/`ADR-00100` (fiber stackbottom handling), `ADR-00719` (Win32 fibers); found while delivering [TDD-00183](../tdd/TDD-00183.md) Stage 3
- **Date**: 2026-09-20

## Context

`TestE2EHTTPListenGCModeConcurrentChurn` began failing intermittently on Windows — the server process dying mid-request with `0xC0000005`, the Go client reporting a forcibly-closed connection. It reproduced at roughly one run in two, and the full suite had passed on the same tree earlier the same day, so it read as a flake.

It is not a flake. Reduced, it is: **a `-mm=gc` HTTP server crashes as soon as a collection happens while a connection fiber is running.** No allocation churn is needed — a handler returning `req.path` is enough. What is needed is *concurrency*: one request at a time is clean, six concurrent requests crash almost immediately.

## Investigation

- 45 consecutive runs of the reduced repro: clean at `HEAD`, crashing on the first or second attempt with the Stage 3 working tree; clean under `-mm=manual`; clean under `-mm=gc` with a single connection at a time. So: the collector, plus more than one live connection.
- Every backtrace was the same shape — six frames inside `libgc-1.dll` below `__kml_http_append_conn` → `__kml_event_loop_run`. The fault was a NULL header dereference in the mark phase, and `rbx` held `0x312e312f746e6569`: the ASCII `"ient/1.1"`, a fragment of the `Go-http-client/1.1` request header. The collector was walking HTTP text as if it were a pointer graph.
- Ruling out the obvious suspects, each over 45 runs: AcceptEx (forced to the AFD accept poll), the zero-read arming (forced to the AFD receive poll), the Stage 4 high-resolution timer, description recycling (retired descriptions never reused), and moving every in-flight op off the collector's heap. All still crashed. A validity check on every op the drain dequeued (description inside the pool, plausible kind and fd) never fired, and a check for an interior pointer reaching the shim's `free()` never fired either. The heap was being corrupted by something that was not the fd layer's bookkeeping.
- The answer was in what a Win32 fiber *is*. `__kml_http_append_conn` mallocs a `fiberStackBytes` block and, under `-mm=gc`, points `GC_stackbottom` at its high end before swapping in — correct under `ucontext`, where that block is the stack. On Windows the block is unused: `makecontext` calls `CreateFiberEx`, and the fiber runs on a stack **the OS allocated**, as `win32io.c`'s own struct comment says (`ss_sp` — "unused — Win32 owns fiber stacks").
- So while a connection fiber ran, the live SP was in one region and `GC_stackbottom` in an unrelated heap block. Boehm scans between them. The "stack" it walked was an arbitrary span of address space — request buffers, free heap, unmapped pages — every word of it a pointer candidate. That is why the crash needed a collection during a fiber, why it grew HTTP text into a register, and why the fault landed inside the mark phase rather than anywhere near the code at fault.
- Concurrency is what makes a collection land inside a fiber at all: with a single connection the handler returns before the loop resumes, and with `-mm=manual` nothing scans anything. Stage 3 did not introduce this — `HEAD` has the same hole and happened not to collect in that window. It is a Windows `-mm=gc` bug that has been there since fibers landed (ADR-00719), exposed by a change in timing.
- The same reasoning exposes a second hole. Under `ucontext` a *parked* fiber's stack is a `GC_malloc`'d block reachable from its connection, so the collector scans it like any other object. An OS-owned fiber stack is invisible, so anything live only in a parked frame — a half-read request, a response buffer — is collectable while its fiber waits. Structurally reachable; not observed, because the first bug crashed first.

## Decision

The platform layer tells the collector which stack is in use, since it is the only code that knows.

- **The running fiber.** `swapcontext` re-points `GC_stackbottom` at the stack actually in use *after* each switch, and `kml_fiber_tramp` does the same on a fiber's first entry. The value comes from the TEB's `NT_TIB.StackBase` — the bounds Win32 swaps on `SwitchToFiber` — so it is right for a fiber and for the converted thread alike. Being the last write before execution continues on that stack, it overrides the IR's (POSIX-correct) store without that store having to become platform-aware.
- **The parked fiber.** Before switching away, the live part of the outgoing stack (`SP` to `StackBase`) is registered with `GC_add_roots`, and the registration is dropped on resume. The range is held in `swapcontext`'s own frame — which lives on the very stack being parked — so it needs no table and cannot be lost or mismatched.
- **Keeping Boehm out of `win32io.c`.** The shim must link with no collector present, so it exposes three function pointers that `gcshim.c` — compiled only under `-mm=gc` — fills in from its constructor. In any other build they stay NULL and each fiber switch pays two predictable branches.

Also fixed in passing, same family and found on the way: an in-flight op is memory the kernel owns, and an orphaned one (a re-armed interest, a closed fd) has no reference the collector can see, so it could be recycled under a live operation. Ops and their write payloads now come from the process heap (`HeapAlloc`) rather than the program's allocator — one level earlier than ADR-00351's `GC_base` guard, on the principle that memory crossing into the kernel never belongs to the collector. Two paths released an op by hand rather than through `op_free`, including one that freed it after a synchronous `WriteFile` success — which still queues a completion packet — so both now go through the single release point.

## Implementation notes

`codegen/llvm/win32src/win32io.c` (the fiber/collector section, `swapcontext`, `kml_fiber_tramp`, `op_alloc`/`op_release`) and `codegen/llvm/gcsrc/gcshim.c` (the three hooks, set in the existing constructor). A TEB is read as `(NT_TIB *)NtCurrentTeb()`: mingw declares `struct _TEB` opaque, and a TEB begins with its `NT_TIB`. `GC_stackbottom` carries a deprecation attribute in current Boehm headers and is still the documented way to say "the stack now in use" — the emitted IR writes the same variable — so the assignment suppresses that one warning locally.

Nothing outside Windows is touched: POSIX keeps `ucontext` over a `GC_malloc`'d stack, where both properties already hold by construction.

## Side effects discovered

The generator and coroutine paths swap contexts through the same `swapcontext`, so they inherit the fix; they were exposed to the same bug.

## Verification

Windows 11 (26200), MSYS2 UCRT64 clang. The reduced repro (a `-mm=gc` `klain:http` server, six concurrent connections per attempt, server killed and restarted each attempt) ran 45/45 clean with the fix, against a crash within one or two attempts without it; the original churn handler likewise 45/45. `TestE2EHTTPListenGCModeConcurrentChurn` and the GC-mode suites pass repeated (`-count=3`) runs, and the full `./tests` package passes. Linux: the full `./tests` package passes in Docker (`klain-ci`, Go 1.27.1 + clang 19), 0 failures. macOS: not run, no machine reachable; the change is confined to Windows-only files plus a `_WIN32` block in the GC shim, so CI is the check.
