# ADR-00711: Hash-indexed Map/Set — replace the linear-scan backing store

- **Date**: 2026-09-04

## Context

The first full benchmark campaign (benchmarks/run.sh) put `map_churn` at
~18.1s in every klain mode vs 0.34s under Node at scale 10 — ~55× slower,
by far the worst result of the run. `__kml_map_num_find` /
`__kml_map_str_find` (runtime_collections.go) scanned the dense key array
linearly on every `get`/`set`/`has`/`delete`, so building an n-entry map
was O(n²) — 80 rounds × 30k inserts + 30k gets went quadratic.

## Decision

Keep the dense, insertion-ordered `keys`/`vals` arrays (JS `Map`
iteration order; `keys()`/`values()`/iteration/serialization read them
directly and are untouched) and add an open-addressing hash index over
them:

- Header grows 32 → 56 bytes: `+32 idx` (i64 slots: −1 empty, −2
  tombstone, else entry index), `+40 idxcap` (power of two, starts 16),
  `+48 used` (occupied + tombstones). `size`/`cap`/`keys`/`vals` offsets
  are unchanged, so every out-of-runtime reader keeps working.
- One shared probe per key kind (`__kml_map_num_probe` /
  `__kml_map_str_probe`) returns `{slot, entry}` — the found entry, or
  the insert slot (first tombstone on the probe path, else the
  terminating empty slot). `find` is now a probe wrapper, so `get`/`has`
  needed no change. Linear probing; number keys hash with an xor-fold
  multiply (Fibonacci constant), string keys with FNV-1a.
- `set` appends the entry as before, then writes the index slot and
  rehashes (doubling, tombstone purge) past 3/4 load of
  occupied+tombstones — probes always terminate at an empty slot.
- `delete` keeps the swap-remove of the dense arrays, tombstones the
  deleted key's slot, and re-probes the moved (former last) entry's key
  to repoint its slot at the vacated position.
- `Map.clear`/`Set.clear`/no-arg `removeAllListeners` previously emitted
  a bare `size = 0` store; with an index that would leave stale entries
  aliasing future inserts onto old slots (caught by the existing
  `TestE2EMapClear`/`TestE2ESetClear`/EventEmitter tests). They now call
  a shared `__kml_map_clear` that also resets `used` and memsets the
  index back to empty.

`Set`, the frozen-object tracker, EventEmitter/EventTarget listener maps,
`console.time/count`, and performance marks all ride on the same helpers
and inherit the speedup unchanged.

## Consequences

- `map_churn` scale 10: 18.1s → **0.29s** (~60×), now ahead of Node's
  0.34s in every mode. Checksum identical; a dedicated repro covering
  set/get/update/delete/re-insert/iteration order/`clear` matches Node
  byte-for-byte.
- Full Map/Set/JSON/Console/Event test subset and the Node oracle lane
  are green (oracle count unchanged, as expected for a perf-only change).
- Two same-day follow-up fixes to out-of-line copies of the header
  layout, both found the hard way: the gc-mode frozen-set creator
  hand-builds the header (`GC_malloc_uncollectable` special case) and was
  still 32 bytes — the probe then read a garbage idx pointer on the first
  object-field write, a deterministic segfault in any gc-mode program
  that writes a field (caught by the nbody benchmark); and
  `__kml_map_free` now frees the idx array alongside keys/vals.
- Maps still leak in non-`gc` modes when never explicitly freed; that
  pre-existing gap is part of the benchmark campaign's auto-mode
  findings, tracked separately.
