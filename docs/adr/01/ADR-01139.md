# ADR-01139: TS2304 "cannot find name" against TypeScript's and Node's globals

- **Relations**: `Implements TDD-00230` (P2.7, P3.1); `Extends ADR-01134`, `ADR-01138`
- **Date**: 2026-09-25

## Context

A name nothing declares was left to codegen, which reported "undefined
variable" where it happened to look the name up, or compiled the name as a
builtin whether or not Node has such a global. tsc reports TS2304, "Cannot
find name". Two of the project's own examples were programs tsc rejects this
way:

- `examples/eventemitter/event_map.ts` used `EventEmitter` without importing
  it. Node throws `ReferenceError: EventEmitter is not defined`.
- `examples/language/namespaces_v2.ts` used a namespace's `Kind` outside
  the namespace.

`lib/es.d.ts` declares only what this compiler implements. It cannot decide
TS2304 on its own: a program may name a global TypeScript knows and this
compiler lacks, and that is not a type error.

## Investigation

- **Global names are finite and checkable.** Every global name tsc resolves
  for a Node program comes from TypeScript's library (`src/lib`, already
  fetched at v5.6.3) or `@types/node`. The oracle uses
  `@types/node` 22.20.4. Its globals are:
  - the top-level declarations of its script files (`globals.d.ts`: `var
    process`, `var console`, …);
  - the contents of `global { … }` augmentations inside its module
    declarations (`declare module "buffer" { global { var Buffer … } }`).
- **The declaration parser could not read all of `@types/node`.** It lacked:
  - import types (`import("buffer").Blob`, `typeof import("x").Y`);
  - bodiless functions outside `declare` (`global { function atob(data:
    string): string; }`), which a declaration file allows because it is
    ambient throughout.
- **Names the merged program no longer shows.** On the project's own
  programs (`tools/tsdiag -roots`), the first cut reported 1,059
  diagnostics, none of them real errors:
  - the resolver drops import statements from builtin modules and rewrites
    their uses to internal names (`childprocess__kml_builtin`,
    `url__reexport_kml_builtin`), or leaves them bare (`ServerResponse`);
  - an import-equals alias (`import Cfg = App.Config`) is not bound by the
    binder;
  - the parser erases a `declare class`/`interface`/`type` outright.
- **Type positions are not ready.** Reporting unresolved type names put 78
  false positives on TypeScript's corpus. The checker's type-name scopes
  miss a class's type parameters in its constructor, a generic arrow's type
  parameters, and more.
- **Reporting only on demand misses references.** The checker typed an
  identifier only when a check asked for its type. `console.log(y)` never
  typed `y`, because the call's callee is not typed.

## Decision

- **Fetching and generating the name list.**
  - `tools/conformance/fetch.sh` fetches `@types/node` 22.20.4 from the npm
    registry into `.types-node/` (gitignored).
  - `conform.GlobalNames` collects every global name from both sources.
    `tools/libconform -globals lib/tsglobals.txt` writes the list (1,958
    names), embedded as `lib.KnownGlobal`. The names of the declarations
    the parser erases (`declare type PropertyKey`, `declare class`) come
    from `Program.AmbientNames`.
  - `TestGlobalNamesUpToDate` fails when the list is stale (and skips
    without the corpora).
- **Parser.**
  - The `import("m").A.B<T>` type is a new `ast.ImportType` node. It is
    also accepted after `typeof`. The checker leaves it unanswered, and
    codegen rejects it cleanly.
  - `ParseDeclarations` treats a bodiless function as ambient (as `declare
    function` is): `ambientFunction` is shared by both paths.
  - The parser records the names of the ambient declarations it erases in
    `Program.AmbientNames`.
- **Resolver.** The resolver records, on the merged program, the local names
  that imports from builtin modules bind (`Program.BuiltinImports`). The
  binder keeps the program it bound (`Binding.Program`).
- **Checker.**
  - It reports TS2304 for a value reference the binder cannot resolve, in
    every expression `checkNode` visits.
  - It skips `-compat=js`, where the name is a run-time ReferenceError.
  - It skips names bound where the merged program no longer shows them:
    builtin imports, erased ambient declarations and import-equals aliases.
    It also skips the compiler's own names (a builtin module's
    `…_kml_builtin` marker, the `__kml` prefix).
  - A file's top-level name the resolver mangled (`Kind__kml_mod0`) is
    reported under its source name. That is how a namespace's enum used
    outside it (`Kind.Tall`) is caught: the rename pass mangled the use
    too, but the binder scopes the declaration to the namespace.
  - It skips TypeScript's intrinsic names (`globalThis`, `arguments`,
    `undefined`) and every name in `lib.KnownGlobal`.
  - Each name and position is reported once.
- **`lib/node.d.ts`** starts the Node and web declarations with `console`:
  the methods this compiler implements, in TypeScript's own `Console`
  shape (0 `tools/libconform` divergences). `console.log(y)` is then a
  checked call.
- **Type positions** are not reported yet (BACKLOG).
- **The two examples** now import `EventEmitter` and qualify
  `Geometry.Kind`. tsc accepts both, and `event_map.ts` prints what Node
  prints.

## Side effects discovered

- **A dynamic import's non-literal specifier was not renamed.** In
  `import(p)`, the resolver's rename pass had no case for the call, so `p`
  kept its source name while its declaration was mangled. TS2304 reported
  it; the rename pass now rewrites the specifier (`resolver/rename.go`).
- **Tests relied on names tsc rejects:** an undeclared class in
  `instanceof`, `EventEmitter` without its import, a namespace's `Kind`
  outside it, and `typeof` of an undeclared name. They now import or
  qualify the name, or expect TS2304. `typeof` of an undeclared name moved
  to the `-compat=js` lane, where JavaScript reads it as `"undefined"`.
- **`typeof` a builtin module function** (`typeof readFileSync`,
  `typeof emitter.on`) reads `"number"` where Node reads `"function"`
  (BACKLOG: `typeof` a builtin module function). Their declarations are
  not in `lib/` yet.
- **A namespace's type members leak to the enclosing scope** (BACKLOG):
  the parser desugars them to bare top-level names. The strict lane now
  reports a value use outside the namespace, but a type position and
  `-compat=js` still accept it.

## Verification

- **`tools/tsdiag`:** 1,591 reports, of which 1,589 match tsc's baselines.
  - TS2304: 4 reported, 4 matching.
  - The 2 that don't match are the known Annex B TS2554 cases.
  - The project's programs report 0.
- **Tests.** `TestE2ECannotFindName` covers an undeclared name, a
  block-scoped `let` read outside its block, and a program using a builtin
  import, an import-equals alias, an ambient class and library globals.
  `TestE2ELetDoesNotLeakBlock` now expects TS2304.
- **Parsing.** `parser.ParseDeclarations` now reads every file of
  `@types/node` 22.20.4 and TypeScript's `src/lib`.
- **Test262 and Node-core** are measured with the early errors of
  [ADR-01140](ADR-01140.md), which recovered the parse-negative tests that
  TS2304 had exposed: Test262 strict 7,019 and js 7,769; Node-core strict 61
  and js 63.
