# ADR-00209: `const` requires an initializer; `eval`/`arguments` reserved as strict-mode binding names

- **Relations**: `Extends ADR-00181, ADR-00168` (both shipped the adjacent strict-mode/early-error parameter-name rules and disclosed the remaining binding-name gaps).
- **Date**: 2026-08-17

## Context

Two parser early-error gaps, both in the same "a construct parses fine, but the spec's early-error rule on it isn't enforced" category [ADR-00168](ADR-00168.md)/[ADR-00181](ADR-00181.md) already chipped at:

1. **`const` with no initializer** — `const x;` is an unconditional `SyntaxError` in JS (strict or sloppy alike; a `const` binding can never be left uninitialized). This compiler accepted it silently, allocating an uninitialized `const` alloca.
2. **`eval`/`arguments` as a binding name** — in strict-mode code these two identifiers may not be *bound* by a `let`/`const`/`var` (or a for-of/for-in loop variable), not just used as a parameter name. The parameter-name half was already enforced ([ADR-00181](ADR-00181.md) for class methods, [ADR-00168](ADR-00168.md) for `"use strict"` functions); the binding half was the deferred remainder.

## Investigation

- **`const` initializer**: every single-declarator `const`/`let`/`var` — statement-level and C-style for-init alike — funnels through `parseOneVarDeclarator` (`parser/parser_stmts.go:157`), which parsed an optional `= init` and never checked that a `const` actually got one. The for-of/for-in loop-variable forms, which legitimately have no `= init`, take their own dedicated parsers (`parseForOfBody`/`parseForInBody`/`parseForOfPatternBody`) and never reach `parseOneVarDeclarator`, so the check can live there without touching them.
- **Strict binding names**: the parser has no global strict-mode context (`docs/status/LANGUAGE-CONSTRUCTS.md` records this deliberately), only two local strict sites — a function body whose first statement is a literal `"use strict"` (`bodyStartsWithUseStrict`, `parser_stmts.go`) and an always-strict class body (`parser_classes.go`). Both already looped over *parameters* rejecting `eval`/`arguments`; neither looked at what the body *declares*. A binding can be nested (`if (true) { var eval; }`), so a flat scan of the body's top statements would miss real cases.

## Decision

1. **`const` initializer**: in `parseOneVarDeclarator`, when no `= init` is present and `kind == "const"`, return a `SyntaxError` (`'const' declaration 'x' must be initialized`). Sloppy/strict-independent, matching JS.
2. **Strict binding names**: a small recursive statement walker, `strictBindingError` (`parser_stmts.go`), rejects a `let`/`const`/`var` declaration (`VarDeclaration`/`VarDeclarationList`) or a for-of/for-in loop variable that binds `eval`/`arguments`. It recurses through the control-flow statements that share the body's own lexical scope — blocks, `if`/`else`, all loop bodies, `switch` cases, `try`/`catch`/`finally`, labeled statements — but **stops at a nested function/class boundary**: with no inherited global strict context, a nested function is re-checked on its own terms when it is parsed. Called at both existing strict sites (after the `"use strict"` function-body param loop, and after the class-method param loop).

## Implementation notes

- The walker keys off the same two-name predicate (`strictReservedBinding`) the message text uses, so the error string is centralized in `strictBindingReject`.
- The `switch` on `ast.Statement` guards the typed-nil `*ast.BlockStatement` case (a loop/if body is always non-nil in practice, but `Alternate`/`Init` can be an untyped nil interface, caught by the `case nil` arm) — no panic on an absent branch.
- Class coverage is the main method/constructor path (`fn.Body != nil` guards the abstract-method case). Getter/setter accessor bodies route through a separate class-member branch and are not walked here — a narrow, disclosed remainder, consistent with the "narrow safe subset" the parameter rules already committed to.

## Side effects discovered

- The strict binding walk deliberately does **not** cover *assignment* to `eval`/`arguments` (`eval = 1` in strict code is also an early error), only *binding* declarations — assignment-target strictness needs the same absent global-strict context and is left with the other deferred strict early-errors in [LANGUAGE-CONSTRUCTS.md](../status/LANGUAGE-CONSTRUCTS.md). No valid program is miscompiled by either fix; both only turn a previously-accepted illegal program into a clean rejection.

Existing strict-parameter and `const`-reassignment tests still pass.
