# TDD-00188: Runtime call-frame stack for `console.trace()` / `Error.stack` (a shadow call stack)

- **Status**: Not Started
- **Date**: 2026-09-08
- **Notes**: The runtime-readable stack trace, distinct from [TDD-00073](TDD-00073.md) (DWARF-for-debuggers). Node's `console.trace()` and `Error.stack` produce a *string of `.ts` frames* readable by the running program in an ordinary optimized build — DWARF/`lldb` frames don't satisfy that. The mechanism is a **shadow call stack**: a per-fiber stack of frame records pushed/popped around each user-function body, walked to format `at <fn> (<file>:<line>)`. The hard parts are the `setjmp`/`longjmp` unwind interaction (a `longjmp` to a `catch` skips the normal pops, so try must snapshot and restore the shadow depth) and per-fiber isolation (each ucontext async fiber owns its own shadow stack). Recommended behind a flag (`--stack-traces`), since always-on push/pop is a per-call cost that the CLI/microservice hot path shouldn't pay unconditionally.

## Context

`console.trace(msg)` today prints `Trace: <msg>` to stderr and then *nothing*
— no frames (`emit_call.go`'s `case "trace"` routes to `emitConsolePrint` with
a `"Trace: "` prefix). `Error.stack` is likewise absent: `errorObjType`
(`emit_exceptions.go`) is `{i64 kind, ptr message, ptr name, …}` with no
`stack` field, so reading `err.stack` cannot yield the Node string. Both gaps
share one missing ingredient — a representation of the *current dynamic call
chain* that the running program can read as a string.

This is **not** [TDD-00073](TDD-00073.md). That plan emits DWARF metadata and
builds `-g -O0`/`-Og` so `lldb`/`gdb` can resolve native frames — a
*debugger-time* capability, off in normal builds, and it explicitly rejects a
runtime `backtrace()` as the primary mechanism. Node's `console.trace` /
`Error.stack` are *runtime-time*: the program itself materializes a frame
string in every build, including the default `-O2` one. A native
`backtrace()`/`backtrace_symbols()` cannot faithfully serve this — user
functions compile to symbols like `@alpha__kml_mod0` (no `file:line`), and
`-O2` inlining drops and merges frames — so the output would be neither the
`.ts` function names nor a stable frame set. Per the faithfulness rule, that
divergence is avoidable, so we avoid it: track the frames ourselves.

## Design

### The representation: a per-fiber shadow call stack

A thread-/fiber-local growable stack of **frame records**. Each record is a
pointer to a *static* per-function descriptor plus one mutable field:

- **Static `FrameDesc`** (one per emitted user function, in a read-only global):
  `{ const char *name; const char *file; int32 defLine; }` — the function's
  source name (the un-mangled `.ts` name, not `alpha__kml_mod0`), its defining
  file, and the line of its declaration. Emitted once alongside each
  `define`, costing no per-call work.
- **Live frame slot**: `{ FrameDesc *desc; int32 callLine; }` — `callLine` is
  updated at each call site so a frame can report *where in the caller* the
  next call happened (Node's `at <callee> (<file>:<lineOfCallInCaller>)`).
  V1 may ship `defLine` only and defer per-call-site line precision (see Open
  questions).

`console.trace` / `Error.stack` walk this stack top-to-bottom and format each
record as `    at <name> (<file>:<line>)`, matching Node's indentation and
shape. `Error.stack`'s first line is `<name>: <message>` (e.g.
`Error: boom`); `console.trace`'s is `Trace: <msg>` (already emitted).

### Instrumentation points

- **Function prologue/epilogue** (`emit_func.go`, the `define …` sites): push
  the frame record in the entry block; pop on *every* normal exit. Because the
  emitter's dead-code/terminator model gives functions potentially many `ret`
  points, the pop is cleanest as a single epilogue block that all returns
  branch through — or, more robustly, a depth restore keyed off a saved base
  (see unwinding). Arrow functions, methods, generators, and async fiber
  bodies all get the same treatment.
- **Call sites**: set the current frame's `callLine` to the call's source line
  immediately before the call (cheap store), if per-call-site precision is in
  V1.

### The hard part 1 — `setjmp`/`longjmp` unwinding

`throw` is `__kml_throw`, which `longjmp`s to the nearest try's `setjmp`
(`emit_exceptions.go`: the jmpbuf handler stack, popped by `__kml_throw` on the
throw path). A `longjmp` **skips every intervening function epilogue**, so the
normal pops never run and the shadow stack would be left too deep. Fix: `emitTry`
snapshots the current shadow-stack **depth** into the try frame right after its
`setjmp`, and on the catch path (`setjmp != 0`) truncates the shadow stack back
to that depth before running the catch body. This mirrors exactly how the
jmpbuf stack itself is already managed, and is the single load-bearing
correctness invariant: shadow depth is restored at every `longjmp` boundary,
never relied on to unwind frame-by-frame.

A thrown `Error`'s `.stack` must be captured **at construction time**
(`buildErrorObj`), not at catch time — Node snapshots the stack when the Error
is created. So `buildErrorObj` walks the shadow stack and stores the formatted
string (or a captured frame-array to format lazily) into a new `errorObjType`
`stack` field.

### The hard part 2 — per-fiber isolation

Async uses ucontext fibers (`emit_async.go`, `emit_generators.go`, the fs/http
fiber paths). A single global shadow stack would interleave frames across
fibers on every `swapcontext`. Each fiber must own its shadow stack: either a
fiber-local pointer swapped in the scheduler's context-switch, or the stack
hung off the fiber control block. The scheduler already swaps a small amount of
thread-local reactor state (the http-in-goroutine work, ADR-00616's
`LockOSThread`) — the shadow-stack pointer joins that swap set. Worker threads
and `klain:sync` goroutines each need their own, same as the GC registration
already does per thread.

### Options considered

- **A — shadow call stack (recommended).** Above. Pros: format-faithful (real
  `.ts` names + `file:line`), works in every build including `-O2`,
  self-contained (no debug-info shipping). Cons: per-call push/pop cost and a
  small code-size bump; the unwind/fiber bookkeeping above.
- **B — runtime DWARF + libunwind symbolization.** Ship debug info (ride
  TDD-00073) and unwind + symbolize at `console.trace`/throw time. Pros: zero
  per-call cost when not tracing. Cons: needs `-g` in normal builds (fights
  TDD-00073's `-O0` framing), `-O2` inlining still corrupts frames, heavy
  runtime dependency, and the symbol names are the mangled emitted symbols
  unless a name side-table is shipped anyway — at which point most of A's cost
  reappears. Rejected as primary.
- **C — hybrid.** A, but frame records carry only `defLine` (no per-call-site
  `callLine`), so call sites emit nothing. Pros: near-A fidelity at lower cost
  and simpler codegen. Cons: the `(file:line)` is the callee's *definition*
  line, not the call site — a visible divergence from Node. Viable as the V1
  cut of A, promoting to full `callLine` later.

### Flagging and default

Always-on push/pop taxes the hot path for a feature most CLI/microservice code
never reads. Ship behind `--stack-traces` (off by default), matching the
mode-flag style (`-mm`, `--debug`). When off: `console.trace` keeps today's
message-only line, and `Error.stack` is the empty string (or absent) — the
current behavior, now documented as flag-gated rather than unimplemented. When
on: full frames. (Open question: whether a cheap always-on variant — C with a
tiny fixed-depth ring — is worth making the default so `Error.stack` is never
silently empty.)

## Open questions

- **Per-call-site `callLine` in V1, or ship Option C (defLine-only) first?**
  C is materially simpler and still names the right functions; the line just
  points at the definition, not the call. Leaning C for V1, promote to full A.
- **Flag-gated off by default, or a cheap always-on ring so `Error.stack` is
  never empty?** Node programs sometimes log `err.stack`; an empty string there
  is its own fidelity gap. A bounded always-on frame count (e.g. last N) might
  be the honest default.
- **Depth cap / recursion.** A runaway-recursion program would grow the shadow
  stack unboundedly (as Node's does until its own limit). Cap at a
  configurable depth and elide the middle with `... N more frames` like Node's
  `Error.stackTraceLimit`?
- **`Error.captureStackTrace` / `Error.stackTraceLimit`** — do we implement the
  V8 static API surface, or just the `.stack` property? Likely `.stack` first,
  the static helpers as a follow-on.
- **Interaction with `-optimize-memory` / escape analysis** — the shadow-stack
  push is a side effect the escape checker must not treat as making the frame
  descriptor escape (it's a static global) nor reorder past a throw.
