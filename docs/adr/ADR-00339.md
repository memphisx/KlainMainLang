# ADR-00339: Streaming `process.stdin` — the `'data'`/`'end'` events

- **Relations**: Extends ADR-00323 (readline fd-0 event-loop integration), ADR-00322 (child_process fd integration)
- **Date**: 2026-08-24

## Context

The only stdin facilities were the blocking `process.readLineSync()` (one line,
halts the program) and the interactive `readline` module (`createInterface`,
per-line `'line'` events). A streaming `process.stdin` — Node's flowing
`Readable` with `.on('data', chunk => …)` / `.on('end', …)` — was ❌ on
[PROCESS-CLI.md](../status/PROCESS-CLI.md), noted as "deferred to a focused
follow-up." It is the canonical primitive for Unix pipe/filter CLI tools
(`cat x | myprog`), directly on the project's priority path (process interaction,
the third tiebreaker).

The prerequisite — non-blocking stdin (fd 0) folded into the central `select()`
event loop — was already built twice: for a spawned child's pipes (ADR-00322)
and for `readline` (ADR-00323). So this is that same three-hook pattern applied
to fd 0 in raw-chunk (rather than line-buffered) mode. An ADR, not a TDD.

## Decision

- **Runtime** (`runtime_stdin.go`): a `%kml.stdin` handle (`'data'` listener,
  `'end'` listener, ended flag) in a single global `@__kml_stdin_active` (one
  stdin). `@__kml_stdin_create` is idempotent — it allocates the handle and sets
  fd 0 non-blocking on first access, returning the active handle thereafter, so
  `process.stdin` evaluates to it wherever it appears. `@__kml_stdin_dispatch`
  drains stdin, firing `'data'` once per `read()` chunk (delivered as a
  NUL-terminated **string** copy — UTF-8 text), and fires `'end'` once on EOF.
  The three loop hooks (`fdset_add`/`dispatch`/`keepalive`) wire in beside the
  readline ones, with no-op stubs (`emitLoopTaskStubs`) when unused
  (`usedStdinRuntime`, joined into `useFullLoop`).
- **Flowing mode**: attaching the `'data'` listener is what makes the stream
  flow — the runtime only registers fd 0 / reads / holds the loop alive once a
  `'data'` listener is present, matching Node (a paused stream with no `'data'`
  handler doesn't consume input).
- **Codegen** (`emit_stdin.go`, `StdinType` in types.go): `process.stdin`
  evaluates to a `StdinType` handle; `process.stdin.on('data'|'end', cb)`
  dispatches on it. Listeners are arrow/function-expression literals only (the
  Worker/child_process/readline posture). `'data'`'s listener takes the chunk as
  a `string`.

## Implementation notes

- One handle, one stdin. A program mixing `readline` and streaming
  `process.stdin` would have both draining fd 0 — as in Node, use one consumer.
- Chunks are UTF-8 strings, not `Buffer`s — this stream has no `setEncoding`;
  binary stdin (a `Buffer`-delivering mode) stays out of scope, consistent with
  the rest of the fd-0 surface.
- `read()` returning `-1` (EAGAIN) means "nothing more right now"; the dispatch
  simply returns and the loop re-polls. `0` is EOF → `'end'` once, then the
  handle no longer keeps the loop alive.

## Verification

- `tests/stdin_stream_test.go` (5 cases): `'data'`+`'end'` byte count, an
  uppercase transform filter, empty-input `'end'`, a >4096-byte multi-chunk
  accumulation, and the unsupported-event rejection. All fed through the real
  binary's stdin.
- `examples/process_stdin/stream.ts` builds and runs (`printf … | stream`) on
  macOS (arm64). Runs clean under `make examples` (`</dev/null` → immediate EOF).
- `go build` / `go vet` clean; readline suite unaffected (shared fd-0 machinery,
  separate handle).
- Machine: verified on Mac (arm64); the change is platform-independent (POSIX
  `read`/`fcntl`/`select`, same as readline/child_process).

## Known limitations (tracked on docs/status/PROCESS-CLI.md)

- `'data'` delivers UTF-8 string chunks, not `Buffer`s; no `setEncoding`.
- No `.pause()`/`.resume()`/`.read()`/`'readable'`; flowing mode only, started
  by the `'data'` listener.
- One listener per event, arrow/function-expression literal only; callbacks fire
  synchronously from the dispatch, not via a microtask.
