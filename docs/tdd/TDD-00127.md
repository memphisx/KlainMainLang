# TDD-00127: Boxed array representation so length mutations cross call boundaries

- **Status**: Implemented — shipped as the object-reference model ([ADR-00517](../adr/ADR-00517.md)). Two decisions diverge from the sketch below and are recorded in the ADR: (1) `Symbol.Ptr` is a *stable slot* holding the header pointer (one level of indirection), not the header pointer directly — needed so an in-place mutation (propagates) and a whole-variable reassignment (stays local) stay distinct, otherwise `a = a.filter(...)` inside a callee would clobber the caller. (2) The header is `{ptr, len}` with **no `cap` field** — `cap` would force widening all three array shapes (named variable, inline object field, nested-element box), a large ripple for a pure perf win with zero fidelity benefit; amortized-growth is deferred as documented perf follow-up. Residual, unchanged from before: an array passed as `obj.field`/`arr[i]` (member/index) or as a HOF callback element takes a transient-copy path, so mutation through it does not propagate (a known limitation, tracked as a caveat, not new behaviour).
- **Date**: 2026-08-27
- **Notes**: Bug fix. Arrays are a flat `(ptr, i64 len)` value type passed as two loose scalar args, so `arr.push`/`splice` inside a callee don't propagate to the caller (unlike JS reference semantics) — and since `.push` reallocs every call, the moved buffer pointer diverges too, not just the length. Chosen fix: uniform shared `{ptr, len, cap}` heap header (one `ptr` arg at the boundary), extending the box already used for nested elements/object fields; the `cap` field also kills realloc-every-push. Element mutation already propagates today; low priority

## Context

Arrays are a flat value type: a bare `malloc`'d element buffer plus a
*separate* `i64` length, with no header and no capacity field. When an array is
passed to a function, the call site loads `(ptr, len)` out of the argument and
appends them as **two independent scalar arguments** (`emit_call.go:1351-1395`);
the callee re-allocates its own private slots for both and stores the incoming
values (`emit_func.go:199-209`). The callee therefore holds a private copy of
*both* the data pointer and the length.

The consequence is a JavaScript-fidelity bug. In real JS an array is a reference
type: `function f(a){ a.push(1) }` grows the caller's array. Here:

- `arr[i] = v` inside a callee **does** propagate — the element buffer is shared
  by pointer, and the element write GEPs into it.
- `arr.push(v)` / `arr.splice(...)` / `arr.unshift(v)` inside a callee **do
  not** propagate. And it is not only the length that is lost: `.push` calls
  `@realloc` on every invocation (`emit_arrays_mutate.go:562`), which may *move*
  the buffer, so the callee's data pointer also diverges from the caller's.

So both the length and the pointer must live in a single place that caller and
callee share, not in per-frame copies. This is a real correctness gap, filed as
a bug rather than a nice-to-have, but genuinely low priority — element mutation
(the common case) already works, and length-mutating an array argument in place
is a less common pattern.

The fix is a representation change, but not a from-scratch one: the codebase
**already boxes arrays** in two places, and this work extends that existing
pattern to the parameter boundary.

## Design

### Existing precedent (the machinery already exists)

Nested array elements are already boxed. `boxArrayValue`
(`emit_arrays_core.go:107-120`) heap-allocates a 16-byte `{ptr, i64}` box and
stores the array aggregate into it; the *element slot* holds a pointer to that
box. `resolveArrayMutLoc`'s `IndexExpression` case
(`emit_arrays_mutate.go:63-77`) loads the box pointer and GEPs into it, so
`matrix[i].push(...)` already propagates to every alias of `matrix[i]` —
precisely because there is one shared heap `{ptr, i64}`. Object/class array
fields (`resolveArrayMutLoc` case at `emit_arrays_mutate.go:34-61`) share an
inline `{ptr, i64}` slot the same way.

What does *not* share is the plain named-variable (`Symbol{Ptr, LenPtr}`) form,
which is exactly what gets decomposed into two loose scalars at a call site.

### Chosen approach: uniform boxed header

Every named array becomes a single shared heap **header** rather than two loose
allocas. The header is:

```
%kl.array = type { ptr, i64, i64 }   ; { data, len, cap }
```

A `Symbol` for an array holds **one** value: a `ptr` to this header (kept in a
single alloca, or carried directly). All reads (`resolveArrayForHOF`, every
`load i64 ... LenPtr`, length reads, HOF normalization) GEP field 1 for length
and field 0 for data out of the header. All mutators
(`push`/`pop`/`shift`/`unshift`/`splice`) write the updated data pointer,
length, and capacity back into the *same* header the caller holds.

At a call boundary the array is passed as **one `ptr` argument** — the header
pointer. The callee binds that pointer directly (no re-alloca of private
`ptr`/`len` slots). Because both sides point at one header, a `push` inside the
callee updates the data pointer, length, and capacity that the caller
subsequently reads. Full JS reference semantics.

This was chosen over a "promote-on-pass" scheme (box only arrays that cross a
call boundary, keep the flat form for purely-local arrays) for three reasons:

1. **Less special-casing, not more.** The boxed `{ptr, len}` shape and its
   box/unbox helpers already exist for nested elements and object fields.
   Making the named-variable form boxed too *unifies* the three array shapes
   rather than adding a fourth mixed one. Promote-on-pass instead needs
   escape-style analysis (any array *ever* passed anywhere must be boxed for its
   whole lifetime, or caller/callee copies diverge after the call), which is
   more analysis and more failure surface.
2. **The `cap` field is a free win.** A capacity field kills realloc-every-push
   (`emit_arrays_mutate.go:562`): growth becomes amortized (double `cap` when
   `len == cap`), which partially pays back the one extra indirection the box
   adds on every access.
3. **Correctness by construction.** One representation, one aliasing rule.

The accepted cost: one pointer indirection on every array element access,
including array-heavy purely-local code (relevant, since the CLI-tools /
microservices target does a lot of array/string processing). The `cap`-based
amortized growth offsets part of this; if profiling later shows a hot local-only
path regressing, promote-on-pass can be revisited as an optimization *on top of*
the uniform header, without changing semantics.

### Aggregate (`Value{Ref}`) form

Array *expressions* (literals, `slice`/`map`/`concat` results, function returns)
currently produce an SSA `{ptr, i64}` first-class aggregate (`Value{Ref}`).
Under the header model these must be boxed into a header on materialization —
i.e. when an expression result is bound to a name, stored into a slot, or passed
as an argument, it is written into a fresh `%kl.array` header and the header
pointer is what flows onward. `boxArrayValue` already does almost exactly this
(a 16-byte `{ptr, i64}` box); it extends to the 24-byte `{ptr, i64, i64}` header
with `cap` initialized to `len`. Read-only consumers that never cross a call
boundary can keep consuming the aggregate directly via `resolveArrayForHOF`;
only materialization points need the header.

### Touch list

- `emitter.go:13-24` — `Symbol`/`Value`: an array `Symbol` becomes a single
  header pointer instead of `Ptr` + `LenPtr`. Decide whether to keep
  `Ptr`/`LenPtr` as *derived* accessors (GEP into the header) to minimize churn
  at the ~dozens of read sites, or migrate every reader explicitly.
- `emit_arrays_core.go:107-145` — `boxArrayValue`/`unboxArrayValue`: widen box
  from `{ptr,i64}` to `{ptr,i64,i64}`; add `cap` init.
- `emit_arrays_mutate.go` — `resolveArrayMutLoc` (`22-80`) returns the header
  pointer uniformly; `push` (`525-576`) gains capacity-aware amortized growth;
  `splice`/`shift`/`unshift` write `cap` back too.
- `emit_call.go:1351-1395` — pack **one** `ptr` header argument instead of
  `(ptr, i64)`.
- `emit_func.go:199-209` (and closure mirror `1055-1095`) — bind the header
  pointer param directly; drop the two-private-slot re-alloca.
- Every `load i64 ... LenPtr` / `resolveArrayForHOF` reader — read length from
  header field 1.

## Open questions

- Keep `Symbol.Ptr`/`Symbol.LenPtr` as derived GEP accessors over the header (to
  limit churn across the many read sites) versus migrating every reader to a
  single `Header` field explicitly. The former is far less diff; the latter is
  cleaner long-term.
- Growth policy for `cap`: pure doubling vs. golden-ratio (1.5×) — doubling is
  simpler and standard; 1.5× is friendlier to allocators that can reuse freed
  runs. Doubling unless a reason emerges.
- Interaction with the memory-management modes (`manual`/`gc`/`auto`,
  [TDD-00001](TDD-00001.md)): the header is a second heap allocation per array;
  confirm it is freed/collected on the same path as the element buffer under
  each mode, and that `-mm=manual` frees the header, not just the buffer.
- Whether returning an array by value (function return) should hand back the
  header pointer directly (aliasing the callee's now-dead frame is fine since
  the header is heap) or a fresh header — return-by-header pointer is correct and
  cheaper; confirm no double-free under `manual`.
