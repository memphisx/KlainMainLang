# ADR-01947: Nullable scalar keys of a Map or Set

- **Relations**: Implements TDD-00230
- **Date**: 2026-10-28

## Context

A `Set<number | null>` failed to compile: clang rejected the IR ("defined with type 'double' but expected '{ i1, double }'"), as did a `Map<number | null, V>` iterated or spread. The key lived in the raw 64-bit key family, which stored only the payload, so `null` and `0` were also the same key. Found by a probe of nullable and three-state scalars outside locals (fields, elements, Map values, captures, returns); every other position matched Node.

## Decision

- A nullable scalar key type (`number | null`, `boolean | undefined`) uses the any-keyed runtime. Keys are boxed and compared by SameValueZero over the boxes, as bigint keys already are. `boxedKeyTy` names the three key kinds stored as boxes: references, bigints and nullable scalars.
- Reading keys back:
  - An array of keys (spread, `Array.from`, `keys()`) keeps the boxes, which are already the array's element representation (`arrayElemType`).
  - A per-entry reader (`forEach`, `entries`, Map inspect) decodes the box through `loadKeyAt`.
  - An iterator's `next()` value is three-state (`T | null | undefined`): a null key reads null, and the done value reads undefined.
- `new Set<K>(array)` reads the source array with the source's own element type and converts each element to `K`. It used to read with `K`'s type.
- The record-field store (`storeArrayElem` on a tuple field) and a `for…of` loop variable give a nullable scalar its `{i1, T}` slot.
- An explicitly typed `new Map<K | null, V>([[null, …], [k, …]])` is no longer rejected as a heterogeneous-key map: a null key fits a nullable `K`, as a null value already fit a nullable `V`.

## Consequences

- Verified on macOS (Apple Silicon) against Node: `TestE2EMapSetNullableScalarKeys` covers `has`/`get`, spread, `for…of`, `forEach`, `next()`, `delete`, inspect, entries and seeded constructors. The Map, Set, for-of, iterator, nullable, tuple and optional suites pass.
