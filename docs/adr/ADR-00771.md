# ADR-00771: `--static` self-contained binaries on Windows (C++ runtime, winpthread, pcre2)

- **Relations**: extends `--static` ([ADR-00738](ADR-00738.md) link-order partition, the Linux `-static` path) to Windows for the non-system libraries; pairs with [ADR-00772](ADR-00772.md) (the static libcurl chain + the dynamic-by-default policy); the mingw toolchain is [TDD-00177](../tdd/TDD-00177.md)
- **Date**: 2026-09-07

## Context

A `klain:tui` (Yoga/C++) or `klain:webview` program on Windows, when built the
default (dynamic) way, imports the mingw C++ runtime DLLs — `libstdc++-6.dll`,
`libgcc_s_seh-1.dll`, `libwinpthread-1.dll` — plus `libpcre2-8-0.dll` for `RegExp`.
None of these exist on a stock Windows box, so the `.exe` fails to launch off a
machine with `C:\msys64\ucrt64\bin` on `PATH` (`The code execution cannot proceed
because libstdc++-6.dll was not found`). Dynamic linking is the right *default*
(it matches Mac/Linux, and Windows apps ship their DLLs via a bundle/installer —
see [ADR-00772](ADR-00772.md)), but there was **no way to produce a self-contained
single-binary on Windows** — `--static` was Linux-only. This ADR makes `--static`
work on Windows for the non-system libraries, so a terminal/CLI tool can be one
file.

## Investigation

Static-linking the C++ runtime with clang on mingw is not one flag:

- `-static-libstdc++` (the driver flag) only brackets the `-lstdc++` the driver
  adds itself; an explicit `-lstdc++` still resolves to the DLL import lib. The
  colon form `-l:libstdc++.a` links the static archive directly.
- The static `libstdc++.a` is **gcc-built**, but the Yoga/webview objects are
  **clang-built**, and clang's RTTI COMDAT sections differ in size from gcc's, so
  the default `ld.bfd` rejects the mix: *"duplicate section … has different
  size."* `lld` folds these but is not part of the required toolchain.
- The static path also surfaces a `strerror` multiple-definition (the win32 fs
  shim vs. the static CRT), and — for `std::thread` users like webview and the
  `klain:sync` goroutine runtime — a `libwinpthread-1.dll` pulled by a global
  `-lwinpthread` in the win32-shim link args.

## Decision

`--static` on Windows statically links the **non-system** libraries; the UCRT
(`api-ms-win-crt-*`, ships with Windows 10+) and core Win32 DLLs stay dynamic.
It is gated by `staticLinkMode` (`llvm.SetStaticLink`, set once from `--static`);
the default build is unchanged (dynamic). Under `--static` on Windows:

- **Compile Yoga's C++ (and the webview amalgamation) with `g++`, not clang**, so
  their objects are ABI/COMDAT-compatible with the gcc-built `libstdc++.a`.
  `g++` ships with `mingw-w64-ucrt-x86_64-toolchain` (already required) and is
  native to the ucrt64 sysroot. The object cache is keyed by compiler
  (`obj-clang` vs `obj-gpp-static`) so the two modes never reuse each other's
  objects. (`yoga.go`, `webview_win32.go`, `embedded_c.go`.)
- **Link the C++ runtime statically** (`winCxxStaticRuntime`, `yoga.go`):
  `-l:libstdc++.a` inside a `-Wl,-Bstatic,--start-group,-lstdc++,-lwinpthread,--end-group,-Bdynamic`
  group (one comma-joined `-Wl` arg so it survives the `-l` partition of
  [ADR-00738](ADR-00738.md); `--start-group` resolves the libstdc++↔winpthread
  circular refs; a thread-free TUI pulls no winpthread) + `-static-libgcc` (drops
  `libgcc_s_seh-1.dll`) + a trailing `-l:libwinpthread.a` + `-Wl,--allow-multiple-definition`
  (the shim's `strerror` wins over the static CRT copy).
- **Static winpthread globally under `--static`** (`hostclang_win32shim.go`): the
  win32-shim link args link `-lwinpthread` dynamically by default, `-l:libwinpthread.a`
  under `--static` — this is what pulled `libwinpthread-1.dll` into every
  thread-using binary. `klainsync`/`embedassets`/worker links route pthread
  through `WorkerPthreadLinkFlags` (dynamic `-pthread` by default, the static
  archive under `--static`).
- **Static pcre2** (`LinkLibFlags`, `hostclang.go`): `-l:libpcre2-8.a` under
  `--static`, `-lpcre2-8` otherwise.

Result under `--static`: a `klain:tui`/`klain:webview` `.exe` imports only stock
Windows DLLs (`KERNEL32`/`USER32`/`ADVAPI32`/`SHELL32`, the UCRT `api-ms-win-crt-*`,
`bcrypt`).

## Verification

- **Windows 11 native**: `klaintop`/`files`/`todo`/`menu`/`explorer` built
  `--static` have **zero** non-stock DLLs (`objdump -p`); klaintop launches with
  `C:\msys64\ucrt64\bin` off `PATH`. The default (dynamic) build imports
  `libpcre2`/`libstdc++` as expected. `Tui`/`Tty` suites green; new tests
  `TestE2ETuiBinaryIsSelfContained`/`TestE2EWebviewBinaryIsSelfContained`/
  `TestE2ETuiMenuAppNavigates` build under `--static` and assert no bundled
  runtime DLL.
- **Docker Linux `klain-ci:latest`**: `Tui`/`Tty` green — the g++/static path is
  Windows+`--static`-gated, so the Linux path (clang, dynamic C++ runtime) is
  unchanged.
- `go build`, `go vet ./codegen/...` clean. **CI note**: `--static` on Windows
  changes how a `klain:tui`/`klain:webview` program links; the Windows CI lane is
  the regression guard.
