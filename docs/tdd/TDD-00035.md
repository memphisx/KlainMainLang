# TDD-00035: RegExp support (staged, PCRE2-backed)

- **Status**: Implemented
- **Date**: 2026-08-07
- **Notes**: All 7 stages (0-6) done — full method surface (construction/literal/fields, `.test()`, `.exec()`, `str.match()`/`str.matchAll()`, `str.replace()`/`str.replaceAll()`, `str.split()`/`str.search()`) plus `--static` linking verified on bare Linux and in a real Docker `scratch` container

## Context

RegExp is the last major "everyday JS" gap in this compiler. `docs/status/README.md` lists `RegExp` under "High complexity — needs PCRE or similar C library," `docs/status/STRING-METHODS.md` marks `.match()`/`.matchAll()` ❌, and `.search()` is currently just `.indexOf()` under another name — its own doc comment (`codegen/llvm/emit_strings.go:362-367`) admits it's "exactly indexOf's behavior under a second name" since there's no `RegExp` to coerce a pattern argument to. Confirmed by direct grep across `lexer/`, `parser/`, `ast/`, `resolver/`, and `codegen/llvm/`: zero mentions of `RegExp`/regex anywhere. 0% implemented at every layer, not just undocumented.

Raised directly by the user as the next planning target — "really powerful and common," and correctly anticipated to "affect multiple places including existing APIs" (`.replace`, `.replaceAll`, `.split`, `.search` all need touching, not just new surface area). Given the size (a new lexer token class with genuine context-sensitive disambiguation — a first for this lexer — a new external C dependency, a new heap-object type, five-plus string-method call sites to extend, three separate expression-dispatch wiring points), this needs a design pass before implementation starts, per the project's own standing rule for significant scoping work.

Two decisions made explicitly before this design was written:

1. **Regex engine: PCRE2, dynamically linked.** Three alternatives were weighed: vendoring PCRE2's actual source into the repo (rejected — PCRE2 isn't a single-file amalgamation like SQLite's; it's dozens of `.c` files plus large generated Unicode tables and normally needs `configure`/CMake to detect platform specifics, which would make this project own building someone else's non-trivial C build system on every compile — against this project's firm "link a system library or hand-roll it ourselves" convention, never "vendor and rebuild a third party's C project"); a first-party hand-rolled backtracking engine (a real, viable "truly zero dependency, ever" option, closer in spirit to how this project already hand-rolls its JSON parser and event loop rather than pulling in a library — but rejected here in favor of PCRE2's maturity and full JS-like syntax for materially less engineering effort); POSIX `regex.h` (already in libc everywhere, zero install, but ERE's grammar is too weak for real JS regex expectations — no `\d`/`\w`/`\s`, no lazy quantifiers, no lookaround, no named groups).
2. **`.replace()`/`.replaceAll()` gain callback-function replacement support** (`str.replace(regex, (match, ...groups) => ...)`) as part of this work, not deferred to a separate follow-on — a very common real-world idiom, and both functions need touching anyway to accept a `RegExp` pattern argument.

## Design

### Stage 0 (prerequisite): lexer, parser, AST, type system, construction — no methods yet

**Lexer disambiguation.** The lexer (`lexer/lexer.go`) is a fully separate, single-pass phase that tokenizes the whole file before parsing ever starts (`lexer.Tokenize`, called once from `parser.New`) — it has zero token-to-token context today (`Lexer`'s fields are just `src, pos, line, col, templateStack`). `/` is currently lexed unconditionally as `SLASH`/`SLASH_ASSIGN` once the existing `//`/`/* */` comment checks (`lexer.go:72-100`) have already run and not matched. Real JS's classic regex-vs-division ambiguity needs resolving the same way real JS engines do it: track whether the previous significant token leaves an expression expected (regex-legal position) or a value just ended (division). Add a `lastSig lexer.TokenType` field to `Lexer`, updated after every real token `NextToken` returns (comments/JSDoc never touch it). Buckets:
  - **Regex-legal** (expression expected): start-of-input; every binary/assignment/comparison/logical/bitwise operator token; `LPAREN`, `LBRACE`, `LBRACKET`, `COMMA`, `SEMICOLON`, `COLON`, `QUESTION`, `ARROW`; keywords that are always followed by an expression (`RETURN`, `TYPEOF`, `VOID`, `NEW`, `THROW`, `CASE`, `AWAIT`); `TEMPLATE_HEAD`/`TEMPLATE_MIDDLE` (opening a `${...}` interpolation).
  - **Division** (value just ended): `IDENT`, `NUMBER`, `STRING`, `TEMPLATE_NO_SUB`/`TEMPLATE_TAIL`, `TRUE`/`FALSE`/`NULL`/`UNDEFINED`, `THIS`/`SUPER`, `RPAREN`, `RBRACKET`, `RBRACE` (real JS is itself ambiguous here too — block-end vs. object-literal-end — treating it as "division allowed" is the standard, accepted simplification), postfix `INC`/`DEC`.
  - This is architecturally consistent with an existing precedent, not a new kind of complexity for this lexer: template literals already carry cross-token state (`templateStack []int`, `lexer.go:14`) to resolve the analogous "does this `}` close a block/object or resume template text" ambiguity.
  - **Known, deliberately-accepted gap**: this lexer has no real `IN`/`OF` token at all — `in`/`of` are plain `IDENT`s with contextual parser-side checks (`parser/parser_exprs.go:192-202`), specifically so `in` stays usable as an ordinary field name elsewhere. That means `lastSig` will read `IDENT` (→ division-legal) even right after a real `in` keyword, so `x in /foo/` will mis-lex the `/` as division. Documented as a known limitation rather than fixed — fixing it would mean threading parser-level goal-symbol context back into the lexer, a much bigger architectural change than this feature justifies, for an idiomatically rare construct.
  - Comment detection keeps running first and winning, unchanged — matches real JS's own behavior that an empty regex literal is inexpressible as `//` (always a comment); `new RegExp("")` is the only way to write one. Not a bug to solve.
  - Pattern/flag scanning: new `readRegex` (parallel to `readString`, `lexer.go:389-426`) that consumes forward tracking backslash-escapes verbatim (preserve `\d`, `\/`, etc. exactly — PCRE2 needs to see them, unlike `readString`'s escapes which get translated) and an `inClass` boolean toggled by unescaped `[`/`]` (an unescaped `/` inside a character class is literal content, not a terminator — matches the real `RegularExpressionClass` grammar production). A newline before the closing `/` is an unterminated-literal lexer error, reusing `readString`'s existing error shape (`lexer.go:420-422`). After the closing `/`, flag letters are consumed greedily with no lexer-level validation (deferred to the parser/emitter, consistent with how this lexer never validates keyword-ness either).
  - New `REGEX` token type (`lexer/token.go`). `Token` currently has one payload field (`Literal`) — add a second (e.g. `Literal2`) for the flags string rather than overloading `Literal` with a separator character.

**AST/parser.** One new node, `ast.NewRegExpExpression{Pattern, Flags Expression}` (`Flags` nilable for the 1-arg form) — same shape as the existing per-builtin dedicated-node convention (`ast.NewURLExpression`, `ast/nodes.go:806-816`). Both surface forms desugar to it: `new RegExp(pattern, flags?)` via `parseNew`'s dispatch (`parser/parser_literals.go:111`, alongside the existing `"URL"`/`"TextEncoder"` cases), and a bare `/pattern/flags` literal via a new `case lexer.REGEX:` in `parsePrimary` (`parser/parser_literals.go:723`) that builds the identical node directly from the token's pattern/flags text. Codegen therefore only ever has one shape to handle — no separate "literal" vs. "constructor" code paths downstream.

Real JS re-evaluates a regex literal fresh every time control reaches it (this was different in very old JS but isn't anymore) — this compiler's normal per-occurrence expression evaluation already gives that for free, so no caching mechanism is needed for correctness. Hoisting a literal's compile step out of a loop body would be a valid future performance optimization, explicitly out of scope here (matches `README.md`'s own "not production-ready, never expected to be" framing).

**Type system.** New `IsRegExp` flag + `RegExpType()` in `codegen/llvm/types.go`, built via `ObjectType(fields []Field)` (`types.go:204`) — following `URLType()`'s real-heap-object shape, not `TextDecoderType()`'s stateless-`"null"`-marker shape (`ADR-00112`), since a compiled pattern needs to persist across calls (avoid recompiling on every `.test()`) and `lastIndex` is genuinely mutable per-instance state for the `g`-flag iteration idiom (`while ((m = re.exec(s)) !== null) {...}`). Visible fields: `source` (`TypePtr`), `flags` (`TypePtr`), `global`/`ignoreCase`/`multiline` (`TypeBool`, decomposed once at construction so no method needs to re-parse the flags string), `lastIndex` (`TypeI64`, mutable). One **hidden** field at index 0 — excluded from `VisibleFields()` (`types.go:426`), the same convention `IsError`'s hidden kind-tag and `IsClass`'s hidden dispatch tag already use — holding the raw `pcre2_code*` compiled-pattern pointer, so `Object.keys`/`JSON.stringify` never try to serialize it.

**Runtime declarations & linking.** New `codegen/llvm/runtime_regexp.go`: hand-written `declare` lines for PCRE2's 8-bit ABI — `pcre2_compile_8`, `pcre2_get_error_message_8`, `pcre2_code_free_8`, `pcre2_match_data_create_from_pattern_8`, `pcre2_match_data_free_8`, `pcre2_match_8`, `pcre2_get_ovector_pointer_8`, `pcre2_get_ovector_count_8`, `pcre2_substring_length_bynumber_8`/`pcre2_substring_copy_bynumber_8`, `pcre2_pattern_info_8` (capture-count discovery right after compile). PCRE2's option/error constants (`PCRE2_CASELESS`, `PCRE2_MULTILINE`, `PCRE2_DOTALL`, `PCRE2_ZERO_TERMINATED`, `PCRE2_ERROR_NOMATCH`, ...) are C preprocessor macros with no linkable symbol — hardcode their numeric values in a Go const block with a comment citing the exact `pcre2.h` and installed PCRE2 version, the same convention `emit_url.go:12-19`'s `CURLUPart` enum already establishes for libcurl. One real relief compared to past cross-platform struct-layout bugs this project has hit (`ucontext_t`, ADR-00051; `GC_stackbottom`, ADR-00080): PCRE2's `pcre2_code`/`pcre2_match_data` are **opaque pointers**, never struct fields this code lays out itself, so only the numeric constants need per-machine re-verification, not a memory layout.

Whichever `ensure*()` helper first declares these calls `e.requireLink("pcre2-8")` (`emitter.go:341`), exactly where `ensureFetch`/`ensureCurlURL` already call `requireLink("curl")` (`runtime_fetch.go:25,414`, `runtime_url.go:25`) — no `main.go` change needed for dynamic linking at all; `LinkLibs()` (`main.go:89-91`) is already fully generic and only adds `-lpcre2-8` to a build that actually used regex.

**Construction codegen.** New `codegen/llvm/emit_regexp.go`: `emitNewRegExpExpression`, following `emitNewURLExpression`'s shape exactly (`emit_url.go:82-113`) — call `pcre2_compile_8`, branch on a non-null error-code output, and on the bad branch call `emitInternalThrow` (`emit_exceptions.go:83-87`) with a message built from `pcre2_get_error_message_8` (a real, catchable error — same convention as `emit_url.go:109`'s `"Invalid URL"`), otherwise store `source`/`flags`/the three decomposed flag booleans/`lastIndex = 0`/the compiled handle into a fresh `RegExpType()` object on the OK branch.

**Dispatch wiring.** All three places `ADR-00112`/`ADR-00113` found necessary the hard way this same session (a real, cite-worthy trap for exactly this compiler's architecture): `codegen/llvm/emit_exprs.go` (generic `emitExpr` dispatch), `codegen/llvm/emit_exprs_types.go` (`inferExprType`, consulted by e.g. `console.log`'s format-string selection and any expression-position use), `codegen/llvm/emit_exprs_vardecl.go` (the *separate* unannotated-`const`-initializer inference switch — it does **not** automatically fall back to `inferExprType` for a dedicated `New*Expression` node; this was a real gap hit and fixed twice already in this codebase's history and would be hit a third time here if skipped).

### Stage 1: `.test(str): boolean`

Smallest possible end-to-end slice — proves compile → link → match → boolean with no result-array machinery at all. New `IsRegExp`-guarded dispatch block in `emit_call.go`, checked before the generic property-name chain — same shape as the existing `IsTextDecoder`+`"decode"` guard (`emit_call.go:103`) and `IsURLSearchParams`+`"toString"`/`"getAll"` (`emit_call.go:535-541`, explicitly ordered ahead of the generic Map dispatch so it isn't shadowed).

### Stage 2: `.exec(str): string[] | null` + `lastIndex`/`g`-flag match-loop machinery

`T | null` is already real, reusable machinery — `Type.Nullable` (`types.go:47-50`), consumed by the existing null-select-at-runtime pattern (`emit_exprs_vardecl.go:40-49`) — so this needs zero new type-system work, just `Nullable: true` on an `ArrayOf(TypePtr)` return type.

V1 result scope: index 0 = the full match, indices 1..N = numbered capture groups, all as plain `string[]` elements; an unmatched *optional* capture group becomes `""` rather than a true per-element `null` (this compiler's arrays have no per-element-nullable-string representation today — a real, documented narrowing, not an oversight). Real JS's exec-result-is-an-array-with-extra-properties shape (`index`, `input`, `groups`) is explicitly deferred — this compiler's arrays are plain `{ptr,i64}` aggregates (`ArrayOf`, `types.go:198-201`) with no room for bolted-on named properties without inventing a new hybrid type, disproportionate for V1.

The `g`-flag stateful loop (read `lastIndex` before matching if `global`, write it after a successful match, reset to 0 after a failed one) is genuinely new state-mutation logic, and the runtime match-loop-and-build-a-result-array helper this stage needs (`__kml_regex_*`-shaped, in `runtime_regexp.go`, following `__kml_split`'s "runtime counts and builds the array, emitter just calls it and wraps the result" precedent — `runtime_strings.go:379`, called from `emit_strings.go:606-625`) is the genuine shared prerequisite Stage 3 reuses — sequenced deliberately before it, not as a peer.

### Stage 3: `str.match(regexp)` / `str.matchAll(regexp)`

Thin wrappers over Stage 2's helper — both new functions in `emit_strings.go` (`.match`/`.matchAll` don't exist at all today). `.match()` branches at **runtime** on the RegExp object's stored `global` field, not at compile time — a non-literal `RegExp` held in a variable has statically-unknowable flags. Without `g`: delegate to Stage 2's single-match logic (one result array, or `null`). With `g`: loop matching from increasing offsets, collecting only full-match strings (no capture groups — matches real JS's own `g`-mode `.match()` behavior) into a `string[]`, never `null` (empty array on zero matches).

`.matchAll()` is scoped down to an eager `string[][]` return rather than a real lazy iterator — no generator/lazy-iteration infrastructure exists anywhere in this compiler today (every `for...of` is over an already-eager array/Map/Set/class-defined iterator), so building one here would be new infrastructure disproportionate to this feature. Real JS's hard requirement that `matchAll` throw a `TypeError` without the `g` flag is preserved (cheap, and a real compatibility signal for ported JS). Each inner `string[]` is exactly one `.exec()`-shaped match array, reusing the same underlying helper as `.match()`'s `g` branch but keeping full capture groups per match instead of only the whole match.

### Stage 4: `str.replace()` / `.replaceAll()`, including the callback form

Extends the existing functions in place (`emit_strings.go:556-604`) by branching on `e.inferExprType(args[0]).IsRegExp` ahead of today's literal-string path — the existing literal behavior for a plain-string pattern is unchanged.

Two independent sub-decisions:
- **String-replacement backreferences**: include `$1`-style numbered backreferences and `$&` (whole match) — cheap once a match's capture offsets are known, a single scan-and-substitute pass over the replacement string. Defer `` $` ``/`$'` (pre-/post-match text) as rare and low-value.
- **Callback form** (confirmed in scope per the decision above): branch separately on `e.inferExprType(args[1]).IsFunc` (existing closure machinery, `emit_func.go`), invoking `(match, ...capturedGroups, offset, string)` per match — mirroring `.exec()`'s already-decided capture-group scope, and omitting real JS's trailing `groups` object for the same reason `.exec()` omits it. This is the single most novel piece of the whole feature — a C-side match loop calling back into a KML closure per iteration — closer in shape to `emit_arrays_hof.go`'s callback-invocation pattern (`codegen/llvm/emit_arrays_hof.go:8-91`) than to any existing string runtime helper. Ship the plain-regex-no-callback path first; layer the callback path on top only once that match loop is proven correct.

### Stage 5: `str.split(regexp)` / `str.search(regexp)`

Smallest remaining surface, reuses Stage 1-2 primitives, both extending existing functions in place. `.split()`'s real-JS quirk — capturing groups in the split pattern get spliced into the result array — is explicitly **out of scope**; plain non-capturing regex-based splitting is in scope, extending `emitStringSplit` (`emit_strings.go:606-625`). `.search()` extends its current placeholder (`emit_strings.go:362-367`) with a real `IsRegExp` branch (one `pcre2_match_8` call, returning the match start offset or `-1`), falling back to today's `.indexOf` delegation unchanged for a plain-string argument.

### Stage 6: `--static` parity with `fetch`/curl

Elevated to a real, expected-to-succeed stage rather than a deferred afterthought. `--static` (`main.go:27-29`, Linux-only) is a genuinely thin mechanism in this compiler: it appends the bare `-static` flag to `clangArgs` and nothing else — there is **no** curl-specific static-linking code inside `main.go` to mirror. The entire curl static story (`ADR-00033`) is a *user-facing documented recipe*, not something the compiler automates: a `fetch`-using static build needs curl's full transitive static dependency chain passed explicitly at the user's own build stage (static archives don't auto-pull their own dependencies), plus, on Alpine/musl specifically, a two-step `clang`-then-`gcc` link since some of musl's static archives are LTO-built in a format only gcc's linker can consume (`README.md:100-114`). This complexity is inherent to curl's TLS backend (GnuTLS → `libp11-kit`), not to static linking in general.

PCRE2 has no TLS backend and no equivalent transitive-dependency chain at all — statically linking it is plausibly just `-static -lpcre2-8` with PCRE2's static archive (`libpcre2-8.a`) installed, no per-distro package juggling or two-step-link workaround expected. This should be **attempted and verified directly** (via the existing `docker/` scratch-image harness that already verifies `--static`+`fetch`, `README.md:177` — add a `--static`+regex Dockerfile alongside `docker/Dockerfile.fetch-test`) as part of shipping this feature, not written off pre-emptively. If real testing surfaces genuine per-distro complexity on par with curl's, document it the same way (a dedicated ADR with the full recipe) rather than trying to automate it in the compiler — but go in expecting "this just works," and confirm rather than assume.

### Flag scope for V1

| Flag | PCRE2 mapping | V1 scope | Reasoning |
|---|---|---|---|
| `g` (global) | *(no compile-time option — a match-loop concern)* | **In** | Core to `.match()`/`.matchAll()`/`.replaceAll()`'s semantics; drives runtime branching (§Stage 3), not a `pcre2_compile_8` option at all |
| `i` (ignoreCase) | `PCRE2_CASELESS` | **In** | Trivial, universally used |
| `m` (multiline) | `PCRE2_MULTILINE` | **In** | Trivial, common with `^`/`$` |
| `s` (dotAll) | `PCRE2_DOTALL` | **In** | Trivial, one option bit |
| `u` (unicode) | `PCRE2_UTF` (+ `PCRE2_UCP` for Unicode-aware `\d`/`\w`) | **Deferred** | This compiler's strings are raw UTF-8 byte buffers already; `PCRE2_UTF` mode changes match semantics enough (multi-byte codepoint boundaries) to deserve its own validation pass rather than folding it into V1 and risking subtle boundary bugs in the first cut |
| `y` (sticky) | `PCRE2_ANCHORED` (per-call, combined with `lastIndex`) | **Deferred** | Rare in practice; a cheap follow-on once Stage 2's `lastIndex` machinery already exists |
| `d` (hasIndices) | *(no direct mapping)* | **Deferred** | Needs a richer `.exec()` result (match start/end offsets) than V1's array-only scope provides |

## Open questions

- **Exact PCRE2 package/link name per platform** needs direct verification on both dev machines before Stage 0 ships (likely `libpcre2-dev`/`-lpcre2-8` on Debian/Ubuntu, `pcre2` via Homebrew on macOS, `pcre2-devel` on Fedora/RHEL) — per the project's own standing platform-verification rule.
- **Whether PCRE2's static story really is as simple as expected** (Stage 6) can only be confirmed by actually trying it against the `docker/` scratch-image harness on real Linux hardware — flagged as "expected easy, verify before declaring it so," not assumed.
- **ReDoS/pathological-pattern exposure**: PCRE2 has no built-in match-step limit unless `pcre2_set_match_limit_8` is explicitly configured via a match context. Recommend a conservative, compiled-in (not user-configurable) default applied at every `pcre2_match_8` call site, documented as a V1 simplification — a KML program compiling and matching a user-controlled pattern is a realistic scenario given this project's stated microservice direction.
- **Empty-match handling** in every `g`-mode loop (`.matchAll()`/`.replaceAll()`/`.split()`) needs an explicit one-character-advance rule to avoid an infinite loop on a zero-length match — a real implementation-time design/test point, not something that falls out "for free" from a naive offset-increment loop.
