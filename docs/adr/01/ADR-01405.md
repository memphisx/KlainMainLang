# ADR-01405: The loop inside the webview's main loop

- **Relations**: Implements TDD-00244; Supersedes ADR-00439
- **Date**: 2026-10-05

## Context

A webview program's `run()` hands the thread to the GUI's main loop. The
runtime kept working through a pump: a 16 ms page `setInterval` that called a
bound native function (on Sailfish, a 16 ms `QTimer`), which fired due JS
timers from the timer queue, stepped the task scheduler and drained
microtasks.

On POSIX, much of the runtime now lives only inside `uv_run`: pool
completions arrive on a `uv_async_t` ([ADR-01395](ADR-01395.md)), libcurl's
sockets and timeout are libuv watchers ([ADR-01397](ADR-01397.md)), and
child processes, `net`, `dgram`, IPC and `fs.watch` are libuv handles. The
pump never ran libuv, so inside a webview none of them completed until
`run()` returned. Verified on the Mac: an `fs.promises.readFile` started
before `run()` settled only after the window closed. Timers also fired up
to 16 ms late.

## Decision

- `loop.c` exports what an embedding host needs: `__kml_loop_run_once` (one
  non-blocking pass), `__kml_loop_backend_fd` (`uv_backend_fd`) and
  `__kml_loop_next_ms` (the soonest of the runtime's own deadlines and
  `uv_backend_timeout`, 0 when work is runnable, -1 when only the backend
  descriptor can bring work). The pass's wait computation moved into
  `pass_wait`/`runnable_now` so the pass and the host share it.
- The host watches the backend descriptor and keeps one timer at the next
  deadline, and runs a pass on either, then re-arms:
  - macOS: a `CFFileDescriptor` and a repeating `CFRunLoopTimer` whose next
    fire date is reset after each pass (`webviewsrc/loop_embed.cc`,
    appended to the webview translation unit; CoreFoundation joins the
    link).
  - GTK: `g_unix_fd_add` and a `g_timeout_add` timer (the same file).
  - Sailfish: a `QSocketNotifier` and a single-shot precise `QTimer`,
    replacing the 16 ms pump.
- A bound callback's thunk kicks a pass on return, so work the callback
  started runs on the next main-loop iteration.
- Every webview program on POSIX links the loop. The page-side pump, its
  bound `__kml_tick` handler and the tick stubs remain on Windows only,
  until its loop is libuv's (TDD-00244 Stage 6).

## Verification

- Mac (M4): the webview tests, windowed ones included
  (`KML_WEBVIEW_SMOKE=1`), and the new `TestE2EWebviewLoopEmbedSmoke` (an
  `fs.promises` read and a chain of timers settle during `run()`) and
  `TestE2EWebviewServerSmoke` (an HTTP server answers a `fetch` during
  `run()`, with no Worker).
- Linux (x86-64, Ubuntu 24.04 container): a webview program compiles and
  links against GTK 3 and `webkit2gtk-4.1` with the embedding in it
  (`__kml_wv_loop_embed`, `g_unix_fd_add`); not run in a window. The full
  test suite (3,925 tests), the 393 examples, and Test262 in both lanes
  (strict 8,498, js 10,506, unchanged, no invalid IR).
- Sailfish: not built (no Sailfish sysroot on either machine) and not run.
