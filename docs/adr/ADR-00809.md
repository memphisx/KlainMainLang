# ADR-00809: `--target`/`--sysroot` cross-compilation flag (TDD-00146 Stage 1)

- **Relations**: `Implements TDD-00146`

- **Date**: 2026-09-09

## Context

TDD-00146 Stage 1 asks for a generic cross-compilation mode — a `--target`
triple plus a `--sysroot` pointing at the target platform's root filesystem —
so a CLI program can be built for another platform (the immediate motivation is
64-bit-ARM Sailfish OS, but the flag is generic and also covers the Android NDK
preset of TDD-00147). This is the shared enabler for both mobile targets and
for cross-built Docker microservices, so it is the first Sailfish piece and the
one fully deliverable off-device.

## Investigation

The compiler already cross-compiles in exactly one place: a Windows *host*
builds the emitted program for the mingw-w64 UCRT target, driven entirely by
`runtime.GOOS == "windows"` in two spots — `HostClangArgs` in
`codegen/llvm/hostclang.go:163` (which returns `--target=x86_64-w64-mingw32
--sysroot=<msys2>`) and the `target triple` line in `emitter.go` (only Windows
stamps one; Linux/macOS rely on clang's host default). So the machinery for
"tell clang a triple + a sysroot, and stamp a matching module triple" already
exists — it was just keyed off the host OS, never off a user request. Every
clang invocation (main compile, the embedded-C runtime, the GC shim) funnels
through `HostClangArgv`, so a single change there retargets all of them at once.

Toolchain probe on the Apple-Silicon dev machine: Apple clang cross-compiles a
TS program to an `aarch64-linux-gnu` ELF object cleanly, but the Mac has no
`lld` and no glibc aarch64 sysroot, so a true Darwin→Linux *link* cannot
complete here. The chosen verification lane is therefore the ADR-00351
Docker-as-Linux precedent — an arm64 Linux container runs natively on the M4,
where `--target aarch64-linux-gnu --sysroot /` links and executes.

Preset resolution (TDD-00146 open question) was decided **explicit**: a preset
name resolves only the *triple*; `--sysroot` is always required and validated
up front, so a missing rootfs fails with a clear compiler message instead of
deep inside clang. No automatic SDK probing.

## Decision

- **`--target <triple|preset>`** and **`--sysroot <path>`** flags in `main.go`.
  A preset name (`sfos-aarch64` → `aarch64-meego-linux-gnu`, Sailfish's native
  Mer-heritage triple — see Implementation notes for why the vendor field
  matters) is expanded via a small
  `crossPresets` map; a bare clang triple passes through verbatim. Guards:
  `--target` requires an existing-directory `--sysroot`; `--sysroot` without
  `--target` is rejected; `--target` + `--static` is rejected (cross static
  linking is not wired up yet); and a **cross-*OS*** target (the triple's OS,
  parsed by `targetOSFromTriple`, differs from the host `runtime.GOOS`) is
  rejected with a clear message — because codegen is still host-OS-keyed (see
  Side effects), so only same-OS/different-arch cross builds are correct today.
- **`llvm.SetCrossTarget(triple, sysroot)`** records the request in a
  package-level `crossTarget` var (mirroring `staticLinkMode`: written once at
  startup, read-only thereafter). `HostClangArgs` returns
  `--target=<triple> -Wno-override-module --sysroot=<path>` when it is set,
  taking precedence over the Windows-host default. `-fuse-ld=lld` is appended
  only when an `lld` is found on PATH — needed for a genuine cross-arch link,
  optional when the target arch matches the host (the Docker lane).
- **IR triple**: the emitter stamps `target triple = "<triple>"` when a cross
  target is active (else the existing Windows-host branch, else nothing). No
  explicit `datalayout` line — LLVM derives it from the triple, matching the
  Windows precedent.
- **`-Wno-override-module`**: clang normalizes `--target` to its canonical
  4-field form (`aarch64-linux-gnu` → `aarch64-unknown-linux-gnu`), which
  differs textually from the stamped module triple and would otherwise warn on
  every build. The override is the intended behavior (the `--target` value
  wins), so the warning is suppressed for cross builds only.

## Implementation notes

- `codegen/llvm/hostclang.go`: `crossTarget` var + `SetCrossTarget` /
  `CrossTargetTriple` / `lldAvailable`; cross branch in `HostClangArgs`.
- `codegen/llvm/emitter.go`: cross-triple branch ahead of the Windows one.
- `main.go`: the two flags, `crossPresets`, and the resolve/validate block
  (placed after `SetStaticLink` so the `--static` guard sees the parsed value).
- The embedded-C runtime needs no special handling — it is compiled through the
  same `HostClangArgv`, so it inherits `--target`/`--sysroot` automatically,
  which is exactly TDD-00146's "the C runtime just follows the same flags."
- **Why the preset uses `aarch64-meego-linux-gnu`, not `aarch64-linux-gnu`.**
  Sailfish is RPM-based: its target libraries, crt objects, and gcc install live
  under `/usr/lib64` (and `/usr/lib64/gcc/aarch64-meego-linux-gnu/<ver>/`), not
  the Debian `/usr/lib` multiarch layout. clang's GCC-installation detector
  finds crt/libgcc/lib64 by matching the *triple* against the gcc install dir
  name — so with the generic `aarch64-linux-gnu` triple it fails to find the
  `meego` gcc dir and the link dies on `crtbeginS.o`/`-lgcc`. Passing the native
  `aarch64-meego-linux-gnu` triple makes the detector match, and everything
  (crt, libgcc, `/usr/lib64` search) resolves automatically — no manual
  `-L`/`-B` fixups. Verified against a genuine Sailfish 5.1.0.11 sysroot
  (exported from the `sailfishos-open/docker-sailfishos-builder` aarch64 image,
  which lays the target tree at `/`).

## Side effects discovered

**This flag is the clang-driver half of cross-compilation only; codegen is still
host-keyed.** Roughly a dozen codegen sites choose C APIs / struct layouts from
the host `runtime.GOOS`/`GOARCH` rather than the target — `ucontextLayout()`
(the fiber scheduler; Darwin vs Linux `ucontext_t` layouts differ → any
async/HTTP program built Mac→Linux would crash), `process.execPath`/`cluster`
(emit the Darwin-only `_NSGetExecutablePath` → a Linux link failure),
`nodePlatformName()`/`process.arch`, the `os.*` module, the math libcall
selection, `dgram`, and the FFI default-library names. The codebase states this
assumption explicitly (`emit_os.go:3`). Consequences:

- **OS-aligned cross builds are correct** (host OS == target OS, e.g. a Linux
  host building for another-arch Linux — the real Sailfish path on the Linux
  box + SDK): every host-keyed branch resolves to the target's own OS. Only
  genuinely arch-specific pieces (the ucontext context-switch, CPU features)
  remain, and both being Linux keeps `platform`/`execPath`/`os.*` right.
- **Cross-*OS* builds (e.g. Mac → Linux) are rejected at the CLI** rather than
  producing a binary that touches those paths and misbehaves or fails to link.
  The guard (host `runtime.GOOS` != the triple's OS) turns a silent footgun into
  a clear "run klainmain on a <targetOS> host" message.

Completing Stage 1 for cross-OS means threading a *target* OS/arch through those
sites (a "target abstraction" replacing the bare `runtime.GOOS` reads), at which
point the guard is lifted. Tracked as remaining Stage 1 work in TDD-00146; not
attempted in this ADR.

A compiled binary already indexes `process.argv` with the first user argument at
`argv[1]` (no Node script-path slot); noted in the example so it does not read
as a cross-compilation quirk.

## Verification

- `tests/crosstarget_test.go` (7 cases, run everywhere via `-emit-llvm`, no
  cross toolchain needed): the `sfos-aarch64` preset and a bare triple both
  stamp the right IR triple; a host build stamps none (non-Windows); and the
  five guards (missing sysroot, sysroot-without-target, nonexistent sysroot
  dir, `--static`, and a cross-OS target) all reject with their messages, and
  the `sfos-aarch64` preset resolves to its Linux triple.
- End-to-end on the Docker arm64 lane (`golang:trixie`, clang 19, arm64 Linux
  native on the M4): `klainmain --target sfos-aarch64 --sysroot / -o hello …`
  produced `ELF 64-bit LSB pie executable, ARM aarch64 … for GNU/Linux`,
  warning-free, and running it printed the correct output (array sort +
  TextEncoder UTF-8 byte count). Note this built `klainmain` *inside* the Linux
  container, so it exercised the **Linux-host → Linux-target** (OS-aligned)
  path — the one that is codegen-correct today, and the real Sailfish build
  path. It does **not** cover Mac-host → Linux codegen (see Side effects). (Mac.)
- **On real hardware, against a real Sailfish sysroot**: binaries cross-built
  with `--target aarch64-meego-linux-gnu --sysroot=<exported 5.1.0.11 rootfs>`
  (cksum-verified over the transfer) ran on a physical **Xperia 10 II, Sailfish
  OS 5.1.0.11**. A libc-only program printed `running on linux/arm64` and exited
  0; a **pcre2/RegExp program linked and ran**, with `ldd` confirming it resolved
  `libpcre2-8.so.0` from the device's `/usr/lib64` — closing the feature-lib +
  lib64 question end to end.
- `examples/cross_compile/sailfish_cli.ts` compiles and runs on the host and
  documents the cross-build + scp-to-phone recipe.
