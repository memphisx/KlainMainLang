# ADR-01666: Type arguments from a generic call's contextual type

- **Relations**: Implements TDD-00230
- **Date**: 2026-10-17

## Context

`const a: number[] = mk()` with `function mk<T>(): T[]` failed in codegen with "cannot infer type argument 'T'". So did `const r: PromiseWithResolvers<number> = Promise.withResolvers()`. tsc infers `T` from the declared type through the call's return type.

## Investigation

The checker's plain generic-call branch inferred only from arguments. Codegen's `inferGenericCallConcreteTypes` (`emit_generics.go`) did the same, so each needed the return-context step.

## Decision

- Checker: the call case calls `inferFromReturnContext` when there are no explicit type arguments. The new `CallTypeArgs(call)` returns the type arguments by name, from explicit arguments, then argument inference, then the return context, for a generic, non-overloaded callee.
- Codegen: when no argument infers a type parameter, `inferGenericCallConcreteTypes` asks `contextTypeArg`, which converts the checker's answer with `reprOf`. Only when that fails does it fall back to the parameter's default.
- A call synthesized for a builtin's lowering is mapped back to the program's call (`callOrigins`), so the checker is asked about a node it typed.

A call with no argument and no context (`make()` as a statement) still has no type argument and is still rejected.

## Verification

- `TestE2EGenericFunctionTypeArgFromContext` matches Node.
- `TestE2EGenericFunctionNoInferableParamRejected` now uses the context-free statement form. The old form printed through `console.log` and now compiles, which matches tsc, since `T` is inferred as `unknown` there.
- Verified on Mac.
