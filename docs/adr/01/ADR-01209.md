# ADR-01209: A top-level `const k = Symbol()` is a module global

- **Date**: 2026-09-28

## Context

BACKLOG 82, found writing `kml_event_target.ts` (ADR-01203): a module's
top-level `const kSecret = Symbol('secret')` read from a function or a
class member failed with "undefined variable 'kSecret__kml_mod1'". Node's
own modules key private state that way (`kDontThrowSymbol`); the global
module used a private static field instead. It is not builtin-specific:
any program's top-level Symbol const has the same failure.

## Investigation

`registerModuleGlobals` (`emit_exprs_vardecl.go`) promotes a top-level
binding to a module global only when `promotableInitInPrePass` proves its
type cannot drift between the pre-pass and the declaration. A call is
promotable when it is a known function, a lowered builtin, or on the
scalar-result allowlist; `Symbol(…)` was none of these, so the binding
stayed a `main()` local that functions cannot see.

## Decision

`isBuiltinSymbolCall` recognises `Symbol(…)` and `Symbol.for(…)` naming
the builtin (not a program binding). Such a call with pre-pass-stable
arguments is promotable, and `decideGlobalType` types it as
`inferExprType` does (the Symbol type), so the global and the
declaration's store agree.

## Implementation notes

`codegen/llvm/emit_exprs_vardecl.go`.

## Side effects discovered

A Symbol-keyed class member (`[kSecret]: number`) is still a parse error
("a computed class member name must be a constant"); tracked with the
computed-key work (BACKLOG 90).

## Verification

Mac (Apple Silicon): `TestE2ESymbolConstVisibleInFunctionsAndClasses`
matches Node v24.19; the same Symbol const in an imported module's class
reads correctly.
