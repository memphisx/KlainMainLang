# RegExp

> Part of the [Implementation Status](README.md) index.

**Coverage**: 100% (14/14) — all 7 stages done, including Stage 6 (`--static` linking, verified both on bare Linux and inside a real Docker `scratch` container — `docker/Dockerfile.regexp-test`). See [TDD-00035](../tdd/TDD-00035.md) for the full design and [ADR-00114](../adr/ADR-00114.md), [ADR-00115](../adr/ADR-00115.md), [ADR-00116](../adr/ADR-00116.md), [ADR-00117](../adr/ADR-00117.md), [ADR-00118](../adr/ADR-00118.md), [ADR-00119](../adr/ADR-00119.md), [ADR-00120](../adr/ADR-00120.md) for what actually shipped.

Matching now follows the **ECMAScript dialect by default** ([TDD-00067](../tdd/TDD-00067.md) Options A + B, [ADR-00206](../adr/ADR-00206.md); verified on Apple Silicon, pcre2 10.47). The whole-program `-regex=<mode>` flag selects fidelity: `es-unicode` (default — `PCRE2_UTF` code-point matching + `NEWLINE_ANY`, plus the option-level fixes), `es-ascii` (the option-level fixes only, byte matching — smallest/fastest for known-ASCII programs), or `pcre` (raw PCRE2/Perl semantics, no ES wrapping — an explicit opt-in for PCRE-only features, *not* a fallback). This retired the three PCRE2-vs-ECMAScript correctness bugs previously listed here (`$`/newline, unset backref, `\uXXXX`/`\xXX` throw) for both ES modes.

**Strict Coverage**: 2/14, ~14% — a row only counts here if it was independently repro-verified with zero known caveats or bugs, of any severity. See the 2026-08-11 audit ([ADR-00166](../adr/ADR-00166.md)) that produced this number; most rows here were already excluded before the audit by this page's own extensive, honestly-disclosed V1 scope narrowings (see Caveats below) — one new bug (flag validation) was found. The three PCRE2-vs-ECMAScript matching bugs disclosed 2026-08-17 are now **fixed** in the default `es-unicode` mode ([TDD-00067](../tdd/TDD-00067.md) Options A + B), but the default's own `NEWLINE_ANY` over-exclusion caveat (see Caveats) lands on the same already-excluded matching rows, so the count is unchanged.

**Caveats** (real, deliberate V1 scope narrowings — not bugs): `.test()` always matches from offset 0 and never reads/writes `.lastIndex`, even for a `g`-flagged RegExp — real JS's `.test()` shares `.exec()`'s stateful `lastIndex` iteration, but `.test()` itself wasn't revisited when `.exec()`'s `lastIndex` machinery landed (see [ADR-00115](../adr/ADR-00115.md)). `.exec()`/`str.match()`'s result array is scope-narrowed: an unmatched optional capture group becomes `""` rather than a true per-element `null` (no per-element-nullable-string array exists), and real JS's `index`/`input`/`groups` extra properties on the result aren't built. `str.matchAll()` returns an eager `string[][]`, not a real lazy iterator (no lazy-iteration infrastructure exists anywhere in this compiler). Neither `match()`/`matchAll()`/`replace()`/`replaceAll()`/`search()` implicitly coerces a non-`RegExp` argument (a compile-time error instead). `replace()`/`replaceAll()`'s replacement template supports `$1`-`$9`/`$&`/`$$` only (`` $` ``/`$'` — pre-/post-match text — are out of scope); its callback form is invoked with a fixed `(match, offset, string)` — real JS's variadic `...capturedGroups` in the middle isn't supported, since a callback's arity is fixed at compile time but a pattern's capture count is only known at runtime (a callback declaring more than 3 parameters is a compile-time error). `str.split()` only splits on a non-zero-length match — real JS's more intricate zero-length-match handling isn't replicated (see [ADR-00119](../adr/ADR-00119.md)), and captured groups in the split pattern are never spliced into the result (out of scope from the start). `u`(nicode)/`y`(sticky)/`d`(hasIndices) flags are out of scope for the whole feature's V1 (deferred, see the TDD's flag scope table); `g`/`i`/`m`/`s` are supported. `--static` linking works with zero extra flags (PCRE2 has no TLS-backend-style transitive dependency chain, unlike `fetch`'s libcurl) — verified on bare Linux and inside a real Docker `scratch` container; see [ADR-00120](../adr/ADR-00120.md). Building `.exec()` also found and fixed 3 general, RegExp-unrelated bugs — bare `ptr`-typed truthiness (`if (someString)`), array-vs-`null` comparison, and string content-based truthiness — see [ADR-00116](../adr/ADR-00116.md).

**Dialect-mode caveats** (the ECMAScript alignment shipped in [TDD-00067](../tdd/TDD-00067.md) Options A + B / [ADR-00206](../adr/ADR-00206.md); what still diverges from ES, per mode):

- **`es-unicode` (default) — `.`/`$`/`m` over-exclude three rare control characters.** The newline convention is `PCRE2_NEWLINE_ANY`, the closest single PCRE2 convention to ES's exact line terminators `\n \r \u2028 \u2029`, but it additionally treats `\x0b` (VT), `\x0c` (FF), and `\x85` (NEL) as line boundaries — so `.` excludes them and `$`/`m` anchor at them, where ES does not. An exact `.` needs the Option C pattern rewrite (not started). This caveat excludes every matching row from Strict Coverage.
- **`es-unicode` — a zero-length global match inside a multi-byte character stops iteration early.** Global iteration advances an empty match by one *byte*; if that lands mid-code-point, `PCRE2_UTF` rejects the start offset and the match is treated as "no match," ending the loop. Only reachable with an empty-capable pattern (`//g`, `/x*/g`) over non-ASCII text — narrow, and fixed properly by the `es-utf16` index stage (not started).
- **`es-ascii` — `.` matches `\r`.** With no compile context, PCRE2's default newline convention treats only `\n` as the line end, so `.` matches `\r` where ES excludes it. Deliberate: `es-ascii` is defined as option-bits-only. Use the default `es-unicode` (which excludes `\r`) if this matters.
- **`pcre` — raw PCRE2/Perl semantics throughout.** All three retired correctness divergences (`$`/newline, unset backref, `\uXXXX` throw) reappear by design in this mode; it exists for PCRE-only features and pattern porting, not ES fidelity.
- **`es-unicode` — `\w`/`\s`/`\b` are not Unicode-aware.** `PCRE2_UCP` is deliberately not enabled: its Unicode-property tables diverge from ECMAScript's (UCP `\s` matches U+180E, dropped as whitespace by ES in Unicode 6.3), and enabling it *lost* net conformance on `built-ins/RegExp`. So `\w`/`\s`/`\b` match the ASCII/PCRE-default set, not ES's Unicode definitions — the ES Unicode class semantics are Option C ([TDD-00067](../tdd/TDD-00067.md)). Code-point `.` (from `PCRE2_UTF`) is unaffected and works.
- **`u`(nicode) flag still not implemented in any mode.** `es-unicode`'s `PCRE2_UTF` gives it code-point matching, but `\u{…}` code-point escapes, surrogate handling, Unicode `\p{…}`/class semantics, and strict-syntax validation are Option C — the `u`/`y`/`d` flags remain out of scope (see the row below).
