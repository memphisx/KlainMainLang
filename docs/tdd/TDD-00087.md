# TDD-00087: `new Promise((resolve, reject) => …)` — the executor constructor

- **Status**: Implemented
- **Date**: 2026-08-20
- **Notes**: resolve/reject as per-site closures capturing a pending task promise; `@__kml_promise_settle` (the missing bare-promise settle+wake+drain, factored from `__kml_task_finish`) with first-settle-wins; the executor invoked immediately with param hints so `resolve(x)`/`reject(e)` type-check. Deferred resolution (a `resolve` stashed into `setTimeout`) drives the lightweight await through a microtask-drain + one-shot timer-fire loop (`@__kml_timer_fire_next`). Direct use only — returning a promise across a function boundary hits the separate promise-return-flattening gap

## Context

`Promise.resolve`/`.reject` ([ADR-00262](../adr/ADR-00262.md)) create *settled*
promises. The executor constructor — `new Promise((resolve, reject) => …)` — is
the last missing core Promise API and the important one: it is how you bridge a
callback/timer/event API into a promise, by capturing `resolve`/`reject` and
calling one later. Today `new Promise(...)` fails at codegen ("unknown class
'Promise'").

The task promise struct, `.then` reactions, the microtask FIFO, the fiber
scheduler, and the timer queue all already exist. What's missing is (1) a way to
*settle a bare promise and wake its awaiter/reactions* from an arbitrary call
site, (2) building `resolve`/`reject` as closures over the promise, and (3)
driving timers while awaiting a promise a timer will settle.

## Design

### The promise, and the executor call

`new Promise<T>(executor)` (emit_classes.go's `emitNewExpression`, intercepted on
`ClassName == "Promise"` → `emitNewPromise`):

1. `p = @__kml_task_alloc_promise()` — pending, waiter=null, reactions=null.
2. Emit two per-site closures capturing `p`:
   - `resolve` — header `{ @__kml_promise_resolve_N, p }`, function
     `void @__kml_promise_resolve_N(ptr %p, <T> %v)`: `storePromiseValue(%p, %v)`
     then `@__kml_promise_settle(%p, 1)`.
   - `reject` — header `{ @__kml_promise_reject_N, p }`, function
     `void @__kml_promise_reject_N(ptr %p, ptr %err)`: store the error bits into
     v0, then `@__kml_promise_settle(%p, 2)`.
   The closure ABI is exactly `{fnptr, env}` with env (here `p`) passed as the
   first argument — the same shape `emitClosureCallByPtr` / the timer & microtask
   drains use.
3. Emit the executor with param hints `resolve: (T)=>void`, `reject: (Error)=>void`
   (via `emitArrowFunctionWithHints`), so the body's `resolve(x)` call gets the
   right signature even though the arrow leaves the params unannotated. Invoke it
   immediately: `emitClosureCallByPtr(executor, [resolve, reject])`.
4. Return `p` typed `Promise<T>` (PromiseTask). `T` comes from `new Promise<T>`'s
   type argument, else `number` (i64) by default.

### `@__kml_promise_settle(ptr %p, i64 %state)` — the missing helper

Factored from `__kml_task_finish`'s body (which today only settles a promise
derived from a *task*). Given the value is already stored in v0/v1 by the caller:

```
if p.state != 0: return              ; first settle wins (later resolve/reject ignored)
p.state = %state
w = p.waiter (field 1)
if w != null: w.pendingProm (task field 6) = null    ; wake the parked awaiter
@__kml_promise_drain_reactions(p)     ; enqueue .then/.catch/.finally reactions
```

The first-wins guard makes a second `resolve`/`reject` (or `resolve` then
`reject`) a no-op, per spec. Setting `state` and clearing the waiter's
`pendingProm` is exactly what the scheduler poll (`__kml_task_sched_step`'s
`chkpp`/`chkpres`) resumes on, so a parked awaiter is resumed; the reaction drain
fires `.then` chains.

### Synchronous vs deferred resolution

- **Synchronous** — the executor calls `resolve`/`reject` before returning (or the
  promise is settled by the time it is awaited). Fully covered by the above: by
  the time `new Promise` returns, `p` is settled; `await`/`.then` observe it.
- **Deferred** — the executor stashes `resolve` into a later callback, canonically
  `setTimeout(() => resolve(v), ms)`. `resolve` is a closure value captured into
  the timer callback's env like any value. The gap: `await p` while `p` is pending
  must let the timer fire. `__kml_task_await_ready`'s top-level drive loop calls
  `__kml_task_sched_step` (which pumps libcurl + the task array) but **not** the
  timer queue. Fix: factor `@__kml_timer_fire_next()` out of `__kml_timer_drain`
  (find the earliest-due timer, sleep until due, fire its closure; return 1 if one
  fired, 0 if the queue is empty) and call it from the drive loop. Then the timer
  fires → its callback calls `resolve` → `@__kml_promise_settle` flips `p`'s state
  → the drive loop's `p.state != 0` check exits the await. An async fn awaiting a
  deferred promise runs inline (current_task null) and drives the same loop, so
  this covers both top-level and in-async-fn awaits. `new Promise` whose executor
  schedules a timer pulls in the timer runtime already (via `setTimeout`).

### First-wins / already-settled edge cases

`@__kml_promise_settle`'s state guard covers double-resolve, resolve-then-reject,
and reject-then-resolve (first wins). Calling `resolve`/`reject` after the promise
is already awaited-and-freed is out of scope (a genuinely dangling continuation);
the common patterns settle exactly once.

## Open questions

- **`Promise.reject` value typing** — a `new Promise<T>` with no type argument
  defaults `T` to `number`; a reject-only executor never observes `T`. Consistent
  with `Promise.reject`'s default ([ADR-00262](../adr/ADR-00262.md)).
- **Non-arrow executor** — V1 targets an arrow / function-expression executor; a
  named-function-reference executor (rare) can be a clean rejection initially.
- **`resolve(aPromise)` (thenable adoption)** — resolving with another promise
  should adopt its state (JS flattens). V1 stores the promise as the value (no
  adoption); revisit if needed.
