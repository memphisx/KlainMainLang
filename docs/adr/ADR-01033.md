# ADR-01033: Windows `child_process` — libuv's environment block and program search, `kill` `ENOSYS`, `fork` by executable path; the `kill` error object

- **Relations**: `Implements TDD-00180` (§3); `Extends ADR-00728`, `ADR-00737`, `ADR-00754`, `ADR-00762`
- **Date**: 2026-09-21

## Context

Four §3 rows of the [TDD-00180](../tdd/TDD-00180.md) audit remained:

- **Environment block.** A custom `env` was converted entry by entry and handed to `CreateProcessW` unsorted, with duplicates, and without the variables a Windows program needs to start (`SYSTEMROOT` above all — without it Winsock and most of the CRT fail in the child).
- **Program search.** `CreateProcessW(NULL, cmd, …)` runs its own search: the *parent's* executable directory, the parent's cwd, the system directories, then the *parent's* `PATH`. Node resolves the program against the **child's** cwd and the **child's** `PATH`, so `spawn('tool', { env: { PATH } })` looked in the wrong place.
- **`process.kill`** terminated the target for every signal. libuv terminates for `SIGTERM`/`SIGKILL`/`SIGINT`/`SIGQUIT` and answers `ENOSYS` otherwise.
- **`child_process.fork`** re-spawned `argv[0]`, which is wrong once the process was started through `PATH` or has changed directory.

## Investigation

libuv's `src/win/process.c`: `make_program_env` (sorted with a case-insensitive ordinal compare, the `required_vars` list carried over from the parent when absent), `search_path` (name as given first when it has an extension, then `.com`, then `.exe`; a name with a directory part is looked up there only; a bare name in the cwd and then each `PATH` element, quotes honoured), and `uv_kill`. De-duplication happens one layer up, in Node's `child_process.js` (case-insensitive, first spelling wins).

Batch files are deliberately not part of the search: without a shell they are refused (`EINVAL`, CVE-2024-27980 — ADR-00740).

Writing the `ENOSYS` test crashed the test program with an access violation **on the error path, not in `kill`**: `__kml_process_kill` built a 24-byte legacy error object (`{kind, message, name}`), and `e.code` in the catch handler read field 3 of the full error struct, past the allocation. That is a cross-platform bug — any program that read `.code`/`.errno`/`.syscall` off a `process.kill` failure was reading garbage.

## Decision

- `build_env_block()` replaces the two ad-hoc assemblies: markers first (so they win under first-wins de-duplication), then the custom list or the parent's block; de-duplicate; add the missing required variables when the list was custom; sort; emit. `NULL` (inherit untouched) when there is neither a custom list nor a marker.
- `search_program()` resolves the program and the result is passed as `lpApplicationName`, so `CreateProcessW`'s own search never runs. Not found is `ENOENT` without calling `CreateProcessW`. The `file` argument of `__kml_win_spawn` (previously ignored) is now the program — `execvp`'s meaning — and `argv[0]` only what the child sees.
- `kill`: signals other than 15/9/2/3 (and `0`, handled earlier) set `ENOSYS`.
- `fork` passes `__kml_win_self_exe()` as the program.
- The `kill` error is a full, zero-filled `errorObjType` carrying `code`, `errno` (through `__kml_uv_errno`, [ADR-01031](ADR-01031.md)) and `syscall: 'kill'`. The message is unchanged.

## Implementation notes

`codegen/llvm/win32src/win32proc.c`, `runtime_spawn_win.go` (fork), `runtime_process.go` (error object), `runtime_fs.go` (`ESRCH`/`ECHILD` in the errno→code table, which a `kill` failure needs to name itself).

The markers still carry raw handle values (`KML_WIN_INHERIT_FD`, `KML_WIN_RR`). They are only meaningful to a process that inherited those handles through the explicit handle list, and the child scrubs them at startup, so this is left as is.

## Side effects discovered

An untyped `'exit'` listener prints a `null` code as `0` (`(code, sig) => …`); annotating the parameters (`code: number | null`) prints `null`. That is the general untyped-callback-parameter inference, not something this change touches.

## Verification

Windows 11 (26200): new `tests/childprocess_faithful_windows_test.go` — a native child dumps its environment in OS order (sorted, `ALPHA` de-duplicated behind `Alpha`, `SystemRoot`/`PATH`/`TEMP`/`USERPROFILE` present under a four-variable custom `env`); a program found only on the child's `PATH`, by bare name, while the same name is `ENOENT` on the parent's; `kill(pid, 'SIGHUP')` → `ENOSYS` with the child still alive and then `(null, 'SIGTERM')`. `TestE2EProcessKillErrorCarriesCodeAndSyscall` (every host) covers the error-object fix. The `ChildProcess|Spawn|Exec|Fork|Cluster|IPC` suites pass (91 s). Linux/macOS not run here; the only shared change is the error object and the two errno names.
