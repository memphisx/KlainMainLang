# ADR-00124: EventSource Stage 2 — named events, `onopen`/`onerror`

- **Relations**: Implements [TDD-00038](../tdd/TDD-00038.md), Extends [ADR-00123](ADR-00123.md)
- **Date**: 2026-08-07

## Context

[ADR-00123](ADR-00123.md) shipped Stage 1: SSE record parsing and `onmessage` for unnamed records, with a genuinely named `event: foo` record deliberately silently withheld (nowhere to deliver it to yet). This ADR implements Stage 2, TDD-00038's last committed stage: `addEventListener(type, cb)`/`removeEventListener(type, cb)` for named events, and `onopen`/`onerror` lifecycle properties.

## Investigation

Stage 1's `onmessage` was implemented as a single dedicated `FuncType`-typed field — deliberately, per that ADR's own reasoning, since Stage 1 alone never needed to store more than one listener per event name. `addEventListener` breaks that assumption directly: it must support multiple listeners for the same event name, and arbitrary (not just `"message"`) event names — a single field structurally cannot do either. Confirmed this was the right moment to build the multi-listener storage TDD-00038's own Design section always called for (a `Map<string,ptr>` of listener lists, reusing `EventEmitter`'s existing C helpers directly) rather than before, when nothing needed it yet.

Read `runtime_eventemitter.go`'s listener-list helpers in full (`__kml_ee_list_create/_push/_remove`, a 24-byte header + `{ptr listener, i64 once}` 16-byte entries) and `emitEventEmitterEmit`'s snapshot-copy-before-iterating dispatch algorithm (`emit_eventemitter.go:329`) — confirmed both are directly reusable: the list helpers as literal `call`s from new hand-written IR, the snapshot-before-iterate defensive pattern (protecting against a listener removing itself or another listener mid-dispatch) as something to *replicate* in IR rather than reuse directly, since `emitEventEmitterEmit` itself is Go-level codegen (`e.emitInstr`/`freshReg`-based) with no standalone callable form, the same limitation Stage 1 already hit and worked around for `emitStringConcat`.

Confirmed directly (compiling a throwaway program) that a *named*, non-inline listener function (`const handler = (ev) => {...}` — as opposed to an arrow literal passed straight to `addEventListener`) had no way to be correctly typed: `MessageEvent` wasn't a resolvable type-annotation name anywhere in this compiler, so `(ev: MessageEvent) => ...` would have failed as an unknown type. A real, if narrow, gap — found by testing the less-common-but-legitimate "extract the handler first" usage pattern before assuming only inline arrow functions needed to work.

## Decision

**Additive design, not a migration of Stage 1's `onmessage` field.** Real spec behavior: `.onmessage =` and `addEventListener('message', cb)` are two independent registration surfaces that both fire for an unnamed record. Rather than migrating `onmessage`'s existing, already-shipped-and-tested field-based storage into becoming sugar over the new map (the TDD's own originally-sketched "one dispatch mechanism, two registration surfaces" framing), this stays two genuinely parallel mechanisms that both get consulted at dispatch time: the dedicated field (checked only when the resolved type is exactly `"message"`) *and* the listener map (checked for whatever the resolved type actually is, always). Both `onopen`/`onerror` follow the identical shape — dedicated fields *and* general dispatch to `"open"`/`"error"` in the map. This was a deliberate divergence from the TDD's literal wording, decided because it avoids reworking already-shipped Stage 1 code and produces identical observable behavior to a true single-mechanism design for every case that matters in practice.

**Field layout: pure appends, not interleaved insertions.** `onopen`/`onerror` were appended *after* `onmessage` on `EventSourceType()` (indices 5, 6) rather than inserted among the existing hidden fields — every Stage 0/1 field keeps the exact index it already had, so `VisibleFields()`'s existing hidden-prefix-skip-count needed no change at all. The new listener-*map* handle, by contrast, was **not** added to the KML object at all — it lives on the runtime's own transfer-tracking entry struct instead (`{ ptr pending, ptr instance, i64 consumedOffset, i64 state, ptr listeners }`, appended at index 4), reachable from Go-level `addEventListener`/`removeEventListener` codegen via the object's *already-existing* hidden handle field. This was chosen specifically to avoid a second full field-reindexing migration on the KML object (Stage 1 already needed one once, moving `readyState` from index 2 to 3) — appending to the *entry* struct instead needed updating every existing entry-struct `getelementptr`'s type literal (mechanical, `sed`-style, no index changes) rather than re-deriving new indices throughout.

**`onopen`/`onerror` reuse `MessageEventType()` rather than a separate `Event` type**, for closure-call ABI uniformity — every dispatch site in this design always calls a listener with exactly one `ptr` argument, so introducing a second, zero-argument calling convention purely for two event names wasn't worth the complexity, even though real `EventSource` passes a plain, data-less `Event` for these two. `data`/`lastEventId` are simply left empty on the payload passed to `onopen`/`onerror` listeners.

**`MessageEvent` is now a resolvable type-annotation name** (`ResolveTypeName`, `types.go`, alongside the existing `Response`/`Date`/`URL`/etc. entries) — the fix for the gap found in Investigation. `EventSource` itself was added to the same switch for symmetry (a user writing `const es: EventSource = new EventSource(...)` had the identical gap, unexercised by any test until now since every existing call site left the type to infer from the `new` expression itself).

**`{once: true}` is not supported for `addEventListener`** — every registered listener is a plain, non-self-removing entry (`__kml_ee_list_push`'s `once` argument is always `0`). A deliberate, minor scope narrowing: real-world SSE listener code essentially never uses this option, and adding it would mean threading a third argument through `addEventListener`'s call surface for a feature with no concrete use case driving it yet.

## Implementation notes

- **New runtime functions** (`runtime_eventsource.go`): `__kml_eventsource_add_listener`/`_remove_listener` (get-or-create the per-event-name list via the existing `__kml_map_str_get`/`_set` + `__kml_ee_list_create` primitives, then `_push`/`_remove`), `__kml_eventsource_dispatch_event` (the general "call every listener registered for this type" walker, snapshot-copy-then-iterate as described in Investigation).
- **Go-level codegen** (`emit_eventsource.go`): `resolveEventSourceListenerArg` mirrors `resolveEventEmitterListenerArg` (emit_eventemitter.go) directly — same hint-if-arrow-literal-else-plain-emitExpr shape, same three validation checks (is a function, exactly one param matching the payload type, void return). `emitEventSourceAddListener`/`emitEventSourceRemoveListener` are new, dispatched from `emit_call.go` exactly like `.close()` already was (`mem.Property == "addEventListener" && ....IsEventSource`).
- **Two mechanical bugs found and fixed during implementation, both the same class as one already hit in Stage 0** ([ADR-00122](ADR-00122.md)'s `%entry`/`entry:` label collision): all three new Stage 2 IR functions (`add_listener`/`remove_listener`/`dispatch_event`) were first written with their first parameter literally named `%entry`, again colliding with the implicit `entry:` block label — caught immediately via a manual `--emit-llvm` + `clang` compile (the exact same class of error, "unable to create block named 'entry'"), fixed by renaming to `%es_entry` throughout, matching the established fix. Separately, removing Stage 1's `noop:`/`buildmev`/`callcb` labels while restructuring `dispatch_record`'s tail left one earlier branch (`skipstrip`'s `shoulddispatch` check) pointing at a now-deleted `%noop` label — an "undefined value" verifier error, fixed by re-adding a small dedicated `noop: ret void` block as its own separate return point alongside the new `afteronmsgfield: ... ret void` path.

## Side effects discovered

**`MessageEvent`/`EventSource` weren't resolvable type-annotation names** (see Investigation/Decision) — a real, narrow pre-existing gap (nothing before this stage ever needed to *name* either type in source, only construct/receive them structurally), fixed as part of this same work rather than deferred, since Stage 2's own `addEventListener` usage pattern is what surfaced it.

No other bugs found. `{once: true}` and the `onmessage`/`addEventListener('message', ...)`-as-two-parallel-mechanisms design (see Decision) are deliberate scope choices, not discovered-but-unfixed gaps.

## Verification

- `go build -o klainmain .` and `go vet ./...` clean.
- Manually compiled and ran (bypassing `go test`) against real local Go servers covering: `onopen` firing on connect, `onerror` firing on a refused connection, a named `"greeting"` event reaching `addEventListener` while an unnamed record simultaneously reaches `onmessage` on the same connection, and `removeEventListener` actually stopping delivery (`count` stayed 0) — including a case using `MessageEvent` as an explicit annotation on an extracted, non-inline handler, confirming the type-name-resolution fix.
- `go test ./...` passes in full, including 5 new Stage 2 tests in `tests/eventsource_test.go` (`onopen`, `onerror`, `addEventListener` receiving a named event, `removeEventListener` stopping delivery, and `onmessage`/`addEventListener('message', ...)` both firing independently for the same unnamed record).
- Ran the full pre-existing suite to confirm no regressions from the entry-struct/object-struct field-layout changes (blanket-replaced across every existing `getelementptr` site, verified each replacement was index-safe before applying): all pass.
- `examples/eventsource/eventsource.ts` extended with `onopen`/`onerror`/`addEventListener` sections; `tools/httpbin-lite` gained a `/stream-named` fixture endpoint. Compiled and ran directly, output matched every inline expected-output comment.
- Verified only on the x86-64 Linux development box (see `CLAUDE.md`'s platform-flagging rule) — pure LLVM-IR-text/Go compiler logic plus already-platform-neutral libcurl/`EventEmitter`-helper reuse, not expected to be platform-sensitive, but not directly confirmed on the Apple Silicon Mac.
