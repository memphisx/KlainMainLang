# TDD-00041: True per-file module scope (mangled internal names)

- **Status**: Implemented
- **Date**: 2026-08-09
- **Notes**: Also unblocked import aliasing as a direct consequence — see `docs/status/MODULES.md`

## Context

[ADR-00022](../adr/ADR-00022.md) shipped named `import`/`export` (V1) with a deliberate simplification: **one flat, globally-unique namespace across every merged file.** Concretely, every top-level declaration name (function/`const`/`let`/`var`/`interface`/`type`/`enum`/`class`) must be unique across *every* file the resolver pulls in, not just within the file that declares it — two unrelated files cannot both declare a same-named helper function, interface, or enum if both end up reachable from the same entry file. `docs/status/MODULES.md` tracks this as the single largest gap in the Modules area (~31% coverage) — the single biggest structural obstacle to a program large enough to actually want multiple files, since real multi-file programs routinely want an internal `helper`, `validate`, or `Result` name reused per-file without every file's author having to negotiate a project-wide unique-name convention by hand.

It's also the direct prerequisite for import aliasing (`import { a as b }`, parsed but explicitly rejected today — ADR-00022's Investigation flagged a naive AST rename as unsafe without real scope-awareness) and, more speculatively, for `export default` and namespace imports (`import * as ns`), both still unstarted — see `docs/status/MODULES.md`. This TDD scopes *only* the per-file-scoping problem itself; whether those other Modules gaps ride on top of the mechanism built here is left to their own follow-on TDDs/ADRs once this lands (see Open Questions).

Picked up now per this project's current prioritization: the three original focus areas (REST API interaction, file I/O, process/CLI) are now substantially built out, so core-language completion is weighted co-equally, and this specific gap is worth a TDD of its own before further module work, rather than growing piecemeal via one-off ADRs.

### Non-goals: this does not make imports Node/webpack-equivalent

Naming/scoping is one gap among several in `docs/status/MODULES.md`; closing it does **not** bring `import`/`export` to real Node.js/webpack parity, and the remaining gaps are deliberately left out of this document rather than added as further stages here:

- **Top-level side-effecting execution** (run imported files' top-level code once, in dependency order, with real circular-import/live-binding semantics) — ADR-00022's other deliberate V1 cut, and a materially different problem (module lifecycle/execution order, not naming). This is the largest remaining piece and, unlike the others below, will likely need its own TDD when picked up — not scoped here or folded into this one.
- **Surface features**: `export default`, `import * as ns` (namespace imports), re-exports (`export { x } from './other'`). Each is comparatively self-contained; namespace imports may end up reusing this TDD's rewrite mechanism (see Open Questions) but aren't designed here.
- **Real module resolution** (`node_modules`, `package.json` main/exports fields, index-file resolution, extension resolution beyond auto-appended `.ts`) — this project has no package ecosystem today by design (relative paths only); closing this gap is a product decision (does this compiler ever want to consume npm packages?) before it's an implementation one.
- **Dynamic `import()` / `import.meta`** — needs a real runtime module loader, which doesn't fit the current whole-program-static-compile architecture as an incremental extension; would be a materially different mechanism, not a follow-on stage of this one.

Kept as a flat list here (rather than a TDD-per-item) purely as a pointer for later — none of these are scoped in any detail yet, and each should get its own Context/Design pass when picked up, following the same "small, focused TDD" pattern used elsewhere in this project (e.g. TDD-00035/38/39/40's staged sub-parts each belong to one coherent feature, not a whole area).

## Design

### The core mechanism: rename, don't re-architect

ADR-00022's whole-program design — parse every reachable file, merge into one `*ast.Program`, hand the *entirely unmodified* `codegen/llvm` emitter a bigger AST — is worth preserving. `codegen/llvm` has no notion of a "module" today and doesn't need one: it just needs every top-level name it sees to already be unique and already correctly bound. That means per-file scoping can be implemented entirely as a **rewrite pass inside `resolver/`, before the merge step**, with zero changes to `codegen/llvm` — the same property ADR-00022 called out as the biggest reason its own design was cheap.

Concretely: give every file's top-level declarations an internally-mangled name (`name__f<fileIndex>`, e.g. `helper__f2` — an integer suffix tied to the file's position in resolution order, not a hash of its path, since path characters aren't valid in LLVM identifiers and a per-build sequential index is simpler and entirely internal). Then walk each file's own AST and rewrite every *reference* that resolves to one of that file's top-level declarations to use the mangled name instead. A reference to an *imported* name (`import { a } from './x'`, or aliased `import { a as b }`) gets rewritten, within the importing file only, to point at the target file's mangled name for `a` — which is what finally makes aliasing safe: `b` inside the importing file simply *is* `a__f<N>` after rewriting, no separate rename step or shadowing risk involved.

This requires the rewrite pass to be **scope-aware**, not a blind find-and-replace: a function parameter, a `let` inside a block, a `catch (e)` binding, a `for (const x of ...)` loop variable, or a generic type parameter (`<T>`) can all legally shadow a top-level name, and references inside that shadowed scope must **not** be rewritten. This is the real substance of the feature — effectively a small binder/scope-tracker over the whole expression/statement/type grammar, tracking which identifiers are currently in scope as the walker descends and only rewriting a reference when it resolves all the way up to a top-level declaration (of the current file, or an explicit import).

### Two shapes considered

- **A. Full per-file privacy (recommended)**: mangle *every* top-level declaration unconditionally, exported or not, whether or not its name happens to collide with anything elsewhere. This matches real ES module semantics — a file's non-exported top-level bindings are private *by construction*, not merely "happens not to collide today." The rewrite mechanism is identical either way; this shape just always uses it, which is simpler to reason about and test (no separate collision-detection pre-pass, no "sometimes mangled, sometimes not" naming that varies build-to-build as unrelated files are added).
- **B. Rename-on-collision only**: keep today's flat namespace as the fast/common path, and only mangle+rewrite when two files actually declare the same top-level name (the technique bundlers like Rollup use for tree-shaken output). Smaller-looking diff-wise, but it needs the *exact same* scope-aware walker as (A) — collision is only knowable after parsing every file, so the "does this identifier resolve to a top-level decl" logic still has to exist and run globally; (B) just skips invoking the rewrite for the (usually large) majority of non-colliding names. It also reintroduces a subtle correctness gap (A) avoids: two files that don't collide *today* can start colliding the moment a third file is added to the build, silently changing which names get mangled — a form of non-locality real per-file scoping is supposed to eliminate.

Recommend **A**: given the walker has to exist regardless, and (A) is the version that's actually semantically "real per-file module scope" rather than "usually-unique flat namespace with a fallback," building the harder-seeming version isn't meaningfully more implementation work and produces the more honest result.

### What the walker needs to handle

A non-exhaustive but representative list of scope-introducing constructs the rewrite pass must track correctly (the implementation phase should audit `ast/nodes.go`'s full ~77 node types against this, not just this list):

- Function/arrow function parameters (including destructured and default-valued params) and their bodies.
- Block-scoped `let`/`const` (including destructuring patterns) inside any `{}` block.
- `for`/`for...of`/`for...in` loop-variable bindings.
- `catch (e)` clause bindings.
- Generic type parameters (`<T>`, `<K, V>` since [TDD-00037](TDD-00037.md)) on functions/interfaces/classes — these can shadow a top-level type name and must resolve to the local type parameter, not a mangled top-level declaration, everywhere within that declaration's scope.
- Class bodies: a class's own name is a top-level declaration (needs mangling + rewriting at every reference, including `new ClassName()`, `instanceof ClassName`, `extends`/type positions), but member/method/field names and `this.x` accesses are not top-level identifiers at all and must be left alone entirely.
- `TypeAnnotation` nodes referencing a user-defined `interface`/`type`/`enum`/`class` name by string — these are a *type-position* reference to a top-level declaration and need the same rewrite as a value-position `Identifier`, but don't participate in value-scope shadowing (a type name and a value name are different namespaces in TypeScript, same as real JS/TS).

### Merge step after rewriting

Once every file's own AST has had its top-level references rewritten (in-file references to its own declarations) and its import references rewritten (to the target file's mangled names), the merge step in `resolver.ResolveProgram` stays close to what it is today: concatenate non-entry files' declarations (in dependency order) followed by the entry file's own statements, drop `ImportDeclaration` nodes, unwrap `ExportDeclaration` nodes. The existing global name-uniqueness check (`resolver.go`'s `checkNames`) becomes a should-never-fire safety assertion rather than a real user-facing error path, since uniqueness is now guaranteed by construction — worth keeping as a defensive check rather than deleting, in case the rewrite pass has a gap.

| Scope-aware AST walker (binder) tracking nested lexical scopes | ❌ Missing | The real substance of this TDD — nothing in the codebase today walks the full expression/statement grammar with scope tracking; `inferExprType` (`codegen/llvm/emit_exprs_types.go`) is the closest existing analogue (a whole-AST-walking, non-codegen pass) but doesn't track scope/shadowing, it only classifies expression types |

## Open questions

- **Diagnostics readability**: once names are mangled before `codegen/llvm` ever runs, do any user-facing compiler errors emitted from codegen (type errors, undefined-reference errors) risk showing a mangled name like `helper__f2` instead of the name the user actually typed? Needs an answer before implementation — likely a small side-table (mangled name → original name + source file) threaded through just far enough for error-formatting to use it, without codegen otherwise needing to know mangling exists.
- **Does this TDD's mechanism get reused directly by `export default`/namespace imports** (`import * as ns from '...'`, still unstarted per `docs/status/MODULES.md`), or does it just make them easier later? A namespace import in particular (`ns.a`, `ns.b`) looks like it wants the same "rewrite a reference to point at a specific file's mangled declaration" mechanism, just keyed by member-access instead of a flat local binding — worth revisiting once this lands, but deliberately not designed here.
- **Should the per-file mangled suffix be visible/stable across incremental builds** (e.g. for future incremental-compilation or debugging use), or is a purely sequential, resolution-order-dependent index acceptable given there's no incremental-build story today (per ADR-00022) and IR-level names are otherwise never user-facing? Leaning toward "acceptable, revisit only if incremental compilation is ever scoped."
- **Interaction with generics monomorphization** ([TDD-00010](TDD-00010.md)): generic functions/classes already synthesize their own per-instantiation names (V1 monomorphization). Confirm the mangling scheme here composes cleanly with that existing name synthesis rather than producing a double-mangled or colliding name — needs checking directly against `codegen/llvm/emit_generics.go` during implementation, not assumed from this document alone.
