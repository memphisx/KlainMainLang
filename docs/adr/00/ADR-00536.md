# ADR-00536: Array destructuring of a string binds its characters

- **Relations**: Extends ADR-00535
- **Date**: 2026-08-31

## Context

`const [a, b] = "xy"` was a compile error ("array destructuring requires an
array variable, function call, or array literal"). Real JS destructures a string
by its characters (`a` = `"x"`, `b` = `"y"`) via its iterator. The companion
`for…of`-over-string work (ADR-00535) added `emitStringToCharArray`, so the
character materialization already existed.

## Investigation

`resolveArrayDataPtr` (`emit_arrays_core.go`) is the shared source-resolver for
both declaration destructuring (`const [a,b] = …`) and assignment-form
destructuring (`[a,b] = …`). It switched on the source node kind (identifier /
call / array literal) and errored otherwise — a string identifier hit "is not an
array", a string literal hit the default error.

## Decision

Add a string case at the top of `resolveArrayDataPtr`, guarded by the strict
`isForOfStringTy` predicate (ADR-00535): materialize the character array via
`emitStringToCharArray` and return its `(dataPtr, len, string)` triple, feeding
the existing unpack machinery. Both callers (declaration and assignment) gain
string support for free. Extra targets past the string length read the empty
string, the same documented past-length behavior array destructuring already has
(ADR-00157).

## Implementation notes

`emit_arrays_core.go` only. Placed before the node-kind switch so a string
identifier or literal is caught before the "not an array" branches. Per byte,
not per code point — the same narrowing as `for…of`/`Array.from`.

## Side effects discovered

String *spread* (`[..."abc"]`) and spread of a string into a call remain
unsupported — separate spread machinery, not this destructuring path.

## Verification

`TestE2EStringDestructuring` (new): a literal, a 3-character literal recombined,
and a string variable, cross-checked against real Node. The array-destructuring
and for-of suites pass. Verified on Mac (Apple Silicon).
