# ADR-01076: util.inspect — `maxArrayLength`, `-0` inside containers, display width

- **Relations**: Extends ADR-01067 (the inspect layout runtime)
- **Date**: 2026-09-22

## Context

BACKLOG §0 item 6, the residue after ADR-01067: an array of any length printed every element (Node shows 100,
then `... n more items`); `-0` printed `0` inside a container (`[ -0 ]` in Node — the top-level case was already
right); the column grouping measured entries in code points where Node's `getStringWidth` counts a full-width
glyph as 2 and a combining mark as 0.

## Investigation

Node's `formatArray` walks `min(length, maxArrayLength)` entries and pushes one `... ${remaining} more item(s)`
entry; `groupArrayElements` leaves that last entry out of the column computation (`outputLength--`) and appends
it after the grouped rows; `reduceToSingleString` treats it as an ordinary entry. `getStringWidth` classifies a
code point as zero-width (C0/C1 controls, combining marks, format characters, variation selectors), full-width
(the East Asian ranges) or 1.

## Decision

- `__kml_inspect_push_more(list, remaining)` appends the entry and flags it (`extra`); `group_array` groups the
  entries before it and re-appends it. The three array walkers cap at 100: `emitInspectArray` (static),
  `inspect_arr` and `kj_inspect` in `dynjson.c` (dynamic / boxed).
- `str_width` in `inspect_reduce.c` is Node's `getStringWidth` (its range tables verbatim).
- `emitInspectField`'s number arm applies the existing `-0` bit-pattern check (`inspectNegZero`, shared with
  the top-level path).

None.

## Verification

Windows, byte-identical to Node 24: 105- and 101-element number arrays (`... 5 more items` / `... 1 more
item`, grouped columns), a 120-element string array, `[ -0, 0, 1.5, -0 ]`, `{ z: -0 }`, a mix of CJK, accented
and combining-mark strings, a 12-element CJK/ASCII array's column widths, an `any` array. E2E:
`tests/inspect_residue_test.go`.
