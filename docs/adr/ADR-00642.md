# ADR-00642: Decorators Stage 2 — method decorators with descriptor replacement

- **Relations**: `Implements TDD-00161` (Stage 2), `Extends ADR-00641`
- **Date**: 2026-09-02

## Context

TDD-00161 Stage 2: experimental **method decorators** — `(target, key,
descriptor)` — including the case where the decorator *replaces* the member by
mutating `descriptor.value` or returning a new descriptor. This is the stage
that collides with the static class model: a static class dispatches methods by
a compile-time direct call / vtable, but a method decorator can swap the
implementation at class-definition time, making dispatch runtime-determined.

## Investigation

- The tag-12 dynamic-function ABI (`emit_dynfunc.go`) is
  `i64 fp(ptr env, i64 thisBox, i64 argc, ptr argv)`. A static instance method
  `@<Impl>_<m>(ptr this, ...args)` is shape-compatible if the receiver comes
  from the call-time `thisBox` rather than a bound env — so a method can be
  boxed into a tag-12 callable by a generated adapter that unboxes the receiver
  and arguments and calls the static function. `emitDynClosureAdapter` is the
  template.
- Method dispatch is `emitClassCall` (`emit_classes.go`). Routing a *decorated*
  method through a runtime slot is a gated change there: non-decorated methods
  (the whole rest of the program) keep the existing static path byte-for-byte.
- The descriptor-replacement contract (TS `__decorate`): start with
  `descriptor.value = <method>`; each decorator may mutate the descriptor or
  return a replacement (`if (r) descriptor = r`); the member's final
  implementation is the effective `descriptor.value`.

## Decision

Per-decorated-method **routing slot** (the TDD's chosen approach):

1. **Slot** — `registerDecoratedMethodSlots` (before any body/call emission)
   declares a module global `@<Class>_<m>__decslot` per supported decorated
   method and records it in `e.decoratedMethodSlots[class][method]`.
2. **Method-box adapter** — `emitMethodBoxAdapter` generates a tag-12 record
   wrapping the static method: unbox `this` and each argument, call
   `@<Impl>_<m>`, box the result. Rejects a signature it can't marshal
   (array/nullable/rest parameters, an unboxable return) as a clean error.
3. **Apply** (from `emitClassDecoratorApplications`, at the class's source
   position): default the slot to the boxed original; build a descriptor
   dynamic object `{ value, writable:true, enumerable:false, configurable:true }`
   bound to a synthetic local; run each decorator bottom-up with
   `(target, key, descriptor)`; adopt a returned dynamic object as the new
   descriptor at runtime (a statically void/scalar return can't be a
   descriptor, so it's ignored); finally store the effective `descriptor.value`
   into the slot.
4. **Route** — `emitClassCall`, when `!forceDirect` and the method has a slot,
   calls `emitDecoratedMethodCall`: load the slot's callable and invoke it
   through the tag-12 ABI with the receiver and boxed arguments, coercing the
   boxed result to the method's declared return type. `super.method()`
   (`forceDirect`) deliberately bypasses the slot — it targets the parent
   implementation directly.

Only plain instance methods on non-generic classes are routed; accessor,
static, and generator method decorators, and method decorators on generic
classes, are a clean rejection (`emitClassDecl`).

## Implementation notes

- `resolver/rename.go`: method-level decorator expressions
  (`m.Decorators`) are now name-rewritten in `rewriteClassDecl`, like the
  field/parameter/class decorators Stage 1 added.
- The slot is keyed by the method's *implementor* class at the call site, so an
  inherited decorated method routes correctly.
- Return-value threading uses the return's static type: a dynamic/`any` return
  is adopted at runtime only when it is actually a dynamic object (tag 10).

## Side effects discovered

- A replacement method written with typed operations on its parameters
  (`descriptor.value = function (n: number) { return n * 2 }`) hits the
  pre-existing "operator on any/unknown" limitation — a function expression in a
  dynamic position gets `any`-typed parameters under `strict`. A non-capturing
  replacement with an untyped/const body works. Same-family as the factory-call
  and captured-closure limitations disclosed in Stage 1; tracked under
  TDD-00161.

## Verification

- `tests/decorators_test.go`: observe-only method decorator (calls unchanged),
  replacement via `descriptor.value`, replacement via a returned descriptor,
  bottom-up multi-decorator order, accessor/static rejections. Property and
  parameter decorators (Stage 1) unchanged.
- `examples/decorators/method_decorators.ts` compiles and runs (observe +
  replacement + composition).
- `go vet`, full `make test-par`, class/inheritance/dyn/reflect/generic suites,
  node oracle, `make status-check`/`reference-check` pass. Mac (Apple Silicon).
