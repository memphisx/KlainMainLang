# ADR-00123: EventSource Stage 1 — SSE record parsing and `onmessage`

- **Relations**: Implements [TDD-00038](../tdd/TDD-00038.md), Extends [ADR-00122](ADR-00122.md)
- **Date**: 2026-08-07

## Context

[ADR-00122](ADR-00122.md) shipped EventSource's Stage 0 (connection plumbing: `readyState`/`close()`/event-loop keep-alive), explicitly with no way to actually receive any SSE data. This ADR implements Stage 1: real SSE record parsing (`data`/`event`/`id`/`retry` fields, comment lines, multi-line `data:` concatenation) and `onmessage` dispatch for unnamed (default type `"message"`) records, per [TDD-00038](../tdd/TDD-00038.md)'s own staging.

## Investigation

Before writing any new parsing primitives, searched for existing string-processing helpers this compiler already has for exactly this shape of problem — confirmed two direct, reusable precedents rather than needing to hand-roll character-by-character scanning:

- `__kml_split(ptr s, ptr sep) -> {ptr, i64}` (`runtime_strings.go`) splits a string on every occurrence of a separator into a fresh array of malloc'd, null-terminated copies — exactly what's needed to split one SSE record into lines.
- `__kml_split_first(ptr s, ptr sep) -> {ptr, ptr}` (`runtime_http.go`) splits on only the *first* occurrence, aliasing the "after" half into the original string rather than copying — built for parsing one `"Key: Value"` HTTP header line, and structurally identical to what an SSE `"field: value"` line needs. `ensureHTTPParseHeaders`'s own doc comment describes almost exactly the algorithm this ADR needed (split into lines, split each line on the first separator, trim, dispatch by field name) — read in full before designing, to reuse the pattern rather than reinvent it.

Confirmed directly that assigning an untyped arrow function into a declared function-typed slot did **not** already thread the slot's declared parameter types into the arrow function's own unannotated parameters — a real, pre-existing, EventSource-unrelated gap, confirmed via a plain repro (`let cb: (b: Box) => void = (b) => { console.log(b.value) }`) before touching anything EventSource-specific. Essential to fix first: `onmessage`'s payload parameter (`ev: MessageEvent`) would otherwise default to `TypeI64` (ADR-00042's existing unannotated-parameter behavior), making `ev.data` a compile error.

## Decision

**No new Go-level codegen for `onmessage` itself.** `onmessage` is declared as a plain `FuncType`-typed field on `EventSourceType()` — assignment (`es.onmessage = (ev) => ...`) already goes through the fully generic object-field-assignment path (`emit_exprs_assign.go`), the same one every other object field uses. The only real gap was the missing hint-threading described below; once fixed, `onmessage` needed zero EventSource-specific assignment code.

**Fix the general hint-threading gap** (`emit_objects.go`'s `emitExprWithObjectHint`): an `*ast.ArrowFunction` expression against an `IsFunc` hint now calls `emitArrowFunctionWithHints(af, hint.FuncParams)`, the same "propagate the known expected shape into the literal" principle [TDD-00007](../tdd/TDD-00007.md)/[TDD-00028](../tdd/TDD-00028.md) already established for object/array literals — arrow functions were simply the one other literal-like expression kind that could carry an unannotated parameter needing outside context, and hadn't been covered yet. Also fixed the same gap one level up: `emitVarDecl`'s scalar-init path (`emit_exprs_vardecl.go`) called plain `e.emitExpr(v.Init)` instead of the hint-aware helper at all, so even with the first fix in place, `let cb: (b: Box) => void = (b) => ...` still wouldn't have worked without this second change.

**SSE parsing lives entirely in new C-runtime IR** (`runtime_eventsource.go`), not Go-level codegen — it runs from the event loop's own per-iteration scan, with no KML-source call site to hang Go codegen off of. Three new functions: `__kml_es_concat` (a standalone two-string concat, since the record parser's `data:`-line accumulation runs from hand-written IR where `emitStringConcat`'s own `e.emitInstr`/`freshReg`-based approach isn't callable), `__kml_eventsource_process_available` (the per-entry record-boundary loop — searches the unconsumed tail for the next literal `"\n\n"` via `strstr`, dispatches each complete record found, advances `consumedOffset` past it, replacing Stage 0's placeholder "just discard everything" logic), and `__kml_eventsource_dispatch_record` (parses one record's lines via `__kml_split`/`__kml_split_first`, accumulates `data:` lines with the real spec's own append-value-then-LF-then-strip-one-trailing-LF algorithm, tracks `event:`/`id:`, and calls `onmessage` — but only when the resolved type is exactly `"message"`).

**A record whose type resolves to anything other than `"message"` is silently withheld, not misdelivered.** This is Stage 1's actual scope boundary, not an incidental gap: `event: greeting` has nowhere to go until Stage 2's `addEventListener` exists. Caught by reasoning through the design *before* writing tests (the first draft called `onmessage` unconditionally, regardless of resolved type) and fixed with one additional `strcmp` check gating the whole dispatch/callback path — verified directly afterward against a real named-event record to confirm it's actually withheld, not just theoretically.

**`retry:` is recognized but discarded.** Parsing it (rather than letting it fall through to "unknown field") matters so a `retry:` line inside a record doesn't get misclassified — but nothing consumes the value until Stage 3's (not-yet-designed) auto-reconnect exists to need it.

**`id:` persistence lives on the KML object itself** (`EventSourceLastEventIdField`, a new hidden field, index 1 — right after the existing hidden handle field), not on the runtime's own transfer-tracking entry struct — keeping all EventSource-observable state (`url`, `readyState`, `onmessage`, and now this) in one place, with the entry struct staying minimal (transfer bookkeeping only). A record with no `id:` field reads the previous value already stored there rather than resetting it, matching the real spec's own persistence-across-records behavior.

**CRLF-terminated streams (`"\r\n\r\n"`) are a known, deliberate Stage 1 gap, not silently broken.** Searching for a literal `"\n\n"` never matches a `"\r\n\r\n"` sequence (no two adjacent LF bytes) — a server using CRLF line endings would simply never have any record detected as complete. Every server this compiler's own tests/examples talk to emits bare-LF records (confirmed by writing the fixture servers that way deliberately), so this hasn't blocked anything real yet, but it's a documented limitation, not an untested one.

## Implementation notes

- **New/changed types** (`types.go`): `EventSourceType()` gained two fields — `EventSourceLastEventIdField` (hidden, index 1) and `onmessage` (visible, `FuncType([MessageEventType()], TypeVoid)`, index 4). `VisibleFields()`'s `IsEventSource` branch now skips the first *two* hidden fields (was one, Stage 0). New `MessageEventType()` — a fixed, concrete `{data, type, lastEventId}` struct with no generic type parameter at all, simpler than `EventEmitter<T>` in exactly the one respect the TDD's Design section called out (the payload shape never varies by user code).
- **Field-order churn**: every raw-IR `getelementptr` in `runtime_eventsource.go` that reaches into the KML object (both from Stage 0's `doopen`/`transferended` readyState writes and this stage's new `dispatch_record`) had to move from the Stage-0 3-field struct literal (`{ ptr, ptr, i64 }`, `readyState` at index 2) to the new 5-field one (`{ ptr, ptr, ptr, i64, ptr }`, `readyState` now at index 3, `lastEventId` at 1, `onmessage` at 4) — a mechanical but easy-to-miss migration, caught by grepping for every existing GEP against the object's struct shape before writing new ones, not discovered via a failed build (Go itself can't catch a wrong hardcoded index inside a string literal).
- **`emitNewEventSourceExpression`** (`emit_eventsource.go`) now explicitly initializes both new fields at construction (`lastEventId = ""`, `onmessage = null`) — malloc doesn't zero memory, so skipping this would have left `onmessage` reads/dispatch-time null-checks operating on uninitialized garbage instead of a real null pointer.
- **Closure-call ABI reused, not reinvented**: `__kml_eventsource_dispatch_record`'s indirect call to a registered `onmessage` closure (`call void (ptr, ptr) %fpVal(ptr %epVal, ptr %mev)`) follows `emitClosureCallByPtr`'s (`emit_func.go`) exact existing header-unpacking convention (`{funcPtr, envPtr}`, env first) — no new calling convention invented.
- **`fmt.Sprintf` argument-index verbs (`%[1]s` etc.), not positional `%s`**, for the two new multi-substitution IR templates — a long hand-written IR string with several distinct interned-string constants (some reused more than once, e.g. the `"\n"` separator used for both line-splitting and `data:`-line joining) is real error-prone territory for plain positional `%s` ordering; explicit indices made every substitution site self-documenting and let the same constant be referenced twice without duplicating it in the argument list.

## Side effects discovered

**The arrow-function/`FuncType`-hint gap** (see Decision) is the one real, non-EventSource-specific bug found and fixed as part of this work — confirmed via a standalone repro unrelated to EventSource before concluding it was general rather than something specific to how `onmessage`'s field was declared. Two regression tests added directly for it (`TestE2EUnannotatedArrowParamHintedFromVarDeclFuncType`, `TestE2EUnannotatedArrowParamHintedFromFieldAssignFuncType`, `tests/func_test.go`), independent of the EventSource-specific test suite.

**The onmessage-fires-for-any-type bug** (see Decision) was caught during design/implementation, before it ever reached a committed test — not a shipped regression, but worth recording here since it's exactly the kind of scope-boundary mistake worth being explicit about for whoever picks up Stage 2 next (the fix is a real, load-bearing `strcmp` check, not incidental).

No other bugs found. The CRLF gap and `retry:`-discarded behavior are deliberate Stage 1 scope cuts (see Decision), not discovered-but-unfixed problems.

## Verification

- `go build -o klainmain .` and `go vet ./...` clean.
- Manually compiled and ran (bypassing `go test`) against a real, hand-written local Go SSE server exercising comment lines, a named event, a multi-line `data:` record with `id:`, and a trailing id-less record — confirmed, in one pass: the comment produced no dispatch, the named event was correctly withheld from `onmessage` (this is what caught the type-filter bug above — the very first manual run over-delivered it before the fix), multi-line data joined with exactly one embedded `\n` and no trailing one, and `lastEventId` correctly persisted onto the id-less trailing record.
- `go test ./...` passes in full, including 4 new Stage 1 tests in `tests/eventsource_test.go` (`onmessage` receives `data`/`type`, multi-line concatenation, `id:` persistence, named-event withholding — the last of these directly encoding the bug found above as a permanent regression test) plus the 2 new general-purpose hint-threading regression tests in `tests/func_test.go`.
- Ran the full pre-existing suite to confirm the `emitExprWithObjectHint`/`emitVarDecl` changes — both general, widely-reached code paths — introduced no regression anywhere else: all pass.
- `examples/eventsource/eventsource.ts` extended with an `onmessage` demonstration; compiled and ran directly against the `tools/httpbin-lite` fixture, output matched every inline expected-output comment.
- Verified only on the x86-64 Linux development box (see `CLAUDE.md`'s platform-flagging rule) — pure LLVM-IR-text/Go compiler logic plus already-platform-neutral libcurl/string-runtime reuse, not expected to be platform-sensitive, but not directly confirmed on the Apple Silicon Mac.
