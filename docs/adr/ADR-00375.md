# ADR-00375: Static field initializers (`static x = expr`)

- **Relations**: Extends [ADR-00374](ADR-00374.md); Implements [TDD-00063](../tdd/TDD-00063.md), [TDD-00121](../tdd/TDD-00121.md)
- **Date**: 2026-08-26

## Context

The TypeScript accept/reject conformance oracle's false-reject reason histogram
ranked `static field initializer on '%s' is not yet supported` at 41 cases —
the most common class-related rejection after the bare-field one (ADR-00374).
`class C { static count = 5 }` is everyday TypeScript; this compiler rejected it
and told the author to use a `static { … }` block instead.

## Investigation

The pieces were already in place:

- Static field storage is a per-field LLVM global,
  `@ClassName_static_<name>` (`emitClassStaticFieldGlobals`,
  `emit_classes.go`).
- `static { … }` blocks already run once at program start in a synthesized
  `@ClassName_staticinit()` function (`emitClassStaticInit`), called from
  `EmitProgram` Pass 3 before any top-level statement.
- A member-assignment to a static field (`ClassName.x = v`) already codegens —
  it is exactly what a `static {}` block writes.

So the initializer only needed lowering to that existing assignment form and
sequencing into the staticinit. The registration path
(`registerClasses`) previously hard-rejected a static field with an initializer,
and also assumed an explicit type annotation (`resolveType(f.Type)`), which a
bare `static x = 5` lacks.

## Decision

- In `registerClasses`, stop rejecting a static field initializer. Infer the
  field's type from the initializer when it carries no annotation, the same
  compile-time inference an instance `x = expr` field and a `let x = expr` use
  (`inferExprType`).
- Lower each `static x = expr` to a `ClassName.x = expr` assignment
  (`classStaticFieldInitStmts`) and run those statements at the top of
  `emitClassStaticInit`, in field-declaration order, ahead of any `static {}`
  block.
- Emit a staticinit function for a class that has static field initializers even
  when it declares no `static {}` block
  (`len(cd.StaticBlocks) > 0 || classHasStaticFieldInit(cd)`).

Ordering: static field initializers run in declaration order, then the `static
{}` block(s). A class that mixes both runs all field initializers ahead of any
block rather than interleaving by exact source position — an `AnnotField`
carries no position, and the mixed case is rare. Real TS interleaves the two by
source order.

## Implementation notes

- `codegen/llvm/emit_classes.go`: removed the rejection and added
  initializer-based type inference in `registerClasses`; new helpers
  `classStaticFieldInitStmts` and `classHasStaticFieldInit`; `emitClassStaticInit`
  runs the field initializers before the blocks.
- `codegen/llvm/emitter.go`: staticinit emission/call gated on static field
  initializers too, not only `static {}` blocks.

## Side effects discovered

`++`/`--` on **any** member expression is unsupported — `C.count++`, `this.x++`,
and `obj.x++` all fail with `update expression requires an identifier`, a
pre-existing limitation independent of this change (compound assignment `C.count
+= 1` works). It is a general member-increment gap, not static-field-specific,
and is left for a separate change. The examples/tests here use `+= 1`.

The pre-existing ADR-00157 null-reference sharp edge is likewise unchanged: a
bare `static name: string` with no initializer reads as a null pointer.
