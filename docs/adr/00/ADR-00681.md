# ADR-00681: object-array `sort(comparator)` was a silent no-op

- **Date**: 2026-09-03

## Context

`objArr.sort((a, b) => a.k - b.k)` left the array unchanged — a silent-wrong
result (found in the faithfulness audit). Numeric-array comparator sort worked.

## Investigation

`emitQsortCall` (`emit_arrays_sort.go`) routes a custom comparator by element
type: `Float`→f64 trampoline, string→str, everything else→**i64** trampoline.
An object/class element (IR `ptr`, not Float/string) fell into the i64 case.
The i64 trampoline (`runtime_collections.go`) reads the comparator's result as
`i64` and `trunc`s to `i32` — but an object comparator (`a.k - b.k`, number
arithmetic) returns a **`double`**. Truncating a double's bit pattern (e.g.
`-1.0` = `0xBFF0…`) to i32 yields `0`, so qsort saw every pair as equal and
never reordered. The f64/str trampolines already read a `double` result.

## Decision

Add `ensureSortTrampolineObj` — identical to the string trampoline (load each
element as `ptr`, call a `double (ptr,ptr,ptr)` comparator, reduce to
-1/0/+1) — and route `elemTy.IsObject || elemTy.IsClass` custom-comparator
sorts to it. The i64 trampoline stays for genuine integer-element arrays (whose
`(a,b)=>a-b` comparator does return i64).

## Verification

Mac. `[{k:3},{k:1},{k:2}].sort((x,y)=>x.k-y.k)` now yields `1,2,3` (was
unchanged). E2E test `TestE2EArraySortObjectComparator`; full array/sort
regression green. Default (no-comparator) object sort is unchanged and out of
scope here.
