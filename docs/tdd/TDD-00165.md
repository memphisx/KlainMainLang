# TDD-00165: Importable module specifiers for the Web-global-backed Node modules (`url`, `timers`, `perf_hooks`, `buffer`, `events`)

- **Status**: Partially Implemented
- **Date**: 2026-09-03

Stages 1–3 shipped — the import wiring is complete; every primary export of all five modules is now importable in every common form (same-name, `node:`, and aliased):
- Stage 1 ([ADR-00666](../adr/ADR-00666.md)): same-name named imports (and the `events` default) validate and erase to the ambient global.
- Stage 2 ([ADR-00667](../adr/ADR-00667.md)): aliased imports of the codegen-recognized reexports (`setTimeout` family / `performance` / `atob` / `btoa` — and `Buffer`, reclassified from parse-time to a `Buffer.from` member call) rename the alias to the canonical global.
- Stage 3 ([ADR-00668](../adr/ADR-00668.md)): aliased imports of the genuine parse-time constructors (`URL`/`URLSearchParams`/`Blob`/`EventEmitter`) are rebuilt into their specialized built-in node under the canonical name during the rename pass, with arity validation preserved.

**Stage 4** (the module-only *extras*) is in progress: the **legacy `url`-module function surface is complete** — `parse`/`format`/`fileURLToPath`/`pathToFileURL`/`resolve`/`urlToHttpOptions`/`domainToASCII`/`domainToUnicode` all shipped ([ADR-00669](../adr/ADR-00669.md)–[ADR-00672](../adr/ADR-00672.md)); the `url` module is hybrid (reexport primaries + marker-dispatched functions). Remaining Stage 4 surface across the *other* modules: `perf_hooks.PerformanceObserver`, `timers/promises`, `events.once`/`on` — each a new feature ranked by leverage.

## Context

The [Node built-in modules index](../status/NODE-MODULES.md) (ADR-00664) named a
specific gap: several modules' functionality works through an ambient **global**,
but their `import … from '<name>'` (and `node:<name>`) specifier is rejected by
the resolver allowlist. The affected set: `url`, `timers`, `perf_hooks`,
`buffer`, `events`. A program written the canonical Node way —
`import { setTimeout } from 'node:timers'`, `import { URL } from 'url'` — fails
to compile even though the functionality is fully present.

The decision to take here (per the request that framed it): examine the
**official-spec** differences between the JavaScript/Web global and the Node
module for each same-named export. Where the spec defines them identically, the
import should just work (bind to the existing global). Where they differ, the
imported form needs its own implementation and must shadow the global when
imported.

## Design

### Spec-difference analysis (the load-bearing finding)

For every module in scope, the **primary same-named export is a spec-identical
re-export of the global** — Node's own docs define these module exports as *the
same object* as the global. There is no behavioral divergence to reconcile:

| Module | Primary export(s) | Spec relationship to the global | Module-only extras (no global to conflict with) |
|---|---|---|---|
| `url` | `URL`, `URLSearchParams` | The **same WHATWG classes** as the globals (`globalThis.URL === require('url').URL` in Node) — identical | Legacy `url.parse`/`format`/`resolve`/`Url`, `fileURLToPath`/`pathToFileURL`, `domainToASCII`/`Unicode`, `urlToHttpOptions` |
| `timers` | `setTimeout`/`setInterval`/`setImmediate`/`clear*` | Node's global and `timers` export are the **same functions** — identical | `timers/promises` (separate subpath), `Timeout`/`Immediate` classes |
| `perf_hooks` | `performance` | The **same `Performance` object** as the global — identical | `PerformanceObserver`, `monitorEventLoopDelay`, `createHistogram`, `constants` |
| `buffer` | `Buffer` | The **same Node global** `Buffer` (Node-specific, not a Web API) — identical | `Blob`/`File`/`atob`/`btoa` (also globals), `constants`, `transcode`, `isUtf8`/`isAscii`, `SlowBuffer` |
| `events` | `EventEmitter` (default + named) | The **same `EventEmitter`** as the global — identical | `once`, `on`, `getEventListeners`, `setMaxListeners`, `EventEmitterAsyncResource` |

So the request's decision tree resolves cleanly to its first branch for every
primary export: **no spec difference → make it work with or without the import.**
The "different implementation when imported, import shadows the global" branch is
*not exercised* by any primary export here, because per spec the module export
**is** the global. The module-only extras are a separate matter — they have no
same-named global to override, so they are simply additional surface, most of it
not yet built (legacy `url.parse`, `PerformanceObserver`, `timers/promises`,
`events.once`).

One latent, *global-level* spec divergence worth recording but out of scope
here: the Web `setTimeout` returns a numeric id, while Node's returns a `Timeout`
object. This compiler's global follows the Web shape (numeric id). That gap
affects the global and any import **equally** (Node's own global is the
Node-shaped one), so it is not an import-vs-global difference — it is a separate
global-fidelity follow-up, not created or closed by this work.

### The mechanism: "global re-export" module specifiers

Because the primary exports are recognized by their **unshadowed identifier
name** — `URL`/`URLSearchParams`/`Buffer` at parse time
(`parser/parser_literals.go`), `setTimeout`/`performance`/`EventEmitter` in
codegen by name (`emit_call.go`) — the cleanest binding for a **same-name**
import is a **validated no-op that leaves the global in place**:

`import { URL } from 'url'` → the resolver confirms `url` exports `URL`, confirms
the local name equals the global name, and binds nothing new — the global `URL`
keeps working exactly as today. This is spec-correct (the module export *is* the
global) and needs no codegen change at all.

A **namespace** import (`import * as timers from 'timers'; timers.setTimeout(…)`)
routes member access on the marker to the same global implementation — the
existing marker-dispatch path (as `querystring.parse` already uses).

### Staging

- **Stage 1 (this stage) — same-name named imports + namespace imports.** Add
  the five specifiers (and their `node:` aliases) as a new "global re-export"
  category. A named import whose local name equals the canonical global name is
  validated and erased. A namespace import binds the marker and routes
  `<ns>.<primaryExport>` to the global. Everything a real program overwhelmingly
  writes (`import { URL } from 'node:url'`, `import { setTimeout } from 'timers'`)
  compiles. Module-only extras (`url.parse`, `PerformanceObserver`, …) reject
  with the existing "built-in module '<m>' has no exported member '<x>'" error
  until built.
- **Stage 2 — aliased imports of the non-parse-time exports.** `import { setTimeout as later } from 'timers'` / `{ performance as perf }` — bind the alias
  through the scope-aware rename pass to the canonical name (feasible because
  these are resolved in codegen by name, not at parse time).
- **Stage 3 — aliased imports of the parse-time constructors.** `import { URL as U } from 'url'` cannot work by post-parse rename (the parser recognizes
  `new URL(...)` by the literal identifier at parse time, before imports are
  resolved). Options: teach the parser's `new` path to consult a resolved alias
  table (larger), or keep it a clean, explicit rejection. Deferred with a clear
  message, not silently broken.
- **Stage 4 (separate, by leverage) — the module-only extras** as their own
  features: `url.parse`/`fileURLToPath`, `PerformanceObserver`, `timers/promises`,
  `events.once`/`on`. Each is a normal new-surface task, ranked by value, not part
  of the import-wiring here.

## Open questions

- **Erase vs. shadow for a same-name import.** Stage 1 erases the import and
  leaves the global — correct only because the export *is* the global. If a
  future module in this category ever had a spec divergence, that module would
  need the shadow-the-global path instead; the category should carry a per-module
  "identical / divergent" flag so a divergent member can't be silently erased.
- **`buffer`/`node:buffer` extras that are also globals** (`Blob`, `atob`/`btoa`):
  importing them is the same erase-to-global case as the primary export — fold
  them into Stage 1's same-name set, or hold for Stage 4? (Leaning: include, since
  they are spec-identical globals too.)
- **Namespace member coverage.** For `import * as t from 'timers'`, which members
  must the marker route — only the primary functions, or also the not-yet-built
  extras (which should still reject)? Route the primary set; unknown members keep
  the standard rejection.
