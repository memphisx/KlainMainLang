# ADR-00225: Intersection types (`A & B`) via field-merge into one struct

- **Relations**: `Implements TDD-00078`
- **Date**: 2026-08-19

## Context

Intersection types (`A & B & ...`) were one of the two remaining `❌` rows in the
Type System status page (with mapped/conditional types). They are common in
idiomatic TS — composing object shapes, mixin-style assembly, extending a config
object — and they map unusually cleanly onto this compiler's object model, which
already represents object types as fixed-shape structs. [TDD-00078](../tdd/TDD-00078.md)
scoped the work; this ADR records what shipped.

## Investigation

- Object types are `ObjectType(fields)` → `Field{Name, Ty}` → `StructIR`/
  `FieldIndex` (`codegen/llvm/types.go`). TypeScript's `A & B` on object types is
  "a type carrying the members of both," i.e. a struct with the union of all
  fields — so an object intersection needs **no new runtime representation**, only
  a compile-time field merge. This is the opposite of a union ([TDD-00043](../tdd/TDD-00043.md)),
  whose value is *one of* its members and so needed a runtime-tagged box; an
  intersection value satisfies *all* members at once, one fully-static struct.
- `&` lexes to `lexer.BITAND` and was only ever consumed as a binary expression
  operator (`parseBitwiseAnd`); `parseTypeAnnotation` only looped on `BITOR`, so
  `&` in a type position was unparsed (`parser/parser_types.go`).
- `resolveType` (`emitter.go`) is infallible (no error return); unions report
  out-of-scope members via use-site validators (`validateUnionMembers`, called at
  ~8 var-decl/param/return checkpoints). Intersection follows the same pattern.
- The resolver's `rewriteType` (`resolver/rename.go`) descended into
  `Fields`/`ElemType`/`KeyType`/`TypeArgs`/`FuncParams`/`FuncRetType` but **not**
  `UnionMembers`, `TupleElems`, or (the new) `IntersectionMembers`. Since even a
  single-file program mangles interface names, a named member of any of these
  composites stayed unmangled while its interface registered under the mangled
  key — resolving to the unknown-name default. This was a latent bug for tuples
  with named elements, surfaced immediately by intersection's named members.

Rejected alternative (per TDD-00078): parse-time flattening of members into one
synthesized object annotation. The parser has no interface registry, so it could
never merge *named* interface members — only inline `{...}`. A distinct lazy
`IsIntersection` type kept through codegen was also rejected as overkill, since
nothing downstream benefits from an un-merged form.

## Decision

An object-type intersection collapses at type resolution into a single merged
`ObjectType`. Concretely:

- **AST**: new `TypeAnnotation.IntersectionMembers []*TypeAnnotation`, mirroring
  `UnionMembers` and following the same head-copy convention (the node copies its
  first member's fields; every list entry, including the first, keeps its own
  `IntersectionMembers` nil).
- **Parser**: a new precedence level `parseTypeAnnotationIntersection` between the
  union loop (`|`, looser) and the atom parser (`&`, tighter), so `A & B | C`
  parses as `(A & B) | C`. A single atom with no trailing `&` returns unchanged.
- **Codegen** (`emit_intersection.go` + one `resolveType` branch): resolve each
  member, then `mergeIntersectionFields` concatenates fields in member order,
  deduplicating a same-named field when both declarations resolve to the same
  type (bounded structural `typeMergeKey`) and erroring on a type conflict. Every
  member must be an object type. The result is a plain `ObjectType`, so all
  existing object machinery (`FieldIndex`, `StructIR`, object-literal coercion,
  array/nullable positions) applies unchanged; the resolved type retains
  `IntersectionMembers` only so the validator can re-check it.
- **Validation**: `validateIntersectionMembers` re-runs the merge to surface a
  non-object member or a field conflict at a use site with a real source
  position. Folded with `validateUnionMembers` into one `validateCompositeType`
  that replaced all 8 union checkpoints, so a new checkpoint (or composite kind)
  can't validate one but not the other. It **recurses** into object fields and
  array elements (depth-bounded against a cyclic Type), because an intersection
  can be nested where the checkpoints don't reach directly — see Side effects.
- **Resolver**: `rewriteType` now descends into `IntersectionMembers` — and, fixed
  in the same pass, the previously-skipped `UnionMembers` and `TupleElems`.
  `rewriteTypeName` is idempotent (a mangled name is never itself a lookup key),
  so the head-copy sharing members[0] with the node is harmless.

Field-conflict handling is `-compat`-governed by design (TDD-00078): `strict`
errors, `js` keeps a TS-faithful `never` field. Only the `strict` behavior ships
here — a conflict is rejected in both modes for now; the `js` `never`-field is a
deferred second stage (a `never` struct *member* is new representation territory).

## Implementation notes

- The `resolveType` intersection branch is checked right after the union branch,
  before the `Fields`/`Name` branches, because the head-copy still carries the
  first member's `Name` and possibly `Fields`.
- On a merge error `resolveType` (which can't return one) yields the fields the
  merge produced (nil on error) → a well-formed empty `ObjectType`, never a
  codegen crash; the use-site validator reports the real error. This is the same
  "safe but unchecked without a validator" property unions already have.
- `typeMergeKey` is depth-capped (8) so a self-referential interface can't spin;
  at the cap it degrades to the bare IR string, which is conservative.

## Side effects discovered

- **Invalid IR for a bad intersection in a nested position** (found running the
  Test262 corpus, which showed a jump in clang-invalid-IR failures once `&`-in-
  annotation inputs began parsing through to codegen). A non-object member is a
  clean error at the 8 use-site checkpoints, but an intersection nested in an
  object field (`interface W { p: A & number }`) or an array element (`(A & B)[]`)
  bypassed them: it resolved to a malformed merged struct and emitted a
  `store ptr 5`-style type mismatch clang rejected. Fixed by making
  `validateIntersectionMembers` recurse into fields/elements (above); a valid
  nested intersection field still merges normally, and a recursive interface
  doesn't loop the (depth-bounded) walk. Regression-tested.
- **Latent `rewriteType` bug fixed in passing**: a named interface used only
  inside a tuple (`[User, number]`) or a union resolved to the unknown-name
  default before this change, because the rename pass never descended into
  `TupleElems`/`UnionMembers`. Now covered by a new tuple regression test.
- **Missing-field leniency is pre-existing, not intersection's**: the
  object-literal builder already accepts a partial literal for a plain
  `interface` (an omitted declared field compiles), so an intersection inherits
  that rather than being made stricter than the object types it merges.
  Tightening it is a separate cross-cutting object-type decision — recorded as a
  shared caveat on the Type System page.
