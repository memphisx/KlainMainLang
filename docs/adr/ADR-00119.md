# ADR-00119: RegExp Stage 5 — str.split() and str.search()

- **Relations**: Implements [TDD-00035](../tdd/TDD-00035.md). Extends [ADR-00114](ADR-00114.md), [ADR-00115](ADR-00115.md), [ADR-00116](ADR-00116.md), [ADR-00117](ADR-00117.md), [ADR-00118](ADR-00118.md)
- **Date**: 2026-08-07

## Context

[TDD-00035](../tdd/TDD-00035.md)'s Stage 5 is `str.split(regexp)`/`str.search(regexp)` — the last method-adding stage (Stage 6 is `--static` linking verification, not new language surface), framed in the TDD as "the smallest remaining surface, reuses Stage 1-2 primitives." Picked up directly following Stage 4, per the user's "continue with Stage 5."

## Investigation

**Found that Stage 5 does *not* actually reuse Stage 1-2's primitives the way the TDD assumed.** Every prior method (`.test`/`.exec`/`str.match`/`str.matchAll`/`str.replace`/`str.replaceAll`) reads and writes the RegExp instance's `lastIndex` property, because real JS threads all of them through the same `RegExpExec`/`lastIndex` machinery. Checked the actual ECMA-262 algorithms for `@@split` and `@@search` directly rather than assuming this pattern continued, and found both are deliberate exceptions: `@@split` tracks its own local search position, completely independent of the regex's `global` flag or `lastIndex` (a *non-global* regex still finds every match when used with `.split()` — confirmed this is real, intended spec behavior, not an oversight); `@@search` always searches from offset 0 and explicitly *restores* whatever `lastIndex` held before the call once it's done, making a `.search()` call invisible to any later `.exec()`/`.test()` iteration on the same instance. This meant `emitRegexSingleMatchCore` (Stage 2's `lastIndex`-driven primitive, reused as-is by every stage since) was the *wrong* tool for `.split()` specifically — looping calls to it against a non-global regex would just return the same first match forever, since it only auto-advances when `global` is true.

**Built a new, genuinely stateless match primitive, `emitRegexMatchAt`, instead of forcing `.split()` through the existing one.** Runs a single PCRE2 match at an explicit caller-supplied start offset, touching no RegExp-instance fields at all — no handle-holder object even needs to be passed beyond the compiled-pattern handle itself. `.search()` still uses `emitRegexSingleMatchCore` (its offset-0-forced, restore-`lastIndex`-after behavior is a thin wrapper around the existing primitive, not a reason to avoid it), but `.split()`'s own internal loop is built entirely on `emitRegexMatchAt`.

**Confirmed `.search()`'s "no match" sentinel already lines up with real JS's return value with zero extra work.** `emitRegexSingleMatchCore`'s `matchStart` return is already `-1` on a failed match (the sentinel introduced for [ADR-00118](ADR-00118.md)'s replace splicing) — exactly what `String.prototype.search` returns for no match — so `emitRegexSearch` needed no branch/`select` at all, just forcing the start offset to `0`, reading `lastIndex` before, and restoring it after.

**Decided against replicating real JS's full zero-length-match handling for `@@split`.** The real spec's algorithm is genuinely intricate here (a zero-length match at certain positions produces a split, at others it's skipped, with several interacting special cases around the end of the string). Given this stage's own "smallest remaining surface" framing, scoped `.split()` down to a clear, simple rule instead: only a non-zero-length match ever produces a split; a zero-length match is always skipped (the search position advances by one byte and continues). This is a real, deliberate divergence from full JS parity — documented rather than silently accepted as "close enough."

**Confirmed the same two-pass (count, then build) convention every other multi-match stage already established remains safe here.** `emitRegexMatchAt` (like `emitRegexSingleMatchCore`) has no observable side effects when called by `.split()`'s loop specifically (no `lastIndex` mutation, no user code invoked) — factored the shared loop shape into `emitRegexSplitScan`, called once with a counting callback and once with a build callback, mirroring `emitRegexCollectGlobalMatches`'s/`emitRegexReplaceAllMatches`'s established shape from the two prior stages.

## Decision

- New file `codegen/llvm/emit_regexp_split.go` (Stage 5's own complexity — a genuinely different match primitive, plus two more real algorithms — again justified a new file over continuing to grow `emit_regexp.go`, per this project's established file-splitting convention):
  - `emitRegexMatchAt(handleReg string, strVal Value, startOffsetReg string) (matchedReg, startReg, endReg string)`: the new stateless single-match primitive described above.
  - `emitRegexSearch(strVal, regexVal Value) Value`: saves `lastIndex`, forces it to `0`, calls `emitRegexSingleMatchCore` (reusing Stage 2's primitive directly — no reason to duplicate its logic here), restores `lastIndex`, and returns the match start (already `-1` on no match).
  - `emitRegexSplitScan(handleReg string, strVal Value, subjectLenReg string, onSegment func(gapStartReg, gapEndReg string)) (finalLastSplitReg string)`: the shared local-search loop, skipping zero-length matches per the scoping decision above, invoking `onSegment` with each real split point's text boundaries (the gap *before* the match, not the match itself).
  - `emitRegexSplit(strVal, regexVal Value) Value`: the two-pass (count via `emitRegexSplitScan`, then build a `string[]`) implementation, appending the final trailing segment (from the last split point to the end of the subject) after the scan completes, exactly mirroring how every earlier multi-match stage's own trailing-segment handling works.
- Dispatch: `emitStringSearch`/`emitStringSplit` (`emit_strings.go`) each gained an `IsRegExp` check on their pattern argument, ahead of their pre-existing plain-string bodies (`.indexOf()`-delegation for search, `__kml_split` for split) — both pre-existing bodies are completely untouched, so a non-`RegExp` argument's behavior is unchanged.
- No `inferExprType`/`emit_exprs_vardecl.go` changes were needed — like Stage 4, both methods already existed with fixed return types (`number` for `search`, `string[]` for `split`) regardless of pattern kind, so the existing unconditional inference cases already cover the RegExp-backed path.

## Implementation notes

Files touched: new `codegen/llvm/emit_regexp_split.go`, `codegen/llvm/emit_strings.go` (two `IsRegExp` guard insertions, plus `emitStringSearch`'s doc comment rewritten to reflect the new real-RegExp-aware behavior instead of the old "this is the entire reachable surface" framing that predated `RegExp` existing at all).

Found and fixed one small pre-existing naming collision while writing `examples/regexp/regexp.ts`'s Stage 5 section: this compiler's whole-program, single-`main()` model means every top-level `const` name must be unique across the entire file (`resolver` package docs) — the new `.search()` example reused `g` as a variable name, already bound by Stage 2's `lastIndex` example earlier in the same file, a hard compile error caught immediately by `make examples`, not a runtime bug. Renamed to `searchRe`; not a compiler bug, just an example-authoring mistake.
