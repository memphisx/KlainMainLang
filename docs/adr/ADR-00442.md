# ADR-00442: klain:webview Stage 6 — window `.d.ts`, async typed bind, nested-tuple params

- **Relations**: Implements [TDD-00142](../tdd/TDD-00142.md); Extends [ADR-00441](ADR-00441.md), [ADR-00439](ADR-00439.md)
- **Date**: 2026-08-28

## Context

Stage 5 shipped typed bind + the `bindings` allowlist but left three items to a
Stage 6: a generated `Window` `.d.ts` (the DX/audit payoff of the typed surface),
**async** typed bind (a typed callback returning `Promise<T>`, which Stage 5
rejected), and advertising **nested-tuple params** (the projection already
supported them recursively).

## Decision

- **`--emit-window-dts`** — a CLI flag that, for a webview program, writes
  `<output>.window.d.ts` declaring `declare global { interface Window { … } }`
  from the typed bindings recorded during codegen. Each `window.name(...)` is a
  page-side Promise, so a sync callback returning `R` declares `Promise<R>` and an
  async one (`Promise<R>`) unwraps once to `Promise<R>`. `bindOne` records
  `{name, params, ret}` for every typed binding with a compile-time-known name
  (`bindings` keys, and `w.bind`/`bindTyped` with a string-literal name);
  `tsTypeString` maps compiler `Type`s back to TS (`number`/`string`/`boolean`,
  `T[]`, `[A,B]`, inline `{…}` object shapes, `unknown` for the unmappable).
  Dual-purpose: IDE autocomplete on `window.*` **and** a machine-checkable record
  of the exact frontend↔backend contract (the audit surface).
- **Async typed bind** — the Stage 5 rejection is removed. When a typed callback
  returns a Promise, the thunk decodes args, calls it, and attaches a
  **per-inner-type settlement runner** (`@__kml_wv_tret_<n>`, cached by inner-type
  shape) that on fulfillment `loadPromiseValue`s the settled `T`, `emitJSONStringifyValue`s
  it, and `webview_return(0, json)` — reusing the Stage 3 reaction plumbing
  (`emitWebviewAsyncReturn`, now parameterized by runner). The raw
  `Promise<string>` path keeps its verbatim `@__kml_wv_return_runner`.
- **Nested-tuple params** — no code change; a `(p: [number, number]) => …`
  binding already decodes via the recursive tuple projection. Now tested/advertised.

## Implementation notes

- `emitWebviewAsyncReturn(promiseRef, runnerFn)` gained the runner parameter so
  the same env/closure/reaction-attach serves both the raw string runner and the
  per-type typed runners.
- `loadPromiseValue(promiseReg, ty)` (emit_task_emit.go) already reconstructs a
  typed value (scalars/ptr via `promiseValFromBits`, arrays via the v0/v1 slots),
  so the typed runner needed no new promise-value machinery.

## Verification

- macOS (Apple Silicon M4), windowed (gated `KML_WEBVIEW_SMOKE`): a page
  `await`s `window.slowAdd(10,7)` (async `Promise<number>`) → `17` and
  `window.sumPair([3,4])` (nested-tuple param) → `7` (`TestE2EWebviewAsyncTypedSmoke`).
- `--emit-window-dts` renders the expected interface for scalars/string/object/
  async/nested-tuple bindings (`TestWindowDTS`, and a full CLI run inspected by
  hand). Compile-tier `TestE2EWebviewAsyncTypedCompiles`.
- Regression: webview/JSON/promise/async suites green; `go vet ./...` clean.
- Linux: compile-tier only, not yet run.
