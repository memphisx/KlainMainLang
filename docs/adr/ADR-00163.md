# ADR-00163: `.reduce()` with no initial value

- **Relations**: Extends [ADR-00153](ADR-00153.md)

## Context

Surveying fresh candidates outside `instanceof`/destructuring: `class MyArray extends Array {}` (real gap, but likely needs its own architectural design — a class extending a built-in whose representation is fundamentally different from a class instance's tagged heap struct, not today's material) and `arr.reduce((acc, val) => acc + val)` — real JS's optional-initial-value form of `.reduce()` — the latter turned out to already be a documented/code mismatch, not a fresh gap: `docs/status/ARRAY-METHODS.md`'s own table already listed `.reduce(fn, init?)` with the initial value marked optional, but `emitArrayReduce` (`codegen/llvm/emit_arrays_hof.go`) required exactly 2 arguments and rejected the 1-argument form outright.

## Decision

`.reduce(cb)` (no initial value) now matches real JS: the array's own first element seeds the accumulator, the fold starts from index 1 instead of 0, and an empty array with no initial value throws (`Reduce of empty array with no initial value`, this compiler's existing internal-throw convention — a plain `Error`, not a `TypeError`, matching how the pre-existing array-index-out-of-bounds throw is also a plain `Error`). The accumulator's type in this form is simply the array's own element type (nothing else to infer it from), still threaded through `resolveCallbackWithHints` exactly as the 2-argument form's `inferExprType(args[1])`-derived hint already was. Argument-count validation now accepts 1 or 2, and the callback is still resolved before the (now-conditional) initial-value evaluation, preserving the existing left-to-right evaluation order note.

## Side effects discovered

`.reduceRight()` (right-to-left fold) doesn't exist in this codebase at all — not a narrower version of this bug, a wholly separate, unimplemented method, confirmed absent from both the codegen dispatch and `ARRAY-METHODS.md`'s own table (unlike `.reduce()`, never claimed as done). Not implemented here — mirroring `.reduce()`'s loop in reverse, plus its own optional-initial-value handling, is a real, separate, comparably-sized piece of work, not a one-line extension of this fix. Noted as a newly-identified gap in `docs/status/ARRAY-METHODS.md` rather than silently left absent.

## Verification

- `go build`, `go vet ./...`, full `go test ./...`, `make examples` (all 109) — all pass.
- 4 new E2E tests (`tests/arrays_test.go`): no-initial-value fold, the single-element case (confirms the callback never runs — the loop starts at index 1 with length 1), the existing 2-argument form still working (regression check), and the empty-array throw, caught via `try`/`catch` and its `.message` checked.
- `examples/arrays/higher_order.ts` extended with all four of those same cases; built and ran directly, output matches the file's own inline comments exactly.
- Full Test262 corpus re-run: 4,463 → 4,463, no aggregate movement — expected, same reasoning as this session's other syntax/behavior fixes: the 1-argument form was a hard codegen error before, so no previously-*passing* file could regress from it.
