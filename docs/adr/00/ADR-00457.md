# ADR-00457: Node-strict net.isIP / isIPv4 / isIPv6

- **Date**: 2026-08-29

## Context

The Node oracle's closest-to-passing runtime failures included
`test-net-isipv4.js` and `test-net-isipv6.js`. Probing showed three
laxities of the platform (macOS) `inet_pton` relative to Node's parser:
leading-zero IPv4 octets accepted (`001.002.003.004`), IPv6 hex groups
longer than 4 digits accepted (`02001:db8::1` — including in the embedded
dotted-v4 tail), and Node-style zone IDs (`fe80::7:8%eth0`) *rejected*
where Node accepts them.

## Decision

Three IR helpers in the net runtime, layered in front of `inet_pton`:

- `__kml_net_v4_strict`: rejects any octet-initial `0` followed by
  another digit; gates the AF_INET attempt.
- `__kml_net_v6_strict`: rejects any hex group longer than 4 characters,
  stops validating at a `%` zone marker, and delegates an embedded
  dotted-v4 tail to `v4_strict` from the current group's start; gates the
  AF_INET6 attempt.
- `__kml_net_pton6z`: copies the address up to the `%` zone marker into a
  stack buffer before `inet_pton(AF_INET6)`, so zone-suffixed addresses
  validate as Node does.

## Verification

Mac (platform-touching: the laxities are macOS `inet_pton` behavior; the
strict pre-checks are platform-independent IR and reject before
`inet_pton` sees the string, but Linux behavior was not separately
probed). A probe generated from the corpus file's full `v6`/`v6not` lists
reports zero false positives/negatives; `tests/net_test.go` covers the
three laxities; net/dgram/tls/WebSocket E2E batches green. Node oracle:
**37 → 39 passed** (`test-net-isipv4.js`, `test-net-isipv6.js`).
