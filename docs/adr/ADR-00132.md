# ADR-00132: Multiple type parameters for user-defined generics (`<K, V>`)

- **Relations**: Extends [ADR-00103](ADR-00103.md), [ADR-00121](ADR-00121.md). Implements [TDD-00037](../tdd/TDD-00037.md)
- **Date**: 2026-08-09

## Context

[TDD-00010](../tdd/TDD-00010.md)/[ADR-00103](ADR-00103.md) scoped user-defined generics (V1 monomorphization, and V2 `@erased` type erasure per [ADR-00121](ADR-00121.md)) to exactly one, unconstrained type parameter throughout — functions, interfaces, and classes alike. [TDD-00037](../tdd/TDD-00037.md) scoped the natural follow-on, multiple type parameters (`<K, V>`), as a fully-designed but not-yet-implemented document. This ADR implements that design.

Picked up as the next roadmap item per the project's own current core-language-completion weighting, alongside `docs/status/README.md`'s TDD index listing TDD-00037 as "Not Started" with no other blocker.

## Investigation

Read TDD-00037's own Design section, which had already done the investigation: `FunctionDeclaration.TypeParams`/`InterfaceDeclaration.TypeParams`/`ClassDeclaration.TypeParams` and `NewExpression.TypeArgs` were already `[]string`/`[]*ast.TypeAnnotation` in `ast/nodes.go` — plural, but unread past index 0 everywhere in `emit_generics.go`. Confirmed by grepping every `TypeParams[0]`, `substituteGenericType(`, `buildGenericParamSig(`, `genericFuncTypeParamIndex(`, and `len(...TypeArgs) == 1` call site directly against the current tree before writing any code — all matched what the TDD's own table predicted, with no drift since the TDD was written the day before.

Confirmed `TypeAnnotation` had no field for a user-defined generic interface's N type arguments (`ElemType`/`KeyType` are semantically the built-ins' own single/paired slots and had to stay untouched) — the TDD's proposed new `TypeArgs []*TypeAnnotation` field was the only real new AST surface needed.

## Decision

**Parser**: three independent comma-rejection choke points became loops, exactly as scoped — `parseTypeParamList` (`parser/parser.go`, declaration site) now collects `IDENT`s separated by `COMMA` into `[]string`; the user-defined-generic-type-usage branch (`parser_types.go`, plain-annotation usage site, e.g. `x: Box<K, V>`) now loops into the new `TypeAnnotation.TypeArgs` field (also setting `ElemType` to the first argument, preserving the pre-existing single-argument fallback behavior other `resolveType` branches already rely on for an unrecognized generic name); `parseNewGenericBody` (`parser_literals.go`, construction site) now loops into the already-plural `NewExpression.TypeArgs`. None of the three check argument count against a declaration's own `TypeParams` — the parser has no symbol table, so arity checking stays deferred to codegen, same as V1.

**Codegen**: every `emit_generics.go` substitution/mangling function was widened from a single `(typeParam string, concrete Type)` pair to `subs map[string]Type`: `substituteGenericType`, `buildGenericParamSig`, `instantiateGenericInterface`, `genericClassMangledFields`, `instantiateGenericClass`, `instantiateGenericFunc`, `genericClassInstanceType`. A new `mangleTypeArgs(typeParams []string, subs map[string]Type)` joins one `mangleTypeArg` suffix per declared type parameter with `_`, in declaration order, so the mangled name stays deterministic regardless of `subs`' own map iteration order (`Pair<number,string>` → `Pair__num_str`). A new `buildTypeArgSubs(typeParams []string, typeArgs []*ast.TypeAnnotation)` zips a declaration's `TypeParams` positionally against a usage site's already-arity-checked `TypeArgs`, resolving each via `resolveType` — the one helper every external call site (function-call inference aside) now goes through to build its `subs` map.

**Generic-function inference**, the one place V1 needed real per-parameter logic (interfaces/classes are always explicit, so nothing new was needed there): `genericFuncTypeParamIndex` now returns `map[string]genericParamPos` (one independent inferable-position lookup per type parameter, `genericParamPos{Idx, IsArray}`) instead of a single `(idx, isArray)` pair. `inferGenericCallConcreteTypes` (renamed/pluralized from `inferGenericCallConcreteType`) loops over `decl.TypeParams`, inferring each independently and returning `(subs, missing, ok)` — `missing` names the specific type parameter that had no inferable position, the moment the first one fails, so `emitGenericFuncCall`'s error message can say `cannot infer type argument 'V' for generic function 'pair'` instead of a generic "a type argument" message. This is a strict generalization of V1's existing single-parameter rule, not a new design axis, exactly as the TDD predicted — no two type parameters can ever compete for the same inference source, since a parameter's type annotation names exactly one type-parameter name.

**V2 `@erased`** needed no new design, only the mechanical `map[string]Type` rework: `registerFunctions`' erased branch (`emitter.go`) now builds `subs := map[string]Type{}` with every one of `fd.TypeParams` mapped to `TypeAny`, instead of a single-entry substitution — no new inference/mangling/ambiguity questions, confirming the TDD's own claim that V2 gets this almost for free.

**Arity checking** at the three call sites the TDD named (`emit_exprs_vardecl.go`, `emit_classes.go`'s `emitNewExpression`, `emit_exprs_types.go`'s `inferExprType`) generalized from `len(init.TypeArgs) == 1` to `len(init.TypeArgs) == len(genDecl.TypeParams)`; `emitNewExpression`'s error message now names the exact required count and the declared parameter names (`generic class 'Pair' requires exactly 2 explicit type argument(s) (e.g. new Pair<K, V>(...))`) instead of a hardcoded "exactly one." `resolveType`'s generic-interface branch (`emitter.go`) switched its guard from `ta.ElemType != nil` to `len(ta.TypeArgs) > 0` and now builds its `subs` map via `buildTypeArgSubs` before calling `instantiateGenericInterface`.

## Implementation notes

- **AST**: `TypeAnnotation.TypeArgs []*TypeAnnotation` (`ast/nodes.go`) — new field, populated only by `parser_types.go`'s generic-usage branch; every built-in (`Promise`/`Map`/`Set`/`EventEmitter`/plain arrays) keeps using `ElemType`/`KeyType` exactly as before, untouched.
- **Files touched**: `ast/nodes.go`, `parser/parser.go`, `parser/parser_types.go`, `parser/parser_literals.go`, `codegen/llvm/emit_generics.go` (largest diff — every substitution/mangling function's signature), `codegen/llvm/emitter.go` (resolveType's generic-interface branch, registerFunctions' `@erased` branch), `codegen/llvm/emit_exprs_vardecl.go`, `codegen/llvm/emit_exprs_types.go`, `codegen/llvm/emit_classes.go` (`emitNewExpression`'s arity check/error message).
- No changes were needed in `registerClasses` (`emit_classes.go`) — its generic-class validation (no `extends`/`implements`/`abstract`/static members) was already arity-agnostic, keyed only on `len(cd.TypeParams) > 0`.
- Kept the parser's generic-usage-branch `ElemType = args[0]` assignment (in addition to the new `TypeArgs` field) deliberately: `resolveType`'s final fallback (`if ta.ElemType != nil { return ArrayOf(...) }`) already treated an unrecognized single-arg generic name's argument as an implicit array-element type before this change; setting `ElemType` to the first of N arguments preserves that exact pre-existing fallback behavior for an unrecognized multi-arg generic name, rather than introducing a new, different fallback.

## Side effects discovered

None new. TDD-00037's own "explicitly out of scope, not a new gap" note (the same type parameter appearing on more than one parameter, e.g. `function same<T>(a: T, b: T): T`, silently coercing the second occurrence's argument against the first's inferred type with no runtime consistency check) is a pre-existing V1 gap, unchanged by this work — confirmed still true by inspection of `inferGenericCallConcreteTypes`, which infers each *type parameter* once from its own designated position regardless of how many parameters share that type parameter's name.

## Verification

- `go build -o klainmain .`, `go vet ./...`, and the full `go test ./...` suite (including the pre-existing generics suite) pass.
- The stale `TestE2EGenericMultipleTypeParamsRejected` (asserted a parse error for `<T, U>`, the exact behavior this ADR replaces) was removed rather than left contradicting the shipped feature.
- Added to `tests/generics_test.go`: `TestE2EGenericFunctionMultipleTypeParams` (independent inference per type parameter), `TestE2EGenericFunctionMultipleTypeParamsMangledNameOrder` (confirms declared-order mangling, `firstOf__num_str`, via direct IR inspection), `TestE2EGenericFunctionUninferableTypeParamNamed` (confirms the error names the specific failing type parameter, `'V'`), `TestE2EGenericInterfaceMultipleTypeParams`, `TestE2EGenericClassMultipleTypeParams`, `TestE2EGenericClassMultipleTypeParamsArityMismatchRejected`, `TestE2EErasedGenericFunctionMultipleTypeParams` (confirms no V1-style mangled symbol for an erased 2-type-param function).
- New example `examples/generics/multi_type_params.ts` — compiled and run manually (`./klainmain` + execute) to confirm real output matches the file's own inline comments before committing, in addition to being picked up automatically by `make examples` (glob-based, no registration needed).
- Verified only on the x86-64 Linux box (this project's other machine, Apple Silicon, wasn't used for this change) — nothing in this diff touches platform-sensitive code (no C runtime, no OS/libc calls), so no platform-specific risk is expected, but noted per the project's own standing rule regardless.
