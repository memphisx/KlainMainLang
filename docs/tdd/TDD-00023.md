# TDD-00023: `EventEmitter<T>` (`events` module)

- **Status**: Implemented ([ADR-00089](../adr/ADR-00089.md))
- **Date**: 2026-08-03

## Context

`docs/status/EVENT-EMITTER.md` tracks Node's `EventEmitter` at 0/6 coverage, flagged as "a bigger prerequisite than it looks" — Node's own `stream` module, event-driven `readline` (`'line'` events), and async `child_process` are all built on top of it. This closes that gap and unblocks those three, in line with the project's own CLI/microservice prioritization.

This is a genuinely novel piece of design, not a routine feature add, for two independent reasons:

1. **Payload typing.** Real Node's `emit(event, ...args)` is fully variadic and untyped. This compiler has none of the prerequisites: rest parameters are homogeneous-only and don't support call-site spread (`f(...arr)` is unimplemented), and `any`/`unknown` is a hard compile error as a function-parameter or array-element type (`emit_dynamic.go`). A real variadic `emit` isn't buildable today.
2. **`class X extends EventEmitter<T>`.** No existing built-in generic (`Map<K,V>`, `Set<T>`, `Promise<T>`) is ever an `extends` target, and no generic mixes with `extends` anywhere in the codebase — `class` inheritance (ADR-00083, TDD-00009 Stage 3) was built entirely around user-declared classes extending other user-declared classes.

## Design

### Payload model: `EventEmitter<T>`, one concrete type per instance

`EventEmitter<T>` is a compiler-recognized generic built-in, monomorphized per concrete `T` at compile time — the same pattern `Map<K,V>`/`Set<T>`/`Promise<T>` already use, not real user-generics (TDD-00010 is unrelated and still unstarted). `new EventEmitter<string>()` gives listeners typed `(data: string) => void`; `.emit(event, data)` takes exactly one payload argument of that same `T`. This is a deliberate narrowing from real Node (single payload, not `...args`), decided with the user before this document was written — the alternative (zero-arg-only events) was rejected as too narrow for the `readline` `'line'`-event use case this feature is meant to unblock.

### Storage: an event-name → listener-list map, listener lists as their own small heap struct

Confirmed by reading `emit_collections.go`/`runtime_collections.go`: `Map<K,V>`'s value storage (`__kml_map_str_set`/`_get`) already stores *any* single-word value uniformly as `i64`, via `ptrtoint`/`inttoptr` for pointer-shaped values (`valueToMapVal`/`mapValFromI64`, `emit_collections.go:364-404`). A listener-list handle is just a `ptr` — a single word — so `Map<string, ptr>`'s existing runtime helpers (`__kml_map_str_create`/`_get`/`_set`/`_keys`) can be called *directly, by name* from new EventEmitter-specific codegen, with no changes to `Map`'s own implementation at all. The earlier assumption that Map's value storage would need modification (an artifact of conflating "the listener list itself" with "the map's value slot") doesn't hold once the value slot is recognized as just a pointer to that list, not the list inline.

Each event's listener list is its own tiny heap struct — `{ptr data, i64 len, i64 cap}` header (byte-identical shape to `runtime_process.go`'s exec-output buffer), each entry `{ptr listener, i64 once}` (16 bytes: the closure header pointer, plus a flag for `.once()`).

`Type.IsEventEmitter` is **deliberately independent from `IsMap`** — unlike `IsURLSearchParams`, which does set `IsMap` on purpose so `.get()`/`.set()`/etc. fall through generically. EventEmitter's surface (`on`/`once`/`emit`/`off`/`removeListener`/`removeAllListeners`/`listenerCount`/`eventNames`) shares no method names with Map's, and letting `.get()`/`.set()`/`.delete()`/`.forEach()` leak onto an EventEmitter value would be a real, silent correctness gap. The underlying runtime pointer is layout-compatible with `__kml_map_str_create()`'s result, but the `Type` value itself carries no flag that would let existing Map-dispatch code match it by accident.

### `class X extends EventEmitter<T>`: a synthetic root, never a real registered class

`EventEmitter` is never added to `e.classes` — no `TagID`, no vtable slot, not `instanceof`-checkable, consistent with `Error`/`Date`/`Map` today. Instead:

- `registerClasses`' Pass 0 (`visit`) treats `extends EventEmitter<T>` as a synthetic root: no recursion into `classDeclByName` (there's no declaration to recurse into), just validation that exactly one type argument was supplied. A class extending *any other* base with type arguments (`extends Bar<T>` where `Bar` isn't `EventEmitter`) is rejected here with a clear error — generic extends is EventEmitter-only for now.
- Pass 1's `haveBase` becomes `cd.BaseClass != "" && cd.BaseClass != "EventEmitter"` — a class directly extending `EventEmitter<T>` flows through the *existing* "root class, implicit constructor rules" logic completely unchanged, since EventEmitter contributes no fields and no constructor to forward through `super(...)`. There is nothing to call `super(...)` on for an EventEmitter-rooted class — matching real Node, where `super()` inside a class extending `EventEmitter` is optional and typically omitted.
- A new hidden struct field, `__kml_ee_listeners` (a `ptr` to the underlying `Map<string,ptr>` handle), is injected — positioned after the existing tag(0)/vtable(1, if present) hidden fields, the third generalization of the same positional-hidden-field scheme Stage 2→3 already established. `HasEventEmitter`/`EventEmitterPayload` propagate down an inheritance chain exactly the way `HasVTable`/`RootClass` already do (read from `baseInfo`, which by topological order is already fully populated by the time a descendant is processed).
- `on`/`once`/`emit`/`off`/`removeListener`/`removeAllListeners`/`listenerCount`/`eventNames` are hand-written Go codegen (a new `emit_eventemitter.go`), dispatched by name from `emit_call.go` exactly the way `Map`/`Set` methods are — never real AST-driven class methods, never a vtable slot. **Overriding one of these names is rejected at `registerClasses` time** as a reserved-name collision (the same mechanism `ClassTagField`/`ClassVTableField` already use for field names, generalized to this fixed method-name set) — this is what keeps "does overriding an EventEmitter method interact with the vtable" out of scope entirely, by construction, rather than by leaving it as an untested edge case.

### `once()`: a flag alongside the raw listener pointer, not a wrapper closure

A wrapper-closure approach (synthesizing a fresh closure that calls the real listener then self-removes) would break `.off()`'s identity-based removal: a caller holding a reference to their original listener could never match it against the synthesized wrapper stored internally — a real, user-visible bug. Instead, each list entry carries the raw listener pointer plus a `once` flag; `.emit()`'s invocation loop removes an entry immediately after calling it if that flag is set. This keeps listener identity exactly what the user passed, at the cost of `.emit()` doing a linear identity-based `__kml_ee_list_remove` per fired `once` entry — real Node has the identical "same closure registered via both `.on()` and `.once()`" ambiguity (first-match removal), not a regression introduced here.

### `emit('error', data)`: throws if unlistened, resolved entirely at the call site

No runtime round-trip: a `strcmp` against the literal `"error"`, gated on "zero listeners were invoked" for this call, feeds directly into the existing `buildErrorObj`/`emitValueToString`/`__kml_throw` machinery (`emit_exceptions.go`) `emitThrow` already uses for a thrown non-object primitive. The throw path branches at Go-compile-time (not runtime — the payload type `T` is fixed per `EventEmitter<T>` instantiation) on whether `T.IsError`: an `EventEmitter<Error>` (or a built-in Error subtype) rethrows the exact payload object via `__kml_throw` directly; any other `T` stringifies the payload and wraps it in a base-Error-shaped object, the same fallback `emitThrow` already applies to a thrown string/number.

### Build order

Standalone `EventEmitter<T>` (no `extends` at all) first, verified end-to-end — it alone delivers the full method surface with zero interaction with the class/inheritance system. Then a single-level `class X extends EventEmitter<T>` with no further subclassing and no vtable. Then multi-level subclassing plus `HasEventEmitter && HasVTable` coexistence (confirming the hidden-field index is 1 vs. 2 correctly in both cases) last. No precedent exists anywhere in this codebase for a generic base class interacting with `registerClasses`' topological-order/override-analysis machinery, so the full matrix is deliberately not attempted in one pass.

## Open questions

- Whether a future user-defined-generics pass (TDD-00010) should eventually subsume this hand-rolled `EventEmitter<T>` the way it might `Map`/`Set`/`Promise` — not decided, not blocking; this feature follows the existing built-in-generic convention rather than waiting on that unstarted work.
- Whether `.eventNames()`'s return order (insertion order, following `__kml_map_str_keys`'s own scan order) should be documented as a guarantee or left unspecified — leaning toward documenting it as insertion order since that's what the underlying implementation already provides deterministically, but not load-bearing for any planned use case.
