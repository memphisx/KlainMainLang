# TDD-00017: fetch() client parity — custom method, headers, request body

- **Status**: Implemented
- **Date**: 2026-07-29

## Context

`fetch()` is GET-only (`CLAUDE.md`'s project-direction section names this explicitly, and `emit_fetch.go`'s own header comment says so): no way to send a POST/PUT/DELETE, no custom request headers, no request body. This is the client-side half of REST API interaction — priority #1 in this project's stated direction — and the server side already has the symmetric capability: `http.listen` request handlers get `req.headers`/`req.query` (`Map<string, string>`) and `req.body` (`ADR-00072`). A KML program can already *serve* a JSON API that reads custom headers and a request body, but can't *call* one beyond a bare GET. Picked up as the next structural priority after `Promise.all`/`.race`/`.allSettled` ([ADR-00073](../adr/ADR-00073.md)) closed out the event loop's own roadmap.

## Design

**API shape: a second, optional `init` argument, not `Request`/`Headers` classes.** `fetch(url)` unchanged; `fetch(url, init)` where `init` is any object value with some subset of `method: string`, `headers: Map<string,string>`, `body: string` fields. No new `Request`/`Headers` runtime type is introduced — this reuses the exact structural-typing pattern `http.listen`'s handler return type already uses for its own optional `headers: Map<string, string>` field (`emit_http.go`'s `FieldIndex("headers")` check, [ADR-00072](../adr/ADR-00072.md)): a call site's init object literal gets its own ad-hoc inferred type, and codegen checks `FieldIndex("method")`/`FieldIndex("headers")`/`FieldIndex("body")` on it directly — no shared `RequestInit` interface has to exist, and no optional-field (`field?:`) syntax is needed at all. Rejected a real `Headers`/`Request` class pair as more machinery than this project's existing conventions call for: every other place this codebase represents a bag of string headers (`req.headers`, a handler's response `headers` field) already uses a plain `Map<string, string>`, not a bespoke class — matching that is more consistent than introducing a one-off `Headers` type solely for the client side.

**Runtime signature**: `__kml_fetch_async(ptr url) -> ptr` (existing, [ADR-00050](../adr/ADR-00050.md)) grows to `__kml_fetch_async(ptr url, ptr method, ptr headers, ptr body) -> ptr`. `method`/`headers`/`body` are each nullable — the function itself branches on runtime nullness (`icmp ne ptr %x, null`) before calling the corresponding `curl_easy_setopt`, since it's one shared piece of IR called from every `fetch()` call site in a program, some of which may pass an init object and some not. The *caller* (`emitFetch`) decides what to pass at each call site based on the init object's own compile-time-known field set — passing a literal `null` for any field the init object doesn't have — so there's no runtime cost or ambiguity for the common `fetch(url)` case, only three extra `icmp`/`br` pairs (all folding to the same `skip*` path) compared to today.

`headers` is a `ptr` to a `struct curl_slist` (libcurl's own linked-list-of-strings type for `CURLOPT_HTTPHEADER`) — built by new codegen (`emitFetch`) from the `Map<string,string>` value using the exact iteration primitives `emit_collections.go`'s `mapKeysAndVals` already exposes (`__kml_map_str_keys`/`__kml_map_str_vals`, the same pair `map.entries()`/`map.forEach()` already use), one `curl_slist_append` call per entry inside a hand-rolled compile-time loop (matching this codebase's existing per-feature loop-emission style — `emit_promise.go`'s `emitPromiseLoop`, `emit_arrays.go`'s HOF loops — rather than factoring out a new "generic loop" abstraction nothing else shares yet). Each "key: value" line is built with the existing `emitStringConcat` helper (`emit_strings.go`), reused as-is.

`body` sets `CURLOPT_POSTFIELDS` directly; combined with `CURLOPT_CUSTOMREQUEST` for a non-GET method (verified against libcurl's own documented behavior, not assumed: setting `POSTFIELDS` alongside a `CUSTOMREQUEST` override is the standard, well-documented way to send a body with an arbitrary HTTP method through the easy/multi interface — curl still sends the custom method line but includes the body). No `CURLOPT_POSTFIELDSIZE` — relying on curl's own `strlen()`-based default for a null-terminated `POSTFIELDS` string, consistent with this compiler's existing plain-C-string model (and its already-documented, unrelated embedded-null-byte limitation, `STATUS.md`'s Known Limitations).

**Validation**: reject at compile time (matching `isPlainStringType`'s existing pattern in `emit_http.go`) if `init.method`/`init.body` are present but not a plain string, or if `init.headers` is present but not exactly `Map<string, string>` — a clear compiler error, not silent misbehavior or a runtime crash.

**Memory**: the `curl_slist` built per call, like every other fetch-related allocation this compiler makes (the pending-fetch struct, the response buffer, the `Response` object itself), is never freed in `manual` mode — consistent with the rest of this feature area's already-documented "everything leaks, `-mm=gc` is the opt-in fix" characteristic ([TDD-00001](TDD-00001.md)), not a new gap. Freeing it selectively while everything else around it keeps leaking would be inconsistent effort for no real benefit; deliberately not attempted here. (Note: `-mm=gc`'s Boehm collector cannot reclaim it either way — `curl_slist_append` uses libcurl's own internal `malloc`, not this compiler's GC-instrumented allocator, so the list lives outside Boehm's reach regardless of compilation mode. Same as every other libcurl-internal allocation already made by `ensureFetch`/`ensureFetchAsync`.)
