# ADR-01952: Null and union narrowing come from the checker alone

- **Relations**: Implements TDD-00230
- **Date**: 2026-10-28

## Context

The emitter kept its own flow narrowing next to the checker's. It recorded a null guard (`if (x != null)`) as a non-null mark on the binding, and a union guard (`typeof`, `instanceof`, `in`, truthiness) as a narrowed type. The checker already answers both questions for every identifier read, so two analyses could disagree, and some did: a guarded bigint, symbol or function member was read through the wrong layout.

A separate bug turned up while testing this: `x?.[i]` evaluated its receiver twice when the receiver's run-time type was not the one inferred, so `it.next().value?.[0]` advanced the iterator twice.

## Decision

The emitter no longer narrows by itself. An identifier read takes its narrowed type from the checker only. The checker's union narrowing covers the `symbol` and `bigint` members, and a call through a union that the checker narrowed to a function calls it as one. The rebinds that change storage stay: an `instanceof` test on a host subclass and the retyped catch binding.

An optional index whose receiver did not need a guard indexes a binding of the value it already evaluated.

## Consequences

- About 400 lines of emitter narrowing are gone, including the narrowed-conditional emit path.
- Tests: the existing narrowing, union and conditional suites, plus `TestE2EBuiltinIteratorIntrinsics`. Outputs were compared against Node on macOS (Apple Silicon) and Linux (x86-64).
