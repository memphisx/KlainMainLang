# ADR-00596: typeof on namespace static methods

- **Relations**: Extends [ADR-00282](ADR-00282.md)
- **Date**: 2026-09-01

## Context

`typeof <namespace>.<method>` answered `"function"` only for the `Promise`
combinators, the `Math` function set, and `JSON.parse`/`stringify`. Every other
static-method reference (`Object.keys`, `console.log`, `Number.isInteger`,
`Date.now`, …) fell through to inference's `"number"` default — a silently wrong
answer, since `typeof` is resolved to a compile-time string constant.

## Decision

Extend `typeofStaticAnswer`'s member-expression handling:

- `console` — any member reference is `"function"` (every console member this
  compiler exposes is a method, and real console has no non-function own
  properties), so no enumeration is needed.
- `Object`/`Number`/`String`/`Array`/`Date`/`Symbol`/`Reflect`/`Boolean` — a
  `typeofNamespaceStatics` table lists each one's static *method* names; a listed
  member is `"function"`. A non-method static (`Number.MAX_VALUE`,
  `Symbol.iterator`) is deliberately absent and falls through to normal
  inference, so it keeps its correct type.

This is allow-list-based by nature (the concern ADR-00282 raised); the ES static
surface of these namespaces is stable, and an unlisted method now reads through
inference rather than a wrong `"number"`. `typeof` remains fully compile-time, so
this can only make an answer *more* correct — it cannot affect runtime behavior.

## Verification

`TestE2ETypeofNamespaceStaticMethods` (`Object.keys`/`console.log`/
`Number.isInteger`/`Date.now`/`Array.isArray`/`String.fromCharCode` → `function`,
`Number.MAX_VALUE` → `number`), matching Node v26. The existing typeof suite
still passes. Built and verified on Mac (Apple Silicon).
