# ADR-00753: `execSync`/`execFileSync` throw on a non-zero exit status

- **Relations**: Implements a [TDD-00180](../tdd/TDD-00180.md) §3 row ("`execSync` non-zero status: Node throws … Here: returns"); extends [ADR-00411](ADR-00411.md) (the blocking `spawnSync` C core these wrap), [ADR-00025](ADR-00025.md) (the bespoke `process.execFileSync` that already throws)
- **Date**: 2026-09-07

## Context

`child_process.execSync(command)` and `execFileSync(file, args)` returned the child's captured stdout unconditionally — a non-zero exit status was silently swallowed. Node instead **throws** in that case (the return value is only produced on success), which is how the overwhelmingly common `try { execSync(cmd) } catch { … }` "run this or fail" idiom detects failure. A compiled program using that idiom saw the command silently "succeed", a correctness gap flagged in the [TDD-00180](TDD-00180.md) §3 audit.

## Investigation

Both `emitCPExecSync` and `emitCPExecFileSync` (`emit_childprocess.go`) already call the blocking `__kml_cp_spawn_sync` core and pulled field 1 (stdout) out of its result struct (`{ i64 status @0, ptr stdout @8, ptr stderr @16, i64 pid @24 }`, `cpSpawnSyncResultType`), ignoring the status at field 0. So the exit status was already computed and discarded — the fix is to branch on it.

The obstacle to full fidelity is the thrown value's shape. Node's `execSync` throws an `ExecException` carrying `.status`, `.stdout`, `.stderr`, `.signal`, `.pid`, `.output`. This project's thrown errors are all one shared `errorObjType` (`kind`/`message`/`name` + the Node error-code trio `code`/`errcode`/`errstr`), with 74 sites and the `AggregateError` layout overlapping its prefix — extending it with exec-specific fields is disproportionate and risky for this fix, and `catch (e)` always binds `e` at `errorObjType` regardless of the thrown value. `spawnSync` already exposes `status`/`stdout`/`stderr` without throwing, so the exit code and captured output remain reachable there.

## Decision

Throw on a non-zero exit; keep the thrown value a plain `Error`.

A shared `cpExecSyncResult(raw, cmdVal)` reads the status (field 0) and stdout (field 1) from the spawn-sync result, then branches: on `status != 0` it builds the message `Command failed: <command>` (runtime `emitStringConcat` of the interned prefix with the command/file expression, matching Node's message prefix) and throws it via `emitInternalThrow`; otherwise it returns the stdout string. Both `emitCPExecSync` (passing the command) and `emitCPExecFileSync` (passing the file) route their result through it.

The richer `ExecException` properties (`.status`/`.stdout`/`.stderr`) are deliberately **not** attached — a documented caveat, with `spawnSync` as the escape hatch when a failing command's exit code or output is needed.

## Implementation notes

- `emitInternalThrow` emits its own `unreachable` terminator, so the throw sits in its own `execsync.fail` block and control falls through to `execsync.ok` on success — the standard branch/label/throw shape (`freshLabel`/`emitTerminator`/`emitLabel`) used by the TypedArray bounds checks.
- Nothing about the message is Windows-specific: on Windows `execSync` runs through `cmd.exe /c` (ADR-00740) and the child's exit code arrives at field 0 the same way, so `exit N` yields status `N` and throws identically to `/bin/sh -c 'exit N'` on POSIX.

## Side effects discovered

None. The `.status`/`.stdout`/`.stderr`-on-the-error gap is pre-existing (they were never attached) and is now the sole remaining item on this row.

## Verification

- New E2E test `TestE2EChildProcessExecSyncThrowsOnNonZero` (`tests/childprocess_test.go`): `execSync("echo ok")` returns `ok`; `execSync("exit 7")` throws with a message starting `Command failed`. `echo`/`exit` are builtins of both `/bin/sh` and `cmd.exe`, so it runs on **every host including Windows** (verified on Windows 11) with no POSIX-tools skip.
- Existing `child_process`/`exec`/`spawn` suite unchanged and green (62s on Windows 11) — no test relied on the old silent-success behaviour.
- `examples/child_process/child_process.ts` extended with an `execSync` success + throw demonstration.
- `go build`, `go vet ./...` clean; `make status`/`make status-check` and `make reference-check` pass (status JSON + website reference JSON updated same-commit — the stale "does not throw" caveat replaced); `make conformance` run at delivery.
- Platform: verified on **Windows 11** (x86-64, MSYS2 UCRT); the POSIX path is unchanged shared code.
