# ADR-00212: Temporal-dead-zone early error, and the block-shadowing bug behind it

- **Relations**: `Implements TDD-00071` (Stage 1 of 2 — TDZ; definite-assignment is Stage 2). `Extends ADR-00210` (the scoping work that left the TDZ caveat).
- **Date**: 2026-08-18

## Context

The Variable declarations status row listed, as a remaining caveat, that a `let`/`const` read before its declaration was rejected only as a generic `undefined variable`, not the spec's `Cannot access 'x' before initialization`. While scoping [TDD-00071](../tdd/TDD-00071.md) this turned out to hide a real correctness bug, not just a weak message: the *shadowing* form was silently miscompiled. `let x = 1; { console.log(x); let x = 2; }` should be a TDZ error — the inner `let x` governs the entire inner block, so the `console.log` sits in its dead zone — but the compiler resolved the reference to the *outer* `x` and printed `1`. That elevated the caveat from cosmetic to a soundness fix.

## Investigation

The symbol table is populated as declarations are emitted in order, so a read of a not-yet-emitted `let` simply wasn't found and fell through to `undefined variable` — and a read inside a block whose own later `let` shadows an outer binding found the *outer* one instead of recognizing the inner binding's dead zone. Real engines model this by hoisting each block's lexical names to the block top in an uninitialized (TDZ) state; the compiler had no such per-block lexical-hoisting notion at the point identifiers resolve.

`resolver/rename.go` already performs a complete scope-aware statement+expression walk (`rewriteStmt`/`rewriteExpr`, 64 expression cases, push/pop scope frames), which is the exact traversal shape a TDZ check needs — read-only rather than rewriting.

## Decision

A new resolver pass, `resolver/readability.go` (`checkTDZ`), run per file before mangling (so errors carry the original name and fire before codegen, as early errors), modeled on `rename.go`'s traversal. It maintains a stack of scope frames; each frame hoists its block's `let`/`const`/`class`/`enum` names in a `tdzUninit` state and records `var`/`function`/parameter/`catch` names as always-readable shadows. Walking a body in order flips each lexical name to `tdzInit` as its declaration is reached (and a declaration's own initializer is walked *before* the flip, so `let z = z + 1` is a TDZ). A variable read resolves against the stack innermost-first; a read that binds to a still-`tdzUninit` lexical name is `cannot access 'x' before initialization`. The shadowing bug is fixed as a direct consequence: inside the block, `x` resolves to the block's own hoisted (uninitialized) `x`, so the pre-declaration read errors instead of silently reading the outer binding.

**Soundness over completeness** ([TDD-00071](../tdd/TDD-00071.md)'s no-false-positives rule): a read that crosses a **function boundary** to reach the TDZ binding is exempt — real TDZ is a runtime check and the closure may legally run after the declaration initializes, so flagging it would be a false positive. `checkRead` tracks whether a function boundary was crossed while walking outward and only errors when the binding is reached within the same function. Node types the walk doesn't descend into (a tagged template, a `new` expression's arguments, object-literal shorthand values, class field initializers) simply miss potential errors — a documented V1 gap — rather than risk a wrong resolution.

## Implementation notes

- Every lexical-kind declaration must flip its name out of TDZ, or a *later* legitimate read would be a false positive. This bit `enum` first: an `EnumDeclaration` isn't a var-decl, so it needed its own `markInitialized` case — otherwise `enum E { A } … E.A` wrongly errored. `interface`/`type` are type-space (`isLexicalKind` excludes them), so they never enter TDZ.
- A for-of loop variable that is a destructuring pattern (`for (const [a, b] of …)`) binds `a`/`b`, not a single `VarName`; those leaf names must be recorded, or a body read of `a` alongside an outer later `let a` would be a false positive. `forLoopVarNames` flattens the pattern.
- The for-head and each for-of/for-in loop get their own frame enclosing the body, matching JS per-loop lexical scoping; the iterable is walked before the loop variable is bound (`for (const x of x)` is a TDZ).

## Side effects discovered

- The shadowing miscompile (reading the outer binding, printing `1`) was a latent correctness bug, not just the documented message-quality gap — now a compile error, matching JS.
- The pre-existing, separate limitation that a top-level function can't reference a sibling top-level `let`/`const` at all ([ADR-00166](ADR-00166.md), a codegen scoping gap) is unchanged: `checkTDZ` correctly *exempts* that cross-function read, after which codegen still rejects it for its own unrelated reason. This ADR neither fixes nor worsens it.
- Definite-assignment for a typed `var` (the other remaining caveat) is [TDD-00071](../tdd/TDD-00071.md) Stage 2, not this change — the interim zero-default from [ADR-00210](ADR-00210.md) still stands for it.

## Verification

- 6 new E2E tests in `tests/func_test.go` (routed through the resolver via `parseAndCompileImports`/`assertOutputImports`, since the single-source helpers bypass the resolver where `checkTDZ` runs): use-before-declaration, the shadowing form, a self-referential initializer (all rejected with `before initialization`); read-after-declaration and enum-after-declaration (allowed); and a closure reading a later outer binding (not flagged — the soundness guarantee).
- Full `go test ./...` green (Mac, Apple Silicon M4); `go vet ./...` clean; `make examples` 126/126 — the critical false-positive check, since it exercises the real resolver path on 126 programs.
- `make conformance`: parse-level early-error signal only; the committed Linux baseline `CONFORMANCE-RESULTS.md` is not overwritten from a Mac run (see [ADR-00210](ADR-00210.md)).
