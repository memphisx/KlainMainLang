# TDD-00249: Stack overflow throws a RangeError

- **Status**: In Progress
- **Date**: 2026-10-11

## Context

Node throws `RangeError: Maximum call stack size exceeded` when recursion
runs out of stack, and a program can catch it. A compiled program cannot:

- `clang -O2` turns a self-call in tail position into a loop (tail-call
  elimination), so unbounded recursion such as
  `function f() { f(); }` never ends.
- A recursion that does grow the stack dies with SIGSEGV.
- The only existing check (`jmpstacksrc/jmpstack.c`) counts nested `try`
  frames, not calls.

Node's `test-fs-readdir-stack-overflow.js` recurses through
`fs.readdirSync('.')`. Compiled, the loop allocates a listing per
iteration until the machine runs out of memory: 10 GB on the Mac, the
whole 7 GB container on Linux arm64. That stopped the macOS and Linux arm64
node conformance runs.

## Design

Two parts.

**1. No tail calls in emitted code.** Every `call` in the emitted IR is
`notail`. LLVM's tail-call elimination pass and the backend's sibling-call
optimization both skip a `notail` call, so recursion grows the stack, as it
does in Node. The marking is done once, on the finished module text in
`EmitProgram`, so no call site can miss it.

**2. A stack-overflow handler.** At startup, `main` calls
`__kml_stack_guard_init(throwFn, msg)` (`stackguardsrc/stackguard.c`). It
records the main thread's stack bounds, installs an alternate signal stack,
and installs a SIGSEGV/SIGBUS handler on it. The handler treats a fault as
a stack overflow when the address lies just below the stack's low end (the
guard region). It then:

- calls `throwFn` (`@__kml_throw_range_error`) with the message. That
  builds a RangeError and longjmps to the innermost `try`, or reports it as
  uncaught and exits 1, as any other throw does;
- when the program has no throw path (`throwFn` null), prints
  `RangeError: Maximum call stack size exceeded` and exits 1.

Any other fault restores the default action and returns, so it faults
again and the process dies as before.

The handler runs with `SA_ONSTACK | SA_NODEFER`, so leaving it by
`longjmp` does not leave SIGSEGV blocked.

Alternatives considered:

- A stack-pointer check in every function prologue against a per-stack
  limit. It needs the limit updated at every stack switch: about 60
  `swapcontext` sites, many in IR emitted from Go.
- A depth counter. A `longjmp` skips the decrements, and suspended async
  fibers would all add to one thread's count.

## Stages

1. `notail` on every emitted call, and the handler for the main thread's
   stack (Linux, macOS).
2. Guard pages on the stacks that run program code off the main thread:
   async task fibers (`tasksrc/task.c`, 256 KB, today malloc'd with no
   guard), generators, worker threads. The handler recognises a fault in
   any registered guard page.
3. Windows: a vectored exception handler for `EXCEPTION_STACK_OVERFLOW`.

## Open questions

- A fault inside libc (for example inside `malloc`, holding its lock) is
  also left by `longjmp`. Node never runs out of stack inside its
  allocator; here a later allocation could deadlock.
