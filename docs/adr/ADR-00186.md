# ADR-00186: `&&` / `||` short-circuit instead of evaluating both operands

- **Date**: 2026-08-13

## Context

The logical operators `&&` and `||` evaluated **both** operands unconditionally, then combined them with a bare `and i1` / `or i1`. This violates one of JavaScript/TypeScript's most fundamental evaluation rules: the right operand of `a && b` must not run when `a` is falsy, and the right operand of `a || b` must not run when `a` is truthy. Real programs rely on this constantly — `obj != null && obj.method()`, `cache ?? expensive()` (via `??`, already correct), `flag || warnAndDefault()` — where evaluating the skipped side is not merely wasteful but wrong (a crash, a spurious side effect).

This was a deferred shortcut, not a design decision: the compound-assignment forms `&&=`/`||=`/`??=` ([ADR-00087]) and the ternary and `??` operators had always short-circuited correctly; only the plain binary `&&`/`||` fell through to the eager both-operands path in `emitBinary`. [ADR-00183] flagged "the non-short-circuiting `&&`/`||`" by name as the next such caveat to correct on sight rather than document as intent.

## Investigation

- `emitBinary` (`emit_exprs_operators.go`) eagerly emits `e.emitExpr(ex.Left)` and `e.emitExpr(ex.Right)` at the top, before dispatching on the operator. The `&&`/`||` cases then did `and i1`/`or i1` on the two already-evaluated results — so any side effect in the right operand had already happened.
- Repro (Linux): `sideL() && sideR()` with `sideL` returning `false` still printed `R`; `sideR() || sideL()` with `sideR` returning `true` still printed `L`.
- The codebase already had the right pattern for this: `emitConditional` (ternary) and `emitNullCoalesce` (`??`) use an `alloca`+store/load to merge a value produced on one of two control-flow paths, deliberately avoiding hand-tracked `phi` predecessor labels (an operand may itself span multiple blocks — a nested `&&`/`||`/ternary). `emit_call_console.go`'s own comment calls that "safer than hand-tracking phi predecessor labels."

## Decision

Intercept `&&`/`||` at the top of `emitBinary`, before the eager both-operands evaluation, and route them to a new `emitShortCircuit` that emits real short-circuit control flow:

1. `alloca i1` for the result; evaluate the left operand; store its bool as the default result.
2. Branch on the left's bool — `&&` evaluates the right operand only when left is true, `||` only when left is false; otherwise jump straight to the merge with the left value already stored.
3. On the right-operand path, store the right's bool and fall through to the merge.
4. Load the result at the merge.

The result type stays `i1` (bool). The value-preserving form of these operators (`x || "default"` yielding the *operand* rather than a boolean) would require a union result type this compiler doesn't have in expression position — out of scope here, and matches typed TS where `&&`/`||` over booleans yield a boolean. `inferExprType` already reports bool for these operators, so no type-inference change was needed.

## Implementation notes

- New `emitShortCircuit(ex)` next to `emitConditional` in `emit_exprs_operators.go`; the old `case "&&"`/`case "||"` blocks (a bare `and i1`/`or i1`) were removed as now-unreachable dead code rather than left behind.
- Both operators share one function — only the branch-target order differs (`&&` evaluates the RHS on left-true, `||` on left-false).

## Verification

- Linux (x86-64): `sideL() && sideR()` now prints only `L` then `false`; `sideR() || sideL()` prints only `R` then `true` — the skipped side's call never runs.
- New E2E tests `TestE2ELogicalShortCircuit` (side-effect skipping) and `TestE2ELogicalShortCircuitValues` (truth table incl. a nested `&&` inside `||`) in `tests/exprs_test.go`; `examples/basics/logical_operators.ts` added.
- Full `go test ./...` green (the existing suite — comparisons, guards, `instanceof`, boolean printing — is the regression net).
- `make conformance` re-run — see `docs/testing/CONFORMANCE-RESULTS.md`.
