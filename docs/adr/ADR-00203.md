# ADR-00203: String- and numeric-literal keys in object destructuring patterns

- **Relations**: `Implements TDD-00065` (Stage 3a); `Extends ADR-00192, ADR-00193`
- **Date**: 2026-08-17

## Context

Object destructuring accepted only a bare identifier in the pattern's key
position — `const { x, y } = obj`, optionally renamed (`{ x: y }`) or nested
(`{ x: { y } }`). The standard JS/TS forms `const { "k": v } = obj` and
`const { 0: v } = obj` were a flat parse rejection (`expected IDENT, got
STRING`/`NUMBER`), and `docs/status/LANGUAGE-CONSTRUCTS.md`'s object-destructuring
row disclosed exactly that gap ("top-level keys must be a plain identifier (no
string-literal keys)").

[TDD-00065](../tdd/TDD-00065.md) originally bundled this with `{ ...rest }` under
one "Stage 3 — object-pattern rest / non-identifier keys." Those are very
different costs — `{ ...rest }` needs a residual object type this compiler's
fixed-shape model doesn't have, while a non-identifier key needs no new
representation at all. The TDD's Stage 3 was therefore split into 3a (this
change), 3b (`{ ...rest }` over a statically-known shape), and 3c (`{ ...rest }`
over `any`/union/generic — deferred). This ADR delivers 3a.

## Investigation

- The object-*literal* grammar already accepts `STRING`/`NUMBER` keys
  (`parser/parser_literals.go:87`, [ADR-00066](ADR-00066.md)), storing the key as
  `keyTok.Literal` — the raw field-name text — exactly as it does for an
  identifier key (`parser_literals.go:120`). So the object model already carries
  string/numeric-named fields through `FieldIndex`; `{ "first-name": 1 }` is a
  field literally named `first-name`.
- The pattern side (`parser/parser_stmts.go:parseObjectPatternProps`) hard-required
  an `IDENT` key (`p.expect(lexer.IDENT)`), the sole reason the forms were
  rejected.
- Codegen (`codegen/llvm/emit_objects.go:unpackObjectPatternInto`) resolves each
  property purely by `objTy.FieldIndex(prop.Key)` — it never inspects how the key
  was spelled. So no codegen change is needed: as long as the parser stores the
  same `keyTok.Literal` field name the literal side stores, the existing field
  lookup, nested-pattern recursion, and array-field handling all apply unchanged.

This makes 3a a pure parser change, confirmed by five probes (string key with
alias, genuinely non-identifier field via literal inference, numeric key, string
key as a for-of loop variable, and a nested pattern reached through a string key)
— all produced correct output with only the parser edit.

## Decision

In `parseObjectPatternProps`, accept `IDENT`, `STRING`, or `NUMBER` as the key
token (mirroring the object-literal key grammar) instead of requiring `IDENT`.
The key's `Literal` is stored as `DestructProp.Key`, identical to the literal
side. Because a non-identifier key has no shorthand form (`{ "x" }` is
meaningless — there is no in-scope variable named `"x"`), a string/numeric key
must bind through an explicit `: local` (or a nested `: [..]`/`: {..}` pattern);
a string/numeric key with no `:` is a clean parse rejection. Identifier keys keep
their shorthand (`{ x }`) unchanged.

## Implementation notes

- `parser/parser_stmts.go`, `parseObjectPatternProps`: replaced the
  `p.expect(lexer.IDENT)` key read with a three-token check + `p.advance()`,
  tracking `nonIdentKey := keyTok.Type != lexer.IDENT`. Added an
  `else if nonIdentKey` branch after the `COLON` block that rejects a
  non-identifier key lacking a binding. The pre-existing `err` variable, formerly
  introduced by the `keyTok, err :=` read, is now a standalone `var err error`
  (still consumed by the nested-pattern and default sub-parses).
- No AST change (`DestructProp.Key` already holds an arbitrary field-name string),
  no codegen change.

## Side effects discovered

- Object *type annotations* still reject a string-literal-named field
  (`type T = { "first-name": string }` → `expected IDENT, got STRING` in the type
  parser), so a non-identifier field is reachable only via object-literal type
  inference, not an explicit annotation. That is a separate parser gap in the type
  grammar, out of scope here; noted in the status caveat.
- 3b/3c (`{ ...rest }`) remain unimplemented by design — see TDD-00065's split.
