# ADR-00532: Exponent notation in number literals (`1e3`, `1.5e-2`)

- **Relations**: Extends ADR-00123
- **Date**: 2026-08-31

## Context

Scientific/exponent notation in number literals was entirely unsupported:
`1e3`, `1.5e3`, `1E3`, `2e-2`, `6.022e23` all failed to compile — the lexer's
number scanner stopped at the `e`, leaving a trailing identifier (`1e3` lexed as
`1` then `e3`), producing a parse error. This is a common, fundamental part of
the ES `DecimalLiteral` grammar and was not documented as a limitation.

## Investigation

`lexer.go`'s `readNumber` consumed a mantissa (digits, one `.`, numeric
separators) and stopped — it had no exponent clause. The codegen side
(`emitNumberLit`) already handled an exponent *string*: a non-dotted exponent
like `"1e3"` falls through `ParseInt` to `ParseFloat`, and a value is emitted as
an exact double bit-pattern. The only gap was the lexer never producing the
token. A dotted-exponent literal (`"1.5e3"`) did hit `emitNumberLit`'s
fraction branch, which returned the string *verbatim* as an LLVM `double`
constant — and LLVM reads `e`-notation ambiguously in a double slot (the exact
concern `llvmDoubleLit` documents), so that path needed hardening too.

## Decision

1. `lexer.go`: after the mantissa, scan an optional exponent — `e`/`E`, an
   optional `+`/`-`, then one or more digits (numeric separators allowed between
   digits). An `e`/`E` only starts an exponent when a digit (optionally after a
   sign) follows, so an identifier boundary like `1 + e` is unaffected. A
   `BigInt` suffix `n` after an exponent is a `SyntaxError` (`1e3n`).
2. `emit_call_number.go`'s `emitNumberLit`: check the hex/bin/oct prefix first
   (a hex literal's digits can be `e`/`E`, e.g. `0x1e`), then route any
   remaining `e`/`E`-containing decimal literal through `ParseFloat` +
   `llvmDoubleLit` (exact bit-pattern) rather than passing `e`-notation verbatim
   to LLVM. A plain fraction with no exponent still passes through verbatim.

## Implementation notes

`lexer/lexer.go` (`readNumber` exponent clause + `hasExp` BigInt guard),
`codegen/llvm/emit_exprs.go` (`emitNumberLit` reorder + exponent normalization).
Every number literal is a `double` (ADR-00123 Stage 1), so `1e3` is `1000` as a
Number, matching JS.

## Side effects discovered

`1e+` (sign, no digit) correctly stays a `SyntaxError` — the `e` isn't consumed
as an exponent, so it parses as `1` then a dangling `e +`. A separate, unrelated
`1e21`-class program that previously failed now compiles.

## Verification

`TestExponentNumbers` (lexer unit): tokenization of `1e3`/`1.5e3`/`1E3`/`2e-2`/
`6.022e+23`/`1_000e1` and the `1 + e` identifier boundary. `TestE2EExponent
NumberLiterals` (E2E): values, arithmetic, and an annotated `const x: number =
5e2`, cross-checked against real Node. `1e3n` rejected. Verified on Mac (Apple
Silicon).
