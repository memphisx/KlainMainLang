# ADR-00491: Array.from mapFn argument

- **Date**: 2026-08-29

## Context

`Array.from(iterable, mapFn)` was rejected — only the 1-argument form
existed, a documented caveat on the Array.from row.

## Decision

Desugar at emit: `Array.from(x, fn)` becomes `Array.from(x).map(fn)`.
Semantically exact here — the observable JS differences (mapFn seeing
holes or a live length) can't arise for dense, materialized arrays. The
type-inference side routes through the same synthetic `.map()` call, so
the closure's parameters are typed contextually against the source
element type; inferring the bare closure standalone instead binds its
`number` params to the default width and mistags the result array (hit
and fixed during this change). `thisArg` stays unsupported.

## Verification

Mac. `tests/arrays_test.go` `TestE2EArrayFromMapFn` (index param +
string source) passes; Array.from batch green;
`examples/arrays/array_methods.ts` extended and re-run.
