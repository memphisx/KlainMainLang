# ADR-01843: A function expression's `this` parameter, on both sides

- **Relations**: `Implements TDD-00230` (P3.3: the checker answers what inferExprType did)
- **Date**: 2026-10-20

## Context

- A function expression that takes a `this` gets it as its first parameter, prepended by `maybeAddThisParamExpr`. The parameter is either declared (`function (this: T, …)`) or implicit (`any`, for a method shorthand reading its own `this`).
- The checker keeps `this` apart from the parameters. Two problems followed:
  - The oracle's function type lacked the leading parameter, and so did an object literal's method field built from it (`{ method() { thisValue = this; } }`, `new Source({ read(n) { … this.items … } })`).
  - `checkerContextualParam(fn, i)` indexed the checker's parameters with the position in the rewritten list. A method shorthand reading `this` therefore looked up its first parameter's context one slot too far, and the parameter fell back to `any`. In `read(n)`, `n` became a box instead of the `number` its context gives.

## Decision

- `funcExprThisType` answers the `this` parameter that `maybeAddThisParamExpr` would add, without rewriting anything. It is exposed to the oracle as the `funcThis` hook.
- The oracle prepends that parameter to a function expression's type and sets `FuncThis`. An object literal's field whose value is a function expression takes the function's own answer (`literalStorage`).
- `checkerContextualParam` skips a leading `this` parameter when it indexes the checker's parameters.
- Three more function-literal facts are mirrored:
  - A parameter default the caller evaluates sets the default mask. The oracle applies `setFuncParamDefaults` to its answers, as emission does (18 rows, `function([x] = iter) {}`).
  - An unannotated function returning a literal with an accessor returns that literal's synthetic class (50 rows, the async-iterator `next() { return { get done() {…} } }` family).
  - Under `-compat=js`, an unannotated parameter is bound from its default, else its call sites, else as a box. Emission never takes the checker's contextual type in that lane, so the oracle no longer does either. `literalParamType` (the `literalParam` hook) is that chain, shared by arrows and function expressions.

## Consequences

- `read(n)`'s `n` is a `number`, as tsc types it. `examples/function_expressions/call_apply.ts` prints what Node prints.
- The function-expression and object-literal rows for these shapes are gone (`name-invoke-fn-strict.js`, the stream examples' `_read`/`_write` methods, `call_apply.ts`).
- A name bound to such a literal (`var ref = async (a = 1) => {}`) gets the literal's answer, both as an identifier and as a module global (`GlobalType`). Its JS-lane parameters are then bound from their call sites, as emission binds them (`ref(false)` makes `a` a boolean), not from the default the checker types.
- What is left for these kinds is the unannotated return type. Emission infers it over the body with the parameters as bound; the oracle uses the checker's result. That is the `inferUnannotatedReturnType` decider's work.
- Verified on Apple Silicon (targeted this/method/contextual/callback/object-literal/bind/call, JS-file, default, accessor and arrow tests).
