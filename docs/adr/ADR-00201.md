# ADR-00201: Tuple types `[T0, T1, ...]`

- **Relations**: `Implements TDD-00066`
- **Date**: 2026-08-17

## Context

This compiler had no tuple type. The gap forced a documented stand-in in several places: `Map.entries()`/`Array.entries()`/`Object.entries()` returned an array of *named-field* objects (`{key, value}`/`{index, value}`) rather than a real `[K, V]` tuple, iterated as `for (const e of m.entries()) { e.key; e.value }` ([ADR-00053](ADR-00053.md)/[ADR-00057](ADR-00057.md)); `new Map(entries)` was rejected for want of a `[K, V]` type; and the standard idiom `for (const [k, v] of Object.entries(obj))` was a clean rejection (`cannot array-destructure a for-of element of non-array type`). Surfaced while resolving the `for...of`-over-entries limitation; `docs/status/README.md`'s own type-representation table already earmarked the intended shape ("Tuple types `[number, string]` → Fixed-size struct"). Scoped in [TDD-00066](../tdd/TDD-00066.md).

## Investigation

A tuple is a fixed-arity, heterogeneous, positional aggregate — structurally an object with positional slots. The `.entries()` builders already produced 2-field structs carrying the right element types (`emit_collections.go`, `emit_arrays_iter.go`); only `Object.entries` stringified. So the blocker was never the storage — it was purely that those structs had *named* fields (`key`/`value`/`index`), which array-pattern destructuring and index access don't accept. This pointed straight at the flagged-`ObjectType` pattern already used pervasively (classes, errors, `Symbol`, URL, entries objects): represent a tuple as an `ObjectType` with synthetic positional field names `"0"`, `"1"`, ... and reuse every struct-machinery consumer.

## Decision

`TupleType([]Type)` builds an `ObjectType` with fields named `"0"`, `"1"`, ..., flagged `IsTuple` (types.go). That reuses `StructIR`/`StructSize`/`FieldIndex`/GEP/field storage, object-literal-style construction, object parameter/return/field passing, spread, and `structuredClone` unchanged; `IsTuple` only distinguishes the four tuple-specific behaviors:

- **Construction** — an array literal built against a tuple hint (`emitTupleLiteral`, storing element *i* into field *i* via the same expression-aware, nullable-boxing field store object literals use). Wired into `emitExprWithObjectHint` and `emitObjectVarDecl`.
- **Constant-index read** — `t[0]` maps to field `"0"` (`emitTupleIndex`); a non-constant index is a clean rejection (its element type isn't statically knowable). `inferExprType` types a constant tuple index likewise, so `n[1][0]` and array-of-tuples indexing (`pairs[1][0]`) resolve.
- **Positional destructuring** — `unpackTuplePatternInto` binds pattern position *i* to field *i* (declaration `const [a, b] = t`, and `for (const [a, b] of tuples)`), with a static arity check (no runtime bounds check), array-typed elements bound as the two-alloca array symbol, nullable-scalar elements as boxed locals, and nested sub-patterns recursing.
- **Rendering** — a tuple serializes to a JSON array (`emitJSONStringifyTuple` → `[e0, e1]`) and stringifies/prints as comma-joined elements (`emitTupleToString` → `String([a,b])` / `${tuple}` / `console.log`), both matching real JS, rather than as an object.

**`.entries()` now returns real tuples**: `Map.entries()` → `[K, V][]`, `Array.entries()` → `[number, T][]`, `Object.entries()` → `[string, string][]` (values still stringified — a heterogeneous object's value type is a union this compiler can't yet form; the tuple *shape* is what unblocks the idiom). Both the construction sites and the four `inferExprType` entry-shape sites switched from the `{key,value}`/`{index,value}` object to `TupleType`. The non-standard `.key`/`.value`/`.index` access is replaced — the docs already framed it as a stand-in awaiting exactly this — and the in-repo usages migrated to destructuring / index access in this change.

## Implementation notes

- New file `emit_tuple.go` holds the tuple-specific emitters (`emitTupleLiteral`, `emitTupleIndex`, `unpackTuplePatternInto`, `emitTupleToString`, `tupleConstIndex`); the tuple JSON serializer lives beside the object one in `emit_call_json.go`.
- Parsing: a `[` at the start of a type position is unambiguously a tuple (an array type `T[]` carries its brackets as a suffix), parsed into a new `ast.TypeAnnotation.TupleElems`; `resolveType` builds the `TupleType`.
- Because a tuple is `IsObject`, every new tuple dispatch (JSON, value-to-string, `emitIndex`, the console loop) is checked *before* the generic object branch it would otherwise fall into.

## Side effects discovered

- The `.key`/`.value`/`.index` entries convention is a breaking change to a shipped (non-standard) API; six in-repo tests and four examples were migrated in the same change, and the docs updated. External code using `.key`/`.value` on entries would need the same one-line migration to destructuring.
- `new Map(entries)` is now unblocked in principle (a `[K, V]` type exists) but remains unimplemented — a clean, separately-shippable follow-on noted in `docs/status/`.
- V1 deliberately excludes tuple element *assignment* (`t[0] = x`), rest/optional/named elements, non-constant indexing, and array methods/`.length` on a tuple — each a clean rejection or unchanged behavior (see TDD-00066).
