# Networking

> Part of the [Implementation Status](README.md) index. All require linking a network library (libcurl for fetch/HTTP; system sockets for WebSocket). A server-side HTTP listener (`http.listen(port, handler)`) is tracked under [HTTP-SERVER.md](HTTP-SERVER.md) instead — listening for incoming connections has no browser-side Web API equivalent.

**Coverage**: 6/6 (100%) · **Strict Coverage**: 1/6 (~17%).

This page follows the shared status-page format ([Status page format](README.md#status-page-format)): **Status** is a bare ✅/❌; **Caveats** lists behavioral divergences from real JS/TS (a non-empty Caveats cell is what excludes an otherwise-✅ row from Strict Coverage); **Notes** carries implementation/representation detail only. One table per index category; each category's figures above derive from its table below.

| Feature | Status | Caveats | Notes |
|---|---|---|---|
| `fetch(url)` / `fetch(url, init)` / `fetch(request)` | ✅ | • Setting a `body` without an explicit `method` sends it as `POST` (libcurl's `CURLOPT_POSTFIELDS` implies `POST` unless overridden); an explicit `method` always wins over that default | • `init` is any value with some subset of `method: string` / `headers: Map<string,string> \| Headers` / `body: string` fields; a real `Request` object works as the sole argument too, destructured the same way<br>• Real non-blocking I/O since [ADR-00050](../adr/ADR-00050.md): uses libcurl's multi-interface, driven by the same `select()`-based event loop `http.listen` uses, so `await fetch(...)` yields instead of blocking when called from inside a connection-handler fiber — one slow upstream call no longer freezes every other connection or timer<br>• Outside any fiber (plain top-level code, no `http.listen`), there's nothing else to overlap with, so it busy-spins the same multi-interface calls to the same effect as a blocking wait<br>• A network-level failure (DNS, connection refused, TLS, timeout) throws; a non-2xx HTTP status still resolves normally (`.ok` distinguishes it), matching real `fetch`<br>• See [ADR-00021](../adr/ADR-00021.md) (original V1), [ADR-00050](../adr/ADR-00050.md) (non-blocking rework), [ADR-00052](../adr/ADR-00052.md) (fixed a real stack-overflow crash in the busy-spin path, confirmed via a slow-endpoint repro), [ADR-00074](../adr/ADR-00074.md) (custom method/headers/body), and [ADR-00130](../adr/ADR-00130.md) (`fetch(request)`) |
| `Response` (`.status`, `.ok`, `.body`, `.text()`, `.json()`, `.arrayBuffer()`) | ✅ | • **These three methods are actually synchronous** (`const body: string = r.text()`, no `await`) despite real WHATWG `fetch` returning `Promise<string>`/`Promise<any>`/`Promise<ArrayBuffer>` from them — nothing documents this or rejects the mistake cleanly: `await res.text()`/`.json()`/`.arrayBuffer()`, the single most instinctive way a TS developer would call them, hard compile-crashes with invalid LLVM IR (`store ptr , ptr %tN` — an empty operand), and along the way frees the string's own backing buffer, a use-after-free. Root cause: `emitAwait`'s only non-Promise guard is `IR != "ptr"`, which a plain string result also satisfies, so it falls into the Promise-yielding path for a value that was never a Promise. Found by the 2026-08-11 audit ([ADR-00166](../adr/ADR-00166.md))<br>• `.json()` reuses `JSON.parse`'s machinery, including its full scope: it validates the body (a non-JSON body — e.g. an HTML error page — throws a catchable `SyntaxError`, [ADR-00223](../adr/ADR-00223.md)) and projects nested objects, array/object-array fields, and top-level `T[]` off the parse tree ([ADR-00224](../adr/ADR-00224.md)); only `any`/`unknown` dynamic shapes remain unsupported<br>• `.text()`/`.json()` are plain null-terminated strings: a binary body with an embedded null byte truncates at the first one, by design — use `.arrayBuffer()` for a binary body<br>• No response-header access yet (no `HEADERFUNCTION` capture exists in this codebase) — see the `XMLHttpRequest` row for the same gap on that side | • Plain object with `status`/`ok`/`body` fields (readable directly, not hidden) plus `text()`/`json()`/`arrayBuffer()` methods<br>• `.arrayBuffer()` ([ADR-00094](../adr/ADR-00094.md)) carries the real byte count and comes back whole regardless of content<br>• Every string in this compiler is a plain null-terminated C string (`.length` is `strlen`-based), so any string value with an embedded `\0` reads as shorter than it actually is; `.text()`/`.json()` keep that behavior by design (JSON/text bodies aren't expected to legitimately contain embedded nulls). Originally confirmed via `httpbin.org/bytes/50000` coming back as a 383-byte string through `.text()`; fixed for the binary case by [ADR-00094](../adr/ADR-00094.md) now that `ArrayBuffer`/`TypedArrays` exist (see [BINARY-DATA-TYPED-ARRAYS.md](BINARY-DATA-TYPED-ARRAYS.md))<br>• See [ADR-00021](../adr/ADR-00021.md) (original V1), [ADR-00094](../adr/ADR-00094.md) (`.arrayBuffer()`), [ADR-00166](../adr/ADR-00166.md) |
| `Request` / `Headers` objects | ✅ | | • Real classes, not just `fetch`'s plain-object `init` (which still works unchanged)<br>• `Headers` is a case-insensitive (lowercased-key) wrapper: `get`/`set`/`has`/`delete` behave like `Map<string,string>`'s own (because storage-wise it *is* one), plus `append(name, value)`, which combines with a comma if `name` is already present instead of overwriting<br>• `new Request(url)` / `new Request(url, init)` builds a plain object (`url`/`method`/`headers`/`body`, all readable directly) — `method` defaults to `"GET"`, `headers` to an empty `Headers`, `body` to `null`<br>• Reverses [ADR-00074](../adr/ADR-00074.md)'s original decision to reject these — see [ADR-00130](../adr/ADR-00130.md)<br>• `http.listen`'s own server-side request-object type annotation is `HttpRequest`, not `Request` — freed up by this change (see the ADR for why) |
| `WebSocket` | ✅ | • Client `new WebSocket(url)` is `ws://` only — `wss://` throws immediately (no TLS)<br>• Neither side supports binary `.send()` (`ArrayBuffer` payloads)<br>• `.close()` on either side doesn't wait for the peer's own echo back before actually closing (a deliberate simplification)<br>• The client's connect + handshake runs *synchronously*, before the constructor returns, so `.onopen`/`.onerror` are deliberately deferred to the first event-loop pass after construction (giving assignment code a chance to run first) rather than fired inline | • Both server and client<br>• Server: `http.listen(port, handler, { ws })`'s optional third-argument handler is called once per successfully upgraded connection with a `WSConnection` (`.onmessage`/`.send(data: string)`/`.close()`), coexisting with ordinary HTTP requests on the same listener; a client `ping` gets an automatic `pong` reply with identical payload (RFC 6455 §5.5.2), and both a peer `close` frame and `.close()` itself send a proper Close frame before the connection ends (RFC 6455 §5.5.1)<br>• A failed connect never throws (`.onerror`/`.onclose` fire instead, matching real `WebSocket`)<br>• See [TDD-00039](../tdd/TDD-00039.md) ([ADR-00125](../adr/ADR-00125.md) Stage 0 frame codec/SHA-1, [ADR-00126](../adr/ADR-00126.md) Stage 1 server handshake, [ADR-00127](../adr/ADR-00127.md) Stage 2 ping/pong + close handshake, [ADR-00128](../adr/ADR-00128.md) Stage 3 client) |
| `EventSource` | ✅ | • The `Content-Type` check on connect is a case-sensitive `"text/event-stream"` prefix match<br>• A `retry:`-driven reconnect replays the *full* stored `Last-Event-ID`, not a per-listener value | • Server-sent events (SSE) over HTTP — connection plumbing (`readyState`/`close()`), `onmessage`/`onopen`/`onerror`, `addEventListener`/`removeEventListener` for named (`event: name`) records (`data`/`event`/`id`/`retry` field parsing, multi-line `data:` concatenation), `\n\n`/`\r\n\r\n`/bare-`\r\r` record boundaries, and auto-reconnect (retries after a dropped connection or network-level connect failure, honoring a server-sent `retry:` delay — default 3000ms — and replaying `Last-Event-ID` as a request header) all work<br>• A response that *arrives* with the wrong shape (non-2xx status, or a 2xx with a `Content-Type` that isn't `text/event-stream`) fails permanently instead of retrying, matching the real spec's distinction between a network failure (retryable) and a malformed response (terminal)<br>• See [TDD-00038](../tdd/TDD-00038.md) |
| `XMLHttpRequest` | ✅ | • Modeled as the real spec's legacy *synchronous* mode: `.send()`/`.send(body)` runs the request to completion before returning, then fires every registered callback once, synchronously — there's no default-async, callback-interleaved mode (this compiler has no re-entrant-into-already-returned-caller callback machinery to support one)<br>• `.setRequestHeader(name, value)` accumulates headers, but names are **not** lowercased here (unlike `Headers`' own methods) — a separate V1 narrowing<br>• `.readyState` is 0/1/4 only (UNSENT/OPENED/DONE); the real spec's HEADERS_RECEIVED/LOADING have no meaning for a transfer that always runs to completion in one call<br>• `.responseText`/`.response` are identical values — only a text `responseType` is supported; no `responseType` other than the default<br>• `.onreadystatechange`/`.onload`/`.onerror` callbacks are zero-argument (deliberately — a payload-carrying callback isn't representable for this particular type, see [ADR-00131](../adr/ADR-00131.md))<br>• `.abort()` is a best-effort `readyState` reset — there's nothing to actually interrupt once a synchronous `.send()` has returned<br>• No `.getResponseHeader()`/`.getAllResponseHeaders()` (same missing-response-header-capture gap `Response` has) | • Not a blocking implementation: `.send()` is built on the exact same non-blocking `__kml_fetch_async` primitive `fetch()` itself uses, so it still yields the current fiber (rather than blocking every other connection) when called from inside an `http.listen` connection handler<br>• Supports `.open(method, url)`, `.setRequestHeader(name, value)`, `.send()`/`.send(body)`, `.abort()`, `.readyState`, `.status`, `.responseText`/`.response`, and the zero-argument callbacks<br>• A network-level failure fires `.onerror` (never throws), matching real `XMLHttpRequest`<br>• See [ADR-00131](../adr/ADR-00131.md) |
