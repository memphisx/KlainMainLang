# TDD-00158: Node-faithful HTTP `'upgrade'` event, `wss://` server, and re-homing the WebSocket-server convenience under `klain:`

- **Status**: Implemented
- **Date**: 2026-09-02

## Context

The last open gap in [`NETWORKING.md`](../status/NETWORKING.md)'s WebSocket
row is the **server side of `wss://`**: the client already speaks `wss://`
(TDD-00039 Stage 4 client, an fd→`SSL*` registry routing frame I/O through
`SSL_read`/`SSL_write`), but the server is `ws://` only. TDD-00039
deliberately deferred a server TLS story, reasoning "same as `https://`
doesn't exist for `http.listen` either." That premise no longer holds:
`https.createServer` / `http2.createSecureServer` shipped (TDD-00111 /
TDD-00139) with a full server-side TLS accept path, an fd→`SSL*` table, and
TLS-aware connection I/O shims (`__kml_http_conn_recv` / `_send` / `_close`,
runtime_http.go:2318–2360). So the raw TLS plumbing a `wss://` server needs
already exists — the WebSocket server just doesn't use it.

But this work is scoped under a stronger directive than "make `wss` work":
**everything under a Node namespace (`http`/`https`/`net`) must match real
Node.js; only bespoke conveniences live under `klain:`.** Measured against
that rule, the *existing* WebSocket-server surface is itself already a
divergence: real Node has no built-in WebSocket server at all. What Node
core actually provides is the HTTP server's **`'upgrade'` event** —
`server.on('upgrade', (req, socket, head) => …)` — over which the `ws` npm
package builds its `WebSocketServer`. This compiler instead exposes a
bespoke `http.listen(port, handler, { ws })` option handing the user a
`WSConnection` with `.onmessage`/`.send()`/`.close()` (TDD-00039). That
convenience is fine — but it does not belong under the `http` namespace.

This document therefore scopes three things as one arc:
1. The Node-faithful `'upgrade'` event on `http`/`https` servers.
2. `wss://` server support, which falls out for free once the upgrade
   socket's I/O routes through the existing TLS-aware conn shims.
3. Re-homing the `WSConnection` frame-codec convenience under `klain:`,
   rebuilt as a *consumer* of the faithful `'upgrade'` event rather than a
   bespoke branch wired into the HTTP dispatcher.

## Design

### The seam

`buildHTTPDispatcher` (emit_http.go:1269) is a per-connection fiber. At
emit_http.go:1624–1643, right after the request headers are parsed, the
following are live and dominate the rest of the fiber:

- `headersMapFinal` — parsed, lowercase-keyed `str→str` header map.
- `fd32` / `fd64` / `fdPtr` — the connection fd in all three forms.
- `methodPtr`, `pathOnly` (1602), `queryMapFinal` (1621) — request line.
- `bufFinal` / `headerEndFinal` / `totalReadA` — the raw read buffer and the
  offset where headers ended, i.e. the **`head`** bytes (anything already
  read past the header terminator).
- Compile-time `e.usedHTTPS1Server` — whether this fd may be TLS, hence
  whether writes must go through the SSL shims.

Today this seam holds only the bespoke `hasWSHandler` branch
(`emitWSUpgradeDetect` → `emitWSHandshakeAndLoop`, emit_websocket.go:38/132).
The design generalizes it into a Node `'upgrade'` dispatch, and rebuilds the
convenience on top.

### Stage 1 — the faithful `'upgrade'` event

**Registration.** Add `"upgrade"` to the server object's `.on` event set
(emit_http.go:683–736; extend the recognized-name list and the rejection
string at line 719). Store the handler closure in a fresh server-handle slot
alongside the existing `listening` slot, and mirror it into a
module-global `@__kml_listen_upgrade_handler` the dispatcher reads (exactly
how `@__kml_listen_ws_handler` works today). An `'upgrade'` handler attaches
identically to `http.createServer(...)`, `https.createServer(...)`, and the
`http.listen` convenience server — because all three share the one `.on`
dispatcher and the one `buildHTTPDispatcher`.

**Detection.** At the seam, when an upgrade handler is registered, reuse the
existing `Upgrade:`/`Connection:` header check (generalized from
`emitWSUpgradeDetect`, which is WebSocket-specific only in that it is
currently *only* reached for `hasWSHandler`; the header predicate itself is
generic). Node fires `'upgrade'` for **any** `Upgrade:` request, not only
`websocket` — so the faithful event does not hard-code the `websocket`
token; it hands the raw request to the user, who inspects
`req.headers['upgrade']` themselves. (RFC 7230 §6.7.)

**The three arguments.**

- **`req`** — an `IncomingMessage`-shaped object built from
  `headersMapFinal` + `methodPtr` + `pathOnly`. The existing
  `ServerRequest`/`IncomingMessage` type used by the normal handler is the
  model; the upgrade `req` is the same shape, minus a body (an upgraded
  connection has no request body).

- **`socket`** — a **`net.Socket`** (`NetSocketType()`, types.go:1496;
  `netSocketIR`, runtime_net.go:41) wrapping `fd64`, with its `SSL*` slot
  (field 5) set to this connection's `SSL*` when `usedHTTPS1Server` (fetched
  via `__kml_http_conn_ssl_get(fd)`), else null. This is the crux of
  faithfulness and of `wss://`: `net.Socket` already wires `.write(bytes)`,
  `.end(data?)`, `.destroy()`, `.on('data', cb)`, `.on('end'|'close', cb)`
  (emit_net.go:428–522), and its struct already carries the `SSL*` slot for a
  TLS-backed socket. Two pieces of glue are new:
    1. **Construction from an accepted HTTP fd.** No existing constructor
       wraps a mid-HTTP-fiber fd into a `netSocketIR`. Add one that `calloc`s
       the struct, stores `fd64` (field 0), the `SSL*` (field 5), state=open.
    2. **Driving `'data'`/`'end'` from the HTTP fiber.** The `net` module's
       own `'data'` delivery runs on the separate `__kml_net_dispatch`
       select loop (runtime_net.go:471+), which does **not** own this fd — the
       HTTP fiber does. So after the user's `'upgrade'` handler returns
       (having attached `socket.on('data', …)` and written its handshake
       response), the fiber enters a **generic raw read loop**: the same
       `swapcontext`-yield-on-`EAGAIN` structure the WS server loop already
       uses (emit_websocket.go:213), but instead of frame-decoding it reads
       raw bytes via `__kml_http_conn_recv` (TLS-aware) and fires the
       socket's field-2 `'data'` listener with each chunk as a `Buffer`. On
       EOF/`0` it fires `'end'`/`'close'` (fields 3/6) and closes via
       `__kml_http_conn_close`. `socket.write(...)` and `.end(...)` route
       through `__kml_http_conn_send` when the socket's `SSL*` is set — see
       "Making `net.Socket` I/O TLS-aware" below.

- **`head`** — a `Buffer` of the bytes between `headerEndFinal` and
  `totalReadA` in `bufFinal` (usually empty for a clean WebSocket upgrade;
  non-empty if the peer pipelined the first frame). Faithful Node passes
  exactly these leftover bytes.

**Making `net.Socket` I/O TLS-aware.** Today `__kml_net_sock_write` /
`_close` (runtime_net.go) branch on the socket's field-5 `SSL*`: a plaintext
socket uses raw `write`/`close`, a TLS one (a `tls.connect` client socket,
TDD-00109) uses the libssl path. Confirm this branch exists and reuse it —
a `wss` upgrade socket sets field 5 to the server-accepted `SSL*`, so
`.write()` already routes correctly with no new code. If any net-socket I/O
site still assumes a client-side `SSL*` shape incompatible with the
server-accepted one, unify them onto the `__kml_http_conn_*` shims (which key
off the shared fd→`SSL*` table and already handle both). This is the single
most important correctness check of the stage: **`wss://` is
"`net.Socket.write` goes through SSL when field 5 is set," nothing more.**

**Result of Stage 1.** A fully faithful, hand-rollable upgrade — the exact
Node-core idiom, no npm package:

```ts
import http from 'http'
import crypto from 'crypto'   // createHash('sha1') for the accept key

const server = http.createServer(handler)
server.on('upgrade', (req, socket, head) => {
  const key = req.headers['sec-websocket-key']
  const accept = crypto.createHash('sha1')
    .update(key + '258EAFA5-E914-47DA-95CA-C5AB0DC85B11')
    .digest('base64')
  socket.write(
    'HTTP/1.1 101 Switching Protocols\r\n' +
    'Upgrade: websocket\r\nConnection: Upgrade\r\n' +
    'Sec-WebSocket-Accept: ' + accept + '\r\n\r\n')
  socket.on('data', (chunk) => { /* raw RFC 6455 frames */ })
})
server.listen(8080)
```

and `wss://` is the identical code with `https.createServer({ cert, key })`
— the socket's I/O is SSL-routed automatically. (This assumes
`crypto.createHash('sha1')` is exposed to userland; see Open Questions —
if not, the faithful raw path still works for anyone who brings their own
accept computation, and the `klain:` layer below never needs it since it
computes the accept internally with the existing `__kml_ws_sha1` helper.)

### Stage 2 — re-home the `WSConnection` convenience under `klain:`

The existing frame codec (`__kml_ws_frame_encode`/`_decode`, runtime
SHA-1/base64), the `WSConnection` object (`.onmessage`/`.send()`/`.close()`),
auto ping/pong, and the close handshake are all worth keeping — they are the
ergonomic layer the `ws` package occupies in Node. But they are a bespoke
convenience and must move out of the `http` namespace.

**New home.** A `klain:ws` module exposing a `WebSocketServer` that attaches
to a Node `http`/`https` server and hands back a `WSConnection` per upgraded
connection — mirroring the *shape* of the `ws` package but under `klain:`,
so its non-Node origin is explicit:

```ts
import http from 'http'
import { WebSocketServer } from 'klain:ws'

const server = http.createServer(handler)
const wss = new WebSocketServer({ server })
wss.on('connection', (socket /* : WSConnection */) => {
  socket.onmessage = (ev) => socket.send('echo: ' + ev.data)
})
server.listen(8080)
```

`wss://` = the same with `https.createServer({ cert, key })`.

**Implementation.** `WebSocketServer({ server })` registers an `'upgrade'`
handler (Stage 1) on the given server. Inside it, the existing handshake +
frame-loop logic (`emitComputeWSAccept`, the persistent decode loop) runs —
but now reading/writing through the `socket` argument's TLS-aware I/O rather
than raw `read`/`write`. Concretely, `emitWSHandshakeAndLoop` /
`emitWSServerLoop` (emit_websocket.go) are refactored to take their fd and a
"TLS or not" decision from the upgrade seam (they already receive `fd32`,
`fd64`, `fdPtr`) and to emit `__kml_http_conn_send`/`_recv`/`_close` in place
of raw `write`/`read`/`close` **when `usedHTTPS1Server`** — the identical
gating the HTTP read path already uses at emit_http.go:1433. Under a plain
server the shims fall through to raw I/O (the conn's `SSL*` is null), so a
`ws://` server is byte-identical to today.

**Removal of `http.listen(..., { ws })`.** The bespoke option is the one
piece that violates the namespace rule, so it is **removed** (not kept as an
alias): the `ws` field on the `http.listen` options object stops being
recognized, its parsing (`hasWSHandler` at emit_http.go:145,172–184) and the
dispatcher branch it drove are deleted, and the one in-repo caller
(`examples/websocket/websocket_server.ts`) is rewritten onto
`klain:ws`'s `WebSocketServer`. The directive is explicit that Node
namespaces match Node; keeping a non-Node `ws` option under `http` — even as
a documented alias — would leave exactly the wart this arc exists to remove.
The convenience is preserved in full under `klain:ws`, its honest name.
A program still passing `{ ws }` to `http.listen` gets a clean "unknown
option" rejection pointing at `klain:ws`, not silent breakage.

### Why not drive the socket off the `net` select loop

`__kml_net_dispatch` (runtime_net.go:471+) is the natural owner of
`net.Socket` `'data'` events, and reusing it would avoid a second read loop.
Rejected: the connection fd is already owned by the HTTP fiber
(`@__kml_http_dispatch`), mid-fiber, with its buffer/offset state on the
fiber stack. Handing it to the select loop would mean unregistering it from
the fiber, migrating the leftover `head` bytes, and re-entering a different
scheduler — strictly more moving parts than letting the fiber that already
owns the fd run the generic raw read loop (which is a trivial variant of the
WS loop it already runs). The socket object still *presents* the full
`net.Socket` API; only its event pump differs, invisibly.

## Open questions

- **`crypto.createHash('sha1')` in userland.** ~~Not exposed.~~ **Closed by
  TDD-00159/ADR-00636** — `crypto.createHash` now exists (md5/sha1/sha256/
  sha384/sha512, `.update`/`.digest`), so a fully hand-rolled faithful upgrade
  (`server.on('upgrade', …)` + `createHash('sha1').…digest('base64')`, no
  `klain:ws`) computes `Sec-WebSocket-Accept` in pure Node code — verified by
  `TestE2EHandRolledUpgradeAcceptKey`. The faithful path is complete.
- **`socket` as a true Duplex / Node stream.** Node's upgrade `socket` is a
  `net.Socket` (a Duplex). This design gives it the `net.Socket` *method*
  surface driven from the HTTP fiber. Whether it should also satisfy the full
  `stream.Duplex` interface (`.pipe()`, backpressure, `'drain'`) is deferred
  — the faithful method surface (`write`/`end`/`destroy`/`'data'`/`'end'`) is
  what upgrade handlers and the `ws` package actually use.
- **Fragmentation / subprotocols / `permessage-deflate`.** Unchanged scope
  from TDD-00039's Open Questions — this document does not add them; it moves
  the existing single-frame codec under `klain:ws` and adds TLS.
- **Non-WebSocket upgrades** (e.g. HTTP/1.1 `Upgrade: h2c`, or a custom
  protocol). The faithful `'upgrade'` event fires for any `Upgrade:` request;
  what the user does with the raw socket is their business. No token
  filtering — matching Node.
- **Platform verification.** Done: verified on macOS (arm64, Homebrew
  OpenSSL) and Linux (Debian/glibc/arm64, Docker `golang:latest` + clang 19 +
  OpenSSL `libssl-dev`) — the fd-handoff glue and the server-accepted `SSL*`
  reuse through `net.Socket.write` (raw upgrade over wss and klain:ws over
  wss) pass on both.
