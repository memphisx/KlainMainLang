# ADR-00258: `.then`/`.catch`/`.finally` directly on a raw fetch `Promise<Response>`

- **Relations**: extends [ADR-00248](ADR-00248.md) (task-promise `.then`/`.catch`/`.finally` value-chaining); builds on the fetch-await path ([ADR-00095](ADR-00095.md)) and `buildResponseFromStatusBody`; superseded by [ADR-00280](ADR-00280.md) (the synchronous drive only — the reaction machinery stands)
- **Date**: 2026-08-20

## Context

`.then`/`.catch`/`.finally` were supported only on a task-shaped promise (from an
async function). A raw `fetch(url)` returns a `Promise<Response>` whose slot holds
a still-pending curl handle, not a settled task promise — so `fetch(u).then(…)`
was a clean rejection, and the only way to consume a fetch was `await` inside an
async function. That is the most natural first thing to reach for, so the gap
stood out.

## Decision

When `.then`/`.catch`/`.finally` is called on a **raw** fetch `Promise<Response>`
(`IsResponse`, not `PromiseResolved`, and — critically — **not** already
`PromiseTask`), drive it to a settled task promise first, then run the existing
reaction machinery on that:

- **`emitFetchHandleToSettledPromise`** loads the pending handle, calls
  `__kml_await_fetch` (the same drive `await` uses), builds the `Response` via
  `buildResponseFromStatusBody`, and settles a freshly-allocated task promise
  *fulfilled* with it. The drive is bracketed in a `setjmp` guard: a
  transport-level failure (which `__kml_await_fetch` throws) is caught and settles
  the promise **rejected**, so `fetch(u).catch(e => …)` recovers it. An HTTP
  4xx/5xx is a fulfilled `Response` (per WHATWG), not a rejection.
- **The `!PromiseTask` guard is load-bearing**: a chained call that itself settles
  to a `Response` — `fetch(u).finally(f).then(g)` — returns a *task* promise that
  still looks `IsResponse`. Without the guard the outer `.then` would re-drive
  that task-promise struct as if it were a fetch handle (reading a bogus pending
  pointer → `__kml_await_fetch` segfault). The guard converts only the genuine
  raw fetch.
- **`emitFulfillCallback`** hints an unannotated `.then` onFulfilled arrow
  parameter to the source's value type, so `fetch(u).then(r => r.status)` binds
  `r` to `Response` without an annotation (mirrors `emitRejectCallback`).

## Consequences

- `fetch(u).then(r => r.status)`, `.catch` on a transport failure, and
  `.finally(...).then(...)` all work with no surrounding async function. Only the
  promise + microtask runtime is pulled in (plus libcurl, which the program uses
  by calling `fetch`); the fiber scheduler is not.
- The fetch drive is **synchronous** at the `.then` call site — this matches the
  compiler's existing model (fetch is the only real suspension, and `await` on a
  settled promise already reads synchronously). Real fetch concurrency lives in
  `Promise.all`/`.any` over an *array* of fetches, unchanged.
- `.then` on a fetch's body accessor (`r.text()`/`.json()`) is unaffected — those
  are synchronous, not promises.

- `go build`, `go vet ./...` clean; full `go test ./...` green (macOS).
- New E2E (httptest server): `TestE2EFetchThenChain` (value chain + Response
