# ADR-00759: Windows child exit codes are full 32-bit, not truncated to 8

- **Relations**: Implements [TDD-00180](../tdd/TDD-00180.md) §3 (Exit code width); extends [ADR-00737](ADR-00737.md) (the pid→slot table this reuses), [ADR-00753](ADR-00753.md)/[ADR-00754](ADR-00754.md) (the `execSync`/spawn-`'error'` exit-status paths)
- **Date**: 2026-09-07

## Context

Windows process exit codes are full 32-bit values: a child that dies of an access violation exits `3221225477` (`0xC0000005`), and `cmd /c exit 300` sets an exit code of `300`. Node reports these verbatim — `child.on('exit', code => …)` and `spawnSync(...).status` both see `300`, not `44`.

The port truncated them to 8 bits. TDD-00180 §3 flagged the row ("Exit code width — Node: full 32-bit; here: `& 0xff`", `win32proc.c:235`): a `spawnSync("cmd", ["/c", "exit 300"])` returned `.status === 44` (`300 & 0xff`), and an async `spawn(...)`'s `'exit'` event delivered `44` as well.

## Investigation

The truncation is structural, not a stray mask. Windows `waitpid` (`win32proc.c`) synthesises a POSIX wait-status word so the shared IR/C decoders — which are cross-platform — can read it: `int st = (pr && pr->killsig) ? (pr->killsig & 0x7f) : (int)((code & 0xff) << 8)`. The POSIX wait word affords only **8 bits** for a normal exit code (`WEXITSTATUS(s) = (s >> 8) & 0xff`), so `(code & 0xff) << 8` was the most that channel could carry.

Two decoders consume that word, both cross-platform and both doing `(st >> 8) & 0xff`:
- `__kml_cp_finalize` (async `spawn`/`exec` `'exit'`/`'close'` + the buffered `exec` callback), emitted as IR in `runtime_childprocess.go` — the `exited:` block.
- `__kml_cp_spawn_sync` (`spawnSync`/`execSync`), C in `runtime_spawnsync.go:150` via `WEXITSTATUS(st)`.

The 8-bit limit is genuine on POSIX — Linux/macOS wait status *is* 8-bit, and Node also reports `code & 0xff` there — so widening the shared word is wrong. Only Windows has 32-bit codes, so the wide value must travel **out-of-band**, and only the Windows decode paths should prefer it.

Rejected: widening the `int *status` channel (its signature is shared with the real POSIX `waitpid`); packing 32 bits into the status word (a normal exit needs the low 7 bits clear to stay `WIFEXITED`, leaving no room for `code << 8` when `code` exceeds 24 bits).

## Decision

Carry the full 32-bit code in the pid slot and hand it back through a Windows-only accessor that the two decoders consult, falling back to the 8-bit value when it is unavailable (a foreign, `OpenProcess`-attached pid with no slot).

- `kml_proc` (the ADR-00737 pid→slot table) gains a `DWORD exitcode`. Windows `waitpid` stores `GetExitCodeProcess`'s full value into it on a normal exit (`if (pr && !pr->killsig) pr->exitcode = code`); the POSIX status word is unchanged, so the `WIFEXITED`/`WIFSIGNALED` shape and the killed-child `('exit', null, 'SIGTERM')` path (`killsig`) are untouched.
- New export `int __kml_win_exit_code(int pid)` returns the stored code (reaped slots are kept, ADR-00737), or `-1` when the pid has no slot.
- Both decoders, **Windows-gated only**, prefer the accessor: `code = wc >= 0 ? wc : (st >> 8) & 0xff`. POSIX decode is byte-for-byte unchanged.

## Implementation notes

- `win32src/win32proc.c`: `exitcode` field; the store in `waitpid`; the accessor.
- `runtime_spawnsync.go`: declares `__kml_win_exit_code` in the `_WIN32` block; the `WIFEXITED` branch picks the wide value under `#ifdef _WIN32`.
- `runtime_childprocess.go`: declares `@__kml_win_exit_code` under the existing `runtime.GOOS == "windows"` block. Rather than thread a platform-conditional `%s` through the finalize `fmt.Sprintf` (whose arg count `go vet` checks), the whole IR is Sprintf'd unchanged and, on Windows, the `exited:` block is swapped with a `strings.Replace` on the finished string — the shared template and its arg list stay identical across platforms.
- The failed-spawn pseudo-pid path zeroes `pr->pid` before returning, so `__kml_win_exit_code` finds no slot and the decoders fall back to the `127` the status word already carries — the exec-failure convention is unaffected.

## Side effects discovered

None. The wide code only ever differs from the old value when a real child exits with a code above 255; every ≤255 exit and every signalled/failed-spawn case is byte-identical.

## Verification

- New E2E `TestE2EChildProcessWideExitCode` (`tests/childprocess_shell_test.go`): `exit 300` via `cmd`/`sh`, asserting `.status`/`'exit'` = `300` on Windows and `44` (`300 & 0xff`) on POSIX. Passes on Windows 11 (native) and Linux (Docker `klain-ci:latest`).
- Manual repro on Windows 11: `spawnSync("cmd", ["/c", "exit 300"]).status` → `300`; async `spawn` `'exit'` → `300`; `exit 44` still → `44`.
- `examples/child_process/child_process.ts` gained a `spawnSync("sh", ["-c", "exit 300"])` demo (POSIX-shaped, notes the Windows value).
- `go build`, `go vet ./codegen/...`, full `go test ./...` (Windows + Docker Linux), `make status-check`, `make reference-check`, `make conformance`.
