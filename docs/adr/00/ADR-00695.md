# ADR-00695: Untyped replace()/replaceAll() replacer-callback parameters default to the (match, offset, string) signature

- **Date**: 2026-09-04

## Context

`String.prototype.replace`/`replaceAll` accept a replacer callback whose
arguments are `(match, offset, string, ...groups)`: the matched substring
(a string), the match offset (a number), and the whole subject string.
When the callback's parameters were left untyped, they fell through to the
compiler's default `number → i64` typing, so the first `match` parameter
was treated as a number.

Repros that failed before this change:

- `"hello".replace(/l/g, (m) => m)` — `error: '%tNNN' defined with type
  'ptr' but expected 'double'`, then clang failed.
- `"hello".replace(/l/g, (m) => "X")` — same invalid-IR failure.
- `"hello".replace(/l/g, (m) => m.toUpperCase())` — `codegen error:
  toUpperCase is only supported on strings` (m inferred as number).

Only the fully-annotated form `(m: string, o: number, s: string) => ...`
worked, which is not what Node requires.

## Investigation

`resolveRegexReplacer` (`codegen/llvm/emit_regexp_replace.go:39`) resolved
the callback via `e.resolveCallback(args[1])`, which does not propagate any
parameter-type hints to an untyped arrow function. The array
higher-order-function paths already solved the identical problem by calling
`e.resolveCallbackWithHints(arg, []Type{...})`
(`codegen/llvm/emit_func.go:3254`), which routes arrow/function-expression
callbacks through `emitArrowFunctionWithHints` so untyped parameters adopt
the hint types. The compute-one-replacement site
(`emit_regexp_replace.go:76`) already passes a string `match`, an `i64`
offset, and the string subject as the call arguments, so the only mismatch
was the callback's declared parameter types.

## Decision

Resolve the replacer callback with hints matching the replacer signature:
`[]Type{TypePtr, TypeI64, TypePtr}` (match: string, offset: number,
string: string). Untyped parameters now default to these types; explicitly
annotated parameters are unaffected. The `> 3` arity error and the
literal-template path are unchanged.

## Implementation notes

Single-line change in `resolveRegexReplacer`: swap `resolveCallback` for
`resolveCallbackWithHints` with the three-element hint slice, plus an
explanatory comment. No change to the compute-one-replacement argument
marshalling, which already supplied the correct runtime value types.

The non-regex string-literal-search `replace`/`replaceAll`
(`emit_strings.go:714`, `:745`) still do not accept a callback at all —
that is a separate, pre-existing limitation and out of scope here.

## Side effects discovered

None. The array-HOF hint mechanism was reused unchanged.
