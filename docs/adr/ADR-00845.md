# ADR-00845: array-literal spread accepts any array-valued expression

- **Relations**: Extends [ADR-00467](ADR-00467.md) (array-literal spread)
- **Date**: 2026-09-10

## Context

A spread element in an array literal required a bare array **variable** — `[...m.
keys()]`, `[...arr.slice(1)]`, `[...arr.map(f)]`, `[...[1,2]]` were all rejected
with "spread element must be an array variable". Spreading an expression is a
common, standard pattern.

## Investigation

`emitSpreadArrayLitData` (`emit_arrays_core.go`) type-asserted each spread's
`sp.Arg` to an `*ast.Identifier` and read the array's data/length via
`arrayDataLenSlots(sym)` — a symbol-slot path, so any non-identifier failed. The
codebase already has `resolveArrayForHOF`, which resolves *either* a variable or
an array-valued expression to `(dataPtr, len, elemTy)` — the same helper the HOFs
use.

## Decision

Pre-evaluate each spread's source array **once** via `resolveArrayForHOF` (in
source order among the spreads), caching its `(ptr, len)` regs; the length-sum
loop and the copy loop then use the cached regs instead of re-deriving from a
symbol slot. The `@value` flat-array rejection is preserved (checked on an
identifier arg before resolving).

Ordering note: the spreads are evaluated before the static elements are stored
(the length-total must be known before the buffer is allocated), so a
side-effecting spread expression evaluates ahead of an interleaved static
element — a rare edge, unchanged in spirit from the prior two-pass structure.

## Implementation notes

`emit_arrays_core.go` `emitSpreadArrayLitData`: a `spreadOf` map keyed by the
`*ast.SpreadElement`, populated once; both loops read from it. No runtime change.

## Verification

macOS (Apple Silicon M4): `[...m.keys()]` → `["a","b"]`, `[...m.values()]` →
`[1,2]`, `[...[1,2], ...[3,4]]` → `[1,2,3,4]`, `[0, ...arr.slice(1), 9]`,
`[...arr.map(x=>x*2)]` — all match Node. New `TestE2ESpreadArrayExpression` +
the spread/array/collection/map suites green; `make examples` clean.
