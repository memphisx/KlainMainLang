## Context

Native-widget desktop GUI is the one UI direction this compiler names but has
never designed. The webview TDDs ([TDD-00142](TDD-00142.md) `klain:webview`,
[TDD-00144](TDD-00144.md) selectable backend) put an SPA in a window — the page
*is* the UI, not native widgets. [TDD-00150](TDD-00150.md) brushes GUI only
tangentially ("FFI-unlocked opentui") inside a terminal-UI roadmap.
[TDD-00033](TDD-00033.md) is a framebuffer placeholder. The only document that
ever named GTK/Qt-QML native binding was [TDD-00032](TDD-00032.md), a
deliberate bootstrapping placeholder whose whole purpose was to record that
**general C FFI was the missing prerequisite** — and to predict that "a real
TDD (or more likely, several) forks off this one once it's actually picked up."

That prerequisite shipped: `node:ffi` ([TDD-00164](TDD-00164.md), Partially
Implemented) now provides `dlopen`, statically-typed C-ABI calls, closure→C
function-pointer trampolines, and raw-memory/struct marshaling. So the reason
TDD-00032 stayed a placeholder is gone, and this is its successor.

Two forces make **Qt/QML** the right first target rather than GTK:

1. **Sailfish reuse.** The Sailfish OS target ([TDD-00146](TDD-00146.md)) wants
   native Silica look-and-feel as the step after its Gecko webview backend.
   Silica *is* a QML component library on Qt 5 (`import Sailfish.Silica`).
   Native Qt/QML on KDE-Linux and Silica on Sailfish are therefore the **same
   hard problem**: a shim over Qt's C++ API driven from compiled klain code,
   with Qt's event loop fused into the fiber scheduler. Designing them together
   means one shim story, not two.
2. **The fusion machinery is already being built.** TDD-00146 Stage 3's
   `-webview=sailfish` backend compiles a C++ Qt/embedlite shim into the binary
   (`webviewsrc/webview_sailfish.cpp`) with Qt-event-loop ↔ `select()` fiber
   fusion. A Qt/QML native binding extends that exact pattern —
   `QQmlApplicationEngine` hosting real components instead of a `RawWebView` —
   reusing the loop fusion rather than inventing it.

GTK (the Gnome-side, plain-C toolkit) is the cleaner `node:ffi` consumer of the
two — no C++ name-mangling or vtables — but it is an entirely separate widget
paradigm with no reuse against Sailfish, so it is scoped here only as a named
later route, not this TDD's deliverable.

## Design

### The core obstacle, and why `node:ffi` is not automatically the answer

Qt's public API is **C++**: mangled symbol names, vtables, templates, `QString`
/ `QVariant` value types with non-trivial ABIs. `node:ffi` calls the **C** ABI.
So `node:ffi` cannot bind Qt directly — a hand-written C (or `extern "C"`
-wrapped C++) shim layer over Qt is unavoidable regardless of route. That shim
is the real work; the question is only *where it lives*:

- **Option A — baked-in compiler shim (recommended).** A `guisrc/qt_qml.cpp`
  compiled per-build, exactly like `webviewsrc/` and every `runtime_*.go` C
  decl today, linked conditionally (`-lQt5Qml -lQt5Quick -lQt5Gui …` only when
  the GUI API is used, the [ADR-00020](../adr/ADR-00020.md) `-lcurl`
  precedent). klain reaches it through the compiler's existing internal C-ABI
  interop (`ensure*()`/`emit_*.go`), **not** through `node:ffi` at all. This
  matches the webview precedent, keeps the ABI surface authored and versioned
  in-repo, and lets the shim's `extern "C"` boundary hide every C++ detail.
- **Option B — standalone shim shared library + `node:ffi`.** Ship the same
  C++ shim as a separate `.so`, `dlopen`'d from user (or stdlib) klain code via
  `node:ffi`. Lets the binding surface evolve without recompiling the compiler
  and keeps GUI out of the compiler binary, but duplicates conditional-linking
  logic, complicates packaging (an extra artifact to distribute — hostile to
  the Sailfish RPM/Harbour bundling story in TDD-00146 Stage 2), and still
  requires authoring the identical C++ shim.

**Recommendation: Option A.** `node:ffi`'s relevance is that it *proved out*
the two hard capabilities this binding needs — closure→C-function-pointer
trampolines and struct marshaling — as reusable machinery; the GUI shim reuses
those internally rather than consuming `node:ffi` as a user. A future
user-extensible route (custom QML types authored in klain) can revisit Option B
once the baked-in surface exists.

### The QML bridge (structural parallel to `klain:webview`)

QML is declarative: a `.qml` scene is loaded by a `QQmlApplicationEngine`, and
native code communicates with it through **context properties** (native objects
exposed to QML), **`Q_INVOKABLE` methods / slots** (QML→native calls), and
**signals** (native→QML notifications). This is structurally the same three-way
contract `klain:webview` already builds on (native object exposed to the page,
page→native calls, native→page resolution), so the typed-bind layer and much of
the dispatch design carry over conceptually — the transport is Qt's
meta-object/signal-slot system instead of a JSON message channel.

- **Scene source**: load a `.qml` file, an embedded QML string, or a
  `klain:assets`-embedded bundle (same embedding mechanism TDD-00142 Stage 7
  uses for SPAs) — QML resources compiled in via `qrc` or read from the
  in-binary asset store.
- **native→QML**: expose a generated context object; its properties and signals
  are how klain state reaches the scene. Property writes emit change signals;
  QML bindings react. No polling.
- **QML→native**: `Q_INVOKABLE`/slot calls on the context object marshal into
  the klain runtime. Callback-bearing calls use the **closure→C-fn-pointer
  trampoline** (the `node:ffi`/TDD-00164 mechanism) so a klain closure can be a
  Qt slot.
- **typed bind / `--emit-window-dts` analogue**: the transport-agnostic typed
  layer from TDD-00142 carries over; a QML context object gets a generated
  typed surface the same way `window.<fn>` did.

### Loop fusion (shared with TDD-00146 Stage 3)

Qt's event loop must co-run with the fiber scheduler's `select()` loop — the
identical problem the GTK and AppKit webview fusions already solve, and the one
the Sailfish webview backend is solving with Qt specifically. Reuse that:
`QEventLoop`/`processEvents` interleaving, with `QSocketNotifier` for the
inverse direction (letting Qt wake on the runtime's fds) if cooperative
`processEvents` polling proves ugly. This TDD should land *after or alongside*
TDD-00146 Stage 3 so the fusion is built once.

### Silica as a thin specialization

Once the KDE-Linux Qt/QML binding exists, Sailfish Silica is almost entirely a
*QML import + Qt-version* delta, not new native code:

- **QML imports**: `import Sailfish.Silica 1.0` and Silica component types
  instead of Qt Quick Controls / Kirigami. Pure QML-side; the C++ shim is
  unchanged.
- **Qt version**: KDE targets current Qt (Qt 5 LTS, and Qt 6 for modern KDE —
  see open questions); Sailfish is frozen near Qt 5.6. The shim must assume
  nothing newer than the *older* target's stable meta-object surface, which is
  a real constraint but not a structural one.
- **Packaging**: Silica apps ride TDD-00146 Stage 2's RPM/Harbour path; KDE
  apps ride the existing `.desktop` packaging. The Harbour allowlist
  (`libsailfishwebengine` etc. allowed; pcre2/bdw-gc bundled) is a TDD-00146
  concern that carries over unchanged.

So the deliverable ordering is: **Qt/QML native binding (KDE-Linux, provable on
the dev machines and in Docker) → Silica as a QML-import specialization on the
Sailfish target**. The expensive, hardware-only tier (real Silica look-and-feel
on a Jolla device) is the *last* mile, resting on everything provable off-device
first.

### Staging

1. **Stage 1 — window + QML scene + native→QML properties/signals.** A
   `QGuiApplication` + `QQmlApplicationEngine` hosting a QML scene from a file
   or embedded string, a generated context object exposing properties/signals,
   loop fusion. No QML→native calls yet. Provable on KDE-Linux + Docker/qemu.
2. **Stage 2 — QML→native invokables + closure/slot trampolines.** Wire
   `Q_INVOKABLE`/slots through the TDD-00164 trampoline; typed-bind surface.
3. **Stage 3 — asset embedding + packaging.** `klain:assets`/`qrc` embedding of
   QML; `.desktop` packaging for KDE.
4. **Stage 4 — Silica specialization on Sailfish.** Silica QML imports, Qt-5.6
   surface guard, RPM/Harbour packaging (TDD-00146 Stage 2), on-device
   verification (Jolla C2 / Xperia 10 II).
5. **GTK (Gnome) — deferred to its own TDD.** Plain-C, no C++ shim, a clean
   `node:ffi`/baked-C consumer, but a separate widget paradigm with no Sailfish
   reuse. Named, not scoped here.

## Open questions

- **Qt 5 vs Qt 6.** KDE has moved to Qt 6; Sailfish is frozen near Qt 5.6.
  Does the shim target Qt 5 (maximal Sailfish overlap, aging on KDE), Qt 6
  (modern KDE, no Sailfish reuse in the shim itself), or abstract over both at
  the `extern "C"` boundary? The meta-object/QML surface this binding touches
  is largely stable across 5→6, but `QString`/`QVariant`/build-system details
  differ. Leaning: author the shim against the stable subset, build it twice
  (Qt5 for Sailfish, Qt6 for KDE) behind the same `extern "C"` API.
- **Qt Quick Controls vs. Kirigami for the KDE-side "native" look.** Bare Qt
  Quick is toolkit-neutral; Kirigami is KDE's convergent component set (the
  KDE analogue of Silica). Does the KDE deliverable ship bare Quick (portable,
  plain) or adopt Kirigami (more "native KDE", heavier dependency)?
- **QML authoring model.** Does the developer write `.qml` by hand (klain
  supplies only the native context object — closest to how Qt apps are built),
  or is there a klain-side declarative API that generates QML? The former is
  far smaller scope and matches the "reimplement the API shape, bind the native
  core" split used elsewhere; the latter is a much larger product.
- **Where the QML/Qt binding surface is authored** — reaffirm Option A
  (baked-in) vs. Option B (`node:ffi`-dlopened shim lib) once Stage 1 exists
  and the packaging cost of a separate artifact is concrete against the
  Sailfish RPM story.
- **Slot-callback threading.** QML calls arrive on the Qt/GUI thread; the
  trampoline must hop into the fiber scheduler. Same shape as the webview async
  bind and the (Android) JNI-thread question — likely one shared solution
  (pipe/eventfd wake into `select()`).
