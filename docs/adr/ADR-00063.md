# ADR-00063: Classes Stage 1 (+1a) — methods, constructors, `this`, `new`, and a class-based `for...of` iterator protocol

- **Relations**: Extends [ADR-00062](ADR-00062.md). Implements [TDD-00009](../tdd/TDD-00009.md) (Stages 1 and 1a of 4)
- **Date**: 2026-07-28

## Context

[ADR-00062](ADR-00062.md) (Stage 0) added lexer/parser/AST support for `class`/`this`/generic `new ClassName(args)`, but every `ClassDeclaration`/`ThisExpression`/`NewExpression` still fell through to codegen's generic "unknown statement/expression type" error — parsing worked, nothing ran. This picks up Stage 1 of [TDD-00009](../tdd/TDD-00009.md): instances as heap-malloc'd structs reusing the exact same object machinery interfaces already use, methods as plain static calls with `this` as an implicit first argument, and constructors reusing the malloc-then-initialize-fields shape `emitObjectLiteral` already established. Per direct instruction, this pass also includes Stage 1a — extending `for...of` with a fourth case for a class implementing a sentinel `next(): T | null` method.

## Investigation

Before writing any code, three parallel investigations (object/struct field machinery; function/closure calling convention + call dispatch; for-of/pre-pass registration) confirmed the concrete design was sound and identified the exact insertion points:

- `emitMember`/`inferExprType`/`emitAssign`'s object-field-read/write paths already recurse generically via `e.emitExpr`/`e.inferExprType` (not just identifiers) and gate purely on `Type.IsObject` — so a class instance's `this.field`/`instance.field` works on *any* expression shape for free, the moment `IsObject: true` is set, with zero changes to those functions.
- There is no LLVM symbol mangling anywhere in this compiler; every function is emitted under its literal source name with a bare `@` prefix. `@ClassName_methodName` is safe by the same reasoning closures' `@__closure_N` names already are — a separate namespace from `e.funcs`, so no *compiler-level* name collision is possible, only the same narrow, pre-existing class of risk (a same-named top-level function producing the same LLVM symbol) closures already accept.
- `emitCall`'s dispatch chain (`codegen/llvm/emit_call.go`) is a long sequence of `if mem.Property == "<name>"` checks, and **most of them have no receiver-type guard at all** (`push`, `map`, `filter`, `join`, string `slice`'s fallback branch, etc.). A class method dispatch check placed anywhere after these would be silently shadowed by a same-named built-in the moment a user wrote e.g. `class Foo { push(...) {...} }`. Map/Set already had to solve this exact problem once (their own dispatch sits ahead of the generic `forEach` case, with a comment explaining why) — that precedent is why the class-method check went in immediately after the Date/Response type-gated checks, before the unguarded chain begins, not "somewhere reasonable" in the chain.
- `emitForOf` (`codegen/llvm/emit_stmts.go`) always converges its three existing cases (array/Map/Set) onto one shared `(dataPtrAlloca, lenAlloca, elemTy)` triple before running a single index-counted loop. That shared tail assumes a known length up front and is structurally incompatible with a lazy `next()`-call protocol — confirmed this needed its own independent loop-emission path, not a fourth case feeding the same tail.

## Decision

**`Type` gets a nominal class tag** (`codegen/llvm/types.go`): `IsClass bool` + `ClassName string`, and `ClassType(name, fields)` which calls `ObjectType(fields)` and stamps both — mirroring `ResponseType()`'s exact shape. Setting `IsObject: true` this way is what makes every existing generic object mechanism apply to class instances unmodified; `IsClass`/`ClassName` exist purely so method dispatch (and, later, `instanceof`) can recognize a class instance as distinct from a plain structural object literal.

**New file `codegen/llvm/emit_classes.go`** holds everything class-specific: `ClassInfo` (the per-class registered shape: `Ty`, `Constructor`/`CtorSig`, `Methods`/`MethodSigs`), `registerClasses` (a new pre-pass, modeled on `registerInterfaces` for field resolution and `registerFunctions` for signature-building, including reusing `inferUnannotatedReturnType` for methods with no explicit return type — pushing a scope that also defines `"this"` first, since an inferred return expression may reference `this.field`), `emitClassDecl`/`emitClassMember` (constructor/method emission), `emitThisExpression`, `emitNewExpression`, `emitClassMethodCall`, and `emitForOfClassIterator` (Stage 1a).

`registerClasses` stores each class's `Ty` into **`e.interfaces[name]`** (the same registry `registerInterfaces` already populates) rather than a separate type-name registry — this is what makes `resolveType` resolve a class name in any type annotation (`function f(p: Point)`, `p: Point | null`, `Point[]`) with zero changes to `resolveType` itself.

**`emitClassMember`** is a deliberately separate function from `emitFunctionDecl`, not a refactor of it — it duplicates the non-async subset of `emitFunctionDecl`'s state-save/reset/restore + parameter-binding loop (methods are structurally never async; the parser hardcodes `isAsync=false` for every class member from Stage 0 onward). One addition beyond a plain function: LLVM parameter slot 0 is always `ptr %p_this`, alloca'd/stored/bound to scope symbol `"this"` ahead of the member's own declared parameters, which are never touched by this — `ast.ThisExpression` evaluation is just `e.lookup("this")` like any other identifier. Precedent for preferring duplication over a conditional receiver parameter threaded through `emitFunctionDecl`: [ADR-00061](ADR-00061.md)'s `resolveObjectPtr` duplicating `emitObjectLiteral` for the same "lower regression risk than adding a new concern to an already-relied-upon function" reason.

**Constructors** (`new ClassName(args)`, `emitNewExpression`): malloc sized to `ClassInfo.Ty.StructSize()`, call `@ClassName_constructor(ptr instance, ARGS...)` if a constructor was declared, return the pointer. **A class with ≥1 field but no constructor is a compile-time error** (`registerClasses`), not a silently-garbage-initialized instance — this compiler has no field-initializer syntax (Stage 0 scope), and `emitObjectLiteral` already refuses to leave any object field unset; requiring a constructor here is the same "no silently uninitialized state" philosophy, just enforced once at class-declaration time instead of at every construction site. A zero-field, methods-only class may omit the constructor.

**Method calls** (`emitClassMethodCall`) mirror the existing named-function-call shape (exact-arg-count + `coerce` + `call RETTY @name(...)`), minus default-value/rest-argument support — Stage 1 requires an exact argument count for both constructors and methods (parses fine per Stage 0's `parseParamList`, just not honored at a call site yet; a documented, narrow gap, not a silent one, since a wrong count is a clear compile error). Dispatch in `emitCall` only fires when the class actually declares a method by that property name (`info.MethodSigs[mem.Property]` check), so a field that happens to hold a closure (`cb: () => void`) still falls through to the existing generic `IsFunc` field-call dispatch further down, unaffected.

**Stage 1a**: a class is iterable if it declares a zero-param method `next` returning `T | null` (`FuncSig.RetType.Nullable`), where `T` isn't itself an array/Map/Set (kept to one-register element types — numbers, bools, strings, object/class instances — all of which already have a well-defined single-register null-or-value shape; an array-shaped `T` would need `{ptr,i64}`-aware null handling, out of scope here). `emitForOf` checks this *before* its existing array/Map/Set resolution logic and, if matched, evaluates the receiver once and hands off to `emitForOfClassIterator`, which builds its own loop reusing the caller's already-created `cond`/`body`/`inc`/`end` labels and break/continue/pending-label bookkeeping: `cond` calls `next()` and tests the result against the sentinel (`icmp eq ptr ..., null` when the element IR is `ptr`; `icmp eq <IR> ..., 0` otherwise); `inc` is just `br label %cond` since calling `next()` again *is* the advance step, no index to bump. The numeric-sentinel branch inherits the exact same "0 is ambiguous with a real 0 value" limitation `.find()`/`process.env` already document — not a new one, confirmed by deliberately testing a `Range` starting at 0 (see Verification).

## Implementation notes

Files touched: `codegen/llvm/types.go`, `codegen/llvm/emitter.go` (new `classes` field + `registerClasses`/class-emission pass wiring into `EmitProgram`), `codegen/llvm/emit_classes.go` (new), `codegen/llvm/emit_exprs.go` (`emitExpr`/`inferExprType`/`emitVarDecl` new cases), `codegen/llvm/emit_objects.go` (`emitObjectVarDecl`'s new case — see also [ADR-00064](ADR-00064.md) below), `codegen/llvm/emit_stmts.go` (`emitStmt`'s no-op case; `emitForOf`'s new dispatch + updated error messages), `codegen/llvm/emit_call.go` (`emitCall`'s new dispatch block).

Non-obvious ordering constraint: `registerClasses` itself needs two internal passes, not one (see [ADR-00064](ADR-00064.md)'s Investigation for why — self-referential class fields).

## Side effects discovered

Two real, pre-existing bugs surfaced while building this stage's own test coverage (a self-referential `Node` linked-list example for Stage 1a) — both fixed as part of this same piece of work, written up separately since they're general object-system bugs, not class-specific ones: **[ADR-00064](ADR-00064.md)**.

## Verification

- `go build -o klainmain .`, `go vet ./...`, `go test ./...` — all green.
- `make examples` — 59/59 passed (58 pre-existing + the new `examples/classes/classes.ts`).
- New tests in `tests/classes_test.go`: fields+constructor+method, a method mutating a field, a method calling another method via `this`, two instances retaining independent state, a class instance as an ordinary function param/return, `new ClassName(...)` chained directly into a method call, a zero-field/no-constructor class, a self-referential class field (including destructuring through it), and both Stage 1a cases (numeric-element and object-element iterators) — plus two negative tests (fields without a constructor; duplicate method name) via `parseAndCompile`.
- Manual `--emit-llvm` spot-check of the compiled example confirmed the emitted shape matches the design exactly: `call void @Point_constructor(ptr %t0, i64 %t8, i64 %t16)`, `call i64 @Point_squaredLength(ptr %t0)` (a method calling another method — plain static calls throughout, no closure-header indirection), and `this.field` compiling to a direct `getelementptr { i64, i64 }, ptr %t0, i32 0, i32 N` — also confirmed `Object.freeze`'s existing frozen-check machinery applies to class instances transparently (visible in the constructor's own emitted IR), for free, via the shared `IsObject` representation.
- Deliberately tested the numeric-iterator sentinel ambiguity with a `Range` starting at 0 (immediately terminates, since 0 is indistinguishable from "done") to confirm it's the same pre-existing `.find()`-style limitation and not a new bug — then re-tested starting at 1 to confirm the mechanism itself is correct.
