# ADR-01959: Object spreads carry index signatures as tsc's do

- **Relations**: Implements TDD-00230 (P2.3)
- **Date**: 2026-10-29

## Context

The checker left an object literal spreading a type with an index signature unanswered (`{ ...process.env, NODE_ENV: "production" }`): `spreadable` refused any index signature, any library type (library types are open, since they list only what this compiler implements), and any instantiated generic (`NodeJS.Dict<string>`). Such a literal compiled without type checking.

`examples/os/os_info.ts` read `childEnv.OS_INFO_EXAMPLE` off exactly such a literal. tsc 5.9 with `@types/node` rejects that read (TS2339 on `{ NODE_ENV: string; }`), so the example was invalid TypeScript that the strict lane accepted.

## Decision

The checker follows tsc's `getSpreadType`:

- A spread contributes its index signatures. The literal keeps a signature only where every part has one (`getUnionIndexInfos`): every spread, and no property of the literal's own beside them. Its value type is the union of the spreads' signatures. A number signature is kept only if every spread declares its own.
- `spreadable` accepts index signatures and instantiated generics. A library type is spread when it is purely a dictionary (an index signature and no members, `NodeJS.Dict<T>` and `ProcessEnv`), since nothing can be missing from it.
- A computed key's signature beside an indexed spread stays unanswered, as before.

The example annotates the binding `NodeJS.ProcessEnv`, which keeps the index signature, as tsc requires.

## Consequences

- `{ ...process.env, NODE_ENV: "production" }.PATH` is rejected with tsc's message; `{ ...env }` reads any key.
- `TestE2EObjectSpreadIndexSignature` passes (Mac), and tsc 5.9 accepts its valid half and the example.
- An object type with two index signatures is still rejected by the parser (unsupported diagnostic 90014); this change does not touch that.
