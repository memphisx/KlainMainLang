# TDD-00104: Web Crypto `crypto.subtle` via selectable native crypto backends

- **Status**: Implemented
- **Date**: 2026-08-23
- **Notes**: `-crypto=openssl|commoncrypto` clones the `-bigint` backend shape: per-backend embedded C file, one shared `__kml_crypto_*` ABI, conditional compile+link. Full surface: digest, getRandomValues TypedArray migration, CryptoKey/CryptoKeyPair, HMAC, AES-GCM/CBC, RSA-OAEP/PSS, ECDSA, PBKDF2/HKDF, raw/pkcs8/spki/jwk formats. JWK ABI shipped as per-component base64url strings (not the JSON exchange sketched here) — see ADR-00319

## Context

`docs/status/WEB-CRYPTO.md` sits at 2/8: only `crypto.getRandomValues` and
`crypto.randomUUID` exist, both built on the in-house CSPRNG shim
(ADR-00024). The remaining six rows — `subtle.digest`, `encrypt`/`decrypt`,
`sign`/`verify`, `generateKey`, `importKey`/`exportKey`,
`deriveKey`/`deriveBits` — need real cryptographic primitives that this
project should not hand-implement wholesale. The decision is to delegate to
established native libraries behind a compiler flag, exactly the way
`-bigint=libtommath|gmp` already selects among backend C files implementing
one shared ABI (TDD-00074).

Target algorithm set (the Web Crypto core that CLI tools and microservices
actually use):

- digest: SHA-1, SHA-256, SHA-384, SHA-512
- encrypt/decrypt: AES-GCM, AES-CBC, RSA-OAEP
- sign/verify: HMAC, ECDSA (P-256/P-384/P-521), RSA-PSS
- generateKey: AES, HMAC, RSA (OAEP/PSS), EC
- importKey/exportKey: `raw`, `pkcs8`, `spki`, `jwk`
- deriveBits/deriveKey: PBKDF2, HKDF

## Design

### Backend selection: `-crypto=openssl|commoncrypto`

- **`openssl` (default, all platforms)** — links `-lcrypto` (OpenSSL 3.x,
  EVP-family APIs only; no deprecated 1.x calls). Located via
  `pkg-config libcrypto`, falling back to `brew --prefix openssl@3` on Mac
  (Homebrew's OpenSSL is keg-only, so the generic `brew --prefix` root is
  not on the include/lib path), then a bare `-lcrypto`.
- **`commoncrypto` (opt-in, macOS only)** — CommonCrypto (in libSystem, no
  `-l` needed) for hashes/HMAC/AES/PBKDF2, plus `Security.framework` +
  `CoreFoundation.framework` for all RSA/EC work via SecKey. Rejected at
  flag-validation time on non-Darwin and in combination with `--static`
  (frameworks are dynamic-only; `--static` is Linux-only anyway).
- A future self-contained backend (own implementations over vendorable
  public-domain sources) is deliberately deferred; the ABI below is the
  seam it would slot into, at which point it could become the default and
  the external libraries stay as options.

Wiring clones the bigint shape end to end: `codegen/llvm/crypto.go` holds
`CryptoBackends`, `CryptoBackendSource(backend)` (`//go:embed
cryptosrc/crypto_openssl.c` / `crypto_commoncrypto.c`), and
`LocateCrypto(backend) (cflags, libs)`; the emitter gains
`SetCryptoBackend`/`CryptoBackend()`/`UsesCrypto()`; `main.go` validates
the flag, writes the selected shim next to the `.ll`, and appends
cflags/libs — all only when the program actually used `crypto.subtle`.

### One C ABI, two implementations

Every backend implements the identical `__kml_crypto_*` contract so the
emitter stays backend-agnostic. Conventions: `long long` return, `0` = ok,
negative = error class (mapped to DOMException-style names by the emitter:
`-1` OperationError, `-2` DataError, `-3` NotSupportedError); variable-size
outputs are malloc'd by the shim and returned via out-params (program
allocator, so GC mode sees them); fixed-max outputs (digests/HMAC, ≤64
bytes) fill a caller buffer.

Hash ids: `1`=SHA-1 `2`=SHA-256 `3`=SHA-384 `4`=SHA-512.
Curve ids: `1`=P-256 `2`=P-384 `3`=P-521.
Alg ids (CryptoKey header): AES_GCM=1, AES_CBC=2, HMAC=3, RSA_OAEP=4,
RSA_PSS=5, ECDSA=6, PBKDF2=7, HKDF=8.


AES/HMAC key generation needs no new ABI function — it is
`__kml_crypto_random_bytes` (already shipped) into a fresh key buffer.

Notes per backend:

- **OpenSSL**: `EVP_Digest`, `EVP_MAC` (HMAC), `EVP_CIPHER_CTX`
  (AES-GCM/CBC), `EVP_PKEY_encrypt/decrypt` with
  `RSA_PKCS1_OAEP_PADDING`, `EVP_DigestSign/Verify` (PSS via
  `EVP_PKEY_CTX_set_rsa_padding`/`set_rsa_pss_saltlen`, ECDSA with
  DER↔raw-r||s conversion in the shim), `EVP_PKEY_Q_keygen`,
  `d2i_PrivateKey`/`d2i_PUBKEY` + `i2d_*`, `EVP_KDF` for PBKDF2/HKDF.
- **CommonCrypto**: `CC_SHA*`, `CCHmac`, `CCCrypt` (CBC).
  **AES-GCM = public `kCCModeCTR` + an in-shim GHASH** — CommonCrypto's
  own GCM entry points are private SPI, so the composition uses only
  public API; the GHASH (~120 lines, bit-reflected carry-less multiply,
  no lookup tables) is validated against NIST GCM vectors in the E2E
  suite. This is the accepted trade-off vs. declaring private SPI
  prototypes (Apple could drop them) or leaving a per-backend hole.
  PBKDF2 via `CCKeyDerivationPBKDF`; HKDF is absent from CommonCrypto's
  public API, so the shim implements RFC 5869 over `CCHmac`.
  All RSA/EC via SecKey (`SecKeyCreateRandomKey`,
  `SecKeyCreateSignature/VerifySignature`,
  `SecKeyCreateEncryptedData/DecryptedData`, `SecKeyCreateWithData`,
  `SecKeyCopyExternalRepresentation`). SecKey's external forms are
  PKCS#1 (RSA) and X9.63 (EC); the shim wraps/unwraps to PKCS#8/SPKI
  with fixed DER templates for RSA and the three curves.
- **JWK lives in the shims, not the emitter**: export builds the JWK JSON
  string in C (shared base64url helper); import scans the flat JWK object
  with a minimal JSON field scanner and reassembles raw/DER key material.
  The emitter bridges: `exportKey("jwk")` feeds the returned JSON through
  the existing JSON parse-tree runtime to yield an object;
  `importKey("jwk", obj)` serializes the object via the existing
  `JSON.stringify` runtime. Both backends thus share exactly one JWK
  format surface.

### CryptoKey / CryptoKeyPair model

Runtime CryptoKey = malloc'd header
`{ i64 algId, i64 hashId, i64 usagesBitmask, i64 extractable, i64 kind,
ptr keyData, i64 keyLen }` — kind `0`=secret `1`=public `2`=private;
usage bits: encrypt=1 decrypt=2 sign=4 verify=8 deriveKey=16 deriveBits=32
wrapKey=64 unwrapKey=128. `keyData` is raw bytes for symmetric keys and
DER (PKCS#8 private / SPKI public) for asymmetric — backend-agnostic, GC
managed like any other allocation, no native handles or finalizers; each
operation re-parses the DER inside the shim.

Compile-time: new `IsCryptoKey` / `IsCryptoKeyPair` Type flags (the
`IsBlob`/`IsArrayBuffer` pattern). A CryptoKeyPair is a malloc'd
`{ ptr publicKey, ptr privateKey }`. Whether `generateKey` yields a key or
a pair is decided at compile time from the algorithm name literal.
Property reads (`key.type`, `key.extractable`, `key.usages`,
`key.algorithm.name`, `pair.publicKey`, `pair.privateKey`) are header
reads in the member-expression path.

### Emitter surface

- Dispatch: `crypto.subtle.<m>(...)` has a MemberExpression (not
  Identifier) receiver — a `isCryptoSubtle(expr)` helper guards routing in
  `emit_call.go` to a new `emit_call_crypto.go`
  (`emitSubtleDigest/Encrypt/…` + `parseAlgorithm`). The same guard keeps
  `inferExprType` and the member-read paths consistent; a bare
  `crypto.subtle` used as a value is a compile error ("must be called
  directly").
- Algorithm arguments must be string literals or object literals with
  literal `name:` / `hash:` / `namedCurve:` fields (compile error
  otherwise — the compile-time dispatch model). Data-bearing fields
  (`iv`, `salt`, `info`, `counter`, `additionalData`) are runtime
  BufferSource expressions; counts (`iterations`, `length`, `tagLength`,
  `modulusLength`, `saltLength`) are runtime i64. `publicExponent` is
  restricted to the literal `new Uint8Array([1, 0, 1])` or omitted
  (65537).
- BufferSource extraction reuses the TextDecoder pattern: ArrayBuffer
  header `{ i64 byteLength, ptr data }`, or `resolveArrayForHOF` for
  (typed) arrays with byte-length scaling for non-u8 element types.
  Binary results come back as fresh ArrayBuffers (the Blob header
  pattern).
- Return surface: every `subtle.*` returns a settled task-shaped Promise
  (the `Promise.resolve(v)` machinery — `emitAllocSettledPromise` +
  `storePromiseValue` + state 1 + `PromiseTask`), so `await`, `.then`,
  `.catch`, `.finally` all behave. Operational failures (bad tag, DER
  parse failure, usage violation) throw synchronously via the exception
  helpers with DOMException names (`OperationError`, `DataError`,
  `NotSupportedError`, `InvalidAccessError`) — a documented deviation
  from spec promise-rejection, consistent with the compiler's synchronous
  builtin model.
- `crypto.getRandomValues` is migrated to accept real TypedArrays
  (`__kml_crypto_random_bytes` straight into the view's bytes), keeping
  the legacy `number[]` form working.

## Open questions

- Whether operational failures can settle the task promise as rejected
  (real spec behavior) instead of throwing synchronously — depends on
  whether a settled-rejected promise value flows through `.catch`/`await`
  identically to `Promise.reject`'s; resolve during implementation and
  record in the ADR.
- `deriveKey`'s derived-key algorithm set (V1: AES-GCM/AES-CBC/HMAC
  targets) — confirm against real-world usage when implementing Phase 4.
