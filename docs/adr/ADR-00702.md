# ADR-00702: -optimize-memory — escape analysis → stack allocation (Stage 1)

- **Relations**: Implements TDD-00134 (Stage 1); Extends ADR-00698 (the escape checker)
- **Date**: 2026-09-04

## Context

Every object literal is heap-allocated (`calloc`), even one that provably
never outlives its block — the largest real perf gap versus Go-class native
code (TDD-00134). TDD-00173 delivered exactly the analysis Stage 1 needs:
the escape checker's "safe to free at block exit" condition (no alias
outlives the block) is the same condition as "safe to place on the stack".

## Investigation

- `emitObjectLiteralWithHint` (emit_objects.go) is the single allocation
  point for fixed-shape literals: one `calloc` (zeroing chosen over malloc
  so omitted optional fields read back 0 — ADR-00157). The two-builder
  split (`e.allocas` entry block / `e.body`) already hosts stack slots.
- clang -O2 already elides a calloc whose pointer never escapes the
  LLVM-visible scope, so a naive RSS benchmark shows no delta; the win is
  the cases clang cannot prove — measured with `console.log(p)` (pointer
  passed to the runtime printer, opaque to clang but whitelisted by the
  escape checker): 2M 32-byte literals, peak RSS 542MB → 459MB, the ~83MB
  delta being exactly the objects.

## Decision

New boolean flag `-optimize-memory` (off by default while the analysis
matures, per the TDD). Under it:

- A second escape-planner run (`planStackAllocs`, `escPlanner.stack`)
  marks implicit let/const declarations whose initializer is a plain object
  literal and whose flow passes the existing checker. Explicit @free/@owned
  declarations are excluded (they asked for a heap free; honoring that
  keeps the annotation's meaning). The FinalizationRegistry register-target
  exemption (ADR-00703) is off in this run — a stack value's scope exit
  emits no free, so the registry would never be notified; registered
  targets stay heap.
- Emission: `emitVarDecl` marks the planned literal node
  (`pendingStackAllocLit`); `emitObjectLiteralWithHint` consumes it —
  entry-block `alloca` of the struct plus a `zeroinitializer` store *at the
  literal site* (not at the alloca), so a loop iteration reusing the slot
  re-zeroes it, preserving calloc's absent-optional-field guarantee. Paths
  that aren't a plain fixed-shape struct (computed keys, accessors, dynamic
  hints) never match the marker and keep the heap path.
- `maybeRegisterAutoFree` skips a stack-emitted declaration (freeing an
  alloca would corrupt the heap) — the `-mm=auto` + `-optimize-memory`
  combination composes.

Stages 2 (flat value-type arrays) and 3 (value-returned tuples) are not
started; class instances (constructors allocate internally), closure
environments, tuples, and Map/Set (runtime-created) stay heap in Stage 1.

## Implementation notes

- New: `codegen/llvm/emit_stackalloc.go` (planner entry + the
  FinalizationRegistry name collector shared with ADR-00703),
  `tests/optimize_memory_test.go`.
- Touched: `escape_check.go` (planner `stack` mode), `emit_objects.go`
  (alloca path), `emit_exprs_vardecl.go` (marker), `emit_autofree.go`
  (skip), `emitter.go` (fields/setter/plan call), `main.go` (flag).

## Side effects discovered

None — the flag off is byte-identical output, and behavioral tests assert
flag-on/flag-off equivalence including optional-field zeroing under loop
slot reuse.

## Verification

Mac (Apple Silicon): IR-level tests assert non-escaping literals lose their
calloc and gain an alloca while returned/stored literals keep both callocs;
behavioral equivalence test (with/without flag); `-mm=auto` combo test; the
Memory/Weak/AutoFree suites pass; RSS churn measurement above.
