# ADR-00180: Class field initializers (TDD-00063 Stage 1)

- **Relations**: `Implements TDD-00063` (Stage 1 of 4). `Extends ADR-00155` (fills the field-initializer syntax [TDD-00021](../tdd/TDD-00021.md) deferred).
- **Date**: 2026-08-13

## Context

[TDD-00063](../tdd/TDD-00063.md) scopes the class-body member surface — the single largest in-scope Test262 gap (7,166 failing class files, 37% of all `language/` failures). Stage 1 is class field initializers (`x = 5`, `n: number = 5`, `#x = 0`): the most contained slice, the one [TDD-00021](../tdd/TDD-00021.md) explicitly deferred ("no field-initializer syntax — pre-existing, not `#`-specific"), and the one with the highest incidental value since field initializers appear across a huge number of otherwise-in-scope files. Before this, a class field was parse-only `name: type;` with no initializer, and a class with own fields but no constructor was a hard compile error (`emit_classes.go`).

## Investigation

- `parser/parser_classes.go`'s field branch required `: type` and forbade `= expr`; `ast.AnnotField` (shared with interface/object-type fields) had no initializer slot.
- The constructor-rules switch in `registerClasses` (`codegen/llvm/emit_classes.go`) already synthesizes a pass-through constructor for a fieldless derived class, and already errors on "fields but no constructor" — the natural place to both splice initializers and relax that error.
- `hasTopLevelSuperCall` (`emit_classes.go:425`) already does the shallow super()-presence scan the spec's "run field initializers right after super()" ordering needs — it only lacked the *index*.
- Generic classes take a **separate** path (`emit_generics.go`): `registerClasses` stores them in `e.genericClasses` and `continue`s (`emit_classes.go:554`), and `instantiateGenericClass` builds a fresh `ClassInfo` **once per distinct type-arg set**. A first attempt that spliced initializers into the shared template AST produced a `void`-typed struct field (`getelementptr { i64, void, ptr }`, LLVM "void type only allowed for function results") because the generic field-type resolver read `f.Type` directly and had no nil (unannotated) handling — and would also have double-spliced across `Box<string>` / `Box<number>`.
- `inferExprType` (`emit_exprs_types.go:225`) is a pure compile-time type query with an `i64` default (matching the compiler's `number → i64` default), safe to call during registration to type an unannotated field from its initializer.

## Decision

Desugar each own **instance**-field initializer into a `this.field = <initExpr>` statement and run it at construction time, in field-declaration order, immediately after super() (or at the top of a base class's constructor), before the constructor body. Reuse the ordinary assignment/member/constructor codegen unchanged — no new emission machinery.

1. **AST**: add `Initializer Expression` to `ast.AnnotField` (nil for every non-class reuse and for a bare `x: T;`).
2. **Parser**: make `: type` optional when an `= expr` initializer follows; an unannotated `x = expr` takes its type from the initializer. A field with neither a type nor an initializer is a clean rejection.
3. **Field type** (`registerClasses` + `genericClassMangledFields`): annotated → `resolveType`/`substituteGenericType` as before; unannotated → `inferExprType(initializer)`.
4. **Constructor** (`registerClasses`, non-generic): for an explicit constructor, splice the init statements at `topLevelSuperCallIndex(body)+1` (which is `0` when there is no super()). When *every* own instance field has an initializer, a class needs no explicit constructor — synthesize one (forwarding `super(...)` first if the base has a constructor, then the inits). The "fields but no constructor" error now only fires when some own field has neither an initializer nor a constructor to set it.
5. **Constructor** (`instantiateGenericClass`, generic): same relaxation, but building a **fresh** constructor/body rather than mutating the shared template AST (this path runs once per type-arg set). A generic class can never `extends`, so inits always go at the very top — no super() to sequence after.
6. **Static field initializers are out of scope for Stage 1** (they would run in the class's `staticinit`, a separate mechanism) — a clean, specific rejection pointing at `static {}` blocks.

## Implementation notes

- Injection anchors on `topLevelSuperCallIndex`, added alongside `hasTopLevelSuperCall` (refactored to share it). Helpers `classFieldInitStmts` (builds the `this.field = init` statements) and `classHasOwnFieldInit` (returns any/all-fields-initialized) are shared by both the generic and non-generic paths.
- Non-generic splicing mutates `cd.Constructor.Body.Body` once (`registerClasses` runs exactly once per class; the resolver merges each class into the program once). The generic path must **not** mutate the template — the double-splice/void-field bug above is exactly what that distinction prevents.
- Private-field initializers need no new work: the `#x` literal (including the `#`) is the field name in both the declaration and `this.#x` access, so the desugared `this.#x = init` matches [ADR-00155](../adr/ADR-00155.md)'s existing storage slot.

## Side effects discovered

Two honest divergences from real JS, both disclosed in the class status pages, neither fixed here (each needs machinery beyond Stage 1's scope):

- **A field initializer can reference constructor parameters** (`class C { x = p; constructor(p: number) {} }` compiles and uses `p`). Real JS evaluates field initializers in a scope that cannot see constructor parameters. This falls out of lowering initializers into the constructor body, where the params are in scope. A faithful fix needs a separate initializer scope.
- **A field initializer referencing a *later* field reads the deterministic zero, not `undefined`** (`a = this.b; b = 5` gives `a === 0`). This is the existing [ADR-00157](../adr/ADR-00157.md) "no `undefined` sentinel on a concrete scalar" behavior, not new to this change.

Also: an unannotated field whose initializer is an expression shape `inferExprType` doesn't specifically recognize falls back to `i64` (the compiler-wide `number` default) — annotate the field to be explicit. `async`/generator/computed members and class expressions remain [TDD-00063](../tdd/TDD-00063.md) Stages 2–4.
