# TDD-00045: Raspberry Pi (aarch64 SBC) target — minimal boot image + GPIO

- **Status**: Not Started
- **Date**: 2026-08-09

## Context

[TDD-00036](TDD-00036.md) scoped a Raspberry Pi Pico target, which is a **freestanding** microcontroller: no OS, no libc, no filesystem. A Raspberry Pi (3/4/5, or any other aarch64 single-board computer) is a completely different category — it boots a real Linux kernel, has a real libc, and is already, today, a valid build target for this compiler in the same sense any other aarch64 Linux box is: `main.go` never emits an explicit `-target` and just shells to host `clang`, so a `klainmain`-compiled binary already runs correctly on Pi hardware once built there. Nothing about the language or codegen needs to change for that baseline case.

What's actually missing is two narrower, mostly independent things, both aimed at the same use case — small automation/robotics programs (e.g. a Pimoroni Trilobot-style rover) written in KlainMainLang and running as the only userspace program on a Pi:

1. A way to produce a **minimal bootable Pi image** — just enough kernel/firmware to boot, plus a compiled KlainMainLang binary set to run at boot — rather than a full Raspberry Pi OS install with a compiled binary dropped on top.
2. A **GPIO binding**, exposed as a TypeScript API and imported like any other stdlib module, since without it there's no reason to target Pi hardware specifically over any other Linux box.

Both are judged technically straightforward relative to this project's usual core-language work — the point of writing this TDD is to scope the two real design decisions (image build mechanism, GPIO binding shape) before starting, not because either is expected to be large.

This is explicitly a secondary, "why not cover more use cases" addition alongside this project's core-language priorities (see the project's own instructions on prioritization) — recorded per this project's standing rule that a new subsystem gets a design pass before implementation, not because it competes with modules/type-system/generics work for priority.

## Design

### Half 1: minimal bootable image via `docker buildx`

This project already has the load-bearing piece: `--static` (see [ADR-00032](../adr/ADR-00032.md), extended for `fetch`/RegExp in [ADR-00080](../adr/ADR-00080.md)/[ADR-00120](../adr/ADR-00120.md)) produces a statically-linked binary against musl, verified end-to-end in a real Docker `scratch` image (`docker/Dockerfile`, `docker/Dockerfile.fetch-test`, `docker/Dockerfile.regexp-test`). Producing an aarch64 static binary needs no new cross-compilation support in `klainmain` itself: `docker buildx build --platform linux/arm64` runs the *entire* existing three-stage Alpine build (Go compiler build → `klainmain --static` → copy into a minimal final stage) under QEMU emulation, on an x86-64 dev machine, unchanged. This sidesteps the cross-compile gap [TDD-00020](TDD-00020.md) (Windows) and [TDD-00036](TDD-00036.md) (Pico) both have to solve properly — here, "cross-compilation" is QEMU emulating the target CPU well enough to just run the native toolchain, not `klainmain` learning to emit a foreign target triple.

What's genuinely new is stage 3. Today's Dockerfiles end in `FROM scratch` because the target is "run this container anywhere Docker runs" — there's no boot process at all, `docker run` just execs the binary directly as the container's PID 1. A real Raspberry Pi boots hardware: it needs the Pi's own firmware blobs (`bootcode.bin`, `start*.elf`, device tree blobs) on a FAT boot partition, then a kernel, then something for the kernel to run as PID 1. Two sub-questions:

- **Kernel/firmware source.** Options: (a) the Raspberry Pi Foundation's own downstream kernel fork + firmware repo (`raspberrypi/firmware`, `raspberrypi/linux`) — most compatible, especially on older Pi models where mainline support has historically lagged; (b) a mainline kernel with a generic aarch64 defconfig, which has gotten meaningfully better Pi support on recent models/kernels but isn't uniformly verified across the whole Pi lineup; (c) a buildroot `raspberrypi*_defconfig` (buildroot already ships several Pi-model-specific defconfigs), which bundles the firmware/kernel/rootfs concern into one tool. (c) is the likely best fit for "minimal" — it's the same "build on an established tool for the hard, unrelated-to-language-design part" posture [TDD-00036](TDD-00036.md) already took toward `pico-sdk` — but unresearched in enough depth to commit to here.
- **What runs as PID 1.** The most literal reading of "boot straight to the executable" is the Linux kernel's own `init=/path/to/binary` command-line parameter, which replaces the entire init system with a single specified program — no systemd, no OpenRC, nothing. This maps directly onto "the compiled KlainMainLang binary is the only userspace program that ever runs," and is worth taking seriously as the default rather than a stretch case: it's a real, standard kernel feature, not a hack. The open risk is process-management edge cases a real init normally absorbs (reaping orphaned children, handling a crash/reboot cleanly) — for a program with no child processes and [TDD-00019](TDD-00019.md)'s existing `SIGINT`/`SIGTERM` handling, this may simply not matter, but isn't verified.

None of this touches compiler code. It's entirely a `docker/` directory addition (a new Dockerfile plus whatever image-assembly step turns the buildx output into a flashable `.img`) and documentation, mirroring how the existing `--static` Dockerfiles work today.

### Half 2: GPIO binding

Unlike the Pico ([TDD-00036](TDD-00036.md)), there's a real OS and kernel underneath, so this is not register-level bit-banging. Linux exposes GPIO to userspace two ways:

- **`/sys/class/gpio`** (sysfs) — the old interface, deprecated since Linux 4.8 and increasingly absent or restricted on modern kernels/distros. Not a good foundation for anything new.
- **The GPIO character-device ABI** (`/dev/gpiochipN`, via `libgpiod`) — the current, actively-maintained interface. This is the right target.

Binding shape: a small hand-written C shim linking against `libgpiod` (Alpine package `libgpiod-dev`, matching the existing Alpine-based static-build pattern), exposed as a new `emit_gpio.go`/`runtime_gpio.go` pair following this project's established per-domain file split, surfaced as a new TypeScript-facing module (naming TBD — plausibly `gpio`, imported the same way `fs`/`os`/`process` are today). This is the same "hand-written one-off binding, not worth waiting on general FFI" call [TDD-00036](TDD-00036.md) already made for the Pico's GPIO surface (see that document's Open Questions) — GPIO's real API surface is a handful of functions (open a line, set direction, read, write, maybe edge-detection/interrupts as a later stage) regardless of which board it's talking to.

A minimal first surface: open a chip/line, set direction (in/out), digital read, digital write. Edge detection/interrupts, PWM, and the I2C/SPI buses some robotics peripherals also need (again, see the Trilobot example) are real follow-on scope, deliberately not this document's minimal core — same "don't pre-solve unrelated problems in one document" posture [TDD-00036](TDD-00036.md) took toward its own out-of-scope list.

The "expose internals over REST or serial" idea from the original ask doesn't need new stdlib for the REST half — that's just an example program using the existing `http.listen` server plus the new `gpio` module. A serial half (talking over `/dev/ttyAMA0` or similar) is a real gap: today's `fs` module can read/write the device node as bytes, but real serial use needs `termios`-level configuration (baud rate, parity, flow control) that `fs` doesn't expose and that isn't scoped here — worth its own future TDD if it turns out to matter, not assumed solvable via `fs` as-is.

## Open questions

- **Buildroot vs. RPi Foundation fork vs. mainline kernel** for the boot image — not decided, see Design.
- **`init=<binary>` direct boot vs. a minimal real init** (e.g. BusyBox's) in front of the compiled binary — the former is architecturally cleaner for this use case but its edge-case behavior (crash/reboot handling) is unverified.
- **GPIO module naming and exact API shape** — not decided; should stay a small, additive surface (line open/direction/read/write) for a first pass rather than trying to cover PWM/I2C/SPI up front.
- **32-bit (`armv7`) Pi models** — explicitly deferred per the original ask; this document is aarch64-only.
- **Testing story** — no CI-friendly hardware target exists today, and QEMU's GPIO fidelity for Pi machine models is unresearched. May end up manual-only, like [TDD-00036](TDD-00036.md).
- **Whether this needs its own `docs/status/` page** (parallel to how other platform targets are tracked) once any part of it actually ships, per this project's standing documentation rules.
