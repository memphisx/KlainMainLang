# ADR-00609: Constant computed key in object destructuring

- **Relations**: Complements [ADR-00608](ADR-00608.md) (constant-key bracket access); reuses the TDD-00065 object-pattern codegen
- **Date**: 2026-09-01

## Context

Object destructuring rejected a computed key outright — `const { [k]: v } = obj`
was a parse error (`expected property name, got [`). For a fixed-shape object a
*constant* computed key (`{ ["a"]: v }`, `{ [0]: v }`) denotes exactly the field
a plain `{ a: v }` / `{ 0: v }` pattern would, so it can be supported with no
codegen change — mirroring the constant-key bracket access of ADR-00608.

## Decision

`parseObjectPatternProps` accepts a `[` computed key when it is a
**compile-time-constant string or number literal**: it parses `[lit]: name`
(with an optional `= default`) and records an ordinary `DestructProp` whose `Key`
is the literal's text — the same field name a non-computed key stores. Codegen
(`unpackObjectPatternInto`, which resolves each prop through `FieldIndex`) is
untouched.

A **runtime-valued** computed key (`{ [k]: v }` where `k` is a variable) is a
clean rejection: a fixed-shape struct has no runtime key lookup to bind against —
a dynamic `{ [k: string]: T }` object is the tool for runtime keys, and it is not
destructured this way. The key must also bind through `: name` (no shorthand for
a computed key), matching JS.

## Verification

`TestE2EObjectDestructuringComputedConstKey` (`{ ["a"]: x, ["b"]: y }` and a
numeric `{ [0]: first }`), matching Node v26, and
`TestE2EObjectDestructuringComputedRuntimeKeyRejected` (a variable key is a clean
error). The destructuring and parser suites still pass. A `= default` on a
computed key reuses the existing nullable-reference default path unchanged
(triggering on the compiler's `null` "not provided" stand-in, ADR-00158). Built
and verified on Mac (Apple Silicon).
