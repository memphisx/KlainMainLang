# TDD-00029: Array-of-arrays (nested array) storage representation

- **Status**: Implemented
- **Date**: 2026-08-05
- **Notes**: `.flat()`/`.flatMap()` followed as a direct follow-on

## Context

Split out of [TDD-00028](TDD-00028.md) (array/Map/Set/EventEmitter literals as general expressions) during that TDD's own implementation. TDD-00028's Open Questions speculated that fixing array literals as general expressions would, as a side effect, also unblock nested array literals (`[[1,2],[3,4]]`) for free — and with that, `.flat()`/`.flatMap()` (`docs/status/ARRAY-METHODS.md`'s two remaining ❌ rows). That speculation turned out to be wrong: it's a separate, real storage-representation gap, confirmed directly while implementing TDD-00028 (see that ADR's/TDD's own writeup — [ADR-00104](../adr/ADR-00104.md)).

Concretely: `const nested: number[][] = [[1,2],[3,4]]` (or the self-inferred `const nested = [[1,2],[3,4]]`) fails at the clang stage with `'%tN' defined with type '{ ptr, i64 }' but expected 'i64'` (or `ptr`, depending on the outer element's declared/inferred IR) — a genuine 16-byte-value-into-8-byte-slot type mismatch, not just a missing dispatch case. TDD-00028 added a clean, deliberate compile-time rejection for this case (`emitArrayLiteralAggregate`'s nested-array guard, `codegen/llvm/emit_arrays_core.go`) rather than leaving the confusing clang-stage error in place, but real support is out of its scope.

## Investigation

An array's backing buffer (`emitArrayLiteralData`/`emitSpreadArrayLitData`, `codegen/llvm/emit_arrays_core.go`) is a flat, `malloc`'d sequence of fixed-width slots, one `elemTy.Align()`-sized slot per element — correct and sufficient for any scalar or single-pointer element type (`number`, `string`, an object/class instance, a `Map`/`Set` handle — all exactly one machine word). A nested array's own value, however, is a `{ptr, i64}` **pair** (16 bytes on a 64-bit target) — the exact aggregate shape `emitArrayLiteralAggregate`/a function's own array-typed return value now produce (TDD-00028) — which cannot be written into or read back out of an 8-byte slot without either (a) widening every "outer" slot to 16 bytes whenever its own element type is itself an array (a genuine layout change, since `elemTy.Align()`/GEP indexing throughout `emit_arrays_*.go` currently assumes a uniform, scalar-or-pointer-sized slot), or (b) boxing: store one more level of indirection — each outer slot holds a plain `ptr` to a separately `malloc`'d 16-byte `{ptr, i64}` box, so the outer array's own slot width stays 8 bytes uniformly, at the cost of one extra heap allocation and one extra dereference per nested-array element access.

Every existing array consumer (`resolveArrayForHOF`, indexing/`emitIndexPtr`, `.length`, every HOF — `.map`/`.filter`/`.reduce`/etc. — `.slice`/`.concat`/`.reverse`/`.sort`/etc., `for...of`) currently assumes a uniform, non-nested element shape; none of them were audited for this TDD, since scoping that fully is exactly the point of writing this TDD before touching any of them.

## Design

Not designed here — this TDD exists to hold the problem statement and initial framing so it isn't lost, not to prescribe an implementation. Two real options surfaced during the Investigation above, worth weighing directly against each other before implementation starts:

- **(a) Widen outer slots when the element type is itself an array** — no extra indirection/heap allocation per access, but is a real layout change: `elemTy.Align()` (`codegen/llvm/types.go`) and every GEP call site that currently assumes `elemTy.IR`-width slots would need to branch on "is this a nested-array element" and use the 16-byte aggregate shape instead. Likely the more invasive option, but the more efficient one.
- **(b) Box nested-array elements behind one more pointer indirection** — every outer slot stays a plain, uniform `ptr` (consistent with every other pointer-shaped element type this compiler already has, e.g. `string[]`), at the cost of one `malloc(16)` + one extra load per nested element access. Likely the less invasive option (fewer call sites need to change — mainly just the element-read/write path, not every GEP/indexing site's width assumption), but adds real per-access overhead a genuinely hot nested-array loop would feel.

Whichever is chosen, `.flat(depth?)`/`.flatMap(fn)` (`docs/status/ARRAY-METHODS.md`) become natural, low-additional-cost follow-ons once nested arrays are real — that dependency (not a design decision of its own) is the one thing carried over from TDD-00028's original, since-corrected speculation.

## Open questions

- ~~Option (a) vs (b) above~~ Resolved: (b), boxing — confirmed `Type.IR`/`Type.Align()` already report a uniform 8-byte `"ptr"` slot for any array-typed `elemTy`, so boxing needed zero layout changes, only a new value shape for what a slot holds. See [ADR-00105](../adr/ADR-00105.md).
- ~~Whether `number[][]` needs to support arbitrary nesting depth~~ Resolved: boxing composes structurally to arbitrary depth for free (an outer array's slot holds a box pointer to an inner `{ptr,i64}` aggregate, regardless of whether that inner array's own element type is itself an array) — not artificially restricted to one level, though this pass's own tests only exercise two levels (`number[][]`/`string[][]`), not deeper.
- ~~Whether `.flat(depth?)`/`.flatMap(fn)` ship now that nested-array storage is real~~ Resolved: done, [ADR-00107](../adr/ADR-00107.md). `depth` is required to be a compile-time constant (a literal integer, or the bare `Infinity` identifier this compiler already recognizes elsewhere) rather than real JS's arbitrary runtime value — this compiler's array element types are static, so the result's own element type has to be knowable at compile time, and it depends on `depth`. `Infinity` flattens as deep as the receiver's own static type actually nests (no real unbounded value needed). `flatMap` has no `depth` parameter at all in real JS either, so it was unaffected by this question.
