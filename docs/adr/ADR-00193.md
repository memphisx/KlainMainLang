# ADR-00193: Nested destructuring patterns (TDD-00065 Stage 2)

- **Relations**: Implements [TDD-00065](../tdd/TDD-00065.md) Stage 2; extends [ADR-00192](ADR-00192.md) (Stage 1); builds on the destructuring codegen core from [ADR-00157](ADR-00157.md)/[ADR-00109](ADR-00109.md)
- **Date**: 2026-08-13

## Context

After [ADR-00192](ADR-00192.md) (Stage 1: destructuring in the for-of loop
variable), the next tracked gap in [TDD-00065](../tdd/TDD-00065.md) is nested
patterns — `const [[a, b], c] = m`, `const { inner: { v }, tag } = o`,
`const { coords: [x, y] } = w` — in every binding position: statement
declaration, for-of loop variable, and destructured function parameter. Each
was a clean parse rejection (`expected IDENT, got [`), since the pattern
element grammar only accepted a leaf identifier at each position.

Nested patterns are a real share of the remaining `dstr` corpus: in
`language/statements/for-of` alone, the leftover `expected IDENT, got [` (48) /
`got {` (36) after Stage 1 were overwhelmingly nested loop-variable patterns.

## Investigation

The pattern element grammar had, as of Stage 1, been factored into two shared
helpers — `parseArrayPatternElems` / `parseObjectPatternProps`
(`parser/parser_stmts.go`) — used by the declaration and for-of positions. The
codegen cores `unpackArrayPatternInto` (`codegen/llvm/emit_arrays_core.go`) and
`unpackObjectPatternInto` (`codegen/llvm/emit_objects.go`) already resolve each
position/field to a data-ptr (array) or object-ptr and bind a leaf `Symbol`.
Nesting is a natural recursion on both: parse a sub-pattern where a leaf name
was expected; in codegen, resolve the element/field to its own array/object
pointer and re-enter the matching unpack with the sub-pattern.

Two duplicate copies of the (Stage-1-era, non-shared) element grammar still
lived in the **parameter** parsers — `parser/parser_stmts.go`'s
`parseParamList` and `parser/parser_literals.go`'s arrow-parameter parser —
each hand-rolling the same holes/rename/`...rest` loop. Routing both through
the shared helpers removes that duplication and gives nested parameters for
free, since the parameter codegen (`emit_func.go`, `emitFunctionDeclAs`) already
funnels through the same recursive `unpack*PatternInto`.

The one genuinely new codegen concern is a nested **array** position past the
source's length (`const [[a, b]] = []`). Real JS throws (can't destructure
`undefined`); this compiler keeps the memory-safe "deterministic zero"
convention [ADR-00157](ADR-00157.md) established for a leaf position — an
out-of-bounds nested array element resolves to an empty array (`{null, 0}`,
whose zero length makes every sub-position itself deterministically zero), and
an out-of-bounds nested object element resolves to a stack-allocated zeroed
struct rather than a null pointer, so the recursive unpack never dereferences
null.

## Decision

1. **AST** (`ast/nodes.go`): add `SubArray []ArrayPatternElem` /
   `SubObject []DestructProp` to both `ArrayPatternElem` and `DestructProp`.
   Exactly one is set for a nested position; for an `ArrayPatternElem`, `Name`
   is `""` when a sub-pattern is present, so a plain `Name == ""` no longer
   implies a hole (sub-pattern fields are checked first).
2. **Parser** (`parser/parser_stmts.go`): make `parseArrayPatternElems` /
   `parseObjectPatternProps` recurse — an element position or a property value
   starting with `[`/`{` parses a nested sub-pattern (via a small
   `parseNestedPatternElem` helper for the array case). Route both parameter
   parsers (`parseParamList` and the arrow parser in `parser_literals.go`)
   through these shared helpers, deleting the two duplicated inline copies.
3. **Codegen**: `unpackArrayPatternInto` dispatches a nested element to a new
   `unpackNestedArrayElem` (in-bounds/out-of-bounds resolve, then recurse);
   `unpackObjectPatternInto` handles a nested property inline (load the field's
   array `{ptr,i64}` or object pointer, recurse). A `= default` combined with a
   nested pattern is a clean rejection, not silently ignored.
4. **Free-variable / bound-name scans** (`codegen/llvm/emit_func.go`): add
   recursive `collectArrayPatternNames` / `collectObjectPatternNames` and use
   them for both the for-of loop-variable scan and `addParamBoundNames`, so a
   nested-bound name correctly shadows an outer variable instead of being
   scanned as a closure capture.

## Implementation notes

- Files touched: `ast/nodes.go`, `parser/parser_stmts.go`,
  `parser/parser_literals.go`, `codegen/llvm/emit_arrays_core.go`,
  `codegen/llvm/emit_objects.go`, `codegen/llvm/emit_func.go`.
- Because the for-of loop variable (Stage 1) and both parameter positions all
  already call the shared unpack cores, making those cores recursive extended
  nesting to every position at once — the only per-position work was parser
  routing.
- Net −130 lines of duplicated parameter pattern-parsing across the two
  parsers.

## Side effects discovered

- **Defaults on a nested position** (`[[a] = [1]]`, `{ k: { a } = d }`) are not
  supported — a clean compile-time rejection. Real but narrow; deferred.
- **Nested patterns in the *assignment* form** (`[[a, b], c] = expr`, not a
  declaration) remain unsupported — assignment destructuring is a separate code
  path ([ADR-00160](ADR-00160.md), `emit_exprs_assign.go`) this stage didn't
  touch; `language/expressions/assignment/dstr` is unchanged as a result.
- A pre-existing, unrelated gap surfaced while writing test cases: arithmetic
  on an array operand (`arr + n`) emits invalid IR (`add ptr …`) instead of a
  clean type error — general operator type-checking, not destructuring, and out
  of scope here.
