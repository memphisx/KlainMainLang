# ADR-00557: JSDoc Object.<K,V> index map now works (status was stale)

- **Relations**: Implements TDD-00130, Extends TDD-00125
- **Date**: 2026-09-01

## Context

The jsdoc status page listed `Object.<K, V>` (the Closure index-map type) as
`missing`, with a caveat that it normalized to `Record<K, V>` but "per-key
field/index access on a `Record` isn't supported (index signatures are a
separate ❌)." That caveat predates index-signature support, which has since
shipped (TDD-00130/ADR-00390): `Record<K, V>` and `{ [k: string]: T }` are
map-backed with real `d[key]` read/write. So `Object.<K, V>` already works
end-to-end — the row was stale.

## Investigation

`normalizeClosureType` (parser/jsdoc_types.go) already rewrites `Object.<K, V>`
→ `Record<K, V>` (and `Object<...>` likewise), covered by
`jsdoc_types_internal_test.go`. A fresh repro confirmed the end-to-end path:

```
/** @type {Object.<string, number>} */
const scores = { alice: 90 };
scores["bob"] = 85;            // index-signature write
console.log(scores["alice"] + scores["bob"]);  // 175
```

compiles and runs, as does the equivalent explicit `Record<string, number>`.

## Decision

Flip the jsdoc `Object.<K, V>` row from `missing` to `implemented` and replace
the stale caveat with a note pointing at the index-signature support that
backs it. No code change — this is a documentation correction plus an E2E test
to lock the behavior.

## Implementation notes

Added an `Object.<string, number>` case to `TestE2EJSDocTypeExpressions`
(read + index-signature write). The normalization itself was already tested at
the parser layer.

## Side effects discovered

None.

## Verification

`TestE2EJSDocTypeExpressions` (now including the `Object.<K,V>` case) passes;
manual repros of both `Object.<string, number>` and `Record<string, number>`
run correctly. Built and verified on Mac (Apple Silicon).
