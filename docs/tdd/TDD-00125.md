# TDD-00125: JSDoc type annotations beyond `@type` (`@param`, `@returns`, …)

- **Status**: Implemented (Stages 1–6)
- **Date**: 2026-08-26

## Context

This compiler already consumes two JSDoc annotations: `@type {T}` (a per-binding
type override, including the `int8..uint64`/`float32`/`float64` width keywords
that are this project's own extension) and `@erased` (generic single-body
compilation). Everything else TypeScript recognizes in its own JSDoc mode
([the handbook reference](https://www.typescriptlang.org/docs/handbook/jsdoc-supported-types.html))
is parsed into a generic tag list by `jsdoc/parser.go` and then ignored.

The most valuable missing piece is typing an **untyped function** from its
JSDoc — the classic "typed JS" workflow:

```js
/**
 * @param {number} a
 * @param {number} b
 * @returns {number}
 */
function add(a, b) { return a + b }
```

Today `a`/`b` fall through to `registerFunctions`' bare-parameter default
(`number`, since Stage-1 of TDD-00123 made that a double) and the `@param`
type is dropped — so a `@param {int32}` or `@param {string}` has no effect,
and there is no way to give an unannotated parameter any type but the default.

`@type` already does the hard part (its value string flows into the same
`TypeAnnotation{Name, Source:"jsdoc"}` seam a TS annotation produces, so it
inherits whatever the type resolver understands — bare names, the width
keywords, and `T[]`). `@param`/`@returns` are the same mechanism keyed by
parameter name / applied to the return slot.

## Design

### Stage 1 — `@param` / `@returns` typing (this stage)

`jsdoc.Comment` gains:
- `ParamType(name string) string` — the type body of the `@param {T} name`
  whose name matches, or `""`.
- `ReturnType() string` — the type body of `@returns`/`@return`, or `""`.

Both share `stripJSDocDecorations`, which removes the JSDoc-only markers a type
body can carry so the remainder is the plain type string the existing resolver
already handles:
- a leading `...` (varargs/rest — `@param {...number}`) — signals a rest param,
  stripped from the type;
- a trailing `=` (optional — `@param {number=}`) — signals optional, stripped.

`@param`'s *name* field also accepts the JSDoc-optional bracket forms
(`[name]`, `[name=default]`); the brackets/default are stripped to recover the
bare name.

The parser threads the leading doc comment into `parseFunctionRest`. After the
parameter list is parsed, for each parameter that has **no inline annotation**
and **no destructuring pattern**, a matching `@param` supplies
`Type = &ast.TypeAnnotation{Name: <stripped type>, Source: "jsdoc"}` — identical
to what an inline annotation or `@type` produces, so codegen needs no change.
Likewise, when the function has **no** inline `: RetType`, `@returns` fills it.

**Precedence.** An inline TS annotation wins — `@param` only *fills in* an
otherwise-untyped parameter/return (the real "typed JS" use case). This differs
deliberately from `@type`-on-a-variable, which overrides its TS annotation:
there, `@type` is the single source of truth for one binding; here a function
may legitimately carry both inline types and stray doc comments, and silently
overriding an explicit `: T` with a doc typo would be surprising.

**Type-expression grammar** is exactly what `@type` supports today (bare type
names, the width keywords, `T[]`); the richer Closure/JSDoc forms
(`Array.<T>`, `Object.<K,V>`, `function(...)`, `?T`/`!T` semantics, `import(...)`)
are their own later stage, tracked as ❌ in the new status page.

### Later stages (tracked, not built here)

Staged by leverage (see `docs/status/JSDOC.md` for the per-tag ledger):

- **Stage 2 — `@typedef` / `@callback`.** Named type aliases and function-type
  aliases declared in a comment, usable wherever a type name is.
- **Stage 3 — `@template`.** JSDoc generics (maps to the existing `<T>`
  monomorphization / `@erased` machinery).
- **Stage 4 — Closure type-expression grammar.** `Array.<T>`, `Object.<K,V>`,
  `function(...)`, `?T`/`!T`, `*`/`?`, the legacy `String`→`string` synonyms —
  a real sub-parser for the JSDoc type language, which also upgrades `@type`.
- **Stage 5 — class/visibility tags.** `@extends`/`@implements`/`@this`,
  `@public`/`@private`/`@protected`/`@readonly`/`@override`/`@enum` on classes.
- **Stage 6 — `import("…")` types and `@satisfies`.**

## Open questions

- **Rest `@param {...T}` onto a real `...rest` parameter.** Stage 1 records the
  base type and the rest marker, but binding a `@param {...number}` to a
  body that reads `arguments` still needs the `arguments` object (unsupported —
  a separate gap). A declared `...rest: number[]` parameter is the supported path.
- **Should a `@param` naming a nonexistent parameter warn?** TS ignores it.
  Stage 1 also ignores it (no error) to stay lenient toward real-world doc drift.
