# ADR-01078: `fs.fchmodSync`, `fs.statfsSync`, `process.umask()`

- **Relations**: Extends ADR-00498 (fd ops), ADR-01077 (the osinfo sidecar)
- **Date**: 2026-09-22

## Context

BACKLOG §2, the "cross-platform features that block a Windows row" bullet naming `process.umask()`,
`fs.fchmodSync` and `fs.statfsSync` (`GetDiskFreeSpaceExW`). None existed on any host.

## Investigation

- `chmodSync` is `chmod` in the IR (`runtime_fs.go` `__kml_fs_chmod`); on Windows the win32 shim defines
  `chmod` as the read-only-attribute model (`win32fs.c`). The fd ops (`fsync`/`ftruncate`/`fstat`) are IR
  wrappers over libc symbols the shim also owns, resolving the fd to a HANDLE through `kfd_handle`. `fchmod`
  fits the same mould: libc on POSIX, a new shim entry (`FileBasicInfo` get/set — libuv's `fs__fchmod` uses
  `FileBasicInformation`) on Windows.
- `struct statfs` is a large platform struct (Linux `<sys/vfs.h>`, Darwin `<sys/mount.h>`) — reproducing its
  layout in IR is exactly what the C-sidecar rule exists to avoid, so it lives in `osinfo.c` (ADR-01077), which
  is already the host-information sidecar. On Windows libuv's `fs__statfs` is `GetDiskFreeSpaceW` on the
  volume root: `bsize = sectors_per_cluster × bytes_per_sector`, `blocks/bfree/bavail` are cluster counts,
  `type/files/ffree` are `0`. Node 24 also reports `frsize` (the cluster size on Windows, `f_frsize` on
  Linux, `f_bsize` on Darwin where the struct has no fragment size).
- A first Windows probe accepted a nonexistent path: `GetVolumePathNameW` answers for any path on an existing
  drive. Node throws `ENOENT: no such file or directory, statfs '<path>'` — libuv probes the path first, so the
  sidecar does too (`GetFileAttributesW`).
- `process.umask()` with no argument is libuv's `umask(0)` + restore; with one, `umask(mask)` returning the old.
  The UCRT exports only `_umask`; Node on Windows answers `0` by default and a set value is inert for created
  files — both reproduced by calling the CRT.

## Decision

- `runtime_fs.go`: `ensureFsFchmod` → `@__kml_fs_fchmod(fd, mode)` over `fchmod`, throwing the fd-shaped fs
  error (`EBADF: bad file descriptor, fchmod`, `err.path` undefined); `ensureFsStatfs` →
  `@__kml_fs_statfs_checked(path, out)` over the sidecar's `__kml_fs_statfs`, throwing the path-shaped
  error with syscall `statfs`.
- `emit_fs.go`: `emitFsFchmodSync`, `emitFsStatfsSync` (the result object is `StatFsType()` — eight `i64`
  fields in the sidecar's `out[8]` order `type, bsize, frsize, blocks, bfree, bavail, files, ffree`, so the
  struct is filled directly), `emitProcessUmask` (`umaskSymbol()` picks `_umask` on Windows).
- `win32fs.c`: `fchmod` (asm-aliased like the other POSIX names) — `KFD_PLAIN` fds only, `EBADF` otherwise.
- `osinfo.c`: `__kml_fs_statfs` for both platforms.
- Resolver `fs` exports gain `fchmodSync`/`statfsSync`; `emit_call.go`/`emit_exprs_types.go` dispatch and
  type the three.

## Implementation notes

`codegen/llvm/runtime_fs.go`, `emit_fs.go`, `emit_call.go`, `emit_exprs_types.go`, `emitter.go`,
`osinfosrc/osinfo.c`, `win32src/win32fs.c`, `resolver/virtual_modules.go`. The `{ bigint: true }` option to
`statfsSync` is accepted and ignored (numbers either way) — recorded as the row's caveat.

## Side effects discovered

None.

## Verification

Windows, byte-identical to Node 24: the fchmod read-only round trip through `fstatSync().mode`, the `EBADF`
message, `statfsSync(os.tmpdir())`'s key order and the `ENOENT … statfs '<path>'` error, `process.umask()`
get/set/restore. Linux (Docker, glibc x86-64): `statfsSync('/')` with all eight fields populated (`type`
`0x794c7630` overlayfs), `fchmodSync(fd, 0o600)` → `600`, `umask()` → `022`, and a file created under
`umask(0o077)` is mode `600`. E2E: `tests/fs_statfs_test.go` (five tests).
