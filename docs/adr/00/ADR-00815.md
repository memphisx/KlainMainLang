# ADR-00815: `-webview=<backend>` selection flag (Stage 1 — plumbing)

- **Relations**: `Implements TDD-00144`

- **Date**: 2026-09-09

## Context

`klain:webview` (TDD-00142) compiles over the *system* browser engine —
WKWebView on macOS, WebKitGTK on Linux, WebView2 on Windows — always, with no
way to choose a different engine. TDD-00144 designs an opt-in `-webview=<backend>`
axis (mirroring `-crypto`/`-bigint`) for the Chromium engines (CEF, QtWebEngine)
and, per TDD-00146 Stage 3, a Sailfish Gecko/embedlite backend. Those shims are
substantial per-engine work; this ADR lands only Stage 1: the selection
mechanism itself, so the flag exists and validates, `system` stays the default
and only working value, and an opt-in backend rejects cleanly instead of
mis-linking.

## Investigation

The backend-flag precedent is `-crypto` (`main.go` validation switch →
`em.SetCryptoBackend` → `CryptoBackendSource(backend)` / `LocateCrypto(backend)`
selected in `EmbeddedCSources`). Webview had no backend parameter: `WebviewSource()`
and `LocateWebview()` were argless (`codegen/llvm/webview.go`), called from
`embedded_c.go:110` under `e.UsesWebview()`, and the Windows precompile path
(`webview_win32.go:48`). The test build path mirrors this in
`tests/compiler_test.go:appendWebview`. The emitter had `cryptoBackend`/
`bigintBackend` fields but none for webview.

## Decision

Thread a backend string, defaulting to `system`, through the same seams:

- **Flag**: `-webview` (default `"system"`) in `main.go`, validated in a switch
  alongside `-crypto`: `system` ok; `cef`/`qt`/`sailfish` recognized (so scripts
  can pin one now) but not yet built; anything else is `unrecognized -webview
  value`. Wired via `em.SetWebviewBackend(*webviewBackend)` on both the entry and
  imported-island emitters.
- **Emitter**: a `webviewBackend` field + `SetWebviewBackend` / `WebviewBackend()`
  (the latter resolving `"" → "system"`), copying the `cryptoBackend` shape.
- **Selection**: `LocateWebview(backend)` and `WebviewSource(backend)` take the
  backend. `system`/`""` keep the existing per-platform behavior; `cef`/`qt`/
  `sailfish` return a clean *"not yet implemented — only -webview=system … is
  currently built"* error from `LocateWebview`; an unknown value returns an
  *"unrecognized webview backend"* error. `EmbeddedCSources` passes
  `e.WebviewBackend()`; because `LocateWebview` runs only under `e.UsesWebview()`,
  a non-`system` backend is rejected only when a program actually opens a webview
  — a plain CLI passing `-webview=qt` is unaffected, while the unknown-*name*
  check in `main.go` fires regardless.

The clean-rejection message lives in `LocateWebview` (single source of truth),
surfaced by the existing `EmbeddedCSources` error path (`main.go:293` fatal).

## Implementation notes

Files: `main.go` (flag, validation switch, two `SetWebviewBackend` call sites),
`codegen/llvm/emitter.go` (field + accessors), `codegen/llvm/webview.go`
(`LocateWebview`/`WebviewSource` take `backend`, dispatch), `webview_win32.go`
(passes `"system"`), `tests/compiler_test.go` (`appendWebview` passes
`em.WebviewBackend()`; two Windows-only test callers pass `"system"`).

No behavior change for existing builds: with the flag unset or `system`, the
binary is byte-for-byte the size it was (verified — 127032 bytes for
`examples/webview/bindings.ts` with and without `-webview=system`).

## Side effects discovered

None. The per-backend embedded-shim slot the TDD Stage 1 exit criterion calls
for is the `WebviewSource(backend)` dispatch; the actual CEF/Qt/Sailfish shims
(and their `Locate*` link recipes + resource bundling) are Stages 2–3, untouched
here.

## Verification

`go build`, `go vet ./...`, `make status-check` green on macOS (Apple Silicon
M4). New E2E test `TestE2EWebviewBackendFlag` (`tests/webview_test.go`) drives the
real CLI: `-webview=bogus` → unrecognized (parse-time, plain program);
`-webview={cef,qt,sailfish}` on a webview program → the not-yet-implemented
rejection; `-webview=system` → compiles a real binary (WKWebView on this host,
skips cleanly where the system engine's dev packages are absent). Existing
`TestE2EWebview*` suite still green.
