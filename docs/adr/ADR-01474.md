# ADR-01474: `for…of` over a plain iterator object

- **Relations**: Extends ADR-01471
- **Date**: 2026-10-08

## Context

Writing `klain:sync`'s `Channel<T>` in TypeScript (ADR-01471), its
`[Symbol.iterator]()` returned the usual iterator object,
`{ next(): IteratorResult<T> { … } }`, and `for (const v of ch)` failed to
compile: "[Symbol.iterator]() must return a class instance with a next()
method". JavaScript code writes iterators this way all the time.

## Investigation

- A class whose `[Symbol.iterator]()` returns an object literal, and an
  object literal whose `[Symbol.iterator]()` does, both failed in `for…of`
  (`emitForOfSymbolIterator` and `emitForOfObjectSymbolIterable`,
  codegen/llvm/emit_generators.go). Each accepted only a generator or a
  class instance, whose `next()` result it reads at fixed struct offsets.
- Spread, `Array.from` and array destructuring of the same iterables
  already worked, and so did calling `it.next()` by hand and reading
  `done`/`value` — only the loop's lowering lacked the general case.

## Decision

`emitForOfIteratorObject`: for an iterator of any other representation,
keep the iterator and each result in hidden locals and run the protocol
through the ordinary expressions — `it.next()`, then the result's `done`
(its truthiness) and `value` — binding the value (awaited with
`for await`) to the loop variable or pattern as the other loops do. Both
the class and the object-literal `[Symbol.iterator]` paths take it; the
async protocol keeps its own shapes.

## Implementation notes

codegen/llvm/emit_generators.go; tests/generators_test.go. The loop's
labels come from the caller, so `break`, `continue` and labelled `continue`
reach it as for every `for…of`.

## Side effects discovered

None.
