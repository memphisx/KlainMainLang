# ADR-01563: A declaration's `this` parameter is never one of its signature's parameters

- **Relations**: Extends ADR-01562
- **Date**: 2026-10-10

## Context

`examples/function_expressions/call_apply.ts` produced invalid IR once
identifiers and calls took their type from the checker: `bump.bind(counter)`
was typed with an extra parameter. The function is declared
`function bump(this: Counter, by: number)`.

## Investigation

The parser keeps a `this:` parameter out of `Params` and records it in
`Program.ThisParams`. The checker's `signatureType` reads it from there as
the signature's `ThisType`. Code generation later inserts `this` at the
head of the declaration's `Params` (`maybeAddThisParam`, the receiver slot
`f.call(obj, …)` passes). The checker builds signatures lazily, so a
signature built after that insertion counted `this` twice: once as
`ThisType` and again as the first ordinary parameter. Mapped to a
representation, the function took `(Counter, Counter, number)`, and
`bind` kept the extra `Counter`.

tsc keeps the `this` parameter apart from the parameter list
(`thisParameter`). `this` is a reserved name, so a parameter with that
name can only be the this-parameter.

## Decision

`signatureType` drops a leading parameter named `this` from the list it
reads. `ThisType` still comes from `Program.ThisParams`.

## Implementation notes

`checker/symbols.go` (`signatureType`).

## Side effects discovered

None.

## Verification

`examples/function_expressions/call_apply.ts` matches Node (Mac). Checker
unit tests pass.
