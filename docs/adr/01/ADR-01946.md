# ADR-01946: Side tables keyed by identity

- **Relations**: Implements TDD-00230
- **Date**: 2026-10-28

## Context

Phase 5 says no table is keyed by an object's address: identity goes through `kml_id_hash` (ADR-01939), so a moving collector can change how identity is computed in one place. Two runtime tables still hashed the address themselves:

- The level table (frozen, sealed, non-extensible) for objects without a header word, such as a RegExp's host record. It mixed `o >> 3` directly.
- The property-attribute records of `Object.defineProperty` (`propattr.c`). They lived in a number-keyed `Map` whose key was the object's address cast to an integer, so both the hash and the equality were the address.

## Decision

- `collections.c` has one side-table shape, `kml_side`: open addressing, grown at half full, hashed through `kml_id_hash`, compared by pointer, and pinned under `-mm=gc` as before. The level table and a new property-attribute table are two instances.
- `propattr.c` reads and sets its record through `__kml_pattr_rec_get`/`__kml_pattr_rec_set` on that table. The number-keyed `pattr_map` is gone.
- Two tables stay keyed by address, deliberately:
  - the typed-array view registry (`views.c`), which maps a view's interior data address to its buffer. That is an address lookup, not identity; a moving collector updates it.
  - RegExp's optional-group table, which is keyed by native PCRE code, not managed memory.

## Consequences

- With `kml_id_hash` still the address, behaviour is unchanged.
- Verified on macOS (Apple Silicon): `defineProperty`/freeze/seal/extensible tests and the sloppy-write tests pass; a probe defining attributes on 300 objects and sealing 200 RegExps matches Node in the default and `-mm=gc` modes.
