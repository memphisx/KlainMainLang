# ADR-01847: An array literal asserted to tuples is built and typed as those tuples

- **Relations**: `Implements TDD-00230` (P3.3: the checker answers what inferExprType did)
- **Date**: 2026-10-21

## Context

- `[[1, "x"]] as [number, string][]` and `[["k", "v"]] as [string, string][]` assert an array of tuples. `resolveType` gives that annotation an array of headerless tuple structs.
- Emission built the literal by its own shape, not by the assertion. It returned the value unconverted while typing the assertion as the tuple array, so either way the value and its type disagreed:
  - the mixed literal was built with boxed union elements and segfaulted when read as tuples;
  - with ADR-01844's rule answering the literal as the asserted tuples, the one-kind literal was answered as tuples while the assertion itself was answered `string[][]`, and segfaulted the other way round.
- The gate caught the second case: `examples/fetch/fetch_request_init.ts` passes `headers: [['X-Trace', 'abc']] as [string, string][]`, and `Request` read it as garbage ("element access through `any` on an array whose element type is not representable").
- The oracle maps a checker tuple to a struct only when told to (`reprCtx.tuples`). Otherwise it assumes a tuple the checker inferred, such as `await Promise.all([a, b])`, and answers the array codegen builds of its one element kind. An assertion's or a field's tuple was answered that way although its storage is the struct.

## Decision

- `emitAsExpression` builds an array literal asserted to an array of tuples with the assertion as its hint (`emitExprWithObjectHint`), as it already did for an `any[]` element and an empty literal. Each element literal is then one of those tuples.
- The oracle answers an assertion whose annotation names a tuple with that annotation's struct layout (`AnnotationType`, `typeNodeHasTuple`).
- A member read of a field holding tuples takes the field's type from the layout its receiver holds (the binding's storage through `heldIdent`, else the receiver's answer).

## Consequences

- `TestE2EAssertedTupleArrayLiteral` reads a mixed and a one-kind asserted tuple array typed, through `any`, through `Object.fromEntries` and through an object literal's field, and matches Node.
- Verified on Apple Silicon (targeted tuple, entries, `Request`/`Headers`, assertion and object-literal tests; `fetch_request_init` against the httpbin-lite fixture on DeskMini follows in the gate).
