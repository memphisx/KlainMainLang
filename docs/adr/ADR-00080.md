# ADR-00080: Fix `-mm=gc` startup crash on Ubuntu's `libgc-dev` build

- **Relations**: Extends [ADR-00071](ADR-00071.md), which introduced `-mm=gc` and only ever exercised it against Homebrew's `bdw-gc` build on macOS/arm64.
- **Date**: 2026-07-30

## Context

GitHub Actions' Release workflow (`.github/workflows/release.yml`, `ubuntu-latest`) started failing `go test ./...` on every push since [ADR-00071](ADR-00071.md) ("Boehm GC mode") landed. The CI log showed three failures, all `-mm=gc`-only:

```
--- FAIL: TestE2EGCModeCorrectnessUnderChurn (1.19s)
    memory_gc_test.go:45: run: signal: aborted (core dumped)
--- FAIL: TestE2EGCModeBoundsMemory (0.18s)
    memory_gc_test.go:79: run under /usr/bin/time: exit status 134
        Command terminated by signal 6
--- FAIL: TestE2EHTTPListenGCModeConcurrentChurn (5.32s)
    memory_gc_test.go:118: server never started listening on 127.0.0.1:8952
```

All three passed locally on macOS/arm64 (Homebrew's `bdw-gc`), so this was specific to Ubuntu's `libgc-dev` package (apt) — a build/platform difference [ADR-00071](ADR-00071.md) never tested against, since that work happened entirely on macOS.

## Investigation

Reproduced with Docker (`ubuntu:latest`, arm64, matching CI's Ubuntu — GitHub's runner is x86-64 but the bug turned out to be platform/libc-behavior driven, not architecture-driven, and did reproduce this way) rather than guessing blind:

- `go test ./tests/ -run TestE2EGCMode...` inside the container reproduced all three failures exactly.
- Running the compiled binary directly surfaced the real abort message, not shown by `go test`'s `signal: aborted`: **`Exclusion ranges overlap`** — a real Boehm GC `ABORT()` string (`os_dep.c`, `GC_exclude_static_roots_inner`), fired when two internally-tracked root-exclusion ranges partially overlap without one containing the other.
- Isolated the bug completely outside this compiler: a ~15-line C program linking `-lgc`, replacing `malloc`/`calloc`/`realloc`/`free` exactly like `codegen/llvm/gcsrc/gcshim.c` did, aborted with the same message — even with **zero** application-level allocations (`n=0` in a loop bound still aborted). This ruled out allocation volume/churn as the trigger, pointing instead at the shim's `malloc` override itself.
- `gdb -batch -ex run -ex bt` on the minimal repro showed the abort originates from inside `GC_init()` itself: `GC_init()` calls glibc's `pthread_getattr_np()` to auto-detect the initial thread's stack bounds, which calls `fopen("/proc/self/maps", ...)`, which mallocs a stdio buffer — and since this shim makes `malloc` the *only* definition of that symbol in the whole link, that allocation reenters `GC_malloc()`/`GC_init()` while the first `GC_init()` call is still mid-setup. The nested `GC_init()` re-registers the same static-data root range a second time with a slightly different computed boundary (heap already grown), which is what corrupts the exclusion-range bookkeeping.
- `gc.h` (Ubuntu's `libgc-dev` package, version `8.2.12-1`) documents `GC_stackbottom` as safe and cheap to set explicitly "prior to calling any GC_ routines" — doing so makes `GC_init()` skip the auto-detection path (and thus the crashing `pthread_getattr_np` call) entirely. Verified in the minimal repro: setting `GC_stackbottom` from `__libc_stack_end` (glibc's own record of the initial thread's true stack top, populated by the dynamic linker before any user code runs, so always valid this early) before `GC_INIT()` fixed both the churn test's abort and — separately — a segfault reproduced the same way for the `http.listen` concurrent-fiber test (`TestE2EHTTPListenGCModeConcurrentChurn`), which crashed one frame deeper in the same `pthread_getattr_np` path, this time triggered by `libp11-kit.so`'s own constructor (a transitive dependency via libcurl → GnuTLS) calling `newlocale()` → `malloc()` **before** this shim's own `__attribute__((constructor))` had run at all.
- That last point ruled out the first fix attempt: setting `GC_stackbottom` only inside `__kml_gc_ctor`. ELF runs a shared object's own constructors before the executable that (transitively) depends on it, regardless of any `__attribute__((constructor(N)))` priority put on the executable's constructor — priority only orders constructors *within* one object's `.init_array`, not across objects. Since `libp11-kit`'s constructor is a dependency of this compiler's output whenever `fetch`/`http.listen`'s TLS support pulls in GnuTLS, its constructor unconditionally runs first and can be the very first `malloc()` call in the process — before `__kml_gc_ctor` ever executes.
- A second fix attempt (a small static bump allocator absorbing every pre-init `malloc`/`calloc`/`realloc`/`free` call until `GC_INIT()` returns) worked for the churn test but not the `http.listen` one: `pthread_getattr_np`'s `/proc/self/maps` read grows its buffer in a doubling loop that can outgrow any small fixed budget, and a naive bump allocator has no way to track true per-block sizes for `realloc`, both of which showed up as a segfault with the bump buffer's address appearing directly in glibc's `pthread_attr_setaffinity_np` frame. Discarded once the simpler `GC_stackbottom` fix proved sufficient on its own — no bump allocator needed at all.

## Decision

Set `GC_stackbottom` from `__libc_stack_end` lazily, on the first call into `malloc`/`calloc`/`realloc`/`free` (not only from the constructor), guarded by a one-shot flag so it's cheap on every call after the first. This covers both call orderings — this shim's own constructor running first (the common case), and a transitive dependency's constructor calling `malloc()` first (the `libp11-kit` case) — without needing to reason about or control ELF constructor ordering across objects at all. `#if defined(__linux__)` scopes the fix to Linux only: `__libc_stack_end` is glibc-specific, and macOS's Homebrew `bdw-gc` build was never observed to hit this bug (its `GC_init()` presumably doesn't take the same `pthread_getattr_np`-via-malloc path, or glibc-specific `/proc/self/maps` parsing simply doesn't exist there).

Rejected alternatives:
- **Constructor priority (`__attribute__((constructor(101)))`)** — doesn't help; the failure mode is cross-object ordering (dependency-before-dependent), which priority annotations can't affect.
- **Bump allocator for pre-init calls** — works for the simple case but not the `pthread_getattr_np`/`/proc/self/maps` growing-buffer pattern without an unboundedly large static buffer, and can't implement `realloc` correctly without tracking real block sizes. More complex and still incomplete versus the `GC_stackbottom` fix, which sidesteps the problem instead of working around it.
- **`dlsym(RTLD_NEXT, "malloc")` to obtain and delegate to the real libc allocator for pre-init calls** — would work, but is meaningfully more code (recursion guard around `dlsym`'s own internal allocation, tracking which pointers came from which allocator so `free()` routes correctly) for a problem the documented `GC_stackbottom` mechanism already solves in ~10 lines.

## Implementation notes

- `codegen/llvm/gcsrc/gcshim.c` — added `ensureGCStackbottomSet()` (idempotent, checked at the top of every shim function and from `__kml_gc_ctor`), and the `#if defined(__linux__)` block declaring `extern void *__libc_stack_end __attribute__((weak));` (weak so the link still succeeds if, on some other libc, the symbol doesn't exist — guarded by a `NULL` check before use).
- No Go code changed — this is a pure C-source fix inside the embedded shim (`codegen/llvm/gcshim.go`'s `//go:embed`), so no codegen, CLI flag, or test-harness changes were needed beyond what already existed.
- `GC_stackbottom` is a deprecated-but-still-exported symbol in current Boehm GC headers (`gc.h` marks it `GC_ATTR_DEPRECATED`, in favor of `GC_set_stackbottom`/`struct GC_stack_base`); kept using the plain global since `codegen/llvm/emitter.go:469` and `codegen/llvm/runtime_http.go`/`runtime_fetch.go` already reference `@GC_stackbottom` directly at the LLVM IR level for the fiber-swap mechanism from [ADR-00071](ADR-00071.md) — using the same symbol here keeps both fixes consistent with each other rather than mixing two different Boehm APIs for stack-bottom management.

## Side effects discovered

None left unfixed — all three CI failures traced to the same root cause and are fixed by the one change.

## Verification

- Reproduced all three original CI failures in a `ubuntu:latest` Docker container (`apt-get install clang libcurl4-openssl-dev libgc-dev golang-go`) before making any change, confirming the repro matched CI exactly.
- After the fix, in the same container: `go build -o klainmain .`, `go vet ./...`, and `go test ./...` (including `TestE2EGCModeCorrectnessUnderChurn`, `TestE2EGCModeBoundsMemory` with `/usr/bin/time` installed, and `TestE2EHTTPListenGCModeConcurrentChurn`) all pass; `make examples` — 67 passed, 0 failed.
- Re-ran the same three `-mm=gc` tests natively on macOS/arm64 (Homebrew `bdw-gc`) to confirm the Linux-only `#if` guard leaves existing macOS behavior unchanged — all pass, as before this fix.
