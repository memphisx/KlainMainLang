# ADR-01494: `[Symbol.iterator]` on builtin iterables

- **Relations**: Extends TDD-00230
- **Date**: 2026-10-09

## Context

`arr[Symbol.iterator]()` failed to compile ("an array has no method
'@@iterator'"), as did the same call on a typed array, Set, Map or
string. `(s as any)[Symbol.iterator]` on a string was `undefined`.

## Investigation

- `x[Symbol.iterator]()` reaches the call path as a call of `@@iterator`
  (`indexCalleeAsMember`). Only classes declaring it, and boxes, had one.
- A dynamic read of `@@iterator` answered arrays and iterable host boxes,
  not strings.
- While checking the Set form, `const it = new Set([5]).keys();
  it.next()` at module level crashed (a pre-existing segfault). The
  module global's type came from inferring `new Set([5])` without its
  element, which inference fixed at the string default, so the iterator
  read numbers as string pointers.

## Decision

- `x[Symbol.iterator]()` on a builtin iterable is the method it is
  (`builtinIteratorCall`): `values()` for an array, typed array or Set,
  `entries()` for a Map, and `[...s].values()` for a string (its code
  points). Emission, inference and both declaration paths use it.
- A dynamic `@@iterator` read on a string box is an iterator method over
  its code points (`stringValues`).
- `new Set(init)` without type arguments infers its element from the
  checker.

## Side effects discovered

- The Set iterator crash, above.

## Divergences

- A string's iterator is an array iterator over its code points; Node's
  is a String Iterator object (`Object.prototype.toString` differs).
