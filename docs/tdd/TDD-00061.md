# TDD-00061: Generator functions (`function* f() { yield x; }`, V1: sync, function-declaration only)

- **Status**: Implemented
- **Date**: 2026-08-12

## Context

Sampling the Test262 conformance harness's largest remaining failure buckets found `function*`/`yield` syntax is not recognized at all — `yield` isn't a lexer token or contextual keyword anywhere in this codebase, and `function*`/`async function*`/`*method() {}` all fail to parse (`expected IDENT, got *` — 2180 files; `expected (, got *` — 1896 files, largely `AsyncGeneratorFunction`-related). Combined, generator syntax is one of the two largest remaining unimplemented-feature buckets (the other being `class` expressions), and — unlike most of this compiler's recent conformance work — genuinely needs new runtime machinery, not just a parser/AST extension over existing codegen. This TDD exists specifically to establish whether that machinery is buildable at all before committing to it, per this project's own standing rule that new-subsystem work gets scoped in writing first.

**The key finding driving this document**: this compiler already has a working, cross-platform-verified, `setjmp`/`longjmp`-safe fiber (suspend/resume) primitive — built for [TDD-00006](TDD-00006.md) Part 2 to make `http.listen`/`await fetch(...)` genuinely concurrent, not synchronous stand-ins. A JS generator is, at its core, exactly the same primitive (a function that suspends mid-body and resumes later with its full local-variable state intact) with a different trigger (an explicit `.next()` call instead of an I/O-readiness event). That prior work already answered the two hardest open questions here — "can this compiler suspend a function mid-body at all" and "does that survive this compiler's unusual exception model" — so this TDD is much narrower than it would otherwise be: mostly new bookkeeping (a per-generator-instance context/stack instead of one global connection array) and new front-end surface (`yield` itself doesn't exist yet at any layer), not a new suspension mechanism.

## Design

### Why fibers, not LLVM coroutines or a CPS rewrite

Already decided, doesn't need re-litigating: [TDD-00006](TDD-00006.md) directly prototyped LLVM coroutine intrinsics against this compiler's `setjmp`/`longjmp` exception model and found a confirmed, reproducible segfault (a coroutine invocation's C stack frame is unwound at every suspend point, so a `jmp_buf` saved before suspending points at a stale stack the instant that frame returns — a `longjmp` to it is undefined behavior). Fibers (`ucontext.h`'s `getcontext`/`makecontext`/`swapcontext`) don't have this problem because a fiber's own OS stack stays live for the entire time it's parked — confirmed by the identical test redone with `swapcontext` instead of a coroutine suspend, which worked correctly. A hand-rolled CPS transform (splitting a generator body into per-`yield` continuation functions, à la async/await's original design-space survey) was already ruled out on effort grounds for async/await, for the same reason it's not attractive here: it needs real live-variable analysis across a control-flow graph, a standalone piece of compiler engineering this project has consistently declined to build. Fibers avoid needing that entirely — ordinary allocas/locals just live on the fiber's own stack and survive a suspend for free, no frame-splitting or capture analysis required.

### Shape of a generator, mapped onto the existing fiber primitive

A generator instance is a heap struct (name pending — `generatorObjType` or similar), roughly:

```
{ ptr ctx           ; this generator's own ucontext_t (malloc'd, ucontextLayout()-sized)
, ptr stack          ; this generator's own fiber stack (malloc'd, same 64KB-fixed precedent runtime_http.go already uses)
, ptr callerCtx       ; where to swapcontext back to on yield/return — set fresh before every .next() call, not fixed like @__kml_main_ctx
, i1  started         ; false until the first .next() call — the body doesn't run at all until then, unlike an ordinary function call
, i1  done            ; true once the body has returned or fallen off the end
, <T> yieldedValue     ; what the most recent yield/return produced — T is the generator's own element type
, <T> sentValue        ; what the next .next(value) call is passing in — becomes yield expr's own value on resume
, ptr argsPack (or a closure-style captured-args slot, TBD) ; the generator function's own declared parameters, bound once at construction time
}
```

**Construction (`gen(args)`, calling the generator function itself)** does *not* run the body — it mallocs the struct above plus the ctx/stack, `getcontext`+`makecontext` (pointing at the compiled generator-body LLVM function, exactly like `runtime_http.go`'s existing per-connection fiber setup), stores the call's arguments into the struct, and returns the struct pointer as the generator's own opaque instance value. This is the same "allocate now, run later" split TDD-00006's connection fibers already use (`makecontext` at accept time, the body only actually executing on the first `swapcontext` into it). The fiber stack's own size must start from `runtime_http.go`'s *current* `fiberStackBytes` constant (1MB, not the original 64KB) — [ADR-00100](../adr/ADR-00100.md) found the 64KB default silently overflowed under `-mm=gc` specifically (the stack is itself `GC_malloc`'d, and a collection triggered mid-fiber runs Boehm's own mark/sweep *on that same stack*, with no crash or signal, just intermittent corruption), bisected up to 1MB. A generator fiber is exactly the same "GC_malloc'd stack running arbitrary user code that can itself trigger a collection" shape, so it almost certainly needs the same size floor, not a fresh, smaller guess.

**`gen.next(value)`** (a new dispatch case in `emitCall`, mirroring how `EventEmitter`/`Map`/`Set` method dispatch already gates on a type tag before falling through to the generic chain): stores `value` into the struct's `sentValue`, allocas a fresh local `ucontext_t` on the *caller's own stack* (this .next() call's save-point — valid only for the duration of this call, unlike the generator's own long-lived `ctx`), stores that local buffer's address into the struct's `callerCtx`, then `swapcontext(&localCtx, genObj.ctx)`. Control resumes inside the generator body (either at its very start, if `!started`, or right after whatever `yield` it last suspended at) until the body hits another `yield`, `return`s, or falls off the end — each of which stores into `yieldedValue`/`done` and does `swapcontext(genObj.ctx, genObj.callerCtx)` to hand control back. `.next()` then reads `{value: yieldedValue, done}` and returns that pair — the standard JS generator-result shape.

**`yield expr`** (a new `ast.YieldExpression`, valid only inside a generator body) compiles to: evaluate `expr`, store into the enclosing generator's own `yieldedValue`, `swapcontext(genObj.ctx, genObj.callerCtx)`, and — once resumed — read `sentValue` back out as the yield expression's own value. Structurally almost identical to `emitAwait`'s read-a-slot shape, except the "who fills the slot" direction reverses (await reads a value some other producer already finished computing; yield *produces* a value and then blocks waiting to be handed a new one).

**`for (const x of gen())`**: a new, fourth `emitForOf` case (distinct from the existing array/Map/Set cases *and* from Stage 1a's class-`next(): T | null` sentinel protocol — a real generator's `{value, done}` result shape doesn't fit that sentinel model, and reusing it would misinterpret a legitimately falsy/zero yielded value as "done"). Loop condition calls `.next()` and branches on `done`; loop body binds `x` to `.value`.

### V1 scope

Mirrors this project's own repeated "ship the anonymous/declaration-only core first, defer the name-binding/expression-position edge cases" pattern ([TDD-00057](TDD-00057.md) nested functions, [TDD-00060](TDD-00060.md) function expressions):

**In scope**: `function* name(params): T { ... }` as a **top-level or nested function declaration only** (not a generator expression, not a class/object method, not an arrow — real JS doesn't have generator arrows either). `yield expr` (not `yield*` delegation). The returned generator instance's `.next(value)` method, and `for...of` iteration over one. A `return expr;` inside the body (or falling off the end) sets the final `{value, done: true}` result.

**Explicitly deferred, not silently dropped**:
- `yield*` (delegating iteration to another iterable/generator) — real, separate design work: needs to drive an *inner* iterator from inside an *outer* generator's own suspended state, a second layer of the same problem.
- `.throw()`/`.return()` methods (injecting an exception into a suspended generator, or forcing early completion so its `finally` blocks run) — real spec behavior, meaningfully more machinery (the exception needs to be raised *inside* the suspended fiber's own stack context, not the caller's), and `for...of`'s `break`/early-`return` out of a generator loop normally calls the generator's own `.return()` for cleanup — V1's for-of case would just stop calling `.next()` without that, a real, documented gap (a generator with a `try { yield x } finally { cleanup() }` wouldn't run `cleanup()` on an early `break`).
- Generator methods on classes/objects (`*method() {}`) — needs the class/object method-dispatch machinery taught about a second calling convention; mechanical once the core exists, but genuinely separate parser/codegen surface.
- `async function*` (async generators) — combines this TDD's fiber-based suspension *with* `emit_async.go`'s separate Promise-slot machinery; two suspension mechanisms interacting is materially riskier than either alone and deserves its own follow-up TDD once V1 is proven, not a same-pass bolt-on.
- A generator expression (`const g = function*() {...}`) — same shape as [TDD-00060](TDD-00060.md)'s own V1/V2 split; natural once both function expressions and generator declarations exist independently, not attempted here.
- `Generator<T>`'s full three-type-parameter real-TS shape (`Generator<T, TReturn, TNext>`) — V1 likely needs just a single element type `T` (mirroring `EventEmitterType(payload Type)`'s exact one-type-parameter precedent), inferred from the body's own `yield` expressions the same way `Promise<T>`/arrow-function return types are already inferred elsewhere in this compiler.

### New front-end surface needed (currently doesn't exist at any layer)

`yield` is not a lexer token, not a contextual keyword, not an AST node. Needs: a lexer/parser recognition (contextual, like `get`/`set`/`async` — a bare `yield` must keep working as an ordinary identifier everywhere outside a generator body, real JS's own rule), a new `ast.YieldExpression`, `*` recognized right after `function`/`async function` (parser-level lookahead, the same shape `async` disambiguation already uses elsewhere in this parser) setting a new `IsGenerator bool` on `ast.FunctionDeclaration`, and a parse-time rejection of `yield` used outside a generator body (mechanical — same "is this identifier valid in this context" check `this`/`super` already get).

### New type-system surface

A `Type.IsGenerator bool` + `GeneratorElemType *Type` tag, structurally identical to `IsEventEmitter`/`EventEmitterPayload` (`types.go`) — `GeneratorType(elem Type)` mirroring `EventEmitterType(payload Type)` exactly.

## Prerequisites

|---|---|---|
| Fiber context-switch primitive (`getcontext`/`makecontext`/`swapcontext`, no hand-written assembly) | ✅ done, cross-platform-verified | `ucontextLayout()` (`runtime_http.go`) already has confirmed `sizeof(ucontext_t)`/field-offset constants for Darwin arm64, Linux x86-64, and Linux arm64 (found the hard way — Linux's ubuntu-latest CI hung until this was fixed; the four offsets are identical across the two Linux architectures but the total struct size isn't, and both differ completely from Darwin). Directly reusable — this project's own hardest, most failure-prone platform-constant work here is already paid for. |
| Confirmation fibers survive this compiler's `setjmp`/`longjmp` exception model | ✅ confirmed via direct prototype (TDD-00006) | A `try { await g() } catch {}`-shaped suspend/resume works correctly under fibers; the identical shape under LLVM coroutines segfaults. A generator's own `try { yield x } finally {}` is the same shape — expected to inherit this safety, but **not yet independently re-verified for the generator case specifically** (see Open Questions). |
| GC-mode (`-mm=gc`) stack-bottom handling across a context switch | ✅ pattern exists, ❌ not yet generalized | `runtime_http.go`'s connection fibers already repoint Boehm's `GC_stackbottom` at the fiber's own stack on switch-in and restore it on switch-out (both directions, both fiber-runs-to-completion and fiber-yields-again cases) — a generator's own fiber needs the identical treatment, but this logic currently lives inline in the HTTP-connection-specific fiber setup, not factored out as a reusable helper. Extracting it (or duplicating it, matching this project's own stated preference for duplication over a shared abstraction when the call sites' surrounding context differs) is real, if small, work. |
| A per-instance (not global-singleton) fiber array/bookkeeping model | ❌ new work | Every existing fiber user (`http.listen` connections, `fetch()`) shares one global connection array and one global `@__kml_main_ctx` swap-back target. A generator's "swap back to" target changes on every `.next()` call (whoever's calling it this time, not a fixed scheduler) and its lifetime is tied to a user-visible heap value (the generator instance itself), not an internal connection-array slot — new struct shape and allocation pattern, not a reuse of the existing HTTP-specific globals. |
| `yield` lexer/parser/AST support | ❌ new work | Doesn't exist at any layer today — see "New front-end surface" above. |
| `for...of` generator case | ❌ new work | The existing three `emitForOf` cases (array/Map/Set) and the Stage 1a class-`next(): T \| null` sentinel case ([ADR-00063](../adr/ADR-00063.md)) are all structurally incompatible with a `{value, done}`-shaped result — needs its own, fourth case, not a fit into any existing one. |
| Generator method-call dispatch (`.next()`) | ❌ new work | New `IsGenerator`-gated block in `emitCall`'s dispatch chain, same shape as the existing `EventEmitter`/`Map`/`Set` type-tag-gated blocks. |

## Open questions

- **Whether a generator's `try`/`finally` genuinely survives a suspend the same way async/await's does** — TDD-00006's own prototype tested `await` across a suspend point, not `yield`; the mechanism should be identical (both are just "swapcontext while a `jmp_buf` is live on this fiber's own stack"), but this project's own standing rule is to verify a claim like this directly rather than assume it carries over, and this specific case (a `yield` *inside* a `try` block, suspended, then resumed from a *different* call site than the one that originally called `.next()`) hasn't been prototyped. Should be a small, targeted throwaway prototype before real implementation starts, not assumed from TDD-00006's async case alone.
- **Whether the generator function's own body should compile through a dedicated new emission path, or attempt to share code with `emitClosureFunc`/`emitFunctionDeclAs`'s existing state-save/reset/restore dance.** Leaning toward a dedicated path, matching [ADR-00063](../adr/ADR-00063.md)'s own precedent: `emitClassMember` was written as "a deliberately separate function from `emitFunctionDecl`, not a refactor of it," duplicating the non-async subset of its state-save/reset/restore + parameter-binding loop rather than threading a new conditional receiver parameter through the shared function, on the reasoning that a new calling convention is lower regression risk as a clean duplicate than as an added concern bolted onto an already-relied-upon function. A generator body's own calling convention (single `ptr %genObj` argument, no return value in the ordinary sense, entered via `makecontext` rather than a normal `call`) is different enough from an ordinary function/closure that the same reasoning likely applies — but this is a leaning, not a decision; worth a closer look once implementation starts.
- **Fixed vs. grow-on-demand generator fiber stack size.** The HTTP connection fibers' own size was revised once already, from 64KB to the current 1MB (`fiberStackBytes`, `runtime_http.go`), after a real `-mm=gc` bug (see Design above) — the same 1MB floor is the obvious starting point here, applied unconditionally rather than re-litigated per feature (matching [ADR-00100](../adr/ADR-00100.md)'s own "avoid a mode-specific footgun" reasoning). Whether a generator body needs *more* than that — e.g. one that recurses through ordinary function calls inside its own body, or a deep call chain before its first `yield` — is untested and worth a real stress-test once built, not assumed safe from the HTTP precedent alone.
- **Naming/shape of the generator instance's public type** — `Generator<T>` (single type parameter, V1) vs. reserving the name for the real three-parameter form and using something else for now. Leaning toward `Generator<T>` matching `EventEmitterType`'s own one-parameter-now precedent (TDD-00023 did the same thing for `EventEmitter<T>` vs. real Node's fuller event-map-typed form) — not fully decided.
- **Whether V1 needs a compile-time-constant answer to "does this function contain a `yield`" to *validate* `IsGenerator`**, or whether `function*` with zero `yield` statements inside (legal, if unusual, real JS — a generator that just runs to completion on the first `.next()`) should be accepted as-is. Leaning toward accepting it (real JS does), just noting it's an available edge case to test once built.
