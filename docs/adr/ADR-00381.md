# ADR-00381: `@typedef`/`@callback` synthesized into type aliases (TDD-00125 Stage 2)

- **Relations**: Extends [ADR-00380](ADR-00380.md); Implements [TDD-00125](../tdd/TDD-00125.md)
- **Date**: 2026-08-26

## Context

Stage 1 (ADR-00380) let `@param`/`@returns` type an untyped function but only
with the existing type-name grammar. The next JSDoc gap is declaring a **named
type in a comment** — `@typedef {Object} Point` + `@property {number} x`, or a
`@callback` function type — and then referring to it by name from `@type` /
`@param` / an inline annotation.

## Investigation

A non-generic TS `type Name = …` alias is registered into `e.interfaces[Name]`
during `registerInterfaces` (`emitter.go`) and thereafter `resolveType` resolves
any annotation whose `Name` matches — regardless of `Source` ("ts"/"jsdoc").
Confirmed by repro: a JSDoc `@typedef {Object}` object type resolves correctly
when referred to by an **inline** `p: Point`, and a `@param {Point}` resolves a
**TS-declared** object alias. So the whole mechanism already exists; the only
missing piece is turning the `@typedef`/`@callback` comment into an
`ast.TypeAliasDeclaration` in the program body.

The blocking subtlety: `parser.peek()` collapses a *run* of adjacent JSDoc
comment tokens to only the **last** (`p.pendingDoc` is overwritten each). So a
`@typedef` comment immediately followed by the `@param` comment for the next
function is silently lost if drained from `pendingDoc` — the exact two-comment
layout the feature is used in.

## Decision

- **`jsdoc.Comment.Typedefs()`** walks the ordered annotation list and returns a
  `TypedefDecl` per `@typedef`/`@callback`, accreting the `@property` (object)
  or `@param`/`@returns` (callback) tags that positionally follow each — the
  JSDoc association convention. `@typedef {Object} N` (or a braceless
  `@typedef N`) is an object type built from `@property`; `@typedef {T} N` with a
  non-`Object` brace body is a direct alias; `@callback N` is a function type.
- **A parser pre-pass (`collectTypedefs`)** scans *every* JSDoc token in the
  stream (not `pendingDoc`, sidestepping the run-collapse), synthesizes an
  `ast.TypeAliasDeclaration` per typedef via `synthTypedef`, and **prepends**
  them to `prog.Body` so they register before any use site. An object typedef
  becomes a `TypeAnnotation{Fields}` (identical to a TS `{ … }` object type); a
  callback becomes `TypeAnnotation{IsFuncType, FuncParams, FuncRetType}`.
- The comments are left in place for their ordinary `@type`/`@param` attachment
  (a `@typedef` carries no per-statement meaning, so re-reading it is harmless).

To distinguish `@typedef {Object} N` from a braceless `@typedef N`, `Annotation`
gained a `HasBrace` flag (`@type`/`@erased` are unaffected — they read `Value`).

## Implementation notes

- Object-typedef fields and callback params/returns reuse Stage 1's
  `paramName`/`stripJSDocDecorations`, so `[name]`/`...`/`=` decorations behave
  the same as in `@param`.
- Alias-to-a-width-keyword (`@typedef {int32} MyInt`) does **not** propagate the
  integer semantics — but neither does a TS `type MyInt = int32`; it is a
  pre-existing type-alias-to-primitive limit, not new here, and is disclosed as
  a caveat on the JSDOC.md `@typedef` row.

## Side effects discovered

None new. The inline `@typedef {{x: number}} N` object-literal-in-a-string form
(as opposed to the `@property` form) still needs the JSDoc type sub-parser
(Stage 4) and is tracked ❌.
