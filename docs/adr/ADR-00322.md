# ADR-00322: Async `child_process` — spawn / exec / execFile

- **Relations**: Extends ADR-00025 (`process.execFileSync`), TDD-00098 (Worker event-loop fd integration); builds on the EventEmitter dispatch posture of TDD-00098's `Worker`
- **Date**: 2026-08-23

## Context

The only child-process facility was the blocking `process.execFileSync`
(ADR-00025): fork+execvp, capture stdout, wait for exit. The async
`child_process` surface — `spawn` (streaming), `exec`/`execFile` (buffered
callback) — was ❌ on [PROCESS-CLI.md](../status/PROCESS-CLI.md). Async process
spawning is core to the CLI-tool / microservice direction (shelling out to
`git`, `ffmpeg`, `docker`, …), and it was the higher-value of the two
EventEmitter-backed process items in the backlog (the other being interactive
`readline`).

Full surface targeted in one delivery: `spawn` returning a ChildProcess whose
`stdout`/`stderr` are `'data'`/`'end'` EventEmitters, with `'close'`/`'exit'`
on the child and a writable `child.stdin`; plus `exec` (shell) and `execFile`
(no shell), both buffering into one `(err, stdout, stderr)` callback.

## Investigation

- `process.execFileSync` (`runtime_process.go`) supplied the fork+pipe+argv
  template, but is fully blocking (single pipe, blocking `read` loop, blocking
  `waitpid`) and captures stdout only.
- The real design precedent is `Worker` (TDD-00098): a forked/threaded child
  whose message pipes are made non-blocking (`fcntl` O_NONBLOCK) and folded
  into the central `select()` loop (`@__kml_event_loop_run`, runtime_http.go)
  via three hooks — `@__kml_worker_fdset_add` (add read fds), a post-select
  dispatch, and `@__kml_worker_keepalive` (hold the loop open) — with no-op
  stubs in `emitLoopTaskStubs` when unused. The channel runtime (TDD-00099)
  repeats the same three-hook shape.
- Listener firing: `Worker` stores one closure header per event and the runtime
  dispatch invokes it through the closure ABI (`fn = header[0]`,
  `env = header[1]`, `call void fn(env, …)`) — no codegen-time `emitCBCall`
  needed at dispatch. `resolveArrayForHOF`/`resolveCallbackWithHints` and the
  `httpNonblockFlag()` / `ensureWorkerFdSetbit` helpers are all reusable.

So `child_process` is "apply the Worker fd-integration pattern to a new source
(a forked child's stdout/stderr pipes)" plus an EventEmitter-style object
model — a re-application of two existing subsystems, not novel design, so an
ADR rather than a TDD.

## Decision

- **Runtime** (`runtime_childprocess.go`): a `%kml.cp` handle
  (pid, three pipe fds, state, exit code, per-event listener slots, mode,
  stdout/stderr accumulators, exec callback) in a process-wide registry.
  `@__kml_cp_spawn` forks with three pipes, dup2's them onto the child's
  0/1/2, execvp's, and makes the parent's two read ends non-blocking.
  `@__kml_cp_fdset_add` / `@__kml_cp_dispatch` / `@__kml_cp_keepalive` are the
  three event-loop hooks (wired into `@__kml_event_loop_run`, no-op stubs in
  `emitLoopTaskStubs` when `child_process` is unused; `usedChildProcRuntime`
  joins the `useFullLoop` driver-selection set). Dispatch drains each child's
  read fds (firing `'data'` closures with a fresh Buffer, or appending in
  buffered mode), fires `'end'` on EOF, and once both pipes are EOF reaps with
  `waitpid(WNOHANG)` and fires `'exit'`+`'close'` (streaming) or the
  `(err, stdout, stderr)` callback (buffered).
- **Object model** (`emit_childprocess.go`, types in types.go): `spawn` returns
  `ChildProcessType` (mode 0); `child.stdout`/`stderr` are `CPStreamType(0/1)`
  views over the same handle pointer, `child.stdin` a `CPStdinType` view.
  `.on` stores the listener closure header into the matching handle slot.
  `exec` = `spawn("/bin/sh", ["-c", cmd], mode 1)`; `execFile` =
  `spawn(file, args, mode 1)`; both store the callback in the handle. Listener
  ABIs: `'data'` `(Uint8Array)`, `'end'` `()`, `'close'`/`'exit'` `(number)`,
  the exec callback `(Error|null, string, string)`.
- **Resolver**: `'child_process'` marker + `{spawn, exec, execFile}` members.

## Implementation notes

- `@write`/`@fcntl` were each declared in two runtimes; extracted guarded
  `ensureWriteDecl`/`ensureFcntlDecl` (runtime_core.go) to avoid a redefinition
  when the full loop and `child_process` are both emitted.
- An empty array literal `spawn("cmd", [])` carries no element type; it is
  special-cased to "no args" rather than routed through `resolveArrayForHOF`.
- Callbacks fire from the loop dispatch, after all synchronous top-level code —
  which is the Node-observable async ordering — but *synchronously within* the
  dispatch (not deferred through a microtask), since `process.nextTick` / a
  microtask-timed callback queue does not exist yet.

## Side effects discovered

None outside the two shared-decl extractions above. Handles and their buffered
output are not freed (`-mm=manual`), consistent with the rest of the runtime.

## Verification

- `go build` / `go vet` clean.
- New `tests/childprocess_test.go` (11 cases): spawn streaming + line count,
  exec (shell) success + non-zero-exit error + stderr capture, execFile,
  stdin→child round trip, exit-code via `'exit'`, `'end'` event, async
  callback ordering, output larger than one 4096-byte read chunk, and
  missing-import rejection. All pass.
- `examples/child_process/child_process.ts` builds and runs (Mac / Apple
  Silicon M4).

### Known limitations (tracked on docs/status/PROCESS-CLI.md)

- Listener callbacks fire synchronously from the dispatch, not via a microtask.
- One listener per event, arrow/function-expression literal only; no
  `removeListener`.
- No `.fork()`, no options object (cwd/env/timeout/stdio/encoding); `'close'`/
  `'exit'` deliver the exit code only (signal death folded to `128+signal`).
