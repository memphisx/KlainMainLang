# ADR-00127: WebSocket Stage 2 — automatic ping/pong + close handshake

- **Relations**: Implements TDD-00039 (Stage 2 of 4 — Stage 0 was ADR-00125, Stage 1 was ADR-00126; Stage 3 remains)
- **Date**: 2026-08-08

## Context

[TDD-00039](../tdd/TDD-00039.md)'s Stage 1 ([ADR-00126](ADR-00126.md)) shipped a working server-side echo but left two real, documented gaps: a client `ping` got no `pong` reply at all, and both a peer-initiated `close` frame and `socket.close()` just dropped the raw fd with no RFC 6455 §5.5.1 closing handshake. Stage 2 closes both gaps.

## Investigation

Both gaps lived in the exact same place: `emit_websocket.go`'s `emitWSServerLoop`, where a decoded frame's opcode was checked only for `8` (close, ending the loop) or `1`/`2` (text/binary, dispatched to `.onmessage`) — every other opcode, including `9`/`10` (ping/pong), fell through to a shared "ignore and loop" path. No new investigation into other subsystems was needed; this was a direct, contained extension of Stage 1's own dispatch chain. Re-verified one specific concern before writing any code, given Stage 0's own history with a dominance bug in structurally similar branching: does `fd32` (defined once at the top of the current pass through `readLoopL`) still dominate two *new* blocks (`closeRecvL`, `pingRecvL`) inserted into the middle of the existing opcode-check chain? Confirmed yes — both new blocks are reached only via `checkOpcodeL`, itself only reached via `decodeLoopL`, itself only ever reached (directly or through its own multi-frame self-loop) after `readLoopL`'s fd/ctx computation has run at least once on the current dynamic execution. No new bypassable path was introduced, unlike Stage 0's actual bug.

## Decision

Extended the existing opcode-dispatch chain (`checkOpcodeL` in `emit_websocket.go`) with two new branches, inserted before the existing text/binary check:

- **`closeRecvL`** (opcode 8): extracts the received frame's payload/length (whatever status code + optional reason the peer sent, if any — possibly empty) and immediately re-sends it as a new Close frame via `__kml_ws_frame_encode`, unmasked, before falling into the existing `endL` cleanup. Echoing the exact payload verbatim is a real, simple, RFC-compliant choice — the spec requires *a* Close frame in response, not a specific code, and this is what many real WebSocket server libraries already do.
- **`pingRecvL`** (opcode 9): extracts the ping's payload and immediately replies with a Pong (opcode 10) frame carrying the identical payload (RFC 6455 §5.5.2's own requirement), then loops back to `decodeLoopL` to keep parsing — a ping never reaches `.onmessage`, matching every real WebSocket server's behavior.
- **`socket.close()`** (`emitWSConnectionCloseMethod`) now sends its own Close frame (status 1000, Normal Closure, RFC 6455 §7.4.1 — no reason text) before closing the fd, rather than closing it bare. Deliberately does **not** wait for the peer's own echo back before actually closing the socket — implementing that wait would need a new timeout-based state machine, real scope beyond this stage; the read loop's existing error handling (`EBADF` on the next `read()`, routed the same as any other non-`EAGAIN` failure) already ends the fiber correctly once the fd is gone.
- An unsolicited Pong (opcode 10, a real possibility — some clients send them proactively) and any other unrecognized opcode still fall through to the pre-existing "ignore, leak the one bounded payload buffer" path unchanged.

## Implementation notes

- File touched: `codegen/llvm/emit_websocket.go` only — no changes needed to `runtime_websocket.go`'s Stage 0 codec (already fully general over any opcode value) or to `types.go`/`emit_http.go`.
- Both new branches reuse `fd32` from the current pass through `readLoopL` and the existing `ensureWSFrameEncode()`/`ensureFree()` (now called unconditionally at the top of `emitWSServerLoop`, alongside the pre-existing `ensureWSFrameDecode()`).
- `emitWSConnectionCloseMethod` builds its 2-byte status-code payload (`{0x03, 0xE8}` = 1000) via two explicit `malloc`+`store` instructions rather than an interned string constant, since it's raw binary (not text) — interning would work as ASCII text, but a raw byte buffer better documents that this is a numeric wire field, not a string.

## Side effects discovered

None. No existing behavior changed for any opcode this stage doesn't touch (text/binary dispatch, the growable-buffer read loop, the handshake) — purely additive.
