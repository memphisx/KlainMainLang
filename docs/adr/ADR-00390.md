# ADR-00390: Index signatures (`{ [k: string]: T }`), map-backed

- **Relations**: Implements TDD-00130; Extends ADR (TDD-00012's dynamic object)
- **Date**: 2026-08-27

## Context

A string index signature — `interface Dict { [key: string]: number }`, `type M =
{ [k: string]: T }` — was a parse error (`expected IDENT, got [`), blocking the
idiomatic dictionary/record interface shape.

## Investigation

The runtime this needs already exists: TDD-00012's computed-key object literals
introduced `IsDynamicObject`, a `Map<string,V>`-backed object with `d[key]`
read/write sugar (`emitDynamicObjectGet`/`…Assign`), literal construction
(`emitDynamicObjectLiteral`), and `Object.keys/values/entries` + `for…of` over
its `IsMap` base. Index signatures are the type-annotation grammar for that
representation — not TDD-00068's dynamic/prototype object model.

## Decision

Parse a string index signature and resolve its type to the existing
`Type{IsMap, IsDynamicObject, MapKey:string, MapVal:V}`. V1 scope: string key
only; no mixed named+index; single homogeneous value type — matching what the
dynamic-object representation supports.

## Implementation notes

- **Parser** (`parser/parser_types.go`): `parseIndexSignature` parses `[ name :
  string ] : V` (numeric/other key = clean rejection). Both the inline
  object-type loop and the interface field loop gained an `LBRACKET` branch
  before the field-name expect; the mapped type `[K in …]` is already handled
  earlier, so a `[` in the field loop is unambiguously an index signature. A
  named property combined with an index signature is a clean rejection.
- **AST**: `TypeAnnotation.IndexSig` and `InterfaceDeclaration.IndexSig` carry
  the value type.
- **resolveType** (`emitter.go`): an annotation/interface with an index
  signature resolves via `indexSignatureType` to the dynamic-object map type;
  `registerInterfaces` registers the interface the same way.
- **Object literal construction** (`emit_objects.go`): a plain object literal
  assigned to an index-signature target is routed to `emitDynamicObjectLiteral`
  (build a map) instead of a fixed struct — the missing link that made `d[key]`
  on a literal-initialized dict work (without it the value was a struct and the
  map-get hung/segfaulted).

## Side effects discovered

- **`JSON.stringify` of a map-backed dynamic object** (a dict or a computed-key
  literal) has no field table to walk; it previously returned an empty string.
  Now a clean rejection with a message pointing at `Object.keys(...)`. A proper
  map-iterating stringify path is deferred (TDD-00130 remains Partially
  Implemented).
- **`Record<string,V>` bracket-access parity** (flag its map result
  `IsDynamicObject`) was scoped in TDD-00130 but deferred here to keep the change
  focused; `Record<string,V>` still reaches only via `.get()/.set()`.
