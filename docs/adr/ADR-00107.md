# ADR-00107: `Array.prototype.flat(depth?)` / `.flatMap(fn)`

- **Relations**: Implements the `.flat()`/`.flatMap()` follow-on left open by [TDD-00029](../tdd/TDD-00029.md)/[ADR-00105](ADR-00105.md)
- **Date**: 2026-08-06

## Context

[TDD-00029](../tdd/TDD-00029.md)'s own Open Questions left `.flat(depth?)`/`.flatMap(fn)` explicitly unresolved after nested-array storage itself shipped (ADR-00105): nested-array storage removed the *representation* blocker, but the flatten logic itself was never designed or built, and the TDD flagged a real, unresolved design question — real JS's `depth` is an arbitrary runtime value, but this compiler's arrays are statically typed with a fixed nesting depth (`number[][]` is exactly two levels, always), so a runtime `depth` can't determine the *type* of a statically-typed compiled function's return value the way it can in dynamically-typed JS. Picked up now at the user's explicit request for a proper implementation (not a narrowed-to-depth-1 stopgap, which was floated and explicitly rejected).

## Investigation

Confirmed `Type.IR`/`Type.Align()` already report a uniform 8-byte `"ptr"` slot for any array-typed element (`codegen/llvm/types.go`, same fact ADR-00105 already established) — flattening doesn't need any new storage layout, only new codegen that concatenates inner arrays' contents.

Resolved the `depth`-vs-static-typing tension by requiring `depth` to be a **compile-time constant**: a literal integer, or the bare `Infinity` identifier this compiler already recognizes as a float64 constant elsewhere (`codegen/llvm/emit_exprs.go`'s `emitIdent`, `emit_exprs_types.go`'s `inferExprType`). This isn't a narrowing hack — it mirrors how real TypeScript's own `FlatArray<T, Depth>` recursive conditional type already needs `Depth` to be a literal type to produce a real element type at all (a non-literal `depth` degrades to `any[]` in real TS too). With `depth` known at compile time, the result type is computed by unwrapping `ElemType` up to `depth` times (stopping early once no longer array-typed — this is what makes `Infinity` implementable without a real unbounded value: it's just "a depth larger than any real array nesting reaches," and the unwrap loop's own `IsArray` check naturally stops there).

Found no existing precedent for a "must be a compile-time-constant *number*" call argument (only string-literal precedents — `process.on`'s event name, `emit_process.go`). Closest numeric precedent, `registerEnums`'s enum-member-value parsing (`codegen/llvm/emitter.go`), doesn't unwrap unary minus either — confirmed there's no existing helper for negative-literal detection anywhere in this codebase, so `resolveFlatDepth` (new) is the first.

While implementing `.flatMap()` and testing it end to end with a callback that returns an array per element (`(x) => [x, x * 10]`), hit a hard clang-stage crash unrelated to `.flat()`/`.flatMap()` themselves: `'%t7' defined with type '{ ptr, i64 }' but expected 'ptr'`. Traced to `emitClosureFunc` (`codegen/llvm/emit_func.go`) — the function underlying every arrow function/closure. Its expression-body branch (`(x) => expr`, as opposed to a block body `(x) => { return expr; }`) built its `ret` instruction from `val.Ty.IR` unconditionally, which is `"ptr"` for any array-typed value — the aggregate `{ptr, i64}` shape the function's own declared return type requires (`retTy.LLVMRetType()`) was never used. A block-bodied arrow function or named function returning an array already went through `emitReturn`'s (`emit_stmts.go`) dedicated `IsArray` branch via ordinary statement dispatch, which has built the aggregate correctly since TDD-00028 — only the expression-body shortcut in `emitClosureFunc` missed it, because nothing had previously exercised "an expression-bodied arrow function whose body is itself an array-producing expression" (array literals as general expressions is itself only as old as TDD-00028/ADR-00104). Confirmed this is real and pre-existing, not something `.flatMap()` introduced — any code shaped like `const f = (x: number): number[] => [x, x]` would already have hit it.

Also confirmed a smaller, related pre-existing gap while auditing the same code path: `.map()`'s own result-store (`emitArrayMap`, `codegen/llvm/emit_arrays_hof.go`) used a raw `store retElemTy.IR ...` for each written result — fine for every element type `.map()` had ever actually been exercised with (scalars, strings, objects), but the exact same 16-byte-into-8-byte-slot mismatch ADR-00105 fixed everywhere else the moment a callback returns an array per element (`.flatMap()`'s own `.map(fn)` step, but also plain `arr.map(x => [x, x])` on its own, with no `.flat()` involved at all).

## Decision

**`depth` must be a compile-time constant** (`resolveFlatDepth`, `codegen/llvm/emit_arrays_transform.go`): omitted defaults to 1 (real JS's own default); a `*ast.NumberLiteral` parses via `strconv.ParseInt`; the bare identifier `Infinity` maps to a large sentinel (`maxFlatDepth = 1<<30`) that the flatten loop's own `IsArray` check naturally caps at the receiver's real nesting depth; anything else (a variable, a non-integer literal, a negative literal — including through a `-` unary wrapping a literal, which needed its own unwrap since no existing helper does this) is a clean compile-time rejection explaining *why* (the result's element type has to be knowable at compile time).

**Flattening** (`emitArrayFlattenOnce`): given an outer array whose own element type is itself array-typed, concatenates every inner array's contents into one fresh buffer — a two-pass runtime loop (sum inner lengths, then `memcpy` each inner array's bytes at a running cursor), the same sum-then-copy shape `emitSpreadArrayLitData` already uses for a compile-time-known list of sources, generalized to a genuine LLVM loop over however many inner arrays the outer array holds at runtime. Reads each outer element via the existing `loadArrayElem` (TDD-00029), which already transparently unboxes a nested-array element regardless of how deep it's nested — no new unboxing logic needed.

**`.flat(depth?)`** (`emitArrayFlat`): calls `emitArrayFlattenOnce` up to `depth` times in a Go-level loop (unrolled at compile time, since `depth` is now known), stopping early once the current element type is no longer array-typed — this is what makes both "depth deeper than the actual nesting" and `Infinity` correct without special-casing either. Always returns a fresh array (an explicit `emitArrayCopy` when the loop never ran — `depth` 0, or a non-nested receiver — matching real JS's own `.flat()` always allocating a new array even when there's nothing to flatten).

**`.flatMap(fn)`** (`emitArrayFlatMap`): `.map(fn)` (reusing `emitArrayMap` as-is) followed by exactly one level of flattening when the callback's return type is itself array-typed — real JS's `flatMap` has no `depth` parameter at all, so none of `.flat()`'s compile-time-constant machinery applies here. When the callback doesn't return an array per element, the mapped result is returned unchanged (flattening a non-array is a no-op in real JS too).

**Both pre-existing bugs found in Investigation are fixed as part of this same piece of work**, not deferred: `emitClosureFunc`'s expression-body branch now mirrors `emitReturn`'s own `IsArray`-aware structure exactly (same named-array-identifier fast path, same `emitExprWithObjectHint` hint-aware evaluation for the array and non-array cases alike — the latter was itself a second, smaller latent gap: the old code used bare `emitExpr` for every expression-bodied arrow function, never threading the declared/inferred return type as a hint the way `emitReturn` already does for block-bodied ones); `emitArrayMap`'s result store now goes through `storeArrayElem` like every other nested-array-element write.

## Implementation notes

Files touched:
- `codegen/llvm/emit_arrays_transform.go`: new `resolveFlatDepth`, `maxFlatDepth`, `emitArrayFlattenOnce`, `emitArrayFlat`, `emitArrayFlatMap`; new `strconv` import.
- `codegen/llvm/emit_arrays_hof.go`: `emitArrayMap`'s result store switched from a raw `store` to `storeArrayElem`.
- `codegen/llvm/emit_func.go`: `emitClosureFunc`'s expression-body branch restructured (IsArray-aware, hint-aware — see Decision).
- `codegen/llvm/emit_call.go`: `flat`/`flatMap` added to the unguarded array-method dispatch chain (same style as `map`/`filter`/`join`/`sort`, right after `sort`).
- `codegen/llvm/emit_exprs_types.go`: `inferExprType`'s `*ast.CallExpression` switch gained `flat`/`flatMap` cases mirroring `emitArrayFlat`/`emitArrayFlatMap`'s own type-computation exactly (best-effort — an invalid `depth` here just falls back to the default rather than erroring, since `resolveFlatDepth`'s real error is what actually surfaces when the call is emitted), so an unannotated `const x = arr.flat(N)`/`arr.flatMap(fn)` infers the correct element type.

## Side effects discovered

Both already covered under Decision (fixed, not deferred): `emitClosureFunc`'s expression-body array-return crash, and `emitArrayMap`'s unboxed nested-array result store.
