# TDD-00043: General union types (beyond `T | null`)

- **Status**: Implemented
- **Date**: 2026-08-09

## Context

`docs/status/TYPE-SYSTEM.md` and [ADR-00008](../adr/ADR-00008.md) both document the same gap: `parser_types.go`'s `T | U` loop only actually retains `U` when it's `null`/`undefined` (setting `Nullable`) — for any other `U`, the code's own comment says it "silently accepts the syntax but uses the first type," so `string | number` parses without error but `number` is discarded during parsing, before codegen ever sees it. ADR-00008 deliberately narrowed its own scope to `any`/`unknown` for exactly this reason, flagging general unions as separate follow-on work "needs parser changes, separate from this work."

This now matters beyond being a documented gap. [TDD-00026](TDD-00026.md)'s own Design section hit it directly: `http.listen`'s response object wanted a `body: string | ArrayBuffer` field and had to fall back to two separate optional fields (`body` and `bodyBytes`) instead, noting explicitly "this compiler has no general union types beyond `T | null` ... so `body: string | ArrayBuffer` on one field isn't an option." This project's own priority list also flags this: "no union types beyond `T | null`" is called out as a real, standing blocker on modeling realistic API surfaces, weighed roughly co-equal against the three CLI/HTTP/file-I/O priority areas as of 2026-08-07.

Picked up now (2026-08-09) as the next general-core-language-completion item, per that same project-direction rebalancing, after modules' TDD-00041/TDD-00042 landed.

## Design

### Reuse the existing `any`/`unknown` runtime-tagged value, don't invent a second one

ADR-00008 already built exactly the machinery a general union needs at runtime: a `{ i8, i64 }` boxed value (`TypeAny`, `codegen/llvm/types.go`) with a tag byte selecting one of {int, float, string, boolean, null, undefined, object} and an `i64` payload holding either the value directly (int/float bit-cast/bool zext) or a `ptrtoint`'d pointer (string/object) — plus a full set of tag-dispatch helpers already built and tested: `emitBoxValue`/`emitUnboxTagPayload`, `emitDynamicToString`, `emitDynamicTypeof`, `emitAnyEquals`/`@__kml_any_eq` (all in `emit_dynamic.go`/`runtime_dynamic.go`).

A union like `string | number` is representationally identical to `any` at runtime — the only real difference is **static**: `any` accepts a value of *any* tag with no compile-time check, while `string | number` should only accept a `string` or a `number` at assignment time, and ideally should reject `boolean`/`object`/etc. as a clean compile error the same way a mismatched concrete-type assignment already is elsewhere in this compiler. So the design is: keep the exact same runtime box and the exact same tag-dispatch helpers, and add a **compile-time member-set check** on top, gated on the declared type actually carrying a member list (vs. bare `any`, which has none).

This also directly answers the open question ADR-00008 raised about arithmetic/param/return/field positions. `any`/`unknown` are rejected outright in those positions (`emit_func.go`'s `containsDynamicElement` guards) because an unconstrained dynamic value can't be type-checked at all at those boundaries. A *constrained* union doesn't have that problem — `string | number` as a parameter type is fully checkable at every call site (the argument's static type must be a member of the set), which is exactly the TDD-00026 motivating case. **V1 of this TDD explicitly allows constrained unions in param/return/array-element/object-field positions — the opposite of `any`'s own restriction there — since that's the actual value this feature exists to unlock.**

### Representation

- `ast.TypeAnnotation` (`ast/nodes.go`) gains `UnionMembers []*TypeAnnotation` — non-nil only when the union has more than one non-null/undefined member (i.e. genuinely a `T | U | ...` beyond today's `T | null` case, which keeps using the existing `Nullable` bool unchanged, zero behavior change for that path).
- `parser_types.go`'s `for p.check(lexer.BITOR)` loop (`parser_types.go:193-207`) stops silently discarding: when `right` isn't `null`/`undefined` and `ta` isn't either, both get appended to a `members` slice instead of `right` being dropped. `null`/`undefined` members keep setting `Nullable` exactly as today (a union can be `Nullable` *and* carry `UnionMembers` at once, e.g. `string | number | null`).
- `codegen/llvm/types.go`'s `Type` struct gains `UnionMembers []Type` (parallel field to `ast.TypeAnnotation.UnionMembers`, resolved). A union type is: `Type{IR: "{ i8, i64 }", IsDynamic: true, UnionMembers: [...], Nullable: <as today>}` — literally `TypeAny` plus a non-empty `UnionMembers`. `IsDynamic` alone still means "bare `any`/`unknown`, unconstrained"; `IsDynamic && len(UnionMembers) > 0` means "constrained union, checked at every assignment/call boundary."
- `emitter.go`'s `resolveType` gets a new branch, checked before the existing named-type fallback: if `ta.UnionMembers != nil`, resolve each member via `e.resolveType` (recursively — reuses everything, including named interfaces as members) and build the `Type{IsDynamic: true, UnionMembers: resolved}` above.

### V1 scope: scalar members only

Restrict `UnionMembers` to combinations of `number`, `string`, `boolean`, `null`, `undefined` for V1 — the same five scalar tags `any` already boxes cleanly today. Object/interface/array/`ArrayBuffer` members are a clean compile-time rejection in V1, not silently accepted:

- Boxing an object pointer (tag 6) already exists in the tag enum "for completeness" per ADR-00008 but has no exercised path anywhere — extending it to real, checked object-member unions means deciding how `emitDynamicToString`/`emitAnyEquals` format and compare a *specific* object shape they currently have zero field knowledge of, which is real, separate design work.
- This walks back the literal TDD-00026 motivating example (`body: string | ArrayBuffer` needs a non-scalar member), which is a known, deliberate scope cut — TDD-00026's two-separate-optional-fields shape stays as-is; this TDD does not retroactively change it. The five-scalar-type surface still directly unblocks realistic cases (an API response field that's a string or a number, a "value or null" JSON-shaped return, `parseFloat`-style "number or the failure sentinel" signatures) without taking on struct-shaped-payload design work in the same pass.
- Extending to object/array members is left as an explicit, called-out follow-on (see Open Questions) — not blocked by anything V1 builds, since the tag-dispatch shape is designed to add a case, not be restructured.

### Assignment-time member-set checking

New helper, `emit_dynamic.go`: `unionAllowsAssignmentFrom(unionTy Type, valTy Type) bool` — walks `unionTy.UnionMembers`, true if `valTy` structurally matches any member (reusing whatever equality check `coerce`/existing type-compat logic already uses for concrete types — e.g. `number`/`i64` matches the `number` member, `string`/`ptr` matches the `string` member). Wired in at every point that currently boxes unconditionally for a dynamic-typed target:

- `emitVarDecl`'s scalar path (`emit_exprs_vardecl.go:228`, `:251`) — before calling `emitBoxValue`, if `ty.UnionMembers != nil`, check the initializer's inferred type against the set and emit a clean compile error (not a runtime one) if it doesn't match. A `let x: string | number;` with no initializer still boxes `undefined` unconditionally, matching `any`'s existing behavior — only meaningful if `undefined` is itself one of the declared members, otherwise likely worth its own error, see Open Questions.
- `emitAssign`'s identifier `=` path — same check, same clean-error shape, on reassignment.
- Function call sites — argument-vs-declared-param-type checking already exists for concrete types; extend it to check `unionAllowsAssignmentFrom` when the param type carries `UnionMembers`, instead of the blanket `IsDynamic` rejection `emit_func.go:65`/`:96`/`:833`/`:840` currently apply. This is the actual mechanism that makes `function f(x: string | number)` type-check its call sites.
- Return statements — same, against `RetType.UnionMembers` when set.
- Array literals / object literal fields — same, reusing `containsDynamicElement`'s existing recursive walk (`emit_dynamic.go`) but changing what it does when it finds a dynamic element: reject only if `UnionMembers == nil` (bare `any`), otherwise recurse into the member-set check instead of an unconditional reject.

### Reading a union value back out — same Staged-V1 restrictions as `any`

No new work needed here — this is the part that comes for free by reusing `any`'s existing machinery exactly:

- `console.log`/template literals → `emitDynamicToString`, unchanged.
- `typeof` → `emitDynamicTypeof`, unchanged (correctly reflects the *current* runtime tag, same as `any` today).
- `===`/`!==` → `emitAnyEquals`, unchanged.
- Arithmetic, and use as if it already had a narrowed concrete type → still a clean compile error, identical to `any` today. **Flow-based narrowing (TypeScript's `if (typeof x === "string") { /* x: string here */ }`) is explicitly out of scope for V1** — this compiler has no flow-typing infrastructure anywhere else (`inferExprType` is a pure bottom-up, non-flow-sensitive pass), and adding narrowing here would be a new class of analysis, not a reuse of existing machinery. A user who needs the narrowed value must currently accept the same Staged-V1 limitation `any` already has: usable for declare/assign/reassign/print/`typeof`/`===`, not much else, until narrowing (or a manual "as" cast, itself not implemented) exists. Noted explicitly as a real, known gap, not silently dropped.

### Guard relaxation, precisely

The change to `emit_func.go`'s existing guards (`:65`, `:96`, `:833`, `:840`) and `emit_dynamic.go`'s `containsDynamicElement`:

```
// before: pty.IsDynamic || containsDynamicElement(pty)   → always reject
// after:  (pty.IsDynamic && pty.UnionMembers == nil) || containsDynamicElementUnconstrained(pty)
```

i.e. the reject condition narrows from "any dynamic-shaped type" to "an *unconstrained* dynamic-shaped type" — bare `any`/`unknown` keep being rejected in these positions exactly as ADR-00008 left them; only a type that also carries a non-empty `UnionMembers` is now allowed through, and immediately gets the member-set check described above instead of a free pass.

## Open questions

- **Uninitialized `let x: T | U;` with no initializer.** `any`'s existing behavior boxes `undefined` unconditionally regardless of declared shape. For a union that doesn't include `undefined` as a member (e.g. `let x: string | number;`), doing the same thing would let an "impossible" tag state exist. Leaning toward: require an initializer for any union that doesn't include `undefined`/`null` as a member (clean compile error otherwise), mirroring how a non-nullable concrete type already behaves — not committed, needs deciding during implementation.
- **Object/interface/array members** (`string | SomeInterface`, `T[] | null` beyond today's already-working nullable-array case, etc.) — explicitly deferred past V1, see Design. Real demand exists (TDD-00026's `body: string | ArrayBuffer` is exactly this shape) but needs its own design pass for how `emitDynamicToString`/`emitAnyEquals`/member-set-checking handle a heap-shaped payload behind the tag, not just a scalar one.
- **Flow-based narrowing** (`typeof x === "string"` narrowing `x`'s effective type inside the branch) — explicitly deferred past V1, see Design. No existing flow-typing infrastructure to build on; would need its own scoping pass if picked up.
- **Whether a union type is itself a valid member of another union** (`(string | number) | boolean` vs. requiring the flattened `string | number | boolean` form) — parser currently builds unions via right-recursion one `|` at a time, so nested unions would naturally flatten already; worth an explicit test either way but not expected to need new design.
