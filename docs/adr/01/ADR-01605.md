# ADR-01605: Windows stack overflow in Workers; Worker paths from URLs

- **Relations**: Implements TDD-00249 (Stage 2, Windows), Extends ADR-01599
- **Date**: 2026-10-13

## Context

BACKLOG §0 listed stack overflow off the main thread (a generator, a
connection fiber, a goroutine, a Worker) as not being a RangeError. On
Windows the vectored handler of ADR-01599 covered the main thread.

## Investigation

Recursing to overflow on Windows, each context separately:

- main thread, generator, async task, HTTP connection fiber, goroutine:
  RangeError already. Win32 fibers carry the system's guard page, and the
  vectored handler is the process's.
- Worker thread: `0xC0000005`. `SetThreadStackGuarantee` is per thread; a
  Worker thread had none, so the handler had no stack left below the guard
  page and faulted.

Writing the Worker case surfaced two path bugs:

- `new Worker(new URL(...))` used the URL's `pathname`, `/R:/x/w.ts` on
  Windows; Node uses `fileURLToPath` (`R:\x\w.ts`).
- The worker module registry matched paths with `strcmp`; on Windows a path
  with `\` did not find a module registered with `/`.

## Decision

- `stackguard.c` exports `__kml_stack_guard_thread()`, which a Worker
  thread calls first on Windows (`worker.c`), keeping the same 64 KB the
  main thread reserves.
- `Worker` converts a `file:` URL as `fileURLToPath` does (a local helper:
  importing `url.ts` from `worker_threads.ts` closes an import cycle).
- The registry compares paths with `/` and `\` as one separator and without
  case on Windows.

## Side effects discovered

- `new Worker(new URL(import.meta.url))` is not recognised as a file that
  starts a worker of itself (only `new Worker(__filename)` is): BACKLOG §0.

## Verification

Windows 11: `TestE2EStackOverflowEveryContextWindows` (main, generator,
task, handler, goroutine, Worker: each a RangeError). POSIX's fiber and
thread stacks stay in BACKLOG §0.
