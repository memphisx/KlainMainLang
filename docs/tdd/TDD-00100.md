# TDD-00100: URLPattern

- **Status**: Implemented
- **Date**: 2026-08-23

## Context

`URLPattern` is the last unimplemented row on the URL status page. It's the WHATWG route-matching API (`urlpattern.spec.whatwg.org`): a pattern per URL component (`pathname: "/books/:id"`), with `.test(url)` and `.exec(url)` extracting named groups. For this project's stated microservice direction it's the standard way to express `http.listen` routing without hand-rolled string splitting, which makes it worth more than its conformance row.

The full spec surface is large (path-to-regexp grammar with `{}` groups, `+`/`?`/`*` modifiers, inline regex groups, per-component canonicalization, a `URLPatternResult` object with per-component `{input, groups}` records, base-URL resolution, and a constructor-string parser that splits one string into components). A V1 has to pick a subset and a result representation this compiler's fixed-shape object model can express.

## Design

**Pattern → regex, at construction, in embedded C.** Each component pattern compiles to an anchored PCRE2 regex once, in the constructor — reusing the PCRE2 dependency RegExp already links (`-lpcre2-8`) and the embedded-C-runtime pattern `json_parse.c`/`bigint`/`dtoa` established: a self-contained `urlpattern.c` implementing a `__kml_urlpattern_*` ABI, compiled alongside the program only when used. PCRE2 function prototypes are declared in the C file directly (no `pcre2.h` include), the same header-less approach the emitted IR takes, so no include-path lookup is needed.

**Input URL parsing via libcurl's URL API** — the same `curl_url`/`curl_url_get` calls `new URL(...)` already uses, called from the C runtime. `.test`/`.exec` therefore link `-lcurl` (plus `-lpcre2-8`), both already conditional-link libraries.

**Constructor: object-init form only.** `new URLPattern({ pathname: "/books/:id", hostname: "{{...}}" })` with any subset of `protocol`, `hostname`, `port`, `pathname`, `search`, `hash`; an omitted component defaults to `*` (matches anything), per spec. Component values may be runtime strings. The constructor-string form (`new URLPattern("https://example.com/:id")`), `baseURL`, and `username`/`password` components are clean compile-time rejections. An init that isn't an object literal is a clean rejection too (the component set must be known at compile time; the *values* need not be).

**Pattern grammar subset**: literal text (regex-escaped), `\x` escapes, full-wildcard `*` (→ `.*`, group not exposed), named groups `:name` (pathname → `[^/]+`, hostname → `[^.]+`, others → `.+`), and the `?` optional modifier on a named group — for a pathname `/:name?` the preceding `/` folds into the optional group (`(?:/([^/]+))?`), matching the spec's full-segment grouping. `{}` groups, `+` modifiers, and inline `(...)` regex groups are rejected at construction with a catchable `TypeError` (the spec's own error type for an invalid pattern). Group names are tracked positionally in the C runtime (no PCRE2 name-table API); regexes compile `PCRE2_ANCHORED | PCRE2_ENDANCHORED` so a component pattern must match the whole component.

**Matching semantics**: the input URL is parsed with libcurl; an unparseable input makes `.test` return `false` and `.exec` return `null` (no throw). Components compared: scheme (no `:`), hostname, port (`""` when absent), path (`"/"` when absent), query and fragment without their `?`/`#` prefixes.

**`.exec` result: `Map<string, string> | null`.** The spec's `URLPatternResult` (per-component `{input, groups}` records with `undefined` for unset optional groups) needs per-component dynamic-key objects — exactly the dynamic-object model this compiler doesn't have ([TDD-00068](TDD-00068.md)). Options considered:

1. A fixed-shape result object with six `Map` fields (`result.pathname.groups`-shaped) — closest to spec, but each `.groups` would still be a Map, and the intermediate records add allocation and surface for no information the merged form doesn't carry.
2. **One merged `Map<string, string>` of every named group across all components** (chosen) — the actual use case (route params) reads groups by name; a name collision across components is the pattern author's own ambiguity. Null on no match preserves the `if (m)` idiom. Unset optional groups are simply absent from the Map (`.get` → `null`), the closest analogue to the spec's `undefined`.
3. Groups-as-parallel-arrays — strictly worse ergonomics than 2.

**Result type**: `URLPatternType()` is a flagged fixed-shape object storing the six (defaulted) component pattern strings — so `pattern.pathname` etc. read like the spec's readonly component accessors via the ordinary field machinery — plus a hidden `__kml_handle` pointer to the C-side compiled state, the same hidden-field trick `Response.__kml_pending` uses. `.test`/`.exec` dispatch on the `IsURLPattern` flag in `emit_call.go`, ahead of the string/RegExp overloads of the same names.
