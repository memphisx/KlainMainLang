# ADR-01308: WHATWG URL encoding, opaque URLs and origins

- **Relations**: `Extends ADR-00076`, `Extends ADR-00874`
- **Date**: 2026-09-30

## Context

`new URL("http://example.com/a b")` threw `Invalid URL`, where Node
percent-encodes the space (BACKLOG 50). Probing further showed more gaps
against Node:

- A non-ASCII byte in a path or query stayed raw (Node: `%C3%A9`).
- `{`, `}`, `^` and `` ` `` in a path stayed raw.
- An opaque URL did not parse at all: `mailto:x@y`, `urn:isbn:1` and
  `data:,hi` all threw.
- A non-special hierarchical URL (`foo://h/p`) reported a tuple origin, where
  Node reports `"null"`.
- `url.toString()` and `url.toJSON()` did not compile.

## Investigation

- The URL is libcurl's URL API. Its parser rejects a space unless
  `CURLU_ALLOW_SPACE` is set. Even then it stores the space raw, unless
  `CURLU_URLENCODE` is also set.
- `CURLU_URLENCODE` diverges again: lowercase hex, `+` for a space in the
  query, and it leaves `{}^`` ` raw. It was tried and dropped.
- curl reads hierarchical URLs only, so `mailto:x@y` has no parse.
- The WHATWG URL Standard defines the input handling directly. It strips
  leading and trailing C0 controls and spaces, and removes tabs and newlines.
  It then percent-encodes each component with its own encode set:
  - fragment: C0, space, `"` `<` `>` `` ` ``
  - query: C0, space, `"` `#` `<` `>`, plus `'` for a special scheme
  - path: the query set plus `?` `^` `` ` `` `{` `}`
  - an opaque path: C0 only
- Only http, https, ws, wss and ftp have a tuple origin.

## Decision

- `__kml_url_whatwg_encode` (`stringsrc/string.c`) prepares every URL string
  before curl sees it, as above: strip, drop tabs and newlines, and encode the
  path, query and fragment with their sets (uppercase hex). The authority is
  left to curl. `CURLU_ALLOW_SPACE` is set so an opaque path's kept space
  parses.
- An opaque URL (a non-special scheme not followed by `/`) bypasses curl.
  `__kml_url_opaque_part` splits it into `href` (scheme lowercased),
  `protocol`, `pathname`, `search`, `hash` and origin `"null"`, and
  `searchParams` is built from its query. `new URL`, `URL.parse` and
  `URL.canParse` all take this path.
- The setters of an opaque URL follow WHATWG, and so does a `searchParams`
  writeback into one:
  - `search`/`hash` re-encode their part (`__kml_url_opaque_set`).
  - `pathname` and the host parts are no-ops.
  - An `href` set to an opaque URL splits it.
- `origin` is `protocol//host` only for a tuple-origin scheme
  (`__kml_url_tuple_origin`), else `"null"`.
- A special scheme's non-ASCII host is case-folded and each non-ASCII label
  punycoded (`__kml_url_idna`, casemap.c, RFC 3492). `url.domainToASCII`
  goes through the same mapper, and `url.domainToUnicode` decodes `xn--`
  labels (`__kml_idna_to_unicode`). So the result no longer depends on
  libcurl's IDN backend, which the Mac's lacks (BACKLOG 104).
- `url.toString()`/`url.toJSON()` return the `href`.
- `URL.parse`'s failure path now frees its curl handle.

## Implementation notes

The encoder is idempotent: `%` is never encoded, and its output is plain
ASCII. So a string that is encoded again (a base, or a setter's re-parse) is
unchanged. It is plain C in `string.c` with no library dependency. The scheme
comparison is its own lowercase loop, since `strncasecmp` is not in the
Windows CRT.

## Side effects discovered

- UTS 46's mapping beyond case folding (NFC, full-width forms) is not
  applied: `ＥＸＡＭＰＬＥ.com` punycodes where Node reads `example.com`.
  The URL row carries this as its caveat.

## Verification

`TestE2EURLIdnaHosts` and `TestE2EURLWhatwgEncodingAndOpaque`
(tests/url_test.go) match Node on
macOS arm64. It covers spaces, non-ASCII and special characters, relative
references against a base, six opaque URLs, their setters and `searchParams`
writeback, non-special and `file:` origins, `href` set across kinds, and
`URL.parse`/`URL.canParse`.
