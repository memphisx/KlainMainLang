# TDD-00176: General `as T` on dynamic values — projection, rejection, or erasure?

- **Status**: Not Started
- **Date**: 2026-09-05

## Context

ADR-00715 carved one exception out of ADR-00371's full type-assertion
erasure: `as T` directly on `JSON.parse(...)` / `.json()` supplies the
projection target, because that matches the assertion's real static effect
in TypeScript and those calls already have a type-directed deserialization
path to hand the target to. The mechanism (`CallExpression.AssertedType`)
was deliberately built as data on the AST rather than a parser rewrite so
that *what consumes it* can grow without touching syntax.

The general question stays open: what should `-compat=strict` do with
`expr as T` where `expr`'s inferred type is `any`/dynamic and `T` is
concrete? Today it is erased — the value silently stays a NaN-boxed
dynamic, and later typed uses either box-coerce per operation or hit the
`any` limits. That is neither TypeScript's static story (the expression
*is* a `T` afterwards) nor a native-representation story (nothing
re-represents). See also the `-compat=js` gap analysis
(the operator-on-`any` bucket is that lane's top regression class):
strict-mode programs that lean on erased assertions effectively smuggle
the same `any` soup into the strict lane.

## Design space

1. **Runtime projection** (`any as T` emits a dynamic→concrete
   projection): the box is inspected and materialized into `T`'s native
   representation — for scalars a checked unbox; for object/array types a
   tree walk structurally identical to the dynamic half of the JSON
   projection (`__kml_dynjson_*` shapes → structs/buffers). Faithful to
   TS's *intent* (narrowing) but stronger than TS's *semantics* (TS
   asserts without checking or converting; a wrong assertion is UB there,
   here it would throw or default-fill). That divergence needs its own
   justification and wording if chosen.
2. **Strict-mode rejection**: `any as T` on a representation-changing pair
   becomes a clean compile error steering toward the typed declaration
   forms (or `-compat=js`). Keeps strict honest; breaks real-world TS that
   uses assertions as its main narrowing tool — likely too hostile.
3. **Status quo erasure** (per-shape carve-outs only): each `any`-producing
   API with a type-directed path gets its own ADR-00715-style attachment
   as need arises (`structuredClone`? worker messages? `Response.body`
   readers?). Cheapest, but accumulates special cases the docs must
   enumerate.

Orthogonal sub-questions:

- Should the *scalar* subset ship first (`(x as number) + 1` unboxing with
  a runtime tag check) — small, high-frequency, and exactly the
  operator-on-`any` shape the conformance data ranks first?
- Does a projection `as` compose with the deep free (ADR-00716) — a
  projected tree is transitively fresh by construction, so it should
  qualify like a JSON.parse tree does?
- What does `-compat=js` do if strict gains projection — same behavior
  (fidelity argues yes: real TS on top of JS semantics still narrows
  statically) or keep the box (js-mode declarations are any-backed
  anyway)?
