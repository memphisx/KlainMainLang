# ADR-00384: JSDoc class/documentation tags + `import()` types (TDD-00125 Stages 5–6)

- **Relations**: Extends [ADR-00380](ADR-00380.md), [ADR-00383](ADR-00383.md); Implements [TDD-00125](../tdd/TDD-00125.md)
- **Date**: 2026-08-26

## Context

After Stage 4 the JSDoc *typing* surface was complete. The remaining tags are
the class/visibility/documentation group (`@public`/`@private`/`@protected`/
`@readonly`/`@override`/`@extends`/`@implements`/`@this`/`@enum`/`@satisfies`,
and `@deprecated`/`@see`/`@link`/`@author`) and the `import("./m").T` type
reference.

## Investigation

Every one of the class/visibility/documentation tags is already inert: the
lexer emits a single JSDoc token, `jsdoc.Parse` reads all tags generically, and
only `@type`/`@param`/`@returns`/`@template`/`@typedef`/`@callback` are acted on
— so the rest are silently accepted and never cause an error. Verified by repro:
a class carrying `@implements`/`@private`/`@readonly` on its members alongside
`@type`/`@returns` compiles and runs, and the typing tags still apply.

This matches how TypeScript and this compiler already treat the *keyword* forms:
TS `private`/`public`/`protected` are accepted and erased here (not enforced),
TS `implements` is accepted structurally, and TS `readonly` is erased (a parse
gap for the field-modifier form). The JSDoc tags are the documentation-comment
spelling of the same erased semantics.

## Decision

**Stage 5 — accept and erase.** The class/visibility/documentation tags are
recognized as accepted-and-erased, consistent with the equivalent TS modifiers,
and flipped to ✅ with an "erased, not enforced" caveat (so none count toward
Strict). `@enum` on a `const` object needs nothing — the object already supports
value access (`Dir.Up`); it is a plain object, not a nominal enum type. Only
`@import` (a comment-form import statement to synthesize) and `@constructor`
(function-as-constructor, a construct this compiler doesn't have) stay ❌.

**Stage 6 — `import("./m").T` types.** `normalizeClosureType` drops the
`import("...")` qualifier to the bare type name. Under whole-program
compilation a type exported by any module in the build is registered by its
bare name, so `import("./shapes").Point` resolves to `Point` whenever that
module is part of the program (typically because the file also imports from it
normally). The `typeof import(...)` value-query form is left untouched. This
completes the TDD's Stage 6 (`import()` types + `@satisfies`, the latter landed
in Stage 5).

## Implementation notes

- No parser/codegen change was needed for the Stage-5 tags — the work is a
  deliberate, tested acceptance and honest status documentation, not new
  behavior. A regression here would be one of these tags *starting* to break
  compilation, which the new E2E test guards against.
- `@import` is intentionally left unsupported: the `import("./m").T` reference
  plus a normal `import` already covers the "use a type from another module"
  case, so synthesizing a comment-form import adds surface for little gain.

## Verification

- `TestE2EJSDocClassAndDocTags` (a class with `@implements`/`@private`/
  `@readonly`/`@override` + `@type`/`@returns`; doc-only tags inert),
  `TestNormalizeClosureType` (the `import("...")` rewrite among the Closure
  rewrites), and manual multi-module repros for `import("./m").T` in `@type`
  and `@param`.
- `go build`, `make test-par`, `make examples`, `make conformance` run.
- Verified on Apple Silicon (M4, macOS).
