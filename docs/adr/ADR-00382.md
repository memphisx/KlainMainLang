# ADR-00382: `@template` JSDoc generics (TDD-00125 Stage 3)

- **Relations**: Extends [ADR-00380](ADR-00380.md); Implements [TDD-00125](../tdd/TDD-00125.md)
- **Date**: 2026-08-26

## Context

Stages 1–2 gave untyped functions `@param`/`@returns` types and named
`@typedef`/`@callback` types. The remaining common typing tag is `@template` —
JSDoc's form of a `<T>` generic:

```js
/**
 * @template T
 * @param {T[]} arr
 * @returns {T}
 */
function head(arr) { return arr[0] }
```

## Decision

`@template` sets the function's existing generic machinery rather than adding a
new one. `jsdoc.Comment.Templates()` returns a `TemplateParam{Name, Constraint}`
per declared parameter — one tag may list several comma-separated names
(`@template T, U`), and a `{Base}` constraint applies to the first name only
(matching TypeScript). `applyJSDocFuncTypes` (which already fills `@param`/
`@returns`) sets `fd.TypeParams` / `fd.TypeParamConstraints` from them when the
function has no inline `<T>` list, so the function is thereafter an ordinary
generic: registered nowhere in `e.funcs`, deferred to on-demand monomorphization
at each call site ([TDD-00010](../tdd/TDD-00010.md) V1 / [TDD-00037](../tdd/TDD-00037.md)),
its `@param {T}`/`@returns {T}` positions resolving the bare `T` per
instantiation exactly as an inline generic's do.

Because the `@template` handling runs inside `applyJSDocFuncTypes` — before the
existing `@erased` check in `parseFunctionDeclaration` — a `@template T` + a
`@erased` tag compose: the type-param list is set first, satisfying `@erased`'s
"must declare a type parameter" requirement.

## Implementation notes

- Inherits every TS-generics V1 limit unchanged: monomorphization needs an
  inferable `T`/`T[]`-typed parameter (no explicit call-site type arguments for
  a function), and the param/return type grammar is `@type`'s subset. No new
  codegen — the generic path is entirely reused.
