# TDD-00079: Mapped and conditional types

- **Status**: Implemented
- **Date**: 2026-08-19

## Context

Mapped and conditional types are the last `❌` pair in the Type System status
page's *Type system features* table. The full scope is wanted: user-defined
mapped types `{ [K in keyof T]: … }` and the common built-in utility types
(`Partial`/`Required`/`Readonly`/`Pick`/`Omit`/`Record`), **and** conditional
types `T extends U ? X : Y` with `infer`.

The enabling insight is that this compiler **monomorphizes** — every type is
concrete by the time codegen runs — so none of this needs `tsc`'s lazy type-level
interpreter. A mapped or conditional type can be **evaluated at `resolveType`
time to a concrete `ObjectType`** (or an existing scalar/array/map type), given
concrete inputs, then fed to the unchanged object machinery. That is what makes
the feature tractable here rather than a research project.

Scoping it now also closes a real silent-wrong-result bug: today `Partial<User>`
resolves to `User[]` (the generic `ElemType` fallback in `resolveType`,
emitter.go:719), and a bare unknown `Name<Args>` resolves to `i64`
(`ResolveTypeName`, types.go:1298) — neither is a clean rejection.

## Design

### The seam to extend (already built)

`substituteGenericType` (emit_generics.go:98) + `instantiateGenericInterface`
(emit_generics.go:312) + the `resolveType` generic-interface hook (emitter.go:700)
already turn "generic interface + concrete type args" into a concrete
`ObjectType` by walking the declaration's fields and substituting each type
parameter. Mapped/conditional evaluation is the same shape: a **field-set rewrite**
(mapped) or a **compile-time branch selection** (conditional), both producing a
concrete `ObjectType`. No new runtime representation, no new codegen — the whole
feature is compile-time type evaluation feeding existing machinery.

### The three genuinely-missing prerequisites (the real work)

- **P-A — type-level grammar/AST.** New tokens (`keyof`, `infer`, `readonly`),
  AST nodes, and parser support for: `keyof T`, indexed access `T[K]`, string-
  literal types (`"a"`), the mapped form `{ [K in keyof T]: F }` with `?`/`-?`/
  `readonly`/`-readonly` modifiers and `as` key remapping, and the conditional
  form `T extends U ? X : Y` / `infer R`. None of this exists — `keyof` isn't
  even lexed.
- **P-B — field-level optional/readonly state.** `parseInterfaceDecl` consumes
  and **discards** the `?` marker (parser_types.go:379–380, "treated as required
  for codegen"); `readonly` isn't a lexer keyword. `ast.AnnotField` and the
  codegen `Field` (types.go:10) carry no optional/readonly bit. Partial/Required/
  Readonly are modifier transforms over exactly this state, so it must exist
  first. (Bonus: it also gives real optional-field semantics, currently absent.)
- **P-C — a general structural assignability predicate** `assignable(a, b Type)
  bool`. Conditional types need "does `T` extend `U`." Today only a *nominal*
  `implements` conformance loop (emit_classes.go:1012, name+IR-string field
  matching) and a scalar-union match (`unionAllowsAssignmentFrom`,
  emit_dynamic.go:126) exist — neither generalizes. The `implements` loop is the
  best template for the object-structural part.

### Staged delivery (each stage independently shippable)

**Stage 0 — foundation + drive-by bug.**
- Add a **clean rejection** for an unknown `Name<Args>` in `resolveType`, so
  partial utility-type recognition never leaves a silent-wrong hole (this also
  fixes the `Partial<User> → User[]` bug independently of the rest).
- Add **string-literal types** (`"a"`), at least in key positions — the input to
  `Pick`/`Omit`/`Record` and `as` remapping. (Open question: general vs key-only.)

**Stage 1 — built-in utility types as field transforms** (highest everyday value).
Recognized by name at the `resolveType` generic branch, like the Promise/Map
special-cases, and evaluated against the resolved type argument:
- `Pick<T,K>` / `Omit<T,K>` — filter the field set by a string-literal-union `K`.
- `Record<K,V>` — literal-union `K` → an object with those keys typed `V`;
  `K = string` → `Map<string,V>`.
- `Partial<T>` / `Required<T>` / `Readonly<T>` — modifier transforms (needs P-B).

  *Honest caveat:* because the object model already zero-fills omitted literal
  fields (calloc, ADR-00157) and has no mutation-checking, `Partial<T>` is
  structurally close to `T` and `Readonly<T>` is a no-op until those semantics
  exist. The clearly-visible wins are `Pick`/`Omit`/`Record` (they change the
  field set). This is worth stating plainly rather than overselling Partial.

**Stage 2 — general user-defined mapped types** `{ [K in keyof T]: F<T[K]> }`.
Needs P-A (`keyof` + indexed access `T[K]` + mapped grammar). Evaluate
homomorphically: for each field of the concrete `T`, emit a field whose type is
the mapped body with `K`/`T[K]` substituted, applying the `?`/`readonly` modifier
deltas and any `as` key remap. This is `instantiateGenericInterface` generalized
from "substitute `T`" to "rewrite the field set."

**Stage 3 — conditional types** `T extends U ? X : Y` + `infer`.
Needs P-A (conditional grammar) + P-C (structural assignability). Evaluate at
`resolveType`: resolve `T` and `U` concretely, `assignable(T,U)` selects the
branch, and `infer R` binds a captured sub-type by structural matching against
`U`. Also unblocks constrained type parameters `<T extends X>`, currently a hard
parser rejection (parser.go:118), since conditionals reuse `extends`.
Distributive-over-unions behavior is an open question (union V1 is scalar-only,
so **non-distributive** is the likely V1).

### Recommended sequence

Stage 0 → 1 (utility types, the 80/20) → 2 (general mapped) → 3 (conditional).
Each is a shippable increment with its own ADR. Stage 3 is the largest because
P-C (structural assignability) is net-new; it's designed here so it isn't
rediscovered later.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Substitution seam (`substituteGenericType`/`instantiateGenericInterface`/`resolveType` hook) | Done | Extend, don't invent (emit_generics.go:98/312, emitter.go:700) |

## Open questions

- **Optional-field semantics depth**: just a marker Partial/Pick consume, or real
  nullable-on-read semantics? Given the lenient zero-fill model, how much does an
  `Optional` bit actually change observable behavior?
- **Readonly enforcement**: no mutation-checking exists — is `Readonly<T>` an
  accepted-but-unenforced no-op for V1, or do we add assignment-time readonly
  checks (a separate sub-feature)?
- **String-literal types scope**: key positions only (Pick/Omit/Record/remap), or
  a general string-literal type usable anywhere (larger, interacts with unions)?
- **`keyof` result as a first-class type**: does `keyof T` (a union of string-
  literal keys) need to be independently usable, or only consumed internally by
  mapped/Pick/Omit?
- **Distributive conditionals over unions**: distribute, or treat the union as an
  opaque operand in V1?
- **`assignable` fidelity**: structural width/depth subtyping, or start with the
  `implements`-style name+IR-string field match and widen later?
