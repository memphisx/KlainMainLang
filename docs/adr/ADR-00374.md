# ADR-00374: Accept a class with bare (uninitialized) fields and no constructor

- **Relations**: Extends [ADR-00157](ADR-00157.md); Implements [TDD-00063](../tdd/TDD-00063.md), [TDD-00121](../tdd/TDD-00121.md)
- **Date**: 2026-08-26

## Context

The TypeScript accept/reject conformance oracle's false-reject reason
histogram ranked `class '%s' has a field with no initializer and no constructor
to initialize it` at 35 cases. The construct — `class C { x: number }`, a field
declared with a type but no initializer and no constructor — is one of the most
common shapes in real TypeScript, and TypeScript accepts it. This compiler
rejected it outright.

## Investigation

Instances are allocated with **calloc**, not malloc
(`emit_classes.go:emitNewExpression`, the `@calloc(i64 1, …)` call), precisely
so an unverified field reads as a deterministic zero rather than garbage
([ADR-00157](ADR-00157.md)). A class *with* a constructor that leaves a field
unassigned already relies on this — verified: `class P { x: number; y: number;
constructor(){ this.x = 5 } }` compiles and reads `p.y === 0`.

The rejection was therefore vestigial. `registerClasses`
(`emit_classes.go`) only synthesized a constructor when *every* own field had an
initializer (`allFieldsInit`), falling through to the error otherwise. The
generic-class path (`emit_generics.go`) carried the identical restriction.
`classFieldInitStmts` already skips fields with no initializer, so a synthesized
constructor over a partially-initialized class runs exactly the initializers
that exist and leaves the rest calloc-zeroed.

## Decision

Drop the `allFieldsInit` precondition on constructor synthesis. When a class has
own fields and no explicit constructor, synthesize a constructor that runs
whatever field initializers exist; the remaining fields keep their calloc'd
zero. This accepts the bare-field-declaration form with no new runtime
machinery.

The non-generic error case is narrowed, not deleted: it now fires only when a
derived class adds own fields *and* the base has a rest-parameter constructor —
the one shape whose implicit pass-through `super(...args)` isn't representable
without a general spread-call mechanism this compiler lacks (the same limitation
the no-own-fields pass-through case already carries). Its message now names that
specific situation. The generic path drops the error entirely, since a generic
class cannot `extends`.

## Implementation notes

- `codegen/llvm/emit_classes.go`: relaxed the synthesis `case` condition,
  narrowed and re-messaged the error `case`, removed the now-unused
  `allFieldsInit` binding and the dead `classHasOwnFieldInit` helper.
- `codegen/llvm/emit_generics.go`: merged the `allFieldsInit` case into the
  general `len(ownFields) > 0` synthesis case; removed the error case.

## Side effects discovered

The pre-existing ADR-00157 sharp edge is unchanged and unrelated: a bare
*reference*-typed field (`name: string`) defaults to a null pointer, so
dereferencing it (`p.name.length`) segfaults — exactly as it already does for a
constructor that leaves the same field unassigned. This is the zero-convention's
known limitation, not introduced here.
