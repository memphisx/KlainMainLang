# ADR-01031: `err.errno` is libuv's own numbering on Windows (`ENOENT` → `-4058`)

- **Relations**: `Implements TDD-00180` (open question 2); `Extends ADR-00770`, `ADR-00784`, `ADR-01021`
- **Date**: 2026-09-21

## Context

[ADR-00770](ADR-00770.md) gave errors Node's numeric `err.errno` as the negated OS errno and recorded one divergence: on Windows Node reports libuv's fixed `UV__E*` values (`ENOENT` is `-4058`), while this port — whose shim normalises errno to Linux numbers so `err.code` matches — reported `-2`. It was left as "low-value". It is observable, and nothing about native compilation prevents the faithful value.

## Investigation

`uv/errno.h` defines each `UV__E*` as `UV_ERR(E*)` *unless* the platform is Windows, where the `-4xxx` fallbacks are always taken (`#if defined(EACCES) && !defined(_WIN32)`). The mapping is therefore a pure function of the error *name*, and the IR already has the (errno, name) table that drives `err.code`.

`err.errno` is produced at four sites, each negating inline: `__kml_fs_throw2` (fs), `__kml_net_conn_errobj` (net), the spawn `'error'` object (child_process) and the `http` listen error.

## Decision

One IR helper, `@__kml_uv_errno(i32) -> i32`, emitted alongside `@__kml_errno_code` (so every site that can name an errno can translate one). On POSIX it is `0 - e`, as before. On Windows it is a switch generated from `errnoCodePairs()` through the `uvWinErrno` name→value table; an errno with no libuv name yields `UV_UNKNOWN` (`-4094`), and `0` stays `0`. The four sites call it instead of negating.

The translation happens only at the error-object boundary: the shim and the emitters keep Linux errno numbers internally, so nothing host-specific leaks into the IR's control flow.

## Implementation notes

`runtime_fs.go` (`uvWinErrno`, `emitUVErrno`, called from `ensureErrnoCode`), `runtime_net.go`, `runtime_childprocess.go`, `runtime_http.go`. `EOPNOTSUPP` and `ENOTSUP` share `-4049`, as in libuv.

## Side effects discovered

None.

## Verification

Windows 11 (26200): `TestE2EFsErrorErrno` and `TestE2EChildProcessSpawnErrorCodeErrno` now expect `-4058` on Windows and `-2` elsewhere (`uvENOENT()`); `TestE2EWinAccessDeniedIsEPERM` asserts `-4068` for `EISDIR`; `TestE2ENetConnectFailureEmitsError` passes. POSIX behaviour is byte-identical by construction (`sub 0, e`); not re-run on Linux/macOS here.
