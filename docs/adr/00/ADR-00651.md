# ADR-00651: Strict-lane clean rejection of an incompatible scalar reassignment

- **Relations**: `Implements TDD-00162` (the strict half; the compat=js widening + implicit-any policy stay open in the TDD)
- **Date**: 2026-09-03

## Context

The invalid-IR backlog histogram (ADR-00650's scoping) found that a large
`language/expressions`/`language/statements` sub-family of the Test262
`CLANG_ERROR` files is one root cause: a binding reassigned across types. The
strict lane inferred a binding's type from its initializer / first assignment
and then, on a later incompatible assignment, emitted a bare
`store <slotIR> <value>` whose value carried a different LLVM type — invalid IR
clang rejects (`constant expression type mismatch: got 'ptr' but expected
'i64'/'double'`, `floating point constant invalid for type`). This was a
long-standing strict-lane gap, not a recent relaxation: strict silently
type-picked and miscompiled rather than rejecting.

TypeScript itself infers the binding's type (`let x = 5` is `number`) and
reports the incompatible assignment (`x = 'hi'`) as a type error. The project's
two-tier rule says the strict lane rejects what it can't represent cleanly; a
variable that genuinely holds different types must be annotated `: any` (which
already works — the D1 dynamic box) or compiled with `-compat=js`.

## Decision

In `emitAssign`'s scalar-variable path (emit_exprs_assign.go), after coercing
the RHS to the binding's type, reject when the coerced value's storage IR still
differs from the slot's:

```go
if rhs.Ty.IR != sym.Ty.IR {
    return error "cannot assign a <kind> value to '<name>' (a <kind>) — a
      variable's type is fixed at its declaration; annotate it `: any` for a
      value that holds different types, or compile with -compat=js"
}
```

This fires exactly where the emitted `store` would be type-invalid, so it can
only reclassify a program that was already failing to compile — never one that
worked. All the composite/aggregate targets (array, object, dynamic, nullable
scalar) return from their own branches above, so this scalar-store site is the
only place an IR mismatch reaches the emitter. A dynamic (`: any`) binding takes
the boxing branch instead and is unaffected. The diagnostic runs the identifier
through `pureDisplayName` so the source name shows, and names each type via
`scalarTypeKind` (falling back to the IR).

## Investigation

On the target `language/expressions` cluster the guard reclassifies ~7/10
sampled invalid-IR files to a clean rejection. It deliberately does *not* touch
the other large store-mismatch family — a `ptr`-typed value used directly in a
numeric op (`add i64 %ptr`, `trunc i64 %ptr`) — which is an arithmetic-site
coercion gap (TDD-00162's operator/coercion follow-on), not a reassignment
store. One residual reassignment shape still slips through
(`var x; x = undefined; x = (null ?? 42) || 43`): there `coerce` mislabels the
value's type as the slot's while keeping a numeric register, so the guard's
`rhs.Ty.IR` check passes — a `coerce`-honesty bug recorded against TDD-00162,
not fixed here.

## Side effects discovered

None. The full `go test ./tests/` suite passes unchanged — the guard rejects
only inputs that previously produced invalid IR.

## Verification

- `tests/exprs_test.go`: `TestE2EIncompatibleReassignmentRejectedInStrict` —
  rejects `let x = 5; x = 'hi'`, untyped-first-assignment then incompatible,
  and string/boolean variants; keeps compatible reassignment and the `: any`
  escape hatch compiling and running.
- `go build`, `go vet`, full `go test ./tests/` (exit 0). Mac (Apple Silicon).
