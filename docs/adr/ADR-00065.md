# ADR-00065: Implement Number.toPrecision/toExponential/toString(radix), Math.clz32/fround/imul, and Object.hasOwn/hasOwnProperty

- **Date**: 2026-07-28

## Context

Four small, self-contained gaps picked off `STATUS.md`'s roadmap as a quick-wins batch, at the user's request: each follows an existing dispatch/emission pattern closely enough that no new infrastructure was needed. Bundled into one ADR since they're an unrelated batch of small features done together, not one design — same precedent [ADR-00057](ADR-00057.md) set for a batch of small `Array.prototype` additions.

## Investigation

**`Number.prototype.toFixed(n)`** (`emitNumberToFixed`, `codegen/llvm/emit_strings.go`) was the template for `toPrecision`/`toExponential`: evaluate the receiver to a `double`, `sprintf` into a malloc'd buffer with a fixed-format string, return the buffer as a `TypePtr` string.

For `toPrecision`, empirically verified (via a standalone C program, not assumed) that plain `%.*g` strips trailing zeros — wrong, since JS's `toPrecision` always shows exactly `n` significant digits (`(1).toPrecision(4) === "1.000"`) — but glibc's `%#.*g` (the `#` flag) keeps them, matching JS for the common case. Also found and confirmed two real, narrower deviations from real JS the `#` flag doesn't fix: (1) when the rounded value has no fractional digits left, `%#g` still leaves a bare trailing `.` (`"1235."` instead of `"1235"`) — cheap to trim with a one-byte buffer check; (2) exact halfway-tie rounding can differ, since glibc's `%g` rounds half-to-even and JS's spec algorithm does not (confirmed `(1234.5).toPrecision(4)` gives `"1234."` via `%#.4g`, i.e. rounds to even 1234, not JS's 1235) — a narrow, rare-in-practice edge case, not fixed (would need a real correctly-rounded decimal conversion algorithm, disproportionate to this batch's scope).

For `toExponential`/`toPrecision`'s exponential branch, confirmed `%e`/`%g` always render a 2-digit, zero-padded exponent (`"1.23e+03"`) where real JS always uses the minimum digit count (`"1.23e+3"`) — a cosmetic-only difference (the numeric value is exact either way), documented rather than fixed (would need post-processing the exponent digits).

For `Math.clz32`/`fround`/`imul`, checked `emitMathCall`'s dispatch switch (`codegen/llvm/emit_call.go`) and confirmed no existing LLVM intrinsic usage anywhere in this compiler — `ensureMathFuncs` only declares libm functions. `llvm.ctlz.i32` is a standard IR intrinsic (not a libm call), so it needed its own `ensureCtlz32` following the same `usedX bool` + `emitGlobal("declare ...")` pattern, but with no `-lm` link requirement.

For `Object.hasOwn`/`.hasOwnProperty`, confirmed this compiler's object types are fully structural/static (every field a class/interface/object-literal type has is known at compile time — `Type.FieldIndex`, `codegen/llvm/types.go`) — so unlike real JS's runtime property check, this can be a compile-time-constant `true`/`false`, provided the key is a compile-time string literal. Checked `emitCall`'s `Object.*` static dispatch (`codegen/llvm/emit_call.go:92-109`, keyed on `mem.Object` being identifier `"Object"`) as the template for `Object.hasOwn(obj, key)`, and the `isDateMethodName`/`isResponseMethodName`-style early type-gated instance-method checks as the template for the `obj.hasOwnProperty(key)` instance-call form.

**Found and fixed a real dispatch-ordering bug of my own making while wiring this up**: the new `hasOwnProperty`/`toString` checks were initially placed *before* `emit_call.go`'s existing [TDD-00009](../tdd/TDD-00009.md) class-method-call dispatch — since a class instance's `Type` also has `IsObject: true` (by design, see [ADR-00063](ADR-00063.md)), a class declaring its own `toString()`/`hasOwnProperty()` method would have been silently shadowed by the new generic built-in behavior, exactly the class of bug that ADR already went to some care to avoid for the built-in array/string method chain. Caught by testing a class overriding both methods directly (not assumed), and fixed by moving the two new checks to *after* the existing class-dispatch block, so a class's own method always wins, matching real JS's prototype-chain resolution order (own property/method before the inherited default).

## Decision

Added four independent pieces of dispatch, each gated the same way the codebase's existing type-gated instance methods are (`mem.Property == "<name>" && <type predicate>(e.inferExprType(mem.Object))`, checked early — before the long unguarded built-in name chain, and after the class-method dispatch block):

- `emitNumberToPrecision`/`emitNumberToExponential` (`emit_strings.go`) — `sprintf`-based, as described above. A shared `numberToDouble` helper factors out the receiver-widening step both (and `toFixed`, left as-is) need.
- `emitNumberToStringRadix` (`emit_strings.go`) — no `sprintf` conversion exists for an arbitrary base, so this hand-rolls the classic repeated-`urem`/`udiv` digit loop, writing digits into a 70-byte buffer from the end backward (room for a sign + 64 base-2 digits + a null terminator) so the result can be returned as `buf+startIdx` with no `memmove` — the pre-placed null terminator at the buffer's last byte is already correctly positioned regardless of how many digits end up written. Gated by a new `isNumberTy` predicate (`IR != "ptr" && !IsDate`) placed next to the existing `isStringTy`, since a string's `IR` is also non-numeric-shaped but a plain `!IsObject && !IsArray && !IsFunc` check alone doesn't exclude it. Radix defaults to 10 when omitted; a non-integer receiver is truncated to its integer part first (documented, not fixed — real JS can expand fractional digits in the target base too).
- `emitMathClz32`/`emitMathFround`/`emitMathImul` (`emit_call.go`) — `clz32` via the new `llvm.ctlz.i32` intrinsic (`is_zero_undef=false`, so `clz32(0) == 32` matches real JS); `fround` via a plain `fptrunc double to float` / `fpext float to double` round-trip; `imul` via `trunc` both operands to `i32`, `mul i32`, `sext` back to `i64` — genuine 32-bit-wraparound integer multiplication, distinct from plain `*`'s double-precision (and therefore exact only up to 2^53) result, which is the entire point of `imul` existing in real JS.
- `emitHasOwnProperty` (`emit_objects.go`) — shared by both `Object.hasOwn(obj, key)` (added to the existing `Object.*` static switch) and `obj.hasOwnProperty(key)` (a new early type-gated check). Requires the key to be a string literal; a non-literal key is a compile error, not a silent always-false/true or a runtime scan this compiler has no field-name table to back.

## Implementation notes

Files touched: `codegen/llvm/emit_call.go` (dispatch wiring for all four, plus the ordering fix), `codegen/llvm/emit_strings.go` (`isNumberTy`, `numberToDouble`, `emitNumberToPrecision`, `emitNumberToExponential`, `emitNumberToStringRadix`, `writeDigitAndDecrement`), `codegen/llvm/emit_objects.go` (`emitHasOwnProperty`), `codegen/llvm/emit_exprs.go` (`inferExprType` cases for all four, placed after the existing class-dispatch check for the same shadowing reason as `emitCall`), `codegen/llvm/emitter.go` (`usedCtlz32` field), `codegen/llvm/runtime.go` (`ensureCtlz32`).

## Side effects discovered

None beyond the dispatch-ordering bug described above, caught and fixed before landing (see Investigation).
