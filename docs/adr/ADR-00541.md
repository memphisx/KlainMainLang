# ADR-00541: `klain:sync` Stage 1 — GMP goroutine scheduler, `go`, and CSP channels

- **Relations**: `Implements TDD-00143`
- **Date**: 2026-08-31

## Context

TDD-00143 scopes a Go-fidelity goroutine runtime as the marquee `klain:` opt-in:
real preemptive M:N concurrency, cheap goroutines, CSP channels, and `select`,
staged 1–5. Stage 1 is the valuable core that needs none of the precise-stack-map
machinery Stages 4–5 depend on: a GMP work-stealing scheduler, `go`, and
buffered/unbuffered channels whose blocking send/receive park the *goroutine*
(the OS thread keeps running other goroutines), plus the runtime hook a later
cooperative-preemption pass will call.

## Investigation

The repo's existing async/fiber/worker/channel runtime is **hand-emitted LLVM
IR**, not compiled C (only `gcsrc/gcshim.c` and the asset embedder are C). The
reusable primitives were mapped: the `ucontext` fiber core (`runtime_http.go`),
the Worker pthread + Boehm `GC_register_my_thread` pattern (`runtime_worker.go`,
TDD-00098), and the atomics lowering (`emit_atomics.go`). A GMP work-stealing
scheduler with `hchan` channels and goroutine-parking is far too much branch-
heavy control flow to hand-emit as IR; the webview binding (`webviewsrc/`)
established that an embedded C/C++ runtime links cleanly via `EmbeddedCSources`.
So the scheduler is a self-contained C runtime, matching the TDD's `klainsyncsrc/`
call, and built/tested standalone before any codegen wiring.

Two macOS `ucontext` facts were derived the hard way (isolated repros):
initial SP lands at the high end of the stack region (correct), but
`makecontext` **faults if the stack region contains any `PROT_NONE` page** — so a
low-end overflow guard page crashes on macOS, while the existing HTTP/generator
fibers already run on plain unguarded malloc'd stacks.

## Decision

Ship Stage 1 as an embedded C runtime `codegen/llvm/klainsyncsrc/klainsync.c`
linked only when a program imports `klain:sync` (gated by `usedSync`):

- **Scheduler (GMP).** One P (local run queue) per `GOMAXPROCS`, one pinned M
  (pthread) per P, a global run queue backstop, and half-queue work stealing.
  An M never self-terminates — it parks idle and is reaped by process `exit()`,
  matching Go's "main returns kills all". Each goroutine has its own `ucontext`
  stack; blocking channel ops park the G by swapping back to the M's scheduler
  context (deferred lock-release and deferred self-ready close the double-run
  window across Ms).
- **Channels (`hchan`).** A mutex-guarded ring (or unbuffered rendezvous) with
  `sendq`/`recvq` of `sudog` wait nodes. A wait node is either a parked G (woken
  via the scheduler) or a blocked non-M thread (the program's main thread, woken
  via its own condvar) — both kinds share one queue so a goroutine and main can
  rendezvous. Elements are a fixed 8-byte i64 slot; codegen bitcasts each
  `Channel<T>` element through i64.
- **Surface.** `import { go, Channel } from 'klain:sync'`. `go(() => void)`
  spawns a goroutine (function-member dispatch → `klainsync_go`, decomposing the
  closure `{fnptr, env}` header). `new Channel<T>(capacity)` binds as an
  identity constructor (like `Webview`/`MessageChannel`), carrying T in the
  type's `ElemType`; `.send(v)`/`.receive()`/`.close()` dispatch on `IsChannel`.
  Channel ops are **synchronous blocking**, not `await` — goroutine bodies are
  non-async `() => void`, and Go channels have no await; this is more faithful
  than the TDD's inherited `await` framing.
- **GC.** Under `-mm=gc` (`KLAINSYNC_GC`), each M registers with Boehm and each
  goroutine stack is added as a conservative root region for its lifetime, so a
  live object reachable only from a parked goroutine survives.

`klain:sync` is native-only (a compile error under plain `tsc`/Node).

## Implementation notes

- Stacks are unguarded `mmap` regions (256 KiB) — a guard page is impossible on
  macOS `makecontext` (see Investigation) and the existing fibers are likewise
  unguarded; a guarded/growable stack converges with the Stage-5 precise-stack-
  map work. Deep goroutine recursion is undefined behaviour, documented.
- The trampoline returns to `ks_curm->sched_ctx` explicitly (not a fixed
  `uc_link`): a goroutine that parks and resumes on a *different* M must hand
  control to whichever M runs it now, or it falls through a stale context.
- Codegen wiring mirrors `MessageChannel`: AST `NewChannelExpression`, parser
  `parseNewChannelBody` (type arg + capacity), resolver identity/walk cases,
  `IsChannel`/`ChannelType`, `inferExprType`/vardecl cases, and
  `emit_sync.go`'s constructor + method emit with the i64 slot bitcasts.
- The test build path (`tests/compiler_test.go`) links the runtime via a new
  `appendSync` helper, matching the CLI's `EmbeddedCSources` gating.

## Side effects discovered

- A builtin **handle type referenced inside a named function declaration** was
  losing its type (`ch.send` → "a number has no method 'send'") because
  `reliableGlobalType` didn't promote a channel to a module global, so a
  function body couldn't see the binding's type. **Fixed here**: a channel is
  promotable (unlike the `Worker`/`MessageChannel` handles `isHandleNewExpr`
  excludes, `klainsync_chan_new` opens no thread/fd and the scheduler starts
  lazily), so `NewChannelExpression` is added to `reliableGlobalType`. This is
  what makes the idiomatic fan-out — a `spawn(work)` helper that references a
  top-level channel and spawns goroutines — work; covered by
  `TestE2EGoroutineChannelInHelperFunction`. (The `MessageChannel` analog is
  still excluded by design — it opens pipes at construction.)
- Per-iteration capture of a loop `let` directly in a closure is separately
  pre-existing and broken (reproduces with a plain array of closures, no
  goroutines); the workaround — pass the value as a function parameter — works
  and is what the fan-out example/test use.

## Verification

- The C runtime was validated standalone (rendezvous, 100-goroutine buffered
  fan-in, buffered close-drain) — 5/5 stable and **clean under
  ThreadSanitizer** after fixing a status-field race and a `gosched` double-run
  hazard.
- E2E (`tests/goroutines_test.go`): rendezvous, three-stage concurrent pipeline,
  buffered fan-in, `Channel<string>` (pointer element), and two compile-error
  rejections — all pass. Example `examples/goroutines/pipeline.ts` runs.
- Stages 2–5 (loop-back-edge safepoints + sysmon preemption, `select`,
  blocking-syscall P-handoff, async signal preemption, growable stacks) remain.
