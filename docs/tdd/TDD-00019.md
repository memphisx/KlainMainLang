# TDD-00019: POSIX signal handling (`process.on('SIGINT'/'SIGTERM', handler)`)

- **Status**: Implemented ([ADR-00079](../adr/ADR-00079.md))
- **Date**: 2026-07-30

## Context

`http.listen` never returns — the only way to stop a running server today is `process.exit()` or an external `kill`, with no chance to run cleanup code first. This is the last open item in `docs/status/HTTP-SERVER.md` (graceful shutdown), explicitly deferred by [ADR-00072](../adr/ADR-00072.md) ("Graceful shutdown (`SIGINT`/`SIGTERM`) is explicitly out of scope — it needs POSIX signal handling, infrastructure that doesn't exist anywhere in this compiler, and is a distinct piece of design work best scoped on its own later") and flagged by [TDD-00004](TDD-00004.md)'s Prerequisites table as "a genuinely new gap this feature surfaces, not previously needed by anything." No design work exists anywhere for it yet — this document is that design pass, written before implementation per `CLAUDE.md`'s standing rule for new-subsystem work.

Goal: `process.on('SIGINT' | 'SIGTERM', handler: () => void)` — register a zero-arg closure that fires when the process receives that signal, so a server can run cleanup code and call `process.exit()` itself instead of dying instantly.

## Design

### Scope (V1, deliberately narrow)

- Only `'SIGINT'` and `'SIGTERM'` — not `'exit'`/`'uncaughtException'`/`'unhandledRejection'`. Those don't involve real signal delivery at all (they're separate, unrelated mechanisms — process-exit hooks and exception/promise-rejection hooks respectively); left for a later, separate pass.
- Only fires while a `http.listen`-driven or timer-driven event loop is actively iterating. A plain synchronous top-level script with no `http.listen`/`setTimeout`/`setInterval` has no loop to check a pending-signal flag from, so a registered handler in that shape simply never gets a chance to fire — a documented, deliberate scope boundary, not a silent bug. Interrupting arbitrary blocking syscalls compiler-wide (`process.readLineSync`, `fs.readFileSync`, ...) so Ctrl-C works mid-read in a plain CLI script is a materially bigger, separate problem, explicitly out of scope here.
- One handler slot per signal — registering `process.on('SIGINT', ...)` twice overwrites the previous handler, the same single-slot-narrowing convention `console.time()` already uses ([ADR-00029](../adr/ADR-00029.md)).
- No automatic process termination after the handler runs. The event loop just continues iterating; it's entirely up to the TS-level handler to call `process.exit()`. This sidesteps needing any `.close()`/listener-teardown machinery — `.close()` itself stays unimplemented after this feature, only the signal-driven "run cleanup, then exit yourself" path exists.

### Why a raw OS signal handler can't just call the TS closure directly

POSIX signal handlers must be async-signal-safe: they can interrupt the program at literally any instruction, including mid-`malloc`, mid-`longjmp`, or mid-`swapcontext` fiber switch. This compiler's closure-invocation path, exception machinery (`setjmp`/`longjmp` via a global jump-buffer stack, `runtime_exceptions.go`), and fiber scheduler (`ucontext.h`, `runtime_http.go:436-450`) all assume they're only ever entered from ordinary, non-reentrant control flow — [TDD-00006](TDD-00006.md) already documents in depth that LLVM coroutine suspension across a `setjmp`/`longjmp` boundary segfaults for exactly this class of reason. Calling arbitrary TS code from real signal context would risk the same kind of corruption, just triggered by an async signal instead of a suspend point.

**The design avoids this by construction**: the actual OS-level signal handler does the absolute minimum — one `volatile` store to a flag — and nothing else. The TS closure is invoked later, from ordinary control flow at the top of the event loop's own iteration, the exact same place a due timer's closure is already invoked today. By the time that code runs, we're back in the scheduler's normal context (not inside any suspended fiber's stack, not inside a live `setjmp` scope), so it's exactly as safe as firing a timer callback already is.

### Mechanism

1. **Globals** (emitted lazily, once, the first time `process.on` is called for a given signal): `@__kml_sigint_pending`/`@__kml_sigterm_pending` (`i8`, always accessed via `volatile` load/store — required so `-O2` can't cache the flag across the `select()` call or eliminate a store as dead; the LLVM-IR equivalent of C's mandatory `volatile sig_atomic_t` for this exact pattern) and `@__kml_sigint_closure`/`@__kml_sigterm_closure` (`ptr`, null = unregistered).
2. **The raw handler**: a small hand-written IR function `define void @__kml_sig_handler(i32 %signum)`, dispatching on `%signum` (`2` = SIGINT, `15` = SIGTERM) and doing nothing but `store volatile i8 1` to the matching pending flag. This is the *only* code that ever runs in real async signal context — it must stay this minimal, permanently.
3. **Registration** (`emitProcessOn`, new): validates the event-name argument is exactly the string literal `"SIGINT"` or `"SIGTERM"` (compile error otherwise — dynamic/computed event names rejected, same precedent `Object.hasOwn`'s dynamic-key rejection already sets, `emit_objects.go:775-778`), validates the handler closure via the existing `timerCallbackPtr` helper (`emit_timers.go:23-35`, already exactly "validate a `() => void` closure argument," reused as-is by passing `"process.on"` as its caller-name), stores the closure pointer into the matching global, and — only the first time that particular signal is registered — emits `call ptr @signal(i32 2, ptr @__kml_sig_handler)` (or `15`).
4. **Delivery**: both existing event loops — `@__kml_event_loop_run` (`runtime_http.go:685`, used whenever `http.listen` is called) and `@__kml_timer_drain` (`emit_timers.go:249`, the simpler standalone loop used when only `setTimeout`/`setInterval` are used without `http.listen`) — get an identical block inserted at the very top of their `outerloop:` label: load each pending flag (`volatile`), and if set, clear it, load the matching closure global, and if non-null invoke it via the existing `call void (ptr) %fp(ptr %ep)` GEP pattern already used by both loops' own timer-fire logic — before falling through to the loop's normal timer-scan/`select()` work. A single check point at the literal top of the loop, re-entered after every iteration, naturally covers both races: a signal that arrived since the last check (seen before computing `select()`'s timeout) and a signal that interrupts a blocking `select()` call directly (seen immediately on looping back after `EINTR`).

### A real correctness bug found while designing this, must be fixed alongside it

`select()`'s return value (`runtime_http.go:855`/`:859`, `%selrc1`/`%selrc2`) is currently **not checked at all** — execution falls straight through to `afterselect` and reads the fd_set as though it reflects real readiness. POSIX leaves the fd_sets *unmodified* on an `EINTR` return (they still hold whatever was written in as the *watch* set), so after a signal interrupts `select()`, every watched fd — including the listener — would look spuriously "ready." The listener socket is never set non-blocking (only accepted connections are, `runtime_http.go:890-893`), so a spurious `accept()` call after `EINTR` could block indefinitely, hanging the whole server instead of promptly reacting to the signal that was supposed to shut it down. **Fix**: branch on `%selrc1 < 0` / `%selrc2 < 0` right after the call, and on failure skip straight to the signal-check-then-loop-back path, bypassing `checklistener`/`scanconn`/`checktimerfire` entirely for that iteration.

### Why `signal()`, not `sigaction()`

`sigaction()` needs a hand-laid-out `struct sigaction` passed by pointer, and that struct's byte layout differs between Darwin and Linux (`sa_mask` size, presence of `sa_restorer`) — exactly the class of bug already hit once with `ucontext_t`'s platform-specific size/layout ([ADR-00051](../adr/ADR-00051.md)). `signal()`'s C signature (`void (*signal(int, void (*)(int)))(int)`) is two scalars with no struct at all, identical on both platforms this compiler targets, so there's no layout to get wrong. The one thing `sigaction` buys that `signal()` doesn't — precise control over `SA_RESTART` — doesn't matter here: `select()`/`poll()` are documented (Linux's `signal(7)`, and equivalently on BSD/Darwin) to always return `EINTR` on a signal regardless of `SA_RESTART`, since silently restarting `select()` with its original timeout would incorrectly extend the wait past what the caller asked for. Worth confirming this empirically during implementation (on both Darwin and Linux via the existing Docker path), not just trusting the documentation.

## Open questions

- Whether a future `.close()` API (if ever built) should integrate with this same pending-flag mechanism, or be a fully separate concept — not decided, not needed for V1 since `process.exit()` already gives a complete (if blunt) way to stop.
- Whether `'exit'`/`'uncaughtException'`/`'unhandledRejection'` should eventually live under the same `process.on(...)` dispatch switch this adds, or get their own separate entry points given they don't involve real signals at all — leaning toward reusing the same `case "on":` switch (same call-site shape from the TS programmer's perspective) but not committed.
- Whether re-registering a handler for the same signal should be a compile error (catching an obvious mistake early) rather than silently overwriting the previous one — leaning toward silently overwriting, matching `console.time()`'s existing precedent, but not strongly held.
