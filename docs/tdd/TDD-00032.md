# TDD-00032: Native library bindings / GUI (placeholder)

- **Status**: Not Started
- **Date**: 2026-08-06

## Context

This is a deliberately shallow **bootstrapping placeholder**, not a committed design — written to record the scope and the key blocking prerequisite found while researching UI directions for this compiler (alongside [TDD-00031](TDD-00031.md)'s terminal UI work and [TDD-00033](TDD-00033.md)'s direct-hardware placeholder), so the thinking isn't lost and a future real design pass has somewhere to start from rather than re-deriving this from scratch. Not scoped in enough detail for implementation to start from — that's the point; a real TDD (or more likely, several) forks off this one once it's actually picked up.

The original question was whether this compiler could target a GUI toolkit — QML/Qt was the specific example raised — the way it already targets libcurl for `fetch`. Research into how the Node ecosystem does this surfaced the real shape of the problem:

- Hand-written native-addon bindings (`node-qt`/`edge-qt`-style: C++ compiled against Node's N-API) exist for Qt, but Qt's own public API is C++ (name-mangled ABI, vtables, templates) — a materially harder FFI target than the plain-C libraries this compiler already links (libcurl, Boehm GC). Binding Qt directly would likely mean writing a C shim layer around it first, on top of everything else below.
- **GObject Introspection** (how `node-gtk` binds GTK) is the more instructive precedent: rather than hand-writing a binding per function, GLib-based libraries ship machine-readable `.gir` metadata, and *one generic* runtime layer — built on `libffi` — reads that metadata and calls arbitrary C functions dynamically, with no per-function binding code at all.
- Pure FFI libraries (`ffi-napi`) bind `libffi` directly with no introspection layer, letting JS declare a C function's signature by hand and call it.

Both routes converge on the same missing foundation: **this compiler has no general way for user code to declare and call an arbitrary external C function at all.** Every existing piece of native interop (libcurl, libc, Boehm GC) is hand-written Go-side codegen baked into the compiler itself (`ensure*()`/`emit_*.go`/`runtime_*.go` pairs) — there is no `extern`, no user-facing FFI, no way to pass a KlainMainLang closure to C as a callable function pointer (which any real GUI toolkit's event-loop/signal-driven API needs immediately). That's not a GUI-specific gap; it's a standalone, foundational capability GUI merely happens to need first.

## Design

Not scoped. What research so far suggests the eventual shape will need to answer, for whoever picks this up:

- **Whether general FFI is worth building as its own thing before any GUI work starts**, vs. building just enough narrow, hand-written bindings for one specific toolkit (the same one-off pattern libcurl already uses) and deferring general FFI indefinitely. The libcurl precedent argues for narrow-and-specific being viable *for one library*; the GUI case is harder because toolkits are usually large, callback-heavy, and multiple viable choices exist (see below), so a generic mechanism amortizes better here than it would have for libcurl alone.
- **Which toolkit**, if a specific binding is built rather than general FFI: QML/Qt (C++, hardest ABI, richest declarative UI model) vs. a plain-C toolkit (GTK via its C API, raylib, SDL2, dear imgui via `cimgui`) — a C-API toolkit sidesteps the C++ name-mangling/vtable problem entirely and would very likely be the pragmatic starting choice if this is ever picked up, even though QML was the original example that prompted this research.
- **Closure-to-C-function-pointer trampolines.** Independent of which toolkit, any callback/event-loop-driven GUI API needs a way to hand a KlainMainLang closure to C as a raw, C-callable function pointer — a capability that doesn't exist in any form today (this compiler's closures use their own internal calling convention, never exposed as a plain C ABI function pointer). This is likely the single hardest new piece of codegen either direction would need, independent of the FFI-vs-hand-bindings question above.
- **Struct marshaling for a general FFI** — this compiler already does C-ABI-correct struct layout internally (every `runtime_*.go` C declaration), but never exposes that machinery to user-declared types. A general FFI would need a user-facing way to describe a foreign struct's layout, not just call foreign functions.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| User-facing `extern`/FFI function declarations | ❌ missing | The actual gap this whole placeholder exists to name. Nothing today lets a KlainMainLang program declare an arbitrary external C function signature. |
| Closure → C function pointer trampolines | ❌ missing | Required for any callback-driven C API (GUI event loops, GLib signal handlers), not specific to one toolkit choice. |
| User-facing foreign struct layout description | ❌ missing | This compiler's own C-ABI struct-layout logic exists internally (every `runtime_*.go` file) but isn't exposed to user code. |
| Conditional linking against an external library only when used | ✅ precedent exists | `-lcurl` is already linked only when `fetch`/`http.listen` is actually used ([ADR-00020](../adr/ADR-00020.md)) — the same pattern would extend to a GUI toolkit's own linking. |
| A concrete toolkit decision | ❌ not made | See Design above — genuinely open, and probably shouldn't be decided until (or unless) the FFI-vs-hand-bindings question above is settled first. |

## Open questions

Everything in Design above is genuinely open — this placeholder exists to name the problem and its real prerequisite, not to settle any of it. The expected next step, if this is ever picked up, is a real design pass (likely its own TDD titled around "general C FFI," since that's the piece with value well beyond GUI alone — e.g. it would also unlock `ncurses` as an alternative to [TDD-00031](TDD-00031.md)'s hand-rolled termios primitives, or future database client libraries), with a second, narrower TDD for a specific toolkit binding only once FFI itself has a real design.
