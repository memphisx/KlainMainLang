# TDD-00181: `fs.watch` — native file-change watching across the event loop

- **Status**: In Progress
- **Date**: 2026-09-07

## Context

`fs.watch(filename[, options][, listener])` returns an `FSWatcher` that emits `'change'`/`'rename'` events as a file or directory changes. It is the last unimplemented item in the [TDD-00180](TDD-00180.md) §4 "missing entirely" fs list, and the only one that is a *subsystem* rather than a leaf call: it must feed a live OS event source into the compiler's single `select()`-based event loop (`runtime_http.go`). The six sibling fs additions (ADR-00750–00755) were self-contained; this one touches the loop itself.

The user directed the **faithful, event-driven** implementation (native OS backends), not a `stat`-poll interim. That is what this TDD designs.

## Design

### The three OS backends

Each host has a different native change source; the shared shape is "a source the loop can wait on, that yields (event-kind, name) records."

| OS | Mechanism | Loop integration |
|---|---|---|
| Linux | `inotify` (`inotify_init1(IN_NONBLOCK)`, `inotify_add_watch`) | The inotify instance **is a readable fd** — add it to the loop's read `fd_set` directly; `select()` wakes on change; `dispatch` `read()`s `struct inotify_event` records. No thread. |
| macOS/BSD | `kqueue` + `EVFILT_VNODE` on an `open()`ed fd (`NOTE_WRITE`/`NOTE_RENAME`/`NOTE_DELETE`/`NOTE_ATTRIB`) | The kqueue **is a readable fd** — same as inotify: add it to the `fd_set`, `dispatch` `kevent()`s with a zero timeout. Watching a directory's entries needs one open fd per entry (kqueue watches fds, not paths). |
| Windows | `ReadDirectoryChangesW` on a directory `HANDLE`, run on a **watcher thread** (overlapped/blocking read loop) | Windows `select()` waits only on sockets, and the loop has **no wakeup channel** (the [TDD-00180](TDD-00180.md) §1 gap). So the thread posts its `FILE_NOTIFY_INFORMATION` records to a mutex-guarded queue and writes one byte to a **loopback wakeup socket**; the loop adds that socket's read end to its `fd_set`; `dispatch` drains the queue and the wakeup byte. |

`inotify`/`kqueue` map cleanly onto the existing readiness loop. Windows is the one that forces new infrastructure — the wakeup socket — which is deliberately the same primitive an eventual IOCP reactor ([TDD-00180](TDD-00180.md) Option A/B) would want, so this is not throwaway.

### Event-loop integration

fs.watch registers the standard hook trio the loop already calls for `worker`/`chan`/`cp`/`readline`/`stdin`/`net`/`dgram`/`ipcc`:

- `__kml_fswatch_keepalive() -> i1` — true while any `FSWatcher` is open (unclosed), so a program that only watches stays alive.
- `__kml_fswatch_fdset_add(fdset, maxfd)` — add the backend's wait fd (Linux: the inotify fd; macOS: the kqueue fd; Windows: the wakeup socket's read end).
- `__kml_fswatch_dispatch()` — after `select()`, read pending records from the backend and fire each watcher's listener.

No-op stubs (`emitLoopTaskStubs`) stand in when the program never calls `fs.watch`, exactly like the other subsystems. The keepalive is folded into the loop's `%anywork` chain and the fdset into its fd-scan; no `select()` timeout change is needed (all three backends are fd-readable).

### The `FSWatcher` object and JS surface

`fs.watch(path, listenerOrOptions?, listener?)` returns an `FSWatcher` (`IsFSWatcher` typed object) with:

- `.on('change'|'rename', (eventType, filename) => …)` — one listener slot per event (the `Worker`/`ChildProcess` posture; arrow-literal only), the `(eventType, filename)` shape.
- `.close()` — stop watching, remove the wait fd, drop the keepalive.
- Options: `{ persistent?, recursive?, encoding? }` — `persistent` (default true) maps to the keepalive; `recursive` is honoured where the OS supports it natively (macOS/Windows) and is a documented caveat on Linux (inotify is not recursive without walking the tree); `encoding` only `'utf8'`.

The listener also being passable as `fs.watch(path, listener)` is Node's overload; both forms are accepted.

### Event semantics

Node emits `'rename'` when an entry appears/disappears (create/delete/move) and `'change'` when content/attributes change. The backends map: inotify `IN_CREATE`/`IN_DELETE`/`IN_MOVED_*` → `'rename'`, `IN_MODIFY`/`IN_ATTRIB` → `'change'`; kqueue `NOTE_RENAME`/`NOTE_DELETE` → `'rename'`, `NOTE_WRITE`/`NOTE_ATTRIB` → `'change'`; Windows `FILE_ACTION_ADDED`/`REMOVED`/`RENAMED_*` → `'rename'`, `FILE_ACTION_MODIFIED` → `'change'`. `filename` is the entry name (relative), UTF-8.

Node makes no guarantee about coalescing or ordering and its behaviour is famously platform-dependent; matching the per-event mapping above is the fidelity bar, not byte-identical event streams.

## Staging

1. **Stage 1 — integration skeleton + Linux backend.** The hook trio + stubs + loop wiring, the `FSWatcher` object, the `fs.watch` emitter, and the inotify backend. Fully testable on Linux (native and via the project's Docker image). Status row **not** flipped to ✅ yet — the row is only claimed once every target platform passes.
2. **Stage 2 — Windows backend.** The watcher thread, the loopback wakeup socket, the mutex-guarded record queue, `ReadDirectoryChangesW`. Testable on Windows 11 + the ConPTY-independent E2E path.
3. **Stage 3 — macOS backend.** kqueue `EVFILT_VNODE`, one fd per watched entry. CI-validated (no local Apple Silicon in this session).
4. **Stage 4 — flip coverage.** Only when Stages 1–3 pass on their platforms: add the `file-system.json` row (✅ with the recursive/coalescing caveats), the website reference entry, and the shipped example.

## Open questions

1. **Recursive on Linux** — emulate by walking the tree and adding a watch per directory (with the inherent races), or reject `recursive: true` on Linux as a clean caveat? Leaning: reject with a caveat initially; tree-walk is a later refinement.
2. **Directory vs file watch on macOS** — kqueue watches fds; watching a directory for entry churn means an fd per entry and re-scanning on `NOTE_WRITE`. Confirm the per-entry-fd budget is acceptable or gate large directories.
3. **Whether the Windows wakeup socket should be shared** with a future general loop wakeup (stdin, IOCP) rather than fs.watch-private — almost certainly yes; design it standalone but reusable.
