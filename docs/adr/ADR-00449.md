# ADR-00449: Node stream constructors default to string chunks

- **Date**: 2026-08-29

## Context

Hit in passing while probing the Node oracle's stream bucket: the
un-parameterized `new stream.Readable({ read() {} })` compiled, but pushing a
string and reading it in a `'data'` listener printed a raw pointer value
(`4306083464`) — from `String(c)` *and* from `c.toString()`. Silent garbage,
the worst class of wrongness.

## Investigation

`emitNewNodeStream` (`codegen/llvm/emit_node_stream.go`) defaulted
`inTy, outTy` to `TypeI64` for `Readable`/`Writable`/`Transform`; only
`PassThrough` already defaulted to string chunks (ADR-00422, with the
rationale "Node's non-objectMode streams carry strings/Buffers" — equally
true of the other three). With an i64 chunk type, `push("hello")` coerced
the string's pointer into the numeric chunk word, and the listener printed
that number. `inferExprType` mirrored the same defaults. A repo-wide grep
found no test or example relying on the numeric default — every numeric
chunk user writes `<number>` explicitly.

## Decision

All four Node-stream constructors default to string chunks (`TypePtr`);
`<T>` still overrides for numeric/typed-array chunk streams. Two sites:
`emitNewNodeStream` and the `NewNodeStreamExpression` case of
`inferExprType`. No runtime change — the chunk type was always
construction-time static.

## Verification

Mac. Repro now prints `hello` via both `String(c)` and `c.toString()`;
`tests/streams_test.go` gains `TestE2ENodeReadableDefaultStringChunks`;
`examples/streams/default_string_chunks.ts` added; full `-run Stream` E2E
batch green. Node oracle aggregate unchanged (37 — the affected corpus
files stack further blockers); TS oracle untouched (codegen-only).
