# TDD-00013: Error subtypes / tagged errors

- **Status**: Implemented
- **Date**: 2026-07-28

## Context

Classes Stage 2 ([ADR-00067](../adr/ADR-00067.md), implementing [TDD-00009](TDD-00009.md)'s Stage 2) added a hidden runtime type tag to every user-defined class instance and a working `instanceof` operator against those classes. `Error` was deliberately left out of that pass: `new Error(msg)` today is a single, untagged `{message: ptr}` struct (`errorObjType`, `codegen/llvm/emit_exceptions.go`) shared by every thrown value regardless of what it actually represents, there is no `TypeError`/`RangeError`/`SyntaxError`/etc. anywhere (no lexer keyword, no parser rule, no AST node, no constructible type — confirmed via direct grep while scoping Stage 2), and `x instanceof Error` is a clean compile error today ("instanceof is only supported against user-defined classes").

Picking this up separately rather than folding it into Stage 2 was a deliberate scope call: Error subtyping is real, distinct design surface (built-in-hierarchy-vs-tag-the-existing-struct, and whether user code can ever subclass `Error` before inheritance exists), not a small extension of Stage 2's diff. It's being scoped now rather than left as a bare `STATUS.md` one-liner because real-world TypeScript/JavaScript code leans on `instanceof Error`/`TypeError`/custom error subclasses heavily enough that it's a real compatibility gap worth tracking properly, not a cosmetic one.

## Design

Two genuinely different shapes, not yet decided between:

### Option A — Narrow: tag the existing `Error` struct directly

Give `errorObjType` its own tag field (reusing the exact `ClassTagField`/`VisibleFields()` mechanism Stage 2 already built for user classes — see `codegen/llvm/types.go`), and add a small, fixed, built-in set of Error kinds (`Error`, `TypeError`, `RangeError`, `SyntaxError`, ...) as an enum-like discriminant rather than a full class hierarchy. `new TypeError(msg)` would need its own lexer/parser recognition (mirroring how `new Error(msg)` is already hardcoded in `parseNew`, `parser/parser.go`) producing the same struct shape with a different tag value. `instanceof Error` matches any tag; `instanceof TypeError` matches only that one. `catch (e)` would still bind `e` as the single shared (now tagged) Error type — no change to the catch-binding mechanism itself.

Smaller in scope: no dependency on Stage 3 (inheritance), buildable standalone. The real limitation: user code can never define its own `class MyError extends Error` this way — only the fixed built-in set of kinds would be `instanceof`-recognizable, since there's no general subclassing mechanism here, just a closed enum.

### Option B — General: model Error as a real built-in class hierarchy

Once [TDD-00009](TDD-00009.md) Stage 3 (`extends`/vtables) lands, define `Error`, `TypeError`, `RangeError`, etc. as actual built-in classes with real inheritance (`TypeError extends Error`), and let user code write `class MyError extends Error { ... }` the same way real TypeScript does. `instanceof` then falls out of Stage 3's own subtype-check machinery for free, no separate mechanism needed.

More consistent with the rest of this compiler's design (one mechanism for "a type with data, behavior, and identity," not a special-cased Error enum sitting outside it) and closes the *actual* real-world pattern (custom error subclasses) that Option A can't reach at all. Strictly gated on Stage 3 existing first, which today is explicitly deprioritized (see TDD-00009's own open questions: "not scheduled yet, not abandoned either," triggered by a concrete need to compile real third-party class-inheritance-dependent code).

### Leaning

No recommendation finalized here. Option A is buildable today and closes the more common shallow case (`try { ... } catch (e) { if (e instanceof TypeError) ... }` against a small fixed set of built-in kinds) at low cost; Option B is the "real" fix but is transitively blocked on Stage 3, which has its own independent low-priority status. A reasonable path is Option A now, superseded by Option B once Stage 3 exists and user-defined error subclasses become a concrete ask — but this isn't decided, just the shape of the tradeoff.

## Prerequisites

| Dependency | Status | Notes |

| `TypeError`/`RangeError`/etc. as constructible `new X(msg)` forms | ❌ not started | `parseNew` (`parser/parser.go`) only hardcodes `Array`/`Map`/`Set`/`Error`/`Date`; each new Error kind needs its own case (Option A) or becomes a real registered class (Option B, via the existing generic `new ClassName(...)` path once Option B's built-in classes are registered). |
| `class` inheritance (`extends`/`super`) | ❌ not started | Stage 3 of [TDD-00009](TDD-00009.md) — required for Option B, irrelevant to Option A. |
| `catch` clause binding a narrowed Error subtype | ❌ not started | Today's `catch (e)` binds a single fixed `errorObjType` regardless of what was thrown (`emit_exceptions.go`); neither option changes the binding mechanism itself, only what `e instanceof X` can then distinguish at runtime. |

## Open questions

- Option A vs. Option B — not decided (see Design above); the deciding factor is likely whether real third-party TS/JS code needing custom `Error` subclasses shows up before Stage 3 is otherwise justified.
- If Option A ships first: which built-in kinds are worth adding (`TypeError`/`RangeError` cover the most common real-world `catch` narrowing; `SyntaxError`/`EvalError`/`URIError` are rarer and could be deferred further).
- Whether `.name`/`.message`/`.stack` should be real fields on the (tagged) Error shape once this lands — today only `.message` exists; `.name` in particular is what real JS code often branches on instead of `instanceof` (`e.name === "TypeError"`), so it may be worth adding regardless of which option is picked.
