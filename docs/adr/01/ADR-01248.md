# ADR-01248: An override with different parameters

- **Relations**: `Extends ADR-00631, ADR-01238`
- **Date**: 2026-09-29

## Context

`examples/eventemitter/override.ts` overrides
`emit(event: string, name: string, value: number)` on an `EventEmitter`
subclass. The idiom worked with the code-generated EventEmitter. After
ADR-01238, `emit` is `emit(eventName: string | symbol, ...args: any[])`,
and the override was rejected ("overrides an inherited method with an
incompatible signature"). tsc accepts it, since method parameters are
bivariant.

## Decision

An override whose signature differs from the inherited method's keeps the
inherited signature, so every call site and the vtable slot use one
convention:

- its body is compiled under its own signature
  (`Class_method__kml_ovr`);
- the method's symbol is an adapter with the inherited signature. It
  converts the arguments (a rest tail spread into fixed parameters,
  unboxing, boxing) and the result, and calls the body with the receiver.
- The adapter is the closure adapter's body (`emitAdapterFunc`, factored
  out of `emitClosureAdapter`), with the receiver in the env slot.

A conversion the adapter does not take is still the clean rejection, and
so is an async or `this:`-typed override.

## Verification

Mac (Apple Silicon), against Node v24.19:
`TestE2EEventEmitterOverrideNarrowerSignature` (direct, virtual through
an `EventEmitter`-typed receiver, `super.emit`); the `override.ts`
example; the class and EventEmitter suites.
