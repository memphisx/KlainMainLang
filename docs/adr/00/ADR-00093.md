# ADR-00093: Fix missing `GC_stackbottom` restore on `http.listen`'s read-loop yield (4th swapcontext site ADR-00071 missed)

- **Relations**: Extends [ADR-00071](ADR-00071.md), which introduced the `GC_stackbottom` fiber-swap fix this ADR completes. Extended by [ADR-00101](ADR-00101.md), which found this restore was still incomplete (didn't cover a fiber running to completion without yielding again) and moved it to the resumer side.
- **Date**: 2026-08-04

## Context

GitHub Actions' CI (`go test ./...`) failed on the latest `main` commit, in `TestE2EHTTPListenGCModeConcurrentChurn` (`tests/memory_gc_test.go`):

```
--- FAIL: TestE2EHTTPListenGCModeConcurrentChurn (0.34s)
    memory_gc_test.go:148: request 2: GET /req2: Get "http://127.0.0.1:8952/req2": read tcp 127.0.0.1:53534->127.0.0.1:8952: read: connection reset by peer
    memory_gc_test.go:148: request 3: GET /req3: Get "http://127.0.0.1:8952/req3": read tcp 127.0.0.1:53524->127.0.0.1:8952: read: connection reset by peer
    memory_gc_test.go:148: request 4: GET /req4: Get "http://127.0.0.1:8952/req4": read tcp 127.0.0.1:53530->127.0.0.1:8952: read: connection reset by peer
```

This is the exact failure signature [ADR-00071](ADR-00071.md) documented for its own `GC_stackbottom` bug: a client-side "connection reset by peer" is what a SIGSEGV in the server process looks like from the other end of the socket. ADR-00071's negative-control section describes reproducing this identical message by temporarily reverting its fix. That ADR's fix was believed complete (3 `swapcontext` sites patched, verified passing 5 repeated local runs plus CI at the time), so a regression appearing now pointed at either a missed site or a change since then that reintroduced the gap.

## Investigation

- Re-read [ADR-00071](ADR-00071.md) in full. It states the fix needed "exactly 3 `swapcontext` call sites": `__kml_http_append_conn`'s initial fiber launch, `__kml_event_loop_run`'s `rresume` block, and `ensureFetchAsync`'s `__kml_await_fetch` `doyield` block.
- Grepped every `swapcontext`/`GC_stackbottom` reference across `codegen/llvm/`:

  ```
  codegen/llvm/emitter.go:510      (startup snapshot into @__kml_gc_orig_stackbottom — not a swap site)
  codegen/llvm/runtime_fetch.go    (gcRestoreStackbottom, 2 sites: __kml_await_fetch + its group-wait twin)
  codegen/llvm/runtime_http.go:595 (gcSetStackbottom, __kml_http_append_conn's initial launch)
  codegen/llvm/runtime_http.go:687 (gcSetRStackbottom, __kml_event_loop_run's rresume)
  codegen/llvm/emit_http.go:325    (swapcontext call, doYieldL block — NO gc handling at all)
  ```

  This found a **4th real `swapcontext` site**, in `buildHTTPDispatcher`'s `doYieldL` block (`codegen/llvm/emit_http.go`, ~line 322): the per-connection fiber's own read loop, reached when a non-blocking `read()` returns `EAGAIN` (no request data available yet) and the fiber yields back to `@__kml_main_ctx` so the scheduler can service other connections/timers. Unlike the sibling `doyield` block in `runtime_fetch.go`, this site had no `GC_stackbottom` restore before its `swapcontext` call at all.
- Compared directly against `runtime_fetch.go`'s pattern (lines ~375-383, ~457-464): that block restores `GC_stackbottom` from `@__kml_gc_orig_stackbottom` immediately before swapping back to main, guarded by `e.isGCMode()`. `emit_http.go`'s `doYieldL` had no equivalent.
- Reasoned through why this specific gap produces exactly the observed symptom: `__kml_event_loop_run`'s `rresume` block sets `GC_stackbottom` to a fiber's own stack right before resuming it — but only ever *sets* it on the way in; it never restores it on the way back out, because that restore was assumed to already be handled by the callee (matching ADR-00071's inventory of 3 sites). When `doYieldL` swaps back to main without restoring, `GC_stackbottom` is left pointing at the yielding fiber's 64KB `malloc`'d stack for the entire time control is back on the *main* stack — accepting new connections, resuming other fibers, scanning timers — until the next `rresume` overwrites it (correctly, but for a *different* fiber, still not the main stack). Any Boehm collection triggered during that window, while the live SP is genuinely on the main stack, has its root-stack scan walk between the live main SP and the stale fiber-stack address left behind by the yield — an unrelated, likely-unmapped range, matching ADR-00071's own description of the crash this whole mechanism exists to prevent.
- This explains the failure's load-dependent, non-deterministic character: a connection only ever reaches `doYieldL` if `read()` returns `EAGAIN`, which requires the fiber to run ahead of the client's data actually arriving on the socket — more likely under concurrent load (6 racing requests) and on a slower/more virtualized CI runner than on a fast, lightly-loaded dev machine. This matches this project's own precedent: `ucontextLayout`'s doc comment (`codegen/llvm/runtime_http.go`) notes a previous fiber/stack bug that "hung/reset connections" only on GitHub Actions' `ubuntu-latest`, never locally.
- Attempted a local repro before and after the fix (`go test ./tests/ -run TestE2EHTTPListenGCModeConcurrentChurn -count=20`, both with and without the fix) — passed 20/20 both times on this dev machine (macOS/arm64-class fast local loopback), consistent with the "CI-only, timing-dependent" pattern rather than disproving the diagnosis; the code-level evidence (this is the one `swapcontext` site missing the restore/set pairing all 3 siblings have) stands on its own regardless.

## Decision

Add the same conditional `GC_stackbottom` restore `runtime_fetch.go`'s `doyield` block already uses, to `emit_http.go`'s `doYieldL` block, immediately before its `swapcontext` call:

```
%origbottom = load ptr, ptr @__kml_gc_orig_stackbottom, align 8
store ptr %origbottom, ptr @GC_stackbottom, align 8
```

Built via `e.freshReg()` + `e.emitInstr(...)` rather than a hardcoded register name, since (unlike `runtime_fetch.go`'s raw `e.emitGlobal(fmt.Sprintf(...))` string blob) `buildHTTPDispatcher` builds this function's IR incrementally through the normal Go-side emitter API — a hardcoded `%origbottom` would risk colliding with another register name in a function assembled this way. Guarded by `e.isGCMode()`, matching every other GC-mode-conditional emission in this codebase — emits nothing in `manual` mode.

No alternative approach was considered: this is a straightforward case of applying an already-established, already-reviewed pattern (ADR-00071's own restore/set pairing) to the one site that was missed, not a new design decision.

## Implementation notes

- File touched: `codegen/llvm/emit_http.go`, `buildHTTPDispatcher`'s `doYieldL` block only.
- No change needed to `runtime_http.go`, `runtime_fetch.go`, or `emitter.go` — `@__kml_gc_orig_stackbottom` is already declared and snapshotted unconditionally in GC mode (`emitter.go`'s `EmitProgram` Pass 3), regardless of whether `http.listen` is used in a given program, so this fix only needed to *read* that existing global from a new call site.
- After this fix, all 4 real `swapcontext` sites in the codebase now correctly pair a `GC_stackbottom` set (swapping into a fiber) with a restore (swapping back to main): `__kml_http_append_conn` (set) / `doYieldL` (restore, this fix) / `rresume` (set) / `__kml_await_fetch`'s two `doyield` blocks (restore).

## Side effects discovered

None new. This closes a gap in ADR-00071's own stated scope rather than surfacing an unrelated issue.

## Verification

- `go build -o klainmain .`, `go vet ./...` — clean.
- **Negative control**: reverted this fix (`git stash` on `emit_http.go`) and ran `go test ./tests/ -run TestE2EHTTPListenGCModeConcurrentChurn -count=20` and `-count=5` — both passed on this dev machine, consistent with the bug being CI-timing-dependent rather than always-reproducing locally (see Investigation) — not proof by itself, so the fix's correctness rests on the code-level diagnosis (the missing restore, confirmed by direct comparison against the 3 already-fixed sibling sites) plus this being the only asymmetric set/restore pairing in the whole `GC_stackbottom` mechanism.
- With the fix restored: `go test ./tests/ -run TestE2EHTTPListenGCModeConcurrentChurn -count=8 -v` — 8/8 pass.
- `go test ./...` — full suite green (~50s).
