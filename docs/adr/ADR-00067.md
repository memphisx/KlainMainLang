# ADR-00067: Classes Stage 2 — runtime type tags and `instanceof`

- **Relations**: Extends [ADR-00063](ADR-00063.md), [ADR-00064](ADR-00064.md). Implements [TDD-00009](../tdd/TDD-00009.md) (Stage 2 of 4)
- **Date**: 2026-07-28

## Context

[ADR-00063](ADR-00063.md) (Stage 1 + 1a) shipped class instances, methods, constructors, and a class-based `for...of` iterator protocol, all with no inheritance. `Type.IsClass`/`ClassName` were added there specifically so a later stage could recognize a class instance distinctly — the doc comment on those fields already said "and, later, `instanceof` (Stage 2)." This ADR is that stage: [TDD-00009](../tdd/TDD-00009.md)'s own Stage 2 design section (a hidden per-instance tag field, `instanceof` reading it) is the starting point. Narrowed the scope for this pass to user-defined classes only, deferring `Error`/`TypeError`/etc. to a new [TDD-00013](../tdd/TDD-00013.md) rather than folding it in — real, separate design surface (narrow-tag-the-existing-struct vs. a real built-in class hierarchy, and whether user code can ever subclass `Error` before Stage 3 exists) that deserved its own pass rather than being squeezed into this diff.

## Investigation

Confirmed directly (not assumed) before implementing:

- `instanceof` was completely absent — no lexer token, no parser rule, no AST node, no codegen case anywhere (grepped the whole repo). The only two hits for the string "instanceof" were doc comments anticipating this stage (`types.go`'s `IsClass` comment, `STATUS.md`'s roadmap row).
- `Error` (`codegen/llvm/emit_exceptions.go:9`, `errorObjType`) is a single shared, untagged `{message: ptr}` struct with no `ErrorType()` constructor analogous to `ClassType()`/`ResponseType()` — every thrown value, Error or not, gets boxed into this same shape. No `TypeError`/`RangeError`/etc. exist as constructible types at all.
- The parser already builds a generic `ast.BinaryExpression{Op, Left, Right}` for every relational operator via precedence climbing (`parser/parser.go:1451` `parseRelational`) — no new AST node was needed for `instanceof`; it slots in as one more operator string at the same precedence tier as `<`/`>`/`<=`/`>=`, with `emitBinary`/`inferExprType` dispatching on `Op == "instanceof"` like every other operator.
- The existing `any`/`unknown` boxing scheme (`emit_dynamic.go`, `{i8 tag, i64 payload}`, tags 0–6) is a related but genuinely separate mechanism from what this stage needed: it's a stack/SSA-value tag distinguishing *kinds* of dynamic value (int/float/string/object/...), not a heap-embedded per-class identity. `kmlTagObject` (tag 6) is a no-op passthrough today with no discrimination among object shapes — exactly the gap this stage's class tag fills for the `any`-narrowing case, but a different storage mechanism, not the same field reused.
- Before [TDD-00009](../tdd/TDD-00009.md) Stage 3 (inheritance) exists, every class-typed variable's concrete class is already known at compile time — so `x instanceof Point` on a plain `Point`-typed variable is almost always foldable to a compile-time constant. Decided the `any`/`unknown` case (a value boxed as `any` holding one of several possible classes, narrowed at runtime) was worth including in this same pass specifically because it's the only case that does real, non-vacuous work before Stage 3 — skipping it would have shipped a feature whose only observable behavior was a compile-time constant.
- A real, previously-latent bug surfaced while testing the nullable-class-typed `instanceof` case (see Side effects discovered below): `canonicalizeClassTy` (added in [ADR-00064](ADR-00064.md) to fix self-referential class field staleness) silently dropped a field's `Nullable` flag when swapping in the canonical registry type, since `Nullable` is a property of the field's own annotation, not of the class itself.
- Several existing reflection call sites (`Object.keys`/`values`/`entries`/`assign`, `JSON.stringify`, `for...in`, object-literal/spread field copying) walk `Ty.Fields` directly by position — confirmed each of these would otherwise leak the new hidden tag field as a fake user-visible field/value the moment a class instance flowed through them, a real regression against Stage 1 behavior (class instances already work through these paths today, since they're plain `IsObject` values).

## Decision

**Tag storage** (`codegen/llvm/types.go`): `ClassType(name, fields)` now prepends a hidden `Field{Name: ClassTagField /* "__kml_tag" */, Ty: TypeI64}` at index 0, ahead of every user-declared field. `FieldIndex`/`StructIR`/`StructSize` already derive everything generically from `Fields`' order, so every *named* field access shifts by +1 for free — the same "reuse the existing generic object machinery unmodified" pattern Stage 1 used for `IsObject` itself. A user field literally named `__kml_tag` is a new compile-time error in `registerClasses` (mirrors the existing duplicate-method-name check).

New `Type.VisibleFields()`: returns `Fields[1:]` for a class instance, `Fields` unchanged for everything else. Swapped in at every reflection/enumeration call site that walks *all* fields (as opposed to looking one up by name via `FieldIndex`, which needed no changes): `emitObjectLiteral`'s spread-copy, `emitObjectKeys`/`Values`/`Entries` (plus their `len(...) == 0` "has known fields" guards — see Side effects below), `emitObjectAssign`'s source loop, `emitJSONStringifyObject`, `inferObjectType`'s spread-field-copy, and `emitForIn`. Three of these (`Object.values`/`entries`, JSON.stringify) previously used their loop's own position as the struct GEP index directly; each now re-derives the real offset via `FieldIndex(name)` instead (the same pattern `Object.assign`/the object-literal spread already used), since iterating `VisibleFields()` shifts enumeration position away from real struct offset for a class instance.

**Class ID assignment** (`codegen/llvm/emit_classes.go`): a plain incrementing counter inside `registerClasses`'s existing Pass B, one ID per class in declaration order, stored as `ClassInfo.TagID int64`. No cross-pass persistence needed (Pass A and Pass B already iterate classes in the same order) and no separate `Emitter`-level map — simpler than what was planned during scoping. Kept as a bare `i64`, deliberately *not* merged with a hypothetical future vtable pointer — [TDD-00009](../tdd/TDD-00009.md) explicitly left that merge decision open "until Stage 3 starts"; deciding it now would be designing for a stage not yet scoped.

**Writing the tag**: `emitNewExpression` GEPs field 0 and stores `info.TagID` immediately after `malloc`, before the constructor call — every construction path goes through this one function, including zero-field classes (which now always malloc at least 8 bytes instead of `malloc(0)`, a harmless side effect).

**`instanceof` front end**: new `INSTANCEOF` lexer keyword (`lexer/token.go`, same pattern as Stage 0's `CLASS`/`THIS`); `parseRelational` (`parser/parser.go`) accepts it alongside `<`/`>`/`<=`/`>=`, producing `ast.NewBinaryExpression("instanceof", left, right, pos)` — no new AST node. The right-hand side is never evaluated as a general expression at codegen time: `emitInstanceOf` (`codegen/llvm/emit_classes.go`) requires it to be a bare `*ast.Identifier` naming a class registered in `e.classes`; anything else (a call, a member expression, `Error`/`Date`/`Response`/an unregistered name) is a compile-time error, since this compiler has no runtime constructor values to compare against.

**`instanceof` codegen**, four cases in `emitInstanceOf`:
1. Left is `any`/`unknown`: unbox via the existing `emitUnboxTagPayload`, branch on `tag == kmlTagObject`, and only on that branch `inttoptr` the payload back to a pointer, GEP field 0, load the tag, compare against the target class's `TagID` — merged back through an alloca+branch pattern (consistent with `emitForOfClassIterator`'s own branch/merge shape) rather than an unconditional AND, since dereferencing the payload as a pointer when it isn't one would be undefined behavior. This is the only case emitting real runtime instructions.
2. Left statically `IsClass` with a matching `ClassName`: constant `true`, or (if `Nullable`) a plain `icmp ne ptr ..., null` — no tag load needed at all.
3. Left statically `IsClass` with a different `ClassName`: constant `false` — no inheritance means two distinct classes can never be related.
4. Any other static type: constant `false`, matching real JS (a non-object or unrelated value is never `instanceof` anything).

## Implementation notes

Files touched: `codegen/llvm/types.go` (`ClassTagField`, `ClassType` prepending the tag, `VisibleFields`), `codegen/llvm/emit_classes.go` (`ClassInfo.TagID`, reserved-name guard, tag store in `emitNewExpression`, `emitInstanceOf`, `canonicalizeClassTy` fix — see below), `codegen/llvm/emit_exprs.go` (`emitExpr`/`inferExprType`'s new `"instanceof"` case, `inferObjectType`'s spread fix), `codegen/llvm/emit_objects.go` (`VisibleFields()` swap-ins across `Object.keys`/`values`/`entries`/`assign` and object-literal spread, plus the zero-field-class guard fix below), `codegen/llvm/emit_call.go` (`emitJSONStringifyObject`'s field walk; `emitJSONParseObject` now rejects an `IsClass` target with a clean error rather than silently mishandling the tag), `codegen/llvm/emit_stmts.go` (`emitForIn`), `lexer/token.go` (`INSTANCEOF`), `parser/parser.go` (`parseRelational`).

Non-obvious ordering/correctness details:
- `canonicalizeClassTy` (`emit_classes.go`, [ADR-00064](ADR-00064.md)) swaps a class-typed field's type for the live registry entry to fix self-referential-field staleness — but the live registry entry (`e.classes[name].Ty`) is never `Nullable`, since nullability belongs to the field's own annotation (`Node | null`), not the class itself. Swapping it in wholesale silently discarded a caller's `| null` annotation. Fixed by copying the original `Nullable` flag onto the canonicalized type. Found by `instanceof`'s null-check case (a nullable class-typed field always compiled to constant `true` regardless of actual nullness) — the first consumer that actually depended on `Nullable` surviving canonicalization; nothing in Stage 1/1a's own test suite exercised this.
- A zero-field class (methods-only, e.g. the existing `Utils` test class) has a genuinely known, just-empty field list once `VisibleFields()` strips the tag — but `Object.keys`/`values`/`entries`/`for...in`'s pre-existing `len(...) == 0` guards were written assuming empty `Fields` always means "unknown," which predates classes having any legitimate zero-field case. Fixed by special-casing `IsClass` in those four guards (`!ty.IsClass && len(visFields) == 0`) so a zero-field class enumerates as an empty result instead of erroring, while a plain object's pre-existing empty-fields error is unchanged.

## Side effects discovered

Both bugs above (the `canonicalizeClassTy` Nullable-loss and the zero-field-class reflection guards) are general object-system gaps exposed by, not specific to, this stage's own test coverage — the same pattern [ADR-00064](ADR-00064.md) itself followed for its own two bugs. Both are fixed as part of this change, not deferred.

## Verification

- `go build -o klainmain .`, `go vet ./...`, `go test ./...` — all green (including the full pre-existing suite, confirming the `VisibleFields()` swaps introduced no regressions).
- `make examples` — 60/60 passed (59 pre-existing + the extended `examples/classes/classes.ts`).
- New tests in `tests/classes_test.go`: static `true`/`false` (matching/mismatched class), nullable-class-field null-check reduction, `any`-typed narrowing between two different classes, reserved-field-name compile error, unregistered-class-on-the-right compile error, and a dedicated regression test (`TestE2EClassTagDoesNotLeakIntoReflection`) confirming `Object.keys`/`values`/`for...in`/`JSON.stringify`/`{...spread}`/`Object.assign` all produce tag-free output for both a populated and a zero-field class.
- Manual run of the extended `examples/classes/classes.ts` confirmed the expected `1`/`0` output sequence end-to-end for both the static and `any`-narrowing cases.
