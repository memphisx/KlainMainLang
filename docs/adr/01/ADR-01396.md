# ADR-01396: TLS over the handle table on memory BIOs

- **Relations**: Implements TDD-00244; Extends ADR-01395
- **Date**: 2026-10-05

## Context

[TDD-00244](../../tdd/TDD-00244.md) Stage 5 moves TLS to memory BIOs so the
socket has one owner. The `tls` module's sessions (`tlshandle.c`, over
`klainpool.c`'s handle table) were set on the descriptor with
`SSL_set_fd`. OpenSSL read and wrote the socket itself, so the handle
could not move to a `uv_tcp_t`, which reads into its own callback.

## Decision

- **A session sits on two memory BIOs**, as Node's TLSWrap does. The
  operations table gains `feed` (ciphertext the pool read, or the end of
  the stream) and `drain` (ciphertext to write). It loses `want_write`.
- **The pool owns the socket.** Before a handshake or a read it reads what
  the socket has into the session, and after every session operation it
  drains the ciphertext and writes it.
  - What the socket does not take waits in a per-handle buffer, which arms
    the handle for writable.
  - A TLS write waits while that buffer is non-empty, so the write queue
    keeps its order and its back-pressure.
  - A read of a TLS handle drains every record already fed (not one
    socket-sized chunk) and loops until the session wants more.
  - `pending` counts fed ciphertext that no operation has yet found short,
    so a paused and resumed reader does not stall on records already
    read.
- **A TLS half-close sends `close_notify` and waits for it to be written**
  before `shutdown(SHUT_WR)`.
- The socket's end reaches the session as the BIO's end of stream. A
  handshake still waiting for data at that point fails, as Node reports a
  socket that disconnected before the secure connection was established.
- Windows takes the same path. The `SSL_set_fd` mapping of a descriptor
  to its socket is deleted.
- The HTTP server's and the HTTP client's TLS (`tls.c`) move with the
  server's own Stage 5 move.
