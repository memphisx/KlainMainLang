# ADR-01322: CI runs each platform's parts in parallel, failing fast per platform

- **Relations**: Extends ADR-00732, Amends TDD-00179
- **Date**: 2026-10-01

## Context

Each platform lane ([TDD-00179](../tdd/TDD-00179.md)) ran the whole gate in
one job:
- vet;
- the unit packages;
- the `tests/` suite, unsharded (`make test`);
- the examples.

Since the builtin modules became TypeScript, the suite alone takes over
40 minutes on the Linux test box. The lanes used `fail-fast: false`, so a
failure in one platform let the others run to the end.

Locally, `make test-par` sharded the suite with a shell recipe: deal the
tests into shards, run them concurrently, then re-run the failures
serially. CI could not use that recipe, because Windows has no POSIX
`make`.

The linux-x64 conformance reports were never committed, and nothing
noticed: the website's conformance data simply lacked that platform.

## Decision

1. **`tools/testshard`** holds the sharding:
   - compile the test binary once;
   - deal the tests round-robin into `-shards` shards;
   - run one shard (`-shard i`), or all of them concurrently
     (`-shard -1`);
   - re-run each failed test alone, serially.

   `make test-par` runs every shard. The new `make test-shard` runs one.
   CI calls the tool directly, so Windows runs the same split.
2. **Each platform runs its parts in parallel.** `release.yml`'s test job
   is a matrix over the platforms, with `fail-fast: false`. Each entry
   calls the reusable `test-platform.yml`, whose matrix covers the
   platform's parts with `fail-fast: true`. The parts are:
   - `unit`: vet, the smoke compile, the status check (linux-x64) and
     the unit packages;
   - `examples`: POSIX platforms only;
   - `shard-0` … `shard-5`.

   GitHub's fail-fast cancels within one matrix, so a failing part
   cancels only its own platform's other parts. The other platforms run
   on, and each green one is released.
3. **The release gate** counts parts. Each passing job publishes
   `gate-<platform>--<part>`. A platform gets a release binary when every
   one of its parts published a gate.
4. **`check-conformance`** fails when a supported platform has no
   `docs/testing/<platform>/conformance-summary.json`. The linux-x64
   reports are added from Node304, the Linux x86-64 test box (Ubuntu
   24.04, clang 18).

## Consequences

- A platform's suite time is its slowest shard plus the job setup (2–10
  minutes for the toolchain install, longest on Windows).
- Release behaviour is unchanged. A red platform is dropped from the
  release, and the green ones are attached.
- The shard count lives in three places, each with a comment to keep
  them in step:
  - the parts lists in `release.yml`;
  - `env.SHARDS` in `test-platform.yml`;
  - the release job's gate count.
- `make test` (the whole suite in one process) remains for a single-box
  run.

## Verification

- `make test-shard SHARD=0 SHARDS=400` runs one shard of 10 tests on
  macOS (Apple Silicon).
- The workflow parses (Ruby's YAML loader). Its first real run is the
  next push.
