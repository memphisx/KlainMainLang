# ADR-00083: Classes Stage 3 — inheritance (`extends`, `super`, dynamic dispatch)

- **Relations**: Extends [ADR-00062](ADR-00062.md), [ADR-00063](ADR-00063.md),
  [ADR-00067](ADR-00067.md). Implements [TDD-00009](../tdd/TDD-00009.md).
- **Date**: 2026-07-31

## Context

[TDD-00009](../tdd/TDD-00009.md) staged classes into four parts and shipped
Stages 0-2 (+1a) already: methods/constructors/`this`/generic `new`
([ADR-00062](ADR-00062.md)/[ADR-00063](ADR-00063.md)), and runtime type
tags/`instanceof` ([ADR-00067](ADR-00067.md)). Stage 3 — inheritance — was
the last big piece and, per the TDD's own framing, "the only stage that
genuinely needs dynamic dispatch." Picked up directly as the next class
work; confirmed via grep before starting that `extends`/`super` were
entirely unhandled anywhere in the front end (no keyword tokens, no AST
fields, no codegen path) — a clean slate, not a partial implementation to
extend.

Three scope decisions were made explicit with the user before implementation
(not left to be inferred mid-build), since each is a real fork with a
different effort/risk profile:

1. **Dispatch strategy**: static dispatch except for methods provably
   overridden somewhere in the whole program (vtable dispatch otherwise) —
   the TDD's own stated design, not the simpler "always vtable for any
   hierarchy class" fallback that was offered as a lower-risk alternative.
2. **`super.method(args)`** included alongside `super(args)`.
3. **Implicit constructor synthesis**: a derived class adding no fields of
   its own and declaring no explicit constructor gets a synthesized
   pass-through constructor forwarding every argument to `super(...)`,
   matching real JS/TS default-constructor behavior.

## Investigation

Read the full pre-Stage-3 implementation before designing the diff:

- `codegen/llvm/emit_classes.go`'s `registerClasses` (two passes: seed a
  placeholder `ClassType` per class so self-/forward-referential fields
  resolve, then build each class's real fields/constructor/method
  signatures) and `ClassInfo` (`Ty`, `Constructor`/`CtorSig`,
  `Methods`/`MethodSigs`, `TagID` — no base-class pointer, no vtable,
  nothing hierarchy-aware).
- `emitClassMethodCall`/`emitForOfClassIterator`'s `next()` call both
  hard-coded `call RETTY @ClassName_methodName(ptr this, args...)` — a
  single, unconditional direct call, since before Stage 3 a class-typed
  variable's concrete class was always known exactly at compile time.
- `emitInstanceOf`'s existing 4-case structure (dynamic/any → unbox +
  runtime tag compare; static exact match → constant true; static
  different class → constant false; anything else → constant false) —
  explicitly documented as sound only because no two classes could ever be
  related before inheritance existed.
- `types.go`'s `ClassTagField`/`ClassType`/`VisibleFields` — the hidden tag
  always prepended at field index 0, `FieldIndex`/`StructIR`/`StructSize`
  all purely order-driven over `Fields`. Confirmed this makes base-first
  field layout close to free: a subclass's fields are just the base's own
  (recursively flattened) fields prepended ahead of its own new ones, no
  changes needed to any of the generic GEP/size machinery.
- `emit_func.go:794`'s `emitClosureCallByPtr` — the exact indirect-call IR
  shape (`call RETTY (ptr, ARGTYS...) %fnptr(ARGS...)`) reused as-is for
  vtable dispatch.
- `lexer/token.go`, `ast/nodes.go`, `parser/parser_classes.go`,
  `parser/parser_literals.go`'s `parseNew`/`this`-parsing, and
  `tests/classes_test.go`/`examples/classes/classes.ts` — confirmed no
  `extends`/`super`/`private`/`protected`/`static`/`implements`/`abstract`
  keyword tokens or AST fields existed anywhere; the one `"extends"` string
  match in the parser was `interface extends`'s own unrelated skip-clause
  (`parser_types.go:207`, pre-existing, matched on a bare identifier since
  `extends` wasn't a keyword yet — this had to be updated to check the new
  `EXTENDS` token type once `extends` became one, or it would have silently
  broken).

Considered whether Stage 2's tag field and Stage 3's vtable pointer should
be one merged hidden field (TDD-00009's own open question) or two separate
ones. Decided **separate**: merging would have required every `instanceof`
check (even for non-hierarchy classes) to go through an extra indirection
to reach the tag, complicating the already-shipped, well-tested Stage 2
mechanism for a marginal one-field saving. A class outside any inheritance
tree keeps exactly its Stage 1/2 single-tag layout; only a class in a tree
where *some* method is actually overridden gets the second hidden field —
see Decision.

## Decision

**Front end**: `EXTENDS`/`SUPER` keyword tokens
(`lexer/token.go`); `ast.ClassDeclaration` gained `BaseClass string`; a new
`ast.SuperExpression` (bare `super`) reuses the *existing*
`CallExpression`/`MemberExpression` machinery exactly like
`ThisExpression` already does — `super(args)` parses as
`CallExpression{Callee: *SuperExpression}` and `super.method(args)` as
`CallExpression{Callee: MemberExpression{Object: *SuperExpression}}` via
the parser's ordinary postfix chain (`parser_exprs.go`'s `parseCallMember`),
so no dedicated `SuperCallExpression` node was needed at all — a smaller
surface than originally planned once the existing postfix parsing turned
out to already produce the right shape for free.
`parser_classes.go`'s `parseClassDecl` gained an optional `extends IDENT`
clause right before the existing `{`.

**Registration** (`registerClasses`, rewritten as 5 passes): Pass 0 seeds
every class name under a placeholder type, then validates every `extends`
target and computes a base-before-derived topological order via one DFS
(also catching cycles and unknown/built-in base names — a built-in like
`Error` is simply never in the class-name table, so "extends unknown class
'Error'" falls out for free with no special-casing). Pass 1, per class in
topological order: flattens inherited fields ahead of new ones (rejecting
a name colliding with an inherited or reserved one); builds the *effective*
method table by copying the base's table wholesale then applying this
class's own declarations, marking a name **Virtual** the moment it's found
already present (an override) via a `*MethodSlot` record **shared by
pointer** across every class that has the method available — the key trick
that makes whole-program override detection correct regardless of
processing order: a deep override several levels down retroactively marks
every class between the introduction point and that override as Virtual,
because they all hold the same pointer, not a copy. Also resolves
constructor rules here (see below). Pass 1.5 computes `Descendants` as the
inverse of `AncestorChain` (needed by `instanceof`'s dynamic case). Pass 2,
once every class's override analysis is fully done: groups classes by
`RootClass`, and for each tree with at least one Virtual slot, assigns
slot indices and marks every class in that tree `HasVTable` — deliberately
uniform per whole tree (not per introduction subtree) as a simplification:
a branch with zero overrides of its own still gets the hidden vtable field
if a *sibling* branch has one, but its own calls stay on the direct-call
path regardless (zero added indirection), so the only real cost is one
"often-unused" pointer field on some instances, not a used cause. Pass 3
finally builds each class's real `Ty` via `ClassType(name, inheritedFields,
ownFields, hasVTable)` now that `hasVTable` is known, and publishes it into
`e.interfaces`.

**Field layout** (`types.go`): `ClassType`'s signature changed to
`(name string, inherited, own []Field, hasVTable bool)`. Layout is tag
(index 0, always) → `ClassVTableField` (`"__kml_vtable"`, index 1, only
when `hasVTable`) → inherited fields → own fields. `VisibleFields` skips 1
or 2 leading fields accordingly.

**Method-call dispatch**: `emitClassMethodCall` and
`emitForOfClassIterator`'s `next()` call both now delegate to one new
shared `emitClassCall(objTy, thisVal, methodName, args, pos, forceDirect)`
— looks up the method in the effective table; if its `MethodSlot` is nil or
non-Virtual (or `forceDirect` is set), emits the exact same direct
`call RETTY @Implementor_methodName(...)` shape Stage 1/2 always used;
otherwise loads the vtable pointer off the instance (field 1), GEPs into
the class's `@ClassName_vtable` array at the method's globally-assigned
slot, loads the function pointer, and indirect-calls it via
`emitClosureCallByPtr`'s established IR shape. `super(args)`
(`emitSuperCall`) always resolves directly to `@BaseClassName_constructor`
— constructors have no dispatch concept. `super.method(args)`
(`emitSuperMethodCall`) always takes the direct-call branch via
`emitClassCall`'s `forceDirect=true`, resolving against the scope symbol
`"super"` — bound by `emitClassMember` alongside `"this"` whenever the
enclosing class has a base, to the *same* underlying instance pointer but
typed as the base class, so `super`'s value semantics and its
dispatch-bypass semantics both fall out of one small addition rather than
a second emission path.

**Constructor rules** (in `registerClasses`' Pass 1): an explicit
constructor in a class with a base whose own constructor exists must
contain a `super(...)` call as one of its own top-level statements
(`hasTopLevelSuperCall` — a shallow, non-nested presence check, the same
"cheapest useful check" precedent Stage 1's own "constructor required if
fields present" rule already set), or it's a compile error; calling
`super(...)` when there's no base, or the base has no constructor, is
likewise a compile error. A derived class with zero own fields and no
explicit constructor gets a **synthesized** one: built as a real
`*ast.FunctionDeclaration` whose body is a single `super(...)` call
forwarding every base parameter by name — reusing `emitClassMember`
completely unchanged, since it only ever needed an AST shape, not a
special-cased emission path. Only possible when the base constructor has
no rest parameter (a rest-forwarding `super(...spread)` isn't
representable without a general spread-call mechanism this compiler
doesn't have) — a base with a rest-parameter constructor simply requires
an explicit derived constructor instead; not silently miscompiled, just a
narrower slice (documented in the code, not in this doc's Side effects,
since it was designed in from the start rather than discovered).

**`instanceof`** (`emitInstanceOf`, generalized from 4 cases to 5): the
static case's "different class → false" branch turned out to need
splitting in two once a real bug surfaced — see Side effects.

## Implementation notes

Files touched: `lexer/token.go` (`EXTENDS`/`SUPER`); `ast/nodes.go`
(`ClassDeclaration.BaseClass`, `SuperExpression`);
`parser/parser_classes.go` (optional `extends` clause),
`parser/parser_literals.go` (`super` as a primary expression, mirroring
`this`), `parser/parser_types.go:207` (interface's pre-existing `extends`
skip-clause updated from a bare-identifier-literal match to a real
`lexer.EXTENDS` token-type check, since `extends` stopped being a plain
identifier the moment it became a keyword — would have silently broken
otherwise); `codegen/llvm/types.go` (`ClassVTableField`, `ClassType`'s new
signature, `VisibleFields`); `codegen/llvm/emit_classes.go` (the bulk of
the work — `MethodSlot`, `ClassInfo`'s new fields, `registerClasses`'s
5-pass rewrite, `emitClassDecl`/`emitNewExpression` reading
`info.Constructor` instead of `cd.Constructor` so a synthesized ctor is
picked up transparently, `emitClassVTable`, `emitClassCall`,
`emitSuperCall`/`emitSuperMethodCall`, `emitInstanceOf`'s 5-case rewrite);
`codegen/llvm/emit_call.go` (dispatch for `super(...)`/`super.method(...)`,
checked first — before any `mem.Object`-based generic dispatch, since a
`SuperExpression` receiver never reaches `inferExprType`'s ordinary paths
and shouldn't); `codegen/llvm/emitter.go` (`EmitProgram` gained a Pass 2c
emitting vtable globals after class bodies).

Non-obvious ordering constraint: field-layout finalization (Pass 3) has to
happen *after* the whole-program override analysis (Pass 1 for every
class, then Pass 2's per-tree `HasVTable` decision) because whether a class
carries the hidden vtable-pointer field depends on facts not knowable until
every class in its tree — including ones declared later in the source —
has been examined for overrides. A `provisionalTy` (always `hasVTable =
false`) is used during Pass 1 purely for unannotated-return-type inference
(`this.field` lookups only need field names/types, never the hidden
field's presence), then discarded once Pass 3 builds the real one.

## Side effects discovered

- **A real, load-bearing `instanceof` bug found via
  `examples/classes/classes.ts`, not by inspection**: the original static
  case only handled "`T` is `C` itself or an ancestor of `C`" as true,
  everything else as a compile-time-constant false. That's wrong the
  moment `T` is a *descendant* of `C` — `const s: Shape = new Circle(...);
  s instanceof Circle` was silently and incorrectly compiling to `0`,
  because the concrete runtime subtype held by a base-typed variable isn't
  decidable at compile time at all. Fixed by adding a genuine 2b case: when
  `T` is in `C`'s `Descendants`, emit the same real tag-read-and-compare
  the `any`/`unknown` case already needed (minus the unbox step, since the
  value's already known to be *some* object in the hierarchy), including
  the same nullable-reduces-to-null-check handling case 2 already had.
  Caught immediately by re-running the example after writing it, before
  the change was considered done — not shipped-then-found. A regression
  test (`TestE2EInstanceOfStaticAncestorTypedHoldingDescendant`) now guards
  it directly.
- No other fan-out bugs surfaced this time (unlike [ADR-00082](ADR-00082.md)'s
  15-site hand-written-IR fan-out) — every internal Error-construction site
  from that ADR is entirely independent of class inheritance, and
  `emitErrorInstanceOf` was confirmed untouched/structurally separate both
  before and after this change.
- Deliberately out of scope, unchanged from the TDD: `implements`,
  `static` members, `private`/`protected`, `abstract` (Stage 4, not
  started); generic classes (tracked jointly with function/interface
  generics in [TDD-00010](../tdd/TDD-00010.md)); multiple inheritance (not
  a TS/JS concept); extending a built-in (`Error`, `Date`, `Map`, etc. —
  simply never resolve as a valid `extends` target, since only user
  `class` declarations are ever registered by name).

- `tests/classes_test.go`: 16 new E2E tests — field/method inheritance, a
  direct-call override, dynamic dispatch through a base-typed parameter
  across 2 and 3 levels of hierarchy (including a sibling class with no
  override of its own staying on the direct-call path within an otherwise
  `HasVTable` tree), `super(args)`, the synthesized pass-through

  the correct `1`.
