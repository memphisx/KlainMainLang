# TDD-00040: Real `Request`/`Headers` classes and `XMLHttpRequest` (staged)

- **Status**: Implemented (see [ADR-00130](../adr/ADR-00130.md) — Stage 1, `Request`/`Headers` — and [ADR-00131](../adr/ADR-00131.md) — Stage 2, `XMLHttpRequest`)
- **Date**: 2026-08-08

## Context

[`docs/status/NETWORKING.md`](../status/NETWORKING.md) lists two remaining ❌ rows: real `Request`/`Headers` classes, and `XMLHttpRequest`. Both were previously *deliberately* scoped out — [ADR-00074](../adr/ADR-00074.md)/[TDD-00017](TDD-00017.md) explicitly rejected a `Request`/`Headers` class pair in favor of `fetch(url, init)`'s plain-object `init` argument ("more machinery than this project's existing conventions call for"), and `XMLHttpRequest` was marked "legacy HTTP; lower priority than fetch" with no design ever attempted.

This TDD reverses that scoping decision at explicit user request: the goal is now to bring `NETWORKING.md` to full (6/6) coverage by implementing both for real, rather than leaving them as permanently-out-of-scope rows. This is a genuine design fork from the ADR-00074 precedent, so it gets a TDD of its own rather than growing piecemeal.

## Design

### `Headers` — a flagged `Map<string, string>`, not a new runtime type

This project already has three precedents for "a new browser-API type is just an existing type with a bool flag on it": `URLSearchParams` (`ty := MapType(TypePtr, TypePtr); ty.IsURLSearchParams = true`, `types.go`), `EventEmitter<T>`, and `TypedArray` (`IsArray` + `ElemType`). `Headers` follows `URLSearchParams`'s exact precedent: `HeadersType()` returns a `Map<string,string>` with `IsHeaders = true`. This means `get`/`set`/`has`/`delete`/`forEach`/`entries`/`keys`/`values` are *already implemented* — they're the existing `Map<string,string>` runtime (`__kml_map_str_*`, `emit_collections.go`) with zero new runtime code, exactly as `URLSearchParams` already reuses them for its own `get`/`has`/`delete`/`set`.

Two behaviors need real `Headers`-specific codegen, dispatched in `emit_call.go` ahead of the generic `IsMap` branch (the same "check the narrower flag first" ordering `IsURLSearchParams` already establishes there):

- **Case-insensitive keys**: real `Headers` normalizes every name to lowercase before touching storage. `get`/`set`/`has`/`delete` all lowercase their name argument (`e.ensureStringToLower()` / `@__kml_tolower`, the same primitive `String.prototype.toLowerCase()` already uses) before delegating to the identical `__kml_map_str_get/set/has/delete` calls `emitMapCall` already makes — this is a thin wrapper around `emitMapCall`'s existing logic, not a new mechanism.
- **`append(name, value)`**: the one genuinely new method (real `Map` has no equivalent) — per spec, combines with the existing value using `", "` if `name` is already present, otherwise behaves like `set`. Implemented directly: `has` check, then either `set(name, value)` or `set(name, existing + ", " + value)` via the existing `emitStringConcat` helper (`emit_strings.go`) — same helper `buildFetchHeaderList` already uses to join `"key: value"` lines.

Construction: `new Headers()` (empty) or `new Headers(init)` where `init` is a `Map<string,string>` (copies every entry, lowercasing each key) — deliberately not a full `HeadersInit` union (array-of-pairs, plain object) since this project has no object-literal-as-map coercion mechanism to draw from; `Map<string,string>` is the one input shape every other header-bag API here already uses (`req.headers`, `fetch`'s own `init.headers`).

### `Request` — a plain object, exactly like `Response`/`URL`

`FetchRequestType()` (named to avoid colliding with the *existing*, unrelated `RequestType()`/`IsRequest` in `types.go` — that one is `http.listen`'s server-side `req` object, a completely different type that happens to share the obvious name) is a plain heap object: `url: string`, `method: string`, `headers: Headers`, `body: string | null` — directly readable fields, no dispatched getters, the same "plain object, fields readable directly" precedent `Response`/`URL` already established. `new Request(url)` / `new Request(url, init)` reuses `emitFetch`'s own existing init-field-extraction pattern (`FieldIndex("method")`/`FieldIndex("headers")`/`FieldIndex("body")` on the init argument's inferred type) almost verbatim — `method` defaults to `"GET"`, `headers` defaults to an empty `Headers`, `body` defaults to `null`.

### `fetch()` grows a third call form: `fetch(request)`

`emitFetch` currently branches on argument count (1 or 2). It grows a third shape: a single argument whose inferred type is `IsFetchRequest` is destructured into url/method/headers/body exactly like the `init` object's fields are today — no new runtime signature, `__kml_fetch_async` is unchanged. `fetch(url, init)`'s existing `init.headers` field-type check (`fieldTy.IsMap`) already accepts a `Headers` value with zero changes, since `Headers` *is* `Map<string,string>` under the hood — this is what makes the two features compose for free rather than needing cross-wiring.

### `XMLHttpRequest` — legacy sync-style API, built on the existing non-blocking fetch primitives

The real spec's default-async, callback-driven model (readyState transitions interleaved with other script execution while a request is in flight) doesn't fit this compiler's execution model without new re-entrancy machinery this project doesn't have. Real browsers also still support fully synchronous XHR (`open(method, url, false)`) — this implementation targets that observable behavior: `.send()` runs the request to completion before returning, then fires the registered callbacks once, synchronously, before `.send()`'s call site continues. This is the same class of deliberate simplification `WebSocket`'s client already set precedent for (`WebSocketClientType`'s doc comment: "performs its TCP connect + HTTP upgrade handshake *synchronously*").

Critically, `.send()` does **not** need a new blocking curl transfer path. It reuses `__kml_fetch_async` (build the pending handle) followed by a *new*, small runtime primitive `__kml_await_fetch_settled` — a structural clone of the existing `__kml_await_fetch`'s checkloop/maybeyield/doyield/busyspin loop (`emit_fetch.go`/`runtime_fetch.go`), except it finishes via the already-existing `__kml_pending_finish_settled` (built for `Promise.allSettled`, [ADR-00073](../adr/ADR-00073.md)) instead of the throwing `__kml_pending_finish`. This gets two things for free: (1) `.send()` yields the current fiber instead of blocking the whole process when called from inside an `http.listen` connection handler, identical to `await fetch(...)`'s own non-blocking behavior; (2) a network-level failure surfaces as a `{failed: true, reasonMsg}` value XHR's codegen branches on directly to fire `.onerror` instead of throwing — matching real `XMLHttpRequest`, which never throws from `.send()` on a network error.

Fields: hidden (`__kml_xhr_method`, `__kml_xhr_url`, `__kml_xhr_headers` — a `Map<string,string>` pointer built by `setRequestHeader`, the same `VisibleFields()`-hides-a-prefix convention `EventSourceType`/`WSConnectionType` already use) plus visible `readyState`/`status`/`responseText`/`response` (a plain alias of `responseText` — only a text `responseType` is supported, matching `fetch`'s own `.text()`/`.json()` string-based body model) and three zero-argument callback fields: `onreadystatechange`, `onload`, `onerror`.

**Callback ABI is deliberately zero-argument**, unlike `EventSource`/`WebSocket`'s payload-carrying `onmessage` (`FuncType([]Type{MessageEventType()}, TypeVoid)`). Real `onreadystatechange` also takes no arguments (script reads `this.readyState` off the XHR instance itself) — a `FuncType([]Type{XMLHttpRequestType()}, TypeVoid)` field would require `XMLHttpRequestType()` to reference itself while being constructed, an unbounded Go-level recursion this project's `Type`-as-a-value (not a pointer/lazy-thunk) representation can't express the way a real class's `Field.Ty` self-reference can (see `canonicalizeClassTy`'s doc comment on why *that* case needs a registry-lookup workaround at all). Zero-argument callbacks sidestep the problem entirely and match how real code overwhelmingly uses `onreadystatechange` anyway (closing over the `xhr` variable from the surrounding scope, not receiving it as a parameter).

**Explicitly out of scope, matching existing precedent elsewhere in this feature area**: response header access (`getResponseHeader`/`getAllResponseHeaders`) — `fetch`'s own `Response` doesn't expose response headers either (no `HEADERFUNCTION` capture exists anywhere in this codebase yet), so this isn't a new gap unique to XHR, just the same one inherited. `abort()` is a best-effort `readyState` reset (real abort-mid-flight has no meaning once `.send()` — synchronous by construction here — has already returned). No `responseType` other than the default (text). No `withCredentials`/timeout/upload-progress surface.

### Naming collision to watch during implementation

`codegen/llvm/types.go` already has `RequestType()`/`IsRequest` for `http.listen`'s server-side request object — completely unrelated to this feature's client-side `Request`. The new type uses `FetchRequestType()`/`IsFetchRequest` throughout to avoid any ambiguity; `structuredCloneUnsupportedKind`'s error-message string for both can legitimately say `"Request"` (user-facing text, not a Go identifier) with no actual collision.

## Open questions

None blocking implementation — every piece reuses an existing, already-proven mechanism (flagged-`Map` precedent, `fetch`'s init-extraction pattern, the non-blocking fetch primitives, zero-arg closure fields). The one real design choice (XHR sync-over-async) is made above with its rationale, not left open.
