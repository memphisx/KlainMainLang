# ADR-01943: Each object layout gets a row with its size and pointer map, and -mm=gc allocates through it

- **Relations**: Implements TDD-00230, Extends ADR-01941
- **Date**: 2026-10-28

## Context

TDD-00230 Phase 5 asks for a layout table indexed by type id. It holds:

- the object size;
- a pointer map that tells raw managed pointers, NaN-boxed words, interior pointers and external memory apart;
- field names, the class name, the parent and a method table.

A precise collector needs the pointer map, and `kml_gc_alloc(typeid)` is that table's allocation entry point.

Under `-mm=gc` every object was allocated with `GC_malloc`, so Boehm scanned all of it conservatively. A number field whose bits look like an address keeps whatever block it points into alive.

## Investigation

- **What exists already:**
  - The shape rows (`unitKindShape`, `KmlShape`) are this table's names part: id, class name, keys, a generated getter and setter, and method symbols. They are emitted only for layouts a program boxes, and only when it uses the shape runtime.
  - The parent and the inspect, `toStringTag` and constructor entries are rows of their own kinds, keyed by the same type id.
  - Size and pointer map exist nowhere.
- **Where objects are allocated:** every headered object goes through `emitObjAlloc`, `emitObjAllocInto` or `emitObjMallocInto`. Tuples and entry pairs have no header, so they cannot be found by type id.
- **What a word holds**, judged from the field's type:
  - A `double`, `float` or `i1`–`i32` field holds no address.
  - A dynamic field is a NaN box.
  - An array, function value, string or prefixed host body is a pointer past a prefix word.
  - A headered object is a pointer to the block's start, and so is the key-order list (`kml_alloc` of a raw block).
  - The presence word is a bitmask.
  - Any other `i64` (a JSDoc `int64`, an opaque handle) is left unclassified and traced.
- **Boehm:** `GC_make_descriptor` turns a word bitmap into a descriptor, and `GC_malloc_explicitly_typed` allocates a zeroed object scanned through it. Both live in `gc/gc_typed.h`, part of the same libgc install.

## Decision

- **The layout row** (`unitKindLayout`, 11): `{ i64 id, i64 size, i64 nwords, ptr kinds }`, keyed by the header word's type id, with one kind byte per 8-byte word:
  - 0: data
  - 1: header
  - 2: block start
  - 3: past a prefix word
  - 4: NaN box
  - 5: unclassified

  A moving collector needs these kinds. Boehm traces kinds 2 to 5.
- **Generation:** `layout_table.go` derives the kinds from the layout's `Type`, with offsets from `irStructOffsets`, the same computation `kml_layout.h` uses. The C side's constants come from Go: `KML_UNIT_LAYOUT` and `KML_WORD_TRACED` are prefixed to the shim's source.
- **Allocation:** under `-mm=gc`, a headered object is allocated by `kml_gc_alloc_typed(id, size)` (`emitObjBlock`).
  - The shim caches one descriptor per type id in a lock-free table: a CAS claims the id, then the descriptor is published.
  - A layout without a row, or whose size disagrees with its row, falls back to a conservative `GC_malloc`.
  - The other modes keep `calloc`/`malloc`.
- **The header offset is named:** `hdrWordSize` (with `prefixWordOff = -hdrWordSize`) is the word a block starts with before its body. Every site that computes a body past its header word goes through `emitBodyAddr`, instead of repeating the literal `8`; the emitted IR is unchanged. Field offsets inside records (`{fn, env, …}`, cells) stay field offsets.
- **The names part** stays in the shape rows, keyed by the same id. Merging the two kinds into one row waits for a consumer that needs both at once.

- **32-bit targets are refused.** Every layout, NaN box and header assumes 8-byte words, so a 32-bit triple (`wasm32`, `i686`, any `arm` other than `arm64`/`aarch64`) given with a sysroot used to be miscompiled without a word. `--target` now refuses it up front and names the 64-bit targets.

## Consequences

- `-mm=gc` no longer scans an object's number, boolean or presence words as possible pointers.
- Phase 5 work still open: headerless allocations (tuples, entry pairs, closures' environments) remain conservative; the object-start bitmap; 32-bit layouts (until then, a 32-bit target is refused).

## Verification

- A probe that churns 200,000 linked objects and 50,000 class instances, mixing number, string, array, object, function and `any` fields, matches Node under `-mm=gc` on the Mac, with the typed path in use for every layout. It is now `TestE2EGCModeTypedLayouts`.
- Every `GC` E2E test passes on the Mac.
