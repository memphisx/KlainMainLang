# TDD-00121: Conformance V4 — in-scope Test262 subset counter, Node-core oracle, TypeScript acceptance oracle

- **Status**: In Progress
- **Date**: 2026-08-25

## Context

[TDD-00082](TDD-00082.md) established the external-conformance strategy across three buckets and left three
threads unfinished. Working through them surfaced two problems worth solving now and one conclusion worth
revisiting:

1. **The headline Test262 number is honest but misleading in one direction.** The runner
   (`tools/conformance/main.go`) reports the full, unfiltered corpus — currently 10.9%. That is correct and
   deliberately un-curated, but most of the corpus is out of this compiler's target by construction: `eval`-
   based untyped-JS assertion files (`eval` is an unstarted opt-in, [TDD-00046](TDD-00046.md)), `Intl`
   (`intl402`, out of scope), Annex-B legacy web-compat, and dynamic-object-model probes. A reader who sees
   only 10.9% cannot tell "we fail the in-scope language" from "the corpus mostly tests things we never
   claimed to do." We need a second number: the pass rate over the **in-scope subset**, reported *beside* —
   never replacing — the raw full-corpus number, so both the ceiling (raw) and the target (in-scope) are
   visible. There is no per-test curation involved: the subset is defined mechanically from Test262's own
   `features:`/`flags:` frontmatter tags, so it stays reproducible and auditable, not hand-picked.

2. **The Node.js bucket still has no behavioral oracle.** TDD-00082 designed it (track 3, pure-modules-only
   behind a minimal `common`+`assert`+`require` shim) but deferred implementation behind the async work,
   which has since landed (timers, microtasks, `Promise` chaining, async/await). It is now unblocked.

3. **TDD-00082 concluded the TypeScript-conformance track was *terminal*** — "a type-checker-output corpus
   with no expected-stdout oracle, so it cannot be run against a compile-and-run pipeline." That conclusion
   is correct *only for the compile-and-run framing*. Microsoft's `tests/cases/{compiler,conformance}` corpus
   ships a **baseline** per case in `tests/baselines/reference/`: a case expected to produce type errors has
   a companion `*.errors.txt`; a case expected to compile clean has none. That is a usable **accept/reject
   oracle** for a *front-end* pipeline (parse + resolve, no codegen, no run): does this compiler reject what
   TypeScript rejects and accept what it accepts? This is a different comparison mode than Test262/WPT
   compile-and-run, not an impossible one — so the "terminal" conclusion is **reversed** here. TDD-00082's
   design text stays the honest record of its moment (per the supersession precedent it itself sets); only
   its TS-track status pointer is updated to reference this reversal.

## Design

Three tracks, added beside the existing Test262 runner, each reusing its infrastructure
(`parseFrontmatter`/`normalizeReason`/`blockerOf`/`killableCommand`/worker-pool/`writeReport` shape, the
fetch-don't-vendor pattern in `fetch.sh`, the `harness-shim/` prepend approach).

### Track A — in-scope Test262 subset counter

A **report feature**, not a language feature; the corpus and per-file execution are unchanged.

- Extend `frontmatter`/`parseFrontmatter` to also capture `features: [...]` and `flags: [...]`, using the
  same hand-rolled single-line flow-list extraction already proven for `includes` (Test262's frontmatter is
  regular enough that no YAML dependency is needed — the zero-external-Go-deps rule holds).
- Add `inScope(fm, category) bool`. **Out of scope** (this compiler's typed, no-`eval`, no-dynamic-object,
  no-`Intl` target):
  - category `intl402`, `annexB`, `staging` — wholesale out.
  - `flags` containing `raw` (no harness, usually engine-detail), or `async` (deferred until the async
    harness path is measured, not because it can't run).
  - `features` on a **deny-list** of decisively-out-of-scope tags: the `eval`/`Function`-dynamic family,
    `__proto__`/`Proxy`/`Reflect`/prototype-mutation, `tail-call-optimization`, `Intl`-adjacent,
    `generators`-vs-caveat items, etc. Encoded as an explicit `map[string]bool` with a comment block giving
    the rationale per entry, so the definition is auditable and iterated by evidence, not guessed perfect.
  - Everything else is **in scope** (the core language + the standard-library surface this compiler targets).
- Add `InScope bool` to `result`; in `writeReport`, add a **"## In-scope subset"** section: passed / total /
  % over `InScope` files, plus an in-scope cut of the per-category table. The raw **## Overall** stays first
  and byte-for-byte unchanged. The methodology note is extended to explain that the two numbers bound the
  same thing from opposite ends.

The deny-list is deliberately conservative at first (over-include in scope is the safer error: it depresses
the in-scope number rather than inflating it). Refined by reading the resulting failure buckets.

### Track B — Node-core oracle

> **Scope correction (implementation):** this track was first scoped to the
> "pure modules" (`path`/`querystring`/`url`, ~33 files) per TDD-00082. That
> denominator is meaninglessly small against the ~3,478-file `test/parallel`
> suite, so the implementation runs the **whole** suite and reports honestly
> against it (see [ADR-00366](../adr/ADR-00366.md)). The skip histogram makes the
> harness coupling visible rather than hiding it behind a hand-picked subset.


- `fetch.sh` gains a pinned, sparse, blobless `nodejs/node` checkout of the pure-module tests
  (`test/parallel/test-path*`, `test-querystring*`, `test-url*`) plus `test/common`, into a gitignored dir —
  mirroring the Test262 fetch (SHA-pinned; corpora fetched, never vendored).
- `tools/conformance/node-shim/`: a minimal CommonJS `require` resolver + a `common` stub exposing only the
  probes those ~39 files touch (`mustCall`, `mustNotCall`, platform/flag booleans), reusing the `assert`
  shape from `harness-shim/`. Kept intentionally tiny; a module whose files lean on more of `common` than the
  shim covers is dropped to the hand-mine fallback rather than growing the shim unboundedly.
- Runner: a `-suite=node` mode reusing the compile-through-the-real-pipeline + run path. Reports a **Node-
  core** section (passed / total / % per module). A file that needs an unshimmed `common` surface counts in a
  visible "skipped (unsupported harness)" bucket, not as a silent fail.

### Track C — TypeScript acceptance oracle (front-end only)

- `fetch.sh` gains a pinned (release-**tag**, since TS is versioned — stable denominator) sparse checkout of
  `microsoft/TypeScript` `tests/cases/{compiler,conformance}` + `tests/baselines/reference/*.errors.txt`,
  gitignored.
- Runner: a `-suite=ts` mode that, per `.ts` case, runs **parser + resolver + emitter front-end only** (no
  clang, no execution) and classifies:
  - baseline `*.errors.txt` **present** ⇒ expected-reject ⇒ **pass iff we produced a compile error**;
  - baseline **absent** ⇒ expected-accept ⇒ **pass iff we compiled clean**.
- Error-*message* fidelity (does our message name the same defect at the same position) is a later
  refinement; V1 measures accept/reject only, and says so in the report.
- Cases using syntax/type features this compiler deliberately doesn't target land in a visible
  **out-of-scope** bucket (the discipline Test262's `intl402`/`.html` handling already sets), not as silent
  fails — otherwise the number measures scope, not correctness.
- Multi-file cases (`// @filename:` directives) and cases depending on `lib.d.ts` ambient surface are the
  main classification hazards; start with single-file cases and bin the rest as out-of-scope-for-now.

### Reporting & Makefile

Each track writes its own report doc (`CONFORMANCE-RESULTS.md` keeps Test262 + the in-scope section;
`CONFORMANCE-RESULTS-NODE.md` and `CONFORMANCE-RESULTS-TS.md` for B and C) so the slow full Test262 run stays
independently batchable. `make conformance-node` / `make conformance-ts` targets sit beside `conformance`;
each fetches its corpus first, like `conformance` does.

## Open questions

- Track A: is `async`-flagged inclusion worth measuring once the async harness path is exercised, or does it
  stay out? (Deferred; start out, promote by evidence.)
- Track B: for `url`, is Node's `test-url*` or WPT's `url/` (TDD-00082 track 2) the better oracle? Measure
  both when WPT lands; they are not mutually exclusive.
- Track C: how many cases are single-file and `lib`-independent enough to classify cleanly vs. how much of
  the corpus falls to the out-of-scope bin — only measurable once the runner exists. The initial number is a
  floor, expected to rise as multi-file support is added.
- One combined report vs. per-track docs: per-track chosen for batchability; revisit if cross-track
  blocked-by ranking (TDD-00082's histogram idea) wants a single view.
