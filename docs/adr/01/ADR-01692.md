# ADR-01692: Every declared key has a presence bit, and objects keep their key order

- **Relations**: Implements TDD-00230
- **Date**: 2026-10-18

## Context

TDD-00230 P3.3. ADR-01314 let only an optional member lack its key, and a static layout listed its keys in field order. Node differs in five cases:
- **JSON missing key:** `JSON.parse('{}')` into `{ t: string }` printed `{ t: undefined }`. Node omits `t`.
- **`declare` field:** `declare x: number` was a parse error. Node has no `x` property until something assigns it.
- **Literal order:** a literal written out of field order (`{ n: 2, t: 'a' }` for `{ t: string; n: number }`) listed `t` first.
- **JSON order:** a JSON input listed its keys in field order, not input order.
- **Delete and re-add:** `delete o.b; o.b = 9` listed `b` where it was declared. Node lists it last.

## Decision

**A presence bit for every key.** A layout the program declares takes the presence word whenever it has a member (`withKeyPresence`): interfaces, type literals, intersections, mapped, utility and generic types, literals' inferred types, and classes.
- **An optional field's bit marks its key; a required field's bit marks its absence** (`absentMask`). A zeroed word then has every required key, whichever path allocated the object: a rest copy, a relayout, a stack literal, a C-built object. Only three things set a required field's bit: a JSON input that leaves the key out, a `declare` field at `new`, and delete. Assigning the key clears it.
- **Through a structural view,** an object of another layout has the view's required keys.
- **Merged layouts:** an intersection or an extending interface puts its word after the merged fields. A subclass keeps its base's word where the base's code finds it.
- **Builtin layouts keep the old rule** (`withPresence`, a word only for optional members): their readers and allocators in C know their fields.

**The order slot.** An order pointer, `__kml_order`, follows the presence word. Null means the layout's own order. Otherwise it points at a block `[count, bit, …]` listing the string keys in creation order (`keyordersrc/keyorder.c`).
- **A literal** written in another order gets a copy of a constant block.
- **A JSON projection** records the input's order (`__kml_keyorder_json`, in `json_parse.c`).
- **Assigning a key that was absent** moves it last (`__kml_keyorder_add`, which creates no block when the key already ends the layout's order).
- **Delete** removes it from the block.
- **A literal with a spread** builds its block at run time: each key is pushed as the literal creates it, and a spread pushes the source's present keys in the source object's own order (`__kml_keyorder_push_src`).
- **Integer-like keys** always list first, ascending, as ES orders them.

**Readers.**
- Inspect and `JSON.stringify` render each present key into a slot by bit, then emit the slots in the object's order (`keyOrdered`).
- `Object.keys`, `values`, `entries` and for…in write each present key at its rank (`keyRanks`).
- Through a structural view, only an object of exactly the view's layout has the slot there. Any other reads a null slot.

**Cost.** Each declared object is 16 bytes larger, and a write to an absent key costs one bit test plus a call. Readers of a layout with the slot take the run-time path, and pay a ranking call per read. This is recorded as a perf follow-up: an opt-in flag could drop the slot for programs that never reorder keys.

**Not covered:**
- A boolean or integer field missing from JSON reads `false` or `0`, since its slot can't hold undefined. Its key is still absent.
