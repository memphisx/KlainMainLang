# TDD-00255: `klain:http` as a TypeScript module over a selectable server backend

- **Status**: Implemented
- **Date**: 2026-10-17

## Context

`klain:http` is the last builtin module compiled directly by the code generator rather than written in TypeScript ([ADR-01471](../adr/01/ADR-01471.md) left it for last on purpose). Its server works like this:

- `resolver/virtual_modules.go` marks the import, and `emit_call.go`'s `klainHTTPNamespaceCall` dispatches `listen`, `close` and `closeAllConnections`.
- `emit_http.go`'s `buildHTTPDispatcher` emits a request parser as about 900 lines of IR text. It finds the end of the headers with `strstr`, frames the body by `Content-Length` only, and has no chunked request bodies.
- Each connection is a ucontext fiber in loop.c's `__kml_conn_data` table. The fibers are resumed from the loop pass by readiness bitmaps (`sync_sources`, `scan_conns`), not from libuv read callbacks.
- h2c goes to `http2.c`, which does blocking-style `read`/`write` on the fiber and runs handlers synchronously.
- `HttpRequest` is a type the code generator special-cases (`types.go`).
- The runtime is IR text across `runtime_http*.go`, which `TestIRTextOnlyShrinks` counts against.

This is what keeps two items open:
- TDD-00230 P3.2: `klain:http`'s host objects, and `@lowerType` on class declarations.
- [TDD-00244](TDD-00244.md) Stage 5: the server on libuv handles with handle-ref keep-alive.

It also causes these bugs:
- A connection fiber's stack has no guard page under `-mm=gc` ([TDD-00249](TDD-00249.md)).
- An HTTP example hangs about 1 run in 15 on the M4 (BACKLOG item 8).

`klain:http` is the project's own server, not Node's (`http` is Node's, in TypeScript over `net`). Its reason to exist is speed, memory and native integration ([TDD-00131](TDD-00131.md)). Its backend should be the fastest available server core, chosen at build time.

## Design

### Surface (unchanged for programs)

`lib/node/klain_http.ts`, found by the same `ModulePath` mapping as `klain:ws`. It exports:

- `listen(port: number, handler: (req: HttpRequest) => Res | Promise<Res>, opts?: ListenOptions): void`
  - `Res` is `{ status: number; body?: string | ReadableStream<Uint8Array>; bodyBytes?: ArrayBuffer; headers?: Map<string, string> }`.
  - `ListenOptions` is `{ workers?: number; host?: string }`. `host` becomes a run-time value instead of a compile-time literal.
  - It blocks until `close()`, as today. Top-level code runs as the module task ([TDD-00224](TDD-00224.md)), so `listen` parks that task on a promise settled when the server closes, through the same park an `await` uses. Called outside a task (from a callback), it returns at once.
- `close(): void` and `closeAllConnections(): void`.
- `class HttpRequest`:
  - fields `method`, `path`, `query: Map<string, string>`, `headers: Map<string, string>` and `body: string`;
  - methods `bodyBytes(): ArrayBuffer`, `stream(): ReadableStream<Uint8Array>` and the Node `Readable` view, which comes from `Readable.fromWeb`.

The one-`listen`-per-program limit and the structural handler check in Go go away. The checker types the handler against the declaration like any other call.

### Request flow: callbacks, not fibers

A backend delivers each request as a native callback, `inv(clo, requestHandle)`, from inside the loop. There is no connection fiber, so an async handler is an ordinary promise:

```ts
backend.onRequest((r) => {
  const req = new HttpRequest(r);
  const out = handler(req);
  if (out instanceof Promise) out.then((res) => respond(r, res), (e) => fail(r, e));
  else respond(r, out);
});
```

- **When the handler runs.** A request's body is buffered, and the handler runs once the body is complete, up to the 10 MiB buffer cap (the cap the buffered path has today). A body that reaches the cap first, such as a 12 MiB upload, runs the handler at that point in streaming state:
  - `stream()` yields the buffered prefix and then the rest as it arrives;
  - `req.body` and `bodyBytes()` throw a `RangeError` naming the cap.
  - The handler no longer has to be compiled differently depending on whether the program calls `stream()` anywhere.
- **`stream()`** on a complete body yields the buffer. A streamed body pushes chunks into a `ReadableStream` controller, and backpressure pauses reading. Once `stream()` has started, `req.body` throws a `TypeError` (the body is already disturbed, [ADR-00362](../adr/00/ADR-00362.md)).
- **Responses**:
  - `respond(r, status, headers, bytes)` writes the whole response.
  - A `ReadableStream` body uses `respondStart`/`respondWrite(r, chunk, cb)`/`respondEnd`. The write callback is the backpressure signal.
- **Keep-alive, pipelining, `Expect: 100-continue`, 431 on oversized headers, and chunked request bodies** belong to the backend.
- **Liveness**: the listener and each open connection are referenced libuv handles. `close()` closes the listener, and `closeAllConnections()` closes the connections. When nothing referenced remains, the loop ends, so there is no keep-alive predicate.
- **Cluster (`workers`)**: the primary forks after bind, as today (`SO_REUSEPORT` on POSIX, a round-robin hand-off on Windows). The fork and the hand-off move out of IR text into C natives that the module calls before it serves.

### Backends, selected at build time

`--http-backend=h2o|native`. The default is `h2o` where libh2o is found, otherwise `native`. `klain_http.ts` imports `./internal_khttp_backend`, which the resolver maps to the chosen backend's file. Both backends export the same TypeScript interface: `serve(host, port, onRequest)`, request accessors, `respond`, `respondStart`/`respondWrite`/`respondEnd`, `close` and `closeAll`.

1. **`h2o`**: libh2o, the variant built on libuv (`libh2o-dev` on Ubuntu 24.04, `brew install h2o` on macOS). It runs on the program's own loop: `h2o_context_init(ctx, __kml_loop_uv(), …)`, with each accepted socket wrapped by `h2o_uv_socket_create`. One `h2o_handler_t` turns an `h2o_req_t` into a request handle and calls the TypeScript callback. Responses go through `h2o_send_inline` (whole) or a `h2o_generator_t` (streaming). HTTP/2 (h2c and ALPN) and HTTP/1.1 parsing come from h2o.
2. **`native`**: TypeScript over `net`. That means `uv_tcp_t` handles ([ADR-01681](../adr/01/ADR-01681.md)) plus the llhttp-rules parser natives (`httpParser*`) that Node's `http` already uses here, without `IncomingMessage`/`ServerResponse`'s Node machinery: one parser per connection, requests handed to the module as callbacks, and responses serialized straight to the socket. h2c with prior knowledge hands the socket to `lib/node/http2.ts`'s session over the nghttp2 natives. This backend is the default on Windows, where MSYS2 has no libh2o, and wherever libh2o is missing. h2o's file is the only one with new C (`@lower … @link h2o`).

A third backend, such as `picohttpparser` or io_uring, would only be a new archive that implements the same ABI.

### `@lowerType` on a class (P3.2)

`/** @lowerType kml_khttp_req */ class HttpRequest` declares that instances have a native layout: the backend fills the fields, and TypeScript reads them as ordinary fields. This is P3.2's general mechanism, so a declared class's fields map onto a C struct, and the library builds no copies. Until Stage 3, `HttpRequest`'s constructor reads the fields through natives (`khttpReqString(r, which)`).

### What is deleted

- The `klain:http` virtual-module marker and member list, and `klainHTTPNamespaceCall`.
- `emit_http.go`'s dispatcher and h2 bridge, `emit_http_upgrade.go`'s `klain:http` part, and the `HttpRequest` special cases in `types.go`.
- The `klain:http` parts of `runtime_http.go`, `runtime_http_reqbody.go`, `runtime_http_reswrite.go` and `runtime_http_stream.go`.
- loop.c's connection table: `__kml_listen_fd`, `__kml_conn_data`, `sync_sources`, `scan_conns`, the readiness bitmaps, `__kml_conn_poke` and `__kml_http_xl_*`.
- `httpsrv.c`'s listener table and `http2.c`. The fiber branch of `__kml_task_await_ready` goes with them.

This is gated on nothing else still using them. Node's `http`, `https` and `http2` already run in TypeScript over `net`, so the conn table's only remaining user is `klain:http`.

## Stages

1. **TypeScript module with the `native` backend, at parity.**
   - `klain_http.ts`, the backend interface, and `native` over `net` and the parser natives (with h2c through `http2.ts`).
   - Every existing `klain:http` test and example passes unchanged.
   - Delete the code-generated path and the conn table.
   - Update the status rows and the website reference (`http.json`, which still says `select()`).
   - This closes TDD-00244 Stage 5.
2. **The `h2o` backend.**
   - `LocateH2O` (pkg-config `libh2o`, with a fallback to `-lh2o`) and `--http-backend`.
   - The toolchain action and the box image install `libh2o-dev` / `h2o`.
   - The same test suite runs under both backends: each `klain:http` test runs once per available backend.
3. **`@lowerType` on class declarations.** The checker and code generator map a declared class onto a native layout. `HttpRequest` is the first user.

## Open questions

- Whether Homebrew's `h2o` formula installs the libuv build of the library (`libh2o`) or only the server binary and `libh2o-evloop`. If only the latter, macOS defaults to `native` until the library is vendored.
- HTTPS for `klain:http` (h2o makes it cheap, through ALPN and h2) is a new surface. It is not part of parity, and would come after Stage 2.
