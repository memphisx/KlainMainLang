# ADR-01618: Recursive fs.watch everywhere, positioned transfers in one call, udp6 options on Windows

- **Relations**: Extends ADR-01614, TDD-00244, ADR-01263
- **Date**: 2026-10-14

## Context

Three rows carried platform caveats:

- `fs.watch(dir, { recursive: true })` was documented as watching the top
  directory alone on Linux and Windows.
- A positioned `fs.read`/`fs.write` on Windows seeked, transferred and put
  the position back: three calls, so two transfers on one descriptor from
  the thread pool could read or write at each other's offset.
- `dgram`'s TTL, multicast options and membership on Windows passed IPv4
  option numbers whatever the socket's family, so a `udp6` socket's
  options and groups did not apply.

## Investigation

- Since TDD-00252 a watcher on Windows is a libuv `uv_fs_event_t`, whose
  `UV_FS_EVENT_RECURSIVE` is `ReadDirectoryChangesW` over the tree: a
  change two levels down already reached the listener as `sub/deep/x.txt`,
  as Node prints. The caveat was stale for Windows.
- libuv ignores the flag on Linux (inotify watches one directory); Node
  implements recursion there itself (`lib/internal/fs/recursive_watch`): a
  watch per directory below the root, names relative to the root, and a
  directory that appears is watched with its subtree.
- libuv's `fs__read`/`fs__write` on Windows pass the offset in an
  `OVERLAPPED` to one `ReadFile`/`WriteFile` and restore the file position
  after. With many positioned reads in flight, Node 24 on this machine
  leaves the unpositioned position anywhere (the restores race); the data
  each read gets is right.
- Winsock's IPv6 options are `IPPROTO_IPV6` (41) with `IPV6_UNICAST_HOPS` 4,
  `IPV6_MULTICAST_IF` 9, `IPV6_MULTICAST_HOPS` 10, `IPV6_MULTICAST_LOOP` 11,
  `IPV6_ADD_MEMBERSHIP`/`DROP` 12/13; libuv takes an IPv6 interface as an
  address's scope (`::%3`) and refuses a group of the other family with
  `EINVAL` (Node prints `v4 group EINVAL` for `addMembership('239.1.2.3')`
  on a `udp6` socket).

## Decision

- `fswatch.c` on Linux: a recursive watcher walks the tree (not following
  symbolic links) and starts a libuv handle per directory, reports names
  joined to the directory's path relative to the root, watches a
  directory that appears, and stops, refs and unrefs the handles with the
  watcher.
- `win32fs.c` defines `pread`/`pwrite`: one `ReadFile`/`WriteFile` at the
  offset, the position restored after; `ESPIPE` on a pipe or console,
  `EISDIR` reading a directory. The thread pool's positioned transfers
  call them on every platform.
- `klainpool.c` on Windows picks the IPv6 level and numbers from the
  socket's family for the TTL and multicast options, joins and leaves IPv6
  groups with Winsock's `ipv6_mreq` (the interface from the scope), sets
  `IPV6_MULTICAST_IF` from the scope, and refuses a group of the other
  family with `EINVAL`.

## Implementation notes

`codegen/llvm/fssrc/fswatch.c`, `codegen/llvm/win32src/win32fs.c`,
`codegen/llvm/threadpoolsrc/klainpool.c`; tests
`TestE2EFsWatchRecursive`, `TestE2EFsPositionedParallel`,
`TestE2EDgramUdp6MulticastOptions`.

## Side effects discovered

None.

## Verification

Windows 11 (this machine): the three new tests and the existing fs.watch,
fd and dgram tests; each program's output compared with Node 24. Linux
(Docker, `klain-ci`): the same tests.
