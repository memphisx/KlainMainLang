# ADR-00741: Windows shim header drift, verified against the CI runner's exact headers

- **Relations**: The definitive fix for the header-drift class first patched in [ADR-00734](ADR-00734.md) (`S_IF*` macros) and [ADR-00737](ADR-00737.md) (asm-symbol aliases); extends [ADR-00719](ADR-00719.md) (the Win32 platform layer)
- **Date**: 2026-09-07

## Context

The Windows CI lane had **never** produced a green build. Three commits tried to fix the shim/header drift (ADR-00734's `#undef S_IF*`, then ADR-00737's `__asm__` aliases for `stat`/`fstat`/`mkdir`/`getcwd`), and each still failed on the runner with ~1900 `conflicting types for 'stat'/'fstat'/'mkdir'/'getcwd'` errors → ~382 link failures, a 50-minute red lane.

The root cause of the *repeated* failures was a verification gap, not a code gap: **the dev box's mingw-w64 headers (`r92`) are older than the CI runner's (`r353`, pulled by MSYS2 `update: true`).** The r92 headers do not declare these functions where the r353 headers do, so every "compiles clean on my box" was meaningless — the box could not see the conflict the runner hit. Both prior fixes were shipped on that false signal.

## Investigation

Reproduced faithfully by downloading the runner's exact header package (`mingw-w64-ucrt-x86_64-headers-14.0.0.r353.g6df76fa52-2`) from the MSYS2 repo and compiling against it via a synthetic sysroot (`--sysroot` = r353 `include/` over local `lib/`). This surfaced the precise runner error: `#include <direct.h>` (r353) declares the CRT old-name aliases `int mkdir(const char*)` and `char *getcwd(char*,int)`, and `<sys/stat.h>` declares `int stat(const char*, struct stat*)` / `fstat` — all with signatures that differ from the shim's (`mkdir(const char*, int)`, `getcwd(char*, size_t)`, `stat(const char*, kml_stat*)`). `chdir`/`rmdir` did **not** conflict because the shim's signatures happen to match the old-name ones — which is why only four names failed.

Why win32fs.c pulls `direct.h`/`sys/stat.h` on the runner but not locally is a header-inclusion-chain difference between r92 and r353; the fix is made robust to it rather than dependent on knowing it.

## Decision

Two independent mechanisms, either of which alone closes the conflict, applied together:

1. **`#define NO_OLDNAMES 1`** at the top of `win32fs.c`, before any include. This suppresses the CRT old-name aliases (`mkdir`/`getcwd`/`chdir`/`rmdir`), exactly as `win32proc.c` already does — which is precisely why `win32proc.c` never hit this despite compiling on the same runner.
2. **`__asm__` symbol aliases** (ADR-00737): the four functions are defined under shim-local C identifiers (`kml_win_stat` …) bound to the exported symbol, so no header declaration of the real name can conflict — this is what covers `stat`/`fstat`, which are not old-name-gated.

## Verification

Against the runner's exact r353 headers (not the box's r92): the minimal case reproduces the runner error; `NO_OLDNAMES` alone and the asm-alias alone each drive it to zero; and **all four shim `.c` files (`win32shim`, `win32io`, `win32fs`, `win32proc`) compile with exit 0, zero conflicts, zero errors.** The normal local build + fs suite (r92 headers) still passes, so `NO_OLDNAMES` is link-safe.

The reproduction recipe is the durable outcome: **verify Windows shim/header changes against the runner's pinned header package via a synthetic `--sysroot`, never against the dev box's headers.** A green local compile on the older headers is not evidence.
