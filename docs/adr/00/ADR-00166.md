# ADR-00166: Status-doc accuracy audit and the Strict Coverage metric

- **Relations**: Found while implementing [ADR-00164](ADR-00164.md); prompted a full audit of `docs/status/`
- **Date**: 2026-08-11

## Context

[ADR-00164](ADR-00164.md) found that "Optional parameters (`param?`)" was marked ✅ in `docs/status/LANGUAGE-CONSTRUCTS.md` despite being completely non-functional — `Param.Optional` was parsed but never read by codegen at all, so every omitted-argument call hit a hard "missing argument" error. This was flagged directly: a ✅ row is a claim that the feature was actually verified, and this one plainly hadn't been. The concern raised was that other ✅ rows across `docs/status/` could be the same kind of unverified claim, making the coverage percentages meaningless as a trust signal.

## Investigation

Every populated `docs/status/*.md` page (26 files; 4 unstarted pages with zero ✅ rows were skipped) was independently audited: for every row currently marked ✅, an actual `.ts` repro was written and compiled/run against `klainmain` — not a read of the code or the AST — covering the row's core documented behavior plus the single most obvious edge case (an omitted optional argument, an empty collection, a boundary index, NaN/Infinity input, a missing key). A row already carrying caveat/limitation text (in its own cell or the page's Known Limitations section) got a lighter spot-check, since it was already honestly disclosed as imperfect regardless of the audit's outcome. The work was parallelized across 8 batches (roughly grouped by page size) to make repro-verifying ~360 individual ✅ claims tractable in one pass.

The audit found **33 real, previously-undisclosed false or overclaiming ✅ rows** across 15 pages, beyond the two already fixed in ADR-00164/[ADR-00165](ADR-00165.md). Severity ranged from hard compile crashes and silent memory corruption down to cosmetic display truncation:

**Crashes / memory-unsafety** (7): `.pop()`/`.shift()` on an empty array read uninitialized memory and corrupt `.length` to `-1`; `.charCodeAt()`/`.codePointAt()` out-of-range read uninitialized memory; `Math.floor/ceil/round/trunc/min/max/sign` produce non-deterministic garbage on `NaN`/`±Infinity` via undefined-behavior `fptosi`; `await response.text()/.json()/.arrayBuffer()` hard-crashes the compile and frees a live string buffer (use-after-free) via a Promise-detection gap in `emitAwait`; a string enum assigned to a typed variable produces invalid LLVM IR; `JSON.parse()` into a `float64`/`float32`-typed variable produces invalid LLVM IR.

**Wrong behavior on common, undisclosed patterns** (~15): `&&`/`||` don't short-circuit (both operands always evaluate, contradicting the row's own "Short-circuit evaluation" claim); `finally` doesn't run when `try`/`catch` returns (contradicting the row's own "`finally` always runs" claim); `**` doesn't exist at the lexer level at all; `NaN`'s `!=`/`!==` comparisons are wrong (`fcmp one` instead of `une`); `.push`/`.pop`/`.shift`/`.unshift`/`.splice` all reject a non-bare-variable receiver (`this.field.push(x)`); `.push(...items)`/`.unshift(...items)` reject more than one argument despite that being the row's own documented signature; `Map<string,number>.get()` on a missing key silently returns `0`; `Number.isInteger(Infinity)` returns `true`; `parseInt`/`parseFloat` (and their `Number.*` forms) never return `NaN`; a default parameter can't reference an earlier parameter; a rest-only arrow parameter list fails to parse; `a.length = n` truncation is unsupported; `.sort()`'s no-comparator default is numeric, not real JS's lexicographic default; `new RegExp` doesn't validate its flags string; a top-level function can't reference a sibling top-level `let`/`var`/`const`.

**Minor / doc-drift** (~11): `console.warn` has an undocumented `"Warning: "` prefix; `console.trace` prints no call stack; `NaN`/`Infinity`'s global-shadowing note was stale after `-globals=strict` became the default; JSDoc float precision truncates to 6 significant digits on print; `.at()` (string) returns `""` instead of `undefined` out-of-range; and others documented inline on their respective pages.

Full per-row detail (including the exact repro and root-cause file/line for every finding) is preserved in the audit's own working notes; the summary above and each page's own updated Notes cell are the durable record.

## Decision

Two changes, applied together:

1. **Every false or overclaiming ✅ row found got a real caveat added, same-commit** — either staying ✅ with an honest, specific caveat (the row works for its documented core case; the audit's finding is a real but narrower gap), or downgraded to ❌ where the core documented usage itself is broken (`**`, string enums assigned to a typed variable). No row was silently left as a bare, unqualified ✅ after being found broken.

2. **`docs/status/` now tracks two numbers per page: Coverage and Strict Coverage.** Coverage keeps its existing meaning (works for its core, documented case; caveats disclosed, however severe). Strict Coverage counts only a row with **zero** known caveats or bugs, of any severity, independently repro-verified — not read from the code. A caveat of any severity excludes a row from Strict even though it may legitimately stay ✅ in the loose Coverage column. This gives two honest signals instead of one overloaded one: Coverage answers "does this exist and basically work," Strict answers "is there nothing at all documented wrong with it." Every page's own header now states both; `docs/status/README.md`'s three summary tables carry a `Strict` column showing each linked page's overall Strict figure (page-level, not split by the README's own finer-grained categories, since several categories share one page).

This is now a standing rule (added to this project's own dev-guidance file): ✅ requires an actual repro run, never a read of the code or the AST.

## Implementation notes

Files touched: all 26 populated `docs/status/*.md` pages (new/updated caveat text on the 33 found rows, plus a `**Strict Coverage**` header line on every page) and `docs/status/README.md` (new `Strict` column on all three summary tables, `Reserved ambient-global names`'s row backfilled with a `—` placeholder to keep column count consistent). This project's own dev-guidance file's Standing rules section gained two lines: the ✅-requires-a-repro rule above, and a standing requirement to run `make conformance` (Test262) at the end of every feature/fix delivery regardless of expected movement, since most of the corpus is out of this project's scope and a flat result is normal, not a reason to skip the run.

No code was changed by this ADR itself — every finding above is a **documentation correction**, not a fix. The underlying bugs are real, described precisely enough (repro + root-cause file/line, where found) to fix later, but fixing 33 bugs of this range — from one-line guards to a fundamental short-circuit-evaluation codegen change — in one uncontrolled pass was judged riskier than the problem this ADR actually solves (an untrustworthy status doc). They're deferred, not dropped: this ADR's own presence, plus each page's own updated caveat text, is the tracking mechanism until they're picked up individually.

## Side effects discovered

None beyond the 33 findings themselves — this ADR's own purpose was to surface exactly this class of thing.

## Verification

- Every finding above was independently confirmed via a real `.ts` file compiled and run through `klainmain` — not inferred from reading `codegen/llvm/*.go`. Where a root-cause file/line is cited on a status page, it was located via `grep`/direct reading after the behavioral repro already confirmed the bug, not the other way around.
- `go build`, `go vet ./...`, full `go test ./...`, `make examples` — all pass (this ADR made no code changes, so this simply confirms nothing was accidentally broken by the documentation edits' surrounding session work).
- `make conformance` (Test262) re-run: 4463/53578, unchanged — expected, since this ADR changed no code.
