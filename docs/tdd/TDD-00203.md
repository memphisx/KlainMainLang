# TDD-00203: URL / URLSearchParams WHATWG-conformance overhaul

- **Status**: In Progress

## Context

The WPT `url/` conformance track (TDD-00082, ADR-00871) measured the URL surface
against the standards oracle for the first time and it scored **0** runnable
files: essentially every `url/` test depends on behavior the current
implementation cannot express. Two shortcuts in the original build are the cause,
both taken to reuse machinery that already existed rather than model the surface
faithfully:

1. **`URLSearchParams` is a `Map<string,string>`** (`IsURLSearchParams` flag on a
   Map type). A Map keeps one value per key and groups by key, so it structurally
   cannot represent the WHATWG model: cross-key **insertion order** and
   **duplicate keys**. `?a=1&b=2&a=3` must round-trip verbatim and
   `getAll("a")` must be `["1","3"]`; a Map collapses the first `a` and reorders.
   `.append()` and `.sort()` don't exist at all (compile errors), and `.getAll()`
   returns at most one element.
2. **`URL` is a libcurl passthrough.** `curl_url` parses and every field is read
   back verbatim, so no WHATWG normalization happens: default ports aren't
   stripped (`:80` on http stays), the host case isn't lowercased, and a
   non-special scheme (`foo:bar`) is rejected because libcurl only accepts known
   schemes. The WHATWG static methods `URL.parse`/`URL.canParse` are absent, and
   `JSON.stringify(url)` dumps the field struct instead of honoring
   `URL.prototype.toJSON()` (which returns `href`).

The surface is small and self-contained, so it is worth doing properly now rather
than accreting more per-caveat patches. This TDD records the design and — as
importantly — draws an honest line around the few caveats that are **not** fixable
without a dependency this project doesn't yet have, so they are understood as real
blockers rather than more shortcuts.

## Design

### URLSearchParams → ordered pair-list (the core fix)

Replace the Map backing with a dedicated C runtime structure, an ordered array of
`{ char *key; char *val; }` pairs (`urlsearchparamssrc/urlsearchparams.c`), the
exact WHATWG "list of name-value tuples" model. `URLSearchParamsType()` becomes a
distinct runtime-object type (keeps the `IsURLSearchParams` flag for dispatch, but
is no longer a `MapType`). The C API:

- `__kml_usp_create()` → handle; `__kml_usp_append(h,k,v)`, `__kml_usp_set(h,k,v)`
  (replace first, drop rest), `__kml_usp_get(h,k)` (first or NULL),
  `__kml_usp_get_all(h,k)` (a `{ptr,i64}` string array), `__kml_usp_has(h,k)`,
  `__kml_usp_delete(h,k)` (all matching), `__kml_usp_size(h)`, `__kml_usp_sort(h)`
  (stable, by UTF-16 code-unit key order per spec), `__kml_usp_to_string(h)`
  (percent-encode each pair, `&`-join, `=`-separate), and iteration accessors for
  `keys()`/`values()`/`entries()`/`forEach()`.
- Constructor forms: from a query string (parse, preserving order + duplicates,
  percent-decode), from an array of `[k,v]` pairs, and from an object literal.

All `URLSearchParams` method dispatch in `emit_call.go` routes to these C calls
instead of the Map methods. `URL`'s `.searchParams` is built from the query the
same way. Order-preserving parse replaces the `__kml_http_parse_query` Map fill.

### URL normalization + statics + toJSON

- In `deriveURLFieldsIntoObject`, after libcurl parses: lowercase the scheme and
  host, and strip the port when it equals the scheme's default (http/ws 80,
  https/wss 443, ftp 21). `href`/`origin` re-derive from the normalized parts.
- `URL.canParse(input[, base])` — attempt the parse, return a boolean, never
  throw. `URL.parse(input[, base])` — return a `URL` or `null` (no throw).
  Dispatched as static methods on the `URL` global.
- `JSON.stringify(url)`: the `IsURL` object marker already exists — the JSON
  emitter special-cases it to serialize `href` (its `toJSON`), like Date.

### Legacy `url.*` leniency

`url.parse`/`url.resolve` currently throw on a relative/scheme-less input where
Node is lenient (never throws, returns a best-effort object). Make them
non-throwing where the input is merely relative. `url.format` options, the Windows
paths of `fileURLToPath`/`pathToFileURL`, and `urlToHttpOptions` accepting a legacy
`Url` are smaller follow-on gaps addressed as reachable.

## Genuinely blocked (dependencies, not shortcuts)

These caveats are **not** fixable in this overhaul; each names the real dependency:

- **Non-special-scheme URLs** (`new URL('foo:bar')` valid with `pathname` `'bar'`).
  libcurl's URL API only accepts known/special schemes, so faithful non-special
  parsing requires abandoning libcurl for a hand-written WHATWG parser — a separate,
  much larger piece than this overhaul. The normalization above shrinks the "not a
  WHATWG parser" caveat to this one residual.
- **`URLPattern.exec()` per-component `URLPatternResult`.** Returning the spec's
  nested per-component result object (rather than the merged group Map) needs the
  runtime dynamic object model — [TDD-00068](TDD-00068.md) / [TDD-00155](TDD-00155.md).
- **IDN of non-ASCII domains on the Mac build.** `domainToASCII`/`domainToUnicode`
  need the libcurl build to include libidn2; it's present on typical Linux and
  absent on the Mac build. A platform/build dependency, not a code gap.

## Open questions

- Is `URL.searchParams` live (mutations reflect back into `url.search`)? WHATWG
  says yes; the current field is a snapshot. Decide at implementation — a live link
  needs the URL object to hold the usp handle and re-serialize `search` on mutation.
