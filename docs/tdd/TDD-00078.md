# TDD-00078: Intersection types (`A & B`)

- **Status**: Implemented (see ADR-00225)
- **Date**: 2026-08-19

## Context

Intersection types (`A & B & ...`) are one of the two remaining `❌` rows in the
Type System status page's *Type system features* table (the other being
mapped/conditional types). They are common in idiomatic TS: composing object
shapes (`Props & { children: Node }`), mixin-style assembly, and extending a
config object with extra fields.

They fit this compiler's object model unusually well. Object types are already
fixed-shape structs (`ObjectType` → `Field[]` → `StructIR`); TypeScript's `A & B`
on object types is defined as "a type carrying the members of both," which is
*just another struct* with the union of all fields. So an object intersection
needs **no new runtime representation** — it reduces at type-resolution time to an
ordinary object `Type`. That makes intersection both low-risk and a good next
step, and it builds the exact field-merge core that the currently-*discarded*
`interface X extends Base` clause (parser_types.go:305–308) will later need.

Intersection is, notably, *simpler* than the union types already shipped
([TDD-00043](TDD-00043.md)). A union value is *one of* several shapes chosen at
runtime, so it needed a runtime-tagged box (`IsDynamic`, a member set checked at
each boundary). An intersection value satisfies *all* members simultaneously —
for structs that is a single fixed struct fully known at compile time, with no
runtime tag at all.

## Design

### Core reduction

For object-type members, `A & B` resolves to `ObjectType(merge(A.Fields, B.Fields))`.
No new `Type` kind, no runtime tag, no new codegen struct machinery — the merged
result flows through the same `FieldIndex`/`StructIR`/coercion paths every object
type already uses. Intersection is a compile-time transform that yields a plain
struct.

### Where the merge happens — the key decision

**Option A — Parse-time flattening.** The `&`-loop in the parser merges member
`Fields` directly into one synthesized object `TypeAnnotation`.
*Fatal flaw:* the parser has no interface registry. `A & B` where the members are
*named* interfaces cannot be merged at parse time — their fields aren't known
until `registerInterfaces` runs during codegen (emitter.go:984). Only inline
`{...} & {...}` could ever be flattened this early. Rejected.

**Option B — New AST carrier, merged in `resolveType` (recommended).** Add
`TypeAnnotation.IntersectionMembers []*TypeAnnotation`, mirroring the existing
`UnionMembers` field (nodes.go:1512). The parser only *collects* members; the
merge happens in `resolveType` (emitter.go:626), where named interfaces resolve
through `e.interfaces` and inline objects through the existing `Fields → ObjectType`
branch (emitter.go:702). This threads the same seam union already established and
touches one new branch in the central annotation→`Type` converter.

**Option C — A distinct lazy `IsIntersection` `Type` kept through codegen,**
collapsed at each use site. Overkill: nothing downstream benefits from keeping it
un-merged, and it would duplicate object-type handling everywhere. Rejected.

**Recommended: Option B.**

### Parser precedence

TypeScript binds `&` tighter than `|`: `A & B | C & D` ≡ `(A & B) | (C & D)`.
Insert one new level between the existing union loop and the atom parser:

- `parseTypeAnnotation` (union level) — loops on `|`, each side from →
- `parseTypeAnnotationIntersection` (**new**, intersection level) — loops on `&`,
  each side from →
- `parseTypeAnnotationAtom` (atom level, unchanged).

Reuse the union loop's cycle-avoidance trick (parser_types.go:65–79): when there
are 2+ members, return a *copy* of the head with `IntersectionMembers` set, while
every entry in the list — including the head's original — keeps its own
`IntersectionMembers` nil. The union implementation learned the hard way that
setting the slice on the head-in-place makes it its own first element and sends
member resolution into infinite recursion.

### Merge semantics (new `resolveType` branch)

1. Resolve each member to a `Type`.
2. Require every member be an object type (`IsObject`). Otherwise → a clean,
   specific compile error (see rejections).
3. Concatenate fields in member order. On a duplicate field name:
   - identical resolved field `Type` → dedupe (keep one).
   - differing types → **governed by `-compat`** ([TDD-00075](TDD-00075.md)),
     matching how the axis treats a likely-bug-vs-TS-fidelity split elsewhere:
     - `-compat=strict` (default) → compile error, e.g.
       `field 'x' has conflicting types in intersection (number vs string)`.
       The opinionated, safer-than-JS reading: a conflicting field is almost
       always a mistake, and a `never` field nothing can write is a footgun.
     - `-compat=js` → the TS-faithful `never` field: the field exists in the
       merged shape but is unassignable and unreadable. See Open questions for
       how a `never`-typed *field* lays out in a fixed-shape struct — new
       territory, since `never` has so far only appeared as a `(): never`
       return, never as a struct member.
4. Result: `ObjectType(merged)`. Structurally a plain object type — downstream
   coercion, `FieldIndex`, and `StructIR` need zero changes.

### Assignment / literal construction

Because the result is an ordinary `ObjectType`, an object literal targeting an
`A & B` annotation flows through the *existing* `emitObjectLiteralWithHint`
(emit_objects.go:96) unchanged: it builds field-by-field against the merged
layout, rejects unknown fields, and coerces each. Requiring *all* merged fields
to be present is exactly what an intersection should enforce — see Open questions
for whether the current object-literal builder already errors on a missing field.

### Nullable interaction

`(A & B) | null` composes for free: the union loop wraps the resolved intersection
result with `Nullable`, like any other member. `A & null` is degenerate (`never`
in TS) → reject.

### Interaction with `interface extends`

The parser currently *discards* an `extends Base` clause (parser_types.go:305–308).
The field-merge helper built here is precisely what single- and multi-`extends`
need. This is the natural immediate follow-on (its own ADR, sharing the merge
helper), kept out of V1 because `extends` also carries nominal-identity and
`implements`-conformance concerns beyond field merging.

### Resolver gap to fix in passing

`rewriteType` (rename.go:692) descends into `Fields`/`ElemType`/`KeyType`/
`TypeArgs`/`FuncParams`/`FuncRetType` but **not** into `UnionMembers` or
`TupleElems` — so a named type used only inside a union or tuple is never
rename-rewritten across a module boundary (a latent bug independent of this work).
Adding `IntersectionMembers` requires adding its descent here; fix the
union/tuple omission in the same pass, each with a regression test.

### Scope (V1)

In scope — `A & B & ...` where every member resolves to an object type (named
interface, inline `{...}`, or a `type` alias of either), in every position object
types already work: variable annotation, function param/return/default,
interface/object field, array element `(A & B)[]`, and `type X = A & B`.

Clean rejections (each a specific compile error, never a silent pick):
- a non-object member — `number & string`, `A & string`, `A & (() => void)`,
  `A & T[]`, `A & [number, string]`, `A & (X | Y)` (all `never` or non-struct in
  TS; V1 does not represent them);
- conflicting field types across members — but only under `-compat=strict`
  (default); `-compat=js` keeps the field as `never` instead (see Merge
  semantics);
- a generic-with-type-args member (`Box<number> & A`) — defer, monomorphization
  interaction;
- an `any`/`unknown` member — degenerate.

## Open questions

- **Missing-field policy** — *resolved during implementation*: the object-literal
  builder already accepts a partial literal for a plain `interface` (a field
  declared on the type but omitted from the literal compiles today), so an
  intersection inherits that same leniency rather than being made stricter than
  the object types it merges. Tightening it is a separate, cross-cutting
  object-type decision, not intersection's to make; recorded as a shared caveat.
- **`never`-typed field layout (`-compat=js` path)**: resolved that conflict
  handling is `-compat`-governed (strict = error, js = `never` field), but a
  `never` struct *member* is new. Options: give it a zero-width/placeholder slot
  and reject any read/write of that specific field as a `never` access; or a full
  bottom-type representation. The strict path (the default, and simpler) can ship
  first without answering this — the js path is a clean second stage.
- **Field-type equality for dedupe**: exact IR match is trivially safe. Whether to
  also treat two structurally-identical object field types as equal can wait —
  start strict, loosen only if a real case needs it.
- **Origin marker**: keep the result a pure `ObjectType` (recommended) or carry an
  `IsIntersection` flag purely for better diagnostics. Add the flag only if error
  messages demand it.
