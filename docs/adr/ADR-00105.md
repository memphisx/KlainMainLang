# ADR-00105: Array-of-arrays (nested array) storage representation

- **Relations**: Implements [TDD-00029](../tdd/TDD-00029.md)
- **Date**: 2026-08-06

## Context

[TDD-00029](../tdd/TDD-00029.md) split this off from TDD-00028/[ADR-00104](ADR-00104.md) once direct testing showed a nested array literal (`[[1,2],[3,4]]`) hit a real, separate storage-representation gap rather than being a free side effect of making array literals general expressions: an array's backing buffer is a flat sequence of fixed-width, scalar/pointer-sized slots, but a nested array element's own value is a `{ptr,i64}` *pair* (16 bytes) that doesn't fit in one such slot. TDD-00028 left a deliberate compile-time rejection in place (`emitArrayLiteralAggregate`'s nested-array guard) rather than the confusing clang-stage type-mismatch error direct testing found underneath it.

## Investigation

TDD-00029 identified two real options and left the choice open, pending a call-site audit:

- **(a) Widen outer slots when the element type is itself an array** — no extra indirection, but a real layout change: `Type.Align()`/every GEP call site that assumes `elemTy.IR`-width slots would need to branch on "is this element itself an array."
- **(b) Box nested-array elements behind one more pointer indirection** — every outer slot stays a plain, uniform `ptr` (consistent with every other pointer-shaped element type already, e.g. `string[]`), at the cost of one `malloc(16)` + one extra load per nested-array element access.

Confirmed directly (`codegen/llvm/types.go`'s `ArrayOf`) that `Type.IR` for *any* array type is already `"ptr"` and `Type.Align()` already reports 8 for `"ptr"` — meaning an array-typed `elemTy`'s backing-buffer slot is *already* uniformly ptr-width today, with nothing to widen. Option (b) requires no `Type`/`Align()`/GEP changes anywhere; only the value stored in (and read from) that slot needs to change shape. Option (a) would have needed conditional slot widths threaded through every `elemTy.Align()`-sized GEP call site in `emit_arrays_*.go`. This made (b) the clear choice, not a close call — it reuses the existing slot layout unchanged.

Audited every array-consuming call site across `emit_arrays_core.go`, `emit_arrays_mutate.go`, `emit_arrays_transform.go`, `emit_arrays_search.go`, `emit_arrays_sort.go`, `emit_arrays_iter.go`, `emit_arrays_hof.go`, `emit_exprs_member.go` (indexing), `emit_exprs_assign.go` (index assignment), `emit_stmts.go` (`for...of`), `emit_call_json.go` (`JSON.stringify`), and `emit_objects.go` (`Object.groupBy`). Found they split cleanly into two groups:

- **Single-element read/write sites** (indexing, destructuring, literal/spread population, `for...of`'s loop variable, `push`/`pop`/`shift`/`unshift`/`splice`'s inserted-or-removed element, `.at()`/`.with()`/`.fill()`, `Array.of`, `JSON.stringify`'s per-element/per-field encoding): all route a single element through one GEP'd slot pointer via a raw `load`/`store` of `elemTy.IR`. These only needed the raw load/store swapped for a new pair of helpers that transparently box/unbox — correct for nested arrays with no per-call-site special-casing beyond that swap.
- **Bulk copy/move sites** (`concat`, `reverse`, `slice`, `splice`'s tail shift, `toSpliced`, `copyWithin`, `values`, `Array.from`'s array branch): move `elemTy.Align()`-sized opaque words via `memcpy`/`memmove` without interpreting them. A boxed nested-array element's slot value is just a `ptr` (the box pointer) like any other pointer-shaped element — these needed no changes at all, and copying the box pointer by value gives the same shallow-copy-shares-the-inner-array reference semantics real JS's own `Array.prototype.slice()` etc. already have for object/array elements.
- **Callback-invoking or scalar-register-comparing sites** (`map`/`filter`/`forEach`/`reduce`/`find`/`findIndex`/`findLast`/`findLastIndex`/`some`/`every`, `sort`'s comparator, `indexOf`/`includes` (via `emitElemEq`), `join` (via `emitValueToString`), `Object.groupBy`): found a real, independent, pre-existing gap while auditing these — `emitCBCall` (`emit_func.go`) passes a closure argument as a single `params[i].IR`-typed operand, never decomposing an array-typed argument into the `(ptr, i64)` pair a named top-level function call's own ABI already uses (`emitCallToFuncSig`, `emit_call.go`). Closures have never supported an array-typed parameter at all, for any array element type, not just nested ones — orthogonal to this ADR's own storage-representation question and out of scope to fix here. These call sites reject a nested-array element with a clear compile-time error instead of silently miscompiling.

## Decision

**Boxing (option b).** A nested-array element's slot in its outer array's backing buffer holds a `ptr` to a separately `malloc`'d 16-byte `{ptr,i64}` box, rather than the aggregate inline. New shared helpers in `codegen/llvm/emit_arrays_core.go`:

- `boxArrayValue(val Value) string` — mallocs 16 bytes, stores `val`'s `{ptr,i64}` aggregate into it, returns the box pointer.
- `unboxArrayValue(boxPtr string, elemTy Type) Value` — loads the `{ptr,i64}` aggregate back out of a box pointer.
- `loadArrayElem(gepReg string, elemTy Type) Value` — loads a slot's value, transparently unboxing when `elemTy.IsArray`; identical to the old raw `load` otherwise.
- `storeArrayElem(gepReg string, elemTy Type, val Value)` — stores a value into a slot, transparently boxing when `elemTy.IsArray`; identical to the old raw `store` otherwise.
- `rejectNestedArrayElem(elemTy Type, opName string, pos ast.Pos) error` — the clean compile-time rejection used by every callback-invoking/scalar-comparing site identified above.

Every single-element read/write call site now goes through `loadArrayElem`/`storeArrayElem` instead of a raw `load`/`store elemTy.IR`; every bulk-copy site is unchanged (already correct); every callback-invoking/scalar-comparing site calls `rejectNestedArrayElem` immediately after resolving `elemTy`.

`.fill(val)` boxes `val` once, before its fill loop, and stores that one box pointer into every filled slot — matching real JS's own reference-sharing `.fill()` semantics for a reference-typed value (`[{}].fill(obj)` shares one `obj` across every slot, not a fresh clone per slot); boxing fresh inside the loop would have given every slot an equal-by-value but not reference-equal copy instead.

`new Array<T>(n)` (dynamic size, `calloc`-zeroed) rejects an array-typed `T` outright (`emitNewArraySizedAggregate`): a zero-initialized slot's box pointer would be null, and reading an unwritten element before it's ever assigned would dereference that null box. Real code combining a dynamic-size uninitialized array with a nested-array element type is a narrow enough combination that a clear rejection (with an array literal as the suggested alternative, which never has an unwritten-slot state) was preferred over adding a null-box branch to every read path for it.

Array destructuring (`emitArrayDestructuring`) and `for...of`'s loop variable (`emitForOf`) both needed a further, related fix beyond boxing itself: a destructured/loop-bound array-typed element needs the two-alloca "Named Symbol" representation (`Symbol{Ptr, LenPtr}` — see `CLAUDE.md`'s Array value duality note), not the single scalar alloca every other element type uses, so `.length`/indexing/etc. work on it afterward. Both now branch on `elemTy.IsArray` to allocate the right shape.

## Implementation notes

Files touched:
- `codegen/llvm/emit_arrays_core.go`: new `boxArrayValue`/`unboxArrayValue`/`loadArrayElem`/`storeArrayElem`/`rejectNestedArrayElem`; `emitArrayLiteralAggregate`'s nested-array rejection removed (its element-population loop already routes through `storeArrayElem`, via `emitArrayLiteralData`/`emitSpreadArrayLitData`); `emitNewArraySizedAggregate` gained its own, narrower nested-array rejection (see Decision); `emitArrayDestructuring` gained the two-alloca branch for an array-typed destructured element.
- `codegen/llvm/emit_exprs_member.go`: `emitIndex`'s array-read path now calls `loadArrayElem`.
- `codegen/llvm/emit_exprs_assign.go`: `arr[i] = val`'s store now calls `storeArrayElem`.
- `codegen/llvm/emit_stmts.go`: `emitForOf`'s loop variable gained the two-alloca branch (mirrors destructuring); its per-iteration element read now calls `loadArrayElem`.
- `codegen/llvm/emit_arrays_mutate.go`: `pop`/`shift`'s returned element now via `loadArrayElem`; `push`/`unshift`/`splice`/`toSpliced`'s inserted element(s) now via `storeArrayElem`.
- `codegen/llvm/emit_arrays_transform.go`: `.at()`'s result slot widened to `StructFieldIR(elemTy)` (matches `emitOptionalMember`'s existing array-typed-zero-value convention) and its read now via `loadArrayElem`; `.with()`'s write now via `storeArrayElem`; `.fill()` boxes its fill value once before the loop (see Decision).
- `codegen/llvm/emit_arrays_iter.go`: `.entries()`'s per-element read now via `loadArrayElem`, and its store into the entry object's `value` field now uses `StructFieldIR(elemTy)` instead of `elemTy.IR` (an object struct field's array-typed slot is always the inline `{ptr,i64}` aggregate convention, ADR-00061 — unrelated to this ADR's backing-buffer boxing, but the same fix shape); `Array.of`'s per-argument store now via `storeArrayElem`.
- `codegen/llvm/emit_arrays_hof.go`, `emit_arrays_search.go`: `rejectNestedArrayElem` added to `map`/`forEach`/`filter`/`reduce`/`find`/`findIndex`/`findLast`/`findLastIndex`/`some`/`every`/`indexOf`/`includes`.
- `codegen/llvm/emit_arrays_sort.go`: `rejectNestedArrayElem` added to `emitQsortCall` (covers both `.sort()` and `.toSorted()`) and `emitArrayJoin`.
- `codegen/llvm/emit_objects.go`: `rejectNestedArrayElem` added to `Object.groupBy`.
- `codegen/llvm/emit_call_json.go`: `emitJSONStringifyArray` split into a thin wrapper plus a new `emitJSONStringifyArrayData`/`emitJSONStringifyArrayValue` pair so `emitJSONStringifyValue` can recurse into a nested-array element (an already-evaluated `{ptr,i64}` Value, not an unevaluated expression) the same way it already recurses into a nested object; its per-element read now via `loadArrayElem`.

## Side effects discovered

Found and fixed one real, pre-existing, unrelated bug while wiring `JSON.stringify`'s nested-array recursion: `emitJSONStringifyObject` (`emit_call_json.go`) read every field's value via `load field.Ty.IR, ...` — for an array-typed field (e.g. `{ tags: string[] }`), an object struct's array-typed field slot is a 16-byte `{ptr,i64}` aggregate (`StructFieldIR`, ADR-00061), not `field.Ty.IR`'s plain 8-byte `"ptr"`. Before this fix, `JSON.stringify` on any object with an array-typed field silently read only the field's data pointer (dropping its length) and mishandled it from there — nested arrays just turned this into a hard `extractvalue` type-mismatch instead of a silent wrong answer, which is what surfaced it. Fixed by loading via `StructFieldIR(field.Ty)` instead, the same convention the write side (`emit_objects.go`'s `storeField`) already used correctly.

Confirmed (Investigation above) that closures/arrow-function callbacks don't support an array-typed parameter at all today, for any element type — not a nested-arrays-specific gap. Left unfixed and untracked as its own TDD/ADR for now; `rejectNestedArrayElem`'s error message points at this ADR/TDD-00029 rather than a separate tracking doc, since it's the same underlying limitation surfacing at every one of this ADR's rejection sites.
