# ADR-00160: Destructuring assignment (`[a, b] = expr`, `({ a, b } = expr)`)

- **Relations**: Extends [ADR-00153](ADR-00153.md), [ADR-00157](ADR-00157.md), [ADR-00158](ADR-00158.md)

## Context

Next candidate confirmed while scoping ADR-00159: `let a, b; [a, b] = [1, 2];` failed with `codegen error: can only assign to identifiers or array elements` — a genuinely different feature from destructuring *declaration* (`let [a, b] = ...`, already supported since before this session, extended with defaults in ADR-00158). Assignment targets already-declared bindings rather than introducing new ones, and reaches codegen through the general assignment-expression path (`emitAssign`), not the declaration path (`emitVarDecl`).

## Investigation

Confirmed the LHS already parses correctly with no grammar changes needed: `[a, b]` and `{x, y}` are ordinary array/object literal expressions, and an assignment expression's grammar doesn't distinguish "valid assignment target" from "any expression" at parse time in this compiler (matching real JS — that distinction is enforced at a later, semantic stage everywhere). `emitAssign`'s existing dispatch chain (`codegen/llvm/emit_exprs_assign.go`) already fell through cleanly to a "can only assign to identifiers or array elements" error for any `ex.Left` shape it didn't recognize — exactly the kind of clean rejection this project's philosophy favors, confirming the gap was real but well-contained: two new dispatch branches, not a parser change.

Checked whether the new branches would need their own resolver/closure-capture plumbing, the recurring gotcha this session (ADR-00156, ADR-00158, ADR-00159 each found a real bug from a new AST field the rename pass or free-variable scanner didn't know about). This one didn't: `ex.Left` being an `*ast.ArrayLiteral`/`*ast.ObjectLiteral` reuses AST node types the rename pass and `scanExprFV` already fully traverse generically (an ordinary array-literal *value* `let x = [a, b]` already needed to recursively rewrite/scan `a`/`b` as expressions inside `Elements`/`Properties`) — no new field, so no new blind spot. Verified directly anyway rather than trusting the reasoning alone: both a top-level (mangled-name) case and a closure-capture case work correctly with no further changes.

## Decision

Two new branches in `emitAssign`, inserted before the existing scalar-variable fallback. Both scoped deliberately narrower than the declaration form (ADR-00157/ADR-00158): every target must be a plain, already-declared, non-const, non-array identifier — no nested patterns (`[arr[0], x] = ...`), no rest, no per-element default, no compound assignment operators (`[a,b] += ...`). Real JS allows nested lvalues and defaults in assignment position too; not attempted here; each unsupported combination is a clean, specific compile-time rejection rather than silently mishandled.

**Array form** (`[a, b] = expr`): reuses `resolveArrayDataPtr` (already built for declaration-form destructuring, ADR-00157/ADR-00158) to resolve the RHS, then the identical bounds-check-and-zero-fill shape `unpackArrayPatternInto` already uses — a position past the source's length reads as zero, same reasoning. The array literal parser itself has no hole syntax (`p.parseAssignment()` per element, no empty-slot case), so `[, b] = arr` is already a clean parse-time rejection, nothing to special-case.

**Object form** (`{ x, y } = expr` / `{ x: renamed } = expr`): needs parens at statement level, matching real JS (`{` at statement-start already parses as a block). Reuses `resolveObjectPtr`. Both the shorthand and renamed forms fall out of the *same* code with no branching — an object literal's `Value` for a shorthand property `{ x }` is already parsed as `Identifier{"x"}` (the same name), so treating `prop.Value` as the assignment-target expression (instead of a value-producing one, as a normal object literal reads it) handles shorthand and renaming identically, the same "same AST, different interpretation" reuse the array form gets from `ArrayLiteral`.

Both forms reject a computed key / spread element in the pattern (matching the declaration form's own lack of support for either) and return `Value{Ty: TypeVoid}` — the whole assignment *expression's* own value (real JS: the RHS) isn't computed, since neither branch builds one; only the overwhelmingly common statement-position usage (`[a,b] = [1,2];`, discarding the result) is supported for V1.

## Verification

- `go build`, `go vet ./...`, full `go test ./...`, `make examples` (all 109) — all pass.
- 14 new E2E tests across `tests/arrays_test.go` (basic assignment, the swap idiom, assignment from a variable, out-of-bounds zero-fill, top-level mangled-name correctness, closure capture, and three negative cases — const target, nested target, compound operator) and `tests/objects_test.go` (shorthand, renamed, closure capture, and two negative cases — const target, unknown field).
- `examples/basics/destructuring.ts` extended with a dedicated section; built and ran directly, output matches the file's own inline comments exactly (used distinct variable names from the start — `a`/`b` were already in use earlier in the same file for the swap-via-temporary-array example, a mistake caught during this session's ADR-00158 work and avoided here from the start).
- Full Test262 corpus re-run: 4,462 → 4,462, no aggregate movement — expected, same reasoning as ADR-00158/ADR-00159: `[a,b] = [1,2]` was a hard codegen error before this change, so no previously-*passing* file could regress from it.
