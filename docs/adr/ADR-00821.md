# ADR-00821: Backpressure and mid-read errors for the pooled read stream

- **Relations**: `Implements TDD-00186`, `Extends ADR-00775, ADR-00820`
- **Date**: 2026-09-10

## Context

TDD-00186 Part A moved `fs.createReadStream` onto the thread pool but left it a
**push** model: the worker raced to EOF, posting every chunk regardless of
consumer demand (OQ1, backpressure, deferred) and treating a mid-read `fread`
failure as a clean EOF (OQ2). For a file-serving microservice the first means a
large file's chunks all queue in memory ahead of a slow client — the eager
memory profile the pool was meant to remove; the second silently truncates on
an I/O error instead of surfacing it.

## Investigation

- The WHATWG readable already has the full backpressure machinery — `pull`
  hook (field 9), `hwm` (7), queue total (6), `__kml_rs_desired`,
  `__kml_rs_pull_if_needed` — fired by `__kml_rs_started` at start
  (`runtime_streams.go:520`) and by `__kml_rs_read` after each consumer read
  (`:735`/`:740`). The pooled stream simply didn't use it: `__kml_rs_alloc`'s
  `%ff` argument lands in field 17 (the pending-read fulfiller), leaving the
  pull slot (field 9) **null**.
- `runtime_http_reqbody.go` is the working precedent for a native pull hook over
  a C context (`__kml_reqbody_pull`, `emit_http.go:1345`) and for building an
  error object off an errno inline (the `{i64 kind, ptr msg, ptr name}` shape,
  `runtime_http_reqbody.go:164`).
- The `__kml_ns_flow_onread` pump drives `__kml_rs_read` (`runtime_node_stream.go:203`),
  so a Node Readable consumer (`for await`, `.on('data')`) does fire `pull`.

## Decision

Convert the pooled read stream to **demand-driven, one chunk per credit**:

- A C control block (`kml_stream_ctl`: `mutex`, `cond`, `credits`, `inflight`,
  `stop`, `rs`, `fp`, `hwm`) is allocated on the loop thread before submit and is
  the env of the readable's pull/cancel closures (fields 9/10).
- The worker blocks on the condvar until `credits > 0`, reads exactly one `hwm`
  chunk, and posts a `STREAM_CHUNK` — or `STREAM_END` at clean EOF, or a new
  `STREAM_ERROR` (with errno) on `ferror`/OOM.
- The pull hook (`__kml_pool_stream_pull`, loop thread) grants one credit unless
  a read is already `inflight`, and returns NULL (a synchronous pull). The
  `STREAM_CHUNK` drain clears `inflight` and calls `__kml_rs_pull_if_needed`,
  which grants the next credit only while the consumer is under its high-water
  mark — so at most ~one chunk is outstanding.
- `STREAM_ERROR` builds the fs error object on the loop thread (the reqbody
  shape) and calls `__kml_rs_error`, so a consumer's `for await` / `'error'` sees
  it. The message is not yet errno-specific.
- A cancel hook (`__kml_pool_stream_cancel`, field 10) sets `stop` and wakes the
  worker, which ends the stream — so `reader.cancel()` releases the worker.

**Keepalive by in-flight reads, not existing streams.** The pool's `inflight`
count (which pins the loop alive) now bumps on each *credit grant* and drops on
each completion, instead of once at submit. A demand-starved stream therefore
sits at 0, so abandoning a `for await` early (a `break`, which does not fire the
WHATWG cancel) lets the loop exit instead of hanging on a worker that will never
be granted another credit. This was a real regression the push model didn't have
(it always read to EOF); the demand model requires this accounting.

## Implementation notes

- `klainpool.c`: `kml_stream_ctl` + `free_stream_ctl`; `run_read_stream` rewritten
  to the credit loop; `enqueue_work` gains a `bump` flag (one-shot ops bump at
  submit, a stream does not); the `STREAM_CHUNK` drain decrements inflight and
  re-arms the pull; `ctl_new`/`pull`/`cancel` entries.
- `threadpool.go`: `__kml_pool_stream_error` (errno → error object → `rs_error`),
  the `ctl_new`/`pull`/`cancel`/1-arg-`submit_readstream` declarations.
- `emit_fs_stream.go`: allocate the ctl, install the pull/cancel closures via
  `storeStreamField` 9/10, arm `__kml_rs_started`, submit the ctl.

## Side effects discovered

Early `for await` abandonment on a *push*-model pooled stream happened to work
only because the worker read to EOF regardless; making the stream demand-driven
exposed the keepalive assumption, fixed here. A `break` still does not trigger
the WHATWG cancel hook (only `reader.cancel()` does) — harmless now (the loop
exits), but wiring Node stream destroy/return to cancel is a follow-on.

## Verification

- New E2E tests (`tests/fs_stream_test.go`): demand-driven early-`break` exits
  cleanly (no hang), and a mid-read error surfaces to the consumer. Existing
  createReadStream tests (multi-chunk, for-await, on-data, ordered-non-blocking)
  still pass. Example `examples/fs/read_stream_backpressure.ts`.
- Manual: 1 MiB / 16-chunk round-trip intact in default and `-mm=gc` mode; early
  break exits 0.
- `go build`, `go vet`, the fs/stream/pipe E2E suites pass.
