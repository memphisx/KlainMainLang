# ADR-01113: Generics in the checker: type parameters, inference and contextual typing

- **Relations**: `Implements TDD-00230` (Phase 2, P2.6, first increment); `Extends ADR-01111`, `ADR-01112`
- **Date**: 2026-09-24

## Context

[TDD-00230](../tdd/TDD-00230.md) P2.6 gives the checker signatures, generics
and `any`. The checker of [ADR-01111](ADR-01111.md) left every generic
function, class, interface and alias unanswered. It also left every
unannotated callback parameter unanswered, since it had no contextual
typing. Meanwhile, codegen gives an unannotated callback parameter its
`i64` default (`Inferred`) wherever it has no annotation to go by.

## Investigation

- **typescript-go** (`internal/checker/inference.go`, `checker.go`).
  - Inference collects candidates per type parameter by walking a
    parameter type against an argument type.
  - Context-sensitive arguments (function expressions with unannotated
    parameters) are skipped in a first pass. They are typed in a second
    pass from the parameter type instantiated with what the first pass
    inferred.
  - A candidate's literal type is widened unless the type parameter has a
    primitive constraint or occurs at the top level of the return type
    (`getCovariantInference`).
  - A type parameter with no candidate infers `unknown`.
- **tsc 5.6.3 `--strict`** confirms every expectation in the new tests:
  - `id(1)` is `1`, but `wrap(1)` is `number[]`;
  - `first([1, 2])` is `number | undefined`;
  - `pair(1, 'x')` is `[number, string]`;
  - `apply(2, n => n * 2)` is `number`, and `apply([1], xs => …)` types
    `xs` as `number[]`;
  - with `apply<T>(v: T, f: (x: T) => T): T`, `apply(2, x => …)` gives
    `x: number` (the callback sees the first pass's inference widened) and
    the call `number`;
  - `orElse(u, 5)` infers from a `T | undefined` parameter;
  - `len<S extends string>('abc')` keeps the literal;
  - `new Stack(1)` is `Stack<number>`, and `Box<Pair<number, string>>`
    reads `[number, string]`;
  - a callback passed where `(a?: number) => number` is expected has
    `a: number | undefined`.
- tsc prints a generic alias by name (`Pair<string, boolean>`), where the
  checker prints its expansion (`[string, boolean]`). These are the same
  type.

## Decision

- **The binder declares a function's type parameters** in the function's
  scope (a `TypeParameter` symbol of kind `TypeOnly`). Two with the same
  name are a redeclaration. `Binding.ScopeOf` returns a function-like
  node's scope, and a signature's annotations resolve in it (TypeScript
  resolves parameter annotations in the function's scope too).
- **Type parameters are types** (`TypeParam`, with its `extends`
  constraint). A generic function type lists its type parameters.
  `instantiate` substitutes through unions, arrays, tuples, function types
  and object types.
- **A generic call** uses explicit type arguments when written. Otherwise
  it infers them:
  - each argument's type is walked against its parameter's (type
    parameter, union with fixed members, array, tuple, function parameters
    and result, object properties);
  - the context-sensitive arguments come last;
  - candidates are joined, and widened unless the parameter keeps literals
    (the rule above);
  - no candidate infers `unknown`.
  An argument the checker cannot type poisons the type parameters that
  occur in its parameter: they, and the call, stay unanswered rather than
  guessed.
- **Contextual typing:** an unannotated parameter of a function expression
  or arrow takes the matching parameter type of what it is passed to or
  assigned to: a call's parameter (a generic callee instantiated from its
  other arguments, literals widened unless the constraint is primitive), a
  `new`'s constructor parameter, or an annotated variable's function type.
  The checker finds the context through a parent table built on first use,
  so the answer does not depend on the order in which codegen asks.
- **An optional parameter's type includes `undefined`** in a signature and
  in a function type annotation, as under `--strict`.
- **Generic interfaces, aliases and classes** are instantiated per argument
  list.
  - An interface's or class's instance is nominal, keyed by the symbol and
    the arguments, so a self-reference (`next: Node<T>`) resolves to the
    instance being built.
  - An alias is memoised per argument list.
  - Their type parameter names resolve through an environment the checker
    pushes while typing the declaration. A function's own type parameters,
    declared by the binder, take precedence.
  - `new C(args)` infers a generic class's arguments from its
    constructor's parameters, through the same inference as calls.
  - In a generic class, a method without a return annotation and a field
    typed only by its initializer stay unanswered: their expression types
    would depend on the arguments, and expression types are cached per
    node.
- **Not in this increment:**
  - generic arrows (the parser has none, BACKLOG §0 item 1b);
  - overloads, and `*Signature` keeping its declaration;
  - a generic base class (`extends Base<T>`);
  - the call-site scope for explicit type arguments (they resolve from the
    module scope);
  - `-compat=js` as a checker mode;
  - the options struct.

## Side effects discovered

- **Codegen types an unannotated callback parameter `i64`** (`Inferred`)
  where a contextual type exists. Examples:
  - `run((a) => (a ?? 0) + 1)` in
    `examples/basics/optional_params_functype.ts`;
  - `apply(2, (x) => x * 3)` and `apply("q", (x) => x + "!")` in
    `examples/generics/generic_promise.ts`;
  - `(x) => { … }` assigned to an annotated function type in
    `examples/closures/fall_off_the_end.ts`.

  The shadow report records five such answers, where the checker gives the
  contextual `number` or `string`. In the sixth, `a` is
  `number | undefined`, which has no representation mapping yet.
