# ADR-00796: Gate the fs thread pool off on Windows (the documented inline fallback was never wired)

- **Relations**: Extends ADR-00773, ADR-00775; Implements TDD-00185, TDD-00186
- **Date**: 2026-09-08

## Context

A documentation audit of `docs/BACKLOG.md` and `docs/status/README.md`
cross-checked the shipped-state claims against the code. ADR-00773 and the
File System status data both state that the TDD-00185 blocking-work thread
pool is POSIX-only and that "Windows keeps the inline path" — but the code
had no such gate.

## Investigation

- `emitFsAsyncPromise` (`codegen/llvm/emit_fs_async.go`) routed every
  `fs.promises` op through `emitFsPromisePooled` unconditionally; the only
  decline was binary-data `writeFile`/`appendFile`.
- `emitFsCreateReadStream` (`codegen/llvm/emit_fs_stream.go`) had dropped the
  eager fill entirely in ADR-00775 — `ensureFsReadStream` (the pre-pool
  read-to-EOF helper) had become dead code with no caller.
- `threadpoolsrc/klainpool.c` includes `<sys/socket.h>`/`<sys/select.h>` and
  uses pthread condvars + a `socketpair` wakeup with no Win32 lane. Although
  the Win32 shim provides a `socketpair` (win32proc.c), the pool source has
  never been compiled or run on Windows.

Net effect: on Windows, any `fs.promises` op or `fs.createReadStream` would
emit pool IR and pull `klainpool.c` into the link — an untested-at-best,
broken-at-worst path that contradicts the documented behaviour.

## Decision

Make the code match the documented design: the pool is POSIX-only until the
Windows reactor work (TDD-00182/TDD-00183) subsumes it.

- `emitFsPromisePooled` returns `pooled=false` when `runtime.GOOS ==
  "windows"` (host == target; no cross-compilation), so `fs.promises` falls
  through to the existing inline settled-Promise path.
- `emitFsCreateReadStream` takes a Windows branch that restores the
  pre-TDD-00186 eager path verbatim (`__kml_fs_read_stream` fill +
  `__kml_rs_close`), re-animating the dead `ensureFsReadStream` helper.

## Implementation notes

- `codegen/llvm/emit_fs_async.go` — the pooled-dispatch gate.
- `codegen/llvm/emit_fs_stream.go` — the eager Windows branch, copied from
  the pre-ADR-00775 shape of the function.
- No change on POSIX: the pooled paths are byte-identical there.

## Side effects discovered

The same audit found the status index (`docs/status/data/_index.json`)
carrying stale category-level caveats (fetch body Promises, fs pooling,
`process.memoryUsage`) that the detail pages had already corrected —
fixed in the same pass.

## Verification

- `go build`, `go vet ./codegen/...` clean (macOS M4).
- `go test ./tests/ -run 'FsAsync|FsStream|ReadStream|WriteStream|Promises'`
  passes on macOS (the POSIX path, unchanged).
- The Windows branch is compile-verified only from this machine; runtime
  behaviour there needs the next Windows-box session.
