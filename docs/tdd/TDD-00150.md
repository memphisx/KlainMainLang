# TDD-00150: TUI framework roadmap — native `klain:tui`, then FFI-unlocked opentui/GUI, then Vue/React compat layers

- **Status**: Partially Implemented — Stage 1 shipped ([ADR-00519](../adr/ADR-00519.md)): native `klain:tui` (vendored Yoga flexbox + double-buffered ANSI diff painter + the `Box`/`Text`/`List`/`Spinner`/`Progress`/`TextInput` component kit + `render`/`enter`/`leave`). Stages 2–5 (general C FFI, `opentui`, `vue-termui`, `ink`) not started.
- **Date**: 2026-08-30

## Context

[TDD-00031](TDD-00031.md) shipped the raw terminal primitives ([ADR-00518](../adr/ADR-00518.md)): raw mode, live terminal size, `SIGWINCH`, synchronous key reads, on top of the already-present `isTTY`, ANSI output, `process.stdout.write`, and `EventEmitter`. Enough for a hand-rolled prompt or menu, not enough for **layout** — flexing boxes, columns, wrapped text, scroll regions, redraw-on-resize component trees. That layer is what every serious Node TUI (`ink`, `blessed`, `opentui`, `vue-termui`) provides, and TDD-00031 deliberately deferred it.

This TDD is not a pick-one survey — the goal is to **eventually support all of the viable options**, staged so each stage ships standalone value and the ordering follows achievability × value under this project's fixed authoring-model priority:

> **native vanilla TypeScript > Vue > anything else** (`x > y` = x ranks higher).

So a first-party native layer comes first and React-oriented `ink` comes last, with Vue in between. The pivot in the middle is **general C FFI**, whose design is already named (as a placeholder) in [TDD-00032](TDD-00032.md): it is the single foundation that unlocks `opentui`'s native backend, the GUI-toolkit crossover (GTK/Qt/SDL2/raylib/imgui) TDD-00032 was really about, and a long tail of other C libraries — so it is elevated by leverage (the standing "enablers that unblock clusters rank up" rule), not left at its low face value.

The compilation constraints that shape all of this are unchanged from TDD-00031/TDD-00032: whole-program AOT with no runtime `require()`/reconciler-host ([ADR-00022](../adr/ADR-00022.md)), no JS engine at runtime (no V8, no `Proxy`, no `eval`), a fixed-shape object model, and — today — no user-facing FFI or closure→C-function-pointer trampoline at all (TDD-00032's core gap).

## Design

### Two independent axes

The libraries differ along two axes that are easy to conflate:

1. **The render/layout substrate** — what actually computes a box tree and paints cells: Yoga (flexbox) + a diff painter (ink), a bespoke widget engine (blessed), or a *native* renderer reached over FFI (opentui).
2. **The authoring model** — how a developer describes the UI: an FP `state → view` function (Elm-like), Vue reactivity (`ref`/`reactive`), or React components + hooks.

The key realization: **we can own the substrate once (axis 1) and then hang multiple authoring models on top of it (axis 2).** `klain:tui` builds our own substrate natively; `vue-termui`-compat and `ink`-compat then become *alternative front-ends over the same painter/layout*, not full re-implementations. `opentui` is the exception — its value is a *different* (native) substrate, which is why it, alone among the four, depends on the FFI stage.

### Staged roadmap

Each stage is independently shippable and ordered by (ease × value) within the priority hierarchy. Effort is relative; "unlocks" is the leverage that justifies the ordering.

---

#### Stage 1 — Native `klain:tui` core  ·  priority: **native (highest)**  ·  effort: **medium**  ·  prereqs: **none beyond TDD-00031**

Our own substrate + the vanilla-TS authoring model, sitting directly on the shipped primitives. Three parts:

- **Layout**: vendor **Yoga** (Facebook's self-contained C/C++ flexbox engine) as an `EmbeddedCSources` member — the exact mechanism bigint/crypto/tls/dtoa and the webview `.cc` binding already use, so no new architecture and, crucially, **no FFI** (Yoga is a clean data-in/data-out C ABI). This harvests the one genuinely hard external asset without writing a layout engine from scratch.
- **Rendering**: a double-buffered ANSI painter — component tree → Yoga layout → diff against the previous frame's cell grid → emit the minimal cursor-move + write sequence (plain ANSI + `process.stdout.write`, already present). Repaint driven by `SIGWINCH` and input.
- **Authoring**: an Elm/`ratatui`-style `state → view(state): Element` + `update(state, event)` loop (fits the project's FP lean; no reconciler, no `Proxy`, no fibers — none of the runtimes we lack), plus a component starter kit (Box, Text, List, Spinner, Progress, text input).

**Unlocks**: a real, dependency-free, portable-by-default TUI framework shipped as `klain:tui` — *and* the reusable painter+layout substrate that Stages 4 and 5 build their compat front-ends on. This is the load-bearing stage; the standing "don't defer the hard part" rule means it must close through the app loop (Stages 1's parts 2–3), not stop at a static Yoga binding.

---

#### Stage 2 — General C FFI foundation  ·  priority: **enabler (leverage-elevated)**  ·  effort: **high**  ·  prereqs: none, but is the hard core of [TDD-00032](TDD-00032.md)

The pivot. Give user code a way to declare and call an arbitrary external C function, hand a KlainMainLang closure to C as a raw C-callable function pointer, and describe a foreign struct's layout — the three gaps TDD-00032 names. Likely shaped as a JSDoc/`extern`-style typed declaration lowered to a direct C-ABI call (the compiler already lays out C-ABI structs correctly internally for every `runtime_*.go` decl; this exposes that machinery), with the **closure→C-function-pointer trampoline** as the single hardest new piece of codegen (every callback-driven C API — GUI event loops, GLib signals, opentui's render callbacks — needs it).

**Unlocks (the reason it's elevated despite being the highest-effort stage):**
- **`opentui`** — bind its native renderer backend directly instead of hand-porting (Stage 3).
- **The GUI crossover TDD-00032 was really about** — GTK (plain-C API; optionally the generic `libffi` + GObject-Introspection `.gir` route `node-gtk` uses, which binds arbitrary GLib libraries with *no per-function code*), SDL2, raylib, dear imgui (via `cimgui`'s C API), and — behind a hand-written C shim for its C++ ABI — Qt/QML. This is where "GUI bindings to GTK/Qt" actually come from.
- **`ncurses`** as an alternative TUI backend, and a long tail of C libraries (DB clients like `libpq`/`sqlite3`/`hiredis`, compression, etc.).

Because Stage 2's leverage reaches well beyond TUI, it may be worth splitting into its own top-level "general C FFI" TDD when picked up (as TDD-00032 anticipated), with this roadmap consuming it. It is placed after Stage 1 (which needs nothing) but ahead of Stages 3–5 because all three either require it (Stage 3) or are lower-priority authoring models (4, 5).

---

#### Stage 3 — `opentui` support via FFI  ·  priority: **other (but cheap post-Stage 2)**  ·  effort: **low–medium given Stage 2**  ·  prereqs: **Stage 2**

`opentui`'s value is a native (Zig/GPU-adjacent) rendering backend plus a TS API layer. Pre-FFI this was a dead end (binding the native backend needed an FFI we don't expose, and the TS layer assumes a live runtime). Post-Stage 2, the native backend binds like any other C library, and the thin API/state layer is hand-reimplemented over it — the same "reimplement the API shape, bind the native core" split the project uses everywhere. Low marginal cost once FFI exists, so worth doing even though it's "anything else" tier — it brings an existing toolkit and exercises the FFI+callback path end-to-end.

**Unlocks**: proof-of-life for the whole FFI-bound-native-UI pattern that the GUI branch (GTK/Qt) then reuses.

---

#### Stage 4 — `vue-termui` compat front-end  ·  priority: **Vue (middle)**  ·  effort: **high**  ·  prereqs: **Stage 1**

A Vue-flavored authoring model over Stage 1's painter+layout. The obstacle is Vue 3 reactivity, which is `Proxy`-based (property-access interception) and we have no `Proxy`. Two routes, both real work: (a) a **compile-time reactivity lowering** — because we are a compiler, not a runtime, `ref`/`reactive`/`computed` access can be statically rewritten into explicit dependency-tracking subscriptions, sidestepping `Proxy` entirely (the more on-brand route); or (b) a minimal runtime `Proxy` subsystem (a large, general addition). Targets the same `Element`/painter substrate from Stage 1, so only the reactivity + component-syntax layer is new. Vue-tier priority puts it ahead of React.

**Unlocks**: Vue developers; and a reusable reactivity mechanism (route a) that would have value beyond the terminal.

---

#### Stage 5 — `ink`/React reconciler front-end  ·  priority: **React (lowest)**  ·  effort: **very high**  ·  prereqs: **Stage 1**

React-for-the-terminal as an authoring model over Stage 1's substrate. `ink`'s core *is* a React reconciler — a runtime scheduler over a live heap of fibers — and its Yoga layout dependency is **already satisfied for free** by Stage 1. What remains is implementing enough of the reconciler (tree diffing + the core hooks: `useState`/`useEffect`/`useReducer`) to run `ink` component trees. This is the hardest authoring model and the lowest priority (React-oriented), so it is deliberately last; partial support (function components + the common hooks, no concurrent-mode/suspense) is the realistic ceiling and is fine at this tier.

**Unlocks**: the large existing `ink` ecosystem, to whatever depth the reconciler subset reaches.

### Why nothing is rejected outright

The earlier framing of this TDD rejected opentui/ink/vue-termui as incompatible. That was true *only pre-FFI and only for a full runtime port*. Reframed as (a) own-the-substrate-once + (b) hang-front-ends-on-it, plus (c) FFI for external native substrates, every option has a home — the question is purely ordering, which the stages above settle by value and effort under the priority rule.

## Open questions

- **Yoga's C++ vs C surface.** Yoga is C++ with a C ABI (`yoga/Yoga.h`); the webview `.cc` embedded-source path already establishes a C++ TU is not new ground — confirm the C ABI header alone avoids dragging in a full C++ toolchain build.
- **Immediate-mode re-render vs. retained tree** (Stage 1). Re-rendering the whole `Element` tree each frame and relying on the cell-diff keeps output minimal but recomputes layout every frame; whether to add a retained/memoized node tree (closer to ink) is a perf question to settle against a real workload, per the "faithful now, perf-flag later" rule.
- **Should Stage 2 (general C FFI) be its own TDD?** Its leverage reaches far beyond TUI (GUI, ncurses, DB clients), exactly as TDD-00032 predicted. Likely yes — a dedicated "general C FFI" design TDD that this roadmap and a future GUI-toolkit TDD both consume, rather than scoping FFI inside a TUI document.
- **Vue reactivity route** (Stage 4): compile-time lowering of `ref`/`reactive` (on-brand, no `Proxy`) vs. a general runtime `Proxy` subsystem (broader but heavier). A genuine fork for the implementing stage.
- **How much of `ink`/React to implement** (Stage 5): function components + `useState`/`useEffect`/`useReducer` is the realistic subset; concurrent mode / suspense / class components are out. Confirm that subset runs real-world `ink` apps before committing.
- **GUI toolkit choice off the Stage 2 branch.** Plain-C toolkits (GTK, SDL2, raylib, `cimgui`) sidestep the C++ ABI problem and are the pragmatic first GUI targets; Qt/QML (richest declarative model, hardest ABI) needs a C shim first. This is TDD-00032's own open question, now with a concrete enabler stage to hang it on.
