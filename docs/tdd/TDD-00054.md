# TDD-00054: klmpm — a klainmain-native package manager

- **Status**: Partially Implemented (Stages 1-2, see [ADR-00146](../adr/ADR-00146.md)/[ADR-00147](../adr/ADR-00147.md))
- **Date**: 2026-08-10

## Context

[TDD-00053](TDD-00053.md) (npm/`node_modules` interop) is fundamentally bottlenecked by npm's distribution convention: packages ship compiled JS + a signature-only `.d.ts`, neither of which this compiler can use, since it compiles TypeScript *source* directly to native code with no JS runtime fallback. A package manager built **for** this compiler doesn't have that problem by construction — a klmpm package is a git repository containing real `.ts` source, because that's the only thing that could ever have been published to it in the first place. This TDD designs that system: both the compiler-side resolution (small, mechanical, buildable independent of anything else) and klmpm itself (real new infrastructure — a manifest/lockfile format, a fetch/versioning model, and the CLI tool).

Deliberately staged so the compiler-side piece can land on its own, well ahead of klmpm actually existing — a hand-created `klain_modules/<name>/` directory with a `klain.json` and some `.ts` files exercises the exact same resolution path a real klmpm-fetched package would, with nothing about the resolver caring how that directory came to exist.

## Design

### Architectural starting point: this compiler already does the hard part for free

Because `resolver.ResolveProgram` does whole-program source compilation with no linker and no separate compilation units ([ADR-00022](../adr/ADR-00022.md)), a klmpm package needs **no binary distribution story at all** — no ABI, no static/dynamic linking format, no "compiled for which target" question. A package is just more `.ts` files that get fetched into a local directory and then resolved exactly like today's relative imports already work (per-file mangling from [TDD-00041](TDD-00041.md), re-exports from [TDD-00051](TDD-00051.md), and dependency-ordered top-level execution from [TDD-00052](TDD-00052.md) all apply to a fetched package's files with zero package-awareness needed past the initial specifier lookup). This is the single biggest reason to prioritize klmpm over deeper npm interop investment — the amount of *new* mechanism required is genuinely small.

### Manifest: `klain.json`, one schema for both a project and a package

A klmpm project *is* a package (no `dependencies`/`devDependencies` split, no separate "workspace root" concept in V1) — the same schema describes your own project's manifest and any dependency's own manifest, recursively:

```json
{
  "name": "left-pad",
  "version": "1.2.0",
  "main": "src/index.ts",
  "dependencies": {
    "some-other-pkg": { "source": "github:someuser/some-other-pkg", "version": "v0.4.0" }
  }
}
```

- `"main"` points at real `.ts` source, unambiguously — unlike npm's `main`/`module`/`types` split, there's only ever one artifact a klmpm package can contain, so there's no entry-point ambiguity for the compiler to guess around (contrast [TDD-00053](TDD-00053.md)'s fallback-probe hack, needed there only because npm's convention gives no clean signal).
- `"dependencies"` maps a **name** — the identifier every `import` statement actually uses — to a `{source, version}` pair. **The name is never a URL.** This is the one deliberate fix relative to Go modules' model: Go's import path *is* the VCS location, so moving a repository breaks every call site across every consumer that ever imported it. Here, only the manifest's one `source` line needs to change; every `import { x } from 'some-other-pkg'` across every consumer's source stays untouched.
- No `"scripts"` field, anywhere, ever — not sandboxed, not opt-in, structurally absent from the schema. Since every klmpm package is source compiled by the same pipeline as everything else, there is no legitimate reason (no native-addon build step, no bundler step) to run arbitrary code at fetch time the way npm historically needed to. This closes npm's single worst security property for free, as a consequence of the architecture, not a policy klmpm has to keep enforcing.
- `"source"` addressing: `"github:user/repo"` shorthand, or a full git URL for non-GitHub hosts (GitLab, sourcehut, self-hosted) — not restricted to one forge, unlike Go's more rigid VCS-detection-from-import-path scheme.
- Monorepo/subpath support (a single repo containing multiple klmpm packages, each with its own nested `klain.json`) is explicitly deferred — a reserved but unimplemented `"path"` field in the source spec is the likely V2 shape, mirroring Go's nested-module approach, not designed further here.

### Versioning: semver tags, Minimal-Version-Selection-style resolution — not a SAT solver

A version constraint is a single "at least this version" floor (a semver tag, e.g. `"v1.2.0"`), never a range operator (`^`/`~`/etc.). Resolving the whole dependency graph (project + every transitively-reachable package's own `dependencies`) picks, for each package name, the **maximum** floor requested anywhere in the graph — deterministic, no backtracking, no constraint-satisfaction search. This is Go modules' MVS algorithm, deliberately chosen over Cargo/npm-style range-based solving: it's dramatically simpler to implement and reason about, and this project's own demonstrated taste throughout its ADRs consistently favors a smaller, predictable mechanism over a more powerful but heavier one. A direct, load-bearing consequence: **exactly one version of any given package ever exists in one build** — no nested/duplicate-version resolution the way `node_modules` sometimes needs, which is also what keeps the compiler-side resolution flat and simple (next section).

### Lockfile: `klain.lock` — klmpm's bookkeeping, never read by the compiler

Records, per resolved package, the exact fetched git commit and a content hash, for reproducibility and integrity verification on a later fetch:

```json
{
  "packages": {
    "left-pad": { "source": "github:someuser/left-pad", "version": "v1.2.0", "commit": "<sha>", "integrity": "sha256:<hash>" }
  }
}
```

Purely klmpm's own concern — the compiler never parses `klain.lock` (or, for that matter, the project-root `klain.json`'s `dependencies` section either — see the next section for exactly what the compiler *does* need).

### Fetch mechanism: shell out to `git`, no protocol client of our own

`git clone --depth 1 --branch <tag-or-commit>` (or an equivalent shallow fetch at the pinned ref) into the local store — git is already installed on essentially every dev machine, and reimplementing any part of the git wire protocol would be pure waste for zero benefit over just using it. This compiler already has exactly the capability klmpm's CLI needs to do this: `process.execFileSync(file, args?)` ([ADR-00025](../adr/ADR-00025.md)) — a synchronous, shell-free subprocess call, already shipped, already sufficient (a package manager's fetch step has no need for async/streaming subprocess I/O).

### Storage: a global content-addressed store, pnpm-style

`~/.klmpm/store/<name>@<resolved-ref>/` holds one real, fetched copy of a given package+version, shared across every project on the machine that needs it — a project's own `klain_modules/<name>` is a reference into that store (a symlink on Linux/Mac; Windows symlink support is a known open question, deferred consistent with [TDD-00020](TDD-00020.md) — Windows support generally — being unstarted anyway, not a new gap this TDD introduces). Crucially, **the compiler-side resolver never needs to know or care** whether `klain_modules/<name>` is a symlink or a real directory — `os.Stat`-style filesystem resolution already follows symlinks transparently, so this is entirely an implementation detail of klmpm's storage layer, invisible past the resolver's existing path-resolution code.

### Compiler-side resolution (Stage 1 — buildable today, independent of klmpm existing)

This is the part directly actionable without klmpm itself: given a bare specifier that isn't a known built-in module and isn't a relative path (today's existing rejection point, `resolver.go`'s `resolveImportPath`):

1. **Locate the project's `klain_modules/` directory once**, by walking upward from the *entry file's* directory (not each importing file's own directory — deliberately different from Node's per-importer-relative walk) until a `klain_modules/` directory is found or the filesystem root is reached. Anchoring at the entry file rather than each importer is what makes the "exactly one version of any package" property from MVS resolution actually hold at the resolution layer too: every file in the whole program, whether part of the entry tree or itself inside a fetched package, resolves a bare specifier against the *same* single `klain_modules/`, never a nested one.
2. **The compiler does not read the project-root `klain.json` at all.** It only needs `klain_modules/<name>/klain.json`'s `"main"` field, once that directory is confirmed to exist — the project's own dependency list is klmpm's bookkeeping for what to *fetch*, not something the resolver needs to cross-reference to know what already exists on disk.
3. No `klain_modules/<name>/` found → the same "bare/package-style imports are not supported" rejection this compiler already gives today — fully backward compatible, zero cost for a project that never uses klmpm (the upward walk only ever happens for a specifier that would otherwise be a hard rejection anyway).
4. Precedence, unchanged and explicit: a built-in module (`fs`/`path`/etc.) is always checked, and always wins, before any `klain_modules` lookup — a klmpm package can never shadow a real built-in name, same reasoning [TDD-00053](TDD-00053.md) applies for npm interop.
5. Past step 2, the resolved `main` file is just another file to the existing DFS (`visit`) — no new merge/mangling/codegen logic anywhere.

Because this step doesn't need `klain.lock`, doesn't need a project-root manifest, and doesn't need klmpm's fetch/store logic to exist at all, it can be implemented and tested purely by hand-constructing a `klain_modules/<name>/klain.json` + source tree — exactly the workflow that motivated staging this TDD this way.

### klmpm the tool (Stage 4 — the actual new binary/subcommand)

A CLI with a small surface: `klmpm init`, `klmpm add <name> <source> [version]`, `klmpm install` (resolve the full graph via MVS, fetch anything missing from the store, populate/refresh `klain_modules`, write `klain.lock`), `klmpm remove <name>`. Proposed to be written in klainmain-compilable TypeScript itself (the user's own stated preference) — a real, concrete forcing function/dogfooding exercise for the compiler's own `fs`/`process.argv`/`process.execFileSync` surface, not just a nice idea. Whether it ships as a standalone `klmpm` binary or a `klainmain pkg` subcommand of the main compiler binary is left open (see Open Questions) — doesn't affect any of the design above either way.

## Open questions

- Standalone `klmpm` binary vs. a subcommand of the main `klainmain` binary — undecided, doesn't affect the design above.
- Integrity anchor: trust git's own commit SHA as sufficient, or additionally compute and pin a SHA-256 over the fetched tree in `klain.lock` for defense-in-depth beyond git's hash — undecided, leaning toward adding the extra hash since it's cheap and git's SHA-1 has known theoretical weaknesses, but not load-bearing enough to block Stage 1/2 design.
- Whether a future "hybrid" mode letting a `klain.json` dependency point at an npm-style source ([TDD-00053](TDD-00053.md)) is worth ever unifying into one manifest format, as the user raised — leaning toward keeping them fully separate (different `dependencies` shapes, no shared schema) rather than one schema trying to serve two very different trust/format models; revisit only if a real concrete need shows up.
- Monorepo/subpath support's exact `"path"` field shape — deferred to V2, not designed here.
- Whether `klain_modules` should be gitignored-by-default tooling guidance (mirroring `node_modules`) or something klmpm itself scaffolds (a generated `.gitignore` entry on `klmpm init`) — small, but worth deciding before Stage 4.
