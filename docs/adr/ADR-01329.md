# ADR-01329: Builtin library modules compiled once and linked as objects

- **Relations**: Implements TDD-00238 (Stage 4), Extends ADR-01326
- **Date**: 2026-10-02

## Context

[TDD-00238](../tdd/TDD-00238.md) Stage 4 compiles each builtin library
module once and links its object. ADR-01326 made every library function
compile to the same IR in every program, and ADR-01327/ADR-01328 moved the
runtime the library calls into C. What remained was producing the module
objects, keying their cache and linking them.

## Investigation

- A program's IR already contains every function of each library module it
  imports, whatever it uses (two programs importing different `node:path`
  exports carry the same 102 library definitions), and library symbols are
  named by module (`<name>__kml_modL<n><key>`, `__kml_global_…`,
  `__kml_lib_<key>_init`).
- So no second emission mode is needed: the program is emitted as before
  and its IR is split by owner. Emission keeps setting the program's
  `used*` flags, so the program's C runtime set already covers every
  library body; no per-module runtime manifest is needed.
- Splitting the example corpus showed what makes a module's text depend on
  its program, each fixed by a rule:
  - linkage that depended on whether the program named a definition;
  - helpers the emitter generates about a library declaration only when
    the program uses it (class-reference thunks, function-value wrappers,
    record views), whose names still carry the module key;
  - definitions listed in emission order.
- And what breaks identity across units:
  - a private constant copied into two units has two addresses: a function
    value's header is such a constant, and a function's property bag is
    keyed by it (`assert.ok` vanished);
  - content-named strings were private: a property key can be compared by
    address.
- A call from one object into another cannot be inlined (the lesson of
  ADR-01328's `__kml_str_cmp`).

## Decision

1. **The split** (`codegen/llvm/libsplit.go`, `SplitLibUnits`): one unit
   per library module and one for the program.
   - A library module owns its source-level functions and methods, its
     module globals, its init and init guard. Every other `__`-prefixed
     name is the program's, even when it carries a module key.
   - A library definition is `hidden` in every program; a program
     definition reached from a module unit becomes `hidden`. Everything
     stays one instance in its owner's unit; other units declare it.
   - `linkonce_odr` and `weak_odr` definitions are copied into each unit
     that names them; the linker keeps one. The program's unit always
     carries every `weak_odr` one (a C object may name it).
   - A module's unit lists its declarations, copies and definitions sorted
     by name.
2. **Identity-bearing constants are one symbol.** Content-named strings
   (`@.s.<hash>`) are `linkonce_odr hidden` constants without
   `unnamed_addr`, like constructor names.
3. **Hot leaf helpers are `weak_odr`** (`__kml_nb_*`,
   `__kml_str_alloc`/`_len`/`_free`): each unit carries and inlines its own
   copy.
4. **The cache** (`LibObjects`): a module's object is keyed by a hash of
   its unit's text, the target OS, the compile flags and the host clang
   arguments. Any option that changes library code changes the text, so no
   option dimension is listed by hand. A miss compiles the unit into the
   user cache directory next to the C runtime objects.
5. **The link** adds the module objects and drops what the program does not
   reach (`-dead_strip`; `-ffunction-sections -fdata-sections` with
   `--gc-sections` elsewhere), except under `node:ffi`, which looks the
   executable's own symbols up.
6. **`-lib-objects`** is on by default; `-lib-objects=false` compiles the
   library with the program, as before.

## Implementation notes

- `tools/libsplit`: splits one program's IR into files.
  `tools/libsplit/check.sh` builds each given example with and without
  `-lib-objects`, runs both, compares the output and counts distinct texts
  per module unit; `tools/libsplit/timing.sh` times both builds with a warm
  cache.
- A library class's shape method adapters stay the program's: they are
  emitted only for the methods the program reaches dynamically.
- A module unit has two texts where the program decides its globals'
  storage: under workers they are `thread_local`. Each text is its own
  cache entry.

## Side effects discovered

- Fixed in passing: `ensureFnMeta` did not link `dynobj.c`, which
  `fnmeta.c` calls (16 tests failed to link).

## Verification

- macOS (Apple Silicon): splitter unit tests; `check.sh` over the assert,
  path, url, streams, events, JSON, strings and ffi examples: every split
  build matches its whole build, one text per module unit. With a warm
  cache `node_stream.ts` builds in 3.5 s instead of 5.7 s, and its binary
  is 1.32 MB instead of 1.59 MB.
- Linux (DeskMini, Node304): `make examples` 376/376 with
  `-lib-objects` (and without); `make test-par` green with it on by
  default.
- Linux (Node304, serial, warm object cache): compiling all 370 examples
  (`tools/libsplit/timing.sh`) takes 1,017.9 s with library objects
  against 1,673.0 s whole, 39% less.
