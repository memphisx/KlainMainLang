# ADR-00615: XMLHttpRequest.open() async argument (synchronous XHR)

- **Relations**: `Extends ADR-00490`, `Implements TDD-00040`
- **Date**: 2026-09-01

## Context

`XMLHttpRequest.open()` rejected any call with more than two arguments —

```go
if len(args) != 2 {
    return ..., fmt.Errorf("xhr.open() requires 2 arguments (method, url)")
}
```

so the real signature `open(method, url, async?, user?, password?)` was
unavailable, and in particular `xhr.open("GET", url, false)` failed to
compile. That third argument is the standard way to ask for a *synchronous*
request, and a synchronous HTTP client is exactly the primitive a
closed-loop load generator needs — the `examples/goroutines/load_test.ts`
demo had no real request to make and instead ran a synthetic CPU loop
dressed up as a load test.

## Investigation

`send()` (`emit_xhr.go`) already calls `__kml_fetch_async` immediately
followed by `__kml_await_fetch_settled` (`emit_xhr.go:214-220`): it blocks
the caller until the HTTP round-trip completes, then populates
`status`/`responseText`. From TS that *is* synchronous XHR. Crucially,
`__kml_await_fetch_settled` checks `@__kml_current_task` and takes the
`taskyield` path when running inside a `klain:sync` task
(`runtime_fetch.go:197-198`) rather than busy-spinning the OS thread — so N
worker goroutines each doing a blocking `send()` yield while their transfers
are in flight, and the requests genuinely overlap.

So the synchronous client already existed and already cooperated with the
goroutine scheduler; the only gap was `open()` refusing the `async` argument.

Verified with a repro (12 goroutines, each `open("GET", url, false)` +
`send()` against the httpbin-lite fixture): all 12 returned 200.

## Decision

Relax `open()` to accept 2–5 arguments. `method`/`url` are used as before;
args 3–5 (`async`, `user`, `password`) are evaluated for their side effects
and otherwise not consulted:

- `async === false` maps exactly onto the existing synchronous `send()` — a
  genuine blocking request, faithful and complete.
- `async === true` also blocks, because there is no main-thread event loop
  to dispatch a deferred `onload` off. This is a documented narrowing, not a
  fake async — recorded in `docs/status/NETWORKING.md`.
- `user`/`password` are evaluated but not yet wired to curl auth — a second
  documented narrowing.

## Implementation notes

Single-function change in `emitXHROpen` (`emit_xhr.go`): the arg-count guard
becomes `< 2 || > 5`, and a loop emits `args[2:]` so their side effects
occur. No runtime or type-layout change — `send()` is untouched.

## Side effects discovered

None. The `user`/`password` auth wiring and any real async-XHR dispatch
remain open narrowings, tracked in `docs/status/NETWORKING.md`.

## Verification

Mac (Apple Silicon M4). `go test ./tests/ -run TestE2EXHR` green, including
the new `TestE2EXHRSyncOpenThreeArgs` (3-arg synchronous form) and the
extended arg-count rejection case (6 args). Standalone goroutine repro:
12/12 synchronous requests returned 200. Rewrote
`examples/goroutines/load_test.ts` to a real in-process HTTP load test on
top of this.
