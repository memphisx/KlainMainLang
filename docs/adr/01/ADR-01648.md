# ADR-01648: Stack overflow is a RangeError off the main thread on POSIX

- **Relations**: Implements [TDD-00249](../../tdd/TDD-00249.md) (Stage 2); Extends [ADR-01583](ADR-01583.md), [ADR-01605](ADR-01605.md)
- **Date**: 2026-10-16

## Context

[ADR-01583](ADR-01583.md) turned an overflow of the main thread's stack or a
task fiber's into Node's RangeError on Linux and macOS.
[ADR-01605](ADR-01605.md) did it for every stack on Windows, with
`TestE2EStackOverflowEveryContextWindows` covering the main thread, a
generator, a task, an HTTP handler, a goroutine and a Worker. On the Apple
Silicon Mac that test's contexts, run one by one: generator and handler
threw the RangeError, a goroutine died with SIGILL, and a Worker hung.

## Investigation

The handler (`stackguardsrc/stackguard.c`) already recognises an overflow on
any stack: the fault lies next to the interrupted stack pointer. Two things
kept it from running:

- An alternate signal stack is per thread, and only the main thread had one.
  A fault on a Worker or a goroutine's machine thread had no stack to run
  the handler on.
- The Worker thread blocks every signal (`worker.c`), SIGSEGV included. A
  synchronous fault under a blocked SIGSEGV never reaches the handler.

Goroutine stacks (`klainsync.c`) had no guard page, so recursion ran into the
mapping below. Generator stacks (malloc'd in emitted IR) and the
`klain:http` connection fibers (`loop.c`) had none either. They threw on
macOS only because a large malloc sits next to unmapped memory there.

## Decision

- `__kml_stack_guard_thread()` on POSIX maps a 256 KB alternate stack for
  the calling thread once the handler is installed. A pthread key's
  destructor unmaps it when the thread ends. The Worker thread and each
  goroutine machine thread call it at start.
- The Worker thread leaves SIGSEGV and SIGBUS unblocked.
- Goroutine stacks get a PROT_NONE page below the range handed to
  `makecontext`, as task fibers have.
- In the default memory mode, generator stacks and `klain:http` connection
  fiber stacks come from `__kml_fiber_stack_alloc` (guarded). Under
  `-mm=gc` both stay collected heap blocks. The collector scans them while
  the fiber is parked, and a guard page inside a block would fault that scan.
- The every-context test runs on every platform.

## Implementation notes

`codegen/llvm/stackguardsrc/stackguard.c`, `codegen/llvm/workersrc/worker.c`,
`codegen/llvm/klainsyncsrc/klainsync.c`, `codegen/llvm/loopsrc/loop.c`,
`codegen/llvm/emit_generators.go`, `tests/stack_overflow_contexts_test.go`.
`klainsync.c` builds with `_XOPEN_SOURCE 700`, which hides `getpagesize`, so
it uses `sysconf(_SC_PAGESIZE)`.

## Side effects discovered

Neither generator stacks nor `klain:http` connection stacks are ever freed.
The connection fibers go when `klain:http` moves to libuv.

## Verification

`TestE2EStackOverflowEveryContext` passes on the Apple Silicon Mac and on
Linux x86-64 (DeskMini).
