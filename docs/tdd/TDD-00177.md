# TDD-00177: Windows support — toolchain, C runtime target, and Node-faithful platform semantics

- **Status**: Partially Implemented
- **Date**: 2026-09-05

## Context

The compiler has only ever run on Linux (x86-64, glibc) and macOS (Apple Silicon). A third development machine, Windows 11 x86-64, was set up on 2026-09-05 to start a Windows port. The first sanity pass established where things stand:

- `go build` and `go vet ./...` pass once two Unix-only test helpers (`Setpgid`, `syscall.Kill` in `tests/http_test.go` and `tools/conformance/main.go`) were split into build-tagged files.
- The compiler itself emits LLVM IR and the per-program C helpers fine. The `clang` step then fails: with LLVM's stock Windows `clang` there is no C runtime at all (`'math.h' file not found`), and with a mingw-w64 UCRT sysroot a hello world gets all the way to the linker and dies on `memmem`, a GNU/BSD extension no Windows C runtime provides.
- The repo checked out with CRLF (`core.autocrlf=true` on the new box), which would silently break every golden-output test. Fixed locally; a committed `.gitattributes` is the durable fix.

The obvious next step is "point clang at the mingw sysroot and shim `memmem`", and that is the right first move. But it must not quietly become the strategy. The project's standing rule is faithfulness to observable Node.js behavior, and Node on Windows is **not** a POSIX program: it runs on libuv's Win32 backend (I/O completion ports, `CreateProcessW`, console control handlers), and a great deal of what a Windows user sees — `process.platform === 'win32'`, backslash `path` semantics, `os.EOL`, no `SIGUSR1`, `cluster` round-robin instead of shared-accept, `fs.chmod` only toggling the read-only bit — follows from that. A port that reaches "tests pass" by emulating POSIX on Windows would ship a runtime whose observable behavior matches Linux Node rather than Windows Node, in exactly the places Windows users would notice.

This document therefore separates two decisions that the toolchain choice tends to conflate:

1. **Which C toolchain/runtime does the emitted program link against?** (a build-plumbing question)
2. **Which platform semantics does the runtime implement on Windows?** (a faithfulness question)

and lays out a staged plan where decision 1 is made now, cheaply and reversibly, while decision 2 is made per subsystem against Node's documented Windows behavior.

### How much of the runtime assumes POSIX

Occurrence counts across `codegen/llvm/*.go` and the embedded `*src/*.c` helpers (a symbol grep, so comments and IR declarations both count; it measures exposure, not effort):

| API family | Symbols | Occurrences | Windows story |
|---|---|---|---|
| Event loop | `select` (Berkeley), `poll` | ~440 | Winsock `select` works on **sockets only**; pipes, stdin, and child stdio need a different wait primitive |
| Process model | `fork`, `execvp`, `waitpid`, `pipe`, `kill` | ~200 | No `fork`. Node uses `CreateProcessW`; `cluster` primary spawns workers and hands sockets over |
| Signals | `signal`, `sigaction` | ~120 | Only `SIGINT`/`SIGBREAK`/`SIGHUP` exist, via console control handlers; `SIGTERM` handlers are never called; `process.kill` is unconditional terminate |
| Sockets | `socket`, `getaddrinfo`, `fcntl`, `ioctl` | ~260 | Winsock2 is close to BSD sockets but non-blocking mode is `ioctlsocket(FIONBIO)`, errors are `WSAGetLastError`, fds are `SOCKET` handles |
| Threads | `pthread_*` | small | winpthreads (mingw) or Win32 threads; `SharedArrayBuffer`/`Atomics` unaffected |
| Dynamic loading | `dlopen`, `dlsym` | ~20 | `LoadLibraryW`/`GetProcAddress` for `-dynimport=lazy` islands |
| Files | `stat`, `lstat`, `readdir`, `realpath`, `symlink`, `readlink`, `chmod`, `mkdtemp`, `umask` | ~70 | Win32 wide-char APIs; UTF-16 paths; symlinks need a privilege; mode bits are mostly fiction |
| Misc libc extensions | `memmem`, `strndup`, `getline`, `setenv`, `sysconf`, `clock_gettime`, `nanosleep` | ~70 | Shim layer; UCRT lacks most of these |
| `long` in C helpers | | 93 sites | Windows is LLP64 (`long` is 32-bit). Any helper that pairs a C `long` with an IR `i64` is an ABI bug on Windows |

Two structural facts matter more than the counts:

- The emitted IR does not carry a target triple or datalayout (clang warns "overriding the module target triple"). Windows codegen needs `x86_64-w64-windows-gnu` (or `-msvc`) emitted explicitly, and every place that assumes the SysV x86-64 calling convention for struct returns (`{ptr, i64}` aggregates) needs checking against the Win64 convention, which passes aggregates larger than 8 bytes by hidden pointer.
- The whole async story sits on one central `select()` reactor (`__kml_event_loop_run`). Everything that waits — sockets, timers, child stdio, signals-as-pipe, fs async, workers — funnels through it. That is the load-bearing decision for Windows.

## Design

### Option A: mingw-w64 toolchain with POSIX emulation kept as-is

Target `x86_64-w64-mingw32` against the MSYS2 UCRT sysroot, shim the missing libc extensions, and paper over the rest with the closest POSIX-looking Windows call (`_pipe`, `_spawnvp`, Winsock `select`).

- Fastest to a green hello world. `pacman` provides every optional dependency (`libcurl`, `pcre2`, `libtommath`, `openssl`, `nghttp2`, `gc`) in matching ABI.
- Fails on its own terms almost immediately: mingw-w64 has **no `fork`**, and Winsock `select` cannot wait on pipes or stdin, so the event loop and process model have to be rewritten anyway. What survives is only the "small libc shim" part.
- Where it does work, it produces Linux-Node behavior on Windows, which the faithfulness rule forbids.

### Option B: Cygwin/MSYS runtime (real POSIX layer)

Link against `cygwin1.dll`/`msys-2.0.dll`, which really do implement `fork`, POSIX `select` on everything, signals, and `/cygdrive` paths.

- Almost everything compiles unchanged.
- Rejected: `fork` is emulated by copying address space and is notoriously slow and fragile; paths are POSIX-style, not Windows-style; the runtime DLL must ship with every compiled binary; and the observable behavior is Cygwin's, which is further from Windows Node than Option A. Also a GPL/LGPL runtime dependency for every user's binary.

### Option C: MSVC (`x86_64-pc-windows-msvc`) with Win32-native runtime

Use clang's default Windows target, MSVC's headers and the Windows SDK, and write the platform layer directly against Win32.

- The most faithful target: it is exactly what Node itself is built with on Windows, so `process.platform`, path handling, console behavior, and error codes line up by construction.
- Costs: the Windows SDK and Build Tools are a multi-GB, licensed install with no package manager for the optional C libraries (vcpkg exists but is a second ecosystem to document); MSVC's C runtime lacks even more of the POSIX surface than UCRT-via-mingw does (no `unistd.h` at all); `winpthreads` is unavailable so worker threads go straight to Win32 threads.
- Nothing about the *semantics* of Option C requires the MSVC toolchain. The Win32 API is the same from either compiler.

### Option D (recommended): mingw-w64 UCRT toolchain, Win32-native platform layer

Separate the two decisions:

- **Toolchain**: `x86_64-w64-mingw32` with the MSYS2 UCRT64 sysroot, driven by the already-installed LLVM `clang` via `--target` and `--sysroot`. This is the same Universal C Runtime that MSVC programs use, so binaries have no extra runtime dependency beyond what every Windows 10+ box ships. `pacman` covers every optional library. Static linking of those libraries is straightforward here, which may let `--static` stop being Linux-only.
- **Semantics**: a platform abstraction layer in the C helpers, `__kml_plat_*`, with a POSIX implementation (the current code, mechanically moved) and a Win32 implementation written against Node's documented Windows behavior — not against "what does mingw provide that looks like this call". mingw's POSIX-ish conveniences (`_pipe`, `_spawn*`, `unistd.h`) are allowed in the Win32 implementation only where they are thin wrappers over the same Win32 call libuv makes; the event loop, process model, signals, and fs metadata are written to Win32 directly.

This keeps Option C's faithfulness with Option A's install story. If MSVC-toolchain support is ever wanted (for example, to link against vcpkg builds), it becomes a `--target` flag over the same platform layer, not a second port.

### Faithfulness catalog: what "Windows Node" observably does

This is the acceptance list for the semantics decision, per subsystem. Each item is Node's documented behavior on Windows and is the target regardless of toolchain.

| Area | Windows Node behavior | Consequence for this compiler |
|---|---|---|
| `process.platform` | `'win32'` | Compile-time constant, same mechanism as the existing `linux`/`darwin` branch |
| `path` | `path` is `path.win32`: `\` separator, `;` delimiter, drive letters, UNC, case-insensitive-but-preserving | Default dispatch flips per target; `path.posix` remains available |
| `os.EOL` | `'\r\n'` | Compile-time constant |
| `fs` paths | UTF-8 in, UTF-16 to the kernel; `\\?\` long-path prefix for >260 chars | All fs helpers go through a `utf8→wchar` boundary; no `fopen(char*)` |
| `fs.stat` | `mode` synthesised (`0o666`/`0o777` from read-only bit and extension), `ino`/`dev` real via `GetFileInformationByHandle`, `uid`/`gid` are 0, `blksize`/`blocks` are 4096/real | Stat struct is populated field by field, not `memcpy`d from `struct stat` |
| `fs.chmod` | Only clears/sets read-only; other bits ignored, no error | Do not call `_chmod` and hope; implement the documented subset |
| `fs.symlink` | Needs Developer Mode or admin; `'junction'` type exists and needs neither; `EPERM` otherwise | Surface Node's `'dir'`/`'file'`/`'junction'` argument |
| `fs.watch` | Recursive works (`ReadDirectoryChangesW`); filenames may be null on rename | Different backend, same event surface |
| Event loop | IOCP-based; `setImmediate`/timers/`nextTick` ordering identical to Unix | A completion-port reactor behind the same `__kml_event_loop_run` contract; ordering tests must pass unchanged |
| `child_process` | `CreateProcessW`; `shell: true` means `cmd.exe /d /s /c`; no `uid`/`gid`/`detached` setsid; `.bat`/`.cmd` need a shell; `windowsHide`, `windowsVerbatimArguments` exist; argv is quoted into one command line | Distinct spawn backend; argument quoting is a known, documented algorithm |
| `cluster` | Primary accepts, round-robin dispatches connections to workers (`SCHED_RR`); workers are spawned processes with an IPC pipe; no shared listening socket | Current fork-and-share-accept design (`SCHED_NONE`, Linux's default) is not available and not faithful; implement RR with `WSADuplicateSocketW` handle passing like libuv |
| Signals | `process.on('SIGINT'|'SIGBREAK'|'SIGHUP')` fire via `SetConsoleCtrlHandler`; `'SIGTERM'` listeners are accepted but never fire; `process.kill(pid, sig)` terminates unconditionally for any signal except `0` (existence check) | Console control handler backend; `SIGWINCH` (already supported on Unix) has a console-resize analogue via `ReadConsoleInput`; `SIGUSR*` are compile errors matching Node's `ENOSYS`-flavoured runtime error |
| `process.exit` codes | Same numeric surface; uncaught exception is still `1`; killed-by-signal reports `null` signal, code `1` on Windows | Test expectations that assert `signal: 'SIGKILL'` must have a Windows variant |
| `tty` | `isatty` via `GetConsoleMode`; raw mode via console mode flags; `columns`/`rows` via `GetConsoleScreenBufferInfo`; ANSI needs `ENABLE_VIRTUAL_TERMINAL_PROCESSING` | `klain:tui` needs this toggled on at startup, as Node does |
| `net` | Winsock; `EADDRINUSE` maps from `WSAEADDRINUSE`; `SO_REUSEADDR` means something different (Node sets `SO_EXCLUSIVEADDRUSE`) | Errno mapping table; do not set `SO_REUSEADDR` |
| `dns` | `getaddrinfo` exists (Winsock) | Largely portable |
| `worker_threads` | Real threads | winpthreads or Win32 threads; unaffected semantically |
| `crypto` | OpenSSL in Node | Keep `-crypto=openssl` default; a `-crypto=cng` backend (Windows CNG/`bcrypt.dll`, ships with the OS) is the exact analogue of `-crypto=commoncrypto` on macOS — a zero-install path worth adding later |
| `-dynimport=lazy` | n/a in Node (this compiler's own feature) | `LoadLibraryW`; islands become `.dll` |
| `Webview` | out of scope per README | Stays out; compile error on Windows |

### Staged plan

Each stage is independently shippable and gets its own ADR. Stages 0 and 1 are cheap and strategy-independent; the strategy decision above bites from Stage 2 on.

**Stage 0 — Toolchain plumbing.** `main.go`: on `GOOS=windows`, invoke `clang --target=x86_64-w64-mingw32 --sysroot=<detected UCRT64>`, default output `.exe`, refuse `--static`/`-package`/`-crypto=commoncrypto` cleanly with the existing message pattern. Emit `target triple`/`datalayout` in the IR for every host, not just Windows (removes the existing clang warning too). Add a `libc_shim.c` helper compiled only on Windows for `memmem`, `strndup`, `getline`, `setenv`/`unsetenv`, `clock_gettime`, `nanosleep`. Audit the 93 `long` sites in the C helpers and replace with `int64_t`/`intptr_t`. Commit `.gitattributes` (`* text=auto eol=lf`). Exit: hello world and the pure-language E2E suites (`exprs`, `strings`, `arrays`, `classes`, `generics`, …) pass on Windows.

**Stage 1 — Platform constants and pure-computation modules.** `process.platform`, `os.EOL`, `os.*`, `path` defaulting to `win32`, `process.env` case-insensitivity, `process.argv` from `GetCommandLineW`/`CommandLineToArgvW`. Exit: `path_test`, `os_test`, `process_test` pass with Windows expectations.

**Stage 2 — Platform abstraction layer and event loop.** Introduce `__kml_plat_*` in the C helpers; move the current POSIX code under it unchanged; add the Win32 reactor (IOCP, or a hybrid of `WSAPoll` for sockets plus a wait-thread pool for pipes/console — TDD-level decision below). Timers and `setImmediate` ordering tests are the acceptance suite. Exit: `timers_test`, `async_test`, `streams_test`, `net_test` pass.

**Stage 3 — fs.** Wide-char boundary, synthesised stat, chmod subset, symlink/junction, `fs.watch`. Exit: `fs_test`, `fs_async_test`, `fs_stream_test` pass with Windows expectations.

**Stage 4 — Processes and signals.** `child_process` via `CreateProcessW` with Node's quoting; console control handlers; `process.kill` semantics; `cluster` round-robin with socket duplication. Exit: `childprocess_test`, `signals_test`, `cluster_test`, `http` cluster tests pass.

**Stage 5 — Optional libraries and distribution.** Document `pacman` package names; verify `fetch`, `RegExp`, `bigint`, `crypto.subtle`, `tls`, `http.listen` link and run; evaluate `--static` on Windows; add `-crypto=cng`. Exit: full `go test ./...` and `make conformance` on Windows; CI job on `windows-latest` with the `msys2` action.

**Stage 6 — Docs.** README "Requirements (Windows)" from the install record below; website reference badges; status-page rows gain a platform column or a Windows caveat set (needs its own small design, since status JSON is single-platform today).

### Install record (for README, once Stage 0 ships)

What the Windows box needed, in order, as of 2026-09-05:

1. Git for Windows (provides Git Bash; the Makefile and scripts assume a POSIX shell).
2. Go 1.26+ (`winget install GoLang.Go`).
3. LLVM 15+ (`winget install LLVM.LLVM`), which provides `clang`, `lld`, and ASan.
4. GNU Make (`winget install GnuWin32.Make`, or MSYS2's `make`).
5. MSYS2 (`winget install MSYS2.MSYS2`), then `pacman -S mingw-w64-ucrt-x86_64-toolchain` for the UCRT sysroot. Optional libraries later: `pacman -S mingw-w64-ucrt-x86_64-{curl,pcre2,libtommath,openssl,nghttp2,gc}`.
6. Not needed: Visual Studio Build Tools / Windows SDK (only if an MSVC-target flag is ever added). Not needed: `node`, except for the website reference-check guard.
7. Repo setting: `git config core.autocrlf false` before first checkout, until `.gitattributes` lands.

## Open questions

1. **Reactor primitive for Stage 2.** *Resolved for now (ADR-00719): the hybrid — Winsock `select` over sockets (not `WSAPoll`, which never reports a failed connect), `PeekNamedPipe`/console waits over the rest, short slices only when both kinds are present. IOCP remains the upgrade path.* Full IOCP (libuv's model: overlapped I/O everywhere, including sockets via `WSARecv`/`AcceptEx`) is the faithful and scalable choice but is a different programming model from readiness-based `select`, so the socket code changes shape too. The hybrid (`WSAPoll` for sockets, dedicated waiter threads posting to one completion port for pipes/console/child handles) keeps the readiness model and touches less code, at the cost of one thread per non-socket handle. Recommendation: hybrid first, since it preserves the existing readiness-based socket helpers, with the completion port as the single wake-up object so a later move to full IOCP is incremental. Decide in the Stage 2 ADR after measuring how many readiness assumptions live in `runtime_net.go` and `runtime_http.go`.
2. **Struct-return ABI.** Whether any emitted IR relies on SysV's two-register return of `{ptr, i64}` in a way that breaks under Win64's hidden-pointer convention. Clang handles this for C-visible signatures given the right triple; internal IR-to-IR calls are convention-agnostic. Needs an empirical check in Stage 0 with the aggregate-heavy array and string paths, not a code read.
3. **Which existing tests get Windows-variant expectations vs. skip.** *Convention adopted (ADR-00719): a test whose expectation is POSIX-shaped and which Node on Windows fails identically is skipped there with the reason (`skipPOSIXToolsOnWindows`, `skipSignalDeliveryOnWindows`); a test of a real feature with a different Windows shape gets a Windows variant (`process.execPath`, the EventSource refused-connect grace). Host-specific quirks get a pure-Go probe (`skipIfLoopbackH2PrefaceIntercepted`).* Tests asserting `signal: 'SIGKILL'`, `uid`/`gid`, Unix `mode` bits, `/tmp`, or fork-specific cluster behavior are asserting Linux Node, and Windows Node genuinely differs. A per-test `if runtime.GOOS == "windows"` expectation is faithful; a blanket skip hides bugs. Decide the convention in the Stage 1 ADR.
4. **Status page representation.** Whether a feature that works on Unix but not yet on Windows is ✅ with a caveat, or whether the tables grow a platform column. The caveat route needs no generator change but overstates coverage on Windows; the column route is the honest one and touches `cmd/statusgen`. Defer to Stage 6.
5. **`--static` on Windows.** mingw can produce a fully static binary against static UCRT-linked libraries from `pacman`, which would lift the Linux-only restriction. Whether that is worth supporting depends on whether Windows users want single-file distribution as much as Docker users do. Evaluate in Stage 5.
6. **MSVC target flag.** Not planned. Revisit only if a concrete need appears (for example, a user needing vcpkg-built libraries or MSVC-ABI interop through the FFI surface). One datapoint: PerryTS, the other TS-to-native compiler this project benchmarks against, targets MSVC and ships its own CRT/SDK sysroot fetched with `xwin` (`perry setup windows`, ~1.5 GB, license prompt) rather than requiring Visual Studio — so the MSVC route is viable without the Build Tools install, which weakens the install-story argument for mingw and leaves faithfulness-of-semantics as the deciding factor either way.

### Findings from the port (2026-09-05, ADR-00718/00719)

- The mingw toolchain decision held: every optional library came from `pacman`, and the only toolchain-level issues were LLP64 (`long` in the embedded C, `curl`'s 32-bit `long` outputs, zlib's `uLong`) and Win64 `_setjmp` needing a 16-byte-aligned buffer.
- The Linux-ABI-in / Win32-out shim boundary kept every emitter untouched except two layout hooks (`addrinfo`, `ucontext`), the fork sites, and a few compile-time constants — the separation of toolchain and semantics the design argued for worked in practice.
- Two cross-platform bugs surfaced only because Windows exercised them: the un-terminated `process.argv` array handed to `execv`, and the first `.then` on a `fetch` typing its callback parameter as `number`.
- A traffic-filtering product (AdGuard) on the host this was developed on intercepts loopback traffic: HTTP/2 prefaces are answered by its own nghttp2, TLS handshakes are reset, and multi-megabyte request bodies are cut (a pure Go client/server pair fails the same way; Node's `http2.connect` fails there too). Disabling it, or excluding `127.0.0.1`, makes every affected test pass; the corresponding tests probe for the filter rather than treating it as a Windows caveat.
- OpenSSL on Windows talks Winsock directly, so anything handing it a descriptor must pass the `SOCKET`, not this project's fd number, and must not expect errno to carry `EAGAIN` afterwards — the two TLS bugs the port found.
- Test-run environment on Windows: MSYS2's `usr/bin` on PATH (coreutils for the child_process tests) and its `ucrt64/bin` ahead of Git for Windows' (a `curl` with HTTP/2; the optional libraries' DLLs). Goes into the README's Windows section (Stage 6).
