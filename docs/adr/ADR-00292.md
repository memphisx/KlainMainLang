# ADR-00292: Mixed int/float arithmetic promotes to double

- **Relations**: Extends [ADR-00187](ADR-00187.md)'s integer-vs-float operator split; found while testing [ADR-00293](ADR-00293.md)'s yield inference
- **Date**: 2026-08-22

## Context

`emitBinary` unified operand types with a left-biased `coerce(right,
left.Ty)`: with an integer left and a float right, the float was silently
`fptosi`'d — `i * 1.5` computed `i * 1`, `i / 2.0` computed `i / 2`, and
`3 === 3.5` compared `3 === 3` (true!). Real JS arithmetic is double; this
wasn't the documented "declared `: number` is i64" narrowing but a plain
wrong-answer bug on any mixed expression.

## Decision

Before unification, when exactly one operand is float and both are numeric,
**both promote to double** — for `+ - * / % **` and the ordering/equality
operators. Bitwise/shift ops are deliberately excluded (JS ToInt32-truncates
there, which the integer path already approximates). Date duration
arithmetic keeps its own rules. `inferExprType`'s `+`/`-` cases gain the
same float-join, and `*`/`/`/`%` gain explicit cases (they previously fell
through to the generic fallback).

All-integer expressions are untouched — exact i64 semantics (`3/2 === 1`)
remain this compiler's documented number model.

## Verification

Node-diff (byte-identical): `i * 1.5`, `i + 0.5`, `i - 0.25`, `i / 2.0`,
`i % 2.5`, both operand orders, `3 === 3.5` / `3 < 3.5`, and the inferred
`const x = i * 1.5` typing as a double. E2E: `TestE2EMixedNumericPromotion`.
Full suite green.
