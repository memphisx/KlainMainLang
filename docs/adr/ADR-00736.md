# ADR-00736: fs errno fidelity — unlink on a directory, W_OK on read-only, sharing violations

- **Relations**: Implements three §4 rows of [TDD-00180](../tdd/TDD-00180.md) (the Windows faithfulness audit); extends [ADR-00719](ADR-00719.md) (the Win32 platform layer), [ADR-00684](ADR-00684.md) (`err.code` on fs errors), [ADR-00027](ADR-00027.md) (the original fs surface)
- **Date**: 2026-09-07

## Context

Three rows from the audit's fs table, picked because each is a one-line change in `win32src/win32fs.c` with an observable `err.code`:

| Case | Node | Was |
|---|---|---|
| `fs.unlinkSync(dir)` | `EPERM` (libuv's `fs__unlink`; macOS BSD `unlink` agrees) | `EISDIR`, the Linux answer |
| `fs.accessSync(roFile, W_OK)` | `EPERM` (libuv's `fs__access`) | `EACCES` |
| Sharing violation (e.g. `unlinkSync` of a file another handle holds open without `FILE_SHARE_DELETE`) | `EBUSY` ("resource busy or locked") | `EACCES` |

Writing the E2E test for the first row exposed a fourth, **cross-platform** bug the audit's code-read missed: `unlinkSync` never reached the platform layer's `unlink()` at all. `__kml_fs_unlink` (`runtime_fs.go`) called ANSI C `remove()`, and `remove()` on an empty directory *removes it* — on every host. `fs.unlinkSync(emptyDir)` silently deleted the directory where Node throws. The audit's Windows row was therefore doubly wrong: not "EISDIR instead of EPERM" but "succeeds instead of throwing".

## Decision

- `__kml_fs_unlink` calls POSIX `unlink()` instead of `remove()` — libc on POSIX hosts, the Win32 layer's on Windows. This makes the per-host directory errno fall out naturally: Linux `EISDIR`, macOS `EPERM`, Windows `EPERM` (below). The `@remove` declaration moves to `ensureFsRm`, its only remaining user (`rmSync`'s first attempt legitimately wants "file or empty directory in one call").
- `win32fs.c` `unlink_w`: a real directory (not a junction/symlink) sets `EPERM`, not `EISDIR`.
- `win32fs.c` `access`: `W_OK` against a read-only file sets `EPERM`, not `EACCES`.
- `win32fs.c` `win_errno`: `ERROR_SHARING_VIOLATION` maps to `EBUSY` (libuv's mapping), leaving `ERROR_ACCESS_DENIED`/`ERROR_LOCK_VIOLATION` on `EACCES`.

## Consequences

- `tests/fs_errno_fidelity_test.go`: three E2E tests with per-host expectations under the ADR-00719 convention. The sharing-violation test holds the file open via `fs.openSync` and documents that when `FILE_SHARE_DELETE` lands (TDD-00180 §4, first row) its Windows expectation flips from `EBUSY` to success — update it alongside that change, not before.
- The `access(W_OK)` test skips for root on POSIX (root passes the write check regardless), so it asserts `EACCES` on the CI lanes and `EPERM` on Windows, and skips in a root Docker shell.
- Verified on Windows 11 x86-64 (this box: the three new tests plus the fs-related suite) and Linux x86-64 (Docker `klain-ci`: same subset plus the full suite). macOS expectations follow BSD `unlink(2)`/`access(2)` semantics and ride the CI lanes.
- `fs.rmSync(emptyDir)` without `{ recursive: true }` still removes the directory via `remove()`, where Node throws `ERR_FS_EISDIR` — an adjacent gap observed while fixing this, deliberately not changed here; it needs its own look at `__kml_fs_rm`'s fallback chain.
