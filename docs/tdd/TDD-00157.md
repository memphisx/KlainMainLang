# TDD-00157: Overridable EventEmitter methods in a subclass

- **Status**: Implemented
- **Date**: 2026-09-02

## Context

`EventEmitter<T>` (TDD-00023) exposes `on`/`once`/`emit`/`off`/
`removeListener`/`removeAllListeners`/`listenerCount`/`eventNames` as
hand-written codegen dispatched by name (emit_call.go), never as real
AST-driven class methods. A consequence recorded as a fidelity gap: a class
in an EventEmitter-rooted tree that *declares* one of those names is a
clean compile-time error (`registerClasses`, emit_classes.go), so there is
no way to override `emit`/`on`/etc. — the single most common real-world
`EventEmitter` subclass idiom (wrap `emit` to log/count, wrap `on` to
lazily attach a source, etc.).

This is the highest-leverage EventEmitter gap: `EventEmitter` is the
substrate under streams, `http`, `net`, and worker events, so making it a
real overridable surface lifts fidelity across that whole cluster rather
than one leaf API. It is scoped now because the dispatch machinery already
prefers a real `MethodSig` over the built-in (emit_call.go's member-call
order), so the change is small and self-contained rather than a rewrite.

Out of scope (unchanged, separately documented): open-ended untyped
`emit(event, ...args)` varargs beyond a declared tuple payload — that is a
static-typing limitation, not an override one, and stays a caveat.

## Design

Two mechanisms change; a third (dispatch preference) already does the right
thing and is only relied upon.

### 1. Allow declaring an EventEmitter method name (the override)

`registerClasses` (emit_classes.go:998) currently returns an error when a
`hasEventEmitter` class declares any `isEventEmitterMethodName` method.
Remove that rejection. The declared method then flows through the ordinary
`MethodSigs`/vtable path exactly like any other method: it gets a signature,
a vtable slot, and a `@Class_method` body.

**Dispatch already prefers it.** emit_call.go's instance-member dispatch
checks `info.MethodSigs[mem.Property]` *before* the `info.HasEventEmitter &&
isEventEmitterMethodName(...)` built-in branch. So once the method is a real
`MethodSig`, `x.emit(...)` on a static receiver routes to the override, and
a `Shape`-typed receiver holding a subclass routes virtually through the
vtable — no dispatch change needed. The built-in branch stays as the
fallback for every EE method the class did *not* override.

**Signature check.** An override's declared signature must be compatible
with the built-in it replaces (e.g. `emit(event, payload): boolean`,
`on(event, listener): this`). V1 does *not* enforce structural compatibility
against the synthetic built-in signature — TypeScript itself only checks an
override against a real base declaration, and `EventEmitter<T>` has no real
base method node here. A wildly-wrong override signature is the author's
problem, same as any unchecked `as`-erased position. Recorded as a caveat.

### 2. Route `super.<eeMethod>(...)` to the built-in (or nearest real override)

An override body must be able to reach the underlying behavior, i.e.
`emit(e, p) { this.count++; return super.emit(e, p); }`. Today
`emitSuperMethodCall` (emit_classes.go:2769) relies on the `super` scope
symbol, which is bound only when the base is a *registered* class. A class
directly `extends EventEmitter<T>` has `BaseClass == ""` (the synthetic
`EventEmitter` is never registered), so `super` is unbound and
`super.emit(...)` errors.

New rule, checked at the top of `emitSuperMethodCall`, before the `super`
lookup:

- If the enclosing class (`__kml_enclosing_class`) `HasEventEmitter` and
  `methodName` is an EventEmitter method name:
  - Walk the enclosing class's `AncestorChain` looking for the nearest
    ancestor that *itself declares a real `MethodSig`* for `methodName` (a
    real override, not the built-in). If found → `emitClassCall` directly to
    that ancestor's implementation against `this` (existing forceDirect
    path), so `B extends A extends EventEmitter` with both overriding `emit`
    has `B`'s `super.emit` reach `A`'s.
  - If no ancestor overrides it → route to the built-in
    `emitEventEmitterCall` against `this`'s hidden listener-map field
    (`classEventEmitterFieldIndex`), reusing the exact IR the non-override
    instance dispatch emits.

`this` (not `super`) is the receiver in both cases — always bound inside an
instance method — so the direct-EE-extend case (no `super` symbol) works.

### 3. `'error'` special-case and chainability

The built-in `emit('error', ...)`-throws-if-unlistened behavior and `on`'s
`return this` chainability live inside `emitEventEmitterCall`, so a
`super.emit('error', e)` / `super.on(...)` inherits them unchanged. An
override that *replaces* `emit` without calling `super.emit` opts out of the
throw-on-unlistened behavior — which is exactly real Node semantics (you
overrode it).

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| EventEmitter built-in dispatch (`emitEventEmitterCall`) | Built (TDD-00023) | Reused verbatim for the `super` fallback |
| Real class methods + vtable dispatch | Built (TDD-00009 Stage 3) | The override rides this path unchanged |
| `super.method()` (`emitSuperMethodCall`) | Built (TDD-00009 Stage 3) | Extended with the EE-method branch |
| `AncestorChain` on class info | Built | Used to find the nearest real override for `super` |
| `classEventEmitterFieldIndex` / listener-map field | Built (TDD-00023) | The `super`-fallback receiver field |

## Open questions

- Multi-level `super` chaining where an *intermediate* class overrides only
  *some* EE methods is covered by the AncestorChain walk, but is thin on
  test coverage; the E2E suite pins the single-override and two-level cases.
- Whether to later enforce override-signature compatibility against the
  synthetic built-in signature (currently unchecked, matching the erased-`as`
  stance). Deferred, not blocking.
