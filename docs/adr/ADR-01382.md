# ADR-01382: A child's exit is dispatched after its streams are read

- **Relations**: Extends ADR-00767, TDD-00230
- **Date**: 2026-10-04

## Context

`TestE2EClusterLevelEventsAndWorkers` failed 35 times in 100 runs on the
x86-64 Linux box: the cluster `'exit'` listener printed `left 1` (the worker
still in `cluster.workers`) where Node prints `left 0`. Only a run where the
worker started slowly failed: the first run of a freshly built binary, or a
run pinned to one busy CPU (`taskset`), which failed 12 times in 60.

## Investigation

- `lib/node/cluster.ts` follows Node's `primary.js`: on the worker
  process's `'exit'` the worker is removed only if its IPC channel is
  already disconnected; otherwise its `'disconnect'` removes it later.
- An event trace of the failing order: `exit` with `connected true`, then
  `disconnect`. Node clears `connected` the moment the channel's read
  returns its end, and a process's descriptors close before it can be
  reaped, so in libuv's readiness order the end of the channel always comes
  before the exit.
- `__kml_tcp_dispatch` ran `proc_dispatch` (the `waitpid` reap and the
  `'exit'` callback) before the stream handles' reads. A worker whose
  channel end and exit reached the same pass had its `'exit'` first.
- The channel took its end from the socket's `'end'` event, which a stream
  emits after its reads, not at the read itself as Node's channel does.

## Decision

- `__kml_tcp_dispatch` reads the stream handles first and reaps children
  after them. A child reaped while one of its stdio handles (its IPC
  channel among them) still has data or its end to read keeps its exit
  for exactly one more pass, which reads them first (`pending` 2, the loop
  kept alive and not blocking meanwhile). A pipe held open by a grandchild
  never delays the exit by more than that pass.
- An unref'd child's exit reaped on an earlier pass is still dispatched at
  the start of a pass, before its streams' close: when they were what
  held the loop, the loop ends and the exit goes unreported, as in Node.
- A socket calls its `_kmlOnEof` hook when its read returns the end, and the
  IPC channel disconnects there, as Node's channel does in its `onread`.

## Implementation notes

`codegen/llvm/threadpoolsrc/klainpool.c` (`__kml_tcp_dispatch`,
`proc_dispatch`, `proc_dispatch_unrefd`, `proc_keepalive`,
`proc_fdset_add`), `lib/node/net.ts`,
`lib/node/internal_child_process_channel.ts`.

## Side effects discovered

- With piped stdio, Node itself reports an unref'd child's `'exit'` only
  sometimes (its loop usually ends first). `TestE2EChildProcessUnref` keeps
  the usual outcome as fixed output and compares the `stdio: 'ignore'` case
  with Node.

## Verification

Node304 (x86-64 Ubuntu, docker): the cluster program 100 times on one busy
CPU, every run `left 0`, with Node's event order; the cluster, fork,
child_process and HTTP-cluster tests; `TestE2EChildProcessUnref` and
`TestE2EChildProcessRefAfterUnref`.
