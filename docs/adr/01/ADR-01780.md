# ADR-01780: Nested destructuring patterns take a default

- **Relations**: `Implements TDD-00230`
- **Date**: 2026-10-20

## Context

- A nested pattern with a default was rejected at compile time in declarations, parameters and assignments: `[[a, b] = d]`, `{ k: { x } = d }`, and `[[a] = d] = src` as an assignment. Test262's `dstr` suites use the form throughout.
- Three older bugs sat beside it:
  - An `any` element present but `undefined` kept its `undefined`, where JavaScript applies the default (`var [h = 5] = [undefined, 3]` gave undefined). This affected both the declaration and the assignment leaf.
  - An empty source literal types its elements as numbers, so an array default was converted to a number: `var [h = [7, 8]] = []` gave NaN.

## Decision

- **Declarations and parameters:** a nested element or field with a default binds a hidden leaf with that default (`nestedDefaultName`). `emitNestedPatternDecl` then destructures the hidden name with the sub-pattern, right after that element, so evaluation order holds. A hidden value with no static shape for the pattern is destructured as an `any`.
- **Assignments:** a hidden `any` (`declareHiddenAny`) takes the element through the leaf assignment, or the field with `undefined ? default : value`. The nested pattern is then assigned from it.
- An `any` element with a default tests for `undefined` and takes the default branch, in both leaf paths.
- A default whose kind doesn't fit the element type (`defaultFitsElem`) binds the name as an `any`, boxing whichever value arrives.

## Consequences

- `TestE2EJSFileNestedPatternDefaults` covers declarations, parameters, generator parameters, assignments, a default evaluated only when needed, and mixed-kind defaults.
