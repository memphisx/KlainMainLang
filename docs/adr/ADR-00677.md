# ADR-00677: `events.on` — an async iterator over an event

- **Relations**: Implements TDD-00167 (completes it — `once` shipped in
  ADR-00675); builds on ADR-00676 (array-yielding generators), ADR-00674
  (`Promise<T[]>` values), ADR-00263/TDD-00087 (Promise executor / escaping
  resolvers), TDD-00085 (async generators)
- **Date**: 2026-09-03

## Context

`events.on(emitter, name)` was TDD-00167's deferred, load-bearing piece: it
returns an async iterator that yields the event's argument array on each
emission, buffering events between iterations and parking the consumer when the
queue drains. `events.once` shipped as a one-shot Promise; `on` is the streaming
form (`for await (const [x] of on(ee, 'data'))`).

## Investigation

The naive `while (true) yield await once(...)` loses every event emitted in the
window between one `yield` returning and the next `once` re-arming — TDD-00167
ruled it out. A faithful iterator needs an unbounded buffer plus a parked-waiter
resolver so no emission is dropped.

Two prerequisites had to hold, both verified with throwaway repros first: (1) an
async generator can yield an **array** element type — delivered by ADR-00676;
(2) a `Promise` **resolver can escape** its executor and later resume a parked
`await` when called from an event listener (`setTimeout(() => resolve(v))` →
`await p` resumes). Both worked.

The one real obstacle was **listener registration timing**. A plain
`async function*` runs its body — and so registers its listener — only on the
first `.next()`, i.e. when `for await` first pulls. Any event emitted between the
`on(...)` call and that first pull would be lost. Node attaches the listener
*synchronously at the `on(...)` call*. So `on` cannot be a single async
generator; the listener registration must run eagerly, before the iterator body.

A second obstacle surfaced on first run: `for await (const [n] of on(...))`
array-destructures an element whose type is now an array (`number[]`), but every
generator `for-of`/`for-await` loop rejected array-pattern destructuring of a
non-tuple element (a stale invariant from before ADR-00676 — "an async
generator's element type is never an array").

## Decision

Desugar `on(ee, name)` to a **synthesized setup + iterator function pair**,
memoized per (element type, arity):

```ts
function __kml_events_on_setup_<key>(ee, name): <state> {
  const st = { q: [], resolve: null };
  ee.on(name, (...a) => {                 // registered eagerly, at the on(...) call
    const item = [...a];
    if (st.resolve !== null) { const r = st.resolve; st.resolve = null; r(item); }
    else { st.q.push(item); }
  });
  return st;
}
async function* __kml_events_on_iter_<key>(st): elem[] {
  while (true) {
    if (st.q.length > 0) { yield st.q.shift(); }
    else { yield await new Promise((res) => { st.resolve = res; }); }
  }
}
```

with `on(ee, name)` becoming
`__kml_events_on_iter_<key>(__kml_events_on_setup_<key>(ee, name))`. Constructing
the generator instance evaluates its argument, so `setup` runs eagerly and
attaches the listener before any consumption; the returned instance is what
`for await` drives. The shared `st` cell (an object holding the queue and the
pending-waiter resolver) is captured by the listener and read by the iterator —
a burst of synchronous emissions buffers into `st.q`, and a later emission
resolves a parked consumer's `st.resolve`.

The helper pair is generated as **TypeScript source**, parsed with the ordinary
parser, its two signatures registered (a normal function + an async generator),
and its bodies emitted directly — reusing the whole existing generator / Promise
/ EventEmitter / closure machinery rather than hand-writing IR. Generating
source (not hand-built AST) keeps the desugar legible and lets the type checker
and codegen treat the helpers exactly like user code.

Array-element destructuring in the six generator loop sites is lifted from a
clean rejection to a real bind: an array-typed element's `{ptr,i64}` aggregate is
split into (data, len) and fed to the shared `unpackArrayPatternInto` core (the
same one plain `const [a, b] = arr` uses).

**V1 scope.** Single-value and homogeneous multi-argument events (reusing
`once`'s `eventsOnceArgShape` rules); a mixed-type multi-argument event, a
payload-less event, and non-scalar payload element types are clean rejections,
identical to `once`. The queue is unbounded (Node's default); iterator
`.return()`/`.throw()` unregistering the listener is a documented follow-up.

## Implementation notes

- The helper pair is emitted **inline, mid-emission**: `emitFunctionDecl` /
  `emitGeneratorFunctionDecl` each fully save and restore the current function's
  emission context and write the finished function into `e.functions`, so
  emitting a helper from inside another function's body is safe and needs no
  extra pass. LLVM tolerates the forward call since both `define`s land in the
  same module.
- Type inference (`eventsOnGeneratorType`) and the emit path share
  `ensureEventsOnHelperSigs`, so `for await`'s inferred iterable type is exactly
  the registered iterator generator's `GenTy` — no risk of a hand-computed type
  drifting from the emitted instance's layout. Inference registers signatures
  only; bodies are emitted solely from the emit path.
- All new code is in `emit_events_helpers.go`; the wiring is one dispatch case
  (`emit_call.go`), one inference case (`emit_exprs_types.go`), one allowlist
  entry (`resolver/virtual_modules.go`), and the six-site array-destructure lift
  (`emit_generators.go`, shared with ADR-00676).

## Side effects discovered

The array-destructure-of-array-element rejection (six generator loop sites) was
a stale post-ADR-00676 invariant; lifting it also benefits any generator
yielding arrays that a consumer destructures, not just `events.on`.
