# TDD-00151: `node:sqlite` — a real synchronous SQLite API (DatabaseSync / StatementSync)

- **Status**: Partially Implemented
- **Date**: 2026-08-31

## Context

Node exposes an experimental built-in SQLite module, `node:sqlite`
(`DatabaseSync`, `StatementSync`), stabilising as the standard way a Node
program talks to an embedded SQL database with no npm dependency. It is a real
Node API, so under this project's namespace convention (Node module names =
real Node behaviour; bespoke re-imaginings live under `klain:`) it belongs at
the specifier `node:sqlite`, implemented faithfully.

It is also an unusually good fit for a native compiler, for two reasons that
make it cheaper than most Node APIs of comparable value:

- **The API is entirely synchronous.** `DatabaseSync` and `StatementSync`
  block — `db.prepare(sql).get(id)` returns a row, it does not return a
  Promise. That sidesteps the event-loop / fiber / trampoline machinery that
  `fetch` and `http.listen` needed; it slots into the same blocking-I/O tier
  as `fs.readFileSync`.
- **Linking libsqlite3 is already a solved, low-risk pattern.** The C-library
  linking convention (`ensure*()` externs + a conditional `-l` flag through
  `LinkLibs()`) has a working precedent in `libcurl` for `fetch`
  ([ADR-00021](../adr/ADR-00021.md)), and SQLite is *easier* than libcurl:
  its public-domain single-file amalgamation static-links routinely on
  musl/Alpine, unlike libcurl's TLS/compression dependency chain that made
  `--static` a real fight ([ADR-00033](../adr/ADR-00033.md)). This was already
  noted as low-risk prior art in [TDD-00011](TDD-00011.md) and
  [TDD-00035](TDD-00035.md).

The value is high against this project's stated targets. CLI tools and Docker
microservices both routinely want local persistence; today every program this
compiler produces is stateless or holds state only in heap structures that
vanish at exit. `node:sqlite` gives real ACID persistence and a SQL surface
directly, with no server to run and no protocol to hand-roll.

### Where this sits in the broader database strategy

This is deliberately *not* a general "database support" decision — it is the
one database surface that is also a **built-in Node API**, which is what earns
it a first-class native implementation rather than a package.

The wider plan for talking to real databases (PostgreSQL, MariaDB, and the
like) runs on two other rails, both out of scope here: **compiling the existing
npm client packages** as they become compilable, and — where a native
reinterpretation buys something — a **`klain:`-namespaced package that matches
the signatures** of the popular client for that database, on this compiler's own
runtime. `node:sqlite` is orthogonal to both: it is neither a third-party
client nor a bespoke re-imagining, it is a standard Node module, so it is
implemented faithfully under its real specifier, the same as `http` or `fs`.

**On the earlier SQLite discussion in [TDD-00011](TDD-00011.md):** that
document did not reject SQLite the technology — it rejected mapping SQLite into
a **key/value shape to back an `IndexedDB` front-end**, because a single-table
`key BLOB, value BLOB` KV projection is a poor use of a relational engine and a
poor fit for that API. Exposing SQLite's *actual* relational SQL surface — which
is exactly what `node:sqlite` is — was never what that document ruled out. So
the two are complementary, not contradictory: TDD-00011 would use SQLite (if at
all) as an invisible KV engine; this TDD exposes SQL *as the public API* because
that is the Node contract. They share exactly one thing — the `libsqlite3`
linking mechanism — and can share a single `ensureSQLite3()` / `LocateSQLite`
layer if both ever ship. Neither blocks or depends on the other.

## Design

Four layers, each with a direct working precedent in the codebase. The order
below is roughly the order of implementation; the genuinely undecided part is
Layer 3 (row shape), called out as its own subsection and the primary Open
Question.

### Layer 1 — module registration and constructor recognition

- **Register the specifier.** Add `"node:sqlite": "sqlite__kml_builtin"` to
  `virtualBuiltinMarkers`, and a `virtualModuleMembers["node:sqlite"]`
  allowlist (`DatabaseSync`, `StatementSync`, `constants`, and `backup` if/when
  Layer 4 lands) in `resolver/virtual_modules.go`. There is no bare `sqlite`
  Node module, so — like the `klain:` entries — it is registered explicitly and
  *not* run through the auto-`node:`-prefixer; whether to *also* accept a bare
  `"sqlite"` alias for ergonomics is an open question below (leaning no, to
  stay faithful).
- **Recognise the constructor at parse time.** `new DatabaseSync(path, opts?)`
  follows the existing builtin-constructor pattern in
  `parser/parser_literals.go` (the switch that already special-cases `URL`,
  `Headers`, `Request`, `Worker`, `Webview`, …): add
  `case "DatabaseSync"` producing a dedicated `ast.NewDatabaseSyncExpression`
  AST node, routed in `codegen/llvm/emit_exprs.go` to `emitNewDatabaseSync`.
  `StatementSync` is *never* `new`'d by user code (it is only returned from
  `db.prepare()`), so it needs no parser case — only the type + dispatch layers
  below. The end-to-end template to imitate is `new URL()`
  (`parseNewURLBody` → `emitNewURLExpression` → `URLType()`/`IsURL` + a
  libcurl handle stored in the heap struct); SQLite mirrors it almost exactly,
  swapping the `CURLU*` handle for a `sqlite3*`.

### Layer 2 — the two handle-bearing objects (Type flags + method dispatch)

The compiler models builtin objects-with-methods as a heap struct carrying the
native handle plus a boolean discriminant flag on `Type`, with method calls
dispatched on that flag. This is exactly how `Response`, `Headers`, `URL`,
`ServerResponse`, `IncomingMessage` already work.

- Add `IsSQLiteDatabase` / `IsSQLiteStatement` flags and
  `SQLiteDatabaseType()` / `SQLiteStatementType()` constructors in
  `codegen/llvm/types.go`. The database struct holds the `sqlite3*`; the
  statement struct holds the `sqlite3_stmt*` (plus a back-reference to its
  database for error reporting and a cached column-count/name list).
- Dispatch in `codegen/llvm/emit_call.go` `emitCall`, mirroring the existing
  `IsServerResponse` / `IsIncomingMessage` checks: `db.<m>()` routes on
  `inferExprType(mem.Object).IsSQLiteDatabase` to `emitSQLiteDatabaseMethod`;
  `stmt.<m>()` routes on `IsSQLiteStatement` to `emitSQLiteStatementMethod`.
  `db.prepare()` returns a value typed `SQLiteStatementType()`, so the
  `stmt.get()/.all()/.run()` chain type-checks and dispatches with no extra
  plumbing.

**`DatabaseSync` V1 surface:** `exec(sql)`, `prepare(sql) → StatementSync`,
`close()`, `isOpen`. The constructor options object (`open`, `readOnly`,
`enableForeignKeyConstraints`, `enableDoubleQuotedStringLiterals`, `timeout`)
maps directly onto `sqlite3_open_v2` flags + a couple of `PRAGMA`s /
`sqlite3_busy_timeout`. `open: false` + a later `db.open()` is a small
follow-on.

**`StatementSync` V1 surface:** `get(...params)`, `all(...params)`,
`run(...params) → { changes, lastInsertRowid }`, plus `sourceSQL` /
`expandedSQL`. `iterate()` (a real JS iterator), `columns()`,
`setReadBigInts()`, `setAllowBareNamedParameters()` are Layer 4.

**Parameter binding** is variadic and mixed-type — positional
(`?`/`?NNN`/`$name` passed as trailing args) and named (a single object arg
whose keys map to `:name`/`@name`/`$name`). The value→SQLite mapping is fixed
by the spec and small: `number`→`bind_int64`/`bind_double` (integrality
decides which), `string`→`bind_text`, `null`/absent→`bind_null`,
`Uint8Array`→`bind_blob`, `bigint`→`bind_int64` (with range check). Named-param
binding needs a compile-time-known object literal or a typed object; a fully
dynamic bag hits the same fixed-shape limit as row output (Layer 3).

`ensureSQLite3()` (new, in a `runtime_sqlite.go`) declares the externs used —
`sqlite3_open_v2`, `sqlite3_close_v2`, `sqlite3_prepare_v2`, `sqlite3_step`,
`sqlite3_reset`, `sqlite3_finalize`, the `sqlite3_bind_*` and
`sqlite3_column_*` families, `sqlite3_column_count`, `sqlite3_column_name`,
`sqlite3_column_type`, `sqlite3_changes64`, `sqlite3_last_insert_rowid`,
`sqlite3_errmsg`/`sqlite3_extended_errcode`, `sqlite3_busy_timeout` — following
`runtime_url.go`'s `ensureCurlURL()` exactly. Linking: `requireLink("sqlite3")`
(guarded like `requireLink("curl")`), plus a `LocateSQLite`
pkg-config→`brew --prefix`→bare-`-l` probe copied from `LocateCrypto`
(`crypto.go`), so the Homebrew `sqlite` keg-only include/lib prefix on macOS is
found. libsqlite3 ships on macOS and virtually all Linux, so — like libcurl —
the default path is link-the-system-lib, not vendor-the-amalgamation; a
bundled-amalgamation fallback via `CSource`/`EmbeddedCSources`
(`embedded_c.go`) is a documented future option for `--static` / minimal-image
builds, not V1.

### Layer 3 — result row shape (the actual design decision)

`stmt.get()` returns an object whose **keys are the SQL result columns** and
`stmt.all()` returns an array of them. In untyped Node this is a dynamic-shape
object decided at runtime by the query. This compiler has a **fixed-shape
object model** (no prototypes, no dynamic property bags) — the same wall that
keeps nested/dynamic `JSON.parse` limited. This is the one part of `node:sqlite`
that is not a straight port, and it needs a deliberate answer.

Three options:

**Option A — typed rows via the annotation this compiler already reads
(recommended for V1).** Require the row shape to be statically known, supplied
the way TS code already supplies it. Node's own `.d.ts` types `get<T>()`,
`all<T>()`, so TS authors *already* write `db.prepare(sql).all<{ id: number,
name: string }>()`; a `/** @type {{ id: number, name: string }} */` override
(the JSDoc mechanism the compiler already parses) is the equivalent for the
un-generic call site. Given the shape, codegen emits a concrete struct and maps
columns to fields **by name** (via `sqlite3_column_name`) at read time, with the
spec's type coercion (`INTEGER`/`REAL`→number, `TEXT`→string, `BLOB`→Uint8Array,
`NULL`→null). This is faithful to observable behaviour for the overwhelmingly
common case (you know your schema), fits the compiler's static ethos, and reuses
existing object-construction codegen. The divergence is narrow and honest: the
*value* of a column you didn't declare isn't reachable, because there is no
field for it — a compile-time shape requirement, not a wrong runtime answer.
Requires generic call-site type arguments (`.all<T>()`) to be threaded into
`inferExprType`; if generics on builtin methods aren't wired yet, the JSDoc
override path stands alone for V1 and the generic form follows.

**Option B — a dynamic row record (faithful to untyped JS, deferred).** A real
runtime dictionary of `string → tagged-value` (a variant over the five SQLite
storage classes), accessed `row.col` / `row["col"]`. This is the fully faithful
shape and the only one that supports `SELECT *` against an unknown schema or
column names not known until runtime — but it needs exactly the dynamic-object /
tagged-value machinery the codebase does not yet have (the same gap that limits
`JSON.parse`). It should be built *with* that machinery, not as a one-off for
SQLite, and is therefore the documented perf/faithfulness follow-up rather than
V1 — consistent with the standing rule to implement faithfully now and record
the strategy swap as future work rather than diverging in behaviour. When it
lands, it becomes the default and Option A becomes an optimisation the type
annotation opts into.

**Option C — arrays instead of objects (rejected).** Return each row as a
positional array (`[1, "ada"]`). Trivially implementable and shape-free, but it
is *not what `node:sqlite` does* — it would be an observable divergence for no
reason other than implementation convenience, which the faithfulness rule
forbids. (SQLite's raw `sqlite3_column_*` is positional under the hood, but the
Node API's contract is name-keyed objects.) Not pursued.

**Recommendation:** ship Option A as V1 (faithful for known-schema code, which
is the norm and is exactly how the TS types are written), and record Option B as
the follow-up that removes the annotation requirement once the dynamic-object
subsystem exists. Document the V1 requirement plainly in the status caveats:
"result rows need a statically known shape (`.all<T>()` / `@type`); `SELECT *`
against an unknown schema awaits the dynamic-object work."

### Layer 4 — beyond V1 (staged for ordering, not dropped)

Faithful completion of the module, each an independent follow-on once V1 works:

- `StatementSync.iterate()` — a real JS iterator over rows (lazy `sqlite3_step`),
  once the row-shape decision from Layer 3 is settled; `columns()`,
  `setReadBigInts()` (INTEGER→`bigint`, needs BigInt interop — `LocateBigInt`
  exists), `setAllowBareNamedParameters()`.
- `DatabaseSync.function()` / `aggregate()` — user-defined SQL functions
  backed by `sqlite3_create_function_v2` calling back into a compiled closure.
  This *does* reintroduce the C-trampoline-to-closure pattern
  (`qsort` comparators, timer callbacks are the precedent), the one piece of V1
  that the synchronous surface otherwise avoids.
- The `constants` export (`SQLITE_CHANGESET_*`, `SQLITE_OPEN_*`, …) — a plain
  frozen constants object; cheap, and an easy conformance win.
- Session/changeset extension (`createSession`, `applyChangeset`), extension
  loading (`loadExtension`/`enableLoadExtension`), and the newer async
  `backup()` — genuinely lower priority; `backup()` is the only async member and
  is the one place the event loop would re-enter, so it is deliberately last.

### Error handling

SQLite errors surface in Node as a thrown `Error` carrying `code`
(`'ERR_SQLITE_ERROR'`), `errcode`, and `errstr`. Map `sqlite3` non-OK returns
onto the compiler's existing exception model (`setjmp`/`longjmp`,
[TDD-00006](TDD-00006.md)) by constructing that error object from
`sqlite3_errmsg` / `sqlite3_extended_errcode` and throwing it — same mechanism
any other builtin uses to raise, so `try/catch` around a bad query behaves
faithfully.

## Open questions

- **Row shape (the real one).** Confirm Option A (statically-typed rows via
  `.all<T>()` / `@type`) as the V1 contract, with Option B (dynamic record)
  as the documented follow-up gated on the dynamic-object subsystem — or is the
  annotation requirement unacceptable enough that V1 should wait for Option B?
  Leaning A-first: it is faithful for the known-schema norm, matches how the
  Node `.d.ts` types are already written, and ships value now without blocking
  on a whole new object subsystem.
- **Bare `"sqlite"` alias?** Register only `node:sqlite` (faithful — there is no
  bare Node `sqlite`), or also accept `"sqlite"` for ergonomics? Leaning
  faithful-only.
- **INTEGER default: `number` or `bigint`?** Node defaults INTEGER→`number` and
  opts into `bigint` via `setReadBigInts(true)`; faithful default is `number`,
  but values beyond 2^53 lose precision exactly as they do in Node. Match Node
  (default `number`, precision caveat documented) rather than diverging to
  `bigint`-by-default.
- **System lib vs. vendored amalgamation for V1.** Default to linking the
  system `libsqlite3` (libcurl posture) and treat the bundled-amalgamation
  `CSource` path as a later `--static`/minimal-image option — or is
  reproducible-build parity across the two dev machines reason enough to vendor
  the amalgamation from the start? Leaning system-lib-first.
- **Named-parameter binding from a non-literal object.** Positional params and
  object *literals* bind cleanly; a named-param object whose shape isn't
  statically known hits the same fixed-shape wall as Layer 3 — does V1 require
  the bound object be typed/literal, deferring the fully-dynamic case alongside
  Option B?
