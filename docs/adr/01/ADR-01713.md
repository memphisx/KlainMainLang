# ADR-01713: Stack allocation and auto frees: module globals, self-capture, forward capture

- **Relations**: `Fixes ADR-00704`; `Implements TDD-00230`
- **Date**: 2026-10-18

## Context

`make mode-lanes` on macOS segfaulted `res_backpressure_drain` and `http_upload` under `-mm=auto -optimize-memory`, and `Readable.from` overflowed the stack under every `-optimize-memory` build. The escape analysis (TDD-00134, TDD-00173) planned three kinds of value as block-local although they outlive their block:

1. **Module globals.** A builtin module's top-level object literal is bound to a module global, but it was allocated on the stack of the module's init function, which returns.
2. **Self-capture.** A closure whose own body hands itself on, such as `const pump = () => { ... res.once('drain', pump) }`. The checker never examined the initializer for the binding's own name.
3. **Forward capture.** A closure declared earlier in the block that names a later binding (`read` calling `nextSyncWithSyncValues` in `readableFrom`) captures that binding's cell and carries it out of the block. The checker looked only at the statements after the declaration.

Cases 2 and 3 equally made `-mm=auto` free such a value at block exit.

## Decision

- A declaration promoted to a module global is never stack-allocated.
- A binding's own initializer counts toward its escape analysis, for both the stack and the free planner.
- A binding named by an earlier statement in its block is not a candidate.

## Verification

macOS (Apple Silicon):
- the five examples BACKLOG #12 named have no mismatch in any lane;
- `TestE2EOptimizeMemorySelfReferencingClosure` passes in `-mm=auto` and in the default mode;
- the optimize-memory, auto-free and escape E2E tests pass.
