# TDD-00063: Class-body expansion (expressions, field initializers, async/generator/computed members)

- **Status**: Implemented (Stages 1–4) — field initializers [ADR-00180](../adr/ADR-00180.md); async methods + method-modifier parsing [ADR-00181](../adr/ADR-00181.md); instance generator methods [ADR-00182](../adr/ADR-00182.md); computed member names (constant string/number) [ADR-00184](../adr/ADR-00184.md); class expressions (nominal binding) [ADR-00185](../adr/ADR-00185.md). Deliberately deferred as clean rejections: static/async generator methods, well-known-symbol computed keys, `extends <expression>`, and a class expression used as a runtime value or with named self-reference
- **Date**: 2026-08-13

## Context

A per-file sweep of the full Test262 `language/` corpus (23,724 files, run through the actual compiler) shows the class area is the single largest concentration of in-scope failures by a wide margin:

| Directory | Failing | Passing |
|---|---|---|
| `language/statements/class` | 3,718 | 649 |
| `language/expressions/class` | 3,448 | 611 |
| (next largest: `for-await-of`) | 1,142 | 92 |

Class accounts for **7,166 failing files — 37% of all `language/` failures**, more than the next six directories combined. Of those, only 12 are negative tests we wrongly accept; **7,154 are positive tests blocked on a real feature**. Decorators (genuinely out of scope — needs metadata reflection, see [../status/README.md](../status/README.md)'s High-complexity table) account for only 20, so they are not the story.

Classes are already a shipped, core feature ([TDD-00009](TDD-00009.md), 15/15 on [LANGUAGE-CONSTRUCTS.md](../status/LANGUAGE-CONSTRUCTS.md)) — the base construction/method/inheritance machinery exists. Every blocker above is a **class-body member form the parser doesn't accept yet**, and each one is shared between class *declarations* (`statements/class`) and class *expressions* (`expressions/class`), so the same work counts twice. Grouping the 7,154 by first blocker (both dirs, decorators excluded):

| Blocked files | Blocker | Feature |
|---|---|---|
| 2,542 | `unexpected token class in expression` | Class expression position (`const C = class {…}`) |
| 952 | `expected IDENT, got *` / `expected (, got *` | Generator / async-generator methods (`*m()`, `async *m()`) |
| 727 | `expected IDENT, got async` | Async methods (`async m()`) |
| 511 | `expected }, got [` / `expected IDENT, got [` | Computed member names (`[expr]() {}`, `[expr] = v`) |
| 273 | `a destructured parameter requires an explicit type annotation` | Destructured method params — [TDD-00005](TDD-00005.md) territory, out of scope here |
| 202 | `expected :, got =` | Field initializers (`x = v`, `#x = v`) |
| 107 | `extends unknown class` | `extends <expression>` (non-identifier base) |

### The honest ceiling

The first-error counts above are **not** a flip estimate — they are an upper bound on what parses. [TDD-00061](TDD-00061.md) is the cautionary precedent: shipping generators moved `make conformance` by exactly **zero** files, because the corpus's generator tests probe real JS's dynamic object model (`.prototype`, `Object.getPrototypeOf`, `GeneratorFunction`) that this compiler's static representation has no equivalent for. The class corpus has the same trap in force: a large fraction of these files pull in `propertyHelper.js`/`verifyProperty` (property descriptors — enumerable/writable/configurable), `Object.getPrototypeOf`/`.prototype`/`.constructor`, well-known symbols (`Symbol.iterator`, `Symbol.hasInstance`, `Symbol.species`), or `new.target` — none of which the nominal fixed-shape class model can satisfy, and none of which this TDD proposes to add.

So the realistic flip count is **materially lower than 7,154** and is not knowable up front. That does not sink the work — it reshapes it. Two things remain genuinely valuable and are what this TDD optimizes for:

1. **Contained wins that flip real tests.** Field initializers and class expressions in binding position back tests whose assertions are plain value checks (`assert.sameValue`), which this compiler *can* satisfy — and field-initializer syntax is incidental in a huge number of otherwise-in-scope files.
2. **Removing class as a blanket parse gate**, so the genuine remaining gaps (the dynamic-model ones above) become individually visible rather than hidden behind a parse error — the exact framing that made [TDD-00060](TDD-00060.md)'s payoff measurable.

The recommendation (below) front-loads the contained wins and treats the heavy method/expression machinery as measure-then-continue, rather than assuming the full mass flips.

## Design

Four sub-features, staged so the cheapest/highest-incidental-value work lands first and the one architecturally-novel piece (class expressions) lands last, reusing everything before it. Each stage is independently shippable with its own ADR.

### Stage 1 — Field initializers (`x = v`, `#x = v`)

The most contained piece, and the one [TDD-00021](TDD-00021.md) explicitly deferred ("no field-initializer syntax — pre-existing, not `#`-specific"). Today a class field is parse-only `name: type;` with no initializer (see `parser/parser_classes.go`'s field branch and `ast.ClassDeclaration`'s doc comment: "Fields carry no initializers — initial values are assigned via `this.field = value` in the constructor").

- **Parser** (`parser_classes.go`): in the field branch, after the member name, accept an optional `= <assignment-expr>`. The type annotation becomes optional when an initializer is present (infer the field type from the initializer's `inferExprType`, same as a `let x = expr` with no annotation). Add an `Initializer ast.Expression` field to `ast.AnnotField`.
- **Codegen** (`emit_classes.go`): lower each initializer to an implicit `this.field = <expr>` prepended to the constructor body, **after** the synthesized/explicit `super(...)` call and before the user's constructor statements — matching the spec's field-initialization order. A class with field initializers but no explicit constructor gets the same synthesized default constructor path that already exists, with the initializers as its body. Private-field initializers reuse [TDD-00021](TDD-00021.md)'s existing `#x` storage slot unchanged; only the write site is new.
- **Scope cut**: initializer expressions that reference `this` are allowed (they run in constructor context where `this` is live); an initializer referencing a *later* field is a forward-reference the constructor-prologue ordering already resolves in declaration order — reject an initializer referencing a not-yet-initialized later field only if it falls out naturally, don't build TDZ machinery for it.

### Stage 2 — Method modifiers: `async` / `*` / `async *`

Parser first, then codegen, and codegen is the heavy part.

- **Parser** (`parser_classes.go` member loop): before the member name, detect a leading `async` (contextual — `async` is *also* a legal method name, so require the next token to be a member-name-start, mirroring the existing `get`/`set` 2-token disambiguation directly above it) and a leading `*`. Set `fn.IsAsync` / `fn.IsGenerator` on the `FunctionDeclaration` the member already produces — both flags already exist on the node and are already respected for top-level functions. `async *` sets both.
- **Codegen — async methods**: reuse the existing async-function lowering (`emit_func.go`) at method position. A method is already a `FunctionDeclaration` with an implicit `this`; the async transform composes with that the same way it composes with a top-level function.
- **Codegen — generator methods** (the genuinely new work): generators today are registered top-level-only, keyed by name in `e.generators`, and constructed via `emitGeneratorConstruction` (`emit_generators.go`) — there is no `this`. A generator *method* needs (a) a per-class dispatch key instead of a global name (the name-mangling scheme `registerClasses` already uses for ordinary methods and for [TDD-00030](TDD-00030.md) get/set), and (b) the instance `this` captured into the generator object's frame alongside its arguments, so the fiber body can reach `this.field`. The `ucontext.h` fiber primitive itself ([TDD-00006](TDD-00006.md) Part 2) is reused unchanged — only the construction path (what gets stored into the generator object) and the dispatch key change.
- **Scope cut**: `async *` (async generators) only after sync generator methods work and only if measurement justifies it — the whole `for-await-of`/async-generator corpus is separately gated on real async-iteration semantics this compiler doesn't have, so async-generator *methods* would parse-unblock tests that then fail at runtime regardless. Parse it, flag it, reuse the sync-generator path where possible, but treat runtime async-generator semantics as out of scope for this TDD.

### Stage 3 — Computed member names (`[expr]() {}`, `[expr] = v`)

This compiler dispatches methods **statically by name**; an arbitrary runtime-valued computed key is fundamentally incompatible with that and stays out of scope. The in-scope subset, mirroring object-literal computed keys ([TDD-00012](TDD-00012.md)):

- **Compile-time-constant string/number keys** (`["foo"]() {}`, `[0]() {}`): resolve the constant at parse/emit time to a fixed member name — indistinguishable from writing the name directly.
- **Well-known symbols** (`[Symbol.iterator]() {}`, `[Symbol.asyncIterator]() {}`): map each recognized well-known symbol to a fixed reserved method slot the iteration machinery already looks for. This is what the bulk of *real* computed-name class tests actually use.
- **Reject** any other computed method/field name (a non-constant, non-well-known-symbol expression) with a clean, specific diagnostic — not a parser crash.

### Stage 4 — Class expressions (`const C = class [Name] {…}`)

The one architecturally-novel piece, deliberately last so a class expression's body inherits Stages 1–3. Unlike function expressions ([TDD-00060](TDD-00060.md)), functions here are already first-class runtime values (closures), so a function expression evaluates to a real value. **Classes are not first-class values in this compiler** — a class name is a nominal, compile-time type, and there is no runtime constructor object to hand around. That difference dictates the scope.

- **Parser**: add `case lexer.CLASS:` to the primary-expression switch (`parser_literals.go`, directly mirroring the existing `case lexer.FUNCTION:` a few lines below the field branch). It reuses `parseClassDecl` (which already accepts an optional name via its `defaultName` parameter, the same hook `export default class {}` uses) and wraps the result in a new `ast.ClassExpression` node, analogous to `ast.FunctionExpression`.
- **Semantics — recommended V1: compile-time nominal binding, binding-position only.** `const C = class {…}` registers the (possibly anonymous, given a fresh synthetic name) class into the same nominal class table a `class C {…}` declaration populates, bound under the LHS name `C`. `C` is then usable exactly as a declared class name — `new C()`, `C` as a type annotation, `extends C`. This is the direct analog of [TDD-00060](TDD-00060.md)'s name-binding pass for classes, and it covers the overwhelming majority of the corpus's class-expression tests, which do `var C = class {…}; new C()` or probe the body's member semantics.
- **Out of scope (V1)**: a class expression used as a **runtime value** — passed as an argument, returned from a function, stored in an array of constructors, or an anonymous class expression in non-binding position. There is no first-class constructor value to produce; these are a clean, specific compile-time rejection, not silently mishandled. A named class expression's name-leakage rule (visible inside its own body, not outside) follows [TDD-00060](TDD-00060.md)'s V1 posture — defer the self-reference subset if it needs new scope machinery, reject cleanly until then.
- **`extends <expression>`** (the 107-file bucket): out of scope — the nominal model can only extend a named class. Clean rejection, noted here so it isn't rediscovered mid-implementation.

## Open questions

- **Generator-method `this` capture**: exactly how `this` rides into the fiber frame alongside the generator's arguments — a new slot in the generator object struct vs. threading it through the existing argument-store path. Resolve against `emitGeneratorConstruction`'s current layout at implementation time.
- **Field-initializer evaluation order with inheritance**: confirm the prologue lands after `super(...)` returns in a derived class (fields of a subclass initialize after the base constructor runs) and that this composes with the existing synthesized-default-constructor path without a second `super` call.
- **Stage 2 stop point**: whether async-generator *methods* are worth parsing+flagging at all given their runtime semantics are out of scope — decide after sync generator methods are measured against `make conformance`.
- **Realistic flip target**: unknown until Stages 1–2 are measured. Treat the 7,154 as a parse-unblock ceiling, not a goal; re-decide whether Stages 3–4 earn their cost from the Stage 1–2 conformance delta, per the [TDD-00061](TDD-00061.md) lesson.
