# TDD-00088: Microtask-accurate `await` ordering (`await` always yields a tick)

- **Status**: Implemented
- **Date**: 2026-08-20

## Context

`await` on an already-settled promise reads it synchronously instead of yielding a
microtask tick. Real JS always suspends the async function at every `await` — even
of an already-settled promise — and resumes it via a microtask, so code queued
before it (the caller's synchronous continuation, earlier `.then`/`queueMicrotask`
callbacks) runs first. Grounded:

```
async function f(): Promise<void> { console.log("a"); await Promise.resolve(1); console.log("b") }
f(); console.log("c")
// JS: a c b     — this compiler: a b c
```
```
console.log("1"); Promise.resolve().then(() => console.log("3"))
console.log("2"); await Promise.resolve(); console.log("4")
// JS: 1 2 3 4   — this compiler: 1 2 4 3
```

Root cause: a non-may-suspend ("inline") async fn (TDD-00084 Part A) runs straight
through with no suspension point, so `await` of a settled promise just reads the
value and continues. Only may-suspend fns (awaiting a fetch / another such fn) run
on a fiber and can park — and even they take a settled-await synchronously
(`__kml_task_await_ready` returns immediately when the promise is already settled).

This closes the last architectural async caveat and moves the `async` functions,
`await`, and `.then` rows toward strict.

## Design

**Unify `await` onto an "attach a resume reaction + park" model** — the same
reaction/microtask machinery `.then` already uses:

- Any async fn whose body **contains an `await`** runs as a coroutine task (a
  fiber), broadening the may-suspend classification from "awaits a
  fetch/combinator/may-suspend fn" to "contains any await". An async fn with **no**
  `await` (`async () => 5`) stays inline — it settles immediately, has no
  suspension point, and so has no ordering to get wrong.
- `await p` compiles to: attach a **resume-this-task** reaction onto `p`'s reaction
  list (field 4 — the list `.then` reactions live on), then **park** (swap to the
  scheduler/resumer). When `p` settles — immediately if already settled, or later
  when its own producer settles it — its reactions are enqueued on the microtask
  FIFO (`__kml_promise_drain_reactions`). When the FIFO drains, the resume
  reaction's runner **swaps back into the parked fiber** (like the scheduler's own
  resume), which then reads `p`'s value/rejection and continues past the `await`.
  So the resume is **always** a microtask tick, ordered after everything already
  queued — exactly JS's semantics, for both settled and pending `p`.
- Rejection is unchanged in spirit: on resume the fiber reads `p`'s state and
  re-throws a rejection at the `await` (fiber-safe exceptions).

**Why this is correct + minimal-ish:** it reuses three existing pieces — the
promise reaction list, the microtask FIFO, and the fiber scheduler's
swap-into-a-task — and only adds the glue: a "resume a parked task" microtask
closure, and an `await` that registers it instead of reading synchronously.

**Cost:** every async fn containing an `await` now links the fiber/task runtime
(the "no fiber for a pure-async program" property from TDD-00084 Part A relaxes).
`libcurl` is still linked only when `fetch` is used. The added weight is the
ucontext scheduler, not curl — acceptable for correct ordering.

## Stages

1. **Resume-reaction primitive.** A runtime microtask closure that swaps into a
   given task (`__kml_task_resume`), and an `await` lowering that attaches it to
   the awaited promise + parks — wired for the already-fiber (may-suspend) path
   first. Verify a may-suspend `await` now yields a tick.
2. **Broaden classification.** Every async fn with an `await` becomes a task; the
   inline path keeps only no-`await` async fns. Verify the inline-await cases
   (`f`/`main2` above) now order correctly (`a c b`, `1 2 3 4`).
3. **Top-level `await` + event loop.** A top-level `await` and the program-exit
   drain interleave microtasks, tasks, and timers in spec order.
4. **Regression + ordering battery.** The full async/generator/fetch suite stays
   green; a set of ordering tests (settled await, chained awaits, await vs
   `.then`/`queueMicrotask`, fire-and-forget) locks the semantics.

## Open questions

- **Settled-await fast path.** Keep a synchronous read for a settled await inside a
  fiber (faster, but wrong ordering), or always route through the microtask? For
  correctness: **always** route through the microtask.
- **Resume-context management.** The resume runner swaps into `task.ctx` from the
  microtask-drain context; the task must swap back to that context on its next
  park/finish. Confirm the resumerCtx bookkeeping matches the scheduler's.
- **Performance.** A fiber per awaiting async call. Acceptable for this target
  (CLI/microservices), but worth a note; a future optimization could keep a
  fast path for an async fn whose every await is provably already-settled *and*
  whose result is not observed across a tick — out of scope here.
