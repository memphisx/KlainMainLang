# ADR-00342: Promote top-level class-instance / Blob / Date bindings to module globals

- **Relations**: Extends [TDD-00093](../tdd/TDD-00093.md) (module-global promotion)
- **Date**: 2026-08-24

## Context

A named `function`/`async function` is emitted with its own fresh scope, so it
reads a top-level `const`/`let`/`var` only if that binding is promoted to an LLVM
module global (TDD-00093, `registerModuleGlobals`). That promotion already
covered scalars, strings, arrays, object literals, `Map`/`Set`, and
composite-returning calls — but its recognition gates (`reliableGlobalType` /
`promotableInitInPrePass`, `emit_exprs_vardecl.go`) did not recognize a
**`new`-expression** initializer. So `const c = new C()` and `const b = new
Blob(...)` stayed `main()` locals, and a named/`async` function referencing them
failed with `undefined variable` — the case that surfaced building the
`Blob.stream()` example (a top-level `Blob` used inside an `async` function).

The pre-existing status wording ("a top-level function can't reference a sibling
`let` at all") was stale — scalars/objects/`Map` already worked.

## Decision

Recognize a `new`-expression initializer that produces a single fixed slot as
promotable, computing its type via the canonical `inferExprType` and reusing the
storage paths that already honor `moduleGlobals` (`emitObjectVarDecl`, the
scalar/ptr fall-through in `emitVarDecl`). Two new helpers in
`emit_exprs_vardecl.go`:

- `promotableNewExpr(init)` — returns the type when `init` is a promotable
  `new`-expression: a **class instance** (`*ast.NewExpression`, excluding
  `Promise` and generic classes), or a builtin handle in the allowlist. It gates
  on a single fixed slot (`!IsArray && !IsDynamicObject`), which excludes 2-slot
  `{ptr,i64}` TypedArray/array aggregates.
- `isHandleNewExpr(init)` — the builtin allowlist: `Blob`, `Date`, `Error`,
  `URL`, `URLSearchParams`, `URLPattern`, `RegExp`, `Headers`, `ArrayBuffer`,
  `DataView`, `TextEncoder`, `TextDecoder`, `Request`, `AbortController`,
  `Event`, `CustomEvent`, `EventTarget`, the streams (`ReadableStream`/
  `WritableStream`/`TransformStream`/`CompressionStream`, the Node streams), and
  `EventEmitter`.

`promotableNewExpr` types the binding via `inferExprType`, which must therefore
be complete for these nodes. It was **not**: `inferExprType` lacked cases for
`NewAbortControllerExpression`/`NewEventExpression`/`NewCustomEventExpression`/
`NewEventTargetExpression`, so it fell back to the `i64` default and the global
was declared/typed as a scalar, losing `IsAbortController`/`IsEvent`/… — which is
why `ac.abort()` failed to dispatch even at top level. Completing those four
`inferExprType` cases (matching `emitVarDecl`'s own type assignments) fixed the
drift at its source, and those handles now promote correctly. This was a latent
`inferExprType`↔`emitVarDecl` inconsistency, not specific to promotion.

Both gate functions call it; the store side needs no change.

### Why the allowlist is curated, not "every handle"

Each handle earns its place by verification (a targeted construct + method/field
probe from a named function, then a full E2E-suite pass), not by membership in a
category. Two families needed a targeted fix to join:

- **Event handles** (`AbortController`/`Event`/`CustomEvent`/`EventTarget`) — see
  the `inferExprType` note above; the gap was a mistyped global, fixed at source.
- **Streams + `EventEmitter`** (`ReadableStream`/`WritableStream`/
  `TransformStream`/`CompressionStream`, the Node streams, `EventEmitter`) — each
  has a *dedicated* var-decl emitter (`emitNewReadableStream` + a local
  `alloca`/`define`/`store`, `emitEventEmitterVarDecl`, …) that always stored into
  a fresh local and ignored `promotedGlobalDecls`, so a promoted binding's global
  stayed null and a named function reading it saw an empty handle (a promoted
  `ReadableStream` silently dropped its chunks). A shared
  `storePtrHandleVarDecl(v, val)` helper makes all of them promotion-aware (the
  same branch `emitObjectVarDecl` already had), and `EventEmitter` also gained its
  missing `inferExprType` case.

Still excluded: the **connection handles** — `Worker`/`WebSocket`/`EventSource`
(construction opens a thread/socket, unsuited to a module-global-at-startup),
`BroadcastChannel`/`MessageChannel`, `XMLHttpRequest` — stay `main()` locals,
unchanged.

**Generic class instances and `TypedArray`s promote too:**

- **`TypedArray`** (`const buf = new Uint8Array([…])`) — a 2-slot `{ptr,i64}`
  `IsArray` value, promoted via the *same two-global (data + length)* path as a
  plain array (`registerModuleGlobals`'s `IsArray` branch, `emitArrayVarDecl`
  which already both constructs the TypedArray and honors the promoted globals).
  Only `reliableGlobalType` needed to recognize the `NewTypedArrayExpression`.
- **Generic class instance** (`const b = new Box<number>()`) — `inferExprType`
  computes its shape via `genericClassInstanceType` (a pure lookup), and
  `registerModuleGlobals` calls `instantiateGenericClass` to force the
  monomorphized class's *real registration* (methods/dispatch) before Pass 2
  emits the function bodies that call `b.get()`. Field access rides the type's
  own `Fields`; the method side needs that registration.

### Exclusions (unchanged behavior, clean `undefined variable`, never miscompiled)

- A generic instance with **inferred** type arguments (`new Box(5)`), or a
  **nested** generic (`new Box<Box<number>>()` — a pre-existing generic
  limitation, fails at top level too).
- `new Promise(...)` — task-promise semantics.
- The connection handle families (`Worker`/`WebSocket`/`EventSource`,
  `BroadcastChannel`/`MessageChannel`, `XMLHttpRequest`).

## Implementation notes

- `emit_exprs_vardecl.go`: `reliableGlobalType` returns `promotableNewExpr`'s
  type before its un-annotated switch; `promotableInitInPrePass` returns true for
  the same set. No storage-path edits — a class instance rides `emitObjectVarDecl`
  (already `moduleGlobals`-aware), `Blob` the same, `Date` the scalar
  fall-through (`emit_exprs_vardecl.go`'s single-slot global store).
- Ordering already holds: `registerModuleGlobals` (Pass 1.7) runs after
  `registerClasses` (0.5) and `registerFunctions` (1), so the types resolve.
- A same-named local still shadows the global (`lookup` checks scopes before
  `moduleGlobals`).

## Verification

- `tests/module_global_new_test.go`: a class instance with a mutating method
  read from a named function; the original top-level-`Blob`-in-`async` repro; a
  `Date`; the verified builtin handles (`Error`/`URL`/`URLSearchParams`/`RegExp`/
  `Request`/`ArrayBuffer`) read from a named function; `AbortController` staying a
  clean `main()`-local; local-shadows-global.
- Full E2E suite green with the full allowlist (the excluded families were
  filtered out precisely because they fail this suite); `go vet` clean.
- Machine: verified on Mac (arm64); platform-independent.
