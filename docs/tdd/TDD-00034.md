# TDD-00034: `TextDecoder` non-UTF-8 encoding support (staged)

- **Status**: Not Started
- **Date**: 2026-08-07
- **Notes**: Low priority throughout; Stage 4 (most WHATWG labels) not expected to ever be picked up

## Context

`TextEncoder`/`TextDecoder` shipped UTF-8-only in [ADR-00112](../adr/ADR-00112.md), a deliberate V1 narrowing: this compiler's strings are already raw UTF-8 byte buffers, so `encode`/`decode` were a direct byte copy with no real transcoding. Raised directly as a follow-on question ("how much effort is the rest of the non-UTF-8 work?") while discussing that ADR. This is explicitly low priority — done for completeness of the design record, not because any current use case needs it — so it's scoped here as a staged TDD rather than picked up now.

One asymmetry worth stating up front: real `TextEncoder` is UTF-8-only *by spec* — it has no encoding argument at all, so `.encode()` needs no further work regardless of what's decided below. Everything in this document is about `TextDecoder`'s input side only.

## Design

### Stage 0 (prerequisite, shared by every stage below): give TextDecoder real per-instance state

`IsTextDecoder` (`types.go`) is currently a stateless marker — `Ref` is always the constant `"null"`, and `new TextDecoder(label)` evaluates `label` for side effects and then discards it (`emitNewTextDecoderExpression`, `emit_call_encoding.go`). Once `.decode()`'s behavior needs to vary by encoding, that can no longer hold: a `TextDecoder` instance needs to remember which decoder it was constructed with.

Two options considered:

- **(a) Runtime tag.** Give `TextDecoder` a real 1-word heap allocation holding a small encoding-tag enum, set at construction by matching `label` against known label strings (the same `ensureStrcmp`-chain shape `emit_eventemitter.go`'s event-name dispatch and `emit_stmts.go`'s `switch` lowering already use), and read by `.decode()` to branch into the right decode implementation. Works for a `label` that's any runtime string expression, not just a literal — plausible for this compiler's CLI-tool focus (e.g. an encoding name read from `argv`/a config file).
- **(b) Compile-time resolution only.** Require `label` to be a string literal and resolve the decoder at compile time, erroring on a non-literal `label`. Less code, but a real capability regression from today (any expression is currently accepted, just ignored) and brittle for the CLI use case above.

**Recommendation: (a).** The marginal cost over (b) is small (one heap word, one `switch`), and it avoids narrowing what's already accepted today. An unrecognized label should keep today's permissive fallback (silently treat as UTF-8) rather than newly become a hard error — consistent with `atob`/`decodeURI`'s existing "permissive on malformed input, documented as V1 simplification" convention (`docs/status/GLOBAL-FUNCTIONS.md`).

This is genuinely shared prerequisite work, not part of any one stage — worth building once before Stage 1, not re-decided per stage.

### Stage 1: Latin-1 / windows-1252 — low effort

Labels: `"latin1"`, `"iso-8859-1"`, `"iso8859-1"`, `"l1"`, `"cp819"`, `"ascii"`, `"us-ascii"`, `"windows-1252"`, `"x-cp1252"`, and the rest of the WHATWG Encoding Standard's alias list for this encoding. Note a real spec quirk worth matching deliberately rather than "fixing": per the WHATWG standard, the `"iso-8859-1"` label (and its aliases) resolve to the **windows-1252** encoding, not textbook ISO/IEC 8859-1 — real browsers and Node's `TextDecoder` do this for web-compat reasons. The two differ in the 0x80–0x9F range (windows-1252 has printable characters there — curly quotes, en/em dash, ellipsis, trademark sign — where true ISO-8859-1 has C1 control codes). Implementing the windows-1252 table for both labels matches real-world `TextDecoder` behavior bit-for-bit; implementing "correct" ISO-8859-1 would not.

Mechanism: single-byte-to-UTF-8, table-driven — the same loop-with-lookup-table shape `ensureBase64Decode`/`ensurePercentDecode` (`runtime_encoding.go`) already use. Bytes 0x00–0x7F map to themselves (pure ASCII passthrough); 0x80–0xFF map through a 256-entry constant table to a Unicode code point, most needing a 2-byte UTF-8 encoding (U+0080–U+07FF) except a handful in the U+2000+ range needing 3 bytes. Each source byte maps independently — no cross-byte state, unlike Stage 2 — so a worst-case `len*3+1`-byte output buffer covers every input up front, the same over-allocate-then-track-`oi` pattern `ensureBase64Encode` already uses.

A UTF-8-codepoint-encoder helper (given an arbitrary Unicode code point, emit its 1–4-byte UTF-8 form) doesn't exist yet anywhere in this codebase and is worth writing once, shared with Stage 2 below (which needs the full 4-byte range; Stage 1 only ever needs up to 3).

### Stage 2: UTF-16 (LE and BE) — medium effort

Labels: `"utf-16le"`, `"utf-16"`, `"unicode"` (all little-endian by default per spec); `"utf-16be"` (big-endian).

Real variable-length transcoding, not table-driven: read 2 bytes per code unit (byte-swapped if BE), detect a surrogate pair (a high surrogate 0xD800–0xDBFF followed by a low surrogate 0xDC00–0xDFFF) and combine via the standard `0x10000 + (high - 0xD800) * 0x400 + (low - 0xDC00)` formula into a single code point above U+FFFF, then UTF-8-encode the result (reusing Stage 1's codepoint encoder, this time needing its full 4-byte range). Two cases need a defined *permissive* behavior, matching this project's established convention rather than throwing: a lone/unpaired surrogate (substitute the U+FFFD replacement character, `EF BF BD` in UTF-8) and a trailing odd byte (drop it silently, the same "drop the incomplete trailing group" precedent `ensureBase64Decode` already sets for a truncated base64 group).

More logic than Stage 1 (variable 1-or-2-code-unit consumption per iteration, output up to 4 bytes, surrogate arithmetic) but still fully self-contained — no lookup table at all, pure arithmetic.

### Stage 3: Greek — ISO-8859-7 and windows-1253 — low effort, done on principle rather than expected use

Requested to be scoped explicitly (ahead of Stage 4) for personal/cultural reasons, not because of an expected use case — noted here as-is rather than justified further.

Labels: `"iso-8859-7"`, `"iso8859-7"`, `"iso-ir-126"`, `"csisolatingreek"`, `"greek"`, `"greek8"`, `"ecma-118"`, `"elot_928"` all resolve to ISO-8859-7 (unlike Stage 1's `"iso-8859-1"`, this label is *not* redirected to a Windows codepage by the WHATWG spec — it resolves to itself); `"windows-1253"`, `"x-cp1253"`, `"cp1253"` resolve to windows-1253 separately. These are two distinct standard mapping tables (they disagree in several slots, not just the 0x80–0x9F range), so this stage is two more Stage-1-shaped tables, not one.

Mechanism: 100% reuse of Stage 1's generic single-byte-table decoder — the only new content is two 256-entry data tables (well-documented public Unicode mapping data for ISO-8859-7 and windows-1253) plus two new tag values and label strings feeding into Stage 0's dispatch chain. Genuinely cheaper than Stage 1's own first implementation, since Stage 1 has to build the shared machinery once; this is closer to "add a table" than "add a feature."

### Stage 4: everything else in the WHATWG Encoding Standard's label list — super low priority

Listed for completeness/honesty about what full spec compliance would require, not as committed work — matches this project's existing practice of naming a permanent ceiling explicitly (e.g. `Proxy`/`Reflect`, full vanilla-JS compatibility, `docs/status/README.md`'s "What Is NOT Implemented") rather than pretending the roadmap stops right after the useful part.

- **Remaining single-byte legacy codepages**: ISO-8859-2 through -16 (minus -7, done in Stage 3), windows-1250/1251/1254–1258, KOI8-R/KOI8-U, mac-roman, IBM866, and others. Each is individually cheap (another Stage-1/3-shaped table) but there are roughly twenty of them.
- **Multi-byte/stateful legacy CJK encodings**: Shift_JIS, EUC-JP, ISO-2022-JP, EUC-KR, GBK, gb18030, Big5. A different order of magnitude of effort from everything above — variable byte-length-per-character with lead/trail byte range rules, in ISO-2022-JP's case stateful escape-sequence-driven mode switching, and multi-thousand-entry mapping tables where a simple 256-entry array no longer suffices.

No realistic use case in this project's stated CLI/microservice direction motivates either half of this stage. Not expected to ever be picked up; kept as a stage only so this document doesn't quietly imply the label list ends at Stage 3.

## Open questions

- Whether an unrecognized/unsupported label should stay permissive (fall back to UTF-8, today's behavior) once several real encodings exist and "unsupported" starts meaning something more concrete — Design recommends staying permissive for consistency with `atob`/`decodeURI`, but this is worth re-confirming at implementation time rather than assuming.
- Whether Stage 0's runtime tag should be a bare `i64` enum or reuse `IsError`'s existing hidden-kind-tag convention (TDD-00013/ADR-00082) more directly for consistency — a small implementation-time call, not a design fork.
- Stage 4 is deliberately left without a "when would this get picked up" answer — realistically, never, unless a concrete use case appears that changes this project's priorities.
