# ADR-01106: Diagnostics with stable codes, and a parser that recovers from errors

- **Relations**: `Implements TDD-00230` (Phase 1, P1.3); `Extends ADR-01101`, `ADR-01105`
- **Date**: 2026-09-23

## Context

A parse error was a `fmt.Errorf` string, `line:col: message`, returned up
through every parse function to the first caller, which stopped. A file with
five mistakes reported one, and fixing it revealed the next. Nothing
downstream could tell one kind of error from another except by matching the
wording: the conformance runner buckets reasons by text, and the TypeScript
oracle can only compare accept against reject.

[TDD-00230](../tdd/TDD-00230.md) P1.3 asks for recovery through parsing
contexts, one error per position, and diagnostics taken from a message table
with a stable numeric code (TypeScript's where the condition is the same), a
severity, a byte span, related spans, a hint, the JavaScript error kind, the
Test262 phase and a structured payload, collected per file, with a
machine-readable output mode. Every later phase reports through the same
collection.

## Investigation

- **The error sites.** The parser built 97 errors (about 85 distinct
  messages), the scanner 17, the P1.5 type conversion 11; about 470
  `return nil, err` lines carried them up. Most sites already had the token at
  hand. Four messages had no position at all, and three pointed users at
  design documents (`see docs/tdd/TDD-00063.md Stage 3`, `(TDD-00085)`,
  `(see docs/tdd/TDD-00010.md)`), which runtime and compile-time messages must
  not do.
- **typescript-go's recovery** (`internal/parser/parser.go`,
  `parseListIndex`, `parseDelimitedList`, `abortParsingListOrMoveToNextToken`,
  `isListElement`, `isListTerminator`): every list records a parsing context;
  when the current token is not an element, the list either aborts (the token
  belongs to an enclosing list) or skips it. Element parsers never fail: a
  missing piece is synthesised and reported, and `parseErrorAtRange` drops a
  second error at the position of the last.
- **Our element parsers do fail**, often part-way through syntax that is
  valid but not implemented (`[await x]() { … }` fails at `[` with "a computed
  class member name must be a constant"). Resynchronising token by token from
  there treats the rest of that member as list elements: a Test262 file with
  two such members reported seven errors, the first at the enclosing `try`.
- **Speculation.** The parser speculates in two places only: explicit call
  type arguments (`f<T>(x)` against `a < b > (c)`) and the `(T) =>`
  function-type-or-group choice (ADR-01105). Arrow functions are recognised
  by token look-ahead. Neither speculative region contains a statement or
  member list.
- **Consumers of the error text**: `main.go` prints it; the resolver prefixes
  the file; the three conformance runners bucket the reason and extract a
  blocker from it; the Go tests match substrings of it.

## Decision

- **A `diag` package.** `Message{Code, Severity, Kind, Phase, Text}` and a
  table of 105 messages (`diag/messages.go`). Codes below 90000 are
  TypeScript's and are used only where the condition is the one TypeScript
  reports under that code (TS1005 "'X' expected", TS1109 "Expression
  expected", TS1268 for an index-signature key, TS2392 for a second
  constructor, …); 90001 up are this compiler's (constructs it does not
  implement, and its own JSDoc annotations). The wording stays this
  compiler's. `Diagnostic{Message, Text, Span{File, Pos, Start, End},
  Related, Hint, Payload}`; `Error()` renders `line:col: text` exactly as
  before, so every existing message reads the same. `List` keeps a file's
  diagnostics and drops a second one at the position of the last. `Errors`
  is a set used as an error, one line per diagnostic, each naming its file.
- **Every error the scanner, the parser and the type conversion report is a
  diagnostic** built from the table, with the token's byte range (a node's,
  for the type conversion; a position reported at a node gets its offset from
  the line table). The four position-less messages gain a position except the
  unterminated template literal, which keeps its old text. The document
  references are removed from the three messages.
- **Recovery through parsing contexts.** The statement lists of a file, a
  block and a switch clause, and the member list of a class, each record their
  context and catch their elements' errors (`parser/recovery.go`). After
  reporting, the list resynchronises:
  - an element that failed on its first token, though that token can start
    one, skips it;
  - skipping steps over a bracketed group whole;
  - the list resumes at its terminator, or at a token that can start its next
    element **at an element boundary** (after a `;` or a `}`, or on a new
    line), and aborts to the enclosing list at a boundary token that belongs
    to it instead.

  The boundary rule is the adaptation to element parsers that fail
  mid-element: the rest of a failed member is skipped as a unit, and the
  Test262 file above reports its two real errors and nothing else.
- **Speculation is untouched.** While a speculative parse is in progress no
  list recovers, so a failure still reaches the caller that tries the other
  reading.
- **Input the scanner cannot read** is reported in place of the parse error
  it causes, as before: once the unreadable token has been scanned, the next
  parse error is replaced by the scanner's diagnostic, and later ones are
  dropped (past it the parser sees only the end of input). Errors reported
  before it stay.
- **Order.** Diagnostics are kept in source order, as `tsc` prints them.
  'catch' or 'finally' expected (TS1472) is reported at the token where the
  clause was expected, as TypeScript does, not at `try`: a statement's own
  errors, found first, must not sort after it.
- **Output.** The resolver attributes a file's diagnostics to it. The driver
  prints one `klainmain: parse error: file: line:col: message` line per
  diagnostic, or, with the new `-diagnostics=json`, an array on stdout with
  each diagnostic's code, severity, file, line, column, byte range, message,
  JavaScript error kind and phase. The conformance runners bucket reasons and
  blockers by the first diagnostic.

## Implementation notes

- **New:** `diag/diag.go`, `diag/messages.go`, `diag/diag_test.go`,
  `parser/recovery.go`, `parser/recovery_test.go`,
  `tests/diagnostics_cli_test.go`.
- **Changed:** `lexer/lexer.go` and `lexer/token.go` (`Token.Err`,
  `Lexer.Offset`), every `parser/*.go` error site, `ast/type_convert.go`,
  `resolver/resolver.go`, `main.go`, `tools/conformance/{main,node,ts}.go`,
  `README.md` (the flag).
- **The class member loop** became a closure per member so a member's error
  can be recovered; its `continue`s return nil. The rewrite was mechanical and
  checked against a brace-aware scan that leaves inner loops and function
  literals alone.
- **Checks that run after a list** see its recovered elements. An overload
  group left open by a member's error is closed by that error, so the
  class-level "has no implementation" check does not report it a second time.
- **A token the parser builds itself** (a computed member name's desugared
  token) has no byte range; `errAt` then takes the offset from the line and
  column, so such a diagnostic still sorts into place.

## Side effects discovered

- **An unterminated string literal at the end of the input was accepted** as
  a string running to the end, and a carriage return inside one was accepted
  too. Both are now the unterminated-string error (TS1002), as in Node and
  TypeScript; Test262's `line-terminators/invalid-string-cr.js` now passes.
- **A `;` between class members was rejected** (`m() {};`, `class A { ; }`).
  It is the empty class element.
- **A computed `["constructor"]` key was taken for the constructor**, so a
  class with both it and a real constructor was rejected as having two. It is
  an ordinary method; the constructor's function symbol moved from
  `@Class_constructor` to `@Class__kml_ctor`, in the reserved namespace, so
  that method's own `@Class_constructor` cannot collide with it.
- **Next consumer, not done here:** Test262's negative parse tests count any
  rejection as a pass. With each diagnostic's kind and phase available, the
  runner can require a `SyntaxError` in the parse phase; a rejection for an
  unimplemented construct would then stop counting.

## Verification

All on macOS arm64 (M4):

- **First diagnostic against the P1.5 parser, whole corpus** (59,519 files:
  examples, tools, apps, tests, Test262, and the source strings embedded in
  the Go tests). On every file that failed before and still fails, the first
  diagnostic is the old error, except:
  - 63 files whose first error was the rejected class-member `;`: they now
    reach their next error;
  - four `try` statements without a clause, now positioned at the missing
    clause (TypeScript's position);
  - the three messages whose document references were removed, and the
    positions added to "expected ] in …" and the class overload message.

  184 Test262 files that failed now parse (the class-member `;` and the
  computed `["constructor"]` method). The only real source that changed from
  parsing to failing is Test262's `invalid-string-cr.js`, a negative test;
  59 fragments cut from Go test files at backquotes (not programs) now end in
  an unterminated string. The two ASTs that changed on files parsing on both
  builds are Test262's computed `["constructor"]` method tests. 2,444 files
  report more than one diagnostic.
- `go test ./diag ./parser ./lexer ./ast`: recovery in statement, block,
  switch-clause and class-member lists; one error per position; the scanner
  rule; speculation unchanged (`(): (number[]) => []`, `a < b > (c)`,
  `f<number>(1)`); byte spans and codes; the JSON writer.
- `tests/diagnostics_cli_test.go`: the driver prints every error of a file,
  one line each, and `-diagnostics=json` gives their codes, byte ranges, kind
  and phase.
- `tests/classes_test.go`: the empty class element and the computed
  `["constructor"]` method print what Node 26.10.0 prints.
- `make examples`: 358 passed, 0 failed (together with ADR-01107).
- `make conformance` (with ADR-01107): strict 7,084 / 53,578 (in scope
  6,921), js 7,669 (in scope 7,471), 11 more than the P1.6 run in each lane
  (the class-member `;`, the computed `["constructor"]` method, the
  unterminated string). Invalid IR unchanged (strict 1, js 5); no timeouts.
- `make test-par` (with the other of the two): passes apart from the four
  known macOS `-mm=gc` thread-local-root failures in
  `tests/task_reclaim_gc_tls_test.go`. An earlier run hit the known flaky
  `TestE2EHTTPServerListeningEvent` hang (BACKLOG §0 item 1), which then
  passed six times of six alone; another timed a shard out while a second
  heavy job ran beside it.
