# TDD-00074: `bigint` — arbitrary-precision integers behind a selectable backend

- **Status**: Implemented
- **Date**: 2026-08-18
- **Notes**: V1 ships the backend-agnostic `__kml_bigint_*` ABI + full operator/typeof/print/`BigInt()` surface, with two backends selected by `-bigint=libtommath|gmp`. Default is **`libtommath`** (public domain), not the doc's `libbf` (MIT), which needs vendoring and is deferred — the ADR records why. Fixed `i128` rejected (silent overflow); hand-rolled `native` and cross-type `number` comparison deferred. Each backend is an embedded C file compiled alongside the program (the `gcshim.c` pattern)

## Context

`bigint` is the last unimplemented primitive on `docs/status/TYPE-SYSTEM.md`'s Type-primitives table (`❌`, and the sole gap keeping that category at 11/12). In JavaScript/TypeScript it is a distinct primitive type — *not* a bignum library object — with its own literal syntax (`123n`), its own `typeof` tag (`"bigint"`), a dedicated operator set that is **deliberately non-interoperable with `number`** (mixed `bigint + number` is a `TypeError`), and arbitrary precision (`10n ** 100n` is exact, no overflow). It also unblocks `BigInt64Array`/`BigUint64Array` (tracked as blocked on this in `docs/status/BINARY-DATA-TYPED-ARRAYS.md`).

Scoping it now because it is the remaining primitive gap, and because — unlike most features — its central design question (*how are the digits represented at runtime?*) has several genuinely legitimate answers spanning a **zero-dependency ↔ external-library ↔ raw-speed ↔ correctness** spectrum, no single one of which is right for every program. That is exactly the situation the existing `-regex=`/`-mm=`/`-globals=` whole-program mode selectors already model: expose the choice as a flag rather than hard-coding one representation. This document scopes the representation options, the backend-agnostic architecture that makes multiple representations cheap to offer, the `-bigint=<backend>` flag, and the language surface; implementation is a separate, staged follow-on.

## Design

### The representation question

Five representations were weighed. They divide into one recommended family (external arbitrary-precision C library, which the flag selects among), one deferred family (hand-rolled native), and one rejected option (fixed-width).

**Rejected — fixed `i128`.** LLVM has native `i128`, so arithmetic is one instruction and there is no dependency or heap allocation. But it silently overflows past ±2^127: `10n ** 100n`, large factorials, and crypto-size integers produce wrong answers with **no error**. That is precisely the "silent divergence from real JS/TS that is fixable" the project's guiding principle says to fix rather than ship, and it is worse than incomplete — `typeof x === "bigint"` and printing `123n` both look correct, so it passes casual tests and fails exactly the workloads `bigint` exists for. It is also *not* interchangeable with the other representations: being a value type, it cannot hide behind the opaque-pointer ABI below without being boxed (throwing away its only advantage). Excluded entirely — a backend labelled `bigint` should never overflow.

**Recommended family — an external arbitrary-precision C library.** This is the same call already made for RegExp (delegate the hard engine to a mature C library, PCRE2, rather than hand-rolling it — TDD-00035) and for `fetch` (libcurl): link a proven library **conditionally, only when the feature is actually used**, via the existing `requireLink` plumbing (ADR-00020). The genuinely hard parts of a bignum — division/modulo (Knuth Algorithm D), exponentiation, and base-10 conversion for printing — come correct and fast for free. The one real reservation is *which* library, because they differ in license and speed:

| Backend | License | Speed | Handle type | Notes |
|---|---|---|---|---|
| **libbf** (Fabrice Bellard, QuickJS) | **MIT** | good | `bf_t` (+ a `bf_context_t`) | Small; **purpose-built to back a JS engine's BigInt**; also does arbitrary-precision floats (a possible future path). The default. |
| **gmp** | **LGPL** v3 / GPL v2 | **fastest** | `mpz_t` | Decades-optimized. LGPL adds distribution obligations under static linking (see Open questions) — the reason it is not the default. |
| **libtommath** | **public domain** | good | `mp_int` | Zero licensing considerations of any kind; simple API. The choice when public-domain matters most. |

All three give **real arbitrary precision** (identical correctness); they trade only license against raw speed, which for CLI-tool/microservice `bigint` workloads is very unlikely to bind. `libbf` is the default on two grounds: MIT (no copyleft) and its literal design purpose (a JS engine's BigInt).

**Deferred family — hand-rolled native bignum.** A from-scratch `{sign, len, limbs[]}` implementation is the only option that keeps compiled programs pure-libc (matching the "programs are pure libc by default" ideal most literally), with no per-machine install, no static-link obligation, and no license question. But it is substantial, high-risk engineering (correct multiplication/division/mod, sign handling, carry propagation, and a division-heavy base-10 printing loop), it reinvents a mature wheel against the RegExp precedent, and it is slower than the C libraries unless heavily optimized. It is **not rejected** — it is a legitimate future backend (`-bigint=native`) that the architecture below makes addable *without touching any codegen*, but it is out of scope for the first delivery.

### The backend-agnostic ABI (the key architectural decision)

The flag is only cheap if adding a backend does **not** mean re-writing the operator, `typeof`, stringification, and JSON codegen once per backend. So: write all of that codegen **once** against a fixed internal ABI over an **opaque `ptr` handle**, and make each backend a single self-contained runtime template that implements that ABI. The codegen never knows which library is underneath — the same discipline `resolveArrayForHOF` uses to hide two array shapes behind one interface, and the `ensure*()` runtime-template pattern (`runtime_regexp.go`, `runtime_fetch.go`) uses to emit a C-backed surface.

The ABI (uniform signatures; every operand and result is an opaque `ptr` to a heap handle):

```
__kml_bigint_from_str(ptr digits, i64 len, i32 radix) -> ptr   ; 123n literal, BigInt("…")
__kml_bigint_from_i64(i64)                            -> ptr   ; BigInt(123), number→bigint
__kml_bigint_to_i64(ptr)                              -> i64   ; Number(bigint) (lossy, as in JS)
__kml_bigint_to_str(ptr, i32 radix)                  -> ptr   ; printing, .toString(radix)
__kml_bigint_add/sub/mul/tdiv/mod/pow(ptr, ptr)      -> ptr   ; + - * / % **  (/ truncates toward 0)
__kml_bigint_and/or/xor(ptr, ptr)                    -> ptr   ; & | ^  (two's-complement)
__kml_bigint_shl/shr(ptr, ptr)                       -> ptr   ; << >>  (>>> is a TypeError — see surface)
__kml_bigint_neg(ptr) / __kml_bigint_not(ptr)        -> ptr   ; unary - and ~
__kml_bigint_cmp(ptr, ptr)                           -> i32   ; <0/0/>0, drives < > <= >= == ===
```

- **Codegen surface (written once, backend-agnostic):** a new `emit_bigint.go` (mirroring `emit_symbol.go`) plus new `IsBigInt` branches in `emit_exprs_operators.go` (`emitBinary`/`emitArith`/`emitUpdate`/`emitUnary`), `typeofString`, `emitValueToString`/`emitConsolePrintVal`, and `emit_call_json.go`. Each calls the ABI; none references a specific library.
- **Backends (one file each, the only per-backend code):** `runtime_bigint_libbf.go`, `runtime_bigint_gmp.go`, `runtime_bigint_tommath.go`. Each emits its library's implementation of the ~15 ABI functions, plus the `declare`s for the underlying C calls (via new `ensureBigint*` helpers in the `runtime_core.go` style), plus one `requireLink("bf"|"gmp"|"tommath")` so `-l…` appears only when a program actually uses `bigint`. The handle representation (`bf_t`/`mpz_t`/`mp_int`) is private to the template and hidden behind the `ptr`.
- The emitter selects one template from a new `e.bigintBackend` field. **Stage 0 is the whole cost**: the lexer/type/inference groundwork, the ABI, all the shared codegen, *and the first backend*. The second and third backends are bounded ~15-function templates against an already-proven ABI — additive, no codegen change. This is what makes "three backends now, `native` later" tractable rather than 3–4×.

### The `-bigint=<backend>` flag

Following the `-mm=`/`-globals=`/`-regex=` convention exactly — a whole-program compile-time selector:

- **`libbf`** — MIT, JS-BigInt-designed, small. **The default** (`-bigint` unset resolves here).
- **`gmp`** — LGPL, fastest. Explicit opt-in for compute-heavy programs whose distribution model can absorb the LGPL obligations (Open questions).
- **`libtommath`** — public domain. Explicit opt-in when avoiding any copyleft/notice obligation is the priority.
- *(future)* **`native`** — the deferred hand-rolled zero-dependency backend; lands as a pure runtime template behind the same ABI, no codegen change.

Because every backend implements the same ABI with the same semantics, the flag changes **only** the linked library and its performance/license profile — never a program's results. That is the property that makes it safe to expose as a knob rather than a silent implementation detail (unlike `-regex`, where the modes are deliberately *different* semantics; here they are deliberately *identical* semantics, different implementations).

### Memory-management integration (per backend)

Each `bigint` is a heap handle plus the library's internal limb storage; both must land on the active memory mode's allocator so that `-mm=gc` can collect unreachable bigints and `manual` behaves like everything else (never freed — the default posture). The libraries differ in how cleanly their allocator can be redirected, which is a real per-backend caveat, not a uniform given:

- **libbf** — `bf_context_init(ctx, realloc_cb, opaque)` takes a realloc callback; route it to `malloc`/`realloc` (`manual`) or `GC_malloc`/`GC_realloc` (`gc`). Clean.
- **gmp** — `mp_set_memory_functions(...)` installs custom alloc/realloc/free at runtime; same routing. Clean.
- **libtommath** — the stock system library allocates through compile-time `MP_MALLOC`/`MP_REALLOC`/`MP_FREE` macros with **no runtime hook**, so a linked distro `libtommath` allocates via stdlib `malloc`. Fine under `manual`; under `-mm=gc` its limbs live off-GC-heap and would not be collected. Resolution options (Open questions): document a `gc`-mode leak caveat for `libtommath`, or vendor a `libtommath` built with GC hooks. This does not affect `libbf`/`gmp` and does not gate the default.

The handle struct itself is allocated by the wrapper on the same allocator (via `ensureMalloc`/the GC allocator already threaded through the codegen), so handle and internals stay consistent.

### Language surface and semantics

Bounded to match real JS/TS, with this compiler's usual "clean compile error, not silent coercion" posture where JS would throw a runtime `TypeError`:

- **Literals** — `123n`, `0x1fn`, `0b…n`, `0o…n`, and numeric separators (`1_000n`). A trailing `n` after any integer literal; **not** valid on a float (`1.5n` is a SyntaxError, as in JS). Lexer recognizes the suffix and emits a new `BIGINT` token; the literal compiles to a `__kml_bigint_from_str(interned-digits, len, radix)` call at its evaluation point (interning the digit string; a build-once cached global is a possible later optimization).
- **`typeof`** → `"bigint"`.
- **`BigInt(x)`** — from an integer `number`/`i64` (`from_i64`; a non-integer number is a `RangeError` in JS → clean compile error where statically knowable, else runtime), from a string (`from_str`), from a boolean. **`Number(bigint)`** back via `to_i64` (lossy for large values, matching JS).
- **Operators** — `+ - * / % **` (with `/` truncating toward zero, JS `BigInt` semantics, *not* float division), `& | ^ ~` (two's-complement over arbitrary precision — the library's logical ops), `<< >>`, unary `-`, `++`/`--`. **`>>>` is a `TypeError` on bigint in JS** → clean compile error. **Unary `+` on a bigint is a `TypeError`** in JS → clean compile error.
- **Mixing with `number`** — `bigint + number` (and every mixed arithmetic/bitwise op) is a `TypeError` in JS. As a statically-typed compiler this is a **clean compile error** at the operator site — strictly better than a runtime throw, and it falls out naturally from the `IsBigInt`-vs-`i64` type check in `emitBinary`. This replaces the position `symbol` occupies today (the reject-all-but-`===` guard at `emit_exprs_operators.go:64`) with a real bigint operator path.
- **Comparisons** — `< > <= >=` and `===`/`!==` between two bigints via `cmp`. `10n === 10` is `false` (different types) and `10n === 10n` is `true`, both static. Cross-type numeric comparison (`10n < 5`, `10n == 10` — legal and meaningful in JS) is **deferred** to keep V1 tight (Open questions); same-type only in V1.
- **Printing** — the `symbol` precedent exactly: `console.log(10n)` prints `10n` (console path appends `"n"`), while `String(10n)` / template-literal `` `${10n}` `` yield `"10"` (no suffix). Both call `__kml_bigint_to_str`; only the console branch adds `n`. This is the documented split between `emit_call_console.go` and `emitValueToString`.
- **`JSON.stringify(bigint)`** — a `TypeError` in JS ("Do not know how to serialize a BigInt"). Mirror `symbol`'s existing JSON path (`emit_call_json.go`), which already rejects.
- **Out of scope (noted, not built):** `BigInt64Array`/`BigUint64Array` (this feature unblocks them; a separate follow-on riding the TypedArray machinery), `BigInt.asIntN`/`asUintN`, and cross-type `number`↔`bigint` comparison.

### Codebase grounding (where each piece lands)

- **Lexer** — `lexer/lexer.go:370` `readNumber`; add trailing-`n` recognition at each return path (hex/bin/oct/decimal), emitting a new `BIGINT` token (`lexer/token.go:8` enum + `tokenNames`). `1.5n` rejected.
- **AST/inference** — `ast/nodes.go:440` `NumberLiteral` (a `Bigint bool` flag, or a new `BigIntLiteral` node); `inferExprType` numeric-literal case at `emit_exprs_types.go:246` returns `BigIntType()`.
- **Type system** — `codegen/llvm/types.go`: new `IsBigInt` flag (mirror `IsSymbol`, `:163`), `BigIntType()` constructor (mirror `SymbolType()`, `:414`; `IR:"ptr"`), a `TypeBigInt` var (`:1230` block), and `ResolveTypeName` `case "bigint":` (`:1280`/`:1292`).
- **Operators/typeof** — `emit_exprs_operators.go`: `IsBigInt` branches in `emitBinary` (`:150+`), `emitArith` (`:463+`), `emitUpdate` (`:408`), `emitUnary` (`:366`, reject unary `+`); `typeofString` `:353` → `"bigint"`.
- **Stringification/console/JSON/typeof-dynamic** — `emit_exprs_types.go:36`, `emit_call_console.go:84`/`:378`, `emit_call_json.go`, `emit_dynamic.go` (dynamic `typeof` tag).
- **Call dispatch** — `emit_call.go` (`case "BigInt":`), `emit_exprs_vardecl.go` (var-decl type inference).
- **Runtime/linking** — new `runtime_bigint_*.go` templates + `ensureBigint*` decls (`runtime_core.go` style) + `requireLink(...)` (`emitter.go:538`); `LinkLibs()` → `main.go:106` already turns them into `-l…`.
- **Flag plumbing** — new `-bigint=<backend>` CLI flag threaded to a `bigintBackend` emitter field (mirror `-regex`/`-mm` threading); the conformance harness link path (`tools/conformance/main.go`) mirrors `main.go`'s.
- **Reserved names** — `resolver/reserved_names.go` (register `BigInt`, alongside `Number`/`String`/`Symbol`).

### Recommended staging

- **Stage 0 — foundation + `libbf` (default).** Lexer `123n`, `BIGINT` token, `IsBigInt`/`BigIntType()`/`ResolveTypeName`, `inferExprType`, the full ABI, all backend-agnostic codegen (operators, mixing-as-compile-error, `typeof`, printing split, `BigInt()`/`Number()`, JSON-reject), the `-bigint=` flag defaulting to `libbf`, and the `libbf` runtime template with its memory-mode allocator hook. Ships a complete, conformant `bigint` on one backend. E2E test (`tests/*_test.go`) + example (`examples/`) as required for any new language feature.
- **Stage 1 — `gmp` backend.** One runtime template (`runtime_bigint_gmp.go`) + `requireLink("gmp")` + `mp_set_memory_functions` hook; `-bigint=gmp` lights up. No codegen change.
- **Stage 2 — `libtommath` backend.** One runtime template + `requireLink("tommath")`; `-bigint=libtommath` lights up. Resolve the `gc`-mode allocator caveat (document vs. vendor). No codegen change.
- **Future (own TDD/ADR when picked up)** — `native` hand-rolled zero-dependency backend; cross-type `number`↔`bigint` comparison; `BigInt64Array`/`BigUint64Array`; `BigInt.asIntN`/`asUintN`.

Each stage is independently shippable and independently verifiable with a focused example; `--static`/scratch-container linking is verified per backend the way RegExp Stage 6 (ADR-00120) verified PCRE2.

## Open questions

- **GMP LGPL obligations under static linking.** Dynamic linking (the normal build) is light: ship the license text, state GMP is used and is LGPL, keep its notices — the user can already swap `libgmp.so`. Static linking (`--static`/scratch containers) is heavier: LGPL v3 §4 requires giving the user the means to relink (ship your own object files or source against which they can substitute a modified GMP — object files suffice; the app need not be open-sourced). This bites only when distributing a *closed, statically-linked* binary using `-bigint=gmp` to third parties; for the project's own CLI tools / internal microservices it is effectively moot. It is the reason `gmp` is not the default, not a reason to exclude it — `libbf` (MIT) and `libtommath` (public domain) carry none of this. Confirm whether `--static` + `-bigint=gmp` should be a clean compile-time rejection (steering users to `libbf`/`libtommath` for static builds) or allowed-with-a-warning.
- **`libtommath` under `-mm=gc`.** No runtime allocator hook (see Memory-management). Resolve at Stage 2: a documented `gc`-mode leak caveat (bigint limbs allocated off-GC-heap), or vendor a `libtommath` compiled with GC hooks. Does not affect the default.
- **Cross-type `number`↔`bigint` comparison.** JS allows `10n < 5` and `10n == 10` (true) even though `10n === 10` is false. V1 scopes comparisons to same-type; whether to add mixed comparison (via conversion) or leave it a clean compile error is a Stage-1+ call — mixed *arithmetic* stays a compile error regardless (matches JS's `TypeError`).
- **Literal materialization strategy.** Build each `123n` via `from_str` at its evaluation point (simple, V1) vs. a build-once cached global (avoids re-parsing a literal in a loop). Start simple; revisit if it shows up in a profile.
- **`Number(bigint)` / `BigInt(number)` rounding-and-range edges.** `Number(huge_bigint)` is lossy in JS (nearest double); `BigInt(1.5)` is a `RangeError`. Confirm the non-integer-`number`→`bigint` case is a clean compile error where statically knowable, and the runtime path otherwise.
- **Flag/value names.** `-bigint=` vs `-bignum=`; `libbf`/`gmp`/`libtommath` vs shorter aliases (`bf`/`gmp`/`tommath`). Should read naturally alongside `-mm=`/`-regex=`/`-globals=`.
- **Default-backend availability on the build machine.** If `-bigint` is unset and `libbf` is not installed, the error should name the missing library and the flag, and point at the alternatives — not fail as an opaque linker error.
