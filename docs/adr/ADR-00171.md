# ADR-00171: Generator function front-end (`function* f() { yield x; }` lexer/parser/AST) — parses, cleanly rejected by codegen

- **Relations**: Implements the front-end slice of [TDD-00061](../tdd/TDD-00061.md)
- **Date**: 2026-08-12

## Context

[TDD-00061](../tdd/TDD-00061.md) scoped generator functions but deliberately deferred the actual suspend/resume codegen (a materially larger piece of work reusing this compiler's existing `ucontext`-based fiber primitive). This ADR picks up the first slice: `yield` doesn't exist at any layer of this compiler today (not a lexer token, not a contextual keyword, not an AST node), and `function*`/`yield`/`yield*` all fail to parse. Per direct instruction, this pass builds the real lexer/parser/AST support — the front-end surface TDD-00061 identified as needed regardless of which codegen approach eventually gets built — while explicitly not touching codegen beyond what's needed to keep this compiler's own "parses now, cleanly rejected, never silently mishandled" standard intact.

## Investigation

**Where `yield` binds precedence-wise**: real JS's own grammar makes `YieldExpression` itself an `AssignmentExpression` production — lower precedence than the ternary/logical/comparison/arithmetic chain, so `x = yield y` parses as `x = (yield y)`, not `(x = yield) y`. Confirmed this compiler's `parseAssignment` (`parser_exprs.go`) is the right insertion point: it already calls `parseTernary()` and then checks for assignment operators, so intercepting *before* that descent — rather than adding a new case within the ternary/logical chain — is what makes `yield`'s own operand able to consume a full `AssignmentExpression` (via a right-recursive `parseAssignment()` call), matching the spec shape.

**Hard keyword vs. contextual keyword**: real JS treats `yield` as contextual — a valid ordinary identifier outside a generator body (and in non-strict mode generally), reserved only inside one (and always in strict mode). This compiler already made the identical tradeoff for the closest analogous case, `await` (`AWAIT` is a hard, unconditionally-reserved lexer keyword in `lexer/token.go` — never usable as a plain identifier anywhere, even outside an `async` function), rather than threading enclosing-function-kind context through the parser the way real engines do. Confirmed no such context-tracking mechanism exists anywhere in this parser for anything else either (`this`-only-in-a-method, `break`-only-in-a-loop, and the like are all enforced at *codegen* time against the emitter's own per-function state, never at parse time) — so making `yield` contextual would mean introducing a wholly new kind of parser state this codebase doesn't otherwise have, just for this one keyword. Decision: match the `await` precedent exactly (hard keyword), not a new mechanism — see Side effects for the real, measured conformance cost of this choice.

**Silent-miscompile risk, confirmed by direct testing before deciding where to guard**: a `function* gen(): number { return 42; }` (legal, if unusual, real JS — a generator with no `yield` at all, which just runs to completion on the first call) was directly tested with no codegen-level guard in place: it silently compiled and *ran* as an ordinary function, no error at all — `IsGenerator` was parsed correctly but never checked anywhere downstream. Likewise, a bare `yield 1;` inside a non-generator function, with no guard on the expression side, silently compiled as a void no-op. Both are exactly the "parses now, silently mishandled" failure mode this project's conventions treat as worse than a clean rejection — closed by two checks, not left as a known gap, even though this ADR is scoped to "front-end support."

## Decision

1. `lexer/token.go`: new `YIELD` token, added to the keyword table exactly like `ASYNC`/`AWAIT` — `yield` can never be used as a plain identifier anywhere in this compiler (matching `await`'s own existing scope, not real JS's narrower "reserved only inside a generator" rule).
2. `ast/nodes.go`: `FunctionDeclaration.IsGenerator bool`; new `YieldExpression{Argument Expression /* nil for bare yield */, Delegate bool /* yield* */}`.
3. `parser/parser_stmts.go`'s `parseFunctionDecl`: `p.match(lexer.STAR)` right after consuming `function`, before the name — covers both `function* name()` and `async function* name()` (the latter already routes through `parseFunctionDecl(isAsync=true, ...)`). Scoped to this one call site only — not class methods (`parser_classes.go`), not object-literal methods or function expressions (`parser_literals.go`'s separate `case lexer.FUNCTION:`) — matching TDD-00061's own V1 scope (top-level/nested function declarations only).
4. `parser/parser_exprs.go`: new `parseYield`, called from `parseAssignment` when the next token is `YIELD`. Handles `yield*` (delegate), a bare `yield` with no operand (same ASI "no line terminator" restriction `return`/`break`/`continue` already use, plus a check against every token that can legally follow a yield-with-no-operand in expression position — `)`, `]`, `}`, `,`, `:`, in addition to `;`/EOF, since `yield` can appear inside a call's argument list or a literal, unlike the statement-only return/break/continue), and `yield expr` (a right-recursive `parseAssignment()` call for the operand).
5. **No parser-level "is this actually inside a generator" check** — `yield` parses successfully in any expression position, generator body or not. Deliberately deferred to codegen (see Investigation): this parser has no other precedent for tracking that kind of enclosing-context state, and codegen rejects every `YieldExpression` uniformly anyway (see item 6), so a parser-level distinction between "wrong context" and "not implemented" would be precision this compiler currently has no way to act on differently either way.
6. `codegen/llvm/emit_func.go`'s `emitFunctionDeclAs` (the single shared choke point for top-level, nested, and on-demand-generic-instantiated function bodies): `decl.IsGenerator` is a clean, explicit rejection. `codegen/llvm/emit_exprs.go`'s `emitExpr` `*ast.YieldExpression` case: the same message, reachable directly for a `yield` with no enclosing generator at all (item 5's consequence).
7. `resolver/rename.go`: `*ast.YieldExpression`'s `Argument` is recursed into via `rewriteExpr`, mirroring `AwaitExpression`'s identical treatment — so cross-module identifier renaming inside a `yield`'s operand is already correct for whenever real generator codegen lands, not a gap the next slice would need to discover and fix separately.

## Implementation notes

- Files touched: `lexer/token.go`, `ast/nodes.go`, `parser/parser_stmts.go`, `parser/parser_exprs.go`, `codegen/llvm/emit_func.go`, `codegen/llvm/emit_exprs.go`, `resolver/rename.go`.
- `inferExprType` has no explicit case for `*ast.YieldExpression` — falls through to its existing blind `TypeI64` default. Deliberately left as-is: `inferExprType` never emits code, and every path that would actually *use* a wrong inferred type also unconditionally reaches one of the two hard rejections above before compilation could ever complete, so the blind default is unreachable in a successful build, not a live gap.

## Side effects discovered

- The hard-keyword choice (item 1) has a real, measured Test262 cost: 4 regressions, all real, non-strict-mode use of `yield` as a plain identifier (`var yield = 1;`, an object shorthand property named `yield`, an arrow-function parameter named `yield`, a label named `yield`) — legal in real JS, now a parse error here. Offset by 8 new passes (files expecting `yield` to be rejected as an identifier specifically in strict-mode/generator contexts, which a blanket reservation satisfies) — net +4. A real, understood, and now-documented tradeoff, not a bug; revisiting it into a true contextual keyword would need the same kind of parser-level "current function's own kind" tracking this parser doesn't have anywhere else, a larger change than this slice's own scope.
- Confirmed and closed, not just theorized: a generator function with no `yield` statements, and a bare `yield` with no enclosing generator, both silently compiled as something else entirely (an ordinary function; a void no-op) before the two codegen guards in Decision item 6 were added — see Investigation.
