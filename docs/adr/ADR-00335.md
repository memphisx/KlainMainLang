# ADR-00335: Spread in call arguments (`f(...arr)`)

- **Relations**: Implements TDD-00106
- **Date**: 2026-08-24

## Context

`f(...arr)` failed to parse — the one core-language gap flagged under "What Is
NOT Implemented → Medium complexity". TDD-00106 scoped V1 to the case that fits
the existing ABI cleanly.

## Decision

Per TDD-00106, V1 supports a spread argument **only as the sole filler of a
callee's rest parameter**, optionally after fixed arguments:
`f(...arr)`, `f(a, b, ...arr)` — for both named functions and closures/arrows.

The enabling fact: a rest parameter's ABI is `(ptr, i64 len)` — identical to how
an array variable is already passed as an argument. So the spread forwards the
array's own `(ptr, len)` buffer straight into the rest slot (via
`resolveArrayForHOF`) instead of the malloc-and-pack-N-scalars path a
compile-time-known arg count uses. The spread array's element type must match
the rest element type.

Everything else with a spread argument is a **clean compile error** naming the
V1 limitation (spread into a fixed-arity function, a non-last spread, multiple
spreads) rather than a miscompile — since the parser now accepts a spread in any
argument position. Spread into a variadic builtin (`console.log(...a)`,
`Math.max(...a)`) is likewise rejected (each would need bespoke work).

## Implementation notes

- Parser: `parseArgList` (parser_literals.go) now accepts `ELLIPSIS`, producing
  the existing `SpreadElement` node — mirroring the array-literal spread parser.
  The arrow-function detector was also taught that a `(` followed by `...` is
  unambiguously an arrow's rest parameter (a parenthesized expression can never
  begin with `...`), so `const f = (...xs) => …` now parses — previously it fell
  through to parenthesized-expression parsing and errored.
- `emit_call.go`: `checkSpreadArgs`/`singleSpread` enforce the V1 rule and detect
  the sole-spread case; `emitCallToFuncSig`'s rest branch forwards
  `resolveArrayForHOF`'s `(ptr, len)` with an element-type check. The closure-call
  path (`emitClosureCallByPtr`, emit_func.go) got the identical guard + forward,
  so spread into a closure/arrow rest param works too.
- The generic "spread outside an array literal" guard (emit_exprs.go) message
  was broadened to also mention the rest-parameter call form.

## Side effects discovered

- **Arrow/closure rest parameters didn't parse at all** — `const f = (...xs) =>
  …` (even without a spread call) fell through to parenthesized-expression
  parsing and errored, a latent gap the arrow detector never covered. Fixed here
  (the `(`-then-`...` detection above), which also unblocks spread into
  closures. Named + closure rest params and spread-into-both now all work.
- Multiple spreads / mixed positional+spread would reuse the existing runtime
  array-concat primitive (`emitSpreadArrayLitData`), currently wired only to
  array literals — a V2 follow-on.

## Verification

- `tests/spread_test.go`: `sum(...arr)`, `label("hi", ...a)` (fixed + spread),
  string-array spread, an arrow-function rest param spread, and the four
  rejection cases (fixed-arity, multiple spreads, non-last spread, spread not
  aligned to the rest slot).
- `examples/language/spread_args.ts` run on macOS (arm64).
- Machine: verified on Mac (arm64); the change is platform-independent.
