# TDD-00052: Top-level side-effecting code in imported files

- **Status**: Implemented (see [ADR-00145](../adr/ADR-00145.md))
- **Date**: 2026-08-10

## Context

[MODULES.md](../status/MODULES.md) and `resolver/resolver.go`'s package doc both flag this as the last deliberate V1 scope narrowing in the module system: imported (non-entry) files may currently only contain declarations — no bare executable statements (`console.log(...)`, `if`/`for`/`while`, a bare expression statement). Only the entry file's top-level statements "really run." Real ES modules run each file's own top-level code exactly once, in dependency order, the first time it's imported, with a guard against re-running on a cycle. `docs/adr/ADR-00022.md` and `MODULES.md` both name this precisely as the deferred work: "run-once guards, dependency-ordered execution, deciding what happens when a cycle means a module is used before its own top-level code has finished running."

A pre-implementation investigation (this session) turned up something worth designing around directly rather than discovering mid-implementation: `resolver.go`'s existing `validateDeclarationsOnly` already permits `*ast.VarDeclaration` unconditionally in non-entry files, **including its initializer expression**, which can already be arbitrary (a function call, a reference to another file's top-level binding). That's legal syntax *today*. For two files that import each other (a real cycle) where one's top-level `let`/`const` initializer reads the other's top-level binding, the read can land on an uninitialized LLVM alloca — real undefined behavior, not a clean compile error or a clean runtime error. No existing test exercises this specific shape (`TestE2EImportCircular` only exercises circularly-calling *functions*, which is safe — functions are position-independent `define`s with no execution-order dependency). This TDD's own stated goal — "guard against re-running on cycles" — is the natural place to close this, not a separate fix.

## Design

### Why the acyclic case is (almost) free

A pre-implementation read of `codegen/llvm` (`EmitProgram`, `emitter.go`) confirmed codegen has **zero concept of "file"** — by the time the resolver hands codegen a merged `*ast.Program`, every top-level statement is already file-oblivious, and `Program.Body`'s order is literally `main()`'s sequential instruction order (`EmitProgram`'s Pass 3). Function/class declarations are pre-scanned and registered in earlier passes (Pass 0.5/1/2), so they're fully position-independent regardless of where their declaration statement sits in the merged body — calling `foo()` from a statement that textually precedes `function foo(){}` already works today, and continues to. `resolver.go`'s dependency-first `order` (built by the existing DFS in `visit`) already gives:

- **Dependency-order execution** for free — a file's own imports/re-exports are fully visited (and land earlier in `order`) before the file itself, transitively, so a straight append of `order`'s files' full bodies (then the entry file's own body last) is already correct "importee runs before importer" ordering, for chains of any depth.
- **Run-once, diamond-safe execution** for free — `files` is keyed by absolute path and a file is only ever appended to `order` once (memoized), so a diamond-shared dependency's top-level code runs exactly once regardless of how many files import it.

So the merge step (`resolver.go`'s final `merged.Body = append(...)` loop) needs **no changes at all** — it already appends each non-entry file's full, unfiltered body (`unwrap` only strips `Import`/`ExportFrom` nodes and unwraps `ExportDeclaration`; it never filtered by statement kind — the *only* thing currently keeping non-declaration statements out of that merge is `validateDeclarationsOnly`, called earlier). The real work is entirely in *when and how strictly* that validation applies.

### Cycle detection: which files are "cyclic"

`visit`'s DFS marks a file in-progress before recursing into its own imports (a placeholder `fileInfo` is written before the imports loop, replaced with the real one after) — this is already how the existing cycle-tolerance works (a back-edge to an in-progress file is silently skipped rather than infinite-looping). This TDD adds an explicit `stack []string` (the current DFS recursion chain) alongside a `cyclic map[string]bool`, both scoped to `ResolveProgramWithOptions`:

- `visit` pushes `path` onto `stack` right before recursing into its own imports, pops it (via `defer`) right before returning.
- When `visit` finds `path` already in `files` (the existing "seen, skip" case): if `path` is also currently on `stack` (a real back-edge, not just an already-finished diamond dependency), every file from `path`'s position in `stack` to the top (inclusive — this covers cycles spanning more than 2 files, e.g. `A → B → C → A`) is marked `cyclic[...] = true`.

This is a superset-safe approximation of exact strongly-connected-component detection (a stack-slice-based mark, not full Tarjan) — deliberately: over-marking a file as cyclic when it's arguably not the *tightest* SCC member only costs that file some ergonomics (it stays on the stricter rule below), never a safety hole. Given this compiler's scale (dozens of files, not thousands), the simplicity is worth it over implementing Tarjan.

**The entry file is always safe regardless of its own cyclic-ness.** The final merge unconditionally appends the entry file's body *last*, strictly after every file in `order` — including any cyclic cohort it happens to structurally participate in (e.g. entry imports A, A imports back to entry: this is a real back-edge, both get marked `cyclic`, but entry is never a member of `order` and always runs after `A` regardless). So the restriction below is never applied to the entry file, unchanged from today.

### The two rules

- **Acyclic non-entry files**: `validateDeclarationsOnly` no longer runs at all. Any top-level statement is allowed, executed once, in dependency order, exactly as designed above.
- **Cyclic non-entry files**: `validateDeclarationsOnly` still runs (same allowed statement-kind set as today: function/var/let/const/interface/type/enum/import/export-from/class, no bare executable statements) — but gains one new check closing the bug found above: a top-level `VarDeclaration`'s `Init`, if present, must be a **compile-time literal** — a number/string/boolean/null/undefined literal, a prefix `+`/`-` applied to a numeric literal, or an array/object literal whose elements/property values are themselves (recursively) literals. No identifier reference, no call, no member access — nothing that could read another binding, from this file or any other, is allowed. This is deliberately more conservative than "no *cross-file* reference" (which would need tracking which identifiers resolve to an import) — a flat "must be a literal" rule is simple to implement, simple to explain, and provably safe: a literal can't observe any not-yet-run initialization, from anywhere.

This means a mutual pair of cyclic files can still do `export const MAX = 100;` (a literal), but not `export const MAX = other.BASE * 2;` (a reference) — the latter is rejected with a clear, actionable error rather than silently risking an uninitialized read.

**Explicitly out of scope for this TDD**: class *static* field initializers carry the same theoretical hazard (per the pre-implementation investigation, "every class's static block runs before any top-level statement, in declaration order" — a pre-existing simplification already true within one file) but `ClassDeclaration` stays unconditionally allowed in a cyclic file either way, and this TDD does not extend the literal-only check into static field initializers. Noted as a known caveat, not silently dropped — see Open Questions.

### Pipeline restructuring this requires

`validateDeclarationsOnly` currently runs *inside* `visit`, per-file, immediately after parsing — but a file's cyclic-ness may not be knowable until a much later back-edge is discovered elsewhere in the graph. The call must move to a **new pass after the full DFS completes** (`cyclic` is only final once `visit(entryAbs, true)` returns), iterating `order` (which already excludes the entry file) and calling the (renamed/extended) validator only for `cyclic[path]`.

## Open questions

- Whether class static-field initializers deserve the same literal-only treatment for cyclic files in a follow-up, once there's a concrete repro rather than a theoretical one.
- Whether a bare top-level `return` (found, pre-existing: silently exits `main()` with a coerced-to-`i32` status code, already reachable from the entry file today — `emitter.go`'s `currentRetType` defaults to `TypeI32` at the program level) is worth rejecting outright in a later pass. Unrelated to this TDD's actual scope (it doesn't get *more* dangerous once more files can execute — it just becomes reachable from more files) — noted here since it surfaced during the same investigation, not fixed by this TDD.
