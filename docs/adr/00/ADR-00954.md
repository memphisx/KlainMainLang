# ADR-00954: `yield` expression is TNext (`any`), not the yield element type

- **Date**: 2026-09-15

## Context

Test262 `built-ins/GeneratorPrototype/return/try-finally-set-property-within-try.js`
emitted invalid IR (a survivor from the Bucket B invalid-IR census). The kernel:

```ts
var obj = { foo: 'not modified' };
function* g() {
  try {
    obj.foo = yield;
  } finally {
    return 1;
  }
}
```

`obj.foo` is a string field; `obj.foo = yield` stored the resume value's word
straight into the string (`ptr`) slot:

```
error: '%t62' defined with type 'i64' but expected 'ptr'
  store ptr %t62, ptr %t32, align 8
```

## Investigation

This project collapses a generator's TNext (the `.next(v)` resume type) onto its
TYield (the element type): `.next(v)` coerce-checks `v` into the element type and
stores it in the `__sent` slot, which `GeneratorType` types as `elem`
(`types.go:1259`). The ordinary-resume path of `emitYieldResumeDispatch`
(`emit_generators.go`) returned that `__sent` load **verbatim, still typed
`elem`**, as the value of the `yield` expression.

When the element type differs from the target an rvalue `yield` is stored into
(here `elem` ≠ `string`), the member-assignment store
(`storeScalarOrNullableField`, `emit_nullable_scalar.go:314`) calls
`coerce(val, fieldTy)`. `coerce` only performs a real conversion into a `ptr`
target when the source is dynamic (`emit_exprs_coerce.go:60`); a plain non-dynamic
`elem` word falls through the generic scalar path, which relabels the type but
keeps the register — a coerce-honesty slip producing the `store ptr <i64>`.

In TypeScript a `yield` expression's type is TNext, which defaults to `any` — so
the faithful shape for a resume value consumed as an rvalue is a dynamic box, not
the element word. That also matches runtime reality: the caller may send anything.

## Decision

In `emitYieldResumeDispatch`'s mode-0 (ordinary resume) path, box the loaded
`__sent` value to `any` via `emitBoxValue` before returning it as the `yield`
expression's value. Every downstream consumer then coerces from a dynamic box to
its own concrete target (string field, `number` local, etc.) through `coerce`'s
existing dynamic-conversion arms, which are well-typed for any target.

The `.next(v)` **store** side is unchanged: `v` is still coerce-checked into the
element type (the TNext==TYield collapse stands), so a mismatched `.next()`
argument remains a clean compile error, not invalid IR.

## Implementation notes

- Single site: `emit_generators.go`, the `nextL` label in
  `emitYieldResumeDispatch`. The `.return(v)` (mode 2) and `.throw()` (mode 1)
  paths are untouched — they carry the generator's completion value / thrown
  error, not an rvalue resume.
- `emitBoxValue` is a no-op on an already-dynamic value, so an element type that
  is itself `any` costs nothing.

## Side effects discovered

- `TestE2EGeneratorMismatchedNextValueRejected` was written around the old
  behavior: it used `yield [...yield]` to force the sent slot array-typed, then
  `.next(false)` to trip the array-store guard. With the inner `yield` now `any`,
  `[...yield]` spreads a dynamic value and rejects at the spread ("not an array")
  before the `.next()` guard fires. Rewrote the test to annotate the element type
  directly (`function* (): number[]`), exercising the same `.next()`-value
  aggregate-store guard without depending on the incidental spread typing.
- Spreading an `any` value (`[...anyValue]`) is still a compile-time rejection
  here rather than TS's compile-accept / runtime-throw — a pre-existing
  dynamic-spread limitation, merely surfaced by this change, not introduced.
