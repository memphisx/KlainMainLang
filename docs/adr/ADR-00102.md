# ADR-00102: `http.close()` — listener teardown

- **Relations**: Implements [TDD-00027](../tdd/TDD-00027.md); references [TDD-00019](../tdd/TDD-00019.md)/[ADR-00079](ADR-00079.md) (settles that TDD's open question about whether a future `.close()` should reuse its pending-flag mechanism)
- **Date**: 2026-08-05

## Context

`docs/status/HTTP-SERVER.md`'s last open row was `.close()`: `http.listen` never returned on its own, and `process.on('SIGINT'/'SIGTERM', handler)` (TDD-00019/ADR-00079) only lets a handler run cleanup and end the whole *process* via `process.exit()`, not stop the listener specifically. The motivating gap: a program (typically a test, or a short-lived script) that wants to start a server, do some work against it, and then genuinely stop serving — without killing the process outright. This was `docs/status/README.md`'s Structural Priority #3's only remaining item.

## Investigation

Read `codegen/llvm/emit_http.go`'s `emitHTTPListen` and `codegen/llvm/runtime_http.go`'s `__kml_event_loop_run` end to end before deciding anything, since this compiler's execution model (everything emitted into one `main()`, the entire event loop living inside one blocking `call void @__kml_event_loop_run()`) constrains what shape `.close()` can even take:

- `emitHTTPListen` followed its `@__kml_event_loop_run()` call with `e.emitTerminator("unreachable")`, on the (previously correct) assumption the loop never returns. There is no point in a KlainMainLang program's control flow, before or after this feature, where TS code runs "alongside" a live server the way it does in real Node (`listen()` returning immediately, an implicit event loop keeping the process alive afterward) — the only code that ever runs while the loop is active is code the loop itself calls back into: a request handler, a `setTimeout`/`setInterval` callback, or a `process.on(...)` handler. This ruled out a returned `Server`-handle-with-a-`.close()`-method design: no code could ever hold such a handle at a useful moment. Restructuring the whole-program execution model so the event loop runs implicitly after `main()`, Node-style, was considered and rejected as a much larger, separate redesign with no other motivating need right now.
- `__kml_event_loop_run`'s `scandone:` block (its only exit point, `alldone: ret void`) computed `anywork = havetimer OR haslistener`, with no accounting for connections already accepted and mid-request. Closing the listener while one was suspended (parked on more data, or an in-flight `await fetch(...)`) would let the loop exit immediately, orphaning that fiber's `ucontext_t`/64KB stack and its still-open, unflushed socket — a real, demoable bad first impression for a feature whose whole point is "stop cleanly."
- TDD-00019 (`docs/tdd/TDD-00019.md`) explicitly left open "whether a future `.close()` API should integrate with this same pending-flag mechanism, or be a fully separate concept." Re-read why that mechanism (`volatile i8` flags, checked once per `outerloop:` iteration) exists at all: solely because a *real OS signal* can interrupt at an async-signal-unsafe instruction, so the raw handler must do the provably-safe minimum and defer real work to ordinary control flow. `http.close()` has no such hazard — it's always invoked as a plain function call from code the loop is already synchronously running one of (handler body, timer callback, signal-closure body). Decided against reusing the pending-flag indirection: direct, immediate mutation of `@__kml_listen_fd` is correct and simpler, with no reason to defer the effect to the next `outerloop` iteration.
- Grepped for a type-checker "never returns" concept before assuming removing `unreachable` was safe — found none (`TypeNever`/dead-code-diagnostic machinery doesn't exist anywhere in this codebase). "Never returns" was represented purely by the one `emitTerminator("unreachable")` call plus the emitter's own dead-code-after-terminator drop (`emitInstr`/`emitTerminator`'s `blockDone` guard). This meant no parser/type-checker change was needed, but also surfaced a real new risk: `buildHTTPDispatcher` unconditionally emits a fixed-name `@__kml_http_dispatch` function, relying on "only one `http.listen` call site is ever reachable" — true before this feature only because the first call never returned. Once it can, a second `http.listen(...)` call site (previously always dead code, so harmless even though Go-side codegen would still visit it) becomes genuinely reachable and would produce a confusing duplicate-LLVM-symbol error from the backend instead of a clean diagnostic.

## Decision

- `http.close()`: a bare global function (zero arguments, `void` return), dispatched in `emit_call.go` alongside `http.listen` — not a method on a returned handle, per the reasoning above.
- New runtime function `@__kml_http_close` (`runtime_http.go`, `ensureHTTPClose`): loads `@__kml_listen_fd`, and if it's `>= 0`, calls `close()` on it and stores `-1` back — a direct, unconditional mutation, not a pending-flag deferred to the next loop iteration. Idempotent (a no-op if already `-1`, matching Node's own tolerance of a redundant `.close()`).
- Connection draining: a new `@__kml_conn_active` `i64` counter (declared in `ensureFiberRuntime` alongside the rest of the connection table), incremented once in `__kml_http_append_conn` right after a new entry is appended, decremented at both of `buildHTTPDispatcher`'s connection-finish sites (`parseL` — normal completion — and `noReqL` — malformed/aborted request) via a small shared `emitConnActiveDecrement` closure. Folded into `scandone`: `anywork = havetimer OR haslistener OR (activeconns > 0)`. `checklistener` already gated new `accept()`s on `haslistener` alone, so this doesn't reopen accepting — it only keeps the loop alive long enough for connections already in flight to finish naturally. A still-running `setInterval` anywhere still keeps the loop alive regardless of `.close()`, matching real Node (not treated as a bug).
- Compile-time guard: a new `httpListenCallSeen bool` field on `Emitter`, checked and set at the top of `emitHTTPListen`, rejecting a second call site anywhere in the program with `"http.listen may only be called once per program"` instead of letting it reach the backend as a duplicate-symbol failure.
- Removed `emitHTTPListen`'s trailing `e.emitTerminator("unreachable")`. No other IR change needed — the `@__kml_event_loop_run()` call was always an ordinary non-terminator instruction.
- Clustering: no new IPC. `.close()` inside a `{ workers: N }` worker mutates only that worker's own copy of `@__kml_listen_fd`/`@__kml_conn_active` (every relevant global is per-process, per `fork()`'s address-space-copy semantics) — sibling workers are unaffected. Documented as V1 scope; a full-cluster stop still goes through an external signal to the whole process group, as the test harness's `startHTTPClusterServer` cleanup already does.

Rejected alternative: skip connection draining and document dropped in-flight connections as a known limitation. Rejected because the fix is cheap (one counter global, roughly a dozen lines total across two files) against a real, demoable failure mode (a client-visible hung/reset connection) of exactly the kind this codebase has been bitten by before (ADR-00052, ADR-00098).

## Implementation notes

Files touched: `codegen/llvm/emitter.go` (new `usedHTTPClose`/`httpListenCallSeen` fields), `codegen/llvm/emit_http.go` (top-of-file doc comment rewritten; `emitHTTPListen`'s guard + `unreachable` removal; `buildHTTPDispatcher`'s `emitConnActiveDecrement` helper at both finish sites; new `emitHTTPClose`), `codegen/llvm/runtime_http.go` (`ensureFiberRuntime`'s new `@__kml_conn_active` global; `__kml_http_append_conn`'s increment; `scandone`'s `anywork` fix; new `ensureHTTPClose`), `codegen/llvm/emit_call.go` (dispatch switch extended to `"close"`).

One pre-existing code path became newly live and was checked for correctness rather than assumed safe: `EmitProgram`'s tail (`emitter.go`) calls `__kml_timer_drain()` (if the program used timers) then `ret i32 0`, both previously unreachable whenever the last live top-level statement was `http.listen(...)`. Confirmed by inspection that `__kml_event_loop_run` itself already drains every due one-shot timer as part of keeping `anywork` true before it can reach `alldone`, so `__kml_timer_drain()`'s post-loop call remains a genuine no-op in this scenario; `ret i32 0` becomes the program's real, natural exit code absent an explicit `process.exit()`. No code change was needed for this.

## Side effects discovered

The second-`http.listen`-call-site gap described in Investigation/Decision above — not present in the original feature request, found while reasoning through what "code after `http.listen()` becomes reachable" actually implies for `buildHTTPDispatcher`'s fixed-name dispatcher function. Fixed as part of this change (the `httpListenCallSeen` guard), not deferred.

## Verification

Run on x86-64 Linux only (this project's other development machine is Apple Silicon macOS — not yet re-verified there; this change touches the fiber/event-loop code that has had real platform-specific bugs before, ADR-00051/ADR-00101, so treat as unverified on macOS until confirmed).

- `go build -o klainmain .`, `go vet ./...` — clean.
- `go test ./...` — full suite (including every existing `TestE2EHTTPListen*`/`TestE2ESignal*` test — concurrent connections, clustering in both `manual` and `-mm=gc` modes, headers/query/body, GC-mode churn) passes with no regressions from the `scandone` change.
- New tests added to `tests/http_test.go`: `TestE2EHTTPListenCloseExitsProcess` (a handler closes on `/shutdown`; asserts the triggering request still gets its response, the process exits on its own — via `waitExit`, not a forced kill — with code 0, and a `console.log` placed after the `http.listen(...)` call actually ran), `TestE2EHTTPListenCloseIsIdempotent` (calling `.close()` twice doesn't misbehave), `TestE2EHTTPListenSecondCallSiteRejected`, `TestE2EHTTPCloseWrongArgCountRejected`. All pass.
- Manual repro: compiled and ran a small handler calling `http.close()` on `/shutdown`; confirmed via `curl` that the triggering request still returns its response, the process exits on its own (`$?` = 0), and a `console.log` after `http.listen(...)` prints. Confirmed the second-call-site guard and the zero-args guard both reject with a clear `codegen error` at compile time (`--emit-llvm` on a two-`http.listen`-call-site program, and on `http.close(1)`).
- `examples/http/http_close.ts` (new) compiled and run standalone (`curl /hello` then `curl /shutdown` while running, confirming the server answers and then exits cleanly) and unattended via a self-closing `setTimeout` (confirming it exits within the timeout with no client ever connecting, matching how `make examples` runs every example).
- Ran the example-suite loop by hand (`make` itself isn't installed in this sandbox) reproducing `Makefile`'s `examples` target: built `tools/httpbin-lite`, pointed it at the correct fixture port (`HTTPBIN_LITE_PORT=8765`, `Makefile`'s own default — an initial run using the wrong ad hoc port surfaced 3 false failures in the `fetch`/`promise_all` examples, unrelated to this change, resolved by using the right port), then compiled and ran every `examples/**/*.ts` file unattended: 73/73 passed, including both `http_server.ts` (whose stale "no `.close()` in V1" comment was also corrected here) and the new `http_close.ts`.
