# ADR-00440: klain:webview Stage 4 — packaging (`.app` bundle / `.desktop` launcher)

- **Relations**: Implements [TDD-00142](../tdd/TDD-00142.md); Extends [ADR-00437](ADR-00437.md)
- **Date**: 2026-08-28

## Context

`klain:webview` could build a desktop app but only produced a bare executable.
Stage 4's exit criterion is a **double-clickable artifact on macOS**. A bare
Cocoa binary launched from a terminal can open a *background* window (no proper
activation); the `.app` bundle is what grants LaunchServices activation, so
packaging is a real capability, not cosmetics.

## Investigation

- `main.go` uses the stdlib `flag` package (main.go:16-23); the executable is
  fully written to `outBin` right after `clang` runs (main.go:182), where the
  emitter `em` is still in scope, so `em.UsesWebview()` is queryable. Output is
  always a single file — no directory/bundle abstraction existed.
- The TDD offered "a build-flag or a `klmpm` task." klmpm's CLI does **not**
  exist and its design deliberately has no scripts/task concept
  ([TDD-00054](../tdd/TDD-00054.md)), so a build-flag on `klainmain` is the only
  viable home.
- The vendored webview 0.10.0 engine calls `[NSApplication sharedApplication]` +
  `[NSApp run]` directly — a regular Cocoa GUI app, so the plist must **not** set
  `LSUIElement` (that would make an accessory app with no activation).

## Decision

A `-package` build-flag (host-GOOS gated, like `-static`): after compiling, wrap
`outBin` into a macOS `.app` (`Contents/{MacOS/<exe>, Info.plist, Resources/
icon.icns}`) or a Linux `.desktop` launcher. Metadata via flags with defaults so
bare `-package` works: `-app-name` (default = binary name), `-app-id` (default
`com.klain.<slug>`), `-app-version` (default `1.0.0`), `-app-icon` (optional).

- The binary is **copied** into the bundle (the standalone binary remains).
- `Info.plist` carries the mandatory `CFBundle*` keys plus
  `NSHighResolutionCapable` (sharp WKWebView) and `LSMinimumSystemVersion=10.13`;
  `CFBundleIconFile` only when an icon exists. All interpolated values are
  XML-escaped.
- Icon: a `.icns` is copied verbatim; a `.png` is converted via the macOS
  `iconset` + `iconutil` multi-resolution pipeline (zero third-party deps),
  falling back to `sips -s format icns`, and to no-icon-with-a-warning if both
  fail. On Linux the `.desktop` `Icon=` takes an absolute path to the `.png`/
  `.svg` directly.
- Pure, host-independent `buildInfoPlist` / `buildDesktopEntry` string builders
  are split from the fs/exec-touching `writeMac…`/`writeLinux…` so they unit-test
  on any platform. All lives in `packaging.go` (`package main`).
- A non-webview program only **warns** (a `.app` can wrap any GUI binary);
  Windows/other GOOS is a clean `fatal`.

**Deferred** (recorded, not dropped): multi-window (the codegen guard is trivial
to drop, but true multi-window needs reworking Cocoa run-loop / app-delegate
ownership in the vendored engine — an engine-integration task, and the TDD scopes
it "if demand exists"); bundling `dist/` into the app + runtime resource-path
resolution (the asset-bundling methodology, its own follow-up); manifest-driven
(`klain.json`) metadata (flags now, manifest later).

## Side effects discovered

A served-SPA app (`examples/webview/spa.ts`) reads `dist/` from disk relative to
the process CWD; launched as a bundle, LaunchServices sets CWD to `/`, so it
can't find `dist/`. V1 packages self-contained inline-HTML apps perfectly; the
served-SPA-in-a-bundle case waits on asset bundling. Disclosed in the docs.

## Verification

- macOS (Apple Silicon M4): `klainmain -package -app-name "Klain Demo"
  examples/webview/inline.ts` produced `Klain Demo.app`; `plutil -lint` passes;
  `Contents/MacOS/inline` has the executable bit; `open` launches it as a
  **foreground** GUI process (window renders). A `.png` icon produced a real
  multi-resolution `Resources/icon.icns` referenced by the plist.
- `packaging_test.go`: pure-builder unit tests (plist keys, `&`-escaping, no
  `LSUIElement`, icon-conditional; `.desktop` fields, quoted-absolute `Exec`;
  slug/default/icon-validation) run everywhere; a guarded bundle-structure test
  fabricates a stub executable (no clang/WebKit) and asserts the layout.
- Linux `.desktop` generation is pure file-writing; the builder is unit-tested
  cross-platform; a full launch on Linux is not yet run (no display) — disclosed.
