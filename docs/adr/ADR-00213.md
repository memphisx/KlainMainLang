# ADR-00213: definite-assignment early error for a typed `var`/`let`

- **Relations**: `Implements TDD-00071` (Stage 2 of 2 — completes it, alongside [ADR-00212](ADR-00212.md)'s Stage 1). `Extends ADR-00210` (whose function-scoped `var` created the case this now catches).
- **Date**: 2026-08-18

## Context

The last caveat on the Variable declarations row: a typed `var` read on a control-flow path where it was never assigned returned a deterministic zero default ([ADR-00210](ADR-00210.md) Stage C's interim), rather than the TypeScript `variable 'x' is used before being assigned` compile error the signed-off hybrid wanted. Making `var` function-scoped is what created a reachable "declared but not assigned on this path" state (`if (c) { var r = 1 } use(r)` with `c` false), so this closes the debt that change introduced. It also covers a typed `let` declared without an initializer and read before assignment.

## Investigation

Catching this needs flow-sensitive analysis — a must-analysis tracking which bindings are definitely assigned on *every* path to each read — which nothing in the pipeline did. [TDD-00071](../tdd/TDD-00071.md) scoped it as Stage 2 of the binding-readability pass, sharing `resolver/readability.go`'s scope-aware traversal with the Stage 1 TDZ check.

The load-bearing constraint is [TDD-00071](../tdd/TDD-00071.md)'s **no-false-positives** rule: the analysis must never reject a program that is actually valid. This dictates the direction of every conservative choice — the assigned-set must never claim *fewer* bindings than the truth, or a genuinely-assigned binding would be flagged. The first implementation got this backwards for loops, and a real example caught it (below).

## Decision

A second pass, `checkDefiniteAssignment` in `resolver/readability.go`, run per file after the TDZ check. It analyzes each function body (and the script top level, and each nested function/closure) independently, threading an assigned-set of binding ids through the statements:

- **Tracked bindings** are typed `let`/`var` locals. A binding annotated `any`/`unknown` or nullable (`T | null`/`T | undefined`) is **exempt** — those legitimately hold `undefined`/`null`. An unannotated binding is still tracked (concrete-typed here). `const` always has an initializer, so it's assigned at declaration.
- **`var` function-scoping** is modeled by pre-hoisting every function-scoped `var` into the function frame, so an assignment anywhere attributes to the one binding.
- A **read** of a tracked binding not in the assigned-set is the error. A read that crosses a **function boundary** to reach the binding is exempt (a closure may run after the assignment) — the same soundness exemption as the TDZ pass.
- **`if`/`else` merge** is the intersection of the branches that complete normally; a branch containing any `return`/`throw`/`break`/`continue` is conservatively excluded (over-approximating divergence, which only ever enlarges the merged set — sound). An `if` with no `else` contributes nothing definite. This is what catches the flagship `if (c) { … } use(x)`.
- **Loops, `switch`, and `try`/`catch`** use a sound over-approximation: every name the construct assigns *anywhere* is pre-seeded as assigned before the construct is walked. This is what keeps valid code accepted — a loop-carried assignment (`for (…) { if (i===0) x=1; else x=x+1 }`), a `switch` that assigns in every case with a `default`, a `for`-init that runs unconditionally, and a `try`/`catch` that assigns on both paths all stay compiling — at the cost of missing the genuinely-unsafe forms of those constructs (a documented gap).

## Implementation notes

- The soundness direction is subtle and was gotten wrong first: the initial loop handling *discarded* body assignments (restore-to-before), which under-counts the assigned-set and therefore **rejects valid code**. `make examples` caught it immediately — this project's own `examples/basics/var-scope.ts` has `for (var i = 0; …) {} console.log(i)`, whose unconditionally-run for-init assignment was discarded, flagging a valid read. The fix was to over-seed (pre-mark every assigned name) rather than discard — the opposite direction. This is the concrete reason the no-false-positives rule drove the design, not a footnote to it.
- Assignment forms recognized: `=`/compound assignment to an identifier, `++`/`--`, a declaration initializer, and destructuring leaves (recorded assigned). A compound assignment (`x += …`) and `++x` also count as a *read* of the target first.
- Nested functions, class methods, and arrow/function expressions are each analyzed as their own unit; a read of an outer binding from inside one is exempt, so no closure pattern produces a false positive.

## Side effects discovered

- The analysis is intentionally **sound but incomplete**: it does not catch every case TypeScript's `--strict` definite-assignment does (a binding assigned only inside a loop that might not run, or one assigned across correlated conditions like `if (c) {x=1} if (!c) {x=2}`). Those still fall through to [ADR-00210](ADR-00210.md)'s zero/`undefined` default rather than erroring — the honest, narrowed remainder now on the status row. This was the explicit trade chosen (no false positives over full parity).
- The pre-existing [ADR-00166](ADR-00166.md) limitation (a nested function can't reference an outer local at all) is unaffected: the DA pass exempts that cross-function read, and codegen still rejects it separately.
