# ADR-00898: Unary `~` on a non-numeric operand

- **Date**: 2026-09-12

## Context

Part of the invalid-IR (Test262 `CLANG_ERROR`) sweep. Bitwise NOT on a
non-numeric operand emitted invalid IR:

```ts
~({})                 // clang: '%t2' defined with type 'ptr' but expected 'i64'
~(function(){})
```

From `language/expressions/bitwise-not/S11.4.8_A3_T5.js`. The emitted IR was a
`trunc i64 %ptr to i32` on the object pointer.

## Investigation

`emitUnary`'s `~` case (`emit_exprs_operators.go`) called `toInt32(arg)`
unconditionally. `toInt32` does `coerce(v, TypeI64)` then `trunc i64 → i32`; for
an object/string operand `coerce` has no numeric conversion and returns the
pointer unchanged, so the `trunc` received a `ptr`. Unary `-` right above
already guards this exact case (rejecting a non-numeric operand cleanly), but
`~` had no such guard.

## Decision

Guard the `~` case for a non-numeric operand (not `Float`, not `IsInteger()`,
not `i1`; BigInt and dynamic operands are handled earlier):

- `-compat=strict`: a clean compile error ("unary '~' requires a number or
  bigint operand"), consistent with unary `-` and the binary object-operator
  rejection.
- `-compat=js`: box the operand and run the real `ToNumber` (`emitAnyToNum`),
  then the existing `ToInt32 ^ -1` tail — so `~{}` correctly yields `-1`
  (`ToNumber({})` → NaN → `ToInt32` → 0 → `~0` = -1).

## Implementation notes

- The compat-js path reuses `emitBoxValue` + `emitAnyToNum` (the same ToNumber
  the dynamic unary path uses) and feeds the resulting double back through the
  unchanged `toInt32`/`int32ToNumber` tail.

## Side effects discovered

None. Bitwise/unary E2E suites unaffected; only a non-numeric `~` operand,
previously invalid IR, changes behavior.

## Verification

- `TestE2EBitNotObjectRejectedStrict` / `TestE2EBitNotObjectCompatJS` (new).
- The Test262 file is no longer `CLANG_ERROR` under strict and runs to exit 0
  under `-compat=js`.
- `make examples` 296/296; bitwise/unary E2E suites green.
