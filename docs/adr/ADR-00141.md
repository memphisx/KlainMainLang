# ADR-00141: Import-gated built-in bindings, Stage 1 (default/namespace form)

- **Relations**: Implements TDD-00049
- **Date**: 2026-08-10

## Context

TDD-00049 found that every Node-style pseudo-namespace this compiler ships — `fs`, `path`, `os`, `querystring`, `assert`, `http` (as a module), `cluster`, plus this project's own invented `Memory.free(x)` — was recognized in `codegen/llvm` by bare AST-identifier-text matching (`id.Name == "fs"`), with zero connection to the resolver's real per-file scope machinery ([TDD-00041](../tdd/TDD-00041.md)/[ADR-00134](ADR-00134.md)). A two-file empirical repro during that TDD's own scoping confirmed this was a live bug, not just a design smell: a function-local `let fs = {...}` (never importing the real `fs` module) got silently routed to the real built-in `fs.readFileSync` instead of the user's own value, crashing on a path the user's code never referenced. Top-level declarations of the same names were accidentally safe only because unrelated per-file mangling happened to rewrite them first — not by design.

This ADR implements TDD-00049's Stage 1: gate the built-ins above behind a real `import`, using the exact scope-aware machinery already built for file-to-file imports, and close the shadowing bug as a structural consequence rather than a special-cased patch.

## Investigation

Confirmed by direct grep across `codegen/llvm/*.go` that these names are checked in three shapes, all needing the same fix:

- Member-expression call dispatch (`emit_call.go`): `fs.readFileSync(...)`, `path.join(...)`, `Memory.free(...)`, etc. — 7 sites.
- Member-expression property-read dispatch (`emit_exprs_member.go`): `cluster.isPrimary`, `path.sep`, `os.EOL` — 3 sites.
- The parallel type-inference switches (`emit_exprs_types.go`) that mirror both of the above, for compile-time return-type lookups (needed so e.g. `fs.readFileSync(...).length` type-checks without re-emitting) — 7 sites.
- One additional shape missed on first pass and found only once the fix was already in progress: `assert` is *itself* callable in real Node (`assert(cond)`, equivalent to `assert.ok`), so it also has a **bare-identifier-callee** dispatch entry (`emit_call.go`'s "Global built-in functions" switch, alongside genuinely ambient globals like `parseInt`/`fetch`) and its type-inference counterpart in `emit_exprs_types.go`'s matching switch — 2 more sites, for 19 total.

`resolver/resolver.go` was read in full to confirm the existing mechanism this reuses: `mangleFileDecls` gives every top-level declaration a file-private mangled name; `renameFile` (`resolver/rename.go`) then rewrites every *reference* to a name via a real scope-aware walk (a `scope` stack of locally-bound names always wins over the file-level lookup table). Critically, `rewriteExpr`'s `*ast.MemberExpression` case recurses into `Object` through the generic `*ast.Identifier` case *before* doing any namespace-specific work — so a plain `lu.names[alias] = marker` entry, the same shape a real named import already produces, gets picked up for free by both a member-expression object and a bare-identifier callee, with zero changes needed to `rename.go` itself.

Also confirmed: `resolver.ResolveProgram` only ever reads from a real file on disk (`os.ReadFile`), and only it — never a bare `parser.Parse` call — actually consumes/strips `*ast.ImportDeclaration` nodes before codegen runs. Several existing test helpers (`buildBinary`, `buildBinaryGC`, `parseAndCompile`, `compileAndRun`, `compileAndRunExpectExit` in `tests/compiler_test.go`) call `parser.Parse` directly, bypassing the resolver entirely — a pre-existing divergence from `main.go`'s real pipeline that only became observable once these built-ins started requiring a real import to reach codegen at all.

## Decision

**Virtual module specifiers**, resolved entirely within `resolver/resolver.go`, never touching the filesystem: `resolver/virtual_modules.go` adds a fixed table (`virtualBuiltinMarkers`) mapping each Category-B specifier (`'fs'`, `'path'`, `'os'`, `'querystring'`, `'assert'`, `'http'`, `'cluster'`, `'memory'`) to a reserved marker name (`fs__kml_builtin`, `Memory__kml_builtin`, etc.) — chosen to be unreachable by `mangleName`'s own `__kml_modN`-suffixed scheme, so it can never collide with a real user declaration.

`ResolveProgram`'s three passes over each file's `*ast.ImportDeclaration` statements (the dependency-visiting walk, the specifier-validation pass, and the lookup-table-building pass) each gained an early check: if `imp.Source` is a known virtual specifier, skip the normal file-resolution path entirely. In the lookup-table pass specifically, `virtualImportLocal(imp)` extracts the local binding name — either a namespace import's alias (`import * as fs from 'fs'`) or a default import's specifier (`import fs from 'fs'`, represented per [TDD-00042](../tdd/TDD-00042.md) as `{Imported: "default", Local: "fs"}`) — and binds it into the same `lookup` map real imports use (`lookup[local] = marker`), *not* the separate `ns` (namespace-member) map [TDD-00042](../tdd/TDD-00042.md) added. Using `lookup` rather than `ns` is what makes this a plain, general identifier rewrite rather than the compile-time member-access resolution `ns` triggers — it's what lets the *same* mechanism cover both `fs.readFileSync(...)` and `assert(cond)`'s bare-callee form with no extra code.

Any named specifier on a virtual-module import (`import { readFileSync } from 'fs'`) is rejected with a clear, actionable error rather than silently doing nothing — Stage 1's real scope boundary, not an oversight. Supporting it needs a second, new codegen dispatch shape (bare-identifier-call, keyed per-member rather than per-namespace) not built here; left for a later stage, see TDD-00049's Open Questions.

All 19 dispatch sites listed under Investigation were changed from `id.Name == "fs"` (etc.) to `id.Name == "fs__kml_builtin"` (etc.) — mechanical once the marker convention was fixed, since every site already had the same `if id, ok := ...Object.(*ast.Identifier); ok && id.Name == "..."` (or `switch id.Name { case "...": }`) shape.

A friendlier diagnostic was added at `emitCall`'s final fallback (`emit_call.go`): if a call's callee is a member expression on a bare identifier matching one of the known built-in names (checked via a small `builtinModuleSpecifiers` display-only map — not a dispatch decision, resolver already made that call), the error names the specific missing import (`'fs' is not defined — did you forget "import fs from 'fs'"?`) instead of the generic `only simple function calls are supported`. This only fires once every real dispatch path — including a legitimately-imported builtin, which never reaches this fallback at all — has already failed to match, so it can't misfire on a working program.

**`process` and `console` are unaffected** — matching real Node, which leaves both ambient (no `require`/import needed) despite `process` being Node-specific rather than an ECMAScript-spec global. This is Category C in TDD-00049's own split, resolved there, not revisited here.

## Implementation notes

- `resolver/virtual_modules.go` (new): the marker table and `virtualImportLocal` helper.
- `resolver/resolver.go`: three early-exit checks added to the existing per-file import loops; no change to the loops' existing behavior for real file imports.
- `codegen/llvm/emit_call.go`, `emit_exprs_member.go`, `emit_exprs_types.go`: 19 dispatch-site renames, plus the new fallback diagnostic and its `builtinModuleSpecifiers` map in `emit_call.go`.
- `tests/compiler_test.go`: four new additive helpers (`buildBinaryImports`, `buildBinaryGCImports`, `compileAndRunImports`, `assertOutputImports`, `parseAndCompileImports`, `compileAndRunExpectExitImports`) that write `src` to a real temp file and call `resolver.ResolveProgram` instead of `parser.Parse` — added rather than modifying the existing `buildBinary`/`parseAndCompile`/etc. in place, since those are shared by hundreds of unrelated tests across the suite and changing their behavior (even if provably safe for the no-import case) wasn't this ADR's job to risk. `startHTTPServer`/`startHTTPServerGC`/`startHTTPClusterServer`/`startHTTPClusterServerGC` (`tests/http_test.go`) and `startBackgroundServer` (`tests/signals_test.go`) *were* switched to call the new `*Imports` variants internally, since grep confirmed all their callers are exclusively `http.listen`-based tests that need the import regardless.
- `tests/import_gated_builtins_test.go` (new): the direct regression coverage — see Verification.
- Every existing example (`examples/assert/assert.ts`, `examples/fs/fs.ts`, `examples/path/path.ts`, `examples/os/os.ts`, `examples/querystring/querystring.ts`, `examples/memory/memory_free.ts`, `examples/http/http_server.ts`, `http_close.ts`, `http_binary_body.ts`, `http_cluster.ts`, `examples/process/graceful_shutdown.ts`, `examples/websocket/websocket_server.ts`) and every affected test file (`tests/fs_test.go`, `path_test.go`, `os_test.go`, `node_core_modules_test.go`, `memory_test.go`, `memory_gc_test.go`, `symbol_test.go`, `signals_test.go`, `websocket_test.go`, `http_test.go`) got the now-required import line(s) added. `examples/os/os.ts` needed both `os` and `path` (it calls `path.join` for a config-path example one screen down from the `os.*` calls) — missed on the first pass, caught by running `make examples` end-to-end rather than trusting the unit-test suite alone.
- `examples/strings/strings.ts` and `examples/process/process.ts` both declare a local `string`-typed variable literally named `path` — real, pre-existing code that's exactly the naming freedom this feature is for. Confirmed neither needed any change (they never called a `path` module method on it).

## Side effects discovered

- `path.join(...)`'s error path, when `path` isn't imported, doesn't reach the new friendly diagnostic — `mem.Property == "join"` matches an earlier, unconditional dispatch branch shared with `Array.prototype.join` first, producing `join takes 0 or 1 arguments` instead of a "did you forget to import" hint. Still a clean compile-time error, just a confusing one for this one specific property name. Not fixed here — a message-quality nice-to-have, not a correctness gap; left for whoever next touches that dispatch branch.
- Property-read (non-call) access to an unimported built-in (`os.EOL` with no `import os`) falls through to a plain `undefined variable 'os'` rather than the friendlier hint — the hint was only added to `emitCall`'s fallback, not the parallel property-read fallback. Same non-fix reasoning as above.
- TDD-00049's own Open Questions section already flags that this stage does **not** close the shadowing bug for Category A (`Math`, `console`, etc.) or Category C (`process`) — both stay on the same bare-identifier dispatch as before, by design (gating them behind import would be wrong, see the TDD's Design section). Noted here again since it's easy to assume "fixed" without re-reading that section.
- [TDD-00047](../tdd/TDD-00047.md) (`Worker`) assumed `import { Worker } from 'worker_threads'` — a **named** import. This ADR only ships default/namespace-form binding; `worker_threads` therefore still needs Stage 2 (named per-member imports) before it can ship in the shape that TDD originally sketched, not just Stage 1 landing. Flagged in TDD-00047's own text; not re-derived here.
