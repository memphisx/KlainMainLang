# ADR-00098: Fix dangling connection-array pointer causing intermittent `http.listen` hangs under concurrent load

- **Relations**: Extends [ADR-00049](ADR-00049.md) (fiber-based concurrent connection handling), [ADR-00072](ADR-00072.md) (the dispatcher this bug lives in); same general bug class as [ADR-00052](ADR-00052.md) (hand-written IR in this same connection-handling machinery, a different invariant broken the same way — a value computed once outside a loop that should have been recomputed on every entry); found while working on [ADR-00097](ADR-00097.md)/[TDD-00025](../tdd/TDD-00025.md)
- **Date**: 2026-08-04

## Context

While writing an E2E test for TDD-00025's multi-process clustering feature (`TestE2EHTTPListenClusteringMultipleWorkerPIDs`, `tests/http_test.go`), Go's `net/http.Transport`-based concurrent requests against a running `http.listen()` server hung indefinitely — some requests never received a response. Reproduced with as few as 2 concurrent `http.Get` goroutines. Confirmed via `git stash` (temporarily reverting every clustering-related change and rebuilding) that this reproduces on **unmodified, pre-clustering code** too — a real, pre-existing, unrelated bug in `http.listen`'s single-process connection dispatcher, not something the clustering work introduced. The user, asked directly whether to defer this as a documented known limitation or root-cause it now, chose to fix it now.

## Investigation

The user-visible symptom was misleading at first: plain concurrent `curl` (40 separate short-lived processes, each one connection) against the same server always succeeded, while Go's `net/http.Transport` (persistent-connection client, goroutines) hung even at just 2 concurrent requests. This looked client-implementation-specific. Ruled that out methodically rather than guessing:

- Raw `net.Dial` + hand-written HTTP/1.1 request text, 2 concurrent goroutines: **passed**.
- The exact request bytes Go's `http.Transport` actually sends (same headers, no `Connection: close`), via raw `net.Dial`: **passed**.
- `http.Client{Transport: &http.Transport{DisableKeepAlives: true}}`, 2 concurrent goroutines: **passed instantly**, every time.
- The *original* `http.Get`-based repro, re-run 30+ times in a fresh `go test` invocation each time: **flaky** — sometimes instant, sometimes hung for the full timeout.

The flakiness (not "always hangs," not "never hangs") was the key signal: a genuine race, not a deterministic protocol-handling gap. That pointed at the fiber-based connection dispatcher's own state management rather than anything about HTTP semantics or the client library.

Found stray leftover server processes from earlier hung test runs still alive and **spinning at 99.9% CPU for 18+ minutes** (`ps aux`) — a process stuck in a tight loop, not a process blocked/sleeping in `select()`/`read()` waiting correctly. That reframed the search: something in the dispatcher's own control flow was looping without making progress, specifically under concurrent connection load.

Read `buildHTTPDispatcher` (`codegen/llvm/emit_http.go`, the per-connection fiber body) end to end. Found the bug: `selfIdx`/`connData`/`selfSlot`/`fdPtr`/`ctxPtrSlot` were computed **once**, at fiber-entry, before the read loop:

```go
connData := e.freshReg()
e.emitInstr(fmt.Sprintf("%s = load ptr, ptr @__kml_conn_data, align 8", connData))
selfSlot := ... // GEP from connData
fdPtr := ...     // GEP from selfSlot
ctxPtrSlot := ... // GEP from selfSlot
```

`fdPtr`/`ctxPtrSlot` were then reused for the fiber's entire lifetime, including across every `swapcontext`-based suspend/resume cycle in the read loop (`doYieldL`, entered on `EAGAIN` from a non-blocking `read()`). But `@__kml_conn_data`'s backing buffer is genuinely mutable out from under a suspended fiber: `__kml_http_append_conn` (`runtime_http.go:673-727`) grows it via `realloc()` — doubling from an initial capacity of 8 (`runtime_http.go:682-689`) — every time a new connection is accepted and the array is full. `realloc()` is free to move the block. Any fiber suspended (yielded, waiting for more request data) at the moment a *different*, concurrently-accepted connection triggers that growth is left holding `fdPtr`/`ctxPtrSlot` pointers into memory that may have been moved or freed — a genuine use-after-free. Reading through it can return garbage (explaining the CPU-spin: a fiber looping on a corrupted fd value, never satisfying its own loop exit condition) or, less catastrophically, silently misbehave.

This explains every earlier observation:
- **curl's 40-way concurrency always passed**: each `curl` process completes its single request-response cycle about as fast as the loopback round trip allows, rarely triggering a *suspend* (the non-blocking `read()` usually succeeds immediately on localhost, so the fiber rarely actually hits `doYieldL` and gets suspended across a growth event).
- **Go's goroutine-scheduled concurrent dials genuinely stagger more**, and `MaxIdleConnsPerHost`/dial-queueing behavior in `net/http.Transport` (versus `DisableKeepAlives: true`, which removes that queueing) made a suspended-fiber-during-growth window measurably more likely — matching the observed flakiness rather than a deterministic reproduction.
- **The initial capacity of 8** means growth realistically happens within the first handful of concurrent connections in any test that opens more than a few at once — consistent with reproducing at `n=2` already, given no lower bound on *when* within a test run the race window lands.

Confirmed no other use of `@__kml_conn_data`/`@__kml_conn_len` in this file has the same bug: the event loop's own scan/accept/fd_set-building code (`__kml_event_loop_run`, e.g. `runtime_http.go:1049`, `1099-1103`) always reloads `@__kml_conn_data` fresh on every pass, and `@__kml_current_conn_idx` is correctly re-stored right before every fiber resume (`rresume`, `runtime_http.go:1100`) — only `buildHTTPDispatcher`'s own per-fiber cached GEP chain was stale-prone.

## Decision

Recompute `selfIdx`/`connData`/`selfSlot`/`fdPtr`/`ctxPtrSlot` at the **top of `readLoopL`** (the read loop's own label) instead of once before it. `readLoopL` is re-entered both on the fiber's first pass and on every resume-after-yield (`doYieldL`'s own `br label %readLoopL`), so this guarantees every subsequent use of `fdPtr`/`ctxPtrSlot` — through `checkErrL`/`checkEagainL`/`doYieldL` within that same pass, and (since no further yield happens once a request is fully buffered) all the way through `parseL`/`noReqL`'s final `store i64 -1, ptr fdPtr` — is always derived from whatever `@__kml_conn_data` currently points at, never a pre-suspend snapshot. This mirrors the existing, already-correct pattern the same function already used for `fd64`/`fd32` (also recomputed at the top of `readLoopL` on every pass) — those were already being recomputed per-iteration, they just derived from a `fdPtr` that itself wasn't.

No change to `__kml_http_append_conn`'s growth strategy itself (doubling from capacity 8 is unproblematic; the bug was purely about a stale reader, not the writer/grower).

## Implementation notes

Single file touched: `codegen/llvm/emit_http.go`, `buildHTTPDispatcher`. The five `e.freshReg()`/`e.emitInstr()` calls building `selfIdx`/`connData`/`selfSlot`/`fdPtr`/`ctxPtrSlot` moved from immediately after `e.pushScope()` (function entry) to immediately after `e.emitLabel(readLoopL)`, ahead of the pre-existing `fd64 := ...` line. Every later reference in the Go function body (`checkErrL`'s `fd32`/`noReqL`'s `close`/`__kml_http_send_response` calls, `doYieldL`'s `ctxPtrSlot` load, the two terminal `store i64 -1, ptr fdPtr` sites) is unchanged — they still reference the same Go string variables, which now just hold SSA register names defined inside `readLoopL` rather than before it. LLVM's dominance requirement is satisfied because every block using them is only reachable through `readLoopL` first.

## Side effects discovered

None beyond what's already described above — no other stale-snapshot-across-a-`swapcontext` pattern was found elsewhere in this file during this investigation, though a full audit of every hand-written IR function using `@__kml_conn_data` (or any other `realloc`-grown global) for this same class of bug was not performed as part of this fix; scoped narrowly to the confirmed reproduction.

## Verification

- Confirmed the bug reproduces on unmodified code via `git stash` (temporarily reverting all TDD-00025 changes, rebuilding, re-running the same repro) — 3/3 hangs at `n=40`, `n=10`, and `n=2` concurrent `http.Get` goroutines.
- After the fix: the same scenario run 30 times in a row (fresh `go test` invocation each time, `-run TestProbeSingleProcessConcurrency -timeout 5s`) — 30/30 clean. A separate hand-written Go reproducer (`net/http`, `n=2` and `n=40`) run 20 and 8 times respectively against freshly-started server processes — 28/28 clean, `0.0%` CPU on the server process after each run (confirmed no lingering spin). The clustered scenario specifically (3 workers, 40 concurrent Go requests) — 6/6 clean.
- `tests/http_test.go`'s new `TestE2EHTTPListenClusteringMultipleWorkerPIDs`/`TestE2EHTTPListenClusteringDefaultIsSingleProcess` (ADR-00097) — pass, including under `-count=3`.
- Full suite: `go test ./...` clean; `go test ./tests/ -run 'TestE2EHTTP' -count=3` (every HTTP-related E2E test, run three times) clean with no flakes.
- Checked for and killed stray leftover server processes from pre-fix hung runs (`ps aux`, matched by binary path) before relying on any post-fix measurement, since a stale zombie process still bound to a test's fixed port would otherwise silently make a "fixed" test still exercise old buggy behavior.
