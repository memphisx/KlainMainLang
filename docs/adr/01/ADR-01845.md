# ADR-01845: A JS call-site parameter is inferred inside its function's resolution

- **Relations**: `Implements TDD-00230` (P3.3: the checker answers what inferExprType did)
- **Date**: 2026-10-20

## Context

- Under `-compat=js`, an unannotated parameter is typed from its call sites (`callSiteParam`). Codegen asks for it first, through `JSCallSiteParam`, while registering signatures. That happens before anything has read the function itself.
- Typing a site's argument (`props([1])`) asks for the argument's contextual type (`keepsLiteral`). That reads the callee, so the function's symbol type was computed right then. Its parameter was still being inferred, so the busy sentinel was cached as the parameter, and the function's symbol type was left unanswered.
- Every later call of such a function had no checker answer. The full shadow run counted 5,130 unanswered calls, nearly all of them this pattern: a function called more than once (`subject = props([])`, then `props([1])`).
- A read of the function name took the other order and was right. Its symbol was then already resolving, and the re-entry met `typeOfSymbol`'s cycle handling.

## Decision

- `JSCallSiteParam` resolves a function declaration's symbol type before reading its parameter. The parameters are then inferred inside that resolution, as a read of the function infers them, and a site argument that reads the function back meets the cycle handling instead of caching a half-built signature.

## Consequences

- Such a function now compiles with the parameter type its sites agree on, where a cached miss used to fall back to a box.
- `TestJSCallSiteParamBeforeFunctionRead` asks for the parameter first, as codegen does. It fails without the change.
- Verified on Apple Silicon (checker package, targeted JS-lane tests). The gate on Linux x86-64 (DeskMini) and a full shadow run (Node304) follow.
