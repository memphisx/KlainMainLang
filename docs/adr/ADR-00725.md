# ADR-00725: `klain:webview` on Windows — the WebView2 backend

- **Relations**: Extends [ADR-00719](ADR-00719.md) (Windows Stages 1–4; left `Webview` as the largest documented skip group), [ADR-00436](ADR-00436.md) (webview build plumbing), [ADR-00443](ADR-00443.md) (`serve` embedding); implements [TDD-00177](../tdd/TDD-00177.md) (the `Webview` row of the faithfulness catalog, revised here)
- **Date**: 2026-09-06

## Context

After ADR-00719 the Windows port's largest remaining skip group was `klain:webview`: `LocateWebview` rejected `windows` at compile time ("unsupported platform … POSIX only") and 13 tests skipped there. TDD-00177's catalog had carried the README's "Windows is out of scope" line forward without examining it. The vendored binding (webview/webview 0.10.0, `codegen/llvm/webviewsrc/webview.h`) already contains a Windows backend — `WEBVIEW_EDGE`, a Win32 window hosting Microsoft Edge WebView2 — selected automatically under `_WIN32`. What was missing was the build inputs and a check that the module's observable behaviour holds on that engine.

## Investigation

- **Build inputs.** The Edge backend needs one header, `WebView2.h`, and the system libraries the header names for MSVC through `#pragma comment(lib, …)` (`advapi32 ole32 shell32 shlwapi user32 version`), which the mingw driver does not honour. MSYS2 packages the SDK header as `mingw-w64-ucrt-x86_64-webview2-loader` (`/ucrt64/include/WebView2.h`, plus a `WebView2Loader.dll` this project does not use). The binding defaults to `WEBVIEW_MSWEBVIEW2_BUILTIN_IMPL=1`: its own loader finds the Edge WebView2 runtime through the registry and `GetAvailableCoreWebView2BrowserVersionString`, so no loader DLL has to ship beside a compiled app. The runtime itself (`Microsoft EdgeWebView`, 152.x on the development box) is part of every Windows 10/11 install. Compiling the header as C++14 for `x86_64-w64-mingw32` produced no diagnostics.
- **First windowed run** (the `TestE2EWebviewSmoke` program built with the CLI): the window opened, the page called the bound native function, `terminate()` returned from `run()`, exit 0. The only output beyond the program's own is one Chromium log line on stderr at teardown (`ui\gfx\win\window_impl.cc … Failed to unregister class Chrome_WidgetWin_0. Error = 1412`), the browser process's own logging when the host window is destroyed first; Electron and every WebView2 host print the same line.
- **`serve` hung.** The single-file app path (`new Webview({ serve })`, ADR-00443) never reached the page's `done` callback. The embedded static server was fine (`curl` against the ephemeral port returned the fixture with the right headers), and a reduced program showed the cause: an `init` script registered *after* `html()`/`navigate()` never ran. On WKWebView and WebKitGTK nothing loads until the run loop starts, so the order in which a program issues `init` and `navigate` before `run()` does not matter — every existing smoke test, and the `serve` constructor (which navigates inside `new Webview` before the program can call `init`), rely on that. WebView2 issues `Navigate` to the browser process immediately, and `AddScriptToExecuteOnDocumentCreated` sent afterwards applies to the *next* document. The vendored `init` is fire-and-forget on Windows (no nested message loop; the only nested loop is inside `webview_create`, before any dispatch can be queued), and `webview_dispatch` there is `PostThreadMessage(WM_APP)` consumed only by `run()`.
- **Test harness.** The webview compile-tier tests were the only ones that `os.Stat` the built binary rather than executing it, and clang's mingw driver names `-o prog` as `prog.exe` (every other test passes because `os/exec` appends `.exe` itself). The embedded server's `Content-Length: %ld` formatted an `int64_t` through a 32-bit `long` on LLP64 (right by luck for sizes below 2 GB; a `-Wformat` warning on every Windows build).

## Decision

- **`LocateWebview` gains the Windows case** (`webview_win32.go`): probe the sysroot for `WebView2.h` and fail with the `pacman` package name if absent; link `-lole32 -lshell32 -lshlwapi -luser32 -ladvapi32 -lversion -lstdc++`. No `-I`, no DLL, no define: the header selects `WEBVIEW_EDGE` under `_WIN32`, and the built-in loader is the default.
- **Navigation is deferred on Windows.** `WebviewSource()` appends a short C++ tail on Windows defining `__kml_wv_navigate` / `__kml_wv_set_html`, which post the upstream `webview_navigate` / `webview_set_html` through `webview_dispatch`. The emitter calls those names on Windows (`webviewNavigateSym()` / `webviewSetHTMLSym()`) at its three navigation sites: the constructor's `serve` navigation and the `navigate` / `html` methods. A navigation requested before `run()` therefore happens when the loop starts, after every `init` the program issued — the order WebKit gives; a navigation requested from inside the loop (a bound callback, a timer) runs on the next iteration, which is unobservable. The vendored header is untouched.
- **Module contract made explicit.** "`init` may be registered after `html()`/`navigate()` (or after a `serve` constructor) and still runs at document creation, provided it precedes `run()`" is now a tested property on every host (`TestE2EWebviewInitAfterHTMLSmoke`), not an accident of WebKit's scheduling.
- The Chromium teardown log line is left alone: it is the runtime's own stderr output, not a fault, and silencing it would mean redirecting the browser process's logging.

## Implementation notes

- `codegen/llvm/webview.go`: the `windows` case, the doc comment's Windows bullet, and `WebviewSource()` appending `webviewWin32Deferral` on Windows.
- `codegen/llvm/webview_win32.go`: `locateWebviewWindows`, the C++ tail, the two symbol selectors.
- `codegen/llvm/emit_webview.go` / `runtime_webview.go`: the three call sites use the selectors; the two shim declarations are emitted on Windows only.
- `codegen/llvm/embedassetssrc/embed_assets.c`: `Content-Length: %lld` with an explicit `long long` cast.
- `tests/compiler_test.go`: every build helper names the binary `prog` + `llvm.HostExeSuffix()`, so `os.Stat` and `exec` agree on every host.
- `tests/webview_test.go`: `TestE2EWebviewInitAfterHTMLSmoke` (windowed, gated by `KML_WEBVIEW_SMOKE` like the others); `TestWebviewWindowsMissingSDKMessage` (the probe's message, via `KLAIN_SYSROOT`); `TestE2EWebviewWindowsNoLoaderDLL` (the built exe imports no `WebView2Loader.dll`, checked with `debug/pe`).
- The MSYS2 package is added to the README's Windows list; `TDD-00177`'s catalog row and prerequisites table are updated to the shipped state.

## Side effects discovered

- `-package` refused Windows outright; a console-subsystem executable launched from Explorer opens a console window beside the webview. Addressed in [ADR-00726](ADR-00726.md).
- The Windows smoke runs take ~1.3 s each; the Edge runtime's first-launch profile (`%APPDATA%\<exe name>\EBWebView`) is created per executable name, as upstream designs it — `prog.exe` under the test harness leaves one such folder behind.
- The `.rc`/`.res` mechanism and the format warning are Windows-only; the Linux and macOS webview paths are unchanged and were not rebuilt this session (the Linux compile tier ran in the Docker lane — see Verification).

## Verification

Windows 11 x86-64, LLVM 22.1.8 clang, MSYS2 UCRT64 with `mingw-w64-ucrt-x86_64-webview2-loader 1.0.3912.50-1`, Edge WebView2 runtime 152.0.4191.66:

- `KML_WEBVIEW_SMOKE=1 go test ./tests -run 'Webview|WindowDTS|TupleJSONParse|Embed'`: 30 passed, 0 skipped — the 13 former Windows skips (compile tier and `serve`) plus the seven windowed smoke runs (round trip, page-tick pump, async bind, typed bind, async typed + nested tuple, `serve`, and the new `init`-after-`html` run), each opening a real window and terminating from the page.
- The three new tests pass; `TestE2EWebviewWindowsNoLoaderDLL` confirms the import table carries no loader DLL.
- All four examples (`examples/webview/inline.ts`, `spa.ts`, `embedded.ts`, `explorer.ts`) compile and open their windows on Windows; `spa.ts` (Worker-hosted `http.createServer`) and `embedded.ts` (`serve`) render their pages.
- The reduced `serve` and ordering repros that hung before the deferral now print `page title: ["Fixture"]` / `native got: ["after-html"]` and exit 0.
- `make conformance` and the full `go test ./tests` results for this delivery are recorded in its closing ADR, [ADR-00731](ADR-00731.md) (Verification).
