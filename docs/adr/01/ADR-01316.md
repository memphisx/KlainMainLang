# ADR-01316: exec() results carry index, input and groups

- **Relations**: `Implements TDD-00230` (P3.2, P3.3); `Extends ADR-01307`
- **Date**: 2026-09-30

## Context

BACKLOG 119: `re.exec(s)` returned a plain `string[] | null`. `m.index`,
`m.input` and `m.groups` did not compile, and `console.log(m)` showed
`[ 'a' ]` where Node shows `[ 'a', index: 0, input: 'ab', groups: undefined ]`.
Named groups (`(?<year>\d+)`) had no way to be read. `str.match()` with a
non-global regex is `exec` and had the same gap. Found beside it: optional
access on a dictionary (`d?.key` on `Record<string, T> | undefined`) did not
compile.

## Investigation

- An array value is a `{data, len}` header (TDD-00213). Every array
  operation reads only those two words through the header pointer, and a
  stored or passed array keeps its header. So words appended after them
  travel with the array, and nothing else sees them.
- PCRE2 reports named groups through its name table (`PCRE2_INFO_NAMECOUNT`,
  `NAMEENTRYSIZE`, `NAMETABLE`), sorted by name. JavaScript lists groups in
  pattern order, and an unmatched named group is present with the value
  `undefined`.
- Whether `str.match(re)` is global depends on `re`. A literal's flags are
  known at compile time.

## Decision

- **Header.** `exec` allocates a 40-byte header: `data`, `len`, then
  `index` (a code-unit offset under `es-utf16`, as `lastIndex` is), `input`
  and `groups`. No match is the null header. The result's type is marked
  `ExecArray` (`execArrayType`), and so is the `RegExpExecArray`
  annotation. `RegExpMatchArray` stays plain, because a `match()` result
  from a variable regex has no extended header.
- **Reads.** `m.index`, `m.input` and `m.groups` load from the header
  (`emitExecArrayMember`). `m?.index` on a possibly-null result is
  `undefined` for the null header. Inspect lists the three after the
  elements, `groups` as `undefined` when absent. JSON ignores them, as it
  does in JavaScript.
- **Groups.** `__kml_regex_groups` (`stringsrc/string.c`) builds a
  null-prototype string dictionary from the name table, in group order,
  with headered strings. A group that did not participate maps to
  `undefined`. It returns NULL when the pattern names no group. Using
  string.c now always pulls in the map and string-header runtimes it calls.
- **`str.match()`** with a regex literal or `new RegExp(p, "flags")` whose
  flags lack `g` is `exec` (`matchIsExec`), extras included.
- **Declarations.** `RegExp.prototype.exec` and `test` are `@intrinsic`,
  and `RegExpExecArray` declares `groups`, as TypeScript's es2018 lib does.
- **Dictionary `?.`.** `emitOptionalMember` accepts a dictionary receiver
  and types the read as the dictionary's value type.

## Implementation notes

- `emitRegexSingleMatchCore` keeps its signature. `emitRegexMatch` adds
  the groups build, requested only by `exec` and literal non-global
  `match`, so the other callers' IR is unchanged.
- A value of `ExecArray` type is only produced by `exec` or by `match` with
  a known non-global pattern, so its header is always the 40-byte one.

## Side effects discovered

- `matchAll`'s entries, and `match()` with a regex held in a variable,
  still lack the extras (BACKLOG 119, narrowed).

## Verification

`tests/regexp_exec_extras_test.go` compares with Node on macOS arm64:
- named, unnamed and unmatched groups;
- `index`/`input` through a `while ((r = g.exec(s)))` loop;
- a `RegExpExecArray` parameter;
- destructuring, JSON and `console.log`;
- the null result;
- literal `str.match()`;
- dictionary optional access.
