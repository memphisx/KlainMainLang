# ADR-01404: HTTP listeners and connection fibers on their own libuv watchers

- **Relations**: Implements TDD-00244; Extends ADR-01402
- **Date**: 2026-10-05

## Context

On POSIX, every subsystem but the HTTP server had moved to libuv handles of
its own. The primary listener, the additional listeners and the connection
fibers still described what they waited for as select()-style bitmaps,
which the bridge turned into libuv watchers each pass: one `uv_poll_t` per
wanted descriptor, stopped and started again every pass so that a
descriptor closed and reopened under the same number between passes was
registered again with the kernel.

## Decision

- Each source owns its watcher: one per connection slot, one per additional
  listener and one for the primary listener. A pass syncs them to their
  descriptors (`sync_sources`) and runs libuv once. Watchers whose owner let
  go of its descriptor are dropped before any is added, so a number reused
  by a new connection never meets the old watcher. A watcher is restarted
  only when its events change: a connection parked on a write also waits
  for writability.
- The watchers' callbacks only record readiness in bitmaps, which grow to
  the highest watched descriptor. The fibers resume after `uv_run` returns,
  outside libuv's callbacks, as before.
- The watchers stay unreferenced: whether the server holds the loop is
  still the pass's decision (`has_listener`, `has_conns`,
  `__kml_http_xl_keepalive`).
- `__kml_loop_fd_forget` (a handle taking over a descriptor) drops whichever
  source watcher has it.
- The bridge's per-descriptor table, the re-arm, and the POSIX build of
  `__kml_http_xl_fdset_add` are deleted. Windows keeps its select() pass
  until TDD-00244 Stage 6.

## Divergence from TDD-00244

The TDD moves the listener and connection table onto `uv_tcp_t`, with the
fibers resumed from read callbacks. The fibers' read and write paths
(`emit_http.go`, the request-body and response-write runtimes) call
`read`/`write`/`accept` on the descriptor themselves; a `uv_tcp_t` owns
its socket's reads and hands over buffers, so it would rewrite every one of
those paths at once. A `uv_poll_t` gives the same wake-ups over the same
descriptors, and the libuv loop is the only waiter either way. The read
paths are generated per program, specialized to each server's handler, so
`uv_tcp_t` becomes possible once they are fixed runtime code.
