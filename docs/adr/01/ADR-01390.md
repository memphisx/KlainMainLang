# ADR-01390: fs.watch on uv_fs_event_t

- **Relations**: Implements TDD-00244; Extends ADR-01389
- **Date**: 2026-10-04

## Context

[TDD-00244](../../tdd/TDD-00244.md) Stage 4 moves the event sources onto
native libuv handles. fs.watch used inotify on Linux and kqueue on macOS
through the fdset/dispatch hooks. On macOS a directory's event named the
directory, not the changed entry ([ADR-00758](../00/ADR-00758.md)), and
`recursive`, `persistent: false`, `ref()` and `unref()` did nothing.

## Decision

- **On POSIX each watcher is a `uv_fs_event_t`** (`loop.c`'s
  `__kml_loop_fs_event_start`/`_stop`): inotify on Linux, FSEvents or kqueue
  on macOS. Its callback queues the event in `fswatch.c`, and the loop's
  dispatch fires the listener. A null filename becomes the watched path's
  base name, as libuv names a watched file. `__kml_fswatch_fdset_add` is
  Windows-only.
- **`recursive` is libuv's `UV_FS_EVENT_RECURSIVE`**, applied on macOS.
- **`persistent: false`, `ref()` and `unref()` work**: only a ref'd open
  watcher holds the loop, and the handle's libuv ref follows.
- Every watcher stays in the registry, which keeps its listeners reachable
  under `-mm=gc`.

## Side effects discovered

- `recursive` on Linux needs Node's own recursive watcher (a watch per
  directory), and on Windows the subtree flag of `ReadDirectoryChangesW`.
  Both stay a caveat on the status row.

## Verification

- Mac (M4): `TestE2EFsWatchChange`, `TestE2EFsPortWatch`; a directory
  watch, `persistent: false`, `unref()`, `unref()` then `ref()`, and a
  recursive watch print what Node 24 prints.
- Linux x86-64 (Ubuntu 24.04 container): test-par 3922 tests pass,
  examples 393/393, Test262 strict 8498 and js 10506 (unchanged), no
  invalid IR.
