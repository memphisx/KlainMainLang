# ADR-00255: A `.catch`/onRejected callback's error parameter is the error object

- **Relations**: refines [ADR-00248](ADR-00248.md) (task-promise `.then`/`.catch`/`.finally` value-chaining); uses the arrow param-hint path from [ADR-00245](ADR-00245.md)
- **Date**: 2026-08-20

## Context

A settled/rejected task promise's `.catch(f)` (and `.then(onF, onR)`'s second
arg) runs its callback with the rejection reason — which in this compiler is an
`Error`-family object (`errorObjType` = `{ i64 kind, ptr message, ptr name }`).
The callback was previously emitted with no type on its parameter, so the arrow's
lone param defaulted to `i64`; any `e.message`/`e.name`/`e.errors` access then hit
"field access on non-object". Annotating it (`(e: Error) => ...`) did not help
either — an `Error` annotation on a plain arrow param did not resolve to the
error-object shape. The documented workaround ("annotate to access `.message`")
therefore did not actually work.

## Decision

Two small changes make the reject callback's parameter the error object, with or
without an annotation:

- **`resolveType`** now maps any error-kind name (`Error`, `TypeError`, …, the
  members of `errorKindIDs`) to `errorObjType` (with `IsError` set). So an
  explicit `(e: Error) => ...` — or any error-family annotation — resolves to the
  real 3-field error shape rather than a bare object placeholder.
- **`emitRejectCallback`** wraps the callback emission: for an arrow with an
  unannotated parameter it supplies `errorObjType` as the param hint (via
  `emitArrowFunctionWithHints`), so `(e) => e.message` binds `e` to the error
  object; anything else falls through to a plain `emitExpr`. It is wired into
  `.catch` (args[0]) and `.then`'s onRejected (args[1]).

`.message`/`.name` read the two `ptr` fields directly; `.errors` stays the
kind-guarded AggregateError accessor from [ADR-00248](ADR-00248.md).

## Consequences

- `p.catch((e) => e.message)` and `p.catch((e: Error) => e.name)` both work; the
  former "annotate to access `.message`" caveat is removed (it never worked).
- Only the reject callback's *first* parameter is hinted; a reject callback is
  unary in practice, so this matches the reaction's single-reason argument.
- A separate, pre-existing issue is **not** addressed here: `await X.catch(...)`
  does not suspend on the source (it can print past the await before the catch
  runs) — tracked independently, not part of this change.
