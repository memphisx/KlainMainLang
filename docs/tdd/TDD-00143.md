# TDD-00143: `klain:sync` — a Go-fidelity goroutine runtime (preemptive M:N scheduling, channels, select)

- **Status**: Not Started
- **Date**: 2026-08-28

> Supersedes [TDD-00133](TDD-00133.md). That document scoped `klain:sync` as a
> thin layer over the *existing cooperative fiber scheduler*; the real goal is
> to match Go's concurrency semantics — genuine **preemptive** scheduling,
> goroutines, channels, and `select` — which is a substantially larger runtime
> and makes 00133's reuse-the-fibers foundation inadequate. 00133's channel/
> `select` surface and its "why not multi-thread `async`" framing carry forward
> here unchanged.

## Context

This compiler's identity is *portability by default, Go-class power by opt-in*.
The marquee opt-in is **real concurrency** — and the point is to bring Go's
actual model, not a JavaScript-flavoured approximation of it. Go's goroutines
are unique among mainstream runtimes: millions of them, cheap growable stacks,
and a scheduler that **preempts** a goroutine that will not yield, so one busy
task cannot starve the rest. That preemptive, M:N, work-stealing model is the
whole reason to build this rather than telling users to reach for `Worker` or
`async`.

**Scope fence (unchanged from [TDD-00133](TDD-00133.md), restated because it is
load-bearing).** Nothing here changes `async`/`await`, Promises, or `Worker`.
Those stay JS-faithful and single-threaded-by-contract, so ordinary TS/Node code
keeps running under real Node. This is an *explicitly non-Node* import under the
`klain:` namespace ([TDD-00131](TDD-00131.md)); a program that never imports
`klain:sync` links nothing and pays nothing. `async` must **not** become
multi-threaded — that would make identical code race differently than Node.
Goroutines are a parallel, separate world reached only through this package.

Why supersede rather than amend 00133: 00133's foundation was "park on the
existing `ucontext` fiber scheduler, cooperatively." Full Go fidelity needs a
real **GMP scheduler**, a **compiler safepoint-insertion pass**, **preemptible
goroutine stacks**, and eventually **signal-based async preemption** — none of
which 00133 anticipated, and each of which is foundational (later stages build
on them). The honest move is a fresh plan.

## Design

### Surface (`import { go, Channel, select } from 'klain:sync'`)

Unchanged in spirit from 00133; the semantics behind it are what deepen.

- **`go(fn: () => void)`** — spawn a goroutine. Cheap enough to have thousands
  live; preemptively scheduled onto the pool.
- **`Channel<T>(capacity = 0)`** — typed CSP channel with Go semantics:
  unbuffered rendezvous (capacity 0) or buffered ring; `await ch.send(v)` /
  `await ch.receive(): T`; `ch.close()` (receive then yields zero value + a
  closed flag, send after close panics); a `nil`/never-constructed channel
  blocks forever; `for await (const v of ch)` ranges until close.
- **`select(...cases)`** — Go's `select`: evaluate all cases, run one ready case;
  if several are ready, choose **pseudo-randomly** (Go's fairness); if none,
  park the goroutine on all of them until one fires. A `default` case makes it
  non-blocking.

### The scheduler — GMP

A real Go-style scheduler in an embedded C runtime (`klainsyncsrc/`), not the
single-threaded fiber loop:

- **G** — a goroutine: its own stack, a saved execution context, and a status
  (running / runnable / waiting / dead).
- **M** — an OS thread (`pthread`), mirroring `Worker`'s thread setup and GC
  registration.
- **P** — a logical processor: a *local run queue* plus the right to execute Gs.
  `GOMAXPROCS` defaults to CPU count. An M must hold a P to run Gs — this is what
  bounds parallelism and localises the common-case run queue (no global-lock
  contention per schedule).
- **Work stealing**: an idle P steals half of another P's local queue; a global
  run queue backstops. Spinning-M management avoids thundering-herd wakeups.

This delivers the real parallelism (N cores, N runnable Gs) *and* the scheduling
structure preemption hangs off.

### Preemption — the crux, in two tiers

A goroutine that never blocks on a channel must still be interruptible. Go does
this in two layers, and so should we:

1. **Cooperative safepoints (a new compiler pass).** The emitter inserts a tiny
   preempt-check — `if (g->preempt) runtime_yield()` — at **function entry and
   at every loop back-edge**. That single load + predictable branch preempts
   essentially all real code, *including tight `for` loops that call nothing*
   (Go historically checked only function entry, which is why a call-free loop
   could hang it pre-1.14; inserting at back-edges too closes that common gap
   up front). A `sysmon` helper thread flags a G's `preempt` when it has run
   longer than a threshold (~10ms).
2. **Asynchronous (signal-based) preemption — full Go 1.14+ fidelity.** For the
   pathological case with no safepoint reachable (hand-written asm, an
   unrolled call-and-back-edge-free loop), `sysmon` sends a signal (`SIGURG`) to
   the M; the handler, if the G is at an async-safe point, redirects it into the
   preemption routine. This is the hard part under LLVM — it needs async-safe-
   point awareness (recoverable register/stack state), the same machinery family
   as precise stack maps — so it is the **fidelity-completing final stage**, not
   V1.

Tier 1 alone is genuine preemption of real-world non-cooperating goroutines;
tier 2 removes the last starvation corner. Building tier 1 first mirrors Go's
own evolution.

### Goroutine stacks

- **V1: fixed, guard-paged stacks.** `mmap` a modest stack (e.g. 64–256 KiB)
  with a guard page for overflow detection, driven via `ucontext` (the existing
  fiber primitive). Simple and correct; goroutines are far cheaper than OS
  threads. Divergence from Go: no automatic growth, so very deep recursion can
  overflow (a clean fault, not silent corruption), and each G costs more memory
  than Go's 8 KiB start.
- **Later: growable/moving stacks (Go's model).** An 8 KiB start plus a
  `morestack` prologue that grows-and-copies on overflow. Copying a stack means
  **relocating the pointers into it** — which requires **precise stack maps**,
  the exact prerequisite [TDD-00135](TDD-00135.md) (precise/moving GC) needs.
  These two features converge; growable goroutine stacks are gated on that map
  infrastructure.

### Channels & select

A C `hchan`: a bounded ring buffer (or the rendezvous fast path for capacity 0),
plus `sendq`/`recvq` intrusive lists of parked Gs. Blocking `send`/`receive`
park the **G** (the scheduler runs another runnable G on that M), never the OS
thread. `close` wakes all waiters; `select` uses Go's algorithm (gather cases,
random tie-break among ready ones, else enqueue on all and park).

### Blocking calls & the P/M handoff

When a goroutine makes a genuinely blocking call (`fs`, a blocking `fetch`, a
syscall), Go detaches the **P** from the blocked **M** so the P's other Gs keep
running on a fresh M. V1 can start simpler — a blocking call blocks its M, and
`sysmon` hands the P to a spare M if the block outlasts a threshold — with full
entersyscall/exitsyscall handoff as a refinement. (Restricting V1 goroutines to
channel/compute work and documenting the blocking-call caveat is the fallback if
handoff slips.)

### GC interaction

Preemption safepoints double as GC safepoints. Under `-mm=gc` (Boehm,
conservative) each M is thread-registered (as `Worker` already does), but
goroutine stacks live on `mmap`'d regions that must be added as roots / scanned
— a real integration point. Under `-mm=manual`, a G's stack is freed on exit; a
leaked blocked goroutine leaks (documented, like other manual-mode handles). The
precise-stack-map work that unlocks growable stacks (above) and async preemption
also unlocks *precise* scanning here — the three converge with
[TDD-00135](TDD-00135.md).

### Lifecycle & exit

Lazily create the scheduler on first `go`/channel use. Match Go's exit: when the
program's top-level completes, outstanding goroutines are abandoned (Go's
fire-and-forget `main`-returns-kills-all), *not* awaited as a nursery. A
structured-concurrency wrapper could sit on top later, but the base semantics
are Go's.

## Staged plan

| Stage | Content | Exit criterion |
|---|---|---|
| 1 | GMP scheduler + `go` (fixed guard-paged stacks) + buffered/unbuffered `Channel`; cooperative safepoint at function entry only | N goroutines run in parallel on N cores and communicate over channels; blocking `send`/`receive` park the G, not the M |
| 2 | Safepoint-insertion pass extended to **loop back-edges** + `sysmon` preempt-flagging | a goroutine in a tight, call-free `for` loop is preempted and does not starve its P |
| 3 | `select` (random-fair) + full channel semantics (close/nil/range) + P-handoff on blocking syscalls | `select` over multiple channels matches Go; a goroutine blocked in `fs`/`fetch` doesn't freeze its P's other goroutines |
| 4 | Signal-based **async preemption** (`SIGURG`, async-safe points) | a goroutine with no reachable cooperative safepoint is still preempted — full Go 1.14+ fidelity |
| 5 | Growable/moving goroutine stacks (`morestack` + stack copy) — gated on precise stack maps, converging with [TDD-00135](TDD-00135.md) | goroutine start cost approaches Go's 8 KiB; deep recursion grows instead of faulting |

Stage 1 already surpasses [TDD-00133](TDD-00133.md)'s reuse-the-fiber-loop plan
(real M:N parallelism + a proper scheduler). Each stage is independently
shippable with its fidelity gap disclosed; nothing in 1–3 depends on the precise
stack maps that 4–5 need, so the practical, high-value core (preemptive
goroutines + channels + select) lands without waiting on the moving-GC work.

## Open questions

- **Fixed vs. growable stacks for V1** — fixed guard-paged is the proposed start;
  is the memory-per-goroutine cost acceptable until Stage 5, or should growable
  stacks (and thus precise stack maps) be pulled earlier?
- **Async-preemption feasibility under LLVM/`setjmp`** — can async-safe points be
  identified well enough that `SIGURG` redirection is safe, given exceptions are
  `setjmp`/`longjmp` on a C stack (the same constraint that ruled out LLVM
  coroutines across a `try`/`catch`)? Stage 4 may prove tier-1 cooperative
  preemption is the practical ceiling.
- **P/M handoff scope for blocking calls** — full `entersyscall`/`exitsyscall`
  handoff vs. a `sysmon`-driven approximation vs. a documented V1 caveat.
- **GC scanning of goroutine stacks under Boehm** — register each G stack as a
  root region, or require the precise path.
- **`panic`/`recover` across goroutines** — Go's per-goroutine panic propagation
  vs. this compiler's `setjmp`/`longjmp` exceptions; how a goroutine's unrecovered
  panic terminates the program.
- **Pure-TS (Node-runnable) reference shim** — carried over from
  [TDD-00133](TDD-00133.md): ship a slow single-threaded Promise-based
  implementation so the *same import* runs under plain `tsc`/Node, or make
  `klain:sync` native-only (a compile error off this compiler)?
- **Structured-concurrency layer** — Go's fire-and-forget `main`-returns-kills-all
  is the base; is a nursery/`WaitGroup`-style wrapper worth offering on top?
- **Memory-model guarantees** — commit to channel happens-before only, or a
  broader documented model?
