# TDD-00172: File API family — fs-backed data layer + UI-abstracted file picker

- **Status**: Not Started
- **Date**: 2026-09-03

## Context

`File` / `Blob` / `FileReader` and the File System Access API
(`showOpenFilePicker`, `FileSystemFileHandle`) are listed out-of-scope as
browser-only. But they split cleanly into two layers, and only one is actually
browser-specific: the **data layer** (read a file's bytes as text/arraybuffer/
dataURL) is a thin reinterpretation over the existing fs runtime, while the
**picker layer** (choose a file through a UI) is the only part that needs a
front end. This ties directly into the interactive-native-app direction
(`klain:tui`, `klain:webview`) — a TUI config editor / log viewer / file manager
wants exactly `showOpenFilePicker() → File → FileReader.readAsText()`. Where no
UI backend exists, the data layer still works (it *is* fs), and the picker
degrades explicitly rather than guessing.

## Design

### Layer 1 — data (fs-backed, always available, no UI)

Faithful W3C shapes, backed by the fs runtime and existing primitives:

- `Blob` (already present) + `File extends Blob` — `.name`, `.lastModified`,
  `.type`, `.size`, `.text()`, `.arrayBuffer()`, `.stream()`, `.slice()`. A
  `File` is **path-backed** (a native path — the reinterpretation; browsers
  forbid constructing a File from a path) or in-memory bytes.
- `FileReader` — `readAsText` / `readAsArrayBuffer` / `readAsDataURL`
  (base64 via the existing `btoa`) / `readAsBinaryString`, the `onload`/
  `onerror`/`onprogress` events, `.result`, `.readyState`, `.abort()`. Async:
  the read fires `onload` on the event loop (an fs read + an EventTarget
  dispatch), so browser code ports unchanged.
- `FileList` — the array-like a picker/`<input multiple>` returns.

This layer is the "pass through to fs/Node" answer: a program that just reads a
file uses fs directly or a path-constructed `File`; no UI is involved.

### Layer 2 — picker (UI-backend-abstracted)

`showOpenFilePicker(opts)` → `FileSystemFileHandle[]`, `showSaveFilePicker` →
handle, `showDirectoryPicker` → `FileSystemDirectoryHandle`. Handles expose
`.kind`, `.name`, `.getFile()` → a Layer-1 `File`, `.createWritable()` → a
`FileSystemWritableFileStream` (`.write`/`.seek`/`.truncate`/`.close`,
fs-backed); a directory handle exposes `.values()`/`.entries()` async iterators
and `.getFileHandle`/`.getDirectoryHandle`.

The picker resolves a path through a pluggable **`FilePickerProvider`** seam
(the architectural core — the "expand to other UI options" hook):

- **`klain:tui` active** → a built-in modal TUI file-picker widget (directory
  navigation, filter by `opts.types`, single/multi select) overlaid on the
  render loop; the returned Promise resolves when the user selects/cancels.
- **`klain:webview` active** → the OS-native file dialog (NSOpenPanel / GTK
  file chooser, or the webview's own `<input type=file>`).
- **no UI backend (headless)** → degrade explicitly: honor an explicit path in
  `opts` (a `klain:` extension), else argv/stdin, else reject with a clear
  "no file-picker UI available; pass a path" — never silently pick a file.

A future GUI backend (opentui / GTK, [TDD-00150](TDD-00150.md)'s FFI-unlocked
arc) implements the same `FilePickerProvider` interface — one seam, many front
ends.

### Async / consent

`FileReader` and the pickers ride the event loop (the pickers return Promises;
a TUI picker awaits user selection through the loop). The browser's per-pick
permission prompt has no native analogue — invoking the picker is the consent,
and a `PERMISSION_DENIED`-style rejection is reserved for a backend that itself
refuses.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| fs runtime (read/write) | Built | the data layer's backing store |
| `Blob` / `ArrayBuffer` / typed arrays | Built | `File extends Blob`, `readAsArrayBuffer` |
| `btoa` / base64 | Built | `readAsDataURL` |
| EventTarget + event loop | Built | `FileReader` events; async pickers |
| `klain:tui` | Built | the first picker backend (a new modal widget) |
| `klain:webview` | Built | the native-dialog picker backend |

## Staging (ordering, not dropping)

1. **Data layer**: `File extends Blob` (path- and bytes-backed) + `FileReader`
   (`readAsText`/`ArrayBuffer`/`DataURL`, events) over fs. No UI — near-term,
   standalone-useful.
2. **The `FilePickerProvider` seam + `klain:tui` file-picker** →
   `showOpenFilePicker` / `FileSystemFileHandle.getFile()`.
3. **`klain:webview` native-dialog backend** (parity) + the headless
   degradation policy.
4. **Writable + directory + save**: `createWritable`/`FileSystemWritableFileStream`,
   `showDirectoryPicker`/`FileSystemDirectoryHandle`, `showSaveFilePicker`.
5. **Future UI backends** (opentui/GUI) via the same seam.

## Open questions

- **Headless degradation policy**: reject outright, or honor an explicit
  `opts.path` / argv / stdin? A `klain:`-namespaced `path` escape hatch keeps the
  standard call working non-interactively (and gives CI a deterministic hook).
- **TUI picker composition**: how a modal picker overlays a running `klain:tui`
  app's render loop (suspend + restore) and returns focus.
- **Construct-from-path**: browsers forbid `new File` from a filesystem path;
  allowing it is the native reinterpretation — confirm we expose it (or a
  `klain:` helper) so the data layer is usable without a picker.
- **Node overlap**: this is *not* Node's `fs` — it's the Web File API shape over
  fs. A program wanting Node semantics uses `fs`; this is for browser-shaped code
  and the picker UX. Keep the two clearly separate on the status pages.
