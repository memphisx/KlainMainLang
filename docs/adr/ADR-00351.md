# ADR-00351: Fix Linux `-mm=gc` + `Worker` exit crash (GC shim `free()` on a foreign OpenSSL pointer)

- **Relations**: Extends [ADR-00071](ADR-00071.md), [ADR-00100](ADR-00100.md) (GC allocator shim)
- **Date**: 2026-08-25

## Context

`TestE2EWorkerGCModeRoundTrip` segfaulted under `-mm=gc` on Linux (glibc/arm64,
Docker) while passing on Mac — a long-standing open bug (tracked in this
project's own notes and on
[CONCURRENCY-WORKERS.md](../status/CONCURRENCY-WORKERS.md)), long assumed to be
the per-thread Boehm thread-registration / fiber-stack-bottom path that was only
ever verified on Mac.

## Investigation

A gdb backtrace (with Boehm's stop-the-world signals `SIGPWR`/`SIGXCPU` passed
through, so gdb reached the real fault) showed the crash was **not** in the
worker/fiber machinery at all, and not during a collection:

```
GC_free  ← libcrypto OPENSSL_cleanup ← exit ← __libc_start_main
```

The program runs to completion and prints the correct output; the segfault is at
**process exit**. OpenSSL registers an atexit `OPENSSL_cleanup` handler (libcrypto
is pulled in transitively — the worker runtime links libcurl). That handler
`free()`s OpenSSL-internal memory that OpenSSL did **not** obtain from this
program's allocator (e.g. a private/secure arena). The GC allocator shim
([ADR-00071](ADR-00071.md)) defines `free()` for the whole link and forwarded
every non-bump pointer straight to `GC_free`. `GC_free` on an address outside the
GC heap dereferences GC block metadata for that address → segfault.

This is why it looked worker-specific: the worker runtime is the `-mm=gc` test
path that links libcurl→libcrypto. Any `-mm=gc` program using `fetch`/`tls` would
hit the same exit crash — it was latent, not worker-bound. It reproduced only on
Linux because that build's OpenSSL runs this cleanup path (the Mac libcurl TLS
backend differs — see [ADR-00080](ADR-00080.md)/[ADR-00099](ADR-00099.md)).

## Decision

Guard the shim's `free()` with `GC_base(ptr)`: only call `GC_free` when Boehm
actually owns the pointer (GC_base returns the containing object's base, or NULL
for an address outside the GC heap). A foreign pointer is dropped — under a
collector nothing needs an explicit release, and the process is exiting anyway.
`realloc` is left as-is (no foreign-realloc path observed); this is a one-line
correctness guard on the `free` fast path, after the existing bump-pointer check.

## Verification

- Docker (Linux glibc/arm64): `TestE2EWorkerGCModeRoundTrip` now **passes** (was
  a reliable segfault); the `-mm=gc` string/class churn tests still pass.
- Mac (arm64): the same test still passes; no behavior change (the Mac path never
  reached the crashing cleanup).
- Machine: verified on Mac (arm64, Homebrew) and Linux (Docker `golang:latest`,
  `libgc-dev` + `libcurl4-openssl-dev`).
