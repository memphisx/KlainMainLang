# ADR-00674: Fix `Promise<T[]>` value corruption — resolve-thunk vs. closure array-arg ABI mismatch

- **Date**: 2026-09-03

## Context

Every array-valued promise created through a `new Promise` executor corrupted its
elements: `new Promise<number[]>((res) => res([10, 20, 30]))` awaited to garbage
values (the length survived, the elements were nonsense). `Promise<T[]>` is the
natural shape for a number of Node APIs (notably `events.once`, whose contract is
`Promise<args-array>`), so this blocked that work — it was found while building
`events.once` (TDD-00167).

## Investigation

Narrowed by elimination:

- Scalar promises (`Promise<number>`, `Promise<string>`) round-trip perfectly.
- An **async function returning an array** (`async f(): Promise<number[]> {
  return [1,2,3] }`) round-trips perfectly — so `storePromiseValue`/
  `loadPromiseValue` and the two-field (data-ptr, len) promise value slots are
  correct.
- Only the `new Promise` **executor**'s `resolve(arr)` path corrupted arrays.

Reading the emitted IR pinned it exactly. The executor calls `resolve` through
the ordinary closure ABI, and that ABI passes an **array argument boxed**: `call
void (ptr, ptr, i64) %res(ptr %env, ptr %boxptr, i64 %len)`, where `%boxptr` is a
heap pointer to the `{data, len}` header. But `emitResolveThunk` declared its
value parameter as a single `{ptr, i64} %v` (`StructFieldIR(valTy)`). So the
thunk read `%boxptr` (the header pointer) *as if it were the data pointer* and
stored that — on await, `arr[0]` then dereferenced the header, not the elements.

## Decision

Make the resolve thunk's array-value parameter match the closure array-argument
ABI. In `emitResolveThunk`, when the value type is an array:

- Declare the parameter as `ptr %vptr, i64 %vlen` (the same `(box, len)` shape
  `emitClosureCall` marshals a `resolve(arr)` into), instead of `{ptr,i64} %v`.
- Load the data pointer out of the box (`%vptr` field 0) and rebuild the
  `{ptr, i64}` aggregate that `storePromiseValue` expects (data pointer + the
  `%vlen` length).

Scalar and void resolutions are unchanged.

## Implementation notes

Localized to `emit_promise_new.go`'s `emitResolveThunk`. The `.then`/adopt and
async-return paths already store the aggregate directly (not via a closure call),
so they were correct and are untouched. `reject` carries an error object (a plain
pointer), so it needed no change.

## Verification

New E2E tests in `tests/async_test.go`: `new Promise<number[]>` and
`new Promise<string[]>` executors resolving with arrays now round-trip
(`10 20 30 3`, `a ccc 3`). `Promise.resolve([7,8,9])` round-trips too. The
`Async|Promise|Await` suite is green (Mac). This unblocks `events.once`
(TDD-00167).
