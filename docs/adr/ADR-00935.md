# ADR-00935: `TestE2EStdinDoesNotBlockLoop` is feedback-driven, not wall-clock-timed

- **Relations**: Supersedes the timing design of ADR-00867; Relates to TDD-00183
- **Date**: 2026-09-14

## Context

`TestE2EStdinDoesNotBlockLoop` failed on the GitHub **macOS arm64** runner while
the same commit passed on the M4 dev Mac and on every Linux lane. The failing
assertion was "the 15ms `setInterval` tick count strictly advanced across an 80ms
quiet stdin window" (ADR-00867). Nothing in the commit touched the reactor,
timer, or stdin paths — it was a false failure.

## Investigation

The property under test is real and correct: the runtime must not park the event
loop inside a blocking stdin read, so a timer keeps firing while stdin is idle.
The proxy ADR-00867 chose — *count timer ticks across a fixed 80ms wall-clock
window* — silently assumes the OS schedules the child for at least one 15ms tick
inside that window. On a dedicated M4 that holds (measured `4 → 9 → 13` ticks per
window). On an oversubscribed shared CI runner the child can be starved of CPU
for the whole 80ms, so zero ticks fire and the strict-advance check false-fails.
80ms was picked only as "comfortably longer than 15ms" (~5 ticks) — it was never
a correctness boundary, just a bet on scheduling latency, and that bet is an
external-environment dependency a unit test should not carry.

## Decision

Replace wall-clock pacing with a **feedback-driven** protocol that distinguishes
*slow* from *blocked*:

- The child emits a `tick N` heartbeat on every interval fire (in addition to the
  `chunk … ticks=N` echo and the `end ticks=N` line).
- The Go driver drains stdout through a channel and advances the protocol only by
  *observing* fresh heartbeats: prove the loop is alive before any input
  (`awaitTicks(2)`), then per chunk — write it, read its echo (tolerating
  interleaved heartbeats), then require ≥2 fresh heartbeats during the idle window
  before writing the next chunk.
- Each read has a generous 15s deadline. That deadline means *stalled*, not
  *slow*: a contended host produces heartbeats later but still produces them; a
  genuinely blocking read produces none during the idle window and the wait times
  out — the exact regression guarded, now caught by absence of progress rather
  than by rate of progress.

A residual monotonicity check on the observed per-chunk counts stays as a cheap
sanity guard (strict advance is already guaranteed by the heartbeat gating).

## Implementation notes

`tests/stdin_stream_test.go` only. No production/runtime change — this is purely a
test-robustness fix. The stdout drain goroutine keeps the child from blocking on a
full pipe now that it prints ~66 heartbeat lines/sec.

## Verification

- `go test ./tests/ -run TestE2EStdinDoesNotBlockLoop -count=8` green.
- `GOMAXPROCS=1 … -count=10` green (constrained-scheduling proxy for a contended
  runner) — the earlier design's failure mode.
- Platform: Apple-Silicon Mac.
