# ADR-01608: node:ffi on Windows checked against Node 26.10

- **Relations**: Extends ADR-01095, TDD-00229
- **Date**: 2026-10-13

## Context

The `node:ffi` tests compare with Node ≥ 26.10 behind `--experimental-ffi`.
CI installed that oracle on POSIX only, so on Windows they skipped, and the
MSVC STL `unordered_map` order the runtime reproduces there (ADR-01095) had
never met a Windows Node (BACKLOG §2).

## Investigation

With Node 26.10.0 and 26.11.1 for Windows (the release zips, checksums
verified), unpacked as the oracle:

- `ffi.dlopen(null)` and `new DynamicLibrary(null)` throw `TypeError`
  `ERR_INVALID_ARG_TYPE` "Library path must be a string": the Windows build
  opens no library for null. Ours opened the process.
- The tests open the process for libc's functions; on Windows the C runtime,
  `ucrtbase.dll`, has them, `getpid` as `_getpid`.
- With that, the symbol accumulator order (`TestE2EFFIAccumulatorOrderMatchesNode`)
  and every other comparison match Node 26.10.0.
- Node 26.11.1 accepts a safe-integer number for an `int64`/`uint64`
  argument (`labs(5)` is `5n`); 26.10.0 throws, as ours does. The oracle is
  pinned to 26.10.0 (`ffiNodeMinVersion`, CI); following 26.11 is a separate
  decision.

## Decision

- On Windows a null library path throws Node's `TypeError`.
- On Windows the FFI tests open `ucrtbase.dll` where they open the process,
  name `_getpid` for `getpid`, and are held to Node's own output
  (`ffiWindowsLibrary`, `ffiPortable`); POSIX keeps its expectations.
- CI installs the 26.10.0 oracle on Windows too and records it by
  `process.execPath`.

## Verification

Windows 11, `KML_FFI_NODE` = Node 26.10.0: every `FFI` test passes,
`TestE2EFFINullLibraryWindows` included. POSIX: unchanged paths.
