# ADR-00214: definite-assignment precision for `do/while` and `switch`

- **Relations**: `Extends ADR-00213` (the definite-assignment pass this sharpens); `Implements TDD-00071`.
- **Date**: 2026-08-18

## Context

[ADR-00213](ADR-00213.md) shipped definite-assignment with a uniform sound-but-blunt rule for loops, `switch`, and `try`: every name the construct assigns anywhere is pre-seeded as assigned (over-approximated), which never rejects valid code but misses real errors. Two of those constructs can be made precise without opening the general fixpoint/path-sensitivity problem, because their control flow is bounded:

- A **`do/while`** body runs at least once, so its *definite* assignments genuinely hold afterward — unlike a `for`/`while` that may run zero times.
- A **`switch`** with a `default` covers every discriminant, so a binding assigned on every case entry is genuinely definite afterward.

Both were surfaced by stress-testing the analysis for where it under-reports.

## Decision

Add a name-based must-analysis, `definiteAssignsOf` (`resolver/readability.go`), and use it to credit the *precise* definite set for these two constructs instead of the blunt over-seed. It is a sound over-approximation of the true definite set — straight-line assignments and `if`/`else` (intersection of both branches, excluding a diverging branch) are exact, while a nested loop/`try`/unrecognized statement falls back to gathering every name it *might* assign. Over-approximating the credit is what preserves no-false-positives: crediting too little would reject valid code (see [ADR-00213](ADR-00213.md)'s loop-direction bug).

- **`do/while`**: over-seed for loop-carried read safety and walk the body for reads as before, then restore the pre-loop state and credit `definiteAssignsOf(body)`. So `do { x = 1 } while(…)` and `do { if(c) x=1; else x=2 } while(…)` stay accepted, while `do { if(c) x=1 } while(…)` is now caught.
- **`switch`**: credit `switchDefiniteAssigns(cases)` — the intersection, over every case entry, of what running from that case through fall-through (until a `break`/`return`, which `definiteAssignsOf` stops at) assigns — but only when a `default` is present (otherwise an unmatched discriminant assigns nothing, so nothing is credited). So a `switch` that assigns in every case *with a default* is accepted (including fall-through, `case 1: case 2: x=…`), while one that leaves a binding unassigned on some case, or has no `default`, is now caught.

`for`/`while`/`for-of`/`for-in` and `try`/`catch` keep the blunt over-seed from [ADR-00213](ADR-00213.md) — precise handling there needs the loop-may-not-run and may-throw reasoning that isn't bounded the way these two are.

## Implementation notes

- `switchDefiniteAssigns` flattens the case list from each entry index onward and lets `definiteAssignsOf` stop at the first `break`, which models fall-through-until-break without a separate CFG.
- The monotonicity that makes this sound: intersection and union both preserve the superset relation, so an over-approximation at the leaves (`gatherAssignedNamesStmt` for unrecognized/nested-loop statements) propagates to an over-approximation of the whole `definiteAssignsOf`, and the switch's intersection-of-over-approximations still contains the true definite set.

## Side effects discovered

Stress-testing mapped the remaining escapes (all sound — they compile rather than mis-reject, and are covered by tests so a future tightening's effect is visible):

- **`for`/`while` body-only assignment** (`let x; while(c){x=1} use(x)`): not caught (the loop may run zero times). Because a plain `let` slot — unlike a `var` ([ADR-00210](ADR-00210.md)) — is not zero-pre-initialized, the escaping read is uninitialized memory, not a clean default. Candidate follow-ups: tighten `for`/`while` (risks rejecting the common `let r; for(…){r=…} use(r)` pattern), or zero-initialize tracked `let` slots so an escape is deterministic.
- **`try` body assignment** (`try { x=1 } catch {}`): not caught (`try` may throw before the assignment).
- **Correlated conditions** (`if(c){x=1} if(!c){x=2}`): *rejected* — the one place the analysis rejects a program that is valid at runtime, because distinguishing it from a genuine one-branch gap needs path-sensitivity. This matches TypeScript's own `--strict` behavior, but it is a real exception to "never rejects valid code" and is called out as such.

## Verification

- 10 new/updated E2E tests in `tests/func_test.go`: `do/while` unconditional/`if-else` accepted, conditional rejected; `switch` default-all-cases/fall-through accepted, missing-assign and no-default rejected; plus two documented-escape tests (`while`-only and `try`-body) that assert the analysis does *not* flag them today.
- Full `go test ./...` green (Mac, Apple Silicon M4); `go vet ./...` clean; **`make examples` 126/126** — the false-positive gate, confirming the tightening rejects no real program.
- `make conformance`: parse-level early-error signal only; the committed Linux baseline `CONFORMANCE-RESULTS.md` is not overwritten from a Mac run (see [ADR-00210](ADR-00210.md)).
