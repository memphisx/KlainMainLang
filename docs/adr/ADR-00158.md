# ADR-00158: Destructuring default values (`[a = expr]`, `{ a = expr }`)

- **Relations**: Extends [ADR-00153](ADR-00153.md) (Test262 full-corpus conformance harness), [ADR-00157](ADR-00157.md) (uninitialized-heap-memory reads)

## Context

ADR-00157 fixed the two memory-safety bugs blocking this feature and left array destructuring with a real, reliable "was this position provided" signal (the bounds check it added). Picking the feature back up: array destructuring defaults have a clean foundation now; object destructuring defaults still needed their own investigation, since a JS object's "was this field provided" question is answered completely differently than an array's "was this index in range" one.

## Investigation

Confirmed directly (not assumed) how this compiler represents `T | null` at runtime, since a destructuring default can only be sound where a real "not provided" signal exists. For a pointer-backed type (`string | null`), the null check is genuine: `p.y === null` compiles to `icmp eq ptr %v, null`. For a *scalar* nullable type (`number | null`, `boolean | null`), it isn't: `p.y === null` compiles to `icmp eq i64 %v, 0` (or `icmp eq i1 %v, false`) — the same storage a real value of `0`/`false` also uses. `null` there is a fake in-band sentinel, not a distinguishable state — the exact same ambiguity ADR-00157 already found for optional (`?:`) fields, just for a different reason (there it was uninitialized-vs-zero; here it's real-null-vs-zero). Triggering a default off that comparison would silently override a legitimately-stored zero. This drew the real boundary for object destructuring defaults: sound only for a pointer-backed nullable field (string, array, object/interface, class instance), not for a nullable scalar or a non-nullable (including merely-optional `?:`) field — those get a clean compile-time rejection instead of an unsound default.

Investigating the object case surfaced an unrelated, pre-existing, real bug while building a repro to test it: `let b: Box = { items: null }` for `interface Box { items: number[] | null }` failed to *compile* (clang error, not a codegen error) with `store {ptr, i64} null, ptr %t3, align 8` — `null` is only a valid literal for a bare `ptr`, not the `{ptr, i64}` aggregate an array field actually stores as (`StructFieldIR`, ADR-00061). Root cause: `coerce()` (`codegen/llvm/emit_exprs_coerce.go`) special-cases a null literal assigned to any non-`ptr`-IR target as "become the zero value," but an array's own `Type.IR` is `"ptr"` too (ADR-00157's own earlier finding), so this case fell through unchanged instead — the null literal's own `ptr null` ref just got handed straight to a `store` whose declared type was the aggregate. Nothing to do with destructuring specifically; any `T[] | null` field assigned a literal `null` anywhere hit this. Fixed as a blocking prerequisite (the array-side of object destructuring defaults is untestable without it), not deferred, per this project's "fix bugs hit in passing" rule — small, contained, one function.

## Decision

**Array destructuring** (`[a = expr]`, both the `let [a] = arr` statement form and a destructured function parameter): unconditional, any element type. The default is evaluated lazily, only inside `unpackArrayPatternInto`'s existing out-of-bounds branch (ADR-00157) — real JS's own laziness (a default expression with a side effect only runs when actually needed), for free from the branch already being there.

**Object destructuring** (`{ a = expr }`, both forms): accepted only when the field's resolved type is `Nullable && IR == "ptr"`; a default on any other field shape is a compile-time error naming the requirement, not a silently-wrong runtime check. `unpackObjectPatternInto` loads the field once (as it already did), then — only when a default is present — branches on `icmp eq ptr %v, null` before deciding which value to store, mirroring the array side's branch-then-store shape rather than a `phi` (same reasoning ADR-00157 used: every destination here is already a mutable `alloca`, so each branch can just store its own value).

A later pattern position's default may reference an earlier one in the same pattern (`[a, b = a]`, `{ x, y = x }` — real JS), since codegen processes elements in source order and each is `e.define`d before the next default is evaluated.

## Implementation notes

- `ast.DestructProp` gained a `Default Expression` field (no restructuring — it already had room). `ArrayDestructuring.Names []string` and `Param.ArrayPattern []string` both needed a real per-element struct to carry a default at all: replaced with a new `ast.ArrayPatternElem{Name, Default}`, mirroring `DestructProp`'s existing shape rather than adding a second parallel slice (which would risk index desync between two independently-grown slices — a smaller diff, but a fragile one).
- The type change was deliberately chosen over the smaller-diff alternative because of what it bought elsewhere: `go build` found every real call site for `ArrayPatternElem` immediately (parser, `unpackArrayPatternInto`, free-variable scanning, `resolver/rename.go`'s scope-binding) — the same "compiler-checked, not silently skipped" experience ADR-00156 got from its own `Update []Expression` change, in deliberate contrast to that same ADR's `VarDeclarationList` case (a genuinely new *sibling* type, which no signature change catches, and which did silently skip two real call sites until audited by hand). Introducing `ArrayPatternElem` as a replacement type for an *existing* field bought the same safety here.
- Two call sites needed *new* logic the compiler couldn't have caught by itself, since they don't reference the field at all until you know to add it: `resolver/rename.go`'s pattern-default rewriting (new `rewritePatternDefaults` helper, called right after `bindParams` so a self-referencing default resolves against the pattern's own just-bound names, not an outer/imported binding of the same spelling) and `emit_func.go`'s free-variable scan (a nested closure referencing a name whose value comes from a pattern default must see that default's own free variables too, not just the pattern's bound names).
- There's a small, deliberate asymmetry between statement-position and parameter-position pattern defaults for a *forward*-referencing pattern (`[a = b, b]`, real JS: a runtime TDZ error, since `let` hasn't finished binding `b` yet) — parameter defaults (`bindParams` binds every pattern name before any default is rewritten) would resolve `b` as local even in `a`'s own default; statement defaults (processed strictly left-to-right, matching source order) would not. Both are defensible, neither is "wrong" given this compiler doesn't model TDZ at all either way, and the case itself is a real-JS runtime error anyway — not reconciled further.
- The **array-field coerce bug** fix (unrelated to destructuring's own logic, a blocking prerequisite found investigating it): `coerce()` now special-cases `v.Ty.IsNull && target.IsArray` before the existing (now correctly-scoped-to-non-array) null-to-zero-value branch, returning the inline LLVM aggregate-constant literal `{ ptr null, i64 0 }` — no new instructions needed, since LLVM IR text accepts a constant aggregate literal directly wherever a `{ptr, i64}`-typed operand is expected.

## Side effects discovered

The array-field `null`-literal coerce bug (see Investigation) — fixed here as a blocking prerequisite, verified independently of destructuring with a standalone repro and its own regression test (`TestE2ENullableArrayField`, `tests/exprs_test.go`), not folded into a destructuring-specific test where its own significance would be easy to miss on a future read.

- 15 new E2E tests across `tests/arrays_test.go` (array-side defaults: used when out-of-bounds, unused when in-bounds, forward-reference within a pattern, closure-capture of a default's own free variable, destructured-parameter form) and `tests/objects_test.go` (object-side: used when null, unused when present, a nullable-array field specifically — exercising the coerce fix, destructured-parameter form, and both compile-time rejections — non-nullable field, nullable-scalar field).

Not investigated further via the per-file diff the prior three ADRs in this series used: `= expr` inside a destructuring pattern was a hard parse error before this change, so no previously-*passing* file could regress from the new syntax itself — the only residual regression surface was the `coerce()` fix and the resolver plumbing changes, both covered directly by the full test suite and example run above.
