# ADR-00727: `klain:tty` / `klain:tui` at a Windows console — verified under a pseudo-console (ConPTY) harness

- **Relations**: Extends [ADR-00719](ADR-00719.md) (Windows Stages 1–4; wrote the console-mode branches, left them test-unverified), [ADR-00518](ADR-00518.md) (the tty primitives, verified by hand under a pty on macOS), [ADR-00520](ADR-00520.md) (`readKey(ms)`); implements [TDD-00177](../tdd/TDD-00177.md) (the `tty` catalog row)
- **Date**: 2026-09-06

## Context

ADR-00719 replaced the termios/`TIOCGWINSZ` code of the tty shim and the `klain:tui` painter with console-mode API branches (`SetConsoleMode` raw mode with `ENABLE_VIRTUAL_TERMINAL_INPUT`, `GetConsoleScreenBufferInfo` for the size, `PeekConsoleInputW`-driven `readKey(ms)`, `ENABLE_VIRTUAL_TERMINAL_PROCESSING` on stdout). They were exercised at a real console by hand during that work, but nothing in the suite reaches them: every tty/tui test runs the program on pipes, which is the non-console path (80×24 fallback, no raw mode, `readKey` over a pipe). On macOS the same gap is covered by manual pty runs (ADR-00518); on Windows, a machine that development leaves after this port, a manual-only verification would be a permanent blind spot.

## Investigation

- Windows 10 1809+ has a pseudo-console API (`CreatePseudoConsole`, the `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` attribute for `CreateProcessW`) — the primitive Windows Terminal, VS Code and OpenSSH use to host console programs. A child spawned under it is attached to a genuine console: `GetConsoleMode` succeeds on its standard handles, the screen buffer has the requested size, VT bytes written to the console's input pipe become key events (and, in VT-input mode, come back out of `ReadFile` as the same escape sequences a POSIX terminal sends), and the console's rendering reaches the output pipe as a VT stream. No third-party module is needed: five kernel32 exports plus `CreateProcessW` with a `STARTUPINFOEX`, all reachable from `syscall`.
- The first run showed the child printing on the *test process's* stdout while the console had clearly attached (the pseudo-console set its title from the executable's name). `CreateProcess` hands a child copies of the parent's standard handles even with `bInheritHandles=FALSE` when they are not console handles — the test binary's are pipes — and those took precedence over the console's. A terminal emulator has no standard handles at all, which is why its shell picks up the console; clearing the three standard handles (`SetStdHandle(…, NULL)`) for the duration of the spawn, then restoring them, reproduces that. Go's `os.Stdout` keeps the handle value it captured at start-up, so the test process is unaffected.
- The output pipe only reaches EOF once the pseudo-console is closed, and closing it before the child has exited would kill the child; the harness therefore waits for the process (with a kill past the timeout), then closes the console, then drains.

## Decision

A Windows-only test harness, `tests/conpty_windows_test.go`: `runInConPTY(t, bin, cols, rows, timeout, feed)` runs a compiled program under a `cols×rows` pseudo-console, hands `feed` a writer to the console's input on its own goroutine, and returns the rendered output and exit code. It skips where `CreatePseudoConsole` is absent or `KML_NO_CONPTY=1`.

Console-backed tests in `tests/tty_console_windows_test.go`, each the program a user would run in a terminal:

- `TestE2ETtyConsoleSize` — a 100×30 console reports `process.stdout.columns/rows` = 100×30 and `isTTY` = true (the same program over pipes falls back to 80×24, `TestE2ETtyWinSizeFallback`).
- `TestE2ETtyConsoleRawReadKey` — raw mode: a single `q` reaches `readKey` without Enter, and an arrow key arrives as `27 91 65`.
- `TestE2ETtyConsoleReadKeyTimeout` — `readKey(200)` returns `""` with nothing pressed; `readKey(5000)` returns the key pressed later.
- `TestE2ETuiConsoleLoop` — a `klain:tui` state→view→update loop laid out to the console's width on the alternate screen, moving its selection on `↓` and quitting on `q`, then printing its result after `leave()`.

## Implementation notes

- No compiler change was needed: the branches ADR-00719 wrote behave as written. The harness and tests are Windows-only by file suffix; nothing is added to the POSIX build.
- The harness assembles `STARTUPINFOEX` by hand (`syscall.StartupInfo` + the attribute-list pointer, `Cb` = 112 on x86-64) and passes the `COORD` size to `CreatePseudoConsole` packed into one register as the ABI requires.
- The rendered output is the console's re-encoding (cursor moves, `\x1b[?9001h`-style mode toggles, the title sequence), not the program's raw bytes, so the assertions are on text and exit behaviour, never on exact byte sequences.

## Side effects discovered

- The same harness delivers Ctrl+C to the console (`\x03` with processed input on), which is the faithful way to test `process.on('SIGINT')` on Windows — where Go's `os.Process.Signal` cannot send SIGINT and the six signal tests skip. Done in [ADR-00728](ADR-00728.md).
- `klain:tui`'s row/column fallbacks and the tty shim's read a console handle from `_get_osfhandle(1)` while raw mode uses `GetStdHandle(STD_INPUT_HANDLE)`; both resolve to the console under the harness. No change.

## Verification

Windows 11 x86-64: `go test ./tests -run 'TestE2ETtyConsole|TestE2ETuiConsole'` — 4 passed in 6 s. The programs under the harness printed `size=100x30 tty=true`, `first=113 second=27 91 65`, `alen=0 b=z`, and the TUI loop reached `chose gamma` with exit code 0 after two `↓` presses and `q`.
