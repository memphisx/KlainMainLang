# TDD-00126: Opt-in JSDoc (and inline-TS) type enforcement flag

- **Status**: Not Started
- **Date**: 2026-08-27
- **Notes**: A compiler flag that promotes the currently-erased modifier tags (`@readonly`/`@private`/`@protected`/`@override`/`@implements`/`@satisfies`/`@enum` and their inline-TS equivalents) into enforced front-end checks, for pure-JS-with-JSDoc authors who want JSDoc to *be* the type system. Erase-don't-enforce stays the default (parity: inline `readonly`/`private`/`satisfies` are erased here too, so enforcing only the JSDoc spelling would be backwards); the flag clears those [JSDOC.md](../status/JSDOC.md) Strict caveats only when asked. Front-end only, zero codegen/runtime cost; incrementally gate-able per check. Reuses [TDD-00113](TDD-00113.md) structural subtyping for `implements`/`satisfies`

## Context

The JSDoc surface ([TDD-00125](TDD-00125.md)) is functionally complete, but a
cluster of tags sits permanently outside Strict coverage because they are
**accepted and erased, not enforced**: `@readonly`, `@private`/`@protected`/
`@public`, `@override`, `@implements`, `@satisfies`, `@enum`. This is not a gap
in the JSDoc plumbing — it is the same stance the compiler takes toward the
*inline* TS equivalents. The inline `readonly`, `private`, and `satisfies`
keywords are likewise erased here without access-, mutation-, or
conformance-checking. Enforcing only the JSDoc spelling would make a doc comment
stricter than the real keyword, which is backwards; so the default must stay
erase-don't-enforce for both spellings equally.

The default is right for the common case — someone writing typed TS with the
occasional stray doc comment, where a stale `@param` must never override a live
inline `: T`. But there is a legitimate opposite case: an author writing **pure
JavaScript** who wants JSDoc to *be* the type system, enforcement included. For
that user, "accepted and erased" is a downgrade, not a feature. We want to
respect that intent **without** changing the experience for the default,
performance-oriented majority.

The natural shape is an **opt-in compiler flag** that turns the erased modifiers
into enforced checks. This TDD exists mainly so the idea is not lost; the design
below is a starting sketch, not a committed plan.

## Design

A single front-end flag (working name `--strict-modifiers`, final spelling TBD)
that, when set, promotes the currently-erased modifier semantics into
compile-time checks. Because the JSDoc tags are already synthesized into the
same AST/type nodes as their inline-TS counterparts ([TDD-00125](TDD-00125.md)
Stage 5), enforcement is a **type-checker pass**, not JSDoc-specific work — and
it necessarily applies to the inline spelling too (a `private` field and an
`@private` field must behave identically, per the parity argument above).

Candidate checks, each independently gate-able so the work can land
incrementally:

- **`readonly` / `@readonly`** — reject assignment to the field outside its
  declaring constructor. Cheapest and highest-value; a good Stage 1.
- **`private` / `protected` access** — reject member access from outside the
  class (resp. subtree). Needs a notion of "access site class," which the
  resolver mostly already has for method dispatch.
- **`override` / `@override`** — require a matching base-class member; error if
  the name doesn't override anything.
- **`implements` / `@implements`** — structural conformance check of the class
  against the named interface(s). The heaviest; reuses the structural-subtype
  machinery from [TDD-00113](TDD-00113.md) `matchExtends`.
- **`satisfies` / `@satisfies`** — excess-property / conformance check of the
  value against the type, *without* widening the value's own type.
- **`enum` / `@enum`** — nominal enum-member typing / narrowing (larger; may
  stay out of even the opt-in first cut).

All checks are **front-end only** (parse + resolve), emit clean diagnostics, and
have **zero codegen or runtime cost** — set or unset, the emitted IR is
identical. The flag only decides whether a violation is an error.

Interaction with the type-carrying tags is unchanged: `--strict-modifiers` does
**not** touch `@param`/`@returns`/`@type` precedence. Those already do the right
thing (fill-not-override for params/returns; authoritative for `@type` on one
binding), independent of enforcement.

Open sub-question: whether this is one flag or a small family (e.g.
`--strict-access`, `--strict-readonly`) — leaning toward one umbrella flag with
the option to split later if users want finer control.

## Open questions

- Flag spelling and granularity (one umbrella vs. per-check flags).
- Does enforcement apply to inline TS modifiers unconditionally under the flag,
  or is that itself opt-in? Leaning unconditional-under-the-flag, since the
  parity argument says the two spellings must not diverge.
- Should `@enum` nominal typing be in the first cut or deferred as its own
  stage? Leaning deferred — it is a type-model change, not just a check.
- Is there a real user demand signal yet, or is this purely speculative? Ship
  only once a pure-JS-with-JSDoc user actually hits the erased-modifier wall.
