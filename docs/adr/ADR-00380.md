# ADR-00380: `@param`/`@returns` JSDoc typing for untyped functions

- **Relations**: Implements [TDD-00125](../tdd/TDD-00125.md)
- **Date**: 2026-08-26

## Context

The compiler consumed only two JSDoc annotations — `@type` (a per-binding type
override) and `@erased` — leaving the whole "typed JS" workflow unsupported: an
untyped `function add(a, b)` could not be typed from a leading `@param
{number} a` / `@returns {number}`, so its parameters fell through to
`registerFunctions`' bare default (`number`) and the JSDoc type was dropped.

## Investigation

`@type`'s value string already flows into a `TypeAnnotation{Name, Source:
"jsdoc"}` (`parser_stmts.go`, `parser_types.go`, `parser_classes.go`), which is
the identical slot an inline `: T` fills — so it inherits whatever the type
resolver understands (bare names, the `int8..uint64`/`float32` width keywords,
`T[]`). `@param`/`@returns` are the same seam, keyed by parameter name / applied
to the return slot; no codegen change is needed.

Two parser gaps had to be closed first: `jsdoc.Parse`'s regex
(`@(\w+)\s*(?:\{([^}]+)\})?([^\n@]*)`) captured a tag's brace body but *dropped*
the trailing text — which for `@param {T} name` is where the parameter name
lives. And the JSDoc type body can carry markers the resolver doesn't understand
(`...` varargs, trailing `=` optional, `[name]` optional-bracket).

## Decision

- **`Annotation` gains a `Text` field** holding the post-brace trailing text;
  `Parse` populates it for every tag. `@type`/`@erased` are unaffected (they
  read `Value`).
- **`Comment.ParamType(name)`** returns the stripped type of the `@param`/`@arg`/
  `@argument` whose name (recovered from `Text` via `paramName`, unwrapping
  `[name]`/`[name=default]`) matches; **`Comment.ReturnType()`** returns the
  stripped type of `@returns`/`@return`. `stripJSDocDecorations` removes a
  leading `...` and a trailing `=`.
- **`applyJSDocFuncTypes(fd, doc)`** (in `parseFunctionDeclaration`, after
  `parseFunctionRest`) fills each parameter that has **no inline annotation and
  no destructuring pattern** from a matching `@param`, and the return type when
  there is no inline `: RetType`. The value becomes a
  `TypeAnnotation{Name, Source: "jsdoc"}` — identical to an inline annotation.

**Precedence:** an inline TS `: T` wins; `@param` only *fills in* an otherwise
untyped slot. This differs deliberately from `@type`-on-a-variable (which
overrides its TS annotation) — a function may legitimately carry both real
inline types and stray doc comments, and silently overriding an explicit type
with a doc typo would be surprising.

## Implementation notes

- Applied post-hoc on the returned `*ast.FunctionDeclaration` rather than
  threading `doc` through `parseFunctionRest`'s six call sites — the top-level
  function declaration is the only position that carries a leading doc comment
  in practice, and the AST already exposes `Params`/`ReturnType` to fill.
- The supported type-expression grammar is exactly `@type`'s; the richer
  Closure/JSDoc forms (`Array.<T>`, `Object.<K,V>`, `function(...)`, real
  `?T`/`!T`/union) are a later stage (a dedicated type sub-parser) tracked in
  `docs/status/JSDOC.md`.

## Side effects discovered

`@type`'s existing grammar limits are now documented precisely (verified by
repro): a union/nullable/object-shape body in a JSDoc string silently resolves
to the first member or is a clean rejection — captured as ❌ rows on the new
JSDOC.md status page rather than left implicit.
