# ADR-00638: WebSocket binary frames — binary `.send()` and byte-exact binary receive

- **Relations**: `Implements TDD-00160`, `Extends ADR-00125` (frame codec), `ADR-00127`/`ADR-00128` (WS server/client), `ADR-00633` (wss)
- **Date**: 2026-09-02

## Context

The WebSocket stack (TDD-00039, and the `'upgrade'`/`wss://` work in
TDD-00158) was text-only by design. The loudest remaining WebSocket caveat on
[NETWORKING.md](../status/NETWORKING.md) — *"Neither side supports binary
`.send()` (`ArrayBuffer` payloads)"* — plus a lossy binary-receive path (a
decoded opcode-2 frame was copied into a `strlen`-terminated string, so a
payload with an embedded NUL truncated) were both consequences of that one
narrowing. Binary frames are the most commonly-hit WebSocket gap, so both the
send and the receive half are closed here. Design in [TDD-00160](../tdd/TDD-00160.md).

## Investigation

The frame codec `__kml_ws_frame_encode` already takes the opcode as a
parameter (`emit_websocket.go`, `runtime_websocket_client.go`); the send sites
simply hardcoded `i32 1` (text) and sized the payload with `strlen`. The
decode side already distinguished opcode 1 vs 2 and merged both into the
`isData` dispatch (emit_websocket.go:476–481) — the binary payload pointer and
length were already in hand, just funnelled into a string.

The browser-faithful receive shape is `ev.data: string | ArrayBuffer`. That is
not currently expressible: union members are limited to number/string/boolean,
object/interface/class, and ReadableStream (`emit_dynamic.go:138`) —
`ArrayBuffer` is not an allowed member, and `typeof anArrayBuffer === "object"`
collides with object members in the `typeof`-narrower. A union-typed `data`
would require a self-contained type-system arc, so it was rejected for this
feature and recorded as future work.

## Decision

**Send** — a shared `wsResolveSendPayload` (emit_websocket.go) inspects the
argument's compile-time type: a `string` stays a text frame (opcode 1, strlen
length); an `ArrayBuffer` (`{i64 size, ptr data}` header) or a byte-width
`Uint8Array` (element align 1, via `resolveArrayForHOF`) becomes a binary
frame (opcode 2) sized from the buffer/view — binary-safe. Any other type is a
clean compile-time rejection. Both send sites (server `emitWSConnectionSend`
unmasked, client `emitWSClientSend` masked) call it; only the mask bit/key
differ.

**Receive** — following the in-repo `req.body` / `req.bodyBytes()` idiom,
`WSMessageEventType` gains `isBinary: bool` plus two hidden fields
(`__kml_ws_msg_bytes`, `__kml_ws_msg_len`) backing a new `ev.dataBytes():
ArrayBuffer` method. `ev.data` stays the string view; `ev.dataBytes()` wraps
the exact payload bytes, no NUL truncation. Observable semantics are faithful
(every byte recoverable via a real ArrayBuffer); only the *typing* of `data`
diverges from the browser, tracked as the union follow-up above.

## Implementation notes

- `storeWSMsgBinaryFields` fills the three new fields on both dispatch paths.
  The server reuses the already-copied `strBuf` (exact bytes + trailing NUL)
  as the `dataBytes()` buffer — no extra allocation.
- The client dispatch is raw IR: `wsClientCallCallback` became a method
  (needs `WSMessageEventType`'s widened layout) taking
  data/isBinary/bytes/len; the four non-data events pass `false`/`null`/`0`,
  the message event passes `%disbinary`/`%dstrbuf`/`%dpayloadlen` (all of
  which dominate the call block). `buildEmptyWSMessageEvent` zero-inits the
  new fields so a non-message event's `ev.isBinary` reads false rather than
  malloc garbage.
- `ev.dataBytes()` is wired in `emit_call.go` and `inferExprType`
  (emit_exprs_types.go), guarded structurally on the hidden byte field so it
  matches only a WebSocket message event.

## Side effects discovered

None. The union-typed `ev.data: string | ArrayBuffer` fidelity gap (requiring
`ArrayBuffer` as an allowed union member) is the one documented follow-up,
captured as a caveat on the `WebSocket` status row.

## Verification

`TestE2EWebSocketBinaryRoundTrip` (tests/websocket_test.go): a client sends a
`Uint8Array([1, 0, 2, 255])` (masked binary frame); the server reads it
byte-exact via `ev.dataBytes()` — the embedded `0` and the `255` both survive
— and echoes the raw bytes back as its own binary frame; the client reads
`ev.isBinary === true` and all four bytes verbatim. Full WebSocket suite green
(`go test ./tests/ -run 'TestE2EWS|TestE2EWebSocket'`); `examples/websocket/
websocket_binary.ts` compiles and runs. Verified on macOS (M4).
