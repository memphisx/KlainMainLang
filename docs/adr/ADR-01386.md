# ADR-01386: libcurl driven through its socket API

- **Relations**: Implements TDD-00244; Extends ADR-01385
- **Date**: 2026-10-04

## Context

[TDD-00244](../tdd/TDD-00244.md) Stage 3. After
[ADR-01385](ADR-01385.md) the loop has no descriptor ceiling, but a fetch
on a socket at or above `FD_SETSIZE` still failed with "Couldn't connect
to server": `curl_multi_fdset` cannot report such a socket, so the loop
never waited on it. libcurl was also driven from several places with
`curl_multi_perform`: every loop pass, the scheduler step, each new
transfer, the keep-alive count, the fetch pump, the synchronous
`XMLHttpRequest` wait, and `http.get` with no loop. The last two waited in
`curl_multi_wait` or not at all.

## Investigation

- A first attempt set `CURLMOPT_SOCKETFUNCTION`/`CURLMOPT_TIMERFUNCTION`
  and kept `curl_multi_perform`. The socket callback was never called: only
  `curl_multi_socket_action` maintains libcurl's socket set. Every fetch
  then waited out its 30 s `CURLOPT_TIMEOUT`.
- The off-loop curl drives had to change with it. A traced test-par run
  (a log line on each subset-drive branch) found that
  `__kml_loop_turn`'s cannot-run result, `top_wait`'s and `spin`'s subset
  drives are never reached in the test corpus. The only hits were two
  request-body connection fibers, which [TDD-00244](../tdd/TDD-00244.md)
  Stage 5 owns. So no drive outside the loop depends on
  `curl_multi_perform`'s progress without readiness.
- The number of running transfers changes without a socket event when a
  transfer is removed (an aborted fetch). Counting only from socket events
  kept the loop alive forever after `fetch` with an aborted signal
  (`TestE2EFetchAbortedSignalThrows`).
- macOS's libcurl is built without `poll()` and waits in `select()` itself.
  It refuses a socket at or above `FD_SETSIZE` inside curl, whatever drives
  it.

## Decision

On POSIX (`fetch.c`):
- **The multi handle registers the socket and timer callbacks.** They
  keep a per-thread table of the sockets libcurl waits on, with their
  directions, and its next deadline (0 for none).
- **Every drive is `curl_multi_socket_action`**:
  - `kick()` runs a timeout action. It serves whatever is due, starts a
    transfer just added, and refreshes the running count. The stored
    deadline is cleared only when it was due, because the timer callback
    reports changes only.
  - The loop's `__kml_curl_loop_perform(r, w)` acts on each watched socket
    the wait reported ready, then kicks.
  - A wait outside the loop (`__kml_curl_drive_once(ms)`: the synchronous
    `XMLHttpRequest`, `http.get` without a loop and its post-loop flush,
    the fetch pump) polls the table's sockets itself, bounded by the
    deadline, then acts and kicks.
- **The other call sites go through the same driver.** The scheduler step
  and a new transfer kick; the keep-alive check kicks and reads the
  running count.

`curl_multi_fdset`, `curl_multi_perform` and `curl_multi_wait` are
called only on Windows, until its loop moves to libuv in Stage 6: there
curl's sockets are Winsock handles, not small descriptors.

## Implementation notes

- `task.c` calls `__kml_curl_kick`, and `emit_http_client.go`'s drive and
  flush call `__kml_curl_drive_once`.
- The loop passes its ready sets to `__kml_curl_loop_perform`.

## Side effects discovered

- A fetch above fd 1024 still fails on macOS, inside the system libcurl's
  own `select()` (above). Only a different HTTP client would lift it there.
  It stays on BACKLOG §0 as a macOS-only gap.

## Verification

- New: `TestE2ELoopFetchAbove1024` (Linux): an HTTP server and a fetch
  with 1,100 descriptors open. Skipped on macOS (above) and on Windows
  (Stage 6).
- DeskMini: the Fetch, HTTP client, XHR, AbortSignal, EventSource,
  WebSocket and event-loop suites pass.
- Mac (M4): 150 sequential top-level fetches, the wait probes, and an
  aborted-signal fetch that exits.
- Full gates: Node304 test-par, DeskMini examples, Test262 strict and js.
