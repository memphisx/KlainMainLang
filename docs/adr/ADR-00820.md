# ADR-00820: Pooled binary fs writes and the pooled callback form

- **Relations**: `Implements TDD-00185`, `Extends ADR-00773, ADR-00774`
- **Date**: 2026-09-10

## Context

TDD-00185 made the one-shot `fs.promises` string ops genuinely non-blocking on
the blocking-work thread pool (ADR-00773/00774), but left two cases still
running inline on the event-loop thread — the two leftovers BACKLOG §1 tracked
under "real async streaming":

- **Binary `writeFile`/`appendFile`** (an `ArrayBuffer`/`TypedArray` body):
  `emitFsPromisePooled` returned `pooled=false` for these, so a body with an
  embedded NUL fell through to the inline explicit-length write.
- **The classic callback form** `fs.readFile(path, cb)`: `emitFsAsyncCallback`
  ran the throwing sync helper inline under a setjmp guard and fired the callback
  synchronously — never touching the pool.

For the microservice/REST-server target both freeze the single `select()`
reactor for the duration of the syscall; closing them removes the last inline
`fs` I/O on the priority-2 path.

## Investigation

- The pool's submit entry `__kml_pool_submit` (`threadpoolsrc/klainpool.c`) only
  carries `strdup`'d C strings, so it cannot convey an explicit byte length or an
  embedded NUL — the stated reason binary writes were declined
  (`emit_fs_async.go:181`). The inline path already had the explicit-length
  runtime helpers `__kml_fs_write_file_bytes` / `__kml_fs_append_file_bytes`
  (`emit_fs.go:168,188`), reused by the `copyfile` pool thunk.
- The callback form's blocker is GC reachability: the malloc'd pool item is
  invisible to Boehm, so a callback closure stored only there could be collected
  mid-flight under `-mm=gc`. Long-lived event-loop structures that hold JS
  pointers already solve this with `GC_malloc_uncollectable` (scanned, never
  collected) — timer nodes, channel endpoints, Map headers.
- A promise *reaction* is exactly such a structure: `emitAttachPromiseReaction`
  (`emit_promise_then.go:186`) pushes a `{closure, next}` node onto the promise's
  reaction list, and `__kml_pool_settle` → `__kml_promise_settle` →
  `__kml_promise_drain_reactions` runs it on the loop thread at drain time. So a
  callback attached as a reaction on the pooled promise stays rooted by the
  reaction node and runs on the right thread for free.
- The alternative — a `KML_CMP_CALLBACK` completion kind + a generic
  `__kml_pool_invoke_cb` C thunk — was rejected: a C-driven invoke erases the
  callback's static `(err)` vs `(err, data)` arity and data element type, and
  there is no uniform `(i64,i64)` closure-call convention (`emitCBCall`,
  `emit_func.go:3307`, coerces per declared param type). It would reinvent the
  per-site specialized runner the reaction desugar already gives in IR.

## Decision

**Binary writes onto the pool.** Add op ids `KML_OP_WRITEFILE_BYTES` /
`KML_OP_APPENDFILE_BYTES`, two IR thunks over the existing `*_bytes` helpers, and
a submit entry `__kml_pool_submit_write_bytes(opid, promise, path, data, len)`
that `strdup`s the path and `malloc`+`memcpy`s the byte buffer into a block the
work item owns — so no GC pointer crosses the thread boundary. `emitFsPromisePooled`
now routes an `ArrayBuffer`/`TypedArray` body through `emitFsPromisePooledBytes`
instead of declining.

**Callback form as pooled-promise + reaction.** `emitFsAsyncCallback` first tries
`emitFsPromisePooled` (which now also handles binary bodies). On success it
resolves the callback and calls `emitFsCallbackReaction`, which synthesizes a
per-site runner `@__kml_fs_cb_run_N(ptr %env)` — built through the
`emit_chan.go` IR-builder-swap idiom so it composes with `emitCBCall`. The runner
reads the settled promise's state/result words and invokes the callback via
`emitCBCall` (full arity/type reconciliation) with `(null, data)` on fulfil or
`(err[, empty])` on reject, reconstructing `data` from the words (a bare pointer
for `readFile`, a `{ptr,i64}` aggregate for `readdir`). The reaction env carries
the promise and the callback's closure header, keeping the callback GC-rooted.
Windows (no pool build) still falls back to the inline guarded path.

## Implementation notes

- `klainpool.c`: new `data`/`datalen` item fields, freed alongside `arg0`/`arg1`
  at both the stream-job and dispatch free sites.
- `threadpool.go`: `poolThunkSpec` gains an optional `params` override (the byte
  thunks take an `i64` length, breaking the derived ptr-only signature); the new
  `__kml_pool_submit_write_bytes` declaration.
- `emit_fs_async.go`: `emitFsPromisePooledBytes`, `emitFsCallbackReaction`,
  `emitFsCbRunner`, and helpers `loadPromiseWord` / `fsAsyncDataFromWords`. The
  byte op ids (`10`/`11`) must stay in sync with the `KML_OP_*` enum after
  `READSTREAM = 9`.
- The reaction runner reads promise fields 0/2/3 exactly as `__kml_pool_settle`
  writes them; `data` is tagged with `spec.resultTy` and coerced by `emitCBCall`,
  matching the inline form bit-for-bit (both are `ptr`-repr).

## Side effects discovered

None. The `-webview`/binary decline comment and the stale "no thread pool" file
header on `emit_fs_async.go` were corrected in passing.

## Verification

- New E2E tests (`tests/fs_async_test.go`): pooled binary write/append preserving
  an embedded NUL (Promise and callback forms), pooled callback `readdir` array
  delivery, and a deterministic non-blocking proof (a `setTimeout(0)` fires
  before the pooled read's callback). Example `examples/fs/fs_async_pool.ts`.
- Manual repros run in both default and `-mm=gc` mode (4 MiB round-trip; callback
  form write/read/readdir/error path) — GC rooting confirmed.
- `go build`, `go vet`, and the fs / async / promise / stream E2E suites pass.
