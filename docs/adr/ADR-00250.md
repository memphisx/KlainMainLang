# ADR-00250: One task-aware event loop — unifying the two program-exit loops (TDD-00084 Part B)

- **Relations**: `Implements TDD-00084` (Part B); builds on [ADR-00249](ADR-00249.md), [ADR-00244](ADR-00244.md), [TDD-00006](../tdd/TDD-00006.md)
- **Date**: 2026-08-19

## Context

Two program-exit loops existed, mutually exclusively dispatched (emitter.go): the
`select()`-based `__kml_event_loop_run` (runtime_http.go — listener, connections,
curl-multi, WebSocket, EventSource, timers) and the coroutine drive
`__kml_task_run_all` (runtime_task.go — pumps curl + resumes ready tasks +
microtasks, a busy loop, no timers). So a program mixing may-suspend async tasks
with a timer (or with EventSource/WebSocket/`http.listen`) got one loop or the
other — e.g. a `setTimeout` scheduled inside a suspending async fn never fired,
because `task_run_all` drives tasks but not timers. TDD-00084 Part B.

## Decision

**Option B2 — the event loop absorbs the task scheduler.** `__kml_event_loop_run`
gains a task drive at the top of each iteration (its `timerscan` block): drain
microtasks, `__kml_task_sched_step`, drain microtasks again, and record whether
any task is still active. That active-task flag is OR'd into the loop's
`anywork` liveness test (so an in-flight task keeps the loop alive), and forces a
zero-timeout `select()` while a task is active (the same busy-drive `task_run_all`
already did, so a task made runnable by another task's completion is stepped
promptly rather than blocked behind `select()`).

**Linking.** The three symbols the loop now references
(`__kml_task_active`/`__kml_task_sched_step`/`__kml_drain_microtasks`) are always
defined: their real versions when the program uses the task/microtask runtimes,
otherwise no-op stubs emitted at finalization (`emitLoopTaskStubs`, guarded by
`usedHTTP`). A pure EventSource/WebSocket program thus links a no-op task drive
and is byte-for-byte unaffected.

**Dispatch.** The exit dispatch routes a program mixing tasks with timers or
SSE/WS through the single task-aware `__kml_event_loop_run`
(`useFullLoop = usedEventSource || usedWSClient || (usedTaskRuntime && usedTimers)`;
`ensureHTTPRuntime` is pulled in for the task+timer case). A pure-task program
(fetch only) keeps the lighter `task_run_all`; a pure-timer program keeps
`timer_drain`; a pure-async program with neither (Part A) still links no loop and
no libcurl.

## Consequences

- A may-suspend program that also uses a timer, EventSource, WebSocket, or
  `http.listen` drives all of them to completion under one loop — a `setTimeout`
  inside a suspending async fn now fires.
- A pure EventSource/WebSocket/`http.listen`/timer program and a pure-task program
  are unchanged (no-op task drive / unchanged dispatch respectively).
- Known caveat (unchanged from `task_run_all`, waiter-list refinement is future
  work): while a task is in flight the loop busy-polls (zero-timeout `select()`) at
  full CPU — brief for a normal `await fetch`, but a long-running background task
  under an `http.listen` server would spin.
- Residual (not this ADR): a top-level `await` still drives via
  `__kml_task_await_ready` (curl + tasks only), so a timer is not fired
  *concurrently* during a top-level await — it fires once the await completes and
  the unified exit loop runs.

- `go build`, `go vet ./...` clean; full `go test ./...` green (macOS).
- New E2E test `TestE2ETaskPlusTimerFires` (a `setTimeout` inside a fetch-awaiting
