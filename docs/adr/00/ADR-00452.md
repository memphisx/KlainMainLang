# ADR-00452: interface `extends` lists with field merging; constructor types erased

- **Date**: 2026-08-29

## Context

Two related TS-oracle parse buckets: `expected {, got <` (45 — a generic
base in `interface X extends Base<T>`; the V1 parser skipped exactly two
tokens after `extends`) and `expected IDENT, got new` (66 — constructor
types `new (params) => R` in type positions).

## Decision

- `parseInterfaceDecl` now parses a full `extends` clause: a comma-
  separated list of bases, each optionally qualified (`ns.Base`) and/or
  generic (`Base<T, U>`). Simple (unqualified, non-generic) base names are
  recorded on a new `ast.InterfaceDeclaration.Extends`; qualified/generic
  bases are consumed and dropped as before.
- `registerInterfaces` gains a merge phase: base fields precede own
  fields, own re-declarations win, method signatures merge the same way;
  iterated to a fixpoint so multi-level chains resolve in any declaration
  order (a cycle just stops changing). Base names are retried under the
  owner's `__kml_modN` resolver suffix — the Extends list holds
  source-written names while the registry holds resolver-mangled ones
  (found when the merge silently did nothing on the first run).
- Constructor types: `new (params) => R` in a type position parses as the
  function type it structurally is — accept-and-erase, no first-class
  constructor values (`parseTypeAnnotationAtom` consumes the `new` when
  `(` follows).

Generic bases (`extends Boxed<number>`) parse but do not merge — their
literal use sites still reject on the missing fields, disclosed as a
status caveat (better than the previous whole-file parse failure).

## Implementation notes

`ast/nodes.go` (Extends field), `parser/parser_types.go` (extends clause +
`new` type atom), `codegen/llvm/emitter.go` (merge phase in
`registerInterfaces`).

## Side effects discovered

Un-gating `extends Foo<T>` exposed a **pre-existing infinite recursion**:
an infinitely expanding generic (`interface Foo<T> { x: Foo<Foo<T>> }`,
the corpus's `infinitelyExpandingTypes*` cases) sent `resolveType` →
`instantiateGenericInterface` → `resolveType` into unbounded recursion —
observed as a real TS-oracle hang (28 CPU-minutes on one case; the suite
has no per-case timeout). Fixed here with a depth cap (32) on generic
interface/alias instantiation: past the cap the remaining tail resolves
as an opaque empty object type — TS handles these lazily, so eager
expansion has no finite answer. Also added a `TS_VERBOSE=1` per-case
progress mode to the TS runner, which is how the hanging case was found.

## Verification

Mac. `tests/interfaces_test.go` (new file: merge E2E, constructor-type
E2E) and `examples/interfaces/extends_merge.ts` pass; interface/type/
generics E2E batch green; the two `infinitelyExpandingTypes` cases now
compile in milliseconds. TS oracle: agreement 5079 → 5084 (match-accept
1337 → 1356; most extends cases stack further blockers, so the headline
percentage holds at 54.9%). Node oracle unchanged (37).
