# TDD-00217: real `http.createServer` connection timeouts

- **Status**: Implemented
- **Date**: 2026-09-16

## Context

`http.createServer` accepted `requestTimeout`/`headersTimeout` only at Node's
disabled value `0`, and rejected `keepAliveTimeout` entirely (ADR-00977). A
positive value — the common slowloris-hardening configuration — was a
compile-time rejection because the fiber-per-connection dispatcher enforced no
per-connection idle deadline: a connection parked reading its request (or idle
between keep-alive requests) waited forever.

The reactor already computes a soonest-deadline that bounds its `select()` wait
(`%bestfire` for JS timers; the `%cmdlabs` "extra-deadline" slot for
EventSource-reconnect / fetch-`AbortSignal` / libcurl / spawn-timeout deadlines,
folded in without firing JS timers early — `runtime_http.go`). This gives us a
wake mechanism to hang connection deadlines off.

## Node semantics

- **`headersTimeout`** (default 60000ms): from connection established until the
  request headers are fully received. Exceeded → the connection is aborted.
- **`requestTimeout`** (default 300000ms): from connection until the entire
  message (headers + body) is received. Exceeded → aborted.
- **`keepAliveTimeout`** (default 5000ms): after a response completes on a
  persistent connection, how long to wait for the next request's first bytes
  before closing the idle socket.

`headersTimeout` and `requestTimeout` both run from connection start; the earlier
fires first while headers are still arriving, and once headers are in only
`requestTimeout` remains. `keepAliveTimeout` governs only the idle gap between a
finished response and the next request.

## Design

### Per-connection deadline, fd-indexed

A single fd-indexed global `@__kml_conn_deadline = [1024 x i64]` holds each
connection's current absolute monotonic-ns deadline (`0` = none) — the same
fd-space and 1024 cap as the existing `@__kml_conn_writepark` bitset. One value
per connection is enough because at any instant only one timeout is active
(headers *or* request *or* keep-alive-idle), and the dispatcher republishes it at
each phase transition. `@__kml_http_any_timeout` (i64, set at `listen` when any
timeout is configured) gates the whole feature so a server with no timeouts pays
one load+branch per loop iteration and nothing else.

### Dispatcher: publish the deadline at phase transitions

The three timeout values are compile-time constants (createServer options,
primary server in V1), baked into the dispatcher IR. Because both header- and
request-timeouts run from connection start, the *initial* deadline is
`connStart + min⁺(headersTimeout, requestTimeout)` — the smaller positive of the
two, computed at compile time. The dispatcher keeps two locals: `connStart` (ns)
and `phase` (1 = in-request, 3 = keep-alive-idle). Transitions, each a small
helper call (`__kml_http_arm_from(fd, base, timeoutNs)` — stores `base+timeoutNs`,
or `0` when `timeoutNs<=0`):

| Site (`emit_http.go`) | Action |
|---|---|
| connection start (before read loop) | `connStart = now`; arm `initialTimeout`; `phase = 1` |
| bytes read while `phase == 3` (`accumulateL`) | first byte of the next keep-alive request: `connStart = now`; arm `initialTimeout`; `phase = 1` |
| headers complete (`headersParsed = 1`) | re-arm `connStart + requestTimeout` (headers no longer bound it) |
| handler dispatch (`parseL`) | clear (no timeout while the handler runs / writes) |
| keep-alive re-arm ×3 (buffered / streamed / `res.write` tails) | `arm(now, keepAliveTimeout)`; `phase = 3` |

Clearing at dispatch is what makes a timeout impossible during response writes,
so the swept fiber is *always* parked on a read — see teardown.

### Reactor: fold + sweep

- **Fold** (`__kml_http_conn_next_deadline_ns`): the soonest active connection
  deadline, min-merged into `%cmdlabs` exactly like the spawn-timeout fold, so
  `select()` wakes by it without firing JS timers early. Returns `0` (no
  constraint) when the feature is off, so it never keeps the loop alive on its
  own.
- **Sweep** (`__kml_http_conn_sweep_timeouts`, called at the top of the loop
  body beside `__kml_abort_to_fire_due`): for each active connection whose
  deadline has passed, `shutdown(fd, SHUT_RDWR)` and clear the deadline. The
  parked read then returns EOF; the fd is readable, so this same iteration's
  `select()` returns it and the existing resume path unwinds the fiber through
  its ordinary EOF/`noReqL` cleanup. **No fiber is torn down from outside** — the
  reactor only shuts the socket and lets the fiber finish itself, which is why
  timeouts are cleared during the handler/write phase (a fiber parked on a
  *write* must never be resumed by an EOF-read).

### Teardown: silent close (V1)

V1 closes the timed-out connection without writing Node's `408 Request Timeout`
response first. The security-relevant behavior — bounding how long a slow or idle
connection ties up a fiber — is fully delivered by the `shutdown`. Emitting a 408
would require distinguishing plain from TLS connections in the reactor sweep (a
raw write to a TLS socket corrupts the stream); deferred as a documented caveat
with a clean follow-up (route the 408 through the TLS-aware `__kml_http_conn_send`
keyed off a per-fd TLS flag). fd reuse is safe: `append_conn` clears the new fd's
deadline, and the sweep clears on expiry.

### Scope / caveats (V1)

- Primary server only (like `'close'`/`'clientError'`); an additional
  `createServer` still rejects a positive timeout.
- Silent close, no 408 body (above).
- HTTP/2 not covered — the h2 dispatch path is synchronous and separate.
- `keepAliveTimeout` governs the idle gap; the advertised `Keep-Alive: timeout=5`
  header value is still independent of the configured number (cosmetic).

## Staging

Single stage — all three timeouts land together (they share the deadline slot and
sweep). The 408 body and h2/additional-server coverage are documented caveats,
not sub-stages of the core mechanism.
