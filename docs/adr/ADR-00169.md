# ADR-00169: Generalized call dispatch + object literal method shorthand

- **Relations**: Extends [ADR-00153](ADR-00153.md); reuses [TDD-00060](../tdd/TDD-00060.md)'s function-expression machinery
- **Date**: 2026-08-12

## Context

A pass over the Test262 conformance harness's largest failure buckets (prompted directly, not found in passing) looked for genuinely missing, high-impact features rather than more early-error edge cases. Two of the largest buckets turned out to be well-scoped, real gaps rather than variants of anything already tracked:

- **"only simple function calls are supported" (4720 files, the single largest bucket)**: `emitCall`'s callee dispatch special-cases specific expression shapes (bare identifier, member expression, index expression, arrow/function-expression IIFE) instead of a general "evaluate the callee, call it if it's function-typed" fallback — so `f()()`, `(cond ? f : g)()`, and calling a plain object's function-typed field's own call result all failed, even though the underlying closure-call machinery (`emitClosureCallByPtr`) already handles any function-typed value regardless of the expression that produced it.
- **"expected }, got (" (3859 files)**: object literal method shorthand (`{ foo() {...} }`) doesn't parse at all — confirmed directly (`const obj = { valueOf() { return 42; } }` fails to parse). Object literals only supported `key: value`, shorthand `{x}`, spread, and computed keys; `key: function(){...}` (the desugared form) already worked, so this was purely a missing parser shorthand.

A third large bucket, `new obj.method()` (~3040 files, "expected (, got ."), was investigated and deliberately not picked up — it's Test262's own `not-a-constructor` idiom (calling `new` on a non-constructor to verify a `TypeError`), not a pattern real TypeScript code uses; supporting an arbitrary `new`-expression target doesn't fit this compiler's static-type model well and has low real-world value relative to its cost.

## Investigation

**Call dispatch**: `emitCall`'s existing branches for a function-typed object field (`mem.Property` fallback) and array-element call (`IndexExpression`) already used the exact same pattern this fix generalizes — evaluate the sub-expression, check `.IsFunc`, dispatch via `emitClosureCallByPtr`. `inferExprType` already has cases for `*ast.CallExpression` and `*ast.ConditionalExpression` (needed to know a chained/conditional callee's own function-ness ahead of emitting it), so the fallback needed no new type-inference machinery — but did surface one real gap: `inferExprType`'s own `*ast.CallExpression` case had no fallback for calling a plain (non-class) object's function-typed field (`obj.getHandler()` where `getHandler: () => T`) — every branch there was either a hardcoded built-in name or a class-method lookup. Confirmed directly: `b.getHandler()()` (needing to know `b.getHandler()`'s own return type before the outer call could dispatch) failed even after the `emitCall` fallback existed, because `inferExprType` couldn't answer "what does this call return" for that shape. Fixed by adding a fallback there too, delegating to the `MemberExpression` case's own already-correct general object-field-type resolution.

**Object literal methods**: `parseObjectLiteral` parses each property's key then branches on `COLON` (explicit value) vs. a bare `IDENT` key (shorthand). Class methods already parse the identical `(params): RetType { body }` tail via the shared `parseFunctionRest`, called right after the member name once `p.check(lexer.LPAREN)` is seen (`parser_classes.go`). The same check, inserted before the existing `COLON`/shorthand branches, lets any property key (identifier, string, or numeric literal — `PropertyName` isn't restricted to identifiers in real JS either) be followed by a method body instead. No `async`/generator method shorthand: confirmed class methods don't support either yet (a separate, pre-existing gap, not something to newly introduce inconsistently here).

**`this` inside a method-shorthand body**: confirmed this fails cleanly today ("'this' is only valid inside a method or constructor body"), not silently. A class method's `this` has a known static type because it comes from the enclosing (nominally-typed) class; an object literal has no nominal type at all, so giving `this` a real static type — and then threading the object's own pointer into the call as an implicit first argument at every `obj.method()` call site — is new, non-trivial design work, not a mechanical extension of what this fix builds. Left as a documented, deferred gap rather than attempted here.

## Decision

1. `codegen/llvm/emit_call.go`: add a general fallback at the end of `emitCall`'s dispatch chain (after every more-specific branch, including the import-forgot diagnostic, so a more helpful error still wins when both could apply) — if `inferExprType(ex.Callee).IsFunc`, evaluate the callee and dispatch via `emitClosureCallByPtr`.
2. `codegen/llvm/emit_exprs_types.go`: add a matching fallback to `inferExprType`'s `*ast.CallExpression` case — if the callee is a `MemberExpression` whose own inferred type `IsFunc`, return its `FuncRetType`.
3. `parser/parser_literals.go`'s `parseObjectLiteral`: after consuming a property's key token, check for `LPAREN` before the existing `COLON`/shorthand checks; if present, parse the method body via `parseFunctionRest("", false, false)` and wrap it as an anonymous `*ast.FunctionExpression` value — the same value shape `key: function(){}` already produces, so no codegen changes were needed on the value side at all.

## Implementation notes

- Files touched: `codegen/llvm/emit_call.go`, `codegen/llvm/emit_exprs_types.go`, `parser/parser_literals.go`.
- The object-literal-method fix required zero codegen changes — `emitObjectLiteral`/`emitObjectLiteralWithHint` already handle a `*ast.FunctionExpression`-valued property exactly like any other value expression, since `key: function(){}` already worked before this ADR.

## Side effects discovered

Comparing full Test262 pass lists before/after (via `tools/conformance -passlist`) found the net pass count unchanged (4499 → 4499) despite both fixes being real, verified improvements — 4 genuine new passes exactly offset by 4 new regressions, all four regressions the same accidental-pass-via-blanket-rejection pattern already documented in [ADR-00168](ADR-00168.md):

- `language/expressions/object/method-definition/name-param-redecl.js` / `name-super-call-param.js`: object-literal methods now parse for real, exposing that this compiler doesn't check "a `let`/`const` in a method body can't redeclare a parameter name" or "an object-literal method can't contain `super()`" — neither implemented anywhere (the first is actually a general function-body early-error rule, not method-specific; this compiler has no lexical-redeclaration-vs-parameter check for any function shape). Deferred, same class of gap as ADR-00168's own deferred 7.
- `language/expressions/optional-chaining/early-errors-tail-position-optchain-template-string(-esi).js`: `a?.fn\`hello\`` (a tagged template immediately after an optional-chain member) should be a SyntaxError; this compiler has no such check. Low real-world value (this exact combination is rare and its own spec rule is narrow).

New genuine passes: `language/expressions/assignmenttargettype/simple-complex-{callexpression,memberexpression}{,.identifiername}-expression.js` — real static-semantics checks that only became reachable once an object literal combining a computed key with a method (`{ [v]: 1, f() {} }`) could parse at all.

Also observed: the object-literal-method fix eliminated its own specific parse error everywhere in the corpus (the "expected }, got (" bucket dropped to zero), but many of the same files hit a *different*, still-missing feature further into the same file — e.g. destructuring in a `catch` clause binding (`catch ({ f }) {}`, confirmed absent), now the 4th-largest bucket at 3286 files. Not picked up here — noted for a future pass, not silently dropped.
