# TDD-00067: Aligning the PCRE2 RegExp backend with ECMAScript semantics

- **Status**: Not Started
- **Date**: 2026-08-17

## Context

RegExp shipped ([TDD-00035](TDD-00035.md), ADR-00114–ADR-00120) on a PCRE2 backend: the JS pattern string is handed **verbatim** to `pcre2_compile_8`, and the only compile options ever set are `PCRE2_CASELESS` (`i`), `PCRE2_MULTILINE` (`m`), and `PCRE2_DOTALL` (`s`) — assembled in `__kml_regex_parse_flags` (`codegen/llvm/runtime_regexp.go:98`). The base option set is `0`. Nothing translates or normalizes the pattern between JS syntax and PCRE2 syntax (confirmed: no preprocessing pass in `codegen/llvm/emit_regexp.go`).

That means the engine currently exposes **PCRE2 (Perl) regex semantics, not ECMAScript semantics**. For ASCII patterns the two dialects mostly coincide, which is why the shipped feature looked complete against its own hand-written examples/tests — but Test262 exercises exactly the edge cases where they diverge, and those are silently wrong (wrong match, wrong result string) or hard-error at runtime.

Surfaced during the machine switch back to Apple Silicon: `make conformance` scored ~10 files lower on Mac (pcre2 10.47) than the committed Linux baseline, concentrated in `annexB/built-ins/RegExp/RegExp-*-escape-*` (`RUNTIME_NONZERO_EXIT`). That Mac/Linux delta is a *symptom*, not the disease: because patterns pass through verbatim, behavior is at the mercy of whatever the linked PCRE2 version does with a given escape, so two PCRE2 versions disagree. The broader goal scoped here is to make RegExp match JS/TS expectations as Test262 defines them — the version-divergence falls out of that for free.

Scoped as investigation → design now; implementation is a separate, staged follow-on (this document sets the stages).

## Investigation

Five minimal probes, each isolating one dialect gap, compiled and run on Mac (Apple Silicon, pcre2 10.47). Every one diverges from real JS:

| Probe | JS result | This compiler | Root cause |
|---|---|---|---|
| `/foo$/.test("foo\n")` | `false` | `true` | PCRE2 `$` matches *before a final newline* by default; ES `$` (no `m`) matches only at true end. Needs `PCRE2_DOLLAR_ENDONLY` whenever `m` is absent. |
| `/(a)?b\1/.test("b")` | `true` | `false` | Backref to an **unset** group: ES matches empty string; PCRE2 default fails the match. Needs `PCRE2_MATCH_UNSET_BACKREF`. |
| `/\u0041/.test("A")` | `true` | **throws** `PCRE2 does not support \F, \L, \l, \N{name}, \U, or \u` | ES `\uXXXX`/`\xXX` escapes; PCRE2 default doesn't accept `\u`. Needs `PCRE2_ALT_BSUX \| PCRE2_EXTRA_ALT_BSUX`. |
| `"a\u2028b".replace(/./g,"X")` | `"X\u2028X"` | `"XXXXX"` | Two gaps at once: (a) no `PCRE2_UTF`, so the subject is scanned as raw UTF-8 **bytes** — `.` matches each of U+2028's 3 bytes; (b) ES `.` must *not* match the line terminators `\n \r \u2028 \u2029`. |
| `/\d/u.test("5")` | `true` | `true`, but `u` is **silently ignored** | The `u` flag isn't validated or implemented (the flag-validation gap already recorded in ADR-00166). It happens to be harmless here; it is not for `\u{…}`, surrogate handling, or strict-syntax patterns. |

Three of these (`$`/newline, unset backref, `\u`) are undisclosed correctness bugs — `docs/status/REGEXP.md`'s Caveats section documents the *known* V1 narrowings (`.test` offset-0, no `.groups`, `$1`–`$9` only, etc.) but not these. They are noted here as deferred rather than fixed in passing, because the fix *is* this work.

## Design

The gaps fall into three tiers by implementation cost, which map cleanly onto staged delivery.

### Option A — Compile-option alignment (low risk, ASCII-safe, high value)

Add the PCRE2 compile options that move the dialect toward ECMAScript without changing behavior for the ASCII patterns that already work:

- `PCRE2_ALT_BSUX | PCRE2_EXTRA_ALT_BSUX` — interpret `\u`, `\x`, `\0` the ECMAScript way (fixes the `\uXXXX` **throw**, the single highest-frequency everyday-JS gap here).
- `PCRE2_MATCH_UNSET_BACKREF` — unset-group backref matches empty.
- `PCRE2_DOLLAR_ENDONLY`, set **only when `m` is absent** — `$` anchors at true end. (With `m`, ES and PCRE2 already agree that `$` matches at line boundaries.)

All three are per-compile option bits OR-ed into the existing `optout` in `__kml_regex_parse_flags`; the only control-flow change is making `DOLLAR_ENDONLY` conditional on the multiline flag already parsed there. No codegen-shape or offset-math change. This is the recommended first stage — it is where the conformance-per-effort ratio is highest and it removes a hard runtime error.

### Option B — Unicode correctness (`PCRE2_UTF`/`PCRE2_UCP` + the index-space reconciliation)

Enable `PCRE2_UTF` (and `PCRE2_UCP` for `\w`/`\s`/`\b` Unicode semantics) so `.` and character classes operate on code points, not bytes. The hard part is **not** the flag — it is that PCRE2_8 reports match offsets in **UTF-8 byte** positions, while ES `.index`/`lastIndex`/`.exec` slicing/`.split` boundaries are defined in **UTF-16 code-unit** positions, and this compiler stores strings as UTF-8 internally. Today, for any non-ASCII subject, `.index`/`lastIndex` are already byte offsets masquerading as JS indices — a latent divergence Option B forces a decision on (convert byte<->UTF-16 offsets at every boundary, or formally adopt a different index space). ES `.` must also exclude `\u2028`/`\u2029`, which interacts with PCRE2's newline convention (`PCRE2_NEWLINE_*`). Larger, touches every offset-producing site in `emit_regexp*.go`.

### Option C — Full ES-dialect normalization pass (most faithful, most work)

A pattern-translation front end (JS regex source → PCRE2 source) to handle what options can't: Annex B legacy octal/decimal escapes (`\1` with no group 1 = octal char), the `u`/`v` code-point dialects (`\u{…}`, `\p{…}`, set operations), and ES-specific character-class edge cases. In spirit this is a small hand-rolled ES-regex parser/normalizer in front of PCRE2 — the same "hand-roll the JS-specific layer, delegate the engine" split TDD-00035 already chose. Defer until A and B are measured.

### Dialect selection via a compiler flag

Options A–C are not just a one-way migration that silently changes everyone's match results — they are points on a faithfulness spectrum, and each is a legitimate thing to *want*. Expose the level as a compile-time flag, following the existing `-mm=`/`-globals=` convention (`-regex=<mode>`), whole-program:

- **`ecmascript` (default)** — full ES fidelity: the Option C normalization pass layered over A + B. This compiler exists to run TypeScript/JavaScript, so matching the language's own regex semantics is the correct default and the project's target.
- **`es-unicode`** — Option B: the option-level alignment plus `PCRE2_UTF`/`PCRE2_UCP` and byte↔index reconciliation, but no Annex-B/`u`-dialect normalization pass. Unicode-correct, lighter than full `ecmascript`.
- **`es-ascii`** — Option A: the cheap compile-option alignment only. ASCII-faithful to ES; deliberately does *not* pay for UTF matching or a normalization pass. For programs whose patterns and subjects are known-ASCII (a large fraction of CLI/microservice use), this is the smallest and fastest mode that is still ES-correct where it matters.
- **`pcre`** — today's behavior verbatim: the pattern goes to PCRE2 with only `i`/`m`/`s` mapped and no ES wrapping. This is a **feature, not a fallback** — PCRE2 is a more feature-complete engine than the ECMAScript dialect (recursion/subroutines, possessive quantifiers, conditionals, callouts, `\p{…}` in PCRE syntax), and a developer who wants that power, or who is porting an existing PCRE pattern, can ask for it explicitly and knowingly accept non-ES semantics.

Framing note: PCRE2 being the more *powerful* engine does not make it the more *correct* one here. ECMAScript regex is a distinct dialect, not a subset — it has behaviors PCRE2's defaults get wrong (the three Known-correctness bugs) and legacy Annex-B semantics PCRE2 doesn't reproduce at all, while PCRE2 has features ES lacks. Two overlapping supersets of a common core is precisely the situation a mode selector fits: `ecmascript` for "run my JS/TS as written," `pcre` for "give me the full engine."

### Recommended path

Implement the stages in order — A, then B, then C — because each is a strict prerequisite of ES fidelity for the next: Stage 1 = Option A, measured against a RegExp-focused Test262 subset before/after; Stage 2 = Option B, gated on the index-space decision below; Stage 3 = Option C, only for the residual after A + B. Each stage is independently shippable and independently improves the conformance number.

The flag rides along for free: `-regex=pcre` is available from day one (it is today's behavior); each completed stage lights up its mode (`es-ascii` after A, `es-unicode` after B); and the default points at the highest ES stage implemented so far, becoming the true `ecmascript` target once C lands. That keeps every intermediate release honest — the default is always the most ES-faithful mode that actually exists — without ever silently regressing a program that wanted raw PCRE.

| RegExp-focused conformance subset runner | ❌ Missing | `tools/conformance` runs the whole corpus; a `built-ins/RegExp` + `annexB/**/RegExp` filter would give a tight before/after signal per stage without a full 53k-file run. |

## Open questions

- **Index space (the crux of Option B).** Do `.index`/`lastIndex`/`.exec` offsets get converted from PCRE2 byte offsets to true UTF-16 code-unit indices (full ES fidelity, a conversion at every boundary), or does this compiler formally document a UTF-8 code-point index space and accept the divergence? This decision blocks Option B and should be made before it starts — it may also interact with how the rest of the string layer reports indices.
- **`u`/`v` flags.** Approximate `u` via `PCRE2_UTF|PCRE2_UCP` (cheap, imperfect — offset space and some syntax still differ), or hold it as an explicit "not yet" error until Option C can do it properly? The `v` (unicodeSets) flag is strictly beyond PCRE2 options.
- **Newline convention for `.` and `$`.** ES line terminators are exactly `\n \r \u2028 \u2029`; choosing a `PCRE2_NEWLINE_*` convention that reproduces that for both `.` (excluded) and `$`/`m` (boundaries) without a per-pattern rewrite needs verifying against the corpus.
- **Version pinning vs. option-hardening.** Once Option A sets explicit options, is the residual Mac/Linux delta zero, or does some behavior still depend on the linked PCRE2 version (arguing for a documented minimum PCRE2 version)? Measure after Stage 1.
- **Flag and mode names.** `-regex=` vs `-regexp=`; `es-ascii`/`es-unicode`/`ecmascript`/`pcre` vs a shorter or numbered set. Should match whatever reads most naturally alongside the existing `-mm=`/`-globals=` flags.
- **Cost of an `ecmascript`-by-default.** Shipping Option C as the default means the normalization pass + UTF matching are on unless opted out. Correct for a correctness-first target, but the `es-ascii`/`pcre` modes exist precisely for the size/perf-sensitive case — measure the normalization-pass and `PCRE2_UTF` overhead (binary size, match throughput) to confirm the default isn't painful for the common ASCII program, and to size the win from dropping to `es-ascii`.
- **Flag granularity.** Whole-program (simplest, matches `-mm=`/`-globals=`) vs. a per-`RegExp` pragma. Whole-program is the V1 recommendation; a per-pattern override is a possible later refinement if real programs need to mix a `pcre`-power pattern into an otherwise-`ecmascript` build.
- **Disclosure.** *Resolved 2026-08-17* — the three correctness bugs (`$`/newline, unset backref, `\u` throw) are now disclosed under `docs/status/REGEXP.md`'s **Known correctness bugs**, with the Strict Coverage note confirming the 2/13 count is unchanged (each lands on an already-excluded row). Stage 1 will erase bugs 1 and 3 and can then trim that note.
