# TDD-00095: TS `namespace` declarations with function merging

- **Status**: Implemented
- **Date**: 2026-08-22

## Context

Real TS/JS has function/object duality: one binding can be both callable
(`assert(x)`) and a property carrier (`assert.sameValue(...)`). This
compiler's flat model has no representation for it, which forced the Test262
harness shim to pick the namespace form only — leaving every file that uses
the bare-call form (631 in the current corpus, measured from the blocked-by
histogram's faillist) permanently blocked, and leaving a real TS core
feature (`namespace`, including its signature declaration-merging idiom)
unimplemented.

## Design

Three options considered:

1. **TS `namespace X { ... }` + function merging** (chosen). The exact
   mechanism TypeScript itself defines for callable-namespace duality:
   `function assert(...)` merged with `namespace assert { export function
   sameValue(...) }`. A genuine language feature — usable by any program,
   not just the harness.
2. Compiler special-case making a class callable (dispatch bare call to a
   designated static). Rejected: not TS, invents semantics.
3. Runner-level textual rewrite of bare `assert(` calls in harness includes.
   Rejected: doesn't help test files that use the bare form directly (the
   majority of the blocked set), and starts down the road of editing inputs.

### V1 scope

- Top-level `namespace X { ... }` only; members are `export function` and
  `export const` declarations. No nesting, no `export namespace`, no
  non-exported members, no `declare namespace`.
- **Merging**: a top-level `function X(...)` may coexist with `namespace X`
  (either order). Same-name class/variable collision stays an error.
- **Desugaring in the parser**: each member lowers to an ordinary top-level
  declaration named `X__kmlns_<member>`, and the parser records the
  namespace's member set in the AST program (`ast.Program.Namespaces`).
  `__kmlns_` cannot appear in user identifiers (no `__` prefix collision in
  practice; the same convention other internal manglings already rely on).
- **Member access**: `X.member(args)` and value-position `X.member` resolve
  through the namespace table (checked before generic member emission, only
  when `X` isn't shadowed by a local). A bare call `X(...)` resolves to the
  merged function as before — no dispatch change needed.
- Resolver/multi-file: namespaces V1 are single-file (the entry file or one
  imported file's own body); `export namespace` across modules is out of
  scope.

## Open questions

- Whether `export const` members need value-position support beyond calls
  (V1 implements reads through the same mangled-name lookup).
- Whether namespace merging should ever extend to interfaces (TS allows it);
  no current consumer.
