# ADR-01577: Closure flow follows tsc's control-flow container

- **Relations**: Extends ADR-01572, Implements TDD-00230
- **Date**: 2026-10-11

## Context

Comparing the TypeScript acceptance suite's strict lane with its baseline
showed 27 new false rejections reported as TS7034 ("variable implicitly has
type 'any' in some locations"), including all three
`capturedLetConstInLoop` cases. tsc accepts
`let x; (function () { return x })` and `let y; y = 1; const k = () => y`.
Since TypeScript 5.4, a closure created after a mutable local's last
assignment continues its creator's flow. An evolving binding read there has
the type it evolved to at that point, not an implicit `any`.

The checker reported TS7034 for every captured read of an evolving binding,
before consulting `ClosureNarrows`, which already models the 5.4 rule for
typed bindings. `ClosureNarrows` had a gap of its own: it compared only
assignment and read positions. A hoisted function declaration therefore
saw narrowing that tsc denies (`function f() { return x.length }` after
`let x: string | undefined = "a"` was accepted; tsc reports TS18048).

## Decision

- An evolving binding's captured read reports TS7034/TS7005 only when
  `ClosureNarrows` says the closure does not continue its creator's flow.
  Otherwise the read is typed along that flow.
- `ClosureNarrows` crosses only function expressions and arrow functions
  between the read and the declaring function (tsc's
  `getControlFlowContainer`). The binder records each reference's scope
  (`refScope`) for this.

## Verification

- Both programs above compile, and the hoisted case reports TS18048 at the
  same position as tsc 5.9.3.
- Checker unit cases cover all three.
- Mac: checker and binder unit tests.
- Linux (DeskMini and Node304 kmlbox): tsdiag, the TypeScript suite and the
  full gates.
