# TDD-00086: Generator protocol completion — `.throw()`, `.return()`, `yield*`

- **Status**: Implemented
- **Date**: 2026-08-20

## Context

Generators (TDD-00061/ADR-00172) implement `.next()`, `yield`, and `yield`'s
sent-value resume over a per-instance ucontext fiber. Three pieces of the
iterator protocol are still missing, all clean rejections today:

- **`.throw(e)`** — inject an exception at the generator's current suspension
  point, so a `try/catch` around the `yield` in the body can handle it, and an
  uncaught one propagates to the `.throw()` caller and finishes the generator.
- **`.return(v)`** — force the generator to complete as if `return v` ran at the
  suspension point, running any enclosing `finally` blocks, and yield
  `{value: v, done: true}`.
- **`yield*` (delegation)** — iterate an inner iterable, re-yielding each of its
  values, forwarding sent values (and, fully, `.throw()`/`.return()`) into the
  inner iterator, and evaluating to the inner iterator's own return value.

These matter because generators are the substrate for iteration protocols and
(fused with the task scheduler, TDD-00085) async iteration; a generator that
can't be `.throw()`n into or `.return()`ed can't model cancellation or resource
cleanup, and `yield*` is how generators compose at all.

A pre-existing bug surfaces here and is folded into the work: **a `return` inside
a generator's `try/finally` does not run the `finally`** — `emitGeneratorReturn`
suspends done=true without calling `emitPendingFinallys` (verified: the `finally`
body simply never runs). `.return()`/`.throw()` both depend on finally-on-exit
working, so this is fixed as part of Stage 2.

## Design

### Resume-mode dispatch at the `yield` point (the core mechanism)

Today a resumed `yield` unconditionally reads `__sent` and continues. To let a
`.next()`/`.throw()`/`.return()` each resume differently, the generator carries a
**resume mode** the resumer sets before swapping in, and every `yield`'s
post-swap code dispatches on it. New generator-struct fields:

- `__resumeMode` (i64): `0` = next (return `__sent`), `1` = throw, `2` = return.
- `__thrown` (ptr): the error object a `.throw(e)` injects (mode 1).
- `.return(v)`'s value reuses the existing `__sent` slot (same element type).

`emitYieldExpression` becomes, after `emitGeneratorSwapToCaller` returns:

```
  mode = load __resumeMode
  switch mode: [1 -> throwL, 2 -> returnL], default nextL
throwL:
  err = load __thrown
  call void @__kml_throw(ptr err)      ; body's try/catch handles, else propagates
  unreachable
returnL:
  rv = load __sent
  <emitPendingFinallys>                ; run enclosing finally blocks (lexically correct here)
  emitGeneratorSwapToCaller(rv, done=true)
  ret void
nextL:
  sent = load __sent                   ; the yield expression's value
  ... (continues, sent used by the body) ...
```

Because this code is emitted at the `yield`'s lexical position, `e.pendingFinallys`
already reflects exactly the enclosing `try/finally`s, so mode 2's
`emitPendingFinallys` runs the right cleanup — the same call an ordinary `return`
statement makes. Mode 1's `__kml_throw` reuses the fiber-safe jmpbuf stack: a
`try` in the body pushed a jmpbuf at runtime, so the throw lands in its `catch`;
with no enclosing `try` it longjmps out to the jmpbuf the `.throw()` call site
pushes (below).

`emitGeneratorReturn` (the `return` *statement*) gains the missing
`emitPendingFinallys()` call before its done=true swap — the folded-in bug fix.

### Stage 1 — `.throw(e)`

`gen.throw(e)` dispatches (like `.next`) on `IsGenerator` in emit_call.go to a new
`emitGeneratorThrow`:

- **not started** (`__started == 0`): mark done; `__kml_throw(e)` to the caller —
  the body never runs (JS semantics).
- **done**: `__kml_throw(e)` to the caller.
- **started, suspended**: set `__resumeMode = 1`, store `e` into `__thrown`, push a
  jmpbuf around the swap-in. On normal swap-return the body caught the throw and
  either yielded again or returned — build `{value: __yielded, done: __done}` like
  `.next()`. On longjmp back (uncaught in the body), pop, mark done, and re-throw
  the caught error to the `.throw()` caller.

The swap-in save/restore (caller-ctx, GC stackbottom, pending-obj global) is
identical to `emitGeneratorNextByValue`; factor the shared swap into a helper
parameterised by the pre-swap field writes and the post-swap jmpbuf handling.

### Stage 2 — `.return(v)` (and the finally fix)

`emitGeneratorReturnMethod`:

- **not started / done**: mark done; return `{value: v, done: true}` without
  running the body.
- **started, suspended**: set `__resumeMode = 2`, store `v` into `__sent`, swap in.
  The body's `yield` resume (mode 2) runs enclosing finallys then swaps back
  done=true with `v` in `__yielded`. Build `{value: __yielded, done: __done}`.

V1 scope: a `finally` block that itself `yield`s during a `.return()` (which in JS
can resurrect the generator) is out of scope — a `finally` doing ordinary cleanup
is the case supported; a `yield` reached via a mode-2 return runs on the fiber and
would re-suspend, so detect and reject it rather than miscompile (open question
below on how cheaply that's detectable).

### Stage 3 — `yield* innerGen()` (delegation, no forwarding)

Lower `yield* E` inside a generator body to a loop over the inner generator
(`emitYieldStar`), requiring `E` to be a generator instance of the same element
type in V1 (a general iterable needs `Symbol.iterator`, TDD-00044):

```
inner = E                        ; construct once
r = inner.next(<zero>)
loop:
  if r.done: break
  sent = yield r.value           ; ordinary yield: re-emit each inner value
  r = inner.next(sent)
end:
  <yield* value> = r.value       ; the inner generator's return value
```

This reuses `emitGeneratorConstruction` + `emitGeneratorNextByValue` +
`emitYieldExpression` wholesale — no new fiber machinery. The `yield*`
sub-expression's value is the inner's final `.value`.

### Stage 4 — `.throw()`/`.return()` forwarding through an active `yield*`

To make a `.throw()`/`.return()` that arrives while delegating forward to the
inner iterator (JS semantics), the `yield r.value` inside the Stage-3 loop must
inspect the resume mode instead of blindly continuing: on mode 1 call
`inner.throw(err)`, on mode 2 call `inner.return(v)`, feeding the result back into
the loop's `r`. This needs the Stage-1/2 `emitGeneratorThrow`/`ReturnMethod` as
callable-on-a-value helpers (they already take an evaluated instance pointer, like
`emitGeneratorNextByValue`). Staged last because it composes 1–3; delegation
without forwarding (Stage 3) is already useful and independently shippable.

| Async-generator forwarding (`async *`) | Out of scope | `.throw()`/`.return()` on an async generator is a follow-on; this TDD is sync generators |

## Open questions

- **Mode-2 return through a `yield` in `finally`**: cheapest sound way to reject
  (or support) a `yield` reached during a `.return()`-driven finally. A body-scan
  for "yield lexically inside a finally" at registration is one option; another is
  a runtime "in mode-2 unwind" flag the `yield` checks. Leaning toward a
  compile-time rejection for V1.
- **`.throw()`/`.return()` result typing**: `.next()` infers `{value,done}` in
  `emit_exprs_types.go`; `.throw()` returns the same shape, `.return(v)` likewise —
  confirm the inference path is shared cleanly rather than three near-duplicates.
- **`yield*` element-type match**: V1 requires the inner generator's element type
  to equal the outer's. A widening/mismatch is a clean rejection; revisit if a
  concrete need for differing `TNext`/`TReturn` types appears (this compiler's
  single-`T` generator model collapses yield/return/next types anyway).
