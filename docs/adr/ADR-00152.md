# ADR-00152: Closing gaps found on a second pass over ADR-00151 (array-typed closures, class-method rest params, erased-generic forward references)

- **Relations**: Extends [ADR-00151](ADR-00151.md), [ADR-00105](ADR-00105.md), [ADR-00150](ADR-00150.md)
- **Date**: 2026-08-10

## Context

Asked to re-examine every scope cut made while shipping [ADR-00149](ADR-00149.md)/[ADR-00150](ADR-00150.md)/[ADR-00151](ADR-00151.md) (nested function declarations, fixed-point return-type inference, tagged template literals) rather than accept "documented as a known limitation" as the default resolution — several were quick unilateral calls that deserved either a real fix or a real justification, not a footnote. This ADR covers what a real second pass found and fixed, and draws an explicit, reasoned line around what's still deliberately out of scope rather than leaving that boundary implicit.

## Investigation and Decision

### 1. Class-method call with an array-literal argument plus trailing arguments

ADR-00151 found this (`f.build(["n="], 7)` failing "expression does not yield an array") and explicitly deferred it as "out of scope." Re-investigated instead of left alone: `emitClassCall` (`codegen/llvm/emit_classes.go`) had **no notion of `sig.HasRest` at all** — a strict `len(args) != len(sig.ParamTypes)` arg-count check, and a loop treating the rest slot's own declared array *type* as if it applied to one positional scalar argument. The free-function call path (`emitCallToFuncSig`) already had the correct `regularCount`/rest-packing shape; `emitClassCall` never got it. Fixed by porting that exact shape (own `regularCount`, a rest-packing tail identical to `emitCallToFuncSig`'s), covering both the direct-call and vtable-indirect-call (overridden method) paths. Not a corner case: **any** class method with a rest parameter was affected, not just ones also taking a leading array — confirmed via `sm.total(1,2,3,4)` (no array param at all) failing identically before this fix.

### 2. `@erased` generic function forward-reference

[TDD-00058](../tdd/TDD-00058.md)/[ADR-00150](ADR-00150.md) fixed the same-file forward-reference boundary for plain unannotated functions, explicitly noting the `@erased` generic case (a separate signature-building path, `buildGenericParamSig`) as "no confirmed repro yet" — an assumption, not a checked fact. Written a repro (`/** @erased */ function makeA<T>(x: T) { return makeB() }; function makeB() { return { val: 1 } }`) and confirmed it reproduced the identical bug. Fixed by extracting `buildErasedFunctionSig` (mirroring `buildFunctionSig`'s own extraction) and folding `@erased` unannotated declarations into the same `reinferUntilFixedPoint` sweep.

### 3. Array-typed closure parameters (the real fix, not just a cleaner rejection)

ADR-00151 broadened `emitClosureFunc`'s guard from "reject a destructured array param" to "reject any array-typed param" after confirming the narrower guard let invalid LLVM IR through — a strictly safer rejection, but still a rejection, and the reason it mattered was that an arrow function's tag-function `strings: string[]` parameter made an arrow function permanently unusable as a tag. Investigated whether this was actually fixable rather than accepting it as a structural limit, since [ADR-00105](ADR-00105.md) already fully designed how arrays flow through this compiler (a `{ptr,i64}` aggregate, or a boxed pointer as a nested-array element) — the closure ABI just never finished being taught it, unlike the named-function ABI.

Fixed for real, at every point a closure's array-typed parameter is bound or called:
- **`emitClosureFunc`** (`codegen/llvm/emit_func.go`): array parameters now expand into two LLVM params `(ptr, i64 len)`, mirroring `emitFunctionDeclAs` exactly — including reusing `unpackArrayPatternInto` for a destructured array parameter.
- **`emitClosureCallByPtr`** (a direct `closureVar(args)` call): decomposes an array-typed argument into its `(ptr, i64)` pair at the call site, and builds the indirect-call function-type string to match.
- **`emitCBCall`** (HOF/callback dispatch — `.map()` etc., `setTimeout`, `EventEmitter`, `.replace()`): same decomposition, for both the `cbClosure` and `cbNamed` branches — the latter meaning a **named function** passed as a HOF callback with an array parameter was equally broken before this fix, previously masked because `Type.IR` for an array is the bare marker `"ptr"`, so the old code silently passed the *address of* the `{ptr,i64}` aggregate's register as if it were a plain scalar pointer rather than actually decomposing it — invalid IR the moment anything exercised it, not merely mistyped.
- **Rest parameters on closures needed one more piece**: a closure *value*'s own `Type` (`FuncParams`) had no way to distinguish "one array-typed parameter" from "a rest parameter collecting N individual trailing call arguments" — `FuncSig.HasRest` exists for named functions, nothing equivalent existed for a closure value. Added `Type.FuncHasRest`, set wherever a closure's own function-type gets constructed (`emitArrowFunctionWithHints`'s real closure construction, and `inferExprType`'s separate, pre-existing duplicate computation used before any closure value exists yet — e.g. for an unannotated `const f = (...) => ...` binding, which reads the *inferred* type, not the real one, to define the symbol). `emitClosureCallByPtr` then gained the same `regularCount`/rest-packing shape as `emitCallToFuncSig`/`emitClassCall`. Also fixed the same latent bug `buildFunctionSig` already had a fix for but `inferExprType`'s arrow-function duplicate didn't: an *unannotated* rest parameter now defaults to `ArrayOf(TypeI64)` in both places, not a bare scalar.
- Capturing an array **variable** from the enclosing scope into a closure's environment is a different mechanism (an env slot holds one heap-cell pointer, not a `(ptr, i64)` pair) and is untouched — `gatherCaptures` still rejects it. Not the same gap as an array-typed *parameter*.

This directly means: an arrow function can now be used as a tagged-template tag (correcting ADR-00151's "structural consequence, not itself a bug" framing — it was a bug, in the sense that it was fixable, not a hard architectural wall) — with or without a `...rest` parameter.

### 4. Every callback-invoking array HOF method now supports a nested-array element too

[TDD-00029](../tdd/TDD-00029.md)/[ADR-00105](ADR-00105.md)'s own `rejectNestedArrayElem` doc comment already named the exact root cause: "closures don't decompose an array-typed parameter into `(ptr, i64)`." Once #3 above was fixed, this guard was provably obsolete for every method that only needed it *because of* that reason — confirmed by reading each site rather than assuming: `.map()`, `.forEach()`, `.filter()`, `.reduce()`, `.find()`, `.findIndex()`, `.findLast()`, `.findLastIndex()`, `.some()`, `.every()` (10 methods, `emit_arrays_hof.go` + `emit_arrays_search.go`) all invoke a callback via `emitCBCall`/`emitClosureCallByPtr`'s now-fixed decomposition. Each had its own raw, non-array-aware `load`/`store` for the element (bypassing `loadArrayElem`/`storeArrayElem`'s existing box/unbox handling entirely) — switched to the existing helpers, and the guard removed. `.find()`/`.findLast()` additionally needed a null-safe unbox for their own "not found" sentinel slot (a null box pointer, not yet a real boxed value) — added `loadArrayElemMaybeNull` rather than reuse `loadArrayElem` unconditionally, which would dereference null on a genuine no-match. Confirmed correct (not just "doesn't crash") by running the not-found path explicitly: `m.find(...)` with no match returns `null`, not garbage.

Three methods were checked and confirmed to need a **different, unrelated** fix, not this one, and are left rejected:
- `.indexOf()`/`.includes()`/`.join()` compare or stringify an element as a bare register directly — no callback involved at all, so #3's fix doesn't reach them; they'd need `emitElemEq`/stringification taught to unbox first, a different, self-contained piece of work.
- `.sort()`'s custom comparator runs through a C-ABI `qsort()` trampoline (`emit_arrays_sort.go`) with one fixed, hand-generated trampoline per element kind (i64/f64/str) — a fourth, array-aware trampoline is real, separate design work (its own function, its own box/unbox-under-`qsort`'s-raw-byte-pointers handling), not a two-line change like the other ten.
- `Object.groupBy`'s buckets store every element uniformly as a raw `i64` (`ptrtoint`'d for a pointer-shaped element) — a different storage scheme than a plain array's backing buffer, with no 16-byte-aggregate slot to begin with; would need its own redesign, not just a swapped load/store call.

`new Array<T[]>(n)` (construction, not consumption of an existing element) is unrelated to any of this and untouched.

### 5. Found while validating #3/#4: two more real, previously-undiscovered bugs

- **`.map()`/`.flatMap()`'s own `inferExprType` case only recognized a literal arrow-function callback** — `matrix.map(rowSum)` (a *named* function reference) silently fell through to "same type as the receiver," which happened to be harmless whenever the callback's return type coincided with the receiver's own element type (the overwhelmingly common case, e.g. mapping `number[]` through a `number → number` function) but was genuinely wrong otherwise — found via exactly the case this session's own testing produced (`number[][].map(rowSum: number[] → number)`, wrongly inferred as `number[][]` instead of `number[]`). Fixed with a small shared helper, `callbackReturnType`, resolving a callback argument's return type whether it's a literal arrow function, a named function, or a closure variable — the same three shapes `resolveCallback` (emit_func.go) already resolves for real emission, reused here purely for inference.
- **`s += "b"` (string `+=`) produced invalid LLVM IR outright** — `emitArith`'s `"+"` case reached the generic numeric `add` unconditionally; `s = s + "b"` always worked (`emitBinary` has its own string handling), `+=` never went through it. No test anywhere exercised `+=` on a string before this session. Fixed by routing `emitArith` through `emitStringBinary` when the compound-assignment target is string-typed, stringifying a non-string operand first for `+` specifically (mirroring `emitBinary`'s own mixed-type handling) — threading a new `pos ast.Pos` parameter through `emitArith`'s six call sites.

## Explicitly out of scope, found and not fixed

- **Spread in call arguments (`f(...arr)`)** — confirmed absent entirely (`unexpected token ... in expression`), independent of every fix above (reproduces for a plain top-level function, no arrays-as-parameters or classes involved). Not attempted: spreading a runtime-length array into a statically-typed rest slot, possibly combined with other positional arguments or multiple spreads, is genuine design space (how much of it is even representable without a length known at compile time; whether a spread into a *non*-rest fixed-arity parameter list needs a different rule) — the kind of decision this project's own standing practice requires a TDD for before implementation, not a mid-fix addition. Not previously documented anywhere in `docs/status/` either — a real, newly-found gap, distinct from the already-tracked "no working call-site array spread" note in `EVENT-EMITTER.md`'s own caveats (which only explained why `EventEmitter`'s single-payload-type design was chosen, not that this was a general, otherwise-undocumented language gap).
- A function-**type annotation** with a rest parameter (`let cb: (...args: number[]) => void`) — a different AST shape (`ast.TypeAnnotation.FuncParams` has no per-parameter `Rest` marker at all) than the arrow-function-**value** case this ADR fixes; no confirmed repro or expected use found, left alone rather than guessed at.
