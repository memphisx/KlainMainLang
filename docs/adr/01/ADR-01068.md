# ADR-01068: `klainmain -run` and the link directory honour `KML_SCRATCH`

- **Relations**: Extends ADR-01036 (the `KML_SCRATCH` knob)
- **Date**: 2026-09-22

## Context

BACKLOG §0 item 13: `klainmain -run` built its temporary binary under the OS temp directory even with
`KML_SCRATCH` set, so every `-run` on the SSD-conscious Windows box wrote the binary (and clang's own temporaries)
to `%TEMP%` instead of the RAM drive.

## Investigation

`internal/scratch.Apply()` (ADR-01036) redirects `TMP`/`TEMP`/`TMPDIR` for the process and its children — the test
runner (`tests/main_test.go`) and the conformance driver call it; `main.go` never did. `os.MkdirTemp("",
"klainrun-")` (`main.go`), the link directory (`hostclang.go`, `kml-link-`) and clang's `-save-temps`-free object
files all read the temp directory, so one call at the top of `main()` covers every write the CLI makes.

## Decision

`main()` calls `scratch.Apply()` right after flag parsing (before any temp-directory use); a bad `KML_SCRATCH`
value is a fatal, named error. No new flag — the variable is the knob.

## Implementation notes

`main.go` only. The `-run` message keeps printing the binary's real path, which now shows the scratch root.

## Side effects discovered

None.

## Verification

Windows: `KML_SCRATCH=R:\kml-scratch klainmain -run x.ts` reports `compiled: R:\kml-scratch\tmp\klainrun-…\x.exe`;
unset, the OS temp directory as before.
