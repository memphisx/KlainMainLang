# ADR-00527: `arr.sort()` result infers the receiver's array type

- **Relations**: Extends ADR-00152
- **Date**: 2026-08-31

## Context

`const sorted = arr.sort()` — capturing `.sort()`'s result in an unannotated
`const` — failed to typecheck as an array: `inferExprType`'s member-call switch
knew every other type-preserving array method (`reverse`/`fill`/`toReversed`/
`toSorted`/`concat`/`with`/`copyWithin`/`values`/…) returned the receiver's own
array type, but `"sort"` was simply absent from that case list, so the result
fell through to an untyped default and a later index/`.length` read errored.
`arr.sort()` with an explicit `: number[]` annotation already worked. Tracked as
a caveat on the `.sort(fn?)` status row.

## Investigation

`codegen/llvm/emit_exprs_types.go`'s `inferExprType` handles the type-preserving
array methods in one `case` returning `objTy` when `objTy.IsArray`. `.sort()`
sorts in place and returns the same array (identical element type), so it
belongs in exactly that case — the emit side (`emitArraySort`) already returns
`ArrayOf(elemTy)`, so only the inference side was out of sync.

## Decision

Add `"sort"` to the type-preserving `case` in `inferExprType`, alongside
`reverse`/`concat`/etc. No emit-side change — `emitArraySort` already produces
the array aggregate.

## Implementation notes

One-token change in `emit_exprs_types.go`. `"sort"` had no other handling
anywhere in `inferExprType`, so there was no conflicting branch to reconcile.

## Side effects discovered

None. The `.sort()` row keeps its two remaining caveats (the numeric-vs-
lexicographic default-sort divergence and the nested-array rejection), so it
stays out of Strict Coverage — this only removes the type-inference caveat.

## Verification

`TestE2EArraySortResultInfersArrayType` (new): an unannotated `const sorted =
arr.sort()` and `const ss = strs.sort()` are indexed, `.length`-read, and
`.join()`-ed. Existing `TestE2EArraySort` still passes. Verified on Mac (Apple
Silicon).
