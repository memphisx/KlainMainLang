# ADR-00482: Array.from iterables; JSON.stringify of map-backed dicts

- **Relations**: Clears TDD-00130's stringify deferral; extends [ADR-00107](ADR-00107.md)-era Array.from
- **Date**: 2026-08-29

## Context

Two long-standing status caveats: `Array.from` supported only the
array-like overload, and `JSON.stringify` of an index-signature /
computed-key dict was a rejection ("build it from Object.keys(...)").

## Decision

- **Array.from**: a Set yields its elements, a Map its entries (the
  existing `[K, V][]` tuple-array `.entries()` path), a string its
  characters (per byte — this compiler's string model; multi-byte UTF-8
  code points split, the same stance `charAt` takes). Inference mirrors
  each shape. Class iterators and plain arrays unchanged; generators
  remain the documented gap.
- **JSON.stringify of map-backed values**: a new
  `emitJSONStringifyMapDict` iterates the runtime key list — each entry
  rendered `"key":<value>` with the escaping `__kml_json_str_str` on
  keys, the value re-read through `__kml_map_str_get`, reinterpreted per
  the declared value type, and delegated to the existing recursive value
  serializer. Covers index-signature dicts, computed-key literals, and
  string-keyed `Map`s. Two disclosed deviations: a string-keyed Map
  serializes its *entries* (real JS gives `"{}"` — matching that would
  silently drop data), and a number-keyed Map is a clean rejection (JSON
  object keys are strings). Compact output only — the pretty-printing
  `space` argument isn't threaded through this path.

## Verification

Mac. `tests/json_test.go` (dict + escaping + Map) and
`tests/arrays_test.go` (Set/Map/string overloads) E2Es; `examples/json`
and `examples/arrays` extended; JSON + array batches green. Oracles
unchanged (TS 57.2%, Node 40) — corpus files using these stack further
blockers; the wins here are caveat clears.
