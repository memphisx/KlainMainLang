# ADR-02001: A builtin `new` that matches no generic overload has the interface's type

- **Date**: 2026-11-21

## Context

On the js lane `console.log(new Set(two).size)`, where `two` is an object
given `[Symbol.iterator]` by assignment, failed with `internal compiler
error: no type for NewSetExpression`. HEAD fails the same way.

## Investigation

- The checker types `new Set(x)` against `SetConstructor`'s overloads. An
  expando object matches neither `readonly T[]` nor `Iterable<T>`, so
  overload resolution has no answer.
- The fallback, `sameResultInterface`, gives the result of the first
  non-generic overload when every overload constructs the same interface.
  Set's and Map's overloads are all generic, so there was no answer and the
  expression stayed untyped.

## Decision

When every overload constructs one interface and none is non-generic, the
failed call has that interface's type with its type parameters as `any`
(`Set<any>`). tsc reports the call as an error and still types it from a
candidate. The strict lane still rejects the call; the js lane compiles the
untyped value it runs.

## Implementation notes

- checker/checker.go: `newBuiltinType`, `sameResultSymbol`.

## Verification

- Linux x86 (Node304): the `new Set(two).size` cases in
  `TestE2ECollectionPrototypeMethodReplaced` match Node. The checker unit
  tests and the collection E2E tests pass.
