# ADR-01904: destructured for-of variables in the checker; TS2488 for a bare `next()`

- **Relations**: `Implements TDD-00230` (P3.3 shadow buckets); corrects ADR-01896
- **Date**: 2026-10-21

## Context

- A destructured for-of variable (`for (const [k, v] of m)`, `for (const { x } of a)`) had no type: the checker typed only a plain loop variable, so every leaf was unanswered, Map entries included.
- An array pattern over `any` (`const [a, ...r] = x` with `x: any`) was unanswered too; tsc gives each element `any` and the rest `any[]`.
- ADR-01896 made a `next()` returning a primitive yield `any`, which made a class with only `next()` look iterable to the TS2488 check, which tested whether the checker found an iterated type. tsc requires `[Symbol.iterator]` for for-of whatever `next()` returns.

## Decision

- A destructured for-of variable is its leaf of the iterated element, through the same binding rule as a declaration (widened for `let` and `var`); a `for await` pattern stays unmodelled.
- An array pattern over `any` gives `any`, and `any[]` for its rest.
- The TS2488 check accepts a class only through a `[Symbol.iterator]` in its chain or a builtin base that iterates.

## Consequences

- The `assert` module's deep-equal rows go away; `for (const x of c)` over a class with only `next()` is rejected again in the strict lane.
