# TDD-00068: Object-model evolution — static reach vs. the dynamic/prototype model (TDD-00065 Stage 3c and beyond)

- **Status**: Not Started (direction decided below: object generics now; native dynamic/prototype model is the deferred endpoint; per-type shape descriptor rejected)
- **Date**: 2026-08-17

## Context

[TDD-00065](TDD-00065.md) Stage 3c — object rest (`const { a, ...rest } = obj`)
when `obj`'s shape is **not** statically known — was deferred when Stages 3a/3b
shipped ([ADR-00203](../adr/ADR-00203.md)/[ADR-00204](../adr/ADR-00204.md)).
Probing the three non-static sources (Stage-3b compiler) shows **object rest is
never the blocker** — each source fails to even be treated as an object, for a
reason unrelated to destructuring:

| Source | Result today | Actual blocker |
|---|---|---|
| generic `T` (`function f<T>(o: T)`) | `type argument is not supported in V1 (only number, string, boolean, and arrays of these)` | [TDD-00010](TDD-00010.md) V1 monomorphizes only over scalar/array type arguments — never object types |
| `any` (`function f(o: any)`) | `'o' is not an object` | [TDD-00062](TDD-00062.md) boxes `any` by reference with no static shape and no runtime field table |
| union of objects (`A \| B`) | `'o' is not an object` | [TDD-00043](TDD-00043.md) union V1 is scalar-members-only; object members of a union aren't representable |

The root cause is that this compiler's object model is **fixed-shape nominal
structs**: an object value is a bare struct pointer with no runtime descriptor of
its own fields. Every field access is a compile-time `FieldIndex` → GEP, so
`bindObjectRest` can copy "source visible fields minus named keys" only because
it has the static `Fields` list in hand (`codegen/llvm/emit_objects.go`). With no
static shape, there is nothing to enumerate at runtime.

That makes Stage 3c a symptom of a much larger question — **how far does the
object model move toward real JavaScript?** — that also governs `Object.keys`/
`for...in` over unknown shapes, dynamic property add/delete, prototype chains,
property descriptors, `Proxy`/`Reflect`, and, decisively, best-effort vanilla-JS
compatibility ([TDD-00022](TDD-00022.md)). This document settles the *direction*
once, so individual features stop re-litigating the representation.

## Design

The earlier draft of this document listed three flat "options" (A/B/C). That
framing was wrong: they do not sit on one axis, and some are stages of others.
The honest structure is two axes.

### Axis 1 — static shape reach (no dynamism)

**Object type arguments in generics.** Extend [TDD-00010](TDD-00010.md)'s
monomorphization to accept an object/interface/class type argument, not just
scalars/arrays. Because generics are monomorphized, each instantiation of
`function f<T>(o: T)` has a *concrete* `T`; once that concrete shape reaches the
body, `const { a, ...rest } = o` is ordinary static-shape destructuring and
Stage 3b's `bindObjectRest` handles it unchanged — generic-`T` rest falls out for
free, no rest-specific code and **no runtime representation at all**. It does
nothing for `any`/union sources, which have no static shape at any point.

This is a static type-system extension, scoped in its own document
([TDD-00069](TDD-00069.md)). It is entirely off the dynamism axis below: it
neither advances toward the dynamic model nor is made obsolete by it, so it is
safe to build at any time without creating throwaway work.

### Axis 2 — object dynamism (where prototype semantics live)

A single trajectory with two stages, not competing options:

- **D1 — a real dynamic object model.** Per-*instance* mutable property set + a
  prototype pointer + property descriptors (enumerable/writable/configurable,
  accessor-as-data). This is the home of dynamic add/delete, `Object.keys`/
  `for...in` over dynamic objects, `defineProperty`, `getPrototypeOf`,
  `Proxy`/`Reflect`, well-known symbols — and of **prototype semantics
  themselves**. A correctness-first representation is a per-instance property bag
  (a generalized form of the old "Option C" / the Map-backed representation
  [TDD-00012](TDD-00012.md) already uses for computed-key literals). Slow but
  semantically real; hidden classes are not required for correctness.
- **D2 — hidden classes / inline caches.** A pure *performance* optimization over
  D1 (shape objects + transition trees + inline caches, the V8/SpiderMonkey
  technique). A next stage **of D1**, not a peer of anything on Axis 1.

Prototype support is not a separate item to slot in elsewhere: it *is* D1's
defining content. "Implement JS's prototype nature" = build D1.

### The rejected option — per-type shape descriptor (old "Option B")

Giving every object a hidden header word pointing at a per-*type*, immutable,
emitted-once field table is **rejected**. It is the one direction that is both
expensive and off the path to the endpoint:

- It only ever describes a shape fixed at construction time, so it cannot
  represent per-instance mutation — the moment D1 exists, a per-type descriptor
  is deleted wholesale. It is throwaway work by construction.
- It still taxes every allocation and every `IsObject` consumer (`VisibleFields`,
  `StructIR`, spread, JSON, `structuredClone`, freeze/seal, tuples) and collides
  with the hidden-field conventions classes/errors/generators/regexp already
  layer on — a second metadata mechanism threaded through a model that barely
  holds its first one.
- Its conformance payoff is modest: it buys enumeration of static shapes but
  still fails every descriptor/prototype/well-known-symbol test (the object-model
  ceiling [TDD-00061](TDD-00061.md)/[TDD-00063](TDD-00063.md) already documented).

Big permanent cost, partial result, discarded at the endpoint. Do not build it.

### Why the endpoint is native D1, not the embedded engine

A hybrid — keep the static core, delegate all dynamic objects to the opt-in
embedded engine ([TDD-00046](TDD-00046.md), quickjs) — was considered and does
**not** serve the actual endpoint. [TDD-00022](TDD-00022.md) (best-effort
vanilla-JS compatibility) needs prototype-based classes and dynamic property
addition compiled to **native code through this compiler** — delegating them to
an interpreter would ship quickjs running the program, not a native binary,
defeating the compiler's whole purpose. So vanilla-JS compat is a direct consumer
of D1 and requires it in the core. The embedded engine stays scoped to its own
job — running *arbitrary runtime-provided* source (`eval`/`vm`) — which is a
different need from compiling *known* vanilla-JS source, and the two do not
substitute for each other.

### Decision

- **Now (Axis 1):** object type arguments in generics. Delivers generic-`T`
  rest — the realistic Stage 3c demand for typed app code (`const { id, ...rest }
  = record`) — at zero runtime cost. Because it is purely static, it adds nothing
  to D1's future cost and cannot be invalidated by it. Scoped in
  [TDD-00069](TDD-00069.md); the rest payoff is a side effect.
- **Endpoint (Axis 2), deferred:** the native dynamic/prototype object model
  (D1), later optimized by hidden classes (D2). This is where prototype semantics
  and [TDD-00022](TDD-00022.md) land. Deferred now for the obvious reasons (it is
  the single largest architectural undertaking on the roadmap and an identity
  shift from "static TS subset" toward "a real object model in native code"), but
  it is the committed long-term direction, not an open question.
- **Rejected outright:** the per-type shape descriptor. It is precisely the move
  that would *increase* the eventual dynamism work (build it, thread it
  everywhere, then rip it out), which is the trade this project explicitly wants
  to avoid.
- **Until D1:** `any`/union object rest, and runtime enumeration over unknown
  shapes generally, stay clean compile-time rejections — honest, not silently
  wrong.

The guiding principle behind this ordering: the near-term move must add **zero
throwaway** toward D1. Object generics qualifies (it never touches object
representation); the per-type descriptor is the exact opposite.

## Open questions

- **D1 staging.** Does D1 land first as a correctness-only per-instance property
  bag (slow, but full semantics), with hidden classes (D2) as a strictly later
  optimization pass — or is some minimal shape-sharing unavoidable from day one to
  keep typed-code performance acceptable? (Correctness and performance are
  separable; the naive bag is the honest V1.)
- **Scope of D1 in typed code.** Is the dynamic model gated behind the vanilla-JS
  / `-globals=permissive`-style opt-in and the `any`/dynamic positions only, with
  statically-typed objects staying fixed-shape structs for speed — a two-tier
  object representation — or does everything eventually become dynamic? The former
  preserves the native-performance story for the typed core; the latter is
  simpler but taxes every object.
- **Prototype-chain resolution.** How much of a typed program's prototype/method
  dispatch can stay compile-time-resolved (as class method dispatch already is)
  versus needing a runtime `[[Prototype]]` walk — and where exactly is the line
  drawn for [TDD-00022](TDD-00022.md)'s pre-ES6 prototype-based "classes"?
