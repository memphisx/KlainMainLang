# ADR-00298: `pipeTo`/`pipeThrough`, `TransformStream<I, O>`, `tee()` — the reaction-driven pipeline

- **Relations**: Implements [TDD-00097](../tdd/TDD-00097.md) Stage 3; extends [ADR-00296](ADR-00296.md), [ADR-00297](ADR-00297.md)
- **Date**: 2026-08-22

## Context

TDD-00097 Stage 3 completes the WHATWG pipeline: `src.pipeTo(dst)` with all
four shutdown-propagation rules, the `prevent*` options, and `AbortSignal`;
`TransformStream` with backpressure coupling; `pipeThrough`; `tee()`. The
design constraint from the TDD held: the whole pipeline runs on promise
reactions alone — no fiber, so a pure in-memory pipeline still links neither
the scheduler nor libcurl.

## Investigation

Two problems shaped the design:

- **Typed records vs. a type-agnostic runtime.** read() promises fulfill with
  typed `{value, done}` records (ADR-00296's fulfill thunk). The pipe/tee
  machinery must move chunks without knowing their type, so each site emits
  the inverse thunk — `{i64,i64,i64} @__kml_rs_decode_N(ptr rec)` — stored in
  the pipe/tee context. Fulfill + decode are the only two type-aware points;
  everything between is raw words.
- **`pipeThrough` needs real concurrency.** `rs.pipeThrough(t).pipeTo(w)`
  requires the first pipe to run interleaved with the second (an inline
  await-loop lowering would deadlock against the transform's backpressure).
  The reaction-driven state machine gives that concurrency for free.

## Decision

- **Pipe state machine** (`runtime_streams_pipe.go`): an 80-byte context
  {src, dst, pipe promise, decode thunk, flags, signal-field ptrs, pending
  chunk words, current promise}. `step` → read → `on_read` → (done: close
  dst unless preventClose, settling the pipe promise on the close promise) /
  (chunk: wait `dst.ready` if pending → `on_ready` → write → `on_written` →
  step). Source error → `ws_abort(dst)` unless preventAbort; dest
  error/rejected write → `rs_cancel(src)` unless preventCancel; both reject
  the pipe promise. The AbortSignal's `aborted`/`reason` field pointers are
  resolved at the compile site (the object layout is static) and polled at
  each step boundary; an abort cancels/aborts both ends per the prevent*
  flags and rejects with the reason. Both ends are locked, as in spec.
- **TransformStream** (`%kml.ts` context): the writable side's sink write is
  `__kml_ts_sink_write` — run the transform immediately when the readable
  side has capacity (desiredSize > 0), else **park** the chunk and return a
  pending promise as the in-flight write (the writable's own serialization
  provides at-most-one parked chunk). The readable's pull
  (`__kml_ts_pull`) resumes a parked chunk; parking also re-kicks pull so a
  read that parked *before* the chunk arrived is served (the one deadlock
  found in testing). Sink close runs flush then closes the readable; sink
  abort errors it. Defaults: writable HWM 1, readable HWM 0 (transform on
  demand — spec defaults). An identity transform (no callback) requires
  matching I/O chunk representations.
- **tee()**: two branch streams sharing a context; a pull on either branch
  performs at most one source read (`reading` flag) and enqueues the decoded
  chunk into every non-canceled branch; done closes both, a source error
  errors both; the source is cancelled only when both branches have
  cancelled.
- `pipeThrough(t, opts)` = lock src + t.writable, start the pipe (its
  promise deliberately unobserved), return `t.readable`.

## Implementation notes

- New `runtime_streams_pipe.go` + `emit_streams_pipe.go`; wiring in the
  usual dispatch points. `TransformStream<I, O>` parses like `Map<K, V>`
  (two type args); a single type arg means I = O.
- The transform/flush callbacks reuse Stage 2's write wrapper and Stage 1's
  pull wrapper shapes verbatim — their env is `{userClosure, readable}`, so
  the controller the callback receives is the readable side's controller.
- Shared runtime helpers `__kml_prom_reject` / `__kml_mkclo` were factored
  out; struct IR names substituted via a string replacer (see ADR-00297).

## Side effects discovered

- A signal abort takes effect at the next chunk boundary (step entry), not
  instantaneously mid-write — caveat.
- `tee()` branch cancel reasons are not composed into an array as in spec;
  the last cancelling branch's reason is forwarded — caveat.
- Cancelling a TransformStream's readable side does not error the writable
  side — caveat.

## Verification

`tests/streams_test.go` Stage 3 block: HWM-1 pipe proving chunk-at-a-time
flow with an async sink, pipeThrough with an uppercase transform consumed by
`for await`, a type-changing transform (`string → number`) with flush,
tee() with independent branch consumption, a chained
`pipeThrough().pipeTo()`, all four propagation rules + `preventAbort`, and a
timer-driven `AbortController` aborting a pipe. Full `go test ./...` green
(Mac); `go vet` clean.
