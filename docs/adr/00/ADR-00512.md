# ADR-00512: TypedArray construction as a general expression

- **Relations**: `Implements TDD-00018`, `Extends ADR-00104`
- **Date**: 2026-08-30

## Context

TypedArray construction (`new Uint8Array(...)`, etc.) was restricted to a
variable declaration's initializer — `new Uint8Array([1,2,3])` as a function
argument, a return value, an object field, or a method-chain head was a clean
compile error (`emit_exprs.go`: "a TypedArray constructor must be used in a
variable declaration"). TDD-00028/ADR-00104 lifted the identical restriction on
plain array literals and `new Array/Map/Set/EventEmitter`, but TypedArrays were
out of that scope. This is the enabler half of the "binary" leverage cluster:
building a typed buffer inline to hand to a sink (`ws.send`, a request body, a
stream write) rather than always naming an intermediate `const`.

## Investigation

A TypedArray's Type **already is** an array: `TypedArrayType` (`types.go:1455`)
calls `ArrayOf(elemTy)` and sets `IsTypedArray`, so `IsArray`/`ElemType` are set
exactly like a `number[]`. The whole array method/indexing/for-of surface, and
crucially the `{ptr, i64}` aggregate **value form** (the second of the two array
shapes — see the codegen conventions), therefore already apply to a TypedArray.
The only thing missing was a *construction site* that produces that aggregate:
the four existing forms (`emitTypedArrayFromArrayLiteral`/`FromSize`/
`FromArrayLike`/`FromBuffer`, `emit_arraybuffer.go`) all write into two caller-
provided allocas (the "named Symbol" form the var-decl supplies), so they can't
yield a value.

So this needed no new representation — just an aggregate-producing wrapper, the
same shape as `emitNewArraySizedAggregate`/`emitArrayLiteralAggregate` for plain
arrays.

## Decision

1. `emit_exprs.go`: `NewTypedArrayExpression` in general-expression position now
   calls a new `emitNewTypedArrayAggregate` instead of erroring.
2. `emit_arraybuffer.go`: `emitNewTypedArrayAggregate` allocates two temporary
   entry-block allocas, calls the existing `emitNewTypedArrayVarDecl` into them
   (reusing all four construction forms verbatim), loads them, and assembles the
   `{ptr, i64}` aggregate `Value` — the exact form every array consumer already
   accepts. The var-decl path is unchanged (still calls `emitNewTypedArrayVarDecl`
   directly), so no regression there.
3. `emit_exprs_types.go`: `inferExprType` now returns `TypedArrayType(ElemKind)`
   for a `NewTypedArrayExpression` (previously it fell through to the default),
   so the value has the right compile-time type at argument/return/field sites.

## Implementation notes

- The temporary allocas are the minimal-risk route: the four construction forms
  stay byte-for-byte as they were, and only their storage target changes from
  the var-decl's allocas to throwaway ones whose values are immediately hoisted
  into the aggregate.
- Not addressed here: a TypedArray as a **ternary** arm — that's a pre-existing
  limitation of the array value form itself (`ternary operator is not supported
  for array types`), applying equally to plain arrays, and out of scope.

## Side effects discovered

The `.buffer` property remains unimplemented — a separate, genuinely
representation-changing feature (each TypedArray would need a back-reference to a
real `ArrayBuffer`), tracked as its own caveat on the status page. This ADR does
not touch it.

## Verification

- New E2E `TestE2ETypedArrayGeneralExpression` (`tests/typedarrays_test.go`):
  inline argument, function return, object field, and inline `.map().join()`
  chain. Passes.
- Existing TypedArray/ArrayBuffer/DataView suites pass (no regression).
- `examples/typedarrays/typedarrays.ts` extended; output byte-identical to
  `node examples/typedarrays/typedarrays.ts`.
- Machine: Apple Silicon M4 (macOS).
