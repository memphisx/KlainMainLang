# TDD-00233: Structural object types read any layout that satisfies them

- **Status**: Implemented
- **Notes**: Stages 1–2 [ADR-01210](../adr/ADR-01210.md), Stage 3 [ADR-01215](../adr/ADR-01215.md); a value of another kind written into a field shadows it (ADR-01215)
- **Date**: 2026-09-28

## Context

TypeScript's object types are structural: a value of an interface or type
literal type is any object that has the members, in any layout. This
compiler lays each object type out statically and reads a member at a
fixed offset. Three failures follow:

- A class instance passed where an interface is expected keeps its class
  layout and is read at the interface's offsets:
  `interface Named { name: string; age: number }` with
  `class P { age = 41; extra = "e"; name = "kyr" }` and
  `show(new P())` segfaults.
- An interface's method signatures (`area(): number`) are not members of
  its object type (`interfaceMethodSigs` serves `implements` checks
  only), so `s.area()` on an interface-typed value is "an object has no
  method" — whether the value is a class instance or an object literal.
  The status page records this as a note on the `implements` row
  ("not a mechanism for polymorphic dispatch through an interface-typed
  reference").
- Two plain object types whose layouts differ are bridged by copying
  (`emitObjectRelayout`): writes through the copy do not reach the
  original, and `===` against it is false (BACKLOG 74).

[TDD-00230](TDD-00230.md) keeps assignability structural "even though
representations are nominal" but does not say how a value of one layout
lives in a slot typed by another. Interface-typed parameters that receive
class instances (repositories, handlers, injected services) are the
ordinary shape of the programs this project targets.

## Design

### Options

1. **Copy at the boundary** (extend today's relayout to classes, binding
   methods as closures). Small, but identity and mutation stay broken —
   the third failure above, spread to every class.
2. **A checked view.** A structural-typed value is the original object's
   pointer. Every member access checks the object's header word: the
   type's own layout id reads the member at its static offset; any other
   header reads it through the layout table (`emit_shape.go`,
   `__kml_shape_get`/`__kml_shape_set`, method records called with the
   object as `this`). Identity and mutation are the object's own.
3. **Interface tables** (Go's fat pointer: object plus a per-(class,
   interface) table of offsets and methods). Fast and faithful, but every
   interface-typed slot becomes two words: arrays, fields, boxing and the
   C runtime all change.

Option 2 is the recommendation: it is faithful, reuses the layout table
that dynamic property access already uses, and costs one compare on the
fast path (an object literal built as the type, or an object of the same
layout). The slow path's name lookup is what per-site caches
([TDD-00220](TDD-00220.md)) speed up later; option 3 stays available as a
representation change inside TDD-00230 P3.3 if measurements ask for it.

### Stage 1: method signatures are members

An interface's or type literal's method signature `m(p): R` (and `m?(p)`)
becomes a function-typed member of its object type, as TypeScript types
it. An object literal typed by the interface carries its methods as those
members. `implements` checking keeps reading the signatures.

### Stage 2: the checked view

- **Boundary.** Coercing a class instance, or a plain object of another
  layout, to a plain object type keeps the pointer (no relayout) and marks
  the source layout's row as needed (`noteBoxedLayout`).
- **Access helpers.** `emitRecordGet(obj, T, name)`,
  `emitRecordSet(obj, T, name, v)` and `emitRecordCall(obj, T, name,
  args)`: load the header; equal to `T`'s layout id → the static GEP;
  else box the object and take the dynamic path
  (`emitDynAnyMemberGetNamed`/`SetNamed`, `emitDynAnyMethodCall`),
  converting the boxed result to the member's declared type. A null object
  keeps today's null handling.
- **Sites.** Member read and write, compound assignment and `++`/`--`,
  method calls through a function-typed member, optional chaining,
  destructuring, `in`, spread, `Object.keys`/`values`/`entries`,
  `JSON.stringify` and console.log. The last five walk the layout table's
  key list for a foreign layout.
- **Deleted**: `emitObjectRelayout`, `needsObjectRelayout*` and the copy
  sites (BACKLOG 74).

### Stage 3: arrays and fields of structural type

An element or field typed by a plain object type holds the pointer as
stored; reads go through the same helpers. Union members that are plain
object types (`needsObjectRelayoutBoxing`) keep the pointer too.

## Open questions

- Whether a class's getter/setter behind an interface member reads through
  the layout table's accessor records unchanged (they are there for
  `anyObj.x`); to be confirmed in Stage 2.
- Whether any C runtime path (dynjson.c, inspect) reads a plain object's
  fields by offset from a pointer it was handed as that type; those paths
  then take the key list too.
