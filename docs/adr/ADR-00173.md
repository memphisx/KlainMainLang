# ADR-00173: `for...of` over a generator

- **Relations**: Implements the remainder of [TDD-00061](../tdd/TDD-00061.md)'s V1 scope; extends [ADR-00172](ADR-00172.md)
- **Date**: 2026-08-12

## Context

[ADR-00172](ADR-00172.md) shipped real generator construction/`yield`/`.next()` but explicitly deferred `for...of` iteration, driving a generator manually via `.next()`/`.value`/`.done` instead — the natural, idiomatic way to consume a generator. This ADR closes that gap.

## Decision

A fourth, independent `emitForOf` case (`emit_stmts.go`), alongside the existing array/Map/Set path and Stage 1a's class-`next(): T | null` sentinel case ([ADR-00063](ADR-00063.md)) — a generator's own `{value, done}` result doesn't fit the sentinel model (a legitimately falsy/zero yielded value must not be misread as "done," the same reason `.next()`'s own result shape exists at all).

`s.Iterable` is evaluated exactly once (constructing exactly one generator instance — it may itself be a `gen(...)` call, which must not run again per iteration), then driven by a new `emitForOfGenerator`, calling `.next()` repeatedly against that same instance until `done`. Required splitting `emitGeneratorNext` into a thin receiver-evaluating wrapper plus `emitGeneratorNextByValue` (an already-evaluated instance pointer) — `for...of` needed the latter directly; the plain `gen.next()` call site still uses the wrapper unchanged.

`emitForOfGenerator` mirrors `emitForOfClassIterator`'s own defensive alloca-then-reload shape for the per-iteration result, rather than referencing the `.next()` call's returned SSA value directly across the `cond`/`body` label boundary — matching established precedent rather than relying on a domination argument through `emitGeneratorNextByValue`'s own several internal sub-labels (the suspend/resume swap itself).

## Implementation notes

- Files touched: `codegen/llvm/emit_stmts.go` (`emitForOf`'s new dispatch + updated fallback error messages, now mentioning "generator" as a valid iterable), `codegen/llvm/emit_generators.go` (`emitGeneratorNextByValue` split out, `emitForOfGenerator` new).
- `break`/`continue`/labeled break inside a generator `for...of` loop reuse the exact same `cond`/`body`/`inc`/`end` label plumbing and break/continue-stack bookkeeping every other `for...of` case already shares — no generator-specific handling needed there.
- `break`ing out of a generator `for...of` loop early leaves the generator's own fiber/stack simply abandoned, never resumed again — matching this project's established "leak everything, never free" convention (no `.return()` to run any pending `finally` cleanup inside the generator, since `.throw()`/`.return()` remain out of V1 scope per TDD-00061).

## Side effects discovered

`make conformance` moved by exactly zero files again (confirmed via a full before/after pass-list diff) — the same "real feature, zero corpus overlap" finding [ADR-00172](ADR-00172.md) already documented, investigated further here rather than just re-reported: sampled a still-failing `language/statements/generators/` test directly and found it asserts on `g.prototype`/`Object.getPrototypeOf(it)` — Test262's own generator tests probe real JS's dynamic object model (a generator's own `%GeneratorPrototype%`, `Symbol.iterator`, the `GeneratorFunction` constructor) at a level this compiler's static, non-dynamic generator representation was never designed to have any equivalent for at all, not just a missing-feature gap `for...of` support could close. This is a materially different, deeper mismatch than the "still missing `yield*`/methods" explanation ADR-00172 gave — worth noting precisely rather than assuming the same shallow cause twice.

## Verification

- Linux x86-64, both `manual` and `-mm=gc` memory modes. `go build`, `go vet ./...`, `go test ./...` all pass.
- New E2E tests in `tests/generators_test.go`: a basic inline `for (const x of gen())`, confirmation the iterable is constructed exactly once (not once per iteration), `break`, `continue`, iterating an already-constructed generator variable, and a string element type.
- Independently verified by temporarily disabling the new dispatch and confirming all six new tests fail with the exact predicted "for...of requires an array, Map, Set, generator, or class-with-next() value" error, then restoring and confirming they pass again.
- `examples/generators/generators.ts` extended with a `for...of` section (including a Fibonacci generator and a `break`/`continue` case). `make examples` — 112/112.
- `make conformance` — 4503/53578 (8.4%), unchanged from ADR-00172's own number; see Side effects for why.
