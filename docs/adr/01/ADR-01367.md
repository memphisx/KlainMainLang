# ADR-01367: A generic class's `new` infers its type arguments

- **Relations**: Extends TDD-00010
- **Date**: 2026-10-03

## Context

`new Box(5)` against `class Box<T> { constructor(v: T) }` failed codegen:
"requires exactly 1 explicit type argument … inference isn't supported for
class construction". tsc and the checker infer `Box<number>`. Found while
porting WeakRef to TypeScript (ADR-01366).

## Investigation

- Codegen monomorphizes a generic class per type-argument list. Each `new`
  site resolved the list from explicit arguments only (`classTypeArgs`), at
  six sites: emission, type inference, and the variable-declaration and call
  pre-passes.
- The checker's own answer for the `new` was not reachable from those
  sites, since codegen does not always hold the node the binder bound.
  Inferring from the constructor's parameters needs only the checker's type
  for each argument.

## Decision

`newTypeArgs` is the one resolver:
- explicit arguments (with defaults) first;
- else each type parameter a constructor parameter is annotated with
  outright takes its argument's type as the checker gives it, named back
  through `checkerTypeAnnotation` (a class or interface by name, a
  primitive, an array, `any` for the rest).

All six sites use it. A type parameter that no parameter gives directly is
still an error.

## Implementation notes

`codegen/llvm/emit_classes.go`, `emit_call.go`, `emit_exprs_types.go` and
`emit_exprs_vardecl.go`; `TestE2EGenericClassRequiresExplicitTypeArgument`
becomes `TestE2EGenericClassTypeArgumentInferred`.

## Verification

Mac (Apple Silicon), against Node 24: `new Box(5)` and `new Box(new Item())`
with their fields and inspect output; the generics group.
