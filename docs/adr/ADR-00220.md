# ADR-00220: `&&` / `||` value-preserving under `-compat=js`

- **Date**: 2026-08-18
- **Relations**: Implements [TDD-00075](../tdd/TDD-00075.md) (a further inhabitant); extends [ADR-00186](ADR-00186.md) (the bool form) and [ADR-00217](ADR-00217.md) (the `-compat` axis)

## Context

[ADR-00186](ADR-00186.md) made `&&`/`||` short-circuit but yield a **bool**, not JS's value-preserving operand (`a && b` → `b` or the falsy `a`; `a || b` → `a` or `b`). That divergence is a natural `-compat` inhabitant ([TDD-00075](../tdd/TDD-00075.md)): a stricter, simpler default with JS fidelity on demand. This ADR adds the value-preserving form under `-compat=js`, leaving `strict` (the default) exactly as ADR-00186 shipped.

## Investigation

- `emitShortCircuit` (`emit_exprs_operators.go`) allocates an `i1`, stores `toBool(left)`, branches (evaluating the right only when needed), stores `toBool(right)`, and returns the `i1`.
- `inferExprType` for `&&`/`||` already returns the **left operand's type** — which, for same-typed operands, is exactly the value-preserving result type. So no type-inference change is needed: `const x = 5 && 3` already infers `x` as `number`; only the emitted value was wrong (a coerced bool `1`, not `3`).
- The general value-preserving result of differently-typed operands (`0 || "hi"`) is a union this compiler can't represent, so the fidelity has to be scoped to same-typed operands.

## Decision

Under `-compat=js`, when both operands share a **simple, single-slot type** (`sameShortCircuitType`: same IR and kind, excluding aggregates — arrays/tuples/nullable-scalar/dynamic), `emitShortCircuit` produces the **actual operand value** via `emitShortCircuitValue`: an alloca of that type, store the left value, branch on `toBool(left)` (for `&&`: evaluate the right when the left is truthy; for `||`: when falsy), store the right value on that path, load the result. The right operand is still evaluated only on the non-short-circuit path (short-circuiting preserved).

**Scope:** differently-typed operands fall through to the bool form (a documented `-compat=js` limitation — the union result is out of reach), and `strict` is untouched (still bool). No `inferExprType` change (it already returns the left type, which matches the value-preserving result for same-typed operands).

## Implementation notes

- `emit_exprs_operators.go`: `emitShortCircuit` gains a `compatJS() && sameShortCircuitType(...)` fast path to `emitShortCircuitValue`; both helpers added. The existing bool body is unchanged, so `strict` codegen is byte-for-byte the same.

## Side effects discovered

- A pre-existing, now-clearer inconsistency: even in `strict`, `inferExprType` returns the left operand's type for `&&`/`||` while `emitShortCircuit` returns a bool, so `const x = 5 && 3` allocates a `number` slot and stores the coerced bool `1`. Left as-is (it's the `strict` contract from ADR-00186, and the value-preserving `js` path is now the consistent one); noted so it isn't mistaken for new breakage.

## Verification

- `tests/logical_values_test.go` — value-preserving under `-compat=js` (`5 && 3`→`3`, `0 || 7`→`7`, `"" || "fallback"`, `timeout || 30`, `true && false`→`false`) and the unchanged `strict` bool form.
- `go vet ./...` clean; `Expr|Stmt|Operator|Control|Logical|Cond|Bool` suites green (strict path untouched); full `go test ./...` at the delivery's end.
- Platform-independent (no native code).
