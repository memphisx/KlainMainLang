# ADR-00137: `process.stdout.write(s)` / `process.stderr.write(s)`

- **Date**: 2026-08-09

## Context

`docs/status/PROCESS-CLI.md` tracked a real, small gap: `console.log`/`console.error` (`emit_call_console.go`) always append a trailing newline, and this compiler had no way to write a string to stdout/stderr without one — blocking a progress indicator (`process.stdout.write("."); process.stdout.write(".")`) or assembling one line from several pieces. This project's own project-direction guidance weights "Terminal / process interaction" as one of the three areas that get a tiebreaker when picking the next small feature, and this row was called out by name there (`docs/status/PROCESS-CLI.md`'s Caveats). Picked up as a self-contained, well-scoped item rather than as part of a larger piece of work.

## Investigation

- Read `codegen/llvm/emit_call_console.go`'s `emitConsolePrint`/`emitConsolePrintVal` to find the existing fd=1/fd=2 output convention: fd 1 (stdout) goes through libc's buffered `printf`, fd 2 (stderr) through unbuffered `dprintf(2, ...)`. A doc comment on `emitConsoleGroupIndent` (same file) explains why fd 1 specifically must stay on `printf` and never `dprintf`: mixing a raw fd write with stdio's own buffered `printf` on the same descriptor risks interleaving output out of order. That constraint applies equally here, so `process.stdout.write` reuses `printf`/`ensurePrintf` and `process.stderr.write` reuses `dprintf`/`ensureDprintf` — the exact same underlying calls `console.log`/`console.error` already use, just with a `"%s"` format and no trailing `\n` appended.
- Checked how the call-dispatch router (`codegen/llvm/emit_call.go`'s `emitCall`) recognizes existing `process.*` calls: a single-level shape check (`mem.Object.(*ast.Identifier)` named `"process"`, `switch mem.Property`). `process.stdout.write(...)` is a two-level member chain (`Call(Member(Member(Identifier "process", "stdout"), "write"), args)`) — `process.stdout` itself is never a real bindable value (no `Type`/`inferExprType` case needed for it, matching how `ClassName.staticMethod(...)` and `super.method(...)` are also special-cased ahead of the generic dispatch chain rather than evaluated as ordinary expressions first). Added a second, separate shape check for this rather than trying to force it into the single-level switch.
- Considered validating that the argument is statically a string (this compiler has no runtime `toString()` coercion to fall back on). Checked how existing single-string-argument built-ins in the same file (`process.chdir(path)`, `process.execFileSync(file, ...)`) handle this: none add an explicit type check beyond `e.coerce(val, TypePtr)`, which is a no-op passthrough when the argument's IR type is already `ptr` and otherwise leaves it unchanged (falls through `coerce`'s `default: return v` case) rather than erroring cleanly — a wrong-typed argument becomes an LLVM IR type mismatch caught by `clang`, not a compiler error message. Matched this existing (imperfect but consistent) precedent rather than introducing new validation depth only for this one function; a real fix would be a general built-in-argument-type-checking pass, out of scope here.

## Decision

Added `process.stdout.write(s)` and `process.stderr.write(s)`, each taking exactly one string argument and writing it verbatim — no auto-appended newline, unlike `console.log`/`.error`. `process.stdout.write` emits `call i32 (ptr, ...) @printf(ptr @"%s", ptr <s>)`; `process.stderr.write` emits `call i32 (i32, ptr, ...) @dprintf(i32 2, ptr @"%s", ptr <s>)` — reusing `ensurePrintf`/`ensureDprintf` from `runtime_core.go`, already declared for `console.log`/`.error`'s own use, so this adds no new C-runtime surface.

## Implementation notes

- `codegen/llvm/emit_process.go`: new `emitProcessStreamWrite(args []ast.Expression, streamName string, fd int, pos ast.Pos) (Value, error)` — shared by both, parameterized on the stream's name (for the error message) and fd (1 or 2, selecting `printf` vs `dprintf`).
- `codegen/llvm/emit_call.go`: new shape check in `emitCall`, right after the existing single-level `process.*` switch — matches `Call(Member(Member(Identifier "process", "stdout"|"stderr"), "write"), args)` and dispatches to `emitProcessStreamWrite` with the matching fd.
- Text-only, same scope narrowing `console.log`'s own string formatting already has — not binary-safe past an embedded null byte (`printf`/`dprintf`'s `%s` both stop at the first `\0`); a binary-safe variant would need the explicit-length `fwrite`-based path `emit_fs.go`'s `ArrayBuffer`/`TypedArray` `writeFileSync` overload already uses (ADR-00094), not attempted here since the status-page gap this closes was specifically about the missing-newline behavior, not binary safety.

## Side effects discovered

None — no other bugs or surprises hit while implementing this; it's a small, additive, self-contained pair of functions reusing existing runtime declarations.

## Verification

- `go build -o klainmain .`, `go vet ./...`, `go test ./...` all pass.
- Manual repro: a `process.stdout.write("a"); process.stdout.write("b"); console.log("")` / `process.stderr.write("err1"); process.stderr.write("err2")` program compiled and run directly, confirming `ab\n` on stdout (the two writes concatenated with no gap, `console.log`'s own newline appended after) and `err1err2` on stderr (no newlines at all).
- New tests in `tests/process_test.go`: `TestE2EProcessStdoutWriteNoAutoNewline`, `TestE2EProcessStderrWriteNoAutoNewline`, `TestE2EProcessStdoutWriteDoesNotGoToStderr`, `TestE2EProcessStdoutWriteInterleavesWithConsoleLog` (confirms the `printf`-not-`dprintf` fd=1 choice keeps output ordered against `console.log` calls), `TestE2EProcessStdoutWriteWrongArgCountRejected`, `TestE2EProcessStderrWriteWrongArgCountRejected`. Added a `compileAndRunCaptureStderr` test helper (`tests/compiler_test.go`) to capture stdout/stderr separately and untrimmed, since the existing `compileAndRun`/`assertOutput` helpers trim trailing newlines — exactly the detail this feature's own tests need to assert on precisely.
- `examples/process/process.ts`: extended with a `process.stdout.write`/`process.stderr.write` section; compiled and run directly (`./klainmain -o /tmp/... examples/process/process.ts`), output confirmed correct.
- Flagging which machine this was verified on, per this project's own practice for platform-sensitive claims: implemented and verified only on the x86-64 Linux box this session ran on. Nothing here touches platform-specific code (`gcsrc/`, `runtime_os.go`, etc.) — both `printf`/`dprintf` are standard POSIX libc, present identically on macOS — so no reason to expect Mac-specific divergence, but it hasn't been directly re-run there.
