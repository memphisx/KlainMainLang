# TDD-00080: JS-faithful float-to-string (shortest round-trip)

- **Status**: Implemented
- **Date**: 2026-08-19

## Context

Floats print through bare `%g` (C's 6-significant-digit default), so
`console.log(1.1 + 2.2)` prints `3.3` instead of JS's `3.3000000000000003`, and
any value with more than 6 significant digits, or one that trips `%g` into
scientific notation, prints wrong ([ADR-00166](../adr/ADR-00166.md)). This is the
**only remaining single-caveat row** in the Type System page's primitives table
(JSDoc extended floats), so fixing it both closes a real correctness bug and
earns a Strict row. It affects every float print path: `console.log`, template
literals, `String(x)`, and the dynamic (`any`-boxed) float print.

## The problem precisely

JS `Number`→string (ECMAScript `Number::toString`, spec 6.1.6.1.20) emits the
**shortest** decimal string that round-trips to the same IEEE-754 double, laid out
with fixed thresholds: fixed notation when the decimal exponent `n` is
`-6 < n ≤ 21`, exponential otherwise. `%g` matches neither: its precision defaults
to 6 (truncating), and its fixed-vs-exponential switch is coupled to the requested
precision rather than to JS's `21`/`-6` thresholds. Two failure modes follow:
`1.1 + 2.2` loses digits, and a naive "raise the precision" fix over-prints
(`0.1` → `0.10000000000000001` at `%.17g`) and/or throws integers into exponential
(`%.1g` of `100` is `1e+02`).

## Design

### Option A — shortest round-trip + ECMAScript reassembly (recommended)

A C helper `__kml_dtoa(char *buf, double v)`:

1. **Special cases**: `NaN` → `"NaN"`; ±∞ → `"Infinity"`/`"-Infinity"`; `0`/`-0`
   → `"0"` (matching `String(-0)`; see Open questions on the console `-0`
   divergence). Emit the sign for negatives, then work on `|v|`.
2. **Shortest significant digits**: loop `d = 1..17`, format `snprintf("%.*e", d-1, v)`
   (scientific, `d` significant digits) and `strtod` it back; the first `d` whose
   value equals `v` exactly is the shortest round-tripping digit count. `%e` (not
   `%g`) is used because it exposes the digit string and decimal exponent
   uniformly, independent of magnitude.
3. **Reassemble per ECMAScript rules** from the `d` digits `s` and the decimal
   point position `n` (the leading digit's power of ten, read from the `%e`
   exponent):
   - `k ≤ n ≤ 21` (k = digit count): digits then `n−k` trailing zeros.
   - `0 < n ≤ 21`: digits with a decimal point after position `n`.
   - `-6 < n ≤ 0`: `"0."`, then `−n` zeros, then digits.
   - otherwise: exponential — first digit, `"."`, remaining digits, `"e"`, sign,
     and the (unpadded, JS-style) exponent.

This yields exactly JS's output for the common range and the correct shortest
digits everywhere; the `strtod` round-trip check guarantees no precision loss.

### Option B — port a canonical shortest-float algorithm (Ryu/Grisu)

Exact and fast, but a large amount of vendored code for a formatter — overkill for
this project's needs. Rejected as the V1.

### Option C — always `%.17g`

Fixes precision but is not shortest (`0.1` → `0.10000000000000001`) and keeps
`%g`'s wrong thresholds. Rejected (still wrong).

**Recommended: Option A.** The `%.*e` retry gives shortest digits with a trivial,
provably-correct termination (round-trip equality), and the ECMAScript reassembly
is a small, well-specified state machine.

### Integration

Embedded C file `dtoasrc/dtoa.c` (`//go:embed`), compiled and linked **only when a
program prints a float**, mirroring the bigint/JSON embedded-C pattern
(`UsesFloatFmt` flag + `ensureDtoa()` decl + a `main.go` compile step + a test-
harness `appendDtoa`). The three current `%g` sites — the scalar float print
(emit_exprs_types.go), the dynamic/`any` float print (emit_dynamic.go), and the
`printfFmtFor`-style helper (types.go) — call `__kml_dtoa(buf, v)` into the
existing 32-byte scratch buffer instead of `sprintf(buf, "%g", v)`.

## Open questions

- **`-0`**: `String(-0)` is `"0"` but Node's `console.log(-0)` shows `-0`. V1 emits
  `"0"` for both (the `String` behavior); note the console divergence, or special-
  case the console path later.
- **float32**: this compiler widens `float` to `double` before printing, so the
  shortest is computed against the double value. A value that originated as a
  32-bit float may therefore print more digits than a JS `Float32`-aware toString
  would — acceptable for V1, worth a note.
- **Link granularity**: conditional-link (only when a float is printed) vs always-
  link. Conditional matches the existing embedded-C helpers and keeps float-free
  programs plain-libc; recommended.
- **Exponent formatting details**: confirm against Node — sign always present
  (`e+21`, `e-7`), no zero-padding, and the fixed/exp boundary values.
