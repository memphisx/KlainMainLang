# ADR-01484: A dictionary type is the object itself

- **Relations**: Implements TDD-00230; Supersedes the representation in ADR-00485 and ADR-01225's conversions
- **Date**: 2026-10-09

## Context

A dictionary type (`{ [k: string]: T }`, `Record<string, T>`, an
interface with an index signature or one extending `NodeJS.Dict<T>`) was
a string-keyed map at run time. Converting a static object or an `any`
bag to it made a map copy (ADR-01225), and boxing it back into `any`
made a bag copy. In JavaScript there is one object, so writes made
through the dictionary never reached the source:

```ts
const o = { a: 1 };
const d: Record<string, number> = o;
d.a = 10;            // Node: o.a is 10; here o.a stayed 1
```

## Investigation

- An `any` holding a static object already aliases it: writes through
  the `any` (including keys the object did not have) show on the object,
  identity holds, and a typed binding converted back from the `any` is
  the same object.
- An `any` with a declared property type already existed as the
  "index-signature view" (`DynPropTy`, TDD-00229, used for node:ffi's
  `lib.symbols`): member and bracket reads produce the declared type.
- With every dictionary-type constructor (index signature, open-key
  `Record`, a generic interface's index signature) returning that view,
  the dictionary probe matched Node, aliasing included. The broad
  dictionary-adjacent test set (dictionaries, records, expandos,
  `Object.keys`/`entries`/`fromEntries`, JSON, URL, querystring, headers,
  env, dynamic objects) passed apart from four cases:
  - `r["x"].push(v)` (the mutator's receiver resolution only knew the
    map form);
  - a missing string read printed `null`;
  - `interface I extends NodeJS.Dict<T> {}` (the heritage test only knew
    the map form, twice).
- An array literal stored into an `any` member became a dynamic array.
  Unboxing it to `string[]` copied it, so `(a.l as string[]).push("2")`
  was lost. The same happened through a dictionary of arrays.

## Decision

- A dictionary type is `any` with a declared property type
  (`dictViewType`): the object itself, in whatever representation its
  value has. Conversions between a static object, an `any` bag and a
  dictionary are the same object, as in JavaScript.
- A read through the view has the declared type. A missing key is
  undefined: a string, object or array read is marked possibly
  undefined. An array read keeps its live header (`dynPropRead`), so a
  mutator through it changes the stored array.
- A value stored through the view is built with the declared type as
  its contextual type (`dynStoreHint`). A plain `any` member's array
  literal stays an array of any: typing it from its elements broke a
  later push of another kind through the `any` (test-par caught it,
  `[ 1, NaN ]` for `o.list.push("x")`).
- A missing key read as an object or class is the absent pointer, and the
  inferred type of a view read carries that absence (`dynPropReadType`),
  so `cluster.workers[9] === undefined` holds (test-par caught it).
- `(x as T[]).push(v)` with x held as `any` is x's own mutation, the
  dynamic call: the assertion is erased, as in JavaScript, rather than
  mutating a converted copy (`arrayMutators`, emit_call.go).
- `isDictType`/`dictValType` recognize either form. The map form remains
  for the fresh values whose construction builds a map (a computed-key
  literal, `Object.fromEntries`, `Object.groupBy`, regexp groups). Such a
  value is new when converted, so the conversion's copy is not
  observable.
- The shadow oracle maps a string index signature to the view.
- `checkerDictType` (a function's own property the checker types as a
  dictionary) recognizes the view form too; it knew only the map form,
  so such a read was plain `any` (the shadow report's second bucket).
