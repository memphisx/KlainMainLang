# TDD-00016: `Promise.all` / `.race` / `.allSettled`

- **Status**: Implemented
- **Date**: 2026-07-29

## Context

The last named gap in [TDD-00006](TDD-00006.md) (Event Loop): both of that document's two real slices — the `select()`-based wait loop (Part 1) and the fiber-based suspension mechanism, used for concurrent `http.listen` connections and non-blocking `await fetch(...)` (Part 2) — are done and shipped, but everything built on top of them so far only concurrently awaits *one thing per call site*. A microservice handler that needs to fan out to several upstream APIs at once and combine their results — a completely ordinary REST-API-client shape, and squarely inside this project's stated microservice/REST-API-interaction priority (`CLAUDE.md`'s project-direction section) — has no way to express that: it would have to `await` each `fetch()` one at a time, serializing calls that have no real dependency on each other. Scoped as its own document (rather than folded directly into an ADR) because it needed a real design decision — build a second, parallel wait mechanism, or generalize the one Part 2 already built — not just a mechanical extension.

## Design

**The scope is narrower than "await N promises" sounds**, because of a fact specific to this compiler's async model (see `emit_async.go`'s own header comment): an ordinary `async function`'s body runs to completion *synchronously* at call time — there are no real suspend points, no CPS transform, nothing. `Promise<T>` for an ordinary async function is a malloc'd slot holding an already-computed value by the time the caller ever sees it. The **only** kind of `Promise<T>` in this entire language that is genuinely still pending at some later point in the program is `fetch()`'s own `Promise<Response>` — the one value [ADR-00050](../adr/ADR-00050.md) gave real non-blocking machinery to. That means:

- `Array<Promise<Response>>` is the only case with actual concurrency to have. `Promise.all`/`.race`/`.allSettled` here must genuinely wait on N in-flight libcurl transfers together.
- `Array<Promise<T>>` for any other `T` has nothing to parallelize — every element is already resolved by construction. The honest behavior is a plain, order-preserving, synchronous collection/pick/report over already-settled values, not a simulation of concurrency that doesn't exist. Building fake suspend points for this case would be pure ceremony with no payoff.

Both cases are covered by the same three builtins, branching once (at codegen time, since `T` in `Array<Promise<T>>` is always statically known) on whether `T` is `Response`.

**Response branch — reuse Part 2's mechanism, don't build a second one.** [ADR-00049](../adr/ADR-00049.md)/[ADR-00050](../adr/ADR-00050.md) already solved "park a fiber until some asynchronous condition becomes true": a connection-array entry carries a `pendingFetch` field; `__kml_await_fetch` parks (yields via `swapcontext`) when running inside a fiber, or busy-spins `curl_multi_perform`+drain directly when running at top level (no event loop to yield into — nothing else could run concurrently in that case anyway). The natural generalization: add a second condition field, `pendingGroup`, and a `__kml_await_group_wait` that is a structural clone of `__kml_await_fetch`'s own wait loop, except it polls "is this *group* of pending fetches satisfied" instead of "is this *one* pending fetch done." A "group" is a malloc'd `{ ptr membersArr, i64 count, i64 mode }`: `membersArr` points at the same 40-byte pending-fetch structs `__kml_fetch_async` already produces (no copying/wrapping — a group just points at the ones the calling code already has), and `mode` (0 = wait for all, 1 = wait for first) lets `.all`/`.allSettled` and `.race` share one primitive instead of needing two. The event loop's own resume-scan (`__kml_event_loop_run`) gets a third branch, `rcheckgroup`, alongside its existing fd-ready and pendingFetch checks, mirroring the existing `pendingFetch != null` handling exactly.

An alternative considered and rejected: loop over the array calling the existing single-fetch `__kml_await_fetch` one element at a time. Simplest to implement, but not real concurrency — it would silently serialize exactly the fan-out pattern this feature exists to unlock, defeating [ADR-00050](../adr/ADR-00050.md)'s own multi-interface work in the one place it matters most (N *concurrent* upstream calls from a single handler). Rejected on those grounds without prototyping.

**Non-Response branch — reuse the existing resolved-value convention.** For any other `T`, each builtin does its own synchronous loop (collect in order for `.all`, first element for `.race`, always-"fulfilled" for `.allSettled`) directly over the array's already-resolved Promise slots — the same free-after-read convention a plain `await` already uses on a single slot.

**Result shape — reuse the existing return convention.** Both branches, once they've computed their result value (a `Response`, an `Array<T>`, or an `Array<Settlement<T>>`), wrap it back into a Promise using the exact same malloc-and-store convention an ordinary async function's `return` already uses (`emitAsyncPrologue`/`emitReturn`) — so `await Promise.all(...)` reads its result back through `emitAwait`, not new await-side code. This mostly worked as designed, with one real exception found only once actually tested end-to-end (not caught by design review): `emitAwait`'s existing `promiseTy.IsResponse` branch unconditionally assumed *every* `Promise<Response>` it's ever handed is a still-pending fetch handle that it itself must finish waiting on — true for a raw `fetch()` call (the only producer that existed before this feature), false for `.race`'s own return (already fully resolved by the time it's wrapped). Fixed with a new `PromiseResolved` flag distinguishing the two — see [ADR-00073](../adr/ADR-00073.md)'s Investigation for how this was found and the exact corruption it caused. Left here as a documented example of this TDD's design not fully anticipating an interaction with existing code, rather than edited away.

**`Settlement<T>` shape** (`.allSettled`'s per-element result): `{ status: "fulfilled" | "rejected", value: T, reason: Error }`. This compiler has no optional/union struct fields, so both `value` and `reason` are always allocated and always written (the inapplicable one zero-filled), matching how this project's other "one of two shapes" values (e.g. `T | null`) already work — not a new convention.

**A real, deliberate constraint inherited from the existing Promise model, not new here:** a plain `await p` already frees `p`'s slot once read (`emitAwait`'s existing behavior) — this project's `Promise<T>` has always been a single-owner, read-once value, not a real re-readable future. `Promise.all`/`.race`/`.allSettled` inherit this unchanged: each combinator call frees every element's own Promise slot as it consumes it, so feeding the same array to a second combinator call afterward is a use-after-free, exactly like awaiting the same promise variable twice already was. Not guarded against at compile time (this compiler doesn't track "already consumed" on values generally); documented in the example and test comments instead.

## Open questions

- **`Promise.race([])` (a runtime-empty array) hangs forever**, matching real JS's own `Promise.race([])` never settling — but here for a different reason (array length isn't known at compile time, so there's no earlier point at which this could be rejected). Documented as accepted behavior in the implementation, not silently guarded against; revisit only if it turns out to matter in practice.
- **Feeding the same array to two different combinator calls is an unguarded use-after-free** (see the Design section above). Not addressed here — would need this compiler to track "already consumed" on values generally, a bigger piece of work than this feature's own scope.
- **Real Promise rejection** (as opposed to a transport-level `fetch()` failure, the only kind of "rejection" this compiler's Promise model can express at all) is out of scope, unchanged from every other async-related document in this project.
