# ADR-01829: Iterator-creating calls are answered on the checker's side

- **Relations**: `Implements TDD-00230` (P3.3: inferExprType's kinds switch to the checker)
- **Date**: 2026-10-20

## Context

- `arr.keys()`, `values()` and `entries()` on an array, a Map or a Set are codegen's lazy iterator. Only codegen can name that representation.
- `codegenCallRepr` is the hook through which the checker's side asks codegen for such names. It covered iterator methods but not the calls that create the iterator. So the checker side left those calls unanswered, the largest `switchFallback` bucket on the examples and apps.

## Decision

- `codegenCallRepr` answers `keys()`/`values()`/`entries()` with no arguments, on an array-iterable or Map/Set receiver, with `CollIterType(receiver, kind)`. That is what the intrinsic types give.
- `ArrowFunction` stays unswitched. The checker's mapping is right about a find callback's `T | undefined` parameter, which the old inference misses. But it maps an annotated tuple return (`(): Pair => [a, b]`) to an array, while emission builds a tuple. A kind switches only when the old inference agrees with the checker over the whole corpus.

## Consequences

- On `examples/arrays/array_methods.ts`, disagreements drop from 10 to 7.
- Verified on Apple Silicon (targeted tests), and with the gate on Linux x86-64 (DeskMini).
