# ADR-00793: process.stdin.setEncoding('utf8') + chainable stream methods

- **Relations**: `Extends ADR-00339`, `Implements TDD-00024`
- **Date**: 2026-09-08

## Context

The canonical Node stdin-drain idiom is
`process.stdin.setEncoding('utf8').on('data', …).on('end', …)`. This compiler's
streaming `process.stdin` (ADR-00339) supported `.on('data'|'end')` and
`.setRawMode` but not `.setEncoding`, and `.on` returned void, so both the
`setEncoding(...)` opener and the `.on(...).on(...)` chain were compile errors —
the most common shape of real-world stdin code did not compile.

## Investigation

- `emit_stdin.go:emitStdinMethodCall` rejected any method other than `on`/
  `setRawMode`, and `on` returned `Value{Ty: TypeVoid}`.
- The `'data'` listener already receives each chunk as a UTF-8 string
  (`cpArrowClosure` with `[]Type{TypePtr}`), so `setEncoding('utf8')` requires no
  behavioural change — it is a faithful no-op. A non-utf8 encoding cannot be
  honored (there is no Buffer chunk to re-decode), so it is a clean rejection,
  not a silently wrong decode — the same posture the module's binary-mode gap
  already takes.
- Chaining needs two things: the methods must *return the stream*, and
  `inferExprType` must keep the `IsStdin` tag across a chained call so the
  dispatch at `emit_call.go` (`inferExprType(mem.Object).IsStdin`) still fires on
  `process.stdin.setEncoding('utf8')` (a `CallExpression`, not the bare member).

## Decision

- `emitStdinMethodCall`: add a `setEncoding` case — one string-literal arg,
  `'utf8'`/`'utf-8'` accepted as a no-op, anything else a clean compile error.
  Both `setEncoding` and `on` now return the stdin handle (`StdinType`) instead
  of void, so the stream chains.
- `inferExprType` (`CallExpression` arm): a call of `on`/`setEncoding` on an
  `IsStdin` object infers back to `StdinType()`, so `X.setEncoding(...).on(...)`
  and `X.on(...).on(...)` type-resolve.

`.pause()`/`.resume()`/`.read()`/`'readable'` stay unimplemented: they require
real flow-control/pull state, and a no-op would be a non-faithful divergence
(data would keep flowing after a `pause()`), so they remain documented caveats
rather than stubs.

## Implementation notes

- Files: `codegen/llvm/emit_stdin.go` (the `setEncoding` case + chainable
  returns + updated error/doc text), `codegen/llvm/emit_exprs_types.go` (the
  chained-call `IsStdin` inference).
- `setRawMode` still returns void and is intentionally handled before the
  streaming runtime is touched (it must not trigger the `O_NONBLOCK` flip);
  unchanged here.

## Side effects discovered

None. The single-listener-per-event, arrow-literal-only, synchronous-dispatch
posture is unchanged.

## Verification

macOS (Apple Silicon M4). `process.stdin.setEncoding('utf8').on('data', …).on('end', …)`
fed piped input is byte-identical to Node; a non-utf8 encoding is a clean
compile error. New tests `TestE2EStdinSetEncodingAndChaining` and
`TestE2EStdinSetEncodingNonUtf8Rejected` pass; the existing `TestE2EStdin*`
suite stays green; `make examples` runs the updated `process_stdin/stream.ts`
clean.
