# TDD-00094: Async-generators row to strict — nested generators, async `yield*`, `.next()` shape

- **Status**: Implemented
- **Date**: 2026-08-20

## Context

The async-generators row (`async function*` / `async *m()`) is ✅ but not **strict** — its Caveats
cell holds three items that keep it out:

1. **A nested `function*` (sync or async) is a clean rejection** (`emit_func.go`
   `emitFunctionDeclAs`: "a nested generator function declaration is not yet supported"). V1 was
   top-level-only.
2. **`.next()` returns an *already-resolved* `Promise<{value,done}>`** (the body runs synchronously
   to the next `yield`) rather than a pending one — annotated "observably identical for a `for
   await` consumer."
3. **`yield*` delegates to another *generator* only** — not a general `Symbol.asyncIterator`
   async iterable (which `for await...of` now consumes, TDD-00089).

Closing all three makes the row strict (async/promise strict 6/9 → 7/9). Nested generators is the
large one and — since the same rejection covers sync generators — also lifts a caveat on the
sync-generator row.

**Scoping finding (why nested generators is non-trivial):** a nested **function declaration** can't
capture an enclosing local *at all* today — `function outer(){ const x=5; function inner(){ return
x } }` fails with `undefined variable 'x'`. Only arrows/closures capture (via an env struct, boxing
mutable captures onto shared heap cells — ADR-00001). Named function declarations are separate
top-level LLVM functions with no env. So nested generators can't lean on existing function-decl
capture — there is none.

## Design

**Give a generator instance a closure env, reusing the arrow-closure machinery.** A generator
already has a per-instance heap struct (ctx/stack/`__paramN`/…) and a construction site where the
enclosing scope is live. Add an `__env` field; at a nested generator's *definition* gather its free
variables with the same `gatherCaptures`/box-mutable-cell path arrows use, build the env struct, and
at construction store the env pointer into the instance's `__env`. The body reads a captured name by
dereferencing its cell through `__env` (the same indirection an arrow body uses), so a mutation of
an enclosing `let` after the generator is created **is** seen on the next `.next()` — by reference,
JS-faithful (the property that makes it strict-eligible rather than a by-value-snapshot caveat).

- **Registration.** A top-level generator is registered in a pre-pass (`buildGeneratorSig`). A
  nested one is encountered *during* body emission; register its `GeneratorInfo` (now carrying
  `CaptureNames`/`CaptureTypes`) at that point, with captures gathered from the live scope, so a
  `g(args)` call constructs it.
- **Struct/type.** `GeneratorType` gains the `__env` field (a ptr); `GeneratorInfo` gains the
  capture layout. Non-capturing nested generators get an empty env (a null `__env`) and otherwise
  emit exactly like a top-level generator.
- **Async fold-in.** Because `async function*` fuses the sync-generator fiber with the task
  scheduler (TDD-00085), the env mechanism is identical for sync and async — nested `async
  function*` falls out of the same work.

**`yield*` over an async iterable (item 3).** Extend `emitYieldStar`'s async path: when the operand
is not a generator but a `[Symbol.asyncIterator]()` class (TDD-00089), delegate by driving
`obj[Symbol.asyncIterator]().next()` and re-yielding each awaited `{value,done}` — reusing
`emitForAwaitOfAsyncIterable`'s call/await core, but re-yielding instead of binding a loop var.

**`.next()` shape (item 2).** Verify whether the already-resolved-promise return is *actually*
observably identical (it should be: a `for await` consumer awaits it either way, and a manual
`await it.next()` too). If genuinely indistinguishable, it is a **Note, not a caveat** — move it to
the Notes column (this is the misplaced-note audit, not new behavior). If a real difference exists
(e.g. ordering against other microtasks), it stays a caveat and the row can't be strict until the
async-generator step is made to return a pending promise — a larger item flagged, not hidden.

## Stages

1. **Nested generators (sync + async), by-reference capture.** `GeneratorType.__env` +
   `GeneratorInfo` capture layout; nested-declaration registration with `gatherCaptures`; store
   `__env` at construction; body reads captures through it; lift the `emitFunctionDeclAs` rejection
   for a generator whose captures are all resolvable (a capture the machinery can't box stays a
   clean rejection, never a silent miscompile). Verify capture-by-reference, non-capturing nested,
   and nested async.
2. **Async `yield*` over a `Symbol.asyncIterator` iterable.** Extend `emitYieldStar`.
3. **`.next()`-shape audit + drive to strict.** Reclassify the note if observably identical; update
   the status rows (async-generator + sync-generator nested caveat) and counts.

## Open questions

- **Definition-time vs construction-time env.** JS captures the lexical env at *definition*; each
  `g()` shares it. Building the env at the definition point (a local holding the env struct) and
  storing it into every instance at construction matches that. If definition and construction are in
  different scopes (a generator returned across a boundary), the env local must still be reachable —
  the same limitation arrow closures already have; out of scope beyond it.
- **A capture the boxer can't handle** (an array variable — `gatherCaptures` already rejects
  capturing an array). Keep it a clean rejection for nested generators too, narrowing over time,
  never a silent miscompile.
- **`.next()` pending-promise.** If the shape audit finds a real observable difference, making async
  `.next()` return a genuinely-pending promise is a separate, larger change (the body would suspend
  before the first `yield` too) — flagged here, not smuggled into this row's strict claim.
