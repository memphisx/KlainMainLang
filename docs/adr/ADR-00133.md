# ADR-00133: Fix two `EventSource` auto-reconnect hangs in the event loop's own `select()` wait

- **Relations**: Extends [ADR-00122](ADR-00122.md), [ADR-00123](ADR-00123.md), [ADR-00124](ADR-00124.md), [ADR-00129](ADR-00129.md). Implements [TDD-00038](../tdd/TDD-00038.md)
- **Date**: 2026-08-09

## Context

A GitHub Actions run of `go test ./...` failed with `panic: test timed out after 10m0s`, stuck in `TestE2EEventSourceAutoReconnectReplaysLastEventID` — the whole test binary killed by Go's own test-suite timeout, not a per-test failure. The user reported this before any further work was to proceed.

`TestE2EEventSourceAutoReconnectReplaysLastEventID` (`tests/eventsource_test.go`) exercises Stage 3's auto-reconnect (ADR-00129): a server sends a `retry: 50` + `id: abc123` + `data: first` record and then ends the response (simulating a mid-stream drop); the client should reconnect ~50ms later replaying `Last-Event-ID: abc123`, and the test's own second server response echoes that value back so the test can observe `count == 2` and call `es.close()`.

## Investigation

Reproduced locally by running the single test in a loop: it hung on roughly 1 in 6–15 runs (`go test ./tests/... -run TestE2EEventSourceAutoReconnectReplaysLastEventID -count=1`, repeated). Confirmed the *compiled KML binary itself* was stuck, not the Go test harness, by inspecting the leftover child process directly: `/proc/<pid>/status` showed `State: S (sleeping)`, `/proc/<pid>/wchan` showed `do_select`, and `ss -tan`/`lsof -p <pid>` showed the client's TCP socket to the test server still `ESTABLISHED`. `gdb -p <pid>` was blocked by this box's `ptrace_scope=1` (no sudo available in-session), so diagnosis went through `/proc/<pid>/{status,wchan,fd,fdinfo}` plus live instrumentation instead of a debugger backtrace.

Reproduced independently of `go test` entirely: a standalone Go `httptest`-style server plus a directly-compiled KML binary (`klainmain -o repro repro.ts`, no `go test` in the loop at all) hung at the same rate, confirming this isn't specific to the Go test harness or CI's environment — a real, timing-dependent bug in the compiled program's own event loop.

Instrumented `runtime_eventsource.go`/`runtime_http.go` directly with temporary `dprintf(2, ...)` calls (declared via the already-existing `ensureDprintf()`) at `__kml_eventsource_close`, the scan's `doopen2`/`checkopenstate`/`doreconnectschedule`/`doreconnect` transitions, and the main loop's `scandone` — rebuilt `klainmain`, ran the repro in a loop capturing stderr until a hung run was caught, and diffed its trace against a successful run's. The hung run's trace stopped cleanly after `[DBG doreconnect]` and one `[DBG scandone]` line — no `doopen2-pre` for the reconnected transfer ever printed, meaning the process blocked in `select()` before ever getting a chance to process the already-*sent* second response.

Root cause (bug 1, intermittent): `__kml_eventsource_connect` (shared by the original connect and every reconnect) calls `curl_multi_perform()` once, synchronously, immediately after `curl_multi_add_handle()`, to kick the transfer off — entirely outside `__kml_event_loop_run`'s own select()-then-perform cycle. For a fast/local response, that single call can fully deliver the whole body into `pending->buf` (via `__kml_curl_write_cb`) before `select()` is ever reached this iteration. The bytes are already off the real socket — there is no *new* readability event left for `select()` to wait for — but nothing had told the loop this already-arrived data still needed dispatching. With no JS timer due and no other socket activity forthcoming, `select()`'s `notimeoutpath` (a `NULL` timeout) then blocked forever on a socket that would never produce anything new, with the buffered `replayed-abc123` message — and the `onmessage` handler's own `es.close()` that would have unblocked everything — permanently stuck behind it.

While fixing bug 1 and re-testing, found a second, **fully deterministic** bug by testing the identical scenario with its incidental `setTimeout(() => {}, 800)` removed (the existing test, and every other `EventSource` test in the file, always has some `setTimeout`, which was incidentally bounding `select()`'s wait and masking this): with zero JS timers anywhere in the program, the *first* connection's response also hung, every single run. Traced with the same `dprintf` approach (now also printing `nfds`/`hascurl`): the first connection's data got dispatched fine, but once `__kml_eventsource_scan` detected EOF and called `doReconnectSchedule` (setting `reconnectAtMs` to a real deadline ~50ms out), `nfds` dropped to `0` (no live curl handle to watch during the wait) and nothing else was pending — `select(0, ..., NULL)` blocks forever, equivalent to `pause()`. Root cause (bug 2): `reconnectAtMs` is pure runtime bookkeeping, never entered into `@__kml_timer_data` (the JS-visible `setTimeout`/`setInterval` queue) — `__kml_event_loop_run`'s `select()`-timeout computation (`timerscan`'s `%besti`/`%bestfire`) had no way to know a reconnect deadline existed at all, so a reconnecting `EventSource` in a program with no other timer/listener/fetch in flight would hang deterministically waiting for a deadline nothing ever checked.

Both bugs are the same underlying class already named once in this codebase: `runtime_http.go`'s own `%forcezero` mechanism (TDD-00039 Stage 3, added for `WebSocket` client `onopen`/`onclose` notifications) exists for exactly "a synchronous side channel resolved real work outside `select()`'s own wait/wake cycle" — `EventSource` never got an equivalent for either its own version of that hazard (bug 1) or its separate reconnect-deadline gap (bug 2).

## Decision

**Bug 1 fix** — a new `__kml_eventsource_has_pending_work()` (`runtime_eventsource.go`) scans every non-`CLOSED`, non-waiting-to-reconnect entry for either unconsumed buffered bytes (`pending->buf->len > entry->consumedOffset`) or an already-set `done` flag; the main loop (`runtime_http.go`) calls it once per iteration, right before computing `select()`'s timeout, and — mirroring `wscsetloop`'s existing `%forcezero` pattern exactly — routes a true result into the same `%forcezero` flag, forcing an immediate (zero-wait) `select()` re-check instead of a real blocking wait.

**Bug 2 fix** — a new `__kml_eventsource_next_reconnect_ms()` (`runtime_eventsource.go`) returns the soonest `reconnectAtMs` among every waiting entry, or `-1` if none is waiting. `runtime_http.go`'s `scandone` now folds this into the *existing* `%besti`/`%bestfire` computation: renamed the original `%havetimer` to `%havetimer_js` (still `%besti != -1`, i.e. "a real JS timer exists"), computed the ES reconnect deadline in nanoseconds (both clocks are `monotonicClockID()` — `CLOCK_MONOTONIC` — so comparable after `* 1000000`), took the earlier of it and any real timer's own `%bestfire`, and defined a new merged `%havetimer = %havetimer_js OR %hasesreconnect` for everything downstream that only needs "should `select()` block indefinitely or not" (the `anywork0`/`usetimer` computations).

**Kept `%besti` (the *which* JS timer to fire) pointing only at real timers.** `checktimerfire`'s own `dofire` block indexes `@__kml_timer_data[besti]` to actually invoke a timer callback — since `%besti` stays `-1` whenever only an ES reconnect bounded the wait, that block was changed to branch on `%havetimer_js` again, not the new merged `%havetimer`. Missing this on the first pass caused a segfault (`%besti == -1` indexing the timer array) the moment a reconnect-only wait's deadline came due — caught immediately by re-running the same no-timer repro after the first attempt at this fix, before it ever reached a test file. Reconnects themselves are still only ever actually fired by `__kml_eventsource_scan`'s own `dowait`/`doreconnect` deadline check (unchanged) — bug 2's fix only makes sure the wait *leading up to* that check is bounded, never fires anything itself.

## Implementation notes

- Files touched: `codegen/llvm/runtime_eventsource.go` (two new functions), `codegen/llvm/runtime_http.go` (`scandone`'s `%havetimer` split/merge, the pre-`select()` `%forcezero` check, `checktimerfire`'s branch fixed back to `%havetimer_js`), `tests/eventsource_test.go` (one new regression test).
- Diagnosis-only, not part of the shipped fix: the `dprintf`-based instrumentation described above was added, used to catch both bugs live, and fully reverted (`git checkout --`) before writing the real fix — none of it is in the final diff.
- `__kml_eventsource_has_pending_work`/`__kml_eventsource_next_reconnect_ms` both reuse the exact struct-field GEP indices already established by `__kml_eventsource_scan`/`__kml_eventsource_close` (`entry = {pending(0), instance(1), consumedOffset(2), state(3), listeners(4), url(5), retryMs(6), reconnectAtMs(7), contentType(8)}`, `pending = {easy(0), buf(1), done(2), status(3), result(4)}`, `buf = {data(0), len(1), cap(2)}` — see `runtime_eventsource.go`'s own top-of-file doc comment) — no new struct layout, just two new read-only scans over the existing `@__kml_es_data` array.
- Both new functions are declared/defined unconditionally by `ensureEventSourceRuntime`, which `ensureHTTPRuntime` already calls unconditionally (same reasoning `__kml_event_loop_run`'s other always-referenced symbols — `__kml_group_satisfied`, `__kml_wsclient_scan` — already rely on, per that function's own doc comment): every program that pulls in the event loop at all gets these symbols defined, whether or not it ever constructs an `EventSource`, so the `.ll` always links.

## Side effects discovered

- The reproduction loop left several orphaned, permanently-hung `prog` child processes on this box from *earlier* sessions' own `go test` runs (visible via `ps -ef --forest` reparented under PID 1/systemd-equivalent) — silent evidence this exact bug had already been intermittently hitting local runs before it was ever investigated, just never below the threshold of "worth chasing." Killed manually as part of this cleanup; not otherwise a code change.
- `gdb -p <pid>` requires `ptrace_scope=0` or root on this box (Ubuntu default hardening, `/proc/sys/kernel/yama/ptrace_scope`); no `sudo` was available in-session, so this ADR's diagnosis went through `/proc/<pid>/{status,wchan,fd,fdinfo}` and direct source instrumentation instead. Noting for next time this project needs to debug a hung native binary on this specific machine.

## Verification

- Both bugs reproduced reliably *before* the fix: bug 1 at roughly a 1-in-6–15 rate over dozens of standalone runs (both via `go test -count=1` in a loop and via a directly-compiled binary run outside `go test` entirely); bug 2 at 100% (5/5, then confirmed again after the `%besti` correction) once the test's own `setTimeout` was removed.
- After the fix: the original repro run 100/100 with no hang (`timeout 3 ./repro`, looped); `go test ./tests/... -run TestE2EEventSourceAutoReconnectReplaysLastEventID -count=30` all pass; the no-timer variant run 100/100 directly and `-count=20` under `go test`, all pass.
- Added `TestE2EEventSourceAutoReconnectNoOtherTimerInProgram` (`tests/eventsource_test.go`) — the same reconnect-and-close scenario with *no* `setTimeout` anywhere in the program, deliberately, since every other `EventSource` test in the file has one and would not have caught bug 2 at all.
- Full suite: `go build -o klainmain .`, `go vet ./...`, and `go test ./...` all pass, including `TestE2EEventSource*`/`TestE2EWebSocket*`/`TestE2EHTTP*`/`TestE2EFetch*` run at `-count=3`–`5` to check for regressions in the shared event-loop code path.
- Verified only on the x86-64 Linux box (this project's other machine, Apple Silicon, wasn't used for this fix). Nothing in the diff is platform-conditional (`clock_gettime`/`select`/`curl_multi_*` are already used unconditionally elsewhere in this same file on both platforms), so no platform-specific risk is expected, but noted per the project's own standing rule regardless — this is exactly the kind of "genuinely intermittent, low base rate" bug that the project's own platform-switching guidance warns can look fixed on one machine while still lurking on the other.
