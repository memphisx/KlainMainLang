# ADR-00979: Background AbortSignal.timeout dispatch

- **Relations**: Extends ADR-00238, ADR-00978; Implements TDD-00216
- **Date**: 2026-09-16

## Context

`AbortSignal.timeout(ms)` only latched its `aborted` flag lazily
(`__kml_signal_aborted`, checked by the fetch await loop / resume scan). It never
dispatched the `"abort"` event, so `addEventListener('abort', …)` listeners and
the `onabort` property never fired at the deadline, and a bare `signal.aborted`
read did not reflect the timeout in the background. This was a standing caveat on
the AbortController/AbortSignal status row; caveats are bugs, so it is fixed here
rather than re-documented.

## Investigation

- `emit_abort.go` `emitAbortSignalTimeout` stored only `deadlineNs`; nothing
  dispatched. `codegen/llvm/emit_timers.go` (`__kml_timer_drain`,
  `__kml_timer_fire_next`) and `runtime_http.go` (`__kml_event_loop_run`) are the
  sleep/`select()` points; they fire `void(env)` closures inline.
- No global list of live AbortSignals existed — timeout signals were reachable
  only via the fetch pending-handle (`runtime_http.go` `fdfoldloop`), which is why
  a non-fetch timeout was invisible to the loop.
- **Rejected: schedule a real timer.** A real timer keeps the loop/drain alive
  until it fires, turning `fetch(url, { signal: AbortSignal.timeout(30000) })` that
  completes in 100 ms into a 30 s hang. Node avoids this by unref-ing the timeout.
- **Rejected: add an `unref` field to timer entries.** The entry layout
  `{i64,i64,i64,ptr}` is hardcoded across `emit_timers.go` and the event loop;
  threading a 5th field is invasive and error-prone.

## Decision

A **separate abort-timeout registry** the loops fire *from* but never stay alive
*for* — unref by construction, so no hang is possible.

- Registry (thread-local, mirrors the timer queue): `@__kml_abort_to_data/len/cap`,
  an array of `{ i64 deadlineNs, ptr sig }`. `emitAbortSignalTimeout` calls
  `@__kml_abort_to_register(deadline, sig)`.
- Two loop-facing helpers, **always emitted** (from `ensureTimerRuntime`, which the
  event loop also pulls in) so the loop hooks compile unconditionally and are
  cheap no-ops on an empty registry: `@__kml_abort_to_soonest()` (soonest unfired
  deadline, 0 = none) and `@__kml_abort_to_fire_due()` (fire every past-due entry,
  mark it `-1`). `fire_due` dispatches through `@__kml_abort_to_fire_fn`, a
  function pointer that stays null until `register` arms it — so the
  abort-specific dispatcher symbol is referenced only where it is defined,
  independent of emission order.
- One compile-time dispatcher `@__kml_abort_timeout_fire(ptr sig)`
  (`emitAbortTimeoutDispatcher`, builder-state swap like `emitClosureFunc`): set
  `aborted`, build+store a `TimeoutError` DOMException reason, then
  `emitFireOnabort` + `emitDispatchToMap` over the signal parameter — reusing the
  compile-time emitters, so no runtime listener-map/closure/reason helpers.
- Loop integration (fold the soonest deadline into the wait, keep the timer's own
  deadline separate, fire due aborts after waking): `__kml_event_loop_run` folds
  into `%cmdlabs` and calls `fire_due` per iteration; `__kml_timer_drain` and
  `__kml_timer_fire_next` fold into the sleep target and, after waking, fire due
  aborts then re-check whether the chosen timer is actually due (if we woke only
  for an abort, drain loops back / fire_next returns progress).

The registry is never part of any keep-alive decision, so a lone timeout or an
early-completing fetch exits immediately without firing (Node unref parity). The
lazy `deadlineNs` latch stays (fetch fold, `AbortSignal.any` snapshot); the
registry is the sole listener dispatcher and fires each entry once.

## Implementation notes

- Files: `emit_abort.go` (registry, dispatcher, register), `emit_timers.go`
  (`ensureAbortRegistryGlobals` wired into `ensureTimerRuntime`; drain/fire_next
  fold+recheck), `runtime_http.go` (event-loop fold + per-iteration fire),
  `emitter.go` (`usedAbortTimeout`/`usedAbortRegistry` flags).
- `soonest`/`fire_due`/registry globals are emitted whenever timers are; only the
  dispatcher + `register` are gated on actual `AbortSignal.timeout` use.

## Side effects discovered

A fetch-attached timeout signal's listeners/`onabort` now also fire at the
deadline (previously fetch only threw) — a bonus from the registry being
independent of the fetch path. `AbortSignal.any` live propagation remains open
(separate caveat).

## Verification

- `go build` + `go vet` clean.
- New E2E tests (`tests/abort_test.go`): `TestE2EAbortSignalTimeoutBackgroundDispatch`
  (onabort + listener fire at the deadline while a later timer keeps the loop
  alive; `aborted` reflects it) and `TestE2EAbortSignalTimeoutUnref` (a lone
  timeout exits immediately without firing). Full `TestE2EAbort*`/`Fetch*`/`Timer*`
  groups pass on macOS arm64 (M4).
- Manual: a 30 s timeout with an http server closing at 100 ms exits at ~0.1 s
  (matching the no-abort baseline), never hanging; a 60 ms timeout fires its
  onabort via the event loop.
