# ADR-00088: `Array.from(iterable)` (array-like overload)

- **Relations**: Extends [ADR-00063](ADR-00063.md). Implements
  [TDD-00009](../tdd/TDD-00009.md)'s Stage 1a iterator-protocol consumer
  side.
- **Date**: 2026-07-31

## Context

Listed in `docs/status/README.md`'s "High priority / low complexity" table
with a specific reason it had gotten cheaper since last scoped: "a general
iterable protocol now exists (a class implementing `next(): T | null`,
ADR-00063) — just needs draining that (and a plain array) into a fresh
array." Picked up alongside ADR-00085/ADR-00086/ADR-00087 as the fourth of a
small batch of self-contained features. Scoped from the start to the
array-like overload only, per that same status-page note ("The array-like
overload is the only one needed initially").

## Investigation

Read `emit_arrays_iter.go`'s existing `emitArrayOf` (`Array.of(...items)`)
for the established shape of a `Array.<static>` builtin that returns a fresh
`{ptr, i64}` array aggregate — reused its malloc + per-slot `getelementptr`/
`store` pattern for the plain-array-copy path.

Read `emit_classes.go`'s `emitForOfClassIterator` (`for...of` over a class
implementing the Stage 1a iterator protocol) to understand the existing
drain-by-repeated-`next()` mechanism: a `next(): T | null` zero-arg method,
called in a loop, terminated by comparing the return value against a
zero/null sentinel (`icmp eq elemTy.IR nextVal, zero`). Confirmed the
detection rule this compiler already uses to recognize a class as iterable
(`emit_stmts.go:344-346`, `emitForOf`): `MethodSigs["next"]` exists, takes
zero parameters, and has a nullable return type that isn't itself an
array/map/set — reused this exact rule for `Array.from`'s own dispatch
rather than inventing a second one.

Since a class iterator's length isn't known upfront (unlike a plain array),
checked `emit_arrays_mutate.go`'s `emitPush` for this compiler's existing
"grow a heap array one element at a time" pattern:
`realloc(curPtr, (curLen+1)*elemAlign)` per element. Confirmed
`realloc(NULL, n)` is a valid, ordinary `malloc(n)` per the C standard, so
the drain loop's initial pointer can start as a bare `null` with no special
first-iteration case.

## Decision

New `emitArrayFrom(args []ast.Expression, pos ast.Pos) (Value, error)`
(`emit_arrays_iter.go`), dispatched from `Array.from(...)` in `emit_call.go`
right alongside the existing `Array.isArray`/`Array.of` bare-identifier
namespace check. Exactly one argument; two cases based on
`inferExprType(args[0])`:

- **Plain array** (`IsArray`): resolve via the existing
  `resolveArrayForHOF`, `malloc` a fresh buffer of the same byte length, one
  `memcpy`, wrap in a fresh `{ptr, i64}` aggregate — a straight, independent
  copy (mutating the source afterward doesn't affect the result, confirmed
  directly).
- **Class instance implementing the iterator protocol**: same
  `MethodSigs["next"]` shape-check `emitForOf` already uses. Drains via a
  `cond`/`body`/`end` loop shaped exactly like `emitForOfClassIterator`'s
  own (call `next()`, compare against the zero/null sentinel, branch to
  `end` on the sentinel), except the loop body appends each element into a
  growing `(ptr alloca, i64 len alloca)` pair via the same
  realloc-per-element shape `emitPush` already established, rather than
  running a caller-supplied loop body.
- Anything else (a plain scalar, a string, an object with no `next()`, a
  Map/Set — Map/Set iteration goes through a different, array-materializing
  path already, not this one) is a clean compile error naming what's
  missing, not a silent miscompile.

`inferExprType` (`emit_exprs_types.go`) got a matching `"from"` case next to
the existing `"of"` one: the plain-array branch returns `ArrayOf(*argTy
.ElemType)`; the class-iterator branch returns `ArrayOf(sig.RetType`, with
`Nullable` cleared).

Real JS's second (`mapFn`) and third (`thisArg`) arguments, and iterating a
string/`Map`/`Set` directly through this entry point, are deliberately not
built — matching the status page's own "array-like overload... only one
needed initially" scoping note.

## Implementation notes

Files touched: `codegen/llvm/emit_arrays_iter.go` (`emitArrayFrom`);
`codegen/llvm/emit_call.go` (dispatch, alongside `Array.isArray`/`Array.of`);
`codegen/llvm/emit_exprs_types.go` (`inferExprType`'s `"from"` case).

Non-obvious: the class-iterator branch reads `nextVal.Ty.IR` (the value
actually returned by the `emitClassCall` to `next()`) to pick the
zero/null sentinel, not `elemTy.IR` computed separately beforehand — both
are the same type in practice (`nextVal.Ty` *is* `sig.RetType` with
`Nullable` still set), but sourcing the sentinel check from the freshly
emitted call's own result type keeps the "what does 'done' look like" check
textually next to the value it's checking, mirroring
`emitForOfClassIterator`'s own layout.

## Side effects discovered

While manually verifying the class-iterator path, hit a real, pre-existing
bug in the Stage 1a iterator protocol itself, **not introduced by this
change**: a `next(): number | null` iterator whose *legitimate* first
returned value is exactly `0` terminates immediately, because this
compiler's nullable-number representation uses a bare `0` as both "the
number zero" and "null" — indistinguishable at the sentinel-comparison
`icmp eq i64 nextVal, 0` both `emitForOfClassIterator` and this ADR's own
drain loop use. Confirmed independently of `Array.from`: a plain
`for...of (const x of new Counter(5))` over a hand-written counter class
starting at `0` hits the exact same silent-empty-iteration behavior. Not
fixed here — this is the same pre-existing gap ADR-00087 also ran into from
a different angle (`number | null` via `??`/`??=`), and fixing it for real
would need a different runtime representation for nullable non-pointer
types (a boxed `{value, isNull}` pair, or similar) across every consumer of
this protocol, not a narrow one-call-site patch. Worked around in this ADR's
own tests/examples by choosing iterators whose legitimate values never
include a real `0`. Flagged in `docs/status/LANGUAGE-CONSTRUCTS.md`'s Known
Limitations rather than silently left undiscoverable.
