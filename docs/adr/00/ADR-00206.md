# ADR-00206: RegExp ECMAScript-dialect alignment (Options A + B) and the `-regex` mode selector

- **Relations**: `Implements TDD-00067`. `Extends ADR-00114` (RegExp construction / PCRE2 compile plumbing).
- **Date**: 2026-08-17

## Context

The RegExp backend (TDD-00035, ADR-00114–ADR-00120) handed the pattern to `pcre2_compile_8` verbatim, mapping only `i`/`m`/`s` to `PCRE2_CASELESS`/`MULTILINE`/`DOTALL` and setting no base options. That exposed PCRE2's Perl semantics, not ECMAScript's, so three everyday-JS behaviors were wrong (documented as Known correctness bugs in `docs/status/REGEXP.md`, analysed in TDD-00067):

1. `/foo$/.test("foo\n")` returned `true` (PCRE2 `$` matches before a trailing newline; ES anchors at true end).
2. `/(a)?b\1/.test("b")` returned `false` (backref to an unset group; ES matches empty).
3. `/A/` threw `PCRE2 does not support \u` at construction (PCRE2's default escape dialect isn't ES's).

TDD-00067 staged the fix as Option A (compile-option alignment), Option B (`PCRE2_UTF`/`UCP` code-point matching), the `es-utf16` index stage, and Option C (a normalization pass), behind a whole-program `-regex=<mode>` selector. This ADR implements Stages 1 and 2 (A + B) together — B's index-space question resolved to "keep byte offsets," which removed what would otherwise have gated it, so there was no reason to ship A alone first.

## Investigation

- `codegen/llvm/emit_regexp.go:emitNewRegExpExpression` is the sole pattern-compilation site; every method reads the one stored `pcre2_code*` handle, so changing the compile options propagates to all matching methods without touching the match sites.
- `__kml_regex_parse_flags` (`codegen/llvm/runtime_regexp.go`) already computes the `i`/`m`/`s` option bits and decomposes the multiline flag — the bit needed to gate `PCRE2_DOLLAR_ENDONLY`.
- The index-space decision (TDD-00067's central open question) was settled by reading the rest of the string layer: `.charCodeAt`/`.codePointAt` index by byte and return the byte value (ADR-00028, `docs/status/STRING-METHODS.md`), `.length`/`.slice` are byte-based. PCRE2_8's ovector offsets are already byte positions, so keeping them makes `match.index` consistent with `str.slice(match.index)`; converting to UTF-16 would make RegExp the only UTF-16-indexed surface in the language. Option B therefore needs no conversion layer.
- Real `pcre2.h` (Homebrew libpcre2 10.47, `/opt/homebrew/include/pcre2.h`, Apple Silicon) was read to get the option values, per the project's platform-sensitive-constant rule — `PCRE2_ALT_BSUX`=2, `PCRE2_DOLLAR_ENDONLY`=16, `PCRE2_MATCH_UNSET_BACKREF`=512, `PCRE2_UCP`=131072, `PCRE2_UTF`=524288, `PCRE2_NEWLINE_ANY`=4.
- `PCRE2_EXTRA_ALT_BSUX` (which enables `\u{…}`) was deliberately excluded: it needs a compile-extra-options context, and, more importantly, `\u{3}` without the `u` flag is an ES quantifier (`u` ×3), not a code point — so it must ride with the deferred `u`-flag/Option C work, not be set unconditionally.

## Decision

Add a whole-program `-regex=<mode>` flag (`pcre` / `es-ascii` / `es-unicode`; unset resolves to the highest implemented ES stage, `es-unicode`), threaded like `-mm=`/`-globals=`:

- `main.go` validates the value and calls `em.SetRegexMode(*regex)`; `es-utf16`/`ecmascript` are recognized but rejected as not-yet-implemented.
- `Emitter.regexMode` + `SetRegexMode` + `resolveRegexMode` (the single place the default is defined).

At each RegExp construction, `regexModeOpts()` yields the mode's PCRE2 configuration, applied in `emitNewRegExpExpression`:

- **`baseOpt`** (compile-time immediate) OR-ed into the parsed options: `ALT_BSUX | MATCH_UNSET_BACKREF` for both ES modes, plus `UTF` for `es-unicode`. Fixes bugs 2 and 3, and (es-unicode) makes `.`/classes code-point-based. `PCRE2_UCP` is deliberately **not** set — see Side effects; the conformance data ruled it out of B.
- **`DOLLAR_ENDONLY`** applied via a runtime `select` on the already-parsed multiline `i1` (present ⇒ 0, absent ⇒ 16), so it is off when `m` is set. Fixes bug 1.
- **`NEWLINE_ANY`** (es-unicode only) set on a `pcre2_compile_context` created/configured/freed around the compile call, in place of the `ptr null` the other modes pass. The compiled pattern copies what it needs, so the context is freed immediately after compiling.

`pcre` mode sets none of these — today's behavior, kept as an explicit opt-in for PCRE-only features, not a fallback.

The index space stays byte-based (see Investigation); Option B adds no offset-math change. `__kml_regex_parse_flags` is untouched — all mode logic lives at the Go call site because the mode is a compile-time constant.

## Implementation notes

- New `used`-flag `usedRegexCompileContext` guards `ensureRegexCompileContext` (declares `pcre2_compile_context_create_8`/`pcre2_set_newline_8`/`pcre2_compile_context_free_8`), so a `pcre`/`es-ascii` program never emits those decls or links anything extra.
- Constants live in `runtime_regexp.go`'s existing hardcoded-macro block, with the same re-verification caveat (values read on the Mac; re-verify against the linked `pcre2.h` on the Linux machine before relying on them there).
- The `DOLLAR_ENDONLY` gate must read the multiline flag *before* the compile call; the load was added early (the later per-field struct store still reads the same slot, harmlessly).
- `tools/conformance` gained a `-regex` flag (threaded to `em.SetRegexMode` via a package-level var set in `main`) so a run can measure a specific dialect — used to make the UCP call above, and useful for any future per-mode measurement.
- Files touched: `main.go`, `codegen/llvm/emitter.go`, `codegen/llvm/runtime_regexp.go`, `codegen/llvm/emit_regexp.go`, `tools/conformance/main.go`, `tests/compiler_test.go`, `tests/regexp_test.go`, `examples/regexp/regexp_dialects.ts`, `docs/status/REGEXP.md`, `docs/tdd/TDD-00067.md`.

## Side effects discovered

- **Default behavior changed**: the default `-regex` (unset) now resolves to `es-unicode`, not the old raw-PCRE path. This is intended (the default should be the most ES-faithful mode available) and more correct; the full `go test ./...` E2E suite passed unchanged, confirming no ASCII-program regression.
- **`PCRE2_UCP` dropped from es-unicode based on conformance data.** The first cut set `UTF | UCP`. Measuring per-mode on `built-ins/RegExp` Test262 (via a new `-regex` flag added to `tools/conformance`) showed UCP *cost* conformance: `es-ascii` 38, `es-unicode` UTF-only 37, `es-unicode` UTF+UCP 36 (baseline `pcre` 36). The single UCP loss isolated to `built-ins/RegExp/u180e.js` — PCRE2's UCP `\s` matches U+180E, which ES dropped as whitespace in Unicode 6.3. UCP's Unicode `\w`/`\s`/`\b` semantics (with the ES-divergence corrections) are therefore reassigned to Option C; `es-unicode` ships UTF-only. Consequence: `\w`/`\s`/`\b` stay non-Unicode in every mode for now (documented caveat in `docs/status/REGEXP.md`); code-point `.` is unaffected.
- **New `es-unicode` caveats** (documented in `docs/status/REGEXP.md`, excluded from Strict Coverage): `NEWLINE_ANY` over-excludes `\x0b`/`\x0c`/`\x85` from `.`/`$`/`m` vs ES's exact four terminators (exact `.` is Option C); and a zero-length global match whose one-byte advance lands mid-code-point is treated as no-match under `PCRE2_UTF`, ending iteration early (fixed properly by the `es-utf16` index stage). Both tracked in TDD-00067.
- **`es-ascii` retains** the pre-existing `.`-matches-`\r` divergence (no compile context, so PCRE2's default newline convention); deliberate, since `es-ascii` is defined as option-bits-only.

## Verification

Machine: Apple Silicon M4, pcre2 10.47, `clang -O2`.

- New E2E test `TestE2ERegExpDialectModeMatrix` (`tests/regexp_test.go`, 14 sub-cases) pins the per-mode behavior for all three modes: `$`/newline, unset backref, `\u` escape, UTF-vs-byte `.` on `"café"`, the default resolving to `es-unicode`, and the `.`-vs-`\r` mode split. All pass.
- New helper `buildBinaryRegexMode`/`compileAndRunRegexMode` (`tests/compiler_test.go`) mirrors `main.go`'s `SetRegexMode`.
- New example `examples/regexp/regexp_dialects.ts` compiles and runs under the default mode with output matching every annotated line.
- Full suite green: `go build`, `go vet ./...`, `go test ./...` (incl. the ~392s E2E package).
- **Conformance (Mac, Apple Silicon, pcre2 10.47).** Measured Mac-vs-Mac to isolate the change from the known Mac/Linux platform delta (the committed `CONFORMANCE-RESULTS.md` is a Linux run at 5225; a fresh Mac `-regex=pcre` baseline — i.e. pre-change behavior — is 5215). New default `es-unicode`: **5220** full-corpus → **+5 on this machine**. Gains are RegExp/regexp-literal tests (`S15.10.2.11_A1_T5/T7`, `S7.8.5_A1.1_T1`/`A2.1_T1`, `staging/sm/RegExp/ignoreCase-multiple`). The one apparent loss (`built-ins/RegExp/S15.10.4.1_A8_T3.js`, an object-`toString` pattern-coercion test) is **flaky** — it passes/fails nondeterministically across runs in *both* modes, so it is not a mode regression. Per-category A/B on `built-ins/RegExp`: `es-ascii` 38, `es-unicode` 37, `pcre` 36. The canonical Linux `CONFORMANCE-RESULTS.md` was left untouched (not overwritten with a Mac run) and should be regenerated on the next Linux session.
