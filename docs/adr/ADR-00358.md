# ADR-00358: NUL-terminate the net dispatch 'data' chunk buffer

- **Date**: 2026-08-25

## Context

CI (Linux, full `go test ./...`) intermittently failed `TestE2ETLSCreateServer`:

```
tls_test.go:77: echo: got "echo:helloV", want "echo:hello"
```

The compiled `tls.createServer` echo server received `"helloV"` instead of the
5-byte `"hello"` the client sent — one extra byte of stack/heap garbage (`V`)
appended to the chunk. The accompanying `http: TLS handshake error ... bad
record MAC` stderr line was a red herring from an adjacent `httptest` server
closing down; the real failure is the off-by-one in the echoed content. The bug
is load- and allocator-dependent, so it reproduced only under the full parallel
suite on Linux glibc, never in isolation on macOS.

## Investigation

KML strings are NUL-terminated C strings — string concatenation and `.length`
go through `strlen` (`codegen/llvm/emit_strings.go:60`). A `socket.on('data',
(chunk: string) => ...)` listener therefore binds the chunk pointer directly and
computes its length with `strlen`.

The net dispatch handed that listener a buffer built in `__kml_net_dispatch`'s
`firedata` block (`codegen/llvm/runtime_net.go`):

```
%buf = call ptr @malloc(i64 %n)
call ptr @memcpy(ptr %buf, ptr %chunkptr, i64 %n)
call void %dfp(ptr %dep, ptr %buf, i64 %n)
```

`malloc(n)` is **not** NUL-terminated. `strlen(buf)` then reads past `[n]` until
it hits a stray `0` — on a fresh heap that byte is usually `0` (invisible),
under load it is garbage (`V`), yielding `"helloV"`.

Why only TLS tripped it: the existing net echo tests use `(chunk: Uint8Array)` +
`TextDecoder.decode`, which carries the explicit length `n` and never calls
`strlen` on the buffer. `TestE2ETLSCreateServer` is the first test to consume a
socket chunk as a `string`, so it was the first to exercise the over-read. The
HTTP request path already keeps its buffer NUL-terminated deliberately
(`codegen/llvm/emit_http.go:662`); the net data path was the outlier.

Confirmed with an AddressSanitizer build of a plaintext `net` echo server whose
listener declares `(chunk: string)`:

```
==ERROR: AddressSanitizer: heap-buffer-overflow ...
READ of size 6 at 0x... in strlen ... in __closure_1
```

The `READ of size 6` past a 5-byte allocation is exactly the `"helloV"`
symptom. After the fix the same ASan build is clean and echoes `"echo:hello"`.

## Decision

NUL-terminate the chunk buffer in `firedata`: allocate `n+1`, `memcpy` the `n`
read bytes, and store a `0` at `[n]`. The listener is still invoked with length
`n`, so `Buffer`/`Uint8Array` consumers are unaffected while `string` consumers'
`strlen` now stops exactly at the read length.

## Implementation notes

- `codegen/llvm/runtime_net.go`, `firedata` block: `malloc(n)` → `malloc(n+1)` +
  `getelementptr i8 ... i64 %n` + `store i8 0`.
- Only the server/connection drain path needed changing; this is the single
  place accepted-socket chunks are materialized for the `data` listener.

## Side effects discovered

The `(chunk: string)` socket-listener path had no direct test coverage — the
plaintext net tests all used `Uint8Array`. Added `TestE2ENetStringChunkEcho`
(plaintext, cheaper than the TLS path) to guard the NUL-termination invariant.

## Verification

- ASan repro: buggy tree reports `heap-buffer-overflow` in `strlen`; fixed tree
  clean, echoes `"echo:hello"`. (macOS, Apple Silicon.)
- `TestE2ENetStringChunkEcho` (new) passes.
- `go test ./tests/ -run 'TestE2ENet|TestE2ETLS|TestE2EWebSocket'` passes.
- `go vet ./...` clean, `go build` clean.
