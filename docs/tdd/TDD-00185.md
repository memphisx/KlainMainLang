# TDD-00185: Blocking-work thread pool for real async I/O

- **Status**: Implemented
- **Date**: 2026-09-08

Stages 1-3 shipped: the general per-loop wakeup fd, the shared pool + per-loop
completion queue, and `fs.promises.readFile` end-to-end
([ADR-00773](../adr/ADR-00773.md)); then the whole plain `fs.promises` table —
`writeFile`/`appendFile`/`unlink`/`mkdir`/`rmdir`/`rename`/`copyFile`/`readdir`
([ADR-00774](../adr/ADR-00774.md)), POSIX. The two Stage-3 follow-ons then
shipped ([ADR-00820](../adr/ADR-00820.md)): binary-data `writeFile`/`appendFile`
(an `ArrayBuffer`/`TypedArray` body, copied raw at submit) and the legacy
**callback** form both run on the pool now, off the loop thread — the callback
firing from a GC-safe settle reaction. Windows (no pool build yet) keeps the
inline path. Stage 4 (real streaming) was spun out into its own document,
[TDD-00186](TDD-00186.md) — its Part A (pool-backed `fs.createReadStream`) has
since shipped.

## Context

`fs.promises.*`, the `fs` callback forms, and `fs.createReadStream` are
**fake-async**: the blocking syscall runs *inline on the event-loop thread* and
the Promise is handed back already settled. `emit_fs_async.go` says so in its own
header — "this compiler has no thread pool, so V1 is async-shaped, not truly
non-blocking." `emitFsAsyncPromise` ([emit_fs_async.go](../../codegen/llvm/emit_fs_async.go)
`:153`) allocates a settled Promise, runs the synchronous helper (`emitFsReadFileSync`
et al.) under a setjmp guard, and sets state to fulfilled before returning;
`createReadStream` ([runtime_fs_stream.go](../../codegen/llvm/runtime_fs_stream.go))
`fopen`s and `fread`s to EOF eagerly.

For the CLI-tool target this is invisible. For the **microservice / REST-server
target it is disqualifying**: a request handler that `await`s
`fs.promises.readFile` freezes the single `select()`-based reactor
([runtime_http.go](../../codegen/llvm/runtime_http.go) `:1255`,
`@__kml_event_loop_run`) for the whole read — every other in-flight connection,
timer, and microtask stalls. This is BACKLOG §1 item 2, the largest remaining
faithfulness gap on the priority-1/2 path.

It is scoped now because everything the fix builds *on* already exists — only the
off-thread machinery is missing:

- the Promise settle + fiber-park/resume path (`@__kml_promise_settle`
  [emit_promise_new.go](../../codegen/llvm/emit_promise_new.go) `:27`; a parked
  `await` fiber resumed as a microtask, [runtime_task.go](../../codegen/llvm/runtime_task.go))
  is exactly the completion callback a background thread needs;
- real OS threads already ship twice — `Worker` (`pthread_create`,
  [runtime_worker.go](../../codegen/llvm/runtime_worker.go) `:165`) and the
  `klain:sync` M:N scheduler ([klainsync.c](../../codegen/llvm/klainsyncsrc/klainsync.c));
- the loop-wakeup socketpair (ADR-00757) already proves a thread can wake the
  reactor's `select()` — it just isn't a general primitive yet (Windows /
  `fs.watch` only).

## Design

A **libuv-style blocking-work thread pool**: file I/O runs on pool threads; the
Promise is *settled on the loop thread*. That last invariant is the whole design
— the loop, fiber, timer, microtask, and Promise state are all `thread_local`
and the reactor is thread-pinned (`@__kml_reactor_thread_lock`,
[runtime_http.go](../../codegen/llvm/runtime_http.go) `:726`), so a pool thread
**must not** touch a Promise, enqueue a microtask, or allocate on the JS/GC heap.
It does the raw syscall and marshals a plain result back; the loop thread does
everything JS-visible.

Three new primitives, mirroring the existing microtask-queue shape
([runtime_microtask.go](../../codegen/llvm/runtime_microtask.go)):

### 1. General loop-wakeup fd (`runtime_loopwake`)

Generalize ADR-00757's socketpair into one process-wide, per-loop wakeup
descriptor: `pipe2`/`socketpair` on POSIX, the existing socketpair on Windows.
Its read end is folded into the reactor read `fd_set` every iteration (next to
the libcurl fds); any thread writes one byte to break `select()`. The loop
drains the byte and proceeds to the completion drain. This is the same primitive
TDD-00182/00183 (the owned-handle reactor / IOCP) want, so it is built here as a
**shared reactor primitive**, not an fs-local hack — the reactor work inherits it.

### 2. Completion queue (`runtime_threadpool`, loop side)

A per-loop MPSC queue (mutex + intrusive singly-linked list) of completed work
items. Each item carries: the target Promise pointer, the op kind, the raw result
(a `malloc`'d buffer + length, or a scalar), and an errno (0 = success). Pool
threads push + write the wakeup byte; the loop thread drains the queue inside the
`timerscan:` block (where microtasks/tasks are already pumped) and, **on the loop
thread**, wraps the raw result into the JS value, then `@__kml_promise_settle`s
(or fires the callback). First-settle-wins already holds.

### 3. The pool (`runtime_threadpool`, worker side)

`N` pthreads (default 4, libuv's default; see OQ1) blocking on a work queue
(mutex + condvar), reusing the `Worker` `pthread_create` pattern — **not**
`klain:sync`, which is a deliberately separate non-Node world. A submitted work
item binds an existing blocking `*Sync` C helper to already-marshaled scalar/copied
args (e.g. a `strdup`'d path). The worker pops, runs the syscall into a **raw
`malloc`** buffer (never a GC allocation — Boehm does not scan pool-thread stacks
as roots; see [[project_finalization_registry]] macOS-TLS caveat), pushes the
completion, writes the wakeup byte. No JS callback ever runs mid-flight — the
`fs` ops are pure syscalls — so no JS heap or GC interaction happens off-thread.

### Lowering change

`emit_fs_async.go` stops running `spec.sync` inline. Instead it: evaluates the
args, `strdup`s/copies them into a work item, allocates a **pending** Promise,
submits the item, and returns that pending Promise. The awaiting fiber parks on
an unsettled Promise through the *existing* await path — no new suspend
machinery. The callback form submits identically and fires the callback from the
completion drain. `createReadStream` (Stage 4) submits chunk-sized reads rather
than one read-to-EOF.

### Staging (each stage is an independently testable checkpoint)

1. **Wakeup primitive.** `runtime_loopwake` on POSIX + Windows, folded into the
   reactor. No fs behavior change. Provable in isolation: a thread writing the
   wakefd cuts short a pending `select()` timeout.
2. **Pool + completion queue, one op end-to-end.** Route
   `fs.promises.readFile` through the pool. E2E test: a `setInterval` keeps
   firing while a large `readFile` is in flight (proves the loop no longer
   blocks). Example under `examples/`.
3. **Rest of the fs async table.** writeFile/appendFile/unlink/mkdir/rmdir/
   rename/copyFile/readdir + the callback forms (`fsAsyncOps()`).
4. **Streaming (candidate split to its own TDD).** `createReadStream` chunked
   via the pool instead of eager read-to-EOF; `Response.text()`/`.json()`/
   `.arrayBuffer()` returning real Promises that yield rather than driving
   libcurl to completion synchronously ([emit_fetch.go](../../codegen/llvm/emit_fetch.go) `:257`).

## Open questions

1. **Pool size + config — DECIDED.** Match libuv exactly: **default 4 threads**,
   `UV_THREADPOOL_SIZE` env read once at pool init for Node fidelity. No compiler
   flag for now (env is the Node-faithful knob; a flag can follow if wanted).
2. **One global pool or one per loop — DECIDED.** **One shared process-wide pool**
   (libuv's model). The **completion queue + wakefd are per-loop**, keyed by the
   submitting thread, so a completion routes back to the loop that issued the
   work. Shapes the Stage-2 queue ownership: the work item records its origin
   loop's completion queue + wakefd at submit time.
3. **GC safety across the thread boundary.** Confirm the worker's raw-`malloc`
   result buffer is safe with `-mm=gc`/`-mm=auto` (worker never GC-allocates; the
   loop thread GC-wraps at settle). Expected safe, but verify on Linux where the
   Boehm shim is touchier ([[project_benchmark_leak_findings]]).
4. **Relationship to the Windows reactor (TDD-00182/00183).** Orthogonal — the
   pool handles blocking *file* I/O, the reactor handles *socket/pipe* readiness —
   but they share the Stage-1 wakeup primitive. Not a dependency either way; note
   the shared primitive so neither reinvents it.
5. **Cancellation.** `fs` has no cancel; an aborted request whose handler is
   mid-`readFile` still lands its completion and settles a Promise nothing awaits.
   Harmless; no cancel path needed. Confirm no leak of the strdup'd args on the
   drop path.
