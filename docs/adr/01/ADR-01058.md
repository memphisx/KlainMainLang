# ADR-01058: `parentPort!.x` dispatches like `parentPort.x`; Windows `realpath` walks links when the final-path query can't answer

- **Relations**: Extends ADR-00769 (Windows readlink/lstat), ADR-00748 (Windows paths); Implements TDD-00098 (parentPort surface)
- **Date**: 2026-09-22

## Context

BACKLOG §0 item 2, two unrelated small bugs:

- `parentPort!.postMessage(v)` — the non-null assertion tsc users write because `parentPort` is typed
  `MessagePort | null` — failed with "a number has no method 'postMessage'"; without the `!` it worked.
- On this box's OSFMount RAM drive (`R:`), `fs.realpathSync(<symlink>)` threw `EINVAL: invalid argument, lstat …`
  where Node resolves it; `TestE2EFsPathOps` passed with `TMP` on `C:` and failed with `KML_SCRATCH=R:`.

## Investigation

`parentPort` is not a declared binding: its meaning lives in the by-name dispatch tables (`emitCall`
`emit_call.go:755`, and the member/inference sites). With a `NonNullExpression` wrapped around the identifier,
`mem.Object` was no longer an `*ast.Identifier`, the table lookups fell through, and `inferExprType` of the bare
unknown identifier gave the scalar default. `unwrapGlobalThis` (`emit_exprs_member.go`) already peels
`globalThis.` off the same three sites (call, member, inference), so it is the one place to erase the `!` too.

For `realpath`, a C probe on `R:` showed the cause: `GetFinalPathNameByHandleW(VOLUME_NAME_DOS)` returns 0 with
`ERROR_INVALID_FUNCTION` (the volume has no DOS device name — only `\Device\OSFMDisk0\…` in `VOLUME_NAME_NT` form),
and `win32fs.c`'s `realpath` mapped that to `EINVAL`. libuv's `realpath` makes the same call, so Node's
`realpathSync.native` fails there too — but `fs.realpathSync` is Node's JS lstat/readlink walk, which never asks the
kernel for a final path. A second case fell out while testing the walk: a relative link target stored with forward
slashes (`fs.symlinkSync("dir/sub/f.txt", link)`) is one the kernel will not follow — Node cannot `open` the link
either — yet Node's realpath resolves it, because the walk resolves `readlink`'s text with `path.resolve`.

## Decision

1. `unwrapGlobalThis` erases a `NonNullExpression` whose operand is an identifier that is **not** a declared local
   (`!e.isShadowedByLocal`). A `!` on a real local keeps its own path (it strips nullability from a typed value).
2. `win32fs.c`: `realpath` keeps the fast path (kernel follows, final DOS path — case-corrected, like `.native`)
   and falls back to `realpath_walk` whenever that path can't answer — the follow-open fails, or the final-path query
   does. The walk is Node's: `GetFullPathNameW` for an absolute normalized path, then component by component open
   with `FILE_FLAG_OPEN_REPARSE_POINT`; a symlink/junction's target (`reparse_target_utf8`, shared with `readlink`)
   replaces the walked prefix when absolute (`X:\`, `X:/`, UNC) or joins the link's parent when relative, the
   unwalked remainder is appended, the whole thing re-normalized and the walk restarts. 40 hops → `ELOOP`
   (`ERROR_CANT_RESOLVE_FILENAME`); a missing component → the open's own error (`ENOENT`). Case is kept as given, as
   Node's walk keeps it.

## Implementation notes

- `codegen/llvm/emit_exprs_member.go` (`unwrapGlobalThis`), `codegen/llvm/win32src/win32fs.c` (`realpath_walk`,
  `realpath`). A `win32src` edit needs a compiler rebuild (the C sources are embedded).
- The walk allocates its four 32 K-wchar buffers on the heap; `free()` may clobber the last error, so the error is
  read (`failp`) before `free_keep_err` in `realpath` and the walk sets a specific last error on its own exits.

## Side effects discovered

- `fs.readFileSync`/`open` on a symlink whose relative target was stored with forward slashes fails with `ENOENT`
  — the kernel doesn't follow it. Node fails the same way (verified: `readFileSync` → `ENOENT` on Node 24), so it is
  faithful; a program that needs it followed must create the link with a backslash target.

## Verification

- `TestE2EWorkerParentPortNonNullAssertion` (`tests/worker_test.go`).
- `TestE2EWinRealpathWalksLinks` (`tests/fs_faithful_windows_test.go`): relative link, dir link + trailing
  component, chain, `..`/`.`, ELOOP, dangling, missing — every line produced by Node 24 first, on both `R:`
  (OSFMount) and `C:` (NTFS). `TestE2EFsPathOps` passes with `KML_SCRATCH=R:` and with `TMP` on `C:`. Windows only;
  the POSIX `realpath` is untouched.
