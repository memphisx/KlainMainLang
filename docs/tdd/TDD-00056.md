# TDD-00056: Dynamic `import(...)` V2 — real laziness via runtime-loaded shared libraries

- **Status**: Not Started
- **Date**: 2026-08-10
- **Notes**: Shares its whole parser/resolver frontend with [TDD-00055](TDD-00055.md); only the codegen backend differs (a `.so`/`.dylib` island per dynamic-import target, `dlopen`'d and run-once on first actual use — genuinely closer to real ES module semantics than V1's eager merge). Reopens the linker-adjacent boundary [ADR-00022](../adr/ADR-00022.md) deliberately avoided; explicitly incompatible with `--static` (clean compile-time rejection, same posture as `-mm`'s existing mutual-exclusivity pattern), and `-mm=gc` across the `dlopen` boundary is flagged unverified, not assumed

## Context

[TDD-00055](TDD-00055.md) scoped dynamic `import(...)` as a literal-specifier form resolved eagerly at compile time — a real capability (syntax compatibility, a `Promise`-returning spelling identical to a static import), but honest about its narrowness: the target's top-level code always runs at startup regardless of whether the call site is ever reached, and a runtime-computed specifier is a clean compile error, not a restriction with room to grow. Real dynamic import's actual value propositions — lazy loading, genuinely runtime-gated execution — are structurally unavailable to a design that merges everything into one `*ast.Program` before codegen ever runs.

Raised directly, as an alternative: what if a dynamic-import target were compiled into its own shared library instead, `dlopen()`'d only the first time its `import()` call site actually executes? This would deliver real laziness, and — as a direct consequence of the loading mechanism, not extra design work — could support a *bounded* form of runtime-variable specifier later (see Open Questions), something [TDD-00055](TDD-00055.md)'s eager-merge model can never offer no matter how much it's extended.

The cost, worked through in conversation before writing this TDD: this reopens exactly what [ADR-00022](../adr/ADR-00022.md) deliberately avoided — a real linker-adjacent boundary, with its own ABI/layout-consistency questions — and collides directly with an already-shipped feature, `--static` (Linux scratch-container builds, one of this project's own stated priority use cases). The resolution for that collision, decided directly rather than left open: **a clean compile-time rejection** — `--static` plus any actual dynamic-import usage is simply an error, the same way `-mm=manual`/`-mm=gc` are already mutually exclusive by construction. No attempt to make the two coexist; they're a real, permanent "pick one" fork, and the compiler says so plainly rather than producing a binary that mysteriously can't load its own plugins.

## Design

### Shares its whole frontend with TDD-00055 — this is purely a backend/codegen alternative

Parsing (`import(...)` in expression position, the dedicated parse function, `Specifier` staying a general expression so a non-literal argument gets a real error message), and resolution (treating a literal specifier as a dependency edge, rejecting a non-literal one) are **identical** to [TDD-00055](TDD-00055.md)'s Stage 2 — not reimplemented here. The only thing that changes is what happens *after* a dynamic-import target is identified: instead of merging it into the main program's AST (eager, V1), it becomes the root of its own separate compilation output (lazy, this TDD) — selected by a new flag, `-dynamic-import=eager|lazy` (default `eager`, i.e. [TDD-00055](TDD-00055.md)'s behavior unchanged unless explicitly opted into this one). Keeping both as distinct, explicit modes rather than one superseding the other is deliberate: they have genuinely different tradeoffs (single self-contained `--static`-compatible binary vs. real laziness at the cost of a multi-artifact, dynamically-linked build), and a caller should choose on purpose, not receive a silent behavior change.

### One resolve pass, partitioned output — not independently-recompilable plugins

The whole reason a real ABI-versioning story can be avoided: this stays **one `klainmain` invocation, one resolve pass**, discovering every static import *and* every literal dynamic-import specifier exactly as today — but instead of merging every reachable file into a single `*ast.Program`, files reachable *only* through a dynamic-import edge (plus whatever they themselves statically import) are partitioned into separate "islands," each compiled to its own shared library (`.so` on Linux, `.dylib` on Mac) alongside the main executable. Because every struct/class layout decision in the whole program is still made by one consistent pass, the main binary and every island automatically agree on shared type layouts — no build-system convention ("always rebuild together") needs to be trusted; the compiler itself guarantees it structurally, the same way `--static`'s ADR-family already treats platform/linking guarantees as things to verify and encode directly rather than assume.

A single `klainmain app.ts` invocation using this mode therefore produces multiple artifacts: the executable, plus one shared library per distinct dynamic-import target (naming/output-directory convention still open, see Open Questions). This is a real, new deployment/packaging concern worth being explicit about — a program using `-dynamic-import=lazy` needs every produced artifact shipped together (a Dockerfile `COPY` of a directory, not a single binary); a program not using dynamic import at all is completely unaffected, still one self-contained binary exactly as today.

### Stable export symbols — a deliberately different naming scheme from the rest of the compiler

[TDD-00041](TDD-00041.md)'s per-file mangled names (`name__kml_modN`) are only unique *within one compile's own index space* — fine for a single merged program, not something a separately-`dlsym()`'d island can rely on matching against. Each island instead exports its members under a deterministic, hash-derived name (e.g. `__kml_dynmod_<hash of the island's absolute source path>_<export name>`), computed identically by both sides (the main binary's call-site code and the island's own compiled symbol table) since both are derived from the same resolve pass's knowledge of that file's absolute path — no runtime handshake needed to agree on names.

Every exported **function** in an island is compiled directly in the closure-header-compatible thunk form from the start (unlike [TDD-00055](TDD-00055.md)'s Stage 3, which has to retrofit thunks onto already-existing plain top-level functions) — since an island's codegen is a dedicated mode built for exactly this purpose, there's no reason to ever emit the bare, non-closure-shaped form for one of its exports at all. This sidesteps V1's thunk problem entirely rather than solving it twice.

### Module-init-once — genuinely closer to real ES module semantics than V1

Each island exports one more well-known symbol, an idempotent `__kml_module_init` — the island's own top-level statements, run exactly once, the first time the island is actually loaded. The call-site's generated code: check a cached `dlopen` handle for this island (keyed by the same deterministic name above); if absent, `dlopen()` it, call `__kml_module_init` exactly once, cache the handle; either way, `dlsym()` the requested export(s) and pack the result the same way [TDD-00055](TDD-00055.md)'s object-synthesis step does, wrapped in `wrapResolvedPromise`. This means an island's top-level code runs **only if and when** its `import()` call site is actually reached at runtime — the real "run once, on first actual import" semantics real ES modules have, which [TDD-00055](TDD-00055.md)'s eager-merge design can never provide no matter how it's extended. Worth stating plainly since it inverts the usual "V1 is simpler but less correct" framing: here, V2 is *more* faithful to real JS semantics, not just faster/lazier.

### New runtime shim

A small new C shim (this project already has direct precedent for this shape of thing — `codegen/llvm/gcsrc/gcshim.c`) wrapping `dlopen`/`dlsym`/`dlclose`/`dlerror` (`dlfcn.h`), called from generated IR the same `ensure*()`-declared-once pattern every other C runtime call already uses. Locating an island's `.so` at runtime needs to be relative to the running executable's own location (a fixed absolute path baked in at compile time breaks the moment the binary is moved) — `/proc/self/exe` on Linux, `_NSGetExecutablePath` on Mac; **both need direct, hands-on verification on the actual dev machines before being trusted**, not assumed from documentation, matching this project's own standing rule about platform-touching claims.

### `--static` incompatibility

Exactly the resolution decided in Context: `main.go`'s flag validation rejects `--static` outright when the program actually uses `-dynamic-import=lazy` with at least one real dynamic-import call site present — a clean, explicit compile-time error naming both flags and explaining why (a statically-linked binary generally cannot `dlopen()` anything at runtime), not a silent fallback to eager mode and not a mysterious runtime failure. Same posture `-mm=manual|gc`'s mutual exclusivity already uses.

### GC coordination — open, unverified

If `-mm=gc` (Boehm GC) is combined with `-dynamic-import=lazy`, the collector needs to see roots living inside a `dlopen()`'d island's own data/bss segments and needs its allocator to be safely callable from code running there. Boehm GC has support for this on ELF/Linux in many configurations, but per this project's own standing rule, that claim needs direct verification on both dev machines before shipping, not an assumption carried over from general knowledge of the library — flagged here explicitly so it isn't quietly assumed away during implementation.

## Open questions

- Output artifact naming/location convention for islands (a sibling `<binary>.d/` directory? flat alongside the binary? something else) — undecided, affects both the runtime path-resolution logic and Docker/deployment guidance.
- Whether a *bounded* runtime-variable specifier is worth designing later, once this lands — e.g. mirroring how real bundlers handle `import(\`./locales/${lang}.js\`)`: enumerate every file matching a template literal's static prefix/suffix at compile time (each becoming its own island), and dispatch by runtime string match among that compile-time-known finite set at the call site. A real, legitimate extension, but a distinct piece of design work from this TDD's core (real laziness via `.so` loading) — not scoped here, noted for a possible follow-on.
- Whether V1 (eager, [TDD-00055](TDD-00055.md)) stays worth maintaining once this lands, given they'd then do overlapping-looking things through different flags — current lean, per Design: yes, keep both, since they serve genuinely different constraints (`--static`-compatible single-binary vs. real laziness), but worth re-confirming once both actually exist side by side rather than deciding permanently now.
- Exact hashing scheme for stable export symbols (content of the hash input, collision handling if two islands' hashes ever coincide) — needs a real answer before implementation, not left to "pick something reasonable" mid-build.
