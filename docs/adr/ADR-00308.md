# ADR-00308: `SharedArrayBuffer` + `Atomics` — shared memory across worker threads

- **Relations**: Implements [TDD-00099](../tdd/TDD-00099.md); extends [ADR-00305](ADR-00305.md) (Worker), [ADR-00078](ADR-00078.md) (ArrayBuffer)
- **Date**: 2026-08-23

## Context

The Worker delivery ([TDD-00098](../tdd/TDD-00098.md)) shipped message-passing only and explicitly deferred `SharedArrayBuffer`/`Atomics` as "not designed". With real pthreads in place, deep-copy envelopes were the only concurrency primitive — no shared state, no cross-thread blocking/wakeup. Designed in [TDD-00099](../tdd/TDD-00099.md) and implemented here.

## Investigation

- `ArrayBuffer`'s hidden `{ i64 byteLength, ptr data }` header (`emit_arraybuffer.go`) already gives TypedArray views aliasing semantics over one buffer; threads share an address space, so the identical representation *is* a shared buffer once the type system stops deep-copying it at the worker boundary. No new memory layout needed.
- LLVM's `atomicrmw`/`cmpxchg`/`load atomic`/`store atomic` with `seq_cst` map one-to-one onto the `Atomics` RMW surface — verified by a hand-written `.ll` prototype compiled with the exact clang invocation (returns old value, correct cmpxchg-failure behavior).
- `Atomics.wait`/`notify` need a futex; macOS has no public futex syscall. Prototyped the portable substitute: process-wide pthread mutex + condvar over an address-keyed waiter list. Critical prototype finding: **zero-initialized static storage is not a valid mutex/cond on Darwin** — `PTHREAD_MUTEX_INITIALIZER` carries a nonzero signature and locking a zeroed `pthread_mutex_t` returns `EINVAL(22)` (repro in scratch, Mac). So the runtime must call `pthread_mutex_init`/`pthread_cond_init`, guarded by a `cmpxchg` init gate.

## Decision

- **`SharedArrayBuffer`**: `new SharedArrayBuffer(n)` parses through the existing ArrayBuffer body parser (`Shared` flag on the AST node); the result type sets `IsSharedArrayBuffer` *alongside* `IsArrayBuffer`, so `.byteLength`, all TypedArray view constructions, and `DataView` work through the existing `IsArrayBuffer` paths with zero new code. The only behavioral differences: structured clone passes the header pointer through unchanged (share-not-copy — the spec's own `postMessage` semantics; a plain `ArrayBuffer` stays rejected), and under `-mm=gc` the header+data are `GC_malloc_uncollectable` (the only live reference may sit on another thread's stack or in a pipe envelope, invisible to this thread's Boehm scan).
- **`Atomics` plain ops**: `Atomics` dispatches like `Math` (namespace member call, no import). `load`/`store`/`add`/`sub`/`and`/`or`/`xor`/`exchange`/`compareExchange` lower directly to the LLVM atomic instructions, `seq_cst`, on any **integer** TypedArray (`Int8`…`Uint32`); float TypedArrays are a compile-time rejection (the spec's `ValidateIntegerTypedArray`). Spec return values throughout (old value for RMW, stored value for `store`).
- **`Atomics.wait(i32ta, idx, expected, timeoutMs?)` / `notify(i32ta, idx, count?)`**: runtime waiter list `{ addr, notified, next }` (nodes stack-allocated in the waiter's frame) under one process-wide mutex/cond pair. The expected-value check happens *under the mutex* (closes the check-then-sleep race against a concurrent store+notify); `notify` marks up to `count` matching nodes and broadcasts — a spurious cond wakeup can never fake an `"ok"` because only a matching notify sets a node's flag. Timeout via `pthread_cond_timedwait` against `clock_gettime(CLOCK_REALTIME)`; `ETIMEDOUT` is emitted per-OS (Darwin 60, Linux 110), and a timeout that raced a notify re-checks the flag under the mutex before reporting `"timed-out"`. `wait` requires an `Int32Array` (spec) and is allowed on the main thread (Node's posture, not the browser's throw).

## Implementation notes

- `ast/nodes.go` (`Shared` flag), `parser/parser_literals.go` (`SharedArrayBuffer` case), `codegen/llvm/types.go` (`IsSharedArrayBuffer`, `SharedArrayBufferType`, annotation name), `emit_arraybuffer.go` (shared construction + gc-mode allocation), `emit_structured_clone.go` (share-not-copy carve-out), `emit_worker.go` (payload error message), `emit_atomics.go` (new — dispatch + atomic-instruction lowering), `runtime_atomics.go` (new — init gate, waiter list, wait/notify), `emit_call.go`/`emit_exprs_types.go` (dispatch + inference), plus `ensureGCUncollectable`/`ensurePthreadMutexDecls`/`ensureClockGettime` decl dedup shared with the worker/date runtimes.
- `Atomics.wait`'s result is the spec's string (`"ok"`/`"not-equal"`/`"timed-out"`), materialized via two selects over interned constants.

## Side effects discovered

- The free-variable scanner missed `new TypedArray/ArrayBuffer/DataView(...)` constructor arguments inside closures — surfaced immediately when a worker handler built an `Int32Array` view over a captured SAB. Fixed separately: [ADR-00310](ADR-00310.md).
- Arrays (including TypedArrays) still can't be captured by closures, so cross-thread code re-views the SAB inside each handler — pre-existing limitation, unchanged.

## Verification

darwin/arm64 (Mac): `tests/shared_memory_test.go` — local aliasing views, SAB crossing a worker boundary with cross-thread visibility (`100+23=123` read back on the parent), full single-thread op matrix including `"not-equal"` and a real 50ms `"timed-out"`, and a genuine cross-thread block: worker parks in `Atomics.wait`, main stores+notifies 100ms later, worker wakes with `"ok"` and reads the new value. Compile-time rejections (float TA, non-Int32 wait) asserted. Example `examples/workers/shared_counter.ts` (two threads × 1000 `Atomics.add` → exactly 2000). Full `go test ./...` green on the Mac; the same suites also pass on Linux (glibc/arm64, Docker `golang:latest` + clang 19).
