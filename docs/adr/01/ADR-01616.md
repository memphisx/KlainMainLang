# ADR-01616: `-crypto=cng`: node:crypto over Windows CNG

- **Relations**: Implements TDD-00177 (Stage 5), Extends ADR-00637
- **Date**: 2026-10-13

## Context

TDD-00177's Stage 5 listed one item left: an optional `-crypto=cng` backend,
a third implementation of node:crypto's native ABI (the `__kml_native_crypto_*`
functions `lib/node/crypto.ts` and crypto.subtle are written over) on the
Windows CNG primitives in `bcrypt.dll`, next to `crypto_openssl.c` (the
default, the reference) and `crypto_commoncrypto.c` (macOS). With it a
Windows program that uses crypto ships with no OpenSSL dependency at all —
`bcrypt.dll` is part of every Windows install.

## Investigation

- The ABI is the 36 exported functions of `crypto_openssl.c`
  (`__kml_native_crypto_*`, plus `__kml_crypto_gen_rsa`/`__kml_crypto_gen_ec`,
  which `crypto_commoncrypto.c` also defines). The OpenSSL-only helpers
  (`__kml_crypto_b64url_*`, `__kml_crypto_jwk_import_*`) are internal to that
  file, not called from IR.
- CNG speaks its own key blobs (`BCRYPT_RSA*_BLOB`, `BCRYPT_ECC*_BLOB`), not
  DER — the same situation as SecKey on macOS, so the CommonCrypto backend's
  mini-DER layer is the template.
- What CNG lacks, probed on this machine with small standalone programs:
  - SHA-224 (no `BCRYPT_SHA224_ALGORITHM`).
  - AES-CTR (no chaining mode). AES-GCM exists
    (`BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO`) but takes only a 12-byte nonce,
    and chained calls must pass whole blocks; Node accepts any IV length and
    streams `update()` calls of any size.
  - Ed25519 (CNG has Curve25519 for ECDH only).
  - Point compression: CNG imports and exports only uncompressed points.
  - Explicit RSA-PSS salt recovery on verify: `BCryptVerifySignature` needs
    the exact salt length, while libcrypto's default auto-detects it.
- What CNG does that this needed, confirmed by experiment: an
  `ECCPRIVATE_BLOB` imported with X and Y zeroed has its public point derived
  from d (re-export matched the generated key byte for byte); raw RSA through
  `BCRYPT_PAD_NONE` on `BCryptEncrypt`/`BCryptDecrypt` round-trips; an HMAC
  algorithm handle and `BCryptDeriveKeyPBKDF2` accept an empty key/password
  and match Python's `hmac`/`hashlib.pbkdf2_hmac`.

## Decision

`codegen/llvm/cryptosrc/crypto_cng.c` implements the whole ABI over CNG:

- **Digests**: CNG hash objects (MD5, SHA-1/256/384/512; `hash.copy()` is
  `BCryptDuplicateHash`); SHA-224 is a software SHA-256 core with its IV.
- **HMAC** is RFC 2104 over those digests, inner and outer contexts keyed up
  front (so SHA-224 works and a copy is two duplicates). **PBKDF2** is
  `BCryptDeriveKeyPBKDF2` (the in-shim HMAC for SHA-224); **HKDF** (RFC 5869)
  and **scrypt** (RFC 7914) are composed here, as in the CommonCrypto backend.
  **Random** is `BCryptGenRandom` with the system-preferred RNG.
- **AES** CBC/ECB are CNG keys (the CBC chaining value is the IV buffer CNG
  updates in place); padding and block buffering are done here so
  `update()` output sizes match EVP's. CTR (128-bit big-endian counter) and
  GCM (CTR plus GHASH, any IV length, streamed) are built on CNG's AES-ECB —
  the CommonCrypto backend's composition. CNG's own GCM was rejected for the
  12-byte-nonce and whole-block restrictions above.
- **Keys** travel as components (RSA n/e/d/p/q/dp/dq/qi, EC X/Y/d, the
  Curve25519 32-byte value). A mini-DER layer reads and writes PKCS#1,
  PKCS#8, SPKI, SEC1, encrypted PKCS#8 (PBES2) and legacy `DEK-Info` PEM;
  a key goes into a CNG handle (`RSAPUBLIC`/`RSAPRIVATE`, `ECCPUBLIC`/
  `ECCPRIVATE` blobs) only for the operation at hand, and the EC import is
  also the on-curve validation.
- **RSA**: keygen is `BCryptGenerateKeyPair` and exports the full private
  blob. Sign, verify, `publicEncrypt`/`privateDecrypt`/`privateEncrypt`/
  `publicDecrypt` use CNG's raw RSA, with the paddings done here (RFC 8017
  EMSA-PKCS1-v1_5, EMSA-PSS with libcrypto's salt-length specials and
  auto-recovery on verify, RSAES-OAEP with any digest and label,
  RSAES-PKCS1-v1_5, no padding) — so every libcrypto option behaves as there.
- **EC P-256/P-384/P-521**: ECDSA is `BCryptSignHash`/`BCryptVerifySignature`,
  whose r||s is converted to and from DER (kept as is for
  `dsaEncoding: 'ieee-p1363'`). ECDH is `BCryptSecretAgreement` +
  `BCryptDeriveKey(BCRYPT_KDF_RAW_SECRET)`, whose little-endian result is
  reversed. Point decompression (`y = rhs^((p+1)/4)`, all three primes are
  3 mod 4) and the `0 < d < n` check use a small 544-bit bit-serial
  modular arithmetic; the curve constants were checked against
  `openssl ecparam -param_enc explicit`.
- **Ed25519/X25519**: the CommonCrypto backend's compact Curve25519 code,
  with SHA-512 from CNG.
- **KeyObject** (`key_parse`, `key_export`, `key_info`, `key_jwk`,
  `key_from_jwk`) works over the same components — so, unlike
  `-crypto=commoncrypto`, crypto.subtle's asymmetric algorithms run on this
  backend.

Error strings are libcrypto's, kept per thread, as in the CommonCrypto
backend.

Wiring: `codegen/llvm/crypto.go` adds `cng` to `CryptoBackends`, embeds the
source and links `-lbcrypt`; `main.go` accepts `-crypto=cng` only when
compiling on Windows, and allows it with `--static` (on Windows `--static`
links every non-system library in, and `bcrypt.dll` is a system DLL — it
was already in the static link's system-library list); `embedded_c.go`
refuses `tls` under `cng` as under `commoncrypto` (the `tls` module is
libssl).

## Implementation notes

- `codegen/llvm/cryptosrc/crypto_cng.c` (new), `codegen/llvm/crypto.go`,
  `codegen/llvm/embedded_c.go`, `main.go`, `README.md` (the `-crypto` flag),
  `tests/webcrypto_test.go`, `tests/compiler_test.go`,
  `tests/crypto_port_test.go`.
- CNG algorithm providers are opened once (`InitOnceExecuteOnce`) and shared
  by every thread; the pool's KDF and keygen jobs use them concurrently,
  which CNG supports.
- RSA private operations need p and q (`BCRYPT_RSAPRIVATE_BLOB`); a JWK
  private key must carry all eight members.

## Side effects discovered

What this backend does not do, each failing the way the CommonCrypto
backend reports its gaps (an unknown name is `-1`/"unknown digest", an
unavailable key type an empty keygen result):

- SHAKE digests (no XOF in CNG), as on CommonCrypto.
- RSA keygen with a public exponent other than 65537 (CNG generates F4 only),
  RSA-PSS-restricted keys, DSA, DH, Ed448/X448, and EC curves other than the
  three NIST prime curves.
- `keyObject.export()` with a `cipher` (writing an encrypted PEM/PKCS#8) —
  reading such keys works.
- The libcrypto error strings for a few RSA decoding failures are not
  reproduced (the operation still fails); OpenSSL 3.2's implicit rejection
  for PKCS#1 v1.5 decryption is not emulated — a bad padding fails.

## Verification

Verified on Windows 11 (x86-64, MSYS2 UCRT64 clang):

- Standalone harnesses against the object file: SHA-224 against Python's
  `hashlib`; ECDH key/point/secret round trips (compressed and uncompressed)
  on all three curves; generated PKCS#8 keys accepted by `openssl pkey
  -check` and byte-identical to OpenSSL's re-encoding.
- `go test ./tests -run 'TestE2ECryptoPortCNG|TestE2ESubtleDigestVectors|TestE2ESubtleHmacJwk|TestE2ESubtleDerive|TestE2ESubtleAsymmetric'`
  — all pass with the new `cng` subtests. New tests, each comparing
  against Node: `TestE2ECryptoPortCNG` (the commoncrypto parity program),
  `TestE2ECryptoPortCNGEncryptedKey` (PBES2-encrypted key, missing and
  wrong passphrases), `TestE2ECryptoPortCNGAsymmetric` (PKCS#1 v1.5 and
  SHA-224 RSA signatures byte for byte, PSS with default and explicit salt,
  OAEP with label, private encrypt / public decrypt, PKCS#1/SPKI/SEC1/JWK
  exports, ECDSA DER and P1363, ECDH public keys, compressed points,
  `convertKey`, shared secrets, an invalid point, `diffieHellman`).
- The full targeted crypto selection
  (`-run 'WebCrypto|Crypto|Subtle'`) — see the run recorded with this
  change.
