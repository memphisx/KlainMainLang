# TDD-00200: Statically-typed heterogeneous / union-element arrays

- **Status**: Partially Implemented
- **Date**: 2026-09-10

## Relation to existing work

This is not new ground — it is the **array half of Bucket B** (boxed-`any`
representation completeness) that [TDD-00076](TDD-00076.md) deferred when it
shipped the *operator* half, and the concrete realization of two items parked as
"deferred" elsewhere:

- [TDD-00062](TDD-00062.md) (bare `any` param/return, Implemented) explicitly
  scopes **out** `any[]` / `{ x: any }` and a boxed array's element access — the
  representation hole this closes for the array case.
- [TDD-00043](TDD-00043.md) (general unions, Implemented) is V1 scalar-members-
  only; "object/array members … deliberately deferred" — a `(A | B)[]` union
  *inside* an array is exactly that deferral.
- It inhabits the [TDD-00075](TDD-00075.md) `-compat=strict|js` axis, as the
  sibling of [TDD-00076](TDD-00076.md): 00076 is `any` *operators* under
  `-compat=js`, this is `any`/union *array storage* under `-compat=js`. Both
  reuse the single-word NaN box ([TDD-00156](TDD-00156.md)) and the D1 dynamic
  walker ([TDD-00155](TDD-00155.md)).

## Context

This compiler's arrays are homogeneous — a single static element type, one
storage width, one uniform buffer. A statically-typed heterogeneous array has no
element type to store against, so two shapes are rejected today:

- Explicit union element type — `const a: (number | string)[] = [1, "two"]` —
  fails `any/unknown is not yet supported as an array element or object field
  type` (the union resolves its element to a dynamic type, caught by
  `validateCompositeType`/`containsDynamicElement`).
- Inferred heterogeneous literal — `const a = [1, "two", true]` — fails `array
  elements must share one type … a heterogeneous array is not supported`
  (`inferArrayType`).

This blocks `JSON.stringify(mixedTypeArray)` (docs/status JSON row, deliberately
`missing`), and the same root gap blocks `typeof`, spread, and `.map`/`.filter`
over a mixed array. The two faithful *workarounds* already exist and stringify
correctly: a fixed-length **tuple** (`[number, string, boolean]`, TDD-00066), and
a wholly-`any` **dynamic array** (`const a: any = [1, "two", null]`, ADR-00639's
dynamic walker). The missing case is only a *statically-typed* variable-length
heterogeneous array.

The observable-semantics target (real JS) is a plain array whose elements happen
to differ in type — `JSON.stringify([1, "two", true])` → `[1,"two",true]`,
`arr.map(String)`, `typeof arr[0]`, etc. Native compilation makes the *uniform*
representation impossible, but a **boxed-element** representation is possible;
this is exactly the `strict` ↔ `-compat=js` divergence axis.

## Design

A union-element / inferred-heterogeneous array lowers to a **NaN-boxed-element
array** — element storage is one `i64` box per slot (the same encoding
`emitBoxValue`/`__kml_any_eq`/the dynamic walker already use), rather than a
native scalar buffer. Reads unbox to `any`; writes box. This is effectively a
type-checked `any[]` whose *declared* element type is the union (so element
access is typed as the union, not bare `any`), backed by the boxed buffer.

- **`-compat=js`: accept and lower.** A `(A | B | …)[]` annotation, and an
  inferred heterogeneous literal, both produce a boxed-element array. Every
  consumer that already understands a boxed/`any` value comes along for free:
  `JSON.stringify` (dynamic walker), `typeof`, template/`String()` coercion,
  `.map`/`.filter`/`.forEach` (box in, box out), spread, indexing. The element
  type reported by `inferExprType` is the union (or `any` for the inferred
  literal), so downstream dispatch stays typed where it can be.
- **strict: reject, but recognizably.** Keep the clean compile-time rejection —
  a boxed array is a real representation change, not zero-cost, so strict stays
  uniform-only. Replace today's two opaque errors with one **actionable**
  message naming the escape hatches: express a fixed-length mix as a **tuple**
  (`[number, string, boolean]`), or opt into the boxed representation with
  **`-compat=js`** (or an explicit `any[]`). The message must be recognizable
  (stable phrasing, points at both alternatives) so it reads as a deliberate
  divergence, not a bug — consistent with the no-doc-refs-in-user-output rule
  (inline the guidance, no ADR/TDD paths).

Recommended direction: reuse the existing box machinery end-to-end rather than a
new tagged-union storage — the boxed-element array *is* an `any[]` with a
narrower declared element type, so most of the work is (a) letting
`validateCompositeType` accept a union/`any` element under `-compat=js` by
routing it to the boxed shape, (b) an `inferArrayType` path that yields a boxed
array for a heterogeneous literal under `-compat=js`, and (c) confirming each
consumer already boxes/unboxes (most do via the dynamic walker).

## Open questions

- Does a declared `any[]` already allocate a boxed-element buffer, or is only a
  wholly-`any` *value* (a dynamic bag) supported? If the former exists, the union
  case is mostly a type-checking/relabelling job; if not, the boxed-element array
  storage is the real new subsystem.
- Element type reported for the inferred literal — bare `any`, or the synthesized
  union of the observed element types (better downstream typing, more inference
  work)? Under `-compat=js` a bare `any` is the cheaper start.
- Nested case: `(number | string)[][]` and a boxed element that is itself an
  array/object — the box already carries arrays/objects (ADR-00478), so this
  should fall out, but needs a test.
- Does strict keep rejecting an explicit `any[]` too, or is `any[]` the one
  strict-legal spelling that opts into boxing (distinct from a *union* element)?
