# ADR-01104: clang timeouts are not invalid IR; the equivalence corpus covers the strict lane

- **Relations**: `Extends ADR-01099`
- **Date**: 2026-09-23

## Context

The Test262 run after the P1.6 step ([ADR-01103](ADR-01103.md)) reported 76
strict-lane files in the "clang (invalid IR — codegen bug)" phase, against 1 in
the previous report, and 57 in the js lane against 5. The IR-equivalence
corpus (`tools/irdiff`) showed no IR change in any js-lane Test262 file across
the same steps, and it never compiled the strict lane at all, so the numbers
could not be told apart from a strict-lane codegen regression.

The run was also much slower than usual: about 40 minutes per lane on the M4,
where both lanes used to take about 26 minutes together.

## Investigation

- `tools/conformance/main.go`'s `phaseOf` mapped `CLANG_TIMEOUT` and
  `CLANG_ERROR` to the same phase, and clang ran under the same 5-second
  budget as the compiled test binary (`-timeout`).
- An endpoint-security agent on the machine held about two cores and inspects
  every spawned process. Each Test262 file spawns clang, links a binary and
  runs it.
- The compiler itself did not slow down: compile-only CPU time over the same
  120 Test262 files is 1.6–2.1 s for the session-start, P1.4 and P1.6 builds
  alike, with no consistent order across rounds.
- Re-running the strict lane with a 30-second clang budget and `-faillist`
  gave 7,073 passes and exactly one clang failure, the pre-existing
  `constant expression type mismatch` at `emit_nullable_scalar.go:427` (via
  `emit_tuple.go:39`). The other 75 were timeouts on valid IR.

## Decision

- clang gets its own budget, `-clang-timeout`, 30 seconds by default. clang
  runs slowly but never hangs on a module, and concurrency stays capped by
  `-workers`, so a longer budget does not raise peak memory. `-timeout` stays
  at 5 seconds and now bounds only the run of the compiled test.
- `CLANG_TIMEOUT` has its own phase, "clang (timeout — slow compile, not
  invalid IR)", with the short label `clang-timeout` in the per-reason table
  and in `conformance-summary.json`'s `byPhase`. The invalid-IR phase counts
  only clang rejections.
- `tools/irdiff` compiles every `.js` file in both emitter lanes: `-compat=js`
  under its own path and `-compat=strict` as `<path>#strict`.

## Implementation notes

- `tools/conformance/main.go`: the `-clang-timeout` flag sets the package-level
  `clangTimeout`, which both the Test262 path (`runOne`) and the Node-suite
  path (`tools/conformance/node.go`) use for their clang context.
- `tools/irdiff/irdiff.py` builds a job list of (file, lane). `cmp.py` skips
  keys missing from the baseline, so the first strict-lane comparison needs a
  baseline recorded with the new script.

## Side effects discovered

- The two lanes' reports from the P1.6 run (strict 7,019, js 7,620) undercount
  by the timed-out files. They are replaced by the run recorded below.

## Verification

All on macOS arm64 (M4):

- `go vet ./tools/conformance` and `go test ./tools/conformance` pass.
- Strict lane with a 30-second clang budget: 7,073 / 53,578, one clang
  failure (pre-existing).
- Full `make conformance` (both lanes, the P1.6 front end) with the default
  30-second clang budget: strict 7,073 / 53,578 (in scope 6,910 / 42,942),
  js 7,658 / 53,578 (in scope 7,460 / 42,942). Invalid IR: strict 1 (the
  pre-existing `emit_nullable_scalar.go` site), js 5. No clang timeout and no
  run timeout in either lane. The previous reports, from a run before P1.6,
  had strict 6,986 and js 7,550.
