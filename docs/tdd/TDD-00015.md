# TDD-00015: `JSON.parse` into nested object fields

- **Status**: Superseded
- **Date**: 2026-07-28
- **Notes**: Superseded by [TDD-00077](TDD-00077.md), which reverses this doc's additive span-finding design for a full dynamic-tree rewrite once the goal widened to the whole JSON surface (`SyntaxError` validation + `any`-typed parse, neither reachable by span-finding). The array-typed-field clean-rejection drive-by this TDD found still shipped independently as [ADR-00189](../adr/ADR-00189.md)

## Context

`JSON.parse(s)` into a flat, one-level object with primitive fields works ([ADR-00007](../adr/ADR-00007.md)). A field that is itself an object is rejected with a clean compile-time error rather than attempting broken codegen — `emitJSONParseObject` (`codegen/llvm/emit_call.go:1252-1256`) walks `targetTy.Fields` upfront and errors on the first `f.Ty.IsObject`. `STATUS.md` tracks this as the one remaining ❌ in the JSON category. This TDD scopes what a real fix looks like, since ADR-00007 explicitly deferred it as "meaningfully more work than the flat case" without designing that work.

**Why nested fields can't just reuse the flat-field lookup.** The flat-field parser (`@__kml_json_find_value`, `runtime.go`) finds a field's value with a plain `strstr(json, "\"name\":")` — correct only because a flat object has each key exactly once in the entire text. Once a field is itself an object, a nested sub-object can contain a key with the same name as a field elsewhere in the outer object (or in a later sibling), and a bare `strstr` has no notion of "search only inside this sub-object's `{...}` span." Using it unmodified risks silently matching the wrong occurrence — exactly the class of bug ADR-00007 was written to avoid reintroducing (recall its own motivating bug was `JSON.parse` reading garbage silently rather than failing clearly).

**A second, related gap found while scoping this**: the same upfront-rejection loop only checks `f.Ty.IsObject`, not `f.Ty.IsArray`. An array-typed interface field is not rejected and falls through to `emitJSONParseFieldValue`'s default case (`atoll`), which assumes an `i64`-shaped scalar. Confirmed directly — this is not hypothetical:

```ts
interface Bag { tags: string[]; }
const b: Bag = JSON.parse('{"tags":["a","b"]}');
```

compiles to invalid LLVM IR (`clang` rejects it: `'%t5' defined with type 'i64' but expected 'ptr'` — the `phi` merging the found/missing branches disagrees with itself because `atoll`'s `i64` result is stored into a slot typed `ptr` for the array's `{ptr,i64}` aggregate). This is a **compile-time IR-generation crash today, not silent corruption** (the miscompiled program never runs — `clang` catches the type mismatch), but it means an array-typed field is just as unsupported as a nested-object field, without the same clean rejection ADR-00007 gave nested objects. Both gaps share one root cause: neither has a bounded sub-span to parse independently, and this TDD's design (bracket/brace-matching to isolate a sub-value's text extent) covers both.

**Third connection worth naming**: `Response.json()` (`codegen/llvm/emit_fetch.go`, see `emitResponseJSON`) is a declaration-context analogue of `JSON.parse` that reuses `emitJSONParseObject` directly for its typed-target path. Whatever ships here automatically extends to `response.json()` deserialization with no separate work — same as ADR-00007's flat-object support already did.

## Design

The core problem: given JSON text and a target field whose type is `IsObject` (or `IsArray`), isolate that field's value's exact `{...}` or `[...]` substring before parsing it, rather than treating the surrounding text as flat.

### Approach: recursive descent via a new `@__kml_json_span` helper

Replace the "find pattern, hand the rest to a scalar parser that stops on its own" shape with an explicit **span-finding** step for non-scalar fields:

1. New runtime helper `@__kml_json_span(ptr valueStart) -> {ptr start, i64 len}` (or two out-params): given a pointer already positioned at the start of a JSON value (post `@__kml_json_find_value`, same as today), determine the value's exact extent by scanning forward with a **depth counter** — increment on `{`/`[`, decrement on `}`/`]`, skip over string literals *without* counting brackets inside them (a quoted `"}"` must not decrement depth), until depth returns to 0. This is a single linear scan, no allocation — mirrors the existing `@__kml_json_find_value`'s "return a pointer into the original text, let the caller reparse" style rather than copying substrings around.
2. **Object-typed field**: once the span is known, recurse — call `emitJSONParseObject` again with the *sub-slice* as the new `jsonVal` and the field's own `Ty.Fields` as the new target. Since `@__kml_json_find_value`'s `strstr` only needs to operate within the sub-span (not the whole original text), pass the span's `(start, len)` down so the recursive call's own field lookups are naturally bounded to it — this is what actually prevents the sibling-key false-match ADR-00007 flagged. In practice this likely means giving `@__kml_json_find_value` an optional end-bound parameter (search stops at `start+len`, or a bounded `strstr`-equivalent), since libc's `strstr` has no length-bounded variant (`strnstr` is BSD-only, not portably available) — a small hand-rolled bounded search, consistent with this codebase's existing preference for small custom runtime helpers over relying on non-portable libc extensions.
3. **Array-typed field**: same span-finding step, then reuse whatever array-parsing path exists (there currently isn't one — `JSON.parse` into a bare array-typed variable isn't itself implemented per `STATUS.md`; parsing a JSON array into `T[]` is out of scope for *this* TDD and should stay a clean rejection, now correctly triggered by adding `f.Ty.IsArray` to the upfront-rejection check alongside `f.Ty.IsObject`.) Fixing the array case for real is really "implement `JSON.parse` → array," a separate, larger feature — this TDD's actionable scope is: (a) design nested-*object* parsing fully, (b) as a same-session drive-by fix, make the array case fail cleanly like the object case already does, since that's a one-line change to an existing check, not new design work.
4. **Recursion depth**: no explicit limit needed beyond what the type system already bounds — `targetTy.Fields` is a compile-time-finite tree (an interface can't recursively reference itself as a field type without infinite struct size, which `StructSize()` would already choke on independently), so nesting depth is bounded by however deep real interface declarations go. No runtime recursion-guard needed; this is compile-time codegen recursion (Go function calls during `emitJSONParseObject`), not emitted-IR recursion — bounded by the type declaration, not by untrusted input.

### Rejected alternative: full JSON parse to an in-memory tree first

Parse the whole JSON text into a generic tree (tagged union of object/array/string/number/bool/null, similar to how `any`/`unknown` is already represented — see `emit_dynamic.go`), then walk the tree against the target type. This is the architecturally "proper" way a real JSON library works, and would also make `JSON.parse` → array and `JSON.stringify` of dynamic/mixed shapes easier later. Rejected as the *first* step here because it's a much bigger lift than the problem in front of us — it means building a real parser (tokenizer + recursive-descent parse into heap tree nodes) where today there's a set of narrow field-value extractors, and duplicates work the `any`/`unknown` boxed-value machinery may eventually want to own anyway. The span-finding approach above is additive to the existing `@__kml_json_find_value`/`emitJSONParseFieldValue` shape and ships nested objects without a rewrite; if `JSON.parse` → arbitrary/dynamic shape (not just a statically-typed target) is ever wanted, *that* is when the tree-based rewrite becomes the right call, not now.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Flat-object `JSON.parse` (`emitJSONParseObject`, `emitJSONParseFieldValue`) | ✅ done ([ADR-00007](../adr/ADR-00007.md)) | The base case this design recurses into |
| `@__kml_json_find_value` (unbounded `strstr`-based field lookup) | ✅ done, needs a bounded variant | New optional end-bound parameter needed so recursive calls stay confined to their sub-span |
| Escaped-string-aware scanning (skip brackets inside quoted strings) | ✅ precedent exists | `@__kml_json_str_str`/`@__kml_json_parse_field_str`'s existing escape-decode loops are the direct precedent for "don't get confused by `\"` while scanning" |
| `Response.json()` reuse of `emitJSONParseObject` | ✅ already wired | No separate work needed — inherits whatever ships here automatically |
| `JSON.parse` → bare array (`T[]`) | ❌ not implemented at all | Explicitly out of scope for this TDD; array-typed *fields* should get the same clean-rejection treatment nested objects already have until this lands separately |
| Interface fields recursively referencing an object type | ✅ effectively bounded already | `StructSize()`/type declarations can't express infinite recursion, so no new depth-guard is needed |

## Open questions

- Should the bounded-search variant of `@__kml_json_find_value` be a new helper (`@__kml_json_find_value_bounded`) or should the existing one grow an optional length parameter (0/-1 meaning "unbounded", used by the existing top-level flat-object call sites)? Leaning toward a second helper to avoid changing the signature every existing call site depends on, but not decided.
- Doubly-nested objects (a field whose type has its own object-typed field) fall out naturally from the recursive design above, but haven't been traced through by hand against a concrete example — worth a manual dry run before implementation, not just trusting the recursion argument.
- Whether the array-typed-field clean-rejection fix (Design, point 3) should land as part of *this* TDD's implementation pass or as its own tiny separate ADR before the nested-object work starts, since it's an independent, much smaller fix once noticed. Leaning toward landing it first/separately — it's a one-line addition to an existing check, not blocked on anything above.
