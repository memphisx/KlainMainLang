# ADR-00795: fs.constants (access modes + copyFile flags)

- **Relations**: `Extends ADR-00788`
- **Date**: 2026-09-08

## Context

`fs.accessSync(path, mode)` and `fs.copyFileSync(src, dest, mode)` took their
mode argument as a raw number — a program had to write `fs.accessSync(p, 4)` or
`fs.copyFileSync(a, b, 1)` and know the magic values, because `fs.constants` (the
namespace Node exposes for exactly this) did not exist. The numbers were already
accepted and correctly interpreted; only the named surface was missing.

## Investigation

- `http2.constants` (TDD-00139 Stage 4, `emit_http2_settings.go`) is a working
  precedent: a compile-time namespace where a member read resolves to a literal
  with no runtime object, and a binding carries an `IsH2Constants` type flag so
  reads through an alias resolve identically. `fs.constants` is the same shape.
- The constants with a real consumer here are the POSIX access modes
  (`accessSync`) and libuv's copyFile flags (`copyFileSync`, which already masks
  `COPYFILE_EXCL`). All are platform-invariant: the access bits are POSIX-standard
  (`F_OK`=0/`X_OK`=1/`W_OK`=2/`R_OK`=4, identical on Linux and macOS) and the
  `COPYFILE_*` values are libuv's own (`1`/`2`/`4`), not the host OS's — so one
  compile-time table is correct on every target, and the values match Node's
  `fs.constants` byte-for-byte.
- Named-import access (`import { constants } from 'fs'`) requires the resolver's
  fs export allowlist to carry `constants`. While there, `accessSync`/`chmodSync`/
  `truncateSync`/`symlinkSync` — real Node exports with existing codegen dispatch
  — were absent from that allowlist, usable only via the `fs.` namespace form; a
  latent bug fixed in passing.

## Decision

Add `fs.constants` as a compile-time numeric namespace, modelled on
`http2.constants`:

- `emit_fs_constants.go`: `fsConstants` table (`F_OK`/`R_OK`/`W_OK`/`X_OK`,
  `COPYFILE_EXCL`/`COPYFILE_FICLONE`/`COPYFILE_FICLONE_FORCE`), plus
  `isFsConstantsExpr`/`emitFsConstant`. Members emit as `number` (double), as
  Node types them; an unknown member is a clean compile error naming the covered
  set.
- `emit_exprs_member.go` / `emit_exprs_types.go`: a `fs.constants.NAME` read (or
  through an alias / named import carrying the new `IsFsConstants` flag) resolves
  to the literal; `fs.constants` itself binds as the flagged namespace value.
- `resolver/virtual_modules.go`: add `constants` (and the four missing
  dispatchable sync exports) to the fs named-export allowlist.

**Deliberately omitted:** the `O_*` open flags. No API here consumes them
(`writeFileSync`'s `flag` is a string like `'a'`/`'w'`), and their numeric values
are genuinely host-specific — a compile-time literal can't honor that faithfully.
Added if and when a flags-taking `open` API arrives.

## Consequences

- `fs.accessSync(p, fs.constants.R_OK)` and
  `fs.copyFileSync(a, b, fs.constants.COPYFILE_EXCL)` read as Node code; the raw
  numbers still work unchanged.
- `accessSync`/`chmodSync`/`truncateSync`/`symlinkSync` now import by name.

## Verification

macOS (Apple Silicon M4 Pro). `TestE2EFsConstantsValues` (all seven values match
Node), `TestE2EFsConstantsNamedImportAndConsumers` (named import + `accessSync`
R_OK + `copyFileSync` COPYFILE_EXCL overwrite-refusal), and
`TestE2EFsConstantsUnknownMemberRejected` (clean compile error) pass; the fs
suite stays green; `make examples` runs the updated `fs/fs.ts` clean.
