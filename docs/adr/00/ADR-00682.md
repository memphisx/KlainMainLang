# ADR-00682: optional-chaining `a?.m()` didn't short-circuit a method call

- **Date**: 2026-09-03

## Context

`a?.m()` on a `null` receiver still **invoked** `m` (running its side effects
and returning its real value), instead of short-circuiting to `undefined`. On a
receiver whose method touches real `this`, this would fault. Found in the audit.

## Investigation

`?.` is a bool `Optional` flag on `MemberExpression` (`ast/nodes.go`); a
following `(args)` wraps it in a plain `CallExpression`, so the `?.` lives only
on the inner member node. `emitOptionalMember` (`emit_exprs_member.go`) honored
`Optional` only for member **reads** — method **calls** go through `emitCall`,
which never inspected `mem.Optional` and dispatched the call unconditionally.

## Decision

Add `emitOptionalCall`, hooked in `emitCall` when the callee is an optional
member. It mirrors `emitOptionalMember`: evaluate the receiver once; if it's a
null pointer, store the undefined/zero sentinel and **do not call**; otherwise
bind the receiver to a throwaway local and run the call through it (so a
side-effecting receiver is evaluated exactly once). A nested chain (`a?.b?.m()`)
composes — a nullish inner link already produces the null sentinel the guard
catches. The null-branch result uses the same scalar-zero / null-pointer
stand-in `emitOptionalMember` already uses (a scalar `a?.m()` yields `0`, not a
distinct `undefined` — the pre-existing, disclosed sentinel limitation); the
fixed bug is that the method is no longer invoked on null.

## Verification

Mac. `a?.m()` on null no longer prints the method's side effect and yields the
sentinel; a non-null receiver still calls. E2E tests
`TestE2EOptionalChainCallShortCircuits` / `…NonNullInvokes`; full
exprs/classes/call regression green.
