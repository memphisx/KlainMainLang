# ADR-00885: RegExp exec/test subject and constructor pattern/flags ToString a non-string argument

- **Relations**: `Extends ADR-00884`
- **Date**: 2026-09-11

## Context

Continuation of the A1 invalid-IR sweep (BACKLOG §4). A sampled category run
(`go run ./tools/conformance -category=built-ins/RegExp`, macOS arm64,
lane=strict) showed **11 of 1,879 RegExp files as CLANG_ERROR**. Unlike
DataView/String/Date/Array, RegExp has *no* bare numeric-arg coerce sites; its
invalid-IR files split into two distinct causes:

- A non-string subject to `.test()`/`.exec()`, or a non-string
  pattern/flags to `new RegExp(...)` — a non-`ptr` word left where a string
  pointer is required. Sources include `var __string;`, and a `void` value from
  a no-return `(function(){})()` (test262 `test/*`, `S15.10.4.1_*`).
- `var __matched = []` (untyped empty array) with `.push(re.exec(...)[0])` — the
  untyped-array element-inference problem (a separate, architectural cluster).

## Investigation

`emitRegexTest`/`emitRegexExec` did `strVal = e.coerce(strVal, TypePtr)` on the
subject; `emitNewRegExpExpression` did the same for pattern/flags. `coerce` has
no conversion from a non-`ptr` scalar to `ptr`, so an `undefined`/`void`/number
subject stayed a non-`ptr` word and reached `pcre2_match_8` / the flag validator
as invalid IR. The existing flags null-pointer guard only caught a runtime null
`ptr`, not an `undefined`-*typed* (i64) or `void` value.

The faithful fix is ToString, not rejection: JS coerces the subject
(`re.test(123)` matches `"123"`, `re.test(undefined)` matches `"undefined"`),
`new RegExp(undefined)` is the empty pattern, and `new RegExp(p, undefined)` has
no flags. A no-return function call is typed `void` in this compiler but is
`undefined` in JS, so `void` in value position is treated as `undefined` here.

## Decision

- New helper `regexSubjectToString`: a string subject coerces as before; a
  `void`/`undefined` subject becomes the literal `"undefined"`; anything else is
  `emitValueToString` (full JS ToString). Used by `.test()` and `.exec()`.
- `emitNewRegExpExpression`: an `undefined`/`void` pattern becomes the empty
  string (empty regex); a non-string pattern is ToString'd. Flags: an
  `undefined`/`null`/`void` value is `""` (no flags); a non-string value is
  ToString'd; a string keeps the existing null-pointer→`""` guard.

## Implementation notes

- `codegen/llvm/emit_regexp.go` only.
- The `void`-as-`undefined` treatment is local to these RegExp entry points; the
  general "no-return call in value position" typing is unchanged.

## Side effects discovered

- The remaining 4 RegExp CLANG_ERROR files
  (`prototype/exec/S15.10.6.2_A3_T{1,5,6,7}`) are the untyped `var x = []` +
  `push` element-inference bug, not this path — the large architectural item
  tracked in the invalid-IR backlog (needs a real element type for an untyped
  empty array). Left for that work.
- `var f;` (uninitialized, no annotation) is typed `number` here, not
  `undefined` — a separate undefined-sentinel gap (TDD-00187 territory),
  unrelated to this fix.

## Verification

- Sampled RegExp category: **11 → 4 CLANG_ERROR** (7 reclassified; the 4 left
  are the untyped-array cluster above). macOS arm64, lane=strict, isolated
  `-workdir`, reduced workers (an unrelated conformance run was in progress).
- New E2E `TestE2ERegExpNonStringArgs` (number/void subject ToString, undefined
  pattern/flags); the existing `TestE2ERegex*`/`TestE2ERegExp*` suite stays
  green.
- `go build`, `go vet ./...` — clean.
