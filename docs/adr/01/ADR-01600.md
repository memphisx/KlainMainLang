# ADR-01600: Streamed request bodies: EAGAIN leak and 100 Continue

- **Relations**: Extends ADR-00362
- **Date**: 2026-10-13

## Context

`examples/streams/http_upload.ts` (a `klain:http` server reading its body
with `req.stream()`, fed by an in-process `fetch` POST of 8 MiB) grew
without bound on Windows: capped at 1 GB it reached the cap and failed with
`unexpected end of request body`. The program itself is correct; Node runs
the same shape in a few tens of MB.

## Investigation

Each side alone stayed small (the server with Node's `fetch`: 28 MB; our
`fetch` against a Node server: 18 MB). Our `fetch` against our server grew
in either one or two processes, and so did Node's `http.request` once it
sent `Expect: 100-continue`. libcurl sends that header on large POSTs and
holds the body back until it hears `100 Continue` (it gives up after 1 s);
Node's client waits indefinitely.

Two defects:

- The server never answered `Expect: 100-continue`. Node's server writes
  `HTTP/1.1 100 Continue` as soon as the headers are parsed when nothing
  listens for `'checkContinue'`.
- `__kml_reqbody_read_step` (`runtime_http_reqbody.go`) allocated its 64 KiB
  chunk buffer before `read` and handed it over only when bytes arrived; on
  EAGAIN or a failed read the buffer was dropped. The event-loop pump calls
  it on every pass while a streamed body is in flight, so a slow or held-back
  body leaked 64 KiB per pass. This is not Windows-specific.

## Decision

- The generated HTTP/1.1 dispatcher (`emit_http.go`) writes
  `HTTP/1.1 100 Continue\r\n\r\n` after parsing the headers when `Expect` is
  `100-continue` (case-insensitive), as Node's server does by default.
- `__kml_reqbody_read_step` frees the chunk buffer on EAGAIN and on early end;
  `errno` is read before the free.

## Implementation notes

`'checkContinue'` is not exposed on `klain:http`, so the 100 is always sent.
Node's `http.createServer` path is separate and was not changed.

## Side effects discovered

- The Windows examples runner (`tools/testsel/examples.py`) now runs in a job
  object of 2 GB, 1 GB per program and 64 processes.

## Verification

Windows 11: the example peaks at 54 MB (was over 1 GB), a 12 MiB upload at
42 MB, Node's `Expect` client receives the 100 and a full count.
`TestE2EStreamsRequestBodyExpectContinue` (100 Continue, then the body in
eight slow pieces) and the existing request-stream tests pass. Linux: owed.
