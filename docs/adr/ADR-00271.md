# ADR-00271: Thenable adoption — `resolve(aPromise)` in a `new Promise` executor

- **Relations**: Implements [TDD-00091](../tdd/TDD-00091.md); extends [ADR-00263](ADR-00263.md), [ADR-00267](ADR-00267.md) (the executor constructor); reuses [ADR-00248](ADR-00248.md)'s reaction/microtask machinery
- **Date**: 2026-08-20

## Context

`new Promise((resolve) => resolve(anotherPromise))` should make the outer promise adopt the inner
one — settle with its value on fulfil, its reason on reject. It was the sole real caveat on the
`new Promise` executor row (the other, "a bare top-level-function executor reference is
unsupported," turned out **stale** — `emitExpr` already resolves such a reference to a closure
value, verified with resolve+reject executors). Before this, `resolve(aPromise)` was a hard
`clang` type error: `resolve`'s parameter is the value type (`i64`) and the argument a promise
(`ptr`).

## Investigation

`resolve` is a per-site closure whose env is the target promise (`emit_promise_new.go`
`buildBuiltinClosure`). The `.then` implementation (`emit_promise_then.go:159-190`) already has the
exact primitive adoption needs: register a reaction closure on a source promise that fires — as a
microtask — when the source settles, enqueuing immediately if the source is already settled. And
`__kml_promise_settle` already copies-in a settlement, wakes a parked awaiter, and drains the
target's reactions. So adoption is "attach a settlement-copy reaction to the argument promise,"
not new machinery.

A synchronous alternative (drive the argument to settled inside `resolve`, then settle the target)
was rejected: it would settle the target synchronously at the `resolve` call, diverging from JS
where adoption is a microtask job — an ordering caveat that would keep the row non-strict.

## Decision

Mark the resolve closure's type `IsPromiseResolver`. In `emitClosureCallByPtr`, when a resolver is
called with a single argument whose compile-time type is a `Promise`, adopt instead of coercing:
`emitPromiseAdopt(target=env, src=arg)` builds a `{src,tgt}` env + an adopt closure over
`@__kml_promise_adopt_runner`, and registers it on `src` (enqueue-now-if-settled, else attach to
`src`'s reaction list). When it fires, the runner copies `src`'s state + value/reason bits into
`tgt` (honoring first-settle-wins on `tgt`) and calls `__kml_promise_settle(tgt, srcState)`. A
plain-value argument falls through to the normal store-and-settle path; a `Promise<void>` resolve
takes no argument and is never marked.

## Implementation notes

- `types.go`: new `Type.IsPromiseResolver`.
- `emit_promise_new.go`: set it on `resolveTy` (only when `resolve` has a value parameter); new
  `ensurePromiseAdoptRunner` (`@__kml_promise_adopt_runner`) and `emitPromiseAdopt` (the
  register-or-enqueue, mirroring `emitPromiseThen`).
- `emit_func.go`: the `emitClosureCallByPtr` hook — guarded by `IsPromiseResolver` +
  `inferExprType(arg).IsPromise`, so it costs nothing for a normal callback and adopts only a
  genuine promise argument.
- `emitter.go`: `usedPromiseAdoptRunner` guard flag.

## Side effects discovered

- With adoption done and the stale top-level-function caveat removed, the `new Promise` executor
  row is caveat-free → **strict**. Async/Promise strict moves **5/9 → 6/9** (page header updated).
- A custom duck-typed thenable (a class with a `then` method) is **not** adopted — only a typed
  `Promise` argument is. This compiler has no `PromiseLike<T>`/structural-thenable type, so a
  non-`Promise` `{ then }` value passed to `resolve` is a clean compile-time type mismatch, not a
  silent miss. Tracked as a general "no `PromiseLike` type" scope point (a note on the row), not a
  new-Promise-specific behavioral bug.
