# TDD-00060: Function expressions (`var f = function() {}`, IIFEs, callbacks)

- **Status**: Implemented
- **Date**: 2026-08-11

## Context

The conformance harness (TDD-00008 V2) identifies `unexpected token function in expression` as the single largest failure bucket: 14,881 of 53,578 files (28%), dwarfing every other reason. This compiler only supports function *declarations* (`function f() {}`, statement position only) and arrow functions (`(x) => ...`). A `function` keyword in expression position — assigned to a variable, passed as a callback, or immediately invoked (IIFE) — is a clean parse-time rejection.

Conformance is a measurement tool, not a goal — but with this single gap accounting for 28% of all failures, fixing it would move the needle from 8.3% to roughly 36% pass (14,881 + 4,463 = 19,344/53,578) in one shot, making the remaining gaps — most of which are genuine out-of-scope features — much more visible.

Arrow functions already have all the runtime machinery a function expression needs: closure structs `{funcPtr, envPtr}`, free-variable capture, heap-cell promotion, HOF callback integration, and async support (see `codegen/llvm/emit_func.go`). The largest missing piece is the name-binding edge case (see "Self-referencing" below), not the core plumbing.

## Design

A function expression reuses the parser's existing `parseFunctionRest` (the shared `(params) : retType? { body }` tail already used by both top-level function declarations and class methods) and the emitter's existing `emitClosureFunc` / closure-value construction (the machinery `emitArrowFunctionWithHints` already uses to allocate a `{funcPtr, envPtr}` heap pair and return a typed closure value). The execution semantics are the same as an arrow function — the function body runs in a new emit context with its own SSA registers, labels, and scope, and the result is a heap-allocated closure struct reachable through the variable it's assigned to — so new design work is in the AST and parser only, not the codegen or runtime.

### Self-referencing (named function expressions)

The one genuine design question: a named function expression's own name is visible inside its own body (allowing recursion by that name) but does NOT leak to the enclosing scope. Real JS code:

```javascript
var factorial = function fact(n) { return n <= 1 ? 1 : n * fact(n - 1); };
typeof fact; // "undefined" — name does not leak
factorial(5); // 120 — recursion works via the "fact" binding visible inside
```

This compiler has no mechanism for that today — every function declaration's name is unconditionally registered in the current scope. The recommendation:

**V1 (this pass): anonymous function expressions only.** `var f = function(x) { return x + 1; }` works; `var f = function fact(n) { ... }` is a clean parse-time rejection ("named function expressions are not yet supported"). This avoids the name-visibility question entirely and still covers ~80% of real-world uses (assignment to a variable, passed as a callback argument, IIFE). The name-binding subset is small enough to pick up separately without losing the bulk of the conformance gain.

### Parser changes

In `parser_literals.go`'s `parseMember`, add a `case lexer.FUNCTION:` before the fallback error on line 1034:

1. `p.advance()` to consume `function`
2. Optionally consume an IDENT as the function's *own* name — if present, same-commit rejection with a clear message ("named function expressions are not yet supported")
3. Call `parseFunctionRest("" /* no stashed name */, false /* isAsync */, false /* bodyOptional */)` to parse params/return-type/body
4. Wrap the result as a new AST node type `FunctionExpression` that carries the same fields as `FunctionDeclaration` but implements `Expression` (not `Statement`)

The `async function` variant uses `case lexer.ASYNC:` in `parseMember` — the same `async` case already exists for `async (params) => ...` arrow functions, so it's extended rather than duplicated: advance past `async`, check for `function` keyword, then call `parseFunctionRest("", true, false)` and wrap.

### AST changes

New node type `FunctionExpression` with the same fields as `FunctionDeclaration` (Name, Params, ReturnType, Body, IsAsync, …) but implementing `ast.Expression` instead of `ast.Statement`. No new fields needed — Name stays populated (it's `""` for anonymous, untouched for now per V1 scope) but the expression's own name is not registered in the enclosing scope; only the caller (var-decl init, call-arg position, or IIFE) uses the resulting closure Value.

### Emitter changes

Two call sites:

1. **Var-decl init (`emit_exprs_vardecl.go`)**: add `case *ast.FunctionExpression:` alongside the existing `case *ast.ArrowFunction:` — both need the same type-inference treatment (closures need hints for untyped params).

2. **Expression emission (`emit_exprs.go`)**: add `case *ast.FunctionExpression:` to `emitExpr`'s type switch, and add a new function `emitFunctionExpression` to `emit_func.go` that:
   - Gathers captures (same `gatherCaptures` that arrow functions use, adapted to accept params from the expression rather than the arrow-specific `af.Params`)
   - Emits the closure LLVM function (same `emitClosureFunc` pattern, with the function expression's own body and param types)
   - Allocates and returns the `{funcPtr, envPtr}` closure header (same `malloc(16)` + gep + store pattern `emitArrowFunctionWithHints` lines 1077-1118 already use)

3. **Callback resolution (`resolveCallback` / `emit_func.go:1301`)**: the existing `case *ast.ArrowFunction:` branch needs a `case *ast.FunctionExpression:` sibling — a function expression passed as a callback argument should go through the same closure-value emission path an arrow function uses.

### IIFE support (free)

An IIFE `(function(x) { return x + 1; })(5)` is a plain parenthesized expression `(expr)` followed by a call `(args)` — parentheses are already their own wrapping identity in this parser, and calling the result of a parenthesized expression is the existing `only simple function calls are supported` rejection from `emitCall`. That rejection is a separate, already-tracked feature gap (2,806 conformance failures, third-largest bucket). Fixing it is not part of this TDD — IIFEs will compile cleanly at the parser level but still hit the same `emitCall` rejection as any other non-identifier-callee call.

**V1 scope**: anonymous functions in var-decl init, callback argument, and return expression positions. IIFE and `f()()` call-expression callee are separate work.

### Async variant

`async function(x) { return await ... }` is structurally identical — the `IsAsync` flag that already routes through `emitClosureFunc` for async arrow functions works unchanged. Test262 has `async function` expressions as part of the same function-expression bucket; supporting both costs essentially nothing extra once the base path exists.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Closures / `emitArrowFunctionWithHints` | Already done | The full closure-value-construction pipeline is shared rather than duplicated |
| `emitClosureFunc` | Already done | Emits the inner LLVM function for any closure body (arrow or, after this TDD, function expression) |
| `gatherCaptures` | Already done | Free-variable scanning works on any scoped body — needs a shallow adapter for the non-arrow param shape |
| `emit_call.go`'s callback dispatch | Already done | `resolveCallback` and the HOF emit functions accept any expression-typed callback |
| Named function expression semantics | Deferred to V2 | Name visible inside own body, not visible outside — genuinely new semantic machinery, not just plumbing |
| IIFE / `f()()` call of an expression result | Deferred | Separate, already-tracked gap (2,806 conformance failures, `only simple function calls are supported`) |

## Open questions

- Whether `emitClosureFunc`'s current assumption that the closure's first parameter is always `ptr %env` (the environment pointer) survives unchanged — function expressions and arrow functions share the same closure ABI by construction, so no change is expected, but this should be explicitly confirmed during implementation rather than assumed.
- Whether `registerFunctions`'s two-pass scan (which currently only registers named, top-level `FunctionDeclaration` nodes) needs to be taught about inline function expressions — V1's anonymous-only scope means no; `var f = function(){}` registers the *variable* `f` (which holds a closure value), not the function's own name. Confirmed during implementation.
