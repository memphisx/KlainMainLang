# ADR-00116: RegExp Stage 2 — .exec(str), and three general truthiness/null-comparison bugs it exposed

- **Relations**: Implements [TDD-00035](../tdd/TDD-00035.md). Extends [ADR-00114](ADR-00114.md), [ADR-00115](ADR-00115.md)
- **Date**: 2026-08-07

## Context

[TDD-00035](../tdd/TDD-00035.md)'s Stage 2 is `.exec(str): string[] | null` plus the `lastIndex`/`g`-flag stateful-iteration machinery real JS's `.exec()` (and, per spec, `.test()` too — see [ADR-00115](ADR-00115.md)'s own note on this, left for Stage 2 deliberately) depends on. Picked up directly following Stage 1, per the user's "continue with Stage 2."

The TDD's Design section stated `T | null` was "already-real, reusable machinery," citing `Type.Nullable`. That turned out to be true only for a plain `ptr`-shaped `T` (a nullable string, object, etc.) — never for an array, because this is the first feature in this compiler's history to actually need a nullable *array* return type. Investigating why exposed three separate, real, pre-existing bugs, none of them RegExp-specific, all blocking `.exec()`'s designed return type from being usable at all for its single most common real-world usage pattern (`if (m !== null)` / `while ((m = re.exec(s)) !== null)`).

## Investigation

**Bug 1 — `if (someString)` (and any other bare ptr-typed truthiness check) was already completely broken, a hard compile failure.** Found by writing the most basic possible smoke test for `.exec()`'s null check and hitting a `clang` parse error immediately: `toBool` (`emit_exprs_types.go`, the function `if`/`while`/ternary conditions actually call) emitted `icmp ne <IR> <ref>, 0` unconditionally for any non-float, non-i1 type — including a bare `ptr`, where LLVM requires the `null` keyword, not a bare integer `0` (confirmed by hand-compiling a two-line reproduction `.ll` file: `icmp ne ptr %v, 0` is rejected with "integer constant must have integer type"). Confirmed this was a real, live gap in the existing codebase, not something the RegExp work introduced, by testing `if (someExistingStringVar)` against `main` (pre-Stage-2) directly — it already failed to compile. Apparently never exercised by any existing test or example, since idiomatic KML code written so far always used an explicit comparison (`str !== ""`, `str.length > 0`) rather than JS's bare-value truthiness for a string.

While fixing this, found a second, separate, *already-correct* implementation sitting right next to the broken one: `emitToBool` (`emit_exprs_coerce.go`) already handled `ptr` correctly (`icmp ne ptr %s, null`) — but is called from entirely different call sites (array HOF predicates: `.filter`/`.some`/`.every`/`.find` callback results), never from `if`/`while`. Two near-duplicate functions doing the same conceptual job had quietly diverged. Diffing them turned up a second, independent bug: `emitToBool`'s float branch used `fcmp une` (unordered-or-not-equal — true whenever *either* operand is NaN, regardless of the specific relation), while `toBool`'s used `fcmp one` (ordered-and-not-equal — false whenever either operand is NaN). Real JS's `Boolean(NaN) === false`, so `one` is correct and `une` is a second latent bug in the less-used of the two functions — `emitToBool`'s callers all currently pass an already-`boolean`-typed HOF predicate result in practice, so this was never actually triggered, but would have been the moment a float predicate expression reached it directly.

**Bug 2 — comparing an array-typed value against `null` was unimplemented, also a hard compile failure.** `.exec()`'s whole `T[] | null` design requires `m !== null` to work. Traced `emitBinary`'s equality-operator path (`emit_exprs_operators.go`): `ty := left.Ty` for an array is `ArrayOf(...)`, whose `IR` field is `"ptr"` (a simplification `types.go` makes deliberately for other purposes — `ArrayOf`'s doc comment, and `StructFieldIR`'s existence specifically to give arrays a different shape than `ty.IR` implies at struct-field-storage sites). The generic `icmp %s %s %s, %s` comparison code uses `ty.IR` ("ptr") as the textual LLVM type for the instruction, but the actual SSA value held in `left.Ref`/`right.Ref` for an array is a `{ptr,i64}` aggregate, not a plain `ptr` register — `icmp ptr %aggregateReg, ...` is a real type mismatch (LLVM's `icmp` only ever accepts int/ptr/float operands, never an aggregate, by design — there is no way to compare a struct directly). Confirmed this is a genuinely new gap, not merely an unlucky RegExp-specific interaction: no array-typed value has ever needed a null comparison before this feature (nothing else in the language produces a `T[] | null`).

**Bug 3 — even after fixing 1 and 2, string truthiness was still semantically wrong.** A naive "extend `toBool`'s new ptr/null handling to treat any non-null string as truthy" produces `if ("")` evaluating truthy — wrong; real JS's string truthiness is *content*-dependent (empty string is falsy), the one JS primitive where "is this pointer merely present" isn't the right question at all — every other ptr-backed value in this compiler (object, array, Map, Set, closure, ...) is truthy whenever non-null, full stop. Also found that the existing `isStringTy` helper (`emit_strings.go`, already used pervasively for string-vs-other-ptr-type dispatch decisions) is not precise enough to safely reuse here: it returns true for `Map`/`Set`/`EventEmitter`/`ArrayBuffer`/`TextEncoder`/`TextDecoder`/`Promise` too (anything `IR=="ptr"` and not `IsObject`/`IsArray`/`IsFunc`), since none of those carry a distinguishing flag `isStringTy` checks against. Using it directly for truthiness would have introduced a *fourth* bug: `if (someMap)` would incorrectly base its truthiness on the first byte of the Map's internal representation instead of always being truthy.

## Decision

**Stage 2 itself** (`emit_regexp.go`):
- `regExpExecResultType()`: `ArrayOf(TypePtr)` with `Nullable: true` — confirmed this really is just the existing `Type.Nullable` field, no new type-system field needed, once the codegen bugs above were fixed. "Null" for this array is represented as a `{ptr: null, len: 0}` aggregate — this compiler's only way to represent "absent" for a `{ptr,i64}` value, since a bare LLVM `null` constant only has meaning for a plain pointer type.
- `emitRegexExec`: loads `global`/`lastIndex` from the RegExp instance, selects the match start offset (`lastIndex` if `global`, else `0`), discovers the pattern's capture-group count via `pcre2_pattern_info_8`/`PCRE2_INFO_CAPTURECOUNT` (needed to size the result array — unknowable statically), runs `pcre2_match_8`, and on success builds a `string[]` (full match + numbered captures, an unmatched optional group → `""`) via a runtime loop over the ovector PCRE2 returns, updating `lastIndex` to the match's end offset only when `global`. On failure, resets `lastIndex` to `0` only when `global`, and returns the null sentinel. Deliberately does **not** special-case a zero-length match by auto-advancing — real JS's `RegExpBuiltinExec` doesn't either (that behavior lives in `matchAll`/`replace`/`split`'s own algorithms, Stage 3-5's problem, already flagged in the TDD's Open Questions).
- `emitRegexStoreLastIndex`: a small shared GEP+store helper for the two branches (advance / reset) that mutate `lastIndex`.

**The three bug fixes** (`emit_exprs_types.go`, `emit_exprs_coerce.go`, `emit_exprs_operators.go`):
- `toBool` gained array handling (extract the data pointer, compare to `null` — but *only* for a `Nullable` array; a non-`Nullable` array is unconditionally truthy, matching real JS's "any array, even an empty one, is truthy" and deliberately avoiding a false "falsy" result from glibc's `malloc(0)` sometimes returning `NULL` for an ordinary empty array) and a new `isPlainStringTy` + `emitStringTruthiness` path (a small branch: null-check first — loading through a genuinely null pointer would be real UB — then, if non-null, check whether the first byte is the NUL terminator).
- `isPlainStringTy` (`emit_exprs_types.go`): `isStringTy(ty) && !ty.IsMap && !ty.IsSet && !ty.IsEventEmitter && !ty.IsArrayBuffer && !ty.IsTextEncoder && !ty.IsTextDecoder && !ty.IsPromise` — deliberately more precise than reusing `isStringTy` bare, scoped to *this* call site only (not a change to `isStringTy` itself, which is correct for its own existing, narrower dispatch-decision call sites).
- `emitToBool` (`emit_exprs_coerce.go`) is now a one-line delegate to `toBool` — the two implementations' divergence (the NaN bug above) was itself evidence they should never have been separate; consolidating fixes the NaN bug as a direct consequence rather than needing a second, parallel fix.
- `emitBinary` (`emit_exprs_operators.go`) gained an early special case, before the generic coerce/icmp path: `(left.IsArray && right.IsNull) || (left.IsNull && right.IsArray)` extracts the array operand's data pointer and compares *that* to `null` for `==`/`!=`/`===`/`!==`. General array-vs-array equality (a separate, still-unimplemented gap — not exercised by anything built so far) is untouched.

## Implementation notes

Files touched: `codegen/llvm/emit_regexp.go` (new `regExpExecResultType`, `emitRegexStoreLastIndex`, `emitRegexExec`), `codegen/llvm/runtime_regexp.go` (extended `ensureRegexMatch` with `pcre2_pattern_info_8`/`pcre2_get_ovector_pointer_8`; new `pcre2InfoCaptureCount`/`pcre2Unset` constants, the latter verified against the real, now-system-installed `pcre2.h` directly rather than assumed — `PCRE2_UNSET` and `PCRE2_ZERO_TERMINATED` happen to share the same bit pattern, `~(PCRE2_SIZE)0`, but are kept as separately named constants since they mean different things at their respective call sites), `codegen/llvm/emit_call.go` (`.exec` dispatch), `codegen/llvm/emit_exprs_types.go` (`inferExprType` case, `toBool` rewrite, `isPlainStringTy`, `emitStringTruthiness`), `codegen/llvm/emit_exprs_coerce.go` (`emitToBool` consolidation), `codegen/llvm/emit_exprs_operators.go` (array-vs-null comparison).

`libpcre2-dev` is now genuinely installed system-wide on this development machine (the user ran `sudo apt-get install libpcre2-dev` between sessions, per [ADR-00114](ADR-00114.md)/[ADR-00115](ADR-00115.md)'s noted requirement) — all verification in this ADR was done directly, with no `LIBRARY_PATH` workaround needed.

An unmatched optional capture group's ovector entry is `PCRE2_UNSET` (`~(PCRE2_SIZE)0`) specifically in its *start* offset — checking only `ovector[2*i] == PCRE2_UNSET` (not also the end offset) is sufficient and matches PCRE2's own documented contract.

## Side effects discovered

**A fourth, real, pre-existing bug was found but is explicitly NOT fixed here, out of scope for this stage**: `0.0 / 0.0` (float division producing `NaN` at runtime, as opposed to the already-recognized `NaN` global constant) crashes the compiled program outright (`SIGSEGV`, confirmed directly) when the result is later used — isolated to something in `console.log`'s handling of a runtime-computed NaN and/or float equality codegen for `n === n` (which produced a garbage non-boolean-looking printed value, `374741928`, rather than `0`/`1`, in a separate isolated repro), not the `toBool`/truthiness code this ADR touches (confirmed by testing this stage's own NaN-falsiness fix against the bare `NaN` global identifier instead, which works correctly and doesn't crash). Flagged here rather than silently dropped, per the project's own standing rule — not tracked under a dedicated `docs/status/` entry yet since its exact scope (division-by-zero specifically? all runtime-computed-NaN codegen? just `console.log`? just `===`?) hasn't been isolated, and pursuing it further was judged out of scope for a RegExp `.exec()` stage. Worth a dedicated investigation in its own right.

## Verification

- `go build ./...` and `go vet ./...` clean.
- `go test ./...` — full existing suite passes unchanged, plus the new tests below.
- New tests (`tests/regexp_test.go`): capture-group extraction on a successful match, `null` on no match, an unmatched optional group becoming `""`, the full `while ((m = re.exec(s)) !== null)` global-iteration idiom (verifying `lastIndex` advances correctly across repeated calls, then resets to `0` on the terminating failed match), a non-global RegExp never touching `lastIndex`, `lastIndex` resetting after a failed match specifically, bare string truthiness (`if (s)`/`if ("")`), a non-Nullable array staying truthy regardless of content (both empty and non-empty), `NaN` being falsy, and a `Map` staying truthy regardless of content (the `isPlainStringTy` precision fix, specifically).
- Updated example: `examples/regexp/regexp.ts`, verified via `make examples` (80/80 passed).
- Manually verified via scratch `.ts` files before the formal test suite was written: capture groups, the no-match/null case, the global-flag `while` loop (including confirming exact `lastIndex` values at each step by direct inspection, not assumed), non-global `lastIndex` staying untouched, `lastIndex` resetting after switching to a non-matching string mid-sequence, bare string/empty-string truthiness, non-nullable empty-array truthiness, and the `NaN`-via-bare-global-identifier case.
- Verified on: x86-64 Linux only (this session's machine) — the same outstanding Apple Silicon re-verification note as ADR-00114/ADR-00115 applies to the PCRE2-facing pieces; the truthiness/null-comparison bug fixes are pure LLVM IR codegen with no platform-specific behavior at all, so no separate Mac-specific risk is expected there.
