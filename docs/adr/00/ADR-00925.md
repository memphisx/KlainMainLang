# ADR-00925: `--no-any` — ban the any/unknown escape hatch (TDD-00209 Stage 1)

- **Date**: 2026-09-13

## Context

The default `strict` lane is TS-faithful and accepts `any`/`unknown` (explicit
annotations, evolving-any from a null-initialized binding, `any[]`, boxed `any`
fields). Some deployments want a stronger guarantee: no dynamic escape hatch at
all, so the binary is provably fully static. This is a separate opt-in flag, not
a new compat mode.

## Decision

`--no-any` (strict lane only): every explicit `any`/`unknown` type annotation is
a compile error, and the evolving-any widening is disabled so a null-initialized
untyped binding/field falls back to the ordinary strict cross-type rejection.
Under `-compat=js` the flag is meaningless and is ignored with one stderr
warning.

- **Detection.** `resolveType` — the single entry point every user type
  annotation flows through — records the first violation
  (`checkNoAnyAnnotation` → `typeAnnotMentionsBareAny`, a recursive walk over
  every child annotation: element/key/args/func-params/return/fields/union/
  tuple/intersection/conditional/mapped/keyof, and a trailing-`[]` name strip so
  `any[]` is caught). `EmitProgram` surfaces the recorded error, superseding the
  produced IR. Only active when the flag is set (zero cost otherwise). A
  *constrained* union (`string | number`) is not `any` — it stays allowed.
- **Evolving-any.** `crossTypeWidenedBindings` (locals) and the
  `classFieldNullEvolves` widening (fields) are gated off under `--no-any`, so
  `let x = null; x = 5` / `this.#field ??= 1` hit the ordinary strict rejection
  rather than widening.
- **Compound-assign safety.** `emitLogicalCompoundAssign` now uses
  `coerceChecked` for its store, so a `??=`/`||=`/`&&=` whose right-hand side is
  incompatible with a null-typed location (which can occur once widening is off)
  is a clean compile error, never a `store ptr <double>` (invalid IR). This also
  hardens the normal lanes.

## Scope

- `as any` is erased in this compiler (ADR-00371) — `5 as any` is `5` (number),
  so no `any` is produced and nothing is rejected. Correct.
- Value-level implicit `any` at a **variable/const binding** — `const x =
  JSON.parse(s)` with no `as T`, whose inferred type is bare `any` — is now
  rejected too (a check at the var-decl site, distinct from the annotation walk).
  A concrete `as T` projection is accepted. Value-level `any` in other positions
  (an inferred-`any` function return, a nested any-valued sub-expression) is not
  yet flagged — the remaining Stage 2 residue (TDD-00209); in practice narrow,
  since operators and member access on a bare `any` are already unsupported.

## Verification

- `tests/no_any_test.go` (new, 8): rejects explicit `any`/`unknown`, `any[]`,
  `any` param, `any` field, and evolving-null; accepts concrete code and a
  constrained union.
- The `--no-any -compat=js` warning verified by hand.
- Logical-assign / nullish / coalesce test lanes green (the `coerceChecked`
  change); macOS arm64.
