# ADR-00162: `instanceof` against built-in types (`Array`, `Map`, `Set`, `Date`, `RegExp`)

- **Relations**: Extends [ADR-00153](ADR-00153.md)

## Context

Surveyed fresh candidates outside the destructuring/collections area this session had been working through (ADR-00156–ADR-00161), since the remaining nearby ones there (object rest, computed destructuring keys, `new Map(entries)`) all need real type-system prerequisites this compiler doesn't have. Two candidates investigated directly: spread in call arguments (`f(...arr)`) and `instanceof` against a built-in type name. The first turned out to already be documented (`docs/status/README.md`'s "Newly identified gaps") as needing a TDD before implementation — spreading a runtime-length array into a statically-typed, fixed-arity call target is real, unresolved design space, not a mechanical fix — so it was skipped. `instanceof` against a built-in was not previously documented anywhere and turned out to be well-scoped once investigated.

## Investigation

Confirmed directly: `arr instanceof Array`, `d instanceof Date` (`d` a real `new Date()`), `r instanceof RegExp`, `m instanceof Map` all failed identically with "instanceof is only supported against user-defined classes" — even the *exact-own-type* case (a real `Date` failing `instanceof Date`), not just a mismatched one. `emitInstanceOf`'s own doc comment (`codegen/llvm/emit_classes.go`) already explained why: the right-hand side must be a bare identifier naming a class registered through `registerClasses`, since only those carry the hidden runtime tag field the whole check is built around — a built-in type was never registered that way, so it hit the same "not a registered class" rejection every genuinely-unregistered name would.

Checked whether a *runtime* tag check was actually needed for these five types, or whether this compiler's own static typing already has the answer. It does: `Type.IsArray`/`IsMap`/`IsSet`/`IsDate`/`IsRegExp` are compile-time-known flags on every expression's already-inferred type, and — unlike real JS, where a value's prototype chain can in principle be manipulated at runtime — this compiler has no dynamic-prototype mechanism at all for a runtime check to ever disagree with a compile-time one. Confirmed this reasoning already had precedent in the very same function: a statically-mismatched *user*-class comparison (case 3/4 in `emitInstanceOf`'s own doc comment) already resolves to a compile-time constant `false`, not a runtime check — extending the same idea to five built-in flags is consistent, not a new mechanism.

Considered including `Object` too (real JS: `instanceof Object` is true for anything that isn't one of the primitive types). Rejected: unlike the five concrete types above, `Object`'s condition isn't one flag — it's "not a primitive," which only has a sound answer if every current *and future* object-shaped `Type` flag this compiler has is enumerated and kept in sync by hand. A silently-stale list would make `instanceof Object` quietly wrong for a type added after the fact, with no compiler error to catch it — a real, novel maintenance hazard the five single-flag cases don't share. Left as the existing clean rejection instead of taking on that risk for an admittedly common check.

## Decision

New package-level `builtinInstanceofTypes` map (`name string → func(Type) bool`) in `codegen/llvm/emit_classes.go`, checked in `emitInstanceOf` after the existing `errorKindIDs` check but only when the right-hand name isn't a *registered* class — a real user-defined class (reachable only under `-globals=permissive`, though confirmed separately that these five names specifically can never be shadowed at all, even there — `new Date(...)` etc. resolve to the built-in before any scope information exists) always takes precedence over the built-in fallback. The left side is still evaluated for real via `emitExpr` (side effects execute, matching every other branch), only its resulting `.Ty` feeds the compile-time-constant decision — an expression like `makeArr() instanceof Array` still runs `makeArr()`.

## Verification

- `go build`, `go vet ./...`, full `go test ./...`, `make examples` (all 109) — all pass.
- 7 new E2E tests (`tests/classes_test.go`): true/false for `Array`, both `Map`/`Set` cross-checked against each other, `Date` against a real instance and a non-Date value, `RegExp`, a side-effect-evaluation check, and confirmation that `instanceof Object` is still cleanly rejected (not silently allowed to guess).
- `examples/classes/classes.ts` extended with a short section building on the file's own existing `instanceof`-against-user-classes examples; built and ran directly, output matches the file's own inline comments exactly.
- Full Test262 corpus re-run: 4,462 → 4,463 — a small, real positive movement (unlike the last several rounds' net-zero, this one changes existing *behavior* rather than only unlocking previously-hard-error syntax, so a non-zero shift is expected either way).
