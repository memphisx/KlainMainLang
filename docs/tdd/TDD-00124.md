# TDD-00124: Self-Hosting — Rewriting the Compiler in Its Own Language

- **Status**: Not Started
- **Date**: 2026-08-26

## Context

The compiler is written in Go. A recurring long-term question is whether it can
eventually be rewritten in KlainMainLang-compatible TypeScript and compile
itself, so the Go implementation is retired entirely and the toolchain is
"self-hosting."

Self-hosting is a well-established milestone (TypeScript's own `tsc` compiles
itself; most mature compilers bootstrap). It is attractive for three reasons:

1. **Dogfooding at the highest difficulty.** A compiler is one of the most
   demanding programs a language can host — heterogeneous trees, visitor
   dispatch, large string manipulation, file and process I/O, careful integer
   arithmetic. Attempting it surfaces every ergonomic gap in the language, which
   is exactly the kind of pressure that hardens a general-purpose language.
2. **One fewer language in the stack.** Contributors would only need to know the
   target language, not Go.
3. **Proof of maturity.** A byte-reproducing self-compile is a strong,
   objective signal that the language and standard library are real.

This document scopes *whether* and *how*, not *when*. It is a
feasibility/reference doc in the same spirit as [TDD-00020](TDD-00020.md)
(Windows) and [TDD-00048](TDD-00048.md) (WebAssembly): a decided direction and
a map of the prerequisites, not a committed near-term target. It is deliberately
gated behind substantial core-language work.

**What self-hosting does and does not remove.** It removes the **Go**
dependency. It does **not** remove the external C toolchain: this project
fundamentally emits LLVM IR *text* and hands it to `clang`, then links libc
(and, on demand, libcurl/libssl/etc.). A self-hosted compiler still shells out
to `clang` and links a C runtime. "No Go" is reachable; "no external toolchain"
is a different, out-of-scope goal.

## Design

### Feasibility

Nothing in the pipeline is exotic for a typed language to express:

- **Lexer / Parser** — character/string scanning and recursive-descent tree
  building. Pure text processing.
- **Resolver** ([ADR-00022](../adr/ADR-00022.md)) — merges entry + imports into
  one `*ast.Program`; tree walking + symbol tables (`Map`s).
- **Codegen** — tree walk emitting LLVM IR *strings* via the two-builder
  (`allocas`/`body`) pattern; SSA register/label counters; C-decl bookkeeping.
- **Driver** — argument parsing, file I/O, and a `clang` subprocess.

Every stage is text-in / text-out with in-memory trees. The hard part is not any
single algorithm; it is that the language must be **ergonomic enough** to
express large, heterogeneous, mutually-recursive data (the AST and the symbol
tables) without fighting the type system.

### The language gate (the real blocker)

Self-hosting is gated on the compiler being *pleasant* to write in this
language. The gaps map almost exactly onto the existing hard-roadmap items:

- **A richer object / node model.** An AST is dozens of node shapes walked by
  visitors that branch on node kind. Today's fixed-shape nominal structs plus
  monomorphized generics can encode a lot, but an ergonomic
  `visit(node): T`-style dispatch wants either (a) genuine **discriminated
  unions with exhaustive narrowing** over a closed node-kind set (the natural,
  type-safe encoding — partially present, [TDD-00043](TDD-00043.md) and the
  union-field/narrowing TDDs) or (b) the deferred **dynamic / prototype object
  model** ([TDD-00068](TDD-00068.md)). One of these must mature first.
- **Generics depth.** Symbol tables, environments, and IR builders are generic
  containers (`Map<string, Symbol>`, `T[]`, result/option-shaped returns).
  Explicit call-site type arguments and richer constraint handling
  ([TDD-00010](TDD-00010.md)/[TDD-00113](TDD-00113.md)) reduce friction.
- **Faithful primitives.** A compiler is heavy on integer index/offset
  arithmetic *and* occasional real-number work; the `number`-as-double model
  with clean integer escape hatches ([TDD-00123](TDD-00123.md)) is a
  prerequisite for writing it without constant caveats.
- **Binary-safe strings and I/O.** Source files, IR buffers, and byte streams
  must round-trip exactly — the embedded-null-byte and binary-safety work
  ([TDD-00120](TDD-00120.md), [ADR-00094](../adr/ADR-00094.md)) matters because
  a compiler manipulates source text and emits large buffers constantly.
- **`fs` / `process` / subprocess.** Reading sources, writing `.ll`, and
  spawning `clang` — `fs` and `process` exist; a `clang` invocation needs the
  `child_process`-style spawn surface to be solid.
- **Error/diagnostic modeling.** Structured errors with positions
  ([TDD-00072](TDD-00072.md)) — the compiler threads `pos` through every node
  and reports precise diagnostics.

Until a critical mass of the above is in place, a self-host would be an exercise
in fighting the type system rather than a clean rewrite.

### Bootstrap mechanics

The standard three-stage bootstrap proves reproduction:

1. **Stage 0 (seed):** the Go compiler compiles the new TS-written compiler
   source → binary **A**.
2. **Stage 1:** **A** compiles the same TS source → binary **B**. This proves
   the language can express, and A can compile, the compiler.
3. **Stage 2:** **B** compiles the same TS source → binary **C**. If **B** and
   **C** are **byte-identical**, the compiler reproduces itself and the Go seed
   is no longer on the critical path.

The Go implementation is kept as the stage-0 seed for a long transition period
regardless (and as a differential oracle — running both on the same input and
diffing output is a powerful regression check during the migration).

### Migration strategy (incremental, not big-bang)

A single all-at-once rewrite is high-risk. A staged path de-risks it and yields
value at each step:

1. **Partial self-host as a proving ground.** Rewrite the front end
   (lexer + parser producing the AST) in the new language first, while codegen
   stays in Go behind a stable AST-serialization boundary. This exercises the
   language on the least-exotic stage and surfaces ergonomic gaps early, cheaply.
2. **Resolver + type layer** next, then **codegen** last (codegen is the largest
   and most idiom-heavy — the two-builder pattern, SSA counters, and the
   `ensure*` decl bookkeeping all get re-expressed in the language's own idioms).
3. **Differential testing throughout.** For every stage ported, run the Go and
   TS versions on the whole `examples/` + `tests/` corpus and diff the emitted
   IR / program output; a mismatch is a bug in the port. This turns the existing
   conformance and example suites into the self-host acceptance harness.
4. **Flip stage-0 to the self-hosted binary** only after a byte-reproducing
   Stage 1 == Stage 2 and a green corpus.

### Non-goals

- Removing `clang` / LLVM / libc (see Context — out of scope by design).
- A bit-exact match to the Go implementation's *IR text* (only observable
  program behavior needs to match; IR formatting may differ). Byte-reproduction
  is required only between the self-hosted compiler's own successive stages.
- Doing this before the language gate above is cleared.

## Open questions

- **Unions vs. a dynamic object model for the AST.** Which encoding does the
  language commit to for heterogeneous nodes? This is the single biggest
  language-design fork and should be settled (likely in [TDD-00068](TDD-00068.md)'s
  resolution) before any serious self-host attempt.
- **How much of Go's concurrency is actually needed?** The Go codebase uses
  goroutines (e.g. the conformance runner's sharding). The compiler *core* is
  largely sequential; the parallel harness could stay in a thin Go/driver shim
  or be re-expressed with this language's Worker/async model — decide whether
  the self-host includes the tooling or only the compiler.
- **Bit-reproduction scope.** Confirm the acceptance bar is Stage 1 == Stage 2
  byte-identical *binaries* (or `.ll`), and whether determinism (register/label
  numbering, map iteration order) needs auditing to guarantee it.
- **Transition ownership.** How long does the Go seed live, and is there a point
  where it is deleted vs. kept indefinitely as a trusted bootstrap oracle?
- **Performance.** Is a self-hosted compiler fast enough to be the day-to-day
  build tool, or does it start as a correctness demonstrator while Go stays the
  production compiler? (Common early-self-host reality.)
