# ADR-00817: `-webview=sailfish` moc build integration + un-gating

- **Relations**: `Extends ADR-00816`, `Implements TDD-00146`

- **Date**: 2026-09-09

## Context

[ADR-00816](ADR-00816.md) landed the Sailfish webview shim and proved it
compiles/links against a `-devel` sysroot, but left `-webview=sailfish` gated in
`LocateWebview` because the shim is a Qt `QObject` that needs Qt's **moc** run
over it before clang — a step the embedded-C-source pipeline (compile one `.cc`
straight on the clang line) had no hook for. This ADR wires that hook, un-gates
the flag, and verifies an end-to-end cross-build produces a real aarch64 binary.

## Investigation

`EmbeddedCSources` returns `[]CSource`, each written to a file and appended to the
clang argv by main.go's two build loops and the test build path
(`appendWebview`). No writer had a pre-compile step. The shim `#include`s
`webview_sailfish.moc`, so that file must be generated (by moc) beside the written
source before clang runs. The target's own aarch64 `moc 5.6.3` lives at
`<sysroot>/usr/lib64/qt5/bin/moc`; it emits portable C++ and runs natively on a
same-arch Linux build host — which is the only place a Sailfish webview build
runs, since the cross-OS-webview guard (main.go) already rejects a macOS→Linux
webview build.

Three concrete cross-build breakages surfaced only when driving clang end-to-end
(g++ in the earlier standalone compile had hidden them):

1. **`-Wenum-constexpr-conversion`**: Qt 5.6's `qtypetraits.h` does `T(0) < T(-1)`
   on enums; modern clang makes this a hard error (gcc doesn't diagnose it).
2. **xulrunner absolute symlinks vs `--sysroot`**: the pkg-config `-L…/xulrunner-qt5-devel-<v>/lib`
   is an absolute symlink to `…/sdk/lib` (holding `libxpcomglue.a`), and
   `sdk/lib/libxul.so` is itself an absolute symlink to the runtime dir holding
   the real `libxul.so`. Absolute symlink targets escape the sysroot, so ld
   resolves neither `-lxpcomglue` nor `-lxul`.
3. **libstdc++**: the shim uses `std::map`/`std::string`/`std::function`, so it
   needs `-lstdc++` (the system Linux backend links it too); pkg-config doesn't.

## Decision

- **moc hook**: `CSource.NeedsMoc()` (true for the `webview_sailfish` member) tells
  every writer to run `RunSailfishMoc(mocPath, srcPath, sysroot)` after writing the
  source and before clang. `SailfishMocPath(sysroot)` picks the sysroot's moc (else
  a PATH `moc`). moc links the sysroot's Qt libraries, so `RunSailfishMoc` sets
  `LD_LIBRARY_PATH=<sysroot>/usr/lib64` **on the moc subprocess only** — exporting
  it process-wide made the host clang load the target's libstdc++/libtinfo and
  fail.
- **un-gate**: `LocateWebview("sailfish")` now returns `LocateWebviewSailfish(CrossTargetSysroot())`
  (a clean error when no `--sysroot`). `WebviewSource("sailfish")` already returned
  the real shim.
- **the three fixes**, all in `LocateWebviewSailfish`: append
  `-Wno-enum-constexpr-conversion` to cflags; rewrite each sysroot `-L` that is an
  absolute symlink back into the sysroot, and derive an extra `-L` from each
  `-Wl,-rpath,<abs>` (version-agnostically reaching the runtime dir with the real
  `.so`); append `-lstdc++`.

## Implementation notes

Files: `codegen/llvm/embedded_c.go` (`CSource.NeedsMoc()`, the `webview_sailfish`
member name), `codegen/llvm/webview.go` (un-gate), `codegen/llvm/webview_sailfish.go`
(`SailfishMocPath`, `RunSailfishMoc` with per-subprocess `LD_LIBRARY_PATH`, the
cflag/`-L`/`-lstdc++` fixes), `codegen/llvm/hostclang.go` (`CrossTargetSysroot`),
`main.go` (moc pass in both build loops), `tests/compiler_test.go` (moc pass in
`appendWebview`). Keying the moc pass off the member name avoids widening the many
positional `CSource` literals.

## Side effects discovered

The moc + sysroot-symlink handling is Sailfish-specific but the pattern (a
CSource declaring a pre-compile need; resolving sysroot-absolute symlinks) is
reusable if a future Qt backend (TDD-00144 `qt`) lands.

## Verification

End-to-end in an arm64 Linux container (debian:trixie-slim + clang 19 + lld +
pkg-config), against the real Sailfish 5.1.0.11 `-devel` sysroot from
`docker/Dockerfile.sfos-sysroot`, driving the cross-built linux/arm64 klainmain:

```
klainmain -webview=sailfish --target sfos-aarch64 --sysroot /sfos -o wvapp wvapp.ts
```

(a webview program with `bind`/`html`) produced a valid **aarch64 ELF PIE**
(`file`: `ELF 64-bit LSB pie executable, ARM aarch64`) whose `readelf -d` shows
NEEDED `libsailfishwebengine.so.1`, `libqt5embedwidget.so.1`, `libxul.so`,
`libQt5Qml.so.5` and RUNPATH `/usr/lib64/xulrunner-qt5-91.13.1`. moc ran and
produced `webview_sailfish.moc` (verified present). `go build`, `go vet`, and
`TestE2EWebviewBackendFlag` (the sailfish case now asserts the clean
`requires --sysroot` rejection) green on macOS. The remaining tier is the
on-device windowed run (Wayland/lipstick launch env + the `loadFrameScript` URL
scheme + the CustomEvent bridge), which needs live device iteration.
