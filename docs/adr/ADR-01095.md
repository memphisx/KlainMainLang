# ADR-01095: node:ffi runtime library registry — Node's table order, validation, errors and function objects

- **Relations**: `Implements TDD-00229`, `Extends ADR-01091`, `Supersedes ADR-01091`'s symbol-order decision (its item 5)
- **Date**: 2026-09-23

## Context

After [ADR-01091](ADR-01091.md), probing `node:ffi` beyond the test corpus
against a real `--experimental-ffi` Node (26.10.0) found the library model
itself divergent:

- A bound function was the raw C symbol pointer typed `ptr`: `typeof` said
  `"string"`, `console.log(functions)` printed `{ abs: '' }`, and
  `lib.functions.abs === lib.functions.abs` compared two C strings over code
  memory (SIGBUS).
- `lib.symbols`/`lib.functions` were rebuilt from a compile-time accumulator:
  a runtime-string name was never recorded, conditional registration was
  invisible, a library with nothing registered could not be enumerated
  (`Object.keys` compile error), a re-request with a different signature was
  not diagnosed, and nothing was checked after `close()`.
- ADR-01091's "reverse registration order" was a coincidence of small inputs:
  Node keeps both tables in `std::unordered_map<std::string, …>`
  (`src/node_ffi.h`) and enumerates its iteration order — e.g. registering
  `abs, labs, toupper, fabs, strlen, getenv` enumerates
  `labs strlen getenv fabs toupper abs` on macOS.
- No argument validation: Node's per-type rules (`Argument 0 must be an int32`,
  argument-count errors, `int64` requiring a `bigint`) were missing.

## Investigation

- Node's sources (`src/node_ffi.cc`, `src/ffi/types.cc`, `lib/ffi.js`, 26.10):
  `ResolveSymbol` / `PrepareFunction` / `GetFunction` / `GetFunctions` /
  `GetSymbol` / `Close`, which tables each operation inserts into, the error
  codes (`ERR_FFI_LIBRARY_CLOSED`, `ERR_FFI_CALL_FAILED`,
  `ERR_INVALID_ARG_VALUE`, `ERR_INVALID_ARG_TYPE`), `SignaturesMatch` comparing
  libffi types (aliases and the whole pointer family coincide), the JS wrapper
  caching callables per raw function, `dlopen` closing the library when
  definitions fail, and `ParseFunctionSignature` reading only `return` and
  `arguments` (other keys ignored).
- A validation table from probing every type against 22 values (numbers,
  -0, NaN, bigints, strings, buffers, views, null/undefined, objects): 8–16-bit
  kinds accept `-0`, 32-bit kinds reject it; 64-bit kinds take only an
  in-range `bigint`; floats take any number; the pointer family takes a bigint in
  [0, 2^64) (else "a non-negative pointer bigint"), a string, a buffer/view/
  ArrayBuffer, null or undefined. `bool` validates as `uint8`, and `char` as
  the platform char — `int8` on macOS/arm64, `uint8` on Linux/arm64 (Docker
  `node:26.10.0`).
- Order: re-implementing three hash tables was considered and rejected in
  favour of using the same container Node uses. Node's macOS build uses libc++
  and its Linux build libstdc++ — what clang links on those hosts — so a
  `std::unordered_map<std::string, void*>` reproduces the order by
  construction. A 400-trial randomized differential (1–500 real libc symbol
  names, duplicates) between Node 26.10.0 and a C++ program: identical on
  macOS/arm64 (libc++) and on Linux/arm64 (Docker, g++ 14 libstdc++). Windows
  Node uses the MSVC STL while this toolchain is mingw, so there the order
  needs a port of `<xhash>`.

## Decision

- **Registry** (`ffisrc/ffi_registry.c`): a `KmlFfiLib { handle, path, closed,
  symbols, functions }` whose first two words stay the compiler-visible
  `__kml_handle`/`path` fields; `KmlFfiFn { cfn, sig, rec, lib, name }`. The C
  entry points mirror Node step for step and return status codes that
  `emitFFIStatusCheck` turns into Node's coded errors. `dlopen` uses
  `RTLD_LAZY` (libuv's flag, which also appears in macOS's dlerror text). On
  POSIX a NULL `dlsym` result is a failure only when `dlerror()` reports one
  (uv_dlsym); on Windows a NULL result is.
- **Order container**: `ffisrc/ffi_umap_stl.cc` (real `std::unordered_map`,
  C++, linked with `-lc++`/`-lstdc++`) on POSIX; `ffisrc/ffi_umap_msvc.c` on
  Windows — FNV-1a 64, `hash & mask`, 8 initial buckets, ×8 growth below 512,
  front-of-bucket insertion, list-order rehash splicing.
- **Bound functions are function objects**: an extended tag-12 record
  `{ thunk, entry, arity|1<<62, name, props }` whose `props` bag holds the own
  `pointer` bigint. The registry caches it per name, giving Node's identity
  (`getFunction`/`getFunctions`/`lib.functions` all hand out the same one). The
  thunk is a per-signature-identity dynamic-ABI entry point (`@__kml_ffi_dyn_N`)
  for calls through `any`; direct calls keep the static signature and inline
  the same checks. `fnmeta.c` renders an extended record as
  `[Function: abs] { pointer: 123n }` (collapsing to `[Function]` past depth 2).
- **Checks in Node's order**: arguments evaluated, then closed library, then
  argument count, then each argument (C validators over the boxed value).
  Static signature problems (unknown type, `void` argument, non-array
  `arguments`, non-string type) are Node's runtime TypeErrors at the call, not
  compile errors; only a signature computed at run time stays a compile error.
  `buffer`/`arraybuffer` are valid return types (a pointer bigint).
- **Accumulators**: `lib.symbols` / `getSymbols()` / `lib.functions` /
  `getFunctions()` are fresh null-prototype dynamic objects filled in the
  container's order. The symbols object carries the typings'
  `{ [symbol: string]: bigint }` view (`Type.DynPropTy`, a `bigint | undefined`
  read) so `lib.symbols.x > 0n` compiles in strict mode. `getFunctions(defs)`
  and `dlopen`'s `functions` stay static structs (literal order) flagged
  `IsNullProtoObject`; `dlopen` without definitions returns a frozen empty one.
- **Library value**: `new DynamicLibrary(null).path` is `''`; it renders as
  Node's `DynamicLibrary { path: [Getter], symbols: [Getter] }`.

## Implementation notes

`emit_ffi_runtime.go` (registry wiring, validators, records, thunks,
accumulators), `emit_ffi.go` (open, `ffiParseSignatureRT`, definitions,
methods, direct call), `types.go` (`FFILibReg` removed, `IsNullProtoObject`,
`DynPropTy`), `embedded_c.go` + the test harness's `appendFFIRegistry`. The
dynamic thunk must save/restore `currentRetType` — emitted lazily from inside a
`void` closure, it otherwise leaked `TypeAny` and that closure returned
`ret i64 10`.

`tests/ffi_oracle_test.go` now trusts only a Node ≥ 26.10.0 as the FFI oracle
(`ffiNodeMinVersion`): an older ffi-capable Node on PATH (26.3.0 here) accepts
`-0` for `int32` and hands out a fresh callable per `getFunction`, and silently
failed the expectations.

## Side effects discovered

- A value of `ArrayBuffer`/`DataView` type boxed into `any` still boxes as a
  string pointer (the same family as TDD-00228's handles), so passing one to a
  pointer parameter *through `any`* is not recognized; the direct path handles
  it. BACKLOG.
- Windows: the MSVC order port is unverified until the Windows lane runs the
  FFI oracle.

## Verification

`tests/ffi_test.go`: `TestE2EFFIFunctionObjects`, `TestE2EFFIArgumentValidation`,
`TestE2EFFISignatureAndLifecycleErrors`, `TestE2EFFIAccumulatorShapes`
(fixed expectations checked against Node 26.10.0 by `assertSameAsNodeFFI`),
`TestE2EFFIAccumulatorOrderMatchesNode` (direct comparison, order is
platform-specific). The 400-trial order differential through the compiler
(runtime `getSymbol` names): identical to Node 26.10.0 on macOS/arm64. A
41-line ground-truth probe (validation, errors, identity, closed library,
dlopen shapes): byte-identical to Node on macOS/arm64. Linux verified in Docker
(see the BACKLOG/HANDOVER for the lane result).
