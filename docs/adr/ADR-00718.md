# ADR-00718: Windows Stage 0 — mingw-w64 clang target, stdio binary mode, memmem, LLP64 helper audit

- **Relations**: Implements [TDD-00177](../tdd/TDD-00177.md) (Stage 0)
- **Date**: 2026-09-05

## Context

First session on a Windows 11 x86-64 development machine. Goal: get the pipeline (`klainmain` → LLVM IR → `clang` → native binary) producing a runnable executable at all, and get the test lanes compiling, so the port's real work (TDD-00177 Stages 1–5) can be measured against a pass/fail split rather than one uniform build error.

Starting state: `go build` passed; `go vet ./...` failed on Unix-only `syscall.SysProcAttr{Setpgid}` / `syscall.Kill` in two packages; every E2E test failed before running a single program with `'math.h' file not found`, because LLVM's stock Windows `clang` targets MSVC and ships no C runtime.

## Investigation

- **Toolchain.** The `clang` invocation was `exec.Command("clang", ...)` in 22 places (`main.go`, `codegen/llvm/yoga.go`, one `codegen/llvm` unit test, and every `tests/*_test.go` build helper). Pointing clang at the MSYS2 mingw-w64 UCRT sysroot (`--target=x86_64-w64-mingw32 --sysroot=C:\msys64\ucrt64`) got a hello world to the linker. TDD-00177 records why mingw (toolchain) and Win32-native (semantics) are separate decisions; this ADR only does the toolchain half.
- **`memmem`.** The only link failure after that: `__kml_str_indexof` calls `memmem`, a GNU/BSD extension absent from every Windows C runtime. Declared at `codegen/llvm/runtime_strheader.go` (the former unconditional `declare`).
- **CRLF on stdout.** With the link fixed, the two `codegen/llvm` IR harness tests failed with every output line ending in `\r`. The UCRT opens stdin/stdout/stderr in text mode and rewrites `\n` to `\r\n` on write. Node on Windows does not do this: `console.log("a")` writes the bytes `a\n`, and `process.stdout.write` is byte-exact. Faithful behavior is binary mode on all three descriptors from process start.
- **LLP64.** Windows x86-64 is LLP64: C `long` is 32 bits. The embedded C helpers used `long` at 93 sites. Most are IR-facing, i.e. a signature or a memory store the emitted IR treats as `i64` — for example the string-header length store `*(long *)base = len` in `buffer_codecs.c` and `json_parse.c`, which would write 4 bytes where the IR reads 8. The exceptions are casts into a library's own `long` API (GMP `mpz_set_si`, OpenSSL `d2i_*`, `ERR_get_error`, `strtol`/`sysconf` results), which are correct as written.
- **Line endings.** The fresh clone had `core.autocrlf=true` (Git for Windows' default), so every file was CRLF on disk and `gofmt -l` listed the whole tree. The golden-output tests compare bytes, so this would have failed them silently.
- **Target triple.** The emitted IR carried no `target triple`, so clang warned "overriding the module target triple" on every compile.

## Decision

1. **One clang entry point.** `codegen/llvm/hostclang.go` adds `ClangCommand(args...)`, `HostClangArgs()`, and `HostExeSuffix()`. Every former `exec.Command("clang", ...)` now goes through `ClangCommand`, which on Windows prepends `--target=x86_64-w64-mingw32 --sysroot=<ucrt64>` and elsewhere prepends nothing. The sysroot is `KLAIN_SYSROOT` if set, else `<MSYS2_ROOT>\ucrt64`, else `C:\msys64\ucrt64`, probed for `include/stdio.h`.
2. **Default output gets `.exe`** on Windows when `-o` is not given (`main.go`).
3. **`memmem` is defined in IR on Windows** (`ensureMemmem`), a byte loop over `memcmp`; other hosts keep the libc `declare`. No extra C shim file to plumb through 22 call sites.
4. **stdio in binary mode.** On Windows the emitted `main()` prologue calls `_setmode(fd, _O_BINARY)` for fds 0–2 before anything else, and the module declares `_setmode`. This is a faithfulness decision, not a convenience: Node's byte-exact stdio is the observable behavior.
5. **`target triple = "x86_64-w64-windows-gnu"`** is emitted on Windows only. Linux and macOS IR is unchanged, so their output stays byte-identical and no cross-host verification is needed for this change.
6. **LLP64 audit.** `long` → `int64_t` in the six IR-facing helpers (`buffer_codecs.c`, `embed_assets.c`, `http2.c`, `ipc.c`, `json_parse.c`, `tls.c`), with `<stdint.h>` added where missing. `bigint_gmp.c`, `crypto_openssl.c`, `klainsync.c`, and the one `unsigned long ERR_get_error()` in `tls.c` are left alone as library-typed.
7. **Unix-only test helpers** split by build tag: `tests/procgroup_{unix,windows}_test.go` and `tools/conformance/procgroup_{unix,windows}.go` provide `setProcGroup`/`killProcGroup`. Unix keeps the exact prior behavior (`Setpgid` + group `SIGKILL`); Windows uses `CREATE_NEW_PROCESS_GROUP` and a plain `Process.Kill`, with the known gap that a clang `-cc1` child can outlive its driver on timeout.
8. **`.gitattributes`** with `* text=auto eol=lf` so a Windows clone is LF regardless of `core.autocrlf`. `.gitignore` gains `/klainmain.exe`.

## Implementation notes

- `hostclang.go` lives in `codegen/llvm` rather than `main.go` because the E2E test helpers in `tests/` and the C++ binding build in `yoga.go` need it too; `tests/` already imports the package.
- `ensureMemmem` is guarded by a new `usedMemmem` field on the emitter, matching the other `ensure*` once-only pattern.
- The `codegen/llvm/runtime_websocket_test.go` harness hand-writes its own `main()` and so never gets the binary-mode prologue; it normalizes `\r\n` on Windows itself rather than teaching each hand-written `main` about `_setmode`.
- `gofmt` on this machine (Go 1.27) reformats struct field alignment in `emitter.go` and several test files that older gofmt accepted. Those files were left as-is to keep the diff to the actual change; a separate formatting-only commit can normalize them.

## Side effects discovered

- `embed_assets.c` includes `sys/socket.h` (it serves the embedded SPA over a socket), so it does not compile on Windows yet — a Stage 2 item, expected.
- The `--static`, `-package`, and `-crypto=commoncrypto` flags already refuse non-Linux/non-macOS hosts with their existing messages; nothing new needed.
- `go test ./tests` on Windows is the first time the E2E suite has been measured off Linux/macOS; the failure histogram is recorded below and drives the ordering of TDD-00177's later stages.

## Verification

Windows 11 x86-64 (mingw-w64 UCRT sysroot via MSYS2, LLVM 22.1.8 clang, Go 1.27):

- `go build -o klainmain.exe .` and `go vet ./...` pass. `GOOS=linux go vet ./tests ./tools/conformance` also passes, confirming the Unix side of the build-tag split still compiles.
- Hello world: `klainmain.exe hello.ts` produces `hello.exe` with no clang warning; `od -c` on its output shows the trailing byte is `\n`, not `\r\n`.
- `go test ./codegen/llvm ./lexer ./parser ./jsdoc ./klmpm ./tools/conformance`: all pass.
- `go test ./tests`: see the histogram below.

**The STATUS_BAD_STACK cluster was a real ABI bug, fixed in this ADR.** On mingw-w64 x86-64, C's `setjmp(buf)` is a macro for `_setjmp(buf, NULL)`: the second argument is the frame `longjmp` will SEH-unwind to, and NULL means "don't unwind". The IR called a bare one-argument `setjmp`, so that register held garbage and the matching `longjmp` faulted. Fix: `setjmpCall(buf)` in `runtime_exceptions.go` emits `call i32 @_setjmp(ptr buf, ptr null)` on Windows and the libc `setjmp` elsewhere; all ten emission sites (eight `Sprintf` sites, plus the raw templates in `emit_promise_then.go` and `runtime_task.go`) go through it, and the declaration follows. The 512-byte jmpbuf slots comfortably hold Win64's 256-byte `jmp_buf`. Re-running the 128 exception/assert/promise/async tests after the fix: 0 STATUS_BAD_STACK (was 72 in the full lane), 50 pass, and the remaining 78 failures are all in the table's libcurl/errno/fork rows.

Open bug from this run: the four `Object.freeze` tests and `TestE2EJSONParseArrayField` die with an access violation (`0xC0000005`). Not investigated here; tracked as a Stage 1 item in TDD-00177.

### After installing the optional libraries

The 292-test `-lcurl` row and the 12-test sqlite row were pure install gaps. `pacman -S mingw-w64-ucrt-x86_64-{curl,sqlite3,pcre2,libtommath,openssl,nghttp2,gc,zlib}` provides all of them for the mingw target (winget has no equivalent: it distributes applications, not development libraries). The linker prefers each package's DLL import library, so a compiled binary needs `C:\msys64\ucrt64\bin` on PATH at run time or it exits `0xC0000135`; static-vs-DLL linking is a Stage 5 decision. Re-running the library-dependent groups with that PATH:

|---|---|---|---|

So after Stage 0 plus the library install, the failure set is no longer about the build environment. It is the platform layer TDD-00177 describes.

`make conformance` was **not** run: the Test262 corpus is not fetched on this machine yet and the runner is Unix-shaped (Stage 5 wires it up). Recorded here rather than silently skipped.
