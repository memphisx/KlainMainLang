# ADR-00772: static libcurl under `--static` on Windows; dynamic-by-default is the cross-platform policy

- **Relations**: completes [ADR-00771](ADR-00771.md) (the `--static` non-system-lib story on Windows) with the networking chain; revisits the linking policy the README describes (dynamic default + `--static` for scratch images)
- **Date**: 2026-09-07

## Context

Two questions surfaced while making Windows binaries self-contained:

1. **The networking chain.** A `fetch`/`http`/`tls`/WebSocket program (including the
   `loadtest` showcase app) links `libcurl` — and, when nothing is done, imports
   `libcurl-4.dll` (and, transitively, its ssl/nghttp2/… DLLs). `--static`
   ([ADR-00771](ADR-00771.md)) covered the C++ runtime but not curl, so a
   networking program could not be a single binary on Windows.
2. **The policy.** An earlier iteration made CLI/TUI binaries *static by default*
   on Windows. That was the wrong call: it is **inconsistent** with Mac/Linux
   (which link dynamically by default and gate full-static behind `--static`), and
   the justification ("Windows has no system libs") over-generalized — dynamic
   linking assumes the target has the libraries on *every* platform (a Linux
   binary needs `libcurl.so` on the target; a musl/Alpine box lacks glibc). The
   honest principle is: **dynamically link what the target OS guarantees present
   (its system libc — glibc/libSystem/UCRT); statically link the rest only when
   the user asks for a self-contained build.**

## Investigation

Static libcurl on mingw is often blocked because a Debian/Ubuntu build drags an
unresolved MIT krb5/gssapi archive chain. **On the ucrt64 sysroot it does not:**
`curl-config --features` shows `Kerberos`/`SPNEGO`/`SSPI` — curl uses Windows
**SSPI** (`secur32`), not MIT krb5, so there is no external krb5 chain to resolve.
`pkg-config --static --libs libcurl` yields the full chain, all present as static
archives: curl, ssl, crypto, z, ssh2, brotli{dec,common}, zstd, nghttp2,
ngtcp2{,_crypto_ossl}, nghttp3, psl, unistring, iconv, idn2 — plus Windows system
import libs (ws2_32/secur32/crypt32/wldap32/bcrypt/iphlpapi/gdi32). A minimal C
program linked with this chain runs with only `System32` on `PATH` and imports no
curl/ssl/nghttp2 DLL.

The emitter declares curl symbols directly in the IR (no `dllimport`), so no
`CURL_STATICLIB` define is needed. One collision: static `libcurl.a` pulls
`libws2_32.a`'s socket symbols (`connect`/`bind`/`getaddrinfo`/…) and the static
CRT's `strerror`, which the win32io/win32fs shims also define — resolved with
`--allow-multiple-definition` (the shim's Winsock wrappers win, first-definition;
curl's socket calls then route through the shim, verified functional).

## Decision

- **Policy: dynamic-by-default on all platforms; `--static` is the opt-in
  self-contained build, consistent across Linux/macOS/Windows.** No platform
  embeds libraries by default. The static-by-default Windows exception is removed.
- **`winCurlStaticChain`** (`hostclang.go`) emits the full static chain under
  `--static` on Windows: the mingw archives forced static in one comma-joined
  `-Wl,-Bstatic,--start-group,…,--end-group,-Bdynamic` group (partition-safe;
  `--start-group` for the circular ssl/crypto refs), the Windows system import
  libs dynamic, and `-Wl,--allow-multiple-definition` for the shim collisions.
  `LinkLibFlags("curl")` returns this under `--static`, `-lcurl` otherwise.
- **`--static` semantics per platform** (same user-facing promise — "no non-system
  deps"): Linux = full static incl. glibc (`-static`, scratch/distroless-ready);
  Windows = static non-system libs, UCRT/Win32 dynamic (this ADR + ADR-00771);
  macOS = rejected for now (no static libSystem) — feature-lib-static is future
  work. Showcase apps are built `--static` (`make apps`); the website guides teach
  `--static` for the distributable single binary.
- **Distribution of dynamic builds** (the default) is a packaging concern, tracked
  separately: on Mac/Linux you declare deps (Homebrew/apt); on Windows you bundle
  the DLLs beside the `.exe` or, where licensing forbids redistribution, the
  installer/docs redirect the user to the vendor's download.

## Verification

- **Windows 11 native**: a minimal C curl program linked with the chain runs off
  `PATH` (`libcurl/8.20.0 OpenSSL/3.6.3 …`) with no curl DLLs. `--static`
  `loadtest` (TUI + HTTP) → **zero** non-stock DLLs. The default build imports
  `libcurl-4.dll` as expected. The `Fetch`/`Http` E2E tests pass with curl
  statically linked and routed through the Winsock shim (real HTTP: status/text/
  JSON, redirects, custom methods+headers+body, abort/timeout) — proving static
  curl is functional, not just linkable. (Static-curl binaries are ~12MB and link
  slower; the networking suite needs a raised `go test -timeout`.)
- `go build`, `go vet ./codegen/...` clean. Docker Linux + conformance run at
  delivery; the Linux/default paths are unchanged (all static gating is
  Windows+`--static`).
