# ADR-00707: -optimize-memory — value-returned small tuples (Stage 3, TDD-00134 complete)

- **Relations**: Extends ADR-00702, ADR-00704, ADR-00705; Implements TDD-00134 (Stage 3, final part)
- **Date**: 2026-09-04

## Context

The idiomatic Go-style error pattern — `function f(): [T, Error] { … }` /
`const [v, err] = f()` — paid a heap allocation per call: a tuple is a
heap-`calloc`'d struct returned by pointer, and a returned literal *escapes*
by definition, so Stage 1's stack planner could never help it. TDD-00134
Stage 3 calls for returning small tuples **by value** as an LLVM aggregate,
which clang passes in registers (both x86-64 SysV and arm64 AAPCS pass a
≤16-byte aggregate in two registers).

## Investigation

- Precedent: `LLVMRetType()` already returns aggregates for two return
  shapes — arrays (`{ptr, i64}`) and nullable scalars (`{i1, T}`) — so the
  aggregate-return plumbing (definition line, call line, both driven by
  `FuncSig.RetType`) was known to hold up. The tuple case slots in as a
  third branch keyed on a new `Type.TupleByVal` flag.
- The one authoritative ABI record is the registered `FuncSig`: the function
  definition (`emitFunctionDeclAs` reads `retType := sig.RetType`), every
  direct call (`emitCallToFuncSig` reads `sig.RetType`), and the body's
  `return` lowering (`e.currentRetType` is set from the same copy) — so a
  flag set once on `FuncSig.RetType` keeps all three sides consistent by
  construction.
- The hazard is **indirect calls**: a function referenced as a value is
  invoked through its function-*type* annotation, which knows nothing of a
  per-function ABI flag — a mismatched `call ptr` against an
  aggregate-returning definition is garbage at runtime. So a program-wide
  scan (the established reflection-walk pattern of `collectFinRegNames` /
  `thisEscapesFn`) disqualifies any candidate whose name appears anywhere
  other than as a direct call's callee.
- The second hazard is the call-site result outliving the frame: spilling
  the returned aggregate to an *alloca* would dangle if the bound tuple
  pointer escaped (pushed into an outer array, returned through a
  pointer-ABI caller). The spill therefore goes to the **heap** — matching
  today's allocation count on that path exactly — and only the direct
  destructuring consumer gets the allocation-free extractvalue path, which
  is the pattern the TDD names as the point.
- Found in passing: an async function returning `Promise<[T, U]>` emitted a
  tuple-literal `return` as an **array** literal (`{ptr, i64}` aggregate
  stored into the `ptr` promise slot — invalid IR, every mode, pre-existing).
  The async return path emitted the value without a type hint; the sync path
  already hinted with `currentRetType`.

## Decision

Under `-optimize-memory`, a top-level function returns its tuple by value
when all of:

- the declared return type is a tuple of 1–2 fields, each stored as a plain
  scalar IR word (`i64`/`double`/`ptr`/`i1` — no array `{ptr,i64}` slots,
  no nullable-scalar `{i1,T}` slots, no `any`/`unknown`);
- the function is not `async` (both variants) and not a generator;
- the function's name is never used as a value anywhere in the program
  (only ever a direct call's callee).

Lowering:

- `return [a, b]` builds the aggregate with `insertvalue` — zero
  allocation. Any other returned expression evaluates to the usual tuple
  pointer and the aggregate is loaded from it. Bare `return;` yields
  `zeroinitializer` (the `ptr null` the pointer ABI would produce is an IR
  type mismatch here).
- `const [v, err] = f()` destructures the raw aggregate with
  `extractvalue` — also allocation-free. The handshake is a one-shot
  `wantTupleAggregate` emitter flag set by the destructuring path and
  grab-and-cleared at `emitCallToFuncSig` entry, so a nested call inside an
  argument expression can never observe it.
- Every other consumer receives the aggregate spilled to a fresh heap
  `malloc` — semantics and allocation count identical to the pointer ABI.

## Implementation notes

- `codegen/llvm/emit_tuple_byval.go` (new): `tupleByValEligible`,
  `planTupleByValReturns` (runs in `EmitProgram` after
  `classifyAsyncSuspension` — `MaySuspend` excludes — and before any body
  or call is emitted), `collectFnValueRefs` (reflection walk),
  `emitTupleByValReturn`, `spillTupleAggregate`, `unpackTupleAggregate`.
- `types.go`: `Type.TupleByVal` + the `LLVMRetType()` branch.
- `emit_stmts.go`: the `emitReturn` by-value branch (+ bare-`return;`
  zeroinitializer case) and the in-passing async-return hint fix.
- `emit_call.go`: entry grab of `wantTupleAggregate`; keep-or-spill at the
  call result.
- `emit_arrays_core.go`: the destructuring fast path (direct
  identifier-callee calls only, shadowing-checked).
- Generic instantiations register their sigs after the plan pass and are
  never flagged — they keep the pointer ABI; generators' return types are
  not tuples, so they fall out naturally.

## Side effects discovered

- Async tuple-literal returns were invalid IR in every mode (fixed here, see
  Investigation; regression test `TestE2EAsyncTupleReturn`).
- A top-level `const alias: (n: number) => [number, number] = pair` fails
  with "undefined function or closure" in every mode — a pre-existing
  top-level function-alias limitation unrelated to this change (the same
  binding inside a function body works and correctly disqualifies the
  by-value ABI).

## Verification

- `tests/tuple_byval_test.go` (new): behavioral equivalence with and without
  the flag (literal returns, named-tuple returns, recursion, forwarding
  `return g()`, whole-tuple binding via the spill path, holes); IR-shape
  assertions (aggregate signatures, insertvalue/extractvalue); exclusions
  (3-field tuple, function-used-as-value) keep `define ptr`; no-flag mode
  emits no aggregate tuple signatures; the async tuple-return fix.
