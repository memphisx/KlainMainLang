# ADR-00072: `http.listen` — request headers, query string, request body, response headers

- **Relations**: Extends [ADR-00048](ADR-00048.md), [ADR-00049](ADR-00049.md)
- **Date**: 2026-07-28

## Context

`http.listen` ([TDD-00004](../tdd/TDD-00004.md), ADR-00048) only ever parsed the request *line* — `req.method`/`req.path` — and only read `status`/`body` off a handler's response. Per `STATUS.md`'s Roadmap and this project's stated #1 priority bucket (REST API interaction), the remaining gap was request headers, query-string parsing, the request body, and response headers beyond `status`/`body`. This closes all four. Graceful shutdown (`SIGINT`/`SIGTERM`) is explicitly out of scope — it needs POSIX signal handling, infrastructure that doesn't exist anywhere in this compiler, and is a distinct piece of design work best scoped on its own later.

## Investigation

Read `codegen/llvm/emit_http.go` in full. Confirmed the read path was a genuinely fixed one-shot `read(fd, buf, 8191)` at a **fixed offset (always byte 0)** — a retry after an `EAGAIN`-triggered `swapcontext` yield fully overwrote whatever a previous partial read had returned, with no accumulation across multiple `read()` calls at all. `RequestType()` (`types.go`) was a plain `ObjectType`, confirmed only 3 references to it/`"Request"` in the whole codebase (the definition, `ResolveTypeName`'s dispatch case, `buildHTTPDispatcher`'s construction), so extending its field list was fully contained.

`Map<string,string>` (`MapType(TypePtr, TypePtr)`) was the natural type for `headers`/`query` — confirmed building one programmatically at codegen time (not via user `new Map()` syntax) was already established precedent (`emit_call.go`'s `emitConsoleCountMapEnsure`), and confirmed reading it from user code needed zero new dispatch (`resolveMapOrSetForCall`'s generic arbitrary-expression branch already handles any Map-typed field access).

Checked for existing reusable string-parsing primitives before writing anything new: `ensureStringSplit()`'s `@__kml_split` (splits on every occurrence of a separator, and — confirmed by reading its IR — always returns independent malloc'd copies per part, never aliases into the source buffer, which matters once the source buffer can later move via `realloc`), `ensureStringTrim()`, `ensureStringToLower()`. Found no "split on first occurrence only" primitive (needed for `Key: Value` header lines and `path?query`, where the value/query itself may legally contain the separator again) — this was the one genuinely new low-level primitive needed (`__kml_split_first`).

**Found, while designing query-string parsing, that `decodeURIComponent`/`encodeURIComponent` already exist in this compiler** (`emit_call.go`, `runtime.go`'s `ensurePercentDecode`/`ensurePercentEncode`) — an incorrect assumption in an earlier planning pass (recorded, then corrected, in this same investigation) had concluded no percent-decoding primitive existed. Query keys/values are percent-decoded via the same `@__kml_decode_uri_component` `decodeURIComponent` itself calls, rather than shipping raw/undecoded values as a documented V1 gap.

**Found a real, pre-existing bug while writing the example** for this feature (`examples/http/http_server.ts`): a ternary expression using a chained-member-expression Map field as one branch (`req.query.has('name') ? req.query.get('name') : 'stranger'`) produced an LLVM IR type mismatch at `clang` link time ("`%tN` defined with type 'ptr' but expected 'i64'"). Root-caused to `inferExprType`'s `CallExpression` case (`emit_exprs.go`): its Map/Set method-call type resolution (`.get`/`.has`/`.keys`/etc.) only ever computed the receiver's type by looking up `mem.Object` as a bare `*ast.Identifier` via `e.lookup()` — with no fallback for a receiver that's itself a more complex expression (`req.query`, a `MemberExpression`, not an identifier). A plain local `Map<string,string>` variable (`let q = req.query; q.get(...)`) worked fine, proving the bug was specifically about the identifier-only lookup, not Map/ternary type inference generally. The same function already had exactly this identifier-or-`inferExprType`-fallback pattern for the `.size` property a few lines above, just not for method calls.

## Decision

**Request side** (`RequestType()`, `types.go`): added `query`/`headers` (both `Map<string,string>`) and `body` (`string`) fields, alongside the existing `method`/`path`.

**New `runtime.go` primitives**: `@__kml_split_first(ptr s, ptr sep) -> {ptr, ptr}` (first-occurrence-only split — the one new low-level primitive); `@__kml_http_parse_headers(ptr headerBlock, ptr map)` (splits on `"\r\n"`, then each line on first `": "`, lowercases the key, trims the value); `@__kml_http_parse_query(ptr q, ptr map)` (splits on `"&"`, then each pair on first `"="`, percent-decodes both key and value, a bare flag with no `"="` stores an empty string); `@__kml_http_serialize_headers(ptr map) -> ptr` (two-pass size-then-fill, building the response's optional extra header block).

**`__kml_http_send_response`** gained a 4th parameter, `ptr extraHeaders` — `""` when the handler's return type has no `headers` field (byte-identical output to before this feature), or `@__kml_http_serialize_headers`'s result otherwise.

**`buildHTTPDispatcher`'s read loop** (`emit_http.go`) was redesigned around an accumulating, growable buffer rather than one fixed-size one-shot read: new entry-block `alloca`s (`bufPtr`/`bufCap`/`totalRead`/`headersParsed`/`headerEnd`/`contentLen`/`headersMap`) replace the old single loaded-once `buf` SSA value. These live as plain `alloca`s (not connection-slot fields) specifically because `buildHTTPDispatcher`'s `entry:` block is the fiber's *only* invocation (a `makecontext` target, never re-entered per event-loop tick) — its own stack frame, and everything on it, survives any number of internal `swapcontext` suspends exactly like the pre-existing `fdPtr`/`ctxPtrSlot` GEPs already relied on. New labels: `growL`/`doGrowL` (doubles `bufCap` via `realloc`, capped at 10MiB — `maxHTTPRequestBytes` — against a hostile/malformed `Content-Length` or a client that never sends the blank-line terminator, aborting via the existing `noReqL` path rather than growing without bound), `haveCapL` (issues `read()` at the buffer's current end offset), `accumulateL` (extends `totalRead`, re-terminates), `checkCompleteL`/`findHeaderEndL`/`gotHeaderEndL` (first time only: finds `"\r\n\r\n"`, parses every header line, extracts `Content-Length` via `has`+`get`+`atoll`), `checkBodyCompleteL` (loops back to `readLoopL` until `Content-Length` bytes are actually present past the header block). `checkErrL`/`checkEagainL`/`doYieldL`/`noReqL` needed **zero changes** — `doYieldL`'s existing `br label %readLoopL` was already the correct resume point once `readLoopL` itself became offset-aware.

**Response headers**: `emitHTTPListen` validates an optional `headers` field is exactly `Map<string,string>` (via a new `isPlainStringType` helper, matching the same many-flag-exclusion idiom `emit_memory.go`'s `freeResolvedPointer` already uses for its own type switch) — required to check the *type*, not just field existence, since (unlike `status`/`body`, which just get coerced) treating a wrong-shaped value as a `Map` and walking its entries at runtime would corrupt memory rather than just misbehave. Absent: zero extra branches, `extraHeadersRef` is directly the interned empty string. Present: GEP+load, branch on non-null, serialize or use empty string.

**`inferExprType` fix**: unified the identifier-lookup and `inferExprType`-fallback paths for Map/Set method-call type resolution, so a chained member expression (any expression, not just a bare identifier) whose type is `Map`/`Set` resolves correctly — same fix shape as the pre-existing `.size` fallback a few lines above.

## Implementation notes

Files touched: `codegen/llvm/types.go` (`RequestType()`), `codegen/llvm/runtime.go` (4 new helpers, `ensureHTTPRuntime`'s dependency list, `__kml_http_send_response`'s signature/format, a stale doc-comment correction), `codegen/llvm/emit_http.go` (read-loop redesign, response-headers handling, new `isPlainStringType`/`maxHTTPRequestBytes`), `codegen/llvm/emit_exprs.go` (`inferExprType`'s Map/Set method-call fallback fix), `tests/http_test.go` (new tests), `tests/collections_test.go` (regression test for the `inferExprType` fix), `examples/http/http_server.ts` (extended to demonstrate the new fields).

**A real SSA-dominance bug was caught and fixed before this ever reached `clang`**: `growL`'s "too big" abort path originally branched straight to `noReqL` without ever passing through `haveCapL`, where `fd32` (needed by `noReqL`'s `close()` call) used to be computed — an LLVM IR value must dominate every use, and this path didn't dominate that one. Fixed by hoisting the `fd64`/`fd32` load+trunc to the top of `readLoopL` itself (executed identically every time that label is entered, so purely a repositioning, not a behavior change), which dominates every downstream label including `growL`'s early-exit.

Header-block parsing works by NUL-terminating the buffer at the *start* of the found `"\r\n\r\n"` (not consuming it), then separately `strstr`-ing for the request line's own first `"\r\n"` to find where the header block itself begins — so `@__kml_http_parse_headers` never sees the request line as a spurious first "header."

## Side effects discovered

None new beyond what was already fixed in the same pass (the `inferExprType`/ternary bug above) or already tracked (`STATUS.md`'s graceful-shutdown gap, unaffected by this change). Malformed header lines (no `": "`) are silently skipped, not rejected — a deliberate, documented choice matching this codepath's existing tolerance for malformed input elsewhere. No HTTP keep-alive/pipelining (`Connection: close` always sent, unchanged from before) — any bytes beyond one logical request are simply never looked at.

## Verification

- `go build ./...`, `go vet ./...` clean.
- Manual `curl` smoke tests against a running server: confirmed `req.path` correctly excludes a `?a=1&b=2` query string (the pre-existing bug this also fixes); confirmed `req.query.get()`/`req.headers.get()` (mixed-case sent, lowercase looked up)/`req.body` all read correctly for a `POST` with headers, query string, and a JSON body; confirmed response `headers` (`X-Custom-Header`, `Content-Type`) reach the raw socket response correctly formatted, with the existing `Content-Length`/`Connection: close` unaffected.
- **The critical case**: a 50KB body sent both in bulk and rate-limited (`curl --limit-rate`, forcing several genuinely separate, small `read()` syscalls server-side rather than one big one) both round-tripped correctly — direct proof the buffer-growth/accumulation state machine actually works across multiple reads, not just the common single-read case.
- `tests/http_test.go`: 10 new tests (headers case-insensitive lookup, query parsing including a bare flag and percent-decoding, no-query-gives-empty-map, request body, no-body-gives-empty-string, a 200KB body forcing buffer growth, a 100KB body verified byte-for-byte for content integrity — not just length, response headers, no-response-headers-is-unchanged, wrong-typed-`headers`-field-rejected) — all passing alongside the 14 pre-existing HTTP tests (including the 30,000-request stack-leak regression and the `-mm=gc` concurrent-fiber test from ADR-00071), zero regressions.
- `tests/collections_test.go`: new regression test for the `inferExprType` fix (a ternary over `.has()`/`.get()` on a chained Map field access).
- `go test ./...` full suite green; `make examples` 62/62 passing, including the extended `examples/http/http_server.ts` (verified manually with `curl` against `/hello?name=world` with a custom header, and `/echo` with a POST body).
