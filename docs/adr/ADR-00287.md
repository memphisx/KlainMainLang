# ADR-00287: `parseInt`/`parseFloat` return a double and produce real `NaN`; `charCodeAt`/`codePointAt` bounds-checked with `NaN` out of range

- **Relations**: Same 2026-08-11 audit cluster as [ADR-00284](ADR-00284.md)–[ADR-00286](ADR-00286.md); charCodeAt's byte-space semantics per [ADR-00166](ADR-00166.md) unchanged
- **Date**: 2026-08-22

## Context

`parseInt` returned a bare `strtoll` i64 (so `parseInt("abc")` was `0`,
never `NaN`); `parseFloat` had the same no-conversion hole through `strtod`.
`.charCodeAt()`/`.codePointAt()` did an unchecked byte load, reading whatever
memory sat past the string for an out-of-range index — the audit's
memory-unsafety finding.

## Decision

- **`parseInt` returns a double** (as real JS — beyond 2^53 JS's own
  parseInt loses precision the same way): `strtoll` runs with an `endptr`
  slot; `endptr == input` (no digits consumed — strtoll skips leading
  whitespace itself, like JS) selects NaN (`0x7FF8000000000000`), otherwise
  the parsed value via `sitofp`. **`parseFloat`** gets the same endptr
  no-conversion → NaN select. Inference for both (bare and `Number.`-forms)
  becomes `TypeF64`.
- **`charCodeAt`** computes `strlen` and bounds-checks the index; out of
  range (negative or ≥ length) returns NaN, in range the byte value — as a
  double, since only a double can carry the NaN. The load itself is clamped
  to index 0 when out of range (still inside the allocation) and its value
  discarded, so no wild read ever happens. `codePointAt` stays charCodeAt's
  byte-space alias.

## Residual caveats (disclosed, not fixed here)

- `parseInt("0x10")` with no explicit radix is `0` here (strtoll base 10
  stops at the `x`), where JS auto-detects hex → `16`. Radix values outside
  2–36 are strtoll's behavior, not JS's NaN.
- `parseFloat` inherits strtod extras: `parseFloat("inf")` parses (JS: NaN
  — JS only accepts the full word `Infinity`, which strtod also accepts)
  and hex float syntax parses.
- `codePointAt` out of range gives NaN, where real JS gives `undefined` —
  this compiler has no `undefined` representation for a numeric result
  (nearest faithful value; previously it was garbage memory).

## Verification

- Node-diff (node v26.3.0, byte-identical): `parseInt("abc")`/`("")`/
  `("12px")`/`("  42")`, `parseFloat("abc")`/`("3.5kg")`/`("  .5")`,
  `Number.isNaN(parseInt("abc"))`, `"abc".charCodeAt(3)`/`(-1)`/`(100)` →
  `NaN`, in-range values and arithmetic on them (`parseInt("42") + 1`,
  `String.fromCharCode("A".charCodeAt(0) + 1)`).
- New E2E: `TestE2EParseAndCharCodeNaN` (tests/exprs_test.go); full suite
  green.
