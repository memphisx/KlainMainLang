# ADR-00812: Harbour private-lib bundling for bdw-gc (`-mm=gc`)

- **Relations**: `Extends ADR-00810`, `Implements TDD-00146`

- **Date**: 2026-09-09

## Context

ADR-00810 gave `-package=rpm:harbour` a private-lib bundling path: link
libraries that are not on the Sailfish Harbour allowed-libraries list are copied
out of the sysroot into `/usr/share/harbour-<name>/lib` and the binary is linked
with an rpath to that dir, so a store app carries them itself. It shipped
covering `pcre2` (RegExp). It explicitly left one case open: the
Boehm-Demers-Weiser collector (bdw-gc / libgc) used under `-mm=gc`, which is
also off the allowed list but reaches the link a different way, so the ADR-00810
filter never saw it.

## Investigation

The bundling filter, `harbourLibsToBundle`, works over `em.LinkLibs()` — the set
recorded by `requireLink` (`packaging_rpm.go:40`). Feature libraries like pcre2
and curl land there. bdw-gc does not: `-mm=gc` links it via `LocateGC()`
(`codegen/llvm/gclocate.go`), which returns a bare `-lgc`/pkg-config flag
appended directly to the clang argv in `main.go` (~line 246), never touching
`requireLink`. So `gc` was absent from `LinkLibs()`, and both the rpath decision
(`main.go:309`) and the `writeRPM` bundle list (`main.go:425`) skipped it — a
`-mm=gc` Harbour build linked libgc as a *system* dependency that the device
does not carry (the device probe of the Xperia 10 II found no libgc among the
system libraries; it is not in the base Sailfish image).

The SONAME resolver `findSonameInSysroot` is already generic — it globs
`lib<name>.so.*` under the sysroot lib dirs — so the only missing piece was
getting `gc` into the bundle list. Its SONAME is `libgc.so.N`, so the resolver
key is `"gc"`.

## Decision

Fold bdw-gc into the Harbour bundle set based on the `-mm=gc` flag rather than
on `LinkLibs()`. `harbourLibsToBundle(linkLibs, gcMode)` gains a `gcMode bool`;
when set it appends `"gc"` (de-duplicated) after the `requireLink`-derived libs.
Both call sites in `main.go` pass `*mm == "gc"`. The rest of the pipeline —
rpath at link time, SONAME copy into `SOURCES`, `%install`/`%files` under the
private lib dir — is the ADR-00810 pcre2 path unchanged.

A `-mm=gc` Harbour build therefore needs libgc present in the `--sysroot` (with
a `libgc.so` dev symlink for `-lgc` to resolve), exactly as pcre2 does; a proper
Sailfish `gc-devel` target provides it. This is faithful to the Harbour model:
the app ships its own copy of a non-system library rather than assuming one.

## Verification

- `packaging_rpm_test.go`: `TestHarbourLibsToBundleGC` (gc folded in only under
  `gcMode`, once, alongside/without feature libs) and `TestWriteRPMBundlesGC`
  (a fabricated sysroot with `libgc.so.1` → staged into `SOURCES`, installed
  under `/usr/share/harbour-<name>/lib` in the spec).
- End-to-end on the arm64 Docker lane (native, not emulated): a `-mm=gc` program
  cross-built `--target sfos-aarch64 --sysroot=<exported 5.1.0.11 rootfs>
  -package=rpm:harbour` produced `harbour-gcgreeter-1.0.0-1.aarch64.rpm`
  containing `/usr/share/harbour-gcgreeter/lib/libgc.so.1`, with the binary
  carrying `RUNPATH /usr/share/harbour-gcgreeter/lib` resolving `NEEDED
  libgc.so.1` (readelf-confirmed). The sysroot's libgc was a stand-in staged
  from Debian trixie (bdw-gc is not in the base Sailfish image), so this
  exercises the full link/rpath/package flow; the specific Sailfish libgc ABI
  and an on-device install were not exercised. (Mac + arm64 Docker.)

## Consequences

The last non-allowlisted link library is now bundled, so `-mm=gc` Harbour
packages are self-contained. Any future library linked outside `requireLink`
(as LocateGC-style flags) will need the same explicit fold-in; the pattern is
now established.
