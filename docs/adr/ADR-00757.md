# ADR-00757: `fs.watch` Windows backend — ReadDirectoryChangesW + a loop wakeup socket (TDD-00181 Stage 2)

- **Relations**: Implements [TDD-00181](../tdd/TDD-00181.md) Stage 2; extends [ADR-00756](ADR-00756.md) (the FSWatcher subsystem + Linux backend), [ADR-00719](ADR-00719.md) (the Win32 shim + its socket-table `select`), [ADR-00737](ADR-00737.md) (the `socketpair` used for the wakeup channel)
- **Date**: 2026-09-07

## Context

[ADR-00756](ADR-00756.md) shipped the `fs.watch` subsystem with the Linux inotify backend, where the change source is a readable fd that drops into the loop's `select()` directly. Windows has no such fd: `ReadDirectoryChangesW` runs against a directory `HANDLE`, and the shim's `select()` waits only on sockets. Worse, the loop had **no wakeup channel** for a background thread to interrupt a blocking `select()` (the [TDD-00180](../tdd/TDD-00180.md) §1 gap). This ADR is the Windows backend, which builds that wakeup channel.

## Decision

A C backend (`win32src/win32fswatch.c`) driven by IR hooks (`emitFsWatchWindows` in `runtime_fswatch.go`).

- **Watcher thread.** Each `fs.watch` opens the target's directory (`FILE_LIST_DIRECTORY` + `FILE_FLAG_BACKUP_SEMANTICS`) and spawns a thread blocking in `ReadDirectoryChangesW`. A file watch watches the parent directory and filters records by the basename (case-insensitive); a directory watch takes them all. `FILE_ACTION_ADDED`/`REMOVED`/`RENAMED_*` map to `'rename'`, `FILE_ACTION_MODIFIED` to `'change'`.
- **Wakeup socket.** `fsw_init` creates a loopback `socketpair` (the shim's, [ADR-00737](ADR-00737.md)); the read end is a shim socket fd the loop's `select()` understands. On each change the thread pushes a `(watcher, kind, name)` record onto a `CRITICAL_SECTION`-guarded queue and writes one byte to the write end, waking `select()`. The read end is made non-blocking so the drain loop cannot stall.
- **Loop hooks.** `__kml_fswatch_fdset_add` adds the wakeup socket's read fd (from `__kml_fswatch_win_wakefd`) while any watcher is open; `__kml_fswatch_dispatch` calls `__kml_fswatch_win_next` in a loop, mapping each record back to its `FSWatcher` (the C context pointer is stored in the handle's field 0) and firing the listener with `(eventType, filename)`; when the queue drains, `next` empties the wakeup socket. `keepalive`/`on` are as Linux; `close` calls `__kml_fswatch_win_stop`, which `CancelIoEx`es the blocking read, joins the thread, and closes the handle.

The wakeup socket is deliberately generic — it is the loop wakeup primitive the §1 audit and an eventual IOCP reactor both want, built fs.watch-first but reusable.

## Implementation notes

- The C backend calls the shim's POSIX-named `socketpair`/`read`/`write`/`close`/`fcntl` over its fd table (declared `extern`), so the wakeup fd is a first-class loop fd rather than a raw `SOCKET`.
- `win32fswatch.c` is registered in `hostclang_win32shim.go`'s embed + object list, compiled and cached like the other shim objects.
- The `FSWatcher` struct/registry and the JS surface are shared with the Linux backend verbatim; only `__kml_fs_watch`/`_dispatch`/`_close` differ (a thread+queue+socket instead of a bare inotify fd).

## Side effects discovered

None. The Windows loop hooks are inert (no-op stubs) unless a program calls `fs.watch`, so existing loop-driven programs are unaffected; verified the worker/timer/HTTP-listen/fs suites still pass on Windows 11.

## Verification

- `TestE2EFsWatchChange` (`tests/fs_test.go`), now un-gated on Windows, passes **natively on Windows 11**: a `ReadDirectoryChangesW` modification is delivered as `event=change name=fwtest.txt`; a directory create as `evt=rename name=created.txt`; both exit 0 (the watcher thread stops and the loop terminates on `close()`). The same test still passes on Linux via Docker (`klain-ci:latest`).
