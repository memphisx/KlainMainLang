# ADR-01020: Windows graceful-close drain — deliver a response written before closing a socket the peer is still sending to

- **Relations**: Fixes a Windows-only bug in [ADR-00971](ADR-00971.md)/[ADR-00973.md](ADR-00973.md) (TDD-00215 clientError/431 default); Extends [TDD-00177](../tdd/TDD-00177.md) (Windows platform lane); Relates to [ADR-00742](ADR-00742.md) (WSA→errno mapping)
- **Date**: 2026-09-19

## Context

`TestE2EHTTPClientErrorDefault431` and `TestE2EHTTPClientErrorSocketWriteEnd` (TDD-00215) failed **only on Windows** — the client received an empty response instead of the `431 Request Header Fields Too Large` default (or the `clientError` listener's custom `400`). Both pass on Linux and macOS. They were invisible until now because Windows was not in CI; this is exactly the class of platform bug the Windows lane exists to catch.

Both tests send a valid `GET / HTTP/1.1\r\n` request line followed by an unterminated ~11 MiB header block, to drive the server's oversized-header path. The server is supposed to detect the 10 MiB `maxHTTPRequestBytes` cap, send the 431, and close.

This was first misattributed (in a prior session and the working notes) to an environmental loopback issue. It is not: with the machine's HTTP-inspecting proxy fully out of the path, the tests still failed, and a klain-free .NET replica of the exact flow (valid request line + 11 MiB flood, server writes 431 back) delivered the response fine on the same box. The bug is in klain.

## Investigation

`KML_IO_TRACE=1` on the compiled server showed the server doing everything right:
```
recv total = 8,388,607 bytes      (accumulated to the cap)
[io] write fd=513 n=67 -> 67 (wsa 0)   ← the 431 is written successfully
[io] close fd=513 kind=1                ← then closed immediately
```
So the 431 **is** written to the socket — but the client reads 0 bytes.

Root cause: the socket `close()` shim (`win32src/win32io.c`) already did `shutdown(SD_SEND)` before `closesocket()` (an earlier fix for bare-close RSTs). But `shutdown(SD_SEND)` only flushes the *send* direction. Windows still issues an **abortive close (RST) when the receive buffer holds bytes the peer sent that were never read** — and here it does: the server stopped reading at the 10 MiB cap while the client was still uploading (8–11 MiB sent, only ~8.4 MiB consumed). The RST discards the just-queued 431 from the send buffer. Linux's `close()` delivers the queued data in the same situation, which is why the tests pass there.

The normal request/response path is unaffected (and ~188 other HTTP/net Windows tests pass): there the server consumes the whole request, so the receive buffer is empty at close and `shutdown(SD_SEND)+closesocket()` closes gracefully. Only "respond while the peer is still sending" (431/413/redirect/early-reject mid-upload) hits it.

## Decision

In `close()`'s socket branch, after `shutdown(SD_SEND)` and before `closesocket()`, **drain unread inbound data** so no unread input forces the RST — the Winsock graceful-close discipline, matching Linux's observable behavior.

Guards that keep it cheap and safe:
- **One non-blocking probe first.** Only a first `recv` that returns data (`r > 0`) enters the drain. The common close — request fully consumed, or an idle keep-alive close — gets a single `recv` returning `EWOULDBLOCK`/FIN and closes immediately, with no added latency.
- **Ride out the in-flight remainder.** When data is present the peer is often mid-send (its blocked writes unblock as we drain), so on `EWOULDBLOCK` we wait for readability in short 20 ms slices via `select`, stopping after ~100 ms of quiet — enough for the receive buffer to be empty at `closesocket()` time.
- **Bounded.** A 32 MiB byte cap and the idle-wait bound mean a peer that never stops sending cannot hang the close; past the cap we accept the RST, as any bounded server must.

The change is confined to `win32src/win32io.c` (Windows-only); Linux/macOS `close()` is untouched.

## Verification

- Windows (MSYS2 UCRT64 clang 22): `TestE2EHTTPClientErrorDefault431` and `TestE2EHTTPClientErrorSocketWriteEnd` pass; a direct 11 MiB-flood repro now returns the 67-byte 431 to the client (was empty). Full loopback-network E2E families (HTTP/HTTP2/Net/TLS/WebSocket/Fetch/SSE/streams) pass with no regression to keep-alive or streaming.
- Linux/macOS: unaffected by construction (Windows-only file); the shared HTTP dispatcher IR is unchanged.
