# ADR-00800: node:ffi symbol accumulators — library.functions/.symbols, no-arg getFunctions()/getSymbols()

- **Relations**: Extends ADR-00797, ADR-00799; Implements TDD-00164 (residual surface)
- **Date**: 2026-09-09

## Context

Node's `DynamicLibrary` keeps runtime accumulators of everything resolved
through it: `library.functions` (previously resolved callable wrappers),
`library.symbols` (previously resolved addresses), plus the no-argument
`getFunctions()`/`getSymbols()` forms. The Stage A ADR documented these as
unavailable — bindings here are compile-time values with no runtime registry.
That caveat is closable without a registry at all.

## Decision

The registration record rides on the library's *type*: `FFILibraryType()`
carries a shared `*FFILibReg` pointer, so the accumulator travels with the
value through destructuring and assignment (the copy in the variable's
symbol-table type is the live one). Every static resolution appends to it in
source order: `dlopen`/`getFunctions` definitions, literal-name
`getFunction` (with its signature) and `getSymbol` calls. A `getSymbol` entry
later re-resolved as a function upgrades in place, keeping its position.

Reading `library.functions` (or no-arg `getFunctions()`) materializes an
object with one callable `IsFFIFunction` field per recorded signature-bearing
entry; `library.symbols` / `getSymbols()` yields every recorded name as a
`bigint` address. Values are re-`dlsym`'d against the live handle at the read
point — the same address the original resolution got, so no storage is needed
and the emitted object is ordinary (destructuring, `Object.keys`, member
calls all come free).

Caveats (documented in the status row):

- The record is compile-time and per library value: a runtime-computed name
  passed to `getFunction`/`getSymbol` is resolved but not recorded, and a
  registration inside dead/conditional code is still recorded (an
  over-approximation of Node's runtime truth).
- The property read reflects registrations *textually before* it, matching
  emission order — same-expression-order semantics as Node in straight-line
  code.

## Verification

- `tests/ffi_test.go` (macOS M4): `lib.functions` mixing dlopen-definition
  and `getFunction` registrations (both callable), `symbols`/`getSymbols()`
  bigint addresses with identity across reads, no-arg `getFunctions()`
  callable, `Object.keys` in true resolution order
  (`strlen,getpid,abs`), and per-variable isolation (a second
  `DynamicLibrary` accumulates independently).
