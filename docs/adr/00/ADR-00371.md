# ADR-00371: TypeScript type assertions (`as T` / `as const` / `satisfies`) — parsed and erased

- **Date**: 2026-08-25

## Context

Auditing the TypeScript accept/reject conformance oracle (TDD-00121 Track C) surfaced that this compiler
rejected `x as T` outright — `const y = 5 as number` failed with `undefined variable 'as'`. Type assertions
(`as T`, `as const`) and the `satisfies` operator are ubiquitous, everyday TypeScript; rejecting them at
parse time blocks a large amount of otherwise-in-scope code and conformance cases. This is the highest-value
"easy win" among the recently-documented front-end gaps.

## Investigation

`as`/`satisfies` had no handling anywhere in the parser (only import `as`-aliases existed), so `5 as number`
parsed as two adjacent expressions and reached codegen as a reference to an undefined `as`. The type parser
(`parseTypeAnnotation`) and, on the codegen side, `resolveType` + `coerce` already exist.

A first attempt represented `as T` as an `AsExpression` AST node and emitted `coerce(value,
resolveType(T))`. That produced invalid IR on the common cases: `"hi" as string` (a same-storage retag that
`coerce` mishandled) and `JSON.parse(x) as number` (a boxed-`any` → scalar conversion `coerce` doesn't do),
and an object-literal `as Interface` broke the var-decl's object-field tracking because the assertion node
sat between the literal and the declaration. Adopting the asserted type while emitting the source
representation created value/slot IR mismatches (`constant expression type mismatch: got ptr, expected i64`).

## Decision

Treat all three forms as **erased**: parse `expr as T`, `expr as const`, and `expr satisfies T` as a
left-associative postfix in `parseAssignment` (after the ternary chain), consume the syntax, and return the
inner expression **unchanged** — no AST node, no codegen, the expression keeps its own inferred type.

This matches TypeScript's *runtime* semantics exactly (assertions are erased and never change runtime
behavior). It deliberately does **not** reproduce TS's *static* effect: the assertion does not re-type the
expression, so a cast the code relies on to widen/narrow a type has no effect and will fail (or not) at the
use site as if the cast weren't there. That is a sound, zero-risk position — strictly more code compiles than
before (where every `as` was a hard parse error), with no possibility of a miscompiled reinterpret.

`as`/`satisfies` are contextual keywords (plain identifiers), so the parse hook is gated on the identifier
text; `as const` is detected by the `const` keyword following `as`.

## Implementation notes

One hook in `parser/parser_exprs.go` (`parseAssignment`). No AST, inference, or codegen changes — the
initial `AsExpression` node and its `emitExpr`/`inferExprType` cases were removed once the erase-only
approach was chosen. Precedence is looser than the ternary/binary chain (so `a + b as T` groups as
`(a + b) as T`) — not exactly TS's precedence, but immaterial for erased assertions.

## Side effects discovered

None. The erase-only approach touches no existing value/type path.

## Verification

`go build ./...` + `go vet` clean. New `tests/as_cast_test.go` (6 cases): scalar `as`, `string` `as` +
`.length` on the result, `as const`, `satisfies`, chained `as ... as ...`, and object-literal `as Interface`
— all compile and run. Targeted class/object/string/generic E2E suites green. Verified on macOS (arm64).
