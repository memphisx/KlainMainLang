# ADR-00168: Function expressions (V1: anonymous only) + early-error checks that fix the conformance regressions it exposed

- **Relations**: Implements [TDD-00060](../tdd/TDD-00060.md)
- **Date**: 2026-08-12

## Context

TDD-00060 designed function expressions (`var f = function(x) { ... }`, callback arguments, `async function(...) {...}`) V1-scoped to anonymous functions only, reusing the arrow function closure machinery. A prior session in this repo implemented the parser/AST/codegen side of that design (still uncommitted in the working tree at the start of this session) but never finished the follow-through: `make conformance` was not re-run and compared against the pre-change baseline before the session ended, so a real regression shipped into the working tree undetected.

Comparing a full Test262 run before and after the function-expression change (via a `-passlist` flag added to `tools/conformance` for this comparison) showed the aggregate pass count dropped from 4463 to 4455 — a net change of -8, made up of 19 regressions offset by 11 unrelated new passes the feature also produced.

A second pass (same session, after the regression fix below shipped) code-reviewed the prior session's implementation directly rather than trusting its passing tests, prompted by a general distrust of unreviewed prior-session work after other low-quality changes had been noticed elsewhere in this project's history. That review found five more real, verified bugs in the prior session's own codegen work, described in their own Investigation subsection below.

## Investigation

All 19 regressions were `negative: {phase: parse}` Test262 files — tests that only pass if this compiler's pipeline returns *some* compile error, regardless of message. Before this change, `function` in expression position was a blanket parse-time rejection ("unexpected token function in expression"), which accidentally satisfied every one of these negative tests — including ones whose actual spec point has nothing to do with function-expression support at all (duplicate parameter names, `eval`/`arguments` as a strict-mode parameter name, a non-simple parameter list combined with a `"use strict"` directive, reserved words as object-literal shorthand properties in strict mode, legacy octal escapes in a directive prologue, `let`/`const` vs `var` redeclaration). Once function expressions parse for real, these pre-existing gaps in early-error checking are exposed instead of masked.

This compiler has no strict-mode concept anywhere (confirmed: no `isStrict`/`StrictMode` identifier anywhere in `parser/`, `resolver/`, or `codegen/llvm/`), so none of these were ever actually checked — the previous "pass" was accidental, not a sign the check existed.

Of the 19, three classes were cheap, low-risk, and correct to add outright:

- **Duplicate parameter names** (8 of 19, e.g. `param-duplicated-strict-1.js`, `13.1-8gs.js`, the async default-param case `nameless-dflt-params-duplicates.js`): TypeScript — this compiler's actual source language — rejects a duplicate parameter name unconditionally, not just in strict mode, so an unconditional check has no false-positive risk against any real intended use of this compiler.
- **Non-simple parameter list (default/rest/destructured) + a literal `"use strict"` directive as the function body's first statement** (3 of 19: `use-strict-with-non-simple-param.js`, `early-errors-expression-NSPL-with-USD.js`, `nameless-rest-param-strict-body.js`): a real, narrow ES2015+ rule, cheap to check once the body is parsed.
- **`eval`/`arguments` as a parameter name under the same literal-`"use strict"`-first-statement condition** (1 of 19: `param-eval-strict-body.js`).

The remaining 7 needed either a general strict-mode-context threaded through the parser during object-literal shorthand-property parsing (reserved words as shorthand properties, 3 tests), lexer-level tracking of octal escapes across a whole directive prologue (1 test), block-scoped `let`/`const`-vs-`var` redeclaration detection (2 tests, actually unconditional in real JS, not strict-mode-specific, but a materially different and larger feature — no block-scope conflict tracking exists anywhere in this parser/resolver today), or test262 `flags: [onlyStrict]` support in the conformance harness itself (1 test, `13.1-4gs.js`, which has no literal `"use strict"` in its source at all — the harness doesn't implement test262's flag-driven strict/sloppy dual-run convention). These are real, separate, larger scope cuts — deferred, not fixed here.

### Second-pass review: 6 more bugs found, 5 fixed

A structured review of the full diff (not just the regression fix above) found the prior session had added `*ast.FunctionExpression` as an arrow-function sibling in most, but not all, of the ~15 places `*ast.ArrowFunction` gets special-cased across `codegen/llvm/`. Every miss followed the same shape: a call site pattern-matches `*ast.ArrowFunction` for some arrow-specific behavior, and the equivalent `*ast.FunctionExpression` case was never added alongside it, so the new node type silently fell through to generic handling instead of erroring loudly.

- **`emitExprWithObjectHint` (`emit_objects.go`)**: propagates a function-typed hint's declared param types into an `*ast.ArrowFunction` (so `let cb: (b: Box) => number = (b) => b.value` correctly types `b`), but had no matching `*ast.FunctionExpression` case — the identical `function(b) { return b.value; }` form defaulted `b` to `i64` and hard-failed as "field access on non-object." Reachable from every hint-aware call site (var-decl init, object/array literal elements, call arguments, returns, assignments), not just the one repro.
- **`emitCall`'s IIFE dispatch (`emit_call.go`)**: recognized `*ast.ArrowFunction` as an immediately-callable callee but not `*ast.FunctionExpression`, so `((x) => x+1)(5)` worked while `(function(x) { return x+1; })(5)` — the exact IIFE shape TDD-00060's own Design section describes as "parses cleanly but hits the same emitCall rejection as any other IIFE" — actually differed from that description: it wasn't equally deferred, it flatly didn't work at all while the arrow form did.
- **`resolveEventEmitterListenerArg`/`resolveEventSourceListenerArg` (`emit_eventemitter.go`/`emit_eventsource.go`)**: same missing-hint-propagation shape, for a function-expression listener passed to `.on()`/`.addEventListener()` — an untyped payload parameter got no hint and failed the listener's own arity/type check for code that works fine as an arrow function.
- **`parseParamList`'s duplicate-name check (this ADR's own fix, `parser/parser_stmts.go`)**: as originally written, skipped any parameter with a destructuring pattern entirely (`ArrayPattern`/`ObjectPattern` non-nil), so two destructured params binding the same local name — `function f({x}, {x}) {...}` — parsed successfully and then silently miscompiled: `unpackObjectPatternInto` calls `e.define("x", ...)` once per param, so the second argument's binding silently overwrote the first's, with the first argument's value unreachable in the body.
- **`scanExprFV`'s `*ast.FunctionExpression` case (`emit_func.go`)**: built its bound-names set from each param's plain `Name` only, ignoring destructured pattern field/element names — the exact wrong-answer capture bug `gatherCaptures`' own comment already documents and avoids (a pattern field sharing a name with an outer-scope variable must shadow it, not be free-variable-scanned as a capture of the outer binding). Reachable whenever a function expression nested inside another closure's body destructures a parameter whose name collides with something the *enclosing* closure would otherwise capture — e.g. `arr.map(function({items}) { return items; })` written inside a closure that also has an outer `items` array in scope, which wrongly hit "capturing array variable 'items' in a closure is not yet supported" for code that never references the outer array at all. Confirmed this exact shape was already a latent, pre-existing bug in the identical `*ast.ArrowFunction` case in `scanExprFV` (unchanged by this session, not something newly introduced) — the new `*ast.FunctionExpression` case just copied the same already-buggy pattern instead of the correct one `gatherCaptures` uses two functions above it in the same file.

### A sixth bug found: cross-function labeled `break`/`continue`

Fixing the IIFE dispatch (above) let two more Test262 files reach codegen for the first time: `language/statements/break/S12.8_A6.js` and `language/statements/continue/S12.7_A6.js`, both shaped like `LABEL1: do { (function(){ break LABEL1; })(); } while(0);` — a labeled `break`/`continue` inside a nested closure, targeting a loop in the *enclosing* function. Confirmed directly: this compiled, but the generated LLVM IR had the closure's inner function body emit `br label %dowhile.end.N` referencing a label defined in a completely different LLVM function — invalid IR that `clang` itself rejected, not a clean error from this compiler. Both regressed from "pass" to "fail" (the same accidental-pass-via-blanket-IIFE-rejection pattern as this whole ADR's other findings) because the negative-parse-phase conformance check only inspects this compiler's own parser/`EmitProgram` errors, never clang's downstream IR validation.

Root cause: `e.breakStack`/`e.continueStack`/`e.namedLabelStack` (`emitter.go`) were never saved, cleared, or restored when entering a new function's own emission context (`emitFunctionDeclAs`, `emitClosureFunc`, `emitFunctionExpression` all save/reset/restore `e.allocas`/`e.scopes`/`e.regCtr`/etc. for exactly this reason, but not these three) — so a closure nested inside a live loop silently inherited the outer loop's break/continue/label targets instead of getting its own empty ones. This is a pre-existing bug in the whole closure/nested-function architecture, not something this session's function-expression work introduced — it just had no way to reach codegen for a *labeled* cross-function break/continue before IIFEs (the most natural way to immediately invoke a nested closure) worked at all.

**First attempt, reverted**: save current stacks, reset to `nil` on function entry, restore via a plain assignment near the end of the function (mirroring the existing pattern for every other per-function emitter field). This turned the silent-bad-IR bug into a Go-level slice-bounds panic on the exact repro above.

**Root cause of that panic, and the actual fix**: `emitDoWhile` (and every other loop-emitting function) manages `breakStack`/`continueStack`/`namedLabelStack` with its own push-then-`defer`-pop pattern — the pop runs unconditionally when the function returns, success or error. The first attempt's restore was a *plain* assignment near the bottom of `emitFunctionDeclAs`/`emitClosureFunc`/`emitFunctionExpression`, reached only on the success path. The repro's inner `break LABEL1` — now correctly rejected as "undefined label" once the reset made `namedLabelStack` empty inside the closure — returned an error immediately, which unwound straight out of the nested-closure emission *without ever reaching that plain-assignment restore*. Control returned to the enclosing `emitDoWhile` with `namedLabelStack`/`breakStack`/`continueStack` left in their reset (`nil`) state; `emitDoWhile`'s own deferred pop then tried to trim a slice that was no longer there, and panicked. The fix: restore all three fields via `defer`, registered immediately after the reset, so the restore runs on every exit path (error or success) — not just the one the first attempt happened to test.

## Decision

1. Ship the function-expression feature as originally designed (TDD-00060, V1: anonymous only) — parser/AST/codegen unchanged from the prior session's work, except for the second-pass fixes in item 5 below.
2. `parser/parser_stmts.go`'s `parseParamList`: reject a duplicate parameter name unconditionally (applies to function declarations, function expressions, and class methods alike, since all three share this function) — checked against each parameter's *real* bound name(s): a plain param's own name, or (after the second-pass fix) a destructured param's pattern field/element names, since its own `Name` is only a synthetic internal placeholder.
3. `parser/parser_stmts.go`'s `parseFunctionRest`: after the body parses, if the body's first statement is a literal `"use strict"` expression-statement, reject a non-simple parameter list (default value, rest, or destructuring pattern) and reject `eval`/`arguments` as a parameter name. New helper `bodyStartsWithUseStrict` — deliberately narrower than the full directive-prologue rule (only checks the textually-first statement, not a whole run of leading string-literal statements), since every regressed test uses that shape.
4. Leave the remaining 7 first-pass regressions unfixed, as a known, documented gap (see status docs).
5. Fix all 6 second-pass bugs: add the missing `*ast.FunctionExpression` case to `emitExprWithObjectHint`, `emitCall`'s IIFE dispatch, and both event-listener resolvers (mirroring each site's existing `*ast.ArrowFunction` case exactly); extend the duplicate-parameter check (item 2) to destructured params' real bound names instead of skipping them; factor the "a destructured param's real bound names are its pattern's own field/element names, not its synthetic `Name`" logic — previously correct in `gatherCaptures` and `emitFunctionExpression`'s own capture-gathering, wrong in both `scanExprFV` nested-closure cases (`*ast.ArrowFunction` and `*ast.FunctionExpression` alike) — into one shared `addParamBoundNames` helper (`emit_func.go`) used by all four sites; and reset+restore `e.breakStack`/`e.continueStack`/`e.namedLabelStack` on entry to `emitFunctionDeclAs`/`emitClosureFunc`/`emitFunctionExpression` alike, restored via `defer` (see the subsection above for why plain-assignment restore isn't safe here).

## Implementation notes

- Both `parseParamList`/`parseFunctionRest` checks are pure parse-time rejections using already-parsed `ast.Param`/`ast.BlockStatement` shape — no `ast` changes needed for those two.
- They also apply (correctly) beyond just the new function-expression path, since `parseFunctionRest`/`parseParamList` are shared by function declarations, function expressions, and class methods alike — part of why the final fixed pass count is higher than baseline + the 12 fixed regressions would predict on their own; some previously-failing, unrelated Test262 files also happened to hit these same checks.
- `addParamBoundNames(bound map[string]bool, params []ast.Param)` is the one place the "plain name vs. pattern field/element names" logic now lives; `gatherCaptures`, `emitFunctionExpression`, and both `scanExprFV` nested-closure cases (`*ast.ArrowFunction`, `*ast.FunctionExpression`) all call it instead of each independently inlining the same three-way `Name`/`ArrayPattern`/`ObjectPattern` check.
- The break/continue/named-label reset+restore is applied identically in all three per-function save/reset/restore blocks (`emitFunctionDeclAs`, `emitClosureFunc`, `emitFunctionExpression`) — a bare `break`/`continue` inside a nested function declaration is exactly as invalid as inside a closure, even though no Test262 repro happened to exercise that specific combination.

## Side effects discovered

- The `*ast.ArrowFunction` case in `scanExprFV` had the same destructured-pattern-bound-names bug as the new `*ast.FunctionExpression` case, confirmed pre-existing (unchanged by this session's diff) — not introduced here, but fixed alongside it via the shared `addParamBoundNames` helper rather than left half-fixed.
- The break/continue/named-label reset also fixes an unlabeled `break`/`continue` inside *any* closure nested in a loop (`for (...) { (function(){ break; })(); }`), not just the labeled case Test262 happened to catch — confirmed directly (see Verification): previously this too would have silently inherited the outer loop's break target and produced invalid cross-function IR: now it's a clean "break statement outside of loop or switch" error, consistent with real JS (a `break`/`continue` genuinely cannot reach through a function boundary in real JS either).
- No other side effects beyond what's described above.
