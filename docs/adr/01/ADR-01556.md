# ADR-01556: Representation rules the checker-side mapping lacked; Array.of as a literal; generator values in objects

- **Relations**: Extends ADR-01554, ADR-01555, TDD-00230
- **Date**: 2026-10-10

## Context

TDD-00230 P3.3 moves `inferExprType` onto the checker's types, mapped to
codegen's representations. Letting the mapping decide member reads, calls
and identifiers across the end-to-end suite showed where it named a
representation codegen does not build:

- Values codegen holds boxed though their static type is narrower:
  `Object.defineProperty`/`create`/`getPrototypeOf`/`setPrototypeOf`/
  `getOwnPropertyDescriptor`/`groupBy` results; a class's value behind a
  module-level `typeof C` binding, and calls through it; a builtin type's
  method read as a value (`m.get`, `/x/.test`, `process.send`); a call of
  an overloaded function whose implementation returns `any`
  (`execSync(cmd, { encoding })`, whose overload says string). A binding
  initialized with such a value, an array literal holding one and a
  non-null assertion of one hold it the same way.
- Bindings and reads that keep a tuple: a read of a declared interface or
  class field typed as a tuple, a function declared to return a tuple, and
  an unannotated holder of either.
- A number or boolean an array pattern binds without a default, from a
  source that is not a literal, may lie past the source's end; codegen
  holds it in an undefined-capable slot (nested patterns, and array
  patterns inside object patterns, too).
- In the js lane, a literal of nested mixed literals is an array of boxed
  rows; a `[]` whose stores mix kinds is a boxed-element array, and so
  are `filter`/`slice`/`concat`… results and callback parameters over it.
- An async function declaration whose body only throws: tsc types it
  `Promise<void>`, codegen `Promise<never>`, as for a plain one
  (ADR-00869).
- A parameter or local of type `typeof C` reads the class's statics typed.

The same pass found compiler bugs:

- `function* g(): number` names what the generator yields, a form this
  project accepts; the checker took it as the result type, so its calls
  were numbers.
- `Array.from("hey")` inferred `unknown[]`: a string gave `Iterable<T>` and
  `ArrayLike<T>` no candidate.
- Calling an object literal's generator method (`o.g()`) failed to
  compile ("an object has no method"), and a generator function stored as
  a property (`{ seq }`) was a typed function field while a generator
  method was boxed.
- `Array.of(1, "x")` was rejected, and `Array.of()` built a number array;
  Node builds `[1, "x"]` and an empty array.
- The empty-array element inference missed stores in a call chain's
  receiver (`p.then(f).then(g)`) and under `await` and other operators.
- Old inference left `FuncCountsArgs` unset on a function expression
  reading `arguments`.

## Decision

- The mapping applies each representation rule above.
- The checker reads a generator annotation that is not an iterator,
  iterable or generator type as the yield type (`Generator<T, any,
  unknown>`), and a string infers `T = string` for `Iterable<T>`,
  `IterableIterator<T>` and `ArrayLike<T>`.
- `Array.of(…)` lowers to the array literal of its arguments; with none,
  an empty boxed-element array.
- An object literal holds a generator function value boxed, and a method
  call through a fixed-layout object's boxed field is the boxed object's
  dynamic method call.
- The empty-array element walk descends into a call's receiver and every
  operand expression.
