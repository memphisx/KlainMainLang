# TDD-00037: Multiple type parameters for user-defined generics (`<K, V>`)

- **Status**: Implemented
- **Date**: 2026-08-07
- **Notes**: Extends [TDD-00010](TDD-00010.md)'s single-type-parameter scope; no explicit call-site type arguments (constraints added later by [TDD-00113](TDD-00113.md))

## Context

[TDD-00010](TDD-00010.md) scoped user-defined generics (V1: monomorphization, [ADR-00103](../adr/ADR-00103.md); V2: `@erased` opt-in type erasure, [ADR-00121](../adr/ADR-00121.md)) to exactly one, unconstrained type parameter throughout — functions, interfaces, and classes alike. That document's own Open Questions section named multiple type parameters (`<K, V>`) as a real, likely-natural follow-on, deliberately not designed there. This document is that follow-on.

The restriction is enforced today at a single, explicit choke point: `parser.parseTypeParamList` (`parser/parser.go:107-125`, shared by function/interface/class declarations) parses one identifier and then hard-errors the moment it sees a comma:

```go
if p.check(lexer.COMMA) {
	t := p.peek()
	return nil, fmt.Errorf("%d:%d: multiple type parameters on %s are not yet supported (see docs/tdd/TDD-00010.md)", t.Line, t.Col, context)
}
```

A matching, separate choke point exists for *explicit* type arguments at a `new Box<...>(...)` construction site (`parser/parser_literals.go`'s `parseNewGenericBody`) and for a generic-interface usage (`parser/parser_types.go`'s "user-defined generic type usage" branch, the one that stores a single parsed argument into `TypeAnnotation.ElemType`) — both currently reject a second, comma-separated argument the same way. Picked up now because it's the single most commonly requested shape of container/utility type (`Pair<K, V>`, `Result<T, E>`, a two-key lookup) that today's generics genuinely cannot express, and because — per the investigation below — the AST already carries the *plumbing* for it (`TypeParams`/`NewExpression.TypeArgs` are already `[]string`/`[]*ast.TypeAnnotation`, not scalars) even though nothing downstream walks past index 0 yet.

## Design

### What's structurally already N-ary vs. what's hardcoded to exactly one

Read every generics-adjacent type/function across `ast/nodes.go` and `codegen/llvm/emit_generics.go` ([TDD-00010](TDD-00010.md)'s implementation) to separate "already a slice, just unused past index 0" from "a genuinely scalar field/parameter that needs to become a map/slice":

| Already plural (no AST change needed) | Currently scalar (real design/code work) |
|---|---|
| `FunctionDeclaration.TypeParams []string`, `InterfaceDeclaration.TypeParams`, `ClassDeclaration.TypeParams` | `TypeAnnotation` has no field for a *user-defined* generic interface's N type arguments — `ElemType`/`KeyType` are semantically the built-ins' own single/paired slots (`Promise<T>`/`Array<T>`/`Set<T>`'s `ElemType`, `Map<K,V>`'s `KeyType`+`ElemType`) and must stay exactly as they are |
| `NewExpression.TypeArgs []*ast.TypeAnnotation` | `substituteGenericType(ta *ast.TypeAnnotation, typeParam string, concrete Type) Type` — single `(name, Type)` pair |
| | `mangleTypeArg` returns one suffix per call; nothing joins N of them yet |
| | `genericFuncTypeParamIndex(decl) (idx int, isArray bool)` — returns exactly one inference site, for `decl.TypeParams[0]` only |
| | `buildGenericParamSig(params, typeParam string, concrete Type) FuncSig`, `genericClassMangledFields`, `instantiateGenericInterface` — all take one `(typeParam, concrete)` pair |

This split matters for scoping the work: the parser-level rejection is nearly cosmetic (lift the comma check, loop), but every substitution/mangling/inference function in `emit_generics.go` needs its single-pair signature widened to a set — real, mechanical-but-nontrivial rework, not a one-line change.

### New AST field: `TypeAnnotation.TypeArgs []*TypeAnnotation`

A user-defined generic interface usage (`Box<number, string>`) needs somewhere to carry N type arguments. Reusing `ElemType`/`KeyType` for this would overload fields whose meaning is already fixed for the built-ins (`Map<K,V>`'s `KeyType` in particular means something structurally different — a *map key type*, not "the first of several generic arguments"). Adding a new `TypeArgs []*TypeAnnotation` field, populated only by the parser's "user-defined generic type usage" branch (`parser_types.go`), keeps every built-in's existing parsing/resolution untouched and gives `resolveType`'s generic-interface branch (`emitter.go:431`, `if genDecl, ok := e.genericInterfaces[ta.Name]; ok && ta.ElemType != nil`) a real multi-arg source to switch to (`ta.TypeArgs` instead of a single `ta.ElemType`, with the existing single-arg case becoming `len(ta.TypeArgs) == 1`'s special case, not a separate code path).

### Parser changes: lift three independent comma-rejections into loops

Three separate parse sites, none sharing code today, each need the same shape of change (parse a comma-separated list instead of one item, matching arity between a declaration's `TypeParams` and a usage's argument count deferred to codegen, not the parser — the parser has no symbol table):

1. `parseTypeParamList` (`parser.go`) — declaration site (`function f<K, V>`, `interface Box<K, V>`, `class Box<K, V>`). Loop collecting `IDENT` tokens separated by `COMMA` into `[]string`, same `EXTENDS`-rejection (constraints stay out of scope, see Open Questions) applied per parameter.
2. The "user-defined generic type usage" branch (`parser_types.go`) — usage site as a plain type annotation (`x: Box<number, string>`). Loop parsing type annotations into the new `TypeArgs` field.
3. `parseNewGenericBody` (`parser_literals.go`) — usage site at construction (`new Box<number, string>(...)`). Loop parsing type annotations into the already-plural `NewExpression.TypeArgs`.

None of these three loops need to check *count* against a declaration's own `TypeParams` — same reasoning V1 already relies on: the parser has no symbol table, so arity checking is deferred to codegen (`registerFunctions`/`registerInterfaces`/`registerClasses` and the instantiation call sites), the same place today's "did you supply a type argument at all" checks already live (`emit_exprs_vardecl.go:150`, `emit_classes.go:1344`, `emit_exprs_types.go:350` — all three currently hardcode `len(init.TypeArgs) == 1`, all three generalize to `len(init.TypeArgs) == len(genDecl.TypeParams)`).

### Codegen: from `(typeParam string, concrete Type)` to `map[string]Type`

Every one of `emit_generics.go`'s substitution/mangling functions takes a single `(typeParam string, concrete Type)` pair today; the natural generalization is a `map[string]Type` (type-parameter name → concrete type), built once per instantiation/usage site and threaded through:

- `substituteGenericType(ta, subs map[string]Type) Type` — `if concrete, ok := subs[ta.Name]; ok { return concrete }`, same array-suffix (`ta.Name == typeParam+"[]"`) handling per entry.
- `buildGenericParamSig(params, subs map[string]Type) FuncSig`, `genericClassMangledFields`, `instantiateGenericInterface` — each just passes `subs` through to `substituteGenericType` instead of a single pair; no other change to their own logic.
- `mangleTypeArg` itself is unchanged (still mangles one `Type`); its callers now join N suffixes: `strings.Join(suffixes, "_")` (e.g. `Box<number,string>` → `Box__num_str`), computed in declared type-parameter order so the mangled name is deterministic regardless of a map's iteration order.

### The real design decision: per-type-parameter inference for generic *functions*

Classes and interfaces don't need new inference logic — `new Box<number, string>(...)` and `x: Box<number, string>` are both explicit, unambiguous type-argument lists (the same reason V1 never needed inference for either). Generic **functions** are the one case V1 solved with inference (`identity(5)` infers `T = number` with no explicit `<...>`), and that's exactly what needs to generalize correctly for N type parameters.

`genericFuncTypeParamIndex` today finds *the* (singular) parameter position typed `T`/`T[]` for `decl.TypeParams[0]`. Generalized: for **each** type parameter in `decl.TypeParams`, independently find its own first matching parameter position (bare or one-level-array), producing a `map[string]int` (type-parameter name → parameter index, or absent if none found) rather than one `(idx, isArray)` pair. At a call site, `inferGenericCallConcreteType` becomes a loop: infer each type parameter's concrete type from its own designated argument position, and if *any* type parameter in `decl.TypeParams` has no inferable position, reject the call — naming that specific type parameter in the error message (e.g. `"cannot infer type argument 'V' for generic function 'pair' — declare a parameter typed 'V' or 'V[]' to infer from"`), the direct N-ary generalization of V1's existing single-parameter rejection (`emitGenericFuncCall`'s current error, `emit_generics.go`).

This is a strict generalization, not a new design axis — V1's existing rule ("every type parameter must be inferable from some parameter's own declared type") already implies this. No two type parameters can ever compete for the same inference source, since a given parameter's type annotation names exactly one type-parameter name (`p.Type.Name == typeParam`), never two — `function pair<K, V>(k: K, v: V): [K, V]`-shaped signatures (once tuple types exist — they don't yet, see [`docs/status/TYPE-SYSTEM.md`](../status/TYPE-SYSTEM.md)) work cleanly; interim signatures like `function makePair<K, V>(k: K, v: V): SomeInterface` work today already, tuple return types are an orthogonal, pre-existing gap not caused or fixed by this document.

**Explicitly out of scope, and not a new gap this document introduces**: the *same* type parameter appearing on more than one parameter (`function same<T>(a: T, b: T): T`, legal V1 syntax today) already only infers from the first occurrence and silently coerces every later occurrence's argument against that inferred type, with no runtime check that the two arguments actually agree (`same(1, "x")` compiles today, coercing `"x"`'s `ptr` value against a `number`-shaped parameter slot — a real, pre-existing gap, since fixing it needs actual generic type-consistency checking, a different and larger problem than N-ary type parameters). This document neither fixes nor worsens that; noted here only so it isn't mistaken for new N-ary-specific breakage during review.

### V2 (`@erased`) needs almost none of this new design — only the mechanical rework

Because V2 never infers anything (a `@erased` function's body compiles exactly once, with every occurrence of every one of its type parameters substituted to the same target, `TypeAny`, regardless of which type parameter it was), extending it to N type parameters is nearly free once `substituteGenericType`/`buildGenericParamSig` accept a `map[string]Type`: `registerFunctions`' existing V2 branch (`emitter.go`) just builds `subs := map[string]Type{}; for _, tp := range fd.TypeParams { subs[tp] = TypeAny }` instead of a single-entry substitution, with no new inference/mangling/ambiguity questions at all. Worth stating explicitly since it's the one place this document's added complexity (the per-type-parameter inference design above) doesn't apply.

## Open questions

- **Type parameter constraints (`<T extends Base>`) and default type parameters (`<T = number>`)** — explicitly still out of scope here, same as [TDD-00010](TDD-00010.md) left them; this document is multiple *unconstrained* type parameters only, not a broader generics-expressiveness pass.
- **Explicit call-site type arguments on a function call** (`identity<number>(5)`) remain out of scope for the same reason [TDD-00010](TDD-00010.md) gave (the `a<b>(c)` grammar ambiguity) — N-ary inference doesn't change that calculus, since the ambiguity is about the `<` token itself, not about how many type parameters follow it.
- **Mangled-name stability** — [TDD-00010](TDD-00010.md) already left "is the mangling scheme a stable, inspectable detail or a free-to-change implementation detail" undecided for the single-param case; this document's `_`-joined N-ary suffix (`Box__num_str`) inherits the same open question, not a new one.
- **Should `genericFuncTypeParamIndex`'s generalization (a `map[string]int` of type-parameter name → inferable parameter index) also detect and reject at *declaration* time a type parameter that provably can never be inferred** (e.g. one that only ever appears in the return type, across every parameter), rather than only failing lazily at the first call site the way V1 does today for the single-param case? Leaning toward keeping today's lazy-at-call-site behavior for consistency with V1 rather than introducing a new, earlier validation pass — not decided.
- **Whether interface/class field ordering should be required to match declaration-order `TypeParams`** (i.e., is `Box<number, string>` positionally `K=number, V=string` matching `interface Box<K, V>`'s own declared order, with no named-argument form) — assumed yes, matching how every other positional-generic precedent in this codebase already works (`Map<K,V>`, `new Box<T>(...)`), but not explicitly re-confirmed against alternatives since none seem worth considering for an unconstrained, unlabeled type-parameter list.
