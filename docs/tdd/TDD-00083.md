# TDD-00083: Promise concurrency — microtasks/`.then`, `Promise.any`, and the true-suspension question

- **Status**: Implemented
- **Date**: 2026-08-19

*Stage 2 async-function suspension, the combinator generalization, the rejection model, Stage 3 microtasks, and `Promise.any`/`AggregateError`/value-chaining shipped directly ([ADR-00244](../adr/ADR-00244.md), [ADR-00245](../adr/ADR-00245.md), [ADR-00248](../adr/ADR-00248.md)). The architectural remainder this document scoped — a non-suspending `async` fn returning a rejected (not synchronously-thrown) promise, `.any` over raw fetch responses, event-loop/task-scheduler unification, and destructured/nullable params in a genuinely-suspending fn — was delivered by [TDD-00084](TDD-00084.md).*

## Context

The Async / Promise area is 3/6 (50%), Strict 0/6. The pieces that exist are
substantial and were deliberate: `async`/`await` (malloc-slot model), a unified
`select()` event loop (TDD-00006), ucontext fiber suspension for `http.listen`
handlers, and `Promise.all`/`.race`/`.allSettled` with **real** concurrency over
`Array<Promise<Response>>` (TDD-00016/[ADR-00073](../adr/ADR-00073.md)). The
primary microservice fan-out — issue N `fetch()`es, wait on them together —
already works via `Promise.all([fetch(a), fetch(b)])` over the raw handles.

What is *not* there, and what this document scopes:

- **`Promise.any`** — the one missing combinator (❌).
- **A microtask model** — no `queueMicrotask`, no `Promise.prototype.then`/
  `.catch`/`.finally`, no rejection/`.catch` surface, no ordering semantics.
- **Composition concurrency** — the deliberate limitation from TDD-00016: a user
  `async function` body runs to completion *synchronously* at call time, so
  `Promise.all([fetchUser(a), fetchUser(b)])` — where `fetchUser` is an async fn
  that awaits a fetch — does **not** overlap; only the raw-handle form does. True
  overlap needs async functions to suspend at `await`, which they cannot today.
- **`for await...of`** — out of scope (async-iteration ceiling, TDD-00063).

This needs a TDD, not a bare ADR, because the composition-concurrency item is a
genuine architectural fork (generalize the fiber model vs. stay synchronous), not
a mechanical extension.

## Investigation: the current machinery (confirmed directly against `codegen/llvm/`)

- **Async functions are inlined synchronous code.** `emitAsyncPrologue`
  (emit_async.go:16) mallocs `StructFieldSize(T)` bytes; `return v` stores into
  that slot and branches to the return block (emit_func.go:148, :896);
  `emitAsyncEpilogue` (emit_async.go:36) emits `ret ptr %coroHdl`. The body runs
  top-to-bottom at call time. `emitAwait` (emit_async.go:80) just loads-and-frees
  the slot — except fetch's `Promise<Response>` (`!PromiseResolved`), which calls
  `@__kml_await_fetch`. **No coroutine, no continuation, no state machine.**
- **Fibers are HTTP-connection-scoped, not async-function-scoped.**
  `ensureFiberRuntime` (runtime_http.go:479) wraps `getcontext`/`makecontext`/
  `swapcontext`; fibers are spawned *only* by `__kml_http_append_conn`
  (runtime_http.go:708) on socket accept, with the entry point hardwired to the
  HTTP dispatcher (:715), a 1 MiB stack (:26), and `uc_link = @__kml_main_ctx`.
  The per-slot struct is `{ i64 fd, ptr ctx, ptr stack, ptr pendingFetch, ptr
  pendingGroup }` (40 bytes). A handler suspends at `await fetch` by storing the
  pending handle into its **own connection slot** and `swapcontext`-ing to main
  (`__kml_await_fetch` doyield, runtime_fetch.go:419), discovered via the global
  `@__kml_current_conn_idx`. Top-level (no fiber) `await fetch` **busy-spins**
  (runtime_fetch.go:430). There is **no primitive to run an arbitrary closure on
  a fresh fiber**, and no per-async-call park state.
- **One unified event loop.** `__kml_event_loop_run` (runtime_http.go:880)
  select()s over the listener, connection fds, curl-multi fds, WS-client fds,
  with a timeout folded from timer/EventSource-reconnect/fetch-timeout deadlines;
  it fires due timers inline (:1487) and runs the resume scan (:1388) that
  re-enters a fiber when its `pendingFetch`/`pendingGroup` is satisfied or its fd
  is ready. It strictly subsumes the standalone `__kml_timer_drain`
  (emit_timers.go:281), but the two are dispatched mutually-exclusively at program
  exit (emitter.go:982): a program gets the full loop *or* the bare timer-drain.
- **Combinators branch on `IsResponse`.** `emit_promise.go` builds a 24-byte group
  `{ ptr members, i64 count, i64 mode }` and calls `@__kml_await_group_wait`
  (runtime_fetch.go:579, a structural clone of `__kml_await_fetch` parking on
  `pendingGroup`) for the Response case; for any other `T` it loops over
  already-resolved slots. `mode` is 0 = all, 1 = race.
- **No microtask queue, no `.then`, no `queueMicrotask`, no rejection model** —
  confirmed absent.

## Design

Three committed stages, ordered by dependency (§ Staged delivery). Nothing is
deferred — the area is driven to a real, Strict close, not a fourth loose-✅ with
the hard part carved off.

### Stage 1 — `Promise.any` (small, high-certainty)

Add the missing combinator. Over `Array<Promise<Response>>`: reuse the group
mechanism with a new `mode = 2` ("first fulfilled") — the group is satisfied when
any member finishes successfully, or all fail. On all-reject, throw an
`AggregateError` (a new named Error kind, following the fixed-enum convention —
`errorKinds`, emit_exceptions.go — carrying an `errors` array). Over any other
`T`: the elements are already resolved, so return the first (all are "fulfilled"
by construction; the all-reject path is unreachable there). Raises Async/Promise
to 4/6. Self-contained; no model change.

### Stage 2 (foundational) — true async-function suspension

This is the core of the feature and the thing that makes the whole area actually
*close* rather than stay loose-✅. Today the special-casing everywhere — combinators
branching on `IsResponse`, `emitAwait`'s pending-vs-resolved split, "the only
pending promise is `fetch`'s" — exists solely because user async functions cannot
suspend. Give them real suspension and that entire pile of caveats collapses:
every `async function` call returns a genuinely-pending promise, combinators work
over *any* `Array<Promise<T>>` with real concurrency (the `IsResponse` branch
folds away), and `Promise.all([fetchUser(a), fetchUser(b)])` overlaps like it
should. So this is built, not deferred — the raw-handle workaround is exactly the
kind of "it technically works if you contort the code" caveat that keeps the row
out of Strict.

A user `async function` call must run its body up to the first `await`, then
**suspend** and return a still-pending promise (JS runs the eager prefix
synchronously, so this is genuinely the coroutine model — no lazy shortcut). From
the confirmed feasibility map, four pieces:

1. **A connection-independent fiber-spawn primitive** — run an arbitrary closure
   (the async body) on a fresh ucontext/stack with its own park slot, generalizing
   `__kml_http_append_conn` (runtime_http.go:708), whose entry point is currently
   hardwired to the HTTP dispatcher (:715).
2. **Per-async-call park state** — a fiber/task struct carrying its own
   `pendingFetch`/`pendingGroup`/resolved-value + a pointer to the promise slot it
   fulfills, instead of the shared connection-slot fields keyed by
   `@__kml_current_conn_idx`.
3. **A generalized scheduler** — the event loop's resume scan (runtime_http.go:1388)
   extended (or unified) over this task set, and made the single program-exit loop
   for any async program (today top-level `await fetch` busy-spins with no loop,
   and the two exit loops are mutually exclusive, emitter.go:982).
4. **A suspendable async frame** — the largest change: `emit_async.go`/`emit_func.go`
   emit a fiber launch + a frame whose locals survive across `await`, replacing the
   inlined-synchronous body every await/combinator site assumes today. Fiber stacks
   sized far below the HTTP path's 1 MiB (most async bodies are shallow), reclaimed
   when the call completes.

Cost is real and stated plainly: a fiber stack per in-flight async call, and a
rewrite of the async model's core assumption. That is the price of closing the
area, and per the standing "close it or don't start it" rule we pay it here rather
than shipping a fourth caveat-bearing half-feature.

### Stage 3 — microtasks + `.then`/`.catch`/`.finally` + `queueMicrotask` (against the real model)

Built *after* suspension so it targets the final model: real pending promises with
real resolution, not pre-resolved slots. A global microtask FIFO
(`@__kml_microtasks`) drained by `@__kml_drain_microtasks` at the spec points —
after the current synchronous run, after each fired timer, and after each task
resumption. `queueMicrotask(cb)` pushes. `Promise.prototype.then(onF, onR?)` /
`.catch` / `.finally` attach a resolution/rejection callback to a promise: fired as
a microtask on resolve for an already-settled promise, or registered on the task
for a still-pending one (the scheduler runs it when the promise settles) — the same
machinery for a pending user async promise and a pending fetch, now that both
exist. `.then` returns a new promise (chaining). Rejection rides on the
[TDD-00013](TDD-00013.md) tagged-error model.

## Staged delivery — all committed, ordered by dependency (nothing deferred)

1. `Promise.any` (+ `AggregateError` kind) — small, independent of the rewrite,
   works in the current model; closes the combinator set (Async/Promise 3/6 → 4/6).
2. **True async-fn suspension** (foundational rewrite) — generalized fiber spawn,
   per-call park, scheduler-as-exit-loop, suspendable frame; folds away the
   `IsResponse` special-casing so combinators get real concurrency over any
   `Array<Promise<T>>`.
3. Microtask queue + `queueMicrotask` + `.then`/`.catch`/`.finally` — against the
   post-suspension model.

`for await...of` (async iteration, currently the TDD-00063 ceiling) becomes
*reachable* once Stage 2 exists — real async iterators need real suspension — and
is the natural next feature area on top of this, tracked separately rather than
folded in (it is a distinct surface, not a carved-off piece of concurrency).

## Open questions

- Stage 3: does `.then` on a pending `fetch` promise separate cleanly into 3b, or
  is it small enough to fold in? Decide when the settled-promise `.then` lands and
  the pending-callback disposition is prototyped.
- Stage 3: unhandled-rejection reporting — track and warn at exit, or out of
  scope for V1? Lean out-of-scope until `.catch` exists.
- Stage 2: fiber stack size — the HTTP path uses 1 MiB; a per-async-call fiber
  wants far smaller (most async bodies are shallow). Measure a safe floor.
- Stage 2: memory reclamation of fiber stacks for completed async calls (the HTTP
  path ties stack lifetime to the connection); free-on-completion vs. a small pool.
- Stage 2: does the resolved-slot fast path stay for a synchronous async fn that
  never awaits (avoid a fiber when the body can't suspend), or does every async
  call go through a fiber uniformly? Prototype both — the fast path avoids a stack
  alloc for the common no-await async fn.
