# TDD-00071: Binding-readability analysis — proper TDZ and definite-assignment errors

- **Status**: Implemented
- **Date**: 2026-08-18
- **Notes**: Definite-assignment (Stage 2) is deliberately sound-not-complete — never a false positive, misses harder flow cases

## Context

[TDD-00070](TDD-00070.md)/[ADR-00210](../adr/ADR-00210.md)/[ADR-00211](../adr/ADR-00211.md) closed most of the `let`/`const`/`var` scoping gap. Two caveats remain on the Variable declarations status row, and both come down to one question the compiler can't yet answer statically: **at this read of `x`, is `x` in a state where reading it is legal?**

1. **No temporal-dead-zone (TDZ) error, and a real shadowing bug behind it.** A `let`/`const` read before its declaration is currently rejected only as a generic `undefined variable` (because the binding simply isn't in the symbol table yet), not as the distinct `Cannot access 'x' before initialization`. Worse, the *shadowing* form is silently miscompiled: `let x = 1; { console.log(x); let x = 2; }` should be a TDZ error (the inner `let x` governs the whole inner block, so the `console.log` is in its dead zone), but today the reference resolves to the *outer* `x` and prints `1`. That is a correctness bug, not just a message-quality gap.

2. **No definite-assignment error for a typed `var`.** Making `var` function-scoped ([ADR-00210](../adr/ADR-00210.md) Stage C) created a reachable state that couldn't exist before: a typed `var` read on a control-flow path where its assignment never ran (`if (c) { var r = 1 } use(r)` with `c` false). To stay safe, that read currently returns a deterministic zero default; the signed-off hybrid wanted the TypeScript behavior — a `Variable 'r' is used before being assigned` compile error — which needs flow analysis this compiler doesn't have.

Both are the same shape of question, so they are scoped together here.

## Design

A single static, flow-sensitive pass — call it **binding-readability analysis** — that walks a function body tracking, per binding, a small state, and reports an error at any read that isn't legal in the binding's current state. It runs in the resolver (early errors, before codegen, matching how real engines reject these before the program runs), mirroring the traversal shape `resolver/rename.go` already uses.

### Binding state lattice

Per binding, at each program point, one of:

- **TDZ** — a `let`/`const`/`class` binding is hoisted to the top of its block but not yet initialized (control has not reached its declaration). A read here → `Cannot access 'x' before initialization`.
- **Declared-unassigned** — a typed `var`/`let` that has been declared (TDZ passed) but not definitely assigned on all paths to here. A read of a **typed** binding here → `Variable 'x' is used before being assigned`. An `any`/`unknown` binding in this state is **exempt** (it legitimately reads back `undefined`).
- **Assigned** — initialized/assigned on all paths to here. Reads are legal.
- **Out of scope / undeclared** — unchanged existing `undefined variable` path (codegen still owns this; the analysis need not duplicate it).

The two caveats are two transitions out of the unreadable states: TDZ → caveat #2, Declared-unassigned(typed) → caveat #1.

### TDZ (caveat #2)

Model per-block lexical hoisting: on entering a block, every `let`/`const`/`class` name declared directly in it becomes an in-scope binding in state **TDZ**; its declaration statement flips it to Declared-unassigned/Assigned. A read that resolves to a binding still in TDZ is the error. This is what makes the shadowing case correct: inside the inner block, `x` resolves to the block's own (hoisted, TDZ) `x`, not the outer one, so the pre-declaration read is a TDZ error rather than a silent outer-binding read.

**V1 scope:** statically-decidable, same-function TDZ — a read textually before the declaration in the same or a nested non-function block. A read inside a *closure/nested function* that could legally run after the declaration is **not** flagged (real TDZ is a runtime check; flagging the closure case statically would be a false positive). This matches the "V1-scoped" boundary [TDD-00070](TDD-00070.md) already set.

### Definite-assignment (caveat #1)

Track a **definitely-assigned set** as the walk proceeds, with control-flow-aware merges:

- Straight-line: an assignment (`x = …`, `x += …`, `++x`, a declaration initializer, a destructuring target) adds `x`.
- `if (c) A else B`: the set after is (set-before ∪ (assigned-in-A ∩ assigned-in-B)) — a binding is definitely assigned after only if assigned on **both** branches (or already before). A bare `if` with no `else` contributes nothing definite.
- Loops (`for`/`while`/`do`/`for-of`/`for-in`): the body may run zero times, so body assignments are **not** definite after the loop (except a `do/while`, whose body runs at least once).
- `switch`: definite only if assigned in every case *including* `default` and no case falls through unassigned — conservative default is "not definite."
- `try/catch/finally`: assignments in `try` are not definite after (it may throw partway); `finally`'s are.
- An early `return`/`throw`/`break`/`continue` prunes its path from the join (a binding unassigned only on a path that diverges before the read doesn't count against the read).

A read of a **typed** binding not in the definitely-assigned set is the error. **Conservatism rule:** when the analysis can't prove a binding is unassigned on some reaching path, it must treat it as assigned (no error) — a false *negative* (a missed error) is a documented V1 gap; a false *positive* rejects valid code and is not acceptable. So the emitted errors are a sound subset of TypeScript's.

`any`/`unknown` bindings are exempt (they default to `undefined`). `var` and `let` are treated the same by this analysis; `const` always has an initializer ([ADR-00209](../adr/ADR-00209.md)) so it's assigned at declaration.

### Options considered

- **One unified pass vs. two passes.** Recommended: **one pass** with the per-binding state lattice above — TDZ and definite-assignment are the same traversal answering "is this read legal," and sharing the walk avoids two near-identical expression visitors. A binding flows TDZ → Declared-unassigned → Assigned in one sweep.
- **Resolver vs. emitter.** Recommended: **resolver**, as a new `resolver/readability.go` mirroring `rename.go`'s scope-aware `rewriteStmt`/`rewriteExpr` traversal (but read-only, collecting/checking rather than rewriting). Rationale: these are *early* errors (whole-program reject before run), the resolver already has the scope-frame machinery and a complete 64-case expression walker to model against, and it keeps flow analysis out of the linear emitter where a CFG doesn't fit.
- **Reusing `scanExprFV`.** Rejected as the core: it returns an unordered free-variable *set*, but definite-assignment needs evaluation-order traversal (read-vs-assign sequencing, branch joins). It can still inform the closure-capture handling.

## Open questions

- **Merge precision for `try`/`switch`/labeled `break`.** The conservative defaults above are sound (no false positives) but may miss real errors; how much precision is worth it in V1 vs. deferred is an implementation call.
- **Closure capture of a not-yet-assigned binding.** A binding read only inside a closure is exempt from both TDZ and definite-assignment in V1 (can't prove when the closure runs). Confirm this exemption is applied uniformly so no false positive escapes through a callback.
- **Where binding type comes from.** Exempting `any`/`unknown` needs the binding's type; if the resolver can't cheaply know it, the pass errs toward exempt. Decide whether this pass consumes an existing type signal or does a shallow local inference for the common annotated/`= literal` cases.
- **One pass or staged delivery.** TDZ (#2) is self-contained and higher-certainty (no false-positive risk — it's textual order, not flow); definite-assignment (#1) carries the false-positive risk. Even under one design, TDZ could land first as a lower-risk stage, with definite-assignment gated behind more testing. Decide at implementation time.
