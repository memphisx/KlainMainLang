# ADR-01036: Test and conformance scratch off the SSD — `KML_SCRATCH`, RAM-drive wrappers, runtime C sidecars compiled once

- **Date**: 2026-09-21

## Context

The E2E suite (about 3,200 tests) and the Test262 runner (about 53,000 files per lane) each build a native program per case: IR, the embedded C runtime sources that program needs, objects, an executable — all deleted seconds later. On a development laptop whose SSD is soldered that churn is a real cost, and a day of two full suites plus a conformance run had put tens of GB on the drive. Speed is not the motive: measured on the Windows box, writing a 600 KB artifact takes 0.65 ms against roughly 1,100 ms of `clang -O2` for the same program.

## Investigation

Where the writes go:

- `t.TempDir`, the compiler's own build directories (`os.MkdirTemp` in `main.go`, `hostclang.go`) and clang's temporaries all follow the process temp root — `TMP`/`TEMP` on Windows, `TMPDIR` elsewhere.
- The conformance runner writes to `-workdir`, default `.conformance-out` inside the repository. It already reuses one set of file names per worker and removes each binary after its run, and writes nothing for a file that fails before codegen.
- Both harnesses wrote every embedded C runtime file a program uses (`dtoa`, the bigint/crypto backends, the JSON tree, the thread pool, …) into the program's directory and had clang recompile it from source — per test, per conformance file. The sources are identical every time; only the Windows platform shim was already compiled once (`win32ShimObject`).
- Cross-volume moves were already safe: `RunClangLink`/`moveFile` fall back to copy.

Alternatives considered: documenting the `TMP`/`TEMP`/`TMPDIR` trio instead of adding a variable — rejected, because it does not cover the conformance workdir and the right member of the trio differs per host; pointing `GOCACHE` at the scratch too — left to the user, since an empty build cache costs a full rebuild of the compiler on every run.

## Decision

1. **`KML_SCRATCH`** (`internal/scratch`): when set, `Apply` creates `<root>/tmp` and sets `TMP`, `TEMP` and `TMPDIR` to it for the process and so for every child. Called from `tests/main_test.go`'s `TestMain` and from `tools/conformance`, whose default workdir becomes `<root>/conformance-out/run-<pid>` (an explicit `-workdir` still wins).
2. **Runtime C sidecars are compiled once.** `llvm.CSource.CachedObject(cacheDir, compileFlags)` compiles a member to `<name>-<hash>.o` and returns that path on every later call. The hash covers the source, the member's own flags, the caller's code-generation flags, `HostClangArgs()`, the host OS and the Windows compat header, so a rebuilt compiler, an ASan build or a cross target never links a stale object. Concurrent builders are safe: an in-process mutex per object, and across processes each writes a pid-named temp object that a rename publishes (a lost race reuses the winner's). `-l`/`-L`/`-Wl,` flags are dropped from the `-c` line; the caller still puts the member's flags on the link line. The C++ and moc members return `ErrCObjectUncacheable` and are built from source as before, as is any member whose cached compile fails — so a genuine compile error still surfaces through the normal clang path.
   - Test harness: every `append*` helper goes through `sidecarArg`, which carries the code-generation flags already on the clang line (`-O`, `-f…`, `-g`, `-D`, `-m`, `-std=`, `-I`) into the sidecar's compile. Cache: `<temp root>/klainmain-cobj`.
   - Conformance runner: `<workdir>/cobj`, flags `-O2`.
   - The CLI driver is unchanged: a user's build compiles its sidecars from source.
3. **`tools/ramdisk/run.sh`** (macOS `hdiutil` RAM device + APFS; Linux tmpfs mount as root, else a directory under `/dev/shm`) and **`run.ps1`** (Windows, OSFMount's command line; reuses an existing drive letter) create the volume, export `KML_SCRATCH` and `GOTMPDIR`, run the command, tear down. README documents both and the Docker `--tmpfs …:exec` form.

## Implementation notes

`internal/scratch/scratch.go`, `codegen/llvm/cobj_cache.go`, `tests/main_test.go`, `tests/compiler_test.go`, `tools/conformance/main.go`, `tools/ramdisk/run.sh`, `tools/ramdisk/run.ps1`, `README.md`.

On Windows the link line no longer names a `.c` file when every sidecar is cached, so `win32CompileArgs` adds no `-I`; the cached compile goes through `ClangCommand`, which does.

## Side effects discovered

OSFMount's command line needs an elevated shell to create or remove a drive; `run.ps1` therefore reuses a drive that already exists and leaves it in place.

## Verification

Windows x64. With `KML_SCRATCH` and `GOTMPDIR` on a 12 GB OSFMount RAM drive: targeted E2E tests covering the fs, bigint, JSON, float-format, crypto, URLPattern, child_process, thread-pool and goroutine-runtime sidecars pass, and `<root>/tmp/klainmain-cobj` holds one object per member and flag set. `run.ps1` verified for the reuse path and exit-code propagation; creating/removing the drive from the script needs elevation and was done by hand. `run.sh` is written from the documented `hdiutil`/tmpfs interfaces and is **not yet run** on macOS or Linux.
