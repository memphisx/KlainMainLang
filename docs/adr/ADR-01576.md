# ADR-01576: Bounded codegen expansion of self-nesting generic interfaces

- **Relations**: Extends ADR-01573, Implements TDD-00230
- **Date**: 2026-10-11

## Context

A scan of the TypeScript suite in the js lane (each case in its own
process, with 20-second and 4 GB limits) found `infinitelyExpandingTypes1.ts`
and the `promisePermutations` cases spending their time and memory in
`layoutKey`. In the js lane, codegen instantiates interfaces such as
`interface List<T> { next: List<T>; owner: List<List<T>> }` itself, because
strict mode's early rejection doesn't apply. Two problems compounded:

- The depth cap (8) bounds depth but not breadth. Every self-referencing
  member multiplies the work at each level.
- `layoutKey` spells out every nested object in full. The key of such a
  type is therefore exponential in the nesting, and a single 289 MB string
  ran the process out of memory.

## Decision

- Within one top-level generic interface instantiation, each
  sub-instantiation is built once per depth and type arguments
  (`genericAtDepth`). The depth cap truncates an instantiation identically
  at the same depth, so the result is the same type the cap produced
  before. A first attempt budgeted the instantiation count instead. It
  failed `TestE2EGenericInterfaceSelfReturningMethods`: the budget ran out
  within the first branch walked, which cut a `Deferred<U>`'s later members
  short only a level or two down.
- Within one call, `layoutKey` caches the key of each object type it has
  already rendered, by its field slice.
- A nested object key longer than 128 bytes is replaced by its SHA-256
  digest. Keys are compared and used as map keys, never parsed.

## Verification

- `infinitelyExpandingTypes1.ts` and `promisePermutations.ts` compile in
  under a second (the latter took 27–44 seconds).
- `TestE2EExpandingInterfaceAndSelfReferentialLoopCompileJS`.
- Linux (DeskMini kmlbox): the TypeScript suite in both lanes and full
  gates.
