# TDD-00050: Reserved ambient-global names — reject by default, opt-in real-JS shadowing

- **Status**: Implemented
- **Date**: 2026-08-10

## Context

Raised directly: real browsers (and Node) genuinely let a program do `const Math = {}` — JS has no reserved words for its own built-in globals, `Math`/`process`/`fetch`/etc. are ordinary, reassignable bindings like any other. [TDD-00049](TDD-00049.md) already found and fixed this for Category B (`fs`/`path`/etc. — now import-gated, with correct real-JS-style shadowing once imported). It deliberately left Category A (`Math`/`JSON`/`console`/…) and Category C (`process`) unfixed — a local variable using one of those names still silently miscompiles, calls routing to the built-in instead of the user's own value, exactly the bug class TDD-00049 closed for Category B.

The ask here is different from TDD-00049's fix, though: not "restore correct real-JS shadowing" as the default, but the **opposite** — reject shadowing these names as a compile error by default (stricter than real JS, a deliberate safety net), with a compiler flag for anyone who explicitly wants real JS/browser semantics instead.

**A structural discovery changes this TDD's scope, found while investigating**: not every built-in name is resolved the same way today.

- `Math`, `JSON`, `console`, `process`, `crypto`, `performance`, `Object`/`Array`/`String`/`Number` (as static namespaces), `Infinity`/`NaN`, and the ~19 bare global functions (`parseInt`, `fetch`, `setTimeout`, `Symbol`, …) are all resolved as plain `*ast.Identifier` references — codegen-level, resolvable at any point after parsing.
- `Map`, `Set`, `Date`, the `Error` family (`TypeError`/`RangeError`/`SyntaxError`/`EvalError`/`URIError`/`ReferenceError`), `RegExp`, `URL`, `EventSource`, `WebSocket`, `URLSearchParams`, `Headers`, `Request`, `XMLHttpRequest`, `ArrayBuffer`, `TextEncoder`/`TextDecoder`, `EventEmitter`, and the 8 TypedArray constructors are **parser-level special forms**: `parser/parser_literals.go`'s `parseNew` does a bare textual `switch` on the identifier immediately after `new`, unconditionally, before any scope/symbol-table concept exists in this compiler at all. `new Map()` can never mean anything but the built-in — there is no mechanism today by which a user's own `class Map {}` could ever be reachable through `new Map()`.

Real permissive shadowing is cheap for the first group (reuses `e.lookup()`-first-then-fallback, a pattern `NaN`/`Infinity` already use — see Investigation) and expensive for the second (needs the parser to stop committing to the built-in meaning before any resolution phase exists — a real restructuring of `new`-expression handling). **Decided directly** (asked, not assumed): the second group stays reserved even under the permissive flag — default-reject applies to both groups uniformly, but the flag only lifts the restriction for the first.

## Investigation

- `parser/parser_literals.go`'s `parseNew` (confirmed by direct read): a `switch nameTok.Literal` immediately after consuming `new`, 23 explicit cases plus `typedArrayElemKinds` (8 more names) checked in the `default` branch before falling through to a generic `new SomeUserClass()` parse. This is genuinely a parser production, not a codegen dispatch — the AST node type itself (`*ast.NewMapExpression` vs. a generic `*ast.NewExpression`) is decided here, permanently, before `resolver`/`codegen` ever run.
- `codegen/llvm/emit_exprs.go`'s identifier-evaluation case, and `emit_exprs_types.go`'s `inferExprType` `*ast.Identifier` case, both already check `e.lookup(ex.Name)` **first**, falling back to `NaN`/`Infinity` only on a lookup miss — with an explicit comment confirming this was deliberate: "only after a local lookup miss, so a user-declared variable of the same name still shadows them." This is the exact mechanism the permissive flag needs for every other Category-A/bare-global-function name — it already exists and already works correctly for two of them.
- By contrast, every `Math`/`JSON`/`console`/`process`/`crypto`/`performance`/`Object`/`Array`/`String`/`Number`-as-namespace dispatch site (`emit_call.go`, `emit_exprs_member.go`, `emit_exprs_types.go`) and every bare-global-function case (`emit_call.go`'s "Global built-in functions" switch: `parseInt`, `parseFloat`, `isNaN`, `isFinite`, `fetch`, `btoa`, `atob`, `encodeURIComponent`, `decodeURIComponent`, `encodeURI`, `decodeURI`, `setTimeout`, `setInterval`, `setImmediate`, `clearTimeout`, `clearInterval`, `clearImmediate`, `structuredClone`, `Symbol`) matches on bare `id.Name` unconditionally — no `e.lookup()` check first. That inconsistency (some built-ins shadow correctly, most don't) is the actual root cause both of the original bug and of why "just flip a flag" isn't already possible.
- `resolver/rename.go`'s `scope.bind(name)` is the single choke point every local binding already passes through (function/arrow params via `bindParams`, `VarDeclaration`, `ArrayDestructuring`/`ObjectDestructuring`, `ForOfStatement`/`ForInStatement`, `catch` params) — the natural hook point for reject-by-default, alongside `resolver.go`'s `mangleFileDecls` for top-level declarations. Generic type parameters (`function f<Math>()`) bind through the same `scope.bind` call but have no `ast.Pos` of their own anywhere in the AST (`TypeParams []string`, no position tracking) — **deliberately out of scope**: an extremely low-value edge case, and the enclosing declaration's own position is the best available fallback if ever checked, not attempted here.

## Design

### Two name tiers

| Tier | Names | Under `strict` (default) | Under `permissive` |
|---|---|---|---|
| **1 — plain identifiers** | `Math`, `JSON`, `console`, `process`, `crypto`, `performance`, `Object`, `Array`, `String`, `Number`, `Infinity`, `NaN`, `parseInt`, `parseFloat`, `isNaN`, `isFinite`, `fetch`, `btoa`, `atob`, `encodeURIComponent`, `decodeURIComponent`, `encodeURI`, `decodeURI`, `setTimeout`, `setInterval`, `setImmediate`, `clearTimeout`, `clearInterval`, `clearImmediate`, `structuredClone`, `Symbol` | Rejected | Real shadowing — `e.lookup()` checked first at every dispatch site, exactly like `NaN`/`Infinity` already do |
| **2 — parser-level `new` forms** | `Map`, `Set`, `Date`, `Error`, `TypeError`, `RangeError`, `SyntaxError`, `EvalError`, `URIError`, `ReferenceError`, `RegExp`, `URL`, `EventSource`, `WebSocket`, `URLSearchParams`, `Headers`, `Request`, `XMLHttpRequest`, `ArrayBuffer`, `TextEncoder`, `TextDecoder`, `EventEmitter`, `Int8Array`, `Uint8Array`, `Int16Array`, `Uint16Array`, `Int32Array`, `Uint32Array`, `Float32Array`, `Float64Array` | Rejected | **Still rejected** — decided directly, see Context |

Category B (`fs`/`path`/`os`/`querystring`/`assert`/`http`/`cluster`/`Memory`) is **not** part of either tier — [TDD-00049](TDD-00049.md) already made these ordinary, unreserved identifiers outside of a file that actually imports them; nothing to protect here.

### New compiler flag: `-globals=strict|permissive` (default `strict`)

Mnemonic match for the existing `-mm=manual|gc` style (`main.go`). `strict` is the default specifically because it's the *new*, stricter-than-real-JS behavior being added — existing programs that happen to declare something named `Math` today are already hitting the silent-miscompile bug this closes, so `strict` becoming the default is a pure improvement, not a behavior change worth gating behind opt-in.

### `strict` mode (default): reject at every binding site

A validation pass alongside (not replacing) `resolver/rename.go`'s existing traversal: at every point `scope.bind(name)` is already called (function/arrow parameters, `let`/`const`/`var`, array/object destructuring, `for...of`/`for...in` loop variables, `catch` parameters) and at every top-level declaration (`resolver.go`'s `mangleFileDecls` loop), check `name` against the combined Tier 1 ∪ Tier 2 set and reject with a clear error (`'Math' is a reserved built-in name — pass -globals=permissive to allow shadowing it`) if `-globals=strict` (or the flag is unset).

Implementation shape avoids restructuring every function in `rename.go` to return `error` (none do today): thread a single `*error` slot through the already-passed-everywhere `lookupTable` struct, written once by the first violation found during the traversal, checked by the caller (`resolver.go`) immediately after `renameFile` returns — the traversal always completes regardless (nothing after the first violation needs to keep succeeding), so a first-write-wins pointer is sufficient without early-exit plumbing.

### `permissive` mode: real shadowing for Tier 1, `e.lookup()`-first

Every Tier 1 dispatch site across `emit_call.go`/`emit_exprs_member.go`/`emit_exprs_types.go` (member-call switches, property-read switches, both type-inference mirrors, and the bare-global-function switch) gets the same one-line change `NaN`/`Infinity` already have: check `e.lookup(id.Name)` (does a real local/global binding already exist for this name?) before falling through to the built-in behavior. Since `strict` mode structurally guarantees no such binding can ever exist, this check is a no-op — provably safe — whenever `-globals=strict`; it only ever matters, and only ever fires, under `-globals=permissive`.

Tier 2 gets no codegen change under either mode — `strict` rejects the declaration at the resolver level (the same validation pass as Tier 1), and `permissive` has nothing to lift, by decision.

## Open questions

- **Exact flag name/values**: `-globals=strict|permissive` proposed for consistency with `-mm`; not bikeshed further here.
- **Error message wording** for a Tier 2 rejection under `permissive` mode — should it explain *why* (parser-level, not liftable) or just reject the same as `strict`? Leaning toward a distinct message mentioning the constructor-level limitation, so a permissive-mode user isn't confused about why `-globals=permissive` didn't actually unblock `class Map {}`.
- **Generic type parameters** (`function f<Math>()`) are deliberately unchecked (no position info available, extremely low value) — worth a one-line note in whatever ships so it's a known, accepted gap rather than a silent one.
- **Does `strict` mode's rejection also cover a *type-position* reference** (`let x: Math` where `Math` was never a real type) — out of scope here; this TDD is about binding/declaration collisions, not type-name resolution, and none of Tier 1's names are meaningful in type position today anyway.
