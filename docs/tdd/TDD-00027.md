# TDD-00027: `http.close()` — listener teardown

- **Status**: Implemented ([ADR-00102](../adr/ADR-00102.md))
- **Date**: 2026-08-05

## Context

`http.listen()` still never returns on its own — [TDD-00019](TDD-00019.md)/[ADR-00079](../adr/ADR-00079.md) added `process.on('SIGINT'/'SIGTERM', handler)` so a handler can run cleanup and call `process.exit()`, but that ends the whole *process*, not the listener specifically. This is the last open row in [HTTP-SERVER.md](../status/HTTP-SERVER.md) (`.close()`, ❌) and TDD-00019's own Open Questions section explicitly left "whether a future `.close()` API should integrate with the same pending-flag mechanism, or be a fully separate concept" undecided. The motivating use case is a program (typically a test) that wants to start a server, do some work against it, and then genuinely stop serving and let the rest of the program (or the process itself) continue/exit — without an external `kill`.

## Design

### Shape: bare global function, not a `Server` handle

`http.close()` — a bare global function, zero arguments, `void` return, exactly like `process.exit()` and `http.listen` itself. **Not** a method on a `Server`-like object returned by `http.listen()`. This isn't a stylistic choice: `http.listen()`'s call to `@__kml_event_loop_run()` is a single blocking call — the entire event loop lives inside it. There is no point in a program's control flow, before this feature or after it, where TS code executes *while `http.listen()`'s own call frame is still on the stack but not itself inside the loop* — the only code that ever runs "at the same time" as the loop is code the loop itself calls back into: a request handler, a `setTimeout`/`setInterval` callback, or a `process.on(...)` handler. `http.close()` can therefore only ever be *reached* from one of those three places. A returned handle object would have nowhere meaningful to be held — the sequential code textually after `http.listen(...)` in a user's `main()` doesn't run concurrently with the server the way it does in real Node (where `listen()` returns immediately and the event loop keeps running after `main` script execution "finishes"). Restructuring this compiler's whole-program execution model so the event loop runs implicitly at the end of `main()`, Node-style — which would let `http.listen()` return a real handle synchronously — is a materially larger, higher-risk redesign, explicitly out of scope here.

### Mechanism: direct mutation, not the SIGINT/SIGTERM pending-flag indirection

`process.on('SIGINT'/'SIGTERM', ...)` ([TDD-00019](TDD-00019.md)) uses a `volatile i8` pending-flag checked at the top of `outerloop:`, specifically because a *real OS signal* can interrupt the program at an arbitrary, potentially-unsafe instruction — the raw handler must do the provably-safe minimum and defer real work to ordinary control flow. `http.close()` has no such hazard: it is only ever invoked as an ordinary function call from code the loop is already synchronously running (a handler body, a timer callback, a signal-handler closure already itself running from safe control flow per TDD-00019's own design). There is nothing async-signal-unsafe about mutating `@__kml_listen_fd` and calling `close()` immediately, inline, at the `http.close()` call site itself. This also answers TDD-00019's open question: `.close()` is a **fully separate mechanism**, not integrated with the pending-flag machinery.

`__kml_http_close()` (new, `runtime_http.go`):
```llvm
define void @__kml_http_close() {
entry:
  %fd = load i32, ptr @__kml_listen_fd, align 4
  %active = icmp sge i32 %fd, 0
  br i1 %active, label %doclose, label %done

doclose:
  call i32 @close(i32 %fd)
  store i32 -1, ptr @__kml_listen_fd, align 4
  br label %done

done:
  ret void
}
```
Idempotent and safe to call redundantly (twice, or with no listener ever started) — a no-op when `@__kml_listen_fd` is already `-1`, matching Node's own tolerance of a redundant `.close()`.

### Connection draining: `@__kml_conn_active`

Node's `server.close()` semantics: stop accepting *new* connections immediately, let already-open ones finish naturally. Implemented via a new `i64` global, `@__kml_conn_active`, tracking how many connection-table entries currently have `fd >= 0`:

- Incremented once, in `__kml_http_append_conn` (`runtime_http.go`), right after a new connection's `@__kml_conn_len` is bumped.
- Decremented at both of `buildHTTPDispatcher`'s existing connection-finish sites (`emit_http.go`'s `parseL` — normal completion — and `noReqL` — malformed/aborted request), alongside the existing `store i64 -1, ptr %fdPtr` at each.
- Folded into `__kml_event_loop_run`'s `scandone` block, which computes the loop's *only* exit condition:
  ```llvm
  %anywork0 = or i1 %havetimer, %haslistener
  %anywork = or i1 %anywork0, %hasactiveconns
  ```
  so the loop keeps servicing already-accepted connections (`checklistener` already gates new `accept()`s on `haslistener`, so this doesn't reopen accepting) until they've all naturally finished, even after the listener itself is gone.

**Alternative considered and rejected**: skip draining, document dropped in-flight connections as a V1 limitation. Rejected — the fix is cheap (one global, roughly ten lines total across two files) and the dropped-connection failure mode (a client-visible hung/reset connection) is exactly the kind of timing-dependent bug this codebase has hit before ([ADR-00052](../adr/ADR-00052.md), [ADR-00098](../adr/ADR-00098.md)) and is worth avoiding outright rather than documenting around.

Known interaction, not a bug: a still-running (uncancelled) `setInterval` anywhere in the program keeps `havetimer` true forever (`reschedule` never marks a repeating timer done), so `.close()` alone will not make `__kml_event_loop_run()` return while one is active — this mirrors real Node (`server.close()` doesn't end the process if other timers/handles are still active) and isn't addressed by this feature.

### Clustering scope: single-process only

Every relevant global (`@__kml_listen_fd`, `@__kml_conn_data`/`@__kml_conn_active`, ...) lives in per-process address space — `fork()` in `__kml_http_cluster_fork` ([TDD-00025](TDD-00025.md)) gives each worker an independent copy, with zero IPC between them. `http.close()` called inside one worker closes only that worker's own listening-socket copy and stops only that worker's own loop; sibling workers are unaffected and keep serving on their own fd copies. **Documented V1 scope, not addressed here**: a full-cluster shutdown still requires the existing external-signal-to-the-whole-process-group approach the test harness's `startHTTPClusterServer` cleanup (`tests/http_test.go`) already uses. No new IPC machinery is attempted.

### Compile-time guard: still only one `http.listen` call site

`buildHTTPDispatcher` emits a fixed-name function, `@__kml_http_dispatch`, relying on "only one `http.listen` call site is ever reachable in a program" — true before this feature because the first call never returned, so a second call site was always dead code. `.close()` breaks that: code textually after `http.listen(...)` (including a second `http.listen(...)` call) can now genuinely execute. A second call site would otherwise fail as a confusing duplicate-symbol error from the LLVM backend. This feature adds an explicit compile-time guard (`emitHTTPListen` rejects a second call site with a clear error) rather than attempting to support multiple listeners — a larger scope change deferred indefinitely.

### The trailing `unreachable`

`emitHTTPListen` currently emits `unreachable` right after `call void @__kml_event_loop_run()`, on the correct-at-the-time assumption that the call never returns. This is removed. No other IR change is needed — the call was always an ordinary non-terminator instruction; removing the following `unreachable` lets Go-side codegen naturally continue emitting whatever AST node comes next into the same live basic block, exactly as any two ordinary consecutive statements already do. This project's compiler has no separate type-checker notion of "never returns" (confirmed: no `TypeNever`/dead-code-diagnostic machinery exists anywhere) — "never returns" was represented purely as this one `emitTerminator("unreachable")` call plus the emitter's own dead-code-after-terminator skip, so no parser/type-checker changes are needed elsewhere.

One concrete pre-existing code path becomes newly live: `EmitProgram`'s tail (`emitter.go`) calls `__kml_timer_drain()` (if the program ever used timers) and then `ret i32 0`. Both were previously unreachable no-ops whenever the last live top-level statement was `http.listen(...)`. After this change they run for real once `http.listen()` returns — but `__kml_event_loop_run` itself already drains every due one-shot timer as part of keeping `anywork` true before it can ever reach `alldone`, so `__kml_timer_drain()`'s post-loop call remains a genuine no-op in this scenario; `ret i32 0` becomes the program's real, natural exit code absent an explicit `process.exit()`. Confirmed safe by inspection, no code change required.

## Open questions

- None blocking. Genuinely deferred, not decided here: whether a future `{ workers: N }` full-cluster `.close()` (via some IPC/shared-memory mechanism) is ever worth building — no known use case requires it today, the existing process-group-signal approach already covers it externally.
