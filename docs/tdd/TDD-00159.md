# TDD-00159: `crypto.createHash` — a faithful Node Hash object

- **Status**: Implemented
- **Date**: 2026-09-02

## Context

TDD-00158 shipped the Node-faithful HTTP `'upgrade'` event so a WebSocket
server can be written against Node core (`server.on('upgrade', …)`) rather
than only the bespoke `klain:ws` convenience. But that faithful path is
**incomplete**: completing a WebSocket handshake by hand requires computing
`Sec-WebSocket-Accept = base64(sha1(key + GUID))`, and Node code does that
with `crypto.createHash('sha1').update(key + GUID).digest('base64')`. This
compiler exposes no `crypto.createHash`, so the hand-rolled faithful upgrade
can't actually run as written for Node — you'd have to bring your own SHA-1.
"`klain:ws` computes it internally" does not make the *faithful* path
faithful; either the Node code runs unchanged or it doesn't.

`crypto.createHash` is also a broadly-useful Node primitive in its own right
(content hashing, etags, checksums), so it is worth doing properly rather
than as a WebSocket-driven one-off.

## Design

Node: `crypto.createHash(algorithm)` returns a `Hash` (a Transform stream in
Node, but universally used as `.update(data).digest(encoding)`). Scope V1 to
that surface:

- **`crypto.createHash(algorithm: string)`** — `algorithm` a string literal;
  one of `md5`/`sha1`/`sha256`/`sha384`/`sha512` (the common set; others are
  a clean rejection). Returns a `Hash` handle.
- **`.update(data)`** — `data` a `string` (UTF-8 bytes) or a
  `Buffer`/`Uint8Array`/`ArrayBuffer` (the `emitCryptoBufferSource` sources
  the subtle APIs already accept). Appends to the handle's accumulation
  buffer; returns the handle (chainable), matching Node.
- **`.digest(encoding?)`** — `'hex'` or `'base64'` return a `string`; omitted
  returns a `Buffer` (Uint8Array). Other encodings (`base64url`, `latin1`,
  `binary`) are a clean rejection in V1. Computes over the accumulated bytes.

**Accumulate-then-digest, not streaming.** The handle holds a growing byte
buffer; `.update` appends; `.digest` runs the existing one-shot
`__kml_crypto_digest(hashId, buf, len, out, outLen)` (OpenSSL `EVP_Digest`
/ CommonCrypto) over the whole buffer. The digest of concatenated updates is
bit-identical to a streaming digest, so this is faithful in observable
output; internal streaming (`EVP_DigestUpdate`) is a memory/perf refinement
recorded as future work, not a behavior difference (the project's standing
"faithful now, perf later" rule). Reusing the existing primitive means the
only new backend code is adding `md5`.

**Backends.** `__kml_crypto_digest`'s algorithm map (crypto_openssl.c,
crypto_commoncrypto.c) currently covers sha1/256/384/512 (ids 1–4). Add
`md5` as id 5 (`EVP_md5()` / `CC_MD5_*`). `createHash`'s algorithm-name →
id map lives in the emitter (distinct from `subtleHashID`'s WebCrypto
`"SHA-256"` spelling — Node's `crypto` uses the OpenSSL lowercase names).

**Handle shape.** A `HashType` (a bare tagged ptr, like the klain:ws handle)
pointing at a `{ i64 hashId, ptr buf, i64 len, i64 cap }` struct. `.update`/
`.digest` route by `IsHash` receiver type in emit_call.go. The encoders both
exist: `__kml_buf_hex_enc` (hex), `__kml_base64_encode_bytes` (base64); the
no-encoding path wraps the raw digest bytes in a `Buffer`.

## Open questions

All three original deferrals are **closed by ADR-00637**:

- ~~**Streaming vs accumulate.**~~ Done — `Hash`/`Hmac` now hold the backend's
  real streaming context (`EVP_MD_CTX`/`EVP_MAC`, CommonCrypto `CC_*`/`CCHmac`);
  no input buffering.
- ~~**`createHmac`.**~~ Done — `crypto.createHmac(algo, key)` with the same
  `.update`/`.digest` surface; Wikipedia HMAC-SHA256 vector verified.
- ~~**Full encoding set.**~~ Done — `hex`/`base64`/`base64url` (byte-exact),
  `latin1`/`binary` (sharing the UTF-8-only string caveat), or a `Buffer`.

Remaining (genuinely out of scope, not faithfulness gaps): `.update`'s
optional `inputEncoding` for `'hex'`/`'base64'` string inputs (V1 treats a
string as UTF-8), and `Hash` as a full `stream.Transform`.
