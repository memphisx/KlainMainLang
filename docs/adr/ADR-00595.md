# ADR-00595: Nested patterns and defaults in destructuring assignment

- **Relations**: Extends [ADR-00160](ADR-00160.md), [ADR-00161](ADR-00161.md); brings the assignment form to [ADR-00193](ADR-00193.md)/[TDD-00065](../tdd/TDD-00065.md) declaration-form parity
- **Date**: 2026-09-01

## Context

Destructuring *assignment* (`[a, b] = e`, `({ x } = e)` — targets are
already-declared variables, not a fresh `const`/`let`) was strictly flatter than
the declaration form: every target had to be a plain identifier, with no nested
patterns and no per-element defaults (ADR-00160's V1 scope). The declaration form
already supported both via `unpack{Array,Object}PatternInto`. This asymmetry was
five separate caveats across the array- and object-destructuring rows.

## Decision

Replace the flat assignment-form handlers with a recursive pair
(`emitDestructAssignArrayElems` / `emitDestructAssignObjectProps`) that mirrors
the declaration-form unpackers but stores into existing symbols instead of
defining new ones:

- **Nested patterns**: a target position that is itself an array/object literal
  recurses. The source element is loaded out-of-bounds-safely (OOB → `(null, 0)`
  for a nested array, a zeroed stand-in for a nested object), exactly as
  `unpackNestedArrayElem` does, so a short source never dereferences null.
- **Array-element defaults** (`[a = 1] = e`): the array position uses
  out-of-bounds as the presence signal (no nullable requirement), matching the
  declaration form.
- **Object-property defaults** on a nullable-reference field (null is the
  presence signal) are supported — shorthand `{ x = default }` and keyed
  `{ k: x = default }`. (The shorthand needed a parser change, done in the
  follow-on ADR-00597.)
- **Rest** (`[a, ...rest] = e`) and the plain-leaf paths are preserved unchanged.
  Compound ops and object rest (`{ ...rest } = e`) stay rejected.

An array-typed *field* nested under an object pattern loads the `{ptr, i64}`
aggregate directly (it is stored inline in the struct), not via `loadArrayElem`.

Null-vs-`undefined` note: like the declaration form, a default fires on `null`
(the compiler's only "absent" signal for a reference), a deliberate divergence
from JS's `undefined`-only trigger — consistent across both destructuring forms.

## Verification

New E2E tests: nested array (`[[a,b],[c,d]] = grid`), nested object
(`({ p, q: { r, s } } = obj)`), an array field inside an object pattern
(`({ arr: [x, y], n: z } = mixed)`), and an array-element default
(`[d = 5, e = 6] = [99]`) — all match the declaration form and Node where they
agree. The existing array/object destructuring + assignment suites still pass.
Built and verified on Mac (Apple Silicon).
