# ADR-00365: In-scope Test262 subset counter beside the raw full-corpus number

- **Relations**: `Implements TDD-00121`
- **Date**: 2026-08-25

## Context

The conformance runner reports the full, unfiltered Test262 corpus — currently
10.9% overall. That number is honest but reads worse than the compiler's actual
in-scope correctness, because most of the corpus is out of this compiler's target
by construction: `intl402` (internationalization), `annexB` (legacy web-compat),
`staging` (not-yet-standard proposals), files flagged `raw`/`async`/`module`, and
files tagged with dynamic-model features (`Temporal`, `Intl.*`, `dynamic-import`,
`Proxy`, `Reflect`, `explicit-resource-management`, …). A reader seeing only 10.9%
cannot separate "fails the in-scope language" from "the corpus tests things never
claimed." TDD-00121 Track A adds a second number — the pass rate over the in-scope
subset — reported *beside*, never replacing, the raw number.

## Investigation

Direct frequency sampling of the checked-out corpus (`.test262/test`) grounded the
filter: `flags` are dominated by `generated` (17003, provenance — not scope-
relevant), `async` (5624), `noStrict` (2530), `module` (832), `raw` (32); the
largest out-of-scope `features` buckets are `Temporal` (6160+), `Intl.*`,
`dynamic-import` (~1000), `Proxy` (~400+), `Reflect.*`, `explicit-resource-
management`. In-scope-relevant tags (`TypedArray`, `BigInt`, `class*`,
`destructuring-binding`, `generators`, `Symbol.iterator`) are the ones a typed
subset does target, so they are deliberately *not* excluded.

The existing `parseFrontmatter` already extracted `includes`/`negative` with a
hand-rolled single-line flow-list regex (no YAML dep, per the zero-external-Go-deps
rule); `features`/`flags` share that exact shape, so the extraction generalized
into one `parseFlowList` helper rather than new bespoke parsing.

An alternative — detecting `eval(` usage textually to exclude the "eval as its own
assertion" majority — was rejected for Track A: it is not frontmatter-mechanical
(it reads the body), so it would make the denominator less auditable. The
feature/flag/category filter is fully reproducible from each file's own tags.

## Decision

- Extend `frontmatter` with `Features`/`Flags`, populated via a shared
  `parseFlowList(re, block)` helper (`reFeatures`, `reFlags`).
- Add `inScope(fm, category) bool`: out if category ∈ {`intl402`,`annexB`,
  `staging`}, or any flag ∈ {`raw`,`async`,`module`}, or any feature with an
  `Intl`/`Temporal` prefix or present in an explicit `outOfScopeFeature` deny-list
  (dynamic code/import, dynamic object model, realms, resource management, TCO,
  runtime decorators). Conservative by design — when in doubt a feature stays
  in-scope, which can only lower the in-scope number, never inflate it.
- Add `InScope` to `result`, set once in `runOne` after parsing frontmatter.
- `writeReport` gains a **## In-scope subset** section (passed/total/% over
  in-scope files, plus the count excluded and why) directly after the raw
  **## Overall**, and three in-scope columns on the per-category table. The raw
  Overall line is unchanged, byte-for-byte.

## Implementation notes

Single file: `tools/conformance/main.go`. The per-category aggregate struct gained
`inTotal`/`inPass` fields. The deny-list is a package-level `map[string]bool` with
per-group comments giving the rationale, so the scope definition is auditable in
place and iterated by reading the resulting in-scope failure buckets, not guessed
perfect up front. `Intl`/`Temporal` are prefix-matched in `inScope` rather than
enumerated (both are large, versioned tag families).

## Side effects discovered

None. The change is report-only: the corpus walked, the per-file compile/run, and
every existing section (phase summary, blocked-by histogram, reason buckets) are
untouched.

## Verification

`go vet` + `go build ./...` clean. Smoke run (`-limit 1500`, an alphabetical slice
of `annexB` + early `built-ins`, written to a scratch report) confirmed the section
renders and the filter behaves: `annexB` shows in-scope total 0 (correctly wholly
excluded), `built-ins` shows 290/414 in-scope. The representative full-corpus number
is produced by the batched `make conformance` run at end of session (per the
run-once standing rule), which also regenerates `docs/testing/CONFORMANCE-RESULTS.md`.
