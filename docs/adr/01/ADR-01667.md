# ADR-01667: Typed JSON keeps undeclared keys; `in` sees expandos

- **Date**: 2026-10-17

## Context

`const p: P = JSON.parse(text)` and `const p: P = await res.json()` projected the JSON onto `P`'s fields and dropped every other key. Node keeps all of them, because the annotation does not change the value. Separately, `"b" in o` answered `false` for a property added at runtime (`(o as any).b = 1`), although inspect, `Object.keys` and `JSON.stringify` already listed it.

## Decision

- `emitJSONProjectObject` ends with `emitJSONExpandoRest`. That calls `__kml_json_expando_rest` (`dynobjsrc/dynjsonnode.c`) with a table of the shape's field names. Every other key of the JSON object becomes an expando property, converted by `__kml_dynjson_from_node`. The projection sets `usedObjExtensible`, so inspect, keys and stringify read the extras.
- The static `in` with a string-literal key that the shape lacks asks `__kml_shape_expando_has`; before, it was a constant `false`.

## Side effects discovered

The key order of a projected object follows the declared type, with extras after the declared fields, rather than the JSON text. This divergence existed before this change and is disclosed on the JSON status rows.

## Verification

- `TestE2EJSONParseTypedKeepsExtraKeys` matches Node for nested objects, object arrays and the `in` operator.
- Verified on Mac.
