# ADR-00074: fetch() client parity — custom method, headers, request body

- **Relations**: Extends [ADR-00050](ADR-00050.md). Implements [TDD-00017](../tdd/TDD-00017.md). Superseded by [ADR-00130](ADR-00130.md) (its Request/Headers-class rejection only — the custom method/headers/body mechanism this ADR built is unchanged and still how a plain `init` object works)
- **Date**: 2026-07-29

## Context

`fetch()` was GET-only (`emit_fetch.go`'s own header comment said so plainly), the one gap left in this project's REST-API-interaction priority's client side — the server side already got symmetric capability in [ADR-00072](ADR-00072.md) (`req.headers`/`req.query`/`req.body`). Picked up as the next structural priority after [ADR-00073](ADR-00073.md) (`Promise.all`/`.race`/`.allSettled`) closed out the event loop's own roadmap. [TDD-00017](../tdd/TDD-00017.md) scoped the design (a second, optional `init` argument reusing this compiler's existing `Map<string,string>`/`FieldIndex`-on-inferred-type conventions rather than new `Request`/`Headers` classes); this ADR is that implementation.

## Investigation

- Verified every new `CURLOPT_*` constant directly against `curl.h` on this dev machine (`/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk/usr/include/curl/curl.h`), the same standard every existing libcurl constant in this codebase already documents: `CURLOPT_POSTFIELDS`=10015 (`CURLOPTTYPE_OBJECTPOINT`=10000 + 15), `CURLOPT_HTTPHEADER`=10023 (`CURLOPTTYPE_SLISTPOINT`=10000 + 23), `CURLOPT_CUSTOMREQUEST`=10036 (`CURLOPTTYPE_STRINGPOINT`=10000 + 36). Also confirmed `curl_slist_append`/`curl_slist_free_all`'s exact signatures from the same header.
- Read `emit_collections.go`'s `mapKeysAndVals` (already used by `map.entries()`/`map.forEach()`) and `emit_strings.go`'s `emitStringConcat` — both reusable as-is for building `"key: value"` header lines from a `Map<string,string>`, no changes needed to either.
- **Two real, correct-but-surprising behaviors were found only by testing against a real echo server, not by design review** — both confirmed as genuine libcurl behavior, not compiler bugs, and both caught by the new fuzz lane (`FuzzFetchInitOracle`) on its very first run, before any real `-fuzz` mode was even used:
  - Setting `CURLOPT_POSTFIELDS` (i.e. an `init.body`) with no explicit `method` implicitly switches the request into `POST` — confirmed directly (a local test server receiving a bare `{ body: "..." }` fetch reported `POST`, not `GET`), matching libcurl's own well-documented default behavior for that option.
  - An *explicit* `method: "GET"` alongside a `body` still sends a genuine GET with a body — `CURLOPT_CUSTOMREQUEST` overrides the auto-POST-from-`POSTFIELDS` default. Confirmed directly the same way, isolating it from the first case (which only applies when no method was given at all).
  - Both are now documented in `STATUS.md`'s `fetch(url, init)` row and this feature's example (`examples/fetch/fetch_init.ts`) rather than left as an implicit surprise.
- A related, unrelated staleness found while updating docs for this feature: `examples/fetch/fetch.ts`'s own header comment still said "no event loop yet, so two fetches issued before either is awaited would run one after another, not concurrently" and "GET requests only — no custom method, headers, or request body yet" — both false as of [ADR-00050](ADR-00050.md)/this ADR respectively. Fixed alongside this work (not deferred), along with two similarly stale sentences in the project's own project-direction section (the `emit_fetch.go` file-map row said "GET only"; the memory-management paragraph still said "no GC yet — every request currently leaks", stale since [ADR-00071](ADR-00071.md)).

## Decision

**`__kml_fetch_async(ptr url) -> ptr`** (runtime.go, [ADR-00050](ADR-00050.md)) grows to **`__kml_fetch_async(ptr url, ptr method, ptr headers, ptr body) -> ptr`**. The three new parameters are each nullable; the function branches on runtime nullness (`icmp ne ptr %x, null`) before calling the corresponding `curl_easy_setopt` — one shared piece of IR called from every `fetch()` call site in a program, some of which may pass an `init` object and some not. A plain `fetch(url)` call site passes all three as literal `"null"`, so it costs three extra folded `icmp`/`br` pairs and nothing else compared to before.

**`emitFetch`** (`emit_fetch.go`) now accepts 1 or 2 arguments. For the 2-argument form, it evaluates `init` once and checks `FieldIndex("method")`/`FieldIndex("headers")`/`FieldIndex("body")` on its inferred type directly — the exact same pattern `emit_http.go`'s `isPlainStringType`/`FieldIndex("headers")` check already established for `http.listen`'s optional response `headers` field ([ADR-00072](ADR-00072.md)). Each field present is resolved to a `ptr` value (a new `loadFieldValue` helper, a generalization of `emitResponseBody`'s existing GEP+load shape); each field absent passes `"null"`. Rejects at compile time (not silently) if `init` isn't an object at all, or if `method`/`body` are present but not plain strings, or `headers` is present but not exactly `Map<string, string>`.

**`buildFetchHeaderList`** (`emit_fetch.go`, new) builds a `struct curl_slist*` from a `Map<string,string>` value: walks `mapKeysAndVals`'s `{ptr, i64}` key/value arrays via a hand-rolled compile-time loop (own `fetchheaders.*` labels, matching this codebase's existing per-feature loop style rather than a new shared "generic loop" abstraction — `emit_promise.go`'s `emitPromiseLoop`, `emit_arrays.go`'s HOF loops are the same pattern, not factored further here either), builds each `"key: value"` line with `emitStringConcat`, and threads the growing list pointer through a single `alloca`, one `curl_slist_append` call per entry. A runtime-empty map naturally produces a null list (the loop just runs zero iterations) — no separate empty-map case needed.

**Memory**: the built `curl_slist`, like every other fetch-related allocation (the pending-fetch struct, the response buffer, the `Response` object itself), is never freed in `manual` mode — consistent with this feature area's already-documented "everything leaks, `-mm=gc` is the opt-in fix" characteristic ([TDD-00001](../tdd/TDD-00001.md)), not a new gap. `-mm=gc`'s Boehm collector couldn't reclaim it regardless of this choice: `curl_slist_append` is libcurl's own internal `malloc`, entirely outside Boehm's reach.

## Implementation notes

- `codegen/llvm/runtime.go`: `__kml_fetch_async`'s signature and body (three new nullable-checked `curl_easy_setopt` calls, verified `CURLOPT_*` constants documented above); new `ensureCurlSlist` (declares `curl_slist_append` only — no `curl_slist_free_all`, matching the deliberate no-free decision above).
- `codegen/llvm/emit_fetch.go`: `emitFetch`'s 1-or-2-arg dispatch and field validation; new `loadFieldValue`/`buildFetchHeaderList` helpers.
- `codegen/llvm/emitter.go`: new `usedCurlSlist` flag.
- `examples/fetch/fetch.ts`: stale header-comment fix (documented above).
- the project's own instructions: two stale-doc fixes (documented above), unrelated to this feature's own scope but found and fixed alongside it per this project's standing "fix bugs found during development" rule.

## Side effects discovered

None beyond the two libcurl behaviors and the doc staleness already described above (all documented, not silently left as surprises).

## Verification

- `go build .`, `go vet ./...`, `gofmt -l`, full `go test ./...` all green, including every pre-existing `TestE2EFetch*` test (confirming the `__kml_fetch_async` signature change didn't regress the plain `fetch(url)` path).
- `tests/fetch_test.go`, all against a local `httptest.Server` (deterministic, offline-capable, same convention the file's existing fetch tests already use): `TestE2EFetchCustomMethodHeadersAndBody` (method+headers+body together, round-tripped through a new `/echo` handler); `TestE2EFetchCustomMethodOnlyNoBody`; `TestE2EFetchHeadersOnlyDefaultsToGet`; `TestE2EFetchPlainCallStillWorksUnchanged`; `TestE2EFetchNonObjectInitRejected`/`TestE2EFetchInitWrongFieldTypesRejected` (compile-time rejection); `TestE2EFetchWrongArgCountRejected` updated to a genuine 3-argument case (2 arguments is now valid).
- `tests/fuzz_codegen_test.go`'s new `FuzzFetchInitOracle` ("Lane D", alongside [TDD-00014](../tdd/TDD-00014.md)'s existing lanes and [ADR-00073](ADR-00073.md)'s Lane C): chains 1-3 `fetch(url, init)` calls with randomized method/headers-presence/body-presence/content against a real local echo server built once and reused across iterations, checked against a Go-computed oracle. Caught both libcurl behaviors described in Investigation on its very first (non-`-fuzz`) run — the oracle itself was wrong twice before being fixed to match confirmed reality, not the compiler. Also fixed a latent, non-triggered bug in the oracle-comparison logic shared with [ADR-00073](ADR-00073.md)'s own Lane C: `compileAndRun` trims *all* trailing newlines off real program output, which a naive `strings.Join(wantLines, "\n")` oracle doesn't account for when the last printed value happens to be empty — fixed in both lanes with a matching `strings.TrimRight`. Run for 90s (442 executions, ~5/sec) after both fixes: zero failures.
- `examples/fetch/fetch_init.ts` (new): compiles and links cleanly. Running it against the real network in this environment hit the same restricted-egress behavior already documented for `examples/fetch/fetch.ts` (a 503/timeout from the sandbox's outbound proxy, not this compiler) — expected, not a regression; the deterministic local-server test suite and fuzz lane above are the real correctness evidence, this example is illustrative/documentation, matching [ADR-00073](ADR-00073.md)'s own precedent for the identical situation.
- `STATUS.md`/the project's own instructions updated per Investigation/Decision above; `docs/tdd/README.md`'s index and [TDD-00017](../tdd/TDD-00017.md)'s own `Status` line updated to `Implemented`, cross-referencing this ADR. `Makefile`'s `fuzz-codegen` target runs the new fuzz lane alongside the existing three.
