# ADR-00924: `any`-typed object/class fields, and evolving-any for null fields (TDD-00208)

- **Date**: 2026-09-13

## Context

A statically-shaped object literal or class could not declare a field of type
`any`/`unknown` — `containsDynamicElement` rejected it ("any/unknown is not yet
supported as an array element or object field type"), even though the array
analogue (`any[]`, TDD-00200) ships. An unannotated `#field = null` reassigned in
a method (`this.#field ??= 1`) inferred type `null` (a `ptr` slot) and emitted a
`double` into it — invalid IR. (Test262
`built-ins/.../logical-assignment/left-hand-side-private-reference-data-property-nullish.js`.)

## Decision

Support a bare `any`/`unknown` field as a NaN-box slot — the field-shaped
counterpart of the boxed-element array. This is **not** the runtime
dynamic-object model (TDD-00155): the field *set* stays static; only a field's
*value type* is `any`.

- **Gate.** `objectFieldDynamicRejected` no longer rejects any dynamic field:
  a bare `any` field is now a boxed slot, and a constrained-union field
  (`string | number`) was already supported (TDD-00119). (A constrained-union
  *array element* stays rejected — a separate, still-open case.)
- **Storage / box-unbox.** An `any` field occupies its normal `i64` slot holding
  a NaN box. Writes box (`coerce(v, TypeAny)`); reads yield the box, consumed by
  the existing dynamic-value paths (`toString`/`typeof`/`===`/JSON/spread/
  destructuring). Because these paths already existed for `any` locals and
  `any[]`, relaxing the gate covered read/write/JSON/console/`===`/`typeof`/
  destructure/spread/nested/arrays with no per-site changes.
- **Structural-coercion guard.** An object/class type with an `any` field can
  only be structurally coerced to another shape whose same field is also `any`:
  a NaN box and a concrete raw field have different layouts, so reading one as
  the other yields garbage (`{x:number}` passed where `{x:any}` is wanted → the
  bits of `5` read as a boxed double, `4.5`). `coerciblePure` now rejects such a
  boxedness mismatch cleanly, before its IR-equality shortcut (objects all share
  IR `ptr`). An object/array *literal* value is exempt — it is constructed
  against the target field type (boxing at construction), so the literal
  pre-check in object construction skips literal exprs.
- **Evolving-any field.** An unannotated `field = null`/`= undefined` that a
  method or the constructor later reassigns to a non-nullish value (or logically
  compound-assigns) is widened to a boxed `any` field — the class-field
  counterpart of ADR-00923's local-binding rule, scanned by
  `classFieldNullEvolves`.

## Implementation notes

- `codegen/llvm/emit_dynamic.go`: `objectFieldDynamicRejected` → always false.
- `codegen/llvm/emit_exprs_coerce.go`: `objectFieldBoxingCompatible` + its check
  before the IR-equality return in `coerciblePure`.
- `codegen/llvm/emit_objects.go`: the object-literal field pre-check skips
  object/array literal exprs (they hint-construct to the field type).
- `codegen/llvm/emit_classes.go`: `classFieldNullEvolves` (deep scan of
  constructor/methods/static blocks) widens a null-init field to `any`.

## Scope / not covered

- Arithmetic (`+`) and property/method dispatch (`.length`, `.toUpperCase()`) on
  an `any` value are a pre-existing general `any` limitation (identical for `any`
  locals), not field-specific — unchanged here.
- A materialized concrete object cannot be *adapted* to a differently-boxed
  object type (would need a runtime re-boxing copy); it is rejected cleanly. An
  object literal in that position works (constructed boxed).
