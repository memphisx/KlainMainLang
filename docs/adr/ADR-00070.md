# ADR-00070: Full-pipeline (codegen-through-binary) fuzz testing

- **Relations**: Extends [ADR-00068](ADR-00068.md). Implements [TDD-00014](../tdd/TDD-00014.md)
- **Date**: 2026-07-28

## Context

[ADR-00068](ADR-00068.md) fuzzed only the lexer and parser, deliberately deferring codegen and the compiled binary itself, on the grounds that mutated raw source bytes rarely stay syntactically valid long enough to reach codegen, and that a crash-only oracle can't catch a compiler that runs to completion and produces a *wrong* answer, only one that panics. [TDD-00014](../tdd/TDD-00014.md) scoped a design for going further: generate guaranteed-valid programs (rather than mutating raw text) using two different generators, one paired with a real correctness oracle and one aimed at broader language coverage with only a well-formedness check.

While prototyping the arithmetic-correctness oracle (before either lane existed as code), the very first hand-written repro — `10 / 0` — surfaced a real, separate bug: silently printing garbage instead of crashing or throwing. That's fixed in [ADR-00069](ADR-00069.md), a prerequisite for this ADR's Lane A (the oracle needed division by zero to have *some* defined, catchable behavior before it could safely generate division expressions at all).

## Investigation

Confirmed `tests/compiler_test.go` already exposes exactly the pipeline plumbing needed (`buildBinary`: parse → codegen → write `.ll` → `clang -O2` → binary path; `compileAndRun`: `buildBinary` + execute + capture stdout), reused directly rather than rebuilt.

Confirmed Go's native fuzzer supports `int64` as a fuzz-corpus parameter type directly (`f.Fuzz(func(t *testing.T, seed int64) {...})`), which meant the generator didn't need a hand-rolled byte-stream-to-PRNG scheme — `rand.New(rand.NewSource(seed))` from a fuzzed `int64` gives a fully deterministic, directly-fuzzable generator input.

Verified (`codegen/llvm/emit_exprs.go`) that `+`/`-`/`*` are emitted without `nsw`/`nuw` overflow flags (plain wraparound two's-complement) and that `/`/`%` on the default `number` (`i64`) type use `sdiv`/`srem` (truncating toward zero) — bit-for-bit what Go's own `int64` operators do, which is what makes Go arithmetic a valid oracle for this specific, deliberately non-JS-conforming subset (`number → i64`, not JS's float `number`).

While writing the oracle's Design section (before running anything), re-read the LLVM Language Reference on `sdiv`/`srem` and found a *second* UB case beyond zero-divisor: dividend `INT64_MIN` with divisor `-1` (the true quotient, `2^63`, overflows `i64`). [ADR-00069](ADR-00069.md)'s guard only covers the zero-divisor case. Decided not to fix this in the same pass — see Decision below.

Considered differential testing against `node` as a stronger oracle; rejected for this pass (see [TDD-00014](../tdd/TDD-00014.md)'s Design section for the full reasoning — in short, this compiler's `number → i64` semantics are a deliberate, documented divergence from real JS in ways a differential generator would need to know about in advance to avoid false positives).

## Decision

Implemented both lanes TDD-00014 scoped, in a new `tests/fuzz_codegen_test.go` (package `tests`, so it can reuse `buildBinary`/`compileAndRun` directly):

- **Lane A — `FuzzArithmeticCorrectness`**: `genArithExpr` recursively builds a random, fully-parenthesized arithmetic expression (`+ - * / %`, unary `-`, integer literals clamped to `[-1000, 1000]`) from an `int64`-seeded RNG, simultaneously computing the expected value with Go's own `int64` arithmetic. Emits `console.log(<expr>);`, compiles and runs it, and asserts the printed stdout matches the Go-computed value exactly. Division/modulo generation substitutes a `1` divisor whenever the generated right-hand value would be `0`, so the lane never needs to model the thrown-`Error` path from [ADR-00069](ADR-00069.md) — it stays a plain "compare two printed numbers" check.
- **Lane B — `FuzzProgramWellFormed`**: `genProgram` builds a template-shaped (not freely recursive) program — a top-level function, 2-4 `let` numbers, a handful of randomly-combined arithmetic updates, an `if`/`else`, a bounded `for` loop, a bounded `while` loop, and an array consumed with `for...of` — all with statically-bounded, always-terminating loop trip counts. No correctness oracle: the only assertions are that `buildBinary` doesn't fail (a parse/codegen/`clang` failure here is unambiguously a compiler bug, since every generated program is syntactically valid by construction) and the resulting binary exits `0` (the generator never throws or calls `process.exit`, so any non-zero exit or crash is a bug).

`math.MinInt64 / -1` was deliberately **not** guarded in this pass — documented as a known gap in `STATUS.md`'s Known Limitations & Bugs rather than fixed, since reaching that exact value by chance through Lane A's clamped-small-literal generator is astronomically unlikely (an intermediate wraparound result would need to land on exactly `-9223372036854775808` before a later `/ -1`), making it a different, deliberately out-of-scope kind of test (see [TDD-00014](../tdd/TDD-00014.md)).

Added `make fuzz-codegen` (running both lanes) and `make fuzz-all` (lexer/parser + codegen) to the `Makefile`, kept separate from the existing `make fuzz` target rather than folded into it, since each codegen-lane iteration shells out to `clang` and runs ~1000x slower than lexer/parser fuzzing (single-digit execs/sec vs. hundreds of thousands/sec) — worth keeping the fast default fast.

## Implementation notes

Files touched: `tests/fuzz_codegen_test.go` (new), `Makefile` (`fuzz-codegen`/`fuzz-all` targets + `.PHONY` entries), `STATUS.md` (new Known Limitations entry + Design Documents bullet), `docs/adr/ADR-00068.md` (added `Relations: Extended by ADR-00070`).

Hit a real generator bug (in the fuzz harness's own code, not the compiler under test) while first running Lane A: `genArithExpr`'s unary-negation case originally emitted `fmt.Sprintf("(-%s)", s)` with no space, so negating a negative literal produced `(--500)` — the lexer reads `--` as the decrement operator (`INC`/`DEC` tokens are lexed greedily, same disambiguation logic `lexer/lexer_test.go`'s `TestIncrementDecrement` already covers), leaving a bogus `500)` behind and a parser error ("update expression requires an identifier"), not a compiler bug. Fixed by adding a space (`"(- %s)"`) — any generator text adjacent to a value that might itself start with `-` needs to stay space-separated for the same reason.

## Side effects discovered

The `math.MinInt64 / -1` UB gap noted above and in `STATUS.md` — found by inspection while writing the Design, not by an actual fuzz-found repro.

## Verification

- `go vet ./tests/...` — clean.
- `go test ./tests/ -run '^FuzzArithmeticCorrectness$|^FuzzProgramWellFormed$' -v` — both lanes' seed corpora pass as ordinary test cases (after fixing the generator's own `--` bug above).
- `go test ./tests/ -run=^$ -fuzz=FuzzArithmeticCorrectness -fuzztime=90s` — 607 executions (clang-per-iteration cost limits throughput vs. lexer/parser fuzzing), 0 failures.
- `go test ./tests/ -run=^$ -fuzz=FuzzProgramWellFormed -fuzztime=90s` — 505 executions, 0 failures.
- `go test ./...` — full suite still passes.
- `make fuzz-codegen FUZZTIME=3s` — confirmed the Makefile targets run correctly; `make clean` afterward confirmed no stray build artifacts were left in `examples/`.
