# ADR-01023: One event loop — coroutine awaits everywhere, loop-driven top-level await, child exit as an event

- **Relations**: `Implements TDD-00223`; `Extends ADR-00050` (non-blocking fetch), `TDD-00083`/`TDD-00084` (coroutine tasks, task-aware loop), `ADR-00754`/`ADR-00761` (child `'error'`/`(code, signal)`), `ADR-01022` (the Windows port wake a child's exit rides); `Supersedes ADR-00280` (the fetch `.then` microtask drive)
- **Date**: 2026-09-20

## Context

Two bugs surfaced while writing the Windows reactor's acceptance tests (ADR-01022, Side effects): a top-level `await fetch()` starved the loop, and a child's exit was polled. Measuring the first one properly — a 50 ms `setInterval` counting beside a 1 s upstream, where Node counts ~20 — showed it was not one function but the shape of the async core:

| Shape | Ticks before |
|---|---|
| `async function` declaration awaiting `fetch` | 20 — but by polling: 7 649 zero-timeout `select()` calls in that second |
| top-level `await fetch(u)` | 0 |
| `async () => { await fetch(u) }` | 0 |
| `async` method awaiting `fetch` | 0 |
| `fetch(u).then(r => r.text()).then(…)` with a timer alive | segfault |
| top-level `await` on a timer promise while a child writes stdout | the child's data arrives only after the await |
| `fetch()` of the program's own server from a callback | deadlock |

Beside the real loop (`__kml_event_loop_run`) stood five private drives (`__kml_task_await_ready`'s `toploop`, `__kml_await_fetch`/`_headers`' `busyspin`, the inline no-task drive in `emitAwaitTaskPromise`, the `__kml_fetch_drive_run` microtask, `__kml_task_run_all`), each servicing a subset of sources and blocking the rest. Only top-level `async function` *declarations* the classifier recognised were coroutines.

## Investigation

- The coroutine machinery itself was correct; it was applied too narrowly, and the loop undermined it: `hasactivetasks → forcezero` made the loop poll with a zero `select()` timeout for as long as *any* task was parked. That is the only reason the declaration case scored 20 (a polling loop has perfect timer accuracy), and it burned a core for every await. `__kml_task_resumable()` was already folded into the "never block while work is ready" decision, so the force was redundant as well as costly.
- The segfault: `.then(r => r.text())` returns a promise, and `.then` did not flatten — the next callback received the inner promise's *pointer* as its "string" and `"body=" + b` ran `__kml_str_alloc` over garbage. `Promise.resolve(1).then(a => later(100, a + 41)).then(v => log(v))` printed `10000000`.
- Reactions were pushed at the head of the promise's list and drained head-first: `p.then(A); p.then(B)` ran B before A.
- `later(20).then(f)` with no `await` anywhere never ran `f`: such a program ended in `__kml_timer_drain`, which fires timers but never drains the microtasks their callbacks queue.
- `__kml_await_group_wait` (`Promise.all/race/any/allSettled` over fetches) and `__kml_await_fetch_settled` had no coroutine-park path: a task waiting on a fetch *group* fell into the main-stack spin. Found the hard way — the first cut of the loop-turn ran the event loop on that task's stack and hung one run in ten.
- `__kml_cp_finalize` called `waitpid(WNOHANG)` only after both stdio pipes hit EOF, and `__kml_cp_fdset_add` forced a zero `select()` timeout until it succeeded: 32 198 loop turns in 2 s for a child that closed its stdio and slept, and `'exit'` could never precede stdio EOF.
- Writing the tests hit a language bug: an un-annotated top-level binding initialised by a builtin call (`const t0 = Date.now()`, `const iv = setInterval(f, 50)`), or by a *scalar*-returning user function, was never promoted to a module global, so no named function could reference it (`undefined variable`). And `setTimeout(async () => …)` was a compile error.

## Decision

**A wait either parks a coroutine or, on the main stack at module top level, takes turns of the real event loop. No other form of waiting exists.**

- **Loop turns (`runtime_loop_turn.go`).** `__kml_loop_turn(pin)` runs `__kml_event_loop_run` for exactly one iteration (a one-shot flag checked at the top of each iteration) and reports *turn taken*, *loop idle*, or *cannot run here*. `__kml_top_await(word)` repeats it until a promise's state word is set; if the loop goes idle first the await can never settle and the process ends as Node ends it — a warning on stderr, **exit code 13**. `pin` holds the loop alive for a wait on an in-flight fetch. This replaced a first design of two until-word targets, which could not express a wait on a fetch group. A turn is refused unless the caller is on the main stack outside any loop callback, coroutine or connection fiber; only there is running the loop identical to suspending the module. The refused case keeps the old subset drive, so the waits that still reach it are no worse than before.
- **Every async callable that awaits is a coroutine (`emit_async_coroutine.go`).** Arrows, function expressions, methods and unclassified declarations are wrapped *at the callee*: the body is emitted unchanged as `<name>.inner`, and `<name>` — same LLVM signature, so closures, method dispatch and builtin callbacks are untouched — copies its LLVM parameters into a heap bundle, spawns a coroutine on a trampoline that calls `inner`, adopts `inner`'s settled promise into the task promise (a rejection through `__kml_task_reject`), and returns the pending promise at the body's first park. "Awaited" is recorded by the emitter itself while the body is emitted (`sawAwait`), not re-derived by an AST walker that can miss node kinds. `hasMaySuspend` is decided up front by a reflective whole-program scan (`programMayWait`: any `await`, `for await`, or `fetch`), because runtime functions emitted early include their park path only when it is set.
- **A parked task no longer makes the loop poll.** The `forcezero` force is deleted; a task-only or fetch program also ends in the full loop rather than `__kml_task_run_all`, so it sleeps in `select()` on libcurl's sockets.
- **Fetch reactions.** The `.then/.catch/.finally` bridge on a fetch promise (`__kml_fetch_slot_to_promise`) runs `__kml_fetch_drive_run` as a spawned coroutine that parks on the transfer. Tasks park on fetch groups (`taskPendingGroup`, checked by the scheduler and `__kml_task_resumable` through `__kml_group_satisfied`) and on the settled single-fetch wait. `res.json() as T` takes the same lazy body-promise path as `text()`/`json()`/`arrayBuffer()` (a per-call-site typed runner) instead of driving the transfer synchronously.
- **One promise per fetch.** `p.then(f)` followed by `await p` must run `f` first — they are two reactions on one promise. They had been two independent waits on the transfer (the awaiting task and the bridge coroutine), resumed in task-array order, which put the `await` first. The bridge promise is now cached on the fetch's pending struct (a tenth field) and `await p` awaits it too, so registration order holds and both see the same `Response` object. Generator fibers and `http.listen` handlers keep the direct wait; neither is a task.
- **An in-flight transfer holds the loop open** (`__kml_curl_inflight()`): it is an open socket, which is what keeps Node's loop alive. Without it a top-level `for await (const chunk of res.body)` found the loop "idle" between chunks and exited 13. The count is asked of libcurl at the keep-alive decision, never cached: the first cut cached the last `curl_multi_perform` result, and a transfer the blocking `XMLHttpRequest.send()` had driven to completion outside the loop left a stale "1" that blocked the final `select()` forever.
- **The fetch bridge rejects with the thrown value itself** (payload + tag), not an error pointer: once `await fetch()` went through the bridge, a fetch aborted with a non-Error reason (`abort(42)`) crashed re-throwing a pointer that was not one.
- **What does not take loop turns.** The synchronous `XMLHttpRequest.send()` wait (`__kml_await_fetch_settled`) is a blocking call by contract and is issued concurrently from goroutine threads — it keeps driving libcurl alone. And a goroutine never takes a turn (`klainsync_on_goroutine`): it has no reactor. Both were found by `TestE2EGoroutineHTTPListenLoadTest`, where eight goroutines each ran the event loop on their own M.
- **Promise resolution with a promise (`runtime_promise_adopt.go`).** A `.then`/`.catch` callback that returns a promise resolves the chain *with* it, with the spec's timing: a NewPromiseResolveThenableJob microtask attaches the settle reaction, which is itself a microtask once the inner promise is settled. A raw fetch handle returned from a callback is bridged first. Type inference of a `.then` call unwraps the same way, so a binding's inferred type agrees with what is built. Reactions drain in registration order. A program with timers *and* microtasks ends in the full loop.
- **Child exit is an event (`runtime_childprocess_exit.go`).** `__kml_cp_finalize` is split: `__kml_cp_reap` runs every iteration and fires `'exit'` the moment `waitpid(WNOHANG)` succeeds (state 1); `__kml_cp_close` fires `'close'` (or the buffered `exec` callback) once the child is reaped **and** its stdio is at EOF (state 2). The zero-timeout force is deleted. The loop is *woken* by the exit: POSIX installs a `SIGCHLD` handler that writes to a non-blocking self-pipe in the read set (a self-pipe rather than `EINTR`, which a signal landing just before `select()` does not produce; owner-pid-gated so a forked cluster worker never swallows the parent's wake bytes); Windows registers a wait on the process handle whose callback posts a packet to the reactor's port. On Windows a bare wake packet now ends `select()` with 0 so the IR loop takes its turn. A registration also forces one non-blocking pass, so a child that died before the watch existed is still reaped at once.
- **In passing.** Un-annotated top-level bindings initialised by a builtin call with a scalar/string result, or by a scalar-returning named function, are module globals (`prePassStableBuiltinCall`; a call *through another top-level binding* is excluded — its type is not known before `main()`). The declaration adopts the pre-registered global's type, so the two cannot disagree; an incompatible initializer is a clean compile error. Timers accept a value-returning callback through a typed discard adapter rather than a signature-mismatched call.

## Implementation notes

- New: `runtime_loop_turn.go`, `emit_async_coroutine.go`, `runtime_promise_adopt.go`, `runtime_childprocess_exit.go`. Touched: `runtime_http.go` (one-shot/pin/depth/idle in the loop; the `forcezero` force removed), `runtime_task.go` (top-level branch → `__kml_top_await`; group park in the scheduler and `task_resumable`; `__kml_group_satisfied` stub), `runtime_fetch.go` (the four main-stack waits take loop turns; `taskParkIR`), `emit_async.go`, `emit_task_classify.go`, `emit_promise_then.go`, `runtime_microtask.go`, `emit_fetch.go`, `emit_call.go`, `emit_func.go`, `emit_classes.go`, `emit_exprs_vardecl.go`, `emit_exprs_types.go`, `emit_timers.go`, `runtime_childprocess.go`, `runtime_ipc.go`, `emitter.go`; Windows: `win32src/win32proc.c` (`__kml_win_child_watch`), `win32src/win32io.c` (`kml_woken`, reactor-port accessors).
- The `%kml.cp` struct grew two fields (25 raw wait status, 26 plain exit code) for `__kml_cp_close`, which may run many iterations after the reap: 216 bytes, allocated in `runtime_childprocess.go` and `runtime_ipc.go`.
- The coroutine bundle stores LLVM values verbatim and nothing in it points into the caller's frame: array arguments travel as their heap header pointer, closure environments and `this` are heap objects, and by-value tuple parameters are already excluded for async signatures.
- An `http.listen` handler is not wrapped: its connection fiber is already its coroutine.
- `await als.run(store, async () => { … })` returned at once: a function type's return type does not carry the task-promise flag, and an await of an unflagged `Promise<void>` reads nothing and continues. Harmless while an async arrow always came back settled; wrong now that it can be pending. `asyncCallbackResult` flags the result at the emit site and in inference.
- The builtin-call promotion is an explicit list (`prePassScalarGlobalFns`/`Namespaces`/`StringMethods`), not "whatever `inferExprType` says": for a call it does not model, inference falls back to a default scalar, and the first cut promoted `const c = structuredClone(set)` as a number.
- `buildBinaryFinRegAuto` (a custom test link step) never linked the float-formatter C file that `buildBinary` and the CLI link; a timers + microtasks program now ends in the full loop, which needs it.
- `TestE2EPromiseAllFetchesRunConcurrently` asserted the old behaviour — it printed the elapsed time *after* an un-awaited `main2()` and expected it to follow the fetches. Node prints that line first. The measurement moved inside the async function, after the `await`, which is what the test was written to time.
- TDD-00223 §1 describes the first design (until-word targets); the loop-turn primitive above is what was built, for the reason given.

## Side effects discovered

- **A stale task-array pointer in the scheduler** (fixed). `__kml_task_sched_step` loaded `@__kml_task_data`/`_len` once and then resumed tasks; a resumed task that spawns a task makes `__kml_task_register` `realloc` the array, and the scan walked freed memory. Latent until now because a resumed task rarely spawned; an `await fetch` inside a task now spawns its bridge coroutine, so `Promise.any([bad(u), good(u), bad(u)])` hit it every time — on Linux a deterministic segfault (the freed block had been reused for a libcurl certificate path; `rcx` held the ASCII of `/certs/c`), on Windows it passed by allocator luck. Both are reloaded per iteration now. `__kml_cp_dispatch` had the same shape against the child registry (a listener may spawn a child) and got the same fix.

- One main-stack wait still spins from inside a loop callback by design of the refusal rule: a connection fiber consuming its own request body via `req.stream()` that awaits (ADR-00986's hazard gate). It is unchanged by this work.
- The Windows timer tick rounds a 50 ms interval to ~62 ms (16 ticks/s, not 20) — TDD-00183 Stage 4, not an event-loop defect; the polling loop had been masking it.

## Verification

- `examples/async/one_event_loop.ts` (new) — top-level await with a child's output arriving during it, async arrow, async method, a flattened `.then` chain with two ordered reactions, an async timer callback, all under a running heartbeat: output is **byte-identical to Node 24** (`node --experimental-strip-types`) on the Windows dev box.
- `tests/event_loop_wait_test.go` (new, portable): each shape against a 600 ms upstream with a 25 ms interval — body arrives, the interval keeps ticking, and the process's own CPU time stays under 350 ms (a spin fails it); fetch-own-server-from-callback; top-level await servicing a child; unsettled TLA → exit 13 + warning; async-arrow ordering; `.then` flattening; reaction order; builtin-call top-level bindings visible in functions.
- `tests/childprocess_exit_test.go` (new, portable): `'exit 7'` immediately and `'close 7'` ~2 s later for `sh -c 'sleep 2 & exit 7'` (a grandchild holds the pipes); a child that closes its stdio and sleeps costs the parent < 500 ms of CPU. Before: 32 198 loop turns in 2 s; after: 3.
- Measured on the Windows dev box: the `async function` declaration case went from 7 649 `select()` calls per second to 16, same output.
- Suites: see the delivery's full `go test ./...` runs on Windows (native) and Linux (WSL2 Ubuntu x86-64). macOS not run from here (`SIGCHLD` = 20 comes from the host signal table) — CI's macOS lanes are the guard.
