# ADR-00064: Fix `emitObjectVarDecl`'s narrow initializer whitelist and self-referential class field type staleness

- **Relations**: Extends [ADR-00063](ADR-00063.md)
- **Date**: 2026-07-28

## Context

Found both bugs while building [ADR-00063](ADR-00063.md)'s ([TDD-00009](../tdd/TDD-00009.md) Stage 1a) linked-list iterator test case — a `Node` class with a `nextNode: Node | null` field. Neither is class-specific; both are pre-existing gaps in the general object system that classes' heavier reliance on chained/self-referential field access simply exposed for the first time.

## Investigation

**Bug 1 — `emitObjectVarDecl`'s initializer whitelist.** `const n = this.cursor;` (inside a method body, `cursor: Node | null`) failed with `"object variable must be initialized with an object literal or function call"`. Traced to `emitObjectVarDecl`'s (`codegen/llvm/emit_objects.go`) switch on `v.Init`'s AST type: it only had cases for `*ast.ObjectLiteral`, `*ast.NewErrorExpression`, `*ast.CallExpression` (with special-cased `JSON.parse`/`response.json()` type-directed parsing, falling back to a generic `e.emitExpr(init)` for anything else), and `*ast.AwaitExpression` — everything else, including a **bare identifier** and a **member-expression field read**, hit the `default: error` branch. Confirmed this predates classes entirely and isn't a classes-specific gap: `const b = a` (aliasing one interface-typed variable to another) and `const x = arr[0]` (indexing into an array of objects) both fail identically with plain `interface`s, no `class` involved. Every one of these expression shapes already evaluates correctly via `e.emitExpr` in every *other* context (e.g. `emitMember`'s own generic `e.emitExpr(ex.Object)` tail relies on exactly this for the object being read) — there was no missing capability, only a switch that hadn't been extended to trust it.

**Bug 2 — self-referential class field type staleness.** After fixing Bug 1, `console.log(b.nextNode.value)` (two levels deep through a directly self-referential field) failed at the `clang` stage with a type mismatch (`i64` expected, `ptr` produced) — traced further back to `registerClasses` (`codegen/llvm/emit_classes.go`, [ADR-00063](ADR-00063.md)) resolving `Node`'s own `nextNode: Node | null` field *before* `Node`'s `Type` was stored into `e.interfaces["Node"]`, so `e.resolveType("Node")` couldn't find itself and silently fell back to `ResolveTypeName`'s unknown-name default, `TypeI64` — a silent miscompile, not just a missed feature. Fixed with a placeholder pre-pass (register every class under `ClassType(name, nil)` before resolving any field), which fixed the immediate crash, but exposed a second, subtler layer: `Field.Ty` is stored *by value*, so a genuinely self-referential field's `Ty` is permanently a snapshot of whatever `Node` looked like at the moment it was captured — for direct self-reference, that's always the still-fields-less placeholder, because Go copies the value in rather than aliasing a live registry entry. Later overwriting `e.interfaces["Node"]` with the fully-resolved type does not retroactively update the already-copied `nextNode` field's own embedded `Ty`. This is only observable by drilling a *second* field access through the self-referential field (`b.nextNode.value` fails; `b.nextNode` alone, used only as an opaque pointer, is fine) — confirmed by testing both depths directly, and confirmed a sibling/forward class reference (`NodeIter` referencing `Node`, declared after it) does *not* have this problem, since `Node` finishes its own registration completely before `NodeIter`'s fields are ever resolved.

Considered fixing this by making `Field.Ty` a pointer or otherwise restructuring `Type`'s storage to support true recursive value construction — rejected as disproportionate: it would touch every `Field{...}` construction site across the codebase (interfaces, `Map`/`Object` synthetic entry structs, etc.) for a problem that, on inspection, only actually manifests at three specific call sites that hand a field's type back out as *the type of an expression a caller might chain further off of*.

## Decision

**Bug 1**: collapsed `emitObjectVarDecl`'s explicit `*ast.NewExpression`/`*ast.AwaitExpression` cases and the `default: error` branch into one generic `default` fallback — `val, err := e.emitExpr(init); store ptr val.Ref into ptrName` — the same generic tail the `*ast.CallExpression` case's non-JSON.parse branch already used. `ObjectLiteral`/`NewErrorExpression`/`CallExpression`'s JSON.parse/response.json special-casing are the only cases that still need to exist, since only those need extra target-type context `emitExpr` alone can't supply.

**Bug 2**: two-part fix, both in `codegen/llvm/emit_classes.go`:
- `registerClasses` now runs a **Pass A** that seeds `e.interfaces[name] = ClassType(name, nil)` for every class before **Pass B** resolves any field/param/return type — so any self- or forward-reference to a class name resolves to at least the correct `IR`/`IsObject`/`IsClass`/`ClassName` immediately (not a silent `i64`), even though its `Fields` may still be a placeholder at that exact moment.
- New helper `canonicalizeClassTy(ty Type) Type`: if `ty.IsClass`, returns the live `e.classes[ty.ClassName].Ty` (fully resolved by the time any code actually runs, since all registration completes before any emission does) instead of the possibly-stale snapshot. Applied at the three places that hand a field's type back out as a chainable expression type: `emitMember`'s generic field-read tail, `emitOptionalMember`'s field-read branch, and `inferExprType`'s `MemberExpression` field-read fallback (`emit_exprs.go`) — plus `emitObjectDestructuring`'s per-property binding (`emit_objects.go`), found and fixed the same way for consistency (`const { nextNode } = b` had the identical staleness risk). Deliberately *not* applied to sites that only use a field's type for its `IR`/`Align()`/coercion shape without handing it back to a caller (e.g. `emitAssign`'s field-assignment branch) — those are already correct regardless of staleness, since a class's `IR` is always `"ptr"` whether or not `Fields` is fully populated yet.

## Implementation notes

Files touched: `codegen/llvm/emit_objects.go` (`emitObjectVarDecl`'s generic fallback; `emitObjectDestructuring`'s canonicalization), `codegen/llvm/emit_classes.go` (`registerClasses`'s two-pass restructure; `canonicalizeClassTy`), `codegen/llvm/emit_exprs.go` (`emitMember`, `emitOptionalMember`, `inferExprType`).

## Side effects discovered

None beyond what's already described above. `canonicalizeClassTy` is a no-op (returns `ty` unchanged) for every non-class type, so plain interfaces/objects are provably unaffected — confirmed by the full existing test suite passing unchanged.

## Verification

- `go test ./...` — all green, including three new regression cases in `tests/classes_test.go`: `const n = this.cursor` (Bug 1, exercised by the Stage 1a object-element iterator test), `a.nextNode.nextNode.value` (Bug 2, two-level self-reference), and `const { nextNode } = b; nextNode.value` (Bug 2, via destructuring).
- Manual repros for both bugs (plain-interface aliasing/indexing for Bug 1; a three-level self-referential chain for Bug 2) confirmed fixed, run before and after each fix to isolate cause and effect.
- `make examples` — 59/59 passed.
