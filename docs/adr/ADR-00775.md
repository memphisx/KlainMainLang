# ADR-00775: Pool-backed `fs.createReadStream` (non-blocking chunked read)

- **Relations**: `Implements [TDD-00186](../tdd/TDD-00186.md)` (Part A); `Extends [ADR-00774](ADR-00774.md)` (the thread pool this adds a streaming completion kind to), [ADR-00343](ADR-00343.md) (the eager `createReadStream` this replaces)
- **Date**: 2026-09-08

## Context

`fs.createReadStream` allocated a WHATWG readable, then `@__kml_fs_read_stream`
`fopen`/`fread`'d the **entire** file to EOF **inline on the loop thread**
(enqueuing each highWaterMark chunk), then closed it. For a file-serving
microservice — the target use case — that froze the reactor for the whole read,
the exact blocking [TDD-00185](../tdd/TDD-00185.md) removed from the one-shot fs
ops but left on the streaming path.

## Investigation

The one-shot pool ([ADR-00773](ADR-00773.md)/[ADR-00774](ADR-00774.md)) posts
exactly **one** completion per work item that *settles a Promise*. A stream is a
different shape: **many** completions, each *feeding a Readable*, plus a terminal
close. Two facts made this tractable: the WHATWG readable already supports async
production (fetch response bodies stream into the same `@__kml_rs_enqueue` over
loop iterations — TDD-00097), so a reader parks on an open-but-empty readable
and resumes on enqueue; and a length-prefixed KML string is trivial to build in
plain C, and the readable leaks its chunks anyway, so the worker needs no GC
allocation.

The one ordering trap: the completion stack is a LIFO Treiber stack. Independent
Promise completions don't care, but a stream's chunks **must** enqueue in read
order — so the drain now reverses each batch to insertion order first.

## Decision

Extend the pool with a streaming **completion kind** (`klainpool.c`):

- **Kinds**: `SETTLE` (Promise, unchanged), `STREAM_CHUNK` (enqueue), `STREAM_END`
  (close). The loop-thread drain dispatches on the kind — `__kml_pool_settle` /
  `__kml_pool_stream_chunk` (→ `@__kml_rs_enqueue`) / `__kml_pool_stream_end`
  (→ `@__kml_rs_close`), all IR helpers, so the C side stays ignorant of the
  stream/Promise layout exactly as before.
- **Synchronous open, pooled read**: `createReadStream` `fopen`s on the loop
  thread (`@__kml_fs_open_read`, throwing on a missing file — preserving the
  eager path's synchronous throw), then `__kml_pool_submit_readstream(rs, FILE*,
  hwm)`. The worker (`run_read_stream`) loops: `fread` one `hwm` chunk, `malloc`
  a length-prefixed KML string, post a `STREAM_CHUNK`; at EOF post `STREAM_END`;
  `fclose`. One work item, many completions — so the worker allocates fresh
  completion structs (`post_completion`) rather than reusing the work item.
- **Ordering**: the drain reverses the LIFO batch to insertion order, preserving
  each stream's chunk order.
- **Inflight/keepalive**: submit increments the loop's inflight once; only
  `STREAM_END` (and `SETTLE`) decrements — chunk completions don't — so the loop
  stays alive across the whole read and blocks on the wakefd between chunks.
- **Backpressure deferred**: the worker reads ahead and chunks queue in the
  readable — the same memory profile the eager path had, now non-blocking. True
  highWaterMark backpressure is a documented follow-on (TDD-00186 OQ1).

## Consequences

`createReadStream` no longer blocks the reactor. Verified on macOS (arm64): a
10 KB file read at `highWaterMark: 64` yields 79 chunks that reassemble
**byte-identically and in order** while a `setInterval` keeps firing during the
read; `for await` / `.on('data')` / `.pipe()` into a write stream all round-trip;
a missing file still throws `ENOENT` synchronously — under both the default and
`-mm=gc` allocators. Test `TestE2EFsCreateReadStreamPooledOrderedNonBlocking`;
the existing stream suite and `examples/fs_streams/` pass unchanged on the new
path. The `Response.text()/.json()` real-Promise return type (TDD-00186 Part B,
already non-blocking) remains staged.
