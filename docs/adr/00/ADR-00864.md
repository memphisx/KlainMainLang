# ADR-00864: Windows reactor Stage 1 — owned kind-tagged fd table + fstat kind dispatch

- **Relations**: Implements TDD-00182 (Stage 1); Extends ADR-00757
- **Date**: 2026-09-11

## Context

TDD-00182 committed to Option A for the Windows event-loop reactor: replace the
CRT-fd-based I/O path with an owned, kind-tagged handle table and (later) a
single unified wait. Stage 1 is the foundation every later stage builds on —
the owned table itself — and is defined as behaviour-preserving except for one
visible win: `fstat(fd)` dispatching on the handle kind.

Done on the Windows box deliberately: the corrected Windows dev direction (this
session, recorded on `docs/BACKLOG.md` §2) is to finish work that genuinely
needs a native Windows box while here, to minimize return trips — the reactor is
exactly such work, and its regression guard (the socket/pipe/fs suites) runs
natively here. (TDD-00182's own "not to be started from the Windows box" note
predates that correction; the ADR supersedes it in practice, per the rule that
design bodies aren't edited post-hoc.)

## Investigation

The pre-Stage-1 layer (`win32io.c`) kept five parallel arrays keyed by fd:
`kfd_kind`, `kfd_nonblock`, `kfd_sock_handle`, `kfd_reset`, `kfd_inherited`
(`win32io.c:167-178`). Sockets live in `[512, 896)`, foreign (libcurl) sockets
in `[896, 1024)`, CRT fds below 512. Cross-file consumers were minimal:
`win32proc.c` read `kfd_kind[fd]` and wrote `kfd_inherited[fd]` (plus
`kfd_handle`/`kfd_register`/`kfd_adopt_socket`); `tls.c` used
`__kml_win_fd_socket`; `win32fs.c`'s `fstat` used `_get_osfhandle` directly.

`fstat(fd)` was wrong on two fd classes (TDD-00180 §1): a socket fd's OS handle
is not a CRT fd, so `_get_osfhandle` returned `INVALID_HANDLE_VALUE` → `EBADF`;
and a pipe/console handle answers `GetFileInformationByHandle` (called first in
`stat_handle`) with a failure, which surfaced as an error rather than a FIFO/
char-device stat.

## Decision

**Owned table (array-of-structs).** Replace the five parallel arrays with one
`kfd_slot kfd[KFD_MAX]` carrying `sock`, `kind`, `nonblock`, `reset`,
`inherited`. Array-of-structs (not struct-of-arrays) so later stages extend the
slot *in place* — Stage 3 adds per-handle overlapped read/write state, Stage 5 a
refcounted shared description for `dup2` aliasing — instead of adding more
parallel arrays, which is the pattern TDD-00182 set out to end.

The three fd ranges and all dispatch are **unchanged** in Stage 1 (the
socket-range partition dissolves only in Stage 5); this is a pure
representation change. Cross-file access moves off the raw arrays onto two
accessor functions — `kfd_kind_of(fd)` and `kfd_set_inherited(fd)` — so
`win32proc.c` and `win32fs.c` never bind to the slot layout and won't rebuild
against it as the struct grows.

**fstat kind dispatch (the visible win).** `kml_win_fstat` now dispatches on
the table's kind first: a socket/foreign fd synthesizes `S_IFSOCK` (libuv's
`uv_fs_fstat` shape — mode from kind, other fields zeroed); otherwise it
resolves the handle via `kfd_handle(fd)` and, when `GetFileType` reports
`FILE_TYPE_CHAR`/`FILE_TYPE_PIPE`, synthesizes `S_IFCHR`/`S_IFIFO` without the
`GetFileInformationByHandle` call that fails on those; regular files fall
through to the existing `stat_handle`. `S_IFSOCK = 0140000` was added to
`win32fs.c`'s local Linux-value mode enum.

## Implementation notes

- `win32io.c`: the table struct + accessors hand-written; the ~52 body field
  accesses converted mechanically (`kfd_kind[x]` → `kfd[x].kind`, etc.) and the
  diff reviewed.
- `win32proc.c`: dropped the three `extern unsigned char kfd_*[]` declarations
  (`kfd_nonblock` was unused) for the two accessor prototypes; the one call site
  (`spawn` marking an inherited socket) uses them.
- `win32fs.c`: `kfd_kind_of`/`kfd_handle`/`KFD_*` declared locally; `fstat`
  rewritten as above; `fstat_synth` helper.
- The shim is content-hash keyed and `//go:embed`-baked into `klainmain.exe`, so
  a Go rebuild re-embeds and recompiles the changed shim — no cache flush needed.

## Side effects discovered

- `TestE2ENetSocketCloseAndReadyEvents` is **pre-existing flaky** on the Windows
  box (~1 in 4 in a tight loop): it occasionally loses the `'data'` chunk before
  `'end'`/`'close'`. Verified flaky on the *baseline* (git-stash + rebuild) too,
  so it is **not** a Stage-1 regression — it is the data/end/close ordering race
  on today's poll-slice reactor, which Stage 2/3 (unified wait + overlapped
  reads) is expected to remove. Left unmasked and deferred to those stages
  rather than papered over by loosening the assertion.

## Verification

Windows dev box, MSYS2 UCRT64 clang 22.1.7 (`/c/msys64/ucrt64/bin`):

- All three win32 C files compile clean (`clang -c -Wall`); `go build`/`go vet
  ./...` clean.
- New `TestE2EFsFstatPipeFd` (cross-platform, `fstatSync(0)` over a piped
  stdin → `isFIFO()===true`) passes.
- Regression: `TestE2EFs*`/`TestE2ENet*`/`TestE2EDgram*`/`TestE2EHttp*`/
  `TestE2ETls*`/`TestE2EWebSocket*`/`TestE2EChildProcess*`/`TestE2EReadline*`/
  `TestE2ECluster*` pass, the sole failure being the pre-existing flake above.
- Not re-verified on macOS/Linux from here; the change is Windows-only C plus a
  cross-platform test whose POSIX behaviour is unchanged (POSIX `fstat` on a
  pipe already worked). CI's four POSIX lanes are the guard.
