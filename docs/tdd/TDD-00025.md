# TDD-00025: Multi-process clustering for `http.listen()`

- **Status**: Implemented
- **Date**: 2026-08-03
- **Notes**: Both `manual` and `-mm=gc` modes production-quality; [ADR-00101](../adr/ADR-00101.md) root-caused and fixed the `-mm=gc` intermittent hang

## Context

This compiler's concurrency model today is entirely single-process, single-thread: `http.listen()` handles many connections *concurrently* via cooperative `ucontext_t` fibers (one per connection, TDD-00006 Part 2/ADR-00049), but never *in parallel* — only one fiber's code ever executes at any given instant, on one CPU core. For a microservice (this project's own stated priority use case alongside CLI tools), that means a single `http.listen()` process can never use more than one core, regardless of machine size.

Discussed with the user as one of three ways to add real parallelism (see the conversation this TDD originates from): (a) true shared-memory threading — rejected, would require making every existing runtime structure (`Map`, arrays, `EventEmitter`'s listener lists, the fiber scheduler, GC) thread-safe, and isn't even how real Node solves this; (b) a `Worker`-isolate model (real threads, message-passing only, matching Node's own `Worker` — already correctly tracked as High effort in `CONCURRENCY-WORKERS.md`); (c) OS-process-level clustering (matching Node's `cluster` module) — fork() multiple copies of the whole process, sharing only the listening socket, so the kernel distributes connections across workers. (c) is what this TDD scopes: it needs no cross-process shared memory at all (OS process isolation provides that for free), so it sidesteps almost every hard problem (b) has, and is a much smaller, more tractable project. (b) remains the eventual "real" answer for CPU-bound worker parallelism and isn't affected by whether (c) is built — see the Design section's Compatibility with (b) note.

## Design

### API surface: an option on `http.listen`, not a new user-facing primitive

```ts
http.listen(port, handler, { workers: N });
```

Deliberately **not** a general-purpose `cluster.fork()`/`child_process`-style primitive users call themselves (that's a different, already-separately-tracked feature area) — narrowly scoped to the one concrete, well-understood use case this project actually has: scaling `http.listen()` across cores. `N` is user-supplied; `os.cpus().length` (shipped in ADR-00090) is the natural value to pass, closing a real loop between two recently-built features. Two small read-only globals for introspection, matching the `process.pid`-style "read live OS state" convention: `cluster.isPrimary: boolean`, `cluster.workerId: number` (`0` for the original process, `1..N-1` for forked workers) — enough for a program to log a startup banner once, or otherwise branch on primary-vs-worker, without any of Node's richer `cluster.on('exit', ...)`/IPC/`worker.send()` surface.

### Mechanism: fork() right after `listen()`, before the event loop starts, all peers symmetric

`__kml_http_cluster_fork(i64 numWorkers)` runs immediately after `__kml_http_bind_and_listen` succeeds and *before* `__kml_event_loop_run` begins — i.e., before any connection-fiber state (`@__kml_conn_data/len/cap`) exists. This ordering is load-bearing, not incidental: forking after any connection has ever been accepted would fork a live fiber's `ucontext_t`/stack into every child, which is unreasoned-about, untested territory (the existing fiber scheduler was never designed with fork() in mind).

The fan-out loop is a flat "spawn N-1 additional peers" loop, **not** each child re-entering the loop (which would fork exponentially — `N-1, then (N-1)² , ...`):
```
for i in 1..numWorkers-1:
    pid = fork()
    if pid == 0:        // child
        workerId = i
        break            // stop forking further — just this one child breaks out
    // parent (pid > 0): loop continues to spawn worker i+1
```
After the loop, **every** process — the original (now `workerId = 0`) and every fork — falls through into the identical `__kml_event_loop_run` call. There is no asymmetric "primary does nothing but supervise" role (unlike Node's actual `cluster`, where the primary never serves requests itself) — a deliberate simplification: it avoids needing any supervisor-only code path (respawn-on-crash, primary-orchestrated graceful shutdown) that this V1 isn't building anyway, at the cost of the primary also doing request-serving work rather than being free to do supervisor bookkeeping later. Worth revisiting if a future respawn-on-worker-crash feature wants a dedicated non-serving primary.

### The listening fd must become non-blocking (a required change, not an optimization)

Confirmed directly against `runtime_http.go`: `__kml_http_bind_and_listen` never calls `fcntl(..., O_NONBLOCK)` on the listening fd itself (only *accepted connection* fds get that treatment, post-`accept()`). Today that's fine — a single process's `select()` already guarantees the listener is ready before its own `accept()` call. Under clustering it's not: multiple worker processes all block in `select()` on the *same inherited* listening fd (standard, decades-old pre-fork-server pattern — the kernel hands each ready connection to exactly one caller's `accept()`), so more than one worker can wake from `select()` believing the listener is ready, but only one will actually get the connection; the others' `accept()` calls would find nothing pending. With a **blocking** listening fd, a "losing" worker's `accept()` call would simply hang — stalling that worker's entire event loop, not just skipping this connection. Fix: make the listening fd non-blocking (the same `fcntl(F_GETFL)`/`fcntl(F_SETFL, ... | O_NONBLOCK)` pair already used for connection fds, applied to the listener too) and treat an `EAGAIN`/`EWOULDBLOCK` `accept()` result as "no connection this round, resume the loop" rather than an error.

`SO_REUSEPORT` is deliberately **not** used — the simpler "fork after `bind()`+`listen()`, inherit the one shared fd" model needs it for nothing (the fd itself is inherited via `fork()`'s normal copy-the-file-descriptor-table semantics), avoiding new platform-specific socket-option constants (Linux `15` vs. Darwin `0x0200`) entirely. Noted as a possible future optimization (a `SO_REUSEPORT`-per-worker model can give the kernel a better load-balancing algorithm on Linux than plain shared-fd `accept()` contention), not required for V1.

### Boehm GC (`-mm=gc`) + `fork()`: register the documented hooks, don't guess

A real, previously-unaddressed risk, confirmed by reading `gcshim.go`/`ADR-00071`/`ADR-00080` directly: nothing in this codebase's Boehm integration registers `pthread_atfork` hooks, and `GC_INIT()` already runs "before main()'s first instruction" (`emitter.go:502`'s own comment) — meaning Boehm is fully live, with whatever internal locks/background-thread state its build enables, well before `http.listen()`'s fork() would ever run. Boehm's own public API ships exactly the fix for this: `GC_atfork_prepare()`/`GC_atfork_parent()`/`GC_atfork_child()`, meant to be wired through `pthread_atfork(3)` around any `fork()` call in a process using Boehm. The design is to register these once, at `-mm=gc` startup (same place `GC_INIT()`/the `GC_stackbottom` snapshot already happen, `emitter.go`), conditionally compiled only into `-mm=gc` builds — cheap, and directly Boehm's own documented answer, not a novel workaround. This needs real verification during implementation (this codebase's own history — `ADR-00051`, `ADR-00052`, `ADR-00080` — is three separate times a plausible-sounding libc/GC assumption turned out wrong on a specific platform), not just trusting the public docs blind.

`manual` mode has no collector state at all — plain `malloc`/`free`, correctly duplicated by `fork()`'s standard copy-on-write semantics with zero special handling needed. Clustering is unconditionally safe in `manual` mode; the Boehm work above is the only mode-specific risk.

### Signals: no primary-forwards-to-workers protocol for V1

Each forked worker's `@__kml_sigint_pending`/`@__kml_sigterm_pending`/`@__kml_sigint_closure`/`@__kml_sigterm_closure` globals are ordinary process memory, independently copied by `fork()` — a worker's own `process.on('SIGINT', ...)` registration (if any) already works correctly post-fork with zero changes needed. Since `fork()` doesn't change process group by default, every worker plus the original process share one process group, so a terminal `Ctrl-C` (which signals the whole foreground process group on POSIX) reaches every worker independently — a reasonable V1 graceful-"stop the whole cluster" story for the common interactive case. **Explicitly not handled**: a signal sent to one specific PID (e.g. `kill <primary-pid>`, not the process group) only reaches that one process; siblings keep running. Real Node's `cluster` primary explicitly forwards shutdown to workers and waits for them to drain — no equivalent exists here. Documented as a known V1 gap, not silently assumed away.

### Compatibility with a future `Worker`-isolate model (b)

Orthogonal by construction: (c) operates purely at `fork()`/process level, before `http.listen()`'s event loop or any fiber ever starts, and never introduces a second OS thread anywhere. A future `Worker` implementation (real `pthread`s within one process) doesn't conflict with anything here, with one real ordering constraint to document when/if it's ever built: `fork()` after real OS threads exist is unsafe (POSIX only guarantees the forking thread survives cleanly into the child) — so a program combining both would need clustering's fork() to happen *before* any `Worker` is ever spawned in that process. Not a blocker for building (c) now; just a constraint to write down for (b)'s own future TDD.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `fork()` | ✅ already used (`execFileSync`, `runtime_process.go`) | Existing precedent doesn't cover this case though — `execFileSync`'s child immediately `execvp()`s or `_exit()`s, never falls back into ordinary KML-emitted code; a cluster worker must instead keep running the *entire* runtime (event loop, fibers, GC) independently post-fork. No evidence from that precedent that the fiber scheduler/GC are fork-safe when the child doesn't immediately replace its image. |
| `__kml_http_bind_and_listen`/`__kml_event_loop_run` | ✅ already done (ADR-00048/00049/00050) | Reused as-is; only the listening fd's blocking-vs-non-blocking mode needs to change |
| `os.cpus().length` as the natural worker-count input | ✅ already done (ADR-00090) | Not a hard dependency (`N` can be any user-supplied number), but the intended common usage |
| `pthread_atfork`/`GC_atfork_*` registration for `-mm=gc` | ❌ not built | New, and the one piece of this design with real unverified risk — see Design section |
| Non-blocking listening-fd `accept()` handling | ❌ not built | Required correctness change, not optional, once more than one process can call `accept()` on the same fd |
| Primary-forwards-signals-to-workers | ❌ not built, deliberately deferred | V1 relies on process-group signal delivery (`Ctrl-C`) instead; a specific-PID signal doesn't propagate |

## Open questions

- Whether `-mm=gc` clustering should ship gated behind explicit verification (i.e., initially only support `workers > 1` in `manual` mode, adding `-mm=gc` support once the `GC_atfork_*` registration is built *and* tested under real concurrent load) or whether both should land together — leaning toward gating manual-mode-first given this project's own history of Boehm-specific surprises, but not decided.
- Whether the primary-also-serves-requests symmetry (no dedicated non-serving supervisor process) will need revisiting once/if worker respawn-on-crash is ever wanted — noted as a real tradeoff in the Design section, not resolved here.
- Whether `SO_REUSEPORT` is worth adding later for better kernel-level load-balancing than plain shared-fd `accept()` contention — not needed for correctness, a possible future optimization only.
