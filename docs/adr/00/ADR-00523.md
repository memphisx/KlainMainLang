# ADR-00523: `optnone` the webview bind thunks — `-O2` miscompiles their setjmp guard

- **Relations**: Relates to TDD-00142 (klain:webview)
- **Date**: 2026-08-31

## Context

A `klain:webview` app that both binds native functions (`w.bind`) and has *any* bound closure call an `fs` operation had **every** binding fail at runtime: each `window.<fn>()` call rejected with the bridge's generic "native handler threw", even bindings that touched neither `fs` nor the failing one. Surfaced while building the read-only file-explorer example (`examples/webview/explorer.ts`): its `home()` bind (just `process.cwd()`) threw solely because sibling `listDir`/`readText`/`readImage` binds call `fs`.

## Investigation

Minimal reproductions (macOS, run under a real webview window):

- `serve` + one bind, no `fs` → works.
- `serve` + two trivial binds, no `fs` → works.
- `serve` + a bind whose closure calls `readdirSync` → **all** binds throw, including a trivial `ping` invoked *before* the fs bind ever runs.
- Calling `readdirSync` at top level (in `main`) with an fs-free bind → works.
- `JSON.parse` inside a bind → works (not implicated).

So the trigger is precisely *an fs op inside a bind thunk*, and it poisons unrelated binds. The generated IR for the innocent `ping` thunk is **byte-identical** in the working and broken builds, and a top-level symbol diff shows no shared-helper difference — pointing at a link/opt-time effect, not codegen.

Each bind thunk (`emitWebviewBindThunk`, `emit_webview.go`) wraps the user-closure call in `emitFsGuarded` — a `setjmp`/`longjmp` guard (`@__kml_push_jmpbuf` + `setjmp`; on `longjmp` it rejects status 1 with `"native handler threw"`). An fs op inside a thunk nests a *second* `setjmp` guard in the same function. Building the broken program with `clang -O0` instead of the usual `-O2` makes it work — confirming a **`clang -O2` miscompilation of the `setjmp`/`returns_twice` handling** once the module contains a bind thunk with a nested setjmp guard. The thunk's own setjmp then spuriously reports a longjmp, turning an ordinary call into a rejection. This joins the project's existing `-O2` `setjmp`/`returns_twice` foot-guns (see the `-O2` notes in `emit_exprs_member.go`, `emit_func.go`, `runtime_process.go`).

## Decision

Emit each per-bind trampoline (`@__kml_wv_bind_N`) with `noinline optnone` so `-O2` leaves its setjmp handling alone. The thunks are cold, per-invocation glue (one call across the JS↔native bridge), so excluding them from optimization has no measurable cost. The pump thunk and the rest of the runtime keep `-O2`.

## Implementation notes

One-line change in `emitWebviewBindThunk`: the `define void @__kml_wv_bind_N(...)` gains `noinline optnone`. `optnone` requires `noinline` in LLVM. The pump thunk (`@__kml_wv_pump`, same file) was left as-is — it carries no direct setjmp and was not implicated.

## Side effects discovered

Two *separate* bugs surfaced in the same example, unrelated to this one and fixed alongside:
- `JSON.parse` is type-directed projection (TDD-00077) — it only projects in a *type-annotated* position. The explorer (and the pre-existing `examples/webview/inline.ts`) used an untyped `const parsed = JSON.parse(args)`, which yields an empty result. Fixed to `const parsed: string[] = JSON.parse(args)`.
- The webview bind bridge passes JS call arguments to native as a JSON-array string; a helper that additionally `JSON.stringify`-wrapped its args double-encoded them. Callers now pass raw args.

A CI regression test isn't added here: exercising a bind requires a live webview window (a display), which the headless test lane can't drive. The three minimal repros above are recorded for manual re-check.

## Verification

- The file-explorer example (`examples/webview/explorer.ts`) now runs end-to-end at the normal `-O2`: directory listing with sizes, live text preview, and image preview (base64 data URL) — captured manually on macOS (Apple Silicon).
- Existing webview examples (`inline`, `spa`, `embedded`) still compile; the webview `go test` suite passes.
