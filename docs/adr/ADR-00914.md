# ADR-00914: Default-parameter filling through first-class function values (TDD-00206 Stage 1)

- **Date**: 2026-09-12

## Relations

- Implements [TDD-00206](../tdd/TDD-00206.md) Stage 1.
- Subsumes [ADR-00911](../adr/ADR-00911.md)'s IIFE-specific call-site padding.

## Context

Default parameters were filled only when the callee was statically identifiable
at the call site — a named function (`sig.Defaults`, `emit_call.go`), a class
method/constructor (`emit_classes.go`), or a literal IIFE ([ADR-00911](../adr/ADR-00911.md)).
A call through a **first-class function value** — a closure bound to a variable,
stored in an object field, or otherwise passed as a value — goes through
`emitClosureCallByPtr`, whose argument loop ran only `i < regularCount && i < len(args)`.
Omitting a trailing parameter emitted a `call` with fewer operands than the
callee's LLVM arity:

```ts
const f = function (a: number, b: number = 10): number { return a + b; };
console.log(f(5));                       // clang: not enough parameters specified for call
const g = (a: number, b = 7) => a + b;
console.log(g(3));                        // same
```

This is the everyday `const f = function(a, b = …)` shape, not just a Test262
exotic; the `meth-dflt-params-ref-{prior,later,self}` object-shorthand-method
files are the stored-method variant. The closure `Type` carried the parameter
*types* (`FuncParams`) but neither the parameter *names* nor the *default
expressions*, so the call site had nothing to fill from.

## Decision

Carry the defaults on the function `Type` and fill at the closure call site,
reusing the call-site machinery the named/class/IIFE paths already use.

- Add `FuncParamNames []string` and `FuncParamDefaults []ast.Expression` to
  `Type` (`types.go`). A helper `setFuncParamDefaults` populates them from a
  closure's `[]ast.Param` (nil `FuncParamDefaults` when no parameter has a
  default). It is called both where a closure *value* is emitted (arrow and
  function-expression construction, `emit_func.go`) and in the two `inferExprType`
  cases that answer "what type is this arrow/function expression" — the latter is
  what a `const f = …` binding's symbol type is actually derived from, so both
  must agree (the same duplication `FuncHasRest` already lives in).
- In `emitClosureCallByPtr`, iterate `i < regularCount` (was `&& i < len(args)`).
  For an omitted parameter, fill from `FuncParamDefaults[i]` if present, otherwise
  with an `undefined` literal (JS semantics — an omitted parameter is `undefined`,
  which coerces to a typed slot's zero; an array slot fills an empty array). A
  default that references an earlier parameter (`b = a`, `z = y`) resolves via the
  existing `paramDefaultScratch` scope, which materializes each earlier
  scalar/array/nullable parameter under its name only while a default is emitted.
- Remove [ADR-00911](../adr/ADR-00911.md)'s IIFE-specific call-site padding: the
  IIFE closure value now carries its own defaults, so the general path handles it.

## Consequences

- Fixes the whole closure-value default-parameter class: variable-bound closures,
  object-field arrow methods, and object-shorthand methods with constant,
  string-typed, cross-parameter (`y = x, z = y`), and array/nullable defaults.
- A default is evaluated in the *caller's* scope here, so this stage does not
  cover a default that references a variable *captured* from the closure's
  defining scope (a sibling-parameter reference is handled by the scratch scope,
  and a module-global / top-level-function reference works because those are
  visible everywhere). That capture case is closed by
  [ADR-00915](../adr/ADR-00915.md) (Stage 2, body-prologue filling with an
  argument-presence mask). No behavior is deferred as a miscompile: before Stage 2
  the capture case was a clean codegen error, never a wrong result.

## Bug fixed in passing

Extending the closure call path to fill omitted parameters surfaced a
pre-existing gap: an **optional** `x?: T` parameter on a first-class function
value was not widened to `T | undefined`. Closures never called
`optionalParamType` (unlike named signatures, [ADR-00042](../adr/ADR-00042.md)/
TDD-00187), so `(a: number, b?: number) => a + (b ?? 99)` typed `b` as a plain
`number`; before this change the omitted call under-supplied the arguments
(invalid IR), and the new fill path would have handed `b` a typed zero (`0 ?? 99`
→ `0`) — a silent wrong result. Fixed by applying `optionalParamType` at all four
closure param-type sites (arrow + function-expression, in both `emit_func.go`
construction and the `inferExprType` mirror that types a `const f = …` binding),
so an omitted optional argument is now a genuinely-absent nullable value, as in
Node.

## Verification

- `TestE2EClosureValueDefaultParams` (new): variable-bound function expression and
  arrow (constant, cross-parameter `a * 2`, string default), object-shorthand
  method with chained `y = x, z = y`.
- `TestE2EClosureOptionalParamAbsent` (new): an omitted optional parameter on a
  closure value / function expression is absent, not a typed zero.
- `TestE2EIIFEDefaultAndOmittedParams` (ADR-00911) still passes through the
  consolidated path.
