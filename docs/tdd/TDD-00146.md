# TDD-00146: Sailfish OS target — cross-compiled CLI tools + a Gecko webview backend

- **Status**: Not Started
- **Date**: 2026-08-29
- **Notes**: Sailfish is glibc Linux (aarch64), so CLI tools need only a `--target`/`--sysroot` cross-compile mode + RPM packaging; the UI route is `sailfish-components-webview` (Gecko/qtmozembed — `runJavaScript` + async messages map onto the [TDD-00142](TDD-00142.md) bind/eval contract) as a `-webview=sailfish` backend under [TDD-00144](TDD-00144.md)'s flag. Harbour allowlist checked: libcurl in, pcre2/bdw-gc must be bundled. Silica/QML generation deliberately out of scope

## Context

Sailfish OS is a glibc-based mobile Linux (Jolla): aarch64 on current devices
(Jolla C2, Sony Xperia 10 III/IV/V), armv7hl on legacy ones, i486 in the SDK
emulator. It is *not* Android — no bionic, no Dalvik/ART in the native tier —
which makes it the closest thing to a "free" mobile target this compiler can
have: the existing Linux pipeline (LLVM IR → `clang -O2` → ELF, plain libc,
`select()` loop, fibers via ucontext) is architecturally at home; what is
missing is a cross-compilation story, a packaging story, and a UI story.

The UI question has an unusually good answer. Sailfish's native UI toolkit is
Silica — a proprietary QML component library on an old Qt 5 (long frozen
around 5.6 for licensing reasons; the 5.0 "Tampella" release notes show no
major Qt bump). Direct Silica integration would mean generating QML and
binding Qt — an entirely new UI paradigm for this compiler, out of proportion
to the platform's size. But Sailfish also ships `sailfish-components-webview`
(`import Sailfish.WebView 1.0`): an embeddable webview backed by the **Gecko**
engine of the system browser (embedlite/qtmozembed; ESR91 as of OS 5.0, ESR102
in progress). Its API, verified in the qtmozembed headers
(`qmozview_defined_wrapper.h`): `Q_INVOKABLE runJavaScript(script, callback)`,
`sendAsyncMessage(name, variant)`, `addMessageListener(name)`, a
`recvAsyncMessage(message, data)` signal, and `loadFrameScript(name)`. That is
structurally the same contract [TDD-00142](TDD-00142.md)'s `klain:webview`
already builds on (eval + a JS→native message channel + native→JS
resolution), so Sailfish slots into [TDD-00144](TDD-00144.md)'s selectable
`-webview=<backend>` design as a third backend rather than a new subsystem.

Store rules matter and were checked against the actual Harbour
`allowed_libraries.conf` (the `sdk-harbour-rpmvalidator` repo):

- `libcurl.so.4` **is** allowed → `fetch` works in store-distributable apps.
- `libpthread`, `libm`, the Qt5 public modules, and the webview stack
  (`libsailfishwebengine.so.1`, `libqt5embedwidget.so.1`) are allowed.
- `libpcre2` is **not** allowed (community packaging exists in Chum) →
  `RegExp`-using Harbour apps must bundle pcre2 app-privately or link it
  statically.
- Boehm (`-mm=gc`) is **not** allowed → bundle it, or ship `-mm=manual`
  binaries — short-lived CLI tools are exactly manual mode's sweet spot.

Harbour only constrains GUI apps; pure CLI tools distribute via Chum
(community OBS) or plain RPM, where the allowlist does not apply.

## Design

### Stage 1 — cross-compilation (`--target`)

The compiler today builds for the host. Add a generic cross-target flag with a
Sailfish preset:

- `--target <triple>` + `--sysroot <path>`: pass the triple and sysroot to
  clang (`clang --target=aarch64-linux-gnu --sysroot=…`), and make the
  data-layout/triple lines in the emitted IR follow the target instead of the
  host. The IR itself is almost target-clean already; the audit points are
  `i64`-vs-pointer assumptions (safe: both targets are LP64), any host-CPU
  feature strings, and the embedded-C runtime (compiled per-build, so it just
  follows the same flags).
- `--target sfos-aarch64` (preset): resolves triple + sysroot from a Sailfish
  SDK build target. Two acquisition routes, both supported:
  1. **Inside the Sailfish SDK** (sanctioned): the SDK's scratchbox2 targets
     (`sfdk`, sb2 + rpmbuild) provide a full target rootfs with glibc, Qt,
     libcurl. `klainmain` runs on the host (or in the SDK chroot) and only
     clang's `--sysroot` points into the target rootfs.
  2. **Bare sysroot**: point `--sysroot` at an extracted target rootfs tarball
     without installing the SDK — enough for CLI binaries, and what CI would
     use.
- Linking: prefer the host clang with `--sysroot` + `-fuse-ld=lld` (no
  target-gcc dependency). The conditional-linking convention is unchanged —
  `-lcurl`/`-lpcre2` only when used, resolved against the sysroot.
- **Explicitly out of scope for Stage 1**: running the compiler *on* the
  device, and armv7hl (32-bit breaks the `number → i64`-centric ABI
  assumptions far more than aarch64 does; treat armv7hl as unsupported until
  someone asks).

Verification without hardware: the emitted binaries run in the SDK emulator
and — cheaper — under `qemu-aarch64 -L <sysroot>` and in an aarch64 glibc
Docker image (the ADR-00351 precedent: Docker on the M4 already stands in for
Linux/arm64). True device verification (Jolla C2) is the only tier that
proves the Wayland/Silica/webview layers; everything CLI-shaped is provable in
emulation.

### Stage 2 — RPM packaging (`-package` grows a `.spec` emitter)

`-package` today emits `.app` (macOS) / `.desktop` (Linux). Add an RPM shape:

- Generate a minimal `.spec` (Name/Version/Summary/License, `%files` with the
  binary and — for GUI apps — the `.desktop` + icon), and drive `rpmbuild`
  when available (native on the SDK/sb2; on the Mac only the spec is
  emitted).
- Harbour naming rules apply to store apps (`harbour-<name>` binary and
  package name, files under `/usr/share/harbour-<name>/`); make that a
  `-package`-time flag (`-package rpm:harbour` vs `-package rpm`), since Chum
  RPMs deliberately don't follow it.
- Bundled private libs (pcre2, bdw-gc when needed) land in
  `/usr/share/harbour-<name>/lib` with an `rpath` entry — the sanctioned
  Harbour pattern for non-allowlisted libraries.

### Stage 3 — Sailfish WebView backend for `klain:webview`

Under TDD-00144's `-webview=<backend>` flag, add `-webview=sailfish`:

- **Shim shape**: the existing 13-function C binding gets a Qt/C++
  implementation (`webviewsrc/` gains a `webview_sailfish.cpp`): a
  `QGuiApplication` + a QML scene hosting `Sailfish.WebView`'s `RawWebView`
  (the low-level type below the Silica-styled `WebView.qml`), driven from C
  via a thin `extern "C"` wrapper. Links `qt5embedwidget`/
  `sailfishwebengine` + Qt5 — all Harbour-allowed.
- **eval**: `runJavaScript(script, callback)` directly.
- **bind**: the same JSON protocol as the WebKit backend, transported over
  embedlite messaging instead of a script-message handler: inject (via
  `loadFrameScript` or an init `runJavaScript`) a shim that forwards
  `window.<fn>(…)` calls as an async message; the native side
  `addMessageListener` + `recvAsyncMessage` → dispatch to the trampoline →
  resolve the page promise with `runJavaScript`. The typed-bind /
  `--emit-window-dts` layer is transport-agnostic and carries over untouched.
- **serve / assets**: `Webview({ serve })` + `klain:assets` embedding carry
  over unchanged — the in-binary HTTP server is engine-agnostic; the view
  just loads `http://127.0.0.1:<port>/`.
- **Loop fusion**: third variant after GTK and AppKit — Qt's event loop
  (`QEventLoop`/`processEvents` integration with the fiber scheduler's
  `select()`, same structure as the GTK fusion; Qt exposes
  `QSocketNotifier` for the inverse direction if polling proves ugly).
- **Look**: the page is the SPA, not Silica-native chrome. Acceptable for V1
  (Jolla's own docs treat WebView apps as first-class); a Silica-ish CSS
  theme is a later nicety, not scope.
- **Qt age**: only the webview component's stable surface is touched, so the
  frozen Qt 5 is not a practical constraint — but assume nothing newer than
  5.6 semantics in the shim.

### Runtime audit (expected-clean, verify anyway)

glibc `select()`/fibers (ucontext)/`fork`/socketpair IPC/signals — all
standard Linux, expected to work as-is on the device. The known platform
variables, all with precedent: libcurl's TLS backend differs per-distro
(ADR-00080/00099/00100 pattern — Sailfish builds curl against OpenSSL;
re-verify the cleanup-at-exit interactions), and `--static` stays Linux-only
and would mostly be moot under RPM packaging anyway. Wayland is irrelevant to
CLI and hidden behind Qt for the webview.

### What this deliberately does not attempt

- **Silica/QML UI generation** — a different compiler product; the webview
  *is* the UI story here (same verdict as TDD-00142 vs. native widgets).
- **On-device compiler** (self-hosting on the phone).
- **armv7hl** (32-bit ABI work without a requester).
- **Android AppSupport** as a delivery vehicle (that's the Android target's
  problem — [TDD-00147](TDD-00147.md) — not Sailfish's).

## Open questions

- **Preset resolution** — should `--target sfos-aarch64` locate an installed
  Sailfish SDK automatically (convenient, magic) or always demand an explicit
  `--sysroot` (predictable)? Leaning explicit-with-good-error.
- **Test-suite strategy for cross targets** — the E2E suite executes compiled
  binaries; for cross builds that means qemu-user wiring (`binfmt` or an
  explicit runner prefix) or an emulator SSH lane. Which becomes the standing
  CI shape for *all* future cross targets (Android shares this problem)?
- **pcre2/bdw-gc bundling mechanics** — static archive into the binary vs.
  private shared lib + rpath in the RPM; static is simpler but collides with
  the "static is Linux-only, glibc-hostile" history.
- **RawWebView vs. styled WebView.qml** — RawWebView avoids pulling Silica
  theming into the shim but re-implements popups/pickers; the styled one
  drags in more QML surface. Needs a device experiment.
- **Frame script vs. injected shim for bind** — `loadFrameScript` runs in the
  privileged embedlite context (more capable, Gecko-specific format);
  an ordinary injected script + async message may be enough and stays closer
  to the WebKit backend's shape.
