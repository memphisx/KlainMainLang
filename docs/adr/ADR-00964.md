# ADR-00964: HTTPS/1.1 streamed backpressure + unified `res.write`/`req.pipe(res)` output

- **Relations**: `Implements TDD-00195`, `TDD-00214`. Extends `ADR-00961` (Layer A socket backpressure), `ADR-00962` (observable `res` backpressure), `ADR-00959` (incremental `res` Writable).
- **Date**: 2026-09-15

## Context

Two `res`-streaming edges were left open after ADR-00962:

1. **HTTPS/1.1 chunk writes stayed blocking.** Over TLS the connection socket was
   left blocking for the stream's lifetime, and chunk writes routed through
   `__kml_tls_write_all`, which poll()s internally on `WANT_WRITE`. A slow TLS
   consumer therefore blocked the whole reactor inside `SSL_write`, and
   `res.write` could keep returning `true` past `highWaterMark` — no observable
   backpressure over TLS.
2. **Raw `res.write` interleaved with `req.pipe(res)` on one response was
   unsupported.** A direct `res.write` framed into the per-response output queue
   (`res.__kml_outq`, ADR-00962) while the pipe sink wrote straight to the socket
   via `__kml_res_write_all` — two independent output paths, so bytes from the two
   could reach the wire out of order.

Faithfulness-first (this project's own practice): both are possible natively, so implement, don't
diverge.

## Investigation

Plain HTTP already parks correctly on `EAGAIN` (`__kml_res_write_all` /
`_flush` / `_drain_try`, ADR-00961/00962). The only reason HTTPS differed was the
blocking socket + the blocking `__kml_tls_write_all`. A first cut — reuse the
non-blocking send path over TLS — truncated the stream for a *slow* reader
(clean for a fast one). Instrumenting the fatal path showed no `SSL_get_error`
fatal; the failure was OpenSSL's `SSL_R_BAD_WRITE_RETRY`: after a `WANT_WRITE`,
`SSL_write` must be retried with the *same buffer pointer*, but the output queue
`realloc`s/compacts (`__kml_res_qappend`) between the opportunistic
`__kml_res_drain_try` and the later `__kml_res_flush`, moving the buffer. The
pending record is already encrypted in the write BIO, so only OpenSSL's safety
check needed relaxing.

## Decision

**HTTPS backpressure.**
- New non-blocking TLS write primitive `__kml_tls_write_nb` (`tlssrc/tls.c`):
  one `SSL_write`, `-1`/`errno==EAGAIN` on `WANT_READ`/`WANT_WRITE` *and* on
  `SSL_ERROR_SYSCALL` with `errno` already `EAGAIN`/`EWOULDBLOCK` (a full send
  buffer can surface either way on a non-blocking BIO), `-1`/`errno==0` fatal
  otherwise. It never poll()s, so a slow TLS consumer parks one fiber.
- New shim `__kml_http_conn_send_nb` (`runtime_http.go`): TLS →
  `__kml_tls_write_nb`, plain fd → raw non-blocking `write()`. The `res` writer's
  chunk-write helpers route here on HTTPS (the block-level `write` → shim rewrite
  in `ensureResStreamRuntime` now targets `_nb`, not the blocking
  `__kml_http_conn_send`).
- `__kml_res_begin` now re-enables `O_NONBLOCK` after the (blocking) head send on
  HTTPS too (`RENONBLOCK` is no longer emptied for HTTPS), so the reused
  `@__kml_conn_writepark` / `%wfdset` park path applies unchanged over TLS.
- `SSL_CTX_set_mode(ctx, SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER)` on the server
  context, so a `WANT_WRITE` retry from a moved queue buffer is accepted.

**Unified output path.** `__kml_res_sink_write` (the `req.pipe(res)` sink) now
frames its chunk into the *same* `res.__kml_outq` a direct `res.write` uses, then
blocking-drains via `__kml_res_flush` (preserving the pipe's
drain-before-next-chunk Layer A contract). `__kml_res_sink_close` flushes the
queue before the terminal chunk. Draining one queue in append order sends any
earlier direct-write bytes before the pipe's chunk, so interleaving the two on one
response is correctly ordered.

**Keep-alive over TLS.** With non-blocking TLS chunk writes and `O_NONBLOCK`
restored at stream end (`__kml_res_sink_close`), a streamed HTTPS response now
re-arms the connection for the next request exactly as plain HTTP does, so
`emitResBegin` no longer forces the keep-alive decision off for `usedHTTPS1Server`
(it always passes `allowKA=1`; the decision itself still honours the request
headers). (This is the `res.write` streamed path; the static `ReadableStream`-body
return path's TLS re-arm remains separately gated.)

## Implementation notes

- `__kml_tls_write_nb` clears `errno` before `SSL_write` so the `SSL_ERROR_SYSCALL`
  `errno` test reads the value that call set, not a stale one.
- The moving-write-buffer relaxation is safe because `SSL_MODE_ENABLE_PARTIAL_WRITE`
  stays off: `SSL_write` accepts either the whole length or nothing, so the queue
  head only advances on full success, and the pending encrypted record is
  independent of the (possibly moved) plaintext buffer on retry.
- A `WANT_READ` mid-write only arises during renegotiation, which TLS 1.3 removed
  and this 1.2+ server never initiates; it collapses to the writability wait, like
  `__kml_tls_read_nb`'s symmetric WANT collapse.
- `__kml_res_write_all` remains only for `__kml_res_sink_close`'s terminal chunk.

## Side effects discovered

None outstanding. The earlier slow-reader truncation was the `BAD_WRITE_RETRY`
above, fixed here.

## Verification

macOS arm64 (M4): `go build`/`go vet` clean. New E2E tests:
`TestE2EHTTPSResStreamBackpressure` (a slow TLS reader parks mid-stream — a
concurrent quick TLS request still completes, proving the reactor is not blocked —
and the parked stream then resumes to deliver the whole 2 MiB body intact through
the WANT/EAGAIN park path) and `TestE2EHTTPCreateServerResWritePipeInterleave`
(a direct `res.write` prefix followed by `req.pipe(res)` arrives in order) and
`TestE2EHTTPSResStreamKeepAlive` (two sequential requests on one reused TLS
connection both stream correctly). All existing http/https/tls/websocket/streams/
fetch/http2 suites pass (146s, exit 0). No new invalid IR (http/tls paths, not
Test262-exercised; `make test-par` / `make examples` are the gates).
