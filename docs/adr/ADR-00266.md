# ADR-00266: Event-driven waiter list for `Promise.race`/`.any` over tasks; `new Promise<void>`

- **Relations**: refines [ADR-00073](ADR-00073.md)/[TDD-00083](../tdd/TDD-00083.md) (combinators); closes the `.race` busy-poll caveat
- **Date**: 2026-08-20

## Context

`Promise.race`/`.any` over task promises (from may-suspend async fns) waited via
`__kml_task_await_any_of`/`__kml_task_await_first_fulfilled`. On a task these
**parked with no waiter registered** — `pendingProm` stayed null, so the scheduler
treated the task as "woken" and re-resumed it every step, re-scanning the members
each time: a correct-but-busy poll that spun the scheduler until a member settled.

A separate bug surfaced while testing: `new Promise<void>((resolve) => …)` emitted
the resolve thunk with a `void %v` parameter — invalid IR ("void type only allowed
for function results"). `resolve()` for a void promise takes no argument.

## Decision

**Waiter list.** In the on-task park path of both combinator waits, before
swapping out: register the task as the `waiter` (promise field 1) on **every**
member, and set `pendingProm` to a non-null sentinel (`members[0]`, known pending
since the pre-park scan found none settled). A settling member clears its waiter's
`pendingProm` (`__kml_task_finish`/`__kml_promise_settle` already do this), so the
scheduler's existing `chkpp` resumes the task exactly once — when a member settles
— instead of every step. On resume it re-scans and returns the settled member. A
stale waiter left after the wait returns can only cause a harmless spurious wake
(the next wait re-checks its own condition and re-parks). Top-level (no current
task) still drives the scheduler directly, unchanged.

**`new Promise<void>`.** The resolve thunk and the executor's `resolve` param type
are now argument-less for a void value type (`void @thunk(ptr %p)` /
`resolve: () => void`), and the thunk just settles without storing a value.

## Consequences

- `Promise.race`/`.any` over task promises no longer busy-spin the scheduler while
  waiting; behavior is identical (verified: the same winner as the poll, and the
  first-to-settle member wins when settle times differ — a fast fetch beats a slow
  timer). The `.race` busy-poll caveat is closed.
- `new Promise<void>((resolve) => setTimeout(resolve, ms))` (a void delay) works.
- The `Promise.all`/`.race`/`.allSettled` row keeps its other caveat — each
  combinator call frees every element's own promise slot, so a member can't be
  reused afterward — so the row stays non-strict.
- A pre-existing quirk (not from this change, present with the old poll too):
  `Promise.race` over several `setTimeout`-based tasks can return a member other
  than the shortest-delay one, because the event loop's timer/task resume ordering
  isn't strictly fire-time-first. Tracked separately; orthogonal to the poll.

## Verification

- `go build`, `go vet ./...` clean; full `go test ./...` green (no combinator
  regression).
- New E2E: `TestE2ENewPromiseVoid`, `TestE2ERaceTaskPromisesWaiterList` (fetch
  beats a 400 ms timer in a task-promise race). Confirmed the winner matches the
  old busy-poll on the same input, so the change is behavior-preserving.
- `make examples` at delivery; conformance batched to session end.
