# ADR-00643: Decorators Stage 3 — `emitDecoratorMetadata` and the Reflect metadata API

- **Relations**: `Implements TDD-00161` (Stage 3), `Extends ADR-00642`
- **Date**: 2026-09-02

## Context

TDD-00161 Stage 3: TypeScript's `emitDecoratorMetadata`. With the flag, a
decorated member gets `design:type` / `design:paramtypes` / `design:returntype`
reflection metadata that a decorator (or later code) reads through
`Reflect.getMetadata` — the mechanism dependency-injection frameworks rely on.

This stage is deliberately about **runtime faithfulness**, not the Track C
oracle: `emitDecoratorMetadata` is an emit-time feature, so it cannot change the
accept/reject verdict on any source file. (Verified: the single-file
`decoratorMetadata*` corpus cases that motivated it either already compile after
Stages 1-2, are multi-file/out-of-scope, reject for unrelated reasons, or use
class decorators still gated on Stage 4.)

## Investigation

- TS emits metadata as `Reflect.metadata(key, value)` decorators in its JS
  output. This compiler emits IR directly, so it can call `Reflect.defineMetadata`
  at class-definition time instead of going through `Reflect.metadata` (which
  returns a decorator and would hit the same returned-value-call ABI gap factory
  decorators do). The compiler-generated metadata therefore needs no factory.
- There is no first-class class-constructor value in this compiler, so a design
  type cannot be the real `Number`/`String`/class constructor. The faithful-
  within-limits representation is a name-carrying descriptor object
  (`{ name: "Number" }`, `{ name: "Dep" }`), correct for `.name` inspection but
  not identity.
- Metadata storage reuses D1: no new runtime. The store is a nesting of dynamic
  objects on the target — a reserved root bag, keyed by property key, keyed by
  metadata key.
- A metadata target must be an actual tag-10 dynamic object; a boxed static
  class instance (tag 6) would corrupt the bag functions — so the runtime path
  guards the tag and throws a TypeError on misuse.

## Decision

- **Flag**: `-emit-decorator-metadata` (`SetEmitDecoratorMetadata`), mirroring
  TS. No-op unless set.
- **Design-type descriptors** (`emit_decorators_meta.go`): `designTypeName`
  maps a static `Type` to TS's constructor name (Number/String/Boolean/BigInt/
  Date/Promise/Array/Function/Object, or the demangled class name; `undefined`
  for void/never). `emitDesignTypeDescriptor` builds a `{ name }` dynamic
  object; `emitDesignParamtypes` builds a dynamic array of them.
- **Auto-emission**: when the flag is set, before a decorated member's user
  decorators run, `emitClassMemberDesignMetadata` defines `design:type` for a
  decorated property, and `design:type` (= Function) / `design:paramtypes` /
  `design:returntype` for a decorated method, on the per-class decorator target.
- **Reflect metadata API** (`emit_reflect.go`): `defineMetadata`, `getMetadata`
  / `getOwnMetadata` (V1 does not walk the prototype chain, so they coincide),
  `hasMetadata` / `hasOwnMetadata`, over the nested-bag store. `Reflect.metadata`
  used manually as a decorator factory is a clean rejection (the returned-value-
  call gap).

## Implementation notes

- The store is `target[\x01meta][propKey|\x01ctor][metaKey] = value`, each level
  a lazily-created dynamic object via `emitDynGetOrCreateBag`.
- Design metadata is defined *before* user decorators run, so a user decorator
  reading `Reflect.getMetadata("design:paramtypes", target, key)` sees it —
  matching TS's decorator/metadata ordering.

## Side effects discovered

- A decorated method's replacement whose body iterates a `paramtypes` array with
  a numeric loop (`i < params.length`) hits the pre-existing "operator on
  any/unknown" limitation (the metadata array is `any`); reading by fixed index
  works. Disclosed in the example.
- Metadata targets are limited to real dynamic objects; a boxed static class
  instance is rejected at runtime (see above). Design metadata itself lives on
  the per-class decorator target, which is always a dynamic object.

## Verification

- `tests/decorators_test.go`: method design:type/paramtypes/returntype read by a
  decorator; property design:type incl. a demangled class name; direct
  `Reflect.defineMetadata`/`getMetadata`/`hasMetadata`. A new
  `assertOutputWithDecoratorMetadata` helper compiles with the flag.
- `examples/decorators/decorator_metadata.ts` runs both with the flag (full
  design metadata) and without (guarded — the direct Reflect metadata still
  works), so `make examples` (default flags) passes.
- `go vet`, full `make test-par`, decorator/reflect/dyn suites, node oracle,
  `status-check`/`reference-check` pass. Mac (Apple Silicon).
