# ADR-02054: Compile time held at HEAD's: precise library links, one-pass IR scans

- **Date**: 2026-11-22

## Context

- Against the last release, compiling the benchmark set (20 examples,
  `-emit-llvm`) took 15–25 % more user CPU per file, up to 70 % on
  `examples/arrays/from_async.ts`. Profiles (Node304, `runtime/pprof`)
  placed it in:
  - code generation of library functions the program never calls: a
    library file naming `Array` and `prototype` anywhere (`C.prototype`
    beside `Array.from`) linked kml_array.ts (`kml:lower
    Array.prototype`), and that the typed-array module — 400 functions
    for one `Array.fromAsync`; `Array.from` alone linked the
    constructor forms, which only `.call`/`.apply` use;
  - `strings.Replacer` marking every call `notail` over the whole module;
  - `emitNamedRoutines` searching the IR text twice per routine per pass.

## Decision

- A library file links a multi-part `kml:lower` path only where it
  writes that member path (`Array.prototype`), not where it merely names
  its parts; a program still links on the names, which an alias may
  carry.
- `Array.from`/`of`/`fromAsync`'s constructor forms and `Array.fromAsync`
  move to lib/node/kml_array_ctor.ts; the forms link on
  `Array.<static>.call` (the resolver adds `.apply`).
- The `notail` writer scans for `call ` directly; `emitNamedRoutines`
  scans the IR once per pass for every routine's definition and use.

## Consequences

- The same IR, byte for byte, on the benchmark set before and after the
  writer and scan changes.
- Benchmark (Node304, two rounds, compile and link of 20 examples): wall
  41.2 / 39.6 s against HEAD's 41.9 / 42.0 s, user 49.6 / 48.6 s against
  54.0 / 54.1 s, peak RSS 675 MB against 933–1215 MB, binaries 18.4 MB
  against 27.5 MB.
