# ADR-01147: Invalid IR found by Test262: lowered-argument ToNumber, loop captures, `switch` case types

- **Relations**: `Extends ADR-01142`, `ADR-01143`; `Implements TDD-00230` (Phase 3)
- **Date**: 2026-09-25

## Context

Test262 (`-compat=js`) reported 24 clang failures against the staged tree
and none at HEAD. Invalid IR is a compiler bug, not a divergence: a
program either compiles to a correct binary or gets a clean diagnostic.

## Investigation

A fail list from each build (`tools/conformance -faillist`), diffed on
`CLANG_ERROR`, gave the 24. They reduced to six causes:

- **A lowered method passed its argument unconverted (18).** `'abcd'.charAt('2')`
  and `(1.5).toFixed('1')` in `-compat=js` stored a string pointer into a
  `double` parameter. The strict lane rejects these calls, as tsc does.
  This was new with the `@lower` path (ADR-01142, ADR-01143).
- **`BigInt(x)` was typed as a number** by `inferExprType`, so
  `BigInt(0).toString()` took the Number receiver. This was new with
  ADR-01143's number receivers.
- **A for-of/for-in variable captured in two branches of the body.** Its
  heap cell was made at the first capture, inside one branch, and the
  other branch used it. Older than this work: the strict lane emitted the
  same IR for `for (const x of xs) { if (c) f = () => x; else g = () => x }`.
  The `-compat=js` lane now compiles these tests, so the IR surfaced.
- **`switch (null) { case 0: }` compared a pointer with a double.** Older
  than this work.
- **`var n = null; n === 0`** compared the same way, and a `null` binding
  was `===` to an `undefined` one. Older than this work.
- **`Object.fromEntries([["p", "v"]])`** read the string value as an `i64`,
  since a string-pair literal infers as `string[][]`, not a tuple. Older
  than this work.

## Decision

- **Lowered arguments.** `lowerArg` converts an argument to a number
  parameter with `emitUnaryPlus` (ToNumber), as it already converted one
  to a string parameter with ToString.
- **`BigInt(…)`** is typed as a bigint in `inferExprType`.
- **Per-iteration loop cells.** `beginLoopIteration` gives each
  `let`/`const` loop-head binding captured by a closure in the body a
  fresh cell at the body's top, as `emitFor` already did for a classic
  loop. Every for-of variant and for-in emits its body through
  `emitForOfBody`/`emitForInBody`.
- **`switch`** compares a case directly only for two strings or two
  plain numbers of one kind. Any other pairing emits `disc === test`
  against a synthetic binding of the discriminant, so a case matches
  exactly as `===` does.
- **Equality of a nullish binding.** A `null` or `undefined` binding
  against a present number or boolean is never equal. A `null` binding
  is never `===` to an `undefined` one. A literal `null`/`undefined`
  keeps the existing comparison, which also reads a `number | null` held
  as a plain number.
- **`Object.fromEntries`** takes a `T[]` pair's elements 0 and 1
  (`fromEntriesTypes`, `arrayEntryElemOrZero`). A literal is a `T[]` pair
  only when every element of every pair is a string, since its inferred
  type comes from the first pair alone.

## Side effects discovered

- **`[["a", 1]] as [string, number][]`** is rejected as a heterogeneous
  array: the assertion does not type the literal (BACKLOG).
- **`n.a + n.b`** on `Object.fromEntries(e)` with `e: [string, number][]`
  is rejected as possibly undefined; tsc types an index-signature read as
  `number` (BACKLOG).
- **A `string | null | undefined` value** compares `null` and `undefined`
  as one value, the known three-state representation gap (BACKLOG).

## Verification

- **Test262:** the affected categories report no clang failures in either
  lane. The full-run numbers are below.
- **New tests, with Node's output:** `TestE2ELoweredNumberArgToNumber`,
  `TestE2EBigIntCallResultMethods`, `TestE2EObjectFromEntriesStringPairs`,
  `TestE2ELoopVariableCapturedInBranches`, `TestE2ESwitchMixedTypeCases`,
  `TestE2ENullishEqualityAgainstScalars`.
- **Gates (with ADR-01145–01147):** Test262 strict 7,034 (+3 over
  ADR-01144), js 7,825 (+32), no clang failures in either lane; the Node
  suite is unchanged (strict 61, js 63). `make examples` 360/360 apart
  from `chained_listen`'s intermittent hang (1 in 3 alone; HEAD hangs at
  the same rate). `make test-par`: only the four macOS `-mm=gc` failures.
