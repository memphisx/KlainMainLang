# ADR-00827: keep-alive on the union-body (`string | ReadableStream`) string branch

- **Relations**: Extends [ADR-00802](ADR-00802.md) (persistent streamed responses), [ADR-00825](ADR-00825.md) (`res.end()`-driven flush); part of the [TDD-00131](../tdd/TDD-00131.md) `http.createServer`/`klain:http` server
- **Date**: 2026-09-10

## Context

HTTP/1.1 keep-alive already covered the buffered `res.end(…)` path and
chunked/streaming (`ReadableStream` body) responses ([ADR-00802](ADR-00802.md)):
each re-arms the connection at response/stream end so a second request on the
same socket is served. The one response shape left closing unconditionally was
the **union body** (a handler whose `body` field is `string | ReadableStream`)
taking its *string* branch — it sent `Connection: close` even when the client
wanted keep-alive, breaking connection reuse for handlers that return a string
from one route and a stream from another (the common `{ body: string |
ReadableStream }` shape, TDD-00119).

## Investigation

The union-body tail in `emitHTTPResponse` (`emit_http.go:2359`) splits at
runtime on the body box's tag: the stream sub-branch already honoured the
per-response keep-alive decision via `streamKA` (computed at `emit_http.go:2350`
for `(streamingBody || unionBody) && !usedHTTPS1Server`), but the **buffered
string sub-branch** (`:2394`) hard-coded `i1 0` into `__kml_http_send_response`
and then unconditionally stored `fd -1`, decremented the active-connection
count, and returned — the exact "always close" shape. The single-shape buffered
path below it (`:2429`) already demonstrated the correct keep-alive loop:
send with the decision bit, then branch to either a parse-state reset + jump
back to the read loop, or a close + active-count decrement + return.

`streamKA` was already the right register — forced off for HTTPS/1.1 (whose
re-arm path is still unvalidated against the TLS read loop), a real decision
otherwise — so the fix was to feed it to the string branch and give that branch
the same keep-alive fork.

## Decision

In the union-body buffered string branch, pass `streamKA` (not `i1 0`) to
`__kml_http_send_response`, then branch on it:

- **keep-alive** — reset the per-request parse state (`totalReadA`,
  `headersParsedA`, `headerEndA`, `contentLenA`, `headersMapA`, the same five
  stores the single-shape path uses) and `br` back to `readLoopL`, re-arming the
  fiber to serve the next request on the same socket.
- **close** — store `fd -1`, decrement `__kml_conn_active`, `ret void`.

HTTPS/1.1 is unaffected: `streamKA` stays `0` there, so the string branch still
closes, matching the existing HTTPS streaming caveat.

## Implementation notes

- `emit_http.go`: only the buffered sub-branch of the `unionBody` block changed;
  the stream sub-branch and the single-shape paths are untouched. The parse-state
  allocas and `readLoopL` are function-level (declared at `:1752`–`:1773`), so
  the new keep-alive continuation reuses them directly.

## Side effects discovered

None. The chunked/streaming union sub-branch already re-armed; this only brings
the string sub-branch to parity.

## Verification

Verified on macOS (Apple Silicon M4): new `TestE2EHTTPUnionBodyStringKeepAlive`
(two requests on one socket — first keep-alive, second `Connection: close` —
both served, headers asserted) passes; `go test -run TestE2EHTTP` green
(60s full HTTP suite, no regression), including the existing
`TestE2EHTTPChunkedKeepAlive` and the union-body echo paths.
