# ADR-00101: Root cause of the `-mm=gc` clustering hang — `GC_stackbottom` never restored when a fiber runs to completion

- **Relations**: Extends [ADR-00071](ADR-00071.md) (the original `GC_stackbottom`-repointing scheme), [ADR-00093](ADR-00093.md) (the read-loop yield's own restore fix — turned out to still be incomplete), [ADR-00099](ADR-00099.md) (the exhaustive-but-unsuccessful first investigation pass); Implements [TDD-00025](../tdd/TDD-00025.md)'s `-mm=gc` follow-on (now complete — see Status)
- **Date**: 2026-08-05

## Context

ADR-00099 shipped `GC_set_handle_fork(1)` (fixing a 100%-reproducible fork/GC crash) and a 1MB fiber stack, but left `TestE2EHTTPListenClusteringGCModeMultipleWorkerPIDs` failing intermittently (roughly 1 in 40 to 1 in 150 iterations) with two symptoms: a slow hang (a connection fd's read-loop bookkeeping goes arithmetically inconsistent, `totalReadA` observed >= `bufCapA`, and the fiber parks on a `read()` that will never return enough data) and a fast "connection reset by peer" failure (a worker process exits cleanly, no crash signal, well before it should). Six specific hypotheses were tested and ruled out in that pass; none was the root cause. The user explicitly asked not to leave this as an unresolved rabbit hole and to keep testing hypotheses empirically until root-caused, now that ASan/Valgrind tooling (ADR-00100) was available as a next step.

## Investigation

Rather than reach for ASan first (its documented `makecontext`/`swapcontext` limitations made it a poor fit for this specific fiber-heavy code path — noted in ADR-00100's own context), re-derived the failure from first principles by reading `__kml_event_loop_run`'s own exit path, since the "worker exits cleanly with no crash" symptom meant the event loop's `ret void` was being reached legitimately.

- `codegen/llvm/runtime_http.go`'s `__kml_event_loop_run` has exactly one `ret void` (the `alldone:` label), reached when `scandone:`'s `anywork = havetimer OR haslistener` is false — i.e., no pending timer and `@__kml_listen_fd < 0`. Grepping every `store ... @__kml_listen_fd` site (`codegen/llvm/emit_http.go:136`) showed it's set exactly once, before `fork()`'s children have any chance to diverge, and never written anywhere else — ruling out a logic bug that resets it directly. This pointed toward memory corruption landing on it indirectly rather than a control-flow bug.
- That reframing — "some write is corrupting live state through a stale/invisible pointer" — matched the slow-hang symptom's own evidence from ADR-00099 (an arithmetically-impossible `totalReadA`/`bufCapA` relationship) far better than any of the six previously-ruled-out mechanisms, all of which were per-connection-array or fork-timing hypotheses, not corruption-in-general hypotheses.
- Re-read ADR-00071's `GC_stackbottom`-repointing design (needed because Boehm's collector only auto-detects the *original* thread's stack — each `ucontext`-based fiber's own `malloc()`'d stack is otherwise invisible to its root scan, since these are cooperative fibers on one OS thread, not real pthreads Boehm's own `pthread_create` interception would know about). The scheme repoints `GC_stackbottom` at a fiber's own stack immediately before every `swapcontext` *into* it (`runtime_http.go`'s `__kml_http_append_conn` initial launch and `__kml_event_loop_run`'s `rresume` block), and — per ADR-00071 — restores it back to the real process stack immediately before yielding *back out*, with that restore placed at each of the known explicit-yield sites: the read-loop's `doYieldL` (`emit_http.go`) and the two `await`-style yields in `runtime_fetch.go` (`__kml_await_fetch`, `__kml_await_group_wait`).
- The gap: a fiber that runs a request to completion **without yielding again** after the read loop (the common case — full request buffered in one shot, synchronous handler, response sent) never executes any of those explicit-yield restore sites. It just falls off the end of `@__kml_http_dispatch` via `ret void`; control returns to whichever resumer's `swapcontext` call launched it via the automatic `uc_link` mechanism (glibc's own `ucontext` trampoline), which our own emitted IR has no hook into. `GC_stackbottom` is therefore left pointing at that now-defunct fiber's stack indefinitely — until the *next* resume happens to overwrite it. Any collection triggered by the event loop's own subsequent code (or by the next fiber's own allocations, before its own resume-side repoint executes) scans `[current SP, GC_stackbottom]` against the wrong range entirely: `GC_stackbottom` pointing at a `malloc()`'d heap address rather than the real process stack means Boehm's conservative scan either walks a nonsensical range or effectively skips scanning any of main's own current stack-only roots — silently freeing memory still reachable only from a stack local at that moment.
- This single mechanism explains both previously-observed symptoms as one root cause rather than two: which live allocation gets incorrectly collected in that window is essentially random, manifesting as either corrupted per-connection read-buffer bookkeeping (the slow hang) or corruption reaching something whose effect is a clean-looking early process exit (the fast reset) — consistent with why six *specific*, narrower hypotheses (SIGPIPE, marker threads, connection-array growth, fiber stack size alone, choice of Boehm fork-handling API, pure library incompatibility) all failed to reproduce or fix it: none of them touched the actual mechanism.
- Confirmed by inspection (not just reasoning) that this really is the only gap: grepped every `GC_stackbottom` occurrence across `codegen/llvm/`, found exactly two resumer sites (`__kml_http_append_conn`, `__kml_event_loop_run`'s `rresume`) that repoint it going in, and confirmed neither had any code executing after their respective `swapcontext` call returned — the fiber-side restores were the *only* mechanism keeping it correct, and only for the subset of exits that go through an explicit yield.

## Decision

Move the restore from the callee (fiber) side to the resumer (caller) side, unconditionally, immediately after each `swapcontext`-into-a-fiber call returns — covering both an explicit yield and a fiber running to completion identically, since both return control to the same resumer either way:

- `runtime_http.go`'s `__kml_http_append_conn` (`gcRestoreStackbottom`) and `__kml_event_loop_run`'s `rresume` block (`gcRestoreRStackbottom`) now each store `@__kml_gc_orig_stackbottom` back into `@GC_stackbottom` as the very next instruction after their own `swapcontext` call, in both GC-mode code paths.
- The now-redundant callee-side restores are removed (they were always overwritten by the caller-side restore before anything could observe the difference, so keeping both was dead code, not defense-in-depth): `emit_http.go`'s `doYieldL` block, and `runtime_fetch.go`'s two `await`-style yield sites (`__kml_await_fetch`, `__kml_await_group_wait`), which also removes the now-unused `gcRestoreStackbottom`/`gcRestoreStackbottomGroup` Go-side plumbing entirely.

Rejected alternative: keeping the callee-side restores *and* adding the caller-side one (pure redundancy, no correctness benefit — the callee-side restore can never run after the point where its own value would matter, since it's always immediately overwritten again on next repoint or is simply never reached at all in the completion case). Removed per this project's standing rule that unreachable/redundant code is a bug, not a safety margin.

## Implementation notes

Files touched: `codegen/llvm/runtime_http.go` (added `gcRestoreStackbottom`/`gcRestoreRStackbottom`, inserted after each resumer's `swapcontext` call), `codegen/llvm/emit_http.go` (removed the callee-side restore in `doYieldL`, replaced with a comment pointing at the resumer-side fix), `codegen/llvm/runtime_fetch.go` (removed both callee-side restores and their now-unused `gcRestoreStackbottom(Group)` variables/`Sprintf` args), plus removal of two pieces of TEMP DEBUG instrumentation added during ADR-00099's investigation and no longer needed once this was root-caused: an `abort()`-on-corruption assertion in `emit_http.go`'s read loop (`trForRead >= capForRead`), and a per-PID crash/exit catcher constructor in `codegen/llvm/gcsrc/gcshim.c`.

No changes needed to the resumer-side "repoint at fiber's own stack" half of the scheme (`gcSetStackbottom`/`gcSetRStackbottom`) — that half was already correct; only the "restore afterward" half had the gap.

## Side effects discovered

None beyond the bug itself. The fix also slightly simplifies the codebase: four separate callee-side restore sites collapse into two resumer-side ones, and the `emit_http.go`/`runtime_fetch.go` call sites no longer need their own `isGCMode()`-conditional restore plumbing threaded through `fmt.Sprintf` args.

## Verification

- `go build -o klainmain .`, `go vet ./...`, `go test ./...` — clean, no regressions.
- `go test ./tests/ -run TestE2EHTTPListenClusteringGCModeMultipleWorkerPIDs -count=300 -timeout 600s` — **300/300 clean**, zero hangs, zero resets, zero timeouts (previously failing roughly 1 in 40–150 iterations per ADR-00099). Re-ran at `-count=100` again after removing the TEMP DEBUG instrumentation to confirm its removal didn't mask anything — still 100/100 clean.
- `go test ./tests/ -run 'TestE2E.*GCMode' -count=5` — every existing GC-mode test (including the non-clustering concurrent-churn/correctness/bounds-memory tests, and the async-`await fetch` fiber-yield paths exercised indirectly through `runtime_fetch.go`'s modified restore sites) still passes, confirming the callee-side restore removal didn't regress the ordinary (non-clustering) fiber-yield case.
- Confirmed the debug `abort()` assertion (present for the entire 300-iteration verification batch before its removal) never fired — corroborating that the fix addresses the corruption at its actual source rather than merely narrowing the window.

## Status

TDD-00025 is now fully **Implemented**: both `manual` and `-mm=gc` clustering are production-quality. `docs/status/HTTP-SERVER.md`'s "not recommended for production use" caveat for `-mm=gc` clustering is removed.
