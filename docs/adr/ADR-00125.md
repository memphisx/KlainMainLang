# ADR-00125: WebSocket Stage 0 — shared frame codec + SHA-1

- **Relations**: Implements TDD-00039 (Stage 0 only — Stages 1-3 remain)
- **Date**: 2026-08-08

## Context

[TDD-00039](../tdd/TDD-00039.md) scoped `WebSocket` support (server-side `http.listen` upgrade handling and client-side `new WebSocket(url)`) in four stages. Stage 0 is the foundational, no-user-visible-feature layer both directions depend on: a SHA-1 implementation (needed for the handshake's `Sec-WebSocket-Accept`, RFC 6455 §1.3) and a shared RFC 6455 frame codec (masking, all three payload-length forms). This ADR covers that Stage 0 slice only — no AST/parser/emitter dispatch changes, matching the TDD's own staging.

## Investigation

Confirmed before implementing (see TDD-00039's own Context section for the fuller version): no hash of any kind exists anywhere in this codebase (`crypto.subtle.digest` fully unimplemented), and algorithmic runtime helpers in this codebase are hand-written LLVM IR text (`runtime_encoding.go`'s base64/hex), not embedded C — SHA-1 and the frame codec follow that same convention.

Three real bugs were found and fixed during implementation, all via the known-answer test written for this stage (there is no other way to exercise these helpers yet — no AST hook exists):

1. **SSA dominance violation in `ensureWSFrameEncode`.** The RFC 6455 §5.2 length-class branch (small/mid/large) needs to run twice — once before `malloc` to size the header, once after to write the extended-length bytes (which can't happen until the buffer exists). The first version reused the first branch's `%small`/`%mid` condition registers for the second branch. This is invalid: there is a graph-structural path (`entry -> lenSmall -> lenmerge -> checkMid2`) that never passes through `checkMid` (where `%mid` is defined) at all, even though that path is dynamically unreachable (correlated with `%small` being true). LLVM's dominance analysis is a pure CFG-graph property, not a value-correlation analysis, so this is genuinely invalid SSA — confirmed the hard way as a segfault (a garbage/undefined register value along that structurally-valid-but-dynamically-dead path) in the >125-byte unmasked frame test case, which is the one test case that actually exercises the second branch. Fixed by re-deriving the second branch's condition from `%extbytes` (the `phi` defined at the merge point itself, which trivially dominates everything downstream of it) instead of reusing the stale `%small`/`%mid`.
2. **Wrong shift widths in the new `bigEndianLoad`/`bigEndianStore` helpers.** Both took the shift amount from the LLVM *type's* bit width (`i64` → 64) rather than the *field's* bit width (`nbytes*8`). These only coincide when the field being packed/unpacked spans the whole register (true for SHA-1's 4-byte/`i32` word loads, 8-byte/`i64` length trailer, and the frame codec's 4-byte/`i32` mask key and 8-byte/`i64` "large" length form) — but the frame codec's 2-byte "mid" extended-length field is carried in an `i64` register, so `nbytes*8` (16) and the type's width (64) diverge. The bug produced shifts of 56/48 instead of the correct 8/0, extracting entirely the wrong bits — confirmed as the mid-length test case's header bytes coming back `82 7e 00 00` instead of `82 7e 00 c8` (200 encoded as zero). Fixed by deriving `bits` from `nbytes*8` in both helpers.
3. **Missing NUL terminator on the test harness's own `%02x` format string**, and a strlen-unsafe call to `__kml_btoa` (base64) on a raw, non-NUL-terminated 20-byte SHA-1 digest — both confined to `runtime_websocket_test.go` itself, not the runtime helpers under test. The first produced visibly garbled hex output (reading adjacent global constants as format-string continuation); the second is a real, called-out limitation of reusing a strlen-based `__kml_btoa` for binary data (safe here only because this specific digest is independently confirmed to contain no zero byte, and the test buffer explicitly zero-terminates one byte past it) — noted in-line as a real gap Stage 1's actual handshake implementation will need to address with a length-aware base64 encode, not silently relied on going forward.

## Decision

Implemented exactly per TDD-00039's Design section: `__kml_ws_sha1(ptr data, i64 len, ptr out)` (standard FIPS 180-4 padding + a phi-based per-block loop; both the 16-79 message-schedule extension and the 80-round compression are fully unrolled at Go-generation time as straight-line SSA, using `llvm.fshl.i32` for every rotate — no alloca-based mutable state needed anywhere in the algorithm), `__kml_ws_mask_apply(ptr data, i64 len, i32 maskkey)` (one XOR loop, used both to mask and unmask since XOR is its own inverse), and `__kml_ws_frame_encode`/`__kml_ws_frame_decode` (all three RFC 6455 §5.2 length forms, FIN/RSV validated on decode, no fragmentation support — matching the TDD's documented V1 scope cut).

Added two small generic helpers (`bigEndianLoad`/`bigEndianStore`) used by both SHA-1 and the frame codec, rather than writing the big-endian byte-packing/unpacking logic four separate times.

## Implementation notes

- `codegen/llvm/runtime_websocket.go` (new): all five `ensureWS*` functions plus the two `bigEndian*` helpers.
- `codegen/llvm/emitter.go`: five new idempotency-guard fields (`usedWSFshl32`, `usedWSSHA1`, `usedWSMaskApply`, `usedWSFrameEncode`, `usedWSFrameDecode`), following the existing `usedX bool` convention.
- `codegen/llvm/runtime_websocket_test.go` (new): the first test file in the `codegen/llvm` package. Necessary because these helpers have no AST/parser hook yet — every other `tests/*_test.go` harness compiles real TypeScript source through the full pipeline, which doesn't reach code with no syntax to trigger it. `buildAndRunIR` assembles an `Emitter`'s `e.globals` (populated by calling the `ensureWS*` methods directly) with a hand-written `main` IR string, compiles via `clang`, and runs the result — the same "Go-level unit test computing a known-answer digest and a known-answer frame round-trip" TDD-00039 itself called for.
- `__kml_ws_frame_decode`'s `status` field distinguishes incomplete (0, not enough bytes buffered — the caller's scan just waits for more, same shape `EventSource`'s own record scan uses) from a structurally-parsed-but-protocol-invalid frame (2, `FIN=0` or a nonzero RSV bit — still fully parsed so the caller can cleanly close rather than spin) from success (1).

## Side effects discovered

None beyond the three bugs above, all fixed within this same change (none left open). The frame codec and SHA-1 are otherwise unused until Stages 1/3 wire them into `http.listen`/`new WebSocket` — no behavior change to any existing, shipped feature.
