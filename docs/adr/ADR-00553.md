# ADR-00553: DataView getFloat16/setFloat16

- **Relations**: Extends ADR-00294
- **Date**: 2026-09-01

## Context

`DataView` supported every accessor kind except `getFloat16`/`setFloat16`
(half-precision, standardized in ES2024 and shipped by Node). This was the
DataView row's only caveat on the binary-data status page.

## Investigation

`emit_dataview.go` drives every accessor from `dataViewAccessKinds` (width,
signed, float, bigint) plus width-branched conversion code. Float16 is just a
width-2 float: LLVM's native `half` type converts to/from `double` via
`fpext`/`fptrunc`, and the existing `llvm.bswap.i16` handles the endianness.

## Decision

Add `"Float16": {2, true, true, false}` to `dataViewAccessKinds`. In
`emitDataViewGet`, a width-2 float bit-casts the loaded `i16` to `half` and
`fpext`s to `double`. In `emitDataViewSet`, a width-2 float `fptrunc`s the
`double` to `half` and bit-casts to `i16`. The shared bounds-check, endianness
swap, and type inference (`dataViewMethodKind` validates against the same map;
`inferExprType` returns `number` for any float kind) needed no changes.

## Implementation notes

- Only the two width-branch conversions were extended; everything else is
  shared with Float32/Float64.
- `half` lowers to compiler-rt soft-float conversions where the target lacks
  native FP16, which is transparent to the generated IR.

## Side effects discovered

None.

## Verification

`TestE2EDataViewFloat16` round-trips `1.5`, `3.14` (→ `3.140625` at float16
precision, matching Node), and `-0.5` with big- and little-endian flags. Built
and verified on Mac (Apple Silicon).
