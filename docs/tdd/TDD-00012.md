# TDD-00012: Computed property keys `{ [expr]: value }`

- **Status**: Implemented
- **Date**: 2026-07-28

## Context

STATUS.md lists computed property keys as the sole entry in "High priority / low complexity," with a one-line roadmap note: "Dynamic key; needs hash map backing." Picking this up as the next feature after classes (Stage 1, [ADR-00063](../adr/ADR-00063.md)) surfaced more design surface than the one-liner suggests, so it gets scoped here before implementation starts.

Every object literal today compiles to a fixed-shape LLVM struct: `parseObjectLiteral` (`parser/parser.go:1620`) only accepts an `IDENT` as a property key, `ast.ObjectProperty.Key` is a plain Go `string`, and every read/write site (`Type.FieldIndex`, `emitMember`, `emitObjectLiteral`, `emitAssign`'s field-assignment branch) resolves a field name to a fixed `getelementptr` index known at KML-compile-time. A key that's only known at runtime has no GEP index to resolve to — this is a hard, by-design wall, not a partial implementation (STATUS.md: "this compiler's objects are fixed-shape heap structs, not a dynamic property bag").

## Design

### The reuse insight

`Map<K,V>` (`codegen/llvm/emit_collections.go`, runtime IR in `codegen/llvm/runtime.go:1767+`) already exists as a **string-keyed, growable, linear-scan structure** — not a hash map (no hashing/buckets anywhere; `__kml_map_str_find` is an O(n) `strcmp` scan over a flat `keys` array), but functionally exactly what an object with runtime-computed keys needs: `__kml_map_str_create/find/get/set/has/delete/keys/vals`, with values uniformly boxed as `i64` (`valueToMapVal`/`mapValFromI64`, `emit_collections.go:364-410`, already generic over the real value type at the Go-codegen call site).

A computed-key object literal is, structurally, exactly a `Map<string, V>`. The only genuinely new thing is `.field` / `[expr]` dot-and-bracket-notation *sugar* around the existing `.get()`/`.set()` calls — real JS `Map` doesn't support that syntax, but nothing stops this compiler's own object-literal desugaring from routing through the same runtime. This avoids inventing new runtime IR entirely: `emitMapCall(ty, mapPtr, "get"/"set", []ast.Expression{...}, pos)` already takes AST expression nodes (not pre-evaluated `Value`s) as its key/value arguments, so both construction (`{ [k]: v }` → repeated `.set()` calls) and access (`obj.x`, `obj[k]` → `.get()`/`.set()`) can call it directly, synthesizing an `ast.NewStringLiteral(name, pos)` node for a static key exactly the way a real `"name"` string literal would parse.

### Value type inference

There is no single, always-correct `V` for a literal whose properties can have arbitrary, independently-typed values (real TS types this as an index signature, `{ [key: string]: T }`, which itself assumes one `T`). Rather than build a new "unify types across all properties" algorithm, this reuses the exact convention `inferArrayType` (`emit_exprs.go:1196`) already uses for array literals: infer from the **first property's value only**, and `e.coerce` every subsequent property's value to that same type. This is a known, already-accepted simplification elsewhere in the codebase (arrays don't cross-check every element's type either) — not a new gap.

### Representation: a new `Type.IsDynamicObject` flag on top of `IsMap`

A computed-key literal evaluates to `Type{IR:"ptr", IsMap:true, IsDynamicObject:true, MapKey:&TypePtr, MapVal:&V}` — literally a `Map<string,V>` value, with `IsDynamicObject` as an additional marker that gates the new dot/bracket sugar at every read/write site. Plain `Map<K,V>` variables (`IsMap` but not `IsDynamicObject`) are completely unaffected — the sugar is opt-in per-flag, not a general change to how `IsMap` values behave.

A useful side effect of this representation choice: since the value is a genuine `Map`, `.get()`/`.set()`/`.has()`/`.delete()`/`.keys()`/`.values()`/`.entries()`/`.forEach()` all work on it for free, with zero extra code — a dynamic object and a `Map<string, V>` are the same runtime thing, accessible through either API.

### Static + computed keys mixed in one literal

`{ x: 1, [k]: 2 }` is supported: once *any* property in a literal has a computed key, the entire literal is treated as a dynamic object, and static keys just become interned string constants inserted into the same underlying map via the same `.set()` call path. There is no partial/hybrid representation (part fixed-struct, part map) — that would double the number of codegen paths needing to handle "this object" for comparatively little benefit, since real programs needing a computed key are already reaching for a dictionary-shaped value.

### Explicitly out of scope for V1

- **`...spread` combined with a computed key in the same literal** (`{ ...obj, [k]: v }`). Supporting it means walking the spread source's static field list (already known at compile time) and re-inserting each as a `.set()` call, plus deciding merge/override order against computed keys — doable, but adds real scope for a case that's rare in the wild. Rejected with a clear compile-time error in V1; spread-only and computed-only literals both work standalone.
- **Index-signature type annotations** (`interface Foo { [key: string]: T }`, or the same shape in a `type` alias). This TDD only covers the object-literal *expression* form producing an inferred dynamic-object value from a `const`/`let` — not a new declared-type syntax. A dynamic object can't be used as a typed parameter/return/field today for that reason (same constraint arrays/objects already have: you can't declare `let x: number[]` as a target type distinct from what the initializer infers — wait, arrays *can* be annotated; dynamic objects can't yet, since there's no annotation grammar for them). This is a real, separate feature if ever needed.
- **`JSON.stringify` of a dynamic object.** The existing stringify path iterates `Ty.Fields`, which a dynamic object doesn't have (it has `MapKey`/`MapVal` instead). Extending it means teaching JSON serialization about the Map runtime's `keys`/`vals` arrays — plausible, but deferred; `JSON.stringify` on a dynamic-object value fails cleanly rather than being silently wrong.

### `Object.keys` / `Object.values` / `Object.entries`

These need to work on a dynamic object for the feature to be useful at all (build a dict at runtime, then iterate it). `emitObjectKeys`/`emitObjectFieldNames`/`emitObjectValues`/`emitObjectEntries` (`codegen/llvm/emit_objects.go`) currently only handle `Ty.Fields`-based objects; each gets a new branch for `Ty.IsMap` with a string key, delegating to the Map runtime's own `mapKeysAndVals`/`emitMapEntries` helpers (`emit_collections.go:410,437`) instead of walking a field list. This incidentally also makes `Object.keys(someRealMap)` work for any string-keyed `Map<string,V>`, not just dynamic objects — a reasonable, low-risk side effect of the shared representation, not separately designed for.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `Map<K,V>` string-keyed runtime (`__kml_map_str_*`) | ✅ done | The entire backing store this feature reuses; no new runtime IR needed |
| `emitMapCall` accepting AST expression args directly | ✅ done | Lets construction/read/write reuse it verbatim instead of hand-rolling new call-emission code |
| Array-literal-style "infer from first element" convention | ✅ done (`inferArrayType`) | Reused as-is for the value type `V`, rather than inventing a new inference rule |
| Parser support for `[expr]:` inside an object literal | ❌ not started | `parseObjectLiteral` only accepts `IDENT` keys today; needs a new `LBRACKET` branch |
| `ast.ObjectProperty` carrying an optional key expression | ❌ not started | Currently `Key string` only; needs a `KeyExpr Expression` field |
| `Type.IsDynamicObject` flag + dispatch at `emitMember`/`emitIndex`/`emitAssign` | ❌ not started | The core of this feature |
| `Object.keys`/`values`/`entries` support for `IsMap` values | ❌ not started | Needed for the feature to be usable, not just constructible |

## Open questions

- Whether a future index-signature type-annotation syntax (`{ [key: string]: T }` in `interface`/`type`) should reuse this same `IsDynamicObject` representation when it's eventually built, or whether it turns out to need something different once declared-type interaction (assigning a *fixed-shape* object literal to an index-signature-typed variable, or vice versa) is actually scoped. Not decided — flagged for whoever picks that up next.
- Whether `Object.keys`/`values`/`entries` gaining `IsMap` support should extend to non-string-keyed `Map<number,V>` too, or stay string-key-only (matching real `Object.keys`, which only ever produces string keys). Leaning toward string-key-only, since a number-keyed map doesn't correspond to anything in real `Object.*` semantics — not decided until implementation hits the question directly.
