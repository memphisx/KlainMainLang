# ADR-01965: A function expression's return type is deferred past the binding it reads

- **Relations**: Implements TDD-00230 (P2.3, P3.3); follows [ADR-01963](ADR-01963.md)
- **Date**: 2026-10-29

## Context

`const o = { m() { return g(); }, n: function () { return o.m(); } }` is valid TypeScript: tsc types `n` as `() => Error`. tsc resolves a signature's return type when something asks for it, so typing `o` never reads `n`'s body. The checker computed every function expression's return type while typing the expression. Inside `o`'s initializer, `o.m()` met `o` still being typed, so `n`, the object literal and `o` were all left unanswered.

The shadow report's E2E corpus had no way to name the program a disagreement came from: the test suite compiles from temporary directories it deletes.

## Decision

- A Function type's result is read through `Type.Ret()`, which can compute a deferred result on first read.
- A function expression or arrow with no return annotation, not async and not a generator, whose return type is left unanswered after its typing met a query still in progress, gets a fresh, non-interned signature. Its parameters are typed as usual. Its result is computed on the first read that can answer it; a read inside the same cycle leaves it deferred.
- With `KML_SHADOW_KEEP=<dir>` set and no `KML_SHADOW_UNIT`, a compile that records a disagreement copies its entry file into the directory, named by its content hash, and labels its disagreements with that copy.

## Consequences

- `o` in the example has its object type, and `o.n()` is `Error`.
- The shadow harness can run over `make test-par` and name each test program behind a disagreement.
