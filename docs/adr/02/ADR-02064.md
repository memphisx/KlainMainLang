# ADR-02064: Library code reads nothing of the program; a Request may wait

- **Date**: 2026-11-22

## Context

- `libdrift` found three library functions whose bodies differed between
  programs, so the library could not be compiled once:
  - `instanceof Promise` in library code compared the header against the
    program's own classes that extend Promise, inlined.
  - `accessorKeys`, the keys some accessor may define, caches the set on
    first use. When program code asked first, the cached set named
    `defineProperty` calls the program makes. The library then wrote such
    a field (`PerformanceEntry`'s `duration`) by name. `propAttrsUsed`
    answers false for library code, but the cache bypassed it.
- A Request's body may be a stream, read whole before sending (ADR-02050).
  Its collector awaits. In a JavaScript program whose only async-looking
  code is `new Request(url, init)`, the program was classified as never
  waiting, and the compile failed ("an await in a program classified as
  never waiting").

## Decision

- Library code asks a registered table for the program's Promise
  subclasses: `__kml_promise_class_is` (unitreg.c, rows of kind
  `unitKindPromiseClass` added by the program). Program code keeps the
  inline tests.
- `accessorKeys` is empty for program-independent code, whoever asked
  first.
- A `new Request(url, init)` with an init makes the program one that may
  wait, as `new Response(body)` did. Defining the Request collector also
  sets it, for an init that is dynamic.

## Consequences

- `libdrift` over the examples reports no differing library function, and
  the same IR on a repeated compile.
- `TestE2ERequestInitCoercionsJS` and
  `TestE2EFetchRequestInitMembersAndSignal` pass again.
- Verified on Node304 (Linux x86-64).
