# TDD-00231: Builtin modules written in TypeScript, Node's `stream` first

- **Status**: In Progress
- **Date**: 2026-09-25
- **Notes**: Stages 1–3 shipped ([ADR-01161](../adr/ADR-01161.md), [ADR-01162](../adr/ADR-01162.md)); stage 4 shipped: the fs streams over native primitives and a companion module for `fs` ([ADR-01166](../adr/ADR-01166.md)–[ADR-01169](../adr/ADR-01169.md)), and HTTP's request and response with `net`, `tls`, `http` and `https` ported from Node's own layering over native socket, TLS and parser primitives ([ADR-01170](../adr/ADR-01170.md), [ADR-01171](../adr/ADR-01171.md)). ## Context

[TDD-00230](TDD-00230.md) P3.1 declares each Node module for the checker.
Declaring `stream` as `@types/node` has it showed that this compiler's
Node streams are not Node's API. A tsc 7.0.2 `--strict` run over
`examples/streams` rejects most of them:

- `Readable<T>`, `Writable<T>` and `Transform<In, Out>` are generic
  (TS2315, TS2558). Node's classes are not; a chunk is `any`.
- The options-form `read: (self) => self.push(x)` takes the stream as a
  parameter. Node calls `read()` with the stream as `this`.
- `transform: (v, out) => out.enqueue(v)` is the WHATWG shape. Node's is
  `transform(chunk, encoding, callback)` with `this.push`.
- `readable.toWeb()` is an instance method; Node's is the static
  `Readable.toWeb(readable)` (TS2576).
- Chunks are typed by `<T>` and never converted. In Node a string pushed to
  a non-object-mode stream arrives as a `Buffer`, unless an encoding is
  set.

The runtime is written in codegen: `emit_node_stream.go`,
`emit_node_stream_class.go` and `runtime_node_stream.go`, about 3,000
lines. It wraps the WHATWG stream structs, which carry each chunk as two
typed words. A `class X extends Readable` is a synthetic root with a
hidden handle field (ADR-00393). The status page's Node-stream row carries
15 caveats, and `BACKLOG.md` another five.

Rewriting it in codegen would add more of the hand-written emitter code
TDD-00230 is removing. Node's own `stream` is JavaScript over
EventEmitter and `process.nextTick`. The project's direction is a builtin
library in TypeScript over a thin native layer (TDD-00230 P3.2, where a
`@lower` target may be "a function of the TypeScript builtin library").
`stream` is the first module to take that route.

## Design

### Embedded TypeScript modules

- `lib/node/*.ts` holds builtin modules written in TypeScript, embedded
  in the binary like `lib/*.d.ts`.
- The resolver treats an import of such a module (`stream`,
  `node:stream`, `stream/promises`) as an import of a real file. The
  embedded source is parsed, bound, checked and merged into the program
  like a user module, and only when the program imports it.
- A builtin module's diagnostics are compiler bugs, never user errors.
  The module is checked under the strict lane in the test suite
  (`lib/node` has its own test, which checks each file with the checker
  and runs it against Node).
- The declarations in `lib/node.d.ts` stay the checker's view for
  modules still in codegen. A module moved to TypeScript is its own
  declaration (its exported classes and functions), so the two cannot
  drift.
- A builtin module may import another builtin (`events`, `buffer`), and
  may call a native primitive through a `declare function` carrying
  `@lower` (TDD-00230 P3.2).

### `stream` in TypeScript

- Ported from Node's `lib/internal/streams/*.js` in behaviour, not line by
  line: `Readable`, `Writable`, `Duplex`, `Transform`, `PassThrough`,
  `pipeline`, `finished`, `Readable.from`, and `stream/promises`.
- The state machine follows Node's `ReadableState`/`WritableState`:
  - `highWaterMark` (16 KiB, or 16 objects in object mode);
  - `objectMode`;
  - `encoding` and `decodeStrings`;
  - flowing, paused and readable modes;
  - `'readable'`, `'data'`, `'end'`, `'finish'`, `'close'`, `'error'`
    and `'drain'`, with Node's `process.nextTick` ordering;
  - `destroy(err)` and `autoDestroy`.
- A chunk is `any`. A string written to a non-object-mode stream becomes a
  `Buffer`, unless an encoding is set.
- The options form (`new Readable({ read() { this.push(x) } })`) binds
  `this` as Node does. `Duplex` is a `Readable` subclass that carries
  the writable half as its own state, not by copying prototypes.
- A user `class X extends Readable { _read() {…} }` is ordinary
  inheritance, with no synthetic root.
- The WHATWG bridges (`Readable.toWeb`, `Readable.fromWeb`,
  `Writable.toWeb`) are static, as in Node.

### What the compiler must support first

The module is ordinary TypeScript, so each gap it hits is one user code
hits too. Each is a documented caveat today, fixed at its origin:

1. An object-literal method's `this` typed by a `this:` parameter in its
   contextual type, and `fn.call(thisArg, …)` binding it. `.call` discards
   `thisArg` today ([TDD-00137](TDD-00137.md)); the JSDoc `@this` row says
   "a `this` parameter type is not separately modeled".
2. `async *[Symbol.asyncIterator]()` class methods. These are deferred as
   clean rejections in [TDD-00063](TDD-00063.md).
3. Values of several representations meeting in `any`. The Language
   constructs caveat "an array-typed ternary … compile-time rejections"
   is one case: `typeof c === "string" ? Buffer.from(c) : c`. It is
   P3.3's `convert`, driven by the checker's type at the join.
4. A method replaced per instance (`this._read = opts.read`) stays out of
   scope. The module keeps the callback in a field.

### HTTP's streams

`http.IncomingMessage` and `ServerResponse` are Node streams whose native
side lives in the HTTP runtime. They move in a later stage, as
TypeScript subclasses of `Readable` and `Writable` over native read and
write primitives. Until then they keep their runtime, and typing them
from `stream`'s declarations is left open.

### Stages

1. The embedded-module loader, and the compiler gaps 1–3.
2. `Readable`, `Writable`, `PassThrough`, `pipeline`, `finished` and
   `Readable.from` in TypeScript. The examples and E2E tests are rewritten
   to Node's forms and checked against Node.
3. `Duplex`, `Transform` and the WHATWG bridges. The codegen stream files
   are deleted.
4. HTTP's request and response as stream subclasses.

## Open questions

- **Compile time.** Each program importing `stream` compiles the module.
  It is measured in stage 2. If it matters, a precompiled object is an
  option, since nothing in the module depends on the program.
- **Where the object-mode `highWaterMark` counts.** It counts objects in
  Node. Buffer chunks count bytes. Both come from Node's source and need
  no decision, but the byte count needs `Buffer.byteLength` for strings.
