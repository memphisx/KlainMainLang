# ADR-01488: An uninitialized typed local holds undefined

- **Relations**: Extends ADR-01482
- **Date**: 2026-10-09

## Context

BACKLOG 59: `let n: number;` read before any assignment (on a path the
definite-assignment check does not follow, or from a closure) read `0`,
and a `string` read `null`. Node reads `undefined` for both.

## Decision

- A local `let`/`var` declared with a number, boolean or string type and
  no initializer is stored as `T | undefined`, the representation that
  type already has. It starts undefined, and a read after an assignment
  is the assigned value.
- A module global gets the same `T | undefined` storage at registration
  when it has no initializer or one that may be undefined (`const c:
  number = a[9]`), and its declaration stores into that
  (`globalUndefinedStorage`).
- A read the binder proves definitely assigned (every path stored a
  value first, in the declaring function: the analysis behind TS2454,
  `DefinitelyAssigned`) reads the stored value as `T`, as the checker
  types it. A read from a closure may run before any store and keeps
  `T | undefined`. (The shadow report's largest bucket was these reads,
  typed `T | undefined` by codegen and `T` by the checker.) Only a plain
  `x = value` counts: a destructuring target past its source's end
  (`[c, d] = [5]`) is undefined though TypeScript types it `T`.
- A destructuring assignment into such a slot stores its `{ i1, T }`
  storage (test-par caught a bare `T` stored there, invalid IR), and an
  element past the source's end stores undefined.
- BACKLOG 59 and 64 are deleted.
