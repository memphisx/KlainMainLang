# ADR-00580: process.emitWarning options-object form

- **Relations**: Extends [ADR-00395](ADR-00395.md), [ADR-00401](ADR-00401.md)
- **Date**: 2026-09-01

## Context

`process.emitWarning(message, type?)` supported only a string `type` second
argument. Node also accepts an options object `{ type, code, detail }`, which
changes the printed line (a `[code]` tag) and appends a `detail` line.

## Decision

Accept an object-literal second argument with `type`/`code`/`detail` string
fields (any unknown key is a clean rejection). The emitted stderr line becomes
`(node:<pid>) [<code>] <type>: <message>` — the `[code]` segment only when a
code is present — chosen at compile time from which fields the literal carries,
and a `<detail>` line follows when a detail is present. A plain string second
argument keeps its existing `type`-only meaning.

## Scope

Two residuals stay disclosed as the row's caveat: the one-shot
`--trace-warnings` hint line Node prints is omitted (it needs per-unique-warning
dedup state), and the `process.on('warning', …)` listener's `Error` still
carries only `name`/`message`, not `code`/`detail` — the error object's shape is
fixed (`{kind, message, name}`).

## Verification

New `TestE2EProcessEmitWarningOptions` (code+type+detail, code-only, type-only,
plain) with stderr compared byte-for-byte against real Node v26 (modulo the
trace-hint line Node adds and this omits). Built and verified on Mac (Apple
Silicon).
