# ADR-00277: `for await...of` over sync generators, `Map`/`Set`, and arrays of raw fetches

- **Relations**: Extends [ADR-00272](ADR-00272.md) (for-await over a sync array), [ADR-00270](ADR-00270.md) (Promise as a reusable value)
- **Date**: 2026-08-21

## Context

`for await...of` accepted an async generator, a `[Symbol.asyncIterator]()` class,
and a sync array — but a sync *generator*, a `Map`, a `Set`, and an array of raw
fetch `Promise<Response>` were all clean rejections. Real JS treats any sync
iterable in `for await` via CreateAsyncFromSyncIterator: each element is awaited
before binding. These were the documented caveats on the `for await...of` status
row; closing them was the goal.

## Investigation

- `emitForOf`'s `s.Await` block (`codegen/llvm/emit_stmts.go`) dispatched only
  async generators, `@@asyncIterator` classes, and arrays; everything else hit
  the shared rejection.
- The array path (`emitForAwaitOfArray`, `codegen/llvm/emit_generators.go`)
  awaited promise elements unconditionally through `emitAwaitTaskPromise` and
  explicitly rejected a `Promise<Response>` element (its value lives behind the
  fetch pending struct, not the task-promise slot).
- `emitAwait` (`codegen/llvm/emit_async.go`) already contained the exact
  raw-fetch drive needed per element (`__kml_await_fetch` +
  `buildResponseFromStatusBody`), inline in its `IsResponse` branch.
- The sync `for...of` Map/Set path materializes values via
  `mapOrSetValuesArray`; a `Map` iterates values, a `Set` its elements.

## Decision

Share one per-element await and reuse the existing loop shapes:

- **`emitAwaitFetchSlot`** — the raw-fetch drive factored out of `emitAwait`'s
  `IsResponse` branch (slot not freed; a fetch promise stays a reusable value
  per [TDD-00090](../tdd/TDD-00090.md)).
- **`emitAwaitPromiseElem`** — awaits an already-evaluated promise value:
  a raw fetch `Promise<Response>` element goes through `emitAwaitFetchSlot`,
  anything else through `emitAwaitTaskPromise` (which re-throws a rejection at
  the loop, stopping it — matching JS).
- **`emitForAwaitOfArrayCore`** — the array loop split from its
  `resolveArrayForHOF` front end so a prebuilt `(ptr, len)` pair can enter it;
  its per-element await now uses `emitAwaitPromiseElem`, and the raw-fetch
  rejection is deleted.
- **Map/Set in `for await`** — materialize values via `mapOrSetValuesArray`
  (named variable loads from its alloca, any other expression evaluates once),
  `extractvalue` the aggregate, and run `emitForAwaitOfArrayCore`.
- **`emitForAwaitOfSyncGenerator`** — `emitForOfGenerator`'s loop (repeated
  synchronous `.next()` against one instance) plus the per-element await before
  binding; dispatched when `for await`'s iterable is a non-async generator.

## Implementation notes

- `codegen/llvm/emit_async.go`: `emitAwaitFetchSlot`, `emitAwaitPromiseElem`;
  `emitAwait`'s `IsResponse` branch now delegates.
- `codegen/llvm/emit_generators.go`: `emitForAwaitOfArray` split into front end
  + `emitForAwaitOfArrayCore`; new `emitForAwaitOfSyncGenerator`.
- `codegen/llvm/emit_stmts.go`: `s.Await` dispatch gains the sync-generator and
  Map/Set branches; the rejection message lists the full accepted set.
- The awaited element's binding type follows the returned value (`Response` for
  a fetch element), while the alloca is declared from the static awaited type —
  both `ptr`-shaped for every promise element, so no IR mismatch arises.

## Side effects discovered

- A top-level `const` holding an object/closure-shaped value is not promoted to
  a module global ([TDD-00093](../tdd/TDD-00093.md)'s promotable-shape rule), so
  such an iterable declared at top level and consumed inside a function is still
  rejected — a pre-existing promotion-scope limit, unchanged here (see
  [ADR-00279](ADR-00279.md) for where it surfaced).
