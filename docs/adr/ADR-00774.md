# ADR-00774: Pool the whole `fs.promises` op table (TDD-00185 Stage 3)

- **Relations**: `Implements [TDD-00185](../tdd/TDD-00185.md)` (Stage 3); `Extends [ADR-00773](ADR-00773.md)` (the Stage 1-2 pool this generalizes)
- **Date**: 2026-09-08

## Context

[ADR-00773](ADR-00773.md) built the blocking-work thread pool and routed a
single op — `fs.promises.readFile` — through it end-to-end. Stage 3 extends that
to the rest of the async fs table so the whole `fs.promises` surface a
microservice actually awaits is non-blocking: `writeFile`, `appendFile`,
`unlink`, `mkdir`, `rmdir`, `rename`, `copyFile`, `readdir`.

## Investigation

The ops differ in two axes the Stage-2 single-op path didn't have to handle:

- **Arity** — 1 path arg (`unlink`/`mkdir`/`rmdir`/`readdir`) vs 2
  (`writeFile`/`appendFile`/`rename`/`copyFile`).
- **Result shape** — void (the mutators), a single pointer (`readFile`), or a
  `{ptr,len}` aggregate (`readdir` → `string[]`).

Each op already bottoms out in one stable throwing runtime helper (`emit_fs.go`:
`@__kml_fs_unlink`/`_mkdir`/`_rmdir`/`_rename`/`_readdir`, and `copyFile` as
`@__kml_fs_read_file_raw` + `@__kml_fs_write_file_bytes`), so the worker can call
the helper directly. The async table (`fsAsyncOps()`) already binds each op to
its *plain* form (fixed arity, no options object), so `mkdir({recursive})` /
`readdir({withFileTypes})` never reach this path.

One ABI trap, found the hard way: the Stage-2 thunk returned a 16-byte
`{ptr,ptr}` by value (in registers, agreed by both sides). Widening to three
result words (`{i64,i64,ptr}` = 24 bytes) made `readFile` return `null` then
segfault — a 24-byte struct is returned via the >16-byte sret rule under Clang's
C ABI, but hand-written IR lowers a bare aggregate return differently, so the C
caller and the IR thunk disagreed on where the value lived.

## Decision

- **One IR thunk per op**, table-driven (`poolThunks` in `threadpool.go`): the
  shared setjmp-guard scaffold wrapped around a per-op try body that calls the
  underlying `@__kml_fs_*` helper and leaves two result words set. The three
  words `(v0, v1, err)` are written through an **out-pointer**, not returned by
  value — sidestepping the sret mismatch entirely.
- **Generic C submit** `__kml_pool_submit(opid, promise, arg0, arg1)`
  (`klainpool.c`) replaces the readFile-specific entry; the worker's `run_item`
  switches on `opid` to the matching thunk, `arg1` NULL for a 1-arg op. Both args
  are `strdup`'d.
- **Two-word completion settle** `__kml_pool_settle(promise, v0, v1, state)`
  stores both promise value slots, so `readdir`'s `{ptr,len}` and `readFile`'s
  single pointer settle through one path (void ops store ignored zeros).
- **Lowering** (`emitFsPromisePooled`, `emit_fs_async.go`) covers every op in
  `fsPoolOpID`; a `writeFile`/`appendFile` whose data is an `ArrayBuffer`/
  `TypedArray` returns `pooled=false` and falls through to the inline
  byte-length path (unchanged), so binary async writes keep working.

**Deliberately left inline** (noted follow-ons, not this stage): the legacy
**callback** form (`fs.readFile(path, cb)`) — pooling it needs the KML closure
invoked from the completion drain, a different mechanism than settling a
Promise; and **binary-data** `writeFile`/`appendFile`, above.

## Consequences

The whole plain `fs.promises` table is non-blocking. Verified on macOS (arm64):
an end-to-end sweep (`mkdir`→`writeFile`→`appendFile`→`copyFile`→`rename`→
`readFile`×2→`readdir`→`unlink`×2→`rmdir`) round-trips, a pooled mutator rejects
with the Node error shape, and a `TypedArray` `writeFile` still writes via the
inline path — under both the default and `-mm=gc` allocators. Tests
`TestE2EFsPromisesPooledFullTable` / `…PooledMutatorRejection`. Stage 4 (real
streaming) remains.
