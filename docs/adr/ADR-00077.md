# ADR-00077: Coerce object literal fields against their declared type

- **Relations**: Implements [TDD-00007](../tdd/TDD-00007.md)
- **Date**: 2026-07-29

## Context

Picked up directly off `STATUS.md`'s "Next up — bugs found but not yet
fixed" list: an object literal's field values are never coerced against a
declared/expected type (an interface annotation, a function parameter type,
a return type, an array element type, or an outer literal's own field
type), only against the literal's own self-inferred type — a no-op by
construction. `TDD-00007` had already fully scoped this (root cause,
design, and all five call sites needing the fix) before any implementation
started; this ADR is that implementation, done in one pass covering every
call site the TDD identified, rather than landing the variable-declaration
case alone and extending incrementally (the TDD's own first "open
question").

Confirmed the exact repro from the TDD still reproduced before this fix,
unchanged from when it was found:

```ts
interface Point { x: number; y: number }
const p: Point = { x: 1, y: 40.6 };
console.log(p.y); // printed 4630910759336725709 — 40.6's raw float64 bits reinterpreted as i64
```

## Investigation

Read `emit_objects.go`'s `emitObjectLiteral` and confirmed the TDD's root-
cause diagnosis exactly: `storeField`'s `val = e.coerce(val, fieldTy)` was
already correct, but `fieldTy` came from `ty := e.inferObjectType(lit)` —
the literal's own self-inferred struct type — with no way for a caller to
say "actually, coerce against this declared type instead."

Traced all five call sites the TDD named and confirmed each currently
discards a declared type it already has in hand before evaluating the
object literal:
- `emitObjectVarDecl` (`emit_objects.go`): already has `ty` (the resolved
  declared type) in scope; its `*ast.ObjectLiteral` case called the
  hint-less `emitObjectLiteral(init)`.
- Named-function calls (`emit_call.go`'s `emitCall`): `paramTy` is already
  resolved per positional argument (the same data
  [ADR-00042](ADR-00042.md)'s parameter-typing fix reads) but was discarded
  before calling `e.emitExpr(arg)`.
- Closure calls (`emit_func.go`'s `emitClosureCallByPtr`): same shape,
  `ty.FuncParams[i]` was looked up only *after* the argument was already
  evaluated, too late to use as a hint.
- Return statements (`emit_stmts.go`'s `emitReturn`): `e.currentRetType` is
  already tracked through body emission; its generic (non-array, non-async)
  path called `e.emitExpr(r.Value)` with no reference to it until the
  `coerce` call one line later — by then the object literal had already
  been built.
- Array literal elements (`emit_arrays_core.go`): both
  `emitArrayVarDecl`'s literal-element loop and `emitSpreadArrayLit`'s
  static-element branch already have `elemTy` (the array's declared or
  inferred element type) in scope per element.

Confirmed directly, per the TDD's second open question, that **object
spread needs no separate fix**: `{ ...p, x: 5 }` copies each field straight
from `p`'s own already-built struct via a typed load (`f.Ty` comes from
`srcVal.Ty.VisibleFields()`, the source's real stored type) — spread was
never the corruption site, and once the *source* is correctly coerced at
its own construction point (this fix), a spread of it carries the correct
value forward automatically. Verified with `const q: Point = { ...p, x: 5
}` after `p`'s own `y: 40.6` field was fixed — `q.y` reads `40`, not a
corrupted value.

## Decision

Added `emitObjectLiteralWithHint(lit *ast.ObjectLiteral, hint *Type) (Value,
error)` (`emit_objects.go`) as the real implementation; the existing
`emitObjectLiteral(lit)` is now a one-line wrapper calling it with
`hint = nil`, so every caller not listed below is unaffected. When `hint`
is non-nil and `IsObject`, the literal is built against `hint`'s field
layout (types, struct size, GEP indices) instead of the literal's own
`inferObjectType` result — matching the exact "thread an expected-type hint
through" shape `resolveCallbackWithHints` and `emitJSONParseObject`'s
`targetTy` already establish elsewhere in this codebase, per the TDD's
design.

Added `emitExprWithObjectHint(expr ast.Expression, hint Type) (Value,
error)` as the one small piece of shared plumbing every call site uses:
evaluates `expr` normally, except when `expr` is itself an object literal
and `hint.IsObject`, in which case it calls `emitObjectLiteralWithHint`
instead of the plain `emitExpr`. Every one of the five call sites (plus two
adjacent ones found during implementation, see below) now goes through this
instead of a bare `e.emitExpr`.

**Nested object-literal-typed fields** (the TDD's one genuinely new piece of
plumbing) are handled inside `emitObjectLiteralWithHint` itself: each
property's field type is looked up from `ty.FieldIndex(prop.Key)` *before*
evaluating that property's value, then passed as the hint via
`emitExprWithObjectHint` — so a field whose own declared type is another
object type (`address: { ..., coords: Point }`) recurses correctly with no
per-level special-casing.

**Two additional call sites found and fixed in the same pass**, structurally
identical to argument #2 in the TDD's list but not separately enumerated
there: a parameter's **default-value expression**
(`function f(p: Point = { x: 1, y: 40.6 }) {}`) and a **rest parameter**'s
per-element evaluation (`emit_call.go`), both of which evaluate an
expression against an already-known parameter type the same way a regular
positional argument does.

Untyped literals (`const x = {...}`, no declared type anywhere) are
provably unaffected: with no hint, `emitObjectLiteralWithHint` behaves
exactly as `emitObjectLiteral` always did, and an object literal's own
self-inferred type can never itself disagree with its own values by
construction.

## Implementation notes

Files touched: `emit_objects.go` (the new hint-aware implementation +
`emitObjectVarDecl`'s call site), `emit_call.go` (three call sites: regular
positional arguments, default-value expressions, rest-parameter elements),
`emit_func.go` (`emitClosureCallByPtr`, restructured to resolve `paramTy`
before evaluating the argument instead of after), `emit_stmts.go`
(`emitReturn`'s generic non-array return path), `emit_arrays_core.go`
(`emitArrayVarDecl`'s literal-element loop and `emitSpreadArrayLit`'s
static-element branch).

`resolveArrayDataPtr`'s own `*ast.ArrayLiteral` case (used for array
destructuring, e.g. `const [a, b] = [{...}, {...}]`) was deliberately left
unchanged: its element type is entirely self-inferred from the literal
itself (`e.inferArrayType(src)`) with no separate declared type available
at that call site — the same "untyped, nothing to hint against" case as a
bare `const x = {...}`, not a gap in this fix's coverage.

## Side effects discovered

None found beyond what the Investigation section above already covers
(object spread's correctness was verified, not assumed, per the TDD's own
second open question).

## Verification

- Manually re-ran the TDD's exact repro (`Point { x, y: number }` with a
  float literal) and its stated reverse case (a JSDoc-`float64`-annotated
  field given an integer literal) — both now print the coerced value (`40`
  and `5` respectively) instead of the raw bit-reinterpreted garbage
  originally reported (`4630910759336725709` / `2.47033e-323`).
- Manually verified all five call sites plus the two additional ones found
  during implementation (function argument, closure argument, default
  parameter value, return statement, array literal element, nested object
  literal field, object spread of an already-fixed source) via one-off
  `.ts` repros before writing the permanent test suite.
- `tests/objects_test.go`: 10 new E2E tests — one per call site above, plus
  a spread-preserves-the-fix regression test and an explicit "untyped
  literal still infers its own type unchanged" test guarding against a
  regression in the no-hint path.
- `go build -o klainmain . && go vet ./... && go test ./...` (all green)
  and `make examples` (65/65) both passed on the final tree.
