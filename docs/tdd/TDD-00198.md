# TDD-00198: the server `'connection'` event

- **Status**: Implemented
- **Date**: 2026-09-10

## Context

`http.Server` fired `'request'`/`'listening'`/`'upgrade'`/`'close'` but not
`'connection'` — the event Node emits once per accepted TCP connection, handed
the raw socket, before any HTTP parsing. It backs connection counting/logging,
per-socket timeouts, and raw-socket inspection.

## Design

The accept() call itself lives in the hand-written reactor IR
(`runtime_http.go`), which can't readily invoke a user closure. But every
accepted connection runs a **codegen-emitted dispatcher fiber**
(`buildHTTPDispatcher`), and that fiber's entry — the code before the
`readLoopL` read loop — runs exactly once per connection (keep-alive reuse loops
back to `readLoopL`, never re-entering the entry). So firing `'connection'` at
dispatcher entry is once-per-connection, in emitted IR where a closure call is
trivial, observably a hair after accept (before the first byte is read) — close
enough to Node's timing to be faithful.

- A per-server global `@__kml_listen_connection_handler<sfx>` holds the handler
  closure (`.on('connection', cb)` stores into it, routed by the server's
  dispatcher suffix). Declared unconditionally (primary via `ensureHTTPRuntime`,
  additional via `ensureExtraWSUpGlobals`) so the entry hook can read it with no
  whole-program pre-scan — the guard is one load + null-check per connection.
- The entry hook (`emitHTTPConnectionEvent`): load the handler; if null, branch
  straight to `readLoopL`; else read this connection's fd from the conn array
  (the same read `readLoopL` does — `@__kml_current_conn_idx` is already set by
  the scheduler at fiber resume), build a `net.Socket` over it (TLS ssl in
  field 5 for an HTTPS server, exactly as the `'upgrade'` path does), invoke the
  one-parameter handler `(socket)`, then fall into `readLoopL`.

The HTTP parser then owns the byte stream, so the socket is a `write`/`destroy`/
inspect **handle**, not a raw data source: its own `'data'`/`'close'` listeners
are **not** driven (a V1 limitation — driving them would need the connection to
detach from HTTP parsing, the same machinery the `'upgrade'` raw loop uses).
Address fields (`remoteAddress`/`remotePort`) are likewise absent (the accept is
`accept(fd, null, null)`). Counting, logging, `write`, and `destroy` all work.

### Alternatives rejected

- *Fire from the reactor at accept().* The faithful timing, but the reactor is
  hand-written IR with no closure-call path; the dispatcher-entry hook is a hair
  later and lands in emitted IR where the call is one line.
- *Pre-scan gate (like `'upgrade'`).* Unnecessary here — the hook is trivial, so
  unconditional emission with a null-check costs less than the pre-scan does.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Per-connection dispatcher fiber with a stable entry | ✅ Built | `buildHTTPDispatcher` — the once-per-connection seam |
| `net.Socket` build over a fd (TLS-aware) | ✅ Built | Reused verbatim from the `'upgrade'` path ([TDD-00158](TDD-00158.md)) |
| Per-server suffixed handler globals | ✅ Built | `ensureExtraWSUpGlobals` (extended with the connection global) |
| Socket lifecycle listeners on the connection socket | ⚠️ Not driven | Documented; needs the connection to detach from HTTP parsing |

## Open questions

None. `remoteAddress`/`remotePort`, socket `'data'`/`'close'` on the
connection-event socket, and the remaining server events
(`'error'`/`'clientError'`) stay in the backlog.
