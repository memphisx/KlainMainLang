# ADR-01303: `worker_threads` as Node's lib/internal/worker, with a worker as an isolate

- **Relations**: `Implements part of TDD-00230` (P3.1), `Supersedes ADR-00305`, `Supersedes ADR-00306`, `Supersedes ADR-00309`, `Supersedes ADR-00431`, `Extends ADR-01302`
- **Date**: 2026-09-30

## Context

`worker_threads`, `MessageChannel`/`MessagePort` and `BroadcastChannel` were
compiled directly (`emit_worker.go`, `emit_chan.go`, `runtime_worker.go`,
`runtime_chan.go`). Their channels were typed statically: one message type per
direction, fixed by an annotated `parentPort.on('message', (m: T) => …)`, a
`new MessageChannel<T>()` type argument, or a BroadcastChannel name's first
use. A worker module could not be imported, could not start workers, and its
named functions could not read its own top-level bindings. Every builtin
module's state was shared between threads, where each Node worker is an
isolate that evaluates its modules afresh. A port was shared rather than
transferred, a BroadcastChannel name had to be a literal, and listeners were
limited to one arrow literal per event.

## Investigation

Node v24's lib/internal/worker.js starts a thread with its own isolate and
loop; the Worker object talks to it over two MessagePort pairs (public and
internal, `kPort`/`kPublicPort`). lib/internal/worker/io.js makes MessagePort
a NodeEventTarget: `on('message')` starts it, a started port holds the loop
while referenced, `close()` closes both ends and each emits `'close'`. A
message is serialized (V8's ValueSerializer) and deserialized on the other
side; a SharedArrayBuffer keeps its memory, a MessagePort in the transfer list
moves. An uncaught error in a worker reaches the parent's `'error'`, then
`'exit'` with code 1; without an `'error'` listener it is the parent's
uncaught exception. A BroadcastChannel is referenced from construction until
`close()` (a program with an open one never exits; checked against Node
24.19).

Here a worker's code is compiled into the program, so the isolate is made at
compile time: each worker module's entry function evaluates, on the worker's
thread, the executable statements of every builtin module and of the user
modules it imports, then its own; program state is `thread_local` when the
program has workers. Emitting the same statements into two functions works
because codegen keys nothing it emits on statement identity across
functions.

## Decision

**Isolates.** The resolver records each file's user import edges and gives
every `WorkerModule` `Deps`: the executable top-level statements of all
builtin modules and of the user modules the worker file reaches, in
dependency order. `emitWorkerModules` emits `Deps` then `Body` into the
entry. With workers, module globals, class statics, decorator slots, the
Symbol registry, prototype-class globals, the process exit code and the
process event hooks are `thread_local` (`Emitter.isolateTLS`). klainpool.c's
TCP, process and HTTP-parser handle tables are per thread. Under `-mm=gc`
each thread's TLS block is a root: gcshim.c now registers it on macOS too
(the image's TLV key and `__thread_data`/`__thread_bss` span; on current
dyld the key is the descriptor word's low 32 bits).

**Natives** (klainpool.c, `@link pool`):
- MessagePort pairs in a process-wide table: `mportPair`, `mportStart`
  (deliver on this thread's loop as a completion), `mportStop`, `mportRef`,
  `mportPost` (queue a cloned value on the other end), `mportHas`/`mportTake`,
  `mportClose` (both ends deliver what is queued, then `'close'`). A
  referenced, started, open port counts in its loop's in-flight work.
- Workers: the entry of each worker module is registered by path at
  start-up (`__kml_worker_register`, emitted at the top of `main`);
  `workerSpawn(path, port, internalPort, data, onEvent)` starts a detached
  thread (4 MB stack, as Node's) running the emitted `@__kml_worker_thread`;
  the parent hears `onEvent(0 online | 1 exit, code)`; `workerRef`,
  `workerTerminate`, `workerExited`, `workerSelf`, `workerSelfData`,
  `workerSelfFilename`, `workerThreadId`.
- BroadcastChannel's process-wide registry: `bcJoin`, `bcLeave`, `bcCount`,
  `bcMember`.
- The pool's wakeup descriptor is always watched, so another thread can wake
  a loop with nothing in flight.

**Runtime** (runtime_worker.go): the thread main (GC registration, signals
blocked, entry, loop, `__kml_worker_leave(code)`); `@__kml_thread_exit`,
which `process.exit`, an uncaught error and an unhandled rejection take when
the program has workers — on a worker it ends only that thread (parking
first on a coroutine stack, as before); `@__kml_worker_uncaught(tag,
payload)`, which hands the error to the worker's process hook 3; the loop
hook that ends a terminated worker at its next turn.

**Module** (`lib/node/worker_threads.ts`, a global module): `Worker`
(`'online'`, `'message'`, `'error'`, `'exit'`, `postMessage`, `terminate()`
returning the exit code, `ref`/`unref`, `threadId`), `MessageChannel`,
`MessagePort` (EventEmitter plus the EventTarget surface, `onmessage`,
`start`, `close`, `ref`/`unref`/`hasRef`), `BroadcastChannel`,
`receiveMessageOnPort`, `markAsUntransferable`, `isMarkedAsUntransferable`,
`markAsUncloneable`, `isMainThread`, `threadId`, `parentPort` (`MessagePort |
null`), `workerData`, `setEnvironmentData`/`getEnvironmentData` (copied to a
worker at start), `SHARE_ENV`, `resourceLimits`. Messages are cloned by the
structured clone rules, with a SharedArrayBuffer kept and each transferred port replaced by a token the receiver turns into a port
of its own; a port not in the transfer list is a DataCloneError. The web's
`Worker` shape (`onmessage`, `onerror`) and a worker's `self`
(`self.onmessage`, `self.postMessage`) ride the same classes.

**Native callbacks drain the microtasks** (klainpool.c `kml_make_callback`):
each callback from the loop runs, then the tick queue and promise jobs, before
the next — Node's MakeCallback. Before, the whole dispatch ran first: a fork
channel's `'disconnect'` (a nextTick after its EOF) came after the child's
`'exit'` under load, so `cluster.workers` still held the dead worker at
`'exit'`.

**Checking.** The binder binds a worker module's body as a function scope
under the module, and the checker checks it: worker code gets tsc's
diagnostics (`'parentPort' is possibly 'null'`).

**Deleted**: `emit_chan.go`, `runtime_chan.go`, the typed-channel codegen in
`emit_worker.go`/`runtime_worker.go`, `NewWorkerExpression`,
`NewBroadcastChannelExpression`, `NewMessageChannelExpression` and their sema
builders, the `IsWorker`/`IsBroadcastChannel`/`IsMessageChannel`/
`IsMessagePort` types, the `worker_threads` virtual module, the loop's
channel hooks, the resolver's rejections of an imported worker module and of
nested workers, and the bare `onmessage =`/`postMessage()` worker globals
(`self.*` remains).

## Implementation notes

- `new Worker('./w.ts')`'s literal is rewritten by sema to the path the
  resolver resolved (relative to the file it is written in); the worker
  registry is keyed by it. The resolver only resolves literals the file's
  parse-time scan found at a `new Worker` site (`lookupTable.workerLits`).
- A worker module the program also imports is merged whole into the program
  body and its executable statements also form the worker's body.
- The Worker's own ports are unreferenced: the worker holds the parent's loop
  (in-flight count) until the parent hears its exit. What the worker posted
  before it ended is drained before `'exit'`.
- `parentPort` is `MessagePort | null`, as @types/node declares it.

## Side effects discovered

- Worker module bodies had never been bound or type-checked; they are now
  (see Decision). Examples and tests use `parentPort!` as tsc requires.
- The gc test helpers hand-listed their C units and missed the bigint and
  sync runtimes; `buildGCProgram` in `tests/compiler_test.go` is now the one
  gc link path.
- `(this as any).x = …` of a `readonly` field is rejected by codegen, where
  tsc accepts it; worked around in the module (a getter), left open.
- Typed arrays have no `.buffer`/`.byteOffset` (statically or through
  `any`), so a view over a SharedArrayBuffer is copied by the clone rather
  than re-viewed over the same memory.
- `String(fn)` renders `function () { [native code] }`, where Node renders
  the source, so a DataCloneError message for a function differs.

## Verification

- Worker, shared memory, module task, cluster and child_process suites pass;
  the gc worker tests pass on macOS (arm64) with the new TLS roots.
- Every `examples/workers` entry prints what Node 24.19 prints (compared
  directly), including exit behavior of the BroadcastChannel example.
- Rewritten tests assert Node's behavior: an imported worker module
  evaluates on both threads, nested workers, untyped messages, `parentPort`/
  `workerData` null on the main thread, DataCloneError for a function.
