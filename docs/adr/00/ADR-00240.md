# ADR-00240: Abort/timeout errors are DOMException; `instanceof DOMException` + `new DOMException`

- **Relations**: `Implements TDD-00081`; `Extends ADR-00238`, `ADR-00239`; builds on [ADR-00013](ADR-00013.md) (Error-kind enum, TDD-00013 Option A)
- **Date**: 2026-08-19

## Context

The fetch-cancellation work ([ADR-00237](ADR-00237.md)–[ADR-00239](ADR-00239.md))
threw its abort error as a base `Error` (kind 0) with the *name* `"AbortError"`.
That made `err.name === "AbortError"` work but `err instanceof DOMException`
impossible, and every cancellation — manual `abort()` and `AbortSignal.timeout`
alike — surfaced as `"AbortError"`, where WHATWG specifies a timeout aborts with
a `"TimeoutError"`. There was also no `new DOMException(...)` constructor.

## Decision

Add `DOMException` as an eighth entry in the fixed `errorKinds` enum
(emit_exceptions.go). Because the enum index is the runtime kind tag and
`emitErrorInstanceOf` already keys off it, `x instanceof DOMException` becomes
decidable for free (kind-tag equality), and since `"Error"` is the base every
kind unconditionally matches, `instanceof Error` also stays true — which is
exactly the modern WebIDL relationship (DOMException inherits from Error).

- **`new DOMException(message?, name?)`** — a dedicated parse body, since unlike
  the fixed-name kinds its `.name` is the *second argument* (default `"Error"`)
  and its default message is `""`, not the kind name. Carried on a new optional
  `Name` field of the existing `NewErrorExpression` AST node.
- **Abort/timeout errors** — the `__kml_await_fetch` abort path now stores the
  `DOMException` kind tag and picks the name/message from the signal's
  `deadlineNs`: non-zero (an `AbortSignal.timeout` signal) → `"TimeoutError"` /
  "The operation timed out"; zero (a manual `controller.abort()`) → `"AbortError"`
  / "The operation was aborted". The discriminator is exact because only
  `AbortSignal.timeout` ever sets `deadlineNs`, and such a signal can only abort
  via that deadline.

## Consequences

- `catch (e)` after a cancelled fetch: `e instanceof DOMException` and
  `e instanceof Error` both hold; `e.name` distinguishes timeout from abort.
- A real `TypeError`/`RangeError`/etc. is correctly *not* `instanceof
  DOMException` (distinct kind tags).
- Still caveated (kept honest on the status page): DOMException carries no legacy
  numeric `.code`, and a manual `controller.abort(reason)` with a custom reason
  still throws a synthesized `AbortError` DOMException rather than that reason
  value.

## Verification

`new DOMException("boom","NotFoundError")` → name/message correct, `instanceof`
both true; `new DOMException()` → name `"Error"`, empty message; `TypeError`
is not `instanceof DOMException`. A pre-aborted fetch throws an `AbortError`
DOMException (both `instanceof` true); `AbortSignal.timeout(0)` throws a
`TimeoutError` DOMException. `go build`/`go vet ./...` clean; the abort/error
suites and the `fetch-abort.ts` example pass (Apple Silicon, macOS).
