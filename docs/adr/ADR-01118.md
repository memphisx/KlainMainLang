# ADR-01118: Generic base classes in the checker

- **Relations**: `Implements TDD-00230` (Phase 2, P2.6); `Extends ADR-01113`
- **Date**: 2026-09-24

## Context

[ADR-01113](ADR-01113.md) gave the checker generic classes, but a class
whose `extends` clause has type arguments (`class Pair<T> extends
Box<T[]>`) stayed unanswered: `instanceOf` and `constructorType` refused
any class with `BaseTypeArgs`. A class without a constructor of its own
that extends a class with one was unanswered too. [TDD-00230](../tdd/TDD-00230.md)
P2.6 lists the generic base as open.

## Investigation

- **The parser** already keeps the `extends` clause's type arguments for
  any base (`parser/parser_classes.go`). The AST comment saying they exist
  only for `EventEmitter<T>` describes codegen's limit, not the parser's.
- **Codegen** rejects a generic `extends` of a user class (`emit_classes.go`,
  "only EventEmitter<T> currently supports generic extends"). So the
  checker's answer shows in unit tests only, until phase 3 moves the class
  deciders onto it.
- **tsc 5.6.3 `--strict`**, with `class Box<T> { v: T; constructor(v: T);
  get2(): T }`:
  - `new NumBox(1).v` is `number`, and `new NumBox(1)` is `NumBox`, for
    `class NumBox extends Box<number> {}`.
  - `new Pair([1]).v` is `number[]`, and `new Pair([1])` is `Pair<number>`,
    for `class Pair<T> extends Box<T[]> {}`.
  - A base's member annotation names the base's own declarations. With
    `class D<Item> extends Base<Item>`, `Base`'s field `x: Item` is the
    module's `interface Item`, not `D`'s parameter.
  - A base may name its own subclass (`class B0 { child?: D0 }`), and
    `d0.child` is `D0 | undefined`.
- **Two latent faults** in the checker, found while restructuring
  `instanceOf`:
  - `pushEnv` stacked type-parameter environments, so a base class's
    members saw the subclass's parameter names.
  - A class's base was typed before the class was interned. A base member
    naming the subclass therefore rebuilt the subclass from a half-filled
    base, and `d0.child` came out without `D0`'s inherited props (the
    subclass-naming case above answered `?`). A circular `extends` (`class
    A extends B`, `class B extends A`) would have recursed without end.

## Decision

- **The base's type arguments** are typed in the class's own
  type-parameter environment. The base instance is `instanceOf(base,
  args)`, and the subclass copies its props, as before.
- **A class without a constructor** inherits its base's constructor
  signature. The base signature's type parameters are replaced by the
  `extends` clause's arguments, and the signature is generic over the
  subclass's own type parameters, so `new Pair([1])` infers `T` from the
  inherited parameter.
- **`declEnv`**: a class, interface or alias declaration's members see its
  own type parameters only. The environment stack is replaced while the
  declaration is typed, and restored after. Overload signatures inside a
  class still stack on the class's environment.
- **The class is interned before its base is typed**, so a base member
  naming it gets the type being filled. If the base turns out not to be
  modelled, the interned entry is removed and the class is unanswered.
- **A circular `extends`** is unanswered. `classing` guards the base-instance
  chain and `ctorChain` the inherited-constructor chain. tsc rejects such
  a program.
- **The parser** now accepts a definite assignment assertion on a class
  field (`host!: string`), which tsc accepts. The `!` only waives the
  initialisation check this compiler does not perform, and it needs the
  `: T` annotation.

## Implementation notes

- `checker/symbols.go`:
  - `instanceOf`: interning first, `baseInstance`;
  - `constructorType`: the inherited constructor;
  - new `baseTypeArgs` and `declEnv`. `interfaceOf` and `aliasOf` use
    `declEnv`.
- `checker/types.go`: `nominalKey`.
- `checker/checker.go`: the `classing` and `ctorChain` guards.
- `parser/parser_classes.go`: `name!: T`.
- `examples/classes/classes.ts` and
  `tests/classes_test.go` (`TestE2EClassDefiniteAssignmentField`): a field
  set by a helper method called from the constructor.

## Side effects discovered

- `examples/classes/classes.ts` iterates a class whose only protocol is a
  sentinel `next(): T | null` (`for (const n of new Range(1, 6))`). This is
  a documented extension of this compiler; Node throws `Range is not a
  function or its return value is not iterable` on it. It is unrelated to
  this step.

## Verification

All on macOS arm64 (M4):

- `go test ./checker` (`TestGenericBase`), with each expectation checked
  against tsc 5.6.3 `--strict`:
  - a non-generic subclass of `Box<number>`: its fields, its methods and
    its inherited constructor;
  - `Pair<T> extends Box<T[]>` inferring `T` through the inherited
    constructor;
  - a subclass with its own constructor;
  - environment isolation;
  - a base naming its subclass;
  - circular and self `extends`.
- `go test ./tests -run TestE2EClassDefiniteAssignmentField`, and the
  example's new section against Node 24 (`thessaloniki.example 8080`).
- The parser corpus dump (59,519 files) is identical before and after, and
  the resolver corpus dump (107,567 runs) differs only in the edited
  example.
- Shadow report: unchanged at 472, since codegen rejects generic bases.
