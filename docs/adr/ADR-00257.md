# ADR-00257: Destructuring loop variable in `for await...of` (and over sync generators), plus tuple/object `yield`

- **Relations**: refines [ADR-00253](ADR-00253.md) (async generators / `for await`), [ADR-00192](ADR-00192.md) (for-of destructuring loop variable), [TDD-00085](../tdd/TDD-00085.md); reuses the `unpack*PatternInto` core from [ADR-00193](ADR-00193.md)/[TDD-00065](../tdd/TDD-00065.md)
- **Date**: 2026-08-20

## Context

`for await (const x of asyncGen())` bound only a single loop variable — a
destructuring pattern (`for await (const { x, y } of …)` / `const [a, b]`) was a
clean rejection. The array `for...of` path already unpacks a pattern element
through the shared `unpackObjectPatternInto` / `unpackTuplePatternInto` core, so
the async-generator loop was the odd one out.

Two adjacent gaps surfaced while wiring it:

- **The sync generator `for...of` loop** (`emitForOfGenerator`) had the *same*
  gap — it ignored `ArrayPattern`/`ObjectPattern` and defined only `s.VarName`,
  so `for (const [a, b] of gen())` failed with an "undefined variable 'a'" at
  codegen. A real bug, not a rejection.
- **`yield`/generator-`return`** emitted the argument with no type hint
  (`emitExpr`), so `yield [1, 2]` into a tuple-typed element slot built a bare
  array aggregate `{ ptr, i64 }` the `ptr`-typed slot could not hold — a clang
  type error. Any tuple-element generator (sync or async) miscompiled at the
  yield site, independent of the consumer.

## Decision

- **Both generator loops** (`emitForAwaitOfGenerator`, `emitForOfGenerator`):
  when the loop variable is a pattern, define no single binding; in the body,
  after loading the per-iteration `value`, unpack it through the same switch the
  array `for...of` uses — `ObjectPattern` → `unpackObjectPatternInto`,
  `ArrayPattern` over a tuple element → `unpackTuplePatternInto`. A generator's
  element type is never an array (array element types are rejected at
  registration), so a tuple is the only array-destructurable element shape; an
  `ArrayPattern` over a non-tuple element is a clean rejection.
- **`yield` and generator `return`** now emit their argument via
  `emitExprWithObjectHint(arg, elemTy)`, so a tuple/object literal builds the
  slot's shape directly. This fixes the tuple-element miscompile for both sync
  and async generators.

## Consequences

- `for await (const { x, y } of asyncGen())` and `const [a, b]` over a
  tuple-yielding async generator both work; the former `for await` destructuring
  caveat is removed.
- The same destructuring loop variable now works over a **sync** generator too
  (previously an "undefined variable" codegen error).
- Tuple- and object-element generators yield correctly (sync and async) — the
  silent tuple-yield miscompile is gone.
- Still out of scope (unchanged): a general `Symbol.asyncIterator` protocol
  ([TDD-00044](../tdd/TDD-00044.md)) — `for await` still consumes an
  async-generator instance only; a plain array or sync generator stays a clean
  rejection.
