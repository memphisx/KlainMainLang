# ADR-00091: `in` operator (`key in obj`)

- **Date**: 2026-08-03

## Context

`docs/status/README.md`'s roadmap flagged `in` as High priority/Low complexity — "object shapes are already fully structural/static (the same compile-time `FieldIndex` lookup `Object.hasOwn()` already uses), so this is mostly parser/precedence work, not new runtime machinery." Picked up as a fast follow-up after `os` (ADR-00090), explicitly chosen for its small footprint given limited remaining session budget.

## Investigation

Read `emit_objects.go`'s `emitHasOwnProperty` (backing `Object.hasOwn`/`.hasOwnProperty`) — confirmed it's exactly the compile-time `FieldIndex` lookup the roadmap description promised, and confirmed dynamic (computed-key) objects are already out of scope for it too (`!objVal.Ty.IsObject` rejects them, since a dynamic object literal's type sets `IsMap`, not `IsObject` — `in` inherits this same narrowing for free by reusing the function as-is, not by new special-casing).

Read `parser/parser_exprs.go`'s `parseRelational` (where `instanceof` is parsed, at the same real-JS-grammar precedence tier `in` belongs to) and `lexer/token.go` (confirmed `in` is **not** a reserved keyword token anywhere in this compiler). Read `parser/parser_stmts.go`'s existing `for...in` loop detection (`p.peekNth(2).Type == lexer.IDENT && p.peekNth(2).Literal == "in"`) — this compiler already recognizes `in` contextually (by literal text on a plain `IDENT` token), not via a reserved word, so the same approach was used for the new binary-operator position rather than introducing a real `lexer.IN` token, which would have made "in" an identifier a user could no longer name a variable/field after.

## Decision

`in` is parsed inside `parseRelational` as a fifth alternative alongside `<`/`>`/`<=`/`>=`/`instanceof`, matched by `p.peek().Type == lexer.IDENT && p.peek().Literal == "in"` — the exact same contextual-keyword technique `for...in` already established, so a variable/field literally named `in` keeps working everywhere outside this one operator position, and the pre-existing `for...in` loop needed no changes at all (verified by test, not just by inspection).

`emitHasOwnProperty` gained a `callerName string` parameter (previously hardcoded to "hasOwnProperty/Object.hasOwn" in both its error messages) so the same function backs all three call sites — `obj.hasOwnProperty(key)`, `Object.hasOwn(obj, key)`, and now `key in obj` via a two-line `emitInOperator` wrapper that just flips the argument order (`in` puts the key on the left, `hasOwnProperty`/`Object.hasOwn` put the object first) — with error text that reads naturally for whichever syntax the user actually wrote, rather than every `in`-operator error mentioning "hasOwnProperty."

## Implementation notes

Files touched: `parser/parser_exprs.go` (`parseRelational`), `codegen/llvm/emit_exprs.go` (dispatch, mirroring the existing `instanceof` special-case), `codegen/llvm/emit_objects.go` (`emitHasOwnProperty`'s new parameter + new `emitInOperator`), `codegen/llvm/emit_call.go` (updated the two existing `emitHasOwnProperty` call sites for the new parameter), `codegen/llvm/emit_exprs_types.go` (`inferExprType`'s `BinaryExpression` switch — `in` returns `TypeBool`, same case arm as `instanceof`).

No new AST node — `in` reuses the existing `ast.BinaryExpression{Op: "in", Left: key, Right: obj}` shape, identical to how `instanceof` was added.

## Side effects discovered

None.

## Verification

- `go build -o klainmain .` clean.
- `go test ./...`: all passing, no regressions (confirmed the pre-existing `for...in` loop specifically still works via a dedicated regression test, `TestE2EInOperatorForInStillWorks`).
- 6 new tests in `tests/objects_test.go`: object-literal field presence, class-instance field presence, use inside an `if` condition, the `for...in`-still-works regression check, and two negative cases (non-object right-hand side, non-literal key) — both correctly rejected at compile time.
- `examples/objects/objects.ts` extended with two `in`-operator lines; compiled, run, and output manually diffed against the inline expected-output comments.
