# ADR-01130: Local export lists (`export { a, b as c }`, `export {}`)

- **Relations**: `Extends ADR-00144` (re-exports, TDD-00051)
- **Date**: 2026-09-25

## Context

`export {}` is the idiom that marks a TypeScript file as a module. The
parser rejected it with "expected 'from' after export specifier list". The
general form, `export { a, b as c }` (a list of the file's own declarations,
with no `from`), was a documented scope cut of TDD-00051, yet it is ordinary
TypeScript and JavaScript. This came up while writing a checker probe file.

## Investigation

- **The parser** already parses the specifier list for a re-export and
  requires `from` after it (`parseExportFromDeclaration`).
- **The resolver's re-export pass** records each forwarded name as a
  `reExportBinding{local, target, remote}`. Once every file's mangled names
  are final, it resolves each binding through the target's `publicMangled`.
  A binding whose target is the file itself resolves `remote` through the
  file's own mangled declarations, which is exactly what a local export list
  needs.

## Decision

- **The parser** produces an `ExportFromDeclaration` with an empty `Source`
  when no `from` follows a braced list. `export * ` still requires `from`.
- **The resolver:**
  - skips a local list when visiting dependencies;
  - in the re-export pass, requires each name to be a top-level declaration
    of the file (otherwise "cannot export 'x': it is not declared at the top
    level of this file");
  - rejects an export name already used;
  - records a binding whose target is the file itself.
  - The merged program drops the statement, as it drops every
    `ExportFromDeclaration`.
