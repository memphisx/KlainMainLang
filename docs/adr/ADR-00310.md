# ADR-00310: Free-variable scanner missed `new TypedArray/ArrayBuffer/DataView(...)` arguments

- **Relations**: Extends [ADR-00104](ADR-00104.md) (closure captures); found during [ADR-00308](ADR-00308.md)
- **Date**: 2026-08-23

## Context

Hit in passing while wiring a SharedArrayBuffer through a worker handler: `parentPort.on('message', ...)` whose body did `const view = new Int32Array(sab)` failed with `undefined variable 'sab'` at codegen, even though `sab` was in scope at the closure site.

## Investigation

`scanExprFV` (`codegen/llvm/emit_func.go`) walks expression trees to collect a closure's free variables; the constructor-expression cases covered `NewArrayExpression`, `NewSetExpression`, the stream constructors, etc. — but not `NewTypedArrayExpression`, `NewArrayBufferExpression`, or `NewDataViewExpression`. Their argument expressions were never scanned, so an identifier appearing *only* inside one of those constructors was never captured; the closure body then failed at emission ("undefined variable"). Pre-existing since TypedArrays landed ([TDD-00018](../tdd/TDD-00018.md)) — any closure doing `() => new Uint8Array(buf)` over a captured `buf` miscompiled the same way; SAB just made the pattern common.

## Decision

Add the three missing cases to `scanExprFV`: `NewTypedArrayExpression.Arg`, `NewArrayBufferExpression.ByteLength`, and `NewDataViewExpression`'s `Buffer`/`ByteOffset`/`ByteLength`.

## Implementation notes

`codegen/llvm/emit_func.go` only. The other capture path (named function expressions) funnels through the same scanner, so both are fixed at once.

## Verification

`TestE2ETypedArrayConstructionCapturesBufferInClosure` (`tests/shared_memory_test.go`) — an arrow closure viewing a captured `ArrayBuffer` — plus every cross-thread test in that file exercises the pattern through worker handlers. Full `go test ./...` green (Mac).
