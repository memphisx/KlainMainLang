# ADR-00215: zero-initialize an uninitialized `let`/`const` slot (deterministic default for definite-assignment escapes)

- **Relations**: `Extends ADR-00210` (which zero-initialized `var` slots) and `ADR-00214` (which surfaced this as the `let` escape). Related to [TDD-00071](../tdd/TDD-00071.md).

- **Date**: 2026-08-18

## Context

Stress-testing the definite-assignment analysis ([ADR-00214](ADR-00214.md)) found its sharpest gap: a binding assigned only inside a maybe-skipped `for`/`while` body (`let x: number; while (c) { x = 1 } console.log(x)`) is soundly *not* flagged, and — because a plain `let` slot was never zero-initialized the way a `var` slot is ([ADR-00210](ADR-00210.md) Stage C) — the escaping read returned **uninitialized stack memory** (observed: `8426701056`), i.e. undefined behavior, rather than a clean default. The `var` form of the same escape already read a deterministic zero/`undefined`; only `let`/`const` were exposed.

## Decision

Extend the entry-block slot pre-initialization in `emitVarDecl` (`codegen/llvm/emit_exprs_vardecl.go`) from `v.Kind == "var"` to also cover any scalar/dynamic declaration with **no initializer** (`v.Kind == "var" || v.Init == nil`). A `let x: number;` now gets the same `emitVarSlotDefault` store as a `var` — zero for a typed scalar, the `undefined` box for an any-typed slot. `const` always has an initializer ([ADR-00209](ADR-00209.md)) so it never takes this branch; a `let x = e` with an initializer stores immediately and is unaffected.

This makes the definite-assignment analysis's sound-but-incomplete trade **safe**: a read the analysis misses now yields a defined value (a typed scalar's zero, an any-typed slot's `undefined`) instead of UB. It does not weaken any error the analysis *does* catch — those are rejected at compile time (in the resolver, before codegen), so the pre-init store is never reached for them.

## Implementation notes

- The pre-init is a compile-time-constant store placed in the entry (alloca) block, so it is dead and removed by `clang -O2` whenever an unconditional initializer or assignment dominates every read — the common case pays nothing.
- The flagship direct case (`let x: number; console.log(x)`) still errors: the definite-assignment pass rejects it before any IR is emitted, so the new store changes only the paths that pass the analysis but are missed by it.

## Side effects discovered

None. The change is purely additive determinism — no previously-accepted program changes behavior except an escaping uninitialized read, which moves from garbage to a defined default. The remaining definite-assignment escapes (`for`/`while` body-only, `try`-body, and the deliberately-`--strict`-matching correlated-conditions rejection) are unchanged in *which* programs compile; only the runtime value of a missed `let` read is now deterministic.

## Verification

- Re-ran the escape directly: `let x: number; while (n > 0) { x = n; … } console.log(x)` with `n = 0` now prints `0` (was uninitialized garbage); with `n = 5` still prints the correct `1`; an `any`-typed `let x;` prints `undefined`; and the direct `let x: number; console.log(x)` is still a `used before being assigned` compile error.
- Full `go test ./...` green (Mac, Apple Silicon M4); `go vet ./...` clean; `make examples` 126/126.
- `make conformance`: no committed-baseline change (the Linux `CONFORMANCE-RESULTS.md` is not overwritten from a Mac run — see [ADR-00210](ADR-00210.md)).
