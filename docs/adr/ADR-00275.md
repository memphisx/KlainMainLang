# ADR-00275: Async generator `.next()` is a genuinely-pending promise (deferred body, microtask-ordered) — the settle-without-drain deadlock, fixed; plus a `yield*`-async-iterable `.throw`/`.return` swallow fix

- **Relations**: Completes [TDD-00094](../tdd/TDD-00094.md) stage 4; supersedes [ADR-00274](ADR-00274.md)'s reverted deferral; builds on the microtask FIFO ([TDD-00088](../tdd/TDD-00088.md)) and the async-generator fiber/settle machinery ([ADR-00260](ADR-00260.md)/[TDD-00086](../tdd/TDD-00086.md)); premise corrected by [ADR-00281](ADR-00281.md), fixed by [ADR-00283](ADR-00283.md) (node/V8 runs the body synchronously to the first await/yield — the deferral this ADR shipped diverges; the settle-through-__kml_promise_settle fix stands)
- **Date**: 2026-08-21

## Context

The async-generators row was ✅-not-strict on one remaining caveat: `.next()` ran the body
**synchronously** to the next yield and returned an already-*resolved* promise, so a body side
effect before the first yield fired at the `.next()` call rather than as a microtask
(`before, body, after` here vs JS's `before, after, body`). ADR-00274 attempted the fix —
`.next()` enqueues a microtask step and returns a pending promise — but it **deadlocked** and was
reverted, the failure located only as far as "the awaiter parks and is never resumed."

## Root cause

The deadlock was **not** in the fiber/scheduler swap chain, as ADR-00274 guessed. The async
generator's step settled its result promise `q` by **writing `q`'s state/value fields directly**
(`settleAsyncGenResult`, `emitAsyncGenRejectPromise`, and `.return()`'s propagate path all did
`store i64 1/2` into the result slot) — it **never called `__kml_promise_settle`, so it never
drained `q`'s reaction list.**

Synchronously this was invisible: `.next()` ran the body and settled `q` *before* the caller
awaited it, so `q` had no waiter and there were no reactions to drain. Deferred, the ordering
inverts — `await it.next()` parks the caller on the still-pending `q` (attaching a resume reaction),
and *then* the microtask step settles `q`. Setting the state bit without draining left the resume
reaction stranded on `q` forever: the microtask FIFO emptied, no timers/fds remained, yet
`@__kml_task_active` stayed `1` (the parked task never finished), so `__kml_event_loop_run` blocked
on `select` — a quiescent hang, confirmed by inspecting the globals in the wedged process
(`task_active=1`, `mt_len=0`, `timer_len=0`).

## Decision

Route **every** async-generator promise settle through `__kml_promise_settle(q, state)` — which sets
the state bit **and drains `q`'s reactions** (waking any parked awaiter) — instead of a bare
state store. Three sites, all after their value/error is stored:

1. `settleAsyncGenResult` — fulfillment with `{value, done}` (state 1).
2. `emitAsyncGenRejectPromise` — rejection with the body's uncaught throw (state 2).
3. `emitAsyncGeneratorReturnByValue`'s propagate path — `.return(v)` on a not-started/done
   generator (state 1).

A drain with no attached waiter is a no-op, so the synchronous paths (`.throw()`/`.return()` on a
live generator, and any not-yet-awaited `.next()`) are unaffected — the fix is correct whether or
not an awaiter is parked, not a special case for the deferred path.

With settle draining reactions, `emitAsyncGeneratorNextCore` keeps the ADR-00274 deferral:
`.next()` enqueues a per-generator-type microtask step (`ensureAsyncGenStepFn` /
`enqueueAsyncGenStep`, memoized by the generator struct IR) carrying `{genObj, q}` and returns the
still-pending `q`. The step, when the FIFO drains it, runs `emitAsyncGenStepBody` (swap into the
fiber, settle `q`) — now waking the awaiter.

### Also fixed: `yield*`-async-iterable `.throw`/`.return` swallow

Reviewing the settle chain surfaced an unrelated bug in `emitYieldStarAsyncIterable` (ADR-00274
stage 3): after re-yielding an inner element it looped **unconditionally** back to the inner's
`.next()`, ignoring `__resumeMode`. So a `.throw(e)` / `.return(v)` on the outer async generator
while suspended at `yield* someAsyncIterable` was **silently swallowed** — the throw vanished and
another inner `.next()` ran. Fixed by dispatching on the resume mode the same way every ordinary
`yield` does (`emitYieldResumeDispatch`): mode 0 loops for the next element, mode 1 re-throws at the
suspension point so the outer body's `try`/catch-all handles it, mode 2 runs enclosing finallys and
completes the outer with the returned value. This is the outer's **own** path. *(Delegating into the
inner iterator's optional `.throw`/`.return` — the remaining divergence from JS — was then done in
[ADR-00276](ADR-00276.md), which took the async-generators row to strict.)*

## Verification

Mac (Apple Silicon M4). `go build`, `go vet ./codegen/...` clean. The audit program
(`async function* g(){ console.log("body"); yield 1 }` awaited from `main`) now prints
`before, after, body, 1` and exits `0` — JS microtask ordering, no hang (previously wedged in
`select`). Async `yield*` over an inner async generator / `Symbol.asyncIterator` reuses
`emitAsyncGeneratorNextCore`, so its `.next()` is deferred too; its E2E tests still pass. New E2E
tests cover the swallow fix: `yield*` over a user async-iterable delegating values, and `.return`/
`.throw` on the outer while suspended there (completes / propagates, not swallowed). Full
`go test ./...` (via `make test-par`) green.
