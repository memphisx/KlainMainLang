# TDD-00221: `undefined` for a nested-array (`T[][]`) element result

- **Status**: Implemented
- **Date**: 2026-09-17

## Context

TDD-00187 gave the element-absence operations (`.pop()`, `.shift()`,
`.find()`/`.findLast()`, `.at()`) a real `T | undefined` result for scalar and
pointer element types. It deliberately left the **nested-array** case out: when
the receiver is `T[][]`, the element is `T[]`, represented as the `{ptr, i64}`
value aggregate, and `undefinedableElem` (`codegen/llvm/emit_undefined.go:24`)
passes `IsArray` types through unflagged. The status pages carry this as a
recurring caveat on five `array-methods` rows (`.pop`/`.shift`/`.at`/`.find`/
`.findLast`): "a nested-array element still zero-fills the miss (`{null,0}`)
instead of `undefined`".

Empirical re-characterisation (2026-09-17) shows the caveat is **half true**,
which sharpens the target:

- **Already correct** on a miss: `=== undefined`, `== null`, truthiness
  (`if`/`? :`/`!`), and `Array.isArray(...)`. A miss materialises the
  `{null, i64 0}` aggregate (null *data-ptr*), and these paths already test the
  data-ptr — a genuine empty inner `[]` allocates a header, so its data-ptr is
  non-null and it correctly reads as *present*. The null-vs-empty-header
  discriminator from the array-reference-semantics work (TDD-00213) is what
  makes this work.
- **Still wrong** on a miss (all observed vs `node`):
  - `typeof p` → `"object"` (Node `"undefined"`)
  - `String(p)` / `` `${p}` `` → the array coercion, not `"undefined"`
  - `JSON.stringify(p)` → `"[]"` (Node: `undefined`, i.e. the value is dropped)
  - `p ?? alt` → the null-header array is not treated as nullish (and mixing
    element types is a clean type-mismatch reject, not the fall-through)

So the gap is specifically the **value-producing / coercion** operations, not
the comparison/branch ones.

## Design

### Why a raw data-ptr test is not enough

The tempting shortcut — "in `typeof`/`String`/JSON, treat any array with a null
data-ptr as `undefined`" — is **wrong**, because a null data-ptr is also how an
explicitly `null` array (`T[] | null` holding `null`) is represented, and
`typeof null === "object"` while `typeof undefined === "undefined"` (likewise
`String(null) === "null"` vs `String(undefined) === "undefined"`). The data-ptr
alone cannot say which. The *static type* must carry the `IsUndefined` vs
`IsNull` discriminator; only the type knows that a value came from an
absence-producing op (`undefined`-flavoured) rather than a nullable slot.

### The representation

Extend `undefinedableElem` to flag an `IsArray` element type
`Nullable | IsUndefined` (dropping the current `t.IsArray` early-return). The
value stays the `{ptr, i64}` aggregate; the *type flag* is the discriminator,
and the runtime signal is the null data-ptr (field 0). `wrapUndefinedable`
already returns `Value{Ref, Ty: nty}` unchanged for a non-scalar nullable — the
miss branch of each op already stores `{null, 0}`, and the hit branch a real
header, so no new value plumbing is needed at the producers.

### Consumers to teach (each a runtime `data-ptr == null` branch, gated on
`IsArray && IsUndefined`)

| Site | File (approx) | Behaviour on null data-ptr |
|---|---|---|
| `typeof` | `emit_exprs_operators.go` `emitUnary` | emit runtime branch → `"undefined"` else `"object"` (today it is a pure static answer for arrays — this becomes a runtime value for a flagged array) |
| `String()` / template / `toPrimitive` | `emit_toprimitive.go` | → `"undefined"` |
| `JSON.stringify` | `emit_call_json.go` | value is dropped (object property omitted; array element → `null`; top-level → the `undefined` return) — mirror the existing dynamic-`undefined` handling |
| `??` / `?.` | `emit_exprs_operators.go` `emitNullCoalesce` | treat null data-ptr as nullish → evaluate the right operand; needs the aggregate-aware null test (today the ptr path assumes `IR == "ptr"`) |
| `== null` / `=== undefined` | already correct | (leave — regression-test to lock in) |

### The policy decision — strict-consumer rejection

Flagging the type routes array results through `checkStrictUndefinedAssign`
(TDD-00187's strict gate). Under strict mode, `const x: number[] = m.pop()`
would become a **clean compile rejection** (assigning `T[] | undefined` to
`T[]`) — which is what `tsc --strictNullChecks` does, so it is *more* faithful.
But it is a behaviour change: existing strict programs/tests/examples that
consume a nested-array pop/at result without a narrow/`!`/`??` would start
failing to compile. **Recommended**: adopt the strict rejection (faithful, and
consistent with the scalar/pointer cases already shipped), but audit
`tests/`, `examples/`, and the Test262/TS oracles for fallout in the same
change and fix each consumer (narrow, `!`, or `?? default`). `-compat=js` keeps
the lenient path, as it does for scalars.

## Prerequisites

| Dependency | Status | Notes |
