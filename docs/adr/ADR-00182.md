# ADR-00182: Generator methods (TDD-00063 Stage 2b)

- **Relations**: `Implements TDD-00063` (Stage 2b). `Extends ADR-00181` (Stage 2a parsed the forms; this makes `*m()` real). Builds on [ADR-00172](ADR-00172.md) (the generator fiber machinery) and [ADR-00063](ADR-00063.md) (class method dispatch).
- **Date**: 2026-08-13

## Context

[ADR-00181](ADR-00181.md) (Stage 2a) parsed all three class method-modifier forms and implemented async methods, leaving generator methods (`*m()`) a clean codegen rejection. This ADR makes them real: a `*method()` on a class is a genuine generator — calling it constructs a generator instance (it does not run the body) that `yield`s values and can read `this`, driven by `for...of` or explicit `.next()`.

## Investigation

- Free-function generators ([ADR-00172](ADR-00172.md)) compile each generator to a fiber (a private `ucontext_t` + stack) whose instance is a struct (`GeneratorType`) with `__ctx`/`__stack`/`__callerCtx`/`__started`/`__done`/`__yielded`/`__sent` fields plus trailing `__paramN` slots. The body function (`@__generator_body_*`) reads its instance pointer once from a global handoff slot at entry, binds params from the `__paramN` fields, and `yield`/`return` suspend by swapping back to the caller. `.next()` and `for...of` (`emitGeneratorNext`/`emitForOfGenerator`) drive it. None of this had any notion of a receiver — a generator got a clean scope with no `this`.
- The only thing a generator *method* adds over a free-function generator is the implicit `this`. Everything else — the fiber, the suspend/resume, `.next()`, `for...of` — is identical, and every field access in those paths is by field *name* (`FieldIndex`), so adding one more struct field is transparent to them.
- Class method dispatch (`emitClassCall`) resolves a method to its `@Class_method` LLVM function (direct or vtable). A generator method must instead *construct* an instance at the call site, so it needs interception before the normal dispatch — and it must **not** claim a vtable slot, or the vtable emitter would emit a reference to a `@Class_method` symbol that does not exist (its real body is `@__generator_method_*`).

## Decision

Represent a generator method's receiver as a dedicated `__this` slot on the generator instance, stored at construction and read once at body entry to bind `this`. Concretely:

1. **`GeneratorType(elem, params, thisTy)`** gains an optional `thisTy`; when set, the struct carries a `__this` (ptr) field. `GeneratorInfo` gains `ThisTy *Type`.
2. **Registration** (`registerClasses`): a generator method builds a `GeneratorInfo` (via `buildGeneratorMethodInfo`), its registered method return type becomes the generator instance type (so `obj.m()` types as a generator and `for...of`/`.next()` dispatch pick it up), and the info is stored in `ClassInfo.GenMethodInfo`. It is registered like a plain method for name/visibility, but **given no vtable slot**; it is inherited by subclasses (the `GenMethodInfo` map is copied down). V1 scope cuts: static generator methods, abstract generator methods, async generators (`async *`), and generator methods on generic classes are each a clean rejection.
3. **Body** (`emitClassDecl` → `emitGeneratorFunctionDecl`): when `ThisTy != nil`, the body loads `__this` and binds `this` (plus `super` and the lexical enclosing-class identity for visibility) before binding params. The final (post-vtable) class type is threaded in at emit time, since registration only had the provisional pre-vtable type.
4. **Call** (`emitClassCall`): a `GenMethodInfo` hit constructs a generator instance via `emitGeneratorConstructionWithThis`, storing the receiver into `__this` and the args into `__paramN`, and returns the instance — intercepting before the normal/vtable dispatch.

## Implementation notes

- `emitGeneratorConstruction` was split into a thin wrapper over `emitGeneratorConstructionWithThis(info, thisRef, args, pos)` — `thisRef == ""` is the free-function case, unchanged.
- The `__this` field's *type* is only ever `ptr`, so building `GenTy` at registration with the provisional class type is layout-safe; only the `this`-*binding* needs the final class type, set on the shared `GeneratorInfo` at emit time.
- Generator methods deliberately bypass the vtable: dispatch is by the receiver's static class (V1). An overridden generator method reached through a base-typed variable would construct the base's generator — a documented V1 limitation, not silent breakage.

## Side effects discovered

- **Pre-existing bug fixed in passing**: `new C([1, 2, 3])` against `constructor(xs: number[])` was a hard clang-stage type mismatch — the constructor-call path (`emitNewExpression`) never decomposed an array argument into the callee's `(ptr, i64 len)` pair, unlike the already-fixed method-call path (`emitClassCall`). Surfaced by a generator-method test constructing `new Acc([1,2,3])`; a real bug independent of generators, fixed with the same decomposition. Covered by its own test.
- Array-typed and destructured/rest/default parameters remain unsupported on generators generally (a free-function-generator limitation inherited unchanged); a generator method's body may still *read* array-typed `this` fields (that goes through ordinary field access, not the generator param path).
