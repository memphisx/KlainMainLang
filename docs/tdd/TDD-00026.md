# TDD-00026: Binary-safe `http.listen()` request/response bodies

- **Status**: Implemented
- **Date**: 2026-08-04

## Context

Surfaced while investigating whether `tools/httpbin-lite/main.go` — a small local fixture server `make examples` starts so `examples/fetch/*.ts`/`examples/async/promise_all.ts` don't depend on `httpbin.org`'s uptime (ADR-00096) — needed to be written in Go at all, versus dogfooding this compiler's own `http.listen` by writing it in KlainMainLang instead. Checking that concretely (not assuming): every route the fixture serves *except one* is fully expressible with `http.listen` today — `req.method`/`.path`/`.query`/`.headers`/`.body` reads and an arbitrary `Res{status, headers, body}` cover `/get`, `/ip`, `/status/{code}`, `/redirect-to`, `/post`, `/delete`, `/headers`; and `/delay/{n}` doesn't need a real sleep primitive at all — a synchronous CPU-bound loop in the handler delays the response exactly as well, since the handler itself, not a deferred callback, is what has to return late.

The one blocker: `/bytes/16` returns a response body with a guaranteed embedded null byte (the whole point of that route — see ADR-00094's `.arrayBuffer()` null-survival check). `Res.body` is a plain string, and confirmed directly at `codegen/llvm/runtime_http.go:664` (`%%bodylen = call i64 @strlen(ptr %%body)`) that the HTTP response writer computes how many bytes to `write()` via `strlen`, not a carried length — so a null byte in that field truncates the response before any bytes past it reach the socket. Every string in this compiler is a plain null-terminated C string by design (`docs/status/NETWORKING.md`'s Known Limitations already documents this for `fetch`'s `.text()`/`.json()`), and `http.listen` was never revisited for the same gap after `.arrayBuffer()` (ADR-00094) fixed it on the `fetch`/`fs` side — **this is a real, confirmed gap, and until this TDD it was undocumented anywhere in `docs/status/HTTP-SERVER.md`**, unlike its `fetch`/`fs` counterpart. The gap is bidirectional: `req.body: string` (ADR-00072) is `Content-Length`-aware on the *read* side (it accumulates exactly as many bytes as the header promises, via `realloc`, not a `read()`-until-it-looks-done heuristic), but the moment that buffer is exposed to TS code as a plain `string`, every ordinary string operation on it (`.length` included) reverts to `strlen` semantics — so a request body containing a null byte already silently truncates today, symmetric to the response-side gap above.

Scoping this now, rather than just patching around it in the example, so the eventual fix follows the same precedent ADR-00094 already established for `fetch`/`fs`, instead of a one-off.

## Design

Mirror ADR-00094's shape directly: `ArrayBuffer`/TypedArrays (TDD-00018, already implemented) already exist as this compiler's answer to "a byte sequence that survives an embedded null," and `Response.arrayBuffer()` already proves the pattern of adding a binary-safe accessor *alongside* the existing string-based one rather than replacing it. Applying the same shape to `http.listen`:

- **Request side**: add a `req.bodyBytes(): ArrayBuffer` method (name matches `fetch`'s `Response.arrayBuffer()` convention) that returns the exact byte range already accumulated by the `Content-Length`-aware read loop (`runtime_http.go`, ADR-00072) — no new accumulation logic needed, just a new accessor onto a byte count the runtime already tracks internally but currently only exposes through the string it built from that same buffer.
- **Response side**: give the handler's return type an additional optional field carrying a binary body — e.g. `bodyBytes: ArrayBuffer` alongside the existing `body: string` — checked structurally the same way `headers` already is (an optional field, absent behaves byte-identically to today). This compiler has no general union types beyond `T | null` (the project's own instructions), so `body: string | ArrayBuffer` on one field isn't an option; a second, separate optional field is. If `bodyBytes` is present, the response writer must use its real `byteLength` for the `write()` call instead of `strlen`-ing `body` — needs deciding whether `bodyBytes` wins outright when both fields are set, or whether setting both is a compile-time error (leaning toward "wins," matching how an absent `headers` field today just no-ops rather than erroring, but not committed — see Open Questions).
- Once this lands, `tools/httpbin-lite/main.go` (ADR-00096) should be rewritten in KlainMainLang using `http.listen`, since every route except `/bytes/{n}` is already confirmed implementable today, and `/bytes/{n}` would become implementable too via `bodyBytes`. That would remove the last piece of this project's own example/CI infrastructure written in a language other than KlainMainLang itself, and is the concrete motivating use case for actually picking this TDD up rather than leaving it as a documented gap indefinitely.

See [ADR-00106](../adr/ADR-00106.md).
- ~~Whether `req.bodyBytes()` is needed in the same pass as the response-side fix~~ Resolved: shipped together — no extra design work was needed once the request side's `bodyLength` field existed, and proving the fix end to end (a real round trip) needed both sides anyway.
- Whether this should also cover `fetch`-style request bodies sent *by* a KlainMainLang HTTP client to another server (i.e. `fetch(url, { body: someArrayBuffer })`) — still out of scope; this TDD is `http.listen` (server-side) only, `fetch`'s own request-body shape is unaffected.
