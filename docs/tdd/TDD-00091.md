# TDD-00091: Thenable adoption — `resolve(aPromise)` in a `new Promise` executor

- **Status**: Implemented
- **Date**: 2026-08-20
- **Notes**: `resolve(anotherPromise)` adopts the thenable: the outer promise settles with the inner's value (or reason) when it settles, instead of the old `clang` type error coercing a promise to the value type. Reaction-based (reuses `.then`'s reaction-list + microtask FIFO + `__kml_promise_settle`), so adoption is a microtask tick like JS, not synchronous — no ordering caveat. A `Type.IsPromiseResolver` marker + an `emitClosureCallByPtr` hook fire adoption only for a genuine `Promise` argument. Closes the `new Promise` row's last caveat (the other, a top-level-function executor, was verified stale); Async/Promise strict 5/9 → 6/9. Custom duck-typed `{ then }` thenables aren't adopted (no `PromiseLike` type — a clean reject, not a silent miss)

## Context

`new Promise((resolve) => resolve(anotherPromise))` — passing a promise (a thenable) to
`resolve` — should make the outer promise **adopt** the inner one: the outer settles with the
inner's value when it fulfills, or the inner's reason when it rejects. This is core ECMAScript
promise-resolution behavior. It was the sole remaining caveat on the `new Promise` executor row
(TDD-00087); the other listed caveat — a bare top-level-function executor reference — was found
**stale** (it already works via `emitExpr` resolving the reference to a closure value). So closing
adoption makes the row strict.

Grounded — before this it was a hard `clang` type error, `resolve`'s parameter being the value
type (`i64`) and the argument a promise (`ptr`):

```ts
const p = new Promise<number>((resolve) => { resolve(inner()) })  // inner(): Promise<number>
await p   // want inner()'s value; was: argument is not of expected type 'i64'
```

## Design

**Reaction-based adoption, reusing the `.then` machinery.** `resolve` is a per-site closure whose
env is the target promise (emit_promise_new.go). Mark its type `IsPromiseResolver`. At a call
site `resolve(arg)` where `arg`'s compile-time type is a `Promise`, don't coerce — instead
register an **adopt reaction** on `arg`: when `arg` settles, a microtask copies its settlement
(state + value/reason bits) into the target and settles it (`__kml_promise_settle`, which wakes a
parked awaiter and drains the target's own reactions). If `arg` is already settled the reaction is
enqueued immediately; otherwise it is attached to `arg`'s reaction list (field 4) and fires when
`arg` settles — the exact register-or-enqueue pattern `Promise.prototype.then` already uses
(emit_promise_then.go).

**Why reaction-based, not synchronous drive:** a synchronous "drive `arg` to settled inside
`resolve`, then settle the target" would get the value right but settle the target *synchronously*
at the `resolve` call, diverging from JS where adoption is a microtask job. Reaction-based
adoption is a real microtask tick (enqueued via `__kml_microtask_enqueue`), so `resolve(p)`
followed by synchronous code, `.then`, and other microtasks interleaves as in JS — no ordering
caveat, so the row is genuinely strict. It also reuses three existing pieces (the reaction list,
the microtask FIFO, `__kml_promise_settle`) rather than adding a drive loop.

Only a `Promise`-typed argument adopts; a plain value falls through to the normal
store-value-and-settle path. A `Promise<void>` `resolve` takes no argument and so is never marked.

## Stages

1. **Marker + call-site hook.** `Type.IsPromiseResolver`, set on the resolve closure; in
   `emitClosureCallByPtr`, when a resolver is called with a `Promise` argument, adopt.
2. **Adopt runtime + registration.** `@__kml_promise_adopt_runner` (the settlement-copy microtask)
   and `emitPromiseAdopt` (build the `{src,tgt}` env + closure, register-or-enqueue on `src`).
3. **Verify** fulfilled adoption, rejection forwarding, deferred (`setTimeout`) adoption,
   microtask ordering (async, not synchronous), plain-value resolve, and the (already-working)
   top-level-function executor.

## Open questions

- **Nested adoption / a chain of thenables.** `resolve(p)` where `p` itself adopts `q`: each hop
  is its own reaction, so it resolves transitively — covered by the same mechanism, no special
  case. A non-promise "thenable" object (a plain `{ then }`) is **not** adopted — this compiler
  has no duck-typed `.then` probe; only a typed `Promise` argument adopts. That is a narrower
  surface than JS's structural thenable, noted but not a value-correctness gap for typed code.
- **Exact microtask tick count.** V8's `PromiseResolveThenableJob` adds a specific number of
  ticks; this fires one adopt microtask when the source settles. Both are real microtask ticks
  (never synchronous), so ordering against sync code / `.then` / `queueMicrotask` matches; exact
  tick-count parity with a specific engine is not a property this compiler pursues anywhere.
