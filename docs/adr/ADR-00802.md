# ADR-00802: chunked/streaming HTTP responses keep the connection alive

- **Relations**: `Implements TDD-00131`, `Extends TDD-00097`, `Extends ADR-00300`
- **Date**: 2026-09-09

## Context

Keep-alive covered only the buffered response path (`res.end(…)` / the bespoke
`{ status, body: string }`): a chunked/streaming response — a handler whose
`body` is a `ReadableStream` — always sent `Connection: close` and closed the
socket at stream end. For the REST/microservice target a streamed body (SSE, a
large generated payload, a proxied stream) forcing a fresh TCP handshake per
request is a real cost. This is backlog item §1.3's chunked-keep-alive slice.

## Investigation

The buffered path already keep-alives: after `__kml_http_send_response` it
consults `__kml_http_keepalive_decision` and, when persistent, loops the
dispatcher fiber back to its read loop instead of closing
(`emit_http.go` buffered tail).

The streaming path is different (`runtime_http_stream.go`): the dispatcher sends
the chunked head, hands the fd to a reaction-driven `%kml.hws` writer, and
retires its fiber (`ret void`, fd stored as -1). The writer runs entirely as
promise reactions — `read → write framed chunk → read …` — and at stream end
wrote the terminating `0\r\n\r\n` chunk, closed the fd, and decremented the
active-connection count. The head hard-coded `Connection: close`.

Key question: can the writer re-arm the connection instead of closing? The
writer's reactions are enqueued by `__kml_promise_add_reaction` as **microtasks**
and drained by `__kml_drain_microtasks` in the event-loop body — i.e. on the
**main context**, the same context the accept path calls
`__kml_http_append_conn` from (which does `swapcontext(@__kml_main_ctx, fiber)`).
So spawning a fresh dispatcher fiber on the still-open fd from the writer's
stream-end path is safe — no new reactor machinery needed.

## Decision

Thread a keep-alive flag through the streaming writer and, when set, re-arm the
connection at stream end rather than closing it:

- `__kml_http_send_stream_head(connfd, status, extraHeaders, i1 keepalive)`
  selects `Connection: keep-alive` + `Keep-Alive: timeout=5` vs
  `Connection: close` (the buffered path's own two header lines).
- The `%kml.hws` writer context grows a 6th field (`keepAlive i64`); the ctx is
  now 48 B.
- At the writer's `finish` block: on keep-alive, restore `O_NONBLOCK` (the writer
  had cleared it for blocking chunk writes), net-zero the active count
  (decrement this connection, which `append_conn` re-increments as it spawns the
  fresh fiber), free the writer ctx, and call `__kml_http_append_conn(fd)` to
  re-enter the dispatcher on the same fd. Otherwise close as before. (The ctx
  was previously leaked on close — now freed on both paths.)

The flag is the real `__kml_http_keepalive_decision` (client `Connection: close`
and handler-set `Connection: close` both defeat it), computed once before the
streaming tails and passed to both the statically-`ReadableStream` body and the
union-body (`string | ReadableStream`) stream branch.

**Scope held back deliberately:** HTTPS/1.1 streaming stays close-only — the
re-arm path isn't yet validated against the TLS-wrapped read loop — so the flag
is forced off when `usedHTTPS1Server`. The union-body *string* branch (a union
body that resolved to a plain string) also still closes; it retires the fiber
rather than looping, and wiring its read-loop re-entry is separate work. Both
are recorded as caveats, not silently ignored.

## Implementation notes

- `runtime_http_stream.go`: rewrote the streaming runtime from a many-`%s`
  `fmt.Sprintf` to `strings.NewReplacer` token substitution (the added branch
  made the positional args unmanageable). Tokens are uppercase
  (`HWS`/`HEADFMT`/…) so they don't collide with the lowercase `@__kml_hws_*`
  symbol names; the replacer substitutes once, so interned-string values aren't
  re-scanned.
- `emit_http.go`: `streamKA`/`streamKA64` computed before the union/streaming
  tails; both `send_stream_head` and `hws_start` call sites updated.
- The HTTPS `strings.ReplaceAll` rewrites (plaintext `write`/`close` → the
  SSL-aware shims) still match — only the close branch is rewritten, and it is
  unreachable under HTTPS since the flag is forced off there.

## Side effects discovered

The `%kml.hws` writer context was never freed (a per-streamed-response leak).
Fixed here — `free(ctx)` on both the close and re-arm paths.

## Verification

Mac (Apple Silicon). New `tests/http_test.go` `TestE2EHTTPChunkedKeepAlive`:
two requests over one raw socket to a `ReadableStream`-body `klain:http` server —
the first advertises `Connection: keep-alive` and streams its chunks, the
connection re-arms, the second request is served on the same socket and honors
the client's `Connection: close`. Full `TestE2EHTTP*` and streams suites green;
`examples/streams/http_chunked.ts` still streams correctly; `go vet` clean.
Verified manually with a raw Python keep-alive client too.
