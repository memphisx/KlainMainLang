# ADR-00733: First matrix run — Linux aarch64 goroutine crash and `os.cpus()` fidelity, Intel macOS `$INODE64`

- **Relations**: Extends [ADR-00732](ADR-00732.md) (the five-lane matrix; this is what its first run found), [ADR-00569](ADR-00569.md) (`os.cpus()` speed on Apple Silicon), [ADR-00719](ADR-00719.md) (the Windows out-of-line thread-local accessors generalised here)
- **Date**: 2026-09-06

## Context

The first push through the new matrix: macOS arm64 and Linux x64 green, Linux aarch64 red on two tests, macOS x64 red on eleven `fs` tests. Neither platform had ever run the suite before (Linux aarch64 only ever through Docker on the M4). Per the release rule, the run still cut a release with the green platforms' binaries.

## Investigation

**Linux aarch64** (reproduced under Docker's QEMU emulation of `linux/arm64` on the Windows box):

- `TestE2EGoroutineHTTPListenLoadTest` died (SIGABRT on the runner, SIGILL under emulation). The `klain:sync` scheduler's current-M/current-G thread-locals are read directly on Linux; a goroutine stolen by another M resumes on a different thread, and on aarch64 the optimizer hoists the `adrp`/`tprel` address computation across the `swapcontext`, so the resumed code writes the *previous* thread's slot. x86-64's `%fs`-relative access and Darwin's `tlv_get_addr` call never gave the optimizer that opportunity, which is why the same source passed on both. ADR-00719 met exactly this on Windows (fibers) and solved it with out-of-line accessors, gated to `_WIN32`.
- `TestE2EOSCpusFieldsWellFormed`: aarch64's `/proc/cpuinfo` has no `cpu MHz` line, so `speed` was 0 and the test demanded a positive value. Node 22's libuv (`src/unix/linux.c`) does not read `cpu MHz` at all any more: speed is `/sys/devices/system/cpu/cpuN/cpufreq/scaling_max_freq` in kHz, and 0 wherever cpufreq is absent — most VMs and containers, on x86-64 too. The model, absent a `model name` line, comes from the `CPU part` code through libuv's table of ARM part numbers, else `unknown`.

**macOS x64** (not reproduced — no Intel Mac on hand): every failing test reads `struct stat` fields or `readdir` entries (a directory of three files listed as four with a `.txt` name; `stat` sizes 0; `readFileSync` on a directory not throwing because the `S_ISDIR` check saw garbage). On Intel macOS the plain `stat`/`lstat`/`fstat`/`opendir`/`readdir` symbols resolve to the legacy 32-bit-inode variants, whose struct layouts differ; the 64-bit-inode layout this compiler's code was written against — the only one on Apple Silicon — is exported there as `<name>$INODE64`. A C compile picks the right one through the headers; hand-written IR names the symbol itself.

## Decision

- **Scheduler thread-locals through out-of-line accessors on every host** (`klainsyncsrc/klainsync.c`): the `_WIN32` gate is gone. Cost: one non-inlined call per access to the current M/G.
- **`os.cpus()` on Linux follows libuv**: `speed` from `scaling_max_freq / 1000`, 0 when absent (`__kml_os_cpufreq_khz`); the model falls back from `model name` to the `CPU part` code looked up in libuv's ARM table (embedded verbatim), then `unknown`. `TestE2EOSCpusFieldsWellFormed` now requires `speed >= 0` on Linux and keeps `> 0` on macOS. The `fscanf` declaration the RSS reader emitted unguarded is now `ensureFscanfDecl`, shared.
- **Intel macOS `$INODE64`** (`runtime_fs.go`, `emitFSDecl`): on `darwin/amd64` the five entry points are declared as their `$INODE64` exports and wrapped by an *internal* function of the plain name, so no call site changes; every other host gets the plain declaration.

## Implementation notes

- `codegen/llvm/runtime_os.go`: `armPartTable`, `ensureOSCpufreqKHz`, the model/speed blocks of `ensureOSCpusLinux`.
- `codegen/llvm/runtime_core.go`: `ensureFscanfDecl`. `runtime_fs.go`: `emitFSDecl` at the `stat`, `lstat`, `fstat`, `opendir`/`readdir` sites.
- Verification limits are stated below rather than glossed: the `CPU part` path and the Intel wrappers were not executed.

## Side effects discovered

- `/proc/cpuinfo` cannot be overridden inside Docker's emulated arm64 container (a bind mount over it, even privileged, does not take), so the part-code lookup could only be checked by reading; the M4 (or a real aarch64 Linux box) is where `os.cpus()[0].model` should read e.g. `Neoverse-N1` on a GitHub runner.
- Under QEMU the goroutine crash surfaced as SIGILL rather than the runner's SIGABRT; same root cause, same fix.

## Verification

- Linux aarch64 (Docker `klain-ci-arm64`, emulated): `TestE2EGoroutineHTTPListenLoadTest` fails before the accessor change and passes after (13.9 s); the three `TestE2EOSCpus*` tests pass; `os.cpus()[0]` prints `speed: 0` with the QEMU model name, matching libuv's behaviour without cpufreq.
- Linux x64 (Docker) and Windows 11: the `fs`/`os`/goroutine/memory groups pass after the change; `go vet ./...` on both.
- macOS x64: **unverified** — the next matrix run is the test; if the eleven `fs` tests stay red, the Intel MacBook Pro is the place to look at the actual struct layouts. macOS arm64 is unaffected (plain declarations, as before).
