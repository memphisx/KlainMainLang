# ADR-01398: ecdh.getPrivateKey() without leading zero bytes

- **Relations**: Fixes the ECDH surface of `lib/node/crypto.ts`
- **Date**: 2026-10-05

## Context

`TestE2ECryptoECDHAndDiffieHellman` failed once in a parallel test run and
passed on its serial retry. The test generates random keys and compares
its output with Node's line by line.

Node serializes an ECDH private key with OpenSSL's `BN_bn2bin`, which drops
leading zero bytes. About one P-256 key in 256 starts with a zero byte, so
Node's `getPrivateKey()` returns 31 bytes or fewer for it, after
`generateKeys()` and `setPrivateKey()` alike. This runtime always returned
the stored 32 bytes. Over 3,000 keys, Node returned 31 bytes ten times and
this runtime never did.

The test printed the key's length, so it failed whenever Node's run drew
such a key.

## Decision

- `getPrivateKey()` returns the key without leading zero bytes, for both
  crypto backends. The stored key, and every computation with it, are
  unchanged.
- The test no longer prints a length that depends on the random key. It
  asserts the bound (`<= 32`), and a fixed key (`0x…07`) checks the
  unpadded form deterministically.

## Verification

- Mac (M4): 3,000 generated keys plus a padded `setPrivateKey` round-trip
  match Node (`07` for a key of value 7); the ECDH test passes.
- Linux x86-64 (Ubuntu 24.04 container): test-par passes (14 shards,
  3922 tests).
