# ADR-00112: TextEncoder / TextDecoder

- **Date**: 2026-08-07

## Context

`docs/status/ENCODING-TEXT.md` tracked `TextEncoder`/`TextDecoder` at 0% coverage, and `docs/status/README.md`'s Roadmap listed both under "Low effort (C stdlib or a simple wrapper)" in the Web Platform & Node.js APIs backlog — picked up as the first of two low-effort backlog items requested directly (alongside `structuredClone`, ADR-00113), ahead of further work on the terminal-UI direction (TDD-00031).

## Investigation

Checked how this compiler represents strings before deciding how much real transcoding work was needed: `runtime_encoding.go`'s `ensureBase64Encode`/`ensureBase64Decode` (btoa/atob) already documents that "this compiler's strings are already just byte sequences" and operates byte-for-byte. Confirmed the same premise applies here — this compiler's strings are plain NUL-terminated UTF-8 byte buffers, with source text itself read as UTF-8. That makes `TextEncoder.encode(str)` and `TextDecoder.decode(bytes)` direct byte copies with no real UTF-8 validation/transcoding needed, a much smaller scope than the ENCODING-TEXT.md page's original aspirational note ("supports UTF-8, UTF-16, Latin-1"). Decided to narrow V1 to UTF-8 only and update that page to describe what's actually built rather than carry the old aspirational note forward.

Looked at the two existing shapes for a "constructor + methods" built-in to decide which one to follow:
- `URL`/`URLSearchParams` (`emit_url.go`, `types.go`'s `IsURL`): a real heap object with fields, needed because URL genuinely holds parsed state.
- `ArrayBuffer` (`emit_arraybuffer.go`, `types.go`'s `IsArrayBuffer`): `Type{IR: "ptr", IsArrayBuffer: true}`, a marker flag with no fields, because construction produces genuine header state (byteLength + data ptr) but the flag itself needs no payload.

Neither TextEncoder nor TextDecoder needs any per-instance state at all (V1 ignores TextDecoder's `label` argument entirely — see Decision). Modeled both purely as marker types whose value is always the constant `"null"` — the same trick `NullLiteral` already uses (`emit_exprs.go`'s `NullLiteral` case) — so `new TextEncoder()`/`new TextDecoder()` need no heap allocation at all, not even ArrayBuffer's trivial one.

Found that dispatch for `.encode()`/`.decode()` needed three separate wiring points, not just `emit_call.go`'s method-call switch: `emitExpr`'s generic dispatch (`emit_exprs.go`), the pure static-type inferer (`inferExprType`, `emit_exprs_types.go`) used by e.g. `console.log`'s argument-format decision and any expression-position use, and `emitVarDecl`'s own separate unannotated-initializer type-inference switch (`emit_exprs_vardecl.go`) — confirmed by first testing `const bytes = enc.encode(...); bytes.length` and hitting `'bytes' is not an array`, since `emitVarDecl`'s `*ast.CallExpression` case only handled an `Identifier` callee, not a `MemberExpression` one, for anything outside its `default: e.inferExprType(init)` fallback (which itself needed `inferExprType` to already understand `.encode`/`.decode`, so it was a cascading gap, not one bug). Root-caused and fixed by adding `encode`/`decode` cases to `inferExprType`'s existing `mem.Property` switch (`emit_exprs_types.go`, alongside `arrayBuffer`/`text`/`json`), which both `emitVarDecl`'s `default` fallback and `console.log`'s printf-format selection already consult.

## Decision

- New AST nodes `NewTextEncoderExpression` (no arguments) and `NewTextDecoderExpression` (optional `Label Expression`), parsed in `parser/parser_literals.go`'s `parseNew` alongside `URL`/`ArrayBuffer`.
- New marker types `TextEncoderType()`/`TextDecoderType()` (`types.go`'s `IsTextEncoder`/`IsTextDecoder` flags), both `Type{IR: "ptr", ...}` with `Ref` always the constant `"null"` — no allocation, since neither holds state.
- `new TextDecoder(label)`: `label`, if given, is evaluated (for side effects) and then discarded. V1 is UTF-8 only; an unrecognized label is not validated or rejected — the same permissive-and-documented convention `atob`/`decodeURI` already established for malformed input (`docs/status/GLOBAL-FUNCTIONS.md`), rather than adding a runtime `strcmp` branch for a RangeError real `TextDecoder` would throw.
- `TextEncoder.encode(str): Uint8Array` — `strlen` + `malloc` + `memcpy` the string's raw bytes into a fresh buffer, returned as `TypedArrayType("uint8")` (reusing the existing `{ptr, i64}` aggregate TypedArrays already use — see ADR-00078/TDD-00018).
- `TextDecoder.decode(bytes): string` — accepts a `Uint8Array` (`argTy.IsArray` with `elemTy.IR == "i8"`, unsigned) or an `ArrayBuffer` (`argTy.IsArrayBuffer`, reading its 2-word header exactly like `emitArrayBufferByteLength`/`emitTypedArrayFromBuffer` already do); `malloc(len+1)` + `memcpy` + a manual NUL terminator. Any other argument type is a compile-time error, not a runtime one, since the argument's shape is always statically known.
- Both receiver expressions (`objExpr` in `emitTextEncoderEncode`/`emitTextDecoderDecode`) are still evaluated via `emitExpr` even though nothing is read from the result — preserves real JS's left-to-right side-effect evaluation order (e.g. `getEncoder().encode(x)`) despite there being no actual state to read.

## Implementation notes

Files touched: `ast/nodes.go` (2 new node types), `parser/parser_literals.go` (2 new parse functions + `parseNew`'s dispatch), `codegen/llvm/types.go` (2 flags + 2 constructors), `codegen/llvm/emit_exprs.go`, `emit_exprs_types.go`, `emit_exprs_vardecl.go` (dispatch wiring, all three points found necessary per Investigation above), `codegen/llvm/emit_call.go` (`.encode`/`.decode` method-call dispatch), `codegen/llvm/emit_call_encoding.go` (the actual implementation — `emitNewTextDecoderExpression`, `emitTextEncoderEncode`, `emitTextDecoderDecode`).

No new `runtime_*.go` C-function declarations were needed — both operations reuse already-declared `strlen`/`malloc`/`memcpy` (`ensureStrlen`/`ensureMalloc`/`ensureMemcpy`, `runtime_core.go`) directly via hand-emitted `getelementptr`/`load`/`store`/`call` instructions, the same inline style `emit_arraybuffer.go` already uses rather than declaring a new named C helper function per operation.

## Side effects discovered

None — no pre-existing bugs found along the way this time (unlike several recent ADRs in this project's history). The `emitVarDecl`/`inferExprType` gap described in Investigation was specific to this new feature (no prior code path exercised a `MemberExpression`-callee call returning a non-array/object/string type through an unannotated `const`), not a latent bug in unrelated code.

## Verification

- `go build -o klainmain .` and `go vet ./...` clean.
- `go test ./...` — full existing suite (`lexer`, `parser`, `tests`) passes unchanged.
- New tests: `tests/encoding_text_test.go` — `.encode()`'s length/byte values, round-trip through `.decode()`, decoding directly from an `ArrayBuffer`, the ignored-label case, and a compile-time-rejection case for `decode()` called with neither a `Uint8Array` nor an `ArrayBuffer`.
- New example: `examples/encoding_text/encoding_text.ts`, verified via `make examples` (79/79 passed, including this one).
- Manually verified via a scratch `.ts` file compiled and run directly, round-tripping a string through `encode`/`decode` and decoding a hand-populated `ArrayBuffer`/`Uint8Array` view, before the formal test suite was written.
- Verified on: x86-64 Linux only (this session's machine) — no platform-sensitive code involved (pure `strlen`/`malloc`/`memcpy`, no libc/OS-specific behavior), so no Apple Silicon-specific re-verification is expected to be needed, but per the project's own platform-parity standing rule this hasn't been directly re-run on the Mac yet.
