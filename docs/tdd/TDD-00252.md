# TDD-00252: Windows on libuv

- **Status**: Implemented
- **Date**: 2026-10-13

## Context

[TDD-00244](TDD-00244.md) moved the runtime's event loop onto libuv on Linux
and macOS (Stages 1–5). Its Stage 6, "Windows", is one paragraph: replace
`win32io.c`'s `select`, socket remapping and IOCP port with libuv's Windows
backend. Every stage before it left a Windows-only path behind:

- `loopsrc/loop.c` keeps a `select()` pass over 1024-bit sets (29 `_WIN32`
  branches): timers, signals, the pool, TCP, IPC, fs.watch, curl and the
  HTTP listeners each still have `*_fdset_add`/`*_dispatch`/`*_keepalive`
  hooks there (ADR-01385, 01389, 01392–01395, 01397, 01404).
- `timers.c` runs Node's timers and check phases from that pass.
- `fetch.c` drives libcurl through `curl_multi_fdset`.
- `klainpool.c` spawns through `CreateProcessW` in `win32proc.c`, not
  `uv_spawn` (ADR-01391), and reads stdio through the shim.
- `LocateUV` links nothing on Windows (`codegen/llvm/loop.go`).

So Windows carries a second event loop that Linux and macOS no longer test,
and its limits are its own: 512 socket descriptors, stdout writes to a pipe
that block, a child IPC channel over a loopback TCP pair framed by hand, and
no `server.listen(path)`. Node on Windows is libuv's Windows backend; the
closer this runtime is to it, the fewer of those differences remain.

libuv is in CI's Windows package list (`mingw-w64-ucrt-x86_64-libuv`) and on
the Windows dev box.

## Design

### What the POSIX side looks like

The POSIX loop watches descriptors, not libuv stream handles: `uv_poll_t` on
an fd for each TCP handle (`klainpool.c`), the HTTP listeners and the
bridge's remaining hooks (`loop.c`), `uv_timer_t` for timers, `uv_async_t`
for the pool wake, `uv_signal_t`, `uv_fs_event_t`, `uv_spawn`, and
`uv_tty`/`uv_pipe` for stdio. c-ares already polls with
`uv_poll_init_socket`.

### Option A — the POSIX loop on Windows, sockets by poll (chosen)

Compile the POSIX branches on Windows and give them what they need:

- **Sockets** stay shim descriptors for the code above (the `kml_tcp` table,
  `httpsrv.c`, `dgram`), and every `uv_poll_init(loop, h, fd)` becomes
  `kml_uv_poll_init(loop, h, fd)`: `uv_poll_init_socket` with
  `__kml_win_fd_socket(fd)` on Windows. libuv's Windows poll is AFD-based,
  the same mechanism the shim's own `IOCTL_AFD_POLL` uses, and has no
  descriptor ceiling. The shim's socket `read`/`write` become plain
  non-blocking Winsock calls: the overlapped zero-byte reads and the shim's
  completion port leave the socket path.
- **Timers, signals, pool wake, fs.watch** take the POSIX code unchanged:
  `uv_timer_t`, `uv_signal_t` (libuv delivers SIGINT, SIGBREAK, SIGHUP and
  SIGWINCH from console events, as Node does), `uv_async_t`,
  `uv_fs_event_t` (ReadDirectoryChangesW).
- **Child processes** go through `uv_spawn`, as on POSIX and as Node does:
  libuv's Windows spawn quotes arguments, searches `PATH`/`PATHEXT`, and
  gives `windowsHide`/`windowsVerbatimArguments`/`detached` their Node
  meaning. `win32proc.c`'s `CreateProcessW` path, its environment marker and
  its self-spawn marker move onto libuv's options (the marker into the
  child's environment, which `uv_spawn` takes as given).
- **stdio** is `uv_tty_t` for a console and `uv_pipe_t` for a pipe, as
  Node's `process.stdout` is; a write to a pipe no longer blocks the loop.
- **IPC** is a `uv_pipe_t` opened with `ipc = 1` over a named pipe, which
  carries sockets with `uv_write2` as Node's does; the shim's KMLH framing
  and `WSADuplicateSocketW` hand-off go.
- **curl** goes through its socket API (`CURLMOPT_SOCKETFUNCTION` →
  `kml_uv_poll_init`), the POSIX code in `fetch.c`.

What stays in the shim: the fd-level `fs` calls (`open`/`read`/`write`/
`stat` on files and the CRT), path translation, `errno` mapping, and the
socket calls by POSIX name. `win32io.c` loses `select`, the IOCP reactor,
the wake packets, the overlapped socket I/O and the pipe reader threads.

### Option B — libuv stream handles everywhere

Make each TCP handle a `uv_tcp_t` (and the HTTP listener a `uv_tcp_t`
listener) on every host. This is how Node is built, and it would remove the
socket remapping on Windows. It changes the POSIX code that Stages 4–5 just
finished and every consumer of the `kml_tcp` table (`net`, `dgram`, TLS,
HTTP/2, the HTTP server's connection fibers). Rejected for Stage 6: it is a
rewrite of the POSIX transport, not the Windows port; it can follow as its
own step once both hosts share one loop.

### Stages

Each stage leaves the full E2E suite green on Windows, and on Linux (Docker)
for anything shared.

1. **Link and loop core.** `LocateUV` finds the ucrt64 libuv (pkg-config,
   or `-luv` with `ws2_32`/`iphlpapi`/`userenv`/`dbghelp`/`ole32`), and
   `--static` links `libuv.a`. `loop.c` builds its POSIX loop on Windows;
   timers (`timers.c`), the pool wake and signals move onto their libuv
   handles. The bridge hooks keep running from the loop's prepare/check
   phase while their sources are still select-shaped.
2. **Sockets by poll.** `kml_uv_poll_init`; TCP, dgram, HTTP listeners and
   connections, curl's socket API. The shim's socket I/O stops using the
   completion port. The descriptor-ceiling tests run on Windows.
3. **Children and stdio.** `uv_spawn`; `uv_tty`/`uv_pipe` stdio; IPC as a
   libuv IPC pipe, with handle passing by `uv_write2`.
4. **fs.watch and the rest.** `uv_fs_event_t`; the bridge and every
   `_WIN32` hook branch in `loop.c` are deleted, and so are the parts of
   `win32io.c` listed above.

`server.listen(path)` is a named-pipe `uv_pipe_t` listener on Windows and an
AF_UNIX listener on POSIX; it is built after Stage 3, as its own ADR.

## Open questions

- **A socket on two completion ports.** A socket the shim associated with
  its own port cannot join libuv's; libuv's fast poll falls back to a peer
  socket. Stage 2 removes the shim's association, so a socket is only ever
  on libuv's port; check that no path still associates one.
- **Fibers under libuv callbacks on Windows.** Win32 fibers switched from
  inside a libuv callback: expected to work as ucontext does on POSIX; check
  with the coroutine tests in Stage 1.
- **`-mm=gc`** with libuv's threads on Windows (Boehm thread registration
  for libuv's thread pool): check in Stage 1.
