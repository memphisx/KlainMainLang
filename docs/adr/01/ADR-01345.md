# ADR-01345: `KeyObject`, and every key encoding, over OpenSSL

- **Relations**: Implements TDD-00230 (P3.2), Extends ADR-01300, ADR-01344
- **Date**: 2026-10-03

## Context

Backlog 152: `crypto` had no `KeyObject`. `generateKeyPair` refused to run
without `{ type: 'spki', format: 'pem' }` and `{ type: 'pkcs8', format:
'pem' }`. Keys were PEM strings only, an encrypted key was never
decrypted, and `sign`/`verify` took no `padding`, `saltLength` or
`dsaEncoding`. The TypeScript Web Crypto port waits on these primitives,
because Node's `SubtleCrypto` is written over `KeyObject`.

## Investigation

- Node's `lib/internal/crypto/keys.js` keeps a native `KeyObjectHandle`
  behind `SecretKeyObject`, `PublicKeyObject` and `PrivateKeyObject`.
  `createPrivateKey`/`createPublicKey` parse PEM, DER or JWK. `export`
  writes the same encodings back. Node was run as the oracle for every
  member order, detail and error: JWK orders, `prime256v1`, the
  `[object KeyObject]` tag, the `ERR_OSSL_*` codes, and the messages for
  bad options.
- The sign and verify natives already read PEM. So a canonical PEM
  (PKCS#8 for a private key, SPKI for a public one) can be the handle's
  material, and no new handle type is needed in C.
- OpenSSL 3's `OSSL_DECODER` and `OSSL_ENCODER` cover every structure Node
  names: PKCS#1, SPKI, PKCS#8 (encrypted too) and SEC1. The existing JWK
  bridge (`__kml_crypto_jwk_import_rsa`/`_ec`) builds RSA and EC keys from
  members.
- The port found five compiler bugs:
  1. Destructuring an overloaded call whose implementation returns `any`
     was "function call does not return an object".
  2. `x instanceof C` for `x` typed `C` folded to `true`, but the slot can
     hold null. A value that reached it through `any` is null there, as is
     `this` in a method called without a receiver.
  3. An `any` holding a number or string, passed to a class-typed
     parameter, was reinterpreted as a pointer. So `instanceof` passed and
     a private-field read crashed.
  4. `String(x)` and `` `${x}` `` of a class instance held in `any` ignored
     its `Symbol.toStringTag`, which `Object.prototype.toString.call`
     honoured.
  5. `util.inspect` printed `Name [Tag]` even when the class name contains
     the tag. Node omits it there (`SecretKeyObject {}`).

## Decision

1. **`KeyObject`, `SecretKeyObject`, `AsymmetricKeyObject`,
   `PublicKeyObject` and `PrivateKeyObject`** in `lib/node/crypto.ts`, after
   `keys.js`.
   - The handle is a module-private class holding a secret key's bytes or
     an asymmetric key's canonical PEM. `new KeyObject(type, handle)`
     rejects anything else, as Node rejects a non-`KeyObjectHandle`.
   - State is `#private`, so `inspect` shows `SecretKeyObject {}`.
2. **Natives** in `cryptosrc/crypto_openssl.c`, declared in
   `lib/native.d.ts`:
   - `key_parse`: any PEM/DER structure to the canonical PEM. A public key
     may come from a private one. A passphrase goes through the same PEM
     callback as Node's: none cancels the read, rather than prompting.
   - `key_export`: PEM or DER in each structure, with a cipher and
     passphrase.
   - `key_info`: the type and details, digest names as OpenSSL's long names
     (`sha256`).
   - `key_jwk` and `key_from_jwk`: RSA, EC and OKP, in Node's member order.
   - Each clears the error queue on entry, so a failure reports its own
     `ERR_OSSL_*`.
   - The commoncrypto backend gets stubs that fail. That backend is out of
     scope.
3. **Sign and verify** take a `KeyObject`, and `padding`, `saltLength` and
   `dsaEncoding`.
   - RSA padding and PSS salt are set on the signing context.
   - IEEE P1363 converts between DER and `r || s` for EC and DSA keys,
     which share the `SEQUENCE { r, s }` form.
4. **`generateKeyPair`** generates `rsa`, `rsa-pss` (with its hash, MGF1
   hash and salt restrictions), `dsa` (with its divisor length), `ec`,
   `ed25519`, `ed448`, `x25519` and `x448`.
   - Without an encoding a half is a `KeyObject`. With one, it is that
     half's `export`.
   - SPKI or PKCS#8 PEM is the native's own output and is returned
     directly.
5. **The compiler fixes:**
   - The object destructuring source takes an `any` call or await result
     through the dynamic path.
   - An ancestor-class `instanceof` tests the pointer for null.
   - A box with no pointer (a number, boolean, string, null or undefined)
     unboxed into a class slot is null. Every heap kind, streams included,
     keeps its pointer.
   - Dynamic ToString of an object is `Object.prototype.toString`
     (`__kml_object_tostring`).
   - Both inspect paths omit a tag that the constructor name contains.

## Implementation notes

- **Library:** `lib/node/crypto.ts` and `lib/native.d.ts`.
- **Natives:** `codegen/llvm/cryptosrc/crypto_openssl.c` (the natives,
  keygen kinds 4–7, the sign options) and `crypto_commoncrypto.c` (the
  stubs and the option checks).
- **Compiler:**
  - `codegen/llvm/emit_objects.go`: destructuring.
  - `emit_classes.go`: `instanceof`.
  - `emit_exprs_coerce.go` and `emit_narrowing.go`: class-slot unboxing.
    The narrowing arm is for class targets only. Applied to every object
    layout, it nulled a legitimate value in the fs `signal` path.
  - `emit_dynamic.go`: ToString.
- **Inspect:** `dynjsonsrc/dynjson.c` and `inspectsrc/inspect_reduce.c`.
- **Implementation signatures:** `equals` keeps an `any` implementation
  parameter behind its `KeyObject` overload, so the error names the value
  actually passed.

## Side effects discovered

Still open (backlog 152):
- ECDH and `diffieHellman`;
- `publicEncrypt`/`privateDecrypt`;
- `KeyObject.from(cryptoKey)`;
- AES-KW;
- `dh` key pairs;
- importing a `secp256k1` JWK.

A class-typed slot cannot hold a number. A value laundered through `any`
reads as null there (`typeof` is `object`), so library code that validates
its arguments declares them `any`.
