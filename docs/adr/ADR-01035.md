# ADR-01035: Windows — building under a non-ASCII directory, wide library loading, `node:ffi` tests un-skipped

- **Relations**: `Implements TDD-00164` (Windows), `TDD-00180` (§6); `Extends ADR-01019`
- **Date**: 2026-09-21

## Context

Three loose ends around loading code on Windows.

1. All eleven `node:ffi` E2E tests were skipped on Windows with the reason "POSIX-symbol-pinned", although the feature ships there (ADR-01019). Removing the skip showed they had **never run**: the test harness did not link the `LoadLibrary`-backed `dlopen` shim, the link failed, and the harness's "backend may not be installed" rule — meant for a missing bigint library — turned that failure into a skip.
2. `-dynamic-import=lazy` located and loaded its islands with `GetModuleFileNameA`/`LoadLibraryA`, and `node:ffi` loaded libraries with `LoadLibraryA`: a path outside the ANSI code page failed.
3. Writing the test for (2) found a bigger one: **a project in a directory with a non-ASCII name could not be compiled at all.** mingw's `ld` opens its output through the narrow file API and fails with `cannot open output file …: Invalid argument`.

## Investigation

`dlopen(NULL)` has no Windows equivalent; the shim's sentinel handle searches the CRT and core system modules. The POSIX names the UCRT only exports underscored (`getpid`, `strdup`, `fileno`, …) reach a C program through the import library's alias, so a process-image lookup that does not honour the same alias cannot find what the equivalent C program links against.

`clang` itself takes a wide command line and handles UTF-8 paths for the files it opens; only the linker's output is affected, so inputs may stay where they are.

## Decision

- `tests/compiler_test.go`: one `appendFFIDl` helper (link flags + the Windows shim) replaces thirteen copies of the flag-only block, mirroring `embedded_c.go` so the test build and the real build cannot drift. `skipFFIOnWindows` is deleted; `hostSuffix()` knows `dll`.
- The `dlsym` sentinel path retries `_name` in `ucrtbase`/`msvcrt` when `name` is not found.
- `dlopen` (ffi shim) and the island loader cross the wide boundary: UTF-8 → `LoadLibraryW`; `GetModuleFileNameW` → UTF-8.
- `llvm.RunClangLink`: on Windows, an output path with a non-ASCII character is linked to an ASCII-named temp file and moved into place (rename, or copy+remove across volumes). Used by the main link, the island links and the GUI re-link. If no ASCII temp location exists either, the link runs against the real path and reports the linker's own error.

## Implementation notes

`codegen/llvm/runtime_ffi.go`, `emit_dynimport.go`, `hostclang.go`, `main.go`, `tests/compiler_test.go`, `tests/ffi_test.go`, `tests/dynamic_import_test.go`.

## Side effects discovered

- The harness rule that converts a link failure into a skip whenever a bigint/crypto backend is in use can hide any link regression in such a test. It is what hid this one. Narrowing it (skip only when the backend's own library is what failed to resolve) is a test-infrastructure follow-up, not Windows work.
- A user whose **temp directory** is non-ASCII (a non-ASCII account name) still hits the linker limitation for the intermediate objects; `RunClangLink` covers the output path only.

## Verification

Windows 11 (26200): all eleven `TestE2EFFI*` tests run and pass (previously eleven silent skips); `TestE2EDynamicImportLazyNonASCIIPath` compiles and runs a lazy-island program inside `καλημέρα-日本` (it failed at link before `RunClangLink`, and would have failed at load before the wide loader). `go vet ./...` clean. Linux/macOS: `RunClangLink` is a pass-through off Windows; the new dynamic-import test is host-independent but was not run there.
