# ADR-00184: Computed class member names (TDD-00063 Stage 3)

- **Relations**: `Implements TDD-00063` (Stage 3). `Extends ADR-00182`. Mirrors [ADR-00066](ADR-00066.md) (object-literal computed keys, TDD-00012).
- **Date**: 2026-08-13

## Context

[TDD-00063](../tdd/TDD-00063.md) Stage 3 is computed class member names — `['foo']() {}`, `[0]() {}`, `['x']: T = v`. Before this, a `[` in class-member position was a parse error (`expected IDENT, got [` — 511 first-error class files). This compiler resolves member names **statically** (there is no runtime property-key evaluation, and no `obj[expr]` computed member access), so an arbitrary runtime-valued key is fundamentally out of scope; the tractable, genuinely-useful subset is a compile-time-constant key.

## Investigation

- Class members are named by a token consumed in `parseClassDecl`'s member loop; everything downstream (dispatch, fields, visibility, override/vtable, the Stage-2 async/generator handling) keys off that name string.
- Test262's own `computed-property-names/class/` tests confirm the [TDD-00061](TDD-00061.md) ceiling applies here too: `method/string.js` mixes a constant `['b']()` with a dynamic `[ID('d')]()` and asserts via `Object.getOwnPropertyNames(C.prototype)` — both the dynamic key and the reflection API are out of this static model's scope, so these tests won't flip regardless. Stage 3's value is therefore the real language feature (a constant computed name is legitimate code) plus unblocking the parse gate, not a conformance delta — the same justification as Stage 2b.
- The object-literal precedent ([ADR-00066](ADR-00066.md)) already parses `{ [expr]: v }`, but resolves the key at emit time; a class member needs its name at *parse* time, so the constant is resolved there instead.

## Decision

Support a **compile-time-constant string or numeric literal** computed name, desugared at parse time to the equivalent named member — `['foo']() {}` is exactly `foo() {}`, `[0]() {}` is a member named `0`, `['x']: T = v` a field named `x`. A non-constant key (identifier, call like `[ID('d')]`, `Symbol.*`, or a template with interpolation) is a clean, specific rejection.

Concretely, in `parseClassDecl`'s member loop: a `[` in name position parses the key expression, requires `]`, and passes the key through `constMemberName` (returns the text for a `StringLiteral`/`NumberLiteral`, else `ok=false`). On success a synthetic `IDENT` token carrying that text stands in for the member name, so **every** downstream path — plain/async/generator methods, fields with initializers, getters/setters, visibility, the static-`prototype` early error — applies unchanged. The `get`/`set` contextual lookahead was widened to also fire before a `[` so `get ['x']()` works.

## Implementation notes

- Whole change is parser-only: the computed branch in the member-name selection, the widened accessor lookahead, and the `constMemberName` helper. No AST node, no codegen change — the desugared name flows through the existing machinery.
- A computed name whose text is not a valid identifier (a numeric key `[1]`, or `['has-dash']`) is stored as a member with that literal name but is not reachable through this compiler's `.name` access syntax (there is no `obj[expr]` computed access) — the same define-but-not-dot-readable situation object-literal numeric/string keys already have ([ADR-00154](ADR-00154.md)). The common, useful case — a constant key that *is* an identifier (`['greet']()` → `.greet()`) — is fully usable.
- `static ['prototype']()` is correctly rejected: it desugars to the name `prototype`, which the Stage-2a static-`prototype` early error ([ADR-00181](ADR-00181.md)) already catches.

## Side effects discovered

- A computed key evaluating to `'constructor'` (`['constructor']() {}`) is treated as the class constructor, since it desugars to the name `constructor`. Real JS treats a *computed* `'constructor'` method as an ordinary method, not the constructor — a narrow divergence (exercised by Test262's `constructor-duplicate` computed-name tests, which are out of scope anyway for the reflection reasons above), left as a documented V1 limitation rather than special-cased.
- Well-known-symbol keys (`[Symbol.iterator]`) remain rejected: wiring them to a reserved slot only pays off with iteration-protocol integration this compiler's `for...of` (which uses the `next()` sentinel protocol, [ADR-00063](ADR-00063.md), not `Symbol.iterator`) doesn't have — a separate, larger effort with a ceiling-limited payoff, deliberately deferred.
