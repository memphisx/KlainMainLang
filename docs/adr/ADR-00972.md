# ADR-00972: Reject any self-spawn re-exec, not just interpreter flags

- **Relations**: `Extends ADR-00970`
- **Date**: 2026-09-16

## Context

ADR-00970 fixed a conformance memory blowup: a Node-test idiom
`spawnSync(process.execPath, ['-p', expr])` re-runs the compiled binary, which
has no interpreter mode, so it ignores the flag and re-runs its own program body
→ re-hits the same spawn → an unbounded self-fork chain. That fix added a startup
guard that rejects the binary when its argv carries an interpreter/eval flag
(`-p`/`--print`/`-e`/`--eval`/`-i`/`--interactive`).

Running the full Node conformance suite (both lanes) still drove RSS past the
reaper's mem-cap and left hundreds of live processes — the http family aborted at
500/742 with 382 lingering workdir processes. The guard was too narrow: a
self-spawned child **ignores its argv entirely and re-runs main**, so the flag
scan never fires for `spawnSync(process.execPath, ['some-non-flag-arg'])` (or a
script-path argument, the other common idiom). Because `spawnSync` blocks, this
is a *linear* fork chain rather than an exponential bomb — each level spawns one
child and waits — so it climbs RSS/process count steadily instead of exploding.

## Investigation

Reproduced directly: a program doing `spawnSync(process.execPath, ['somearg'])`
grew to **200 live processes in 5 seconds** (`pgrep -fc <binary>`), each blocked
in `spawnSync`'s `poll()` awaiting a child that never terminates — the exact
`main → __kml_cp_spawn_sync → poll` stack the prior session sampled. The flag
guard (`runtime_interp_guard.go`) never triggered because `'somearg'` matches
none of `-p`/`-e`/`-i`.

Why it surfaced now rather than a few commits ago: the self-re-exec is inherent
to a compiled binary the moment `process.execPath` became functional; it was
*exposed* when the conformance denominator switched to the full Node corpus
(TDD-00204, allowlist deleted), so Node's self-spawning test files compile and
run for the first time. The IR-error fixes are a secondary contributor (more node
files reach the spawn). ADR-00970 caught only one shape of the same root cause.

The general signal is available only at spawn time: the *target* is this
executable. argv sniffing at the child cannot distinguish a self-spawn from an
ordinary CLI invocation with arguments without false positives.

## Decision

Detect the self-spawn at the **parent** and mark the child, then reject on the
marker at startup regardless of argv:

- `spawnSync`'s C runtime (`runtime_spawnsync.go`) gains `kml_spawn_is_self(file)`
  — compares `realpath(file)` against this process's own executable path
  (`_NSGetExecutablePath` on macOS, `/proc/self/exe` on Linux). In the forked
  child, before `execvp`, if the target is self it `setenv("KML_KLAIN_REEXEC",
  "1", 1)`.
- The startup guard `@__kml_reject_node_interp_flags`
  (`runtime_interp_guard.go`) checks `getenv("KML_KLAIN_REEXEC")` first, before
  the flag scan, and takes the same `write(2)` diagnostic + `exit(9)` path when
  it is set. The recursion breaks at the first child.

This is precise: the marker is set only when the spawn target resolves to this
binary, so spawning a *different* program, and an ordinary CLI invocation of the
binary with its own arguments, are both unaffected (verified). It composes with
ADR-00970 — the flag scan stays for a human directly typing `mybin -p …`, which
carries no marker.

The behavior is the faithful one: `node <script/args>` on a binary that cannot
interpret scripts exits nonzero with a diagnostic, exactly as Node exits when
handed a flag it rejects — an honest failure instead of a fork chain.

## Implementation notes

- The self-detection + `setenv` is one shared C helper,
  `__kml_mark_child_if_self_spawn` (`runtime_reexec_guard.go`, linked via
  `UsesReexecGuard`), called in the forked child just before `execvp` on **both**
  spawn paths: the blocking `spawnSync`/`execSync`/`execFileSync` C
  (`runtime_spawnsync.go`) and the async `spawn`/`fork` fork+exec IR
  (`runtime_spawn_win.go`'s two `doexec` sites — `cpSpawnForkIR` and
  `execSyncForkIR`). `spawnSync` was the confirmed conformance vector (its
  `poll()` chain is what piled up); the async path is the same class and is
  covered here too rather than left open.
- The guard already runs at `main` start for any program that reads
  `process.execPath` (`ensureExecPath` → `ensureNodeInterpFlagGuard`), which is
  exactly the set of programs that can self-spawn, so no extra call-site wiring
  was needed.
- The test build path hand-mirrors the CLI's embedded-C list
  (`tests/compiler_test.go` `appendSpawnSync`); it gained the `reexecguard`
  source alongside `spawnsync`, or the async path would link-fail in tests only.

## Side effects discovered

- The conformance runner's `-out` flag does not redirect the Node lane's report
  (it still overwrites the canonical `CONFORMANCE-RESULTS-NODE.md`); throwaway
  probe runs must restore it from git afterward. Noted, not fixed here.

## Verification

- New E2E tests (`tests/childprocess_test.go`):
  `TestE2EChildProcessExecPathSelfSpawnRejected` (non-flag self-spawn → child
  `status: 9`, no recursion) and `TestE2EChildProcessSpawnOtherProgramUnaffected`
  (`/bin/echo` → `status: 0`); the ADR-00970 flag test still passes.
- Manual repro: the 200-processes-in-5s fork chain now stays at 0 live children;
  the child exits 9 and the parent's `spawnSync` returns cleanly.
- The bounded Node http-family conformance slice (742 files, `-workers 3`) that
  previously aborted at 500/742 (382 lingering processes, RSS over the cap) now
  **runs to completion** with no mem-cap abort and no orphaned processes.
- Both spawn paths verified: `spawnSync(process.execPath, ['nonflag'])` and
  `spawn(process.execPath, ['nonflag'])` both yield a child that exits 9 with no
  fork chain, while spawning a different program (`/bin/echo`, `printf`) is
  unaffected — `TestE2EChildProcessExecPathSelfSpawnRejected`,
  `TestE2EChildProcessAsyncSelfSpawnRejected`,
  `TestE2EChildProcessSpawnOtherProgramUnaffected`.
