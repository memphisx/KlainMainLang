# ADR-00191: `finally` runs on `return`/`break`/`continue`, not only on fall-through

- **Relations**: Fixes the finally-on-return bug flagged by [ADR-00166](ADR-00166.md)
- **Date**: 2026-08-13

## Context

A `finally` block only ran when control fell off the end of `try`/`catch`. A `return`, `break`, or `continue` inside the `try` or `catch` bypassed it entirely — so the single most common real use of `finally` (cleanup around an early `return`) silently didn't happen. Flagged by the 2026-08-11 audit ([ADR-00166](ADR-00166.md)): "`finally` does NOT run when the `try`/`catch` block itself returns."

The cause is structural: `emitTry` (`emit_exceptions.go`) emits the finally body **inline** at the merge block (`afterL`) that the normal success/caught paths branch to. A `return` inside the try body emits its own `ret` terminator, which sets `blockDone` — so the `br` to `afterL` is dropped as dead code and control never reaches the inline finally. Same for `break`/`continue`, whose `br` to the loop label likewise skips `afterL`.

## Decision

Track enclosing `finally` blocks on a stack and splice them in before any early-exit terminator:

- **`pendingFinallys [][]ast.Statement`** on the emitter — `emitTry` pushes `s.Finally.Body` before emitting the try body, and pops it just before the normal-path inline finally at `afterL`. So while emitting the try/catch, the stack holds every finally that an early exit must run.
- **`emitFinallysToDepth(depth)`** emits the pending finallys from the top down to `depth`, innermost first, each in its own scope. `return` runs all of them (`emitPendingFinallys` = depth 0, the function boundary); `break`/`continue` run only those nested since their target loop/switch.
- **Loop/switch depth tracking** — `pushBreakTarget`/`pushContinueTarget` record `len(pendingFinallys)` at loop entry alongside the break/continue label (and `namedLabel` gains a `finallyDepth` for labeled break/continue), so a `break`/`continue` unwinds only to its own loop, never running a finally that sits *outside* the loop.

### Semantics this gets right

- **Value captured before finally**: `emitReturn` computes the return value into a register first, then runs the finallys, then emits `ret` — so `try { return x } finally { x = 99 }` returns the original `x` (a later scalar write in finally can't change an already-captured value).
- **Abrupt completion in finally wins**: while emitting finally *i*, the active pending stack is narrowed to the finallys outside it, and if that finally has its own `return`/`break`/`continue`, its terminator sets `blockDone` and the original pending exit is dropped — so `try { return 1 } finally { return 9 }` returns `9`, matching JS.
- **Nesting / innermost-first**: `try { try { return } finally { A } } finally { B }` runs `A` then `B`.
- **The throw path is unchanged**: a caught throw still reaches `afterL` and runs the inline finally as before; the fall-through path runs it exactly once.

### Scope

Ordinary functions only. `async`/generator functions return through their own coroutine paths (`coroRetLabel` / `emitGeneratorReturn`) and don't consume `pendingFinallys`; finally-on-early-exit inside an `async`/generator body stays as-is (deferred), since those need the finally spliced into the suspend/resume machinery, not a plain inline emit.

## Verification (Linux, x86-64)

- `return` in try → finally runs; `return` in catch → finally runs; `return` in finally overrides; nested finallys run innermost-first; value captured before finally; `break`/`continue` (labeled and unlabeled) run the loop-nested finally but not an outer one; a caught throw still runs finally once; plain fall-through runs it exactly once.
