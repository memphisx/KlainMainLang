# ADR-00890: `++`/`--` and unary `-` reject a non-numeric operand cleanly (invalid-IR sweep)

- **Date**: 2026-09-12

## Context

`++`/`--` on a non-numeric binding and unary `-` on a non-number emitted invalid
IR: `var x = {}; ++x` produced `add ptr %x, 1`, and `-""` produced `sub ptr 0,
<str-gep>` — both `error: integer constant must have integer type` from clang.
Part of the `integer constant must have integer type` bucket in the 2026-09-12
strict invalid-IR faillist; the operand-type families
`prefix/postfix-{increment,decrement}/S11.{3,4}.*_A{3,4}_T5` and
`unary-minus/11.4.7-4-1` (e.g. Test262 `var x = {}; ++x` expecting
`ToNumber({}) === NaN`).

## Investigation

`emitUpdate` (`emit_exprs_operators.go`) loaded the operand and emitted `add/sub
<sym.Ty.IR> …, 1` unconditionally after its bigint and nullable-scalar branches;
for a `ptr`-typed operand (string/object) `sym.Ty.IR` is `ptr`, so `add ptr, 1`
is invalid. `emitUnary`'s `-` case likewise did `sub <arg.Ty.IR> 0, …` in its
non-float `else`, invalid for a `ptr` operand (its bigint and `-compat=js`
dynamic-ToNumber branches already ran earlier). Binary `/`/`%` on a string
already reject cleanly, so only `++`/`--`/unary-`-` were emitting invalid IR.
tsc rejects all of these (an arithmetic operand must be number/bigint/any), so a
clean rejection is the faithful strict behavior — not a scope cut.

## Decision

Guard both sites on a numeric operand. `emitUpdate`: after the bigint/nullable
branches, reject when `!sym.Ty.Float && !sym.Ty.IsInteger()` (i.e. a `ptr`/void/
aggregate operand) with `operator '++'|'--' requires a number or bigint
operand`. `emitUnary` `-`: split the non-float arm into `IsInteger()` (the
existing `sub 0, x`) vs everything else (the same clean rejection). `IsInteger()`
already excludes `ptr`, so exactly the invalid-IR operands are rejected; number,
float, bigint, and boolean operands are unchanged, and the `-compat=js`
dynamic-ToNumber path (a separate gap) still runs before this guard.

## Implementation notes

- Minimal and targeted: the guard rejects only the `ptr`/aggregate operands that
  produced invalid IR. A boolean (`i1`) operand stays allowed (pre-existing,
  not invalid IR); full ToNumber-on-boolean/string semantics under `-compat=js`
  remain the broader operator-on-any compat=js item.
- Member/index update targets (`obj.x++`) desugar to a compound assignment
  (`emitTargetUpdate`) and are unaffected here.

## Side effects discovered

- The `integer constant must have integer type` bucket is heterogeneous: this
  ADR closes the `++`/`--`/unary-`-` operand-type sub-family. Remaining in the
  bucket and deferred: `parseInt`/`parseFloat`/`padEnd`/`indexOf` non-string
  arguments (a ToString-or-reject arg family), a generator `yield*`-spread
  state-field zero-init (`store {ptr,i64} 0` from the generator sent-value/reset
  path — a distinct generator-internals codegen bug), and `==`/`!=` on
  incompatible types (abstract-equality semantics, separate).

## Verification

- Repros now reject cleanly (not invalid IR): `++{}`, `s++` (string), `-""`,
  `-{}`. Numeric `++`/`--`/unary-`-` (int and float) and bigint `++` unaffected.
- The sampled Test262 files (`prefix-increment/S11.4.4_A3_T5`,
  `postfix-decrement/S11.3.2_A3_T5`, `prefix-decrement/S11.4.5_A4_T5`,
  `unary-minus/11.4.7-4-1`) reclassify CLANG_ERROR → clean COMPILE_ERROR.
- New `TestE2EUpdateNonNumericOperandRejected`; operator/expression suites
  green; `go build`, `go vet ./...`, gofmt clean; full `make test-par` gate run.
