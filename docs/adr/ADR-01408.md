# ADR-01408: fetch above descriptor 1024 on macOS

- **Relations**: Extends ADR-01397
- **Date**: 2026-10-05

## Context

Since libcurl runs through its socket API on libuv watchers
([ADR-01397](ADR-01397.md)), the loop has no `FD_SETSIZE` ceiling. macOS's
own libcurl still has one: it is built to wait with `select()` (poll() is
not trusted on macOS), so it refuses any socket at or above `FD_SETSIZE`
(1024). A program holding more than 1,024 descriptors (one raised `ulimit
-n` past the macOS default of 256) got "Couldn't connect to server" from
every `fetch`. Node's own HTTP client has no such limit.

## Decision

- On macOS, when the descriptor limit at startup exceeds `FD_SETSIZE`,
  `fetch.c` reserves up to 32 low descriptors (`/dev/null`, close-on-exec)
  in a constructor, while the low numbers are still free.
- Every transfer opens its sockets through `CURLOPT_OPENSOCKETFUNCTION`: a
  socket that lands at or above `FD_SETSIZE` is moved (`dup2`) onto a
  reserved number. `CURLOPT_CLOSESOCKETFUNCTION` points a reserved number
  back at `/dev/null` and returns it to the reserve instead of closing it.
- Up to 32 sockets can be open above the limit at once; past that a socket
  stays where it landed and libcurl refuses it, as before.

## Verification

- Mac (M4): `TestE2ELoopFetchAbove1024` (1,100 descriptors open, then a
  `fetch` to the program's own server) now runs on macOS instead of
  skipping, and passes; the same program built before this change fails
  with "Couldn't connect to server".
- Linux (x86-64, Ubuntu 24.04 container), with ADR-01406 to ADR-01409: the
  full test suite (3,927 tests), the 393 examples, and Test262 in both lanes
  (strict 8,498, js 10,506, unchanged, no invalid IR).
