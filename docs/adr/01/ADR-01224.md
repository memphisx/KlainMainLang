# ADR-01224: String.fromCharCode and fromCodePoint encode UTF-8

- **Relations**: `Implements TDD-00230`
- **Date**: 2026-09-29

## Context

`String.fromCodePoint(241)` produced the single byte `0xF1`, which is not
valid UTF-8: every code was truncated to one byte. `"ñ".codePointAt(0)`
was `195`, the first byte of its UTF-8 form. A punycode port hit both.

## Investigation

- Strings are UTF-8 byte sequences, and positions are byte offsets
  (ADR-00028; the byte-model caveats in the string status page). Within
  that model a code point can still be encoded and decoded exactly.
- Node: `fromCharCode` takes each argument's ToUint16 and a surrogate pair
  forms one character. `fromCodePoint` throws
  `RangeError: Invalid code point <n>` for a value that is not an integer
  in [0, 0x10FFFF].

## Decision

- `@__kml_String_fromCodes` (the casemap C file) encodes the arguments as
  UTF-8. For `fromCharCode` it applies ToUint16 and joins a high/low
  surrogate pair into its code point; an unpaired surrogate is encoded as
  itself. `fromCodePoint` validates and throws Node's RangeError.
- `codePointAt(i)` decodes the UTF-8 character starting at byte `i`; a
  byte that starts no valid sequence reads as itself.

## Implementation notes

`codegen/llvm/emit_strings.go`, `casemapsrc/casemap.c`,
`stringsrc/string.c`, `emitter.go`.

## Side effects discovered

- `.length`, `.charCodeAt` and indexing stay byte-based: that is the
  string representation itself, recorded in the status caveats.

## Verification

Mac (Apple Silicon), against Node v24.19: `TestE2EStringFromCodePointUTF8`.
