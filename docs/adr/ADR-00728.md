# ADR-00728: Windows signal delivery — Ctrl+C/Ctrl+Break reach `process.on`, `SIGBREAK`, and the reactor wakes for them

- **Relations**: Extends [ADR-00727](ADR-00727.md) (the pseudo-console harness; recorded this as a side effect), [ADR-00719](ADR-00719.md) (Windows Stages 1–4: console control handlers, SIGTERM never fired), [ADR-00079](ADR-00079.md) (`process.on` signal handlers, TDD-00019); implements [TDD-00177](../tdd/TDD-00177.md) (the Signals catalog row)
- **Date**: 2026-09-06

## Context

ADR-00719 wired `process.on('SIGINT')`/`('SIGHUP')` to `SetConsoleCtrlHandler` and recorded that the six signal tests skip on Windows because Go's `os.Process.Signal` cannot raise SIGINT there. The pseudo-console harness of ADR-00727 can: a terminal raises SIGINT on Windows by pressing Ctrl+C, and the harness stands in for the terminal. Running the six programs that way showed the handlers never ran — a program with a `process.on('SIGINT')` listener kept running after Ctrl+C, whether it was waiting in the `http.listen` reactor or in a 100-second `setInterval`. The console-handler path had only ever been exercised at a real console by hand, on a program with short timers.

## Investigation

Three separate problems, found in this order:

1. **Ctrl+C never reached the child.** A process started in a new process group has Ctrl+C *disabled*, and that attribute is inherited by its children; `go test` and MSYS2's bash both start their children that way. Every route tried — 0x03 on the pseudo-console's input, the win32-input-mode key encoding, and `GenerateConsoleCtrlEvent` after `AttachConsole` — generated the event, and the child (even `ping.exe`) ignored it. `SetConsoleCtrlHandler(NULL, FALSE)` in the harness before the spawn restores normal processing for the child. A user's terminal never starts a program with it disabled, so this is a harness matter, not a runtime one. Windows Terminal sends Ctrl+C in the *win32-input-mode* encoding once the console has asked for it (the `?9001h` the pseudo-console emits at start-up), so that is the encoding the harness uses: a bare 0x03 becomes a plain character under that mode.
2. **The handler set a thread-local flag on the wrong thread.** `__kml_sig_handler` stores into `@__kml_sigint_pending`, which is `thread_local` (each worker thread has its own reactor and polls its own copy). A POSIX kernel runs the handler on the main thread, so the main reactor sees the flag; Windows runs the console control callback on a thread of its own, whose TLS nobody polls. The listener therefore never fired — not even in a program with short timers, which had made the by-hand check look good only because Ctrl+C with no *effective* handler still ends the process.
3. **Nothing interrupted the wait.** On POSIX a signal interrupts `select()`/`nanosleep()` with `EINTR`, which is when the reactor re-checks its pending flags; the Win32 shim's `select` blocked in Winsock `select` with no timeout, and `nanosleep` in a single `Sleep`. Even with the flag on the right thread, an idle server would have noticed Ctrl+C only on its next socket event.
4. **Ctrl+Break was SIGINT.** libuv maps `CTRL_BREAK_EVENT` to `SIGBREAK`, a distinct Node event, not to SIGINT; ADR-00719's shim folded both into signal 2. Node accepts a `'SIGBREAK'` listener on every host and only Windows ever raises it.

`process.kill(pid, 'SIGTERM')` on Windows terminates the target unconditionally, handler or not (libuv's `uv_kill` is `TerminateProcess`); `node` on this machine confirms: the listener never runs, nothing after the call executes, exit code 1. That part of ADR-00719 stands.

## Decision

- **Delivery on the installing thread** (`win32proc.c`): the control handler no longer calls the IR handler. It queues the signal (`kml_sig_queued[sig]`), raises a process-wide wake flag, and returns `TRUE` (for a close/logoff/shutdown event it also sleeps a few seconds so the SIGHUP listener gets its turn before the system ends the process). `__kml_win_sig_deliver()` runs the queued handlers — on the thread that installed them (the main thread, recorded in `signal()`) and on no other; it is called from the shim's waits, so the IR handler stores its flag in the main thread's TLS exactly as on POSIX.
- **Interruptible waits**: while a console handler is installed, `select()` (win32io.c) caps its wait at 50 ms slices and `nanosleep()` (win32shim.c) at 50 ms sleeps; each slice calls `__kml_win_sig_deliver()`, and a delivery ends the wait with `EINTR` (`nanosleep` fills `rem`). The IR already handles `EINTR` on both calls (it must, for POSIX signals — `TestE2ETimerNotPrematurelyFiredBySignal` exists for that path), so no emitter change was needed. Worker threads' waits leave the queue alone.
- **`SIGBREAK`**: `process.on('SIGBREAK', …)` is accepted on every host (a fourth flag/closure pair on the existing machinery, checked after SIGWINCH in both loops); only a Windows build registers signal 21 (libuv's number) with the shim, whose handler maps `CTRL_BREAK_EVENT` to it. An event with no listener returns `FALSE`, so the console's default action applies, as in Node.
- **Tests** (`tests/signals_windows_test.go`, all under the pseudo-console): the Windows variants of the six skipped tests — SIGINT graceful shutdown for an `http.listen` server and for a `setInterval`-only program (plus the 100-second interval not firing early), SIGINT-only when both listeners are registered, the no-listener default (exit `STATUS_CONTROL_C_EXIT`), `process.kill(pid, 'SIGTERM')` terminating unconditionally with exit 1 — and `SIGBREAK` firing on Ctrl+Break without touching the SIGINT listener. The POSIX tests keep their skip on Windows; the harness is the faithful replacement, not a rewrite.

## Implementation notes

- `codegen/llvm/win32src/win32proc.c`: the queue, `__kml_win_sig_deliver`, the installing thread id, the CTRL_BREAK→21 and CLOSE/LOGOFF/SHUTDOWN→1 mapping.
- `codegen/llvm/win32src/win32io.c`, `win32shim.c`: the sliced waits and `EINTR`.
- `codegen/llvm/runtime_process.go`: `@__kml_sigbreak_pending`/`_closure`, the handler's `checkbreak` arm, `ensureSignalRegisteredSigbreak`; `emit_process.go`: the `'SIGBREAK'` case and the accepted-names message; `emit_timers.go` / `runtime_http.go`: the `checksigbreak` block after `checksigwinch` in both loops.
- `tests/conpty_windows_test.go`: `pressCtrlC` (the win32-input-mode Ctrl+C), the Ctrl+C re-enable before the spawn, `runInConPTYArgs` for a command line with arguments.
- The shim cache directory is keyed by the shim sources' hash, so every program built after this change links the new objects.

## Side effects discovered

- Writing 0x03 to a pseudo-console's input produces no `CTRL_C_EVENT` on this Windows build (26100) once win32-input-mode is on; recorded in the harness so nobody retries it.
- The `readlink`/`atoi` declaration collision noted in ADR-00719 is fixed in [ADR-00731](ADR-00731.md); `process.kill` with a signal *name* did not compile — [ADR-00729](ADR-00729.md).

## Verification

Windows 11 x86-64: `go test ./tests -run TestE2ESignal` — the six POSIX tests skip as before, the seven console-backed tests pass (each in under 2 s: the handler fires within one 50 ms slice). `ping.exe` under the harness now exits with `0xC000013A` on Ctrl+C, the reference for "the event was generated". The full Windows suite and the Linux lane are recorded in [ADR-00731](ADR-00731.md).
