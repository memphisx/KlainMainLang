# ADR-00650: `Array.of` / `new Map(entries)` heterogeneous inputs reject cleanly instead of emitting invalid IR

- **Relations**: none
- **Date**: 2026-09-03

## Context

A leverage histogram of the pre-existing invalid-IR backlog (the Test262
`CLANG_ERROR` files — emitted LLVM IR that `clang` rejects, i.e. a codegen
bug rather than an out-of-scope feature) surfaced a family of files where a
scalar is stored raw into a pointer-typed slot: `store ptr 0x3FF0000000000000`
(a boxed `1.0`), `store ptr 0` (a `false`). Two of the reproducers were
builtins that construct an array/map from mixed-typed elements:

- `Array.of(undefined, false, null, undefined)` — `emitArrayOf` inferred the
  element type from the first argument (`undefined` → a `ptr` slot) and then
  `coerce`d the rest to it *silently*, storing `false` as `store ptr 0`.
- `new Map([['foo', 'bar'], [1, 1]])` — `mapKVTypes` inferred `key`/`value`
  types from the *first* entry pair (`string`/`string`) and hinted every later
  pair to that tuple shape, so `[1, 1]`'s numbers stored as `store ptr 0x3FF…`.

An array/tuple *literal* with the same shape (`[1, 'x']`, `[undefined, false]`)
is already a clean compile error — `emitArrayLiteralData` guards
`val.Ty.IR != elemTy.IR` and rejects "array elements must share one type". The
two builtins simply bypassed that guard. A truly heterogeneous array needs
`any[]` (a NaN-boxed `i64` element slot), which this compiler does not yet
support and rejects explicitly at the annotation level; until then the faithful
interim behavior is the *same* clean rejection, not invalid IR.

## Decision

Mirror the array-literal homogeneity guard in both builtins:

- `emitArrayOf` (codegen/llvm/emit_arrays_iter.go): after coercing each argument
  to the first-argument element type, reject when
  `val.Ty.IR != elemTy.IR && !elemTy.IsArray && !elemTy.IsDynamic &&
  !isNullableScalar(elemTy)` — the identical exemption set the literal path
  uses (composite element types legitimately carry a different storage IR).
- `resolveMapEntriesArray` (codegen/llvm/emit_collections.go): in the existing
  per-pair validation loop (which already rejects non-2-element pairs), also
  reject a pair whose inferred key or value type's IR differs from the
  first-pair-derived `keyTy`/`valTy` (same exemptions).

Homogeneous `Array.of(1, 2, 3)` / `Array.of('x', 'y')` and
`new Map([['a','b'],['c','d']])` / `new Map([[1,10],[2,20]])` are unchanged.

## Investigation

The histogram's fp/int-constant `CLANG_ERROR` sub-bucket (73 files) is *not* one
bug — most are other scalar-into-ptr sites (a number passed to `str.indexOf`, a
number stored into an untyped `var` reassigned across types via `??`/`||`).
This ADR closes only the two construction-builtin holes; the dominant remaining
sub-family — an untyped `var` that holds mixed types across reassignments —
needs proper `any` for untyped `var`, a larger item recorded separately as
future work, not folded in here.

## Side effects discovered

None. The guards fire only on inputs that previously produced invalid IR;
every homogeneous input already type-checked identically.

## Verification

- `tests/collections_test.go`: `TestE2EMapFromHeterogeneousEntriesRejected`,
  `TestE2EArrayOfHeterogeneousRejected` (both reject the mixed forms and keep
  the homogeneous forms compiling and running).
- `go build`, `go vet`; the two former reproducers now emit a clean codegen
  error; collections/arrays suites green. Mac (Apple Silicon).
