# ADR-00126: WebSocket Stage 1 — server-side upgrade + persistent echo loop

- **Relations**: Implements TDD-00039 (Stage 1 of 4 — Stage 0 was ADR-00125; Stages 2-3 remain)
- **Date**: 2026-08-08

## Context

[TDD-00039](../tdd/TDD-00039.md)'s Stage 1 adds the first user-visible slice of WebSocket support: `http.listen(port, handler, { ws })` — an optional third-argument handler called once per successfully upgraded connection, given a `WSConnection` with `.onmessage`/`.send()`/`.close()`. Stage 0 ([ADR-00125](ADR-00125.md)) built the frame codec and SHA-1 with no way to reach them from TypeScript at all; this stage wires them into `http.listen`'s existing per-connection fiber.

## Investigation

Confirmed directly against `emit_http.go`/`runtime_http.go` before implementing (TDD-00039's own Context section had already done a first pass; re-verified precisely against the current code since line numbers/exact shapes matter for a change this embedded in existing control flow):

1. **A WS upgrade request has no body**, and `buildHTTPDispatcher`'s existing Content-Length-aware body-wait (`checkBodyCompleteL`) already falls through to `parseL` once headers are found and `Content-Length` defaults to 0 — no special-casing needed to skip the body wait, contrary to what TDD-00039's Design section speculated. The upgrade check could simply live at the top of `parseL`, right after `headersMapFinal` is loaded (`emit_http.go`, previously line 667) — verified by testing directly rather than trusting the original design guess.
2. **`fd32`/`fd64`/`fdPtr`/`ctxPtrSlot`, computed once at the top of the current pass through `readLoopL`, remain valid (dominate) all the way through `parseL`/`noReqL`** — an invariant `buildHTTPDispatcher`'s own doc comment already documents ("since no further yield happens once the request is fully buffered"). Confirmed this still holds for code inserted at the very top of `parseL`, before any of the existing body-extraction logic — safe to pass these Go-side register-name strings directly into new helper functions.
3. **A missing `Sec-WebSocket-Key` reuses the existing `noReqL` cleanup label** (close + mark fiber slot done + decrement `@__kml_conn_active`) rather than duplicating that three-instruction pattern a third time — `noReqL` was already a Go-side variable in scope at the insertion point.
4. **Object-literal-field arrow functions don't get hint-based parameter inference** the way a field *assignment* does (`emitExprWithObjectHint`, `emit_exprs_assign.go:286`) — confirmed by reading `emitHTTPListen`'s own existing second argument (`handler`), which has always required an explicit `(req: Request): Res => {...}` annotation with no hint-injection mechanism. This settled the `ws` handler's own API shape: require `(socket: WSConnection) => {...}` explicitly too, rather than building new hint-propagation machinery for one argument.
5. **`.onmessage = (ev) => ...}` assigned *inside* the `ws` handler body does NOT need the same treatment** — a `MemberExpression` assignment target's declared field type is already threaded through as a hint (`emit_exprs_assign.go:286`), the same mechanism `EventSource.onmessage` already relies on. Confirmed by checking `examples/eventsource/eventsource.ts`, which assigns `messages.onmessage = (ev) => ...` with zero annotation and works. This meant `WSConnectionType()`'s `onmessage` field needed no dedicated codegen at all — free correctness from an existing generic mechanism.
6. **A real, reproduced dominance-adjacent bug was found and fixed during manual end-to-end testing** (see Decision below) — but it turned out to be in the *test client*, not the compiler. Worth recording precisely since it consumed real debugging time: a hand-written Python WebSocket test client's `send_text_frame` helper computed `0x80 | len(payload)` unconditionally, silently corrupting any payload over 125 bytes instead of switching to the 16-bit extended-length form. Diagnosed by adding temporary `printf` instrumentation into the generated IR (`nReg`/`avail`/`payloadLen` at each stage of the read/decode loop) and tracing the exact byte counts back to the client's malformed frame header, not the server's decode. A dedicated Go-level test client (`tests/websocket_test.go`'s `wsSendText`) was written afterward with correct RFC 6455 length-form handling from the start, verified against the same 300-byte case.

## Decision

Implemented per TDD-00039's Design section, with the one correction from Investigation item 1 (no body-wait skip needed):

- **Detection** (`emit_websocket.go:37`, `emitWSUpgradeDetect`): case-insensitive `Upgrade: websocket` (value lowercased via the existing `__kml_tolower`, then `strcmp`) and `Connection: ...upgrade...` (lowercased, then `strstr` substring check, since it's a comma-separated token list) against the already-parsed, already-lowercased-key headers map. Only emitted at all when the call site passed a `ws` handler (`hasWSHandler`), so a program without one pays zero extra branches — verified via `emit_http.go`'s `buildHTTPDispatcher` signature gaining a `hasWSHandler bool` parameter threaded from `emitHTTPListen`.
- **Handshake** (`emit_websocket.go:103`, `emitWSHandshakeAndLoop`): `Sec-WebSocket-Key` + GUID → `__kml_ws_sha1` → the new length-aware `__kml_base64_encode_bytes` (see below) → hand-written `101 Switching Protocols` response via `write()` directly (not `__kml_http_send_response`, whose status+body shape doesn't fit a bodyless fixed-status response).
- **New prerequisite found and fixed**: `__kml_btoa` is strlen-based, unsafe on a raw 20-byte SHA-1 digest that can legitimately contain an embedded `0x00` byte — exactly the gap ADR-00125 flagged as a real follow-on needed before any real handshake could ship. Added `ensureBase64EncodeBytes`/`__kml_base64_encode_bytes(ptr, i64)` (`runtime_encoding.go`), the same algorithm with an explicit length parameter instead of `strlen`, sharing the existing `@__kml_base64_alphabet` table (factored into its own idempotent `ensureBase64Alphabet` so both encoders can coexist in one compile without a duplicate-symbol error).
- **`WSConnection` object** (`types.go`): a hidden `WSConnFdField` (i64, the raw fd copied once at handshake time — deliberately not a pointer back into `@__kml_conn_data`, which can itself move on `realloc`) plus a visible `onmessage` field, modeled directly on `EventSourceType()`.
- **Persistent loop** (`emit_websocket.go:193`, `emitWSServerLoop`): reuses `buildHTTPDispatcher`'s own `swapcontext`-yield-on-`EAGAIN` pattern, with fd/ctx re-derived fresh at the top of every pass (never reused across a yield) exactly like the HTTP read loop already does, and its own growable accumulator (allocas, not bare registers, for everything that must survive a yield — `wsBufPtrA`/`wsBufCapA`/`wsTotalReadA`/`wsConsumedA`/`wsConnObjA`). Each decoded text/binary frame is copied into a freshly null-terminated string and dispatched to `.onmessage` (if set); a close frame or a protocol-error decode status ends the loop; ping/pong/unknown opcodes are silently skipped (their payload leaked — small, bounded, matching this project's existing manual-mode posture elsewhere) — no auto-pong yet, a real Stage 1 gap Stage 2 closes.
- **`.send()`/`.close()`** (`emit_websocket.go:453`/`505`): `.send(data: string)` only (no binary send yet) — a single unmasked text frame (server→client MUST NOT mask). `.close()` just closes the raw fd; the read loop's own existing error handling (an already-closed fd fails `read()` with `EBADF`, routed the same as any other non-`EAGAIN` error) naturally ends the connection on its next pass — no new state needed.

## Implementation notes

- Files touched: `codegen/llvm/types.go` (`IsWSConnection`, `WSConnFdField`, `WSConnectionType`/`WSMessageEventType`, `VisibleFields`/`ResolveTypeName` entries), `codegen/llvm/runtime_encoding.go` (`ensureBase64Alphabet`/`ensureBase64EncodeBytes`), `codegen/llvm/runtime_http.go` (`@__kml_listen_ws_handler` global), `codegen/llvm/emit_http.go` (`emitHTTPListen`'s third-argument handling, `buildHTTPDispatcher`'s new parameter and upgrade-check insertion), `codegen/llvm/emit_websocket.go` (new file), `codegen/llvm/emit_call.go` (`.send()`/`.close()` dispatch), `codegen/llvm/emitter.go` (new idempotency flags).
- `{ workers: N }` and `{ ws }` are independent, coexisting fields on the same options object — `emitHTTPListen` validates each present field independently and only errors if *neither* is present.
- Every value in `emitWSServerLoop` that must survive a `swapcontext` yield is an explicit `alloca`, never a bare SSA register — the same invariant `buildHTTPDispatcher`'s own HTTP read loop relies on (a callee-saved register isn't guaranteed to survive arbitrary code running on a different stack while this fiber is suspended; this fiber's own stack memory is).
- Verified the "does `wsEndL`'s reused `fd32`/`fdPtr` register dominate every predecessor" question explicitly (Stage 0's own encode bug made this worth double-checking carefully): every path into the decode cluster (`decodeLoopL`/`gotFrameL`/`checkOpcodeL`/`dispatchL`/`callOnMsgL`) structurally passes through `readLoopL`'s own fd/ctx computation first, even across `decodeLoopL`'s own multi-frame self-loop — unlike Stage 0's bug, there's no graph-structural path that bypasses the defining block entirely.

## Side effects discovered

- The strlen-unsafe `__kml_btoa`-on-a-binary-digest gap ADR-00125 flagged is now fixed (see Decision) — not left open.
- No fragmentation, no `wss://`, no ping/pong, no proper close handshake, binary `.send()` — all pre-existing, documented TDD-00039 scope cuts, unchanged by this stage.
- Ping/pong/unknown-opcode frames leak their decoded payload buffer (never freed) — small (one frame) and bounded, consistent with this project's existing "manual mode doesn't free most transient allocations" posture elsewhere (e.g. header-lowercasing buffers in `ensureHTTPParseHeaders`), not a new regression pattern.
