# TDD-00022: Best-effort vanilla JavaScript compatibility (opt-in)

- **Status**: Not Started
- **Date**: 2026-07-31

## Context

Found by directly testing plain, untyped JavaScript against the compiler
(not assumed): six representative snippets, four distinct failure shapes.
`var`/no-semicolons/plain loops compile and run unchanged (TypeScript is a
syntactic superset of JS, and this compiler's parser accepts the plain-JS
subset of that grammar already). But idiomatic JS breaks on four separate,
independent things, confirmed with real compiler output:

1. **Class fields assigned only in the constructor, never pre-declared** —
   `class Point { constructor(x, y) { this.x = x; this.y = y; } }` →
   `codegen error: no field 'x'`. This compiler's class field layout is
   fixed at compile time from explicit `x: type;` declarations
   ([TDD-00009](TDD-00009.md) Stage 1) — a syntax vanilla JS class bodies
   don't have at all (JS either assigns fields ad hoc in the constructor,
   the case that breaks, or uses untyped `x;`/`x = v;` class-field syntax,
   which this compiler also has nowhere to put a type for).
2. **Unannotated function parameters called with non-numbers** —
   `function greet(name) { return "hello " + name }` → a clean rejection
   ("has no type annotation (defaults to number) but was called with a
   non-numeric argument here"), already the deliberate, documented behavior
   from [ADR-00042](../adr/ADR-00042.md)/[TDD-00005](TDD-00005.md).
3. **Prototype-based pre-ES6 "classes"** —
   `function Animal(name) { this.name = name }; Animal.prototype.speak =
   function() {...}` → `parse error: unexpected token function in
   expression`. No prototype chain concept exists anywhere.
4. **Dynamic property addition on a plain object literal** —
   `const obj = { x: 1 }; obj.y = 2;` → `codegen error: no field 'y'`.
   Objects are fixed-shape heap structs decided at the literal's own
   declaration.

The user's own framing going in was that a naive "just treat every
unannotated thing as `any`" approach would be "terrible for the compiler."
That instinct is correct, and worth confirming precisely rather than just
agreeing by feel: the `any`/`unknown` runtime
([ADR-00008](../adr/ADR-00008.md)) is explicitly "Staged V1" and already
**rejects arithmetic and most operators on a dynamic value at compile
time** — [TDD-00010](TDD-00010.md)'s own generics-via-type-erasure option
already hit and documented this exact wall (`function add<T>(a: T, b: T):
T { return a + b }` fails under erasure today for the identical reason). A
hypothetical "everything unannotated becomes `any`" mode wouldn't let
`function add(a, b) { return a + b }` — about as basic as untyped JS
gets — compile at all, unless `any`'s operator support were *also*
broadened first, which is itself a separate, large, undesigned piece of
work. Boxing everything as `any` isn't a shortcut to JS compatibility here;
it would make almost nothing work.

## Design

Four independent sub-problems, since they have different costs and
mechanisms and don't need — or benefit from — one unified solution.

### 1. Unannotated function parameters — lean on TDD-00005's option 2, not option 3

[TDD-00005](TDD-00005.md) already scoped this exact question for parameters
specifically and landed on a recommendation directly relevant here: prefer
**call-site inference** (its "option 2") — a whole-program pass collecting
every direct call to a given function and inferring the parameter's type
from the argument types actually passed, producing a real concrete type
(string, i64, a class, etc.), not a boxed `any` — over "option 3" (default
to `any`, dispatch every operation at runtime), which TDD-00005 itself
calls "the biggest lift by a wide margin" since `any` is explicitly
rejected as a parameter type today and would need boxing/unboxing wired
through every arithmetic operator and coercion path a parameter can reach.
This TDD doesn't re-litigate that choice — it adopts TDD-00005's own
recommended direction as the mechanism for the "best-effort JS" flag
proposed below. The one new wrinkle for genuinely untyped (not just
unannotated) JS: a function called with *incompatible* argument shapes at
different call sites (no annotation anywhere to fall back on, unlike a
partially-typed TS codebase) — see sub-problem 4.

### 2. Class fields with no declarations — genuinely new, not covered elsewhere

Infer field names and types by walking the constructor body (and, in a
wider net, every method body — real JS lets any method introduce a new
field, not just the constructor) for `this.NAME = EXPR` assignment targets,
running the existing `inferExprType` on each `EXPR`, and synthesizing the
field list `registerClasses` currently expects from an explicit
declaration — a bounded, mechanical collection pass, not a new inference
engine; it reuses `inferExprType` exactly the way return-type inference
([ADR-00041](../adr/ADR-00041.md)) and parameter inference (above) already
do. The real design question is what happens when the same field is
assigned *different* types across branches or methods — see sub-problem 4;
this document leans toward first-assignment-wins (mirroring ADR-00041's own
precedent and its accepted forward-reference caveats) as the default, with
a hard error if a later assignment clearly disagrees, rather than silently
picking one.

### 3. Prototype-based OOP and general dynamic property add/delete — out of scope even here

Not a type-inference problem — a different **runtime object model**
problem. Every object in this compiler is a fixed-shape heap struct decided
at compile time (`types.go`'s `ObjectType`/`StructIR`); prototype chains
and arbitrary property mutation need a genuinely different backing
representation (a real hash-map-backed dynamic object — structurally
closer to the `Map`-backed dynamic-object machinery
[TDD-00012](TDD-00012.md) already built for computed-key object literals,
but generalized to *every* object, not just ones with a computed key).
`docs/status/README.md`'s own roadmap already flags this as a separate,
speculative, unscoped item ("a genuine dynamic property bag is a
different, heavier object representation... rather than the default") —
this TDD doesn't re-scope that work, it just confirms "best-effort JS
mode" can't absorb it as a side effect: it stays its own, larger,
independent initiative.

### 4. When inference can't produce one concrete type

Two real options, left open rather than decided here:

- **Hard compile error** — "best-effort" means "infer what's decidable,
  and say plainly that the rest needs an annotation," not "make everything
  compile no matter what." Matches this project's own consistent
  "clean errors over silent misbehavior" standing rule, and matches the
  user's own stated skepticism about `any` directly.
- **Fall back to `any` only for the specific value that's genuinely
  polymorphic** — closer to real TypeScript's own implicit-`any` behavior,
  but only actually useful once `any`'s operator coverage is broadened well
  past today's Staged V1 scope (itself separate, undesigned work). Not
  recommended until there's a concrete forcing function (e.g. actually
  needing to consume a real untyped package) — mirrors TDD-00005's own
  conclusion that "this compiler is already, deliberately, a bit stricter
  about `any` than real TypeScript is," and that's a defensible position
  for a project leaning toward the statically-typed end of the TS
  spectrum on purpose.

### Proposed shape: an opt-in flag, not a default-mode change

A compiler flag (e.g. `--js`/`--infer`), off by default, enabling
sub-problems 1 and 2 above — strictly additive to what compiles today,
never changing default/strict behavior for existing TS source. Matches the
"as a last option, once everything else is implemented" framing directly:
deliberately bottom of the roadmap, revisited only once
[TDD-00005](TDD-00005.md)'s own parameter-inference work and
[TDD-00010](TDD-00010.md)'s generics work are further along, since both
share this TDD's core mechanism — a whole-program, `inferExprType`-driven
collection pass, enabled by the same whole-program compile
([ADR-00022](../adr/ADR-00022.md)) that already makes TDD-00010's
monomorphization design tractable.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Whole-program compile (`resolver.ResolveProgram`) | ✅ already exists | What makes "look at every call site / every `this.x =` assignment across the whole program" decidable at all |
| `inferExprType` | ✅ already exists | Reused directly for both class-field and parameter inference, same as return-type inference already does |
| `any`/`unknown` boxed runtime | ⚠️ exists, but Staged V1 | No general arithmetic/comparison operators — the concrete, confirmed reason "just box everything as `any`" doesn't work, not a guess |
| TDD-00005's call-site parameter inference ("option 2") | ❌ not started | This TDD adopts it directly as sub-problem 1's mechanism rather than re-designing it |
| Constructor/method-body field-assignment collection pass | ❌ not started | The one genuinely new piece of engineering this TDD introduces |
| Hash-map-backed general (non-fixed-shape) object representation | ❌ not started, explicitly out of scope | Needed for prototype chains / arbitrary property add-delete — a separate, larger, already-flagged initiative (`docs/status/README.md` roadmap), not absorbed by this TDD |

## Open questions

- First-assignment-wins vs. require-consistency for class-field type
  inference across branches/methods — undecided, leaning first-assignment-
  wins by default with a hard error on a clear later disagreement.
- Hard error vs. `any`-fallback when inference can't produce one concrete
  type — undecided, leaning hard error (see sub-problem 4).
- Whether field inference should scan only the constructor or every method
  body — undecided, leaning constructor-only to start (narrower, safer,
  matches how real JS class fields are *usually* introduced even though
  the language permits more).
- Priority: explicitly the lowest-priority item touching the type system
  right now — not worth returning to before TDD-00005/TDD-00010 are
  further along, since this TDD's core mechanism is shared with both
  rather than independent.
