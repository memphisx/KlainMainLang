# ADR-01091: node:ffi verified against a real `--experimental-ffi` build — six divergences fixed

- **Relations**: `Implements TDD-00164`, `Extends ADR-00797, ADR-00798, ADR-00799, ADR-00800`
- **Date**: 2026-09-23

## Context

`node:ffi` is Node's experimental FFI, landing only in Node v26.1.0+ behind
`--experimental-ffi`. It was built here to the documentation, but never verified
against a running `node:ffi` — the dev and CI oracle Node predated v26.1.0, so
no `assertSameAsNode*` test could diff against it. `FFI.md` itself flagged this
(the `exportString` overflow row was "unverified against a real build"). Given a
26.x Node is now available, a differential oracle — the same posture as the
`node:sqlite` oracle test — is the right way to hold `node:ffi` to its stated
contract: strictly Node-conformant, nothing non-Node on the surface
([TDD-00190](TDD-00190.md)); enhancements (e.g. auto-marshalling `string`) live
in the separate `klain:ffi`.

## Investigation

Every `tests/ffi_test.go` program was run through real `node:ffi` (v26.10.0,
`--experimental-ffi --experimental-strip-types`) and diffed against ours. Six
divergences surfaced, each cross-checked across v26.1.0 / v26.5.0 / v26.10.0
(stable, not per-version) and against the Node docs:

1. `ffi.types.FLOAT` / `DOUBLE` / `BOOL` were `"float32"` / `"float64"` /
   `"uint8"`; Node's are `"float"` / `"double"` / `"bool"` (the canonical-name
   aliases). `JSON.stringify(ffi.types)` from a real build is the reference.
2. A `string` **return** value marshalled the `char*` to a JS string; Node
   exposes it as the raw pointer `bigint` ("pointer-like types travel as
   pointers; pointer return values are exposed as bigint addresses" — docs).
3. A `string` **callback parameter** marshalled to a JS string; Node hands the
   closure the raw pointer `bigint`. A `string` callback **return** of a JS
   string aborts Node ("Callback returned invalid value") — it too wants a
   pointer `bigint`.
4. `exportString` accepted a `bigint` length and truncated to the capacity;
   Node requires a `number` length (`validateInteger` → `ERR_INVALID_ARG_TYPE`)
   and throws `ERR_OUT_OF_RANGE` when it cannot hold the string plus its NUL.
5. `lib.symbols` / `lib.functions` enumerated keys in resolution order; Node
   enumerates them most-recently-registered first (reverse).
6. `registerCallback` caps concurrently-live callbacks at 16 per signature and
   throws past that; Node's libffi closures have no limit.

Fixing the first test to bind a `string` return to a `const` also exposed a
pre-existing, unrelated codegen bug (below).

## Decision

Match Node exactly for 1–5. Keep 6 as a documented divergence-by-necessity.

- **Types (1)**: `ffiTypesConstants` now holds Node's public spellings (what
  `console.log(ffi.types.X)` prints); `ffiTypeNameExpr` runs the constant back
  through `ffiCanonicalType` so a signature written `return: ffi.types.DOUBLE`
  still resolves to `float64`.
- **`string` is pointer-like (2, 3)**: a bound-function `string` return marshals
  as `pointer` (`emitFFIFunctionCall`; `ffi.toString` keeps its own string
  marshalling, which is its purpose), and `ffiReturnKmlType("string")` is now
  `bigint`. In the callback trampoline `string` is merged into the
  pointer/bigint cases for both parameter and return (arg validation, arg
  marshalling, return marshalling).
- **`exportString` (4)**: reject a statically-`bigint` length (the AOT
  equivalent of Node's runtime `ERR_INVALID_ARG_TYPE`); throw a `RangeError`
  when `capacity < strlen+1` instead of truncating, then write the whole string
  plus NUL. The byte-export forms already threw the analogous `RangeError`.
- **Accumulator order (5)**: `ffiLibAccumulatorType` walks the registration
  record back-to-front.
- **Callback slot cap (6)**: unchanged. Callbacks are static per-signature
  trampoline families (no runtime codegen, ADR-00799/ADR-00800); an unbounded
  closure model like libffi's is not achievable without runtime codegen. It
  stays an ours-only test and a disclosed `FFI.md` caveat.

The differential oracle is `assertSameAsNodeFFI` (`tests/ffi_oracle_test.go`):
compile+run ours against a deterministic `want`, then — when a `node:ffi`-capable
Node is on `KML_FFI_NODE` (or PATH) — diff real `node:ffi`'s output against the
same `want`. Where a value would be a non-deterministic pointer, the program
prints structural facts (`typeof`, `> 0n`). CI installs Node 26.10.0 on the
POSIX lanes as this second oracle, alongside the pinned general oracle (24.19.0);
Windows leaves `KML_FFI_NODE` unset and the check self-skips.

## Side effects discovered

- **Pre-existing binding bug, fixed in passing**: `emitVarDecl`'s pre-inference
  switch had no case for an FFI-function-typed callee, so `const p =
  boundFn(...)` (a `lib.getFunction` result called and bound) defaulted the slot
  to `i64` while the value was a `bigint`/pointer — a clang-stage type mismatch.
  Added the `IsFFIFunction` case mirroring `inferExprType`. The example and
  tests confirm it.
- **Still open**: a `getFunction` result off a *destructured* `const { lib } =
  ffi.dlopen(...)` loses its `IsFFIFunction` type in inference (comes back
  `i64`), so binding it to a `const` still fails — a deeper destructuring
  type-propagation gap, distinct from the `new DynamicLibrary` path fixed here.
  Tests and the example sidestep it (call inline, or use `new DynamicLibrary`).
  Tracked as an FFI follow-up.

## Verification

- All 12 `TestE2EFFI*` pass with `KML_FFI_NODE` set to Node 26.10.0 — ours and
  real `node:ffi` print identically for every deterministic case; the 16-slot
  cap is the one ours-only check.
- `examples/ffi/ffi.ts` output is byte-for-byte identical to real `node:ffi`.
- Broad regression (`TestE2EFFI|Const|Var|Let|Generic|Closure|Sqlite|WebSocket`)
  green — the shared vardecl change caused no fallout.
- `make status` / `make reference-check` clean.
- Verified on: macOS (Apple Silicon M4). Node oracle installed via nvm.
