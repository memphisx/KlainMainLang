# TDD-00062: Bare `any`/`unknown` as a function parameter/return type (Staged V2)

- **Status**: Implemented
- **Date**: 2026-08-12

## Context

ADR-00008 shipped `any`/`unknown` as a runtime-tagged `{ i8, i64 }` box (Staged V1: declare/assign/print/`typeof`/`===`), but deliberately **guarded out** their use as a function parameter or return type — an *active* rejection (`emit_func.go:162`, `emit_classes.go:1250`, and the arrow/function-expression equivalents), not just a doc note, because without it the box would silently produce broken IR.

That guard is now the single biggest remaining conformance lever. The Test262 harness shim's `assert` must type its parameters to cover "any test value"; today it can only use a *constrained* scalar union (`number | string | boolean | null`), so every file that asserts on an **object or array** value fails to compile at the call site. `assert.sameValue` alone appears in ~30k corpus files. Lifting the guard is also core type-system completion (a co-equal top priority in this project's own guidance), not just a conformance hack.

This is scoped now because the enabling machinery already exists and was just exercised end-to-end: ADR-00008 built boxing/unboxing/`===`/`typeof`; TDD-00010 V2's `@erased` path already flows a **bare `TypeAny`** parameter/return through the exact codegen below (`erasedParamOK`/`erasedRetOK`); and ADR-00174 fixed the last call-site that mis-coerced instead of boxing a dynamic argument.

## Design

**Scope (Staged V2): lift the guard for the *top-level* bare `any`/`unknown` parameter and return position only.** Keep every other Staged-V1 restriction exactly as-is.

Concretely:

1. **Allow** `isUnconstrainedDynamic(pty)` in parameter and return position (function declarations, arrow functions, function expressions, class methods, static methods). This is a one-line relaxation at each guard: drop `isUnconstrainedDynamic(...)` from the rejection, keep `containsDynamicElement(...)`.
2. **Keep rejecting** `containsDynamicElement` — `any[]`, `{ x: any }`, `Promise<any>`, etc. Nothing downstream (HOF codegen, field access, array indexing) handles a dynamic *element*, so those stay a clean error, identical to V1.
3. **In-body operations on an `any` parameter are unchanged** — the same Staged-V1 surface any `any` local already has: reassign, print, `typeof`, `===`/`!==`, pass-through. Arithmetic, field access, indexing, and calling an `any` remain clean errors (already enforced by the existing operator/member guards, independent of how the value entered scope). An `any` param is therefore useful exactly for what `assert.sameValue` needs: compare two values with `===`.
4. **`unknown` ≡ `any`** in V2, same as V1 — no forced-narrowing distinction (this compiler does no static-only checking that would make the distinction observable).
5. **Argument boxing at the call site**: `emitBoxValue` already boxes every in-scope value shape — int/float/bool/string/**object**/null/undefined (`emit_dynamic.go:170-206`). Objects box by `ptrtoint` (tag=object); `===` on two boxed objects compares payloads = pointer identity = correct JS reference equality. So object arguments Just Work once the guard is lifted.
6. **Array arguments are the one gap**: an array Value is a `{ ptr, i64 }` aggregate (`IsArray`), which `emitBoxValue` does not handle (it would fall into the `default` int branch and mis-coerce). V2 must reject an **array argument passed to an `any` parameter** with a clean compiler error at the call site, not emit broken IR. (This mirrors ADR-00008's original discipline: guard the unsupported shape rather than crash in clang.) Array-valued `any` comparisons stay out of scope until a later stage boxes arrays.

**Recommended direction**: do the guard relaxation + the array-argument call-site guard together, since the second is what keeps the first from regressing ADR-00008's "clean error, never broken IR" invariant. Ship the function-declaration path first (covers plain `function f(x: any)`), then the arrow/function-expression/method/static-method paths, then rewrite the harness shim's `assert` to use bare `any` parameters and measure.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `{ i8, i64 }` box representation | Done (ADR-00008) | `TypeAny`, `emit_dynamic.go` |
| Boxing incl. objects/strings/null/undefined | Done (ADR-00008) | `emitBoxValue` handles every scalar + object shape; **not** arrays |
| Unbox / `typeof` / `===` on a box | Done (ADR-00008) | `emitDynamicTypeof`, `emitAnyEquals`, `@__kml_any_eq` |
| Dynamic param *binding* in the callee | Done | scalar/dynamic path at `emit_func.go:196-212` already allocas+stores a `{ i8, i64 }` param; `@erased` bare-`T` params prove it round-trips |
| Call-site arg boxing for dynamic params | Done (ADR-00008, ADR-00174) | free-function (`emit_call.go:953`) + static-method (`emit_classes.go`) box `IsDynamic` params; **verify** the instance-method (`emitClassCall`) and closure-call paths do too |
| Array-argument-to-`any`-param guard | Missing | new clean error at each call site (this TDD) |
| Boxing an array value | Out of scope | deferred; forces the array-arg guard above |
| Stringifying a boxed object (`console.log`) | Missing / out of scope | not needed for `assert`; still a clean error if hit |

## Open questions

- Does the closure-call path (`emitClosureCallByPtr`) box a dynamic parameter's argument, or does it assume concrete IR? Must be checked before claiming arrow/`() => void` params with `any` work (relevant because `assert.throws(fn)` takes a closure — though its own param isn't `any`).
- Should return-type `any` ship in the same stage as parameter `any`? The codegen guard is symmetric and `@erased` already returns bare `TypeAny`, so it is nearly free — but it has no conformance-shim driver, so it could be split out if it surfaces any caller-side surprise.
- Is an explicit "array passed to `any` parameter" diagnostic worth a dedicated message, or should it reuse the generic union-member-mismatch phrasing? Leaning dedicated, since the cause (array boxing unsupported) is specific.
