# ADR-00223: A validating JSON parse-tree (P1) — `JSON.parse` throws `SyntaxError` on malformed input

- **Relations**: `Implements TDD-00077` (Track P, P1); `Extends ADR-00189`, `ADR-00007`
- **Date**: 2026-08-18

## Context

`JSON.parse` used a lenient, `strstr`-based field extractor ([ADR-00007](ADR-00007.md)) that never validated its input: malformed JSON silently returned zero-value defaults rather than throwing, and outright non-JSON (an HTML error page, single-quoted text) parsed as an empty object. Real JS throws a `SyntaxError`. This is P1 of [TDD-00077](../tdd/TDD-00077.md)'s Track P — the first stage of the parse rewrite: a real recursive-descent parser that builds a tagged value tree and rejects invalid input. Later stages consume the tree for typed projection (P3) and `any`-typed/dynamic parse (P4); P1 delivers the parser + tree + validation.

## Investigation

- The existing per-field extractors (`emitJSONParseObject`/`emitJSONParseFieldValue`, `runtime_json.go`) can't validate: `__kml_json_find_value` locates a key with `strstr` and hands the rest to `atoll`/`strtod`/a string decoder, each stopping at its own natural boundary — nothing ever checks the document is well-formed.
- The throw path is established: `buildErrorObj(errorKindIDs["SyntaxError"], msg, "SyntaxError")` + `call void @__kml_throw` + `unreachable` (as `emit_regexp.go:301` does for a bad pattern) produces a catchable `SyntaxError`. The parser stays pure C (no exception-ABI knowledge): it returns `NULL` + a byte offset, and the emitted IR does the throw.
- The parser runs on **untrusted runtime input**, so unbounded recursion on deeply-nested JSON could overflow the C stack — a real DoS vector. A hard depth cap is required (unlike the compile-time-bounded typed recursion the old design worried about).
- Two existing call sites relied on the lenient behavior and were fixed to valid JSON, since accepting them was the bug: an example's `JSON.parse("'world'")` (single quotes) and a test's `JSON.parse('<html>503…')` (raw HTML) — both throw under real JS and now under P1.
- Considered keeping span-finding and bolting a validation pre-pass on top ([TDD-00077](../tdd/TDD-00077.md) rejected alternative): it means maintaining two parsers and still can't represent an `any`-typed result, so building the tree once is strictly simpler.

## Decision

A self-contained recursive-descent JSON parser in an embedded C file (`codegen/llvm/jsonsrc/json_parse.c`, libc only), compiled alongside the program (the `bigint`/`gcshim` pattern) only when `UsesJSONParse()` is set. Its `__kml_json_*` ABI over an opaque node pointer:

- `KmlJsonNode` — a tagged node (`null`/`bool`/`number`/`string`/`array`/`object`); a number keeps both its parsed `double` and its raw lexeme (for exact large-integer projection in P3); an object keeps insertion-ordered `(key, value)` pairs.
- `__kml_json_parse(text, *err_pos)` → the root node, or `NULL` on malformed input with `*err_pos` set to the offending byte offset. Enforces strict JSON (double-quoted keys/strings, no trailing commas, no leading zeros, no trailing junk, `\uXXXX` + surrogate-pair decoding to UTF-8) and a `KJSON_MAX_DEPTH` (512) nesting cap.
- `__kml_json_free(node)` — recursive, NULL-safe release.

`emitJSONValidate` (called at the top of `emitJSONParseValue`, so `JSON.parse` and `Response.json()` both get it) calls `__kml_json_parse`; on `NULL` it builds `Unexpected token in JSON at position N` and throws a catchable `SyntaxError`; on success it **frees the tree and continues on the existing extraction path**. P1 deliberately parses-and-discards: it adds validation without yet moving projection onto the tree (P3 does that, eliminating the double parse). The tree-construction code is thus written, compiled, and exercised on every valid parse now, ready for P3 to consume.

## Implementation notes

- New: `codegen/llvm/jsonsrc/json_parse.c`, `codegen/llvm/json_tree.go` (`//go:embed` + `JSONParseTreeSource`/`UsesJSONParse`/`ensureJSONParseTree`/`emitJSONValidate`).
- `emitter.go`: `usesJSONParse`/`declaredJSONParseTree` flags.
- `main.go`: compiles `*.jsontree.c` into the clang invocation when `UsesJSONParse()` — no external library to link (unlike bigint).
- `tests/compiler_test.go`: `appendJSONParseTree` mirrors `appendBigIntBackend`, wired into every builder's clang call so the test build can't drift from `main.go`.
- The parser returns `NULL` + offset; the throw lives entirely in emitted IR (the C never touches the exception ABI), matching how the regexp path surfaces a PCRE2 error as a `SyntaxError`.

## Verification (Mac, Apple Silicon M4)

- `tests/json_test.go` — malformed input throws a catchable `SyntaxError` (name + position message); strict rejections (single quotes, trailing comma, leading zero, trailing junk, empty) vs. accepted valid input; valid documents (escapes + a `float64` field) still project; a 5000-deep document is rejected by the depth guard rather than crashing. Uncaught malformed input exits non-zero with `Uncaught: …`.
- Memory safety of the C parser (incl. every free-on-error cleanup path and a `😀` surrogate pair) checked clean under AddressSanitizer via a direct driver. A leak check needs Linux (macOS has no LeakSanitizer) — deferred as a machine-switch follow-up.
- `go vet ./codegen/... ./tests/` clean; the fixed example (`examples/json/json_methods.ts`) run end-to-end.
