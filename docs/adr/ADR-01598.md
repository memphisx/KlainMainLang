# ADR-01598: Windows test runs are bounded

- **Relations**: Extends ADR-01581, ADR-01582, ADR-01042
- **Date**: 2026-10-13

## Context

A full Windows run of the E2E suite exhausted a 64 GB machine: about 5,700
`prog.exe` + `cmd.exe` pairs from one test, and a reboot to recover. Later
runs stalled for an hour on one hung program. Mac and Linux carry guards for
both (ADR-01581's shell self-spawn marker, ADR-01582's data-segment cap, the
conformance reaper); Windows had none of them.

## Investigation

- `TestE2EChildProcessShellSelfSpawnRejected` runs `exec('"<self>" x')`.
  ADR-01581 marks a shell child that starts this executable only on the POSIX
  path (`sh -c`); on Windows the shell is `cmd.exe /d /s /c`, and
  `is_self_spawn` compared just the spawned file (`cmd.exe`). Each copy
  re-ran the program and spawned again.
- The test binary's job object (`procgroup_windows_test.go`) set only
  kill-on-close: no process or memory limit.
- `tools/testshard` dealt each process's tests into one `-test.run` pattern;
  with one shard and one process that pattern (about 4,100 names) passes
  Windows' 32 K command-line limit and the binary never starts. Its serial
  re-run of failures had the same limit. It also ran the test binary from the
  repo root, where `go test` runs it in the package directory, so tests with
  relative paths (`testdata/`, `../apps`) failed under it.
- The test helpers run each compiled program without a deadline; a hung one
  holds the run until `-timeout`.

## Decision

- **Self-spawn through a shell on Windows** (`win32proc.c`
  `shell_runs_self`): for `cmd /c <command>` (outer quotes dropped, as `/s`
  does) or `<sh> -c <command>`, a word in command position that names this
  executable, directly or through `%VAR%`, `$VAR` or `${VAR}`, marks the
  shell, which passes the mark to the copy it starts. A bare name is searched
  on PATH with `.exe`.
- **The test job is bounded**: 512 active processes, 4 GB committed per
  process (as `-mem-cap-mb`), 8 GB for the job, and the binary panics if the
  job cannot be set up.
- **The run is bounded**: `testshard` puts itself in a job of 8 GB and 1,024
  processes; the test binaries' jobs nest inside it.
- **Stuck programs end**: a goroutine in the test binary lists the job's
  processes every 10 s and ends any program under the temp directory that has
  run for 4 minutes; its test then fails on the exit status. The temp
  directory is matched without its volume, since a RAM drive with no DOS
  device mapping reports images as `\Device\<disk>\…`.
- **Conformance runs are bounded**: on Windows `tools/conformance` puts
  itself in a kill-on-close job: `-mem-cap-mb` (4 GB) for the run, half of
  it per process, 512 processes. It prints the peak at exit; a 300-file
  sample at 6 workers peaked at 446 MB.
- **testshard** splits a pattern into command lines under 24,000 characters,
  for the parallel processes and the serial re-run, and runs the binary in
  the package's directory.

## Implementation notes

`JOBOBJECT_EXTENDED_LIMIT_INFORMATION` limits: `ACTIVE_PROCESS` 0x8,
`PROCESS_MEMORY` 0x100, `JOB_MEMORY` 0x200, `KILL_ON_JOB_CLOSE` 0x2000. The
process list is `JobObjectBasicProcessIdList` (class 3). The self-spawn test
uses `%SELF%` on Windows, where cmd does not expand `$SELF`.

## Side effects discovered

- `TestE2EChildProcessForkIPCRoundtrip`, `ForkArgvBranch` and the cluster
  tests failed with `write EBADF`: see ADR-01599.
- The server tests listen on all interfaces, which raises a Windows Firewall
  prompt for every new `prog.exe` when the firewall is on; binding the tests
  to 127.0.0.1 is in BACKLOG.

## Verification

Windows 11: the self-spawn tests pass (each copy exits 9) with no process
left behind; the reaper ended a deliberately hung `ForkSendHandle` program at
4m07s and its test failed at 250 s; full suite runs through `testshard` at
`-j 8` stay inside the job limits. `go vet ./tools/testshard` passes for
windows, linux and darwin.
