# ADR-00421: Linux CI fixes — empty-header-block NUL, libm for frem, float fuzz oracle

- **Relations**: Extends ADR-00072 (response headers), TDD-00123 (float `number` semantics), TDD-00014 (fuzz lanes)
- **Date**: 2026-08-28

## Context

The Release workflow failed on the last two pushes while the full local
suite on the Mac was green. Three independent failure groups, all
Linux-only or introduced by the TDD-00123 `number`→float64 change:

1. `undefined reference to fmod` at link time for any program using `%`
   on floats (now the default `number`), failing several E2E tests.
2. `FuzzArithmeticCorrectness` mismatches — the oracle still computed
   expected values with Go int64 arithmetic (truncating `/`, `srem` `%`).
3. Four HTTP tests (`TestE2EHTTPCreateServerBoundHandle`,
   `…OnRequestUntyped`, `…NodeTestIdiom`,
   `TestE2EHTTPClientInProcessRoundTrip`) failed with garbage bytes in
   the response header block (`malformed MIME header: missing colon:
   "\xcd]\x96…"`).

## Investigation

Verified on the Mac: group 2 reproduced locally too (the oracle is
platform-independent); groups 1 and 3 did not. All three reproduced in
Docker (`golang:latest`, glibc/arm64, Debian clang 19).

- Group 1: `frem double` lowers to a libcall to `fmod`; the clang link
  line (built from `LinkLibs()` in `main.go`, `tests/compiler_test.go`,
  `tools/conformance/main.go`) never passes `-lm`. macOS bundles libm in
  libSystem, so it only fails on Linux. Emission sites:
  `codegen/llvm/emit_exprs_operators.go` `%` in `emitBinary` and the
  compound-assign core.
- Group 2: TDD-00123 made `/` emit `fdiv` and `%` emit `frem` for
  `number`; the Lane-A oracle (`tests/fuzz_codegen_test.go`) still
  asserted i64 semantics. Runtime number formatting was probed against
  node and is byte-identical (`-0`, `1e-7`, `2e+21`, `0.30000000000000004`).
- Group 3: `__kml_http_serialize_headers`
  (`codegen/llvm/runtime_http.go`) is two-pass size-then-fill. With an
  **empty** headers map the fill loop never runs, so the 1-byte malloc'd
  buffer never receives a NUL terminator; `__kml_http_send_response`'s
  `strlen(extraHeaders)` then walks uninitialized heap into the response.
  macOS's zeroed small allocations masked it; glibc returns dirty
  memory. The failing tests are exactly the `res.writeHead(200)`-with-
  no-headers createServer paths (fresh empty headers map → serialized);
  tests passing headers got a terminator from the last `sprintf` and
  kept passing.

## Decision

1. `e.requireLink("m")` at both `frem` emission sites, so `-lm` appears
   on the link line exactly when a program uses float `%` — same
   mechanism as curl/pcre2. Unconditional `-lm` was rejected to keep the
   "only link what's used" discipline.
2. Rewrite the Lane-A oracle in float64: `genArithExpr` computes with Go
   float64 (`math.Mod` for `%`, matching fmod/JS), zero divisors still
   substituted with 1 (keeps Infinity/NaN unreachable — bounded leaf
   magnitudes keep every intermediate finite). A new `formatJSNumber`
   renders expectations the way JS/dtoa does: signed `-0`, fixed
   notation for 1e-6 ≤ |v| < 1e21, exponential outside with unpadded
   exponents (`1e-7`, not Go's `1e-07`).
3. NUL-terminate the serialize-headers buffer up front in the `alloc`
   block (`store i8 0` at `buf+total`). The last `sprintf` writes its
   own NUL at the same final offset, so pre-writing is correct for the
   non-empty case too — no branch needed.

## Implementation notes

- `codegen/llvm/emit_exprs_operators.go`: two `requireLink("m")` calls.
- `codegen/llvm/runtime_http.go`: `%endp` GEP + `store i8 0` in `alloc`.
- `tests/fuzz_codegen_test.go`: float64 `genArithExpr`, `formatJSNumber`.

## Side effects discovered

- The TLS `bad record MAC` noise in the CI log came from the in-process
  client tests hitting the corrupted responses, not a TLS bug of its own
  — gone with fix 3.

## Verification

- Docker (`golang:latest` glibc/arm64, Debian clang 19): all nine
  previously failing tests plus `FuzzArithmeticCorrectness` seeds pass.
- Mac: same targeted set passes; 45s of live fuzzing on
  `FuzzArithmeticCorrectness` clean (formatter agrees with the compiled
  dtoa output across random expressions); `go vet ./...` clean.
