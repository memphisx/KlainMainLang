# ADR-01062: The RegExp `y` (sticky) flag — anchored matching at `lastIndex`

- **Relations**: Implements TDD-00035 (the flag scope table's deferred `y`); Extends ADR-00115/ADR-00116/ADR-00526 (`lastIndex` iteration for `g`), ADR-00549 (flag-string validation, which already accepted `y`)
- **Date**: 2026-09-22

## Context

BACKLOG §0 item 3: `y` was accepted by the flag validator (ADR-00549) and then ignored — `/foo/y.test("barfoo")`
matched, `re.sticky` was not a field, and a sticky tokenizer loop (`while (re.test(s))` with `y`) ran on as a
plain search. Silently wrong matches, the worst kind of divergence for a flag that exists to *restrict* matching.

## Investigation

- `RegExpType()` (`types.go`) carries `global/ignoreCase/multiline/dotAll/lastIndex`; `__kml_regex_parse_flags`
  (`runtime_regexp.go`) decomposes `g/i/m/s` into those fields at construction.
- Both match paths — `emitRegexTest` and `emitRegexSingleMatchCore` (`emit_regexp.go`) — compute the start offset as
  `select global, lastIndex, 0` and pass match option `0` to `pcre2_match_8`; the advance/reset of `lastIndex` after
  the match is gated on the same `global` flag. `str.match`/`matchAll`/`replace`/`replaceAll` iterate through the
  core, so the core is the one place that decides sticky behaviour for every method; `str.search` sets
  `lastIndex = 0` and restores it (ADR-00119), and `str.split` runs its own offset loop (the spec's split uses a
  fresh `y`-flagged clone, so the source regex's own flag is irrelevant there).
- Spec RegExpBuiltinExec: `lastIndex` is read as the start when `global || sticky`; a sticky match may only succeed
  at exactly that offset (else the result is failure and `lastIndex` resets to 0); on success `lastIndex` becomes the
  match end when `global || sticky`. PCRE2's `PCRE2_ANCHORED` match option (`0x80000000`) is exactly "only at the
  start offset".

## Decision

- `RegExpType` gains a `sticky` boolean field; `__kml_regex_parse_flags` gains a seventh out-slot for `y`.
- New `emitRegexMatchStart(objVal, strVal)` returns `(useLastIndex = global || sticky, lastIndex, startOffset,
  matchOpts)` with `matchOpts = sticky ? PCRE2_ANCHORED : 0`; `.test()` and the single-match core both use it for
  the `pcre2_match_8` call and gate their post-match `lastIndex` advance/reset on `useLastIndex`. Nothing else
  changes: the `g` loops stop at the first gap for a `gy` regex because the anchored attempt fails; `search`
  anchors at 0 through the same path; `replace` with a non-global sticky regex honours `lastIndex` as in Node.
- `pcre2Anchored` is recorded with the other hand-verified PCRE2 constants (spelled as its signed i32 value).

## Implementation notes

`codegen/llvm/types.go`, `runtime_regexp.go` (parser + constant), `emit_regexp.go` (construction stores the field;
the two match paths). The status row `u`/`y`/`d` splits into a ✅ `y` row and a `u`/`d` row; website reference
entry `regexp.sticky` added, `regexp.uyd` renamed `regexp.ud`, coverage badge re-synced.

## Side effects discovered

None. `u`/`d` remain out of scope (their own row).
