# TDD-00144: Selectable webview backend — CEF and QtWebEngine (cross-platform, GTK-free)

- **Status**: Not Started
- **Date**: 2026-08-28

## Context

[TDD-00142](TDD-00142.md) ships desktop apps over the *system* browser engine:
WKWebView on macOS, WebKitGTK on Linux (via the vendored `webview/webview`
library, which supports only those two). That is deliberately small and
dependency-light, but it has two limits this document scopes an opt-in escape
from:

1. **Linux = GTK, always.** WebKitGTK pulls in the GTK libraries. A KDE / Qt user
   who wants their system free of GTK packages has no alternative today. (Nuance:
   WebKitGTK needs GTK *libraries* at runtime, not a running GNOME session — but
   "no GTK installed at all" is a legitimate preference.)
2. **No single engine across OSes.** When Windows support begins
   ([TDD-00020](TDD-00020.md)), the system-engine approach means a *third*
   distinct engine (Windows' native WebView2, Edge/Chromium) with its own
   rendering and quirks. A team that wants one identical engine everywhere — same
   rendering, same DevTools, same bugs — has no option.

Two engines can serve both needs at once because they are **toolkit-agnostic and
cross-platform**: **CEF** (Chromium Embedded Framework) and **QtWebEngine** (Qt's
Chromium wrapper). Both run on Linux (X11/Wayland, no GTK), Windows, and macOS.
The user's specific interest is QtWebEngine partly for the hope it also covers
Windows — worth recording, though on Windows the *native* default would be
WebView2, so a Chromium backend there is for uniformity, not necessity.

The cost is the identity trade: both are **Chromium** — heavy binaries, a shipped
Chromium resource bundle, and a multi-process model — the opposite of the small
system-engine default. So this is strictly an **opt-in axis**, never the default.
**Low priority**; it gets materially more interesting once
[TDD-00020](TDD-00020.md) (Windows) is underway, which is the natural trigger to
revisit.

Out of scope here (recorded so it isn't lost): **WPE WebKit** — real, maintained,
*GTK-free* WebKit, the lighter principled answer to limit (1) alone — but it is
embedded-oriented (renders to a surface, needs a Wayland/X11 view backend and
window management) and does not address the cross-platform/Windows goal. If the
GTK-free-but-still-light need dominates, WPE deserves its own TDD; this one is the
"one heavy Chromium engine everywhere" axis the user asked for. **QtWebKit** is
ruled out entirely: deprecated since Qt 5.6, unmaintained, security-stale.

## Design

### Selection mechanism — `-webview=<backend>`

Mirror the established backend-flag pattern (`-crypto`, `-bigint`,
[TDD-00104](TDD-00104.md)/[TDD-00074](TDD-00074.md)): a compiler flag selecting
which webview implementation is compiled and linked, the emitter staying
backend-agnostic because every backend satisfies the same internal `webview_*`
extern ABI (`runtime_webview.go`). Values:

- `system` (**default**) — the current per-platform system engine: WebKitGTK
  (linux) / WKWebView (darwin) / WebView2 (windows, when it lands). No change to
  TDD-00142's behavior.
- `cef` — Chromium Embedded Framework, all platforms.
- `qt` — QtWebEngine, all platforms.

Plumbing reuses `EmbeddedCSources` + a per-backend `LocateWebview<Backend>()`
(the `LocateWebview` / `LocateCrypto` pkg-config/framework split precedent). The
webview binding source becomes backend-selected the same way `CryptoBackendSource`
is (ADR-00436 already made the webview source a C++ `.cc` embedded member).

### The structural reality: each backend is a *substantial* shim, not a wrapper

The internal ABI is tiny (`webview_create/navigate/set_html/init/eval/bind/
return/dispatch/run/terminate/destroy` — ~13 functions). WebKitGTK/WKWebView map
onto it almost 1:1 (the vendored library already does). CEF and QtWebEngine do
**not**: they are large, multi-process, async engines with their own event loops
and object models. Each backend is a hand-written C/C++ shim exposing our
`webview_*` ABI on top of the engine — real work per backend, not a thin binding.

**CEF backend.** A C API layer (`cef_*`) exists over the C++. Structure:
- multi-process (browser + render + GPU + helper subprocesses) — the compiled
  binary needs a **helper executable** and a **Chromium resource bundle**
  (`.pak`, ICU `icudtl.dat`, the CEF framework, locales) shipped alongside;
  single-file distribution is gone.
- `run` → the CEF message loop (`CefRunMessageLoop` / integrated loop); `eval` →
  `frame->ExecuteJavaScript`; `bind` → the CEF message-router or a `cef_v8`
  native-function registration in the render process, with results marshaled back
  across the process boundary to `webview_return`.
- BSD-licensed (Chromium's own license); the largest binary/footprint.

**QtWebEngine backend.** C++ only (`QWebEngineView`/`QWebEnginePage`), so the shim
is a C++ `.cc` exposing our C ABI. Structure:
- needs Qt (QtCore/QtGui/QtWidgets/QtWebEngine) at build + runtime, plus the
  `QtWebEngineProcess` helper and Chromium resources shipped alongside.
- `run` → `QApplication::exec()`; `eval` → `page()->runJavaScript(...)`; `bind` →
  `QWebChannel` (or injected JS + `runJavaScript` callbacks) marshaling arguments
  and results, async, back to `webview_return`.
- LGPLv3 / GPL / commercial; "native-feeling" on KDE; the cross-platform bet the
  user favors for a future Windows target.

### Cross-cutting consequences

- **Async / multi-process ⇒ the loop-fusion pump may need per-backend
  adaptation.** TDD-00142 Stage 3's page-tick pump assumes the GUI thread owns a
  cooperative loop it can drain timers/microtasks on. CEF/Qt own their own
  (multi-process) loops; `webview_return` and the pump must be re-expressed per
  backend. The `bind`/`eval` contract stays the same at the language level.
- **Packaging convergence.** Both engines already force a multi-file artifact
  (binary + Chromium resource bundle + helper). That *changes* the TDD-00142
  Stage 4 packaging story and *aligns* with its deferred "bundle `dist/` into the
  app" question — a CEF/Qt app is already a bundle, so shipping app assets beside
  the engine resources is natural. The `.app`/`.desktop`/`.exe`-installer layout
  must account for the engine payload.
- **Binary size is the headline cost** — tens-to-hundreds of MB of Chromium vs a
  ~100 KB system-engine binary. This is the whole reason it stays opt-in.

### Recommended staging (when picked up)

| Stage | Content | Exit criterion |
|---|---|---|
| 1 | The `-webview=<backend>` selection mechanism: flag, `LocateWebview<Backend>()`, per-backend embedded-shim slot in `EmbeddedCSources`; `system` still the default and only working value | flag parses/validates; `system` unchanged; an unknown/unbuilt backend is a clean rejection |
| 2 | One Chromium backend end-to-end — **QtWebEngine first** (the cross-platform/Windows bet + KDE-native), or CEF first if its resource-bundling proves simpler; a window opens and `bind`/`eval` round-trip; the resource bundle ships alongside | an inline-HTML app runs GTK-free on Linux via the alt backend |
| 3 | The second Chromium backend + the packaging integration (engine payload inside the `.app`/`.desktop`/Windows artifact) + loop-fusion pump adaptation | both alt backends run the example apps; packaged artifacts include the engine payload |

Trigger to start: real user demand for GTK-free Linux, **or** the Windows target
([TDD-00020](TDD-00020.md)) reaching the point where a uniform cross-platform
engine is worth its weight.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Backend-agnostic `webview_*` extern ABI | ✅ built | `runtime_webview.go`; every backend satisfies the same ABI, emitter unchanged |
| Backend-selection flag pattern | ✅ precedent | `-crypto`/`-bigint` (`CryptoBackendSource` + `LocateCrypto`); `-webview` clones it |
| C++ embedded-source + framework/pkg-config plumbing | ✅ built | ADR-00436 (the webview `.cc` member + `LocateWebview`); each backend adds a `Locate*` + source |
| Shipping a resource bundle beside the binary | ❌ new | CEF/Qt need a Chromium payload + helper exe next to the artifact — no such packaging concept today; ties to [TDD-00142](TDD-00142.md) Stage 4 |
| Per-backend loop-fusion pump | ❌ new | TDD-00142 Stage 3's GUI-thread pump assumes a system-engine loop; multi-process engines differ |
| Windows target | ❌ [TDD-00020](TDD-00020.md) | Gates the Windows half of the cross-platform motivation; WebView2 would be the native Windows default regardless |

## Open questions

- **CEF vs QtWebEngine first** — Qt matches the user's cross-platform/KDE interest
  and has the cleaner (if C++-only) API; CEF avoids a Qt dependency but has the
  heavier resource/helper-process shipping story. Decide by which resource-bundle
  + build story is less painful once one is prototyped.
- **Does the Chromium resource bundle live *inside* the packaged artifact** (the
  `.app`/`.desktop`/Windows installer), and how does that reshape TDD-00142
  Stage 4? Likely yes — a Chromium app is inherently multi-file.
- **How does the Stage-3 page-tick loop-fusion pump map** onto a multi-process
  engine's own loop — re-expressed per backend, or replaced by the engine's
  native timer integration?
- **Licensing surface** — Qt (LGPLv3 dynamic-link vs commercial) and CEF (BSD, but
  the Chromium payload) implications for what users can ship.
- **Binary-size budget** — is a tens-to-hundreds-of-MB opt-in acceptable, or
  should this stay a documented capability rather than a shipped default anywhere?
- **Is WebView2 alone enough for Windows** (making CEF/Qt purely a Linux-GTK-free
  and cross-platform-uniformity feature, not a Windows necessity)?
- **Should WPE WebKit** (GTK-free but light, WebKit-not-Chromium) be its own TDD
  for the users who want GTK-free *without* the Chromium weight — a different point
  on the size/uniformity trade than this document's two engines?
