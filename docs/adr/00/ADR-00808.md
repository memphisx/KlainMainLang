# ADR-00808: node:ffi dlopen(null) resolves libm symbols on Linux

- **Relations**: `Extends TDD-00164`, `Extends ADR-00799`

- **Date**: 2026-09-09

## Context

`node:ffi`'s `dlopen(null, …)` opens the running process's own global symbol
scope, the way `TestE2EFFILibcSelfProcess` resolves `strlen`, `pow`, `getpid`,
and `strchr` against the current program. This passed on macOS but broke the
Linux CI lane (`go test` on linux-x64, the node:ffi commit): the test compiled
but exited non-zero at FFI resolve time.

## Investigation

Reproduced in Docker (`golang:latest`, glibc/arm64 on the Mac) with the CI's
optional libs installed: `TestE2EFFILibcSelfProcess` failed there, every other
`TestE2EFFI*` passed. The differentiator is `pow`, which lives in **libm**:

- `strlen`/`getpid`/`strchr` are in libc, always a loaded dependency, so
  `dlsym(NULL, …)` finds them.
- `pow` is in libm. macOS folds libm into libSystem (always linked), so it
  resolves there. Linux only links libm when the program references a libm
  symbol — and this one never does directly (the reference is a runtime `dlsym`),
  so libm is not a dependency and `dlsym(NULL, "pow")` returns NULL → the FFI
  resolver throws → exit 1.

Confirmed the fix by compiling the repro through the CLI in the container and
running it: with the new flags it prints `5n` / `1024` (pow) / `true`.

## Decision

Add `llvm.FFILinkFlags()`, appended by both the CLI (`main.go`) and the test
harness (`tests/compiler_test.go`) whenever `em.UsesFFIDl()`:

- On Linux, non-static: `-rdynamic -Wl,--no-as-needed -lm -Wl,--as-needed`.
  `-rdynamic` exports the executable's own dynamic symbols so `dlsym(NULL, …)`
  can reach them (self-FFI); the `--no-as-needed` island force-keeps `-lm`, which
  the distro-default `--as-needed` would otherwise drop since no libm symbol is
  referenced at link time. This makes `pow` (and the rest of libm) resolvable via
  `dlopen(null)`, matching macOS / Node (whose binary links libm).
- macOS: no-op — libm/libdl are in libSystem already.
- Fully static Linux (`--static`): no-op — `dlopen(null)` can't grow the symbol
  scope at runtime in a static binary anyway, so forcing libm in buys nothing.

## Implementation notes

- The test harness assembles its own clang argv (it does not shell out to the
  CLI), so the flag block is mirrored at all of its build sites — the same
  duplication `WorkerPthreadLinkFlags` already lives with.
- Only `pow` needed libm in the failing test, but the fix is the general one
  (export self symbols + keep libm) rather than a `pow`-specific reference, so
  any libc/libm FFI target resolves through `dlopen(null)` the same way.

## Side effects discovered

None. The Windows FFI rejection is unchanged; the flags are Linux-only.

## Verification

Docker Linux (glibc/arm64, via the Mac): the full `TestE2EFFI*` suite passes,
including `TestE2EFFILibcSelfProcess`; a CLI-compiled repro runs and prints the
expected `pow` result. macOS (Apple Silicon): `go build`/`go vet` clean, FFI
suite unaffected (the flags are a Linux-only no-op there).
