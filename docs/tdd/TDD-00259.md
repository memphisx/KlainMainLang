# TDD-00259: Opt-in ownership checking for existing TypeScript

- **Status**: Not Started
- **Date**: 2026-11-17

## Context

This compiler's users compile TypeScript they already have. Native code and
no garbage collector are why they compile it here, so the next step is the
memory safety and efficiency Rust offers, without rewriting the code into a
different language. The question is how close an optional analysis can get
to Rust's guarantees on code that was written for Node.

What exists is a free-placement oracle, not an ownership discipline:

- [TDD-00001](TDD-00001.md) defined the three memory modes and judged a full
  borrow checker disproportionate and a language-design mismatch: "bolting
  `&`/`move` syntax onto TS-shaped code would mean designing a new language,
  not extending this one."
- [TDD-00173](TDD-00173.md) shipped `@free`, `@owned` (locals and
  parameters) and the implicit auto-free of `-mm=auto`, all behind one
  escape check. `Memory.free` is a compile error under `auto`.
- [TDD-00175](TDD-00175.md) Stage 1 shipped the type-directed deep free
  ([ADR-00716](../adr/00/ADR-00716.md)). Stages 2 (interprocedural
  freshness), 3 (scoped reference counting) and 4 (reuse) are not started.
- [TDD-00163](TDD-00163.md): `FinalizationRegistry`, the existing weak,
  death-notified reference.

The escape check (`memplan/escape.go`, entry `Frees`) is syntactic and
name-based. It follows one binding at a time through the rest of its scope
and answers one question: does any alias of this binding outlive the free?
Its limits decide what this document has to add:

- A value passed to any call is an escape, except to the few callees on
  `escCallWhitelist` (the console printers, `String`, `JSON.parse`,
  `JSON.stringify`). A user function that only reads its argument
  disqualifies it like one that stores it. This is the main limit on reach.
- There are no callee summaries. The only interprocedural rule is the
  `@owned`-parameter contract (`collectOwnedFns`), on direct calls.
- Class instances, closure captures, async functions and generators are
  excluded. A thrown path does not free (a leak, by design).
- It never reasons about two live references to one object, only about
  references that outlive a free.

Other gaps this work touches:

- `using` / `await using` declarations are not parsed
  ([TDD-00164](TDD-00164.md); Test262's `explicit-resource-management` is
  listed unsupported). `[Symbol.dispose]` exists on `fs.Dir` and sqlite.
- A transferred `ArrayBuffer` is copied to a Worker, not detached as in
  Node. A transferred `MessagePort` does move.

This is low priority: it follows [TDD-00230](TDD-00230.md) and the other
open TDDs. It is scoped now so the work is understood when it is reached.

## Design

### Principles

1. **Faithfulness.** The analysis only rejects programs or adds frees,
   reference counts and reuse that no program can observe. An accepted
   program behaves as under Node. Transfer detaching a buffer (Stage 4) is a
   fix toward Node, not a divergence.
2. **Inference first, annotations as overrides.** The resolver merges the
   whole program into one tree, so whole-program inference is possible. An
   annotation is written only where inference cannot prove a property, and it
   overrides inference: `@owned` (exists), `@borrows p`, `@retains p`,
   `@fresh`. Rust-style lifetime parameters and `&`/`&mut` annotations are
   excluded: they cost a change in every signature that touches a
   reference, for safety inference gives on unannotated code.
3. **Gain per changed line.** Stages are ordered by how much they improve
   code that is not edited, and by how few lines unlock the rest.
4. **A safe fallback.** A value the analysis cannot prove stays on the
   existing fallback (left to `auto`'s silent skip, reference counting once
   Stage 7 exists, or the collector under `-mm=gc`). It is rejected only
   when the developer asks for strictness.
5. **Three levels.** `off`; `report` (diagnostics with a suggested fix, never
   failing the build); `strict` (errors for annotated scopes). Strictness can
   be enabled per file or per function, so a codebase ratchets.
6. **Scope.** The strict lane only, with `any` excluded from what can be
   proven (an `any` value can be stored anywhere the checker cannot see), and
   `-mm=auto`.

### Stages

**Stage 0. Report-only analysis.** `-ownership=report` (the name is open)
runs the existing `memplan.Frees` and reports, per binding, freed or skipped
and the first rule that blocked it, with a blocked-by histogram and an
estimate of bytes left to the fallback. It rejects nothing and changes no
code. It is run over `examples/`, `apps/`, the benchmarks and the Node-core
suite. A scratch build that treats every call argument as non-retaining
bounds what Stage 1 could reach. These two numbers decide whether the later
stages are worth their cost. About a week.

**Stage 1. Escape summaries and a builtin table.** A bottom-up pass over the
call graph computes, per function and parameter: retains, returns an alias of
parameter *i*, returns a fresh value. Recursive groups are solved by fixpoint
or treated as retaining. Builtins get the same summaries from a data table
(JSON), audited against the C runtime rather than JavaScript semantics:
`Array.prototype.push` and `Map.prototype.set` retain, `slice` returns fresh,
`console.log` borrows. This replaces the blanket call rule with a precise one
and so accepts more. It subsumes TDD-00175 Stage 2 (`@fresh` inference).
`@borrows`/`@retains` override a summary. Under `strict`, `@owned` misuse
through a call is an error ("`parse(x)` stores `x` at cache.ts:41; pass a copy
or drop `@owned`"). A wrong summary is a use-after-free, so every table row and
rule ships with a differential run of the examples under `-mm=auto` and ASan.
About 5 to 8 weeks, plus the table audit.

**Stage 2. `using` and `Symbol.dispose`.** The TypeScript 5.2 declarations:
parse and check them, then lower them to the `finally` machinery. Disposal
runs in reverse declaration order, and an error in disposal raises
`SuppressedError`. This is RAII in standard TypeScript, and it runs unchanged
under Node. Under `strict`, `Memory.free` on a `using` binding and an escape
of one (returning the resource) are errors. It also covers Test262's
explicit-resource-management tests. About 4 to 6 weeks including
`await using`.

**Stage 3. Mutation during iteration, as an opt-in check.** Inside a loop
over a local or `@owned` container, a structural mutation of that container
(`push`, `splice`, `delete`, `length =`, reassignment) is reported, whether
direct or through a call whose Stage 1 summary mutates its argument. This is
the part of Rust's shared-XOR-mutable rule that maps onto TypeScript.
Mutating while iterating is legal JavaScript, so this is never on by default:
`report` level inside the mode, an error only under `strict`. Whether `for…of`
over a mutating array is faithful today has to be checked first. About 3 to 5
weeks.

**Stage 4. Transfer as a move.** `postMessage(v, [buf])` and
`structuredClone(v, { transfer })` detach the transferred buffer, as in Node,
which first fixes the copy noted above. A use of the sender's binding after
the transfer is a compile error where it is provable, and a detached-buffer
error at run time otherwise. The handoff becomes zero-copy. This is Rust's
`Send` mapped onto a share-nothing threading model. About 2 to 4 weeks; the
detached-buffer state is the hard part.

**Stage 5. Returned references.** A call result Stage 1 marks as an alias of
argument *i* keeps argument *i* alive while the result is live, so `@owned`
pipelines can return views. It is inference over summaries, with no lifetime
syntax. Built only if Stage 0 and 1 data show demand. About 4 to 8 weeks.

**Stage 6. Reuse.** Once TDD-00175 Stage 3 provides scoped reference counts,
a cell whose count is one at the point a same-shaped object is built is
reused in place (Perceus). Unobservable. This is the largest allocation win on
rebuild-heavy code (`map`, spread, persistent trees). Months.

**Stage 7. Reference counting where ownership is duplicated.** Owner/borrow
inference in the style of Lobster: a value with one inferred owner is freed
statically, borrows cost nothing, and only a value whose ownership must be
duplicated is counted. A value that fails the analysis is counted instead of
leaked, so failure costs speed, not memory. Cycles still leak without a weak
reference or a cycle collector. Shares TDD-00175 Stage 3's machinery. Months.

### The combined mode

`-ownership=auto` (name open) combines the stages: Stage 1 inference, Stage 7
counting for the rest, TDD-00175's deep free, counting and reuse, `using`,
transfer as a move, the iteration check at `report` level, and a summary of
the bytes left to the fallback. `-ownership=strict` turns unproven claims in
annotated or strict scopes into errors.

What it can claim: nothing is freed unless proven safe, the rest is counted or
collected, no collector runs for what inference or counting covers, and memory
does not leak except through cycles. It cannot claim Rust's compile-time proof
that nothing leaks or that no aliasing bug exists.

### Comparison

| Property | Rust | C++ | This compiler with the mode |
|---|---|---|---|
| Use after free | proven at compile time | unchecked (Core Guidelines lifetime profile: local heuristic) | proven for every freed value; an unproven value is never freed, so the default path has none |
| Double free | proven | unchecked | excluded per binding (TDD-00173) |
| Leaks | allowed but rare | `unique_ptr`/RAII by discipline | bounded by Stage 7 counting, except cycles |
| Data races | `Send`/`Sync` | unchecked | share-nothing Workers, with Stage 4 moves |
| Mutation while iterating | proven | undefined behaviour | opt-in check (Stage 3) |
| Annotations required | lifetimes and borrows in signatures | `unique_ptr`/`shared_ptr` types | none; overrides only where inference fails |
| Runtime cost | none for owned values; `Rc` for shared ones | as Rust | none for inferred owners; counts only where ownership is duplicated; reuse in place |

The C++ vocabulary maps onto what exists: `unique_ptr` and `std::move` onto
`@owned`, RAII onto `@free` and Stage 2's `using`, `shared_ptr` onto Stage 7,
`weak_ptr` onto `WeakRef`/`FinalizationRegistry`. The analysis Rust adds on
top of that vocabulary, proving that no reference outlives or conflicts with
another, is what Stages 1, 3 and 5 approximate by inference.

Where it falls short of Rust: class-heavy and callback-heavy code mostly stays
on the fallback; objects stay heap references with a header and numbers
default to doubles, so layout costs remain; an error in an inferred summary is
a soundness bug that Rust would have turned into a compile error, so the
burden moves to differential testing.

### Adoption for an existing codebase

1. Enable `-ownership=report` under `-mm=auto`. No edits; the report ranks
   the few lines that block the most memory.
2. Stage 1 inference frees more with no edits.
3. Fix the top blockers it names: typically a helper that stores its argument
   (copy, or `@retains`), a closure capture, a class instance.
4. Add `using` to handles where deterministic release matters (standard
   TypeScript, unchanged under Node).
5. Mark clean files or functions strict so a regression fails the build; the
   report can gate CI on "bytes left to the fallback must not grow".
6. Stage 7 counting covers the remainder without further edits.

### Rejected

- Rust-style lifetime parameters or `&`/`&mut` annotations in JSDoc: a
  rewrite of every signature, for what inference provides.
- Shared-XOR-mutable as a default rule: it rejects most valid TypeScript.
- Generational references (Vale) as a default: a stale access traps, which
  is observable. Acceptable only as an opt-in debugging mode.
- Region syntax (Cyclone): a language redesign; inferred regions overlap the
  arenas TDD-00175 already rejected.

## Open questions

- How much existing code passes? Unknown until Stage 0 runs; the stages after
  it are justified only by its numbers.
- The flag's name and levels, and whether `report` diagnostics are warnings
  with an opt-in to fail.
- Whether the escape check should move from name matching to the binder's
  resolved symbols before Stage 1, removing a class of shadowing bugs.
- How the builtin table stays tied to the runtime: a row that is wrong is a
  use-after-free, and a runtime change does not update the table by itself.
- What `for…of` does today when its array is mutated; Stage 3's faithfulness
  depends on it.
- Whether `any` is excluded per value (unprovable) or by a flag that rejects
  `any` in the program.
- Thrown paths: freeing on unwind needs landing pads or a cleanup stack and
  knowledge of what the catching scope still reads.
- External sources consulted for the comparison: Swift SE-0377 (parameter
  ownership modifiers) and SE-0390 (noncopyable types); Perceus (PLDI 2021)
  and frame-limited reuse; Lobster's memory management notes; Nim's
  destructors and move semantics; Vale's generational references; Hylo's
  mutable value semantics; the C++ lifetime profile (P1179) and safety
  profiles (P3081); Clang's `-fbounds-safety` documentation, which states the
  feature is not yet available in upstream Clang. The status of the Safe C++
  proposal (P3390) comes from secondary sources only.
