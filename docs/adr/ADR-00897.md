# ADR-00897: Mixed string/number `==` reaches the cross-type path

- **Date**: 2026-09-12

## Context

Part of the invalid-IR (Test262 `CLANG_ERROR`) sweep. A loose equality between a
string and a number emitted invalid IR under `-compat=strict`:

```ts
"-1" == -1        // clang: '%t2' defined with type 'double' but expected 'ptr'
```

From `language/expressions/equals/S11.9.1_A5.3.js` and
`language/expressions/does-not-equals/S11.9.2_A5.3.js`. The emitted IR was an
`icmp eq ptr %d, null` on the number operand — a `double` treated as a string
pointer.

## Investigation

In `emitBinary` (`emit_exprs_operators.go`), after `right = coerce(right,
left.Ty)` the string-operation path fires on:

```go
if ty.IR == "ptr" && !ty.IsObject && !ty.IsArray && !ty.IsFunc && !isNullCheck {
    return e.emitStringBinary(...)
}
```

For `"-1" == -1`, `left` is a string (`ptr`) and `right` is a number. There is
no number→string conversion, so `coerce` returned `right` unchanged as a bare
`double`; the guard checked only the *left* type, so the mixed pair entered
`emitStringBinary`, which assumes both operands are strings and compared the
double as a pointer.

The clean cross-type handling already exists further down (the "incompatible
types" strict reject, and the `-compat=js` `emitAnyLooseEquals` Abstract-Equality
box path) — the string path was simply pre-empting it.

## Decision

Require the **right** operand to also be a pointer before taking the string-
operation path (`ty.IR == "ptr" && right.Ty.IR == "ptr" && …`). A mixed
string/number pair then falls through to the existing cross-type handling:

- `-compat=strict`: a clean compile error ("operator '==' between incompatible
  types …"), matching TypeScript's own no-overlap comparison error.
- `-compat=js`: `emitAnyLooseEquals`, the JS Abstract Equality Comparison
  (`ToNumber(string) == number`), which evaluates `"-1" == -1` to `true`.

## Implementation notes

- One-line guard tightening; string↔string and the existing string↔object
  ptr-comparison behavior are unchanged (both operands remain `ptr` there).
- The strict path is a `COMPILE_ERROR`, not invalid IR — the sweep's goal. The
  faithful runtime answer is available via `-compat=js`.

## Side effects discovered

None. String/operator/equality E2E suites unaffected.

## Verification

- `TestE2EStringNumberLooseEqRejectedStrict` (new): strict rejects with
  "incompatible types".
- `TestE2EStringNumberLooseEqCompatJS` (new): `-compat=js` gives `true` / `false`.
- Both Test262 files pass under `-compat=js`; no longer `CLANG_ERROR` under strict.
- `make examples` 296/296; string / operator E2E suites green.
