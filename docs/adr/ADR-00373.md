# ADR-00373: Parse-and-erase three common TS constructs — `debugger`, `readonly T[]`, `this` parameter

- **Relations**: Extends [ADR-00372](ADR-00372.md); Implements [TDD-00121](../tdd/TDD-00121.md)
- **Date**: 2026-08-26

## Context

The TypeScript accept/reject conformance oracle's false-reject blocker
histogram (added in ADR-00372) ranked several common, valid-TS constructs that
this compiler rejected outright. Three of them carry no runtime meaning in an
AOT-compiled native binary and are erased by real TypeScript's own emit, so the
correct handling is to parse and discard them rather than fail:

- the `debugger` statement (7 direct cases, `undefined variable 'debugger'`),
- the `readonly T[]` / `readonly [T, U]` array/tuple type modifier (~11 cases,
  misreported as `'const' declaration must be initialized`),
- a leading `this` parameter, `function f(this: T, …)` (~26 cases, `expected
  IDENT, got this`).

## Investigation

- `debugger` reached codegen as an ordinary identifier expression statement —
  the parser had no statement rule for it. It is a reserved word in JS/TS, so it
  can never be a legitimate identifier; treating it as a statement keyword is
  safe. The existing `SEMICOLON` case (`parser/parser_stmts.go`) already models
  a no-op statement as an empty `BlockStatement`.
- `readonly` before a type never reached a handler: `parseTypeAnnotationAtom`
  (`parser/parser_types.go`) expected a type-name/atom and the contextual
  `readonly` keyword derailed it. The mapped-type `{ readonly [K in T]: V }`
  form is consumed earlier in the object-type path, so an atom-level `readonly`
  is unambiguous.
- A `this` parameter is lexed as the reserved `THIS` token, so
  `parseParamList`'s `expect(IDENT)` failed. It is only valid as the first
  parameter and is never a runtime argument.

## Decision

Parse each construct and erase it, matching real TS's runtime behavior:

- **`debugger`**: a statement-level case (recognized via the contextual-keyword
  switch in `parseStatement`) that consumes the token and an optional trailing
  semicolon (ASI-aware `consumeSemicolon`) and returns an empty
  `BlockStatement` — the same no-op node `;` already produces.
- **`readonly T[]`**: in `parseTypeAnnotationAtom`, when the current token is the
  contextual `readonly` and a type follows (IDENT/STRING/`[`/`(`/`{`), consume
  `readonly` and return the underlying type unchanged. The trailing `[]` / tuple
  is parsed by the normal atom machinery, so `readonly number[]` and `readonly
  [T, U]` both work in variable/parameter/return/field positions. Immutability
  is not enforced — the same stance as `Readonly<T>`.
- **`this` parameter**: at the top of `parseParamList`, when no parameters have
  been collected yet and the current token is `THIS`, consume it and its
  optional `: Type` annotation and drop it (no `ast.Param` appended), so the
  real parameters bind by their own positions.

## Implementation notes

- Files: `parser/parser_stmts.go` (`debugger` case in `parseStatement`; `this`
  handling in `parseParamList`), `parser/parser_types.go` (`readonly` branch in
  `parseTypeAnnotationAtom`).
- No AST, resolver, or codegen changes — all three are pure front-end erasure.
- `ReadonlyArray<T>` (the alias spelling) is intentionally out of scope here; it
  would route through the generic-type path, not the modifier grammar.

## Side effects discovered

None. The `arguments` object (also in the blocker histogram) is a genuine
runtime feature, not an erasure, and stays unsupported/documented.

## Verification

  `readonly` array type / array param / tuple type, and `this` parameter on a
  declaration and a function expression. All pass.
- Example: `examples/types/erased-syntax.ts` compiles and runs, output as
  annotated.
- `go test ./parser/ ./lexer/ ./tests/` pass; `go vet` clean.
- TS oracle (`make conformance-ts`) rechecked after the change.
