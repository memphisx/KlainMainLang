# ADR-00211: cross-block `var`/lexical redeclaration early-error (`let x; { var x }`)

- **Relations**: `Extends ADR-00210` (which shipped block-scoped redeclaration checking but left this one intersection case out); `Implements TDD-00070` (closes the cross-nested-block item in its Open questions).
- **Date**: 2026-08-18

## Context

[ADR-00210](ADR-00210.md) added block-scoped redeclaration early-errors but deliberately under-reported one case, listed as a remaining caveat on the Variable declarations status row: the cross-nested-block intersection `let x; { var x }`. A `var` inside a nested block hoists to the enclosing function's scope (ADR-00210's own Stage C), so it collides with a block-scoped `let`/`const`/`class`/`enum` of the same name in an enclosing scope — a `SyntaxError` in real JS (the spec's "a Block's `LexicallyDeclaredNames` must not intersect its `VarDeclaredNames`" static semantics). ADR-00210's checker only compared declarations *within* a single scope, so this collision across a block boundary compiled instead of being rejected.

## Investigation

`resolver/scopecheck.go`'s `checkScopeBody` walks one block/function body and rejects same-scope duplicates, then recurses into nested scopes — but each recursion only ever saw its own level's declarations. The missing piece is, for each scope, the set of `var` names declared *anywhere in its nested subtree* (not crossing a nested function boundary, which owns its own var environment). That set intersected with the scope's own lexical names is exactly the spec's forbidden overlap.

The var-hoisting side already existed (ADR-00210 Stage C promotes a nested `var` to function scope at codegen), so this is purely an early-error the static pass was not yet computing — no codegen change.

## Decision

Extend `scopecheck.go` with a `var`-name gatherer and an intersection check:

- `gatherVars(stmt, out)` recursively collects every `var`-kind binding (plain, list, or destructuring-pattern leaves; plus a `for (var …)` init and a `for (var x of/in …)` loop variable) introduced by a statement and its nested scopes, stopping at a nested `FunctionDeclaration` boundary. `gatherNestedVarNames(body)` runs it over only the scope-*opening* statements of a body, so a `var` declared directly at that level is excluded (that's a same-scope concern already handled).
- `checkVarLexicalIntersection(body, lexicalNames)` reports `identifier 'x' has already been declared`, positioned at the offending nested `var`, when any lexical name in the enclosing scope also appears in the nested-var set.
- `checkScopeBody` now tracks which of its own bindings are lexical (`isLexicalKind` — `let`/`const`/`class`/`enum`) and runs the intersection against its nested vars. `checkLexicalScopes` runs the same intersection at module top level (top-level lexical names vs. nested vars); direct top-level `let x; var x` stays `mangleFileDecls`'s job, so only *nested* vars are gathered at the top level and the two never double-report.

The check is intentionally one-directional and scope-accurate, so the legal inverses stay legal: `var x; { let x }` (a block `let` shadowing an outer `var`) and `{ let x } var x` (non-overlapping scopes) both compile, and a block-scoped `for (let i …)` may still reuse an outer `let i`.

## Implementation notes

- `gatherVars`'s first-write-wins map keeps the *earliest* nested `var` position for the error, and its `FunctionDeclaration` case is the boundary stop; arrow functions and function expressions live in expression position, which the statement-only walk never descends into, so they need no explicit boundary case.
- The intersection is skipped entirely when a scope has no lexical names (the common case), so the extra walk only runs where a collision is even possible.

## Side effects discovered

None new. The remaining Variable declarations caveats after this — no full TypeScript definite-assignment *errors* (a conditionally-unassigned typed `var` reads a zero default), and the generic `undefined variable` message for a `let`/`const` temporal-dead-zone read instead of a distinct "cannot access before initialization" — are unchanged and still tracked on the status row; both require read-detection/flow analysis, a separate piece of work.

## Verification

- 6 new E2E tests in `tests/func_test.go`: nested `var` colliding with an enclosing `let` (function scope and module top level) rejected, `let i; for (var i …)` rejected; the legal inverses (`var x; { let x }`, `{ let x } var x`, `let i; for (let i …)`) still compile and run.
- Full `go test ./...` green (Mac, Apple Silicon M4); `go vet ./...` clean; `make examples` 126/126 (no false positive on the existing corpus).
- `make conformance`: parse-level early-error signal only; the committed Linux baseline `CONFORMANCE-RESULTS.md` is not overwritten from a Mac run (see [ADR-00210](ADR-00210.md)).
