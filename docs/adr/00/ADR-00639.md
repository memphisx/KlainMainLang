# ADR-00639: JSON.stringify `space` for dynamic values, nested-array dynamic literals, and the `any`→pointer coercion

- **Relations**: `Implements TDD-00077` (Track P Stage P4)
- **Date**: 2026-09-02

## Context

TDD-00077's Stage P4 — dynamic (`any`-typed) JSON parse plus dynamic-value /
mixed-array stringify — was left `Partially Implemented` pending the D1 dynamic
object model, which shipped separately (TDD-00155). With D1 in place, a repro
sweep of P4's surface showed the parse-to-dynamic-tree path and the compact
dynamic-value stringify path already worked end to end (`const v: any =
JSON.parse('{…}')` navigates and re-serializes). Three genuine gaps remained,
each found by running compiled programs and diffing against Node, not by reading
code:

1. `JSON.stringify(dynamicValue, null, 2)` was a hard codegen rejection —
   `"JSON.stringify with a space argument is not supported for a dynamic value
   yet"` (`emit_call_json.go:220`). The static path already pretty-prints
   (ADR-00222); the dynamic C walker did not take an indent.
2. A nested **array** literal inside an `any`-typed object literal
   (`{ vals: [1,2,3] }`) was built as a static array boxed as `any`, so both
   dynamic member access (`o.vals[2]`) and `JSON.stringify` failed at runtime
   with `"… statically-typed value in a dynamic position"`.
3. Surfaced while writing the P4 example: `const s: string = <any>` produced
   **invalid IR** (`'%tN' defined with type 'i64' but expected 'ptr'`) — a
   general `any`→pointer coercion hole, not JSON-specific, but reached directly
   by `const text: string = JSON.stringify(v)`.

## Investigation

- The dynamic walker `__kml_dynjson_stringify` / `stringify_val`
  (`codegen/llvm/dynjsonsrc/dynjson.c`) emitted `[`…`]` and `{`…`}` with no
  newline/indent machinery; the compact separators were `,` and `:`.
- `emitDynObjLiteral` (`emit_dynobj.go`) recursed a nested `*ast.ObjectLiteral`
  into `emitDynObjLiteral` but had **no** `*ast.ArrayLiteral` case, so a nested
  array fell to the generic `emitExpr`+`emitBoxValue` path (a static tag-7
  array). `emitDynArrLiteral` was already symmetric (it recurses both nested
  object and array literals) — the object path was the asymmetric one.
- `coerce` (`emit_exprs_coerce.go:14`) handled a dynamic source into
  `float`/`i1`/integer targets but had no `ptr`-target case; `TypeAny`'s IR is
  now `i64` (NaN-boxing, ADR-00628), so a dynamic→string coercion fell through
  the same-IR passthrough and the int/int switch, leaving the raw `i64` box
  register where a `ptr` was required. Confirmed this path *never* compiled
  before (`const a: any = "hi"; const s: string = a`), so adding a case can only
  fix, never regress, previously-compiling code.

Rejected alternative for (3): typing `emitJSONStringifyDynamic`'s result as
`string` instead of `any`. `JSON.stringify` returns `string | undefined`
(undefined for a top-level `undefined`/function value); the dynamic path already
returns a boxed `undefined` for that case, relied on by
`TestE2EDynJSONStringifyLiteralsAndUndefined`. Narrowing the return type to
`string` would turn that into a null pointer and break the `undefined` result.
The general `any`→pointer coercion is the correct, broader fix.

## Decision

1. **`space` for dynamic values.** Thread a `const char *indent` (one indent
   unit, or NULL/"" for compact) through `stringify_val` and
   `__kml_dynjson_stringify`. A new `sb_indent` helper writes a newline plus
   `depth` copies of the unit before each nested element; objects use `": "`
   (colon-space) when pretty, `":"` when compact; empty containers stay inline
   (`{}` / `[]`). The unit is the same compile-time-constant string the static
   path resolves (`jsonSpaceUnit`), interned and passed as the new pointer
   argument; an empty unit passes `null` → byte-identical compact output.
2. **Nested array dynamic literals.** Add an `*ast.ArrayLiteral` case to
   `emitDynObjLiteral` that recurses into `emitDynArrLiteral`, making the object
   path symmetric with the array path.
3. **`any`→pointer coercion.** Add a `target.IR == "ptr" && !target.IsArray`
   case to `coerce`'s dynamic-source block: extract the box's payload
   (`__kml_nb_pay`, which is the data pointer for a string, kind 0) and
   `inttoptr` it. This matches TS's unchecked `any`→`string` assignment (no
   runtime conversion).

## Implementation notes

- C ABI change: `__kml_dynjson_stringify` gains the `indent` parameter *before*
  the `err` out-param; the IR `declare` in `dynjson_c.go` becomes
  `(i64, i64, ptr, ptr)` and `emitJSONStringifyDynamic` gains an `ind
  jsonIndent` argument, matching the static entry points.
- The object walker writes each value to a probe buffer first (a value may be
  skippable — `undefined`/function), so the newline/indent is emitted only for
  entries that are actually written, keeping `wrote`-gated trailing-indent
  correct.
- The coercion case is deliberately scoped to non-array pointer targets; a
  dynamic→typed-array conversion is a different unwrap and is not needed here.

## Side effects discovered

- The `any`→pointer coercion hole (3) is general and was almost certainly
  contributing to the Test262 `clang (invalid IR)` bucket; this fix should
  retire a slice of it. Not separately audited here.
- Fixed a stale comment in `examples/json/json_methods.ts` that claimed nested
  object fields "are not yet supported" while the file itself demonstrates them.

`TestE2EDynJSONStringifyPrettySpace` and
`TestE2EDynJSONNestedArrayLiteralInObject` pass; the full JSON + dynamic-object
+ any suites pass (`go test -run 'TestE2EJSON|TestE2EDynJSON|TestE2EDynObj|
TestE2EDynArr|TestE2EDynProto|TestE2EDesc|TestE2EAny|TestE2EDynStage'`). New

failed. Pretty-print output diffed byte-identical against Node v26 across
numeric and tab units, empties, top-level scalars, floats/unicode, and nested
mixed literals (the only Node difference is its extra multi-line detail appended
to the circular-structure error, whose first line — the `message` — matches).
