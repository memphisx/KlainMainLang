# ADR-01392: Stream handles on their own libuv watchers

- **Relations**: Implements TDD-00244; Extends ADR-01391
- **Date**: 2026-10-04

## Context

[TDD-00244](../../tdd/TDD-00244.md) Stage 4 deletes the bridge hooks of net,
dgram and child processes. The handle table in `klainpool.c` (TCP, UDP,
Unix-domain and IPC pipes, child stdio) still put its descriptors in the
bridge's sets each pass (`__kml_tcp_fdset_add`), held the loop through
`__kml_tcp_keepalive`, and polled every handle in `__kml_tcp_dispatch`.

TLS reads and writes the socket itself until Stage 5 moves it to memory
BIOs, so a `uv_tcp_t` cannot own the descriptor yet. libuv's API for a
descriptor another library reads is `uv_poll_t`.

## Decision

- **Each POSIX handle's descriptor is a `uv_poll_t`** on the thread's
  loop, armed for what the handle waits on: readable while listening,
  reading or handshaking, writable while connecting, writing or when the
  TLS session wants to write. A native that changes this re-arms the
  handle. The dispatch runs from a `uv_check_t` after each poll, from the
  readiness the watchers reported.
- **A watcher is referenced as libuv's stream handles are**: while the
  handle is `ref()`'d, or while writes are queued. The loop's liveness on
  POSIX is `uv_loop_alive`, so these watchers, child processes and
  fs.watch handles hold it as libuv counts them. The bridge's own timer,
  wake and per-descriptor watchers are unreferenced.
- **Work ready without the descriptor** (a close to report, a failed
  connect, decrypted bytes, a shutdown after the last write, a child exit
  held for its streams) starts an idle handle so that poll does not block:
  a referenced one when the work holds the loop, an unreferenced one when
  it does not.
- A handle taking a descriptor makes the bridge release its watcher for
  it (`__kml_loop_fd_forget`); libuv allows one watcher per descriptor.
- **A forked cluster worker calls `uv_loop_fork`** before anything else
  (`__kml_loop_after_fork`). A program that listens before
  `http.listen({ workers })` forks has already created the loop, and the
  workers otherwise share the primary's kernel event queue: under load
  one worker served every request.
- **The bridge's wake is referenced for the duration of its own
  `uv_run`.** The pass has already decided the loop is alive; with only
  unreferenced watchers waiting, `uv_run` would return without polling.
- The three TCP hooks are Windows only, until Stage 6.
- The move to `uv_tcp_t`/`uv_udp_t`/`uv_pipe_t` follows Stage 5's TLS
  move.

## Verification

- Mac (M4): a net echo server and client exit once both close; the
  net, dgram and child-process spawn/exec tests; the httpbin-lite fixture
  idles and answers.
- Linux x86-64 (Ubuntu 24.04 container): test-par passes (14 shards);
  `TestE2EHTTPClusterCombinedWithCreateServer` failed once under load
  before the `uv_loop_fork` call, and every `TestE2EHTTPCluster` test then
  passed 8 runs under 14 busy CPU loops; examples 393/393; Test262 strict
  8498 and js 10506 (unchanged), no invalid IR.
