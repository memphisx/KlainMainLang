# ADR-01428: Implicit-any parameters, async results, contextual positions

- **Relations**: Implements TDD-00230 (P2.3, P2.6, P2.7), Extends ADR-01427, Supersedes ADR-00042 (in the strict lane)
- **Date**: 2026-10-06

## Context

ADR-01427 left the strict lane accepting `function f(a) {}`, typing `a` as a
number (ADR-00042), where tsc under `--strict` reports TS7006. Reporting
TS7006 needs the checker to know where a parameter has a contextual type,
and a first cut reported 69 parameters in the builtin library's own
TypeScript and about 60 in the examples that tsc does not. Those exposed
gaps behind them:

- a call of an async function had no type in the checker at all
  (`f().then(v => …)`), the "async functions' results" item of TDD-00230's
  checker row;
- no context for a returned value, for a `new` of a builtin constructor
  (`new Promise<T>((resolve) => …)`), for an assignment to a property
  (`ws.onmessage = (ev) => …`), or for an optional member whose type is a
  callable interface (`write?: UnderlyingSinkWriteCallback<W>`);
- `resolve()` on a `Promise<void>`'s resolver was "expected 1 arguments":
  tsc lets a trailing parameter that accepts `void` be omitted;
- the checker's parent map skipped a worker module's body, which is
  checked but kept outside `Body` (`Program.WorkerModules`).

## Investigation

- tsc 5.9.3 on probes for each case above, under `--strict --target
  es2022`.
- tsc reports TS7006 only where a parameter has no contextual signature; a
  callback whose callee the checker cannot type yet (a host API it does not
  model) has one in tsc, so a report there would reject a program tsc
  accepts.
- With the checker typing async results, the return types codegen takes
  from the checker (ADR-01427) met three cases where the value returned is
  held wider than its TypeScript type: a hoisted `var` read before its
  assignment (`undefined`, typed `number`), a `null`-initialized field that
  evolves to `any`, and a generator annotated with its yield type (this
  compiler's form).

## Decision

- Checker: TS7006 (TS7019 for a rest, at its `...`) for an unannotated
  parameter with no default and no contextual signature, outside
  `-compat=js`. A function in a position that has a context (an argument,
  a property value, an assigned, returned or awaited value, an element, a
  branch, an annotated variable's initializer) is not reported even when
  the checker cannot name that context.
- Checker: an async function's result is its annotation, else
  `Promise<awaited(body's return type)>` (`Promise<void>` with no value
  returned); an async generator's stays unanswered.
- Checker contexts: a return operand takes the enclosing function's
  declared result (awaited for an async one); a `new` of a builtin
  constructor value takes its construct signature's parameter, with the
  explicit type arguments; `o.p = e` takes `p`'s declared type, except an
  expando assignment (`f.p = e` on a function), which declares `p` from
  `e` and so gives it no context (tsc's assignment declaration). A
  contextual type with `null`/`undefined` members drops them whatever the
  remaining object is.
- `Type.MinArgs` is the one count of required arguments (call arity,
  assignability, overload arity), with tsc's trailing-void rule.
- The parent map walks worker module bodies.
- Codegen keeps its old return type over the checker's where the old is the
  wider storage: `any`, a nullable form of the same type, or a generator
  (`widerStorage`).
- `ast.Param` carries its position.
- Codegen: an unannotated parameter of an arrow or function expression
  with no hint, default or contextual type is `any` in both lanes (it was
  `any` in the strict lane and a number in `-compat=js` for an arrow, a
  number in both for a function expression; `inferExprType`'s mirrors
  follow). An `any` parameter's value is bound for a later parameter's
  default at every call path (`method(x, y = x)`): the binding had skipped
  dynamic parameters, harmless while a method's untyped parameter was a
  number.

## Side effects discovered

- `apps/klainconf/main.ts` assigned `child.pid` (`number | undefined`) to a
  `number`, a type error the spawn result's new type exposes; it now
  defaults to 0.
- Seven example functions had untyped parameters, which tsc rejects; they
  are annotated.
- The first cut of the member-assignment context recursed without bound on
  an expando assignment of a function (`f.x = function () {}`): the
  context read `f.x`'s type, which is the assigned function's. Test262's
  strict lane overflowed the stack on it.

## Verification

- Every probe against tsc 5.9.3: same codes and positions (TS2794 aside).
- Every example and app compiled in the strict lane: no implicit-any report
  outside the seven fixed parameters.
- `go test` of the checker, binder, parser and ast packages; targeted
  end-to-end tests of returns, closures, fields and async iteration.
