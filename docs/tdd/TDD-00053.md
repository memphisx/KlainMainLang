# TDD-00053: npm/`node_modules` interop (best-effort, opt-in)

- **Status**: Not Started
- **Date**: 2026-08-10
- **Notes**: Bottlenecked on [TDD-00022](TDD-00022.md) — npm packages ship compiled JS + signature-only `.d.ts`, neither usable by this compiler; realistic scope is a package that happens to publish its own `.ts` source with ~0 dependencies of its own. Lower priority than [TDD-00054](TDD-00054.md)

## Context

`docs/status/MODULES.md` lists bare/package-style imports (`import x from 'somepackage'`) as ❌, "by design — no package ecosystem." This TDD scopes what it would actually take to lift that, deliberately kept separate from [TDD-00054](TDD-00054.md) (a from-scratch, klainmain-native package manager) — the two have almost nothing in common mechanically once you look closely, and conflating them would blur two very different risk/value profiles.

The direct prompt: could this compiler resolve bare imports against an existing `npm`/`yarn`/`pnpm` project's `node_modules`, the way real Node/TS tooling does? Worth designing precisely rather than hand-waving, because the honest answer is "yes, narrowly, and the narrowness is the important part to get right up front" — see Design.

## Design

### The real blocker isn't resolution — it's that npm packages don't ship what this compiler needs

Node's module resolution algorithm itself (walk up from the importing file through ancestor `node_modules` directories, read `package.json`, follow its entry-point field) is well-specified, well-understood, and not the hard part. The hard part: **npm's whole distribution convention is built around shipping compiled JavaScript (`main`/`module`) plus a separate, implementation-free type-declaration file (`types`/`typings`, `.d.ts`)** — precisely the two artifacts this compiler cannot use. This compiler compiles TypeScript *source* directly to native code; it has no JS runtime, no JS interpreter fallback, and no use for a `.d.ts` file's signatures without a real implementation behind them. Pointing this compiler's resolver at a typical package's `main` field hands it minified/transpiled CommonJS or ESM `.js` — syntactically often outside even this compiler's already-broad JS-superset parsing, and semantically full of exactly the dynamic patterns [TDD-00022](TDD-00022.md) catalogued as unsupported (prototype assignment, dynamic property add, `require`/CJS interop shims, bundler-injected helpers).

So the realistic scope is much narrower than "install any npm package": **a package that happens to publish its own `.ts` source** (some do — a `src/` directory included in the published tarball, or the GitHub repo itself checked out directly instead of the npm-registry tarball) **and stays within [TDD-00022](TDD-00022.md)'s best-effort JS/TS subset once inferred.** This matches the user's own framing going in exactly: "probably simple typescript packages in npm with minimal to 0 dependencies of their own." Any transitive dependency the package itself has must *independently* clear the same bar — since this compiler does whole-program compilation with no separate compilation units ([ADR-00022](../adr/ADR-00022.md)), every transitively-reachable file is merged into one AST, so one incompatible file anywhere in the dependency subtree fails the whole build. Failure probability compounds with dependency depth; "minimal to 0 dependencies" isn't a nice-to-have, it's close to a hard requirement in practice.

### Scope decision: klainmain does not reimplement `npm install`

This TDD does not build a registry client, a `package-lock.json` solver, or anything that fetches packages. `npm install`/`yarn`/`pnpm install` already exist, are already what real projects use, and reimplementing any part of that is pure waste. This TDD's only job is: **given a `node_modules` directory that some other tool already populated**, resolve bare specifiers against it. This also means postinstall-script execution risk is not this compiler's concern at all — whatever the user already accepted by running their own package manager's install step is unchanged; klainmain only ever *reads* the result afterward, never triggers an install.

### Resolution algorithm (V1 scope)

- Triggered only under a new opt-in flag, independent of [TDD-00022](TDD-00022.md)'s own flag (a package could in principle be fully-typed, well-annotated TS needing no inference at all — the two concerns are orthogonal even though in practice almost every real package will need both). Proposed: `-packages=npm` (mirrors `-mm`/`-globals`'s existing shape in `main.go`), off by default.
- A bare specifier (already the case that's rejected today in `resolveImportPath`) triggers, in order: (1) the existing built-in-module check (`fs`/`path`/etc., unchanged, checked first — a real built-in always wins, npm has a long history of userland packages shadowing built-in names and that ambiguity is not worth introducing here); (2) under `-packages=npm`, a Node-style upward walk from the importing file's directory through ancestor `node_modules/<pkg>/` directories to the filesystem root, classic CommonJS resolution — no `package.json` `"exports"` conditional-map support in V1 (real, but substantially more complex than a flat `main`-style lookup, and orthogonal to the actual blocker above).
- Entry-point resolution deliberately does **not** follow `package.json`'s `main`/`module`/`types` fields (they point at exactly the artifacts described above as unusable). Instead: look for a klainmain-specific convention, most likely a dedicated field this compiler recognizes on top of a normal `package.json` (e.g. `"klainmain": "src/index.ts"`) so a package author can opt in explicitly and unambiguously; failing that, a fixed fallback probe (e.g. `src/index.ts` at the package root) as a best-effort guess. No field and no fallback match → a clean, explicit compile error naming the package and explaining why (no compatible TypeScript source found), never a silent fall-through to compiling `main`'s JS.
- Everything past entry-point resolution is unchanged — the resolved file is just another file to the existing `resolver.ResolveProgram` DFS ([TDD-00041](TDD-00041.md)'s per-file mangling, [TDD-00051](TDD-00051.md)'s re-exports, [TDD-00052](TDD-00052.md)'s dependency-ordered top-level execution all apply identically, with zero package-awareness needed anywhere past the initial specifier-to-path lookup).

### Why this is explicitly experimental, not a roadmap commitment

Given the narrowness above, this is realistically most useful as a demonstration/escape-hatch ("if you happen to control or vendor a small TS-source package, you can reach it without copying it into your own tree") rather than "the npm ecosystem is now available." Framed and documented as such if built — `docs/status/MODULES.md` should describe it with the same honesty as this TDD, not oversell it.

## Prerequisites

| Dependency | Status | Notes |

| [TDD-00022](TDD-00022.md) (best-effort vanilla JS compat) | ❌ Not Started | The actual hard blocker — see Design. This TDD is close to inert without it; almost no real package's source clears today's strict-TS-only bar |

## Open questions

- Exact spelling of the klainmain-recognized entry-point field (`"klainmain"`? a nested `"klainmain": { "source": "..." }` object, leaving room to grow?) — undecided, needs to be picked before implementation, not during.
- Whether to support `package.json` `"exports"` conditional maps at all, ever, given their complexity relative to their payoff here (a package targeting this compiler at all is already an edge case; one *additionally* using conditional exports for a klainmain-specific condition is a smaller edge case still) — leaning "not unless a real concrete case demands it."
- Whether this is worth building before [TDD-00054](TDD-00054.md) (klmpm) lands, given klmpm packages are source-only *by construction* and so don't hit this TDD's central blocker at all — current lean, per the conversation that produced both TDDs: klmpm is the higher-value, better-architectural-fit target; this TDD stays a low-priority, opt-in experiment behind it.
