# ADR-00963: Optional parameters in arrow / function-type annotations

- **Implements TDD-00187**
- **Date**: 2026-09-15

## Context

`(x?: T) => void` — an optional-parameter marker inside a function *type*
annotation, and the same marker on an arrow-function *expression*'s first
parameter — failed to parse. Two distinct gaps surfaced:

- `type Cb = (x?: number) => void` — the function-type parser recognized a
  `name:` documentation prefix but not `name?:`, so it tried to read `x` as a
  type and choked on the `?`.
- `const k = (x?: number): number => …` — the arrow-detection lookahead in the
  primary-expression parser did not treat a leading `IDENT ?` as an arrow
  parameter list, so `(x?: …)` was parsed as a parenthesized ternary
  (`unexpected token : in expression`).

## Investigation

- `parser/parser_types.go:384` — function-type param loop matched only
  `IDENT COLON` for the optional documentation name.
- `parser/parser_literals.go:1905` — the `LPAREN` arrow-detection disjunction
  lacked an `IDENT QUESTION {COLON|RPAREN|COMMA}` arm.
- Once both parsed, `const f: Cb = (x?: T) => …` segfaulted: the arrow body
  emits an optional `?`-param with the nullable-scalar `{i1,T}` ABI
  (`optionalParamType`/`undefinedableElem`, emit_undefined.go:23), but the
  variable's declared function type `Cb` carried a *plain* scalar param type —
  the parser discarded the `?`. The slot's function-pointer ABI disagreed with
  the closure it held.

## Decision

1. Function-type parser: accept `name?:` and record the optionality on the
   parsed param `TypeAnnotation` as `Nullable + Undefined` (`T | undefined`),
   which `resolveType` lowers to exactly the same nullable-scalar Type as
   `undefinedableElem`, so a typed binding's slot ABI matches the arrow body.
   Same treatment applied to the object-type method-signature tail.
2. Arrow-detection lookahead: an `IDENT` followed by `?` and then `:`, `)`, or
   `,` is an optional first parameter → parse as an arrow. The existing
   `parseArrowFunction` already handled the `?` marker on the params
   themselves.
3. **Contextual parameter-ABI typing.** A closure's parameter optionality ABI is
   authoritatively the *expected* function type's when one exists — a
   `const f: F = …` binding or a function-typed argument slot — overriding the
   closure's own `?` markers (`contextualParamOptionality`). Routed through
   `emitExprWithObjectHint`'s new `hint.IsFunc` case, which emits the arrow /
   function expression against `hint.FuncParams`. A `?`-param bound into a
   required slot rides the plain ABI (the slot guarantees presence, so the
   marker is vacuous); a plain param bound into an optional slot widens to the
   nullable-scalar aggregate the caller marshals. This makes every binding site
   — variable, argument, (and any other `emitExprWithObjectHint` consumer) —
   agree on the ABI, not just the direct-`const` case.
4. **First-class-call arity checking.** A closure `Type` now carries
   `FuncParamOptional []bool` (a `?`-declared, defaulted, or rest parameter is
   optional), populated at closure-value construction (`setFuncParamDefaults`,
   shared by the emit and `inferExprType` paths) and at function-type-annotation
   resolution (from a new parallel `ast.TypeAnnotation.FuncParamOptional`, which
   the parser records distinctly from the `T | undefined` ABI marker so an
   explicit union still requires its argument). `emitClosureCallByPtr` rejects a
   missing argument for a required parameter — the same clean arity error a named
   function's call site already emits — instead of the previous silent
   zero-fill. The HOF-callback path (`emitCBCall`) is unchanged: there the
   runtime always supplies the element/index/array, so a callback declaring fewer
   parameters is genuine JS undefined-binding, not a missing required argument.

## Implementation notes

- `parser/parser_types.go` — both the function-type atom and
  `parseObjectTypeSignatureTail` now thread a `paramOptional` bit onto the param
  annotation.
- Ternaries in parens (`(a ? 1 : 2)`) are unaffected: the new arm requires the
  token after `?` to be `:`/`)`/`,`, never an operand.

## Side effects discovered

- The initial parser-only fix left an ABI skew (arrow declaring *more* optional
  params than its declared type) that segfaulted; decision 3 (contextual
  parameter-ABI typing) closes it at every binding site, not just `const`.
- The HOF-callback path (`map`/`filter`/`reduce`) already threads element-type
  hints through `emitArrowFunctionWithHints`; `contextualParamOptionality` only
  touches a scalar param's nullable/undefined dimension when the hint is a
  concrete type, and an HOF element is always present, so an optional HOF
  callback param safely drops to the plain ABI. Verified no regression.
- Closing the ABI skew surfaced a pre-existing closure-arity looseness (a
  first-class call with fewer args than required params zero-filled silently
  where a named call already errored); decision 4 closes it so the two call
  paths agree.
