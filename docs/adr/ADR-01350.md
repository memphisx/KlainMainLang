# ADR-01350: TS7051/TS7006, TS2416, TS2749, TS2552 and scoped TS2304 in the strict lane

- **Relations**: Extends ADR-01342, ADR-01349
- **Date**: 2026-10-03

## Context

Backlogs 49, 34, 33, 32, 37 and 47. The strict lane accepted programs tsc rejects under
`--strict`:
- a function type whose parameter has a name but no type: `type F =
  (string) => void` is TS7051, and `(x) => void` is TS7006;
- a class member that overrides its base's with an incompatible type:
  `m(x: string)` over `m(x: number)` is TS2416;
- a value with no type meaning used as a type: `const C = class {}` then
  `let c: C` is TS2749;
- a misspelled type name near a known one (`Pont` for `Point`): tsc's
  TS2552. The checker left it unreported, so the program compiled;
- a type name used outside the block, function or namespace that declares
  it (`const k: Kind` for a namespace's `Kind`): TS2304. Type names were
  checked against every declaration in the program;
- a member a namespace import's module does not export (`fs.nopeSync()`):
  TS2339 on `typeof import("fs")`. The resolver left a bare `fs`, which
  surfaced as "cannot find name 'fs'".

## Investigation

- tsc's `reportImplicitAny` gives a signature parameter without a type
  TS7051 ("did you mean 'arg0: string'?") when the parameter is in a
  function type, call signature or method signature and its name is a
  type keyword or resolves to a type. Otherwise it gives TS7006, or TS7019
  for a rest parameter.
- The function-type parser fills in an untyped parameter's type as `any`,
  so the checker could not tell `(x) => void` from `(x: any) => void`.
- TS2416 compares each derived member with the base member of the same
  name. Method parameters are bivariant, which `relate` already models.
- Untyped parameters of function *declarations* (`function f(x)`) are not
  TS7006 here. That lane keeps its parameter-type inference (ADR-00042)
  and is a separate decision.

## Decision

1. **`SignatureParameter.Untyped`** marks a parameter the parser gave
   `any`. `checkTypeNames` walks function types, method signatures and
   call signatures, and `checkSignatureParams` reports TS7051 (a type
   keyword, or a name that resolves to a type), TS7006 or TS7019.
2. **`checkOverrides`**: for a non-generic class with a modelled base, each
   own, non-private, non-accessor member whose type is not assignable to
   the base's (missing members count) is TS2416 at the member.
3. **`valueAsType`**: a type reference that resolves to no type, while
   scope lookup finds a program value with no type meaning (a variable or
   function, not a class, enum or import), is TS2749 ("did you mean
   'typeof C'?") instead of TS2304.
4. **TS2552**: a type name nothing resolves (TypeScript's libraries and
   `@types/node` included) within tsc's spelling distance of a known one is
   reported with that suggestion, from the sorted candidates, within tsc's
   ten-suggestion budget.
5. **Scoped type names**: the binder exposes the scope each node opens
   (`OpenedScope`) and the namespace scope of each desugared member statement
   (`StatementScope`). `checkTypeNames` carries the innermost scope down, and
   a name that resolves in no enclosing scope but is declared by the program
   in a non-enclosing one is TS2304. Type parameters keep the program-wide
   check.
6. **Unknown namespace-import members**: the resolver's rename pass, which
   replaces `ns.member` with the member's mangled name, reports a member
   the module does not export as TS2339 with tsc's `typeof import("…")`
   type text. An unlisted member of a builtin class (`emitter.nope()`)
   already reported TS2339.

## Implementation notes

`ast/type_nodes.go` (the walker regenerated), `binder/binder.go`, `parser/parser_types.go`,
`resolver/resolver.go`, `resolver/rename.go`,
`checker/check.go`, `checker/check_test.go`, `diag/messages.go`,
`codegen/llvm/emitter.go` and `examples/classes/classes.ts`.

`examples/classes/classes.ts` used a class expression's binding as a type
(`m: Money`), which tsc rejects with TS2749. It now writes
`InstanceType<typeof Money>`, which codegen resolves as it resolves the
class (`decideAnnotationType`, test `TestE2EInstanceTypeOfClassExpression`).

## Side effects discovered

- `class D extends B { v: number }` over `v: number | string` is accepted by
  tsc and by the checker, but codegen rejects a field redeclared with a
  different type: a representation limit, not a type error.
- TS2416 lands on the member's declaration position (one column after
  tsc's).
