# ADR-00117: RegExp Stage 3 — str.match() and str.matchAll()

- **Relations**: Implements [TDD-00035](../tdd/TDD-00035.md). Extends [ADR-00114](ADR-00114.md), [ADR-00115](ADR-00115.md), [ADR-00116](ADR-00116.md)
- **Date**: 2026-08-07

## Context

[TDD-00035](../tdd/TDD-00035.md)'s Stage 3 is `str.match(regexp)` and `str.matchAll(regexp)`, explicitly scoped as thin wrappers reusing Stage 2's (`.exec()`, [ADR-00116](ADR-00116.md)) match-loop machinery rather than a peer stage. Picked up directly following Stage 2, per the user's "continue with Stage 3."

## Investigation

**Re-derived real JS's exact `.match()`/`.matchAll()` semantics directly rather than trusting the TDD's own Design section**, and found a real mistake in it: the TDD stated `.match()`'s global-mode result is "never `null` — an empty array on zero matches, matching real JS." That's wrong. Real JS's `%Symbol.match%` (the algorithm `String.prototype.match` delegates to) returns `null` when zero matches were found, in both the global and non-global cases — an empty array is never returned by `.match()` at all. Confirmed directly rather than assumed, since this is exactly the kind of detail worth double-checking before encoding it into a compiler. Per `docs/tdd/README.md`'s own convention ("If the real implementation diverged from the original design, that divergence belongs in the ADR... not retrofitted into the TDD's Design section"), the TDD's Design text is left as originally written (a historical record of the thinking at the time, including this mistake) and only its `Status` line is updated — this ADR is where the correction actually lives.

**Confirmed `.match()` without the `g` flag is byte-for-byte identical in shape to `regexp.exec(str)`** (full match + capture groups array, or `null`) — real JS's spec literally defines the non-global case as "return `RegExpExec(rx, S)`." This meant Stage 2's per-call matching logic (previously the body of `emitRegexExec` directly) needed to become a reusable subroutine callable from a different receiver shape (`.exec()` is `regexp.exec(str)`; `.match()` is `str.match(regexp)` — object and argument swapped) — refactored `emitRegexExec` into a thin wrapper around a new `emitRegexSingleMatchCore(objVal, strVal Value) Value`, with no behavior change to `.exec()` itself.

**Confirmed `.match()`'s global-mode loop and `.matchAll()`'s loop are structurally identical**, differing only in what gets collected per match (real JS: `.match()`'s global algorithm resets `lastIndex` to `0`, then loops calling the exec-equivalent — which itself reads/writes `lastIndex` each iteration since `global` is true — collecting each match's full text only, until a call returns `null`; `%RegExpStringIteratorPrototype%.next` behind `.matchAll()` does the identical loop, yielding the *whole* per-call match array instead). Factored this shared shape into `emitRegexCollectGlobalMatches`, parameterized by a `storeElem` callback deciding what actually lands in each destination slot.

**Confirmed `.matchAll()`'s "eager `string[][]` instead of a real lazy iterator" scope decision (already made in the TDD) composes for free with existing nested-array machinery.** TDD-00029's `storeArrayElem`/`loadArrayElem` (boxed `{ptr,i64}`-behind-a-`ptr`-slot representation for an array-typed array element) already handles exactly this shape with zero new boxing logic needed — confirmed by using `storeArrayElem(destSlot, ArrayOf(TypePtr), matchValue)` directly inside `emitRegexCollectGlobalMatches`'s callback and testing a real `for (const m of str.matchAll(re))` loop, which worked immediately.

## Decision

- Refactored `emitRegexExec` (`emit_regexp.go`) into a thin argument-evaluating wrapper over the new `emitRegexSingleMatchCore(objVal, strVal Value) Value` — the entire single-match/lastIndex-mutation/result-array-building logic from Stage 2, now callable from any context that already has an evaluated `(RegExp instance, subject string)` pair. Also factored `emitRegexLoadField` (a named-field GEP+load helper) out of what was previously an inline closure, and rebuilt `emitRegexHandleLoad` on top of it.
- `emitRegexCollectGlobalMatches(regexVal, strVal Value, storeElem func(destSlot string, match Value)) (dataReg, countReg string)`: resets `lastIndex` to `0`, then runs a two-pass count-then-fill loop calling `emitRegexSingleMatchCore` repeatedly until it returns the null sentinel — the same "runtime counts, then builds the array" shape `__kml_split` already established for a hand-written C-runtime-text helper, but built here as directly Go-emitted IR instead, since each pass needs to call back into an already-Go-emitted function (`emitRegexSingleMatchCore`), not something a separate raw-text helper could invoke. Each pass re-runs the identical deterministic match sequence (real PCRE2 work happens twice per match — an accepted simplicity tradeoff, matching `README.md`'s own "not production-ready" framing).
- `emitStringMatch`: loads the RegExp argument's `global` field and branches at runtime (never known statically) — non-global delegates directly to `emitRegexSingleMatchCore`; global calls `emitRegexCollectGlobalMatches` with a `storeElem` that extracts just index 0 (the full-match string) from each per-call result, then returns `null` if the final count is `0` (the corrected behavior — see Investigation), otherwise the collected `string[]`.
- `emitStringMatchAll`: throws a catchable `TypeError` if `global` is false (matches real JS's own hard requirement), otherwise calls `emitRegexCollectGlobalMatches` with a `storeElem` that boxes the *whole* per-call match array via `storeArrayElem`, returning `ArrayOf(ArrayOf(TypePtr))` — never `null` (real JS's `matchAll` always returns a real iterator; an empty array is the natural eager equivalent for zero matches, not `null`).
- No implicit string-to-RegExp coercion for either method's argument (a compile-time error instead) — the same documented scope narrowing `.search()` already established (`docs/status/STRING-METHODS.md`).
- Dispatch: plain, unguarded `mem.Property == "match"`/`"matchAll"` checks in `emit_call.go`, positioned alongside `.replace`/`.split`/`.search` (not the `IsRegExp`-receiver-guarded shape `.test`/`.exec` use) — these are *string* methods (receiver is the string, argument is the RegExp), matching the TDD's own framing, not RegExp-instance methods. The string-vs-non-string and RegExp-argument-vs-not checks happen inside the target functions themselves, the same convention `.replace`/`.split` already use.

## Implementation notes

Files touched: `codegen/llvm/emit_regexp.go` (the `emitRegexExec`/`emitRegexSingleMatchCore` split, `emitRegexLoadField`, `emitRegexCollectGlobalMatches`, `emitStringMatch`, `emitStringMatchAll`), `codegen/llvm/emit_call.go` (dispatch), `codegen/llvm/emit_exprs_types.go` (`inferExprType` cases — `"match"` → `regExpExecResultType()`, `"matchAll"` → `ArrayOf(ArrayOf(TypePtr))`, both unconditional, matching `"split"`'s existing unconditional case rather than `.test`/`.exec`'s `IsRegExp`-guarded ones).

No `emit_exprs_vardecl.go` change was needed — like `.test()`/`.exec()` before them, `match`/`matchAll` are ordinary `MemberExpression`-callee calls, and `emitVarDecl`'s existing generic fallback (`inferred.IsArray` triggering `ty = inferred`) already routes an unannotated `const m = str.match(re)`/`const all = str.matchAll(re)` through `inferExprType` correctly.

## Side effects discovered

None found while implementing this stage specifically — the three general bugs found and fixed while building Stage 2 ([ADR-00116](ADR-00116.md)) were prerequisites this stage relies on (`m !== null`/`if (m)` against a nullable array, string content-based truthiness) but nothing new surfaced here.
