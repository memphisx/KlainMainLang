# ADR-00145: Top-level side-effecting code in imported files (dependency-ordered, cycle-guarded)

- **Relations**: Implements [TDD-00052](../tdd/TDD-00052.md)
- **Date**: 2026-08-10

## Context

The last deliberate V1 scope narrowing named in `resolver/resolver.go`'s package doc and [ADR-00022](ADR-00022.md): imported (non-entry) files could only contain declarations, no bare executable top-level statements. Real ES modules run a file's top-level code once, in dependency order, the first time it's imported, with a guard against re-running on a cycle. [TDD-00052](../tdd/TDD-00052.md) scoped closing this.

A pre-implementation investigation (see the TDD's own Design section for the full writeup) found the acyclic case would be nearly free — `codegen/llvm` has no concept of "file" at all, and the resolver's existing dependency-first `order` already gives run-once, diamond-safe, dependency-ordered execution as a structural side effect of how files are already visited and deduplicated. That same investigation surfaced a real, pre-existing, undocumented bug: `validateDeclarationsOnly` already permitted `VarDeclaration` unconditionally in non-entry files, including its initializer expression — so a circular pair of files could already (before this ADR) read each other's not-yet-initialized top-level binding, an uninitialized-LLVM-alloca read with no clean error. No existing test exercised this shape. Closing it became part of this TDD's own scope rather than a separate fix, since "guard against re-running on cycles" was already the feature's stated goal.

## Investigation

See [TDD-00052](../tdd/TDD-00052.md)'s Design section for the detailed reasoning already captured pre-implementation (dependency order and diamond-dedup already correct for free; function/class position-independence in codegen already confirmed by direct read; why the merge step itself needed zero changes). Confirmed empirically during implementation:

- `TestE2EImportCircular` (pre-existing) only exercises circularly-calling *functions* — safe regardless, since functions are position-independent `define`s. It does not exercise a circular *variable* read, which is exactly the gap found.
- The entry file is always positionally safe regardless of its own cyclic-ness: the final merge unconditionally appends the entry file's body last, strictly after every file in `order` — including any cyclic cohort it happens to structurally participate in (e.g. entry imports A, A imports back to entry) — so the restriction never needs to apply there.

## Decision

**Cycle detection** (`resolver/resolver.go`'s `visit` closure): added `stack []string` (the current DFS recursion chain) and `onStack map[string]bool`, pushed/popped around each file's own recursion via `defer`. On the existing "already seen" branch, if the target is also currently on `stack` (a real back-edge, not just an already-finished diamond dependency), every file from the target's stack position to the top (inclusive) is marked in a new `cyclic map[string]bool` — covering cycles spanning more than two files. This is a deliberate superset-safe approximation of exact SCC detection, not full Tarjan: over-marking only costs a file some ergonomics (it stays on the stricter rule below), never a safety hole.

**Validation moved out of `visit`, into a new post-DFS pass.** `validateDeclarationsOnly` used to run inline, per-file, immediately after parsing — but a file's cyclic-ness can only be known once the *entire* DFS completes (a much-later back-edge from a different branch of the graph can still retroactively mark an already-finished file). The call now happens in a new loop over `order` (after `visit(entryAbs, true)` returns), only for `cyclic[path]` files.

**Two rules, split on cyclic-ness:**
- **Acyclic non-entry files**: no restriction at all — any top-level statement is allowed. The merge step (`resolver.go`'s final `merged.Body = append(...)` loop) needed *zero* changes; it already appended each file's full, unfiltered body (`unwrap` only ever stripped `Import`/`ExportFrom` nodes and unwrapped `ExportDeclaration`, never filtered by statement kind) — the validation call was the only thing keeping non-declaration statements out.
- **Cyclic non-entry files**: `validateDeclarationsOnly` renamed to `validateCyclicFile` and extended — same allowed-statement-kind set as before (function/var/let/const/interface/type/enum/import/export-from/class, no bare executable statements), **plus** a new check: a top-level `VarDeclaration`'s `Init`, if present, must satisfy a new `isLiteralExpr` — a number/string/boolean/null/undefined literal, a prefix `+`/`-` on a numeric literal, or an array/object literal whose elements/property values are themselves (recursively) literals. No identifier reference, no call, no member access — nothing that could observe another binding's not-yet-run initialization survives the check. Closes the bug precisely without modeling real ES modules' TDZ/live-binding semantics.

**Explicitly out of scope**, per the TDD: class *static* field initializers carry the same theoretical hazard but are not covered by `isLiteralExpr` — `ClassDeclaration` stays unconditionally allowed in a cyclic file either way. Noted as a known caveat, not silently dropped.

## Implementation notes

- `resolver/resolver.go`: `visit` gained `stack`/`onStack`/`cyclic`; the inline `validateDeclarationsOnly` call removed from inside `visit`, replaced by a new post-DFS loop over `order`; `validateDeclarationsOnly` renamed to `validateCyclicFile` with the new `VarDeclaration` case; new `isLiteralExpr` helper. Package doc comment updated to describe the new split (acyclic vs. cyclic) instead of the old blanket restriction.
- No codegen changes — confirmed by the pre-implementation investigation and by the full test/example suite passing unmodified against `codegen/llvm`.
- `tests/imports_test.go`: the pre-existing `TestE2EImportExecutableStatementInNonEntryFileRejected` asserted behavior that is no longer correct (an acyclic non-entry file's bare statement is now legal) — renamed to `TestE2EImportExecutableStatementInAcyclicNonEntryFileRuns` and converted from an error-expectation to an output assertion, rather than left half-obsolete or duplicated alongside a new test making the same point.

## Side effects discovered

The bug named in Context — already covered above as the reason `isLiteralExpr`/cyclic-file handling exists at all, not a separate discovery from this pass.

## Verification

- 6 new tests in `tests/imports_test.go`: a 3-level acyclic dependency chain asserting exact execution order (`TestE2ETopLevelSideEffectDependencyOrderChain`), a diamond-shared dependency asserting its top-level code runs exactly once (`TestE2ETopLevelSideEffectDiamondRunsOnce`), a cyclic file with a bare statement still rejected (`TestE2ECyclicFileBareStatementStillRejected`), the exact bug scenario — a circular pair each reading the other's top-level binding — now rejected (`TestE2ECyclicFileNonLiteralVarInitRejected`), and a cyclic file with a literal-only initializer still working (`TestE2ECyclicFileLiteralVarInitStillAllowed`).
