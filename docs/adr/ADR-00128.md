# ADR-00128: WebSocket Stage 3 — client-side `new WebSocket(url)`

- **Relations**: Implements TDD-00039 (Stage 3 of 4, the last — Stage 0 was ADR-00125, Stage 1 was ADR-00126, Stage 2 was ADR-00127); fixes a real bug in ADR-00126's own `ensureBase64EncodeBytes`
- **Date**: 2026-08-08

## Context

TDD-00039's final stage: `new WebSocket(url)` for `ws://` only, per the TDD's own design — a real outbound `connect()` (this codebase's first, per the TDD's own Context section investigation), a synchronous connect+handshake (a deliberate simplification the TDD explicitly left open, avoiding new non-blocking-connect machinery in the event loop's hand-rolled `select()` call), and a fifth event-loop-scanned resource (mirroring `EventSource`'s own "grow-only array, not fiber-parked" shape) for the ongoing, non-blocking post-handshake read side.

This stage surfaced more real bugs than any prior one — five, all found by actually running the feature end-to-end rather than by inspection, several of them intermittent or silent enough that they would not have been caught by code review alone. Each is documented below with how it was found, since the "how" is as important as the fix for a codebase whose own standing rule is to distrust unverified platform/runtime claims.

## Investigation & Decision

**Design**, per the TDD: `WebSocketClientType()` (`types.go`) with a hidden handle field pointing at a new runtime entry (`{ i64 fd, i64 state, i64 pendingNotify, ptr buf, i64 consumedOffset, ptr instance }`) in a new grow-only array (`@__kml_wsc_data/_len/_cap/_active`, `runtime_websocket_client.go`). `new WebSocket(url)` (`emit_websocket_client.go`) parses the URL via the same `curl_url`/`CURLUPART_*` machinery `new URL(...)` already uses (passing `CURLU_NON_SUPPORT_SCHEME` so a `ws://` scheme parses even though libcurl doesn't treat it as a transport it supports), rejects anything but `ws://` (a synchronous throw — a malformed URL/unsupported scheme is a programmer-facing contract issue, not a network failure), generates a `Sec-WebSocket-Key` via the existing `__kml_crypto_random_bytes`, and calls `__kml_ws_client_open` (`runtime_websocket_client.go`) — a single function performing DNS resolution (`inet_pton` fast path, `getaddrinfo` fallback for a real hostname, **Linux-only** for the fallback: `struct addrinfo`'s field layout is not POSIX-stable the way `sockaddr_in`'s already-relied-upon layout is, and this project's own standing rule is to verify such an offset directly rather than trust it from memory — not yet done for Darwin, so a hostname argument on macOS fails cleanly there rather than risking a wrong-offset struct read; a numeric IP host still works on both), a blocking `connect()`, sending the handshake request, and blocking-reading + validating the response (status line, `Sec-WebSocket-Accept` — computed via the newly-factored-out `emitComputeWSAccept`, shared with the server's own Stage 1 handshake rather than duplicated).

**The synchronous-connect ordering problem and its fix**: `.onopen`/`.onmessage`/`.onclose`/`.onerror` can only be assigned *after* `new WebSocket(url)` returns, but by then the connection has already succeeded or failed (it's synchronous). Solved via a `pendingNotify` flag on the entry: `readyState` is set immediately (the real, already-known outcome), but the *callback* invocation is deferred to the client's first `__kml_wsclient_scan()` pass — by which point top-level script code has had a chance to run the assignments. A failed connect/handshake never throws (matching real `WebSocket`, which never throws synchronously for a network failure) — it fires `onerror` then `onclose` on that same deferred first pass instead.

## Bugs found and fixed (all during this stage's own end-to-end testing)

1. **`ensureBase64EncodeBytes` read one byte past the input buffer** (a real bug in ADR-00126's own Stage 1 code, not new to this stage). It copied `__kml_btoa`'s "clamp the index to `len` and read anyway" trick, which is only safe for `__kml_btoa` because a null-terminated C string guarantees a real, defined `0x00` at `str[len]`. A raw 20-byte SHA-1 digest has no such guarantee — `digest[20]` is uninitialized stack/heap memory. Found via a client/server accept-value mismatch that was *consistently wrong by a fixed amount per compiled binary* (always +3 in the base64 alphabet, every run) rather than randomly wrong — the signature of reading a fixed-but-garbage stack byte, not a logic error in the encoding math itself. Fixed by replacing the clamp-and-read with real branches (`br i1 %has1/%has2`) and a `phi` merging a genuine `0` for the padding case, never issuing the out-of-bounds load at all. Verified against a known-input isolated test (`bytes(range(1,21))` against Python's own `base64.b64encode`) and re-confirmed the original SHA-1/handshake known-answer tests (Stage 0/1) still pass.
2. **A real SSA-dominance bug introduced while fixing bug 1**: the rewritten `loopcheck:` block's `phi` nodes claimed their back-edge value came from `%loopbody`, but after inserting new labeled blocks (`b64loadb1`/`b64mergeb1`/etc.) between `loopbody:` and the loop's own tail code, that tail code — including the `br label %loopcheck` back-edge — was now textually part of block `%b64mergeb2`, not `%loopbody`. This produced not wrong values but an actual infinite loop in the compiled program (confirmed as a stray process still spinning at 99.9% CPU from an earlier, pre-fix test run, 17 minutes later). Fixed by updating the `phi`'s predecessor label to `%b64mergeb2`. This is the same *class* of bug ADR-00125's own encode-function fix addressed (a stale/incorrect predecessor reference), independently rediscovered — worth calling out as a real, repeating risk in this file's hand-rolled-IR style whenever new blocks are spliced into the middle of an existing one.
3. **The client's event-loop scan (`__kml_wsclient_scan`) was unreachable for a WebSocket-only program.** Its call site was placed inside `__kml_event_loop_run`'s `checkes` block, mirroring `__kml_eventsource_scan`'s own call site exactly — but that block only runs when `%hascurl` is true (`@__kml_curl_multi` initialized), which `EventSource` can rely on (it can't exist without curl) but a pure-POSIX-socket WebSocket client cannot: a program using only `new WebSocket(url)` (no `fetch`, no `EventSource`) never touches curl at all, so `%hascurl` stays false and the scan call was never reached. Found via `onopen`/`onmessage` simply never firing in an otherwise-correct manual test. Fixed by moving the call to `afterselectok`, unconditional on `%hascurl`.
4. **A pending client notification could wait far longer than necessary — including, with a longer-lived real timer in the same program, effectively indefinitely, until that unrelated timer happened to fire.** `select()` legitimately has nothing to wake it early on a freshly-connected, freshly-returned `new WebSocket(url)` (nothing has been sent yet, so there's nothing for the peer to answer, so the fd isn't readable) — so it blocks for whatever the next real timer's wait is, or forever with none. Fixed with a new `%forcezero` flag (set by the same `wscsetloop` fd-registration pass whenever it sees a `pendingNotify` entry) that both routes `select()` into the timed-wait path *and* clamps that path's own computed wait to zero, overriding a real timer's own (possibly much longer) remaining wait — the first attempt only did the former, which turned out not to be sufficient on its own once a real timer's `%bestfire` was already set to a distant, real value.
5. **`.close()` didn't update its own entry's `state`/`fd`, causing `select()` itself to start failing on every subsequent iteration.** The original design left full cleanup to the *next* scan pass noticing a failed `read()` (`EBADF`) on the closed fd — but `__kml_event_loop_run`'s own fd-set-registration loop re-adds any entry still marked `state=OPEN` to `select()`'s watched set every iteration, and `select()` is permitted to fail outright (and did, in practice) when handed an already-closed fd. Its existing failure handling skips straight back to `outerloop` without ever reaching the timer-fire check — starving the whole program's *unrelated* timers from ever firing again, hanging indefinitely. Fixed by having `.close()` itself immediately mark the entry `CLOSED` (state, fd, `readyState`, `@__kml_wsc_active`) and fire `onclose`, rather than deferring that to a read that will now never happen.

## Implementation notes

- Files touched: `ast/nodes.go` (`NewWebSocketExpression`), `parser/parser_literals.go` (`new WebSocket(url)` parsing), `codegen/llvm/types.go` (`WebSocketClientType`, `IsWebSocketClient`), `codegen/llvm/runtime_websocket_client.go` (new), `codegen/llvm/emit_websocket_client.go` (new), `codegen/llvm/emit_websocket.go` (factored `emitComputeWSAccept` out of the Stage 1 handshake code so the client can reuse it), `codegen/llvm/runtime_encoding.go` (bug 1 fix), `codegen/llvm/runtime_http.go` (bugs 3 and 4's fixes, in `__kml_event_loop_run`), `codegen/llvm/emit_call.go` (`.send()`/`.close()` dispatch), `codegen/llvm/emitter.go` (`e.usedWSClient` keep-alive gate, mirroring `e.usedEventSource`).
- `wss://` is rejected with a distinct, clearer error message than an arbitrary unsupported scheme, per the TDD's own open question — not implemented, a real, separately-tracked follow-on.
- A client can never connect to a server in its own process (the blocking connect needs the very event loop it's blocking to ever accept and answer) — documented directly in `examples/websocket/websocket_client.ts` after first writing the example the wrong way and hitting exactly this deadlock.

## Side effects discovered

- Bug 1 (the base64 buffer overread) affected the **already-shipped** Stage 1/2 server-side handshake too (`emitComputeWSAccept`'s only other caller): any real `http.listen(..., { ws })` server had roughly a 1-in-256-per-digest-byte chance of computing a wrong `Sec-WebSocket-Accept` whenever the byte past the 20-byte stack digest happened to be non-zero — which, being stack-layout-dependent, would be *consistent* within one compiled binary and thus easy to misdiagnose as "works for me" during any manual testing that didn't specifically vary the input. Now fixed for both sides by the same shared function.
- No other opcode/frame-handling behavior changed — this stage is purely additive on top of Stages 0-2.
