# TDD-00021: `#x` real private fields

- **Status**: Implemented
- **Date**: 2026-07-31

## Context

[TDD-00009](TDD-00009.md) Stage 4 ([ADR-00084](../adr/ADR-00084.md)) built
TypeScript's `private`/`protected` keyword modifiers — a compile-time-only
access restriction, erased with zero runtime trace, exactly matching real
TypeScript's own behavior. That deliberately left out `#x` syntax: the
*other*, older privacy mechanism, a real ECMAScript language feature (not
TS-specific) that TypeScript also accepts directly. Flagged as a documented
gap rather than silently missing (`docs/status/LANGUAGE-CONSTRUCTS.md`'s
own row for it) and picked up here for real scoping, per this project's
standing rule that a feature needing a design pass gets a TDD before
implementation.

The two mechanisms are not redundant. `private balance: number` is a
same-named field that instance-typed reflection can still see —
`Object.keys(acct)`, `JSON.stringify(acct)`, `{...acct}` all show
`balance`, matching real TypeScript exactly (its privacy is a type-checker
concept, invisible to the JS runtime `private` compiles down to). `#balance:
number` in real JS is genuinely hidden from every one of those — reflection
never sees a `#`-prefixed key at all, because at the language level a
private name literally isn't a string-keyed property. That's the actual
gap: not a second syntax for the same behavior, but a mechanism with a
real, observable different guarantee this compiler's `private` categorically
can't provide (having been built explicitly as zero-runtime-cost).

## Design

### What's genuinely new vs. what Stage 4 already built

Confirmed directly (`codegen/llvm/types.go`'s `VisibleFields`): today's
`private`/`protected` fields are *not* stripped from `VisibleFields()` —
only the hidden tag/vtable fields are. That's correct and intentional
(matches real TS), but it also means the **access-control** half of `#x`
(can this line of source code even write `obj.#balance`) is *identical* in
shape to what `private` already enforces: exact-class-only, no subclass
access, no protected-style relaxation (real JS has no `#`-equivalent of
`protected` — a private name is always exactly-declaring-class-only).
`registerClasses`' existing `FieldOrigin`/`OwnFieldVisibility` maps and
`checkMemberVisibility` (`emit_classes.go`) already implement exactly this
check for `vis == "private"`. The only **new** runtime-observable behavior
`#x` needs is the reflection-hiding — everything else can reuse Stage 4's
machinery directly, keyed by name.

### Front end: `#name` as part of the identifier, not a modifier keyword

Unlike `private`/`protected` (keywords preceding a normal name), `#` is
part of the field/method's actual name (`#balance`, not `private balance`)
— real JS spec treats it as a distinct token kind (`PrivateIdentifier`),
syntactically valid only in member-declaration and member-access position,
never usable as a plain variable name. Confirmed via grep: `lexer/lexer.go`'s
`NextToken` currently only recognizes an identifier starting with a
letter/`_`/`$` (`readIdent`, entered at line ~111); `#` has no lexer
handling anywhere. Smallest faithful change: recognize `#` immediately
followed by a valid identifier-start character as the start of a distinct
token (e.g. `PRIVATE_NAME`, literal including the `#`), reusing
`readIdent`'s existing scan loop for everything after the `#`. This keeps
`#foo` from ever tokenizing as a usable plain identifier anywhere outside
the positions that explicitly accept a `PRIVATE_NAME`.

Two places need to accept the new token: `parser_classes.go`'s member loop
(a field/method name may now be `PRIVATE_NAME` as well as `IDENT` — no
`private`/`protected` modifier applies to it, since the `#` already fully
determines its visibility) and wherever a `MemberExpression`'s property is
parsed (`this.#balance`, `obj.#balance` — currently always expects
`lexer.IDENT` after the `.`).

### Real JS's lexical restriction — deliberately not enforced at parse time

Real JS additionally requires `#name` (bare, as in the `#x in obj`
ergonomic brand-check form, or in member position) to be a `SyntaxError`
unless it appears textually inside the body of a class that actually
declares that private name — checked at parse time, before any semantic
analysis. Threading a "which private names are visible right now" stack
through the parser is real, additional plumbing this design deliberately
punts on: `super`'s own Stage 3 precedent already established the cheaper
alternative this project uses elsewhere — parse permissively, reject
semantically once the surrounding class context is known
(`registerClasses`/`emitClassMember`, which already track exactly this via
`"__kml_enclosing_class"`). A `#name` reference outside any class, or
naming a private field/method the enclosing class doesn't actually declare,
becomes a `checkMemberVisibility`-shaped compile error instead of a
parser-level one — same end result (a clean compile-time rejection, not a
silent miscompile), less new machinery. `#x in obj` itself (real JS's
"ergonomic brand check," testing private-field presence without throwing)
is not scoped here at all — a separate, smaller follow-on if ever needed,
not blocking the core feature.

### Reflection hiding — the one genuinely new runtime-observable piece

`VisibleFields()` (`types.go`) currently strips a fixed-count leading
prefix (tag, optionally vtable) by index — sufficient for those, since
they're always at fixed leading positions. A `#`-named field can be
*anywhere* among a class's own declared fields, interleaved with public
ones, so hiding it needs a name-based filter over the full field list, not
an index slice — a small, mechanical extension (filter `Fields` on `!
strings.HasPrefix(f.Name, "#")` in addition to the existing index-based
skip), touching every one of `VisibleFields()`'s existing call sites for
free (`Object.keys`/`values`/`entries`, `JSON.stringify`, spread, `for...in`
— all already route through this one function, per its own doc comment).

### Deliberately out of scope for V1

- **Runtime brand-check on `any`/`unknown` access.** Real JS throws a
  `TypeError` reading `obj.#x` where `obj` isn't an instance of the
  declaring class — for a *statically*-typed access this compiler already
  gets for free (the field wouldn't resolve via `FieldIndex` on a
  non-matching static type, a compile error, not a runtime one). Only a
  dynamic (`any`/`unknown`) receiver could reach a mismatched-class
  `#field` access at runtime at all, and this compiler's `any`/`unknown`
  machinery is already narrow by design ([ADR-00008](../adr/ADR-00008.md)'s
  Staged V1) — a real but narrow gap, not addressed here.
- **The strict lexical (parse-time) validity restriction** — see above;
  semantic (registration/emission-time) rejection is the chosen substitute.
- **`#x in obj` ergonomic brand checks.**
- **Static private fields (`static #x`)** — real JS allows this too;
  omitted only because it's a straightforward combination of two features
  each independently supported (Stage 4 `static`, this TDD's `#x`), not a
  new mechanism — a natural, low-risk follow-on once both exist, not
  designed further here.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `private` access-control semantics (exact-class-only) | ✅ already exists | `FieldOrigin`/`OwnFieldVisibility`/`checkMemberVisibility` ([ADR-00084](../adr/ADR-00084.md)) — reusable as-is once `#name` fields are registered through the same maps |
| `"__kml_enclosing_class"` lexical-context tracking | ✅ already exists | `emitClassMember`/`emitClassStaticInit` ([ADR-00084](../adr/ADR-00084.md)) — what makes semantic (not parse-time) lexical-validity rejection possible |
| `#` as a lexer token | ❌ not started | No handling anywhere in `lexer/lexer.go` — confirmed via direct grep |
| `MemberExpression` property accepting a private name | ❌ not started | Every property-parsing site currently hard-expects `lexer.IDENT` |
| Name-based (not index-based) field hiding in `VisibleFields()` | ❌ not started | Current implementation only strips a fixed leading-index prefix (tag/vtable) — needs a filter pass, not just a wider slice |
| Parser-level "declared in an enclosing class" validity stack | ❌ deliberately out of scope | Substituted with semantic (registration-time) rejection instead — see Design |

## Open questions

- Should a `#name` reference that fails validation report as a parse error
  or a `registerClasses`-time compile error, given this design's "parse
  permissively, reject semantically" choice? Leaning toward the latter
  (consistent with how `super` misuse is already reported) but not
  decided — worth checking the resulting error message still reads clearly
  at an unexpected position (e.g. `#foo` used as a bare top-level
  expression, which would otherwise need its own parser-level handling to
  even reach the semantic check).
- Whether `#name` fields should be allowed to shadow/coexist with a
  same-named public field on the same class (real JS: `x` and `#x` are
  entirely different names, no collision) — expected to fall out for free
  from the existing name-uniqueness checks, since they're different exact
  strings, but not verified against actual code yet.
- Whether this is worth building at all before a concrete need shows up:
  `private` already covers the overwhelmingly common "keep implementation
  details out of the public API surface" use case for this project's
  actual target programs (CLI tools, microservices) with a real hidden
  gap only for code that specifically relies on `#`-field reflection-hiding
  (e.g. serializing an object and expecting private data to be silently
  excluded) — a real but narrower need than `private` itself was.
