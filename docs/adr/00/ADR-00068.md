# ADR-00068: Add native Go fuzz testing for the lexer and parser

- **Relations**: Extended by [ADR-00070](ADR-00070.md)
- **Date**: 2026-07-28

## Context

The lexer and parser are hand-written recursive/character-driven code with a lot of lookahead and bespoke edge-case handling (template literal nesting, `>>>` vs `>>`/`>=` disambiguation, JSDoc-comment splicing into the token stream, and so on). That kind of code is exactly where a single malformed or adversarial input can trip an unbounded loop, an off-by-one slice, or an index-out-of-bounds panic that the existing table-driven unit tests, which only cover inputs someone thought to write by hand, would never surface. There was no fuzzing in the project before this.

## Investigation

Confirmed the module targets Go 1.26 (`go.mod`), which has full support for native fuzzing (`go test -fuzz`, stable since Go 1.18) — no external fuzzing framework needed.

Looked at the two candidate entry points:
- `lexer.Tokenize(src string) ([]Token, error)` (`lexer/lexer.go:461`) — pure, no side effects.
- `parser.Parse(src string) (*ast.Program, error)` (`parser/parser.go:20`) — pure, calls `Tokenize` internally.

Considered fuzzing further down the pipeline (codegen, or the full compile-to-binary path via `clang`), but rejected that as a starting point: those stages shell out to an external compiler, so each fuzz iteration would be orders of magnitude slower, and most randomly-mutated token/AST input isn't a meaningful "valid IR was miscompiled" signal — it's just "malformed input was rejected," which the lexer/parser layer already tests far more cheaply. Fuzzing codegen is a reasonable follow-on but wasn't scoped here.

## Decision

Added one native Go fuzz target per package, in a new `fuzz_test.go` file alongside each package's existing `_test.go` file (same external test-package convention, `lexer_test`/`parser_test`):

- `FuzzTokenize` (`lexer/fuzz_test.go`) — calls `lexer.Tokenize`, asserts that a successful tokenization always ends with a trailing `EOF` token, and treats a returned error as an acceptable outcome (malformed input is expected to be rejected cleanly, not to panic or hang).
- `FuzzParse` (`parser/fuzz_test.go`) — calls `parser.Parse` and only requires it not panic or hang; a `Parse` error is an acceptable outcome for almost any fuzzed input since most byte strings aren't valid TypeScript.

Both seed corpora combine a curated set of literal strings (covering the trickier lexer/parser edge cases already exercised by the hand-written unit tests — template literal nesting, `>>>=`, arrow vs. `==`, unterminated strings/comments, JSDoc, empty/malformed programs) with every `.ts` file under `examples/` (walked and added via `f.Add` at seed time), so the corpus starts from real, representative KlainMainLang source rather than only hand-picked snippets.

Added a `make fuzz` target (`Makefile`) that runs both fuzz functions for a configurable duration (`FUZZTIME`, default `30s`), matching the existing `make test`/`make examples` shortcut conventions — `-run=^$` so plain `go test`/`make test` still only runs the seed corpus as regular test cases (fast, deterministic, CI-safe) and never enters actual fuzzing unless `-fuzz` is explicitly requested.

## Implementation notes

Files touched: `lexer/fuzz_test.go` (new), `parser/fuzz_test.go` (new), `Makefile` (`fuzz` target + `.PHONY` entry).

Both fuzz functions walk `../examples` with `filepath.Walk`, filtering to `.ts` files, and ignore read errors per-file rather than failing the whole seed step — a seed corpus that's missing a few files is fine, but a fuzz target that can't even start because one example file has a permissions problem is not worth failing over.

Go's native fuzzer persists any failing input under `testdata/fuzz/<FuzzName>/` in the package directory the first time it finds a crasher, so that regression gets checked into the repo and replayed by every future `go test` automatically. No such files exist yet, since no crasher was found — nothing to check in for now, but future contributors should expect `testdata/fuzz/` directories to appear and get committed if a crash is ever found.

## Side effects discovered

None. Both targets ran clean (see Verification) — no crashers, no hangs.

## Verification

- `go vet ./lexer/... ./parser/...` — clean.
- `go test ./lexer/... ./parser/...` — passes (runs both fuzz functions' seed corpora as ordinary test cases).
- `go test ./...` — full suite still passes.
- `go test ./lexer/ -run=^$ -fuzz=FuzzTokenize -fuzztime=30s` — ~10.8M executions, 0 crashers.
- `go test ./parser/ -run=^$ -fuzz=FuzzParse -fuzztime=30s` — ~10.2M executions, 0 crashers.
- `make fuzz FUZZTIME=3s` — confirmed the Makefile target itself runs both in sequence correctly.
