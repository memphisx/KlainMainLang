# ADR-00430: the ClientRequest handle — request().end(), abort, response/error events

- **Relations**: Extends [ADR-00429](ADR-00429.md), [ADR-00412](ADR-00412.md); part of [TDD-00138](../tdd/TDD-00138.md)
- **Date**: 2026-08-28

## Context

`http.get`/`request` returned void, so the ubiquitous corpus shapes
`http.request(options, cb).end()` and `const req = http.request(…);
req.end()` failed ("a number has no method 'end'", ~17 files + the
'close'/'abort' neighbors). Node's contract: `request()` sends nothing
until `.end()`; `get()` auto-ends.

## Decision

Both calls return a ClientRequest handle — `{ ptr url, ptr userCb,
i64 state }` (0 pending · 1 fired · 2 aborted):

- The per-site firing tail (fetch_async + reaction registration +
  drive-or-defer) is extracted into a once-emitted
  `@__kml_httpc_begin(url, cb)` (the completion thunk likewise became
  once-emitted — it never had per-site content). `get` stores state 1
  and begins immediately; `request` stores state 0.
- `.end()` (no body — a body argument is a clean Stage-2 rejection)
  fires a pending request via `@__kml_httpc_req_end`; `.abort()`/
  `.destroy()` cancel only a not-yet-fired request (an in-flight libcurl
  transfer is not torn down — caveat); `.on('response', cb)` binds the
  callback slot; `.on('error', cb)` is accepted but never fired (no
  async transport-error delivery exists — failures throw instead, so a
  `mustNotCall()` error listener behaves correctly on success paths).
  Methods return the handle, so chaining works.
- Inference: http/https `get`/`request` → `ClientRequestType()`;
  handle methods chain.

## Implementation notes

`emit_http_client.go` (begin/req_end extraction,
`emitClientRequestMethod`), `types.go` (`IsClientRequest`),
`emit_call.go` dispatch, `emit_exprs_types.go` inference (http + https).

## Side effects discovered

None; the ADR-00429 variable-options branch composes with this
unchanged.
