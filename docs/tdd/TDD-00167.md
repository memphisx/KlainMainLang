# TDD-00167: `events` async helpers — `once` and `on`

- **Status**: Implemented
- **Date**: 2026-09-03

Both shipped: `events.once` ([ADR-00675](../adr/ADR-00675.md), on top of the Promise<T[]> fix [ADR-00674](../adr/ADR-00674.md)) and `events.on` ([ADR-00677](../adr/ADR-00677.md), on top of array-yielding generators [ADR-00676](../adr/ADR-00676.md)). The `on` design below was implemented as a synthesized eager-registration setup + async-iterator pair — see the ADR.

## Context

[TDD-00165](TDD-00165.md) Stage 4 named `events.once` / `events.on` — the
`events` module's static helpers — as module-only extras. Both integrate an
`EventEmitter` with async control flow: `once` returns a `Promise` of the event's
arguments; `on` returns an async iterator that yields them.

## Design

### `events.once(emitter, name)` — desugar to a Promise

Reuse the existing Promise + EventEmitter machinery rather than new low-level
plumbing: `once(ee, name)` is emitted as

```
new Promise<elem[]>((res, rej) => ee.once(name, (…args) => res([…args])))
```

The listener's parameters are typed from the event's payload by the existing
`EventEmitter.once` hinting; the args are packed into an array and passed to
`resolve`, matching Node's contract that `once` resolves with the argument array
(`const [v] = await once(ee, 'x')`). The synthesized `Promise` carries an explicit
`<elem[]>` type argument because the value type isn't inferrable through the
nested listener. This depends on the **Promise<T[]> value fix** ([ADR-00674](../adr/ADR-00674.md)) — array-valued promises were corrupt before it.

**V1 scope.** Single-value events and homogeneous multi-argument (same-type
tuple) events → `Promise<elem[]>`; a mixed-type tuple event has no single array
element type (this compiler's arrays are homogeneous) and is a clean rejection.
Payload-less events and non-scalar payload element types are also deferred.

### `events.on(emitter, name)` — async iterator (deferred)

`on` returns an `AsyncIterableIterator` that yields an args array on each emission,
buffering events that arrive between iterations. A faithful implementation needs a
per-iterator event queue and the async-iterator protocol wired to `for await`; a
naive `while (true) yield await once(...)` loses events emitted during processing,
so it is deliberately not shipped as an approximation. This is the load-bearing
remaining piece — its own stage.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Promise machinery + async/await | Built | `once` desugars to `new Promise` |
| `Promise<T[]>` value support | Built | [ADR-00674](../adr/ADR-00674.md) — required for `once`'s array result |
| `EventEmitter.once` + payload typing | Built | The listener's params are hinted from the event payload |
| Async iterator + `for await` protocol | Built (generators) | `on` needs a custom async-iterable object over an event queue |

## Open questions

- **`on`'s buffering model**: an unbounded queue (Node's default) vs. a bounded
  one with a documented cap; and how a `close`/`return` on the iterator
  unregisters the listener.
- Mixed-type multi-argument events for `once`: a tuple-typed promise value (rather
  than a homogeneous array) would lift the V1 restriction, but needs
  tuple-valued-promise support end to end.
