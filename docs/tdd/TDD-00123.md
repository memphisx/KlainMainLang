# TDD-00123: `number` as IEEE-754 double (JS-faithful) instead of i64

- **Status**: Implemented (Stages 1–4; Stage 5 audit + Stage 6 docs folded in)
- **Date**: 2026-08-26

## Context

TypeScript/JavaScript's `number` is a 64-bit IEEE-754 double. This compiler
instead models a bare `: number` (and every plain integer literal) as a signed
64-bit integer (`TypeI64`), with `/** @type {float64} */` as an opt-in double.
That is the single largest fidelity gap in the project — the first caveat on the
Type-primitives status row — and it silently miscomputes ordinary code:

- `const x: number = 0.1 + 0.2` yields `0` (should be `0.30000000000000004`)
- `10 / 3` yields `3` (should be `3.3333333333333335`)
- `5 % 2` on fractional operands truncates
- `2 ** -1` yields `0` (should be `0.5`)

The goal: make `number` default to `float64` so untyped arithmetic matches
JS/TS, while keeping the existing integer types (`/** @type {int8..int64,
uint8..uint64} */`) as the escape hatch for real integers (loop-tight code, C
interop, bit manipulation).

The float machinery already exists and is pervasive — `TypeF64`/`TypeF32`, a
per-`Value` `Type.Float` flag, `fadd`/`fdiv`/`fcmp` arithmetic, `fptosi`/`sitofp`
coercion, and dtoa-based printing are all in place and used by the current
`float64` support. Literals containing a `.` already produce `TypeF64` and do
**not** truncate; mixed int/float arithmetic already promotes to double. So this
is mostly about flipping the *default* an integer-looking literal / bare
`number` resolves to, then auditing every site that hard-codes `TypeI64` (or
`.IR == "i64"`) as a stand-in for "a number."

Scoped now because the user has prioritized JS fidelity for `number`, and
because the recently-landed front-end fidelity work (ADR-00372–00376) makes the
arithmetic gap the most visible remaining divergence.

## Design

### The three seams that must agree

A plain integer literal's type is decided in three places that bypass each other;
all three must flip together or they desync (the map's top desync risk):

1. `ResolveTypeName` — `codegen/llvm/types.go:1853`, `case "number": return
   TypeI64` → `TypeF64`. Governs every `: number` annotation, `number[]`, object
   field, param, return.
2. `emitNumberLit` — `codegen/llvm/emit_exprs.go:~202`. A `.`-bearing or
   oversize literal is already `TypeF64`; a plain integer literal (`42`) is
   `TypeI64` → change to `TypeF64`. Hex/bin/oct literals (`0xFF`) are a separate
   decision (see Open questions).
3. `inferExprType` for `*ast.NumberLiteral` — `codegen/llvm/emit_exprs_types.go:302`
   — must mirror `emitNumberLit` exactly.

Everything else follows from the `Type.Float` flag these produce.

### What comes for free

- **Arithmetic** (`emitBinary` `emit_exprs_operators.go:8`, and its compound-assign
  twin `emitArith` `:704`): the `+ - * / % **` int/float fork already keys on
  `ty.Float`. Both must be kept in lockstep (the second desync risk).
- **Comparison**: `fcmp` vs `icmp` fork at `:286` already handles NaN-correct
  predicates.
- **Unary `-`, `++`/`--`**: already float-aware (`fneg`, `fadd 1.0`).
- **Printing**: `emit_call_console.go:147` and `emitValueToString`
  `emit_exprs_types.go:37` route floats through dtoa (shortest round-trip),
  which prints an integer-valued double as `5`, not `5.0`. Verified today:
  `float64 = 5` prints `5`, `0.1 + 0.2` prints `0.30000000000000004`.
- **Coercion**: `coerce` (`emit_exprs_coerce.go:6`) has the full int↔float matrix.

### The decisions that aren't free

**Bitwise / shift results must be `number` (double), not i64.** JS computes `&
| ^ ~ << >> >>>` via `ToInt32`/`ToUint32` but the *result is a Number*. If the
result stayed `TypeI64`, then `const x = 5 & 3; x / 2` would do integer division
(→ `1`) instead of `1.5`. So: compute in the integer domain (32-bit truncation,
as `emitBitShift` already does for shifts), then `sitofp` the result back to
`TypeF64`. Operands coerce via `ToInt32` (`fptosi` to i32, mod 2^32). Sites:
`emit_exprs_operators.go:317-360`, `inferExprType` `emit_exprs_types.go:~458`.

**Integer-valued builtins that return `number` must return `TypeF64`.** In JS
`Math.floor`, `Math.round`, `Math.ceil`, `Math.trunc`, `Math.abs`, `parseInt`,
`Number()`, and count/index queries (`.length`, `indexOf`, `charCodeAt`, …) all
return doubles. Keeping them i64 reintroduces the division-fidelity bug the same
way bitwise would (`arr.length / 2`). They must return `TypeF64` (an
integer-valued double). Sites: `emit_call_math.go` (`:127` floor etc.),
`emit_call_number.go`, string/array length + index queries.

**Array/string/typed-array indices stay i64.** `arr[i]` coerces the index to
`TypeI64` (`emit_exprs_member.go:243`); with a float `number` index this becomes
an `fptosi` truncation — correct for valid indices. Review NaN/negative index
edges. Internal induction vars in `for...of`/`for...in` (`emit_stmts.go`) are
compiler-private i64 and stay i64.

**Map/Set number keys need a float-safe strategy.** `valueToMapKey`
(`emit_collections.go:578`) currently `fptosi`-truncates a number key to i64, so
`1.5` and `1` would collide. Reuse the `bitcast double → i64` pattern
`valueToMapVal` already uses (`:597`) so the full 64-bit double pattern is the
hash key. `Map<number>` internal storage stays an i64-slot map; only the
key-encoding changes.

**Date stays i64.** `Date` is `IR:"i64"` (ms since epoch). `Date − Date` returns
a `number`, so that *result* becomes `TypeF64` (`emit_exprs_operators.go:~255`),
but Date's internal representation and arithmetic stay i64.

**any/unknown boxing.** `TypeAny = { i8, i64 }` (`types.go:1808`) already boxes a
float `number` by bitcasting through the i64 payload slot; verify unbox
reconstructs `TypeF64` from the tag (`emit_dynamic.go`).

**Genuinely-integer builtin struct fields stay i64.** `status`, `readyState`,
`lastIndex`, cpu-time buckets, fds, etc. (`types.go:647,650,782,964,1006,…`) are
integer by nature — audit individually, do not blanket-flip. User object/interface
`number` fields follow `ResolveTypeName` automatically.

**Unannotated param/return defaults** (`emit_func.go:1444,1493,1625,2017`, the
`Inferred` i64 default) become `TypeF64`.

### Staging

Each stage compiles, tests, and ships independently; fidelity improves
monotonically.

- **Stage 1 — value-model flip.** The three seams + unannotated-default flip.
  Arithmetic/comparison/printing ride existing float paths. Delivers correct
  `0.1+0.2`, `10/3`, `5%2`, `2**-1`. Biggest test-corpus churn (integer-division
  assertions).
- **Stage 2 — integer-boundary operators.** Bitwise/shift → `ToInt32` compute,
  `TypeF64` result; `Math.floor/ceil/round/trunc/abs`, `Number()`, `parseInt`,
  `Date − Date` → `TypeF64`.
- **Stage 3 — counts & indices.** `.length`, `indexOf`/`lastIndexOf`/`search`/
  `charCodeAt`/`codePointAt`/… → `TypeF64`; audit index-coercion sites for the
  `fptosi` boundary.
- **Stage 4 — collections & any.** Float-safe `Map`/`Set` number keys; any/unknown
  box/unbox round-trips a `TypeF64`.
- **Stage 5 — escape hatch & interop.** Confirm `/** @type {int8..int64,uint*} */`
  still work and interconvert cleanly; freeze the genuinely-integer builtin
  fields as i64 (audited list).
- **Stage 6 — corpus & docs.** Migrate tests/examples asserting integer `/`/`%`/
  `**`; update status pages (drop the Type-primitives i64 caveat, revise the
  `**`/operator caveats, sweep every "number → i64" claim) and note the
  superseded framing in the affected ADRs.

## Open questions

- **Integer literals in integer contexts.** JS makes *every* literal a double.
  Simplest and most faithful: `42` → `TypeF64` unconditionally, coercing at
  int-required sites (index, bit op, typed-array, explicit int-typed target).
  Confirm no builtin that takes an integer count regresses (`new Array(n)`,
  `.repeat(n)`, `setTimeout(fn, ms)`) — all should coerce cleanly.
- **Hex/bin/oct literals** (`0xFF`, `0b101`, `0o77`). JS still makes these
  doubles, but they read as bit-pattern intent. Flip them to `TypeF64` too for
  consistency, or keep as `TypeI64`? Leaning flip-for-consistency, since
  `0xFF / 2` should be `127.5`.
- **A whole-program `-number=int` opt-out?** The escape hatch is per-binding
  (`/** @type {int64} */`). A program that is entirely integer-arithmetic (a CLI
  cruncher) pays the double-vs-int perf cost everywhere. Worth a `-compat`-style
  flag to restore i64 as the default? Not needed for correctness; note as a
  possible follow-on.
- **Loop-counter performance.** `for (let i = 0; i < n; i++)` makes `i` a double
  with an `fptosi` at every `arr[i]`. Correctness-first; a later optimization
  could detect integer-only induction variables and keep them i64. Out of scope
  for the initial stages.
- **`Number.MAX_SAFE_INTEGER` boundary.** Doubles are exact to 2^53; beyond that,
  precision loss matches JS exactly. No action needed, but document it.
- **`-0` / `NaN` / `Infinity`.** Already produced as `TypeF64`; confirm they flow
  through comparisons, `Object.is`, `Number.isNaN`, and map keys correctly once
  `number` is float everywhere.
