# ADR-00818: `-webview=sailfish` on-device bring-up — the shim runs on real hardware

- **Relations**: `Extends ADR-00816, ADR-00817`, `Implements TDD-00146`

- **Date**: 2026-09-09

## Context

[ADR-00817](ADR-00817.md) made `-webview=sailfish` cross-build a real aarch64
binary. This ADR is the on-device bring-up: running that binary on a physical
Xperia 10 II (Sailfish 5.1.0.11) over an SSH/tmux session and getting a
klain:webview app to render, round-trip a `bind` call, and exit cleanly — the
last tier TDD-00146 Stage 3 could not reach without hardware.

## Investigation

Binaries were transferred to the device by base64-chunking through the tmux SSH
session (no scp/HTTP — the device's classifier blocks binding a local server) and
run under the session's inherited Wayland env (`XDG_RUNTIME_DIR=/run/user/100000`,
`WAYLAND_DISPLAY=../../display/wayland-0`, `QT_QPA_PLATFORM=wayland`). A
`KLAIN_WV_DEBUG` env gate was added to the shim to trace its lifecycle to stderr
(it has no page-console visibility — Gecko page `console.log` does not surface).
Five distinct failures were found and fixed, each only observable on device:

1. **Operations before the view was ready.** `loadHtml`/`runJavaScript` issued
   from the constructor were rejected: *"run javascript can be called only after
   view is initialized."* The `RawWebView` is usable only after it emits
   `viewInitialized()`.
2. **RawWebView as the QML root → 0×0.** `RawWebView { anchors.fill: parent }` as
   the root item has no parent, so `anchors.fill` is a no-op and it never sizes —
   a blank window even after the page loaded.
3. **Inactive view → no paint.** Even sized and loaded, a `RawWebView` does not
   paint unless `active: true` (the shipped `WebView.qml` sets it too). This was
   the actual white-screen cause.
4. **page→native bridge did not deliver.** A `CustomEvent` on `window`
   (non-bubbling) with the frame script's bubble-phase `addEventListener` never
   reached the frame script. It works only as a **bubbling** event on `document`
   caught in the **capture phase** with `wantsUntrusted=true` (a page-script event
   is untrusted).
5. (confirmed working, not a fix) `loadFrameScript("file://…")` executes, and
   `sendAsyncMessage` → the chrome-side `recvAsyncMessage` signal delivers — the
   transport the bridge relies on.

## Decision

- Queue every view operation (`navigate`/`setHtml`/`eval`) until `viewInitialized()`,
  then flush; do the message-listener subscription, `forceViewActiveFocus`, and
  frame-script install in that handler. `init`/`bind` only *store* their scripts;
  they are injected on `domContentLoaded` (guarded to the `true` transition), when
  `runJavaScript` is valid.
- QML is a sized root `Item` (grown to the window by `SizeRootObjectToView`) with
  `RawWebView { anchors.fill: parent; active: true }`; the view is located via
  `findChild("kmlRawWebView")`.
- The bridge: page `window.external.invoke` dispatches a **bubbling** `kmlrpc`
  `CustomEvent` on `document`; the frame script catches it with
  `addEventListener('kmlrpc', …, /*capture*/ true, /*untrusted*/ true)` and
  forwards `sendAsyncMessage('embed:kmlrpc', …)`; the chrome side's
  `recvAsyncMessage` runs the bound trampoline. Native→page (`eval`, promise
  resolution) uses `runJavaScript`.
- A `KLAIN_WV_DEBUG` stderr trace is kept in the shim (zero-cost when unset) —
  a device-tethered backend needs it for future bring-up.

## Implementation notes

All in `webview_sailfish.cpp`: `mReady`/`mPending` + `whenReady()`, the
`onViewInitialized` slot, the wrapped-`Item` QML + `findChild`, `active: true`,
and the `document`/bubbles/capture bridge (`kExternalInvokeJS`, `kFrameScriptJS`).
The page-tick pump (`__kml_tick`, ADR-00439) already rides the same `webview_bind`
path, so klain-level timers/microtasks/promises are pumped on the GUI thread with
no extra work.

## Side effects discovered

The `__kml_tick` pump round-trips through the page at ~60 Hz (CustomEvent →
frame script → `sendAsyncMessage` → `recvAsyncMessage`), which is heavier over
embedlite's IPC than the system backend's WebKit message handler. It is correct
and matches the system backend's page-driven design, but a **native `QTimer`
driving the tick thunk directly** would avoid the per-tick IPC — recorded as a
perf follow-up, not a behavior gap (the faithful behavior works now).

## Verification

On a physical **Xperia 10 II (Sailfish 5.1.0.11)**: a cross-built
`-webview=sailfish` smoke app (window + `w.html(...)` + a `w.bind("done", …)` the
page calls from a `setTimeout`) **renders** ("Γεια σου Xperia", white on dark
blue — confirmed visually), the **bind round-trips** (`KLAIN_ONDEVICE_BIND_OK`
with the page's argument delivered to the native callback), and **exits cleanly**
(`terminate()` → `run()` returns → `KLAIN_ONDEVICE_RUN_RETURNED`). Gecko fell
back to offscreen/software rendering (the Adreno GL compat libs are absent) and
still composited correctly. `go build`, `go vet`, `TestE2EWebviewBackendFlag`
green on macOS. `-webview=sailfish` is now working end-to-end, engine to screen.
