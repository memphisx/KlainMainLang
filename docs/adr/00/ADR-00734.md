# ADR-00734: Windows CI lane — the Win32 shim did not compile against the runner's mingw headers

- **Relations**: Extends [ADR-00733](ADR-00733.md) (the first matrix runs), [ADR-00719](ADR-00719.md) (the Win32 shim)
- **Date**: 2026-09-06

## Context

Both matrix runs of the day ended the Windows lane red after 50 minutes with 386 failing tests, every one a link error (`undefined reference to swapcontext`, `socket`, `stat`, …) or a `stat` field read as garbage. The lane looked like a hang from outside; the log shows the whole suite ran, every program failing to link because the Win32 shim objects were missing from the link line. On this development box the same commit passes.

## Investigation

`win32fs.c` declares the Linux mode bits it writes into the IR's stat layout as an enum named `S_IFMT`, `S_IFDIR`, …. The runner's MSYS2 (`update: true`, mingw-w64 headers newer than this box's 14.0.0.r92) pulls `<sys/stat.h>` in through `<windows.h>`, where those names are macros (`#define S_IFMT _S_IFMT` → `0xF000`), so the enum became `0xF000 = 0170000` and clang stopped with "expected identifier". The compiler warns and continues without the shim objects (`win32ShimObjects` returns an error, `win32LinkArgs` prints it), so every subsequent link lacked the platform layer; the concurrent re-attempts to rewrite the cached shim source also produced the "user-mapped section open" warnings in the log. The `stat`-shaped failures were the UCRT's own `stat` being linked in the shim's place.

## Decision

`win32fs.c` `#undef`s the six `S_IF*` names before its enum, so the enum is correct whether or not a header defined them. The fix is verified to compile with both LLVM's clang and MSYS2's `mingw-w64-ucrt-x86_64-clang` on this box (the latter installed for the purpose, since the lane builds with it); the runner's newer headers are what exercises the `#undef` path.

## Side effects discovered

- A shim compile failure degrades to a warning and a doomed link for every test rather than a clear early failure. A follow-up could make `go build`'s Windows lane run a one-program smoke compile before the suite so a shim problem fails in seconds, not 50 minutes.
- MSYS2's clang warns that the shim's `strerror` is "redeclared without dllimport"; harmless (the shim deliberately shadows the CRT's).

## Verification

Windows 11: the `fs`, fetch-abort, promise, embed and `os.cpus()` groups that failed on the runner pass with the fixed shim; the next matrix run is the runner-side confirmation.
