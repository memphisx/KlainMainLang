# ADR-00253: Async generators (`async function*`) and `for await...of`

- **Relations**: `Implements TDD-00085` (Stages 2–3); builds on [ADR-00172](ADR-00172.md) (sync generators), [ADR-00244](ADR-00244.md) (coroutine tasks), [ADR-00249](ADR-00249.md) (settled task promises)
- **Date**: 2026-08-20

## Context

Sync generators ([ADR-00172](ADR-00172.md)) are per-instance ucontext fibers that
`yield` back to their caller; coroutine tasks ([ADR-00244](ADR-00244.md)) are
fibers that `await` on the scheduler. An async generator is the fusion — a fiber
that both `yield`s to a consumer and `await`s — with `.next()` returning a
`Promise<{value,done}>`. Stage 1 ([TDD-00085](../tdd/TDD-00085.md)) added the
`for await...of` parse; this ADR adds the async-generator runtime and the
consumer codegen. Before this, `async function*` was silently mis-compiled as a
*sync* generator (the `async` ignored).

## Decision

**One fiber, driven to the next yield per `.next()` (`emitAsyncGeneratorNextByValue`).**
An async generator reuses the sync-generator instance struct and fiber
unchanged. Its `.next(v)` swaps into the fiber (running the body to its next
`yield`/`return`) and returns an *already-settled* `Promise<{value,done}>`:
fulfilled with the result, or rejected if the body threw. Two additions over the
sync path make the fusion work:

- **`await` inside the body busy-drives.** `current_task` is saved (in memory, so
  it survives a `longjmp`) and reset to `null` across the swap, so an `await` in
  the generator body takes the top-level drive path (a `fetch` busy-spins; a task
  promise drives `sched_step`) instead of mis-parking the *consumer* task. Emitting
  an async-generator body sets `hasMaySuspend` and pulls the task runtime so those
  awaits emit the scheduler-driven path.
- **A throw rejects the outstanding `.next()`.** The swap is bracketed in a
  `setjmp`; a throw from the body (which already propagates back through the swap,
  as sync generators confirm) is caught and settles the promise rejected (marking
  the generator done). `current_task` is restored on both the normal and catch
  paths.

`.next()`'s result type is `Promise<{value,done}>` (`GeneratorIsAsync` on the
generator type drives both the type inference and the `.next()` dispatch).

**`for await...of` (`emitForAwaitOfGenerator`).** The async analogue of the
sync generator for-of: each `.next()` promise is awaited (`__kml_task_await_ready`
+ re-throw a rejected step via `emitTaskRethrowIfRejected`) before reading
`.done`/`.value`. V1 consumes an async-generator instance only; any other
iterable — including a plain array or a *sync* generator — is a clean rejection
(no general `Symbol.asyncIterator` protocol, which needs well-known symbols this
compiler doesn't have).

## Consequences

- `async function*` with `yield`, `await` between yields, and `for await...of`
  consumption all work — including the primary use case, paginating over `fetch`
  responses (`async function* p() { … yield await fetch(u) … }`).
- A throw in an async-generator body rejects the awaiting `.next()`, catchable at
  the consumer.
- Documented V1 divergences / scope cuts: `.next()` returns an *already-resolved*
  promise (the body runs synchronously to the next yield, driving its awaits)
  rather than a pending one — observably identical to real JS for a `for await`
  consumer, differing only if the promise is held without awaiting; and `yield*`,
  a general `Symbol.asyncIterator` iterable, `.return()`/`.throw()`, and a
  destructuring `for await` loop variable stay unsupported (Stage 4 / future).
- Async generator *methods* (`async *m()` on a class) remain deferred
  ([TDD-00085](../tdd/TDD-00085.md) Stage 4).
