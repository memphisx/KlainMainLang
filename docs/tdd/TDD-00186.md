# TDD-00186: Real async streaming I/O (pool-backed file streams, fetch body Promises)

- **Status**: Partially Implemented
- **Date**: 2026-09-08

## Context

[TDD-00185](TDD-00185.md) made the one-shot `fs.promises` ops genuinely
non-blocking on the thread pool (Stages 1-3) and flagged its Stage 4 — *real
streaming* — as a candidate for its own document. This is that document.

Two distinct gaps remain, both listed under BACKLOG §1.2:

1. **`fs.createReadStream` blocks the loop.** `emit_fs_stream.go` allocates a
   WHATWG readable, then calls `@__kml_fs_read_stream` which `fopen`s and
   `fread`s the *entire* file to EOF **inline on the loop thread**
   ([runtime_fs_stream.go](../../codegen/llvm/runtime_fs_stream.go): "eager
   read-to-EOF, no select()"), enqueuing each highWaterMark chunk, then closes.
   For a file-serving microservice this freezes the reactor for the whole read —
   the exact disqualifier TDD-00185 set out to remove, still present on the
   streaming path.

2. **`Response.text()`/`.json()`/`.arrayBuffer()` return a value, not a Promise.**
   A WHATWG divergence — the real methods return `Promise<T>`. Note this is
   **only a return-type gap, not a blocking one**: `@__kml_await_fetch` already
   *parks the fiber* (swapcontext back to the loop; [runtime_fetch.go](../../codegen/llvm/runtime_fetch.go)),
   so `await response.json()` does not freeze the loop today. Lower priority than
   item 1 for that reason.

## Design

### Part A — pool-backed `fs.createReadStream` (this stage)

Reuse TDD-00185's pool, extended with a streaming **completion kind**. The
one-shot ops post exactly one completion that *settles a Promise*; a stream job
posts *many* completions that *feed a Readable*:

- **Completion kinds** (`klainpool.c`): `SETTLE` (promise, unchanged),
  `STREAM_CHUNK` (enqueue one chunk into a readable), `STREAM_END` (close it).
  The loop-thread drain dispatches on the kind — `__kml_pool_settle` /
  `__kml_pool_stream_chunk` (→ `@__kml_rs_enqueue`) / `__kml_pool_stream_end`
  (→ `@__kml_rs_close`) — all IR helpers, so the C side stays ignorant of the
  stream/promise layout exactly as in Stage 2.
- **Synchronous open, pooled read.** `createReadStream` `fopen`s on the loop
  thread (`@__kml_fs_open_read`, throwing on a missing file — preserving the
  current synchronous throw), then submits `__kml_pool_submit_readstream(rs,
  FILE*, hwm)`. The worker loops: `fread` one `hwm` chunk, `malloc` a
  length-prefixed KML string, post a `STREAM_CHUNK`; at EOF post `STREAM_END`;
  `fclose`. The chunk buffer is built in plain C (a length-prefixed byte string
  is trivial) and the readable leaks its chunks anyway (as the eager path
  already does), so no GC allocation happens off-thread.
- **Inflight / keepalive.** Submit increments the loop's inflight once; only
  `STREAM_END` (and `SETTLE`) decrements — chunk completions don't — so the loop
  stays alive across the whole read and blocks on the wakefd between chunks.
- **Backpressure is deferred** (a documented follow-on): the worker reads ahead
  and the chunks queue in the readable, the *same* memory profile the eager path
  already had — but now non-blocking. True highWaterMark backpressure (pause the
  worker until the consumer drains) is a later stage.

### Part B — fetch body Promises (shipped, ADR-00794)

`text()`/`json()`/`arrayBuffer()` return a real `Promise<T>`: the body is
buffered synchronously (driving the parked fetch to done, as before), then boxed
in an already-settled task promise (`wrapSettledTaskPromise`), so `await
res.json()`, `res.text().then(...)`, and `Promise.all([...])` all see a genuine
thenable. Already non-blocking (the fiber parks), so this was a faithfulness/
return-type fix, not a perf one — shipped unconditionally (open question 3
resolved: no `-compat` toggle). A typed-declaration `const p: T = await
res.json()` still parses straight into `T` (the shared `JSON.parse`-style
projection), the one kept ergonomic carve-out.

The **lazy** variant — settling the body promise off the fetch reactor
completion so the download overlaps intervening work, and surfacing a JSON parse
error as a promise *rejection* — stays a documented perf/edge follow-on (the body
is buffered at the accessor call today).

## Open questions

1. **Backpressure.** When to pause the worker on a slow consumer — poll the
   readable's queue depth vs a highWaterMark, or a loop→pool credit signal.
   Deferred; the first stage reads ahead.
2. **Mid-read `fread` error** (vs the initial `fopen`, handled synchronously).
   Currently treated as EOF; Node emits an async `'error'` on the stream. A
   `STREAM_ERROR` kind that errors the readable is the faithful follow-on.
3. ~~**Part B ordering** — fold into a `-compat` toggle, or ship
   unconditionally.~~ Resolved (ADR-00794): shipped unconditionally — no toggle,
   the settled-promise wrap is a pure return-type/thenability fix with no
   behavioral downside.
