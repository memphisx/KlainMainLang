# ADR-01168: Front-end fixes found by the fs port: optional methods, overload context, alias defaults, closure narrowing

- **Relations**: `Implements [TDD-00230](../tdd/TDD-00230.md)` (P2 checker precision); `Extends [ADR-01167](ADR-01167.md)`, [ADR-01162](ADR-01162.md)
- **Date**: 2026-09-26

## Context

Porting Node's fs streams (ADR-01167) as ordinary TypeScript hit gaps a
program hits too; each is fixed where it lives.

## Investigation and decision

- **Optional class methods** (`_construct?(cb): void;`, which Node's
  Readable reads as `this._construct != null`) did not parse. The parser
  takes `name?(…)` in a class body as a bodiless method with `IsOptional`;
  the checker types the member `T | undefined` (an unguarded call is
  TS2722, as tsc reports); code generation leaves an unimplemented
  optional method's vtable slot null, answers `this.m != null`,
  `if (this.m)`, `typeof this.m` and `this.m?.(…)` from the slot, and
  compiles a call of one no class implements to Node's `TypeError`.
- **Contextual typing through overloads**: a callback argument of an
  overloaded call took its context from the overload set's own type,
  which is the first signature; any other arity got none. It now takes the
  parameter of the overload the call resolves to (`pickOverload`, factored
  out of `resolveOverload`, inferring type arguments from the other
  arguments only). A nested overloaded call in such a callback was not
  checked at all before; tsc's TS2322 there is now reported.
- **Overload signatures kept their unrenamed type names**: the resolver's
  rename pass mangled a program's top-level types (`OM` →
  `OM__kml_mod0`) but not inside `FunctionDeclaration.Overloads`, so a
  signature naming an alias typed as unanswered. The pass now rewrites
  each overload signature with the implementation.
- **A builtin module's member as a flow-node callee**: `dottedType` did not
  resolve a builtin module marker (`fs__kml_builtin`), so a statement
  `fs.writeFileSync(path, …)` made every later read of `path` unanswered
  (`unknownGuard`). It resolves the marker as `TypeOf` does.
- **Generic alias defaults**: `type A<T = X>` dropped its defaults at parse
  time, so `NodeJS.ArrayBufferView` (whose `TArrayBuffer` defaults) was
  unanswered, and with it every `writeFileSync` signature.
  `TypeAliasDeclaration` keeps its `TypeParameters` nodes and `aliasOf`
  fills omitted arguments from the defaults, as `interfaceOf` does.
- **Narrowing a property path in a closure**: `if (this.pos !== undefined)
  this.pos += n` inside an arrow (and `o.p` under a captured `o`) was
  reported possibly undefined, where tsc narrows along the closure's own
  flow from the declared type at its start. A non-local root now narrows
  so, as a captured name already did.

## Side effects discovered

- A namespace-qualified generic alias used with its defaults (`N.A` for
  `namespace N { type A<T = string> }`) is still unanswered.
- Code generation does not apply a generic alias's defaults either (`let
  a: A = ['x']` for `type A<T = string> = T[]` is a codegen rejection).

## Verification

Mac (Apple Silicon): each case run against tsc 7.0.2 and Node v24 —
optional methods (implementing, inheriting and neither), TS2722; the
nested-overload TS2322; `fs.open` callback typing after a preceding
`fs.writeFileSync`; closure narrowing both ways (tsc's TS18048 and TS2532
kept where the narrowing is outside the closure). `go test ./checker/
./binder/ ./resolver/ ./parser/ ./ast/ ./lib/` passes.
