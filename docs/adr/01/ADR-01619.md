# ADR-01619: A captured nested function's cell is made where it is bound

- **Relations**: Extends ADR-00619, TDD-00129
- **Date**: 2026-10-14

## Context

Six WPT `performance-timeline` files failed in clang with "Instruction does
not dominate all uses". Each declares a nested function (`findMatch`) that a
callback passed to `forEach` on an `any` receiver captures.

## Investigation

- `obj.forEach(cb)` on an `any` is emitted twice: once for an array receiver
  and once for anything else (`emitDynArrayMethodCall`), so the callback,
  and its environment, is emitted in both arms.
- A capturing nested function declaration was bound to a plain slot
  (`emitCapturingNestedFunc`); its first capture promoted it to a heap cell
  in place (`promoteCaptureToCell`), at the capture site — inside the array
  arm. The other arm then stored the cell register the array arm defined.
- Captured `var`/`let`/`const` bindings are boxed where they are declared
  (ADR-00619, `hoistedCaptures`), for this reason; `hoistedCaptures` already
  holds a nested function's name when a closure captures it.

## Decision

`emitCapturingNestedFunc` boxes the function in a cell where the name is
bound (`boxHoistedCapture`) when `hoistedCaptures` holds it, as the variable
paths do.

## Implementation notes

`codegen/llvm/emit_func.go`; `TestE2ECapturedNestedFunctionInBothArms`.

## Side effects discovered

The six files then ran and failed, which led to ADR-01620 to ADR-01623.

matching `Nested|Capture|Closure|Letrec`; output compared with Node 24.
