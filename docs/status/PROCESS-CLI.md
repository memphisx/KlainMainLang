# Process / CLI I/O

> Part of the [Implementation Status](README.md) index. What CLI tools and containerized services actually need day-to-day (argument parsing, stdin, environment config, exit codes). Prioritized because the long-term project direction favors CLI/microservice use cases. `console.log`/`.error` already write to stdout/stderr respectively — see [CONSOLE.md](CONSOLE.md) — the gaps below are everything *else* a CLI program needs.

**Coverage**: ~57% (13/23).

**Caveats**: `process.env` is read-only (`getenv()` only, no `setenv()`/`unsetenv()` path). `process.on(...)` now exists, but only for `'SIGINT'`/`'SIGTERM'` — `'exit'`/`'uncaughtException'`/`'unhandledRejection'` are a separate, still-untracked mechanism (no real signal involved). `child_process` coverage is one synchronous helper (`execFileSync`) only — no async spawning. Interactive `readline` (prompt-driven, not just one blocking line) isn't implemented either.

| API | Status | Notes |
|---|---|---|
| Command-line arguments (`process.argv`) | ✅ | Mirrors C's `argv` directly (`argv[0]` is the binary's own path), not Node's two-prefix convention — see [ADR-00002](../adr/ADR-00002.md) |
| Environment variables (`process.env.KEY` / `process.env["KEY"]`) | ✅ | Both dot and bracket notation; returns a possibly-null string (same convention as `.find()`), so `process.env.X ?? "default"` works |
| Exit codes (`process.exit(code)`) | ✅ | Calls C `exit()`; never returns, code after it is correctly unreachable |
| Reading stdin (sync line read) | ✅ | `process.readLineSync()` — one line via POSIX `getline()` (handles arbitrarily long lines), stripped of its trailing `\n`/`\r\n`. Returns `null` at EOF (same possibly-null convention as `process.env`). See [ADR-00024](../adr/ADR-00024.md). |
| Simple synchronous file read/write (`fs.readFileSync`/`writeFileSync`-style) | ✅ | See [FILE-SYSTEM.md](FILE-SYSTEM.md) |
| `process.execFileSync(file, args?)` | ✅ | Node's `child_process.execFileSync`, not `execSync`: `fork()`+`execvp()`s `file` directly with no shell involved, so shell metacharacters in `args` are never interpreted. Returns captured stdout as a string; throws a catchable `Error` on a non-zero exit status or a signal death. V1 scope: no options object (no `cwd`/`env`/`timeout`/`stdio` overrides yet); stderr is inherited (visible on the terminal live), not captured. See [ADR-00025](../adr/ADR-00025.md). |
| `process.cwd()` | ✅ | Current working directory, via POSIX `getcwd(NULL, 0)` (auto-sizing). See [ADR-00026](../adr/ADR-00026.md). |
| `process.chdir(path)` | ✅ | Changes the current working directory via POSIX `chdir()`. Throws a catchable `Error` (same "`<opDesc>` '`<path>`': `<strerror>`" shape `fs.*`'s failures already use) if the path doesn't exist or isn't a directory. See [ADR-00026](../adr/ADR-00026.md). |
| `process.pid` | ✅ | The current process ID, via POSIX `getpid()`. A property read, not a call, matching `process.argv`. See [ADR-00026](../adr/ADR-00026.md). |
| `process.platform` | ✅ | A pure compile-time constant (`"darwin"`/`"linux"`/`"win32"`/...) baked in from the Go compiler's own `runtime.GOOS` — no runtime code at all, since this compiler doesn't cross-compile. See [ADR-00026](../adr/ADR-00026.md). |
| `process.kill(pid, signal?)` | ✅ | Sends `signal` (defaults to `15`/`SIGTERM`, matching real Node) to `pid` via POSIX `kill()`. Throws a catchable `Error` if the target process doesn't exist or the signal can't be sent; signal `0` is the standard POSIX "does this process exist" check and never actually delivers a signal. See [ADR-00026](../adr/ADR-00026.md). |
| `process.stdout.write(s)` / `process.stderr.write(s)` (raw write, no auto-newline) | ✅ | Unlike `console.log`/`.error` (always a trailing newline), a plain write of exactly `s` with nothing appended — useful for a progress indicator or assembling one line from several pieces. `stdout` goes through buffered `printf` (matching `console.log`'s own fd=1 convention, so output ordering against `console.log` calls elsewhere in the same program stays correct); `stderr` goes through unbuffered `dprintf` (matching `console.error`'s own fd=2 convention). Text-only (byte-string, not binary-safe past an embedded null — same scope narrowing `console.log`'s own string formatting already has). |
| Writing/deleting `process.env` (`process.env.KEY = val`, `delete process.env.KEY`) | ❌ | `process.env` is read-only today (backed by `getenv()` only) — no `setenv()`/`unsetenv()` path exists |
| `process.on('SIGINT'/'SIGTERM', handler)` (signal handlers) | ✅ | Lets a running program (e.g. an `http.listen` server) intercept a signal and shut down gracefully instead of dying immediately — the handler runs from ordinary control flow at the top of the event loop's own iteration, never from real async signal context. Event name must be a compile-time string literal, exactly `'SIGINT'`/`'SIGTERM'` (dynamic event names are a clean compile error, matching `Object.hasOwn`'s dynamic-key rejection); handler must be a zero-argument `() => void` closure, same shape `setTimeout`'s own callback requires. One handler slot per signal — registering the same signal twice overwrites the previous handler. Only fires while a `http.listen`-driven or timer-driven event loop is actively iterating; a plain synchronous script with neither has no loop to check from. See [TDD-00019](../tdd/TDD-00019.md)/[ADR-00079](../adr/ADR-00079.md), [HTTP-SERVER.md](HTTP-SERVER.md). |
| `process.on('exit', ...)` / `'uncaughtException'` / `'unhandledRejection'` | ❌ | Distinct from the signal handlers above — these don't involve real POSIX signal delivery at all (process-exit hooks and exception/promise-rejection hooks respectively), a separate, still-untracked mechanism. |
| `process.hrtime()` / `process.hrtime.bigint()` | ❌ | High-resolution elapsed-time pair; `performance.now()` (see [PERFORMANCE-TIMING.md](PERFORMANCE-TIMING.md)) already covers the same monotonic-clock use case with a simpler `double`-milliseconds return, so this is low-priority duplication rather than a real gap in capability |
| `process.memoryUsage()` | ❌ | RSS/heap-size reporting — not meaningful in `manual` memory-management mode the same way it is under a real GC; more relevant once `-mm=gc` is the default (see [MEMORY-MANAGEMENT.md](MEMORY-MANAGEMENT.md)) |
| `process.nextTick(fn)` | ❌ | Same underlying gap as `queueMicrotask` (see [GLOBAL-FUNCTIONS.md](GLOBAL-FUNCTIONS.md)) — no microtask queue exists yet, only the timer queue (see [TIMERS.md](TIMERS.md)) |
| `process.version` / `process.versions` | ❌ | Reports the Node runtime's own version — not obviously meaningful for a compiled native binary with no runtime to version, but commonly probed by scripts checking compatibility |
| `process.uptime()` | ❌ | Seconds since process start |
| `process.stdin` (interactive/streamed reads, not just `readLineSync()`) | ❌ | `process.readLineSync()` (above) is one blocking line at a time; a real `process.stdin` is a readable stream (see [STREAMS.md](STREAMS.md)'s Node section — same underlying gap) |
| `readline` module (`readline.createInterface`, prompt-driven interactive input) | ❌ | Distinct from `process.readLineSync()` above — the real module supports a `prompt`, line history, and event-driven (`'line'` event) reading rather than one synchronous blocking call. Depends on `EventEmitter` (see [EVENT-EMITTER.md](EVENT-EMITTER.md)), itself untracked until now. |
| `child_process.spawn()` / `.exec()` / `.fork()` (async, event-driven) | ❌ | Only the one synchronous helper above (`execFileSync`) exists — no non-blocking process spawning, and no way to stream a child's stdout/stderr incrementally rather than waiting for it to exit and capturing everything at once |
