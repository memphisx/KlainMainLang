# TDD-00070: `let`/`const`/`var` scope semantics — hoisting, TDZ, and redeclaration early-errors

- **Status**: Implemented
- **Date**: 2026-08-18
- **Notes**: Corrects an overstated `docs/status` caveat: `const` reassignment, `let`/`const` block scoping, and top-level `let x; let x` are already rejected. Four real gaps remain, staged A/B/C. **A (bug fix):** the top-level duplicate check is kind-agnostic, so legal `var x; var x` is wrongly rejected — make it kind-aware. **B (new static pass):** a resolver-side lexical early-error walk covering block-scoped `let`/`const` redeclaration and same-block TDZ (`Cannot access 'y' before initialization`). **C (design decision):** desugar `var` to function-scoped hoisting; the one open call is the hoisted-but-unassigned type — recommended hybrid: definite-assignment error for typed `var` (TS-faithful), hoist-to-`undefined` for `any`-typed (JS-faithful)

## Context

The `docs/status` variable-declarations row has long carried the caveat *"No `let`/`const`-vs-`var` scoping distinction — no TDZ/hoisting or redeclaration checks (all three are mutable allocas)."* A direct audit (Mac/Apple Silicon, `klainmain` at [ADR-00209](../adr/ADR-00209.md)) shows that caveat now overstates the gap in some places and understates it in others. What actually holds today:

- `const` reassignment **is** rejected — `Symbol.IsConst` is set at declaration ([ADR-00209](../adr/ADR-00209.md) added the missing initializer requirement) and checked in `emit_exprs_assign.go`.
- `let`/`const` **are** effectively block-scoped: `emit_stmts.go`'s `*ast.BlockStatement` case pushes/pops a scope, so two sibling `{ let z }` blocks are independent, as they should be.
- A module-top-level duplicate — `let x; let x;` at file scope — **is** rejected, in `resolver.go`'s `mangleFileDecls` (`'x' is declared more than once`).

So three of the four things the caveat claims are missing already work. The real remaining gaps, each with a verified repro:

1. **`var x = 1; var x = 2;` at top level is wrongly rejected.** The `mangleFileDecls` duplicate check (`resolver.go:658`) is *kind-agnostic*: it treats a repeated `var` (or `function`) as a collision, but real JS permits re-declaring the same `var`/`function` name — only `let`/`const`/`class`/`enum`/`interface`/`type` collide, and mixing a lexical kind with a `var` of the same name is the actual error. This is a false-rejection correctness bug, not just a missing check.

2. **Block-scoped `let y; let y;` inside a function is not caught.** The redeclaration check exists only at module top level; inside a function or nested block, codegen's `define()` silently shadows, so a duplicate `let`/`const` in the same block compiles and runs (prints `2`) instead of raising `SyntaxError: Identifier 'y' has already been declared`.

3. **`var` is not function-scoped and does not hoist.** `{ var x = 5 } console.log(x)` fails with `undefined variable 'x'`; `console.log(z); var z = 9;` fails instead of printing `undefined`. `var` is being treated as block-scoped, identical to `let`.

4. **No true TDZ.** `console.log(y); let y = 3;` reports a generic `undefined variable 'y'` rather than `Cannot access 'y' before initialization`. Behaviorally this already rejects, so it is message quality rather than a wrong result — but it is the same missing information (a name lexically declared later in this block) that gap #2 needs, so the two are one pass.

Full A+B+C is in scope for this design: the cheap correctness wins, the lexical early-error pass, and true `var` function-scoping/hoisting.

## Design

Three stages, landable independently in order. Stage A is a contained bug fix; Stage B introduces one new static pass; Stage C carries the one genuine multi-option decision (var-hoist typing).

### Stage A — kind-aware top-level duplicate check (correctness fix)

`declRefsOf` (`resolver.go:595`) already unwraps every top-level declaration to its `declRef`s. It needs to also surface each ref's **binding kind** so `mangleFileDecls` can apply the right collision rule:

- Add a `Kind` field to `declRef` — one of `"let"`, `"const"`, `"var"`, `"function"`, `"class"`, `"enum"`, `"interface"`, `"type"`. `*ast.VarDeclaration`/`*ast.VarDeclarationList` already carry a `Kind` string (`ast/nodes.go:49`); the others map from their node type.
- In `mangleFileDecls`, replace the single `mangled[ref.Name]` presence test with kind-aware rules mirroring the spec's `GlobalDeclarationInstantiation`:
  - Two `var`s, or two `function`s, or a `var` and a `function`, of the same name → **allowed** (the second is the same binding; it re-maps to the identical mangled name rather than minting a new one, so `declRefsOf`'s `ref.Set` still runs but is idempotent).
  - Any lexical kind (`let`/`const`/`class`/`enum`/`interface`/`type`) colliding with *anything* of that name → **rejected**, keeping the existing message shape.
- The idempotent-remap detail matters: the codegen side must not `alloca` twice for the same top-level `var`. Since a repeated top-level `var` is rare and the second declaration is really an assignment, the simplest correct lowering is to let Stage C's hoisting pass (below) collapse duplicate `var` names to a single binding before codegen ever sees them — so Stage A's job is purely the *early-error* decision, and the second `var`'s storage question is deferred to and owned by Stage C. Until Stage C lands, Stage A can keep emitting the first binding and treat the second as an assignment to it (a `var x = 2` after `var x = 1` is observably just `x = 2`).

This stage alone fixes gap #1 and is a clean same-commit candidate with its own ADR if we want to ship it ahead of B/C.

### Stage B — a lexical early-error pass (redeclaration + TDZ)

Introduce one static walk, run after parse and before codegen (natural home: the resolver, alongside `mangleFileDecls`, or a new `scopecheck.go` it calls). The pass models the two binding environments the spec distinguishes:

- **Lexical environment** per block (and per function body, per `for`/`for-of`/`for-in` head, per `catch` param, per class body): the set of `let`/`const`/`class` names declared directly in it — its `LexicallyDeclaredNames`.
- **Var environment** per function (and the module/script top): the set of `var` and hoisted-`function` names — its `VarDeclaredNames`.

Early-errors the pass raises, matching the spec's static-semantics rules:

- **Duplicate lexical names in one scope** — `let y; let y;`, `let y; const y;`, `let y; class y{}`, `let y; function y(){}` in the same block → `SyntaxError: Identifier 'y' has already been declared`. Fixes gap #2.
- **`let`/`const` shadowing a `var` (or vice-versa) in the same function scope** — the lexical/var name-set intersection must be empty within a scope. Catches `var y; let y;`.
- **TDZ**: within a block, a *read* (or a non-declaring write) of a name that is `let`/`const`-declared later in the *same or an enclosing lexical scope up to its declaration point*, before that declaration executes, is `ReferenceError: Cannot access 'y' before initialization`. Fixes gap #4. Scope: statically-provable same-block use-before-declaration is the V1 target — this covers the common `console.log(y); let y = ...` case and the `typeof`-of-a-later-`let` case. Data-flow-dependent TDZ (a name read inside a conditionally-executed closure that may run before the declaration) is explicitly out of V1 scope and stays a runtime-undefined-ish rejection, same as today.

Where this pass lives relative to codegen matters for message quality: producing it as a resolver pass means the errors are `parse error`/`SyntaxError`-shaped and surface before any IR is built, which is what real JS engines do (these are *early* errors — the whole script fails to run, not the statement).

Implementation note: this pass needs a block-scope model the resolver does not have yet (today's resolver only walks top-level statements). The walk is a straightforward recursive descent over statement bodies maintaining a stack of `{lexical map, var set, isFunctionBoundary}` frames — the same shape as `emitter.go`'s `scopes []scope` stack, but built statically and kind-aware. It does not need type information, so it is cheap and self-contained.

### Stage C — `var` function-scoping and hoisting (the design decision)

Desugar `var` in the resolver, before codegen, so the emitter's existing block-scope stack keeps working unchanged for `let`/`const` and simply sees every `var` already lifted to its function's entry:

1. **Hoist**: collect every `var` name in a function body (recursively, but not crossing into nested function/arrow/method boundaries — those own their own var environment) and the module/script top. Declare each once at the top of that function's scope.
2. **Split**: rewrite each `var x = e` in place into an assignment `x = e` at its original source position (the binding itself moves to the top; the initialization stays put — this is exactly the observable hoisting semantics). A bare `var x;` becomes just the hoisted binding with no assignment.
3. **Collapse duplicates**: multiple `var x` in the same function collapse to one hoisted binding (this is also what makes Stage A's repeated-top-level-`var` case lower correctly — the second `var x = 2` is now just `x = 2`).

The one genuine open decision is **what type a hoisted-but-not-yet-assigned `var` holds before its initializer runs.** In real JS it is `undefined`; in a typed compiler that is awkward for `var z; ...; z = 9` where `z` is used as a number. Three viable options:

- **Option 1 — hoist-to-`undefined`-as-`any`.** A hoisted `var` with a use before its first assignment is typed `any`/dynamic (the existing `{tag,payload}` boxed representation, `emit_dynamic.go`), initialized to the `undefined` tag, exactly like an uninitialized `let x: any`. Matches JS semantics precisely; cost is that such a `var` loses static typing on its arithmetic (today's `any` rejects most operators — see the `emit_dynamic.go` limitations), so `console.log(z); var z = 9; console.log(z + 1)` would need `z` boxed throughout. Faithful but potentially surprising perf/behavior.
- **Option 2 — definite-assignment error (what real TS does under `--strict`).** A `var` (or `let`) read before it is definitely assigned on all paths is a compile error (`Variable 'z' is used before being assigned`), *unless* the declared/inferred type includes `undefined`. This is the strongest match to the *TypeScript* half of this compiler's dual JS/TS nature, needs no `any`-boxing, and reuses the Stage B TDZ machinery (same "declared-later / not-yet-initialized" analysis) rather than adding a runtime `undefined` slot. Downside: it rejects some technically-valid-JS programs that Option 1 would run.
- **Option 3 — keep `var` ≈ block-scoped `let`, document the divergence.** Do only Stage A+B, leave `var` non-hoisting, and state plainly in `docs/status` that `var` is treated as block-scoped (a permanent, disclosed narrowing rather than a deferred shortcut). Lowest effort, but chosen against for this TDD — full A+B+C is the agreed target.

**Recommended: Option 2 for typed `var`, with Option 1 reserved for the explicitly-`any`-typed case.** A `var z` whose inferred type is a concrete scalar and that is read before assignment is a definite-assignment error (TS-faithful, no boxing, reuses Stage B); a `var z: any` (or an unannotated `var` the inference widens to `any`) hoists to the `undefined` tag and runs (JS-faithful, since `any` already tolerates it). This splits the difference along the same typed-vs-`any` seam the rest of the compiler already uses, and avoids silently boxing ordinary numeric `var`s.

## Open questions

- **Stage C typing decision** — Option 1 vs. 2 vs. the recommended hybrid. This is the one item genuinely left for implementation to settle against real programs; the recommendation (definite-assignment error for typed `var`, hoist-to-`undefined` for `any`-typed) is a starting position, not a settled one.
- **TDZ depth in V1** — statically-provable same-block use-before-declaration is the V1 target. Whether to attempt any closure/conditional-path TDZ (a `let` captured by a closure that could run before the declaration line) or leave it as today's runtime rejection should be decided during implementation; the recommendation is to leave it, matching the "V1-scoped" pattern other features here use.
- **Does the Stage B pass belong in `resolver/` or a new `scopecheck` package?** It needs no type information and runs before codegen, so the resolver is the natural home — but it is large enough (recursive block walk + two name environments) that a dedicated file is warranted regardless of package. Confirm during implementation.
- **Repeated top-level `var` storage** — Stage A defers the second-`var`-binding storage question to Stage C's collapse step. If Stage A ships ahead of C, confirm the interim "first binding + treat second as assignment" lowering does not double-`alloca` or mis-scope the name.
