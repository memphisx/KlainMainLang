# ADR-00976: Scalar-vs-pointer ternary branches reject cleanly instead of emitting invalid IR

- **Date**: 2026-09-16

## Context

Surfaced while writing a repro during the documentation audit (ADR-00975's
sibling find). A conditional expression whose branches mix a non-pointer scalar
(`number`) with a pointer/reference type (an object) emitted invalid IR at the
clang stage instead of compiling or rejecting.

Repro (macOS arm64 / M4):

```ts
type Addr = { port: number }
function f(addr: Addr): void {
  const p = addr ? addr.port : addr   // then: number (double); else: Addr (ptr)
  console.log(p)
}
```

```
error: '%t7' defined with type 'ptr' but expected 'double'
  store double %t7, ptr %t1, align 8
```

The real-world shape was the Node idiom `const p = typeof addr === 'object' &&
addr ? addr.port : addr` on a `server.address()` result. Plain `addr.port`
(without the ternary) already compiles; only the mixed-branch ternary failed.

## Investigation

`codegen/llvm/emit_exprs_operators.go`, `emitConditional` (line 1786). The
function allocates a single result slot typed as the consequent's type (`ty`) and
coerces both branches into it (lines 1819–1844). There is a guard for mismatched
branches (line 1811), but it only checked `isStringTy(ty) != isStringTy(altTy)` —
a string-vs-non-string mismatch. A `number` (double) consequent and an `Addr`
(object, `ptr`) alternate are both non-string, so the guard passed; the alternate
was then coerced to `double` and `store double <ptr>, ptr <slot>` was emitted —
invalid IR. The guard's own comment already stated the intent to reject "a pointer
with a scalar", but the code never implemented that half.

`ternaryNullableScalarType` (the `cond ? scalar : null` case, line 1791) and the
dynamic-branch case (`emitConditionalAny`, line 1808) are handled before the
guard, so broadening it does not disturb them.

Alternative rejected: representing the result as a real `number | Addr` union
value. This typed-subset compiler's union support does not cover a mixed
scalar+object union in a single value slot, so the honest, standing-rule-aligned
outcome is a clean rejection (as the string-vs-number ternary already is), not a
new half-supported representation.

## Decision

Broaden the guard from string-specific to representation-general: reject when one
branch is pointer-like (`ptr` IR, object, array, or string) and the other is a
non-pointer scalar. The two can't share the single result slot without an invalid
store. The error names both branch types and points at the fixes (narrow first,
assign each branch separately, or convert both to one type).

## Implementation notes

- `codegen/llvm/emit_exprs_operators.go`, `emitConditional`: replaced the
  `isStringTy(ty) != isStringTy(altTy)` check with a `ptrLike(ty) !=
  ptrLike(altTy)` check (`ptrLike` = `IR=="ptr" || IsObject || IsArray ||
  isStringTy`). String is pointer-like, so the former string-vs-number rejection
  is subsumed.
- Same-representation ternaries are untouched: number/number, string/string,
  object/object (same type), object/null, numeric-width mixes, and array-element
  scalars all still compile.

## Side effects discovered

None. This is one member of the broader invalid-IR backlog; no other ternary
representation-mix was changed. The `cond ? obj1 : obj2` different-object-shape
case remains a separate (valid-IR, type-soundness) concern, not addressed here.

## Verification

- `TestE2ETernaryScalarObjectMixRejectedStrict` added (a `number` vs object
  ternary now reports "incompatible types").
- Manual battery of valid ternaries (number/number, string/string, object/object,
  object/null, int/float, array-element, string/null-nullable) all compile and run
  correctly.
- `go test ./tests -run 'Ternary|Conditional|Operator|Union|Narrow|InvalidIR'` —
  green. `make examples` — 323/323.
- Machine: macOS arm64 (M4).
