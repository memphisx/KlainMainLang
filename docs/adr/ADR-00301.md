# ADR-00301: Streaming http request bodies — `req.stream()`, headers-complete dispatch

- **Relations**: Implements [TDD-00097](../tdd/TDD-00097.md) Stage 5b; extends [ADR-00296](ADR-00296.md)–[ADR-00300](ADR-00300.md)
- **Date**: 2026-08-22

## Context

TDD-00097 Stage 5b: the last buffered direction. `req.stream()` returns a
`ReadableStream<Uint8Array>` of the request body as it arrives from the
socket; a program that uses it anywhere switches the dispatcher to
**headers-complete dispatch** (the handler runs as soon as the headers are
parsed), and the 10 MiB request cap no longer applies to bodies — only to
the header block.

## Investigation / Decision

- **Whole-program mode, transparent accessors.** Detecting per-request
  whether a handler will stream is impossible at compile time, so
  `req.stream()` anywhere flips the whole program; `req.body` /
  `req.bodyBytes()` stay correct through a **drain**: the body buffer is
  pre-allocated at full Content-Length at dispatch, and the accessors
  complete it in place (fiber-yielding on EAGAIN) before reading. A
  buffered-only program is byte-for-byte unchanged (the drain call resolves
  to a no-op stub).
- **One body context, three feeders** (`runtime_http_reqbody.go`, 48-byte
  `{fd, remaining, bodyBuf, filled, stream, active}` in a hidden
  `__kml_bodyctx` request field): the stream's pull hook (reads with
  fiber-yield on EAGAIN — the event loop's readable-scan resumes the
  connection exactly like the request-read phase); an event-loop/scheduler
  **pump** for consumers outside the fiber (`body: req.stream()` echoed into
  a Stage 5 chunked response — the full duplex echo of a 12 MiB body works
  without ever buffering it); and the accessors' drain.

Four deep bugs found and fixed at the root while wiring this:

1. **`__kml_task_resume` and `__kml_spawn_task` saved the resumer context
   into `@__kml_main_ctx`** (resume) or the parent task's ctx slot (spawn)
   — correct only when invoked from the loop's main context. From a
   connection fiber (an http handler awaiting a task), this left the
   fiber's `uc_link` pointing into a dead frame: a wild-jump crash when the
   fiber ended. Both now save into a per-call stack slot. This was a
   latent pre-existing landmine for any handler-awaits-task shape.
2. **Fiber-yield from a task stack**: the pull/drain yield checked only
   `@__kml_current_conn_idx`, but a task spawned from a handler still sees
   the connection's index — yielding through the conn slot from the task's
   stack clobbered the fiber's saved context. Yield now requires
   `@__kml_current_task == null`; on a task the read returns EAGAIN and
   the pump feeds the parked read.
3. **Re-entrant `read_step` clobbered `remaining`**: enqueue re-enters the
   read path through the stream's pull hook, and the outer frame's stale
   post-enqueue store erased every nested decrement (~450 KB of a 12 MiB
   upload silently unaccounted → the stream never closed). The decrement
   now happens before the enqueue, and the completion check reloads.
4. **The top-level await drive busy-spun at 99 % CPU**, starving the
   uploading peer process for the whole transfer. It now `usleep(200)`s
   per idle drive cycle (also folded `__kml_reqbody_pump` into
   `__kml_task_sched_step`, and streaming-body readiness into the event
   loop's select() timeout alongside ADR-00300's microtask check).

Also fixed: the Stage 5 chunked writer's socket writes silently dropped on
EAGAIN once the client's receive path backed up (a client that uploads
before reading its response) — the writer's fd is now switched to blocking
for its lifetime, matching the buffered response path's write semantics.

## Implementation notes

Dispatcher (`emit_http.go`): under streaming mode `checkBodyCompleteL`
branches to parse at headers-parsed; the body copy is clamped to what
actually arrived; the context is built and stored. `RequestType` gains the
hidden `__kml_bodyctx` field (visible to `Object.keys` — same Stage 4
caveat shape). `req.stream()` dispatch + inference; `req.body` member reads
intercepted for the drain.

## Side effects discovered

- `req.body` after consuming `req.stream()` returns only the pre-stream
  prefix (spec would throw already-disturbed) — caveat.
- A handler must use one body shape per program path — mixing
  `body: string` and `body: req.stream()` returns across branches trips
  return-type inference (first-return-wins), not a streaming bug per se.
- The mode flag depends on `req.stream()` being *emitted* before the
  dispatcher is built — true for handlers and anything they reference; a
  pathological textual order could miss it (not observed; noted).

## Verification

  cap) counted chunk-at-a-time by a task consumer; a 4 MiB
  `req.stream()` → chunked-response echo compared byte-exact by a Go
  client; buffered accessors verified in a streaming-mode program.
- `examples/streams/http_upload.ts`: an in-process 8 MiB fetch upload
  counted via `req.stream()`.
- Full `go test ./...` green (the fiber/task context fixes ran against the
  entire async/generator/http/fetch suite), all 153 examples pass,
