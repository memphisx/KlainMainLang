# TDD-00238: The builtin library compiled once and linked

- **Status**: Implemented
- **Date**: 2026-10-01
- **Notes**: Stages 0–2 [ADR-01323](../adr/ADR-01323.md), Stage 3 [ADR-01325](../adr/ADR-01325.md), Stage 4 [ADR-01326](../adr/ADR-01326.md)/[ADR-01329](../adr/ADR-01329.md), Stage 5 [ADR-01330](../adr/ADR-01330.md): `import()` targets share the program's modules (bundled and lazy backends); the separately compiled islands remain as the opt-in `-dynamic-import=isolated`.

## Context

[ADR-00022](../adr/ADR-00022.md) chose whole-program compilation: every
file a program reaches is merged into one `*ast.Program`, emitted as one
`.ll` and compiled by one `clang -O2`. It rejected separately compiled
units because nothing needed them; there was no incremental-build story
to lose.

Since [TDD-00231](TDD-00231.md) and [TDD-00230](TDD-00230.md) P3, the
builtin library is TypeScript (`lib/node`: 77 files, 38,692 lines) merged
into every program that names it, and that cost is paid on every build:

- A program using `net` or `stream` compiled in about 5 s, 0.3 s of it the
  front end: clang `-O2` compiles every library function, used or not
  (14 MB of IR, [ADR-01239](../adr/ADR-01239.md)). Each P3 port adds to it: since `URL` and
  `Headers` became TypeScript (TDD-00237), a program naming `fetch` or
  `fs` compiles both.
- The `tests/` suite compiles thousands of programs. It ran in about
  20 min a shard on the M4 before the ports, and now takes over 40 min on
  the Linux test box.
- The C runtime files are compiled per program as well. The tests and
  conformance runners cache their objects (`CSource.CachedObject`,
  `cobj_cache.go:38`), but the CLI does not: `main.go:334-355` hands each
  sidecar's source to clang with the `.ll`.

TDD-00231 anticipated this: "If it matters, a precompiled object is an
option, since nothing in the module depends on the program." That is true
of its source, but not of the code emitted from it. Node does the same
work once: its JavaScript builtins are compiled into the `node` binary at
build time (V8's code cache and startup snapshot), and a script never
pays for compiling `fs`.

[TDD-00056](TDD-00056.md)'s islands are this compiler's one separately
compiled unit. They do not solve this, and they show a second problem:
an island is an independent whole-program compile (`main.go:437-499`), with
its own copy of the library, its own `__kml_modN` numbering and its own
class ids. A builtin module imported by both the program and an island
exists twice, with two copies of its state, where JavaScript has one
instance of a module per realm.

## What ties the library's code to one program

Each of these makes the IR emitted for a library file differ from program
to program.

1. **Mangled names.** Every top-level name becomes
   `name__kml_modN` (`resolver.go:1384`), with N the file's first-visit
   index in this program's import walk (`resolver.go:203`). The same file
   is `mod3` in one program and `mod11` in another. Codegen never
   hardcodes a library symbol; it looks names up through `LibExports`
   (`resolver.go:988`), so the scheme can change in one place.
2. **Type ids.** The object header's low 32 bits are a type id
   (`objheader.go:4-19`), allocated from one per-program counter
   (`allocTypeID`, `objheader.go:30`) in emission order: classes in
   topological program order (`emit_classes.go:1008`), generic
   instantiations as call sites reach them (`emit_generics.go:603`),
   object layouts on first use (`objheader.go:88`), host boxes
   (`emit_hostbox.go:134`). Ids are immediates in the IR (`icmp eq i64`).
   Error subclasses start at `errorSubclassTagBase` (1000).
3. **Program-wide dispatchers.** Emitted at finalize (`emitter.go:3206`),
   each switching over every class or layout of the program:
   - the class-reference table and its dispatch
     (`emit_classref.go:114-908`: `__kml_dyn_instanceof`,
     `__kml_dyn_construct`, the static get/set);
   - the shape table behind `__kml_shape_get` and `__kml_obj_*`
     (`emit_shape.go:80`, `emit_record_view.go:302`);
   - `__kml_obj_inspect_custom` and `__kml_obj_tostring_tag`
     (`emit_inspect.go:892-931`);
   - the host-box hooks (`emit_hostbox.go:313`);
   - the function-metadata table `@__kml_fnmeta_tab` (`fnmeta.go:185`).
4. **Per-program emission choices.** About 310 `used*` flags and 363
   `ensure*` declarations decide what runtime exists, and finalize swaps
   in stubs for what is unused (`emitter.go:3050-3160`). The interned
   string pool is numbered program-wide (`@.s%d`, `emitter.go:1610`).
5. **Monomorphization.** A generic function or class is emitted once per
   type-argument list a call site uses (`emit_generics.go`). A library
   generic instantiated with a user type cannot be compiled before the
   user type exists.
6. **One `main`.** A module's top-level statements are not a function:
   they are emitted inline into `@main` in dependency order
   (`emitter.go:2890-3010`). Run-once holds because each file is merged
   once ([TDD-00052](TDD-00052.md)).

Unannotated parameters are not inferred from callers (they default to
`number`, ADR-00042), so a non-generic library function's code does not
depend on its call sites.

## Design

A builtin library module is compiled to an object once per compiler
version, target and option set, cached, and linked. User code stays
whole-program. The library's semantics are unchanged: a module is
evaluated once, in dependency order, and has one instance per process.

### Stage 0: the CLI uses the C object cache

`main.go` compiles each sidecar through `CachedObject`, as the tests do,
into a per-user cache directory (`os.UserCacheDir()/klainmain/cobj`,
`-cache-dir` to move it, `-no-cache` to bypass it). Independent of
everything below, and the cheapest win for the CLI.

### Stage 1: stable names for library symbols

A library file's mangled names derive from its path under `lib/`, not
its visit index: `name__kml_lib_<module>` (`stream`, `internal_http`).
User files keep `__kml_modN`. `LibExports` already funnels every codegen
lookup through one map, so this is a resolver change.

### Stage 2: stable type ids for library classes and layouts

The id space is split. Ids below `kmlUserTypeIDBase` belong to the
library and are assigned when the compiler is built: a generated table
(Go, from walking `lib/` in a fixed order) gives each library class and
each library-owned object layout its id. User classes, user layouts and
every generic instantiation are numbered from `kmlUserTypeIDBase` per
program, as today. This is [TDD-00230](TDD-00230.md)'s requirement that
type ids "stay stable across separately compiled units"; the layout table
it describes is where the library's rows live.

A library generic instantiated only with library types (a
`Map<string, Socket>` inside `net`) is instantiated in the library's
object with a library id. An instantiation that names a user type is
emitted in the program, with a user id, as today.

### Stage 3: dispatch by registration

Each dispatcher in "What ties" item 3 becomes a table that units add to,
instead of a function generated over the whole program:

- The library object carries its rows (class refs, shapes, inspect and
  toStringTag hooks, host-box hooks, function metadata) as constant
  arrays in a named section, or as an array its init function hands to
  `__kml_register_unit`.
- The program's object does the same for its own rows.
- The runtime's dispatchers look a type id up in the merged table: a
  sorted array, or a direct index for the library's dense id range.

Registration happens before any module's code runs. The IR dispatchers
that `switch` over ids today become C or IR functions over the table,
emitted once into the runtime.

### Stage 4: the library as objects

- **What goes into a library object.** Every non-generic function, class
  and constant of one `lib/` module, its library-only generic
  instantiations, its string pool (`@.s_<module>_N`), and its init
  function `__kml_lib_<module>_init`. The init holds the module's
  top-level statements, guarded to run once, and calls the inits of the
  library modules it imports first.
- **The program.** Emitted as today, minus the library's bodies: library
  symbols are `declare`d, with their types from the resolver. `@main`
  calls the init of each library module the program imports before its
  own first statement, in the order the merge would have run them.
- **Runtime choices.** A library module compiles against the runtime
  pieces it uses (its own `ensure*` set). Those are linked as one runtime
  object per option set rather than chosen per program. A `used*` flag
  that changes code inside a library function is a parameter of its
  cache key, and there should be few.
- **The cache.** Keyed by the module's source and its dependencies'
  hashes, the compiler version, the target triple and every option that
  changes emission (`-mm`, `-compat`, `-O`, sanitizers). Built on first
  use into the user cache directory, like Stage 0. A release can ship
  prebuilt objects for its platforms; the cache only needs to be
  correct, not warm.
- **Linking.** The program's object, the library objects it imports
  (transitively), the runtime object and the sidecars. Unused functions
  are dropped by the linker (`-ffunction-sections` with `--gc-sections`,
  or `-dead_strip` on macOS), not by recompiling.
- **`--static`** links the same objects; nothing here needs `dlopen`.

### Stage 5: islands share the library

An island ([TDD-00056](TDD-00056.md)) links against the main binary's
library instead of carrying its own copy: the library objects go into the
main executable and are exported to islands, so a module imported by both
is one instance, with one state. With Stages 1 and 2, an island's
references to library symbols and library type ids resolve against the
main binary. `import('node:url')` loads nothing new.

### Considered: whole-program with per-function caching

Keep one `.ll`, but cache clang's output per function, keyed by its IR.
It runs into the same per-program ids, names and string numbering
(Stages 1 and 2 are needed anyway), and still makes clang see the whole
program's IR. Rejected in favour of objects per module.

### Considered: internal linkage and global DCE only

Emit library functions `internal` and let LLVM's global DCE drop the
unused ones before optimizing. It shrinks
every program's compile but still compiles what is used, every time, and
the program-wide dispatchers keep most of the library reachable: a class
in the class-reference or inspect table is never dead. Worth doing for
user code; not the answer for the library.

## Open questions

- **Granularity.** One object per `lib/` module, or one archive for the
  whole library with an object per module inside it? An archive keeps
  the link line short; per-module objects rebuild less when one module
  changes.
- **Workers.** A worker re-evaluates the builtin modules it uses
  (`resolver.go:1110`, a worker is an isolate). With module inits as
  functions, it calls them again in its own thread with its own module
  state, which needs that state to be per-thread (thread-local, or a
  state block per isolate).
- **How many `used*` choices leak into library code.** Measured in
  Stage 4: each one is a cache-key dimension or a runtime check.
