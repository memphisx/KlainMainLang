# ADR-01089: The no-loop `http` client waits on curl instead of spinning

- **Relations**: `Extends ADR-00404, TDD-00138`
- **Date**: 2026-09-23

## Context

On Windows, `http.get("http://127.0.0.1:1/", …)` (a refused port, no `'error'` listener) died with a stack overflow, `0xC00000FD`. Linux exits 1 through the uncaught-error path.

The same crash failed `examples/http/https_client.ts` in one Windows examples run, when the real HTTPS request hit a transient network error. Directly it passes.

## Investigation

- The backtrace was shallow: `main → __kml_httpc_drive → libcurl → select`. That is a stack exhausted by a loop, not by deep recursion.
- `__kml_httpc_drive` (`codegen/llvm/emit_http_client.go`) is the fallback that services an `http.get` when no event loop runs. It pumped `curl_multi_perform` in a tight loop with `%rp = alloca i32` in the loop body. A non-entry alloca is released only when the function returns, so every pass grew the stack.
- The loop also never waited.
  - On Linux a refused connect fails immediately, so it made a few passes.
  - On Windows the connect retries for about 2 s, so it made millions of passes, pinning a core until the stack ran out.
- `__kml_httpc_flush` (the post-loop flush) had the same in-loop alloca.

## Decision

- Both functions allocate their out-parameter slot once, in the entry block.
- Between pumps, the drive loop checks whether its request is done and otherwise waits on curl's own sockets with `curl_multi_wait(…, 100 ms)`.
- The flush does the same while transfers are running.

## Implementation notes

`codegen/llvm/emit_http_client.go`: the two IR functions, plus a `curl_multi_wait` declaration in `ensureHTTPClientReactions`.

## Side effects discovered

- `req.on('error', …)` is still never fired: transport failures throw instead. This is an existing caveat on the `http` client status row.
- The runtime's `Uncaught: …` line goes to stdout, where Node writes to stderr. Both are unchanged here.

## Verification

- Windows x64:
  - the refused-port program exits 1 after about 2 s. It overflowed the stack before this change, run with the previous binary.
  - `https.get("https://example.com/")` still prints `status: 200`.
- `tests/http_test.go` `TestE2EHTTPClientRefusedConnectExitsCleanly` passes on Windows and on Linux x86-64 (Docker), and the Linux `http` client tests pass.
- The Windows network test batch and both platforms' examples were re-run.
