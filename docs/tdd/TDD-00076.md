# TDD-00076: Real `any` semantics as a `-compat` axis inhabitant (implicit-`any` + operator dispatch)

- **Status**: Not Started
- **Date**: 2026-08-18

## Context

[TDD-00005](TDD-00005.md) (2026-07-13) found that an unannotated parameter defaulted to `i64` with no check, silently corrupting data. Its option 1 (clean rejection at call sites) shipped as [ADR-00042](../adr/ADR-00042.md) and closed the *correctness* hole. Its options 2 (call-site inference) and 3 ("real `any` semantics — match TS's implicit-`any`") were deferred, with the resolution framed as "an opt-in flag, shape undecided."

That flag now exists. [TDD-00075](TDD-00075.md)'s `-compat=strict|js` axis is exactly the "stricter-than-JS by default, JS-faithful on opt-in" split TDD-00005 was reaching for without the vocabulary. TDD-00005 even named the tension explicitly — real TS's implicit `any` is permissive-by-default; this compiler is deliberately stricter — which *is* the `-compat` axis.

Meanwhile, every time `any` reached a new context since ADR-00008 gave it a boxed `{ i8, i64 }` runtime tag, the project made a **local** call rather than a **policy** one: reject arithmetic ([emit_exprs_operators.go](../../codegen/llvm/emit_exprs_operators.go) `IsDynamic` gate), reject nested `any[]`/`{ x: any }` ([ADR-00176](../adr/ADR-00176.md)/[TDD-00062](TDD-00062.md)), box arrays by reference with an `[object Array]` residual ([ADR-00177](../adr/ADR-00177.md)), reuse the box for unions ([ADR-00136](../adr/ADR-00136.md)), map erased generics onto it ([ADR-00121](../adr/ADR-00121.md)). Each was reasonable in isolation; together they're the whack-a-mole symptom of one unmade decision. `docs/status/README.md`'s own backlog makes the connection: a naive "default everything unannotated to `any`" can't work today because boxed `any` rejects arithmetic, so `function add(a, b) { return a + b }` wouldn't compile either.

This TDD settles that one decision. It does **not** implement anything — it scopes the design so implementation can start directly, and (per the standing rule) design work of this size gets a TDD before code.

## Design

### The core move: separate two things wearing one `any` label

The accreted `any` work is really **two independent questions**, and conflating them is why it never resolved:

- **Bucket A — genuinely the `-compat` axis.** "How much of JS's permissive `any` do we admit, and behind which mode?" This is a *policy* decision with a real strict-vs-JS tradeoff. It belongs under `-compat`.
- **Bucket B — representation completeness, orthogonal to `-compat`.** Holes in the boxed-`any` implementation you'd want filled under *either* mode (nested `any[]`/`{ x: any }`, a boxed array's length/element recovery, content-accurate array printing). These are blocked by the `{ i8, i64 }` payload being too narrow to hold a `{ ptr, len }` array, not by any strict-vs-JS choice. They stay [TDD-00062](TDD-00062.md)'s already-scoped deferred set and are explicitly **out of this TDD** — naming them here only so they stop being mistaken for compat divergences.

Everything below is Bucket A.

### Bucket A has two coupled sub-decisions

**A1 — implicit-`any` on unannotated parameters/returns** (TDD-00005 option 3):

- `-compat=strict` (default): an unannotated parameter is a **compile error** — the `noImplicitAny` end of the spectrum, which is where TDD-00005 already said the default should eventually land. This is stricter than today's silent `number`-default (which is neither strict-correct nor JS-faithful — it silently picks a type).
- `-compat=js`: an unannotated parameter defaults to boxed `any`, dispatched at runtime — exactly real TS's implicit `any`.

**A2 — operators on a boxed `any`** (the `IsDynamic` gate at [emit_exprs_operators.go](../../codegen/llvm/emit_exprs_operators.go)):

- `-compat=strict` (default): arithmetic/most operators on `any` are a **clean compile error** — this is already the shipped behavior. This sub-decision is a naming exercise on the strict side: what ships today *is* strict mode.
- `-compat=js`: operators runtime-dispatch on the tag pair, coerce, compute, re-box.

**The coupling, stated plainly:** A1's `js` side is inert without A2. Defaulting `a` and `b` to `any` in `function add(a, b) { return a + b }` only helps if `a + b` on two boxed values actually computes at runtime. So the `-compat=js` implementation order is **A2 first, then A1** — build runtime operator dispatch, *then* let implicit-`any` feed it. The strict side of both is already the status quo; the work is entirely on the `js` side.

### A2 `js`-side: runtime operator dispatch on the box

The box is `{ i8 tag, i64 payload }` with tags `kmlTagInt/Float/Boolean/String/Null/Undefined/Object/Array` ([emit_dynamic.go](../../codegen/llvm/emit_dynamic.go)). `emitAnyEquals` already does exactly this shape for `===`/`==` — a tag-pair switch. Two ways to extend it to arithmetic/relational operators:

- **Option 1 — inline LLVM tag-switch in codegen** (an `emitAnyBinary` mirroring `emitAnyEquals`). For each operator, branch on the tag pair, unbox to the concrete type, call the *existing* per-type operator codegen, re-box the result. **Pro:** no new C runtime, no new ABI, reuses every concrete operator already emitted, and is consistent with the equality path already in the tree. **Con:** code bloat at each `any`-operator site (mitigated — the arms are small and `-O2` folds unreachable tag combos when a static type is known on one side).
- **Option 2 — a C runtime helper** (`__kml_any_binop(op, a, b)` over the box). **Pro:** compact call sites. **Con:** re-implements the coercion ladder and every per-type operation in C, and exposes the box ABI across the language/runtime boundary — a second source of truth for semantics the codegen already owns.

**Recommended: Option 1.** It's the same decision ADR-00008-era equality already made, keeps one source of truth for operator semantics, and needs zero new ABI.

**Coercion scope for V1** — this is where "JS is JS," and the full abstract-operations ladder (`ToPrimitive`/`ToNumber`/`ToString`, `valueOf`/`Symbol.toPrimitive`) is a large surface. Stage it:

- **V1 covers the tag combinations with unambiguous, already-implemented coercions:** `number⊕number` (all arithmetic/relational), `string+string` and `string+any`/`any+string` → string concatenation (JS's `+` overload), `boolean`→number in arithmetic. These map directly onto existing per-type codegen.
- **V1 cleanly rejects (or, under `js`, deopts to a documented best-effort) the exotic combinations** — `object + number` (needs `ToPrimitive`), `array + x`, `null`/`undefined` arithmetic quirks (`null + 1 === 1`, `undefined + 1 === NaN`). Implementing the real ladder is a deliberate later stage, not a V1 gate. The point is that `-compat=js` doesn't have to be *bug-for-bug* complete to be useful — it has to make ordinary loosely-typed code compile and run, which the V1 set does.

### What this retires

- TDD-00005's standing "Partially Implemented / options 2 & 3 not started" becomes a *decided* axis: option 3 is `-compat=js`; the `noImplicitAny` default is `-compat=strict`; the number-default stopgap is superseded (see Open questions on migration). Option 2 (call-site inference) is judged **not worth building** — it has ADR-00041's forward-reference caveats and, with `-compat=js` boxing available as the honest permissive answer, first-call-site guessing is strictly worse than either end of the axis.
- A cluster of scattered `any` caveats in `docs/status` collapse into "strict rejects it / `js` dispatches it" against one axis, instead of N independent limitations.

### Interaction with existing inference

Unannotated-*return* inference ([TDD-00058](TDD-00058.md)) runs first and is unaffected: it still infers a concrete return type when it can. A1 only governs what happens when inference *can't* resolve a type — strict errors, `js` falls to boxed `any`. Precedence is: concrete annotation → inferred concrete type → (`strict`: error | `js`: `any`). This must be spelled out at implementation time so the two mechanisms don't fight.

## Open questions

- **Does `-compat=strict` drop the `number`-default outright (a breaking change for code relying on it) or keep it as a third legacy behavior?** Recommended: drop it once both axis ends exist — it's neither strict-correct nor JS-faithful — but that breaks programs that lean on today's silent `number`. Likely staged: keep the `number`-default as the interim strict behavior until A2's `js` side lands, then flip strict to the `noImplicitAny` error in the same release that makes `js` a real escape hatch. Exact migration window undecided.
- **V1 coercion tag-combination set** — the precise list of combinations `-compat=js` computes vs. rejects/deopts, and whether the rejected ones hard-error or emit a documented best-effort (e.g. `NaN`/string-tag fallback). Leaning: reject with a clear message in V1, revisit once the abstract-operations ladder is scoped.
- **Does `-compat=js` implicit-`any` reach object/array *fields* and array *elements*, or stay parameter/return-scalar only in V1?** The field/element case overlaps Bucket B's payload-width blocker, so V1 likely stays scalar-position only and defers the rest with Bucket B.
- **Relational/equality already partly handled** — `emitAnyEquals` covers `===`/`==`; confirm whether `<`/`>`/`<=`/`>=` on mixed tags follow JS's `ToPrimitive`-then-compare or are restricted to the same V1 unambiguous set as arithmetic.
