# ADR-00676: Generator array element types

- **Relations**: Extends ADR-00172, TDD-00061 (generators), TDD-00085 (async
  generators), TDD-00086 (`yield*`/`.throw`/`.return`), TDD-00094 (nested
  generators), TDD-00096 (element-type inference); builds on TDD-00029
  (nested-array boxing) and TDD-00127 (object-reference array model)
- **Date**: 2026-09-03

## Context

A generator whose declared element type was an array (`function* rows():
number[]`) was rejected at `buildGeneratorSig` with "an array element type is
not yet supported on a generator function" — the same for an array-typed
parameter. Array element types are common in real sources (`yield`-ing rows,
batches, tuples-as-arrays), and the rejection compile-failed whole files.

## Investigation

An array has two live shapes in this codegen: an aggregate `{ptr, i64}`
Value.Ref (register), and a boxed `{data, len}` header pointer (a named
variable's slot, TDD-00127). Crucially the array *type*'s `.IR` is `"ptr"`,
while `StructFieldIR(arrayTy)`/`StructFieldSize` reserve the inline
`{ptr, i64}` 16-byte aggregate for an array-typed struct field
(`types.go:2035`).

The generator machinery is riddled with scalar assumptions that read the field
type's `.IR`: `storeGeneratorField`/`loadGeneratorField` (the `__yielded`/
`__sent` slots), `buildGenNextResult`/`settleAsyncGenResult` (the
`{value, done}` result object's `value` field), the `.next()` merge phi, every
`for-of`/`for-await` loop-variable bind, the `yield*` delegation value loads,
and the async request-queue sent-value slot. Each used `elemTy.IR` (`"ptr"`)
for a store/load/alloca/GEP against a slot the struct layout had reserved as
16-byte `{ptr, i64}` — so the layout and the access disagreed by 8 bytes, and
`emitScalarZero(arrayTy)` produced a bare null pointer where the aggregate was
expected. A prior attempt to convert each site individually (box on store,
unbox on load) did not converge: the two shapes leaked across ~13 value sites
and the two async paths, and it broke scalar generators.

## Decision

Normalize to **one representation throughout**: an array element lives as the
inline `{ptr, i64}` aggregate everywhere the generator machinery already
reserves it — the `__yielded`/`__sent` slots, the `{value, done}` result
object, the merge phi, the async request-queue slot. This matches
`StructFieldIR`/`StructFieldSize`, so no struct layout changes; only the
scalar-assuming *access* sites are corrected to consult `StructFieldIR(elemTy)`
instead of `elemTy.IR`. The array's two shapes are reconciled at exactly one
boundary — the loop variable — where the object-reference model requires a
`{data, len}` header: the aggregate is boxed into a fresh header per iteration.

Concretely:

- `storeGeneratorField`/`loadGeneratorField` override the store/load IR to
  `StructFieldIR(fieldTy)` for an array field (the passed `ir` string, the
  array *type*'s `"ptr"`, is the mismatch); every non-array field is unchanged
  since `StructFieldIR == Type.IR` there.
- New `genZeroElem(t)`: an array's zero is the empty `{ptr null, i64 0}`
  aggregate; every other type defers to `emitScalarZero`. All element-typed
  zero sites (bare `yield`, `return`-with-no-arg, next-after-done, error
  paths, sent-value defaults) route through it.
- New `genDefineLoopVar`/`genStoreLoopVar`: a `for-of`/`for-await` loop
  variable of array type binds a stable `alloca ptr` header slot that each
  iteration re-points by boxing the yielded aggregate into a fresh header
  (a per-iteration reassignment under the object-reference model); every other
  type keeps its plain alloca + direct store.
- `buildGenNextResult`, `settleAsyncGenResult`, the `.next()` phi, the `yield*`
  `loadResultField` closure, and the async request-queue store/load all use
  `StructFieldIR(elemTy)` for the value word.
- `buildGeneratorSig` drops the array-element rejection. An array-typed
  *parameter* stays rejected (a separate slot-population path, out of scope).

## Implementation notes

All changes are in `codegen/llvm/emit_generators.go`. The pivot is that the
array Value convention (`Ref` = `{ptr, i64}` aggregate register) already lines
up with `StructFieldIR`/`StructFieldSize`'s 16-byte reservation, so switching
the access sites from `.IR` to `StructFieldIR` made both agree without any
layout change or per-site box/unbox — the boxing is confined to the single
loop-variable boundary where TDD-00127 genuinely needs a header. Element-type
*compatibility* checks in `yield*` (`innerElem.IR != gctx.elemTy.IR`) remain
`.IR`-based; both arrays compare as `"ptr"`, so a mismatched array element type
is not caught there — no worse than before, and unrelated to correctness of a
well-typed program.

## Side effects discovered

None. Async generators of arrays (`async function* … : number[]` +
`for await`) fell out for free once the shared slots were consistent, and are
covered by a test. The pre-existing invalid-IR backlog (unrelated coercion
paths) is untouched.

## Verification

Mac. New E2E tests in `tests/generators_test.go`: array `yield` + `for-of`
(incl. empty array), manual `.next()` with `.value.join()`, `string[]`
`yield*` delegation, and an async generator of arrays over `for await` — all
pass. The full existing generator/`yield`/`for-of`/`for-await` regression set
passes unchanged (`go test -run` over the generator suites, 39s). Example
`examples/generator_array_yield.ts`. `go build`/`go vet` clean.
