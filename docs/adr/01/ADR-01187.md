# ADR-01187: A `function`'s own `this` is its caller's receiver in untyped JavaScript; TS2683 in the strict lane

- **Relations**: `Extends ADR-01181`, `Implements TDD-00230` (P2.7 diagnostics, phase 5)
- **Date**: 2026-09-28

## Context

Under `-compat=js`, `this` inside a plain `function` was a compile error
("'this' is only valid inside a method or constructor body"), unless the
function was a recognised prototype constructor. Node's own tests read
`this` in callbacks everywhere — `server.listen(0, function () {
this.address() })`, a listener's `this` as its emitter — and that was the
largest bucket of the Node suite's js lane (BACKLOG 75). In the strict lane
the same program is tsc's TS2683 ("'this' implicitly has type 'any'"), which
code generation reported as its own error. A listener declared with an
explicit `this: T` parameter received its arguments shifted by one (the
adapter that boxes a closure ignored the receiver).

## Investigation

- A dynamic function (TDD-00155 Stage 4) already takes the receiver in the
  dynamic ABI (`i64 fn(ptr env, i64 this, i64 argc, ptr argv)`), and an
  emitter's `emit` already calls each listener with the emitter as `this`.
- The receiver was lost on the way: a function passed to a typed callback
  parameter (`listen(port, cb: () => void)`) became a closure thunk, and
  boxing that closure again (to store it as a listener) wrapped the thunk
  in a new adapter that has no `this` to forward.
- `fn.call`/`apply`/`bind` on a function value evaluated and dropped
  `thisArg`.
- tsc's rule (checkThisExpression, getContextualThisParameterType): TS2683
  for a `this` whose container, skipping arrows, is a function declaration
  outside a class or a function expression without a `this:` parameter
  that is not an object literal's member, not the right side of
  `obj.p = …`, and has no contextual signature with a `this` type.

## Decision

- Under `-compat=js`, a `function` expression that reads its own `this`
  compiles as a dynamic function (converted to the closure type code
  generation infers for it); a function declaration that does and is not a
  prototype constructor becomes `const f = function f(…) {…}` — a top-level
  one at the top of the program, where a declaration is initialized.
- A dynamic function's closure thunk carries `{ @__kml_d2s_env, box }` as
  its env; boxing such a closure returns the original function, so its
  receiver and its identity (`removeListener`) survive the round trip.
- `fn.call`/`fn.apply` under `-compat=js` box the function and call it
  through the dynamic ABI with `thisArg`; `fn.bind` builds a dynamic bound
  function (`@__kml_dyn_bound`: `bound <name>`, length less the bound
  count).
- The closure adapter passes the receiver to a `this: T` parameter.
- The checker reports TS2683 by tsc's rule (the strict lane only; tsdiag
  passes `noImplicitThis: false` through `Checker.ImplicitThis`).
- Function metadata looks through a thunk's box and a dynamic bound
  function (`fnFlagThroughBox`, `fnFlagBoundBox`).

## Side effects discovered

- Sloppy-mode `this` in a plain call is `undefined`, not `globalThis`: the
  global object is not a value yet (BACKLOG).

## Verification

Mac (Apple Silicon), against Node v24.19: `tests/js_this_test.go` (function
expressions and declarations as callbacks, `removeListener` after the round
trip, nested declarations, `call`/`apply`/`bind`); a strict-lane
`function (this: EventEmitter, v)` listener; TS2683 on the four shapes tsc
reports it for and none of the shapes it accepts, compared with tsc 7.0.2;
tsdiag: 3,263 diagnostics, 0 false positives over 6,024 cases.
