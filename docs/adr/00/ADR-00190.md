# ADR-00190: Unannotated `let b = true` / `let n = !cond` / `let z = -3.5` infer their real type

- **Relations**: Follows [ADR-00183](ADR-00183.md) (fixes the storage side of boolean printing)
- **Date**: 2026-08-13

## Context

`emitVarDecl`'s type-inference switch (for an unannotated `let`/`const`/`var`) has a blind `TypeI64` default, so every non-i64 initializer shape needs an explicit case. Three shapes were missing, each silently falling through to i64:

- **A bare boolean literal** — `let b = true` stored the boolean as i64, so `console.log(b)` printed `1`/`0` instead of `true`/`false`. (An *annotated* `const b: boolean = true`, and a comparison-valued `let b = x > y`, were already correct — only the bare literal was missed.)
- **A `!`-valued initializer** — `let n = !cond` fell through the same way (`inferExprType`'s `UnaryExpression` case only handled `typeof`), printing `0`/`1`.
- **A negated numeric literal** — `let z = -3.5` is a `UnaryExpression(-, NumberLiteral)`, not a `NumberLiteral`, so it missed the existing float-literal special case and stored `-3.5` as i64, printing `-3`.

Found while auditing example-file comments left stale by [ADR-00183](ADR-00183.md) (the `console.log(boolean)` → `true`/`false` fix): a `console.log(allInRange)` over a `let allInRange = true` still printed `1`, which traced back to this inference gap rather than to the console path.

## Decision

Add the missing inference cases:

- `emitVarDecl`: a `*ast.BooleanLiteral` initializer infers `TypeBool`; a `*ast.UnaryExpression` initializer infers via `inferExprType` (so `!` → bool, unary `-`/`+` → the operand's numeric type, `~` → i64).
- `inferExprType`: the `UnaryExpression` case now returns `TypeBool` for `!`, the operand's type for `-`/`+`, and `TypeI64` for `~` (previously only `typeof` was handled, everything else fell to the i64 default).

This is a runtime-representation fix, not just cosmetic: the variable's alloca is now i1 for a boolean, so it reads back and prints correctly and composes with `&&`/`||`/`!`/comparisons like any other boolean.

## Fallout

- **5 stale test assertions** that had encoded the old `1`/`0` output for a boolean *variable* (`tests/xhr_test.go` ×2, `call_test.go`, `os_test.go`, `structured_clone_test.go`) were corrected to `true`/`false` — the same kind of buggy-behavior-encoding assertion [ADR-00183](ADR-00183.md) swept out of the direct-boolean-expression tests.
- **Example comments**: the same audit corrected the stale `// 1 (true)` / `// 0 (false)` annotations left across 17 example files by [ADR-00183](ADR-00183.md) (which updated tests but not example comments). All are boolean prints that now correctly read `true`/`false`; the two with a boolean *variable* (`crypto.ts`, `xhr.ts`) are correct specifically because of this ADR's inference fix.

## Verification (Linux, x86-64)

- `let a = true` → `true`; `let c = true; c = false` → `false`; `let n = !(y > 3)` → `false`; `let m = y > 3` → `true`; `let z = -3.5` → `-3.5`; `let w = -7` → `-7`.
- New E2E tests `TestE2EUnannotatedBooleanVarInference` and `TestE2EUnannotatedNegativeFloatLiteral` in `tests/exprs_test.go`.
- Full `go test ./...` green after the 5 assertion corrections; `go vet` clean.
- `make conformance` re-run — see `docs/testing/CONFORMANCE-RESULTS.md`.
