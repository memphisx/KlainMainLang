# ADR-01132: TypeScript's declaration syntax parses; interfaces keep their members; a declaration-file parse mode

- **Relations**: `Implements TDD-00230` (Phase 1 P1.5 completion, Phase 3 P3.1 prerequisite); `Extends ADR-01105`
- **Date**: 2026-09-25

## Context

P3.1 declares the builtin surface in `.d.ts` files the checker reads. As a
first measurement of what the parser lacked, it was run over TypeScript's
own `lib.*.d.ts`. Almost every file failed. The failures were ordinary
declaration syntax, which user code writes too:

- optional methods (`get?(): any`);
- `readonly` property and index signatures;
- construct and call signatures with type parameters
  (`new <K, V>(entries?): Map<K, V>`);
- the polymorphic `this` type;
- type-parameter defaults (`<T, TReturn = any>`);
- index signatures keyed by an alias (`[key: PropertyKey]`);
- keyword and computed member names (`delete(key)`, `[Symbol.iterator]()`);
- `get`/`set` accessor signatures;
- constructor types (`abstract new (…) => T`, `new <T>(…) => T`);
- indexed access on any type (`[A, B][0]`);
- a leading `|` in a union split over lines;
- `+readonly`/`-readonly`/`-?` in mapped types;
- `this` parameters;
- trailing commas in type-parameter lists.

## Investigation

- **Two member grammars.** Interfaces were parsed by a member parser that
  predates the type-syntax tree (P1.5). It produced the older
  `AnnotField`/`InterfaceMethodSig` shapes directly and raised
  representation limits as parse errors: a call signature beside
  properties, an index signature beside properties, a second index
  signature. The newer type-literal member grammar covered more forms, but
  not all of the above.
- **Every annotation was converted eagerly.** `parseTypeAnnotation` turned
  every annotation into the older `TypeAnnotation` as it parsed, so a valid
  type that model cannot express was a parse error. A function type's
  return type was even validated through that conversion to tell `(T) =>
  R` apart from a parenthesised type.
- **Signature parameters.** The member grammar read an unannotated
  signature parameter as a type: `(e): boolean` was a parameter of type
  `e`. TypeScript has no type-only parameter; `(e)` is a parameter named
  `e` of type `any`.

## Decision

- **One member grammar**, `parseTypeMembers`/`parseTypeMember`, serves
  object types and interface bodies alike. It covers every member form in
  Context.
  - `PropertySignature` gains `Readonly`, `Computed`, `Accessor` and
    `JSDocType`; `MethodSignature` gains `Computed`; call and construct
    signatures gain `TypeParameters`; `IndexSignature` gains `Readonly` and
    takes any key type; `TypeParameter` gains `Default`.
- **Signature parameters always have names**: `x`, `x?`, `this`, or a
  binding pattern. An unannotated one is `any`. A leading `this: T` types
  `this` and is not a parameter.
- **`InterfaceDeclaration` keeps the declaration as written** (`Members`,
  `TypeParameters`, `Heritage` as type references), which the checker reads.
  - `ast.InterfaceLegacy` derives the older fields for code generation. A
    get/set pair becomes one field of the getter's type.
  - The first member shape code generation cannot represent is recorded in
    `LegacyErr`. `EmitProgram` reports it, so the program still parses and
    the checker sees it.
- **The `this` type** is a `KeywordType` with keyword `this`, including
  `this is T` predicates. Converting it for code generation is the new
  `ThisTypeUnsupported` (90024).
- **`parser.ParseDeclarations`** parses a declaration file. Its annotations
  stay type nodes (`ast.NodeAnnotation`), with no conversion, so every
  TypeScript type form parses. User code keeps the eager conversion until
  phase 2 deletes `TypeAnnotation`.
- **An ambient `declare function` inside a namespace** is a real member with
  a throwing stub, as at the top level (ADR-00471). It had been erased
  (ADR-00462).
- **The resolver renames the type names inside `Members`, `TypeParameters`
  and `Heritage`**, with a generic signature's own type parameters
  shadowing top-level names.

## Implementation notes

- `parser/parser_types.go`: `parseTypeMembers`, `parseTypeMember`,
  `parseMemberName`, `startsMemberName`, `balancedLength`,
  `parseSignatureTail`, `parseTypeParameterNodes` (defaults), the constructor
  and indexed-access forms, and `parseInterfaceDecl`.
- `parser/parser.go`: `ParseDeclarations`, and defaults in the older
  type-parameter list.
- `ast/type_convert.go`: `InterfaceLegacy`, `legacyMethod`,
  `NodeAnnotation`.
- `codegen/llvm/emitter.go`: reporting `LegacyErr`.
- `resolver/rename.go`: `rewriteTypeMember`.

## Side effects discovered

- **Checker gaps.** 521 more TypeScript corpus cases parse, and they
  exposed checker gaps the strict lane would have turned into false
  rejections: interface accessor pairs, optional methods, `this` types and
  predicates, aliased conditions, never-returning calls, readonly paths.
  They are fixed in [ADR-01133](ADR-01133.md) before these changes were
  staged.

## Verification

- **TypeScript 5.6.3's own `lib.*.d.ts`, all of them including
  `lib.dom.d.ts`,** parse in declaration mode.
- **AST dumps over 65,853 files** (TypeScript's cases, Test262, examples,
  apps, tests), comparing only the fields code generation reads:
  - 730 files newly parse, and none newly fails;
  - 15 TypeScript cases change shape, each a signature parameter now read
    as a name (`(e): boolean`, `...restParameters`) or an `extends string`
    base now dropped, as tsc reads them;
  - the only other changes are to files edited this session.
- **`tools/tsdiag`:** corpus parse failures fall from 2,788 to 2,267, and the
  checker runs on 6,576 single-file cases (from 6,099), with 1,358 of 1,360
  reports matching tsc's baselines.
