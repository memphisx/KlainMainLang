# ADR-01582: The conformance runner caps each process's data segment

- **Date**: 2026-10-11

## Context

The conformance runs in a 7 GB Linux arm64 container were killed three
times by the container's OOM killer: Test262 at 1,000 and at 8,000 files,
and the Node suite at 2,000 files. The runner's reaper (`tools/conformance/reaper.go`)
polls the RSS of workdir processes and kills a runaway over `-mem-cap-mb`.
It did not get the chance.

## Investigation

The Docker VM's kernel log shows the memory cgroup killing a test binary,
`node2.bin`, at 7.1 GB anonymous RSS. Then, with the cgroup still full, it
killed the runner itself. Sampling `ps` every 2 seconds caught a test
binary at 1.4 GB, then 4.1 GB two seconds later.

Polling the reaper every 250 ms (`KML_REAPER_INTERVAL_MS`) did not help.
The binary grows past the 3 GB cap and the container limit between two
polls.

## Decision

On Linux, the runner starts each compiled test program under
`RLIMIT_DATA` set to `-mem-cap-mb`, through `sh -c 'ulimit -d <KB> && exec
<program>'`. A program that allocates past it gets an allocation failure
and fails on its own, as it would hit V8's heap limit under Node. The run
goes on.

Only test programs get the limit. Setting it on the runner process, so
that everything inherits it, crashed the runner on x86-64 at startup: the
Go runtime there reserves more than 3 GB of heap metadata as writable
memory, and `RLIMIT_DATA` counts it.

The reaper's aggregate RSS ceiling stays: it covers many processes that
each stay under the limit.

macOS does not apply `RLIMIT_DATA` to mmap'd memory, and Windows has no
rlimits, so the limit is Linux-only (`datalimit_linux.go`,
`datalimit_other.go`).

## Implementation notes

`limitProgram` wraps the run command at both run sites (`runOne` in
`main.go`, the node runner in `node.go`). The shell execs the program, so
the pid, process group and command line the reaper and timeouts use are
the program's. A cap of 0 (`-mem-cap-mb 0`) leaves programs unlimited.

## Verification

- Builds and vets for linux, darwin and windows.
- Linux x64 (Node304): the node suite's strict lane runs to the end with
  `-mem-cap-mb 3000`.
- Linux arm64 (Docker on the Mac, 7 GB): the full Test262 and Node runs
  with `-mem-cap-mb 3000`; see the results committed under
  `docs/testing/linux-arm64/`.
