# ADR-01059: Arrays, TypedArrays and Symbols keep their identity inside `any`; a mixed array literal never reinterprets a buffer

- **Relations**: Extends ADR-00934 (`Array.isArray(any)`), ADR-01057 (`TypedArray.set` offset); Implements TDD-00200 (union-element arrays, the `-compat=js` boxed-literal half), TDD-00212 (any-boxed array rendering); Extends TDD-00044 (Symbol V1)
- **Date**: 2026-09-22

## Context

BACKLOG §0 item 1, three findings from session 21 that turned out to share one root: a value that is *shaped* like
something else once it crosses into an `any` box.

- `const mixed = [[7], new Int32Array([8])]` inferred `number[][]` and stored the Int32Array's header in a
  `number[]` slot: `console.log` printed `[ [ 7 ], [ 4e-323 ] ]` (i32 bits read as doubles) and `ta.set(mixed[1])`
  wrote 0. Node keeps both (`[ [ 7 ], Int32Array(1) [ 8 ] ]`).
- `ta.set(src)` with `src: any` was a compile error (`value is not an array`).
- A Symbol inside an `any` was a plain object: `typeof x` → `"object"`, `Number(x)` / a `set` offset → `NaN`
  where Node throws `TypeError`, and `typeof x === "symbol"` narrowing could not work.

Reproducing those surfaced four more in the same corner, all wrong in the same "loses its identity" way:

- `const y: any = new Int32Array([8, 9]); console.log(y)` printed `Int32Array(0) []`.
- A boxed TypedArray rendered as a plain array (`[ 8, 9 ]`), `Array.isArray` said `true` for it (static and
  boxed), and `JSON.stringify` of any boxed static array was "a statically-typed value in the tree".
- `x[1]` on an `any` holding a plain `number[]` threw "dynamic property access on a statically-typed value is not
  supported" (only `.length` worked).
- `const cfg: any = …; function f() { return cfg.x }` → `undefined variable 'cfg'`: an annotated `any` module
  binding was never promoted to a module global.

## Investigation

- The array literal: `inferArrayType` (`emit_exprs_types.go`) keys heterogeneity on `elemKindKeyBroad`, whose
  array case returned the bare word `"array"`, so two arrays of any storage counted as one kind; and
  `emitArrayLiteralData` (`emit_arrays_core.go`) only rejected `val.Ty.IsArray != elemTy.IsArray` — both sides
  arrays, so the header was stored. Nothing compared the element storage.
- The `Int32Array(0) []`: `reliableGlobalType` (`emit_exprs_vardecl.go`) returned `TypedArrayType(kind)` for a
  `NewTypedArrayExpression` initializer regardless of the annotation, while `emitVarDecl` types an annotated
  binding from the annotation and boxes — the pre-declared global was a raw array header slot, the store an `any`
  word, and the read site loaded the tagged pointer as a header (length 0). The IR showed the box built correctly
  and the wrong read.
- The any-boxed array box (`anyArrayBoxTy`, TDD-00212) carried `{ live header, element-kind byte }` — enough to
  stride and print flat scalar arrays, but no typed-array bit (a `number[]` with `@type int32` and an
  `Int32Array` boxed identically), no kind for `any[]` or nested-array elements, and no element read path at all:
  `emitDynAnyMemberGetNamed` (`emit_dynobj.go`) had arms for dynobj/dynarr only.
- Symbols: `SymbolType()` was a one-field struct (`description`) boxed as `kmlTagObject`; the 3-bit pointer-kind
  space of the NaN box is full (TDD-00156), so a new tag was not an option. Errors solve the same problem with a
  hidden field-0 marker bit (`errorTypeIDFlag`, bit 48 — user-space pointers are < 2^47 on every target, so a
  plain struct whose field 0 is a pointer or small tag can never carry it). The Error probes test bit 48 and the
  low bits (`errorSubclassTagBase`), and the thrown-slot classifier and `dynjson.c` test bit 48 too — so a Symbol
  could not share bit 48 without touching every one of those; a second, independent bit could.
- `Array.isArray`: the static path returned `true` for any `IsArray` type (a TypedArray *is* `IsArray` storage-
  wise); the `any` path checked only the box tag.

Alternatives rejected: (a) a strict-lane `(number[] | Int32Array)[]` union element — TDD-00043 defers object/array
union members and the js lane's `any[]` already gives Node's observable behaviour, so strict keeps its documented
uniform-only rule with a clean rejection; (b) implementing `set(any)` by an emitter-side tag switch — the element
stride by kind already lives in C (`__kml_array_join`), so the walk went there and the emitter consumes one
materialised `double` buffer through the existing copy loop; (c) making a nested-array element fully recursive —
elements are header pointers whose element type is only known statically, so the box describes exactly one more
level (that covers `T[][]`; deeper levels read their length and refuse element reads honestly).

## Decision

1. **Array-literal unification is by storage.** `arrayStorageKey(t)` (`emit_func.go`) names an array's element
   IR, its typed-array family (plain / typed / clamped / bigint / Buffer) and, recursively, a nested element's
   storage. `elemKindKeyBroad` uses it for the array kind, so `-compat=js` boxes `[[7], new Int32Array([8])]` to
   `any[]` (TDD-00200), and `emitArrayLiteralData` rejects two arrays with different keys under one slot in strict
   (or under an explicit annotation) with the element named: "element 1 is a Int32Array, not a number[]".
2. **The any-array box describes what it holds.** `anyArrayBoxTy` is `{ ptr hdr, i8 kind, i8 typed, i8 ikind,
   i8 ityped }` (still one 16-byte cell): `typed` is 0 plain / 1 TypedArray / 2 Uint8ClampedArray; `kind` gains
   `KJ_ANY` (12, elements are boxes) and `KJ_ARRAY` (13, elements are header pointers, described by `ikind`/
   `ityped`); a BigInt64Array's raw i64s are bigint handles, so its kind is -1. `dynjson.c`'s `KjBox` mirrors it.
   `__kml_array_join` / `__kml_array_inspect` take the box and render a TypedArray with Node's `Int32Array(2) `
   prefix; a boxed static array nested in a dynamic value renders through the same walkers (it was `[object
   Array]` / `[Object]`); `JSON.stringify` serialises a plain boxed array as a JSON array and a TypedArray as its
   index-keyed object (`{"0":8,"1":9}`), as the spec does.
3. **Element access through `any`.** `__kml_anyarr_get_by_key(box, key)` answers `length`, a canonical index
   (undefined past the end) and undefined for anything else; a numeric element widens to a double (a JS number is
   a double), a string is its pointer, an `any[]` element is the word itself, a `T[][]` element is re-boxed with
   the inner bytes. An in-range index into an undescribed kind answers the otherwise-unused immediate 1 and the
   emitter arm throws a TypeError rather than inventing `undefined`.
4. **`TypedArray.prototype.set(source)` with an `any` or non-array source** is the spec's ToObject +
   LengthOfArrayLike + per-index Get/ToNumber walk: `__kml_any_arraylike_f64(word, &len)` materialises a boxed
   static array, a dynamic array, a string (characters), a dynamic object (`length` and index keys) or a boxed
   number/boolean (no length → zero elements) as a fresh `double` buffer; null/undefined answer length -1 and the
   emitter throws `Cannot convert undefined or null to object`. The argument is emitted under an `any` hint so an
   object literal becomes a walkable bag, and a named static object is copied to a bag for the read (identity
   never escapes the call). The existing per-element coercion loop then runs unchanged (clamping included).
5. **A Symbol is a tagged struct.** `SymbolType()` is `{ i64 __kml_typeid, ptr description }`, field 0 =
   `symbolTypeIDFlag` (bit 47), stored by both allocation sites (`Symbol()`, `Symbol.for`) and hidden from
   `VisibleFields`. `emitBoxedSymbolProbe` is the field-0 test under a `kmlTagObject` tag check; it feeds
   `typeof` (`"symbol"`), the dynamic ToString (`Symbol(desc)` for `console.log`/`String()`), member reads through
   `any` (`description`; anything else undefined), and `__kml_any_tonum` throws `Cannot convert a Symbol value
   to a number` — which is what `Number(x)`, `+x`, `x * 1` (js lane) and a `set` offset now do.
6. **`Array.isArray`** is `false` for a TypedArray/Buffer statically and, through `any`, reads the box's typed
   byte; **an annotated dynamic module binding** (`any`/`unknown`/union, not a dynamic object) promotes to a
   module global like the js-lane widened bindings already did, with `undefined` as its zero value; and
   `reliableGlobalType`'s typed-array arm applies only to an unannotated binding.

## Implementation notes

- `codegen/llvm/dynjsonsrc/dynjson.c`: `KjBox`, `kj_elem_box`, `kj_elem_render`, `kj_join`/`kj_inspect`, the
  stringify tag-7 arm, `__kml_anyarr_get_by_key`, `__kml_any_arraylike_f64` (calls `__kml_toprimitive`,
  `__kml_any_tonum`, `__kml_dynobj_get` — so `ensureDynJSONC` now forces those three runtimes in whenever the C
  file is linked; the C object references them unconditionally). The C-side `nb_pack`/`nb_double` mirror
  `__kml_nb_pack` and must stay in sync with `runtime_nanbox.go`.
- `emit_dynamic.go`: `anyArrayBoxTy`, `anyArrayBoxBytes`, `boxAnyArray`, the dynstr array arm now passes the box,
  `emitDynamicTypeof` and the dynstr object arm probe for a Symbol. `emit_dynobj.go`: the `kmlTagArray` arm in
  `emitDynAnyMemberGetNamed` (the old `length`-only arm is subsumed) and the Symbol read in the object arm.
- `emit_arraybuffer.go` (`emitTypedArraySet`), `emit_call.go` (`isArray`), `emit_exprs_vardecl.go`
  (`reliableGlobalType`), `emit_func.go` (`arrayStorageKey`, `arrayTypeName`, `elemKindKeyBroad`),
  `emit_arrays_core.go` (`emitArrayLiteralData`), `emit_symbol.go`, `emit_anyops.go`, `types.go` (`SymbolType`,
  `VisibleFields`, `zeroLiteral`), `dynjson_c.go` (declarations).
- The `any`-source `set` with a BigInt64Array target stays the existing compile-time rejection (the source's
  static type is not BigInt-elem); a ToBigInt walk is not built.

## Side effects discovered

- `x * 1` / `+x` on an `any` remain the strict lane's documented compile-time rejection (TDD-00076); the Symbol
  TypeError for those spellings is observable under `-compat=js` and through `Number(x)` in both.
- Node collapses `console.log` nesting past depth 2 (`[ [ [ [Array] ] ] ]`); neither the dynamic walker nor the
  box walker does. Pre-existing; unchanged here.
- `const m: any = new Map()` and the other init-typed `new` shapes (`Set`, channels, WeakMap/Set/Ref) still type
  the binding from the initializer rather than the annotation in both `emitVarDecl` and `reliableGlobalType`
  (consistent with each other, so no wrong read — but not an `any`). BACKLOG §0.
