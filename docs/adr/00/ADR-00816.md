# ADR-00816: `-webview=sailfish` shim — Gecko/embedlite backend (Stage 3 start)

- **Relations**: `Implements TDD-00146`, `Extends ADR-00815`

- **Date**: 2026-09-09

## Context

TDD-00146 Stage 3 adds a `-webview=sailfish` backend so `klain:webview` apps run
on Sailfish OS over its Gecko engine, under the [ADR-00815](ADR-00815.md)
`-webview=<backend>` flag. The engine there is embedlite/qtmozembed, exposed to
apps as the `Sailfish.WebView` QML component. The goal is to satisfy the same
13-function `webview_*` C ABI the vendored webview/webview binding satisfies, so
the entire klain:webview language surface (bind / typed-bind / eval / serve /
`--emit-window-dts`) works unchanged — only the engine underneath differs.

## Investigation

Probed a physical Xperia 10 II (5.1.0.11) over SSH and an exported Sailfish
`-devel` sysroot:

- The device is runtime-only: `Sailfish.WebView` QML + `libqt5embedwidget` /
  `libsailfishwebengine` present, but no headers, no `qmake`, no `.pc` files. A
  reproducible `-devel` sysroot was built instead (`docker/Dockerfile.sfos-sysroot`,
  Qt 5.6.3 + qtmozembed + sailfish-webengine devel).
- The view contract, from `qmozview_defined_wrapper.h`: `Q_INVOKABLE
  runJavaScript(script, cb)`, `sendAsyncMessage(name, variant)`,
  `addMessageListener(name)`, signal `recvAsyncMessage(name, data)`,
  `loadFrameScript(name)`, `load`/`loadHtml`. Engine init is
  `SailfishOS::WebEngine::initialize(profile)` (`libsailfishwebengine/webengine.h`).
- The instantiable view is `RawWebView` (QML type from the plugin, wrapping
  `QuickMozView`, a `QQuickItem`). It owns the QMozWindow/GL/compositor wiring —
  the shipped `WebView.qml` is `RawWebView { … }`. The built-in frame script
  `embedhelper.js` already implements `embedui:runjavascript` (content-side JS
  execution behind `runJavaScript`).
- The bind protocol in webview.h is transport-over-`window._rpc`: `window[name]`
  returns a Promise and calls `window.external.invoke(JSON.stringify({id,method,
  params}))`; native settles via `eval("window._rpc[seq].resolve(...)")`.

## Decision

Host the shipped `RawWebView` QML type from C++ rather than re-instantiate
`QuickMozView` (which would mean re-doing the QMozWindow/GL wiring by hand):
`QGuiApplication` → `SailfishOS::WebEngine::initialize` → a `QQuickView` whose
root item is an inline `RawWebView`. Drive it with `QMetaObject::invokeMethod`
(`load`/`loadHtml`/`runJavaScript`) and read back through the `recvAsyncMessage`
signal.

Reuse webview.h's exact `window._rpc` bind glue verbatim so the TS contract is
untouched; only the transport differs:

- **page→native**: `window.external.invoke` dispatches a DOM `CustomEvent`
  (`kmlrpc`); a small frame script (loaded via `loadFrameScript`) forwards it as
  `sendAsyncMessage("embed:kmlrpc", {msg})`; the chrome side `addMessageListener`
  + `recvAsyncMessage` surfaces it in C++ → `on_message` → the bound trampoline.
- **native→page** (eval, promise resolution): `runJavaScript(script)`,
  fire-and-forget, mirroring webview.h's `eval`.
- **init scripts**: replayed on each `domContentLoaded`.
- **cross-thread dispatch**: Qt 5.6 lacks the functor `invokeMethod` overload, so
  `webview_dispatch` posts a `QEvent` carrying a `std::function` to the GUI-thread
  object, whose `event()` runs it — the Qt variant of the loop-fusion pump.

The shim is one self-contained `webviewsrc/webview_sailfish.cpp` that `#include`s
its moc output (`webview_sailfish.moc`). Because it is a `QObject` with slots, the
build must run the target's aarch64 `moc` (frozen Qt 5.6.3, portable output) over
it before compiling — the one structural difference from the system backend's
single-.cc-on-the-clang-line model. `LocateWebviewSailfish(sysroot)` resolves the
compile/link flags from the sysroot's pkg-config (`PKG_CONFIG_SYSROOT_DIR`);
`sailfishwebengine.pc` transitively pulls Qt5 + qt5embedwidget + xul/nspr with the
xulrunner rpath.

## Implementation notes

New files: `codegen/llvm/webviewsrc/webview_sailfish.cpp` (the shim),
`codegen/llvm/webview_sailfish.go` (`SailfishWebviewShimSource`,
`LocateWebviewSailfish`, `RunSailfishMoc`, the pkg-config recipe). `WebviewSource("sailfish")`
now returns the real shim; `LocateWebview("sailfish")` still gates end-to-end
klainmain builds cleanly because the moc pre-step is not yet integrated into the
`EmbeddedCSources` pipeline — that integration (+ un-gating + an example/E2E lane)
is the next chunk.

## Side effects discovered

The moc requirement means the embedded-C-source pipeline (compile one `.cc` on the
shared clang line) does not fit a Qt backend as-is; wiring `-webview=sailfish`
end-to-end needs a per-source moc hook. Recorded as the remaining Stage-3 work,
not addressed here.

## Verification

Built `docker/Dockerfile.sfos-sysroot` and, in an arm64 Linux container against
that real Sailfish 5.1.0.11 `-devel` sysroot, ran the target's `moc 5.6.3` over
the shim (→ a 116-line meta-object) and compiled it with `g++ -c` to a clean
object (exit 0), then linked it into an executable with the pkg-config recipe
(exit 0). This is compile+link-tier verification against the genuine target
headers/libraries. The on-device windowed run (Wayland/lipstick launch env,
confirming the `loadFrameScript` URL scheme and the CustomEvent bridge) is the
remaining runtime tier, gated on device-session iteration. `go build`, `go vet`,
and `TestE2EWebviewBackendFlag` green on macOS.
