# ADR-00142: Import-gated built-in bindings, Stage 2 (named per-member imports)

- **Relations**: Extends [ADR-00141](ADR-00141.md). Implements [TDD-00049](../tdd/TDD-00049.md)
- **Date**: 2026-08-10

## Context

[ADR-00141](ADR-00141.md) shipped Stage 1 of [TDD-00049](../tdd/TDD-00049.md): `fs`/`path`/`os`/`querystring`/`assert`/`http`/`cluster`/`Memory` require a default or namespace import (`import fs from 'fs'`), closing a confirmed real shadowing/miscompilation bug. Named imports (`import { readFileSync } from 'fs'`) were deliberately rejected with a clear error — real Node itself supports both forms for its core modules, and Stage 1's own design note assumed named imports would need "a second, new codegen dispatch shape (bare-identifier-call, keyed per-member rather than per-namespace)."

This ADR builds that: named per-member imports from every Stage-1 virtual module.

## Investigation

Re-read `resolver/rename.go` in full before designing anything, specifically to check whether Stage 1's prediction (a genuinely new codegen dispatch shape) was actually necessary, or whether the existing machinery already covered it once looked at closely enough.

Found that `rewriteExpr`'s `*ast.MemberExpression` case (added by [TDD-00042](../tdd/TDD-00042.md)/[ADR-00135](ADR-00135.md) for namespace-import member access) already establishes the pattern needed: it *replaces* a node wholesale (`return ast.NewIdentifier(mangled, e.GetPos())`) rather than mutating one of its fields, and every call site of `rewriteExpr` already reassigns its return value back into the field/slice element that held the original expression (`e.Callee = rewriteExpr(e.Callee, sc, lu)`, `e.Args[i] = rewriteExpr(...)`, `s.Init = rewriteExpr(...)`, etc. — confirmed by reading every case in the function). That means the *inverse* replacement — a bare `*ast.Identifier` expanding into a synthesized `*ast.MemberExpression` — is equally supported by the existing architecture with no changes to any call site, only to the `*ast.Identifier` case itself.

Once that was clear, the practical question became: does every dispatch site Stage 1 already built (`emit_call.go`'s member-call switches, `emit_exprs_member.go`'s property-read switches, both type-inference mirrors in `emit_exprs_types.go`) work identically whether the `*ast.MemberExpression` it receives was hand-written by the user (`fs.readFileSync(...)`) or synthesized by the resolver moments earlier? Every one of those sites pattern-matches on `mem.Object.(*ast.Identifier).Name` and `mem.Property` — both plain string fields, populated identically either way. Confirmed directly: a synthesized `MemberExpression{Object: Identifier{"fs__kml_builtin"}, Property: "readFileSync"}` is byte-for-byte indistinguishable, by the time codegen runs, from the same node built by parsing `fs.readFileSync`. **No codegen changes were needed at all** — Stage 1's own prediction (in its Design section, not literally reproduced here since that document is now frozen per `docs/tdd/README.md`'s own rule) turned out to be more pessimistic than the actual shape of the fix.

## Decision

**Resolver-only implementation**, in three pieces:

1. `resolver/virtual_modules.go`: added `virtualModuleMembers`, a per-specifier table of real member names (`"fs": {"readFileSync": true, ...}`), used to validate a named specifier the same way a real file import's specifiers are already validated against that file's own `exportedNames` — an unknown member name is a clean `built-in module 'fs' has no exported member 'bogusMethod'` error, not a silent no-op or a codegen-time crash. Kept by hand in sync with each domain's own dispatch switch in `codegen/llvm` — there's no single source of truth to generate it from, since those switches are Go source, not data.
2. `resolver/rename.go`: `lookupTable` gained a third map, `builtinMembers map[string]builtinMemberRef` (local alias → `{Marker, Member}`), alongside the existing `names`/`ns`. `rewriteExpr`'s `*ast.Identifier` case checks it after `lu.names` (a name can only ever be bound one way — resolver's existing duplicate-binding checks already guarantee that) and, on a match, returns `ast.NewMemberExpression(ast.NewIdentifier(ref.Marker, pos), ref.Member, pos)` instead of the original identifier — guarded by the same `!sc.bound(e.Name)` check every other lookup here already uses, so a local variable shadowing an imported name is unaffected.
3. `resolver/resolver.go`: the per-file import-processing loop's existing Stage-1 branch (recognizing `imp.Source` as a virtual specifier) gained a loop over `imp.Specifiers`, skipping the synthetic `"default"` entry (still handled by `virtualImportLocal`, unchanged from Stage 1) and validating/binding every other one into `builtinMembers` — with the same "already declared in this file" duplicate-name check every other binding path here already has.

`import fs, { existsSync } from 'fs'` (combining a default and named specifiers in one statement, [TDD-00042](../tdd/TDD-00042.md)'s existing sugar) works with no special-casing: the named-specifier loop binds `existsSync` while the pre-existing `virtualImportLocal` call binds `fs`, independently.

## Implementation notes

- `resolver/virtual_modules.go`: `virtualModuleMembers` table added, `virtualImportLocal`/`virtualBuiltinMarkers` unchanged from Stage 1.
- `resolver/rename.go`: `builtinMemberRef` type added; `lookupTable.builtinMembers` field added; `rewriteExpr`'s `*ast.Identifier` case restructured (an explicit `break` after a `lu.names` hit, so the new `builtinMembers` check is only reached when the name wasn't already a plain rename).
- `resolver/resolver.go`: one new validation/binding loop inside the existing Stage-1 virtual-specifier branch; no changes to the two earlier passes (dependency-visiting, specifier-validation) — those already skip virtual specifiers entirely and let this final pass do all real work, same as Stage 1.
- `codegen/llvm`: **zero changes** — see Investigation.
- `tests/import_gated_builtins_test.go`: `TestE2EImportGatedNamedImportRejected` (asserted Stage 1's rejection) replaced with six Stage 2 tests — a function-shaped member (`readFileSync`/`writeFileSync`/`unlinkSync`), a plain-value member (`os.EOL`, deliberately exercised separately from the function case since it's a different dispatch shape one level up in `emit_exprs_member.go`), aliasing (`import { readFileSync as rfs }`), combining default and named specifiers in one statement, a named import shadowed by a real local variable, and an unknown-member rejection.
- `examples/imports/named_builtin_import.ts` (new): named imports of both a function member and a value member, plus aliasing — the project's standing "new feature ⇒ example" rule.

## Side effects discovered

None beyond what [ADR-00141](ADR-00141.md) already recorded (the `path.join`/`Array.prototype.join` message-quality overlap, and Category A/C shadowing staying open by design) — Stage 2 didn't touch codegen at all, so it couldn't introduce a new instance of either.

## Verification

- `go build ./...`, `go vet ./...`, `go test ./...` all clean.
- Manual smoke tests (this session, Linux) before writing formal coverage: function-member named import round-trip, `os.EOL` as a bare named import, aliased named import, a named import correctly shadowed by a function-local variable of the same name, an unknown member name rejected with a clean error, and `import fs, { existsSync } from 'fs'` combining both forms in one statement — all matched expected behavior on the first attempt, consistent with the "no codegen changes needed" finding above.
- `tests/import_gated_builtins_test.go`'s 6 new Stage 2 tests, plus the 8 existing Stage 1 tests in the same file, all pass.
- `make examples`: 98/98 passed (97 from Stage 1 plus the new `named_builtin_import.ts`).
