# TDD-00001: Memory Management: garbage collection and manual memory release

- **Status**: Partially Implemented — the `-mm` flag, `manual` mode (the default, via `Memory.free(x)`, [ADR-00030](../adr/ADR-00030.md)), and `gc` mode (Boehm GC, [ADR-00071](../adr/ADR-00071.md)) are all done; `auto` mode is still not started
- **Date**: 2026-07-12 (revised 2026-07-28 — reframed around a compile-time-selectable mode flag; see below)

## Context

Every heap allocation this compiler emits (arrays growing/`push`ing, object literals, closure environments, string concatenation/slicing/template literals, `Map`/`Set` backing tables, JSON/Date formatting scratch buffers, boxed `any`/`unknown` payloads, …) goes through a plain `@malloc`/`@realloc` call and is never `free`d, except where a program explicitly calls `Memory.free(x)`. There is no ownership tracking, no reference counting, and no reachability analysis anywhere in the emitted code — a program's resident memory only ever grows for as long as it runs, unless the programmer frees things by hand.

**Why this hasn't mattered yet**: every example and test compiles to a short-lived CLI-style process that runs for milliseconds and then exits, at which point the OS reclaims everything in one shot. This is a real, common, and completely legitimate way to run native programs — it's exactly how plenty of tiny C utilities behave too.

**Why it will matter**: this project's longer-term direction includes long-running microservice-style processes (an event loop + a listening HTTP server — see [TDD-00006](TDD-00006.md)/[TDD-00004](TDD-00004.md) — are the biggest missing structural piece toward that). A process that's meant to stay up and keep handling requests, but that never frees a single allocation, will grow without bound and eventually get OOM-killed — a hard blocker for the microservice use case specifically, even though it's a complete non-issue for the CLI use case.

**Why this TDD was revised rather than superseded**: the original version of this document treated "add a GC" and "add manual `Memory.free`" as two independent, freely-stackable features — pick one, the other, or both, no real interaction between them. In practice that framing hid a third, genuinely distinct answer (the compiler deciding for itself when to insert frees, with no runtime collector at all — Stage 2/3 below), and glossed over the fact that these three answers don't actually compose cleanly in one binary: a runtime GC changes what the allocator symbol *is* (`GC_malloc` instead of `malloc`), and compiler-inserted frees need to know, program-wide, that nothing else is freeing the same pointer out from under them. Rather than "features a program can mix and match," this is better modeled as **one compilation-wide choice of memory-management backend**, selected once per compiled binary via a new flag, with each mode fully replacing the others for that build.

## Design

### The three memory-management modes

A new compiler flag, `-mm=manual|gc|auto` (mnemonic: "memory mode"; default `manual`, matching today's shipped behavior with zero migration needed), selects exactly one backend for the whole compiled binary:

| Mode | Who frees | Runtime cost | Safety |
|---|---|---|---|
| `manual` (default) | The programmer, via explicit `Memory.free(x)` calls | None beyond `malloc`/`free` themselves | Same as C: forget to free → leak; double-free/use-after-free are the programmer's problem |
| `gc` | The Boehm collector, automatically, whenever it feels like running | Conservative stack/heap scanning, stop-the-world pauses | Safe by construction — a reachable block is never collected |
| `auto` | The compiler, at specific points it proves are safe (no runtime collector at all) | None beyond the `free` calls themselves — cheaper than `gc` when the analysis succeeds | Safe *if* the escape analysis is correct; a wrong analysis is a real use-after-free, not just a delayed free |

These are mutually exclusive per binary, not layered:

- **`manual` mode** is exactly what exists today: plain `@malloc`, and `Memory.free(x)` is the only way anything is ever released (Stage 1 below). This stays the default — it's what every existing example/test already assumes, and changing the default would be an unannounced behavior change to every program compiled so far.
- **`gc` mode** swaps the allocator symbols (`@malloc`/`@realloc` → `@GC_malloc`/`@GC_realloc`, one-time edits in `runtime.go`'s `ensure*()` declarations) and links `-lgc`. `Memory.free(x)` **stays legal and useful** in this mode — it's not disabled, it lowers to `GC_free` instead of libc `free`, which Boehm documents as always safe to call explicitly as a latency optimization (early-release a block you know is dead now, rather than waiting for the next collection cycle to notice). This is the one place the "complementary" framing from the original TDD still holds: `gc` mode is `manual` mode's allocator plus a safety net, not a replacement for the escape hatch.
- **`auto` mode** compiles with plain `@malloc`/`@free` (no `-lgc`, no runtime collector at all) and has the compiler itself insert `free` calls at compile-time-proven-safe points (Stage 2/3 below). **`Memory.free(x)` is a compile error in this mode** — not just redundant but actively unsafe to allow, since the compiler's own inserted frees have no way to know a value was already released out from under them by a manual call it didn't plan for. This is the one real hard exclusivity rule the mode split needs to enforce.

### Automatic reclamation backend for `gc` mode: four options considered, before landing on Boehm

1. **Reference counting** (increment/decrement a count on every store/scope-exit for each heap-allocated type, free at zero). Deterministic, no pause times — but it means threading inc/dec logic through nearly every existing codegen path (arrays, objects, closures, strings, `Map`/`Set`, `any`/`unknown` boxing all live in separate `emit_*.go` files today, each would need this bookkeeping added). It also doesn't handle reference cycles on its own, and cycles get more likely, not less, once `class`/`extends` (already on the roadmap) lets user code build arbitrary mutable object graphs — refcounting would likely need revisiting again at that point anyway. Highest implementation cost of the realistic options, for a project this size.
2. **Arena/region allocation with scope-based bulk free** (allocate from a per-call bump-pointer arena, free the whole arena — one pointer reset — when the call returns). Cheap at run time and simple to reason about for genuinely local temporaries (a lot of the scratch buffers this compiler already allocates — e.g. every `Date` formatter's `sprintf` buffer — are handed to `console.log` and never touched again, a perfect fit). But it only works for values that provably never escape their allocating scope, which needs a real escape-analysis pass to detect — and this language already returns objects/arrays/closures from functions and stores them in longer-lived variables constantly, so a large fraction of allocations would still need to fall back to today's "never freed" behavior (or be promoted to a longer-lived arena) without that analysis. A good complementary optimization for hot, clearly-local allocations later, not a full fix on its own.
3. **A precise, stack-map-driven tracing collector** (the V8/JVM-style "real" GC). Needs exact enumeration of every live root at every potential collection point — safepoints, stack maps, a relocating (or at least precisely-scanned) heap. This is a serious, multi-month compiler-engineering project in its own right, and disproportionate to what a personal, exploratory compiler like this one needs right now.
4. **A conservative garbage collector, e.g. the Boehm–Demers–Weiser collector (`libgc`)** — swap the declared `@malloc`/`@realloc` symbols for `@GC_malloc`/`@GC_realloc` (a handful of `ensure*()` edits in `runtime.go`), link `-lgc`, and stop there. The collector conservatively scans the native stack, registers, and its own managed heap for anything that looks like a pointer into a live allocation, and reclaims blocks nothing points to — no ownership discipline, no stack maps, and no changes needed to any of the existing per-feature codegen files beyond the allocation call sites themselves. It's decades-old, production-hardened (used by Mono's older runtimes, GCC's Objective-C runtime, GNU Guile, and others), and specifically designed for exactly the "every pointer is just a plain pointer, freely copied around, with zero ownership bookkeeping" world this compiler already lives in.

**Recommended backend for `gc` mode**: option 4 (Boehm GC) — by a wide margin, the best effort-to-correctness ratio for this codebase's current shape, since it requires no redesign of how any existing feature allocates or passes around heap values. Trade-offs worth knowing going in: it would be the project's first non-libc external dependency (adds a build/deploy requirement that doesn't exist today, and only for binaries actually compiled with `-mm=gc` — `manual`/`auto` builds stay dependency-free), it can rarely retain a block slightly longer than necessary if a stray bit pattern happens to look like a pointer (never a use-after-free — only ever a delayed free), and it introduces stop-the-world collection pauses that would need re-evaluating once/if the event-loop/networking work ([TDD-00006](TDD-00006.md)) makes this a latency-sensitive long-running service. Option 2 (arenas) is worth revisiting later as a targeted optimization layered under `gc` mode specifically, for the specific allocations that are provably short-lived — not as a replacement for it, and not applicable to `manual`/`auto` modes at all.

### `manual` mode (default): user-controlled release, staged from cheapest to most Rust-like

**The three families of memory management, in general** — useful background for why `manual` and `auto` are being staged the way they are:

1. **Manual (C/C++)** — the programmer calls `free`/`delete` explicitly. Fast and precise, zero runtime overhead, but the programmer is fully responsible for correctness: forget to free → leak; free twice → corruption; free something still referenced elsewhere → use-after-free, often surfacing as a crash somewhere completely unrelated later. This is `manual` mode.
2. **Automatic tracing GC (Java, Go, JS, Python-ish)** — the runtime periodically determines which heap values are still reachable from the stack/globals/registers and frees everything else. Safe by construction (nothing is ever freed while still reachable), at the cost of runtime overhead and some kind of pause/throughput hit. This is `gc` mode.
3. **Ownership/borrowing, checked entirely at compile time (Rust)** — no runtime GC *and* no manual `free()` calls, because the compiler statically proves exactly when a value's last use happens and inserts the cleanup itself. `auto` mode is a much smaller-scoped cousin of this, not a full reimplementation of it (see below).

**How Rust's model actually works, since it's the interesting third option and the direct inspiration for `auto` mode:**

- Every value has exactly one **owner** (a variable binding). When that owner's scope ends, the compiler automatically inserts a call to the value's destructor (`drop`) — this is RAII (a discipline borrowed from C++), made mandatory and compiler-enforced everywhere rather than opt-in.
- **Assignment moves ownership**, and the compiler tracks it: `let b = a;` (for a non-trivially-copyable type) transfers ownership from `a` to `b`; afterwards, using `a` again is a *compile-time* error, not a runtime check. This is what rules out double-free and use-after-free — the compiler simply refuses to build a program that would do either.
- **Borrowing** (`&T` shared, `&mut T` exclusive) lets code use a value without taking ownership of it. The borrow checker enforces, statically: many shared borrows *or* one exclusive borrow (never both), and no borrow may outlive the value it points to. This replaces "the GC keeps it alive as long as something points to it" with "the compiler proves nothing can point to it after it's gone."
- When single ownership genuinely isn't expressive enough (data that's legitimately shared — e.g. a graph node, or state shared across threads), Rust's answer is `Rc<T>`/`Arc<T>` — i.e. **reference counting, opted into per-value** for the specific cases that need it, not a whole-program GC. Even Rust's own escape hatch is refcounting.
- The reason none of this needs a runtime GC is that the entire discipline is enforced *before the program runs*, by a dedicated compiler pass (the borrow checker) doing lifetime inference across each function. That pass is one of the most complex parts of the whole Rust compiler — a multi-year, still-evolving piece of engineering (the "non-lexical lifetimes" rewrite alone took years) — and building the equivalent here would be disproportionate to this project's scope. It'd also be a language-design mismatch: TypeScript programmers don't think in terms of "who owns this value," and bolting `&`/`move` syntax onto TS-shaped code would mean designing a new language, not extending this one. `auto` mode deliberately does not attempt this — see below.

**What's actually feasible for KlainMainLang — a staged plan spanning `manual` and `auto` modes, from cheapest to most Rust-like:**

- **Stage 1 — a raw, unsafe `Memory.free(x)` builtin. (`manual` mode — done, [ADR-00030](../adr/ADR-00030.md))** Resolves `x`'s underlying heap pointer (array data pointer, object struct pointer, closure header + environment, Map/Set backing buffers) and frees it. Shallow only: frees the value's own top-level allocation(s), never anything reachable *through* it (a string field inside a freed object, a captured variable's shared cell) — no analysis, no safety net beyond nulling out a named variable's own storage after freeing it. The programmer is fully responsible, exactly like C — including the same C-shaped footgun where a string *literal* is a compile-time global constant, not malloc'd, so freeing one crashes exactly like C's own `free("literal")`.
- **Stage 2 — scope-exit auto-free via a JSDoc annotation, plus a cheap escape check. (`auto` mode, first cut)** e.g. `/** @free */ let buffer: number[] = loadBigThing()` — the compiler inserts `free(buffer)` at every exit path of the enclosing block (return, break, throw, fallthrough), the same places `finally`-block cleanup already hooks into. The part that actually matters for safety: before allowing `@free`, do a conservative, purely local check — does this identifier ever appear in a `return`, get assigned to a variable from an outer scope, get passed somewhere it might be stored, or get captured by a closure? If it might escape the block, reject `@free` at compile time rather than silently creating a dangling reference elsewhere. This is *not* Rust's lifetime inference — it's a much smaller, local check — but it gets most of the ergonomic and safety value of "drop at end of scope" without needing anything like a borrow checker, since scopes here are already lexical/block-based. Note this is opt-in *per variable* via the annotation even within `auto` mode — unannotated values in an `auto`-mode build simply keep leaking until Stage 3 broadens coverage, which is fine: `auto` mode is defined as "the compiler frees what it can prove is safe to free," not "nothing ever leaks."
- **Stage 3 — a `@owned`/linear-value annotation with last-use liveness analysis. (`auto` mode, full version)** Closer to Rust in spirit than Stage 2: mark a value as single-owner, and have the compiler free it right after its statically-determined *last use* — not at block-exit (which can be too late for a long block, or express the wrong granularity), but exactly where data flow says it's no longer needed. Natural fit for functional/pipeline-style code, where each stage consumes its input and produces a new output (e.g. `function transform(/** @owned */ input) { const out = input.map(...); return out }` — the compiler frees `input` right after the `.map()` line, with no explicit free call needed anywhere). Needs a liveness analysis (a real, well-understood, bounded compiler pass — nowhere near a full borrow checker, but a genuine step up from Stage 2's block-exit model) plus the same escape check as Stage 2, applied at the last-use point instead of the block boundary.

**Sequencing across modes**: `manual` mode (Stage 1) is already done and stays the default — no work needed there beyond what's shipped. Of the two *not-started* modes, `gc` is the next one to build: it's a small, low-risk, high-leverage change (allocator swap + link flag + the `-mm` flag plumbing itself) and directly unblocks the HTTP server's leak problem, the most concrete real-world case this project has today for needing any of this. `auto` mode should come last, and only once Stage 2's escape check has been built and exercised — getting the escape analysis wrong is a correctness bug (use-after-free), not just a missed optimization, so it carries real risk that `gc` mode structurally cannot: a bug in `gc` mode's implementation degrades to "delayed free," never to memory corruption.

## Open questions

- Exact `-mm` flag surface: is it purely a compiler flag (`klainmain -mm=gc file.ts`), or does it also need a matching source-level marker (e.g. a `STATUS.md`/package-level declared mode) so a file can't be accidentally compiled in the wrong mode for what it assumes? Leaning toward compiler-flag-only for now, since nothing in the language itself should need to know or care which mode it's built under — `Memory.free`'s legality is the only mode-sensitive surface, and that's enforced at compile time regardless of how the mode was selected.
- Whether `gc` mode should be the eventual *default* once built and proven out (flipping away from `manual`), given it's strictly safer for the long-running-process case this project is aiming at. Not committed — revisit once `gc` mode actually exists and has some real mileage on it (e.g. via the HTTP server load-testing this project already does for other features).
- Exact escape-check rules for Stage 2 (`@free`/`auto` mode) — sketched above, not fully specified against every AST shape (e.g. conditional returns, nested closures).
- Whether `auto` mode's Stage 2/3 annotations should share syntax with any future Rust-inspired ownership work, or whether that's over-thinking a feature that doesn't exist yet.
