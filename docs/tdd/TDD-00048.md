# TDD-00048: WebAssembly target (`wasm32-unknown-wasi`)

- **Status**: Not Started
- **Date**: 2026-08-10
- **Notes**: Not a queued priority — reference/feasibility document. Shares its root blocker (no build-host/compile-target distinction anywhere in this compiler) with [TDD-00020](TDD-00020.md); `-mm=gc` and the `ucontext`-based fiber scheduler have no real wasm equivalent at all

## Context

Not previously mentioned anywhere in `docs/status/` or the roadmap — raised directly by a request to be educated on feasibility, not because it was already a queued priority. Written up here so the shape of the work is on record and can be weighed against the rest of the backlog with real information, the same reference-document role [TDD-00020](TDD-00020.md) (Windows) already plays for the lowest-priority end of this project's scope.

`main.go` never passes `-target` to clang, and the emitted `.ll` never sets a `target triple`/`target datalayout` line — clang's default is always "compile for whatever's running me." `runtime_core.go`'s own comment says outright this is deliberate, not an oversight: `errnoAccessor()` picks a symbol name based on `runtime.GOOS` — "the host this compiler itself is running on (and will therefore also be clang'ing on — this project doesn't cross-compile today)." A WebAssembly target is a cross-compile target by definition (no dev machine *runs* wasm as its native OS), so it inherits every open question [TDD-00020](TDD-00020.md) already scoped for Windows cross-compiling, plus several WASI-specific ones with no real analog there.

## Design

### Two unrelated things get conflated under "WebAssembly support" — this document scopes only the first

1. **`wasm32-unknown-wasi`**: a standalone binary run by a WASI runtime (`wasmtime`, `wasmedge`, `wasmer`) or embedded in server-side/edge platforms that speak WASI — closest in spirit to what this project already does (compile to a binary, run it), just a sandboxed, capability-based target instead of the host's native one.
2. **Browser (`wasm32-unknown-emscripten` or similar)**: no filesystem, no real sockets, execution driven entirely by a hosting JS page, blocking-looking code needs Asyncify or a JS-side event-loop bridge. A materially bigger, browser-specific lift with its own toolchain (Emscripten, not `wasi-sdk`) and its own JS-interop design questions.

**Recommended scope for this TDD and any V1: option 1 (WASI) only.** It's the one that could plausibly serve this project's own stated priorities (per the project's own instructions: CLI tools, Docker microservices) — a WASI binary is a portable, sandboxed CLI artifact, conceptually adjacent to a static Linux binary in a scratch container. The browser target has no connection to those priorities and would need its own separate TDD if ever genuinely wanted; not designed here.

### The structural blocker underneath every individual gap below: no target/host distinction exists anywhere in this compiler

This is the same root cause [TDD-00020](TDD-00020.md) hit for Windows, generalized: every `runtime.GOOS`/`runtime.GOARCH` check in `codegen/llvm` (macOS `arc4random()` vs. portable `rand()` in `emit_call_math.go`, `__error` vs. `__errno_location` in `runtime_core.go`, Darwin-specific clock IDs and `sockaddr`/`SOL_SOCKET` constants across `runtime_http.go`/`emit_os.go`/`runtime_fs.go`/`runtime_websocket_client.go`) reads **the Go compiler's own build host** — i.e. whichever of the two dev machines happens to be running `klainmain` — and bakes that choice into the emitted IR text at Go-compile-time, not at codegen-invocation-time. Build host and compile target have been the same machine for the entire life of this project so far.

A wasm target makes that assumption visibly wrong for the first time: `klainmain` still runs natively (Linux or macOS), but must emit IR for a third, unrelated platform. Concretely, every one of those `runtime.GOOS` switches needs to become a runtime decision (an actual compiler flag, e.g. `-target-os=wasi`, read at `main.go`'s flag-parsing time and threaded into `codegen/llvm`) rather than a Go `switch runtime.GOOS` baked in at the point this compiler's own source was built — otherwise a wasm build compiled *on* Darwin would silently emit `arc4random()`/`__error` calls into IR meant for a WASI target that has neither. **This is not wasm-specific engineering** — it's the same foundational rework any real cross-compile target needs (Windows cross-compile, per [TDD-00020](TDD-00020.md), needs an equivalent third `runtime.GOOS`-shaped branch that also can't actually be driven by Go's own `runtime.GOOS` once compiling *on* macOS/Linux *for* Windows) — but wasm is what surfaces it as a hard blocker rather than a latent one, since a WASI build has essentially none of the same syscalls/symbols as either Linux or Darwin to fall back on by accident.

**Recommended**: if either this or [TDD-00020](TDD-00020.md) is ever picked up first, build the target-flag plumbing (a real `-target-os`/`-target-triple` value threaded through `codegen/llvm`, replacing every `runtime.GOOS` codegen-time branch with a runtime lookup against it) as its own shared, reusable piece rather than wasm- or Windows-specific — both documents would otherwise end up separately reinventing the identical mechanism.

### Toolchain: `wasi-sdk`

`wasi-sdk` bundles a clang already configured for `wasm32-wasip1`/`wasm32-wasip2` plus `wasi-libc` (a real, if partial, POSIX-shaped libc — enough `stdio.h`/`stdlib.h`/`string.h`/`math.h` to cover `runtime_core.go`'s baseline). Installable on both dev machines (Homebrew/apt-adjacent packaging exists); a new per-machine dependency exactly like `bdw-gc` already is for `-mm=gc` (`gclocate.go`), not a new *class* of problem for this project's build story. `main.go`'s `clangArgs` assembly would need `--target=wasm32-wasip1 --sysroot=<wasi-sdk path>` (or invoke `wasi-sdk`'s own `clang` wrapper directly) gated behind the new target flag from the previous section.

### Runtime surface audit — what's portable as-is vs. what has no WASI equivalent

| Subsystem | Current implementation | WASI status |
|---|---|---|
| Arithmetic, control flow, strings, arrays, objects, closures (non-async), classes, JSON | Plain LLVM IR — `malloc`/`realloc`/`memcpy`/pointer arithmetic, no OS syscalls | Portable as-is once the target-triple plumbing exists — this is the bulk of the ~88%-covered core language surface (`docs/status/README.md`) and doesn't touch any subsystem below |
| `malloc`/`free`/`strlen`/`memcpy`/`printf`/math (`runtime_core.go`) | Plain C stdlib | `wasi-libc` implements this baseline; expected close to free, not yet verified |
| `Math.random()` (`emit_call_math.go`) | `arc4random()` (BSD/Darwin) or portable `rand()`/`srand()`/`time()` fallback | The portable fallback branch already exists and is exactly what a WASI build needs — no new code, just needs the target-flag plumbing above to select it instead of the Darwin/BSD branch when building *on* macOS *for* wasm |
| `errno` (`runtime_core.go`'s `errnoAccessor()`) | `__errno_location`/`__error`, host-`runtime.GOOS`-selected | `wasi-libc` has its own `errno` handling; needs a third case, same shape as the target-flag rework above, not yet confirmed against `wasi-libc`'s actual symbol |
| `try`/`catch`/`throw` (`setjmp`/`longjmp`, `runtime_exceptions.go`) | POSIX `setjmp.h` | Present in `wasi-libc`, but wasm's own structured control flow isn't a linear native stack — cross-toolchain reports of `setjmp`/`longjmp`-over-wasm correctness gaps exist; needs direct empirical verification against whatever `wasi-sdk` version is used, the same "don't trust the header exists, prototype it" discipline [TDD-00019](TDD-00019.md) applied to `sigaction`'s struct layout. **Also needs the [TDD-00047](TDD-00047.md) finding folded in if ever combined with Workers**: `@__kml_thrown`/`@__kml_jmp_stk`/`@__kml_jmp_top` are process-wide globals already flagged there as a threading blocker — moot for wasm specifically since wasm threads aren't in this document's scope either, but worth remembering these two documents share a dependency if both are ever picked up |
| `-mm=gc` (Boehm GC, `gclocate.go`) | Conservative *native call stack* scanning | **No real equivalent** — wasm's linear-memory execution model doesn't expose an inspectable native call stack to a program running inside it at all. This isn't "Boehm needs a wasm port," it's "conservative stack-scanning GC's core assumption doesn't hold on this target." `-mm=gc` is very likely permanently out of scope for a WASI build, not just unported — `manual` mode only, and that should be stated as a hard, documented constraint of the target rather than a temporary gap |
| Event loop / fiber scheduler (`getcontext`/`makecontext`/`swapcontext`, `runtime_http.go`/`emit_http.go`/`runtime_fetch.go`/`emit_websocket.go`) | POSIX `ucontext.h` | **No equivalent exists in WASI at all** — not unported, structurally absent, the same class of gap [TDD-00020](TDD-00020.md) found for `ucontext.h` on Windows (which at least has the Fibers API as a real substitute; wasm has nothing analogous, since a wasm module can't allocate and switch to a second execution stack the way a native process can). Removes `async`/`await` suspension, `http.listen`'s per-connection concurrency, and non-blocking `fetch` — i.e. most of what [TDD-00006](TDD-00006.md) built. Emscripten's Asyncify (a whole-module post-`clang` bytecode transform via `wasm-opt`) is the closest real answer, but it's a new build-pipeline stage with real performance cost, not a drop-in library swap — a genuine decision, not a given, and likely out of scope for a V1 |
| `fetch`/`URL`/`URLSearchParams` (`runtime_fetch.go`, `runtime_url.go`) | libcurl | No `wasm32-wasi` libcurl build in the toolchains this project would realistically use. WASI's own emerging sockets story (`wasi-sockets`, part of the still-unstable Preview 2/3 component model) is a different, non-libcurl-shaped API — would need a from-scratch client built directly against it, a real standalone project, not a link-flag change. Out of scope for a V1 |
| `select()`-based multiplexing (backs the event loop above) | POSIX `select()` over socket fds | Moot without the fiber scheduler it serves; `wasi-sockets` (still unstable) would need its own polling story regardless, unrelated to POSIX `select()` |
| `pthread`/`Worker` ([TDD-00047](TDD-00047.md)) | Not built at all yet, for either target | wasm threads are a separate, still-inconsistently-supported proposal (shared linear memory + atomics, browser/runtime support varies) — moot for a WASI V1 either way |
| `fs.*` (`runtime_fs.go`) | POSIX `dirent.h`/paths, free-form path access | `wasi-libc` implements a real POSIX-shaped subset, but WASI's filesystem model is capability-based (a program can only see directories explicitly "preopened" for it by the host runtime at launch, e.g. `wasmtime run --dir=.`) — a structurally different access model from a native program's free-form path access, not just a portability shim. Needs real design work on what a preopened-directory story looks like for this project's `fs` API, not assumed to be drop-in even though the underlying libc calls exist |
| `--static` (`main.go:27-29`) | Already Linux-only (macOS ships no static libc) | Moot — WASI binaries are inherently statically linked (no dynamic linking model in the base spec), so the flag's entire reason for existing doesn't apply to this target either way |

### What a genuinely useful, honestly-scoped V1 looks like

Given the audit above, a real V1 is closer to **"compile pure TypeScript logic plus basic preopened-directory file I/O to a portable sandboxed binary — `manual` mode only, no networking, no `async`/`await` suspension beyond today's already-synchronous stand-in behavior"** than to full parity with the native targets. That's a genuinely shippable, smaller thing — not the same project running somewhere else — and matches this project's own recurring pattern of narrow, honestly-scoped V1s (RegExp's `u`/`y`/`d`-flag exclusions, `symbol` V1's scope) rather than blocking on full parity before shipping anything.

## Open questions

- Is a WASI-sandboxed binary actually useful for this project's stated CLI-tool/microservice direction, or is this purely a "because it's there" exploration? Worth answering honestly before investing in the target/host rework — that single piece of foundational work has zero payoff for the two platforms already supported, and only pays for itself if wasm (or some other future cross-compile target, e.g. [TDD-00020](TDD-00020.md)'s Windows) is genuinely wanted.
- Does the target/host rework get built once, generically, and shared between this document and [TDD-00020](TDD-00020.md), or does whichever of the two is picked up first just build a narrower, target-specific version? Recommend the shared version if there's any real chance both are ever wanted — building it twice would be pure duplicated effort solving the identical problem.
- Does a V1 explicitly ship as `manual`-mode-only, synchronous-only, no-networking from day one (recommended — see "What a genuinely useful V1 looks like" above), or is that considered too narrow to be worth shipping at all? Not decided.
- `fs.*`'s preopened-directory model: does this project's `fs` API surface a "which directories were preopened" concept to user code, or does it just silently fail/throw on any path outside what the host runtime granted? Real design work, not scoped here.
- Sequencing against [TDD-00047](TDD-00047.md) (Workers) and [TDD-00020](TDD-00020.md) (Windows): all three are large and independent of each other technically, but [TDD-00047](TDD-00047.md) and this document both touch the exception-state globals, and this document and [TDD-00020](TDD-00020.md) both need the target/host rework — worth deciding a real order rather than picking whichever seems most exciting in the moment, given the shared-infrastructure overlap noted above.
- Browser (non-WASI) wasm target: deliberately out of scope for this document — see Design section. Worth a TDD of its own only if a real browser-deployment use case shows up; nothing today points at one.
