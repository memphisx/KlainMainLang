# ADR-00099: `GC_set_handle_fork(1)` for `-mm=gc` + `http.listen` clustering — fixed one real crash, one residual hang remains unresolved despite extensive investigation

- **Relations**: Extends [ADR-00097](ADR-00097.md) (manual-mode clustering), [ADR-00098](ADR-00098.md); Implements TDD-00025's `-mm=gc` follow-on (partially — see Status). Extended by [ADR-00101](ADR-00101.md), which root-caused and fixed the residual hang left open here.
- **Date**: 2026-08-04

## Context

TDD-00025 deferred `-mm=gc` support for `http.listen({ workers: N })` clustering as a follow-on, since Boehm's collector needs explicit handling to behave correctly across `fork()`. This ADR covers that follow-on work, including a second, much deeper investigation pass explicitly requested after an initial report of "found one real fix, one issue remains unresolved" — the user asked for the root cause to be found, not deferred, so this ADR documents an unusually large number of hypotheses tested and ruled out.

## Investigation

### The real, fixed bug: wrong Boehm fork-handling mechanism

The TDD's own sketch (manually registering `pthread_atfork(GC_atfork_prepare, GC_atfork_parent, GC_atfork_child)`) turned out to be the wrong mechanism. Reading Boehm's actual installed header (`/usr/include/gc/gc.h:494-517`) directly: those three functions are for **manual** invocation around one specific `fork()` call site, paired with `GC_set_handle_fork(-1)` — a fallback for platforms where automatic registration might be unavailable. The documented normal path for "I'm going to `fork()` and keep calling GC functions in the child" (exactly `__kml_http_cluster_fork`'s case) is a single call: `GC_set_handle_fork(1)` before `GC_INIT()`.

Confirmed this fix is real and necessary: a minimal standalone C reproduction (fork() 3 times, allocate under GC, link `-lcurl` to match `http.listen`'s always-on transitive `libcurl`→GnuTLS→`libp11-kit` dependency chain) reproduced Boehm's `"Exclusion ranges overlap"` abort 20/20 times without this fix, 0/20+ times with it.

### Two real test-harness bugs found while investigating further

1. A Go `testing` package behavior (not introduced by this work, but repeatedly corrupted this investigation's own results until identified): a test **timeout** (`panic: test timed out`) bypasses `t.Cleanup` entirely. A hung test run's spawned cluster workers were never killed — they kept running, still bound to the test's hardcoded port, silently answering every *subsequent* test run for the rest of the session (including completely unrelated runs) instead of that run's own freshly-compiled binary. This produced many misleading, contradictory results before being identified, including one entire "clean" 100-iteration run that was actually just repeatedly hitting one stale leftover process the whole time.
2. Even without a timeout, `syscall.Kill(-pgid, ...)` + `cmd.Wait()` in cleanup only confirms the *original* process is reaped, not that a forked worker sibling has actually released the listening socket yet. Fixed with a `waitPortFree` helper that polls until the port is genuinely refused before returning cleanup, used by all cluster-server test helpers (`tests/http_test.go`).

Both are real, kept fixes, independent of whether the underlying hang gets resolved.

### The residual hang: exhaustive investigation, root cause not found

`TestE2EHTTPListenClusteringGCModeMultipleWorkerPIDs` still fails intermittently — roughly 1 in 40 to 1 in 150 iterations (20 concurrent Go `http.Get` requests against a 3-worker `-mm=gc` cluster), **confirmed on fully clean process/port state each time** (a rigorous "no stale process anywhere on the box" check immediately before every verification run, after the harness bugs above made this necessary).

**Symptom, precisely characterized via kernel-level `strace` evidence** (`trace=read,write,close,select,pselect6,accept,accept4,fcntl`, immune to any application-level artifacts): a worker's connection fd receives a complete 95-byte HTTP GET request in exactly one `read()` call, then — instead of proceeding to parse and respond — immediately issues a second `read()` on the same fd with an arithmetically-inconsistent byte-count argument (`7896` where the read-loop's own capacity/already-read-bytes bookkeeping should produce `8096`), gets `EAGAIN`, yields, and is never resumed (no more data is ever coming — the client already sent everything and is waiting for a response that will never arrive). No `accept()`/`close()` occurs on that fd between the two reads, ruling out fd-number reuse by a different connection.

**Hypotheses tested and ruled out, each with direct empirical evidence, not just reasoning:**

| Hypothesis | Test | Result |
|---|---|---|
| `SIGPIPE` default disposition killing a worker mid-write | `LD_PRELOAD`-injected `signal(SIGPIPE, SIG_IGN)` | Hang still occurred |
| Boehm parallel-mark background threads racing fork() | Checked `/proc/<pid>/status` `Threads:` count for all 3 workers, idle and under 30-connection load | Always `1` — this build never spawns marker threads |
| `@__kml_conn_data` `realloc()`-driven growth exposing a residual ADR-00098-class staleness | Pre-sized initial capacity to 64 (`>` the test's 20 connections, so growth never triggers) | Hang still occurred |
| Fiber stack (`fiberStackBytes`, was 64KB, itself `GC_malloc`'d) too small for GC mode's deeper call stacks (Boehm's own mark/sweep running on that same stack mid-fiber) | Bumped to 1MB, verified via repeated large-`-count` batches | **Real, kept improvement** (a 64KB heap-allocated stack for a GC-tracked root is a legitimate latent risk regardless), but **did not eliminate the hang** on its own — confirmed via a clean, non-strace, freshly-verified-clean-environment run that still failed at `-count=100` |
| `GC_set_handle_fork(1)`'s automatic `pthread_atfork` registration having a gap | Switched to the documented manual alternative: `GC_set_handle_fork(-1)` + explicit `GC_atfork_prepare()`/`GC_atfork_parent()`/`GC_atfork_child()` wired directly around `__kml_http_cluster_fork`'s `fork()` call | Hang still occurred — **both mechanisms fail equally**, ruling out "which Boehm fork-handling API" as the variable |
| General timing-sensitive race, not GC-specific — manual mode just never hits the window because it's faster | Ran the *identical* churn workload (100,000-iteration string-concat handler) through `manual`-mode clustering, `-count=100` | **100/100 clean, 25.6s total** — proves this is genuinely GC-mode-specific, not exposed by slowness alone |
| `libp11-kit`/GnuTLS's own allocator having a fork-safety bug, surfaced because `gcshim.c` makes `GC_malloc` the *only* malloc process-wide (forcing third-party libraries' allocations through a conservative collector they weren't necessarily designed against) | Isolated minimal C repro: `fork()` 3x + GC allocation churn + `-lcurl` linked, **no HTTP/fiber/event-loop code at all**, run 300 times | 300/300 genuinely clean (2 apparent failures were confirmed to be the test script's own file-flush-timing artifact — the full "ALL DONE" output was actually present in both cases on manual inspection) — **rules out a pure library-level incompatibility**; the bug requires the full fiber/`select()`/non-blocking-I/O machinery to manifest |

Also attempted, inconclusive due to environment/tooling limits rather than a negative result: a custom `LD_PRELOAD` signal handler (`SIGSEGV`/`SIGABRT`/`SIGBUS`/`SIGILL` + `backtrace()`) never fired during any caught failure; `gdb --batch --ex 'set follow-fork-mode child'` could not cleanly observe the full 3-process fan-out due to all-stop semantics halting the parent when following into a child, and `ptrace_scope=1` on this machine blocks attaching to an already-running non-child process without root.

**Net position**: the bug is real, confirmed GC-mode-and-clustering-specific (not present in manual mode under an identical workload, not present in GC mode without clustering, not reproducible in a fork+GC+curl-linked scenario without the full event loop), low-frequency, and requires the complete `http.listen` fiber/non-blocking-I/O/`select()` machinery combined with `fork()` and Boehm GC to manifest — none of the six specific mechanisms tested above (SIGPIPE, marker threads, connection-array growth, fiber stack size, choice of Boehm fork-handling API, pure library incompatibility) is the root cause. Further progress likely needs tooling not available in this environment: an ASAN/Valgrind-instrumented build of the full dependency chain (this compiler's own runtime + Boehm + libcurl + GnuTLS + libp11-kit), or kernel-level memory-write watchpoints, to catch the actual moment the read-loop's buffer-capacity bookkeeping goes wrong.

## Decision

- **Ship `GC_set_handle_fork(1)`** (`codegen/llvm/gcsrc/gcshim.c`) — real, verified fix for a 100%-reproducible crash.
- **Ship `fiberStackBytes` = 1MB** (was 64KB, `codegen/llvm/runtime_http.go`) — a legitimate, defensible improvement (a small `GC_malloc`'d block serving as a scanned GC root running the collector's own mark/sweep on it is inherently risky) even though it did not fully resolve the residual hang. Applied unconditionally (both memory modes), not gated to `-mm=gc` only, to avoid a mode-specific footgun.
- **Do not mark `-mm=gc` clustering as fully supported.** TDD-00025's status stays "Partially Implemented": `manual` mode is solid and thoroughly verified (ADR-00097/ADR-00098) and is what's documented as recommended; `-mm=gc` mode has two real improvements from this ADR but a confirmed, unresolved, low-frequency hang under concurrent load remains, and it should not be recommended for production use.
- Keep `TestE2EHTTPListenClusteringGCModeMultipleWorkerPIDs` and the `waitPortFree`/`startHTTPClusterServerGC` harness fixes — correct and valuable regardless of the open bug (the harness fixes benefit every cluster test, not just GC mode).

## Implementation notes

Files touched: `codegen/llvm/gcsrc/gcshim.c` (`GC_set_handle_fork(1)` + doc comment), `codegen/llvm/runtime_http.go` (`fiberStackBytes` named constant replacing four hardcoded `65536` literals, now `1048576`), `tests/http_test.go` (`waitPortFree`, `startHTTPClusterServerGC`, `TestE2EHTTPListenClusteringGCModeMultipleWorkerPIDs`).

## Side effects discovered

The two test-harness bugs described above — both fixed, documented in detail since they're exactly the kind of thing that could silently corrupt *other* future test investigations on this codebase if not written down.

## Verification

- `go build -o klainmain .`, `go test ./...` — clean, no regressions in the standard (non-`-count`) suite, confirmed after every change made in this investigation (including the ones later reverted for not helping).
- The `GC_set_handle_fork(1)` crash fix: verified via a minimal standalone repro (20/20 failures → 0/20+) and the full compiler's own output.
- The `fiberStackBytes` change: verified `go test ./tests/ -run 'TestE2E.*GCMode'` still passes; does not regress anything, but is not sufficient alone to close the residual hang (verified failing again at `-count=100` on a freshly-confirmed-clean environment after this change alone).
- The residual hang was **not resolved** despite the six ruled-out hypotheses above, each independently verified via direct reproduction (not just code reading) with a fully clean environment confirmed immediately before each run. Explicitly not claimed as fixed.
