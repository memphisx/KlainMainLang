# ADR-00106: Binary-safe `http.listen()` request/response bodies

- **Relations**: Implements [TDD-00026](../tdd/TDD-00026.md)
- **Date**: 2026-08-06

## Context

[TDD-00026](../tdd/TDD-00026.md) scoped this while investigating whether `tools/httpbin-lite/main.go` (a Go fixture server `make examples` starts, ADR-00096) could be rewritten in KlainMainLang using its own `http.listen`. Every route except `/bytes/{n}` was already expressible; that one route's whole point is a response body with a guaranteed embedded null byte. `Res.body` is a plain string, and `codegen/llvm/runtime_http.go`'s response writer computed how many bytes to `write()` via `strlen(body)`, not a carried length — a null byte in that field truncated the response before any bytes past it reached the socket. The gap was bidirectional: `req.body: string` was already `Content-Length`-aware on the *read* side (ADR-00072), but once exposed to TS code as a plain string, every ordinary string operation on it reverted to `strlen` semantics.

## Investigation

Confirmed the fix should mirror `Response.arrayBuffer()`'s own precedent (ADR-00094) directly: `ArrayBuffer`/TypedArrays (TDD-00018) already exist as this compiler's answer to "a byte sequence that survives an embedded null," and `Response.arrayBuffer()` already proves the pattern of adding a binary accessor *alongside* the existing string-based one. Read `codegen/llvm/emit_fetch.go`'s `emitResponseArrayBuffer` (wraps an already-buffered body pointer + a `bodyLength` field into an `ArrayBuffer` header, no copy) and confirmed `RequestType()`/`buildHTTPDispatcher` (`codegen/llvm/types.go`/`emit_http.go`) already compute the real `Content-Length`-derived byte count internally (`contentLenFinal`) but never expose it — exactly the same shape.

Traced `__kml_http_send_response` (`codegen/llvm/runtime_http.go`) and found a second, deeper problem beyond `Content-Length`'s own wrong value: the entire response (status line + headers + body) is built via one `sprintf` call, with the body passed through a `%s` conversion. `sprintf`'s `%s` is itself NUL-terminated-aware — even after fixing `Content-Length` to carry the real byte count, folding a binary body into that same `%s` would still truncate it at its first embedded null byte. Fixing the header's claimed length alone would not have been sufficient; the write mechanism itself needed to change to an explicit-length `write()` for the body, separate from the header block's own (still string-based, and correctly so — HTTP headers are text) `sprintf`.

## Decision

Two additions, following `Response.arrayBuffer()`'s established shape directly:

- **`RequestType()`** (`types.go`) gains a `bodyLength: i64` hidden field (mirroring `ResponseType()`'s own `bodyLength`) plus a new `IsRequest` flag (mirroring `IsResponse`/`IsURL`) so method-call dispatch can recognize a `Request` receiver. `buildHTTPDispatcher` stores the already-computed `contentLenFinal` into it.
- **`req.bodyBytes(): ArrayBuffer`** (`emit_http.go`'s `emitRequestBodyBytes`, dispatched from `emit_call.go` on `IsRequest` receivers) wraps `body`+`bodyLength` into an `ArrayBuffer` header exactly like `emitResponseArrayBuffer` does — no copy, no new accumulation logic, since the real byte count was already being tracked internally.
- **`Res`'s optional `bodyBytes: ArrayBuffer` field**: `emitHTTPListen` validates its type (`IsArrayBuffer`) the same structural way `headers` is validated. `buildHTTPDispatcher`'s response-writing tail resolves the actual bytes to write as: if `bodyBytes` is present at the type level *and* non-null at runtime, use its real `byteLength`+data pointer; otherwise fall back to `body`'s own `strlen` — resolving the TDD's "which field wins" open question as "bodyBytes wins outright when both are set," matching `headers`' own low-ceremony "present vs. absent, checked at the call site's static return type, with a defensive runtime null check" convention exactly (an omitted `bodyBytes` field costs zero extra branches; a present-but-null one behaves exactly like today, matching how absent `headers` already no-ops rather than erroring).
- **`__kml_http_send_response`**'s signature changed to take an explicit `i64 %bodylen` parameter instead of computing it via internal `strlen(body)`, and its body write changed to a second, explicit-length `write()` call instead of folding the body into the header `sprintf`'s own `%s` — the actual fix for the deeper problem found in Investigation. This function has exactly one call site (`buildHTTPDispatcher`), so this was a plain signature change, not a new parallel function.
- `new Array<T>(n)`-style dynamic sizing has no equivalent gap here — `bodyLength` is always populated by the read loop itself, never left in an unset/zero-by-default state the way TDD-00029's own dynamic-array-of-arrays edge case was.

`req.bodyBytes()` shipped in the same pass as the response-side fix (not deferred, despite the TDD leaving that open) — no extra design work was needed once the `bodyLength` field existed, and the `TestE2EHTTPListenBodyBytesRoundTripSurvivesEmbeddedNull` test below needed both sides anyway to prove the fix end to end. `fetch`'s own client-side request bodies (`fetch(url, { body: someArrayBuffer })`) remain explicitly out of scope, as scoped by the TDD.

## Implementation notes

Files touched:
- `codegen/llvm/types.go`: `RequestType()` gained `bodyLength: i64` and `IsRequest = true`; new `IsRequest` field doc comment.
- `codegen/llvm/emit_http.go`: `emitHTTPListen` validates an optional `bodyBytes` field's type; `buildHTTPDispatcher` stores `contentLenFinal` into the request's `bodyLength` field and resolves `bodyDataRef`/`bodyLenRef` (bodyBytes-vs-body, with the runtime null check) before calling `__kml_http_send_response`; new `emitRequestBodyBytes`.
- `codegen/llvm/emit_call.go`: new dispatch case routing `req.bodyBytes()` (property name `"bodyBytes"` on an `IsRequest`-flagged receiver) to `emitRequestBodyBytes`.
- `codegen/llvm/runtime_http.go`: `__kml_http_send_response`'s signature and body changed as described in Decision; doc comments on both the function itself and `ensureHTTPRuntime`'s overview updated to match.

## Side effects discovered

None beyond the `sprintf %s` truncation issue itself, which Investigation already found and Decision already fixes — that was the actual bug, not a separate side effect.

## Verification

- `go build ./...`, `go vet ./...`, and the full `go test ./...` suite pass (Linux x86-64 dev box), including every pre-existing `http.listen` test (headers, query string, request body, clustering, `http.close()`, ...) unchanged.
- New tests in `tests/http_test.go`: `TestE2EHTTPListenBodyBytesRoundTripSurvivesEmbeddedNull` (an 8-byte payload with two embedded null bytes, posted and echoed straight back through `req.bodyBytes()`/`Res.bodyBytes`, compared byte-for-byte against the original — including asserting `Content-Length` matches the real byte count), `TestE2EHTTPListenBodyBytesWinsOverBodyField` (a much-longer `body` string is ignored once `bodyBytes` is set), `TestE2EHTTPListenBodyBytesByteLength` (`.byteLength` reflects the real count for a payload containing a null byte), `TestE2EHTTPListenWrongBodyBytesFieldTypeRejected` (a non-`ArrayBuffer` `bodyBytes` field is a compile error).
- New example: `examples/http/http_binary_body.ts`. Manually verified end to end (not just via the Go test harness) by running the compiled binary and round-tripping `printf 'AB\x00CD' | curl --data-binary @- http://localhost:8081/echo | xxd` — output was `4142 0043 44` (`AB\x00CD`), confirming the embedded null survives a real client round trip, not just the Go test harness's own HTTP client.
