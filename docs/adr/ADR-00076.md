# ADR-00076: URL / URLSearchParams

- **Date**: 2026-07-29

## Context

Picked up as the next roadmap item after the codegen/parser file-splitting
housekeeping ([ADR-00075](ADR-00075.md)): `STATUS.md`'s backlog listed
`URL`/`URLSearchParams` as the cheapest unblocked item that still serves the
REST-API-client priority (parsing/building request URLs alongside
`fetch`). Chosen over the other low-effort candidates
(`TextEncoder`/`TextDecoder`, `structuredClone`, `setImmediate`) for exactly
that reason.

## Investigation

- Considered hand-rolling a URL parser (the backlog's original assumption:
  "C string parsing, no external dependency needed") versus reusing
  libcurl, already linked into every binary for `fetch()`
  ([ADR-00021](ADR-00021.md)). libcurl ships a purpose-built URL API
  (`curl/urlapi.h`: `curl_url()`/`curl_url_set()`/`curl_url_get()`/
  `curl_url_cleanup()`) — read directly off this dev machine's SDK headers
  (`/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk/usr/include/curl/urlapi.h`),
  the same "verify against the real header, don't trust memory" standard
  every other libcurl constant in this codebase already follows
  ([ADR-00074](ADR-00074.md)). Using it avoids reimplementing IPv6-bracket
  hosts, punycode, percent-decoding edge cases, and other URL-parsing
  subtleties that are easy to get subtly wrong by hand — a strictly better
  outcome than the backlog's original "no dependency needed" framing
  assumed, since the dependency was already there.
- Read `types.go`'s `RequestType()` (`http.listen`'s `req` object) and
  found it already represents `req.query` as a plain `Map<string,string>`,
  built via `runtime_http.go`'s `ensureHTTPParseQuery`/
  `__kml_http_parse_query` (splits on `&`, then `=`, percent-decodes both
  sides via the existing `decodeURIComponent` machinery). This is the exact
  same problem `URLSearchParams` needs solved, so `emit_url.go` reuses
  `__kml_http_parse_query` directly for both `URL`'s own `.searchParams`
  field and `new URLSearchParams(str)`, rather than writing a second query-
  string parser. This also settled the design question of how
  `URLSearchParams` should behave on a repeated key: exactly like
  `req.query` already does (last value wins, single value per key) —
  consistent with an established precedent in this codebase, not a new
  scope-narrowing decision made in isolation.
- Read `emit_collections.go`'s `resolveMapOrSetForCall` (resolves a Map/Set-
  typed variable *or* an arbitrary expression like a struct field access to
  its heap pointer) and confirmed it already handles a Map-typed object
  field with no changes needed — `url.searchParams.get(...)` needed zero
  new dispatch code beyond `IsURLSearchParams`-gated `.toString()`/
  `.getAll()`.
- **Found and fixed a real, pre-existing crash while testing, unrelated to
  this feature's own code**: `console.log()` of any `ptr`-typed value that
  is genuinely `null` at runtime segfaults on this platform (confirmed with
  a plain `Map<string,string>` — `const m = new Map<string,string>();
  m.set("a","1"); console.log(m.get("z"))` crashes with SIGSEGV on its
  own, no `URL`/`URLSearchParams` involved). Root cause:
  `emitConsolePrintVal` (`emit_call_console.go`) passes a `ptr` argument to
  `printf`'s `%s` with no null check; glibc happens to print `"(null)"` for
  a `NULL` `%s` argument, but Darwin's libSystem printf has no such special
  case and calls the equivalent of `strlen(NULL)` internally, segfaulting.
  This was reachable before this feature ever existed (any `Map.get()`
  miss), just never exercised in an existing test — `URLSearchParams.get()`
  on a missing key hit the identical code path and is what actually
  surfaced it here.

## Decision

- `new URL(url)` — single-argument form only (no base-URL resolution),
  matching the same "narrow to a plain struct, no full class hierarchy"
  scoping `fetch(url, init)` already established for `Request`/`Headers`.
  Parses via `ensureCurlURL` (new `runtime_url.go`: declares `curl_url`/
  `curl_url_cleanup`/`curl_url_get`/`curl_url_set`) and returns a plain
  `IsObject` heap struct (`URLType()`, `types.go`) with fields `href`,
  `protocol`, `host`, `hostname`, `port`, `pathname`, `search`, `hash`,
  `origin`, `searchParams` — all ordinary field reads via the existing
  object machinery, matching `Response`'s own `status`/`ok`/`body` pattern.
  A URL part absent from the input (no port/query/fragment) reads back as
  `""`. A malformed URL (`curl_url_set` returns non-`CURLUE_OK`) throws a
  catchable `Error("Invalid URL")`, the same "surface a C-level failure as
  a KML exception" convention `ensureFsThrow`/`ensureHTTPThrow` already use.
- `new URLSearchParams()` / `new URLSearchParams(init)` — `init` tolerates
  a leading `?` (so passing a `URL`'s own `.search` straight through just
  works). Type-wise this **is** a `Map<string,string>` with an added
  `IsURLSearchParams` flag (`URLSearchParamsType()`, `types.go`): `get`/
  `set`/`has`/`delete`/`size`/`keys()`/`values()`/`entries()`/`forEach()`
  all come free from the existing Map dispatch (`emit_collections.go`),
  with `.toString()` (percent-encode back to a query string, reusing
  `encodeURIComponent`'s own runtime helper) and `.getAll()` (0 or 1
  elements) added specifically for `IsURLSearchParams` in `emitCall`,
  checked *before* the generic Map dispatch block.
- **Scope narrowing, not a bug**: single value per key (a repeated
  query-string key keeps only the last value) — `.getAll()` therefore never
  returns more than one element, and there's no true multi-value
  `.append()` (would need a different backing structure entirely to
  represent faithfully). Documented in `STATUS.md`'s URL table row, its
  Known Limitations table, and this feature's own example.
- No `URLPattern` (still ❌, unrelated scope).
- **Bug fix, bundled into this same piece of work**: `emitConsolePrintVal`'s
  `ptr` case now `select`s the interned string `"null"` when the value is
  actually a null pointer at runtime, before ever handing anything to
  `printf`. This fixes the crash for every `console.log` call site, not
  just `URLSearchParams`/`Map` — e.g. any future feature returning a
  possibly-null `ptr` gets this for free too.

## Implementation notes

- Files touched: `ast/nodes.go` (`NewURLExpression`, `NewURLSearchParamsExpression`),
  `parser/parser_literals.go` (`parseNew`'s dispatch + two new
  `parseNewURLBody`/`parseNewURLSearchParamsBody`), `codegen/llvm/types.go`
  (`IsURL`/`IsURLSearchParams` flags, `URLType()`/`URLSearchParamsType()`,
  and `ResolveTypeName` cases for `URL`/`URLSearchParams` type annotations),
  `codegen/llvm/emitter.go` (`usedCurlURL` flag), new
  `codegen/llvm/runtime_url.go` (`ensureCurlURL`), new
  `codegen/llvm/emit_url.go` (construction + `.toString()`/`.getAll()`),
  and one-line wiring into `emit_exprs.go`'s `emitExpr` dispatch,
  `emit_exprs_types.go`'s `inferExprType` (both the `NewURLExpression`/
  `NewURLSearchParamsExpression` cases and a `toString`/`getAll` case
  inside the existing `IsMap` property-type switch), `emit_exprs_vardecl.go`'s
  untyped-`const`/`let` inference switch, and `emit_call.go` (the
  `IsURLSearchParams`-gated dispatch block, placed immediately before the
  generic `IsMap || IsSet` block it falls through to).
- `emit_url.go`'s construction code deliberately does **not** call
  `curl_free()` on any of the strings `curl_url_get` returns — every part
  string is intentionally leaked (a handful of small allocations per
  `new URL(...)` call) rather than freed, the same "a short-lived CLI
  program's bounded per-call leak is a non-issue in the default `manual`
  memory-management mode" tradeoff `STATUS.md` already documents elsewhere
  (and moot under `-mm=gc`). This kept the implementation to straight-line
  Go-orchestrated IR emission with no conditional-free branches to get
  right per optional part.
- `curl_url_get`'s failure code doubles as "this part is simply absent"
  (no port/query/fragment) as well as genuine errors — `curlURLGetPart`
  (`emit_url.go`) treats any non-zero code as "absent," which is correct
  for this use (the one genuinely fatal case, a malformed URL, is already
  caught earlier by `curl_url_set`'s own return code).
- `emitStrBranch` (`emit_url.go`) is a small new local helper: the same
  alloca+store-in-each-branch+load-after-merge shape
  `emitConsoleCountMapEnsure`/`emitConditional` already establish elsewhere
  in this codebase, specialized to a `ptr` result since every URL part is
  a string. Reused seven times in this file (`protocol`'s presence-independent
  parts don't need it, but `hostname`/`port`/`host`/`pathname`/`search`/
  `hash`/`getAll`'s output pointer all do) rather than duplicating the
  branch/merge boilerplate inline each time.

## Side effects discovered

The `console.log`-crashes-on-null-`ptr` bug described above (Investigation
+ Decision) — fixed in this same piece of work, not deferred, since it
directly blocked testing this feature's own `.get()` on a missing key.

## Verification

- Manual smoke testing first (`/tmp/url_smoke.ts` and incremental
  isolation files) to bisect the initial segfault down to the
  `console.log`/null-`ptr` root cause described above, confirmed
  independently with a plain `Map<string,string>` before touching any
  `URL`-specific code.
- `tests/url_test.go`: 11 new E2E tests covering URL part extraction, a
  part absent from the input, `href` round-tripping, the invalid-URL throw
  path, `.searchParams` reads (present/absent keys), both
  `URLSearchParams` constructor forms (empty, from a query string, from a
  `URL`'s own `.search` with its leading `?`), `.set()`/`.delete()`,
  duplicate-key last-value-wins + `.getAll()`, `.toString()`'s percent-
  encoding, and the `Map.get()`-miss-prints-`"null"` regression test for
  the bundled bug fix.
- `examples/url/url.ts` added and run via `make examples`.
- `go build -o klainmain . && go vet ./... && go test ./...` (all green,
  ~163s) and `make examples` (65/65, up from 64 — the new `url.ts`) both
  passed on the final tree.
