# ADR-00850: `Number("0b…")` / `Number("0o…")` — binary and octal string prefixes

- **Relations**: Extends string `ToNumber` ([ADR-00545](ADR-00545.md) the hex/parseFloat split)
- **Date**: 2026-09-10

## Context

`Number("0b101")` and `Number("0o17")` returned `NaN`; JS's `ToNumber` accepts
`0b`/`0B` (binary) and `0o`/`0O` (octal) prefixes just as it accepts `0x` hex.
The `0x` form already worked because it rides C's `strtod`, which does not
recognize the binary/octal spellings. This is a shared path: string coercion
through `+x`, template interpolation, and arithmetic on a stringified value all
route through `__kml_to_number`, so all of them were wrong for these prefixes.

## Decision

`__kml_to_number` gains a prefix pre-check ahead of its `strtod` path: past
leading ASCII whitespace, a `0` followed by `b`/`B` or `o`/`O` parses the
remaining digits with `strtoll` at base 2 or 8 and requires the tail to be
whitespace-only (`"0b101x"` → `NaN`). A leading sign is deliberately *not*
accepted — `Number("-0b1")` is `NaN` in JS — because the check only fires on a
literal leading `0`; a signed or malformed input falls straight through to the
existing `strtod` path unchanged, so hex, decimals, `Infinity`, `""`→0, and junk
→`NaN` all behave exactly as before.

## Implementation notes

`runtime_core.go` (`ensureToNumber`, new `rdx_*` prefix blocks + `entry2`
fallthrough; `ensureStrtoll` pulled in). `parseInt`/`parseFloat` are untouched —
`parseFloat("0b1")` is `0` (prefix parse stops at `b`), which was already
correct.

## Verification

macOS (Apple Silicon M4): matches Node — `Number("0b101")` → 5, `Number("0o17")`
→ 15, `0B11`/`0O10` → 3/8, `"  0b101  "` (surrounding whitespace) → 5;
`Number("0b")`, `Number("0b2")`, `Number("-0b1")`, `Number("0b101x")` all `NaN`;
`0xff`/`42`/`3.14`/`""` unchanged. `TestE2EGlobalConversionFunctions` extended +
the expression/parseFloat suites green.
