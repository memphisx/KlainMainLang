# ADR-01195: `.finally`'s promise settles as the spec's thenFinally does

- **Relations**: `Extends ADR-00248`
- **Date**: 2026-09-28

## Context

`p.finally(f).catch(h)` ran `h` two microtasks earlier than Node: the
runner copied the source's settlement into the result as soon as `f`
returned.

## Investigation

The spec's thenFinally/catchFinally return `PromiseResolve(C,
onFinally()).then(() => value)` (or a thrower): the result promise is
resolved with that promise, so it settles after the `.then` reaction runs
(one microtask) and its adoption job runs (another).

## Decision

The finally branch stores the source's value/reason in the result and
settles it through `@__kml_promise_defer_settle(q, state, 2)`, a microtask
that re-queues itself once and then settles `q` (firing its reactions and
the unhandled-rejection bookkeeping). An `onFinally` returning a promise is
waited for (`@__kml_promise_finally_wait`): once it settles, the result
takes its rejection, or else the source's settlement, one microtask later.

## Implementation notes

`codegen/llvm/emit_promise_then.go` (`ensurePromiseDeferSettle`).

## Side effects discovered

- An `onFinally` that returns a promise was not waited for; now it is.

## Verification

Mac (Apple Silicon), against Node v24.19:
`TestE2EFinallySettlesAfterTwoTicks` (interleaved with a five-link `.then`
chain, an `onFinally` returning a delayed promise and one that rejects);
the `.finally` tests of the async, fetch, module-task and
reject-reason files.
