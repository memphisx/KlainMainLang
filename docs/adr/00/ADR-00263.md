# ADR-00263: `new Promise((resolve, reject) => …)` — the executor constructor

- **Relations**: `Implements TDD-00087`; builds on [ADR-00249](ADR-00249.md) (task promise struct), [ADR-00248](ADR-00248.md) (`.then` reactions), [ADR-00262](ADR-00262.md) (`Promise.resolve`/`.reject`)
- **Date**: 2026-08-20

## Context

The last missing core Promise API — the executor constructor, how a
callback/timer/event API is bridged into a promise. TDD-00087 has the design; this
records what shipped.

## Decision

`new Promise<T>(executor)` (intercepted in `emitNewExpression` on
`ClassName == "Promise"` → `emitNewPromise`):

- Allocate a pending task promise (`@__kml_task_alloc_promise`).
- Build `resolve`/`reject` as per-site closures capturing the promise: closure
  header `{ @__kml_promise_resolve_N, p }` with `p` passed as the callee env (the
  first argument by the closure ABI). `resolve_N(ptr p, T v)` stores `v` and
  settles fulfilled; `reject_N(ptr p, ptr err)` stores the error and settles
  rejected. Each guards on the promise's state field first, so only the **first**
  settle writes the value (a later resolve/reject is a no-op — the state guard in
  `__kml_promise_settle` alone isn't enough because the value store happens in the
  thunk).
- **`@__kml_promise_settle(ptr p, i64 state)`** — the missing bare-promise
  settle+wake+drain, factored from `__kml_task_finish`: set state, clear a parked
  waiter's `pendingProm` (so the scheduler poll resumes it), and
  `@__kml_promise_drain_reactions` (fire `.then` chains). First settle wins.
- Emit the executor with param hints `resolve: (T)=>void`, `reject: (Error)=>void`
  (so the unannotated arrow params get the right closure signatures) and invoke it
  immediately with the two closures.
- Typed `Promise<T>` (task); `T` from `new Promise<T>`, default `number`.

**Deferred resolution.** A `resolve` stashed into a `setTimeout(() => resolve(v))`
settles the promise only when the timer fires. The lightweight (no-fiber) await
path was extended into a loop that drains the microtask FIFO **and** fires the
next due timer (`@__kml_timer_fire_next`, a one-shot factored from
`__kml_timer_drain`) until the promise settles — so `await new Promise((res) =>
setTimeout(() => res(v), ms))` waits correctly. `__kml_timer_fire_next` is the
real timer step when the program uses timers, else a no-op stub. The may-suspend
(fiber) path already parks the awaiting task and the event loop fires the timer,
so that case worked unchanged.

## Consequences

- `new Promise((resolve, reject) => …)` works: synchronous resolve/reject,
  conditional settle, first-settle-wins, `.then`/`.catch`/`await`, and **deferred**
  resolution from a `setTimeout` callback (the wrap-a-timer pattern).
- **Boundary limitation (pre-existing, surfaced here):** returning a promise
  *across a function boundary* — `function f(): Promise<T> { return new Promise(...) }`
  or `async function f() { return new Promise(...) }` — does not work, because an
  async function does not flatten a returned promise and a plain function's
  `Promise<T>` return type is not tagged task-shaped. `return Promise.resolve(x)`
  from an async fn is likewise a pre-existing clang error. Direct use (bind to a
  variable / await / chain the `new Promise` expression itself) is the supported
  path; promise-return flattening is tracked separately.
- `resolve(aPromise)` stores the promise as the value rather than adopting its
  state (no thenable flattening) — V1 scope.
- The lightweight-await loop now drives timers, so a pure-`new Promise`+`setTimeout`
  program resolves without the full fiber event loop.
