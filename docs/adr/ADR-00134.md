# ADR-00134: True per-file module scope via mangled internal names

- **Relations**: Extends [ADR-00022](ADR-00022.md). Implements [TDD-00041](../tdd/TDD-00041.md)
- **Date**: 2026-08-09

## Context

[ADR-00022](ADR-00022.md) shipped named `import`/`export` with one flat, globally-unique namespace across every merged file — two unrelated files could not declare the same-named top-level function/interface/enum/etc. if both were reachable from the same entry file, and import aliasing (`import { a as b }`) was parsed but rejected outright as unsafe without real scope tracking. [TDD-00041](../tdd/TDD-00041.md) scoped a fix: give every file's top-level declarations a file-private mangled name, and rewrite every reference to one via a real scope-aware walk. This ADR is that implementation.

## Investigation

- Confirmed `codegen/llvm` could stay completely untouched, same as ADR-00022's own design: since renaming happens entirely inside `resolver/` before the merge step, `codegen/llvm` only ever sees an already-unique, already-correctly-bound AST — exactly what it already assumed.
- The real substance of the work is a scope-aware AST walker: a function parameter, block-scoped `let`/`const`, loop variable, `catch` parameter, or generic type parameter can all legally shadow a top-level name, and a reference inside that shadowed scope must not be rewritten. Audited `ast/nodes.go` (~77 node types) directly rather than assuming coverage from the language grammar alone, and confirmed `FunctionDeclaration`/`ClassDeclaration`/`InterfaceDeclaration`/`EnumDeclaration`/`TypeAliasDeclaration` never appear nested inside a block in this language (declarations are top-level only) — so the nested-statement walker (`rewriteStmt`) doesn't need cases for them at all, only the top-level dispatcher (`rewriteTopLevelStmt`) does.
- **Found a real bug during implementation, by testing against the existing example suite rather than trusting the design by inspection alone** (`make examples` initially reported `examples/json/json_methods.ts` and `examples/structured_clone/structured_clone.ts` failing with `clang` type-mismatch errors like `'%t294' defined with type 'ptr' but expected 'i64'`, on a plain single-file program with no imports at all). Root-caused via a minimal repro (`interface Point {...}; const points: Point[] = [...]`) plus a diff of the emitted IR against the pre-change compiler: `parser/parser_types.go`'s "Array suffix" handling (`parseTypeAnnotation`, ~line 182) encodes a named type followed by `[]` as a single flat string — `TypeAnnotation.Name = "Point[]"` — rather than via the `ElemType` field. A plain `lu[ta.Name]` lookup in the rename walker therefore never matched `"Point[]"` against the lookup table's `"Point"` key, silently leaving the reference unrenamed while the interface declaration itself *was* renamed to `Point__kml_mod0` — `codegen/llvm/emitter.go:504-510`'s own `resolveType` then failed its `e.interfaces[base]` lookup (interfaces are registered under the now-mangled name) and silently fell through to a default numeric type instead of erroring, producing a `ptr` value stored into an `i64`-typed array slot. Fixed by teaching `rewriteType` to strip trailing `"[]"` (repeated, for `Foo[][]`) before the lookup and reattach it after. This is exactly the kind of thing this project's own standing practice — fix bugs found during development rather than paper over them — exists for: found via the example suite, not via reading the type-annotation code, and fixed as part of this same piece of work rather than deferred.
- **Considered whether to only mangle on an actual detected collision** (TDD-00041's Design section's "shape B") vs. mangling every top-level declaration unconditionally (shape A). Went with shape A, as the TDD recommended: the same scope-aware walker is required either way, and always-mangle is the version that's genuinely "real per-file module scope" (a file's non-exported declarations are private *by construction*) rather than a namespace that happens to be unique today and could start colliding the moment an unrelated file is added to the build.
- **Re-examined the existing cross-file duplicate-name test** (`TestE2EImportDuplicateNameAcrossFilesRejected`) before assuming it should simply be deleted. Its actual scenario — `main.ts` importing `add` from *both* `math.ts` and `dup.ts` under the same local name, with no `as` — is a different, still-genuine conflict (two different files' exports bound to the same local identifier) that real ES modules also reject, distinct from "two unrelated files privately declaring the same name" (which TDD-00041 explicitly intends to allow). Kept this test (renamed to `TestE2EImportSameLocalNameFromTwoFilesWithoutAliasRejected` for clarity) and implemented the corresponding check explicitly in the import-lookup-building loop, rather than relying on the old global uniqueness check (removed) to catch it as an accidental side effect.

## Decision

Every top-level declaration (function/`const`/`let`/`var`/interface/type alias/enum/class) in every file — including the entry file — gets a mangled name `original__kml_modN`, where `N` is a sequential index assigned the moment the file is first visited (stable across cycles). A per-file scope-aware walker (`resolver/rename.go`) then rewrites every reference within that file — value-position identifiers, `new ClassName(...)`, type annotations (including the array-suffix and generic `TypeArgs` cases), `extends`/`implements` targets — that resolves through real lexical scoping to one of that file's own top-level declarations or to an import binding, leaving anything locally shadowed (params, block-scoped locals, loop/catch variables, generic type parameters) untouched. Import aliasing (`import { a as b }`) is now fully supported: `b` is simply bound to the target file's mangled name for `a`, no separate rename step. Binding two different files' exports to the same local name without `as` is still rejected. The old global cross-file name-uniqueness check is replaced by (a) an in-file duplicate check folded into the mangling pass itself and (b) a should-never-fire defensive assertion after mangling, kept per TDD-00041's own recommendation rather than deleted outright.

## Implementation notes

- `resolver/rename.go` (new file): `scope` (a stack of locally-bound-name frames), `renameFile`/`rewriteTopLevelStmt` (top-level dispatch — never binds a name into `scope`, since top-level lookups always go through the lookup table, not shadowing), `rewriteStmt`/`rewriteExpr`/`rewriteType` (the nested-statement/expression/type walkers), `rewriteFunctionLike`/`rewriteClassDecl`/`rewriteInterfaceDecl` (per-declaration-kind scope setup), `rewriteTypeName` (the `Foo[]`/`Foo[][]` flat-suffix fix described above).
- `resolver/resolver.go`: `fileInfo` gained `index`/`mangled` fields; `mangleFileDecls`/`setDeclName`/`mangleName` added; `ResolveProgram` now runs two full passes over every file (mangle-all-declarations, then build-lookup-and-rename-all) before the existing merge step, and the aliasing-rejection `if spec.Local != spec.Imported` check is gone.
- Deliberately did **not** touch `codegen/llvm` at all — verified by `git diff --stat` showing zero changes there, the same property ADR-00022's own design relied on.

## Side effects discovered

- The `Foo[]`/`Foo[][]` flat-name-suffix encoding (described above) is now a real, load-bearing detail any *future* AST-rewriting pass in this codebase needs to know about too — noted here since nothing in `ast/nodes.go`'s own doc comments called it out before this ADR.
- Flagging which machine this was verified on, per this project's own practice for platform-sensitive claims: implemented and verified only on the x86-64 Linux box this session ran on — nothing in the change touches platform-specific code (`gcsrc/`, `runtime_os.go`, etc.), so no reason to expect Mac-specific divergence, but it hasn't been directly re-run there.

## Verification

- `go build ./...`, `go vet ./...`, `go test ./...` all pass.
- `make examples` — 90/90 pass (87 pre-existing + 3 new `examples/imports/scoping*.ts` files), including catching and fixing the `json_methods.ts`/`structured_clone.ts` regression described above before considering this done.
- `tests/imports_test.go`: all pre-existing import tests still pass unchanged in behavior/expectation except `TestE2EImportAliasingRejected`, which is now `TestE2EImportAliasing` and asserts aliasing *works* (compiles and runs, correct output) instead of erroring. Added `TestE2EImportSameNameDifferentFilesNoCollision` (two files privately declaring same-named helpers, no collision) and `TestE2EImportSameExportedNameFromDifferentFilesViaAliasing` (two files both exporting the same name, disambiguated via `as` in the importing file). Renamed `TestE2EImportDuplicateNameAcrossFilesRejected` to `TestE2EImportSameLocalNameFromTwoFilesWithoutAliasRejected` with an updated comment explaining the narrower, still-real scenario it now covers.
- New example: `examples/imports/scoping.ts` + `scoping_a.ts`/`scoping_b.ts` — two files each with a same-named private `helper()` and a same-named exported `run()`, imported into one entry file via two different aliases.
