# ADR-01088: Threads the collector does not know allocate from libc under `-mm=gc`

- **Relations**: `Extends ADR-00071, ADR-00351, ADR-01049`
- **Date**: 2026-09-23

## Context

`make examples MM=gc` on Linux x86-64 aborted `examples/async/promise_all.ts`, `examples/fetch/fetch.ts` and `examples/events/fetch-abort.ts` with Boehm's `Collecting from unknown thread`. All three pass at the previous commit, `d147c2b`. The staged coroutine-stack change (task stacks became an anonymous mapping rather than a GC_malloc'd block, ADR-01050) makes the heap smaller, so collections come sooner. That exposed an older hazard which had so far dodged the timing.

## Investigation

- The shim (`codegen/llvm/gcsrc/gcshim.c`) defines `malloc`/`calloc`/`realloc`/`free` for the whole process. Every thread therefore allocates through `GC_malloc`, including threads that libraries start themselves.
- libcurl resolves a host name on its own thread (getaddrinfo). `promise_all.ts` fetches a `.invalid` name, which is exactly such a lookup.
- A `GC_malloc` there that triggers a collection aborts: Boehm stops the world only from a registered thread.
- Even without the abort, a block handed to that thread would be collectable while only that thread (whose stack is no root) referenced it.
- Registering such threads on the fly was rejected. They exit without unregistering, and Boehm would then signal dead threads.

## Decision

On glibc:
- A thread for which `GC_thread_is_registered()` is false (a positive answer is cached per thread) is served by glibc's own `__libc_malloc`/`__libc_calloc`/`__libc_realloc`.
- Each such block goes into a mutex-guarded open-addressing set. `free`/`realloc` on any thread recognise those blocks and return them to glibc. Other non-GC pointers (the OpenSSL arena case, ADR-00351) are still dropped, as before.
- A foreign thread resizing a GC object gets a libc copy.
- The set is consulted only while it is non-empty, so programs that never see a foreign thread pay one atomic load per `free`.

## Implementation notes

`codegen/llvm/gcsrc/gcshim.c` only, inside `#if defined(__GLIBC__)`. `GC_thread_is_registered` is declared by hand, since `gc.h` declares it only under `GC_THREADS`. macOS and Windows are unchanged (on Windows the collector discovers threads itself, and gc-mode fetch examples already ran clean there).

## Side effects discovered

A separate, older collector crash remains, recorded in BACKLOG §0 item 20. With this fix, 25 rounds of three concurrent `.invalid` lookups under allocation churn segfault near the end of the run, while 10 rounds pass, and `GC_DONT_GC=1` passes. The suspected cause is glibc thread bookkeeping (the TLS DTV, reallocated while the resolver `dlopen`s NSS modules) held only where the collector does not scan. This is unverified.

## Verification

Linux x86-64 (Docker):
- The six examples that regressed under `MM=gc` pass 5/5 each: `promise_all`, `fetch`, `fetch-abort`, `fetch_init`, `classes`, `for_await_iterables`. The last two were fixed by ADR-01086.
- `tests/task_reclaim_gc_tls_test.go` `TestE2EGCModeFetchFromResolverThread` passes 6/6, and fails 6/6 with this fix disabled in-container, with `Collecting from unknown thread`.
- The gc test group passes.
