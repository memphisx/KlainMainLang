# TDD-00069: Object type arguments in generics (extends [TDD-00010](TDD-00010.md) monomorphization)

- **Status**: Implemented
- **Date**: 2026-08-17
- **Notes**: Accept an object/interface/class type as a generic type argument, not just scalars/arrays. `Type` has no name field (a resolved named interface is a structural `ObjectType`), so `mangleTypeArg` mangles objects *structurally* (field-count + each field name/type) and classes by `ClassName` — stronger than the planned nominal-only V1: anonymous inline object types and bare object-literal args work too. Field access/destructuring/`T[]` ride existing per-instantiation monomorphization. Map/Set/Promise/closure args stay clean rejections

## Context

User-defined generics ([TDD-00010](TDD-00010.md), N-ary via [TDD-00037](TDD-00037.md))
are monomorphized, but a concrete type argument may only be a scalar
(`number`/`string`/`boolean`) or a one-level array of those. An object,
interface, or class type argument is a clean rejection — `mangleTypeArg`
(`codegen/llvm/emit_generics.go:40`) returns *"type argument is not supported in
V1 (only number, string, boolean, and arrays of these)"* for any `IsObject`/
`IsClass`/… type.

That excludes the single most common real-TypeScript generic pattern: a container
or helper over a record type (`identity<Point>`, `Box<User>`, `function
first<T>(xs: T[]): T` with `T` an object). It is also the near-term, Axis-1 move
that [TDD-00068](TDD-00068.md) settled on: because generics monomorphize, an
object type argument makes the concrete shape available inside the generic body,
so `const { a, ...rest } = o` becomes ordinary static-shape destructuring and
[TDD-00065](TDD-00065.md) Stage 3c's generic-`T` rest falls out of the existing
`bindObjectRest` — with **no new runtime representation**, and nothing that the
eventual dynamic object model would have to undo.

## Design

The substitution machinery is already type-agnostic. `substituteGenericType`
(`emit_generics.go:98`) returns the concrete `Type` for a bare `T` and
`ArrayOf(concrete)` for `T[]`, whatever the concrete type is; `buildGenericParamSig`,
inference (`genericFuncTypeParamIndex`), and per-instantiation body emission all
thread a `subs map[string]Type` that already carries any `Type`. **The only hard
blocker is mangling**: every instantiation needs a stable, unique,
LLVM-identifier-safe suffix, and `mangleTypeArg` has no case for an object type.

### Mangle nominal object types by name

`Type` already carries the needed identity: `ClassName` for a class
(`types.go:120`) and `Name` for a named type (`types.go:11`), both made unique
per file by the resolver's own name mangling ([TDD-00041](TDD-00041.md)). So:

- **Class type argument** → mangle by `ClassName` (e.g. `Box__Point`).
- **Named interface / named object type argument** → mangle by `Name`.
- **Anonymous inline object type** (`f<{ x: number }>`, or inference from a bare
  object literal `f({ x: 1 })` whose type has no name) → **V1 clean rejection**
  with a "give the type a name (an interface)" hint. A structural canonical mangle
  (ordered field-name+type encoding, recursive) is deferred to a V2 — it is the
  only part of this that needs genuinely new design, and the nominal case covers
  the realistic usage (`const r: Rec = …; f(r)`).

### What rides existing machinery unchanged

Once a type parameter is bound to a concrete object type, everything downstream
already works because the body is emitted per-instantiation against that concrete
type's real `Fields`/`FieldIndex`:

- field access on a `T`-typed parameter (`o.x`), and destructuring
  (`const { a, b } = o`, `const { a, ...rest } = o` via Stage 3b);
- `T[]` parameters/returns (array of the object type, via `ArrayOf(concrete)`);
- passing a `T` value along, returning `T`, storing it in a generic
  interface/class field.

### Scope (V1)

- **In:** a named object/interface/class type as a type argument to a generic
  function (inferred from a `T`/`T[]` parameter position), interface, or class
  (`new Box<Point>()`, `Box<Point>` annotations); bare `T` and one-level `T[]`
  substitution positions, matching the existing V1 depth limit.
- **Out (clean rejection or unchanged):** an anonymous inline object type
  argument (needs V2 structural mangling); nesting a type parameter deeper than
  one array level (`T[][]`, `Box<Box<Point>>` — the existing V1 limit,
  unchanged); explicit call-site type arguments for a *function*
  (`identity<Point>(p)` — still inference-only, unchanged); constraints
  (`<T extends …>`).

## Open questions

- **Named-vs-structural at the mangling site.** Does a resolved named-interface
  type reliably carry a non-empty `Name` where `mangleTypeArg` sees it, or does
  inference (`inferExprType`) sometimes hand back a structural `ObjectType` with
  `Name == ""` for a value whose declared type *was* a named interface? This
  decides how often the V1 named-only rule actually bites in practice — needs a
  direct probe before implementation.
- **Method dispatch on a `T`-typed value when `T` is a class.** Per-instantiation
  emission binds `T` to a concrete class, so a method call `o.m()` in the body
  should resolve — but the generic body may be type-checked with `T` opaque
  *before* monomorphization, which could reject the call up front. This is the
  main implementation risk; prototype it first.
- **Mangling collisions.** Confirm two distinct types that happen to share a
  short name in different modules mangle distinctly (they should, given the
  resolver's own mangling, but verify at the generic instantiation site
  specifically).
- **Inference from a plain object-literal argument.** `f({ x: 1 })` infers an
  anonymous type → V1 rejects it. Is the "name the type" ergonomic hit acceptable
  for V1, or does the anonymous case pull structural mangling forward from V2?
