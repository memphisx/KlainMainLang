# ADR-01085: HTTPS on Windows uses the system certificate store

- **Relations**: `Extends ADR-00080`
- **Date**: 2026-09-23

## Context

On Windows, `examples/http/https_client.ts` failed with `SSL connect error`. Under the examples runner it ended in `0xC00000FD`, on the unhandled-error path of ADR-01081's side effect. Every `fetch`/`https.get` of an `https:` URL failed the same way from a compiled program.

## Investigation

- The same binary succeeds in two cases:
  - run from `C:\msys64\ucrt64\bin`;
  - run with `CURL_CA_BUNDLE` pointing at `C:\msys64\ucrt64\etc\ssl\certs\ca-bundle.crt`.
- The MSYS2 libcurl/OpenSSL build resolves its CA bundle relative to the running executable (`<exe dir>/../etc/ssl/certs`). `curl -v` from that directory reports that path. A compiled program anywhere else has no roots.
- Node always has roots (its bundled store). The Windows certificate store is always present, and libcurl's `CURLSSLOPT_NATIVE_CA` makes the OpenSSL backend use it.

## Decision

On a Windows target, every curl easy handle the runtime creates sets `CURLOPT_SSL_OPTIONS` (216) to `CURLSSLOPT_NATIVE_CA` (16), right after `curl_easy_init`. There are two creation sites: the fetch/http client (`__kml_fetch_async`) and EventSource (`__kml_eventsource_connect`). Other targets are unchanged: their libcurl finds the system bundle itself.

## Implementation notes

`withCurlNativeCA` (`codegen/llvm/runtime_fetch.go`) wraps both IR templates and splices the one `setopt` line after the `curl_easy_init` line.

## Side effects discovered

`http.get` to a refused port with no `'error'` listener overflowed the stack on Windows. That is the same path a transient TLS failure takes. Fixed in ADR-01089.

## Verification

Windows x64: `https.get("https://example.com/")` and `examples/http/https_client.ts` run from `R:\` both print `status: 200` / `body received over TLS` and exit 0. This needs real network access, like the example itself, so there is no E2E test.
