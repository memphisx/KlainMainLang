# ADR-00988: writeFileSync / appendFileSync { mode }

- **Relations**: `Extends ADR-00785`
- **Date**: 2026-09-17

## Context

`writeFileSync(path, data, { mode })` / `appendFileSync(...)` clean-rejected the
`mode` option (ADR-00785 parsed only `{ encoding, flag }`). Node applies `mode`
as `open(2)`'s permission argument, so a freshly-created config/secret/script
file gets the requested bits (`0o600`, `0o755`, …). Without it the everyday
`writeFileSync(p, data, { mode: 0o600 })` idiom failed to compile.

## Investigation

The write runtimes (`__kml_fs_write_file`/`_append_file` and their `_bytes`
siblings, runtime_fs.go) open via `fopen(path, "wb"/"ab")` — no mode argument;
the OS creates with `0666 & ~umask`. Node's semantics: the `mode` arg to
`open(2)` (a) applies **only when the file is created** — an existing file keeps
its permissions — and (b) is **reduced by the umask**. A naive post-write
`chmod(path, mode)` violates both: it re-modes an existing file, and it sets the
exact bits ignoring the umask (verified: `{ mode: 0o666 }` gave `666` where Node
gives `644` under umask `022`).

## Decision

Keep the `fopen` write path; apply `mode` as a conditional, umask-reduced
`chmod` afterwards, emitted around the write at the call site
(`emitFsWriteLikeCall`, emit_fs.go):

1. Before the write, capture whether the file already exists
   (`@__kml_fs_exists`, the `access()`-based predicate).
2. After the write, call `@__kml_fs_chmod_created(path, mode, existed)` — a new
   runtime helper (runtime_fs.go) that chmods **only when `existed` is false**,
   applying `mode & ~umask`. The umask is read via the portable `umask(0)` +
   restore idiom (no read-only form exists); this runs only on the synchronous,
   main-thread write path, so the transient-umask window carries no race.

`fsTextOption` gains a `mode` key (writeFileSync/appendFileSync only, via an
`allowMode` flag; readFileSync still rejects it, matching Node's read options
`{ encoding, flag }`). `mode` may be any numeric expression, coerced to i64.

## Implementation notes

- `chmod` was already declared inline in `ensureFsPathOps` (chmodSync). Since
  `emitGlobal` does not dedup and the new helper also needs it, both now go
  through a shared, guarded `ensureChmodDecl` to avoid a double `declare`.
- The chmod is best-effort (no throw): the write itself already succeeded, and a
  chmod failure on a file we just created as its owner is not a Node-observable
  error at this point.

## Side effects discovered

`TestE2EFsWriteFileSyncModeOptionRejected` asserted `{ mode }` was rejected —
now valid, so it was repointed at a still-unsupported key (`{ signal }`) as
`TestE2EFsWriteFileSyncUnsupportedOptionRejected`.

## Verification

macOS arm64 (M4). Values cross-checked against `node -e` under umask `022`:
`0o666`→`644`, `0o777`→`755`, `0o640`→`640`, `0o600`→`600`; a pre-existing file
re-written with a different `mode` keeps its original perms (mode ignored on an
existing file), for both the string and `Uint8Array` data paths. New E2E tests
(tests/fs_test.go): `TestE2EFsWriteFileSyncMode` (perms via `os.Stat`, using
`0o600` so the assertion is umask-independent) and `TestE2EFsReadFileSyncModeRejected`.
Example: the write section of examples/fs/fs.ts. `go build`/`vet` clean; the fs
suite; `make examples`; `make status` + `make reference-check`.
