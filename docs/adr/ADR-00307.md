# ADR-00307: Event-loop lost-wakeup deadlocks — resumable-task check, conn poke, curl deadline fold

- **Date**: 2026-08-23

## Context

The streaming-upload example (`examples/streams/http_upload.ts` — an in-process 8 MiB POST consumed chunk-at-a-time by an async handler) hung hard on roughly 40% of runs, indefinitely blocked in `select()`. Introduced with the streams work ([ADR-00299](ADR-00299.md)–[ADR-00301](ADR-00301.md)) and shipped undetected — the example suite ran it once per delivery, so a 40% flake passed often enough to hide; it had been intermittently stalling the CI examples run ever since. Surfaced during the Workers delivery's final example pass; a compiler built from the last commit reproduced the identical hang rate, pinning the defect to the streams-era loop integration rather than anything newer.

## Investigation

Diagnosed on live hung processes (darwin/arm64): `sample` for stacks, then — since the runtime's globals are `thread_local` and opaque to lldb without debug info — by appending hand-written `dbg_*` accessor functions to the emitted `.ll`, recompiling, and calling them from lldb against freshly-captured hangs. Register reads of the blocked `select` frame showed `nfds = 4` (the listener alone) with a NULL timeout.

Three distinct lost-wakeup holes emerged, peeled in sequence — each fix shrank but did not eliminate the hang until all three were closed:

1. **libcurl's internal deadline was never consulted.** During transfer states with no fds to watch — most notably the `Expect: 100-continue` wait a large POST triggers (and this server never sends `100 Continue`) — `curl_multi_fdset` contributes nothing and libcurl's documented contract requires the caller to wake it by `curl_multi_timeout()`. The loop never called it, so nothing bounded the wait.
2. **A fetch completion drained after the scheduler step left its awaiter parked forever.** Loop iteration order is `task_sched_step` (resumes satisfied tasks) → select → `curl_multi_perform` + message drain (marks completions). A completion landing in that same iteration's drain leaves the parked task resumable with `task_active` already 0, curl with no fds left, and no timer — `select` blocks on the listener alone. Verified directly: the hung process's suspended task had `pendingFetch->done == 1`.
3. **A connection fiber awaiting an async handler's promise parks as "resume when my fd is readable".** That is usually right (the handler's own input arrives on that fd), but when the handler's final body chunk was fed by the request-body *pump* rather than the fiber, the fd never becomes readable again — the handler finishes, its promise resolves, and the fiber that must write the response never wakes. Verified directly: hung state showed the handler task done, the conn slot fd open with no pending markers, and the client task waiting on the never-sent response.

## Decision

Three complementary mechanisms, all following the loop's existing "a resumed await re-checks its own condition, so a spurious wake is benign" convention:

- **Fold `curl_multi_timeout` into the select timeout via a dedicated extra-deadline slot** — and migrate the two pre-existing non-timer deadline folds (EventSource reconnect, fetch `AbortSignal` deadlines) into the same slot. The first version folded curl's deadline into `%bestfire`, which regressed timer ordering: `checktimerfire` fires the soonest JS timer whenever `now >= %bestfire`, so a near-immediate curl deadline fired pending timers early (caught as a deterministic `Promise.race` test failure — a 400ms timer beating a fast fetch). The pre-existing folds carried the same latent hazard. Now `%bestfire` holds JS-timer fire times only; the select wait is the minimum of the timer wait and the slot's deadline, and a 0ms curl answer degenerates to a poll.
- **`@__kml_task_resumable()`** — a scan mirroring `task_sched_step`'s exact resume conditions (fetch done or headers-done, awaited promise settled, or no park reason), OR-ed into the never-block-while-work-is-ready condition beside the microtask and request-body checks. Stubbed false when the task runtime is absent.
- **`@__kml_conn_poke`** — a one-shot thread-local flag set by `__kml_task_finish`/`__kml_task_reject`: the next conn scan resumes every parked fiber once (each re-checks and re-parks), and an un-serviced poke also forbids blocking in `select`. Cleared after the scan.

## Implementation notes

`runtime_http.go` (the three loop folds + poke read/clear + `curl_multi_timeout` fold block), `runtime_task.go` (`__kml_task_resumable`, poke stores in finish/reject, stub), `runtime_fetch.go` (`curl_multi_timeout` declaration), `emit_task_classify.go` (`ensureConnPokeGlobal`). Debugging technique for next time: the runtime's `thread_local` globals are unreadable from lldb without debug info (the symbol resolves to the TLS descriptor, not the value) — appending exported accessor functions to the emitted `.ll`, recompiling, and calling them from lldb on a captured hang is the practical way to read this runtime's state post-mortem.

## Side effects discovered

None beyond the fixed hangs; the extra per-iteration work is two O(tasks/conns) scans and one `curl_multi_timeout` call.

## Verification

darwin/arm64: before the fixes the example hung on 4–8 of every 20 runs (reproduced against both the current tree and a clean-HEAD build); after each partial fix the hang persisted (re-verified by fresh captures showing the next hole); after all three, **109 consecutive clean runs** (59 + 50 across the instrumented variant and the original example). Full `go test ./...`, `make examples`, and `make conformance` run at delivery end alongside the Workers work.
