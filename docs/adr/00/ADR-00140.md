# ADR-00140: `assert` module

- **Date**: 2026-08-09

## Context

`docs/status/NODE-CORE-MODULES.md` listed `assert` (Node's real assertion library, distinct from `console.assert`, which logs and keeps running rather than throwing) as one of eleven not-started lower-priority core modules, and specifically called it out — alongside `util` — as the two most likely to matter for this project's CLI/microservice direction. Picked up opportunistically (alongside `querystring`, see [ADR-00139](ADR-00139.md)) because, unlike most of that group, it needed no new runtime subsystem: throw/catch (`setjmp`/`longjmp`) and typed binary comparison (`==`/`!=`) already existed and cover almost everything `assert`'s core surface needs.

## Investigation

- Read `codegen/llvm/emit_exceptions.go`: `errorObjType` is a fixed `{i64 kind, ptr message, ptr name}` struct; `errorKinds`/`errorKindIDs` is a closed enum (`Error`, `TypeError`, `RangeError`, `SyntaxError`, `EvalError`, `URIError`, `ReferenceError`) with no `AssertionError` slot. Adding a new kind would touch every `instanceof`/kind-tag site across the codebase for the sake of one name string. Decided instead to reuse `buildErrorObj(kindID, msgPtr, namePtr)` directly with `kindID = 0` (base `Error`) and `namePtr` set to `"AssertionError"` — the exact mechanism `emitInternalThrow` already uses to give internally-raised errors a specific `.name` without a matching kind tag. Consequence: `e instanceof Error` still holds for a caught `AssertionError` (correct — real Node's `AssertionError` also extends `Error`), but there's no way to `instanceof`-distinguish it from a plain `Error`; acceptable since this compiler has no `instanceof AssertionError` syntax to support in the first place (`instanceof` only works against the closed built-in kind enum or a user `class`).
- Read `codegen/llvm/emit_call_console.go`'s `emitConsoleAssert` for the existing branch shape (`br i1 cond, pass, fail` / build message in `fail` / fall through to `pass`) — reused the same shape for `emitAssertCheck`, swapping the fail branch's `dprintf` calls for a thrown `AssertionError`.
- Read `codegen/llvm/emit_exprs_operators.go`'s `emitBinary`: handles `==`/`!=` across every representation this compiler has (dynamic/`any` via `emitAnyEquals`, Symbol identity, numeric `icmp`/`fcmp`, and string comparison via `emitStringBinary`'s `strcmp`), and already rejects unsupported comparisons (e.g. two arrays) with a clear error. Rather than writing a second comparison implementation for `assert.equal`/`.notEqual`, synthesized an `ast.BinaryExpression` (via `ast.NewBinaryExpression`) from the call's own two argument expressions and handed it straight to `emitBinary` — get every existing comparison rule (and its existing error messages) for free, and any future fix to `==` automatically applies here too.
- Considered whether `equal`/`strictEqual` need genuinely different behavior. Real Node's `equal` does an implicit-coercion `==` while `strictEqual` does `===`. This compiler's `==` and `===` are already identical (no implicit type coercion exists anywhere in its type system — confirmed against `TYPE-SYSTEM.md`), so making them true aliases (both compile to the same `==` binary op) is a correct, deliberate scope narrowing, not a missed distinction — documented as such in both the module's own doc comment (`emit_assert.go`) and `NODE-CORE-MODULES.md`.
- Considered `assert.deepEqual`/`.deepStrictEqual`: would need a generic recursive object-equality helper, which doesn't exist yet anywhere in this codebase (object fields are fixed-shape heap structs with no generic field-enumeration/comparison machinery — see `docs/status/OBJECT-COLLECTIONS.md`). Explicitly out of scope, not silently dropped — noted in this module's own doc comment and the status page.
- Considered `assert.throws(fn, expectedErrorOrMatcher)` matching against a specific error type/message/RegExp, the way real Node supports. This compiler has no matcher-object or "test a value against a constructor/RegExp" machinery to build that on, so `assert.throws` here only checks that *something* was thrown — a real, documented scope narrowing, not silently dropped.
- Read `codegen/llvm/emit_exceptions.go`'s `emitTry` for the `setjmp`/`longjmp` try/catch pattern (`__kml_push_jmpbuf`/`setjmp`/branch on the return value/`__kml_pop_jmpbuf` on the success path only, since `__kml_throw` itself pops on the throw path) — reused the identical low-level sequence directly in `emitAssertThrows` rather than trying to route through `emitTry`'s statement-list-shaped API, since the "body" here is a single closure call, not a parsed `try` block's AST.

## Decision

Implemented `assert` as a pseudo-namespace (same `path`/`os`/`querystring` convention) with `ok`, `equal`/`strictEqual` (aliases), `notEqual`/`notStrictEqual` (aliases), `fail`, and `throws`, plus a directly-callable bare `assert(cond, message?)` (real Node's `assert` module is itself callable, equivalent to `.ok`). Every check funnels through `emitAssertCheck`, which throws a `buildErrorObj(0, msgPtr, "AssertionError")` on failure; `equal`/`notEqual` synthesize a binary `==`/`!=` expression and reuse `emitBinary` outright; `throws` runs the target closure inside its own `setjmp` frame and fails (throws its own `AssertionError`) only if that closure returns without throwing.

## Implementation notes

- `codegen/llvm/emit_assert.go` (new): `emitAssertModuleCall` (dispatcher), `emitAssertMessage` (stringifies a message argument via `emitValueToString`, not `coerce` — a message isn't necessarily string-typed at the call site, and `coerce`'s numeric/pointer reinterpretation would silently misbehave on e.g. a bare number passed as a message), `emitAssertThrowFail`, `emitAssertCheck`, `emitAssertBinary`, `emitAssertThrows`.
- `codegen/llvm/emit_call.go`: dispatch block for `id.Name == "assert"` (delegates every property straight to `emitAssertModuleCall`), plus a `case "assert":` in the bare-identifier global-function switch for the callable form.
- `codegen/llvm/emit_exprs_types.go`: `inferExprType` returns `TypeVoid` for every `assert.*` call and for a bare `assert(...)` call — every one of this module's operations is a side-effecting check with nothing to hand back.
- A message argument is only ever evaluated inside the failure branch (mirroring `emitConsoleAssert`'s existing precedent), so a message expression with side effects (e.g. a function call building a formatted string) never runs on the success path.

## Side effects discovered

None — no bugs hit in the existing `emitBinary`/exception machinery this reuses.

- Verified only on the x86-64 Linux box this session ran on, per this project's own practice for platform-sensitive claims — though nothing here touches platform-specific code; it's pure reuse of already-cross-platform-verified `setjmp`/`longjmp` exception machinery and `emitBinary`.
