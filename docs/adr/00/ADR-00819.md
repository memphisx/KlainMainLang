# ADR-00819: `-webview=sailfish` native QTimer loop-fusion pump

- **Relations**: `Extends ADR-00818`, `Implements TDD-00146`

- **Date**: 2026-09-09

## Context

[ADR-00818](ADR-00818.md) got `-webview=sailfish` running on device, but the
loop-fusion pump (ADR-00439 — what drives klain-level `setTimeout`/`setInterval`/
microtasks/promises on the GUI thread under `run()`) rode the runtime's default
page-side path: an injected `setInterval(() => window.__kml_tick(), 16)` whose
each call is a full embedlite IPC round-trip (CustomEvent → frame script →
`sendAsyncMessage` → `recvAsyncMessage` → the bound thunk). At ~60 Hz that is a
lot of IPC and JS churn for a heartbeat, flagged there as a perf follow-up.

## Investigation

The page-side pump binds `__kml_tick` via `webview_bind`; its thunk
(`emitWebviewPumpThunk`, `emit_webview.go`) does nothing but call three runtime
drains — `__kml_timer_tick()`, `__kml_task_sched_step()`, `__kml_drain_microtasks()`
— then `webview_return`. Those three are always defined for a webview program
(real runtimes, or no-op stubs from `emitLoopTaskStubs`) with external linkage, so
a separately-compiled C++ shim can declare them `extern "C"` and call them
directly. Driving them from a native timer needs neither the page round-trip nor
the `webview_return`.

The runtime still injects its page-side installer, guarded by
`if(!window.__kml_pump){…}` — so pre-setting `window.__kml_pump` truthy stops the
`setInterval` from ever being created, with no change to the runtime.

## Decision

Drive the pump natively in the Sailfish shim: a `QTimer` at 16 ms whose `timeout`
slot calls `__kml_timer_tick()` / `__kml_task_sched_step()` / `__kml_drain_microtasks()`
directly. The timer is created and started in `onViewInitialized` (GUI thread, so
the drains run there — the same thread the page-driven thunk used). The page-side
pump is suppressed by injecting `window.__kml_pump=1;` at the top of the
`domContentLoaded` handler, before the runtime's init scripts. The `__kml_tick`
binding still exists (harmless, now unused). No IPC per tick; the bridge now
carries only real `bind` calls.

## Implementation notes

`webview_sailfish.cpp`: `extern "C"` decls for the three drains; a `QTimer *mPump`
member; the `onPumpTick` slot; timer setup in `onViewInitialized`; the
`window.__kml_pump=1;` suppression in `onDomContentLoaded`. This is the Qt variant
of the loop fusion TDD-00146 anticipated (a native timer integrated with the Qt
event loop, rather than the GTK/AppKit page-tick pump).

## Side effects discovered

None. The drains are called unconditionally at 16 ms even when idle, exactly as
the page pump did; they short-circuit on empty queues.

## Verification

On the physical Xperia 10 II: a smoke app that terminates from a **klain-level
`setTimeout`** (not a page timer) logs `KLAIN_NATIVE_PUMP_TIMER_FIRED` and exits
cleanly (`run()` returns) — proving the native pump drives the klain runtime — while
a page→native `bind` in the same run still round-trips (`KLAIN_BIND_OK`). The
`embed:kmlrpc` message count for the whole run dropped from ~170 (60 Hz `__kml_tick`
flood) to **1** (the single real bind call). `go build`, `go vet`,
`TestE2EWebviewBackendFlag` green on macOS.
