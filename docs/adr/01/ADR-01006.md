# ADR-01006: zlib results are Buffer-typed

- **Date**: 2026-09-18

## Context

A stale-caveat verification sweep over `docs/status/data/*.json` (running each
divergence-verb caveat's repro against both the compiled binary and Node)
confirmed the `zlib` caveat "a decompressed result needs an explicit `: Buffer`
annotation to call `.toString()`": `zlib.gunzipSync(g).toString()` was a
compile error (`a TypedArray has no method 'toString'`), where Node returns a
`Buffer`.

## Investigation

`emit_zlib.go` documented "Output is always a Buffer" yet returned
`TypedArrayType("uint8")` (a bare `Uint8Array`) from the `*Sync` forms and as
the callback-result hint; the inference mirror in `emit_exprs_types.go`'s
`zlib__kml_builtin` branch did the same. A Node `Buffer` here is storage-wise
the identical `{ptr,i64}` shape with the `IsBuffer` flag (TDD-00103), so the
fix is purely a type-flag change — no runtime/ABI difference.

## Decision

Return `BufferType()` everywhere a zlib result is typed: the `*Sync` result,
the callback parameter hints, and both callback invocation sites, plus the
inference branch. Buffer methods (`.toString()`, string search, …) then
dispatch normally; everything Uint8Array-shaped keeps working since a Buffer
IS a Uint8Array here.

## Implementation notes

- `codegen/llvm/emit_zlib.go`: all four `TypedArrayType("uint8")` sites → `BufferType()`.
- `codegen/llvm/emit_exprs_types.go`: the `zlib__kml_builtin` `*Sync` inference → `BufferType()`.

## Side effects discovered

None. The pre-existing annotated `: Buffer` escape hatch keeps compiling.

## Verification

New `TestE2EZlibResultIsBuffer` (sync + callback `.toString()`/`.length`,
byte-exact vs Node); full `Zlib` test group passes; `make examples` and
`make conformance-node` green (macOS arm64). Caveat deleted from
`docs/status/data/node-core-modules.json`.
