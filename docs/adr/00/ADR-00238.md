# ADR-00238: AbortSignal.timeout + mid-flight fetch cancellation (stage 3c)

- **Relations**: `Implements TDD-00081` (Stage 3c); `Extends ADR-00237`
- **Date**: 2026-08-19

## Context

Stage 3b only cancelled a fetch whose signal was aborted *before* the await
([ADR-00237](ADR-00237.md)) — it checked the signal once, at the await's entry.
That missed the actual reason `AbortController` exists: **`AbortSignal.timeout(ms)`
cancelling a slow request**, and an abort landing while the request is in flight.
This closes that.

## Decision

- **`AbortSignal.timeout(ms)`** — a new static returning a standalone signal with
  a monotonic-ns `deadlineNs` (a field appended to `AbortSignalType`). Parsed as a
  static member call on the `AbortSignal` identifier.
- **`__kml_signal_aborted(signal) -> i1`** — a shared helper: true if the signal's
  `aborted` flag is set, or its deadline has elapsed (in which case it latches the
  flag). Null → false; reuses `__kml_monotonic_ns` from the timer runtime.
- **`__kml_await_fetch` now checks every spin, not just at entry.** The abort check
  moved to the top of the wait loop and calls `__kml_signal_aborted`, so a deadline
  that elapses — or a signal aborted mid-flight — tears the transfer down
  (`curl_multi_remove_handle` + `curl_easy_cleanup`) and throws an `AbortError`
  while the request is still running.
- **The event-loop resume scan** (`rcheckfetchdone`, runtime_http.go) also consults
  `__kml_signal_aborted` per parked fetch fiber, so a fetch awaited inside an
  `http.listen` handler / `Promise.all` resumes and throws on abort/timeout too.

## Implementation notes

`AbortSignalType` gained `deadlineNs` as a trailing field, so `aborted` stays at
offset 0 (the fetch check reads it as a raw byte). The busy-spin (top-level await)
path checks the deadline on every loop iteration, so its timeout is precise.

## Side effects discovered

- **Fiber-path timeout precision.** When a fetch is awaited on a *connection fiber*
  (inside an `http.listen` handler) rather than at top level, its
  `AbortSignal.timeout` fires when the event loop next wakes — precise under load,
  but on an otherwise-idle loop `select()` can block past the deadline because the
  deadline is not yet folded into `select()`'s own timeout. Folding the minimum
  live fetch-deadline into the `select()` wait is the remaining refinement. The
  top-level/`await`-driven path (the common `AbortSignal.timeout` usage) is precise.
- A bare `signal.aborted` read reflects a `timeout` deadline only after some await
  loop has checked it; there is no background thread latching it.

## Verification

- `tests/abort_test.go`: `AbortSignal.timeout(0)` cancels a fetch deterministically
  (deadline already past at the await); the earlier abort-before/after-await cases
  still pass. Manually verified a real `AbortSignal.timeout(300)` cancels a hung
  connection at ~300ms.
- `examples/events/fetch-abort.ts` extended with the timeout case; runs correctly.
- The event-loop consumers (HTTP/WebSocket/EventSource/fetch/Promise/XHR) all still
  pass, and `go build`/`go vet ./...` are clean, on Apple Silicon (macOS).
