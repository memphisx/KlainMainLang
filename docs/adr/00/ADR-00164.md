# ADR-00164: Optional (`param?: T`) function parameters

- **Relations**: Extends [ADR-00157](ADR-00157.md), [ADR-00158](ADR-00158.md)
- **Date**: 2026-08-11

## Context

Surveying fresh candidates for the next well-scoped fix: `function f(x?: number) { return x; }` compiled as a definition, but calling `f()` (omitting the optional argument) failed with `codegen error: missing argument 1 with no default`. `docs/status/LANGUAGE-CONSTRUCTS.md` already listed "Optional parameters (`param?`)" as ✅ with no caveat — a real doc/code mismatch, the same class of gap ADR-00163 found for `.reduce()`.

## Investigation

`ast.Param.Optional` is set correctly by the parser (`optional := p.match(lexer.QUESTION)`) and round-trips onto the AST — the `?` itself parses fine. But `grep -rn "\.Optional" codegen/llvm/*.go` returned zero matches: nothing in codegen ever read the field. `FuncSig` (`codegen/llvm/types.go`) tracked `Defaults []ast.Expression` (explicit `= expr` values) but had no equivalent slot for "no default, but omission is still legal." Every call-site argument-binding loop — `emitCallToFuncSig` (`emit_call.go`), `emitClassCall`/`emitStaticMethodCall` (`emit_classes.go`) — therefore fell straight into the "missing argument" error for any omitted optional argument, identically to a genuinely missing required one.

The natural fix reuses `Type.zeroLiteral()` (ADR-00157): a `param?: T` with no explicit default has exactly the same "no real `undefined` sentinel for a concrete scalar type" shape ADR-00157/ADR-00158 already settled — the zero value of `T` is this compiler's established stand-in.

While wiring the array-typed case, two more bugs surfaced in passing (see Side effects discovered).

## Decision

Added `Optional []bool` to `FuncSig`, populated identically to `Defaults` by all three signature builders (`buildParamSig`, `buildGenericParamSig`, `buildFunctionSig`) from `p.Optional`. At each of the three call sites, a new branch sits between the existing `Defaults[i] != nil` branch and the final "missing argument" error: if `Optional[i]` is set, emit the parameter type's zero value as the argument instead of erroring. For a scalar/pointer-IR type this is `paramTy.IR` + `paramTy.zeroLiteral()`; for an array-typed parameter (which decomposes into two LLVM params, `ptr`+`i64 len`, at the callee side) it's the pair `"ptr null", "i64 0"` — an empty array, not a single zero operand.

`emitClassCall`/`emitStaticMethodCall`'s own `minRequired` arg-count check (which already excluded trailing defaulted params from the "too few arguments" error) now also excludes trailing optional params, the same way.

## Implementation notes

Files touched: `ast/nodes.go` unchanged (`Param.Optional` pre-existing). `codegen/llvm/types.go` (`FuncSig.Optional`), `codegen/llvm/emit_classes.go` (`buildParamSig`, `emitClassCall`, `emitStaticMethodCall`), `codegen/llvm/emit_generics.go` (`buildGenericParamSig`), `codegen/llvm/emitter.go` (`buildFunctionSig`), `codegen/llvm/emit_call.go` (`emitCallToFuncSig`).

Generic function calls (`identity<T>(x: T)`) can't exercise the zero-arg case in practice — V1 generics infer `T` only from a provided argument (see `examples/generics/generics.ts`), so a generic function's sole optional parameter with no other way to infer `T` has no legal zero-argument call form regardless of this fix; not a new limitation, pre-existing to how generics are scoped.

## Side effects discovered

Two pre-existing, unrelated bugs surfaced while building the array-typed-optional-parameter repro, both fixed here as blocking prerequisites (small, contained, found in passing per this project's standing rule):

1. **Array-typed default parameter values never worked at all.** `function f(a: number[] = [1,2,3])` failed to *compile* (hard clang-stage error: `'%tN' defined with type '{ ptr, i64 }' but expected 'ptr'`) — `emitCallToFuncSig`'s `Defaults[i] != nil` branch evaluated the default expression and passed the resulting `{ptr,i64}` aggregate register directly where the callee's LLVM signature expects two separate scalar params. Fixed by giving that branch the same `IsArray` decomposition (`extractvalue` + two-part `argParts`) the direct-argument branch already had, mirroring `emitClassCall`'s existing shared-decomposition shape. Covered by `TestE2EDefaultParamArray`.
2. **String concatenation with a null string operand segfaulted.** See [ADR-00165](ADR-00165.md) — found via `'Hi, ' + name` crashing when `name`'s zero value (a null string pointer) reached `emitStringConcat`'s unconditional `strlen()` call; confirmed independent of this feature (a plain `let s: string | null = null; console.log('x' + s)` crashed identically before the fix). Fixed and documented separately since it's a general string-operator bug, not specific to optional parameters.
