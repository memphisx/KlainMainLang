# ADR-01798: Object.prototype's methods as values

- **Relations**: `Implements TDD-00230`
- **Date**: 2026-10-20

## Context

- `Object.prototype` is one shared null-prototype bag, and it was empty. `Object.prototype.hasOwnProperty` read as a value was undefined. Only the call form `Object.prototype.m.call(o, …)` was compiled, and only statically.
- Test262's `propertyHelper.js` starts with `Function.prototype.call.bind(Object.prototype.hasOwnProperty)`. Every test using `verifyProperty` failed with "Function.prototype.call called on a non-function": about 100 in the destructuring and generator directories alone.

## Decision

- An `objproto_fill` hook (hooks.c) runs when the bag is created. A program that reads `Object.prototype` defines it (`ensureObjProtoFill`). It installs the methods as non-enumerable properties: `hasOwnProperty`, `propertyIsEnumerable`, `toString`, `toLocaleString` and `valueOf`, each a dynamic function compiled from parsed source over the existing static `Object.prototype.m.call(this, …)` form, plus `constructor`.
- A dynamic get whose chain ends at an ordinary object (not an explicit null prototype) reads on in this bag, so `o.hasOwnProperty` and `o.toString` are those functions. A static member read naming one of them also defines the hook. `in` already answered for these names, and `for…in` and inspection skip non-enumerable keys.

## Consequences

- `TestE2EJSFileObjectPrototypeMethodValues` compares the method values, `call.bind` wrappers, the bag's own keys and its rendering against Node.
- The bag is filled only when the program reads `Object.prototype` or names one of its members statically. A read with a runtime key in a program that does neither finds it empty.
- Still missing from the bag: `isPrototypeOf`, `__proto__`, and `__defineGetter__`/`__defineSetter__`/`__lookupGetter__`/`__lookupSetter__`. A parsed helper body cannot reach the `Object.*` statics that `isPrototypeOf` needs.
