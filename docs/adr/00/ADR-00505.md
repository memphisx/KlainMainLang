# ADR-00505: HTTPS/1.1 server — `https.createServer` + `allowHTTP1`

- **Relations**: `Implements TDD-00111` (the residual 1.1-over-TLS items); `Extends ADR-00504` (h2-over-TLS accept branch), `ADR-00344`/`ADR-00345` (TLS server CTX/ALPN), `ADR-00346` (wss fd→SSL registry pattern)
- **Date**: 2026-08-29

## Context

[ADR-00504](ADR-00504.md) shipped h2-over-TLS (`http2.createSecureServer`) but
deliberately left two items open, both requiring HTTP/1.1 to be served over a
TLS connection: a general `https.createServer` (HTTPS/1.1) and the opt-in
`allowHTTP1` 1.1-over-TLS fallback on the h2 secure server. Until now `https`
was client-only (`get`/`request` over libcurl) and `https.createServer` was a
clean rejection. Serving plain HTTPS/1.1 is the most common shape of the
microservice use case this project targets, so it closes the last gap on
TDD-00111.

The obstacle 00504 named: the h2 secure path drives each connection *inline and
blocking* (never joining the fiber conn table), which is fine for a single
nghttp2 session but would serialize a 1.1 server to one connection at a time.
The 1.1 event loop, by contrast, is a hand-written non-blocking select() loop
over raw fds with a per-connection fiber — and it was not SSL-aware.

## Decision

Rather than a separate blocking 1.1-over-TLS drive, **make the existing 1.1
connection fiber SSL-aware** so a TLS connection is served by the exact same
dispatcher, keeping the full non-blocking/fiber concurrency model, keep-alive
posture (`Connection: close`, one request per connection), WS-upgrade path, and
streaming tail unchanged.

The mechanism is a per-fd SSL indirection (the wss fd→SSL registry pattern,
ADR-00346):

- A small fd→SSL* registry (`@__kml_http_conn_ssl_*` + `_set`/`_get`) and three
  I/O shims — `__kml_http_conn_recv`/`_send`/`_close` — route through SSL when
  the fd has a live registry entry, else fall through to raw `read`/`write`/
  `close` (byte-identical to the pre-TLS path). All three are emitted once,
  only when the HTTPS/1.1 path is used (`usedHTTPS1Server`).
- The dispatcher's request `read`, `__kml_http_send_response`'s header+body
  write and close, the `noReq` close, and the chunked streaming writer
  (`__kml_hws_*`) are all routed through the shims when `usedHTTPS1Server`.
- Reads use a new `__kml_tls_read_nb` that maps `SSL_ERROR_WANT_*` to
  `errno = EAGAIN`, so the dispatcher's existing EAGAIN-yield path applies
  unchanged. Writes use `__kml_tls_write_all`, which drains the whole buffer,
  `poll()`-ing on `WANT_*` — preserving the "one blocking write succeeds in
  full" contract the buffered/streaming response writers assume, over a
  non-blocking TLS socket.

The event loop's TLS accept branch (from 00504) is generalized: after the
handshake, a non-h2 (or no-ALPN) connection goes to `tls1serve` — register the
SSL, then rejoin the ordinary `setnonblock`/`append_conn` path — when the 1.1
path is enabled, else it is dropped (h2-only, Node's `allowHTTP1:false`).

`https.createServer({ cert, key }[, handler])` builds the server `SSL_CTX` with
an **http/1.1-only ALPN** callback (`offer_h2 = 0`, a new `__kml_tls_server_ctx`
parameter) — since no nghttp2 driver is linked, a `curl --http2` client must
fall back to 1.1 rather than negotiate a protocol the server can't speak — then
delegates the handle/listen/close/address and `(req, res)` wiring to the shared
`emitHTTPCreateServer` core, exactly as `http2.createSecureServer` does.

`http2.createSecureServer({ …, allowHTTP1: true }, …)` additionally enables the
1.1 path, so ALPN chooses h2 (inline nghttp2 drive) or http/1.1 (fiber conn
table over the shims) on the same TLS port.

## Implementation notes

- `offer_h2` was threaded through `__kml_tls_server_ctx` (a 4th param); the two
  existing callers (`tls.createServer`, `http2.createSecureServer`) pass `1`.
  A second ALPN callback (`alpn_select_h1_cb`) offers http/1.1 only.
- `emitCertKeyPtrs` now tolerates (and ignores) an `allowHTTP1` key, and rejects
  a function-literal first argument cleanly — the bare-listener form
  (`createServer((req,res)=>…)`) is invalid for a TLS server, which needs the
  `{ cert, key }` object first.
- `allowHTTP1` is read only from an inline options **literal** (the practical
  form); a variable-bound options object leaves it at its `false` default.
- The shims are emitted only for `usedHTTPS1Server` — an h2-only secure server
  links neither `__kml_tls_read_nb`/`_write_all` nor the registry, and pays no
  runtime branch it doesn't need.

## Side effects discovered

- The obsolete `TestE2EHTTPSCreateServerRejected` (which asserted the clean
  rejection) was repurposed to assert the missing-`{ cert, key }` rejection.

## Verification

- New E2E `TestE2EHTTPSServer` (`tests/http_test.go`): a `https.createServer`
  over a self-signed fixture serves an h2-capable `curl` at HTTP/1.1 (h1-only
  ALPN) and echoes a POST body (Content-Length read loop over the SSL shims).
- New E2E `TestE2EHTTP2SecureServerAllowHTTP1`: one `createSecureServer({ …,
  allowHTTP1: true })` serves both an h2 client (`http_version=2`) and a 1.1
  client (`1.1`) on the same TLS port.
- Existing `TestE2EHTTP2SecureServer` (h2-only drop of a 1.1 client) still
  passes — the `allowHTTP1:false` default is unchanged.
- New `examples/https/https_server`. `go test` http/tls/net/websocket/fetch
  suites pass; `go vet` clean. Verified on macOS (M4).
