# ADR-00569: os.cpus() reports the libuv speed fallback on Apple Silicon

- **Relations**: Extends ADR-00024
- **Date**: 2026-09-01

## Context

`os.cpus()` read each core's clock via `sysctlbyname("hw.cpufrequency")`. That
key is unavailable on Apple Silicon (M-series dropped the fixed-clock model), so
the call fails and the code reported `speed: 0`. The status page claimed this
"matches real Node's documented M-series behavior" — but a direct comparison on
an M4 Pro (Node v26.3.0) shows real Node reports `speed: 2400`, not `0`: libuv
falls back to a fixed 2400 MHz nominal on macOS/arm64. So the `0` was a genuine
divergence, not parity.

The sibling `times.irq: 0` claim, by contrast, *is* parity — real Node reports
`irq: 0` on Darwin too (Mach's per-core tick array has no IRQ bucket).

## Decision

When the `hw.cpufrequency` sysctl yields `0` (Apple Silicon), report `2400` MHz
— libuv's fixed macOS/arm64 fallback — instead of `0`. A real value (Intel
Macs, where the sysctl works) flows through unchanged. `os.cpus()[].speed` now
byte-for-byte matches real Node on the same hardware.

Both `os.cpus()` caveats are consequently retired: `speed` now matches Node, and
`irq: 0` was always parity (reclassified from a caveat to a note).

## Side effects discovered

None. Only the Darwin speed-fallback branch changed; Linux (`/proc/cpuinfo`
`cpu MHz`) and the Darwin tick counters are untouched.

## Verification

`TestE2EOSCpusFieldsWellFormed` tightened to assert `speed > 0` (never `0`);
compared against Node v26.3.0 on an Apple M4 Pro (`speed: 2400`, `irq: 0` — both
now matched). Built and verified on Mac (Apple Silicon); the Intel-Mac path is
unchanged and carries the same prior verification status.
