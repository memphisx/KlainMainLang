# ADR-00085: Numeric separators (`1_000_000`)

- **Date**: 2026-07-31

## Context

Flagged in `docs/status/README.md`'s "Newly identified gaps" list (2026-07-30
audit) as confirmed absent from the lexer, and picked up as one of a small
batch of self-contained, low-complexity front-end features to close out
alongside the larger in-flight class-inheritance work. No new runtime
machinery needed — purely a lexer change.

## Investigation

Confirmed via direct read of `lexer/lexer.go`'s `readNumber` that no `_`
handling existed anywhere in any of the four numeric-literal scan loops
(decimal, hex, binary, octal) — an underscore inside a numeric literal would
have broken the scan (falls through to "unrecognized character" territory
one token later) rather than being silently accepted.

The token's raw literal text flows straight into the emitted LLVM IR: for a
decimal integer, `emitNumberLit` (`codegen/llvm/emit_exprs.go:96`) uses the
lexed string directly as the IR immediate operand (`Value{Ref: v, ...}`), and
LLVM IR has no concept of a numeric separator. This means the separator has
to be stripped inside the lexer itself — accepting `_` in the character class
but still writing it into the token's literal buffer would produce invalid
IR (`i64 1_000_000` is not a valid LLVM integer literal), not just a cosmetic
issue.

## Decision

Added a shared `readDigitRun(buf *strings.Builder, isDigit func(rune) bool,
line, col int) error` helper that consumes a run of digits (per the caller's
own digit predicate — hex/binary/octal each have a different one) allowing a
single `_` between two digits; the separator is simply never written to
`buf`, so every downstream consumer (parser, codegen) sees a clean literal
string exactly as if the separator had never been there. A leading, trailing,
or doubled separator is rejected with a clean lexer error
(`numeric separator '_' must be between two digits`) rather than silently
producing a malformed literal.

The regular decimal branch (which also has to track `hasDot` for the decimal
point) couldn't reuse the shared helper directly, since it interleaves two
different characters it might see (`.` and `_`); it got the same rule
inlined instead, with the `.` transition explicitly resetting the
"last was digit" tracking so `1_.5`/`1._5`-shaped inputs are rejected too
(underscore immediately touching the decimal point is disallowed, matching
real JS's own separator placement rule).

## Implementation notes

Files touched: `lexer/lexer.go` (`readDigitRun` helper; hex/binary/octal
branches of `readNumber` now call it; the decimal branch got the same
skip-and-validate logic inlined).

No parser or codegen changes were needed — by design, since the separator
never survives past the lexer.

## Side effects discovered

None — this is purely additive lexer syntax; every existing numeric literal
(no underscores) is scanned by exactly the same code path as before, just
with an extra `else if c == '_'` branch that was previously unreachable
(would have hit the loop's `break` and moved on to the next token).

While testing this manually, ran into what looked like a separate float bug
(`const pi: number = 3.14_159` printed `3`, not `3.14159`) — investigated and
confirmed this is **not** a bug: this compiler's own documented design has a
bare `number` type annotation always mean `i64`
(`docs/status/TYPE-SYSTEM.md`'s `number → i64` row), with `f64` inference
only kicking in for an *unannotated* `let`/`const` whose initializer is
itself a float literal (`emit_exprs_vardecl.go:135-140`). `let pi = 3.14_159`
(no annotation) prints correctly. Not a new gap and not something this ADR
touches — just a reminder that an explicit `: number` on a float literal is
this compiler's documented int64-truncating behavior, not a separator-related
regression.

  `TestE2ENumericSeparatorMisplacedIsError` (doubled and trailing separator,
  both rejected at parse time).
- `examples/basics/hex.ts` extended with three numeric-separator lines,
  every inline expected-output comment verified against the actual compiled
  binary's output.
- `go build -o klainmain . && go vet ./... && go test ./...` all green.
- `make examples`: full suite passed, including the extended `hex.ts`.
