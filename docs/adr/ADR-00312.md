# ADR-00312: Binary-data caveat batch — `Atomics.isLockFree`, `ArrayBuffer`/`SharedArrayBuffer.slice`, 3-argument TypedArray views, DataView BigInt accessors

- **Relations**: Extends [ADR-00078](ADR-00078.md), [ADR-00294](ADR-00294.md), [ADR-00308](ADR-00308.md)
- **Date**: 2026-08-23

## Context

The Binary Data & Typed Arrays status page carried four mechanical caveats — no `Atomics.isLockFree`, no buffer `.slice()`, only whole-buffer views at offset 0, and no 64-bit DataView accessors. All four are direct extensions of shipped designs, closed together at the start of the binary-data completion batch.

## Investigation

- `.slice` had a natural insertion point: the existing `"slice"` property dispatch (`codegen/llvm/emit_call.go`) already disambiguates array vs string; an `IsArrayBuffer` check slots in front. `emitNormalizeSliceIdx` (emit_arrays_sort.go) already implements the spec's negative-index/clamping rules.
- The 3-argument view form needed parser+AST work (the node carried a single `Arg`); the DataView constructor's RangeError checks (emit_dataview.go:64–81) were the model for the new offset/length validation. The free-variable scanner and resolver walker needed the new child expressions ([ADR-00310](ADR-00310.md)'s lesson).
- `getBigInt64`/`setBigInt64` needed an unsigned half the bigint ABI lacked: `__kml_bigint_to_i64` is signed-only (`mp_get_i64` / `mpz_get_si`).

## Decision

- `Atomics.isLockFree(n)`: an `or` of `icmp eq` against 1/2/4/8 — every supported width lowers to native LLVM atomics on both hosts, so the answer depends only on the size.
- `buffer.slice(start?, end?)`: normalize both indices against `byteLength`, allocate a new header+data of the receiver's own kind (a `SharedArrayBuffer` slices to a new `SharedArrayBuffer`, keeping the gc-mode uncollectable allocation), `memcpy` the sub-range.
- `new XArray(buffer, byteOffset, length?)`: `NewTypedArrayExpression` gains nil-able `ByteOffset`/`Length` children. RangeError throws for a negative, misaligned (offset % elemSize ≠ 0 — unaligned element access stays rejected, closing TDD-00018's open question by exclusion), or out-of-bounds offset; an explicit length is bounds-checked without the whole-span divisibility requirement.
- DataView `get/setBigInt64`/`get/setBigUint64`: new `bigint` field on `dataViewAccessKinds` (width 8); gets wrap the raw i64 through `__kml_bigint_from_i64`/`from_u64`, sets require a compile-time `IsBigInt` value (the spec's TypeError) and unwrap via `to_i64`/`to_u64`. The new `from_u64`/`to_u64` ABI pair landed in **both** backends (libtommath and GMP); both `to_*` conversions implement the spec's mod-2^64 wrapping.

## Implementation notes

`codegen/llvm/emit_atomics.go`, `emit_arraybuffer.go` (`emitArrayBufferSlice`, `emitTypedArrayFromBuffer` rewrite), `emit_dataview.go`, `emit_bigint.go` + `bigintsrc/bigint_tommath.c`/`bigint_gmp.c`, `parser/parser_literals.go`, `ast/nodes.go`, `resolver/rename.go`, `emit_func.go` (scanner), `emit_call.go`/`emit_exprs_types.go` (dispatch + inference). In passing: `.subarray` had no `inferExprType` case at all — an unannotated `const v = ta.subarray(...)` failed as "not an array" for every TypedArray; fixed.

## Side effects discovered

None beyond the `.subarray` inference gap above (fixed here).

Examples extended (`examples/typedarrays/`, `examples/basics/dataview.ts`, `examples/workers/shared_counter.ts`). Full `go test ./...` green on darwin/arm64.
