# ADR-00971: HTTP server `'clientError'` event (TDD-00215 Stage 1)

- **Relations**: `Implements TDD-00215`
- **Date**: 2026-09-16

## Context

`http.createServer(...).on(event, listener)` recognized `'request'`, `'stream'`,
`'listening'`, `'upgrade'`, `'close'`, and `'connection'`, rejecting every other
name at compile time. Node's `'clientError'` `(err, socket)` — fired when a
client connection produces a protocol error before it can be dispatched to a
request handler — was missing. It is a common hardening surface (log/rate-limit
malformed clients), and unlike the previously-tracked "ReadableStream-body return
over HTTPS/1.1" keep-alive caveat it is genuinely reachable through the ordinary
`createServer` API. (That keep-alive caveat described a shape no public API can
produce — a returned `ReadableStream` body only routes through `klain:http`'s
plain-TCP `http.listen`; `createServer` requires `(req, res) => void` and ignores
a returned object — so its status caveat is corrected same-commit.)

## Investigation

`buildHTTPDispatcher` (`emit_http.go`) already funnels every connection-abort
path to a single label, `noReqL`. Reading it showed `noReqL` is reached by *three*
distinct edges: the header-block overflow abort (`tooBig`, the 10MiB cap at
`growL`), the read-loop EOF/error edges (`checkErrL`/`checkEagainL`), **and** an
ordinary keep-alive idle-EOF (`idleRetire`, and a zero-byte first read). So
`clientError` could not simply fire at `noReqL` — a clean idle close reaches it
too, and would produce a spurious event.

The compiler's hand-rolled request parser is lenient: a garbage request line that
*does* contain `\r\n\r\n` is parsed and dispatched (a weird but complete request),
never reaching `noReqL`. The deterministic error triggers are therefore the
header-block overflow and a request truncated by the peer closing mid-parse.

Reusable machinery already existed: `emitHTTPConnectionEvent` builds a
`net.Socket` over the connection fd (calloc 64, fd in field 0, the TLS `SSL*` in
field 5 for an HTTPS server) and invokes a stored `{fn,env}` closure header;
`buildErrorObjWithCode` mints an `errorObjType` carrying `.message`/`.name`/`.code`
(the shared error object already supports `err.code`, used by `node:sqlite`).

## Decision

Add a per-connection **reason discriminator** (`i32` alloca, init 0) that the
error edges set right before branching to `noReqL` — terminal, so no keep-alive
reset is needed:

- `1` = header-block overflow (the connection is still open).
- `2` = a request truncated by the peer (bytes were buffered, then EOF/reset).
- `0` = a clean close / idle keep-alive EOF — no event, byte-identical to before.

The EOF/read-error edges route through a shared `abEndL` block that sets reason 2
only when `totalRead > 0` (otherwise it is an ordinary close, reason 0).

`noReqL` then branches on the reason:

- reason 0 → straight to teardown (unchanged).
- A registered `'clientError'` listener (`@__kml_http_clienterror_evt`, primary
  server only in V1) → build a `net.Socket` over the fd + an `Error` whose
  `.code` is `HPE_HEADER_OVERFLOW` (reason 1) or `ECONNRESET` (reason 2) and
  `.message` `"Request Header Fields Too Large"` / `"Parse Error"`, invoke
  `listener(err, socket)`, then close.
- No listener → Node's default: reason 1 writes
  `HTTP/1.1 431 Request Header Fields Too Large\r\nConnection: close\r\n\r\n`
  (the connection is still open) then closes; reason 2 has no socket left to
  answer, so it just tears down.

`.code` is a deliberately small, honest set: the parser produces no llhttp `HPE_*`
codes, so exact Node parity is impossible without a parser rework — documented as
a caveat rather than faked.

## Implementation notes

- All changes in `codegen/llvm/emit_http.go` (dispatcher + `.on('clientError')`
  registration) and one global declaration in `runtime_http.go`
  (`@__kml_http_clienterror_evt`, next to `@__kml_http_close_evt`).
- `fd64`/`fd32` are computed once at `readLoopL` and dominate `noReqL` (the
  existing code already relies on this), so the socket build and the 431 write
  reuse them directly.
- The 431 write and the connection close route through `__kml_http_conn_send` /
  `__kml_http_conn_close` when `usedHTTPS1Server`, else raw `write`/`close` —
  the same TLS-aware shim pattern the rest of the dispatcher uses.
- Primary-server-only (like `'close'` shipped first): a suffixed additional
  server rejects `.on('clientError')` with a clear message; its dispatcher's
  global load is null, so it takes the no-listener default.

## Side effects discovered

- The no-listener malformed path changed from a silent close to Node's 431
  (an intentional, approved behavior change — strictly more useful and faithful).
- `net.Socket` methods (`socket.end()` etc.) are not wired into this construction
  site — the listener receives an inspect/`write` handle, but `socket.end()`
  references an undeclared `@__kml_net_sock_close` here. Left as a V1 limitation
  (the listener can still read `err`/inspect the socket); wiring the full socket
  method surface is follow-on work.

## Verification

- New E2E tests (`tests/http_test.go`): `TestE2EHTTPClientErrorListenerFires`
  (a truncated request → the listener records `count=1`, `code=ECONNRESET`,
  reported back through a later normal request) and
  `TestE2EHTTPClientErrorDefault431` (header overflow, no listener → the 431
  default). Manual repros also confirmed overflow-with-listener
  (`HPE_HEADER_OVERFLOW`), a normal request unaffected, and a clean zero-byte
  close firing nothing.
- New example `examples/http/client_error_event.ts` (self-driving via `net`),
  runs clean and prints `clientError: ECONNRESET`.
- Full `TestE2EHTTP*` suite green; `go build`/`go vet` clean.
- Stage 2 (`'error'`/`EADDRINUSE`) remains — see TDD-00215.
