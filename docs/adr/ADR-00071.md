# ADR-00071: `-mm=gc` — Boehm GC mode

- **Relations**: Implements [TDD-00001](../tdd/TDD-00001.md)
- **Date**: 2026-07-28

## Context

[TDD-00001](../tdd/TDD-00001.md) scopes memory management as three mutually-exclusive compilation modes selected by a not-yet-built `-mm` flag: `manual` (already shipped — `Memory.free(x)`, [ADR-00030](ADR-00030.md)), `gc` (Boehm GC), and `auto` (compiler-inserted frees, no runtime collector — still not started). `STATUS.md`'s Roadmap has flagged memory management as the most pressing of this project's three structural gaps: `http.listen`'s stack-safety bugs are fixed and the server survives a 100,000-request load test ([ADR-00052](ADR-00052.md)), but every one of those requests still permanently grows the heap, so a long-running process eventually gets OOM-killed regardless. This ADR builds `gc` mode to close that gap. `auto` mode stays out of scope.

## Investigation

**TDD-00001's original sketch for `gc` mode turned out to be wrong.** It proposed swapping the declared symbol in `ensureMalloc()`/`ensureRealloc()` (`runtime.go:25-30`, `53-58`) from `@malloc`/`@realloc` to `@GC_malloc`/`@GC_realloc`. Grepping the actual call sites found this wouldn't work at all: every allocation across the codebase hardcodes the literal IR text `call ptr @malloc(...)` (128 sites), `@realloc(...)` (17), `@free(...)` (14), `@calloc(...)` (2) directly via `fmt.Sprintf`, across 16 files — `ensureMalloc()` et al. only ever emit a one-time `declare`, with zero influence on what a call site actually invokes. Editing what gets *declared* would just declare an unused second symbol; every existing call site would keep calling libc's real `malloc`.

Considered rewriting all ~161 call sites to reference a mode-dependent symbol name (threaded through a shared Go helper). Rejected: mechanical but high-touch and error-prone across 16 files, for no benefit over the alternative below.

**Decided instead on a link-time allocator shim**: a small C source, compiled in and linked only when `-mm=gc` is set, that *defines* `malloc`/`calloc`/`realloc`/`free` as thin wrappers over `GC_malloc`/`GC_realloc`/`GC_free`. Since the `.ll`-derived object's references to those symbols are otherwise undefined, and this shim is the only thing in the link that defines them, this needs no special linker flags (`-flat_namespace`, `--defsym`, `LD_PRELOAD`) on either Linux or macOS — confirmed empirically (see Verification) via `nm`/`otool -L` that `malloc` resolves to the shim's own definition, not libc's, on macOS, and via `nm` on the Alpine/musl Docker build that the same holds there. This also means **zero changes were needed to any of the 161 existing call sites**, and `Memory.free(x)` ([ADR-00030](ADR-00030.md), `emit_memory.go`) automatically became "release to the collector early" in `gc` mode for free, since its `call void @free(...)` now resolves to the shim's `GC_free`-backed definition — Boehm documents `GC_free` as always safe to call explicitly, as a latency optimization.

One nuance considered and set aside: this shim technique doesn't make *third-party* libraries' (e.g. libcurl's) internal allocations GC-managed on macOS, the way ELF's flatter symbol resolution would on Linux (Mach-O's two-level namespace binds a shared library's own internal calls to its own dependencies at its own link time, not the main executable's). Concluded this doesn't matter: libcurl already frees its own internal buffers correctly with plain, paired `malloc`/`free` calls — the actual problem this feature solves is this compiler's *own* emitted allocations never being freed, which the shim covers identically and completely on both platforms. Full Linux/macOS parity was achievable without ever needing to reach for that distinction.

**`http.listen`'s concurrent fibers surfaced a second, real correctness gap.** `http.listen`'s connections ([TDD-00006](../tdd/TDD-00006.md) Part 2) each run on a `ucontext_t` fiber with its own `malloc`'d 64KB stack (`runtime.go:__kml_http_append_conn`). Reasoned through two candidate concerns:

1. Whether Boehm's conservative scanner would find pointers a suspended fiber left sitting in its own stack buffer at all. Concluded yes, automatically: since that stack buffer is itself allocated via the same shimmed `malloc` and stays reachable via the global connection array (itself a root, being static data), Boehm's ordinary heap-content tracing already scans it like any other managed block — no extra registration needed for this part.
2. Whether a collection triggered *while a fiber is actively running* is safe. Concluded no, this is a real, separate risk: Boehm's *root*-stack scan walks from the live SP register to the registered `GC_stackbottom` — the *original* process stack's address, set once at program start. If the CPU's SP currently points into a fiber's malloc'd stack block (because `swapcontext` physically switched onto it), that scan walks between two arbitrarily distant, unrelated addresses, very likely reading unmapped memory.

Confirmed this is a real crash, not a theoretical one, with a negative-control experiment (see Verification): temporarily disabling the fix and re-running the concurrency test crashed the server ("connection reset by peer") on every one of several repeated runs.

**The fix**: repoint the global `GC_stackbottom` at a fiber's own stack-high address immediately before `swapcontext`-ing into it, and restore it to the original process stack's address immediately before switching back to `@__kml_main_ctx`. Exactly 3 `swapcontext` call sites needed this, confirmed by direct reading of `runtime.go`: the initial fiber launch (`__kml_http_append_conn`), the event loop's resume scan (`__kml_event_loop_run`'s `rresume` block), and the yield-back-to-main path (`ensureFetchAsync`'s `__kml_await_fetch`, `doyield` block).

## Decision

Implemented:

- A new `-mm=manual|gc` flag (`main.go`), validated right after `flag.Parse()` alongside the existing `-static`/`GOOS` guard. `auto` is rejected with an explicit "not implemented yet" message rather than a generic unrecognized-value error, since it's a real, scoped-but-unbuilt future value, not a typo.
- `Emitter.SetMemMode(mode string)` / `isGCMode() bool` (`emitter.go`) — a setter, not a constructor argument, so none of the dozens of existing zero-arg `NewEmitter()` call sites needed to change.
- `codegen/llvm/gcsrc/gcshim.c` (embedded via `codegen/llvm/gcshim.go`'s `//go:embed` into `GCShimSource`): the four forwarding functions plus a `__attribute__((constructor))` function calling `GC_INIT()`, guaranteeing initialization before `main()`'s first instruction regardless of allocation order.
- `codegen/llvm/gclocate.go`'s `LocateGC()`: tries `pkg-config --exists bdw-gc` then `gc` (the two names actually seen — Homebrew's `bdw-gc` formula and Alpine's `gc-dev` package both ship a `bdw-gc.pc`; Debian/Ubuntu's `libgc-dev` ships neither, ships no `pkg-config` file at all in fact, and falls through to the bare `-lgc` fallback, which works there since headers/libs land in default search paths). Deliberately avoids hardcoding any Homebrew prefix path (breaks Intel Macs) — `pkg-config` is the portable answer.
- `EmitProgram`'s Pass 3 (`emitter.go`, right after the existing `@__argv_ptr`/`@__argv_len` setup): when `isGCMode()`, declares `@GC_stackbottom` (external) and an internal `@__kml_gc_orig_stackbottom`, snapshotting the original value.
- The 3 `swapcontext` sites in `runtime.go`, each gated on `e.isGCMode()`, emitting nothing at all in `manual` mode.
- `main.go`'s clang invocation writes the shim out next to the `.ll` file and appends `LocateGC()`'s cflags/libs, only when `-mm=gc`. `-lgc` is added directly here, not via the existing `requireLink`/`LinkLibs()` demand-driven mechanism (curl, libm) — `gc` mode is a whole-binary choice, not tied to one builtin being used.
- `tests/compiler_test.go`'s `buildBinaryGC` mirrors this exact logic (calling the same `llvm.LocateGC()`/`GCShimSource`), specifically to avoid the dual-clang-invocation drift risk [ADR-00020](ADR-00020.md) already flagged once for `buildBinary`/`buildBinaryMultiFile` vs. `main.go`.

## Implementation notes

Files touched: `main.go`, `codegen/llvm/emitter.go`, `codegen/llvm/runtime.go`, `codegen/llvm/gclocate.go` (new), `codegen/llvm/gcshim.go` (new), `codegen/llvm/gcsrc/gcshim.c` (new), `tests/compiler_test.go`, `tests/memory_gc_test.go` (new), `tests/http_test.go` (added `startHTTPServerGC`), `examples/memory/memory_gc.ts` (new), `docker/Dockerfile.gc` (new), `docker/hello_gc.ts` (new), `.github/workflows/release.yml`, `STATUS.md`, `README.md`, `docs/tdd/TDD-00001.md` (Status line only), `docs/tdd/README.md` (index), `docs/adr/README.md` (index).

**`gcshim.c` had to live in its own subdirectory** (`codegen/llvm/gcsrc/`, not directly in `codegen/llvm/`) — a `.c` file placed directly inside a Go package directory makes `go build` demand cgo ("C source files not allowed when not using cgo or SWIG"), even though nothing about this feature actually uses cgo (the file is only ever read via `//go:embed`, never compiled by the Go toolchain itself). Moving it one level down, into a directory with no `.go` files at all, sidesteps this entirely — `go build` doesn't scan it as a package.

**Boehm's `GC_malloc` always returns zeroed memory**, unlike libc's `malloc` — this is why the shim's `calloc(nmemb, size)` is just `GC_malloc(nmemb * size)` with no separate zeroing step; Boehm's public API has no distinct `GC_calloc`.

**Two of the three `swapcontext` sites live inside plain Go string-concatenation-built IR blobs** (`__kml_http_append_conn`, `__kml_event_loop_run` — backtick literals with `+ fmt.Sprintf(...) +` splices for numeric layout constants only), so the conditional GC fixup could be spliced in as a plain Go string variable. The third (`ensureFetchAsync`'s `__kml_await_fetch`) was a single large `e.emitGlobal(\`...\`)` raw-string call with no existing `Sprintf` — converting it to `fmt.Sprintf` to inject the conditional required escaping every existing `%` in the rest of that function's IR text to `%%`, done carefully to avoid corrupting any of its `getelementptr`/`phi` instructions.

## Side effects discovered

None new beyond what TDD-00001 and TDD-00006 already track (the pre-existing "fiber ctx/stack slots are never freed, tombstoned forever" leak is unrelated to and unaffected by this change — those buffers are simply always reachable, GC or not, so this ADR doesn't change that behavior either way).

## Verification

- `go build ./...`, `go vet ./...` — clean.
- Manual smoke test: `./klainmain -mm=gc -o /tmp/gctest examples/...` compiles and runs correctly; confirmed via `nm`/`otool -L` on macOS that `_malloc` is a locally-defined (`T`) symbol (the shim), not an undefined import from libSystem, while `_GC_malloc` is correctly imported from `libgc.dylib`. Confirmed the inverse for a `manual`-mode build (`_malloc` undefined, imported from libSystem as normal).
- `-mm=auto` and `-mm=bogus` both rejected at the CLI with the expected error messages and a non-zero exit code.
- `tests/memory_gc_test.go`'s `TestE2EGCModeCorrectnessUnderChurn`: a 2,000,000-iteration loop churning ~216MB of throwaway string concatenations under `-mm=gc` produces the exact correct final checksum.
- `TestE2EGCModeBoundsMemory`: the same churn program's peak RSS (parsed from `/usr/bin/time`'s macOS/Linux-specific output) stays under 100MB against ~216MB actually allocated — measured in practice at ~2.3MB peak vs. ~388MB peak for the equivalent `manual`-mode build, a stark, direct confirmation that real collections are happening.
- **Negative control, run before considering the fiber fix done**: temporarily reverted the `GC_stackbottom` fixups at all 3 `swapcontext` sites (kept `-mm=gc` itself, i.e. Boehm still active) and re-ran `TestE2EHTTPListenGCModeConcurrentChurn` three times — the server crashed every single time ("connection reset by peer" — a SIGSEGV from the client's point of view, the same failure shape [ADR-00052](ADR-00052.md) documented for its own, different stack-safety bug). Restored the fix and confirmed the same test then passes consistently across 5 repeated runs.
- `TestE2EHTTPListenGCModeConcurrentChurn`: 6 concurrent requests, each churning ~14.4MB inside an `http.listen` handler under `-mm=gc`, all return correct, distinct responses.
- `go test ./...` — full suite green (145s).
- `make examples` — 62/62 passing, including the new `examples/memory/memory_gc.ts` (compiled in the default `manual` mode `make examples` uses, per TDD-00001's "opt-in dependency" requirement — its output is identical either way; only the memory profile differs).
- `docker build -f docker/Dockerfile.gc . && docker run --rm ...` — built and ran successfully against `alpine:3.21`/musl, confirming full Linux parity independent of the macOS dev-machine testing above (note: 3 stages, not `FROM scratch` like `docker/Dockerfile`'s `--static` demo — Alpine ships no `gc-static` package, so `-mm=gc` here links dynamically against `libgc`; the final stage is a minimal Alpine image with just that shared library installed, mirroring `docker/Dockerfile.fetch-test`'s `dynamic-fetch-demo` target rather than its static one). Also surfaced and fixed an unrelated Docker-recipe mistake along the way: `golang:1.26-alpine`'s clang can't link at all ("posix_spawn failed", reproduced even for a plain `manual`-mode compile) — the working recipe (matching `docker/Dockerfile`'s existing pattern) builds the Go compiler itself in `golang:1.26-alpine`, then compiles the `.ts` program in a separate, plain `alpine:3.21` stage.
