# TDD-00084: Unifying the async model — every `async` function a promise, one scheduler

- **Status**: Implemented ([ADR-00249](../adr/ADR-00249.md), [ADR-00250](../adr/ADR-00250.md), [ADR-00251](../adr/ADR-00251.md)) — all three parts done. **Part A** ([ADR-00249](../adr/ADR-00249.md)): every async function returns a real task-shaped promise; a non-suspending one uses the inline catch-and-settle wrapper (Option A2), so `.then`/`.catch`/`.finally`, the `Promise` combinators, and `await` (re-throwing a rejection) work on ordinary async results with **no fiber runtime or libcurl** linked. **Part B** ([ADR-00250](../adr/ADR-00250.md), Option B2): `__kml_event_loop_run` is task-aware and the single exit loop for a program mixing tasks with timers/EventSource/WebSocket/`http.listen`. **Part C** ([ADR-00251](../adr/ADR-00251.md)): `Promise.any` over raw fetches (mode 2 → first transport-success, else `AggregateError`) and destructured/nullable-scalar parameters in a genuinely-suspending fn (marshalled through the task args bundle). A rest parameter in a suspending fn stays a clean rejection (separate)
- **Date**: 2026-08-19

## Context

[TDD-00083](TDD-00083.md) delivered true suspension, the combinator set,
rejection, microtasks, `Promise.any` skip-rejected + `AggregateError`, and
`.then`/`.catch`/`.finally` value-chaining. Its remaining items all trace to a
**single root cause plus one structural split**, confirmed directly against
`codegen/llvm/` while closing the Stage-3 follow-on ([ADR-00248](../adr/ADR-00248.md)):

1. **A non-suspending `async` function is inlined synchronous code and throws
   *synchronously at call time*.** `emitAsyncPrologue` mallocs a result slot and
   the body runs top-to-bottom at the call site (emit_func.go / emit_async.go); a
   `throw` in that body propagates immediately instead of settling a rejected
   promise. Real JS: calling an `async` function *never* throws synchronously — it
   always returns a promise, rejected if the body throws. Consequence: only a
   **may-suspend** async fn (one that awaits a fetch or another such fn,
   `classifyAsyncSuspension`) produces a real task promise (`PromiseTask`); a
   non-suspending one produces a bare resolved slot that is not `PromiseTask` and
   never rejects.

2. **`.then`/`.catch`/`.finally` and `Promise.any` require a `PromiseTask`.**
   `emitPromiseThen` rejects any non-task promise (emit_promise_then.go); a
   resolved async-fn result or a `fetch` `Promise<Response>` cannot take a `.then`.
   This is a *direct* consequence of (1): those promises aren't tasks.

3. **Two mutually-exclusive program-exit loops.** `__kml_event_loop_run`
   (runtime_http.go — `select()` over the listener, connection fds, curl-multi
   fds, WS-client fds, folding timer/SSE/fetch deadlines) and `__kml_task_run_all`
   (runtime_task.go — drives the coroutine scheduler + microtasks) are dispatched
   in a priority chain at emitter.go:1013 (`usedEventSource||usedWSClient` →
   event loop; else `usedTaskRuntime` → task_run_all; else `usedTimers` →
   timer_drain). A program that mixes tasks with EventSource/WebSocket/`http.listen`
   gets one loop *or* the other, not both.

4. **Two smaller marshalling gaps.** `bindTaskParamsFromBundle`
   (emit_task_emit.go) rejects a destructured or nullable-scalar parameter in a
   genuinely-suspending fn; and `Promise.any` over `Array<Promise<Response>>`
   (raw fetches) is a clean rejection (emit_promise.go).

This is a genuine architectural fork (uniform-task cost vs. preserving the
no-fiber fast path, and which loop subsumes which), so it is scoped here before
implementation rather than as a bare ADR.

## Design

### Part A — every `async` function returns a real (task-shaped) promise

The keystone: a non-suspending `async` fn must return a settled `PromiseTask`
promise (resolved on normal return, **rejected** on throw), so every downstream
consumer (`.then`, `.any`, combinators, `await`) treats all async results
uniformly. Two options:

- **Option A1 — uniform tasks.** Every `async` call spawns a coroutine task
  (fiber), retiring `classifyAsyncSuspension` entirely. Simplest, most uniform;
  but pays a fiber stack + a `swapcontext` for the common no-await async fn that
  used the malloc-slot fast path — a real per-call cost on code that never
  suspends.

- **Option A2 (recommended) — keep the fast path, add a catch-and-settle
  wrapper.** A non-suspending async fn stays inline (no fiber), but its body is
  bracketed in a `setjmp` handler that settles the promise: normal completion
  stores the value and marks it fulfilled; a caught throw stores the error and
  marks it rejected (reusing the `__kml_task_reject` promise shape). The promise
  is tagged `PromiseTask` (already settled). No fiber for the fast path; the only
  added cost is one `setjmp` per non-suspending async call. `classifyAsyncSuspension`
  stays — it now selects *fiber task* vs *inline settled-task*, not *task* vs
  *not-a-task*.

Either way the `PromiseTask` distinction stops meaning "came from a fiber" and
starts meaning "is a real promise," so `emitPromiseThen`'s non-task rejection and
the combinators' `IsResponse`/resolved-slot special-casing collapse.

### Part B — one scheduler

Fold the coroutine scheduler and the `select()` I/O loop into a single
program-exit loop so a program mixing tasks + fetch + timers +
EventSource/WebSocket/`http.listen` drives everything to completion.

- **Option B1 — task loop absorbs I/O.** Give `__kml_task_sched_step` the
  `select()` body (I/O readiness + deadline folding) that `__kml_event_loop_run`
  has, and make `__kml_task_run_all` the single exit loop.

- **Option B2 (recommended) — event loop absorbs tasks.** `__kml_event_loop_run`
  already `select()`s over every I/O source and folds every deadline; add the
  task-resume scan + microtask drain to each iteration, and widen its termination
  condition to "no pending I/O *and* no active task *and* no pending
  microtask/timer." The event loop is the structural superset (it already pumps
  curl, which is how a task's `await fetch` makes progress today), so extending it
  is less invasive than teaching the task step to `select()`. Retire the
  emitter.go:1013 priority chain in favor of the one unified loop whenever any of
  {tasks, timers, fetch, SSE, WS} is used.

### Part C — the derived unblocks

Once A and B land, the rest fall out:

- **Non-task `.then`/`.any`** — a resolved async-fn result and a `fetch`
  `Promise<Response>` are now `PromiseTask`s, so `emitPromiseThen` accepts them
  and the reaction machinery works unchanged.
- **`Promise.any` over raw fetches** — route the `IsResponse` case through the
  same first-fulfilled/`AggregateError` path Part A unifies (or a fetch-group
  variant of `__kml_task_await_first_fulfilled`).
- **Destructured/nullable params in a suspending fn** — extend
  `taskBundleFields`/`bindTaskParamsFromBundle` to carry a nullable-scalar `{i1,T}`
  slot and to run the existing `unpack*PatternInto` against a bundle field, the
  same machinery the non-suspending path already uses.

## Staged delivery (ordered by dependency)

1. **Part A (Option A2)** — non-suspending async fn → settled `PromiseTask`
   (catch-and-settle wrapper). Unblocks non-task `.then`/`.catch`/`.finally` and
   `Promise.any` over non-fiber async results with no scheduler change.
2. **Part B (Option B2)** — unify the exit loops; a mixed tasks + I/O program runs
   under one loop.
3. **Part C** — `.any` over raw fetches, and destructured/nullable param
   marshalling in a suspending fn.

## Open questions

- Part A: does the catch-and-settle wrapper need to run the microtask drain at
  the non-suspending async fn's completion (a `.then` attached to its result),
  or does the single exit-loop drain suffice? Prototype both.
- Part B: termination — the unified loop must not exit while a task is parked on
  an I/O source whose readiness the loop itself provides; state the exact
  "still-live" predicate over {conns, curl handles, WS fds, timers, active tasks,
  microtasks} before implementing.
- Part B: does `http.listen(...)`'s own inline `__kml_event_loop_run` (which never
  returns) coexist with a task program, or does a server-plus-tasks program need
  the unified loop reachable from the listener path too?
- Part A: with A2, is there any observable ordering difference between a
  settled-inline async result and a fiber-task result feeding the same
  combinator? Confirm the microtask/settlement order matches.
