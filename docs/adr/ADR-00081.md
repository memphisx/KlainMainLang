# ADR-00081: `path` module (join, resolve, dirname, basename, extname, parse, format, isAbsolute, sep, delimiter)

- **Date**: 2026-07-30

## Context

The 2026-07-30 Node.js APIs audit ([README.md](../status/README.md)) found
`path` completely untracked (0/8, confirmed zero references anywhere in
`codegen/llvm/`), despite being flagged as directly relevant to this
project's own stated CLI-application priority
([CLAUDE.md](../../CLAUDE.md)'s Project direction): almost any real
file-handling CLI script needs to join/resolve/split paths, and there was no
way to do that portably at all — a program would have to hand-roll string
concatenation with a hardcoded `/`. Picked up as the next roadmap item after
that audit, alongside `os` (still open, see [OS.md](../status/OS.md)).

## Investigation

- Confirmed via `grep` across `codegen/llvm/`, `parser/`, `lexer/` that
  nothing named `path`/`__kml_path_*` existed anywhere before this change.
- Considered writing the string-manipulation logic (segment splitting,
  `..`-resolution, suffix stripping) as an embedded C source file compiled
  alongside the emitted `.ll` — `gcshim.go`'s `//go:embed gcsrc/gcshim.c`
  establishes exactly that pattern for `-mm=gc`'s allocator shim. Rejected:
  that pattern is conditional (only linked under `-mm=gc`); making it
  unconditional for every binary would be a bigger architectural change than
  this feature needs, and every other domain in this codebase (including
  algorithmically-comparable ones — `readdir`'s realloc-doubling directory
  listing in `runtime_fs.go`, `trim`'s character-scan loop in
  `runtime_strings.go`) hand-emits its C-runtime helpers as LLVM IR text via
  `emitGlobal`. Followed that existing convention instead.
- Read `runtime_http.go`'s `__kml_event_loop_run` and `runtime_fs.go`'s
  `__kml_fs_readdir` for the established idiom for a hand-rolled loop inside
  a standalone `define` block: `alloca` + `load`/`store` for mutable loop
  state (not SSA `phi` chains — `trim`'s helper uses `phi`, but the
  memory-based style is more directly extensible to the multiple mutable
  variables `path.join`/`.resolve`'s segment-normalization stack needs) and
  a `{ptr, i64, i64}` malloc'd struct with `realloc`-doubling growth for a
  growable array, identical in shape to `readdir`'s own `bufslot`.
- Read `emit_url.go`'s `URLType()`/`storeField` pattern (building a plain
  heap object with `malloc(StructSize())` + `getelementptr`/`store` per
  field) for `path.parse`'s `{root, dir, base, ext, name}` return shape, and
  its `emitStrBranch` helper (alloca+branch+merge for a `ptr` result) reused
  directly for `path.parse`'s `root` field and `path.format`'s
  `base`/`dir` fallback logic.
- Worked out that `path.resolve`'s real algorithm (Node processes arguments
  **right to left**, stopping at the first absolute segment) is exactly
  equivalent to processing **left to right** starting from `cwd()`, where
  any segment starting with `/` *resets* the accumulator instead of
  appending to it — both formulations keep only the last absolute segment
  seen plus everything after it. The left-to-right form unrolls at compile
  time (the call site's argument count is already known to
  `emitPathResolve`, so each argument becomes a small inline
  branch-and-merge in the *calling* function, using the same
  `freshLabel`/`emitLabel`/`emitAlloca` machinery `emitConditional`
  (ternary) already uses) rather than needing a genuine runtime loop over a
  dynamic argument array.
- Verified real Node's exact behavior directly with a live `node -e`
  process (`/Users/kyriakosbompotis/.nvm/versions/node/v26.3.0`) rather than
  assuming it from memory, for every function and a battery of edge cases
  (multi-slash collapsing, `..` above root, trailing slashes, dotfiles).
  This caught a real mismatch during that verification pass — see Side
  effects discovered.

## Decision

- **`path.join(...segments)`**: concatenates every argument with `/`
  between (`emitStringConcat`, already-existing Go helper, called
  repeatedly — no new low-level concat IR needed), then runs the result
  through a new `__kml_path_normalize(ptr raw, i1 is_absolute)` runtime
  helper. `is_absolute` is decided by the *first* argument alone (checking
  its own byte 0, not the concatenated raw string) so an empty leading
  segment can't manufacture a spurious leading `/`.
- **`path.resolve(...segments)`**: the left-to-right "reset on absolute"
  formulation described in Investigation, starting from
  `__kml_process_cwd()` (already existed, `runtime_process.go`). Always
  passes `is_absolute = true` to normalize (the accumulated raw path is
  absolute by construction).
- **`__kml_path_normalize`** (shared join/resolve backend, `runtime_path.go`):
  splits `raw` on `/` via a single character-scan loop, classifying each
  segment (empty → skip, `.` → skip, `..` → pop the last pushed segment
  unless it's itself `..` — in which case keep a leading `..` for a
  relative result, or drop it entirely for an absolute one since you can't
  go above root — anything else → push) onto a growable stack, then rejoins
  the stack with `/`, prefixed with `/` when absolute and defaulting to `.`
  (relative) or `/` (absolute) when the stack ends up empty.
- **`path.dirname(p)`** / **`path.basename(p, ext?)`**: each trims trailing
  slashes, then scans backward for the last remaining `/` — straight-line
  POSIX string logic, no segment stack needed. `basename`'s `ext` stripping
  matches real Node's own two-part rule, discovered empirically (see Side
  effects discovered): the entire `path` argument equaling `ext` returns
  `""`; otherwise a suffix match that would consume the *whole* basename is
  left unstripped (only a *partial* suffix match strips).
- **`path.extname(p)`**: calls `__kml_path_basename(path, null)`, then scans
  that basename backward for the last `.`; `""` if none found or if it's at
  index 0 (a dotfile's leading dot isn't an extension).
- **`path.parse(p)`**: `{root, dir, base, ext, name}`, a plain
  `ObjectType` (`PathParsedType()`, `types.go`) — `name` is computed by
  calling `__kml_path_basename(path, extname(path))` (reusing the
  ext-stripping machinery directly, rather than a separate substring
  routine, since "name" is exactly "base minus its extension").
  **`path.format(obj)`**: the inverse, matching real Node's own algorithm —
  `base` wins over `name`+`ext` when non-empty, `dir` falls back to `root`
  when empty, and `dir`+`base` are joined without a separator when `dir`
  equals `root` (so `/` + `foo` is `/foo`, not `//foo`).
- **`path.isAbsolute(p)`**: `p[0] === '/'` — a single byte load and compare,
  safe even for an empty string (every string in this compiler is a
  malloc'd, null-terminated buffer, so byte 0 always exists and an empty
  string's terminator simply compares unequal to `/`).
- **`path.sep`/`path.delimiter`**: compile-time constants `"/"` and `":"` —
  this compiler doesn't cross-compile (confirmed precedent:
  `process.platform`, `PROCESS-CLI.md`), so the Windows forms are never
  needed.
- `path` is dispatched the same way `process`/`fs`/`crypto` already are: a
  bare identifier recognized only inside a `MemberExpression`'s `Object`
  position (`emit_call.go`'s dispatcher, `emit_exprs_types.go`'s
  `inferExprType`, `emit_exprs_member.go`'s non-call property reads for
  `sep`/`delimiter`) — not a real declared variable, so it never needs
  resolver/parser-level special-casing.

## Implementation notes

- New files: `codegen/llvm/runtime_path.go` (`ensurePathNormalize`
  — emits `__kml_path_stack_append`, `__kml_path_stack_join`,
  `__kml_path_normalize_onesegment`, and `__kml_path_normalize` together
  under one used-flag, since nothing else calls the first three
  independently — plus `ensurePathDirname`, `ensurePathBasename`,
  `ensurePathExtname`) and `codegen/llvm/emit_path.go` (the
  Go-orchestrated emitters: `emitPathJoin`, `emitPathResolve`,
  `emitPathDirname`, `emitPathBasename`, `emitPathExtname`,
  `emitPathIsAbsolute`, `emitPathParse`, `emitPathFormat`,
  `emitPathStartsWithSlash`).
- `types.go`: `PathParsedType()`, following `ResponseType()`/`URLType()`'s
  established shape (a plain `ObjectType` with a descriptive field list).
- `emitter.go`: five new `used*` flags (`usedPathNormalize`,
  `usedPathDirname`, `usedPathBasename`, `usedPathExtname`).
- Wiring: `emit_call.go` (dispatch block, placed before the `crypto` block),
  `emit_exprs_types.go` (both the call-return-type switch and the
  `sep`/`delimiter` non-call property-type switch), `emit_exprs_member.go`
  (the `sep`/`delimiter` value read, placed right after the existing
  `isProcessEnvExpr` check).
- `__kml_path_basename`'s early "whole path equals ext" check
  (`checkwholepath` block) runs a `strcmp` against the *raw, untrimmed*
  `path` argument, before any trailing-slash trimming — this matters
  because it's checking the literal call argument (e.g.
  `basename("foo.js", "foo.js")`), not the computed basename segment.
- The segment-normalization stack (`__kml_path_stack_append`) never frees
  popped or superseded entries — consistent with this compiler's default
  `manual` memory-management mode leaking everything by design (a bounded
  per-call allocation, the same tradeoff `ADR-00076`'s `new URL(...)`
  already documents for its own part strings); moot under `-mm=gc`.

## Side effects discovered

Verifying `path.basename(p, ext)` against real Node surfaced a genuinely
non-obvious rule that a naive "strip the suffix if it matches" implementation
gets wrong: `path.basename(".js", ".js")` returns `""`, but
`path.basename("/foo/.js", ".js")` returns `".js"` (unchanged) — same
apparent suffix match, different outcome, because Node special-cases "the
*entire input path* equals ext" (→ `""`) separately from "the *computed
basename* equals ext" (→ left unstripped). The first implementation attempt
here only had the second rule and returned `""` for both cases. No existing
test caught this (the module didn't exist before), but it's exactly the
kind of easy-to-misjudge library-shim behavior worth calling out explicitly
— fixed before landing, not deferred.

## Verification

- Manual smoke testing throughout implementation: `/tmp/path_smoke.ts`
  (join/resolve/dirname/basename/extname/isAbsolute/parse/format/sep/delimiter)
  and a dedicated `/tmp/basename_edge.ts` for the `ext`-stripping rule,
  each diffed line-by-line against the real output of the same calls run
  through a live `node -e` process — zero mismatches on the final tree,
  including multi-slash collapsing (`"a//b///c"` → `"a/b/c"`), `..` above
  root (`resolve("/a", "..", "..", "b")` → `"/b"`), and trailing-slash
  dirname (`"/a/b/c/"` → `"/a/b"`).
- `tests/path_test.go`: 8 new E2E tests (`TestE2EPathJoin`,
  `TestE2EPathResolve`, `TestE2EPathDirname`, `TestE2EPathBasename`,
  `TestE2EPathExtname`, `TestE2EPathIsAbsolute`, `TestE2EPathParseFormat`,
  `TestE2EPathSepDelimiter`), covering the same cases confirmed manually
  above.
- `examples/path/path.ts` added, with inline comments giving the expected
  output per line, and run via `make examples` (68/68, up from 67).
- `go build -o klainmain . && go test ./...` (all green, ~190s) on the
  final tree.
