# TDD-00066: Tuple types (`[T0, T1, ...]`)

- **Status**: Implemented (V1) — see [ADR-00201](../adr/ADR-00201.md)
- **Date**: 2026-08-17

## Context

This compiler has no tuple type. That gap was papered over in several places with a documented stand-in: `Map.entries()`/`Array.entries()`/`Object.entries()` return an array of named-field objects (`{key, value}`/`{index, value}`) rather than a real `[K, V]` tuple, iterated as `for (const e of m.entries()) { e.key; e.value }` (see [ADR-00053](../adr/ADR-00053.md)/[ADR-00057](../adr/ADR-00057.md)); `new Map(entries)` is rejected because "each entry would need a real `[K, V]` tuple type"; and the standard idiom `for (const [k, v] of Object.entries(obj))` is a clean rejection (`cannot array-destructure a for-of element of non-array type`). `docs/status/README.md`'s own type-representation table already earmarks the intended shape: **"Tuple types `[number, string]` → Fixed-size struct."**

## Design

A tuple is a fixed-arity, heterogeneous, positional aggregate — structurally an object with positional slots. Represent `[T0, T1, ...]` as an ordinary **`ObjectType` with synthetic positional field names `"0"`, `"1"`, ...** plus an `IsTuple` marker (the same "flag a generic ObjectType" pattern classes, errors, `Symbol`, URL, entries objects, etc. already use). This reuses `StructIR`/`StructSize`/`FieldIndex`/GEP/field storage, object-literal construction, object parameter/return/field passing, spread, and `structuredClone` with no new storage machinery — only the handful of sites that must treat a tuple *differently from* a plain object need `IsTuple`:

- **Index access** `t[0]` / `t[1]` — a compile-time-constant index maps to field `"i"`; a non-constant index is a clean rejection (its element type isn't statically knowable). This is what array-index (`emitIndex`) must special-case, since a tuple has no array backing buffer.
- **Destructuring** `const [a, b] = t` and `for (const [a, b] of tuples)` — bind pattern position *i* to field `"i"`.
- **Rendering** — `console.log`/template/JSON serialize a tuple as an array literal (`[e0, e1]`), matching real JS, not as an object.

**Entries become real tuples.** `Map.entries()` → `[K, V][]`, `Array.entries()` → `[number, T][]`, `Object.entries()` → `[string, string][]` (values still stringified — a heterogeneous object's value type is a union this compiler can't yet form; the tuple *shape* is what unblocks the standard idiom). The `{key,value}`/`{index,value}` object convention — and its `.key`/`.value`/`.index` access — is replaced; the docs already framed it as a stand-in awaiting exactly this. In-repo `.key`/`.value`/`.index` usages migrate to destructuring / index access in the same change.

### V1 scope

In: tuple type annotations (`[T0, T1, ...]`, and `[T0, T1][]`); tuple literals in a tuple-typed context (declaration initializer, and the entries builders); constant-index read; array-pattern destructuring (declaration, assignment, and `for...of`, including a tuple element inside a nested pattern); rendering as an array; tuple as a function parameter/return/object field (free, via the object machinery); the three `.entries()` methods.

Out (deferred, each a clean rejection or unchanged behavior): tuple element *assignment* (`t[0] = x`); rest/optional/named tuple elements (`[string, ...number[]]`, `[a: string, b: number]`); non-constant index; `.length` and array methods on a tuple (it is not array-backed); a tuple nested in `any`/a union; `new Map(entries)` (a natural, separately-shippable follow-on now that `[K, V]` exists); spreading a tuple into a call.

### Alternatives considered

- **A dedicated array-backed representation** (a real backing buffer like `number[]`): rejected — a tuple is heterogeneous, so a homogeneous element buffer can't hold it; the struct representation is the only fit and reuses far more.
- **Keep entries as objects, only add positional-object destructuring** (the "#3a bridge"): lower-risk and non-breaking, but leaves the compiler without a real tuple type, so `t[0]`, tuple-typed variables, and eventually `new Map(entries)` all stay impossible. Rejected in favor of the real type the docs already promised.

## Open questions

- **Object.entries value type**: kept as `string` (stringified) in V1. A faithful `[string, <union of field types>]` needs the union box as an object-field/array-element type, still out of scope ([TDD-00043](TDD-00043.md)); revisit if/when that lands.
- **Tuple element mutation**: read-only in V1. `t[0] = x` on a fixed-shape struct is trivially a field store, so this is a small, safe follow-on rather than a design fork.
