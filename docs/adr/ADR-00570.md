# ADR-00570: process.memoryUsage().rss is the instantaneous RSS

- **Relations**: Extends ADR-00507
- **Date**: 2026-09-01

## Context

`process.memoryUsage().rss` read `getrusage(2)`'s `ru_maxrss`, which is the
process's **peak** resident set size over its lifetime. Real Node's
`memoryUsage().rss` is the **instantaneous** resident set — it can go down as
well as up. So a program watching `rss` to observe live memory pressure saw a
monotonic high-water mark instead of the current value. Disclosed as a caveat.

## Decision

Add `__kml_current_rss_bytes() -> i64` reading the live resident set, and have
`emitProcessMemoryUsage` call it instead of `getrusage`:

- **Darwin**: `task_info(mach_task_self(), MACH_TASK_BASIC_INFO=20, …)` →
  `resident_size` (u64 at offset 8 of `struct mach_task_basic_info`, a 12-word
  info block). `mach_task_self_` is the extern task port.
- **Linux**: `/proc/self/statm` field 2 (resident pages) × 4096. The 4 KiB page
  size holds on x86-64 and arm64 Linux; a read failure returns 0.

## Side effects discovered

None. The V8-heap fields (`heapTotal`/`heapUsed`/`external`/`arrayBuffers`)
still report 0 (no managed heap) — that remains the row's sole caveat. `getrusage`
is no longer pulled in by `memoryUsage`.

## Verification

`TestE2EProcessMemoryUsageRssPositive` extended to allocate ~1M elements between
two readings and assert `rss` grew (a peak-only value would already be at its
max). Compared against real Node's live-`rss` semantics. Verified on Mac (Apple
Silicon) and on Linux — both aarch64 and x86-64 glibc (via Docker
`golang:latest`), where `rss` reads a positive value from `/proc/self/statm` and
grows across the allocation.
