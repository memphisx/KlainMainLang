# ADR-01151: Generic arrow functions, function expressions and object-literal methods

- **Relations**: `Implements TDD-00230` (P3.1, the TS2304 blocker); `Extends ADR-00469`
- **Date**: 2026-09-25

## Context

The type-position TS2304 check (ADR-01152) needs every type parameter
bound. A generic arrow was not:

- `<T>(x: T): T => x` parsed as a `<T>` type assertion applied to a plain
  arrow, whose `T`s named nothing. Codegen rejected the call
  (`argument 1 has a type incompatible…`).
- `<T,>(x: T) => x` did not parse.
- `function <U>(v: U) { … }` as an expression dropped its type
  parameters without erasing their uses.
- `{ twice<W>(w: W) { … } }` did not parse.

## Investigation

- **The assertion branch** (`parser_exprs.go`) read any leading `<` in a
  unary position as `<T>expr`. tsc reads `<T…>(…) =>` as a generic arrow
  in a `.ts` file.
- **A generic class method** has its type parameters erased to `any` in
  its annotations (`ast.EraseTypeParams`, ADR-00469). Its type nodes keep
  the references for the checker.
- **Object-literal methods** took the method-shorthand branch only at `(`.

## Decision

- **Generic arrows.** `genericArrowAhead` recognises a generic arrow: a
  name then `,` / `>` / `extends` / `=`, a balanced `<…>` (`>>` and `>>>`
  counted as nested closers), then a parenthesized group followed by `=>`
  or a return type. Anything else stays an assertion.
  `parseGenericArrow` parses the list with `parseTypeParameterNodes` and
  records it on `ArrowFunction.TypeParams`. It then erases the parameters
  in the arrow's annotations, as a method's are.
- **Function expressions and object-literal methods** erase their parsed
  type parameters the same way (`eraseTypeParams`) at every
  `NewFunctionExpression` site. The method-shorthand branch also takes a
  `<`.
- **The parser records every type parameter name it parses**
  (`Program.TypeParamNames`): declaration lists, type-node lists,
  `infer U` and a mapped type's key. The resolver merges them across
  files.

## Side effects discovered

- **44 more TypeScript corpus cases parse.** One, `controlFlowGenericTypes.ts`,
  showed a checker false positive on a constrained type parameter. Fixed
  in ADR-01152.

## Verification

- **`TestE2EGenericArrowFunctions`** runs each form with Node's output:
  `<T>`, `<T,>`, a constraint with a default, a function expression, an
  object-literal method, and a `<number>(…)` assertion that stays an
  assertion.
- **Example:** `examples/generics/generic_arrows.ts`, same output as
  Node; tsc accepts it.
- **tsdiag:** 6,539 cases checked (was 6,495), no new false positives.
- **Gates (with ADR-01148–01153):**
  - Test262: strict 7,032 and js 7,832 (the handover's were 7,034 and
    7,825), no clang failures in either lane. The two strict files lost
    call `str.slice(obj, obj2)` with objects for `number` parameters,
    which tsc rejects (TS2345).
  - Node suite: strict 61, js 63, unchanged.
  - `make examples`: 360 pass. `chained_listen` timed out once, its
    known intermittent hang, and passes 3 of 3 runs alone.
  - `make test-par`: only the four macOS `-mm=gc` failures.
