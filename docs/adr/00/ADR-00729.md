# ADR-00729: `process.kill(pid, 'SIGTERM')` — signal names, not just numbers

- **Relations**: Extends [ADR-00026](ADR-00026.md) (`process.kill`), [ADR-00728](ADR-00728.md) (found while writing the Windows SIGTERM variant)
- **Date**: 2026-09-06

## Context

Node's canonical form is the signal *name*: `process.kill(pid, 'SIGTERM')`. This compiler accepted only a number. A string argument was coerced to `i64` without conversion, so the emitted call carried a `ptr` where the runtime expected `i64` and clang rejected the module ("constant expression type mismatch"). The Windows SIGTERM test of ADR-00728 was the first program in the suite to use the name form.

## Decision

- A literal name resolves at compile time through a per-host table (`signalNumbers`, `runtime_process.go`): the names Node's `os.constants.signals` exposes on that host with the numbers its `kill()` takes — Linux numbers on Linux and on Windows (the shim accepts Linux numbers; `SIGBREAK` is libuv's 21), Darwin numbers on macOS. An unknown literal is a compile-time rejection (`unknown signal`), the counterpart of Node's `ERR_UNKNOWN_SIGNAL`.
- A dynamic string goes through `__kml_signal_from_name`, a `strcmp` chain over the same table emitted on demand; an unknown name yields `-1`, and `kill()` then fails with `EINVAL` through the existing throw path.
- A number is unchanged.

## Implementation notes

- `codegen/llvm/emit_process.go` (`emitProcessKill`), `runtime_process.go` (`signalNumbers`, `ensureSignalFromName`), `emitter.go` (the once-flag).
- `tests/process_test.go`: literal (`SIGTERM` → 15 in the thrown message), dynamic (`SIGINT`/`SIGKILL` → 2/9), unknown-name rejection.

## Side effects discovered

- The thrown message still prints the number (`kill(pid=…, signal=15): …`); Node's message carries the name. Left as is — the number is what the OS was asked for.

## Verification

Windows 11 and Linux (Docker lane, see [ADR-00731](ADR-00731.md)): the three new tests pass; `TestE2ESignalSigtermIsTerminateOnWindows` uses the name form.
