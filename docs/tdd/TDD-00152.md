# TDD-00152: Nested function declarations inside a lexical block

- **Status**: Implemented

- **Date**: 2026-09-01

## Context

Nested function declarations were V1-scoped ([TDD-00057](TDD-00057.md)) to the
enclosing function/arrow body's own *immediate* statement list — a `function`
declared one block deeper (inside an `if`/`for`/`while`/bare block) was a clean
compile error (`nested function declarations are only supported directly in an
enclosing function's own body`). Declaring a helper inside a conditional or loop
body is common real-world code, so lifting the one-block-deeper restriction is a
worthwhile completion — this was [TDD-00057](TDD-00057.md)'s own remaining open
question, orthogonal to [TDD-00129](TDD-00129.md)'s capture work (which it now
composes with).

## Design

A lexical block is its own scope for nested function declarations. The exact
per-body mechanism the enclosing function already runs — `pushNestedFuncScope`
(pre-scan the statement list, register each declaration under a mangled name,
classify capturing vs. non-capturing, re-infer unannotated return types to a
fixed point) — is reused at **block** granularity:

- The `*ast.BlockStatement` emit case pushes a nested-func scope over the block's
  own statements before emitting them and pops it at block exit. Because
  `if`/`for`/`while`/`do-while` bodies and `try`/`catch`/`finally` blocks all
  route their block through `emitStmt`, this single site covers them. A block's
  functions are popped when the block ends, so they don't leak out — faithful
  strict-mode block scoping.
- `switch` iterates its case bodies directly (bare cases aren't wrapped in a
  `BlockStatement`), so `emitSwitch` pushes one nested-func scope over *all*
  cases' statements — a switch body is a single lexical block in JS, so a
  function declared in one case is visible across cases (fallthrough).
- `resolveFuncRef` already searches nested-func scopes innermost-first, so a
  block-local function shadows an outer one and is invisible after the block.

### For-loop variable capture

A block-nested function that closes over a **C-style `for (let i …)` loop
variable** is rejected cleanly. The loop variable lives in a single alloca reused
across iterations; a closure over it would share the counter cell and corrupt the
loop (empirically: an infinite loop). This is the same per-iteration-binding
limitation arrow functions hit. Detection: `emitFor` records its init-declared
names in `activeForLoopVars` for the duration of the body; the block pre-scan
rejects a declaration whose free variables intersect that set — checked *before*
the capturing/non-capturing split, since a loop variable isn't an
`enclosingCapturables` binding (declared in the for-init, not a body statement)
and would otherwise be misclassified as non-capturing and emit a broken direct
call. The suggested fix in the message is to copy the loop variable to a `const`
inside the body and capture that (which works).

Capturing a for-loop *body local* (`const doubled = i * 2` then capturing
`doubled`), an enclosing parameter, or a `while`-loop context all work — only the
for-loop variable itself is special.

## Open questions

- **for-of / for-in specialized variants**: array-iteration `for…of` routes its
  body through the `BlockStatement` case, so block-nested functions work there,
  and `switch` is now covered by `emitSwitch`'s own scope. The residual is the
  specialized `for…of`/`for…in` iterator variants (generator/stream/Symbol.iterator
  paths) that iterate their statement list directly. Capturing such a loop
  variable is a clean rejection (or resolves correctly when the function also
  captures an enclosing binding), never a miscompile — so no correctness gap,
  only a coverage edge left for a follow-up.
- **Use-before-declaration** inside a block inherits TDD-00129 Stage 1's
  at-or-after-declaration limitation unchanged.
