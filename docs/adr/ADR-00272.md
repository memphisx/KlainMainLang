# ADR-00272: `for await...of` over a sync array; generic-type array-suffix parse fix

- **Relations**: Implements [TDD-00092](../tdd/TDD-00092.md); extends [ADR-00253](ADR-00253.md), [ADR-00269](ADR-00269.md) (`for await` paths); extended by [ADR-00277](ADR-00277.md)
- **Date**: 2026-08-20

## Context

Two items, the second a bug found while testing the first.

1. **`for await...of` over a sync array.** JS awaits each element of a sync iterable; the common
   case is an array of promises consumed sequentially. This compiler rejected any non-async-gen /
   non-`Symbol.asyncIterator` iterable.
2. **Generic-type array-suffix parse bug.** `const ps: Promise<number>[] = …` (and
   `Map<string, number>[]`) failed to parse — the `[]` was dropped and the parser reported the
   initializer missing. Surfaced writing a `for await` test with a typed array-of-promises.

## Investigation

- **for await array:** the `for await` gate in `emitForOf` (`emit_stmts.go`) rejected arrays. The
  array for-of loop shape (`resolveArrayForHOF` + index loop) and the shared task await
  (`emitAwaitTaskPromise`) already exist; only the per-element await before binding is new.
- **parse bug:** in `parseNonUnionType` (`parser_types.go`), the `Promise`/`Array`/`Set`/
  `EventEmitter` branch (line ~370) and the `Map` branch (line ~390) each `return` the generic
  `TypeAnnotation` immediately — *before* the array-suffix loop (line ~423). So `Foo<...>[]` never
  consumed its `[]`. The simple-name path handles `T[]`; the user-generic fallback path (line
  ~419) had the same early return. `parseTrailingArrayBrackets` already wraps a type in the
  ElemType-based array annotation for the `{...}[]` / `(fn)[]` forms.

## Decision

1. **for await array.** When `for await`'s iterable is an array, dispatch to a new
   `emitForAwaitOfArray`: loop by index, load each element, and if the element type is a `Promise`
   drive it via `emitAwaitTaskPromise` (re-throwing a rejection, so a rejected element propagates
   and stops the loop) — a plain value is an identity await — then bind the awaited value (or
   unpack a destructuring pattern). The bound type is the element type awaited (`T` for
   `Promise<T>`). A raw-fetch `Promise<Response>` element is a clean rejection.
2. **parse fix.** Route the `Promise`/`Array`/`Set`/`EventEmitter`, `Map`, and user-generic
   branches' results through `parseTrailingArrayBrackets` instead of returning directly, so a
   trailing `[]` wraps the generic in an array type exactly like every other `T[]`.

## Implementation notes

- `emit_generators.go`: `emitForAwaitOfArray` (mirrors `emitForAwaitOfAsyncIterable`'s binding /
  destructuring, with the array index loop and the per-element await).
- `emit_stmts.go`: the array branch in the `for await` gate.
- `parser_types.go`: three `return &ast.TypeAnnotation{…}` → `return parseTrailingArrayBrackets(p,
  source, &ast.TypeAnnotation{…})`.

## Side effects discovered

- **A named `function` declaration can't read a top-level `const`/`let`** (any type): `const x =
  5; function g() { console.log(x) }` fails with `undefined variable 'x__kml_mod0'`, because
  top-level statements are emitted into the synthetic `main()` (the variable is a `main()` local)
  while a named function is a separate top-level LLVM function with no access to `main()`'s locals.
  An **arrow function / closure captures it fine** (closure env), so `const h = () => …x…` works —
  the gap is specific to hoisted `function` declarations. A significant **pre-existing**
  architectural limitation (module-level variables would need promotion to true globals),
  undocumented until now and orthogonal to this work — flagged for its own future effort, not
  fixed here. (Tests here keep the `const` inside the consuming function, where it works.)
