# ADR-02061: A NUL is a character to the string builtins; Latin-1 base64

- **Date**: 2026-11-22

## Context

- Strings carry their byte length in a header, and `.length`, slicing,
  search, concatenation and `JSON.stringify` read it. Several C builtins
  used `strlen` instead and stopped at an embedded NUL: `toUpperCase`,
  `toLowerCase`, `normalize`, `trim`/`trimStart`/`trimEnd`,
  `encodeURI(Component)` and `btoa`/`atob`. Their comments said some
  strings had no header, which is no longer so.
- `btoa` encoded a string's UTF-8 bytes (`btoa("é")` was `w6k=`, Node
  `6Q==`) and accepted characters above U+00FF. `atob` returned its raw
  bytes, so a byte from 0x80 was no character (`atob("/w==")` was not
  `"\xff"`).

## Decision

- Those builtins take the length from the header.
- `btoa` reads each character as one byte (Latin-1) and throws the
  `InvalidCharacterError` DOMException for one above U+00FF. `atob`
  writes each decoded byte as one character (two UTF-8 bytes from 0x80).
- Their only callers are the JavaScript globals and methods, so no
  internal caller depends on the old byte semantics.

## Consequences

- NUL-holding strings and base64 round trips match Node in
  `TestE2EStringLocaleCase` and the base64 tests.
- Verified on Node304 (Linux x86-64).
