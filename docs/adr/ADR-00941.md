# ADR-00941: Array returns & closure captures share the header — reference semantics across every boundary (TDD-00213 Stage 3)

- **Relations**: Implements TDD-00213 Stage 3; Relates to ADR-00939, ADR-00940, TDD-00127, TDD-00212
- **Date**: 2026-09-14

## Context

Stages 1 and 2 (ADR-00939/00940) made local bindings and object/class fields
share an array's `{data,len}` header cell, so aliasing, `===` identity, and
mutation-visibility matched Node for those bindings. Two boundaries still
snapshotted:

- **Function returns.** The array return ABI was the inline `{ptr,i64}` aggregate
  (`ret {ptr, i64}`), so a function returning an existing array (`return g.arr`)
  handed the caller a *copy* of the data pointer/length. The caller minted a fresh
  header, so a later push didn't propagate back and `x === g.arr` was false:

  ```ts
  const g = { arr: [1, 2, 3] };
  function get(): number[] { return g.arr; }
  const x = get(); x.push(4);
  console.log(g.arr);       // [1,2,3]   — Node: [1,2,3,4]
  console.log(x === g.arr); // false     — Node: true
  ```

- **Closure capture.** Capturing an array variable in a closure was a hard
  compile error (`capturing array variable '…' in a closure is not yet
  supported`) — a nested function closing over an array simply didn't compile.

## Decision

Stage 3 shares the header across both remaining boundaries.

- **Return ABI flip.** An array is returned as a **pointer to its shared
  `{data,len}` header** (`LLVMRetType(array)` → `"ptr"`), mirroring the
  header-pointer param ABI (`packArrayArg`) and field storage (Stage 2). At the
  return site (`emitReturn`, plus the expression-bodied-arrow return path)
  `arrayReturnHeader(val)` shares `val.ArrayHeader` when present (a returned
  field/global/captured/named array keeps its identity) and mints one otherwise (a
  transient/new array literal is a new object). Every consumer of an array call
  result derefs the header back into the `{ptr,i64}` aggregate and carries the
  header in `Value.ArrayHeader` via `arrayValueFromHeaderReg`, so binding a call
  result aliases the returned array. The consumer sweep covered the ordinary call
  path, class/dynamic method calls, closure/function-pointer calls, HOF callback
  calls (`emitCBCall`, both closure and named — this is what makes `reduce` into an
  array accumulator and `flatMap`'s array-returning callback well-typed), the
  dynamic-function and standard-decorator boxing adapters, the signature-coercion
  adapters (box and unbox arms), and the two optional-call (`a?.m()`) merge paths.
  Trampolines that forward and re-return with the same `LLVMRetType` (func-value,
  mustCall) pass the header pointer through unchanged, so they needed no edit.

- **Closure capture.** An array symbol's storage is already a slot holding the
  shared header pointer, and an array `Type.IR` is `"ptr"`, so the existing
  capture-cell machinery (`promoteCaptureToCell` + env-cell bind) copies exactly
  that header pointer with no new code path — the enclosing scope and the closure
  share one cell, so a mutation through the closure and an outer reassignment are
  mutually visible. The only additions were removing the two rejections (arrow and
  function-expression capture gathers, and the generator capture gather it shares)
  and seeding the TDZ-misuse case (a closure reading the array before its
  declaration completes) with a fresh **empty header** instead of a null pointer,
  so that path yields an empty array rather than dereferencing null.

## Verification

- Return aliasing: returning an object field / global array aliases it (a caller
  push propagates), two calls returning one source array are `===`-equal, a
  returned fresh literal is a distinct object each call. Closure capture:
  capture-and-read, capture + mutation visible across calls, outer mutation visible
  through a captured reader, and a generator capturing an array all match Node.
- A latent post-Stage-2 inconsistency in the optional-call array paths (they still
  built a 16-byte `{ptr,i64}` for what Stage 2 had already made an 8-byte
  header-pointer result slot) was corrected in the same sweep.
- `go vet`, the full `make test-par` and `make examples` gates, and
  `-optimize-memory` / `-mm=gc` on the return/capture paths. macOS arm64.

## Notes

The shared-buffer free policy is still TDD-00213 Stage 4: a returned or captured
array's buffer is now aliased, so `-optimize-memory` deep-free must not free a
shared buffer at a binding's scope exit. Until Stage 4 lands the deep-free keeps
its prior ownership assumption (a documented hazard; GC mode is already correct).
The pre-existing array-in-container gaps noted in ADR-00940 (`Map<K, T[]>`,
`Promise.all` of `Promise<T[]>`, an array `.then` callback, a self-referential
class array field) remain out of scope here.
