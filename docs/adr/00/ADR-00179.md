# ADR-00179: The comma / sequence operator (`(a, b, c)`)

- **Date**: 2026-08-12

## Context

The comma operator — evaluate each operand left to right, yield the last — was unsupported outside a `for` header (where the comma is already special-cased). `(a, b, c)` failed to parse ("expected ), got ,"), the sixth-largest Test262 parser-error bucket (2783 first-blockers, grown as more files parse further). It is a clean, bounded language feature.

## Investigation

- `parseExpression()` is `parseAssignment()`, and comma-separated lists (call arguments, array elements, parameters) parse one assignment-expression apiece — so the comma operator can be added at the parenthesized-group level without touching those lists.
- The grouping parse (`parser_literals.go`) parsed a single expression then expected `)`. The arrow-vs-group disambiguation eagerly treats `(IDENT , …)` as an arrow parameter list, so a bare-identifier-first sequence (`(a, b)`) is still taken as an arrow and fails without `=>` — a documented limitation; the common forms (`(expr, expr)` with a non-trivial first operand, an assignment, a call) are unambiguous.
- **Two traversal gaps found**, both because a new AST node must be threaded through every existing walk:
  - The resolver's rename pass (`resolver/rename.go`, TDD-00041) didn't recurse into the new node, so an identifier referring to a top-level declaration inside a sequence kept its original name while the declaration was mangled — `let y = …; (99, y)` failed as "undefined variable 'y'" in the full pipeline (but not the resolver-less test path).
  - The var-declaration's per-init-kind type switch (`emit_exprs_vardecl.go`) had no sequence case, so `const s = (…)` fell to its number default: a sequence whose last operand wasn't a number allocated an i64 slot and stored a pointer into it (invalid IR).

## Decision

1. Add `ast.SequenceExpression{ Exprs []Expression }`.
2. Parse it in the grouping: after the first expression, while the next token is `,`, collect `parseAssignment()` operands (each a single assignment expression, so sequence commas never conflict with list commas).
3. Codegen (`emitExpr`): evaluate each operand, return the last one's Value. `inferExprType` and `scanExprFV` (free-variable scan) return/recurse on the operands; the last operand's type is the sequence's type.
4. Thread the node through the two traversals that were missing it: the resolver rename walk and the var-decl type switch.

## Implementation notes

- `ast/nodes.go`, `parser/parser_literals.go`, `codegen/llvm/emit_exprs.go` (emit), `emit_exprs_types.go` (inferExprType), `emit_func.go` (scanExprFV), `resolver/rename.go`, `codegen/llvm/emit_exprs_vardecl.go`.
- Known limitation (unchanged): a bare-identifier-first sequence `(a, b)` is still parsed as an arrow-parameter list and rejected without `=>`; use a non-identifier first operand.

## Side effects discovered

None beyond the two traversal gaps fixed here — both are the general "a new expression node must be added to every AST walk" hazard, worth noting for future node additions.
