# ADR-00345: `tls.createServer` (TLS server)

- **Relations**: Implements TDD-00110; extends ADR-00344 (`tls.connect`)
- **Date**: 2026-08-24

## Context

ADR-00344 shipped the TLS client (`tls.connect`). This adds the server half —
`tls.createServer` — a TLS-terminating listener, reusing the `net` server the
same way the client reused the net client.

## Decision

Per TDD-00110. **`tls.createServer({ cert, key }, connectionListener?)`** returns
a **net-shaped Server** (`NetServerType`) with a server `SSL_CTX*` stored in a new
struct field. `cert`/`key` are PEM **strings** (as Node's are), loaded into the
ctx via a mem BIO (`__kml_tls_server_ctx` in `tlssrc/tls.c`).

- `netServerIR` gained a 4th field, the server `SSL_CTX*` (null for a plaintext
  `net` server — `calloc` zeroes it, so net is behavior-unchanged).
- The net accept loop (`@__kml_net_dispatch`) branches on it: when non-null, the
  freshly-`accept()`ed fd is wrapped by `__kml_tls_server_accept(ctx, fd)` — a
  **blocking** `SSL_accept`, storing the `SSL*` in the connection socket's field 5
  (the same field the client uses, so reads/writes already route through
  `SSL_read`/`SSL_write`). A failed handshake closes the fd and drops the
  connection. Then the existing non-blocking fcntl + connection-listener fire
  proceed unchanged.

The blocking `SSL_accept` runs in the event loop (a stalled handshaking client
blocks the loop — the same posture as the client's blocking handshake and net's
blocking connect). A non-blocking handshake would need a "retry when fd ready"
primitive that doesn't exist yet.

## Implementation notes

- The accepted fd may **inherit `O_NONBLOCK`** from the non-blocking listen socket
  (platform-dependent — it does on this macOS), which would make the blocking
  `SSL_accept` fail with `WANT_READ`. `__kml_tls_server_accept` defensively clears
  `O_NONBLOCK` (fcntl) before the handshake; the caller restores non-blocking
  after. This was the concrete bug the server test surfaced.
- `emitTLSNetSymbols` (tls.go) now also resolves `__kml_tls_server_accept` (the
  net accept path references it): a declare when `tls` is used, a no-op stub
  otherwise — same mechanism as the client-side ABI.

## Scope / exclusions (V1)

- `cert`/`key` PEM strings only (no file paths, chains, passphrase, or SNI cert
  selection); no `requestCert` (client-cert auth), no ALPN; fires `'connection'`
  (not a distinct `'secureConnection'`).

## Verification

- `tests/tls_test.go`: a compiled `tls.createServer({cert,key})` echo server (the
  cert/key are a self-signed pair generated in-process by the Go test and passed
  as PEM string literals); a Go `crypto/tls` client (`InsecureSkipVerify`)
  connects, writes, and reads the echo. The net server suite still passes (the
  accept-path branch is dead for plaintext servers).
- Manual: `openssl s_client` against the compiled server handshakes (TLSv1.3);
  a compiled `tls.connect` client round-trips against a compiled server (two
  processes).
- Machine: verified on Mac (arm64), Homebrew `openssl@3`.
