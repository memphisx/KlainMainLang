# TDD-00075: `-compat` — a whole-program semantic-fidelity axis (stricter-than-JS default, opt-in JS faithfulness)

- **Status**: Partially Implemented — see [ADR-00217](../adr/ADR-00217.md) (step 1) and [ADR-00218](../adr/ADR-00218.md) (object-to-string). Built: the `-compat=strict|js` axis; `-globals` absorbed and removed; `bigint`↔float comparison (`strict` rejects, `-compat=js` does JS's exact comparison); and object-to-string (`console.log(obj)` → `Foo { x: 1 }` always, `[object Object]` string-coercion under `js`, including array rendering — which also unblocked `console.log(array)` — and honoring a class `.toString()` override in coercion); and `&&`/`\|\|` value-preserving ([ADR-00220](../adr/ADR-00220.md), same-typed operands). Remaining inhabitant — error-kind matching — not yet built.
- **Date**: 2026-08-18

## Context

Working through `bigint`'s caveats ([TDD-00074](TDD-00074.md)/[ADR-00216](../adr/ADR-00216.md)) surfaced a recurring shape that the current documentation model handles badly. Some divergences from JavaScript are neither bugs nor permanent scope narrowings — they are **deliberate choices where this compiler is stricter or safer than JS, and faithfully matching JS would be a footgun**. The canonical example: `10n < 5.5` (comparing a bigint to a float). JS evaluates it as an exact real-number comparison; in practice a bigint-vs-float comparison is almost always an accident, so *rejecting* it at compile time is the better compiler behavior — but it is, undeniably, a divergence from JS.

`docs/status/` currently has only two buckets for a divergence: a **bug / deferred shortcut** (fix it to match JS) or a **permanent narrowing** (fixed-shape objects, etc. — here forever). The behaviors above are a third kind, and filing them as "caveats" conflates a deliberate safety decision with an unfinished feature.

The pattern is not new — it already exists as a one-off. **`-globals=strict|permissive`** ([TDD-00050](TDD-00050.md)/[ADR-00143](../adr/ADR-00143.md)) rejects ambient-global shadowing by default (safer than JS) and opts into real-JS shadowing under `permissive`. Nobody calls strict-mode's rejection a caveat; it is a deliberate default with a JS-faithful escape hatch. This document generalizes that one-off into a single, named compatibility axis, so these decisions become explicit design choices rather than an accreting list of caveats — and gives `bigint`'s float-comparison case (and the next features') a proper home.

Scoped now, ahead of implementation, because the very next `bigint` refinement (cross-type comparison) wants to make exactly this kind of "stricter default, JS on demand" decision, and it should land against a real axis rather than as another bespoke caveat.

## Design

### The axis

A whole-program flag, following the existing `-mm=`/`-globals=`/`-regex=` convention:

- **`-compat=strict`** (default) — the compiler's opinionated, safer-than-JS semantics. A program that hits a governed behavior gets the stricter result: a clean compile error, or the more conservative runtime behavior. Divergences here are deliberate and documented as such.
- **`-compat=js`** — best-effort faithful reproduction of JS's *observable* behavior for the governed behaviors, footguns included, for programs that need bit-for-bit fidelity.

**Default is `strict`.** This preserves the compiler's identity — typed, safe, catches likely bugs — and, crucially, makes every governed divergence a deliberate *opt-out* rather than a silent accident. `js` is the escape hatch. This mirrors `-globals`'s own strict default rather than `-regex`'s faithful default (see "Composition" for why those differ).

### What it governs — and what it must not

`-compat` governs **only** behaviors where there is a genuine *strict/safe vs JS-faithful* tradeoff. It is explicitly **not** a home for:

- **Bugs** (`.charCodeAt` out-of-range reading garbage, `%g` float printing, the `[object Object]` stringification gap) — those get fixed to match JS in *both* modes.
- **Permanent narrowings** (fixed-shape objects, no dynamic property bags) — those stay in both modes.
- **Behaviors where JS's choice is also the safer/correct one** — then there is no tradeoff, and the JS behavior is simply the default (it does not belong on this axis at all). Guarding against over-populating the flag matters: the bar for adding an inhabitant is "the stricter behavior is genuinely better *and* the JS behavior is genuinely wanted by someone."

Inventory of current/candidate inhabitants:

| Behavior | `strict` (default) | `js` | Source |
|---|---|---|---|
| `bigint` ↔ `number` comparison across the **float** boundary (`10n < 5.5`) | compile error (the value is almost certainly a bug) | JS's exact real-number comparison | this doc |
| `&&` / `\|\|` result | a bool | JS's value-preserving operand (`a && b` → `b`, or the falsy `a`) | [ADR-00186](../adr/ADR-00186.md) |
| Ambient-global shadowing | reject a colliding declaration | real-JS/browser shadowing | [TDD-00050](TDD-00050.md) — **absorbs** the current `-globals` flag, see Composition |
| Error **kind & wording** | the compiler's own concise diagnostics | classify under the JS error kind (`TypeError`/`RangeError`/…), optionally match Node/V8 wording | [TDD-00072](TDD-00072.md) Part 2 — folded in |
| **String-coercing** a `.toString()`-less class instance (`"" + obj`, `` `${obj}` ``, `String(obj)`) | a useful view — `Foo { x: 1 }` (class name + fields) — never `[object Object]` | `[object Object]` (JS's primitive `ToString`) | this doc — a class-defined `.toString()` is honored in *both* modes; only the no-`toString` default is gated |
| *(candidate, not committed)* `**` integer-vs-float semantics | exact i64 (`2 ** 3 = 8`, negative exp → 0) | JS Number (always double) | [ADR-00187](../adr/ADR-00187.md) — entangled with `number → i64`, needs its own analysis first |

**Integer `bigint`↔`number` comparison** (`10n < 5`, `10n == 10`) is deliberately *not* on this list: it is exact and correct in *both* modes, so it is always-on and ships independently of the flag (see [TDD-00074](TDD-00074.md)'s follow-on). Only the float boundary is a tradeoff.

Likewise **`console.log(obj)` / Node-style structured printing** is *not* a gated behavior: rendering a class instance as `Foo { x: 1 }` (its class name + fields) is what Node's `console.log` does *and* the useful one, so it is always-on in both modes — distinct from JS's *primitive* `ToString` (`[object Object]`), which is what `console.log` deliberately does **not** use. (The two are genuinely different operations in JS: `util.inspect` vs `ToString`.) So the empty-string that `console.log(new Foo())` currently prints is simply a bug to fix, and only the *string-coercion* default above is the compat knob. This distinction is the crux of the design and why only one of the two conversions is gated.

Inhabitants land incrementally — the flag ships with a first set and grows, exactly like `-regex`'s staged modes. `-compat=js` selecting an inhabitant that isn't implemented yet errors cleanly (or documents that it currently no-ops), rather than silently pretending.

### Composition with the existing per-area flags

`-compat` sets the semantic posture directly. Ambient-global shadowing — the one existing flag that fits the strict-vs-JS duality — is **absorbed** into it rather than coordinated alongside it:

- **`-globals` → folded into `-compat`, the standalone flag removed.** `-compat=strict` is today's `-globals=strict` (a declaration colliding with a built-in name like `Math`/`fetch` is a compile error); `-compat=js` is today's `-globals=permissive` (real-JS/browser shadowing, with the parser-level `new`-form built-ins `Map`/`Date`/`RegExp` staying reserved either way, exactly as [TDD-00050](TDD-00050.md) established). There is no separate globals flag and no `-compat`-plus-`-globals` precedence to reason about — one axis, one knob. The lost granularity ("permissive globals but otherwise strict") is a deliberate simplification; if a real program ever needs it, it returns via the per-behavior opt-in in Open questions, not a resurrected flag.
- **`-regex`** is deliberately **left independent**. Its axis is *ECMAScript-dialect vs PCRE-power* — both legitimate, neither "safer than the other" — not strict-vs-JS. (Its default is already the ES-faithful mode, so there is nothing for `-compat=js` to flip.) Folding it under `-compat` would misrepresent what its modes mean.
- **`-mm`** (memory management) is entirely orthogonal — not a semantics-vs-JS axis.

This keeps the umbrella honest: it *is* the strict-vs-JS axis — absorbing every behavior that fits that duality, `-globals` included — while flags whose axis is something else stay out of it. Removing `-globals` is a user-facing flag change, but the project makes no cross-commit stability guarantee, so a clean removal (not a deprecated alias) is acceptable.

### Relationship to the other compatibility-adjacent TDDs

- **[TDD-00022](TDD-00022.md)** (best-effort vanilla-JS *compilation*) is a **different, heavier axis**: making *untyped* JS compile at all (default-to-`any`, prototype classes, dynamic property bags). `-compat=js` is about the *semantic fidelity of typed programs that already compile* — it must **not** be read as "vanilla JS compiles now." The two are complementary and a future all-in "just run my JS" experience might imply both, but this axis neither depends on nor blocks 00022.
- **[TDD-00072](TDD-00072.md)** Part 2 proposed a `compatibilityMode` for error-kind/wording matching against the same conceptual axis. This document **subsumes** that: error-kind classification becomes a `-compat=js` behavior, so there is one compatibility knob, not two. TDD-00072 Part 1 (the diagnostic renderer — caret/snippet, default-on) is unrelated and stays in 00072.

### Documentation consequence

A behavior governed by `-compat` stops being a bucket-1 "caveat." `docs/status/` renders it the way the `-globals`/`-mm` rows already render in the Cross-Cutting section: ✅ with a note of the form *"`strict` (default): <behavior>; `-compat=js`: <JS behavior>."* Concretely, once the axis exists, `bigint`'s float-comparison line moves out of the Caveats column into this framing, and a short **Cross-Cutting** entry describes `-compat` itself (alongside Memory management and Reserved ambient-global names).

### Recommended path

1. **Land the axis plumbing + its first inhabitant.** The `-compat` flag threaded to an emitter field + the resolver hook that sets the `-globals` baseline, plus the `bigint` float-comparison behavior (`strict`: the existing clean compile error — already how V1 behaves, now *reframed* as deliberate; `js`: deferred until the exact comparison is built, erroring cleanly if selected). This alone converts a caveat into a design choice at near-zero cost, because `strict` is already the shipped behavior.
2. **Migrate the existing one-offs.** Re-document `-globals` as the first coordinated per-area override; fold TDD-00072 Part 2's error-kind matching in as a `js` behavior.
3. **Add inhabitants incrementally** (`&&`/`||` value-preserving; the JS-exact `bigint`↔float comparison; later candidates), each with its own ADR, each measured against `make conformance` (a `-compat=js` conformance pass likely becomes a distinct measurement — see Open questions).

Each step is independently shippable; step 1 is the whole point and is cheap.

## Open questions

- **Naming / label collision.** `-compat=strict` overloads "strict," which already means something specific in `-globals=strict`. Alternatives: `-compat=native|js`, `-compat=off|js`, or `-js`. The word chosen for the default should not imply it is the *less* capable mode (it is the recommended one). Leaning `-compat=strict|js` for consistency with the family, but the overload is real — resolve before implementing.
- **`-globals` absorption (resolved).** `-globals` is folded into `-compat` and removed as a standalone flag (see Composition), not kept as a coordinated override — one axis is the goal. `-regex` stays independent (its axis is dialect-choice, not strict-vs-JS). The residual question is only the per-behavior-opt-in granularity below, should someone need permissive-globals without full `js` mode.
- **Granularity of `js`.** All-or-nothing (like `-globals`), or per-behavior opt-in (`-compat=js:bigint-float,logical-values`)? Start all-or-nothing; revisit only if real programs need to mix a single JS behavior into an otherwise-strict build.
- **The over-population guard, operationalized.** What is the concrete checklist for admitting an inhabitant, so the flag does not slowly absorb every divergence? Draft bar: (a) the strict behavior is genuinely safer/better, (b) the JS behavior is genuinely wanted by a real use case, (c) it is not a bug and not a permanent narrowing. Needs to be written where future ADRs will see it.
- **`**` and the `number → i64` entanglement.** JS `**` returns a double; this compiler's is i64. Making `-compat=js` faithful here is really about `number` being `i64` rather than a double — a far deeper representation question than a per-operator toggle. Likely *not* an early inhabitant; flagged so it is not casually added.
- **Conformance semantics.** Does `make conformance` grow a second `-compat=js` run, and if so, which number is "the" headline? Probably: strict-default stays the headline (it is the recommended mode), with `-compat=js` reported as a separate fidelity measurement.
