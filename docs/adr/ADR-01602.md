# ADR-01602: Windows runs the libuv event loop

- **Relations**: Implements TDD-00252 (Stages 1–2), Extends TDD-00244, Supersedes ADR-01024
- **Date**: 2026-10-13

## Context

Windows kept a second event loop, a `select()` pass over the shim's IOCP
emulation, after Linux and macOS moved to libuv (TDD-00244). Every source
had Windows-only `*_fdset_add`/`*_dispatch`/`*_keepalive` hooks, and the
Windows loop's limits were its own (TDD-00252, Context).

## Investigation

- libuv is in the ucrt64 sysroot (`mingw-w64-ucrt-x86_64-libuv`, also CI's).
- The POSIX loop watches descriptors with `uv_poll_t`; libuv's Windows
  `uv_poll_init_socket` polls a `SOCKET` (AFD), and the shim gives the
  `SOCKET` behind a descriptor (`__kml_win_fd_socket`).
- `<uv.h>` brings Winsock and the CRT's `io.h`/`sys/stat.h`, whose
  declarations of `socket`, `accept`, `read`, `stat`, `mkdir`, … clash with
  the shim's POSIX ones that `klainpool.c` uses.
- libcurl reports real `SOCKET`s in both link modes: since lld (ADR-01597)
  its socket calls bind to Winsock, not to the shim as ADR-00772 describes.
- A child's stdio pipe and the console are not sockets: libuv cannot poll
  them. The shim drives them with overlapped zero-reads and reader threads
  whose completions and wakes go to its own completion port, which only its
  `select()` drained.
- The console signal handler only queues the signal; `select()` and
  `nanosleep()` delivered it.
- Node 24 on Windows: twenty 50 ms intervals take about 1250 ms (the
  system tick); ADR-01024 had made them about 1010 ms here.

## Decision

- `LocateUV` links libuv on Windows (static under `--static`), with the
  system libraries its `libuv.pc` names.
- `loop.c`, `timers.c`, `fetch.c`, `ipcc.c` and `fswatch.c` take their POSIX
  code on Windows. A watched socket is polled by its `SOCKET`
  (`kml_uv_poll_init`); libcurl's sockets by their own value
  (`__kml_loop_sock_watch`); its wait outside the loop by `WSAPoll`
  (`__kml_win_poll_sockets`).
- `kml_uv_win.h` includes `<uv.h>` with the clashing Winsock and CRT names
  renamed, drops Winsock's constants, and includes the compat header in a
  mode that declares the shim's functions (`KML_COMPAT_OVER_WINSOCK`).
- `klainpool.c`: the pool wake is the port's `uv_async_t` and TCP handles are
  `uv_poll_t` watchers, as on POSIX. A descriptor libuv cannot poll (a pipe,
  the console) is asked of the shim's `select()` without waiting from the
  loop's check callback; a referenced one reading or writing, and a live
  referenced child, hold the loop through that check handle.
- The shim wakes a loop through the function it registered
  (`__kml_win_set_loop_wake`, its `uv_async_send`), and a forwarder thread
  per loop takes the shim port's completions, queues them for the drain and
  wakes the loop. A Worker releases both as it ends.
- Signals: the loop pass delivers the console handler's queued signal
  (`__kml_win_sig_deliver`) before dispatching the watchers.
- curl on Windows: `curl_multi_socket_action` takes a 64-bit `SOCKET`, so
  `CURL_SOCKET_TIMEOUT` is passed as `~0` (an `int` -1 reached libcurl as
  `0xFFFFFFFF`, an unknown socket). libcurl 8.20 hands its resolver thread
  pool's results back only when every handle is processed, so the timer
  callback also calls `curl_multi_socket_all`; without it a failed lookup
  waited for the 30 s transfer timeout (Node: `ENOTFOUND` in about 60 ms).
  Linux's older libcurl does not need it, but takes the same call.
- A cluster worker's listener is polled by its round-robin channel from the
  primary (`__kml_win_poll_socket`, the shim's `kfd_rd_src`): its
  connections arrive there, not on the listener's socket.
- A pipe the shim watches is asked again after the dispatch drained it, which
  arms the next zero-read whose completion wakes the loop.
- The shim's descriptor table grows: CRT descriptors below 8192 (the CRT's
  own limit), the owned pool (sockets, pipe ends) at 8192–16383. Its bounds
  were the IR's 1024-bit `fd_set`, which the loop no longer uses; the
  descriptor-ceiling tests (`TestE2ELoop*Above1024`) run on Windows, opening
  `os.devNull` and without `ulimit`.
- Timers keep Node's resolution: ADR-01024's high-resolution wait is gone
  with the `select()` pass, and `TestE2ETimerIntervalResolution` checks
  Node's figure.

## Side effects discovered

- A write to `process.stdout` redirected to a pipe blocks the loop until the
  reader drains it: Node 24 on Windows does the same (20 MiB to a reader that
  waits 2 s: the write returns after 2036 ms, a 100 ms timer fires then). The
  backlog item is closed as Node's behaviour.

## Implementation notes

Child processes, their stdio pipes and the IPC framing keep the shim's spawn
and pipes until TDD-00252 Stage 3 (`uv_spawn`, libuv pipes); the
`select()` emulation and the hooks' no-op stubs go in Stage 4.

## Verification

Windows 11: timers, child processes (output, exit, `close`), fetch in both
link modes, signals under the pseudo-console, named-pipe clients, cluster
round-robin, and the targeted E2E groups (timers and event loop, child
process, networking, fetch, signals, pipes and stdin, clusters). A parent
waiting 2 s on a child used 0 ms of CPU. `TestE2EReactorForeignSocketOnPort`
is removed: it asserted the shim reactor's AFD poll for libcurl's sockets,
which libuv now polls. TDD-00180's TLS write-error probe
(`TestE2ETLSServerWriteAfterClientDestroy`: a TLS server writing while its
client destroys the connection) gives `ECONNRESET`, as Node 24 does on the
same machine. Linux and macOS: owed (shared files changed:
`fetch.c`, `loop.c`, `klainpool.c`).
