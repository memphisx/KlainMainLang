# ADR-00082: Error subtypes / tagged errors — `TypeError`, `RangeError`, etc.

- **Relations**: Implements [TDD-00013](../tdd/TDD-00013.md) (Option A). Extends [ADR-00067](ADR-00067.md), class Stage 2's runtime type tag / `instanceof` mechanism, reusing the same shape for a sibling, non-class case.
- **Date**: 2026-07-30

## Context

[TDD-00013](../tdd/TDD-00013.md) scoped two options for closing a gap Classes Stage 2 ([ADR-00067](ADR-00067.md)) deliberately left open: `new Error(msg)` was a single, untagged `{message: ptr}` struct shared by every thrown value regardless of what it actually represented, there was no `TypeError`/`RangeError`/etc. anywhere (no lexer keyword, no parser rule, no AST node), and `x instanceof Error` was a clean compile error. Option A (tag the existing `Error` struct with a small built-in kind enum, no dependency on class inheritance) was buildable standalone; Option B (a real built-in class hierarchy with `extends`) is strictly gated on [TDD-00009](../tdd/TDD-00009.md) Stage 3, which isn't scheduled. Picked up this session to implement Option A, with the full standard kind set (`Error`, `TypeError`, `RangeError`, `SyntaxError`, `EvalError`, `URIError`, `ReferenceError`) and a real `.name` field, both confirmed directly rather than assumed.

## Investigation

Read through the full existing exception/class-tag machinery before designing the diff:

- `codegen/llvm/emit_exceptions.go:9` — `errorObjType` was a bare package-level `var = ObjectType([]Field{{"message", TypePtr}})`, not a function like `ClassType()`/`ResponseType()`.
- `codegen/llvm/types.go:274-314` — `ClassTagField`/`ClassType`/`VisibleFields()` is the exact precedent this reuses: a hidden tag field prepended at index 0, with `VisibleFields()` stripping it for enumeration (`Object.keys`, JSON, spread, for-in) so it never leaks as a fake user-visible field.
- `codegen/llvm/emit_classes.go:476-535` (`emitInstanceOf`) — the existing class `instanceof`'s four-case structure (dynamic/any value → unbox + runtime tag compare; static matching class → compile-time true; static different class → compile-time false; any other type → compile-time false) was the direct template, but Error kinds can't reuse it as-is: `emitInstanceOf` looks up `e.classes[rightIdent.Name]`, and Error/TypeError/etc. are never registered there (they're not `class` declarations) — they need their own parallel dispatch, keyed off a different hidden tag field on a different shared type.
- `parser/parser_literals.go:111-142` (`parseNew`) — `"Error"` was already one hardcoded case among `Array`/`Map`/`Set`/`Date`/etc.; adding six more built-in-name cases was a direct, mechanical extension of the same switch.
- **Load-bearing hazard found by direct read, not by symptom**: `codegen/llvm/runtime_exceptions.go`'s `@__kml_throw` hand-writes the uncaught-exception print path as raw IR text, `getelementptr { ptr }, ptr %errObj, i32 0, i32 0` — hardcoded against the *old* single-field struct shape, bypassing the generic `FieldIndex`/`StructIR` machinery entirely (this is hand-written IR, not codegen output, so it can't pick up a field-order change automatically). Changing `errorObjType`'s field count/order without also fixing this exact GEP would silently make every *uncaught* error print garbage instead of its message.
- **A second, unrelated pre-existing bug found while writing the test for the above**: `emitThrow`'s dispatch condition, `val.Ty.IsObject || val.Ty.IR == "ptr"`, treats *any* `ptr`-IR value — including a bare string literal (`TypePtr`'s IR is also `"ptr"`) — as already object/Error-shaped, skipping the wrap-in-Error-struct path entirely. `throw 'plain string'` therefore passed the raw string pointer straight to `__kml_throw` as if it were an `errorObjType` instance; any later `.message`/`.name`/`instanceof` access against the caught value read the string's own bytes as struct fields, segfaulting. Reproduced directly (`tests/errors_test.go`'s `TestE2EThrownPrimitiveIsInstanceOfErrorNotSubtype` crashed with exit 139 before the fix). This predates this session entirely — confirmed by inspecting the pre-change file content, not introduced by the `errorObjType` layout change — but surfaced only now because nothing previously exercised `throw <string>` followed by a field read on the caught value.
- Confirmed `errorObjType`'s malloc'd storage is only ever referenced as an opaque `ptr` at `SettlementType`'s `reason` field and `Promise.allSettled`'s `buildSettlement` (`emit_promise.go`) — both already go through generic `FieldIndex`/`StructIR`, so they'd inherit a layout change with zero code changes *for reading*. Writing a new instance is a different story — see the `make examples` finding below.
- **The big one, found only after `go test ./...` was already green**: ran `make examples` as a final pass and got three segfaults (`array_bounds.ts`, `fs.ts`, `division_by_zero.ts`) nothing in `tests/` had caught. `grep -rn "malloc(i64 8)" codegen/llvm/` turned up **15 separate hand-rolled call sites**, across 10 files, that build a minimal Error object *without going through `emitNewError`/`emitThrow` at all* — every internally-generated runtime error this compiler has ever thrown (array bounds, division by zero, frozen-object write, `ArrayBuffer` length/`set()` bounds, invalid `URL`, and every `fs`/`fetch`/`http`/`process.execFileSync`/`process.kill` OS-level failure) constructs its own `malloc(i64 8)` + `store ptr <msg>` + `call @__kml_throw` sequence by hand, each one independently agreeing with the *old* 1-field layout. None of `tests/`' existing exception tests exercise any of these — they all use `throw new Error(...)` or a `catch` around a manually-thrown value, never an array-bounds violation or a division by zero, so nothing caught the mismatch until `make examples` ran a program that actually hit one. This is exactly the class of gap [ADR-00079](ADR-00079.md)'s own Side effects section already warned about in general terms ("found empirically, not by inspection") — a hand-written-IR invariant with no single source of truth, silently violated at a distance.
- Considered giving each kind its own `Type` (a real `ErrorType(kind)` constructor per TDD-00013's Prerequisites table) instead of one shared `errorObjType` with a runtime discriminant. Rejected: `catch (e)` has no way to know a caught value's concrete kind at compile time (the whole point of `instanceof` narrowing), so every kind still needs to collapse to one shared static type at the `catch` boundary regardless — a per-kind `Type` would only add bookkeeping (which `Type` to pick for `new TypeError()`'s `inferExprType`, `emit_exprs_vardecl.go`'s var-decl fallback, etc.) without buying anything back.

## Decision

One shared struct shape for every kind, keyed by a runtime discriminant — the same convention `ClassTagField` already established for user classes:

```
errorObjType fields: { kind: i64, message: ptr, name: ptr }   (was: { message: ptr })
```

- `kind` (hidden field, index 0) is one of `errorKinds`' 7 entries (`emit_exceptions.go`), `"Error"` always index 0 — the base every other kind is unconditionally `instanceof`.
- `message` behavior is unchanged in spirit: a no-arg `new XError()` still defaults `.message` to the kind's own name string, generalizing the previous hardcoded `"Error"` default rather than changing it.
- `name` is the interned kind-name string, stored once at construction — not derived at each `.name` read, since it's static per construction site.
- `IsError bool` (new `Type` flag, `types.go`) marks this family, mirroring `IsClass`; `VisibleFields()` strips the hidden `kind` field for `IsError` types the same way it already does for `IsClass`'s `ClassTagField`.

`instanceof` against a built-in kind is a new, parallel mechanism (`emitErrorInstanceOf`, `emit_classes.go`), dispatched from `emitInstanceOf` before the `e.classes` lookup:
- **`instanceof Error`** (the base) never needs a runtime tag comparison — every constructible kind is unconditionally an Error. Static `IsError` value → compile-time `true`. Dynamic (`any`/`unknown`) value → the existing unbox-and-check-object-tag result *is* the answer, no further field read.
- **A specific kind** (`TypeError`, ...) always needs the runtime tag comparison, since every kind shares one `Type` — the tag is the only thing distinguishing a `TypeError` instance from a `RangeError` one. Static `IsError` value → GEP field 0, load, `icmp eq` against the target kind's ID. Dynamic value → unbox, confirm object tag, then the same GEP+compare off the unboxed pointer (identical shape to class `instanceof`'s own dynamic branch).
- Any other static type (number, string, class instance, plain object, Date, Response, ...) → compile-time `false`, matching the existing class-`instanceof` precedent.
- No null-check branch is needed here (unlike class `instanceof`'s `Nullable` case): `"Error"` isn't a resolvable type-annotation name anywhere (`resolveType`/`ResolveTypeName`), so no code path ever produces a statically `Error`-typed, `Nullable` value.

`emitThrow`'s non-object wrap path (a bare `throw <number>`/`<bool>`/`<string>`) now builds the same 3-field shape by hand (kind `0`/Error, stringified message, name `"Error"`) instead of the old 1-field malloc — and, per the bug found above, the dispatch condition narrowed from `val.Ty.IsObject || val.Ty.IR == "ptr"` to just `val.Ty.IsObject`, so a bare string now correctly goes through the wrap path instead of being passed through raw.

Given the 15-site fan-out found while verifying (see Investigation), every Go-emitted construction site now goes through one new shared helper, `buildErrorObj(kindID int64, msgPtr, namePtr string) string` (`emit_exceptions.go`) — malloc, GEP+store all three fields, return the register — so `errorObjType`'s layout has exactly one place that knows how to build an instance of it, not 15. A second helper, `emitInternalThrow(msgPtr string)`, wraps `buildErrorObj` with the "kind 0/Error, throw, unreachable" tail every internally-generated runtime error shares. The 6 hand-written-IR-text runtime helpers across 4 files (`ensureFsThrow`, `ensureFetch`, `ensureFetchAsync`, `ensureHTTPThrow`, `ensureExecFileSync`, `ensureProcessKill` — 7 throw sites between them, since `ensureFetchAsync` and `ensureExecFileSync` each have more than one) can't call a Go function mid-template, so those 7 sites were expanded by hand instead, each now interning `"Error"` once and splicing it into the same 3-field GEP pattern — mechanically identical to `buildErrorObj`'s shape, just inlined as raw IR text.

## Implementation notes

- `ast/nodes.go` — `NewErrorExpression` gained a `Kind string` field; `NewNewErrorExpression(kind, msg, pos)`.
- `parser/parser_literals.go` — `parseNew`'s switch gained 6 new cases (`TypeError`/`RangeError`/`SyntaxError`/`EvalError`/`URIError`/`ReferenceError`), all calling the now-kind-parameterized `parseNewErrorBody(pos, kind)`.
- `codegen/llvm/types.go` — `IsError bool` on `Type`; `VisibleFields()` extended.
- `codegen/llvm/emit_exceptions.go` — `errorKinds`/`errorKindIDs` table; `errorObjType` rebuilt as a 3-field `IsError` type; `buildErrorObj`/`emitInternalThrow` (new, shared); `emitNewError`/`emitThrow` both rewritten on top of `buildErrorObj`.
- `codegen/llvm/runtime_exceptions.go` — the `@__kml_throw` uncaught-path GEP fixed to `getelementptr { i64, ptr, ptr }, ptr %errObj, i32 0, i32 1`, with a new doc comment on `ensureExceptionHelpers` calling out that this hand-written GEP must be kept in sync with `errorObjType`'s layout by hand — the exact landmine this session hit.
- `codegen/llvm/emit_classes.go` — `emitInstanceOf` gained one new branch (`errorKindIDs` lookup) ahead of the `e.classes` lookup; `emitErrorInstanceOf` is new, ~60 lines, structurally mirroring `emitInstanceOf`'s existing dynamic/static split.
- Every other internal error-construction site switched to the new helpers (Go-emitted, via `emitInternalThrow`/`buildErrorObj`): `emit_exprs_member.go` (division-by-zero guard, array bounds check), `emit_arraybuffer.go` (length-not-a-multiple, `set()` source-too-large), `emit_arrays_transform.go` (`.with()` out-of-range), `emit_url.go` (invalid URL), `emit_objects.go` (frozen-object write), `emit_promise.go` (`Promise.allSettled`'s rejection-reason object — the one non-throwing use of `buildErrorObj`, called directly rather than through `emitInternalThrow`).
- The 7 hand-written-IR-text sites, expanded in place (no shared Go helper possible — see Decision): `runtime_fs.go` (`ensureFsThrow`), `runtime_fetch.go` ×2 (`ensureFetch`'s network-failure path, `ensureFetchAsync`'s `__kml_pending_finish`), `runtime_http.go` (`ensureHTTPThrow`), `runtime_process.go` ×3 (`ensureExecFileSync`'s exit-code and signal-death paths, `ensureProcessKill`).
- `emit_exprs_types.go`'s `inferExprType` and `emit_exprs_vardecl.go`'s untyped-`const`-init fallback both already returned the shared `errorObjType` for `*ast.NewErrorExpression` — needed no change, since the type is still one shared value regardless of which kind was constructed.
- Not done, consistent with TDD-00013's explicit scope: no user-definable `class X extends Error` (needs Stage 3 inheritance), no `.stack`, no change to `catch`'s binding mechanism itself (still one shared `errorObjType`-typed variable).

## Side effects discovered

- **The `@__kml_throw` uncaught-path GEP** (see Investigation) — fixed as part of this change, not a separate follow-up, since shipping the layout change without it would have been an immediate regression.
- **`emitThrow`'s over-broad `ptr`-IR passthrough condition** (see Investigation) — a real, pre-existing bug (predates this session), fixed here rather than deferred since it was found directly inside the function already being modified for this feature, with a small, low-risk, test-covered fix. `throw <number>`/`throw <bool>` were unaffected (already routed through the wrap path); only bare-string throws were broken.
- **The 15-site fan-out** (see Investigation's `make examples` finding) — every one of them was on the *old* 1-field layout, so all 15 would have silently built a corrupt Error object (or, after this ADR's other fixes, an under-sized 8-byte allocation read as if it were 24 bytes) the moment `errorObjType` gained a second/third field. All 15 fixed as part of this change; none deferred. This is the largest single piece of this ADR's diff by file count, even though the feature itself (`TypeError`/`RangeError`/etc.) only directly touches a handful of files — a useful reminder that a shared internal data shape with no single point of construction is a standing risk for exactly this kind of "not its own bug, but every reader of it needs its own hand-verified fix" fan-out. Worth being alert to whether any *other* shared hand-written-IR shape in this codebase has the same property, though that audit is out of scope here.
- `console.log(boolExpr)` prints `0`/`1`, not `"true"`/`"false"` — not a new finding (existing, documented convention, see `TestE2EInstanceOfStaticTrue` in `classes_test.go`), but worth noting here since it initially looked like a bug in this session's own new `instanceof`-against-`Error`-kind tests before being traced to the pre-existing convention.
- The uncaught-exception message (`"Uncaught: %s\n"`) prints to **stdout** via `@printf`, not stderr via `@dprintf` — also pre-existing, not changed here, but worth flagging since it's easy to assume otherwise (confirmed directly while writing `TestE2EUncaughtErrorSubtypePrintsMessage`, which initially asserted on stderr and failed with an empty capture until corrected).

## Verification

- `tests/errors_test.go` (new, 9 tests): message/name defaults and explicit values for a subtype and for plain `Error`; matching-kind and mismatched-kind `instanceof`; `instanceof Error` true for all 7 kinds; `catch (e)` narrowing via `if (e instanceof TypeError) ... else if (e instanceof RangeError)`; a thrown bare string is `instanceof Error` but not `instanceof TypeError` (the `emitThrow` bug-fix regression guard); an uncaught `TypeError` still prints its real message (the `__kml_throw` GEP regression guard).
- `examples/try_catch/try_catch.ts` extended with a `RangeError`/`TypeError`-narrowing example; run directly (`./klainmain examples/try_catch/try_catch.ts && ./examples/try_catch/try_catch`) and output checked by hand.
- **`make examples` (all 68 examples)**: caught the 15-site fan-out `go test ./...` alone had missed — `array_bounds.ts`, `fs.ts`, and `division_by_zero.ts` all segfaulted (exit 139) after the initial `errorObjType`/`emitThrow`/`__kml_throw` fix, before the other 15 hand-rolled construction sites were found and fixed. Re-ran clean (68 passed, 0 failed) after the fix — this is now the authoritative "did this actually work end-to-end" check for this change, not `go test ./...` alone, since none of the existing exception tests happened to exercise an internally-thrown runtime error.
- `go build -o klainmain .` and `go test ./...` (full suite): all green — run repeatedly through this session (after the core codegen change, after the `emitThrow` bug fix, and again after the 15-site fan-out fix), each time clean.
- `docs/status/LANGUAGE-CONSTRUCTS.md` (new row + `instanceof` row's note updated, page coverage 50/58 → 51/59) and `docs/status/README.md` (Classes/OOP category 6/13 → 7/14, two "not started" table rows flipped to done with strikethrough per this page's existing convention, three prose cross-references updated) both updated; `docs/tdd/TDD-00013.md`'s Status line and `docs/tdd/README.md`'s index both point back to this ADR.
