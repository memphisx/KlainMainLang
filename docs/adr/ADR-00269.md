# ADR-00269: `Symbol.asyncIterator` — user-defined async iterables in `for await...of`

- **Relations**: Implements [TDD-00089](../tdd/TDD-00089.md); extends [ADR-00253](ADR-00253.md), [ADR-00254](ADR-00254.md) (async generators / `for await...of`); builds on [ADR-00265](ADR-00265.md) (unified async-method promises), [ADR-00268](ADR-00268.md) (`await` await machinery)
- **Date**: 2026-08-20

## Context

`for await...of` (TDD-00085) consumed only an async-generator *instance*: its dispatch in
`emitForOf` checked `objTy.IsGenerator && objTy.GeneratorIsAsync` and rejected everything
else. A user class implementing the async-iteration protocol by hand — a
`[Symbol.asyncIterator]()` method returning an iterator with `async next(): Promise<{value,
done}>` — could not be consumed, even though it is the standard shape a paginating API or a
stream wrapper takes. `Symbol.asyncIterator` was an explicit V1 scope cut in TDD-00085; this
closes it and moves the `for await...of` coverage from "async generators only" to "the
async-iteration protocol."

## Investigation

Two independent rejection sites blocked it, confirmed by repro:

- **Parser** — `[Symbol.asyncIterator]() {}` fails at `parser_classes.go` with *"a computed
  class member name must be a constant string or number literal … a dynamic key (identifier,
  call, Symbol, or interpolation) is not yet supported."* `constMemberName` accepts only
  `StringLiteral`/`NumberLiteral`; a constant computed key desugars to a plain named member
  (`['foo']()` ≡ `foo()`), so there is no distinct computed-method AST node.
- **Codegen** — `for await` over any non-async-generator fails at `emit_stmts.go` with *"'for
  await...of' requires an async generator (V1 scope, TDD-00085)."*

Everything else the protocol needs already existed: class method dispatch on an instance
(`emitClassCall`, `emit_classes.go:1735`), the shared task-promise await
(`emitAwaitTaskPromise`, `emit_async.go:272` — parks/drives and re-throws a rejection), and
structural `{value,done}` reads (`emitForAwaitOfGenerator`, `emit_generators.go`). The
accessor keys (`"get x"`) are precedent that a reserved, non-identifier `MethodSigs` key
dispatches fine and can't collide with a user method (`emit_classes.go:269`).

`Symbol` itself (TDD-00044) is an opaque unique value with no well-known symbols and no
runtime protocol-dispatch point — so the design resolves the well-known symbol entirely at
compile time, as a reserved member name, not a runtime value.

## Decision

Represent `Symbol.asyncIterator` as the reserved `MethodSigs` key `@@asyncIterator` (the
spec's `@@`-prefix convention) and wire the two rejection sites to it:

1. **Parser desugar.** In the computed-class-member branch, when `constMemberName` fails, try
   `wellKnownSymbolMemberName`: a `MemberExpression` `Symbol.asyncIterator` desugars to the
   member name `@@asyncIterator`; any other dynamic key stays a clean rejection. The method
   registers in `MethodSigs["@@asyncIterator"]` through the ordinary path. `Symbol.iterator`
   (the sync protocol) is deliberately *not* recognized — sync `for...of` already dispatches
   structurally on a `next(): T | null` method, and a general sync `Symbol.iterator` protocol
   is a separate future item; admitting it as a parse-only key would leave a
   parses-but-doesn't-dispatch half-state.

2. **`for await` dispatch.** When the iterable is not an async generator, accept a class whose
   `MethodSigs` has `@@asyncIterator` and lower it in `emitForAwaitOfAsyncIterable`:
   `it = iterable[Symbol.asyncIterator]()` via `emitClassCall`; then a loop that calls
   `it.next()` (a task-shaped `Promise<{value,done}>`), awaits it via `emitAwaitTaskPromise`,
   reads `.done`/`.value` off the settled result via `FieldIndex`, and either exits or binds
   the loop variable — reusing the destructuring `unpack*PatternInto` core exactly as
   `emitForAwaitOfGenerator` does. The result-object type comes from the iterator's
   `next()` return type (`nextSig.RetType.PromiseType`).

No new runtime machinery: method dispatch, the task await, and structural `{value,done}`
reads all pre-existed; the new code is one parser branch and one loop-emitter.

## Implementation notes

- `llvmSafeSymbol` (`emit_classes.go`) gained an `@@` → `__kml_wks_` substitution: `@` is
  illegal in a bare LLVM identifier, so the method function symbol
  `Range__kml_mod0_@@asyncIterator` failed to assemble. The substitute uses the same
  `__kml_` reserved namespace as the private-name (`#`) substitution already there; the
  un-substituted `@@asyncIterator` stays the dispatch key in `MethodSigs`.
- Error messages un-mangle the iterator class name via `inspectClassName` so the user sees
  `It`, not `It__kml_mod0`.
- The iterator instance is held in an alloca and reloaded each turn (it may be `return this`
  or a fresh object — either way a heap ptr).
- `emitAwaitTaskPromise` is reused unchanged; it selects the fiber-park path or the
  microtask/timer-drive path by `e.hasMaySuspend`, so an iterator whose `next()` awaits real
  work and one that settles inline both work.

## Side effects discovered

- Parameter-property shorthand (`constructor(private end: number)`) is still unsupported —
  unrelated to this work, surfaced only while writing the repro; fields are declared
  explicitly. Not tracked as a new caveat here.
- Object literals cannot carry a `[Symbol.asyncIterator]()` method (object-literal
  properties are values, not `this`-bound methods), so both the iterable and the iterator
  must be class instances — the same limitation the sync class-iterator path lives with.
  Disclosed as a caveat, not silently mishandled.
