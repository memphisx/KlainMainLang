# TDD-00044: `symbol` V1 (opaque unique values)

- **Status**: Implemented
- **Date**: 2026-08-09
- **Notes**: Scoped to `Symbol()`/`===`/`typeof`/`.description`/`.toString()` only — no dynamic property keys, no well-known symbols, no `Symbol.for` registry

## Context

`docs/status/TYPE-SYSTEM.md` lists `symbol` at 0% — no lexer, parser, or codegen trace of it anywhere in the tree. The usual reasons `Symbol` is hard in a JS/TS implementation — dynamic property keys and well-known symbols like `Symbol.iterator` driving protocol dispatch (`for...of`, etc.) — don't have a cheap answer here: this compiler's objects are fixed-shape heap structs decided at compile time (`docs/status/README.md`'s "What Is NOT Implemented"), and `for...of` over a user class is already a compile-time structural check (`ADR-00063`), not a runtime `Symbol.iterator` lookup. Full `Symbol` is out of reach without dynamic property bags.

But most real use of `Symbol` doesn't need either of those — it needs a guaranteed-unique opaque token, compared with `===`, occasionally printed for debugging. That narrower shape is fully buildable on machinery this compiler already has. Picked up now as a bounded, honestly-scoped V1, the same shape as this project's existing "Staged V1" features (`any`/`unknown`, general unions — `docs/status/TYPE-SYSTEM.md:9-11`): a real, useful subset shipped cleanly, with everything past that subset a clean compile error rather than a silent wrong behavior.

## Design

### Representation: reuse the plain object-struct machinery, don't invent a new heap shape

A `Symbol` is a 1-field heap struct — `{ description: ptr }` — built via `ObjectType([]Field{{Name: "description", Ty: TypePtr}})` exactly like `URLType()`/`HeadersType()` do (`codegen/llvm/types.go:343`), plus a new `IsSymbol bool` marker flag on `Type` (parallel to `IsDate`/`IsURL`) to key every special-case dispatch site below:

```go
func SymbolType() Type {
    ty := ObjectType([]Field{{Name: "description", Ty: TypePtr}})
    ty.IsSymbol = true
    return ty
}
var TypeSymbol = SymbolType()
```

Reusing `IsObject`'s existing struct-alloc/GEP-field-access machinery means `.description` reads (`sym.description`) work with **zero new code** in `emit_exprs_member.go` — same as how `URL.protocol` etc. already come for free from `IsObject`'s generic field path today.

### No id/counter needed — pointer identity *is* uniqueness

The obvious instinct is a global monotonic counter for a `.description`-adjacent `id` field, so `===` can compare ids. Unnecessary: each `Symbol(...)` call already heap-allocates a fresh, distinct struct, and `===`/`!==` on any `IsObject`-shaped pointer already lowers to `icmp eq/ne ptr` (`emit_exprs_operators.go`'s generic comparison switch, reached because `IsObject` is excluded from the string-comparison branch at `emit_exprs_operators.go:100`). Two different `Symbol()` calls get two different heap addresses, so pointer identity alone gives exactly JS's "every Symbol is `===` only to itself" semantics, for free, with no extra field or state. (The one caveat — a freed-then-reused address in `manual` mode coincidentally aliasing two logically-different symbols — is the same pre-existing, documented footgun `Memory.free` already has everywhere else, not something specific to Symbol worth engineering around.)

### Construction: `Symbol()` / `Symbol("desc")`, no `new`

Dispatched exactly like `structuredClone`/`btoa` — a bare-identifier case in `emitCall`'s "Global built-in functions" switch (`emit_call.go:~692`): `case "Symbol": return e.emitSymbolConstructor(ex.Args, ex.GetPos())`. 0 or 1 string argument; missing/omitted description stores `""` (this compiler's established default for an absent string field — same choice already made for a missing JSON string field, see `docs/status/JSON.md`'s ADR-00024 note — rather than trying to model real JS's `undefined` distinction). `new Symbol(...)` is not special-cased and so falls through to the existing "unknown class" rejection `new` already produces for any unregistered name — a real, if generic, compile error, matching real JS's own "Symbol is not a constructor" intent closely enough for V1.

`inferExprType`'s `CallExpression` case (`emit_exprs_types.go:428-432`, where `btoa`/`structuredClone` already report their return type) needs the matching addition: bare `Symbol(...)` infers as `TypeSymbol`. `ResolveTypeName` (`codegen/llvm/types.go:1082`, right next to the existing `case "any", "unknown": return TypeAny`) gets `case "symbol": return TypeSymbol` — the only change needed for `let s: symbol` annotations to resolve.

### `typeof`

`typeofString` (`emit_exprs_operators.go:287`) gains `case ty.IsSymbol: return "symbol"`, checked **before** the existing `case ty.IsObject, ty.IsArray: return "object"` — ordering matters since `SymbolType()` sets `IsObject` too.

### Formatting: one helper, two call sites, one documented deviation from real JS

`emitSymbolToString(val Value) (Value, error)` — GEP-loads `description`, concatenates `"Symbol(" + description + ")"` via the existing `emitStringConcat` — is the single implementation, called from:

- **`.toString()`** — a new `IsSymbol`-keyed check in `emit_call.go` alongside the existing `isDateMethodName(...) && e.inferExprType(mem.Object).IsDate` dispatch (`emit_call.go:86`).
- **`console.log`** — a new explicit branch in `emitConsolePrint` (`emit_call_console.go:19`), same shape as the existing `val.Ty.IsDynamic` branch right above it: check `val.Ty.IsSymbol` before falling through to the generic `PrintfFmt()` path (which would otherwise print the raw struct pointer as if it were a C string — garbage output, not a crash, but silently wrong).
- **Template literals** — `emitValueToString` (`emit_exprs_types.go:36`) gains an `IsSymbol` branch before its generic `v.Ty.IR == "ptr" && !v.Ty.IsObject && ...` passthrough check (line 47 needs `&& !v.Ty.IsSymbol` added to that condition too, or the symbol struct pointer would be passed through as if it were already a raw C string).

**Deliberate V1 deviation, to document explicitly, not silently:** real JS throws `TypeError: Cannot convert a Symbol value to a string` on template-literal interpolation (`` `${sym}` ``) while allowing `console.log(sym)` and `.toString()`. V1 here treats all three identically (all format as `Symbol(desc)`) rather than adding a third, stricter code path — the same kind of documented, deliberate simplification this project already made for `any`'s boolean-printing convention (`docs/status/TYPE-SYSTEM.md`'s Known Limitations table).

### Binary operators: only `===`/`!==`/`==`/`!=` are meaningful

`===`/`!==` fall out for free (see "No id/counter needed" above) via the existing generic `icmp eq/ne ptr` path, since `IsObject` already excludes Symbol from the string-comparison branch. Everything else (`<`, `+`, arithmetic, etc.) needs an explicit reject — real JS throws `TypeError` for all of these on a Symbol operand, stricter than plain objects (which real JS does allow relational-compare via `ToPrimitive`, however meaninglessly). New guard at the top of `emitBinary` (`emit_exprs_operators.go:8`), same shape/style as the existing `dateCompoundAssignGuard`'s rejection message:

```go
if (left.Ty.IsSymbol || right.Ty.IsSymbol) && ex.Op != "==" && ex.Op != "!=" && ex.Op != "===" && ex.Op != "!==" {
    return Value{}, fmt.Errorf("%d:%d: operator '%s' is not supported on symbol — only ===/!== are meaningful", ex.GetPos().Line, ex.GetPos().Col, ex.Op)
}
```

### Real interaction bug this design has to close, found while tracing existing `IsObject`-keyed dispatch

Reusing `IsObject` for the struct representation is what makes `.description` free — but it also means **every existing dispatch site keyed on a bare `ty.IsObject` check will silently mis-handle a Symbol as if it were a plain data object**, unless each one gets an explicit `IsSymbol` carve-out checked first. Found two real, concrete ones by tracing the current dispatch order (not hypothetical — both would produce genuinely wrong, non-crashing output if left unguarded, exactly the failure mode this project's practice refuses to ship):

- **`JSON.stringify`** — `emitJSONStringifyValue` (`emit_call_json.go:178`) checks `if val.Ty.IsObject { return e.emitJSONStringifyObject(val) }` *before* anything else. Left unguarded, `JSON.stringify(Symbol("x"))` would silently serialize as `{"description":"x"}` instead of erroring — real JS omits/errors on a bare symbol argument. Needs an `if val.Ty.IsSymbol { return Value{}, fmt.Errorf(...) }` check ahead of the `IsObject` branch.
- **`structuredClone`** — `emit_structured_clone.go:46`'s reject-list switch (`case ty.IsURL: ... case ty.IsMap: ...`) already exists specifically to intercept special `IsObject`-shaped types before they hit the generic `case ty.IsObject:` deep-clone-by-field-copy path (`:95`). Needs `case ty.IsSymbol:` added to that same reject switch — real JS's `structuredClone` throws `DataCloneError` on a Symbol, and the generic path would otherwise silently field-copy the description into a *new, distinct* struct, breaking the exact identity-based equality this feature exists to provide (a cloned "symbol" that no longer `===` the original — actively worse than most silent-wrong-output cases, since it defeats Symbol's entire purpose).

Any other `ty.IsObject`-keyed dispatch site touched or found during implementation should get the same audit — these two were confirmed by reading the code, not an exhaustive guarantee no others exist.

### Explicitly out of scope for V1

- **Dynamic property keys** (`obj[sym] = 1`) — needs the dynamic-property-bag object model this compiler doesn't have at all; not a Symbol-specific gap.
- **Well-known symbols** (`Symbol.iterator`, etc.) — `for...of` is a compile-time structural check already (`ADR-00063`); there's no runtime protocol dispatch point for a well-known symbol to hook into.
- **`Symbol.for(key)` / `Symbol.keyFor()`** (the global symbol registry) — a real, separate feature (needs a process-wide string→symbol map); no demand signal for it yet, cut the same way `TDD-00043` cut object-member unions from its own V1.
- **`Map<symbol, V>` / using a symbol as an object field key** — `MapType`'s key-type assumptions and the object-field-access path (`Object.hasOwn`'s literal-string-key-only restriction, `ADR-00065`) aren't audited for a Symbol key in this pass; left a clean compile error (whatever happens to occur naturally) rather than explicitly wired through.
- **`instanceof Symbol`** — low-value niche; not wired.

## Open questions

- **Where the new code should live.** Small enough that it could be a handful of inline additions across existing files (`types.go`, `emit_call.go`, `emit_call_console.go`, `emit_exprs_types.go`, `emit_exprs_operators.go`, `emit_call_json.go`, `emit_structured_clone.go`) rather than a new dedicated `emit_symbol.go` — but this project's own file-map convention has generally given even small domains their own file once they're a distinct concept (`emit_memory.go` is 97 lines). Leaning toward a small `emit_symbol.go` housing `SymbolType()`/`emitSymbolConstructor`/`emitSymbolToString`, with the unavoidable scattered call-site edits (typeof, binary guard, JSON/structuredClone reject-list entries) staying in their existing files — not committed, worth a quick look at implementation time.
- **Whether `Symbol()`'s no-arg form should store `""` or need its own `Nullable`-style "no description" marker** distinct from `Symbol("")` (empty string explicitly passed). Real JS's `.description` is `undefined` for the no-arg form specifically. Leaning toward not distinguishing, for the same reason the JSON-missing-string-field precedent didn't (`ADR-00024`) — not committed.
