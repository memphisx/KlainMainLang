# ADR-00109: Destructured function parameters

- **Date**: 2026-08-06

## Context

`docs/status/LANGUAGE-CONSTRUCTS.md` documented `function f({x,y}) {}` / `function f([a,b]) {}` as a confirmed gap: `parser/parser_stmts.go`'s `parseParamList` unconditionally `expect`s `IDENT` for every parameter, so a destructuring pattern in parameter position was a parse error. Picked up at the user's explicit request as part of a broader pass through `LANGUAGE-CONSTRUCTS.md`'s remaining gaps, alongside ADR-00108's operator fixes.

## Investigation

Confirmed three genuinely independent parameter-binding implementations exist, not one shared code path, each needing the identical fix:

- `parser/parser_stmts.go`'s `parseParamList` — used by named `function` declarations (and, incidentally, interface method signatures, which route through the same function).
- `parser/parser_literals.go`'s `parseArrowFunction` — arrow functions parse their **own**, separate parameter list, confirmed by direct testing (a first attempt that only fixed `parseParamList` compiled named-function destructured params fine but still parse-errored on `({x,y}: T) => ...`).
- `codegen/llvm/emit_classes.go`'s class method/constructor parameter-binding loop — a third copy of the same shape as `emit_func.go`'s `emitFunctionDeclAs`, confirmed by direct testing again (a constructor with a destructured param compiled but then failed at codegen with `undefined variable 'x'`).

Confirmed via `codegen/llvm/emitter.go`'s `registerFunctions` that no per-field type inference exists anywhere for object/array shapes — an unannotated plain parameter silently defaults to `number`, but there's no sensible scalar fallback for a pattern. This makes an explicit type annotation the only workable V1 rule: required, not inferred, and enforced as a parse-time error when absent.

Confirmed (`ast/nodes.go`) that the existing statement-level destructuring AST nodes (`ArrayDestructuring`/`ObjectDestructuring`) and their codegen (`emitArrayDestructuring`/`emitObjectDestructuring`) already do 90% of the needed work — both resolve a data/object pointer once via a small `resolve*Ptr` helper, then loop over pattern names/props doing GEP+load+alloca+`e.define`. The loop body itself has no dependency on where the pointer came from (a statement's `Init` expression vs. an already-known incoming parameter register).

Also confirmed the array-vs-object asymmetry that shaped the array-pattern scope: closures (arrow functions) don't support array-typed parameters *at all* yet, independent of destructuring — a pre-existing gap already documented in ADR-00105's own Investigation (`emitClosureFunc`'s param loop always passes every parameter as one plain scalar/`ptr` value, never decomposing an array into its `(ptr, i64)` pair the way a named function's own ABI does). A destructured *array* parameter on an arrow function would hit this identical gap, so it's rejected with a clear error rather than left to silently drop the length. Object-typed closure parameters have no such gap (a plain `ptr`, same as any other closure parameter), so object-destructured arrow parameters work fully.

## Decision

**Parser**: `ast.Param` gained `ArrayPattern []string` / `ObjectPattern []DestructProp` fields (mirroring `ArrayDestructuring.Names`/`ObjectDestructuring.Props`' own shapes exactly, so codegen can share the unpack logic — see below). `Name` still holds a synthetic internal name (`"__param0"`, etc.) for LLVM parameter naming and error messages when a param is a pattern. Both `parseParamList` and `parseArrowFunction` gained an identical pattern-detection branch: when the next token is `{`/`[` instead of `IDENT`, parse the pattern (reusing the same prop/name/hole-parsing loops the statement-level destructuring parsers already have), require a `: Type` annotation immediately after (a clean parse error if absent), and reject a pattern combined with `...` (rest) or `= default` (both real, valid TS, both deliberately out of scope for V1 — rest must bind a collector, not a nested pattern at all; a pattern default needs a null/undefined check on the whole incoming value before unpacking, real added complexity).

**Arrow-function disambiguation**: `parser_literals.go`'s `(` lookahead (deciding whether to parse an arrow function or a parenthesized expression) never checked for a leading `{`/`[` at all — found directly, by testing `({x,y}: Point): number => x*y`, which parse-errored (`expected ), got :`) because the parser fell through to treating `(` as a parenthesized-expression start and choked on the `{x,y}` object literal followed by an unexpected `:`. Fixed with a new bounded lookahead, `destructuredArrowParamLookahead`: scans forward (the parser's token buffer is fully pre-lexed, so unbounded-distance lookahead is cheap) to the matching close brace/bracket and checks for an immediately-following `:` — the same "type annotation always required" rule that already disambiguates a destructured parameter from a plain parenthesized object/array literal expression (`({a: 1})`, `([1, 2])`), which starts identically.

**Codegen**: factored the reusable "unpack a pointer + pattern into named locals" core out of `emitArrayDestructuring`/`emitObjectDestructuring` into `unpackArrayPatternInto`/`unpackObjectPatternInto` (`emit_arrays_core.go`/`emit_objects.go`) — each statement-level function now just resolves its `Init` pointer, then delegates. All three parameter-binding sites (`emit_func.go`'s `emitFunctionDeclAs` and `emitClosureFunc`, `emit_classes.go`'s method/constructor loop) bind the raw incoming parameter under its synthetic name exactly as before, then call the same two functions directly against the already-known pointer — no `Init` expression to fabricate or resolve. `emitClosureFunc` additionally rejects an `ArrayPattern` outright (see Investigation).

**Found and fixed a real, unrelated pre-existing-shaped bug while verifying end to end** (not a hypothetical — reproduced via a growing example file, then bisected to a ~9-line repro): `gatherCaptures` (`emit_func.go`, the closure free-variable scanner that decides what an arrow function needs to capture from its enclosing scope) built its "already bound by this closure" set from `p.Name` alone — for a destructured parameter, that's the synthetic internal name, never the pattern's own field/element names. A destructured field sharing a name with an outer-scope variable (`x`/`y` from a top-level `const [x, y] = ...`, colliding with `({x, y}: Point) => x*y`'s own parameter names) was wrongly free-variable-scanned as a capture of the *outer* binding — and since capture setup runs after parameter unpacking within the same function body, it silently overwrote the correct local (parameter) binding with the captured (outer) one. `x * y` computed the outer values, not the arguments — a genuine wrong-answer bug, not a rejection. Fixed by adding every pattern's field/element names to `gatherCaptures`' bound set alongside `p.Name`.

## Implementation notes

Files touched:
- `ast/nodes.go`: `Param` gained `ArrayPattern`/`ObjectPattern`.
- `parser/parser_stmts.go`: `parseParamList`'s pattern-detection branch; array-pattern hole support (`[, b, c]`) added to match `parseArrayDestructuring`'s existing convention.
- `parser/parser_literals.go`: `parseArrowFunction` gained the identical pattern-detection branch (a separate implementation from `parseParamList`, not shared — see Investigation); new `destructuredArrowParamLookahead`; the arrow-vs-parenthesized-expression `isArrow` condition gained the `{`/`[` case.
- `codegen/llvm/emit_arrays_core.go`: `emitArrayDestructuring` split into itself (resolves `Init`) plus new `unpackArrayPatternInto` (the reusable core).
- `codegen/llvm/emit_objects.go`: `emitObjectDestructuring` split the same way into itself plus new `unpackObjectPatternInto`.
- `codegen/llvm/emit_func.go`: `emitFunctionDeclAs`'s and `emitClosureFunc`'s param-binding loops both gained pattern-unpack branches (`emitClosureFunc`'s array-pattern branch is a rejection, not an unpack — see Decision); `gatherCaptures`' bound-set fix (see Decision).
- `codegen/llvm/emit_classes.go`: the class method/constructor param-binding loop gained the identical pattern-unpack branches as `emitFunctionDeclAs`.

## Side effects discovered

The `gatherCaptures` capture-shadowing bug, already covered under Decision — found and fixed as part of this same piece of work, not deferred.

## Verification

- `go build ./...`, `go vet ./...`, and the full `go test ./...` suite pass (Linux x86-64 dev box) after every incremental change, including after the `gatherCaptures` fix.
- New tests in `tests/func_test.go`: object-destructured params on named functions (including field renaming `{x: px, y: py}`), array-destructured params (including a hole), object-destructured params on arrow functions, object-destructured params on class methods/constructors, a dedicated `TestE2EDestructuredArrowParamShadowsOuterSameNamedVariable` regression test for the capture-analysis bug, `TestE2EParenthesizedObjectLiteralStillParsesAsExpression` (confirms the new arrow-disambiguation lookahead doesn't misfire on `({x:1,y:2})`/`([1,2,3])` used as plain parenthesized literal expressions), and four rejection tests (array-destructured arrow param, missing type annotation, a pattern default value, a destructured rest parameter).
- New example: `examples/basics/destructuring.ts`, extended with a full destructured-parameters section covering every case above — manually built and run end to end, every line matched its inline expected-output comment, both before and after the `gatherCaptures` fix (the "before" run is what surfaced the bug: `area({x:5,y:6})` printed `200`, i.e. the outer `x`(10) × outer `y`(20), instead of `30`).
