# ADR-01330: Dynamic import() shares the program's modules; three backends

- **Relations**: Implements TDD-00238 (Stage 5), Extends ADR-01329, ADR-00515
- **Date**: 2026-10-02

## Context

[TDD-00238](../tdd/TDD-00238.md) Stage 5 has islands share the builtin
library with the program. A dynamic `import()` had two backends:

- `-dynamic-import=eager`, the default, never built
  ([TDD-00055](../tdd/TDD-00055.md) Stages 2–3): every `import()` was a
  compile error pointing at the other flag. As designed it ran the target's
  top-level at startup, whether or not `import()` was reached.
- `-dynamic-import=lazy` ([ADR-00515](ADR-00515.md)): each target an
  independent whole-program compile in a shared library, with its own copy
  of the library, C runtime and event loop, driven by the importer through
  a poll export ([TDD-00225](../tdd/TDD-00225.md)).

A builtin module both sides import was two instances. With the program
setting `EventEmitter.defaultMaxListeners = 5`, a target reading it saw
`10`; Node prints `5`.

## Investigation

- Splitting a target's own IR against the program's (`SplitLibUnits` on
  both): 224 of the island program unit's 1,167 definitions are also
  defined by the program. Most are content-named helpers (one name, one
  body); the rest are runtime singletons (`__process_argv_*`, task and
  well-known-symbol state), `main` and `llvm.global_ctors`.
- Both sides number their own classes from the same base, so their rows in
  the type-id registration tables ([ADR-01325](ADR-01325.md)) would
  collide.
- The event loop is still one IR function whose body depends on the
  program's `used*` flags ([TDD-00240](../tdd/TDD-00240.md) left it until
  the `klain:http` redesign). Running a target on the program's loop by
  seeding the program's emitter with the target's flags would replay
  `ensure*` calls by hand.
- Node's ordering (24.19, measured): a target is evaluated on the fifth
  microtask after `import()`, and the `import()` reaction runs on the
  eleventh; two imports of one target settle on the same microtask.

Rejected: keeping islands as separate compiles and linking them against
the program with duplicate definitions dropped. It fixes the duplicate
instance but not the id collision or the loop, each a further mechanism.

## Decision

`-dynamic-import` takes `bundled` (default), `lazy` or `isolated`;
`eager` is removed.

1. **bundled.** The resolver merges each target like a static import, over
   a dynamic edge. A file only dynamic edges reach (`DynStatements`) does
   not run in `main`: each target's dynamic-only files run, dependencies
   first and each behind its own run-once flag, in the target's module
   body `@__kml_dyn_<h>_body` (`DynModules`). Their top-level bindings are
   module globals, as a library module's are. `import()` calls
   `__kml_dynimport_init` (`dynimportsrc/dynwhen.c`): the target's cached
   module promise, or a new one whose body starts as a task five microtasks
   later. A reaction on the module promise (`__kml_dynimport_when`) builds
   the result object from the module globals and fulfills the `import()`
   promise four microtasks later, or rejects it with the module's reason.
   A top-level `await` parks the task on the program's one loop; a
   top-level throw rejects the module promise, so every `import()` of the
   target. One emission covers the program and every target, so flags,
   type ids and names are shared.
2. **lazy.** The same emission and semantics. A dynamic-only file is
   mangled with `isl_<hash>` (`ast.DynModuleKey`), and a target's body,
   module promise and result builders are named `__kml_dyn_<hash>_*` and
   exported. `SplitIslandUnits` gives each target one unit,
   `isl_t_<hash>`: its body, and each file only it reaches. A file several
   targets reach goes into the program's unit. A program definition only
   one target's code reaches (a closure, a generated helper) moves into
   that target's unit. A definition the executable reaches that names
   island code fails the split. The executable links with exported
   symbols (`-Wl,-export_dynamic`, `-rdynamic`) and without dead-code
   stripping. Each target's unit is compiled position-independent and
   linked as `<binary>.d/<hash>.so|.dylib`, its references to the
   executable left undefined (`-undefined dynamic_lookup` on macOS).
   `import()` opens it (`__kml_dynimport_open`) and finds the body, module
   promise and result builder with `dlsym`.
3. **isolated.** The former `lazy`, unchanged: each target its own
   program, with its own instance of every module it imports. A
   deliberate divergence from Node, kept for programs that want a target's
   import-time state apart from their own. Its own `import()` calls now
   compile `bundled` instead of the unbuilt `eager`.

`--static` refuses `lazy` and `isolated` when the program uses `import()`.
`lazy` refuses Windows (a DLL cannot bind to the executable's symbols
without an import library).

## Implementation notes

- `resolver/resolver.go`: `dynEdges`; the dynamic-only set is computed
  before mangling (`fileKey`); `DynStatements`, `DynModules`, each export's
  `Mangled` name.
- `codegen/llvm/emit_dynmodule.go`: the module body, the result builder,
  the `import()` lowering; `writeDetachedFunc` (`emit_libinit.go`) writes
  both compiled functions, as it writes a library module's init.
  `emitLibInitCalls` skips dynamic-only statements in `main`.
- `codegen/llvm/libsplit.go`: island owners, `moveIslandHelpers`,
  visibility (`setReachable`: hidden within one executable, default when a
  shared library binds to it); `IslandObjects` and `cachedUnitObject`.
- `main.go`: the lazy link and `islandPlacement`. The shared libraries
  (lazy and isolated) are now built before `--run`, which used to start
  the program before its islands existed.
- `inferExprType` and the variable-declaration typing of an `import()`
  expression now mark it a task promise: `const p = import('./m')` was a
  compile error in every backend.

## Side effects discovered

- `JSON.stringify` and `console.log` of a subclass instance behind its base
  class's static type serialized the base class's fields under the base
  class's name. The object split (`emitExtraSplit`) now also takes the
  dynamic path when a class with subclasses holds an instance of another
  class (header type id), outside library code, whose text may not depend
  on the program; the null-guarded JSON branch takes the split too.
- Module namespace objects do not exist: the `import()` result holds the
  target's annotated scalar and string exports only, and `import * as ns`
  cannot be used as a value. `import('node:…')` needs a builtin's
  namespace. Tracked in the BACKLOG.
