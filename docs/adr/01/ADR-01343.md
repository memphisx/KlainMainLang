# ADR-01343: A JWK is a plain object

- **Relations**: Extends ADR-01342, ADR-01339, Superseded by ADR-01347
- **Date**: 2026-10-03

## Context

`crypto.subtle.exportKey("jwk", key)` returned a `Map<string,string>`, so
programs read `jwk.get("kty")`. In Node a JWK is a plain `JsonWebKey`
object: `jwk.kty` reads the member, and `jwk.get` is not a function. Only
key material was present; Node's JWK also carries `key_ops`, `ext` and, for
most algorithms, `alg`. TS2339 for builtin interfaces (ADR-01342) now
rejects `jwk.get` as tsc does, and `jwk.kty` was a codegen error ("field
access on non-object").

The same gate found that a `-compat=js` prototype constructor's
`Base.call(this, …)` threw "Cannot set properties of a non-object value".

## Investigation

- Node 24's member order: `key_ops`, `ext`, `alg` (when the algorithm names
  one), `kty`, then the key material. EC keys list `x`, `y`, `crv`, `d`. RSA
  keys list `n`, `e`, `d`, `p`, `q`, `dp`, `dq`, `qi`. `alg` is
  `HS1`…`HS512`, `A128GCM`/`A256CBC`…, `RSA-OAEP`/`RSA-OAEP-256`…,
  `PS1`…`PS512`, and absent for ECDSA. `key_ops` lists the key's usages in
  Web Crypto's order.
- A boxed string must be the runtime's length-prefixed form, 8-byte aligned.
  A C literal is neither, and a raw pointer from the crypto shim has no length
  prefix.
- `Animal.call(this, name)` reached the `Function.prototype.call` intrinsic
  through the lowered-call fallback (ADR-01339). That fallback runs before
  `emitCall`'s prototype-constructor path, which applies the constructor to
  the receiver object.

## Decision

1. `exportKey("jwk")` builds a dynamic object. `__kml_jwk_new`
   (`dynobjsrc/jwk.c`) sets the leading members from the key's algorithm,
   hash and usages, and the key material follows in Node's order. Its codegen
   type is `any`, so member reads, `Object.keys`, `JSON.stringify` and
   `console.log` take the dynamic-object paths. The Map setter's
   handwritten IR is deleted.
2. `importKey("jwk", …)` reads each member of any object (`__kml_any_get_cstr`);
   an object literal keeps its compile-time path.
3. `jwk.c` is a runtime unit linked only by programs that use a JWK, so the
   dynamic-object runtime does not pull in the dynamic-array one.
4. `Function.prototype.*` intrinsics do not apply to a `-compat=js`
   prototype constructor.

## Implementation notes

`codegen/llvm/{emit_call_crypto,emit_exprs_types,emit_lowered,runtime_dynarr,
runtime_crypto_subtle,embedded_c,emitter}.go`, `codegen/llvm/dynobjsrc/jwk.c`,
`tests/webcrypto_test.go`, `examples/crypto/crypto.ts`.

## Side effects discovered

- Tests and the example that tsc rejects were corrected: an RSA key
  generated without `publicExponent`, and a socket `'error'` listener reading
  `err.code` on an `Error` (now `NodeJS.ErrnoException`).
- Still open: `importKey` does not validate a JWK's `kty`, `key_ops`, `ext` or
  `alg`.

## Verification

Mac (Apple Silicon), against Node v24.19: JWK probes for HMAC, AES-CBC,
AES-GCM, ECDSA P-256/P-384 and RSA-OAEP. The targeted E2E groups: JSMode,
Subtle, WebCrypto, Crypto, NetConnect, FunctionCall.
