# ADR-00120: RegExp Stage 6 — `--static` linking verification

- **Relations**: Implements [TDD-00035](../tdd/TDD-00035.md). Extends [ADR-00114](ADR-00114.md), [ADR-00115](ADR-00115.md), [ADR-00116](ADR-00116.md), [ADR-00117](ADR-00117.md), [ADR-00118](ADR-00118.md), [ADR-00119](ADR-00119.md)
- **Date**: 2026-08-07

## Context

[TDD-00035](../tdd/TDD-00035.md)'s Stage 6 — the last stage of the whole RegExp feature — is verifying `--static` linking actually works for a `RegExp`-using program, not new language behavior. The TDD predicted this would be "materially simpler than curl's static story" since PCRE2 has no TLS-backend-driven transitive dependency chain the way libcurl does, but explicitly flagged this as "expected easy, verify before declaring it so" rather than assumed. Picked up to close out the feature, per the user's "let's wrap this up."

## Investigation

**Confirmed the prediction directly, on both a bare Linux build and inside a real Docker container, rather than trusting it.** On the x86-64 Linux dev machine directly: `klainmain --static` against a program exercising `.match()`/`.replace()`/`.split()`/`.search()` linked with **zero extra flags** — no special `-l` list, no clang-then-gcc two-step workaround (`ADR-00033`'s curl recipe needed both). Verified the result was genuinely static via `file` (reports "statically linked") and `ldd` (reports "not a dynamic executable" — the correct output for a real static binary, not an error), then confirmed the program's actual output was correct (matched a native, non-static build of the identical program byte-for-byte). Confirmed `libpcre2-8.a` (the static archive `-static -lpcre2-8` needs) was already present on this machine as a side effect of `libpcre2-dev` already being installed (per [ADR-00114](ADR-00114.md)'s noted requirement) — Debian/Ubuntu's `-dev` packages bundle both the `.so` symlink and the `.a` archive together, no separate static-specific package needed.

**Repeated the same verification inside an actual Docker container** (`docker build`/`docker run`, both genuinely executed, not assumed) using the exact three-stage shape `docker/Dockerfile` (the original, non-fetch `--static` demo) already established — build the compiler with `golang:1.26-alpine`, statically compile the demo program on `alpine:3.21` with `clang musl-dev pcre2-dev` (no `pcre2-static` package needed — Alpine's plain `pcre2-dev` already includes the archive), then copy just the resulting binary into a `FROM scratch` final stage with nothing else in it at all. The build succeeded with the exact same "no special flags" simplicity as the bare Linux test, and running the resulting container printed output identical to both the native build and the Docker build's own compile-time run — genuine proof it works, not merely that it linked: `scratch` has no libc, no dynamic linker, and no shell at all, so a binary that wasn't truly self-contained couldn't even start.

## Decision

No code changes — this stage is purely verification, and the TDD's own prediction is confirmed correct: `--static`'s existing implementation (`main.go`) and `RegExpType`'s existing dynamic-linking convention (`requireLink("pcre2-8")`, [ADR-00114](ADR-00114.md)) already compose correctly for the static case with no special-casing needed anywhere. The one artifact this stage adds is a new Docker verification harness, `docker/Dockerfile.regexp-test` + `docker/regexp-demo.ts`, mirroring `docker/Dockerfile`'s simple single-stage `--static` shape (not `docker/Dockerfile.fetch-test`'s more elaborate clang-then-gcc workaround, since none of that complexity turned out to be needed here) — kept as a permanent, re-runnable confirmation of this finding, the same role `Dockerfile.fetch-test` already serves for curl.

## Implementation notes

Files added: `docker/Dockerfile.regexp-test`, `docker/regexp-demo.ts` (exercises `.match()`/`.matchAll()`/`.replace()`/`.split()`/`.search()` together, printing output that's easy to eyeball-verify against the same program run natively).

`docker/regexp-demo.ts` intentionally avoids declaring a top-level `const g` (or any other name already used in `examples/regexp/regexp.ts`) — not because of any actual naming conflict between the two files (they're compiled completely independently, in separate `klainmain` invocations), but out of habit after [ADR-00119](ADR-00119.md)'s own naming-collision mistake within a single file.

## Side effects discovered

None.

## Verification

- Direct Linux build: `klainmain --static docker/regexp-demo.ts` linked cleanly with no extra flags; `file`/`ldd` confirmed genuine static linking; output matched a native (non-static) build of the same program exactly.
- Docker: `docker build -f docker/Dockerfile.regexp-test -t kml-regexp-static .` succeeded (Alpine/musl, `clang musl-dev pcre2-dev` only); `docker run --rm kml-regexp-static` printed correct output from inside a `FROM scratch` container with nothing else in it — the strongest form of "this binary is genuinely self-contained" proof available, since a non-static binary literally cannot start in that environment at all.
- This closes out [TDD-00035](../tdd/TDD-00035.md) — all 7 stages (0 through 6) are now done; the TDD's own `Status` line moves from `Partially Implemented` to `Implemented`.
- Verified on: x86-64 Linux only (both the bare build and the Docker container, which itself ran as `linux/amd64`) — per this project's standing platform-verification rule, `--static`+PCRE2 has not been separately verified on the Apple Silicon Mac. This is a smaller gap than it might sound: `--static` itself is already Linux-only by design (`main.go` refuses it immediately on macOS, unrelated to RegExp), so there is no separate macOS "does `--static` work with PCRE2" question to answer at all — only the ordinary (non-static) PCRE2 dynamic-linking story ([ADR-00114](ADR-00114.md), [ADR-00115](ADR-00115.md), [ADR-00116](ADR-00116.md), [ADR-00117](ADR-00117.md), [ADR-00118](ADR-00118.md), [ADR-00119](ADR-00119.md)) still carries that outstanding cross-platform re-verification note.
