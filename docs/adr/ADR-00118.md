# ADR-00118: RegExp Stage 4 — str.replace() and str.replaceAll()

- **Relations**: Implements [TDD-00035](../tdd/TDD-00035.md). Extends [ADR-00114](ADR-00114.md), [ADR-00115](ADR-00115.md), [ADR-00116](ADR-00116.md), [ADR-00117](ADR-00117.md)
- **Date**: 2026-08-07

## Context

[TDD-00035](../tdd/TDD-00035.md)'s Stage 4 is `str.replace(regexp, replacement)`/`str.replaceAll(regexp, replacement)`, explicitly flagged in the TDD as "the single most novel piece of the whole feature" because of callback-function replacement — a C-side match loop calling back into a KML closure. Picked up directly following Stage 3, per the user's "continue with Stage 4."

## Investigation

**Confirmed Stage 3's two-pass "re-run the match sequence twice" convention is unsafe to reuse directly for replace().** `.match()`/`.matchAll()`'s `emitRegexCollectGlobalMatches` ([ADR-00117](ADR-00117.md)) runs the entire match loop twice because *matching itself* has no observable side effects. Computing a replacement can: the callback form calls into real KML code, which the spec (and ordinary programmer expectation) requires happens exactly once per match — running it twice would double any side effects (a counter increment, a `console.log`, anything). This ruled out naively extending the existing two-pass helper and required a genuinely different, 3-pass structure for the multi-match case: **pass 1** counts matches (pure — extracted the existing count-only loop out of `emitRegexCollectGlobalMatches` into a new shared `emitRegexCountGlobalMatches`, used by both Stage 3 and Stage 4 now); **pass 2** re-matches once for real, computing each match's replacement text exactly once and storing `(start, end, replacement ptr, replacement len)` into four count-sized parallel arrays; **pass 3** (pure — no re-matching, no re-invoking anything) sums the final output length from the already-computed pieces and builds the result string. Verified this design directly with a real side-effect-counting test (a closure incrementing a counter once per match) before trusting it.

**Confirmed replace()/replaceAll() need the match's raw byte offsets, which nothing built so far exposed.** `.exec()`'s own result array deliberately omits `index`/`input` (a documented Stage 2 scope narrowing) — correct for `.exec()` itself, but replace needs to know exactly *where* in the subject a match occurred to correctly copy the surrounding "gap" text. Extended `emitRegexSingleMatchCore`'s signature to also return the raw match start/end byte offsets (`-1`/`-1` on no match) alongside its existing exec-shaped result array — a backward-compatible addition; every pre-existing caller (`.exec()` itself, `.match()`, `.matchAll()`) now just discards the two new return values (`_, _`) since none of them need offsets.

**Confirmed a genuine arity mismatch rules out the TDD's own suggested callback shape.** The TDD's Design section recommended `(match, ...capturedGroups, offset, string)`. Checked how this compiler actually invokes a resolved callback (`emitCBCall`, `emit_func.go`) and confirmed the generated `call` instruction's argument list must exactly match the callback's own statically-declared parameter count (`cb.paramTypes()`) — there is no variadic/spread-call support to pass a runtime-variable number of arguments (a pattern's capture count is only known at runtime; a callback's arity is fixed at compile time). Verified this is exactly how the existing array-HOF callback convention already works too (`emitArrayMap`'s `if cb.arity() >= 2 { ... }`, a compile-time-only conditional never gated on anything runtime). Concluded the TDD's suggested shape is unbuildable as stated and narrowed the real V1 shape to a fixed `(match, offset, string)` — dropping the variadic capture-group spread entirely, with a callback declaring more than 3 parameters rejected as a compile-time error rather than silently producing a broken call. This is a real, deliberate divergence from the TDD's own Design text (left as-is, per the project's established convention of correcting mistakes in the ADR rather than retrofitting the TDD — see [ADR-00117](ADR-00117.md) for the precedent).

**Confirmed backreference template expansion ($1-$9/$&/$$) can reuse `.exec()`'s already-extracted group strings directly**, rather than needing separate raw-ovector access: a match's group text is already available as `match[N]` (index `N` of the exec-shaped result array `emitRegexSingleMatchCore` already builds), so `$N` just becomes "look up element `N`," with an in-range check against the array's own length (`extractvalue match, 1`) to leave an out-of-range `$N` as literal text, matching real JS, rather than an out-of-bounds read.

**Decided against a true two-pass scan for template expansion** (count the expanded length, then build) in favor of a single pass sized against a cheaply-computed safe upper bound (template length + sum of every group's length — the worst case if every `$N` expanded to its full group text). This avoids writing the character-by-character `$`-escape scanning logic twice, at the cost of a small amount of wasted `malloc` space, which "not production-ready, never expected to be" (`README.md`) makes an easy tradeoff.

## Decision

- `emitRegexSingleMatchCore` (`emit_regexp.go`) now returns `(result Value, matchStartReg, matchEndReg string)` — a backward-compatible signature extension (see Investigation). All four pre-existing call sites updated to discard the two new values where unused.
- New `emitRegexCountGlobalMatches(regexVal, strVal Value) string` (`emit_regexp.go`), extracted from `emitRegexCollectGlobalMatches`'s first phase — the shared, side-effect-free "how many matches are there" pass both Stage 3's two-pass collector and Stage 4's three-pass replacer now call.
- New file `codegen/llvm/emit_regexp_replace.go` (Stage 4's own complexity justified splitting it out of the already-large `emit_regexp.go`, matching this project's established file-splitting convention once a domain outgrows one file):
  - `regexReplacer` + `resolveRegexReplacer`: resolves `replace()`/`replaceAll()`'s second argument exactly once — either a `Callback` (via the existing `resolveCallback`, rejecting arity `> 3`) or a literal template `Value`.
  - `emitRegexComputeOneReplacement`: computes one match's replacement text — either `emitRegexExpandTemplate` (pure, template `$`-escape expansion) or exactly one `emitCBCall` (the callback path, `(match, offset?, string?)` per the resolved arity).
  - `emitRegexExpandTemplate`: single-pass `$1`-`$9`/`$&`/`$$` backreference expansion against one match's already-extracted group strings, sized against the safe upper bound described in Investigation. `` $` ``/`$'` (pre-/post-match text) remain explicitly out of scope, per the TDD's own original narrowing.
  - `emitRegexReplaceSingleMatch`: the non-global `str.replace()` case — at most one `emitRegexSingleMatchCore` call; on a match, splices `subject[0:start] + replacement + subject[end:]` via three `memcpy`s; on no match, returns the original subject string unchanged (real strings are immutable, so reusing the same pointer is safe).
  - `emitRegexReplaceAllMatches`: the shared 3-pass multi-match algorithm described in Investigation, used by both `str.replace()` (when `global` is true) and `str.replaceAll()` (always, after its own guard).
  - `emitRegexReplace`: the entry point both `emitStringReplace`/`emitStringReplaceAll` (`emit_strings.go`) now call once their pattern argument is confirmed `IsRegExp`, ahead of the existing literal-string implementation (which is otherwise completely unchanged — a non-`RegExp` first argument still goes through exactly the pre-existing `__kml_replace`/`__kml_replace_all` path). `requireGlobal` (true only for `replaceAll`) throws a catchable `TypeError` for a non-global RegExp (matching real JS) before doing anything else; `replace()` itself never throws for this, instead branching on the `global` flag at runtime between the single-match and all-matches builders.
- No `inferExprType`/`emit_exprs_vardecl.go` changes were needed at all — unlike every prior stage, `replace`/`replaceAll` already existed as string methods returning a plain string (`TypePtr`) regardless of pattern kind, so the existing unconditional inference cases already cover the new RegExp-backed path correctly.

## Implementation notes

Files touched: `codegen/llvm/emit_regexp.go` (the `emitRegexSingleMatchCore` signature extension and its four call-site updates, the `emitRegexCountGlobalMatches` extraction), new `codegen/llvm/emit_regexp_replace.go`, `codegen/llvm/emit_strings.go` (two `IsRegExp` guard insertions ahead of the existing literal-string bodies).

`emitRegexReplaceAllMatches`'s pass 2 stores into four separately `malloc`'d parallel arrays (`starts`, `ends`, `replPtrs`, `replLens`) rather than one array-of-structs — simpler `getelementptr` arithmetic at every call site (`i64`/`ptr`-typed uniform GEPs throughout, no struct-layout offset math), at the cost of four allocations instead of one; not expected to matter for this project's stated scope.

## Side effects discovered

None found while implementing this stage specifically.
