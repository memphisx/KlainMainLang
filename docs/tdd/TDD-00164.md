# TDD-00164: General C FFI — AOT `node:ffi` (`dlopen` + static signatures + closure→C-pointer trampolines)

- **Status**: Not Started
- **Date**: 2026-09-03

## Context

[TDD-00150](TDD-00150.md) Stage 2 ("General C FFI foundation") is the pivot that
unlocks its own Stages 3–5 (`opentui`, `vue-termui`, `ink`) plus the GUI
crossover ([TDD-00032](TDD-00032.md): GTK/Qt/SDL2/raylib/imgui) and a long tail
of C libraries (`libpq`, `hiredis`, `ncurses`, compression). TDD-00150 named it
concretely but explicitly deferred a real design ("may be worth splitting into
its own top-level TDD when picked up"), and [TDD-00032](TDD-00032.md) is a
self-described bootstrapping placeholder. This TDD is that split-out: the
concrete design for general C FFI. TDD-00032 and TDD-00150 Stage 2 are its
antecedents; nothing in their bodies is edited (design content is immutable
post-hoc) — this document supersedes their placeholder FFI sketch and is what
implementation starts from.

**What forces the design now: Node shipped a first-party FFI.** As of Node
v26.1.0 there is an official, experimental `node:ffi` module (`--experimental-ffi`).
Before it, FFI was userland-only (`node-ffi-napi`, `koffi`) with no canonical
API, so any FFI we built would have been bespoke `klain:` surface by necessity.
That is no longer true. Under this project's faithfulness-first rule and the
`klain:` namespace convention (real Node module names get the real Node API;
bespoke re-imaginings live under `klain:`), the FFI foundation should now
implement the **actual `node:ffi` API** — a program that uses Node's FFI would
then compile here unchanged, rather than needing rewrite to a house dialect.

The fit is unusually good, because `node:ffi` is a thin, static-friendly surface
that maps almost 1:1 onto machinery this compiler already has:

- Its **type-name enum** (`int8`…`uint64`, `float32/64`, `char`, `bool`,
  `pointer`, `string`, `buffer`, `arraybuffer`, `function`, plus aliases
  `i8/u8/…/ptr/str/f32/f64`) is nearly the JSDoc int-width set we already parse
  (`jsdoc/`), and its rule "64-bit integers marshal to `bigint`" is a model we
  already have ([TDD-00101](TDD-00101.md)).
- Its **signatures are plain objects** — `{ arguments: ['int32','int32'],
  return: 'int32' }` — which for an AOT compiler is *easier* than for Node: Node
  parses them at runtime, we can resolve a statically-written signature at
  compile time and emit a direct, correctly-typed C-ABI call.
- Its **library-load** primitives (`dlopen`/`dlsym`/`dlclose`) are the exact
  `ensure*()`-declared-libc-primitive shape `os`/`fs`/POSIX-signal support and
  the TDD-00031 TTY shim already use.

The one genuinely hard piece is unchanged in difficulty and is exactly the gap
TDD-00032/TDD-00150 already flagged: **`library.registerCallback` — handing a
KlainMainLang closure to C as a raw C-callable function pointer** (the
closure→C-function-pointer trampoline). Every callback-driven C API (GUI event
loops, GLib signals, `opentui` render callbacks, `qsort`-style comparators)
needs it.

## Design

### Target surface — real `node:ffi`, AOT-lowered

Implement `import { dlopen, DynamicLibrary, suffix, types, ... } from 'ffi'`
(the Node module id is `node:ffi`; the resolver's Node-name handling applies).
The surface, grouped:

**Library loading / functions**
- `ffi.dlopen(path, definitions?) → { lib: DynamicLibrary, functions }`
- `class DynamicLibrary` — `new DynamicLibrary(path)`, `.getFunction(name, sig)`,
  `.getFunctions(defs)`, `.getSymbol(name) → bigint`, `.close()`, and
  `[Symbol.dispose]()` to drive `using` — but `using` and `[Symbol.dispose]`
  method keys are both unimplemented today (see Prerequisites), so `.close()` is
  the shipping disposal path and the `using` sugar is a separate follow-up.
- `ffi.suffix` (`'dylib'`/`'so'`/`'dll'`), `ffi.dlclose`, `ffi.dlsym`,
  `ffi.types` (type-name constants).

**Callbacks**
- `library.registerCallback([sig,] closure) → pointer`,
  `.unregisterCallback(ptr)`, `.refCallback`/`.unrefCallback`.

**Raw memory helpers**
- `ffi.toString(ptr)`, `ffi.toBuffer/toArrayBuffer(ptr, len[, copy])`,
  `ffi.exportString/exportBuffer/exportArrayBuffer/exportArrayBufferView(...)`,
  `ffi.getRawPointer(src)`, and the primitive accessors
  `ffi.getInt8/16/32/64` + setters (and unsigned/float variants).

### Lowering model — three pieces

**1. The typed call (the easy 80%).** A signature object is a compile-time
constant. `getFunction(name, sig)` binds a symbol (via `dlsym` on the loaded
handle) to a callable whose LLVM type is derived directly from `sig.arguments` /
`sig.return` using the existing C-ABI type mapping (`int32`→`i32`,
`float64`→`double`, `pointer`/`string`/`buffer`→`ptr`, `int64`/`uint64`→`i64`
surfaced as `bigint`). Calling it emits a normal indirect `call` through the
resolved symbol pointer — the compiler already lays out and calls C-ABI
functions correctly for every `runtime_*.go` decl; this exposes that machinery
to user code instead of hard-coding each callee. Argument marshalling reuses the
existing coercions: a JS `string` argument for a `string`/`pointer` param passes
the already-NUL-terminated interned pointer; a `Buffer`/typed-array passes its
data pointer; a `bigint` passes as `i64`.

**2. `dlopen`/`dlsym`/`dlclose` (mechanical).** `ensure*()`-declare the three
libdl entry points once and wrap them. `getSymbol` returns the raw address as a
`bigint`. `DynamicLibrary` is a small handle object (a pointer field), same
shape as the existing value-handle types.

**3. The closure→C-function-pointer trampoline (`registerCallback`, the hard
20%).** A KlainMainLang closure is `{ fn-ptr, env-ptr }` (two words); a C
function pointer is one word and carries no env. The trampoline is a generated
C-ABI wrapper, one per callback *signature*, that (a) has the exact C-ABI
prototype the signature describes, (b) recovers the specific closure's env, and
(c) calls the closure with the marshalled arguments and marshals the return.
Env recovery without a per-callback thunk allocator is the crux — options in
Open questions. This is the single new codegen capability; everything else is
assembly of existing parts.

### Relationship to the AOT model

The whole-program/no-runtime-`require()` constraint ([ADR-00022](../adr/ADR-00022.md))
does **not** block this: `dlopen` loads a *native* `.so`/`.dylib` at runtime,
which is unrelated to JS module resolution — no JS is imported at runtime. The
real constraint lands on the *signature* and possibly the *path*: a signature
must be statically resolvable (a literal object at the `getFunction` call site or
in the `dlopen` definitions map), and the callback trampoline is emitted per
statically-known signature. A fully dynamic, runtime-computed signature is out of
scope (and is exotic even in Node usage).

### Staging within this TDD

- **Stage A — load + typed calls, no callbacks.** `dlopen`/`DynamicLibrary`/
  `getFunction`/`getSymbol`/`suffix`/`close`, scalar + pointer/string/buffer
  args and returns. Proves the end-to-end path against a trivial `add_i32` and a
  real libc call (`strlen`, `getpid`). Ships standalone value.
- **Stage B — raw memory helpers.** `toString`/`toBuffer`/`toArrayBuffer`/
  `export*`/`getRawPointer`/primitive get/set. Needed for any real pointer-out
  API. Mostly wraps existing Buffer/ArrayBuffer machinery.
- **Stage C — `registerCallback` trampolines.** The closure→C-pointer path. The
  hard-part rule ([feedback: don't defer the hard part]) applies to the *TDD's*
  completeness, not each stage: Stage C is the load-bearing piece and this TDD is
  not "done" until it closes — but A/B ship real value first and are ordered for
  incremental delivery, not as a way to drop C.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| C-ABI type layout + direct extern-call machinery | Built (internal) | Every `runtime_*.go` decl already lowers to a correct C-ABI call; this TDD exposes it to user code rather than adding it |
| JSDoc int-width type set (`int8`…`uint64`, `float32/64`) | Built | `jsdoc/`; nearly identical to `node:ffi`'s type-name enum — reuse the parse/lower |
| `bigint` for 64-bit ints | Built | [TDD-00101](TDD-00101.md); `node:ffi` marshals 64-bit ↔ `bigint` |
| `Buffer`/`ArrayBuffer`/typed arrays + data pointers | Built | The `export*`/`toBuffer` helpers wrap these |
| `ensure*()` libc-primitive pattern | Built | `dlopen`/`dlsym`/`dlclose` follow the `os`/TTY-shim shape exactly |
| Closure representation (`{fn-ptr, env-ptr}` + heap env) | Built | The trampoline recovers env from this; capture machinery ([TDD-00057](TDD-00057.md)) is the substrate |
| Closure→C-function-pointer trampoline | **Missing** | The one new codegen capability (Stage C); the core gap TDD-00032/TDD-00150 named |
| `using` / `Symbol.dispose` scope-exit disposal | **Missing** (verified 2026-09-03, Mac) | Two distinct gaps: (a) `using`/`await using` is not a recognized declaration form — `using r = new R()` lexes `using` as a plain identifier (`undefined variable 'using'`), no parser/lexer support; (b) `[Symbol.dispose]()` method keys are rejected at parse (well-known-symbol computed keys are [TDD-00063](TDD-00063.md) Stage 3, still open). Plain `.close()` works, so explicit disposal is the fallback and `using` is a self-contained follow-up (its own parse form + scope-exit-disposal codegen, gated on the symbol-key work for the protocol method) |

## Open questions

- **Trampoline env recovery.** A C function pointer carries no env word, so a
  generated wrapper needs to find *which* closure it belongs to. Candidates:
  (a) one static wrapper per signature that reads the env from a
  registration-table slot keyed by an index baked into a family of pre-emitted
  wrappers (bounded number of live callbacks per signature — simple, no runtime
  codegen, caps concurrent callbacks); (b) runtime-allocated executable thunks
  (`libffi` closures / a hand-rolled trampoline page) that close over the env
  pointer (unbounded, but needs W^X-aware executable memory and is the most
  portability-hostile piece); (c) restrict to callbacks C invokes with a
  `void* user_data` argument (GLib/GTK, `qsort_r`, most modern C callback APIs
  pass one) and thread the env through it — zero trampoline machinery, but not
  universal. Likely (c) as the first-class path + (a) as the bounded fallback for
  no-`user_data` APIs; (b) only if forced.
- **`dlopen` path constancy.** Require a compile-time-constant path, or allow a
  runtime string with the signature set still static? Node allows a runtime path;
  a runtime path is compatible with AOT as long as signatures are static.
- **`ffi.types` / signature ergonomics.** Accept the plain-object signature form
  only, or also a JSDoc/`extern`-style typed declaration as a
  compiler-native alternative (a `klain:`-flavored sugar that lowers to the same
  thing)? Faithfulness says the object form is the contract; a sugar is optional.
- **Safety posture.** `node:ffi` is explicitly unsafe (bad signatures crash the
  process). Match Node's "you're on your own" stance, or add opt-in guards
  (arity/type checks at the boundary under a debug flag)? Node-faithful default
  is no guards; a guarded mode fits the project's "options as the differentiator"
  identity as an opt-in.
- **Fast-FFI tiers.** Node documents a Fast-FFI path (register-limited, per-arch)
  vs. a generic path. We emit a direct C-ABI call always, which *is* the fast
  path; no need to model the two tiers — confirm nothing in the observable API
  depends on the distinction.
- **Relationship to `--experimental-ffi`.** Node gates this behind a flag. Do we
  gate `node:ffi` availability behind a compiler flag (mirroring the experimental
  status), or expose it unconditionally? A flag keeps parity with Node's own
  signalling that the surface may shift.
