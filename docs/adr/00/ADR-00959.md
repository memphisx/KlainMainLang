# ADR-00959: Incremental `res` Writable — mid-handler chunked streaming, `req.pipe(res)`

- **Relations**: `Implements TDD-00195` (Stage 2 remainder). Extends `ADR-00825` (res.end-driven flush model), `ADR-00824` (req as a Node Readable).
- **Date**: 2026-09-15

## Context

A server `res` (`http.createServer((req, res) => …)`) was a buffered value object:
`res.write`/`res.end` string-concatenated into a `body` field flushed as one
Content-Length response *after* the handler returned (TDD-00131, ADR-00300).
There was no incremental socket write, no `req.pipe(res)`, and no way for a
handler to stream a response chunk-by-chunk mid-execution — the last open part of
TDD-00195 Stage 2, and a REST-server (priority #1) gap.

## Investigation

The returned-body streaming path (`%kml.hws`, `runtime_http_stream.go`) already
owns a connection fd and frames chunked responses, but it is driven by a
*returned* `ReadableStream` body via promise reactions, not by imperative
`res.write`. The Node `Writable`/pipe machinery already exists in full: a WHATWG
writable (`__kml_ws_alloc`/`_write`/`_close`, `runtime_streams_writable.go`) whose
`{fp,env}` sink closures `__kml_ws_advance` invokes, and `__kml_pipe_to`
(`runtime_streams_pipe.go`) which drives any such writable from a Node Readable.
`req` is already a Node Readable (ADR-00824), and `req.pipe(x)` routes through
`reqAsNodeReadable` → `emitNodeStreamCallOn` (`emit_call.go:764`).

The obstacle TDD-00195 named is fd-ownership: the dispatcher flushes a *returned*
response, whereas a streamed `res` takes the fd *mid-handler*. Reconciling the two
without a new reactor capability was the design question. A full `res`-as-Node-
`Writable` retype was rejected as needlessly invasive (it would rewrite the
`(req,res)` handler typing, `writeHead`/`setHeader`/`statusCode`, and the buffered
tail); instead `res` keeps its `ServerResponseType` identity and *lazily owns* a
WHATWG writable whose sink frames to the fd.

## Decision

`ServerResponseType` gains `__kml_fd` (the connection fd, stored by the dispatcher
before the handler runs), `__kml_wsink` (a lazily-built WHATWG writable, null until
streaming starts), `__kml_streaming` (0 buffered · 1 streaming · 2 ended),
`__kml_keepalive` (decided at head-send), and `__kml_reqheaders`.

- **First `res.write`** calls `__kml_res_begin`: send the chunked head (status +
  serialized headers, `Transfer-Encoding: chunked`, keep-alive decided from the
  request + response headers), clear `O_NONBLOCK` for the stream's lifetime, and
  build the sink whose write closure frames one chunk to the fd and whose close
  closure writes the terminal `0\r\n\r\n`. Each chunk goes through `__kml_ws_write`
  (`res.write`) — the identical entry point `__kml_pipe_to` drives — so the write
  returns Node's backpressure boolean (always `true`: blocking writes drain
  immediately).
- **`res.end`** branches at runtime on `__kml_streaming`: if a prior `res.write`
  began streaming, close the sink (terminal chunk, restore `O_NONBLOCK`, set
  `ended`, poke); otherwise fall back to the buffered path (append to `body`, flip
  `ended`) so the common `res.end('hi')` still sends a single Content-Length
  response — faithful to Node.
- **The dispatcher** reads `__kml_streaming` after the handler (and its
  `emitParkUntilResEnded`): if the response streamed, skip the buffered flush
  entirely and re-arm the connection (keep-alive) or close it, reading
  `__kml_keepalive`.
- **`req.pipe(res)`** starts streaming, then passes `res.__kml_wsink` as the
  `__kml_pipe_to` destination — reusing the pipe machinery unchanged.

Writes are blocking (matching the buffered path and `%kml.hws`); a slow client
blocks the connection's fiber rather than applying socket-level backpressure. That
is a server-wide property (no reactor scans a socket fd for writability), not a
res-specific gap, so true `'drain'` backpressure is a documented perf follow-up
rather than a behavioral divergence.

## Implementation notes

- New `runtime_http_reswrite.go` (`ensureResStreamRuntime`): `__kml_res_begin`,
  `__kml_res_sink_write`, `__kml_res_sink_close`. HTTPS/1.1 routes chunk writes
  through the TLS shim and forces keep-alive off (streamed re-arm over TLS is not
  yet validated).
- `res.end`'s stream branch always emits `@__kml_ws_close`, so the `end` codegen
  must pull `ensureResStreamRuntime` even when no `res.write` appears in the
  handler.
- The runtime template's `strings.NewReplacer` must list longer tokens first
  (`WSINK` before `WS`) since the Replacer resolves ties by argument order.

## Side effects discovered

- `res.write` chunks are stringified (matching the buffered path); a binary
  `Uint8Array`/`Buffer` chunk to `res.write` directly is not yet framed as raw
  bytes (`req.pipe(res)` carries bytes verbatim). Tracked in `docs/status`.
