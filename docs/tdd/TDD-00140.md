# TDD-00140: The `node:test` runner — test/describe, TestContext, hooks

- **Status**: Implemented
- **Date**: 2026-08-28

## Context

Two motivations, equally weighted: `node:test` is a 60-file
MODULE_NOT_IMPLEMENTED block in the Node oracle (plus ~43 harness files
skipped outright on `require('node:test')`), and — more importantly for the
project itself — a native test runner is what makes this compiler usable for
writing real unit tests for one's own code, portably with Node.

The corpus histogram (87 files using the runner): `test(` 434, `it(` 159,
`describe(` 42, module-level `after(` 42, subtests `t.test(` 65, `t.after(`
41, `suite`, a couple of `beforeEach`/`afterEach`; callbacks split ~207
`(t)` / ~153 `()`.

## Design

### Execution model: run-at-registration

Node defers all tests and runs them after the main module finishes. This
compiler runs each test **immediately at its registration site**, awaiting
async bodies inline (the established inline-async posture). For a normal
test file — declarations of tests, nothing meaningful after — the observable
behavior matches; the divergence (top-level code after a `test()` call runs
*after* that test here, *before* it in Node) is disclosed. This avoids a
deferred-closure registry of heterogeneous captured environments, which the
closure model would fight.

### Failure capture

Each test body runs inside the existing setjmp exception frame
(`__kml_push_jmpbuf`/`setjmp`, the same structure `emitTry` emits): a thrown
assertion (all of `assert.*` throw catchable errors) or any other throw
marks the test failed with the error's `.message`, and execution continues
with the next test. Bookkeeping lives in a small IR runtime: pass/fail/skip
counters, TAP-shaped per-test lines (`ok - name` / `not ok - name: msg`),
and an exit-sink summary that exits non-zero when any test failed — wired
into `__kml_run_exit_handlers` exactly like the mustCall verifier
(TDD-00122), which this composes with.

### Surface (V1)

- `test(name?, opts?, fn)` and the `it` alias; an `opts` literal with a
  `skip` key (or `test.skip(...)`) reports the test skipped without running
  it; `todo` likewise.
- `describe(name, fn)` / `suite`: runs `fn` immediately inside its own
  catch frame; the name joins a compile-time prefix stack, so nested test
  names report as `outer > inner` (nesting is knowable at compile time
  because group bodies run at registration).
- **TestContext** (`fn(t)`, contextually typed like every other Node
  callback): `t.test(name?, fn)` (subtest — same machinery, nested name),
  `t.after(fn)` (runs after this test's body, pass or fail), `t.skip()`/
  `t.todo()` (report, body continues — matching Node), `t.diagnostic(msg)`.
  The context is a heap list of after-hooks; arity 0/1 both accepted.
- Module-level hooks: `before(fn)` runs immediately (equivalent under
  run-at-registration); `after(fn)` closures collect in an IR list run by
  the exit sink before the summary; `beforeEach`/`afterEach` hold one
  closure slot each (last registration wins, disclosed) invoked around every
  test body.
- Out of V1: `t.plan`, `mock.*`, `run()`, concurrency options, snapshot
  helpers — clean rejections naming the gap.

### Module identity

`node:test` shares the existing `test` builtin (marker `test__kml_builtin`,
TDD-00122): the runner members join `mustCall`/`mustNotCall`/… in one
module, which is also where Node users expect them (`import { test, mock }
from 'node:test'` — Node's own `mustCall` lives elsewhere, but this
compiler's `test` module was always a superset). The resolver must accept
the `node:`-prefixed specifier.

## Open questions

- Whether `after`-hook failures should themselves fail the process (V1: yes,
  they run inside a catch frame and count as failures).
- Whether the TAP-ish output should aim for literal TAP 13 (`1..N` plan
  line) — V1 prints per-test lines + a summary; exact TAP is cosmetic until
  something consumes it.
