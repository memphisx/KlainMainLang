# TDD-00064: Runtime representation for a nullable non-pointer type (`number | null`, etc.)

- **Status**: Not Started
- **Date**: 2026-08-13

## Context

`T | null` (and `T | undefined`) works when `T` is a **pointer** type — a string, object, array, class instance, Map/Set, etc. — because the null pointer `null` is a distinct, unused bit pattern that means "absent." It does **not** work when `T` is a **non-pointer scalar** (`number`/i64, `boolean`/i1, an annotated `float64`/`float32`, `Date`/i64): those are stored as a bare scalar with a `Nullable` flag on the type but **no runtime value reserved for null**. Every valid scalar is a valid non-null value, so "is this null?" is unanswerable at runtime, and the code paths that need to ask it silently pick a wrong answer.

Three shipped bugs share this exact root cause, currently tracked separately:

1. **`??` / `??=` on a non-pointer `T | null`** — `emitNullCoalesce` (`emit_exprs_operators.go`) short-circuits: for a non-`ptr` left operand it returns the left value unconditionally (`if left.Ty.IR != "ptr" { return left }`), because it has no null test to emit. So `let x: number | null = null; x ?? 42` evaluates to `0`, not `42`. Found building `??=` ([ADR-00087](../adr/ADR-00087.md)).
2. **A class iterator's `next(): number | null` terminates on a legit `0`** — the Stage 1a iterator protocol ([ADR-00063](../adr/ADR-00063.md)) uses bare `0` as *both* the number zero and the "iteration done" sentinel, so an iterator whose first real value is `0` stops immediately (affects `for...of` and `Array.from` over such an iterator). Found verifying `Array.from` ([ADR-00088](../adr/ADR-00088.md)).
3. **`Map<string, number>.get()` on a missing key returns `0`, not `undefined`** — same "no absent value for a scalar" gap, surfaced by the 2026-08-11 audit ([ADR-00166](../adr/ADR-00166.md)).

It's scoped now because the recent operator/inference correctness pass (short-circuit `&&`/`||`, `NaN` comparisons, boolean-var inference — [ADR-00186](../adr/ADR-00186.md)/[ADR-00188](../adr/ADR-00188.md)/[ADR-00190](../adr/ADR-00190.md)) closed the cheap "deferred shortcut" caveats, leaving these three as the largest remaining correctness cluster — and they cannot be fixed piecemeal, because they need one shared decision: *how does a scalar carry "absent"?*

## Design

The core question: give a non-pointer scalar a way to distinguish "a real value" from "null/undefined." Four candidate representations, lowest-to-highest disruption:

### Option A — Presence-flagged struct (a tagged optional) — **recommended**

Represent a nullable scalar `T | null` as a two-field aggregate `{ i1 present, T value }` (LLVM `{ i1, i64 }` for a `number`). `null`/`undefined` is `{ present = false, value = undef }`; a real value is `{ present = true, value = v }`.

- **Null test** is a plain `extractvalue ... 0` + `icmp` on the `present` bit — exactly what `??`/`??=`/`?.`/`if (x !== null)` need.
- **Unwrap** (once known non-null, e.g. after a narrowing guard or a `!` assertion) is `extractvalue ... 1`.
- **Arithmetic / comparison** on a nullable scalar first requires narrowing to `T` (real TS demands this too — `x + 1` is a type error when `x: number | null`), so the payload only ever reaches an arithmetic op already unwrapped. No hot-path overhead on plain (non-nullable) `number`, which stays a bare i64 — only the annotated-nullable slots change shape.
- **Cost**: the storage type of a nullable scalar changes everywhere it can appear — a local alloca, a function parameter, a return type, an interface/object field, an array element. Each site that currently assumes `ty.IR` is the bare scalar IR must consult a helper (e.g. `storageIR(ty)`) that returns `{ i1, T }` when `ty.Nullable && !pointerish(ty)`. This is the bulk of the work and the main risk.

### Option B — Reuse the existing `{ i8, i64 }` union box

TDD-00043's constrained-union machinery already stores a value as a runtime-tagged `{ i8 tag, i64 payload }` box (`IsDynamic` + `UnionMembers`, `emit_dynamic.go`), and already has boxing/unboxing/`unionAllowsAssignmentFrom` plumbing. Model `T | null` as the constrained union `T | null` and reserve a tag value for null.

- **Pro**: reuses a built, tested representation and its assignment/return/call-boundary checks; a single mechanism for "unions" and "nullable."
- **Con**: every nullable scalar becomes a full tag+payload box even though it only needs one bit; arithmetic requires unbox on every use; `float32`/`float64` payloads must co-exist with the i64 payload slot (bitcast dance). Heavier than Option A for the common `number | null` case, and couples the nullable fix to the union box's own current limitations (scalar-members-only, no flow narrowing).

### Option C — Reserved sentinel value

Pick an in-band bit pattern to mean null (e.g. a specific NaN payload for floats; a reserved integer like `INT64_MIN` for i64).

- **Rejected** for the general integer case: any reserved integer is a legit value some program will use, reintroducing exactly bug #2's "the sentinel collides with a real value" failure. Viable only for float (NaN-tagging), which doesn't generalize to `number`/i64/bool, so it can't be the single shared mechanism this document is meant to pick.

### Option D — Heap-box the scalar behind a pointer

`T | null` non-pointer → `ptr` to a heap `T`; null = null pointer, reusing all existing pointer-null machinery verbatim.

- **Pro**: smallest codegen change (nullable scalars literally become pointer-nullable, so `emitNullCoalesce`/`?.` work with zero new logic).
- **Con**: a heap allocation + indirection per nullable scalar; mutation and value-semantics get subtle (assigning a new value must allocate or mutate-through, and two copies of a `number | null` must not alias). A poor fit for a value type, and wasteful for something as common as `number | null`.

**Recommendation**: **Option A**. It's the honest value-type representation, keeps plain `number` a bare i64 (no cost on the overwhelmingly common non-nullable path), and makes the null test a couple of cheap instructions. Option B is the fallback if threading `storageIR` through every scalar-storage site proves too invasive to land safely — it trades runtime overhead for reusing existing plumbing.

### Staging

1. **Stage 1 — representation + locals.** Introduce `storageIR(ty)`/optional helpers, and support a nullable scalar as a **local variable** only: alloca as `{ i1, T }`, store `null`/a real value, and make `emitNullCoalesce` (and `?.`) emit a real presence test. Fixes bug #1 for locals.
2. **Stage 2 — flow narrowing.** `if (x !== null) { … }` / `x ?? d` narrow a nullable scalar to `T` inside the guarded region so arithmetic/comparison type-check and unwrap. (This compiler has no flow narrowing yet — it's the same machinery a general nullable story needs, so it belongs here.)
3. **Stage 3 — boundaries.** Nullable scalar as a function parameter, return type, and object/interface field. Fixes `Map.get()` returning `undefined` (bug #3) once the map value type can be `V | null`.
4. **Stage 4 — the Stage 1a iterator.** Either (a) migrate the class-iterator result to nullable-scalar `next()`, or (b) — likely simpler and independently shippable — migrate it to the generator protocol's `{ value, done }` result struct ([TDD-00061](TDD-00061.md)/[ADR-00172](../adr/ADR-00172.md)), which already carries an explicit `done` bit and sidesteps the in-band sentinel entirely. Fixes bug #2. This stage can be done first and alone if only the iterator bug is wanted.

## Open questions

- **`null` vs `undefined`**: do we need to distinguish them in the payload (two `present` states), or collapse both to "absent"? The existing `IsUndefined` flag distinguishes them for string rendering; a scalar optional probably only needs one "absent" state, with the static type remembering which keyword was written.
- **Option A vs B final call**: settle by prototyping `storageIR` threading for the `number | null` local case (Stage 1) and measuring how many scalar-storage sites actually need to change — if it's contained, Option A; if it sprawls across every field/param/return path at once, reconsider Option B's reuse.
- **Narrowing scope (Stage 2)**: how far does a narrow reach — just the guarded block, or also the fall-through after an early `return`/`throw` in the `else` (`if (x === null) return; /* x is T here */`)? The latter is more useful but needs the same reachability reasoning the try/finally work ([ADR-00191](../adr/ADR-00191.md)) touched.
- **Does the iterator bug (Stage 4) justify waiting on the rest?** Stage 4(b) (migrate to `{ value, done }`) fixes bug #2 with no dependency on Stages 1–3, so it may be worth landing on its own regardless of the larger representation decision.
