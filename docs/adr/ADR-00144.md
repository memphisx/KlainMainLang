# ADR-00144: Re-exports (`export { a } from './x'`, `export * from './x'`)

- **Relations**: Implements [TDD-00051](../tdd/TDD-00051.md)
- **Date**: 2026-08-10

## Context

[TDD-00042](../tdd/TDD-00042.md)/[ADR-00135](ADR-00135.md) shipped `export default`, default imports, and namespace imports, and explicitly left re-exports for later — "a file re-publishing a name it didn't itself declare... touches the `exported`/`mangled` maps' per-file assumption differently." This is that follow-up, picked as the next module-system slice.

## Investigation

- `resolver/resolver.go`'s `fileInfo.mangled` (`resolver.go:52`-ish before this change) turned out to serve two purposes at once: it's both the table `renameFile` uses to rewrite bare references inside a file's own body, and the table an importer reads via `target.mangled[spec.Imported]`. Every case that existed before this ADR made those two purposes coincide. A re-export breaks that: `export { x } from './other'` must not make `x` a usable bare identifier inside the re-exporting file (real ES modules agree — it's forwarding, not a local binding), so re-export aliases could not go into `mangled` the way `mangled["default"]` already does for `export default`. See [TDD-00051](../tdd/TDD-00051.md)'s Design section for the full reasoning; confirmed by writing `TestE2EReExportDoesNotBindLocalName` first and watching it fail against a naive "just alias into `mangled`" draft before the separate-table design was applied.
- `resolver.go`'s DFS (`visit`) only walked `ImportDeclaration.Source` to discover files and build `order` (dependency-first). A file that *only* re-exports (no `import`) from another file would never get that file visited/ordered relative to it — confirmed by tracing `TestE2EReExportChain`'s three-file chain (`c.ts` re-exports from `b.ts`, `b.ts` re-exports from `a.ts`, neither `b.ts` nor `c.ts` has a plain `import`) against the unmodified `visit` before this ADR's change; `a.ts` would never be visited at all.
- Considered folding re-export resolution into the existing `mangleFileDecls` loop (which already handles `export default`'s `mangled["default"]` alias). Rejected: `mangleFileDecls` runs per-file with no cross-file ordering guarantee at the point it currently runs, but a re-export's mangled value depends on the *target* file's mangled table already being final — needed two separate dependency-ordered passes instead (see Decision).
- Considered real ES module semantics for `export *` collisions (a local export silently wins over a colliding star re-export; two colliding star re-exports become an "ambiguous" name that's only an error if actually imported). Rejected in favor of this project's existing stricter posture — every other name collision in the module system (same local name from two files with no `as`, two `export default` in one file) is a hard compile error, not a deferred/silent one; re-exports follow that same precedent.

## Decision

**New AST node**, `ast.ExportFromDeclaration{Specifiers []ImportSpecifier, All bool, Source string}` (`ast/nodes.go`) — reuses `ImportSpecifier`'s `{Imported, Local}` shape rather than a parallel type, since it's the same name-forwarding problem `import { a as b }` already solved. `All` represents `export * from` (no specifiers).

**Parser** (`parser/parser_imports.go`): `export {` or `export *` are unambiguous dispatch points in `parseExportDeclaration` (there's no other `export { ... }`/`export *` form). `export * as ns from` is rejected at parse time with an explicit "not supported yet" message rather than falling through to a confusing error. The new `parseExportFromSpecifierList` accepts the literal `default` token (`lexer.DEFAULT`, not `IDENT`) on either side of an entry, enabling `export { default } from` and `export { default as Foo } from` (re-exporting another module's default) as well as `export { foo as default } from` (re-exporting a named export as this module's own default) — none of which fit the existing `import`-side specifier-list parser, which stays untouched.

**Resolver** (`resolver/resolver.go`):
- `visit`'s dependency-discovery loop now treats `ExportFromDeclaration.Source` as an edge exactly like `ImportDeclaration.Source`, with one difference: hitting a virtual built-in marker (`fs`/`path`/etc.) is an immediate error ("re-exporting from a built-in module is not supported"), not a skip — re-export was deliberately never integrated with `virtualBuiltinMarkers`.
- `fileInfo` gained `reExportBindings []reExportBinding` (local/target-path/remote-name triples, populated before mangled names exist) and `reExportMangled map[string]string` (populated after), plus a `publicMangled(name) (string, bool)` method that checks `mangled` then falls back to `reExportMangled`. `renameFile`'s intra-file lookup table is still built from `mangled` alone — `reExportMangled` is never visible there, which is what keeps a re-export from becoming a usable local identifier.
- Two new dependency-ordered passes (both walk `allPaths`, i.e. `order` then the entry file — a binding's target is always already fully processed):
  1. Right after the DFS, before the existing import-specifier validation loop: expand each `ExportFromDeclaration` (or `export *` into one entry per name in `target.exported` minus `"default"`), reject an unknown remote member or a collision against `info.exported`, then add the local name to `info.exported` and record the binding.
  2. Right after the existing `mangleFileDecls` loop (so every file's own `mangled` is final): resolve each recorded binding into `info.reExportMangled[local] = target.publicMangled(remote)`. Because `target` was necessarily processed earlier in the same pass, a target that is itself a re-exporter (a chain) resolves transitively with no extra code.
- The two existing consumer sites that read `target.mangled[...]` directly (the named-import lookup builder, the namespace-import member-table builder) now go through `target.publicMangled(...)` instead, so both `import { x } from reexporter` and `import * as ns from reexporter` transparently see re-exported names.
- `unwrap()` drops `ExportFromDeclaration` (no runtime statement, same as `ImportDeclaration`); `validateDeclarationsOnly` allows it in a non-entry file, same bucket as `ImportDeclaration`.

**Known accepted gap**: a genuine circular re-export with no real declaration backing it anywhere in the graph (`A` re-exports `x` from `B`, `B` re-exports `x` from `A`, neither ever declares `x`) still fails to compile, but the message reads as an ordinary "no exported member" error rather than calling out the cycle — pass 1 hits the missing-member check for whichever file gets processed against the other side's not-yet-augmented `exported` set. Accepted as-is for V1 (see [TDD-00051](../tdd/TDD-00051.md)'s Open Questions) — it fails closed, just not with the friendliest wording.

## Implementation notes

- `ast/nodes.go`: `ExportFromDeclaration` + `NewExportFromDeclaration`.
- `parser/parser_imports.go`: `parseExportDeclaration`'s signature changed from `(*ast.ExportDeclaration, error)` to `(ast.Statement, error)` (its one call site, `parser/parser_stmts.go:36`, already returned into an `ast.Statement`-typed slot, so this was a no-op there); new `parseExportFromDeclaration`, `parseExportFromSpecifierList`, `expectIdentOrDefault`.
- `resolver/resolver.go`: `fileInfo` gains `reExportBindings`/`reExportMangled` + `publicMangled`; `reExportBinding` struct; `visit`'s import-walking loop restructured to a type switch over `ImportDeclaration`/`ExportFromDeclaration`; `allPaths` construction moved earlier (right after the DFS completes) so the new export-name-augmentation pass can use it before the pre-existing import-specifier validation loop runs; new pass after `mangleFileDecls` for mangled-value resolution; `unwrap`/`validateDeclarationsOnly` updated.
- No codegen changes — `codegen/llvm` never sees either `ImportDeclaration` or `ExportFromDeclaration`, unchanged from before.

## Side effects discovered

None — existing import/export test suite (`tests/imports_test.go`'s pre-existing cases, `tests/import_gated_builtins_test.go`) passed unmodified against the restructured `resolver.go`, confirming the pass reordering didn't change behavior for any non-re-export case.
