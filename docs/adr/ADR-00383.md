# ADR-00383: JSDoc type-expression sub-parser (TDD-00125 Stage 4)

- **Relations**: Extends [ADR-00380](ADR-00380.md); Implements [TDD-00125](../tdd/TDD-00125.md)
- **Date**: 2026-08-26

## Context

Through Stage 3, every JSDoc type body was stuffed verbatim into a
`TypeAnnotation.Name` string. That resolves a bare name, a width keyword, or
`T[]`, but a union / nullable / inline object / `Array.<T>` / `function(...)`
body silently collapsed to the first token or was a clean rejection — the single
biggest quality gap left in the JSDoc surface, and it capped `@type` and
`@param`/`@returns`/`@typedef`/`@callback` alike.

## Decision

Parse a JSDoc type string with the **real TypeScript type parser** instead of
name-stuffing. `jsdocTypeAnnotation(raw)` (`parser/jsdoc_types.go`):

1. `normalizeClosureType` rewrites Google-Closure-only syntax into the
   equivalent TS syntax: `?T`→`T | null`, `!T`→`T`, `*`/`?`→`any`,
   `Array.<T>`→`Array<T>` (and `Foo.<T>`→`Foo<T>`), `Object.<K,V>`→`Record<K,V>`,
   `function(A,B): C`→`(arg0: A, arg1: B) => C`, and the legacy capitalized
   primitive synonyms (`String`→`string`, …).
2. The normalized string is lexed and run through `parseTypeAnnotation`; a
   partial parse (trailing unconsumed tokens) is rejected.
3. On any failure it falls back to the pre-Stage-4 `{Name: raw}` form, so the
   change is never a regression.

Every JSDoc type site now routes through it: `@type` (var / class field / type
alias), `@param`/`@returns`, and the synthesized `@typedef`/`@callback` member
types.

**Nested-brace fix.** An inline object type (`@param {{x: number}}`) carries
nested braces, which the old tag regex (`\{[^}]+\}`) truncated at the first `}`.
`jsdoc.Parse` now extracts the `{...}` type body by **balanced-brace scanning**
(`scanBraceType`) and the trailing text by `lineHead`, so nested object types
survive intact.

## Implementation notes

- Because the JSDoc grammar overlaps the TS grammar almost entirely, the sub-
  parser *is* the TS parser — no second type grammar to maintain. Union,
  nullable-as-`T|null`, inline objects, `T[]`, `Array<T>`, function types, and
  tuples all come for free and behave identically to an inline `: T`.
- `Object.<K,V>` maps to `Record<K,V>`; this parses, but `Record` has no per-key
  field/index access here (index signatures are a separate ❌), so the mapping
  is forward-looking rather than fully usable today — tracked ❌ on JSDOC.md.
- Import types (`import("./m").T`) are out of this stage (Stage 6).

## Side effects discovered

Routing every `@type`/`@param` through the real parser exercises far more of the
type grammar than the old name-stuffing did; the full test/example suite and
Test262 run confirmed no behavior change for the previously-working simple forms
(bare names, width keywords, `T[]` all parse identically).
