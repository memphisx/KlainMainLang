# TDD-00129: Closure capture for nested function declarations

- **Status**: Partially Implemented
- **Date**: 2026-08-27

Stage 1 (capture at/after the declaration point) implemented by [ADR-00386](../adr/ADR-00386.md); Stages 2 (full hoisting) and 3 (capturing generators) not started.

## Context

[TDD-00057](TDD-00057.md) shipped nested function declarations with a deliberate
non-goal: a nested function gets its own clean scope like a top-level function
and **cannot capture** the enclosing body's locals or parameters. Referencing an
outer local is a clean `undefined variable` error:

```
function outer(x: number): number {
  function inner(): number { return x + 1; }  // codegen error: undefined variable 'x'
  return inner();
}
```

That non-goal was correct for V1, and TDD-00057's own final Open Question is
precisely this document's subject: *"Whether closure capture for named nested
functions is worth adding later, and if so whether it reuses `gatherCaptures`
against `*ast.FunctionDeclaration` directly or desugars to the arrow-function
path."* This TDD resolves that question and scopes the capture stage.

It is worth doing now because the non-capturing restriction is the single
surprising cliff in an otherwise-complete nested-function feature — a nested
helper that reads one enclosing variable is idiomatic in FP/callback-heavy code,
and the current error reads as a bug to anyone who doesn't know the V1 scope.

### The decisive fact found while scoping this

Nested functions in this compiler **already escape as first-class values** today,
under TDD-00057's non-capturing scheme (verified):

```
function outer(): () => number {
  function inner(): number { return 5; }
  return inner;              // compiles — nested function returned as a value
}
function m(): number {
  function dbl(n: number): number { return n * 2; }
  return [1, 2, 3].map(dbl)[2];  // compiles → 6 — nested function passed to a HOF
}
```

They escape as a bare function pointer (no env). The moment a nested function can
capture, an escaped capturing function **must carry its captured environment
with it** — a returned/stored `inner` is called long after `outer`'s frame is
gone, so a captured `x` cannot live on `outer`'s stack. That forces a capturing
nested function to be represented as a **closure value** (`{fn, env}` fat
pointer), exactly like an arrow function or a named function expression. A bare
mangled top-level function with a hidden env parameter cannot satisfy the escape
case, because the escaped value would have nowhere to carry the env.

This single fact resolves TDD-00057's open fork: **desugar to the closure path**,
do not bolt a hidden env parameter onto the direct-call path.

## Design

### Chosen approach: capture-triggered desugaring to the named-function-expression path

Split nested function declarations by whether they capture:

- **Non-capturing nested function** (references only its own params/locals plus
  true globals) — **unchanged from [TDD-00057](TDD-00057.md)**: mangled name,
  direct call, zero heap allocation, forward-reference and recursion via the
  per-body two-pass `nestedFuncScopes` registration. This keeps the cheap common
  case cheap.
- **Capturing nested function** (references ≥1 enclosing local/parameter) —
  desugared to the equivalent of a hoisted `const <name> = function <name>(...)
  {...}` binding, reusing the existing closure machinery **unchanged**:
  - `gatherCaptures` / `CapturedVar` / the heap-allocated env struct
    (`emit_func.go`) for the captured environment — including its existing
    **boxed-cell** treatment of a captured variable that is mutated, which gives
    correct JS by-reference capture semantics (a mutation in `inner` is visible
    in `outer` and vice-versa) for free.
  - The **named-function-expression self-capture** ([ADR-00178](../adr/ADR-00178.md)):
    a named function expression already binds its own name inside its own body
    via a synthetic self-capture cell holding the closure's own header, so
    **self-recursion falls out with no new work**.
  - The **closure-value representation** for escape: `return inner`,
    `arr.map(inner)`, storing it in a field — all already work for any closure
    value, so escape of a capturing nested function **falls out for free** once
    it is represented as one.

The only genuinely new work is **binding the name and hoisting** (below);
capture, mutation, recursion, and escape are all reused, not rebuilt.

### Capture detection

During `pushNestedFuncScope` (`emit_func.go`), run the existing free-variable
scan (`scanExprFV`/the `gatherCaptures` free-variable pass already used for
arrow/function expressions) over each nested declaration's body against the
enclosing scope. Classify the declaration:

- **empty capture set** → register in `nestedFuncScopes` as today (direct-call).
- **non-empty capture set** → mark it capturing; it will be emitted as a closure
  value bound to its own name in the enclosing variable scope (`e.scopes`),
  **not** registered in `nestedFuncScopes`.

Because dispatch of a capturing nested function now goes through the ordinary
variable path (`e.lookup(name)` → a closure value → `emitClosureCall` /
`resolveCallback`), the five `resolveFuncRef` call sites TDD-00057 introduced
need no change for it: a capturing nested name is simply a local closure
variable, resolved the way any closure-typed local already is. Non-capturing
names keep resolving through `nestedFuncScopes`. Name-resolution order must make
the nested binding shadow an unrelated top-level function of the same name,
matching TDD-00057's existing visibility rule.

### Binding and hoisting (the only new mechanism)

A capturing nested function is bound to a slot of its own name in the enclosing
body's variable scope. To preserve JS function-declaration semantics
(forward-reference + recursion), use a **letrec-style pre-allocation**, mirroring
`promoteVarToFuncScope`'s "promotion-at-declaration" shape:

1. In the pre-scan, `alloca` the closure-header slot for the name and `define`
   it in the enclosing scope **before** any body statement is emitted.
2. At the declaration point, build the closure (env struct populated with the
   captured cells) and store its header into the pre-allocated slot.
3. References resolve to that slot throughout the body.

**V1 hoisting scope:** support use **at or after** the declaration point (the
common case), matching `promoteVarToFuncScope`'s deliberate
promotion-at-declaration rather than full hoist-to-before-declaration. A call
*textually before* the capturing declaration — where the env's captured cells
may not yet be initialized — is a clean compile error in V1, not a read of an
uninitialized cell. (A non-capturing nested function keeps full hoisting, since
it has no env to initialize — unchanged from TDD-00057.) Full pre-declaration
hoisting for the capturing case, and its TDZ interaction with captured `let`s
declared later, is deferred to Stage 2.

### Staging

- **Stage 1** — capture detection + desugar capturing nested declarations to the
  named-function-expression closure path, bound at declaration point
  (use-at-or-after-declaration). Escape, by-reference mutation, and recursion
  fall out of the reused machinery. Non-capturing path untouched.
- **Stage 2** — full pre-declaration hoisting for the capturing case, resolving
  the TDZ question for captured bindings declared after the function.
- **Stage 3 (note, not committed)** — capturing **nested generators**, currently
  a clean rejection (`emit_func.go`'s "a capturing nested generator needs the
  __env work" guard). This TDD's env foundation is exactly that missing piece;
  combining it with the generator-instance `__env` (already used for a nested
  generator's *non-captured* state) would lift the rejection, but the
  generator-instance + closure-env interaction warrants its own scoping.

### Why not extend `gatherCaptures` onto the direct-call path (a hidden env param)

Rejected by the decisive fact above: a nested function that escapes as a value
would have nowhere to carry a hidden env parameter, so the direct-call
representation cannot support capture + escape together. Since escape already
works today, any capture design must preserve it — which means the closure-value
representation, i.e. the desugaring approach. The hidden-env-param variant would
also fork the call ABI (direct calls pass env, escaped uses can't), reintroducing
exactly the representation split the closure value already resolves cleanly.

### Why not desugar *all* nested functions (drop the direct-call path)

Rejected to preserve TDD-00057's cheap common case: a non-capturing helper stays
a direct call with zero per-call allocation. Only functions that actually capture
pay for an env struct. This is the same cost reasoning TDD-00057 used to choose
the direct-call path originally, now applied per-declaration rather than
globally.

## Open questions

- **Full hoisting + TDZ** (Stage 2): a capturing nested function called before its
  textual position, whose captured `let` is declared even later — reject, or
  define via cell-zero? Real JS gives a TDZ error; matching that needs the
  definite-assignment/TDZ analysis ([TDD-00071](TDD-00071.md)) to see the
  captured cell.
- **One-block-deeper restriction**: TDD-00057 keeps nested declarations to the
  immediate body, not inside a further `if`/`for` block. Capture does not change
  that; both remain gated together. Lifting it stays TDD-00057's own open
  question.
- **Capturing nested generators** (Stage 3): does the generator instance's
  existing `__env` (for non-captured enclosing state) compose with a full
  closure env, or do they need unifying into one env?
- **Interaction with [ADR-00342](../adr/ADR-00342.md)** (a top-level function
  can't reference certain sibling handle-typed globals): orthogonal — that is a
  module-global promotion limit, not an enclosing-locals capture, but confirm a
  capturing nested function referencing such a binding degrades to the same clean
  rejection rather than a miscompile.
