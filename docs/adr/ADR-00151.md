# ADR-00151: Tagged template literals

- **Relations**: Implements [TDD-00059](../tdd/TDD-00059.md); Extended by [ADR-00152](ADR-00152.md)
- **Date**: 2026-08-10

## Context

`` tag`Hello ${name}` `` was a confirmed gap (`docs/status/LANGUAGE-CONSTRUCTS.md`'s row 19, `docs/adr/ADR-00028.md`'s punt on `String.raw`). [TDD-00059](../tdd/TDD-00059.md) scoped it as a desugaring — a tagged template call is exactly `tag(["a","b"], x)`, reusing existing array-literal and rest-parameter-packing codegen unchanged — with one deliberate cut: no `.raw` property on the `strings` array (this compiler's arrays are fixed-shape with no room for one; real `String.raw` stays separately out of scope per ADR-00028).

## Decision

Implemented per TDD-00059's design: a new `ast.TaggedTemplateExpression` node (kept distinct from a desugared `CallExpression` so "this was written as a tagged template" stays recoverable for any future `.raw` work), parsed in `parseCallMember`'s postfix loop (same insertion point as `LPAREN`/`LBRACKET`), and lowered at the point codegen needs a `Value`/`Type` via one shared helper, `desugarTaggedTemplate`, rather than duplicated type-checking/coercion logic.

Three real, previously-undiscovered bugs surfaced while building the example/tests and are fixed here too — see Side effects discovered.

## Implementation notes

- **`ast/nodes.go`**: `TaggedTemplateExpression{Tag, Quasis, Exprs}` + `NewTaggedTemplateExpression`.
- **`parser/parser_literals.go`**: `parseTemplateLiteral`'s quasi/expression scanning loop factored into `parseTemplateRest(headQuasi string)`, shared with the new tagged-template path.
- **`parser/parser_exprs.go`**: `parseCallMember`'s postfix loop gains `TEMPLATE_NO_SUB`/`TEMPLATE_HEAD` cases, structurally identical to the existing `LPAREN` case.
- **`codegen/llvm/emit_call.go`**: `desugarTaggedTemplate(tt) *ast.CallExpression` — builds `ast.NewArrayLiteral` of the cooked quasis as the first argument, `tt.Exprs` untouched as the rest, `tt.Tag` as the callee.
- **`codegen/llvm/emit_exprs.go`**/**`emit_exprs_types.go`**/**`emit_exprs_vardecl.go`**: one new case each (`emitExpr` → `emitCall(desugarTaggedTemplate(ex))`; `inferExprType` → recurse on the desugared call; `emitVarDecl`'s pre-inference switch → delegate to `inferExprType`, since that switch has no default fallback and would otherwise silently misinfer an unannotated `const r = tag\`...\`` instead of erroring).
- **`resolver/rename.go`**: `rewriteExpr` (the per-file name-mangling walk, TDD-00041) gains a `*ast.TaggedTemplateExpression` case rewriting `Tag` and each of `Exprs` — see Side effects discovered.
- **`codegen/llvm/emit_func.go`**: `scanExprFV` (arrow-function free-variable/capture scanning) gains the same case, scanning `Tag` and `Exprs`.

## Side effects discovered

Three real, pre-existing bugs found while validating the feature end-to-end (a tag function accumulating a result via `+=`, and testing arrow-function/class-method tags), none specific to tagged templates themselves — fixed here since all three are small, contained, and directly blocked writing an honest example/test suite for this feature:

1. **`+=` on a string-typed left-hand side produced invalid LLVM IR.** `s = s + "b"` always worked (`emitBinary` has its own string-concat handling), but `s += "b"` reached `emitArith`'s generic numeric `add`/`fadd` case unconditionally — a hard clang-stage "invalid operand type" for the plainest possible case, not just a mixed string/number one. No existing test exercised `+=` on a string anywhere in the suite. Fixed: `emitArith` (now taking a `pos ast.Pos` parameter, threaded through its 6 call sites across `emit_exprs_assign.go`/`emit_objects.go`/`emit_classes.go`) checks `isStringTy(ty)` first and routes to `emitStringBinary`, stringifying either operand via `emitValueToString` first when `op == "+"` and one side isn't already a string — mirroring `emitBinary`'s own top-of-function handling. A non-`+` compound-assignment operator on a string target (`s -= x`) now gets `emitStringBinary`'s existing clean "operator not supported for strings" rejection instead of the same invalid-IR failure.
2. **Any array-typed arrow-function/closure parameter produced invalid LLVM IR**, not just the previously-guarded destructured-array-param case (`emit_func.go`'s existing comment already correctly diagnosed the root cause — a closure ABI that never decomposes an array into its `(ptr, i64)` pair — but the guard only checked `p.ArrayPattern != nil`). Confirmed independently that a plain `(arr: number[]) => arr.length` already failed the same way. The guard is broadened to `pty.IsArray` (a strict superset — a destructured array param's resolved type is already array-typed too), turning both a plain array param and a rest param (inherently array-typed) into the same clean, documented rejection instead of a clang-stage crash.
3. **Rest parameters weren't parsed on arrow functions at all.** `parseArrowFunction` parses its own parameter list separately from `parseParamList` (used by named functions/class methods) and had never gained `...` handling, so `(...rest: number[]) => ...` failed with a confusing "expected IDENT, got ..." rather than any clean, on-topic error. Fixed by mirroring `parseParamList`'s existing `...`/rest handling; combined with fix 2 above, a rest param on an arrow function now parses and then hits the same clean "array-typed closure parameters aren't supported" rejection every other array-typed arrow parameter does — consistent, not a special case. Also added the same default-rest-element-type fallback (`ArrayOf(TypeI64)`) `buildFunctionSig` already gives an unannotated named-function rest param, so an unannotated arrow rest param is diagnosed the same way instead of silently defaulting to a bare scalar.

**A structural consequence of fix 2, not itself a bug**: an arrow function can never be used as a tagged-template tag, since its first parameter (the strings array) is unavoidably array-typed. A named function or a class method taking only the strings array both work fine (neither compiles through the closure/env-struct machinery), covering the realistic cases.

**Found but not fixed, deferred**: a class method call whose first argument is an array literal *and* has further trailing arguments (e.g. `f.build(["n="], 7)` for a method `build(strings: string[], ...values: number[])`) fails with "expression does not yield an array" — confirmed independent of tagged templates (reproduces with a hand-written call, no template syntax at all) and independent of fixes 1-3 above. This is a separate bug in the class-method-call argument-evaluation path, not the general named-function call path (`emitCallToFuncSig`, unaffected) — out of scope for this ADR; a class-method tag taking only the strings array (no additional params) is unaffected and works (`TestE2ETaggedTemplateClassMethodTag`). Not tracked further here since it's outside Functions & closures' own scope — noted so it isn't silently dropped.
