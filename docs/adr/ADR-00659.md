# ADR-00659: Codegen wall-clock guard in the conformance runners

- **Relations**: Extends ADR-00657
- **Date**: 2026-09-03

## Context

Regenerating the `-compat=js` Test262 report stalled: the run climbed to some
file count and then froze at **0% CPU**, never writing a report (the faillist is
written only after every file completes, so a stall yields no output at all). A
stalled measurement is useless and, worse, was the exact trap behind an earlier
false "regression" — a lane that doesn't finish silently under-counts.

The conformance runner has robust *subprocess* timeouts (clang, and running the
compiled test binary) but compiles each file **in-process**
(`parser.Parse`/`resolver.ResolveProgram` → `llvm.NewEmitter().EmitProgram`),
and nothing bounded that in-process work. A parser/emitter that spins forever on
some pathological input would wedge its worker goroutine with no timeout able to
catch it — and with every worker stuck the whole suite freezes with no report.
The runner's own progress comment already named this hazard ("a codegen infinite
loop … isn't caught by the per-file subprocess timeout"). This is a real,
unguarded failure mode regardless of whether a given corpus triggers it.

## Investigation

`runOne` (`tools/conformance/main.go`) called `parser.Parse` + `EmitProgram`
directly in the worker goroutine; the Node and TS suites do the same through
`frontEnd` (`tools/conformance/node.go`). None had any bound on that in-process
work.

Root-causing the specific stall, however, showed it was **environmental, not an
in-process codegen spin**: overlapping runner invocations were sharing the
default `.conformance-out` scratch dir (fixed separately by per-process
isolation, ADR-00657) and a cluster of compiled test binaries were hanging at
*runtime* and not being reaped, blocking workers. Once the runs were isolated
and clean, the `-compat=js` corpus completed with **zero** `CODEGEN_TIMEOUT`
files — no input actually spins the emitter today. So this guard is not the fix
for that stall; it is **defensive insurance** for the unguarded hazard the code
already warned about, added while diagnosing the freeze and kept because it is
cheap and the failure mode is real. If a future `-compat=js` (or any) input ever
does spin codegen, it now surfaces as a countable `CODEGEN_TIMEOUT` bucket
instead of silently wedging the whole run.

## Decision

Run the in-process front-end under a wall-clock guard (`codegenTimeout`, 30 s —
a hang backstop, not a perf gate; real compiles finish in well under a second).
Codegen executes in a spawned goroutine; the worker `select`s on its result vs a
timer. On timeout the file is recorded as `CODEGEN_TIMEOUT` and the worker moves
on, **leaking** the stuck goroutine (it cannot be killed; it dies with the
process at exit). One hanging file can no longer stall the corpus.

`CODEGEN_TIMEOUT` is its own pipeline phase ("codegen (in-process hang —
emitter/parser spin)"), distinct from `CLANG_ERROR` (invalid IR that clang
rejected) and `RUN_TIMEOUT` (a compiled binary that ran too long) — so the
report separates "we spun while compiling" from "we emitted bad IR" from "the
program looped."

## Implementation notes

- `main.go`: `codegenTimeout` const; `runOne` runs parse+emit in a goroutine
  with an in-goroutine panic-recover (the outer deferred recover only covers the
  worker's own goroutine), `select`ing on the result vs `time.After`. Added the
  phase to `phaseOf` / `phaseShort` / `phaseOrder`.
- `node.go`: `frontEnd` (shared by the Node and TS suites) gets the same
  goroutine + `select` guard, returning a `CODEGEN_TIMEOUT` error on timeout.

## Side effects discovered

The actual stall was environmental (scratch-dir contention + un-reaped
runtime-hang binaries), addressed by ADR-00657's per-process isolation and the
existing run/clang subprocess timeouts — not by this guard. The leaked
goroutine on timeout is acceptable for a short-lived batch tool (one per hung
file, dying with the process); it is inert here because nothing times out.

## Verification

- The `-compat=js` full Test262 run completes and writes its report, with a
  **`CODEGEN_TIMEOUT` count of 0** — confirming both that no corpus input spins
  the emitter today and that the guard adds no false positives. The distinct
  phase exists and is wired into `phaseOf`/`phaseShort`/`phaseOrder` for the day
  an input does spin. macOS (Apple Silicon).
