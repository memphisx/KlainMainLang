# ADR-00131: `XMLHttpRequest` — legacy synchronous-style client on top of `fetch`'s own non-blocking primitives

- **Relations**: Implements [TDD-00040](../tdd/TDD-00040.md) (Stage 2 of 2 — Stage 1, `Request`/`Headers`, was [ADR-00130](ADR-00130.md)). Extends [ADR-00050](ADR-00050.md), [ADR-00073](ADR-00073.md)
- **Date**: 2026-08-08

## Context

[`docs/status/NETWORKING.md`](../status/NETWORKING.md)'s last ❌ row, `XMLHttpRequest`, had never had a design pass at all — previously just "legacy HTTP; lower priority than fetch". Picked up as Stage 2 of [TDD-00040](../tdd/TDD-00040.md) right after Stage 1 ([ADR-00130](ADR-00130.md), real `Request`/`Headers`) closed out, per the same explicit user request to bring `NETWORKING.md` to full (6/6) coverage.

## Investigation

- The real spec's default-async, callback-driven model (script keeps running while a request is in flight; `onreadystatechange` fires from later event-loop turns) doesn't fit this compiler's execution model — there's no re-entrant callback-into-already-returned-caller machinery anywhere in this codebase. Real browsers also still support fully synchronous XHR (`open(method, url, false)`) — targeted that observable shape instead: `.send()` runs to completion before returning, firing every registered callback once, synchronously, before returning. Confirmed this is not a novel simplification for this codebase: `WebSocketClientType`'s own doc comment (`types.go`) already documents `new WebSocket(url)` performing its connect + handshake synchronously for the identical reason (no non-blocking-connect machinery in the hand-rolled `select()` loop) — same category of deliberate scope call, already accepted once.
- Investigated whether `.send()` needed a new blocking transfer path (rebuilding what `ADR-00095` deliberately deleted — the old blocking `__kml_fetch`) or could reuse the *non-blocking* `__kml_fetch_async` (`runtime_fetch.go`, [ADR-00050](ADR-00050.md)) instead, just waited on synchronously from within `.send()`'s own codegen. Chose the latter: `__kml_await_fetch`'s existing checkloop/maybeyield/doyield/busyspin shape already does exactly "wait until done, yielding the fiber if one exists, busy-spinning otherwise" — reusing it (rather than reintroducing a dead code path `ADR-00095` removed on purpose) means `.send()` called from inside an `http.listen` connection handler still yields instead of blocking every other connection, for free.
- The one gap: `__kml_await_fetch` throws a catchable `Error` on a network-level failure (matching `fetch`'s own semantics) — but real `XMLHttpRequest.send()` never throws for a network error; it fires `.onerror` instead. Found `__kml_pending_finish_settled` already existed, built for `Promise.allSettled` ([ADR-00073](ADR-00073.md)) for exactly this "don't throw, tell me if it failed" need — but it's only ever called from inside `__kml_await_fetch`'s own group-wait sibling (`__kml_await_group_wait`), which polls a *group* of pending fetches, not a lone `__kml_await_fetch`-style single-pending wait. Needed the single-pending wait loop *paired* with the non-throwing finish, which didn't exist as one primitive — built `__kml_await_fetch_settled` for it (see Decision).
- Considered whether to keep `onreadystatechange`/`onload`/`onerror` payload-carrying, matching `EventSource`/`WebSocket`'s own `onmessage` (`FuncType([]Type{SomePayloadType}, TypeVoid)`). Rejected: real `onreadystatechange` itself already takes zero arguments (script reads `this.readyState` off the `XMLHttpRequest` instance) — and a payload type of "the `XMLHttpRequest` instance itself" would require `XMLHttpRequestType()` to construct a `FuncType` field whose parameter type is `XMLHttpRequestType()` again, an unbounded Go-level recursion this project's `Type`-as-a-plain-value representation (not a lazy thunk or pointer) can't express the way a real user-defined class's genuinely self-referential field can (`canonicalizeClassTy`, `emit_classes.go`, exists specifically to patch around *that* case for classes — no equivalent mechanism exists for a hardcoded builtin type like this one). Zero-argument callbacks sidestep the problem entirely, and match how idiomatic code actually uses `onreadystatechange` anyway (closing over the outer `xhr` variable).

## Decision

**`XMLHttpRequestType()`** (`types.go`): hidden fields (`__kml_xhr_method`/`__kml_xhr_url`/`__kml_xhr_headers`, written by `open()`/`setRequestHeader()`, read by `send()` — the same `VisibleFields()`-hides-a-prefix convention `EventSourceType`/`WSConnectionType` already use) plus visible `readyState`/`status`/`responseText`/`response` (a plain alias of `responseText` — only a text `responseType` is supported) and three zero-argument callback fields, `onreadystatechange`/`onload`/`onerror`. `readyState` uses only 0 (UNSENT), 1 (OPENED), 4 (DONE) — the real spec's 2/3 (HEADERS_RECEIVED/LOADING) have no meaning for a `.send()` that runs to completion before returning at all, the same "simplified state model" `EventSourceType`'s own 3-state (vs. the real spec's 4-state, including CLOSING) choice already established.

**`.send()`/`.send(body)`** (`emit_xhr.go`'s `emitXHRSend`): calls `__kml_fetch_async` (identical to `fetch()`'s own call), then the new `__kml_await_fetch_settled(pending) -> {i1 failed, i64 status, ptr body, ptr reasonMsg, i64 bodyLen}` (`runtime_fetch.go`) — a structural clone of `__kml_await_fetch`'s own wait loop, differing only in its `finish:` block, which calls `__kml_pending_finish_settled` instead of the throwing `__kml_pending_finish`. Codegen branches on the returned `i1 failed` directly: on success, sets `status`/`responseText`/`response`, `readyState = 4`, fires `onreadystatechange` then `onload`; on failure, `readyState = 4` (status/responseText stay at their empty defaults), fires `onreadystatechange` then `onerror` — no exception ever thrown, matching real `XMLHttpRequest`.

**`__kml_pending_finish_settled` extraction**: it previously lived inline inside `ensurePromiseCombinators` (`.allSettled`-only). Factored out into its own `ensurePendingFinishSettled()` so `ensureFetchAwaitSettled()` can depend on it directly without pulling in `Promise.all`/`.race`'s group-wait machinery into a program that uses `XMLHttpRequest` but never touches `Promise.allSettled`.

**`.open(method, url)`**: stores into the hidden fields, resets the accumulated headers map fresh (a real `open()` call restarts header state, matching the spec), sets `readyState = 1`, fires `onreadystatechange`. **`.setRequestHeader(name, value)`**: accumulates into the hidden headers map via the plain `__kml_map_str_set` — deliberately *not* lowercased (unlike `Headers`' own `get`/`set`/`has`/`delete`, [ADR-00130](ADR-00130.md)) — a real, documented V1 narrowing (see `docs/status/NETWORKING.md`'s Known Limitations), not an oversight. `.send()` converts the accumulated map into a `curl_slist` via the exact same `buildFetchHeaderList` (`emit_fetch.go`) `fetch(url, init)` already uses — no new header-building code. **`.abort()`**: a best-effort `readyState = 0` reset — real abort-mid-flight has no meaning once `.send()` (synchronous by construction) has already returned by the time `.abort()` could possibly be called.

**Deliberately out of scope**, matching existing precedent elsewhere in this feature area rather than introducing a new gap: `.getResponseHeader()`/`.getAllResponseHeaders()` (no `HEADERFUNCTION` response-header capture exists anywhere in this codebase yet — `fetch`'s own `Response` doesn't expose response headers either); any `responseType` other than the default text; `withCredentials`/timeouts/upload progress.

## Implementation notes

- `codegen/llvm/types.go`: `IsXHR` flag, `XHRMethodField`/`XHRURLField`/`XHRHeadersField` hidden-field-name constants, `XMLHttpRequestType()`, `VisibleFields()`'s new 3-hidden-field case, `ResolveTypeName`'s `"XMLHttpRequest"` case (alongside `"Request"`/`"Headers"`, added together with [ADR-00130](ADR-00130.md) since `emit_exprs.go`'s `NewXExpression` switch needed all three cases to compile as one unit — the constructor itself was stubbed in that same earlier pass; this ADR is `.open()`/`.setRequestHeader()`/`.send()`/`.abort()`, the real method surface).
- `codegen/llvm/emit_xhr.go`: `emitXHROpen`/`emitXHRSetRequestHeader`/`emitXHRSend`/`emitXHRAbort`, plus two small shared helpers new to this file — `xhrStoreField` (the mutating GEP+store counterpart to `loadFieldValue`, needed because, unlike every other builtin object type this compiler has, an XHR's own fields are written after construction, not just read) and `emitXHRFireCallback` (null-check-then-call a zero-arg callback field via the existing `emitClosureCallByPtr(ptr, ty, nil, pos)` — its own per-argument loop is simply a no-op for a `nil` slice, so no new zero-arg call path was needed at all).
- `codegen/llvm/emit_call.go`: `IsXHR` method dispatch (`open`/`setRequestHeader`/`send`/`abort`), placed ahead of the `IsHeaders`/generic-`Map` checks — order doesn't actually matter here (`XMLHttpRequestType` sets neither `IsMap` nor `IsHeaders`), kept first purely for reading order (constructor-heavy builtin types before Map-shaped ones).
- `codegen/llvm/runtime_fetch.go`: `ensurePendingFinishSettled()` (the extraction described above) and `ensureFetchAwaitSettled()` (the new wait-loop-plus-non-throwing-finish primitive).
- `codegen/llvm/emitter.go`: two new one-time-emission guard flags, `usedPendingFinishSettled`/`usedFetchAwaitSettled`, alongside the existing `usedFetchAsync`/`usedPromiseCombinators`.

## Side effects discovered

None beyond the `__kml_pending_finish_settled` extraction already described above under Decision (a refactor, not a behavior change — `Promise.allSettled`'s own existing tests continue to pass unchanged, confirming it).
