# ADR-00129: EventSource Stage 3 — CRLF boundaries, terminal failure, auto-reconnect

- **Relations**: Implements [TDD-00038](../tdd/TDD-00038.md), Extends [ADR-00122](ADR-00122.md), [ADR-00123](ADR-00123.md), [ADR-00124](ADR-00124.md)
- **Date**: 2026-08-08

## Context

[ADR-00122](ADR-00122.md)/[ADR-00123](ADR-00123.md)/[ADR-00124](ADR-00124.md) shipped `EventSource` Stages 0-2 (connection plumbing, SSE record parsing, named events/lifecycle callbacks), leaving three documented gaps: CRLF-terminated (`\r\n\r\n`) record boundaries weren't detected (bare-LF `\n\n` only), a non-2xx or wrong-`Content-Type` response was parsed as if it were valid SSE data instead of failing outright, and a dropped connection ended permanently `CLOSED` with no retry. Raised directly by the user reviewing the shipped feature against the real `EventSource` spec and asking to close these gaps in one pass rather than leave them as standing narrowings.

## Investigation

Read TDD-00038's own Open Questions section (all three gaps were already tracked there, just undesigned) and the real WHATWG HTML "Fetching the event source" algorithm before designing anything. Two things from that reading materially changed the plan versus a naive first pass:

- The spec draws a hard line between a *network-level* failure (DNS, connection refused, a mid-stream drop after a successful open — reestablish the connection, i.e. retry) and a response that *arrived* but had the wrong shape (status ≠ 200, or `Content-Type` isn't `text/event-stream` — fail the connection, permanently, no retry ever). An initial framing that treated "any failure" as retryable would have been spec-incorrect (retrying a 404 forever) — this is called out explicitly since the design almost shipped that way before rereading the spec's own algorithm structure.
- Auto-reconnect never needs fiber-parking or the general-purpose `setTimeout` timer queue: `new EventSource(url)` is fire-and-forget from KML code's perspective, and reconnecting is pure runtime bookkeeping, not user-visible code — wrapping it in a KML closure just to hand it to `__kml_timer_schedule` would be indirection with no payoff.

**A real bug found mid-implementation, not just a hypothetical avoided.** The first working version of the status/Content-Type check read both via `curl_easy_getinfo` directly from `__kml_eventsource_scan`'s `checkstatus` step, with a "couldn't check because the transfer already finished, assume it's fine" fallback for whichever attribute wasn't available yet. That fallback is unsound: `__kml_curl_drain_messages` (`runtime_fetch.go`) unconditionally does `curl_multi_remove_handle`+`curl_easy_cleanup` on `CURLMSG_DONE`, so once a transfer finishes, the easy handle is gone — calling `curl_easy_getinfo` on it afterward isn't just stale data, it's a use-after-free. Status turned out to be safe regardless (`__kml_curl_drain_messages` already safely captures it into `pending->status` *before* cleanup, for `fetch`'s own use — reusable as-is), but Content-Type has no equivalent safe post-cleanup source; the pending struct fetch and EventSource share only ever stores status. The "assume OK" fallback for Content-Type combined badly with how *reliably* the race triggers: `TestE2EEventSourceWrongContentTypeEndsClosedNoRetry`'s response (a 200 with a ~18-byte `text/plain` body) is small enough to always finish inside a single `curl_multi_perform` call, so "assume OK" fired on *every* attempt — the connection opened, the next scan noticed the already-ended transfer and treated it as a normal (retryable) drop-while-open, and reconnecting hit the identical race again, forever. Not a crash — an infinite reconnect loop against a permanently dead endpoint, which surfaced as the test hanging under `go test` (no timeout of its own; `tests/compiler_test.go`'s `exec.Command(...).Output()` blocks indefinitely on a hung child process) rather than a visible failure. Confirmed by isolating the exact test, watching it hang consistently, then bisecting the checkstatus logic to find the "assume OK on race" branch as the cause.

Root-caused rather than patched around: extending the *shared* fetch/EventSource pending struct to also capture Content-Type (mirroring how status is captured) would have meant updating every `getelementptr` call site across both `runtime_fetch.go` and `runtime_eventsource.go` for a change fetch itself doesn't need — too much blast radius on an already-shipped, well-tested feature for what turned out to be an avoidable tradeoff. Instead, added a dedicated `CURLOPT_HEADERFUNCTION` callback scoped entirely to EventSource's own runtime file: libcurl calls it once per response header line, strictly before the body write callback ever runs, and therefore strictly before the transfer can possibly finish and get cleaned up — regardless of how small or fast the response is. This closes the race at its root (Content-Type is captured the moment it's parsed, every time, not "if we're lucky enough to still be live when we check") rather than picking a better fallback for an unsound approach.

## Decision

**CRLF-tolerant boundaries**: `__kml_eventsource_process_available`'s single `"\n\n"` `strstr` search became three parallel searches (`"\n\n"`, `"\r\n\r\n"`, `"\r\r"`), picking whichever match starts earliest in the unconsumed tail. The three patterns can never spuriously overlap (no two share a substring relationship), so "earliest wins" is unambiguous and correctly handles a stream that varies its line-ending style record-to-record, not just a stream that's internally consistent. The extracted record is passed through a new `__kml_es_normalize_record(ptr raw, i64 rawlen)` helper (a two-pointer in-place-into-a-copy scan converting every `\r\n` or lone `\r` to `\n`) before reaching the unchanged, still-`\n`-splitting `__kml_eventsource_dispatch_record` — spec-correct, not an approximation, since the real SSE line-splitting algorithm treats `\r`/`\n`/`\r\n` as interchangeable line terminators throughout a record, not just at its boundary.

**Terminal vs. retryable failure**: `__kml_eventsource_scan`'s `checkstatus` step (reached whenever an entry is `CONNECTING` with a live in-flight transfer) reads status via `curl_easy_getinfo(CURLINFO_RESPONSE_CODE)` only while `pending->done == 0`; once done, it reads the value `__kml_curl_drain_messages` already safely captured into `pending->status` before cleanup. Content-Type is read from a new `contentType` field on the `es_entry` runtime struct, populated by the new `__kml_eventsource_header_cb` (`CURLOPT_HEADERFUNCTION`, `CURLOPT_HEADERDATA` = the `es_entry` pointer itself) as soon as a `Content-Type:` header line arrives — always safe to read regardless of transfer state, since it's this file's own heap allocation, not libcurl's. A status outside `[200,300)`, or a non-null Content-Type that isn't a `"text/event-stream"` prefix match (`strncmp`, case-sensitive — a documented narrowing), tears down the easy handle (only if not already torn down) and permanently closes: `state`/`readyState` → `CLOSED`, `onerror` fires once, `@__kml_es_active` decrements, no reconnect ever scheduled. A `null` (never-seen) Content-Type is treated leniently.

**Auto-reconnect**: two new `es_entry` fields, `retryMs` (defaults 3000, matching the real spec's default; overridable by a `retry:` field in any dispatched record, now `atoll`'d into this field instead of being parsed-and-discarded) and `reconnectAtMs` (an absolute deadline in milliseconds off a new standalone `__kml_eventsource_now_ms()` helper — `clock_gettime(CLOCK_MONOTONIC, ...)`, declared via `ensureClockGettime()` directly rather than pulling in the general-purpose timer-queue subsystem for an unrelated purpose). `reconnectAtMs == 0` means "has a live transfer right now"; nonzero means "waiting to reconnect, no live easy handle exists" — checked first in the scan's per-entry body, ahead of the existing `CONNECTING`/`OPEN` dispatch. Connection setup was factored out of `__kml_eventsource_open` into a new `__kml_eventsource_connect(ptr url, ptr headers, ptr es_entry) -> ptr pending`, shared by the original connect and every reconnect; a reconnect passes a `curl_slist` built from `"Last-Event-ID: " + instance.lastEventId` when non-empty (reusing `ensureCurlSlist`'s `curl_slist_append`, the same mechanism `fetch(url, init)`'s custom headers already use). Reconnect is scheduled from two triggers converging on one `doReconnectSchedule` block: a mid-stream drop while `OPEN`, and a network-level connect failure while still `CONNECTING` (`pending->done` becomes true without a status ever becoming available — distinguishable from a same-scan terminal failure precisely because `checkstatus` always resolves status, live or from `pending->status`, before this branch is ever reached). Both set `readyState` back to `CONNECTING` (never surfaced as `CLOSED` during a retry wait, matching the real spec) and leave `@__kml_es_active` untouched — a waiting-to-reconnect entry is still "work outstanding" for the event loop's keep-alive check. `.close()` during the wait skips the now-meaningless curl teardown and just marks `CLOSED` directly.

## Implementation notes

- **`runtime_eventsource.go`**: `es_entry` grew from 5 fields/40 bytes (Stage 2) to 9 fields/72 bytes (`ptr pending, ptr instance, i64 consumedOffset, i64 state, ptr listeners, ptr url, i64 retryMs, i64 reconnectAtMs, ptr contentType`) — every existing `getelementptr`'s struct-literal type string needed the trailing fields appended (mechanical, done via a blanket `sed` replace across the file, then hand-verified each call site's index still pointed at the right field).
- **`__kml_eventsource_open` reordered**: Stage 0-2 connected first, then allocated the entry. Stage 3 allocates the entry *first* (fields zeroed/defaulted), *then* connects, passing the entry pointer through so `__kml_eventsource_connect` can hand it to libcurl as `CURLOPT_HEADERDATA` — the header callback needs somewhere to write into that exists before the transfer starts.
- **Another `%entry`/`entry:` label collision**, the same class of bug [ADR-00122](ADR-00122.md) and [ADR-00124](ADR-00124.md) each already hit once: `__kml_eventsource_connect`'s new third parameter was first named `%entry`, colliding with the implicit `entry:` block label ("unable to create block named 'entry'" from `clang -S -x ir`). Fixed by naming it `%es_entry`, matching the existing convention `close`/`add_listener`/`remove_listener` already use for the same kind of parameter. Three-for-three now on this exact mistake across this file's history — worth a mental note that any new IR function taking the entry pointer as a parameter should default to `%es_entry`, never `%entry`, from the first draft.
- **SSA dominance drove the exact block shape of `checkstatus`**: status is read via one of two blocks (`statuslive`/`statusfromdone`) feeding a `phi` in `mergestatus`, and any value that's only meaningful along *one* of those paths (e.g. the live easy-handle pointer) is never threaded past `mergestatus` — every later block that needs it (`ft_teardown`) reloads it fresh from `pending_cs` (which dominates unconditionally) instead, even though the reload is dynamically redundant on the paths that matter. LLVM's dominance check is purely structural (it doesn't correlate two branches on the same runtime condition), so reusing a conditionally-defined value across a later branch on the *same* boolean still fails to verify unless the defining block structurally dominates the use.
- Every `%[N]s`/`%[N]d` explicit `fmt.Sprintf` index in the large `checkstatus`/`checkct`/`doreconnectschedule` block had to be re-derived by hand after the design changed mid-implementation (the UAF fix removed two placeholders, the header-callback addition added a new interned prefix) — worth calling out since a wrong index here doesn't fail to compile (Go's `fmt` silently substitutes whatever argument that index resolves to) and would have surfaced as subtly wrong IR rather than a build error; caught by IR-validating every version via `clang -S -x ir ... -o /dev/null` before running any test.

## Side effects discovered

The use-after-free/infinite-retry-loop bug described in Investigation was found and fixed as part of this same work, not deferred — see Investigation and Decision for the root cause (an unsound live-`curl_easy_getinfo`-with-lenient-fallback design) and fix (the dedicated header callback). No other bugs found; the case-sensitive `Content-Type` prefix match and the "one shared `retry`/`reconnectAtMs` per entry, not per-listener" design are deliberate, documented scope choices (see `docs/status/NETWORKING.md`'s Caveats), not discovered-but-unfixed gaps.

## Verification

- `go build -o klainmain .` and `go vet ./...` clean.
- Every intermediate version of the generated IR validated with `clang -S -x ir <file>.ll -o /dev/null` (catching both the `%entry`/`entry:` collision and a `fmt.Sprintf` argument-index mismatch before ever running a test) — done for every non-trivial change to `runtime_eventsource.go` during this work, not just once at the end.
- `tests/eventsource_test.go`: two pre-existing tests updated for the new, spec-correct behavior (a connection-refused failure now retries — `readyState` back to `CONNECTING`, not permanently `CLOSED` — so both needed an explicit `es.close()` to let the process exit instead of hanging on an unbounded retry loop with nothing to stop it), plus 5 new tests: CRLF and bare-CR record boundaries, non-2xx and wrong-`Content-Type` both ending permanently `CLOSED` with no retry (the second of these is what caught the UAF/infinite-loop bug — it hung under `go test` until the header-callback fix landed), and end-to-end auto-reconnect confirming the *replayed* `Last-Event-ID` value actually reached the server (not just that a second `onmessage` fired, which a reconnect with the wrong or no header would also produce). All 19 EventSource tests pass; full `go test ./...` passes with no regressions.
- `examples/eventsource/eventsource.ts` extended with terminal-failure (`/status/404`) and auto-reconnect (`/stream-retry`, a new `tools/httpbin-lite` fixture that drops after one record and echoes the replayed `Last-Event-ID` back) sections; compiled and ran directly against a locally started `httpbin-lite`, output matched every inline expected-output comment.
- Verified only on the x86-64 Linux development box (see the project's own platform-flagging rule) — pure LLVM-IR-text/Go compiler logic plus already-platform-neutral libcurl reuse (the same multi-interface/write-callback machinery `fetch`/Stages 0-2 already established), not expected to be platform-sensitive, but not directly confirmed on the Apple Silicon Mac.
