# ADR-02025: A transformer's start() promise, and stream controllers

- **Date**: 2026-11-22

## Context

- A transformer's `start()` promise did not hold back the first
  transform, and its rejection did not error the stream: both sides were
  marked started on the next microtask whatever `start` returned.
- Several problems turned up next to it:
  - A stream callback parameter typed `any` (`start(c: any)`) received
    the controller's raw pointer as a box. It read as a string, and
    `c.enqueue` was not a function (or the program crashed).
  - A transformer's controller reported itself as a
    ReadableStreamDefaultController.
  - `String()` of a stream, reader, writer or controller was its inspect
    text, and a template literal of a controller was empty.
  - A TransformStream's inspected `backpressure` was derived from the
    readable's desired size rather than its `[[backpressure]]` flag.
  - A synchronous `flush` finished the writable's close at once, so a
    `terminate()` inside it left the writable closed, where Node shows it
    erroring.

## Decision

- `start`'s result, a promise or a thenable read at run time, is the one
  start promise both sides react to, writable first
  (`__kml_ts_start_promise`). Each side starts when it fulfills, or
  errors with its reason.
- A callback literal that types a parameter `any`/`unknown` over a static
  argument goes through the stream's adapter arrow, whose call boxes the
  argument (`streamCallbackNeedsAdapter`).
- A transformer's controller type carries `HostTag`
  TransformStreamDefaultController. That is its class, its members
  through `any`, and its inspection: `stream:` is its TransformStream,
  found from the readable's pull closure (`__kml_ts_of_readable`), which
  is now wired before `start` runs.
- `String()` of a stream object is `[object <Class>]`.
- The transform context keeps `[[backpressure]]` (word 9). It is true
  from setup, cleared by the readable's pull, and set after an enqueue
  that leaves the readable with backpressure. Inspection reads it.
- A synchronous `flush` acts as a fulfilled flush promise: the readable's
  close, and the writable's close finishing, come a microtask later, as
  `TransformStreamDefaultSinkCloseAlgorithm` reacts to it.
