# ADR-01683: klain:http's h2o backend

- **Relations**: Implements TDD-00255, Extends ADR-01682
- **Date**: 2026-10-17

## Context

TDD-00255 Stage 2 adds a second server backend under `klain:http`: libh2o's libuv build, running on the program's own loop, selected at build time with `-http-backend`. ADR-01682 shipped the module and the `native` backend that the h2o one has to match.

## Investigation

- **Packages.** Ubuntu 24.04's `libh2o-dev` (h2o 2.2.5, library 0.13.5) is the libuv build; its pkg-config name is `libh2o`. Homebrew's `h2o` (2.2.6) ships only `libh2o-evloop`, h2o's own event loop, so macOS has no usable build. MSYS2 has none. This answers TDD-00255's open question.
- **A standalone probe** on the Linux box (`uv_default_loop`, `h2o_context_init`, `h2o_uv_socket_create`, one `on_req` handler) showed:
  - HTTP/1.1, h2c by prior knowledge, and h2c by `Upgrade` all reach the handler (`req->version` 0x101 / 0x200).
  - `Expect: 100-continue` is answered by h2o.
  - A request can be answered later from another loop callback.
  - **No streaming request body.** 0.13 buffers the whole body into `req->entity` before `on_req`, up to `max_request_entity_size` (default 1 GiB), and has no API to start the handler sooner.
  - **No header limit.** A 70 KB header block is accepted.
  - **The loop never ends.** After `h2o_context_request_shutdown`, h2o's context timers keep it alive. Disposing the context once connections drain hits `h2o_timeout_dispose`'s assertion: shutdown itself links timeout entries, even from a zero timer. Unreferencing the handles `h2o_context_init` created works on both protocols. The listener and the connections are referenced handles of their own, so the loop then ends once they close.
  - **No `Content-Length`.** `h2o_send_inline` does not set `res.content_length`, so a whole response went out without it, and HTTP/1 fell back to `Connection: close`.

## Decision

**Selection.** `-http-backend=native|h2o` sets `lib.HTTPBackend`, and the resolver maps `./internal_khttp_backend` to `internal_khttp_h2o.ts`. `h2o` without libh2o (`LocateH2O`: pkg-config `libh2o`, then `libh2o.so` on the compiler's search path) is a clear error naming the package.

**`native` stays the default.** TDD-00255 planned `h2o` as the default where the library is found. With 0.13 it cannot keep the native backend's behaviour past the 10 MiB cap: native runs the handler at the cap, streams the rest with backpressure, and keeps memory bounded with no upper limit. h2o holds the whole body in memory first, and answers 413 past 1 GiB. Defaulting to h2o would put that difference on every Linux program, so h2o is opt-in, and the flag's help names the difference.

**C unit** (`codegen/llvm/h2osrc/klainh2o.c`, `@link h2o`, flags from `H2OFlags`: libh2o, libuv, OpenSSL).
- One `h2o_globalconf_t` and context per process. The handles the context creates are unreferenced.
- Requests are exchanges in an id table. An id is the slot plus a generation, so a stale id never finds the slot's next occupant.
- A shared chunk on the request's pool (`h2o_mem_alloc_shared`) marks the exchange gone when h2o disposes of the request. Calls on a gone exchange do nothing, and a pending write's callback gets -1.
- A header block over 16 KiB (Node's `--max-http-header-size`) is answered 431, and the connection closes, as on the native backend.
- Responses:
  - a whole response is `h2o_send_inline` with `content_length` set;
  - a streamed one is a generator, where `proceed` is the write callback, the backpressure signal;
  - `Content-Length`, `Transfer-Encoding`, `Connection` and `Keep-Alive` from the handler are left to h2o (`Connection: close` turns keep-alive off);
  - header names keep the handler's case on HTTP/1 (`orig_name`), but the framing fields h2o writes itself are lowercase (`transfer-encoding: chunked`), which HTTP allows;
  - reason phrases are Node's `STATUS_CODES`.
- `close()` closes the listener and requests the context's shutdown, so HTTP/2 sessions get GOAWAY. 0.13 keeps an idle HTTP/1 keep-alive connection open through a shutdown, so the unit counts each connection's unanswered requests (through the connection's `get_socket`). It ends the idle ones at `close()`, ends each busy one when its count reaches zero, and marks every later response non-persistent. The shutdown flag is cleared on the next `listen`. `closeAllConnections()` shuts down every accepted socket's descriptor, so h2o sees it end.
- Under `-mm=gc`, h2o allocates from the collector while libuv's lists are raw memory, so the accepted handles are held in a table the collector scans, until their close callback.

**TypeScript** (`lib/node/internal_khttp_h2o.ts`) exports the native backend's functions. The body arrives complete, so a body of 10 MiB or more puts the request in streaming state before the handler runs: `stream()` yields all of it, and `req.body`/`bodyBytes()` throw as on the native backend.

**Both backends now join a repeated request header** with `, `, as Node does. The native backend used to keep the last value.

## Side effects discovered

- **An unannotated callback returning object literals of different shapes failed to compile** ("object has no field 'headers'"). Its return type was inferred from the first return alone. Both arrows and function expressions, sync and async, now build the contextual return type's object when every return is an object literal of its fields (`contextualObjectReturn`). That is the contextual signature's single object type, or the awaited one of `R | Promise<R>`.

- **Under `-mm=gc`, the frames below a task swap were not roots.** While a task runs, the collector scans the task's stack (`GC_stackbottom`, or the thread's record, points at it), so the thread's own stack under the swap was not scanned. Whatever only those frames referenced could be collected while the task allocated. Here that was the h2o backend's exchange, which an async handler's spawner holds: concurrent async handlers answered exchange id 0, and their clients hung. `task.c` now reports leaving the thread's own stack and coming back, and gcshim pushes the stack left, from its last frame to its bottom, at every collection (`GC_set_push_other_roots`), one record per thread.

- Tests:
  - `make test-h2o` runs every `klain:http` test with `KLAIN_TEST_HTTP_BACKEND=h2o`;
  - CI runs it on Linux;
  - `TestE2EContextualReturnObjectShapes`.

  - a smoke program covering HTTP/1.1 keep-alive, h2c, joined headers, a streamed response, a 12 MB body, 431, and `close()` ending the program;
