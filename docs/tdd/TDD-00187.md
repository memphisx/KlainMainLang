# TDD-00187: `undefined` for a concrete scalar — retiring the zero-fill caveat family

- **Status**: Partially Implemented
- **Date**: 2026-09-08

## Context

A whole family of documented caveats share one root cause: operations that
TypeScript's own `lib` types describe as `T | undefined` are modelled here as
returning a bare, **zero-filled** `T`. There is no way for a concrete scalar
(`number`/i64, `boolean`/i1, an annotated `float`/`Date`) to say "absent," so
each of these sites picks a wrong-but-deterministic value instead:

- `Array.prototype.pop()`/`.shift()`/`.find()`/`.at()` on an empty array or a
  miss return `emitScalarZero`/`zeroRef` (`emit_arrays_mutate.go:108-128, :408`,
  `emit_arrays_hof.go:397-446`, `emit_arrays_transform.go:257-311`) — TS types
  all four `T | undefined`.
- An omitted optional field (`interface P { x: number; y?: number }`, read
  `p.y`) reads `calloc`-zero (`emit_objects.go:169-175`, ADR-00157) — TS types it
  `number | undefined`. Array destructuring past length reads zero (ADR-00157
  Bug 2).
- `process.env.MISSING` returns a null string, not `undefined`
  (`emit_process.go:166-214`); out-of-range `argv[i]` returns `""`
  (`emit_exprs_member.go:386-`) — TS types both `string | undefined`.
- `process.stdout.columns`/`.rows` off a TTY returns `80`/`24`, a deliberate
  tested divergence (`emit_tty.go:80-97`, BACKLOG §2) — Node returns `undefined`.

Each is individually ✅ with a real caveat, so each excludes its row from Strict
Coverage. One representation answer retires the family at once — the reason
BACKLOG §1.1 ranks this the highest-leverage enabler.

Crucially, **the representation already exists.** [TDD-00064](TDD-00064.md)
shipped all four stages of a presence-flagged `{ i1 present, T value }` optional
(Option A) for *annotated* nullable scalars — `storageIR`/`isNullableScalar`/
`nullableScalarStorageIR` (`types.go:2186-2206`), flow narrowing, parameter/
return/field boundaries, and `Map<K,number>.get()` returning a real
`undefined`. Separately, the NaN-boxed `any` ([ADR-00628](../adr/ADR-00628.md))
already encodes `undefined` (`0x0A`) distinctly from `null` (`0x02`). The
sentinel is real in both the annotated-nullable world and the dynamic world —
it is simply **unreachable from a bare concrete scalar**, because the operations
above are inferred as bare `T` rather than `T | undefined`. This makes TDD-00187
overwhelmingly a *type-inference + reuse* task, not a new-representation task —
a very different (smaller, lower-risk) shape than TDD-00064 was.

## Design

**Core move**: make `inferExprType` return `T | undefined` (i.e. a `Nullable`,
`IsUndefined` `Type`) for each absence-capable operation, and make each emit
site produce the value in the representation TDD-00064 already defined:

- **Non-pointer scalar `T`** (`number`, `boolean`, annotated `float`/`Date`):
  the existing `{ i1, T }` optional. The absent path stores `{ present=false }`
  where it currently stores `emitScalarZero(T)`; the present path stores
  `{ present=true, value=v }`. Every consumer path (`??`, `?.`, `=== undefined`,
  narrowing, `String()`, `typeof`) already handles `{ i1, T }` from TDD-00064 —
  this is the whole point of reusing it.
- **Pointer `T`** (`string`, object, array, class): `undefined` is the null
  pointer, exactly as `TypeUndefined` (`types.go:2371`) already is. No storage
  change; only the *static type* gains `Nullable|IsUndefined` so `=== undefined`
  and narrowing engage. (`null` vs `undefined` stay distinct **statically** via
  the `IsUndefined` flag — see Open questions — but share the null-pointer bit
  pattern, which is faithful for these sites since none of them can produce a
  real `null`.)

Nothing new is invented at the representation layer. The work is (a) flipping
the inferred return type at each site, (b) swapping the zero-fill for a
present=false store on the absent branch, and (c) the migration policy below.

### The one real decision — what happens to existing bare-`T` consumers

Flipping `.pop()` from `number` to `number | undefined` is faithful to TS, but
today's programs (and the test corpus) freely write `let x: number =
arr.pop()`. Real TS **strict** rejects that (`Type 'number | undefined' is not
assignable to 'number'`); TS with `strictNullChecks: false` accepts it and
treats the result as bare `number`. This compiler already carries exactly that
axis — the `strict` vs `-compat=js` split. So the policy writes itself and
introduces no new concept:

- **`strict` (default):** the operations are `T | undefined`. Assigning to a
  bare `T`, or using in arithmetic without narrowing/`!`, is a **compile
  error** with a faithful message — the honest, TS-strict behaviour. Programs
  narrow (`const x = arr.pop(); if (x !== undefined) …`) or assert (`arr.pop()!`).
- **`-compat=js`:** `strictNullChecks: false` semantics — the result auto-widens
  to bare `T` at the assignment/use boundary, preserving today's lenient
  programs. The *value* is still faithfully absent-aware where it is observed as
  `T | undefined` (e.g. `=== undefined`, `??`); it only silently unwraps where a
  bare-`T` context demands it.

This is the recommended direction: it is the genuinely faithful behaviour under
each mode, reuses an axis that already exists, and means the corpus migration is
a mode-gated, mechanical narrowing pass rather than a semantics gamble. The
alternative — flip the types but auto-unwrap everywhere regardless of mode —
is rejected: it would keep `let x: number = arr.pop()` compiling in strict mode,
which is exactly the un-faithful leniency the strict mode exists to reject.

### Staging

Ordered by leverage and independence; each stage is a shippable ADR with its own
E2E test + example, and each retires specific caveat rows same-commit.

1. **Stage 1 — array element-absence ops.** `.pop()`/`.shift()`/`.find()`/
   `.at()` return `T | undefined`. Highest frequency, most self-contained,
   exercises both the scalar `{ i1, T }` and pointer-null paths. Establishes the
   `strict`/`compat=js` migration policy end-to-end (this is where the corpus
   narrowing pass happens). `zeroRef`/`emitScalarZero` on the miss branch →
   present=false store.
2. **Stage 2 — optional-field & destructuring reads.** `p.y` for `y?: T`, and
   `let [a,b] = [x]`'s out-of-range `b`, become `T | undefined` instead of the
   ADR-00157 calloc-zero. The calloc stays (it is still the correct *storage*
   zeroing); what changes is the *read*'s inferred type and the present-bit
   derivation. Needs a "was this field provided" signal — for a `?:` field the
   static type already says so; the present bit is the field's own nullable slot
   where the field is itself a nullable scalar, else a pointer-null / a struct
   presence bit. (Resolve exact mechanism in Open questions.)
3. **Stage 3 — environment & argv boundaries.** `process.env.X` and
   out-of-range `argv[i]` → `string | undefined`. Cheap: `string` is a pointer,
   so `undefined` = null pointer; the null-string result already flowing out of
   `emitGetenvCall` just needs the `Nullable|IsUndefined` static type and the
   `""`-substitution at `argv.out` removed. Fixes `process.env.MISSING ===
   undefined` and `argv[99] === undefined`.
4. **Stage 4 — TTY & closed-stream off-nominal reads.** `stdout.columns`/`.rows`
   off a TTY → `number | undefined`, **retiring the deliberate 80×24 divergence**
   (BACKLOG §2 explicitly folds in here). Closed-stream scalar reads likewise.
   Last because it flips a *documented, tested* divergence — its test currently
   asserts `80`, and that assertion inverts here.

## Open questions

- **`null` vs `undefined` on the pointer path.** For a pointer `T`, both share
  the null bit pattern; the `IsUndefined` static flag is the only distinguisher.
  Is that enough for every observable — `typeof x` (`"undefined"` vs `"object"`
  for null), `String(x)` (`"undefined"` vs `"null"`), `JSON.stringify` (key
  dropped vs `null`)? These read the static type, so it *should* suffice, but
  Stage 3 (`process.env`) is the first place a pointer-typed value is observed as
  `undefined` rather than `null` and must confirm each observable renders right.
- **Stage 2 present-bit source.** For an optional *pointer* field, present =
  non-null is unambiguous. For an optional *scalar* field, calloc-zero and a
  real stored `0` are indistinguishable at the slot — so the field's storage
  itself must become the `{ i1, T }` optional when the field is `?:` on a scalar
  (widening the struct layout), or carry a separate presence bitmap. Decide
  between per-field `{ i1, T }` widening (simple, local, some space cost) vs a
  per-object presence bitmap (compact, more plumbing) during Stage 2.
- **Corpus migration size under strict.** How many existing tests/examples write
  `let x: T = arr.pop()` and now need `!`/narrowing? Measure in Stage 1 before
  committing to the strict-default; if it is pervasive in the corpus's own
  fixtures (as opposed to user code), that is a signal about the assertion style
  to standardise on, not a reason to weaken the mode.
- **`.at()` TypedArray/bigint miss.** `.at()` on a BigInt64Array miss currently
  yields `0n`; the `T | undefined` flip must extend to the bigint element type,
  not just i64/double (`emit_arrays_transform.go:304-309`).
- **Does Stage 4 need a per-row status re-vote?** Flipping 80×24 → `undefined`
  changes a row from "✅ with a tested divergence caveat" toward Strict-eligible;
  confirm the divergence caveat is fully removed (not merely reworded) in the
  same commit, per the Strict-Coverage rule.
