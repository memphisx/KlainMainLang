# ADR-00936: Boxed arrays render their contents in string contexts (TDD-00212 Stage 1)

- **Relations**: Implements TDD-00212; Relates to ADR-00478, TDD-00062
- **Date**: 2026-09-14

## Context

An array boxed into `any` stringified to the placeholder `[object Array]` in
every string context (`String([1,2,3])`, `` `${a}` ``, `"" + a`), where JS
produces `"1,2,3"`. A statically-typed array renders fine because the emit site
knows its element type; the `any`-boxed case lost it — the box (ADR-00478) was a
bare 16-byte `{ ptr data, i64 len }` with no element descriptor, so the stringify
site (`emit_dynamic.go`, which sees only the runtime `kmlTagArray`) fell back to
the honest `[object Array]` stand-in (the deviation documented in TDD-00062).

## Investigation

The element type IS known at box time (`emitBoxValue`'s array arm receives
`v.Ty.ElemType`) and simply discarded. Recording a compact element-kind
descriptor in the box lets the render site recover it. Two representations were
weighed in TDD-00212: converting to a boxed-element dynarr at box time (Option A,
rejected — O(n) copy that breaks `===` identity and live mutation), versus an
element descriptor added to the box header (Option B, chosen). The heterogeneous
/ nested / object-element cases already lower to a D1 dynamic array
(`kmlTagDynArray`, rendered by `__kml_dynarr_join`), so only genuinely-static flat
arrays reach the `kmlTagArray` box this ADR changes.

## Decision

Stage 1 (string contexts; both lanes):

- **Box layout.** The `any`-array box header becomes `{ ptr, i64, i8 }`
  (`anyArrayBoxTy`) — the old `{data, len}` shape (data@0, len@8 **unchanged**)
  plus a trailing element-kind byte. Because the first 16 bytes are identical,
  every existing reader of the `{ ptr, i64 }` (the `__kml_any_eq` array arm, an
  `any`→array unbox) is unaffected; only the stringify arm reads `elemKind@16`.
  `boxArrayValue` (the 16-byte nested-array element slot, TDD-00029) is untouched
  — the new `boxAnyArray` is a distinct helper used only at the `any` boundary.
- **Descriptor.** `arrayElemKind` maps a flat scalar/string element type to a
  `KJ_*` code (f64/f32, signed+unsigned int widths, bool, string). A kind not
  representable at box time (nested array, object, boxed-any) stores the sentinel
  `-1`.
- **Render.** `__kml_array_join(data, len, kind)` (added to `dynjson.c`, reusing
  its `Sb` builder and `__kml_dtoa`) strides the buffer by `kind` and joins with
  `,` using JS `Number.prototype.toString` semantics (NaN/Infinity print
  literally, unlike JSON). `kind < 0` returns `[object Array]` unchanged — no
  regression on cases this stage does not render.

`console.log`'s `util.inspect` bracket form (`[ 1, 2, 3 ]`) is Stage 2 — a boxed
array currently routes through ToString, so `console.log(a)` prints `1,2,3` for
now (already a strict improvement over `[object Array]`).

## Implementation notes

Files: `codegen/llvm/emit_dynamic.go` (`anyArrayBoxTy`, `arrayElemKind`,
`boxAnyArray`, the stringify arm), `codegen/llvm/dynjson_c.go` (declare
`__kml_array_join`), `codegen/llvm/dynjsonsrc/dynjson.c` (the helper). The
descriptor integers and the C `KJ_*` enum must stay in sync.

Live-mutation-through-box (a `push` after boxing showing up in the box) is not in
Stage 1: `emitBoxValue` receives an already-loaded `{data,len}` aggregate, so the
box is a snapshot — the same as before this change, so no regression. Carrying the
live heap header pointer is tracked in TDD-00212 for a later stage.
