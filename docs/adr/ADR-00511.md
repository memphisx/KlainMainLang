# ADR-00511: `class X extends Transform` (Node stream subclassing, Stage C2)

- **Relations**: `Implements TDD-00132`, `Extends ADR-00510`
- **Date**: 2026-08-30

## Context

TDD-00132 Stage C2, the last stream-subclassing shape. Stage C1 (ADR-00510)
shipped `extends Duplex` — two independent sides on one instance. `Transform` is
not two independent sides: chunks written in must route through a
`_transform(chunk, enc, cb)` override whose `this.push(...)` feeds the readable
side, with the readable side ending when the writable side closes. This is the
"one genuinely new mechanism" the TDD flagged.

## Investigation

The options-form Transform (`new Transform({ transform })`,
`emit_node_stream.go` `case "transform"`) already had the exact runtime: an
`rs` + `ws` joined by a 72-byte **TSCTX** whose sink (`__kml_ts_sink_write`)
runs the transform when the readable side has capacity, else parks the chunk,
and whose `__kml_ts_pull` resumes a parked chunk
(`runtime_streams_pipe.go:466`). The slot-2 transform closure ABI is
`ptr(ptr %env, i64 %v0, i64 %v1)` returning a promise-or-null (line 482).

That ABI is **identical** to what `emitClassStreamWrite` already emits for a
`_write` sink. And a class `_transform` needs no controller argument: `this.push`
inside the method already reaches the readable side through the instance's
hidden Node-stream handle (whose `rs` is TSCTX slot 0). So the whole feature is:
reuse the TSCTX wiring, sourcing slot 2 from the subclass's `_transform` method.

`ensureNodeStreamRuntime` already pulls in `ensureStreamPipeRuntime`
(`runtime_node_stream.go:29`), so the TSCTX functions are available.

## Decision

1. Add `ClassInfo.HasNodeTransform`, set for `extends Transform` and every
   descendant (distinguishes a Transform from a plain Duplex — both set
   readable+writable).
2. Remove the compile-time Transform reject guard; accept `Transform<T>`
   (both sides `T`) and `Transform<In, Out>` (writable-in, readable-out).
3. In `emitConstructNodeStreamHandle`, branch to a new
   `emitConstructNodeTransformHandle` before the independent read/write path.
   It mirrors the options-form Transform wiring, with slot 2 =
   `emitClassStreamWrite(_transform, …)` — the same thunk as a `_write` sink.

`_flush` stays out of V1 scope (slot 3 = null), as do `_writev`/`cork`/`_final`.

## Implementation notes

- `emit_classes.go`: `HasNodeTransform` flag + set; guard removed; base
  type-arg switch extended to the 2-arg `<In, Out>` form.
- `emit_node_stream_class.go`: new `emitConstructNodeTransformHandle`.
- No runtime changes — the TSCTX sink/pull machine is reused verbatim.

## Side effects discovered

Node's default (non-`objectMode`) streams deliver **Buffer** chunks, so a Node
`_transform` doing `chunk.toUpperCase()` fails there unless `objectMode`/encoding
is set — this compiler's chunks are typed by `<T>` and need no such flag. The
example uses `super({ objectMode: true })` so it runs identically under both.
Not a divergence in this compiler; a Node default. `_flush` remains unimplemented
(tracked in TDD-00132).

## Verification

- New E2E tests (`tests/streams_test.go`): `TestE2ENodeStreamClassExtendsTransform`
  (uppercasing `_transform` + `this.push`) and `TestE2ENodeStreamClassTransformPipe`
  (`Readable.from(...).pipe(transform)` with `highWaterMark: 2` exercising the
  TSCTX chunk-parking backpressure path). Both pass.
- `examples/streams/class_extends.ts` extended with a `Transform`; output
  matches `node` per stream (every chunk delivered correctly). The lines of two
  independent readable streams interleave in a different order than `node`, a
  microtask/event-loop scheduling difference, not a data defect.
- A standalone pipe repro also matched Node (`doubled: 2,4,6,8,10`).
- Machine: Apple Silicon M4 (macOS).
