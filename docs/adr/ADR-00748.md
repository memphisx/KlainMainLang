# ADR-00748: Windows fs — `\\?\` extended-length prefix for paths over MAX_PATH

- **Relations**: Implements a [TDD-00180](../tdd/TDD-00180.md) §4 row; extends [ADR-00719](ADR-00719.md) (the Win32 fs layer), [ADR-00743](ADR-00743.md) (the `CreateFileW` open path that consumes these paths), [ADR-00487](ADR-00487.md) (recursive `mkdir`)
- **Date**: 2026-09-07

## Context

`to_wide` (the UTF-8→UTF-16 path converter every fs call in `win32fs.c` goes through) never added the `\\?\` extended-length prefix, so a path at or beyond Windows' historical `MAX_PATH` (260) failed with a path-too-long error where Node (via libuv's `fs__capture_path`) succeeds. A compiled program could not create, write, stat, or delete a file under a deep directory tree.

## Decision

`to_wide` leaves short paths byte-for-byte unchanged — zero behavioural change for the overwhelming majority — and, only for a near-limit path, normalizes it with `GetFullPathNameW` (absolute, backslash-separated, `.`/`..` resolved — the form the extended prefix requires) and wraps it: `\\?\` for a drive path, `\\?\UNC\` for a UNC path (`\\server\share`). An already-extended path is left alone.

The threshold is `MAX_PATH - 12` (248), **not** 260: `CreateDirectoryW` reserves 12 characters for an 8.3 name within the directory, so a 248–259-character *directory* path fails plain with `ERROR_FILENAME_EXCED_RANGE` even though it is under 260. Reproduced directly: a 253-char `CreateDirectoryW` returns error 206 while the same path under `\\?\` succeeds. Using one threshold (248) for every fs op keeps files and directories consistent, and the recursive `mkdir` chain crosses into `\\?\` before the directory limit bites, so each prefix — plain below 248, extended above — refers to the same location and the chain holds.

## Consequences

- `tests/fs_longpath_test.go` (cross-platform — POSIX handles long paths natively): create a >260-char tree, then `mkdir -p`/write/read/stat/unlink all succeed. Verified on Windows 11 and Linux (Docker).
- Short paths never call `GetFullPathNameW`, so their exact bytes (including any mixed `/`-`\` separators and trailing dots the current code relies on) are unchanged; only near-limit paths are normalized, which is required for the extended form anyway.
- Two earlier tests (`argv_utf8`, `fs_longpath`) were renamed off the `_windows` suffix — a Go GOOS build constraint that had silently made them Windows-only — so they now also guard Linux/macOS.
- Still open in §4: `fs.watch`, `utimes`, `link`, `fsync`, `ftruncate`, `copyFile`, `statfs`, junction symlinks — those are unimplemented JS APIs (cross-platform feature work), not Windows path bugs.
