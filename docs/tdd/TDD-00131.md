## Context

Early on, several Node.js APIs were implemented with **bespoke shapes** that don't
match Node's real signatures — most visibly the HTTP server: this compiler
exposes `http.listen(port, (req) => ({ status, body }))` (the handler *returns* a
response object), where Node is `http.createServer((req, res) => { res.writeHead(
200); res.end(body) }).listen(port)` (a mutable `res` you write to). There is no
`http.createServer` at all.

This breaks the portability goal: **code written for KlainMainLang should also
run under real Node.js** (browser-specific APIs excepted). Today, code using the
bespoke shapes won't run in Node, and real Node code won't compile here.

## Design

### Principle

The standard Node module names — `http`, `fs`, `process`, `net`, `stream`,
`events`, … — expose the **real Node.js API** (faithful method names,
signatures, and object shapes), so a program's Node-facing code is portable in
both directions. Fidelity is measured against the `.d.ts` / documented Node
signatures and, systematically, the Node `test/parallel` conformance oracle
([TDD-00121](TDD-00121.md) / [TDD-00082](TDD-00082.md)).

### The `klain:` namespace (the strategy this TDD records)

The existing bespoke implementations are **not deleted** — they are deliberate
re-imaginings of how an API "should" work, and worth keeping. They move to a
`klain:`-prefixed specifier namespace:

- `import http from 'klain:http'` → the current bespoke `http.listen(handler ⇒
  response)` model.
- `import http from 'http'` → the real Node `http.createServer`/`(req, res)`
  model.

Documentation makes it explicit that `klain:*` is **not Node** — it is this
project's own API surface, which under the hood may share mechanics with the Node
implementation (both ride the same fiber/event-loop runtime) but is a separate,
intentional design. The namespace is reusable for future bespoke re-imaginings
beyond the modules that have a Node counterpart.

### Mechanism

The specifier→marker table (`resolver/virtual_modules.go`
`virtualBuiltinMarkers`) already maps `"http" → "http__kml_builtin"`, and codegen
dispatches on the marker. The namespace split is a table change plus a second
codegen dispatch:

1. Add `"klain:http" → "klainhttp__kml_builtin"` (a distinct marker), and route
   the existing `emitHTTPListen`/`emitHTTPClose`/… dispatch under it.
2. Repoint `"http" → "http__kml_builtin"` at a **new** Node-faithful
   implementation (`http.createServer`, `(req, res)`, a `ServerResponse`
   `res` object, `server.listen(port[, cb])`).
3. Generalize the `klain:` prefix in the specifier resolver so future
   `klain:<mod>` names resolve to their bespoke marker without a per-module
   special case.

Both implementations reuse the shared runtime (the `select()` loop, the
connection-fiber model, the request parser) — only the user-facing shape differs.

### Stage 1 — `http` (this document's detailed scope)

Node's `http` server model to implement under the `http` specifier:

- `http.createServer(listener)` returns a `Server`. The `listener` is `(req:
  IncomingMessage, res: ServerResponse) => void`.
- `server.listen(port[, callback])` starts accepting; returns the server (Node
  chains). The optional callback fires once listening.
- `req` (`IncomingMessage`): `.method`, `.url`, `.headers` — mapping the existing
  parsed-request fields (`HttpRequest`) onto Node's property names.
- `res` (`ServerResponse`, a Writable): `res.writeHead(status[, headers])`,
  `res.setHeader(k, v)`, `res.statusCode`, `res.write(chunk)`, `res.end([chunk])`.
  The imperative writes are buffered/streamed onto the same response path the
  bespoke dispatcher already drives from its returned `{status, body, headers}` —
  i.e. `res` accumulates status/headers/body and flushes on `.end()`, reusing the
  buffered-vs-chunked machinery ([ADR-00300](../adr/ADR-00300.md)).
- `server.close()` / `closeAllConnections()` map to the existing teardown.

The key new codegen is the **`res` object as a mutable Writable** and
`createServer(...).listen(...)` returning a `Server` value that carries the
listener — versus the bespoke single-call `http.listen`.

### Later stages — one per diverged module

Each subsequent stage takes one module, inventories its divergence from Node,
moves the bespoke shape (if any) to `klain:<mod>`, and implements the Node shape.
Candidate order by portability leverage (to be confirmed against the Node oracle
histogram, [TDD-00082](TDD-00082.md)):

1. `http` (Stage 1, above) — the flagship.
2. `stream` / `fs` streams — `Readable`/`Writable`/`Duplex` as real classes with
   `class X extends Readable`, `.pipe`, event-based `data`/`end` (today: options
   -form only, string chunks).
3. `events` — `EventEmitter` variadic `...args`, subclassing, `instanceof`
   (today: single payload type, no subclass override).
4. `process` — `unhandledRejection`, `process.memoryUsage()`, `process.version`,
   and any signature gaps.
5. `fs` — async signatures / `fs.promises` fidelity, binary `readFile`.
6. `net` / `dgram` / `dns` / `child_process` — audit each against Node.

A per-module divergence inventory is maintained as a living checklist (a
follow-up scan / the Node-oracle false-reject histogram feeds it), not frozen
here — the strategy and Stage 1 are what this document fixes.

## Open questions

- Whether `http` remains ambient (as `http.listen` effectively is today) or
  becomes strictly import-gated (`import http from 'http'`) like `fs`. Node
  requires the import; matching that is more faithful but changes existing
  ambient usage — decide as part of Stage 1.
- How faithfully `res` must implement the full Writable-stream contract
  (backpressure, `cork`/`uncork`, `drain`) versus a pragmatic
  `writeHead`/`write`/`end` subset in V1.
- Whether `klain:http` keeps its single-`http.listen`-per-program restriction or
  is generalized once the Node `Server`-object model exists alongside it.
- Migration of the existing `http.listen` examples/tests/ADRs to the `klain:http`
  import (a mechanical but broad sweep) — staged so nothing breaks mid-flight.
