# ADR-01711: Guarded generator stacks under -mm=gc; a finished generator releases its stacks

- **Relations**: `Implements TDD-00249`; `Fixes ADR-01648`
- **Date**: 2026-10-18

## Context

ADR-01648 left `-mm=gc` generator stacks as collected heap blocks without a guard page, so an overflow inside a generator could overwrite the heap instead of throwing. A generator stack can't simply be a root, as task stacks are: its frames point back at the generator, so every generator would stay reachable forever. While measuring a fix, two more problems showed up, in every memory mode:
- a generator's jmpbuf stack (`__kml_jmp_stack_new`, about 16 KB) was never freed;
- every generator made its own mmap, mprotect and munmap calls.

For 300,000 short generators: `-mm=gc` took 9.3 s and 2.2 GB RSS; the default mode took 52 s and 3.3 GB.

## Decision

- **Owner cell (`-mm=gc`, POSIX).** A generator's stack is a guarded mapping owned by a small collected cell, which is the generator's stack field. The cell is a collector object kind of its own, whose mark procedure scans the stack. The frames are therefore traced exactly while the generator is reachable, and a no-order finalizer gives the stack back. The cell also owns the jmpbuf stack.
- **What gets scanned.** A body that swaps out records where its frames end (`__kml_gen_stack_park`), and only that slice is scanned. A generator that hasn't started has nothing to scan. A body suspended inside another coroutine's resume has its whole stack scanned.
- **Collection pacing.** Once the live owned stacks double since the last collection, a collection runs, because the collector's own pacing doesn't see memory outside its heap.
- **Release on completion.** A sync generator whose body has completed releases its stack and jmpbuf stack at once, in every mode, since its body never runs again.
- **Stack pool.** Spent fiber stacks, both `__kml_fiber_stack_alloc`'s and the owned ones, go to a pool of 64 for reuse.

## Consequences

- The 300,000-generator run takes 3.4 s and 75 MB under `-mm=gc`, and 3.3 s in the default mode. The default mode still keeps each generator's object and context (about 1 KB), like every other manual-mode allocation.
- On Windows, generator stacks are unchanged.

## Verification

- macOS (Apple Silicon) and Linux x86-64 (DeskMini): `TestE2EStackOverflowGeneratorGC` passes, as do the GC, generator, stack-overflow, task and coroutine E2E tests.
- macOS: completed, thrown, returned and delegated generators match Node in both memory modes.
