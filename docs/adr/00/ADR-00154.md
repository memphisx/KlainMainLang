# ADR-00154: Object literal string/numeric-literal property keys

- **Relations**: Extends [ADR-00153](ADR-00153.md) (Test262 full-corpus conformance harness)
- **Date**: 2026-08-11

## Context

ADR-00153's failure-reason table surfaced `expected IDENT, got STRING` (3,087 files) and `expected IDENT, got NUMBER` (671 files) as two of the largest COMPILE_ERROR buckets in the Test262 conformance run. Investigating directly (`parser/parser_literals.go:84`, `parseObjectLiteral`) found the cause: an object literal's `PropertyName` grammar was implemented as bare `IDENT` only — `{ "foo": 1 }` and `{ 0: "a" }`, both ordinary JS/TS syntax, were a clean parse-time rejection rather than a silent miscompile, but a real gap all the same. Picked as the first of the "easy win" candidates identified while triaging the conformance report for opportunities where coverage gained is large relative to the design effort needed.

## Investigation

Confirmed the exact blocker with minimal repros (`{"foo": 1}` → `expected IDENT, got STRING`; `{0: "a"}` → `expected IDENT, got NUMBER`) and confirmed `ObjectProperty.Key` (`ast/nodes.go`) is already a plain `string`, with downstream consumers (`codegen/llvm/emit_objects.go`'s `FieldIndex(prop.Key)` lookups) keying purely off that string — nothing downstream assumes the key came from an `IDENT` token specifically. This made the fix front-end-only: widen which token kinds `parseObjectLiteral` accepts, no codegen changes needed.

Scanned the corpus by directory to separate genuinely in-scope files from `intl402`/`Temporal`-heavy noise (out of this project's priorities regardless of size): the STRING bucket was dominated by `built-ins/Object` (152), `built-ins/Array` (23), `language/statements` (23), `language/module-code` (11); the NUMBER bucket by `built-ins/Array` (568, mostly array-like-object test fixtures such as `{0: 'a', 1: 'b', length: 2}`) plus smaller `language/` counts — real, core-language-adjacent usage, not internationalization noise.

Checked whether the same `IDENT`-only restriction exists elsewhere (destructuring patterns, `interface`/type-annotation field declarations — `parser_classes.go`, `parser_stmts.go`, `parser_types.go` all have their own separate `p.expect(lexer.IDENT)` call sites for property/field names). Confirmed directly that `interface Digits { "0": string }` still fails identically post-fix — a `#`-name-shaped but separate gap, deliberately left alone here to keep this change scoped to the one grammar production (`ObjectLiteral`'s `PropertyName`) it was investigating, not a general "quoted property names everywhere" sweep.

## Decision

Widened `parseObjectLiteral`'s property-name gate from bare `lexer.IDENT` to `IDENT | STRING | NUMBER`, using the token's own `Literal` text as the key in all three cases — matching what an equivalent identifier key would already produce (`{"foo": 1}` and `{foo: 1}` both key as `"foo"`). Shorthand (`{ x }`) stays `IDENT`-only, since it's sugar for referencing an in-scope binding of the same name — a string or numeric literal has no such binding to shorthand from, matching real JS (`{"foo"}` is itself a `SyntaxError`).

## Implementation notes

`parser/parser_literals.go`: replaced the single `keyTok, err := p.expect(lexer.IDENT)` with an explicit three-way `check` (clearer error message: `expected property name, got %s` instead of misleadingly implying only `IDENT` was ever valid) followed by `p.advance()`, then branched only on whether a `COLON` follows — a `COLON` accepts any of the three token kinds, its absence re-checks for `IDENT` (shorthand) and rejects otherwise.

Numeric keys aren't dot- or bracket-readable back through existing syntax (no identifier spells `0`, and bracket-string member access on a static struct type isn't implemented — only on dynamic Map-backed computed-key literals). Real, but not part of this change's scope; documented as a caveat rather than silently left implicit, and worked around in the example/test via `JSON.stringify` (which walks the field list by name, not through access syntax).

## Side effects discovered

Regenerating the conformance report (`go run ./tools/conformance`) after the fix moved overall passed count from 4,475 to 4,474 — a net decrease of one, not the increase the bucket sizes might suggest. Diffing per-file pass/fail against a stashed baseline (both runs instrumented with a temporary debug dump, reverted before landing) found zero newly-passing files and one newly-failing one: `language/expressions/object/__proto__-duplicate.js`.

That file is a negative test (`negative: {phase: parse, type: SyntaxError}`) for `({ __proto__: null, other: null, '__proto__': null })` — real JS requires a `SyntaxError` for a *duplicate* `__proto__` key when at least two are written as plain `PropertyDefinition: PropertyName: AssignmentExpression` entries (an Annex B legacy rule, `sec-__proto__-property-names-in-object-initializers`). This compiler has no such check. It was reported as passing before this change only because the blanket `IDENT`-only restriction rejected the file's `'__proto__': null` entry for an unrelated reason (any string key at all), coincidentally producing "fails to parse" for the wrong cause. Post-fix, the file parses and compiles cleanly, so the harness correctly reclassifies it as `expected a parse-phase rejection but this compiled` — an honest failure, not a regression in real behavior. Duplicate-`__proto__` detection itself is a real, narrow, un-scoped gap (Annex B semantics, not core language) — noted here rather than fixed, consistent with the project's "note as deferred, never drop silently" rule for gaps found in passing but out of the current change's scope.

The overall bucket movement in the regenerated report reflects the normal cascading-blocker effect, not a failed fix: `expected IDENT, got STRING`/`got NUMBER` both effectively disappeared (35 and 3 residual raw-parser matches respectively, both outside `ObjectLiteral` — confirmed via direct corpus scan), while `expected }, got (` (object literal method shorthand, `{ foo() {} }` — a separate, not-yet-implemented feature) jumped from 823 to 3,633, since files previously blocked earlier by the key restriction now parse further and hit that next, different, still-real blocker instead. Object literal method shorthand is now the largest addressable non-mega-scope bucket remaining after generators/function-expressions/class-expressions/Temporal-Intl, and is the natural next candidate.

- `examples/objects/objects.ts` extended with a string/numeric-literal-key section; built and ran directly, output matches the file's own inline comments exactly.
- Full Test262 corpus re-run (`go run ./tools/conformance`); before/after per-file diff performed via a temporary debug-dump instrumentation (not landed) to isolate the one `__proto__`-duplicate regression documented above from noise.
