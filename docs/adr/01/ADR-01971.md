# ADR-01971: A function reads a let/const declared after it through a shared cell

- **Relations**: Extends [ADR-01014](ADR-01014.md); found while implementing TDD-00230 (P3.3)
- **Date**: 2026-10-30

## Context

Two shadow rows named a read of an identifier that codegen treated as an undefined global:

```ts
function outer(): void {
  const log = (): void => { console.log(msg); };
  const msg = "hi";
  log();
}
```

```ts
function bad(): number {
  const v = pre();
  let base = 5;
  function pre(): number { return base + 1; }
  return v;
}
```

Both failed to compile with `undefined variable`. Node prints `hi` for the first. The second throws `ReferenceError: Cannot access 'base' before initialization` at run time, which a `try` can catch. tsc accepts both. The first is common in real code (a handler that closes over a server declared after it). The second was a documented posture: a clean compile-time error in place of the run-time dead-zone error.

## Investigation

- A closure captures the bindings its body names when it is built (`gatherCaptures`, `codegen/llvm/emit_func.go`). A binding whose declaration has not run yet is not in scope, so the lookup fails and the name falls through to the global path.
- `setForwardClosures`/`forwardClosureSym` already gave a later `const f = () => …` an entry-block heap cell that an earlier closure captures and the declaration then stores into. A null pointer in the cell marks the dead zone, and `emitClosureCall` throws the ReferenceError on it. It was limited to closure-valued declarations read from arrows and function expressions, and only for reads written before the declaration.
- A null sentinel only works for a value that is never null. A number, a boolean, or a `T | null` object can hold any bit pattern, so the dead zone needs a separate flag.
- A nested function declaration is hoisted: letrec (ADR-01014) builds it at its first reference, which can come before a `let` that its body reads but that is written above the function. So for a function declaration the textual order of the read and the binding says nothing.
- The declaration paths are many: scalar, nullable, object literal, array and others. Some store into the forward cell. The object-literal path stored into its own slot, so the flag was never set and the closure threw forever.

## Decision

- **Candidates.** `setForwardClosures` records every `let`/`const` of the body with an initializer or an annotation, not only closure-valued ones. A read inside any nested arrow, function expression or function declaration makes it a candidate, whatever the order. A cell is still made only when a function being built cannot find the name in scope (`forwardClosureSym`), so a binding already declared is captured as before.
- **Cells.** A closure-valued binding keeps the null-sentinel cell. Any other type gets an entry-block cell with the value (seeded with its type's default, `undefined` for `any`), followed by a one-byte flag at the next 8-byte offset. `Symbol.ForwardFlag` holds that offset. Captures copy it into the closure's symbol (the three capture sites). A nullable-scalar `{ i1, T }` binding keeps its own path.
- **Declaration.** `forwardInitialized` sets the flag and returns the binding without `ForwardFlag`, so the declaring scope reads it unchecked from then on. The four paths that store into the forward cell call it. `emitVarDecl` then calls `settleForwardCell` for any other path. That function loads the value the path stored, converts it to the type the closures were built with, stores it into the cell, sets the flag, and rebinds the name to the cell, so later writes reach the closures.
- **Reads.** `emitIdent` checks a binding with `ForwardFlag`. When the flag is clear it throws `ReferenceError: Cannot access 'x' before initialization`, Node's message.

## Implementation notes

- `codegen/llvm/emit_func.go`: `setForwardClosures` candidates, `forwardClosureSym` cells, `forwardInitialized`, `emitForwardCheck`. Comments that described the compile-error posture now describe the cell.
- `codegen/llvm/emit_exprs_vardecl.go`, `codegen/llvm/emit_arrays_core.go`: the declaration sites, and `settleForwardCell`.
- `codegen/llvm/emit_exprs.go`: the read check. `codegen/llvm/emitter.go`: `Symbol.ForwardFlag`. `codegen/llvm/emit_generators.go`: the generator capture site.
- The flag is set when the declaration starts, not after its initializer runs. A closure the initializer itself calls, which reads the binding, sees the type's default instead of throwing. That case was already handled through `varsBeingInitialized`.

## Side effects discovered

- A direct read of a `let` before its declaration in the same scope stays a compile error. tsc rejects it (TS2448), so the strict lane does too.

## Verification

- `TestE2ENestedFunctionCaptureTDZRejected` asserted the old compile error. It is replaced by `TestE2ENestedFunctionCaptureTDZThrows`, which catches the ReferenceError and prints its name and message.
- `TestE2EClosureCapturesLaterBinding` covers number, string, object literal, array, `any`, boolean, a hoisted function declaration, a per-iteration `let` in a loop, writes after capture, and a call in the dead zone. Its output matches Node's.
- New example: `examples/closures/forward_capture.ts`. Its output matches Node's.
- Closure, capture, hoisting, TDZ, letrec, forward and nested E2E suites pass (Mac).
