# TDD-00205: Element-type inference for an untyped empty array literal (`[]`)

- **Status**: Implemented
- **Date**: 2026-09-11

## Context

An untyped empty array literal `[]` has no elements to infer from, so
`inferArrayType` blindly defaults it to `number[]`
(`emit_exprs_types.go:241`, `return ArrayOf(TypeF64)`). The binding's element
type is then fixed at `double` for its whole lifetime, and `arr.push(v)` coerces
each pushed value to it (`emit_arrays_mutate.go:589`, `e.coerce(v, elemTy)`).
When the real element type isn't `number`, the store is invalid IR:

```ts
const a = [];
a.push("hi");   // clang: constant expression type mismatch:
                //        got type 'ptr' but expected 'double'
```

This is a recurring root cause behind the invalid-IR (CLANG_ERROR) backlog
(memory "Invalid-IR backlog histogram"; BACKLOG §4). Concretely it is the
residue of the RegExp A1 sweep (ADR-00885) — the four
`built-ins/RegExp/prototype/exec/S15.10.6.2_A3_T{1,5,6,7}` files all do

```js
var __matched = [];
do { var e = __re.exec(s); if (e !== null) __matched.push(e[0]); ... }
```

where `e[0]` is a string, so `__matched` should be `string[]`. The pattern
(`var x = []` then `x.push(nonNumber)`) is common across Test262 and real code.

It is scoped now because the A1 sweep (ADR-00882–00885) closed the cheap
coerce-at-arg-site families and repeatedly bottomed out on this one item, which
is the single largest remaining invalid-IR contributor that is *not* a
one-line fix. It is the array half of [TDD-00076](TDD-00076.md)'s deferred
Bucket B, and the concrete realization of the `any[]` hole parked in
[TDD-00062](TDD-00062.md) and the union-inside-array case deferred in
[TDD-00043](TDD-00043.md) — see the status index's "What Is NOT Implemented"
note on the empty-array element type.

### Current behavior (measured, macOS arm64)

| Program | Today |
|---|---|
| `const a=[]; a.push(5)` | works (F64 default happens to match) |
| `const a=[]; a.push("hi")` | **invalid IR** |
| `const a=[]; a.push({x:1})` | **invalid IR** |
| `const a=[]; for(…) a.push("x"+i)` | **invalid IR** (loop) |
| `const a=[]; a[0]="x"` | clean compile error already (indexed-assign is `coerceChecked`) |
| `let a=[]; a=[1,2,3]` | works (reassignment retypes) |
| `const a=[]` never pushed | works (element type unobservable) |

Two facts shape the design: the **indexed-assignment** grow path
(`emitArrayIndexAssignGrow`) already rejects a mismatch cleanly rather than
emitting invalid IR, and whole-array **reassignment** already retypes the
binding. Only the `push` (and sibling append: `unshift`/`splice`-insert/`concat`)
path emits invalid IR, because it coerces blindly to the declaration-time
element type.

## Design

The root problem is that the element type is decided at the declaration site
with no information. TypeScript solves the same problem with an *evolving
`any[]`*: `let a = []` starts as an implicit-any array whose element type widens
from each control-flow assignment/push, finalizing when the array is first read.
This compiler is monomorphized and typed-subset, so the analogous move is a
**whole-scope usage pre-pass** that infers the element type before emission.

### Option A (recommended) — usage pre-pass, staged

Mirror the existing `crossTypeWidenedBindings` pre-pass
(`emit_func.go:1556`), which already walks a scope body to classify untyped
scalar bindings by the kinds assigned to them. Add a sibling pass for
array-typed empty-literal bindings that collects **element-contributing
usages** and unifies their types:

- Contributors: `name.push(v…)`, `name.unshift(v…)`, `name[i] = v` (grow),
  `name.splice(i, d, v…)` inserts, and whole-array reassignment `name = expr`
  (already handled, folded in for completeness). The element type of each is
  `inferExprType` of the argument (which already resolves e.g.
  `re.exec(s)[0] → string`).
- Unify:
  - **All contributors one type** → set the binding's `elemTy` to it. Fixes the
    string/object/…-first common case at zero runtime cost, no new
    representation. This is Stage 1 and closes the RegExp exec-loop residue.
  - **No contributor** → keep today's harmless default (the element type is
    unobservable for a never-populated array).
  - **Heterogeneous** (e.g. `number` + `string`) → Stage 2 (below).

Unlike `crossTypeWidenedBindings`, this pass must include **`const`** bindings:
`const a = []` binds the reference but the contents still mutate via `push`, so
the element type must be inferred for const too.

Wiring points: the pass runs where `crossTypeWidenedBindings` already runs
(`emit_func.go:122`/`1859`/`2767`, `emitter.go:2113` for the module scope), its
result feeds a lookup consulted by `inferArrayType` (empty case) and by the
empty-array `emitVarDecl` so the binding's `Symbol.Ty` carries the inferred
`elemTy`.

### Stage 2 — heterogeneous arrays

A genuinely mixed `[]` (`a.push(1); a.push("x")`) has no single element type.
Following the documented `-compat` split (TDD-00075/00076):

- **`-compat=js`**: lower to a **NaN-boxed-element array** (the D1 dynamic
  array, `runtime_dynarr.go`, already used for `JSON.parse` output), so
  `typeof`/`JSON.stringify`/`.map`/spread all follow through the existing D1
  walker.
- **strict**: a clean compile error naming the escape hatches — a fixed-length
  **tuple**, or opt into `-compat=js` — never invalid IR. (The message shape
  already exists for the scalar case, ADR-00651.)

### Stage 0 — safety backstop (cheap, do first regardless)

Independent of inference, change `emitPush`'s `e.coerce(v, elemTy)`
(`emit_arrays_mutate.go:589`) and the sibling append sites to `coerceChecked`,
so a still-mismatched element becomes a clean rejection instead of invalid IR —
the same hardening the A1 sweep applied elsewhere (ADR-00882–00885). This
converts every remaining "push into wrongly-typed array" invalid-IR file into an
honest COMPILE_ERROR even before inference lands, and guards against regressions.

### Options considered and rejected

- **Option B — always box `[]` as a D1 `any[]`.** Uniform and handles
  everything, but pays boxing cost on *every* untyped empty array (including the
  overwhelmingly common homogeneous case) and broadens the D1 representation
  into hot paths. Reserved as the Stage 2 heterogeneous fallback, not the
  default.
- **Option C — infer only from the immediately following statement.** Too
  fragile: misses pushes in loops, later blocks, and conditionals — exactly the
  RegExp exec-loop shape.

## Open questions

- **Closure capture.** `crossTypeWidenedBindings` deliberately does not descend
  into nested function/arrow bodies (each is its own scope). An array declared
  in an outer scope and pushed to *inside* a closure would not see that
  contributor. Acceptable as a documented V1 edge (a clean rejection / F64
  fallback), matching the scalar pass — or worth a captured-binding second
  pass?
- **Append breadth for Stage 1.** Is `push` + indexed-assign + reassignment
  enough contributor coverage to clear the measured backlog, or must
  `unshift`/`splice`-insert/`concat`/spread-into be in Stage 1 rather than a
  follow-up?
- **Read-before-first-push.** TS finalizes an evolving array's type at its first
  *read*. Does any in-scope program read the empty array (e.g. `.length`,
  iteration) *before* the type-determining push in source order, and does the
  monomorphized single-pass emitter need the pre-pass result to be
  order-independent (it is, since the pass sees the whole body first)?
- **Interaction with `-optimize-memory` `@value` flat arrays** (ADR-00706): does
  an inferred-`elemTy` empty array participate in flat-array packing the same as
  an annotated one, or is that orthogonal?
