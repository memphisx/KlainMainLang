# ADR-00732: Five-platform CI matrix, release binaries gated per platform, stamped `--version`, install scripts

- **Relations**: Implements [TDD-00179](../tdd/TDD-00179.md); extends [ADR-00396](ADR-00396.md) (`process.versions`, the hand-typed `klainVersion` this replaces), [ADR-00728](ADR-00728.md) (the Windows CI lane this generalises)
- **Date**: 2026-09-06

## Context

See TDD-00179. In short: one Ubuntu test job and tag-only releases, a `process.versions.klain` stuck at `0.52.0` against `v0.63.0` tags, and no way to install without building.

## Decision

- **`.github/workflows/release.yml`**: a `test` matrix of five lanes (`linux-x64`, `linux-arm64`, `macos-x64`, `macos-arm64`, `windows-x64`; `fail-fast: false`), each ending with a `gate-<platform>` artifact on success; a `release` job that always runs, reads the gates, exits quietly when none passed, otherwise runs `go-semantic-release` (`--allow-no-changes`), cross-compiles a stamped binary for each passed platform (`-trimpath -s -w -X KlainMainLang/codegen/llvm.KlainVersion=<v>`, `CGO_ENABLED=0`) into `dist/`, writes `checksums.txt`, and `gh release upload`s them. The reference lane (`linux-x64`) alone runs `make status-check`; POSIX lanes run `make examples`.
- **Version**: `codegen/llvm/version.go` exports `var KlainVersion = "0.0.0-dev"`; `main.go` gains `--version` (`klainmain <v> <os>/<arch>`); `Makefile` `build` stamps `git describe`, new `dist` target mirrors the release build; `VERSIONING.md` documents where the version lives; the `process.versions` status row and reference prose say so.
- **Installers**: `install.sh` and `install.ps1` at the repo root (README "Install" section with the one-liners); asset naming `klainmain-v<version>-<platform>[.exe]` + `checksums.txt`; `/dist/` ignored.

## Implementation notes

- `tests/process_test.go` reads `llvm.KlainVersion` rather than asserting a literal, so the test passes under any stamp.
- `checksums.txt` lines are `<sha256>  <name>`; MSYS2's `sha256sum` marks binary mode with `*`, which `make dist` strips and both installers tolerate.
- The Windows installer edits only the *user* `Path` (and only when the folder is missing from both the user and the current process PATH).
- `make help` parses `## target:` comments, so the version notes in the Makefile use plain `#`.

## Side effects discovered

- Two Windows-only source files of this delivery had Go's `_windows.go` suffix by accident and were invisible to the Linux build — caught by the Linux lane, renamed to `_win32.go` (ADR-00731). The matrix makes that class of mistake impossible to miss.
- The examples runner (`make examples`) is a POSIX Makefile recipe; the Windows lane skips it. A Windows-runnable examples lane is future work.

## Verification

- Windows 11: `go build` → `klainmain 0.0.0-dev windows/amd64`; `make build` → `klainmain 0.63.0-dirty windows/amd64`; `TestE2EProcessVersion*` pass; `make dist` produced the five binaries and `checksums.txt`.
- `install.sh` in the Linux container against a `file://` base of that `dist/`: installs, prints the version and the PATH hint (exit 0); a missing release exits 1 with the message; a release without the platform exits 2 listing the assets present. `install.ps1` on Windows against the same base: installs to the override directory, adds it to the user PATH, prints the clang reminder (exit 0); the test PATH entry was removed afterwards.
- The workflow itself can only be proven by the first push to `main`; the macOS lanes are the ones to watch (TDD-00179 open question 3). The YAML was reviewed by hand (no `actionlint` on this box).
