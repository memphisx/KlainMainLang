# ADR-01389: Signals and the pool wake on libuv handles

- **Relations**: Implements TDD-00244; Extends ADR-01385
- **Date**: 2026-10-04

## Context

[TDD-00244](../../tdd/TDD-00244.md) Stage 1 maps `signal()` plus a pending
flag to `uv_signal_t`, and the thread pool's wake socketpair to
`uv_async_t`. [ADR-01385](ADR-01385.md) kept both: a handler that set the
flag and woke the wait through `uv_async_send`, and a socketpair whose read
end the pool's fdset hook put in the wait.

## Decision

- **A watched signal is an unref'd `uv_signal_t`** on the thread's loop
  (`loop.c`'s `__kml_loop_signal_start`/`_stop`), as Node's signal handles
  are. Its callback marks the signal (`process.c`'s `__kml_signal_note`)
  and the next pass's dispatch runs the watcher. `uv_signal_start`'s error
  is the native's result, so a refused signal is `-EINVAL`. Stopping
  SIGPIPE re-ignores it. The signal natives are compiled only when used
  (`-DKML_PROC_SIGNALS`), and they link the loop.
- **The pool wakes the loop through the bridge's `uv_async_t`**
  (`__kml_loop_waker`, `__kml_loop_wake`). The socketpair and
  `__kml_pool_fdset_add` are deleted.
- Windows keeps `signal()` and its reactor-port wake until Stage 6.
- **A cross build links a bare `-luv`** for `--sysroot` to resolve.
  `LocateUV` ran the host's pkg-config, which names the host's copy.

- Linux x86-64 (Ubuntu 24.04 container): test-par 3922 tests pass,
