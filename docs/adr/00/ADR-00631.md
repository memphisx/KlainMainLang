# ADR-00631: Overridable EventEmitter methods in a subclass

- **Relations**: `Implements TDD-00157`, `Extends ADR-00303`
- **Date**: 2026-09-02

## Context

`EventEmitter<T>` (TDD-00023) exposed `on`/`once`/`emit`/`off`/
`removeListener`/`removeAllListeners`/`listenerCount`/`eventNames` as
hand-written codegen dispatched by name (emit_call.go), and a class in an
EventEmitter-rooted tree that *declared* any of those names was a clean
compile-time error (emit_classes.go's `registerClasses`). That blocked the
single most common real-world subclass idiom — wrapping `emit` to
log/count, wrapping `on` to lazily attach a source — recorded as the
top-leverage EventEmitter fidelity gap (EventEmitter is the substrate under
streams/`http`/`net`/worker events).

## Investigation

The instance-member dispatch in emit_call.go (~line 465–487) already checks
`info.MethodSigs[mem.Property]` *before* the `info.HasEventEmitter &&
isEventEmitterMethodName(...)` built-in branch — so a real `MethodSig`
already wins at the call site, statically and virtually through the vtable.
The only thing forcing the built-in was the rejection in `registerClasses`
(emit_classes.go:998) preventing the method from *becoming* a `MethodSig`.
The remaining piece was `super.<eeMethod>(...)`: `emitSuperMethodCall`
(emit_classes.go:2769) relies on the `super` scope symbol, which is bound
only for a *registered* base class — a class directly `extends
EventEmitter<T>` has `BaseClass == ""` (the synthetic EventEmitter is never
registered), so `super` is unbound.

## Decision

1. Remove the reserved-name rejection: a `hasEventEmitter` class may declare
   any EventEmitter method name. It then flows through the ordinary
   `MethodSigs`/vtable path and wins at every call site via the existing
   dispatch order. The built-in branch remains the fallback for un-overridden
   methods.

2. In `emitSuperMethodCall`, before the `super` lookup: if the enclosing
   class (`this`'s class) `HasEventEmitter` and the method name is an
   EventEmitter method, route the super call using `this` as receiver —
   to the nearest ancestor that itself overrides the method (found via the
   base's `MethodImplementor` table, which already resolves to the closest
   implementor at/below the base), or, when none does, to the built-in
   `emitEventEmitterCall` against `this`'s hidden listener-map field. This
   makes `super.emit(...)` work in both the direct-extend case (no bound
   `super`) and multi-level overrides (`B extends A extends EventEmitter`,
   both overriding `emit`, has `B.super.emit` reach `A`'s).

Override signature compatibility against the synthetic built-in is not
enforced (matching the erased-`as` stance and TS's own base-declaration-only
checking) — a caveat, not a blocker.

## Implementation notes

- emit_classes.go:998: rejection replaced with an explanatory comment.
- emit_classes.go `emitSuperMethodCall`: new EventEmitter-method branch at
  the top, reusing `classEventEmitterFieldIndex` + `emitEventEmitterCall`
  (the exact IR the non-override instance dispatch emits) and `emitClassCall`
  (forceDirect) for the ancestor-override case.

## Side effects discovered

A general pre-existing bug, surfaced while an override's untyped-arrow
listener argument decoded to garbage: the *class-method* call path
(`emitClassCall`) did not contextually type an untyped arrow/function-
expression argument's parameters from a function-typed parameter's declared
signature — the free-function path already did. Fixed separately in
ADR-00632.
