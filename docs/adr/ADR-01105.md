# ADR-01105: Type syntax as node kinds, converted to annotations in one place

- **Relations**: `Implements TDD-00230` (Phase 1, P1.5); `Extends ADR-01102`
- **Date**: 2026-09-23

## Context

The parser turned type syntax straight into `ast.TypeAnnotation`, the flat
struct code generation reads, and made the model's decisions as it went:
`x is T` became `boolean`, `asserts x` became `void`, `readonly` and `new`
were dropped, a generic function type's parameters were erased to `any`, a
template literal type became `string`, `ns.T` kept only `T`, `T[]` was spelled
into the name string, `null`/`undefined` union members were folded into flags,
and the builtin generics (`Promise<T>`, `Map<K, V>`, …) were matched by name
to fill `ElemType`/`KeyType`. What the source said was gone before any later
phase could look at it. A checker can't narrow on a predicate that was
already erased to `boolean`.

[TDD-00230](../tdd/TDD-00230.md) P1.5 makes type syntax node kinds, kept as
written, with one conversion function producing the existing annotation for
codegen until phase 2 replaces `resolveType`.

## Investigation

- **Entry points.** All type parsing goes through `parseTypeAnnotation`
  (`parser/parser_types.go`, about 1,100 lines). JSDoc types reach it too:
  `parser/jsdoc_types.go` normalises Closure syntax to TypeScript and parses
  the result.
- **The parser's decisions** were spread over `parseTypeAnnotation`,
  `parseUnionType`, `parseTypeAnnotationIntersection` and
  `parseTypeAnnotationAtom`, with `eraseTypeParamsIn` applied to method
  signatures and generic function types. Rejections of shapes the annotation
  model cannot hold (an empty tuple, a non-`string`/`number` index key, an
  index signature with named members, two index or call signatures, a call
  signature with other members) were raised mid-parse.
- **One place depends on a rejection to choose a parse.** `(T) => …` is tried
  as a function type first. If its return type fails, a single unnamed
  parameter is re-read as a parenthesised type and the `=>` is left to the
  enclosing arrow function. `const f = (): (Foo[]) => []` relies on this: the
  empty tuple `[]` is rejected, so `(Foo[])` is the return type and `[]` is the
  body. The rejection is part of the grammar decision there.
- **Two `[]` spellings.** `T[]` directly on a name became the name string
  `"T[]"`. A `[]` after anything else (a parenthesised, literal, object, tuple,
  `typeof`, template or generic type) became `ElemType` wrapping. Code
  generation reads both, so the conversion has to reproduce which one applies.
- **Who inspects annotations generically.** No `reflect.DeepEqual`, `%v`
  printing or serialisation of annotations exists in codegen, the resolver or
  the parser. Three reflective walkers in codegen descend into every exported
  field of the AST, annotations included; all three skip unexported fields.
- **The walker generator** read only `ast/nodes.go`, knew only `Expression`,
  `Statement` and `Node` as child interfaces, and rejected embedded fields.

## Decision

- **New node kinds** in `ast/type_nodes.go`, named after TypeScript's:
  `KeywordType`, `TypeReference` (qualifier segments, type arguments),
  `ArrayType`, `TupleType` with `NamedTupleMember`/`OptionalType`/`RestType`
  elements, `UnionType`, `IntersectionType`, `ParenthesizedType`,
  `FunctionType` and `ConstructorType` (type parameters, named, optional and
  rest parameters), `TypeLiteral` with `PropertySignature`,
  `MethodSignature`, `CallSignature`, `ConstructSignature` and
  `IndexSignature` members, `MappedType`, `ConditionalType`, `InferType`,
  `TypeOperator` (`keyof`, `readonly`), `IndexedAccessType`, `TypeQuery`,
  `LiteralType`, `TemplateLiteralType`, and `TypePredicate`
  (`x is T`, `asserts x [is T]`, `asserts this [is T]`). Two interfaces
  embed `Node`: `TypeNode` and `TypeMember`.
- **Every node records its location** in a `Range` field: the first token's
  line and column (also returned by `GetPos`) and the byte range of its source
  text.
- **The parser builds only nodes.** `parseType` and the functions under it
  know the grammar and nothing about the annotation model. There is no builtin
  type name in the parser: `Promise<A, B>` and `Map<K>` parse like any other
  generic.
- **One conversion, `ast.TypeAnnotationOf(node, source)`** in
  `ast/type_convert.go`, makes every decision listed in Context and raises
  every rejection, with the same messages and positions the parser used to
  report. The positions come from the nodes; a `TypeReference` keeps the
  position of each comma between its type arguments for the arity messages.
  Its deletion is a phase 2 exit criterion.
- **`parseTypeAnnotation` is a wrapper**: parse a node, convert it. The about
  40 AST fields holding annotations, and every reader of them, are unchanged.
- **Each annotation points back at its node** (`TypeAnnotation.TypeNode()`),
  including the annotations of nested types. The field is unexported:
  `TypeAnnotation` stays excluded from the generated traversal, and the
  reflective walkers still in codegen (function-name inference, the stack
  allocation `this`-escape scan, the FinalizationRegistry binder scan) skip
  unexported fields, so no existing walk reaches the type nodes. The last of
  these counts any `Name` field as a binding and would otherwise have read
  type-syntax names as bindings.
- **The `(T) =>` choice** validates the tentative return type through the
  conversion, so a return type the model rejects still makes the parentheses a
  grouping, exactly as before.
- **Labelled tuple elements** (`[min: number, max: number]`) are accepted,
  closing that part of BACKLOG item 1b. The label documents the position; the
  tuple is the same value as without labels, as in TypeScript. An optional
  (`[a?: T]`, `[T?]`) or rest (`[...T[]]`) element has no storage in the
  fixed-shape tuple model and is rejected by the conversion.
- **The walker generator** reads `nodes.go` and `type_nodes.go`, and treats any
  interface embedding `Node` as a child type. `ForEachChild` and
  `RewriteChildren` cover the type nodes.
- **Answer to TDD-00230's open question** ("which AST structs change shape in
  P1.5, and when"): none change shape in P1.5. Declarations keep their
  annotation fields, and interface bodies keep being read member by member
  into `Fields`/`Methods`. Each reader moves to the nodes in phase 2 when the
  checker takes over the decider it feeds, and the annotation fields go with
  the conversion.

## Implementation notes

- **New:** `ast/type_nodes.go`, `ast/type_convert.go`,
  `parser/type_nodes_test.go`.
- **Changed:**
  - `parser/parser_types.go`: the type grammar rewritten to build nodes
    (`parseType`, `parseUnionType`, `parseIntersectionType`, `parseTypeAtom`,
    `parseTypeReference`, `parseParenOrFunctionType`, `parseObjectType`,
    `parseTupleElement`, `parseSignatureTail`, `parseIndexSignatureNode`,
    `parseTypeParameterNodes`). `parseIndexSignature` and
    `parseObjectTypeSignatureTail` remain as converting wrappers for
    `parseInterfaceDecl`.
  - `eraseTypeParamsIn` moved to `ast.EraseTypeParams`, used by the
    conversion, interface method signatures and generic class methods
    (`parser/parser_classes.go`).
  - `ast/nodes.go`: the annotation's back-pointer and its `TypeNode()`
    accessor.
  - `ast/gen/main.go`, `ast/walk_generated.go`, `ast/walk_test.go`: the
    reflection-oracle test now also checks every type tree reachable from an
    annotation.
- **Union members.** The conversion keeps the old folding exactly: the first
  member's own `Nullable`/`Undefined` seed the result, a single remaining member
  is itself the result (with the folded flags), and several are headed by a
  distinct copy of the first so no member is its own list entry.
- **Declaration type-parameter lists** (`function f<T extends C>`, classes,
  interfaces, aliases) still go through `parseTypeParamList`, which converts
  each constraint as it is read. The constraints' annotations point at their
  nodes.

## Side effects discovered

- **Accepted input that TypeScript rejects is now rejected:**
  - `<T>string` (a type-parameter list followed by something other than a
    function type) was accepted and meant `string`. It is now "expected a
    function type after a type parameter list". The same holds after
    `new (…)`, which now requires the `=>` of a constructor type.
  - A type predicate whose subject is not a parameter name
    (`string[] is T`) is now "expected a parameter name before 'is'".
- **Changed wording on malformed input:** an unclosed builtin generic reports
  its name with `<T>` like every other generic (`Map<string, number` without
  `>`: "expected '>' to close Map<T>" instead of "Map<K,V>").
- **Error order in one type:** a rejection now comes after the whole
  annotation has parsed, so a later syntax error in the same annotation is
  reported first. No file in the equivalence corpus has both.
- **A P1.1 leftover:** the lexer fuzz test was still named `FuzzTokenize`,
  after the function P1.1 deleted. It is `FuzzScan` now, in `make fuzz` too.
- **Still open (BACKLOG item 1b):** `<T,>(x: T) => x` is read as a type
  assertion, not a generic arrow function; `new classes[0]()` needs classes as
  values first.

## Verification

All on macOS arm64 (M4):

- **Parser-level equivalence against the P1.6 parser.** Every file of the
  corpus (examples, tools, apps, tests, the full Test262 tree and every source
  string embedded in the Go tests: 59,519 files) was parsed by both builds and
  a reflective dump of the AST's exported fields compared, annotations
  included, together with the parse error text. No difference.
  A targeted set of 1,107 programs puts 123 type forms (valid and invalid) in
  eight TypeScript positions and in JSDoc. The only differences are the
  `<T>string` and unclosed-`Map` cases listed above.
- `go test ./ast ./parser`: node shapes for every kind, predicate forms,
  ranges and back-pointers, and each conversion rejection with its position.
  The reflection oracle checks the generated traversal on every type tree in
  the corpus.
- `tests/tuple_test.go`: labelled tuples print what Node 26.10.0 prints; the
  optional and rest rejections. `examples/tuples/tuples.ts` gains a labelled
  section, output identical to Node's.
- `make examples`: 358 passed, 0 failed.
- `make test-par`: passes apart from the four known macOS `-mm=gc`
  thread-local-root failures in `tests/task_reclaim_gc_tls_test.go`.
