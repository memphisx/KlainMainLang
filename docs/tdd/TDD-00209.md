# TDD-00209: `--no-any` — a strict-lane flag banning the `any`/`unknown` escape hatch

- **Status**: Partially Implemented

## Context

The default `strict` lane is really *TS-faithful*: it accepts `any`/`unknown`
(explicit annotations, evolving-any from a `null`-initialized binding, `any[]`,
boxed `any` fields). Some deployments — CLI tools, microservices — want a
stronger guarantee: **no dynamic escape hatch at all**, so the produced binary is
provably fully static (no NaN-boxing, no runtime type tags, no dynamic dispatch),
and any reliance on `any` is a compile error the developer must resolve.

This is a separate opt-in **flag**, not a new compat mode (the mode axis stays
`strict`/`js`). It composes on top of `strict`. Under `-compat=js` it is
meaningless (js is best-effort untyped) and is ignored with a warning.

## Design

`--no-any`: when set (and not under `-compat=js`), every use of the `any`/
`unknown` dynamic type is a clean compile error.

**Stage 1 — explicit annotations (this stage).** A post-parse validation pass
walks every type annotation in the program (variable/parameter/field/return
types, `as` casts, generic arguments, array/map/tuple/function-type element
types, union/intersection members) and rejects a bare `any`/`unknown`
(`Name == "any" || "unknown"`), with the source position. A *constrained* union
(`string | number`) is NOT `any` — it stays allowed (it is statically member-set
checked). Recurses through `ElemType`/`KeyType`/`TypeArgs`/`FuncParams`/
`FuncRetType`/`Fields`/`UnionMembers`/`TupleElems`/`IntersectionMembers`.

**Stage 1 — evolving-any.** The evolving-any widening (ADR-00923/00924: an
unannotated `let x = null; x = 5`, `#field = null; ??=`) is disabled under
`--no-any`, so such a binding falls back to the ordinary strict cross-type
rejection (which already guides to `: any` / `-compat=js`). No new reject path
needed — just gate the widening.

**Stage 2 (follow-up) — value-level implicit any.** A builtin that yields `any`
without an annotation (`JSON.parse`, `Reflect.get`, …) is not caught by the
annotation walk. Flagging value-level `any` production needs a codegen-site check
and is a documented follow-up; Stage 1 catches all developer-written `any`.

Under `-compat=js`: the flag is ignored, and the compiler prints one warning to
stderr (`--no-any is ignored under -compat=js`).

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `any`/`unknown` type resolution | Done | `ResolveTypeName`, TypeAnnotation AST |
| Evolving-any widening | Done | ADR-00923 (locals) / ADR-00924 (fields) — gated here |
| compat-mode plumbing | Done | `SetCompatMode` / `compatJS` |
