# TDD-00160: WebSocket binary frames — binary `.send()` and byte-exact binary receive

- **Status**: Implemented
- **Date**: 2026-09-02

## Context

TDD-00039 built the WebSocket stack (client `new WebSocket(url)`, the
server-side per-connection frame loop, `wss://` on both sides via TDD-00158)
against a deliberate text-only narrowing. The remaining WebSocket caveats on
[NETWORKING.md](../status/NETWORKING.md) are all consequences of that one
choice:

- *"Neither side supports binary `.send()` (`ArrayBuffer` payloads)."*
- Binary receive is lossy: a decoded binary frame (opcode 2) is copied into a
  `strlen`-terminated string and delivered through `WSMessageEventType.data`,
  so any payload with an embedded `NUL` truncates through ordinary string
  operations — the exact narrowing `WSMessageEventType`'s own doc comment
  flags as *"a real, documented V1 narrowing… a binary-safe accessor
  (mirroring `req.bodyBytes()`) is a real, undesigned follow-on."*

Binary frames are the most commonly-hit WebSocket gap (protocol buffers,
MessagePack, image/audio chunks, any framed binary protocol), and the wss
arc just finished makes this the natural next piece. Both the send and the
receive half are in scope — send alone would leave the receive truncation
bug live, and closing only half a feature is not closing it.

## Design

Two independent halves; the send half has no type-model fork, the receive
half does.

### Send: `.send(data: string | ArrayBuffer | Uint8Array)`

The frame codec (`__kml_ws_frame_encode`) already takes the opcode as an
argument — the send sites hardcode `i32 1` (text) and derive length from
`strlen`. Overload on the argument's compile-time type via `inferExprType`:

- **string** → unchanged: opcode 1, length from `strlen`.
- **`ArrayBuffer`** (`IsArrayBuffer`) → opcode 2; the byte pointer and length
  come from the buffer's `{ i64 size, ptr data }` header (`emit_arraybuffer.go`
  layout), not `strlen` — binary-safe past embedded `NUL`s.
- **`Uint8Array`/typed array** (`IsTypedArray`) → opcode 2; pointer + byte
  length from the view. (Scope V1 to `Uint8Array`; other element widths reject
  cleanly, matching the codebase's usual typed-array narrowing.)
- Any other type → a clean compile-time rejection naming the accepted set.

This applies symmetrically to both send sites, preserving each side's masking
rule: server→client unmasked (`emitWSConnectionSend`), client→server masked
with the existing 4-random-byte key (`emitWSClientSend`). The mask bit and key
are orthogonal to the opcode, so the only change per site is
opcode-and-length selection plus reading bytes from a buffer header instead of
`strlen`.

### Receive: byte-exact binary payloads

The frame loop already decodes opcode 2 (`isBinary` at emit_websocket.go:478)
and merges it into the `isData` dispatch — the decoded payload pointer and
length are already in hand at `dispatchL`; today they are copied into a
`strlen`-terminated string and dropped into `data`. The design question is
only how to surface a binary payload to user code.

**The browser-faithful shape is `ev.data: string | ArrayBuffer`** (discriminated
by `binaryType`). This is **not currently expressible**: union members are
restricted to number/string/boolean, object/interface/class, and
ReadableStream (`emit_dynamic.go:138`) — `ArrayBuffer` is not an allowed union
member, and `typeof anArrayBuffer === "object"` collides with object members
in the `typeof`-narrower. A union-typed `data` field therefore requires
extending the type system's union model (member tagging + `instanceof`/
`typeof` narrowing for `ArrayBuffer`) — a self-contained type-system arc, not
a WebSocket one.

**Chosen design (matches the in-repo `req.body` / `req.bodyBytes()` idiom the
`WSMessageEventType` doc already names):** extend `WSMessageEventType` to

```
{ data: ptr /* string view */, isBinary: bool, __kml_ws_msg_bytes: ptr, __kml_ws_msg_len: i64 }
```

- **`ev.data`** — unchanged string view (text frames: the payload; binary
  frames: the same `strlen`-view, still truncating at a `NUL` — but no longer
  the *only* way to read the payload).
- **`ev.isBinary`** — `true` for opcode 2, `false` for opcode 1. This is the
  Node `ws` `('message', (data, isBinary) => …)` discriminant, exposed as a
  field so the browser-style `onmessage = ev => …` single-callback ABI is kept.
- **`ev.dataBytes(): ArrayBuffer`** — a method mirroring `req.bodyBytes()`:
  wraps the already-copied payload bytes (hidden `__kml_ws_msg_*` fields) in an
  `ArrayBuffer` header, byte-exact, no `NUL` truncation. Available for both
  frame kinds (a text frame's raw UTF-8 bytes are legitimately readable this
  way too, matching `req.body`/`req.bodyBytes()` coexisting).

This keeps observable semantics faithful — every byte of a binary frame is
recoverable, in order, via a real `ArrayBuffer` — and diverges from the
browser only in the *typing* of `data` (a string view rather than a
`string | ArrayBuffer` union), which is recorded below as future type-system
work, not a behavioral divergence.

Both `WSConnectionType` (server) and `WebSocketClientType` (client) share
`WSMessageEventType`, so a single type change covers both receive paths;
`buildEmptyWSMessageEvent` (the onopen/onclose/onerror filler) sets
`isBinary=false`, empty bytes.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `__kml_ws_frame_encode` opcode arg | Built | Already takes opcode + mask; send sites just hardcode 1 |
| Opcode-2 decode + `isData` dispatch | Built | emit_websocket.go:476–481 already routes binary to `dispatchL` |
| ArrayBuffer `{i64 size, ptr}` header + wrap helper | Built | emit_arraybuffer.go; `req.bodyBytes()` is the exact wrap precedent |
| `inferExprType` for ArrayBuffer/TypedArray args | Built | `IsArrayBuffer`/`IsTypedArray` |
| Union-typed `data: string \| ArrayBuffer` | Missing | Deferred to a type-system arc (union ArrayBuffer member) — not this TDD |

## Open questions

- Whether to accept `Buffer`/`DataView` send arguments in V1 or only
  `ArrayBuffer`/`Uint8Array`. Leaning: `ArrayBuffer` + `Uint8Array` now, others
  as a clean rejection, since those two cover the overwhelming majority of
  real binary-send call sites.
