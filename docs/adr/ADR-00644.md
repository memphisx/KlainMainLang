# ADR-00644: Decorators Stage 4 — class decorators (observe-only; replacement refused)

- **Relations**: `Implements TDD-00161` (Stage 4a), `Extends ADR-00643`
- **Date**: 2026-09-02

## Context

TDD-00161 Stage 4: class decorators — `@dec class C {}`, where the decorator
receives the class constructor. The common shape is registration
(`@Component`/`@Injectable`/`@Controller`/`@Entity`): observe the class, record
it, return nothing. A class decorator may also *return a replacement
constructor*, which every `new C()` and static reference must observe — deeply
invasive against the static-class model (every construction site), so that is
Stage 4b. This ADR ships 4a: observe-only class decorators run faithfully; a
returned replacement is refused at runtime (loudly), never silently dropped.

## Decision

- **Accept** class decorators on a non-generic class (`emitClassDecl` no longer
  rejects them; a generic class stays a clean rejection — its per-instantiation
  monomorphization has no single decorator target).
- **Apply** (`emitClassDecoratorApplications`, after member decorators, matching
  TS's `__decorate` ordering; bottom-up among multiple): `dec(target)`, where the
  per-class decorator target stands in for the constructor (the same object member
  decorators receive, and the one design metadata lives on).
- **Refuse replacement**: if a class decorator's return is statically dynamic
  (`any`), a runtime check throws when the returned value is not `undefined` —
  "a class decorator that returns a replacement constructor is not supported
  yet". A statically-void return needs no check. Observe-only decorators (the
  registration majority) are unaffected.
- **Metadata tie-in** (Stage 3): with `-emit-decorator-metadata`, a decorated
  class emits `design:paramtypes` for its constructor under the constructor
  sentinel key — the dependency-injection pattern (`@Injectable` reading its
  constructor's parameter types).

## Implementation notes

- Ordering: member decorators (property/parameter/method) run first, then class
  decorators — so a class decorator sees the fully member-decorated class.
- The per-class target is a stable dynamic object, so a registration decorator
  keying a registry by the class's identity works within the program.

## Side effects discovered

- **Oracle impact is flat**, and the reason is informative: Stages 1-4 dropped
  the TypeScript-oracle's `@`-blocker from 181 false-rejects to 11 (the `@`
  lexer wall is gone), but the *net* false-reject count barely moved because
  decorated corpus files then hit independent downstream gaps — most notably
  **factory decorators** (`@dec(...)`, ~19 cases), which call a returned value
  and hit the bare-function-as-value ABI gap. Factory decorators, not the
  class-vs-method distinction, are the next real oracle lever; they span all
  placements and are tracked under TDD-00161.
- Class-decorator *replacement* (Stage 4b) is deferred — it requires routing
  every construction/static-reference site through a runtime constructor value.

## Verification

- `tests/decorators_test.go`: observe-only class decorator (class unchanged);
  bottom-up ordering with a member decorator (member first, then classes);
  a replacement-returning class decorator compiles (accept); a decorated class's
  constructor `design:paramtypes` read by the decorator under
  `-emit-decorator-metadata`.
- `examples/decorators/class_decorators.ts` runs (a `@table`/`@auditable`
  registration registry) under default flags.
- `go vet`, full `make test-par`, class/inheritance/generic/decorator suites,
  node oracle, `status-check`/`reference-check` pass. Mac (Apple Silicon).
