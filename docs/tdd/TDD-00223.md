# TDD-00223: One event loop — every wait parks or runs the loop

- **Status**: Implemented
- **Date**: 2026-09-20

## Context

In Node there is exactly one way to wait: the current continuation is suspended and the event loop runs — *all* of it (timers, sockets, servers, child processes, fs, workers, microtasks) — until the awaited thing settles. This runtime has one real event loop (`__kml_event_loop_run`, `runtime_http.go`) and, beside it, several private drive loops that each service a *subset* of sources and block everything else while they spin:

| Drive | Where | Services | Starves |
|---|---|---|---|
| `__kml_task_await_ready` `toploop` | `runtime_task.go` — an `await` with no current task and no connection fiber | microtasks, tasks, timers (+ `usleep(200)`) | every fd: sockets, servers, child stdio, workers, fs |
| `__kml_await_fetch` / `_headers` `busyspin` | `runtime_fetch.go` — same situation, awaiting a fetch | libcurl only, at 100 % CPU | everything else, timers included |
| the inline no-task drive | `emit_async.go` `emitAwaitTaskPromise` (programs with no may-suspend fn) | microtasks, timers, libcurl | every fd |
| `__kml_fetch_drive_run` | `emit_promise_then.go` — `.then/.catch/.finally` on a fetch promise | a microtask that drives the fetch synchronously | everything, for the whole transfer |
| `__kml_task_run_all` | end of `main` for a task-only program | tasks + libcurl, spinning | (nothing else exists, but it burns a core for the duration of every transfer) |

Measured against a 1 s upstream with a 50 ms `setInterval` counting alongside (Node counts ~20):

| Shape | Ticks |
|---|---|
| `async function` declaration awaiting `fetch` (a coroutine task) | 20 |
| `async function` awaiting a timer promise | 20 |
| top-level `await fetch(u)` | **0** |
| `async () => { await fetch(u) }` | **0** |
| `async` method awaiting `fetch` | **0** |
| `fetch(u).then(…)` with a timer alive | **segfault** |
| top-level `await` on a timer promise while a child writes stdout | the child's data is not delivered until after the await |
| `fetch()` of the program's own `http.createServer` from a callback | deadlock (the server is never accepted) |

The coroutine-task machinery (TDD-00083) is correct; it is applied only to top-level `async function` *declarations* the classifier recognizes as suspending. Everything else that awaits takes a private drive.

## Design

The rule: **a wait either parks a coroutine or, on the main stack at module top level, runs the real event loop until the awaited thing settles. No other form of waiting exists.**

### 1. Top-level `await` runs the event loop

An `await` reached with no current task and no connection fiber is, by construction (§2), module top-level code on the main stack. Nothing else is suspended beneath it, so running the real loop from there is *semantically identical* to Node suspending the module: the module's continuation is the only thing waiting, and every callback the loop runs sees the same world it would in Node.

`__kml_event_loop_run` gains an until-condition: two thread-local `ptr`-to-`i64` globals (`@__kml_loop_until_a/_b`; the loop returns when either target is non-zero — a promise's state word, a fetch's `done` and `headersDone` words). It is checked once per iteration after the microtask/scheduler drain. `__kml_loop_run_until(a, b)` sets them, runs the loop, clears them. The three main-stack drives (`toploop`, both `busyspin`s, the inline no-task drive) become calls to it.

If the loop finds nothing left alive while the condition is unmet, it returns and the await site does what Node does with an unsettled top-level await: a warning on stderr and **exit code 13**.

This is not a nested event loop in the sense that produces LIFO completion order: it is only ever entered from the main stack at top level, where there is nothing to be ordered against. It cannot be entered from a callback, because a callback that awaits is a coroutine (§2).

### 2. Every async callable that awaits is a coroutine

Rejected: extending the declaration-only specialised path (args bundle, `void(ptr)` entry, call-site spawn) to arrows, function expressions and methods — each has its own calling convention (closure env, `this`, vtable slots, builtin-callback thunks), and every call site would need a spawn variant.

Chosen: **wrap at the callee.** An async arrow / function expression / method / unclassified declaration whose body contains an `await` is emitted as two functions with the *same* LLVM signature:

- `inner` — today's body, unchanged. On a coroutine every `await` inside it parks through the existing task paths (`__kml_task_await_ready` `ontask`, `__kml_await_fetch`'s task-yield), so by the time it returns, its promise is settled.
- `outer` — the symbol everything already calls. It allocates the task promise `P`, copies its own LLVM parameters verbatim into a heap bundle, spawns a coroutine on a trampoline that reloads them and calls `inner`, adopts `inner`'s settled promise into `P` (value, or re-throw of the rejection reason so the task trampoline rejects `P`), and returns `P` — at the callee's first park, exactly when a JS async function returns its promise.

Because `outer` has `inner`'s signature, closures, method dispatch, and callbacks handed to builtins work unchanged. The bundle is type-agnostic (it stores LLVM values, not language values). Parameters that are pointers into the caller's frame (array header slots) are re-homed in the bundle the way the declaration path already does.

`hasMaySuspend` becomes "the program contains an `await`, a `for await`, or a fetch-promise reaction" — decided by a pre-pass, so the task-aware await paths are always the ones emitted.

### 3. A fetch promise is settled by the loop

`.then/.catch/.finally` on a fetch promise no longer queues a microtask that drives the transfer. The bridge runs as a spawned coroutine: its headers wait parks on the fetch (the scheduler already resumes a task whose fetch reached `headersDone`/`done`), the loop keeps running, and the bridge promise settles when libcurl delivers. The segfault is root-caused and fixed as part of this, not assumed gone.

### 4. One loop at the end of `main`

`__kml_task_run_all` and `__kml_timer_drain` as end-of-main drives are replaced by `__kml_event_loop_run` whenever the program can wait on anything beyond plain timers. A task-only program then sleeps in `select()` on libcurl's fds instead of spinning.

### 5. Child-process exit is an event, not a poll

Node: `'exit'` fires when the process ends, whatever its stdio is doing; `'close'` fires once the process has ended **and** its stdio streams have closed. Today `__kml_cp_finalize` calls `waitpid(WNOHANG)` only after both pipes hit EOF and the loop re-enters `select()` with a zero timeout until it succeeds (32 198 iterations in 2 s for a child that closes stdio and sleeps), and `'exit'` cannot precede stdio EOF.

- The loop is *woken* by child exit: POSIX installs a `SIGCHLD` handler that writes to the loop's wake channel (no lost-wakeup window, unlike relying on `EINTR`); Windows registers a wait on the process handle (`RegisterWaitForSingleObject`) whose callback posts a packet to the reactor's port — libuv's mechanism on each platform.
- Each iteration reaps every live child with `waitpid(WNOHANG)`. A reaped child records its status and fires `'exit'` at once; `'close'` fires when it is reaped and both stdio pipes are at EOF, in either order. The zero-timeout force is deleted; a child that closed its stdio and is still running costs nothing until it exits.
