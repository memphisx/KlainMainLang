# TDD-00113: Generic type-parameter constraints (`<T extends X>`)

- **Status**: Implemented
- **Date**: 2026-08-25
- **Notes**: Parse + store `extends X` per type parameter; enforce the bound at each instantiation via `matchExtends` (structural, width subtyping) with a clean error on violation. Member access on a constrained `T` rides monomorphization (no special support). Enforced on generic functions and classes; type-alias constraints parsed but not enforced. Depends on [TDD-00069](TDD-00069.md) object type args for the common object-shape case

## Context

Type-parameter constraints were a hard parse error (`type parameter constraints
on … are not yet supported`), so any real TypeScript using `<T extends X>` — a
very common idiom — failed to compile. This adds them. Their primary use is
constraining `T` to an object shape (`<T extends { id: number }>`), which is only
meaningful now that object type arguments exist ([TDD-00069](TDD-00069.md),
delivered alongside).

## Design

Because generics **monomorphize**, member access on a `T`-typed value already
resolves per-instantiation once `T` binds to a concrete type (object type args,
TDD-00069) — the generic body is emitted against the real concrete shape, not
type-checked once with `T` opaque. So a constraint's job here is narrower than in
a classic checker:

1. **Accept the syntax** — parse `T extends <TypeAnnotation>` and carry it on the
   declaration.
2. **Enforce the bound** — at each instantiation, the concrete type argument must
   structurally satisfy the constraint; otherwise a clean compile error.

Member-access-through-the-constraint needs no special support: it falls out of
monomorphization.

### Enforcement

Reuse `matchExtends` (`emit_conditional_types.go`), the structural-subtype test
conditional types already use — width subtyping, so an object with **extra**
fields satisfies a smaller constraint shape (`{ id, name }` satisfies
`{ id }`). At each generic instantiation site (function call inference; class
`new C<…>()`), after `subs` is built, `checkTypeParamConstraints` runs
`matchExtends(concrete, constraintAnnotation, {})` for every constrained
parameter and errors on failure, naming the parameter and constraint (demangled
via `inspectClassName`).

### Plumbing

- AST: a `TypeParamConstraints []*TypeAnnotation` slice (positionally aligned
  with `TypeParams`, nil = unconstrained) on `FunctionDeclaration`,
  `InterfaceDeclaration`, `ClassDeclaration`, `TypeAliasDeclaration`.
- Parser: `parseTypeParamList` now also parses the `extends` clause per parameter
  and returns the constraints alongside the names.
- Resolver: the rename pass rewrites each constraint annotation (with the type
  parameters bound in scope, so a constraint referencing a sibling parameter
  stays bound while a reference to a named type is per-file renamed).
- Codegen: `checkTypeParamConstraints` at the function-call and class-`new`
  instantiation sites.

### Scope (V1)

- **In:** constraints on generic functions and generic classes, enforced;
  constraint may name an interface/class/object type or a scalar; member access
  on a constrained `T` (via monomorphization).
- **Out / unchanged:** constraints on type aliases are parsed and stored but not
  enforced (aliases are expanded, not instantiated); a constraint referencing the
  *same* parameter list positionally (`<T, U extends T>`) resolves structurally
  but isn't specially validated; no default type parameters (`<T = X>`).
