# ADR-00172: Generator function suspend/resume codegen (construction, `yield`, `.next()`)

- **Relations**: Implements [TDD-00061](../tdd/TDD-00061.md); extends [ADR-00171](ADR-00171.md)'s front-end
- **Date**: 2026-08-12

## Context

[ADR-00171](ADR-00171.md) shipped `function*`/`yield` as real, parsed AST, cleanly rejected by codegen. This ADR picks up the codegen itself: TDD-00061's central finding — that this compiler's existing `ucontext.h`-based fiber primitive (built for `http.listen`/`await fetch(...)`, TDD-00006 Part 2) is directly reusable as the suspend/resume mechanism — is confirmed correct by direct implementation and testing, not just design-time analysis.

## Decision

A generator instance is a heap struct (`GeneratorType`, `types.go`) carrying its own `ucontext_t`/stack (mirroring `runtime_http.go`'s exact connection-fiber shape and constants — same `ucontextLayout()`, same `fiberStackBytes`), a `callerCtx` slot (rewritten before every `.next()` call, unlike a connection fiber's fixed scheduler swap-back target), `started`/`done` flags, `yielded`/`sent` value slots, and its own declared parameters as trailing fields — reusing `ObjectType`'s struct-layout machinery (`StructIR`/`StructSize`/`FieldIndex`) purely for that, not `IsObject` itself (same reasoning `IsEventEmitter` already established).

- **Construction** (`gen(args)`, `emitGeneratorConstruction`) mallocs the struct + its own ctx/stack, `getcontext`+`makecontext` (pointed at the generator's own dedicated compiled body function), stores the call's arguments, and returns the struct pointer — the body never runs until the first `.next()`.
- **The generator body's own entry** (`emitGeneratorFunctionDecl`) is a zero-argument LLVM function (mirroring `http.listen`'s `@__kml_listen_dispatch` entry point, which also takes none): it reads a new global handoff slot (`@__kml_gen_pending_obj`) exactly once, at entry, to learn its own instance pointer — every later resume picks up mid-function with that pointer still live as an ordinary local on the generator's own never-torn-down fiber stack, never re-reading the global. A dedicated emission path, not a refactor of `emitFunctionDeclAs`/`emitClosureFunc` — same reasoning [ADR-00063](ADR-00063.md)'s `emitClassMember` already established for a differing calling convention.
- **`yield expr`**/**a `return`/fall-through exit** (`emitYieldExpression`/`emitGeneratorReturn`, sharing `emitGeneratorSwapToCaller`) store the value and a `done` flag, then `swapcontext(ownCtx, callerCtx)` — no `ret <value>` in the ordinary sense at all; `yield` continues afterward (reading `sent` back as its own expression value once resumed), `return`/fall-through never resumes (its trailing `ret void` is unreachable in practice, a well-formedness terminator only).
- **`.next(value)`** (`emitGeneratorNext`) checks `done` first (a no-op on an already-finished generator, matching real JS), else allocas a fresh local `ucontext_t` as this call's own save point, writes it into the generator's `callerCtx`, and swaps in.
- **GC mode**: `.next()`'s own swap repoints `GC_stackbottom` around the swap, mirroring `runtime_http.go`'s identical connection-fiber launch/resume pattern exactly — no GC bookkeeping inside the generator body's own `yield`/`return` swap at all, matching `emit_http.go`'s existing fiber-yield precedent (the *resumer* always owns this, not the yielding side, since a fiber that runs to completion in one shot has no swap of its own to hang a restore off of).

V1 scope narrowed further than TDD-00061's own design during implementation: an explicit return-type annotation is required (no yield-based T inference), a plain non-destructured parameter list, and a non-array element/parameter type (no aggregate-typed zero-value machinery built yet — `emitScalarZero`'s own existing scope). `yield*`, `.throw()`/`.return()`, generator methods, async generators, and nested generator declarations remain deferred exactly as TDD-00061 scoped.

## Investigation / bugs found during implementation

Two real, confirmed-by-direct-testing bugs, both fixed before this shipped — not found by inspection alone:

1. **Missing pending-object handoff store**: the very first end-to-end test (construct + one `.next()`) segfaulted inside the generator body's own entry — `emitGeneratorConstruction` set up the fiber correctly but never actually *wrote* the instance pointer into `@__kml_gen_pending_obj` before the first swap, so the body's own entry read a permanently-null global. Fixed by writing it unconditionally in `emitGeneratorNext`, right before every swap (harmless on every resume after the first, since only the generator's own first-ever entry reads it).
2. **`e.currentGenerator` not reset for nested closures — a real, confirmed memory-corruption bug, not a theoretical gap**: an arrow function's own plain `return n;`, declared *inside* a generator's own body, was silently routed through the *enclosing* generator's own suspend-and-swap machinery, because `emitClosureFunc`/`emitFunctionDeclAs`/`emitFunctionExpression` never saved/reset `e.currentGenerator` the way they already do for `e.breakStack`/`e.continueStack`/`e.namedLabelStack` (ADR-00168's own identical fix, one session earlier, for the same class of bug). Confirmed directly: the arrow function's own separately-compiled LLVM function emitted a GEP into the generator's own instance-struct layout, reinterpreting its own unrelated `%env` closure-environment parameter as if it were a generator instance pointer — a hard clang-stage type mismatch that would have been silent memory corruption at runtime had the types happened to line up. Fixed by adding the identical save-nil-restore-via-defer treatment to all three closure/function state-save blocks, matching ADR-00168's own established pattern exactly (defer, not a plain end-of-function assignment — the same lesson that ADR already documents for why a plain assignment isn't safe against an early error return).

## Side effects discovered

`make conformance` moved by exactly zero files (confirmed via a full before/after pass-list diff — byte-identical pass sets). Investigated why, not just reported the flat number: sampled the actual `language/statements/generators/` and `built-ins/GeneratorFunction/` Test262 directories directly — the corpus's own generator tests are dominated by `for...of` iteration over a generator (not implemented — a separate, deferred `emitForOf` case per TDD-00061), `yield*`, generator methods on classes/objects, async generators, and destructured/default parameters (all explicitly out of V1 scope, rejected cleanly). V1's actual scope (a plain top-level generator function, manually driven via `.next()`) essentially doesn't overlap with the corpus's own idiomatic usage, despite being a real, extensively-verified, working feature — the same "real feature, zero conformance payoff due to corpus idiom mismatch" pattern already documented in ADR-00170.

## Verification

- Linux x86-64, both `manual` and `-mm=gc` memory modes. `go build`, `go vet ./...`, `go test ./...` all pass.
- New E2E tests in `tests/generators_test.go`: basic yield/return sequence, `.next()` on an already-finished generator (zero value, not the stale last-yielded one), sent values (`const a = yield x`), generator function parameters (including an infinite generator via `while (true)`), a string element type, bare `yield`, a generator with no `yield` at all (runs to completion on its first `.next()`), a nested closure inside a generator body (the regression guard for bug 2 above), two independent instances of the same generator function advanced out of order, and an interleaved-generators-with-per-iteration-allocation stress shape.
- `tests/func_test.go`'s existing generator-rejection tests updated to match what's actually still rejected in V1 (missing return-type annotation, a nested declaration, `yield` outside any generator, `yield*`) rather than the blanket "not yet supported" ADR-00171 shipped.
- Manually verified beyond the automated suite: a GC-mode stress test (3 interleaved generators, each allocating array literals every iteration to pressure a real Boehm collection mid-suspend) — 200/200 correct runs, no crash, in both `-mm=gc` and manual mode.
- `examples/generators/generators.ts` (new). `make examples` — 112/112.
- `make conformance` — 4503/53578 (8.4%), unchanged from ADR-00171's own number; see Side effects for the full accounting of why.
