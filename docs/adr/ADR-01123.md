# ADR-01123: The strict lane rejects TypeScript's type errors

- **Relations**: `Implements TDD-00230` (Phase 2, P2.7); `Extends ADR-01122`, `ADR-00651`, `ADR-00656`; `Supersedes` TDD-00201's claim that ToPrimitive arithmetic on a statically-typed object is faithful in both lanes
- **Date**: 2026-09-24

## Context

[ADR-01122](ADR-01122.md) gave the checker TypeScript's type errors and
measured them against TypeScript's own baselines, with no error reaching a
user. The remaining question was what the default lane does with them.
Switched on for the E2E suite, the checker rejected 16 tests:
- about half expect codegen's own rejection message for a program tsc also
  rejects;
- the rest exercise behaviour this compiler accepted in strict mode and tsc
  rejects: ToPrimitive arithmetic on objects
  ([TDD-00201](../tdd/TDD-00201.md)), extra call arguments read through
  `arguments`, and a hole in a `number[]` literal.

## Investigation

An audit of the design records for what `-compat=strict` means:

- **[TDD-00075](../tdd/TDD-00075.md)** created the axis. `strict` is the
  compiler's opinionated, safer-than-JS semantics; `js` is best-effort
  JavaScript fidelity. The naming alternatives it lists (`native|js`,
  `off|js`) name the same two modes.
- **[TDD-00209](../tdd/TDD-00209.md)** (`--no-any`) states that the default
  strict lane "is really TS-faithful". It makes the fully static,
  `any`-free guarantee a separate flag, "not a new compat mode (the mode axis
  stays `strict`/`js`)".
- **[ADR-00651](ADR-00651.md)**'s two-tier rule: the strict lane rejects what
  it cannot represent, and a variable holding values of different types needs
  `: any` or `-compat=js`, as tsc requires.
- **[ADR-00656](ADR-00656.md)**: Test262 already counts a deliberate
  strict-lane rejection that `-compat=js` recovers as `STRICT_REJECT`, apart
  from failures.
- No record proposes a `-compat=ts` lane.
- TDD-00201 says ToPrimitive is "faithful in both lanes for statically-typed
  objects". tsc rejects `obj * 2` (TS2362), so that half contradicts the
  TS-faithful strict lane.

## Decision

- **The strict lane rejects every type error the checker reports**, with
  tsc's code, message and position. `-compat=js` compiles the same program as
  JavaScript. Each diagnostic has the kind `TypeScript` (`diag.TypeScriptError`:
  valid JavaScript that TypeScript's type rules reject) and the hint
  "TypeScript rejects this program; -compat=js compiles it as JavaScript". The
  CLI labels it `type error` and prints the hint.
- **Where:** the resolver checks the merged program on the strict lane
  (`resolver.TypeCheck`), attributing each diagnostic to the file its
  top-level statement came from. The CLI, dynamic-import islands and the
  conformance runner all compile through it. The E2E helpers that parse
  directly call `TypeCheck` too (`parseStrict`), so the suite tests what users
  get. A worker module's body is not bound yet, so not checked.
- **JavaScript-only behaviour moves to `-compat=js`:**
  - ToPrimitive arithmetic on objects: the strict tests become js-lane tests.
    Unary `+`, comparisons and `==` on objects stay legal in strict, as tsc
    allows them.
  - Extra arguments read through `arguments` need an overload signature with
    a rest parameter to be valid TypeScript. The tests and
    `examples/basics/arguments_object.ts` declare one.
  - A hole in an array literal is typed `(T | undefined)[]`, and reads as
    `undefined`.
- **Conformance** counts a checker-only rejection as `STRICT_REJECT`, and
  never as the syntax error a parse-negative Test262 test expects.
- **Messages** follow tsc's display: a literal source is widened against a
  non-literal target, an operator's operands are shown as typed when a
  bigint is involved and widened otherwise, and `{}` prints as `{}`.

## Implementation notes

- `resolver/resolver.go`: the statement-to-file map, `TypeCheck`.
- `checker/check.go`: `CheckFiles`, the hint, message display;
  `checker/checker.go` (`file`); `checker/types.go` (`{}`).
- `diag/diag.go` (`TypeScriptError`), `diag/messages.go`.
- `main.go` (`reportDiagnostics`).
- `tools/conformance/main.go` (`typeErrorOnly`).
- **Tests:**
  - `tests/compiler_test.go` (`parseStrict`);
  - `tests/toprimitive_test.go`: six tests move to `assertOutputCompatJS`;
  - `tests/func_test.go`: two tests gain an overload signature;
  - `tests/dynamic_test.go`, `tests/bigint_test.go`,
    `tests/callback_falloff_test.go`: the checker's message;
  - `tests/arrays_test.go`: holes are `undefined`.
- **Status:** a new Type System row, "TypeScript type errors", and its
  reference entry (`types.typeerrors`).

## Side effects discovered

- A hole in an array literal now reads `undefined` in these tests, where the
  `number[]` form read a zero stand-in. The zero stand-in was a divergence of
  its own. `console.log` still renders a hole as `undefined` instead of
  Node's `<1 empty item>` (BACKLOG §0 item 4).

## Verification

All on macOS arm64 (M4):

- `klainmain` on `let a: number = "x"`: the type error with tsc's message and
  the hint. With `-compat=js`, the program reaches codegen.
- The bigint operator messages match tsc 5.6.3 for ten operand shapes
  (`5n + 1`, `b * 2`, `true + 1`, `{} + 1`, …).
- The 13 updated tests pass.
- Test262 (`make conformance`):
  - Strict lane: 7,129 → 7,064 of 53,578.
    - Strict-lane rejections recoverable under `-compat=js` (`STRICT_REJECT`)
      rose from 706 to 1,113: JavaScript tests TypeScript's type rules
      reject.
    - Parse-negative tests counted as accepted rose from 698 to 714. For 16
      tests, codegen's rejection had counted as the expected syntax error;
      now the checker rejects them first, with a type error that does not
      count.
  - js lane: 7,716, unchanged.
- The other gates: see ADR-01122.
