# TDD-00245: Timers as Node's own timer lists, in TypeScript

- **Status**: Implemented
- **Date**: 2026-10-05

## Context

`setTimeout`, `setInterval` and `setImmediate` are compiler intrinsics
(`emit_timers.go`) over a C queue (`timerssrc/timers.c`): an append-only
array of `{id, fire, interval, closure}`, one `uv_timer_t` per pending entry
on POSIX ([ADR-01394](../adr/01/ADR-01394.md)), a scan of the array on Windows.
Three divergences from Node follow from that shape:

- **The handle is a number.** `setTimeout` returns the entry's id: `typeof`
  reads `"number"`, `Timeout`'s methods work only on a statically typed
  handle, and the state Node keeps on the `Timeout` (`hasRef()` reading
  `null` once the timer fired or was cleared, `refresh()` of a fired timer
  re-arming it unreferenced, `[Symbol.toPrimitive]`) has nowhere to live.
- **`setImmediate` is a 0 ms timer.** Node runs immediates in the check
  phase, after I/O polling: scheduled from an I/O callback, an immediate
  runs before a 0 ms timeout. Here the two are indistinguishable.
- **The queue never shrinks.** Every timer ever created keeps its entry, and
  `clearTimeout`, `refresh`, `ref`/`unref` and `hasRef` scan them all. A
  server that arms a timeout per request grows by one entry per request and
  slows down linearly.

Node solves all three in JavaScript (`lib/timers.js`,
`lib/internal/timers.js`) over a small native surface: the `Timeout` and
`Immediate` classes hold their own state, timers with the same duration
share a linked list, a priority queue orders the lists by expiry, and one
libuv timer is armed for the earliest list. Immediates are a linked list
that a `uv_check_t` drains, with a `uv_idle_t` keeping the poll from
blocking while any is referenced. Retired timers are unlinked, and the
garbage collector (or this compiler's memory mode) owns the handle.

## Design

Port Node's timer modules to TypeScript, as `timers/promises` already is
([ADR-01271](../adr/01/ADR-01271.md)), and shrink the native side to Node's.

### The TypeScript side

- `lib/node/internal_timers_core.ts` ports `lib/internal/timers.js`:
  `Timeout`, `Immediate`, `TimersList`, the duration map, the priority
  queue, `insert`, `active`/`unrefActive`, `processTimers` and
  `listOnTimeout` (microtasks drained after every callback, as
  `runNextTicks` does), and `processImmediate`.
- The globals `setTimeout`, `setInterval`, `setImmediate`, `clearTimeout`,
  `clearInterval` and `clearImmediate` become a global module
  ([TDD-00232](TDD-00232.md)) exporting Node's `lib/timers.js` functions;
  `NodeJS.Timeout` and `NodeJS.Immediate` resolve to its classes.
  `clearTimeout(number)` finds a timer through the known-by-id map that
  `[Symbol.toPrimitive]` populates, as Node's does.
- `lib/node/timers.ts`, `internal_timers.ts` and `timers_promises.ts` call
  the module directly.
- Out of scope, as elsewhere in this runtime: async hooks' init/destroy
  emission and `AsyncResource` context.

### The native side

`lib/native.d.ts` gains Node's binding (`internalBinding('timers')`):

| Native | Node's | POSIX | Windows (until TDD-00244 Stage 6) |
|---|---|---|---|
| `timersInit(processTimers, processImmediate)` | `setupTimers` | stores both callbacks | same |
| `timerSchedule(ms)` | `scheduleTimer` | one `uv_timer_t` | a deadline the loop's wait folds in |
| `timerToggleRef(on)` | `toggleTimerRef` | `uv_ref`/`uv_unref` | a flag the keep-alive reads |
| `timerNow()` | `getLibuvNow` | `uv_update_time` + `uv_now` | the monotonic clock in ms |
| `immediateToggleRef(on)` | `toggleImmediateRef` | `uv_idle_start`/`stop` | a flag the wait reads (wait 0) |
| `immediateSetPending(n)` | `immediateInfo[kCount]` | the check handle skips when 0 | the loop's after-dispatch step skips when 0 |

`processTimers(now)` returns the next expiry as Node's does: 0 for none,
positive when the next list is referenced, negative when not. The native
side re-arms and re-refs the single timer from that.

`timerssrc/timers.c` shrinks to that binding. Its queue, the per-entry
`uv_timer_t`s, `__kml_timer_tick` and the loop's Windows timer scan are
deleted. A dynamic-import island's deadline reads the binding's armed
expiry. The webview's Windows tick pump runs `processTimers` and
`processImmediate` through the same binding.

### Codegen

`emit_timers.go`'s intrinsics and their callback adaptation are deleted;
calls lower to the global module like any other library function. A timer
created from C (none today) would go through the TypeScript functions too.

## Open questions

- The cost of a timer in compiled TypeScript (class instance, list links)
  against today's C entry, measured on a per-request-timeout server before
  the switch.
- Whether `Timeout`'s `_idlePrev`/`_idleNext` and other underscore fields
  stay visible to user code, as in Node (they are public there), or become
  `#private`.
