# ADR-00267: `new Promise` executor may be a function expression or closure-typed value

- **Relations**: refines [ADR-00263](ADR-00263.md) (the executor constructor)
- **Date**: 2026-08-20

## Context

`new Promise(executor)` ([ADR-00263](ADR-00263.md)) accepted only an
`*ast.ArrowFunction` executor — a `function(resolve, reject) { … }` expression, or
a closure-typed variable (`const exec = …; new Promise(exec)`), was rejected, even
though the caveat text implied a function expression was allowed.

## Decision

Emit the executor from whatever expression it is: an arrow literal or a
function-expression literal is emitted with the two param hints
(`resolve: (T)=>void`, `reject: (Error)=>void`) so its unannotated params get the
right closure signatures; any other expression is emitted as a value and required
to be closure-typed (`IsFunc`). All closures share the `{fnptr, env}` ABI and the
executor's two params are pointer-typed regardless, so the immediate invocation
(env, resolveClo, rejectClo) works for every form.

## Consequences

- `new Promise(function(resolve, reject) { … })` and `new Promise(exec)` (a
  closure-typed variable) both work, alongside the arrow form.
- A bare **top-level-function** reference as the executor stays unsupported — the
  general "a top-level function can't be passed by reference" limitation, not
  specific to `new Promise`.
- Still out of scope (a genuine feature, not a residual — tracked on the row):
  **thenable adoption**, `resolve(aPromise)` adopting the inner promise's state.
  It needs `resolve`'s parameter to be a `T | PromiseLike<T>` union with a runtime
  tag so the settle thunk can tell a value from a promise — union-typed parameters
  are a type-system feature, not a small addition, and `resolve` is an ordinary
  closure param that can't be intercepted at the call site.
