# TDD-00234: child_process as a TypeScript module

- **Status**: Implemented
- **Date**: 2026-09-29

## Context

TDD-00230 P3.1 moves the builtin surface into declarations and, where the
module is plain JavaScript in Node, into TypeScript. TDD-00231 made that
possible (`net`, `tls`, `http`, `https`, `stream`, `url`'s legacy API are
Node's own code in `lib/node/`). `child_process` is still code-generated
(`emit_childprocess*.go`, `runtime_childprocess*.go`). That form cannot match
Node in several ways:

- A `ChildProcess` is not an `EventEmitter`. Each event takes one
  listener, and only an arrow or function-expression literal. `once`,
  `off`, `listenerCount`, a listener stored in a variable and a second
  `'exit'` listener are all compile errors.
- `child.stdout`/`stderr`/`stdin` are not streams. There is no
  `pipe()`, `setEncoding`, async iteration, `'readable'`, back-pressure or
  `'drain'`, and a child's output can't be piped into another stream (a
  file, `process.stdout`, another child's `stdin`).
- `spawn`'s options are read at compile time from an object literal, so a
  computed options object is rejected.
- There is no `'spawn'` event. Errors are not Node's (`spawn x ENOENT`,
  `errno`, `code`, `syscall`, `path`, `spawnargs`).
- The fork IPC channel (TDD-00141) is a separate code path from the
  streams.

Node's `lib/child_process.js` and `lib/internal/child_process.js` are
JavaScript over two native handles: `Process` (spawn, kill, the exit
callback) and `Pipe` (a stream handle, the one `net.Socket` wraps). The
stream half already exists here: `lib/native.d.ts`'s TCP handles are
fd-generic stream handles (`read`/`send` on the descriptor, the
reactor's dispatch), and `net.connect({ path })` already makes a
Unix-domain one.

## Design

### Native surface (`lib/native.d.ts`, `klainpool.c`)

- `processSpawn(file, args, envPairs, cwd, detached, stdio, onExit): number`
  spawns with `posix_spawn` (with `fork`/`exec` as the fallback for
  `cwd` and `setsid`, as libuv does). It returns the pid, or `-errno` for
  `ENOENT`/`EACCES`, reported the way libuv reports a failed spawn.
  - `stdio` is one integer per descriptor: `-1` for a pipe, `-2` to
    ignore it (`/dev/null`), or an inherited fd (≥ 0).
  - Each pipe is a `socketpair(AF_UNIX, SOCK_STREAM)`, libuv's
    `UV_CREATE_PIPE`. The parent's end becomes a stream handle (the
    existing TCP-handle table), read back with `processStdio(i)` after
    the spawn.
  - `onExit(exitCode, signal)` runs on the loop thread.
- Exit detection keeps the existing SIGCHLD self-pipe
  (`runtime_childprocess_exit.go`), moved into `klainpool.c`. The
  dispatch reaps with `waitpid(WNOHANG)` and calls each handle's
  `onExit`. A live process handle holds the loop open; `unref` releases
  it.
- `processKill(pid, signal): number` returns 0 or `-errno`.
- `spawnSync(file, args, envPairs, cwd, stdio, input, timeout, maxBuffer,
  killSignal)` blocks natively. It polls the child's pipes, feeds
  `input`, enforces `timeout` and `maxBuffer` with `killSignal`, and
  returns `{ pid, status, signal, stdout, stderr, error }` through the
  last-result accessors, as the native DNS/fs calls do. Node's own
  `spawn_sync.cc` is native code too; `execSync`/`execFileSync` are
  TypeScript over it, as in Node.

### TypeScript (`lib/node/child_process.ts`)

- A port of Node v24's `lib/child_process.js` and the parts of
  `lib/internal/child_process.js` the native surface serves:
  `normalizeSpawnArguments` (shell, `argv0`, env, `cwd` validation),
  `ChildProcess extends EventEmitter` (`spawn()`, `kill()`, `ref`/`unref`,
  `pid`, `exitCode`, `signalCode`, `killed`, `connected`, `stdio`,
  `'spawn'`/`'exit'`/`'close'`/`'error'`/`'disconnect'`/`'message'`),
  `spawn`, `exec`/`execFile` (buffered output, `maxBuffer`, `timeout`,
  `killSignal`, `encoding`, the error shape with `cmd`/`code`/`signal`,
  `stdout`/`stderr`), `spawnSync`/`execSync`/`execFileSync`, `fork`.
- The stdio pipes are `net.Socket`s over the pipe handles, as Node's are.
  This needs `net.Socket` to accept an existing handle (`{ handle }`),
  which Node's does through `_handle`.
- `fork` keeps TDD-00141's wire (json serialization, newline-framed,
  `NODE_CHANNEL_FD`) with the channel on its own socketpair: `send`
  (with its callback), `'message'`, `disconnect`, `connected`. Handle
  passing (`send(msg, socket)`) and `serialization: 'advanced'` are not
  ported.
- `util.promisify(exec)` works, since `exec` is a function value with
  `util.promisify.custom`, as in Node.
- The code-generated `child_process` is deleted, including the
  `ChildProcess` type in codegen. `klain:` has no replacement for it.

### Windows

The TCP handles on Windows ride the win32io layer (TDD-00231). A
Windows process handle uses `CreateProcessW` with overlapped named pipes
(libuv's `uv_spawn` on Windows) registered with the loop's completion
port, and a wait registration (`RegisterWaitForSingleObject`) posting a
completion for the exit. It is compile-checked here and first run on the
Windows machine, as `net`'s handles were.

## Open questions

- The child side of the fork channel (`process.send`,
  `process.on('message')`) stays codegen until `process` is itself a
  TypeScript object. Both sides must keep TDD-00141's wire byte for byte.
- `detached` on POSIX is `setsid()` in the child. With `posix_spawn` that
  needs `POSIX_SPAWN_SETSID`, which macOS and glibc ≥ 2.26 have. Older
  glibc falls back to `fork`/`exec`.
