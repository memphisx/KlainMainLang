# ADR-00161: Array rest destructuring (`[a, ...rest]`)

- **Relations**: Extends [ADR-00153](ADR-00153.md), [ADR-00157](ADR-00157.md), [ADR-00160](ADR-00160.md)

## Context

Investigating the two remaining confirmed candidates from ADR-00160's closing note — computed destructuring keys (`{[key]: val} = obj`) and `new Map(entries)` — both run into the same structural wall this compiler's static-shape objects already hit elsewhere: a computed key needs a runtime-resolved field on a type whose field offsets are fixed at compile time (`FieldIndex(name string)` is a static lookup), and object rest destructuring (`{ a, ...rest } = obj`) needs a real "the interface type minus these field names" type this compiler has no mechanism to express. Both would need real type-system work first, not a quick fix. Array rest destructuring (`[a, ...rest] = arr`) doesn't have either problem — arrays are dynamically-sized regardless of static element typing — so it was picked up instead.

## Investigation

Confirmed `[a, ...rest] = arr` (assignment) already *parses* today with no grammar change: an array literal already accepts `...expr` via `SpreadElement` (needed for array-literal spread, unrelated to destructuring), so `[a, ...rest]` on the left of `=` already parses as `ArrayLiteral{Elements: [Identifier{"a"}, SpreadElement{Arg: Identifier{"rest"}}]}` — the codegen gap (ADR-00160's array-destructuring-assignment branch had no `SpreadElement` case) is the only real gap there. The *declaration* form (`let [a, ...rest] = arr`) needed a real parser change, since `parseArrayDestructuring` and the two destructured-parameter array-pattern parsers (a pre-existing near-duplication this session already worked around rather than refactored, see ADR-00158) only ever expected a plain `IDENT` or a hole.

## Decision

Declaration form: `ast.ArrayPatternElem` gained a `Rest bool` field (Name still holds the rest variable's own name). All three array-pattern parsers (`parser_stmts.go`'s `parseArrayDestructuring`, and the two destructured-function-parameter pattern parsers in `parser_literals.go`/`parser_stmts.go`) recognize `...name` and `break` immediately after — a real syntax rule enforced for free by that `break`, not by an explicit check: anything else before the closing bracket (a trailing comma, another element) now hits a clean "expected ], got ..." at the bracket instead of silently accepting `[...rest, a]`, which real JS also rejects. Combining rest with a default (`[...rest = []]`) is impossible to even write, for the same reason — no `=` parse path exists on that branch.

`unpackArrayPatternInto` (the shared codegen core for both the declaration form and destructured parameters, ADR-00157/ADR-00158) builds the rest array with the same `malloc` + `memcpy` shape `emitArraySlice` (`.slice()`, `codegen/llvm/emit_arrays_sort.go`) already established for "copy a byte range of the source into a fresh buffer," including the identical `select i1 (end - start) < 0, 0, (end - start)` clamp for when the rest position is already past the source's actual length (an empty array, not an error — same "no negative length" reasoning `.slice()` needs for an out-of-range start index). A genuinely new, independent copy, not an aliasing view into the source's own backing buffer — matching real JS.

Assignment form (`[a, ...rest] = arr`): the existing array-destructuring-assignment branch (ADR-00160) now recognizes a `*ast.SpreadElement` as its own case — must be the last element (checked explicitly here, since assignment reuses the general array-literal grammar, which has no parser-level "rest must be last" enforcement the way the dedicated pattern parsers get for free), and its target must already be declared as an array (checked via `sym.Ty.IsArray`, since assignment — unlike declaration — has no `e.define` step to create a fresh binding of the right shape). Builds the same malloc+memcpy rest array, then stores directly into the target's existing `Ptr`/`LenPtr` allocas rather than defining a new symbol.

## Side effects discovered

None — checked directly rather than assumed, since this session's last four rounds each found a real resolver/closure-capture bug from a new AST field the rename pass or free-variable scanner didn't know about (ADR-00156, ADR-00158, ADR-00159, and implicitly guarded against in ADR-00160). This one didn't need any: `bindParams`/`rewritePatternDefaults`/`scanStmtsFV`'s existing `ArrayPatternElem` handling already iterates every element's `.Name` generically, and `Rest` doesn't change that shape — a rest element still just has a name to bind or scan, same as any other. Verified directly anyway: a destructured-parameter rest binding referenced inside a nested closure correctly hits the same *pre-existing*, unrelated "capturing array variable in a closure is not yet supported" rejection every other array-typed capture already does — confirming the free-variable scan found it correctly (an "undefined variable" error would have meant it didn't), not a new gap.

## Verification

- `go build`, `go vet ./...`, full `go test ./...`, `make examples` (all 109) — all pass.
- 9 new E2E tests (`tests/arrays_test.go`): basic rest, rest empty when the source is shorter than the pattern, rest capturing the whole array (`[...all]`), independent-copy confirmation (mutating the source after destructuring doesn't affect the rest array), a destructured-parameter rest, the assignment form, and three negative cases (assignment rest target must already be an array, assignment rest must be last, declaration rest must be last, rest combined with a default).
- `examples/basics/destructuring.ts` extended with a dedicated section covering all three positions (declaration, parameter, assignment) plus the independent-copy case; built and ran directly, output matches the file's own inline comments exactly.
- Full Test262 corpus re-run: 4,462 → 4,462, no aggregate movement — expected, same reasoning as ADR-00158/ADR-00159/ADR-00160: `...` inside an array pattern was a hard parse error before this change, so no previously-*passing* file could regress from it.
