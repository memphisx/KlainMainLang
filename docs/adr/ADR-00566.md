# ADR-00566: Number.prototype.toString(radix) renders fractional digits

- **Relations**: Extends ADR-00552
- **Date**: 2026-09-01

## Context

`Number.prototype.toString(radix)` truncated a fractional receiver to its
integer part — `(255.5).toString()` returned `"255"`, `(255.5).toString(16)`
returned `"ff"`. It also coerced the receiver to `i64` before formatting, so
even the default (base-10) form lost the fraction. The radix *was* already
validated to 2..36 (ADR-00552); the function's own doc comment claiming
otherwise was stale, and the status page's "doesn't validate the radix" caveat
was wrong.

## Decision

- **Default / radix 10** (the common case) is exactly `String(x)`, so it is
  delegated straight to `emitValueToString` — the faithful shortest-round-trip
  decimal, fractional part included. This holds for both the no-argument form
  (handled before any radix work) and a runtime `radix === 10` (a branch that
  delegates).
- **Any other base** runs `emitNumberRadixIntFrac`: the integer part
  (truncated toward zero, sign kept) via the existing repeated-urem/udiv digit
  loop (extracted to `emitNumberRadixIntPart`), and — when the receiver has a
  fractional part — a `"."`-prefixed fractional expansion by the classic
  repeated-multiply-by-radix algorithm (`emitNumberRadixFrac`).

The fractional loop multiplies the residual by the radix, emits the integer
part of each product as a digit, and continues on the remaining fraction.

## Faithfulness

For a **power-of-two base** (2/4/8/16/32) the double multiply-by-radix and the
digit subtraction are both exact, so the expansion is bit-exact to V8 — e.g.
`(0.1).toString(2)` yields the full 53-significant-bit
`0.0001100110011001100110011001100110011001100110011001101`, matching Node.
For a **non-power-of-two base** the double arithmetic can differ from V8's
exact-bignum result in the trailing digits, and a genuinely non-terminating
expansion is capped at 1100 fractional digits. Base 10 sidesteps both by
delegating to the shortest-decimal path. These residuals are the row's sole
remaining caveat.

## Side effects discovered

None. The integer-only paths (`(255).toString(16)`, `(-255).toString(16)`,
`(0).toString(2)`, `(35).toString(36)`) are unchanged — the extracted
`emitNumberRadixIntPart` is the original loop verbatim, now fed the truncated
integer part.

## Verification

New `TestE2ENumberToStringRadixFractional` (base-10/no-arg fractional,
`ff.8`, `0.1` in binary, `11.11`, `a.4`, and the exact 0.1 binary expansion)
plus the existing `TestE2ENumberToStringRadix`,
`TestE2ENumberToStringRadixRangeError`, `TestE2EBigIntToStringRadix`, and the
WebCrypto hex-formatting tests pass. Built and verified on Mac (Apple Silicon).
