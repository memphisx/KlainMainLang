# ADR-01646: A `for await` makes its callable a coroutine

- **Relations**: Extends [ADR-01388](ADR-01388.md)
- **Date**: 2026-10-16

## Context

`Readable.from([1, 2, 3]).some(fn)` called outside any coroutine (the
module body, a timer, a `nextTick`) aborted with "internal error: a wait
outside a coroutine inside an event-loop callback". `find` and `forEach`
did the same; `toArray` and `every` worked. From inside an async function
all of them worked.

## Investigation

`some`, `find` and `forEach` (`lib/node/stream.ts`) each wait only in a
`for await` over `mapOperator(...)`, an async generator. Their emitted IR
had no `.inner`/`.tramp` pair: they were compiled as plain functions.
Codegen makes an async callable a coroutine when `sawAwait` is set, and only
an `await` expression or an adopted `return <promise>` set it. The
async-generator `for await` (`emitForAwaitOfGenerator`) waits with
`__kml_task_await_ready`, but never set the flag. Called from a coroutine,
the wait parked the caller's coroutine, so the bug only showed outside one.
`every` awaits `this.some(...)` itself, and `toArray`'s loop over `this`
already came out as a coroutine. User-code copies worked because other
statements in them set the flag.

## Decision

`emitForOf` sets `sawAwait` for every `for await`, before any of its
iteration forms is picked: each step waits.

## Implementation notes

`codegen/llvm/emit_stmts.go`.

## Verification

`TestE2EForAwaitOnlyWaitIsCoroutine` matches Node's output and order. The
async, stream and for-await suites pass on Linux x86-64 (DeskMini); Apple
Silicon Mac probes.
