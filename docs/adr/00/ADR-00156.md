# ADR-00156: Multi-declarator `let`/`const`/`var`, for-loop comma-update

- **Relations**: Extends [ADR-00153](ADR-00153.md) (Test262 full-corpus conformance harness)
- **Date**: 2026-08-11

## Context

Investigating small, self-contained candidates in the conformance report's failure table (`expected ;, got ,`, `expected ), got ,` — 601 and 558 files respectively) with direct repros found something more foundational than expected: `let i = 0, j = 10;` — multiple comma-separated declarators sharing one `let`/`const`/`var` — didn't parse *at all*, at any scope, not just inside a `for` loop. `parseVarDecl` (`parser/parser_stmts.go`) only ever parsed a single `IDENT[: type][= init]` and returned one `*ast.VarDeclaration`. A related but distinct gap sits next to it: a `for` loop's update clause only supports one expression (`i++`), not the common two-pointer idiom `i++, j--`.

## Investigation

Confirmed both gaps are real and separate (fixing one doesn't fix the other): `let i = 0, j = 10;` fails with `expected }, got =`-shaped errors depending on context; `for (...; ...; i++, j--)` fails specifically at the update clause. Neither is the general JS comma (sequence) operator, which stays out of scope everywhere else in this compiler (`let x = (1, 2, 3)` still doesn't parse, unchanged) — both are narrower, well-known idioms in their own specific grammar positions.

Representing multi-declarator support cost more thought than the fix itself: `ast.ForStatement.Init` is a single `Statement` slot (a `for` loop's init clause), so simply wrapping multiple declarators in a `*ast.BlockStatement` looked tempting but is actively wrong — `BlockStatement` pushes its own scope (`emitStmt`'s `case *ast.BlockStatement`), which would hide every declared name the instant the "statement" ended, breaking exactly the case that matters most (`for (let i = 0, j = 10; ...)`, where the loop's own test/update/body must still see `i`/`j`).

## Decision

Added `*ast.VarDeclarationList` (`Decls []*VarDeclaration`) as a new statement kind, returned by `parseVarDecl` only when more than one declarator is present (a single declarator still returns a plain `*ast.VarDeclaration`, unchanged). `parseVarDecl`'s signature changed from `(*ast.VarDeclaration, error)` to `(ast.Statement, error)` — safe, since its only two callers (top-level statement dispatch, `for`-loop init) already only ever used the result as a generic `ast.Statement`. `emitStmt` handles the new node by looping `emitVarDecl` once per declarator — no new codegen machinery, since each declarator is an ordinary, independent `VarDeclaration` under the hood.

The `for`-loop update clause changed from a single `Expression` to `[]Expression`, parsed as a comma-separated list and evaluated in declared order every iteration, purely for side effects (the value of each is always discarded already, so no new codegen semantics were needed there either — just a loop instead of one call).

`export let a = 1, b = 2;` is a deliberate, narrower scope cut: `parser/parser_imports.go`'s `parseExportDeclaration` already type-switches on the exact set of statement kinds `export` accepts, and `*ast.VarDeclarationList` isn't one of them — this produces a clean rejection for free, with no additional code, rather than silently mis-exporting only one of several names.

## Implementation notes

Introducing a new statement kind meant auditing every existing `case *ast.VarDeclaration` type-switch for a silent-skip risk, not just adding the obvious ones — a real correctness bug, not just a missing feature, in two of them:

- `resolver/rename.go`'s `rewriteStmt` (local reference-rewriting *and* scope-binding for shadowing/reserved-name checks — `sc.bind`/`lu.checkBinding`). Missing this would have meant a local `let i = 0, j = 10;` inside any function silently failed to register `i`/`j` in the local scope, with knock-on effects on later shadowing/reserved-name checks in that same function — found and fixed before it could ship, not found in the field.
- `codegen/llvm/emit_func.go`'s `scanStmtsFV`/`scanExprFV` (closure free-variable capture analysis) — both the general statement-list scan and the `*ast.ForStatement`-specific `Init` handling. Missing this would have meant a nested closure referencing a multi-declarator-bound name (`let a = 1, b = 2; const f = () => a + b;`) was incorrectly treated as capturing a free variable instead of a local one — wrong codegen, not a compile error, the worst kind of miss. Verified directly with a targeted repro (a closure returned from an outer function, called after the outer function returns) rather than trusting the fix by inspection alone.
- `resolver/resolver.go`'s per-file declaration-name mangling (TDD-00041): `declNameOf`/`setDeclName` were single-name-only APIs used by three call sites (a defensive uniqueness assertion, `mangleFileDecls`, `exportedNames`). Replaced both with `declRefsOf` (`[]declRef{Name, Set}`) so every call site loops over however many names a statement actually introduces — `declNameOf` itself became dead code once every caller moved to the new function and was deleted rather than left unused. Also added a matching case to `validateCyclicFile`'s per-declarator literal-initializer check (TDD-00052's import-cycle restriction).
- The for-loop `Update` type change (`Expression` → `[]Expression`) was compiler-enforced rather than found by audit — Go's type checker caught the one remaining site (`resolver/rename.go`'s `*ast.ForStatement` case in `rewriteStmt`) immediately on `go build`, unlike the `VarDeclarationList` additions above, which needed a manual grep audit since introducing a new sibling type doesn't change any existing type signature.

## Side effects discovered

Regenerating the conformance report moved overall passed count from 4,474 to 4,461 — a net *decrease* of 13 (11 newly passing, 24 newly failing), the largest net movement of the three fixes in this series, but the same underlying story as ADR-00154's `__proto__`-duplicate finding and ADR-00155's two early-error gaps: every one of the 24 newly-failing files is a negative test (`negative: {phase: parse, type: SyntaxError}`) that was previously "passing" only because the old blanket multi-declarator rejection happened to produce *a* SyntaxError, for the wrong reason. Unmasked, they reveal three real, narrow, pre-existing gaps, none introduced by this change:

- 18 files (`arguments-strict-list-*`, `eval-strict-list-*`, testing every position — first/middle/final/repeated, with and without an initializer): real JS forbids `arguments`/`eval` as a declared binding name in strict mode. This compiler has no such restriction at all, for any declaration form, single- or multi-declarator — a real gap, not new here.
- 2 files: `const x, y = 1;` / `const x;` — real JS requires every `const` declarator to have an initializer. Confirmed directly (independent of Test262) that a single-declarator `const x: number;` with no initializer already compiled cleanly before this change — a pre-existing gap this feature's multi-declarator form simply gave a second way to reach.
- 1 file (`language/asi/S7.9_A5.7_T1.js`): tests an unrelated ASI restriction (no line terminator between a postfix `++`/`--` and its operand, `x \n ++ \n ++ \n y`) using a multi-declarator `var x=0, y=0;` only as unrelated setup code in the same file — the real gap is this compiler not enforcing that ASI restriction, incidentally uncovered because the setup line now parses.

None fixed here — each is a real, separate, narrow language-completeness gap, noted rather than silently dropped, consistent with how ADR-00154/ADR-00155 handled the same shape of finding.

## Verification

- `go build`, `go vet ./...`, full `go test ./...` — all pass.
- 9 new E2E tests (`tests/stmts_test.go`): multi-declarator `let`/`const`/`var` at top level and inside a function body, a closure-capture correctness case for each of the two audited codegen sites (plain multi-declarator and for-loop-init multi-declarator), the update-clause comma idiom, and two negative cases (`export` + multi-declarator, and plain comma-separated non-declaration for-init, both still cleanly rejected as scoped).
- `examples/control_flow/control_flow.ts` extended with a multi-declarator + comma-update section; built and ran directly, output matches the file's own inline comments exactly.
- Full Test262 corpus re-run; before/after per-file diff via the same temporary debug-dump instrumentation the prior two ADRs used (not landed), confirming all 24 newly-failing files are the three narrow gaps above and all 11 newly-passing files are genuine (spot-checked `language/statementList/block-let-declaration.js`: `let a, b = 42, c;` — mixed initialized/uninitialized `let` declarators, valid real JS unlike `const`'s stricter rule).
