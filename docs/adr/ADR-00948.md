# ADR-00948: Reference-type Map keys and Set elements via the any-keyed runtime

- **Relations**: `Extends ADR-00939, ADR-00943` (array reference semantics, TDD-00213; the value-side analogue for Map values)
- **Date**: 2026-09-15

## Context

A Map keyed by an object or array, and a Set of objects/arrays, produced
invalid IR. `mapRuntime` classified any non-string, non-dynamic key as the
numeric runtime family, so a reference key's `ptr` / `{ptr,i64}` operand was
passed into `__kml_map_num_set`'s i64 key slot. Confirmed pre-existing on
committed HEAD (the object-key half never worked; the array-key half is the
key-side analogue of the ADR-00943 value-side bug).

Repros (`./klainmain --emit-llvm x.ts | clang -O0 -S -emit-llvm -x ir -o /dev/null -`):

```ts
const m = new Map<number[], string>(); m.set([1], "a"); // {ptr,i64} into i64
const s = new Set<number[]>();          s.add([1]);      //   ditto
const mo = new Map<{ x: number }, string>(); mo.set({ x: 1 }, "a"); // ptr into i64
const so = new Set<{ x: number }>();          so.add({ x: 1 });     //   ditto
```

Controls that already worked: scalar keys/elements (`Map<number,V>`,
`Set<string>`), `WeakMap<object,V>` (its own key path), and every array-valued
container from the ADR-00943–00947 bundle.

## Investigation

`mapRuntime` (`emit_collections.go`) returned `("any","i64")` only for a
`keyTy.IsDynamic` key. A reference type (`IsArray` / `IsObject`) is neither
string nor scalar, so it fell through to the `"num"` default — a `ptr`/aggregate
stored raw in an i64 slot. The any-keyed runtime already exists (TDD-00211,
NaN-boxed keys, SameValueZero identity) and is exactly the right home for
reference keys: two distinct objects/arrays box to distinct payloads and compare
unequal, while the same reference boxes consistently — reference identity.

The any-map key comparison is NaN-box-aware (required for the mixed-scalar
any-key case) and, for array boxes, dereferences to the array's underlying data
pointer, so the same named array set and probed matches — verified by repro.

Iteration surfaced a second layer: `keys()`, `entries()`, `forEach`, and Set
`for...of` all load each key slot at `keyTy.IR` (`"ptr"` for a reference key),
but the any-keyed runtime's `_keys` array holds i64 NaN-boxes. Loading a box as
a `ptr` reinterprets its bits as a header/object pointer → segfault. The boxed
keys must be **materialized** back to real pointers before they are presented.

## Decision

- `mapRuntime`: a reference key type (`isReferenceKeyTy`: `IsArray || IsObject`)
  routes to the `"any"` runtime family, `i64` operand — the same family dynamic
  keys use.
- `mapKeyRef`: box a reference key (`emitBoxValue`) exactly as a dynamic key is
  boxed, giving reference-identity keys.
- `emitSetCall` add/has/delete and the `new Set([...])` seed loop are generalized
  off the hardcoded str-vs-num split onto `mapRuntime`/`mapKeyRef`, so a
  reference element rides the any family like a Map key.
- `materializeKeysAggregate` (new): converts an any-keyed collection's raw keys
  aggregate (i64 boxes) into a proper `keyTy[]` array of live pointers — each
  array key's boxed **header pointer** (array elements store header pointers,
  TDD-00213) or each object key's boxed **object pointer**. Applied at every
  key-surfacing site (`keys()`, Set `values()`/for-of, `mapKeysAndVals` — which
  feeds `entries()`/`forEach`). A scalar/string/any key type passes through
  unchanged. Values are untouched (they already round-trip correctly).

## Implementation notes

`mapKeysAndVals` gained a `keyTy` parameter so it can materialize keys for its
`entries()`/`forEach` callers; the string-keyed consumers (Headers,
URLSearchParams, `util.inspect`, fetch header list, structuredClone) pass their
own key type (a non-reference type → pass-through, zero behavior change).

## Side effects discovered

- **Named-array-through-a-slot identity (pre-existing, NOT introduced here):**
  `arr[0] === a` is already `false` for an array-of-arrays on committed HEAD —
  a named array has no header cell, so storing it into any slot mints a fresh
  header and the readback compares unequal to the original. Iterating an
  array-keyed collection's `keys()` inherits exactly this gap
  (`m.keys()[0] === arrayKey` is `false`), and `new Set([namedArray]).has(namedArray)`
  is `false` for the same reason the array-literal element loses identity.
  Object keys are unaffected (objects carry a stable pointer), and the
  reference-vs-content distinction on set/get/has/delete is correct in all
  cases. This is one shared named-array limitation, not a collection-specific
  regression.
