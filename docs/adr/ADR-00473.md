# ADR-00473: explicit call-site type arguments (`id<string>(x)`)

- **Relations**: Extends TDD-00010's monomorphization; Extends [ADR-00452](ADR-00452.md)'s depth cap
- **Date**: 2026-08-29

## Context

Generic calls with nothing to infer from (`make<number>()`) were a hard
rejection — the `cannot infer type argument` bucket (67 TS-oracle
false-rejects) whose own error message admitted explicit type arguments
weren't supported.

## Decision

- Parser: in the call/member chain, a `<` after an identifier/member
  callee tries a backtracking parse — a type-annotation list closed by
  `>` and followed by `(` is a call with `CallExpression.TypeArgs`;
  anything else restores the cursor and leaves `<` to the comparison
  level. `a < b` / `a > (b)` keep parsing as comparisons; the genuinely
  ambiguous `f<a, b>(c)` resolves as type arguments, matching TS's own
  disambiguation.
- Codegen: `emitGenericFuncCall`/`genericCallReturnType` accept explicit
  arguments — substitutions build positionally via `resolveType`,
  bypassing inference; inference remains the fallback, its error message
  now pointing at the explicit form. Non-generic callees ignore (erase)
  the arguments.

## Side effects discovered

The corpus's `cyclicGenericTypeInstantiation` (`foo<typeof y>()` where
`y`'s type depends on the call) sent the newly reachable
inference/instantiation loop into unbounded recursion — a real oracle
**stack overflow**. Both generic-call entry points now carry the same
depth cap (8) the interface/alias instantiation got in ADR-00452, and
the case compiles in milliseconds.

## Verification

Mac. `tests/generics_test.go` E2Es (explicit args incl. the
nothing-to-infer `make<number>()`, comparison non-regression) and the
`examples/generics/erased_generics.ts` extension pass; parser +
generics/operators/string/template batches green. TS oracle agreement
5232 → 5234 (the bucket's files stack further blockers). Node oracle
unchanged (40).
