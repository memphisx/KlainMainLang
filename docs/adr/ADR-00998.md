# ADR-00998: RegExp `.flags` canonical order and empty-pattern `.source`

- **Date**: 2026-09-17

## Context

Two `RegExp` accessors diverged from V8 in observable, isolated ways:

- `.flags` returned the constructor's flag string verbatim, so
  `new RegExp("x", "ig").flags` was `"ig"` where JS re-sorts flags into the
  canonical `d,g,i,m,s,u,v,y` order (`"gi"`).
- `.source` of an empty pattern was `""`, where JS substitutes the non-empty
  placeholder `"(?:)"` (`new RegExp("").source === "(?:)"`), so that a
  serialized `/.../` never round-trips to the empty, comment-like `//`.

Both were documented caveats on the `.source` / `.flags` row (REGEXP.md).

## Investigation

- `emit_regexp.go` stores `patternVal.Ref` and `flagsVal.Ref` verbatim into the
  RegExp instance's `source`/`flags` fields at construction. Both a `/.../`
  literal and `new RegExp(...)` desugar to the same `NewRegExpExpression` node,
  so one construction site covers both forms.
- Flags are already validated (no invalid or duplicate characters) before this
  point, so canonicalization is a pure reorder — for each byte of the fixed
  `dgimsuvy` order, keep it if the input contains it.
- Both the pattern and the flags can be runtime values (`new RegExp(someVar)`),
  so the normalization must run at runtime, not as a compile-time Go rewrite.

## Decision

Route the stored `source`/`flags` through two runtime helpers, leaving the
compiled pattern (used for matching) untouched:

- `__kml_regex_flags_canon(flags)` scans the canonical order and appends each
  present flag byte, returning a fresh headered string no longer than its input.
- `__kml_regex_source_norm(src)` returns a fresh headered `"(?:)"` for a
  zero-length pattern and the source unchanged otherwise.

## Implementation notes

- `runtime_regexp.go`: new `ensureRegexFlagsCanon`/`ensureRegexSourceNorm`
  (guarded by `usedRegexFlagsCanon`/`usedRegexSourceNorm`).
- `emit_regexp.go`: call both before the `storeField("source"/"flags")` pair.
- Only the stored fields change; `compilePatternRef` / the pcre2 handle are
  unaffected, so matching behavior is identical.

## Side effects discovered

None. A non-empty pattern's `.source` and any already-canonical flag string pass
through byte-identical.

## Verification

- New E2E `TestE2ERegexFlagsSourceCanonical` (mixed flag orders, `y`/`u`,
  empty-pattern source and flags, literal and `new RegExp` forms); differential
  against `node` — all match.
- Caveats removed from the REGEXP.md `.source` / `.flags` row;
  `make status`/`status-check`/`reference-check` and `make examples` clean.
