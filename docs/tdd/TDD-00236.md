# TDD-00236: `dns` as Node's lib/dns.js over a native DNS client

- **Status**: Implemented
- **Date**: 2026-09-30

## Context

`dns` is one of the modules TDD-00230 P3.1 still compiles directly
(emit_dns.go). That module covers `lookup` (one address, IPv4 only),
`promises.lookup`, and `resolve`/`resolve4`, which it answers with
`getaddrinfo`. `getaddrinfo` is the OS resolver, not a DNS `A` query. Its
callbacks fire synchronously, and its errors carry no Node code.

Node splits the module in two:
- **`lookup` and `lookupService`** are libuv's `getaddrinfo`/`getnameinfo`
  on the thread pool.
- **Everything else** is c-ares: `resolve*`, `reverse`, `Resolver`,
  `getServers`/`setServers`, and the promises API. c-ares is a real DNS
  client. It reads the system's servers, sends queries over UDP (TCP on
  truncation), and parses each record type into the objects Node returns
  (`{ exchange, priority, type: 'MX' }`, TXT chunk arrays, SOA objects,
  TTLs on request). A failure gets a c-ares status, mapped to `ENOTFOUND`,
  `ENODATA`, `ESERVFAIL`, `EREFUSED`, `ETIMEOUT`, `ECONNREFUSED`, …

Porting Node's JS (lib/dns.js, internal/dns/utils.js,
callback_resolver.js, promises.js) is mechanical. What needs a decision is
what stands in for `cares_wrap`.

## Design

**The JS layer** is Node's four files converted as the other P3.1 ports
were:
- `lib/node/dns.ts` and `lib/node/dns_promises.ts`;
- `internal_dns_utils.ts`, `internal_dns_callback_resolver.ts` and
  `internal_dns_promises.ts`, with `ResolverBase`, the error codes and
  `DNSException`.

**`cares_wrap` stand-ins** are natives on the existing thread pool. Each
completes with `(status, count)` and hands its result over as a JSON
string (the pool's last-string channel), which the TS side parses:

- `getaddrinfo(host, family, hints, order)`: every address, in libuv's
  order, or the EAI code (`ENOTFOUND` with errno `-3008`, …).
- `getnameinfo(address, port)`: `[hostname, service]`.
- `query(channel, type, name)`: the parsed answer, or a c-ares status.
- `channel*`: a resolver's servers, timeout, tries and max timeout.

**Options for the DNS client:**

1. **Vendor c-ares.** The most faithful, being the same code Node runs.
   It adds a large third-party C library to embed and build on every
   platform (none ships it: macOS has no system c-ares).
2. **The system `libresolv`** (`res_nmkquery`/`res_nsend`, plus
   `res_ninit` for the servers). It is on macOS and glibc, not Windows
   (there, `DnsQuery_A`). Its retry and timeout policy is the system's,
   so `Resolver({ timeout, tries })` and `setServers` with ports map
   onto it only partly.
3. **An own client.** The DNS wire format over UDP, retried per server
   with c-ares' timeout/tries/maxTimeout rules, TCP on a truncated
   answer. Servers come from `/etc/resolv.conf` (POSIX) or
   `GetNetworkParams` (Windows). The parsers mirror c-ares':
   - the CNAME chain for A/AAAA/CNAME;
   - TXT records as chunk lists;
   - SOA from the answer's SOA record;
   - `ENODATA` for an answer without the type.

**Recommended: option 3.** It is a bounded amount of C (the wire format is
small and stable), behaves the same on all three platforms, and exposes
exactly the knobs Node's API has (`setServers` with ports,
`timeout`/`tries`/`maxTimeout`, `cancel`). Option 1's fidelity is not
needed where the observable results are the records and status codes,
and those follow from the RFCs.

**Stages:**
1. The JS layer; `lookup` (`all`, `family`, `hints`, `order`/`verbatim`),
   `lookupService`, `getDefaultResultOrder`/`setDefaultResultOrder`, the
   error-code constants, and `promises.lookup`/`lookupService`. The
   compiled module is deleted.
2. The client and `Resolver`: `resolve`, `resolve4`/`resolve6` (with
   `ttl`), `resolveMx`/`Txt`/`Srv`/`Ns`/`Cname`/`Ptr`/`Soa`/`Naptr`/`Caa`,
   `reverse`, `getServers`/`setServers`, and the promises `Resolver`.
3. `resolveAny`, `resolveTlsa`, `cancel`, `setLocalAddress`.

## Open questions

- **Byte-level checking.** Node's answers depend on the network. Tests
  compare with Node on the same host at the same moment, over
  stable names (`localhost`, `example.com`) plus error paths. A local
  stub DNS server in the test harness would make it deterministic, so
  the test harness may need one.
