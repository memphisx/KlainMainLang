# TDD-00194: Native platform capabilities — web-standard proxies (Notifications first) + `klain:sailfish`

- **Status**: Not Started
- **Date**: 2026-09-09
- **Notes**: Expose useful device capabilities the way [TDD-00144](TDD-00144.md)/[TDD-00142](TDD-00142.md) expose the webview — a C++ shim over the platform's own library behind an `extern "C"` ABI, no FFI. Two lanes: **portable web-standard proxies** (one JS/Web API, a per-platform backend — Notifications, Geolocation, Vibration, Web Share, Network Information, Media Session, Sensors, Battery) and an opt-in **`klain:sailfish`** for capabilities with no web equivalent (KeepAlive/background, D-Bus, Alarms, Configuration, Secrets/keychain). **Notifications is Stage 1** — every supported platform has a notifier, so it is the flagship cross-platform proxy. Sailfish Crypto is explicitly *not* pursued (it is secrets-management whose default plugin is OpenSSL — see Context)

## Context

The device probe + plugin survey for Sailfish ([TDD-00146](TDD-00146.md),
[[project_sailfish_device_probe]]) turned up a catalog of Nemo/Sailfish QML/C++
plugins that back genuinely useful mobile-app capabilities. Two things make this
worth scoping as one coherent design rather than ad hoc additions:

1. **The mechanism is already proven and is not FFI.** Every one of these is a
   plugin backed by a shared library (`libnemonotifications-qt5`,
   `libsailfishcrypto`, …). The `-webview=sailfish` shim ([ADR-00816](../adr/ADR-00816.md)–[ADR-00819](../adr/ADR-00819.md))
   established the pattern: a small C++ shim links the platform library and
   exposes an `extern "C"` ABI the emitted runtime calls, reusing the sysroot /
   moc / pkg-config machinery. Each capability is one shim + one binding — no FFI,
   no per-call marshalling dialect.

2. **Notifications is the most interesting because it is not platform-specific.**
   Every target has a native notifier — Sailfish (`Nemo.Notifications`), macOS
   (`UserNotifications`/`NSUserNotification`), Linux desktop
   (`org.freedesktop.Notifications` over D-Bus), Windows (WinRT toast). So the web
   `Notification` API is a *portable* surface with a per-platform backend, exactly
   the `-webview=<backend>` shape. The one awkward case is **headless Linux** (a
   server/container with no session bus or notification daemon), where a
   notification is meaningless — handled by a pluggable/opt-out backend, below.

**Crypto is deliberately excluded.** The Sailfish "Secrets and Crypto" framework
is secrets *management*, not a general crypto provider, and its default encryption
plugin (`org.sailfishos.secrets.plugin.encryption.openssl`) is OpenSSL underneath
with "none of these plugins use TEE/TPM or other secure-hardware." Backing
`crypto.subtle` with it would be OpenSSL plus IPC indirection, no gain. OpenSSL
stays the `crypto.subtle` backend. Sailfish *Secrets* survives only as a possible
`klain:sailfish` keychain (Lane B), not as a crypto backend.

## Design

### Two lanes

**Lane A — portable web-standard proxies.** One JS/Web API, a per-platform native
backend, so the same TS runs everywhere. These already have web/Node shapes:

| Web API | Sailfish backend | Other backends | Notes |
|---|---|---|---|
| `Notification` | `Nemo.Notifications` | macOS `UserNotifications`, Linux `org.freedesktop.Notifications`, Windows toast | **Stage 1** — see below |
| Geolocation | `QtPositioning` | CoreLocation, GeoClue, Win32 | standard Qt module on-device |
| Vibration (`navigator.vibrate`) | `QtFeedback` / `Nemo.Ngf` | — (haptics are mobile-mostly) | |
| Web Share (`navigator.share`) | `Sailfish.Share` / `TransferEngine` | macOS `NSSharingService`, Windows share | |
| Network Information | `Nemo.Connectivity` / `Connman` | reachability APIs | online/offline + type |
| Media Session | `Amber.Mpris` | MPRIS/SMTC/Now Playing | |
| Generic Sensors / DeviceOrientation | `QtSensors` | platform sensor APIs | |
| Battery Status | `Nemo.Mce` / upower | IOKit/Win32 | |

**Lane B — `klain:sailfish` (opt-in, non-portable).** Capabilities with no web
equivalent, clearly namespaced as Sailfish-only:

- `KeepAlive` — background execution / wakelocks. No web API; foundational for
  real background apps and daemons. Highest Lane-B value.
- `DBus` — generic system-bus access; a general escape hatch reaching anything
  without a bespoke shim.
- `Alarms`/`Time`, `Configuration` (dconf key–value), `Secrets` (system keychain —
  the mobile analogue of Keychain/Keystore), `Ambience`, `Store`.
- Privileged/niche last: `Contacts`, `Calendar`, `Accounts`, `Telephony`,
  `Messages`.

### Backend selection

Follow the `-webview=<backend>` precedent ([TDD-00144](TDD-00144.md)): the emitter
stays API-agnostic; a per-platform `Locate<Cap><Backend>()` + shim source is
selected by target/host, with a flag where a program legitimately needs to choose
(notably `-notifications=<backend>` for the headless case). Lane-A proxies default
to the target's native backend; a program that never uses the API links nothing
(the established conditional-link convention).

### Stage 1 — Notifications (cross-platform)

**Portable core** — the web `Notification` surface:
`new Notification(title, { body, icon, tag })`, `.close()`, the `onclick` /
`onclose` events, and the static `Notification.permission` /
`Notification.requestPermission()` (trivially "granted" on platforms without a
prompt). This is the subset every backend can satisfy.

**Per-platform backends:**
- **Sailfish** — `Nemo.Notifications` `Notification` type (verified mapping:
  `summary`←title, `body`, `icon`, `category`←tag; `publish()`/`close()`,
  `clicked`/`closed`). Shim over `libnemonotifications-qt5`, same build path as the
  webview shim.
- **macOS** — `UserNotifications` (fallback `NSUserNotification`), a framework
  link, no extra deps.
- **Linux desktop** — `org.freedesktop.Notifications` over the session D-Bus
  directly (no libnotify dependency needed), the cross-desktop standard.
- **Windows** — WinRT toast (later, gated on the Windows target work).

**Headless Linux — the pluggable case.** With no session bus / notifier a
notification is meaningless. `-notifications=<backend>` selects: `auto` (default —
freedesktop when a session bus is present, else no-op), `none` (explicit no-op),
`stderr` (log the notification — useful for servers/CI), or `custom` (the program
supplies a notifier hook). This is the "custom implementation when headless"
escape.

**Sailfish-specific extras** (`urgency`, `remoteActions`, `replacesId`,
`previewSummary`/`previewBody`, `resident`, `itemCount`) do not belong on the
portable `Notification` — they surface as an optional `klain:sailfish/notifications`
augmentation, so portable code stays portable and power users still reach the full
Nemo surface.

### Reuse

All of this rides the machinery built for the webview + [TDD-00193](TDD-00193.md):
the `-devel` sysroot (Qt/Nemo headers via `zypper`), the moc pre-step for any Qt
`QObject` shim, `LocateWebviewSailfish`-style pkg-config resolution, and the
builder/CI images (a capability shim compiles in the same lane).

### Staging

| Stage | Content | Exit criterion |
|---|---|---|
| 1 | Notifications: portable web API + Sailfish backend + Linux freedesktop backend + the `-notifications` headless selector | `new Notification(...)` shows on a Sailfish device and a Linux desktop; headless no-op/stderr works |
| 2 | Notifications: macOS backend (+ Windows toast when the Windows target lands); the `klain:sailfish/notifications` extras | notification round-trips on macOS; Sailfish extras reachable |
| 3 | The next Lane-A proxies by priority — Vibration, Geolocation, Web Share | each shows on Sailfish + one desktop backend |
| 4 | `klain:sailfish` Lane B — KeepAlive first, then D-Bus | a background task survives; a D-Bus call round-trips |

## Open questions

- **One flag or per-capability flags?** `-notifications=<backend>` is clearly
  needed for the headless case; do other Lane-A proxies need selectors, or is
  target-native-by-default enough for them?
- **`klain:sailfish` granularity** — one module with sub-imports
  (`klain:sailfish/notifications`) vs separate `klain:` names per capability.
- **Permission model** — Sailfish/desktop notifications need no runtime prompt;
  macOS/iOS-style prompts do. `Notification.requestPermission()` must resolve
  sanely on no-prompt platforms without inventing a UI.
- **Event delivery** (`onclick`/`closed`, `remoteActions`) needs the GUI/event
  loop running — trivial inside a `klain:webview` app (its loop is live), but a
  headless CLI firing a notification and exiting has nowhere to deliver a later
  click. Scope click/action callbacks to programs with a running loop.
- **The Linux backend's reach** — is `org.freedesktop.Notifications` alone the
  right desktop target (works on GNOME/KDE/most), or is a libnotify option worth
  it?
- **Does Notifications pull in a general D-Bus client** the runtime should expose
  as `klain:sailfish/DBus` anyway (Lane B), rather than a notifications-only
  bus shim?
