# ADR-01846: A for-of variable's element type, and a spread of an any

- **Relations**: `Implements TDD-00230` (P3.3: the checker answers what inferExprType did)
- **Date**: 2026-10-20

## Context

- The checker typed a `for (const x of …)` variable only for an array or a string iterable. For any other iterable it left the variable unanswered, including an `any`, a tuple, a `Map`, a `Set`, a typed array and a generator.
- `iteratedType` already covers each of those, as a spread and a destructured read use it. An unanswered loop variable makes every read through it unanswered, so emission fell back for each of them. In `lib/node/kml_headers.ts`, `for (const pair of init)` over an `any` left `pair[Symbol.iterator]` unanswered in every program that links `Headers`, which is one source of the 4,238 unanswered index reads in the full shadow run.

- An object literal spreading an `any` (`{ ...(yield), y: 1 }` in an unannotated generator) was unanswered too, because the checker handled no object spread. Its generator's type was then unanswered, and so was every read through `C.prototype.gen`, `gen()` and `iter.next`. That is the Test262 `yield-spread-obj` family in the unanswered member reads.

## Decision

- A plain `for-of` variable takes `iteratedType` of the iterable. That is tsc's element type: an `any`'s is `any`, a tuple's the union of its elements, a `Map`'s a `[K, V]` entry.
- `for await` keeps its own rules: an array's elements awaited, a string's characters.
- An object literal with a spread of an `any` is `any`, as tsc's `getSpreadType` makes it. Any other spread stays unanswered until the checker merges spread properties.

## Consequences

- `TestForOfBindingElement` covers an `any` and a tuple iterable; `TestTypeOf` covers the spread of an `any`.
- Verified on Apple Silicon (checker package, targeted for-of, iterator, generator, typed-array, strict-diagnostic, `Headers`, spread, object-literal, destructuring and yield tests). The gate on Linux x86-64 (DeskMini) and a full shadow run (Node304) follow.
