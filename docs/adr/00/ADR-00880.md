# ADR-00880: `.then`/`.catch` `function`-expression callbacks adopt the source promise's value type

- **Date**: 2026-09-11

## Context

A Test262 async-lane finding (see `HANDOVER`'s NEXT list): `.then` onFulfilled
handlers written as `function (arg) { … }` received a tiny denormal double
(`5e-324` / `1e-323`) instead of the promise's resolution value. The
`built-ins/Promise/prototype/then/rxn-handler-*.js` files — which use the
`function (arg) { … }` form, being plain JS — compared `arg !== obj` and failed
(ASYNC_TEST_FAILURE), or crashed on field access.

Minimal repro (macOS arm64):

```ts
var obj = { tag: 99 }
Promise.resolve(obj).then(function (arg) { console.log(arg === obj, arg.tag) })
// before: prints `false` and garbage; arg's bits were the object pointer
//         reinterpreted as a float64
```

## Investigation

`codegen/llvm/emit_promise_then.go` hints a `.then`/`.catch` callback's
unannotated parameter to the source promise's value type so the body sees the
right shape. But `emitFulfillCallback`/`emitRejectCallback` applied the hint
**only to `*ast.ArrowFunction`** (`emit_promise_then.go:41`, `:29`); a
`*ast.FunctionExpression` fell through to a plain `emitExpr`.

Without the hint, an unannotated function parameter takes the
codegen-wide default for a no-annotation/no-hint param — `float64`
(`emit_func.go:2464`, ADR-00042). The per-call-site then-runner
(`emitThenRunner`) loads the settled value per the promise's *inner* type and
calls the closure, so an object (`ptr`) or integer resolution value was passed
into a parameter slot the callee reads as a `double`: the pointer/integer bits
bit-cast to a denormal double — exactly the `5e-324` symptom.

`resolveCallbackWithHints` (`emit_func.go:3453`) already shows the intended
shape: it hints both arrows (`emitArrowFunctionWithHints`) and function
expressions (`emitFunctionExpression(fe, hints)`). The then/catch helpers simply
never grew the `FunctionExpression` arm.

## Decision

Hint `function`-expression callbacks the same way arrow callbacks are hinted.
In `emitFulfillCallback`, when the source value type is non-void, a
`*ast.FunctionExpression` argument is emitted via `emitFunctionExpression(fe,
[]Type{valueTy})`; in `emitRejectCallback`, via
`emitFunctionExpression(fe, []Type{errorObjType})`. Arrow handling is unchanged.

## Implementation notes

- `codegen/llvm/emit_promise_then.go`: added the `*ast.FunctionExpression` arm
  to both `emitFulfillCallback` and `emitRejectCallback`.
  `emitFunctionExpression(fe, hints)` already existed (`emit_func.go:2585`) and
  applies the hint identically to the arrow path.
- `.finally` takes no argument, so it needs no hint and is untouched.

## Side effects discovered

None. The pre-existing top-level `this` limitation (`'this' is only valid
inside a method or constructor body`) still blocks the verbatim `noStrict`
rxn-handler files that read `this`; that is a separate gap, not this fix.

## Verification

- New E2E `TestE2EPromiseThenFunctionExprCallback` (object + number resolution
  through a `function` callback) — passes.
- Existing promise/await/then/catch/thenable E2E suite
  (`go test ./tests/ -run 'TestE2E(Promise|Await|NewPromise|Thenable|Then|PartA|Resolve)'`)
  — green.
- `go build`, `go vet ./...` — clean.
- Node oracle re-run for regression check.
