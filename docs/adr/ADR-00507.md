# ADR-00507: process.memoryUsage()

- **Date**: 2026-08-29

## Context

`process.memoryUsage()` was one of a small set of remaining `missing` rows in
the Process / CLI I/O status area, and the highest-leverage of the "quick win"
gaps: process/CLI introspection is a stated priority tier, and code that logs
memory (health endpoints, CLI diagnostics) calls this without needing exact
V8-heap semantics. The prior status note deferred it as "not meaningful in
`manual` memory-management mode" — but `rss` (resident set size) is a real,
OS-level number that does not depend on a managed heap, so at least that field
is honestly reportable today.

## Investigation

Node's `process.memoryUsage()` returns
`{ rss, heapTotal, heapUsed, external, arrayBuffers }`, all byte counts. Of
these, only `rss` has a native analogue in this compiler's model — the others
are V8-heap accounting with no counterpart in a native `manual`/`gc` build.

`getrusage(2)` is available on both target platforms and exposes `ru_maxrss`
without any `/proc` parsing or Mach `task_info` platform split. Struct `rusage`
begins with two `struct timeval` fields (32 bytes on both Linux and macOS —
`time_t` + `suseconds_t`, each padded to 16), so `ru_maxrss` (a `long`) sits at
a stable byte offset 32. Units differ: macOS reports `ru_maxrss` in bytes, Linux
in kilobytes.

The alternative of reading *instantaneous* RSS (`/proc/self/statm` on Linux,
`task_info` on macOS) was rejected for this pass: it needs a per-platform code
split written in hand-authored LLVM IR, whereas `getrusage`+offset-32 is one
uniform path. The cost is that `rss` is *peak* RSS, not the live value —
disclosed as a caveat.

## Decision

Emit `process.memoryUsage()` as a fixed-shape object (`memoryUsageType()`,
matching Node's field set and order, all fields `i64`). Populate it by
`getrusage(RUSAGE_SELF, buf)` into a stack buffer, loading the `i64` at offset
32; on Linux multiply by 1024 to normalize kilobytes → bytes. `calloc` zeroes
the struct, so the four V8-heap fields are left at 0 rather than fabricated.

## Implementation notes

- `emitProcessMemoryUsage` / `memoryUsageType` in `emit_process.go`; dispatch in
  `emit_call.go`; return-type inference in `emit_exprs_types.go`.
- `ensureGetrusage` declares `getrusage` once (`runtime_core.go`), guarded by a
  new `usedGetrusage` flag.
- The rusage buffer is over-allocated to 256 bytes (the struct is ~144) so the
  offset-32 load is always in bounds regardless of platform struct padding.

## Side effects discovered

None. The instantaneous-RSS and real heap-accounting fields remain follow-ups,
tracked as caveats on the status row.

## Verification

- `TestE2EProcessMemoryUsageRssPositive` (rss > 0; heap fields == 0) and
  `TestE2EProcessMemoryUsageWrongArgCountRejected`, both passing.
- `examples/process/process_info.ts` extended and run.
- Verified on macOS (Apple Silicon M4). Linux path (the ×1024 scaling) is
  compile-correct but not yet run on the x86-64 box.
