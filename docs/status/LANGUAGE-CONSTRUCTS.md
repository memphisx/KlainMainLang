# Language Constructs

> Part of the [Implementation Status](README.md) index. Covers control flow, operators, variable declarations, functions/closures, async/Promise, enums, interfaces, and classes/OOP.

**Coverage**: 63/65 rows on this page, ~97% (see the index's Coverage Summary for the breakdown by sub-category).

**Strict Coverage**: 34/65, ~52% — a row only counts here if it was independently repro-verified with zero known caveats or bugs, of any severity. See the 2026-08-11 audit ([ADR-00166](../adr/ADR-00166.md)) that produced this number; every caveat added by that audit excludes the row from this count even though the row stays ✅ in the Coverage column above.

**Caveats**: TDD-00009 is now fully implemented (Stages 0-4) — `class` has real single inheritance (`extends`/`super`), `static` members/`static {}` blocks, `private`/`protected` visibility (compile-time-only, matching real TypeScript's own erasure), `abstract` classes/methods, and `implements` (a compile-time-only structural self-check, not polymorphic dispatch through an interface type) — see [ADR-00083](../adr/ADR-00083.md) (Stage 3) and [ADR-00084](../adr/ADR-00084.md) (Stage 4). Real JS/TS `#x` runtime-private field syntax — a *different* mechanism from the `private` keyword modifier, with a real observable difference (genuine reflection-hiding, not just type-level erasure) — is now done too, see [TDD-00021](../tdd/TDD-00021.md)/[ADR-00155](../adr/ADR-00155.md). No class-field-initializer syntax at all yet (`#x = 1;` inline, private or public — every field, `#`-named or not, still needs an explicit constructor assignment), and no early-error validation for a `#name` colliding across static/instance in the same class, or `#constructor` specifically banned as a name (both real, narrow gaps found running the Test262 conformance harness against real-world `#`-using code, deferred rather than fixed). `async`/`await` is a synchronous resolved-slot read for everything except `await fetch(...)`, which is genuinely non-blocking (yields via a fiber inside an `http.listen` handler) — see [TDD-00006](../tdd/TDD-00006.md). Numeric separators, optional catch binding, and logical assignment operators are now done — see [ADR-00085](../adr/ADR-00085.md)/[ADR-00086](../adr/ADR-00086.md)/[ADR-00087](../adr/ADR-00087.md). Destructured function parameters are now done too — see [ADR-00109](../adr/ADR-00109.md). Getters/setters on classes are now done too — see [TDD-00030](../tdd/TDD-00030.md)/[ADR-00110](../adr/ADR-00110.md); object-literal getters/setters remain out of scope (an object literal's `Type` is pure structural value-equality with no name to hang an accessor table off). Nested function declarations are now done too, V1-scoped — see [TDD-00057](../tdd/TDD-00057.md)/[ADR-00149](../adr/ADR-00149.md). An unannotated function forward-referencing another unannotated, later-declared function's non-scalar return type ([ADR-00041](../adr/ADR-00041.md)'s originally-accepted boundary) is also now resolved by a bounded fixed-point re-inference sweep — see [TDD-00058](../tdd/TDD-00058.md)/[ADR-00150](../adr/ADR-00150.md); a genuinely circular pair of mutually-recursive unannotated functions still can't converge and keeps the old scalar-default fallback, not a new failure mode. Tagged template literals are now done too (desugared to a plain call; no `.raw` property on the `strings` array) — see [TDD-00059](../tdd/TDD-00059.md)/[ADR-00151](../adr/ADR-00151.md). Array-typed arrow-function/closure parameters (including rest params, and by extension an arrow function as a tagged-template tag) are also now fully supported, closing the gap ADR-00151 itself had only narrowed to a cleaner rejection — see [ADR-00152](../adr/ADR-00152.md). Function expressions support both the anonymous and named forms; a named function expression binds its own name inside its body for self-reference/recursion (a name shadowing a top-level function of the same name is the one remaining clean-error case) — see [TDD-00060](../tdd/TDD-00060.md)/[ADR-00168](../adr/ADR-00168.md)/[ADR-00178](../adr/ADR-00178.md). This compiler still has no general strict-mode parser context or block-scope (`let`/`const`-vs-`var`) redeclaration tracking, so 7 Test262 early-error cases around a literal `"use strict"` directive (reserved words as object-literal shorthand properties, a legacy octal escape in a directive prologue, block redeclaration, and one case with no literal `"use strict"` marker the harness can detect at all) stay unrejected; a narrower, unconditional-where-safe subset — duplicate parameter names, and a non-simple parameter list or `eval`/`arguments` as a parameter name specifically under a literal `"use strict"` directive — is caught.

See [ADR-00083](../adr/ADR-00083.md). `extends` now also accepts one built-in generic, `EventEmitter<T>` ([TDD-00023](../tdd/TDD-00023.md)/[ADR-00089](../adr/ADR-00089.md)) — a synthetic root never itself registered as a real class, so `extends` isn't exclusively a user-class-to-user-class relationship anymore. |
| `instanceof` (against user-defined classes) | ✅ | [TDD-00009](../tdd/TDD-00009.md) Stages 2-3 — every instance carries a hidden runtime type tag. A class-typed variable whose static class is `T` itself or an ancestor of `T` folds to a compile-time constant; one whose static class is an *ancestor* of the right-hand class (e.g. `const s: Shape = new Circle(...); s instanceof Circle`) needs a real runtime tag read, since the concrete subtype isn't known until then — same real check an `any`/`unknown`-typed value already needed. See [ADR-00067](../adr/ADR-00067.md) for the original unregistered-class compile-error behavior and [ADR-00083](../adr/ADR-00083.md) for the inheritance generalization; `instanceof` against `Error`/`TypeError`/etc. is a separate, sibling mechanism keyed off a different hidden tag — see the `Error` subtypes row above and [TDD-00013](../tdd/TDD-00013.md). `instanceof` against five built-in types (`Array`, `Map`, `Set`, `Date`, `RegExp`) is now done too — always a compile-time constant off the already-known static type, no runtime tag involved — but `instanceof Object` still isn't: real JS's "true for anything non-primitive" semantics would need an exhaustive, easy-to-drift enumeration of every object-shaped type this compiler has, a real risk the five concrete cases don't share. See [ADR-00162](../adr/ADR-00162.md). |

## Known Limitations

| Limitation | Notes |
|---|---|
| A `T \| null` where `T` is a non-pointer type (e.g. `number \| null`) has no real "is this null" runtime check | Both bare `??` (`emitNullCoalesce`) and the new `??=` ([ADR-00087](../adr/ADR-00087.md)) treat a non-pointer-typed value as never-null, so `let x: number \| null = null; x ?? 42` silently evaluates to `0`, not `42`. Found while building `??=`, not fixed — inherited as-is from `??`'s pre-existing behavior. A genuine fix needs a different runtime representation for nullable non-pointer types, not a narrow patch. |
| A class iterator's `next(): number \| null` whose legitimate first value is exactly `0` terminates immediately | The Stage 1a iterator protocol ([ADR-00063](../adr/ADR-00063.md)) uses a bare `0` as both "the number zero" and "iteration done," since nullable numbers have no separate null representation (same root cause as the row above). Affects both plain `for...of` over such a class and [`Array.from`](ARRAY-METHODS.md) draining one ([ADR-00088](../adr/ADR-00088.md)). Found while verifying `Array.from`, not fixed — work around by choosing an iterator whose real values never include `0` (e.g. start counting from 1), or fix would need the same different nullable-number representation as the row above. |
