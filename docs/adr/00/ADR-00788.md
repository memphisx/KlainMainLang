# ADR-00788: fs leaf batch — `readlinkSync` grow buffer, `copyFileSync` mode, `futimesSync`

- **Relations**: closes several `fs` leaves in BACKLOG §3 (extends [ADR-00497](ADR-00497.md) path ops / [ADR-00498](ADR-00498.md) fd ops / [ADR-00094](ADR-00094.md) copy); the Windows time shim follows [ADR-00755](ADR-00755.md)
- **Date**: 2026-09-08

## Context

A cluster of small, real `fs` gaps remained: `readlinkSync` used a fixed 4096-byte
buffer, `copyFileSync` rejected the `mode` argument, and `futimesSync` (the
fd-based `utimesSync`) was missing. Batched here.

## Decision

- **`readlinkSync` — unbounded target.** `__kml_fs_readlink` now grows its buffer
  (256, doubling) and retries `readlink` until the result fits strictly inside
  (`n < cap`), freeing each undersized attempt — no more 4096-byte cap, and the
  exact-boundary truncation can't happen. (In practice the OS caps symlink
  targets at `PATH_MAX`, so the old cap rarely bit; this removes the theoretical
  edge and the caveat.)
- **`copyFileSync(src, dest, mode)`.** `mode` is a runtime `i64` bitmask (works
  for a literal or a computed value). `COPYFILE_EXCL` (bit 1) is enforced by
  `__kml_fs_copy_excl_guard`, which opens `dest` with `O_WRONLY|O_CREAT|O_EXCL`
  (the "wx" flag bits) — atomically failing with a real `EEXIST` if `dest`
  exists, exactly as Node — then closes the freshly-created empty file that the
  existing binary-safe `read_file_raw`+`write_file_bytes` copy then fills. The
  `COPYFILE_FICLONE`/`FICLONE_FORCE` bits are best-effort copy-on-write hints and
  a faithful no-op here.
- **`futimesSync(fd, atime, mtime)`.** `utimesSync`'s fd twin — same seconds/
  `Date` time forms and the same two-`timeval` buffer, targeting an open fd.
  POSIX `futimes(2)`; a new win32 `kml_win_futimes` shim (`SetFileTime` on
  `_get_osfhandle(fd)`, mirroring the existing `utimes` shim) covers Windows.

## Fixed in passing

`fs.closeSync` was implemented and dispatched but missing from the named-import
allowlist (`resolver/virtual_modules.go`), so `import { closeSync } from 'fs'`
failed while `fs.closeSync` worked — added.

## Deliberately left (with reasons)

- **`rmSync` `maxRetries`/`retryDelay`** — a faithful retry needs restructuring
  the throw-based recursive `__kml_fs_rm` to be catchable-and-retryable; the
  retryable errors (`EBUSY`/`EPERM`/`ENOTEMPTY`) are Windows-centric and don't
  arise on the POSIX removal path in practice. Left rather than fake-accepted.
- **`fdatasyncSync` == `fsyncSync`** — macOS has no `fdatasync` (Node maps it to
  `fsync` there too), so the alias is already faithful on the verifying box; the
  Linux data-only optimization is not observable in a file's contents.
- **`birthtimeMs` = 0 on Linux (glibc)** — needs a `statx` syscall path; Linux-
  only and not verifiable from the Mac dev box.

## Verification

Verified on macOS/Apple Silicon against `node`: a 500-byte symlink target reads
back whole; `copyFileSync` overwrites by default and throws `EEXIST` under
`COPYFILE_EXCL`; `futimesSync` sets an fd's mtime (read back via `statSync`).
New `TestE2EFsCopyFileSyncModeExcl`/`…ReadlinkSyncLongTarget`/`…FutimesSync`, the
updated `examples/fs/fs.ts`, full `make test-par`, Node oracle. The win32
`futimes` shim compiles under the same source; its behavior rides the Windows CI
lane.
