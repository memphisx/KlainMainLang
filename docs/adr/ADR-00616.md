# ADR-00616: LockOSThread — the Node reactor is thread-affine under klain:sync

- **Relations**: `Extends ADR-00615`, `Implements TDD-00143`
- **Date**: 2026-09-01

## Context

`examples/goroutines/load_test.ts` runs an HTTP server inside a `klain:sync`
goroutine (`go(() => http.listen(...))`) and hammers it with a pool of worker
goroutines making synchronous `XMLHttpRequest` calls (ADR-00615). It
**intermittently deadlocked** — ~40% of runs at 2000 requests, multi-M only;
`GOMAXPROCS=1` was always clean.

## Investigation

`sample` on a hung process showed every worker goroutine busy-spinning in
`curl_multi_perform` (waiting for a response) and the **server goroutine
absent from every thread**. A gated stall-dumper added to the scheduler
(`ks_live`, per-P/per-M state) confirmed the server goroutine was *dead*:
`ks_live` had dropped by one, all live Gs were the busy-spinning workers, and
every run queue was empty.

A `dprintf` at the event loop's `alldone` exit printed `listen_fd=-1` at the
moment `http.listen` returned. `@__kml_listen_fd` (and `@__kml_conn_active`,
`@__kml_main_ctx`, `@__kml_conn_data`, `@__kml_current_conn_idx`) are
`internal thread_local` — **per-M, not per-goroutine**. `__kml_event_loop_run`
(runtime_http.go) keeps the loop alive only while `haslistener ||
hasactiveconns || …`. When the reactor goroutine is cooperatively preempted
(a safepoint in the compiled handler) and the work-stealing scheduler resumes
it on a *different* M, that M's thread-locals are their defaults —
`listen_fd = -1` → `haslistener = false` → the loop exits and the goroutine
returns, orphaning the live server. `GOMAXPROCS=1` has one M, so no migration,
so no early exit — exactly the observed asymmetry.

This is a Go-semantics violation: goroutine-owned state must travel with the
goroutine (Go keeps it in the `g`), never in TLS. The reactor is moreover
*thread-affine by construction* — its `ucontext` connection fibers are created
on one OS thread and cannot legally `swapcontext` on another — so the correct
Go primitive is `runtime.LockOSThread`, not per-field migration.

## Decision

Add `LockOSThread` to `klain:sync` and apply it to the reactor goroutine:

- `ks_g` gains `locked_m`; `ks_m` gains `locked_g` + a per-M mutex/condvar
  (`lmu`/`lcv`). `klainsync_lock_os_thread()` binds the current G↔M and flushes
  the M's local run queue to the global queue (the locked M will never pop its
  P again). `klainsync_unlock_os_thread()` reverses it (unused by the reactor,
  which owns its M for the process lifetime).
- A locked M runs **only** its locked G: `ks_findrunnable` returns that G when
  runnable and otherwise parks on `lcv` — it never pops its P, steals, or drains
  the global queue, so the locked G can be neither migrated nor stolen.
- `ks_ready` routes a locked G's wakeup to its M's `lcv` (set-status +
  signal under `lmu`, race-free) instead of a shared queue; `ks_execute`'s
  gosched/preempt re-ready keeps a locked G on its own M. sysmon skips
  preempt-flagging and stuck/rescue accounting for a locked G (its M is
  legitimately dedicated).
- `__kml_event_loop_run` calls `@__kml_reactor_thread_lock()` at entry — a
  wrapper that calls `klainsync_lock_os_thread()` when klain:sync is linked and
  is a no-op otherwise (and a further no-op off a goroutine, e.g. a normal
  main-thread server). Preemption is preserved: the locked reactor G still
  yields at safepoints, it just resumes on the same M.

## Implementation notes

`codegen/llvm/klainsyncsrc/klainsync.c` (struct fields, `ks_ready`,
`ks_findrunnable`, `ks_execute`, sysmon, the two public functions, per-M
lmu/lcv init for both regular and rescue Ms) and `codegen/llvm/runtime_http.go`
(the gated wrapper + the entry call). Non-goroutine and single-threaded HTTP
servers are unaffected (the lock no-ops). Only `http.listen` is locked today;
if other reactor entry points are ever driven from goroutines they need the
same treatment.

## Side effects discovered

A separate latent lost-wakeup exists in `ks_ready`: a G pushed onto a busy M's
*local* queue never signals parked idle Ms (only the global path does). It is
not fatal without a circular dependency, and was not the cause here; left as a
documented follow-up (a `wakep`-style fix was drafted and reverted for lack of
an isolating repro).

## Verification

Mac (Apple Silicon M4). The load-test pattern that reproduced the hang is now
**0 hangs across 30 runs at TOTAL=2000 and 15 runs at TOTAL=8000** (was ~40%),
with a genuine measured latency distribution (p50 1ms, p99 4.1ms, max 124ms,
~3400 rps). New regression test `TestE2EGoroutineHTTPListenLoadTest` passes
`-count=3`. Full goroutine/channel/select/XHR/HTTP/worker/fetch suites green;
64-way pure-goroutine stress against the external fixture unchanged (3000/3000).
