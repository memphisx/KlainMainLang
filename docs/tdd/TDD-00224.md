# TDD-00224: A module with a top-level `await` runs as a coroutine

- **Status**: Implemented
- **Notes**: Stage 1 (the entry program) shipped — [ADR-01050](../adr/ADR-01050.md); it let the finished module task's stack be reclaimed instead of pinning it, sized the Windows module stack from the linker's real 2 MiB reserve, and added a main-stack hand-off for a blocking `http.listen` in module code. Stage 2, Worker modules, shipped — [ADR-01055](../adr/ADR-01055.md) (a worker's `'error'` now carries the Error object, and a worker thread ends from its own stack, never a coroutine's). Stage 2, islands: §5 assumed the island shares the importer's runtime; it is a separate copy in a shared library, so the hand-off is a poll bridge from the importer's loop — [TDD-00225](TDD-00225.md)/[ADR-01056](../adr/ADR-01056.md). §3's tick branch is deleted; `@__kml_top_await` stays for its two non-module callers.
- **Date**: 2026-09-21

## Context

[TDD-00223](TDD-00223.md) §1 made a top-level `await` wait on the main stack by taking turns of the real event loop until the awaited promise's state word turns non-zero (`@__kml_top_await`). Its argument was that nothing is suspended beneath module top-level code, so there is "nothing to be ordered against". That is wrong in one observable way: the continuation of an `await p` is itself a *reaction on `p`*, and its position among `p`'s other reactions is visible.

```ts
const log: string[] = [];
const p = new Promise<number>((resolve) => setTimeout(() => resolve(7), 5));
p.then(() => { log.push("r1"); Promise.resolve().then(() => log.push("r1-child")); });
const v = await p;
log.push("top-" + v);
p.then(() => log.push("r2"));
await null;
log.push("end");
setTimeout(() => console.log(log.join(",")), 0);
```

Node: `r1,top-7,r1-child,r2,end`. This compiler: `top-7,r1,r2,end,r1-child` — the main-stack wait notices the state word after the loop turn in which the timer resolved `p`, before `p`'s reaction jobs have run. [ADR-01044](../adr/ADR-01044.md) patched the *settled / plain-value* case with a snapshot tick (`@__kml_microtask_tick`) and recorded the pending case as open.

Inside an async function none of this is wrong: `@__kml_task_await_ready`'s `ontask` branch registers the resume as a reaction in the promise's own list and parks (TDD-00088), so the order is Node's by construction. The defect is only that module top-level code is not a task.

This document amends TDD-00223 §1. §2–§5 of that document stand.

## Design

### Options

**(a) Module body as a coroutine.** What an engine does: the module is an async function; its evaluation promise settles when the body ends.

**(b) Keep the main-stack wait, make it a reaction.** The await registers a marker reaction on the promise; the microtask drain becomes interruptible and stops at the marker, returning to the waiting main stack. Rejected: the drain is entered from many places (loop iteration, task finish, fiber drives); each would need to unwind to the main-stack waiter from an arbitrary depth of callback frames that are *above* it on the same stack — impossible without abandoning those frames. It only works when the drain that reaches the marker is the one `@__kml_top_await` itself called, which is exactly the case that already works.

**(c) Main stack as the task, event loop on a fiber.** Keeps `main()` and its allocas in place, but every loop callback would then run on a fiber stack, the end-of-main loop would have to hand over to a loop instance suspended mid-iteration, and "is this the main stack" tests across the runtime (`@__kml_loop_turn`, the fetch waits, the connection-fiber guards) change meaning. Rejected: larger blast radius than (a) for the same result.

**Chosen: (a).**

### 1. Shape of the emitted program

Decided by a pre-pass, `programHasTopLevelAwait(prog)`: an `await` / `for await` whose nearest enclosing function is the module itself (not nested in any function, arrow, method or class static block body). A program without one is emitted exactly as today — byte-for-byte.

With one:

- The top-level statements are emitted into `define void @__kml_module_body(ptr %args)` — its own `allocas`/`body` builder pair — instead of `main()`. `%argc`/`%argv` are published to two internal globals by `main()`'s prologue before the spawn; top-level reads of them load the globals.
- `main()` keeps its prologue (stdio mode, cluster seed, uptime init, …), then:
  1. `P = @__kml_task_alloc_promise()`; `@__kml_spawn_module_task(@__kml_module_body, P)` — runs the body to its first park or to completion, exactly JS's "evaluate synchronously up to the first await";
  2. `@__kml_event_loop_run()` on the main stack, as the end of `main()` already does — the module task is resumed from inside it by its resume microtask, like any other task;
  3. after the loop returns: if `P` is still pending → the unsettled path (§4); otherwise the existing epilogue (cluster wait, exit handlers, exit code).
- The epilogue is emitted into `main()`'s builders after the split point. Anything the epilogue reads must be a global, never a register defined by a top-level statement (verify at implementation; today it reads only globals).

`hasMaySuspend` is already true for such a program (`programMayWait`), so every `await` in the module body takes the task-aware path with `@__kml_current_task` set: it parks as a reaction. The non-promise-operand case is the ordinary "wrap in a settled promise and park" path async functions use.

### 2. The module task is a task with three differences

`@__kml_spawn_module_task` shares `@__kml_spawn_task`'s body through a common internal helper taking `(fn, args, promise, stackBytes, flags)`:

- **Stack size.** Module top-level code today enjoys the process main stack; top-level recursion depth must not regress to `taskStackBytes` (256 KiB). The module task gets the platform's main-thread default (8 MiB; 1 MiB on Windows, matching the PE default). The task struct gains a `stackBytes` field (index 13); the GC stack-bottom computations that hard-code `taskStackBytes` (`@__kml_gc_set_task_sb`, the scheduler's resume) read the field instead. Memory: an untouched `malloc`ed 8 MiB region is not resident on Linux/macOS; on Windows 1 MiB of commit.
- **The stack is never freed.** Closures capture top-level `let`/`const` by pointer to the alloca, and they outlive the body (timers, servers). Today that is safe because `main()`'s frame lives for the whole process; the module task's stack gets the same lifetime — it is excluded from whatever reclaims finished tasks' stacks. One per process, so not a leak in any meaningful sense.
- **An uncaught throw is an uncaught exception, not a rejection.** `@__kml_task_trampoline`'s catch-all rejects the task's promise; for the module that would turn `throw` at top level into a silent rejected `P`. The module trampoline has no catch-all: the task's own jmpbuf stack is empty at entry, so an uncaught throw reaches the process-level uncaught path (`'uncaughtException'` listeners, message, exit code 1) exactly as it does from `main()` today.

`AsyncLocalStorage`: the module task inherits `@__kml_root_async_ctx` at spawn (the existing spawn rule) and *is* the root for everything it spawns afterwards; `als.enterWith` at top level writes the module task's field, which children inherit — equivalent to today's root semantics.

### 3. What is deleted

For a program with a top-level `await`, nothing reaches `@__kml_top_await`'s main-stack branch any more from module code, and the [ADR-01044](../adr/ADR-01044.md) tick (`@__kml_microtask_tick` from `emitAwait` / the settled entry of `@__kml_top_await`) is unreachable — the coroutine gives the same order for free. They remain only for the main-stack waits that are not module-body awaits: the synchronous body accessors (`.text()` on the main stack), and waits issued from inside a loop callback (result `2`). `emitAwait`'s "no enclosing async callable → tick" branch is deleted outright; whether `@__kml_top_await` keeps any caller is determined at implementation, and it is deleted if it has none.

### 4. Unsettled top-level await

The loop returns to `main()` only when nothing alive can wake it. If `P` is still pending then, `main()` calls `@__kml_tla_unsettled()` (warning on stderr, exit code 13). Node runs `process.on('exit')` listeners with code 13 in this case; verify what this runtime does today and match Node.

### 5. Dynamic-import islands and workers

- An **island** (`import()` target compiled as a shared library, TDD-00056) drives its top level by calling its `main()` from `__kml_dynmod_<hash>_init`, synchronously, from inside the importer — possibly from a loop callback or a task. An island's `main()` must not run an event loop. For an island with a top-level `await`, `init` spawns the module task and returns its promise `P`; the importer's `import()` promise adopts `P` (fulfils with the namespace object when `P` fulfils, rejects when it rejects — here the module trampoline *does* keep the catch-all, because a throwing imported module rejects the `import()` promise in Node). Stage 2.
- A **Worker** entry runs its own top level on its own thread with its own loop; it takes the same shape as §1 on that thread. Confirm how the worker entry is emitted (own `main`-like function vs shared) at implementation. Stage 2.

### Stages

1. Entry program: pre-pass, body/epilogue split, module task (stack size field, never-freed stack, no catch-all), unsettled path, deletion of the tick branch. Tests: the probe above, the ADR-01044 transcription, top-level throw after an await (message + exit 1), unsettled (exit 13), top-level recursion depth ≥ today's, `process.argv` at top level, `-mm=gc`, closures over top-level bindings firing after the body ended. IR-diff across `examples/` must show changes only in programs with a top-level `await`.
2. Islands and workers (§5).
