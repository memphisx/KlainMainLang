## Progress

- **Stage 1 (shipped, ADR-00651):** strict now cleanly rejects an incompatible *scalar
  reassignment* (`let x = 5; x = 'hi'`, untyped `let x; x = 1; x = 's'`) instead of emitting invalid
  IR — the guard fires exactly where the store would be type-invalid. Reclassifies ~7/10 of the
  target `language/expressions` invalid-IR cluster; the `: any` annotation is the working escape
  hatch. **This is narrower than full noImplicitAny:** `let x; x = 1` (single-type first-assignment
  inference) still compiles rather than being rejected at the declaration — closing that gap (reject
  an untyped-uninitialized binding outright) is Stage 2 and needs an examples/tests audit first.
- **Stage 2 (shipped, ADR-00653):** the `-compat=js` widening — an untyped scalar binding assigned two
  or more distinct scalar kinds is backed by the any-box from declaration (a per-scope pre-pass,
  `crossTypeWidenedBindings`), so `let x = 5; x = 'hi'` *works* under `-compat=js` while strict still
  cleanly rejects it. Single-kind bindings stay unboxed (no perf cost). Covers module globals (read by
  named functions) and function scopes. V1 edges: nested-closure reassignment of an enclosing binding,
  object/array bindings, and assignments nested in a larger expression are not widened.
- **Coerce-honesty bug (fixed, ADR-00652):** the `var x; x = undefined; x = (null ?? 42) || 43` slip
  was the `??` emitter, not `coerce` in general — for a nullish-literal left it built a `ptr` result
  slot and stored a non-ptr right (`coerce(number, ptr)` silently returning the number). Fixed: `null
  ?? x` / `undefined ?? x` yields the right operand's own type; a genuine ptr|non-ptr `??` union is a
  clean rejection via `coerceChecked`. The Test262 coalesce file that started the trace now compiles.

## Context

The invalid-IR backlog histogram (see the leverage scoping that produced
ADR-00650) found that its single largest scalar-into-`ptr` sub-family — ~41
`language/expressions` Test262 files, plus more in `language/statements` — is
one root cause: an **untyped binding reassigned across types**. The canonical
shape is Test262's coalesce/logical-assignment corpus:

```js
var x;
x = undefined;
x = (null ?? 42) || 43;   // number stored raw into the binding's ptr slot
```

Today an untyped, uninitialized `var`/`let` becomes implicit `any` (a dynamic
`{ i8, i64 }` box) **only under `-compat=js`** (emit_exprs_vardecl.go ~560,
TDD-00076 A1). In the strict baseline lane it instead falls through to a fixed
type (bare `let x;` → the `TypeI64` default; `var x = 5` → inferred `number`),
so a later assignment of a different type emits `store <fixedIR> <ptrOrScalar>`
— invalid IR clang rejects (`constant expression type mismatch: got 'ptr' but
expected 'i64'/'double'`, `floating point constant invalid for type`).

The machinery to *hold* a cross-type scalar already exists and works: an
explicitly annotated `let x: any = 1; x = 'hi'; x = true` compiles and prints
correctly today (the D1 dynamic box). This is therefore a **typing-policy
wiring gap**, not a new subsystem — the values already have a home; untyped
bindings just aren't routed to it, and inferred-typed bindings emit a bad store
instead of a clean rejection on an incompatible reassignment.

## Design

Two binding shapes, decided independently:

### 1. Untyped, *uninitialized* binding (`let x;` / `var x;`)

TypeScript itself types this implicit `any` (with `noImplicitAny` off) or
errors (with it on). The dynamic box already handles it under `-compat=js`.
Two viable strict-lane policies:

- **Option A — strict also infers implicit `any`.** Drop the `e.compatJS()`
  guard on the `TypeAny` assignment (line 560). Most faithful to plain TS/JS
  (these are valid programs), and makes the Test262 files *pass* rather than
  merely stop emitting bad IR. Cost: erodes the "strict = every type is
  known/annotated" identity; a typo'd `let x;` silently becomes `any`.
- **Option B — strict cleanly *rejects* an untyped-uninitialized binding**
  (mirroring `noImplicitAny`, the recommended TS setting), `-compat=js` keeps
  the implicit `any`. Matches the project's two-tier model (strict =
  clean-rejection, compat=js = JS bag-of-values) and still removes the invalid
  IR (reclassified to a clean compile error, like ADR-00650). Cost: the
  Test262 strict-lane files stay failing (as clean rejections, not passes).

**Recommended: Option A.** The faithfulness-first rule (observable semantics
win; diverge only on genuine impossibility) points here — the behavior is not
just possible but already implemented for the annotated case, and implicit
`any` is TS's actual default. The two-tier model's "strict clean-rejection" is
for constructs this compiler *can't* represent, not for ones it can. Revisit
only if implicit-any turns out to mask real bugs in the strict lane's own
corpus.

### 2. Untyped, *initialized* binding (`var x = 5; x = 'hi'`)

TS infers `number` here (NOT `any`) and reports the later `x = 'hi'` as a type
error. So this is *not* an implicit-any case:

- **Strict:** the inferred type stands; an incompatible reassignment is a clean
  **type-mismatch rejection** (today it emits invalid IR — the real bug). This
  is a faithful match to TS.
- **`-compat=js`:** JS has no such error; widen the binding to `any` on an
  incompatible reassignment (a *widening* pass — the binding's slot must then
  be a dynamic box from the start, so this needs a pre-pass that scans a
  binding's assignments to decide its representation, not a first-assignment
  decision). Larger; can be staged after the strict rejection lands.

### Assignment path

Once an untyped binding is `IsDynamic`, assignments must route through the
existing coerce-to-any/box-store path (the same one the annotated `let x: any`
assignment uses — emit_exprs_assign.go / emit_dynamic.go), not the bare
`store <IR>` path. `emitAssign` already dispatches on the symbol's type for the
nullable-scalar and union cases; add/confirm the `IsDynamic` arm covers a
plain (unconstrained) `any` local.

### Operators on `any`

Reads of these bindings feed operators. `+`/arithmetic on `any` is currently
`operator '+' on any/unknown is not yet supported` (a clean rejection). The
Test262 coalesce cluster mostly uses `??`/`||`/comparison, not `+`, so many
files unblock without it — but full coverage of the sub-family needs
operator-on-any, scoped as its own stage/TDD rather than folded in. Verify per
file which operators each surviving CLANG_ERROR uses before claiming closure.

## Open questions

- Option A vs B for the strict lane (recommended A) — the one policy call that
  needs sign-off before implementation, since it sets the strict-lane identity
  for untyped bindings.
- Does implicit-any-in-strict interact with definite-assignment analysis
  (TDD-00071/ADR-00210–00215)? An implicit-`any` `let x;` read before assignment
  should be `undefined` (the box's undefined tag), not a definite-assignment
  rejection — confirm the analysis exempts a dynamic binding.
- Staging: land item #1 Option A + item #2 strict rejection together (both pure
  wiring over existing machinery, and together they close the invalid-IR holes);
  defer operator-on-any and compat=js widening to follow-on stages.
