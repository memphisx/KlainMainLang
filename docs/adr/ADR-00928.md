# ADR-00928: Variadic `arguments` — reflect the actual call-time arguments

- **Relations**: `Implements TDD-00210`. `Extends ADR-00387` (the declared-params-only `arguments`), `ADR-00464` (class-method `arguments`), `TDD-00200` (boxed-element `any[]` arrays)
- **Date**: 2026-09-13

## Context

`arguments` was synthesized from a function's *declared* parameters only
(`synthesizeArgumentsObject`, emit_func.go — ADR-00387), and only when every
parameter shared one simple type. A function receiving more arguments than it
declares — `function f() { return arguments[0] + arguments[1] }` called as
`f(3, 4)`, or a `String.prototype.replace` replacer reading capture groups
positionally via `arguments` — saw a short (or empty) `arguments` and read out
of bounds. Mixed parameter types were a clean rejection. This is a real
Node-fidelity gap and the remaining blocker under the capture-group replacer
work (ADR-00922).

## Decision

`arguments` reflects the values *actually* passed: the declared parameters
followed by any overflow. Elements are heterogeneous, so `arguments` is a boxed
`any[]` (one NaN box per slot, reusing TDD-00200), and `arguments[i]` is `any`.

A function that reads `arguments` and has no explicit rest gains an implicit
trailing rest parameter `...__kml_arguments_rest: any[]`; the existing
rest-collection call ABI then delivers every overflow argument to it. At entry
`arguments` is built as the boxed declared parameters concatenated with the
already-boxed overflow. A function with an explicit `...rest` or a destructured
parameter keeps the V1 clean rejection (TDD-00210 open question).

## Implementation notes

- **Stage 1 (implicit rest).** `maybeAddArgumentsRestParams` appends the
  synthetic rest parameter, driven by a free-variable scan for `arguments`
  (`paramsUseArguments`). It is called at the *one* authoritative signature
  computation, `buildFunctionSig` (emitter.go), so the definition site and every
  call site agree on the now-variadic LLVM arity; it is idempotent because the
  re-inference sweep re-enters `buildFunctionSig`. `buildFunctionSig` types the
  synthetic rest's element as `TypeAny` (a normal rest defaults to `number`).
- **Stage 2 (build `arguments`).** `synthesizeArgumentsObject` was rewritten:
  read the rest array's data pointer + length, `malloc` a
  `(declared + overflow)`-slot i64 buffer, `emitBoxValue` each declared
  parameter into the leading slots, `memcpy` the already-boxed overflow after
  them, and bind `arguments` as `ArrayOf(TypeAny)`. It no longer requires
  homogeneous parameter types (the old restriction) — every declared-parameter
  shape (scalar/string/array/nullable/object/any) boxes through the one
  `emitBoxValue` path. Class methods, which register no synthetic rest, get the
  boxed declared parameters (non-variadic) — a strict improvement over the old
  homogeneous-only synthesis.
- **Stage 3 (callback ABI).** Function expressions gain the same implicit rest
  (`emitFunctionExpression`), mirrored in `inferExprType`'s `FunctionExpression`
  case so the callback-value's inferred type carries `FuncHasRest`; both special
  case the synthetic rest's element type to `TypeAny`. `emitCBCall` packs the
  trailing arguments into the rest slot (`packBoxedRestArg`) for both the
  closure and named-callback kinds. HOF argument-sequence builders now consult
  `Callback.acceptsArgAt` instead of a bare `arity() >= n` check, so an
  `arguments`-using callback still receives the index/array extras; the
  `String.replace` path builds the full `(match, caps…, offset, string)`
  sequence when the replacer has a rest. Arrow functions are excluded (real JS
  arrows have no own `arguments`).
- **Boxing gotcha.** `packBoxedRestArg` uses `emitBoxValue`, not `coerce`: a NaN
  box is itself an `i64`, so `coerce`'s IR-equality shortcut passed an
  `i64`-typed value (a HOF index) through *unboxed*, storing a raw integer where
  a box was expected. The direct-call rest path avoids this only because it
  boxes via `emitExprWithObjectHint` at the AST level; the callback path works
  from already-evaluated `Value`s and must box explicitly.
- **Return-type inference.** A function's un-annotated return type is inferred at
  registration time, before `arguments` is a bound symbol, so
  `return arguments[0] + arguments[1]` inferred its element as the scalar
  default and picked a lossy concrete return type — the boxed string-concat
  result was then coerced to a number (returned `0` instead of the concatenated
  string). `inferUnannotatedReturnType`/`…Params` now bind `arguments` as
  `any[]` in the inference scope (keyed off the synthetic rest parameter's
  presence, via `defineArgumentsForInference`), so the `+` infers `any` and no
  lossy coercion is inserted.
- **`let`/`var` regex capture count (extends ADR-00922).** The static
  capture-count scan (`constRegexLiteral`) admitted only a `const` regex-literal
  binding, so a replacer whose pattern is a `var`/`let` (the S15.5.4.11_A4
  files) fell to the `(match, offset, string)` narrowing and never received the
  capture groups. It now also admits a `let`/`var` regex-literal binding, gated
  on a one-time reflective reassignment pass (`collectReassignedIdents`): the
  binding is honored only if the name is never an assignment target or `++`/`--`
  operand anywhere in the program (a reassigned binding stays capture-unknown —
  sound, verified).

## Side effects discovered

- `const n = x as number` where `x` is `any` did not narrow the binding to
  `number` (an explicit `: number` was needed) — a pre-existing `as`-cast
  inference limitation surfaced by the `arguments` example. **Fixed** in
  [ADR-00929](ADR-00929.md): `as T` now narrows a dynamic operand to the
  asserted concrete type.

## Consequence for the String.replace files (honesty)

The four `built-ins/String/prototype/replace/S15.5.4.11_A4_T*` Test262 files now
**pass under `-compat=js`** (verified via the repro harness): populating
`arguments`, the callback ABI, the return-type inference fix, and the `var`
capture-count extension together close them. `arguments[i]` is `any`, so their
`arguments[2] + arguments[1]` is an operator on `any` — which only `-compat=js`
supports; under **strict** these files cleanly reject at that operator (a
documented `any` limitation), moving from a runtime near-miss to an honest
rejection. Variadic `arguments` is worth doing on its own merits, for every
`arguments`-reading function.
