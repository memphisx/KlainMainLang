# ADR-00092: `setImmediate(fn)` / `clearImmediate(id)`

- **Relations**: Extends [ADR-00031](ADR-00031.md)
- **Date**: 2026-08-03

## Context

`docs/status/TIMERS.md`/`README.md` flagged `setImmediate`/`clearImmediate` as a small, already-unblocked follow-on — its stated prerequisite (the timer-queue mechanism from `setTimeout`/`setInterval`, ADR-00031) already shipped. Picked as a quick follow-up to the `in` operator (ADR-00091), chosen for its small footprint given limited remaining session budget.

## Investigation

Read `emit_timers.go` in full — `__kml_timer_schedule(closure, delayMs, intervalMs)` already accepts `delayMs=0` and fires as soon as the drain loop next scans the queue (its fire time is simply "now"). `__kml_timer_drain`'s scan loop has no concept of distinct phases (it's a single flat "find the pending entry with the smallest fire time" loop) — unlike real Node/libuv, which runs `setImmediate` callbacks in a dedicated "check" phase, guaranteed to fire before a same-tick `setTimeout(fn, 0)` when both are scheduled from inside an I/O callback. Given this compiler's simpler single-queue design, `setImmediate(fn)` and `setTimeout(fn, 0)` are genuinely indistinguishable at the mechanism level — not a gap to design around, since there's no phase concept anywhere in this event loop for either to distinguish itself against.

## Decision

`setImmediate(fn)` is `emitSetTimeout`'s exact call shape with `delayMs` hardcoded to the literal `0` and no delay argument accepted at all (real Node's `setImmediate` doesn't take one either) — same `timerCallbackPtr` validation (zero-arg, void-returning closure), same `__kml_timer_schedule` call, same `i64` id return type. `clearImmediate(id)` is `clearTimeout`/`clearInterval`'s existing `emitClearTimer` helper called with a different name string for its error messages — no new runtime function at all, since cancellation-by-id is already name-agnostic.

The real-Node phase-ordering guarantee (`setImmediate` before same-tick `setTimeout(fn,0)`) is explicitly *not* replicated — documented as a known, deliberate scope narrowing in `docs/status/TIMERS.md` rather than silently assumed to hold.

## Implementation notes

Files touched: `codegen/llvm/emit_timers.go` (new `emitSetImmediate`), `codegen/llvm/emit_call.go` (two new dispatch cases, `setImmediate`/`clearImmediate`, in the same bare-global-function switch `setTimeout`/`clearTimeout` already live in), `codegen/llvm/emit_exprs_types.go` (`setImmediate` added to the existing `setTimeout`/`setInterval` → `TypeI64` case).

No new AST nodes, no new runtime IR (`runtime_*.go` untouched) — the entire feature is two small Go functions reusing existing declared C symbols.

## Side effects discovered

None.

## Verification

- `go build -o klainmain .` clean.
- `go test ./...`: all passing, no regressions.
- 6 new tests in `tests/timers_test.go`: fires after sync code, fires before a later `setTimeout`, `clearImmediate` cancels before firing, and 3 negative cases (wrong arg count on `setImmediate`/`clearImmediate`, non-function callback).
- `examples/timers/timers.ts` extended (`setImmediate` firing + a cancelled one); compiled, run, and output confirms `"immediate fired"` prints immediately after synchronous code, before any `setTimeout`/`setInterval` output, and the cancelled one never prints.
