# ADR-00894: URLSearchParams array accessors return via out-parameter (Windows x64 struct-return ABI)

- **Relations**: `Extends ADR-00873`
- **Date**: 2026-09-12

## Context

The Release CI failed on **windows-x64** with `exit status 0xc0000005` (access
violation) in three new URLSearchParams tests — `TestE2EURLSearchParamsDuplicateKeys`,
`MultiValueAndOrder`, `Iteration` — while every POSIX lane (macOS/Linux, both
arches) passed. These are new tests from the URL/URLSearchParams overhaul
(TDD-00203/ADR-00873), so this is their first Windows run, not a pre-existing
regression. (A separate Windows-only failure, `TestE2EStdoutFlushesIncrementally`,
is the incremental-stdout item and unrelated.)

## Investigation

The three crashing tests share one trait: they call `getAll`/`keys`/`values` or
iterate — the accessors that return the 16-byte `kml_arr` (`{ void*, int64_t }`)
**by value**. The passing URLSearchParams tests (`toString`, `set`, `append`,
`sort`) return a string pointer or void. A codebase-wide grep confirms these are
the **only** four C functions declared to return `{ptr, i64}` by value
(`declare {ptr, i64} @__kml_usp_{get_all,keys,values,entries}`); every other
array-returning path is inline IR or already uses an out-parameter.

A two-eightbyte struct return is ABI-divergent on x86-64: the **System V** ABI
(Linux/macOS) returns it in RAX:RDX, which matches the emitted IR's `{ptr,i64}`
register return, so it works; the **Windows x64** ABI returns a >8-byte struct
via a hidden `sret` pointer, so clang lowers the C *definition* to
`void @f(ptr sret, …)` while the IR *caller* still reads two registers — caller
and callee disagree, producing the access violation. This is the unique place
the by-value aggregate return was introduced (ADR-00873), hence the unique crash.

## Decision

Return the array through a caller-provided out-parameter — one ABI on every
target. The four C functions become `void __kml_usp_X(kml_arr *out, …)` writing
`out->ptr`/`out->len`; their IR declares become `declare void @__kml_usp_X(ptr,
…)`; and each call site (`getAll` inline, and the shared `uspArray` helper for
`keys`/`values`/`entries`) allocas a `{ptr,i64}`, passes its pointer, and loads
the result. The consumed value shape (`ArrayOf(...)`) is unchanged.

## Implementation notes

- The out-parameter is the first argument, matching the common sret convention;
  the `{ptr,i64}` alloca is an ordinary entry-block slot loaded right after the
  call.
- No other `{ptr,i64}`-by-value C return exists, so this is the complete fix for
  the pattern; a guard could be added later if the pattern recurs.

## Verification

- POSIX (macOS arm64): `getAll`/`keys`/`values`/`for…of`/`toString` all produce
  the correct output after the change; full `TestE2EURL*` suite green; `go
  build`, `go vet ./...`, gofmt clean; full `make test-par` + `make examples`
  (296/296) run.
- **Windows verification is pending** — no Windows VM is available in this
  environment. The fix is an ABI-safety change with an airtight rationale (the
  unique by-value 16-byte struct return, the exact set of crashing tests), and
  is correct-and-verified on POSIX; the Windows crash should be resolved when
  next built on the Windows box.
