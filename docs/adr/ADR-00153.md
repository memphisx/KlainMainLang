# ADR-00153: Test262 full-corpus conformance harness (TDD-00008 Design V2)

- **Relations**: Implements [TDD-00008](../tdd/TDD-00008.md) (Design V2)

## Context

TDD-00008 V1 hand-curated which upstream conformance files were "worth" porting into `compiler_test.go` — after roughly a month, 6 tests out of a combined 53,872 upstream files across both suites. Revisited on the premise that hand-curation was itself the problem: coverage against an *external* benchmark stayed self-reported, since whatever wasn't judged worth porting never became a tracked number at all. See TDD-00008's own "Design V2" section for the full design (fetch mechanism, harness architecture, classification rules, report shape) — this ADR records what was actually built and found running it, not a repeat of that design.

## Decision

Built as designed in TDD-00008 V2: `tools/conformance/fetch.sh` clones `tc39/test262` (pinned by commit SHA — the upstream repo has no versioned release tags, confirmed directly against the remote, so a SHA is the real reproducibility mechanism, not a tag as the TDD's own prose assumed) into a gitignored `.test262/`; `tools/conformance/main.go` walks the full, unfiltered corpus, compiles each file through this repo's own existing pipeline (`parser.Parse` → `llvm.NewEmitter`/`EmitProgram` → `clang`, the same sequence `tests/compiler_test.go`'s `buildBinary` already uses), classifies negative/positive per Test262's own frontmatter, and generates `docs/testing/CONFORMANCE-RESULTS.md`.

**One design decision needed a real-time correction the TDD didn't anticipate**: running the harness unmodified against the raw upstream corpus showed 0/45 even on `left-shift` (already fixed and verified working, ADR-00047) — because the *shared harness* (`sta.js`) is itself a prototype-based pseudo-class with dynamic property assignment (`Test262Error.prototype.toString = function(){}`, `Test262Error.thrower = function(){}`), which this compiler's type system can't represent at all. Every file would have failed identically on the harness, before ever reaching its own test content — not real per-file signal, just one restated "this compiler doesn't do vanilla JS" bucket. Checked with the user rather than silently deciding either way (this cuts against the TDD's own "no source transformation" principle, which was written before this was known): approved approach was to add a compiler-compatible shim for exactly the two universal harness files (`tools/conformance/harness-shim/{sta,assert}.js`), reimplementing their *observable* behavior with real `class`/typed functions, while every actual test file stays 100% unmodified.

The shim itself needed two more empirically-found workarounds, neither assumed up front:
- Test262's `assert` is simultaneously callable (`assert(x)`) and a property namespace (`assert.sameValue(...)`) — real JS's function/object duality, which this compiler has no representation for at all. Kept the namespace form only (a `class assert` with `static` methods) — measured directly against the corpus that it covers ~68% of `language/` files vs. ~12% using the bare-call form; a file using only the bare form fails to compile against the shim (`undefined function 'assert'`), a real and visible gap, not silently patched.
- `assert.sameValue`/`.notSameValue`/`.throws` need a parameter type covering "any test value." Bare `any`/`unknown` is rejected as a parameter type outright; a per-method generic type parameter doesn't parse on a class method at all (confirmed directly: `static sameValue<T>(...)` gives `expected :, got <`). A *constrained* union (`number | string | boolean`) works — `isUnconstrainedDynamic` only rejects the bare/unconstrained form (`codegen/llvm/emit_dynamic.go`) — used instead; a call passing an object/array/null fails to compile at that specific call site.

## Side effects discovered

Running the harness surfaced three real, small, scoped compiler bugs, fixed immediately per the project's standing "fix now, or track it" rule (all three are the identical root cause, found incrementally): `emitStaticMethodCall` (`ClassName.staticMethod(...)`, `codegen/llvm/emit_classes.go`) is a wholly separate function from `emitClassCall` (instance methods), and had never received any of the fixes ADR-00152 gave the latter — no default-parameter-value fallback (`sig.Defaults` was written by `buildParamSig` but never read here), no rest-parameter support, no array-typed-parameter `(ptr, i64)` decomposition. All three ported over, mirroring `emitClassCall`'s already-fixed shape exactly rather than inventing a fourth copy of the same logic. Found via the shim's own `assert.sameValue(actual, expected, message)` calls in real Test262 files routinely omitting the optional trailing `message` argument — an extremely common, ordinary call shape, not an edge case.

Several large, real, previously-undocumented feature gaps surfaced too — not fixed here (each is real, independent design/implementation work), added to `docs/status/README.md`'s "What Is NOT Implemented" instead of left as only a number in the generated report: function expressions (`var f = function(){}`, IIFEs — by far the single largest failure bucket, ~13,300 of ~53,600 files), calling the result of a call directly (`f()()` — ~2,600 files, also independently confirmed via TDD-00057's own nested-function work this session), no generic object-to-string conversion at all (`` `${obj}` ``, bare `console.log(obj)` for a class instance both fail — real JS's `[object Object]` default isn't implemented in any form), and `class` expressions (~1,400 files).

## Verification

- `go build`, `go vet ./...` (`tools/conformance` included), full `go test ./...` — all pass, plus three new tests for the static-method fixes (`TestE2EStaticMethodDefaultParam`, `...RestParam`, `...ArrayParam`, `tests/classes_test.go`).
- Smoke-tested against `test/language/expressions/left-shift` (a category with already-known-correct behavior, ADR-00047) before the full run, to validate the classification logic itself — went from 0/45 (harness-blocked) to 12/45 once the shim was in place, with a genuinely diverse, informative failure distribution (not one dominant bucket) confirming real per-file signal.
- Full run: 53,578 files (`_FIXTURE.js` include-only files excluded, not real tests) in well under a minute, 16 parallel workers. **4,475 / 53,578 passed (8.4%)** — `language/` alone (the category closest to "core language," 23,724 files): 4,376 passed (18.4%). Read alongside the report's own methodology note: a large share of the remaining failures are the shared harness's own known limitations (the ~12% bare-`assert` files, `assert.throws`'s unverified error-kind check, no `compareArray`) or this compiler's deliberate non-goal of vanilla-JS engine compatibility (`eval()`-based assertions, TDD-00022 not started) rather than per-feature correctness gaps — the report's "most common failure reasons" table is what makes that distinction legible per-bucket instead of collapsing everything into one percentage.
- Spot-checked several individual failure buckets by hand against real `klainmain` output (not just trusting the aggregate number): confirmed `unknown class 'Boolean'` (boxed primitive wrapper objects, genuinely unimplemented), and confirmed the object-stringification gap independently of any test262 file (`console.log(new Foo())` fails identically).
