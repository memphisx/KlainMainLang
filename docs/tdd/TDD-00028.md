# TDD-00028: Array/Map/Set/EventEmitter literals as general expressions

- **Status**: Implemented
- **Date**: 2026-08-05

## Context

`emitExpr`'s core dispatch (`codegen/llvm/emit_exprs.go:56-65`) has no real case at all for `*ast.ArrayLiteral`, `*ast.NewArrayExpression`, `*ast.NewMapExpression`, `*ast.NewSetExpression`, or `*ast.NewEventEmitterExpression` — every one of them unconditionally returns a compile error ("array literal must be used in a variable declaration", etc.) the instant any of these appears anywhere other than directly as a `const`/`let` initializer. Concretely, none of these compile today:

```ts
first([1, 2, 3]);                          // array literal as a call argument
function make(): number[] { return [1, 2]; } // array literal as a return value
const box = { data: [1, 2, 3] };            // array literal as an object-literal field value
arr = [1, 2, 3];                            // plain reassignment (no let/const)
const nested = [[1, 2], [3, 4]];            // array literal as an element of another array literal
```

Found while implementing generics ([ADR-00103](../adr/ADR-00103.md)) — `first([1,2,3])` failed identically to a plain, non-generic `firstNum([1,2,3])`, confirming this has nothing to do with generics. It was already a known, named boundary before that: [ADR-00057](../adr/ADR-00057.md) found the exact same restriction blocking `number[][]` literals (needed for `.flat()`/`.flatMap()`) and documented it in `docs/status/ARRAY-METHODS.md` as a "known limitation." Revisited now at the user's explicit request, and with a sharper framing: this isn't a documented edge case a user could reasonably be expected to already know about — `[1,2,3]` failing to pass as a function argument is a basic, unannounced ergonomics gap in the middle of the language's most common data shape. It gets a real TDD and a real fix, not another "known limitation" footnote.

## Investigation

Read `emit_arrays_core.go`'s `emitArrayVarDecl` (`:8-116`) and `emit_collections.go`/`emit_eventemitter.go`'s `emitMapVarDecl`/`emitSetVarDecl`/`emitEventEmitterVarDecl` to understand *why* the restriction exists — it's not the same restriction for all four forms, which matters for scoping the fix:

- **`Map<K,V>`/`Set<T>`/`EventEmitter<T>`**: trivial under the hood. `new Map<K,V>()` etc. already compute a single heap pointer (`call ptr @__kml_map_str_create()`/`@__kml_map_num_create()`) and only write it into an alloca because the *caller* (`emitMapVarDecl` etc.) is hardwired to a `*ast.VarDeclaration`. As a general expression, this needs no new codegen at all — just an `emitExpr` case that runs the same heap-pointer-creation logic and returns `Value{Ref: heapPtr, Ty: ty}` directly, skipping the alloca/store.
- **Array literals (`[...]`) and `new Array<T>(n)`**: a real gap, not just missing plumbing. `emitArrayVarDecl` writes the malloc'd data pointer and the length directly into two *caller-supplied* allocas (the "Named Symbol" representation — `Symbol{Ptr, LenPtr}`, see the project's own Array value duality note) — there is no existing code path that builds an array literal's malloc+populate loop and hands back a single `{ptr, i64}` **aggregate** `Value` (the other legal array representation this compiler already has and uses everywhere else — e.g. a function returning an array already does exactly this via `insertvalue`, and `emitArrayVarDecl`'s own `*ast.CallExpression` branch at `:47-60` already *consumes* one via `extractvalue`). The aggregate-producing side of that round trip simply doesn't exist yet for a literal.
- **Element-type context**: `emitArrayVarDecl` gets its element type for free from the var-decl's own resolved/inferred type before it's ever called. A general expression usually doesn't have that — `first([1,2,3])` needs the literal's element type inferred from its own first element (exactly what `inferArrayType`, `emit_exprs_types.go:99-112`, already does — it's just never wired into `emitExpr` itself), while a context with a known target type (a declared parameter, an object literal field with a declared array-typed field) should coerce against that target instead, the same hint-propagation shape `emitExprWithObjectHint`/TDD-00007 already established for object literals.
- Confirmed the same gap also blocks plain reassignment (`arr = [1,2,3]`, no `let`/`const`) — `emit_exprs_assign.go` has no `*ast.ArrayLiteral` case on the right-hand side either, so it falls through to the same `emitExpr` dead end.
- Confirmed (via `ADR-00057`'s own investigation, re-verified) that a *nested* array literal (`[[1,2],[3,4]]`) hits this identical wall for its inner literals — they're just array-literal elements of an outer array literal, evaluated via the same blocked `emitExpr` path. Fixing this TDD's scope therefore also directly unblocks `.flat()`/`.flatMap()` (`docs/status/ARRAY-METHODS.md`'s two remaining ❌ rows), without needing any array-methods-specific work of its own.

## Design

Two independent fixes, different difficulty, worth landing separately (Map/Set/EventEmitter first — small, low-risk — array literals second — the real work):

### Map<K,V> / Set<T> / EventEmitter<T> as general expressions

Add `emitExpr` cases for `*ast.NewMapExpression`/`*ast.NewSetExpression`/`*ast.NewEventEmitterExpression` that factor the existing heap-pointer-creation logic out of `emitMapVarDecl`/`emitSetVarDecl`/`emitEventEmitterVarDecl` into a small shared helper each (e.g. `emitMapCreate(keyTy, valTy) (string, error)` returning the heap pointer register), called both by the var-decl path (store into the alloca, as today) and the new general-expression path (return `Value{Ref: heapPtr, Ty: ty}` directly, no alloca). No aggregate/hint machinery needed — same shape as any other single-`ptr`-valued expression already handled.

### Array literals / `new Array<T>(n)` as general expressions

New `emitArrayLiteralValue(lit *ast.ArrayLiteral, hintElemTy *Type) (Value, error)` (naming TBD during implementation): runs the same malloc-and-populate-a-loop logic `emitArrayVarDecl` already has (`:98-115`, plus the existing `emitSpreadArrayLit` path for spread elements), but instead of storing the resulting data pointer/length into caller-supplied allocas, builds and returns the `{ptr, i64}` aggregate via two `insertvalue`s — the exact shape a call already returns for an array-typed return value, so every existing *consumer* of that aggregate (`emitArrayVarDecl`'s own `*ast.CallExpression`/generic-expression branches, `resolveArrayForHOF`, array-typed call-argument passing in `emit_call.go`) needs no changes at all to accept a literal built this way.

Element type resolution: `hintElemTy` non-nil when the surrounding context already knows the target element type (an array-typed function parameter via `emitExprWithObjectHint`-style hint propagation, extended to array types the same way it already covers object types for TDD-00007; an object-literal field declared as an array type; a declared var-decl type) — coerce every element against it. `hintElemTy` nil falls back to `inferArrayType`'s existing first-element-inference rule (already the array literal's established convention, unchanged). `new Array<T>(n)`'s dynamic-size form gets the same aggregate treatment as its own small, separate case (currently `emitArrayVarDecl:24-36`, calloc-based).

Wire the new function into `emitExpr`'s `*ast.ArrayLiteral`/`*ast.NewArrayExpression` cases (replacing the unconditional errors) and into `emit_exprs_assign.go`'s assignment right-hand side. `emitArrayVarDecl`'s own existing direct-into-allocas literal path can either keep being a separate, marginally cheaper fast path (avoids one `insertvalue`+`extractvalue` round trip for the extremely common var-decl case) or be unified to call the new general helper and extract from its result, same as the `*ast.CallExpression` branch already does — an implementation-time call, not a design-blocking one; both are correct.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `{ptr, i64}` aggregate array representation | ✅ already exists | Already produced by array-returning function calls, already consumed by `emitArrayVarDecl`'s `*ast.CallExpression` branch and `resolveArrayForHOF` — this TDD adds a second *producer* (a literal), not a new representation |
| `inferArrayType` (first-element inference) | ✅ already exists | `emit_exprs_types.go:99-112` — reused as-is for the no-hint case |
| Hint-propagation mechanism (`emitExprWithObjectHint`) | ✅ exists for object literals ([TDD-00007](TDD-00007.md)/[ADR-00077](../adr/ADR-00077.md)) | Needs extending to cover array-typed hints too (or a parallel array-hint variant) — the mechanism/precedent exists, the array-specific plumbing doesn't yet |
| `Map<K,V>`/`Set<T>`/`EventEmitter<T>` heap-pointer creation | ✅ already exists | `emitMapVarDecl`/`emitSetVarDecl`/`emitEventEmitterVarDecl` — needs factoring out of the var-decl-specific function, not new logic |
| `emitSpreadArrayLit` (spread elements in a literal) | ✅ already exists | `emit_arrays_core.go:121` — needs the same allocas-vs-aggregate generalization as the non-spread path |

## Open questions

- ~~Exact naming/shape of the new array-literal-as-expression function and whether `emitArrayVarDecl`'s literal path is unified with it or kept as a separate fast path~~ Resolved during implementation: `emitArrayLiteralAggregate`/`emitNewArraySizedAggregate` (`codegen/llvm/emit_arrays_core.go`), and `emitArrayVarDecl` *is* unified to call through them (extracting via `storeArrayAggregateInto`) — see [ADR-00104](../adr/ADR-00104.md).
- ~~How array-typed hint propagation should be threaded alongside the existing object-typed `emitExprWithObjectHint`~~ Resolved: extended the existing function in place (kept its name despite now covering both hint kinds, to avoid an unnecessary mechanical rename across its many existing call sites) — see [ADR-00104](../adr/ADR-00104.md).
- ~~Whether this TDD's fix should also explicitly close out `.flat()`/`.flatMap()`, since nested-array-literal support is a direct, no-extra-design-needed side effect of this fix~~ Resolved, and the premise was wrong: confirmed directly during implementation that a nested array literal (`[[1,2],[3,4]]`) hits a *separate*, real storage-representation gap — an array's backing buffer is a flat sequence of fixed-width, scalar/pointer-sized slots, but a nested array element's own value is a 16-byte `{ptr,i64}` pair that doesn't fit in one such slot without a boxing/indirection layer this compiler doesn't have. Not a free win. Split out into [TDD-00029](TDD-00029.md); this TDD instead added a clean, deliberate compile-time rejection for a nested array literal rather than leaving the confusing clang-stage type-mismatch error that direct testing found. `.flat()`/`.flatMap()` stay ❌, now tracked against TDD-00029 instead of this TDD.
- `new Map<K,V>()`/`new Set<T>()`/`new EventEmitter<T>()` as a call *argument* or return value still needs the receiving context to know `K`/`V`/the element type the same way a var-decl's own annotation provides it today (these have no literal elements to infer from, unlike arrays) — resolved as: not needed for V1. These three already have sensible defaults (string keys/number values for `Map`, string elements for `Set`, `ptr` payload for `EventEmitter`) matching their own var-decl defaults, and an explicit `<K,V>`/`<T>` type argument is always available at the construction site itself (`new Map<string, number>()`) regardless of surrounding context — so, unlike an array literal (which has no per-instantiation syntax to pin its element type other than context), there was no real gap left to fix here. No hint-propagation extension was needed for these three.
