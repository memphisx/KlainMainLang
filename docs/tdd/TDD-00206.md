# TDD-00206: Default-parameter filling through first-class function values

- **Status**: Implemented

## Context

Default parameters (`function f(a, b = 10)`) are filled correctly only when the
callee is statically identifiable at the call site:

- **Named function** (`emitCallToFuncSig`, `emit_call.go`) — fills from
  `sig.Defaults`, with a `paramDefaultScratch` scope so a later default can
  reference an earlier parameter (`b = a`).
- **Class method / constructor** (`emit_classes.go`) — same `sig.Defaults` +
  `paramDefaultScratch` path.
- **IIFE** (a literal `FunctionExpression` callee) — [ADR-00911](../adr/ADR-00911.md)
  pads the argument list from the literal's own `Param.Default` expressions.

A call through a **first-class function value** — a closure bound to a variable,
stored in a field, or passed around — goes through `emitClosureCallByPtr`
(`emit_func.go`), whose argument loop runs only `i < regularCount && i < len(args)`.
When a trailing parameter is omitted it emits a `call` with fewer operands than
the function's LLVM arity:

```ts
const f = function (a: number, b: number = 10): number { return a + b; };
console.log(f(5));               // clang: not enough parameters specified for call

const g = (a: number, b = 7) => a + b;
console.log(g(3));               // same
```

This is not a Test262 exotic — it is the everyday `const f = function(a, b = …)`
shape, and the residual `meth-dflt-params-ref-{later,prior,self}` Test262 files
are the stored-method variant. The closure `Type` carries `FuncParams` (the param
*types*) but neither the parameter *names* nor the *default expressions*, so the
call site has nothing to fill from.

## Design

Two mechanisms are possible; they differ in *where* a default is evaluated.

### Option A — carry defaults on the closure `Type`, fill at the call site

Add the parameter names and default expressions to the function `Type`
(`FuncParamNames []string`, `FuncParamDefaults []ast.Expression`), populated when
the closure *value* is built (arrow / function-expression emission). Then
`emitClosureCallByPtr` fills omitted trailing parameters exactly like the named /
class / IIFE paths already do, reusing the existing `paramDefaultScratch` for
sibling-parameter references.

- **Pros**: reuses the proven call-site machinery verbatim; no ABI change; no
  change to how closure *bodies* are emitted; incremental and low-risk; the
  `Type` already flows intact through a `const f = …` binding (that is how
  `FuncHasRest` survives today).
- **Cons**: a default is evaluated in the **caller's** scope, not the closure's.
  This is observably wrong only when a default expression references a variable
  captured from the closure's *defining* scope (`let base = 1; const f = (x = base) => …`)
  — the caller may not have `base` in scope, or may have a different `base`.
  Constant defaults, and defaults referencing earlier *parameters* (via the
  scratch scope), are correct. This is the same limitation [ADR-00911](../adr/ADR-00911.md)
  already accepts for the IIFE path.

### Option B — body-prologue filling with an argument-presence mask

Every function with ≥1 default gains a hidden trailing `iN argmask` parameter.
The caller passes zero/undefined values for omitted slots plus the mask (it knows
the arity statically). The function *body* prologue, for each defaulted
parameter `i`, does `if !(mask >> i & 1) { paramSlot = eval(default) }` — the
default evaluated inside the function's own scope.

- **Pros**: fully faithful — defaults see the closure's captured environment,
  `this`, and sibling parameters, exactly as JS specifies; a single uniform
  mechanism across named / closure / method / opaque-value calls.
- **Cons**: a larger, riskier change touching every function-emit path and every
  call path for defaulted functions; a genuine ABI change (the mask parameter,
  the zero-fill of omitted typed slots); interaction with the rest-parameter ABI.
  The *only* observable behavior it adds over Option A is the
  captured-variable-in-default case.

### Recommended direction

**Stage 1 (Option A)** now: it closes the entire reproducing bug class (the
common `const f = function(a, b = …)` shape and the Test262 stored-method files)
with proven machinery and no ABI churn, at the cost of the same documented
caller-scope limitation the IIFE path already has. Consolidate [ADR-00911](../adr/ADR-00911.md)'s
IIFE-specific call-site padding into the general path at the same time (the IIFE
closure value now carries its own defaults, so the special case is redundant).

**Stage 2 (Option B)** later, as the faithful completion: move default evaluation
into the body prologue via a presence mask, so a default referencing a captured
outer variable evaluates in the closure's own scope. Staged for *ordering*, not
dropped — the residual divergence after Stage 1 is precisely one narrow,
documentable case (a default that reads a captured, non-parameter variable), and
Stage 2 is the design that removes it.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `paramDefaultScratch` (sibling-param default scope) | Built | `emit_classes.go`; reused by Stage 1 as-is |
| Closure `Type` flows through a binding | Built | `FuncHasRest` already survives `const f = …`; `FuncParamNames`/`FuncParamDefaults` ride the same path |
| Call-site default fill for named/class/IIFE | Built | Stage 1 mirrors it in `emitClosureCallByPtr` |
| Argument-presence mask ABI | Missing | Stage 2 only |
| Body-prologue default emission | Missing | Stage 2 only |

## Open questions

- Stage 2: does the presence mask belong on the closure header, or as a real
  trailing call parameter? A trailing parameter keeps opaque-value calls uniform
  (the mask travels with the call, not the identity) but changes the LLVM
  signature of every defaulted function.
- Stage 2 interaction with the rest-parameter slot and with async closures'
  coroutine prologue ordering.
