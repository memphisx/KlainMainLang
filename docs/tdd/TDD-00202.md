# TDD-00202: Faithful thrown values — `throw`/`catch` any value

- **Status**: Implemented
- **Date**: 2026-09-11

## Context

The runtime assumes **thrown value == Error**. `errorPtrFromValue`
(`emit_exceptions.go`) wraps a thrown primitive into an `errorObjType` struct
(stringified message), and the catch variable is *always* bound as `errorObjType`
(`emit_exceptions.go:458`). Every `e.message` / `e.name` / `e instanceof X` /
`e.code` reads that fixed struct at static offsets.

So anything that is not an Error is mishandled:

- `throw "x"` → `e` is `Error: x` (`typeof e === "object"`); Node/TS give the
  string `"x"` (`typeof e === "string"`, `e === "x"`). ❌
- `throw 42` → `e` is `Error: 42`. ❌
- `throw { custom: 1 }` → `e` is typed `errorObjType`, so `e.custom` reads a
  garbage offset. ❌
- `throw new Error(...)` → `e` is the Error. ✅ (the only faithful case today)

This blocks Test262 (`bitwise-and/S11.10.1_A2.4_T2.js` now compiles but fails its
`e === "x"` check, ADR-00869) and any `throw <non-Error>` + identity/`typeof`
check. In TypeScript the catch binding is `unknown`; at runtime a thrown value is
any value.

## Design

### Representation (decided)

A `catch` slot must hold whatever was thrown — a number (`i64`), a string
(`ptr`), an object (`ptr`), a boolean (`i1`), from possibly different throw sites
reaching one catch. A single slot over heterogeneous machine representations
requires a **uniform tagged representation**; this is intrinsic to "throw any
value", not a compat=js choice.

**Decision: reuse the existing NaN-boxed `any`** (the D1 model, TDD-00155/00156)
as the representation of `unknown` for the thrown slot and the catch variable, in
**both** `-compat` lanes. Rationale:

- TS binds `catch(e)` as `unknown`, whose only faithful operations are
  *narrowing* — `typeof e`, `e instanceof Error`, `e === v`, and member access
  after narrowing. TS rejects arithmetic on `unknown`. So the boxed value is
  narrowed to a concrete type before any real use; it **never** enters the
  pervasive operator-dispatch machinery NaN-boxing powers in compat=js. The
  NaN-box is used here only as *storage + narrowing*, bounded to one value per
  catch — it does not make strict arithmetic dynamic.
- The `any` encoding already supports exactly the needed narrowing ops
  (`__kml_any_eq`, typeof, instanceof, member access), and `emitBoxValue` already
  boxes objects (tag-object), strings, numbers, booleans, `null`/`undefined`,
  arrays, and closures. A parallel `{tag,payload}` thrown-value type would
  duplicate all of that for no behavioral difference.

`errorObjType` is already `IsObject` (+`IsError`), so an Error boxes through the
existing tag-object path (`emit_dynamic.go:405`) and unboxes back to its pointer.

### Stages

**Stage 1 — thrown slot + catch var become `any`.**
- `@__kml_thrown` holds a NaN-boxed `any` (i64), not a bare `ptr`.
- `emitThrow` boxes its argument via `emitBoxValue` (primitive → tagged scalar,
  object/Error → tag-object) and stores that; drops `errorPtrFromValue`'s
  primitive→Error wrapping.
- The ~41 internal throw sites keep calling `@__kml_throw(ptr errObj)`: that
  entry point becomes a thin shim that boxes its `errorObjType` pointer as a
  tag-object `any` before storing, so no internal site changes. (A second
  `@__kml_throw_any(i64)` entry point serves `emitThrow`.)
- `emitTry`'s catch binding defines the param as `TypeAny` (unknown) with the
  boxed value; `__kml_get_thrown` returns the boxed i64.

**Stage 2 — narrowing round-trips.** `typeof e`, `e === <primitive>`,
`e instanceof Error`/subtype, and `e == null` over the boxed value. Mostly reuse
of existing any-narrowing ops; verify `throw "x"` ⇒ `e === "x"`,
`typeof e === "string"`, and `throw 42` ⇒ `e === 42`.

**Stage 3 — member access on a caught value (regression-critical).**
Existing code and tests do **unguarded** `catch(e) { e.message }` relying on the
old `errorObjType` static typing. With `e: any`, `e.message` / `.name` / `.code`
/ `.stack` must resolve on a tag-object Error through the any member-access path.
Two sub-options, to settle during Stage 3:
- (a) Teach any member access to recognize the error kind tag (field 0) and read
  `errorObjType`'s fixed offsets for the known Error fields.
- (b) Flow-narrow `e` to `errorObjType` inside an `if (e instanceof Error)` guard
  (and, pragmatically, treat a bare `e.message` as an implicit Error access) so
  the static path is reused.
Recommended: (a) for correctness on un-narrowed access, with (b) as an
optimization where a guard is present.

### Faithfulness

Fully faithful in both lanes: the caught value is the thrown value, of its real
type. The only strict-mode concession is that `e`'s representation is the
NaN-box — behavior is unchanged (narrow-before-use), and no dynamic operators are
introduced into strict.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| NaN-boxed `any` + `emitBoxValue`/unbox | Done (TDD-00155/00156) | Boxes object/string/number/bool/array/closure already |
| `__kml_any_eq`, any `typeof` | Done | Stage 2 narrowing reuse |
| any `instanceof` | Verify | Needed for `e instanceof Error` narrowing |
| any member access on a fixed-struct (non-bag) object | **Missing** | Stage 3 crux — `e.message` on a boxed Error |
| `errorObjType` boxes as tag-object | Done | `IsObject`; round-trips through `emitBoxValue` |

## Open questions

- Does the current any member-access path handle a tag-object whose target is a
  fixed struct (`errorObjType`), or only D1 property bags? Determines Stage 3 (a)
  size.
- Should a bare unguarded `e.message` (no `instanceof` guard) be allowed (matches
  this project's existing lenient code/tests) or rejected as TS would for
  `unknown`? Leaning allow, to avoid breaking existing catch blocks.
- `e.stack` is not currently a real field (needs a runtime call-stack, TDD-00188)
  — out of scope here; `.message`/`.name`/`.code` are the targets.
