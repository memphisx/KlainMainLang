# ADR-01397: libcurl's sockets and timer on libuv handles

- **Relations**: Implements TDD-00244; Extends ADR-01396
- **Date**: 2026-10-05

## Context

Since [TDD-00244](../tdd/TDD-00244.md) Stage 3, libcurl reports the sockets
it waits on and its next deadline through `CURLMOPT_SOCKETFUNCTION` and
`CURLMOPT_TIMERFUNCTION`. The select bridge still carried both: each pass
copied the socket table into its bitmaps (`__kml_curl_loop_fdset`), folded
the deadline into its wait (`__kml_curl_loop_deadline_ns`), and drove
libcurl from the bitmaps' readiness (`__kml_curl_loop_perform`).

## Decision

- **Each socket libcurl reports is a libuv watcher**, started, re-armed
  and closed as libcurl's socket callback says. The watcher closes on
  `CURL_POLL_REMOVE`, before libcurl closes the socket. **Its deadline is
  a libuv timer.**
- Both callbacks drive libcurl inside the wait
  (`curl_multi_socket_action`) and settle finished transfers. The loop's
  pass then fires the client reactions and resumes the fibers waiting on
  a fetch, as before.
- The handles are unreferenced. An in-flight transfer still holds the loop
  through libcurl's running count, which also checks abort signals.
- `loop.c` exposes the two handle kinds to runtime files that do not
  include libuv: `__kml_loop_io_watch` (events, re-arm, close) and
  `__kml_loop_timer_new` (start, stop).
- Windows keeps `curl_multi_fdset` and the three bridge functions until
  Stage 6.
- A wait outside the loop still polls libcurl's sockets itself.

## Verification

- Mac (M4): the fetch, HTTP client and top-level-await tests.
- Linux x86-64 (Ubuntu 24.04 container): test-par passes (14 shards;
  `TestE2ECryptoECDHAndDiffieHellman` failed in the parallel run and
  passed on the serial retry, see ADR-01398); examples 393/393; Test262
  strict 8498 and js 10506 (unchanged), no invalid IR.
