# ADR-01996: node:ffi detection counts the dlopen native only

- **Date**: 2026-11-21

## Context

On the Mac the full test suite drove single clang processes to 1.7–2.3 GB,
and the 3 GB memory guard stopped a run with two of them at once. Every one
compiled a program that reads the global object as a value
(`TestE2EGlobalObjectAsValue`, `TestE2ETypeofBuiltinValues`,
`TestE2ENodeGlobalIsGlobalThis`, …). The previous build compiled the same
tests in 150 MB: `TestE2EGlobalObjectAsValue` took 5 s there and 30 s here.

## Investigation

- The test's `prog.ll` reached clang whole: 108 MB, every builtin library
  module included, compiled as one unit. A program that uses node:ffi keeps
  its module whole and its symbols exported, because `dlopen(null)` looks
  them up (`ExportsRuntime`, codegen/llvm/cobj_cache.go). Every other program
  links its library modules as cached objects (`LibObjects`).
- `UsesFFIDl` had become a search of the final IR for `@__kml_native_ffi_`.
  `__kml_native_ffi_view` is registered in `runtimeSymbols`, which
  `emitBoxValue` reaches, so every program that boxes the global object
  defines it and counted as an FFI program.
- `clang -O2 -c` on that IR takes 2.4 GB and 25 s with either build, so the
  whole-module compile itself is unchanged; the classification is what
  changed.

## Decision

`UsesFFIDl` searches for the dlopen native, `@__kml_native_ffi_open`, which
only a program that opens a library through node:ffi reaches.

## Implementation notes

- codegen/llvm/emit_ffi_runtime.go: `UsesFFIDl`.

## Verification

- Mac: the FFI tests (tests/ffi_test.go) and the global-object tests pass;
  `TestE2EGlobalObjectAsValue` builds in 5 s again, with no clang above
  20 MB.
