# ADR-01192: Unhandled promise rejections are reported, as Node's default does

- **Relations**: `Extends ADR-00334`, `Extends ADR-00207`
- **Date**: 2026-09-28

## Context

A rejected promise nothing consumed was dropped: the program went on and
exited 0. Node's default (`--unhandled-rejections=throw`) reports it after
the microtask checkpoint — to `process.on('unhandledRejection')` listeners,
else as an uncaught exception that exits 1. A failing `await fetch` inside
an async `listen` callback therefore looked like a hang: the server kept
the loop alive and the error was never seen. `'unhandledRejection'`
listeners were not accepted.

## Investigation

- Rejections settle through `__kml_promise_settle`,
  `__kml_promise_drain_reactions` (every settle that fires reactions),
  `__kml_task_reject`, and the non-suspending `async` function's direct
  state store.
- Consumers attach through `emitAttachPromiseReaction` (then/catch/finally),
  `__kml_promise_attach`, `__kml_promise_add_reaction`, `__kml_pdyn_attach`,
  the adoption and generator/webview reaction pushes, and
  `__kml_task_await_ready` (every await); the combinators over task
  promises read their members' settlement directly, and the runtime polls a
  module's top-level-await promise (the main loop's wait, an importer
  polling an island).
- A rejection can be consumed after it happens (`Promise.reject(x)` then
  `.catch`), so the decision belongs at the checkpoint, and a consumer must
  mark the promise rather than be inferred from its reaction list (drained
  on settle).

## Decision

- The promise struct gains a flags word (slot 6): bit 0 handled, bit 1
  queued. Every consumer above marks the promise handled (a combinator its
  members, a module task its own promise); every rejection point queues it
  when nothing consumes it yet.
- `__kml_drain_microtasks` ends with `__kml_unhandled_check`: each queued
  promise still unhandled is reported — to the `'unhandledRejection'`
  listener with `(reason, promise)` (both `any`), else to
  `'uncaughtException'`'s (the program goes on), else the `Uncaught:` print,
  the `'exit'` listener and exit code 1.
- `process.on('unhandledRejection', …)` is accepted.
- Promises a runtime creates for itself are handled from birth, as the
  specs say: a web stream's `closed` and a writer's `ready` (WHATWG's
  SetPromiseIsHandledToTrue), a source's or sink's returned promise (the
  stream reacts to it — uponPromise), and a coroutine body's own settled
  promise, which its trampoline reads into the task's promise.
- A rejection the runtime stored without a reason (an Error tag over a null
  payload) is reported as `undefined`.

## Side effects discovered

- `.then`/`.catch` on a combinator's promise (ADR-01193) and `x instanceof
  Promise` (ADR-01194) were rejected; `.finally(cb).catch(h)` settles one
  microtask earlier than Node (BACKLOG).

## Verification

`tests/unhandled_rejection_test.go` (the handled shapes, the listener, the
default exit 1); the full `tests/` suite.
