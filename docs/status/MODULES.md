# Modules

> Part of the [Implementation Status](README.md) index.

**Coverage**: ~93% (14/15).

**Caveats**: Whole-program compilation, not separate compilation units — `resolver.ResolveProgram` parses the entry file plus everything it transitively imports and merges them into one `*ast.Program` before codegen runs. There is no linker step, no per-file LLVM module boundary, and `codegen/llvm` never sees an `import`/`export` node. See [ADR-00022](../adr/ADR-00022.md), [ADR-00134](../adr/ADR-00134.md), [ADR-00135](../adr/ADR-00135.md), and `resolver/resolver.go`'s package doc for the full design. Every top-level declaration now has true per-file scope and import aliasing works (see below); an acyclic imported file's top-level statements now run once, in dependency order (see the table row below) — a file that participates in an import cycle still may not run arbitrary top-level side-effecting code. A namespace import (`import * as ns`) is a compile-time-only construct — `ns` is never a real runtime value, only usable as the object of a dotted member access (see the table below). **Node-style built-ins (`fs`/`path`/`os`/`querystring`/`assert`/`http`/`cluster`/`Memory`) now require a default, namespace, or named import** (`import fs from 'fs'`, `import * as fs from 'fs'`, or `import { readFileSync } from 'fs'`) — see the table row below and [TDD-00049](../tdd/TDD-00049.md)/[ADR-00141](../adr/ADR-00141.md)/[ADR-00142](../adr/ADR-00142.md). `process`/`console` deliberately stay ambient, matching real Node.

| Feature | Status | Notes |
|---|---|---|
| `export function` / `const`/`let`/`var` / `interface` / `type` / `enum` | ✅ | A declaration-level modifier, nothing more — consumed entirely by the resolver |
| `import { a, b } from './relative/path'` | ✅ | Named imports only; relative paths only (`./`, `../`), `.ts` auto-appended if omitted; resolved against the importing file's own directory, not `cwd` |
| Circular imports | ✅ | Supported for the declarations-only case — verified directly with two files calling each other's exported functions |
| Diamond-shaped import graphs | ✅ | A file imported from multiple places is parsed once and merged once (memoized by absolute path) |
| Imported (non-entry) files may run top-level side-effecting code | ✅ | An *acyclic* imported file's top-level statements now run exactly once, in real dependency order, strictly before whatever imports it — no restriction to declarations-only anymore. Diamond-shared dependencies still run exactly once (existing per-path memoization). A file that genuinely *participates in an import cycle* keeps the original declarations-only restriction (no bare executable statements), now additionally requiring a top-level `var`/`let`/`const` initializer to be a compile-time literal — closing a real bug found while designing this: a circular pair of files could already (before this) read each other's not-yet-initialized top-level binding via an unrestricted `VarDeclaration.Init`, an uninitialized-alloca read. No TDZ/live-binding modeling — a literal-only initializer sidesteps the need for it entirely. See [TDD-00052](../tdd/TDD-00052.md)/[ADR-00145](../adr/ADR-00145.md) |
| True per-file module scope (mangled internal names) | ✅ | Every top-level declaration gets a file-private mangled name, and every reference to it is rewritten via a real scope-aware walk — two unrelated files may freely declare the same top-level name. See [TDD-00041](../tdd/TDD-00041.md)/[ADR-00134](../adr/ADR-00134.md). Binding two different files' exports to the *same local name* in one importing file with no `as` is still rejected (a real conflict, same as real ES modules) |
| Import aliasing (`import { a as b }`) | ✅ | A direct consequence of the per-file rename mechanism above — `b` is simply bound to the target's mangled name for `a`, no separate rename step. See [TDD-00041](../tdd/TDD-00041.md)/[ADR-00134](../adr/ADR-00134.md) |
| `export default` | ✅ | Named (`export default function foo() {...}`/`class Foo {...}`/`interface`/`type`/`enum`) and anonymous function/class forms, plus an arbitrary expression (`export default 42`, wrapped as a synthetic `const`). Exposed only under the export key `"default"` — a named default export's own name stays usable for intra-file self-reference (recursion, etc.) but is not itself importable via `import { foo }`, matching real ES modules. See [TDD-00042](../tdd/TDD-00042.md)/[ADR-00135](../adr/ADR-00135.md) |
| `import x from './path'` (default import) | ✅ | Also combinable with a named list in one statement: `import x, { a, b } from './path'`. Sugar over the same specifier machinery as a named import (`{Imported: "default", Local: "x"}`) — no separate resolver mechanism. See [TDD-00042](../tdd/TDD-00042.md)/[ADR-00135](../adr/ADR-00135.md) |
| `import * as ns from '...'` (namespace import) | ✅ | Compile-time-only: `ns.member` is rewritten directly to that member's mangled name during resolution; `ns` itself is never a runtime value. Only actually-exported members are reachable (`ns.privateHelper` is rejected, same visibility rule as a named import). Using `ns` as anything other than the object of a non-computed dotted access (assigning it to a variable, passing it as a value, `ns["x"]`) reaches codegen as a plain undefined reference rather than getting a dedicated error message. `ns.default` reaches a default export the same way any other member does. Type-position access (`let x: ns.SomeInterface`) and `new ns.SomeClass(...)` are not supported — the latter is a pre-existing, namespace-independent restriction (`new` already only accepts a single bare identifier). See [TDD-00042](../tdd/TDD-00042.md)/[ADR-00135](../adr/ADR-00135.md) |
| Re-exports (`export { x } from './other'`, `export * from './other'`) | ✅ | Named re-export list (with `as` aliasing) and star re-export both work, including default re-export in either direction (`export { default } from`/`export { default as Foo } from` to re-export another module's default; `export { foo as default } from` to re-export a named export as this module's own default). `export *` never forwards a `default`, matching real ES modules. Chains of arbitrary depth resolve transitively (a file re-exporting from a file that itself re-exports resolves through). A re-export forwards a name to this file's importers only — it does *not* become a usable bare identifier inside the re-exporting file itself, same as real ES modules. Namespace re-exports (`export * as ns from`) are parsed and explicitly rejected with a clear error rather than silently mis-parsed — no concrete use case yet. Re-exporting from a built-in module (`export { readFileSync } from 'fs'`) is likewise an explicit, rejected scope cut, not an oversight. See [TDD-00051](../tdd/TDD-00051.md)/[ADR-00144](../adr/ADR-00144.md) |
| Bare/package-style imports (`import x from 'somepackage'`) | ✅ | klmpm Stage 1 only ([TDD-00054](../tdd/TDD-00054.md)) — a bare specifier resolves against `klain_modules/<name>/klain.json`'s `"main"` field, found by walking upward once from the *entry file's* own directory (not re-walked per importing file, unlike Node — every file in the whole program, including one inside a fetched package, resolves a given name against the same single `klain_modules`). This is deliberately just the resolution half: no klmpm tool exists yet to actually fetch/version/lock a dependency — a `klain_modules/<name>/` directory has to be hand-constructed today. A real built-in module name (`'fs'`/`'path'`/etc., see the import-gated built-in bindings row below) is always checked, and always wins, before any `klain_modules` lookup is attempted. npm/`node_modules` interop is a separate, unstarted, differently-scoped mechanism — see [TDD-00053](../tdd/TDD-00053.md) |
| Dynamic `import(...)` | ❌ | Parses cleanly (recognized in expression position) and is explicitly rejected with a "not yet supported" error, rather than a generic parse failure — real support is staged separately: [TDD-00055](../tdd/TDD-00055.md) (eager, literal-specifier-only, wrapped in a resolved `Promise` — this compiler's whole-program AOT model means the target's top-level code would still run at startup regardless of whether the call site executes) or [TDD-00056](../tdd/TDD-00056.md) (V2 — real laziness via a `dlopen`'d shared library per target, incompatible with `--static`) |
| `import.meta.url` | ✅ | The only supported member — resolved entirely at compile time, per file, into a plain string literal (`"file://" + that file's own absolute path`, matching real Node/browser convention); codegen never sees a real "module metadata object". Bare `import.meta` or any other member (`import.meta.resolve`, etc.) is a clean parse-time error. See [TDD-00055](../tdd/TDD-00055.md) Stage 1/[ADR-00148](../adr/ADR-00148.md) |
| Import-gated built-in bindings (`fs`/`path`/`os`/`querystring`/`assert`/`http`/`cluster`/`Memory`) | ✅ | `import fs from 'fs'`, `import * as fs from 'fs'`, and `import { readFileSync } from 'fs'` (including aliasing and combining a default with named specifiers in one statement) all bind through the same scope-aware machinery as a real file import — a local variable of the same name correctly shadows it instead of silently colliding, closing a confirmed real miscompilation bug (see [TDD-00049](../tdd/TDD-00049.md)'s Context). Importing an unknown member is a clean, explicit rejection. `process`/`console` stay ambient by design, matching real Node/JS. See [ADR-00141](../adr/ADR-00141.md)/[ADR-00142](../adr/ADR-00142.md) |
