# TDD-00085: Async generators (`async function*`) and `for await...of`

- **Status**: Implemented
- **Date**: 2026-08-20
- **Notes**: All 4 stages done: `for await...of` parsing; the fused `async function*` fiber (`yield` + `await` in body + `.next(): Promise<{value,done}>` + throw→reject); `for await...of` consumption; async generator *methods* `async *m()`. `yield*`/`Symbol.asyncIterator`/`.return()`/`.throw()` are V1 scope cuts. Fuses the sync-generator fiber ([TDD-00061](TDD-00061.md)) with the coroutine-task scheduler park ([TDD-00083](TDD-00083.md)) into one fiber that both `yield`s and `await`s, so `.next()` returns `Promise<{value,done}>`; `for await...of` desugars to `await iter.next()`. A no-await async generator stays off the scheduler (fast-path philosophy). `yield*`/`Symbol.asyncIterator`/`.return()`/`.throw()` are V1 scope cuts

## Context

With the async model fully unified ([TDD-00084](TDD-00084.md)) and sync
generators shipped ([TDD-00061](TDD-00061.md)), async iteration is now
*reachable* — it was explicitly the ceiling both of those left open
([TDD-00063](TDD-00063.md)'s "async-generator runtime semantics are out of
scope"). This TDD provides those semantics: `async function*`, and the
`for await...of` that consumes it.

What exists (both are ucontext-fiber subsystems, the exact two this fuses):

- **Sync generators** ([TDD-00061](TDD-00061.md)/[ADR-00172](../adr/ADR-00172.md),
  `emit_generators.go`). A generator instance is its own fiber (per-instance
  `ucontext_t` + stack). `.next(v)` swaps *into* the fiber from its caller;
  `yield x` stores `{value:x, done:false}` into the instance struct and swaps
  *back* to the caller (`emitGeneratorSwapToCaller`); return/fall-off stores
  `{value, done:true}`. The caller's resume target changes every `.next()`.
- **Coroutine tasks** ([TDD-00083](TDD-00083.md)/[ADR-00244](../adr/ADR-00244.md),
  `runtime_task.go`). An async fn is a fiber that, at `await p`, parks
  (`pendingPromise = p`, state = suspended) and swaps to its resumer; the
  scheduler (`__kml_task_sched_step`, driven by the unified event loop, [ADR-00250](../adr/ADR-00250.md))
  resumes it when `p` settles.

What is missing, confirmed directly:

- `for await (...)` does not parse (`expected (, got await`).
- `async function*` parses ([TDD-00061](TDD-00061.md)) but codegen rejects it,
  as do async generator *methods* ([TDD-00063](TDD-00063.md) Stage 2's
  deferral).
- No async-iterator protocol: `.next()` returning `Promise<{value,done}>`, and
  the consumer awaiting each step.

This needs a TDD, not a bare ADR: fusing the two fiber subsystems (a fiber that
suspends for *two* different reasons — yield to the consumer, await on the
scheduler) and settling the `.next()`-returns-a-promise protocol is genuine
design, not a mechanical extension of either one.

## Design

### The core fusion — an async-generator fiber that both yields and awaits

An async generator instance is a generator instance (per-instance fiber + the
`{value, done, callerCtx, ownCtx, __sent}` struct) whose body can *also* park on
the scheduler. The two suspension points are distinct:

- **`yield x`** — the value is ready now: store `{value:x, done:false}`, swap
  back to *whoever called `.next()`* (the existing `emitGeneratorSwapToCaller`
  path, unchanged), and that `.next()` call resolves its promise with
  `{value:x, done:false}`.
- **`await p`** — the next value is not ready yet: park the fiber on the
  scheduler exactly as a task does (`pendingPromise = p`, swap to the resumer);
  when `p` settles the scheduler resumes the fiber, which runs on to its next
  `yield`/`return`, at which point the *pending* `.next()` promise settles.

So the instance struct gains the task-park fields (`pendingPromise`/state/resumer
+ the per-task jmpbuf stack for fiber-safe exceptions, [ADR-00244](../adr/ADR-00244.md)),
i.e. it becomes a generator struct *and* a task struct — the same fiber, two
suspend reasons. `.next()`'s own resume target (the caller) and the scheduler's
resume target (main/parent task) are both already per-swap values, so this is
additive, not a rework of either.

### `.next()` returns a `Promise<{value,done}>`

`asyncGen.next(v)` allocates a task promise Q, then swaps into the fiber:

- If the fiber reaches a `yield`/`return` *without awaiting*, it swaps straight
  back and `.next()` settles Q immediately with `{value,done}` (a resolved
  promise) — the common no-await-between-yields case stays cheap.
- If the fiber hits an `await` first, it parks on the scheduler and `.next()`
  returns Q *pending*; Q settles later when the fiber next yields/returns. This
  reuses the task settle/reject machinery — a throwing async generator rejects
  the outstanding `.next()` promise.

`.next()`'s result type is `Promise<{value: T, done: bool}>`
(`PromiseOf(genNextResultType(T))`, both types already exist).

### `for await...of` — the consumer

Parse `for await (const x of expr) body` (only inside an async context; a plain
function is a clean rejection, matching JS). Represent it as the existing
`ForOfStatement` with an `Await bool` flag (least-invasive). Codegen desugars to:

```
loop:
  const __r = await iter.next()      // await the Promise<{value,done}>
  if (__r.done) break
  const x = __r.value
  <body>
  goto loop
```

reusing `emitAwait` (which already drives the scheduler / re-throws a rejection)
and the existing `{value,done}` field reads. The iterable in V1 is an async
generator instance (has an async `.next()`); a general `Symbol.asyncIterator`
protocol is out of scope (this compiler has no well-known symbols —
[TDD-00044](TDD-00044.md)).

### Options weighed

- **`.next()` promise vs. always-suspend.** Option A (chosen): settle Q
  synchronously when the fiber yields without awaiting, pending only when it
  awaits — matches the task fast-path philosophy ([ADR-00249](../adr/ADR-00249.md))
  and keeps a fetch-free async generator off the scheduler. Option B (always
  return a pending promise driven by the scheduler) is simpler but forces every
  async generator onto the fiber/libcurl path even when it never awaits —
  rejected for the same reason Part A kept the no-fiber fast path.
- **Struct fusion vs. a wrapper task around a sync generator.** Chosen: one fiber
  that is both. A wrapper (a task that drives a separate sync-generator fiber)
  doubles the fiber count and can't let `await` inside the generator body park
  the *generator's* own stack — rejected.

## Staged delivery (ordered by dependency)

1. **`for await...of` parsing + AST** (`Await` flag on for-of), gated to an async
   context; a clean rejection elsewhere. Cheap, unblocks the consumer syntax.
2. **`async function*` top-level declarations + the fused fiber** — the core:
   generator struct + task-park fields, `yield` (swap-to-caller, resolve
   `.next()`), `await` (scheduler park), `.next(): Promise<{value,done}>`,
   throw → reject the outstanding `.next()`.
3. **`for await...of` codegen** — the desugaring above, over a Stage-2 async
   generator.
4. **Async generator *methods*** (`async *m()` on a class) — reuse Stage 2 with
   the per-class/`this`-captured generalization [TDD-00063](TDD-00063.md) already
   built for sync generator methods. Deferred within this TDD if Stage 1–3
   conformance delta doesn't justify it (the [TDD-00061](TDD-00061.md) lesson).

`yield*` (async delegation), a general `Symbol.asyncIterator` iterable, and
`.return()`/`.throw()` on an async generator are explicit V1 scope cuts.

## Open questions

- Does the async-generator instance struct extend the generator struct with the
  task fields, or embed a task struct by pointer? Prototype both — the former
  keeps one fiber/one allocation, the latter reuses `__kml_spawn_task` verbatim.
- Backpressure: `for await` calls `.next()` strictly serially (await each before
  the next), so there is no concurrency to manage in V1 — confirm no consumer
  ever needs two `.next()` promises outstanding before committing to the
  single-outstanding-`.next()` assumption in the settle path.
- `make conformance`: like [TDD-00061](TDD-00061.md)/[TDD-00063](TDD-00063.md),
  the `for-await`/async-generator corpus leans on the dynamic object model
  (`Symbol.asyncIterator`, async-iterator prototype chain) above this static
  model's ceiling — treat any flip as a bonus, not the goal.
