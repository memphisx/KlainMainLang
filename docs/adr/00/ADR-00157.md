# ADR-00157: Uninitialized-heap-memory reads (optional fields, class fields, array destructuring bounds)

- **Relations**: Extends [ADR-00153](ADR-00153.md) (Test262 full-corpus conformance harness)
- **Date**: 2026-08-11

## Context

Scoping destructuring default values (`{a = 1} = obj`, `[a = 1] = arr` — the next Test262 conformance candidate after ADR-00156) required first answering a basic question: what does "the source value is absent" actually mean in this compiler's statically-typed object/array model? Investigating that question directly, rather than assuming, found two real memory-safety bugs — not a missing feature, a genuine correctness/safety defect in already-shipped, ✅-marked functionality. Flagged to the user before any fix, per this project's standing rule that a large bug found in passing gets a decision, not a silent fix.

## Investigation

**Bug 1 — uninitialized object/class-instance fields.** `interface Point { x: number; y?: number }`, `let p: Point = { x: 1 }` (omitting the optional `y`), then `console.log(p.y)` printed a different, large, address-shaped number every run (140735447688072, 140724852604056, 140732953528856, ...) — the classic signature of reading truly uninitialized memory, not a bug that only looks wrong. Root cause: `emitObjectLiteralWithHint` (`codegen/llvm/emit_objects.go`) allocates the object's heap storage with plain `malloc(StructSize)`, then loops only over the properties actually present in the source literal, calling `storeField` for each — a field declared in the interface but never mentioned in a given literal (because it's `?:`) simply never receives a `store` at all, leaving its slot however malloc happened to leave it. `resolveObjectPtr`'s own inline-object-literal case (used by `let {a} = {a: 1, b: 2}`-shaped destructuring) had the identical pattern, independently.

Checked whether `class` instances were exposed the same way, since the docs claimed "every field must be set explicitly" as a stated design philosophy. Confirmed directly that claim isn't actually enforced: `class Box { x: number; y: number; constructor() { this.x = 1; } }` (never assigning `y`) compiles with no error at all — no definite-assignment check exists. `emitNewExpression`'s class-instance allocation (`codegen/llvm/emit_classes.go`) uses the identical `malloc`-then-selectively-store pattern, so an under-assigned field is exposed to the same class of bug, for the same reason, just reached through a different front-end path (a missing check, not a missing store).

**Bug 2 — array destructuring past the source array's length.** `let [a, b] = [1]` printed a real address-shaped garbage value for `b`, non-deterministic across runs. Root cause: `unpackArrayPatternInto` (`codegen/llvm/emit_arrays_core.go`) issued a `getelementptr`+load at each pattern index unconditionally, with *zero* runtime bounds check against the source array's actual length — worse than Bug 1, since this reads *past* an allocated buffer entirely (an actual out-of-bounds heap read, undefined behavior in the C sense), not just an uninitialized-but-in-bounds slot.

Checked whether this compiler already has an established, shipped answer for "index past the end" elsewhere, rather than inventing one from scratch. It does: plain `arr[10]` indexing (`emitIndexPtr`, `codegen/llvm/emit_exprs_member.go`) already does a real runtime bounds check (`icmp uge` against the length, branching to `emitInternalThrow("Array index out of bounds")` on failure) — a deliberate, already-shipped design choice that plain indexing throws rather than silently returning `undefined` the way real JS does. Destructuring past the end is a different situation, though: `let [a, b] = [1]` is ordinary, valid JS (parsing a variable-length CSV row, an optional trailing element, etc.), not an explicit arbitrary-index read a program is more likely to have a bug in — throwing there would make a common, correct idiom always crash, a worse outcome than the plain-indexing case. Chose a different resolution for the same underlying "there's no `undefined` sentinel for a concrete scalar type" problem Bug 1's fix already had to make: read as a deterministic zero instead — safe, consistent with Bug 1's own resolution, and not real JS's `undefined` (documented as a known simplification, same as everywhere else in this compiler `undefined`-for-a-concrete-type doesn't have a real representation).

## Decision

**Bug 1**: swapped `malloc` for `calloc` at all three allocation sites carrying this exact risk (`emitObjectLiteralWithHint`, `resolveObjectPtr`'s object-literal case, `emitNewExpression`'s class-instance allocation) — `ensureCalloc()`/`@calloc` was already an established pattern in this codebase (`new Array(n)`, `ArrayBuffer`, both of which are required to be zero-initialized by their own JS semantics), so this isn't a new mechanism, just applying the existing one to two more allocation sites that needed it. A field/element never explicitly stored to now reads a deterministic zero instead of allocator garbage.

**Bug 2**: `unpackArrayPatternInto` now does the same shape of runtime bounds check `emitIndexPtr` already established as precedent, but resolves differently on failure — branch to a zero-fill path instead of a throw. `resolveArrayDataPtr` (the statement-level `let [a,b] = expr` resolver) now also returns the source's runtime length (an SSA register for an identifier/call-expression source, or a compile-time-constant literal for an array-literal source, both valid as the `icmp`'s right-hand operand) alongside the existing pointer and element type. The three destructured-function-parameter call sites (`emit_func.go` ×2, `emit_classes.go` ×1) pass the raw incoming `%p_<name>_len` parameter register directly — no new plumbing needed there, since array parameters were already passed as `(ptr, len)` pairs.

Both fixes lean on the same insight: since every destination here is a mutable `alloca` (an object/class field's GEP'd slot is written via `store`, and a destructured local's own storage is always a fresh `alloca`), the two branches (in-bounds vs. out-of-bounds) can each just `store` their own value into the same destination — no LLVM `phi` node needed to merge two SSA values, which would have been substantially more complex for the array-typed-nested-destructuring case (merging an aggregate `{ptr,i64}` shape). A new `Type.zeroLiteral()` helper (`codegen/llvm/types.go`, mirroring the existing `Type.Align()` switch's shape) returns the right zero spelling per IR kind (`0.0` for float/double, `null` for `ptr`, `0` otherwise) for the scalar case; the array-typed case stores `null`/`0` directly into the pattern-local's own `Ptr`/`LenPtr` allocas, no helper needed.

## Implementation notes

- `codegen/llvm/emit_arrays_core.go`: `resolveArrayDataPtr`'s signature grew a `lenVal` return; `unpackArrayPatternInto`'s grew a `lenVal` parameter. Both are internal-only functions (not exported, no external callers), so this was a clean, compiler-checked signature change — same "the type checker finds every real call site for free" experience ADR-00156 already noted for its own `Update []Expression` change, in contrast to `VarDeclarationList`'s silent-skip risk (a genuinely new sibling type, not a changed signature).
- `codegen/llvm/emit_func.go`, `emit_classes.go`: the destructured-array-parameter call sites already had the exact string they needed (`%p_<name>_len`, the raw incoming parameter register) sitting right next to the existing `%p_<name>_ptr` usage — no new computation, just passing one more string through.
- Ran `go vet`, full `go test ./...`, and `make examples` (all 109 example programs — a broader smoke test than the unit suite alone, since these three allocation sites are on the hot path for nearly everything) after landing, not just after the initial repro fix, to catch anything the two targeted bugs' own narrow tests wouldn't.
- Found and fixed one unrelated, pre-existing bug while working in this area: the Makefile's `clean` target (`find examples -type f ! -name '*.ts' -delete`) deleted `examples/imports/klain_modules/greeter/klain.json` — a real, tracked package-manifest fixture, not a generated build artifact — the first time `make clean` ran during this work. Restored via `git checkout`, then fixed the rule itself to delete only extensionless files (`! -name '*.*'`, matching exactly what a compiled example binary looks like — confirmed no tracked file under `examples/` is itself extensionless).

## Side effects discovered

None beyond the two bugs themselves and the Makefile issue above — no new gaps surfaced investigating this one, unlike ADR-00154/00155/00156's pattern of unmasking coincidental Test262 passes. These are safety fixes to existing, already-shipped functionality, not new syntax/semantics support, so they don't interact with Test262's classification the same way.

Destructuring default values (the feature this investigation was originally scoping) are *not* implemented here — this ADR is purely the safety-fix prerequisite the earlier investigation found was missing. Revisiting that feature now has an actual foundation: a real "was this position/field provided" signal (bounds check for arrays; nothing equivalent for object fields yet, since real absence-tracking there would still need either a nullable-type check or a new mechanism this ADR deliberately didn't invent).

## Verification

- `go build`, `go vet ./...`, full `go test ./...`, `make examples` (all 109) — all pass.
- 7 new E2E tests: `tests/objects_test.go` (optional field omitted reads zero, the same repeated after deliberate heap-churn to rule out "looked zero by luck," class field unassigned in constructor reads zero), `tests/arrays_test.go` (in-bounds destructuring unaffected, partial and fully-out-of-bounds scalar destructuring read zero, nested-array-element out-of-bounds reads a safe empty array, destructured function parameter out-of-bounds reads zero).
- Manually confirmed the pre-fix garbage was real (non-deterministic across repeated runs of the same binary) before fixing, and that the post-fix value is deterministic across repeated runs, for both bugs independently.
- Full Test262 corpus re-run: 4,461 → 4,462 passed — a small, expected-neutral-to-positive movement (these are safety fixes to undefined behavior, not new syntax support, so no plausible mechanism exists for a previously-*correct* test to start failing because of them).
