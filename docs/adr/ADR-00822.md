# ADR-00822: RPM packaging tests tolerate an arch-incapable rpmbuild host

- **Relations**: `Extends ADR-00810`
- **Date**: 2026-09-10

## Context

The `Release` workflow's `test (linux-x64)` lane began failing at `go test` on
three RPM packaging tests — `TestWriteRPMStructure`, `TestWriteRPMBundlesPcre2`,
`TestWriteRPMBundlesGC` — each `writeRPM: rpmbuild: exit status 1`. The
`test (linux-arm64)` and `test (macos-arm64)` lanes passed.

## Investigation

The `rpmbuild` stderr was `error: No compatible architectures found for build`.
The tests build an **aarch64** RPM (`--target aarch64`, `BuildArch: aarch64`) on
every host. Stock `rpm` on the x86-64 Ubuntu runner has only its own host
platform definitions under `/usr/lib/rpm/platform/`; it lacks the `aarch64-*`
platform files a cross-arch build needs, so `rpmbuild` refuses the foreign
target. The arm64 lane builds it natively and succeeds; macOS has no `rpmbuild`,
so `writeRPM` already falls back to writing the spec only.

The x64 runner is the odd one out: `rpmbuild` is *present* but *incapable* of the
target arch. The tests' own comments already state the actual `rpmbuild` run is
"exercised on the arm64/Sailfish lanes, not required here" — but the code treated
any present-but-failing `rpmbuild` as fatal, so the incapable x64 host failed.

## Decision

A test helper `rpmbuildErr(t, err)` fatals only on a host that can natively build
the target (`runtime.GOARCH == "arm64"`), where a `rpmbuild` failure is a real
bug; on any other host a failure is logged and tolerated. The spec and build tree
are written before `rpmbuild` runs, so the structural assertions still validate
everywhere; the real cross-build stays covered by the arm64 lane. Production
`writeRPM` behaviour is unchanged.

## Verification

`go vet` and the RPM tests pass locally on macOS/arm64 (rpmbuild absent →
spec-only fallback). The x64 lane will now tolerate its arch-incapable rpmbuild;
the arm64 lane keeps its strict native-build assertion.
