# ADR-00867: `TestE2EStdinDoesNotBlockLoop` startup-race fix; piped-stdout buffering gap found

- **Relations**: `Relates to TDD-00183`, `Relates to TDD-00185`
- **Date**: 2026-09-11

## Context

`TestE2EStdinDoesNotBlockLoop` (added with the Windows IOCP reactor work,
TDD-00183 Stage 1) failed **deterministically on macOS**: the first two stdin
chunks reported `ticks>0:false`. The test feeds `process.stdin` three lines with
80 ms gaps and asserts a 15 ms `setInterval` fired during each quiet window
(proof the loop is not blocked in a stdin read).

## Investigation

The runtime's non-blocking stdin is **correct**. With the producer given enough
lead time, the timer fires during the quiet gaps exactly as intended — measured
tick counts advance monotonically across each 80 ms window (`4 → 9 → 13`). The
macOS `O_NONBLOCK` flag (`httpNonblockFlag` = `0x4`) is right and the select-loop
timeout path consults the pending `setInterval` deadline.

The failure was a **test artefact, not a reactor bug**: process startup
(dyld + Boehm + runtime init) is tens of ms warm and **hundreds of ms on the cold
exec of a freshly built test binary** (~0.7 s measured). That startup overlaps
the producer's first 80 ms windows, so the first writes are already buffered in
the pipe by the time the loop first reads — delivered in one early read at
`ticks=0`, before the first 15 ms tick. The test was timing its writes from
`cmd.Start()` with no guarantee the child's loop was running.

Attempting a stdout `READY` handshake surfaced a **second, genuine finding**: when
stdout is a pipe (not a TTY), the runtime's libc stdio is **fully block-buffered
and flushes only at exit** — a program printing three lines 300 ms apart delivers
all three at exit, not as produced. Node flushes `process.stdout` incrementally,
so `prog | tee` / `| grep` / Docker log capture diverges. Pre-existing, unrelated
to this test; recorded in BACKLOG as its own item (relevant to the CLI/Docker
targets). stderr is unbuffered, so it is the reliable handshake channel.

## Decision

- **Handshake over stderr**: the child prints `READY` on stderr (unbuffered); the
  Go producer waits for it before the timed writes, so the check is independent of
  startup latency without weakening it.
- **Assert the real property**: each chunk reports its absolute tick count; the
  test requires the count to **strictly increase across the two quiet 80 ms gaps**
  (`end`, which follows the last chunk with no gap, need only not regress). A
  blocking read — the regression guarded — would freeze the count across a gap,
  which this catches. This is not masking: the underlying non-blocking behaviour
  was verified directly (the monotonic advance), and the assertion now states it
  precisely rather than via the startup-sensitive "chunk one saw a tick".

## Verification

- `go test ./tests/ -run TestE2EStdinDoesNotBlockLoop -count=8` — green, stable.
- Runtime non-blocking stdin confirmed correct by direct timing (tick counts
  advance across quiet stdin windows).
- Platform: Apple-Silicon Mac.
