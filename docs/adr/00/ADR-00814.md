# ADR-00814: Generator/iterator wrapper return annotations (`Generator<T>`)

- **Relations**: `Extends ADR-00293`

- **Date**: 2026-09-09

## Context

A generator declared with the idiomatic-TypeScript return annotation —
`function* counter(): Generator<number> { yield 1; }` — miscompiled: `clang`
rejected the emitted IR with `store {ptr, i64} 0x3FF0000000000000, ptr %t16`
(the `double` 1.0 stored into a `{ptr, i64}` slot). Found while testing the
cross-compile work; it reproduces on a plain host build and is unrelated to
cross-compilation.

## Investigation

This codebase's generator convention writes the *element* type directly as the
return annotation: `function* f(): number` yields numbers, `function* g():
number[]` yields arrays (`buildGeneratorSig`, `emit_generators.go`). The
annotation is resolved with the ordinary `resolveType`, whose value stored as
the yielded/sent field type (`GeneratorType`, `types.go:1215-1216`).

`resolveType` has no case for `Generator`/`IterableIterator`/etc., so
`Generator<number>` (a `Name` with a single type argument in `ElemType`) fell
through to the generic single-type-argument path that builds `Array<T>`/`T[]`
— producing `number[]`, an array type. `GeneratorType` then laid the
yielded/sent fields out as the inline `{ptr, i64}` array aggregate
(`StructFieldIR`, `storeGeneratorField`), while a scalar `yield 1` produced a
`double` value — hence the type-mismatched store and the invalid IR. So the
wrapper annotation was silently misread as "generator of `number[]`", never
diagnosed.

## Decision

Unwrap the standard generator/iterator wrapper types at the generator return
annotation. `generatorElemAnnotation(fd.ReturnType)` (`emit_generators.go`)
returns the annotation to resolve as the element type:

- a wrapper name (`Generator`, `AsyncGenerator`, `Iterator`, `AsyncIterator`,
  `IterableIterator`, `AsyncIterableIterator`, `Iterable`, `AsyncIterable`) →
  its first type argument (`Generator<T, TReturn, TNext>` → `T`; TReturn/TNext
  are ignored in V1). A bare wrapper with no argument (`Generator`) → nil, i.e.
  infer the element type from the body, same as no annotation;
- anything else → the annotation itself (the bare-element convention, unchanged:
  `: number`, `: number[]`, `: {x,y}`).

`buildGeneratorSig` resolves that annotation, or falls back to the existing
body-yield inference (`inferGeneratorElemType`) when it is nil. This is a
faithfulness fix — the wrapped form is what a TypeScript author actually writes
— and it is confined to the generator signature path; `resolveType` is
untouched (a `Generator<T>` used as a *value* type, e.g. a variable annotation,
is a separate, rarer surface and out of scope here).

## Verification

- `tests/generators_test.go`: `TestE2EGeneratorWrapperReturnAnnotation` covers
  `Generator<number>`, `IterableIterator<number>`, and the three-arg
  `Generator<number, void, unknown>` summing to 15; the existing bare-element
  and array-element tests are the regression guard.
- Manual battery (macOS): `Generator<number>`, `Generator<T,TReturn,TNext>`,
  `IterableIterator<number>`, `Iterator<string>`, bare `Generator` (infers),
  `AsyncGenerator<number>` with `for await`, `.next().value`, and the direct
  `: number` / `: number[]` regressions all compile and run correctly.
- `examples/generators/generators.ts` gains a `Generator<number>` and an
  `IterableIterator<string>` generator, built and run.

## Consequences

Idiomatic-TS generator annotations compile instead of emitting invalid IR. A
generator/iterator wrapper used as a plain *value* type is still resolved by the
generic path (and would still be wrong); lifting that needs `resolveType` to
know the generator instance type without the body/param context, tracked as a
follow-up if it surfaces.
