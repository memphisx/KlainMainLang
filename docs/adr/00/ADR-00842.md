# ADR-00842: `String.prototype.split(sep, limit)` — the optional limit argument

- **Relations**: Extends [ADR-00004](ADR-00004.md) (`split`) and the RegExp split
- **Date**: 2026-09-10

## Context

`str.split(sep, limit)` rejected the `limit` argument at compile time ("split
takes exactly 1 argument"), so the standard two-argument form (`"a-b-c".split(
"-", 2)` → `["a","b"]`) was unavailable for both string and RegExp separators.

## Decision

`emitStringSplit` accepts 1 or 2 arguments. It performs the full split (plain
`__kml_split` or the RegExp path) as before, then — when a `limit` is given —
caps the result array's reported length to `min(fullLen, limit)`. A negative
limit is treated as "no cap" (matching JS's `ToUint32(limit)`, which turns a
negative into a huge count). The capped elements past `limit` remain allocated
but unreferenced (consistent with the manual-memory default); the observable
result is identical to recomputing a limited split.

## Implementation notes

`emit_strings.go` `emitStringSplit`: the plain and RegExp paths now produce a
common `result` aggregate, and a shared post-step clamps its `{ptr, i64}` length
via `select`s. No runtime change.

## Verification

macOS (Apple Silicon M4): matches Node — `"a-b-c-d".split("-", 2)` →
`["a","b"]`, `split("-", 0)` → `[]`, `split("-", 10)` → all three, no-limit
unchanged, and a RegExp separator with a limit (`"a1b2c".split(/[0-9]/, 2)` →
`["a","b"]`). New `TestE2EStringSplitLimit` + the string/split suites green.
