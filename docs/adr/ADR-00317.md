# ADR-00317: `crypto.getRandomValues` accepts real TypedArrays and ArrayBuffers

- **Relations**: Implements [TDD-00104](../tdd/TDD-00104.md) (Phase 1); extends [ADR-00024](ADR-00024.md); closes the migration deferred in [ADR-00078](ADR-00078.md)
- **Date**: 2026-08-23

## Context

`crypto.getRandomValues` predates ArrayBuffer/TypedArrays and filled a plain
`number[]` with one random byte value per i64 element — the last caveat on
the two ✅ rows of `docs/status/WEB-CRYPTO.md`. With TypedArrays shipped and
the subtle-crypto work adding a shared BufferSource extraction path, the
real API shape became nearly free.

## Investigation

`emitCryptoGetRandomValues` (`emit_call_encoding.go`) required a *named*
`number[]` variable because a plain array had no other reachable heap
location. TypedArrays/ArrayBuffers don't have that constraint: a TypedArray
resolves to a raw `(ptr, len)` via `resolveArrayForHOF`, and an ArrayBuffer
is a header holding its data pointer — both writable in place through
`__kml_crypto_random_bytes`, no per-element copy loop needed.

## Decision

`crypto.getRandomValues(view)` now takes, per the real API:

- any TypedArray — bytes filled in place (`len * elemSize`), the argument
  returned;
- an ArrayBuffer — its whole byte range filled, the argument returned;
- (legacy) a named `number[]` variable — unchanged one-byte-per-element
  behavior, kept for back-compat.

No `-crypto` backend involvement: the fill still uses the in-house CSPRNG
(`arc4random_buf`/`getrandom()`), so plain getRandomValues programs gain no
library dependency.

## Implementation notes

`emit_call_encoding.go` only; the TypedArray branch reuses
`resolveArrayForHOF` + element-size scaling, the ArrayBuffer branch the
`{ i64 byteLength, ptr data }` header loads. Type inference was already
argument-passthrough and needed no change.

## Side effects discovered

None. The spec's 65536-byte quota and integer-TypedArray-only restriction
are not enforced (float TypedArrays are accepted); noted as a status caveat.

## Verification

Mac: `TestE2EGetRandomValuesTypedArray` (Uint8Array fill + return-value
identity, Uint32Array scaling, ArrayBuffer fill, nonzero-content check) and
the legacy `number[]` path both green; crypto example extended and rerun.
