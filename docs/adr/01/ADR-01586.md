# ADR-01586: An island never installs the stack guard

- **Date**: 2026-10-11

## Context

The full E2E run on macOS failed `TestE2EDynamicImportIsolated` with a bus
error, right after the island's top level printed. It failed every time
under `go test` and never when the same binary ran from a shell.

## Investigation

The crash report showed a `KERN_PROTECTION_FAILURE` in the executable's own
`__TEXT`: one page of it was `---`. The faulting stack pointer was on a task
fiber, and that page sat 984 KB below it.

An isolated dynamic import compiles the target as a shared library with its
own `main`. The importer's loader runs that `main` once, on the importer's
fiber. That `main` called `__kml_stack_guard_init` (ADR-01583), which:

- put its guard page 984 KB below the current stack pointer. On a fiber,
  that address is whatever is mapped there. When a Go process starts the
  program, the layout puts the executable's code there.
- replaced the importer's SIGSEGV/SIGBUS handlers with the island's copy,
  which has no throw path.

## Decision

- An island's `main` does not call `__kml_stack_guard_init`
  (`codegen/llvm/emitter.go`). The importer's handler covers the whole
  process. The island still embeds the stack-guard runtime file, because its
  task fibers take their stacks from `__kml_fiber_stack_alloc`.
- On macOS, `sg_limit_main` (`codegen/llvm/stackguardsrc/stackguard.c`)
  places the guard page only on the main thread, and only when the stack
  pointer is inside that thread's stack. On Linux, `MAP_FIXED_NOREPLACE`
  already refuses an address that is mapped.

## Verification

- `TestE2EDynamicImportIsolated` passes under `go test` (macOS); it failed 5
  of 5 before.
- `TestE2EDynamicImport*` and `TestE2EStackOverflow*` pass (macOS).
