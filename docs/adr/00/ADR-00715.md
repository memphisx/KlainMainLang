# ADR-00715: `as T` on `JSON.parse` / `.json()` supplies the projection target

- **Relations**: Extends ADR-00371 (a scoped carve-out from full assertion erasure); softens the ADR-00571 member-target caveat
- **Date**: 2026-09-05

## Context

`benchmarks/programs/klain/json_churn.ts` writes the idiomatic
`const parsed = JSON.parse(text) as Record[]`. Under ADR-00371 every
`as T` is erased and the expression keeps its own inferred type, so
`parsed` stayed `any` and the parse took the dynamic NaN-boxed-tree path
(`__kml_dynjson_from_node`) — even though the program explicitly named the
concrete shape, and even though the same program with
`const parsed: Record[] = JSON.parse(text)` routes through the typed
projection (`emitDeclJSONProjection` → `emitJSONProject`). Beyond the
performance asymmetry, this blocked TDD-00175 Stage 1 (deep reclamation),
which covers typed projections only.

In real TypeScript the *static* type of `JSON.parse(x) as T` **is** `T` —
the assertion narrows `JSON.parse`'s declared `any`. In this compiler the
static type drives representation, so honoring the assertion here is the
*faithful* behavior; manufacturing a dynamic tree from an explicitly-typed
expression was the divergence. `-compat=strict`'s identity is "no loose
`any` soup" — the dynamic tree remains `-compat=js`'s (and the untyped
declaration context's) job.

## Investigation

- `parser/parser_exprs.go:51-66` — `as`/`satisfies` parsed and dropped.
- The projection target reaches `JSON.parse` only through a declaration
  annotation (`emitDeclJSONProjection`, emit_objects.go) — the bare-call
  path (`emit_call.go`) hard-codes `TypeAny`.
- Alternatives considered for carrying the asserted type:
  - a general `TypeAssertion` AST node — rejected: ~13 generic expression
    walkers (free-variable scanners, escape/purity checks, task
    classification, both resolver rewriters …) would each need a case, a
    real regression surface for a change whose *behavior* is scoped to two
    call shapes;
  - a parser rewrite special-casing the pattern into a synthetic
    annotation — rejected as too magic, and it loses the node for future
    generalization.
- Chosen shape: an `AssertedType *TypeAnnotation` **field on
  `ast.CallExpression`**, attached by the parser only on the honored call
  shapes. Zero walker churn; the follow-up design question (TDD-00176) can
  widen what *consumes* it without re-touching syntax.
- Found while wiring: the resolver's module renaming rewrites type names
  inside declaration annotations (`rewriteType`, resolver/rename.go) but
  naturally didn't visit the new field — the asserted `Rec` missed the
  mangled `Rec__kml_mod0` interface entry and resolved to the numeric
  default. Repro: `codegen error: field access on non-object`.

## Decision

`expr as T` written **directly on** a `JSON.parse(...)` call or a
`.json()` method call (either optionally `await`-wrapped) supplies the
projection target type, exactly as a `const p: T = ...` declaration
annotation does. Everything else about ADR-00371 stands: all other `as`
targets, `as const`, the angle-bracket form (ADR-00451), and — pointedly —
`satisfies T` stay fully erased. `satisfies` never narrows in TypeScript
(`JSON.parse(x) satisfies T` remains `any` there too), so including it
would itself be a fidelity bug.

Honored under `-compat=strict` only; `-compat=js` keeps the JS-faithful
dynamic tree (its declarations are any-backed regardless). A target the
projection cannot deserialize into (class, union/`any`, function) declines
the attachment and keeps today's dynamic-tree behavior rather than
erroring — matching erased-assertion semantics for shapes the carve-out
doesn't cover.

## Implementation notes

- `ast/nodes.go` — `CallExpression.AssertedType`.
- `parser/parser_exprs.go` — the `as` loop attaches (never a wrapper
  node); `assertableCall` recognizes the shapes; chained `as A as B`
  keeps the outermost.
- `resolver/rename.go` — `rewriteType(e.AssertedType, …)` alongside the
  existing call-site `TypeArgs` rewrite.
- `codegen/llvm/emit_call_json.go` — `callAssertedTargetTy` (resolve +
  honor gate); consumed by `emit_call.go` (bare `JSON.parse`, bare
  Response `.json()`) and `emit_exprs_types.go` (both `inferExprType`
  sites), which is what makes an *unannotated* `const p = JSON.parse(s)
  as Rec[]` flow into the typed array-decl emitter and from there through
  `emitDeclJSONProjection` unchanged.
- A declaration annotation still wins over the assertion when both are
  present (the decl emitters never consult the call's field).

## Side effects discovered

- The ADR-00571 caveat ("member/element assignment targets aren't
  projected") no longer bites for the asserted form:
  `obj.items = JSON.parse(s) as Item[]` projects, since the type rides on
  the call and needs no declaration context. Status row updated.
- `json_churn.ts` now exercises the typed path as written — no benchmark
  edit — which is what put TDD-00175 Stage 1's deep free in reach for it
  (ADR-00716).
