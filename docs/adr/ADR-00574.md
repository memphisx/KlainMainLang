# ADR-00574: structuredClone deep-copies Map and Set

- **Relations**: Extends ADR-00113

- **Date**: 2026-09-01

## Context

`structuredClone(obj)` rejected `Map` and `Set` at compile time, alongside the
genuinely un-cloneable reference types (functions, Promise, EventEmitter, …).
But `Map`/`Set` are spec-cloneable — real `structuredClone` deep-copies their
entries — so the rejection was a gap, not a correctness guard.

## Decision

Clone `Map`/`Set` with a runtime entry loop (the rest of `structuredClone` is
compile-time-unrolled, but a collection's entry count is only known at runtime):

- `emitDeepCloneMap`: create a fresh map (str- or num-keyed per the key type),
  walk the source's parallel keys/values arrays, `emitDeepClone` each key **and**
  value (deep, so an object value is independently copied), and insert.
- `emitDeepCloneSet`: same over the elements.

`structuredCloneUnsupportedKind` no longer lists `Map`/`Set`; `emitDeepClone`
dispatches them to the new cloners. `Headers`/`URLSearchParams` (also Map-backed)
are still caught by their own earlier cases, so they stay rejected.

## Scope

`cloneableCollectionElem` restricts the key/value element types to
scalar/string/object — a **nested array/Map/Set** element is rejected with a
clear error, because the clone loop loads each element at its scalar/pointer
slot width, which does not match an array's `{ptr,i64}` aggregate shape.
Extending to array-valued/nested-collection entries is a follow-on. This is the
row's residual caveat.

## Side effects discovered

None. The reject list for the genuinely un-cloneable types is unchanged; only
plain `Map`/`Set` reach the new path.

## Verification

New `TestE2EStructuredCloneMapIsIndependentCopy` (independent entries + a deeply
copied object value) and `TestE2EStructuredCloneSetIsIndependentCopy`; the rest
of the structuredClone suite (scalars/arrays/objects/nested, and the still-
rejected class-instance case) passes. Built and verified on Mac (Apple Silicon).
