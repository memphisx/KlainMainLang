# ADR-01629: `existsSync` follows a link on Windows; a junction reads back without a trailing separator

- **Relations**: Extends ADR-01030
- **Date**: 2026-10-14

## Context

Node's `test-fs-symlink-dir-junction` failed on Windows at
`assert(!fs.existsSync(linkPath))` for a junction whose target does not exist.

## Investigation

- `existsSync` (`lib/node/internal_fs.ts`) was `access(path) === 0`. Access
  does not follow a link on Windows (libuv's `fs__access` reads the link's own
  attributes), so a dangling junction or symbolic link existed. Node's
  `ExistsSync` stats the path after a successful access on Windows for this
  reason. Node 24.19 gives `false` for both a dangling junction and a dangling
  file link; `accessSync` succeeds on both, as ours does.
- `readlinkSync` of a junction gave `C:\dir\` with a trailing separator,
  for any spelling of the target. Node 24.19 gives `C:\dir`.
  `create_junction` stores the separator, as libuv does; the reader kept it.

## Decision

- `existsSync` on Windows stats the path once access succeeds. A failed or
  missing stat is `false`. The callback `exists` stays on access alone, as in
  Node.
- `reparse_target_utf8` (`win32fs.c`) drops a junction's trailing separator
  unless the target is a drive root (`C:\`).

## Implementation notes

`lib/node/internal_fs.ts`, `win32src/win32fs.c`.

## Side effects discovered

The corpus's `test-fs-symlink-dir-junction` (Node 22.11) expects the trailing
separator kept when the link was made with one; Node 24 and 26, the versions
this project matches, drop it. That file stays a Windows failure until the
corpus moves.

## Verification

Windows 11: `TestE2EWinSymlinkJunction` covers both (its old expectation of
the trailing separator encoded the bug), and the Node 24.19 comparison of
four target spellings and two dangling links matches.
