# ADR-00385: Rest parameters in function type annotations

- **Relations**: Extends ADR-00166
- **Date**: 2026-08-27

## Context

A function *type annotation* carrying a rest parameter failed to parse. Both the
rest-only form and the leading-positional-then-rest form were rejected:

```
function apply(f: (...xs: number[]) => number): number { ... }
//                 ^ 1:20: expected type name, got ...
function apply(f: (a: number, ...xs: number[]) => number): number { ... }
//                            ^ 1:31: expected type name, got ...
type Fn = (...xs: number[]) => number;
//         ^ 1:12: expected type name, got ...
```

This surfaced while auditing the Functions & closures caveats. The
[ARRAY-METHODS.md]/[LANGUAGE-CONSTRUCTS.md] "Rest parameters" row carried an
[ADR-00166] caveat phrased as an *arrow-expression* lookahead gap — "a rest-only
arrow parameter list … fails to parse … the arrow-function lookahead never
checks for a leading `...` token." That description is now stale: every
arrow-*expression* rest form parses and runs today (rest-only `const f = (...xs:
number[]): number => …`, as a call argument, returned from a function, and as an
IIFE were all verified compiling). The genuine remaining gap was in the separate
type-annotation grammar, which callback-heavy code and `.d.ts` files exercise
constantly.

## Investigation

The function-type parameter loop in `parser/parser_types.go` (the
`tok.Type == lexer.LPAREN` branch, ~line 212) parsed each parameter as an
optional documentation-only `name:` followed by a type annotation. It had no
case for a leading `lexer.ELLIPSIS` token, so `...` fell straight through to
`parseTypeAnnotation`, which errors with `expected type name`.

The codegen side already had the needed representation: `Type.FuncHasRest`
(`codegen/llvm/types.go:36`) marks the last `FuncParams` entry as a rest slot
whose stored type is the collected array type (`number[]`), and the closure
call-site paths (`emit_func.go:1988`/`2060`, `checkSpreadArgs`) already honor it
for arrow/function-expression *values* (`emit_exprs_types.go:2100`/`2138`). Only
the type-annotation → AST → `resolveType` path failed to carry the flag, since
the AST `TypeAnnotation` had no rest marker at all.

## Decision

Thread a rest marker through the three layers, reusing the existing
`FuncHasRest` convention rather than inventing a per-parameter representation:

1. **AST** (`ast/nodes.go`): add `FuncHasRest bool` to `TypeAnnotation`,
   documented to mark the last `FuncParams` entry as a rest slot holding the
   collected array type — mirroring `codegen/llvm` `Type.FuncHasRest`.
2. **Parser** (`parser/parser_types.go`): in the function-type parameter loop,
   consume an optional leading `...`. Only the final parameter may be rest — a
   `...` seen when a rest was already recorded, or any further parameter after a
   rest, is a clean `a rest parameter must be last in a function type` error.
   Set `FuncHasRest` on the produced function-type annotation.
3. **Codegen** (`codegen/llvm/emitter.go` `resolveType`): copy
   `ta.FuncHasRest` onto the `FuncType` it builds, so a value assigned to the
   annotated slot is called with the same variadic/spread machinery a directly
   -written rest closure already uses.

## Implementation notes

- The rest marker is a single bool because a rest parameter is always last;
  this matches the existing `Type.FuncHasRest` semantics exactly, so no
  downstream call-site code needed changing — the flag simply now also arrives
  from a written type annotation, not only from an inferred closure literal.
- The stored parameter type for a rest slot is the whole array type
  (`number[]`), consistent with how `emit_exprs_types.go` records it for closure
  literals; the collected-element handling at call sites is unchanged.

## Side effects discovered

- The [ADR-00166] "Rest parameters" caveat is stale in its arrow-expression
  framing (all arrow-expression rest forms already parse). The status row is
  updated to drop that wording; the row now has an empty Caveats cell and enters
  Strict Coverage.
