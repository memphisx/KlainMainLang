# ADR-00832: `Number.prototype.toExponential()` with no argument (shortest round-trip)

- **Relations**: Extends [ADR-00551](ADR-00551.md) (the fixed-precision `toExponential`) and [TDD-00080](../tdd/TDD-00080.md) (the shortest-round-trip `__kml_dtoa`)
- **Date**: 2026-09-10

## Context

`(12345).toExponential()` — the no-argument form — was a compile error
("toExponential takes exactly 1 argument"), while Node returns the value in
exponential notation with the minimum number of mantissa digits that uniquely
represent it (`1.2345e+4`). A real parity gap. Unlike the `fractionDigits` form,
this cannot use a fixed `sprintf("%.*e", …)` precision — it needs the
shortest-round-trip digit count.

## Investigation

The default number→string formatter `__kml_dtoa` (`dtoasrc/dtoa.c`, TDD-00080)
already computes exactly that: it loops `prec` 1..17, formats with `"%.*e"`, and
picks the first precision whose `strtod` round-trips to the original double —
then lays the digits out per ECMAScript `Number::toString`, including a JS-style
exponential branch (sign always, no zero-padding). `toExponential()` with no
argument wants the same shortest digits but *always* in exponential form, so the
right move was a sibling that reuses that loop and emits only the exponential
branch — not a reimplementation.

## Decision

- New C helper `__kml_dtoa_exp(char *buf, double v)` in `dtoa.c`: handles
  `NaN`/`±Infinity`/`0` (`"0e+0"`), runs the same shortest-`prec` `%.*e`
  round-trip loop as `__kml_dtoa`, then renders `d0[.rest]e±exp` in JS style
  (sign always present, exponent unpadded). Declared in IR by `ensureDtoa`
  alongside `__kml_dtoa`.
- `emitNumberToExponential` accepts 0 or 1 args: 0 args → `__kml_dtoa_exp` into a
  scratch buffer, finalized as a length-headed string; 1 arg → the existing
  fixed-precision `%.*e` + `__kml_strip_exp_zeros` path, unchanged.
- `inferExprType` already types `toExponential` as a string (`TypePtr`) — no
  change.

## Implementation notes

`dtoasrc/dtoa.c` (`__kml_dtoa_exp`); `float_fmt.go` (`ensureDtoa` declares it);
`emit_strings.go` (`emitNumberToExponential` 0-arg branch). The Number row's
`toExponential` caveat is retired (now a note).

## Verification

macOS (Apple Silicon M4): repro matches Node across `(12345)` → `1.2345e+4`,
`(0.1)` → `1e-1`, `(100)` → `1e+2`, `(0)` → `0e+0`, `(-12345)` → `-1.2345e+4`,
`(3.14159)` → `3.14159e+0`, `(1e21)` → `1e+21`, and the 1-arg `(5).toExponential(2)`
→ `5.00e+0`. New `TestE2ENumberToExponentialNoArg` + `go test -run
'TestE2ENumber|TestE2EMath'` green.
