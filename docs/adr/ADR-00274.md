# ADR-00274: Nested generators (by-reference capture), async `yield*` over an async iterable, and the nested-function resolver fix

- **Relations**: Implements [TDD-00094](../tdd/TDD-00094.md) stages 1–3; extends [ADR-00253](ADR-00253.md), [ADR-00259](ADR-00259.md)–[ADR-00261](ADR-00261.md) (generators); reuses [ADR-00001](ADR-00001.md) (closure capture) and [ADR-00269](ADR-00269.md) (`Symbol.asyncIterator`)
- **Date**: 2026-08-20

## Context

The async-generators row was ✅ but not strict, held out by three caveats: (1) a nested `function*`
was a clean rejection; (2) `.next()` returns an already-resolved promise; (3) `yield*` delegated to
a generator only. This closes (1) and (3) and audits (2). Along the way it fixes a **pre-existing**
resolver bug that blocked nested generators from being useful.

## Investigation

- **Nested generators.** A nested `function*` reached `emitFunctionDeclAs`'s "not yet supported"
  reject. Generators have what plain nested functions lack — a per-instance heap struct and a
  construction site — so a closure env can ride on the instance rather than needing general
  function-declaration capture (which does not exist: only arrows capture).
- **Pre-existing resolver bug (the real blocker).** A nested function — generator *or* plain — could
  not call a top-level function: `function outer(){ function inner(){ return dbl(21) } }` failed with
  `undefined function 'dbl'`. Root cause: `resolver/rename.go`'s `rewriteStmt` had **no
  `*ast.FunctionDeclaration` case** (its comment claimed nested functions "aren't supported"), so the
  rename pass never descended into a nested function's body — top-level references inside it were
  never mangled to their `__kml_mod<n>` names, so they didn't match `e.funcs`. Orthogonal to
  generators; surfaced by them.
- **`.next()`-shape audit.** Confirmed a **real** divergence, not a misplaced note:
  `async function* g(){ console.log("body"); yield 1 }; g().next()` prints `body` **synchronously**
  at the `.next()` call, where JS runs the body as a microtask (`before, after, body` in JS vs
  `before, body, after` here). `emitAsyncGeneratorNextCore` swaps into the fiber and settles the
  promise synchronously.

## Decision

1. **Nested generators (stages 1–2).** Register a nested `function*` in `pushNestedFuncScope` as a
   `GeneratorInfo` (new `nestedFuncEntry.Gen`); `lookupGenerator` resolves it (nested scopes before
   `e.generators`). Its captures are gathered at the declaration's emission (`gatherGenerator
   Captures`, using a `scanExprFV` now extended with `yield`/`await` cases) and recorded on the
   info. `GeneratorType` gains an `__env` field; construction boxes each captured cell **by
   reference** (reusing the arrow boxing, ADR-00001) into the env and stores it in `__env`; the body
   binds each capture through `__env` as a `Boxed` symbol. So a mutation of an enclosing `let` after
   the generator is created is seen by a later `.next()` — JS-faithful. Sync and async fall out of
   the same code. An array capture stays a clean rejection.
2. **Resolver fix.** `rewriteBlock` hoists nested function names into the block frame; `rewriteStmt`
   gains a `*ast.FunctionDeclaration` case that walks the body — so nested-local names stay local and
   the body's top-level references get mangled.
3. **Async `yield*` over an async iterable (stage 3).** `emitYieldStar`, when its operand is a
   `Symbol.asyncIterator` class inside an async generator, delegates via a new
   `emitYieldStarAsyncIterable`: get the iterator, loop `await it.next()` and re-yield each `{value}`
   until `done` — the iterator/await core reused from `emitForAwaitOfAsyncIterable`. V1 forwards
   values only.

## Side effects discovered

- The `scanExprFV` fix (adding `yield`/`await`) also closes a latent bug: a closure capturing a
  variable used **only** inside an `await`/`yield` in its body previously missed the capture.
- **The `.next()`-shape caveat is real (stage 4), and the deferral deadlocks** — *the deadlock was
  later root-caused and fixed in [ADR-00275](ADR-00275.md) (the step settled its promise without
  draining reactions); the deferral now ships. That clears the `.next()` caveat; the last
  divergence (a `yield*` over a user async-iterable delegating `.throw`/`.return` into the inner's
  optional methods) was then closed in [ADR-00276](ADR-00276.md), taking the row to strict.* Driving the row to
  strict needs the async generator's `.next()` to return a genuinely-pending promise — the body run
  as a microtask, not synchronously. This was **attempted**: `emitAsyncGenStepBody` was factored out,
  a per-generator-type microtask step function emitted, and `.next()` changed to enqueue it and
  return a pending promise. It compiles but **deadlocks at runtime**: the awaiter parks on the
  pending `.next()` promise, the microtask step swaps into the generator fiber, and control never
  returns to resume the awaiter — a fiber/microtask/scheduler-interaction bug that needs lldb-level
  tracing of the swap chain, not a contained change. Reverted to the synchronous swap-and-settle
  (`emitAsyncGenStepBody` kept, called synchronously); the deferral scaffolding was removed to avoid
  dead code. So this ADR closes 2 of the 3 caveats; the row stays ✅-not-strict until the
  deferred-`.next()` deadlock is debugged — a focused fiber-scheduler effort, precisely located here.

## Verification

Mac (Apple Silicon M4). `go build`, `go vet ./...` clean. New E2E tests: non-capturing nested
generator, capturing (by-value and by-reference — `10`→`99` after mutation), nested async generator
with capture + top-level `await`, a nested function/generator calling a top-level function (the
resolver fix), and async `yield*` over a `Symbol.asyncIterator` range. Full `go test ./...` (and
`make test-par`) green; the broad resolver change verified across the whole suite.
