# TDD-00235: process stdio, tty and readline as TypeScript modules

- **Status**: Implemented
- **Date**: 2026-09-29

## Context

TDD-00230 P3.1 moves Node's modules that are JavaScript in Node into
TypeScript. TDD-00231 did `net`, `tls`, `http`, `https` and `stream`, and
TDD-00234 did `child_process`. The process's own stdio and `readline` are
still code-generated (`emit_stdin.go`, `runtime_stdin.go`,
`emit_readline.go`, `runtime_readline.go`, and the `process.stdout.write`
special forms). That form cannot match Node:

- `process.stdin` is not a stream:
  - `'data'` delivers strings, not Buffers;
  - it has no `pause()`/`resume()`/`read()`/`'readable'`, no `pipe()` and
    no async iteration;
  - each event takes one listener, and only an arrow or function-expression
    literal;
  - listeners run synchronously from the dispatch.
- `process.stdout`/`stderr` have only `.write`, `.isTTY`, `.columns` and
  `.rows`. They can't be piped into, have no `'resize'`, and their writes
  take no callback or encoding.
- `readline.createInterface` ignores its options: input is always stdin,
  output always stdout, and there is one interface at a time. It has no
  `'pause'`/`'resume'`/`'SIGINT'`, no history, no completer, no
  `prompt()`/`setPrompt()`, no async iteration and no `readline/promises`.
  It can't read a file stream or a child's stdout line by line, the most
  common use in CLI tools.
- `tty` has no module: no `isatty`, `ReadStream`, `WriteStream`, cursor
  helpers or colour depth.
- `klain:tty`'s `readByte()`/`readKey()` exist only because a raw
  `process.stdin` did not. They match no standard API.

Node's own `lib/tty.js`, `lib/readline.js`, `lib/internal/readline/*.js`
and `lib/internal/bootstrap/switches/is_main_thread.js` (`getStdin`,
`getStdout`, `createWritableStdioStream`) are JavaScript over three native
pieces:
- a TTY handle (`tty_wrap`: `setRawMode`, `getWindowSize`);
- a pipe handle (`pipe_wrap`, which `net.Socket` wraps);
- `guessHandleType(fd)`.

The stream half exists here: `lib/native.d.ts`'s TCP handles are fd-generic
stream handles, and `net.Socket` takes an existing handle
(`new Socket({ handle })`, TDD-00234).

## Design

### Native surface (`lib/native.d.ts`, `klainpool.c`)

- `guessHandleType(fd): 'TTY' | 'FILE' | 'PIPE' | 'TCP' | 'UNKNOWN'` —
  `fstat` + `isatty`, as libuv's `uv_guess_handle`.
- `streamOpen(fd, readable): number` — an existing descriptor as a stream
  handle in the reactor's table, libuv's `uv_pipe_open`/`uv_tty_init`.
  - A readable TTY is reopened through its `/dev/tty`-equivalent path
    (`ttyname`), as `uv_tty_init` does. Making the shared descriptor
    non-blocking would change the terminal for the parent shell too.
  - A pipe or socket is put in non-blocking mode.
  - The handle keeps the loop alive only while active (reading, writing,
    closing), per ADR-01231.
- `ttySetRawMode(handle, mode)`: `tcsetattr` with libuv's raw flags, the
  original mode restored at exit (`uv_tty_reset_mode`).
- `ttyGetWindowSize(handle): [cols, rows] | null`.
- `writeSync(fd, bytes)`: a blocking write loop. For a regular file, TTY or
  POSIX pipe, Node's stdout and stderr write synchronously (Node docs
  "A note on process I/O"). Synchronous writes also keep `process.stdout`
  ordered with `console.log`, which writes the descriptor directly.
- SIGWINCH is delivered through the reactor's signal pipe as a
  window-size change on every TTY write handle.
- Windows:
  - console handles take the win32io layer (`ReadConsoleInputW` for a raw
    console, `SetConsoleMode`);
  - pipes take overlapped named pipes, as `net`'s handles do;
  - this is compile-checked here and first run on the Windows machine.

### TypeScript

- **`lib/node/tty.ts`** — a port of `lib/tty.js`:
  - `isatty`;
  - `ReadStream extends net.Socket`: `isRaw`, `isTTY`, `setRawMode`;
  - `WriteStream extends net.Socket`: `columns`/`rows`, `'resize'`,
    `getWindowSize`, `getColorDepth`/`hasColors` (Node's
    `internal/tty.js` env rules), `cursorTo`, `moveCursor`, `clearLine`,
    `clearScreenDown`. Its `_write` goes through `writeSync` for a TTY.
- **`process.stdin` / `stdout` / `stderr`** — created on first read, as
  Node's getters do (`getStdin`, `createWritableStdioStream`):
  - by `guessHandleType`: a TTY → `tty.ReadStream`/`WriteStream`; a pipe
    or socket → `net.Socket` over `streamOpen`; a file → `fs.ReadStream`
    for stdin and a synchronous `fs` Writable for output;
  - stdin starts paused (a `'data'` listener, `resume()`, `pipe()` or
    async iteration starts it) and delivers Buffers unless `setEncoding`
    is called. `pause()` stops reading, so a program that only pauses
    stdin exits.
  - `process` is still code-generated, so these getters bind the
    TypeScript objects the way `url`'s companion globals are bound
    (`companionMangled`).
- **`lib/node/readline.ts`** — a port of Node v24's `lib/readline.js`,
  `lib/internal/readline/interface.js`, `callbacks.js`, `utils.js`,
  `emitKeypressEvents.js` and `promises.js`:
  - the `Interface` over any Readable input and optional Writable output:
    `'line'`, `'close'`, `'pause'`, `'resume'`, `'SIGINT'`, `'SIGTSTP'`,
    `'SIGCONT'`, `'history'`;
  - `crlfDelay`, `terminal` (key decoding, line editing, history,
    `completer`, `prompt`/`setPrompt`/`getPrompt`, `write`, `line`,
    `cursor`, `getCursorPos`);
  - `question` with an `AbortSignal`, `[Symbol.asyncIterator]` over
    `'line'` events (Node's `on(this, 'line')` buffering);
  - `readline.promises` and `readline/promises` (`Interface.question`
    returning a promise, `Readline` for cursor control);
  - `cursorTo`, `moveCursor`, `clearLine`, `clearScreenDown`,
    `emitKeypressEvents`.
- **Deletions.** The code-generated stdin, readline and
  `process.stdout.write` forms and their runtime are deleted, and so is
  `klain:tty` (`readByte`/`readKey`): a bespoke API matching no standard.
  Its uses become `process.stdin.setRawMode(true)` + `'data'`, including
  the `klain:tui` loop (TDD-00150), whose key reads move to a `'data'`
  listener.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| TypeScript builtin modules | Built | TDD-00231 |
| `net.Socket` over an existing handle | Built | TDD-00234 |
| Stream handles, reactor dispatch, active-handle keepalive | Built | `klainpool.c`, ADR-01231 |
| `fs.ReadStream` in TypeScript | Missing | `fs` streams are code-generated; a file stdin needs a Readable over `fsRead` (the thread-pool natives exist) |
| `process` object members bound to TypeScript values | Missing | the `url` companion mechanism covers module globals, not `process.stdin` |
| `StringDecoder` for `setEncoding` | Unknown | checked during implementation |

## Open questions

- Whether `process` itself should move to TypeScript first (it is still
  codegen: `argv`, `env`, `exit`, `on('SIGINT')`, …) or keep the binding
  mechanism above until P3.2.
- A file stdin: Node reads it through `fs.ReadStream`, which is not yet a
  TypeScript module. Either port `fs.ReadStream`/`WriteStream` first (a
  larger `fs` step) or give a file descriptor a stream handle too (the
  reactor reports a regular file always readable, as `poll` does).

## Notes

- Implemented by ADR-01239 (stdio, `tty`) and ADR-01243 (`readline`,
  `readline/promises`). A file stdin is a stream handle over the descriptor,
  not an `fs.ReadStream`.
- `klain:tty`'s deletion is not a restructure step: it moved to BACKLOG
  (after the restructure).
- Windows console and pipe handles are compile-checked only; the Windows
  machine runs them first.
