# ADR-00684: `fs` errors carry `err.code` (`ENOENT`, …)

- **Date**: 2026-09-03

## Context

Every `fs` failure threw an Error whose `.code` was unset, so the canonical
Node idiom `if (e.code === 'ENOENT')` never matched (found in the faithfulness
audit — the highest-leverage `fs` coverage gap for CLI tools).

## Investigation

`errorObjType` (`emit_exceptions.go`) already has the Node error-code trio —
fields 3–5 `code`/`errcode`/`errstr` — populated for `node:sqlite` failures
(ADR-00540). But `__kml_fs_throw` (`runtime_fs.go`) hand-built a **truncated
24-byte, 3-field** object (`kind`/`message`/`name`) and never set the trio, so
`.code` read unset memory.

## Decision

`__kml_fs_throw` now mallocs the full `errorObjType` (`StructSize()`) and fills
the trio: `code` = the errno **name** string via a new `__kml_errno_code`
mapper, `errcode` = the raw errno, `errstr` = `strerror`. The mapper's
errno→name switch is generated from Go's `syscall.Exxx` constants, so the
numeric values are correct on **both** Linux and macOS (they differ for
`ENAMETOOLONG`/`ELOOP`/`ENOTEMPTY`); an unmapped errno yields `null`.

## Side effects discovered

`.code` is now faithful; `err.errno` (the negative numeric errno Node exposes),
`err.path`, and `err.syscall` remain absent (the caveat is narrowed, not
removed). The message string format still differs from Node's
`ENOENT: <text>, <syscall> '<path>'` — a separate follow-up.

## Verification

Mac. `readFileSync('/nope')` → `e.code === 'ENOENT'` is `true`; `mkdirSync` on an
existing dir → `EEXIST`; `.message`/`.name` unchanged. E2E test; full fs
regression green. Linux errno values covered by the `syscall`-derived switch (to
re-verify on the Ubuntu box / CI).
