# ADR-00688: assigning an incompatible value to a typed array element emitted invalid IR

- **Date**: 2026-09-03

## Context

The invalid-IR backlog's `constant expression type mismatch: got type 'ptr' but
expected 'double'` cluster. Repro: `var a = []; a[100] = "not a number"` — `a`
infers `number[]`, and storing a string into a `double` slot emitted a
pointer-typed constant against a `double` element: invalid IR.

## Investigation

The `arr[i] = value` path (`emit_exprs_assign.go`) coerced the RHS to the
element type with plain `coerce`, then `storeArrayElem`. But `coerce(stringValue,
double)` can't convert a pointer to a scalar and returns the value unchanged, so
the mismatched operand reached the store — the same "coerce silently returns an
incompatible value" shape as ADR-00686.

## Decision

Use `coerceChecked` (which runs `coercionIsSound`) instead of plain `coerce` for
the array-element store: a value that genuinely can't convert to the element
type is a clean compile error (`type mismatch in array-element assignment`)
rather than invalid IR. This is the correct typed-subset behavior — `const a:
number[] = []; a[i] = 'str'` is a type error. Under `-compat=js` the element type
is `any`, into which every value coerces (boxes), so only a genuine strict-mode
mismatch is rejected; valid stores (`number`→`number[]`, `string[]`, nested
`number[][]`, typed-array clamps) are unaffected.

## Verification

Mac. `a[100] = "not a number"` on a `number[]` is now a clean compile error, not
a clang crash; `number`/`string`/nested-array/typed-array assignments still
compile and run. In `built-ins/Array` this cleared 3 more invalid-IR files
(CLANG_ERROR 33→30). Full array/assign/typed-array/object regression green (78s).
