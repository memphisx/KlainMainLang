# ADR-00866: Bitwise/shift operators run the ToPrimitive number ladder on object operands (TDD-00201)

- **Relations**: `Implements TDD-00201`, `Corrects ADR-00859`
- **Date**: 2026-09-11

## Context

`({valueOf: function(){return 1}} & 1)` — an object literal used *inline* as a
bitwise/shift operand — emitted `trunc i64 <object ptr> to i32`, invalid IR clang
rejects with `'%t' defined with type 'ptr' but expected 'i64'`. Test262
`language/expressions/bitwise-and/S11.10.1_A2.2_T1.js` (and `A2.3_T1`) are the
representative CLANG_ERROR files. ADR-00859 catalogued this exact file under "side
effects discovered" as a *full-file interaction bug* that "compiles in isolation" —
that diagnosis was wrong; see below.

## Investigation

ADR-00859 wired the ToPrimitive number ladder into two places: a `coerce` hook
(object → numeric target) and an `emitBinary` pre-pass for `- * / % ** < > <= >=`.
It reasoned that bitwise/shift operators "already coerce operands to i64 (running
the same ladder through `coerce`), so they are not listed" in the pre-pass.

That reasoning does not hold for an inline object-literal operand. By the time
`toInt32`/`emitBitShift` call `coerce(operand, i64)`, the operand's Value no longer
reliably carries its `IsObject` type (it has been materialised as a bare `ptr`), so
`coerce`'s `objectMayToPrimitive` guard does not fire and the raw pointer is
truncated. The pre-pass, which runs on the freshly-typed `emitExpr` result, is the
dependable hook — exactly as it already is for arithmetic/relational. The
"compiles in isolation" / "full-file interaction" framing in ADR-00859 was an
artefact of a named-`const` operand (whose Value stays object-typed through
`coerce`) versus an inline literal; it is not a whole-file phenomenon.

## Decision

In `emitBinary` (`emit_exprs_operators.go`):

- Add `& | ^ << >> >>>` to the **number-hint ToPrimitive pre-pass** alongside the
  arithmetic/relational operators, so an object operand with an applicable
  `@@toPrimitive`/`valueOf`/`toString` method field is coerced to its primitive
  (then to `double`) before `toInt32`/`emitBitShift` truncates to i32.
- Add the same operators to the **strict no-primitive reject** branch, so an object
  with no usable numeric ToPrimitive method (e.g. `valueOf`/`toString` both return
  objects) produces the clean "operator on an object without a primitive value"
  compile error — matching TypeScript, which rejects a non-number bitwise operand —
  rather than truncating a pointer. `-compat=js` behaviour is unchanged (it routes
  through the existing dynamic dispatch).

This is pure mirroring of the arithmetic path; no new mechanism. Faithful in both
`-compat` lanes (the object is statically typed — no NaN-box/`any`).

## Side effects discovered

- **Function / non-primitive operands under `-compat=js` remain invalid IR** for
  *every* binary operator (`f - 1`, `{} & function(){}` in the js lane emit
  `sub ptr`/`trunc ptr`). This is the pre-existing broad "operator-on-any"
  compat=js gap, not specific to bitwise and not introduced here — strict rejects
  these cleanly at the declaration/operator layer. Tracked in the invalid-IR
  backlog, not as a caveat on this feature.
- `bitwise-and/S11.10.1_A2.4_T2.js` and `order-of-evaluation.js` still CLANG_ERROR
  with "expected value token": a bitwise operand that is a throwing call returning
  `never`/void emits an empty operand. Separate invalid-IR family (empty-operand,
  cf. ADR-00856); a distinct repro.
