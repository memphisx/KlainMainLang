# ADR-01500: `reduce` on a builtin iterator has the lib's type

- **Relations**: Extends ADR-01494, TDD-00230
- **Date**: 2026-10-09

## Context

After ADR-01494, Test262
`built-ins/Iterator/prototype/reduce/reducer-memo-can-be-any-type.js`
emitted invalid IR on the strict lane. The test calls
`values[Symbol.iterator]().reduce(f, {})`. The variable taking the
result got a `ptr` slot, but the lib's `Iterator.prototype.reduce`
returns a boxed `any` (`i64`).

## Investigation

- Name-based inference typed every two-argument `.reduce(f, seed)`
  call as the seed's type without checking the receiver. That is right
  only for an array's own reduce.
- At module level, `values.values().reduce(...)` worked only because
  the global pre-pass typed the result from the checker. In a function
  body the same call fell to the i64 default, so `{}` printed as `0`.

## Decision

- The seed-typed `reduce` rule applies only when the receiver is an
  array.
- `reduce` on an Array, Map or Set iterator takes the checker's type of
  the call. The lib result is coerced at the store like any other
  `any` value.

## Divergences

None.

## Files

codegen/llvm/emit_exprs_types.go

## Verification

- DeskMini (Linux x86-64), compared with Node:
  - `{}` seed: prints `{}` at module level and in a function body;
  - numeric seed: `16 number`.
- Test262 strict, `built-ins/Iterator` category (654 files): no new
  failures and no invalid IR. The test above now fails at run time
  instead.
