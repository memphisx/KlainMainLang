# ADR-00722: `path.win32` — per-host `path` flavour, explicit `path.posix`/`path.win32`, Windows file URLs

- **Relations**: Implements [TDD-00178](../tdd/TDD-00178.md); extends [ADR-00719](ADR-00719.md) (Windows Stages 1–4, the open Stage 1 item), [ADR-00671](ADR-00671.md) (file-URL pair, POSIX)
- **Date**: 2026-09-06

## Context

After the Windows port, `path` still meant `path.posix` on Windows: `\` was
not a separator, `path.sep` was `/`, and `path.join('C:\\Users', 'me')`
produced `C:\Users/me`. Node's `path` on Windows is `path.win32`, and Node
exposes both `path.posix` and `path.win32` on every platform. TDD-00178
chose a C port of Node's `lib/path.js` win32 object over an IR port; this
ADR records what landed and what the port exposed on the way.

## Investigation

- Node's algorithms were taken from `lib/path.js` at v24.x and ported
  function by function with the JS names kept, so `path_win32.c` reads
  against the JS. Every helper the win32 object relies on
  (`normalizeString`, `isWindowsReservedName` including the superscript
  `COM¹`-style names, `isWindowsDeviceRoot`, `_format`) is in the file.
- Faithfulness was checked by a differential harness rather than by
  reading: 186 cases (join/resolve/dirname/basename/extname/isAbsolute/
  parse/format, including drive-relative, UNC, `\\?\` and `\\.\` device
  paths, reserved names, mixed separators, trailing separators) run
  through the C under ASan/UBSan and through real Node 24's `path.win32`,
  outputs diffed: zero mismatches. Two of my own initial expectations
  were wrong and the oracle corrected them (a UNC root is its own
  `dirname`; `parse` of a UNC path reports the share root with its
  trailing separator as both `root` and `dir`).
- The `resolve()` no-argument case is the one place Node's win32 code
  branches on the host (`isWindows`): on a non-Windows host it returns
  `cwd` with `/` replaced by `\`. The sidecar takes that flag from the
  emitter.
- One port bug found by the harness before it reached a test: `dirname`'s
  reverse scan set `matchedSlash` on the separator branch instead of the
  non-separator branch, which turned `C:\a\b\c` into `C:\a`.
- `url.pathToFileURL` / `url.fileURLToPath` (ADR-00671) were "working" on
  Windows only because `path.resolve` was posix: with the win32 default
  they produced `file:///C:%5Cfoo` and could not parse a drive path back.
  Node's win32 halves (`lib/internal/url.js`: `pathToFileURL` with the UNC
  branch, `getPathFromURLWin32`) are ported into the same sidecar. Two
  libcurl behaviours had to be worked around there: it serialises a
  `file:` URL without its host (so a UNC href is rebuilt from host +
  pathname), and it refuses `file://server/...` outright
  (`CURLUE_BAD_FILE_URL`), so the host is split off before parsing and
  rejoined afterwards. It also returns a drive path without the leading
  `/` (`C:/foo` for `file:///C:/foo`), which the sidecar normalises.

## Decision

- `codegen/llvm/pathsrc/path_win32.c` (embedded via `path_win32.go`,
  listed in `EmbeddedCSources` and the test harness's sidecar list) holds
  the win32 flavour; the posix flavour stays as the IR in `runtime_path.go`.
- `pathFlavorOf(objExpr)` resolves the member object: the bare module
  marker is the host's flavour (`runtime.GOOS == "windows"` → win32,
  the same compile-time switch as `process.platform`), `path.posix` and
  `path.win32` are explicit. Every `emitPath*` takes the flavour;
  `sep`/`delimiter` and the type-inference entries follow the same table.
  The resolver's member list gains `posix` and `win32`, so
  `import { win32 } from 'path'` binds too.
- `join`/`resolve` pass their compile-time-known argument count and an
  entry-block `[N x ptr]` alloca to the sidecar; `parse` returns the
  existing `PathParsedType` object filled from five out-pointers.
- `pathToFileURL`/`fileURLToPath` branch on the host flavour: posix keeps
  ADR-00671's code path unchanged; win32 evaluates the input once and
  routes both the raw string (a UNC input keeps its host) and the resolved
  path through the sidecar.

## Implementation notes

- Strings cross the C boundary as TDD-00120 heap strings; the sidecar
  allocates its outputs with the `[i64 len][bytes][\0]` header.
- `getenv("=C:")` gives Node's per-drive current directory on Windows (the
  CRT exposes the hidden `=X:` variables); on other hosts it is NULL and
  Node's `cwd` fallback applies.
- The test file `tests/path_test.go` was rewritten: every bare-`path` test
  carries a Windows expectation (backslash forms, or a `cwd`-drive check
  for `resolve`), and new `TestE2EPathWin32*` / `TestE2EPathPosixExplicit`
  / `TestE2EPathNamedFlavourImport` tests run on every host. The file-URL
  tests in `tests/node_core_modules_test.go` gained Windows variants
  (drive paths, UNC, the two Node error messages).
- `examples/path/path_win32.ts` is host-independent by construction
  (explicit flavours only).
- Status: `docs/status/data/path.json` (the "POSIX-only" caveat on
  `sep`/`delimiter` is gone; a `path.posix / path.win32` row is added, with
  caveats for the missing `normalize`/`relative` and for the flavour
  objects being dispatch targets, not values); `_index.json` backlog rows
  for TDD-00177 (item closed) and TDD-00178 (open items). Reference:
  `website/src/data/reference/path.json` lede, `sep`/`delimiter` badge
  now `exact`, a new `path.posixwin32` entry.

## Side effects discovered

- Not fixed here: the posix flavour's trailing-slash caveat on `join`
  remains; converging posix onto the C sidecar (TDD-00178 option C) would
  remove it. `normalize`/`relative`/`toNamespacedPath`/`matchesGlob` are
  missing from both flavours.
- The flavour objects are not first-class: `const p = path.win32` is a
  compile error today. Recorded as a status caveat.
- Tooling, not code: a bash heredoc on the Windows box collapses `\\` to
  `\` even with a quoted delimiter, which first looked like a lexer bug
  ("invalid hexadecimal escape sequence" for `"D:\\x"`). Files with
  backslashes must be written with an editor tool there.

## Verification

- Differential harness (WSL2 clang 18, `-fsanitize=address,undefined`)
  against Node v24.19.0 `path.win32`: 186/186 cases identical.
- Windows 11 (mingw-w64 UCRT clang, MSYS2): `go test -run 'TestE2EPath|TestE2EFileURL' ./tests` passes (15 path tests, 5 file-URL tests, Windows variants active); `examples/path/path_win32.ts` prints the documented output.
- Linux x86-64 (WSL2 Ubuntu 24.04, clang 18, Go 1.27.1): the same test selection passes with the posix defaults and the explicit `path.win32` tests exercising the sidecar; the example prints the same output as on Windows.
- Linux x86-64 Docker (`golang:latest` + release-workflow apt packages + `libclang-rt-19-dev`, clang 19): full `go build`, `go vet`, `make status-check`, `go test ./...`, `make examples` — results in the commit message.
