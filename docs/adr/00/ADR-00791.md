# ADR-00791: process.memoryUsage() heapTotal/heapUsed from the real object heap

- **Relations**: `Implements TDD-00024`, `Extends ADR-00570`
- **Date**: 2026-09-08

## Context

`process.memoryUsage()` returned Node's five-field shape, but only `rss` held
a real value (ADR-00570). `heapTotal`/`heapUsed`/`external`/`arrayBuffers` were
calloc-zeroed, disclosed as a caveat on the grounds that "there is no managed
V8 heap to measure." That is true of a *V8* heap, but this compiler does have
an object heap — either the C allocator's arena (default) or Boehm's collected
heap (`-mm=gc`) — and both allocators can report their total/in-use bytes. A
real `heapUsed`/`heapTotal` is useful for exactly the microservice/CLI target
(leak detection, memory monitoring), and a zero there is a worse answer than a
real-but-reinterpreted one.

## Investigation

- `emit_process.go:emitProcessMemoryUsage` stored only `rss`; the four V8
  fields rode the calloc zero.
- Node semantics: `heapUsed` is the *live* V8 JS-object heap, `heapTotal` its
  reserved size; `external`/`arrayBuffers` are off-heap C++-binding bytes.
- Native analogues:
  - `-mm=gc` (Boehm): `GC_get_heap_size()` is the reserved heap;
    `GC_get_heap_size() - GC_get_free_bytes()` the live bytes. This is a real
    *managed collected* heap, the closest possible analogue to V8's.
  - default (system allocator): Darwin `malloc_zone_statistics` gives
    `size_allocated` (reserved) and `size_in_use` (live); glibc `mallinfo2`
    gives `arena+hblkhd` and `uordblks`. This is the whole-process C arena, not
    a JS-only heap — a reinterpretation, but it *is* this compiler's only heap.
  - `external`/`arrayBuffers`: no native off-heap accounting exists here (Buffers
    live in the same heap/rss), so a faithful value is impossible — they stay 0.
- `mallinfo2` returns a struct **by value** and both allocator-stat structs have
  platform-specific layouts, so this must be a C shim (the termios/tmpdir/homedir
  precedent), never IR-level struct reads.

## Decision

Add `__kml_heap_total_bytes()` / `__kml_heap_used_bytes()` (a new `procmem`
embedded C shim, `ProcMemSource`, gated by `usedHeapStats`/`UsesHeapStats()`).
The shim selects at compile time: `KLAIN_GC` → Boehm; `__APPLE__` →
`malloc_zone_statistics`; `__GLIBC__` → `mallinfo2` (falling back to legacy
`mallinfo` below glibc 2.33); any other platform → 0 (the prior behaviour, so
Windows and musl stay at 0 pending their own verification). `emitProcessMemoryUsage`
now stores `rss`, `heapTotal`, and `heapUsed`. `external`/`arrayBuffers` remain
0, now documented as *no native analogue* rather than *no heap*.

In `-mm=gc` the shim's `CFlags` carry `-DKLAIN_GC=1`; `gc.h` is already on the
global include path `LocateGC` adds, and `-lgc` is already linked in gc mode.

## Implementation notes

- Files: `codegen/llvm/emit_process.go` (store the two fields + shim source +
  getter), `codegen/llvm/emitter.go` (`usedHeapStats`),
  `codegen/llvm/embedded_c.go` (POSIX/all-platform `CSource`, `-DKLAIN_GC` in gc
  mode), `tests/compiler_test.go` (`appendProcMem`, threaded into every build
  chain), `tests/process_test.go`, `examples/process/process_info.ts`.
- The two `declare`s are emitted once (guarded by `usedHeapStats`) so a program
  calling `memoryUsage()` more than once does not emit duplicate declarations.

## Side effects discovered

The pre-existing `process_info.ts` comment already misattributed `rss` to
`getrusage` (ADR-00570 had moved it to `task_info`); corrected in passing.

## Verification

macOS (Apple Silicon M4), default allocator mode: `heapTotal`/`heapUsed` are
positive, `heapUsed <= heapTotal`, and both grow across a large allocation
loop; `external`/`arrayBuffers` are 0. `TestE2EProcessMemoryUsageRssPositive`
updated and green; the whole `TestE2EProcess*`/`TestE2EOS*` suites pass;
`make examples` runs `process_info.ts` clean. The `-mm=gc` (`KLAIN_GC`) and
Linux (`mallinfo2`) branches are encoded but **not** verified on this machine
(libgc is not installed here; Linux is not the dev box) — the Boehm and
glibc APIs used are standard, to be confirmed on those targets like the other
`/proc`/gc paths.
