# ADR-00416: http2 Stage 3 — client sessions (`http2.connect` / `session.request`)

- **Relations**: Implements [TDD-00139](../tdd/TDD-00139.md) Stage 3; Extends [ADR-00415](ADR-00415.md), [ADR-00357](ADR-00357.md)
- **Date**: 2026-08-27

## Context

The last big http2 piece and the TDD's one genuinely-new subsystem: a
client-mode nghttp2 driver. The dominant corpus shape is an in-process pair —
`server.listen(0, () => { const client = http2.connect(…); … })` — which is
also the hard case: one thread, and the existing h2c *server* drive blocks in
`read` between frames.

## Decision

**C driver (`http2src/http2.c`)**: an `h2c_sess` list of client sessions —
`__kml_h2c_connect_url` (parses an `http://host:port` authority, getaddrinfo +
blocking TCP connect, nonblocking thereafter, client-mode nghttp2 session,
SETTINGS submitted; a non-`http://` authority returns NULL → IR throws
naming the TLS limitation), `__kml_h2c_request` (body-less submit —
END_STREAM at submit, i.e. GET-shaped; `:method`/`:path` from the literal,
`:scheme`/`:authority` fixed by the session, plus literal extra headers),
`__kml_h2c_pump_all` (one nonblocking send/recv round per session; fires the
IR callbacks; a `close()`d session terminates with GOAWAY once its last
stream closes), `__kml_h2c_flush` (bounded drive-to-completion, registered
via `atexit` at connect so loop-less programs still finish).

**The deadlock and its fix**: a single pump before the server's blocking read
is not enough — loopback TCP delivery is asynchronous, so the client can read
a partial response, hit EAGAIN, and the process then parks forever in the
server's `read` (diagnosed by stack sampling + byte-level tracing). The
server drive now alternates: while client streams are open, it waits in a
2ms `poll` on its own fd, pumping the client sessions between polls; with no
client work it blocks exactly as before. Server and client drivers share the
file, so this costs no linkage machinery.

**IR bridge**: four generic callbacks (`__kml_h2c_on_header/response/data/
end`) over a fixed 32-byte stream context (cbResponse/cbData/cbEnd/
headersMap), emitted for **every** program that links the h2 driver — the C
file references them unconditionally, which a server-only program's link
otherwise breaks (found the hard way).

**Surface**: `http2.connect(authority, cb?)` → session handle
(`.request(headersLit?)`, `.close(cb?)`, `.destroy()`, accepted-no-op
`.on(...)`/`.ping`/`.settings`); `session.request` → client stream
(`.on('response'|'data'|'end')` with contextual typing through `mustCall`
wrappers, `.end()` no-op, request bodies a clean rejection, `'close'`/
`'error'` accepted no-ops). Response headers arrive as the same
`Map<string,string>` shape the server side uses — `':status'` is a *string*
in the map (corpus asserts of `headers[':status'] === 200` fail honestly;
Node types it as a number).

## Side effects discovered

Two real pre-existing h2 **server** bugs, exposed the first time anything
read a non-pseudo request header:

- `on_header` freed the map key after insert on the wrong belief that the map
  copies it — the dangling key collapsed every real request header behind one
  garbage entry. The map stores pointers as-is; the entries now live for the
  request (leaking in manual mode, the standing convention).
- The C-side header strings lacked the length-prefixed IR string layout, so
  binary-safe string ops read a garbage header at ptr-8 (values truncated to
  one character). New `kml_strn` helper allocates them in the proper layout.
