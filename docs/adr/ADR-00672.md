# ADR-00672: The remaining legacy `url` helpers — `resolve` / `urlToHttpOptions` / `domainToASCII` / `domainToUnicode` (TDD-00165 Stage 4)

- **Relations**: Implements TDD-00165 (Stage 4); Extends [ADR-00671](ADR-00671.md)
- **Date**: 2026-09-03

## Context

Wrapping up the legacy `url`-module functions after `parse`/`format`/
`fileURLToPath`/`pathToFileURL`: the last four helpers `url.resolve(from, to)`,
`url.urlToHttpOptions(url)`, `url.domainToASCII(domain)`, and
`url.domainToUnicode(domain)`.

## Decision

All four register in `moduleFunctionMembers["url"]` (the hybrid-module machinery)
and dispatch via the `url` marker.

- **`url.resolve(from, to)`** — resolves `to` against the base `from` using the
  same libcurl base-relative resolution `new URL(to, from)` performs (seed the
  handle with `from`, then set `to`), and returns the resulting URL string.
  Absolute bases only; a scheme-less/malformed base throws `Invalid URL` — the
  Stage-4a leniency gap it shares with `url.parse`.
- **`url.urlToHttpOptions(url)`** — a pure field remap of a WHATWG `URL` into the
  `http.request` option bag (`HttpOptionsType`): `protocol`/`hostname`/`hash`/
  `search`/`pathname`/`path`(=pathname+search)/`href`/`port`/`auth`(=user[:pass]).
  No external dependency.
- **`url.domainToASCII` / `url.domainToUnicode`** — wrap the bare domain in a
  throwaway `http://<domain>` URL and read the host back with libcurl's
  `CURLU_PUNYCODE` (→ ASCII) or `CURLU_PUNY2IDN` (→ Unicode) flag, returning `""`
  on any failure to match Node's contract.

## Platform note (`domainToASCII`/`domainToUnicode`)

IDN conversion of a **non-ASCII** domain requires the libcurl build to include an
IDN backend (libidn2). Where it is present (typical Linux builds) the functions
convert fully; where it is absent the conversion fails and the function returns
`""` — which is exactly Node's own failure contract, so the behavior stays
correct, only degraded. **Verified on Mac (2026-09-03): this build lacks the IDN
backend** (`CURLUE_LACKS_IDN`), so an ASCII domain passes through
(`domainToASCII("example.com")` → `"example.com"`) but a non-ASCII domain returns
`""`. This is the same platform-dependent-libcurl situation the TLS-backend ADRs
([ADR-00080](ADR-00080.md)/[ADR-00099](ADR-00099.md)/[ADR-00100](ADR-00100.md))
already document; the Linux path is unverified here and should be confirmed on
the x86-64 box.

## Verification

E2E tests in `tests/node_core_modules_test.go`: `url.resolve` (relative,
root-absolute, dot-dot), `urlToHttpOptions` (full field check), and
`domainToASCII` ASCII pass-through + empty-input `""`. The IDN-conversion path is
deliberately **not** asserted in the portable suite (backend-dependent). `go test`
over the import/module/url suites green (Mac); `go vet ./...` clean. With these,
the legacy `url`-module function surface is complete.
