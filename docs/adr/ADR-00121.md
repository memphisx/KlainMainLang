# ADR-00121: User-defined generics V2 — `@erased` opt-in type erasure

- **Relations**: Implements [TDD-00010](../tdd/TDD-00010.md), Extends [ADR-00103](ADR-00103.md)
- **Date**: 2026-08-07

## Context

[TDD-00010](../tdd/TDD-00010.md) scoped user-defined generics as two phases: V1 (monomorphization, unconditional default) shipped in [ADR-00103](ADR-00103.md); V2 (an opt-in, per-declaration JSDoc annotation into type erasure, reusing the existing `any`/`unknown` boxed-value machinery) was deliberately deferred, tracked as not-started in both the TDD and `CLAUDE.md`'s "current blockers" list. This ADR implements V2.

The TDD left three concrete open questions for whoever picked V2 up: the annotation's name/syntax, whether it applies per-declaration or per-call-site, and (implicitly, via Option B's own stated ceiling) how a `T`-typed position outside the machinery's existing support — arithmetic, `T[]`, an object field typed `T` — should fail.

## Investigation

Read the existing V1 implementation (`codegen/llvm/emit_generics.go`, `emitter.go`'s `registerFunctions`) and confirmed there is no "compile the generic body once, generically" path today — V1 only ever emits fully-specialized, concrete-type bodies via `emitFunctionDeclAs(decl, mangledName, sig)`. That function is already fully decoupled from `decl.Name`/`decl`'s own (possibly `T`-named) annotations, which is exactly the shape V2 needs: build one `FuncSig` with `T` positions resolved to `TypeAny` instead of a concrete type, and call `emitFunctionDeclAs` exactly once, under the function's own source name, instead of once per distinct call-site type argument.

Read the JSDoc attachment mechanism (`jsdoc/parser.go`, `parser/parser.go`'s `pendingDoc`/`takeDoc()`) and confirmed the established convention: a call site takes the pending doc immediately after entering the declaration and translates it into a real AST field right there (`parseVarDecl`'s `@type` handling is the direct precedent) — the raw `*jsdoc.Comment` itself never survives onto the AST node. Also confirmed `parseFunctionDecl`/`parseFunctionRest` never called `takeDoc()` at all before this work — no JSDoc annotation of any kind was previously readable on a top-level function declaration.

Read the `any`/`unknown` machinery (`emit_dynamic.go`, [ADR-00008](ADR-00008.md)) and confirmed `emitBoxValue` is infallible (every concrete `Type` has a tag), and that today's function-signature guards (`emit_func.go`, param/return `IsDynamic`/`containsDynamicElement` checks) reject *any* dynamic param/return type unconditionally — that's the exact gate V2 needs to open, narrowly.

Considered routing an erased call through a new, bespoke call-emission function (mirroring V1's `emitGenericFuncCall`) vs. reusing the existing `emitCallToFuncSig` (already shared by both plain and V1-generic calls) with one added branch. Chose the latter: `emitCallToFuncSig` already handles defaults, rest params, and array-vs-scalar argument shapes, none of which V2 needed to reimplement — the only genuinely new behavior is boxing a scalar argument when its target param type is dynamic, which coerce (concrete-to-concrete IR conversion only, no notion of boxing) doesn't do and was never asked to. This also means a mixed signature (`function wrap<T>(label: string, x: T): T`) works with no extra code: only the `T`-typed positions get the new branch, every other parameter goes through the pre-existing path unchanged.

## Decision

**Annotation**: `/** @erased */` directly above a generic function declaration — the TDD's own suggested spelling, adopted as-is.

**Semantics: per-declaration, not per-call-site.** The open question of whether a single generic declaration could have some call sites monomorphized and others erased is resolved as no — `@erased` recompiles the whole declaration's body exactly once; V1 monomorphization and V2 erasure are mutually exclusive per-declaration, matching the TDD's own "Rust `&dyn Trait` is a separate, explicitly-opted-into mechanism" framing (an opt-in escape hatch, not a per-use-site toggle).

**Scope: functions only, and only a *bare* `T` parameter/return position is erased.** `T[]`, or `T` nested inside an object field, are deliberately out of this first slice — narrower than V1 accepts as a concrete type argument, by design: those positions still hit the pre-existing `containsDynamicElement` guard and fail with the existing "any/unknown is not yet supported as a ... type" error rather than silently miscompiling a dynamic array element or object field (neither of which any other part of the dynamic-value machinery currently handles). Generic interfaces and classes are untouched — V2 is scoped to the function case the TDD actually motivates (a pass-through/identity-shaped function), consistent with "ship the common case cleanly, document the narrower gap."

**The arithmetic ceiling is not new work — it already exists and already fires correctly.** `function add<T>(a: T, b: T): T { return a + b; }` marked `@erased` hits the pre-existing "operator '+' on any/unknown is not yet supported" rejection ([ADR-00008](ADR-00008.md)) the moment its body is emitted, with no changes needed anywhere — confirmed directly rather than assumed (see Verification).

**Mechanism**: `registerFunctions` (`emitter.go`) checks `fd.Erased` before deferring a `TypeParams`-bearing declaration to V1's on-demand-instantiation registry; if set, it builds one `FuncSig` via the *same* `buildGenericParamSig`/`substituteGenericType` helpers V1 already has, just substituting `TypeAny` for the type parameter instead of a call-site-inferred concrete type, and registers it directly into `e.funcs[fd.Name]` — not `e.genericFuncs`. Everything downstream that already treats `e.funcs` as the source of truth (call dispatch in `emit_call.go`, `inferExprType`'s `CallExpression` case, `EmitProgram`'s Pass 2 emission loop) therefore handles an erased function exactly like a plain one with an unusual (`TypeAny`-containing) signature, with no new dispatch code needed in any of those three places — only the two narrow additions below were actually required.

## Implementation notes

- **AST**: `FunctionDeclaration.Erased bool` (`ast/nodes.go`), next to the existing `TypeParams`.
- **jsdoc**: `Comment.HasTag(tag string) bool` (`jsdoc/parser.go`) — a generic "does this tag exist" query, `GetType()`'s existing single-tag-value lookup had no equivalent.
- **Parser**: `parseFunctionDecl` (`parser/parser_stmts.go`) now calls `p.takeDoc()` (previously never called for a top-level function at all) and, when the doc has `@erased`, sets `fd.Erased` — or returns a clean parse error if `fd.TypeParams` is empty (`@erased` on a non-generic function), caught at the declaration site rather than deferred to codegen.
- **`emitter.go`**: `registerFunctions`'s existing `if len(fd.TypeParams) > 0` branch gained an `fd.Erased` sub-case (described in Decision) before falling through to the pre-existing `e.genericFuncs[fd.Name] = fd` line. `EmitProgram`'s Pass 2 emission filter changed from `len(fd.TypeParams) == 0` to `len(fd.TypeParams) == 0 || fd.Erased`, so an erased function's already-registered single signature gets its body emitted exactly once, the same pass a plain function's is.
- **`emit_func.go`**: `emitFunctionDeclAs`'s two dynamic-type guards (return type, each parameter) each gained a narrow bypass — `decl.Erased && retType.IsDynamic` / `decl.Erased && pty.IsDynamic` — that allows through *exactly* bare `TypeAny`, not anything `containsDynamicElement` alone would also catch (an array-of-`T`/object-field-of-`T` still rejects even when `decl.Erased`, per the Decision's scope cut).
- **`emit_call.go`**: `emitCallToFuncSig`'s two argument-evaluation branches (a supplied argument, and a default-value fallback) each gained an `if paramTy.IsDynamic` case that calls `e.emitBoxValue` instead of `e.coerce` — the one piece of genuinely new call-site behavior, since `coerce` has no boxing concept and would otherwise emit a call with a type-mismatched argument.

## Side effects discovered

**`emitVarDecl`'s pre-inference type switch (`emit_exprs_vardecl.go`) never accounted for a dynamic return type** on a bare-identifier function call — the same shape of gap [ADR-00103](ADR-00103.md)'s side effect #3 found for a plain-string return, now recurring for `TypeAny`. Confirmed directly: `const y = identity("hi")` for an `@erased identity<T>` failed at the clang stage (`invalid cast opcode for cast from '{ i8, i64 }' to 'i64'`) — the switch's `e.funcs[callee.Name]` branch checked `IsArray`/`IsObject`/`IsFunc`/`IsDate`/`IsMap`/`IsSet`/`isStringTy` but not `IsDynamic`, so `y`'s inferred storage type silently fell through to the switch's `i64` default instead of `TypeAny`, and the later `coerce`-based store tried (and failed) to truncate a boxed struct into a scalar. Fixed by adding `|| sig.RetType.IsDynamic` to that condition — a one-line fix, but a real, silent-until-clang-stage bug, not a hypothetical: this is `@erased`'s single most natural usage pattern (an unannotated `const` holding a call result), exactly mirroring how ADR-00103's analogous bug was found via `identity`'s own most natural V1 usage.

No other bugs found. The scope cuts described in Decision (`T[]`, `T`-typed object fields, generic interfaces/classes, per-call-site mixed erasure) are deliberate, not discovered gaps — tracked here as this feature's own scope, not follow-on TODOs.

## Verification

- `go build -o klainmain .` and `go vet ./...` clean.
- `go test ./...` passes in full, including 7 new tests in `tests/generics_test.go`: pass-through erasure across number/string/boolean, a mixed concrete+erased-parameter signature, an unannotated-`const` result (the exact case the side effect above was found through), `@erased` on a non-generic function rejected, `@erased` with a `T[]` position rejected, and arithmetic on an erased `T` rejected.
- Manually inspected `--emit-llvm` output for a function called with three distinct concrete argument types: confirmed exactly one `define { i8, i64 } @identity(...)` symbol (no `@identity__num`/`@identity__str` V1-style mangling) — asserted directly via `strings.Count` in `TestE2EErasedGenericFunctionSingleCompiledSymbol`, the same "don't just trust output, check the IR" reasoning [ADR-00103](ADR-00103.md) used for its own memoization test.
- `examples/generics/erased_generics.ts` (new) compiled and run directly via the built `klainmain` binary; output matched every inline expected-output comment exactly.
- Verified only on the x86-64 Linux development box (see `CLAUDE.md`'s platform-flagging rule) — like V1, this is pure LLVM-IR-text/Go compiler logic with no OS/libc-specific code path, so it isn't expected to be platform-sensitive, but that expectation hasn't been directly confirmed on the Apple Silicon Mac.
