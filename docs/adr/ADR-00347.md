# ADR-00347: `new Map(entries)` — the `[K, V][]` initial-entries constructor overload

- **Relations**: Implements TDD-00066 (tuple type); extends ADR-00159 (`new Set(iterable)`)
- **Date**: 2026-08-24

## Context

`new Map<K, V>()` was construction-only — the constructor rejected any argument
outright (`new Map() does not accept arguments`). The real spec seeds a map from
any iterable of `[key, value]` pairs, and the `[K, V]` tuple type that overload
needs already exists (TDD-00066). This closes that gap, mirroring the
already-shipped `new Set(iterable)` (ADR-00159).

## Decision

**`new Map(entries)`** accepts an initial-entries argument narrowed to "an array
of 2-tuples" — the only iterable/pair concept a general expression has in this
compiler. K/V resolution (shared helper `mapKVTypes`):

1. An explicit `<K, V>` wins.
2. Otherwise, when entries are given, K/V are inferred from the source's
   `[K, V][]` element type. A **bare array literal** of pairs (`[[k, v], ...]`)
   carries no tuple type of its own without a contextual hint, so its first
   element's two positions are read via `inferExprType` to derive K/V.
3. Otherwise the bare-form string-key / number-value defaults stand.

The map is created, then seeded by walking the entries array: each element is a
2-tuple (a heap struct, IR `ptr`), so field 0 (key) and field 1 (value) are
GEP'd out and passed to the same `__kml_map_str_set`/`__kml_map_num_set` helper
`map.set()` uses. Duplicate keys resolve last-wins (a plain overwrite), matching
JS.

A **bare array literal** source is emitted with a `[K, V]` tuple element hint
(the same hinted-array-literal path an annotated `[K, V][]` var decl uses), since
its inner `[k, v]` arrays have no tuple type without that push. A non-literal
source (an annotated variable) already carries its element type and goes through
`resolveArrayForHOF` unchanged.

## Implementation notes

- `NewMapExpression` gained an `Init Expression` field (nil for the bare form),
  paralleling `NewSetExpression`. `parseNewMapBody` now parses the optional
  argument instead of erroring.
- Codegen lives in `emit_collections.go` (`mapKVTypes`, `resolveMapEntriesArray`,
  `emitMapSeedFromEntries`); `inferExprType`'s `NewMapExpression` case reuses
  `mapKVTypes` so the expression's static type matches what codegen builds.
- `reliableGlobalType` now returns `ok=false` for a `new Map([…])` with inferred
  K/V (exactly as it already did for `new Set([…])`): the entries source must be
  in scope, so the decl must run in source order as a `main()` local rather than
  a pre-declared, out-of-order global.
- Validation: a bare literal whose elements are not 2-element array literals is a
  clean compile error, not a miscompile (a scalar stored as a tuple pointer).

## Side effects discovered

The resolver's per-file rename pass (TDD-00041) had no case for
`NewMapExpression.Init` — it never existed before this ADR — so a reference to an
already-declared `[K, V][]` variable inside `new Map(pairs)` was never rewritten
to `pairs`'s mangled top-level name, failing codegen with `'pairs' is not an
array`. This is the identical bug ADR-00159 hit for `NewSetExpression.Init`;
`rewriteExpr` now descends into `NewMapExpression.Init` too. Regression-covered
by `TestE2ENewMapFromEntriesVariable`.
