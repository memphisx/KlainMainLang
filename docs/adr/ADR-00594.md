# ADR-00594: Deterministic conformance runs (worker headroom)

- **Relations**: Extends [TDD-00008](../tdd/TDD-00008.md), [TDD-00121](../tdd/TDD-00121.md)
- **Date**: 2026-09-01

## Context

The conformance runner (`tools/conformance`) produced **run-to-run-varying**
pass counts — the Node suite flapped across 43/44/45/46 on identical inputs.
Investigation traced this entirely to the harness, not the compiler. Each file
gets a **wall-clock** timeout for both its `clang -O2` compile and its run, and
the runner spawned `runtime.NumCPU()` workers. With every core busy running a
CPU-bound `clang -O2`, a *trivial* test binary (e.g.
`test-process-env-delete.js`, which needs ~10 ms of CPU) gets **starved of CPU**
and its wall-clock budget expires before the scheduler ever runs it — a spurious
`RUN_TIMEOUT`. Which files lose the race varies per run, hence the flapping.
Confirmed two ways:

- At `-workers=1` (zero contention) exactly 22 files time out, stably; the
  flapping files are never among them.
- The Node suite hard-coded `NumCPU()` and ignored `-workers` entirely.

The oracle corpora are fixed and the compiler's output is deterministic (the
same category run at `-workers=1` is byte-identical across baseline and current
code); the nondeterminism was purely the harness's self-inflicted CPU
saturation.

## Decision

Default the worker pool to `NumCPU() - 2` (min 1), and thread the `-workers` flag
into the Node suite (it was hard-coded). Leaving two cores free means the
scheduler always has room to run the short-lived test binaries and the timeout
killer, so they don't starve. **This is the whole fix** — two back-to-back Node
runs at the default are byte-identical.

The per-file timeout stays **5s** (unchanged):

- The flapping is a *starvation* problem, not a too-short-budget problem — the
  headroom fixes it directly, so the timeout doesn't need to grow.
- 5s is the value the entire Test262 baseline was measured at. A much larger
  budget (30s) lets 53k concurrent `clang -O2` runs live long enough to peak the
  machine's memory and spuriously fail otherwise-passing compiles; an
  intermediate value (10s) lands right on a couple of pathological Node tests
  whose own runtime is 10–30s and re-introduces flapping. 5s sits cleanly below
  them (they fail deterministically) and is overridable via `-timeout` for a
  targeted measurement.

## Result

The Node suite is deterministic at the defaults: two back-to-back runs give
byte-identical pass sets (**45 passed**), with **zero regressions** versus the
committed baseline (the +1 is a URL test from concurrent feature work). The same
headroom applies to Test262 through the shared flag; its 5s timeout is unchanged,
so its numbers stay directly comparable to the baseline.

## Verification

`-workers=1` vs `-workers=12` timeout isolation confirmed the 22 genuine timeouts
are stable and the extra ones are contention artifacts; `10 workers / 5s` gave
byte-identical Node pass sets across two runs, while `12 workers / 30s` and
`10 workers / 10s` both flapped. Verified on Mac (Apple Silicon, 12 cores).
