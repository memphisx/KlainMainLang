# ADR-00066: Implement computed property keys `{ [expr]: value }`

- **Relations**: Implements TDD-00012
- **Date**: 2026-07-28

## Context

`STATUS.md` listed computed property keys as the sole entry in its "High priority / low complexity" roadmap section, with a one-line note: "Dynamic key; needs hash map backing." Object literals compile to fixed-shape LLVM structs — `parseObjectLiteral` (`parser/parser.go:1620`) only accepted an `IDENT` key, and every read/write site resolved a field name to a fixed `getelementptr` index known at compile time (`Type.FieldIndex`, `emitMember`, `emitObjectLiteral`, `emitAssign`'s field-assignment branch). A runtime-computed key has no such index to resolve to.

## Investigation

Confirmed the fixed-shape model directly: `ast.ObjectProperty.Key` was a plain Go `string`, and `Type.FieldIndex` only ever matches a compile-time-known name, returning a clean compile error otherwise (`STATUS.md`'s "fixed-shape heap structs, not a dynamic property bag").

Found that `Map<K,V>` (`codegen/llvm/emit_collections.go`, runtime IR in `codegen/llvm/runtime.go:1767+`) already implements exactly the structure a computed-key object needs: a string-keyed, growable, linear-scan array pair (`__kml_map_str_create/find/get/set/has/delete/keys/vals` — not actually a hash map, an O(n) `strcmp` scan, but functionally sufficient and already correct/tested), with values uniformly boxed as `i64` via `valueToMapVal`/`mapValFromI64`. `emitMapCall` already takes raw `ast.Expression` nodes (not pre-evaluated `Value`s) for its key/value arguments, so it can be called directly from new codegen sites without hand-rolling new runtime IR.

Rejected building a bespoke hash table (STATUS.md's original framing) as unnecessary duplication once the Map reuse path was clear — same runtime, same correctness guarantees, zero new IR.

Rejected unifying value types across every property (a `V` that has to fit every property's own value) in favor of reusing the exact "infer from the first element only" convention `inferArrayType` already uses for array literals — consistent with an existing, already-accepted simplification rather than a new one.

Full scope write-up, including what's explicitly deferred (spread + computed key combined, index-signature type-annotation syntax, `JSON.stringify` of a dynamic object), is in TDD-00012 — not repeated here.

## Decision

An object literal with at least one computed key (`{ [expr]: value }`) now compiles to a **dynamic object**: a real `Map<string,V>` heap value (`Type.IsMap: true`), tagged with a new `Type.IsDynamicObject` flag that additionally enables `.field`/`[expr]` dot-and-bracket sugar over the existing `.get()`/`.set()` machinery. Plain `Map<K,V>` variables never set this flag, so their behavior is unchanged.

- `V` is inferred from the first property's value (`inferDynamicObjectType`, `codegen/llvm/emit_exprs.go`), mirroring `inferArrayType`.
- Construction (`emitDynamicObjectLiteral`, `codegen/llvm/emit_objects.go`) creates the map once, then calls `emitMapCall(..., "set", ...)` per property — static keys become synthesized `ast.StringLiteral` nodes, so the exact same call path handles both static and computed keys in a mixed literal (`{ x: 1, [k]: 2 }`).
- Reads (`emitMember`, `emitIndex`) and writes (`emitAssign`, both the `MemberExpression` and `IndexExpression` branches) each gained an `IsDynamicObject` branch ahead of their existing fixed-shape-object logic.
- Writes go through a new `emitDynamicObjectAssign`, not `emitMapCall`'s `"set"` directly — it needs to evaluate the key and RHS expressions exactly once each (for compound-assignment's get-then-set, and to avoid double-evaluating a side-effecting bracket key) and must return the coerced assigned value, whereas `emitMapCall`'s `"set"` case returns the map identity.
- `Object.keys`/`Object.values`/`Object.entries` (`emit_objects.go`) each gained an `IsMap` branch that delegates to `emitMapCall(..., "keys"/"values"/"entries", nil, pos)` instead of walking `Ty.Fields` — this also makes these three work on any string-keyed `Map<string,V>`, not just dynamic objects, as an incidental side effect of sharing one representation.
- A computed key that isn't a string, or a literal combining `...spread` with a computed key, are both clean compile-time errors (`emitDynamicObjectLiteral`, `emitDynamicObjectGet`, `emitDynamicObjectAssign`).

## Implementation notes

Files touched: `ast/nodes.go` (`ObjectProperty.KeyExpr`, `ObjectLiteral.HasComputedKey`), `parser/parser.go` (`parseObjectLiteral`'s new `LBRACKET` branch), `codegen/llvm/types.go` (`Type.IsDynamicObject`), `codegen/llvm/emit_exprs.go` (`inferObjectType`'s dispatch to the new `inferDynamicObjectType`; `emitMember`/`emitIndex`/`emitAssign`'s new branches; the var-decl `ty.IsObject` check widened to `ty.IsObject || ty.IsDynamicObject`), `codegen/llvm/emit_objects.go` (`emitDynamicObjectLiteral`, `emitDynamicObjectGet`, `emitDynamicObjectAssign`, and the `Object.keys`/`values`/`entries` `IsMap` branches).

Two ordering/consistency bugs surfaced and were fixed while wiring this up (see Side effects below) — both are why the final diff touches a couple more call sites than the original plan.

## Side effects discovered

**Bracket-read ordering bug (caught by manual testing, fixed before landing):** `emitIndex`'s existing "string indexing" branch uses `isStringTy`, a ptr-catch-all (`IR == "ptr" && !IsObject && !IsArray && !IsFunc`) that doesn't exclude `IsMap`. Adding the new dynamic-object branch *after* that check meant `obj[k]` on a dynamic object was first misrouted into `emitStringCharAt`, corrupting output. Fixed by placing the new branch *before* the string-indexing check, mirroring the existing `GroupMap` special case's own ordering (which avoids the same trap for the same reason). `isStringTy` itself was left unchanged — it's relied on elsewhere as an intentional "no more specific check already claimed this ptr" catch-all, and every other type it could otherwise misclassify (`Map`, `Set`, `GroupMap`) already has its own dedicated interception earlier in each dispatch chain; this dynamic-object branch just needed to join that same pattern, not change the shared helper.

**`inferExprType`'s hardcoded `Object.keys`/`values`/`entries` return type (caught by a segfault, fixed before landing):** `const vals = Object.values(obj)`'s var-decl type came from a *separate* inference site (`inferExprType`'s `CallExpression` case, keyed on `mem.Property == "values"`) that unconditionally returned `ArrayOf(TypePtr)`, matching the old fixed-shape-only behavior. Once `emitObjectValues` started returning `ArrayOf(valTy)` for a dynamic object (e.g. `ArrayOf(TypeI64)` for numeric values), the var-decl's inferred element type (`ptr`) no longer matched what the value actually was (`i64`) — reading an element then treated a raw number as a pointer, and `console.log` on it dereferenced garbage, segfaulting. Fixed by making this second inference site check the receiver's actual type (`IsMap`/`MapKey`/`MapVal`) the same way `emitObjectKeys`/`Values`/`Entries` do, falling back to the old `TypePtr`-based behavior only for genuine fixed-shape objects. This is a second, independent place object-literal-related type decisions have to stay in sync with actual codegen — worth remembering for any future change to `Object.*` return shapes.

**A real, pre-existing asymmetry, not introduced here but newly visible:** `Object.values`/`Object.entries` on a fixed-shape object still stringify every value (a compiler-specific simplification predating this change), while the new `IsMap` branch returns real typed values — `Object.values({x: 1})` gives `["1"]` (a string) but `Object.values({x: 1, [k]: 2})` gives `[1, 2]` (numbers). Not fixed here (changing the fixed-shape behavior is unrelated, unscoped work); noted in `STATUS.md`'s feature-row comment for future reference.
