# ADR-00208: RegExp `ecmascript` mode — the Option C source-normalization pass (v1) and the default advance

- **Relations**: `Implements TDD-00067` (Stage 4 / Option C). `Extends ADR-00206` (Options A + B / `-regex` selector), `ADR-00207` (Stage 3 / `es-utf16`).
- **Date**: 2026-08-17

## Context

TDD-00067's final stage, Option C, is a JS-regex→PCRE2 source normalization pass for the dialect gaps that PCRE2 compile *options* cannot close. The TDD lists several: Annex-B legacy octal/decimal escapes, the `u`/`v` code-point dialects (`\u{…}`/`\p{…}`/set operations), the ES Unicode class semantics for `\w`/`\s`/`\b`, and the exact `.` line-terminator set. A complete ES-regex front end is a large, open-ended piece of work; this ADR ships a real, bounded **v1** of it behind `-regex=ecmascript` and advances the default to that mode, with the remaining sub-items honestly deferred and disclosed.

The one transform v1 performs is the **exact `.` rewrite**. es-unicode approximates ES's `.` (any character except `\n \r \u2028 \u2029`) with `PCRE2_NEWLINE_ANY`, which additionally excludes `\x0b` (VT), `\x0c` (FF), and `\x85` (NEL) — a documented Strict-Coverage-excluding caveat. Confirmed against Node: `"a\x0bb".replace(/./g,"X")` is `XXX` in ECMAScript but `X\x0bX` under es-unicode. The rewrite makes `.` exact and retires that caveat for the default mode.

## Investigation

- **A pattern can be a runtime value** (`new RegExp(someVar)`), not only a `/…/` literal, so a compile-time Go rewrite would miss the dynamic case. The normalization must run at runtime, before `pcre2_compile`, as a `__kml_regex_*` helper — the same place the flag parse already runs.
- The single compile site is `emitNewRegExpExpression` (`emit_regexp.go`); it already stores the original pattern into `.source` separately from what it hands to `pcre2_compile_8`, so normalizing only the compiled form (keeping `.source` verbatim) is a one-line split of the pattern register.
- The `.` divergence was isolated by running `"a\x0bb"`/`"a\x0cb"` under es-unicode vs Node (see Context). `\n`/`\r` already agree (both exclude), so only the three extra control chars differ — exactly what an explicit `[^\n\r\u2028\u2029]` class fixes without a newline-convention change.
- **`$`/`m` exactness was ruled out of v1**: ES `$`/`m` anchor at exactly the four terminators, but no PCRE2 newline convention is exactly that set, and `.`-style rewriting of `$` would need a lookahead that perturbs match structure. `NEWLINE_ANY` is kept for `$`/`m` (still over-including the three control chars there) — a narrower residual caveat than before.
- **Index space**: TDD-00067 line 64 defines `ecmascript` as "Option C over A + B + the index-space stage," i.e. folding in `es-utf16`'s UTF-16 indices. That conflicts with the TDD's own later resolution (Open questions, 2026-08-17) that a UTF-16 index space must not be the default because it desyncs from the byte-indexed string layer (`.charCodeAt`/`.slice`, ADR-00028). Since `ecmascript` is intended to become the default, this ADR resolves the conflict in favor of the more fundamental constraint: **`ecmascript` is byte-indexed** (dialect normalization only), and `es-utf16` remains the separate opt-in for spec-exact UTF-16 offsets. The two concerns — dialect faithfulness and index space — are made orthogonal rather than bundled.

## Decision

- **`__kml_regex_es_normalize(pattern, dotAll)`** (`runtime_regexp.go`): a runtime scan that copies the pattern byte-for-byte, tracking escape state (a `\` copies itself and the next byte verbatim) and character-class depth (an unescaped `[`/`]` toggles it). An unescaped top-level `.` with `dotAll` absent is replaced by the 19-byte class `[^\n\r\u2028\u2029]` (memcpy from a private constant; the `\u….` escapes are interpreted because `ecmascript` also sets `PCRE2_ALT_BSUX`). Every other byte — escaped chars, class contents, `.` under dotAll — is copied unchanged, so a pattern with no rewritable `.` comes out byte-identical. Output bound `len*19+1` cannot overflow.
- **`ecmascript` mode** (`regexModeOpts`): es-unicode's option set (`ALT_BSUX | MATCH_UNSET_BACKREF | UTF`, conditional `DOLLAR_ENDONLY`, `NEWLINE_ANY`, `utfMatching`) plus `normalize: true`, and **not** `utf16Index` — byte-indexed. `emitNewRegExpExpression` calls the normalizer on the compiled pattern only (the `.source` store keeps the original).
- **Default advance**: `resolveRegexMode` now resolves unset → `ecmascript` (was `es-unicode`). `main.go` accepts `ecmascript`; no mode is rejected anymore. es-utf16 is deliberately *not* the default (its UTF-16 index space diverges from the string layer).

## Implementation notes

- New `used`-flag `usedRegexESNormalize`; `ensureRegexESNormalize` pulls in `strlen`/`malloc`/`memcpy` and emits the private `@.kml_regex_dot_repl` constant plus the function once.
- The normalizer takes the dotAll `i1` from the same `dotAllSlot` the flag parse already fills, loaded just before the compile call.
- Files touched: `main.go`, `codegen/llvm/emitter.go`, `codegen/llvm/runtime_regexp.go`, `codegen/llvm/emit_regexp.go`, `tools/conformance/main.go` (default-description text), `tests/regexp_test.go`, `examples/regexp/regexp_ecmascript.ts`, `docs/status/REGEXP.md`, `docs/tdd/TDD-00067.md`.

## Side effects discovered

- **Default behavior changed** for `.`: a `.` in a default-mode RegExp now matches `\x0b`/`\x0c`/`\x85`, where before (es-unicode default) it excluded them. This is strictly more ES-correct; the full `go test ./...` suite passed unchanged, and the `.`-vs-`\r`/`\n` behavior (the cases any existing test exercises) is identical, so no ASCII program regressed.
- **Remaining Option C is deferred and disclosed** (docs/status/REGEXP.md), each an honest caveat, not a silent gap: `\u{…}`/`\p{…}` code-point escapes and the `u`/`v` flags; ES Unicode `\w`/`\s`/`\b` (the `PCRE2_UCP` + U+180E-correction work); Annex-B legacy octal/decimal escapes (still `RUNTIME_NONZERO_EXIT` on the `annexB/**/RegExp-*-escape-*` files, the TDD's version-delta open question); and exact `$`/`m` anchoring (still `NEWLINE_ANY`).
- `es-utf16` did not gain the normalization pass — it stays "es-unicode matching + UTF-16 indices." Combining both (normalization *and* UTF-16 indices) is a future mode if a real program needs it; nothing does yet.

## Verification

Machine: Apple Silicon M4, pcre2 10.47, `clang -O2`.

- New E2E `TestE2ERegExpEcmascriptMode` (11 sub-cases, cross-checked against Node): VT/FF now match `.`, `\n` still excluded, dotAll still matches everything, escaped/class dots stay literal, `.source` unchanged, and the A+B fixes still hold under the mode. The default-mode matrix case was renamed `default-resolves-ecmascript`.
- Full suite green: `go build`, `go vet ./...`, `go test ./...` — the default advance routes every RegExp in the whole E2E corpus through the normalizer, so a green suite is the identity-preservation proof.
- Example `examples/regexp/regexp_ecmascript.ts` runs under the default mode with output matching Node line-for-line.
- Conformance (Mac, Apple Silicon, pcre2 10.47): `built-ins/RegExp` subset holds at **37/1879** in the default (ecmascript) mode, and the **full corpus at 5220/53578** — identical to ADR-00206's Mac es-unicode baseline (5220), i.e. no regression. The `.` line-terminator Test262 files are eval-based/out-of-scope so they do not flip here, and the exactness is verified directly against Node instead. The canonical Linux `CONFORMANCE-RESULTS.md` (5225, a different platform per ADR-00206's Mac/Linux delta) was left untouched, to be regenerated on the next Linux session.
