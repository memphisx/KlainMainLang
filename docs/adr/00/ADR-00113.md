# ADR-00113: structuredClone(obj)

- **Date**: 2026-08-07

## Context

`docs/status/GLOBAL-FUNCTIONS.md` tracked `structuredClone(obj)` as unimplemented ("Deep copy; medium complexity"), and `docs/status/README.md`'s Roadmap listed it under "Low effort (C stdlib or a simple wrapper)" — "recursive deep-copy of heap objects." Picked up as the second of two low-effort backlog items requested directly, alongside `TextEncoder`/`TextDecoder` (ADR-00112).

## Investigation

Real `structuredClone` implements the HTML spec's structured-clone algorithm: a runtime graph walk that has to discover an arbitrary value's shape (and cycles) as it goes, because JS values are dynamically shaped. This compiler's values are never dynamically shaped that way — every expression's type is already known at compile time (`inferExprType`), including full field lists for object types (`Type.Fields`/`VisibleFields()`/`FieldIndex()`, `types.go`) and element types for arrays (`Type.ElemType`, recursively, since a nested array's element type is itself a `Type` with `IsArray` possibly set — TDD-00029). That makes the entire clone unrollable into straight-line codegen at the call site, generated once per distinct static type shape, rather than needing any runtime type-tag dispatch or cycle detection at all (a compile-time-infinite type, e.g. a struct containing itself by value, cannot exist in this compiler's fixed-size heap-struct representation, so cycles are structurally impossible, not just unhandled).

Looked for existing array/object element-copy machinery to reuse rather than hand-rolling new GEP/load/store sequences:
- `emit_arrays_core.go`'s `loadArrayElem`/`storeArrayElem` already transparently unbox/rebox a nested-array element (TDD-00029's boxed `{ptr,i64}`-behind-a-`ptr`-slot representation) — using these instead of raw loads/stores means `emitDeepCloneArray` gets nested-array support for free, with no boxing-awareness of its own, by simply recursing with `elemTy` as the next call's type.
- `emit_objects.go`'s `emitObjectLiteralWithHint`'s object-spread (`{...obj}`) branch already does a field-by-field `getelementptr`/`load`/`storeField` copy loop using `ty.VisibleFields()`/`FieldIndex()`/`StructIR()`/`StructFieldIR()` — `emitDeepCloneObject` mirrors this shape, adding a recursive `emitDeepClone` call per field instead of a flat load-then-store.

Considered scoping down to "arrays/objects of scalars only" (no recursion) to keep this genuinely low-effort, but since the array/object machinery above already composes recursively for free (a recursive `emitDeepClone` call is barely more code than a flat copy), decided the fuller recursive version was not meaningfully more expensive to build and is substantially more useful — verified directly with nested object fields (`Shape.points: Point[]`) and array-of-arrays (`number[][]`) test cases, both working correctly with no extra code beyond the recursion itself.

Had to decide what to do with reference/identity-bearing types (`Map`, `Set`, `EventEmitter`, `URL`, `ArrayBuffer`, functions, class instances, `Error`, `Promise`, `any`/`unknown`). Silently falling through to a shallow pass-through (returning the same pointer) would be a real correctness bug disguised as success — a "clone" that still aliases the original's mutable backing storage, exactly the kind of bug the project's own standing rule says must not be papered over. Rejected all of these at compile time instead, each with its own named error message, checked in `structuredCloneUnsupportedKind`. `URL`/`URLSearchParams` needed checking ahead of the generic `IsObject`/`IsMap` cases specifically because `URLType()` sets `IsObject` and `URLSearchParamsType()` sets `IsMap` internally (storage reuse, not really being a plain object/Map) — checked directly against `types.go`'s doc comments for both flags to confirm this before writing the rejection order.

## Decision

`structuredClone(obj)` is a single global function (`emit_call.go`'s existing bare-identifier `switch id.Name` dispatch, alongside `btoa`/`fetch`/etc.), implemented in a new `emit_structured_clone.go`:

- `emitDeepClone(val, ty, pos)` is the recursive core: rejects the reference-like kinds listed above via `structuredCloneUnsupportedKind`, dispatches arrays to `emitDeepCloneArray` and plain objects (`ty.IsObject`) to `emitDeepCloneObject`, and passes every scalar (number/boolean/string/Date/null/undefined) straight through unchanged — a scalar is already a value type, so "cloning" it needs no allocation.
- `emitDeepCloneArray` allocates a fresh backing buffer sized `len * elemTy.Align()`, loops `0..len`, and for each element: `loadArrayElem` (transparently unboxing a nested-array element), recurse via `emitDeepClone` with `elemTy`, then `storeArrayElem` (transparently reboxing).
- `emitDeepCloneObject` allocates a fresh struct sized `ty.StructSize()`, and for each of `ty.VisibleFields()`: load the field, recurse via `emitDeepClone` with the field's declared type, store into the new struct at the same GEP index.
- TypedArrays fall out for free: `TypedArrayType(...)` is `ArrayOf(elemTy)` with `IsTypedArray` set on top of `IsArray`, so `emitDeepCloneArray`'s `ty.IsArray` dispatch already covers them with no special-casing — a `Uint8Array` clone is just an array-of-`i8` clone.
- Also wired `structuredClone` into `inferExprType`'s `CallExpression` switch (`return e.inferExprType(ex.Args[0])` — a clone's static type is always identical to its argument's) and into `emitVarDecl`'s separate unannotated-initializer inference switch, both needed for the same reason ADR-00112 needed them for `.encode()`/`.decode()`: an unannotated `const clone = structuredClone(x)` needs its true (array/object) type known before `clone[0]`/`clone.field` can type-check, and neither inference path falls through to the other automatically for an `Identifier`-callee call.

## Implementation notes

Files touched: `codegen/llvm/emit_structured_clone.go` (new — `emitStructuredClone`, `structuredCloneUnsupportedKind`, `emitDeepClone`, `emitDeepCloneArray`, `emitDeepCloneObject`), `codegen/llvm/emit_call.go` (dispatch case), `codegen/llvm/emit_exprs_types.go` and `emit_exprs_vardecl.go` (type-inference wiring, same two spots ADR-00112 touched for the same underlying reason).

No new AST node was needed — `structuredClone(x)` parses as an ordinary `CallExpression` with an `Identifier` callee, same as `btoa`/`isNaN`/etc.; no parser changes at all were required.

## Side effects discovered

None found while implementing this one — unlike several other features in this project's history, no pre-existing unrelated bug surfaced along the way. The `inferExprType`/`emitVarDecl` gap this exercised is the same category ADR-00112 already found and fixed (not a new instance of it — both fixes landed together in this session).

## Verification

- `go build -o klainmain .` and `go vet ./...` clean.
- `go test ./...` — full existing suite passes unchanged.
- New tests: `tests/structured_clone_test.go` — scalar pass-through, independent-copy verification for both arrays and objects (mutate the clone, confirm the original is untouched), recursion through nested object fields *and* nested arrays inside an object field simultaneously, array-of-arrays independence, and compile-time-rejection cases for `Map` and for a user-defined class instance.
- New example: `examples/structured_clone/structured_clone.ts`, verified via `make examples` (79/79 passed, including this one).
- Manually verified via a scratch `.ts` file (mutating a clone's nested array element and nested object field, confirming the source `Shape`/`number[][]` values were unaffected) before the formal test suite was written.
- Verified on: x86-64 Linux only (this session's machine). All codegen here is pure `malloc`/`getelementptr`/`load`/`store` sequences with no OS/libc-specific behavior, so no platform divergence is expected, but per the project's own platform-parity standing rule this hasn't been directly re-run on the Mac yet.
