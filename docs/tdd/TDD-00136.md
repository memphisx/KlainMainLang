# TDD-00136: `process.version` / `process.versions` reporting for a non-Node binary

- **Status**: Decided & Implemented (V1) — [ADR-00396](../adr/ADR-00396.md). `node`/`v8` = pinned baseline (v22.11.0) as the ceiling, `klain` = compiler version, no fabricated keys; real `openssl`/`zlib` and a `--node-compat` floor deferred.
- **Date**: 2026-08-27

## Context

`process.versions` (23 uses across the corpus `test-process-*.js`) and
`process.version` are commonly probed by real Node code — almost always to
**feature-gate**: `if (Number(process.versions.node.split('.')[0]) >= 18) …`.
They are currently `❌` ([PROCESS-CLI.md](../status/PROCESS-CLI.md)). Unlike
`execPath`/`emitWarning` (mechanical, [ADR-00395](../adr/ADR-00395.md)), what a
*compiled native binary with no JS runtime* should report here is a genuine
design decision, so it gets a TDD rather than a guessed value.

## The tension

- **Report nothing / `undefined`** — breaks every script that probes
  `process.versions.node` (a `.split` on undefined throws), and many libraries do
  this at import time.
- **Report a recent Node version** (e.g. `"22.0.0"`) — satisfies the probes, but
  is a **lie that misleads feature-gating**: a script that sees Node 22 will
  reach for APIs this compiler doesn't implement, turning a clean "missing
  feature" error into a confusing runtime failure deep in library code.
- **Report a conservative floor** (the lowest Node version whose *implemented*
  surface this compiler faithfully covers) — honest for gating (scripts opt into
  only what's supported), but picking/maintaining that number is real work and it
  understates newer features that *are* supported.

## Options to decide

1. **Floor-version `versions.node`** + a distinct `versions.klain` (this
   compiler's own version) so code that specifically wants to detect this
   compiler can, while generic Node code gets a safe gating number. `version` =
   `"v" + versions.node`. The floor is a hand-maintained constant.
2. **Compiler-version-as-truth**: `version` = this compiler's own version;
   `versions` = `{ klain: <ver> }` with **no** `node` key (or `node` = the
   compiler version). Maximally honest about "not Node", but breaks `versions.node`
   probes outright.
3. **`compat` mode-gated**: under `-compat=js` report a Node floor version (best
   effort to run real scripts); under `-compat=strict` (default) report the
   compiler's own identity. Ties the choice to the existing compatibility knob
   ([the `compat` flag](../../README.md)) rather than inventing a new one.
4. **Configurable**: a `--node-compat-version` flag (default = a floor), so the
   author declares what to claim. Most flexible, most surface.

## Recommendation (to be ratified)

Option 1 or 3. Both keep `versions.node` a *safe* number (honest gating) while
still exposing the compiler's real identity — the difference is whether the
choice is static (1) or follows `-compat` (3). Option 2 is cleanest philosophically
but breaks the dominant real-world use (probing `versions.node`), and option 4
adds a flag for what is almost always the same answer.

## Open questions

- Which sub-keys does `versions` carry (`node` only, or also `v8`/`uv`/`openssl`
  with plausible-but-fake values)? Fake dependency versions have the same
  mislead-the-probe risk as a fake `node`.
- What is the floor `node` version, and how is it kept honest as the implemented
  surface grows — tie it to the conformance oracle, or hand-bump per release?
- Is there a real consumer in this project's target (CLI tools / Docker
  microservices) that needs `versions` at all, or is this purely
  run-someone-else's-script compatibility?
