# TDD-00145: Status tracking as JSON source-of-truth, with Markdown generated from it

- **Status**: Partially Implemented — Phases 1–5 shipped ([ADR-00444](../adr/ADR-00444.md), [ADR-00445](../adr/ADR-00445.md)): `cmd/statusgen` with an ordered-segment page model (a design divergence from the sketch below, recorded in the ADR); the full corpus proved byte-identical, then flipped — `docs/status/data/*.json` is canonical, the pages are generated (`make status`), and CI guards the sync (`make status-check`). Phase 5 kept the importer as on-demand `export`/`roundtrip` tooling with no routine role, per the "if cheap" clause. Remaining: the website reference projection deriving badges/differences from the status source (the Reconciliation section), pending an editorial review of the reference `differences[]` content
- **Date**: 2026-08-28

## Context

`docs/status/` is the source of truth for implementation coverage: ~30 per-area
detail pages plus the aggregate [README.md](../status/README.md), all hand-edited
Markdown. That format has three recurring failure modes:

1. **Hand-maintained numbers drift.** Every page carries a `**Coverage**` /
   `**Strict Coverage**` line, and the README repeats per-category and
   per-section totals (`336 / 351 features, ~96%`). These are all derivable from
   the row tables, but today they are typed by hand and go stale — the standing
   rules already have to say "update the README counts same-commit," precisely
   because nothing enforces it.
2. **The table format is load-bearing but unvalidated.** Coverage is defined as
   "✅ rows / total rows" and Strict as "✅ rows with an empty Caveats cell /
   total"; a mistyped `•`, a stray `<br>`, an escaped-vs-unescaped `|` in a
   `string \| null` cell, or a 3-column page where a 4-column one was assumed all
   silently change the derived numbers. The reference website's anti-drift guard
   (`website/scripts/check-reference.mjs`) had to grow special cases for every one
   of these Markdown quirks — header-name Caveats-column detection, per-table
   header re-detection on multi-table pages, bracket-preserving row keys — just to
   read the tables reliably.
3. **The same caveats are authored twice.** The reference website already models
   each API row as structured JSON (`website/src/data/reference/*.json`), whose
   `differences[]` field is the status page's Caveats column re-typed by hand with
   ADR/TDD links stripped. Two hand-maintained copies of the same prose drift
   against each other; the guard exists only to catch that drift after the fact.

The reference-docs initiative demonstrated the inverse works well: a structured
JSON model with a generator and a build-time guard is materially easier to keep
correct than free Markdown, and percentages become a computed field rather than a
manual one. This TDD scopes flipping the status system the same way — **JSON
becomes the source of truth; the Markdown pages and the public reference JSON are
generated projections of it** — without losing a single piece of information the
current Markdown carries, and with a first-implementation gate that proves the
round-trip is lossless in both directions before the source of truth is switched.

## Design

### Guiding principles

- **One source, many projections.** A per-area JSON source drives (a) the
  `docs/status/*.md` detail page, (b) its contribution to the README aggregate,
  and (c) the public `website/src/data/reference/*.json` badges/caveats. Nothing
  tabular or numeric is authored more than once.
- **Structure the tabular and numeric; store prose verbatim.** Rows, statuses,
  and per-row caveat/note bullets are modeled as data (so numbers derive and the
  reference projection can consume them). Free-form prose — page intros, "Known
  limitations", the README's roadmap and gap sections — is stored as **opaque
  verbatim Markdown blocks**. Over-structuring prose is where a round-trip loses
  bytes; keeping it verbatim guarantees fidelity while still structuring
  everything the numbers and the reference depend on.
- **Derivation is the whole point.** Every coverage/strict fraction, every
  percentage, and every README section total is computed by the generator from
  the rows. They never appear in the source JSON.
- **Lossless is provable, not asserted.** The first implementation must
  demonstrate a byte-identical round-trip (Markdown → JSON → Markdown) across
  every current page before the source of truth is switched. That diff is the
  acceptance gate (see [Bidirectional verification](#bidirectional-verification-the-first-implementation-gate)).

The distinction that matters: the README's per-category **summary caveats** are a
hand-curated shortlist, *not* the same text as the page's per-row caveats — so they
are authored on the index source, not derived from the pages. The coverage/strict
*numbers* on both the pages and the README are always derived.

### Schema sketch

Shape only; the field names below are illustrative. Two documents: a per-area
detail source, and one index source.

```ts
// docs/status/data/<AREA>.json — one per detail page
interface StatusArea {
  id: string            // slug, e.g. "string-methods"
  file: string          // "STRING-METHODS.md"
  title: string
  intro: {
    blockquote: string[]        // verbatim > lines
    blocks: string[]            // ordered verbatim Markdown blocks (paragraphs, code lines)
  }
  coverageStyle: 'standard' | 'multiCategory' | 'custom'
  coverageTemplate?: string     // only for 'custom' (DESKTOP-WEBVIEW), with {loose}/{strict} slots
  tables: Table[]
  sharedCaveats?: SharedCaveat[]
  knownLimitations?: string     // verbatim Markdown section body
  lastUpdated?: string          // "YYYY-MM-DD", only if the page has a footer
}

interface Table {
  heading: string | null        // "## …" name, null on a single-table page
  featureColumn: 'Feature' | 'Tag' | 'API'
  hasCaveats: boolean
  hasNotes: boolean
  countsTowardParity: boolean    // false for JSDOC's extensions table
  rows: Row[]
}

interface Row {
  feature: string                // verbatim cell text, backticks included
  status: 'implemented' | 'missing'   // ✅ / ❌
  caveats?: string[]             // bullet fragments (Markdown, incl. `code` and links)
  notes?: string[]
  extension?: boolean            // this project's own extension (JSDOC width keywords, @erased)
}

interface SharedCaveat {
  appliesToHeading?: string      // e.g. every row under "## …", or a predicate note
  intro: string                  // "Shared crypto.subtle caveats (apply to every ✅ subtle row):"
  bullets: string[]
}

// docs/status/data/_index.json — the README source
interface StatusIndex {
  project: { blockquote: string[]; intro: string }
  sections: Section[]
  notImplemented: string         // verbatim Markdown (Medium/High tables + prose)
  fidelityGaps: string           // verbatim Markdown table + intro
  tddBacklogNotes: Record<string, string>  // TDD number -> authored Notes override
  roadmap: string                // verbatim Markdown
  statusPageFormat: string       // verbatim Markdown
  lastUpdated: string
}

interface Section {
  heading: string
  blurb: string                  // verbatim Markdown paragraph(s)
  totalStyle: 'features' | 'none'
  rows: CategoryRow[]
}

interface CategoryRow {
  category: string
  areaId: string                 // links to a StatusArea (+ which table if the page is multi-category)
  tableHeading?: string          // disambiguates when the page hosts several categories
  summaryCaveats: string[]       // authored curated shortlist
  statusTextOverride?: string    // non-fraction status ("2/3 modes", "✅ 2 modes")
  strictOverride?: string        // "—"
}
```

### Derived computations the generator owns

- **Per-table coverage/strict**: `coverage = implemented / total`;
  `strict = (implemented ∧ empty caveats) / total`, over parity-counting tables
  only. Extension rows / `countsTowardParity:false` tables are excluded from the
  parity figure exactly as the current pages do.
- **Percentage formatting** must match today's convention exactly, or the
  round-trip fails: an exact integer percent renders bare (`100%`, `50%`, `0%`);
  a non-exact one renders with a leading tilde (`~93%`, `~85%`). Rule to
  replicate: `p = round(100·n/d)`; emit `~p%` when `100·n/d ≠ p`, else `p%`.
- **Coverage line rendering** per `coverageStyle`: `standard` (single fraction
  each), `multiCategory` (`Cat A x/y (…) · Cat B …`, plus the trailing "A row
  counts toward Strict only when its **Caveats** column is empty." sentence that
  the multi-category pages carry), `custom` (interpolate the derived numbers into
  `coverageTemplate` for DESKTOP-WEBVIEW's bespoke wording).
- **README section totals** (`sum implemented / sum total, ~pct`) summed across
  the section's member tables, same percentage rule.
- **README Contents TOC** and per-section category tables (Coverage/Strict cells)
  from the areas.
- **TDD backlog table**: read `docs/tdd/README.md`'s index, filter to
  Not Started / In Progress / Partially Implemented, join each row's authored Note
  override from `tddBacklogNotes`.
- **Public reference projection** (see below): `badge` and `differences[]` from
  each row's status + caveats.

### Reconciliation with the website reference

The public `website/src/data/reference/*.json` files carry two kinds of content:
values that duplicate the status page (`badge`, `differences[]`, the coverage
figures) and genuinely public-facing prose the status pages do not have
(`signature`, `description`, `params`/`returns`, `snippet`/`exampleKey`,
`seeAlso`, `spec` links). Recommended split:

- The **duplicated** values stop being authored on the reference side. The website
  generator derives each entry's `badge` and `differences[]` from the status
  source (differences = the row's caveats with ADR/TDD/doc references stripped —
  the same strip already done by hand), and the coverage figures from the derived
  numbers.
- The **public prose** stays hand-authored, but in a slimmed reference source that
  holds only those fields plus the `statusRow` back-reference. The website build
  merges status-derived (badge/differences/coverage) + authored-prose → the
  rendered page.
- The existing anti-drift guard then compares JSON ↔ JSON (does every ✅ status
  row have a public-prose entry?) instead of parsing Markdown, and all its
  Markdown-quirk special-casing retires.

This kills the caveat duplication (item 3 in Context) outright, and is the reason
to do the reference and status work under one schema rather than two. A heavier
alternative — folding the public prose *into* the status source as an optional
`reference` sub-object per row, so a single file generates everything — is
possible but couples compiler-side tracking to public-doc copy and bloats the
source; keep the two layers separate but both JSON and cross-checked.

### Bidirectional verification (the first-implementation gate)

The switch is only safe if the round-trip is provably lossless. First
implementation, in order:

1. **Importer** (Markdown → JSON): parse every current `docs/status/*.md` +
   `README.md` into the schema above. This is throwaway-grade but must be exact.
2. **Generator** (JSON → Markdown): render the schema back to Markdown.
3. **Round-trip diff**: `generator(importer(committed.md))` vs `committed.md`,
   byte-for-byte, for every page and the README. Iterate schema + generator until
   the diff is empty across the whole corpus. **An empty diff is the acceptance
   criterion** — it proves information survives both directions (parse then emit
   reproduces the source exactly), which is the "lose nothing" guarantee the whole
   change hinges on.
4. **Flip the source of truth**: commit the generated JSON as canonical; the
   `.md` files become build outputs. A `make status` target (and a CI guard)
   regenerates them and fails if the working tree differs — the ongoing forward
   gate, analogous to the reference anti-drift check.
5. The importer is retained at least through the flip as a re-derivation / fuzz
   tool (regenerate JSON from MD, diff against canonical JSON), then may be
   retired once the forward gate has proven stable; the reverse direction
   (JSON → MD) is the only one exercised routinely afterward.

Doing step 3 on a **single representative page first** (STRING-METHODS: one table,
Known Limitations, standard coverage) de-risks the schema before the multi-table
(LANGUAGE-CONSTRUCTS/TYPE-SYSTEM/JSDOC), 3-column (DESKTOP-WEBVIEW/NOTIFICATIONS),
and README shapes are attempted.

### Determinism pitfalls (each will surface as a round-trip diff)

- **Percentage tilde rule** and integer rounding — must match the current pages
  exactly (see above).
- **Bullet reconstruction** — `•`-prefixed fragments joined with `<br>`; cells
  with a single unbulleted line vs. a one-bullet list; trailing punctuation.
- **Inline code and links verbatim** inside caveat/note fragments, including
  escaped `\|` inside `Map<string,string>` / `string \| null` cells.
- **Multi-category coverage line** punctuation (`·` separators, the `(~x%)`
  parenthetical, the trailing Strict-definition sentence).
- **Bespoke coverage wording** (DESKTOP-WEBVIEW's "20/20 surface, 100%. Strict:
  0/20").
- **Column-set and header-name** variation (`Feature`/`Tag`/`API`; 3- vs 4-col).
- **Parity-excluded** extension tables/rows kept out of the figure.
- **`Format:` line** presence/exact text; blank-line spacing between sections;
  the `---` horizontal rules in the README; the `*Last updated:*` footers
  (preserve the stored date; do not auto-bump — matching the existing rule that a
  footer changes only when that file's content does).

### Tooling and placement

Recommended: a Go tool in the compiler repo (e.g. `cmd/statusgen`, run by a
`make status` target and in CI), because `docs/status/` is compiler-side, the
existing workflow is `make`-driven, and a Go tool can emit **both** the `.md`
pages and the website reference projection in one pass — keeping the
status→reference derivation in a single place. Source JSON lives in
`docs/status/data/`. The website build then consumes the generated reference JSON
as it does today. An all-Node alternative (mirroring `gen-examples.mjs` /
`check-reference.mjs`) is viable but would re-implement the derivation on the
website side and reintroduce a cross-language seam.

### Phasing

1. **Schema + single-page round-trip** — model, importer, generator; byte-clean
   on STRING-METHODS.
2. **All detail pages** — extend to multi-table, 3-column, Tag/API, shared
   caveats, extensions; byte-clean across every `docs/status/*.md`.
3. **README aggregation** — sections, derived totals, authored gap/roadmap/format
   blocks, TDD-backlog derivation; byte-clean on `README.md`.
4. **Flip + guards** — JSON canonical, `make status` + CI forward gate; website
   reference projection consumes the status source; retire the reference guard's
   Markdown parsing.
5. **Retire the importer** once the forward gate is proven; keep as an on-demand
   re-derivation tool if cheap.

## Open questions

- **Where the public-facing reference prose lives** — a slimmed separate authored
  file cross-checked against the status source (recommended), or folded into the
  status source per row (single file, but couples the tracker to public copy).
- **Contents TOC and section ordering** — derive the TOC and section order from
  the data, or keep an explicit authored order in `_index.json`? Deriving is less
  to maintain; an explicit order is safer against reordering surprises during the
  round-trip.
- **TDD backlog table** — fully derive from `docs/tdd/README.md` (filter to
  not-done) with authored per-row note overrides, or keep authored? Deriving keeps
  it in sync with the TDD index automatically but adds a second cross-source
  dependency to the generator.
- **Go vs. Node for the generator** — Go (one pass emits MD + reference JSON,
  lives with the compiler and CI) vs. Node (matches the existing website scripts
  but re-implements derivation across a language seam).
- **Whether the importer is permanent** — retire after the flip, or keep as a
  standing MD→JSON re-derivation/fuzz check that continuously re-proves the
  round-trip both ways.
- **Migration granularity** — one big flip after the whole corpus is byte-clean,
  or page-by-page with a mixed authored/generated interim state (harder to guard,
  but smaller blast radius).
