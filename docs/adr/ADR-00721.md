# ADR-00721: TCP_NODELAY on accepted `http.listen` sockets

- **Relations**: Extends [ADR-00720](ADR-00720.md) (Linux TUI build break; recorded this as a deferred side effect)
- **Date**: 2026-09-06

## Context

`TestE2EHTTPListenManyRequestsDoesNotLeakStack` sends 30000 sequential
keep-alive requests to a compiled `http.listen` server. On a native Linux
box or the Mac it finishes in seconds. Under WSL2, and under Docker Desktop
on Windows (both a Linux VM whose loopback honours delayed ACK), every
request took about 40 ms, so the test alone ran for 20 minutes and pushed
the `tests` package toward its 40 minute CI timeout. ADR-00720 identified
the cause and deferred the fix; this ADR lands it.

## Investigation

The server writes a response as two `write()` calls (status line + headers,
then body). With Nagle's algorithm on, the second small write is held back
until the first is acknowledged, and the client's delayed-ACK timer holds
that acknowledgement for ~40 ms. Measured inside the Docker container while
the pre-fix test ran: ~120 TCP segments per second, i.e. 20–25 requests per
second, matching the timer.

Node's `http.Server` has `noDelay: true` by default (`http.createServer`
options; `server.noDelay`), so it calls `setNoDelay(true)` on every accepted
socket. `net.createServer` does **not** (its `noDelay` defaults to `false`),
so the `net` accept path in `codegen/llvm/runtime_net.go` is deliberately
left alone; `socket.setNoDelay()` there is already a real `setsockopt`
(`codegen/llvm/emit_net.go`, `emitNetSocketSockOpt`).

Alternatives considered:

- Coalescing header and body into one `write()`: would also hide the stall
  for small responses, but is a buffering change to the response path, and
  Node's observable behaviour is the socket option, not a single write.
- Setting the option on the listening socket and relying on inheritance:
  Linux inherits `TCP_NODELAY` across `accept()`, but that is not portable
  (macOS and Winsock do not guarantee it), and the per-socket call is what
  Node does.

## Decision

Call `setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &1, 4)` on every fd returned
by `accept()` in the HTTP event loop, before the TLS/h2 branch so HTTPS,
HTTP/2 and WebSocket connections (all accepted through the same block) get
it too. The option value comes from a constant global
(`@__kml_http_nodelay_one`), not an alloca: `doaccept` is a loop-body block
of `__kml_event_loop_run`, and a loop-body alloca is exactly the stack leak
the affected test exists to catch.

`IPPROTO_TCP` (6) and `TCP_NODELAY` (1) have the same values on Linux,
macOS and Winsock, so no per-platform constant is needed (the existing
`emitNetSocketSockOpt` already hard-codes them).

## Implementation notes

- `codegen/llvm/runtime_http.go`: the constant global next to the socket
  declarations in the HTTP runtime's ensure function; the `setsockopt`
  call in `doaccept`. The call runs even when `accept()` failed (fd is
  `-1`, `setsockopt` returns `EBADF`, ignored) so no extra basic block is
  needed.
- No new test: the existing many-requests test is the regression guard and
  now doubles as a timing canary on delayed-ACK loopbacks.

## Side effects discovered

None new. The `bad record MAC` server-side log in
`TestE2ETLSConnectVerifyFails` noted in ADR-00720 remains open.

## Verification

- Windows 11 (mingw-w64 UCRT clang, MSYS2): `TestE2EHTTPListenManyRequestsDoesNotLeakStack` passes in 56 s (it skipped there before only because clang was not on PATH; the Windows shim maps `setsockopt` to Winsock).
- Linux x86-64 (Docker Desktop on Windows, `golang:latest` + the release workflow's apt packages, clang 19): pre-fix, the same test was still running after 13 minutes at ~25 requests/s; post-fix the same test passes in 5.5 s, and the HTTP/HTTPS/h2/WebSocket/cluster test families all pass (48 s total).
