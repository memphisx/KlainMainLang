# ADR-00078: ArrayBuffer / TypedArrays

- **Relations**: Implements [TDD-00018](../tdd/TDD-00018.md)
- **Date**: 2026-07-30

## Context

Picked up as the next roadmap item after `URL`/`URLSearchParams` (`ADR-00076`) and the object-literal-coercion bug fix (`ADR-00077`): `STATUS.md`'s backlog flagged `ArrayBuffer`/TypedArrays as the Medium-effort item everything else kept citing as a blocker (the `fetch`/`fs` null-byte-truncation bug, `crypto.getRandomValues`'s `number[]` workaround, `TextEncoder`/`TextDecoder`). `TDD-00018` fully scoped the design (three research passes confirming the existing array system's representation, confirming no existing precedent for "one allocation, multiple typed views," and confirming `emitIndexPtr`/`emitIndex` are already fully generic over element type) before any implementation started; this ADR is that implementation, built to the "Core set" scope confirmed with the user during planning: `ArrayBuffer` + 8 numeric TypedArrays, all 3 construction forms, full reuse of existing array methods, plus `.set()`/`.subarray()`/`.byteLength`.

## Investigation

Manual smoke-testing (compiling and running one-off `.ts` repros before writing the permanent test suite, per this session's established practice) found and fixed two real bugs the codegen-reading-correct design review didn't catch:

- **`.map()` didn't preserve a TypedArray receiver's element type.** `emitArrayMap` (`emit_arrays_hof.go`) sizes its output array from `cb.retType()` — the callback's own inferred return type — not the receiver's element type. For a plain `number[]` this is a distinction without a difference (both default to `i64`), but for `new Uint8Array([10,20,30,40,50]).map((x: number) => x * 2)`, the unannotated arrow's inferred return type defaulted to `i64` (8 bytes/element) while the receiver's actual element width is 1 byte — so the mapped output was allocated and *written* at an 8-byte stride, but a variable declared `: Uint8Array` reads it back at a 1-byte stride. Confirmed directly: `doubled[0]` read correctly (`20`, offset 0 is offset 0 regardless of stride) but `doubled[1]`–`doubled[4]` all read `0` (reading into the unused high bytes of the previous i64-sized write). Real JS's `TypedArray.prototype.map()` always returns the same TypedArray kind as the receiver — this compiler's version didn't.
- **The exact same bug existed a second time, independently, in the type-inference path.** `emit_exprs_types.go`'s `inferExprType` has its own separate `"map"` case — used only to decide an *unannotated* variable's declared type (`const doubled = a.map(...)`, no `: Uint8Array`) — which computed its answer from the callback body's own inferred type, via a completely different code path than `emitArrayMap`'s actual emission logic. Fixing `emitArrayMap` alone left this second path disagreeing with it: an unannotated `doubled` got declared as a plain 8-byte-element `number[]` while the (now-fixed) actual data was written at 1-byte stride — the identical stride-mismatch failure mode, just inverted. Found directly via `examples/typedarrays/typedarrays.ts` (which deliberately leaves `doubled` unannotated), not by inspection — the annotated-variable test case alone would not have caught it.
- **Array literals cannot be evaluated as a general sub-expression in this compiler** — confirmed directly: `new Uint8Array([1, 2, 300, -1])` initially failed with "array literal must be used in a variable declaration," because `resolveArrayForHOF` routes any non-identifier expression through the general `emitExpr`, which rejects `*ast.ArrayLiteral` outright everywhere except a variable declaration's own initializer (the same restriction `Array`/`Map`/`Set` construction already has). Handled as its own case (`emitTypedArrayFromArrayLiteral`), evaluating each element directly, rather than losing this common, natural construction form.

Also confirmed directly (not just from the TDD's design review) that the core new mechanism works as intended: a `Uint8Array` view and an `Int32Array` view constructed over the *same* `ArrayBuffer` correctly see each other's writes, reinterpreted at each view's own element width (writing bytes `[1,0,0,0]` through the `Uint8Array` view and reading `1` back through the `Int32Array` view) — the one thing this feature needed that nothing in the existing array system provided.

## Decision

Built exactly to `TDD-00018`'s design, with the two bug fixes above folded in:

- `ArrayBuffer`: `Type{IR: "ptr", IsArrayBuffer: true}`, a hidden `{i64 byteLength, ptr data}` heap struct, `.byteLength` via a dedicated `emitMember` case (same pattern `.size` already uses for Map/Set) — general expression, works anywhere.
- TypedArrays: `IsTypedArray bool` riding on the existing `IsArray`/`ElemType` (`ArrayOf(elemTy) + IsTypedArray`), one `elemKind`-string → `Type` lookup table (`Int8Array`…`Float64Array`, 8 variants). Construction restricted to a variable declaration's initializer, matching `Array`/`Map`/`Set`'s existing restriction — one AST node (`NewTypedArrayExpression{ElemKind, Arg}`) parsed by a single shared `parseNewTypedArrayBody`, dispatching at codegen time on `inferExprType(arg)` into view/copy-construct/own-buffer paths (plus the array-literal special case found above).
- `.set()`/`.subarray()`/`.byteLength` added as new, `IsTypedArray`-gated dispatch; every other method (`.fill`, `.slice`, `.reverse`, `.at`, `.indexOf`, `.includes`, `.forEach`, `.some`, `.every`, `.reduce`, `.find`, indexing, for-of, `.keys()`/`.values()`/`.entries()`) needed zero changes, confirmed by the test suite exercising a representative sample of each.
- `.map()` fixed in both of the places identified above to force the result's element type to the receiver's own `elemTy` whenever the receiver `IsTypedArray`, matching real JS semantics.
- Deliberately out of scope, per the TDD: `Uint8ClampedArray`, `DataView`, `BigInt64Array`/`BigUint64Array`, `.buffer` property, the 3-argument sub-range view form, and any of the follow-ups this unlocks (`fetch`/`fs` fix, `crypto.getRandomValues` migration, `TextEncoder`/`TextDecoder`).

## Implementation notes

Files touched: `ast/nodes.go` (`NewArrayBufferExpression`, `NewTypedArrayExpression`), `parser/parser_literals.go` (`parseNew`'s dispatch + `parseNewArrayBufferBody`/`parseNewTypedArrayBody`), `codegen/llvm/types.go` (`IsArrayBuffer`/`IsTypedArray` flags, `ArrayBufferType()`/`TypedArrayType()`, `ResolveTypeName` cases), new `codegen/llvm/emit_arraybuffer.go` (construction + `.set()`/`.subarray()`/`.byteLength`), one new case in `emit_arrays_core.go`'s `emitArrayVarDecl` switch, one case each in `emit_exprs.go`'s dispatch (`ArrayBuffer` only — `TypedArray` construction is deliberately absent from general-expression dispatch, consistent with its var-decl-only restriction), `emit_exprs_types.go`'s `inferExprType` (`ArrayBuffer` case, plus the `.map()` fix), `emit_exprs_vardecl.go`'s untyped-inference switch (both new AST nodes), `emit_exprs_member.go` (`.byteLength`), `emit_call.go` (`.set()`/`.subarray()` dispatch block), and `emit_arrays_hof.go` (`emitArrayMap`'s fix — the one existing file this feature needed to change, contrary to the TDD's "zero changes needed" framing for the reused array machinery, which held for every other method except this one).

No new `runtime_*.go` file was needed — unlike `URL` (which needed `runtime_url.go` for libcurl's URL API declarations), every C primitive this feature uses (`malloc`/`calloc`) was already declared by existing `ensure*()` helpers.

## Side effects discovered

Both `.map()` bugs above (Investigation section) — found and fixed in this same piece of work, not deferred, since they directly blocked verifying this feature's own example/tests.

## Verification

- Manual smoke testing across 8 separate `.ts` repros before writing the permanent suite: own-buffer construction + indexing wraparound, `ArrayBuffer` + view construction + cross-element-type buffer sharing (`Uint8Array`/`Int32Array` over the same bytes), array-literal and copy-construct-from-another-TypedArray forms, `.set()`/`.subarray()` (including the buffer-sharing write-through-one-read-through-other check), reused HOFs/`.slice`/`.reverse`/`.at`/for-of, both throw paths (`ArrayBuffer` length not a multiple of the element size; `.set()` source too large), and `Float64Array`/negative `Int32Array` values.
- `tests/typedarrays_test.go`: 16 new E2E tests, including explicit regression tests for both `.map()` bugs found above.
- `examples/typedarrays/typedarrays.ts` added and run via `make examples`.
- `go build -o klainmain . && go vet ./... && go test ./...` (all green) and `make examples` (66/66 — one transient network-timing flake on an unrelated pre-existing example, reproduced clean on immediate re-run) both passed on the final tree.
