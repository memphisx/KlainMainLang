# TDD-00046: Opt-in embedded JS engine for `eval`/`vm` (pluggable backend, quickjs-ng first)

- **Status**: Partially Implemented
- **Date**: 2026-08-09

## Context

`eval(s)` and the `vm` module are the two remaining Global-functions/Node-core-modules gaps blocked on the same root cause: this compiler is ahead-of-time only, with no JIT or interpreter to run code text that only exists at runtime. `docs/status/GLOBAL-FUNCTIONS.md` and `docs/status/NODE-CORE-MODULES.md` currently both describe this as permanent ("won't implement").

It doesn't have to be permanent — a small embedded JS engine, linked in only when a compile-time flag opts in, can back both. This is scoped now (while genuinely low priority — see below) because it's a real design fork with several non-obvious wrinkles worth settling on paper before implementation starts: which engine, how the opt-in flag is shaped so it can grow to more than one engine, how results cross into this compiler's own type system, and how the two runtimes' memory stay isolated.

**Priority**: deliberately low. This should be picked up opportunistically as the project pushes toward broader language-surface coverage, not ahead of the three core-priority areas or this project's own blockers list (modules, real concurrency, the type system, generics). Nothing else in the roadmap depends on it.

**Engine survey** (see conversation history for the full comparison): V8 was ruled out — its build (`gn`/`ninja`, snapshot blobs) and JIT-tiered architecture fight this project's "single AOT-compiled binary, `--static` on Linux" identity at every turn. Bun isn't an embeddable library (it's an application); its engine, JavaScriptCore, has the same heaviness/JIT problems as V8. Escargot (Samsung) is real and actively maintained (ES2025 target, static/shared lib builds on Linux/macOS) but is LGPL-2.1 — static-linking obligations that land on anyone who statically links a `klainmain`-compiled binary, in direct tension with the `--static` flag. Nova and newer pure-Rust engines (lumen, brimstone) are interesting but too immature (Nova self-reports ~80% test262, "small-scale deployment" only) or have no track record yet. **quickjs-ng** (MIT, pure C, no JIT, a release roughly every two months, full test262 run per PR) is the best fit and the only one scoped for V1 here.

## Design

### Opt-in flag

A new `main.go` flag, following the existing `-mm=manual|gc` pattern (`flag.String`, explicit named default, `switch` validation, `fatal()` on an unrecognized value):

```
-eval-engine string
      embedded JS engine backing eval()/vm.* — "none" (default) or "quickjs".
      Pulls in a full embedded JS engine as a build dependency; purely opt-in.
      See docs/tdd/TDD-00046.md.
```

Without the flag (the default, `-eval-engine=none`), source using `eval(...)` or `vm.*` is a hard compile error pointing at the flag and this doc — the same shape as the existing `-mm=auto is not implemented yet` message. This is the mechanism that satisfies "the user is completely aware of what he is doing": there is no way to end up with an embedded JS engine linked into your binary by accident.

The value is a **name, not a boolean**, specifically so a second engine (Escargot, or whatever exists by the time this is picked up) is a new accepted value plus a new adapter, not a flag redesign — see Extensibility below.

### Extensibility: a capability table + adapter boundary

A new small registry (proposed home: `codegen/llvm/evalengine.go`), modeled directly on `gclocate.go`'s `LocateGC`:

```go
type EvalEngineCapability struct {
    Name     string
    OS       []string // nil = any runtime.GOOS
    Arch     []string // nil = any GOARCH
    MemModes []string // which -mm values this engine has been verified safe under
    License  string
    Locate   func() (cflags, libs, sources []string, err error)
}

var evalEngines = map[string]EvalEngineCapability{
    "quickjs": {
        Name: "quickjs", OS: nil, Arch: nil, MemModes: []string{"manual", "gc"},
        License: "MIT", Locate: locateQuickJS,
    },
}
```

`quickjs-ng` itself needs no OS/arch/mm restriction (portable C11, isolated heap — see below) — the restriction fields exist for *future* engines that might, e.g., only ship a prebuilt static lib for specific platforms, or that turn out unsafe under `-mm=gc`. `main.go` validates the requested engine against the current `runtime.GOOS`/`GOARCH`/`-mm` the same way it already validates `--static` against `runtime.GOOS`, with a `fatal()` explaining exactly what's unsupported and why — never a silent fallback.

Every engine plugs into the **same** small C ABI, so the codegen side (`emit_eval.go`, proposed) never branches on which engine is active:

```c
int  kml_eval_init(void);
void kml_eval_shutdown(void);
// Returns a KML tag/payload pair via out params; see emit_dynamic.go's
// kmlTag* scheme. Non-zero return = threw; *out_err is a KML-owned string.
int  kml_eval_run(const char *code, int8_t *out_tag, int64_t *out_payload, char **out_err);
```

A second engine later is: one `Locate` function, one adapter `.c` file implementing this same three-function contract, one new map entry. Nothing else in codegen changes.

### Marshaling: JSON round-trip, not a bespoke value marshaler

The recommended design: **eval's result crosses the C boundary as a JSON string, not a live engine value.** quickjs-ng has `JSON.stringify` built in — the adapter calls it on the eval result internally, hands back a plain `char*`, and `emit_eval.go` feeds that string through the **existing** `runtime_json.go` JSON-parse pipeline to materialize a `TypeAny`-boxed value, exactly as `JSON.parse(s)` already does today. This one decision buys three things at once:

1. **No second marshaler to write or maintain** — reuses already-tested code, with the same known limitation this project already documents (flat objects only — see `docs/status/JSON.md`; nested-object `JSON.parse` is [TDD-00015](TDD-00015.md), still open).
2. **Heap isolation for free** — the only thing that ever crosses the boundary is a `malloc`'d C string, never a pointer into quickjs's own heap. quickjs-ng's internal GC (refcount + cycle collector) and this compiler's own memory mode (`manual`/`-mm=gc`) never need to know about each other. This should still be **directly verified on both dev machines** the first time it's built (per this project's own platform-verification practice) rather than assumed from this reasoning alone.
3. **Non-marshalable results reject themselves** — a function, a circular structure, or `undefined` either throws or serializes to `undefined` under real `JSON.stringify` semantics too, which becomes the natural "can't marshal this" rejection path with no extra bespoke logic. Reject via `emit_exceptions.go`'s existing `try`/`catch`/`throw` machinery (setjmp/longjmp) — a catchable error, not silent garbage, per this project's "fix bugs, don't paper over them" rule.

### `vm` module V1 scope

Scope V1 to `vm.runInNewContext(code: string, sandbox?: object): any` only — a fresh quickjs context, with `sandbox`'s fields (if given) injected as globals before running (same JSON round-trip: the KML object is stringified, parsed into the fresh context, each top-level key set as a global). `vm.Script`/`.runInContext`/`.runInThisContext`/timeout options are deliberately out of scope for V1, staged for later the same way RegExp ([TDD-00035](TDD-00035.md)), EventSource ([TDD-00038](TDD-00038.md)), and WebSocket ([TDD-00039](TDD-00039.md)) were each built in stages. `vm` is isolation for convenience here, explicitly **not** a security sandbox — that's true of real Node's `vm` too, and should be stated plainly wherever this ships, not implied.

### Build: vendoring, not a system package

Unlike `-mm=gc` (which expects `bdw-gc`/`libgc` already installed via `brew`/`apt`), quickjs-ng isn't a standard OS package on either dev machine and has none of Boehm GC's platform-specific build fragility (`GC_stackbottom`, `ucontext_t` layout, etc. — see ADR-00080/ADR-00051). The simpler, more deterministic option: **vendor a pinned quickjs-ng source snapshot into the repo**, compiled once into a static archive as part of the `-eval-engine=quickjs` build path, the same way `-mm=gc` today appends an extra source file (`gcShimPath`) to `clangArgs` — this would append the adapter `.c` file and the vendored archive/sources instead. This pins an identical, known-good version across both the x86-64 Linux box and the Apple Silicon Mac, which a system-package approach can't guarantee. This would be the **first** vendored third-party C source tree in this repo (everything else is either plain libc or an expected-preinstalled system library) — flagged as a genuinely new pattern for this project, not just a repeat of the `-mm=gc` story.

### The warning

Print a one-line, in-character warning to stderr at compile time when `-eval-engine` is anything other than `none` and the program actually contains an `eval`/`vm` call — e.g.:

> `klainmain: heads up — this program uses eval()/vm.* under -eval-engine=quickjs. "Klain Main" is right there in the name: we're not going to stop you, but you're now shipping a full embedded JS engine inside an ahead-of-time-compiled binary to run code that only shows up at runtime. Godspeed.`

Illustrative wording only — finalize at implementation time. Exact emission point (flag-parse time in `main.go` vs. first actual lowering inside `EmitProgram`, which only warns if `eval`/`vm` is really used) is an open question below.

## Open questions

- Vendoring mechanism (plain copy vs. git submodule) and the exact quickjs-ng version to pin — and whether to track upstream or freeze once picked.
- Exact point the compile-time warning fires from — unconditionally whenever `-eval-engine` is set, or only when `eval`/`vm` is actually lowered (requires `EmitProgram` to expose that it happened).
- Whether `-mm=gc` genuinely needs no special handling around quickjs-ng's own allocator, or whether this needs a direct ASan/valgrind pass before trusting it — the heap-isolation reasoning above (nothing but a `malloc`'d string crosses the boundary) should hold, but per this project's own platform-verification practice this needs confirming on both dev machines when actually built, not just assumed from design.
- What a second engine (Escargot, most likely) would need beyond this doc's mechanism — in particular, whether its LGPL-2.1 license means `-eval-engine=escargot` must dynamically link rather than vendor-and-statically-link to stay easily compliant, or whether relinking-object provision is enough. Deliberately left unresolved since it only matters if/when that engine is actually added.
