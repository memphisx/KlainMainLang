# ADR-00704: -optimize-memory — stack-allocated closure headers and environments

- **Relations**: Extends ADR-00702; Implements TDD-00134 (Stage 1, closure part)
- **Date**: 2026-09-04

## Context

ADR-00702 shipped `-optimize-memory` for object literals and left closure
environments heap-bound — TDD-00134 called them "a high-value escape target
(every arrow allocates one) but the trickiest to prove non-escaping". With
the binding-level escape checker already deciding the object case, the
closure case turns out to need no new analysis at all: a closure literal
bound to a let/const that passes the same flow check cannot outlive its
block either.

## Investigation

A closure is two fixed-size heap blocks (`emitArrowFunctionWithHints` /
`emitFunctionExpression`, emit_func.go): the 16-byte `{fnPtr, envPtr}`
header and, when there are captures, an env struct of N cell *pointers* —
both compile-time-sized, so both alloca-able. The captured variables
themselves live in separate heap cells (`promoteCaptureToCell`) shared by
pointer with the enclosing scope and any other closure; those must stay
heap regardless (another capturer may escape), and do.

The existing checker already handles the closure-specific hazards: calling
the candidate (`f()`) propagates nothing; passing it as an argument
(setTimeout, HOFs), returning it, or storing it disqualifies; a
`Memory.free(f)` mention disqualifies (the existing double-free guard).

## Decision

- Stack-plan candidacy (escape_check.go, `p.stack` branch) widens to
  non-async ArrowFunction and non-async, non-generator FunctionExpression
  initializers. Async closures are excluded: invoking one hands the
  header/env to a task that can outlive the block.
- Both emission twins route their header+env allocation through one helper
  (`closureAllocs`, emit_stackalloc.go): entry-block allocas when the
  literal is the stack-planned marker (consuming it), the previous mallocs
  otherwise. No zeroing needed — every slot is stored immediately. Capture
  cells (including a named function expression's self-cell) are untouched.
- `maybeRegisterAutoFree`'s existing stack-skip covers closures too (a
  `__kml_closure_free` on an alloca would corrupt the heap).

## Implementation notes

Files: escape_check.go (candidacy), emit_stackalloc.go (`closureAllocs` +
doc header), emit_func.go (both allocation sites rewired), tests in
optimize_memory_test.go. A nested closure declared inside another closure's
body allocas into the enclosing *emitted function*'s entry block — the
per-function builder swap emitClosureFunc already does provides that for
free.

## Side effects discovered

None; flag-off output is unchanged, and the escaping cases (returned,
pushed, setTimeout-passed) verifiably keep all their mallocs.

## Verification

Mac (Apple Silicon): IR tests assert a two-closure function loses every
`malloc(i64 16)` (2 header allocas, capture cells still `malloc(i64 8)`)
while escaping closures gain no alloca; behavioral equivalence with/without
the flag including loop-iteration closures over loop variables; the
Closure/Arrow/Capture/Memory/FinReg/HOF suites pass; `go vet` clean.
