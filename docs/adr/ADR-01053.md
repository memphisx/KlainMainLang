# ADR-01053: An error inside a nested function body is a compile error, not a compiler crash

- **Date**: 2026-09-21

## Context

The 2026-09-21 Test262 run (both lanes, Windows x64) listed twelve files whose reason was a recovered compiler
panic, `CRASH: runtime error: slice bounds out of range [:-1]` — among them the in-scope
`language/{statements,expressions}/async-function/try-return-finally-return.js` and
`language/expressions/async-arrow-function/try-return-finally-return.js`. Reduced:

```ts
async function f() {
  try {
    return "early-return";
  } finally {
    return await new Promise(function(resolve, reject) { resolve("override"); });
  }
}
```

The executor's `resolve("override")` is a legitimate typed-subset rejection (an unparameterised `new Promise`); the
defect is that reporting it crashed the compiler.

## Investigation

The conformance runner recovers the panic into a reason string, which says nothing about where it came from. With a
stack (`KML_CONF_STACK=1`, added here): `popScope` ← `emitTry` (`emit_exceptions.go`, the try body's error path).

`emitFunctionDeclAs`, `emitClosureFunc` and the function-expression emitter (`emit_func.go`) each save `e.scopes`,
set it to nil for the nested body, and restore it on the *normal* path only. Every error return in between left the
nested function's own, shorter scope stack in place. The error then unwound through the enclosing emitters —
`emitFinallysToDepth` and `emitTry` each pop the scope they pushed — and the second pop ran off the bottom of the
wrong stack. Outside a scope-pushing construct the same error surfaced cleanly, which is why it went unnoticed.

Each of the three already restores its break/continue/label/finally stacks in a `defer` "so an error return partway
through … must not skip the restore"; the scope stack was the one piece left out.

## Decision

Each of the three emitters defers a restore of `e.scopes` that runs when the normal-path restore has not
(`scopesRestored`). The defer is registered before `defer e.popNestedFuncScope()`, so it runs after it — the nested
scope is popped on its own stack first.

`tools/conformance`: with `KML_CONF_STACK` set, a recovered compiler panic prints its stack to stderr.

## Implementation notes

`codegen/llvm/emit_func.go`, `tools/conformance/main.go`.

## Side effects discovered

The committed Windows reports of that run still bucket these twelve files under the crash reason; they fail either
way (now as ordinary compile errors), so no pass count moves. The next full run re-buckets them.

## Verification

Windows 11 x64: `TestE2ENestedFunctionErrorInsideTryFinallyIsNotAPanic` (function-expression and arrow forms);
the eight Test262 categories that contained a crash re-run with `KML_CONF_STACK=1`: zero crashes. Targeted E2E batch
over every test with a closure, a function expression or an expected compile error: see the session's final pass.
