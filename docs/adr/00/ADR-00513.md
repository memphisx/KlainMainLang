# ADR-00513: `res.statusCode` getter/setter on Node's `ServerResponse`

- **Relations**: `Implements TDD-00131`
- **Date**: 2026-08-30

## Context

Node's `http.createServer((req, res) => …)` `res` object (TDD-00131 Stage 1)
supported `writeHead`/`setHeader`/`write`/`end` but not the imperative
`res.statusCode = N` property — Node's common alternative to
`res.writeHead(status)` when headers are set separately. Reading `res.statusCode`
back (e.g. to log or echo it) also had no support. This was the one concrete,
self-contained gap called out on the createServer status row.

## Investigation

`ServerResponseType` (`types.go:1652`) stores the status in an i64 field named
`status`; Node exposes it as the property `statusCode`. Method calls on `res`
already dispatch through `emitServerResponseMethod` (`emit_call.go:67` →
`emit_http.go`), but there was no handling for a **property** read or a
**property assignment** — those fall to the generic member/assignment paths,
which don't know the `statusCode`→`status` field-name mapping and reject it.

The `process.exitCode = N` setter (`emit_exprs_assign.go:193`) is the exact
template: a property-name-guarded assignment special-case that stores into a
known slot.

## Decision

Three small, symmetric additions, all keyed on `Property == "statusCode"` and the
receiver's `IsServerResponse`:

1. **Setter** (`emit_exprs_assign.go`): `res.statusCode = N` stores the coerced
   i64 into the `status` field. Compound assignment (`+=`) is rejected, matching
   the `process.exitCode` precedent.
2. **Getter** (`emit_exprs_member.go`): `res.statusCode` loads the `status`
   field, mirroring the `req.url`→`path` field aliasing already there.
3. **Type inference** (`emit_exprs_types.go`): `res.statusCode` infers `i64`
   (matching the stored field and `writeHead`'s status argument), so it can be
   used in expressions (`"code=" + res.statusCode`).

## Implementation notes

- The field is named `status` internally and `statusCode` in the Node API; all
  three sites translate the name, so nothing else in the response path changes —
  the dispatcher still reads `status` after the handler returns.

## Side effects discovered

The rest of the Writable contract is **not** addressed and is architectural, not
incremental: `res.write` returning a backpressure boolean, `drain`/`cork`/
`uncork`, and a non-blocking `server.listen` are all incompatible with the
current **buffered** response model (the handler fully builds `{status, body,
headers}`, which is flushed only after it returns — ADR-00300/ADR-00391). Real
backpressure requires writing to the socket incrementally during the handler;
non-blocking listen requires restructuring the top-level accept loop around the
event loop. Each warrants its own TDD rather than a vacuous half-implementation
(a buffered `res.write` would always return `true`). Tracked as the remaining
open scope on TDD-00131 and the createServer status caveat.
