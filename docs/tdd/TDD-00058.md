# TDD-00058: Fixed-point unannotated-return-type inference (closes ADR-00041's forward-reference boundary)

- **Status**: Implemented
- **Date**: 2026-08-10
- **Notes**: Bounded re-inference sweep over same-scope unannotated function declarations (top-level and TDD-00057 nested), not a general multi-pass type system; a genuinely circular unannotated pair still can't converge and keeps the old default-fallback behavior; `@erased` generics were folded into the same sweep by ADR-00152 after a real repro confirmed the gap

## Context

[ADR-00041](../adr/ADR-00041.md) added best-effort return-type inference for an unannotated function (`function makeA() { return ... }`, no `: T`) — a single top-to-bottom pass over `registerFunctions` computes each function's inferred return type from its own first `return` statement, in source order. That ADR's own Investigation section accepted a known boundary at the time: a function calling another unannotated function *declared later in the same file*, where the callee returns a non-scalar (object/array/closure/`Date`/…), infers wrong — the caller's own inference runs before the callee has been registered, sees no signature for it, and falls back to the same generic-identifier-call default every other not-yet-known callee gets.

Confirmed still live and reproduces exactly as described:

```ts
function makeA() { return makeB() }
function makeB() { return { x: 1 } }
console.log(makeA().x)
```
```
klainmain: codegen error: 3:21: field access on non-object (no field 'x')
```

`docs/status/LANGUAGE-CONSTRUCTS.md`'s Known Limitations table and `docs/status/README.md`'s Functions & closures row both still track this as open. Picked up now alongside [TDD-00057](TDD-00057.md) (nested function declarations) since that work reuses the exact same signature-building helper (`buildFunctionSig`, factored out by [ADR-00149](../adr/ADR-00149.md)) in a second place — `pushNestedFuncScope` — that has the identical single-pass shape and would otherwise ship with the identical boundary from day one.

## Design

### Root cause, precisely

`registerFunctions` (`emitter.go:804`) and `pushNestedFuncScope` (`emit_func.go`, TDD-00057) each do one linear pass over their own statement list, calling `buildFunctionSig(fd)` once per declaration and writing the result straight into `e.funcs`/the current `nestedFuncScope` as they go. For an unannotated `fd`, `buildFunctionSig` calls `inferUnannotatedReturnType`, which runs `inferExprType` on `fd`'s first `return` expression — including, for `return makeB()`, `inferExprType`'s `*ast.CallExpression` case, which resolves `makeB`'s return type via `resolveFuncRef("makeB")` (ADR-00149) against whatever's in `e.funcs`/the nested scope stack *at that exact moment in the loop*. If `makeB` hasn't been reached yet, that lookup misses, and `inferExprType`'s final fallback (`emit_exprs_types.go`, the function's own unconditional `return TypeI64` after every other case falls through) is what `makeA` gets registered with — not literally `void` as ADR-00041's older prose describes (the `TypeI64` catch-all was added later), but the observable failure is the same: a wrong, silently-registered signature that only surfaces as a downstream error once something actually depends on the real shape (`.x` field access, an array method, calling the result, etc.).

### Fix: bounded fixed-point re-inference, not a general multi-pass type system

Not attempting real fixed-point/multi-pass type inference in general — this stays exactly what ADR-00041 already committed to (single-source-of-truth-per-function, best-effort, source-derived), just applied enough times for a same-scope forward-reference chain to fully settle:

1. While doing the existing single pass, collect every non-generic function declaration whose `ReturnType == nil` (the only ones whose registered signature can possibly be wrong from ordering — an explicit annotation is never inference-dependent) into a `[]*ast.FunctionDeclaration` alongside the existing `e.funcs`/scope writes.
2. After that first pass finishes (so every declaration — including ones declared after an early unannotated one — has *some* entry, even if a still-provisional one for another unannotated function), re-run `buildFunctionSig` for every collected declaration, in the same source order, writing each result back into `e.funcs`/the scope immediately (not batched) so a later re-inference in the *same* sweep can already see an *earlier* one's freshly corrected result.
3. Repeat step 2 until a full sweep changes no return type, or the sweep count reaches `len(collected)` — an upper bound that's always enough for any acyclic reference chain to fully propagate one more hop per sweep (the same reasoning a Bellman-Ford relaxation bound uses), reached only by a genuinely non-terminating case (see below).
4. A genuinely **circular** pair of unannotated functions with no independently-typed base case (`function a() { return b() }; function b() { return a() }`, both unannotated, mutually recursive with nothing else to anchor a real type) cannot converge by construction — the sweep cap is hit and whatever the last computed value is (today, `TypeI64`, same as before this fix) stays registered. Not a new failure mode: this is the exact same "falls back to a default, not a crash" behavior ADR-00041 already established, just now reachable only by a genuinely undecidable shape instead of by *any* same-file forward reference.

Change detection between sweeps compares each collected function's `RetType` via `reflect.DeepEqual` rather than a hand-written field-by-field comparator — `Type` (`codegen/llvm/types.go`) carries ~30 fields today and has grown steadily over the project's history; a hand-rolled comparator would silently drift out of sync the next time `Type` gains a field, exactly the kind of two-copies-that-can-disagree risk `buildFunctionSig`'s own extraction (ADR-00149) was just written to avoid elsewhere. `reflect` has no existing use in `codegen/llvm` today; this introduces it for one narrow, cheap (small N, compile-time-only) comparison.

### Where this applies

Both `registerFunctions` (top-level) and `pushNestedFuncScope` ([TDD-00057](TDD-00057.md)'s nested-scope pre-registration) get the identical treatment — same helper, same shape, same bug. A nested function forward-referencing a same-body unannotated sibling that returns an object is exactly as broken today as the top-level case without this fix, just not yet independently reported anywhere since nested declarations didn't exist before this same work session.

### Explicitly not covered

An `@erased` generic function (TDD-00010 V2) builds its signature via `buildGenericParamSig`, a separate path from `buildFunctionSig`, still registered within the same `registerFunctions` loop and still subject to the identical ordering problem in principle. Left alone here — folding it into the same sweep would mean tracking two different "recompute this declaration's signature" shapes in one worklist for a case with no known real repro yet (an erased generic function returning an object literal from a not-yet-registered unannotated sibling call is a narrower/rarer combination than the plain-function case this TDD has an actual, confirmed repro for). Noted as a known remaining gap, not a regression — it had this exact same limitation before this document's fix too.
