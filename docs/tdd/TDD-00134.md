# TDD-00134: Escape analysis + value-layout optimizations (opt-in `-optimize-memory`)

- **Status**: Not Started
- **Date**: 2026-08-27

## Context

Today every object, tuple, array element of object type, and closure environment
is heap-allocated (`malloc` under `-mm=manual`, `GC_MALLOC` under `-mm=gc`).
There is **no escape analysis** and no stack allocation. This is the largest
*real* remaining gap versus Go-class native code: Go's speed comes substantially
from proving a value doesn't outlive its frame and putting it on the stack,
avoiding GC pressure, fragmentation, and cache misses entirely.

Crucially, unlike the concurrency work ([TDD-00133](TDD-00133.md)) these are pure
**optimizations with no semantic change** — the program behaves identically, just
allocates less. They fit the compiler's "menu of opt-in toggles" identity as a
single `-optimize-memory` axis, kept off by default until proven safe, then made
default.

## Design

Three related lowerings, staged. The LLVM/clang layer already handles the
micro-optimizations (SIMD, inlining, register allocation); the leverage here is
the **allocation/layout decisions clang cannot make** without our type
information.

### Stage 1 — Escape analysis → stack allocation

A per-function analysis that marks an allocation site (object literal, tuple,
`new` of a fixed-shape class, closure env) as **non-escaping** when its pointer
provably does not leave the function: not returned, not stored into a heap
object/global/array, not passed to a call that could retain it, not captured by
an escaping closure. A non-escaping allocation is emitted as an entry-block
`alloca` instead of `malloc`/`GC_MALLOC`.

- Conservative by construction: any uncertainty ⇒ heap (soundness over
  completeness), matching how the definite-assignment analysis
  ([TDD-00071](TDD-00071.md)) already errs.
- Reuses the free-variable/capture machinery ([TDD-00129](TDD-00129.md)'s
  `scanExprFV`, the closure `gatherCaptures`) to see what escapes via closures.
- Interacts cleanly with both memory modes: a stack value is simply never handed
  to the collector; under `-mm=gc` (Boehm, conservative) a stack `alloca` is
  already scanned, so correctness is free.

### Stage 2 — Flat value-type arrays (`Point[]` as packed structs)

Today an array of a fixed-shape object type is an **array of pointers** to
separately-heap-allocated elements (8-byte ptr slots — verified in
`emit_arrays_core.go`), so it fragments and thrashes cache. For an array whose
element is a fixed-shape value type with no dynamic/union fields, lay the elements
out **inline** (one contiguous `malloc` of `N * sizeof(Struct)`, AoS), enabling
clang's auto-vectorization.

- **Design tension:** this changes aliasing — today two array slots holding the
  same object pointer alias; inlined elements are value copies. So it is a
  **value-type opt-in** (a distinct element semantics), not a default flip, and
  relates directly to the array-boxing/reference-semantics question in
  [TDD-00127](TDD-00127.md). Likely gated behind an explicit marker (a `readonly`
  value-struct, or a dedicated `Vec<T>`/`@value` annotation) rather than inferred,
  to keep JS reference semantics the default.

### Stage 3 — Value-returned tuples (`[T, Error]`)

Tuples are heap-`malloc`'d structs today (`TupleType` → object). A small tuple
returned from a function can instead be returned **by value** as an LLVM
aggregate, which clang passes in registers (e.g. `RAX`/`RDX`) — eliminating the
allocation for the idiomatic Go-style `function f(): [T, Error] { … }` /
`const [v, err] = f()` pattern. Bounded to small tuples (register-passable);
larger ones stay heap.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Fixed-shape object/tuple structs (`%struct`, GEP field access) | Built | The values escape analysis proves stack-safe |
| Free-variable / capture analysis | Built | [TDD-00129](TDD-00129.md)/closure `gatherCaptures` — reused to see closure escapes |
| Two-builder alloca/body split (entry-block allocas) | Built | Stack allocations go in `e.allocas` already |
| Array element layout (`emit_arrays_core.go`) | Built | Stage 2 changes the object-element case only |
| An analysis pass framework over a function body | Partial | Escape analysis is a new whole-body walk |

## Open questions

- Granularity of `-optimize-memory`: one flag for all three stages, or per-stage
  toggles? Default-on once proven, or opt-in indefinitely?
- Stage 2's opt-in marker: reuse `readonly`, introduce `@value`/`Vec<T>`, or infer
  from "no field ever mutated + no aliasing observed"? The aliasing-semantics
  change makes inference risky.
- How far interprocedural to go: intraprocedural escape analysis is safe and
  cheap; a summary-based interprocedural pass catches more but is a bigger build.
- Closure environments are a high-value escape target (every arrow allocates one)
  but the trickiest to prove non-escaping — stage within Stage 1 or defer.
