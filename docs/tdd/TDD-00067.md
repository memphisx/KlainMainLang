# TDD-00067: Aligning the PCRE2 RegExp backend with ECMAScript semantics

- **Status**: Implemented
- **Date**: 2026-08-17

## Context

RegExp shipped ([TDD-00035](TDD-00035.md), ADR-00114–ADR-00120) on a PCRE2 backend: the JS pattern string is handed **verbatim** to `pcre2_compile_8`, and the only compile options ever set are `PCRE2_CASELESS` (`i`), `PCRE2_MULTILINE` (`m`), and `PCRE2_DOTALL` (`s`) — assembled in `__kml_regex_parse_flags` (`codegen/llvm/runtime_regexp.go:98`). The base option set is `0`. Nothing translates or normalizes the pattern between JS syntax and PCRE2 syntax (confirmed: no preprocessing pass in `codegen/llvm/emit_regexp.go`).

That means the engine currently exposes **PCRE2 (Perl) regex semantics, not ECMAScript semantics**. For ASCII patterns the two dialects mostly coincide, which is why the shipped feature looked complete against its own hand-written examples/tests — but Test262 exercises exactly the edge cases where they diverge, and those are silently wrong (wrong match, wrong result string) or hard-error at runtime.

Surfaced during the machine switch back to Apple Silicon: `make conformance` scored ~10 files lower on Mac (pcre2 10.47) than the committed Linux baseline, concentrated in `annexB/built-ins/RegExp/RegExp-*-escape-*` (`RUNTIME_NONZERO_EXIT`). That Mac/Linux delta is a *symptom*, not the disease: because patterns pass through verbatim, behavior is at the mercy of whatever the linked PCRE2 version does with a given escape, so two PCRE2 versions disagree. The broader goal scoped here is to make RegExp match JS/TS expectations as Test262 defines them — the version-divergence falls out of that for free.

Scoped as investigation → design now; implementation is a separate, staged follow-on (this document sets the stages).

## Investigation

Five minimal probes, each isolating one dialect gap, compiled and run on Mac (Apple Silicon, pcre2 10.47). Every one diverges from real JS:

| Probe | JS result | This compiler | Root cause |
|---|---|---|---|
| `/foo$/.test("foo\n")` | `false` | `true` | PCRE2 `$` matches *before a final newline* by default; ES `$` (no `m`) matches only at true end. Needs `PCRE2_DOLLAR_ENDONLY` whenever `m` is absent. |
| `/(a)?b\1/.test("b")` | `true` | `false` | Backref to an **unset** group: ES matches empty string; PCRE2 default fails the match. Needs `PCRE2_MATCH_UNSET_BACKREF`. |
| `/\u0041/.test("A")` | `true` | **throws** `PCRE2 does not support \F, \L, \l, \N{name}, \U, or \u` | ES `\uXXXX`/`\xXX` escapes; PCRE2 default doesn't accept `\u`. Needs `PCRE2_ALT_BSUX \| PCRE2_EXTRA_ALT_BSUX`. |
| `"a\u2028b".replace(/./g,"X")` | `"X\u2028X"` | `"XXXXX"` | Two gaps at once: (a) no `PCRE2_UTF`, so the subject is scanned as raw UTF-8 **bytes** — `.` matches each of U+2028's 3 bytes; (b) ES `.` must *not* match the line terminators `\n \r \u2028 \u2029`. |
| `/\d/u.test("5")` | `true` | `true`, but `u` is **silently ignored** | The `u` flag isn't validated or implemented (the flag-validation gap already recorded in ADR-00166). It happens to be harmless here; it is not for `\u{…}`, surrogate handling, or strict-syntax patterns. |

Three of these (`$`/newline, unset backref, `\u`) are undisclosed correctness bugs — `docs/status/REGEXP.md`'s Caveats section documents the *known* V1 narrowings (`.test` offset-0, no `.groups`, `$1`–`$9` only, etc.) but not these. They are noted here as deferred rather than fixed in passing, because the fix *is* this work.

## Design

The gaps fall into three tiers by implementation cost, which map cleanly onto staged delivery.

### Option A — Compile-option alignment (low risk, ASCII-safe, high value)

Add the PCRE2 compile options that move the dialect toward ECMAScript without changing behavior for the ASCII patterns that already work:

- `PCRE2_ALT_BSUX` — interpret `\uXXXX`, `\xXX`, `\0` the ECMAScript way (fixes the `\uXXXX` **throw**, the single highest-frequency everyday-JS gap here). *Note (2026-08-17): `PCRE2_EXTRA_ALT_BSUX` (which additionally enables `\u{…}`) is deliberately NOT set here or in B — it requires a compile-extra-options context, and more importantly `\u{3}` without the `u` flag is an ES quantifier (`u` ×3), not a code point, so unconditionally reinterpreting it would be wrong. It rides with the deferred `u`-flag/Option C work.*
- `PCRE2_MATCH_UNSET_BACKREF` — unset-group backref matches empty.
- `PCRE2_DOLLAR_ENDONLY`, set **only when `m` is absent** — `$` anchors at true end. (With `m`, ES and PCRE2 already agree that `$` matches at line boundaries.)

All three are per-compile option bits OR-ed into the existing `optout` in `__kml_regex_parse_flags`; the only control-flow change is making `DOLLAR_ENDONLY` conditional on the multiline flag already parsed there. No codegen-shape or offset-math change. This is the recommended first stage — it is where the conformance-per-effort ratio is highest and it removes a hard runtime error.

### Option B — Unicode matching (`PCRE2_UTF` + newline convention)

Enable `PCRE2_UTF` so `.` and character classes operate on code points, not bytes, and set `PCRE2_NEWLINE_ANY` (via a `pcre2_compile_context`) so `.` and `$`/`m` treat `\u2028`/`\u2029` (and `\n`/`\r`) as line boundaries — the closest single PCRE2 newline convention to ES's exact four terminators (it over-includes `\x0b`/`\x0c`/`\x85`, the documented `es-unicode` caveat; an exact `.` is Option C).

**`PCRE2_UCP` is deferred to Option C, not set here.** Measured against `built-ins/RegExp` Test262 (2026-08-17, Mac), enabling UCP *lost* conformance: PCRE2's UCP `\w`/`\s`/`\b` tables diverge from ECMAScript's — UCP `\s` matches U+180E, which ES dropped as whitespace in Unicode 6.3 (`u180e.js`). es-unicode with UTF-only scored +1 on that subset vs the pre-alignment baseline; UTF+UCP scored 0. So `es-unicode` keeps `\w`/`\s`/`\b` non-Unicode, and the ES Unicode-class semantics (the correct subset of what UCP provides, minus its ES divergences) become part of Option C's normalization pass.

The index space stays as-is. **Resolved (see Open questions):** offsets remain in the UTF-8 byte / code-point space the rest of this compiler's string layer already uses (`.charCodeAt`/`.length`/`.slice` are all byte-indexed, ADR-00028), because PCRE2_8's ovector offsets are already byte positions and keeping them makes `match.index` line up with `str.slice(match.index)`. Converting them to UTF-16 code units would make RegExp the *only* UTF-16-indexed surface in an otherwise byte-indexed language — so that conversion is split out into its own stage (`es-utf16`) rather than folded into B. This keeps Option B to "flip UTF matching on, keep the offsets," with no per-boundary conversion touching `emit_regexp*.go`.

### Option B-index — UTF-16 code-unit index space (`es-utf16`)

The stage between B and C. On top of `es-unicode`, convert PCRE2's byte offsets to true UTF-16 code-unit positions at every offset-producing/consuming boundary (`.index`/`lastIndex`/`.exec` slicing/`.split`/replace splice points in `emit_regexp*.go`) so `.index` matches the ES spec exactly rather than this compiler's byte space. Requires a byte↔UTF-16 conversion helper that does not exist yet, and formally diverges from the rest of the string layer's index space — which is why it is opt-in under its own mode, not part of the default `es-unicode`. Independently shippable; measured on the same RegExp Test262 subset. Kept distinct so the byte-space default (matching `.charCodeAt`/`.slice`) and the spec-exact-index mode are each selectable.

### Option C — Full ES-dialect normalization pass (most faithful, most work)

A pattern-translation front end (JS regex source → PCRE2 source) to handle what options can't: Annex B legacy octal/decimal escapes (`\1` with no group 1 = octal char), the `u`/`v` code-point dialects (`\u{…}`, `\p{…}`, set operations), the ES Unicode class semantics for `\w`/`\s`/`\b` (`PCRE2_UCP` plus corrections for where its tables diverge from ES, e.g. U+180E), and ES-specific character-class edge cases. In spirit this is a small hand-rolled ES-regex parser/normalizer in front of PCRE2 — the same "hand-roll the JS-specific layer, delegate the engine" split TDD-00035 already chose. Defer until A and B are measured.

### Dialect selection via a compiler flag

Options A–C are not just a one-way migration that silently changes everyone's match results — they are points on a faithfulness spectrum, and each is a legitimate thing to *want*. Expose the level as a compile-time flag, following the existing `-mm=`/`-globals=` convention (`-regex=<mode>`), whole-program:

- **`ecmascript`** — full ES fidelity: the Option C normalization pass layered over A + B + the index-space stage. This compiler exists to run TypeScript/JavaScript, so matching the language's own regex semantics is the correct eventual target. Not yet implemented; explicitly selecting it errors until Option C lands.
- **`es-utf16`** — the index-space stage (between B and C, see "Index space" below): everything `es-unicode` does *plus* converting PCRE2's UTF-8 byte offsets to true UTF-16 code-unit positions at every `.index`/`lastIndex`/`.exec`/`.split`/replace boundary, for spec-exact index reporting. Heavier than `es-unicode` (a conversion at every offset-producing site) and deliberately its own mode, since it diverges from the byte/code-point index space the rest of this compiler's string layer uses (`.charCodeAt`/`.length`/`.slice`, ADR-00028) — a program mixing `es-utf16` RegExp indices with byte-indexed `.slice` would get mismatched positions. Not yet implemented.
- **`es-unicode`** — Option B: the option-level alignment plus `PCRE2_UTF` and `PCRE2_NEWLINE_ANY`, so `.` and the character classes operate on code points (`\w`/`\s`/`\b` stay non-Unicode — `PCRE2_UCP` is Option C, see below). Offsets stay in the **UTF-8 byte / code-point index space the rest of the string layer already uses** (see "Index space" — no per-boundary UTF-16 conversion; that is `es-utf16`'s job). Unicode-correct for matching, lighter than `es-utf16`/`ecmascript`. Caveat: `PCRE2_NEWLINE_ANY` makes `.` (and `$`/`m`) treat `\x0b`/`\x0c`/`\x85` as line boundaries too, three more than ES's exact `\n \r \u2028 \u2029` — an exact `.` needs the Option C rewrite.
- **`es-ascii`** — Option A: the cheap compile-option alignment only (`ALT_BSUX`, `MATCH_UNSET_BACKREF`, conditional `DOLLAR_ENDONLY`). ASCII-faithful to ES; deliberately does *not* pay for UTF matching, the newline convention, or a normalization pass. For programs whose patterns and subjects are known-ASCII (a large fraction of CLI/microservice use), this is the smallest and fastest mode that is still ES-correct where it matters. Caveat: without the newline convention, `.` still matches `\r` (PCRE2's default treats only `\n` as the line end), where ES's `.` excludes it — inherited from today's behavior, fixed at `es-unicode` where `NEWLINE_ANY` excludes `\r`.
- **`pcre`** — today's behavior verbatim: the pattern goes to PCRE2 with only `i`/`m`/`s` mapped and no ES wrapping. This is a **feature, not a fallback** — PCRE2 is a more feature-complete engine than the ECMAScript dialect (recursion/subroutines, possessive quantifiers, conditionals, callouts, `\p{…}` in PCRE syntax), and a developer who wants that power, or who is porting an existing PCRE pattern, can ask for it explicitly and knowingly accept non-ES semantics.

The **default** (`-regex` unset) resolves to the highest ES stage actually implemented — `es-unicode` as of A + B. It advances to `es-utf16`, then `ecmascript`, as those land, so every release's default is the most ES-faithful mode that exists without ever silently falling back to raw PCRE.

Framing note: PCRE2 being the more *powerful* engine does not make it the more *correct* one here. ECMAScript regex is a distinct dialect, not a subset — it has behaviors PCRE2's defaults get wrong (the three Known-correctness bugs) and legacy Annex-B semantics PCRE2 doesn't reproduce at all, while PCRE2 has features ES lacks. Two overlapping supersets of a common core is precisely the situation a mode selector fits: `ecmascript` for "run my JS/TS as written," `pcre` for "give me the full engine."

### Recommended path

Implement the stages in order — A, then B, then the `es-utf16` index stage, then C — each a strict prerequisite of ES fidelity for the next: Stage 1 = Option A; Stage 2 = Option B (index-space decision resolved below — byte space, so B carries no conversion work); Stage 3 = `es-utf16`, the UTF-16 code-unit index conversion; Stage 4 = Option C, only for the residual. Each stage is independently shippable and independently improves the conformance number. **Stages 1 and 2 (A + B) land together** in the first delivery — B's index-space question resolving to "keep byte offsets" removes what would have gated it, so there is no reason to hold A back for a separate measurement round.

The flag rides along for free: `-regex=pcre` is available from day one (it is today's behavior); each completed stage lights up its mode (`es-ascii` after A, `es-unicode` after B, `es-utf16` after the index stage); and the default points at the highest ES stage implemented so far, becoming the true `ecmascript` target once C lands. That keeps every intermediate release honest — the default is always the most ES-faithful mode that actually exists — without ever silently regressing a program that wanted raw PCRE.

## Open questions

- **Index space (the crux of Option B).** *Resolved 2026-08-17* — offsets stay in the **UTF-8 byte / code-point** space. The decisive factor: the rest of the string layer already committed to byte indices (`.charCodeAt`/`.codePointAt` index by byte and return the byte value, `.length`/`.slice`/`.indexOf` are byte-based — ADR-00028, `docs/status/STRING-METHODS.md`, `ENCODING-TEXT.md`), so converting only RegExp to UTF-16 would leave `match.index` unable to feed `str.slice(match.index)`. PCRE2_8's ovector offsets are already byte positions, so B keeps them verbatim (no conversion layer, no `emit_regexp*.go` offset-math change). True UTF-16 code-unit indices are still wanted for full ES fidelity, but as their own opt-in stage (`es-utf16`, between B and C) with its own byte↔UTF-16 helper — not folded into B and not the default, precisely because the default must stay consistent with the byte-indexed string layer.
- **`u`/`v` flags.** Approximate `u` via `PCRE2_UTF|PCRE2_UCP` (cheap, imperfect — offset space and some syntax still differ), or hold it as an explicit "not yet" error until Option C can do it properly? The `v` (unicodeSets) flag is strictly beyond PCRE2 options.
- **Newline convention for `.` and `$`.** *Resolved 2026-08-17 for B* — `es-unicode` uses `PCRE2_NEWLINE_ANY`, the closest single convention to ES's exact `\n \r \u2028 \u2029`. It over-includes `\x0b`/`\x0c`/`\x85` (documented `es-unicode` caveat, excludes those rows from Strict Coverage); an exact match needs the Option C `.`→character-class rewrite. `es-ascii` leaves the PCRE2 default untouched, so its `.` still matches `\r` — a separate documented caveat, since Option A is defined as option-bits-only with no compile context.
- **Version pinning vs. option-hardening.** *Partially resolved 2026-08-17 (Mac).* The residual Mac/Linux delta is **not** yet zero after A + B. It lives in the `annexB/built-ins/RegExp/RegExp-*-escape-*` files (`RUNTIME_NONZERO_EXIT`) — Annex-B legacy-escape semantics (`\2` to a non-existent group, decimal/octal escapes) that are Option C territory, so they still throw and stay PCRE2-version-sensitive. The three A/B-targeted behaviors are now explicit and version-independent. Re-measure after Option C; a documented minimum PCRE2 version may still be warranted for the Annex-B escapes until then.
- **Flag and mode names.** `-regex=` vs `-regexp=`; `es-ascii`/`es-unicode`/`ecmascript`/`pcre` vs a shorter or numbered set. Should match whatever reads most naturally alongside the existing `-mm=`/`-globals=` flags.
- **Cost of an `ecmascript`-by-default.** Shipping Option C as the default means the normalization pass + UTF matching are on unless opted out. Correct for a correctness-first target, but the `es-ascii`/`pcre` modes exist precisely for the size/perf-sensitive case — measure the normalization-pass and `PCRE2_UTF` overhead (binary size, match throughput) to confirm the default isn't painful for the common ASCII program, and to size the win from dropping to `es-ascii`.
- **Flag granularity.** Whole-program (simplest, matches `-mm=`/`-globals=`) vs. a per-`RegExp` pragma. Whole-program is the V1 recommendation; a per-pattern override is a possible later refinement if real programs need to mix a `pcre`-power pattern into an otherwise-`ecmascript` build.
- **Disclosure.** *Resolved 2026-08-17* — the three correctness bugs (`$`/newline, unset backref, `\u` throw) are now disclosed under `docs/status/REGEXP.md`'s **Known correctness bugs**, with the Strict Coverage note confirming the 2/13 count is unchanged (each lands on an already-excluded row). Stage 1 will erase bugs 1 and 3 and can then trim that note.
