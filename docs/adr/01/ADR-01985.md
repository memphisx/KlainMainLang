# ADR-01985: Narrowed unions at calls, `new` and void ternaries

- **Relations**: Implements TDD-00230; follows [ADR-01984](ADR-01984.md)
- **Date**: 2026-11-07

## Context

Five programs Node runs failed to compile:

- `t ? a() : b()` with both calls returning nothing: "an expression
  produced no value".
- `v.run()` on `v: (() => number) | R` narrowed to `R`: the receiver is
  held boxed, and no call rule took a boxed receiver, so the call fell
  through to "a number has no method".
- `xs.map(x => x.length)` over `([number, string] | string[])[]`: a tuple
  with mixed element kinds had no representation outside an annotation.
- `new c()` with `c: typeof K | null` narrowed by `if (c)`: the checker
  typed the callee from its declared type, not its narrowed read.
- `let w: WeakMap<object, number> | null = new WeakMap()`: inference from
  the return context unified against the whole union and found nothing,
  leaving the defaults, which tsc does not do.
- A local class whose derived constructor read a local in a nested
  function was rejected, as was one naming a catch binding, a
  destructured binding or a loop variable written after it.

## Decision

- A ternary whose arms are both void runs the chosen arm and is
  `undefined`. One void arm beside a value is boxed.
- A method call on a boxed receiver is the box's dynamic method call.
- A mixed-element tuple is its tuple type, an array of its elements
  ([ADR-01977](ADR-01977.md)).
- The binder records a flow-narrowed read for `new v()` of a variable, and
  the checker types the callee from it.
- Inference from the return context retries against the context without
  null and undefined when the whole union gives no candidate.
- A derived constructor declares its copies of the locals right after its
  top-level `super()` call. A read before that call is still rejected.
- A catch binding's cell opens the catch body, as a parameter's opens its
  function. A destructured binding's cell follows the destructuring; the
  block rebuild that hoists the class splices it in after that statement.
- A `for (let i …)` variable gets a cell per iteration, opening the body.
  The body reads and writes the cell. Its value is written back to the
  loop's binding at the body's end and before each `continue` of the
  loop, bare or labeled, so the test and update clauses see it.
- A `for…of`/`for…in` binding gets a cell opening the body, with nothing
  to write back, since each iteration binds it anew.
- A `var` binding written after the class is still rejected.

## Consequences

- Covered by `TestE2ENarrowedUnionsAndVoidTernary`,
  `TestE2ELocalClassDerivedCtorNestedFunction`,
  `TestE2ELocalClassCatchAndDestructuredCells` and
  `TestE2ELocalClassLoopVariableCell`, which match Node.
