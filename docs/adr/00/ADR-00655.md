# ADR-00655: Fix the CI-breaking regressions from the last release

- **Relations**: Extends ADR-00650
- **Date**: 2026-09-03

## Context

The `Release` workflow (Linux, `go test ./...`) failed on the previous release
commit. Three tests failed:

- `TestE2EObjectFromEntriesBareLiteral`
- `TestE2EObjectFromEntriesRoundTrip`
- `TestE2EHTTPUpgradeCoexistsWithNormalHTTP`

The first two reproduce on any platform (deterministic compile errors); the
third failed only on Linux CI.

## Investigation

**`Object.fromEntries` (real regression).** Both fromEntries tests failed with
`new Map(...) entries must share one value type — a heterogeneous-value map is
not supported`, at the *first* entry's value (`Object.fromEntries([['x', 10],
['y', 20]])`). The heterogeneous-entries guard added in ADR-00650
(`resolveMapEntriesArray`, `codegen/llvm/emit_collections.go`) compared each
pair's element types against the caller-supplied `keyTy`/`valTy`. But
`Object.fromEntries` normalizes those — it forces the key type to string/`ptr`
and derives the value type from a tuple inference over the source — so the
comparison ran the raw literal `10` (`i64`) against a `valTy` that had been
derived differently, and rejected a perfectly uniform entries array. The guard
was validating each pair against a *normalized* type rather than against the
other pairs.

**HTTP upgrade coexistence (flaky test, correct server).** The Linux failure
was `got "HTTP/1.1 200 OK\r\nContent-Length: 10\r\nConnection: close\r\n\r\n",
want body 'plain http'` — the server's response was *correct* (200, the 10-byte
body `plain http` announced by Content-Length), but the test issued a single
`conn.Read` and asserted on it, assuming one TCP segment carried both headers
and body. On Linux the body arrives in a later segment, so the lone read saw
only the headers. (The interleaved `tls: bad record MAC` line in the CI log was
from a concurrent TLS test, not this one.)

## Decision

- **Guard**: compare each entry pair's key/value types against the **first
  pair's own inferred types**, not the caller-normalized `keyTy`/`valTy`. This
  is a true homogeneity check among the pairs — exactly ADR-00650's intent
  (`new Map([['a','b'],[1,1]])` still rejects) — without the false positive from
  a normalized reference type.
- **Test**: since the request sends `Connection: close`, read the response to
  EOF (`io.ReadAll`) instead of a single `Read`, so headers and body are both
  captured regardless of TCP segmentation.

## Implementation notes

- `codegen/llvm/emit_collections.go`, `resolveMapEntriesArray`: track
  `refKey`/`refVal` from element 0; compare elements 1..n against those.
- `tests/http_upgrade_test.go`: `io.ReadAll(conn)` in place of a single
  512-byte `Read`; add the `io` import.

## Side effects discovered

None beyond the two fixed here. The compiler is deterministic; the earlier
apparent Test262 movement was conformance-runner measurement noise (shared
scratch dir across concurrent runs), tracked as separate harness-robustness
work.

## Verification

- `go test ./tests/ -run 'TestE2EObjectFromEntries'` and the
  `TestE2EMap|TestE2ECollections|TestE2EObject` suites — green on macOS
  (Apple Silicon).
- Genuinely heterogeneous entries still reject cleanly (`new Map([['a','b'],
  [1,1]])` → `heterogeneous-key map is not supported`).
- **All three originally-failing tests re-run on Linux in a `golang:latest`
  Docker container (with clang + libssl/libcurl/libtommath/libpcre2) — all
  PASS**, confirming the Linux-only failure is resolved on the platform that
  exhibited it.
