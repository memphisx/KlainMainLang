# ADR-00242: Deterministic correctly-rounded `Math.cbrt` (fdlibm), not platform libm

- **Relations**: Fixes a cross-platform CI failure; sibling of the other Math builtins ([ADR-00166](ADR-00166.md) audit context)
- **Date**: 2026-08-19

## Context

`TestE2EMathCbrtExpm1Log1p` asserts `Math.cbrt(27) === 3`. It passed on the macOS
dev machine but failed on Linux CI: `got "3.0000000000000004", want "3"`.

Root cause, confirmed directly in a glibc container: the platform libm `cbrt` is
not reliably correctly-rounded. glibc's **runtime** `cbrt(27)` returns
`3.0000000000000004` (~1 ULP high) and `cbrt(2)` returns `…34` rather than the
correctly-rounded `…32`; macOS/BSD libm, V8/Node, Go's `math.Cbrt`, and fdlibm all
return the correctly-rounded values. (gcc's compile-time constant fold uses MPFR
and also gives 3 — which is why a C `printf("%.17g", cbrt(27.0))` misleadingly
prints `3` under gcc: that path never calls the runtime function.) The compiler
emitted a plain `call @cbrt`, so results diverged by platform.

A single Newton/Halley refinement of the libm result was tried and rejected: it
merely relocates the ULP error — it fixed `cbrt(27)`/`cbrt(2)` but made
`cbrt(0.001)` wrong (`0.0999…92` instead of `0.1`). Correct rounding needs the
real algorithm, not a one-step polish of a bad seed.

## Decision

Route `Math.cbrt` through `@__kml_cbrt`, the public-domain fdlibm/musl `cbrt`
algorithm (rough bit-hack seed → degree-4 `1/cbrt` polynomial → 23-bit rounding →
one Newton step to 53 bits, correctly rounded to < 0.667 ULP). It is emitted once
on demand via the `ensure*` convention (`ensureCbrt`, guarded by `usedCbrt`) as
self-contained LLVM IR — no libm dependency, so the result is identical on every
platform. `emitMathCbrt` replaces the generic `emitMathUnaryFloat` path for
`cbrt` only; the other unary math builtins still call platform libm (none has
shown a cross-platform divergence).

The `@cbrt` libm declaration is left in place (harmless unused `declare`).

## Consequences

- `Math.cbrt` is deterministic and correctly-rounded on Linux and macOS alike,
  matching V8/Node.
- The failing CI test passes; the class of "libm last-ULP differs by platform"
  bug is removed for `cbrt` specifically. Other libm-backed Math functions remain
  platform-delegated and could in principle show the same divergence — not
  chased here without evidence of an actual failure.

## Verification

In a glibc container matching CI (Debian, clang-16 — a clang new enough for the
compiler's opaque-pointer IR, which the image's default clang-14 rejects):
- The exact failing test `TestE2EMathCbrtExpm1Log1p` now passes.
- A 22-value sweep (including `0.001`, `2`, `123.456`, negatives, `0`, and values
  raw glibc gets wrong) produced output **identical to V8/Node** for every value.
- New regression test `TestE2EMathCbrtCorrectlyRounded` (rounding-sensitive
  values) passes on both macOS and the glibc container. `go build`/`go vet ./...`
  clean. Verified on Apple Silicon (macOS) and Linux (Docker glibc).
