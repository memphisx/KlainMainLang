# TDD-00018: ArrayBuffer / TypedArrays

- **Status**: Implemented — see [ADR-00078](../adr/ADR-00078.md)
- **Date**: 2026-07-29

## Context

`STATUS.md`'s "Web Platform & Node.js APIs backlog" (Medium effort tier) has flagged `ArrayBuffer` + TypedArrays as the item everything else keeps citing as a blocker: it's the prerequisite for actually fixing the `fetch`/`fs` null-byte-truncation bug (currently deferred as "not fixable in isolation" — every string in this compiler is a plain null-terminated C string, so any value with an embedded `\0` reads as shorter than it actually is, with no way to represent raw bytes faithfully instead), for `crypto.getRandomValues`'s documented `number[]`-as-a-stand-in workaround (`ADR-00024`, which explicitly says "a real, documented deviation from the actual API... until ArrayBuffer/TypedArrays exist") to eventually use a real buffer type, and for `TextEncoder`/`TextDecoder` (currently ❌, blocked on `Uint8Array` existing as a real return/input type). Picked up now as the next roadmap item after `URL`/`URLSearchParams` (`ADR-00076`) and the object-literal-coercion bug fix (`ADR-00077`).

This is a new subsystem — a new IR representation — rather than a wrapper over an existing one, so it gets scoped here before implementation, per this project's standing process for anything this size.

Three research passes (via the Explore agent, read-only) established the design space before any of this was written:

1. The existing `number[]` array system (`{ptr, i64}` LLVM aggregate, or `Symbol{Ptr, LenPtr}` allocas for a named variable — see `codegen/llvm/emit_arrays_core.go`) already tracks length purely in **element count**, never byte count; there is no independent "buffer byte size" concept anywhere today. `codegen/llvm/types.go`'s `Align()` already knows the byte width of every numeric IR type this needs (`i8`/`i16`/`i32`/`i64`/`float`/`double`, both signed and unsigned variants, driven by the same JSDoc `@type` machinery `int8`...`uint64`/`float32`/`float64` already use). No `BigInt64Array`/`BigUint64Array` — this compiler has no `bigint` support, already noted as out of scope in `STATUS.md`.
2. There is **no existing precedent anywhere in this codebase** for "one heap allocation, multiple typed views into it" (searched `emit_arrays*.go`, `emit_objects.go`, `emit_collections.go`, all `bitcast` usages in the codebase — every hit is an unrelated scalar `double↔i64` bit-reinterpret for `any`/Map-key boxing, not a memory/pointer view). Every array allocation today is `malloc`'d/`calloc`'d and owned by exactly one `(ptr, len, elemTy)` triple. This is the one genuinely new mechanism this feature needs.
3. `codegen/llvm/emit_exprs_member.go`'s `emitIndexPtr`/`emitIndex` (array indexing + bounds checks) are fully generic over `elemTy.IR`/`elemTy.Align()` and never inspect how the backing memory was allocated. Confirmed directly: a TypedArray sliced out of an `ArrayBuffer` indexes through the *exact same codepath* a plain `number[]` already uses, as long as the `(ptr, elementCount)` contract holds and the element type's natural alignment is respected.
4. `fetch`'s response-body accumulation (`runtime_fetch.go`'s `__kml_curl_write_cb`) and `fs.readFileSync` (`runtime_fs.go`'s `ensureFsReadFile`, via `ftell`) both already compute the real byte count internally before discarding it in favor of a bare null-terminated string — fixing either to use a real buffer is a small, well-understood follow-up once this type exists, not part of this pass.
5. The strongest precedent for *how* to represent a new built-in riding on existing machinery is `URLSearchParams` (`ADR-00076`): it **is** a `Map<string,string>` plus one boolean flag (`IsURLSearchParams`) gating exactly two extra methods, with get/set/has/delete/iteration falling through unchanged to the generic Map dispatch. TypedArrays should do the identical thing against the existing **array** machinery.

## Design

### `ArrayBuffer`

`new ArrayBuffer(byteLength)` is a general expression (works anywhere — as a function argument, a return value, nested — like `Date`/`URL`/`Response`, *not* restricted to a variable-declaration initializer the way `Array`/`Map`/`Set` already are). Representation: `Type{IR: "ptr", IsArrayBuffer: true}` — deliberately not `IsObject`, so it never goes through the generic `FieldIndex`/`Object.keys`/JSON reflection path, the same reasoning `Map`/`Set`'s own internal layout already uses for its hidden fields. The runtime value is a pointer to a 2-word heap struct (`{i64 byteLength, ptr data}`, `calloc`'d so the buffer itself is zero-initialized, matching real `ArrayBuffer`'s zero-fill guarantee); `.byteLength` gets its own dedicated property read in `emitMember`, gated on `IsArrayBuffer` — exactly the pattern `.size` already uses for Map/Set instead of the generic field-index path. The `data` word is internal, read only by TypedArray construction code, never exposed to KML code as a field.

### TypedArrays

One new `Type` flag, `IsTypedArray bool`, set alongside the *existing* `IsArray`/`ElemType` fields (`ty := ArrayOf(elemTy); ty.IsTypedArray = true`) — mirroring `IsURLSearchParams` riding on `IsMap`. `elemTy` is one of the already-existing numeric constants (`TypeI8`/`TypeU8`/`TypeI16`/`TypeU16`/`TypeI32`/`TypeU32`/`TypeF32`/`TypeF64`), selected by a small constructor-name → `Type` lookup table. Covers the 8 core numeric variants: `Int8Array`, `Uint8Array`, `Int16Array`, `Uint16Array`, `Int32Array`, `Uint32Array`, `Float32Array`, `Float64Array`.

**Construction is restricted to a variable-declaration initializer**, matching the existing restriction on `new Array<T>(...)`/`new Map<K,V>()`/`new Set<T>()` (all three already reject general-expression use today with "must be used in a variable declaration" — this is a deliberate consistency choice, not a new limitation being introduced). One new AST node, `NewTypedArrayExpression{ElemKind string; Arg Expression}`, parsed by a single `parseNewTypedArrayBody` shared across all 8 constructor names, handled by a new case in `emitArrayVarDecl`'s switch exactly where `*ast.NewArrayExpression` already lives. Codegen inspects `e.inferExprType(ex.Arg)` to choose one of three construction paths:

- **View** (`argTy.IsArrayBuffer`): no allocation. Builds a `{ptr, i64}` aggregate directly from the buffer's existing data pointer and `byteLength / elemTy.Align()` (element count) — throwing a catchable Error (matching the `Invalid URL`/array-out-of-bounds convention) if `byteLength` isn't evenly divisible by the element size. Writes through this view are visible through the original buffer and any other view over it, since it's the same underlying memory, not a copy.
- **Copy-construct** (`argTy.IsArray` — a `number[]` or another TypedArray): `calloc`s a fresh buffer sized for the source's element count, loop-copying and coercing (`e.coerce(val, elemTy)`) each element — this is the exact same truncation/wraparound path plain assignment already uses, so `new Uint8Array([-1, 300])` correctly becomes `[255, 44]` (mod-256 wraparound) with no new coercion logic. (`Uint8ClampedArray`'s clamp-instead-of-wrap semantics would need a distinct store path here — out of scope, see below.)
- **Own buffer** (anything else, treated as a plain size expression): identical to `NewArrayExpression`'s existing `calloc(n, elemTy.Align())` path, just with `elemTy` fixed by the constructor name instead of a type annotation.

No case is needed in `emitExpr`'s general dispatch for `NewTypedArrayExpression` (consistent with var-decl-only construction); `emit_exprs_vardecl.go`'s untyped-inference switch gets one new case mirroring the existing `NewArrayExpression` case there, so `const v = new Uint8Array(10)` infers its type with no explicit annotation needed.

New methods, `emit_call.go`, an `IsTypedArray`-gated dispatch block placed before the generic array-method chain (mirroring exactly where `IsURLSearchParams`'s block sits before generic Map dispatch):
- `.set(source, offset?)` — copies elements from another TypedArray/`number[]` starting at `offset` (default 0); throws if the copy doesn't fit.
- `.subarray(start?, end?)` — a **view**, not a copy: GEP into the existing data pointer at `start * elemTy.Align()`, reusing `.slice()`'s existing `emitNormalizeSliceIdx` for negative-index/clamping normalization.
- `.byteLength` — `length * elemTy.Align()`, alongside the array machinery's pre-existing `.length`.

Everything else — indexed read/write with bounds checks, `.length`, `.fill`, `.slice` (a real copy, unlike `.subarray()`), `.reverse`, `.at`, `.indexOf`, `.includes`, `.map`, `.filter`, `.reduce`, `.forEach`, `.some`, `.every`, for-of iteration, `.keys()`/`.values()`/`.entries()` — needs **zero new code**: it already dispatches purely on `elemTy` and the `(ptr, len)` pair via `emit_arrays_*.go`'s existing functions and `resolveArrayForHOF`, with no assumption anywhere about how the backing memory was allocated.

### Memory/lifetime

An `ArrayBuffer`/TypedArray is not wired into `Memory.free()` in this pass — it's simply never explicitly freed by user code (the same "a bounded leak is a non-issue for a short-lived program in manual mode" tradeoff already accepted for `new URL(...)`'s libcurl-owned strings); `-mm=gc` reclaims it like everything else. This sidesteps the aliasing-lifetime question (freeing a view out from under its buffer, or the buffer out from under a live view) entirely for now — a genuine open question, deferred until real usage patterns clarify what's actually needed (see Open questions).

### Deliberately out of scope (documented gaps, each a natural separate follow-up)

- `Uint8ClampedArray` — real clamp-on-write semantics need a distinct store path (not just truncation); skipped entirely rather than approximated, stays ❌.
- `DataView` — endianness-explicit arbitrary-offset reads/writes.
- `BigInt64Array`/`BigUint64Array` — needs `bigint` support this compiler doesn't have (already noted elsewhere in `STATUS.md`).
- Actually fixing `fetch`/`fs`'s null-byte truncation, migrating `crypto.getRandomValues` off its `number[]` workaround, and `TextEncoder`/`TextDecoder` — each unlocked by this work, none bundled into it.
- `.buffer` property on a TypedArray (would require every TypedArray, including the "own buffer" construction form, to carry a back-reference to a real `ArrayBuffer` object — a shape change from the plain `{ptr,i64}` array representation this design deliberately keeps).
- The 3-argument `new XArray(buffer, byteOffset, length)` sub-range view form — only whole-buffer views at offset 0 are supported, avoiding non-zero-offset alignment questions entirely (a `calloc`'d buffer's start is always naturally aligned for any element width; a sub-range starting at an arbitrary byte offset might not be).

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Numeric IR types for every TypedArray variant (`i8`/`i16`/`i32`/`i64`/`float`/`double`, signed+unsigned) | ✅ already done | `codegen/llvm/types.go`'s `TypeI8`...`TypeF64` constants, already used by the JSDoc `@type` system |
| `Align()`/byte-width-by-`IR` | ✅ already done | Pure function of `IR`, no array/TypedArray-specific field needed |
| Generic array indexing/HOF/mutation machinery, agnostic to allocation origin | ✅ already done, confirmed directly | `emit_arrays_*.go` + `resolveArrayForHOF`/`emitIndexPtr`/`emitIndex` — verified they only ever touch `(ptr, len, elemTy)`, never how `ptr` was allocated |
| A proven "existing machinery + one gating flag" pattern for a new built-in | ✅ already proven | `IsURLSearchParams` riding on `IsMap` (`ADR-00076`) |
| A proven "dedicated property read outside generic field reflection" pattern | ✅ already proven | `.size` for Map/Set |
| `e.coerce`'s int truncation/wraparound semantics | ✅ already correct | Confirmed: `trunc i64 to i8` on a negative or out-of-range input already gives the correct mod-256-style wraparound real JS non-clamped `TypedArray` writes need, with no new coercion code |
| "One allocation, multiple typed views" mechanism | ❌ not designed until this document | The one genuinely new piece of plumbing this feature needs |
| Var-decl-only construction restriction, precedent | ✅ already established | `new Array<T>(...)`/`new Map<K,V>()`/`new Set<T>()` already work this way; this design follows the same restriction rather than inventing a new rule |

## Open questions

- Whether `Memory.free()` should eventually accept `ArrayBuffer`/TypedArrays, and if so, how to handle a view outliving (or outlived by) its buffer — deliberately deferred rather than guessed at in this pass.
- Whether the 3-argument sub-range view form (`new XArray(buffer, byteOffset, length)`) is worth adding later, and if so, whether non-natural-alignment offsets need an unaligned-load/store path or should simply be rejected at construction time.
- Whether `Uint8ClampedArray` is worth adding later with real clamp semantics, given how narrow its real-world usage is compared to the other 8 variants.
