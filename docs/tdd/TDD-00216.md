# TDD-00216: Background AbortSignal.timeout dispatch

- **Status**: Implemented

- **Date**: 2026-09-16

## Context

`AbortSignal.timeout(ms)` (TDD-00081 Stage 3c, ADR-00238) only ever latches its
`aborted` flag *lazily*: `__kml_signal_aborted` sets the flag when something
(the fetch await loop, the event-loop resume scan) happens to check it. It never
dispatches the signal's `"abort"` event, so `addEventListener('abort', …)`
listeners and the `onabort` property (ADR-00978) never fire at the deadline, and
a bare `signal.aborted` read does not reflect the timeout in the background. This
was a standing caveat on the AbortController/AbortSignal status row. Caveats are
bugs; this closes it.

## Design

**Do not schedule a real timer.** A real `setTimeout`-style entry keeps the event
loop / drain alive until it fires, which would turn the common
`fetch(url, { signal: AbortSignal.timeout(30000) })` that completes in 100 ms into
a 30 s hang. Node avoids this by *unref-ing* the timeout timer (it never keeps the
loop alive on its own). We get the same "unref by construction" by keeping abort
timeouts in a **separate registry** that the loops *fire from* but never *stay
alive for*.

Components:

1. **Registry** (`emit_abort.go`, thread-local like the timer queue):
   `@__kml_abort_to_data/len/cap` — a growable array of `{ i64 deadlineNs, ptr sig }`.
   - `@__kml_abort_to_register(i64 deadlineNs, ptr sig)` — append (called from
     `emitAbortSignalTimeout`).
   - `@__kml_abort_to_soonest() -> i64` — the soonest unfired deadline, or 0 when
     none. Loops fold this into their sleep/`select()` target (treating 0 as "no
     constraint"), so they wake by the deadline.
   - `@__kml_abort_to_fire_due()` — fire every entry whose deadline ≤ now, marking
     each fired (`deadlineNs = -1`).

2. **One shared dispatcher** `@__kml_abort_timeout_fire(ptr %sig)`, emitted once at
   compile time (so its body can use the compile-time emitters `emitDispatchToMap`
   / `emitFireOnabort` against the `%sig` parameter — no per-signal synthesis, no
   runtime listener-map/closure/reason helpers). Body: set `aborted = 1`; build a
   `TimeoutError` DOMException reason (`buildErrorObj`, compile-time IR) and store
   it; load the signal's `listeners` map and `emitDispatchToMap`; `emitFireOnabort`.
   `__kml_abort_to_fire_due` calls this for each due signal.

3. **Loop integration** at every sleep/wait point (gated on `e.usedAbortTimeout`):
   - **`__kml_event_loop_run`**: fold `__kml_abort_to_soonest` into the `select()`
     extra-deadline (`%cmdlabs`), and call `__kml_abort_to_fire_due` once per
     iteration.
   - **`__kml_timer_drain`** and **`__kml_timer_fire_next`** (pure-timer / await
     paths): fold the soonest abort deadline into the sleep target (kept separate
     from the timer's own deadline), and after waking call `__kml_abort_to_fire_due`
     then re-check whether the chosen timer is actually due — if we woke only for an
     abort, loop back rather than firing the timer early.

   The registry is never part of any keep-alive decision, so a lone
   `AbortSignal.timeout` with no other pending work exits without firing (Node
   unref parity), and an early-completing fetch never hangs.

The lazy `deadlineNs`/`__kml_signal_aborted` latch stays as-is (fetch fold,
`AbortSignal.any` snapshot still use it); the registry is additive and is the sole
listener dispatcher. Firing is idempotent with the lazy latch (both only ever set
`aborted`; only the dispatcher dispatches, and it fires each entry once).

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `onabort` field + `emitFireOnabort` | Built | ADR-00978 |
| `emitDispatchToMap` over a listener map | Built | emit_eventtarget.go |
| `buildErrorObj` / TimeoutError DOMException | Built | emit_exceptions.go; fetch already builds the same reason |
| Timer sleep/`select()` fold points | Built | emit_timers.go, runtime_http.go — need additive fold+fire |
| Growable thread-local array pattern | Built | mirror `__kml_timer_schedule` |

## Open questions

- Firing order when a fetch's own deadline fold and the registry fire at the same
  deadline: both wake in the same iteration; the dispatcher runs listeners, fetch
  still throws its own `TimeoutError`. Resolved: acceptable — no double dispatch
  (registry is the sole dispatcher), reason ends up `TimeoutError` either way.
