# ADR-00239: Fold fetch AbortSignal.timeout deadlines into the event-loop select()

- **Relations**: `Implements TDD-00081` (Stage 3c); `Extends ADR-00238`
- **Date**: 2026-08-19

## Context

Stage 3c ([ADR-00238](ADR-00238.md)) made `AbortSignal.timeout` cancel a fetch,
but left one gap: a fetch awaited on a *connection fiber* (inside an `http.listen`
handler) fires its timeout only when the event loop next wakes. On an otherwise-
idle loop, `select()` blocks with a null timeout (`notimeoutpath`) and would sail
past the deadline. This folds the deadline into `select()` so it wakes on time.

## Decision

Before the event loop's `select()`-timeout decision (`__kml_event_loop_run`,
runtime_http.go), add a scan of the connection array: for every parked fetch
fiber (`pendingFetch != null`) whose signal carries a non-zero `deadlineNs`, fold
the soonest deadline into `%bestfire` and set a `%havefetchdl` flag — exactly the
compare-and-store shape the EventSource-reconnect deadline already uses. The
`%usetimer` decision then includes `%havefetchdl`, so a program with a live
fetch-deadline but no JS timer takes the bounded `timeoutpath` instead of the
infinite `notimeoutpath`, and `select()` wakes at (or, for an already-past
deadline, immediately before) the deadline. The resume scan (which already
consults `__kml_signal_aborted`) then aborts the timed-out fetch and the resumed
fiber throws `AbortError`.

## Implementation notes

Two entry-block allocas (`%fdsi` index, `%havefetchdl` flag) and a self-contained
`fdfoldloop`/`fdfolddone` block set spliced ahead of the `%usetimer` computation.
The deadline is read as field 3 of the `{ i1, ptr, ptr, i64 }` `AbortSignal`
layout, and the pending's signal as field 5 of the extended pending struct — the
same offsets `__kml_signal_aborted` and `__kml_await_fetch` use. Monotonic-ns
throughout (`__kml_monotonic_ns`, shared with the timer runtime), so the fold
composes with existing timer/EventSource deadlines via the same `%bestfire` min.

## Verification

End-to-end: an `http.listen` handler that awaits
`fetch("http://10.255.255.1/", { signal: AbortSignal.timeout(400) })` (a non-
routable address whose connect hangs) — a client request returned
`handler caught: AbortError` in **~429 ms**, i.e. the timeout fired at the
deadline on an otherwise-idle loop, which it could not before this fold. The
event-loop consumers (HTTP/WebSocket/EventSource/fetch/Promise/timer/abort) all
still pass, and the busy-spin (top-level `await`) timeout is unaffected.
`go build`/`go vet ./...` clean on Apple Silicon (macOS).
