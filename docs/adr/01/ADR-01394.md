# ADR-01394: JS timers on uv_timer_t

- **Relations**: Implements TDD-00244; Extends ADR-01393
- **Date**: 2026-10-05

## Context

[TDD-00244](../../tdd/TDD-00244.md) Stage 1 moves timers to `uv_timer_t`.
`setTimeout`/`setInterval` entries sat in a per-thread queue that the loop
scanned each pass. Finding the soonest one, running the due ones, and
deciding whether a ref'd one held the loop each took a linear pass. A
dynamic-import island read the queue through IR text to fold its earliest
deadline into its wait.

## Decision

- **On POSIX each pending entry is a `uv_timer_t`** on the thread's loop,
  armed by schedule, `refresh()` and an interval's next round, and closed
  when the entry is cleared or done. `unref()`/`ref()` unreference the
  handle, so the loop's liveness (`uv_loop_alive`) counts ref'd timers.
  libuv fires them inside the wait, in due order (creation order among
  equals), with microtasks drained after each callback.
- **A delay counts from the call**, as Node's timers start from
  `GetNow()`, which refreshes the loop's clock. libuv counts whole
  milliseconds, so a timer's libuv deadline is its due time rounded up to
  the next millisecond: it never fires before its delay, and timers keep
  their due order (creation order among equals). A delay below 1 ms runs
  as 1 ms, as in Node, which also keeps a timer created inside the timers
  phase out of that phase.
  - A first version counted from libuv's cached loop time. That time can
    trail the call by part of a millisecond, so a timer could fire just
    before its delay (`TestE2ELoopTimerNeverEarly`, under test-par).
- The queue stays as the id index and for the drains that fire timers
  outside the loop: a lightweight await on a connection fiber
  (`__kml_timer_fire_next`) and the webview tick. These fire an entry
  directly and re-arm or close its handle.
- An island's deadline is `__kml_timer_next_deadline_ns` in `timers.c`;
  the IR-text scan of the queue is deleted.
- Windows keeps the loop's scan until Stage 6.

## Verification

- Mac (M4): a timer-ordering probe matches Node (equal delays, 0 → 1 ms,
  microtasks after each callback, `unref()`, intervals); the timer,
  event-loop, Worker and dynamic-import tests; codegen unit tests.
- Linux x86-64 (Ubuntu 24.04 container), with the clock as decided: the
  loop and timer tests pass 6 runs under 14 busy CPU loops; test-par
  passes (14 shards, 3922 tests); examples 393/393; Test262 js 10506
  (unchanged; strict 8498 on the first version), no invalid IR.
- `TestE2ETimersModule` raced a 5 ms timeout against two rounds of a 1 ms
  interval, which CPU starvation reorders in Node too. Its timeout is
  50 ms, and the expected order is Node's.
