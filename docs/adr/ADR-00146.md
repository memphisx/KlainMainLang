# ADR-00146: klmpm Stage 1 — compiler-side `klain_modules` resolution

- **Relations**: Implements [TDD-00054](../tdd/TDD-00054.md) (Stage 1 only)
- **Date**: 2026-08-10

## Context

[TDD-00054](../tdd/TDD-00054.md) designed klmpm, a klainmain-native package manager, deliberately staged so the compiler-side resolution piece is buildable and testable independent of klmpm-the-tool ever existing — a hand-constructed `klain_modules/<name>/klain.json` + source tree exercises the exact same resolution path a real klmpm-fetched package would. This ADR implements exactly that stage: nothing about fetching, versioning, the lockfile, or the CLI tool itself.

## Decision

`resolver.go`'s bare-specifier rejection point (`resolveImportPath`) now takes a `klainModulesDir string` (computed once per `ResolveProgramWithOptions` call, via a new `findKlainModulesDir`, walking upward from the *entry file's* own directory — not each importing file's own directory, the deliberate departure from Node's per-importer walk the TDD called for, so every file in the whole program resolves a given package name against the same single directory). "" means no `klain_modules` directory exists anywhere above the entry file, in which case a bare specifier is rejected exactly as it always has been — fully backward compatible, zero cost for a project not using klmpm.

When a bare specifier is encountered and `klainModulesDir != ""`, `resolveKlmpmPackage` looks for `klainModulesDir/<name>/klain.json`, reads only its `"main"` field (a new `klmpmManifest` struct, `encoding/json`), and resolves that field the same way a relative import resolves — `.ts` auto-appended if omitted, confirmed to exist. Per the TDD's design, **the compiler never reads a project's own root `klain.json`** (its `"dependencies"` list is klmpm's own bookkeeping for what to fetch, not something the resolver needs) — only a package directory's presence and its own manifest's `"main"` field.

Precedence, matching the TDD exactly: a real built-in module (`fs`/`path`/etc.) is checked, and always wins, before any `klain_modules` lookup is even attempted — this needed no new code, since the virtual-builtin check already happens at every call site before `resolveImportPath` is ever invoked (TDD-00049's existing dispatch), so a `klain_modules/fs/` decoy package is structurally unreachable regardless.

`resolveTsFile` factors out the "join, auto-append `.ts`, confirm exists" mechanics shared by both a relative import and a klmpm package's `"main"` field resolution — previously inlined once inside `resolveImportPath`, now reused by both `resolveImportPath`'s relative branch and `resolveKlmpmPackage`.

## Implementation notes

- `resolver/resolver.go`: `resolveImportPath` gained a third parameter (`klainModulesDir`), all 4 existing call sites updated; new `resolveTsFile` (shared file-resolution mechanics, returns `(abs string, found bool, err error)` rather than overloading `error` to carry a non-error path value); new `resolveKlmpmPackage`; new `findKlainModulesDir`; new `klmpmManifest` struct. `ResolveProgramWithOptions` computes `klainModulesDir` once, right after resolving `entryAbs`. Package doc comment updated to describe the new resolution path.
- No changes anywhere past the initial specifier-to-path lookup — a resolved package file is just another file to the existing DFS (`visit`), same as [TDD-00041](../tdd/TDD-00041.md)/[TDD-00051](../tdd/TDD-00051.md)/[TDD-00052](../tdd/TDD-00052.md) already apply uniformly regardless of a file's origin.

## Side effects discovered

None.

## Verification

- `go build ./...`, `go vet ./...`, `go test ./...` all clean, full pre-existing suite unmodified.
- 12 new tests in `tests/klain_modules_test.go`: basic bare-package resolution, `"main"` without a `.ts` extension, a package's own relative imports still working, one package bare-importing another (transitive), the deliberate "anchored at entry, not per-importer" design choice locked in via a decoy nested `klain_modules` that must be ignored, built-in precedence over a same-named decoy package, and five distinct rejection cases (missing package, missing manifest, manifest missing `"main"`, `"main"` pointing nowhere, invalid JSON) plus a no-`klain_modules`-anywhere control case confirming unchanged behavior.
- `examples/imports/klain_modules_package.ts` + a hand-built `examples/imports/klain_modules/greeter/` package (new) — manually run standalone (`hello world from a klain_modules package`, matching the comments) and via `make examples`: 106/106 passed (104 from [ADR-00145](ADR-00145.md) plus these 2 new files, including the package's own `index.ts` compiling standalone as its own entry point too).
