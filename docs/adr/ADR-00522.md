# ADR-00522: `klain:tui` List viewport — scroll-to-selected + scrollbar

- **Relations**: Extends ADR-00519; Implements TDD-00150 (Stage 1 polish)
- **Date**: 2026-08-30

## Context

The Stage 1 `List` (ADR-00519) painted every item at its natural height with no notion of a viewport, so a list with more items than its box could show was the standing caveat on the `List` status row. Worse, because Yoga's default `flexShrink` is 0 (unlike the web default of 1), a `List` measured at its full item-count height did not yield to a fixed-height parent — it overflowed the box entirely, painting items past the container's bottom border.

## Investigation

`kmltui_measure` (`codegen/llvm/tui.go`) returns a `List`'s natural height as its item count. In `paint_node`'s `K_LIST` case the loop used the row index directly as the item index and stopped at `min(nitems, h)`, always painting from item 0. A repro — 12 items in a `Box({ border:'single', height:5 })` — showed all 12 items rendered, the last nine spilling below the box, confirming both the overflow (no shrink) and the missing viewport.

## Decision

Two coupled changes, both confined to the embedded C runtime:

- **Yield to a bounded container**: `__kml_tui_node` sets `YGNodeStyleSetFlexShrink(yg, 1)` for `K_LIST` nodes, so a tall list inside a fixed-height box shrinks to that box's content height instead of overflowing. An explicit `flexShrink` prop still overrides it, and in an auto-height container (no overflow) shrink is a no-op, so natural sizing is unchanged.
- **Scroll + scrollbar**: the `K_LIST` paint case computes a scroll offset each frame from the selected index (`off = selected - h/2`, clamped to `[0, n-h]`), paints only the visible window, and — when `n > h` — draws a 1-column scrollbar on the right edge (`█` thumb sized `h*h/n`, `░` track), reserving that column so item text paints into `w-1`. The offset is derived, not stored, so it fits the immediate-mode model (the tree is rebuilt every frame).

Rejected: a retained per-list scroll offset (would need state to survive the per-frame tree rebuild, which the model deliberately avoids) and up/down arrow indicators overlaid on item text (intrusive; a dedicated scrollbar column is cleaner and shows absolute position).

## Implementation notes

The selected-row highlight fill and item text both clamp to the content width `w-1` when the scrollbar is present, so the bar is never overwritten. `selected == -1` (no selection) scrolls to the top (`off = 0`).

## Side effects discovered

None beyond the intended behaviour change. `List` now paints zero-caveat, which promotes its status row into Strict coverage for the Terminal-UI area.

## Verification

- New E2E test `TestE2ETuiListViewport` (`tests/tui_test.go`): 12 items in a height-5 box with item 8 selected — output contains `item-8`, does not contain the scrolled-off `item-0`, and contains a scrollbar thumb (`█`).
- Existing `TestE2ETui*` tests still pass; all four `examples/tui/*.ts` still compile.
- Manual repro on macOS (Apple Silicon): the 12-item list shows a 3-row window around the selection, clipped inside the box, with the thumb tracking position.
