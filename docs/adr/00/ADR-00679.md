# ADR-00679: AsyncLocalStorage — timer-callback context propagation

- **Relations**: Extends ADR-00678 (AsyncLocalStorage Stages 1–2); Implements
  TDD-00168 Stage 3; builds on the timer runtime (`emit_timers.go`) and the
  whole-program pre-scan pattern of ADR (programUsesHTTPUpgrade)
- **Date**: 2026-09-03

## Context

ADR-00678 delivered AsyncLocalStorage with context propagation across `await`,
but a `setTimeout`/`setInterval`/`setImmediate` callback scheduled inside
`als.run(...)` saw no store when it fired — the store was already restored by
the time the deferred callback ran, and the callback fires from the top-level
event loop (no task), so it read the empty root context. `setTimeout` inside a
request scope is the single most common ALS idiom after `await`, so this closes
the gap.

## Investigation

The timer entry struct `{ i64 id, i64 fireAtNs, i64 intervalMs, ptr closureHdr }`
is a spelled-out literal in ~20 sites in `emit_timers.go` with no named constant,
and the callback fires at three places via `call void (ptr) %fp(ptr %ep)`.
Widening the entry to carry a captured context would touch all of those. A
cleaner, lower-risk seam is the **callback closure itself**: capture the context
at schedule time and wrap the closure so it installs/restores that context around
its own invocation — leaving the timer runtime's struct and fire logic
completely untouched.

## Decision

At each `setTimeout`/`setInterval`/`setImmediate` emit (in the shared
`timerCallbackPtr`), when the program uses AsyncLocalStorage, wrap the user's
`{fn, env}` closure in a **context-binding trampoline**:

- capture the current context head now — `%cc = call @__kml_als_ctx_get()`;
- build `env2 = { ptr origClosure, ptr %cc }`;
- return a fresh `{ @__kml_als_timer_tramp, env2 }` header, scheduled in place of
  the original.

`@__kml_als_timer_tramp(env2)` (runtime_asynchooks.go) saves the current context,
installs `%cc`, invokes the original closure, and restores — so the callback runs
with exactly the context that was live at its schedule point. Because timers fire
from the top-level loop (no running task), install/restore operate on the root
context, which is what a top-level fire reads. `setInterval` reuses the same
wrapper for every fire, so each repeat keeps the context.

**Gating.** A whole-program pre-scan `programUsesAsyncLocalStorage(prog)` (run in
EmitProgram before Pass 2, mirroring `programUsesHTTPUpgrade`) sets
`e.programUsesALS`. The wrap only happens when true, so a program with no
AsyncLocalStorage gets byte-for-byte unchanged timer code — no wrapper alloc, no
context machinery. The pre-scan is needed because a `setTimeout` inside a
function body is emitted (Pass 2) before the top-level `new AsyncLocalStorage`
(Pass 3), so the emit-time `usedAsyncLocalStorage` guard is not yet set there.

The context accessors were refactored into `ensureAsyncCtxAccessors`
(get/set + the trampoline), shared by the full ALS runtime and the timer-wrap
path so a timer-only-plus-ALS program pulls in just the accessors.

## Implementation notes

- `wrapTimerClosureWithAsyncCtx` and the pre-scan walker
  (`walk{Stmt,Expr,Block}ForALS`, a focused copy of the upgrade walker's node
  coverage) live in `emit_asynchooks.go`; the trampoline in
  `runtime_asynchooks.go`; the one wrap call in `timerCallbackPtr`.
- The wrapper is transparent to `__kml_timer_schedule` — it still receives a
  plain `{fn, env}` header, so no timer-runtime change was needed.

## Side effects discovered

None. `.then`/reaction and EventEmitter-listener context propagation remain the
next fidelity step (TDD-00168 Stage 5); they are separate dispatch paths from
timers and unaffected.

## Verification

Mac. New E2E test `TestE2EAsyncLocalStorageTimerPropagation` (a `setTimeout`
inside `run` sees the store, context empty again afterward). Manual: `setInterval`
inside `run` keeps context across all three fires; a plain timer program with no
ALS is byte-for-byte unchanged and still passes. Full timer + async + ALS
regression green. `go build`/`go vet` clean.
