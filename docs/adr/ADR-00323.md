# ADR-00323: Interactive `readline` — createInterface, 'line', question, close

- **Relations**: Extends ADR-00322 (child_process event-loop fd integration)
- **Date**: 2026-08-23

## Context

The only stdin facility was the blocking `process.readLineSync()` (one line at
a time, halting the program). Node's `readline` module — `createInterface`,
the `'line'` event, `question(query, cb)`, `close()` / `'close'` — was ❌ on
[PROCESS-CLI.md](../status/PROCESS-CLI.md). It is the natural interactive-CLI
primitive (prompts, menus, REPL-ish input), and the last of the two
EventEmitter-backed process items in the backlog after async `child_process`.

The prerequisite it shares with `child_process` is non-blocking stdin folded
into the event loop — which ADR-00322 had just built for a spawned child's
pipes, making `readline` a direct re-application (now for fd 0).

## Investigation

- `process.readLineSync()` (`runtime_process.go`) is a blocking `getline()` on
  the C stdin global — no event-loop integration, no incremental reading.
- ADR-00322 established the exact pattern to reuse: make a read fd non-blocking
  (`fcntl` O_NONBLOCK via `httpNonblockFlag()`), and register it into
  `@__kml_event_loop_run` through three hooks — `*_fdset_add`, `*_dispatch`,
  `*_keepalive` — with no-op stubs (`emitLoopTaskStubs`) when unused and a
  `used*Runtime` flag joining the `useFullLoop` driver-selection set. Listeners
  are stored closure headers the runtime dispatch invokes through the closure
  ABI. `ensureWorkerFdSetbit` builds the `fd_set` bit.

So `readline` is "the child_process fd-integration pattern applied to stdin
(fd 0)" plus line-buffering and the one-shot `question` callback — an ADR, not
a TDD.

## Decision

- **Runtime** (`runtime_readline.go`): a `%kml.rl` handle (line listener, close
  listener, one-shot question callback, closed flag, a growable line buffer),
  stored in a single global `@__kml_rl_active` (one interface at a time — one
  stdin). `@__kml_rl_create` sets fd 0 non-blocking and records the handle.
  `@__kml_rl_dispatch` reads whatever stdin has, appends to the buffer, and
  emits one line per newline (CR stripped, NUL-terminated copy); a pending
  `question` callback consumes the next line one-shot instead of firing
  `'line'`; on EOF it flushes an unterminated final line, then fires `'close'`.
  `@__kml_rl_question` writes the prompt to stdout and arms the callback;
  `@__kml_rl_close` fires `'close'` immediately. The three loop hooks
  (`fdset_add`/`dispatch`/`keepalive`) wire in beside the child_process ones,
  with stubs when `readline` is unused (`usedReadlineRuntime`).
- **Codegen** (`emit_readline.go`, `ReadlineType` in types.go):
  `readline.createInterface(options?)` returns a `ReadlineType` handle — the
  options object is accepted syntactically but not evaluated (input is always
  stdin, output always stdout). `rl.on('line'|'close', cb)`, `rl.question`,
  `rl.close()` dispatch on the handle type; listeners are arrow/function-
  expression literals only (the Worker/child_process posture).
- **Resolver**: `'readline'` marker + `{createInterface}` member.

## Implementation notes

- `__kml_rl_emit` early-returns when the interface is already closed, so an
  `rl.close()` called from inside a `'line'` callback stops further `'line'`
  events even for input already buffered in the same dispatch batch.
- With piped (non-TTY) stdin the whole input arrives at once, so a chain of
  `question` prompts is written before their answers interleave — an artifact
  of non-interactive feeding, not of a real terminal.

## Side effects discovered

None. The `@write`/`@fcntl` shared-decl guards added in ADR-00322 already cover
this runtime's use of both.

## Verification

- `go build` / `go vet` clean.
- New `tests/readline_test.go` (7 cases): multi-line `'line'` events, `'close'`
  on EOF, `question` (nested/chained), unterminated-final-line flush, CR
  stripping, explicit `close()` mid-batch, and missing-import rejection. All
  pass, fed through the binary's real stdin.
- `examples/readline/readline.ts` builds and runs (Mac / Apple Silicon M4).

### Known limitations (tracked on docs/status/PROCESS-CLI.md)

- Callbacks fire synchronously from the dispatch, not via a microtask.
- One listener per event, arrow/function-expression literal only.
- The `createInterface` options object is ignored (always stdin/stdout); one
  active interface at a time; no history/editing, `SIGINT`, or completer.
