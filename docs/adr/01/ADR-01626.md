# ADR-01626: ASan/UBSan on Windows through MSYS2's CLANG64 clang; the stack guard's handler is not instrumented

- **Relations**: Extends ADR-01605, TDD-00177, TDD-00249
- **Date**: 2026-10-14

## Context

The sanitizer tests (`buildBinaryASan`, the array-reference free policy)
skipped on Windows: the toolchain, MSYS2's UCRT64 clang, has no ASan/UBSan
runtime for the mingw target.

## Investigation

- UCRT64's `compiler-rt` package carries builtins, profile and fuzzer
  runtimes but no sanitizer one. UBSan's trap mode links without a runtime
  (it stops the program, with no report); the minimal and full UBSan
  runtimes and ASan do not link.
- MSYS2's CLANG64 environment ships the same LLVM release (22.1.7) with
  `libclang_rt.asan_dynamic-x86_64.dll` and the UBSan runtimes, on the same
  UCRT C runtime. Its clang, given the compiler's own `--target`/`--sysroot`
  (the UCRT64 tree), links the UCRT64 libraries the program uses and takes
  only the sanitizer runtime from its own tree. Its default unwinder,
  libunwind, is not in the UCRT64 tree; libgcc's, which UCRT64 code uses,
  is. The ASan DLL imports `libc++.dll`, nothing else outside the system.
- With that, every sanitizer test passed but `TestE2EZlibPortHandlesASan`,
  which died with an access violation and no report; any callback run on
  libuv's thread pool did (`fs.readFile`). Under gdb, passing first-chance
  faults through: the stack guard's vectored exception handler (ADR-01605)
  faulted on its first line, over and over. The runtime's C files are
  compiled with the caller's flags, so the handler was instrumented; ASan on
  Windows commits shadow memory on first touch by catching the access fault,
  the handler sees every exception first (it is registered first), and its
  instrumented read of the exception record checked shadow not yet
  committed.

## Decision

- `llvm.SanitizerClang` names the clang a sanitizer build runs, extra
  arguments and the runtime files it needs beside the program: the host's
  clang elsewhere; on Windows CLANG64's, with `--unwindlib=libgcc`, the ASan
  DLL and `libc++.dll`. The test helpers run it (`clangSanitized`) and skip
  only when it is not installed (`requireSanitizers`).
- `sg_handler` carries `no_sanitize("address", "undefined")`: code that runs
  inside exception dispatch must not touch instrumented memory.
- `TestSanitizersReport` builds a seeded heap overflow and signed overflow
  through the same path and requires both reports, so a clean sanitizer
  test cannot be a silent sanitizer.

## Side effects discovered

None.

## Verification

Windows 11 (this machine), with `mingw-w64-clang-x86_64-clang`,
`-compiler-rt` and `-lld` installed: `TestSanitizersReport`, all six ASan
tests, the stack-overflow tests.
