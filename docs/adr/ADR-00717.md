# ADR-00717: x86-64 conservative-scan pinning in the gc-mode collection tests

- **Relations**: Extends ADR-00701 (FinalizationRegistry), TDD-00112 (weak collections)
- **Date**: 2026-09-05

## Context

The first CI run containing `TestE2EFinRegGCModeCollectedFires` (added with
the FinalizationRegistry work) failed on the x86-64 Linux runner: the
orphaned referent was never collected (`deref null: false`, no cleanup
callback), while macOS/M4 and arm64 Linux pass. The test asserts the
gc-mode death-signal path end to end: an object created in a helper,
registered, orphaned, then `gc(); gc()` — expecting the WeakRef to go null
and the callback to fire.

## Investigation

All under Docker (arm64 native + `--platform linux/amd64` emulation,
Debian trixie, libgc 8.2.8), reproducing the CI environment:

- **Deterministic, not flaky**: 10/10 failures on emulated amd64; 10/10
  passes on arm64 and macOS. Emulation matches the real runner's result.
- The weak-only sibling (`TestE2EGCModeWeakCollected`) passes on amd64 —
  but only incidentally: a *standalone* weak-only orphan with no
  subsequent calls fails on amd64 too. The registry is not the culprit
  (its cell already stores a null target under gc, ADR-00701).
- A pure-C Boehm repro (GC_malloc referent, GC_malloc_atomic link word,
  `GC_general_register_disappearing_link`, two `GC_gcollect`s) collects
  correctly on amd64 — libgc and the runtime design are sound.
- Optimizer matrix on the same emitted IR: `-O0` collects; `-O1`/`-O2`
  pin; `-O2 -fno-inline` still pins; an interposed stack-clobbering
  recursive call still pins; allocation noise between collections still
  pins. So the pin is a stale copy of the referent pointer in a stack
  slot of the *live* caller frame (an `-O2` spill/temp), which the
  conservative scan legitimately finds — not registers, not inlining
  alone, not dead-frame residue.
- 50 orphans created in a loop: 49–50 of 50 collect on amd64 — the same
  call path re-executed overwrites the previous iteration's spill slots,
  leaving at most the last iteration pinned.

## Decision

Reshape the test to the loop form its own investigation proved out: the
watched orphan is iteration 0 of a small decoy loop through the same
factory; only iteration 0 is registered and asserted on, so the decoys
scrub the poisoned slots and at most the (unasserted) last decoy stays
pinned. Verified 5/5 on emulated linux/amd64, arm64 Linux, and macOS/M4.

No product change: Boehm makes no promptness guarantee for conservative
collection, and the pinned-referent behavior is inherent to `-O2` code on
x86-64. It is now disclosed as a gc-mode status caveat instead — a
straight-line-created, immediately-orphaned referent may survive
collection indefinitely on x86-64 builds; referents that churn through
reused code paths collect normally (which is what real workloads do —
the RSS-bounded gc churn test passes on the same runner).

## Implementation notes

- tests/finalization_test.go — the reshaped source and the findings in
  brief, so the next platform surprise starts from evidence.
- Machine claims: amd64 behavior verified via Docker `--platform
  linux/amd64` emulation on the Mac (matching the real CI runner's
  failure signature exactly); arm64 Linux via native Docker; macOS
  natively.

## Side effects discovered

- `buildBinaryAuto` (tests/memory_auto_test.go) lacked the JSON
  parse-tree / dynamic-JSON C backends in its clang chain — any auto-mode
  test using JSON failed to link. Fixed alongside ADR-00716's tests.
