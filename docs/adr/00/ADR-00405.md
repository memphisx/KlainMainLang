# ADR-00405: Async event-loop delivery for the `http` client (TDD-00138 Stage 2)

- **Relations**: Implements TDD-00138; Extends ADR-00404 (Stage 1), ADR-00050 (fetch/event loop)
- **Date**: 2026-08-27

## Context

Stage 1's `http.get` (ADR-00404) **blocked** on the libcurl transfer, so calling
this program's own in-process `http.listen` server deadlocked the single event
loop (the client starved the server on the same thread). That is the shape most
of the 117 `http.get`/`request` corpus files use, so it had to be fixed.

## Decision — a completion-reaction fired by the event loop

Instead of blocking, `http.get` registers a **completion reaction** and returns:

- A process-wide registry of `{ pending, closure }` pairs
  (`__kml_httpc_register`). The closure is a per-site thunk whose env captures
  `{ userCb, pending }`.
- The event loop, which already pumps every fetch transfer unconditionally
  (`curl_multi_perform` each iteration), calls **`__kml_httpc_fire_ready()`**
  right after `__kml_curl_drain_messages()` — one added line. It fires each
  reaction whose `pending->done` flag is set (field index 2), then clears the
  slot so it fires once.
- The thunk reads status/body off the now-done pending, builds the
  `IncomingMessage`, invokes `userCb(res)` (which registers `res.on('data'|
  'end')`), then delivers the body chunk + `end`.

At the call site, `http.get` branches on `@__kml_listen_fd`: if a listener is
registered the running loop will drive it, so it **returns immediately**;
otherwise (no loop) it **busy-drives** (`__kml_httpc_drive` — pump curl + drain +
fire until the pending is done), preserving the top-level/external-server case.

## Why this is low-risk to the shared loop

The only event-loop change is the single additive `__kml_httpc_fire_ready()`
call — a no-op when the registry is empty (every non-http-client program). The
registry and drive helpers are otherwise isolated. Verified: the full
http.listen / fetch / await / timers / async / net / promise suites pass
unchanged.

## Consequences

An in-process `createServer(...).listen(0, () => http.get(...))` round-trip works
byte-identical to Node (`pong`, status 200), and the external-server case
(no loop, busy-drive) still works. `http.get` returns `void` in V1 (no
`ClientRequest`); request bodies (`req.write`) and `res.headers` are follow-ons.
The remaining gate for the corpus files is the bare `const server =
http.createServer()` server form (a separate server gap).
