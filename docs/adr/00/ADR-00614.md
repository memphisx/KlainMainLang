# ADR-00614: Close the generator iterator on `return`/labeled-exit from a `for…of` body

- **Relations**: Extends [ADR-00613](ADR-00613.md) (iterator-close on `break`); builds on the pending-`finally` mechanism ([ADR-00191](ADR-00191.md))
- **Date**: 2026-09-01

## Context

[ADR-00613](ADR-00613.md) closed the generator iterator when a `for…of` loop ends
by `break` or normal completion (via the loop-exit label). But a `return` from
inside the loop body — or a labeled `break`/`continue` to an *outer* loop — exits
through the function's own return / control-flow path, not the loop-exit label,
so the generator was left suspended and its `finally` never ran on that path.

## Decision

Register a synthetic **iterator-close `finally`** on the shared `pendingFinallys`
stack when a `for…of` iterates a sync generator, so every control-flow abrupt
completion that already unwinds finallys also closes the generator, correctly
interleaved with any body/consumer `finally`.

- The generator instance is evaluated once, bound to a synthetic local, and a
  `<gen>.return()` `ExpressionStatement` is pushed onto `pendingFinallys`. When an
  early exit runs pending finallys, it emits that call, which drives
  `emitGeneratorReturnByValue` (resumes the suspended fiber to run its `finally`,
  or is a no-op if already done).
- **Ordering is the crux**: the close is pushed *before* this loop's
  break/continue targets record their depth. So a plain **this-loop `break`** (and
  normal completion) — which unwind only to that later depth and close once via
  the loop-exit label (ADR-00613) — do **not** double-run it; while a **`return`**
  (unwinds to the function boundary), an **outer** labeled `break`/`continue`
  (unwinds across this loop's level), and a body `try/finally` all run it in the
  correct innermost-first order. A **this-loop `continue`** does not run it (it
  keeps iterating), because it unwinds only to the post-push depth.

## Scope

Covers `return`, this-loop `break` (ADR-00613), outer labeled `break`/`continue`,
and normal completion. A **`throw`** propagating out of the body does not yet
close the iterator — exceptions unwind through a separate mechanism than the
control-flow `pendingFinallys` path (and this compiler's `try/finally`-without-
catch re-propagation is itself a pre-existing gap), so it is left as a documented
residual. Async generators are consumed by the `for await…of` path, untouched.

## Verification

`TestE2EForOfGeneratorReturnFromBodyRunsFinally` (return runs the finally),
`TestE2EForOfGeneratorReturnNestedFinallyOrder` (body finally then generator
finally, innermost-first), and `TestE2EForOfGeneratorLabeledBreakAndContinue`
(outer labeled break closes; `continue` does not) — all matching Node v26. The
break/normal-completion cases (ADR-00613) still pass, and the generator, for-of,
and exception suites are green. Built and verified on Mac (Apple Silicon).
