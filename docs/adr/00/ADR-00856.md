# ADR-00856: Emitter rail — reject empty-operand stores instead of shipping invalid IR

- **Date**: 2026-09-10

## Context

The invalid-IR backlog (the ranked set of Test262 files that reach `clang` and
fail with a codegen bug rather than a clean rejection) has a distinct cluster —
call it **B** — where an expression whose emit path is *recognized* but
*unimplemented for some edge* returns a zero `Value{}` (empty `Ref`). That empty
`Ref` is then formatted straight into a store: `store <ty> , ptr …`. The result
is malformed LLVM that `clang` rejects with an opaque scratch-file diagnostic —
the failure is silent at the emitter and only surfaces, confusingly, at the
external tool. Worse, nothing structurally prevents a *future* feature from
regressing the same way: any new emit path that forgets to produce a value ships
invalid IR undetected.

This is the highest-leverage anti-revisit move in the invalid-IR work: it changes
the whole class of bug from silent to loud, permanently.

## Investigation

Every non-alloca, non-terminator instruction flows through the single chokepoint
`emitInstr` (`codegen/llvm/emitter.go`). The only direct `e.body.WriteString`
sites outside it (`emit_async.go`, `emit_generators.go`) are pre-built labels,
`ret`, and GC set/restore blocks — never value stores — so `emitInstr` sees every
store that could carry an empty operand.

The malformed shape is precise: a well-formed store always has a non-empty value
token between the type and the first comma (`store i64 0,`, `store ptr %r,`,
`store double 0x…,`, `store ptr getelementptr(…),`). The bug leaves a bare comma
there (`store i64 ,`). This is distinguishable from the *other* store-shaped
invalid-IR clusters — e.g. A1's type mismatch `store i1 %t4, ptr` where `%t4` is a
`ptr` — which have a **non-empty** operand and must continue past to `clang` for
the A1 coercion sweep to own. The guard must catch only the empty-operand shape.

`EmitProgram` returns `(string, error)` and there is no `recover()` anywhere in
codegen, so a sentinel panic recovered at that boundary yields a clean compile
error uniformly, without threading an `error` return through the hundreds of
`emitInstr` call sites.

## Decision

Add a detection helper `malformedStoreValueOperand(line)` that, for a `store `
line, skips the type token and reports whether the value operand is empty (bare
comma or end-of-string). In `emitInstr`, when a `store ` line trips it, `panic`
with a sentinel `emitGuardPanic`. Recover that sentinel at the top of
`EmitProgram` and convert it to a clean compile error:

> `unsupported operation: an expression produced no value and cannot be stored — this construct is not yet implemented`

Any other panic re-propagates unchanged. The message is deliberately generic (the
rail is a last-resort net with no source position): where a construct is *known*
unsupported, the specific emit path should still raise its own targeted error
(e.g. the pre-existing "the 'in' operator requires a string literal key") — the
rail exists only for the paths that have none, and a generic-but-clean rejection
is strictly better than the invalid IR it replaces.

## Implementation notes

- `codegen/llvm/emitter.go`: `emitGuardPanic` type, `malformedStoreValueOperand`,
  the guard in `emitInstr`, and the `recover` in `EmitProgram` (whose signature
  gained named returns `(ir string, err error)` for the deferred assignment).
- The guard is on the hot path but pays only a cheap `strings.HasPrefix(line,
  "store ")` for non-stores; the operand scan runs only for store lines.
- Separation of clusters is exact: a non-empty operand (A1 type mismatch, etc.)
  is not touched and still reaches `clang`.

## Side effects discovered

A full Test262 faillist run (strict lane, isolated — no concurrent suites, per
the contention caveat) reclassified **17 files** from `CLANG_ERROR` (silent
invalid IR) to a clean compile-time rejection. The 17 are diverse edge cases
across unrelated features (e.g. `in` with a discarded conditional in a `for`-init,
`replaceAll` functional-replace no-match, private-reference logical assignment,
class field init-error evaluation) — they are *not* "a few missing builtins" as
the earlier backlog note anticipated (that note's example, `ArrayBuffer.resize`,
has since been implemented). Each underlying feature gap remains open on its own
merits; this ADR does not fix them — it converts their *failure mode* from
invalid IR to an honest rejection. The aggregate `CLANG_ERROR` count is not a
clean before/after for this change alone (the working tree carries a large
inherited staged set relative to the last committed report); the defensible,
change-scoped claim is the 17-file reclassification and zero remaining
empty-operand stores in the corpus.

## Verification

- `codegen/llvm/emit_store_guard_test.go`: unit test pinning
  `malformedStoreValueOperand` across malformed and well-formed store forms
  (including `atomic`, `getelementptr`, float-hex, `null` value tokens — no false
  positives), plus an integration test that `emitInstr` panics with the sentinel
  on an empty-operand store and writes a well-formed store through untouched.
- `go build`, `go vet ./codegen/llvm/` clean.
- Test262 faillist run confirmed **0** remaining `store <ty> , ptr` malformed
  stores across 53578 files; 17 files now reject cleanly.
- Full `make test-par` (see delivery) — no regression (a guard that only fires on
  invalid IR cannot break a passing test).
- Platform: Apple-Silicon Mac.
