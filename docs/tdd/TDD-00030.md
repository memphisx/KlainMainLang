# TDD-00030: Getters / setters (`get x() {}` / `set x(v) {}`)

- **Status**: Implemented (see [ADR-00110](../adr/ADR-00110.md))
- **Date**: 2026-08-06

## Context

`docs/status/LANGUAGE-CONSTRUCTS.md` documents this as a confirmed gap: no accessor-property parsing anywhere in `parser_literals.go`/`parser_classes.go` — `get`/`set` are recognized only as plain identifiers. Picked up at the user's explicit request, immediately following destructured function parameters (ADR-00109) and the operator-completeness pass (ADR-00108).

This is architecturally different from the last several features picked up in this pass: today, every object/class instance in this compiler is a heap-allocated struct with a fixed field layout known entirely at compile time — `obj.x` is always a plain `GetElementPtr`+`load`, `obj.x = v` is always a plain `GetElementPtr`+`store`. Getters/setters mean *some* property names on a type must instead route through a method call. This needs a real design pass before implementation, per this project's own standing rule for work of this shape.

## Design

### Scope: classes only, not object literals

This compiler's object types are pure structural value types: two object literals with the same field names/types collapse to an identical `Type{Fields: []Field{...}}` (Go struct-value equality, used implicitly everywhere two object shapes are compared or coerced against each other — see `emit_objects.go`'s `emitObjectLiteralWithHint`/TDD-00007). A `Type` carries no method table, no name, nothing to hang a per-shape accessor table off. Making an object-literal getter part of type identity would mean promoting every object-literal `Type` to carry its own accessor side-table and touching every structural comparison/coercion site in the compiler — a materially larger, structurally invasive change.

Classes already sidestep this entirely: `IsClass`/`ClassName` make a class instance's type nominal (never structurally unified with a different class's instances), and `e.classes[name]` (`ClassInfo`) is already a name-keyed registry carrying a full method table (`Methods`/`MethodSigs`/`MethodImplementor`/`MethodDispatchSlot`, TDD-00009 Stage 3) — exactly the kind of home an accessor table needs, with zero changes required to `Type`'s own structural-equality shape. **V1 scope is classes only.** Object-literal getters/setters are a separate, larger follow-on if ever needed.

### No new storage — accessors are just methods, dispatched through a name-mangled key

A getter/setter needs no new struct field, no new heap layout, no new `Type`/`Field` concept at all. `get x(): T { ... }` is exactly a zero-arg method returning `T`; `set x(v: T) { ... }` is exactly a one-arg `void` method. Both already fit `ast.FunctionDeclaration`/`ClassInfo.Methods`/`MethodSigs`/dispatch completely unmodified — the *only* new things needed:

1. **Parsing**: `ast.FunctionDeclaration` gains `AccessorKind string` (`""` / `"get"` / `"set"`), set when a class member's name is preceded by the contextual keyword `get`/`set`.
2. **A mangled dispatch key**: register a getter for property `x` under the method name `"get x"`, a setter under `"set x"` (a space can never appear in a real identifier, so this can never collide with a genuine user-declared method name). Every existing piece of method machinery — inheritance copy-then-override, override/vtable analysis (`MethodSlot`/`MethodDispatchSlot`), `MethodImplementor`, abstract-completeness checking, visibility (`OwnMethodVisibility`), and the actual call codegen (`emitClassCall`) — already operates purely on a `map[string]...` keyed by method name and needs **zero changes** to correctly inherit, override (including through a vtable when overridden — an accessor is exactly as overridable as any other method), and dispatch a getter/setter once it's registered this way. This is the crux of the whole design: reuse, don't reinvent.
3. **Property lookup**: `emitMember`/`emitOptionalMember`/`emitAssign` need to check "does this class have an accessor for property `x`" (a `MethodSigs["get "+x]`/`["set "+x]` lookup) *before* falling into the existing `FieldIndex` path — a genuine `Field` is never created for an accessor-only property name, so `FieldIndex` already correctly reports "not found" for one; the accessor check just needs to run first and intercept.

### Read path

`emitMember`'s general object-field-read branch (`emit_exprs_member.go`, right after `objVal, err := e.emitExpr(ex.Object)`, before the `FieldIndex` call): if `objVal.Ty.IsClass`, look up `"get "+ex.Property`/`"set "+ex.Property` on `e.classes[objVal.Ty.ClassName].MethodSigs`. If neither exists, fall through to the existing `FieldIndex` path unchanged (every non-accessor class, and every non-class object, is byte-identical to today). If a getter exists, call it via the existing `emitClassCall(objTy, objVal, "get "+prop, nil, pos, false)` and return its result — the same function every ordinary `obj.method()` call already goes through, so inheritance/override/vtable dispatch and visibility checking all come for free. If *only* a setter exists (no getter), reading is a clean compile-time error ("property has no getter") rather than a silent wrong value.

`emitOptionalMember` (`obj?.x`) needs the identical check threaded into its existing "determine `resultTy` before branching on null" structure — the getter's return type becomes `resultTy`, and the non-null branch calls the getter instead of doing a GEP+load.

`this.x` inside any method (including a *different* method than the accessor itself) goes through this exact same `emitMember` path with no special-casing needed — `this` is an ordinary `Symbol` like any other, so real JS's own "even internal `this.x` invokes the accessor" semantics fall out for free. The accessor's *own* body reads its real backing storage under a different name (e.g. `get x() { return this._x }`) — `_x` is a perfectly ordinary field, no special mechanism needed; a user who writes `get x() { return this.x }` gets exactly real JS's own infinite-recursion stack overflow, not a compiler bug.

### Write path

`emitAssign`'s object-field-assignment branch (`emit_exprs_assign.go`): same accessor lookup, inserted before `FieldIndex`. If a setter exists:
- Plain `=`: evaluate the RHS hint-aware against the setter's declared parameter type (`emitExprWithObjectHint`, matching how a plain field assignment already coerces against the field's declared type), call the setter via `emitClassCall` with that one argument, return the assigned value (matching a plain assignment expression's own value — real JS's assignment-to-a-setter also evaluates to the assigned value, not the setter's `void` return).
- Compound (`+=` etc.): requires *both* a getter (to read the current value) and a setter (to write the new one) — a clean error naming whichever is missing. Read current via a getter call, compute the new value via the existing `emitArith`, call the setter with the result.
- Logical (`&&=`/`||=`/`??=`): **rejected outright for V1** with a clear compile error. `emitLogicalCompoundAssign` is generic over "any assignable `ptr`+`Type` lvalue" specifically *because* it can cheaply re-load the same memory location across its short-circuit branches — an accessor has no such location, and evaluating a getter/setter more than once per source-level use would risk observable double-invocation of user code with side effects, unlike a plain memory location. Not attempted here; a real fix would need `emitLogicalCompoundAssign` itself to grow a call-based variant.
- If only a getter exists (no setter), writing is a clean compile-time error ("property has no setter") — the read-only-property case.

If *neither* a getter nor a setter is found for the property name, both read and write paths fall through to the existing `FieldIndex` logic completely unchanged.

### Parsing: contextual `get`/`set`, not reserved keywords

Like `in` (ADR-00091) and unlike `static`/`private`/`protected`/`abstract` (real reserved tokens), `get`/`set` must stay ordinary `lexer.IDENT` text — a field, method, or variable literally named `get`/`set` must keep working everywhere outside this one grammatical position. `parser/parser_classes.go`'s class-member loop, after its existing modifier loop and before consuming the member name, gets a lookahead-gated check: `p.peek()` is `IDENT` with literal `"get"`/`"set"`, **and** the token after that is itself a plausible member name (not `(`, which must keep parsing as an ordinary method literally named `get`/`set`, e.g. `get(): number { ... }`) — mirroring the `for...in` loop's own existing 2-token disambiguation lookahead (`parser_stmts.go`), a closer precedent than `in`'s simpler 1-token check since `get`/`set` (unlike `in`) are also valid names on their own.

### Validation (`registerClasses`)

All at class-registration time, alongside the existing per-method processing:
- **Arity/shape**: a getter must take exactly 0 parameters and must not declare (or infer) a `void` return type; a setter must take exactly 1 parameter and is always treated as `void` regardless of any declared return (matching real JS: a setter's return value is always discarded).
- **Get/set type agreement**: when both a getter and setter are declared for the same property name (in either order), the getter's return type and the setter's parameter type must match — otherwise reading and writing the same property would disagree on its type.
- **Mutual exclusion**: an accessor name must not collide with a plain data field name (own or inherited — checked against the class's already-flattened field list) or a plain method name (own or inherited) under the *same*, unmangled property name. A regular method must symmetrically reject reusing a name already claimed by an inherited accessor.
- **Duplicate accessor**: at most one getter and at most one setter per property name per class (redeclaring `get x()` twice in the same class is an error, same as any other duplicate-method check this compiler already has).
- **Static accessors**: **rejected outright for V1** with a clear compile error (`static get x()`/`static set x()`) — real TS supports these, but they'd need `emitStaticFieldRead`/`emitStaticFieldAssign` (a separate code path from instance field access) taught the identical accessor-check, and static accessors are rare enough in practice to defer rather than double the surface area of this first pass.
- **Abstract accessors**: fall out for free — an abstract class's accessor with no body is stored in `info.Methods` under its mangled key exactly like any other method, so the existing abstract-completeness check (every inherited-or-own method must have a real implementation by the time a concrete class is reached) already covers `abstract get x(): number;` with no changes needed.

### Deliberately out of scope for V1

- **Object-literal getters/setters** — see Scope above.
- **Static getters/setters** — see Validation above.
- **Bulk enumeration awareness**: `{...obj}` spread, `const {x} = obj` destructuring, `JSON.stringify(obj)`, `Object.keys`/`.values`/`.entries`/`.assign` on a class instance with accessors. All of these walk `VisibleFields()`/`Fields` directly — an accessor-only property is never a real `Field`, so these paths simply won't see it at all: not a crash, not a silently wrong value, just an incomplete result (the accessor is invisible to reflection). Documented as a known limitation, not fixed here. A real fix would need `VisibleFields()`-driven enumeration sites taught to also synthesize entries for accessor names — real, but deferred.
- **`#x in obj` / accessor existence checks via `in`** — the `in` operator (ADR-00091) already only checks `FieldIndex`; an accessor-only property would report `false`, same reasoning/deferral as bulk enumeration above.

## Prerequisites
