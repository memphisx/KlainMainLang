# ADR-00386: Closure capture for nested function declarations (Stage 1)

- **Relations**: Implements TDD-00129; Extends ADR-00149 (TDD-00057), ADR-00178
- **Date**: 2026-08-27

## Context

Nested function declarations ([TDD-00057](../tdd/TDD-00057.md)/[ADR-00149](ADR-00149.md))
shipped with a deliberate non-goal: a nested function got its own clean scope
like a top-level function and could **not** capture the enclosing body's
locals/parameters. Referencing one was a clean `undefined variable` error:

```
function outer(x: number): number {
  function inner(): number { return x + 1; }  // codegen error: undefined variable 'x'
  return inner();
}
```

[TDD-00129](../tdd/TDD-00129.md) Stage 1 closes that gap for the common
use-at-or-after-declaration case.

## Investigation

The decisive fact (found while scoping, verified against the source): nested
functions **already escape as first-class values** under the non-capturing
scheme — `return inner` and `arr.map(dbl)` both compile, as a bare function
pointer. So a capturing nested function cannot stay a bare mangled function: an
escaped `inner` runs after its enclosing frame is gone, so a captured `x` must
travel with it. That forces the **closure-value representation** (`{fn, env}`),
exactly what arrow/function-expression closures already use — and settles
TDD-00057's open fork in favor of *desugaring to the closure path* rather than
bolting a hidden env parameter onto the direct-call path.

Everything the capture needs already existed and is reused unchanged:
`gatherCaptures`/env-struct with by-reference boxed cells for mutated captures;
the named-function-expression self-capture ([ADR-00178](ADR-00178.md)) for
recursion; and the closure-value call/return/store/pass-as-callback paths for
escape.

Two constraints shaped the mechanism. First, `pushNestedFuncScope` runs *before*
the enclosing scope's params/locals are `define()`d (`emit_func.go`), so capture
classification at pre-scan must be **syntactic**, not `e.lookup`-based. Second,
the bare-identifier call dispatch (`emit_call.go`) resolves `resolveFuncRef`
(nested + top-level direct calls) *before* the closure-value lookup — so a
capturing nested function must be kept **out** of `nestedFuncScopes`, or a call
would wrongly direct-dispatch to an LLVM symbol that was never emitted.

## Decision

Capture-triggered split, classified at pre-scan:

- **Non-capturing** nested declaration → unchanged: mangled name, direct call,
  hoisted/forward-referenceable via `nestedFuncScopes`.
- **Capturing** nested declaration (references a binding of some enclosing
  function scope) → recorded in a new `nestedFuncScope.capturing` set,
  deliberately absent from `byName`/`byDecl`. At its declaration point
  `emitStmt` emits it via `emitCapturingNestedFunc`, which synthesizes the
  equivalent named `ast.FunctionExpression`, runs it through
  `emitFunctionExpression` (reusing all closure machinery), and binds the
  resulting closure value to the function's own name in the current scope.

Because a capturing function is out of `resolveFuncRef`, a call after the
declaration falls through to the closure-value lookup (correct), and a call
*before* it cleanly errors as `undefined function or closure` — which is exactly
Stage 1's use-at-or-after-declaration boundary, not a link failure.

**Syntactic capture classification.** A new emitter stack `enclosingCapturables`,
parallel to `nestedFuncScopes`, holds one frame per enclosing function body: its
parameters plus its `var`/`let`/`const`/destructured locals — *not* its
function/class declaration names (those are resolved by name, never closed over,
so excluding them keeps a helper that merely calls a sibling function on the
cheap direct-call path). A declaration captures iff a free variable of its body
(excluding its own params and its own name) is present in any frame.
Over-approximation is safe: a declaration wrongly flagged capturing becomes a
zero-capture closure (correct, only slightly less efficient); under-approximation
cannot happen for an in-scope local, since every such binding is in a frame.

## Implementation notes

- `pushNestedFuncScope` gained a `params []ast.Param` argument (all four callers
  updated: plain decl, arrow, function-expression, generator) to seed the
  capturable frame; `popNestedFuncScope` pops the parallel `enclosingCapturables`
  frame; both are popped on every early-error return via a local `popFrames`
  closure to keep the two stacks balanced.
- **Generators are excluded** from the capturing path and stay on the existing
  direct-registration route regardless of capture — a capturing nested generator
  needs the generator-instance `__env` combined with a closure env, deferred to
  TDD-00129 Stage 3.
- Recursion of a capturing nested function resolves through the
  function-expression self-capture, not the enclosing-scope name slot (which is
  defined only *after* emission).

## Side effects discovered

- Capturing an **array** variable is a clean rejection, inherited unchanged from
  the closure machinery (`capturing array variable '%s' in a closure is not yet
  supported`) — not new to this change.
- Full pre-declaration hoisting of a capturing nested function, and a capturing
  nested generator, are explicitly deferred to TDD-00129 Stages 2 and 3.
