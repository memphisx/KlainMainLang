# TDD-00199: Destructured callback parameters (`([k, v]) => …`)

- **Status**: Implemented ([ADR-00854](../adr/ADR-00854.md))
- **Date**: 2026-09-10

## Context

Array/tuple destructuring in a function *parameter* position without an explicit
type annotation is unsupported, and even with an annotation it only works for a
homogeneous array element type:

- `arr.map(([k, v]) => …)` — **parse error** ("expected ), got =>"): the
  destructured-arrow lookahead (`destructuredArrowParamLookahead`) only accepts a
  pattern parameter when a `:` type annotation follows it, so an un-annotated
  pattern is treated as a parenthesized array-literal expression.
- `a.map(([x, y]: number[]) => x + y)` — **works** (homogeneous element type).
- `a.map(([x, y]: [number, number]) => x + y)` — **codegen error** "undefined
  variable 'x'": a tuple type annotation on a destructured param does not bind
  its elements.

This blocks the single most common destructuring idiom in real code — iterating
`Object.entries(o)`, `Map` entries, or `[key, value]` pairs with `.map`/`.filter`
/`.forEach`. Object-destructured params (`({a, b}) => …`) already work, and
`for (const [k, v] of Object.entries(o))` already destructures a heterogeneous
entry tuple — so the machinery exists in adjacent positions; only the parameter
path is missing.

## Design

Two independent gaps, both required for zero-caveat completeness:

### 1. Un-annotated pattern parameters (contextual typing)

The closure emitter already threads a `hints []Type` channel
(`emitArrowFunctionWithHints`): a HOF call site supplies each un-annotated
parameter's type from the receiver's element type. When `p.Type == nil` and the
param is a pattern (`ArrayPattern`/`ObjectPattern`), use `hints[i]` as the
pattern's type instead of erroring.

- **Parser**: extend `destructuredArrowParamLookahead` to scan to the param
  list's matching `)` and accept a following `=>` (optionally past a
  `: returnType`), so `([k, v]) => …` is recognized as an arrow. Drop the
  "a destructured parameter requires an explicit type annotation" error, leaving
  `p.Type == nil` for the codegen hint path to fill.
- **Codegen**: in `emitArrowFunctionWithHints`, when `p.Type == nil` and the
  param carries a pattern, take `paramTypes[i] = hints[i]`. The existing
  `unpackArrayPatternInto` / `unpackObjectPatternInto` closure-param calls then
  bind the leaves.

### 2. Heterogeneous tuple param binding

`unpackArrayPatternInto` binds each leaf using a single uniform `*pty.ElemType`,
which is correct for `number[]` but wrong for a `[string, V]` tuple (the two
positions differ). This needs a tuple representation with per-index element
types, reusing whatever the working `for (const [k, v] of Object.entries(o))`
path already uses to decompose an entry tuple — factor that into a shared
per-index unpack so the parameter path binds `k: string`, `v: V` correctly.

The two gaps compose: (1) supplies the tuple type via a hint; (2) binds its
heterogeneous positions. Ship together — (1) alone still fails on the dominant
`Object.entries`/`Map` case, which is a caveat.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| `hints []Type` contextual-typing channel | Built | `emitArrowFunctionWithHints`; HOF sites populate it |
| Object-pattern params (`({a,b}) =>`) | Built | Template for the pattern-param path |
| For-of heterogeneous tuple destructuring | Built | `for (const [k,v] of Object.entries(o))` — source of the per-index unpack |
| Homogeneous array-pattern param binding | Built | `unpackArrayPatternInto` with a uniform `ElemType` |
| Tuple type with per-index element types | Missing | The core of gap 2 |

## Open questions

- Does a first-class tuple `Type` (per-index element list) already exist for the
  for-of path, or does that path special-case entry decomposition inline? The
  answer decides whether gap 2 is a plumbing job or a new `Type` shape.
- Nested patterns in a param (`([[a], b]) => …`) and defaults
  (`([a = 1]) => …`) — in scope, or a follow-on? The parameter default is
  already rejected elsewhere.
