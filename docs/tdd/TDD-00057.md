# TDD-00057: Nested function declarations

- **Status**: Implemented
- **Date**: 2026-08-10
- **Notes**: V1 scoped to a declaration written directly in its enclosing function/arrow body's own immediate statement list (hoisted, forward-referenceable, self-recursive) — not one block deeper inside an `if`/`for`/etc.; deliberately no closure capture of the enclosing scope's locals (separate, larger follow-up)

## Context

`docs/status/LANGUAGE-CONSTRUCTS.md` and `docs/status/README.md` list nested function declarations (`function outer() { function inner() {...}; return inner(); }`) as a confirmed gap — the roadmap's own one-line note calls it "separate from closures; mostly a scoping change." This TDD scopes what "mostly a scoping change" actually means in this compiler's codegen model, since the honest picture is more nuanced than that phrase suggests.

Traced directly against the source before designing anything: the parser and AST already handle this construct for free. `parseStatement` (`parser/parser_stmts.go:9`) is the single dispatch point for both `Program.Body` and every `{...}` block body (`parseBlock`, `parser/parser_stmts.go:815`) — a `function` keyword inside a block already parses into a normal `*ast.FunctionDeclaration`, which already satisfies `ast.Statement` and can already sit inside `BlockStatement.Body`. The actual and only blocker is a single explicit rejection in codegen: `emit_stmts.go:51-52` returns a clean `"nested function declarations are not supported"` error the moment `emitStmt` reaches one.

Removing that rejection alone isn't enough to make the feature work correctly, though — it would compile, but two things this compiler doesn't do for a plain `*ast.FunctionDeclaration` today would silently misbehave or reject:

1. **Forward reference / self-recursion.** Top-level functions can call each other regardless of source order because `registerFunctions` (`emitter.go:791`) pre-scans and registers every signature into `e.funcs` before any body is emitted (a two-pass setup). A nested function has no equivalent prescan, so a sibling declared later in the same block, or a nested function calling itself, would fail to resolve.
2. **Namespace collisions.** `e.funcs` is a single flat, whole-program map. Two nested functions with the same name in different enclosing functions, or a nested function shadowing an unrelated top-level function of the same name, would silently clobber each other if registered directly into it.

Closures (capturing an enclosing scope's local variables) are a separate, much larger piece of work — see Design's Non-goal below — which is exactly what "separate from closures" in the existing roadmap note was already trying to flag, just without the detail this document now adds.

## Design

### Scope (V1)

A nested function declaration is supported when written **directly in the immediate statement list of an enclosing function's own body block** — the body of a top-level `function`, or (recursively) the body of another nested function, or the block body of a `=> { ... }` arrow function. It is **not** supported one level deeper, inside a further `if`/`for`/`while`/`switch`/bare-`{}` block nested within that body — that shape is a clean compile error, not silent misbehavior, and is deliberately left for later (see Open Questions).

Within its supported position, a nested function declaration:

- Is visible for calls anywhere in the enclosing body, including *before* its own textual position (hoisted) and from within its own body (recursion) — matching real JS/TS function-declaration hoisting.
- Is visible to the enclosing function's own further-nested functions (a grandchild can call a function declared in its parent or grandparent), via the same lexical-scoping reasoning real JS uses for named function visibility.
- Is **not** visible outside its enclosing function.
- Does **not** capture the enclosing function's local variables or parameters — its body may reference only its own params/locals plus true globals (top-level functions, enums, classes, imports), exactly like a top-level function today. Referencing an outer local produces the same "undefined variable" error referencing any unrelated unbound identifier would.
- A generic (`<T>`) nested function declaration is a clean compile error — TDD-00010's generic-function machinery is scoped to top level only; extending it to nested position is out of scope here.
- A duplicate nested function name declared twice directly in the same body is a clean compile error, rather than a silent last-wins overwrite.

**Non-goal — closure capture.** A real JS/TS nested function closes over its enclosing scope's locals the same way an arrow function does. That mechanism (`gatherCaptures`/`CapturedVar`/heap-allocated env struct, `emit_func.go:200-445`) is arrow-function-specific today and reused here only implicitly, in spirit, by giving a nested function *its own* clean scope the same way a top-level function already gets one — not by extending the capture machinery to a second AST node type. A nested function that references an enclosing local fails cleanly at the same "undefined variable" check every other out-of-scope reference already hits. Generalizing capture to named nested functions is real, separately-scoped follow-up work, not attempted here.

### Mechanism

**Per-body two-pass registration, scoped rather than global.** Reuse `registerFunctions`' per-declaration signature-building logic (return type resolution/inference, parameter type resolution, defaults, rest-param detection — `emitter.go:826-876`) via a new shared helper, `buildFunctionSig(fd *ast.FunctionDeclaration) (FuncSig, error)`, called both by the existing top-level `registerFunctions` loop and by a new `pushNestedFuncScope(body []ast.Statement) error`.

`pushNestedFuncScope` walks `body` (direct statements only, not recursively into sub-blocks) and, for each `*ast.FunctionDeclaration` found:
- Rejects a generic declaration and a same-scope duplicate name as described above.
- Assigns it a unique mangled LLVM name (`fmt.Sprintf("%s__nested%d", fd.Name, e.nestedFuncCtr)`, matching the existing `__nested_%d`-style convention `emit_func.go:893`'s `@__closure_%d` already establishes for compiler-synthesized names).
- Builds its `FuncSig` via `buildFunctionSig`.
- Records both under the source name (for lookup) and under the `*ast.FunctionDeclaration` pointer itself (so `emitStmt` can distinguish "this exact declaration was pre-registered directly in my body" from "this is a deeper, unsupported nesting" without re-deriving position information).

This produces one `nestedFuncScope` frame per enclosing body, pushed onto a new `Emitter.nestedFuncScopes []nestedFuncScope` stack right after the enclosing function's own `e.pushScope()` (`emit_func.go:37` for a plain function, the equivalent point in `emitClosureFunc` for an arrow function's block body), and popped once its body finishes emitting. Because `emitFunctionDeclAs` is already fully reentrant (it save/resets/restores every piece of per-function emitter state — allocas, body builder, register/label counters, scopes — around its own emission, already exercised recursively today by `emit_generics.go`'s on-demand generic instantiation), a nested function's body is emitted by simply calling `emitFunctionDeclAs(nestedDecl, mangledName, sig)` recursively from `emitStmt`'s `*ast.FunctionDeclaration` case — no new function-emission path is needed, only the lookup/dispatch layer around it.

**Name resolution.** A new `resolveFuncRef(name string) (mangled string, sig FuncSig, ok bool)` searches `e.nestedFuncScopes` innermost-to-outermost first, falling back to the existing flat `e.funcs[name]` lookup. Five existing `e.funcs[<identifier>]` call sites — every place a bare identifier used as a callee or callback is resolved against the flat map — switch to this helper instead of a direct map index:

| Site | Purpose |
|---|---|
| `emit_call.go:765` | Direct call dispatch (`inner(...)`) |
| `emit_exprs_types.go:209` | `inferExprType` treating a bare function name as an `IsFunc` value |
| `emit_exprs_types.go:406` | `inferExprType` of a `CallExpression`'s return type |
| `emit_exprs_vardecl.go:112` | `emitVarDecl`'s own pre-inference switch (same reasoning as the row above, duplicated for a separate historical reason — see that file's own comments) |
| `emit_func.go:1078` (`resolveCallback`) | Passing a nested function by name as a callback (HOF methods via `resolveCallbackWithHints`, timers, `EventEmitter`, `.replace()`, etc. all funnel through this one function) |

No other call site needs to change: everywhere else that dispatches on a *value* already holding `Type{IsFunc: true}` (a closure variable) is untouched, since a nested function is called through its resolved LLVM name exactly like a top-level function, never boxed into a closure value.

### Why not just desugar to an arrow function assigned to a local variable?

Considered and rejected for V1. It would get capture semantics for free (reusing `gatherCaptures` unchanged) and would make self-recursion "just work" via the same capture-by-reference-to-a-heap-cell mechanism arrow functions already use for any captured variable — but it would also turn every nested-function call into an indirect call through a loaded function pointer (`emitClosureCall`) instead of a direct call, add a heap allocation per invocation of the enclosing function for the env struct even when nothing is captured, and require the enclosing local-variable slot for the nested function's own name to be alloca'd and pre-populated before its closure is built (a letrec-style ordering concern) to make self-reference and forward-reference work at all. The plain-named-function path above gets forward-reference and recursion for free from the same two-pass mechanism top-level functions already rely on, with a direct call and zero extra allocation — strictly cheaper for the common case (a helper function that doesn't need to close over anything), at the cost of not supporting capture. Given captures are being deliberately deferred anyway (see Non-goal above), the cheaper mechanism is the right default; a future closure-capturing nested function could reuse this document's scoping/hoisting design and add capture on top rather than needing a different foundation.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Two-pass top-level function registration (`registerFunctions`) | Done | Signature-building logic factored out into `buildFunctionSig`, reused unchanged |
| Reentrant `emitFunctionDeclAs` (save/reset/restore per-function emitter state) | Done | Already exercised recursively by TDD-00010 V1 generic instantiation |
| A scope stack for *variables* (`e.scopes`/`pushScope`/`lookup`) | Done | Not reused directly — nested functions get their own analogous stack (`nestedFuncScopes`) rather than piggybacking on the variable one, since a function name and a variable name are resolved through different call-site logic today |
| Arrow-function closure/capture machinery (`gatherCaptures`, env struct) | Done, not reused | Deliberately out of scope for V1 — see Non-goal |

## Open questions

- Whether to lift the "directly in the immediate body, not one block deeper" restriction later. Doing so generally (nested function declarations legal inside an `if`/`for` body too) would mean pushing/popping a `nestedFuncScopes` frame around every block a statement list can appear in, not just a whole function body — mechanically similar to this design but touching every block-processing call site (`emitIf`/`emitFor`/`emitWhile`/etc.) instead of just `emitFunctionDeclAs`/`emitClosureFunc`. Left for a follow-up once real usage shows the V1 restriction is actually felt.
- Whether closure capture for named nested functions is worth adding later, and if so whether it reuses `gatherCaptures` against `*ast.FunctionDeclaration` directly or desugars to the arrow-function path after all now that hoisting/forward-reference is solved separately by this document.
