# TDD-00220: Dynamic-object performance — hidden classes + inline caches (D2)

- **Status**: Not Started
- **Date**: 2026-09-17

## Context

The native dynamic object model (D1, [TDD-00155](TDD-00155.md), Implemented)
gives `any`/dynamic values a real per-instance property bag with prototype
chain and descriptors, behind the `@__kml_dynobj_*` runtime surface. It was
scoped **correctness-first**: the property store is an insertion-ordered linear
array, and every `get`/`set`/`has` on a tag-10 dynamic object is an O(n)
`strcmp` scan of that array plus, for a miss, a walk up the prototype chain
repeating the scan at each link. [TDD-00068](TDD-00068.md) and TDD-00155 both
name this explicitly as the honest V1 with the perf gap *recorded, not designed
around*, and both point at a later optimization tier they label **D2 — hidden
classes / inline caches** — a pure performance layer over D1, correctness-neutral.

This document is that tier's design. It is being scoped now (not built now) so
the design thinking is captured rather than lost: D2 is **not** currently
prioritized — per this project's standing rule, caveat-reducing work comes
first, and D2 deletes no caveats (D1 already made the behavior faithful). It is
recorded here as the standing performance follow-up so it can be picked up
deliberately once D1's remaining caveat-bearing residue (Stage-6 widening,
method-carrying-class boxing, primitive-member dispatch through `any`) is closed.

Why it will matter: as more of the Node/JS surface routes real workloads through
tag-10 objects (`JSON.parse → any`, vanilla-JS prototype "classes", `Proxy`,
dynamic property graphs), the linear scan becomes the dominant cost on the
dynamic path — the same reason every production JS engine (V8, SpiderMonkey,
JSC) uses hidden classes. This is the documented perf-strategy swap the standing
"faithful now, faster later" rule anticipates, delivered as an *invisible*
change beneath the runtime API rather than a behavior divergence.

## Design

The whole optimization lives **beneath the `@__kml_dynobj_*` boundary**. Callers
(codegen sites emitting member get/set/`in`/delete, `Object.keys`, JSON, etc.)
are unchanged; D1's observable semantics — insertion order, descriptor
attributes, proto-chain walk, accessor invocation, frozen/readonly rejection —
are all preserved exactly. TDD-00155 already reserved the room this needs: "the
header word has room for a shape pointer, and nothing here is discarded by it
except the linear scan's interior."

Two independent, composable mechanisms:

### 1. Hidden classes (shape objects + transition trees)

A **shape** (a.k.a. hidden class / map) is an immutable descriptor shared by all
dynamic objects that have the same keys, in the same insertion order, with the
same attributes. It holds: an ordered key→slot map, per-slot attribute bits
(enumerable/writable/configurable, data-vs-accessor), the prototype pointer, and
a **transition table** (key + attrs → resulting shape).

- A dynamic object's header stores a **shape pointer** (the reserved word) plus
  a flat **values array** indexed by slot. The key strings and attributes move
  *out* of the per-instance entry array and *into* the shared shape; the instance
  keeps only values. This also shrinks each instance.
- **Property add** follows a transition edge: from the current shape, look up
  `(key, attrs)` in its transition table; hit → move to the target shape and
  append the value; miss → create the target shape once, record the edge, cache
  it. Objects built in the same key order thus converge on the same shape chain
  (the transition tree rooted at the empty shape for a given prototype).
- **Property lookup** becomes: read shape, find the slot for the key *in the
  shape* (still a per-shape structure, but shared and cacheable — see inline
  caches), read `values[slot]`. No per-instance key compare on the fast path.
- **Delete / attribute change / proto set** transition to a new shape (or, for
  delete specifically, fall back to a "dictionary-mode" shape — see below),
  matching how engines dispose of the fast path when an object is mutated in a
  shape-hostile way.
- **Dictionary (megamorphic) mode**: an object that is deleted from, or that
  accretes an unbounded/one-off key set, is demoted to a self-describing hashed
  property map (essentially D1's own store, or a hash-indexed variant) and its
  shape pointer marked dictionary. This is the graceful degradation path that
  keeps worst cases from exploding the transition tree — a documented parity with
  engine behavior, and the natural home for the "optional key-hash word per
  entry" ladder rung TDD-00155 mentioned.

### 2. Inline caches (IC)

At each dynamic member-access **call site**, cache the last-seen shape(s) and the
resolved slot/handler, so a repeated access with the same shape skips the shape
lookup entirely.

- Because access is emitted through `@__kml_dynobj_get/set`, the IC lives either
  (a) as a small per-call-site cache structure the codegen threads into the
  runtime call (site id → {shape, slot}), or (b) as monomorphic-inline guard code
  the codegen emits around the call. Option (a) keeps codegen simple and the
  cache in the runtime; option (b) is faster but bloats IR. **Recommended: start
  with (a)** — a per-site 1-entry (monomorphic) cache, widening to a small
  polymorphic set (≤4) before falling through to the general shape lookup, then
  the linear/dictionary path. This mirrors the mono→poly→megamorphic ladder and
  is measurable in isolation.
- The IC guard is a single pointer compare (`instance.shape == cached.shape`);
  on hit, use the cached slot directly.

### Staging (each independently shippable, correctness-neutral, benchmark-gated)

1. **Shapes for construction + lookup** — introduce shape objects and the
   transition tree; migrate the instance layout to shape-pointer + values array;
   keep a linear/dictionary fallback for any un-shaped or demoted object.
   `Object.keys`/`for...in`/spread walk the shape's ordered keys. No IC yet.
2. **Monomorphic inline caches** at get/set sites.
3. **Polymorphic ICs** (bounded set) + megamorphic fallthrough.
4. **Dictionary-mode demotion** tuning (delete-heavy / key-explosion objects) and
   the optional per-entry key-hash for the dictionary store.

Each stage lands with a benchmark delta in the self-hosted benchmarking output
(the established results convention) — D2 is justified by numbers, not face
value — plus a correctness re-run of the full D1 E2E suite (behavior must not
move) and `make examples`.

### Rejected / non-goals

- **Any observable change.** If a stage changes insertion order, descriptor
  reporting, proto-walk results, or accessor timing, it is wrong by definition —
  D1 is the oracle.
- **Per-type static shape descriptors** — already rejected outright by
  TDD-00068/TDD-00155 as throwaway work a per-instance model deletes; D2 does not
  revive it. Statically-shaped nominal objects (Tier S) stay fixed-shape structs
  and are untouched by D2 entirely.
- **JIT / runtime code generation.** ICs here are data caches + guard compares,
  not runtime-emitted machine code; this stays an AOT-compiled runtime.

## Open questions

- **IC placement** — runtime-side per-site cache (simpler) vs. codegen-emitted
  inline guards (faster, more IR): start with the former, but the crossover point
  is worth measuring before committing stage 2's shape.
- **Transition-tree memory bound** — pathological key-order variety can grow the
  tree; what is the demotion heuristic (per-root shape count? per-object
  transition count?) that trips dictionary mode?
- **Shapes across the `dlopen` island boundary** ([TDD-00056](TDD-00056.md)) and
  across `-mm=gc` — shape objects are long-lived shared metadata; confirm their
  lifetime/rooting under GC and whether islands share or duplicate the transition
  tree.
- **Interaction with `Proxy`** ([TDD-00155](TDD-00155.md) Stage 7) — a proxied
  object must bypass ICs (every trap is a call); confirm the IS_PROXY flag short-
  circuits the fast path cleanly.
