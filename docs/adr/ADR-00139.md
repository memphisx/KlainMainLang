# ADR-00139: `querystring` module (`.parse`/`.stringify`)

- **Date**: 2026-08-09

## Context

`docs/status/NODE-CORE-MODULES.md` grouped eleven lower-priority Node core modules together, all previously at 0% — `querystring` among them, explicitly noted there as "largely superseded by the already-implemented `URLSearchParams`." Picked up opportunistically (alongside `assert`, see [ADR-00140](ADR-00140.md)) precisely because that superseding relationship makes it cheap: `URLSearchParams` and `http.listen`'s `req.query` already do the percent-decode-into-a-`Map<string,string>` and percent-encode-a-`Map<string,string>`-into-a-string work this module needs, so there was no new runtime subsystem to build.

## Investigation

- Read `codegen/llvm/emit_url.go`'s `emitNewURLExpression` and `runtime_http.go`'s `ensureHTTPParseQuery`: `__kml_http_parse_query(ptr q, ptr map)` already splits an `"a=b&c=d"` string on `&`, each pair on the first `=`, and percent-decodes both key and value via `__kml_decode_uri_component` — exactly `querystring.parse`'s job, no new C runtime needed.
- Read `emitURLSearchParamsToString` (same file): builds `"k1=v1&k2=v2"` from a `Map<string,string>` by iterating `__kml_map_str_keys`/`__kml_map_str_vals` and percent-encoding each pair via `__kml_encode_uri_component` — exactly `querystring.stringify`'s job too.
- Checked whether `querystring.parse` should strip a leading `?` the way `new URLSearchParams(str)` does (`emitStripLeadingQuestionMark`). Real Node's `querystring.parse('?a=1')` does *not* strip it — `?a` becomes a literal key. Confirmed by reasoning about Node's actual documented behavior (`querystring` predates `URL`/`URLSearchParams` entirely and never had a "tolerate a leading `?`" convenience); matched that instead of copying `URLSearchParams`'s behavior blindly.
- Checked `req.query`'s field type (`codegen/llvm/types.go:854`): a plain `MapType(TypePtr, TypePtr)`, not a distinguished wrapper type the way `URLSearchParamsType()`/`HeadersType()` are. Matched this — `querystring.parse` returns a plain `Map<string,string>`, not a new pseudo-type, so it interoperates directly with `req.query`, `new Map<string,string>()`, and anything else already typed that way.
- Considered adding `querystring.parse`/`.stringify` as methods on `URLSearchParams` itself instead of a separate namespace, but real Node genuinely ships `querystring` as its own module with this exact shape — matching that surface (even though it's "legacy") is more useful for anyone porting existing Node code than inventing a different API.

## Decision

Implemented `querystring.parse(str: string): Map<string, string>` and `querystring.stringify(m: Map<string, string>): string` as a pseudo-namespace dispatched in `emitCall`/`inferExprType`, the same convention `path`/`os`/`fs` already use (a bare `mem.Object.(*ast.Identifier)` name check, no parser/resolver changes needed). Both functions are thin wrappers: `parse` allocates a fresh map via `__kml_map_str_create` and calls the existing `__kml_http_parse_query`; `stringify` shares its entire body with `URLSearchParams.toString()` via a newly extracted `emitMapStrToQueryString(mapPtr string) (Value, error)` helper.

## Implementation notes

- `codegen/llvm/emit_url.go`: `emitURLSearchParamsToString` split into a thin wrapper (resolves `objExpr` to a map pointer, then calls the shared helper) and the new `emitMapStrToQueryString(mapPtr string)`, which holds the percent-encode-and-join loop unchanged. No behavior change for `URLSearchParams.toString()` itself.
- `codegen/llvm/emit_querystring.go` (new): `emitQuerystringParse`/`emitQuerystringStringify`.
- `codegen/llvm/emit_call.go`: dispatch block for `id.Name == "querystring"` (`parse`/`stringify`), placed right after the existing `os` block.
- `codegen/llvm/emit_exprs_types.go`: `inferExprType` cases for `querystring.parse` (→ `MapType(TypePtr, TypePtr)`) and `.stringify` (→ `TypePtr`), placed alongside the existing `fs`/`path`/`os` cases.
- `querystring.stringify` rejects a non-`Map` argument with a compile error (`inferExprType(args[0]).IsMap` check) before calling `resolveMapOrSetForCall`, rather than letting a type mismatch surface as a confusing downstream IR error.

## Side effects discovered

None — no bugs hit in the existing `URLSearchParams`/`req.query` machinery this reuses.
