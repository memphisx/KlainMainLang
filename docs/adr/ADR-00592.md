# ADR-00592: BigInt64Array compound element assignment

- **Relations**: Extends [ADR-00313](ADR-00313.md), [TDD-00101](../tdd/TDD-00101.md)
- **Date**: 2026-09-01

## Context

`a[0] += 1n` on a `BigInt64Array`/`BigUint64Array` element was a clean rejection
("load, compute, and assign instead") — the only compound-assignment gap left on
these arrays, whose elements are stored as raw i64/u64 but are semantically
bigints.

## Decision

Handle the compound form by round-tripping through the bigint runtime: load the
raw i64 element, wrap it into a bigint (`__kml_bigint_from_i64` for
`BigInt64Array`, `__kml_bigint_from_u64` for `BigUint64Array` — chosen by the
element type's signedness), apply the operator via `emitBigIntBinary`, then store
the result back through the existing `coerceTypedArrayStore` unwrap. A non-bigint
right-hand side is a clean compile error (the spec's TypeError).

Additionally, `console.log` of a whole `BigInt64Array`/`BigUint64Array` now shows
the `n` suffix on each element: `emitInspectArray` wraps each raw element into a
bigint (signed/unsigned per the element type) before formatting, so the `IsBigInt`
inspect path adds the suffix. (Node's `TypeName(len)` prefix on typed-array prints
stays a separate, general omission.)

## Verification

`TestE2EBigInt64ArrayCompoundAssign` (`+=`, `-=`, `*=` on `BigInt64Array`, `+=`
on `BigUint64Array`) and the whole-array `n`-suffix print, compared byte-for-byte
against Node v26. The existing TypedArray suite still passes. Built and verified
on Mac (Apple Silicon).
