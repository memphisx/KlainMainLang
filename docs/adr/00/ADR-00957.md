# ADR-00957: Array.from array-like `{ length: n }` overload (+ map/flatMap index-inference fix)

- **Date**: 2026-09-15

## Context

`Array.from({ length: n }, (_, i) => …)` — the idiomatic "build a range/sequence
of length n" pattern — was rejected: `Array.from argument is not iterable`. Only
the iterable forms (array, Map, Set, string, class with `next()`) and the 2-arg
`(iterable, mapFn)` form were implemented; the array-like (object-with-`length`)
overload was unbuilt (BACKLOG §4).

## Investigation

`emitArrayFrom` (`codegen/llvm/emit_arrays_iter.go`) already desugars the 2-arg
form to `Array.from(src).map(mapFn)`, so only the single-arg path needed to accept
an array-like and produce the source array. The spec's array-like protocol reads
`length`, coerces via ToIntegerOrInfinity, clamps to `max(0, …)`, then reads keys
`0..length-1`. The dominant real-world use is the undefined-fill case
(`{ length: n }` with no indexed props), which is what this builds; indexed
array-like props (`{ length: 2, 0: 'a' }`) are out of scope (documented).

The element universe is the NaN-boxed `any` slot (TDD-00076/TDD-00200), so an
omitted element is the boxed `undefined` sentinel (`nbUndefined`) — a faithful
hole read (`typeof` "undefined", `=== undefined` true, `=== null` false).

While verifying the example, `Array.from({ length: 5 }, (_, i) => i * i)` rendered
`5e-324` denormals. This reproduced on a plain array too:
`const s = [5,6].map((_, i) => i * i); s[1]` → `5e-324`, but the inlined
`[5,6].map((_, i) => i * i).join(",")` was correct, and `(x) => x * x` /
`(a, b) => a * b` / `(_, i) => i * 1` were all correct. The tell: only the
*variable-bound* result, and only when the index param appears on *both* sides of
an arithmetic op.

Root cause: `emitArrayMap` hints its callback `[elemTy, TypeI64]` (both element
and index) at codegen (`emit_arrays_hof.go:16`), but the `inferExprType` `map`
case (`emit_exprs_types.go:2960`) passed only `hofElemHint(mem.Object)` — the
element hint. An unhinted param defaults to `TypeF64` (`callbackReturnType`,
line 466), so the index `i` inferred as float, `i * i` inferred `TypeF64`, and the
bound variable's type became `float[]` while codegen actually stored `i64`. Reads
through the mis-typed variable bit-cast the i64 to double → `5e-324`. `flatMap`
had the identical one-hint inference (line 3008).

## Decision

1. **Array-like overload**: in `emitArrayFrom`, add a branch for
   `srcTy.IsObject && !srcTy.IsArray && !srcTy.IsClass && !srcTy.IsTuple` with a
   `length` field. Load `length`, coerce to i64, clamp negatives to 0, `malloc`
   `n * 8`, and a runtime loop stores `nbUndefined` into each slot; return an
   `any[]`. Mirror the same return type in `inferExprType`'s `Array.from` case.
2. **map/flatMap index-inference fix**: pass `TypeI64` as the second hint to
   `callbackReturnType` in both the `map` and `flatMap` cases of `inferExprType`,
   matching the codegen callback hints.

## Implementation notes

- The class branch had to be excluded explicitly — a class type is also
  `IsObject`, so an unguarded object branch stole `Array.from(new Counter())` and
  broke three existing iterator tests. Tuples excluded for the same reason
  (their fields are positional "0","1",…, no `length`).
- The array-like `length` field is read by index via `FieldIndex("length")` +
  gep, not `obj.length` member access — the latter is intercepted by the
  array/string `.length` path (a separate, pre-existing collision on objects with
  a field literally named `length`).

## Side effects discovered

- **`any[]` literal `=== undefined` / `=== null` returns false** (BACKLOG §3
  any-equality): a genuine `[undefined, …]` literal element compares unequal to
  `undefined`, though `typeof` and printing render it correctly. The array-like
  path (which stores `nbUndefined` directly) is correct; the literal-boxing path
  is not. Distinct pre-existing bug in the D1 NaN-box any-eq subsystem
  (TDD-00155), not fixed here.
- Indexed array-like properties (`{ length: 2, 0: 'a' }`) are not read — the
  undefined-fill subset only.
