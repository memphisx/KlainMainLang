# ADR-00689: Promise.any value fidelity and Promise.allSettled result shape

- **Relations**: `Extends ADR-00073, ADR-00683`, `Implements TDD-00016`
- **Date**: 2026-09-04

## Context

Two Promise-combinator bugs surfaced while exercising the combinator paths with
mixed-outcome inputs:

1. `Promise.any` returned garbage for a numeric fulfillment value. Repro:

   ```ts
   async function m() { return await Promise.any([Promise.reject('x'), Promise.resolve(2)]); }
   m().then(v => console.log(v));
   ```

   printed `4611686018427387904` (the bit pattern of `double` 2.0 reinterpreted
   as `i64`) instead of `2`. A string winner already worked.

2. `Promise.allSettled` produced the wrong per-element object shape. Repro:

   ```ts
   async function m() { return JSON.stringify(await Promise.allSettled([Promise.resolve(1), Promise.reject('e')])); }
   m().then(v => console.log(v));
   ```

   emitted
   `[{"status":"fulfilled","value":1,"reason":null},{"status":"rejected","value":0,"reason":{...Error...}}]`
   where Node gives `[{"status":"fulfilled","value":1},{"status":"rejected","reason":"e"}]`.
   Two problems: (a) each element carried both `value` and `reason`; (b) a
   rejected `reason` was a synthetic Error wrapper, not the raw thrown value.

## Investigation

- `promiseArrayElemType` (`codegen/llvm/emit_promise.go`) derives the combinator's
  value type from `inferArrayType`, which keys the element type off the array's
  *first* element (`emit_exprs_types.go:205`). With `Promise.reject('x')` first,
  that element's resolved type is `never` (a rejected promise never yields a
  value — `TypeNever`, `types.go`), whose `IR` is `i64` and carries no
  value-encoding information. `Promise.resolve(2)` stores its winner as `double`
  bits; `loadPromiseValue`/`promiseValFromBits` (`emit_task_emit.go`) then decoded
  that slot as a raw `i64` because the inferred type said `i64`. A homogeneous
  numeric array (`[Promise.resolve(2), Promise.resolve(3)]`) worked, confirming
  the reject-first inference as the cause.
- `SettlementType` (`types.go`) is a fixed `{status, value, reason}` struct (this
  compiler has no optional fields), so `emitJSONStringifyObject` walked all three
  keys unconditionally. ADR-00683 had already made an unset slot serialize as
  `null` rather than crash, but real JS omits the inapplicable key entirely.
- The rejected `reason` was built with `buildErrorObj`/stored as an Error object.
  The rejection model wraps every thrown value in an Error carrying its string
  form in `.message` (confirmed: `catch (e)` of `Promise.reject(42)` yields an
  Error object, not `42` — a pre-existing, compiler-wide divergence, not specific
  to allSettled).

## Decision

1. **Promise.any value type**: in `promiseArrayElemType`, when the inferred inner
   type is `never`/`void` and the argument is an array literal, scan the literal
   for the first concrete (non-`never`, non-`void`) member `Promise<T>` and adopt
   its `T`. This mirrors faithful TS, which widens `never` out of the element
   union. The winner value then decodes with the correct shape.

2. **allSettled shape**: serialize a settlement object specially. `isSettlementType`
   detects the `{status, value, reason}` shape structurally (no new `Type` flag),
   and `emitJSONStringifySettlement` emits only `status` plus, chosen at runtime
   from the `status` discriminant, either `value` (fulfilled) or `reason`
   (rejected). The discriminant is a pointer-equality check against the interned
   `"fulfilled"` constant (`internString` dedups, so a fulfilled entry's slot
   holds that exact pointer) — no string compare.

3. **allSettled raw reason**: store the raw rejection value's string form as
   `reason` instead of the Error wrapper. The task path recovers it from the
   stored Error's `.message` (`loadErrorMessage`); the fetch/Response path stores
   its transport-failure message string directly. The settlement JSON path reads
   the `reason` slot as a string.

## Implementation notes

- Files touched: `codegen/llvm/emit_promise.go` (element-type widening,
  `loadErrorMessage`, both rejected-branch reason stores) and
  `codegen/llvm/emit_call_json.go` (`isSettlementType`,
  `emitJSONStringifySettlement`, hook in `emitJSONStringifyObject`).
- The settlement JSON branch uses an alloca-slot merge (the same pattern
  `emitJSONStringifyValue`'s null-object branch uses) rather than a `phi`, so the
  per-branch string-concat accumulators don't need explicit block-label capture.
- No change to `SettlementType`'s struct: a string pointer is stored into the
  `reason` slot (nominally `errorObjType`, IR `ptr`), which is layout-compatible;
  only the settlement JSON path reads it, and it reads it as a string.

## Side effects discovered

- A non-string rejection `reason` in allSettled is serialized via its string
  form: `Promise.reject(42)` gives `"reason":"42"` (quoted) and
  `Promise.reject(new Error("boom"))` gives `"reason":"boom"`, where Node gives
  `42` and `{}` respectively. This follows from the compiler-wide rejection model
  that wraps every thrown value in an Error carrying its stringified form — a
  string rejection (the common case, and the repro) reproduces Node exactly.
  Full raw-reason preservation would require carrying rejection reasons as
  `any`/boxed values end to end (a much larger change to the whole throw/catch
  subsystem); deferred and recorded here as future work.

## Verification

- Both repros now match Node: `2`, and
  `[{"status":"fulfilled","value":1},{"status":"rejected","reason":"e"}]`; pretty
  mode (`JSON.stringify(..., null, 2)`) also matches.
- New E2E test `tests/promise_combinator_shape_test.go` (any reject-first numeric
  and string winners; allSettled JSON shape; allSettled property access still
  works) passes; the existing `Async|Promise|AllSettled` suite stays green.
- New example `examples/async/promise_combinator_shape.ts` runs with the expected
  output. `go build` and `go vet ./codegen/llvm/` are clean.
