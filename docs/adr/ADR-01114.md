# ADR-01114: Overload signatures kept in the AST, and overload resolution in the checker

- **Relations**: `Implements TDD-00230` (Phase 2, P2.6); `Extends ADR-01113`
- **Date**: 2026-09-24

## Context

[TDD-00230](../tdd/TDD-00230.md) P2.6 resolves a call against its
overloads in declaration order: arity, then inference, then applicability.
The parser erases overload signatures (`function f(x: string): number;`
before the implementation) and returns only the implementation, so the
checker saw only the implementation's signature. TypeScript hides that
signature from callers: `conv('a')` against `(x: string): number` and
`(x: number): string` is `number`, never the implementation's
`string | number`.

## Investigation

- **`parser/parser_stmts.go`** (a function's overload group) and
  **`parser/parser_classes.go`** (a method's) verify that an
  implementation follows its signatures, then drop the signatures.
- **Codegen** never reads a signature. The reflective AST walkers in
  codegen (`fnmeta.go` names values from declarations, assignments and
  parameter defaults; `emit_stackalloc.go` scans a function body) find
  nothing to act on in a body-less signature.
- **typescript-go** (`chooseOverload`) tries the candidates in order.
  Arity comes first, then type argument inference for a generic candidate,
  then each argument's assignability. If no candidate fits, the call is
  error TS2769.
- **tsc 5.6.3 `--strict`** confirms the test expectations:
  - `conv('a')` is `number` and `conv(1)` is `string`;
  - `opt(1)` is `number` and `opt(1, 'x')` is `string`;
  - a generic overload `gen<T>(x: T[]): T` gives `gen([true])` as
    `boolean`;
  - an overloaded method dispatches the same way;
  - `conv(u)` with `u: string | number` is TS2769.

## Decision

- **The parser keeps the signatures:**
  `FunctionDeclaration.Overloads` lists an implementation's overload
  signatures in source order, for a function and for a method. The field
  is excluded from the generated AST walker (`ast/gen`), and from its
  reflection oracle test, because signatures carry no code. Every walker
  therefore still sees only the implementation, as before.
- **An overloaded function's type is its signatures**, in order (the
  implementation's is not callable from outside). A generic signature's
  type parameters are named through the checker's type environment, since
  the binder never visits a signature. The type prints as tsc prints an
  overloaded function: `{ (x: string): number; (x: number): string }`.
- **A call resolves to the first signature that fits:** arity (required
  parameters, optional ones, a rest), then inference for a generic
  signature, then each non-callback argument assignable to its parameter.
  An argument the checker cannot type leaves the call unanswered, since
  the pick could depend on it, and so does a call no signature fits
  (TS2769, P2.7's to report).
- **Assignability** (`checker/overloads.go`) is TypeScript's relation for
  the types the checker models:
  - `any`, `unknown` and `never`;
  - unions on either side;
  - literals to their primitive, and the native widths as numbers;
  - `void` to `undefined`;
  - a type parameter through its constraint;
  - arrays, tuples and function types (arity and result);
  - class instances by derivation, else structurally;
  - object types structurally, where optional properties may be absent.

  It is the relation overload applicability needs. It is not yet the full
  checker relation (excess properties, `satisfies`, variance).

## Implementation notes

- **Changed:**
  - `ast/nodes.go` (`Overloads`), `ast/gen/main.go` and the regenerated
    `ast/walk_generated.go`, `ast/walk_test.go`;
  - `parser/parser_stmts.go` and `parser/parser_classes.go`;
  - `checker/types.go` (a function type's `Overloads`, printing);
  - `checker/symbols.go` (overloaded functions and methods; a signature's
    type parameters from the environment);
  - `checker/checker.go` (calls).
- **New:** `checker/overloads.go`; the tests are in
  `checker/generics_test.go`.
