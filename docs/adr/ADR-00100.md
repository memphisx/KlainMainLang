# ADR-00100: Fix `-mm=gc` startup crash under AddressSanitizer, and add ASan/UBSan test-build helpers

- **Relations**: Extends [ADR-00071](ADR-00071.md) (`-mm=gc`), [ADR-00080](ADR-00080.md) (the previous earliest-known pre-constructor-malloc crash, same general class of bug)
- **Date**: 2026-08-05

## Context

Asked to make AddressSanitizer/Valgrind available for future memory-corruption debugging (following up on [ADR-00099](ADR-00099.md)'s unresolved `-mm=gc` clustering hang, where better tooling was identified as the likely next step). Valgrind needed a system package install the user had to run themselves (`sudo apt install valgrind`, no passwordless sudo available); ASan needed no install (bundled with the already-installed `clang`, verified directly via `clang -fsanitize=address`) but needed real testing before it could be considered usable.

## Investigation

Added `buildBinaryASan`/`buildBinaryGCASan` test helpers (`tests/compiler_test.go`, mirroring `buildBinary`/`buildBinaryGC`) and smoke-tested both before trusting them for real debugging:

- **`buildBinaryASan` (manual mode)**: a trivial program reported `LeakSanitizer: detected memory leaks`. Confirmed this is an expected false positive, not a bug: this project's `manual` memory mode never frees by design (`CLAUDE.md`: "every heap allocation is malloc'd and (almost) never freed"). Fixed by baking `detect_leaks=0` into the binary itself via ASan's `__asan_default_options()` hook (a small `asan_options.c` compiled alongside, `const char *__asan_default_options(void) { return "detect_leaks=0"; }`) rather than relying on callers remembering an `ASAN_OPTIONS` env var. Actual corruption checks (heap-buffer-overflow, use-after-free, all of UBSan) are unaffected.
- **`buildBinaryGCASan` (gc mode)**: a *trivial* `console.log("hello")` program segfaulted before printing anything, 100% reproducibly. This was the real finding.

Root-caused via direct `gdb` backtraces (not guessed), through two rounds since the first hypothesis was wrong:

1. First backtrace pointed at `ensureGCStackbottomSet()`'s read of `__libc_stack_end` (`gcshim.c:48` at the time). Tested `__attribute__((no_sanitize("address)))` on that function alone — still crashed, ruling out "ASan's own instrumentation mis-firing on this read" as the cause.
2. Tested removing the `__libc_stack_end` read entirely (a minimal repro with `ensureGCStackbottomSet` reduced to a no-op) — **still crashed**, proving the first backtrace's blamed line wasn't the real culprit; gdb had stopped at the first frame in *this* function, not necessarily the actual origin.
3. A fresh backtrace on that reduced repro showed the true chain: `_dl_start_user` → `_dl_init` (the dynamic linker's own constructor-running phase, *before* `__libc_start_main` even runs) → `__asan_init` → `InitializeAsanInterceptors` → `dlsym()` hunting for `__isoc99_printf` to wrap → dlsym's own internal error-formatting path (it didn't find the symbol via the fast path) → `malloc(144)` for the error message → this shim's `malloc()` → `GC_malloc_kind()` (inside `libgc.so.1`) → `__tls_get_addr()` → **crash at address `0x0`**, inside `__interceptor___tls_get_addr` — ASan's own interceptor for thread-local-storage access, called from *inside* the very function (`InitializeAsanInterceptors`) that's still in the process of installing it. A genuine circular bootstrap dependency: Boehm's allocator needs TLS, ASan hasn't finished wiring up its TLS interceptor yet, and the trigger for reaching Boehm at all is ASan's *own* startup calling `malloc()`.

This is a strictly earlier and different trigger than [ADR-00080](ADR-00080.md)'s `libp11-kit`-constructor case: it happens during the dynamic linker's own init, before `__libc_start_main` has even set `__libc_stack_end`, and the crash is inside Boehm's own TLS access, not anything `gcshim.c` touches directly — no amount of stackbottom-setting logic could have avoided it.

ADR-00080 explicitly considered and rejected a bump allocator for its own (later, milder) trigger, because `pthread_getattr_np`'s `/proc/self/maps` read needs a *growing* buffer via `realloc`, which a naive bump allocator can't serve without real per-block size tracking. Confirmed that rejection doesn't apply here: every pre-constructor allocation actually observed (both this new ASan case and the original `libp11-kit` case) is small and one-off, never grown or freed within the narrow pre-constructor window — exactly what a fixed bump buffer handles fine.

## Decision

Added a small (64KB), fixed-size, no-real-free bump allocator (`preCtorBump`/`bumpAlloc`/`isBumpPtr`, `gcshim.c`) serving every `malloc`/`calloc`/`realloc`/`free` call that happens *before* `__kml_gc_ctor` has actually run (tracked via a new `ctorDone` flag, set at the end of the constructor). Once `ctorDone` is true, allocations go through the unchanged `ensureGCStackbottomSet()` + `GC_malloc`/`GC_realloc`/`GC_free` path exactly as before. Falls through to real `GC_malloc` if the bump buffer is ever exhausted pre-constructor (not fully safe in that case, but no worse than before this fix existed, and never observed to happen).

This is a genuine improvement beyond just fixing ASan: it also simplifies the invariant `GC_INIT()` is called under. Previously, `GC_INIT()` (via `ensureGCStackbottomSet`'s lazy call) could run from *whichever* code happened to call `malloc()` first — this project's own constructor, or a transitive dependency's, in either order. Now `GC_INIT()` unconditionally runs from `__kml_gc_ctor` only, in a single, known-safe, non-reentrant context; every earlier allocation (from any source) is transparently served by the bump buffer and never touches Boehm at all.

Also added, since getting `buildBinaryGCASan` working was the actual point of this work: `buildBinaryASan`/`buildBinaryGCASan` (`tests/compiler_test.go`) as opt-in debugging helpers — not part of the regular `go test ./...` run (ASan roughly doubles memory/time cost), for a specific future investigation to call deliberately. `-O1 -g -fno-omit-frame-pointer` matches ASan's own documented recommendation for accurate stack traces.

## Implementation notes

Files touched: `codegen/llvm/gcsrc/gcshim.c` (the bump allocator, `ctorDone` flag), `tests/compiler_test.go` (`buildBinaryASan`, `buildBinaryGCASan`, `asanOptionsSource`).

Valgrind itself was not installed in this pass (needs the user's own `sudo apt install valgrind`, communicated separately) — this ADR covers only the ASan side, which needed no install and was the one that turned out to need a real fix before it was usable at all.

## Side effects discovered

None beyond the crash itself — this pass was specifically about getting the tooling working, not chasing the still-open [ADR-00099](ADR-00099.md) clustering hang with it (that's the natural next step now that `buildBinaryGCASan` actually works, not done as part of this ADR).

## Verification

- `go build -o klainmain .`, `go vet ./...`, `go test ./...` — clean, no regressions.
- `buildBinaryASan`: a trivial program (array sum + string concat) runs clean under `-fsanitize=address -fsanitize=undefined` with zero false-positive leak reports (confirmed both with and without the `detect_leaks=0` fix, to verify the fix actually changes the outcome rather than the test being vacuous).
- `buildBinaryGCASan`: the same trivial program, confirmed crashing 100% reproducibly before the bump-allocator fix (`gdb` backtrace captured both before and after fixing the wrong first hypothesis), confirmed passing cleanly after. Additionally verified against a real allocation-heavy workload (200,000-iteration string-concatenation churn, matching the scale used elsewhere in this project's own GC test suite) — runs clean, correct output, confirming the fix holds under real GC pressure, not just at trivial-program startup.
