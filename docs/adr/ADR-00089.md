# ADR-00089: `EventEmitter<T>` (`events` module)

- **Relations**: Extends ADR-00083. Implements TDD-00023.
- **Date**: 2026-08-03

## Context

`docs/status/EVENT-EMITTER.md` tracked Node's `EventEmitter` at 0/6 coverage, flagged as "a bigger prerequisite than it looks" since Node's `stream` module, event-driven `readline`, and async `child_process` are all built on top of it. This work closes that gap. Requested directly by the user as the next feature after reviewing the project roadmap; `os` module was deferred to the following iteration.

Two design decisions were made with the user before implementation (see [TDD-00023](../tdd/TDD-00023.md) for the full design pass):

1. **Payload model**: `EventEmitter<T>`, a compiler-recognized generic built-in (the same monomorphized-per-`T` pattern `Map<K,V>`/`Set<T>`/`Promise<T>` already use), not real Node's fully-variadic `emit(event, ...args)` — this compiler has no working `any[]`/call-site array spread/heterogeneous rest parameters to build that on.
2. **`class X extends EventEmitter<T>` in scope**, integrated with the real class-inheritance machinery from ADR-00083 rather than deferred to a later pass or restricted to composition.

## Investigation

Read `emit_collections.go`/`runtime_collections.go` (`Map<K,V>`'s value storage), `emit_classes.go`'s `registerClasses`/`ClassInfo`/`emitNewExpression`/`emitClassCall` (the inheritance/vtable/hidden-tag-field machinery from ADR-00083), `emit_func.go`'s closure-header/trampoline shape, `emit_timers.go`'s `timerCallbackPtr` (existing closure-argument validation precedent), and `emit_exceptions.go`'s `buildErrorObj`/`emitThrow`/`emitValueToString`.

Two things initially assumed turned out to need correction during design, both caught before writing code (see TDD-00023's Design section for detail):

- Assumed `Map<K,V>`'s value storage would need modification to hold a listener list — turned out unnecessary. A listener list is its own small heap struct; the *map's value* is just a `ptr` to that struct, a single word, which `Map`'s existing `ptrtoint`/`inttoptr` value storage already handles for any pointer-shaped value type with zero changes.
- Confirmed (via `docs/status/LANGUAGE-CONSTRUCTS.md` and direct grep of `emit_func.go`/`emit_call.go`) that rest parameters are homogeneous-single-type-only, call-site array spread (`f(...arr)`) is unimplemented, and `any`/`unknown` is a hard compile error as a parameter/array-element type — ruling out a real variadic `emit(event, ...args)` for V1.

## Decision

`EventEmitter<T>` is a `Type.IsEventEmitter` marker (deliberately **not** also setting `IsMap`, unlike `IsURLSearchParams` — EventEmitter's method surface shares no names with Map's, and letting `.get()`/`.set()`/`.forEach()` leak onto an EventEmitter value would be a real, silent correctness gap). Storage-wise the underlying pointer is layout-compatible with `__kml_map_str_create()`'s result, and the existing `__kml_map_str_*` helpers are called directly by name from new EventEmitter-specific codegen — no changes to `Map`'s own implementation.

Each event's listener list is its own heap struct: `{i64 len, i64 cap, ptr data}` header (mirroring Map's own header field order for consistency), each entry `{ptr listener, i64 once}` (16 bytes).

`class X extends EventEmitter<T>`: `EventEmitter` is never registered in `e.classes` — no vtable slot, no `TagID`, not `instanceof`-checkable, consistent with `Error`/`Date`/`Map` today. `registerClasses`' Pass 0 treats `extends EventEmitter<T>` as a synthetic root (validates exactly one type argument, no recursion into `classDeclByName`); Pass 1's `haveBase` excludes `EventEmitter`, so a directly-extending class flows through the existing "root class, no base constructor to forward through `super(...)`" rules unchanged. A third hidden struct field, `__kml_ee_listeners`, is injected after the existing tag/vtable fields — the second generalization of that positional-hidden-field scheme (Stage 2→3 was the first). `HasEventEmitter`/`EventEmitterPayload` propagate down an inheritance chain the same way `HasVTable`/`RootClass` already do. A class in an EventEmitter-rooted tree declaring any of EventEmitter's own method names (`on`/`once`/`emit`/`off`/`removeListener`/`removeAllListeners`/`listenerCount`/`eventNames`) is a compile-time reserved-name-collision error — this is what keeps "override an EventEmitter method" out of scope by construction, with no vtable-interaction design needed.

`once()`: a flag alongside the raw listener pointer in each list entry, not a wrapper closure — a wrapper would break `.off()`'s identity-based removal (a caller's own reference to the original listener would never match a synthesized wrapper). `.emit()` snapshot-copies the listener list before invoking (so a `.once()` entry removing itself mid-loop can't perturb indices not yet visited), invokes every entry via the standard closure-call trampoline (`emitCBCall`), removes once-flagged entries from the *real* list afterward.

`emit('error', data)` unlistened-throws: resolved entirely at the `.emit()` call site's own IR — a `strcmp` against the literal `"error"`, gated on "zero listeners were invoked." The throw path branches at Go-compile-time (not runtime — `T` is fixed per instantiation) on `payloadTy.IsError`: an `EventEmitter<Error>` rethrows the exact payload object via `__kml_throw` directly; any other `T` stringifies the payload and wraps it in a base-Error-shaped object via the existing `buildErrorObj`/`emitValueToString`, the same fallback `emitThrow` already applies to a thrown string/number.

## Implementation notes

New files: `codegen/llvm/emit_eventemitter.go` (Go codegen — var decl, dispatch, `on`/`once`/`emit`/`off`/`removeListener`/`removeAllListeners`/`listenerCount`/`eventNames`), `codegen/llvm/runtime_eventemitter.go` (hand-written IR-text helpers: `__kml_ee_list_create`/`_push`/`_remove`).

Modified: `codegen/llvm/types.go` (`EventEmitterType`, `ClassEventEmitterField`, `ClassType`/`VisibleFields` generalized to a 3rd hidden field — this changed `ClassType`'s signature, a breaking Go-level change caught immediately by `go build` at all 3 real call sites in `emit_classes.go`), `codegen/llvm/emit_classes.go` (`registerClasses` Pass 0/1, `ClassInfo`, `emitNewExpression`), `codegen/llvm/emit_call.go`/`emit_exprs_types.go` (dispatch + type inference, both a standalone-receiver branch and a class-embedded-receiver branch sharing one `emitEventEmitterCall` core), `codegen/llvm/emitter.go` (`EventEmitter<T>` type-annotation resolution), `ast/nodes.go` (`NewEventEmitterExpression`, `ClassDeclaration.BaseTypeArgs` — the latter changed `NewClassDeclaration`'s signature, one call site in `parser/parser_classes.go`), `parser/parser_classes.go`/`parser_literals.go`/`parser_types.go` (`extends EventEmitter<T>`, `new EventEmitter<T>()`, `EventEmitter<T>` as a type annotation).

Listener-argument validation (`resolveEventEmitterListenerArg`) generalizes `timerCallbackPtr`'s arity-0 validation to arity-1 + a payload-type match, and propagates the payload type as a hint into an untyped arrow-function parameter via `emitArrowFunctionWithHints` (the same mechanism Map/Set's own `forEach` callbacks already use) — so `e.on('x', data => ...)` needs no explicit parameter annotation. Deliberately restricted to real closures (arrow functions or closure-typed variables), same as `timerCallbackPtr` — a bare reference to a top-level named function has no runtime pointer representation to store for `.emit()` to invoke later from a different call site.

Non-obvious ordering constraint: `emitNewExpression`'s listener-map construction must happen before the constructor call, so a constructor body that itself calls `this.emit(...)`/`this.on(...)` sees an already-initialized map.

## Side effects discovered

A real bug found and fixed while writing the `EventEmitter<Error>` test: the initial `EventEmitter<T>` payload-type resolution only special-cased `T = Error` in `emitter.go`'s general type-annotation resolver (`EventEmitter<T>` appearing as a declared type elsewhere), but `new EventEmitter<T>()`'s own construction path (`emitEventEmitterVarDecl`) resolves its type argument independently and was missed — so `new EventEmitter<Error>()` silently defaulted `T` to `TypeI64` instead of `errorObjType`, later surfacing as a confusing `"cannot convert type ptr to string in template literal"` error from an unrelated-looking code path (`emitValueToString`'s generic fallback, reached because `payloadTy.IsError` was false when it should have been true). Fixed by factoring a single shared `resolveEventEmitterPayloadType` helper used by all three call sites (`new EventEmitter<T>()`, `EventEmitter<T>` as a type annotation, `extends EventEmitter<T>`) instead of duplicating (and getting out of sync) the `"Error"` special-case in each.

`"Error"` remains deliberately *not* a resolvable type-annotation name in general (per `emitErrorInstanceOf`'s existing doc comment in `emit_classes.go`, an invariant about a *Nullable* Error-typed value never arising) — this fix is narrowly scoped to the one `EventEmitter<T>`-payload position, not a general `ResolveTypeName` change, so that invariant still holds everywhere else.

No other new bugs found in already-shipped code.
