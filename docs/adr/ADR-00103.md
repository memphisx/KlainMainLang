# ADR-00103: User-defined generics V1 — monomorphization for functions, interfaces, classes

- **Relations**: Implements [TDD-00010](../tdd/TDD-00010.md)
- **Date**: 2026-08-05

## Context

[TDD-00010](../tdd/TDD-00010.md) scoped user-defined generics as a two-phase design: V1 monomorphizes unconditionally; V2, deferred, adds a JSDoc opt-in (`@erased`) into type erasure for cases V1 handles badly. This ADR implements V1. Per a scoping decision made at the start of this work, V1's scope was widened beyond the TDD's original title ("functions and interfaces") to also include generic classes, since all 5 stages of class support (TDD-00009) are now fully implemented and architecturally ready for it — scoped down significantly relative to a plain class (see Decision).

`docs/status/README.md`/`TYPE-SYSTEM.md` tracked "No user-defined generics" as the sole remaining gap in `Type system features`; `function identity<T>(x: T): T {...}` and `interface Box<T> { value: T }` both previously failed with a clean parse error (`expected (, got <` / `expected {, got <`), confirmed in TDD-00010's own Context section.

## Investigation

Read `codegen/llvm/types.go`'s existing generic-adjacent helpers (`ArrayOf`/`MapType`/`SetType`/`PromiseOf`) and confirmed they build a fresh, uncached `Type` value per call — "monomorphization" for the built-ins is Go-side type distinctness only, not a distinct emitted LLVM symbol per instantiation. The one real name-mangling precedent in the codebase is classes (`@ClassName_methodName`).

Read `emitter.go`'s `registerFunctions`/`registerInterfaces`/`registerClasses` (all three walk the whole merged program once, before any body is emitted) and `emit_func.go`'s `emitFunctionDecl` (already reuses a pre-registered `FuncSig` rather than recomputing it) — confirmed the codebase already had the exact separation needed (signature registration vs. body emission) to build on.

Considered the TDD's literal "collect every instantiation, then emit" two-pass design vs. **on-demand (lazy) specialization during the single existing emission pass**. Chose the latter: `resolver.ResolveProgram` already merges the whole program before codegen runs, and LLVM IR text tolerates a call site referencing a function defined later in the same module (only the final module's symbol table matters, not textual order) — so a generic call/usage site can evaluate its own argument's real type, build a mangled name, and emit the specialization right there, reusing `emitFunctionDecl`'s/`emitClassDecl`'s existing save-and-restore-emitter-state machinery (already proven safe to call mid-emission of something else). This avoids a second, independent "type-only" shadow walker that would have to duplicate `inferExprType`'s scope-aware logic — a real duplication/drift risk a literal two-pass implementation would have introduced.

## Decision

**V1 scope, uniformly**: exactly one, unconstrained type parameter (`<T>`, not `<T, U>` or `<T extends Base>`) — TDD-00010's own open questions marked multi-param/constrained generics as follow-ons.

**Generic functions** — inference-only, matching the TDD: `identity<T>(x: T): T` infers `T` from whichever argument lines up with a parameter typed `T` (or `T[]`, inferring from the array's element type); a generic function with no parameter typed `T`/`T[]` (e.g. `make<T>(): T`) is rejected at the first call site with a clear error, since explicit call-site type arguments (`identity<number>(5)`) are out of V1 scope (the `a<b>(c)` grammar ambiguity the TDD already identified). Accepted concrete types: `number`, `string`, `boolean`, and arrays of these — `mangleTypeArg` (`emit_generics.go`) rejects anything else (object/class/Map/Set/Promise/closure) with a clear error naming the type argument as unsupported.

**Generic interfaces** — structural, reusing the exact single-type-parameter parsing branch `Promise<T>`/`Array<T>`/`Set<T>`/`EventEmitter<T>` already used (`parser_types.go`'s `parseTypeAnnotation`), storing the parsed argument into the existing `TypeAnnotation.ElemType` field rather than adding a new one. `resolveType` gets one more early branch (alongside the existing Promise/Map/Set/EventEmitter checks) recognizing a registered generic interface name and substituting the concrete type into its declared fields via `ObjectType` — the existing TDD-00007 field-coercion machinery then works unchanged.

**Generic classes** — explicit `new Box<number>(...)` syntax, not inference: unlike a bare call, `new` unambiguously starts a constructor call, so there's no grammar ambiguity to avoid (the same reasoning that already lets `extends EventEmitter<T>` and `new Map<K,V>()` parse real type arguments). Deliberately out of V1 scope: `extends` on/targeting a generic class, `implements`/`abstract`, static fields/methods/blocks, and `instanceof` against a bare generic name — `registerClasses` rejects all of these at registration time with a clear error, before a generic class declaration is ever entered into `e.genericClasses`. Each concrete instantiation (`Box__number`, `Box__string`) is a full, independent `ClassInfo` with its own runtime tag (continuing `registerClasses`' own `TagID` sequence via a new `e.nextClassTagID` field, so a generic instantiation's tag can never collide with an unrelated real class's), never `HasVTable` (no inheritance possible).

**Mangling**: `<declName>__<suffix>` (double underscore, matching `emit_classes.go`'s `ClassName_methodName` style) — `num`/`str`/`bool`, with `arr` appended per array level (e.g. `identity__numarr`).

**Pure vs. impure split** (found necessary during implementation, not anticipated in the TDD): `inferExprType` and `emitVarDecl`'s own pre-inference type switch must never trigger real emission as a side effect of merely asking "what type is this expression" — both are called speculatively/repeatedly elsewhere in the emitter. Every generic-instantiation entry point therefore has two forms: a pure one (`genericClassInstanceType`, `inferGenericCallConcreteType`, `genericCallReturnType`) that only computes a `Type`/mangled name via the shared pure core (`genericClassMangledFields`, `substituteGenericType`), and the real, memoized, body-emitting one (`instantiateGenericClass`, `instantiateGenericFunc`) called only from the actual call/construction site (`emit_call.go`'s dispatch, `emitNewExpression`).

## Implementation notes

- **AST**: `FunctionDeclaration.TypeParams`, `InterfaceDeclaration.TypeParams`, `ClassDeclaration.TypeParams []string`; `NewExpression.TypeArgs []*TypeAnnotation` (`ast/nodes.go`).
- **Parser**: a shared `parseTypeParamList` helper (`parser/parser.go`, next to `expectGT`) used by `parseFunctionRest` (`parser_stmts.go`), `parseInterfaceDecl` (`parser_types.go`), and class-decl parsing (`parser_classes.go`); `parseTypeAnnotation`'s former "skip any other generic" fallback branch now parses one type argument into `ElemType` instead of discarding it (`parser_types.go`); `parseNewGenericBody` (`parser_literals.go`) parses an optional `<TypeArg>` before the argument list.
- **Codegen**: new `codegen/llvm/emit_generics.go` holds all generics-specific logic. `emit_func.go`'s `emitFunctionDecl` was refactored into a thin wrapper around a new `emitFunctionDeclAs(decl, llvmName, sig)` (two previously-hardcoded `decl.Name` `WriteString` call sites now take the passed-in name) — the same shape `emit_classes.go` already had via `emitClassMember` (already fully parameterized, no changes needed there beyond a new `emitClassDeclAs` sibling to `emitClassDecl`). `emit_call.go`'s big inline `e.funcs[id.Name]` call-emission block was extracted into a shared `emitCallToFuncSig(name, sig, args, pos)`, called both by the existing concrete-function dispatch and by generic dispatch.
- **`Emitter` fields** (`emitter.go`): `genericFuncs`/`genericInterfaces`/`genericClasses` (raw AST, keyed by source name — deliberately never also entered into `funcs`/`interfaces`/`classes`, since `T` isn't resolvable until a real call/usage/construction site supplies a concrete type) and `nextClassTagID` (continues `registerClasses`' own tag sequence for on-demand generic-class instantiation).
- **`registerFunctions`/`registerInterfaces`/`registerClasses`** each route a `TypeParams`-bearing declaration into the new generic registry instead of computing a signature/shape that would otherwise silently resolve every bare `T` to `i64` via `ResolveTypeName`'s existing unknown-name default. `EmitProgram`'s Pass 2/2b loops (and `registerClasses`' own topological-order visit) skip `TypeParams`-bearing declarations for the same reason a generic declaration is never entered into the non-generic registries.
- **Recursion safety**: both `instantiateGenericFunc` and `instantiateGenericClass` register the signature/`ClassInfo` into `e.funcs`/`e.classes` *before* emitting the body — a direct or mutual recursive call inside the body sees the memo entry and reuses it instead of recursing into specialization again, the same principle top-level forward references already rely on (`registerFunctions` runs fully before any body is emitted).

## Side effects discovered

Three real, pre-existing bugs surfaced while testing this feature end-to-end, all fixed as part of this same piece of work (not deferred, since each was small and directly blocked verifying V1 itself):

1. **`ast.FunctionDeclaration.pos` was never set for any top-level function or class method** — `parser_stmts.go`'s `parseFunctionRest` builds the struct via a bare literal and can't reach the unexported `pos` field, and (unlike `InterfaceDeclaration`/`ClassDeclaration`) there was no `NewFunctionDeclaration` constructor to set it through. Every `decl.GetPos()` call for a function declaration returned `Pos{}` (rendered as `0:0` in error messages) since the feature shipped. Fixed via a new exported `(*FunctionDeclaration).SetPos` method (`ast/nodes.go`) and a captured position (`posOf(p.peek())`, right after the name) threaded through both of `parseFunctionRest`'s return paths.
2. **`inferExprType`'s `*ast.NewExpression` case and `emitVarDecl`'s own pre-inference type switch both looked up a class purely by its literal source name** (`e.classes[ex.ClassName]`) with no generic-aware fallback — for a *plain* class this was always correct, but it meant `const b = new Box<number>(...)` (unannotated) silently mistyped `b`'s alloca as the wrong IR before this ADR's work gave `Box<number>` anywhere real to resolve to. Not user-visible before this ADR (no generic classes existed to construct), but would have been a real, silent bug the moment generic classes shipped without this fix — addressed by the pure/impure split described in Decision.
3. **`emitVarDecl`'s pre-inference type switch never accounted for a plain string (`ptr`, non-array/object/func/date/map/set) return type** on a bare-identifier function call — confirmed with a plain, *non-generic* function (`function greet(x: string): string { return x } const y = greet("hi")`) failing at the clang stage (`'%t2' defined with type 'ptr' but expected 'i64'`), entirely unrelated to generics. Found because it also broke the single most natural generic-function usage pattern, `const y = identity("hi")`. Fixed in the same condition already handling array/object/etc. (`emit_exprs_vardecl.go`), by adding an `isStringTy(...)` check; a regression test for the plain-function case was added to `tests/func_test.go` (`TestE2EUnannotatedConstFromStringReturningFunction`) alongside the generic-specific one in `tests/generics_test.go`.

No other bugs or limitations were found beyond the V1 scope cuts already described in Decision (multi-param/constrained generics, generic-class inheritance/vtable/statics/`instanceof`, explicit call-site type arguments for functions) — all tracked as TDD-00010's own open questions / natural follow-ons, not new discoveries.

## Verification

- `go build -o klainmain .` and `go vet ./...` clean.
- `go test ./...` passes in full (`go test ./... -count=1`), including the new `tests/generics_test.go` (15 tests: multi-instantiation and memoization for functions/interfaces/classes, array-of-scalar inference, recursion, every V1 scope-cut error path) and the new regression test in `tests/func_test.go`.
- Manually inspected `--emit-llvm` output for a generic function called 3 times (2 distinct types) and a generic class constructed 3 times (2 distinct types): confirmed exactly one `define` per distinct instantiation in both cases (memoization), via `strings.Count` assertions in the corresponding tests rather than just checking program output (a wrongly-duplicated `define` for the same mangled name would otherwise still produce correct output while being a real, silent codegen bug — an actual duplicate-symbol clang failure).
- `examples/generics/generics.ts` (new) compiled and run directly via `klainmain` (`make`/`make examples` weren't available in this sandbox — no `make` binary — so this was verified by directly invoking the built `klainmain` binary instead of the Makefile target); output matched every inline expected-output comment exactly.
- Verified only on the x86-64 Linux development box (see the project's own platform-flagging rule) — this feature is pure LLVM-IR-text/Go compiler logic with no OS/libc-specific code path, so it isn't expected to be platform-sensitive, but that expectation hasn't been directly confirmed on the Apple Silicon Mac.
