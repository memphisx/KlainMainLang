# ADR-00108: `i64::MIN / -1` UB guard, and `%=` (was entirely unimplemented)

- **Date**: 2026-08-06

## Context

`docs/status/LANGUAGE-CONSTRUCTS.md`'s own Known Limitations documented a real, unfixed gap: dividing an integer type's minimum representable value by `-1` is undefined behavior at the LLVM IR level (`sdiv`/`srem` on that exact input pair), separate from the zero-divisor UB `emitDivZeroGuard` already caught (ADR-00069). Picked up at the user's explicit request to close out `docs/status/README.md`'s Operators row, alongside a broader pass to see what else in that page could be completed.

## Investigation

While tracing every `sdiv`/`srem` call site to scope the fix (`codegen/llvm/emit_exprs_operators.go`), found a second, unrelated, much more basic gap: `%=` (`PERCENT_ASSIGN`) was never a lexer token at all. `lexer/lexer.go`'s `case '%':` never checked for a following `=` the way `+`, `-`, `*`, `/` all do — confirmed directly that `x %= 3` is a parse error (`unexpected token = in expression`), not just a missing codegen path. `docs/status/LANGUAGE-CONSTRUCTS.md`'s own "Assignment operators" row claimed `%=` as done (bundled into one row with `+= -= *= /= &= |= ^= <<= >>= >>>=`) — it wasn't. Confirmed the gap ran all the way through: no `PERCENT_ASSIGN` token type (`lexer/token.go`), not in the parser's assignment-operator token list (`parser/parser_exprs.go`'s `parseAssignment`), and — even if lexing/parsing were fixed — `emitArith` (`codegen/llvm/emit_exprs_operators.go`, the function every compound-assignment op routes through: array element, object field, and plain scalar variable all call it generically keyed on the trimmed operator string) had no `case "%":` at all, only `"/"` — every compound op besides `%=` was already routed there correctly.

## Decision

**`i64::MIN / -1` (and the same case for every other signed width this compiler has, `i8`/`i16`/`i32`)**: extended `emitDivZeroGuard` to a second guard, run only for signed types, after the existing zero-divisor check: `divisor == -1 && dividend == <that width's minimum value>` throws a distinct `"Division overflow"` catchable error (kept separate from `"Division by zero"` — a different, more accurate message for a genuinely different condition, not the same UB class). New `signedIntMin(ir string) string` maps each of the four integer IR widths to its literal minimum. Unsigned division needed no change — there's no negative divisor to trigger this case at all.

**`%=`**: added `PERCENT_ASSIGN` the same way its three siblings already exist — a new token constant + string mapping (`lexer/token.go`), the lexer's `%` case gained the same `if l.peek() == '='` check `+`/`-`/`*`/`/` already have (`lexer/lexer.go`), the parser's assignment-operator token switch gained it (`parser/parser_exprs.go`), and `emitArith` gained the missing `case "%":`, mirroring its `"/"` case exactly (same `emitDivZeroGuard` call, same signed/unsigned `srem`/`urem` split). No changes needed at any of the three compound-assignment call sites (array element, object field, scalar variable, all in `emit_exprs_assign.go`) — all three already dispatch generically through `emitArith` keyed on the trimmed operator string, so fixing `emitArith` itself was sufficient.

Both fixes landed together since the second was found while directly scoping the first, and both are real, small, `docs/status/`-documented-or-claimed operator gaps — exactly the kind this pass was for.

## Implementation notes

Files touched:
- `codegen/llvm/emit_exprs_member.go`: new `signedIntMin`; `emitDivZeroGuard` gained the second (signed-only) overflow check and its `left Value` parameter (needed to read the dividend, not just the divisor).
- `codegen/llvm/emit_exprs_operators.go`: all three `emitDivZeroGuard` call sites updated for the new `left` parameter; `emitArith` gained `case "%":`.
- `lexer/token.go`: new `PERCENT_ASSIGN` constant + `"%="` string mapping.
- `lexer/lexer.go`: `%`'s lexer case now checks for a following `=`.
- `parser/parser_exprs.go`: `parseAssignment`'s token switch gained `lexer.PERCENT_ASSIGN`.

## Side effects discovered

None beyond `%=` itself, already covered above — that was the actual finding, not a tangential side effect.

## Verification

- `go build ./...`, `go vet ./...`, and the full `go test ./...` suite pass (Linux x86-64 dev box).
- New tests: `tests/exceptions_test.go`'s `TestE2EDivisionOverflowThrows` (`/`, `%`, and `/=` on `i64::MIN / -1` all catch `"Division overflow"`; confirmed `10 / -1` and `i64::MAX / -1` — i.e. `-(i64::MIN+1) / -1` — still compute correctly, not spuriously rejected); `tests/exprs_test.go`'s `TestE2EArithmeticCompoundAssign` (`+=`/`-=`/`*=`/`/=`/`%=` chained together — no prior test exercised `%=` at all); `lexer/lexer_test.go`'s `TestArithmeticOperators` gained a `%=` case.
- Manually confirmed, before writing the fix, that `x %= 3` was a genuine parse error (`unexpected token = in expression`) — not a hypothetical, a directly reproduced repro.
- Manually ran a broader scratch script after the fix (`x %= 3`, `-17 % 5`, array-element and object-field `%=`, `i64::MIN / -1` and `i64::MIN % -1` caught as `"Division overflow"`, `5 / 0` still caught as `"Division by zero"`, plain `7 / 2`/`7 % 2`) — every value matched hand-computed expected output.
