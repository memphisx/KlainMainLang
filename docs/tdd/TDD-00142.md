# TDD-00142: `klain:webview` — desktop applications via the system webview

- **Status**: Partially Implemented
- **Date**: 2026-08-28

## Context

The single biggest capability gap before this compiler can build and
demonstrate *applications* (as opposed to CLI tools and services) is a
window on screen. [TDD-00032](TDD-00032.md) (native toolkit bindings) and
[TDD-00033](TDD-00033.md) (framebuffer) recorded earlier research passes
and both stalled on real blockers of their era; this TDD supersedes them
as the actionable plan, on two grounds that have changed since they were
written:

1. **The closure→C-function-pointer blocker named by TDD-00032 no longer
   exists.** Every callback-driven C integration shipped since —
   timers, stream thunks, the nghttp2 driver, the fork IPC channel,
   cluster worker events — hands C code a `{function pointer, env}`
   pair via `buildBuiltinClosure` plus a fixed-ABI thunk. That is
   exactly the `(fn, void *user_data)` shape every windowing/webview
   API uses. General user-facing FFI remains unbuilt and is *still not
   required*: one well-chosen library binding, hand-written in the
   established libcurl/nghttp2 `ensure*`/embedded-source pattern, is
   the whole cost.
2. **The webview route needs no widget toolkit at all.** The
   [webview/webview](https://github.com/webview/webview) library (MIT,
   the same foundation Tauri's model popularized) is a ~13-function C
   API over the *system* browser engine — WKWebView on macOS, WebKitGTK
   on Linux, WebView2 on Windows. No bundled engine, no Chromium, small
   binaries. The application's UI is ordinary HTML/CSS/JS — which means
   **any SPA (React/Vue/Svelte/vanilla, anything that builds to static
   assets) becomes the frontend of a compiled binary**, talking to
   native code through injected bindings.

The product shape this unlocks, concretely: a single compiled binary
that opens a window, renders a real UI, and whose buttons call straight
into typed, native KlainMainLang functions — file system, HTTP client,
child processes, crypto, workers, everything already shipped. This is
the Tauri architecture with the Rust backend replaced by this compiler,
minus the IPC-to-separate-process complexity (same process, direct
calls).

The `klain:` namespace ([TDD-00131](TDD-00131.md)) is the right home:
this is a bespoke capability with no Node equivalent, exactly what the
namespace exists for.

## Design

### The library, pinned down

`webview/webview` C API (from `core/include/webview/api.h`, read
2026-08-28), the complete surface this TDD binds:

```c
webview_t webview_create(int debug, void *window);
webview_error_t webview_destroy(webview_t w);
webview_error_t webview_run(webview_t w);            // blocks: the GUI main loop
webview_error_t webview_terminate(webview_t w);      // thread-safe
webview_error_t webview_dispatch(webview_t w, void (*fn)(webview_t, void *), void *arg); // thread-safe, runs fn on the GUI thread
void           *webview_get_native_handle(webview_t w, webview_native_handle_kind_t kind);
webview_error_t webview_set_title(webview_t w, const char *title);
webview_error_t webview_set_size(webview_t w, int width, int height, webview_hint_t hints);
webview_error_t webview_navigate(webview_t w, const char *url);   // URLs and data: URIs
webview_error_t webview_set_html(webview_t w, const char *html);
webview_error_t webview_init(webview_t w, const char *js);        // runs before every page load
webview_error_t webview_eval(webview_t w, const char *js);
webview_error_t webview_bind(webview_t w, const char *name,
                             void (*fn)(const char *id, const char *req, void *arg), void *arg);
webview_error_t webview_unbind(webview_t w, const char *name);
webview_error_t webview_return(webview_t w, const char *id, int status, const char *result); // thread-safe
```

Semantics that shape the design:

- `webview_bind("f", fn, arg)` injects a `window.f(...)` into every
  page; calling it from page JS returns a **Promise** and invokes `fn`
  on the GUI thread with `req` = a JSON array of the call's arguments
  and an opaque `id`. `webview_return(id, 0, json)` resolves that
  promise (status ≠ 0 rejects). The return may happen later and from
  another thread — async native handlers are first-class.
- `webview_run` **owns the process's main loop** and must run on the
  main thread (a hard Cocoa requirement on macOS). Everything after it
  is callback-driven.
- The implementation is C++14 under a `extern "C"` API; per platform it
  needs: macOS — `-framework WebKit` (+ ObjC runtime, all in libSystem's
  orbit) and `-lc++`; Linux — `pkg-config --cflags --libs gtk4
  webkitgtk-6.0` (falling back to `gtk+-3.0 webkit2gtk-4.1`, both API
  generations are supported upstream) and `-lstdc++`.

### Module surface (V1)

```ts
import { Webview } from 'klain:webview'

const w = new Webview({ title: "My App", width: 900, height: 600, debug: false })

w.navigate("http://127.0.0.1:8080/")   // or:
w.html("<!doctype html><h1>hi</h1>")   // inline document (small UIs, no server)

w.bind("save", (args: string) => {     // page: await window.save({path, text})
  const req = JSON.parse(args)         // args = the JSON array of call arguments
  fs.writeFileSync(req[0].path, req[0].text)
  return JSON.stringify({ ok: true })  // resolves the page-side promise
})

w.init("console.log('injected before every load')")
w.eval("document.title = 'pushed from native'")
w.setTitle("Renamed")
w.setSize(1024, 700)

w.run()        // blocks — the window is the program now
// statements after run() execute at window close; w.terminate() from a
// bound callback (or another thread) ends run() programmatically.
```

Surface decisions, with rationale:

- **A handle class, not a namespace.** `new Webview(opts)` returns a
  ptr-slot handle (`IsWebview` type flag), the same single-slot pattern
  as `http.createServer`'s Server / `ChildProcess`. Parse-time
  constructor (the `Agent`/`Readable` posture); methods dispatch on the
  flag in `emit_call.go`. One window per process in V1 — a second
  `new Webview` is a clean rejection (multi-window is a later stage;
  the C API supports it, the constraint is only scoping).
- **`bind` V1 is string-JSON-in / string-JSON-out.** The callback
  receives `req` verbatim as a string (the page's argument list as a
  JSON array) and returns a string that must be valid JSON, or nothing
  (resolves `undefined`). No automatic marshaling of typed parameters
  in V1 — `JSON.parse`/`JSON.stringify` already exist and keep the
  contract fully explicit. A `bindTyped`-style sugar that JSON-decodes
  into a declared object type can come later without breaking this.
  The callback runs on the GUI thread; its return triggers
  `webview_return(id, 0, result)` immediately after it returns
  (synchronous resolution). Throwing inside the callback maps to
  `webview_return(id, 1, quoted message)` — a rejected page promise —
  via the existing setjmp catch scaffold (`emitFsGuarded`'s shape).
- **`run()` blocks and that is the honest contract.** No pretending the
  program keeps flowing; Node-style top-level continuation does not
  exist under a GUI loop. Statements after `run()` are the shutdown
  path.
- **`debug: true`** enables devtools/inspector (the C API's `debug`
  flag) — essential during SPA development.

### The SPA-as-frontend patterns (what "pack any SPA" means in practice)

Three loading patterns, all V1-expressible, documented as the module's
canonical recipes:

1. **Inline document** — `w.html(fs.readFileSync("ui.html"))` or a
   template-literal document. Zero extra moving parts; right for small
   tools. A single-file SPA build (`vite build` with
   `vite-plugin-singlefile`, or any inliner) collapses a whole React/
   Svelte app into one HTML string, so even this pattern carries a real
   SPA.
2. **Served SPA** — the already-shipped `http.createServer` serves the
   SPA's `dist/` directory; `w.navigate("http://127.0.0.1:<port>/")`.
   Because `server.listen` and `w.run` both want to own a loop, the
   server runs in a **Worker thread** (real OS threads, already
   shipped): the worker binds an ephemeral port, posts it back, the
   main thread navigates and enters `run()`. This is the pattern for
   multi-asset SPAs with routing/code-splitting. A static-file-serving
   helper (walk `dist/`, content-types, index.html fallback) belongs in
   the example, not the compiler.
3. **External URL** — `w.navigate("https://...")` for hybrid/remote
   UIs. Nothing to build; noted for completeness.

Native→page communication in all three: `w.eval(js)` (fire-and-forget
into the page) and bound-callback return values. Page→native: the bound
`window.*` functions. That pair is the whole IPC story — same-process,
no serialization beyond the JSON contract itself.

### Event-loop coexistence — the one real design problem

`webview_run` and `__kml_event_loop_run` cannot both own the process.
V1 resolves this by **contract rather than machinery**:

- The GUI loop owns the main thread. Bound callbacks may use every
  *synchronous* facility (fs, spawnSync, crypto, JSON, …) and the
  busy-driving HTTP client (`http.get` without a listening server
  drives itself to completion — already how the client works loopless).
- Anything event-loop-shaped (servers, timers, stream pumps, fork IPC)
  runs in a **Worker**, which owns its own loop legitimately. Workers +
  channels + `postMessage` already exist; this is composition, not new
  runtime.
- `webview_dispatch` is the thread-safe hook by which a Worker's result
  can poke the GUI thread — V1 exposes it indirectly: `w.eval` is made
  thread-safe by routing through `dispatch` when called off the GUI
  thread (Stage 2), so a worker can push UI updates.

A deeper fusion — pumping this runtime's timers/microtasks *on* the GUI
thread — is Stage 3, with two candidate mechanisms recorded now so the
options aren't relost: (a) a page-driven tick (`w.init("setInterval(()
=> window.__kml_tick(), N)")` bound to a native pump of
`__kml_timer_drain` + microtasks — the page is a perfectly good timer
source and it needs zero new native surface); (b) re-arming
`webview_dispatch` from a platform timer. (a) is the recommended
starting point; it is embarrassingly simple and entirely within the V1
binding surface.

### Compiler/build plumbing (shared with any future `klain:ui`)

Two genuinely new pieces, both designed here because a native-widget
module later ([TDD-00032](TDD-00032.md)'s successor) reuses them:

1. **A C++ embedded source.** `webview.cc`/headers vendored via
   `go:embed` (the `http2src`/`jsonsrc` pattern; MIT license text
   retained). The `CSource` record grows an extension/language field —
   today `main.go`, `tests/compiler_test.go`, and
   `tools/conformance/main.go` all write `<name>.c` and pass it to
   `clang`; a `.cc` member must be written with its real extension
   (clang's driver then compiles it as C++14) and the link line gains
   `-lc++` (darwin) / `-lstdc++` (linux) exactly once. All three
   writers share `EmbeddedCSources`, so the change is one struct field
   plus three call-site suffix fixes — the drift-proofing that ADR-00411
   established stays intact.
2. **Per-platform framework/pkg-config resolution for a GUI
   dependency.** The resolver follows `crypto.go`'s exact precedent
   (`LocateWebview()`): darwin → `[]string{"-framework", "WebKit"}` and
   nothing else (WebKit.framework ships with the OS — **zero install
   step on macOS**); linux → `pkg-config` probe for
   `gtk4 + webkitgtk-6.0`, falling back to `gtk+-3.0 + webkit2gtk-4.1`,
   with a clean compile-time error naming the apt/dnf packages when
   neither resolves. `requireLink`/`EmbeddedCSources` gate everything on
   actual use, as always.

Runtime shape: `runtime_webview.go` declares the 13 externs
(`ensureWebviewRuntime`), `emit_webview.go` implements the constructor +
method dispatch + the two thunks (bind trampoline: `fn(id, req, env)` →
copy `id`/`req` to length-prefixed strings → invoke user closure under a
setjmp frame → `webview_return`; dispatch trampoline for thread-safe
eval). Handles: a single calloc'd struct `{ ptr webview_t, ptr
boundListHead }` — bound closures are retained on the handle so
`-mm=manual` semantics are explicit (never freed) and `-mm=gc` sees the
references.

### Platform + testing posture

- **POSIX only, both dev machines.** macOS: WKWebView, zero
  dependencies. Linux: WebKitGTK dev packages required at *build* time
  on the build machine, shared libs at run time — same class of
  requirement as `libgc`/`libnghttp2`, documented in README
  Requirements. Windows: out of scope with the rest of the project
  ([TDD-00020](TDD-00020.md)).
- **Headless CI reality**: creating a webview needs a display server.
  The Linux CI has none, and even locally a windowed E2E test is
  hostile to `make test-par`. The testing contract is therefore
  three-tier: (1) **compile-tier E2E tests** — every module feature
  compiles to a binary (link line proves the C++/framework plumbing) —
  these run everywhere; (2) a **smoke run** that creates a window,
  `eval`s a probe that calls a bound function which `terminate()`s, and
  asserts the roundtrip output — skipped unless
  `DISPLAY`/`WAYLAND_DISPLAY` is set or on darwin, and excluded from
  the parallel bucket; (3) the **example app** (below) as the manual/
  demo artifact. This is a genuine, disclosed weakening of the usual
  run-verified ✅ bar on CI — the smoke test runs on both dev machines
  by hand instead, and each platform's verification is stated per the
  platform-claims standing rule.
- **Example**: `examples/webview/` with a real mini-app — an inline-HTML
  counter + file-browser (bind → `fs.readdirSync`, eval pushing
  results) as `inline.ts`, and a served-SPA skeleton (`worker serves
  dist/, main navigates`) as `spa.ts`. The README gets a screenshot;
  this is the "actual application" demo the whole feature exists for.

### Staged plan

| Stage | Content | Exit criterion |
|---|---|---|
| 0 | Plumbing: C++ `CSource` support (extension field, `-lc++`/`-lstdc++`), `LocateWebview()`, vendored `webviewsrc/` | a hand-written `.cc` + framework link compiles via all three build paths |
| 1 | `new Webview(opts)`, `navigate`/`html`/`setTitle`/`setSize`/`init`/`eval`/`run`/`terminate`/`destroy` | inline-HTML window opens and renders on both dev machines |
| 2 | `bind`/`unbind` with sync JSON returns + throw→reject; thread-safe `eval` via `dispatch`; served-SPA Worker recipe + example app | page button drives a native `fs` call and repaints with the result; SPA example serves `dist/` |
| 3 | Loop fusion V1: page-tick pump for timers/microtasks on the GUI thread; async `bind` (callback returns a `Promise`, `webview_return` fires at settlement). **Both implemented ([ADR-00439](../adr/ADR-00439.md)).** — **typed `bind`** (auto-JSON-decode the page's arguments into the callback's declared parameter types and auto-encode the return, since every signature is statically known) is **deferred to ride with Stage 5's `bindings`-object surface**: both want natural signatures, so they are built together rather than typed-bind landing bare here | `setTimeout`-driven UI updates work without a Worker ✅; async `bind` resolves the page promise at settlement ✅ |
| 4 | Packaging: macOS `.app` bundle + icon, Linux `.desktop` file — a `klainmain -package` build-flag (klmpm's CLI doesn't exist, so build-flag it is), metadata via `-app-name`/`-app-id`/`-app-version`/`-app-icon`. **Implemented ([ADR-00440](../adr/ADR-00440.md)).** Multi-window **deferred** ("if demand exists" — the codegen guard is one line, but true multi-window needs Cocoa run-loop/app-delegate ownership rework in the vendored engine); `dist/` asset-bundling into the app deferred (its own methodology follow-up) | double-clickable `.app` opens and renders on macOS ✅ |
| 5 | Ergonomics & security surface: **typed `bind`** (auto-JSON-decode the page's arguments into the callback's declared parameter types and auto-encode the return — a positional tuple projection reusing the JSON machinery, which also unblocks `JSON.parse<[T,U]>`) and a **`bindings` object** on the constructor whose statically-known keys become the `window.*` names, function-typed values bound — a compile-time desugar over Stage 2's `webview_bind`, working for an object literal or a variable of functions. The keys **are** the allowlist (the explicit-capability answer to the security question); `w.bind()` stays the raw escape hatch, and `w.bindTyped(name, fn)` is the imperative typed form. **Implemented ([ADR-00441](../adr/ADR-00441.md)).** Async typed bind rejected cleanly (→ Stage 6) | `new Webview({ bindings: { add, greet } })` exposes typed `window.add`/`window.greet` — args decode, returns JSON-encode ✅ |
| 6 | Typed-surface completion: a **`--emit-window-dts`** flag generating `declare global { interface Window { … } }` from the bound signatures (IDE autocomplete + the machine-checkable frontend↔backend contract / audit surface); **async typed bind** (`Promise<T>` — a per-inner-type settlement runner that JSON-encodes the settled value); **nested-tuple params** (already supported by the recursive projection). **Implemented ([ADR-00442](../adr/ADR-00442.md)).** | a generated `.d.ts` types `window.doSth()` in the page ✅; an `async` typed binding resolves the page promise with an encoded value ✅ |
| 7 | **Implemented ([ADR-00443](../adr/ADR-00443.md)).** Embed a whole SPA bundle into the executable — a single-file desktop app, no external `dist/`. A `klain:assets` primitive `embedDir("./dist")` (compile-time literal path) walks the built SPA directory and links its bytes into the binary as a read-only in-memory FS (path → bytes + content-type); recommended mechanism is a packed manifest+blob `.incbin`'d via a generated `.s` (fast, no giant hex-in-IR), with a runtime `__kml_embed_*` lookup. A `new Webview({ serve: "./dist" })` sugar composes `embedDir` + a serve + `navigate`. (Implemented via a minimal in-binary static HTTP server on a detached pthread that returns its ephemeral loopback port synchronously — cleaner than the Worker-served approach originally sketched here; see [ADR-00443](../adr/ADR-00443.md).) The static-serve rule (exact file; dir → `index.html`; miss → `index.html` for SPA history-routing / `404.html` for SSG) covers **both** Quasar `-m spa` (single `index.html` + hashed `assets/`, ~160 files) and SSG (per-route `index.html` + `404.html`, ~400 files) output shapes — validated against this project's own website. Future optimization noted: a webview custom URI-scheme handler serving embedded bytes on the GUI thread (no Worker/loopback), which also benefits the [TDD-00144](TDD-00144.md) Chromium backends. **SSR is explicitly out of scope** — this embeds *static* build output (SPA/SSG) only; running a framework's server-side render on the compiled backend (auto-finding + compiling the framework's server code, marshaling its data-fetch bindings) is a far-future per-framework idea, not this stage | `new Webview({ serve: "./dist" })` compiles a Quasar SPA/SSG build into one binary that opens and renders with no `dist/` folder beside it |

Stages 0–2 are the committed scope ("pack any SPA against a compiled
backend"); 3–5 are sequenced but re-evaluated after 2 ships — per the
no-deferring rule, nothing in 0–2 depends on them, and each stage is
independently shippable with its caveats disclosed. Stage 3's loop fusion +
async `bind` shipped; typed `bind` moved into Stage 5 so it lands together
with the `bindings` object it enables (both want natural signatures like
`() => void` / `(id: number) => User`, not the string-JSON contract) — both
surfaced during ergonomics/security review after 2 landed.

## Open questions

- Whether `bind`'s V1 string-contract should auto-JSON-quote a plain
  returned string vs. requiring valid JSON verbatim (current lean:
  require valid JSON, error loudly at the C boundary — explicit beats
  guessing; sugar can come with typed bind).
- Whether Stage 3's async `bind` should ride the existing task-promise
  runtime (`.then` reactions firing `webview_return`) or a simpler
  dedicated settlement hook on the handle — decide when Stage 3 opens,
  after the Promise machinery's behavior under a foreign main loop is
  observed in practice.
- WebKitGTK API generation pinning: probe-and-fallback (design above)
  vs. requiring 6.0 — revisit against what Debian stable/Ubuntu LTS
  actually ship. (Stage 0 landed pinning webview 0.10.0, which serves
  WebKitGTK 6.0 / 4.1 both; the vendored header compiles against
  webkit2gtk-4.1 on Ubuntu 24.04.)
- Whether the served-SPA recipe eventually deserves compile-time asset
  embedding (bundle `dist/` into the binary) — likely a `klmpm`
  ([TDD-00054](TDD-00054.md)) concern, not a compiler one. Wanted:
  ship a desktop app as one file with no `dist/` folder beside it.
- The backend↔frontend **security model** (Stage 5): the `bindings`
  object makes the exposed surface an explicit allowlist, but the
  broader questions — capability scoping, whether page origins are
  constrained (a `navigate` to a remote URL then gets the same
  `window.*` surface as a local page), and what data classes may cross
  — are open. The generated `Window` `.d.ts` is the audit artifact this
  hangs off.
- `bind` ergonomics: passing a bare function and deriving its name vs.
  requiring an explicit string — settled by the Stage 5 `bindings`
  object (the object's keys supply the names), which is preferred over
  any ambient "auto-expose every top-level handler" model precisely
  because the latter has no allowlist.
