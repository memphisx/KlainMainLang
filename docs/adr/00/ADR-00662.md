# ADR-00662: Closure free-variable scan misses try / for-in / throw / do-while / labeled statements

- **Date**: 2026-09-03

## Context

A closure that referenced an enclosing-scope variable *only* from inside a
`try`/`catch`/`finally`, `for...in`, `throw`, `do…while`, or labeled statement
failed to capture that variable: the reference resolved to nothing at codegen
(`undefined variable 'x'`) or, for a `for...in` over a captured D1 dynamic
object under `-compat=js`, fell through to the static "for...in requires an
object with known fields" rejection because the captured symbol's dynamic type
was never in scope during type inference.

Surfaced running the `-compat=js` Test262 for-in bucket: `language/statements/
for-in/return-from-{try,catch,finally}.js`, each an IIFE
(`(function(){ for (var x in obj) { try { return 42 } … } })()`) closing over a
top-level `obj`. Under `-compat=js` `obj` is a D1 dynamic object (`TypeAny`), so
`obj` is a captured main-scope local, not a module global.

## Investigation

- `emitForIn` (`codegen/llvm/emit_stmts.go`) already has a dynamic-key path
  (`isUnconstrainedDynamic(objTy)` → `emitDynAnyKeys`); the top-level case works.
  Debug printing showed that inside the IIFE, `inferExprType(obj)` returned the
  default `i64` (lookup miss), not `TypeAny` — the symbol was not in the closure
  scope at all.
- Reading `obj.name` from the same closure *did* work, so capture itself was
  fine — the difference was the reference site. `obj.name` is a
  `MemberExpression` the free-variable scanner walks; `for (…in obj)` is a
  `ForInStatement` it does not.
- `scanStmtsFV` and its eager-boxing twin `capScanStmts`
  (`codegen/llvm/emit_func.go`) switch over statement kinds but had **no case**
  for `ForInStatement`, `TryStatement`, `ThrowStatement`, `DoWhileStatement`, or
  `LabeledStatement`. A free variable reachable only through one of those was
  never added to the capture set. This is mode-independent — a strict-mode
  `try { return n + 1 }` closure over `n` hit the same miss.

## Decision

Add the five missing statement cases to both `scanStmtsFV` and `capScanStmts`,
mirroring the existing `ForStatement`/`ForOfStatement` handling:

- `ForInStatement`: scan `Object` in the outer bound set; bind `VarName` in an
  inner set before scanning `Body`.
- `DoWhileStatement`: scan `Body` then `Test`.
- `LabeledStatement`: recurse into the single labeled `Body`.
- `ThrowStatement`: scan `Argument`.
- `TryStatement`: scan `Body`; for `Catch`, bind `Param`/`ObjectPattern` names
  in an inner set before scanning the catch `Body`; scan `Finally`.

## Implementation notes

The two scanners are deliberately separate copies (one accumulates the bound set
for `gatherCaptures`, one resets at each closure boundary for eager boxing), so
each got the identical five cases. No change to `scanExprFV`/`capScanExpr` was
needed — the expressions inside these statements were already walkable once the
statement itself is visited.

## Side effects discovered

Fixes capture for these constructs in **all** modes, not just `-compat=js`
(e.g. a strict closure returning from inside a `try`). No behavior change for
closures that already captured correctly.

## Verification

- `tests/jsmode_test.go`: `TestE2EClosureCapturesInsideTry` (strict),
  `TestE2EClosureCapturesInsideForInAndDoWhile` (strict),
  `TestE2EJSModeForInOverCapturedDynamicObject` (`-compat=js`).
- Test262 `-compat=js`: `for-in/return-from-{try,catch,finally}.js` now pass
  (were CLANG/codegen failures).
- `go test ./tests -run 'Destructur|Closure|Capture|ForIn|ForOf|Arrow|JSMode'`
  green (Mac); full `make test-par` green (Mac).
