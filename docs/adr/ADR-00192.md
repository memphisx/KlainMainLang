# ADR-00192: Destructuring the loop variable of a for-of (TDD-00065 Stage 1)

- **Relations**: Implements [TDD-00065](../tdd/TDD-00065.md) Stage 1; reuses the destructuring codegen core from [ADR-00157](ADR-00157.md)/[ADR-00158](ADR-00158.md)/[ADR-00161](ADR-00161.md)/[ADR-00109](ADR-00109.md)
- **Date**: 2026-08-13

## Context

Destructuring already worked in the statement-declaration, assignment, and
function-parameter positions, but **not** as a for-of loop variable —
`for (const [a, b] of pairs)` / `for (const { x, y } of points)` was a plain
parse rejection, since `parseForOfBody` only ever accepted a bare `IDENT`.

This is the single dominant blocker in the Test262 `language/statements/for-of`
corpus: of ~640 failures there, `expected IDENT, got [` (139) +
`expected IDENT, got {` (99) = **238** were the loop variable being a pattern.
It is also the first stage of [TDD-00065](../tdd/TDD-00065.md), which scoped
the whole destructuring-generalization effort after a conformance-driven
survey found `dstr` (8,788 files corpus-wide, ~14% passing in the core
non-`eval` dirs) to be the largest coherent, in-scope, non-`eval` cluster left.

## Investigation

The parser's for-of/for-in detection (`parser/parser_stmts.go`,
`parseForStatement`) keys on `peekNth(2)` being the `of`/`in` keyword right
after the loop variable `IDENT` — a lookahead that can't work for a pattern of
arbitrary length. But `peekNth(1)` being `[` or `{` (immediately after
`let`/`const`/`var`) is an unambiguous signal that a pattern follows: no other
for-loop form starts that way.

The element-list grammar for both pattern kinds already existed inside
`parseArrayDestructuring`/`parseObjectDestructuring` (holes, `= default`,
`...rest`, renames), but was inlined into those two functions, not reusable.

On the codegen side, `emitForOf` (`codegen/llvm/emit_stmts.go`) already
materializes each element per iteration (`loadArrayElem`), and the
declaration/parameter positions already funnel through two shared unpack
cores — `unpackArrayPatternInto(dataPtr, lenVal, elemTy, elems)` and
`unpackObjectPatternInto(objPtr, objTy, props, pos)`. So the loop variable only
needed to route the already-loaded element into those same cores rather than
into a single binding — no new unpack logic, and every existing per-element
rule (holes, defaults, rest, array-typed elements) comes along for free.

Alternative considered and rejected: desugaring `for (const P of it)` into
`for (const $tmp of it) { const P = $tmp; … }` at parse time. Rejected because
the element type isn't known at parse time (it drives the object-vs-array
unpack choice), and it would materialize an extra binding the codegen path
doesn't need.

## Decision

1. **AST** (`ast/nodes.go`): add `ArrayPattern []ArrayPatternElem` and
   `ObjectPattern []DestructProp` to `ForOfStatement`, mirroring `Param`'s own
   pattern carriers. Both nil ⇒ the existing bare-`VarName` path, untouched.
2. **Parser** (`parser/parser_stmts.go`): factor the two pattern element-list
   grammars into shared `parseArrayPatternElems` (`[`…`]`) and
   `parseObjectPatternProps` (`{`…`}`) helpers, and rewrite
   `parseArrayDestructuring`/`parseObjectDestructuring` to call them (no
   behavior change). Detect a pattern loop variable in `parseForStatement`
   (`peekNth(1)` is `[`/`{` after the kind keyword) and parse it in a new
   `parseForOfPatternBody`, which requires `of` after the pattern (a pattern in
   for-*in* stays unsupported).
3. **Codegen** (`codegen/llvm/emit_stmts.go`, `emitForOf`): when a pattern is
   present, define no single loop binding; instead unpack the per-iteration
   element in the loop body — an object pattern through
   `unpackObjectPatternInto(elemVal.Ref, elemTy, …)`, an array pattern by
   extracting the element aggregate's `{ptr,i64}` and calling
   `unpackArrayPatternInto(innerPtr, innerLen, *elemTy.ElemType, …)`.
4. **Free-variable scan** (`codegen/llvm/emit_func.go`): the closure-capture
   scan marked `s.VarName` as loop-local; extend it to mark each of a pattern's
   element/property names instead, so a closure in the body that references a
   pattern-bound name isn't misclassified as capturing an outer variable.

## Implementation notes

- Files touched: `ast/nodes.go`, `parser/parser_stmts.go`,
  `codegen/llvm/emit_stmts.go`, `codegen/llvm/emit_func.go`.
- The unpack cores call `e.define(...)` themselves, so the bindings land in the
  loop's own pushed scope and are overwritten (in generated IR, restored) each
  iteration — no per-iteration alloca growth, since codegen emits the loop body
  once.

## Side effects discovered

- **Map-entry iteration is still values-only.** This compiler iterates a `Map`
  by values, not `[key, value]` entries ([ADR-00011](ADR-00011.md)), so
  `for (const [k, v] of map)` does not yield entries — it would array-destructure
  each value. Unchanged here and a separate gap.
- **Nested patterns as the loop variable** (`for (const [[a, b], c] of …)`)
  remain a clean parse rejection — that is [TDD-00065](../tdd/TDD-00065.md)
  Stage 2 (a nested-pattern AST field + recursive unpack), not this stage.
- A large share of the remaining `for-of/dstr` failures are the **runtime
  iterator protocol** (`[Symbol.iterator]`, iterator-close) — out of scope for
  the whole TDD, and the reason Stage 1's real flip count is bounded (see
  Verification).

## Verification

- Linux (x86-64). `go build`, `go vet ./...`, `go test ./...` all pass
  (`tests` suite green).
- Four new E2E tests in `tests/stmts_test.go` (object pattern, renamed object
  pattern, array pattern over nested arrays, array pattern with a hole + rest).
- Extended `examples/basics/destructuring.ts` with the for-of forms; compiles
  and runs with the expected output.
- Conformance (`tools/conformance -category language/statements/for-of`):
  **111 → 124 passing** (+13); the `for-of/dstr` sub-dir **57 → 69** (+12). The
  gap between the 238 parse-unblocked files and the 13 net flips is the
  out-of-scope iterator-protocol/nested-pattern remainder, exactly as
  [TDD-00065](../tdd/TDD-00065.md) predicted.
