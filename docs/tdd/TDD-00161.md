# TDD-00161: Decorators — `@decorator` on classes, methods, accessors, properties, and parameters

- **Status**: Partially Implemented

- **Date**: 2026-09-02

## Context

Decorators are the single largest front-end gap in the TypeScript acceptance
oracle (TDD-00121 Track C). Of the 2,927 false-rejects (valid TS this compiler
wrongly rejects), the `@` character is the #1 blocker at **170** occurrences,
and **141** single-file false-reject cases contain a `@decorator` at a
class/member position — more than 2× the next distinct feature cluster
(declaration merging, 71). The lexer rejects `@` outright as an unexpected
character, so every decorated file dies at lex time.

Why now: it is the highest-leverage TS-conformance work by a wide margin, and
decorators are load-bearing in the real frameworks this project's stated
targets (Docker microservices / CLI tools) lean on — dependency-injection and
routing frameworks are decorator-first. This is scoped as its own TDD because
it is a new subsystem with a genuine multi-option design fork and a hard
interaction with the static class model.

**The oracle trap (why this cannot be a parse-and-ignore).** The Track C oracle
checks accept/reject agreement only, not runtime behavior. Parsing `@dec` and
discarding it would flip all 141 cases to "match-accept" while silently
miscompiling every program whose decorator actually transforms its target —
exactly the masking the standing rules forbid ("never mask"; "faithfulness
first"). So each stage here must ship *faithful* behavior for the subset it
accepts and *cleanly reject* the rest, never accept-without-applying.

## Design

### The two dialects

TypeScript has two incompatible decorator systems, selected by the
`experimentalDecorators` compiler flag (mirrored in the corpus by a
`// @experimentalDecorators: true` directive — present in 49 of the 141 cases;
the remainder rely on the TS-5.0+ default, standard decorators):

- **Legacy / experimental** (`experimentalDecorators: true`): a decorator is
  `(target, propertyKey?, descriptorOrParamIndex?) => any`. Class decorators
  receive the constructor and may return a replacement constructor;
  method/accessor decorators receive `(target, key, PropertyDescriptor)` and may
  return a replacement descriptor; property decorators receive `(target, key)`
  (observe-only); parameter decorators receive `(target, key, index)`
  (observe-only). With `emitDecoratorMetadata`, `design:type` /
  `design:paramtypes` / `design:returntype` reflection metadata is emitted.
  This is what `reflect-metadata`-based DI frameworks use today.

- **Standard / TC39 stage 3** (the TS-5.0 default): a decorator is
  `(value, context) => value | void`, where `context` is
  `{ kind, name, static, private, addInitializer, access, metadata }`. Applies
  to class, method, getter, setter, `accessor` fields (auto-accessors), and
  fields — **no parameter decorators**. Replacement is by return value;
  side-effect init via `context.addInitializer`.

### The governing decision: decorators vs. the static class model

This compiler's classes are static (fixed field layout + a compile-time vtable,
`emit_classes.go`). A method/class decorator that *returns a replacement* makes
the class's runtime shape decorator-determined — the same static-vs-runtime
tension D1 resolved for objects (TDD-00155). Three dispositions, staged by
increasing difficulty rather than chosen exclusively:

1. **Observe-only decorators need no shape change.** A property decorator
   (`(target, key)`), a parameter decorator (`(target, key, index)`), and any
   decorator whose return value is discarded run a call at class-definition
   time and never alter dispatch. These compile as an ordered sequence of calls
   emitted into the per-class static initializer (`emitClassStaticInit` already
   exists as the once-before-main hook), with zero vtable impact. This alone
   accepts-and-faithfully-runs a large share of the corpus (metadata/DI-shape
   tests, `parameterDecorators*`, `propertyDecorators*`).

2. **Descriptor-replacing method/accessor decorators** require the decorated
   member to be reachable through a runtime `PropertyDescriptor` whose `value`
   the decorator can swap. Faithful support routes a *decorated* method through
   a per-class runtime descriptor slot (initialized to the static
   implementation, then overwritten by each decorator's returned descriptor,
   applied bottom-up per spec) and makes calls to that specific member consult
   the slot. Undecorated members keep the static vtable path untouched — the
   cost is paid only where a decorator is actually present.

3. **Class-replacing decorators** (a class decorator returning a new
   constructor) are the hardest: every `new C()` and every static reference
   must observe the replacement. Deferred to the last stage; until then a
   class decorator that returns a value is a clean rejection, while a
   class decorator whose result is ignored (the common logging/registration
   case) rides stage 1.

### Recommended direction and staging

Implement **experimental decorators first** (flag-gated, matching TS): it covers
the plurality of corpus cases, is the dialect real DI frameworks ship today, and
its observe-only + descriptor model maps onto the existing static-init and
(stage 2) a narrow runtime-descriptor mechanism without a standard-decorators
`context` object. Standard decorators follow as a parallel dialect behind the
default, reusing the same parse tree.

| Stage | Content | Accepts / rejects |
|---|---|---|
| **1 — parse + observe-only** | Lex `@`; parse decorator lists on class, method, accessor, property, and parameter (AST: a `Decorators []Expression` field on the relevant nodes). Emit experimental-dialect calls for **observe-only** decorators (property, parameter, and class/method decorators whose return is unused) into the class static initializer, bottom-up, with the correct `(target, key[, index])` arguments. | Accepts observe-only decorated classes and runs the decorators faithfully; **cleanly rejects** any decorator whose return value would replace a member/class (stage 2/4), with a clear message. |
| **2 — method/accessor descriptor replacement** | Per-class runtime descriptor slot for each *decorated* method/accessor; apply returned descriptors; route calls to that member through the slot. | Adds value-replacing method/accessor decorators. |
| **3 — `emitDecoratorMetadata`** | `design:type`/`design:paramtypes`/`design:returntype` emission behind the flag; requires a minimal `Reflect.metadata` shim. | Unblocks the `decoratorMetadata*` cluster. |
| **4 — class replacement** | Class decorator returning a replacement constructor observed by all construction/static-ref sites. | Closes experimental decorators. |
| **5 — standard decorators** | The TC39 `(value, context)` dialect as the default; `accessor` auto-accessor fields; `addInitializer`; `Symbol.metadata`. | The non-`experimentalDecorators` corpus share. |

Each stage lands with E2E tests + an example and updates the status JSON +
Track C number same-commit. Stage 1 alone is expected to convert the bulk of
the observe-only/metadata-shape false-rejects.

## Open questions

- **Descriptor slot vs. vtable patch** (stage 2): does a decorated method get a
  dedicated per-instance/per-class descriptor slot consulted at every call, or
  is the class's vtable entry itself overwritten at static-init? The latter is
  cheaper (no per-call branch) but only works when the replacement is knowable
  as a single function pointer with the static ABI; a boxed closure return
  forces the slot. Resolve when stage 2's first repro is in hand.
- **Standard vs. experimental default** (stage 5): TS defaults to standard from
  5.0; the corpus mixes both by directive. Match TS's flag-gated default, or
  pick one dialect as the compiler's default and require the flag for the other?
  Leaning: mirror TS exactly (flag-gated) so the oracle's per-case directive is
  honored.
- **Parameter decorators under standard decorators**: not in TC39 stage 3.
  Under the standard dialect a parameter decorator should be a clean rejection,
  not silently accepted — confirm the corpus's standard-dialect cases don't rely
  on them.
- Whether `emitDecoratorMetadata` (stage 3) is worth its `Reflect.metadata`
  shim for the oracle alone, or waits until a DI-framework example concretely
  needs it.
