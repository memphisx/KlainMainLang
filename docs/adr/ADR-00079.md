# ADR-00079: POSIX signal handling — `process.on('SIGINT'/'SIGTERM', handler)`

- **Relations**: Implements [TDD-00019](../tdd/TDD-00019.md). Extends [ADR-00072](ADR-00072.md), which explicitly deferred graceful shutdown pending this exact infrastructure.
- **Date**: 2026-07-30

## Context

`http.listen` never returns — the only way to stop a running server was `process.exit()` or an external `kill`, with no chance to run cleanup code first. This was the last open item in `docs/status/HTTP-SERVER.md` (graceful shutdown), explicitly deferred by [ADR-00072](ADR-00072.md) ("Graceful shutdown ... is explicitly out of scope — it needs POSIX signal handling, infrastructure that doesn't exist anywhere in this compiler") and flagged by [TDD-00004](../tdd/TDD-00004.md)'s Prerequisites table as "a genuinely new gap this feature surfaces, not previously needed by anything." No design work existed anywhere for it.

Surfaced this session by asking "what's the next big thing to tackle?" against the current `docs/status/README.md` roadmap — signal handling was the clear pick: it's the single blocker on an otherwise ~86%-complete HTTP server, and it directly serves this project's stated microservice priority.

## Investigation

Two `Explore` agents plus direct file reads established the concrete mechanics before any design was committed to [TDD-00019](../tdd/TDD-00019.md):

- `codegen/llvm/runtime_http.go:685` (`@__kml_event_loop_run`, used whenever `http.listen` is called) and `codegen/llvm/emit_timers.go:249` (`@__kml_timer_drain`, the simpler standalone loop used when only `setTimeout`/`setInterval` are used without `http.listen`) are two *separate* hand-written IR loops, each with their own `outerloop:` label re-entered every iteration.
- `timerCallbackPtr` (`emit_timers.go:23-35`) already validates a `() => void` closure argument and returns a `ptr` to its `{funcPtr, envPtr}` header — directly reusable. Invocation is the fixed `call void (ptr) %fp(ptr %ep)` GEP pattern both loops' existing timer-fire logic already uses.
- `process.*` calls are routed in `emit_call.go:146-167`'s `switch mem.Property` — a `case "on":` follows the exact shape of `exit`/`kill`/`cwd`/`chdir`.
- `emitHasOwnProperty` (`emit_objects.go:775-778`) is the precedent for rejecting a non-compile-time-literal argument: assert `args[0].(*ast.StringLiteral)` directly, reject anything else.
- Confirmed via `grep` that nothing in `codegen/llvm/` declared `signal`/`sigaction` anywhere — genuinely new ground.
- **A real hazard, not previously documented anywhere**: a raw POSIX signal handler can interrupt the program at literally any instruction, including mid-`malloc`, mid-`longjmp`, or mid-`swapcontext` fiber switch. This compiler's exception machinery (`setjmp`/`longjmp`, `runtime_exceptions.go`) and fiber scheduler (`ucontext.h`, `runtime_http.go:436-450`) both assume they're only ever entered from ordinary, non-reentrant control flow — [TDD-00006](../tdd/TDD-00006.md) already documents in depth that LLVM coroutine suspension across a `setjmp`/`longjmp` boundary segfaults for exactly this class of reason. Calling arbitrary TS closure code from real signal context would risk the same kind of corruption.
- Considered `sigaction()` over plain `signal()` for its `SA_RESTART` control, but rejected it: `sigaction()` needs a hand-laid-out `struct sigaction`, whose byte layout differs between Darwin and Linux (`sa_mask` size, presence of `sa_restorer`) — exactly the class of bug already hit once with `ucontext_t`'s platform-specific size/layout ([ADR-00051](ADR-00051.md)). `signal()`'s C signature is two scalars, no struct, identical on both platforms this compiler targets. `select()`/`poll()` are documented (Linux `signal(7)`, equivalently on BSD/Darwin) to always return `EINTR` on a signal regardless of `SA_RESTART`, so the restart-control `sigaction` would have bought wasn't actually needed.

## Decision

Two-part design, matching [TDD-00019](../tdd/TDD-00019.md):

1. **Registration** (`emitProcessOn`, `emit_process.go`): the event-name argument must be the compile-time string literal `"SIGINT"` or `"SIGTERM"` (anything else, including a dynamic/computed value, is a clean compile error). The handler is validated via the existing `timerCallbackPtr`. The closure pointer is stored into one of two module-level globals (`@__kml_sigint_closure`/`@__kml_sigterm_closure`); the first time a given signal is registered, `signal(2 | 15, @__kml_sig_handler)` is called once (idempotent, same `ensure*()`-style guard as everywhere else in this compiler).
2. **Delivery**: `@__kml_sig_handler` (a tiny hand-written IR function, `runtime_process.go`) is the *only* code that ever runs in real signal context — it does nothing but `store volatile i8 1` into a pending-flag global for whichever signal fired. Both event loops (`__kml_event_loop_run`, `__kml_timer_drain`) got an identical block inserted at the very top of their `outerloop:` label: check each pending flag, clear it, and — if a handler is registered — invoke it via the same `call void (ptr) %fp(ptr %ep)` trampoline pattern timers already use. This is invoked from ordinary control flow at the top of the loop's own iteration, never from signal context, sidestepping the hazard above by construction.

A program that never calls `process.on` for a given signal never calls `signal()` for it either — that signal's OS-level disposition stays default (`SIG_DFL`, terminate immediately), matching pre-existing behavior with zero added overhead. Registering a handler suppresses the default terminate action but does **not** automatically end the event loop — the handler is expected to call `process.exit()` itself. This sidesteps needing any `.close()`/listener-teardown machinery; `.close()` itself remains unimplemented after this ADR.

V1 scope, deliberately narrow: only `'SIGINT'`/`'SIGTERM'` (not `'exit'`/`'uncaughtException'`/`'unhandledRejection'`, which don't involve real signal delivery at all); one handler slot per signal (re-registering overwrites); only fires while a `http.listen`- or timer-driven event loop is actively iterating — a plain synchronous top-level script with neither has no loop to check the flag from, and interrupting arbitrary blocking syscalls compiler-wide is a materially bigger, separate problem left alone here.

## Implementation notes

- `codegen/llvm/runtime_process.go`: `ensureSignalHandlerRuntime()` (declares `@signal`, the four globals, `@__kml_sig_handler`) and `ensureSignalRegisteredSigint`/`Sigterm` (the one-time `call ptr @signal(...)`, called from `emitProcessOn`).
- `codegen/llvm/emit_process.go`: `emitProcessOn`.
- `codegen/llvm/emit_call.go:146-167`: new `case "on":` in the `process.*` switch.
- `codegen/llvm/emit_timers.go`: `ensureTimerRuntime()` now unconditionally calls `ensureSignalHandlerRuntime()` — the pending-signal globals must exist whenever `__kml_timer_drain`'s IR references them, whether or not the specific program ever calls `process.on`, the same "every symbol the loop's IR mentions must be declared regardless of whether the feature is used" reasoning `ensureHTTPRuntime` already documents for `ensureFetchAsync`. Since `ensureHTTPRuntime` already calls `ensureTimerRuntime()`, both loops get this for free from one insertion point.
- `codegen/llvm/runtime_http.go`: the signal-check block inserted at the top of `outerloop:`; the `afterselect:` fix (see Side effects below).
- `codegen/llvm/emit_timers.go`: the identical signal-check block at the top of `__kml_timer_drain`'s `outerloop:`; the `dosleep`/`dofire` fix (see Side effects below).
- The pending flags are `i8`, always accessed via `load volatile`/`store volatile` — required so `-O2` doesn't cache the flag's value across the `select()`/`nanosleep()` call or eliminate a store as dead, the LLVM-IR equivalent of C's mandatory `volatile sig_atomic_t` for this exact pattern.
- `afterselect:` is reached from two predecessor blocks (`timeoutpath`/`notimeoutpath`), each defining its own `%selrc1`/`%selrc2` — merged via a `phi i32` before the new return-value check, rather than duplicating the check in both predecessors.

## Side effects discovered

Two real, pre-existing bugs surfaced while building this — neither could have manifested before, since nothing in this compiler ever installed a custom signal handler prior to this feature, so no signal ever interrupted these two blocking calls:

- **`select()`'s return value was never checked** (`runtime_http.go`, `%selrc1`/`%selrc2`). POSIX leaves the fd_sets *unmodified* on an `EINTR` return — they'd still hold the *watch* set built for that iteration, not real readiness info. Falling through to `afterselect` unchecked meant every watched fd, including the listener, would look spuriously "ready." The listener socket is never set non-blocking (only accepted connections are), so a spurious `accept()` after `EINTR` could block indefinitely — hanging the whole server exactly when a signal was trying to wake it up to shut down. Fixed as part of this change: `afterselect` now branches on the (phi-merged) return value and skips straight back to `outerloop` on failure.
- **`nanosleep()`'s return value was never checked** (`emit_timers.go`'s `__kml_timer_drain`). Found empirically, not by inspection: a manual test (`process.on('SIGINT', ...)` + a 100-second `setInterval`, signaled after ~500ms) printed the interval's callback output immediately, despite the interval being nowhere near due. `dosleep` unconditionally fell through to `dofire` regardless of whether `nanosleep` actually completed its requested duration or returned early via `EINTR` — so *any* signal arriving during a timer wait fired that timer early, not just by a little, but by however much time was left. Fixed by checking `nanosleep`'s return value and looping back to `outerloop` (which re-checks signals, then recomputes the now-shorter remaining wait) on early return instead of proceeding to `dofire`.

Both are covered by regression tests (see Verification) — `TestE2ETimerNotPrematurelyFiredBySignal` specifically targets the second one.

No `.close()` API exists after this change; `http.listen` still has no formal way to stop accepting connections mid-run short of the whole process exiting. Not needed for the graceful-shutdown use case this ADR addresses (the handler just calls `process.exit()`), but noted as a real, distinct remaining gap in `docs/status/HTTP-SERVER.md`.

## Verification

- `tests/signals_test.go` (new, 8 tests): `TestE2ESignalSigintGracefulShutdown`/`TestE2ESignalSigtermGracefulShutdown` — a real `http.listen` server, signaled via `cmd.Process.Signal` (not a shell `kill`, which proved unreliable in this session's own sandboxed shell for unrelated reasons — confirmed by observing even a signal-handling-free "while(true){}" binary exhibiting the same shell-specific non-termination, ruling out the compiler as the cause), asserting both a clean exit code *and* that the handler's own marker output actually appeared (not just that the process died, which would also pass under the OS's own default disposition). `TestE2ESignalBothRegisteredIndependently` — registering both signals fires only the one actually sent. `TestE2ESignalNoHandlerDefaultDisposition` — a program that never calls `process.on` still terminates via default OS disposition, confirming this change doesn't alter existing behavior for programs not using the new feature (and confirmed directly via `--emit-llvm` that no `call ptr @signal(...)` is ever emitted without a matching `process.on` call). `TestE2ESignalSetIntervalOnlyGracefulShutdown` — the same mechanism works through `__kml_timer_drain` (no `http.listen` at all), using a `fs.writeFileSync`-based readiness signal rather than a stdout marker line, since `console.log` output sits in fully-buffered libc stdio when stdout is a pipe and is never visible to a polling reader until the process exits — confirmed directly (an earlier stdout-marker version of this test reliably timed out). `TestE2ETimerNotPrematurelyFiredBySignal` — the `nanosleep` regression test above. `TestE2ESignalDynamicEventNameRejected`/`TestE2ESignalUnsupportedEventNameRejected` — compile-time rejection of a non-literal or unsupported event name.
- `go test ./...` (full suite, ~161s): all green, confirming the `afterselect:`/`outerloop:` control-flow changes didn't regress any existing event-loop/timer/HTTP test.
- Manual end-to-end runs (both via direct shell signaling and via the Go test harness) of the actual motivating scenario: an `http.listen` server registering `process.on('SIGINT', ...)`, receiving a real request while running, then shutting down cleanly on `SIGINT` with the handler's own cleanup code observed to run.
- New example: `examples/process/graceful_shutdown.ts` — an `http.listen` server that sends itself a real `SIGINT` via `process.kill(process.pid, 2)` after a short delay (proving the full registration → OS delivery → handler round trip, not just that `process.exit()` works), verified under `make examples`.
- `docs/status/HTTP-SERVER.md` and `docs/status/PROCESS-CLI.md` updated (❌ → ✅ for the relevant rows, coverage percentages recomputed); `docs/status/README.md`'s Node.js APIs coverage table and Roadmap updated to match.
