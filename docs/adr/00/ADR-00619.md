# ADR-00619: Eager-box captured locals so their heap cell dominates all uses

- **Date**: 2026-09-01

## Context

Building an interactive load tester surfaced a real codegen crash. A worker's
non-blocking stop check —

```ts
let stopped = false;
select(stop.recvCase((_) => { stopped = true; }), defaultCase(() => {}));
if (stopped) break;
```

failed at the clang step with `invalid LLVM IR input: Instruction does not
dominate all uses!`, pointing at a `call ptr @malloc` / `load` pair for the
captured `stopped`.

## Investigation

A local captured by a closure is heap-boxed so the closure and the enclosing
scope share one mutable cell by pointer (`promoteCaptureToCell`, emit_func.go).
The box was allocated **lazily, at the closure-construction site**. When the
closure literal sits inside a *conditional* block — a `select` case handler, an
`if`/`else` branch, `&&`/ternary — the `malloc` lands in that block, which does
not dominate a read of the variable after the conditional. Confirmed general,
not select-specific: a closure inside an `if`-branch (`arr.forEach(() => {
flag = true })`) crashes identically. A module *global* was immune (it's a real
global that dominates everything); only function/block locals and params hit it.

## Decision

Move box creation from the lazy capture site to the variable's **declaration**
(params: to function entry) — a position that dominates the variable's whole
scope. Crucially this boxes **exactly the same set** of variables as before
(the captured ones), only earlier: eager boxing sets the symbol `Boxed`, so the
existing lazy `promoteCaptureToCell` path (`if !cap.Sym.Boxed`) is simply
skipped and reuses the eager cell. Non-captured locals are untouched (no
over-boxing); module globals are still resolved directly.

- `capScanExpr`/`capScanStmts` + `capturedLocalNames`: faithful copies of the
  free-variable scanners that **reset** the bound set to the closure's own
  params at each closure boundary, so a nested closure's reference to an
  enclosing local surfaces as a capture. The originals are untouched
  (`gatherCaptures` relies on their accumulate-bound behavior).
- An `e.hoistedCaptures` set is computed and installed (save/restore, like
  `e.allocas`) at every function-body emission: the top-level program body,
  `emitFunctionDeclAs`, `emitClosureFunc`, `emitFunctionExpression`.
- `boxHoistedCapture` allocates the cell, seeds it (type default, or the param
  value), and registers a `Boxed` symbol. `emitVarDecl`'s scalar/ptr path and
  the three param loops box eagerly when the name is in `hoistedCaptures`.

**`var` vs `let`/`const` placement:** function-scoped `var` and params box in the
entry block (dominates unconditionally); `let`/`const` box at their declaration
point in the body — which dominates their block scope and, inside a loop,
re-runs the malloc per iteration so each iteration's closure gets its own cell,
matching prior lazy behavior and JS `let` semantics. An initial entry-only
placement regressed `var`-hoisting cases and per-iteration `let` capture; the
split fixes both.

## Verification

Mac (Apple Silicon M4). The two repros (captured bool in a `select` case; a
closure in an `if`-branch) go from crash to correct output. A captured *number*
and a nested capture still work; a function of non-captured locals emits **zero**
malloc boxes (no over-boxing). `go build`/`go vet` clean. `make test-par` green
(two network/signal tests flake under parallelism, pass on the serial re-run).
`make examples` 249/0.
