# ADR-00764: `spawn(cmd, args, { timeout, killSignal })`

- **Relations**: Extends [ADR-00433](ADR-00433.md) (spawn options), [ADR-00762](ADR-00762.md)/[ADR-00763](ADR-00763.md) (the spawn-options struct) and [ADR-00761](ADR-00761.md) (the `(code, signal)` event the timeout kill surfaces through); addresses [TDD-00180](../tdd/TDD-00180.md) §3
- **Date**: 2026-09-07

## Context

The last of [TDD-00180](../tdd/TDD-00180.md) §3's spawn-option rows implemented
here: Node's `timeout` — kill the child after N ms — with its companion
`killSignal` (default `SIGTERM`). Unlike `cwd`/`env`/`windowsHide`, `timeout` is
not a one-shot CreateProcess/exec detail: it needs the **event loop** to notice
the deadline and kill a child that is otherwise silent, which is why it is the
heaviest of the four §3 spawn options. Its effect surfaces cleanly through the
`(code, signal)` event shape ([ADR-00761](ADR-00761.md)): a timed-out child
reports `(null, '<killSignal>')`.

## Investigation

A spawned child's read pipes fold into the shared `select()` loop
(runtime_http.go); `__kml_cp_dispatch` drains/reaps after each wake. The loop
already bounds `select()` by an "extra-deadline slot" (`%cmdlabs`) into which the
EventSource-reconnect, fetch-abort, and libcurl deadlines are folded — the exact
mechanism a `timeout` needs so a silent slow child (no pipe traffic, no other
timer) is still woken on time. `__kml_monotonic_ns` (the timer runtime) gives the
clock; `@kill` sends the signal; the recorded-signal field 21
([ADR-00761](ADR-00761.md)) already turns a kill into the faithful
`(null, signal)` event.

## Decision

- **State**: two new cp-struct fields — 22 (absolute monotonic-ns deadline, 0 =
  none) and 23 (killSignal, default 15). `__kml_cp_spawn` gains `timeout_ms` and
  `killsig` params; on spawn it stores `deadline = monotonic_ns() + timeout_ms·1e6`
  (or 0) and the signal. Struct → 24 fields / 192 bytes; both `calloc` sites and
  `cpStructBytes` move together.
- **Deadline into the wait**: `__kml_cp_next_timeout_ns()` returns the soonest
  live child's deadline (0 = none), folded into `%cmdlabs` in the loop exactly
  like the curl/EventSource deadlines (min-take). A stub
  (`emitLoopTaskStubs`) stands in for programs that never spawn.
- **Fire**: `__kml_cp_dispatch`, which already iterates live children after each
  `select()`, kills a child whose deadline has passed (once — the deadline is
  zeroed), recording `killSignal` into field 21 so the subsequent reap fires
  `('exit', null, '<signal>')`.
- **Options** (`cpSpawnOpts`): `timeout` is any numeric expression → i64 ms;
  `killSignal` is a literal signal name (→ the host's number via `cpSignalTable`)
  or a numeric literal. Defaults: no timeout, SIGTERM.

## Implementation notes

- `%cmdlabs` holds an **absolute** monotonic-ns deadline (the select code derives
  the wait as `deadline − now`), so the cp deadline is stored and folded absolute
  — no per-iteration relative recompute.
- `ensureChildProcRuntime` now pulls `ensureTimerRuntime` (`@__kml_monotonic_ns`)
  and `ensureCPKill` (`@kill`) since the dispatch fire needs both even when the
  program never calls `child.kill`.
- **Two regressions caught by the full suite** (both fixed here): (1) the initial
  `cpSpawnOpts` in `emitCPSpawn`'s no-options path didn't default `timeoutRef`, so
  a plain `spawn(cmd)` emitted `i64 ,` — invalid IR; (2) `ensureCPKill`'s new
  unconditional call collided with `runtime_process.go`'s own independent
  `declare @kill` (a program using both `spawn` and `process.kill`), an "invalid
  redefinition" — deduped by making `runtime_process` reuse `ensureCPKill` as the
  single owner of the declaration. Both are the "run the *full* childprocess
  suite after a cp-runtime change" lesson again.
- Back-quotes in an IR comment terminate the Go raw-string literal — the
  `timeout` comments were written without them (a recurring trap this session).

## Side effects discovered

- A child killed by `timeout` whose **grandchild** still holds the stdout/stderr
  pipes (e.g. `sh -c "sleep 10"`, where `sh` is killed but `sleep` inherits the
  pipe) delays the `'exit'` event until the pipe reaches EOF, because finalize is
  gated on both pipes closing — a pre-existing architectural property (no process
  groups; `detached` is not implemented). A direct child (`spawn("sleep",…)`)
  reaps promptly. Documented as a caveat.

## Verification

- New E2E tests: `…SpawnTimeout` (direct child → `(null, 'SIGTERM')`),
  `…SpawnTimeoutKillSignal` (`SIGKILL`), `…SpawnTimeoutNotHit` (a fast child keeps
  its normal `(2, null)`). Full `TestE2EChildProcess*` green on Windows 11 and
  Docker Linux.
- Manual repros: **Windows 11 native** — timeout kills a direct `sleep` promptly
  with `(null, 'SIGTERM')`; `killSignal: 'SIGKILL'` → `'SIGKILL'`; a fast child is
  untouched. **Docker Linux `klain-ci:latest`** — same, prompt.
- `examples/child_process` extended; compiles and runs. `go build`, `go vet
  ./codegen/...` clean. `make status`/`reference-check`/`conformance` at delivery.
