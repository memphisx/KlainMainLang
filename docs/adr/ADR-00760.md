# ADR-00760: `socket.setKeepAlive(enable, initialDelay)` threads the idle time

- **Relations**: Implements [TDD-00180](../tdd/TDD-00180.md) §5 (`TCP_KEEPIDLE` translation); extends [ADR-00737](ADR-00737.md) (the Winsock option-translation layer in `win32io.c`)
- **Date**: 2026-09-07

## Context

`socket.setKeepAlive(enable, initialDelay)` in Node sets SO_KEEPALIVE and, when enabling with a delay, the keepalive *idle* time — how long an idle connection waits before the first probe. The port accepted the second argument but dropped it (`emit_net.go`: "not threaded into the socket option in V1"), so `setKeepAlive(true, 30000)` behaved as `setKeepAlive(true)`.

TDD-00180 §5 flagged the underlying Windows hazard: the idle time is Linux `TCP_KEEPIDLE`, option number **4** — but option 4 at `IPPROTO_TCP` on Windows is **`TCP_MAXSEG`**, not a keepalive control. So the naive path (emit the Linux number, let the Winsock shim pass it through) would silently reconfigure the segment size. libuv/Node never take that path: on Windows they set keepalive timing through `WSAIoctl(SIO_KEEPALIVE_VALS)`.

## Investigation

The emit side (`emit_net.go` `emitNetSocketSockOpt`) evaluates `setKeepAlive`'s extra args only for side effects. Socket-option constants come from the `runtime.GOOS` branch helpers (`netKeepAliveConst`, `httpSockConstants`): on Windows they return the **Linux** numbers, and `win32io.c`'s `setsockopt` translates `SOL_SOCKET`-level options to Winsock (`SO_REUSEADDR`→`SO_EXCLUSIVEADDRUSE`, etc.). `TCP`-level options bypassed that switch entirely, so a `TCP_KEEPIDLE` would have reached Winsock as `TCP_MAXSEG`.

Node's contract (net.js → libuv `uv_tcp_keepalive`): SO_KEEPALIVE tracks `enable`; the idle time is set **only when `enable` is true and the delay is non-zero**, as `~~(initialDelay / 1000)` seconds. Linux uses `setsockopt(IPPROTO_TCP, TCP_KEEPIDLE, seconds)`, macOS `TCP_KEEPALIVE` (0x10), Windows `SIO_KEEPALIVE_VALS` with the time in **milliseconds** and libuv's default 1 s probe interval.

## Decision

Thread the delay, faithfully per platform, keeping the emit side platform-agnostic and the Windows remap in the shim.

- `emit_net.go`: capture `setKeepAlive`'s `initialDelay` (a number — a literal arrives as `double`, normalised to i64 ms), compute `seconds = ms / 1000`, and — guarded at runtime by `enable != 0 && seconds > 0` — emit a second `setsockopt(IPPROTO_TCP, TCP_KEEPIDLE, &seconds, 4)`.
- New `netKeepIdleConst()` returns `(6, 4)` on Linux/Windows and `(6, 0x10)` on macOS — the same `runtime.GOOS` posture as the neighbouring socket-constant helpers.
- `win32io.c` `setsockopt`: a new pre-switch branch on `IPPROTO_TCP`/`TCP_KEEPIDLE` issues `WSAIoctl(SIO_KEEPALIVE_VALS, { onoff = 1, time = seconds × 1000, interval = 1000 })`, converting the incoming seconds to milliseconds. `WSAIoctl` is now bound in `ws_init`. This dodges the `TCP_MAXSEG` collision the pass-through would have caused.

## Implementation notes

- The runtime guard mirrors libuv exactly: `setKeepAlive(false)` and `setKeepAlive(true, 0)` set SO_KEEPALIVE only and never touch the idle time.
- `SIO_KEEPALIVE_VALS = _WSAIOW(IOC_VENDOR, 4) = 0x98000004`; its input struct is `{ u_long onoff, keepalivetime, keepaliveinterval }`, all in ms — matching libuv's `uv_tcp_keepalive` on Windows.
- The delay reaches the emitter as a `double` (numeric literals are f64 here), so it is `fptosi`'d to i64 before the `sdiv`; a typed i64 value is used directly.

## Side effects discovered

The broader §5 Winsock option table (`SO_SNDBUF`/`SO_RCVBUF`/`SO_LINGER`/`SO_RCVTIMEO`/`SO_SNDTIMEO`) remains unaddressed, but no user-reachable JS path emits those today — Node exposes no setter for them on `net.Socket`/`dgram`. They stay recorded in TDD-00180 §5 as translation-layer correctness to add if a path ever reaches them; `TCP_KEEPIDLE` is fixed here because `setKeepAlive`'s delay *does* reach it.
