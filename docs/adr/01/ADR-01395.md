# ADR-01395: The pool's completion port on its own uv_async_t

- **Relations**: Implements TDD-00244; Extends ADR-01394
- **Date**: 2026-10-05

## Context

Each event-loop thread has a completion port in `klainpool.c`. Pool work
items, Worker events and MessagePort deliveries complete into it. Its
in-flight count holds the loop: outstanding work, a ref'd Worker, a
started MessagePort. The select bridge read that count each pass through
`__kml_pool_keepalive` and drained the port through
`__kml_pool_dispatch`, woken by the bridge's shared `uv_async_t`.

Other threads change the count: a Worker's exit and `ref()`, and
deliveries to a port owned by another thread. libuv lets only the loop's
own thread change what holds the loop (`uv_ref`/`uv_unref`).

## Decision

- **Each POSIX port owns a `uv_async_t`** on its thread's loop. Its
  callback drains the completions and pokes the connection fibers, as the
  pass did.
- **The async is referenced exactly while the count is positive.** A
  count change on the port's own thread re-matches the reference at once.
  A change from another thread sends the async, and the loop thread
  re-matches the reference in the callback. A loop never exits while a
  hold is pending, because a hold taken from another thread always comes
  with a wake.
- The bridge's own wake no longer serves the pool, and its accessor
  functions are deleted.
- Windows keeps the two hooks until Stage 6.
