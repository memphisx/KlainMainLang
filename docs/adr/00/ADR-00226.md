# ADR-00226: Fix exponential-time `inferExprType` on deep binary expressions

- **Date**: 2026-08-19

## Context

Running the full Test262 corpus (`make conformance`) after the intersection-types
work ([ADR-00225](ADR-00225.md)), the run wedged at ~53,500/53,578 files: the
progress counter froze while the process pinned ~5 cores at 100% indefinitely.
The per-file subprocess timeout (5s, for clang and the compiled binary) could not
catch it, because the conformance tool calls the emitter *in-process* — so a
compiler that loops on a given file loops inside the tool's own goroutines. The
Aug 18 run had completed the same tail, so this was newly reachable.

## Investigation

A `SIGQUIT` goroutine dump of the hung process showed an unbounded
`inferExprType` recursion cycling between two lines of the `*ast.BinaryExpression`
case in `codegen/llvm/emit_exprs_types.go`:

- the bigint short-circuit (then :336) inferred **both** operands:
  `inferExprType(ex.Left).IsBigInt || inferExprType(ex.Right).IsBigInt`;
- then the operator switch inferred them **again** in each arithmetic branch
  (`+`, `-`, `**`, `??`, …), e.g. `lt := inferExprType(ex.Left); rt := inferExprType(ex.Right)`.

So every binary node re-inferred each child ~twice, and each of those re-inferred
*their* children twice, and so on: inference cost `O(2^depth)`. A left-associative
chain like `a + b + c + ...` has its left operand be another binary node at every
level, so a ~40-term chain is ~2^40 inference calls — minutes-to-hours of pure CPU,
indistinguishable from a hang. Test262 has many deep string-concatenation and
arithmetic expressions; one in the corpus tail crossed the threshold. (The
intersection parser change likely made a specific file reach codegen that
previously failed at parse on a `&` in a type position — but the exponential blow-up
is a pre-existing latent bug independent of intersections.)

Reproduced directly: a generated 45-term `"x" + "x" + ... ` chain never finished
compiling before the fix.

## Decision

Infer each operand exactly once, at the top of the `*ast.BinaryExpression` case,
and reuse the two results (`lt`, `rt`) everywhere below — the bigint check and
every operator branch. `inferExprType` does no codegen and has no side effects, so
computing both operands eagerly (even for `&&`/`||`/`??`, which may not need the
right one) is free of observable change; the bigint check already forced both
unconditionally anyway. This makes each node do exactly two recursive calls →
inference is now linear in expression size. Behavior is otherwise identical: every
branch returns the same type it did, just off the hoisted values.

## Implementation notes

Purely local to the `*ast.BinaryExpression` case in `emit_exprs_types.go`. No
signature or type changes; no other `inferExprType` case was touched.

## Side effects discovered

Surfaced only because the conformance tool runs the emitter in-process with no
wall-clock guard around a single file's codegen. A defensive per-file compile
timeout in the tool would have turned this from a whole-run hang into one
`compile (timeout)` result — worth considering separately, but the real fix is the
linear-time inference here.

## Verification

- The generated 45-term concatenation now compiles in ~0.07s and prints the
  correct length; a 64-term string chain and a 64-term numeric chain are added as
  regression tests (`tests/inference_test.go`) — the test framework compiles and
  runs them, so a re-regression would time the suite out.
- `go test ./tests/ -run 'BigInt|Date|Nullish|Intersection|String|Template'`
  passes — the hoist preserved bigint/Date/`??`/string-concat result typing.
- `make conformance` now runs to completion (previously hung): 5247/53578 vs the
  prior 5225 — language 4770→4801 as deep-expression files that used to hang now
  compile. Apple Silicon (macOS).
