# ADR-00970: Reject Node interpreter flags in compiled binaries

- **Relations**: Extends ADR-00968
- **Date**: 2026-09-15

## Context

The conformance memory blowup (ADR-00968 added a harness reaper as the safety
net) had an underlying *runtime* cause, not just a harness one. A Node-test idiom
re-runs the interpreter to read a value:

```js
// test-http-max-header-size.js
const child = spawnSync(process.execPath, ['--max-http-header-size=10', '-p', 'http.maxHeaderSize']);
```

Under Node, `process.execPath` is the `node` binary; the child runs
`node -p '<expr>'` in print-eval mode — a *different* execution — prints `10`,
and exits. There is no recursion because the child never runs the test file.

In a compiled program `process.execPath` is the compiled binary itself, which
has no interpreter mode. Handed `-p`, it ignores the flag and re-runs its own
program body — which re-hits the same `spawnSync`, spawning another identical
child, forever. Each parent blocks in `poll()` inside `__kml_cp_spawn_sync`
awaiting a child that never terminates: an unbounded self-fork chain that
exhausted machine memory.

## Investigation

The leak was isolated by family (a workdir-scoped process scan, ADR-00968):
`child-process`, `cluster`, `worker`, `net`, `dgram`, `spawn` families ran
clean; only `http-` leaked (~146 processes), all attributed to
`test-http-conn-reset.js` and peers, in a parent→child chain (each PID's parent
the previous PID). Sampling a live orphan showed the stack
`main → __kml_cp_spawn_sync → poll`, i.e. blocked in spawnSync. The trigger was
`spawnSync(process.execPath, [..., '-p', <expr>])`. A minimal standalone
reproducer — `spawnSync(process.execPath, ['-p', '1 + 1'])` — fork-bombed to
2,600+ processes in five seconds.

The faithful behavior (a compiled binary acting as a `node -p` interpreter,
evaluating an arbitrary runtime source string) is a genuine impossibility: the
same limit as eval/vm, which this compiler supports only for compile-time-known
code. So these specific tests cannot pass. But the infinite recursion is a real
bug independent of that: the binary should not pretend an unhonorable
interpreter invocation is a normal run of itself.

## Decision

A compiled binary that reads `process.execPath` (the prerequisite for spawning
itself) now runs a startup guard before its program body: if `argv` contains a
flag that unambiguously requests Node interpreter/eval mode — `-p`, `--print`,
`-e`, `--eval`, `-i`, `--interactive` — it writes a diagnostic to stderr and
exits with status 9, instead of running `main`.

This mirrors what Node itself does with a flag it rejects (exit nonzero), breaks
the recursion at the first spawned child, and turns the self-re-exec tests into
honest nonzero-exit failures rather than a fork bomb.

The guard is gated on `process.execPath` use (the only way a program passes its
own path to spawn), so a compiled CLI tool that never reads `execPath` is
unaffected even if it takes a `-p`/`-e` argument of its own — the minimal blast
radius. The flag set is limited to interpreter/eval flags for the same reason.

## Implementation notes

- `codegen/llvm/runtime_interp_guard.go`: `ensureNodeInterpFlagGuard` emits
  `@__kml_reject_node_interp_flags(i32 %argc, ptr %argv)` — an argv loop doing
  `strcmp` against each flag, writing the message via `write(2, …)` and calling
  `exit(9)` on a match. Emitted once, during codegen.
- `ensureExecPath` (runtime_process.go) calls the guard-emitter, so the guard IR
  is present whenever `usedExecPath` is set (before final assembly).
- `EmitProgram` (emitter.go) emits the guard call at the top of `main`, gated on
  `usedNodeInterpGuard`, after the alloca/setvbuf prologue and before the body.

## Side effects discovered

- These interpreter/eval-flag tests still cannot *pass* (klain is not a JS
  interpreter). They now fail cleanly on a nonzero child exit. A test whose
  expected value is gated behind an unimplemented Node CLI flag (e.g.
  `--max-http-header-size`) fails on the flag, not via fork bomb.
- The harness reaper (ADR-00968) remains as defense-in-depth for any other
  escape path and as the machine-safety backstop.

## Verification

- `tests/childprocess_test.go`:
  `TestE2EChildProcessExecPathInterpFlagRejected` —
  `spawnSync(process.execPath, ['-p', '1 + 1'])` returns `status: 9`, no
  recursion. Passes.
- Standalone repro confirmed fixed: the parent spawns exactly one child, which
  exits 9 with the diagnostic; zero leftover processes (previously 2,600+/5s).
- Normal programs unaffected: a program reading `execPath` runs with no args and
  with non-interpreter args; a program not reading `execPath` runs even with a
  `-p` argument of its own.
- `child_process` + `process` E2E suites pass; `go build`/`go vet` clean.
  macOS arm64 (M4).
