# ADR-00889: Array-destructuring default applies on an `undefined` element (fixes invalid IR + semantics)

- **Date**: 2026-09-12

## Context

`const [x = 23] = [undefined]` (and the elision-hole form `const [x = 23] = [,]`)
emitted invalid IR — `store ptr 0x4037000000000000, ptr %slot` (`error: floating
point constant invalid for type`). Surfaced as the largest single cluster in the
fresh invalid-IR histogram: 18 of the 25 `floating point constant invalid for
type` files were the Test262 `ary-ptrn-elem-id-init-{undef,hole}` family (across
`const`/`let`/`var`/`for-of`/`for-await-of`). Reproduced on macOS arm64 from the
2026-09-12 strict conformance faillist.

Two bugs shared one root: an array element typed `undefined` (a literal
`[undefined]` or a hole) is a `ptr`/`undefined`-represented slot, but a numeric
default is a `double` — and the destructuring emitter (a) stored the default
into that slot without matching its representation (the invalid IR, in the
runtime-dead out-of-bounds branch that clang still validates), and (b) applied
the default only on an out-of-bounds index, never on an in-bounds `undefined`
element — so even had it compiled, `const [x = 23] = [undefined]` would bind
`undefined`, not `23`. JS applies a destructuring default whenever the matched
value is `undefined`, not only when the position is absent.

## Investigation

`unpackArrayPatternInto` (`emit_arrays_core.go`) branches per element on
in-bounds vs out-of-bounds; the scalar out-of-bounds default did
`coerce(defVal, elemTy)` then `store elemTy.IR …`. For a `number[]`/string source
this is fine, but for an `undefined`-typed element `elemTy.IR` is `ptr`, and
`coerce(double, ptr)` keeps the double register (the documented "coerce-honesty"
gap) → `store ptr <fpconst>`. The in-bounds branch loaded the element (always
`undefined`) and bound that, so the default never applied. `TypeUndefined` is
`{IR:"ptr", IsNull:true, IsUndefined:true}` (`types.go`), and both `[undefined]`
and a hole `[,]` type the element `undefined` — confirmed by reproducing both.

## Decision

When an element position has a default **and** its type is statically
`undefined` (`elemTy.IsUndefined`, a non-nested scalar/array leaf), bind the
name directly to the default — skipping the in-bounds/out-of-bounds branch
entirely. The element is always `undefined`, so the default always applies
(correct value), the binding takes the default's own type (correct type,
`const [x = 23] = [undefined]` → `x: number`), and no mismatched store is
emitted (no invalid IR). An array-typed default routes through the existing
`boxArrayValue` header slot; a scalar default gets a slot of its own type.

This is narrower than fully general default-on-`undefined` (a `(T | undefined)[]`
source with a runtime-`undefined` element would still need a runtime check +
type union — a separate, larger item), but it exactly covers the observed
family: a statically-`undefined` element is where both the invalid IR and the
wrong value actually occurred.

## Implementation notes

- The new branch sits before the in-bounds `icmp`/`destr.ok`/`destr.oob`
  emission, guarded on `elem.Default != nil && elemTy.IsUndefined && elem.SubArray
  == nil && elem.SubObject == nil` — nested sub-patterns keep their existing
  path (a default on a nested pattern is already a clean rejection).
- Unaffected: a real-typed source with a default (`[a = 10, b = 20] = [1]` →
  `1 20`), an in-bounds present element, and OOB-over-a-typed-source all keep
  their existing branch.

## Verification

- The four sampled Test262 files (`ary-ptrn-elem-id-init-{undef,hole}` under
  `const`/`let`/`for-of`) now compile and run clean (exit 0 — they self-assert,
  so this is a PASS, not merely a compile). Expect ~18 strict + comparable js
  conformance gains, and the `floating point constant invalid for type` bucket
  drops from 25 to ~7.
- New `TestE2EArrayDestructuringDefaultUsedWhenElementUndefined`; existing
  destructuring suite green; `go build`, `go vet ./...`, gofmt clean; full
  `make test-par` gate run.
