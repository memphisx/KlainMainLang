# TDD-00092: `for await...of` over a sync array

- **Status**: Implemented (see ADR-00272)
- **Date**: 2026-08-20

## Context

`for await...of` (TDD-00085/00089) consumed an async generator or a `[Symbol.asyncIterator]()`
class. In JS, `for await` also works over a **sync** iterable — it awaits each element, so an
array of promises is consumed sequentially and an array of plain values awaits each as a harmless
identity:

```ts
for await (const x of [f(1), f(2), f(3)]) { … }   // awaits each promise in order
```

This was a clean rejection ("requires an async generator or a class with `[Symbol.asyncIterator]`").
It is the common sync-iterable case (an array of promises); closing it narrows the `for await`
row's remaining caveat to the rarer sync-generator/Map/Set forms.

## Design

Reuse the array for-of loop shape, awaiting each element before binding. When `for await`'s
iterable is an array, dispatch to `emitForAwaitOfArray`:

- The bound value's type is the element type **awaited**: `T` for a `Promise<T>` element, the
  element type itself for a plain value.
- Loop by index over the array's `(ptr, len)` (via `resolveArrayForHOF`); each turn, load the
  element and — if the element type is a `Promise` — drive it to settled with the shared
  `emitAwaitTaskPromise` (which re-throws a rejection, so a rejected element propagates to a
  surrounding `try/catch` and stops the loop). A plain-value element is an identity await.
- Bind the awaited value to the loop variable (or unpack a destructuring pattern through the same
  `unpack*PatternInto` core the other for-await paths use).

Sequential by construction (element N settles before N+1 binds), matching JS `for await` over a
sync iterable. A raw-fetch `Promise<Response>` element is a clean rejection (its value isn't read
through the task-promise slot — a rarer, separate case).

## Stages

1. **Dispatch + loop.** Array branch in `emitForOf`'s `for await` gate → `emitForAwaitOfArray`.
2. **Verify** an array of promises (sequential), an array of plain values (identity await),
   rejection propagation, and a destructuring loop variable.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Array `(ptr,len)` resolution (`resolveArrayForHOF`) | Built | emit_arrays_core.go |
| Task-promise await (`emitAwaitTaskPromise`) | Built | emit_async.go — drives + re-throws |
| Destructuring unpack core | Built | emit_generators.go for-await paths |

## Open questions

- **Other sync iterables.** A sync generator, `Map`, or `Set` in `for await` stays a clean
  rejection — rarer than an array, and each needs its own streaming/await wiring. Left as a
  narrowed caveat, not silently mishandled.
- **A named `function` declaration can't read a top-level `const`/`let`** — surfaced while
  testing, unrelated to this work: top-level statements are emitted into the synthetic `main()`
  (the variable is a `main()` local), and a hoisted `function` is a separate top-level LLVM
  function with no access to those locals. An arrow function / closure captures it fine (closure
  env), so the gap is specific to `function` declarations. A pre-existing architectural
  limitation (module-level variables would need promotion to true globals), out of scope here.
