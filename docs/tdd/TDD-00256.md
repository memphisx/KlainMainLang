# TDD-00256: Optional-field presence

- **Status**: Implemented
- **Date**: 2026-10-17

## Context

An optional member, `name?: T`, can be missing from an object or present holding `undefined`. Node tells the two apart:
- `{ a: 1, b: undefined }` prints `{ a: 1, b: undefined }`.
- `Object.keys` gives `['a', 'b']`.
- `'b' in o` is true.
- `JSON.stringify` drops the key either way.

This compiler stores an optional field's value only. An undefined value is read as "no key" (`Field.Optional`, `types.go`), so:
- the present-undefined case prints and enumerates as missing (BACKLOG #94);
- `delete c.f` on a class's optional field cannot be expressed at all, so it is a compile error (#92).

The data only needs to be right in these places:
- what keys an object has: `in`, `Object.keys`/`entries`, `for…in`, `hasOwnProperty`, `Object.hasOwn`;
- inspect;
- spread and `Object.assign`;
- `delete`.

A read of the value is already right, because both states read `undefined`.

## Design

### Options

**A. Presence bits in the header word.** Bits 51–63 of field 0 are free (`objheader.go`). One bit per optional field would mark "key present".
- Every exact comparison of a header against a type id would have to mask the bits first: `instanceof`, layout dispatch, `emitAnyToLayout`, and the C runtime's checks of the header word.
- There are only 13 bits.
- Rejected: dozens of comparison sites change, and a missed one fails silently.

**B. A second absent value meaning "missing".** A distinct NaN-box pattern for scalars, and a third sentinel cell for pointers, alongside `nullRef`.
- Every undefined test, comparison, conversion and box would have to accept both values. Those sites are spread over the code generator and the C runtime, so the change has no clear edge.
- Rejected for the same reason as A.

**D. A side table of present-undefined keys.** `shapesrc/shape.c` already keeps per-object expando keys in a hash table keyed by object address.
- Marking "present, undefined" there would leave layouts alone, and writes of `undefined` into optional fields are rare.
- Nothing removes an entry when its object is freed. A new object allocated at the same address would inherit stale marks, and under `-mm=gc` the table also keeps dead objects alive.
- Rejected: correctness would depend on address reuse never happening.

**C. A presence word in the layout (recommended).** A layout with optional fields gets a hidden `i64` field: bit *k* is set when optional field *k* has its key. Field values and their representations do not change.
- Object literals set the bits statically, from which keys they write.
- Assigning to an optional field sets its bit. `delete` clears it and stores the field's undefined.
- JSON projection sets the bits from the keys the input actually has.
- Copies keep the bits: structural views, `emitAnyToLayout` and copies field by field.
- The key surfaces listed under Context test the bit instead of "value is undefined".
- Layouts with more than 64 optional fields get a second word.
- Class instances with optional fields get the same word, which makes `delete` on such a field expressible (#92).

The layout table (`emit_shape.go`, with `shapesrc/shape.c` looking layouts up by header) records where the word sits. The C runtime (`dynobj`, inspect, JSON) then finds it from the header's type id, the same way it finds field offsets today.

### Stages

1. **Layout.** The hidden field, its entry in the layout table, and bits set by object literals and assignment.
2. **Readers.** `in`, `Object.keys`/`entries`, `for…in`, `hasOwnProperty`, and inspect test the bit.
3. **Copies.** JSON projection, spread, `Object.assign`, `structuredClone`, and boxing to `any` or a dynamic object keep the bits.
4. **Classes.** The word on class instances, and `delete` on an optional field.

Each stage ships with E2E tests that compare against Node. #94 closes after stage 2 and #92 after stage 4.
