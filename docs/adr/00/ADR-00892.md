# ADR-00892: Generator `.next()`/`.return()` value coercion + emitter guard against a scalar-into-aggregate store

- **Date**: 2026-09-12

## Context

`yield [...yield]` driven by `iter.next(false)` emitted invalid IR: `store {ptr,
i64} 0, ptr %sentField` — a bare scalar constant into the array-typed sent-value
slot (`error: integer constant must have integer type`). The Test262
`yield-spread-arr-single` / `named-yield-spread-arr-single` family (6 files
across expression/statement × sync/async generators), part of the 2026-09-12
strict invalid-IR faillist.

## Investigation

The generator's yield-result ("sent") field is typed as the generator's element
type. For `yield [...yield]` the two yields (`yield` → undefined, `yield [...]` →
array) unify the element type to a form the coerce mis-handles: `iter.next(false)`
ran `coerce(false, elemTy)` in `emitGeneratorNextByValue`, which returned the
element type but kept the boolean's `0` register (the known "coerce-honesty"
gap), and `emitSyncGeneratorNextCore` then stored that `0` into the aggregate
sent slot. Traced by instrumenting `emitInstr` — the store originates at
`storeGeneratorField` from the `.next()` core, not the creation init. Fully
untangling the generator model here (a distinct TNext type separate from the
yield type, plus union/undefined element types) is a large feature, out of scope
for the invalid-IR sweep.

## Decision

Two layers, matching the sweep's "clean rejection over invalid IR" principle:

1. **Coerce the `.next()`/`.return()` argument with `coerceChecked`** at the
   three sync/async sent-and-return sites (`emitGeneratorNextByValue` sync +
   async, the `.return()` value), so a plainly-mismatched argument is a clean
   COMPILE_ERROR naming the position (matching tsc's generator-TNext checking).
   This alone fixes the async family, where the element type is a clean array.

2. **An emitter store-guard** (`scalarConstIntoAggregateStore`, alongside the
   existing cluster-B empty-operand guard in `emitInstr`): a bare scalar
   constant (`0`, `-1`, `1.5`) stored into an aggregate-typed slot (`{ … }`) is
   rejected cleanly. A register, `zeroinitializer`, `null`, or an aggregate
   literal into the same slot passes untouched, so only the invalid shape is
   caught. This backstops the sync case (where the unified element type slips
   past `coerceChecked`) and is a permanent rail against any future
   coerce-honesty slip that would otherwise ship a malformed aggregate store to
   clang.

## Implementation notes

- The existing `malformedStoreValueOperand` guard only handled an *empty*
  operand and mis-parses aggregate type tokens (they contain spaces/commas);
  `scalarConstIntoAggregateStore` parses the `{ … }` type by its closing brace,
  then classifies the value operand's first character.
- The `coerceChecked` sites reuse the standard coercion-soundness machinery, so
  a genuinely-coercible argument still flows through.

## Side effects discovered

- The generator element type conflates the yielded type (`T`) and the sent type
  (`TNext`); a faithful `iter.next(x)` where `x`'s type differs from the yield
  type needs the separate-TNext model (deferred). Until then such a call is a
  clean rejection rather than invalid IR.

## Verification

- The 6 `yield-spread-arr-single`/`named-` files reclassify CLANG_ERROR → clean
  COMPILE_ERROR (both sync and async). Real generators unaffected: a
  sent-value generator (`let x = yield 1; … yield x + 10` with `.next(5)`),
  array-yielding generators, and `for…of` over them all run correctly.
- New `TestE2EGeneratorMismatchedNextValueRejected`; generator/array/tuple/
  collection/spread suites green (the store guard is global — checked for
  over-rejection); `go build`, `go vet ./...`, gofmt clean; full `make test-par`
  gate run.
