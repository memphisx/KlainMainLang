# ADR-00943: Array-valued Map/WeakMap values via the shared header pointer

- **Relations**: `Extends ADR-00939, ADR-00940` (array reference semantics, TDD-00213)
- **Date**: 2026-09-15

## Context

`Map<K, T[]>` (an array as a Map value) produced invalid IR — `clang`
rejected `ptrtoint ptr %{ptr,i64}` where the array's `{ptr,i64}` aggregate
was fed into the map's uniform i64 value slot. Confirmed pre-existing on
committed HEAD (not a TDD-00213 regression); one of five array-in-container
bugs surfaced closing out the reference-semantics work.

Repro:

```ts
const m = new Map<string, number[]>()
m.set("a", [1, 2, 3])
const v = m.get("a")
```

`./klainmain --emit-llvm x.ts | clang -O0 -S -emit-llvm -x ir -o /dev/null -`
→ `'%tN' defined with type '{ ptr, i64 }' but expected 'ptr'`.

## Investigation

Map values are stored as one i64 word (`emit_collections.go`
`valueToMapVal`/`mapValFromI64`). An array Value's `Ty.IR` is now `"ptr"`
(the header-pointer model, ADR-00939), but its `Ref` is still the
`{ptr,i64}` aggregate — so `valueToMapVal`'s `case "ptr"` emitted
`ptrtoint ptr <aggregate>`, the invalid IR. The fix mirrors
`storeArrayFieldHeader` (Stage 2): store the array's shared **header
pointer** as the i64, and rebuild the array from it on `get()`.

Getting the surrounding semantics right pulled in three coupled spots, each
verified against a runtime repro rather than by reading:

- Truthiness (`toBool`, `emit_exprs_types.go`) already had a nullable-array
  path testing the data pointer.
- `map.get(k) === undefined` was constant-folded to `false` by
  `emitNullableScalarNullCompare` (`emit_nullable_scalar.go:512`) because the
  static type isn't marked `IsUndefined`.
- Marking the array `IsUndefined` was rejected: `toBool` folds ANY
  `IsUndefined` value's truthiness to a constant `false`
  (`emit_exprs_types.go:3461`) — a separate pre-existing bug that also breaks
  string/object-valued maps (`if (map.get(presentKey))` wrongly false). See
  Side effects.

A deeper inconsistency shaped the final design: an absent array is a **null
header** in a Map miss but an **empty (non-null) header** in a null
`T[] | null` object field. A header-null test is right for the first and
wrong for the second; a **data-pointer** test is consistent for both (both
rebuild `{null,0}`). The data-pointer test is therefore used everywhere.

## Decision

- `valueToMapVal`: an array value stores `arrayReturnHeader(v)` (its shared
  header, minting one for a transient) `ptrtoint`'d to i64.
- `mapValFromI64`: an array value type rebuilds via a null-guarded header
  deref (`arrayValueFromHeaderSlotGuarded`) so a miss (i64 0 → null header)
  reads as the `{null,0}` empty array instead of dereferencing null.
- The array `get()` result is marked `Nullable` (NOT `IsUndefined`) so its
  truthiness tests the array pointer: a miss is falsy, a present array truthy.
- `emitNullableScalarNullCompare` defers to the operator path for an array
  operand compared to the `undefined` literal only (a `T[] | null` field
  `=== null` keeps its presence-bit handling), so `map.get(k) === undefined`
  is a runtime null-pointer test.
- The operator path's array-vs-nullish branch (`emit_exprs_operators.go`) is
  extended from `null` to any nullish literal (null/undefined/void).
- Array bindings propagate `Nullable` to the symbol; the array-identifier
  load (`emit_exprs.go`) rebuilds a nullable array through the null-guarded
  loader, so `const z = m.get(missKey); if (z)` is both safe and falsy.

## Implementation notes

`arrayValueFromHeaderSlotGuarded` (new, `emit_arrays_core.go`) is the
null-guarded sibling of `arrayValueFromHeaderReg`, factored so both the
map-get and the nullable array-identifier reload share one guard. The
data-pointer truthiness/equality test is deliberately uniform across the two
absent-array representations rather than header-based.

## Side effects discovered

- **Pre-existing `toBool` bug (NOT fixed here):** a possibly-undefined
  POINTER value (a `string | undefined` / object `V | undefined` Map get)
  folds its truthiness to a constant `false` at `emit_exprs_types.go:3461`,
  so `if (map.get(presentStringKey))` is wrongly false. Confirmed independent
  of arrays. Left as a separate fix — it touches the hottest truthiness path
  and warrants its own change + full test-par. Tracked in docs/BACKLOG.md.
- **Present-empty nullable array edge:** an empty array stored and read back
  from a Map is truthy in JS but reads falsy / `=== undefined` here, because
  an empty array and an absent one are both `{null,0}` (null data pointer).
  This is the same edge every nullable-array test in the compiler shares
  (e.g. RegExp.exec `T[] | null`); documented, not newly introduced.

## Verification

- `TestE2EMapArrayValue` (tests/collections_test.go): store/get round-trip,
  reference identity (`get(k) === original`, mutation visible), miss
  `=== undefined` + falsy, present truthy, empty stored.
- Regression: `go test -run 'TestE2E(Map|WeakMap|NewMap|ForOfMap|Array|
  Nullable|.*Truthiness|.*Optional|.*NullCompare)'` green on macOS arm64
  (Apple Silicon M4), including the previously-regressed
  `TestE2ENullableArrayField`.
- `clang -O0 -S -emit-llvm -x ir` clean on the repro.
