# ADR-00769: `lstat(symlink).size` is the target-path length on Windows

- **Relations**: fixes a Windows-only gap in [ADR-00497](ADR-00497.md) (the path-based fs ops, incl. `lstatSync`/`readlinkSync`) and the Windows stat shim ([ADR-00495](ADR-00495.md) offsets, [ADR-00737](ADR-00737.md) symbol aliasing); addresses [TDD-00180](../tdd/TDD-00180.md) §4
- **Date**: 2026-09-07

## Context

On POSIX a symlink's `lstat().size` is the byte length of the path string the
link points at (the target). Node preserves this on Windows too — libuv fills
`statbuf.st_size` for a reparse point from the link target's length, so
`fs.lstatSync(link).size === fs.readlinkSync(link).length`. The port's Windows
stat shim (`win32src/win32fs.c`) instead reported `st_size` from
`BY_HANDLE_FILE_INFORMATION.nFileSize*`, which for a reparse point opened with
`FILE_FLAG_OPEN_REPARSE_POINT` is **0** — so `lstatSync(link).size` came back 0
on Windows where Node returns the target length. (`statSync(link).size`, which
follows the link, was already correct — it stats the target file.) POSIX hosts
were already faithful via native `lstat(2)`; this is a Windows-only fix.

## Decision

In `stat_handle`, when the resolved mode is `S_IFLNK` (an `lstat` of a reparse
point that `is_reparse_link` recognises), overwrite `st_size` with the byte
length of the link target, read from the same reparse buffer `readlink` uses.
The reparse-parsing that `readlink` already did inline is factored into a shared
helper `reparse_target_utf8(HANDLE)` returning the target as a malloc'd UTF-8
string (PrintName-preferred, `\??\` NT-prefix stripped), so the size and
`readlinkSync` derive from one code path and agree by construction. A forward
declaration lets `stat_handle` (earlier in the file) call the helper (defined
beside `readlink`).

## Faithfulness notes

- `lstat(link).size === readlinkSync(link).length` holds on Windows as it does on
  POSIX. The value is the length of the *user-facing* target form (PrintName) —
  the string `readlinkSync` returns — which for a link created through this
  compiler's `symlinkSync` round-trips to the exact target argument.
- fd `fstat` and following `stat` are unchanged (never `S_IFLNK`).

## Verification

- New E2E test `TestE2EFsLstatSymlinkSize` (`tests/fs_test.go`): creates a
  symlink, asserts `lstatSync(link).size === target.length` and
  `statSync(link).size === 11` (the target's bytes). Skips on a Windows box
  without symlink privilege (Developer Mode/admin), the same probe the existing
  `TestE2EFsPathOps` uses.
- **Docker Linux `klain-ci:latest`**: `TestE2EFsLstatSymlinkSize` +
  `TestE2EFsPathOps` pass (POSIX native `lstat`, symlinks need no privilege).
- **Windows 11 native**: the `win32fs.c` shim compiles clean and `lstat` on a
  regular file works, but the symlink assertions **skip** — this dev box has no
  symlink privilege (Developer Mode off), the same skip `TestE2EFsPathOps` takes.
  The Windows `S_IFLNK` size path is therefore **CI-lane-pending** (the runner
  creates symlinks), not yet exercised on a real Windows symlink.
- `go build`, `go vet ./codegen/...` clean. `make status`/`status-check`,
  `make reference-check`, `make conformance` run at delivery.
