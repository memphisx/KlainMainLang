# TDD-00077: JSON dynamic-tree rewrite — validating parser, `any`-typed parse, dynamic-value stringify

- **Status**: Partially Implemented — Track S (stringify `space` pretty-printing + generic `toJSON()`) shipped ([ADR-00222](../adr/ADR-00222.md)); Track P **P1** (validating parser + tagged value tree + catchable `SyntaxError`) shipped ([ADR-00223](../adr/ADR-00223.md)); **P3** (type-directed projection off the tree — nested objects, array/object-array fields, top-level `T[]`, float-variable fix) shipped ([ADR-00224](../adr/ADR-00224.md)); **P4** (`any`-typed/dynamic parse + dynamic-value stringify) is not started
- **Date**: 2026-08-18

## Context

JSON is the most-used serialization surface in real JS/TS, and this compiler's implementation is the narrow, statically-typed slice of it. `JSON.stringify` is broad but has holes; `JSON.parse` only handles a flat object of primitive fields (and a bare `number`). The accumulated gaps, from the status pages ([JSON.md](../status/JSON.md), and mirrored in [NETWORKING.md](../status/NETWORKING.md)'s `Response.json()` row + [README.md](../status/README.md)'s rollup):

**`JSON.parse` gaps**
- Nested object fields — clean-rejected ([ADR-00007](../adr/ADR-00007.md)); the original driver of [TDD-00015](TDD-00015.md).
- Array-typed fields (`{ tags: string[] }`, `{ items: Item[] }`) — clean-rejected ([ADR-00189](../adr/ADR-00189.md)).
- Top-level `JSON.parse` → `T[]` — not implemented at all.
- Parsing into a `float64`/`float32`-annotated `number` — a hard *compile* failure ([ADR-00166](../adr/ADR-00166.md)): the float target falls through to the generic branch, which returns a `ptr` stored into a `double` slot.
- No `SyntaxError` on malformed input — the current `strstr`-based field-finder never validates, so bad JSON silently yields defaults instead of throwing.
- No parse into `any`/`unknown` — there is no dynamic value to hold an arbitrary shape.

**`JSON.stringify` gaps**
- No `space` argument — `JSON.stringify(obj, null, 2)` (pretty-printing) is silently ignored, despite being one of the most-used forms (config files, logs, readable request bodies).
- No generic `toJSON()` — only `Date` is special-cased; a user class with `toJSON()` isn't honored.
- No dynamic-value / mixed-array stringify — a heterogeneous or `any`-typed value has no single static type to serialize against.

TDD-00015 scoped the nested-object case with an **additive span-finding** design (extend the existing per-field text extractors with brace/bracket matching), and *deliberately rejected* a full parse-to-tree rewrite as too big for the problem in front of it. The decision now is to take the rewrite anyway — because the goal has widened from "nested objects" to *perfect the whole JSON surface*, and the two hardest remaining items (**runtime `SyntaxError` validation** and **`any`-typed parse**) are exactly the ones span-finding cannot reach: both need a real parser that builds an in-memory value. Once that parser exists, every typed-projection gap (nested objects, array fields, top-level arrays, float targets) falls out of walking the tree against the target type. This TDD therefore **supersedes [TDD-00015](TDD-00015.md)**.

Ordering decision: **stringify first**. Its highest-value wins (`space`, `toJSON()`) are additive to the existing serializer and need none of the parser rewrite, so they ship independently and early; the tree-dependent parse work follows.

## Design

### Two independent tracks

- **Track S (stringify)** — additive, no tree. Ships first.
- **Track P (parse)** — the dynamic-tree rewrite. The substantial new subsystem.

### Track S: complete `JSON.stringify`

1. **`space` argument (pretty-printing).** `JSON.stringify(value, replacer, space)` — support `space` as a number (N spaces, capped at 10 per spec) or a string (used literally, first 10 chars). Thread an indent context (current depth + unit) through `emitJSONStringifyValue`/`Object`/`Array`, inserting newline + `depth×unit` before each element/member and a space after each `:`. The `replacer` (2nd arg) stays out of scope in V1 (a clean rejection if a non-`null` replacer is passed), since the function/array replacer is far less used than `space` and independent of it.
2. **Generic `toJSON()`.** Before the `IsObject` branch, if the value's class/type declares a `toJSON()` method (check `MethodSigs["toJSON"]`, the same lookup `toString()` override already uses), call it and serialize the result, exactly as the `Date` special-case already does — then delete the `Date`-specific path in favor of `Date.toJSON` being an ordinary instance of this rule.
3. **Dynamic-value stringify** (mixed arrays, `any`-typed values) is deferred to Track P Stage P4 — it needs the same dynamic representation the parser produces, so it lands with it rather than as a second, throwaway mechanism.

### Track P: the JSON value tree

The core is a runtime parser that turns JSON text into an in-memory **tagged value tree**, plus two consumers of that tree.

**P1 — the tree representation + validating parser.**

- **Node shape** (a C struct, one tag + a union-ish payload):
  - `kind`: `object | array | string | number | bool | null`.
  - `string`: a decoded (unescaped) C string.
  - `number`: store *both* the raw lexeme and a parsed `double` — the tree is type-agnostic, and typed projection (P3) coerces per the target's numeric type (`i64`/`float32`/`float64`), which a bare `double` alone would lose precision for on large integers (the same 2^53 concern bigint exists for).
  - `object`: a list of `(key, child)` pairs (insertion-ordered; duplicate keys keep JS's "last wins").
  - `array`: a list of child nodes.
- **Where it lives**: a self-contained embedded C file compiled alongside the program — the established pattern for a substantial runtime component (`bigint_*.c` [TDD-00074](TDD-00074.md)/[ADR-00216](../adr/ADR-00216.md), `gcshim.c`), rather than hand-written text IR, which would be unmaintainable for a recursive-descent parser. The ABI is a small `__kml_json_*` surface over an opaque node `ptr`, mirroring the bigint ABI's shape.
- **The parser**: a standard recursive-descent JSON tokenizer + parser producing the tree. **Malformed input throws a catchable `SyntaxError`** — reuse the tagged-error machinery ([TDD-00013](TDD-00013.md)/[ADR-00082](../adr/ADR-00082.md)) and the same catchable-throw path the bigint div-by-zero guard already uses, so `try { JSON.parse(bad) } catch (e) { ... }` works. The error carries a position (offset) for a useful message, aligning with [TDD-00072](TDD-00072.md)'s diagnostics.
- **Depth guard (security)**: unlike the *typed*-recursion of the old design (bounded at compile time by the finite type declaration), this parser runs on **untrusted runtime input**, so deeply-nested adversarial JSON could overflow the C stack. A hard nesting-depth limit (reject past e.g. 512 levels with a `SyntaxError`) is a real requirement, not optional — the same class of concern as the object inspector's compile-time bound ([ADR-00221](../adr/ADR-00221.md)), here at runtime.
- **Memory**: nodes via the active allocator (plain `malloc` in manual mode, GC-visible under `-mm=gc` — the tree must be walkable by the collector, same as every other heap value). In manual mode, a typed projection (P3) copies scalars/strings out and the tree becomes garbage; a dynamic parse (P4) keeps the tree alive *as* the value.

**P3 — typed projection (the tree → a statically-typed target).** Given the tree and a compile-time target type, walk them together:
- object type ← object node: per field, look up the key in the node's pairs (bounded to *that* node, which is what structurally prevents the sibling-key false-match the old `strstr` risked), recurse on the field type. **Nested objects fall out.**
- array type `T[]` ← array node: allocate a `{ptr,i64}` array of the node's length, project each element as `T`. **Array-typed fields and top-level `JSON.parse` → `T[]` both fall out**, including `Item[]` (recurse into object elements).
- scalar target ← scalar node: coerce the node's number to the target's numeric type (`i64`/`float32`/`float64` — **the float-target compile bug disappears**, since projection is type-directed instead of falling through to a `ptr` helper), string→string, bool→`i1`.
- **type/shape mismatch** (e.g. target expects an object, node is a string) → a `SyntaxError`/`TypeError` at runtime, matching real JS's runtime failure rather than silent garbage.
- This **retires the entire span-finding extractor path** (`emitJSONParseObject`/`emitJSONParseFieldValue` and the `__kml_json_find_value`/`parse_field_str` helpers) and every current parse caveat/rejection.

**P4 — dynamic parse + dynamic-value stringify (`any`/`unknown`).** When the target is `any`/`unknown` (or unannotated under `-compat=js`, see [TDD-00076](TDD-00076.md)), keep the tree itself as the runtime value, boxed as a dynamic value. Dynamic-value `JSON.stringify` (Track S item 3, and mixed arrays) then walks the tree back out to text. **This is the stage coupled to the dynamic object model** — see Open questions.

### Rejected alternative: keep span-finding, bolt validation on top

TDD-00015's additive span-finding, extended with a validation pre-pass. Rejected because it means maintaining *two* parsers (a validator that walks the whole text, then extractors that walk it again per field) and still cannot represent an `any`-typed result at all — the tree is unavoidable the moment dynamic parse is in scope, so building it once and projecting from it is strictly simpler than validating-then-re-extracting.

## Open questions

- **The central one: does the JSON value tree unify with [TDD-00068](TDD-00068.md)'s D1 per-instance dynamic object model, or start JSON-specific and converge later?** A JSON object node is structurally a per-instance property bag — i.e. a concrete first instance of exactly what D1 describes. Building the tree as (or toward) the D1 representation avoids a throwaway JSON-only dynamic value, but drags P4 into the object-model design's timeline; keeping it JSON-specific ships P4 sooner but risks a second dynamic representation that D1 later has to absorb. **P1–P3 are independent of this and can proceed regardless** — only P4 (dynamic parse / dynamic stringify) is gated on it. Leaning: ship P1–P3 first (they retire every current typed-parse caveat and the float bug), then decide P4's representation once [TDD-00068](TDD-00068.md) Axis 2 is actually being designed.
- **Number representation in the tree** — storing raw lexeme + parsed `double` handles per-target coercion, but confirm the large-integer path (a JSON integer beyond 2^53 projected into an `i64` field) parses from the lexeme, not the lossy `double`.
- **`SyntaxError` message shape and position** — offset-only, or line/column? Ties to [TDD-00072](TDD-00072.md) Part 1's diagnostic renderer; likely offset in V1.
- **Depth-guard limit** — the exact cap (512? configurable?) and whether it's shared with any other runtime recursion bound.
- **Manual-mode lifetime of a dynamic (P4) tree** — a P4 result *is* the tree, so it lives as long as the value; confirm no premature free when the tree is the returned value rather than a projected copy.
- **`replacer` argument** — deferred in V1 (clean rejection for a non-`null` replacer); revisit whether the array-form (key allowlist) is worth a later stage.
