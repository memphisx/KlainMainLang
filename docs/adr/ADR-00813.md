# ADR-00813: Target OS/arch abstraction — macOS→Linux cross-OS builds (TDD-00146 Stage 1 completion)

- **Relations**: `Extends ADR-00809`, `Implements TDD-00146`

- **Date**: 2026-09-09

## Context

ADR-00809 shipped the clang-driver half of cross-compilation (`--target`/
`--sysroot`, the `sfos-aarch64` preset, IR-triple stamping) but rejected any
**cross-*OS*** target at the CLI, because codegen still chose C APIs and struct
layouts from the build host's `runtime.GOOS`/`GOARCH`. Its "Side effects
discovered" section named the remaining work: thread a *target* OS/arch through
those sites so the guard can be lifted. This ADR does that for the one
fully-execution-verifiable direction, **macOS→Linux**.

## Investigation

The host-keyed reads are far more numerous than ADR-00809's "roughly a dozen"
estimate: 122 `runtime.GOOS`/`GOARCH` reads across `codegen/llvm`. Classifying
them splits cleanly in two:

- **Target-code emission** (~the vast majority): every site that decides what C
  the *compiled program* does — `ucontextLayout()` (the fiber context size:
  Darwin 880 vs Linux/arm64 4560 bytes — a mismatch crashes any async/HTTP
  program), `process.platform`/`arch`, `process.execPath`/`cluster`
  (`_NSGetExecutablePath` vs `/proc/self/exe`), the `os` module, the math
  libcall selection, `dgram`, DNS, `fs` stat-struct layouts, `fswatch`
  (kqueue vs inotify), clocks, `net`, `childprocess`, `worker`, FFI default
  libs, and the `-ldl` link decision. Both the Darwin and the Linux code paths
  already exist in the emitter — they were just selected by the host.
- **Host toolchain** (a handful): `HostClangArgv`/`HostClangArgs`/`LinkLibFlags`
  (the clang driver — already special-cased for the cross target), the
  Windows `staticLinkMode` link flags, and the `yoga`/`webview` C++ build/link
  recipes. These describe the machine running clang, not the target.

The mechanism mirrors the existing `crossTarget`/`staticLinkMode` package vars
(`hostclang.go`): a single package-level accessor pair, written once at startup.

## Decision

- **`targetGOOS()` / `targetGOARCH()`** (package-level, `hostclang.go`): return
  the cross-target's parsed OS/arch when a `--target` is active and the triple's
  field was recognized, else the host's `runtime.GOOS`/`GOARCH` — so with no
  cross target the behavior is byte-for-byte the pre-cross behavior. The triple
  is parsed once in `SetCrossTarget` (`tripleGOOS`/`tripleGOARCH`) and cached on
  the `crossTarget` struct; `CrossTargetGOOS()`/`CrossTargetGOARCH()` expose it
  to `main.go`.
- **Convert the target-code-emission sites** from `runtime.GOOS`/`GOARCH` to the
  accessors (the ~30 runtime/emit files); leave the host-toolchain sites reading
  `runtime.GOOS`.
- **Lift the CLI guard for macOS→Linux only.** The cross-OS gate now rejects
  only the pairs that are not (yet) supportable: a Windows target (needs the
  mingw link toolchain, not wired for cross) and a macOS target from a non-macOS
  host (cannot be execution-verified here, so not claimed). macOS→Linux is
  allowed; same-OS cross-arch is unaffected.
- **Reject cross-OS webview/TUI post-emit.** `klain:webview` and `klain:tui`
  (Yoga) still choose their C++ compile/link recipe (libc++ vs libstdc++,
  `.dylib` vs `.so`, macOS frameworks) from the host, so a macOS→Linux build of
  one is rejected with a clear message rather than emitting a broken link. Plain
  CLI plus the whole Node runtime surface cross-compiles fine.

Why macOS→Linux only (not the symmetric Linux→macOS): every enabled path must
be provable by *running* the binary, not by inspection (the project's ✅ rule).
The M4 can link a Linux ELF (lld + the exported sysroot) and run it under an
arm64 Linux container; it cannot run a Mach-O produced on Linux. Windows is a
separate, much larger toolchain story.

## Verification

- `tests/crosstarget_test.go`: `TestCrossTargetMacToLinuxCodegen` asserts from
  the emitted IR that a `sfos-aarch64` build of an async program stamps the
  Linux ucontext size (`[4560 x i8]`, and *not* `[880 x i8]`) and bakes
  `process.platform`/`arch` as `"linux"`/`"arm64"`. The preset and foreign-OS
  guard tests were updated for the new accepted pair. (Runs on Linux + macOS
  hosts, no toolchain needed.)
- **End-to-end macOS→Linux** (Mac host + arm64 Linux container): an async
  program (an `await`ed user async function + array-sort HOF + `TextEncoder`)
  cross-linked on the M4 with `ld.lld` against the exported Sailfish 5.1.0.11
  sysroot → `ELF 64-bit LSB pie, ARM aarch64, interpreter
  /lib/ld-linux-aarch64.so.1`, and *ran* in a `debian:trixie-slim` arm64
  container printing `platform=linux arch=arm64` / `sorted[0]=1 sum=4
  utf8len=6`. The `sum=4` from an awaited async function is the live proof the
  fiber scheduler used the Linux 4560-byte context layout — the Darwin 880 would
  have crashed the task switch. (Mac + arm64 Docker.)

## Consequences

macOS→Linux CLI cross builds are correct and verified. The `targetGOOS()`/
`targetGOARCH()` accessors are now the single place codegen reads the platform;
new runtime code must use them, not `runtime.GOOS`, or it silently mis-targets.
Lifting the remaining pairs (Linux→macOS, any→Windows) is now purely a
verification/toolchain question, not an architectural one. A `bdw-gc` note: a
cross `-mm=gc` build follows the same sysroot rule as the pcre2/curl feature
libs (the target's libgc must be in the sysroot).
