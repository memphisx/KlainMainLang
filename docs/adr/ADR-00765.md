# ADR-00765: `spawn(cmd, args, { detached })`

- **Relations**: Extends [ADR-00433](ADR-00433.md) (spawn options) and [ADR-00763](ADR-00763.md)/[ADR-00764](ADR-00764.md) (the spawn-options struct and mode-bit threading); addresses [TDD-00180](../tdd/TDD-00180.md) §3
- **Date**: 2026-09-07

## Context

Node's `detached` makes a spawned child a new session/process-group leader so it
can outlive its parent (the basis for launching a long-running daemon, usually
paired with `child.unref()`). The remaining spawn-option row after
`env`/`windowsHide`/`timeout`. On POSIX it is `setsid()` in the child before
exec; on Windows it is `DETACHED_PROCESS` (no inherited console) plus
`CREATE_NEW_PROCESS_GROUP`.

## Investigation

The POSIX fork path (`cpSpawnForkIR`) already runs child-side setup (chdir, dup2,
the custom-env `environ` assignment) before `execvp`; `setsid()` slots in there,
gated on a mode bit. The Windows path (`__kml_win_spawn`) already computes a
`create_flag` for `windowsHide` (`CREATE_NO_WINDOW`); `detached` is another
branch of the same `dwCreationFlags`. `DETACHED_PROCESS` and `CREATE_NO_WINDOW`
are mutually exclusive (both concern the console), so one wins. The effect is not
portably observable from an E2E test — Windows has no sessions, macOS no `/proc`
— but on Linux `/proc/$$/stat`'s session field equals the pid exactly when the
child is a session leader, which is a direct repro.

## Decision

- **Option**: `detached` is a literal boolean in `cpSpawnOpts`; a non-literal is
  a clean rejection. A dynamic (non-literal) options object does not read it.
- **Bit threading**: `detached` is mode **bit 3** (`| 8`), joining `windowsHide`
  (bit 2) in `optBits`. The POSIX fork IR reads `mode & 8` directly; the Windows
  path receives it as `flags & 4` (the `mode >> 1` shift in `cpSpawnForkIR`).
- **POSIX**: the forked child calls `setsid()` (declared POSIX-only) before the
  chdir/exec, becoming a session + group leader.
- **Windows**: `__kml_win_spawn` sets `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`
  when `flags & 4`; detached takes precedence over `windowsHide`'s
  `CREATE_NO_WINDOW` since `DETACHED_PROCESS` already implies no window and the
  two cannot combine. Redirected stdio (the pipes) is unaffected — the child
  simply has no console.

## Implementation notes

- Mode-bit map recap: bit 0 buffered, bit 1 shell/verbatim, bit 2 windowsHide,
  bit 3 detached. `__kml_win_spawn` `flags = mode >> 1`, so flags bit 1 =
  windowsHide, bit 2 = detached.
- `detached` alone does not change whether the parent waits for the child — that
  is `child.unref()` (not yet implemented). Documented as a caveat; `detached`
  here delivers the session/group semantics, which is the part that needs the
  platform layer.

## Side effects discovered

None. `stdio` arrays and PATHEXT-style `.cmd`/`.bat` resolution remain the open
child_process items (TDD-00180 §3).

## Verification

- New E2E test `TestE2EChildProcessSpawnDetached` (`detached: true` accepted,
  stdout captured). Full `TestE2EChildProcess*` green on Windows 11 and Docker
  Linux.
- Manual repros: **Windows 11 native** — `detached: true` runs with stdio intact.
  **Docker Linux `klain-ci:latest`** — a detached child reports `leader`
  (`/proc/$$/stat` session == pid, i.e. `setsid` took effect) where a plain child
  reports `notleader`.

  ./codegen/...` clean. `make status`/`reference-check`/`conformance` at delivery.
