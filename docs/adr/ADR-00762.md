# ADR-00762: `spawn(cmd, args, { env })` — a custom child environment

- **Relations**: Extends [ADR-00433](ADR-00433.md) (spawn's options object) and [ADR-00737](ADR-00737.md) (the `__kml_win_spawn` CreateProcessW path); addresses [TDD-00180](../tdd/TDD-00180.md) §3 (remaining spawn options)
- **Date**: 2026-09-07

## Context

`child_process.spawn`'s options object accepted `{ cwd, shell, stdio: 'pipe' }`;
`env` was a clean rejection. Node's `env` gives the child a specific environment
and, unlike a shell `export`, **fully replaces** the parent's — `env` does not
merge with `process.env` unless the caller spreads it in (`{ ...process.env, X }`).
The most common spawn option after `cwd`, and cleanly E2E-testable — the first of
[TDD-00180](../tdd/TDD-00180.md) §3's remaining-spawn-options rows.

## Investigation

`__kml_cp_spawn(file, argsdata, argslen, mode, cwd)` (runtime_childprocess.go)
forks and `execvp(file, argv)`s on POSIX (inheriting the process `environ`) and
calls `__kml_win_spawn(...)` on Windows, which builds a `CreateProcessW`
environment block only to inject the cluster-IPC inherit marker. Two ways to
apply a custom env on POSIX: `execvpe(file, argv, envp)` — but it is a **GNU
extension absent on macOS**; or point the global `environ` at the block and
`execvp`, which is portable and keeps `execvp`'s PATH search (it falls back to a
default path when the new environ has no `PATH`). The latter avoids a
platform-split exec call.

## Decision

- **Lowering** (`cpBuildEnvp`, emit_childprocess.go): an `env` object literal
  `{ KEY: "val", ... }` becomes a `malloc`'d NULL-terminated `char**` whose
  entries are `"KEY=" + value` strings (built with the ordinary string-concat
  runtime, so each is a NUL-terminated C string). Values must be strings — a
  non-string value is a clean rejection (Node stringifies; only strings are wired
  here). Never freed (`-mm=manual`); it must outlive the fork/CreateProcess.
- **ABI**: `__kml_cp_spawn` gains a trailing `ptr %env` param (NULL = inherit),
  threaded from `cpSpawnCall`. `cpSpawnOptions` now returns an `envRef` alongside
  `cwd`/`shell`. A **dynamic** (non-literal) options object still supports `cwd`
  only; its `env` is not readable at compile time — documented.
- **POSIX apply** (`cpSpawnForkIR`): in the forked child, before `execvp`, a
  non-NULL `%env` is stored into the external global `@environ`; execvp then
  inherits it (fully replacing the parent's). `@environ` is declared on POSIX
  only.
- **Windows apply** (`__kml_win_spawn`, win32proc.c): a new trailing `char**
  spawn_env` param. When non-NULL, each UTF-8 `"KEY=val"` entry is converted to
  wide (the conversion's wide count includes the terminating NUL, which is
  exactly the per-entry separator a double-NUL block needs) and concatenated into
  a `CREATE_UNICODE_ENVIRONMENT` block that replaces the child's; the cluster-IPC
  inherit marker is appended to whichever block is built. Command resolution is
  unaffected — `CreateProcessW(NULL, cmd)` searches the *current* process PATH,
  not `lpEnvironment`.

## Implementation notes

- The `__kml_win_spawn` decl grew from 8 to 9 params; the four other callers
  pass `ptr null`/`NULL`: `execSyncForkIR`, `clusterForkIR`, the worker-spawn
  site (all IR), **and `runtime_spawnsync.go`'s own C forward-declaration + call**
  — the last is separate from the IR decl and was the one easy to miss (a stale
  8-arg call passed a garbage 9th `spawn_env`, silently blanking `spawnSync`'s
  output on Windows; caught by the full `TestE2EChildProcess*` suite).
- POSIX PATH resolution with a replaced env: `execvp` falls back to a default
  search path when the new `environ` omits `PATH`, so `spawn("sh", …, { env })`
  still finds `sh` — matching Node closely enough for the common case.

## Side effects discovered

None. `detached` / `windowsHide` / `timeout` / `stdio` arrays remain clean
rejections — separate follow-on rows (TDD-00180 §3).
