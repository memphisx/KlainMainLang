# ADR-00159: `new Set(iterable)`

- **Relations**: Extends [ADR-00153](ADR-00153.md) (Test262 full-corpus conformance harness)

## Context

Next candidate off the conformance report's failure table, picked back up from where the original "easy wins" triage first flagged it: `new Set()`/`new Map()` unconditionally rejected any constructor argument (`parseNewSetBody`/`parseNewMapBody`, `parser/parser_literals.go`), a small, previously-identified, bounded gap (~161 files). Scoped to `Set` only this round — `new Map(entries)` needs each entry to be a `[K, V]` pair, and this compiler has no tuple types at all (`docs/status/README.md`'s own "no intersection/tuple/mapped types" line), so a sound implementation needs that prerequisite first; left as the existing clean rejection rather than a narrower, awkward partial (e.g. same-type-only entries) that wouldn't actually match real `Map`'s constructor shape.

## Decision

`new Set(iterable)` accepts one optional argument — narrowed from the real spec's `Iterable<T>` to "an array expression," the only iterable concept a general expression has in this compiler. `NewSetExpression` gained an `Init Expression` field (nil for the pre-existing no-argument form). Element type resolution order: explicit `<T>` type argument, else inferred from the initializer array's own element type (matching real TS: `new Set([1,2,3])` infers `Set<number>`), else the pre-existing string-element default for the bare no-argument form.

Codegen creates the empty set exactly as before (`emitMapOrSetCreate`), then — only when an initializer is present — loops over it with a hand-written index/GEP/insert loop (no generic "iterate an array" helper exists anywhere in this codebase to reuse; every other array-consuming site hand-rolls its own, matching this project's own "don't add abstraction beyond what's needed" convention), inserting each element via the same `__kml_map_str_set`/`__kml_map_num_set` calls `.add()` already uses.

## Side effects discovered

Building the very first test that used an already-declared *variable* as the initializer (`new Set(arr)`, as opposed to a literal `new Set([1,2,3])`) surfaced a real bug, not in the new code but in the resolver's existing per-file name-mangling machinery (TDD-00041): `arr` compiled to `codegen error: 'arr' is not an array` even though `arr` was declared correctly one statement earlier. Root cause, found via targeted debug tracing rather than guesswork: `resolver/rename.go`'s `rewriteExpr` had a `case *ast.NewMapExpression`/`case *ast.NewSetExpression` already (for their `KeyType`/`ValType`/`ElemType` type annotations), but neither rewrote an `Init` expression — because neither had one to rewrite, until this change added `NewSetExpression.Init`. The reference to `arr` inside `new Set(arr)` was therefore never rewritten to `arr`'s own mangled top-level name (`arr__kml_mod0`), so codegen looked it up under the wrong (unmangled) key and found nothing. The same audit-every-existing-switch discipline ADR-00156/ADR-00158 already established for a new AST field found a second, same-shaped gap in the same pass: `codegen/llvm/emit_func.go`'s `scanExprFV` (closure free-variable capture analysis) had no case for `NewSetExpression` at all — a closure referencing an outer variable only through `new Set(outerVar)` would have silently failed to capture it. Both fixed directly (one line each) rather than deferred, since they block the feature's own basic correctness, not a separate concern.

## Verification

- `go build`, `go vet ./...`, full `go test ./...`, `make examples` (all 109) — all pass.
- 7 new E2E tests (`tests/collections_test.go`): array-literal source (number and string), an already-declared array variable (the exact case that found the mangling bug, with a comment explaining why), an explicit `<T>` type argument combined with a variable source, an empty-array source, the pre-existing no-argument form (regression check), and a closure capturing a variable referenced only inside `new Set(...)` (the exact case that found the free-variable-scan bug).
- `examples/set/set.ts` extended with a dedicated section, including a non-identifier (`.map()` call result) source expression, not just a bare variable or literal; built and ran directly, output matches the file's own inline comments exactly.
- Full Test262 corpus re-run: 4,462 → 4,462, no aggregate movement — expected, since an argument to `new Set(...)` was a hard parse error before this change, so no previously-*passing* file could regress from it.
