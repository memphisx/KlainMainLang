# ADR-00517: Object-reference array representation (shared headers)

- **Relations**: `Implements TDD-00127`
- **Date**: 2026-08-30

## Context

Arrays were a flat value type: a bare `malloc`'d element buffer plus a
*separate* `i64` length, with no shared header. A named array variable was two
allocas (`Symbol{Ptr, LenPtr}`); passing an array to a function appended those
two values as two independent scalar arguments, and the callee re-allocated its
own private slots for them. The consequence was a JavaScript-fidelity bug:
`arr[i] = v` inside a callee propagated (the element buffer is shared by
pointer), but `arr.push(v)` / `arr.splice(...)` / `arr.unshift(v)` did **not** —
the callee held a private copy of both the length and (after a reallocating
`push`) the data pointer. In real JS an array is a reference value: `function
f(a){ a.push(1) }` grows the caller's array.

## Investigation

The mutators (`emit_arrays_mutate.go`) already write a new data pointer/length
back through two *addresses* (`ptrPtr`, `lenPtr`) obtained from the receiver.
For an identifier receiver those addresses were `sym.Ptr`/`sym.LenPtr` — the two
per-frame allocas. So propagation across a call boundary reduces to: make those
two addresses point into **one shared cell** that both caller and callee hold.

The blast radius was measured: `.LenPtr` (array-only) appeared at 18 read sites,
funnelled largely through three resolve helpers (`resolveArrayForHOF`,
`resolveArrayDataPtr`, `resolveArrayMutLoc`) plus `emitIdentifier`; array-Symbol
creation happened at ~15 sites; and the (ptr, i64) call ABI was packed/bound at
~25 sites across `emit_call.go`, `emit_classes.go`, `emit_func.go`,
`emit_func_adapt.go`, and `emit_task_emit.go`.

Two forks the TDD left open were decided against faithfulness, per this project's
faithfulness-first rule:

- **Fixed-header vs. object-reference.** A fixed `{ptr,i64}` header addressed
  directly by `Symbol.Ptr`/`LenPtr` would fix `push` propagation with almost no
  read-site churn — but it regresses **parameter reassignment**: `a =
  a.filter(...)` inside a callee would write through the shared header and
  clobber the caller's array. Distinguishing an *in-place mutation* (must
  propagate) from a *whole-variable rebind* (must stay local) requires one level
  of indirection — a stable slot holding the header pointer. Object-reference
  chosen.
- **`cap` field.** Deferred. A capacity field forces widening *all three* array
  shapes (named variable, inline object/class field, nested-array element box)
  from `{ptr,i64}` to `{ptr,i64,i64}`, rippling into object struct layouts and
  every field offset — for a pure performance win with zero fidelity benefit.
  Keeping the header at `{ptr,i64}` makes the named-array representation
  *identical* to the already-working boxed shape the other two shapes use.
  Amortized-growth is left as documented future perf work.

## Decision

A named array is a **stable slot** (`Symbol.Ptr`) holding a pointer to a shared
heap `{data, len}` header (`arrayHeaderTy`). `LenPtr` is removed from `Symbol`.

- `arrayDataLenSlots(sym)` loads the current header pointer from the slot and
  returns the data-field address (the header pointer itself; field 0 is at
  offset 0) and the len-field address. Every read and every in-place mutator
  goes through it, so it always observes the header the slot points at *now*.
- In-place mutators (`push`/`pop`/`shift`/`unshift`/`splice`) write the new data
  pointer/length through the header → propagates to every alias, including a
  callee the array was passed to.
- Whole-variable reassignment (`a = expr`) rebinds the slot to a *fresh* header
  (`boxArrayValue`), a local rebind that does not clobber the caller — so
  `a = a.filter(...)` behaves, and non-aliasing of `x = otherArray` is preserved.
- Call ABI keeps the two-word `(ptr, i64)` shape, but `ptr` is now the header
  pointer; the `i64` length is redundant (the callee reads length from the
  header) and kept only for ABI stability. A variable argument passes its own
  header pointer (`packArrayArg` → `arrayDataLenSlots`); a transient array
  expression passes a fresh header (`arrayArgFromAggregate`); an empty/omitted
  array argument passes a fresh `{null,0}` header (`emptyArrayArgHeader`) so the
  callee never dereferences a null header.

## Implementation notes

- Helpers added in `emit_arrays_core.go`: `newArrayHeader`,
  `newArrayHeaderSlot`, `newArrayHeaderSlotFromAggregate`, `arrayDataLenSlots`,
  `bindArrayParam`, `packArrayArg`, `arrayArgFromAggregate`,
  `emptyArrayArgHeader`. `boxArrayValue` already mallocs exactly a `{ptr,i64}`
  header, so it doubles as the aggregate→header boxer.
- Creation sites migrated: var-decl, array/rest/nested destructuring, object
  and tuple destructuring, `for...of`/`for await...of` array loop variables
  (for-of, generators, streams), the `arguments` object, module globals (a
  single `@..._hdr` slot global instead of two data/len globals), and all
  callee param bindings.
- The destructuring branches inside `emitArrayVarDecl` were left untouched: the
  preamble now points a header's field addresses at the same `ptrName`/`lenName`
  locals the branches already store into, so only the allocation changed.
- **Ordering constraint** in the nested-array destructuring element: the header
  is built inside each `ok`/`oob` live block (after `emitLabel`), not in the
  post-terminator dead zone where the old two allocas lived (allocas bypass to
  the entry block via `emitAlloca`; a `malloc` via `emitInstr` would be dropped
  there).

## Side effects discovered

- **Async/suspending array parameter segfault.** `bindTaskParamsFromBundle`
  (`emit_task_emit.go`) still bound array params in the old two-alloca shape;
  under the header model `arrayDataLenSlots` then treated the stored data
  pointer as a header and dereferenced garbage — a segfault for any suspending
  function that awaited before touching an array/rest parameter (caught by
  `TestE2ESuspendingRestParam`). Fixed to wrap the bundle's (data, len) into a
  fresh header slot. A suspending function's array parameter remains an
  independent copy (as before the change) — the bundle carries the aggregate,
  not the header, so mutations do not propagate across the async boundary.
- **Object-field / element array arguments don't propagate.** Passing
  `obj.field` (a member/index array) to a mutating function takes the transient
  (fresh-header) path in `packArrayArg`, so an in-place mutation inside the
  callee is not seen by the field. This is a known limitation, not new
  behaviour (the pre-header code did not propagate it either); tracked as the
  `array-arg-field` caveat on the relevant status rows.
- **HOF callback array elements don't propagate.** A callback receiving a
  nested-array element (`m.forEach(row => row.push(0))`) gets a transient
  header; the pre-header code did not propagate this either.
- **Runtime → user-closure chunk delivery.** Every runtime path that hands a
  `Uint8Array` chunk to a user listener passed a raw `(ptr, len)` pair, which the
  listener's array parameter now misreads as a header (garbage length, then a
  crash on `.decode`). Fixed at each site to box `(ptr, len)` into a header
  first: the Readable/Writable/`_write`/`_transform` sink thunks
  (`emit_streams.go`, `emit_node_stream.go`, `emit_node_stream_class.go`,
  `emit_streams_writable.go`), and the worker message adapter
  (`emit_worker.go`). `net`/`dgram`/`child_process` deliver from fixed C
  templates that don't know the listener's chunk type (their listener may be
  `string` *or* `Uint8Array`), so a per-listener adapter closure
  (`ensureChunkHeaderAdapter` / `ensureDgramMsgHeaderAdapter`) is inserted only
  when the parameter is array-typed. Found via `parallel_sum` (workers) hanging
  and net string-chunk tests corrupting — see the verification below.
