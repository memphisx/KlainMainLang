# ADR-00122: EventSource (Server-Sent Events) Stage 0 — connection plumbing

- **Relations**: Implements [TDD-00038](../tdd/TDD-00038.md)
- **Date**: 2026-08-07

## Context

[TDD-00038](../tdd/TDD-00038.md) scoped `EventSource` (the last unstarted row in `docs/status/NETWORKING.md`'s API table) as a staged feature: Stage 0 (connection plumbing — `readyState`, `close()`, event-loop keep-alive integration, no SSE parsing/dispatch yet), Stage 1 (SSE record parsing + `onmessage`), Stage 2 (named events + `onopen`/`onerror`), with auto-reconnect deliberately left undesigned as a later follow-on. This ADR implements Stage 0.

## Investigation

Confirmed directly (not assumed) two facts the TDD's own investigation had already surfaced: `__kml_curl_write_cb` (`runtime_fetch.go:47-81`) already fires per chunk as data streams in, and `new EventSource(url)` is fire-and-forget (never `await`ed), so no fiber-parking primitive is needed at all — only a fourth thing for `__kml_event_loop_run` to scan every iteration, alongside its existing timer/fd/fetch-resume scans.

Read `runtime_http.go`'s `ensureHTTPRuntime`/`__kml_event_loop_run` in full before writing any new IR, specifically to answer: is `__kml_event_loop_run` safe to call without `http.listen` ever running? Confirmed yes — `scandone`'s own exit condition (`havetimer OR haslistener OR hasactiveconns`) and `@__kml_listen_fd`'s `-1` sentinel default already make "no listener" a real, tolerated case. But also confirmed something the TDD hadn't fully spelled out: before this ADR, `__kml_event_loop_run` was reachable *exclusively* from `emit_http.go`'s `http.listen(...)` codegen — a plain top-level `setTimeout`/`setInterval` with no `http.listen` only ever reached the narrower `__kml_timer_drain()` (`emitter.go`'s Pass 3 tail called that, not the fuller loop). So "is it safe to call standalone" and "is anything already calling it standalone" were two separate questions — the first was already true, the second wasn't, and routing a plain top-level EventSource-using script through the fuller loop was the one genuinely new integration point Stage 0 needed.

Also confirmed directly (compiling a throwaway program and reading the resulting `.ll`) that `ensureHTTPRuntime`'s own doc comment's warning is real and not hypothetical: it already unconditionally pulls in `ensureFetchAsync`/`ensurePromiseCombinators` specifically because `__kml_event_loop_run`'s hand-written IR body references their symbols unconditionally, regardless of whether the program actually uses `fetch`/`Promise.all`. The same requirement applies to this ADR's own new `__kml_eventsource_scan` — missing it on the first attempt would have broken every existing `http.listen`-only program (an undefined-symbol link failure) the moment `__kml_event_loop_run`'s body was edited to call it unconditionally; caught before it ever reached a build by reasoning through the existing precedent rather than by trial and error.

Considered building EventSource's own transfer-tracking struct from scratch vs. reusing `ensureFetchAsync`'s existing 40-byte pending-fetch struct (`{ ptr easy, ptr buf, i64 done, i64 status, i64 result }`) as-is. Chose full reuse: an EventSource's easy handle is added to the *same* global `@__kml_curl_multi` handle via `CURLOPT_PRIVATE` pointing at one of these structs, exactly like a plain fetch — so the existing, unmodified `__kml_curl_drain_messages` already detects "this SSE connection ended" (`CURLMSG_DONE`) for free. Only a genuinely new, smaller "entry" struct (`{ ptr pending, ptr instance, i64 consumedOffset, i64 state }`, 32 bytes) was needed on top, to hold the two things a plain fetch's pending struct has no use for: the reverse link back to the KML-level object (`instance`), and Stage-0-forward `consumedOffset`/`state` bookkeeping. This is a real, deliberate divergence from the TDD's own originally-sketched entry shape (`{ ptr easy, ptr buf, i64 consumedOffset, i64 state, ptr instance }`, which duplicated `easy`/`buf` directly rather than indirecting through the existing pending struct) — found during implementation to be strictly more reuse, not just a cosmetic rename.

## Decision

Implemented exactly as scoped in the TDD's Design section, with the one struct-shape refinement above. Concretely:

- **A fourth event-loop scan, not a fiber-parking mechanism.** `__kml_eventsource_scan()` (`runtime_eventsource.go`) is called once per `__kml_event_loop_run` iteration, immediately after the existing `curl_multi_perform`/`__kml_curl_drain_messages` calls (so every entry's `pending->done`/buffer state is already fresh). It walks a flat, grow-only array of entry pointers (`@__kml_es_data`/`_len`/`_cap`, realloc-doubling, same shape the timer queue already uses) and, for each not-yet-`CLOSED` entry: if the transfer ended (`pending->done`), marks it `CLOSED` and writes `readyState=2` back into the KML object via `instance`; otherwise, if still `CONNECTING` and any bytes have arrived, transitions to `OPEN` (`readyState=1`) — libcurl's write callback firing at all being a sufficient proxy for "connected," per the TDD's own reasoning. Stage 0 has no parser: `consumedOffset` is simply set to the buffer's current length every pass, discarding the bytes.
- **Event-loop keep-alive**: `scandone`'s `anywork` condition gained a fourth OR-term, `@__kml_es_active > 0` (a live counter, incremented on open/decremented on close-or-completion — mirroring `@__kml_conn_active`'s existing pattern exactly, including "grow-only array, dead entries flagged in place, never actually removed").
- **`emitter.go`'s Pass 3 tail**: when the program constructed at least one EventSource (`e.usedEventSource`), emit a call to the full `__kml_event_loop_run()` instead of the narrower `__kml_timer_drain()` — `__kml_event_loop_run` already generalizes plain timer draining (confirmed by reading its body, not just its doc comment), so this is a strict upgrade, not a special case needing both calls.
- **Object shape**: `EventSourceType()` (`types.go`) follows `RegExpType()`'s exact precedent — one hidden field (`EventSourceHandleField`, a `ptr` to the runtime's own entry struct) plus plain visible fields (`url`, `readyState`), `VisibleFields()` skipping index 0 the same way.
- **`close()` is synchronous**: `emitEventSourceClose` (`emit_eventsource.go`) calls `__kml_eventsource_close` (idempotent — a no-op if already `CLOSED`, `curl_multi_remove_handle`+`curl_easy_cleanup`, decrements `@__kml_es_active`) *and* separately stores `readyState=2` directly into the KML object in the same instruction sequence, so a read immediately after `close()` never has to wait for the next scan iteration — matching real `EventSource`'s own synchronous `close()`.
- **No `CURLOPT_TIMEOUT`** on the EventSource easy handle (unlike `fetch`'s 30-second cap) — deliberate, not an oversight: an SSE stream is meant to stay open indefinitely, so capping it would be actively wrong.

## Implementation notes

- **New files**: `ast` gained `NewEventSourceExpression` (`ast/nodes.go`, mirroring `NewURLExpression`'s single-string-argument shape exactly); `parser/parser_literals.go` gained `parseNewEventSourceBody` wired into `parseNew()`'s switch; `codegen/llvm/emit_eventsource.go` (construction + `close()`, Go-level codegen) and `codegen/llvm/runtime_eventsource.go` (the three new C-runtime IR functions) are new, following this codebase's established `emit_*.go`/`runtime_*.go` split.
- **Dispatch wiring**: `NewEventSourceExpression` needed the same three-site treatment every other built-in constructor gets — `emit_exprs.go`'s main `emitExpr` switch, `emit_exprs_types.go`'s `inferExprType`, and `emit_exprs_vardecl.go`'s unannotated-`const`/`let` pre-inference switch (all three mirroring the existing `NewRegExpExpression`/`NewURLExpression` cases immediately above each new one). `.close()` dispatch is one new guarded branch in `emit_call.go`, mirroring `IsRegExp`'s `.test()`/`.exec()` branches (`mem.Property == "close" && e.inferExprType(mem.Object).IsEventSource`).
- **A real, non-cosmetic bug found while writing the raw IR**: naming `__kml_eventsource_close`'s parameter `%entry` collided with the function's own implicit `entry:` block label — LLVM IR puts SSA value names and basic-block labels in the same namespace within a function, so `define void @__kml_eventsource_close(ptr %entry) { entry: ...` fails to verify (clang: "unable to create block named 'entry'"). Fixed by renaming the parameter to `%es_entry`; caught immediately via a manual `--emit-llvm` + direct `clang` compile before it ever reached the Go test suite (see Verification) — worth calling out since it's the kind of error `go build` alone (which never lexes the embedded IR strings) cannot catch.
- **A real, non-hypothetical hang found while writing the first test**: `emitter.go`'s new keep-alive branch means a program that constructs an EventSource and *never* closes it (and has nothing else keeping the process alive either) now runs `__kml_event_loop_run()` forever, by design — this is correct behavior (the same "an open resource keeps the process alive" contract a real Node `setInterval` already has), but the very first version of `TestE2EEventSourceReadyStateStartsConnecting` didn't call `close()` at all and hung indefinitely as a result. Not a codegen bug — the test was wrong; fixed by adding an explicit `close()` after the assertion. Documented here because it's exactly the kind of thing worth flagging for whoever picks up Stage 1/2: any Stage 0-era example/test that doesn't explicitly close its EventSource will hang the compiled binary forever, not just leak a handle.

## Side effects discovered

None beyond the two implementation-time findings already folded into Decision/Implementation notes above (the pending-struct reuse refinement, the `%entry` naming collision) — no other bugs, and no scope narrower than what TDD-00038 already committed Stage 0 to.

## Verification

- `go build -o klainmain .` and `go vet ./...` clean.
- Manually compiled a throwaway program with `--emit-llvm` and linked the result directly with `clang -lcurl` (bypassing `go test`) before writing any Go-level tests, specifically to catch IR-level bugs (like the `%entry`/block-label collision above) that `go build` alone cannot see — confirmed `readyState` reads `0` immediately after construction and `2` immediately after `close()`.
- `go test ./...` passes in full, including 5 new tests in `tests/eventsource_test.go` against a local `httptest.Server` (real TCP/HTTP, not mocked): `readyState` starts `CONNECTING`, transitions to `OPEN` once bytes actually arrive (observed via a `setTimeout` callback, forcing a real event-loop iteration), `close()` is synchronous, `close()` is idempotent (called twice, verified the process doesn't hang or exit early — i.e. `@__kml_es_active` wasn't double-decremented), and a refused connection (nothing listening on the target port) correctly lands in `CLOSED` rather than stuck `CONNECTING` or wrongly read as `OPEN`.
- Ran the full pre-existing suite (`go test ./...`, all packages) to confirm the `__kml_event_loop_run`/`ensureHTTPRuntime` edits — a genuinely shared, heavily-relied-upon function — introduced no regression in `http.listen`/`fetch`/timer/signal-handling behavior: all pass.
- Added `examples/eventsource/eventsource.ts` and a matching `GET /stream` endpoint on the local `tools/httpbin-lite` fixture server (same deterministic/offline-capable pattern `examples/fetch/*.ts` already uses); compiled and ran it directly against the fixture, output matched every inline expected-output comment exactly (`0`, `1`, `2`).
- Verified only on the x86-64 Linux development box (see `CLAUDE.md`'s platform-flagging rule) — this reuses the exact same libcurl multi-interface/event-loop machinery `fetch`/`http.listen` already have platform-neutral behavior for, so it isn't expected to be platform-sensitive, but that expectation hasn't been directly confirmed on the Apple Silicon Mac.
