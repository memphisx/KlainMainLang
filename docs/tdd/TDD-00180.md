# TDD-00180: Windows faithfulness audit — where the platform layer is still CRT/POSIX-shaped

- **Status**: Not Started
- **Date**: 2026-09-07

## Context

[TDD-00177](TDD-00177.md) split the Windows port into two decisions: the *toolchain* (mingw-w64 against the MSYS2 UCRT sysroot) and the *semantics* (a Win32-native platform layer written against Node's documented Windows behaviour, not against "what mingw provides that looks like this POSIX call"). The port shipped under that plan (ADR-00718/00719 and follow-ups), with the standing worry that a POSIX-emulation layer is the easy path but not the faithful one.

This document is the audit of what actually got built, subsystem by subsystem, against libuv's `src/win/*` and Node's documented Windows behaviour. It answers three questions: did the toolchain decision hold, where does the implemented layer still produce Linux-Node (or plain CRT) behaviour on Windows, and whether closing those gaps is incremental work on the current layer or needs a reactor change.

The audit read `codegen/llvm/win32src/{win32shim,win32io,win32fs,win32proc}.c`, `kml_posix_compat.h`, and every Windows branch in the Go emitters. Line numbers are as of 2026-09-07. One finding was fixed in passing (`Math.random()` never exceeded 1.5e-5, [ADR-00735](../adr/ADR-00735.md)); everything else is recorded here, unfixed.

## Design

### Verdict on the toolchain decision

It held. The only mingw-specific costs the port paid were LLP64 (`long`), the 16-byte `_setjmp` alignment, and a header-set drift on the CI runner (ADR-00734). No `_spawn*`, `_exec*`, `system()`, `popen()`, `_stat`, `_chmod`, `_mkdir`, `_access`, `_unlink`, or narrow `*A` Win32 API is used anywhere in `win32src/`. Process creation is `CreateProcessW`, fs metadata is `GetFileInformationByHandle`/`FileBasicInfo`, paths cross a UTF-16 boundary, `isatty` is `GetConsoleMode`, `getrandom` is `BCryptGenRandom`, clocks are QPC. The MSVC option (TDD-00177 Option C) buys nothing here: every divergence below is a Win32 call not yet made, not one mingw cannot make.

### Where CRT/POSIX shape still leaks

The CRT dependency that remains is the **fd table**: non-socket fds are CRT fds (`_open_osfhandle`/`_read`/`_write`/`_close`, `win32io.c:192-503`), sockets live in a side table above 512. That one choice is the root of most of the behavioural gaps in the I/O column. Everything else is a per-subsystem omission.

Ranked by user impact. **Node** is the reference behaviour, **Here** is what a compiled program observes on Windows today.

#### 1. Event loop and stdio (`win32io.c`)

| Area | Node (libuv) | Here |
|---|---|---|
| Reading `process.stdin` or a child's stdout pipe | Overlapped reads, never blocks the loop | fds 0/1/2 are never registered as pipes, so `read()` falls to CRT `_read` and **blocks the whole loop** until a line or EOF (`win32io.c:482-487`, `runtime_stdin.go:47-78`) |
| Console input | Translated on a tty thread | `plain_readable` reports readable on any input record (key-up, focus, mouse), then the read blocks until Enter (`win32io.c:579-588`) |
| Idle behaviour with a pipe or console watched | Blocks in `GetQueuedCompletionStatusEx`, zero wakeups | 10 ms poll slice forever (`win32io.c:654`), 50 ms when a console-ctrl handler is installed (`:655`); no wakeup channel at all (`:682-684`) |
| Full pipe on write | Queued, completed asynchronously | Plain fds are declared always-writable (`:643`), then `_write` blocks |
| Child stdio pipes | Named, `FILE_FLAG_OVERLAPPED`, IOCP | `CreatePipe` synchronous 4 KB anonymous pipe (`:408-419`) |
| `fs.fstatSync(0)` on a pipe/console | `isFIFO()` / `isCharacterDevice()` | `-1`/`EIO`: `GetFileInformationByHandle` is called before the `GetFileType` dispatch (`win32fs.c:204-210`) |
| Socket count | Handle-bound | 384 sockets (fds 512..895) then `EMFILE` (`win32io.c:181-191`) |
| `dup2` of a socket | Refcounted description | Raw `SOCKET` copied, closing either fd closes both (`:421-433`) |
| Timer deadlines | QPC | `GetTickCount64`, 15.6 ms tick (`:619-621`) |
| Socket watched only in `exceptfds` | Reports | `p_select` with three NULL sets → `EINVAL` (`:633,656-670`) |

#### 2. Console and encoding

| Area | Node | Here |
|---|---|---|
| Non-ASCII on a console | `WriteConsoleW`, correct on any code page | UTF-8 bytes through `_write`; mojibake unless the console is 65001 (`emit_call_console.go:11`, `win32shim.c:94-113`; no `WriteConsoleW`/`SetConsoleOutputCP` in the tree) |
| Non-ASCII typed on a console | `ReadConsoleW` → UTF-8 | CRT `_read` in the input code page (`win32io.c:452,491`) |
| `process.argv` | `GetCommandLineW` + `CommandLineToArgvW`, UTF-8 | CRT `argv`, ACP-encoded; non-ASCII arguments become `?` (`emitter.go:2036-2045`) |
| ANSI escapes on a tty | VT processing enabled at startup | Enabled only inside `setRawMode(true)` (`emit_tty.go:191-192`); `console.log('\x1b[31m…')` prints the escape literally |
| `SIGWINCH` / `'resize'` | libuv has a console-resize watcher thread | "no console equivalent" (`win32proc.c:12`); never fires |
| `process.stdout.columns` off-tty | `undefined` | 80/24 (`emit_tty.go:198-207`) |

#### 3. `child_process` and `cluster` (`win32proc.c`, `runtime_spawn_win.go`)

| Area | Node | Here |
|---|---|---|
| `exec` / `shell: true` | `cmd.exe /d /s /c "<cmd>"`, verbatim, `COMSPEC` honoured | Command routed through `quote_arg`, so embedded quotes are escaped: `exec('echo "hi"')` prints `\hi\` (`runtime_spawn_win.go:290-300`); `cmd.exe` hardcoded |
| `spawn(cmd, {shell:true})` | Runs through the shell | Option evaluated and discarded (`emit_childprocess.go:257-259`) |
| `.bat`/`.cmd` without a shell | `EINVAL` (CVE-2024-27980) | `CreateProcessW` fails and a fake child reports exit 127 (`win32proc.c:166-179`); no PATHEXT search at all (`:159`, `lpApplicationName = NULL`) |
| Spawn failure | `'error'` event, no `'exit'` | `'exit'` with 127; the `'error'` slot exists but nothing fires it (`emit_childprocess.go:573-578`) |
| Killed child | `('exit', null, 'SIGTERM')`, exit code from `TerminateProcess(…,1)` | `128+sig` encoded as a POSIX status (`win32proc.c:235`, `runtime_childprocess.go:183-194`) |
| `process.kill(pid, sig)` | Terminates only for `SIGTERM`/`SIGKILL`/`SIGINT`, `EINVAL` otherwise, `ESRCH` if exited | Any non-zero signal terminates (`:249-255`); after reap, falls back to `OpenProcess(pid)` and can hit a **reused pid** (`:251`) |
| Handle inheritance | `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` | `bInheritHandles = TRUE`, no list (`:159`); safe today only because pipes and sockets are created non-inheritable |
| Std handles for the child | Invalid parent handles replaced by NUL | Passed through raw (`:133-137`) |
| Environment block | Sorted, case-folded, deduped, `SYSTEMROOT` guaranteed | Parent block + one appended marker, unsorted (`:139-155`); the marker `KML_WIN_INHERIT_FD=<fd>:<HANDLE>` leaks a raw handle value |
| Cluster re-spawn | `process.execPath` | Resolves `argv[0]` (`:112-113`, `runtime_spawn_win.go:106-108,227-229` compute the exe path and discard it) |
| IPC channel | Named pipe `\\.\pipe\uv\…` | Loopback TCP `listen(1)`/`accept()` **without verifying the peer** (`:261-276`); any local process can win the race |
| Listening socket to workers | `WSADuplicateSocketW` | `DuplicateHandle` on the `SOCKET` (`:97-102,185,191-203`), which Winsock documents as unsupported for layered providers |
| Scheduling | `SCHED_RR` | Shared accept (`SCHED_NONE`); TDD-00177 open question 7 |
| Exit code width | Full 32-bit (`3221225477` for an access violation) | `& 0xff` (`:235`) |
| `env`, `detached`, `windowsHide`, `windowsVerbatimArguments`, `argv0`, `timeout`/`killSignal`/`maxBuffer`, `stdio` other than `'pipe'` | Supported | Compile errors or absent (`emit_childprocess.go:68-91,168-170,261-268,396-398`) |
| `execSync` non-zero status | Throws with `status`/`stdout`/`stderr` | Returns (`emit_childprocess.go:164-166`) |

### What this means for the strategy

Three conclusions.

1. **No toolchain change is warranted.** Nothing above is a mingw limitation. The MSVC route (TDD-00177 Option C, open question 6) would inherit every one of these gaps unchanged.

2. **The fd table is the one structural decision worth revisiting; everything else is a list.** The reactor findings in §1 (blocking stdin, blocking console, 10 ms spin, always-writable pipes, no wakeup channel, the 384-socket cap, `dup2` aliasing, `fstat(0)`) all follow from routing non-socket I/O through CRT fds. Two ways out:

   - **Option A — keep readiness, own the fd table.** Replace CRT fds with a private table of `HANDLE`s carrying a kind tag (file, anonymous pipe, named pipe, console, socket), do reads with `ReadFile` on overlapped named pipes plus a console-input thread, and add one wakeup event to the wait set. The reactor stays `select`-shaped, so `runtime_net.go`/`runtime_http.go` are untouched. Cost is roughly the size of `win32io.c` again. Solves everything in §1 except the 15.6 ms timer tick (needs `timeBeginPeriod` or a waitable timer) and leaves the "one thread per non-socket handle" shape libuv also had before IOCP.
   - **Option B — IOCP reactor.** libuv's model: overlapped `WSARecv`/`AcceptEx` for sockets too, one `GetQueuedCompletionStatusEx` wait. Faithful and scalable, and the natural home for named pipes and `fs.watch`, but the socket helpers change from readiness to completion, which reaches into the IR-level `runtime_net.go`/`runtime_http.go`/TLS paths. TDD-00177 already parks this as "the upgrade path".

   Recommendation: Option A first, designed so the handle table and wakeup object are what an IOCP reactor would need anyway. It is the smaller change and removes the CRT from the I/O path entirely, which is the actual faithfulness debt. Decide in its own TDD when the Windows work resumes; do not start it from the Windows box.

3. **The rest is incremental and can be done from any host that cross-checks on the CI lane.** Grouped by the test file that would prove each: errno tables (§4, §5) and `err.errno`/`syscall`/`path` shape; `child_process` shell/quoting/`.bat`/`'error'` event/exit-code shape (§3, first eight rows); `FILE_SHARE_DELETE` + `\\?\` prefixing in `to_wide` (§4, first two rows); `WriteConsoleW`/`CommandLineToArgvW`/VT-at-startup (§2); `IPV6_V6ONLY` and `SO_*` translation (§5). Each is a one-ADR change against the existing layer. Security-flavoured rows (`socketpair` peer verification, `SO_REUSEADDR` under `SO_REUSEPORT`, pid reuse in `kill`, raw handle in the environment, `bInheritHandles=TRUE`) go first within that pile.

### Test strategy

The ConPTY harness (ADR-00727) is the only way to observe §2 rows on a real console; the pipe-based E2E suite cannot see them (verified 2026-09-07: `od -c` of piped output shows correct UTF-8 and intact escapes, which says nothing about a console). Every §1 row needs a test that would hang or spin on the current code: a `process.stdin` `'data'` handler alongside a running `setInterval`, a child writing more than 4 KB to its stdout while the parent writes more than 4 KB to its stdin, an idle loop with one pipe watched measured for CPU. §3–§6 rows are ordinary E2E tests with `runtime.GOOS == "windows"` expectations under the ADR-00719 convention.

## Open questions

1. **Option A or B for the fd table**, and whether Option A's console-input thread and pipe-reader threads should post to a completion port from day one (so B is a refactor, not a rewrite) or to a plain event.
2. **`err.errno` numbering on Windows.** Node exposes libuv's negative Windows-specific values (`-4058`); the shim deliberately keeps Linux-ABI numbers internally so the emitters stay host-agnostic. Faithful means translating at the error-object boundary only; needs a table and a decision on whether Linux and macOS programs should also see libuv-negative numbers (they do in Node: `-2` on Linux).
3. **Whether `process.env` enumeration and `os.*` breadth are done cross-platform first**, since Windows would then inherit the Win32 branches for free rather than adding Windows-only surface.
4. **Static OpenSSL/curl on Windows.** The `.exe` currently carries `ucrt64/bin` DLL dependencies Node does not have; TDD-00177 open question 5 (`--static`) covers it and is unchanged by this audit.
