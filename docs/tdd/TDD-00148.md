# TDD-00148: namespaces V2 — `module` synonym, non-exported members, type members, sibling references

- **Status**: Implemented (Stages 1–4, plus the V3 nesting/dotted-name/relative-reference extension — [ADR-00453](../adr/ADR-00453.md))
- **Date**: 2026-08-29
- **Notes**: Stages 1–4 + V3 (nesting, dotted names, relative references — [ADR-00453](../adr/ADR-00453.md)) shipped; `X.Enum.Member`/`X.Class.static` chains resolve too ([ADR-00480](../adr/ADR-00480.md))

## Context

Namespaces V1 (TDD-00095) covers exactly `namespace X { export function/const }`.
The TS acceptance oracle shows internal modules are the single largest
remaining agreement cluster: the `module` blocker alone marks 124
false-rejects, `'export' can only precede …` (mostly `export module`) 144,
and a large share of `undefined variable` (291) is namespace-scoped sibling
references. Node's older-corpus files and the TS compiler test suite both
use the `module X { }` spelling heavily.

## Design

Four stages, all building on V1's parser-desugar model (members lower to
flat top-level declarations; no new codegen object model):

1. **`module X { }` synonym.** The pre-ES2015 spelling of `namespace`.
   Contextual: only when followed by IDENT `{`, so `module.exports`-style
   expressions and variables named `module` keep parsing as before.
   `export namespace X {}` / `export module X {}` at top level parse as the
   plain declaration — exportness is meaningless in V1/V2's single-file
   namespace scope, so it is tolerated and dropped rather than rejected.

2. **Non-exported value members.** `function f() {}` / `const c = …`
   without `export` inside a namespace body: desugared and mangled exactly
   like exported members, but recorded with `exported=false` —
   `ast.Program.Namespaces` changes meaning from member-set to
   member→exported map. An outside `X.f` use of a non-exported member is a
   clean "not exported" rejection (previously the V1 parser rejected the
   whole namespace).

3. **Type members.** `class` / `interface` / `type` / `enum` declarations
   (exported or not) inside a namespace body desugar to *bare-name*
   top-level declarations — deliberately unmangled, matching the existing
   qualified-`new`/`extends` precedent where `new X.C(…)` already resolves
   through the final segment's bare name (ADR-00408). Consequences,
   disclosed: two namespaces declaring the same class name collide with the
   usual duplicate-declaration error, and `X.Enum.Member` from outside
   stays unsupported (the inside-body bare `Enum.Member` form works).

4. **Sibling references.** A member function body referencing a sibling
   value member by bare name (`function g() { return f(); }`). Codegen
   tracks the namespace of the function being emitted (derived from the
   `__kmlns_` infix in its mangled name) and falls back at the three
   resolution points — variable `lookup`, user-function call resolution,
   and inference — to the `ns__kmlns_name` mangled form when the bare name
   is undefined. Local shadowing wins naturally (scope lookup runs first).
   Top-level namespace `const` initializers referencing siblings stay
   unsupported (they emit in `main`, outside any namespace context) — a
   clean error, noted in status.

### Rejected alternatives

- **Bare-name desugar for value members too**: would make sibling
  references free, but collides a namespace's `f` with a same-named
  top-level `f` — a combination V1 already supports (function merging is
  the feature's founding use case, TDD-00095).
- **Parse-time token/AST rewriting of sibling references**: no AST walker
  exists; a hand-rolled one over every node type is high-risk for a
  fallback three resolution points cover.
- **Dotted names (`module A.B.C`)**: requires multi-segment member
  resolution through the whole member-expression chain; deferred with a
  clean rejection, tracked for a V3.
