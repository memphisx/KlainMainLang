# ADR-00706: `/** @value */` flat value-type arrays (AoS inline element layout)

- **Relations**: Implements TDD-00134 (Stage 2); relates to TDD-00127 (array reference semantics)
- **Date**: 2026-09-04

## Context

An array of a fixed-shape object type is an array of pointers to
separately-heap-allocated elements (TDD-00127's reference model): N+1
allocations, pointer-chasing on every traversal, no cache locality, no
auto-vectorization. TDD-00134 Stage 2 calls for an opt-in flat layout — one
contiguous buffer with the element structs laid out inline (AoS, stride =
`StructSize`).

The layout cannot be inferred or defaulted: it changes aliasing semantics.
Two slots of a pointer array can hold the same object; inline slots are
value copies. So it is an explicit per-binding opt-in, resolving TDD-00134's
open marker question in favor of a JSDoc annotation (the same channel the
width overrides and `@free`/`@owned` already use) rather than `readonly`
reuse or a new `Vec<T>` type name.

## Investigation

- Storage shape: a flat array reuses the named-array storage exactly — a
  stable slot holding a pointer to a heap `{data, len}` header
  (`newArrayHeader`) — so `arrayDataLenSlots` and the `.length` read path
  work unchanged. Only the meaning of `data` differs: structs, not pointers.
- Type modeling: a new `Type.IsFlatArray` flag that is deliberately **not**
  `IsArray`. Every existing pointer-slot operation (HOFs, `sort`, `slice`,
  spread, destructuring, `Array.isArray` paths, …) type-gates on `IsArray`,
  so the flat type falls into those gates' rejection branches instead of
  silently corrupting the buffer. The supported surface gets explicit
  `IsFlatArray` branches. The element view carries a `Type.Inline` marker so
  the shared `loadArrayElem`/`storeArrayElem` chokepoints know the slot *is*
  the value.
- Read semantics: `arr[i]` yields an interior pointer (a view) rather than
  materializing a copy. That keeps `arr[i].x = 1`, `const v = arr[i]; v.x`
  and `for...of` field writes behaving like the reference model with zero
  copies; the cost is the documented Vec/C++-`vector` contract — a growth
  realloc (`push`) invalidates previously-taken views.
- One pre-existing dispatch trap surfaced: `isStringTy` treats any bare
  `ptr` type without an excluding flag as a string, so `ps[0]` on a flat
  array was intercepted by the string-charAt path in `emitIndex`
  (`emit_exprs_member.go`) before array indexing was ever reached, and the
  resulting "single-char string" then failed field access. Fixed in the
  predicate itself so every `isStringTy` catch-all site is covered at once.
- `-mm=auto`: `freeSymbol`'s generic-pointer branch would have freed the
  flat array's header while leaking the data buffer. The array branch
  (free data, reset header to `{null, 0}`) is exactly right for the flat
  layout too — one owned buffer, elements inline — so `IsFlatArray` joins
  that branch, and `symbolTypeFreeable` lists it explicitly.
- `-mm=gc` needs nothing: `@malloc`/`@realloc` are the shim-interposed
  symbols regular array growth already goes through.

## Decision

`/** @value */` on a `const`/`let` array declaration opts that binding into
the flat layout. V1 rules:

- Element type must be a fixed-shape plain object (interface/object-literal
  shape): classes (hidden tag/vtable, constructor identity), tuples, nested
  arrays, and dynamic values are rejected at the declaration.
- Construction is from an array literal (no spread elements). Each element
  expression is emitted and its fields `memcpy`'d into the slot — a value
  copy, so later mutation of a source object is not seen through the array.
- Supported operations: index read (view), index write (field-copy),
  `.length`, `for...of` (binds a per-element view), `.push` (realloc +
  field-copy append; may move the buffer, invalidating taken views).
- Everything else — HOFs, mutators beyond push, `slice`, spread,
  destructuring — is a compile-time rejection naming the supported surface.
- `@value` is mutually exclusive with `@free`/`@owned` and single-declarator
  only (parser-enforced). A `@value` array promoted to a global (read by
  other functions) is rejected for now.

## Implementation notes

- `codegen/llvm/types.go`: `IsFlatArray`, `Inline`, `FlatArrayType(elem)`.
- `ast/nodes.go` + `parser/parser_stmts.go`: `VarDeclaration.ValueArr` from
  the `/** @value */` JSDoc marker.
- `codegen/llvm/emit_arrays_flat.go` (new): declaration lowering
  (`emitFlatArrayVarDecl`), `for...of` (`emitForOfFlatArray`), `push`
  (`emitFlatArrayPush`), the `flatElemView`/`flatArrayElemOK` helpers.
- Wiring: `emit_exprs_vardecl.go` (route + non-array rejection),
  `emit_exprs_member.go` (`emitIndexPtr` flat branch, `Inline`-strided GEP,
  `.length`), `emit_arrays_core.go` (`loadArrayElem`/`storeArrayElem`
  `Inline` branches; flat-aware spread/destructuring rejection messages),
  `emit_stmts.go` (`for...of` dispatch), `emit_call.go` (push dispatch +
  method rejection), `emit_exprs_types.go` (inference),
  `emit_strings.go` (`isStringTy` exclusion), `emit_memory.go` (free path).
- The `Inline` marker is cleared by `loadArrayElem` when it hands back the
  view value, so downstream field access sees an ordinary object type.

## Side effects discovered

- The `isStringTy` bare-`ptr` catch-all remains a standing trap for any
  future `ptr`-shaped type: each new flag must be added to its exclusion
  list (`isForOfStringTy`'s comment already documents the same pattern).
