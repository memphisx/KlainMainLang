# ADR-00602: Nested function declarations inside a lexical block

- **Relations**: Implements [TDD-00152](../tdd/TDD-00152.md); lifts [TDD-00057](../tdd/TDD-00057.md)'s one-block-deeper restriction; composes with [ADR-00386](ADR-00386.md) (capturing nested declarations)
- **Date**: 2026-09-01

## Context

A `function` declared one or more blocks deeper than its enclosing
function/arrow body — inside an `if`/`for`/`while`/bare block — was a clean
compile error. Only declarations directly in the body's immediate statement list
were registered (by `pushNestedFuncScope`, run once per function/arrow/generator
body). Declaring a helper inside a conditional or loop is ordinary code, so the
restriction was worth lifting.

## Decision

Run the existing per-body nested-function mechanism at **block** granularity. The
`*ast.BlockStatement` emit case pushes a nested-func scope over the block's own
statements before emitting them and pops it at block exit — the same
`pushNestedFuncScope`/`popNestedFuncScope` pair a function body uses, with `nil`
params (a block introduces none). Because `if`/`for`/`while`/`do-while` bodies
and `try`/`catch`/`finally` blocks route their block through `emitStmt`, this one
site covers them; `emitSwitch` pushes one nested-func scope over all its cases
(a switch body is a single lexical block, so a case's function is visible across
cases). Block-scoped visibility falls out for free: `resolveFuncRef`
searches nested-func scopes innermost-first, and the block's scope is popped when
the block ends, so a block-local function shadows an outer one and is invisible
afterward (faithful strict-mode block scoping).

### For-loop variable capture rejected

A block-nested function closing over a C-style `for (let i …)` loop variable is
rejected with a clear message. The loop variable is one alloca reused across
iterations; a closure over it shares the counter cell and corrupts the loop
(observed: an infinite loop). `emitFor` records its init-declared names in a new
`activeForLoopVars` stack for the duration of the body; the block pre-scan rejects
a declaration whose free variables intersect that set. The check runs *before*
the capturing/non-capturing split — a loop variable isn't an
`enclosingCapturables` binding (it's declared in the for-init, not a body
statement), so it would otherwise be misclassified as non-capturing and emit a
broken direct call. Capturing a for-loop *body local*, an enclosing parameter, or
a `while` context is unaffected and works.

## Verification

New E2E tests: `TestE2ENestedFunctionInsideIfBlock` (declare + call in an `if`
block), `TestE2ENestedFunctionInsideBlockCaptures` (capture enclosing param +
block-local), `TestE2ENestedFunctionCapturingForLoopVarRejected` (clean
rejection). The existing nested-function, closure, loop, and generator suites
still pass; `TestE2ENestedFunctionInsideIfBlockRejected` (which asserted the old
error) is replaced by the positive test. Matches Node v26 on the working cases.
Built and verified on Mac (Apple Silicon).
