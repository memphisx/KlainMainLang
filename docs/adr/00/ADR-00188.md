# ADR-00188: `!=` / `!==` on floats use the unordered predicate so `NaN != NaN` is true

- **Relations**: Fixes the NaN-comparison bug flagged by [ADR-00166](ADR-00166.md)
- **Date**: 2026-08-13

## Context

`!=` and `!==` between float operands emitted LLVM's *ordered* not-equal predicate `fcmp one`. An ordered predicate returns **false** whenever either operand is NaN — so `NaN !== NaN` (and `NaN != x` for any `x`) evaluated to `false`, the opposite of JavaScript, where NaN's defining property is that it is unequal to everything including itself (`NaN !== NaN === true`). Flagged by the 2026-08-11 audit ([ADR-00166](ADR-00166.md)) as "`NaN`'s `!=`/`!==` comparisons are wrong."

This is a deferred shortcut, not a design choice: `one` was presumably chosen as the mechanical mirror of `oeq` without accounting for NaN's asymmetry between the equal and not-equal predicates.

## Investigation

- The float comparison map in `emitBinary` (`emit_exprs_operators.go`) mapped `<`/`>`/`<=`/`>=` to ordered `olt`/`ogt`/`ole`/`oge`, `==`/`===` to ordered `oeq`, and `!=`/`!==` to ordered `one`.
- Repro (Linux): `const x: float64 = NaN; x !== x` printed `false`; every `!=`/`!==` against NaN printed `false`.
- Working through each predicate against JS semantics:
  - **`==`/`===`** → `oeq` is correct: `NaN === NaN` is `false` in JS, and `oeq` returns false for any NaN operand. (Confirmed already printing `false`.)
  - **`<`/`>`/`<=`/`>=`** → ordered is correct: every relational comparison with NaN is `false` in JS, exactly what the ordered predicates give.
  - **`!=`/`!==`** → ordered `one` is *wrong*: it returns false for a NaN operand, but JS wants `true`. The unordered `une` returns true when either operand is NaN (and behaves identically to `one` for non-NaN operands), matching JS exactly.

Only `!=`/`!==` were wrong; the fix is isolated to those two entries.

## Decision

Map `!=`/`!==` to `fcmp une` (unordered not-equal) instead of `one`. `==`/`===` stay `oeq` and the relational operators stay ordered — all three already matched JS. Integer comparisons (`icmp ne`, etc.) are unaffected: NaN is a float-only value, so this never touches the default i64 `number` path.

## Verification (Linux, x86-64)

- `const x: float64 = NaN`: `x === x` → `false`, `x !== x` → `true`, `x !== 1.0` → `true`, `x < 1.0`/`x > 1.0`/`x >= 1.0` → `false`. A non-NaN float still compares normally (`2.5 !== 2.5` → `false`, `2.5 !== 3.5` → `true`).
- New E2E test `TestE2ENaNComparisons` in `tests/exprs_test.go`; a NaN-comparison section added to `examples/globals/globals.ts` (whose stale `1`/`0` boolean-print comments, left over from before [ADR-00183](ADR-00183.md), were corrected to `true`/`false` in passing).
- Full `go test ./...` green; `go vet` clean.
- `make conformance` re-run — see `docs/testing/CONFORMANCE-RESULTS.md`.
