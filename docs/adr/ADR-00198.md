# ADR-00198: Static-string `eval` fast path — compile a constant expression in place, no embedded engine

- **Relations**: Implements a subset of [TDD-00046](../tdd/TDD-00046.md) (the embedded-engine `eval`) ahead of and independent of the engine itself
- **Date**: 2026-08-13

## Context

[TDD-00046](../tdd/TDD-00046.md) scopes a full `eval` via an opt-in embedded
JS engine (quickjs-ng) for the general case, where the string is only known at
runtime. But when the argument is a **compile-time-constant string**, no engine
is needed: the string can be run through this compiler's own parser and codegen
— which also means such a test exercises *this* compiler rather than a bundled
interpreter, matching the whole conformance philosophy.

The opportunity is large: of the Test262 corpus, 1,536 files use `eval(`, and
**1,023** call it with a static string literal. Today `eval(...)` isn't
recognized at all — it falls through to `undefined function or closure 'eval'`.

## Investigation

`eval` is a **direct eval** by default: the code runs in the caller's scope and
its result is the completion value of the last statement. Restricting the fast
path to a string that parses as a **single expression** makes all three hard
parts disappear:

- **Scope**: emitting the parsed expression at the call site resolves its free
  variables against the enclosing scope — exactly direct eval's own rule.
- **Completion value**: an expression's completion value is just its value.
- **Declaration leakage / hoisting**: an expression introduces no bindings, so
  there is no `var`-into-caller-scope or strict-vs-sloppy scoping to model.

The critical correctness question was what to do with strings **outside** the
subset (dynamic, non-expression, or unparseable). The tempting move — emit a
runtime `throw` so `assert.throws(SyntaxError, () => eval("bad"))` "passes" — is
a false-positive trap: the conformance harness-shim's `assert.throws` catches
**any** thrown value (this compiler has no first-class error constructors to
compare a type against — `tools/conformance/harness-shim/assert.js`), so a
throw of any kind would spuriously satisfy every negative `eval` test. A
**compile error** instead keeps those negatives honestly failing (as
COMPILE_ERROR) while positive expression-evals genuinely pass — no
test-by-test hand-picking, and no way to inflate the number.

One residual, narrow false-positive path is accepted and noted: a negative test
whose eval'd string is a valid expression in *this* parser that also throws at
runtime for a real reason (e.g. a null dereference) would satisfy the shim's
type-blind `assert.throws`. Rare, and not worth gating on given the shim can't
check types anyway.

## Decision

Add `emitStaticEval` (`codegen/llvm/emit_eval.go`), dispatched from `emitCall`'s
identifier-callee branch **after** every user-binding lookup (so a user-defined
function named `eval` still wins):

1. Require exactly one argument that is a compile-time-constant string — a
   string literal or a no-substitution template literal (`staticStringValue`).
   Its `.Value` is already the decoded UTF-8 (escapes resolved at lex time,
   [ADR-00194](ADR-00194.md)) — exactly what a re-parse needs.
2. `parser.Parse` the string. Accept only a program that is exactly one
   `*ast.ExpressionStatement`; emit that expression and return its value.
3. Everything else — a dynamic argument, a parse failure, or a
   statement/declaration — is a clean compile error pointing at
   [TDD-00046](../tdd/TDD-00046.md).

## Implementation notes

- Files touched: `codegen/llvm/emit_call.go` (one dispatch line),
  `codegen/llvm/emit_eval.go` (new).
- No import cycle: `parser` does not import `codegen`, and `codegen` may import
  `parser`.
- **Known limitation — outer top-level references.** An eval'd expression that
  references a *top-level* binding (`var x = 1; eval("x + 1")`) fails to
  resolve, because the resolver mangles top-level declaration names
  ([TDD-00041](../tdd/TDD-00041.md)) before codegen but the freshly-parsed eval
  AST carries the original names — so the lookup misses and it's a clean
  compile error (never wrong output). Self-contained expressions
  (`eval("2 ** 10")`, `eval("'a' + 'b'")`) and references to non-mangled
  builtins work. Lifting this needs the eval expansion to run inside the
  resolver (splice-before-mangle) rather than at codegen time — a natural next
  stage, deferred.

## Verification

- Linux (x86-64). `go build`, `go vet ./...`, `go test ./...` all pass.
- Five E2E tests in `tests/eval_test.go` (static expression eval, eval-as-value,
  and clean rejection of a statement, invalid syntax, and a dynamic argument).
- New example `examples/globals/static_eval.ts`, runs with the expected output.
- Conformance: **5180 → 5225 (+45)**, no test regressions; the report's
  "wrongly-accepted" phase went 690 → 679 (some negative eval tests now fail
  honestly as compile errors rather than compiling), confirming no negative was
  flipped by a spurious throw.
