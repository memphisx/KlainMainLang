# ADR-00767: `child.unref()` / `child.ref()`

- **Relations**: Extends [ADR-00322](ADR-00322.md) (the ChildProcess event-loop keepalive) and [ADR-00765](ADR-00765.md) (`detached`, which `unref` usually pairs with); addresses a Windows-port follow-up ([TDD-00180](../tdd/TDD-00180.md))
- **Date**: 2026-09-07

## Context

A spawned child holds the event loop open until it exits: `__kml_cp_keepalive`
returns true while any child handle is live. Node lets a program opt out of that
with `child.unref()` — the child no longer keeps the parent's loop alive, so the
parent can exit without waiting for it (the basis, with `detached`, for launching
a process that outlives the launcher) — and `child.ref()` re-references it. Both
were missing; flagged in the Windows-port review as the natural companion to the
`detached` option just shipped.

## Decision

- A new cp-struct field 24 (`i64` unref flag, 0 = referenced). The struct grows to
  25 fields / 200 bytes; both `calloc` sites and `cpStructBytes` move together.
- `__kml_cp_keepalive` now counts a live child only when its unref flag is 0 — an
  unref()'d child no longer holds the loop open.
- `child.unref()` stores 1 into field 24; `child.ref()` stores 0. Both take no
  arguments and **return the ChildProcess**, so the calls chain (`spawn(...).unref()`),
  matching Node.

## Implementation notes

- The flag only affects keepalive; the child is otherwise untouched — its pipes
  still drain and it still finalizes (firing `'exit'`/`'close'`) *if* the loop
  happens to run for another reason. This matches Node: `unref` changes only
  whether the child keeps the loop alive, not the child itself.
- `unref` before the loop starts (the common case) means a program whose only
  pending work is that child exits immediately after `main`, leaving the child
  running — exactly Node's behaviour, and why it pairs with `detached`.

## Side effects discovered

None. This is the last of the ChildProcess handle-method gaps the Windows-port
review surfaced alongside the spawn options.

## Verification

- New E2E tests: `…Unref` (an unref()'d `sleep 3` child → the parent prints and
  exits at once, `'close'` never fires) and `…RefAfterUnref` (`ref()` re-references,
  so `'close'` fires). Full `TestE2EChildProcess*` green on Windows 11 and Docker
  Linux.
- Manual repros: **Windows 11 native** — unref'd child, program exits in ~0.13 s
  (not the child's 3 s); `ref()` after `unref()` makes it wait and fire `'close'`.
  **Docker Linux `klain-ci:latest`** — exits in ~0.04 s.
- `examples/child_process` updated. `go build`, `go vet ./codegen/...` clean.
  `make status`/`reference-check`/`conformance` at delivery.
