# ADR-01050: The entry module with a top-level `await` runs as a coroutine

- **Relations**: `Implements TDD-00224` (Stage 1); `Extends ADR-01044, ADR-01048`
- **Date**: 2026-09-21

## Context

[TDD-00224](../tdd/TDD-00224.md): the continuation of a top-level `await p` is a reaction on `p`, and its place among
`p`'s other reactions is observable. The main-stack wait (`@__kml_top_await`, TDD-00223 §1) noticed the promise's
state word after the loop turn that settled it, ahead of every reaction. The TDD's probe printed
`top-7,r1,r2,end,r1-child`; Node prints `r1,top-7,r1-child,r2,end`.

## Investigation

- `emitter.go` `EmitProgram` Pass 3 emits the prologue (argv, GC stack bottom, static initialisers), the top-level
  statements and the epilogue into one `allocas`/`body` builder pair, written out as `main()`.
- The epilogue reads only globals (`@__kml_process_exit_code`, the runtime's own state) — TDD open question 1: nothing
  moves. `%argc`/`%argv` are used only by the prologue and by the fixed lines written straight into `main()`'s text;
  top-level code reads `@__argv_ptr` / `@__process_argv_ptr`.
- TDD open question 2 (never free the module task's stack): unnecessary. Top-level bindings captured by a closure are
  heap-boxed at declaration (`hoistedCaptures`), simple scalars are module globals, so nothing points into the body's
  frame once it has returned. The module task is reclaimed by `@__kml_task_reclaim` like any other (ADR-01048);
  `TestE2EModuleTaskClosuresOutliveTheBody` covers it in both memory modes.
- The TDD put the Windows module stack at 1 MiB "matching the PE default". That is the MSVC linker's default; the
  mingw-w64 linker this compiler drives reserves 2 MiB (`objdump -p`: `SizeOfStackReserve 0x200000`). Measured with a
  non-optimisable recursion: depth 20000 passes on `main()`'s stack and overflowed a 1 MiB fiber. 2 MiB restores parity
  (both pass 20000, both overflow at 30000).
- The klain `http.listen` runs `@__kml_event_loop_run` inline. In a module task that would run the loop on the
  coroutine's own stack — the loop would switch contexts out from under itself, and every connection fiber would see a
  non-null `@__kml_current_task` and take the task branch of `@__kml_task_await_ready`. `const cfg = await load();
  http.listen(…)` is an ordinary program, so this had to work in Stage 1.

## Decision

- `programHasTopLevelAwait(prog)` (reflective walk of `prog.Body`, stopping at every function-like and class node)
  sets `e.moduleTask` before any emission. Islands are excluded (Stage 2); worker modules are emitted from their own
  bodies and are untouched. A program without a top-level await is emitted byte-for-byte as before.
- Body/epilogue split: `beginModuleBody` parks `main()`'s builders after the prologue; the top-level statements and
  the owed frees are emitted into a fresh pair and written as `define internal void @__kml_module_body(ptr)`;
  `endModuleBody` restores `main()`'s builders and emits
  `P = @__kml_task_alloc_promise(); @__kml_spawn_task_ex(@__kml_module_body, null, P, <stack>, @__kml_module_trampoline)`.
- `@__kml_spawn_task` became a two-line wrapper over `@__kml_spawn_task_ex(fn, args, promise, stackBytes, tramp)`.
  The task struct gains field 13, `stackBytes` (struct 112 B); the three GC stack-bottom sites
  (`@__kml_task_gc_restore`, the scheduler's resume, `@__kml_task_resume`) and the spawn read it instead of the
  `taskStackBytes` constant. Module stack: 8 MiB (POSIX), 2 MiB (Windows, as `ss_size` → the fiber's reserve).
- `@__kml_module_trampoline` has no catch-all: the task's jmpbuf stack is empty at entry, so an uncaught throw reaches
  `@__kml_throw_any`'s process-level uncaught path exactly as from `main()`.
- `emitAwait`'s plain-value branch takes the task path when `e.inModuleTask` (as it does for `e.isAsync`). The
  ADR-01044 tick branch stays for the two remaining non-task top levels — worker modules and islands — until Stage 2.
- `main()`: spawn, then the one event loop in a small loop of its own — if the loop returned because the module task
  asked for an inline run of it (`@__kml_module_run_loop`, which parks the module task in state 3 and sets
  `@__kml_module_wants_loop`), `main()` resumes the task with `@__kml_task_resume` and runs the loop again. The klain
  `http.listen` calls `@__kml_module_run_loop` instead of the loop when `e.moduleTask`; off the module task the helper
  is the plain inline run.
- Unsettled: after the loop, `P` still pending → the warning, `@__kml_process_exit_code = 13` and the `'exit'`
  listeners with 13 when the lifecycle runtime is in use, `exit(13)`. Verified against Node 24: warning first, then
  `exit 13 13` from the listener.

## Implementation notes

`codegen/llvm/emit_module_task.go` (new), `emitter.go` (flag, split, loop, check), `runtime_task.go` (field 13,
`spawn_task_ex`), `emit_async.go`, `emit_http.go`, `runtime_loop_turn.go` (message constant shared).

The struct's literal spellings elsewhere (`{ ptr, …, i64, ptr }` with 13 fields) were left alone: they index fields
0–12, whose offsets are unchanged.

## Side effects discovered

- A parked coroutine held the process open forever — [ADR-01051](ADR-01051.md). Blocked the unsettled path.
- `await finished(readable)` continued before the stream's `'end'` on the task path —
  [ADR-01052](ADR-01052.md). Surfaced by `examples/streams/node_stream.ts` once its top level became a task.
- Under `-mm=gc` a task's stack block is a collector allocation, so the module task's is an 8 MiB zeroed object;
  performance only, recorded in `docs/BACKLOG.md`.
- A stack overflow is a segfault here and a `RangeError` in Node — unchanged by this work.

## Verification

Windows 11 x64: `tests/module_task_test.go` (10 tests) and the five existing top-level-await tests pass. IR diff over
`examples/` between this compiler and one with `e.moduleTask` forced off: 322 identical, 19 differ, all 19 contain a
top-level await; their run output is identical under both except `node_stream.ts`, which changed from wrong to
Node's order with ADR-01052. Broader runs: see the session's final pass.
