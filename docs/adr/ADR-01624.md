# ADR-01624: A class method's destructured `any` parameter, and a captured `for (var …)` binding, compile

- **Relations**: Extends ADR-01619, TDD-00065
- **Date**: 2026-10-14

## Context

Test262's js lane had 49 files failing in clang: 48 in
`language/{statements,expressions}/class/dstr` ("'%t0' defined with type
'ptr' but expected 'i64'") and `staging/sm/String/thisv-error.js`
("Instruction does not dominate all uses"). They were never recorded as
deferred; the count had moved between commits on every platform.

## Investigation

- `class C { method({ poisoned }) {} }` under `-compat=js`: the parameter is
  `any`, stored as `i64` in its slot, but the method's prologue loaded it
  with `load ptr` (hard-coded) before unpacking the pattern. A function's
  prologue loads it with `patternParamIR`, and unpacks an `any` array pattern
  through `unpackDynArrayParam`, which the method path lacked as well.
- `for (var key of keys) { if (…) f(() => key); else g(() => key) }`: the
  loop head bound `key` to a plain slot; the first capturing closure promoted
  it to a heap cell inside the `then` block, and the `else` block's closure
  read that cell. The same held for a `for…in` head and a `for…of` over an
  `any` iterable. A `let`/`const` head was already right (a fresh cell per
  iteration).

## Decision

- A class method's or constructor's destructured parameter is loaded at its
  own type, and an `any` array pattern is unpacked dynamically, as a
  function's is.
- A captured `var` loop head (`for…of`, `for…of` over `any`, `for…in`) gets
  its cell in the entry block when the loop is entered (`boxLoopVar`, using
  `boxHoistedCapture` as every function-scoped `var` does); each iteration
  stores into it, so all closures share the one binding, as in JavaScript.

## Implementation notes

`codegen/llvm/emit_classes.go`, `emit_stmts.go` (`boxLoopVar`,
`defineForOfVar`, `emitForIn`), `emit_stmts_forof_any.go`; tests
`TestE2ECapturedLoopVarInBothArms`, `TestE2EClassMethodDestructuredAnyParam`
(`tests/func_test.go`).

## Side effects discovered

- A `for (var x of/in …)` binding is not visible after the loop (BACKLOG
  §0 168).
- An untyped array of closures cannot be called through under `-compat=js`
  (BACKLOG §0 169).

## Verification

Windows 11 (this machine): the tests, each case compared with Node 24; the
two `class/dstr` directories have no clang failure (216 / 1920 and
158 / 1920 passed, from 160 and 144); `thisv-error.js` compiles (it fails
at run time on `String.prototype` methods called on `null`).
