# ADR-00097: Multi-process clustering for `http.listen()`

- **Relations**: Implements [TDD-00025](../tdd/TDD-00025.md); Extends [ADR-00048](ADR-00048.md)/[ADR-00049](ADR-00049.md) (event loop, fiber-based connection concurrency); see also [ADR-00098](ADR-00098.md) (a pre-existing connection-handling bug found while testing this feature, unrelated to clustering itself but required to make it reliably testable)
- **Date**: 2026-08-04

## Context

`http.listen()`'s concurrency model is entirely single-process, single-thread: connections are handled *concurrently* via cooperative `ucontext_t` fibers (one per connection), but never *in parallel* — only one fiber's code ever executes at any given instant, on one CPU core. For a microservice (this project's own stated priority use case alongside CLI tools, per `CLAUDE.md`), that means a single `http.listen()` process can never use more than one core regardless of machine size. [TDD-00025](../tdd/TDD-00025.md), written and scoped in a prior session, already lays out the design: OS-process-level clustering via `fork()`, matching Node's `cluster` module in spirit but narrower — an option on `http.listen` itself rather than a general `cluster.fork()`/`child_process` primitive.

## Investigation

Verified every claim in TDD-00025 against the actual current code (not assumed from the design doc, which was dated the day before this work and could have drifted):

- `__kml_http_bind_and_listen` (`runtime_http.go:521-564` at the time) never applied `O_NONBLOCK` to the listening fd — confirmed via direct grep, only accepted connection fds got that treatment (`runtime_http.go:954-956`).
- `accept()`'s existing failure handling (`runtime_http.go:950-951`) already treats any `newfd < 0` as "continue the loop, no errno inspection" — this already behaves correctly as `EAGAIN`/`EWOULDBLOCK` handling once the listening fd itself becomes non-blocking, so no new branch was needed there.
- `grep -rn atfork codegen/llvm/` → zero matches: nothing registers `pthread_atfork`/`GC_atfork_*` for `-mm=gc` builds.
- `fork()`'s only existing call site (`execFileSync`, `runtime_process.go:161`) always `execvp()`s or `_exit()`s in the child — never falls back into ordinary emitted code, so it isn't reusable as-is for a cluster worker, which must keep running the whole runtime (event loop, fibers) independently post-fork.
- `emitHTTPListen` (`emit_http.go`) hard-required exactly 2 arguments, with no existing precedent for an optional trailing options object in that file — `fetch(url, init)` (`emit_fetch.go`, ADR-00074) turned out to be the right precedent to copy instead: any value whose inferred type has the right named field(s), via `FieldIndex` on the object literal's own inferred type, no shared interface required.
- Found and fixed one drift from the TDD's own text along the way: it cites `emitter.go:502` for the "`GC_INIT()` runs before `main()`'s first instruction" comment; the real line is `emitter.go:505` (the `GC_stackbottom` snapshot block is 503-515, gated by `e.isGCMode()` at line 509).
- **A latent duplicate-declaration bug**, found while adding `fork()`'s declaration for clustering's own use: `close()`/`read()`/`fork()` were each independently `declare`d inline by both `ensureExecFileSync` (`runtime_process.go`) and `ensureHTTPRuntime` (`runtime_http.go`), each guarded only against *itself* being called twice, not against the *other* function also declaring the same external symbol. Confirmed directly against `clang` (a two-line repro `.ll` with the same `declare` twice) that LLVM rejects this outright: `invalid redefinition of function`. This was harmless before this change (no program combining `execFileSync` and `http.listen` existed to trigger it), but adding `fork()` as a second, independent declare site for clustering would have introduced a live instance of exactly this bug the moment a program used both features.

## Decision

Implemented TDD-00025's design directly, staged manual-mode-first per the TDD's own leaning (its Open Questions section flags Boehm GC's `fork()` safety as the greater unverified risk, consistent with this project's history of GC/libc platform surprises — ADR-00051/ADR-00052/ADR-00080):

- **API**: `http.listen(port, handler, { workers: N })` — third argument optional; omitted or `N <= 1` is a byte-identical no-op (today's single-process behavior). `N`'s field is validated as a plain (non-float) `i64`-backed `number`.
- **Fork timing**: `__kml_http_cluster_fork(numWorkers)` is called in `emitHTTPListen` right after `__kml_http_bind_and_listen` succeeds and before `buildHTTPDispatcher`/any connection-fiber state exists — forking a live fiber's `ucontext_t`/stack was explicitly out of scope per the TDD.
- **Fan-out**: a flat "spawn N-1 additional peers" loop (not each child re-entering the loop, which would fork exponentially) — every process, original included, falls through into the identical `__kml_event_loop_run()` afterward. No dedicated non-serving primary in this V1 (matches the TDD's documented tradeoff).
- **Non-blocking listener**: the listening fd now gets the same `fcntl(F_GETFL)`/`fcntl(F_SETFL, ...|O_NONBLOCK)` treatment connection fds already got, applied right after `listen()` succeeds.
- **`cluster.isPrimary`/`cluster.workerId`**: new read-only globals, dispatched in `emit_exprs_member.go` alongside the existing `process`/`os`/`Math` pseudo-namespace checks, backed by `@__kml_cluster_worker_id` (set by the fork loop; `0` = original process). Both call `ensureHTTPClusterFork()` themselves too, so the backing global is declared even if `cluster.*` is read before any `http.listen(..., {workers})` call.
- **Declaration-dedup fix**: added three tiny dedicated `ensure*Decl()` helpers (`ensureForkDecl`/`ensureCloseDecl`/`ensureReadDecl`, `runtime_core.go`) guarded by their own flags, and pointed both `ensureExecFileSync` and `ensureHTTPRuntime`/`ensureHTTPClusterFork` at them instead of inlining the `declare`s directly — restores the `ensure*()` pattern's actual invariant (`CLAUDE.md`: "declared exactly once") for these three symbols specifically, not audited/fixed project-wide.
- **`-mm=gc` support deliberately deferred** (`pthread_atfork`/`GC_atfork_*` registration in `gcshim.c`) — tracked as a second pass; `manual` mode (no collector state, plain `malloc`/`free`, correctly duplicated by `fork()`'s ordinary copy-on-write semantics) is unconditionally safe and is what actually shipped here.
- **`fflush(NULL)` right before each `fork()`**: found while smoke-testing `examples/http/http_cluster.ts` — a top-level `console.log` startup banner printed once per worker instead of once, whenever stdout isn't a TTY (piped output, exactly how a real containerized deployment's log collector reads it — this project's own microservice target). Root cause: `fork()` copies libc's stdio buffers verbatim, so any output still sitting unflushed in stdout's buffer at fork time gets independently flushed by every worker that inherits the copy. `ensureFflushDecl` (`runtime_core.go`) declares `fflush`; `__kml_http_cluster_fork` calls `fflush(NULL)` (flushes every open output stream) immediately before its `fork()` call.

## Implementation notes

Files touched: `codegen/llvm/emit_http.go` (options parsing, cluster_fork call site, `emitClusterIsPrimary`/`emitClusterWorkerID`), `runtime_http.go` (`ensureHTTPClusterFork`, non-blocking listener fd), `runtime_core.go` (the four shared `ensure*Decl` helpers, including `ensureFflushDecl`), `runtime_process.go`/`emitter.go` (routing `execFileSync` through the shared helpers, new `usedForkDecl`/`usedCloseDecl`/`usedReadDecl`/`usedFflushDecl`/`usedHTTPClusterFork` flags), `emit_exprs_member.go` (`cluster.*` dispatch), `tests/http_test.go`, `examples/http/http_cluster.ts`.

`SO_REUSEPORT` deliberately not used, per the TDD — the shared listening fd is inherited via ordinary `fork()` fd-table-copy semantics, needing no new platform-specific socket option.

## Side effects discovered

Three, each documented and handled on its own rather than folded silently into this change:

- The `close`/`read`/`fork` duplicate-declaration bug above — fixed here as a small, targeted prerequisite (not a project-wide audit) since adding `fork()`'s declaration for clustering would otherwise have introduced a live instance of it.
- The stdout-duplicated-across-`fork()` bug above (`fflush(NULL)` fix) — found via this feature's own example, fixed as part of this same change since it's specific to the new `fork()` call site this feature adds.
- A real, pre-existing, unrelated bug in `buildHTTPDispatcher`'s connection dispatcher: `fdPtr`/`ctxPtrSlot` were computed once from a snapshot of `@__kml_conn_data` at fiber-entry and reused across every yield/resume cycle, dangling if `__kml_http_append_conn`'s `realloc()`-driven array growth moved the buffer while the fiber was suspended. Found while writing this feature's own E2E test (a concurrent-request test is exactly what exposes it — every existing test before this one only ever drove 1-2 connections at a time, sequentially or with one deliberately slow one). Confirmed to reproduce on the *unmodified*, pre-clustering codebase too (via `git stash`), so it's not a clustering-specific bug — see [ADR-00098](ADR-00098.md) for the fix, investigation, and verification. This feature's own clustering test would have been unreliable (intermittent hangs) without that fix, so ADR-00098 was written and merged as a prerequisite of this one, in the same session.

## Verification

- `go build -o klainmain .`, `go test ./...` — clean, no regressions.
- Manual smoke test: compiled a program calling `http.listen(8099, handler, { workers: 3 })`, ran it directly, fired 12 concurrent `curl` requests — confirmed 3 distinct worker PIDs (via `process.pid`) actually served them, and `cluster.workerId` matched (0/1/2) for each.
- Confirmed the two-argument form (`workers` omitted) forks nothing: `pgrep -P <server-pid>` showed no children, and `cluster.isPrimary`/`cluster.workerId` read `true`/`0`.
- New tests (`tests/http_test.go`): `TestE2EHTTPListenClusteringMultipleWorkerPIDs` (40 concurrent Go `http.Get` requests against a 3-worker cluster, asserts more than one distinct `process.pid` shows up in the responses — the real correctness check, since it requires `fork()` + the shared listening socket + non-blocking `accept()` to all work together, not just that the binary starts), `TestE2EHTTPListenClusteringDefaultIsSingleProcess` (pins `cluster.isPrimary`/`workerId` for the unchanged two-argument form), and `TestE2EHTTPListenClusteringFlushesStdoutBeforeFork` (pipes a 4-worker cluster's stdout — not a TTY, matching the bug's trigger condition — and asserts a pre-fork `console.log` appears exactly once; confirmed this test actually catches the regression by temporarily reverting the `fflush` call and re-running it, which failed as expected). `startHTTPClusterServer` (new test helper) kills the whole process group on cleanup, not just the one PID `exec.Command` started, since forked workers would otherwise survive test cleanup.
- `go test ./tests/ -run 'TestE2EHTTPListenClustering' -count=3` and `-run 'TestE2EHTTP' -count=3` — run repeatedly (concurrency bugs are non-deterministic) with zero flakes after ADR-00098's fix landed.
