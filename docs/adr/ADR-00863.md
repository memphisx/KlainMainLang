# ADR-00863: Windows CI green — gate the two fs-pool loop-ordering tests, portable temp path for req.pipe

- **Relations**: Extends ADR-00757; relates to TDD-00185, TDD-00186, TDD-00182/00183
- **Date**: 2026-09-11

## Context

The `Release` workflow's `test (windows-x64)` job had been failing since the
"fs thread pool" drop, while all four POSIX lanes (macOS/Linux, x64/arm64)
stayed green. `go test ./tests/...` on the Windows runner failed three tests:

- `TestE2EFsPromisesPooledReadDoesNotFreezeLoop`
- `TestE2EFsAsyncCallbackPooledNonBlocking`
- `TestE2EReqPipeToWriteStream`

## Investigation

Reproduced on the Windows dev box (MSYS2 UCRT64 clang 22.1.7):

- The two fs tests assert the libuv-style thread pool's **loop-ordering**
  guarantee — a concurrently-due `setTimeout(0)` fires *before* an awaited/
  callback read settles, because the read parks on a pool thread.
  `klainpool.c:19-23` states the pool is POSIX-first and Windows keeps the
  **inline (blocking) fs path** until the event-loop reactor lands
  (TDD-00182/00183, BACKLOG §2). On the inline path the read runs to completion
  before the timer, so the assertion (`got "blocked", want "nonblocking"`)
  cannot hold. Not a bug — an unimplemented-on-Windows guarantee.
- `TestE2EReqPipeToWriteStream` hardcoded `/tmp/klain_reqpipe_test_out.bin`. The
  compiled program is a native Windows binary, which resolves that POSIX literal
  to `C:\tmp\…`. The dev box happened to have `C:\tmp`; the CI runner does not.
  `fs.createWriteStream` does not create parent dirs, so the write errored,
  `'finish'` never fired, the handler hung, and the socket closed
  (`wsarecv: An existing connection was forcibly closed`). Confirmed by
  temporarily removing `C:\tmp` locally — the test then failed identically.
  (The adjacent `type_features_test.go` `/tmp/kml_mkp_e2e` case survives because
  it uses `mkdirSync(recursive:true)`, which creates `C:\tmp` itself.)

## Decision

- Add `skipInlineFsPoolOnWindows(t)` (alongside the existing Windows-skip
  helpers in `compiler_test.go`) and call it from the two loop-ordering tests.
  The functional pooled fs tests (`…PooledFullTable`, `…MutatorRejection`,
  binary writes, readdir) keep running on Windows — they assert results, not
  loop ordering, and pass on the inline path.
- Replace the req.pipe test's hardcoded `/tmp/` literal with
  `filepath.ToSlash(filepath.Join(tempDir(t), …))`, so it writes into the OS's
  real temp dir (`t.TempDir()`, i.e. `%TEMP%` on Windows) — auto-created and
  auto-cleaned.

## Implementation notes

- `tests/compiler_test.go`: new `skipInlineFsPoolOnWindows` helper.
- `tests/fs_async_test.go`: skip call added to the two tests.
- `tests/streams_test.go`: portable temp path; added `path/filepath` import.

When the Windows event-loop reactor + thread pool land (TDD-00182/00183), drop
the two skips — the loop-ordering guarantee will then hold on Windows too.

## Side effects discovered

None new. The Windows inline-fs limitation is the already-tracked structural
debt in BACKLOG §2.

## Verification

Windows dev box, MSYS2 UCRT64: `go vet ./tests/` clean; the three tests now
skip (2) / pass (1); the broader `TestE2EFs*`/`TestE2ECreate*Stream`/`ReqPipe`
selection passes (26.8s). POSIX lanes unaffected (skip helper is a no-op off
Windows).
