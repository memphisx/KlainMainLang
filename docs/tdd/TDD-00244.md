# TDD-00244: The runtime on libuv

- **Status**: In Progress
- **Date**: 2026-10-04

## Context

[TDD-00230](TDD-00230.md) Phase 4 settles what the event loop becomes (libuv
on hosted targets, behind a loop interface) and leaves the staging to its own
TDD, written once Phase 3's builtin declarations exist. They do.

The loop today is three loops:

- the full loop, `__kml_event_loop_run`, about 900 lines of IR text in
  `runtime_http.go`, emitted when a program uses tasks with timers, workers,
  child processes, fs.watch, the thread pool, net, IPC or a server;
- `__kml_timer_drain` (`timers.c`) for programs with timers only;
- `__kml_task_run_all` (`task.c`) for programs with tasks only.

The full loop rebuilds three 128-byte `fd_set` bitmaps every pass from the
listener, the connection table, nine per-subsystem `*_fdset_add` hooks and
`curl_multi_fdset`. It decides whether to exit from fourteen keep-alive
predicates, decides whether to block from a `forcezero` flag set by six
hooks and six conditions, folds five deadlines into the `select` timeout,
and fires one timer per pass from a flat array scanned linearly.

Because the loop cannot be re-entered, every wait outside it has a fallback:
`__kml_loop_turn` returns "cannot run" on a fiber, a task or a goroutine,
and its callers then drive a subset by hand (`timer_fire_next`,
`fetch_pump`, `usleep(200)`). `__kml_httpc_drive` and the synchronous XHR
path drive curl alone. Dynamic-import islands and Workers each run their
own copy of the loop.

On Windows, `win32io.c` (3,004 lines) emulates `select` over an IOCP, with
sockets remapped into fds 512–895.

The open bugs this produces are on [BACKLOG](../BACKLOG.md) §0. They include:

- an interval starving during a fetch await (5–7 ticks of 8 on the macOS
  runners);
- HTTP examples hanging about one run in 15;
- `fd_set` overflow at fd ≥ 1024;
- blocking TLS and HTTP/2 paths;
- a handler `await` that `nanosleep`s the server;
- a timer array that never shrinks;
- one due timer per pass;
- a signal lost when it arrives before `select()`;
- a fetch-await in a callback that spins.

Each is a property of this structure, not a local defect.

## Design

### The loop interface

One C header, `kml_loop.h`, is the only thing the rest of the runtime sees:

- `kml_loop_t *kml_loop_current(void)`: the thread's loop. The main thread
  and each Worker own one.
- Handles: `kml_timer`, `kml_poll` (an fd or socket with read/write
  interest), `kml_async` (cross-thread wake), `kml_signal`, `kml_process`,
  `kml_fs_event`, `kml_tcp`, `kml_udp`, `kml_idle`. Each has
  `start`/`stop`/`ref`/`unref`/`close`.
- `kml_loop_run(loop)`: runs until nothing ref'd remains.
  `kml_loop_run_once(loop, nowait)` serves a foreign main loop.
- `kml_work_queue(loop, work, after)`: the thread pool.
- `kml_loop_post(loop, fn, arg)`: any thread posts a callback to the loop.

The hosted backend (`loopsrc/loop_uv.c`) is a thin mapping onto libuv; only
it includes `uv.h`. A freestanding or WASI backend implements the same
header later ([TDD-00036](TDD-00036.md), [TDD-00048](TDD-00048.md)).

### One callback trampoline

Every libuv callback enters JavaScript through `kml_make_callback`, the
pool's existing entry point, which grows into Node's `MakeCallback`:

1. restore the async context captured at registration;
2. run the callback;
3. drain `process.nextTick`, then microtasks.

A Node-observable consequence: every due timer fires in one pass, with
microtasks drained between timers, as Node does since v11.

### Waiting never drives the loop

`uv_run` runs only on the thread's base stack, never from a fiber and never
re-entrantly. Every wait is a park:

- **Top-level code runs in a fiber.** The program's top-level code runs as
  the first task. A top-level `await` then parks like any other, and
  `__kml_top_await`'s idle exit becomes the loop running dry with the main
  task still parked (exit 13, as today).
- **The remaining waits park too.** `__kml_loop_turn`, the subset drives,
  `__kml_httpc_drive` and `spin()` are deleted. A synchronous API that Node
  implements synchronously (`execSync`, sync XHR) runs on its own private
  libuv loop, as Node's `spawnSync` does. That is the one sanctioned nested
  loop: it shares no handles with the main loop.

### Sources onto handles

| Today | libuv |
|---|---|
| timer array, `find_best`, `dofire` | one `uv_timer_t` per JS timer; `unref()` is `uv_unref` |
| keep-alive predicates | handle ref counts; a pinned loop is a ref'd `uv_async_t` |
| `forcezero` | `uv_idle_t` started while work is ready |
| deadline folds | each owner keeps its own `uv_timer_t` |
| thread pool wake socketpair | `uv_async_t`, with `uv_queue_work` for blocking work |
| `signal()` + `sig_pending` | `uv_signal_t` |
| SIGCHLD self-pipe, `waitpid` reap | `uv_spawn` / `uv_process_t` exit callback |
| fs.watch inotify/kqueue/Windows | `uv_fs_event_t` |
| `kml_tcp` table (net, dgram) | `uv_tcp_t`, `uv_udp_t`, `uv_pipe_t` |
| HTTP server listener + conn table | `uv_tcp_t` listener; one fiber per connection resumed from `uv_read` callbacks |
| `curl_multi_fdset` + `curl_multi_perform` | `CURLMOPT_SOCKETFUNCTION` → `uv_poll_t`, `CURLMOPT_TIMERFUNCTION` → `uv_timer_t`, `curl_multi_socket_action` |
| blocking `SSL_accept`/`SSL_connect` | memory BIOs fed from `uv_read`, flushed through `uv_write` |
| nghttp2 pumps | `nghttp2_session_mem_recv`/`mem_send` from the connection's read callback |
| `win32io.c` `select` emulation | libuv's Windows backend |
| dynamic-import islands' private loops | a task on the importer's loop |

### Migration: a bridge first, then one source at a time

Doing every source at once is not reviewable and leaves nothing runnable in
between. The order is:

- **Stage 0 — dependency and build.**
  - libuv joins the link inputs on every hosted target: `-luv`, or
    `libuv.a` for `--static`.
  - It goes in CI's apt and brew lists, the Docker images and the README
    requirements.
  - It is vendored as source for Sailfish and Android.
  - `loopsrc/loop_uv.c` compiles through the object cache.
- **Stage 1 — the loop core in C over libuv, with a select bridge.**
  - `__kml_event_loop_run`'s IR text is deleted. `kml_loop_run` replaces it,
    and the timers-only and tasks-only loops fold into it.
  - Timers move to `uv_timer_t` and the pool wake to `uv_async_t`.
  - Signals move to `uv_signal_t`.
  - Every source not yet ported keeps its `*_fdset_add`/`*_dispatch`/
    `*_keepalive` hooks, driven by a bridge:
    - a `uv_prepare_t` collects their fds into `uv_poll_t` handles (started,
      stopped and closed as the set changes, with no 1024 limit);
    - a `uv_check_t` runs their dispatchers with the ready set;
    - a ref'd `uv_idle_t` stands in for a true keep-alive predicate or for
      `forcezero`.
  - The bridge is the transitional fall-through. It is deleted with the last
    hook, not kept.
- **Stage 2 — waits park.** Top-level code runs in a fiber.
  `__kml_loop_turn`, `top_wait`, the subset drives and `__kml_httpc_drive`
  are deleted. Dynamic-import islands become tasks.
- **Stage 3 — curl through its socket API.** `curl_multi_fdset` and every
  synchronous curl drive go.
- **Stage 4 — net, dgram, child processes, fs.watch, IPC, Workers onto
  native handles.**
  - Their bridge hooks are deleted.
  - Workers post through `uv_async_t`.
- **Stage 5 — the HTTP server.**
  - The listener and connection table move onto `uv_tcp_t`, and the
    connection fibers resume from read callbacks.
  - TLS moves to memory BIOs.
  - HTTP/2 is driven per connection, with the deferred data provider and
    the stream fibers of [TDD-00218](TDD-00218.md) Stage 1.
  - The bridge is deleted.
- **Stage 6 — Windows.** `win32io.c`'s `select`, socket remapping and IOCP
  port go, and libuv's Windows backend replaces them. The fd-level
  `read`/`write` shims that `fs` still needs stay until `fs` moves to
  `uv_fs_*`.
- **Stage 7 — the loop inside a foreign main loop.** The webview and
  Sailfish pumps call `kml_loop_run_once(nowait)` on `uv_backend_fd`
  readiness ([TDD-00142](TDD-00142.md), [TDD-00144](TDD-00144.md)).

Errors carry libuv's negative `errno` on every host from Stage 4 on
([TDD-00180](TDD-00180.md)).

The GC interface (pinned references for native handles, root registration
for fiber stacks) is not part of this TDD. Its native-pointer rule applies
from Stage 4: a `uv_handle_t`'s `data` holds a handle-table index or a
registered root, never a raw managed pointer.

### Tests

These assert structure, not timing counts:

- an interval fires before a slow response arrives;
- no timer fires before its delay;
- a waiting process sleeps (low CPU);
- 2,000 open sockets work (no `fd_set` limit);
- a signal sent before the loop blocks is delivered.

Each runs throttled as well (`taskpolicy -b` on macOS, `nice -n 19` on Linux).
The `minTicks` threshold in `tests/event_loop_wait_test.go` is removed in
Stage 1.

## Open questions

- **Static libuv on Linux.** Ubuntu's `libuv1-dev` ships `libuv.a`, but
  `--static` may need `-ldl -lpthread` ordering. Settle it in Stage 0 on the
  test box.
- **The ucontext stack under libuv callbacks.** Resuming a fiber from inside
  a libuv callback switches stacks while `uv_run` is on the base stack; that
  is how Node-free coroutine runtimes on libuv (e.g. luvit's coroutines) work
  and is expected to be safe, but must be checked under ASan's
  fiber-switch annotations in Stage 1.
