# ADR-01026: Windows — the blocking-work thread pool wakes the reactor's completion port

- **Relations**: `Implements TDD-00185`, `TDD-00186` (on Windows); `Extends ADR-00773` (pool + per-loop wakeup), `ADR-00775` (pooled read stream), `ADR-01022` (the port is the reactor's one wait)
- **Date**: 2026-09-20

## Context

`fs.promises.*`, the `fs` callback forms and `fs.createReadStream` run on a libuv-style thread pool everywhere except Windows, where the emitters declined the pool (`targetGOOS() == "windows"`) and ran the blocking helper inline on the loop thread, handing back an already-settled Promise. A request handler awaiting `fs.promises.readFile` therefore froze the whole reactor for the read — the exact problem TDD-00185 exists to remove — and two loop-ordering tests were skipped on Windows (`skipInlineFsPoolOnWindows`).

The pool was POSIX-only for one reason: a worker wakes its loop by writing a byte to a socketpair whose read end sits in the loop's `select()` set. With the IOCP reactor complete (TDD-00183) that reason is gone.

## Investigation

- `threadpoolsrc/klainpool.c` is pthreads + C11 atomics + stdio; winpthreads provides the first (it already backs `Worker` and `klain:sync` on Windows). The only POSIX-specific part is the wakeup: `socketpair`/`fcntl`/`read`/`write` and `FD_SET` on the IR's Linux-ABI `fd_set`.
- The reactor already exports what a foreign thread needs: `__kml_win_reactor_port()` (the calling thread's port) and `__kml_win_port_wake(port)` (an addressed `PostQueuedCompletionStatus`), added for the child-exit watch. A wake packet makes `select()` return 0 with nothing ready, "exactly as a timeout would", and the loop takes its turn.
- `__kml_pool_dispatch` is called unconditionally every loop turn (`runtime_http.go`), not gated on the wakeup fd being readable, so a turn is all a completion needs.
- A wake posted before the loop reaches `select()` is not lost: the packet stays queued on the port and the drain at the top of `select()` picks it up.
- The pool's per-loop port is thread-local and a `Worker` runs its own loop with its own completion port; `loop_port()` runs on the submitting (loop) thread, so capturing `__kml_win_reactor_port()` there addresses the right reactor.
- The Windows fs helpers the thunks call (`win32fs.c`) keep no shared mutable state, so running them on pool threads is safe.

Keeping the socketpair on Windows (it would work — an owned socket is zero-read armed like any other) was rejected: it spends two descriptors of the 512-slot pool per loop and routes a wake through the network stack to reach a port that can be posted to directly.

## Decision

On Windows the pool's wakeup is a packet to the loop thread's completion port.

- `kml_loop_port` holds `win_port` (captured in `loop_port()`) instead of the `wake_r`/`wake_w` pair.
- `push_completion` calls `__kml_win_port_wake(p->win_port)`.
- `__kml_pool_fdset_add` adds nothing (the port is always waited on); `__kml_pool_dispatch` has no bytes to drain.
- The two emitter gates are removed: `emitFsPromisePooled` and `emitFsCreateReadStream` take the pooled path on every host. The eager read-to-EOF stream helper (`__kml_fs_read_stream`), which only the Windows branch still used, is deleted.
- `--static` on Windows links the static winpthread archive for the pool, as it does for `klain:sync` (ADR-00772), so a pooled program stays self-contained.

## Implementation notes

`codegen/llvm/threadpoolsrc/klainpool.c` (`#ifdef _WIN32` around the wakeup only), `emit_fs_async.go`, `emit_fs_stream.go`, `runtime_fs_stream.go`, `embedded_c.go`, `emitter.go` (dead flag). Tests: `skipInlineFsPoolOnWindows` and its two call sites removed.

## Side effects discovered

None.

## Verification

Windows 11 (26200), MSYS2 UCRT64 clang: all `TestE2EFs*` pass (99), including the formerly skipped `TestE2EFsPromisesPooledReadDoesNotFreezeLoop` and `TestE2EFsAsyncCallbackPooledNonBlocking`, and `TestE2EFsCreateReadStreamPooledOrderedNonBlocking` now on the pooled stream. A pooled program built with `--static` runs and imports no `libwinpthread` DLL. Linux: the full `./tests` package passes in Docker (`klain-ci`, Go 1.27.1 + clang 19), 0 failures. macOS: not run — no macOS machine is reachable from the box this was written on, and the POSIX path is unchanged, so CI is the check.
