# ADR-00521: Width-aware `klain:tui` painter — `wcwidth` + grapheme cells

- **Relations**: Extends ADR-00519; Implements TDD-00150 (Stage 1 polish)
- **Date**: 2026-08-30

## Context

The Stage 1 `klain:tui` painter (ADR-00519) decoded UTF-8 to code points but treated every code point as one grid column. Wide East-Asian and emoji glyphs actually occupy two terminal columns, and combining marks occupy zero, so any content with such characters drifted out of alignment: a bordered box containing CJK text had its right border land in the wrong column, `space-between` rows mis-justified, and `List`/`TextInput` widths were wrong. This was the standing caveat on the `Text` row of `docs/status/data/terminal-ui.json`. Faithfulness-first (a terminal's own `wcwidth` behaviour is observable) makes this a fidelity bug to close, not a divergence to keep.

## Investigation

`codegen/llvm/tui.go` computed layout and paint in code-point counts throughout: `kmltui_measure` summed `kmltui_decode` output length, `kmltui_wrap` advanced its column counter by 1 per code point, and the cell grid (`Cell{ unsigned int ch; ... }`) held exactly one code point per cell with the diff loop advancing the cursor by one column per emitted cell. There was no `wcwidth`. The 4-byte encoder (`kmltui_putcp`) also only emitted up to 3 bytes, so astral-plane emoji (`U+1F300`+) were mis-encoded.

## Decision

Make the whole painter reason in display columns:

- Add a standard `wcwidth` (Markus Kuhn's interval table) — `kmltui_wcwidth(cp)` returns 0 for combining marks / joiners / variation selectors / control chars, 2 for East-Asian-wide ranges and the emoji blocks (`U+1F300..U+1FAFF`, CJK, Hangul, fullwidth forms), 1 otherwise.
- Change `Cell` to hold a whole grapheme as UTF-8 bytes plus its display width: `{ char g[16]; unsigned char nb, w; short fg, bg, attr; }`. `w==2` is a wide lead whose next column is a `w==0` continuation cell; `w==0` cells are skipped by the diff loop (the wide glyph already covered that column and advanced the cursor by 2).
- Paint text through `paint_cps`, which groups a base code point with its trailing zero-width combining marks into one cell and advances the cursor by the base's column width.
- Wrapping (`kmltui_wrap`) and measurement (`kmltui_measure`, via new `kmltui_colwidth`) now count columns, so wide glyphs break lines and size boxes correctly.
- Add a proper 4-byte UTF-8 encoder (`kmltui_enc`) used by both paint and the emit path.

Rejected: storing one code point per cell and special-casing width only at emit time — the diff loop needs per-cell width to place the cursor and to know which columns a wide glyph shadows, so width has to live in the grid.

## Implementation notes

All changes are confined to the embedded C runtime in `codegen/llvm/tui.go`; the `__kml_tui_*` builder ABI the generated IR calls is unchanged, so `emit_tui.go`/`emit_tui_props.go` are untouched. The wide-glyph continuation-cell scheme keeps the diff painter correct across frames: replacing a wide glyph with two narrow ones (or vice-versa) diffs both columns because the continuation cell's `w`/bytes differ from the replacement.

## Side effects discovered

ZWJ grapheme clusters (flag, family, skin-tone emoji sequences) still paint as their constituent wide glyphs rather than one cluster — full grapheme-cluster segmentation is out of scope for Stage 1 and is recorded as the remaining caveat on the `Text` status row.

## Verification

- New E2E test `TestE2ETuiWideCharWidth` (`tests/tui_test.go`): a width-6 `space-between` row with `世` (width 2) and `X` leaves exactly a 3-column gap — a one-column-per-cp painter would leave 4.
- Existing `TestE2ETui*` render/justify tests still pass; all four `examples/tui/*.ts` still compile.
- Manual repro on macOS (Apple Silicon): a bordered column of CJK / emoji / combining-mark / mixed `List` content keeps its right border aligned across every row; combining marks (`é` = `e`+U+0301) fold onto their base.
