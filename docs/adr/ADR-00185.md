# ADR-00185: Class expressions (TDD-00063 Stage 4)

- **Relations**: `Implements TDD-00063` (Stage 4, the final stage). `Extends ADR-00184`. The nominal-binding posture mirrors [ADR-00168](ADR-00168.md)/[ADR-00178](ADR-00178.md) (function expressions, TDD-00060).
- **Date**: 2026-08-13

## Context

[TDD-00063](../tdd/TDD-00063.md) Stage 4 is class expressions — `const C = class {…}`. Before this, a `class` keyword in expression position was `unexpected token class in expression`, the single largest first-error bucket in the whole class corpus (2,542 files). It is the architecturally novel stage: unlike function expressions (functions here are already first-class closure values, so a function expression evaluates to a real value), **classes are compile-time nominal types with no runtime constructor value** — so a class expression cannot produce a value to hand around, and the scope has to be shaped around that.

## Investigation

- `parseClassDecl` already parses the whole class body (Stages 1–3 members included) and already accepts an anonymous class via its `defaultName` parameter (the `export default class {}` hook). So the parser side is a thin wrapper.
- The overwhelming majority of the corpus's class-expression tests do `var C = class {…}; new C()` or probe the body's members — i.e. they use the expression as a **binding**, then reference it by name. A binding is exactly what the nominal model *can* represent: registering the class under the LHS name is indistinguishable from a `class C {…}` declaration for every downstream purpose (`new C()`, `C` as a type, `extends C`).
- `registerClasses`/`emitClassDecl` drive off top-level `*ast.ClassDeclaration` statements. So if a top-level `const C = class {…}` is rewritten to a `class C {…}` declaration *before* registration, the entire existing pipeline (Stages 1–3, inheritance, vtables, visibility) applies with zero new codegen.

## Decision

**V1: compile-time nominal binding, binding-position only.** A `class` in expression position parses (via `parseClassDecl`) into a new `ast.ClassExpression` node wrapping the parsed declaration. A codegen pre-pass (`rewriteTopLevelClassExpressions`, run first in `EmitProgram`) rewrites each top-level `const/let/var X = class {…}` into a `class X {…}` declaration in place — the LHS name wins. Everything downstream is unchanged.

Anything that is *not* a top-level single-declarator binding — a class expression used as an argument, a return value, a nested/non-top-level binding, an `export`-wrapped or multi-declarator binding — is left as a `ClassExpression` node and reaches `emitExpr`, which is a clean, specific rejection (there is no runtime constructor value to produce).

Scope cuts, each a clean rejection, following the TDD:
- **Named-expression self-reference**: the internal name of `class D {…}` is dropped in favour of the LHS name, so a body self-reference to `D` (where `D` ≠ the LHS name) is a clean "unknown class" error. Same-name (`const C = class C {…}`) and anonymous both work fully. The self-reference subset mirrors [ADR-00168](ADR-00168.md)'s V1 deferral for named function expressions.
- **`extends <expression>`**: `parseClassDecl` only parses `extends <Ident>`, so a non-identifier base was never accepted — unchanged.

## Implementation notes

- New `ast.ClassExpression{Decl *ClassDeclaration}`; parser `case lexer.CLASS` in `parsePrimary` (mirroring `case lexer.FUNCTION`), passing a placeholder `defaultName` that the rewrite always overwrites. `rewriteTopLevelClassExpressions` in `emitter.go`; the `emitExpr` rejection case.
- Because the rewrite produces an ordinary `ClassDeclaration`, a class expression **automatically inherits every Stage 1–3 member** — field initializers, async methods, generator methods, computed names — with no extra wiring. Verified directly (a class expression with a generator method iterates via `for...of`).
- The binding is nominal: `C` is a class *name*, not a runtime `const`. Code that uses `C` as a value rather than `new C()` / a type is out of V1 scope (there is no first-class class value here) — the same boundary the whole feature is shaped around.

## Side effects discovered

- A class-expression example initially used `this.items.push(n)` on an array field and hit the pre-existing `this.field.push(...)` limitation (a known, separately-tracked bug, [LANGUAGE-CONSTRUCTS.md](../status/LANGUAGE-CONSTRUCTS.md)'s Array row) — the example was rewritten to avoid it; not a class-expression issue.
- Integer division default (`number` → `i64`, so `550/100 === 5`) surfaced in the same example — the documented `number`-default behavior, avoided in the example by dividing evenly.

- Full `go test ./...` green; `go vet ./...` clean.
- `examples/classes/classes.ts` extended with a class-expression section; compiles and runs with the documented output.
- `make conformance` re-run — see `docs/testing/CONFORMANCE-RESULTS.md`.

With Stage 4 done, [TDD-00063](../tdd/TDD-00063.md)'s core surface is complete (Stages 1–4); the deliberately deferred subsets — static/async generator methods, well-known-symbol computed keys, `extends <expression>`, class-expression runtime values and named self-reference — remain out of V1 scope, each a clean rejection.
