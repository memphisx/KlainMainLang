# TDD-00219: multi-server + Worker/cluster in one program

- **Status**: Implemented
- **Notes**: Option 1 (unify on the non-blocking reactor) shipped — [ADR-00989](../adr/ADR-00989.md).
- **Date**: 2026-09-16

## Context

TDD-00191 gave a program multiple concurrent HTTP servers (plain/TLS/h2c/h2-TLS,
each with its own dispatcher and an entry in the extra-listener table). Separately,
`http.listen(..., { workers: N })` (klain:http) forks `N` processes sharing one
listening socket for cross-core parallelism. The two **cannot be combined**: an
additional `createServer` alongside a `{ workers }` server is a clean compile-time
rejection (`emit_http.go`, the `usedWorkerRuntime` guard).

This was the last item in the `http.createServer` "edges" backlog bullet (the
timeouts and `highWaterMark` shipped as TDD-00217/ADR-00983-00984); it is a
distinct architectural decision, tracked here so the bullet resolves.

## Why they don't compose

They are two different reactor models:

- **Cluster** (`{ workers }`) uses klain:http's *single, blocking* server: each
  forked worker runs one listening socket and polls a shared `MAP_SHARED`
  close/force-close flag region in its reactor (`runtime_http.go`,
  `__kml_cluster_close_flag`). `http.listen` blocks until drain; the fork happens
  before the accept loop.
- **Multi-server** (TDD-00191) uses the *non-blocking* Node model: `listen()`
  returns immediately, and every additional listener is driven from the shared
  `select()` loop via the extra-listener table.

A single program mixing them would need one reactor that is simultaneously the
blocking cluster loop and the non-blocking multi-listener loop, with the
`fork()`-shared listen socket(s) and the extra-listener table coexisting. TDD-00191
Stage 4's Open Questions flag this as an unresolved design choice, not merely
unimplemented work.

## Options

1. **Unify on the non-blocking reactor.** Make the cluster path also use the
   extra-listener/`listen`-returns model: `fork()` after building the listener
   table, each worker running the same non-blocking `select()` loop over all
   listeners, the shared close flag folded into that loop (it already polls it —
   `ccpoll`). The blocking `http.listen` becomes a thin wrapper that forks then
   runs the loop. Highest fidelity; the largest change to the cluster lifecycle.
2. **Per-listener worker pools.** Keep the models separate but allow one program
   to declare workers on *one* server and run the others single-process in the
   primary. Simpler, but a partial answer (the extra servers get no cross-core
   parallelism) and an odd mental model.
3. **Leave rejected (status quo).** The rejection is honest and the two use cases
   (a cluster of one service vs. several distinct services in one process) rarely
   coincide. Documented as an intentional divergence.

Leaning option 1 if pursued, but the cost/benefit is weak: the combination is
uncommon and both halves work well in isolation.

## Open questions

- Does a `fork()`ed worker correctly inherit and re-drive *every* listener in the
  extra-listener table (fds, TLS contexts, h2 vtables), or only the primary
  socket? TLS `SSL_CTX` sharing across `fork()` needs checking.
- How `cluster.isPrimary`/`workerId` branching interacts with per-server
  `.on('request')` handlers bound in the parent before the fork.
- Whether the connection-timeout sweep (TDD-00217) and `'close'`/`'clientError'`
  events (TDD-00215), both primary-server-only today, extend across workers.
