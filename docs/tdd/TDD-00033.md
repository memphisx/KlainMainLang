# TDD-00033: Direct hardware/framebuffer access (placeholder)

- **Status**: Not Started
- **Date**: 2026-08-06

## Context

A deliberately shallow **bootstrapping placeholder**, in the same spirit as [TDD-00032](TDD-00032.md) — recorded so the scoping thinking from researching UI directions isn't lost, not a committed design. This is the third of three UI directions considered together: terminal UI ([TDD-00031](TDD-00031.md), ready for real design work now), GUI via native toolkit bindings ([TDD-00032](TDD-00032.md), blocked on a general-FFI prerequisite), and this one — bypassing a windowing toolkit entirely and drawing straight to a Linux framebuffer device (`/dev/fb0`) or reading raw input events (`/dev/input/eventN`), the model a kiosk app or a minimal display server would use.

Research found this direction is architecturally *smaller* than GUI-via-bindings in one specific way: it dodges the hardest part of that problem entirely. A framebuffer is just a memory-mapped region of bytes representing pixels — no callback-driven event loop, no vtables, no C++ ABI, no widget toolkit. Writing to it is `open()` + `mmap()` + writing pixel bytes directly, and this compiler already shipped most of the necessary plumbing this session: binary-safe `fs.read`/`fs.write` and `ArrayBuffer`/TypedArrays. Reading raw input (`/dev/input/eventN`) is pure polling — read a fixed-size struct in a loop — which fits this compiler's existing synchronous-by-default style far better than an event-driven GUI API would.

The real complication isn't the primitives — it's that this would be the **first feature in this project that can't exist on both development machines at all**, not just "unverified on one." `CLAUDE.md`'s platform-parity standing rule has, until now, always been about verifying a claim on both the Linux x86-64 box and the Apple Silicon Mac — every past cross-platform bug (`ucontext_t`, `GC_stackbottom`, `os.cpus()`'s Darwin path) was a case of *both* platforms being targeted, one just turning out buggy or unverified. Direct framebuffer/DRM access has no macOS equivalent whatsoever — Apple removed that access model entirely; the nearest macOS equivalent would be Metal/Cocoa framework bindings, an entirely different (and likely harder — Objective-C runtime, not plain C) problem, not a platform-specific implementation of the same feature.

## Design

Not scoped — deliberately. What a real design pass would need to resolve first, before any implementation detail:

- **Whether a Linux-only feature is acceptable for this project at all**, given the dual-machine development model this project has followed throughout. This is a product-direction question, not a technical one, and should be settled explicitly (not by default/omission) before any further design work here — likely the very first thing a real TDD for this should open with.
- **Framebuffer (`/dev/fb0`, simplest) vs. DRM/KMS (`libdrm`, the modern replacement — more capable, more complex, and itself a library-binding problem closer in shape to [TDD-00032](TDD-00032.md) than to a bare syscall).** The fbdev approach is simpler and syscall-only (no new library dependency); DRM/KMS is where modern Linux is actually headed (fbdev is legacy/being phased out on some distros) but reintroduces a real library-binding question.
- **Raw input handling** (`/dev/input/eventN` — reading `struct input_event` records) needs root or being in the right group by default on most distros — a real deployment/permissions question for anything beyond a root-run kiosk process, worth surfacing early rather than discovering at implementation time.

## Prerequisites

| Dependency | Status | Notes |
|---|---|---|
| Binary-safe file I/O | ✅ built | `fs.readFileSync`/`writeFileSync` binary-safe support shipped this session — directly reusable for framebuffer byte writes. |
| `ArrayBuffer`/TypedArrays | ✅ built | [TDD-00018](TDD-00018.md) — a natural fit for a raw pixel buffer. |
| `mmap`/`munmap` | ❌ missing | Framebuffer writes are conventionally memory-mapped rather than `write()`-per-frame for performance; no binding exists today. |
| `ioctl` (e.g. `FBIOGET_VSCREENINFO` for screen geometry) | ❌ missing | Same missing primitive [TDD-00031](TDD-00031.md) also needs (for `TIOCGWINSZ`) — likely worth building as one shared, general `ioctl` binding rather than two narrow ones if both TDDs are ever picked up. |
| A settled position on Linux-only scope | ❌ not decided | See Design above — the real blocker, not a missing primitive. |

## Open questions

Everything above is open. If this is ever picked up, the very first step should be the platform-scope question in Design, since it changes whether this is worth a real TDD at all versus staying a permanently-shelved placeholder.
