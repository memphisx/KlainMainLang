# ADR-00966: `url.searchParams` is a live link, not a snapshot

- **Relations**: Implements TDD-00203, Extends ADR-00572
- **Date**: 2026-09-15

## Context

TDD-00203 left one open question: is `URL.searchParams` live? WHATWG says yes —
mutating it writes back into `url.search`/`url.href` — but the field was a
detached snapshot. `url.searchParams.append(...)` changed the params object while
`url.search` and `url.href` kept their original query. BACKLOG §3 tracked it.

Repro (before — all three query readbacks were stale):

```ts
const u = new URL("http://example.com/p?a=1")
u.searchParams.append("b", "2")
u.search      // was "?a=1", Node: "?a=1&b=2"
u.href        // was "…/p?a=1", Node: "…/p?a=1&b=2"
```

## Investigation

The URL object stores each component (`search`, `href`, …) as a materialized
string field plus an independent `searchParams` handle
(`emit_url.go` construction / `deriveURLFieldsIntoObject`). The handle is the
opaque `__kml_usp_*` pair-list (`urlsearchparams.c`); nothing linked it back to
its URL, so a mutation had nowhere to propagate.

The `url.search = …` component setter already re-derives every field from a curl
handle seeded with the current href plus the new query
(`emitURLComponentSet` → `deriveURLFieldsIntoObject`). The writeback needed is
exactly that, driven from a searchParams mutation instead of a `search=`
assignment — which requires the handle to know its owning URL.

## Decision

Give the `__kml_usp` struct an opaque `void *owner` back-pointer (null for a
standalone `URLSearchParams`), set to the URL object whenever a URL builds or
re-derives its `searchParams` handle. After every mutating op
(`append`/`set`/`delete`/`sort`), emit a call to a once-emitted helper
`@__kml_url_usp_writeback(usp)` that:

1. reads `owner`; a null owner (standalone params) returns immediately — the
   call is a cheap no-op there;
2. serializes the pairs (`__kml_usp_to_string`), seeds a fresh curl handle from
   the owner's current `href`, applies the new query, and re-derives the URL's
   string fields.

Re-derivation runs in a new `rebuildSearchParams=false` mode of
`deriveURLFieldsIntoObject` that refreshes `search`/`href`/`query`/`path`/… but
does **not** rebuild the `searchParams` handle — so the live handle the caller
just mutated (and any alias like `const sp = url.searchParams`) keeps its
identity. Construction and the component setters keep `rebuildSearchParams=true`
and now also `__kml_usp_set_owner` the fresh handle.

The C runtime never dereferences `owner`; the emitted helper does, since it
alone knows the URL struct layout — keeping layout knowledge out of the C file.

## Implementation notes

- Also fixed an adjacent derivation bug: a present-but-empty query (a bare `?`,
  or the result of deleting the last pair) now yields `search == ""` rather than
  `"?"`, matching WHATWG/Node — the `search` derivation requires a non-empty
  query before prepending `?`.
- `emitURLUSPWriteback` is called unconditionally after each mutation; the
  runtime owner check keeps standalone params free of URL machinery.

## Side effects discovered

- `new URL("http://h.com/?")` keeps `href` as `http://h.com/` (curl drops the
  empty `?`) where Node preserves the trailing `?`; `search` is correctly `""`.
  A pre-existing curl-serialization nit, unrelated to the live link — left as is.
- `url.searchParams === url.searchParams` identity across separate reads is not
  guaranteed the way Node caches it, but a mutation preserves the mutated
  handle's identity, which is what observable code relies on.
