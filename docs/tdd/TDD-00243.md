# TDD-00243: Typed arrays' `buffer` and `byteOffset`

- **Status**: Implemented
- **Date**: 2026-10-03

## Context

A typed array here is a plain array: a `{data, len}` header flagged
`IsTypedArray` (TDD-00018). A view over an ArrayBuffer points `data` into the
buffer's bytes (`base + byteOffset`), so writes through it already alias the
buffer. What it cannot answer is where it came from:
- `ta.buffer` does not compile, and neither does `ta.byteOffset`;
- `new DataView(ta.buffer, ta.byteOffset, ta.byteLength)` is the standard
  idiom for reading a Buffer or Uint8Array as binary, and it is blocked;
- so is moving DataView to a TS global module (TDD-00230 P3.4), whose class
  reads through `new Uint8Array(buffer, byteOffset, byteLength)` and must
  answer `dv.buffer`;
- a view over a SharedArrayBuffer cannot cross a worker boundary as a view,
  since the receiver cannot recover the buffer it shares.

This is the typed-array half of TDD-00230 P3.3 (one representation per type).

## Design

Node's semantics to match:
- every typed array has a buffer: a view returns the buffer it was made
  over;
- an array that allocated its own storage (`new Uint8Array(4)`,
  `Buffer.from('x')`) returns an ArrayBuffer created on first access and
  the same one after that (`ta.buffer === ta.buffer`);
- `byteOffset` is the view's start within that buffer, and `subarray`
  shares the parent's buffer with the summed offset.

### Option A: widen the typed-array header

Make a typed array's header `{data, len, buf, byteOffset}`.
- Every site that mints an array header would have to mint the wide form
  for a typed array. That includes the re-boxing paths ADR-01011 enumerates:
  element and field stores, HOF callbacks, Map values and returns.
- A header minted by generic array code (a typed array passed through an
  `any[]` or a generic `T[]`) would come out narrow. Reading word 2 of it is
  out of bounds.
- That is a representation change across the array machinery for a property
  few programs read.

### Option B: a runtime view registry (recommended)

The registry maps a data address to `(buffer header, byte offset)`:
- **Registration.** `new T(buffer, off, len)` and `subarray` register the
  view's data address with its buffer and offset. `subarray` copies the
  parent's entry and adds its own offset.
- **Lookup.** `.buffer` and `.byteOffset` look up the data address. A
  miss is an array with its own storage. The runtime then makes an
  ArrayBuffer header `{byteLength, data}` that aliases the bytes, registers
  it at offset 0 and returns it, so later reads return the same buffer.
- **Representation.** The array keeps its two-word header, so every
  existing path stays as it is. The cost lands only on view construction,
  `subarray` and the two property reads.
- **Key collisions.** Two views can share a data address (`new
  Uint8Array(b, 0)` and `new Uint16Array(b, 0)`) but never with different
  buffers, since an address lies in one allocation. One entry per address
  is enough.

**Lifetime.** Storage is never freed explicitly, so under `-mm=manual` and
`-mm=auto` an entry can never go stale. Under `-mm=gc`:
- the registry's table is allocated atomic, so it does not keep views or
  buffers alive;
- each entry's key and buffer fields are registered as disappearing links
  (`GC_general_register_disappearing_link`), so a collected buffer clears
  its entry before its address can be reused;
- a cleared entry is a miss, the own-storage path.

**Threads.** A SharedArrayBuffer's views are made on several threads, so
the registry takes a lock. An open-addressed table behind a mutex is
enough: lookups happen on property reads, not on element access.

### Downstream

- `ta.buffer`, `ta.byteOffset` and Buffer's `buffer`/`byteOffset` compile
  through the registry.
- DataView moves to a TS class over `Uint8Array` (P3.4), and its `IsDataView`
  flag and `emit_dataview.go` are deleted.
- A view posted to a worker sends `(buffer, byteOffset, length)` when the
  buffer is shared, and the receiver re-registers it.

Option B shipped in [ADR-01351](../adr/ADR-01351.md) (registry, property
reads, `subarray`, the `any` path), and DataView in TS in
[ADR-01352](../adr/ADR-01352.md), and worker view transfer in
[ADR-01357](../adr/ADR-01357.md).

## Open questions

- A growable buffer's `resize` can move its bytes. A registered view then
  holds a stale data address. This is already a caveat: views do not
  length-track a resize. Re-registering on `resize` is left to the
  implementation.
